## Background

Sibling projects recorded how a swarm of agents can close hundreds of work items while the product serves figures
from a stand-in. The defence is a definition of "implemented" that a program can evaluate, applied per
capability, with every shortfall named. This bead makes that definition data: one record per capability, eight
Boolean conditions and two riders, a computed status, and a verb through which an agent asks what is real.

A capability is implemented only when all eight hold. Otherwise it MUST be described as partial, with the
missing items named.

1. Code exists in the crate the design maps it to.
2. The crate ships a `CONTRACT.md` with ten sections: purpose, inputs, outputs, invariants, refusals, determinism
   class, evidence class of outputs, validity domain, oracles, known gaps.
3. Known-answer tests pass against a pinned oracle that was never regenerated from the candidate.
4. Outputs that cross the agent boundary carry the claim product: the kind of claim, the evidence class set by
   the weakest input, a tier, a determinism class, a model identity, a seed, and the no-authorization flags. No
   naked numbers reach an agent.
5. A CPU reference path exists. Where a GPU path is claimed, a retained differential check against the CPU path
   exists for the same kernels.
6. The capability is reachable through `frob --json` with a documented schema and exit code, and, where the verb
   registry exposes it to agents, through `frob-mcp`.
7. Cancellation is tested: request, drain, finalize, with no leaked device resources.
8. Its gate has a recorded PASS carrying the measured values, not the targets, in a receipt that names the
   commit, the hardware fingerprint and the seed.

Two riders. *Family certificates*: a capability that emits a certificate about a family of designs or worlds is
implemented only when the certificate travels in a `.frobcert` bundle and the independent offline auditor
`frob-verify` accepts it on a machine with neither the agent nor a GPU, and rejects the registered mutations of
it. *Upper tiers*: a Frontier or Moonshot capability is implemented only when its paper-scale pilot and its
kill-gate decision are on record; a capability that fell back at its kill gate is described by the name of the
fallback.

Every mechanism at any tier also states: what it is (types, data layout, algorithm); which crate owns it; the
verb that exposes it; a known-answer or negative-control test; and a gate with a numeric threshold. Those five
are the fields a record must point at.

Rejected alternative: a status word typed by the implementer ("done", "beta"). It cannot be audited and it is
what produced the stand-in figures elsewhere.

## Scope

In: the capability registry `registries/capabilities.toml`, its schema and its loader rules, which are the only
definition of that file; the status function with its four statuses and the state of each of the eight
conditions; the rule by which dispatch refuses a call with FROB-REF-724 or lets a partial capability run with a
warning; the data the `capabilities` operator verb prints at M0 (the records with their status, and
`--missing`); the per-bead checklist text every capability bead inherits.

Out, with the bead that has it: the full output of the verb from M1 (the sections `build`, `gates[]` and
`devices[]` with resolved modes and ceilings per device, the filters and paging, the MCP tool and the resource
`frob://capabilities`, the human-readable form), in N32b-19, which depends on this bead, reads this registry
and calls this status function, and defines no record, status or dispatch rule of its own; verifying the
conditions for a release (the definition-of-done checker); the gate registry; the contents of any contract.

## Technical approach

**Registry.** `registries/capabilities.toml`, one record per capability (a verb, a pipeline, a kernel family, a
format), schema `frob.capability/1` (DESIGN):

```toml
[[capability]]
id        = "cap:design.check"           # stable
verbs     = ["design.check"]
crate     = "frob-analyze"               # condition 1
contract  = "crates/frob-analyze/CONTRACT.md"   # condition 2
known_answers = ["KA-261", "KA-262"]     # condition 3: registry ids, each with a pinned oracle or derivation
claim_product = true                     # condition 4: envelope test id below
envelope_test = "frob-verbs::tests::design_check_envelope"
cpu_reference = "static"                 # condition 5: tier name of the CPU path; gpu_diff = "" when no GPU path is claimed
gpu_diff  = ""
json_schema = "frob.design.check/1"      # condition 6
mcp       = true
cancellable = true                       # condition 7 applies to verbs that start work; false makes it not-applicable
cancel_test = "frob-verbs::tests::design_check_cancel"   # condition 7; empty only when cancellable = false
gates     = ["GATE-ATEL-02"]             # condition 8
tier      = "solid"                      # solid | frontier | moonshot
pilot     = ""                           # rider: pilot record id when tier is frontier or moonshot
kill_gate = ""                           # rider: the kill gate that governs it, when one exists
fallback  = ""                           # rider: the name the capability is described by if that kill gate fired
first_milestone = "M1"                   # the milestone at which its handler first exists; earlier than the
                                         # verb registry's field (the appendix's value) when a reduced form
                                         # lands early: study.plan is M1 here and M2 in registries/verbs.toml
family_certificate = false               # rider: true requires auditor_accepts and mutations_rejected
```

One record, one schema (DESIGN). The verb's own bead (N32b-19) first sketched a second record for the same
file (an `id` without the `cap:` prefix, tiers written `S`, `F`, `M`, a Boolean `gpu_path`, and the fields
`cancellable`, `fallback` and `first_milestone`). The record above is the one in force: the three fields it
lacked are added to it, `gpu_path` is the non-empty `gpu_diff`, and the tier is written as a word (the verb
registry's letters S, F, M map to `solid`, `frontier`, `moonshot`).

**Loader rules.** An unknown field, a capability with no gate, or a duplicate `id` is a load error. A lint
requires every verb of the verb registry to belong to exactly one capability and every listed gate and known
answer to exist. The file is compiled into `frob-verbs`.

**Status function** (in `frob-verbs`, exact, D0): `fn status(cap, gates, pilots) -> (Status, [ConditionState; 8])`.
Each condition is `met`, `unmet` or `not-applicable`, with a pointer to its evidence, and
`Status = Implemented | Partial { missing } | NotInBuild { missing, first_milestone } | Killed { fallback, adr }`,
printed `implemented`, `partial`, `not-in-build`, `killed`.

1. Condition 1: the crate exists in the workspace and the handler of the named verb is linked in this binary.
2. Condition 2: the contract file exists and `xtask check-contracts` reports its ten sections present.
3. Condition 3: every listed known answer is registered, has a tolerance other than `to set`, and its last
   recorded run passed against a pinned oracle.
4. Condition 4: the envelope test exists and its last recorded run passed; it asserts that the verb's output
   schema embeds the evidence block and, for exporting verbs, the authorization flags.
5. Condition 5: `cpu_reference` is non-empty; if any gate of the capability names a device site, `gpu_diff` must
   name a retained differential check that is current.
6. Condition 6: the schema is registered, the verb has an exit-code table and is in the generated CLI;
   `mcp = true` requires the tool to be generated and present in the served tool list.
7. Condition 7: the cancel test exists and passed; `not-applicable` when `cancellable = false`.
8. Condition 8: every listed gate has status `pass` with a non-empty `measured` field in `registries/gates.toml`.
9. Riders: `family_certificate = true` requires recorded auditor acceptance on a machine with no GPU and every
   registered mutation rejected; tier `frontier` or `moonshot` requires a pilot record with a result and a
   kill-gate decision.

| Status | Rule |
|---|---|
| `implemented` | All applicable conditions met, and both riders where they apply |
| `partial` | The handler is linked and at least one condition or rider is unmet; `missing` lists the unmet conditions by number and text |
| `not-in-build` | No handler is linked (the verb arrives at a later milestone, or its feature group is off): condition 1 is unmet. It is the partial status of an absent capability and, like `partial`, carries `missing` and names its `first_milestone` |
| `killed` | Its kill gate is recorded as fired; `fallback` names what is in force and `adr` the decision, and every description of the capability uses the fallback's name |

DESIGN notes on the four words, which the verb's bead and this one first chose differently. `killed` (this
bead first wrote `Fallback`) is the gate register's own word for a fired kill gate, so the capability view and
the gate view agree; the fallback's name travels in its own field. `not-in-build` (this bead first reported an
absent verb as `partial`) is kept apart because dispatch must tell a verb that cannot run from one that runs
with weaker evidence; the rule that every shortfall is named still holds, since it carries `missing`.

**Surface.** `frob capabilities --json` returns the records with computed status in the standard envelope. The
verb's handler (BD-022) reads status through its interface `StatusSource` and ships only a fail-closed source
(unlinked verbs `not-in-build`, linked ones `partial` with conditions 2 to 8 `not-evaluated`); this bead installs
the registry-driven source in its place and changes no code of the handler. The
output schema is `frob.capabilities.out/1` (DESIGN: the suite's form for a verb's output, `frob.<verb>.out/1`,
and the name N32b-19 uses; this bead first wrote `frob.capabilities/1`). At M0 it has the field
`registry_digest` (the BLAKE3 digest of the compiled capability registry, which N32b-19's cursor frontier pairs
with the gate register's digest from M1) and the sections `capabilities[]` (`id`, `verbs`, `tier`, `status`,
`conditions`, `missing`, `gates`, `first_milestone`, `fallback`) and `summary` (counts by status), as the verb's
row in VERBS-operator lists them; N32b-19 adds the others at M1 without changing these.
`--missing` lists only the capabilities that are `partial` or `not-in-build`, with their missing conditions.

**Use by dispatch (FROB-REF-724).** A call to a verb whose capability is `not-in-build` or `killed` is refused
with FROB-REF-724 ("the verb is not implemented in this build"), exit code 5, retry `never`, with the missing
conditions as `observed`, the capability record as `pointer`, the record's `first_milestone` or `fallback` in
the refusal, and the repair "see `frob capabilities`". A `partial` capability runs: its envelope carries the
warning `partial: conditions <list> unmet`, and its evidence block is whatever the claim product gives. DESIGN
reading, stated because the alternative deadlocks: if a partial capability were refused, no gate could ever be
run through the surface to make it implemented.

**The checklist every capability bead inherits** (copied into bead acceptance criteria): code in its crate;
`CONTRACT.md` with ten sections; known answers against a pinned oracle; claim product on outputs; CPU reference
path and retained differential check where a GPU path is claimed; reachable through `frob --json` (and
`frob-mcp` where exposed); cancellation tested; gate recorded with measured values.

## Acceptance criteria

- [ ] `registries/capabilities.toml` validates against its schema; an unknown field, a capability with no gate
      or a duplicate id is a load error.
- [ ] `frob capabilities --json` prints one envelope whose records each carry a status; at M0 every capability
      beyond the M0 verbs is `not-in-build` (no handler) or `partial`, each with its missing conditions named.
- [ ] Every verb of the verb registry appears under exactly one capability; the lint fails on an orphan verb.
- [ ] A `partial` capability runs and its envelope carries the warning naming the unmet conditions.
- [ ] A capability whose gate record carries the target instead of a measured value is `partial` (condition 8).
- [ ] A Frontier capability with no pilot record is `partial` whatever its gate says.
- [ ] A capability whose kill gate fired is `killed` and is printed under the fallback's name with the ADR
      identifier.
- [ ] Calling a verb that is `not-in-build` or `killed` returns FROB-REF-724 with exit code 5 and retry `never`
      on the CLI and the same refusal over MCP, with the record's `first_milestone` or `fallback`.
- [ ] The README status table and `frob capabilities` agree (both generated; `xtask check-generated`).

## Test plan

### Unit tests
`crates/frob-verbs/tests/capabilities.rs`: `all_eight_true_is_implemented`; `missing_contract_is_partial_2`;
`ka_with_tolerance_to_set_fails_condition_3`; `gate_pass_without_measured_value_fails_condition_8`;
`gpu_gate_without_differential_check_fails_condition_5`; `frontier_without_pilot_is_partial` (tier frontier
with all eight met and no pilot record or no kill-gate decision);
`fired_kill_gate_reports_fallback_name` (synthetic records: kill gate `KILL-METAL` fired → status
`Killed{fallback: "development and replay tier"}`; `KILL-TUI` fired → fallback "no dashboard");
`family_certificate_needs_auditor_and_mutations`;
`unimplemented_verb_refuses_724_exit_5` (a `not-in-build` verb: exit 5, retry `never`, `first_milestone`
present); `status_rules_table` (sixteen constructed capabilities covering each condition unmet in turn, both
riders, the killed case and the not-in-build case; expected status and `missing` for each);
`every_verb_has_one_capability`; `partial_runs_with_warning` (a partial verb answers with `warnings` naming
the unmet conditions); `non_cancellable_condition_7_not_applicable`.

### End-to-end script and logging
`scripts/e2e/capabilities.sh` (sources the STD-E2E helper; seed-free, idempotent): runs `frob capabilities
--json`, `frob capabilities --missing --json`, and one verb that the `--missing` listing reports `not-in-build`
(taken from that listing, so the script stays valid as verbs land; called with `--key cap-724` when its kind is
`run` or `mutate`, so that the answer under test is the dispatch refusal and never a missing-key refusal); asserts one envelope each, the status
of three known records, exit codes 0 and 5, and that the same call through `frob-mcp` over stdio returns the same
refusal (code, exit, `first_milestone`); then runs `xtask check-generated` and asserts the README status table
and the listing agree. Writes `target/e2e-logs/capabilities/<utc>.ndjson` and a transcript; each line has `ts`,
`script`, `bead` (`N00-02`), `step`, `event`, the exact command line, exit code, wall time and the envelope's
`evidence` block; `metric` lines give per-record status and the counts by status (their sum against the number
of records); `refusal` lines give code, exit and first repair against expected; the BLAKE3 digest of the listing
on each surface is logged; on failure the first differing record and field, and the paths of the saved
envelopes and of the capability map used. A final `summary` gives assertions passed and failed and the counts of
implemented, partial, not-in-build and killed capabilities.

### Known answers and negative controls
Known answer: on a fixture capability map none of whose verbs has a linked handler (`synthetic`), every
capability is `not-in-build`, and the summary counts sum to the number of capabilities; on the M0 build the four
declared session verbs are `not-in-build` with condition 1 missing. Negative controls: a dispatcher that refuses partial capabilities
(`partial_runs_with_warning` fails); a registry copy that marks a capability implemented by hand (a `status`
field typed in) must be rejected as an unknown field; a gate record with status `pass` and an empty `measured` must leave the
capability partial; a planted capability record pointing at a contract with nine sections. CX-002 (a closed
work item treated as an accepted capability) is the motivating counterexample. Determinism: the status function
is exact; identical output on both platforms.

## Considerations

- The registry is read by `frob capabilities`, by the README generator and by the release checker; if any of
  those readers disappears, the registry is deleted rather than kept as ceremony.
- Granularity: one record per user-visible capability, not per function. A record whose fixture is narrower than
  its name describes is renamed to the fixture ("exact static family with independent active vertical
  reactions", not "mission synthesis").
- A capability may regress from implemented to partial when a gate is re-run and fails; the table shows it.
