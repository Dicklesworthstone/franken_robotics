## Background

Ambition is calibrated in three tiers. **[S] Solid**: established mathematics and engineering; the risk is
implementation quality. **[F] Frontier**: published research that mainstream robot simulators have not
productized, or a narrowed form of a mechanism whose strong form failed review; real engineering risk. **[M]
Moonshot**: a synthesis proposed by this project; it lives behind a feature flag and never sits on the critical
path. The spine is Solid, the features that make the product worth building are Frontier, and the program works
without every Moonshot.

Two obligations attach to the upper tiers (DESIGN). The reason is the planning record itself: every pilot run
while the specification was written ended with its strong baseline tying or winning, and one speed test turned
out to have had no power to confirm its own claim.

- Every [F] and [M] item names a **paper-scale pilot with a falsifier** that must run before its work package is
  funded, and states the **ceiling of its benefit** before any speed test is run.
- Every [F] and [M] item has a **kill gate with a fallback named in advance**. The fallback is a mechanism of a
  lower tier that the design already contains, so that losing the item costs a capability and never the critical
  path.

A pilot is small enough to run on a CPU in a day, uses exact or hand-checkable arithmetic where it can, is
registered before it runs, and has an outcome that is not known in advance. A pilot that cannot fail is not a
pilot. Its result, including a negative one, is recorded, and its mechanism's tier and scope are revised to
match. An upper-tier capability counts as implemented only when its pilot and its kill-gate decision are on
record, and a capability that fell back is described by the fallback's name. At most four [M] items are active
at once in any milestone.

## Scope

In: the ledger schema and file, the funding refusal, the completeness check ("every upper-tier mechanism has a
row"), the twenty plan-time pilot rows as history, and the seed list of pilots still to run. Out: each pilot's
protocol and execution, which belong to the pilot bead of the owning unit; the re-run of the plan-time pilots
(N00-06 and the beads it names).

## Technical approach

**File.** `crates/frob-conformance/registry/pilots.toml` (one file; the short spelling `registries/pilots.toml`
used in some planning notes refers to this same file). One record per pilot, schema `frob.pilot/1` (DESIGN):

```toml
[[pilot]]
id          = "PILOT-RANK-01"
mechanism   = "ladder rung R1: baseline-controller ranking"   # what would be funded
tier        = "frontier"                 # frontier | moonshot
work_package = "WP-60"
bead        = "BD-310"                   # the bead that runs it
protocol    = "docs/pilots/rank-agreement.md"   # frozen before execution; digest below
protocol_digest = "blake3:…"
registered  = "2026-…"                   # must precede `result.date`
falsifier   = "Kendall τ lower 95% bound below 0.5 on every class tested"
ceiling     = "see N00-17: compute-per-decision ceiling 410/38 ≈ 10.8 at f = 0"
fallback    = "cheap rungs discard only; fixed halving table"
kill_gate   = "KILL-RANK"
cost        = { cpu_core_h = 0, gpu_h = 5, class = "E1" }
tool        = { name = "development oracle", pin = "…" }
status      = "registered"               # registered | running | held | falsified | void
result      = { date = "", summary = "", record = "" }
```

**Rules enforced by the loader and by `crates/frob-conformance/tests/pilots.rs`.**

1. `registered` precedes `result.date`; `protocol_digest` equals the digest of the protocol file at the commit
   of registration (a protocol edited after registration voids the pilot: status `void`).
2. `falsifier`, `ceiling`, `fallback` and `kill_gate` are non-empty; `kill_gate` exists in the gate registry;
   `fallback` names a mechanism whose tier is lower than the pilot's.
3. A result obtained on a development oracle funds or kills a work package and supports no gate.
4. **Funding refusal.** `fn may_fund(work_package) -> Result<(), Refusal>` returns a refusal listing every
   upper-tier mechanism of the package whose pilot is missing, unregistered, `void`, still `registered` or
   `running`, or `falsified`. A falsified pilot means the fallback ships and the mechanism's capability record
   (N00-02) is printed under the fallback's name. The milestone-entry review calls this function per package.
5. **Completeness.** Every capability record with tier `frontier` or `moonshot`, every kernel-manifest entry and
   every verb-registry row carrying an upper-tier tag must be named by the `mechanism` field of at least one
   pilot. An upper-tier mechanism with no row fails the test with its identifier.
6. **Moonshot cap.** At most four pilots or work packages of tier `moonshot` have status `running` in one
   milestone.

## Acceptance criteria

- [ ] The file validates; the twenty history rows are present with their recorded results.
- [ ] `may_fund` refuses a package whose Frontier mechanism has no pilot, an unregistered one, a void one, an
      unfinished one or a falsified one, and names the mechanism and the reason in each case.
- [ ] A pilot whose protocol file changed after registration is `void`.
- [ ] The completeness check fails when an upper-tier capability has no pilot row.
- [ ] GATE-GAUNT-08 can be evaluated from this file and N00-06: no Frontier or Moonshot work package is funded
      without a pilot record that has a falsifier, a computed ceiling, a fallback and a result.

## Test plan

### Unit tests
`pilots.rs`: `result_before_registration_rejected`; `edited_protocol_voids_pilot`;
`fallback_must_be_lower_tier` (a Moonshot fallback for a Frontier mechanism is rejected);
`may_fund_refuses_missing_registered_running_void_falsified` (five synthetic packages, five refusals);
`may_fund_accepts_held`; `upper_tier_capability_without_row_fails`; `fifth_running_moonshot_rejected`;
`development_oracle_result_supports_no_gate`.

### End-to-end script and logging
`scripts/e2e/pilot_ledger.sh` loads the file, calls the funding check for every work package tagged [F] or [M]
through `cargo run -p frob-conformance -- pilots may-fund --all --json`, and asserts that at M0 every such
package is refused with a named reason. Logged per STD-E2E: per package an `assert` line with mechanisms, pilot
ids, statuses and the refusal reason; `summary` with packages fundable and refused and gate GATE-GAUNT-08.

### Known answers and negative controls
Negative controls: a pilot with an empty falsifier; a pilot whose "falsifier" cannot be met by any outcome
(reviewed by hand at registration; the test checks that the falsifier names a measured quantity and a
threshold); a package funded in a scratch ledger despite a falsified pilot. CX-001 is the motivating case.

## Considerations

- The ledger is read by the funding check, by the capability status function and by the milestone exit review;
  it is not a place for narrative.
- A negative pilot result revises the mechanism's tier and scope in the same change; it is never left as a
  footnote.
- Pilots that need dynamics before the CPU referee exists run on a development oracle outside the product and
  are re-run on the referee when it exists; if the verdict differs, the referee's verdict stands.
