## Background

Saying what a system will not do is how its scope stays honest. The first version of the design excluded several
areas outright. Under the maximalist brief of the current design, five of them are admitted in a bounded form,
at Frontier or Moonshot tier, behind feature flags and off the critical path, each with known answers and a kill
gate. The identifier is kept, and each row states what moved in and what stays out. A non-goal that nothing
guards erodes one convenience at a time, so each row gets a guard: a dependency rule, a build-target rule, a
feature-flag rule or a refusal.

| ID | Not in scope | What changed, and the reason | Guard |
|---|---|---|---|
| NONGOAL-01 | A photorealistic renderer | Unchanged. Sensors need geometry-correct depth, timing and labels first. Hero images come from FrankenSim's path tracer offline | No rendering crate in the core dependency graph; sensor kernels output depth, labels and timing only (`check-deps` deny list) |
| NONGOAL-02 | Full-room fluid, granular or cloth simulation inside every training world, and soft robots as primary bodies | Narrowed. Cosserat rods and cables, cloth, films advected by the robot, slosh and coupled multiphysics islands are admitted at Frontier or Moonshot tier behind flags (M6). Their Solid counterparts, a film-friction law and rigid proxies, are in the core. Full-room fluid is out of memory by orders of magnitude | The features `rods`, `cloth`, `advected-film`, `slosh`, `islands` are off by default; a default build contains none of their kernels; islands run on the CPU referee for finalists only |
| NONGOAL-03 | Full aerodynamics, and swimming robots | Narrowed. A compact rotor port for flight is admitted at Moonshot tier (M6). The aerodynamic crates in FrankenSim remain a separate program | No dependency on FrankenSim's aerodynamic crates; the feature `rotor-port` is off by default |
| NONGOAL-04 | Motor actuation, safety-rated board support, hardware sign-off, ROS integration, and any real-time or hardware-in-the-loop claim | Narrowed. Firmware export is admitted at Moonshot tier as an exported artifact behind a caller-owned hardware interface, carrying the no-authorization flags. Bench measurements enter only as imported data | No crate opens a serial, CAN or network device for actuation (deny list of hardware-I/O crates); no ROS dependency; the feature `firmware-export` is off by default and its output carries the flags, all false |
| NONGOAL-05 | A general Python API for authoring designs or driving the studio | Narrowed. The Rust `VecEnv` is primary. An optional Gymnasium-compatible adapter lives under `bindings/`, because the ten-fold test needs rival learning stacks to drive this environment | Python bindings exist only under `bindings/frob-gymnasium`, which exposes the environment API and nothing of the design or studio verbs (symbol list test) |
| NONGOAL-06 | Windows | Unchanged. Targets are Linux x86-64 and macOS on Apple silicon | The supported-target list in the workspace has exactly two triples; a `cfg(windows)` block anywhere in the tree fails the guard |
| NONGOAL-07 | Dexterous in-hand manipulation benchmarks | Narrowed. Mobile-manipulation reach and carry tasks are in scope at M4, and tactile hands are admitted at Moonshot tier (M6). | NONGOAL-09 | Hardware certification or authorization of any kind | New. Every exported artifact says in machine-readable form that it authorizes nothing | The three flags are unit types that serialize as false (compile-fail tests); the flags gate on every exporting verb |

Survivors only, and only if our own profile justifies it | The default step plan contains only data-driven kernels; the feature `specialize` requires a recorded profile share of at least one third |

It costs thousands of policy rollouts per simulated second | An acceptance request citing sampling-controller episodes without a frozen planner record is refused (FROB-REF-817) |

| NONGOAL-16 | Simulated humans as validated agents; browser-based CAD sculpting | New. Scripted humans appear as scenario dressing only | Scene actors of kind `human` are kinematic and labelled `scripted`; no requirement may quantify over a human's response |

## Scope

In: `registries/nongoals.toml`, one guard per row implemented or delegated, and the meta-test that every guard
exists and can fail. Out: the admitted bounded forms themselves (their epics at M6 and M8); the anti-goals
(N00-24).

## Technical approach

1. **Record.** `[[nongoal]]`: `id`, `not_in_scope`, `change` (`unchanged` | `narrowed` | `new` | `carried`),
   `admitted` (what moved in, with tier, feature flag and milestone), `reason`, `guard` (kind and locator),
   `guard_owner` (this bead or the bead that implements the guard).
2. **Guards implemented here** (`crates/frob-conformance/tests/nongoals.rs`):
   a. *Deny lists for `check-deps`* (data in `registries/deny_deps.toml`, read by BD-003's check): rendering
      and path-tracing crates in the core graph (NONGOAL-01); FrankenSim's aerodynamic crates (NONGOAL-03);
      hardware-I/O and ROS client crates anywhere (NONGOAL-04); Python-binding crates outside `bindings/`
      (NONGOAL-05).
   b. *Target guard* (NONGOAL-06): the supported-target list equals {`x86_64-unknown-linux-gnu`,
      `aarch64-apple-darwin`}; a source scan finds no `cfg(windows)` or `target_os = "windows"`.
   c. *Default-feature guard* (NONGOAL-02, -03, -04, -13, -15): building the workspace with default features
      and listing enabled features shows none of `rods`, `cloth`, `advected-film`, `slosh`, `islands`,
      `rotor-port`, `firmware-export`, `specialize`, `step-adjoint`, `lifecycle`; each such feature is declared
      with its tier and its kill gate in the feature table. (DESIGN: the flag spellings here are placeholders;
      the workspace's feature table is the authority and the guard reads its list from that table.)
   d. *Binding surface guard* (NONGOAL-05): the exported symbol list of `bindings/frob-gymnasium` contains only
      environment-API names (make, reset, step, close, spaces, seed and snapshot access).
3. **Guards delegated** (the meta-test checks the named test exists from its milestone on): NONGOAL-07 task
   admission; NONGOAL-08 proof-kind registry and shield class; NONGOAL-09 flags; NONGOAL-10 class-bound family
   training; NONGOAL-11 split-set cap; NONGOAL-12 dialect lint; NONGOAL-14 FROB-REF-817; NONGOAL-16 actor kind.
4. **Change rule.** Moving something into scope is a change to this registry with an ADR; the meta-test fails
   if a feature flag of tier Frontier or Moonshot appears in the workspace without a row here or in the feature
   table that names its kill gate.

## Acceptance criteria

- [ ] Sixteen records load; each has a guard with an owner.
- [ ] The four guard families implemented here pass on the clean tree and fail on their plants (test plan).
- [ ] A default build enables no frontier or moonshot feature.
- [ ] From the milestone at which each delegated guard is due, the meta-test finds its test by name.
- [ ] `docs/SCOPE.md` (generated) prints, per non-goal, what is out, what is admitted behind which flag, and why.

## Test plan

### Unit tests
`nongoals.rs`: `sixteen_nongoals`; `rendering_crate_in_core_graph_denied` (synthetic manifest);
`ros_client_dependency_denied`; `third_target_triple_rejected`; `cfg_windows_block_rejected`;
`default_features_enable_no_frontier_flag`; `frontier_feature_without_kill_gate_rejected`;
`binding_exports_only_env_api` (a planted `design_edit` export fails); `delegated_guard_missing_after_due_fails`.

### End-to-end script and logging
`scripts/e2e/nongoal_guards.sh` runs the test, then `cargo metadata` on the default build to list features and
targets, and applies each plant in a scratch copy. Logged per STD-E2E: non-goal id, guard kind, command, exit
code, the offending crate, feature or symbol; `summary` with guards present and plants caught.

### Known answers and negative controls
No numeric known answers. Negative controls: the plants above; a non-goal record with an empty guard; a
mutant default-feature guard that inspects only the top-level crate (must miss a flag enabled in a member
crate).

## Considerations

- A non-goal is not a prohibition on research; it is a statement about what ships by default and what may be
  claimed.
- At most four Moonshot items are active at once; the feature table is where that cap is counted.
- NONGOAL-04's guard matters for safety as well as scope: nothing in the product can command hardware.
