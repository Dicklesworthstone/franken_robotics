## Background

The claim product is the type that carries, with every result, what is asserted, how strongly, about what, and
that it authorizes nothing. Its combination rule is fixed in the type: class, physics tier and determinism class
take the weakest input, scope takes the intersection, conditions take the union. That rule only protects anyone
if the *leaves* are honest: the first product created for a piece of evidence must have the class that evidence
really supports, and only the component that produced the evidence may create it. This bead specifies leaf
creation and the admission check that decides whether a result may make a given claim.

The rule in one paragraph (DESIGN). A leaf product is created only by the component that produced the evidence:
a checker creates Proved or Certified, the verification harness and the study runner create Tested, and
everything else creates Estimated. An actuator, interface or material card creates one product per field from
that field's provenance, so that a single assumed number is visible as the weakest input of everything built on
it. The reason for making this a type rule and not a convention: an optimizing agent will find any path by
which a statistical result can be reported as a proof, and a rule that lives in a style guide is such a path.

Worked case (a known answer). A comparison of two designs consumes: a kernel whose group-membership identity is
Certified; a friction coefficient from an interface card field marked `assumed`, which is Estimated; and a
paired anytime-valid study on the GPU tier under determinism class D2, which is Tested. The product is a Design
comparison of class Estimated; its weakest input is the friction field of the card; its tier is the GPU tier,
so it is provisional until promoted; its reality scope is `no-claim`. The report prints all of that in one line
and offers, as its first next action, the measurement that would raise the weakest input.

## Scope

In: the leaf-creation capabilities, the per-kind admission table and function, per-field card products, and the
"weakest input" next action. Out: the `ClaimProduct` struct, `combine` and the compile-fail tests (BD-005); the
wording (N00-25); the checkers (the proof subsystem); promotion between tiers.

## Technical approach

1. **Leaf-creation capabilities** (DESIGN sketch, in `frob-core`). Leaf constructors are not public. Each takes a
   zero-sized capability token whose constructor is visible only to the crate allowed to mint that class:

   ```rust
   pub struct ProofToken(());      // constructible only inside frob-lemma, after a checker accepted
   pub struct TestedToken(());     // constructible only inside frob-conformance (harness) and the study runner
   impl ClaimProduct {
       pub fn leaf_proved(t: &ProofToken, cert: CertRef, checker: CheckerId, scope: Scope) -> ClaimProduct;
       pub fn leaf_certified(t: &ProofToken, cert: CertRef, checker: CheckerId, scope: Scope) -> ClaimProduct;
       pub fn leaf_tested(t: &TestedToken, record: LedgerRef, scope: Scope, tier: Tier, det: DetClass) -> ClaimProduct;
       pub fn leaf_estimated(source: InputRef, scope: Scope, tier: Tier, det: DetClass) -> ClaimProduct;  // public
   }
   ```

   Token visibility is enforced by crate-private constructors re-exported through sealed traits, and
   `xtask check-layers` verifies that only the named crates depend on the sealed modules. A compile-fail test
   pins each: a crate other than the proof crates calling `leaf_proved`; a crate other than the harness and the
   study runner calling `leaf_tested`.
2. **Per-field card products.** Loading a card yields one leaf per field: provenance `measured` with an imported
   dataset reference → Tested (through the Ground lane's token, once that lane exists; Estimated before);
   `datasheet` → Estimated with the source; `assumed` → Estimated with the flag `assumed`. The card as a whole
   has no product: consumers combine the fields they read, so an unused assumed field does not weaken a result
   and a used one always does.
3. **Admission table.** `fn admit(kind: ClaimKind, product: &ClaimProduct, evidence: &Evidence) -> Result<(), Refusal>`:

   | Kind | The result must carry | Class it may have | Refused when |
   |---|---|---|---|
   | Proof | A statement with its quantifier prefix and model identity; a certificate hash; a checker identity and build; for a family claim, a `.frobcert` bundle with its assumptions listed as inputs | Proved (Lean kernel accepted a general theorem) or Certified (instance checker, interval or exact-rational certificate, or `frob-verify` on a bundle) | Hash or checker missing (FROB-REF-834); assumptions missing (the auditor refuses the bundle); quantifier prefix differs from the query (FROB-REF-826, FROB-REF-881) |
   | Known answer | The KA identifier, its derivation file digest, the tolerance, the tier and site, and the caught negative control of the same run | Tested | Tolerance `to set`; control `none stated` or not caught in this run; fixture regenerated from the candidate |
   | Parity | The oracle name and pin, the fixture digest and capture date, the tolerance | Tested | The fixture was captured from the candidate; the oracle pin is absent; the result is offered as Reality |
   | Fidelity | The higher tier named, the battery identifier, per-quantity disagreement distributions, the decision-agreement share, the frozen envelope | Tested | The battery is not the frozen one; the envelope was re-baselined without its written rationale; offered as a statement that the trusted tier is right |
   | Design comparison | The study identifier and declared type (anytime-valid or fixed-n exact, never mixed), the world-address family, the e-value or exact interval, each design's own verdict on the mission's hard limits; for "qualified", the qualification receipt and level α_i | Tested (Estimated if any consumed input is Estimated) | Arms in an uncontrolled determinism class (FROB-REF-561); a paired verdict emitted without the hard-limit verdicts; a fixed-n verdict unreachable at the planned n |
   | Reality | The dataset manifest with provenance, the prediction frozen before comparison (its digest predates the data's opening), the calibrated family and cell, the band with nominal coverage and n | Tested within the calibrated cell; otherwise the scope is `NoClaim` | No dataset; the design was never built; a card field the claim rests on is `assumed` (FROB-REF-447); the family differs from the calibrated one |
   | Performance | The disclosure block (world count, time step, substeps, solver iterations, contact count, hardware fingerprint, determinism class); for a ratio, the rival's frozen configuration digest and the measurement protocol | Tested | No disclosure block; a ratio whose ceiling was not computed first (FROB-REF-866); a figure from a D4 run offered as evidence of anything but speed |

4. **Conditions and tier.** `admit` never drops a condition flag; a `model-conditional` product is refused for
   any use that spends prototype budget (FROB-REF-820). A product whose tier is a fast tier and that has no
   promotion record is admitted only with the `provisional` marker.
5. **Next action from the weakest input.** `fn raise_weakest(product) -> NextAction` reads `weakest` (content
   hash and field path) and proposes the cheapest step that would raise it: for an `assumed` card field, the
   measurement that fills it (routed to the experiment-suggestion verb when it exists); for a fast-tier input,
   promotion; for a Tested study, more pairs or qualification. Every envelope whose class is below the class its
   consumer asked for carries this as its first `next_actions` entry.

## Acceptance criteria

- [ ] Only `frob-lemma` can mint Proved or Certified leaves (it does so after a checker accepted: the symbolic
      proof kernel, a Lean capsule, or the auditor crate's verdict; the auditor crate itself has no dependency
      and mints nothing), and only `frob-conformance` and the study runner can mint Tested leaves: two
      compile-fail tests and a layer check prove it.
- [ ] The worked case produces class Estimated, weakest input = the card's friction field, tier GPU with
      `provisional`, reality `NoClaim` (KA-027).
- [ ] `admit` passes one conforming synthetic result per kind and returns the listed refusal for each "refused
      when" entry.
- [ ] A card with one `assumed` field weakens exactly the results that read that field.
- [ ] Over 10⁴ random sets of input evidence, the admitted class equals the meet of the inputs and no public
      function returns a stronger class than its inputs (GATE-SAFE-08).
- [ ] `raise_weakest` names the friction measurement for the worked case.

## Test plan

### Unit tests
`crates/frob-core/tests/claim_admission.rs`: `worked_case_is_estimated_with_friction_weakest`;
`unused_assumed_field_does_not_weaken`; `proof_without_hash_refused_834`; `proof_with_changed_quantifier_refused_826`;
`known_answer_with_uncaught_control_refused`; `parity_fixture_from_candidate_refused`;
`fidelity_on_unfrozen_battery_refused`; `paired_verdict_without_hard_limits_refused`;
`comparison_under_d4_refused_561`; `reality_without_frozen_prediction_refused`;
`reality_on_assumed_card_field_refused_447`; `performance_without_disclosure_refused`;
`model_conditional_cannot_spend_budget_820`; property test `class_is_meet_of_inputs` (10⁴ cases);
compile-fail `tests/ui/leaf_proved_outside_lemma.rs` and `tests/ui/leaf_tested_outside_harness.rs`.

### End-to-end script and logging
`scripts/e2e/claim_admission.sh` drives the real binary on the M1 fixtures: `frob eval run` on the cart fixture
with a card whose friction field is `assumed`, then with the field replaced by a `datasheet` value, asserting
the envelope's `evidence.class`, `weakest` path and first next action in each case; then `frob prove verify` on
a bundle with its assumption list removed (expects a refusal). Logged per STD-E2E: command, exit code, the
evidence block (claim, class, tier, determinism, identities, seed), the weakest input path, the refusal code;
`summary` with gates GATE-SAFE-08 and GATE-LEMMA-06.

### Known answers and negative controls
KA-027, KA-031; CX-014. Negative controls: a `combine` mutant taking the maximum class; a crate that constructs
a `ProofToken` (must not compile); a card loader that assigns one product to the whole card (must fail
`unused_assumed_field_does_not_weaken`); a prediction "frozen" after the data was opened.

## Considerations

- The token design costs a little ergonomics and buys a guarantee that survives careless code review.
- `measured` card fields stay Estimated until the calibration lane can vouch for the dataset; the label is
  conservative on purpose.
- Admission is checked at the agent boundary (every envelope) and again by the auditor for bundles; the two
  must agree on the whole conformance corpus.
