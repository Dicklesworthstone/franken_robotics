## Background

The design is anchored by twenty-four North-Star scenarios: before-and-after acceptance stories, each tagged
with the first milestone that can demonstrate it. They are how a reader, the owner in particular, sees what the
program is for, and they are the program's end-to-end tests: a milestone's exit is defined partly by the
scenarios it demonstrates. Three conventions govern them (DESIGN):

- In the "after" part of a story, numbers are TARGETs or illustrative values unless the story says they are a
  known answer. Incumbent figures in the "before" parts are FACTs about their sources.
- Verb spellings follow the verb registry; where a story names a capability without a spelling, the registry is
  the authority.
- A demonstration is evidence that a path runs. It is never evidence for a claim's numbers, which come from the
  gate.

Scenarios by first milestone: M1: NS-01 (check before you simulate), NS-07 (an import that tells the truth),
NS-13 (a mission answered over a family, on the CPU), NS-22 (the docking fixture). M2: NS-02 (teleport a world),
NS-10 (the same task on a Mac), NS-14 (256 different robots in one batch). M3: NS-03 (an honest A/B), NS-04 (a
kitchen with a wet floor), NS-09 (the exploit is caught), NS-15 (a minimal counterexample world of three edits),
NS-16 (an autopsy that names the cause), NS-17 (qualification that survives 500 adaptive retries). M4: NS-05
(symmetry for free), NS-06 (thirty iterations in an hour, three hundred designs decided), NS-08 (tracks on
rubble), NS-18 (a twelve-dollar ramp against a chassis redesign), NS-19 (a family policy walks an unseen
design), NS-23 (an energy-budget safety claim), and NS-13 at scale. M5: NS-11 (a kernel with a certificate),
NS-12 (your own kitchen), NS-20 (a build packet), NS-21 (a calibrated reality band). M7: NS-24 (the sealed
ten-fold tournament). No scenario is tagged M0, M6 or M8.

Each scenario has its own bead (NS-01 to NS-24) carrying the story, the steps and the acceptance. This bead
builds what they share so that twenty-four scripts do not invent twenty-four conventions.

## Scope

In: the directory layout, the demo-file conventions beyond the schema, the shared script skeleton, the index
runner, the fresh-agent rule, and the two-lane rule for scenarios that need a device or a long run. Out: each
scenario's content; the `demo.yaml` schema itself (BD-002); the logging helper (STD-E2E).

## Technical approach

1. **Layout.** `demos/ns-<nn>/demo.yaml`, `demos/ns-<nn>/inputs/` (designs, tasks, missions, scenes: small,
   licensed for redistribution, each with provenance), `demos/ns-<nn>/expected/` (checksums and the expected
   envelope fragments), `scripts/e2e/ns_<nn>.sh`.
2. **Demo file** (the schema's fields, with the conventions this bead adds):

   ```yaml
   demo_id: ns-01
   title: Check before you simulate
   milestone: M1
   claims: [clm:gate-atel-02, clm:gate-skel-04]      # claim_ids that exist in registries/gates.toml
   actors: [design-agent]
   lane: cpu                                         # cpu | device | long
   commands:                                         # each finishes in under 60 s on the CPU tier (TARGET)
     - run: frob design check demos/ns-01/inputs/quad-a.fbot --json
       expect_exit: 2
       expect: expected/check.json                   # a JSON subset the envelope must contain
       checksum: blake3:…                            # of the canonical result, where the result is D0 or D2
   fresh_agent: true                                 # also run by a fresh agent holding only robot-docs
   not_evidence_for: numbers                         # constant: a demo shows a path runs
   ```

3. **Two lanes.** Every scenario has a `cpu` lane that fits the 60-second rule, using a reduced instance where
   the full scenario needs a device or hours (for example NS-14's 256 designs with 32 worlds each on a GPU
   become 8 designs with 4 worlds each on `batch-cpu`). The full instance is the scenario's end-to-end script,
   marked `lane: device` or `lane: long`, run on the named machine, and not subject to the 60-second rule. The
   reduced instance must exercise the same verbs and the same acceptance predicates; it is labelled `reduced`
   in its log and may not be cited for the scenario's headline numbers.
4. **Script skeleton** (every `ns_<nn>.sh`): source the STD-E2E helper; print the scenario's "before" as a
   comment block with its incumbent figures labelled FACT; start from a clean scratch store (`FROB_HOME` under
   `target/e2e-work/ns-<nn>/`); set the seed explicitly; run each command through `frob --json`; for every verb
   the registry exposes to agents, run the same request through `frob-mcp` and compare the result digests;
   assert exit codes, the expected JSON subset, the claim product (class, tier, determinism, `reality`,
   authorization flags all false) and the scenario's own predicates; on failure print the first differing value
   and the artifact paths; end with the `summary` line naming the gates the scenario touches. The script is
   idempotent and leaves nothing outside its work directory.
5. **Index runner.** `scripts/e2e/northstar_index.sh --milestone M<n> [--lane cpu|device|long]` runs every
   scenario whose milestone is at most the argument and prints a table: scenario, lane, result
   (`demonstrated`, `not demonstrated: <reason>`, `not due`), the gates touched and their recorded statuses. A
   scenario whose capability fell back at a kill gate is printed under the fallback's name with what the
   reduced story shows; a scenario that needs a mechanism not funded is `not demonstrated` with the reason, and
   that is a legitimate exit state where the milestone's own rules allow it (for example the no-GPU variant of
   M2 does not demonstrate NS-10 or the device halves of NS-02 and NS-14; the variant of M4 with no family
   policy does not demonstrate NS-19).
6. **Fresh-agent rule.** Scenarios marked `fresh_agent: true` are also driven by an agent session that starts
   with no context except `robot-docs`; the transcript is stored with the run, and the scenario counts as
   demonstrated for a release only when that session reached the acceptance predicates without instruction
   beyond the scenario's one-paragraph brief. At M1 this applies to NS-01, NS-07 and NS-22.
7. **Consistency checks** (`crates/frob-conformance/tests/demos.rs`): every `demo.yaml` validates; every
   `claim_id` resolves in the gate registry; every command's verb exists in the verb registry at the demo's
   milestone; every input file has provenance and a redistribution licence; `demos/` holds exactly the
   scenarios NS-01 to NS-24 plus the release demos, with no orphan directory.

## Acceptance criteria

- [ ] The layout, skeleton and index exist; `northstar_index.sh --milestone M1 --lane cpu` runs NS-01, NS-07,
      NS-13 and NS-22 from a clean checkout and prints one row each.
- [ ] Each CPU-lane command set finishes in under 60 s on the CPU tier (TARGET; measured and printed).
- [ ] A demo whose `claim_id` is not in the gate registry, or whose verb does not exist at its milestone, fails
      the consistency check.
- [ ] A scenario under a fired kill gate prints under the fallback's name; a scenario that could not run prints
      `not demonstrated` with its reason and never `demonstrated`.
- [ ] CLI and MCP result digests agree for every agent-exposed verb used by a scenario.
- [ ] The fresh-agent transcripts for NS-01, NS-07 and NS-22 are stored with the M1 exit record.

## Test plan

### Unit tests
`demos.rs`: `twenty_four_scenarios_have_demo_files` (from the milestone at which each is due; earlier ones are
stubs with `status: not due`); `unknown_claim_id_rejected`; `verb_not_in_registry_at_milestone_rejected`;
`input_without_licence_rejected`; `reduced_lane_marked_reduced`; `orphan_demo_directory_rejected`.

### End-to-end script and logging
`scripts/e2e/northstar_index.sh` is itself the script. Logged per STD-E2E for every scenario: `start` with
scenario, lane, seed and machine fingerprint; one `cmd` line per command with exit code and wall time and the
envelope's evidence block; `assert` lines for each predicate with expected and observed values; `metric` lines
for every TARGET the story names (with the label TARGET and the gate that owns the number); `refusal` lines
where a refusal is the expected outcome; `end` and a `summary` with assertions passed and failed and gates
touched. Logs contain no private-scene data (NS-12's inputs are synthetic stand-ins in the CPU lane, labelled
`synthetic`).

### Known answers and negative controls
The scenarios with exact known answers are NS-13 (KA-019 to KA-022) and NS-22 (KA-023 to KA-026). Negative
controls of the harness: a demo command that takes 75 s on the CPU lane (reported as over the target); a script
that writes outside its work directory (caught by a post-run scan); a scenario marked `demonstrated` while one
predicate failed (the index recomputes status from the log's `assert` lines, never from the script's exit
alone); a CLI and MCP digest mismatch planted by a build that omits a field on one surface.

## Considerations

- The 60-second rule keeps demos runnable by anyone on a laptop-class CPU; it is why the two-lane rule exists.
- A North-Star number is a TARGET until its gate records it; scripts print the label next to every such number
  so a log is never mistaken for a measurement.
- Stories may be revised only together with their gate: a changed number in a story with no change in the gate
  register is a defect.
