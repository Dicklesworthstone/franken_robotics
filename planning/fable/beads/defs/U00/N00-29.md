## Background

The design is anchored by twenty-four North-Star scenarios: before-and-after acceptance stories, each tagged
with the first milestone that can demonstrate it. They are how a reader, the owner in particular, sees what the
program is for, and they are the program's end-to-end tests: a milestone's exit is defined partly by the
scenarios it demonstrates. Three conventions govern them (DESIGN):

- In the "after" part of a story, numbers are TARGETs or illustrative values unless the story says they are a
  known answer. Incumbent figures in the "before" parts are FACTs about their sources.
- Verb spellings follow the verb registry; where a story names a capability without a spelling, the registry is
  the authority.
- A demonstration is evidence that a path runs. It is never evidence for a claim's numbers, which come from the
  gate.

Scenarios by first milestone: M1: NS-01 (check before you simulate), NS-07 (an import that tells the truth),
NS-13 (a mission answered over a family, on the CPU), NS-22 (the docking fixture). M2: NS-02 (teleport a world),
NS-10 (the same task on a Mac), NS-14 (256 different robots in one batch). M3: NS-03 (an honest A/B), NS-04 (a
kitchen with a wet floor), NS-09 (the exploit is caught), NS-15 (a minimal counterexample world of three edits),
NS-16 (an autopsy that names the cause), NS-17 (qualification that survives 500 adaptive retries). M4: NS-05
(symmetry for free), NS-06 (thirty iterations in an hour, three hundred designs decided), NS-08 (tracks on
rubble), NS-18 (a twelve-dollar ramp against a chassis redesign), NS-19 (a family policy walks an unseen
design), NS-23 (an energy-budget safety claim), and NS-13 at scale. M5: NS-11 (a kernel with a certificate),
NS-12 (your own kitchen), NS-20 (a build packet), NS-21 (a calibrated reality band). M7: NS-24 (the sealed
ten-fold tournament). No scenario is tagged M0, M6 or M8.

Each scenario has its own bead (NS-01 to NS-24) carrying the story, the steps and the acceptance. This bead
builds what they share so that twenty-four scripts do not invent twenty-four conventions.

## Scope

This bead is the demo harness: how a demo directory is laid out, what its file means when it runs, the one piece
of code that runs it, and what the twenty-four scenarios build on top.

In: the directory layout; the demo-file conventions beyond the schema and the run-time meaning of every key; the
one executor of a demo directory, with its run-time rules; the shared script skeleton; the index runner by
milestone; the fresh-agent rule; the two-lane rule for scenarios that need a device or a long run.

Out, and which bead has it:

- Each scenario's content: NS-01 to NS-24.
- The `demo.yaml` schema itself: BD-002, a dependency, which ships the four required keys and admits the eleven
  optional keys of step 2 from M0 (the schema's static check refuses an unknown key, so a demo file using `tier`
  or `expect_exit` validates from the first commit); the narrower shapes of those eleven keys (the values of
  `tier` and `expect_exit`, the non-empty `compare` list, the form of an actor's name): N34x-03, which adds no
  key. Its static checks on every commit (the file validates; its claims exist in the gate registry; every
  released capability has a demo): N34-09, in `check-contracts`.
- The logging helper: STD-E2E.
- `scripts/e2e/demos.sh`: the run of every demo directory of the tree from a clean checkout through this bead's
  executor, the release rule "every path of a release has a demo" read against the rubric, the worked example
  `demos/m0-doctor/` and the report a release cites: N34-12, which depends on this bead. That script holds no
  second implementation of the run-time rules below, and this bead's index is not a second runner of all demos:
  it runs scenarios by milestone, through the same executor.

## Technical approach

1. **Layout.** `demos/ns-<nn>/demo.yaml`, `demos/ns-<nn>/inputs/` (designs, tasks, missions, scenes: small,
   licensed for redistribution, each with provenance), `demos/ns-<nn>/expected/` (checksums and the expected
   envelope fragments), `scripts/e2e/ns_<nn>.sh`. A release demo that is not a scenario has the same layout
   under `demos/<demo_id>/`.
2. **Demo file** (the schema's four required keys, and the optional keys with the conventions this bead adds):

   ```yaml
   demo_id: ns-01
   title: Check before you simulate
   milestone: M1
   claim_ids:                                        # claim identifiers that exist in registries/gates.toml
     - "clm:<the claim of GATE-ATEL-02>"
     - "clm:<the claim of GATE-SKEL-04>"
   actors: [design-agent]
   tier: cpu                                         # the commands of a demo file always run on the CPU tier
   lane: cpu                                         # where the scenario's full instance runs: cpu | device | long
   commands:                                         # each finishes in under 60 s on the CPU tier (TARGET)
     - "frob design check demos/ns-01/inputs/quad-a.fbot --json"
   expect_exit:
     "frob design check demos/ns-01/inputs/quad-a.fbot --json": 2
   expect:                                           # a JSON subset the envelope must contain
     "frob design check demos/ns-01/inputs/quad-a.fbot --json": expected/check.json
   checksums:                                        # of the canonical result, where the result is D0 or D2
     "frob design check demos/ns-01/inputs/quad-a.fbot --json": "b3:…"
   fresh_agent: true                                 # also run by a fresh agent holding only robot-docs
   not_evidence_for: numbers                         # constant: a demo shows a path runs
   ```

   Keys (DESIGN: one form for every demo file, the scenarios' and the release demos' alike, because one executor
   reads them all). Required by the schema: `demo_id`; `claim_ids`; `commands`, a list of command lines;
   `checksums`, a map from a command line to the digest of its result, written `b3:` followed by the BLAKE3
   hash in hexadecimal. Optional, and to be admitted by the schema, whose static check refuses an unknown key:
   `tier`; the four per-command expectations `expect_exit`, `expect_refusal`, `compare` and `expect`, each a map
   keyed by the command line exactly as `checksums` is; and the keys of the North-Star conventions, `title`,
   `milestone`, `actors`, `lane`, `fresh_agent` and `not_evidence_for`. These eleven are the whole optional set
   (BD-002's schema admits exactly these); there is no `status` key. A scenario that is not yet due has no directory
   under `demos/` (DESIGN: a stub carrying a status key would need a twelfth key, and the release runner N34-12,
   which runs every demo directory, would then have to skip stubs; keeping not-due scenarios out of `demos/`
   needs neither). Whether a scenario is due is read from the scenario table of the index runner (step 6).
3. **The executor and its run-time rules.** `e2e_demo_run <demo directory>` (DESIGN name; a shell function in
   `scripts/e2e/lib/demo.sh`, sourced with the STD-E2E helper) is the only code that runs the commands of a
   `demo.yaml`. The scenario scripts, the index below and `scripts/e2e/demos.sh` (N34-12) all call it.
   1. Every command's first word is `frob`. Commands run in order through the binary built from the commit
      under test, with `--json`, with the working directory at the root of the checkout (so that a path such as
      `demos/ns-01/inputs/quad-a.fbot` resolves) and with a fresh store: the state root `FROB_STATE` (STD-E2E:
      `frob` reads no `FROB_HOME` and has no `--root`). The run's own root is the one `e2e_init` exports under
      `target/e2e-scratch/<script>/<run_id>/state/`; for each demo the executor exports `FROB_STATE` as a new
      empty directory inside it, `state/demos/<demo_id>/` (mode 0700), for that demo's commands only (DESIGN:
      one script may run many demos, N34-12, and no demo's result may depend on what an earlier demo stored or
      on an idempotency key it used). A command writes nothing outside the scratch and log directories; a scan
      of the checkout after the run fails the demo if one did.
   2. Each command runs under the machine-envelope guard with a wall limit of 60 s (the TARGET; the measured
      time is logged against it), on the CPU tier. A demo that names a device tier is refused by the executor
      unless it is invoked with `--tier` on a host that has the device, and a release cell that needs a device
      cites a device receipt, not a demo.
   3. The expected exit code of a command is 0 or 2 (completed, with or without findings) unless the demo says
      otherwise for that command: `expect_exit` gives the one code expected, and a demo that demonstrates a
      refusal declares it with `expect_exit: 3` and `expect_refusal: <code>` for the command. Demonstrating a
      refusal is a legitimate release path.
   4. A checksum is the BLAKE3 hash of the canonical bytes of the command's `result` member (not of the whole
      envelope, which carries wall time and budget). A command whose output is not deterministic at class D0 or
      D2 on the CPU tier cannot have a checksum and declares the fields it compares instead (`compare`, a list
      of `result` fields); the executor then compares those fields exactly with the saved copy in `expected/`.
   5. Where `expect` names a file for a command, the envelope must contain that JSON subset.
   6. Every envelope a demo prints must carry its `evidence` block and, for an exporting verb, the three
      no-authorization flags, all false; the executor asserts both.
   7. Where the verb registry exposes a command's verb to agents, the executor repeats the command as an MCP
      tool call over stdio and asserts the same `result` checksum (`--mcp`, on by default when `frob-mcp` is
      built).

   The executor logs, per command, a `cmd` line (exact command line, exit code, wall time), a `metric` line
   with `wall_s` against the threshold 60, and an `assert` line per expectation with expected and observed
   values and, on a checksum mismatch, both digests, the path of the saved output and the first differing
   member. Its verdict for a demo is recomputed from those `assert` lines. Demo outputs are synthetic or
   built-in fixtures; a demo may not read a private scene.
4. **Two lanes.** Every scenario has a `cpu` lane that fits the 60-second rule, using a reduced instance where
   the full scenario needs a device or hours (for example NS-14's 256 designs with 32 worlds each on a GPU
   become 8 designs with 4 worlds each on `batch-cpu`). The `cpu` lane is the scenario's demo file. The full
   instance is the scenario's end-to-end script, marked `lane: device` or `lane: long`, run on the named
   machine, and not subject to the 60-second rule; it is not a demo file and no release cites it as one. The
   reduced instance must exercise the same verbs and the same acceptance predicates; it is labelled `reduced`
   in its log and may not be cited for the scenario's headline numbers.
5. **Script skeleton** (every `ns_<nn>.sh`): source the STD-E2E helper; print the scenario's "before" as a
   comment block with its incumbent figures labelled FACT; start from the clean state root `FROB_STATE` that
   `e2e_init` exports under `target/e2e-scratch/ns_<nn>/<run_id>/state/`; set the seed explicitly. For the `cpu` lane, call the executor on
   `demos/ns-<nn>`, which runs each command through `frob --json`, repeats it through `frob-mcp` for every
   verb the registry exposes to agents and compares the result digests, and asserts exit codes, the expected
   JSON subset and the authorization flags all false. The script then asserts, on the saved envelopes, what a
   demo file does not express: the claim product (class, tier, determinism, `reality`) and the scenario's own
   predicates. For a `device` or `long` lane the script runs the full instance's commands itself, through
   `frob --json` and, for agent-exposed verbs, through `frob-mcp` with the same digest comparison. On failure
   it prints the first differing value and the artifact paths; it ends with the `summary` line naming the
   gates the scenario touches. The script is idempotent and leaves nothing outside its scratch directory.
6. **Index runner.** `scripts/e2e/northstar_index.sh --milestone M<n> [--lane cpu|device|long]` holds the table
   of the twenty-four scenarios with their first milestones (the list in the Background; one copy, which the
   consistency test of step 8 compares with the NS beads' milestones), runs the script
   of every scenario whose milestone is at most the argument and prints a table: scenario, lane, result
   (`demonstrated`, `not demonstrated: <reason>`, `not due`), the gates touched and their recorded statuses. A
   scenario whose capability fell back at a kill gate is printed under the fallback's name with what the
   reduced story shows; a scenario that needs a mechanism not funded is `not demonstrated` with the reason, and
   that is a legitimate exit state where the milestone's own rules allow it (for example the no-GPU variant of
   M2 does not demonstrate NS-10 or the device halves of NS-02 and NS-14; the variant of M4 with no family
   policy does not demonstrate NS-19). The index has no checking logic of its own for a demo file: it reads the
   executor's and the scripts' `assert` lines.
7. **Fresh-agent rule.** Scenarios marked `fresh_agent: true` are also driven by an agent session that starts
   with no context except `robot-docs`; the transcript is stored with the run, and the scenario counts as
   demonstrated for a release only when that session reached the acceptance predicates without instruction
   beyond the scenario's one-paragraph brief. At M1 this applies to NS-01, NS-07 and NS-22.
8. **Consistency checks** (`crates/frob-conformance/tests/demos.rs`): every command's verb exists in the verb
   registry at the demo's milestone; no command names a conformance-build-only or chaos-build-only input of its
   verb's registry tables (a release build answers those with `FROB-REF-802`, and a demo runs on the binary a
   user gets; a planted variant of a scenario runs in its script, as NS-02's does); every input file has provenance and a redistribution licence; a reduced
   lane is marked `reduced`; `demos/` holds exactly the scenarios due at the current milestone plus the release
   demos, with no orphan directory and no directory for a scenario not yet due; every demo file's `milestone`
   equals its scenario's first milestone in the index table. That every `demo.yaml` validates against its schema and that every `claim_id` resolves
   in the gate registry are checks of `check-contracts` (N34-09: `demo.schema`, `demo.claim-unknown`) and are
   not repeated here.

## Acceptance criteria

- [ ] The layout, executor, skeleton and index exist; `northstar_index.sh --milestone M1 --lane cpu` runs NS-01,
      NS-07, NS-13 and NS-22 from a clean checkout and prints one row each.
- [ ] Each command of a CPU-lane demo finishes in under 60 s on the CPU tier (TARGET; measured and printed); a
      demo whose command takes longer fails with the measured time logged (a planted `sim.run` of a long
      horizon in a scratch demo).
- [ ] A demo whose checksum was edited fails with both digests and the saved output path.
- [ ] A demo whose verb does not exist at its milestone fails the consistency check; a demo whose `claim_id` is
      not in the gate registry fails `check-contracts` (N34-09).
- [ ] A scenario under a fired kill gate prints under the fallback's name; a scenario that could not run prints
      `not demonstrated` with its reason and never `demonstrated`.
- [ ] CLI and MCP result checksums agree for every agent-exposed verb used by a demo.
- [ ] The fresh-agent transcripts for NS-01, NS-07 and NS-22 are stored with the M1 exit record.

## Test plan

### Unit tests
`demos.rs`: `twenty_four_scenarios_have_demo_files` (at milestone M, every scenario whose first milestone is at
most M has `demos/ns-<nn>/` and every later one has none: at M1 exactly NS-01, NS-07, NS-13 and NS-22; a
planted `demos/ns-24/` at M1 fails); `scenario_table_matches_beads` (the index runner's table gives the
milestones listed in the Background); `verb_not_in_registry_at_milestone_rejected`;
`conformance_build_input_in_demo_rejected` (a scratch demo whose command carries `--conformance-plant` fails); `input_without_licence_rejected`;
`reduced_lane_marked_reduced`; `orphan_demo_directory_rejected`. (An unknown `claim_id` is rejected by the
static check `demo.claim-unknown` of N34-09.)

`scripts/e2e/tests/demo_run_selftest.sh` (the executor on `synthetic` demo directories in a temporary tree,
with the real `frob` binary): `passing_demo_passes`; `slow_demo_fails_on_time`;
`checksum_mismatch_fails_with_paths`; `refusal_demo_passes_only_with_expected_code`;
`expect_exit_two_fails_on_zero` (a command expected to complete with findings that completes with none);
`missing_evidence_block_fails`; `true_flag_fails` (an output edited to carry a true authorization flag);
`compare_fields_mode`; `json_subset_missing_member_fails`; `write_outside_scratch_fails`.

### End-to-end script and logging
`scripts/e2e/northstar_index.sh` is itself the script. Logged per STD-E2E for every scenario: `start` with
scenario, lane, seed and machine fingerprint; one `cmd` line per command with exit code and wall time and the
envelope's evidence block; `assert` lines for each predicate with expected and observed values; `metric` lines
for every TARGET the story names (with the label TARGET and the gate that owns the number); `refusal` lines
where a refusal is the expected outcome; `end` and a `summary` with assertions passed and failed and gates
touched. Logs contain no private-scene data (NS-12's inputs are synthetic stand-ins in the CPU lane, labelled
`synthetic`).

### Known answers and negative controls
The scenarios with exact known answers are NS-13 (KA-019 to KA-022) and NS-22 (KA-023 to KA-026). Negative
controls of the harness: a demo command that takes 75 s on the CPU lane (reported as over the target); the
edited checksum; an output with a true authorization flag; a script that writes outside its work directory
(caught by a post-run scan); a scenario marked `demonstrated` while one predicate failed (the index recomputes
status from the log's `assert` lines, never from the script's exit alone); a CLI and MCP digest mismatch
planted by a build that omits a field on one surface. Live-dependency proof: changing the built-in fixture a
demo reads changes its checksum, so the checksum reads the output.

## Considerations

- The 60-second rule keeps demos runnable by anyone on a laptop-class CPU; it is why the two-lane rule exists.
  It is a limit on each command (the schema bead BD-002 states it per command, and so does the release script
  N34-12); 60 seconds is a TARGET on the development host, the log records the host fingerprint, and a slower
  host is reported, not excused.
- The checksum covers `result` only; anything timing-dependent in `result` is a defect of that verb's schema
  and is reported as such.
- DESIGN, working directory: demo commands run from the root of the checkout with the store in scratch, because
  the scenarios' command lines name their inputs as `demos/ns-<nn>/inputs/…` (the one exception to STD-E2E's
  `work/` as the working directory, for the demo's `frob` commands only); the post-run scan is what keeps a
  demo from writing into the checkout.
- A North-Star number is a TARGET until its gate records it; scripts print the label next to every such number
  so a log is never mistaken for a measurement.
- Stories may be revised only together with their gate: a changed number in a story with no change in the gate
  register is a defect.
