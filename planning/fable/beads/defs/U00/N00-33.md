## Background

A known answer that nothing can fail validates nothing. Across the whole known-answer suite 325 rows state no
negative control and 133 state no tolerance, or only part of one, for a real-valued truth; such rows are
obligations, not tests, and may not be counted toward a gate (the count of uncounted rows must be zero by M3
for rows due by M3). Each owning unit closes its own. Among the 32 rows of document control, the audit, the
thesis, the bets, the North-Star scenarios and the claim product, fourteen state no control (seven thesis
ceilings and seven North-Star fixture rows) and four state no tolerance. This bead supplies them.

Rule for a control (DESIGN): it is a defect, not a boundary. "The request is refused at the limit" tests the
limit; the control is the build or input in which the limit was removed or the formula was wrong. Each control
below is a mutation of the implementation or a planted input that makes the row's own test fail.

## Scope

In: fourteen control records, four tolerance decisions, and the test run that shows each control caught. Out:
controls for rows that already state one (they are registered by N00-KA and N00-CX); the other units' rows.

Each control becomes a `[[control]]` record (`id`, `seed` = the KA number, `gate`, `kind`, `target`, `defect`,
`expect`) and each tolerance a field update of its known-answer row with a dated note. A control is accepted
only after a recorded run in which the mutant build or planted input made the row's test fail and the clean
build passed.

## Acceptance criteria

- [ ] Fourteen control records exist, each with a recorded run showing `caught = true`.
- [ ] The four tolerances are written to the registry with their reasons; no row of KA-001 to KA-032 remains
      `to set` or `none stated`.
- [ ] The registry's obligation counters for this unit's rows read zero, so that all 32 rows can be counted by
      GATE-GAUNT-02 when their tests pass.
- [ ] Each mutant is a build feature or a test-only function, never present in a release build (checked by a
      symbol scan of the release binary).

## Test plan

### Unit tests
`crates/frob-conformance/tests/ka_controls_part0_8.rs`, one test per control named
`control_ka009_dropped_censoring_is_caught` … `control_ka026_stale_support_is_caught`; each builds the mutant
(a `#[cfg(feature = "mutants")]` variant or a planted fixture), runs the row's own assertion, and requires it to
fail with the value in the "why it is caught" column; then runs the clean variant and requires a pass.
`tolerances_set_for_001_003_004_006`; `no_obligation_rows_left_in_001_to_032`.

### End-to-end script and logging
`scripts/e2e/ka_controls_part0_8.sh` builds with and without the `mutants` feature and runs the suite twice.
Logged per STD-E2E: per control an `assert` line with the row, the mutant, the expected truth, the mutant's
value and `caught`; per tolerance a `metric` line; `summary` with fourteen of fourteen caught and gates
GATE-GAUNT-01 and GATE-GAUNT-02.

### Known answers and negative controls
The mutant values above are themselves hand-checkable: 1/0.87 = 1.149; 300/120 = 2.5; 300/60 = 5;
1 + 0.16 = 1.16; 1/(1 − 0.7) = 3.33, 1/(1 − 0.82) = 5.56, 1/(1 − 0.95) = 20. A control that cannot be caught
(for example a planted defect that errs on the safe side at the fixture's values) is rejected and replaced; the
suite's own record notes one such case elsewhere (an episode count rounded down that still exceeds the exact
count), which is the pattern to avoid.

## Considerations

- The auditor-site controls for KA-019 and KA-020 overlap the bundle mutation corpus of the proof subsystem;
  they are registered once and shared.
- Tolerances for sibling-defect rows are tolerances of this repository's admission tests, not statements about
  the sibling's own test suite.
- If a mutant turns out to be indistinguishable on the fixture, the fixture is extended, never the truth
  loosened.
