## Background

Three doctrine rules govern how mathematics enters the numerical code. Without a check they erode one
convenient shortcut at a time.

- **D-1, algebra first, numbers last.** The primary description of every object is algebraic: a group, an
  algebra, a cone, a representation, a poset. Floating-point arrays are a lowering of that description,
  produced as late as possible and by a replayable derivation.
- **D-3, group elements, not coordinates.** State is stored as group elements. Coordinates (angles, Euler
  triples) appear only at import, export and display, each at one boundary.
- **D-7, derive, don't hand-write.** The arithmetic of a kernel comes from a symbolic derivation with a
  content hash. Hand-written arithmetic is allowed in the referee tier and in kernel skeletons (loops,
  gathers, sorts), not in the mathematical core of a batched kernel.

Decisions that make these checkable. Rotations are stored as unit quaternions; a revolute coordinate is a unit
complex number (c, s) plus an integer turn count, and no raw angle is stored in state; packed single-precision
layouts are generated, not typed: there is no hand-declared packed struct for a group element, and the kernel
toolchain emits structure-of-arrays layouts from the same algebraic description so that the host type and the
kernel layout cannot disagree; generated files are never edited, and a workspace check regenerates and
compares them.

Tier: Solid. These are lints and G0 tests; they add no agent verb and no new `xtask` subcommand (the existing
`check-generated` already covers regeneration).

## Scope

In: three lint families in `frob-conformance/tests/g0_doctrine.rs` (`d1_*`, `d3_*`, `d7_*`), the small
allow-lists they read, their negative controls, and the review rule for what no lint decides.

Out: the regeneration check itself (`xtask check-generated`, BD-004); the kernel manifest and its fields
(BD-014) and the kernel toolchain (BD-018); the dialect lint that forbids sine, cosine and fused multiply-add
in batched kernels (the kernel back-end beads); the importers and exporters where coordinates legitimately
appear (BD-065, BD-066).

## Technical approach

**D-3 lint: no coordinates in state.**

1. Inputs: every state-layout schema the kernel manifest declares (buffer name, element kind, dimension
   exponents, component names), and the public state types of host crates.
2. Rule: a state buffer or state field may have element kind `quaternion`, `unit-complex`, `turn-count`,
   `vector`, `twist`, `wrench`, `scalar` with a physical dimension, or an integer kind. It may not have kind
   `angle`, `euler-triple`, `roll-pitch-yaw` or `axis-angle`. A buffer whose dimension is "angle" (radians as
   a state quantity) is rejected by the same rule.
3. Boundary allow-list (`frob-conformance/registry/coordinate_boundaries.toml`, DESIGN): the modules where
   coordinates may appear, each tagged `import`, `export` or `display`: the design-file readers and writers,
   the telemetry and report formatters, the viewer. One conversion function per direction per boundary. A
   function outside the list that takes or returns a type named for an angle triple fails the lint.
4. A lifted quantity that genuinely needs the angle (a torsion spring, cable wrap) reads the unit complex
   number and the turn count and computes θ = atan2(s, c) + 2π·k locally; it does not store θ in state. The
   lint allows such a local in host code and forbids it in a batched kernel's state layout.

**D-7 lint: derived arithmetic in batched kernels.**

1. Inputs: the kernel manifest, which records for each kernel its tier and, for its arithmetic core, an
   `origin`: `derived { derivation_hash, source_hash }`, `skeleton` (loops, gathers, sorts, reductions,
   scans: no floating-point arithmetic beyond index arithmetic and copies), or `handwritten { reason, adr }`.
2. Rule: a kernel that runs on a batched tier (`batch-cpu`, `gpu-cuda`, `gpu-metal`) and performs
   floating-point arithmetic must have `origin = derived`, and its `source_hash` must equal the hash of the
   checked-in generated file (which `check-generated` separately proves reproducible). `handwritten` is
   accepted only for referee-tier code, or with an architecture decision record identifier that exists.
3. Skeleton check: a file marked `skeleton` is scanned for floating-point operators applied to non-index
   values; a hit fails the lint with the line.
4. If kill gate KILL-KIR fires at M2 (the toolchain cannot express or emit more than 20% of the kernel
   arithmetic, or emitted kernels miss the speed bound of bet BET-01 after one optimization pass: more than
   1.3× slower than a hand-tuned kernel for the same stage on the same backend), its fallback is
   hand-written arithmetic bound by differential tests. The lint then accepts `handwritten` with the kill
   gate's decision record as the `adr`, and additionally requires a registered differential test per such
   kernel. The rule changes by a recorded decision, never silently.

**D-1 lint: lowered late and replayably.**

1. No hand-declared packed single-precision struct for an algebraic object: the lint scans host crates for
   struct definitions whose fields are raw `f32` arrays and whose name or documentation marks them as a group
   element, twist, wrench, inertia or cone point; allowed only inside generated files.
2. Every buffer schema in the kernel manifest names the algebraic description it lowers (a model identity and
   a field path) and the lowering's derivation hash.
3. Replay: for each registered lowering, regenerating the buffers from the algebraic description reproduces
   the bytes exactly (a test, run on the M0 kernels from M0 and on the packed model lowering from M2).
4. What no lint decides: whether an object's primary description is algebraic. Review rule, added to the
   exit-review template: for each new public type in layer-1 and layer-2 crates the reviewer answers "what
   group, algebra, cone, representation or poset is this, and where is the lowering to arrays?"; a type with
   no answer is a finding.

Determinism of the lints: D0. They write a receipt like every Gauntlet target.

## Acceptance criteria

- [ ] `cargo test -p frob-conformance --test g0_doctrine -- d1 d3 d7` passes on the workspace at M0 (the M0
      kernels and host state types) and is re-run at every milestone exit as layouts and kernels are added.
- [ ] `coordinate_boundaries.toml` exists and lists every module in which angle coordinates appear, each with
      its boundary tag.
- [ ] Negative controls caught, each by its own test: a state buffer of kind `euler-triple`; a host state
      struct with a raw `angle: f32` field; a conversion to roll-pitch-yaw outside the boundary list; a
      batched kernel with hand-written floating-point arithmetic and `origin = skeleton`; a batched kernel
      marked `handwritten` with no decision record; a generated file whose hash differs from the manifest; a
      hand-declared `Se3f32` struct in a host crate; a buffer schema with no algebraic source.
- [ ] The replay test regenerates every registered lowering byte for byte.
- [ ] The exit-review template carries the D-1 question.
- [ ] The lint's behaviour under the kill-gate fallback is implemented and tested with a synthetic decision
      record.

## Test plan

### Unit tests

- `d3_state_kinds`: a synthetic manifest (labelled `synthetic`) with allowed kinds passes; each forbidden kind
  fails with the buffer name.
- `d3_boundary_list`: a conversion function inside a listed module passes; the same function in a kernel
  crate fails.
- `d3_lifted_local_allowed`: a host function computing atan2(s, c) + 2π·k into a local passes; the same
  quantity as a state field fails.
- `d7_origin_rules`: the matrix of tier × origin; only the allowed cells pass.
- `d7_skeleton_scan`: a skeleton file with `a[i] = b[idx[i]]` passes; one with `a[i] = b[i] * c[i]` fails.
- `d7_killgate_mode`: with a synthetic KILL-KIR decision record, `handwritten` passes only when a differential
  test is registered for the kernel.
- `d1_no_packed_structs`: the planted `Se3f32` is found; a generated file with the same content is allowed.
- `d1_replay_lowering`: the Cayley step kernel's buffers regenerate byte for byte.

### End-to-end script and logging

`scripts/e2e/doctrine_representation.sh`. Sources the STD-E2E helper. Steps: run the three lint families on
the workspace; run `cargo xtask check-generated`; apply each of the eight planted violations in a scratch
copy and assert the expected failure; run `frob --json spark probe` only to capture the kernel manifest hash
that the receipts cite. Log `target/e2e-logs/doctrine_representation/<utc>.ndjson` with transcript: commands,
exit codes, wall times, counts of buffers, kernels and boundary modules examined, the manifest hash, and on
failure the file and line of the first violation. Final `summary` line.

### Known answers and negative controls

No numeric known answer. Controls are the eight plants above, each registered in `controls.toml`.
Determinism: identical receipts twice on one machine, in debug and release, on Linux and macOS.

## Considerations

- A lint that scans source text can be evaded by renaming; the primary enforcement is on the kernel manifest,
  which every kernel must pass through to be launched, and the source scans are a second line.
- The turn count must be part of the state layout wherever a lifted law reads a revolute coordinate; that
  rule is owned by the algebraic core's circle-valued-joint mechanism and is not duplicated here.
- False positives are handled by the allow-lists, each entry with a one-line reason; an allow-list entry with
  no reason fails the lint.
- These lints cost seconds and run with the workspace checks' budget in mind (the six workspace checks finish
  within 60 s on a warm tree; these run in the Gauntlet's G0 target, not in `xtask`).
