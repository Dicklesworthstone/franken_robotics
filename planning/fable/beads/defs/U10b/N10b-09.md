## Background

Construction C-19 (information has a clock; core in SPEC-C-19) defines two further objects with the same
definitions of packets, deadlines and causal policies. Both are Frontier [F].

The **label count** answers a factory question: how many calibration labels must be attached to manufactured
variants so that one shared controller serves all of them by a commitment deadline? The tempting shortcut is
pairwise compatibility ("every two variants can share a command, so all can"), and it is wrong.

**Schedule classes** answer a testing question: a timing race among capture, delivery, estimator read, watchdog
expiry and actuator commit has factorially many orderings, but orderings that differ only by swapping
independent events are the same execution. A race is explored once per class, not once per ordering.

Nothing is claimed beyond stating both queries correctly: on the fixtures an off-the-shelf satisfiability
solver answers the label question, and extracting the command sets from compliant contact is an open problem.
The benefit is a correct, small search space. Owners in the product: `frob-mission` for label queries on
supplied command sets (milestone M4) and `frob-sense` for the race check (decided at M2).

Terms. *Variant* s: one admitted as-built version of a design. *K_s*: the set of commands that work for variant
s by the deadline. *Label*: a datum attached at the factory that the controller may read before the deadline.
*Hypergraph*: vertices with edges that may contain more than two vertices; a *proper colouring* leaves no edge
monochromatic. *Independent events*: two events whose order does not affect the resulting state. *Conflicting
(dependent) pair*: two events whose order matters, for example a packet delivery and the estimator read that
may or may not see it.

## Technical approach

### 1. Label count (statements C-19.L1, L2; class `Certified` on finite instances by exact enumeration)

- **L1.** Variants can share a label exactly when their command sets have a common point: a set C of variants
  can be served under one label iff ⋂_{s ∈ C} K_s ≠ ∅.
- **L2.** The label count is the least number of colours in a proper colouring of the hypergraph whose
  vertices are the variants and whose edges are the inclusion-minimal collections of variants with empty
  common intersection. (A colour class is servable iff it contains no such collection.)

Worked fixture (KA-114). Commands (x, y) ∈ [0, 1]². Three variants require x ≥ 2/3, y ≥ 2/3 and x + y ≤ 1.
Pairs: {x ≥ 2/3, y ≥ 2/3} contains (1, 1); {x ≥ 2/3, x + y ≤ 1} contains (2/3, 0); {y ≥ 2/3, x + y ≤ 1}
contains (0, 2/3). The triple is empty, because x + y ≥ 4/3 > 1. The hypergraph has the single edge {1, 2, 3},
so two labels suffice and one is impossible. Pairwise compatibility would have authorized one shared
controller: that is the counterexample (CX-051).

Implementation note for convex command sets (a standard theorem, used only to bound enumeration): by Helly's
theorem, in ℝᵈ an inclusion-minimal collection of convex sets with empty intersection has at most d + 1
members, so for d-dimensional convex command sets only collections of size at most d + 1 are tested. For
non-convex sets every collection size is tested.

Algorithm of the reference model: (1) for each collection of variants up to the size bound, decide emptiness
of the intersection exactly (rational linear feasibility for polyhedral sets); (2) keep the inclusion-minimal
empty ones as edges; (3) find the least k for which a proper k-colouring exists (exhaustive search; instances
are small); (4) return k, a colouring and, for k − 1, the edge that defeats every colouring.

FACT (plan-time pilot, to be re-run by the plan-time pilot bead BD-043): on a payload-width fixture one label
was unsatisfiable and two satisfiable, and the frontier moved with the number and timing of labels (3/32, 7/32,
11/32 mm for one, two, three early labels; 3/32 mm when the label is late); ordinary elimination answered the
query.

### 2. Schedule classes (statements C-19.L3, L4; class `Certified` on finite instances by enumeration)

- **L3.** Schedule classes are the orderings of capture, delivery, estimator read, watchdog expiry and actuator
  commit modulo commutation of independent events (two orderings are in one class iff one is reached from the
  other by swapping adjacent independent events).
- **L4.** A timing race is explored once per class: one representative per class is executed, and executing
  any other member gives the same state digest.

Worked fixture (KA-115). Six events containing three mutually independent conflicting pairs: events a₁, a₂,
b₁, b₂, c₁, c₂, where (a₁, a₂), (b₁, b₂), (c₁, c₂) each conflict and events of different pairs are
independent. There are 6! = 720 orderings. A class is fixed by the relative order inside each pair, so there
are 2³ = 8 classes of 720/8 = 90 orderings each.

Canonical representative (DESIGN): the lexicographically least ordering of a class under a fixed event order,
computed by repeatedly emitting the least event all of whose conflicting predecessors have been emitted.

### 3. Honest limits and fallbacks

- The label count depends on the sets K_s being right; on the fixtures a satisfiability solver gives the same
  answer and is the generic comparator. Kill gate KILL-AUGUR-LABELS (decided at M4): deriving command sets
  costs more than labelling every part, or an inner set contains a failing command; fallback: the query is
  kept for supplied sets through a conventional solver and extraction from contact is parked.
- Schedule classes are sound only if the independence relation is right. Kill gate KILL-SCHED (decided at M2):
  the race check misses a planted race; fallback: the fixed total order of same-instant processing, with no
  enumeration.

## Test plan

### Unit tests

- `l1_common_point`: the three pairs intersect (witness points checked by substitution); the triple is
  infeasible (x + y ≥ 4/3 against x + y ≤ 1, exact).
- `l2_label_count_triangle`: answer 2; `l2_one_label_impossible`: every 1-colouring leaves the edge
  monochromatic.
- `l2_matches_brute_force`: 200 seeded instances of up to five axis-aligned or half-plane sets in [0, 1]²: the
  hypergraph answer equals a brute-force search over partitions with direct intersection tests.
- `l2_helly_bound`: on the convex instances no minimal empty collection has more than three members.
- `l3_six_events`: 720, 8, 90; `l3_all_independent`: six mutually independent events give one class;
  `l3_all_conflicting`: six mutually conflicting events give 720 classes.
- `l4_digest_per_class`: executing all 720 orderings on the toy state machine gives exactly 8 distinct digests.
- `controls_are_caught`.

Metamorphic relations: relabelling variants permutes the colouring and keeps the count; adding a variant whose
set contains the whole command space never changes the count; swapping independent events that share an
instant leaves digests unchanged (the control is an ordering by arrival). Determinism: integer and rational
arithmetic, class D0; twice on one machine, debug and release, identical output.

## Considerations

- Colouring is hard in general; the reference model is exhaustive and is meant for fixtures and small
  instances. The product query returns an interval when it stops on budget, never a guess.
- An independence relation is an assumption about the system. It is derived from declared read and write sets
  of events, never written by hand, and the planted-race control exists to detect one that is too generous.
- Performance envelope of the reference: at most eight variants and at most eight events.
- Revisit the Helly bound if command sets with holes become common: the bound holds only for convex sets.
