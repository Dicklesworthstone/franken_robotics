## Background

`Proved` is the strongest of the four evidence classes: a general statement accepted by a Lean kernel, and
re-checked by FrankenLean when its dependency closure permits. The project treats Lean as a second opinion and not
as a prover it drives (ADR-LEMMA-02): theorems are written in stock Lean 4 with Mathlib as a development-time tool,
stock Lean compiles them, and FrankenLean's independent kernel re-checks the compiled declarations and seals them
into a capsule. The reason is a FACT about FrankenLean at `4426f8ea7`: it does not elaborate tactic proofs
(`MetaM`/`TacticM` are not wired and no Mathlib tactic has run); what it does is re-check compiled `.olean` files
(Lean standard library 2,433 of 2,433 modules; Mathlib 9,131 of 11,083 accepted, 0 failed) and seal offline
bundles (`fln seal-capsule`, `fln verify-capsule --require-semantic`). Accepted Mathlib modules a robotics proof
would want: `Algebra.Lie.Basic`, `Algebra.Lie.OfAssociative`, `Algebra.Quaternion`, special linear and unitary
groups, permutation groups, `Order.FixedPoints`. Blocked: `Geometry.Manifold.Algebra.LieGroup`,
`Analysis.Normed.Algebra.MatrixExponential`, `Analysis.Quaternion`, all representation theory. A theorem whose
closure touches a blocked module cannot be re-checked, which is why the algebraic route comes first (ADR-LEMMA-01)
and analytic statements about exp, log and manifolds wait.

BD-380 delivers the Lake project under `lean/` and the `fln` checker on a Linux host (INT-FLN-01: one trivial
theorem re-checked and sealed; INT-FLN-02: a true port identity admitted and its sign-mutated twin rejected). This
bead turns theorem cards into sealed capsules that travel in `.frobcert` bundles under the proof kind
`lean-capsule`, and seals the first three. Tier: Frontier. Rejected alternatives: driving proofs through
FrankenLean's own tactics (only a decision-tree procedure and `omega` exist, 1,423 lines); trusting stock Lean
alone (kept only as the fallback, recorded as a single-kernel check); committing build outputs (they are large and
reproducible from the pins).

## Scope

In: the layout and rules of `lean/Frob/Cards/`; the capsule pipeline (compile, `check-olean`, `seal-capsule`,
`verify-capsule --require-semantic`); the axiom whitelist; the `lean-capsule` payload writer in `frob-lemma` and
its checker in `frob-cert`; the first three sealed cards; the measurement of GATE-LEMMA-02.
Out: the Lake project skeleton and `fln` on the Linux host (BD-380); the closure and memory measurement that must
precede any claim (N12-23); the binding of a theorem's constants to the artifact it is about (N12-24); reflection
(BD-382); the general statements of the dual-route cards T-01, T-03 and T-23 (N12-39); the script (N12-37).

## Technical approach

1. Pins. `lean/lean-toolchain` names Lean v4.32.0 and `lean/lake-manifest.json` the Mathlib commit of FrankenLean's
   own suite lock (FACT: its pin is Lean v4.32.0). The pins move only together with FrankenLean's lock.
2. Host. FrankenLean's suite lock certifies only `x86_64-unknown-linux-gnu`, and the development Mac has no
   Lean 4.32.0 toolchain, so all Lean work runs on a Linux host (upstream item FD-FLN-02 would certify macOS
   aarch64; interim posture: Linux only). A full Mathlib re-check peaked at 92.8 GiB; a single theorem's closure is
   far smaller and its measured size is recorded before any claim (OPEN-LEMMA-1, bead N12-23).
3. Source layout (DESIGN): `lean/Frob/Cards/T<nn>.lean`, one file per card, importing the narrowest Mathlib
   modules that suffice; `lean/Frob/Cards/Closure.lean.txt` is generated and lists each card's module closure.
   A card whose closure meets a blocked module is refused at build time with the module named.
4. Rules a sealed capsule satisfies (INV-LEMMA-06): no `sorry`; no axiom outside the pinned whitelist
   `lean/axioms.whitelist` (DESIGN, initial content: `propext`, `Quot.sound`, `Classical.choice`); no
   `native_decide`, so `Lean.ofReduceBool` and `Lean.trustCompiler` never appear; no proof of a weakened statement:
   the theorem's constants are mapped to the exact symbolic IR of the artifact it is about (N12-24). The capsule
   keeps the hashes of translation, environment, kernel binary, definitions and proof.
5. Pipeline (a subprocess driven by `xtask`-free scripts under `lean/scripts/`; neither Lean nor `fln` is in the
   production dependency graph): `lake build Frob.Cards.T<nn>` with stock Lean; `fln check-olean` on the compiled
   declarations and their closure; `fln seal-capsule` writes `target/lean/T<nn>.flncap`;
   `fln verify-capsule --require-semantic` on the sealed file in an empty environment (no Lean toolchain, no
   Mathlib checkout, no network). Build outputs are not committed; the capsule hash and the statement are.
6. Proof kind `lean-capsule`. Payload (DESIGN): `capsule_blake3`; `statement` with the fully qualified theorem
   name, its pretty-printed type and the hash of its elaborated type; `binding` with the artifact identity and the
   translation hash; `environment` with the Lean version, the Mathlib commit, the `fln` build and the axioms the
   capsule lists. The auditor recomputes: the BLAKE3 of the capsule file when it is named on the command line and
   its equality with `capsule_blake3`; that the statement equals the statement of the query; that the listed axioms
   are a subset of the whitelist embedded in the bundle's definitions. It does not run `fln` (it spawns no
   process). Without the capsule file the verdict is `unsupported`, never `accept`. Every report on this kind
   states the trusted base: the `frob-verify` binary, the Rust standard library and compiler, and the FrankenLean
   kernel.
7. The first three cards (DESIGN; reason: their closures stay inside algebra and order theory, which re-check
   today): T-15, the rational gear law (from f₂ = r·f₁ and e₁ = −r·e₂ it follows that e₁·f₁ + e₂·f₂ = 0, over any
   commutative ring, by ring arithmetic); T-26, the level series (for every n, Σ_{i ≤ n} α/[i·(i + 1)] = α·n/(n + 1)
   < α for α > 0, by induction on n; the infinite sum is analytic and is not needed); T-12, Kleene iteration on
   finite chains (a monotone map on a finite partial order with a least element reaches its least fixed point by
   iteration from the least element; `Order.FixedPoints` re-checks).

```lean
-- DESIGN: statements fix intent, not signatures.
theorem gear_power {R : Type} [CommRing R] (r f₁ f₂ e₁ e₂ : R)
    (hf : f₂ = r * f₁) (he : e₁ = -(r * e₂)) : e₁ * f₁ + e₂ * f₂ = 0 := …
theorem level_series (α : ℚ) (n : ℕ) :
    (Finset.Icc 1 n).sum (fun i => α / ((i : ℚ) * (i + 1))) = α * n / (n + 1) := …
theorem kleene_reaches_lfp {A : Type} [PartialOrder A] [OrderBot A] [Fintype A] (f : A →o A) :
    ∃ n, f^[n] ⊥ = f^[n + 1] ⊥ ∧ ∀ x, f x = x → f^[n] ⊥ ≤ x := …
```

8. Registry. Each sealed card updates its row in the theorem-card registry (N12-06): status `proved`, capsule
   hash, checker identities (stock Lean build, `fln` build). `frob prove list` prints the row; no report prints
   `Proved` without the capsule hash and the checker identity.

## Acceptance criteria

- [ ] GATE-LEMMA-02 (TARGET, M5, claim Proof): at least three Lean theorem cards are compiled by stock Lean,
      re-checked by `fln`, and sealed; each capsule verifies from an empty environment. Recorded with the capsule
      hashes, the closure sizes and the peak memory of each re-check.
- [ ] Negative controls: a card with a `sorry` is refused at sealing; a card that adds an axiom outside the
      whitelist is refused; a card proved with `native_decide` is refused; a statement mutated after sealing (one
      sign changed in the bundle's statement) is rejected by `frob-verify`; a capsule with one flipped byte is
      rejected by hash.
- [ ] `frob-verify` returns `unsupported` for a `lean-capsule` bundle whose capsule file is not supplied and
      states the trusted base, FrankenLean kernel included, in every report on the kind.
- [ ] No build output of Lean or `fln` is committed; `cargo tree` of every production crate shows neither tool.
- [ ] Each sealed card's registry row carries the capsule hash and both checker identities.
- [ ] The closure of each sealed card avoids the blocked modules; the list is generated and checked in.
- [ ] Closing rule: this bead closes when three cards are sealed and its own tests pass; the gate's record is
      written by the end-to-end run of bead N12-37, which depends on this bead and closes after it.

## Test plan

### Unit tests

- `lean/tests/`: `t15_gear_power_seals`, `t26_level_series_seals`, `t12_kleene_seals` (each runs the pipeline
  and asserts `verify-capsule --require-semantic` exits 0); `sorry_is_refused`, `extra_axiom_is_refused`,
  `native_decide_is_refused`, `blocked_import_is_refused` (a file importing
  `Mathlib.Analysis.Normed.Algebra.MatrixExponential` is refused with the module named).
- `crates/frob-cert/tests/lean_capsule.rs`: `capsule_hash_matches`, `capsule_byte_flip_rejects`,
  `statement_mismatch_rejects` (FROB-REF-826), `axiom_outside_whitelist_rejects`, `missing_capsule_is_unsupported`,
  `report_names_fln_in_trusted_base`.
- `crates/frob-lemma/tests/lean_writer.rs`: the writer's bundle round-trips byte-identically (PO-LEMMA-01).

### End-to-end script and logging

`scripts/e2e/lemma_lean_capsule.sh` (bead N12-37), on the Linux host: builds the three cards, seals them, copies
capsule and bundle into an empty container, runs `fln verify-capsule --require-semantic` and `frob-verify`; logs
closure module counts, peak resident memory, wall times, hashes, and each negative control's refusal.

### Known answers and negative controls

KA-226 (the level series telescopes: Σᵢ α/[i·(i + 1)] = α·m/(m + 1) after m terms and α in the limit). The
negative controls are those of the acceptance list. Mutated statement: replacing e₁ = −r·e₂ by e₁ = r·e₂ makes
T-15 false; the proof must fail to compile. Determinism: sealing twice on the same pins gives the same capsule
hash; if it does not, the pipeline records which input hash differs.
