## Background

A certificate bundle names the kind of argument it carries. The auditor `frob-verify` has one small checker per
kind and nothing else. ADR-LEMMA-04: the registry of proof kinds is closed and versioned, and an unknown kind is
rejected. The reason is doctrine rule D-11: consistent hashes do not make an unknown argument valid. A bundle in
which every digest matches and no checker implements the argument must be rejected, and so must a known kind at an
unknown version and a kind used outside its declared scope. The tempting shortcut this blocks (CX-106): "a bundle
whose hashes are all consistent is a valid certificate".

There is exactly one registry, `frob.cert.kinds/1`. Mission answers use a subset of its rows under the same names,
so a proof object's kind is the bundle's kind and the writer maps nothing. This bead creates the registry as data
compiled into `frob-cert`, the dispatch from kind to checker, the catalogue of rule identifiers that a rejection
names, and the invariant test. Tier: Solid. Rejected alternative: an open registry with plug-in checkers (a
producer could then ship its own checker with its bundle).

## Scope

In: the registry table as a `const` in `crates/frob-cert/src/kinds/registry.rs` and as a generated document
`docs/registries/cert-kinds.md`; `(kind, version) → checker` dispatch; the class cap and declared scope per kind;
`RuleId`; the rejection of unknown kinds, unknown versions and out-of-scope use; INV-LEMMA-04's mutation test.
Out: the checkers themselves (BD-027, BD-132, N12-13 to N12-19, N12p1-01, N12p2-02, BD-381); the schema, the
reader and the generic rules, including the bundle-level form of the fabricated-kind test (N12-03); the report
and the `--help` text that print the registry version (N12-04); revisions after this baseline (the ledger
N12x-08).

2. Row schema (DESIGN): `name`, `version` (starts at 1), `cap: Class`, `scope` (`kernel`, `analysis`, `mission`,
   `study`, any combination; initial values from the "Used by" column of Appendix I.4: `mission` for `lp-primal`,
   `lp-farkas`, `conic-farkas`, `interval-box`, `taylor-box`, `sos-gram`, `finite-game`, `alias-pair`,
   `monotone-transport`, `symmetry-transport`, `partition`, `composition`, `product-unreachable`,
   `monomial-product` (§25.31) and `trace-witness`; `mission` and `study` for `sample-coverage`; `kernel` and
   `analysis` for `poly-identity`, `rational-ldlt`, `interval-root`, `complex-connectivity`, `tube-inclusion`,
   `rewrite-trace`, `orbit-count`, `group-enumeration`, `energy-budget`, `alpha-root` and `lean-capsule`, with
   `mission` added to `energy-budget` for exclusion by energy (T-28); a row is widened only by a versioned edit), `requires_side_conditions: &[&str]`, `payload_schema`, `status`
   (`enabled | disabled-pending-cause | not-implemented`). A kind whose checker is not yet built is listed with
   `not-implemented` and dispatches to `Unsupported { kind }`; it is never accepted.
3. Dispatch: `fn dispatch(kind: &str, version: u32, scope: Scope) -> Result<&'static dyn Checker, CheckVerdict>`,
   where `scope` is the scope of the claim the bundle makes, fixed by its `claim.kind` (DESIGN, one table in the
   registry module): `kernel-identity` → `kernel`; `family-inclusion`, `family-exclusion` and `partition` →
   `mission`; `qualification-receipt` → `study`; an analysis claim → `analysis`; a claim kind outside the table is
   `kind.out-of-scope`. Unknown name →
   `Reject { rule: kind.unknown }` (FROB-REF-823: unknown proof kind; repairs, ranked: re-emit with a registered
   kind; upgrade the auditor if the bundle names a newer registry; exit code of the verb: the refusal exit).
   Known name, unknown version → `Reject { rule: kind.version-unknown }`. Use outside declared scope →
   `Reject { rule: kind.out-of-scope }`. Status `disabled-pending-cause` → `Reject { rule: kind.disabled }`.
4. Class cap: a bundle whose `claim.class` exceeds the kind's cap is rejected (`class.above-kind-cap`,
   FROB-REF-834).
5. Rule identifiers. `RuleId` is a dotted ASCII string `<area>.<rule>`; areas: `schema`, `hash`, `kind`, `query`,
   `side`, `field`, `num`, `limits`, `class`, `flags`, and one area per kind. The catalogue is a `const` slice; a
   checker cannot return an identifier outside it (enforced by a closed enum behind the string).
6. Versioning: adding a kind or changing what a checker recomputes bumps the registry to `frob.cert.kinds/2`;
   the auditor accepts exactly the registry versions it was built with. The module exposes `REGISTRY_VERSION`
   (the string `frob.cert.kinds/1`) and `enabled_kinds()` (the enabled (kind, version) pairs, in table order);
   the report and `--help` of N12-04 print both, and nothing else in the crate spells the version string.
7. One false certificate disables the kind and checker version involved (status `disabled-pending-cause`) until
   the cause is found; this is a registry edit, recorded with the counterexample.

## Acceptance criteria

- [ ] The registry lists exactly the 27 kinds above with version, cap, scope and status; the generated document
      matches the compiled table (a diff is a test failure).
- [ ] INV-LEMMA-04: the proof-kind registry is closed, and a checker rejects a kind it does not implement.
      `dispatch` of a fabricated name returns `reject` with rule `kind.unknown` and FROB-REF-823 whatever else the
      caller holds, because dispatch reads no digest (KA-215, CX-106). The bundle form of KA-215 (the stance golden
      with a fabricated kind and every digest recomputed, through the reader) is N12-03's test of its rule 3 on
      this table.
- [ ] A known kind at version 2 dispatched by this version-1 table gives `reject` with `kind.version-unknown` and
      the ranked repairs; the cap check rejects `sample-coverage` and `trace-witness` at class `Certified`
      (`class.above-kind-cap`, FROB-REF-834) and passes both at `Tested`.
- [ ] A kind marked `not-implemented` gives `unsupported`, never `accept`.
- [ ] `REGISTRY_VERSION` and `enabled_kinds()` are exposed and are the only source of the version string in the
      crate (a source scan finds `frob.cert.kinds/` nowhere else); their printing by `frob-verify --help` and in
      every report is N12-04's acceptance.
- [ ] No code path registers a kind at run time (no public constructor of a registry row).
- [ ] `scripts/e2e/lemma_kind_registry.sh` passes and its log ends with a `summary` line.

## Test plan

### Unit tests

`crates/frob-cert/tests/registry.rs` (the tests call the registry module directly with (kind, version, scope,
class) inputs labelled `synthetic`; no bundle reader is needed, so they run at this bead's close):
- `registry_has_27_kinds`; `registry_names_unique`; `registry_caps` (`lean-capsule` is the only kind with cap
  `Proved`; `trace-witness` and `sample-coverage` cap at `Tested`).
- `unknown_kind_rejects`: `dispatch("lp-primal-fast", 1, mission)` gives `Reject { rule: kind.unknown }` with
  FROB-REF-823 (the dispatch half of KA-215).
- `unknown_version_rejects` (`dispatch("lp-primal", 2, mission)`: `kind.version-unknown`, FROB-REF-823, ranked
  repairs "re-emit with a registered kind", "upgrade the auditor"); `out_of_scope_rejects` (`poly-identity` under
  claim kind `family-inclusion`, scope `mission`, which its row does not carry); `claim_kind_scope_table` (each
  claim kind of step 3 maps to its scope; an unlisted claim kind is `kind.out-of-scope`);
  `disabled_kind_rejects` (a row set to `disabled-pending-cause` under the test feature `registry-fixture`);
  `not_implemented_is_unsupported` (`dispatch("tube-inclusion", 1, kernel)` gives `Unsupported`).
- `rule_ids_closed`: every `RuleId` a checker can return is in the catalogue (exhaustive match).
- Compile-fail: constructing a registry row outside the crate does not compile.
- `sample_coverage_certified_rejects` and `trace_witness_certified_rejects`: the cap check at class `Certified`
  gives rule `class.above-kind-cap`, FROB-REF-834; the same kinds at `Tested` pass it.
- `generated_document_matches_table`: `docs/registries/cert-kinds.md` regenerated from the `const` is
  byte-identical to the committed file.
- `registry_version_exposed`: `REGISTRY_VERSION` is `frob.cert.kinds/1`, `enabled_kinds()` lists exactly the rows
  whose status is `enabled`, and a scan of `crates/frob-cert/src` finds the string `frob.cert.kinds/` only in the
  registry module.
- `specimens_in_scope`: every accept-specimen under `crates/frob-cert/tests/specimens/` passes the scope check (a
  specimen rejected only by `kind.out-of-scope` fails the test and names the row and scope to review), so the
  initial scope values cannot silently reject the theorem cards' own specimens as the corpus grows; the
  directory is empty at this bead's close, and the test runs over whatever later beads add.

### End-to-end script and logging

The registry has no user-facing surface of its own until the reader (N12-03), the report (N12-04) and the verb
(BD-027) land, so this bead's own script drives the crate from outside through one example program.
`scripts/e2e/lemma_kind_registry.sh` (header `bead=N12-02 milestone=M0 labels=lemma,frob-cert seed=0
needs=cpu`; sources the STD-E2E helper, idempotent, writes only under `target/`): (1) `start`: commit, toolchain,
host fingerprint; (2) `cargo run -p frob-cert --example kind_registry -- --json` (DESIGN: a standard-library-only
example that prints the compiled table, `REGISTRY_VERSION` and `enabled_kinds()`), asserting 27 rows with unique
names and the caps of `registry_caps`; (3) the same example with `--doc` regenerates `docs/registries/cert-kinds.md`
into the scratch directory, and the script asserts its BLAKE3 equals the committed file's; (4) one probe per
control, `cargo run -p frob-cert --example kind_registry -- --probe <kind> <version> <claim-kind> <class> --json`:
fabricated kind, unknown version, out of scope, disabled (test feature `registry-fixture`), not implemented,
class above cap, and one in-scope kind at its cap, each asserting the verdict, the `RuleId` and the refusal code.
Every NDJSON line (`target/e2e-logs/lemma_kind_registry/<utc>.ndjson`, transcript beside it) carries `ts`,
`script`, `bead` ("N12-02"), `step` (`registry/<control>`), `event`, the exact command line, exit code, wall time,
the registry version printed, the probed kind, version, claim kind and class, the expected and observed verdict,
`RuleId` and code, the document digests, and on a mismatch the first differing row and the command to reproduce;
the `summary` line counts controls run and controls rejected as expected. The bundle-level form of the same
controls (fabricated kind with every digest recomputed, on every specimen) runs in N12-03's script and, from M1,
in the directory-driven run of N12-34, which depends on this bead.

### Known answers and negative controls

KA-215 (unknown kind with consistent hashes → `reject`, FROB-REF-823: the dispatch half here, the bundle half in
N12-03); CX-106. Negative control of the invariant test itself: a build of the dispatch that returns a permissive
default for a name it does not hold must make `unknown_kind_rejects` fail (and, in N12-03, a reader that accepts
when every hash matches must make `unknown_kind_consistent_hashes_rejects` fail). That build is the Cargo feature
`shortcut-accept-on-hashes` of `frob-cert`, a `cfg` branch at the dispatch site, and it is the plant of CX-106 in
N12-CX (`N12-02:shortcut-accept-on-hashes`); the control runner builds it as
`--features gauntlet-mutations,frob-cert/shortcut-accept-on-hashes`, and the released `frob-verify` never carries
it. Determinism: D0.

## Considerations

- The registry is the trust boundary of every certified claim (RISK-35, RISK-36). It grows only by a versioned
  edit with a checker, a specimen and at least three mutations (GATE-LEMMA-03).
- The table's "Checker" column is the coverage map for the kinds: a kind with no enabled checker cannot support a
  `Certified` claim in any report.
- `tube-inclusion` and `alpha-root` are Moonshot and stay `not-implemented` until their mechanisms are funded.
- Kinds and kind versions requested after this baseline enter only by a revision of the ledger N12x-08, never by an
  edit of this table: record kind `packet-manifest` (checker N31b-44), `alias-pair` version 2 (N12x-06), and
  `colouring-bound` version 1 (hypergraph non-colourability, the lower bound of BD-363's label count; checker
  N12p2-01, change `colouring-bound-v1`).
