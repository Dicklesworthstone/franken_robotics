## Background

A certificate bundle names the kind of argument it carries. The auditor `frob-verify` has one small checker per
kind and nothing else. ADR-LEMMA-04: the registry of proof kinds is closed and versioned, and an unknown kind is
rejected. The reason is doctrine rule D-11: consistent hashes do not make an unknown argument valid. A bundle in
which every digest matches and no checker implements the argument must be rejected, and so must a known kind at an
unknown version and a kind used outside its declared scope. The tempting shortcut this blocks (CX-106): "a bundle
whose hashes are all consistent is a valid certificate".

There is exactly one registry, `frob.cert.kinds/1`. Mission answers use a subset of its rows under the same names,
so a proof object's kind is the bundle's kind and the writer maps nothing. This bead creates the registry as data
compiled into `frob-cert`, the dispatch from kind to checker, the catalogue of rule identifiers that a rejection
names, and the invariant test. Tier: Solid. Rejected alternative: an open registry with plug-in checkers (a
producer could then ship its own checker with its bundle).

## Scope

In: the registry table as a `const` in `crates/frob-cert/src/kinds/registry.rs` and as a generated document
`docs/registries/cert-kinds.md`; `(kind, version) → checker` dispatch; the class cap and declared scope per kind;
`RuleId`; the rejection of unknown kinds, unknown versions and out-of-scope use; INV-LEMMA-04's mutation test.
Out: the checkers themselves (BD-027, BD-132, N12-13 to N12-19, BD-381); the schema and generic rules (N12-03).

2. Row schema (DESIGN): `name`, `version` (starts at 1), `cap: Class`, `scope` (`kernel`, `analysis`, `mission`,
   `study`, any combination), `requires_side_conditions: &[&str]`, `payload_schema`, `status`
   (`enabled | disabled-pending-cause | not-implemented`). A kind whose checker is not yet built is listed with
   `not-implemented` and dispatches to `Unsupported { kind }`; it is never accepted.
3. Dispatch: `fn dispatch(kind: &str, version: u32) -> Result<&'static dyn Checker, CheckVerdict>`. Unknown name →
   `Reject { rule: kind.unknown }` (FROB-REF-823: unknown proof kind; repairs, ranked: re-emit with a registered
   kind; upgrade the auditor if the bundle names a newer registry; exit code of the verb: the refusal exit).
   Known name, unknown version → `Reject { rule: kind.version-unknown }`. Use outside declared scope →
   `Reject { rule: kind.out-of-scope }`. Status `disabled-pending-cause` → `Reject { rule: kind.disabled }`.
4. Class cap: a bundle whose `claim.class` exceeds the kind's cap is rejected (`class.above-kind-cap`,
   FROB-REF-834).
5. Rule identifiers. `RuleId` is a dotted ASCII string `<area>.<rule>`; areas: `schema`, `hash`, `kind`, `query`,
   `side`, `field`, `num`, `limits`, `class`, `flags`, and one area per kind. The catalogue is a `const` slice; a
   checker cannot return an identifier outside it (enforced by a closed enum behind the string).
6. Versioning: adding a kind or changing what a checker recomputes bumps the registry to `frob.cert.kinds/2`;
   the auditor accepts exactly the registry versions it was built with and prints them in `--help` and in every
   report.
7. One false certificate disables the kind and checker version involved (status `disabled-pending-cause`) until
   the cause is found; this is a registry edit, recorded with the counterexample.

## Acceptance criteria

- [ ] The registry lists exactly the 27 kinds above with version, cap, scope and status; the generated document
      matches the compiled table (a diff is a test failure).
- [ ] INV-LEMMA-04: the proof-kind registry is closed, and a checker rejects a kind it does not implement. A
      bundle with a fabricated kind and consistent hashes gives `reject` with rule `kind.unknown` (KA-215).
- [ ] A known kind at version 2 offered to a version-1 auditor gives `reject`; a `sample-coverage` bundle claiming
      `Certified` gives `reject`; a `trace-witness` bundle claiming `Certified` gives `reject`.
- [ ] A kind marked `not-implemented` gives `unsupported`, never `accept`.
- [ ] `frob-verify --help` prints the registry version and the list of enabled kinds.
- [ ] No code path registers a kind at run time (no public constructor of a registry row).

## Test plan

### Unit tests

`crates/frob-cert/tests/registry.rs`:
- `registry_has_27_kinds`; `registry_names_unique`; `registry_caps` (`lean-capsule` is the only kind with cap
  `Proved`; `trace-witness` and `sample-coverage` cap at `Tested`).
- `unknown_kind_consistent_hashes_rejects`: take the stance specimen, set `proof.kind` to `lp-primal-fast`,
  recompute every digest; expect `Reject { rule: kind.unknown }`.
- `unknown_version_rejects`; `out_of_scope_rejects` (`poly-identity` under claim kind `family-inclusion` without a
  mission scope row); `disabled_kind_rejects`; `not_implemented_is_unsupported`.
- `rule_ids_closed`: every `RuleId` a checker can return is in the catalogue (exhaustive match).
- Compile-fail: constructing a registry row outside the crate does not compile.

### End-to-end script and logging

`scripts/e2e/lemma_auditor_mutations.sh` (bead N12-34) includes the fabricated-kind mutant for every specimen and
logs the rule returned.

### Known answers and negative controls

KA-215 (unknown kind with consistent hashes → `reject`, FROB-REF-823); CX-106. Negative control of the invariant
test itself: a build of the dispatch that falls through to "accept if hashes match" must make
`unknown_kind_consistent_hashes_rejects` fail. Determinism: D0.

## Considerations

- The registry is the trust boundary of every certified claim (RISK-35, RISK-36). It grows only by a versioned
  edit with a checker, a specimen and at least three mutations (GATE-LEMMA-03).
- The table's "Checker" column is the coverage map for the kinds: a kind with no enabled checker cannot support a
  `Certified` claim in any report.
- `tube-inclusion` and `alpha-root` are Moonshot and stay `not-implemented` until their mechanisms are funded.
