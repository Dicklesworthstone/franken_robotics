## Background

The certificate bundle `.frobcert` (schema `frob.cert/1`, canonical JSON, format identifier FMT-FROBCERT) is
everything needed to re-check one claim on a machine that has neither the agent, a GPU nor the simulator
(ADR-LEMMA-03: one portable bundle format and one auditor built from the standard library only, because a positive
or negative answer must be readable where nothing else is installed). `frob-cert` owns the schema and the reader;
`frob-lemma` owns the writer, written against the schema and sharing no code with the reader. An answer that makes
several claims (a mission answer with several cells or several proofs) is a set of bundles, one per claim, under
one Merkle root, and the hash such an answer cites is that root.

This bead fixes the schema as a specification with a structural validator inside `frob-cert`, and the rejection
rules that do not depend on the proof kind: the query-match rule, the typed-field rule, the flag rule and the class
rule. They exist because the dangerous errors are not arithmetic errors: a certificate that checks, offered for a
different question (CX-107); numbers that are right but bound to the wrong ports or passed with the wrong sign
convention (CX-108, CX-077); an exact argument presented above the class of its weakest input (CX-109); an
artifact with no authorization fields read as neutral (CX-115). Tier: Solid.

## Scope

In: `docs/formats/frob.cert.1.md` (the normative field list), the structural validator
`crates/frob-cert/src/schema.rs`, the generic rules and their rule identifiers, the Merkle-root rule, the
specimen that exercises every field, its generic mutants on disk (`crates/frob-cert/tests/golden/mutants/`, one
per generic rule, with `expected.toml`), and this bead's end-to-end script.
Out: canonical JSON, BLAKE3 and arithmetic (BD-026); per-kind payload rules (BD-027, BD-132 and the other checker
beads); the writer (BD-027, BD-133); the report and the command line, including `--query` (N12-04).

## Technical approach

Specimen (the stance inclusion at half-width 3/14 m; `…` stands for digests and bytes):

```json
{
  "schema": "frob.cert/1",
  "claim": { "kind": "family-inclusion", "class": "Certified",
             "quantifiers": ["exists_causal_policy_per_design", "forall_admitted_worlds",
                             "forall_admitted_executions"], "horizon": "static" },
  "query": { "blake3": "…", "bytes": "…" },
  "definitions": { "units": "SI", "frame": "footprint centre, +z up", "clocks": [],
                   "ports_ordered": ["++", "+-", "-+", "--"] },
  "assumptions": [ { "id": "authority", "value": "independent normal forces", "survives": "grow" },
                   { "id": "world-set", "blake3": "…", "survives": "shrink" } ],
  "plant": { "model": "…", "policy_class": "…" },
  "domain": { "chart": "half-width b in metres", "cell": { "lo": ["3", "14"], "hi": ["1", "2"] } },
  "proof": { "kind": "lp-primal", "version": 1,
             "primitive_equations": ["sum f = W", "sum x·f = P_x", "sum y·f = P_y", "0 <= f <= c"],
             "payload": { "vertices": 4, "forces_newton": [["160","1"], ["130","1"], ["110","1"], ["0","1"]] } },
  "checker": { "name": "frob-verify", "build": "…" },
  "expected_verdict": "accept",
  "lineage": { "merkle_root": "…", "alpha_spend": [] },
  "review": { "equations_reviewed": false },
  "authorization": { "execution_authorized": false, "hardware_safety_signoff": false, "sim_to_real_certified": false }
}
```

Fields (all required unless stated):
1. `schema`: the literal `frob.cert/1`.
2. `claim`: `kind` (for example `kernel-identity`, `family-inclusion`, `family-exclusion`, `partition`,
   `qualification-receipt`), `class` (`Proved | Certified | Tested | Estimated`), `quantifiers` (the ordered
   prefix), `horizon`.
3. `query`: the BLAKE3 digest and the canonical bytes of the statement the bundle certifies (for a mission, the
   canonical `.fmission` bytes; for a kernel, the kernel content hash and the identity text).
4. `definitions`: units, frame (origin, axes, handedness, sign conventions), clocks and the instants used, and the
   ordered ports. The order is data: reordering is a different certificate.
5. `assumptions`: each with an identifier, its value or digest, and `survives: grow | shrink`, the polarity under
   which the certificate survives a change of that assumption. Assumptions are inputs; a bundle whose assumptions
   are missing is rejected.
6. `plant`: the model identity and the policy class digest (channel, timing, indexing, randomization).
7. `domain`: the chart with units and the cell; with several coordinates `lo` and `hi` list one rational per
   coordinate, and open or closed ends are recorded.
8. `proof`: `kind` from the closed registry, `version` (the kind's row version, an integer from 1; the dispatch of
   N12-02 reads the pair, and a later revision of a kind is a new version, N12x-08), `primitive_equations` in
   Unicode text (and as an expression DAG where a kind needs it), `payload`, and side-condition sub-certificates
   where a rule requires them. DESIGN: the version is a field of its own because the auditor accepts a bundle iff
   its (kind, version) is enabled; the format example of the plan omits it.
9. `checker`: name and build the bundle targets. 10. `expected_verdict`. 11. `lineage`: the Merkle root and the
   `alpha_spend` entries of qualification receipts. 12. `authorization`: the three flags (the same object is
   spelled `flags` in the Rust type; the three field names are the same everywhere).
13. `review` (the marker of OPEN-AUGUR-8, whose decision, writer rule and claim rule are N25b-02's):
   `equations_reviewed` (boolean); when it is `true`, also `equations_digest` (BLAKE3 of `proof.primitive_equations`
   in canonical form), `review_record` (the digest of the ledger artifact that names the reviewing session) and
   `scope` (text). Required when `claim.kind` is a mission claim (`family-inclusion`, `family-exclusion`,
   `partition`); optional for `kernel-identity` and `qualification-receipt`, and checked when present. It is a
   separate object from `authorization`, whose fields stay exactly three. DESIGN, why at M0: the validator rejects
   an unknown top-level field and the schema grows only by a new version, so a field added at M1 would have broken
   `frob.cert/1`; the fail-closed value `false` costs nothing until a review exists.

Rules of the format (each a checked rule with a `RuleId`):
- R1 Typed fields: every field that enters the argument is typed with its frame, origin, sign convention and
  units (`field.type`). A first moment where a torque is expected is a type error, not a number.
- R2 Primitive equations travel in the bundle, because a proof about the wrong translation of a contact law is
  still a physical error, and a reviewer can only find it by reading what was proved (`side.equations-missing`).
- R3 A minimum is claimed only with the incumbent value and a checked matching lower bound; an infimum that is
  not attained is returned as an open threshold with a feasible candidate and its gap (`claim.minimum-unbounded`).
- R4 The probability mass of an unresolved set is reported only under a supplied weighting
  (`claim.mass-without-weighting`).
- R5 Numbers are exact rationals (reduced, positive denominator) or outward-rounded intervals with a declared
  implementation and precision; an integer above 2⁵³ travels as a string (`num.rational-form`, `num.interval-decl`).

Generic rejection rules, applied before any kind-specific rule, in this order:
1. Structure and schema (`schema.*`, among them `schema.review-missing`: a mission claim without `review`); every
   recomputable hash matches (`hash.*`, among them `hash.equations-digest`: with `equations_reviewed: true` the
   auditor recomputes the digest of the primitive equations and rejects a mismatch). The auditor does not judge a
   review; it reports the marker (N12-04).
2. Flags: the `authorization` object is present with its three fields, each the literal `false`; missing or true
   is rejected (`flags.missing`, `flags.true`; FROB-REF-833; repair: none, no code path sets a flag, so the
   artifact is foreign or corrupt and must be regenerated).
3. Kind: registry lookup of (`proof.kind`, `proof.version`) under the scope of `claim.kind` (N12-02; FROB-REF-823).
   A kind whose row is `not-implemented` still passes through rules 4 to 6, which read only the registry row and
   the bundle, and the verdict is `unsupported` only when all of them pass (DESIGN: a defect the generic rules can
   see is reported whatever the state of the kind's checker).
4. Query match: the quantifier prefix, the domain, the assumption set and the policy class equal those of the
   query the bundle is offered for, even when every hash is consistent (`query.prefix`, `query.domain`,
   `query.assumptions`, `query.policy-class`; FROB-REF-826; repairs, ranked: offer the bundle for the query it was
   made for; re-derive for the new query). The query offered is the one the caller names (`frob-verify --query
   <file>`, N12-04; `frob prove verify --query q:…`), else the query embedded in `query.bytes`. The comparison is
   field by field and never by digest alone, so a certificate serves another query that asks the same thing and
   is refused for one that asks something else. `query.policy-class`: `plant.policy_class` must equal the digest
   the auditor recomputes from the policy-class section of the offered query's canonical bytes (channel, timing
   with the arrival instant of every packet relative to the commands, indexing, randomization). DESIGN, why 826:
   a family certificate is about the declared model, world set and policy class (§12.2), so the policy class is
   part of what the query assumes; without this comparison the on-time docking inclusion offered for the
   late-packet query passes, since its prefix, domain and assumption rows are equal, and a certificate of a
   different question is accepted.
5. Side conditions and typed fields: every side condition the kind's rule requires is present and every field has
   the declared frame, origin, sign and unit (`side.missing`, `field.type`; FROB-REF-829; repair: re-emit with the
   typed field or the missing sub-certificate).
6. Class: `claim.class` is at most the kind's cap and at most the weakest class among the claim's inputs and
   assumptions; `Proved` or `Certified` requires a certificate hash and a checker identity
   (`class.above-kind-cap` with N12-02's cap check, `class.above-input`, `class.no-receipt`; FROB-REF-834; repair:
   restate the result at the class of its weakest input).

Merkle root (DESIGN): leaves are BLAKE3 digests of the canonical bytes of the per-claim bundles with their
`lineage.merkle_root` field set to the empty string, sorted by digest (duplicates are a `hash.merkle-duplicate`
rejection); an inner node is BLAKE3 of the byte 0x01 followed by its two children's 32-byte digests, left then
right (the prefix keeps an inner node from being read as a leaf, since a leaf's preimage is canonical JSON and
starts with `{`); a level with an odd number of nodes carries its last node up unchanged; a single-claim
answer's root is its only leaf. The auditor recomputes the root when given the whole set and reports
`hash.merkle-root` on a mismatch; given one bundle alone it reports that the root was not recomputed. The class
of a set is the weakest class among its members.

## Acceptance criteria

- [ ] `docs/formats/frob.cert.1.md` lists every field with type, requiredness and rule; the validator rejects a
      bundle with an unknown top-level field, a missing required field or a duplicate key.
- [ ] Each generic rule has a specimen mutation that triggers it and names it as the first failing rule: a flag
      set to true (KA-214), a flag missing (KA-216), a fabricated kind with every digest recomputed (KA-215,
      `kind.unknown`), quantifiers reordered (KA-209, KA-217), a domain changed, an assumption removed, an offered
      query whose policy class differs only in an arrival instant (`query.policy-class`), a torque field carrying
      a first moment, a `Certified` claim over an `Estimated` assumption.
- [ ] A bundle of a `not-implemented` kind with a generic defect is rejected with the generic rule, and without one
      gives `unsupported`.
- [ ] The Merkle root of the six-entry listing (five `Certified` entries and one `Tested` receipt) is recomputed
      by the auditor; changing one entry changes the root; the class of the set is `Tested`.
- [ ] An open threshold (the docking bound ε < (U + ½)/4 at U = ¾: bound 5/16, not attained) is representable and
      a bundle that claims the minimum 5/16 as attained is rejected by R3 (CX-114); the attained stance minimum
      b = 3/14 m with its matching lower bound is accepted.
- [ ] The schema document, the validator and the golden files agree: this bead commits hand-written golden
      bundles (`crates/frob-cert/tests/golden/`, the specimen above and the six-entry listing; every mission-kind
      golden bundle carries `"review": { "equations_reviewed": false }`, written by hand) that the validator
      accepts and that parse and re-serialize byte-identically; the writer's half of the round trip (PO-LEMMA-01)
      is observed in BD-027 and BD-133, which depend on this bead and must reproduce these files byte for byte.
- [ ] `scripts/e2e/lemma_bundle_schema.sh` passes and its log ends with a `summary` line.

### End-to-end script and logging

This bead's own script, `scripts/e2e/lemma_bundle_schema.sh` (header `bead=N12-03 milestone=M0
labels=lemma,frob-cert seed=0 needs=cpu`; sources the STD-E2E helper, idempotent, writes only under `target/`),
drives the binary of BD-026 with this bead's reader and rules from outside: (1) `start`: commit, toolchain, host
fingerprint; (2) `cargo build -p frob-cert --release`; (3) under `env -i`, `frob-verify` on each golden bundle of
`crates/frob-cert/tests/golden/` (expected: `unsupported`, because no checker of a mission kind is enabled at M0,
and never `reject`) and on each generic mutant of `crates/frob-cert/tests/golden/mutants/` with its
`expected.toml`, asserting the first failing rule and the refusal code; (4) the six-entry listing given as a set,
asserting the recomputed Merkle root and the class `Tested`, then with one entry changed, asserting a different
root and `hash.merkle-root`; (5) the rule-order control (true flag and unknown kind: `flags.true`). NDJSON lines
(`target/e2e-logs/lemma_bundle_schema/<utc>.ndjson`, transcript beside it) carry `ts`, `script`, `bead`
("N12-03"), `step` (`generic/<rule>/<specimen>`), `event`, the exact `frob-verify` command line, exit code, wall
time, the mutated field path, the bundle's BLAKE3 before and after the mutation, the expected and observed first
failing `RuleId` and refusal code (FROB-REF-823, -826, -829, -833, -834), the Merkle root recomputed for set
inputs, and on a mismatch the path to reproduce; the `summary` line counts mutations run and mutations rejected by
the expected rule. From M1 the directory-driven run of N12-34, which depends on this bead, applies the same
generic mutations to every kind's specimens.

Negative controls: for the rule order, a bundle with a true flag and an unknown kind reports `flags.true` first;

rule identical across platforms.

## Considerations

- Absence of a flag is never read as false. Authorizing hardware is a human act outside the project and leaves no
  trace in these artifacts. A build packet adds a fourth flag, `fabrication_released`, in its own format.
- The schema grows only by a new schema version; `frob.cert/1` bundles stay readable.
- OPEN-AUGUR-8: whether a review of the primitive equations is recorded in the bundle. The marker (field 13) and
  its two rules are in the format from M0 with the fail-closed value; the decision, the writer rule and the claim
  rule (unreviewed mission bundles cannot be cited under the Proof claim outside the known-answer fixtures) are
  N25b-02's.
- A bundle embeds query bytes; bundles derived from private scenes inherit the privacy mark.
