## Background

`frob-verify` is the offline auditor: a single binary built from the Rust standard library and nothing else, with
no FrankenSim, no GPU and no network, and with `unsafe` forbidden. Its reader is a person or an agent holding only
a certificate bundle, on a machine where nothing else of the project is installed; `frob-verify --help` is listed
as one of that reader's starting documents. What the binary prints is therefore the whole of what an auditor
learns, and it must say exactly what was checked, by what, and on what trust.

The contract fixed here: the auditor returns `accept`, `reject` or `unsupported`, with the first failing rule
named; it states its trusted base in every report (the binary, the Rust standard library and compiler, and for
`lean-capsule` kinds the FrankenLean kernel); its size is capped (TARGET: at most 12,000 lines) so that a person
can read it; and re-serializing a bundle with it gives identical bytes (PO-LEMMA-01), which is what lets two
machines compare digests. It does not run physics and cannot attest that an episode happened. Tier: Solid.

Rejected alternatives: a verdict without the failing rule (a producer could not repair, and a reviewer could not
tell a typed-field error from an arithmetic one); a "warn and accept" mode (an auditor that accepts with warnings
is read as accepting); growing the auditor past the size a person can read (the cap forces each checker to stay
small and forces new kinds to justify their lines).

## Scope

In: the command line of `frob-verify`; the text and JSON reports; exit codes; the trusted-base statement; the
aggregate line for a set of bundles; the `--reserialize` mode and PO-LEMMA-01; the line-count check; `--help`.
Out: parsing, hashing and arithmetic (BD-026); kinds and rules (N12-02, N12-03, the checker beads); the
independence checks on dependencies, sockets and child processes (BD-026 with GATE-WS-03; N12-09).

## Technical approach

1. Command line (DESIGN): `frob-verify [--json] [--reserialize <out>] [--query <file>] <bundle.frobcert>...
   [<capsule file>...]`. It reads only the files named, opens no socket, reads no environment variable and spawns
   no process. `--query` names the canonical bytes of the question the bundles are offered for (a `.fmission`
   file, or a kernel's identity statement); the query-match rule of N12-03 then compares each bundle with that
   query instead of the one it embeds, as `frob prove verify --query q:…` does in tree. A third party who holds a
   bundle and a question checks that the bundle answers that question, not merely its own.
2. Verdict type: `CheckVerdict = Accept | Reject { rule: RuleId } | Unsupported { kind: String }`. `Unsupported`
   means the registry knows no enabled checker for the kind or a needed input (a capsule file) was not supplied;
   it is never counted as accept by any consumer.
3. Exit codes (DESIGN, aligned with the exit table of the `frob` binary, in which 1 is never emitted on purpose
   so that a 1 always means an unhandled failure): 0 every bundle accepted; 2 completed with findings (none
   rejected and at least one `unsupported`); 3 refused (at least one bundle rejected, or an unreadable or
   malformed input, reported with rule `input.unreadable`). The in-daemon verb `prove.verify` returns the same
   verdicts through the envelope; the two must agree on the whole conformance corpus.
4. Text report, one line per bundle and one aggregate line, for example:
   `accept   6 of 6 entries; class of the bundle: Tested (weakest entry e6); all three authorization flags false`.
   A bundle that carries the `review` marker (field 13 of N12-03; required on mission claims) adds
   `equations reviewed: yes` or `equations reviewed: no` to its line; the auditor reports the marker and never
   judges the review.
   A rejection prints the bundle digest, the entry, the rule identifier, the refusal code where one applies and
   the field path of the first failing value. Every report ends with the trusted-base block:
   `trusted base: frob-verify <build>; rustc <version> and the Rust standard library; registry frob.cert.kinds/1`,
   plus `FrankenLean kernel <build>` when any entry is of kind `lean-capsule`.
5. JSON report (`--json`, schema `frob.verify.report/1`, DESIGN): `bundles[]` with `blake3`, `verdict`, `rule`,
   `refusal`, `class`, `kind`, `first_failing_path`, `equations_reviewed` (`true`, `false`, or `null` when the
   bundle carries no marker), and `recomputed_values` (optional: the named values the kind's checker recomputed,
   exact rationals as strings, for example `beta` and `ytw` for `lp-farkas`; keys are listed per kind in
   `CONTRACT.md`; a kind that recomputes nothing worth naming omits the block); `set` with `merkle_root`, `recomputed`, `class`,
   `weakest_entry`; `trusted_base`; `checked` and `not_checked` (the fixed lists below); the three flags, false.
6. The report states what was not checked (fixed text): that the primitive equations describe the physical robot,
   floor or sensor; that the lowering from design and mission to the equations is correct; any trajectory (a
   `trace-witness` is accepted as well-formed only); that the unresolved set is as small as it could be; cost
   data, prices or weightings; any statistical statement beyond recomputing a bound from counts; that any episode
   ran.
7. Class of a set: the minimum over entries; the weakest entry is named. A report never prints `Proved` or
   `Certified` without the certificate's content hash and the checker's identity. The word "verified" does not
   appear in any output of the binary.
8. Re-serialization: `--reserialize` writes the canonical form of the parsed bundle; for every accepted specimen
   the output bytes equal the input bytes (PO-LEMMA-01). A non-canonical input (key order, whitespace, number
   form) is rejected at parse time, so equality is total on accepted bundles.
9. Size cap: a test counts non-blank, non-comment lines under `crates/frob-cert/src` and fails above 12,000
   (TARGET); at 115% of a cap a scope conversation is opened rather than the cap silently raised.

## Acceptance criteria

- [ ] `frob-verify` returns exactly one of `accept`, `reject`, `unsupported` per bundle and names the first
      failing rule on every rejection.
- [ ] Every text and JSON report contains the trusted-base block; a report on a `lean-capsule` entry names the
      FrankenLean kernel.
- [ ] PO-LEMMA-01: re-serializing each specimen gives identical bytes; a non-canonical input is rejected.
- [ ] The standalone binary and `frob prove verify --json` return identical verdicts and rules on the whole
      corpus present at this bead's close (the kernel bundles and their mutants, through the `prove.verify` of
      BD-027); BD-133, which depends on this bead, runs the same agreement test on the mission bundles it adds.
- [ ] The line count of the crate is at most 12,000 (TARGET) and is printed by the test.
- [ ] The word "verified" appears nowhere in the binary's output or help text (string scan in the test).
- [ ] `frob-verify --help` documents the verdicts, the exit codes, the registry version and the enabled (kind,
      version) pairs (N12-02's `REGISTRY_VERSION` and `enabled_kinds()`), `--query`, the trusted base and the
      not-checked list.
- [ ] With `--query`, a kernel bundle offered for another kernel's identity statement is rejected by the
      query-match rule with FROB-REF-826, and the same bundle with its own statement is accepted.
- [ ] `scripts/e2e/lemma_verify_report.sh` passes and its log ends with a `summary` line.

`exit_code_1_never_emitted`;

`review_marker_reported` (a mission golden bundle prints `equations reviewed: no` and `equations_reviewed: false`;
a kernel bundle without the marker prints neither and has `null`); `recomputed_values_are_checker_values` (for BD-027's
`rational-ldlt/accept-pd4` specimen the block holds `pivots` = ("1", "1/3", "1/3", "1"), the values the checker

### End-to-end script and logging

This bead's own script, `scripts/e2e/lemma_verify_report.sh` (header `bead=N12-04 milestone=M1
labels=lemma,frob-cert seed=0 needs=cpu`; sources the STD-E2E helper, idempotent, writes only under `target/`),
runs on the corpus present at this bead's close (the kernel specimens and mutants of BD-027 and the golden files
and generic mutants of N12-03): (1) `start`: commit, toolchain, host fingerprint; (2) `cargo build -p frob-cert
--release`, then `frob-verify --help`, asserting the verdicts, exit codes, registry version, enabled kinds,
`--query`, trusted base and not-checked list, and no occurrence of the word "verified"; (3) under `env -i`, the
text and the JSON report of every file, each run twice, asserting exit 0, 2 or 3 as the manifest says and equal
report digests across the two runs; (4) `--reserialize` of every accepted file, bytes identical; (5) one set of
mixed verdicts (exit 3) and one set with an `unsupported` entry (exit 2); (6) the `--query` pair of
`query_option_compares_offered_query`; (7) `frob prove verify <file> --json` (BD-027's verb) on every kernel file,
asserting the verdict and rule equal the standalone binary's. Its NDJSON lines
(`target/e2e-logs/lemma_verify_report/<utc>.ndjson`, transcript beside it) carry `ts`, `script`, `bead`
("N12-04"), `step` (`report/<specimen-or-mutant>`), `event`, the exact `frob-verify` command line, exit code
against the expected 0, 2 or 3, wall time, the verdict, rule, refusal code and first failing path, the BLAKE3 of
the text and JSON reports (equal across two runs), whether `--reserialize` returned identical bytes, the
trusted-base block, the in-tree envelope's `evidence` block where step 7 ran, and on a mismatch the differing
field and the path to reproduce; a `metric` line gives the crate's line count against 12,000; the `summary`
line counts assertions passed and failed. The directory-driven run of N12-34, which depends on this bead,
captures the same reports on every kind's corpus from M1.

### Known answers and negative controls

KA-222 (bundle round trip: identical bytes on every specimen). Negative controls: a build that reports the last
failing rule instead of the first is caught by a mutant with two defects whose order is fixed (flag true and
unknown kind → `flags.true`); a build that omits the trusted base fails `trusted_base_always_present`.
Determinism: report bytes identical twice on one machine, debug and release, and across platforms (class D0).

## Considerations

- `frob-verify` is one of the few artifacts prepared for a third party (with the replication kit); its help text
  is public-facing documentation and must stand alone.
- The stable toolchain named in `frob-cert`'s own toolchain file is OPEN-WS-3 (default: the newest stable release
  on the day of its first commit, then moved only by ADR); the report prints the compiler version it was built
  with.
- RISK-36: a shared defect between proposer and checker. The report's `not_checked` list is the honest boundary of
  what acceptance means.
