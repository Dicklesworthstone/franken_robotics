## Background

A theorem card is a statement the project wants, with its route and its tier. There are thirty-five, T-01 to T-35.
At plan time the status of every card is HYPOTHESIS: none has been checked. A card is admitted only if a checker
can decide it; candidate obligations that fail that test are not cards (they are tests, monitored assumptions or
separate claims, carried by N12-07). The verb `prove.list` (kind `read`, first milestone M0) prints "certificates
and theorem cards with their classes and checkers". Something must hold the cards as data so that the verb, the
reports and the gates read one source and so that a card's class can only be raised by a checker's receipt.

This bead creates that registry, seeds it with all thirty-five rows, and fixes the status machine. Each card also
has its own bead (`CARD-T-01` to `CARD-T-35`) that makes the row true. Tier: Solid. Rejected alternatives: cards
as prose in documentation (a report could then print a class no receipt supports); a class field writable by the
bead that implements the card (the class is set only by the checker that produced the evidence).

## Scope

In: the schema and the file `registries/theorems.toml`; the seed rows; the status machine; the loader in
`frob-lemma`; the rows of `prove.list`; the check that a row's class is supported by receipts.
Out: the content of each card (the `CARD-T-nn` beads); the non-decidable obligations (N12-07); the verb plumbing
of `prove.list` itself (BD-027).

## Technical approach

1. Row schema (DESIGN):

```toml
[[card]]
id = "T-01"
statement = "For skew-symmetric Ω, cay(Ω)ᵀ·cay(Ω) = I and det cay(Ω) = 1."
tier = ["S", "F"]                      # one per route, in route order
routes = [ { kind = "poly-identity", class = "Certified", status = "hypothesis" },
           { kind = "lean-capsule",  class = "Proved",    status = "hypothesis" } ]
constructions = ["C-05"]
consumers = ["K-cay-step"]
statement_doc = "docs/math/cards/T-01.md"
receipts = []                          # certificate or capsule hashes with checker identities
```

   Per route, two more fields: `route` (the `Route` that N12-01's `choose_route` returns for the card's shape) and,
   for a `lean-capsule` route, `statement` (the registered module, e.g. `lean/Frob/Statements/T01.lean`) with
   `statement_hash` (the elaborated-type hash that the binding check of N12-24 compares; empty until the card bead
   writes the module, and a Lean route cannot leave `hypothesis` while it is empty). The row of T-35 carries
   `sub_entries = [{ reflector, statement_hash, check_definition_hash, capsule, checkers, status }]`, one per
   reflector (`farkas`, `ldlt-pos`, `poly-eq`, `replay`), each with the same status machine as a route
   (CARD-T-35). The file header records the `registries/prooftools.toml` revision the routes were chosen under.

2. Seed (id, tier): T-01 [S]/[F]; T-02 [S]; T-03 [S]/[F]; T-04 [S]; T-05 [S]; T-06 [F] (budget is a HYPOTHESIS);
   T-07 [F]; T-08 [F]; T-09 [S]; T-10 [F]; T-11 [S]; T-12 [F]; T-13 [M]; T-14 [M]; T-15 [S]/[F]; T-16 [S];
   T-17 [F]; T-18 [F]; T-19 [S]; T-20 [F]; T-21 [F]/[S]; T-22 [S]; T-23 [S]/[F]; T-24 [S]/[F]; T-25 [F];
   T-26 [S]/[F]; T-27 [F]; T-28 [S]; T-29 [S]; T-30 [F]; T-31 [S]; T-32 [F]; T-33 [F] (budget is a HYPOTHESIS);
   T-34 [M]; T-35 [F]. Statements and routes are those of the thirty-five card beads; the seed copies them.
3. Status machine per route: `hypothesis → checked` on a receipt from the route's checker; `checked → withdrawn`
   when a receipt's kernel, model or statement hash no longer matches or its proof kind is disabled;
   `hypothesis → parked` (with the unblock condition named) for a Moonshot or blocked route; `hypothesis →
   fell-back` (with the fallback's class) when a kill gate fires. A route in `hypothesis` prints no class.
4. Class of a card as printed: the strongest class among routes in status `checked`; a route's class is printed
   only with its receipt hash and checker identity (INV-LEMMA-01). A card with no checked route prints
   `hypothesis`.
5. Admission rule: adding a card requires a route whose kind is in `frob.cert.kinds/1` or a decision procedure
   named in the route table (`kir-typecheck`, `exhaustive-enumeration`, `bit-vector`); a row whose route is none of
   these fails the registry check with "not decidable here: file under the non-decidable obligations".
6. `prove.list --json` (output schema `frob.prove.list.out/1`): `cards[]` with id, statement, tier, per-route
   kind, route, class, status, receipts (and T-35's sub-entries); `certificates[]` with kernel or mission identity,
   kind, class, hash, checker; `prooftools_revision`. Evidence block: claim Proof. The envelope carries the three
   flags, false. This bead provides the rows as a function of the registry and the receipt store
   (`frob_lemma::cards::list_rows`, DESIGN); the verb that serves them is BD-027's, which depends on this bead.
7. Identifiers are never renumbered; a retired card is tombstoned, not reused.

## Acceptance criteria

- [ ] `registries/theorems.toml` holds thirty-five rows, schema-valid; ids T-01 to T-35 with no gap or duplicate.
- [ ] At creation every route is `hypothesis` (T-13, T-14 and T-34 `parked` with their unblock conditions) and
      `list_rows` gives no class for any card.
- [ ] A row edited by hand to `checked` with no receipt fails the registry check (negative control).
- [ ] A row whose route names a kind outside the closed registry fails the admission check.
- [ ] Given receipts for T-01, T-03 and T-04 (the fixture receipts of BD-021), `list_rows` shows exactly those
      three rows `Certified` with certificate hashes and the checker identity, and nothing else changed. The same
      flip on the live receipts is observed by GATE-LEMMA-00 in `scripts/e2e/lemma_kernel_cert.sh` (N12-33, which
      depends on this bead) through `frob prove list --json`.
- [ ] The output of `list_rows` validates against `frob.prove.list.out/1` and round-trips the registry content;
      every route row carries its `route` and the prooftools revision.

## Test plan

### Unit tests

`crates/frob-lemma/tests/card_registry.rs`: `seed_has_35_cards`; `ids_contiguous`; `initial_status_hypothesis`;
`checked_without_receipt_rejected`; `receipt_hash_mismatch_withdraws` (change the kernel hash of a certified
kernel; the route becomes `withdrawn`); `admission_requires_decidable_route` (a row with route "symplecticity of
the articulated step" is rejected); `printed_class_is_strongest_checked_route`; `moonshot_route_parks` (T-13 prints
`parked: blocked Mathlib modules`); `seed_tiers_match_plan` (the 35 tiers of step 2, including T-21 [F]/[S] in that
order); `seed_parked_rows` (T-13, T-14, T-34 parked at creation); `lean_route_requires_statement_hash` (a Lean
route moved to `checked` with an empty `statement_hash` is rejected); `t35_sub_entries_schema` (four sub-entries,
each `hypothesis`; one hand-edited to `checked` without a capsule is rejected); `rows_carry_route_and_revision`;
`list_rows_schema_valid_and_roundtrip`; `three_receipts_flip_three_rows` (fixture receipts for T-01, T-03, T-04:
exactly those rows change); `tombstoned_id_not_reused`; `listing_sorted_and_byte_identical` (two runs, two
processes).

### End-to-end script and logging

`scripts/e2e/lemma_kernel_cert.sh` (bead N12-33) calls `frob prove list --json` before and after certification
and logs the three rows that change with their receipts. Those NDJSON lines (STD-E2E helper) carry `ts`,
`script`, `bead` ("N12-06"), `step` (`list/before`, `list/after`), `event`, the exact command line, exit code, wall
time, the BLAKE3 of each listing, the count of rows per status, and per changed row its id, route, old and new
status, class, receipt hash and checker identity; a mismatch (any row other than T-01, T-03, T-04 changed, or a
class printed without a receipt) is logged with the row diff and the path to reproduce.

### Known answers and negative controls

KA-220 (T-01, T-03, T-04 certified and replaying offline is what flips the first three rows). Negative controls:
the hand-edited row; a receipt bound to another kernel. Determinism: the listing is sorted by id and identical
across machines.

## Considerations

- A registry exists only because a verb reads it and a gate checks it; `prove.list` and the lemma gates are those
  readers.
- RISK-11: the registry is where "Certified" could become a marketing word; the receipt requirement is the guard.
- OPEN-LEMMA-6 (T-24's counting lemma) and OPEN-LEMMA-1 (closure cost) determine when Lean routes may leave
  `hypothesis`.
