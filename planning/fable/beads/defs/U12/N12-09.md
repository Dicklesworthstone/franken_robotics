## Background

A certificate is only as good as the independence of what checks it. If the checker shares a parser, a hash
implementation, an arithmetic library or a units crate with the code that produced the bundle, one defect can make
both agree. The smallest case that shows it: a canonicalization defect in the producer's hashing that drops a
field before hashing would be reproduced by a checker that reuses that hashing, and a bundle whose statement
differs from the one the proposer evaluated would pass; with two implementations the hashes disagree and the
bundle is rejected.

INV-LEMMA-05 states the invariant: `frob-cert` depends on the standard library only, and producers do not call its
decision code to build witnesses. "A producer never calls the auditor's decision code to construct a witness, so
the two share a format and nothing else." The first half is structural and is enforced by the workspace check
`xtask check-deps` (layer rule L-9: `frob-cert` has an empty dependency table, and only `frob-verbs`, `frob-cli`
and `frob-conformance` may depend on it). The second half needs more than a dependency listing: `frob-verbs` is
allowed to link the checker in order to run it before an answer returns, and nothing in a dependency listing stops
code reachable from a producer from calling a checker function while it searches for a witness. This bead adds the
call-graph lint and the shared-source check, and records the invariant test. Tier: Solid. Rejected alternative:
trusting review (the shortcut "let the solver ask the checker whether this candidate passes" is exactly what a
search loop wants, and it turns the checker's blind spots into the producer's target).

## Scope

In: the test that asserts the dependency listing; the call-graph lint over the workspace; the shared-source-file
check between `frob-cert` and every proposer crate; registration of all three as negative-controlled tests.
Out: `check-deps` itself and rule L-9 (BD-003); the system-call trace of the auditor (BD-026, GATE-WS-03); the
seeded-fault independence campaign with at least 200 mutants per kind (BD-136, BD-294).

## Technical approach

1. Dependency listing. A test runs `cargo tree -p frob-cert --edges normal,build` and asserts one line of output;
   it also asserts that `cargo tree -i frob-cert` (reverse dependencies) lists only `frob-verbs`, `frob-cli` and
   `frob-conformance`. Proposer crates (`frob-lemma`, `frob-mission`, `frob-synth`, `frob-shield`, `frob-opt`,
   `derive/frob-derive`, and any crate that emits a proof object) must not appear.
2. Call-graph lint (DESIGN). `frob-verbs` links both sides, so the lint works on symbols, not crates:
   - `frob-cert` exposes its decision code behind one public entry, `frob_cert::audit(bytes) -> Report`, and marks
     every per-kind checker `pub(crate)`.
   - In `frob-verbs`, the only call site of `frob_cert::audit` is the function `run_checker_before_return`, which
     takes a finished, serialized bundle and returns the report; a source scan asserts that the symbol appears
     nowhere else in the workspace outside `frob-cli` (the `prove verify` command) and `frob-conformance`.
   - No function in `frob-verbs` passes the report back into a producer API: the lint checks that
     `run_checker_before_return` is called only from the answer-finalization path, after the proof search has
     returned, and that its result is used only to return, withhold or downgrade.
3. Shared-source check. The test hashes every source file under `crates/frob-cert/src` and asserts that no file
   under any proposer crate has the same content hash, and that no path under `frob-cert` is a symbolic link or an
   `include!` of a path outside the crate. Zero shared source files is the pass condition.
4. Vendored-copy check: a token-level similarity scan between `frob-cert`'s arithmetic modules and the producer's
   rational and interval code flags near-copies above a threshold (DESIGN: 80% identical token 5-grams per file,
   a number chosen for this lint and reported, not a gate). A flagged pair is a review item, because a copied file
   shares defects as surely as a linked one.
5. Each of the three checks has a negative control kept in the test tree: a fixture workspace in which `frob-lemma`
   depends on `frob-cert`; a fixture source in which a search loop calls `frob_cert::audit`; a fixture proposer
   file byte-identical to an auditor file. The checks must fail on the fixtures.

## Acceptance criteria

- [ ] INV-LEMMA-05 holds: `cargo tree -p frob-cert` prints one line; the reverse-dependency list is exactly
      `frob-verbs`, `frob-cli`, `frob-conformance`.
- [ ] The call-graph lint passes on the workspace and fails on the planted search-loop fixture.
- [ ] Zero source files are shared between `frob-cert` and any proposer crate; the planted identical file is
      caught.
- [ ] The three checks run in the `smoke` battery and their negative controls are registered in the
      negative-control registry.
- [ ] The result (dependency closure `std`; zero shared source files) is recorded for the independence gate that
      cites it.

## Test plan

### Unit tests

`crates/frob-conformance/tests/auditor_independence.rs`: `frob_cert_tree_is_one_line`;
`reverse_deps_are_exactly_three`; `audit_symbol_call_sites` (expects exactly the allowed sites);
`checker_result_not_fed_to_producer`; `no_shared_source_files`; `no_include_outside_crate`;
`fixture_dependency_is_caught`; `fixture_search_loop_is_caught`; `fixture_identical_file_is_caught`;
`similarity_scan_reports` (prints the highest similarity pair and its score).

### End-to-end script and logging

`scripts/e2e/lemma_auditor_mutations.sh` (bead N12-34) logs, before the mutation run, the dependency listing, the
reverse-dependency listing and the shared-file count as `metric` lines with thresholds 1, 3 and 0.

### Known answers and negative controls

Known answer: `cargo tree -p frob-cert` prints one line. Negative controls: the three fixtures above. The
canonicalization counterexample (a dropped field hashed identically by a shared implementation) is kept as a
written case in the test's documentation and realized by the mutation "drop one field before hashing in the
producer", which the independent auditor must reject by hash mismatch. Determinism: not applicable.

## Considerations

- RISK-36 (the proposer and the checker share a defect): early signals are a source file shared between
  `frob-cert` and a proposer and a checker dependency beyond the standard library. If one auditor is judged not
  enough, a second independent checker is added (OPEN-LEMMA-4, bead N12-29).
- A FrankenSymPy-based re-check of the same bundles runs in `frob-conformance` as a second opinion; it is an
  oracle for the auditor and never a part of it (N12-10).
- The lint must stay small: `xtask` has six checks by rule, so these live as tests in `frob-conformance`, not as a
  seventh `xtask` subcommand.
