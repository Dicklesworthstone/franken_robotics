## Background

The offline auditor `frob-verify` implements for itself everything it needs: a canonical-JSON reader, its own
BLAKE3, big-integer and rational arithmetic, and outward-rounded intervals built on integers. That independence
is the point (a checker that shares a hash or arithmetic library with the producer can share its defect), and it
has a cost: the auditor's own implementations could be wrong in a way nothing else notices. Two proof obligations
close that gap without linking anything into the auditor:

- PO-LEMMA-02: the auditor's BLAKE3 equals `fs-blake3`, on the published test vectors and on 10⁶ random inputs.
- PO-LEMMA-04: the rational and interval arithmetic of the auditor agrees with FrankenSymPy's on a shared corpus,
  in a differential test at build time; FrankenSymPy is not linked into the auditor.

The comparisons run in `frob-conformance`, which is allowed to depend on `frob-cert` and reaches the siblings for
re-check only. A FrankenSymPy-based re-check is an oracle for the auditor, never a part of it. Tier: Solid.
Rejected alternative: checking the auditor only against its own specimens (a symmetric error in rational
reduction or in rounding direction would pass every specimen written with the same misconception).

## Scope

In: the BLAKE3 vector test and the 10⁶-input differential; the shared arithmetic corpus and its generator; the
differential harness against FrankenSymPy for rationals and for interval enclosures; the canonical-number-form
cross-check; registration with negative controls.
Out: the implementations under test (BD-026); the bundle-level second opinion and the question of a second
checker (N12-29); mutation campaigns on bundles (BD-136).

## Technical approach

1. BLAKE3, published vectors. The official test-vector file (input lengths 0, 1, 2, 3, 4, 5, 6, 7, 8, 63, 64, 65,
   127, 128, 129, 1023, 1024, 1025, 2048, 2049, 3072, 3073, 4096, 4097, 5120, 5121, 6144, 6145, 7168, 7169, 8192,
   8193, 16384, 31744, 102400 bytes of the repeating pattern 0..250) is vendored under
   `crates/frob-conformance/fixtures/blake3/` with its source and date. The auditor implements the three modes
   (BD-026: plain hash, keyed hash and derive-key, with arbitrary output length; identities in this project are
   BLAKE3 in derive-key mode with the schema name as the context string, BD-005), so all three are checked: for
   every length, the auditor's output equals the file's `hash`, `keyed_hash` (under the file's 32-byte key) and
   `derive_key` (under the file's context string) values, each in full, 131 bytes of extended output, and in its
   first 32 bytes, the default digest.
2. BLAKE3, random differential. 10⁶ inputs drawn from a seeded counter-based stream (seed recorded in the log):
   lengths uniform in [0, 4096] for 90% of cases and log-uniform up to 2²⁰ bytes for 10%, so that chunk and tree
   boundaries (1,024-byte chunks, parent nodes) are crossed many times. For each, the auditor's plain digest is
   compared with `fs_blake3::hash_bytes`, and its derive-key digest, under a context drawn from the registered schema
   names (`frob.cert/1`, `frob.design/1`, `frob.run/1` and the others of the format registry), with
   `fs_blake3::hash_domain(context, input)`; all 32 bytes, zero mismatches. FACT (`fs-blake3`, read 2026-11-23): its
   public interface is `hash_bytes`, `hash_domain` and the streaming `DomainHasher`, with 32-byte output and no
   keyed mode, so the keyed mode and outputs beyond 32 bytes have the published vectors as their only oracle.
3. Arithmetic corpus (DESIGN; shared, generated once and checked in as canonical JSON with its generator and
   seed): (a) 10⁵ rational expressions over +, −, ×, ÷ with numerators and denominators up to 4,096 bits, including
   zeros, sign combinations, non-reduced inputs and results that reduce to integers; (b) 10⁴ comparisons and sign
   tests, including equal values in different unreduced forms; (c) 10⁴ small exact linear-algebra cases: matrix–
   vector products, LDLᵀ pivot sequences of symmetric rational matrices up to 8×8, both definite and indefinite;
   (d) 10⁴ interval enclosures of polynomial and rational expressions over boxes of up to six coordinates with
   rational endpoints; (e) edge cases: division by an interval containing zero (must be refused by both or
   reported as unbounded by both), empty boxes, degenerate (point) intervals.
4. Differential harness. For (a) to (c) both sides compute and the results are compared as canonical reduced
   rationals, exactly. For (d) the property is containment, not equality: the auditor's interval must contain
   FrankenSymPy's exact range bound where FrankenSymPy can compute the range exactly, and the two outward-rounded
   enclosures must overlap and each contain a set of 100 exact rational sample values of the expression in the
   box. A sample value outside the auditor's enclosure is a soundness failure.
5. Build-time position: the harness is a test target of `frob-conformance` run in the `fixtures` battery and in
   continuous integration whenever `crates/frob-cert` changes. Nothing from FrankenSymPy is a dependency of
   `frob-cert` (asserted by N12-09). Its two row-level functions are also registered as the entries KA-223 and
   KA-225 of the G2 table (site `auditor`), so the known-answer rows run in the Gauntlet's form
   `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g2_parity -- KA-223` (and `-- KA-225`), and each
   run writes a receipt with the seed, the case counts and the mismatch totals. The four planted builds of the
   acceptance list are Cargo features of `frob-cert`, one `cfg` branch each at the site it corrupts, built one at
   a time as `--features gauntlet-mutations,frob-cert/<plant>` (convention 1; the released `frob-verify` carries
   none): `blake3-iv-word` (one IV word changed), `blake3-no-derive-key-flag` (derive-key material hashed without
   the derive-key flag), `rational-skip-sign-normalization` (3/−2 left as is) and `interval-sub-inward` (the lower
   endpoint of a subtraction rounded up).
6. Canonical number form cross-check: every rational the auditor writes is reduced with positive denominator; the
   harness re-parses the auditor's output with FrankenSymPy and asserts identical normal form.
7. Records: the corpus digest, both tool builds, mismatch count and, on failure, the first differing case with
   both values.

## Acceptance criteria

- [ ] PO-LEMMA-02: the auditor's BLAKE3 matches every published vector in the three modes (with the 131-byte
      extended output) and `fs-blake3` on 10⁶ random inputs in plain and derive-key modes with zero mismatches;
      the seed and the count are recorded.
- [ ] PO-LEMMA-04: zero disagreements on the rational, comparison and linear-algebra corpus; every interval case
      satisfies containment of all exact samples; division by a zero-containing interval is handled identically.
- [ ] Negative controls caught: an auditor build with one BLAKE3 IV word changed; a build
      that drops the derive-key mode flag; a build
      whose rational reduction skips the sign normalization; a build whose interval subtraction rounds the lower
      endpoint up (inward).
- [ ] FrankenSymPy does not appear in `cargo tree -p frob-cert`; the harness lives in `frob-conformance`.
- [ ] The corpus and vectors are pinned fixtures with provenance; they are never regenerated from the candidate.
- [ ] `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g2_parity -- KA-223` and `-- KA-225` select
      exactly this bead's entries and write receipts; `scripts/e2e/lemma_auditor_oracles.sh` passes and its log
      ends with a `summary` line.

## Test plan

### Unit tests

`crates/frob-conformance/tests/auditor_oracles.rs`:
- `blake3_published_vectors` (35 lengths, modes `hash`, `keyed_hash` and `derive_key`, 32-byte and 131-byte
  outputs); `blake3_empty_input` (digest `af1349b9f5f9a1a6a0404dea36dcc9499bcb25c9adc112b7cc9a93cae41f3262`);
  `blake3_random_1e6` (plain mode against `hash_bytes`); `blake3_derive_key_random` (derive-key mode against
  `hash_domain` with schema names as contexts); `blake3_identity_matches_core` (the identity of a stored specimen
  recomputed by the auditor equals `frob-core`'s identity of the same canonical bytes, the cross-check that makes
  the two implementations meet on the convention of BD-005).
- `rational_corpus_agrees`; `rational_nonreduced_inputs` (6/−4 equals −3/2 on both sides);
  `ldlt_pivots_agree` (a 4×4 pseudo-inertia fixture gives the same pivot sequence and the same sign verdict).
- `interval_contains_exact_samples`; `interval_division_by_zero_interval`; `interval_point_degenerate`.
- `inward_rounding_mutant_is_caught` (negative control: the planted build fails containment on at least one case);
  `blake3_constant_mutant_is_caught` (one IV word changed in a planted build: the published vectors fail at
  length 0); `sign_normalization_mutant_is_caught` (a planted reduction that leaves 3/−2 as is: the canonical
  comparison fails).
- `canonical_form_reparse` (step 6: every rational the auditor writes re-parses in FrankenSymPy to the identical
  normal form); `blake3_mode_flag_mutant_is_caught` (a planted build that hashes derive-key material without the
  derive-key flag: every `derive_key` vector and the derive-key differential fail).
- `corpus_digest_pinned` (the harness refuses a corpus whose digest differs from the pinned one; regenerating from
  the checked-in generator and seed reproduces that digest); `no_frankensympy_in_frob_cert_tree`;
  `fsympy_unavailable_records_not_run` (with the sibling absent the PO-LEMMA-04 record reads `not run`, and the
  test asserts that this is not reported as a pass).

### End-to-end script and logging

This bead's own script, `scripts/e2e/lemma_auditor_oracles.sh` (header `bead=N12-10 milestone=M1
labels=lemma,frob-conformance seed=1 needs=cpu`; sources the STD-E2E helper, idempotent, writes only under
`target/`), runs `FROB_TEST_SEED=1 cargo test -p frob-conformance --test g2_parity -- KA-223` and `-- KA-225`,
then, once per planted build of step 5, the row it corrupts (KA-223 for the two BLAKE3 plants, KA-225 for the two
arithmetic plants) with `--features gauntlet-mutations,frob-cert/<plant>` through `e2e_expect_caught` (each
planted build must be caught), reads the receipts and logs counts, seeds, tool builds and mismatch totals as `metric` lines against
the threshold 0. The directory-driven script of N12-34, which depends on this bead, runs it as a stage. Its
NDJSON lines (`target/e2e-logs/lemma_auditor_oracles/<utc>.ndjson`, transcript beside it) carry `ts`, `script`,
`bead` ("N12-10"), `step` (`oracle/blake3-vectors`, `oracle/blake3-random`, `oracle/blake3-derive-key`,
`oracle/rational`, `oracle/compare`, `oracle/linalg`, `oracle/interval`, `oracle/edge`), `event`, the exact
command line, exit code, wall time, the seed, the case count, the corpus digest, the `frob-cert` build and the
`fs-blake3` and FrankenSymPy builds, bytes hashed per side, the mismatch or containment-failure count against 0,
and on a failure the first differing case (input or expression, both values, the box and the offending sample)
with the path to the fixture that reproduces it; a final `summary` line states PO-LEMMA-02 and PO-LEMMA-04 as
`pass`, `fail` or `not run`.

### Known answers and negative controls

KA-223 (the auditor's BLAKE3 equals the published vectors and `fs-blake3` on 10⁶ random inputs; exact digest;
tier G2, auditor), KA-225 (rational and interval arithmetic agree with FrankenSymPy's on a shared corpus; tier
G2). Negative controls are the four planted builds. Determinism: the random stream is seed-explicit; the
harness is bit-reproducible on one machine and across platforms.

## Considerations

- Agreement with a second implementation is Parity, not proof: both could share a misreading of a specification.
  The published vectors and the exact-sample containment test are the parts that do not depend on the sibling.
- 10⁶ BLAKE3 cases with lengths up to 2²⁰ bytes cost on the order of a gigabyte hashed per side; the long-length
  share is capped so the test stays within the `fixtures` battery's time.
- If FrankenSymPy is unavailable at a milestone (it is not needed for the mission slice, because the auditor uses
  the standard library alone), PO-LEMMA-04 is recorded `not run`, which is not a pass.
