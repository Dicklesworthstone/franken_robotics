## Background

Instance certificates are produced at build time by `derive/frob-derive` and checked by FrankenSymPy. Each is
stored beside the kernel as `K-<name>.cert` with the kernel's content hash inside, and `frob prove verify`
re-checks certificates offline. At M0 this exists for three identities on two kernels. For coverage across the
kernel library (GATE-LEMMA-01) two things are missing: a catalogue that says which identities each kernel family
must declare and by which route each is decided, and a pipeline that turns a kernel's straight-line program and a
declared identity into a certificate, handling the constructs that are not plain polynomials. This bead builds
both. The coverage measurement is BD-379.

What can be certified is fixed by the algebraic route: a kernel's arithmetic is a straight-line program over +,
−, ×, ÷, √ and selects; identities the kernel must satisfy are polynomial identities, checked by FrankenSymPy's
proof kernel (claim `AlgebraicIdentity`, rule `PolynomialNormalForm`, offline verifier `fsym-capsule-consumer`)
and bound to the kernel's content hash. Certificates are over ℚ with square roots; rounding is not modeled. Tier:
Frontier (BET-11). Rejected alternatives: certifying a whole robot's dynamics as one expression (expression swell
breaks the tool's budgets; derivation and certification are per kernel body and per limb, never per robot);
certifying kernels with data-dependent selects as one identity (not a polynomial statement).

## Scope

In: `registries/identities.toml` (the catalogue); the manifest check that a derived kernel declares what its
family requires; the pipeline stages; the three reductions (denominator clearing, square-root witnesses, select
branches); the certificate file layout and its binding to the kernel hash; budgets and status codes.
Out: FrankenSymPy admission and the M0 certificates (BD-019, BD-021, BD-027); the budget pilot (N12-22);
randomized identity testing as a `Tested` route and fallback (N12-21); the coverage gate (BD-379); Lean capsules.

## Technical approach

1. Catalogue (DESIGN; one row per kernel family and identity; the card beads hold the full statements):

| Kernel family | Declared identity | Card | Route and bundle kind |
|---|---|---|---|
| Cayley rotation and SE(3) update (`K-cay-step`) | cay(Ω)ᵀ·cay(Ω) = I, det cay(Ω) = 1; the SE(3) update maps the group to itself | T-01, T-02 | `poly-identity` after clearing the denominator 4 + ‖ω‖² |
| Quaternion update, normalization (`K-normalize`) | ‖q·c‖² = ‖q‖²·‖c‖² | T-03 | `poly-identity`; the normalization's √ by a witness |
| Adjoint and frame-map kernels | Ad(gh) = Ad(g)·Ad(h); group coadjoint is the inverse transpose; pairing invariant | T-04, T-05 | `poly-identity` in group coordinates |
| Convention kernels (ad, ad*, parity map) | ⟨ad_ξᵀ μ, η⟩ = ⟨μ, [ξ, η]⟩; T(P) preserves bracket and pairing | T-16 | `poly-identity` (eighteen variables for the first) |
| Free-body variational step | Spatial momentum is conserved | T-06 | ideal membership modulo the update equations |
| Cone projection kernels (three- and four-dimensional) | P(x) ∈ 𝒦, P(x) − x ∈ 𝒦*, ⟨P(x), P(x) − x⟩ = 0 | T-07 | per-case identities and inequalities, one per select branch |
| Transmission and port kernels | e₁·f₁ + e₂·f₂ = 0 from f₂ = r·f₁, e₁ = −r·e₂ | T-15 | `poly-identity` after substitution |
| Step kernels of a model | Equivariance under each generator of the mechanical symmetry group | T-10 | `poly-identity` per generator on branch-free pieces; otherwise `Tested` |
| Saltation kernels | The saltation formula for the flow, guard and reset, denominator cleared | T-17 | `poly-identity` per event class |
| Symmetry–event kernels | ρ(h)·Ξ_e = Ξ_{h·e}·ρ(h) | T-18 | `poly-identity` per pair, or randomized identity testing |
| Recursion kernels (mass matrix, bias) | Ṁ − 2C + (Ṁ − 2C)ᵀ = 0 | T-33 | identity modulo cᵢ² + sᵢ² = 1, per limb |
| Inertia tables of a model | Each pseudo-inertia positive definite; mass-support bound | T-19 | `rational-ldlt`; one rational inequality |
| Every kernel | Dimensional homogeneity; square roots on even exponent vectors | T-09 | decided by the kernel-IR type checker |

2. Manifest check: a derived kernel's manifest lists its `family`; the identities it declares must include every
   catalogue row of that family, otherwise the kernel is `uncovered: under-declared`.
3. Pipeline, per (kernel, identity):
   a. Load the kernel's straight-line program and its content hash (`KernelId`).
   b. Translate the identity into an expression pair (lhs, rhs) over the program's inputs and outputs by
      symbolic execution of the program in FrankenSymPy expressions.
   c. Reduce: clear denominators (each division introduces a nonvanishing side condition that is recorded and
      must itself be a declared assumption, for example 4 + ‖ω‖² ≠ 0, which holds over the reals); replace each
      square root by a witness symbol t with the side relation t² = radicand (and t ≥ 0 recorded); for each
      select, split into one identity per branch under its guard; for trigonometric coordinates use (cᵢ, sᵢ)
      with the side relation cᵢ² + sᵢ² = 1.
   d. Choose the route (N12-01): direct normal-form equality when there are no side relations; ideal membership
      (lhs − rhs in the ideal generated by the side relations) when there are; refuse to the `Tested` route when
      a cap is exceeded.
   e. Run FrankenSymPy's proof kernel in a subprocess with a time and memory budget; collect its capsule.
   f. Write `K-<name>.cert`: canonical JSON holding the kernel content hash, the identity text, the reduced
      polynomial pair or the membership cofactors, the side relations and nonvanishing conditions, the route,
      the tool build, and the capsule digest; write the corresponding `.frobcert` bundle of kind `poly-identity`
      (for ideal membership the bundle carries the cofactors qⱼ with lhs − rhs = Σ qⱼ·gⱼ, which is again a
      polynomial identity the auditor can expand), and store the bundle digest in the kernel's `proof_digest`.
   g. Replay: `frob prove verify` and `frob-verify` must accept the bundle; a certificate that the tool accepted
      and the auditor rejects is a defect, not a covered identity.
4. Status per (kernel, identity): `certified`, `budget-exceeded` (with the cap named: 8,192 operations, 1,024
   basis polynomials, time, memory), `not-polynomial` (a data-dependent select that cannot be split, an
   elementary function), `tested-only` (routed to N12-21).
5. Regeneration is deterministic: the same kernel and identity produce byte-identical certificates; certificates
   are regenerated when the kernel hash changes, and a stale certificate (hash mismatch) never counts.

## Acceptance criteria

- [ ] `registries/identities.toml` holds the catalogue rows above, schema-valid, each naming its card.
- [ ] The pipeline certifies T-01, T-02 and T-03 on the M0 kernels end to end and the bundles replay in
      `frob-verify`.
- [ ] A kernel with a square root is certified through a witness: the bundle carries t² = radicand as a side
      relation, and removing that relation makes the auditor reject (missing side condition, FROB-REF-829).
- [ ] A kernel with one select yields two certificates, one per branch, each with its guard recorded.
- [ ] An identity over the operation cap returns `budget-exceeded` naming the cap, before any long tool run.
- [ ] A certificate bound to a different kernel hash is not accepted as covering the kernel.
- [ ] Mutated kernels (a flipped sign; a dropped term) produce no certificate: the tool refuses, and a forged
      certificate for them is rejected by the auditor.

## Test plan

### Unit tests

`crates/frob-lemma/tests/producer.rs`: `cayley_orthogonality_certifies` (the identity in the three entries of ω
after multiplying through by (4 + ‖ω‖²)²); `quaternion_norm_certifies`; `sqrt_witness_side_relation_recorded`;
`sqrt_witness_removed_rejects`; `select_splits_into_two`; `ideal_membership_cofactors_expand` (a planar identity
modulo c² + s² = 1: (c² + s²)·x − x has cofactor x); `over_cap_is_budget_exceeded`;
`stale_hash_does_not_cover`; `mutant_flipped_sign_no_certificate`; `mutant_dropped_term_no_certificate`;
`regeneration_is_byte_identical`; `under_declared_kernel_is_uncovered`.

### End-to-end script and logging

`scripts/e2e/lemma_coverage.sh` (bead N12-36) runs the pipeline over the library; per (kernel, identity) it logs
status, route, operation count, basis size where applicable, wall time, peak memory, certificate and bundle
digests.

### Known answers and negative controls

KA-211 (T-01 for the Cayley kernel: `accept`; one changed coefficient gives `reject`), KA-220. Negative controls:
the two mutants; the removed side relation; the stale hash. CX-112 (the certificate is about the program over ℚ
with square roots, not its floating-point output). Determinism: byte-identical regeneration on one machine and
across machines; the tool subprocess is pinned.

## Considerations

- RISK-07: expression swell on a 29-joint humanoid; the early signal is derivation time and peak memory per
  kernel body. Mitigation is structural: per body and per limb.
- Upstream items that raise what the pipeline can certify: FD-FSYM-01 (lift the 8,192-operation cap; interim:
  `frob-kir` owns code generation), FD-FSYM-02 (a Lie-algebra module; interim: explicit matrices in
  `derive/frob-derive`), FD-FSYM-04 (matrix-identity certificate families; interim: entry-wise identities),
  FD-FSYM-05 (faster Gröbner bases; interim: leg-sized systems).
- The nonvanishing conditions introduced by clearing denominators are part of the statement; a certificate that
  hides one certifies a weaker statement than the manifest declares.
- KILL-LEMMA fallback removes the word "certificate" from manifests and keeps this catalogue as the list of
  identities that randomized tests exercise.
