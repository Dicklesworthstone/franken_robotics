## Background

Kernel reflection promotes an instance certificate to `Proved`: a checker function defined in Lean, with a
soundness theorem `check x = true → Spec x`, lets the kernel prove an instance by evaluating `check x`. The
soundness theorem is proved once in stock Lean with Mathlib and re-checked by FrankenLean. That re-check is
possible only if the theorem's dependency closure avoids the Mathlib modules FrankenLean cannot accept today
(`Geometry.Manifold.Algebra.LieGroup`, `Analysis.Normed.Algebra.MatrixExponential`, `Analysis.Quaternion`, all
representation theory, and whatever else its ledger lists as not accepted).

OPEN-LEMMA-2 is the question: do the soundness theorems of the reflectors have closures that avoid the blocked
modules? Fail-closed default: specifications are stated in elementary form, without analysis modules. It blocks
GATE-LEMMA-05, and half of the kill trigger of KILL-REFLECT is exactly its negative answer ("no reflector's
closure avoids the blocked modules"). The four planned specifications were written with this in mind: Farkas
soundness for x over every linearly ordered field containing ℚ; positive definiteness stated as
∀ x ≠ 0, 0 < x ⬝ᵥ A·x without `Matrix.PosDef`, "to keep the dependency closure inside algebra"; polynomial
normal-form equality over every commutative ℚ-algebra; trace replay with equality over ℝ. Whether those choices
suffice is cheap to find out before any proof is written: the closure of a statement is determined by what its
statement and the natural proof import. This bead finds out. It is the first step of the reflection pilot and
must precede BD-382.

## Scope

In: for each of the four soundness statements, a Lean file with the definitions and the statement and a
placeholder proof used only for closure analysis (never sealed); the import closure and its intersection with
blocked and not-accepted modules; alternatives where a statement's first form is blocked; the recorded answer.
Out: the real proofs and the specimens (BD-382, N12-28); kernel-evaluation cost (N12-27); the decision
(N12-32).

## Technical approach

1. Statements analysed (as registered `Statement` definitions, see the binding rule of N12-24):
   - `farkas_sound`: for M : Matrix (Fin m) (Fin n) ℚ, r y : Fin m → ℚ and any linearly ordered field K,
     `farkas M r y = true → ¬ ∃ x : Fin n → K, (∀ j, 0 ≤ x j) ∧ (M.map Rat.cast).mulVec x = fun i => (r i : K)`.
   - `ldltPos_sound`: for symmetric A over ℚ and any linearly ordered field K,
     `ldltPos A = true → ∀ x : Fin n → K, x ≠ 0 → 0 < x ⬝ᵥ (A.map Rat.cast).mulVec x`.
   - `polyEq_sound`: `polyEq p q = true → ∀ (R) [CommRing R] [Algebra ℚ R] (ρ : ℕ → R), p.eval ρ = q.eval ρ`.
   - `replay_sound`: `replay src t = some tgt → ∀ ρ : ℕ → ℝ, src.denote ρ = tgt.denote ρ`.
2. For each: write the definitions of the checker's input types (`PolyExpr`, `Slp`, `Trace`) in the project's
   namespace with the narrowest imports; elaborate the statement under stock Lean at the pin; compute the
   transitive import closure of the file; intersect with the blocked list and with FrankenLean's not-accepted
   ledger; record module count and the intersection.
3. Known pressure points to examine and record explicitly: `LinearOrderedField` and `Rat.cast` (algebra and order
   only, expected clean); `Matrix.mulVec` and dot product (linear algebra basics, expected clean); the statement
   over ℝ in `replay_sound` (the real numbers are constructed through Cauchy sequences in Mathlib's data layer;
   whether that module and its closure are accepted must be read from the ledger; if not, the alternative is to
   state `replay_sound` over every field or every commutative ring that the straight-line program's operations
   make sense in, with division handled by a nonvanishing hypothesis, which avoids ℝ entirely).
4. For a statement whose first form meets a blocked module, try the elementary alternative, record both, and
   recommend the form to register.
5. Answer per reflector: `clean` (closure avoids every blocked module), `clean in alternative form` (with the form
   given), or `blocked` (with the module). OPEN-LEMMA-2 is closed with the table. If every reflector is `blocked`,
   the second half of KILL-REFLECT's trigger is met and N12-32 decides without waiting for proofs.

## Acceptance criteria

- [ ] All four statements elaborate under stock Lean at the pinned version with their placeholder proofs, and
      their closures are listed.
- [ ] Each has an answer `clean`, `clean in alternative form` or `blocked`, with the module names behind it.
- [ ] The placeholder proofs are confined to a directory that the sealing pipeline refuses to seal (a `sorry` is
      refused at sealing; a test asserts it).
- [ ] OPEN-LEMMA-2 is closed in the open-question register with the table; the forms recommended are the ones
      registered for BD-382 and N12-28.
- [ ] Negative control: a deliberately analytic restatement (positive definiteness through `Matrix.PosDef`, or a
      statement through the matrix exponential) is reported with a larger closure and, for the exponential, as
      `blocked`.

### End-to-end script and logging

`scripts/e2e/pilot_lean_closure.sh` (shared with N12-23) gains a step `open-lemma-2` logging, per statement, the
module count, the blocked intersection (threshold 0) and the answer.

### Known answers and negative controls

The blocked list at the pin is the known answer the analysis is compared against. The negative control is the
analytic restatement. Determinism: closures are exact at the pin.

## Considerations

- A clean closure of the statement does not guarantee a clean closure of the proof: a proof may import a tactic
  or lemma from a blocked module. BD-382 re-measures the closure of the finished theorems; this bead removes the
  cheap failures first.
- The specifications are conservative on purpose: the conclusion over every ordered field K covers ℝ, which is
  what forces need, without importing analysis.
- Default while open: elementary forms only.
