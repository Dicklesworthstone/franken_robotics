## Background

The first thing Lemma must show at M0 is the whole path of an instance certificate from the user's side: a kernel
is derived, an identity about its arithmetic is certified at build time by FrankenSymPy's proof kernel, the
certificate is stored beside the kernel with the kernel's content hash inside, and it replays offline in a binary
that shares nothing with the producer. GATE-LEMMA-00 (M0, claim Proof) is the measure: card T-01 (for
skew-symmetric Ω, cay(Ω)ᵀ·cay(Ω) = I and det cay(Ω) = 1), card T-03 (the quaternion update preserves the norm:
‖q·c‖² = ‖q‖²·‖c‖²) and card T-04 (Ad(gh) = Ad(g)·Ad(h), and the group coadjoint is the inverse transpose) are
certified by FrankenSymPy for the M0 kernels, and the certificates replay offline. Passing it also closes the
admission gate INT-FSYM-01 (the derivation annex builds against the FrankenSymPy crates by path, derives the
Cayley step kernel, and its certificate replays in the offline auditor).

The mechanisms are built by other beads (the producer and the three certificates by BD-021; the bundle writer,
the `poly-identity` checker and the three verbs by BD-027). This bead is the end-to-end script that drives them
through the real `frob` binary and the standalone `frob-verify`, with the structured logging every end-to-end
script carries, and that records the gate. Verbs exercised: `prove.kernel` (read, M0: the instance certificate of
a kernel and what it states), `prove.verify` (read, M0: re-check certificates in tree; `frob-verify` repeats the
check offline), `prove.list` (read, M0: certificates and theorem cards with their classes and checkers).

## Scope

In: `scripts/e2e/lemma_kernel_cert.sh`, its fixtures (three mutated certificates), its log schema use, the gate
record. Out: the mechanisms under test; the flag and claim-product gate (N12-11); the mutation suite per kind at
M1 (N12-34).

## Technical approach

Steps of the script (plain shell, `set -euo pipefail`, sources the shared helper of STD-E2E, seed-explicit,
idempotent; it writes only under `target/`):
1. `start`: record commit, toolchain, host fingerprint, the pins of FrankenSymPy from the stack lock.
2. Regenerate: run the derivation for the M0 kernels (`K-cay-step`, `K-normalize` and the adjoint kernel) and
   assert that regeneration reproduces the checked-in sources bit for bit (digests logged).
3. `frob prove list --json`: assert that cards T-01, T-03, T-04 are listed; before certification their routes are
   `hypothesis`.
4. Certify at build time (the producer step), then `frob prove kernel K-cay-step --json` and the same for the
   other two kernels: assert each output names the identity text, the certificate hash, the checker identity
   (FrankenSymPy proof kernel build), class `Certified`, the kernel content hash equal to the kernel's `KernelId`,
   and the sentence that the certificate says nothing about floating-point results; assert the envelope's three
   authorization flags are false.
5. `frob prove verify --json` over all certificates: assert `accept` for each.
6. Offline replay: build `frob-verify` from a copy of `crates/frob-cert` alone in a temporary directory with no
   network (`cargo build --release --offline`), then run it on each bundle with a cleared environment
   (`env -i`): assert `accept`, exit code 0, and the trusted-base block in the report.
7. Negative controls: for each of the three certificates, a copy with one changed coefficient in the polynomial
   payload (digests recomputed so every hash is consistent): assert `reject` from both `frob prove verify` and
   `frob-verify`, with the rule named; a copy whose embedded kernel hash is changed: assert it is not accepted as
   a certificate of the kernel.
8. `frob prove list --json` again: assert the three routes are now `checked` with class `Certified`, receipts
   present, and that no other card changed.
9. `summary`: assertions passed and failed, gates touched (`GATE-LEMMA-00`, `INT-FSYM-01`), and the gate record
   written with the measured values (three of three certified; three of three replayed offline; three of three
   mutants rejected).

Logging (newline-delimited JSON at `target/e2e-logs/lemma_kernel_cert/<utc-timestamp>.ndjson`, with a
human-readable transcript beside it): every line has `ts`, `script`, `bead` (`N12-33`), `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the
envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and
thresholds, digests where state is compared, and on failure the first differing value and the artifact paths
needed to reproduce.

## Acceptance criteria

- [ ] The script exits 0 from a clean checkout on a machine with the M0 toolchain and no GPU, and non-zero if any
      assertion fails.
- [ ] GATE-LEMMA-00 (TARGET, M0, claim Proof): T-01, T-03 and T-04 are certified by FrankenSymPy for the M0
      kernels and the certificates replay offline; the record cites commit, command, output and receipt hash.
- [ ] Each of the three changed-coefficient mutants is rejected by both the in-tree verb and the standalone
      auditor.
- [ ] The standalone auditor is built from the copied crate with no network and run with a cleared environment.
- [ ] The log validates against the shared log schema; it contains one `assert` line per assertion and a final
      `summary`; it contains no scene data.
- [ ] Running the script twice gives identical certificate and bundle digests.

## Test plan

### Unit tests

The script's helper logic is covered by the shared harness's own tests. Script-level self-test:
`scripts/e2e/tests/lemma_kernel_cert_selftest.sh` runs the script against a fixture build in which the producer
is replaced by a build that emits a wrong identity (a sign flipped in the orthogonality statement) and asserts
that the script fails at step 5 with the first differing value logged (negative control of the script itself).

### End-to-end script and logging

This bead is the script; see the steps and the logging above.

### Known answers and negative controls

KA-211 (T-01 for the M0 Cayley kernel: `accept`; one changed coefficient gives `reject`), KA-220 (T-01, T-03 and
T-04 certified and replaying offline; one changed coefficient gives `reject`). Negative controls: the three
mutants, the wrong kernel hash, the self-test's wrong producer. Determinism lanes: twice on one machine (identical
digests); debug and release builds of the auditor (identical verdicts); the Mac and the Linux host (identical
digests and verdicts, class D0).

## Considerations

- Without FrankenSymPy admitted the script cannot pass; M0's fallback posture is "CLI only; no kernel
  certificates", and the gate is then recorded `not run`, which is not a pass.
- The script must not regenerate oracles from the candidate: the three mutants are fixed fixtures checked in with
  their expected rule.
- Wall time is small (three polynomial identities); the offline build of the auditor dominates.
