## Background

The offline auditor `frob-verify` is what stands between a producer's claim and the word `Certified`. A gate that
nothing can fail validates nothing, so the auditor's gate is defined by what it must reject as much as by what it
must accept. GATE-LEMMA-03 (M1, claim Known answer): every proof kind in use has one specimen that `frob-verify`
accepts and at least three mutations that it rejects; the four stance mutations, an unknown kind with consistent
hashes and a changed quantifier are all rejected (100%); the binary lists no dependency outside the standard
library and runs in an empty environment.

The four stance mutations, each of which must cause rejection: a swapped foot order with unchanged forces; an
unreported positive force floor; a passive-authority tag; (60, 30) passed as the torque. The certifier self-test
of the verification program asks for a mutation corpus per proof kind (changed coefficient, reordered
quantifiers, missing side condition, wrong frame or unit, fabricated kind with consistent hashes, a flag set to
true, a boundary opened or closed), with every mutant rejected and every specimen accepted, identical bytes on
re-serialization, standalone and in-daemon verdicts identical on the whole corpus, and dependency count zero.
This bead is the end-to-end script that performs that run from the outside on the pinned corpus (one accepted
specimen and the hand-pinned rejecting mutations of each kind) and records GATE-LEMMA-03. The same run over a
generated corpus of at least 1,000 mutants per kind is the Gauntlet's gate GATE-GAUNT-04 (N38b-11), which
reuses this script's step functions. The script is directory-driven, so kinds added at later milestones are
picked up without changing it.

## Scope

In: `scripts/e2e/lemma_auditor_mutations.sh`; the pinned corpus layout it expects; the build of the auditor
alone; the empty-environment run; the per-file verdict run against a manifest; the re-serialization check; the
verdict comparison between the standalone binary and the in-tree verb; these steps as shell functions that take
a corpus directory and a manifest; the M1 record of GATE-LEMMA-03, and the form of its later parts (a run of
this script, unchanged, over the kinds enabled by then, recorded with `--part <milestone>`).
Out, with the bead that has it: the checkers and the specimens' content (BD-027, BD-132 and the checker beads
N12-13 to N12-19 and N12p1-01). Generated mutants: the one mutation generator and the 200-mutant-per-kind
independence campaign (BD-136, GATE-AUGUR-01 and GATE-AUGUR-06), and the Gauntlet's run of that generator at 1,000 per kind
with its class coverage, the checker-before-answer test and the broken-certifier controls (N38b-11,
GATE-GAUNT-04). Both read this corpus's `accept-*` specimens as bases and keep no second copy of a specimen or
of a named mutation; N38b-11 depends on this bead and calls the step functions below on its generated
directory. The system-call trace of GATE-WS-03 (BD-026).

## Technical approach

Corpus layout (owned by the checker beads, read by the script): `crates/frob-cert/tests/specimens/<kind>/`
containing `accept-*.frobcert` and `reject-<rule>-*.frobcert`, plus a manifest `expected.toml` listing for each
file the expected verdict and, for rejections, the expected first failing rule and refusal code. A file that a
theorem card names also carries `card = "T-nn"` and `log_fields`, the list of per-card fields the card's own
end-to-end section asks for (for example T-22: per vertex the recomputed Σ f, Σ x·f, Σ y·f and the dual margin
yᵀw − β; T-24: the claimed and recomputed counts and whether enumeration ran; T-34: β̄, γ̄ and ᾱ); the script reads
those values from the `recomputed_values` block of the auditor's JSON report (N12-04), so a card's line holds what
the checker recomputed, not what the bundle claimed.

The pinned directory is the one home of accepted specimens and of named mutations (DESIGN: BD-136's fixed
cases A1 to A5 and A7 and N38b-11's named mutants point at these files; neither copies them). Steps 3, 4, 5
(the per-file run against a manifest), 7 and 8 are functions in `scripts/e2e/lib/auditor_corpus.sh` (DESIGN)
taking a corpus directory and a manifest path, so that the generated corpus of N38b-11 is run by the same code.

Steps (plain shell, sources the STD-E2E helper, seed-explicit, idempotent):
1. `start`: commit, host fingerprint, the list of kinds whose registry status is `enabled`.
2. Independence pre-checks, as stages. Run `scripts/e2e/lemma_independence.sh` (N12-09) as a stage, with this
   run's seed: `cargo xtask check-deps --json` (N34-25, the one owner of these rules), `cargo tree -p frob-cert`
   and its inverse, N12-09's tests, and the call-graph lint and the similarity scan with their planted fixtures
   caught. Then run `scripts/e2e/lemma_auditor_oracles.sh` (N12-10) as a stage, with this run's seed: the
   differential oracle rows KA-223 and KA-225 and their planted builds caught. Each stage's summary is read and
   its failures fail this script. From the two stage logs this script copies, as `metric` lines with thresholds,
   the facts the gate cites: the dependency count (threshold 0, so `cargo tree -p frob-cert` prints one line);
   reverse edges (exactly the three allowed crates: no `cert.writer-links-reader` finding); shared-source and
   source-escape findings (0); audit call sites outside the allowed ones (0); oracle mismatches (0).
3. Build alone: copy `crates/frob-cert` to a temporary directory; `cargo build --release --offline` with the
   crate's own stable toolchain file; record the binary's digest and size and the crate's line count against the
   cap of 12,000 (TARGET).
4. Empty environment: run the binary under `env -i` in an empty working directory containing only the bundle
   files (a container or sandbox with no network where the host provides one); a run with the network namespace
   removed is logged as such.
5. For every enabled kind: assert at least one `accept-*` file and at least three `reject-*` files exist; run the
   binary on each file; assert the verdict and, for rejections, the first failing rule and refusal code equal the
   manifest's.
6. Named mutations asserted by name, whatever else exists: the four stance mutations (`reject-lp-primal.port-order`,
   `reject-side.force-floor`, `reject-field.authority`, `reject-field.type-torque`); an unknown kind with
   consistent hashes (`reject-kind.unknown`); a changed quantifier with consistent hashes
   (`reject-query.prefix`); a flag set to true and a flag missing (`reject-flags.true`, `reject-flags.missing`);
   a boundary opened or closed (`reject-partition.boundary`).
6a. Mutants named by the theorem cards, asserted by name and by card (each joins the pinned corpus of its kind,
   with its card tag): T-22 `force_floor_rejects`, `passive_authority_rejects`, `moment_as_torque_rejects` (the
   stance files of step 6, now tagged), `affine_label_rejects`, `closed_end_rejects`; T-24
   `non_least_representative_rejects`; T-25 `non_normal_pair_rejects`; T-27 `scale_pow2_without_range_rejects`;
   T-31 `non_adjacent_step_rejects`, `false_cut_rejects`; T-32 `progress_declaration_required`; T-34
   `gamma_underestimate_rejects`. A card whose kind is not enabled in this build (its checker bead not yet landed,
   or its ledger revision not yet in the registry) is logged `pending` with the reason and the milestone, never as
   passed; step 9 then asserts `unsupported` for its bundles. A card mutant missing from a kind that is enabled
   fails the script.
7. Round trip: `--reserialize` every accepted specimen and compare bytes (PO-LEMMA-01).
8. Agreement: run `frob prove verify --json` (the in-tree verb) on the whole corpus and assert identical verdicts
   and rules to the standalone binary.
9. Kinds not enabled: assert the binary returns `unsupported` for a bundle of each such kind.
10. `summary`: per kind accepted and rejected counts, the 100% rejection of the named mutations, the dependency
    facts, gates touched; the run's receipt (its hash in the `summary` line), from which this bead, the one
    measurer of GATE-LEMMA-03, records the gate with `cargo run -p frob-conformance --example record_gate --
    --gate GATE-LEMMA-03 --receipt <hash>` (the script itself writes no gate row).

Logging: newline-delimited JSON under `target/e2e-logs/lemma_auditor_mutations/<utc-timestamp>.ndjson` and a
transcript beside it; every line carries `ts`, `script`, `bead` (`N12-34`), `step`, `event`, the exact command
line, exit code, wall time, measured values with thresholds; `assert` lines for bundles add the bundle digest,
kind, expected and observed verdict and rule; on failure the first differing value and the path of the offending
file; the `evidence` block of each in-tree verb response is copied in. Per-card tagging: a line for a file with a
`card` tag carries `bead` = `CARD-T-nn` and `step` = `T-nn/<specimen-or-mutant>` (T-25 adds the ambient group:
`T-25/<ambient-group>/<specimen-or-mutant>`), plus the card's `log_fields` with their values from the report and
the expected and observed verdict, so each card's own log contract is met by this one run; a `pending` card logs
one line with its reason. The `summary` line counts files per card as well as per kind.

## Acceptance criteria

- [ ] The script exits 0 from a clean checkout on a host with no GPU, and non-zero on any failed assertion.
- [ ] GATE-LEMMA-03 (TARGET, M1): for every proof kind in use, one accepted specimen and at least three rejected
      mutations; the four stance mutations, the unknown kind with consistent hashes and the changed quantifier
      rejected (100%); no dependency outside the standard library; the binary runs in an empty environment.
      Recorded with the per-kind counts.
- [ ] The standalone binary and the in-tree verb agree on every file.
- [ ] Every accepted specimen re-serializes to identical bytes.
- [ ] A kind with fewer than three rejecting mutations fails the script (negative control: a fixture kind
      directory with two).
- [ ] A corpus file whose observed rule differs from the manifest's fails the script and logs both rules.
- [ ] Every card-named mutant of step 6a is asserted by name for each card whose kind is enabled, and logged under
      `CARD-T-nn` with that card's fields; a card whose kind is not enabled is logged `pending`, never passed.
- [ ] This bead closes on the M1 record. The script needs no change at a later milestone: a run over the kinds
      enabled by then gives a receipt from which GATE-LEMMA-03's part for that milestone is recorded with
      `record_gate -- --gate GATE-LEMMA-03 --receipt <hash> --part <milestone>`. Those later parts are not
      conditions of this bead's close (the M1 exit review depends on this bead, and kinds arrive up to M8).

## Test plan

### Unit tests

Script self-tests under `scripts/e2e/tests/`: `auditor_mutations_selftest_missing_mutant.sh` (a kind with two
mutants → failure); `auditor_mutations_selftest_permissive_build.sh` (an auditor build with the query-match rule
disabled → the changed-quantifier mutant is accepted → the script fails and logs the bundle);
`auditor_mutations_selftest_env.sh` (a build that reads an environment variable is detected as behaving
differently under `env -i`); `auditor_mutations_selftest_card_tag.sh` (a fixture corpus with one `card = "T-22"`
file: its lines carry `bead` `CARD-T-22`, step `T-22/<file>` and the listed fields; removing `closed_end_rejects`
from an enabled kind fails the script; a fixture card whose kind is disabled is logged `pending`).

### End-to-end script and logging

This bead is the script; steps and logging as above.

## Considerations

- "Empty environment" has two meanings and both are tested: an empty process environment, and a machine or
  container with nothing of the project installed. The second is exercised fully by the second-machine script
  (N12-35).
- The corpus is a pinned oracle: mutants are never regenerated from the candidate auditor.
- The M5 conformance bead extends the corpora (certificate mutation corpora); this script reads whatever the
  directories hold.
- Pinned and generated are two corpora with one specimen set: the pinned files prove that each named defect is
  caught by name and never change with the generator; the generated run (BD-136 at 200 per kind, N38b-11 at
  1,000) measures breadth. A mutant the generated run finds accepted becomes a pinned `reject-*` file here.
- Run time grows with kinds; the per-file checks are fast, and the build step dominates.
