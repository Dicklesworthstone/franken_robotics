## Background

The offline auditor `frob-verify` is what stands between a producer's claim and the word `Certified`. A gate that
nothing can fail validates nothing, so the auditor's gate is defined by what it must reject as much as by what it
must accept. GATE-LEMMA-03 (M1, claim Known answer): every proof kind in use has one specimen that `frob-verify`
accepts and at least three mutations that it rejects; the four stance mutations, an unknown kind with consistent
hashes and a changed quantifier are all rejected (100%); the binary lists no dependency outside the standard
library and runs in an empty environment.

The four stance mutations, each of which must cause rejection: a swapped foot order with unchanged forces; an
unreported positive force floor; a passive-authority tag; (60, 30) passed as the torque. The certifier self-test
of the verification program asks for a mutation corpus per proof kind (changed coefficient, reordered
quantifiers, missing side condition, wrong frame or unit, fabricated kind with consistent hashes, a flag set to
true, a boundary opened or closed), with every mutant rejected and every specimen accepted, identical bytes on
re-serialization, standalone and in-daemon verdicts identical on the whole corpus, and dependency count zero.
This bead is the end-to-end script that performs that run from the outside and records the gate. It is
directory-driven, so kinds added at later milestones are picked up without changing the script.

## Scope

In: `scripts/e2e/lemma_auditor_mutations.sh`; the corpus layout it expects; the empty-environment run; the
verdict comparison between the standalone binary and the in-tree verb; the gate record per milestone.
Out: the checkers and the specimens' content (BD-027, BD-132 and the checker beads N12-13 to N12-19); the
200-mutant-per-kind independence campaign (BD-136, GATE-AUGUR-06); the system-call trace of GATE-WS-03 (BD-026).

## Technical approach

Corpus layout (owned by the checker beads, read by the script): `crates/frob-cert/tests/specimens/<kind>/`
containing `accept-*.frobcert` and `reject-<rule>-*.frobcert`, plus a manifest `expected.toml` listing for each
file the expected verdict and, for rejections, the expected first failing rule and refusal code.

Steps (plain shell, sources the STD-E2E helper, seed-explicit, idempotent):
1. `start`: commit, host fingerprint, the list of kinds whose registry status is `enabled`.
2. Independence pre-checks, logged as metrics with thresholds: `cargo tree -p frob-cert` line count (threshold
   1); reverse-dependency count (3); shared-source-file count with proposer crates (0); the differential oracle
   target of N12-10 (0 mismatches).
3. Build alone: copy `crates/frob-cert` to a temporary directory; `cargo build --release --offline` with the
   crate's own stable toolchain file; record the binary's digest and size and the crate's line count against the
   cap of 12,000 (TARGET).
4. Empty environment: run the binary under `env -i` in an empty working directory containing only the bundle
   files (a container or sandbox with no network where the host provides one); a run with the network namespace
   removed is logged as such.
5. For every enabled kind: assert at least one `accept-*` file and at least three `reject-*` files exist; run the
   binary on each file; assert the verdict and, for rejections, the first failing rule and refusal code equal the
   manifest's.
6. Named mutations asserted by name, whatever else exists: the four stance mutations (`reject-lp-primal.port-order`,
   `reject-side.force-floor`, `reject-field.authority`, `reject-field.type-torque`); an unknown kind with
   consistent hashes (`reject-kind.unknown`); a changed quantifier with consistent hashes
   (`reject-query.prefix`); a flag set to true and a flag missing (`reject-flags.true`, `reject-flags.missing`);
   a boundary opened or closed (`reject-partition.boundary`).
7. Round trip: `--reserialize` every accepted specimen and compare bytes (PO-LEMMA-01).
8. Agreement: run `frob prove verify --json` (the in-tree verb) on the whole corpus and assert identical verdicts
   and rules to the standalone binary.
9. Kinds not enabled: assert the binary returns `unsupported` for a bundle of each such kind.
10. `summary`: per kind accepted and rejected counts, the 100% rejection of the named mutations, the dependency
    facts, gates touched; write the gate record with measured values.

Logging: newline-delimited JSON under `target/e2e-logs/lemma_auditor_mutations/<utc-timestamp>.ndjson` and a
transcript beside it; every line carries `ts`, `script`, `bead` (`N12-34`), `step`, `event`, the exact command
line, exit code, wall time, measured values with thresholds; `assert` lines for bundles add the bundle digest,
kind, expected and observed verdict and rule; on failure the first differing value and the path of the offending
file; the `evidence` block of each in-tree verb response is copied in.

## Acceptance criteria

- [ ] The script exits 0 from a clean checkout on a host with no GPU, and non-zero on any failed assertion.
- [ ] GATE-LEMMA-03 (TARGET, M1): for every proof kind in use, one accepted specimen and at least three rejected
      mutations; the four stance mutations, the unknown kind with consistent hashes and the changed quantifier
      rejected (100%); no dependency outside the standard library; the binary runs in an empty environment.
      Recorded with the per-kind counts.
- [ ] The standalone binary and the in-tree verb agree on every file.
- [ ] Every accepted specimen re-serializes to identical bytes.
- [ ] A kind with fewer than three rejecting mutations fails the script (negative control: a fixture kind
      directory with two).
- [ ] A corpus file whose observed rule differs from the manifest's fails the script and logs both rules.
- [ ] The gate is re-recorded at each later milestone for the kinds enabled by then.

## Test plan

### Unit tests

Script self-tests under `scripts/e2e/tests/`: `auditor_mutations_selftest_missing_mutant.sh` (a kind with two
mutants → failure); `auditor_mutations_selftest_permissive_build.sh` (an auditor build with the query-match rule
disabled → the changed-quantifier mutant is accepted → the script fails and logs the bundle);
`auditor_mutations_selftest_env.sh` (a build that reads an environment variable is detected as behaving
differently under `env -i`).

### End-to-end script and logging

This bead is the script; steps and logging as above.

### Known answers and negative controls

KA-207 (stance bundle at b = 3/14 m accepts; each of the four mutations rejects), KA-208 (dual witness at
b = 1/5 m accepts; a perturbed multiplier rejects), KA-209 (docking cell (¾, ¼) accepts; quantifiers reordered
rejects), KA-210, KA-212, KA-213, KA-214, KA-215, KA-216, KA-217, KA-218 (the per-kind condition itself),
KA-222. CX-106, CX-107, CX-108, CX-115. The self-tests are the negative controls of the script. Determinism
lanes: twice on one machine; debug and release; the Mac and the Linux host; verdicts, rules and re-serialized
bytes identical (class D0).

## Considerations

- "Empty environment" has two meanings and both are tested: an empty process environment, and a machine or
  container with nothing of the project installed. The second is exercised fully by the second-machine script
  (N12-35).
- The corpus is a pinned oracle: mutants are never regenerated from the candidate auditor.
- The M5 conformance bead extends the corpora (certificate mutation corpora); this script reads whatever the
  directories hold.
- Run time grows with kinds; the per-file checks are fast, and the build step dominates.
