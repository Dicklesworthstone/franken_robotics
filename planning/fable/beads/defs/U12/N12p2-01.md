## Background

The label query of the mission chapter (BD-363) asks for the least number of calibration labels that lets one
controller serve every admitted variant: with K_s the commands that work for variant s, variants can share a label
exactly when their command sets have a common point, so the count is the least number of colours of the hypergraph
whose edges are the inclusion-minimal collections of variants with empty intersection. An upper bound is easy to
certify (one feasible command per colour, an `lp-primal` witness per class). A matching lower bound is not: "k − 1
labels do not suffice" means every map of the n variants to k − 1 colours leaves some edge monochromatic, which is a
combinatorial statement about the whole edge list, not about any one edge.

Each edge is certified empty by an `lp-farkas` sub-certificate (one per piece when a command set is a union of
polytopes), and those the auditor checks today. No row of the closed proof-kind registry `frob.cert.kinds/1` carries
the colouring step, so BD-363 runs on a fail-closed default: it reports only the lower bound a single edge proves
(one label is impossible when any edge exists), with `attained: false` and the gap, and a claimed
`minimum-with-matching-lower-bound` is refused (`FROB-REF-853`). GATE-AUGUR-19 cannot pass under that default: its
three-reading fixture (conflicts {A, B}, {B, C}, {C, A}) needs the fixed-map count 3 with `attained: true`, and its
lower bound rests on three edges at once (N25c-38, step 2). This bead is the missing kind: its payload, its
checker, its specimens and mutants, and its admission to the registry through the revision ledger.

The shortcut it rules out is CX-271, "variants that are pairwise compatible can share a controller": the three-variant
fixture (x ≥ 2/3, y ≥ 2/3, x + y ≤ 1) has every pair compatible and the triple empty. A colouring argument built
from pairwise edges only would accept one label there; this kind takes the edges the producer certified, of any
size, and checks each one's emptiness certificate.

Tier: the check is a bounded exhaustive search over exact data (Solid mathematics); the label query that uses it is
Frontier on supplied sets, as BD-363 states, which is why the bead carries the Frontier label like the other
checkers built for Frontier consumers (N12-17).

## Technical approach

1. **Payload (DESIGN).**
   ```json
   { "kind": "colouring-bound", "version": 1,
     "statement": "the variants admit no partition into k_minus_1 classes free of conflict sets",
     "payload": { "variants": ["A", "B", "C"],
                  "edges": [ { "variants": ["A", "B"], "emptiness": [ { "kind": "lp-farkas", "...": "…" } ] },
                             { "variants": ["B", "C"], "emptiness": [ "…" ] },
                             { "variants": ["A", "C"], "emptiness": [ "…" ] } ],
                  "k_minus_1": 2 } }
   ```
   `variants` lists the variant identifiers of the query in its order; each edge names at least two of them and
   carries one emptiness sub-certificate per piece of the intersection (one for convex sets, one per piece for
   finite unions of polytopes), each a complete payload of a registered kind (today `lp-farkas`). The bundle's
   `query`, `assumptions` and `review` fields are those of the mission bundle that carries it (N12-03).
2. **Checker steps, in order (first failure reported).**
   - (a) Shape: `variants` has no duplicate and at most 16 entries (BD-363's admission cap), `k_minus_1 ≥ 1`
     (`colouring.variants`); every edge names at least two listed variants and no other identifier
     (`colouring.edge-variant`).
   - (b) Edges: each emptiness sub-certificate is dispatched to its own kind's checker with the query's sets as
     inputs (for `lp-farkas`, `lp-farkas.bounds-query` first, so a sub-certificate over sets other than the
     query's is rejected before any arithmetic); a rejection is reported as `colouring.edge-certificate` with the
     edge, the piece and the sub-rule named.
   - (c) Non-colourability: a backtracking search over maps of the variants to at most k − 1 colours in
     restricted-growth form (symmetry broken by order of first use: variant 1 takes colour 1, each later variant
     takes a used colour or the next new one). A partial map is abandoned as soon as some edge is fully assigned
     and monochromatic, since every completion of it then leaves that edge monochromatic. The claim holds iff the
     search finds no complete map that leaves every edge with two colours; if it finds one, the bundle is rejected
     with `colouring.colourable` and the report names that map. The search counts the complete maps it covered,
     visited or pruned, and checks that the count equals Σ_{j=1}^{k−1} S(n, j) (the number of restricted-growth
     maps with at most k − 1 colours; `colouring.coverage` on a mismatch, a self-check against a search defect).
     For the triangle (n = 3, k − 1 = 2) that is S(3, 1) + S(3, 2) = 1 + 3 = 4.
   - (d) Class: at most `Certified`, and at most the weakest class among the edge sub-certificates and the
     assumptions (the generic class rule of N12-03).
3. **Work limit (DESIGN).** The worst case is Σ_{j≤k−1} S(16, j) maps: 32,768 for k − 1 = 2, 7,174,454 for 3,
   178,973,355 for 4, and 9,433,737,120 for 8. The checker declares a limit of 2·10⁸ complete maps covered, the
   count of step (c). The unit is the covered count and not the nodes visited, because that count is known exactly
   from (n, k − 1) before the search, so the refusal never depends on how far a search got: a bundle whose
   Σ_{j≤k−1} S(n, j) exceeds the limit is refused with `limits.exceeded` before the search starts, and nothing is
   ever approximated. At n = 16 this admits k − 1 ≤ 4; smaller n admit larger k. The nodes a search visits are
   bounded by the limit too: below the first variant every node of the restricted-growth tree has at least two
   children when k − 1 ≥ 2, so the tree has fewer than twice as many nodes as complete maps (238,642,067 nodes for
   178,973,355 maps at n = 16, k − 1 = 4, which a limit of 2·10⁸ counted in nodes would have refused in the worst
   case after admitting it). The limit is printed in `frob-verify --help` and in the registry row's scope, and
   BD-363 keeps its fail-closed interval for any instance beyond it.
4. **Registry.** The row `colouring-bound`, version 1, class cap `Certified`, scope "n ≤ 16 variants, at most 2·10⁸
   complete maps covered", enters `frob.cert.kinds/<revision>` through the ledger change `colouring-bound-v1`
   with status `not-implemented` (N12x-08's first revision), and becomes `enabled` only by the `enable` change
   `colouring-bound-enable`, which this bead writes with N12x-08's six admission items: the payload schema and
   the sentence of what is recomputed (as in N12x-08's row); the cap `Certified` with its reason (an exact
   exhaustive search over certified edges is a proof, not a receipt); the specimens and at least three mutants,
   each rejected by a named rule; a seeded-fault campaign of at least 200 mutated bundles with zero false
   accepts; the standard-library-only closure, sharing no source file with the producer (BD-363, BD-133); review
   by a session that did not write the checker, named in the ledger row. The baseline table of N12-02 is not
   edited. An auditor built before `colouring-bound-v1` answers FROB-REF-823 for the kind, and one built between
   the two changes answers `unsupported`: both are the fail-closed behaviour.
5. **Rule identifiers.** `colouring.variants`, `colouring.edge-variant`, `colouring.edge-certificate`,
   `colouring.colourable`, `colouring.coverage`, plus the generic and `limits.*` rules. They are listed in
   `CONTRACT.md` of `frob-cert`. Refusal codes on `prove.verify`: FROB-REF-829 for a sub-certificate over sets other
   than the query's, FROB-REF-834 for the class, FROB-REF-823 for an auditor without the revision; the other rules
   are plain rejects with exit 3 (N12-REF's mapping rule).

Determinism class D0: exact data, a fixed search order, the same verdict, rule and named map on every platform.

## Test plan

### Unit tests

`crates/frob-cert/tests/kind_colouring_bound.rs`, real bundles under `tests/specimens/colouring-bound/`, no mocks:
- `triangle_accepts_four_maps`; `three_variant_single_edge_accepts`; `three_readings_accepts`.
- `triangle_edge_removed_names_colourable_map`; `triangle_three_colours_colourable`.
- `edge_certificate_perturbed_rejects`; `pairwise_edge_not_empty_rejects` (CX-271).
- `edge_variant_unknown_rejects`; `seventeen_variants_rejects`; `limit_exceeded_before_search`
  (n = 16, `k_minus_1` = 5: the bound 1,275,163,905 is computed and the bundle refused without a search);
  `class_above_assumption_rejects`.
- `limit_admits_sixteen_by_four`: for n = 16 and `k_minus_1` = 4 the bound 178,973,355 is under the limit and the
  admission decision is "search" (asserted on the bound computation and the decision, without running the
  search); the tree's node count 238,642,067 is computed from the same recurrence and asserted, so an
  implementation that reads the limit in nodes fails the test.
- `coverage_count_equals_stirling_sum` (n = 3 to 8 and every `k_minus_1`: the covered count equals
  Σ_{j≤k−1} S(n, j); 4,140 = Bell(8) for n = 8 and `k_minus_1` = 8); `coverage_mismatch_planted` (a search mutant
  that skips the first new-colour branch is caught by `colouring.coverage`).
- `pruning_is_sound`: on the random families, the pruned search and the unpruned enumeration give the same verdict
  and the same first colourable map.
- Property test `matches_bruteforce` (200 random hypergraphs, at most 8 variants; seed recorded).
- `seeded_fault_campaign` (200 mutated bundles from the accepted specimens, seed recorded: an edge dropped, an
  edge's variant renamed, `k_minus_1` raised, an `lp-farkas` multiplier or bound perturbed, a pairwise edge offered
  for a triple, a class raised; zero accepted).
- `unsupported_before_enable` (the auditor at the revision of `colouring-bound-v1`, before
  `colouring-bound-enable`, returns `unsupported` for the triangle specimen).
- `verdict_bytes_identical` (debug and release; the report's map and rule identical twice).

`kind/colouring-bound/<specimen-or-mutant>` once the ledger revision is in the build (`pending` before, with the

### Known answers and negative controls

Known answers: the triangle needs 3 colours (4 maps covered); the three-variant fixture needs 2 (KA-644's lower
bound: one label is impossible); the three-reading fixture's fixed map needs 3. CX-271 is the registered control
(a pairwise-only colouring returns one label on the three-variant fixture and must be rejected). Further negative
controls: the edge-removed and three-colour mutants (a checker that accepted without searching would pass them);
the coverage mutant. Determinism: D0; identical verdicts, rules and named maps on Linux and macOS.

## Considerations

- The search is exponential in n; the cap of 16 variants and the limit on maps covered keep the auditor's time
  bounded and readable. A future kind that carries a shorter argument (for example a clique or an odd-cycle certificate for
  graphs) would be a separate ledger change; this kind stays the general fallback.
- The checker trusts nothing about how the producer found the edges; it needs only that each listed edge is
  certified empty and that no proper colouring with k − 1 colours avoids them. Missing edges can only make the
  claim fail (a colourable map is found), never make a false claim pass.
- Inclusion-minimality of the edges is not checked: a non-minimal edge weakens nothing that the search relies on.
- The kind's lines count against the auditor's 12,000-line cap; the search is a few dozen lines.
