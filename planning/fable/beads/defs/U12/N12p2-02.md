## Background

A kernel's arithmetic is a straight-line program in the kernel intermediate representation `frob-kir`. A rewrite
of it belongs to one of two classes (construction C-14). Class E changes no bit under round-to-nearest with
contraction off: commutation, common-subexpression elimination, dead-code elimination, scaling by a power of two
away from overflow and underflow, and scheduling. Class R is equal over the reals only: reassociation,
distribution, fused multiply-add. A class-E rewrite ships a certificate (source hash, target hash, rule trace)
that an independent checker replays; a class-R rewrite makes a different kernel with a new identity, an error
bound and a fidelity run. The rule table is closed. A silent bit change would invalidate replay and both evidence
ledgers, which is why the trace is checked and not believed. Theorem card T-27 states what the replay establishes:
a class-E rewrite trace maps the source program to the target program using only rules of the closed table.

Why this bead exists, and why at M2. The rewrite engine and its trace format are built at M2 (N21a-19), and the
kernels derived at M2 ship their traces then. N21a-19 ships a reference replayer in `frob-kir`'s tests, which is
not independent of the engine; the plan requires the independent one (C-14: "replayed by an independent
checker"), and GATE-LEMMA-03 requires a specimen and at least three rejected mutations for every proof kind in
use. The checker was first written together with the `orbit-count` and `group-enumeration` checkers in N12-18,
dated M4, which left the M2 kernel work (the e-graph extraction pilot N33c-21 and its derivation pass N33c-22)
either waiting on a later milestone or replaying with the reference replayer only. Its prerequisites (the
registry N12-02, the bundle schema N12-03, the auditor's arithmetic of BD-132) are M0 and M1, so it is split out
of N12-18 and dated M2. N12-18 keeps the two group-theoretic kinds at M4.

Tier: Frontier, with the IR (kill gate KILL-KIR). Rejected alternatives: accepting a rewrite because outputs
matched on test vectors (a test cannot cover the edge set of every input); citing N21a-19's reference replayer as
the certificate's checker (it shares the engine's authors, crate and data structures); a rule table of the
checker's own that differs from the engine's (a valid trace would be rejected, or the checker would admit a rule
the engine never applies).

## Scope

In: the `rewrite-trace` checker in `crates/frob-cert/src/kinds/rewrite_trace.rs`: its payload, an independent
parser of the canonical `frob.kir/1` program text and of the trace format `frob.kir.trace/1`, the class-E rule
interpreter with each rule's precondition, exact-rational checks for folding and power-of-two scaling, the rule
identifiers, caps, specimens and at least three mutations, the differential test against the reference replayer,
the example binary that replays a kernel library's traces, and the registry row's status change to `enabled`.
Out: the rewrite engine, the rule table's definition and the trace format (N21a-19); scheduling (N21a-18); the
IR and its canonical hash (N21a-16); e-graph extraction and the derivation pass (N33c-21, N33c-22); the theorem
card's row (CARD-T-27); the Lean reflector for trace replay (N12-28, M5); the `orbit-count` and
`group-enumeration` checkers (N12-18); the bundle writer for kernel certificates.

## Technical approach

1. **Payload (DESIGN).** The source and target programs as canonical `frob.kir/1` bytes (N21a-16), their BLAKE3
   hashes, the element type (`f32` or `f64`), and the trace in `frob.kir.trace/1` (N21a-19): an ordered list of
   steps `{rule, node, operands_before, result_node}`, plus, for a step of rule E11, its declared input range.
   The checker parses all of it with its own reader, written against the two formats and sharing no code with
   `frob-kir` (the auditor depends on the standard library only).
2. **Closed rule table (version-pinned in the registry row).** Exactly N21a-19's eleven rules, under the names of
   the trace format, and the scheduling step:
   - E1 `share` (two nodes with the same operator and the same operand nodes become one), E2 `dead` (a node with
     no use and no store is removed), E3 `comm-add` and E4 `comm-mul` (operands of + or × exchanged), E5
     `mul-one` (x·1 or 1·x to x, the literal 1 of the element type), E6 `add-negzero` (x + (−0) or (−0) + x to x;
     the literal must be −0: no rule exists for +0, since (−0) + (+0) = +0), E7 `neg-neg`, E8 `select-same`
     (select(p, a, a) to a), E9 `select-const` (the predicate is the literal true or false).
   - E10 `fold-exact`: an operation on literal operands becomes a literal only if its mathematically exact
     result, computed in exact rationals, is representable in the element type (significand within 24 or 53
     bits, exponent in range) and equals the literal written; division folds only when exact; a square root
     folds only when the literal r satisfies r² = operand exactly. Otherwise `rewrite.fold-inexact`.
   - E11 `pow2-scale`: x·2ᵏ·2ᵐ to x·2ᵏ⁺ᵐ. The step's declared range of x is re-checked in exact arithmetic: for
     every x in the range, |x|·2ᵏ and |x|·2ᵏ⁺ᵐ stay below the largest finite value of the type and, for x ≠ 0, at
     or above the smallest normal value (no overflow, no underflow into subnormals). Otherwise, or when the step
     declares no range (the missing side condition of FROB-REF-829), `rewrite.pow2-range`.
   - `schedule`: two adjacent operations in one block exchange places, provided neither reads the other's result
     and they do not both touch one buffer with at least one store. Otherwise `rewrite.schedule-dependent`. The
     schedule is part of the canonical program (N21a-18), so a target that was scheduled can only be reached
     through such steps: N21a-19's trace format defines the `schedule` step kind and N21a-18's scheduler emits
     one step per exchange.
   No step moves an operation across a loop boundary of a bounded loop block. Any other rule name, among them
   reassociation, distribution, fused multiply-add, reciprocal substitution, x·0 to 0 and x − x to 0, is
   `rewrite.rule-not-class-e`.
3. **Checks, in order, first failure reported:** `rewrite.parse` (either program or the trace fails to parse, or
   the element type is not one of the two); `rewrite.source-hash` (the source bytes do not hash to the stated
   source hash); then each step in order: `rewrite.rule-not-class-e`, `rewrite.precondition` (the rule's syntactic
   precondition fails at the stated node, with the rule named), `rewrite.fold-inexact`, `rewrite.pow2-range`,
   `rewrite.schedule-dependent`; finally `rewrite.target-hash` (the canonical bytes of the final program do not
   hash to the target hash). Caps (DESIGN): 10⁶ steps (ten times the engine's default fuel of 10⁵) and 2²⁰ nodes;
   a certificate beyond them is `unsupported`, never `accept`.
4. **Class.** `Certified` within the caps, capped by the inputs (N12-03's generic rule). The statement is equality
   over the reals of source and target, by rules each exact under round-to-nearest with contraction off; the
   bit-identity of emitted kernels on each backend is a test on a pinned corpus (N21a-19, MR-38), not this
   certificate.
5. **Library replay (DESIGN).** `cargo run -p frob-cert --example replay_traces -- --library <dir> --json`
   replays every (source, trace, target) triple stored under `<dir>` by N21a-19's engine and prints, per kernel,
   the verdict, the first failing rule and the step count; exit 0 when all are accepted, 2 when any is rejected.
6. **Registry row.** The baseline row `rewrite-trace` (N12-02, listed `not-implemented` until this checker lands,
   with its checker column pointing here) goes to `enabled` with the specimens and mutants of this bead. At M2 the
   revision ledger does not yet exist; it lands at M3 (N12x-08), and its revision 1 records the registry as it
   then stands, this row included. N12-02's checker column names this bead.

## Acceptance criteria

- [ ] A specimen trace of E1 `share`, E3 `comm-add`, E11 `pow2-scale` (f32, x ∈ [1, 2¹⁰], k = 3, m = 4) and two
      `schedule` steps is accepted, and `frob-verify` accepts its bundle under `env -i`.
- [ ] A trace with a reassociation filed as class E is rejected with `rewrite.rule-not-class-e` (KA-212; in f32
      with a = 10⁸, b = −10⁸, c = 1, (a + b) + c = 1 and a + (b + c) = 0); fused multiply-add, distribution and
      x·0 to 0 are rejected by the same rule.
- [ ] x + (+0) to x filed as E6 is rejected with `rewrite.precondition` naming E6.
- [ ] E10: 0.5·4 to 2 and 1/4 to 0.25 are accepted; 0.1·3 in f32 (the exact product 0.300000004470348… needs a
      26-bit significand) and 1/3 are rejected with `rewrite.fold-inexact`.
- [ ] E11 with a declared range that admits overflow (f32, x ∈ [1, 2¹⁰⁰], k = 30) or underflow (x ∈ [2⁻¹²⁰, 1],
      k = −10) is rejected with `rewrite.pow2-range`.
- [ ] A `schedule` step that exchanges two dependent operations is rejected with `rewrite.schedule-dependent`; a
      trace whose final program does not hash to the target is rejected with `rewrite.target-hash`.
- [ ] Differential: on 10⁴ random programs rewritten by N21a-19's engine the checker accepts every trace, as the
      reference replayer does; for each, three mutated traces (one step deleted, two steps exchanged, one step's
      node altered) get the same verdict from both replayers, and none whose final program differs from the
      target is accepted.
- [ ] `frob-cert` has no dependency on `frob-kir` in its `cargo tree`; the checker's lines count against the
      auditor's 12,000-line cap.
- [ ] The registry row `rewrite-trace` is `enabled`; GATE-LEMMA-03's per-kind condition (one accepted specimen, at
      least three rejected mutations) is recorded; `frob-verify --help` lists the kind.
- [ ] The library replay of the M2 kernel library accepts every stored trace.

### End-to-end script and logging

`scripts/e2e/lemma_auditor_mutations.sh` (N12-34) carries the specimens and mutants under steps
`kind/rewrite-trace/<specimen-or-mutant>`. This bead's own script, `scripts/e2e/lemma_rewrite_trace.sh` (sources
the STD-E2E helper, seed-explicit, idempotent, writes under `target/`): (1) `start`: commit, toolchain, host
fingerprint; (2) `frob-verify` under `env -i` on every specimen and mutant, asserting the expected verdict and
first failing rule; (3) `cargo run -p frob-cert --example replay_traces -- --library <dir> --json` on the
checked-in kernel library, asserting exit 0; (4) the same on a scratch copy in which one trace has a step
deleted, asserting exit 2 and the kernel and rule named. NDJSON to
`target/e2e-logs/lemma_rewrite_trace/<utc>.ndjson` with a transcript; every line carries `ts`, `script`, `bead`
("N12p2-02"), `step`, `event`, the exact command line, exit code, wall time; per trace the kernel name, source and
target hashes, element type, step count, counts by rule, the verdict, the expected and observed first failing
rule and the failing step's index and node; a `summary` with traces accepted, mutants rejected by the expected
rule, and false accepts against 0.

### Known answers and negative controls

KA-212 (a rewrite trace with a reassociation filed as class E is rejected) and KA-087 (the f32 control: 1 against
0). CX-111 (a reassociation is not a harmless rewrite). Negative controls: the mutations above, and the planted
twelfth rule x·0 to 0 (∞·0 is NaN), which the checker names as not in the table. Metamorphic: renaming the
program's inputs changes no verdict; replaying an accepted trace twice gives identical report bytes.
Determinism: D0; identical verdicts and reports on Linux and macOS.

## Considerations

- Equality over the reals is what a class-E trace establishes as a theorem; bit-exactness in floating point is a
  test on a pinned corpus on every backend, not this certificate.
- The trace format and the rule table are N21a-19's. A rule added there is an ADR with its edge-set proof and a
  new checker version (N21a-19's Considerations); until this checker admits it, a trace that uses it is rejected,
  which is the fail-closed direction.
- Scheduling: N21a-18 reorders independent operations, the canonical hash covers the order, and the scheduler
  emits each exchange as a `schedule` step, so a scheduled kernel is certified by replay up to its scheduled
  hash. A trace that omits an exchange ends at a program that differs from the target only in order and fails
  `rewrite.target-hash`: the checker never accepts a scheduled target on a trace that does not show the
  scheduling.
- If KILL-KIR fires, the table still governs any generated kernels that remain and the specialization route's
  bit-identity requirement; the checker stays.
- Auditor size: the IR parser is the largest part; it must stay within the 12,000-line cap shared by every kind.
