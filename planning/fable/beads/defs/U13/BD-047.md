## Background
Construction C-02: frames are objects and a rigid transform `a_from_b` is a morphism from b to a, so transforms form a groupoid. The adjoint Ad is a functor from that groupoid to invertible maps on 𝔰𝔢(3); the group coadjoint is its contragredient on 𝔰𝔢(3)*. A twist is a vector typed by a frame, a wrench is a covector typed by a frame, and their pairing is power, which does not depend on the frame. This replaces 4×4 matrices and 6-vectors whose frames live in comments.

Three different maps move quantities between frames, and using one where another is meant is the classic silent error of robot dynamics code: a wrench moved by the twist map loses its moment arm and nothing faults. The conventions fix them as three types:

| Type | Matrix for g = `a_from_b` | Takes | Law |
|---|---|---|---|
| `TwistMap` | Ad_g | a twist in b to a twist in a | preserves the bracket; Ad(gh) = Ad(g)·Ad(h) |
| `WrenchPushforward` | Ad_g⁻ᵀ | a wrench in b to a wrench in a | ⟨Ad_g⁻ᵀ w, Ad_g ξ⟩ = ⟨w, ξ⟩ |
| `WrenchPullback` | Ad_gᵀ | a wrench in a to a wrench in b | inverse of the push-forward; a Jacobian transpose is a pull-back |

No function accepts one where another is expected. Decision (part of ADR-MARROW-05): the maps are distinct newtypes so that the compiler rejects a push-forward where a pull-back is meant. Rejected: one `Mat6` with a doc comment (the status quo this replaces); a run-time frame tag on every vector in kernels (costs memory and time in batched code; see PO-MARROW-02 in N13-12). Tier: Solid.

## Scope
In: the `Frame` trait and phantom-typed `Transform<A, B>`, `TwistIn<F>`, `WrenchIn<F>`, `PointIn<F>`; the three map types; run-time frame tags for model-indexed frames; frame-typed screw and point Jacobians with their transposes; compile-fail tests; the planar 2R fixture; the Pairing law.
Out: reflections (`Isometry`, N13-02); the airlock's `MixedWrench { force_world, torque_body }` (frob-fsim, which first moves a wrench with the push-forward defined here); zero-cost proof for emitted kernels (N13-12); dynamics recursions (frob-dyn).

## Technical approach
**Types (DESIGN; from the type sketches).**
```rust
pub trait Frame: 'static {}                                   // zero-sized marker
/// `a_from_b`. Transform<A,B> * Transform<B,C> = Transform<A,C>; nothing else composes.
pub struct Transform<A: Frame, B: Frame> { motor: fs_ga::Se3, _frames: PhantomData<(A, B)> }
pub struct TwistIn<F: Frame>  { xi: fs_ga::Twist,  _f: PhantomData<F> }
pub struct WrenchIn<F: Frame> { w:  fs_ga::Wrench, _f: PhantomData<F> }
pub struct TwistMap<A: Frame, B: Frame>(Transform<A, B>);          // Ad_g
pub struct WrenchPushforward<A: Frame, B: Frame>(Transform<A, B>); // Ad_g⁻ᵀ
pub struct WrenchPullback<A: Frame, B: Frame>(Transform<A, B>);    // Ad_gᵀ
```
`AdjointMap` is kept as an alias of `TwistMap` (the name used in the component table). Operations: `Transform::inverse() -> Transform<B, A>`; `act(PointIn<B>) -> PointIn<A>`; `TwistMap<A,B>::apply(TwistIn<B>) -> TwistIn<A>`; `WrenchPushforward<A,B>::apply(WrenchIn<B>) -> WrenchIn<A>`; `WrenchPullback<A,B>::apply(WrenchIn<A>) -> WrenchIn<B>`; `pair(WrenchIn<F>, TwistIn<F>) -> Power`; addition only between values of one frame. The maps are obtained only from a transform (`g.twist_map()`, `g.wrench_pushforward()`, `g.wrench_pullback()`); there is no conversion between map types and no public access to the raw 6×6 matrix except through `Mat6` accessors that keep the type.

**Components** (g = (R, p) = `a_from_b`):
- Ad_g(ω, v) = (R·ω, R·v + p × R·ω).
- Push-forward Ad*_g(τ, f) = (R·τ + p × R·f, R·f); equals `fs_ga::Se3::coadjoint`.
- Pull-back (Ad_g)ᵀ(τ, f) = (Rᵀ·(τ − p × f), Rᵀ·f); equals the push-forward of g⁻¹.
- Check by hand: R = I, p = (1, 0, 0) m, wrench (0, (0, 0, 1) N) in b pushes forward to torque p × f = (0, −1, 0) N·m and the same force. Moving it with the twist map gives zero torque: the moment arm is lost.

**Model-indexed frames.** A compiled model has frames known only at run time (one per body and port). `FrameTag(u32)` and `TaggedTransform { a, b, motor }` carry the names as data; `compose_checked` and the tagged map applications return `Err(FrameMismatch { expected, found })` on a mismatch. The model compiler runs every such check once at model compile time and then lowers to untagged kernels, so batched kernels pay nothing (static frames are phantom types; tagged checks never run inside a step).

**Jacobians.** `ScrewJacobian<F>` has columns `TwistIn<F>`; `apply(q̇) -> TwistIn<F>`; `transpose_apply(WrenchIn<F>) -> JointForces` (a pull-back onto joint space). `PointJacobian<F>` at a point p has columns vᵢ + ωᵢ × p for a screw column (ωᵢ, vᵢ) and pairs with a pure force at p; the screw Jacobian pairs with the wrench (p × F, F) about the frame origin. There is no function that slices rows out of a `ScrewJacobian` and returns a `PointJacobian`.

**The planar 2R fixture** (hand-checkable; the first fixture of the dynamics construction C-04). Links 0.4 m and 0.3 m, joint angles 0 and π/2, axes along +z. Tool point (0.4, 0.3) m. Point Jacobian J = [[−0.3, −0.3], [0.4, 0.0]] m/rad. Tool force (10, 0) N gives joint torques Jᵀ·f = (−3, −3) N·m. Joint rates (0.2, −0.1) rad/s give tool velocity J·q̇ = (−0.03, 0.08) m/s. Power is −0.3 W by both routes (f·v and τ·q̇). Space screw columns are (e_z, 0) and (e_z, (0, −0.4, 0)); with the wrench about the origin (p × F, F) = ((0, 0, −3), (10, 0, 0)) they give the same (−3, −3). Counterexample: taking the lower three rows of the space screw Jacobian as the point Jacobian gives torques (0, 0).

**Laws registered** (harness N13-08, 10⁶ cases, ulp bounds of GATE-MARROW-01): Pairing, ⟨Ad*_g w, Ad_g ξ⟩ = ⟨w, ξ⟩; push-forward composed with pull-back is the identity; `TwistMap` composition Ad(gh) = Ad(g)·Ad(h) through typed composition; chart-change loop: a loop of transforms a←b←c←a composes to the identity inside 64 ulp.

**Determinism and evidence.** Zero-sized markers only; arithmetic is `fs-ga`'s (D2 per platform). Tier G0 laws and G1 fixture on `host`.

## Acceptance criteria
- [ ] Mismatched frames fail to compile (the seed bead's done-condition), shown by `compile_fail` doc tests for: composing `Transform<A,B>` with `Transform<C,D>`; adding `TwistIn<B>` to `TwistIn<C>`; applying a `TwistMap` to a `WrenchIn`; passing a `WrenchPullback` where a `WrenchPushforward` is required; pairing a wrench and a twist of different frames.
- [ ] The planar 2R fixture gives torques (−3, −3) N·m and −0.3 W by both routes and tool velocity (−0.03, 0.08) m/s, exactly in rationals on the host and within 4 ulp in `f64` (the seed bead's done-condition).
- [ ] The lower-three-rows shortcut, which gives (0, 0), is caught: it is planted as a mutation and the fixture fails (the seed bead's done-condition); the control is registered.
- [ ] The push-forward hand check returns torque (0, −1, 0) N·m; the twist-map mutant returns zero torque and fails.
- [ ] The Pairing law and the push-forward/pull-back inverse law pass on 10⁶ cases; rows appended to the GATE-MARROW-01 ledger.
- [ ] `size_of::<Transform<A, B>>() == size_of::<fs_ga::Se3>()` and likewise for the twist and wrench wrappers (the phantom types add nothing).
- [ ] Tagged frames: a mismatched `compose_checked` returns `FrameMismatch` naming both tags.

- `planar_2r_torques_and_power` (KA-228): all stated values, by both routes; rational version with exact equality.
- `planar_2r_lower_rows_shortcut_is_wrong` (CX-117): the shortcut's (0, 0) differs from (−3, −3).

- `pushforward_pullback_inverse`, `pairing_invariant`, `twist_map_functor`, `transform_loop_identity`: law tests through `run_law` (KA-194, KA-244).
- `wrappers_are_zero_cost`: size and alignment assertions.
- `tagged_frames_checked`: mismatch detected; a matched chain of 50 tagged transforms equals the untagged product bit for bit.
### End-to-end script and logging
`scripts/e2e/marrow_frames.sh`: (1) `cargo test -p frob-lie --doc` and the frame tests; (2) the planar 2R fixture test binary with `--nocapture`, whose printed torques, tool velocity and powers the script parses and compares with the known answers; (3) `frob capabilities --json`, asserting the frame-typing row of `frob-lie` is reported and that its status is not `implemented` unless its gate row exists. `STD-E2E` NDJSON at `target/e2e-logs/marrow_frames/<utc>.ndjson` with a transcript: `assert` lines for each compile-fail case (expected failure observed), `metric` lines for the fixture values against their known answers with units, the evidence block of any verb envelope, and on failure the first differing value and the fixture path; summary with counts and GATE-MARROW-01.
### Known answers and negative controls
KA-193, KA-194, KA-228, KA-244; CX-099, CX-117; CX-020 (one adjoint for everything). Planted mutations, each of which must fail at least the fixtures listed: a pull-back in place of a push-forward (pairing law, inverse law, 2R fixture); Ad* and its inverse exchanged (pairing law, hand check, PO-MARROW-01); linear and angular parts exchanged in a twist (2R fixture, pairing law, PO-MARROW-01). Metamorphic: re-expressing every quantity in another body frame leaves powers and energies unchanged. Determinism: identical bytes twice, across thread counts, debug and release.

## Considerations
- C-02's "retired when" rule: if a loop of chart changes exceeds its error budget, that chart pair is withdrawn from the derivative path and the query is refused (FROB-REF-213 in BD-011).
- A reflection is not a morphism of this groupoid; mirror images use `Isometry` (N13-02), never `Transform`.
- The airlock's mixed wrench (world-frame force with body-frame torque, as `fs-mbd` uses) is a fourth type in `frob-fsim` only; a wrench at any other reference point is first moved by the push-forward defined here.
- L-6: above layer 1 no public signature takes a bare `f64` physical quantity; these typed values are what such signatures use.
