## Background
The project's rule is that a plausible shortcut ships with the smallest hand-checkable case that breaks it, and that the case becomes a permanent negative control: a planted defect that a gate must catch. A rule that ships without such a case has not been thought through, and a gate that no deficient model can fail validates nothing. The negative-control registry (`frob-conformance/registry/controls.toml`) is seeded from the counterexample catalogue: each entry becomes at least one control, attached to the gates of the rule it protects.

This bead is the catalogue for the conventions: the eight entries CX-098 to CX-105. For each: the tempting shortcut, the smallest case that breaks it with its numbers, the rule it protects, and the control record it becomes. Tier of the content: Solid.

## Scope
In: the eight entries CX-098 to CX-105 in the counterexample catalogue `frob-conformance/registry/counterexamples.toml`, with the substance each needs to become a control (rule identifiers, kind of control, one planted-defect identifier, the expected observation); a host test that recomputes every number in the table.
Out, with the bead that has it: the catalogue's record schema and loader, and the seeding tool that turns entries into rows of `registry/controls.toml`, allocates their `NC-` identifiers, keeps the seed map, resolves rules that name no gate and proves completeness by the join (N38b-05). This bead writes no row of `controls.toml` by hand. The control runner and the rule that a gate with no caught control cannot pass (N38b-04). The tests that run the controls (owners in the last column). The known-answer registry (N11-KA).

## Technical approach
**Data.** Each row below is one entry of `registry/counterexamples.toml` in the catalogue's record schema (N38b-05): `id` (the CX number, append-only), `shortcut`, `case`, `numeric` (true for all eight), `plan_case` (`"numbers"` for all eight: none of them is among the catalogue's seventeen word-only entries), `case_supplied_by` (empty), `rule`, `rule_ids` (the gates, obligations, cards and refusal codes of the rule column), `defined_in` (§11.2 to §11.8), `same_as` (empty), `label` (DESIGN), `control_kind` (`mutation`, `planted-input`, `planted-design` or `planted-world`) and `plant` (for a mutation, the build or plan flag that plants the shortcut in the real component, never a mock; otherwise the fixture, design or input). The expected observation of the control column is kept in the entry's `case` text so that the seeding tool can copy it into the control's `expect`. The seeding tool writes one control per entry into `controls.toml` (the record `id`, `seed`, `gate`, `kind`, `target`, `defect`, `expect`, `last_seen` of BD-025); DESIGN, correcting an earlier draft of this bead that wrote control records directly: that file is written only by the tool, so control identifiers are allocated once and never rewritten. The second defect of CX-099 (the compile-fail case of the typed API) and of CX-104 (closed-closed windows) are not second controls of the entry: they are the stated controls of KA-194 and KA-204 (N11-KA), from which the tool allocates their own controls with `seed = "KA-194"` and `seed = "KA-204"`.

**Gates and batteries each control attaches to.** CX-098, CX-099, CX-100, CX-102: GATE-MARROW-01 (the law table) and the conventions battery. CX-098, CX-100 and CX-102 are also three of the eight Marrow mutations measured for GATE-MARROW-04 (reversed ad*; a missing parity sign on a mirrored axis; the curvature bracket sign reversed): their `plant` is the `MutationId` of the mutation harness's operations table (N13-18: M1 for CX-098, which shares it with CX-116; M4 for CX-100; M7 for CX-102), the same switch the harness flips, and their `rule_ids` carry GATE-MARROW-04 beside GATE-MARROW-01, so the seeded control of CX-100 is N13-18's M4 record and that of CX-102 its M7 record. CX-101: the design-check battery of the fill rule; the plan names no gate for it, so its `rule_ids` are FROB-REF-168 and §11.5, which the seeding tool resolves through `registry/rule_gates.toml` once N13-04 maps the fill rule to its gate, and until then writes to `registry/seed_findings.toml` with `gate-added` requested. **The boundary of a window (CX-104).** The catalogue states CX-104 with the half-open window (a, b], the conventions chapter's form, while the Sensorium entry CX-201 states [open, close). The decision bead N20a-49 rules between the two; while it is open the fail-closed default `OpensAt`, [a, b), is in force, and on that verdict KA-204 and CX-104 are restated to match KA-475 and CX-201 (N20a-49). The entry keeps the plan's text with this note in its `case`; its two mutations (point sampling, which reads 0 N; closed-closed windows, which count the boundary impact twice) are wrong under either rule and are unchanged.
**Completeness check.** The join of N38b-05 run over this chapter: each of the eight ids is present with every field filled, has a control after seeding, and each control resolves to at least one gate; the chapter count is 8, as the catalogue's table states. ## Test plan
### Unit tests
`cx_registry_conventions_complete` (eight ids, every catalogue field present, `numeric = true`); `cx_conventions_numbers` (every number in the table recomputed: (0, −1, 0) N·m; e_z ↦ −e_z; 64.8 kg and 3.45 kg, ratio 18.8; the loop rotation +a·b about z to second order; 39 units = 32.5 ms and 30.77 Hz; 20 N); `cx_conventions_plan_case` (all eight `plan_case = "numbers"`, `case_supplied_by` empty); `cx_conventions_gates` (after seeding on a scratch copy: CX-098, CX-100, CX-102 → {GATE-MARROW-01, GATE-MARROW-04}; CX-099 → {GATE-MARROW-01}; CX-103 to CX-105 → {GATE-SENS-04}; CX-101 resolved through `rule_gates.toml` or present in `seed_findings.toml`); `cx_controls_have_gates_and_targets` (after seeding, each of the ten controls has a gate, or is CX-101's finding, and a `target` naming its owner's plant: `N13-18:M1`, `M4`, `M7`, `BD-047:cx-099`, `N13-04`'s planted enclosure, `N13-06:cx-103` to `cx-105`). Run as `FROB_TEST_SEED=0 cargo test -p frob-conformance --test g0_laws -- cx_registry_conventions cx_conventions cx_controls_have` (the laws-and-self-tests tier; the three filters select exactly the tests of this list).
### End-to-end script and logging
`scripts/e2e/registry_n11_cx.sh` (sources the STD-E2E helper; idempotent; it calls only cargo targets of its dependencies): runs the unit tests above; N38b-05's seeding tool, `cargo test -p frob-conformance --test seed_controls -- --ignored seed`, twice, asserting that the second run leaves the digest of the committed `controls.toml` unchanged; the join, `cargo test -p frob-conformance --test seed_join`; prints the chapter's eight entries and ten controls with their gates and lists CX-101's finding while it is open; then, on scratch copies under `target/e2e-scratch/registry_n11_cx/` (never the committed files), plants the negative controls below one at a time and asserts each is rejected by its named test. NDJSON at `target/e2e-logs/registry_n11_cx/<utc>.ndjson` with a transcript: each line has `ts`, `script`, `bead` (`N11-CX`), `step`, `event`, the command line, exit code and wall time; `metric` lines for the counts (entries against 8, controls against 10, open findings), the digest of `controls.toml` before and after the second seeding; one `assert` per planted copy with the test that rejected it; on failure the first missing entry or unresolved gate with the registry path; a `summary` line. Running the conventions battery once per control with that control active is the owner's script (`scripts/e2e/conventions.sh`, N13-01), not this bead's.

Determinism: exact.

## Considerations
- A control is a defect, not a boundary: "the request is refused at the limit" tests the limit; the control is the build or input in which the rule was removed.
- If a false result is ever found in use that traces to a convention, it becomes a permanent control here with the case that exposed it.
- CX-101's control depends on the plausibility rule decided in N13-03; until then it is attached to the provisional rule.
- Owed by the owner beads in the last column, not by this registry: each control is run whenever its gate or battery is run, a run in which it is not caught fails that gate or battery, and every control is observed caught (`last_seen.caught = true`, written by the control runner of N38b-04) before the M1 exit; a control never observed is reviewed as suspect. Running the conventions battery with each control active is a stage of N13-01's script.
