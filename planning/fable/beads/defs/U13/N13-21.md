## Background
GATE-MARROW-03 (claim: Known answer; M3; TARGET): Γ_mech and Γ_obs equal the groups on file for all eighteen archetypes and for 24 planted asymmetries (a moved sensor, a one-sided payload, a changed sole material, a reversed gear), with the correct breaker named in every case; zero disagreements. The gate completes at M3, when all eighteen archetypes exist; its rows for the first four archetypes (`quad-mammal`, `humanoid`, `diff-drive`, `mecanum`) are due at M1, because the M1 studio already reports symmetry in `design check` and an M1 agent may already ask which group licenses what. This bead is the M1 end-to-end run through the user-visible verb `analyze.symmetry` (read; M1: Γ_mech and Γ_obs of a design, with the element that breaks each excluded generator; analysis A-03, built by BD-102 on the computation of N13-15 and N13-16). Tier: Solid. It is a test bead.

Γ_mech is the group of automorphisms of the labelled kinematic tree realized by an isometry of the body and preserving every mechanical parameter. Γ_obs is its subgroup that also preserves the sensor suite, the payloads, gravity and every task term. Only Γ_obs may tie weights, augment data, deduplicate designs or enumerate gaits. A "breaker" is the first field that excludes an element of Γ_mech from Γ_obs, or, for a mechanical asymmetry, the first mismatching field found when a candidate isometry is verified.

## Scope
In: `scripts/e2e/analyze_symmetry.sh` in its M1 mode; the groups on file for the four archetypes; the M1 planted asymmetries; the forward-lidar known answer; the provisional M1 rows of the gate.
Out: the computation (N13-15, N13-16); the verb and the near-symmetry report (BD-102); the archetypes (BD-109); the full gate (N13-22).

## Technical approach
**Groups on file** (`tests/fixtures/oracle/symmetry/<archetype>.json`, written by hand from each archetype's definition, with pin and date, never regenerated from the candidate). As built, before any sensor is mounted: `quad-mammal` C₂ × C₂ (order 4: the fore-aft mirror, the left-right mirror, the half-turn about the vertical); `humanoid` C₂ (the sagittal mirror); `diff-drive` C₂ (the mirror exchanging the two driven wheels; the caster breaks fore-aft); `mecanum` C₂ × C₂ (the wheels are handed, and each mirror maps a wheel to one of opposite roller handedness). Each file lists the group's name and order, its generators as exact isometries, and the expected body permutation and joint signs per generator.
**Script steps** (plain shell, idempotent, exact; exits non-zero on failure).
1. `frob design new <name> --template <archetype> --key <k> --json` for the four archetypes, with no sensors and no task; `frob analyze symmetry <id> --json`. Assert: Γ_mech equals the group on file (order, generators up to group equality, permutations and signs); Γ_obs equals Γ_mech (with no sensor, payload or task term the two coincide); the evidence block says determinism `exact`, route `construction` (the archetypes are built with `mirror` and `radial`), class `Certified` when the certificate is attached and `Tested` otherwise; `group_kind` fields are present.
Every edit below is a typed edit of BD-058 through `frob design edit <id> <kind> <target> <value> --expected-parent <DesignId> --key sym-<case>-<run-id> --json`, with the parent the previous step's `DesignId`, using the kinds `add-sensor`, `move-sensor`, `remove-sensor`, `add-payload`, `set-material`, `regear`, `set-param` and `assert-symmetry`; each new `DesignId` is logged.
2. **Forward lidar.** Add one forward-facing lidar on the torso of `quad-mammal` (`add-sensor`), bind the M1 velocity task, and re-run (`frob analyze symmetry <id> --task <velocity task> --json`): Γ_mech = C₂ × C₂ (order 4), Γ_obs = C₂ (order 2); the fore-aft mirror and the half-turn each list the lidar mount as breaker; the first-ranked repair is a typed edit that adds the mirrored sensor. The left-right mirror maps the lidar to itself.
3. **Planted asymmetries, M1 subset** (four kinds on each of the four archetypes where the kind applies; sixteen cases at most, each a typed edit applied to a fresh copy):
   - a moved sensor (a symmetric sensor pair with one mount shifted by 5 mm): Γ_mech unchanged; Γ_obs loses every element that exchanged the pair; breaker = that sensor's mount;
   - a one-sided payload (2 kg on the left, the figure of the zoo's payload breaker row and of the planted variants BD-246 stores for the same cases): Γ_mech unchanged; Γ_obs loses the elements that move the payload; breaker = the payload;
   - a changed sole material on one foot (tyre material on one wheel for the wheeled archetypes): Γ_mech loses the elements that move that foot; first mismatch = that foot's interface card; the encoder permutation of each lost element is still reported as existing;
   - a reversed gear on one joint: Γ_mech loses the elements that move that joint; first mismatch = the signed transmission ratio.
   For each case assert the expected group orders before and after (on file per case), and that the named breaker or first-mismatch field is exactly the planted field.
4. **Near symmetry.** One leg of `quad-mammal` lengthened by 0.4%: Γ_mech drops accordingly, and the near-symmetry report names the link length with its size and the typed edit that restores it.
5. **No sensors is not "no group".** Removing the lidar restores Γ_obs = Γ_mech without any author declaration.
6. **Refusal path.** A design whose `symmetry` block keeps `assert_obs: C2xC2` while carrying the forward lidar and a task (the same design as control variant (a) of the zoo golden ZOO-quad-mammal, built here by typed edits so that this script needs no zoo file; an `assert_mech: C2xC2` on the same design is accepted, because the lidar leaves Γ_mech unchanged) is refused by `frob design check` with FROB-REF-109 (declared symmetry differs from computed symmetry), exit 3. The check is M1 work (the assertion check of N14a-11, run by `design.check`, BD-110, both prerequisites of this bead), so the step is asserted, never skipped.
7. **Record.** GATE-MARROW-03 closes in parts (the M1 part here, the M3 part in N13-22; the delivery register's table of gates that close in parts). The M1 part is measured by the gate's tier run, `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers --features gauntlet-mutations -- GATE-MARROW-03`, whose test drives the same oracle files and planted cases and runs controls (i) to (iv) in the same run, and is entered by the gate recorder (`cargo run -p frob-conformance --example record_gate -- --gate GATE-MARROW-03 --receipt <hash> --part M1`, N38b-19) by a session that did not implement the mechanisms. The part's status is `pass` or `fail` (the register's closed set; "partial" is not a status) with `measured = "4 of 18 archetypes, <k> of 24 planted, <d> disagreements"`; the M3 part stays `not-run` until N13-22.

## Acceptance criteria
- [ ] For the four archetypes Γ_mech equals the group on file and Γ_obs = Γ_mech with no sensors, payload or task; zero disagreements.
- [ ] The forward-lidar case returns Γ_mech = C₂ × C₂, Γ_obs = C₂ and the lidar mount as the breaker of both excluded elements.
- [ ] Every planted asymmetry of the M1 subset changes the right group in the expected way and names the planted field as breaker or first mismatch; zero disagreements.
- [ ] The 0.4% asymmetry is found with its repair edit.
- [ ] The `assert_obs: C2xC2` design with the forward lidar is refused with FROB-REF-109 and exit 3, and the `assert_mech: C2xC2` variant is accepted.
- [ ] Negative controls caught: (i) a build whose filter returns Γ_mech as Γ_obs fails step 2; (ii) a build that ignores interface cards in the descent fails the sole-material cases; (iii) a build that compares gear ratios by absolute value fails the reversed-gear cases; (iv) a breaker reported for a field other than the planted one fails step 3.
- [ ] The M1 part of GATE-MARROW-03 is recorded through the recorder from a `g1_known_answers` receipt (commit, fingerprint, command, receipt hash, the controls caught in the same run), with status `pass` or `fail` and the counts in `measured`, by a session that did not implement the mechanisms; the M3 part is `not-run`; the script's log meets the logging standard; no private data appears in it.

## Test plan
### Unit tests
A dry-run test of the script's command list; a schema test that the oracle symmetry files validate against `frob.symmetry.oracle/1` and that each lists a group whose stated order equals the closure of its generators (checked with an independent small closure routine inside the test, not with `frob-algebra`).
### End-to-end script and logging
`scripts/e2e/analyze_symmetry.sh --milestone m1`, sourcing the `STD-E2E` helper. NDJSON at `target/e2e-logs/analyze_symmetry/<utc>.ndjson` with a transcript. Each `cmd` line has the exact command, exit code and wall time; each envelope's evidence block is copied (class, tier `static`, determinism `exact`, `DesignId`, `ModelId`, task identity); `assert` lines carry archetype or case id, expected and found group names and orders, and the breaker field path expected and found; on failure the first differing element (permutation, signs, isometry) and the paths of the saved envelope and oracle file; `refusal` lines for step 6; `metric` lines for wall time per call (TARGET: under 2 s inside `design check` for a template-sized design); the final `summary` gives assertions passed and failed and the gate touched (GATE-MARROW-03, partial).
### Known answers and negative controls
KA-230 (C₂ × C₂, C₂, lidar mount), KA-259 and KA-270 for the four archetypes; CX-118 (tying under the mechanical group), CX-121 (material edit). Controls (i) to (iv); the planted asymmetries are themselves the gate's controls: each must change the group and name its breaker. Metamorphic: a design built with `mirror` equals its hand-expanded form and has the same groups; relabelling bodies changes nothing. Determinism: exact; envelopes byte-identical twice and across platforms apart from the cost block.

## Considerations
- How the 24 planted asymmetries are distributed over archetypes is not fixed by the gate text; the distribution chosen here (four kinds on six archetypes, of which four exist at M1) is DESIGN and is frozen in the oracle directory before the first measurement.
- Γ_obs depends on the task; the M1 run binds the M1 velocity task. Sensor timing predicates (a spinning lidar's beam order) arrive with the sensing work at M3 and may shrink Γ_obs further; the oracle files state which predicates they assume.
- The schedule note for this gate: rows for the first four archetypes at M1, complete at M3 when all eighteen exist.
- DESIGN (reading shared with the zoo expectation files, ZOO-quad-mammal and ZOO-humanoid): a payload reduces Γ_obs only and leaves Γ_mech unchanged. Reason: the algorithm filters payloads at the step that reduces Γ_mech to Γ_obs ("maps every payload to a payload"), and the nested-groups law (removing every sensor, payload and task term gives Γ_obs = Γ_mech) holds only if Γ_mech never sees a payload. The design-language sentence that a payload "enters both symmetry groups" is read as "both groups are recomputed after a payload edit". The zoo expectation file of `quad-mammal` states the same rule for its 2 kg left-side payload (Γ_mech = C₂ × C₂, Γ_obs = C₂ generated by the transverse mirror).
- The groups on file here (`tests/fixtures/oracle/symmetry/<archetype>.json`) and the symmetry rows of the four M1 zoo expectation files (`zoo/<archetype>.expect.toml`, beads ZOO-quad-mammal, ZOO-humanoid, ZOO-diff-drive, ZOO-mecanum) state the same groups from two hand-written sources; where a zoo expectation file is present, the oracle schema test of this bead also asserts that the two agree for that archetype, so that neither can drift (non-blocking: the two beads are `related`, neither waits for the other).
