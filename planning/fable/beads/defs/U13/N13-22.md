## Background
GATE-MARROW-03 (claim: Known answer; milestone M3; TARGET): Γ_mech and Γ_obs equal the groups on file for all eighteen archetypes and for 24 planted asymmetries (a moved sensor, a one-sided payload, a changed sole material, a reversed gear), with the correct breaker named in every case; zero disagreements. It is one of the gates behind the bet that the right group for equivariance is the observation-preserving subgroup Γ_obs ≤ Γ_mech, and behind the improvement "use only the generators that the current payload, terrain and sensors leave intact, found by intersecting stabilizers, and report each breaker". N13-21 ran the first four archetypes at M1. At M3 the remaining fourteen archetypes exist (BD-246) and the sensing work has refined Γ_obs per robot and task with sensor timing (BD-241, verb `sense.symmetry`). This bead completes the measurement and writes the gate record. Tier: Solid. It is a gate bead run by a session that did not implement the mechanisms.

## Scope
In: the oracle files for the remaining fourteen archetypes and for all 24 planted cases; the M3 mode of `scripts/e2e/analyze_symmetry.sh`; agreement between `analyze.symmetry` and `sense.symmetry`; the gate row.
Out: the mechanisms; the archetypes; controllers and policies that consume the groups.

## Technical approach
**Groups on file, as built, before any sensor is mounted** (the known answer for the eighteen):
| Archetype | Γ_mech as built |
|---|---|
| `quad-mammal`, `quad-sprawl`, `mecanum`, `tracked-flipper`, `wheel-leg` | C₂ × C₂ |
| `hexapod-radial` | D₆ (C₆ with handed legs) |
| `octopod` | D₈ radial; C₂ in a spider layout |
| `biped-point`, `humanoid`, `diff-drive`, `ackermann`, `rocker-bogie`, `balancer-2w` | C₂ |
| `omni-3` | D₃ |
| `swerve-4` | D₄ on a square base |
| `tri-wheel-stair` | C₂, with C₃ or D₃ in each cluster |
| `mobile-manipulator` | trivial with the arm off-centre |
| `snake-crawler` | C₂ under head-to-tail reversal |
Each oracle file gives the group's order, generators as exact isometries, permutations and joint signs, the variant assumed (handed or unhanded legs, radial or spider layout), and, for the reference sensor suite and task of that archetype, the expected Γ_obs with the breaker of every excluded element (for `quad-mammal` with a forward sensor: Γ_obs = C₂, breaker = the sensor mount).
**The 24 planted asymmetries** (DESIGN distribution, frozen before measurement): the four kinds (a moved sensor; a one-sided payload; a changed sole or tyre material; a reversed gear) on six archetypes chosen to cover the group families: `quad-mammal` (C₂ × C₂), `hexapod-radial` (D₆), `humanoid` (C₂), `diff-drive` (C₂), `mecanum` (C₂ × C₂ with handed wheels), `swerve-4` (D₄). For each case the oracle states the groups before and after and the field that must be named: a sensor mount or a payload for the two Γ_obs kinds (Γ_mech unchanged); an interface card or a signed transmission ratio for the two Γ_mech kinds.
**Script, M3 mode** (`scripts/e2e/analyze_symmetry.sh --milestone m3`):
1. For each of the eighteen archetypes (and each on-file variant): create from the template (`frob design new <name> --template <archetype> --key sym3-<archetype>-<run-id> --json`), run `frob analyze symmetry <id> --json` with no sensors; assert Γ_mech equals the file and Γ_obs = Γ_mech.
2. Mount the archetype's reference sensor suite and bind its reference task (typed edits as in N13-21: `frob design edit <id> add-sensor <target> <value> --expected-parent <DesignId> --key sym3-<case>-<run-id> --json`, one per sensor, and likewise for the planted edits of step 3); assert Γ_obs and every breaker equal the file; run `frob sense symmetry <id> --task <task> --json` and assert it reports the same Γ_obs and the same excluded elements with the same reasons (the two verbs must not disagree).
3. Apply each of the 24 planted asymmetries to a fresh copy; assert the groups after and the named field.
4. Special rows: `hexapod-radial` with handed legs gives C₆ and its irreducible decomposition contains complex-type constituents (`frob algebra irreps --design … --task … --in joint-positions --out joint-positions`, the bound model's named channel space of N13-14, reports at least one `complex` constituent); `swerve-4` reports the hub group D₄ and, separately, each module's own symmetry, as the input to the nested-symmetry pilot; `mobile-manipulator` reports the trivial group and the verb states that tying is off and augmentation alone remains; `tri-wheel-stair` reports C₂ for the vehicle and the three-fold group inside each cluster.
5. Law check on every case: Γ_obs ≤ Γ_mech; removing every sensor, payload and task term gives Γ_obs = Γ_mech.
6. Negative controls: re-run steps 1 to 3 against builds with each registered control active (unfiltered Γ_obs; interface cards ignored; gear ratios compared by absolute value; parity sign omitted); each must produce at least one disagreement.
7. Record the M3 part of GATE-MARROW-03 in `registries/gates.toml` (the M1 part is N13-21's): the measurement is the gate's tier run, `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers --features gauntlet-mutations -- GATE-MARROW-03`, which drives the same oracle and case files and catches the controls of step 6 in the same run; the row is entered by the gate recorder (`cargo run -p frob-conformance --example record_gate -- --gate GATE-MARROW-03 --receipt <hash> --part M3`, N38b-19). Status `pass` only with eighteen of eighteen archetypes and twenty-four of twenty-four planted cases agreeing and every breaker correct; measured values (cases, disagreements, wall time), commit, fingerprint, command, receipt hash. One disagreement is `fail`, with the first differing case.
**Evidence.** Claim: Known answer; class `Tested` against the files on file (`Certified` for elements with attached certificates); determinism exact.

## Acceptance criteria
- [ ] Eighteen of eighteen archetypes: Γ_mech equals the group on file; with the reference sensor suite and task, Γ_obs and its breakers equal the file.
- [ ] Twenty-four of twenty-four planted asymmetries: the right group changes in the expected way and the correct breaker is named; zero disagreements.
- [ ] `analyze.symmetry` and `sense.symmetry` agree on Γ_obs and on the reason for every excluded element in every case.
- [ ] The four special rows hold (complex-type constituents for the handed hexapod; D₄ with module symmetries for the swerve base; trivial group for the off-centre manipulator; nested three-fold groups in the tri-wheel clusters).
- [ ] Every negative control is caught; the gate row is written with measured values by a session that did not implement the work.
- [ ] If the gate fails, the status is `fail` and nothing downstream (weight tying, orbit deduplication, gait enumeration) may cite a group for the failing archetype until it is repaired.

## Test plan
### Unit tests
Schema and self-consistency tests of the 18 archetype oracle files and the 24 case files (stated order equals the closure of the stated generators, by the independent closure routine of N13-21's test). `planted_cases_agree_with_zoo_variants`: the gate has one set of 24 planted cases, held twice by hand (the case files here, and the zoo variants `zoo/<archetype>.variants/asym-<kind>.fbot` with their expectation files, `<kind>` being `sensor`, `payload`, `sole` or `gear`, stored by BD-246); the test asserts that the 24 (archetype, kind) pairs are the same on both sides, that each case's typed edit applied to the archetype's default instance yields the variant's `DesignId`, and that the groups after the edit and the breaker field are equal; a planted disagreement in one variant's `[symmetry]` block is reported with the case named.
### End-to-end script and logging
`scripts/e2e/analyze_symmetry.sh --milestone m3`, sourcing the `STD-E2E` helper; NDJSON at `target/e2e-logs/analyze_symmetry/<utc>.ndjson` with a transcript. `cmd` lines with exact command, exit code, wall time; envelope evidence blocks (class, tier `static`, determinism `exact`, design, model and task identities); one `assert` line per archetype, per sensor-fitted case and per planted case with expected and found groups, orders and breaker field paths; on failure the first differing element and the saved envelope and oracle paths; `assert` lines for each negative control; `metric` lines (cases, disagreements against threshold 0); the final `summary` with counts and the gate touched. Idempotent, exact, non-zero exit on failure.
### Known answers and negative controls
KA-259 (the gate), KA-270 (Γ_mech as built for the eighteen), KA-230. Controls: step 6; the 24 planted asymmetries are the gate's own negative controls: each must change the group and name its breaker. Metamorphic: applying an element of Γ_mech to the whole design permutes the report and changes nothing else; a mirrored robot on a mirrored course returns the mirrored result (exercised by the arena's tests with the groups computed here). Determinism: exact; identical envelopes on both machines.

## Considerations
- Where the archetype table lists alternatives (`octopod` radial or spider; `hexapod-radial` handed or not; C₃ or D₃ clusters), each shipped variant has its own oracle file; an archetype is counted as agreeing only if every shipped variant agrees.
- If an archetype's shipped design differs from the table (for example an asymmetric cable route), the oracle is not edited to match the candidate: the difference is a finding against the archetype or an amendment to the table, decided by the Skeleton lead.
- This gate is cited by the bet on Γ_obs equivariance together with the block gate (GATE-MARROW-04) and the learning experiment; it says the groups are right, not that using them pays.
