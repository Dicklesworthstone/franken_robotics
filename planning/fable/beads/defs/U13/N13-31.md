## Background
A guarded predicate falls back, when its single-precision residual is inside the certified error bound, to an exact evaluation of the predicate polynomial on the stored inputs. Every finite single-precision number is an integer of at most 24 bits times a power of two, so the polynomial is an integer computation. The design carries it out in 32-bit limbs with widening multiplies, which exist identically on the CPU, on CUDA and on Metal, with a bit budget capped at 256 bits (eight limbs) per predicate.

Open question OPEN-MARROW-3: may that exact fallback use 64-bit integers where a backend offers them? Default: 32-bit limbs everywhere, so the three backends run the same integer program. Owner: Marrow lead. It is to be decided at GATE-MARROW-05 and is listed as blocking that gate, because the gate's record must say which integer program was measured.

Arguments. For 64-bit limbs: half as many limbs and multiplies, so a faster fallback where 64×64→128 multiplication (or a high-half multiply) is native. Against: the property the default protects is that one integer program, one source, runs on every backend, so a digest of intermediate limbs is comparable across backends and one set of tests covers all; with two limb widths there are two programs to derive, emit, certify and test, and "bit-identical exact path across backends" (a trigger of the guard kill gate) has to be re-stated as "identical final results". The result of an exact computation does not depend on limb width, so decisions would still agree if both programs are correct; the risk is an implementation defect in one of them that the other backend's tests cannot see. Relevance of speed: the fallback is meant to be rare (target below 10⁻³ of evaluations), so its cost matters only if the measured rate is high. A reported fact to recheck through the hardware fingerprint: the Metal shading language on the Mac provides no 64-bit atomic add and no 64-bit compare-and-swap; what 64-bit integer multiply support each backend offers is recorded by the fingerprint, not assumed.

## Scope
In: the decision record, the evidence gathered for it, and the binding of the default until it is made.
Out: implementing a second limb width (only if decided; a new bead would carry it).

## Technical approach
1. **Default in force (fail-closed):** 32-bit limbs with widening multiplies on `batch-cpu`, CUDA and Metal; the kernel generator has one limb width and refuses a manifest that asks for another.
2. **Evidence to gather before GATE-MARROW-05 is recorded:**
   a. From the hardware fingerprint of both machines: which 64-bit integer operations each backend's dialect compiles (add, multiply, high-half multiply), per device.
   b. From the exact-integer probe (the docking-boundary screen) and a micro-benchmark of forced fallbacks: the time per exact fallback with 32-bit limbs for budgets of 91, 131 and 179 bits (three, five and six limbs) on each backend.
   c. Two planning rates, because the battery rate is measured only afterwards by the gate itself: the target, 10⁻³ of evaluations, and the kill threshold, 10⁻², which is the largest rate at which guarded predicates stay on the GPU at all. The share of step time spent in fallbacks is rate × cost per fallback ÷ step time per world; compute it at both rates.
   d. A ceiling, computed before any speed test: if fallbacks are a fraction f of step time, 64-bit limbs can save at most about f/2 of step time (half the limb operations, the same control flow). The record states the computed number at both planning rates.
3. **Decision rule (proposed; the Marrow lead decides):** keep 32-bit limbs unless (i) the computed share of step time spent in fallbacks at the kill-threshold rate exceeds 2% on some backend, and (ii) that backend compiles the needed 64-bit operations, and (iii) a dual-width conformance run shows identical final results on 10⁹ adversarial inputs. If all three hold, 64-bit limbs may be admitted for that backend as a second certified program, with its own manifest field, tests and negative controls; otherwise the default stands.
4. **Record:** an ADR in `docs/adr/` with the evidence (a) to (d), the decision and the date; the open-question row marked decided; the GATE-MARROW-05 record cites it. Ordering: the decision is taken before the gate's measurement (BD-182 depends on this bead), so the gate measures the decided program; when the gate has measured the real battery rate the ADR is annotated with it, and if that rate contradicts the decision's premise the question is reopened by a dated amendment.
5. **If 64-bit limbs are admitted:** the trigger wording of the guard kill gate ("the exact path cannot be made bit-identical across backends") is amended, by a dated amendment made before the measurement it governs, to refer to final exact results; BD-182's cross-backend limb comparison is replaced by a final-result comparison for that backend.

## Acceptance criteria
- [ ] Until the ADR exists, the generator emits only 32-bit-limb fallbacks, and a test asserts it.
- [ ] The ADR records the fingerprint facts, the measured cost per fallback per budget and backend, the computed share of step time and ceiling of the saving at the target and kill-threshold rates, and the decision; after GATE-MARROW-05 it is annotated with the measured battery rate.
- [ ] The GATE-MARROW-05 record names the limb width measured and cites the ADR.
- [ ] If the decision admits 64-bit limbs anywhere: a dual-width conformance run with zero disagreements exists, and the kill-gate wording was amended before its measurement.

## Test plan
### Unit tests
- `fallback_limb_width_is_32`: the emitted fallback for each registered guarded predicate uses 32-bit limbs and widening multiplies only (dialect source scan), on every backend.
- `manifest_rejects_other_limb_width`: a manifest requesting 64-bit limbs is refused by the generator under the default.
- `limb_count_matches_budget`: budgets of 91, 131, 179 and 256 bits give 3, 5, 6 and 8 limbs.
### End-to-end script and logging
`scripts/e2e/marrow_predicates.sh --open-marrow-3`: reads `frob spark fingerprint --json` for the integer capabilities, times the exact fallback per budget on each backend present (10⁶ forced fallbacks each, median and spread), and prints the share of step time and the ceiling at the two planning rates. `STD-E2E` NDJSON at `target/e2e-logs/marrow_predicates/<utc>.ndjson`: `metric` lines for cost per fallback (ns, per backend and budget), fallback rate, share of step time, ceiling of saving; an `assert` line that the ADR exists when the gate is being recorded; summary naming OPEN-MARROW-3.
### Known answers and negative controls
Known answer: the limb counts above; the exact value 13,421,773·2⁻⁵⁰ of the 0.3, 0.4, 0.5 fixture is the same under any limb width. Negative control: a 64-bit variant with a carry dropped between limbs must disagree with the 32-bit program on the adversarial set (this is the defect class the single-program default protects against; the control exists only if a dual-width run is made).

## Considerations
- The question blocks only the wording of the gate record; all implementation proceeds under the default.
- The honest expectation, stated before measurement: the default stands, because the fallback is rare by design and the ceiling of the saving is small.
- If the guard kill gate fires (fallback rate above 10⁻² on a GPU backend), exact evaluation leaves the GPU tiers altogether and this question becomes moot there.
