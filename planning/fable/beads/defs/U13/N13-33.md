## Background
This bead exists only on one branch of a kill-gate decision. If KILL-MARROW-GUARD fires at M2 (the fallback rate of guarded predicates exceeds 10⁻² on the contact battery on either GPU backend, or the exact path cannot be made bit-identical across backends; decided in N13-32), the fallback named in advance is adopted: strict predicates are evaluated exactly only on the strict `batch-cpu` profile and the referee; GPU tiers mark worlds that came within E of a boundary and the sampled referee re-runs them. If the gate does not fire, this bead is closed as not needed, citing the decision's ADR, and nothing here is built.

The reasoning behind the fallback: a strict inequality that decides a discrete outcome must be decided exactly somewhere, or two tiers diverge permanently on a boundary case. If exact evaluation inside GPU kernels is too frequent or cannot be made identical across backends, the GPU tiers stop claiming exact decisions. They decide in plain single precision, they say when a decision was within the certified error bound E of its boundary, and the tiers that do decide exactly (the referee; the transactional, event-located `strict` profile of `batch-cpu`, in double precision) re-run those cases. Trust then comes from the marked share and the agreement rate, both on every receipt, instead of from exactness on the device. Tier: Solid (a fallback is part of the plan).

## Scope
In: the marking form of guarded predicates in device kernels; the per-world mark and its counters; routing of marked world-steps to the background referee; labelling of results; the changes to determinism class reporting; tests.
Out: the decision (N13-32); the background referee itself (BD-214: address-hashed sampling, snapshots, one-step defects, the coverage figure on every receipt); the strict profile (BD-161); the decision-level equivalence test (BD-177).

## Technical approach
1. **Marking kernels.** For every predicate of class `Guarded` in a device kernel, the generator emits the marking form instead of the fallback form: compute p̂ and E = c·u·S exactly as before (same derivation, same constant c from the manifest); decide by the sign of p̂; if |p̂| ≤ E, set bit f of the world's `near_boundary` word, where f is the predicate family (limit, gap, cone, sort, admission). No integer fallback is emitted on GPU backends. The turn-counter branch reads only sign bits of stored numbers, has E = 0, and is never marked. `batch-cpu` keeps the full guarded form (its `strict` profile is one of the exact tiers).
2. **State.** `near_boundary: u32` per world per step, plus cumulative per-family counters in the statistics ring (class `stat`, never feeding state). The mark is cleared at the commit fence and exported with the step's snapshot metadata.
3. **Routing.** The background referee's selection becomes the union of its address-hashed sample and every marked world-step. For a marked step it restores the fence snapshot before the step, runs the step on the referee (or on `strict` when the referee is not available for the model class) and records, per marked family, whether the exact decision equals the GPU decision. The compute this adds is bounded by the marked share; if marked world-steps exceed a declared budget fraction (DESIGN default 5% of world-steps), the referee re-runs an address-hashed subsample of the marked set and reports the sampled fraction, never silently dropping.
4. **Labels and classes.** A GPU result whose episode contains a marked step whose exact decision differed is labelled `boundary-sensitive` and its determinism class for decisions is the weakest input (not D0). Requirement verdicts at a boundary, digests used as identities and anything a certificate cites are taken from the exact tiers for marked episodes; a verb that needs class D0 decisions and is offered an unconfirmed marked GPU result refuses with the existing refusal for an unattainable determinism class on the requested placement.
5. **Receipts.** Every run receipt carries: marked world-steps ÷ world-steps per family; re-run share; agreement rate of exact and GPU decisions on re-run steps; the number of episodes labelled `boundary-sensitive`.
6. **Manifest and registry.** The predicate class recorded in the device kernel manifest becomes `Marked` (a documented sub-state of `Guarded` under the fallback) so that the select lint, which rejects `Plain` predicates on selects whose arms differ at the boundary, still passes only for predicates that either fall back or mark.
7. **Gate rows.** GATE-MARROW-05's device rows take status `killed` with `detail = "KILL-MARROW-GUARD: <fallback>"` through N40-03's propagation of N13-32's `fired` decision (this bead writes no gate row); a new measured quantity replaces them: on the adversarial input set, every case in which the plain sign is wrong is marked (zero unmarked sign errors). That is the property the fallback must keep: a wrong decision is never silent. It is measured by the tier run `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers --features gauntlet-mutations -- KA-260` on a marking build (KA-260's adversarial set, controls (i) to (iii) in the same run), whose receipt the ADR's annotation cites; it enters the gate register only by a dated amendment of the GATE-MARROW-05 device rows made before that run (N40-03's amendment record), and is then recorded from the receipt with `cargo run -p frob-conformance --example record_gate -- --gate GATE-MARROW-05 --receipt <hash>` by the gate's one recorder (N38b-19); the script writes no gate row.

## Acceptance criteria
- [ ] Zero unmarked sign errors on 10⁹ adversarial inputs per GPU backend: whenever the plain single-precision decision differs from the exact one, the mark is set (this is the validity of E, proof obligation PO-MARROW-06, which the fallback still relies on).
- [ ] On the contact battery every marked world-step is either re-run on an exact tier or counted in a reported sampled fraction; none is dropped silently.
- [ ] A marked step whose exact decision differs labels the episode `boundary-sensitive`; a D0-requiring verb refuses an unconfirmed marked result.
- [ ] Receipts carry the four quantities of item 5; the statistics counters do not change state digests.
- [ ] No device kernel contains the multi-limb fallback; `batch-cpu` still contains it; the select lint passes.
- [ ] Negative controls caught: (i) a marking kernel with c divided by ten leaves wrong decisions unmarked on the adversarial set; (ii) a router that ignores the mark leaves marked steps without a re-run and fails the accounting assertion; (iii) a label path that never sets `boundary-sensitive` fails on a planted boundary case (the 0.3, 0.4, 0.5 cone point placed in a contact).
- [ ] If the gate did not fire: the bead is closed with the typed reason "not needed: KILL-MARROW-GUARD not fired", citing the ADR.

## Test plan
### Unit tests
- `marking_covers_all_wrong_signs`: adversarial inputs on `batch-cpu` emulating the device float path; every wrong plain decision has its mark.
- `turn_branch_never_marked`.
- `mark_cleared_at_fence_and_exported`.
- `router_union_of_sample_and_marked`: with 1,000 worlds, 37 marked, sample rate 1%: the selection contains all 37 and the hashed sample.
- `budget_fraction_subsamples_and_reports`: with 20% marked and a 5% budget the reported sampled fraction is 0.25 and the selection is address-hashed.
- `boundary_sensitive_label_and_refusal`.
### End-to-end script and logging
`scripts/e2e/marrow_guard_fallback.sh`: runs the adversarial set on each GPU backend in marking mode (the tier run of item 7, once per backend present, receipt hash logged); runs the contact battery as BD-182 runs it, `frob contact audit --battery standard --tier <gpu-cuda|gpu-metal> --profile lockstep --key mgf-battery-<tier>-<run-id> --json` (a `run` verb: each run has its own idempotency key, `FROB-REF-805` without one, and every envelope must show `idempotent_replay: false`), with the background referee enabled for that job (`frob fidelity shadow start --job <id> --p <p> --cpu-cores <n> --tier referee --json`, BD-214's verb), then `frob fidelity shadow status --job <id> --json`, `frob fidelity ledger --json` and the run receipts. `STD-E2E` NDJSON at `target/e2e-logs/marrow_guard_fallback/<utc>.ndjson` with a transcript: `metric` lines for unmarked sign errors (threshold 0), marked share per family, re-run share, agreement rate, `boundary-sensitive` episodes; `refusal` lines for the D0-requiring verb; the envelope evidence blocks showing the determinism class of marked results; on failure the first unmarked wrong decision as hex inputs with p̂, E and the exact value; summary naming KILL-MARROW-GUARD (fallback adopted).
### Known answers and negative controls
KA-236 (the 0.3, 0.4, 0.5 point must be marked: p̂ = 0 ≤ E); KA-260's adversarial set re-used. Controls (i) to (iii). Determinism lanes: marks are identical twice on one device family; marks may differ between device families where the float paths differ, and the report says so.

## Considerations
- The fallback keeps the certified error bound and gives up the device-side exact arithmetic; it therefore still depends on BD-053's derivation.
- The marked share is itself the quantity that fired the gate (above 1% of evaluations), so the re-run cost is material; the budget fraction and the sampled-fraction report keep it bounded and honest.
- What the project can still claim on GPU tiers after the fallback: bitwise repeatability per backend and independence from batch composition; not exact decisions at boundaries.
