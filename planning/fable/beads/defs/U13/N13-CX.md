## Background
A plausible shortcut ships with the smallest hand-checkable case that breaks it, and the case becomes a permanent negative control: a planted defect that a gate must catch. The negative-control registry (`frob-conformance/registry/controls.toml`) is seeded from the counterexample catalogue: each entry becomes at least one control, attached to the gates of the rule it protects. A gate with no control in the registry cannot record a pass, a control is run every time its gate is run, and a gate run in which a control was not caught is a failure whatever the passing test says.

This bead is the catalogue for the algebraic core: the nine entries CX-116 to CX-124, plus the counterexample of the periodic-and-lifted rule, which was stated with its subsection and has no number yet. Tier of the content: Solid.

## Scope
In: the nine entries CX-116 to CX-124 and the late turn-count entry in the counterexample catalogue `frob-conformance/registry/counterexamples.toml`, with the substance each needs to become a control (rule identifiers, kind of control, one planted-defect identifier, the expected observation); the request for the late entry's number; a host test that recomputes every number in the table.
Out, with the bead that has it: the catalogue's record schema and loader, and the seeding tool that turns entries into rows of `registry/controls.toml`, allocates their `NC-` identifiers, keeps the seed map, resolves rules that name no gate and proves completeness by the join (N38b-05); this bead writes no row of `controls.toml` by hand. Running controls and writing `last_seen` (N38b-04). The number blocks for entries appended after plan time (N38a-40). The tests that the controls make fail (owners listed); the mutation matrix (N13-18), whose eight mutations several of these entries plant.

## Technical approach
**Catalogue record.** Each row below is one entry of `registry/counterexamples.toml` in the record schema of N38b-05: `id` (the CX number, append-only), `shortcut`, `case`, `numeric` (true for all ten), `plan_case` (`"numbers"` for all ten: none is among the catalogue's seventeen word-only entries), `case_supplied_by` (empty), `rule`, `rule_ids` (the gates, ADRs, obligations and refusal codes of the rule and gates columns), `defined_in` (§13.3 to §13.7, §13.11), `same_as` (empty), `label` (DESIGN), `control_kind` (`mutation`, `planted-input`, `planted-design` or `planted-world`), `plant` (for a mutation, the build or plan flag that plants the shortcut in the real component, never a mock; otherwise the fixture, design or world; written `<planting bead>:<name>` as the schema requires: `N13-18:M1` for a switch of N13-18's operations table, otherwise `<first owner named in the entry's item below>:cx-<nnn>`, the Cargo feature or fixture under which that bead builds the plant, and `N13-35:turn-count-is-state` for the late entry) and, for the late entry, `slug`. The expected observation of the control column is kept in the entry's `case` text so that the seeding tool copies it into the control's `expect`. The seeding tool writes one control per entry (the record `id`, `seed`, `gate`, `kind`, `target`, `defect`, `expect`, `last_seen` of BD-025). DESIGN, correcting an earlier draft of this bead that wrote control records directly: `controls.toml` is written only by the tool, so control identifiers are allocated once and never rewritten.

## Test plan
### Unit tests
`cx_registry_marrow_complete` (the chapter's slice of the join: ten entries, every field, one control each after seeding); `cx_entries_have_kind_and_plant` (every `mutation` has a non-empty plant naming its planting bead; CX-116 names `N13-18:M1`; CX-117 names `BD-047:cx-117`, not `M3`; CX-124's plant is not `M4`); `cx_marrow_numbers`; `cx_controls_fire` (through the runner of N38b-04: each control, when active, makes its named test fail by a value assertion with the observation in the table; listed pending for owners not yet closed); `cx_blind_fixture_documented` (CX-116's energy check stays green under the mutation, and the entry says so); `cx_late_slug_mapped` (in milestone-exit mode, fails if the slug is still cited).
### End-to-end script and logging
Each gate script named above runs its controls and logs, per `STD-E2E`, one `assert` line per control (id, seed, gate, caught, observed, expected). This bead's own script, `scripts/e2e/registry_n13_cx.sh` (sources the STD-E2E helper; idempotent; it calls only cargo targets of its dependencies, so no `frob` command), runs the unit tests above (`FROB_TEST_SEED=0 cargo test -p frob-conformance --test g0_laws -- cx_registry_marrow cx_entries_have_kind cx_marrow cx_controls_fire cx_blind cx_late`); N38b-05's seeding tool, `cargo test -p frob-conformance --test seed_controls -- --ignored seed`, twice, asserting that the second run leaves the digest of the committed `controls.toml` unchanged; the join, `cargo test -p frob-conformance --test seed_join`; logs per entry the id or slug, the NC allocated, kind, plant and gates; then reads the control runner's history `registry/control_history.ndjson` (N38b-04) and reports per control the last run in which it was caught. NDJSON at `target/e2e-logs/registry_n13_cx/<utc>.ndjson` with a transcript: each line has `ts`, `script`, `bead` (`N13-CX`), `step`, `event`, the command line, exit code and wall time; `metric` lines for the counts (entries against 9 plus 1 appended, controls against 10); the digest of `controls.toml` before and after the second seeding; on failure the first missing entry or unresolved gate with the registry path; a `summary` of controls caught, not caught, never run and pending.
### Known answers and negative controls

## Considerations
- A control that has never failed its gate in any recorded run is itself suspect and is reviewed at each milestone exit: either the defect cannot be planted as described or the gate is not looking.
- CX-119 and CX-120 are controls on reports and uses, not on arithmetic; their tests assert what the tool says and which group it lets a caller use.
- A false result found in use that traces to one of these rules becomes a permanent control with the case that exposed it.
