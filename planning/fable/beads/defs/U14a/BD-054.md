## Background

Skeleton is the subsystem that owns what a robot is before anything moves. It has three crates at layer 2:
`frob-design` (the design term, its two views, modules, typed edits), `frob-model` (the compiler from a design
to an immutable `RobotModel`) and `frob-io` (import and export with loss reports). This bead is the first of
`frob-design`: the term itself, its one canonical byte form, and its identity.

ADR-SKEL-01 (DESIGN): a design is a term, and a file is a view of the term. The canonical form is JSON with
schema name `frob.design/1` and extension `.fbot`; `DesignId` is the BLAKE3 hash of the canonical bytes.
Reason: constructors (`mirror`, `radial`, …), typed edits, lineage and incremental compilation all need a tree
with stable subterms, and a hash needs one byte representation. A design is not a file of numbers: its leaves
are components (`Body`, `Joint`, `Actuator`, `Transmission`, `Battery`, `Sensor`, `Wheel`, `Track`, `Foot`,
`Payload`) and its internal nodes are constructors (`attach`, `serial`, `mirror`, `radial`, `scale`,
`replace`, `closure`, `use`). Two nested `mirror` constructors make the symmetry C₂ × C₂ a property of the
term, not something to rediscover from expanded numbers.

Rejected alternatives, each with the case that breaks it:

- Hash the file as written: `{"b":1,"a":2}` and `{"a":2,"b":1}` would be two designs, and every memoized
  analysis of the first would miss on the second.
- Hash the in-memory value (a debug rendering or a struct layout): the hash changes with the compiler, so the
  same design changes identity when the toolchain pin moves and every cached result is orphaned.
- Tolerate unknown fields: a reader that ignores an unknown required field such as a contact-law selector
  simulates a different robot from the one described and reports it under the same identity.
- Serialize through a library map: FACT (read 2026-11-21) the `preserve_order` feature of `serde_json` switches
  maps to insertion order and Cargo unifies features across the build graph, so key order would depend on
  which sibling crate is linked. Canonical bytes are therefore written by this project's own writer.

Terms. Canonical form: the unique byte string for a term. View: any other rendering (the S-expression text of
BD-057); a view is never hashed, signed or cited. Subterm hash: the hash of the canonical bytes of a subtree,
used as the memo key of incremental compilation. Provenance: where a value came from (`designed`, `datasheet`,
`measured`, `assumed`, or `default` for a written-out schema default).

## Scope

## Technical approach

Layout (DESIGN): `crates/frob-design/src/{term.rs, path.rs, schema.rs, read.rs, canon.rs, id.rs}`.

```rust
// DESIGN sketch: intent, not signatures.
pub enum Term { Obj(Vec<(Key, Term)>),            // kept sorted by code point of Key
                Arr(Vec<Term>), Str(String), Ident(Ident), Qty(Annotated), Int(i64), Bool(bool),
                Hash(Blake3) }
pub struct Path(Vec<Seg>);                        // "/limbs/of/of/chain/1/body/region/capsule/1"
pub struct Design { term: Term, id: DesignId }    // immutable; an edit returns a new Design
pub struct DesignId(Blake3);                      // printed "b3:<64 hex>"; handle form "design:b3:…"
```

Document shape. Top-level keys, all others refused: `schema` (required, `frob.design/1`), `name` (required),
`meta` (author, licence, source), `root` (the root body), `limbs` (constructor terms), `power_bus`,
`sensors`, `payloads`, `budgets`, `levers`, `locks`, `symmetry`, `reduced`, `init` (named initial conditions,
N14a-03). `name`, `meta` and `init` are read by no mechanical compile product. The optional block `travel` joins
the list at M3 (N14ax-01, a minor version: its absence keeps every existing identity).

The seven rules that make the bytes unique:

1. UTF-8; object keys sorted by code point; no insignificant white space; a duplicate key refuses.
2. A quantity is a string of an exact decimal and a unit token, or an object with that string and its
   provenance, uncertainty and source; a bare string means provenance `designed` (N14a-01).
3. The canonical unit is the coherent SI unit and the canonical decimal is the shortest that equals the exact
   rational; a value with no terminating decimal is a ratio (N14a-01).
4. Degrees and turns become an exact rational of a turn; radians keep their decimal (N14a-01).
5. Integers above 2⁵³, content hashes and rationals travel as strings.
6. Every field the compiler will read is present. Schema defaults for non-physics fields are written out with
   provenance `default`, so a later schema version cannot change the meaning of an existing design. Physics
   fields (fill, material, contact law, joint limits, an actuator's current convention) have no default: a
   document that omits one has no canonical form and refuses with that field's own code.
7. Constructor terms stay unexpanded. The expanded tree is a compile product, never stored.

Canonicalization, as numbered steps:

1. Validate the raw bytes with the shared reader before any map is built: valid UTF-8, no byte-order mark,
   member names compared after escape decoding at every nesting level. A repeated name refuses
   (`FROB-REF-103`). Smallest case: `{"wheel_radius_mm": 60, "wheel_radius_mm": 75}`; a reader that keeps the
   first value simulates a 60 mm wheel, one that keeps the last simulates 75 mm, and both hash the same bytes.
2. Parse into an untyped tree in which every number is still text.
3. Type the tree against the schema, top down. A member the schema does not list refuses (`FROB-REF-103`) with
   the nearest listed name as the first repair. An unknown major version of `schema` refuses
   (`FROB-REF-125`) and names the migration. `null` is not a legal value anywhere.
4. Canonicalize each atom (rules 2 to 5).
5. Write out the non-physics defaults (rule 6). The three the format names: a joint's `origin` (identity),
   a body's `collision` (the mass Region, written as the token `"region"`), a bus's `members` (every actuator,
   written as the selector `"*"`). Each block's bead lists its own. Spellings of written-out defaults are
   DESIGN proposals confined to that content.
6. Emit bytes with the explicit-sort writer: keys in code-point order, no white space between tokens, strings
   escaped by the shared writer's single rule. No canonical byte is produced by serializing a library map or
   a library number.
7. `DesignId` = BLAKE3 of those bytes under the domain string `frob.design/1` (the registry's identity rule),
   through `frob_core`'s identity function. Subterm hash = the same function over a subterm's canonical bytes.

Refusals (exit code 3; each carries `pointer`, `observed`, `required` and ranked repairs as typed edits):

| Code | Meaning | Trigger here | Ranked repairs |
|---|---|---|---|
| `FROB-REF-103` | Unknown, misspelt or duplicate field | A member not in the schema; a repeated member name after escape decoding | 1. `rename` to the nearest listed field (edit distance ≤ 2); 2. remove the member; 3. the list of fields legal at that path |
| `FROB-REF-125` | Unsupported schema version | `schema` names an unknown major version | 1. `migrate` to `frob.design/1` (N14a-18); 2. the versions this build reads |

Determinism class D0: canonical bytes are a pure function of the term. Evidence: an identity names bytes and
carries no verdict. Ledger: nothing is recorded here; storage of versions is the lineage graph's.

## Acceptance criteria

- [ ] Seed condition: canonicalization is idempotent (canon(canon(x)) = canon(x)) on 10⁴ random schema-valid
      documents and on the worked designs `quad-a` and `quad-tray`.
- [ ] Seed condition: the `DesignId` of each golden design is equal on Linux and macOS and equal to the value
      pinned by the independent reference canonicalizer in `tools/oracle/` (the corpus of N14a-26).
- [ ] Seed condition: a duplicate key refuses with `FROB-REF-103`, at nesting depths 1 to 8, also when the
      two names differ only by escapes (`"a"` and `"\u0061"`, which decode to the same name).
- [ ] `{"b":1,"a":2}`-style reorderings and white-space changes of a design leave `DesignId` unchanged; any
      single-byte change of a canonical file either fails to parse or changes `DesignId` (10⁴ mutations).
- [ ] An unknown top-level or nested member refuses with `FROB-REF-103` and offers the nearest field name.
- [ ] `crates/frob-design/CONTRACT.md` has the ten sections (purpose, inputs, outputs, invariants, refusals,
      determinism class, evidence class of outputs, validity domain, oracles, known gaps) and states class D0.
- [ ] The canonical writer has no call path through a library map serializer (checked by a build with a dummy
      dependency enabling `preserve_order`: bytes and digests unchanged).
- [ ] The public API `Design::from_bytes` → `canonical_bytes()` → `id()` is exercised by
      `crates/frob-design/tests/conformance.rs` on the golden corpus; reachability through
      `frob design show <file> --json` (envelope field `bound.design`) is asserted by N14a-21, which depends on
      this bead, and not here.

## Test plan

### Unit tests

`cargo test -p frob-design -- term canon id` (several filters go after `--`).

- `canon_idempotent_golden`: `quad-a.fbot` and `quad-tray.fbot`; canon twice gives identical bytes.
- `canon_key_order_and_whitespace`: 100 shuffles and re-indentations of `quad-a`; one `DesignId`.
- `duplicate_key_refuses`: the wheel-radius case; expected `FROB-REF-103`, pointer `/wheel_radius_mm`.
- `escaped_duplicate_refuses`: depth-8 nesting with members `"a"` and `"\u0061"`; expected `FROB-REF-103`
  with the pointer of the second member (planted: a reader comparing raw, undecoded names lets it through).
- `unknown_field_suggests_nearest`: `"fil": "solid"` on a body; first repair is `rename` to `fill`.
- `unknown_major_version`: `"schema": "frob.design/9"`; expected `FROB-REF-125`.
- `null_is_refused`: `"material": null`; expected a refusal, never a default.
- `subterm_hash_stable_under_sibling_edit`: editing the bus leaves the hash of the `limbs` subterm unchanged.
- `prop_canon_idempotent` (10⁴ cases): a `synthetic` generator of schema-valid documents.
- `prop_single_byte_mutation` (10⁴ cases): parse failure or a different `DesignId`, never the same identity.

### End-to-end script and logging

Covered by `scripts/e2e/skel_author_compile.sh` (N14a-27): `frob design show` on one design in three
key orders and unit spellings asserts one `DesignId`; a planted duplicate key asserts exit code 3 and
`FROB-REF-103`. Logged per step in NDJSON: command line, exit code, wall time, the envelope's `evidence` block,
the digest of the input bytes, the `DesignId`, and on failure the first differing canonical byte offset.

### Known answers and negative controls

- KA-288 (shared with BD-057): canonicalization is idempotent on 10⁴ random designs and the archetypes.
- Known answer of the format registry: `{"b":1,"a":2}` and `{"a":2,"b":1}` have one identity.
- Negative control 1 (planted): a reader built with key-order canonicalization disabled; the reorder test fails.
- Negative control 2 (planted): a writer that serializes a library map; under `preserve_order` its digest
  changes and the four-way feature build catches it.
- Negative control 3 (planted): a reader that keeps the last of two duplicate members; the duplicate test fails.
- Determinism lanes: twice on one machine; debug and release; Linux and macOS: identical bytes (class D0).

## Considerations

- A canonicalization bug is the most expensive defect in the subsystem: it orphans or, worse, merges cached
  results. The reference canonicalizer in `tools/oracle/` is written independently and shares no code.
- The schema is data (`schemas/frob.design-1.json`, generated from the format registry), so that the CLI, the
  MCP tool definitions and the documentation cannot drift from the reader.
- A design above 16 MiB of canonical bytes, or nested deeper than 64 levels, refuses (TARGET limits; importer
  safety). Meshes are never embedded: they are blobs referenced by content hash.
- KILL-SKEL-SEXPR (decided in N14a-20) does not touch this bead: JSON stays canonical on both branches.
- What would make us revisit: a second consumer that needs a binary canonical form. It would be a view.
