## Background

A design is a term whose canonical form is JSON (`frob.design/1`); its identity `DesignId` is the hash of the
canonical JSON bytes (BD-054). ADR-SKEL-02 (DESIGN) adds a second way to read and write the same term: two
lossless views, one identity. The same term can be read and written as an S-expression. The two views are in
bijection on canonical forms and yield the same `DesignId`. The S-expression view is optional for every
consumer. This decision closed the open question OPEN-SKEL-1 (a text syntax for designs); that identifier is
retired and is never reused.

Reason: agents edit nested terms more reliably in a syntax with one bracket kind and quantity atoms
(`0.42m`), while tools and wire formats want JSON. A design term is deeply nested (two `mirror` constructors
around an `attach` around a `chain`), and in JSON an agent must balance braces, brackets and quotes around
every quantity. FACT: FrankenSim's `fs-ir` already keeps canonical S-expressions and a lossless JSON mapping
in step as a tested property (`frankensim/crates/fs-ir/src/lib.rs`); its reader and quantity atoms are reused
through the airlock if they pass admission (N14a-19). A design is not a FrankenScript program and carries no
verbs: the view is data only.

The risk is the classic one of two syntaxes: they drift, and one design acquires two identities, or two
designs one. The format registry's counterexample states it: the S-expression and the JSON of one design are
different bytes, and a cache keyed on whichever arrived first would hold two entries for one design and two
verdicts that a reader could cite as independent. Hence the rules of this bead: only canonical JSON bytes are
ever hashed; the S-expression is a view; the bijection is an invariant with a gate and a kill gate.
Rejected alternatives: S-expression as the canonical form (wire tools and schema validators want JSON); a
free-form text syntax with its own grammar (a third parser to keep in step).

## Scope

In: the S-expression grammar and its canonical layout; the schema-directed mapping in both directions; the
shape table; the verb `design.view`; the property tests of INV-SKEL-04 and PO-SKEL-01; the JavaScript-client
round trip of wide integers and hashes; the GATE-SKEL-05 measurement at crate level; the measurements that
decide KILL-SKEL-SEXPR.

Out: the canonical JSON form and `DesignId` (BD-054); quantity parsing (N14a-01, reused for the atom's

end-to-end script (N14a-28); the same view for `.fmodule` files, which reuses this code (BD-060).

## Technical approach

Layout (DESIGN): `crates/frob-design/src/sexpr/{lex.rs, read.rs, write.rs, shape.rs}` and the shape table
`schemas/frob.design-1.sexpr.toml`.

Grammar (input):

```
sexpr    := atom | '(' sexpr* ')'
atom     := symbol | keyword | string | number | quantity
keyword  := ':' symbol                 a field name; an underscore in the JSON key is written as a hyphen
string   := '"' … '"'                  with the JSON escapes
quantity := magnitude unit-token       no space: 0.42m  -45deg  22.2V  1.2W/K  4000USD  1/3m
comment  := ';' to end of line         input only; never emitted
```

The mapping is schema-directed: both views parse into the same typed term, and the reader knows the node type
expected at each position, so a list is never guessed to be an array or a form. Rules:

1. Document. `(design <name> :schema <string> <block>…)`. Each top-level member becomes a block form headed by
   its key (`power_bus` → `power-bus`).
2. Objects map to keyword forms. Each node type has a row in the shape table: its head (a fixed symbol, or the
   value of a field such as a joint's `class` or a contact's `law`), its positional fields, and the rest as
   `:key value` pairs. Examples: `{"body": "torso", "region": …}` ↔ `(body torso :region … )`;
   `{"class": "R", "axis": [1,0,0], "limits": […]}` ↔ `(R :axis (1 0 0) :limits (-45deg 45deg))`;
   `{"law": "foot-patch", "interface": …, "torsion_radius": …}` ↔
   `(foot-patch :interface rubber-60a/default :torsion-radius 8mm)`.
3. Tagged objects with one shape key map to a headed list: `{"box": [a, b, c]}` ↔ `(box a b c)`;
   `{"shell": "2.5 mm"}` ↔ `(shell 2.5mm)`; `{"mirror": "xz", "of": X}` ↔ `(mirror xz X)`;
   `{"attach": P, "chain": […]}` ↔ `(attach P (chain …))`; a chain element ↔ `(link :joint … :actuator … :body …)`.
4. An object with no row maps to a bare keyword list: `"sink": {"conductance": "1.2 W/K"}` ↔
   `:sink (:conductance 1.2W/K)`. A map from names to values maps to a list of forms headed by the name:
   `:ports ((hip_mount :xyz (0.19m 0.08m 0m)))`. An array of objects that have an `id` maps to forms headed by
   the id: `(levers (thigh :path "…" :bounds (0.15m 0.30m) :manifold R+))`.
5. Arrays map to lists.
6. Quantities map to atoms. An annotated quantity (provenance, uncertainty, source) maps to
   `(q 0.42m :provenance measured :uncertainty 0.001m :source "…")`.
7. Strings. A field of identifier type prints as a bare symbol (`torso`, `al-6061-t6`, `torso.hip_mount`);
   a field of free-text or path type always prints quoted (`"quad-a"`, `"/limbs/of/of/chain/1/…"`). The choice
   is by field type, never by what the text looks like.
8. Canonical S-expression text: one line, one space between elements, keyword pairs in code-point order of
   their JSON keys, canonical atoms (coherent SI units, turn ratios), no comments. `--pretty` reflows with
   indentation for reading; pretty text is accepted on input and is not canonical.

The shape table is checked by a law test: at every position of the schema, no two node types that are legal
there share a head, and every node type has exactly one row or falls under rule 4.

Identity. `DesignId` is computed only from canonical JSON bytes produced from the term. Text of the
S-expression view is never hashed, signed, cited or used as a cache key; offering it where an identity is
required refuses with `FROB-REF-892`. The memo key of "parse and canonicalize, from either view" is the hash
of the input bytes, and its product is the typed term.

The verb.

| | |
|---|---|
| Name, kind, milestone | `design.view`, `read`, M1; CLI `frob design view <design-or-file> --as sexpr\|json [--pretty] --json` |
| Input | A design by name, `DesignId` or file (either view; detected by the first non-space byte, `{` or `(`); schema `frob.design.view.in/1` |
| Output | `result.text` (the requested view), `result.view`, `result.canonical` (true unless `--pretty`), and `bound.design`; schema `frob.design.view.out/1` |
| Refusals | Those of parsing: `FROB-REF-102`, `-103`, `-125`; `FROB-REF-892` when a view is offered as an identity. Exit code 3 |
| Evidence | Class `Tested`, tier `static`, determinism `exact` (class D0); no claim |

Invariants and proof obligations carried here:

- INV-SKEL-04: the JSON and S-expression views of a design have the same `DesignId`, and converting between
  them is the identity on canonical forms.
- PO-SKEL-01: canonicalization is idempotent and both views parse to the same typed term. Verification: a
  property test over 10⁴ random designs and the eighteen archetypes; hash equality.

The JavaScript-client check. A script under `tools/client-js/` decodes canonical JSON with the language's
built-in parser (numbers become binary64), re-encodes it, and reports every wide integer and every hash
field. The values must equal those of the native decoder. They do because canonical-form rule 5 writes
integers above 2⁵³, hashes and rationals as strings; the check exists to catch a writer that forgets.

## Acceptance criteria

- [ ] GATE-SKEL-05 (TARGET): INV-SKEL-04 and PO-SKEL-01 hold on 10⁴ random designs; a JavaScript client's
      round trip of every wide integer and hash matches the native decoder. The measured counts (designs
      tried, mismatches, fields compared) are recorded with the commit and the seed.
- [ ] json → sexpr → json and sexpr → json → sexpr are the identity on canonical forms for the worked designs
      `quad-a` and `quad-tray`, for every archetype available at the time, and for 10⁴ random designs.
- [ ] The S-expression of the worked example in the format's own text parses to the same `DesignId` as its
      JSON.
- [ ] `frob design view quad-a --as sexpr --json` returns the view and `bound.design`; piping its text back
      through `--as json` returns the canonical JSON bytes.
- [ ] A design whose `name` is `"0.42m"`, `"R+"` or `"(x)"` round-trips (strings are quoted by field type).
- [ ] The shape-table law test passes; a planted ambiguous row fails it.
- [ ] Seed condition: the result that decides KILL-SKEL-SEXPR (INV-SKEL-04 held, or not held after one
      repair cycle) is filed for N14a-20.
- [ ] `CONTRACT.md` of `frob-design` states that the S-expression is a view with no identity.

## Test plan

### Unit tests

`cargo test -p frob-design sexpr`.

- `worked_example_same_design_id`: the JSON and the S-expression of `quad-a`; equal `DesignId`.
- `canonical_layout`: the canonical S-expression of `quad-a` is one line, keyword pairs sorted, units SI
  (`0.0025m` for the 2.5 mm shell, `-1/8turn` for −45°).
- `pretty_is_accepted_not_canonical`: pretty text parses to the same term; `result.canonical` is false.
- `string_fields_always_quoted`: names `"0.42m"`, `"R+"`, `"true"`, `"(x)"`.
- `annotated_quantity_roundtrip`: `(q 0.42m :provenance measured :uncertainty 0.001m)`.
- `comment_dropped_on_input`: a `;` comment changes neither the term nor the identity.
- `shape_table_unambiguous` (law test over the schema).
- `prop_inv_skel_04` (10⁴ cases) and `prop_po_skel_01` (10⁴ cases): as stated above, on `synthetic` random
  designs from the generator.
- `js_client_roundtrip`: a corpus of 10³ designs with integers at 2⁵³ − 1, 2⁵³ and 2⁵³ + 1 and with hashes;
  the script's report equals the native decoder's, field by field. Reported `not run`, never passed, on a
  host without the pinned JavaScript runtime.

### End-to-end script and logging

`scripts/e2e/skel_view_roundtrip.sh` (bead N14a-28) drives `frob design view` in both directions on the
worked designs and on generated ones and records GATE-SKEL-05 from the user's side. It logs, per step, the
command line, exit code, wall time, the envelope's `evidence` block, the digests of input and output text, the
`DesignId` on each side and, on failure, the first differing byte offset and the two file paths.

### Known answers and negative controls

- KA-288: the JSON and S-expression views give the same `DesignId`; conversion is the identity on canonical
  forms; canonicalization is idempotent, on 10⁴ random designs and the eighteen archetypes (exact, hash;
  tier G3, host). The appendix states no negative control; this bead registers the three below.
- Negative control 1 (planted): a writer that prints a free-text string bare when it lexes as a symbol. The
  name `"0.42m"` then reads back as a quantity and the round trip fails.
- Negative control 2 (planted): a writer that emits keyword pairs in insertion order. sexpr → json → sexpr
  differs in bytes.
- Negative control 3 (planted): a JSON writer that emits a wide integer as a number. The JavaScript client
  returns 9,007,199,254,740,992 for 2⁵³ + 1 and the comparison fails.
- Metamorphic: any re-indentation, comment insertion or keyword reordering of an S-expression input leaves
  `DesignId` unchanged.
- Determinism lanes: identical text and identities twice, debug and release, Linux and macOS (class D0).

## Considerations

- ✖ KILL-SKEL-SEXPR. Trigger: INV-SKEL-04 cannot be held after one repair cycle. Fallback: the S-expression
  view is removed and JSON is the only syntax, as OPEN-SKEL-1 originally defaulted. Decided at M1 (N14a-20).
  Downstream change if it fires: `design.view` is withdrawn from the verb registry, the `.fmodule` view goes
  with it, and nothing else changes, because no consumer may depend on the view.
- The mapping rules and the shape table are DESIGN proposals confined to the format's examples and to the
  bijection requirement; the format text gives examples and the invariant, not a grammar.
- If N14a-19 admits `fs-ir`'s reader, the lexer and atom reader come through the airlock and only the
  schema-directed layer is written here; if not, the lexer is a few hundred lines in this crate.
- The reader is a fuzz target (it parses agent-written text): depth limit 64, size limit 16 MiB, no recursion
  on the call stack.
