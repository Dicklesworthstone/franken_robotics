## Background

A design is immutable and content-addressed: its `DesignId` is the hash of its canonical bytes. Changing a
design means creating a new version by a typed edit (BD-058, verb `design.edit` for a single edit). An agent
rarely wants one edit. It wants "lengthen the thigh and thin its wall, but do not touch the power bus, and
only if the knee still passes its thermal check", and it wants that to happen exactly once even if the
connection drops and it retries. A patch is the document that says so: a list of typed edits applied to a
named parent, with constraints and an idempotency key. Tier Solid. Owner crate `frob-design`.

```json
{ "schema": "frob.design.patch/1",
  "parent": "design:b3:9f2c…",
  "idempotency_key": "agent-7/turn-41/a",
  "operations": [
    {"op": "set-param", "path": "/limbs/of/of/chain/1/body/region/capsule/1", "value": "0.24 m"},
    {"op": "set-fill",  "path": "/limbs/of/of/chain/1/body", "value": {"shell": "1.5 mm"}} ],
  "constraints": { "locked": ["power_bus", "payloads", "budgets/envelope_max"],
                   "require": ["A-11", "A-13"] } }
```

DESIGN reasons. The expected parent makes concurrent agents safe: two agents that both read version h₀ cannot
both believe they extended it. The idempotency key makes retries safe: a retry after a lost answer returns
the version already created and never a second one. Atomic application makes partial edits impossible: a
design in which the thigh was lengthened and the wall not yet thinned never exists. Rejected alternatives:
last-writer-wins on a mutable design (silently discards one agent's work); a diff of bytes (loses the edit's
type, and with it preconditions, the symmetry effect and the invalidation scope).

## Scope

per-patch locks; required analyses; the idempotency binding as used by this verb; the result (new version,
diff, symmetry effect, invalidation set, verdict survival lists); the refusals; the crate-level measurement

## Technical approach

Layout (DESIGN): `crates/frob-design/src/patch/{schema.rs, apply.rs, result.rs}`; the verb's executor in
`frob-verbs`.

Patch document fields:

| Field | Required | Meaning |
|---|---|---|
| `schema` | Yes | `frob.design.patch/1` |
| `parent` | Yes | The `DesignId` the caller believes is the head of the design it is patching |
| `idempotency_key` | Yes | A caller-chosen key, unique per intended effect; omitting it refuses (`FROB-REF-805`) |
| `operations` | Yes, non-empty | Typed edits in order: `op` (an edit kind of the catalogue), `path`, and the edit's arguments |
| `constraints.locked` | No | Paths or block names this patch must not write, in addition to the design's own `locks` |
| `constraints.require` | No | Analyses that must run without refusal on the candidate version before it is created |

Execution, as numbered steps:

1. Canonicalize the patch document (the same seven byte rules as a design) and take its digest. Resolve the
   design name to its head.
2. Idempotency, in one ledger transaction: look up (principal, verb, key). Found with the same request
   digest: return the stored answer with `idempotent_replay: true`. Found with a different digest: refuse
   with `FROB-REF-803` (exit 7), showing both resolutions. Not found: insert the binding in this transaction.
   A lookup followed by a separate insert is the defect to avoid: two requests with one key both miss and
   both create a version.
3. Stale parent. If `parent` is not the current head, refuse with `FROB-REF-112` (exit 7) and return the
   current head and the diff between `parent` and it, so the caller can rebase without another call.
4. Locks. Compute the write set of every operation. If it meets the design's `locks` or
   `constraints.locked`, refuse with `FROB-REF-111` naming the operation and the locked entry.
5. Apply the operations in order to an in-memory copy, each through the edit engine with its preconditions.
   A refusal from any operation refuses the patch as a whole with that operation's code and its index.
6. Compile the candidate (stage 1 at least) and run each analysis named in `require`. A refusal from any of
   them refuses the patch as a whole. Nothing has been stored yet.
7. Commit: store the new immutable version, add the lineage edges (one per operation, in order, under one
   patch node), move the head from `parent` to the new `DesignId` by compare-and-swap in the same
   transaction as the idempotency binding's completion. Nothing is modified in place.
8. Build the result.

The result (schema `frob.design.patch.out/1`):

- the new `DesignId` (and `ModelId` when the compile completed);
- a structural and parameter diff against the parent;
- the effect on Γ_mech and Γ_obs: both groups before and after;
- the invalidation set: the derived products, analyses, kernels and verdicts that no longer apply, each with
  the field that invalidated it (from influence records);
- which verdicts survive: a verdict names the fields its evidence read; a verdict whose fields are untouched
  is reported as still applying, with that justification, and every other verdict is listed for
  revalidation;
- `settled_pose: required` for each contact surface class: each design version has its own settled initial
  state, computed by the dynamics subsystem and cached under its `ModelId`, and the new version has none yet.

Rules the verb enforces or states:

- Inertia follows geometry. A patch never edits a derived inertia. It edits the Region, the fill or the
  material, and the inertia is recomputed. A `declared` body is the exception and is edited as data. An
  operation that addresses a derived quantity refuses with `FROB-REF-103` (no such field in the term).
- Rollouts are not reused across a mass or geometry edit. The share of a rollout that could be reused exactly
  was assessed as about a tenth of its compute or less (HYPOTHESIS until this project's own dependency
  profile is measured), so the memo graph stops at analyses, step plans, kernels and scene compiles.
- One settled pose per version. A comparison refuses a pair whose initial states were settled for only one
  of the two designs: a robot that starts with its wheels inside the floor invalidates the pair. A buildable
  design that then stalls is a failed trial, not an invalid one.

| | |
|---|---|
| Name, kind, milestone | `design.patch`, `mutate`, M1; CLI `frob design patch <design> --file <patch.json> --json` (the document may also arrive on standard input, in either view) |
| Refusals | `FROB-REF-112` stale parent (exit 7); `FROB-REF-803` key reuse with different content (exit 7); `FROB-REF-805` missing key; `FROB-REF-111` locked path or lever out of bounds; the code of any refused operation or required analysis (exit 3) |
| Evidence | Class `Tested`, tier `static`, determinism `exact`; `bound.design` for parent and result |

Determinism class D0 for everything but wall-clock fields.

## Acceptance criteria

- [ ] GATE-SKEL-08 (TARGET), seed condition: a stale parent refuses in 100 of 100 trials; a repeated
      idempotency key returns the same `DesignId`; a schema migration leaves forward kinematics and mass
      properties bit-identical and old runs replayable (third clause through N14a-18). The crate's test
      battery records the measured counts.
- [ ] The example patch above applies to the worked design and returns: a new `DesignId`; a diff with two
      entries; both groups unchanged (the edits sit under the two mirrors); an invalidation set containing
      the thigh's inertial product and the whole-robot sums and no sibling kinematic product.
- [ ] A patch with `parent` one version behind refuses with `FROB-REF-112`, exit 7, and its answer contains
      the current head and the diff from `parent` to it.
- [ ] The same key with the same content twice returns one `DesignId` and `idempotent_replay: true` the
      second time; the same key with a changed value refuses with `FROB-REF-803`.
- [ ] A patch whose second operation is refused creates no version and leaves the head unmoved.
- [ ] An operation that writes under `constraints.locked` (`set-bus` with `power_bus` locked) refuses with
      `FROB-REF-111`.
- [ ] With `require: ["A-11"]` and an edit that makes the knee fail its envelope, the patch refuses with the
      analysis's code and creates no version.
- [ ] Two patches racing on one parent: exactly one commits, in 100 of 100 seeded interleavings.
- [ ] Reachable through `frob --json` and, where the registry exposes it, through the MCP surface;
      cancellation between steps 5 and 7 leaves no version.

## Test plan

### Unit tests

`cargo test -p frob-design patch` and `cargo test -p frob-verbs design_patch`.

- `example_patch_applies`: asserts the four parts of the result on `quad-a`.
- `stale_parent_refuses_with_head_and_diff`.
- `idempotent_replay_returns_same_version`; `key_reuse_with_other_content_refuses`.
- `atomic_all_or_nothing`: operation 2 of 3 refused; head unchanged; no lineage node.
- `per_patch_lock_refuses`; `design_lock_refuses`.
- `required_analysis_refusal_refuses_patch`.
- `derived_inertia_is_not_addressable`: an operation with a path into a compile product refuses.
- `verdict_survival_lists`: a verdict whose read set is the lidar mount survives a thigh edit; one that read
  the thigh length is listed for revalidation.
- `race_on_one_parent` (100 seeded interleavings under the simulation runtime): one winner, one
  `FROB-REF-112`.
- `gate_skel_08`: the three clauses with measured counts written to the gate record.

### End-to-end script and logging

`scripts/e2e/skel_patch.sh` (bead N14a-29) drives the verb from the CLI: the example patch, the stale parent
100 times, the key replay, the lock and requirement refusals, and the migration steps. It logs per step the
command line, exit code, wall time, the envelope's `evidence` block, `DesignId` before and after,
`idempotent_replay`, the refusal payload, and on failure the first differing field of the expected result.

### Known answers and negative controls

- KA-292: a stale parent refuses in 100 of 100 trials (`FROB-REF-112`); a repeated idempotency key returns
  the same `DesignId`; migration preserves forward kinematics and mass (exact; tier G4, host). The appendix
  states no negative control; this bead registers the two below.
- Negative control 1 (planted): a key binding done as lookup-then-insert in two statements. Under the race
  test two versions are created for one key.
- Negative control 2 (planted): the head moved without compare-and-swap. Under the race test both patches
  commit and one agent's version is lost.
- Negative control 3 (planted): operations stored one by one. The all-or-nothing test finds a half-patched
  version.
- Metamorphic: a patch of n operations equals n single `design.edit` calls in the same order, by
  `DesignId`; a patch followed by the patch of its inverses returns the parent's `DesignId`.
- Determinism lanes: the same patch on the same parent gives the same `DesignId` on Linux and macOS.

## Considerations

- A patch is the natural unit for agents; `design.edit` stays as the one-edit form and is implemented as a
  patch of length one, so the two cannot drift.
- Required analyses cost time before anything is stored; the static ones named in the example finish within
  the preflight budgets, and a requirement on an expensive analysis is the caller's choice.
- Idempotency keys are scoped to (principal, verb) and retained 24 h for mutate verbs that create no job
  (TARGET).
- A stale-parent refusal is information, not an error: it carries what the caller needs to rebase.
