## Background

Habitat is the subsystem that builds the places robots are tested in. Its interiors come from seven
archetypes (home, apartment, office, warehouse, manufacturing plant, retail store, commercial kitchen), each
a typed grammar that emits a structural proxy: boxes and fixtures with exact functional clearances, doors,
ramps, thresholds, stairs, film patches, glass and mirror regions. A hazard is a feature of a place that
causes a specific robot failure: a 20 mm door bar stalls a small wheel; an oil film makes a slip depend on
dwell time; a glass partition is not seen by optical ranging. Each archetype has a hazard registry,
`registries/hazards/<archetype>.toml`, and the generators draw from it. A row has a name, a dimension range
with units, a distribution, the mechanism that represents it, the failure it provokes, and a provenance
field.

The registries serve four consumers: the interior generators (which draw dimensions from them); task files
(which draw world parameters, for example `(draw film :from registry:hazards/commercial-kitchen:wet-floor
:stream world.film)`); the adversarial search, for which the registries are the vocabulary of legal scene
edits; and battery selection, because the registries supply the rows of the scene-by-failure-mode incidence
table, so that a battery can be asked which hazards it leaves uncovered. Interior generation itself is not
claimed as new; what this adds to a generated interior is the hazard list with dimensions and provenance.

The decision that shapes the bead is ADR-HAB-11: every dimension a generator draws carries provenance, and
its provenance is `assumed` until a cited norm or a measurement is recorded. Reason: realism claims need
sources, and validity does not. **Every dimension in the registries at plan time is `assumed`.** The ranges
are generic values chosen to make scenes valid; no building code, workplace regulation or product standard
has been read for them, and none is cited. A row's provenance changes to `norm: <citation>` or
`measured: <dataset>` only when the source is recorded in the source register; a pack counts the `assumed`
dimensions it used; and a report that claims a scene is representative of real buildings is refused while
that count is non-zero (`FROB-REF-312`). The pre-mortem's version of the risk: interiors were toy boxes and
results did not transfer to real places; its leading indicator is the share of dimensions labelled
`assumed`.

## Technical approach

Layout (DESIGN): `registries/hazards/{home, apartment, office, warehouse, manufacturing-plant, retail-store,
commercial-kitchen}.toml`; code in `crates/frob-scene/src/hazards/{schema.rs, load.rs, draw.rs, claim.rs}`.
The file name is the archetype's registry name, the middle part of a row's address. FACT: the task examples
that already exist address `registry:hazards/commercial-kitchen:wet-floor`, so the kitchen file is
`commercial-kitchen.toml`, and the other two long names follow the same pattern; `kitchen.toml`, `plant.toml`
and `retail.toml` are not registry files and the loader does not look for them.

Two names per archetype (FACT: the plan's worked artifacts fix both for the kitchen, the pack family
`kitchen-commercial/galley` and the registry `commercial-kitchen`; the other rows follow the family names the
grammar beads use). The table is data in `crates/frob-scene/src/hazards/schema.rs` and is the only place the
pairing is written:

| Archetype | Registry name (this verb, a row's address and identifier) | Generator family (`scene.gen --family`) |
|---|---|---|
| Home | `home` | `home` |
| Apartment | `apartment` | `apartment` |
| Office | `office` | `office` |
| Warehouse | `warehouse` | `warehouse` |
| Manufacturing plant | `manufacturing-plant` | `plant` |
| Retail store | `retail-store` | `retail` |
| Commercial kitchen | `commercial-kitchen` | `kitchen-commercial/galley` |

`scene.hazards` takes the registry name. DESIGN, for the user who types the other one: a generator family given
in its place is refused like any value outside the schema (`FROB-REF-802`, exit 3), and the refusal's message
and first repair name the registry name it pairs with ("`plant` is a generator family; its hazard registry is
`manufacturing-plant`"). The verb does not accept both, because a row's address must have one spelling.

Row schema (DESIGN spellings confined to the listed contents; this is the one schema of a hazard row, and the
seven per-archetype beads write their examples in it):

```toml
[[hazard]]
slug = "wet-floor"                         # address: registry:hazards/commercial-kitchen:wet-floor
name = "Wet floor"                         # row identifier: commercial-kitchen.wet-floor
provenance = "assumed"                     # one per row: assumed | norm: <citation> | measured: <dataset>
dimensions = [ { id = "thickness", range = ["0.1 mm", "2 mm"], distribution = "uniform" } ]
represented_by = [ { mechanism = "film-patch", tier = "S", latent = "wetness" } ]
provokes = ["slip", "specular depth artifacts"]
```

Two names for a row. The **address** `registry:hazards/<archetype>:<slug>` is what a task file or a generator
writes to draw from it. The **row identifier** `<archetype>.<slug>` (`home.threshold`,
`commercial-kitchen.wet-floor`) is what is recorded with every draw in a pack's resolved-value table, counted
by the manifest, and listed by a refusal. Both are derived from the file name and `slug`; a row has no
separate `id` field.

`provenance` is a field of the row, not of a dimension: `assumed`, `norm: <citation>` or `measured: <dataset>`.
A row whose `dimensions` list has several entries (the riser and the tread of the stairs; the clear width and
the closer torque of the entry door) has one provenance for all of them, and is promoted only when the recorded
source covers every entry; until then the whole row stays `assumed`, which is the fail-closed reading. DESIGN,
correcting an earlier draft of this bead that put `provenance` on each dimension entry and counted distinct
dimensions: the plan gives a row one provenance field and its consolidated table one provenance cell per row,
and the manifest's counting rule (N19a-05) counts distinct row identifiers, so a per-dimension count would
disagree with the manifest's own recount for every row with two entries. Base load rule: the loader accepts
`norm:` and `measured:` only if the citation or dataset is an entry of the source register
(`registries/sources.toml`, schema `frob.sources/1`, built by NAB-09; N19a-39 tightens this: a read date,
dataset admission, the clause syntax).

A dimension entry has one of two forms (DESIGN; the per-archetype beads use both):

- *drawn*: `{ id, range = [lower, upper], distribution }`. `distribution` has no default and must be written;
  every drawn entry at plan time is `uniform` over its range, itself an assumption. A one-sided statement of the
  table is entered with its implied other bound: "curled edge up to 30 mm" is `["0 mm", "30 mm"]`, "slope up to
  10%" is `["0 %", "10 %"]`, "level offset ±10 mm" is `["-10 mm", "10 mm"]`.
- *fixed*: `{ id, value }`, where `value` is a quantity with its unit (`"5 mm"` for the bar of a floor grate,
  `"1.2 m"` for the length of a pallet, `"5"` for the castors of a chair) or a categorical word for a row whose
  dimension is qualitative (`"full-height"`, `"polished"`, `"mirror-like"`, `"moving"`, `"identical-modules"`).
  A fixed entry is not drawn; a generator that uses it records the value with the row identifier, and the row
  counts as `assumed` when used, exactly like a drawn one.

An entry with both `range` and `value`, with neither, with a `range` and no `distribution`, or with a lower
bound above its upper bound is a load error, as is an unknown field anywhere in a row. Quantities are exact
decimals with units; a quantity whose unit does not parse or does not fit the entry's use is a load error. A
load error stops the loader with the file, the row's slug and the field, and no partial registry is ever
served: `cargo test -p frob-scene hazards` fails on the repository's own files, and a verb that needs a registry
of the project root it was given (`scene.hazards`, `scene.gen` for an interior family, a task check that
resolves a `registry:hazards` source) answers one refusal envelope, exit 3, whose pointer is the file, the slug
and the field, with the repairs "1. correct the row; 2. restore the registry from the repository". The plan
gives this refusal no number. It is the row `hazard-registry-invalid` of the second allocation round N35x-02
(family `3xx`, a scene refusal) in the ledger `registries/refusal_allocations.toml`, whose rule assigns the
number (N35-33; a bead never picks one): the row is assigned at that bead's run, at M0, before this bead.
The loader raises it behind the one named constant `HAZARD_REGISTRY_INVALID`, which carries the assigned number,
with exit 3 and retry `after-change`. Every test and script below asserts on that constant's code, never on a
typed number.

Frontier mechanisms. A mechanism marked tier F is listed beside its Solid alternative where the table gives
one, and the Solid alternative represents the hazard until the Frontier mechanism lands (five rows at plan
time: rug, cord, stretch-wrap debris, forklifts and carts, cold-room strip curtain). Three rows name only a
Frontier mechanism (pets, floor vibration, shoppers). DESIGN, the same in NEG-28 and the per-archetype beads:
such a row loads, is listed by the verb with `solid_alternative = false`, is not drawn, and is recorded by the
generator as `not-represented` in the pack, so that a battery can be asked which hazards it leaves uncovered;
a hazard is never silently dropped. (An earlier draft of this bead required a Solid mechanism of every row,
which the plan-time table does not satisfy.)

The hot-liquid row (row 57 of the table) is a ninth. The table gives it one mechanism, the sloshing payload,
and prints no [F] beside it; but that mechanism (the equivalent mechanical slosh model: a rigid mass plus one
to three sprung masses per horizontal axis) is Frontier in the living-world tiers and first lands at M6, with
the kill gate KILL-SLOSH whose named fallback is rigid ballast with a spill metric computed from payload
acceleration. DESIGN, the same in NEG-28, N19a-37 and N19a-38: the registry enters the row with two mechanisms,
`{ mechanism = "sloshing-payload", tier = "F" }` and `{ mechanism = "rigid-ballast", tier = "S" }`, the ballast
being the Solid alternative that represents the row until the slosh model lands. Reasons: the kitchen task of
the plan's worked artifacts draws `tray-fill` from this row at M3, so the row must be drawable at M3; entering
the slosh model as Solid would name a mechanism that does not exist until M6; and entering it as Frontier
alone would make the row undrawable and contradict that task. So the loader sees nine rows that name a
Frontier mechanism: the eight the table marks [F] and this one; six of them have a Solid alternative and three
do not.

Drawing (as numbered steps): 1. a generator or task asks for `registry:hazards/<archetype>:<slug>` and a
dimension id, written after the address as `#<id>` (`registry:hazards/home:stairs#riser`); for a row with
exactly one drawn entry the id may be left out, which is the form of the plan's task example
(`registry:hazards/commercial-kitchen:wet-floor`); a missing id on a row with several drawn entries, and an id
that names a fixed entry, are refused by the caller's check as an unknown field of the row; 2. the value is
drawn from the entry's distribution by a random stream keyed by the address of the draw and the stream
identifier, never by call order; 3. the draw returns the value, its unit, the row identifier and the row's
provenance; 4. the caller records them (below).

Two callers, two records (DESIGN; the plan says only that a pack counts the `assumed` dimensions it used, and an
earlier draft of this bead asked a pack to count draws that a task makes after the pack is frozen, which an
immutable pack cannot do):

- *A generator, while a pack is built.* The address is (grammar, seed, derivation path, attribute name). The
  scene compiler records the resolved value with the row identifier in the pack's resolved-value table, and
  `provenance.dimensions_assumed` is the number of distinct row identifiers with provenance `assumed` among the
  pack's draws: a row used many times, or through two of its dimension entries, counts once (the rule is the
  provenance block's, N19a-05; this bead supplies what it counts).
- *A task file's `draw` form, when an environment is admitted.* `(draw film :from
  registry:hazards/commercial-kitchen:wet-floor :stream world.film)` names a world parameter that differs per
  world and per episode; it is never part of a pack. This bead registers `registry:hazards` as a source kind of
  the randomization plan (BD-200, which until now resolves card fields only): the plan's compiler resolves the
  address through this bead's loader, takes the entry's range and distribution as the law, draws by the plan's
  own world address and the named stream, and writes the row identifier and its provenance into that draw's
  entry of the resolved list, so that the run's `randomization` block counts the row in its provenance shares
  as `assumed`. A row whose only mechanism is Frontier cannot be drawn by a task either: the plan's check
  refuses the draw with the refusal BD-200 gives a source with no usable law (`randomize-no-interval`, exit 3),
  naming the row.

The exclusion hook (for N19a-38, which adds the generator parameter `hazards.exclude`). The generator-side draw
takes the set of excluded row identifiers of the generation request, empty by default. A draw of an excluded
row returns `Excluded` without touching any stream, the generator leaves the hazard out, and the compiler
records the row as `excluded` in the resolved-value table, never silently. Because streams are addressed, the
draws of every other row are unchanged by an exclusion. An `excluded` row and a `not-represented` row are
records, not draws: neither counts toward `dimensions_assumed`, and the manifest loader's recount (N19a-05)
counts only rows with a drawn or used value. This bead builds the hook and its test with the set
passed directly; parsing the parameter and refusing the exclusion of a row a grammar cannot do without are
N19a-38's.

The realism-claim check. `frob_scene::hazards::claim::realism_claim_admissible(manifests, task_rows) ->
Result`: any verb output that claims a scene is representative of real buildings must pass every cited
`SceneId`'s manifest through it, together with `task_rows`, the hazard row identifiers that the randomization
plans of the cited runs drew with provenance `assumed` (empty for a claim that cites no run). A non-zero
`dimensions_assumed` in any manifest refuses, and so does a non-empty `task_rows`; the refusal lists, per
scene, the identifiers of the assumed rows the pack used and, per run, the assumed rows its task drew. DESIGN:
the second input closes the gap the two records above would otherwise leave: a pack built only from cited rows,
run under a task that draws an assumed film thickness, is not a representative world, and the plan's rule is
about what the claim rests on. This is the only implementation of the check; which outputs count as making the
claim, the wiring of each report verb to this function and the collection of both inputs over a report are
N19a-39's.

| Code | Refusal | Trigger | Ranked repairs | Exit |
|---|---|---|---|---|
| `FROB-REF-312` | A realism claim cites a scene with `assumed` dimensions | A report claims representativeness while a cited pack's `dimensions_assumed` is non-zero, or while the task of a cited run drew an `assumed` hazard row | 1. record a norm or a measurement for each assumed row the pack used or the task drew (the refusal lists them per scene and per run by row identifier); 2. drop the claim | 3 |

`scripts/e2e/scene_hazards.sh` (bead N14a-32, which depends on this bead and owns the script) drives `frob

## Considerations

- OPEN-HAB-1: which published building and workplace norms supply the dimension distributions. Default
  (fail-closed): generic ranges labelled `assumed`, and realism claims refused. Owner: project lead. It
  blocks claims of realism, not validity: scenes built from assumed dimensions are valid scenes.
- Validity and realism are separate. A scene whose door is 0.70 m wide is a valid test of whether a 0.72 m
  robot fits; it is not evidence about real homes.
- The registries are also the vocabulary of legal scene edits for the adversarial search and the rows the
  retrofit catalog addresses; a row removed or renamed is a breaking change for both, so slugs are stable
  identifiers and a retired slug is tombstoned.
- Rows whose dimension is qualitative ("low roughness", "moving") carry an identifier and a categorical
  value; they still count as assumed when used.
- The disturbance-law registry of N24cp3-02 (M2: `registries/disturbances.toml`, schema `frob.disturbance/1`,
  addresses `registry:disturbances/<slug>#<id>`, row identifiers `disturbances.<slug>`) reuses this bead's row
  schema where the fields mean the same, with its own file and its own address. If this bead's loader shares a
  row parser with it at M3, neither the disturbance file, its schema name nor its addresses change, and the hazard
  loader never reads that file (a push belongs to no archetype).
