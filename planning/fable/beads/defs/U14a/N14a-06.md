## Background

A design declares which of its parameters an optimizer may move. Such a parameter is a lever: an entry of the
`levers` block with a path into the term, bounds or a finite list of choices, an optional step, a manifold
kind and an optional prior for search (BD-055 types the block). ADR-SKEL-07 (DESIGN): optimizers move levers
only. Continuous optimization and co-design may change a parameter only if the design declares it as a lever
with bounds and a manifold kind. Agents may make any typed edit. Reason: an optimizer that can touch every
number finds the numbers nobody meant to free: it shortens a link past its bearing, thins a wall to nothing,
or relaxes a joint limit, and reports the gain.

The invariant this bead owns is INV-SKEL-08: an optimizer changes only declared levers, inside their bounds
and on their manifolds. The complementary mechanism is the lock: `locks` lists paths or block names that no
edit may change without an explicit `unlock`; a write to a locked field refuses (`FROB-REF-111`). A lock binds
agents and optimizers alike; a lever binds optimizers.

The manifold kind matters because a parameter is not always a real number. A length lives on ℝ₊, an angle on
the circle S¹, a direction on the sphere S², a mount pose on SE(3), a declared inertia on the cone of
physically consistent inertias, and a card choice in a finite set. A step taken as if every parameter were a
real number leaves the manifold: a negative length, an unnormalized axis, an inertia no body could have. Each
kind therefore carries a retraction, a map from a tangent step to a point that is still on the manifold.

Rejected alternatives. Letting optimizers write any field and validating afterwards: the validation catches
out-of-range values, not the freeing of a parameter the designer never offered. Clamping silently to bounds:
a clamped value hides that the search wanted to leave the box, which is itself a finding.

## Scope

In: the `LeverSet` view of a design; the capability handle through which an optimizer reads and moves levers;
per-manifold coordinates and retractions; conversion of a lever move into `set-lever` typed edits; the lock
check used by every edit path; the property test of INV-SKEL-08.

Out: parsing the blocks (BD-055); the edit engine and the edits `declare-lever`, `set-lever`, `lock`, `unlock`
themselves (BD-058); patches (BD-059); the optimizers (their own beads); priors' statistics (the optimizer's).

## Technical approach

Layout (DESIGN): `crates/frob-design/src/levers/{set.rs, handle.rs, manifold.rs, lock.rs}`.

```rust
// DESIGN sketch: intent, not signatures.
pub struct Lever { id: Ident, path: Path, manifold: Manifold, domain: Domain,   // Bounds(lo, hi) | Choices(..)
                   step: Option<Qty>, prior: Option<Prior>, locked: bool }
pub struct LeverSet { design: DesignId, levers: Vec<Lever> }                    // sorted by id
pub struct LeverHandle<'a> { set: &'a LeverSet }       // the only write capability an optimizer receives
pub enum LeverValue { Scalar(Qty), Angle(Qty), Direction([Ratio; 3]), Pose(ExactPose),
                      Inertia(PseudoInertia), Choice(Ident) }
pub struct LeverMove { id: Ident, to: LeverValue }
impl LeverHandle<'_> { fn propose(&self, moves: &[LeverMove]) -> Result<Vec<TypedEdit>, Refusal>; }
```

Manifold kinds, their coordinates and retractions:

| Token | Manifold | Value | Retraction for a tangent step δ from x | Bounds mean |
|---|---|---|---|---|
| `R` | ℝ | a quantity | x + δ | lo ≤ x ≤ hi |
| `R+` | ℝ₊ | a positive quantity | x·exp(δ/x), which stays positive | 0 < lo ≤ x ≤ hi |
| `S1` | circle | an angle | x + δ taken modulo one turn | an arc [lo, hi] |
| `S2` | sphere | a unit direction | (x + δ)/‖x + δ‖ with δ ⟂ x | a cone about a reference direction with a half-angle |
| `SE3` | rigid poses | a frame | x·exp(δ) or x·cay(δ) with the group's retractions | a box on translation and a cone on rotation, relative to a reference pose |
| `inertia-cone` | consistent pseudo-inertias | a 4×4 pseudo-inertia | the affine-invariant or log-Cholesky step, which cannot leave the cone | a mass interval and the mass support |
| `finite` | a finite set | a catalog identifier | none: a move names a choice | membership in `choices` |

`propose`, as numbered steps:

1. For each move, look the lever up by `id`. An identifier that is not a declared lever refuses with
   `FROB-REF-111` (an optimizer tried to move a parameter that is not a lever).
2. A lever with `locked: true`, or whose path lies under an entry of `locks`, refuses with `FROB-REF-111`.
3. Check the value's kind against the manifold, and that it is on the manifold in exact arithmetic where the
   value is exact (a direction's squared norm is 1; a pseudo-inertia passes the exact positivity test).
4. Check the domain. A value outside it refuses with `FROB-REF-111`, with the nearest admissible value in
   `required`. Nothing is clamped.
5. Emit one `set-lever` typed edit per move. The handle has no other output: an optimizer cannot produce an
   edit of any other kind through it.

The lock check, used by every edit path (`design.edit`, `design.patch`, `module.substitute`, the handle): the
write set of an edit (the paths it changes) is compared with `locks` and with the `constraints.locked` list of
a patch; an intersection refuses with `FROB-REF-111` naming the locked entry. `unlock` is itself a typed edit
and is recorded in the lineage; it is never implied by another edit.

Refusal (exit code 3):

| Code | Meaning | Triggers here | Ranked repairs |
|---|---|---|---|
| `FROB-REF-111` | A lever outside its bounds; an edit to a locked field | A move to a non-lever; a move outside bounds or choices; a value off its manifold; a write under a lock | 1. `set-lever` to the nearest admissible value; 2. `declare-lever` (or widen bounds), which an agent may do and an optimizer may not; 3. `unlock` the entry, by an explicit edit |

Determinism class D0 for the checks. Retractions on `R+`, `S1`, `S2`, `SE3` use the deterministic elementary
functions of the Lie library and are D0 only for exact inputs; an optimizer's floating-point step is converted
to an exact decimal before it becomes a `set-lever` edit, so the design that results is exact data.

## Acceptance criteria

- [ ] INV-SKEL-08 holds on 10⁴ random sequences of handle calls against random designs: the structural diff
      between the input design and each output design touches only declared lever paths; every resulting
      value is inside its domain and on its manifold.
- [ ] A move to an undeclared parameter, a move outside bounds, a move on a locked lever and a write under a
      `locks` entry each refuse with `FROB-REF-111`, and none changes the design.
- [ ] On the worked design: lever `thigh` (bounds [0.15, 0.30] m, `R+`) accepts 0.24 m and refuses 0.31 m with
      0.30 m in `required`; lever `knee_card` (`finite`, choices `qdd-m`, `qdd-l`) accepts `qdd-l` and refuses
      `qdd-xl`.
- [ ] The retraction of each manifold kind returns a point on the manifold for 10⁵ random steps (positivity
      for `R+`, unit norm within 4 ulp for `S2`, a positive-definite pseudo-inertia for `inertia-cone`).
- [ ] An `unlock` followed by an edit under the former lock succeeds and both edits appear in the lineage.
- [ ] The handle type exposes no method that returns an edit other than `set-lever` (checked by a compile
      test that fails to build an attempted misuse).

## Test plan

### Unit tests

`cargo test -p frob-design levers`.

- `lever_move_in_bounds_ok`, `lever_move_out_of_bounds_refuses` (0.31 m → `required` 0.30 m).
- `finite_lever_choice`: `qdd-l` accepted, `qdd-xl` refused.
- `non_lever_move_refuses`: the torso wall thickness is not a lever in the worked design.
- `locked_lever_refuses`, `write_under_lock_refuses` (a `set-bus` edit with `locks: ["power_bus"]`).
- `rplus_retraction_stays_positive`: x = 0.21 m, δ = −10 m gives a positive value, never ≤ 0.
- `s2_retraction_unit`: random tangent steps keep ‖x‖ = 1 within 4 ulp.
- `inertia_cone_retraction_positive`: 10⁴ random steps from a consistent pseudo-inertia stay positive
  definite by exact LDLᵀ on the rounded rational result.
- `prop_inv_skel_08` (10⁴ cases): the invariant as stated in the acceptance list.
- `compile_fail_handle_cannot_emit_reshape`: a doc-test that must not compile.

### End-to-end script and logging

Exercised by `scripts/e2e/skel_patch.sh` (N14a-29): a patch whose operations write a path listed in
`constraints.locked` refuses with exit code 3 and `FROB-REF-111`; a `set-lever` outside bounds likewise. Each
step logs the command line, exit code, the refusal's pointer, observed and required values with units, and
the `DesignId` before and after (equal on refusal).

### Known answers and negative controls

- Hand cases: 0.24 m lies in [0.15, 0.30] m; 0.31 m does not, nearest admissible 0.30 m.
- Negative control 1 (planted): a handle that clamps to bounds. `lever_move_out_of_bounds_refuses` fails.
- Negative control 2 (planted): a handle that resolves `id` by path prefix, so a move on
  `/limbs/of/of/chain/1/body/region` reaches a sibling parameter. `prop_inv_skel_08` fails with the first
  non-lever path that changed.
- Negative control 3 (planted): the lock check applied to the declared path and not to the write set; a
  `swap-battery` edit that writes under `power_bus` passes the mutant and fails the test.
- Determinism lanes: the checks are exact; identical refusals twice, debug and release, Linux and macOS.

## Considerations

- A lever on a parameter under a constructor moves every instance (all four thighs), which preserves the
  symmetry groups; a lever that addresses one instance breaks them, and the edit reports the effect.
- The optimizer holds a handle to one design version; after each accepted move it receives the new version's
  handle. A handle is never valid across versions.
- Priors and steps are hints to search and are not checked beyond dimension.
- What would make us revisit: an optimizer class that needs to add or remove components. That is a search over
  typed edits by an agent or a generator, with its own review, and stays outside the lever interface.
