## Background

`frob-model` (layer 2, tier Solid) is the compiler of Skeleton: it turns a design term into an immutable
`RobotModel`. Its pipeline is: Design → **elaborate** → validate → five functors (kinematic, geometric and
inertial, binding, budget, symmetry) → assemble → lowerings. This bead is the first stage.

A design keeps its constructors unexpanded (canonical-form rule 7): a quadruped is one leg under two nested
`mirror` constructors, and that is what makes its symmetry a property of the term. The functors, however,
work on instances: four legs, each with its own bodies, joints and frames. Elaboration is the step between:
it expands constructors, imports modules, and resolves parameters, and returns the expanded tree with resolved
parameters. The expanded tree is a compile product and is never stored in a design.

Two properties of the stage matter to everything after it.

- Memoization per subterm. The memo key of the stage is the subterm hash with the digests of the modules and
  cards it names, so a subterm that occurs four times under mirrors is expanded once, and an edit to one limb
  re-elaborates that limb only (INV-SKEL-02: incremental compilation equals full compilation, bit for bit).
- Source paths. ADR-SKEL-09: every compile product records the fields it read, and invalidation after an edit
  is computed from those records. The functors read the expanded tree, so each expanded value must remember
  which field of the source term it came from; otherwise a read of "the front-left thigh length" could not be
  traced to the one `…/capsule/1` field that four thighs share.

Rejected alternative: storing the expanded tree and editing it. It loses the constructors, and with them the
exact route to symmetry, the single point of edit for a mirrored parameter, and small diffs.

## Scope

In: the crate scaffold of `frob-model` (manifest with layer and rank, `CONTRACT.md`, `contract.toml`,
`tests/conformance.rs`); the driver that walks a term and applies constructor expansion; parameter
resolution; instance identifiers and the identifier map; selector expansion (`joints:*`, `feet:*`, `"*"`);
source-path bookkeeping; the stage's memo key; refusals of unresolved references; the tracked term view
(`Tracked<'_, Term>` with a per-stage `ReadSet`) through which this stage and every later stage and functor read
the term.

Out: the expansion rule of each constructor and the parity signs of `mirror` (BD-056); module loading and
contract checks (BD-060); the checks of the validate stage (N14a-08); the functors (BD-061, BD-062, N14a-09
to N14a-11); the memo graph over all stages, the storage of read sets as influence records, the write sets of
edits, the invalidation set and the mutation test that shows the view was not bypassed (BD-063). BD-063 depends
on the functors, so it cannot be the bead that supplies the view they read through; the view is therefore
introduced here, the first stage of the pipeline, and BD-063 builds on it.

## Technical approach

Layout (DESIGN): `crates/frob-model/src/elaborate/{driver.rs, instance.rs, ident.rs, select.rs, sourced.rs}`.

```rust
// DESIGN sketch: intent, not signatures.
pub struct Sourced<T> { value: T, from: SourceSet }             // SourceSet: sorted field paths of the design
pub struct Instance { id: InstanceId,                           // "leg.fl.thigh"
                      kind: ComponentKind, parent: Option<InstanceIdx>,
                      node: Sourced<TypedNode>,                 // body, joint, end effector, sensor, payload
                      placement: Sourced<ExactIsometry>,        // accumulated constructor transforms, exact
                      parity: i8 }                              // +1, or −1 under an odd number of mirrors
pub struct Elaborated { instances: Vec<Instance>,               // parents before children; deterministic order
                        closures: Vec<ClosurePair>, ident_map: IdentMap, key: MemoKey }
```

The stage, as numbered steps:

1. Read the term only through the tracked view (no stage receives the raw term). The view is introduced by
   this bead (DESIGN: `crates/frob-model/src/track.rs`). `Tracked<'_, Term>` wraps a borrowed term; each accessor
   returns the value of one field and appends that field's path to the `ReadSet` of the stage that holds the
   view; the term's fields are private to the module, so a read that goes round the view does not compile. A
   stage returns its `ReadSet` beside its product. Nothing in this bead interprets a `ReadSet`: storing it as an
   influence record and computing invalidation from it is BD-063. Every value copied into the expanded tree is
   wrapped as `Sourced` with the path it was read from.
2. Walk `root`, then `limbs`, `payloads` and `sensors`, depth first in term order. For each constructor apply
   the expansion rule of BD-056:
   - `attach(parent_port, child)`: the child's instances hang on the named mechanical port;
   - `chain` and `serial(k, link)`: a serial list; `serial` repeats `link` k times;
   - `mirror(plane, limb)`: two images, the second under the reflection, with `parity` negated and axial
     quantities (joint axes read as rotation axes) mapped by det(P)·P·a;
   - `radial(n, axis, limb)`: n images rotated by k/n turn, k = 0 … n − 1, exact in rationals or in the
     cyclotomic field the symmetry code uses;
   - `scale(factor, sub)`: lengths multiplied by an exact positive factor;
   - `replace(path, component)`: the component at `path` in the enclosed subterm is substituted;
   - `closure(port_a, port_b)`: recorded as a `ClosurePair` of two instance ports; the tree stays a tree;
   - `use(module, at, bind, rename)`: delegated to the module bead, which returns a subterm to splice.
3. Memoize: before expanding a subterm, look up (subterm hash, digests of the modules and cards it names).
   A hit returns the expanded subtree, which is then re-based on the current placement and identifier prefix.
4. Resolve parameters. Each parameter's value is its written quantity, or the bound value from an enclosing
   `use … bind`. Provenance travels with the value. Nothing numeric is evaluated in binary64 here: the
   expanded tree is exact data.
5. Derive instance identifiers. Each constructor contributes a suffix by BD-056's rule (two nested mirrors of
   `leg` give `leg.fl`, `leg.fr`, `leg.rl`, `leg.rr`), and a body adds its own name (`leg.fl.thigh`). Build
   the identifier map: instance identifier ↔ (source path, constructor indices). Identifiers must be unique;
   a collision refuses with `FROB-REF-103`. The identifier map is bound to the `DesignId` and is not part of
   any mechanical product: no mechanical product reads names, so a `rename` rebuilds nothing.
6. Expand selectors: a sensor `parent` of `"joints:*"` or `"feet:*"` becomes one sensor instance per matching
   joint or foot; a bus `members` of `"*"` becomes the list of all actuator instances.
7. Order instances so that a parent precedes its children (the model's link numbering is topological: the
   parent index is less than the child index) and siblings follow term order, then constructor index. The
   order depends on nothing else.
8. Return `Elaborated` with its memo key.

Refusals issued here (exit code 3):

| Code | Meaning | Trigger here | Ranked repairs |
|---|---|---|---|
| `FROB-REF-101` | Port type mismatch | `attach` names a port that does not exist on the parent, or one that is not mechanical | `move-mount` to an existing port; the list of the parent's ports |
| `FROB-REF-103` | Unknown or duplicate field | Two instances with one identifier; a `replace` path that names nothing | `rename`; the nearest existing path |
| `FROB-REF-102` | Unit or dimension error | A `scale` factor that is zero, negative or not dimensionless | `scale` with a positive factor |
| `FROB-REF-111` | A lever outside its bounds | A `bind` value outside the module parameter's bounds | The nearest bound |

An expansion that would exceed 4,096 instances (TARGET limit) refuses with the import-limit refusal
`FROB-REF-832` (`import-over-limit`, exit 3, registered by N37-REF; `observed` is the instance count the
expansion would reach, computed from the constructor counts before anything is allocated, `required` is the
limit): a `serial(10⁹, link)` must not exhaust memory. The other import limits by profile are N37-05's.

Determinism class D0: the expanded tree is a pure function of the term and the digests in its key.

## Acceptance criteria

- [ ] The worked design `quad-a` elaborates to 17 body instances (1 torso; 4 legs of 3 link bodies and 1
      foot), 12 revolute joints with 12 actuators, 4 feet, and sensor instances 1 (imu), 12 (`joints:*`
      encoders), 4 (`feet:*` contact sensors) and 1 (lidar).
- [ ] The nested mirrors expand one leg subterm once and serve three memo hits.
- [ ] Hip mounts of the four legs are at (±0.19, ±0.08, 0) m exactly, and the leg images under an odd number
      of mirrors have parity −1.
- [ ] `radial(6, z, limb)` yields six images at exact rotations of k/6 turn; `serial(8, link)` yields eight
      links in order.
- [ ] Every value in the expanded tree carries a non-empty source set, and the four thigh lengths of `quad-a`
      carry the same single source path `/limbs/of/of/chain/1/body/region/capsule/1`.
- [ ] The `Tracked` view is the only way to read a term in `frob-model`: a test crate that reads a field of the
      term without it fails to compile, and the `ReadSet` the stage returns contains every path that occurs in a
      source set of its tree.
- [ ] Elaborating twice, with 1 and with 36 worker threads, in debug and release, on Linux and macOS, gives
      bit-identical trees.
- [ ] Incremental elaboration after `set-param` on the thigh length equals elaboration from an empty memo.
- [ ] An `attach` to a missing port (`FROB-REF-101`), a duplicate instance identifier (`FROB-REF-103`) and an
      over-limit `serial` (`FROB-REF-832`, refused before any instance is allocated) each refuse with the
      stated code.
- [ ] `crates/frob-model/CONTRACT.md` exists with its ten sections and states class D0 for this stage.

## Test plan

### Unit tests

`cargo test -p frob-model elaborate`.

- `quad_a_instance_counts`: the counts of the first acceptance line.
- `mirror_images_exact`: hip mounts at (±19/100, ±2/25, 0) m; parity signs (+, −, −, +).
- `radial_six_exact_rotations`; `serial_repeats_in_order`; `scale_multiplies_lengths` (factor 3/2).
- `replace_substitutes_component`: `replace` of the knee actuator (`qdd-m` → `qdd-l`) written on the leg
  subterm under the two mirrors changes all four knees, because `replace` substitutes on the subterm before
  expansion (BD-056's rule 7, tested there as `replace_before_expand`): the four knee instances carry `qdd-l`,
  the leg is still expanded once with three memo hits, and the instances keep their mirror parities. A change
  to one image only is not a `replace`: it is BD-058's constructor split, tested there.
- `selectors_expand`: `joints:*` → 12, `feet:*` → 4, `members: "*"` → 12.
- `source_paths_shared_under_constructors`: the four thigh lengths share one source path.
- `tracked_view_untracked_read_fails_to_compile` (a compile-fail test) and `read_set_covers_source_sets`.
- `identifier_collision_refuses`; `attach_missing_port_refuses`; `serial_over_limit_refuses`.
- `memo_hit_under_mirror`: one expansion, three hits (counted through the stage's counters).
- `prop_elaborate_deterministic` (10³ `synthetic` designs): bit-identical trees across worker counts.

### End-to-end script and logging

Exercised by `scripts/e2e/skel_author_compile.sh` (N14a-27): `frob design show quad-a --instances --json`
asserts the instance counts and the four hip-mount positions; the planted missing-port design asserts exit
code 3 and `FROB-REF-101`. NDJSON lines carry the command, exit code, wall time, the envelope's `evidence`
block, instance counts as metrics, and the stage's memo counters (computed, served).

### Known answers and negative controls

- Counting known answer (hand-checkable): 1 + 4 × (3 + 1) = 17 bodies; 4 × 3 = 12 actuated joints.
- Geometry known answer: under the two mirrors (through the xz and yz planes) the mount (0.19, 0.08, 0) m has
  images (0.19, −0.08, 0), (−0.19, 0.08, 0) and (−0.19, −0.08, 0) m.
- Counterexample CX-124 (a mirrored revolute joint can be written with the mirrored axis P·a and keep its
  coordinate): for a reflection an axis is an axial vector and maps to det(P)·P·a; the planted mutant that
  maps axes as polar vectors must be caught by `mirror_images_exact` on the hip-abduction axis.
- Negative control (planted): instance order taken from a hash-map iteration. The determinism property fails
  between debug and release.
- Negative control (planted): source sets dropped for values copied under `mirror`. The shared-source test
  fails, and with it the invalidation of all four thighs by one edit.

## Considerations

- The identifier map is the join between names an agent sees and indices the kernels use; it travels with
  telemetry so that a channel can be named `leg.fl.knee`. It is keyed by `DesignId`, not `ModelId`.
- Expansion is exact. An n-fold rotation for n not dividing 4 has irrational entries; they are kept in the
  exact field the symmetry code uses, and converted to binary64 once, at lowering.
- A `closure` makes the mechanism a graph while the instance list stays a tree; which closures can be
  eliminated in closed form is decided later, by the dynamics chapter's recognition step.
- Elaboration cost is linear in instances; the 100 ms budget of preflight stage 1 (TARGET, 95th percentile,
  empty memo, any archetype) covers parse, canonicalize, elaborate and validate together.
