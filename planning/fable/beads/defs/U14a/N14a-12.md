## Background

A compiled `RobotModel` is immutable and is consumed in four forms, called lowerings: (1) an articulated
model for the referee tier (BD-061); (2) packed structure-of-arrays buffers for the batched tiers, with depth
levels and a path table for sparse Jacobians (the kernel-side bead); (3) analysis views for the design
studio: symbolic kinematics for one limb, the leg-permutation group, the budget graph; (4) a variant record
inside a size bucket, so that many different robots can share one batch. This bead builds (3) and the part of
(4) that belongs to the compiler.

Why views. A static analysis rarely wants the whole model. Workspace and singularity analysis want one limb
as a serial chain with its parameters still symbolic; a gait or mode analysis wants to know how the symmetry
group permutes the limbs; co-design wants the budget relations. Handing each analysis exactly that, with a
content hash of its own, is what makes reuse after an edit sound: sibling limbs' symbolic kinematics and
closed-form inverse-kinematics kernels depend on the limb alone, so when one limb module is swapped the
other limbs' views have unchanged hashes and their cached analyses are served (the substitution rules of
BD-077 rely on this). The view is the unit of reuse, not the model.

Why a shape summary. On the batched tiers one step plan serves a shape class: fixed capacities for degrees of
freedom, links, tree depth, collision samples, contacts, rows and actuators. A design is admitted into a
bucket only if its counts fit. The compiler knows those counts exactly; the family-of-bodies subsystem owns
the bucket set and the padded table. The summary is the hand-off between them, and it is needed early: the
paper-scale pilot of padding overhead and bucket count on the first archetypes uses nothing else.

## Scope

In: `LimbView`; the limb-permutation action of Γ_mech and Γ_obs; the budget-graph view; the per-view content
hash and read set; `ShapeSummary`, the one place where a model's own counts (velocity coordinates, links,
depth, actuators, static maximum of collision samples, end effectors, sensor layout, contact-law selectors)
are computed; the pure comparison `fits` of a summary against a plain capacity record, with the padding per
field.

Not in this bead, with the bead that has it: the `ShapeClass` type, the registry of admitted classes, the
workload-dependent parts of a model's requirement (active-contact capacity C, row capacity R) and the
structure hash, the choice of the smallest admitted class, the level decision P-A or P-B, the fit state and
the refusal `FROB-REF-160` (N17a-02 in `frob-phylum`, M2, which depends on this bead: it builds its
requirement from this summary without recounting, and its fit calls `fits` for the summary's fields).

Out: the analyses (their own beads); the packed buffers and the path table (BD-148); the `ModelTable`
layout, masks, buckets and the gather kernel (the family-of-bodies beads); the referee lowering (BD-061).

## Technical approach

Layout (DESIGN): `crates/frob-model/src/lower/{views.rs, limb.rs, perm.rs, shape.rs}`.

```rust
// DESIGN sketch: intent, not signatures.
pub struct LimbView { limb: LimbId, hash: Blake3,                 // content hash of exactly what the view holds
                      root_port: FrameRef,                        // the mechanical port the limb hangs on
                      joints: Vec<LimbJoint>,                     // screw basis, exact reference transform, limits
                      params: Vec<SymbolicParam>,                 // levers and module parameters kept as symbols
                      end_effectors: Vec<FrameRef>, reads: ReadSet }
pub struct LimbPermutation { group: GroupId, action: Vec<Vec<(LimbId, i8)>> }   // per element: limb image and sign
pub struct BudgetGraphView { relations: Vec<Relation>, summaries: Vec<SummaryRef>, hash: Blake3 }
pub struct ShapeSummary { n_v: u16, links: u16, depth: u8,          // links and depth after the fixed-joint fold
                          bodies: u16, folded: u16,                 // bodies before the fold; bodies folded away
                          actuators: u16,
                          samples_static_max: u16,                // collision samples that can be active at once
                          end_effectors: u16, sensor_layout: SensorLayoutId, contact_laws: Vec<LawSelector> }
pub struct ShapeCapacity { n_v: u16, links: u16, depth: u8, actuators: u16, samples: u16 }   // plain numbers
```

Steps:

1. Limbs. A limb is a maximal subtree hanging on one mechanical port of the root body (or of a body named by
   a `use`), as the term states it: each image of a `mirror` or `radial` constructor is one limb. Give each a
   `LimbId` and compute its content hash from the mechanical fields of its subtree only. Images of one
   subterm share the hash.
2. `LimbView`: the serial chain or tree of the limb with exact screw bases and reference transforms in the
   port frame, limits, and every lever or module parameter left as a named symbol with its bounds, so that a
   symbolic derivation (forward kinematics, the Jacobian, a closed-form inverse) is valid over the whole
   parameter box and not at one value.
3. Limb permutation: for each element of Γ_mech and of Γ_obs, the image of each limb and the sign with which
   limb-local coordinates map, read off the symmetry section's body permutation.
4. Budget-graph view: the relations and summary references of the budget section, with a hash.
5. Shape summary: `n_v` (velocity coordinates, including 6 for the floating base); `links` and `depth`
   counted **after the fixed-joint fold**: a body joined to its parent by a joint of class `fixed` belongs to the
   first ancestor reached through a non-fixed joint (or the root), the fold groups of N14b-33's step 1, so
   `links` is the number of fold groups and `depth` the longest root-to-leaf path counted in them; `bodies`
   (before the fold) and `folded` (`bodies − links`) beside them; actuator count; the static maximum of
   simultaneously active collision samples (from the collision primitives and their sample rules); end-effector
   count; the digest of the sensor layout; the set of contact law selectors. DESIGN (stated identically in
   N17a-02):
   the batched tiers' model table holds folded links only, so a class's link capacity bounds folded rows (the
   byte model's n_b = 13 for the reference quadruped); a count before the fold over-states the requirement by
   one link per welded body. The count is structural and needs no inertia; N14b-33, which computes the fold
   itself, asserts that its group count equals this `links` on every design it folds.
6. Fit: `fits(&ShapeSummary, &ShapeCapacity) -> Fit`, returning `Fits { padding }` with the unused capacity
   per field, or `Exceeds { field, need, capacity }`. Pure comparison of the five counts the compiler knows;
   the bucket planner decides. DESIGN (the conflict settled, stated identically in N17a-02): an earlier draft
   took `&ShapeClass`, but that type belongs to `frob-phylum`, one layer above `frob-model` and one milestone
   later, so this crate cannot name it; and N17a-02 recounted n_v, links, depth, actuators and samples from
   the lowered model while this bead counted them too. One count and one comparison: the counts are this
   summary's; `fits` compares them with a plain `ShapeCapacity`; `frob-phylum` converts its `ShapeClass` to a
   `ShapeCapacity`, calls `fits`, and compares the two workload-dependent capacities (contacts C and rows R)
   itself, because no compiled model knows them. The sensor layout is carried under the plan's name
   `SensorLayoutId` (the draft's `SensorLayoutDigest` was a second name for it).
7. Every view records its read set, so a view is invalidated only by an edit inside what it holds.

Determinism class D0. A view is data with a hash; it carries no verdict.

## Acceptance criteria

- [ ] The worked design `quad-a` yields four limbs with one shared `LimbView` hash, each with three joints
      and the thigh length as a symbol bounded by [0.15, 0.30] m.
- [ ] Its limb permutation under Γ_mech = C₂ × C₂ has four elements acting on the four legs as the identity,
      the left-right swap, the fore-aft swap and the diagonal swap.
- [ ] Its shape summary is n_v = 18, links = 13, depth = 3 (after the fold: torso at depth 0, shank at depth
      3, each foot folded into its shank), bodies = 17, folded = 4, actuators = 12, end effectors = 4, and it
      fits a capacity with n_v = 18 with zero padding in n_v and one of 24 with padding 6.
- [ ] Swapping one leg for a different module changes that limb's view hash and leaves the other three
      bit-identical.
- [ ] A `rename` changes no view hash; moving the lidar changes no `LimbView` hash and changes the sensor
      layout digest.
- [ ] `fits` reports `Exceeds { field: n_v, need: 29 + 6, capacity: 24 }` for a 29-joint humanoid against a
      capacity of 24, fits it into 36 with padding 1 and into 48 with padding 13. (The sizes are those of the
      registered default bucket set {12, 18, 24, 36, 48, 64}; an earlier draft used 32, which is in no
      registered set.)
- [ ] Views and summaries are bit-identical twice, in debug and release, on Linux and macOS.

## Test plan

### Unit tests

`cargo test -p frob-model lower::` (one filter: the modules of the layout above).

- `quad_a_limbs_share_hash`; `limb_view_keeps_symbols` (the thigh lever appears as a symbol, not 0.21).
- `limb_permutation_c2xc2`: the four permutations listed above.
- `shape_summary_quad_a`: n_v 18, links 13, depth 3, bodies 17, folded 4, actuators 12.
- `shape_links_after_fold`: a chain of two fixed joints (bracket on bracket on the torso) adds two bodies and no
  link; a fixed joint below a revolute adds a body and no depth; a design with no fixed joint has links = bodies.
- `fit_and_padding`: capacities 12, 18, 24, 36, 48, 64 against summaries of the worked designs.
- `swap_one_limb_changes_one_view`; `rename_changes_no_view`; `move_sensor_changes_layout_only`.
- `budget_graph_view_hash_tracks_relations`.
- `prop_limb_hash_ignores_placement` (10³ `synthetic` designs): two images of one subterm at different
  mounts have equal limb hashes.

### End-to-end script and logging

`scripts/e2e/skel_author_compile.sh` (N14a-27): `frob design show quad-a --shape --json` asserts the shape
summary; logged with the summary fields as metrics, the limb view hashes and the envelope's `evidence` block.

### Known answers and negative controls

- Counting known answers (hand-checkable): 6 + 12 = 18 velocity coordinates; 1 + 4 × 4 = 17 bodies and,
  after the fold, 1 + 4 × 3 = 13 links (the n_b = 13 of the byte model); a foot is four joints below the torso
  (three revolutes and the fixed foot attachment), so the depth in folded links is 3.
- Padding known answer shared with the bucket pilot: a model of 18 coordinates in a class of 24 wastes 6.
- Negative control 1 (planted): a limb hash that includes the mount placement. Mirror images then have four
  hashes, sibling reuse never happens, and `quad_a_limbs_share_hash` fails.
- Negative control 2 (planted): a view that substitutes parameter values for symbols. A derived kernel would
  then be valid at one thigh length only; `limb_view_keeps_symbols` fails.
- Negative control 3 (planted): `n_v` computed without the floating base. The summary test fails (12 ≠ 18).
- Negative control 4 (planted): `links` counted before the fold. `shape_summary_quad_a` fails (17 ≠ 13), and so
  does N17a-02's `requirement_counts_after_fold`.

## Considerations

- The limb is defined by the term, not rediscovered from the expanded tree, so that "the same limb four
  times" is a fact about the design and survives numerical noise in imports.
- A view deliberately omits what its consumer must not read; an analysis that needs more must ask for
  another view, and its read set then says so.
- The variant record itself (padded tables of about 192 bytes per link, masks, the world row) is owned by
  the family-of-bodies subsystem; if its layout changes, only the hand-off struct here changes.
- Whether a limb in contact can be summarized at its port at all is answered no elsewhere (the limb port
  packet's consumer rules); these views are static.
