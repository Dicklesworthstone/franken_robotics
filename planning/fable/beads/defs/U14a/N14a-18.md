## Background

A design file names its schema (`frob.design/1`), and its identity `DesignId` is the hash of its canonical
bytes. Schemas change. The rule for how they change, from the design chapter: a schema has a major and a
minor number and a canonicalization revision. A minor version adds optional fields. A major version needs a
migration, which reads the old object, writes a new one with a `migrate` lineage edge and its provenance,
and leaves the old object in place so that old runs replay against the compiler version that produced them.
`.fbot` and `.fmodule` files travel in a common artifact envelope, which carries the schema, the
canonicalization revision, the payload and parent digests, the generator pin, the validity region and the
licence.

The format registry states the same from its side: the schema name carries a major version; adding an
optional field keeps it; a reader refuses an unknown major version and an unknown required field and never
parses on a best-effort basis; migration is a typed edit that produces a new artifact with a link to the old
one; the old identity stays valid for citing old evidence.

Why this needs care. Identity is bytes. Any change to how bytes are produced (a new written-out default, a
unit token the units library prints differently) would silently change the `DesignId` of every existing
design and orphan every cached analysis and every piece of evidence that cites it. So the three numbers have
three different jobs: the major number says which reader applies; the minor number says which optional
fields exist; the canonicalization revision says which byte rules produced the identity. A design keeps the
identity it was given under its own minor version and revision until someone migrates it on purpose.

The `migrate` edit's row in the edit table: symmetry effect none, by construction; invalidation none if the
migration is certified meaning-preserving, otherwise global. The gate clause it must pass (part of
GATE-SKEL-08): a schema migration leaves forward kinematics and mass properties bit-identical and old runs
replayable.

Rejected alternatives: best-effort reading of newer files (a reader that ignores a field it does not know
simulates a different robot under the same identity); rewriting designs in place on upgrade (old evidence
then cites an identity that no longer exists).

## Technical approach

Layout (DESIGN): `crates/frob-design/src/version/{triple.rs, envelope.rs, migrate.rs, registry.rs}`.

```rust
// DESIGN sketch: intent, not signatures.
pub struct SchemaVersion { major: u16, minor: u16, canon_rev: u16 }
pub struct ArtifactEnvelope { schema: SchemaName,            // "frob.design/1": name and major
                              minor: u16, canon_rev: u16,
                              payload: Blake3,               // the DesignId
                              parents: Vec<Blake3>,          // lineage parents
                              generator: StackReceiptDigest, // the pin of the binary that wrote it
                              validity: Option<ValidityRegion>, licence: Licence }
pub struct Migration { id: MigrationId, from: SchemaVersion, to: SchemaVersion,
                       apply: fn(&Term) -> Result<Term, Refusal>, kind: MigrationKind } // Major | Minor | Recanonicalize
pub struct MigrationCertificate { from: DesignId, to: DesignId, migration: MigrationId,
                                  mechanical_digest_equal: bool, differing_sections: Vec<SectionId> }
```

Where the numbers live. The major number is in the document (`"schema": "frob.design/1"`) and so inside the
hashed bytes. The minor number and the canonicalization revision are in the envelope, outside the hashed
payload: a design's canonical bytes are defined relative to them. A bare file with no envelope is read under
the newest minor and revision of its major and receives an envelope when it is stored.

Rules:

1. Reading. Dispatch on the major number. An unknown major refuses with `FROB-REF-125` and names the
   migration that applies, if one is registered. A known major with a minor above the reader's refuses the
   same way (it may contain fields this reader would have to ignore). A lower minor or revision is read with
   the rules of that minor and revision, and its identity is not recomputed under newer rules.
2. Minor versions. A minor version may only add optional fields whose absence means exactly the previous
   behaviour. Absence stays absence in the canonical form of a design recorded under an older minor.
3. Canonicalization revision. A change to any byte rule (number printing, unit token spelling, written-out
   defaults, string escaping) is a new revision. The golden tables of the canonical form are keyed by
   revision, so a change in a sibling library's printing fails a test instead of changing identities.
4. Migration. `migrate` is a typed edit: it takes a design under version v, applies the registered function
   for v → w, canonicalizes under w, and returns a new immutable design with a new `DesignId` and the
   certificate below. It commits like every edit, through BD-058's design store: one edit record whose op
   carries the migration identifier and both versions, and an envelope whose `parents` names the old design
   and whose `generator` is the tool's stack receipt. The `migrate` lineage edge is built from that record by
   the lineage bead (BD-113), which reads it and adds nothing to it. The old object is left in place and
   remains readable and citable.
5. Meaning preservation. Compile the old design with the reader of v and the new one with the reader of w
   (same compiler version, same card versions) and compare the digests of the mechanical sections. Equal
   digests certify the migration meaning-preserving: the two designs share a `ModelId`, the invalidation set
   of the edit is empty, and every result that cites the old model still applies. Unequal digests make the
   edit global: everything downstream of the model is invalidated and the certificate lists the differing
   sections. The check is run, never assumed: "none, by construction" is the expectation it tests.
6. Symmetry. A migration reports both symmetry groups before and after; they must be equal for a certified
   migration.

Envelope. Written beside the payload when a design is stored or exported: `schema`, `minor`, `canon_rev`,
`payload` (the `DesignId`), `parents`, `generator`, `validity` (for a design produced for a region of a
mission cell; absent otherwise) and `licence` (from `meta.licence`). On export it also carries the
no-authorization flags and the stack receipt, as every exported artifact does. The envelope is canonical
JSON of its own (`frob.design.envelope/1`, DESIGN name) and is not part of the identity.

Refusal (exit code 3): `FROB-REF-125`, unsupported schema version; `required` names the versions this build
reads and the migration to run. Repair: the `migrate` edit.

Migration fixtures. Only version 1 exists, so the mechanism is exercised with two `synthetic` migrations
compiled under a test feature: (a) a major migration to a test-only `/2` that renames `fill` to `occupancy`
and moves `power_bus.sink` into a top-level `thermal` block; (b) a recanonicalization from revision 1 to a
test-only revision 2 that changes one unit token's spelling. Both preserve meaning. A third, (c), drops a
shell thickness on purpose and must be caught.

Determinism class D0.

## Acceptance criteria

- [ ] Migration clause of GATE-SKEL-08 (TARGET): a schema migration leaves forward kinematics and mass
      properties bit-identical and old runs replayable. Measured on fixtures (a) and (b) over every archetype
      available and 10³ random designs: zero differing mechanical digests; forward kinematics at 100 seeded
      configurations and all mass properties bit-identical; the old `DesignId` still resolves and compiles.
      These tests measure and log; the gate row has one recorder, N14a-29, which enters it with `record_gate`
      from the receipt of its script's tier run `e2e_tier g4_chaos GATE-SKEL-08 --mutations` (KA-292 is a G4
      row).
- [ ] Fixture (c) is reported as not meaning-preserving, with the inertial section named, and the edit's
      invalidation set is global.
- [ ] A file with `"schema": "frob.design/9"` refuses with `FROB-REF-125`; a `/1` file whose envelope states
      a minor above the reader's refuses likewise and names the reader's range.
- [ ] A design recorded under canonicalization revision 1 keeps its `DesignId` when read by a build whose
      newest revision is 2; only an explicit `migrate` gives it a new one.
- [ ] After `migrate`, the design store holds one edit record whose op names the migration identifier and
      both versions, and the new version's envelope names the old design in `parents` and the stack receipt in
      `generator`; the old object is unmodified (same bytes, same hash). (The `migrate` lineage edge built
      from this record is asserted by BD-113.)
- [ ] A certified migration yields the same `ModelId` before and after and equal symmetry groups.
- [ ] The envelope of a stored design carries every field listed above (`schema`, `minor`, `canon_rev`,
      `payload`, `parents`, `generator`, `licence`, and `validity` when the design was produced for a region of
      a mission cell), and editing the envelope's licence does not change the `DesignId`.

## Test plan

### Unit tests

`cargo test -p frob-design version --features migration-fixtures`.

- `unknown_major_refuses`, `newer_minor_refuses`.
- `older_revision_keeps_identity`.
- `migrate_major_fixture_preserves_meaning`: fixture (a) on `quad-a`; equal `ModelId`; FK and mass
  bit-identical; new `DesignId` ≠ old.
- `migrate_recanonicalize_preserves_meaning`: fixture (b).
- `lossy_migration_is_global`: fixture (c); certificate names the inertial section.
- `old_object_left_in_place`: bytes and hash of the source design unchanged after migration.
- `migrate_record_has_provenance`: the edit record and the envelope carry the fields of the acceptance line.
- `envelope_outside_identity`; `envelope_carries_listed_fields` (absent `validity` stays absent, never null).
- `minor_adds_optional_field_only`: a registry lint that a minor version's diff against its predecessor
  contains only optional members.
- `prop_migration_fixtures_preserve` (10³ `synthetic` designs).

### End-to-end script and logging

`scripts/e2e/skel_patch.sh` (N14a-29) includes the migration steps: `frob design edit <d> migrate --to
<test-version> --key … --json`, then `frob design show` on old and new, then the re-execution (N29ax-01) of a
referee run recorded against the old design before the migration, by its `recorded_command`, which names the
design by hash, run under a key distinct from the recorded run's (otherwise the idempotency binding returns the
stored receipt instead of re-executing; N14a-29 step 11). It logs both `DesignId`s, both `ModelId`s, the certificate, the largest difference in forward
kinematics and mass (expected exactly zero), and the re-execution's chunk-digest comparison
(`reproduced: true`, zero differing chunks).

### Known answers and negative controls

- KA-292 (third clause): a schema migration leaves forward kinematics and mass properties bit-identical and
  old runs replayable. The appendix states no negative control; this bead registers fixture (c) and the one
  below.
- Negative control (planted): a migration that rewrites a quantity through binary64 (0.1 m becomes
  0.1000000000000000055 m). The mechanical digests differ in the last bit and the certificate must say so.
- Negative control (planted): a reader that re-canonicalizes an old-revision design under the newest rules.
  `older_revision_keeps_identity` fails.
- Metamorphic: migrating then editing equals editing then migrating, for edits whose fields the migration
  does not rename (compared by `ModelId`).
- Determinism lanes: identical new `DesignId`s twice, in debug and release, on Linux and macOS.

## Considerations

- The plan names "the common artifact envelope" and lists its contents without a schema of its own; the
  struct above is confined to the listed contents, and its field spellings are proposals to be reconciled
  with the format registry's envelope rules.
- "Old runs replayable" has two halves. This bead guarantees the design half: the old object stays, with its
  identity, readable under its own version triple. The other half at M1 is N29ax-01: re-execution of a
  recorded referee run by pinned identities and recorded version triple, after the head has moved by this
  edit; replay by an older compiler version across real schema revisions is a later record capability.
- Module files migrate by the same mechanism; a module's contract digest is recomputed under the new version
  and the old digest stays valid for old designs that reference it by hash.
- A real major version will arrive with real pressure to "just read the old files". The refusal with a named
  migration is the fail-closed default.
