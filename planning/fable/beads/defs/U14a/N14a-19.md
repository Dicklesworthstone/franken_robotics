## Background

The design format has a second, lossless view: an S-expression text of the same term (ADR-SKEL-02; built in
BD-057). FACT: FrankenSim's crate `fs-ir` already keeps canonical S-expressions and a lossless JSON mapping in
step as a tested property (`frankensim/crates/fs-ir/src/lib.rs`). The decision record says its reader and
quantity atoms are reused through the airlock *if they pass admission*. This bead is that admission test,
and its recorded outcome decides which reader BD-057 builds on.

Two workspace rules make this an experiment and not an assumption. A foundation that exists is not a
foundation that is admitted: a sibling crate enters the build only after a test at a pinned commit shows it
does what this project needs. And only the airlock crate `frob-fsim` may name types from FrankenSim's
volatile crates (rule L-2), so even an admitted reader is reached through a trait defined on this side.

What is at stake is small and worth settling once. An S-expression lexer is a few hundred lines; reuse saves
that and inherits the sibling's tested round-trip property, and costs a path dependency whose closure and
whose atom grammar this project does not control. A design is not a FrankenScript program and carries no
verbs, so only the data-level reader is in question, never the evaluator.

## Scope

In: a pinned-commit test of `fs-ir`'s reader and writer against the needs of the design view; a measurement
of what the dependency adds to the build; the recorded decision (reuse through the airlock, or an in-crate
reader); the airlock trait if the decision is reuse.

Out: the schema-directed mapping and the verb (BD-057); quantity canonicalization (N14a-01), which is this
project's own on both branches because the canonical decimal and the turn rule are format rules of
`frob.design/1`.

## Technical approach

The experiment, as numbered steps:

1. Pin. Record the FrankenSim commit from the stack lock. Read `fs-ir`'s public reader, writer and atom types
   and list what they accept: bracket kinds, symbol grammar, keyword syntax, string escapes, number atoms,
   quantity atoms and comments.
2. Requirement table. For each need of the design view state whether the sibling meets it:
   a. one bracket kind, symbols containing `-`, `.`, `/` and `:` (`al-6061-t6`, `torso.hip_mount`,
      `rubber-60a/default`, `joints:*`);
   b. keywords of the form `:name`;
   c. strings with the JSON escapes, byte-exact round trip;
   d. quantity atoms with no space (`0.42m`, `22.2V`, `1.2W/K`, `4000USD`), signed, and with a ratio
      magnitude (`1/3m`, `-1/8turn`);
   e. magnitudes delivered as exact text, never as binary64;
   f. `;` comments on input;
   g. position information (line and column) for refusal pointers;
   h. no evaluation, no file inclusion, no reader macros;
   i. bounded depth and size, and no recursion on the call stack, or a wrapper that enforces both.
3. Corpus test. Run the sibling's reader on the canonical S-expression corpus of BD-057's fixtures (at this
   stage: the worked example of the format and 10³ generated texts from a throwaway generator of the grammar)
   and compare token streams with a 150-line reference lexer written for this test only.
4. Hostile input. 10⁶ fuzz executions of the wrapped reader: zero panics, and every over-limit input refused.
5. Build cost. Measure the crates and lines the dependency adds to a build of `frob-design` beyond the
   closure already admitted at M0, and whether it changes the unified feature set of any shared dependency
   (the JSON library's features are a known hazard).
6. Decide by the rule below and record the decision as an architecture decision record with the table.

Decision rule (DESIGN, fixed before the test is run):

- Reuse, through a trait `SexprLexer` in `frob-fsim`, if requirements (a) to (i) are all met or met by a thin
  wrapper that changes no token, the corpus test shows zero differences, the fuzz run is clean, and the
  dependency adds no crate outside the M0 closure.
- Otherwise write the lexer in `frob-design` (`crates/frob-design/src/sexpr/lex.rs`), keep the sibling's
  reader as a cross-check oracle in tests only, and open an upstream work item naming each unmet requirement.

Either outcome passes this bead. What fails it is no recorded outcome.

## Acceptance criteria

- [ ] The requirement table (a) to (i) is filled in from the pinned commit, each row with the path and line
      that supports it.
- [ ] The corpus test ran on at least 10³ texts and its difference count is recorded.
- [ ] The fuzz run of 10⁶ executions is recorded with zero panics, or the decision is "in-crate".
- [ ] The build-cost measurement lists added crates, added lines and any change to unified feature sets.
- [ ] An architecture decision record states the branch taken, and BD-057's dependency on the airlock trait
      or on the in-crate lexer is updated accordingly.
- [ ] If the branch is reuse: `frob-fsim` exposes `SexprLexer`, `xtask check-layers` passes, and no type of
      `fs-ir` appears in a signature of `frob-design`.
- [ ] If the branch is in-crate: an upstream work item is opened under FrankenSim's rules for each unmet
      requirement, labelled `upstream`, with this project's interim posture (its own lexer) and the
      switch-over rule (re-run this bead's corpus and fuzz tests, then replace).

## Test plan

### Unit tests

`cargo test -p frob-fsim --features geometry sexpr_admission` (the feature group is chosen with the airlock
owner).

- `admission_tokens_match_reference`: token streams of the sibling reader and the reference lexer on the
  corpus; expected zero differences.
- `admission_quantity_atoms_exact`: `0.1m`, `1/3m`, `-1/8turn`, `1e400m` arrive as exact text.
- `admission_strings_byte_exact`: strings with every JSON escape round-trip byte for byte.
- `admission_no_evaluation`: an input that would be a program in the sibling's language is returned as data.
- `admission_limits`: depth 10⁴ and a 1 GiB declared length are refused without a stack overflow.

### End-to-end script and logging

None. This is a build-time admission test. Its record is the decision file and the test log, which carries
the pinned commit, the stack-lock digest, the counts of the corpus and fuzz runs and the build-cost figures.

### Known answers and negative controls

- Known answers: the nine requirement rows are yes or no facts about a pinned commit.
- Negative control: the reference lexer is run against a deliberately broken copy of itself (one that splits
  `rubber-60a/default` at the slash); the comparison must report a difference, which shows the comparison can
  fail.
- Determinism: the token stream of a text is identical twice, in debug and release, on Linux and macOS.

## Considerations

- The sibling's API still moves from day to day; a reuse decision is tied to the pinned commit and is
  re-tested when the pin moves (the stack check does this for every admitted foundation).
- If the toolchain admission forces the `frob-units` escape hatch, the sibling's quantity atoms may depend on
  a crate this project cannot name directly; that alone moves the decision to "in-crate".
- KILL-SKEL-SEXPR is independent of this outcome: it concerns whether the bijection can be held at all.
- Cost of being wrong is low in both directions: the lexer is small and sits behind one function.
