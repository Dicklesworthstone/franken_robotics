## Background

A design's identity, `DesignId`, is the BLAKE3 hash of its canonical JSON bytes (`frob.design/1`), produced
by seven byte rules: sorted keys and no insignificant white space with duplicate keys refused; quantities as
exact decimals with unit tokens; coherent SI units with shortest decimals or ratios; angles as rational
turns; wide integers, hashes and rationals as strings; every read field present with defaults written out;
constructors unexpanded. Every cached analysis, every lineage edge and every piece of evidence cites that
identity, so a canonicalization defect is the most expensive kind in the subsystem: it either gives one
design two identities (results are orphaned) or two designs one (results are merged).

The program's definition of "implemented" requires known-answer tests against a pinned oracle that was never
regenerated from the candidate. For a hash, the tempting shortcut is to run the implementation once, paste
the hashes into the tests and call them golden. That pins whatever the implementation did, including its
bugs. This bead builds the alternative: a second, independent implementation of the canonical form, small
enough to read in one sitting, written from the format text and not from the product's code, and a corpus of
designs whose canonical bytes and identities it pins.

DESIGN choices. The reference is a standalone script outside the product's build graph (under
`tools/oracle/`), in a different language from the product, using only that language's standard library plus
a BLAKE3 implementation checked against the published test vectors; it shares no code, no schema file and no
unit table with `frob-design`. It is slow and obvious on purpose: exact rationals from a big-integer library,
an explicit unit table, an explicit list of written-out defaults. Rejected alternatives: two builds of the
same code (they agree on bugs); a property test alone (idempotence and round trips cannot detect a rule that
is consistently wrong, such as sorting keys by UTF-16 code unit instead of code point).

## Scope

In: the reference canonicalizer; the golden corpus with expected canonical bytes and `DesignId`s; the
comparison harness, as a function over any canonicalizer, exercised here with the reference and with planted
wrong canonicalizers; the corpus manifest with its own hash; the procedure for changing a golden value.

Order of work. This bead comes first: the product's canonicalizer (BD-054) depends on it, so that its golden
values exist before the code they judge. The product is plugged into the harness by BD-054's conformance test,
and the product's agreement with the corpus is BD-054's acceptance, not this bead's.

Out: the product's canonicalizer (BD-054, N14a-01) and its run against the corpus (BD-054); the S-expression view (BD-057), although the corpus
supplies its inputs; the shared reader's corpus (the workspace beads); fuzzing.

## Technical approach

Layout (DESIGN): `tools/oracle/design_canon/` (the script, its unit table, its BLAKE3 with test vectors) and
`crates/frob-conformance/fixtures/design_golden/` (`*.fbot` inputs, `*.canon` expected bytes, `manifest.toml`).

The reference, as numbered steps (each written from the format's rules, with no reference to product code):

1. Reject invalid UTF-8, a byte-order mark and duplicate member names after escape decoding, at any depth.
2. Parse to a tree, keeping every number as text.
3. Canonicalize quantities: magnitude to a reduced fraction; scale to the coherent SI unit by an explicit
   table (the units the schema uses, each with its exact rational factor); print the shortest decimal when
   the reduced denominator has only the prime factors 2 and 5, otherwise `p/q`; degrees and turns to a reduced
   ratio of a turn; radians unchanged; an annotated quantity with provenance `designed` and nothing else to
   the bare string.
4. Write out the listed defaults (a joint's identity `origin`; a body's `collision` as `"region"`; a bus's
   `members` as `"*"`; `removable` and `locked` as `false`), each from a table in the script.
5. Serialize: keys in code-point order, no white space, strings escaped by the single rule of the shared
   writer.
6. Hash with BLAKE3 under the domain string `frob.design/1`, in the same way the identity rule of the format
   registry states.

The corpus (at least 40 files, 47 as listed, each with a one-line statement of what it pins):

| Group | Files | What each pins |
|---|---|---|
| Worked designs | `quad-a`, `quad-tray` | The format's two full examples, as authored |
| Key order and white space | 6 | Shuffled keys; nested shuffles; tabs and newlines; keys that sort differently by code point and by UTF-16 unit (a key with a character above U+FFFF beside one in U+E000–U+FFFF) |
| Quantities | 11 | `420 mm` and `0.42 m`; `2.5 mm`; `1/3 m`; `1e-3 m`; `-0 m`; `45 deg`, `0.125 turn`, `-160 deg`; `1.5708 rad`; `4000 USD`; `29.97 Hz`; `0.30000000000000001 m` (an exact value that shares its binary64 with 0.3) |
| Annotated quantities | 4 | Provenance `designed` collapsing to a bare string; `measured` with uncertainty; key order inside the object; a source string with escapes |
| Wide values | 4 | Integers at 2⁵³ − 1 as numbers; 2⁵³ and 2⁵³ + 1 as strings; a 64-digit hash; a rational outside a quantity |
| Defaults | 10 | Each of the five written-out defaults of step 4 (the three the format names, BD-054, and `removable` and `locked`) omitted and written explicitly: one identity per pair, five pairs |
| Constructors | 4 | `mirror` nested twice; `radial(6)`; `serial(8)`; a `use` import: all unexpanded in the bytes |
| Refusals | 6 | Duplicate key; duplicate after escapes at depth 8; unknown field; unknown unit; a bare float where a quantity is required; `null` |

For the refusal group the expected result is "no canonical form", with the reason class.

The harness: `frob_conformance::design_golden::check(canon)` takes any canonicalizer (bytes in; canonical
bytes or a refusal with its reason class out), runs it on every input of the manifest, and compares bytes and
identity with the stored expectations, naming the file and the first differing byte offset.
`cargo test -p frob-conformance --test design_golden` runs it with the reference (invoked out of process) as the
canonicalizer and with the planted wrong canonicalizers below; BD-054's conformance test runs it with the
product. A separate script,
`tools/oracle/design_canon/regenerate.sh`, runs the reference over the inputs and writes the `.canon` files;
it is the only way an expectation is produced. The manifest records, per file, the hash of the input, of the
expected bytes and of the reference script that produced them.

Changing a golden value. An expectation changes only by (a) a deliberate change of the format's rules, with
a new canonicalization revision and a migration, or (b) a defect found in the reference, fixed in the
reference first, with the diff of expectations reviewed by someone who did not write the fix. A golden value
is never updated to match the product.

## Acceptance criteria

- [ ] The reference script exists outside the product's build graph, depends on no product crate, schema
      file or registry, and its BLAKE3 passes the published test vectors.
- [ ] The corpus holds at least 40 inputs in the eight groups, each with a stated purpose; every expectation
      was produced by the reference (the manifest's script hash matches).
- [ ] The harness passes with the reference as the canonicalizer under test on every input (accepted inputs
      by bytes and identity; the refusal group by reason class), and fails, naming file and offset, with each
      planted wrong canonicalizer: keys in UTF-16 code-unit order (the two distinguishing files), magnitudes
      through binary64 in both printings (`1/3 m` and `0.30000000000000001 m` under shortest round-trip
      printing, `29.97 Hz` under exact printing of the double), defaults not written out (the defaults group). The product's
      agreement on every input is asserted by BD-054, which depends on this bead.
- [ ] The two key-order files that distinguish code-point order from UTF-16 code-unit order have different
      expected bytes under the two orders, and the stored expectation is the code-point one.
- [ ] Each pair in the defaults group has one identity.
- [ ] A planted change to one expected byte makes the harness fail and name the file and byte offset.
- [ ] The reference produces byte-identical expectations on Linux and on macOS (the product's cross-platform
      agreement is BD-054's seed condition).
- [ ] `scripts/e2e/skel_design_golden.sh` passes: a fresh regeneration into a temporary directory reproduces
      every stored expectation byte for byte.
- [ ] The regeneration procedure is documented in `tools/oracle/design_canon/README.md` with the two legal
      reasons for changing an expectation.

## Test plan

### Unit tests

- `design_golden::harness_accepts_reference`: iterates the manifest with the reference as canonicalizer.
- `design_golden::harness_rejects_planted`: the four planted canonicalizers (UTF-16 key order; binary64 with
  round-trip printing; binary64 with exact printing; defaults not written out) each fail on the files that pin
  their rule, and on no other group.
- `design_golden::refusals_have_no_canonical_form`: the reference gives "no canonical form" with the stated
  reason class for each refusal file.
- `design_golden::manifest_is_complete`: every input has an expectation and a purpose line; no stray files.
- `design_golden::expectations_from_reference_only`: the manifest's script hash equals the hash of the
  reference in the tree.
- Reference self-tests (run by `tools/oracle/design_canon/selftest.sh`, invoked from one conformance test):
  BLAKE3 vectors; `shortest_decimal` on 1/8, 1/3, 1/40; `turn_ratio` on 45°, 360°, −30°; duplicate-key
  detection on `{"a":1,"a":2}`.

### End-to-end script and logging

`scripts/e2e/skel_design_golden.sh` (this bead; sources the helper of STD-E2E). Steps, each an NDJSON line
with `step`, `status` and `duration_ms`: `selftest` (BLAKE3 vectors and the reference's own self-tests);
`regenerate` (runs `regenerate.sh` into a temporary directory and compares every `.canon` and identity with the
stored one; per file the input hash, the expected and regenerated `DesignId`, and on a mismatch the first
differing byte offset with twenty bytes of context from each side); `manifest` (script hash, input count per
group, stray files); `harness` (the reference and each planted canonicalizer, with the files each failed on);
`summary` (counts, and the manifest's hash).

The product side is exercised by `scripts/e2e/skel_author_compile.sh` (N14a-27), which includes a corpus
step: `frob design show <file> --term --json` on every accepted input, compared with the stored bytes, logged
in the same per-file form.

### Known answers and negative controls

- Known answers of the format registry: `{"b":1,"a":2}` and `{"a":2,"b":1}` have one identity; a file that
  differs only in key order or white space is the same design.
- Hand-checkable quantity answers: 420 mm → `0.42 m`; 45° → `1/8 turn`; −160° → `-4/9 turn`; 1/3 m stays.
- Negative control 1 (planted canonicalizer, and the same mutant of the product in BD-054): keys sorted by
  UTF-16 code unit. The two distinguishing files fail.
- Negative control 2 (planted canonicalizer, and the same mutant of the product in BD-054): the magnitude
  routed through binary64, in two printings. Printed as the shortest round trip, `0.30000000000000001 m` comes
  out `0.3 m` and `1/3 m` comes out `0.3333333333333333 m`, while `29.97 Hz` survives (its round trip is
  `29.97`); printed as the double's exact value, `29.97 Hz` comes out
  `29.969999999999998863131622783839702606201171875 Hz`. Each printing fails on its files, so the corpus
  catches the mutant whichever way it prints.
- Negative control 3 (planted, in the corpus): one expected byte flipped. The harness fails and names it.
- Independence check: the reference is run against a copy of itself with one rule broken (defaults not
  written out); the comparison of the two outputs differs on the defaults group, which shows the corpus
  exercises that rule.

## Considerations

- Two implementations can share a misreading of the text. The corpus therefore includes the format's own
  printed examples and the hand-checkable cases above, whose expected atoms are written in this bead and not
  derived by either implementation.
- The reference covers version 1 only. A new canonicalization revision adds a second reference mode and a
  second set of expectations; the old set stays, because old identities must keep verifying.
- The script's language is not allowed in the product's build graph, and it is not in it: it runs as test
  tooling, as the other out-of-process oracles do.
- The unit table in the reference is a second copy of what the units library knows, kept on purpose; a
  disagreement between them is a finding to investigate, in either direction.
