## Background

A design is immutable; a change is a typed edit that creates a new version. A patch (verb `design.patch`,
BD-059) applies several typed edits to a named parent, atomically, with per-patch locks, analyses that must
pass before the version exists, and an idempotency key. Three properties make it safe for several agents
and unreliable connections: a stale parent is refused, with the current head and the diff returned; the same
key with the same content returns the version already created; and nothing is ever modified in place. Schema
migration (N14a-18) is the fourth property the same gate measures.

GATE-SKEL-08 (TARGET): a stale parent refuses in 100 of 100 trials; a repeated idempotency key returns the
same `DesignId`; a schema migration leaves forward kinematics and mass properties bit-identical and old runs
replayable.

This script measures the gate from the user's side with the real binary, and also walks one edit of each
row of the typed-edit catalogue (N14a-17) and the lever and lock rules (N14a-06) through the command line.

## Scope

In: one script, its fixtures, assertions and log, and the tier run whose receipt the gate is recorded from. Out: the mechanisms (their beads); lineage
queries beyond what a patch answer returns.

## Technical approach

Script: `scripts/e2e/skel_patch.sh --seed <s>`. It creates the worked design in a scratch namespace and
keeps the `DesignId` of every version it creates in shell variables that the log also records. Every
`mutate` and `run` call carries an idempotency key derived from the seed and the step (`skel-patch-<s>-<step>`;
in the patch documents as `idempotency_key`, on `design.new`, `design.edit` and `sim.run` as `--key`), and two
calls that a step compares carry distinct keys, except where a step tests the replay of one key.

Gate receipt. Only the tier run of step 13 produces a receipt (convention 9; STD-E2E). The values measured from
the user's side (stale-parent trials and refusals, 100 of 100; race trials and single commits, 100 of 100; key
replays returning the same identity; the migration comparisons, differing digests 0 and largest
forward-kinematics and mass difference 0; the re-execution result, `reproduced`, chunk digests compared and
differing) are `metric` lines tagged `--gate GATE-SKEL-08` with their thresholds, under the commit, hardware
fingerprint and seed of the `start` line. The script writes no gate row. This bead is the gate's one recorder
(N14b-26: "N14a-29 records, from BD-059's battery"; BD-059's battery and N29ax-01's script measure at their
levels and write none): after a run in which all thirteen steps pass, a session that did not implement the patch
verb enters the row with `cargo run -p frob-conformance --example record_gate -- --gate GATE-SKEL-08 --receipt
<hash of step 13's receipt>`.

Logging. NDJSON to `target/e2e-logs/skel_patch/<utc-timestamp>.ndjson` with a transcript beside it. Every
line has `ts`, `script`, `bead: "N14a-29"` (set once at `e2e_init`; the subject of a step, BD-059, N14a-18 for
steps 10 to 12, N14a-17 for step 9, N14a-06 for steps 6 and 7, is named in the step's title), `step`, `event`, the exact command line, exit code, wall time, the envelope's `evidence`
block, `DesignId` before and after, `idempotent_replay`, the refusal payload (`code`, `pointer`, `observed`,
`required`, `retry`), digests where state is compared, and on failure the first differing field with the
paths of the patch file and of both answers. Steps 4 and 5 log a `metric` line per ten trials with counts.
The `summary` line gives assertions passed and failed and `gates: ["GATE-SKEL-08"]`.

## Acceptance criteria

- [ ] The script exists, is plain shell, seed-explicit and idempotent, and exits non-zero on any failure.
- [ ] Steps 1 to 13 pass on Linux and on macOS, step 11 included: it runs the re-execution path of N29ax-01 (a
      dependency), so no step is logged `partial`.
- [ ] The log carries the measured counts as gate-tagged metrics with the commit, the fingerprint and the seed,
      and the hash of step 13's receipt; the gate row of GATE-SKEL-08 is entered from that receipt with
      `record_gate` (above); the script itself writes no row.
- [ ] A patch call with no key anywhere (document and `--key` both absent) is `FROB-REF-805`, exit 3, and one
      with a `--key` different from the document's key is `FROB-REF-802`, exit 3 (BD-059's rule).
- [ ] With the planted defect "key binding as lookup-then-insert" the script fails at step 5 with two
      versions for one key; with "head moved without compare-and-swap" it fails at step 5 with two commits;
      with "operations stored one by one" it fails at step 6 with a half-patched version.
- [ ] With the planted migration that rewrites a quantity through binary64 the script fails at step 10 and
      names the differing section.
- [ ] A failing run's log names the seed, the trial index and the files needed to reproduce it.

## Test plan

### Unit tests

The script is the test. A shell self-test runs steps 1 to 3 against a binary with the key-binding defect and
checks the non-zero exit.

### End-to-end script and logging

As above: `scripts/e2e/skel_patch.sh`, driving `frob design patch`, `frob design edit` and `frob design
show`; logs under `target/e2e-logs/skel_patch/`.

### Known answers and negative controls

- KA-292: a stale parent refuses in 100 of 100 trials (`FROB-REF-112`); a repeated idempotency key returns
  the same `DesignId`; a schema migration leaves forward kinematics and mass properties bit-identical and old
  runs replayable (exact; tier G4).
- KA-286 through step 9: a payload swap that leaves the assembly inertia unchanged still appears in the
  computed invalidation set.
- Step 1 runs the real analyses it requires (A-11 of BD-103, A-13 of BD-104), not the `synthetic` stand-in
  that BD-059's own acceptance uses before they exist; the log names the analysis versions.
- Hand-checkable result of step 1: the edits sit under two `mirror` constructors, so both groups are
  unchanged (order 4 and order 2).
- Negative controls: the four planted defects of the acceptance list.
- Determinism lanes: the same patch on the same parent gives the same `DesignId` twice, with debug and
  release binaries, on Linux and macOS.

## Considerations

- The race step uses the daemon's simulation runtime with seeded interleavings where it exists; before that
  it uses two background processes and a barrier, and logs which mode it used. Only the seeded mode can
  claim "100 of 100" as a reproducible result.
- Exit code 7 (conflict) is not an error path to hide: the script asserts that the answer carries what a
  caller needs to rebase.
- The migration fixtures are test-only schema versions compiled under a feature; the script refuses to run
  them against a release binary that lacks the feature and logs `not run`.
