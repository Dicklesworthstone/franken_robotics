## Background

Edits are the morphisms of the design category. Each of the 22 typed edits of the catalogue (set a parameter, regear, swap an
actuator, add or remove a limb, move a mount, reshape, wrap in a mirror or radial constructor, add or remove a
closure, change fill, material, limits or contact law, swap a module, add, move or remove a sensor, retime,
add or move a payload, change the bus or battery, set a budget, declare or set a lever, assert a symmetry,
rename, migrate), and the 23rd row that N41p2-01 adds at M1 (extract a limb subterm to a module, with inline
as its inverse; 23 rows and 33 operation kinds in all), has preconditions, an inverse where one exists, a
declared effect on both symmetry groups, and a scope of invalidation. The glossary adds one more property: an edit is "a typed change to a design that
declares its correspondences and returns an invalidation set".

The correspondences are what policy inheritance is built on. Construction C-23 reads: an edit e: d → d′ is not
an isomorphism; "it declares a correspondence between parent and child frames, actuator roles, sensor
channels, contact roles and phase clocks, and that correspondence defines a transport" of the parent's policy
to the child. The inheritance bead (N23a-27) resolves the path of edits from the lineage graph and expects
that "each edit record supplies its correspondence (which parent roles map to which child roles; which are
deleted; which are new)". The edit record of `design.edit` (BD-058) holds the edit identifier, parent, child,
canonical operation, inverse, caller and idempotency key, and nothing about correspondence. As drafted,
inheritance can only assume the identity for parameter edits and must refuse every topology edit with
FROB-REF-531.

Design choice (DESIGN, with its reason). The correspondence is **computed by the edit engine as a deterministic
function of the parent's canonical design and the canonical operation**, and stored in the edit record; a
caller may override entries where the engine cannot know the intent (a swapped module's internals). Reason: for
most edits the correspondence is a fact of the edit (a regear touches one actuator role and leaves every name
alone), and a fact should not be typed by hand; computing it also means records written before this bead can
be upgraded by recomputation. Rejected alternatives: guessing correspondences by name or geometric similarity
on the consumer's side (a wrong guess looks like slow learning); requiring the caller to supply every entry
(nobody would, and the default would be "missing"). The record states geometry and identity, not learning: how
a role's features are transported (adjoint, dual, group element, zero, reset) is decided by the consumer from
these facts.

## Scope

In: the role model of a compiled design; the correspondence schema `frob.design.corr/1`; the rule that
produces it for each of the 33 kinds of the 23 catalogue rows (BD-058's kinds and N41p2-01's `extract-module`)
and for `resolve-sized`, the kind of row 24 that N31b-41 adds at M3,
including instance-scoped edits that split a constructor; caller overrides and their validation; completeness, inverse and
composition laws; storage in the edit record and in patches; `design.edit` and `design.diff` output; upgrade
of older records.

Out: transports of policy parameters, normalizers and recurrent state (N23a-27); the verb `train.inherit` and
its gate (BD-322); the invalidation set (BD-063, N28b-01); the symmetry effect (already in the record); the
edit engine itself (BD-058).

## Technical approach

**1. Roles (DESIGN).** A role is a typed path into the expanded design, stable under edits that do not touch
it:

| Kind | One role per | Path example |
|---|---|---|
| `frame` | body frame and named port frame | `leg.fl.thigh`, `torso#hip_fl` |
| `actuator` | actuated joint coordinate | `leg.fl.knee[0]` |
| `sensor` | channel of a sensor | `imu0/gyro.x`, `enc.leg.fl.knee/pos` |
| `contact` | end effector instance (foot, wheel, track, pad) | `leg.fl.foot` |
| `clock` | phase clock of a limb that carries a contact role | `leg.fl.foot/phase` |

`RobotModel::roles()` lists them in canonical order; the list is a compile product keyed by `DesignId`.

**2. Correspondence record.**

```rust
// DESIGN sketch; canonical JSON under "correspondence" in the edit record
pub struct CorrespondenceRecord { schema: "frob.design.corr/1", entries: Vec<Entry>, digest: Blake3 }
pub struct Entry { kind: RoleKind, from: Option<RolePath>, to: Option<RolePath>, relation: Relation,
                   origin: Origin /* computed | supplied */ }
pub enum Relation {
    Same,                                   // unchanged role, possibly under a new path (rename)
    Moved { parent_from_child: Se3 },       // the role's frame moved in its own parent frame (exact rationals)
    Scaled { factor: Rational },            // a length or radius the role is defined by was scaled
    Mirrored { element: GroupElem },        // image under a constructor's group element, with its parity
    Regeared { old: Rational, new: Rational },   // signed transmission ratio changed
    Recarded { old: CardId, new: CardId },  // actuator, sensor or contact card changed
    Retimed { old: Rational, new: Rational },    // rate in hertz changed
    Relawed { old: LawId, new: LawId },     // contact law changed
    Replaced,                               // a role of the same kind stands in its place; nothing else is known
    New, Deleted,                           // `from` or `to` is absent
}
```

**3. Completeness (checked at every edit).** Every role of the parent appears exactly once as `from` (or in a
`Deleted` entry) and every role of the child exactly once as `to` (or in a `New` entry); `from` and `to` of an
entry have the same kind. The engine can always complete the record (`Replaced`, `New` and `Deleted` are
always available), so an incomplete record is an engine defect and fails the edit before anything is written.

**4. Rule per edit (the computed default).**

| Edit | Entries that are not `Same` |
|---|---|
| `set-param`, `reshape` | `Moved` or `Scaled` for the frames whose placement in their parent frame depends on the parameter (a thigh length moves the knee joint frame along the thigh by the difference); descendants stay `Same` in their own parent frames |
| `regear` | `Regeared` on the actuator roles of the transmission; for a coupling matrix, on every coupled role with the old and new matrix rows |
| `swap-actuator` | `Recarded` on the actuator roles and on sensor roles the card owns (its encoder) |
| `add-limb` / `remove-limb` | `New` / `Deleted` for every role of the limb |
| `move-mount`, `move-sensor`, `move-payload` | `Moved` with the exact transform between old and new mount |
| `mirror` / `radial` (wrapping a limb) | the wrapped limb's roles map `Same` to the identity instance; the generated instances are `New` with `Mirrored { element }` naming their source |
| `mirror` / `radial` with `mode: unwrap` | the entry-wise inverse of `wrap`: the generated instances are `Deleted` |
| `mirror` / `radial` with `mode: fuse`, and the constructor split that precedes an instance-scoped edit | none: the split and the fused design compile to a bit-identical model (BD-058), so every role is `Same` under its instance path; the instance-scoped edit then contributes its own entries for the one image |
| `closure-add` / `closure-remove` | `New` / `Deleted` frame roles of the closure ports; actuator roles unchanged |
| `set-lever` | as `set-param` at the lever's path (a lever on a thigh length moves the knee joint frames) |
| `set-fill`, `set-material`, `set-limits`, `set-budget`, `declare-lever` (and its `remove: true`), `lock`, `unlock`, `assert-symmetry`, and `resolve-sized` (N31b-41's row 24, M3: it only sets fills to concrete walls) | none |
| `set-contact-law` | `Relawed` on the contact role; its clock role stays `Same` |
| `swap-module` | roles at ports with equal names in both port signatures map `Same` (or `Moved` if the port frame differs); internal roles are matched by equal relative path and kind when both modules declare the same internal names, otherwise `Deleted` and `New`; never matched by similarity |
| `add-sensor` / `remove-sensor` | `New` / `Deleted` sensor roles |
| `retime` | `Retimed` on the sensor or actuator roles of that clock |
| `add-payload` / `move-payload` with `remove: true` | `New` / `Deleted` frame roles |
| `set-bus` / `swap-battery` | none on roles (the bus is not a role); the record notes the change for consumers that read voltage |
| `rename` | `Same` with different `from` and `to` paths |
| `migrate` | `Same` for a certified meaning-preserving migration; otherwise the migration supplies the record |
| `extract-module` / its inverse `inline: true` | none: the `ModelId` is unchanged (N41p2-01), so every role is `Same` under the path the expanded instance tree gives it |

An edit applied under a constructor produces one entry per generated instance.

**5. Caller overrides.** `frob design edit … --correspond <kind>:<from>=<to>[,…]` replaces computed entries
(typically `Deleted` + `New` pairs after `swap-module` or after a remove-then-add) by a `Replaced` or `Same`
entry of origin `supplied`. Validation: both paths exist in parent and child, kinds agree, joint classes agree
for actuator roles, and no role is claimed twice; a violation is FROB-REF-101 (type mismatch) or FROB-REF-103
(unknown path), with the pointer. The supplied entries are carried in the operation's arguments (`correspond`),
so they are part of the canonical operation and enter the `edit_id` through it. `--correspond` is the input
`correspond` of `design.edit` that VERBS-design lists from M3 as this bead's (codes 101 and 103 in that row's
list), with the `correspondence` outputs of `design.edit` and `design.diff` below.

**6. Laws.** (i) *Identity*: an edit whose operation changes nothing yields all `Same`. (ii) *Inverse*: the
inverse edit's record is the entry-wise inverse (`Moved` with the inverse transform, `Regeared` swapped, `New`
and `Deleted` exchanged). (iii) *Composition*: along a path, entries compose role by role (transforms
multiply, group elements multiply, ratios chain, anything composed with `Replaced`, `New` or `Deleted` follows
the table in the crate documentation); the composition is associative. (iv) *Commuting edits* compose to the
same record in either order.

**7. Storage and surfaces.** The edit record gains `correspondence` with its digest. The `edit_id` stays a
function of (parent, canonical operation) alone, as BD-058's law requires: the computed entries are a pure
function of the two, and the supplied ones are inside the operation.
A patch (`frob.design.patch/1`) of several edits stores the composed record as well as each step's.
`frob design edit --json` returns it (output schema `frob.design.edit.out/1`, additive); `frob design diff A B
--json` returns the composed record along the lineage path from A to B, or `no lineage path`. A lineage record
written without the field (every record from M1 until this bead) is completed on read by recomputation from its
parent and operation (`origin: computed`), which is exact because the rule is a pure function; the stored row
is not rewritten and its `edit_id` does not move.

**8. Layout.** `crates/frob-model/src/roles.rs`; `crates/frob-design/src/edit/correspondence.rs`; the per-edit
rules beside each edit's implementation; fixtures `fixtures/design/edits/corr/*.json`.

## Acceptance criteria

- [ ] Every kind of the catalogue (the 33 of rows 1 to 23, and `resolve-sized` of row 24 when N31b-41's row is
      in the file, whose golden has only `Same` entries) has a rule and a golden correspondence on the reference quadruped (12
      actuator roles, 4 contact roles, 4 clock roles) or, where the quadruped does not exercise it, on the
      mobile-manipulator fixture.
- [ ] `set-param` thigh length 0.21 m → 0.24 m under the leg constructor: four `Moved` entries (one knee
      joint frame per leg) with a translation of 0.03 m along the thigh axis; every other entry `Same`.
- [ ] `regear` knee belt 1.55 → 1.8: four `Regeared { 31/20, 9/5 }` actuator entries (one per knee);
      nothing else changes.
- [ ] `add-limb` (a one-joint tail): entries `New` for two frames and one actuator role; `remove-limb` is
      its entry-wise inverse.
- [ ] `move-mount` hip 2 cm forward: one `Moved` entry with translation (0.02, 0, 0) m per affected mount.
- [ ] `rename` produces only `Same` entries with changed paths and no other relation. (That the child's first
      action under inheritance then equals the parent's is the consumer's zero-change law, asserted by N23a-27,
      which depends on this bead; it is not needed to close this one.)
- [ ] Completeness holds on 10⁴ random edit sequences from the open modular class's generator; inverse and
      composition laws hold on the same sequences.
- [ ] A supplied override that pairs a revolute actuator role with a prismatic one is refused
      (FROB-REF-101); one that names a missing path is refused (FROB-REF-103).
- [ ] A record written without the field is completed on read to the same digest as a freshly computed one,
      and its `edit_id` is unchanged; a computed record never changes an `edit_id` (BD-058's law holds on the
      generator's 10⁴ sequences).
- [ ] `set-lever` on a thigh-length lever gives the same entries as the equal `set-param`; `extract-module`, a
      constructor split and `fuse` give all `Same`.
- [ ] For each topology edit of the table (`add-limb`, `remove-limb`, `mirror`/`radial`, `closure-add`,
      `closure-remove`, `swap-module`, `add-sensor`, `remove-sensor`, `add-payload`) the record is complete and
      names every new and deleted role, which is what N23a-27 needs to build its map without FROB-REF-531; that
      bead (a dependent) asserts its own use of the records.

## Test plan

### Unit tests

`crates/frob-design/tests/edit_correspondence.rs`, `crates/frob-model/tests/roles.rs`:
- `roles_canonical_order_and_counts` (quadruped: 12, 4, 4; frames and sensor channels as compiled).
- one `corr_<edit>` test per edit kind against its golden file.
- `corr_complete_bijection` (property test); `corr_inverse_law`; `corr_composition_associative`;
  `corr_commuting_edits_agree` (thigh length and knee gearing in both orders).
- `corr_under_constructor_fanout`: an edit under `mirror` yields entries for both instances.
- `corr_swap_module_ports_by_name`: equal port names map `Same`; differing internals are `Deleted` and `New`.
- `corr_override_validated`; `corr_override_changes_edit_id`.
- `corr_upgrade_on_read`; `edit_id_independent_of_computed_record`.
- `corr_set_lever_as_set_param`; `corr_extract_module_all_same`; `corr_split_and_fuse_all_same` (an
  instance-scoped `set-param` on one image: the split contributes nothing, the edit one `Moved` entry).
- `corr_moved_exact`: transforms are exact rationals for rational parameters (no floating point in the
  record).

### End-to-end script and logging

`scripts/e2e/design_edit_correspondence.sh` (sources the STD-E2E helper; NDJSON to
`target/e2e-logs/design_edit_correspondence/<utc>.ndjson` with a transcript): `frob --json design edit` for
set-param, regear, add-limb, move-mount, rename and swap-module on the quadruped fixture; `frob --json design
diff` across the three-edit chain; the two refused overrides; round trips that apply each answer's returned
`inverse` operation with `frob --json design edit` (with `design patch` for a two-operation inverse) and
assert the parent's `DesignId` and the entry-wise inverse record. Every `design edit` and `design patch` call is
a mutate and carries its own key (`--key corr-<seed>-<step>`, or the patch document's `idempotency_key`); an
inverse carries a key distinct from its forward edit's, so it is applied and not answered with the forward
edit's stored result.
Lines carry `ts`, `script`, `bead`, `step`, `event`, command, exit code, wall time, the evidence block (claim,
class, tier `static`, determinism, identities); `metric` lines with counts of entries by relation against the
golden counts; the record digest and `edit_id`; `refusal` lines with code, pointer and first repair; on
failure the first differing entry. `summary`: assertions passed and failed; `gates: []`.

### Known answers and negative controls

Known answers: the entry counts and values of the acceptance list (0.03 m; 31/20 → 9/5; (0.02, 0, 0) m).
Negative controls: a rule that matches roles by position in the role list (fails after a joint re-ordering:
the knee and hip entries swap); a rule that reports a moved mount as `Same` (the consumer's twist and wrench
transport test on the moved-mount fixture fails downstream; here the golden differs); a correspondence that
drops a role (the bijection test); composition that multiplies transforms in the wrong order (the chain
through two `move-mount` edits about different axes). Determinism: D0; record bytes identical twice, in debug
and release, on both host platforms.

## Considerations

- `Replaced` is honest ignorance: a consumer resets what it maps. Overuse (a module swap between two legs
  with different internal names) makes inheritance no better than a fresh start, and the record shows why.
- Clock roles follow contact roles by construction; a phase offset between mirrored limbs is a property of a
  gait, not of the design, and is not recorded here.
- The record grows with the number of roles (hundreds for a humanoid); it is stored once per edit and
  composed on demand.
- If the inheritance experiment is not funded (its pilot's falsifier holds), the correspondence still serves
  `design.diff` and the reuse of analyses by implication.
