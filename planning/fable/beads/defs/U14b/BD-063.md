## Background

Skeleton is the subsystem that owns what a robot is before anything moves. Its compiler (`frob-model`, layer 2,
tier Solid) turns a design term into an immutable `RobotModel`. A design is a tree of components and constructors
(`attach`, `chain`, `serial`, `mirror`, `radial`, `scale`, `replace`, `closure`, `use`), and an agent in the studio
loop edits it many times an hour. Two things must then be true. First, an edit must recompile only what it touched,
so that the time from an edit to the first simulated step stays short. Second, and more important, every derived
product that the edit made stale must be named, so that no analysis, kernel, certificate or verdict computed for
the old design is silently served for the new one.

The plan's decision ADR-SKEL-09 fixes how staleness is found: every compile product records the fields it read,
and invalidation after an edit is computed from those records, not from a hand-kept table. Reason: a hand-kept
"edit X invalidates products Y" table is correct only until someone adds a field or a product; a recorded read set
is correct by construction and can be tested by mutation. Rejected alternative: whole-model recompilation on every
edit (it is the named fallback and is always available with `--no-memo`); rejected alternative: a static dependency
table per edit kind (the table of typed edits predicts scopes, and this bead tests the prediction against the
recorded sets, but the table is never the authority).

The stated ceiling of the benefit, written before any measurement: the gain is the share of an agent's
edit-to-first-step time spent recompiling unchanged subterms, which is small once a rollout takes seconds. The memo
graph is kept for correctness of invalidation first and for latency second. Construction C-12 (a robot is a
composition over typed ports, with five functors giving a design its meaning) names the paper-scale pilot this
bead's tests reproduce: a 64-edit sequence over one modular quadruped, counting recomputed subterms per edit;
falsifier: one stale result after an edit; fallback: whole-model recompilation on every edit.

Terms. `DesignId`: BLAKE3 hash of the canonical JSON bytes of a design (`frob.design/1`). `ModelId`: content hash
of the compiled `RobotModel`. Card: a versioned actuator, battery, transmission, sensor or material record
(`.fcard`). Functor: a structure-preserving map from design terms to a meaning (frames, geometry, channels,
budgets, groups). Γ_mech and Γ_obs: the mechanical symmetry group of the body and its subgroup that also preserves
sensors, payload and task.

## Scope

In: the memo graph over compile stages in `frob-model`; influence records at field granularity; the invalidation
set of a typed edit, returned to `design.edit` and `design.patch`; the property tests of the functor laws and of
incremental-equals-full; the GATE-SKEL-02 measurement.

Out: the functors themselves (kinematic: BD-061; geometric and inertial: BD-062; binding, budget, symmetry: their
own beads); typed edits and their preconditions (BD-058); patches, stale-parent and idempotency (BD-059); module
substitution and the leaf-local rule (BD-077); the memo graph in front of analyses, controllers, step plans and
episodes with shadow recomputation (BD-111). Rollouts are never memoized here.

## Technical approach

**Pipeline and memo keys (DESIGN).** `Design` → elaborate → validate → five functors → assemble → four lowerings.

| Stage | Product | Memo key |
|---|---|---|
| Parse and canonicalize, from either view (JSON or S-expression) | Typed term | Hash of the input bytes |
| Elaborate (expand constructors, import modules, resolve parameters) | Expanded tree with resolved parameters | Subterm hash with the digests of the modules and cards it names |
| Validate (ports, units, bounds, fills) | The same tree, or a refusal | Subterm hash |
| Kinematic functor | Frames, screws, tree, closures | Hash of the subtree's mechanical fields |
| Geometric and inertial functor | Collision primitives; volume moments by fill; pseudo-inertia | Body hash with the material card's version |
| Binding functor | Actuator and sensor channels; joint row descriptors | Joint hash with the card versions |
| Budget functor | Budget relations and per-subtree summaries | Subtree summary hashes |
| Symmetry functor | Γ_mech, Γ_obs, representations, breakers | Canonical tree form with the digest of sensors, payloads and task terms |
| Assemble and lower | `RobotModel`, `ModelId`, the four lowerings | `ModelId` with the compiler version |

The four lowerings are: (1) an `fs_mbd::articulated::ArticulatedModel` for the referee tier, through the airlock
crate `frob-fsim`; (2) packed structure-of-arrays buffers with depth levels and a path table for sparse Jacobians;
(3) analysis views (symbolic kinematics for one limb, the leg-permutation group, the budget graph); (4) a variant
record inside a size bucket. This bead keys all four; lowerings (2) and (4) are produced by later beads and plug
into the same key scheme.

**Influence records (DESIGN).**

```rust
pub struct FieldPath(Vec<PathSeg>);                 // e.g. /limbs/of/of/chain/1/body/fill
pub struct ReadSet(BTreeSet<FieldPath>);            // sorted: iteration order never depends on a hash map
pub struct Product<T> { value: T, digest: Blake3, key: MemoKey, reads: ReadSet }
pub struct InvalidationEntry { product: ProductId, kind: ProductKind, invalidated_by: FieldPath }
pub struct EditOutcome { design: DesignId, model: ModelId,
                         invalidated: Vec<InvalidationEntry>, reused: Vec<ProductId> }
```

1. No stage receives the raw term. Each receives a `Tracked<'_, Term>` view whose accessors append the accessed
   path to the stage's `ReadSet`. Module privacy makes an untracked read a compile error, so the record is a
   superset of the reads by construction (PO-SKEL-03), and the mutation test below checks that the construction
   was not bypassed.
2. A typed edit carries a write set: the paths it changes (for `set-param` one leaf; for `mirror` a whole subterm).
3. The invalidation set of an edit is the set of products whose `ReadSet` intersects the write set, closed under
   the product dependency graph (a product that consumed an invalidated product is invalidated). Each entry
   names the first field, in path order, that invalidated it.
4. Every product not in the set is served from the memo graph by key. Products are stored content-addressed, so
   a subterm repeated under `mirror` or `radial` is compiled once.
5. `design.edit` and `design.patch` return `EditOutcome`: the new `DesignId`, the `ModelId`, the invalidated
   products with the invalidating field, and the reused products. Nothing is modified in place.

**Consequences that must hold.** Renaming a body rebuilds nothing, because no mechanical product reads names.
Moving a camera changes sensor extrinsics, coverage products and Γ_obs, and no kinematic or inertial product. Two
designs with different `DesignId` may therefore share one `ModelId`, and the model is still determined by the
design, the compiler version and the card versions (INV-SKEL-01).

**What the memo graph covers.** Compile products, static analyses, step plans, derived kernels and scene compiles.
It does not cover rollouts: the share of a rollout reusable exactly across a mass or geometry edit was assessed at
about a tenth of its compute or less (HYPOTHESIS until our own dependency profile is measured).

**Determinism.** Class D0: a product is a pure function of its key. Bit-identical across runs, worker counts,
debug and release, Linux and macOS. No wall clock, no address, no hash-map order enters a product or a key.

**Layout.** `crates/frob-model/src/memo/{key.rs, reads.rs, graph.rs, invalidate.rs}`; `tests/incremental.rs`,
`tests/functor_laws.rs`, `tests/influence.rs`. Ledger: each compile writes a record `frob.compile/1` with the
keys served, the keys computed and the invalidation set.

## Acceptance criteria

- [ ] GATE-SKEL-02 (TARGET): the functor laws and INV-SKEL-02 hold on 10⁴ random designs and edits drawn by the
      generator of N14b-01, with the measured counts recorded in `registries/gates.toml`.
- [ ] INV-SKEL-01: compiling one `DesignId` twice, and on Linux and macOS, with the same compiler and card
      versions yields the same `ModelId` and bit-identical products.
- [ ] INV-SKEL-02: for every sampled (design, edit) pair, incremental compilation of the edited design equals full
      compilation from an empty memo graph, bit for bit, product by product.
- [ ] INV-SKEL-06: the invalidation set contains every product that differs after a full recompile, and every
      product outside it is bit-identical.
- [ ] PO-SKEL-03: mutating any field outside a product's record leaves the product bit-identical.
- [ ] `design.edit` returns the invalidation set with the invalidating field for each entry, through
      `frob --json`.
- [ ] The three planted defects below are each caught; `--no-memo` reproduces every product bit for bit.
- [ ] `crates/frob-model/CONTRACT.md` has its ten sections and states determinism class D0 for compile products.
- [ ] Cancellation of a compile leaves no partial product in the memo graph (request, drain, finalize).

## Test plan

### Unit tests

- `memo_key_changes_with_each_declared_input`: for each stage, perturb each declared key input (subterm hash,
  module digest, card version, compiler version) and assert the key changes.
- `rename_rebuilds_nothing`: `rename torso → chassis` on `quad-a`; expected invalidation set empty; `ModelId`
  unchanged; `DesignId` changed.
- `move_camera_invalidates_only_sensing`: `move-sensor lidar` by 0.04 m in z; expected invalidated kinds exactly
  {Binding(sensor extrinsics), Symmetry(Γ_obs), coverage views}; kinematic and inertial digests unchanged.
- `set_fill_invalidates_inertia_and_sums`: thigh `solid` → `{shell: 2 mm}`; expected: that body's inertial
  product, the mass roll-up path to the root, budgets; sibling legs' kinematic products reused.
- `mirror_compiles_subterm_once`: the nested `mirror(xz, mirror(yz, leg))` design computes one leg product and
  serves three hits.
- `tracked_view_records_every_read` (PO-SKEL-03): for each product of the eighteen archetypes available at the
  time, mutate every field outside its record; assert bit identity.
- `functor_commutes_with_attach`, `…_with_mirror`, `…_with_radial`, `…_with_use`: for each of the five functors,
  F(compose(a, b)) = compose(F(a), F(b)) on random terms.
- `sixty_four_edit_sequence` (the C-12 pilot): 64 typed edits on one modular quadruped; after each, incremental
  equals full; the count of recomputed subterms per edit is logged.

### End-to-end script and logging

`scripts/e2e/skel_incremental_compile.sh`. Runs `frob design new --template quad-mammal`, then a fixed sequence of
`frob design edit … --json` calls (set-param, set-fill, rename, move-sensor, swap-actuator, add-payload), and after
each compares `frob design show --products --json` against the same design compiled with `--no-memo`. Asserts
digest equality per product and the expected invalidation set. Logs one NDJSON line per command with `ts`,
`script`, `bead: "BD-063"`, `step`, `event`, the command line, exit code, wall time, the envelope's `evidence`
block, the count of products served and computed, the invalidation set, and on failure the first differing product
with both digests and the paths of the two compile records. A final `summary` line gives assertions passed and
failed and `gates: ["GATE-SKEL-02"]`.

### Known answers and negative controls

- KA-287: incremental compilation equals full compilation bit for bit on 10⁴ random designs and edits (exact,
  tier G3, host). The appendix states no negative control for it; this bead registers the three below.
- KA-289: mutation outside a record leaves the product bit-identical; the invalidation set contains every
  product that differs after a full recompile, on 10⁴ random edits.
- KA-286 (first rejection fixture, passive part): swapping a payload that leaves the assembly inertia unchanged
  must be caught by INV-SKEL-06.
- Planted defect 1: the geometric functor reads `material` through an untracked path; `set-material` then serves a
  stale inertia. The gate must fail.
- Planted defect 2: the binding functor's key omits the card version; a card bump serves the old channel.
- Planted defect 3: a product built from a `HashMap` iteration; debug and release digests differ.
- Metamorphic: applying an edit and its inverse returns every product digest to its original value; two commuting
  edits applied in either order give identical products.
- Determinism lanes: twice on one machine; 1, 8 and 36 workers; debug and release; Linux and macOS: all D0.

## Considerations

- KILL-SKEL-SUBST (decided at M1 by the substitution bead) reads this mechanism: if any reused product differs
  from its recompiled value after one repair cycle, every substitution becomes global and the memo graph keeps
  subterm reuse by content hash only. That fallback is this bead with step 3 widened to "everything downstream
  of the edited subterm".
- Read tracking has a cost on every field access; it is paid at compile time only. TARGET for the whole of
  preflight stage 1 (the compile) is 100 ms at the 95th percentile on any archetype with an empty memo graph.
- Risk: a read set that is too coarse (a whole block instead of a field) is safe and slow; one that is too fine
  is impossible by construction. Coarseness is measured as the mean invalidated share per edit kind and logged.
- The typed-edit table predicts invalidation scopes (for example `set-budget`: stage 6 only; `rename`: none). A
  disagreement between the prediction and the recorded set is a finding against the table, never against the set.
- A memoized product in the evidence closure of a live claim is pinned by Chronicle, not by this cache; the cache
  can be deleted at any time.
