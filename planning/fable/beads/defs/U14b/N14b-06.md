## Background

The archetype catalog is a user-visible capability: an agent lists templates, instantiates one, checks it and
simulates it under a synthesized baseline controller. Two gates are measured on that running path. GATE-SKEL-03:
each of the eighteen archetypes compiles, passes stages 1 to 6 of `design check` with no refusal, has the
symmetry groups on file, and stands or rolls under its baseline controller at the milestone the standing gate
gives for it. GATE-SKEL-07 (mass clause): the mass of each archetype lies within 15% of the mass on file for its
reference robot where one exists. Both close in parts: rows for the first four archetypes at M1, the whole at M3.

Unit tests inside the crates check each piece. This bead is the script that checks the pieces together through
the real `frob` binary, the way an agent would use them, and that produces the log from which the gate rows are
recorded. It is written once at M1 for the first four archetypes and is data-driven, so that M3 adds rows and no
code.

## Scope

Two scripts touch every archetype, and they divide the work so that no expectation is pinned twice. The zoo
script `scripts/e2e/zoo_goldens.sh` (NEG-31, a dependency) checks each archetype's default instance against
the zoo's expectation file: the pinned `DesignId` and byte-identity of the instance, the morphology counts, the
symmetry groups with their breakers, stages 1 to 6 with their reported values, the known answers that have a
verb, and the control variants the zoo files list. This bead's script runs that one as its first stage and
adds what the zoo does not cover: the catalog as a capability (the listing, presets and sensor options, the
two views, the controller, the standing rows, the mass window of the gate) and four cross-cutting controls.

In: `scripts/e2e/skel_archetypes.sh`, its expectation table `scripts/e2e/data/archetypes.toml` (presets,
options and capability rows only; for a default instance it holds the archetype's name and reads `DesignId`,
`n_v` and the groups from the zoo's expectation file through the zoo loader, NEG-30), the `fixture:<name>` form of `sim.run`'s `--controller` input with its loader and the
`zero-gain` fixture, and the log from which
the gate rows are recorded at M1 and again at M3. GATE-SKEL-03 and GATE-SKEL-07 each have one record with a
part at M1 and a part at M3: a part is entered by the gate recorder from the receipt of the gate's tier run,
which cites this script's log, and that log contains the zoo stage's summary; the zoo script writes no gate
record. This bead closes at M1 with the M1 parts. The M3 run of the script over eighteen entries is BD-246's,
which enters the M3 part of GATE-SKEL-07; the M3 part of GATE-SKEL-03 is entered by BD-247, from its own run of
this script with the standing and rolling rows of all eighteen present. Out: the zoo script, its per-archetype golden assertions and the zoo's
expectation files (NEG-31; the `ZOO-…` beads); the templates (BD-109, N14b-02 to -04), the checks (BD-110),
the controllers (BD-116, BD-117, BD-247) and the gate measurement over planted asymmetries (BD-246).

## Technical approach

**Expectation table.** One entry per archetype and preset: `name`, `preset`, `available_from` (M1 or M3),
`n_v`, `gamma_mech`, `gamma_obs_with` (an optional sensor option and the group it must leave), `mass_window_kg`
(from the reference's mass on file, or absent), `class` (the controller class), `standing_row` (the milestone and
tiers at which it is due), `expected_refusal` for named failing presets (for example `quad-sprawl@hot` → 132 at
stage 6), and the pinned `DesignId`. One source per value (DESIGN, the same statement in NEG-31): for the
default instance of an archetype the fields `n_v`, `gamma_mech` and `DesignId` are not written in this table;
the entry says `from = "zoo"` and the script reads them from `zoo/<name>` through the zoo loader, so a golden
exists in one file. The table pins those fields itself only for presets and options that the zoo has no
instance of (`humanoid@g1`, `quad-sprawl@hot`, a sensor option). `mass_window_kg` is the gate's window around
the reference robot's mass on file and is not a golden of the compiled mass, so it stays here.

**Preset rows of GATE-SKEL-07 (M1).** One entry per preset of BD-109, each with its reference and its window,
the window being ±15% around the reference's `mass_on_file` with source and date: `quad-mammal@go2` (the
preset named first in the manifest; a preset is never the zoo's default instance), `@go1`, `@a1`, `@anymal-b`,
`@anymal-c`, `@spot`; `humanoid@g1` (28.339 to 38.341 kg around 33.34014202 kg) and `@h1`;
`diff-drive@stretch3`; `mecanum@tiago`. The reference value is `mass_on_file.value_kg` in
`assets/robots/<name>/manifest.toml` (schema `frob.robot.asset/1`): the exact decimal sum of the body masses of
the model file at the commit pinned in `tools/oracle/models.toml` (BD-067), computed and written with its
source and read date by the asset validation that each reference-robot bead runs (ROBOT-go2 and its nine
siblings, dependencies of this bead). The script reads it there, recomputes the window, and fails if the table's
window disagrees or if the `mass_on_file` that `frob design templates --json` reports for that reference (the
figure BD-109's own mass row used) is a different number, so the three places that state the mass are held to
one value. A preset whose reference asset is absent or carries no mass logs its row `pending` with the reason,
never a pass. The M3 archetypes add `biped-point@cassie` and the two `mobile-manipulator` presets; their
reference-robot beads (ROBOT-cassie, ROBOT-iiwa7) are M3 and are dependencies of BD-246, under which those rows
are run.

**Steps, for each entry available in the build.**

0. Golden stage: run `scripts/e2e/zoo_goldens.sh --milestone <Mn>` (NEG-31) and fail if it fails; its summary
   (archetypes passed, failed and not run; expectations passed and failed; controls caught) is copied into this
   script's log. For default instances this stage is what asserts steps 2 to 5 below; the script repeats those
   steps itself only for the presets and options of its own table.
1. `frob design templates --json` once; assert eighteen entries and the `available` set for the milestone.
2. `frob design new <name> --template <archetype> [--preset <ref>] --key <key> --json` (the idempotency key the
   verb requires, derived as stated below); assert the pinned `DesignId`.
3. `frob design show <id> --json`; assert `n_v`, the compiled mass inside `mass_window_kg` when present.
4. `frob design check <id> --stages 1-6 --json`; assert exit 0 or 2 with no refusal, or the entry's
   `expected_refusal` with its stage; record per-stage wall times.
5. `frob analyze symmetry <id> --json`; assert Γ_mech; with the sensor option, assert Γ_obs and the breaker.
6. `frob design view <id> --as sexpr` then `--as json`; assert the same `DesignId` (the two views agree).
7. `frob control synth <id> --key <key> --json` (a `run` verb); assert the class and one of the three outcomes.
8. Where `standing_row` is due: `frob sim run <id> --tier <tier> --task stand-10s --seed <s> --key <key> --json`
   and `frob sim run <id> --tier <tier> --task traverse-5m-flat --state estimated --seed <s> --key <key> --json`
   (the tasks BD-125 registers, taken on the referee at M1 by the `--task` input of N16ap4-01); assert 10 s
   without a fall and at least 5 m.
9. Repeat steps 2 to 5 in a second process under a second design name and with keys of the second pass, so that
   no call returns the first pass's stored receipt, and compare digests (determinism within one machine); the
   cross-platform comparison reads the pinned `DesignId` values.

**Negative controls run by the script on every execution.** (a) `quad-mammal` instantiated with `--set
sensor_option=forward-lidar` (BD-109's template parameter) and an `assert-symmetry` edit to `assert_obs: C2xC2`
must refuse at stage 5 of `design check` with FROB-REF-109 and name the lidar mount; (b) `mecanum` with all roller angles
equal must fail stage 4 with FROB-REF-118; (c) a template copy with its torso fill deleted must refuse with
FROB-REF-105; (d) a zero-gain controller must fail `stand-10s` for a legged archetype: `frob sim run <id> --tier
referee --task stand-10s --controller fixture:zero-gain --seed 1 --key <key> --json`, where `fixture:zero-gain` is a
conformance fixture this bead registers in `fixtures/controllers/zero-gain.toml` (the synthesized baseline's
class and structure with every derived gain set to zero; never a product controller). If any control passes, the
script fails whatever else it measured.

**The `fixture:<name>` controller form (this bead's, VERBS-sim's `--controller` row).** N16ap4-01's
`--controller` input dispatches the prefix `fixture:` to this bead's loader in `frob-control`. DESIGN: `<name>`
(letters, digits, hyphens) resolves to `fixtures/controllers/<name>.toml`, present in every build, debug and
release; the file carries `schema = "frob.controller.fixture/1"` and a `kind` with a builder in `frob-control`.
This bead registers the kind `baseline-scaled` (the design's synthesized baseline for the task, class and
structure kept, every derived gain multiplied by the file's `gain_scale`, 0 for `zero-gain`); a bead that
registers a fixture controller of another kind adds its builder with it. The file's canonical bytes enter the
`ControllerId`. No file of that name, a file that fails the schema, or a kind with no builder in the build is
`FROB-REF-802` (`pointer` `/controller`).

**Idempotence and seeds.** Each run uses a fresh namespace named from the run's timestamp, explicit seeds for
every `sim run`, and idempotency keys derived from (script, run namespace, step, archetype or preset, pass), so a
re-run after an interruption neither duplicates designs nor reuses a stale one, and the two passes of step 9
never share a key.

## Acceptance criteria

- [ ] At M1 the script passes for `quad-mammal`, `humanoid`, `diff-drive` and `mecanum`, and the M1 parts of
      GATE-SKEL-03 and GATE-SKEL-07 (the ten preset mass rows above, each against its window) are recorded with
      measured values.
- [ ] Each preset's window equals ±15% of the `mass_on_file` in its reference asset; a disagreement between the
      table and the asset, or between the asset and the mass `design templates` reports for that reference,
      fails the run, and a missing reference mass is `pending`, never `passed`.
- [ ] The script is data-driven: at M1 the fourteen entries with `available_from = "M3"` are logged `not run`
      with that reason and counted in the summary, never as passed, and an entry added to a copy of the table
      is run with no change to the script. The M3 run over eighteen entries and the gates' M3 parts are not
      this M1 bead's to close: BD-246 runs the script at M3 and enters the M3 part of GATE-SKEL-07, and BD-247
      enters the M3 part of GATE-SKEL-03 with the standing and rolling rows, the tracked and hybrid ones being
      logged as due at M4.
- [ ] Gate parts are recorded through the gate recorder (N38b-19) from the receipt of the gates' tier run,
      `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers --features
      gauntlet-mutations -- GATE-SKEL-03` (and `-- GATE-SKEL-07`), which drives this script's table and catches
      the four controls in the same run (`cargo run -p frob-conformance --example record_gate -- --gate <id>
      --receipt <hash> --part M1`; the same form with `--part M3` is used under BD-246 for GATE-SKEL-07 and
      under BD-247 for GATE-SKEL-03); this script's log is the evidence the receipt cites.
- [ ] All four negative controls are caught on every run.
- [ ] The script exits non-zero on any failed assertion, is idempotent, and names every seed it uses.
- [ ] The log contains no imported robot's private data and no text from an imported model outside an untrusted
      field.

## Test plan

### Unit tests

The script's own helpers are tested in `scripts/e2e/tests/`: `table_parses`, `window_check` (28.339 ≤ m ≤ 38.341
for `humanoid@g1`), `group_compare` (C2xC2 equals C2×C2 under the canonical spelling), and
`control_must_fail_wrapper` (a control that passes makes the wrapper return non-zero), `preset_windows_from_assets`
(each of the ten windows recomputed from its reference asset equals the table's; a table window off by 1% fails;
a missing asset mass gives `pending`; a `design templates` mass that differs from the asset's fails), and
`table_row_added_runs` (a copy of the table with one more available entry makes the loop run that entry with
no change to the script; an entry with `available_from = "M3"` at M1 is logged `not run` and is not counted as
passed). The loader of the `fixture:` form is tested in `frob-control` (`cargo test -p frob-control
fixture_controller_form`): `fixture:zero-gain` on `quad-mammal` resolves and gives a `ControllerId` different
from `baseline`'s for the same design and task; `fixture:no-such`, a file without the schema line and a file whose
`kind` has no builder are each 802 with `pointer` `/controller`.

### End-to-end script and logging

`scripts/e2e/skel_archetypes.sh`, sourcing the shared helper of STD-E2E and writing
`target/e2e-logs/skel_archetypes/<utc-timestamp>.ndjson` with a transcript beside it. Every line has `ts`,
`script`, `bead: "N14b-06"`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed), measured values with units and thresholds (mass in kg against its window; standing time
against 10 s; distance against 5 m; per-stage time against its budget), digests where state is compared, and on
failure the first differing value and the artifact paths needed to reproduce. The final `summary` line gives
assertions passed and failed, controls caught, and the gates touched.

### Known answers and negative controls

- KA-270 (Γ_mech as built), KA-276 (the refused symmetry declaration), KA-268 (parallel-roller mecanum),
  KA-261 context (no default fill): the four controls above are their running forms.
- Determinism lanes exercised: twice on one machine; debug and release builds of `frob`; the pinned identities
  for Linux and macOS.

## Considerations

- The script is the evidence for gate rows, so the recording session must not have implemented the
  archetypes or the checks (the recorder refuses `self-certified`).
- Runtime: stages 1 to 6 are budgeted at 2 s at the 95th percentile per archetype; the standing runs dominate.
  The script accepts `--only <name>` and `--skip-sim` for development and records which options were used; a
  gate row is recorded only from a run with no option.
- When a standing row cannot run because a contact law or a tier is absent, the script logs `not run` with the
  reason; `not run` is never counted as a pass.
