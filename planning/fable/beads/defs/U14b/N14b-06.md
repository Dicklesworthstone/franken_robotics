## Background

The archetype catalog is a user-visible capability: an agent lists templates, instantiates one, checks it and
simulates it under a synthesized baseline controller. Two gates are measured on that running path. GATE-SKEL-03:
each of the eighteen archetypes compiles, passes stages 1 to 6 of `design check` with no refusal, has the
symmetry groups on file, and stands or rolls under its baseline controller at the milestone the standing gate
gives for it. GATE-SKEL-07 (mass clause): the mass of each archetype lies within 15% of the mass on file for its
reference robot where one exists. Both close in parts: rows for the first four archetypes at M1, the whole at M3.

Unit tests inside the crates check each piece. This bead is the script that checks the pieces together through
the real `frob` binary, the way an agent would use them, and that produces the log from which the gate rows are
recorded. It is written once at M1 for the first four archetypes and is data-driven, so that M3 adds rows and no
code.

## Scope

In: `scripts/e2e/skel_archetypes.sh`, its expectation table `scripts/e2e/data/archetypes.toml`, and the gate rows
it records at M1 and again at M3. Out: the templates (BD-109, N14b-02 to -04), the checks (BD-110), the
controllers (BD-116, BD-117, BD-247) and the gate measurement over planted asymmetries (BD-246).

## Technical approach

**Expectation table.** One entry per archetype and preset: `name`, `preset`, `available_from` (M1 or M3),
`n_v`, `gamma_mech`, `gamma_obs_with` (an optional sensor option and the group it must leave), `mass_window_kg`
(from the reference's mass on file, or absent), `class` (the controller class), `standing_row` (the milestone and
tiers at which it is due), `expected_refusal` for named failing presets (for example `quad-sprawl@hot` → 132 at
stage 6), and the pinned `DesignId`.

**Steps, for each entry available in the build.**

1. `frob design templates --json` once; assert eighteen entries and the `available` set for the milestone.
2. `frob design new --template <name> [--preset <ref>] --json`; assert the pinned `DesignId`.
3. `frob design show <id> --json`; assert `n_v`, the compiled mass inside `mass_window_kg` when present.
4. `frob design check <id> --stages 1-6 --json`; assert exit 0 or 2 with no refusal, or the entry's
   `expected_refusal` with its stage; record per-stage wall times.
5. `frob analyze symmetry <id> --json`; assert Γ_mech; with the sensor option, assert Γ_obs and the breaker.
6. `frob design view <id> --as sexpr` then `--as json`; assert the same `DesignId` (the two views agree).
7. `frob control synth <id> --json`; assert the class and one of the three outcomes.
8. Where `standing_row` is due: `frob sim run --tier <tier> --task stand-10s` and `--task traverse-5m --state
   estimated`; assert 10 s without a fall and at least 5 m.
9. Repeat steps 2 to 5 in a second process and compare digests (determinism within one machine); the
   cross-platform comparison reads the pinned `DesignId` values.

**Negative controls run by the script on every execution.** (a) `quad-mammal --with forward-lidar` with
`assert_obs: C2xC2` must refuse with FROB-REF-109 and name the lidar mount; (b) `mecanum` with all roller angles
equal must fail stage 4 with FROB-REF-118; (c) a template copy with its torso fill deleted must refuse with
FROB-REF-105; (d) a zero-gain controller must fail `stand-10s` for a legged archetype. If any control passes,
the script fails whatever else it measured.

**Idempotence and seeds.** Each run uses a fresh namespace named from the run's timestamp, explicit seeds for
every `sim run`, and idempotency keys derived from (script, step, archetype), so a re-run after an interruption
neither duplicates designs nor reuses a stale one.

## Acceptance criteria

- [ ] At M1 the script passes for `quad-mammal`, `humanoid`, `diff-drive` and `mecanum`, and the M1 rows of
      GATE-SKEL-03 and the humanoid row of GATE-SKEL-07 are recorded from its log with measured values.
- [ ] At M3 the same script, with the table extended to eighteen entries, passes, and the gates' remaining rows
      are recorded; the tracked and hybrid standing rows are logged as due at M4.
- [ ] All four negative controls are caught on every run.
- [ ] The script exits non-zero on any failed assertion, is idempotent, and names every seed it uses.
- [ ] The log contains no imported robot's private data and no text from an imported model outside an untrusted
      field.

## Test plan

### Unit tests

The script's own helpers are tested in `scripts/e2e/tests/`: `table_parses`, `window_check` (28.339 ≤ m ≤ 38.341
for `humanoid@g1`), `group_compare` (C2xC2 equals C2×C2 under the canonical spelling), and
`control_must_fail_wrapper` (a control that passes makes the wrapper return non-zero).

### End-to-end script and logging

`scripts/e2e/skel_archetypes.sh`, sourcing the shared helper of STD-E2E and writing
`target/e2e-logs/skel_archetypes/<utc-timestamp>.ndjson` with a transcript beside it. Every line has `ts`,
`script`, `bead: "N14b-06"`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed), measured values with units and thresholds (mass in kg against its window; standing time
against 10 s; distance against 5 m; per-stage time against its budget), digests where state is compared, and on
failure the first differing value and the artifact paths needed to reproduce. The final `summary` line gives
assertions passed and failed, controls caught, and the gates touched.

### Known answers and negative controls

- KA-270 (Γ_mech as built), KA-276 (the refused symmetry declaration), KA-268 (parallel-roller mecanum),
  KA-261 context (no default fill): the four controls above are their running forms.
- Determinism lanes exercised: twice on one machine; debug and release builds of `frob`; the pinned identities
  for Linux and macOS.

## Considerations

- The script is the evidence for gate rows, so it must be run by a session that did not implement the
  archetypes or the checks when a row is recorded.
- Runtime: stages 1 to 6 are budgeted at 2 s at the 95th percentile per archetype; the standing runs dominate.
  The script accepts `--only <name>` and `--skip-sim` for development and records which options were used; a
  gate row is recorded only from a run with no option.
- When a standing row cannot run because a contact law or a tier is absent, the script logs `not run` with the
  reason; `not run` is never counted as a pass.
