## Background

`frob design check` is the verb an agent runs after every edit. It runs up to eight preflight stages in a fixed
order, stops at the first refusal unless asked for all findings, and returns either a pass with findings or a
refusal with ranked repairs expressed as typed edits, which appear in the envelope as `next_actions`. Its gate
for stages 1 to 6 is: of 100 seeded defects, all refused and at least 95 by the stage and code that own them;
zero refusals on the eighteen archetypes and on 10³ random valid designs.

Unit tests can show that each analysis refuses what it should. They cannot show that the verb, driven from the
outside through the real binary, returns the right exit code, the right envelope, repairs that actually repair,
and timings inside the stage budgets. This bead is that script. It is the running form of the gate from the
user's side. The gate's M1 part (stages 1 to 6) is entered by BD-110, the capstone this bead depends on, through
the gate recorder from the receipt of the gate's tier run; this script measures the same three counts through
the binary and fails if the two routes disagree.

## Scope

In: `scripts/e2e/skel_design_check.sh`, its helper `repair_command` (executes a printed `next_actions` command
verbatim), the tests of the label checker as this script uses it, the rows that the stage beads place in this
script (stage 4's, below), and the run that reproduces the stages 1 to 6 counts of the preflight gate through
the binary and compares them with the tier run and with the recorded part. It enters no gate row: the M1 part
of GATE-SKEL-04 is BD-110's to enter. Out: the stage runner and the verb (N28ap1-01) and the assembled stages
with the gate's record (BD-110); the
corpus and its label checker `scripts/e2e/tools/compare_labels` (N14b-18, which supplies it); the stage-1 step of `scripts/e2e/skel_author_compile.sh` (N14a-27), which runs the stage-1
fixtures alone while a design is authored and compiled and records no gate row; stages 7 and 8 (their script is
in BD-244); the timing gate's own record, which the Atelier bead owns and which reads this script's timing
lines.

## Technical approach

**Steps.**

1. *Options matrix on one archetype* (`quad-mammal`): plain; `--stages 1-2`; `--stages 4`; `--all`;
   `--strict-data`; with and without `--json`. Assert exactly one envelope per invocation with `--json`, the
   stage records present for the selected range, and exit 0 or 2. For `--strict-data` the expectation is read
   first from the cards the design uses (`frob actuator show <card> --json`, VERBS-actuator's row: every field
   with its provenance): exit 0
   or 2 when no required field is `assumed`, otherwise exit 3 with FROB-REF-113 naming one of those fields,
   while the same check without the flag passes (the flag's effect is what is asserted, not a fixed outcome).
2. *False positives.* For each of the eighteen archetypes available in the build, and for both valid populations
   of N14b-18 read by key from `valid.toml` (population 1, 10³ `ValidByConstruction` designs: the gate's letter;
   population 2, 10³ archetype-neighbourhood designs): `frob design check <id> --stages 1-6 --json`. Assert no
   refusal. Record per-stage wall time from each stage record, and report the two populations separately. The
   same check, with the same assertion, on every base named in `labels.toml` that is not one of the archetypes
   (the cart of the first fixture and the generated bases): a defect proves nothing if its base is refused.
3. *Defects.* For each of the 100 defects: `frob design check <id> --stages 1-6 --json`, with `--strict-data`
   where the label's `strict_data` is true and `--task <fixture>` where its `needs_task` is set. Assert exit 3,
   `ok: false`, and compare `refusal.code`, the refusing stage and `refusal.pointer` with the label.
4. *Repairs that repair.* For each refused defect whose refusal carries repairs: apply `next_actions[0]` exactly
   as printed (a `frob design edit …` command), appending only `--key <derived key>` (below) when the printed
   command carries no key, since `design.edit` is a `mutate` verb and refuses a call without one (805); re-run the
   check on the new version, and assert that the
   original refusal is gone. A repair that does not remove its refusal is a failure of this script.
5. *All findings.* For ten designs built by combining two defects from different stages: without `--all`, only
   the earlier stage's refusal; with `--all`, both.
6. *Refusal payload.* For every refusal assert the fields `code`, `message`, `pointer`, `observed`, `required`,
   `unit` where applicable, `affected_claims`, `retry` and at least one entry in `repairs`.
7. *Determinism.* Re-run steps 2 and 3 in a second process; assert identical stage results and identical
   `DesignId` for repaired versions.
8. *Counts.* `compare_labels` reports: refused of 100; refused by the owning stage and code of 100; refusals on
   the archetypes and on each valid population; repairs applied and repairs that removed their refusal.
9. *Stage rows placed here by the stage beads.* Stage 4 (N14b-11): `frob design check <mecanum> --stages 4
   --json` passes with growth vector (3); the parallel-roller variant refuses with FROB-REF-118 and the missing
   direction (−1, 1, 0)/√2, and after `next_actions[0]` is applied the re-check passes; `frob design check
   fixtures/skel/three-link-wheeled-chain.fbot --stages 4 --json` returns exit 2 with stage 4 `undecided`,
   reason `analysis not available`, for as long as the curvature analysis A-09 is not registered in the build
   (it arrives at M3), and never `passed`. Declared plant (STD-E2E header `plants`, `E2E_PLANT_FAILURE`):
   `branch-swap`, a build that uses curvature for wheel layouts; the parallel-roller step must catch it, because
   the defective base then passes.
10. *Two routes, one gate.* Run the gate's tier run, `FROB_TEST_SEED=<seed> cargo test -p frob-conformance
    --test g1_known_answers --features gauntlet-mutations -- GATE-SKEL-04` (the Gauntlet's one run form; there
    is no `frob conformance` command), and read the three counts from its receipt and from the `measured` field
    of the M1 part of GATE-SKEL-04 in `registries/gates.toml`. Assert that both equal the counts of step 8. A
    difference names the first defect on which the two routes disagree.

**Exit codes asserted.** 0: completed, nothing to flag. 2: completed with findings or an `undecided` stage. 3:
refused input. 7: never expected here. 1 never appears on purpose, so a 1 fails the script as an unhandled
failure.

**Timing lines.** For each archetype and stage the script emits a `metric` line with the stage's wall time in
milliseconds and its budget (100, 50, 400, 200, 150 and 600 ms for stages 1 to 6), and at the end the median and
95th percentile per stage and for the total against 2 s. A stage over its budget is logged as a finding even
when the total passes.

**Idempotence and seeds.** A fresh namespace per run; an idempotency key per edit derived from (script, defect
id, step); the generator's version and seed printed in the first line.

## Acceptance criteria

- [ ] On the M1 build the script reports 100 of 100 defects refused, at least 95 by the owning stage and code,
      and zero refusals on the archetypes, on the corpus's bases and on 10³ valid designs (population 1;
      population 2's count is reported beside it).
- [ ] The three counts equal those of the tier run's receipt and those recorded in the M1 part of GATE-SKEL-04
      (entered by BD-110); a planted difference of one in the receipt's counts makes step 10 fail and name the
      defect.
- [ ] The stage-4 rows of step 9 hold, the chain's stage 4 is `undecided` and not `passed` on the M1 build, and
      the `branch-swap` plant is caught.
- [ ] Every repair applied removes the refusal it was offered for, or the script fails and names the defect.
- [ ] Every invocation with `--json` yields exactly one envelope; every refusal has the full payload.
- [ ] Per-stage medians and 95th percentiles are in the log with their budgets.
- [ ] The script exits non-zero on any failed assertion, is idempotent and seed-explicit, and its controls
      (below) are caught on every run.

## Test plan

### Unit tests

Helpers in `scripts/e2e/tests/`: `compare_labels_counts` (a synthetic set of 5 envelopes and labels gives the
expected three counts, run against N14b-18's checker); `owning_stage_mismatch_counted` (a defect refused at an
earlier stage counts as refused and not as owned); `repair_command_parser` (a printed `next_actions` command is
executed verbatim, never reconstructed, with `--key` appended exactly when the printed command has none); `strict_data_expectation` (a card with one `assumed` required field
yields the expectation "exit 3 with 113"; with none, "exit 0 or 2"); `flags_follow_labels` (the command line
built for a defect has `--strict-data` exactly when its label's `strict_data` is true and `--task <fixture>`
exactly when `needs_task` is set); `routes_compared` (a receipt with counts 100, 96, 0 against script counts
100, 95, 0 fails and names the defect counted differently; equal counts pass).

### End-to-end script and logging

`scripts/e2e/skel_design_check.sh`, sourcing the shared helper of STD-E2E and writing
`target/e2e-logs/skel_design_check/<utc-timestamp>.ndjson` with a transcript beside it. Every line has `ts`,
`script`, `bead: "N14b-19"`, `step`, `event`, the exact command line, exit code, wall time, the envelope's
`evidence` block (class `Tested`, tier `static`, determinism `exact`, `ModelId`, no seed for a static check),
stage statuses with per-stage wall time and budget, and for defects the label and the observed code, stage and
pointer. On failure: the first differing field, the defect's file path, its base's `DesignId` and the envelope
saved beside the log. The final `summary` line gives the four counts, assertions passed and failed, controls
caught and `gates: ["GATE-SKEL-04"]`.

### Known answers and negative controls

- KA-291: the gate's counts.
- KA-276: the forward lidar with `assert_obs: C2xC2` is refused (109) with the lidar mount as breaker; KA-268:
  parallel rollers refused at stage 4 (118); KA-261's rule: a body with no fill is refused (105), never defaulted
  to solid.
- Controls run every time: (a) a copy of the corpus with one label deliberately wrong must lower the owned
  count; (b) a valid archetype placed in the defect list must be reported as "not refused"; (c) a wrapper that
  feeds the script a canned passing envelope for every command must fail the repair step, which proves the
  script reads real output; (d) the `branch-swap` plant of step 9; (e) a receipt whose owned count is raised
  by one must fail step 10.
- Determinism lanes: twice on one machine; debug and release builds of `frob`; Linux and macOS through pinned
  `DesignId` values of the repaired versions.

## Considerations

- The gate's part is entered under BD-110 by a session that did not implement the checks (the recorder refuses
  `self-certified`); this script is the independent second route to the same counts, and a disagreement
  between the routes is a finding against whichever one is wrong, never settled by editing a label.
- Defects for the actuator chapter's codes are `not run` until that chapter's checks exist; the script reports
  them separately, and the gate's record states how many of the 100 were run.
- The "repairs that repair" step is the one most likely to find real problems: a repair is easy to print and
  hard to get right. A repair that trades one refusal for another counts as having removed its own, and the new
  refusal is logged.
- Runtime is dominated by the 10³ valid designs; with the stage budgets it is of the order of half an hour on
  one core, and the script accepts `--sample N` for development; a sampled run logs step 10 as `skip` with the
  reason `sampled`, because the comparison with the tier run's receipt and the recorded part holds only for the
  full corpus.
