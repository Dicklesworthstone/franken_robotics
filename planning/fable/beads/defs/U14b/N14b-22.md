## Background

`frob-io` imports URDF and MJCF at M1. The plan names two further formats and deliberately does not schedule
them:

- **SDF** import is added through a feature matrix when a consumer needs it. Tier Solid: the format is XML, the
  in-house reader already parses it, and the mapping is of the same kind as URDF's.
- **OpenUSD** import is Frontier. Only the core specification is settled and robotics schemas are still vendor
  extensions (FACT, source register), so it waits for a real consumer. Its ceiling, stated before any
  measurement: access to assets published only in that format. Its pilot: import one published robot asset by
  hand-mapping its schema; falsifier: a mechanical field with no mapping. Its kill rule: not built until a
  consumer exists.

The reason for writing a bead for work that is not scheduled is the plan's rule against losing features: the
conditions under which each importer is built, and what "built" means for it, are fixed now, so that the first
person who needs SDF or OpenUSD does not improvise an importer without a loss report, limits or a fuzz target.

This bead is the SDF importer. The OpenUSD importer was split off into N14bp1-03, because it has a gate SDF does
not (its pilot, N14b-23, must not have falsified it) and SDF must not wait for that pilot.

## Scope

In: the trigger condition for SDF; the SDF feature matrix and importer. Out: the OpenUSD importer and its pilot
(N14bp1-03, N14b-23); scene import of world-level content, which is the scene subsystem's verb; any writer for
either format.

## Technical approach

**Trigger (the same rule as for OpenUSD in N14bp1-03).** Work starts only when a consumer is recorded in this
bead: a named reference robot, user asset or benchmark that exists in SDF and in no supported format, with its
licence. The record is also committed as `docs/import/sdf-consumer.toml` (DESIGN, so that a test can read it):
`consumer` (name and kind: reference robot, user asset or benchmark), `source` (repository, commit of 40 hex
digits, path), `spdx`, `licence_text_hash`, `why_no_supported_format`, `recorded_by`, `recorded_on`. Without a
recorded consumer the bead stays in the backlog. `sdf` is a value of `design.import`'s `format` from M1
(VERBS-design; BD-065's format dispatch): until this importer is linked, `frob design import <file> --format sdf`,
and a document with an `<sdf>` root imported without `--format`, answer one envelope `FROB-REF-724` (`reason:
feature-not-built`, `mechanism: import.sdf`, exit 5, `retry: never`), before any byte of the document is read and
with no design created, the message naming the consumer condition above; never 802 and never 122. When this
bead lands, the dispatch sends the value to this importer, with no change to the input schema, and
`design.import`'s block names this bead under "Extended by" for the SDF importer behind `--format sdf`.

**SDF, through a feature matrix.** The matrix is a table in `docs/import/sdf-matrix.md`, generated from the
mapping code, with one row per SDF element or attribute and one of three statuses: `mapped` (with its design
field), `reported` (echoed in the loss report with file and line), `refused`.

1. Reader: the in-house XML reader (elements and attributes, no entities, no DTDs, limits, positions).
2. Mapped at first delivery: `model`, `link` with `inertial` (`mass`, `inertia`, `pose`), `collision` and
   `visual` with primitive geometries and meshes by content hash, `joint` types `revolute`, `prismatic`,
   `fixed`, `ball`, `universal`, `screw` (to classes `R`, `P`, `fixed`, `S`, a product of two `R`, `H`),
   `axis` with `limit` and `dynamics`, and `pose` with `relative_to`, resolved through the model's frame graph
   into `parent_from_joint` transforms once, at this boundary.
3. Reported: `plugin` (never executed), `sensor` elements beyond a parent frame and a rate (sensor cards are not
   inferred), surface and solver parameters (class `no-exact-equivalent`), `gazebo`-style extensions.
4. Refused: `include` with a URI (nothing is fetched), any world-level element in a model import, nested models
   beyond the depth limit.
5. Everything else follows the URDF importer's rules: bodies get `fill: declared` with the source's inertial
   values and provenance `datasheet`; an inertia that fails consistency is listed with a proposed repair and not
   changed; a missing actuator limit is filled from a card marked `assumed` and listed; the field-coverage diff
   must be empty; `--strict` refuses with FROB-REF-122; an import that would drop a body of nonzero mass without
   a declared reduction is refused with N14b-34's refusal (ledger row `import-mass-dropped`, raised through that
   bead's accounting function, under the number N35x-02 assigns).
6. A fuzz target and the importer limits are part of the delivery, not a follow-up (registered with BD-307's
   fuzz registry; the SDF limits are a new profile row in the import-limit registry of N37-05, refused with
   FROB-REF-832, exit 3).
7. **The oracle.** The consumer exists in SDF only, so the pinned incumbent that captures URDF and MJCF oracles
   cannot read it. The capture is taken through a pinned SDF-reading tool (DESIGN: the reference SDFormat library's
   own pose resolution, pinned by version and hash) added to the capture scripts of BD-067 under their no-regeneration
   rule, and compared with `fk-parity` (N14b-24). OPEN (owner: Skeleton lead; fail-closed default): if no such
   capture can be pinned, the parity row is logged `not run`, never passed, and the importer is not declared done.

## Acceptance criteria

- [ ] Before any work: a consumer is recorded for SDF, with its licence, in this bead and in
      `docs/import/sdf-consumer.toml`; once the importer is linked, `--format sdf` (and an `<sdf>` root without
      `--format`) is dispatched to it and no longer answers `FROB-REF-724`, and the generated `design.import`
      input schema is byte-identical to the one before.
- [ ] SDF: the feature matrix is generated from the code; every element of the consumer's files is `mapped`,
      `reported` or `refused`; forward-kinematics parity within 10⁻⁹ m and 10⁻⁹ rad over 10⁴ configurations
      against the oracle for the consumer's robot; the field-coverage diff is empty; a `plugin` element is
      reported and nothing is executed; an `include` is refused.
- [ ] The SDF importer has a fuzz target and limits, and an entry in the format documentation.

## Test plan

### Unit tests

In `crates/frob-io/tests/sdf.rs` (`cargo test -p frob-io --test sdf`), on the consumer's files and on synthetic
fixtures labelled `synthetic`:
- `sdf_consumer_record_valid`: `docs/import/sdf-consumer.toml` parses, names a commit of 40 hex digits and an
  admitted SPDX identifier, and its licence-text hash matches the vendored text; a record with a hand-edited
  commit fails.
- `sdf_pose_relative_to`: a link posed relative to another link and a joint posed relative to its child resolve
  to the same `parent_from_joint` as the equivalent URDF fixture. Hand case (synthetic): link A at (0, 1, 0) m
  with yaw 1.5707963267948966 rad in the model frame, link B at (1, 0, 0) m relative to A: B lies at (0, 2, 0) m
  with yaw π/2, within 10⁻¹² m and 10⁻¹² rad; the mutant that resolves against the world frame puts B at
  (1, 0, 0) m and fails.
- `sdf_joint_types`: six types to their classes; `universal` becomes a product of two revolutes.
- `sdf_plugin_reported_not_run`: a `plugin` element with a filename → a `reported` entry; no file is opened.
- `sdf_include_refused`.
- `sdf_matrix_generated`: the documentation table equals the mapping code's table.
- `sdf_unlisted_element_fails_matrix`: an element absent from the matrix makes the generation test fail (the
  matrix is complete over the consumer's files, not over what the author remembered).
- `sdf_dropped_massive_body_refused`: a link with nonzero mass and no mapping, without a declared reduction →
  refused (N14b-34's rule).

### End-to-end script and logging

`scripts/e2e/skel_import_sdf.sh` (written with the importer; sources the STD-E2E helper; NDJSON to
`target/e2e-logs/skel_import_sdf/<utc>.ndjson` with a transcript): `frob design import <file> --format sdf --name
sdf-a --key sdf-imp-1 --json`; `frob artifact read <loss-report digest> --json`; `cargo run -p frob-conformance
--bin fk-parity -- <DesignId> <oracle capture> <identifier map>` against the consumer's capture; `frob design
import <file> --format sdf --strict --name sdf-b --key sdf-imp-2 --json` (a distinct key, refused with
FROB-REF-122 when the consumer's file has a `reported` element); a planted `include` fixture (FROB-REF-122) and a
planted over-limit fixture (FROB-REF-832, exit 3). Each line: `ts`, `script`, `bead: "N14b-22"`, `step`, `event`,
the command, exit code, wall time, the envelope's evidence block, coverage numbers, class counts, maximum
position and rotation differences with their thresholds (10⁻⁹ m, 10⁻⁹ rad), the source hash, the consumer
record's identifier, and on failure the worst configuration and link with the capture path. `summary`:
assertions passed and failed, `gates: []`. Declared plant (`E2E_PLANT_FAILURE`): `relative-to-world` (pose
resolved against the world frame), which the parity step must catch.

### Known answers and negative controls

- Parity with the URDF fixture of the same robot, where one exists: the two imports must compare equal in
  meaning (forward kinematics, mass properties, identifier map).
- Negative controls: an importer that resolves `relative_to` against the world frame instead of the named frame
  (parity fails away from the reference pose); one that drops `plugin` without a report entry (the
  field-coverage diff fails).

## Considerations

- Priority is backlog; no milestone depends on this bead. The milestone label is the earliest at which frontier
  backlog is revisited, not a commitment.
- SDF's frame semantics (`relative_to`) are where importers go wrong; the mapping converts once at the boundary
  and the comparator checks away from the reference pose.
- Licence: assets available only in this format are often under restrictive terms; the consumer record includes
  the licence, and nothing restrictive is vendored.
- Before the importer lands, `--format sdf` is a capability refusal (`FROB-REF-724`, `mechanism: import.sdf`),
  not an unknown value: the value exists behind a condition (VERBS-design's exception for `design.import`'s `sdf`
  and `usd`), `frob capabilities --json` lists the mechanism as absent, and the refusal's message and the agent
  guide's entry for `design.import` state the consumer condition, so an agent that meets the refusal can see why
  and what would change it.
