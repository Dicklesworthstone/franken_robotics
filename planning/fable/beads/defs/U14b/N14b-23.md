## Background

Every Frontier mechanism needs a paper-scale pilot with a falsifier before its work is funded. OpenUSD import is
Frontier in this plan: only the format's core specification is settled, and the schemas that describe robots
(rigid bodies, joints, drives, articulations) are still vendor extensions (FACT, source register). An importer
written against a moving schema can map today's files and silently lose tomorrow's fields.

The plan's row for it: ceiling of the benefit, stated before any measurement: access to assets published only in
that format. Pilot: import one published robot asset by hand-mapping its schema. Falsifier: a mechanical field
with no mapping. Kill rule: not built until a consumer exists.

The pilot is a paper exercise. Nothing is parsed by project code. One asset is read with existing tools, every
mechanical field in it is listed, and each is mapped by hand to a field of the design term or to a class of the
loss report.

## Scope

In: the frozen protocol; the choice of one asset with its licence; the field inventory; the mapping table; the
record. Out: any importer code; any reader for the format; assets under terms that forbid this use.

## Technical approach

**Protocol (registered before the asset is opened).**

1. *Choose the asset.* One published robot description in OpenUSD under a permissive licence, preferably of a
   robot that also exists in URDF or MJCF among the reference fixtures, so that the hand mapping can be checked
   against a known design. Record its source, version, licence and hash.
2. *Inventory.* With the format's own published tools, outside the workspace, list every prim type and
   attribute in the asset that carries mechanical meaning. Expected groups: rigid-body mass, centre of mass,
   inertia (diagonal and principal axes); joint type (revolute, prismatic, fixed, spherical, others), axis,
   local frames on both bodies, limits; drive parameters (target type, stiffness, damping, maximum force);
   collision shapes and their approximations; the articulation root and its fixed or floating base; mimic or
   tendon couplings; contact and material parameters; units and up-axis metadata; composition features that
   change values (references, variants, instancing).
3. *Map.* For each inventoried field write one row: the source field; the target, which is either a field of
   `frob.design/1` (for example joint `class`, `screws`, `origin`, `limits`; body `mass_properties` with
   `fill: declared`; a `coupling` transmission) or a loss-report class (`dropped`, `no-exact-equivalent`,
   `default-filled`, `unsupported`); the conversion rule (units, axis convention, frame composition); and
   whether the conversion is exact.
4. *Classify.* A field is **mechanical** if changing it changes forward kinematics, mass properties, the joint
   tree, limits or actuation. A mechanical field must map to a design field. A field that is not mechanical may
   map to a loss class.
5. *Check.* Where the same robot exists among the reference fixtures, compare the hand-mapped link count, joint
   count, joint classes, total mass and three sampled forward-kinematics poses with the known design.
6. *Record* the table, the counts, the check, and the outcome.

**Where it is recorded.** The protocol is `docs/pilots/skel-openusd-mapping.md` and the mapping table is
`docs/pilots/skel-openusd-mapping.toml` (one `[[field]]` per inventoried field: `prim`, `attribute`, `group`,
`mechanical` (bool), `target` (a `frob.design/1` path or a loss class), `conversion`, `exact` (bool)), so that a
test can check it. The pilot's row in `crates/frob-conformance/registry/pilots.toml` (schema
`frob.gauntlet.pilot/1`, owner N38a-09) was entered with status `registered` by N14b-26 under its Skeleton
identifier (set `SKEL`, the register's next free number, append-only); this bead freezes the protocol (path,
BLAKE3 hash, date, ledger sequence) in that row before the asset is opened and appends one `[[pilot.result]]`
(values: mechanical fields, mapped mechanical fields, loss-class fields, the check's counts; verdict
`falsifier-rejected` or `falsifier-holds`; the composition outcome in `limits`; receipt). Tier `F`; ceiling
"access to assets published only in that format; none on speed"; fallback `{ ships = "no OpenUSD import; the
user converts outside to a supported format and records the tool, as for macros", kill_gate }` as N14b-26
entered it. Report: `docs/delivery/pilots/skel-openusd-mapping.md`.

**Falsifier.** A mechanical field with no mapping: a field that changes kinematics, mass, the tree, limits or
actuation and has no field of the design term to land in. If it holds, OpenUSD import is not funded as
specified; the record states which field, and the choice is between a schema extension proposed to the design
language's owner and leaving the format unsupported.

**Second reportable outcome.** A mechanical field whose value depends on composition features (a variant or an
instance override) in a way a flat mapping cannot resolve. Not a falsifier; it changes the importer's scope to
"flattened assets only", and the record says so.

## Acceptance criteria

- [ ] The protocol's hash in the pilot's row of `crates/frob-conformance/registry/pilots.toml` predates the
      opening of the asset (commit and ledger order).
- [ ] The asset's source, version, licence and hash are recorded; the licence permits the use.
- [ ] The mapping table has one row per inventoried mechanical field and marks each conversion exact or not.
- [ ] The falsifier outcome is recorded as held or not held, with the field named if it held.
- [ ] The record states what the pilot did not do: no parsing by project code, one asset, one vendor's schema
      extension, no round trip.
- [ ] The OpenUSD importer bead (N14bp1-03, which depends on this one) reads this record: it cannot start
      unless the falsifier did not hold.

## Test plan

### Unit tests

No production code. `crates/frob-conformance/tests/pilot_register.rs` (the register's test file, N38a-09) gains,
reading the real `pilots.toml` and the mapping table:
- `skel_openusd_pilot_row_complete`: the row has falsifier, ceiling, fallback, a frozen protocol whose file
  hashes to the registered BLAKE3, and (once run) one result.
- `skel_openusd_pilot_registered_before_result`: the result's date and ledger sequence follow the registration,
  and its `protocol_blake3` equals the registered hash.
- `skel_openusd_mapping_counts`: the inventory's field count equals the table's row count; every row has a
  target; every row with `mechanical = true` targets a path that the `frob.design/1` schema (BD-054, BD-055)
  resolves; the result's counts equal those of the table.
- `skel_openusd_checker_catches_unmapped`: a synthetic table (labelled `synthetic`) with one mechanical field
  targeting a loss class makes the checker report `falsifier-holds`.
- `skel_openusd_reference_check`: where the asset's robot is a reference fixture, the table's link and joint
  counts equal the known design's.

### End-to-end script and logging

`scripts/e2e/pilot_skel_openusd_mapping.sh` (header `# e2e: bead=N14b-23 milestone=M6
labels=skeleton,pilot,frontier gates=GATE-GAUNT-08 seed=0 needs=cpu plants=unmapped-mechanical-field`; it drives the
format's own published listing tool, pinned by version, outside the workspace, and then `cargo test -p
frob-conformance --test pilot_register -- skel_openusd`; it needs no `frob` verb). It sources
`scripts/e2e/lib.sh` (STD-E2E) and writes `target/e2e-logs/pilot_skel_openusd_mapping/<utc>.ndjson` with a
transcript beside it. Every line carries `ts`, `script`, `bead`, `step`, `event`, the exact command, exit code
and wall time; one `metric` line per mapped field with its group, target, exactness and classification; the
asset's hash, the listing tool's version, the protocol hash. On failure: the first unmapped mechanical field and
the paths of the table and the listing output. The `summary` line carries the counts of mechanical fields,
mapped fields and loss-class fields, `falsifier_holds: true|false`, assertions passed and failed, and `gates: ["GATE-GAUNT-08"]`. Exit
non-zero if the planted unmapped field is not caught. The table, the log and the asset's hash are attached to the
pilot record.

### Known answers and negative controls

- If the asset's robot is among the reference fixtures: link count, joint count and total mass equal the known
  design's (total mass within the reference's stated rounding).
- Negative control inside the pilot, which shows it can fail: add to the inventory one synthetic mechanical
  field with no counterpart in the design term (for example a joint type that is not a product of the supported
  classes); the table checker must report the falsifier as held.

## Considerations

- Priority is backlog. The pilot costs under a day and should be run only when a consumer for the format is in
  sight; a pilot run years before the importer would describe a schema that has since changed.
- The result is about one vendor extension at one version; the record names both, and a different extension
  needs its own pilot.
- The asset is never vendored unless its licence allows redistribution; its hash and source are enough for the
  record.
