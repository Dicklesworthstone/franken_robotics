## Background

A module (`.fmodule`) is a reusable design subterm with open ports, parameters and a contract. The contract
carries what the rest of the robot may rely on as scalars and ranges: a mass range, a peak bus demand, a heat
limit. That is enough to check interfaces and not enough to answer the question an agent asks most often about
an assembly of modules: can these legs hold this body, on these feet, with this payload?

A **capability table** (tier Frontier) answers that at the module's level. It carries what a module can *do* at
its ports over a declared operating box, characterized once and cached by content, so that an assembly of
modules can be screened by composing tables before any whole-robot computation runs. It adds nothing to what a
contract may claim about contact dynamics. The three consequences stated for the limb port packet stand: a
port-level summary cannot be inverted at the port; it does not describe a limb whose end effector is in contact
coupled through a moving base; and it is a value for stated conditions, not a universal number.

Design decision and its reason: the table stores two approximations of the attainable wrench set per pose cell,
an outer one (support values, rounded outward) and an inner one (attained points), so that the true set lies
between them. Reason: a screen built on one approximation can only exclude or only admit; with both, each
verdict says which side it is on. Rejected: a single scalar "payload capacity" per module (it is valid for one
stance and one direction and is silently reused for others).

## Technical approach

**Type (DESIGN sketch: intent, not signatures).**

```rust
/// What a module can do at its ports over a declared operating box.
pub struct CapabilityTable {
    module: ModuleHash, cards: Vec<CardVersion>, version: CharacterizationVersion,
    operating_box: OperatingBox,      // end-effector pose cells in the port frame, speed bound, duty bins, bus range
    wrench_outer: Vec<SupportRows>,   // per pose cell: h(u) ≥ max uᵀw over attainable w, outward-rounded
    wrench_inner: Vec<VertexSet>,     // per pose cell: attained wrenches; their hull lies inside the true set
    power: Vec<PowerBounds>,          // electrical power over (wrench cell, speed, duty)
    heat: Vec<HeatBounds>,            // steady heat to the sink over the same cells
    port_inertia: SymPsd6Range, first_mode: FrequencyInterval,
    validity: Validity,               // quasi-static; Froude number ≤ 0.5; bound on the neglected inertial wrench
}
```

**Operating box.** A set of end-effector pose cells in the module's port frame (default 64), each a box of
positions (and orientations where the end effector has them) reachable inside joint limits; a speed bound; duty
bins; the bus voltage range the module's contract assumes.

**Characterization, per pose cell and per direction.** A fixed direction set U (default 26: the normalized
nonzero vectors of {−1, 0, 1}³ in end-effector force space, mapped to port wrenches by the cell's transform;
moment directions are added for end effectors with a patch). For each cell and each u ∈ U, one cone program over
the module's own kinematics and cards:

    maximize   uᵀw
    subject to τ = J(q)ᵀ·f,   w = the port wrench equivalent to f,
               τ within each joint's torque box at the speed bound, read from the card's torque-speed-voltage
               envelope over the declared bus range,
               f within the end effector's contact cone where the declared law has one,
               q the cell's configuration.

Its optimum is the support value h(u), and its maximizer is an attaining wrench.

1. *Outer rows.* For each u, h(u) is evaluated at the cell's vertices and its centre, the largest value is
   taken, enlarged by a bound on the variation of J over the cell, and rounded outward in interval arithmetic.
   The attainable set of every configuration in the cell then lies inside {w : uᵀw ≤ h(u) for all u ∈ U}.
2. *Inner vertices.* The attaining wrenches at the cell's centre, each shrunk toward the origin by the same
   variation bound, so that each is attainable at every configuration of the cell; their convex hull lies inside
   the true set, because at a fixed configuration the attainable set is convex.
3. *Power and heat rows.* At each attaining operating point the card laws give electrical power and steady
   winding heat; the rows store bounds over (wrench cell, speed, duty).
4. *Port inertia and first mode.* The range of the module's articulated inertia at its port over the box, as a
   symmetric positive semidefinite 6×6 range, and an interval for the first natural frequency with the end
   effector fixed.
5. *Validity.* The table is quasi-static. It records the regime in which the neglected inertial wrench is small:
   a Froude number at most 0.5, and an explicit bound on the inertial wrench (the port inertia range times the
   acceleration bound implied by the speed bound and the cell size).

Hand case: a one-joint leg, a horizontal link of 0.25 m with a torque limit of 10 N·m, pressing down: τ = 0.25·f,
so h(down) = 40 N and the attaining wrench is 40 N; the leg cannot pull, so h(up) = 0.

**Memo node.** The table is a node of the memo graph keyed by the module hash, the card versions, the operating
box and the characterization version. A `set-param`, `regear` or `swap-actuator` inside one module changes that
module's hash and re-characterizes that module only; sibling modules' tables are served unchanged. Determinism:
the programs run on the host in `f64` with outward rounding at the end; the table's bytes are a pure function of
its key (class D0 on one platform; cross-platform identity is tested and reported).

**The verb.** `frob module characterize <module> [--box <file>] [--directions 26] [--strict-data] --key <key>
--json`, kind `run`, first milestone M3: it takes an idempotency key and a budget, accepts the bounded
synchronous wait and otherwise returns a job handle. Output schema `frob.module.characterize.out/1`: the table's
identifier, the box, counts of cells and directions, per-cell summary (largest and smallest support value), the
validity record. Evidence: class `Tested` for the table, tier `static`, and `Estimated` with the field named
when a card field the table rests on is `assumed` (the registry's rule for this verb); the outer rows are bounds
by construction and are labelled `outer`, the inner vertices `inner`. Refusals: FROB-REF-114 (the module's
digest or port signature does not match the reference given; repair: name the digest the catalog holds, shown
by `frob module show`), FROB-REF-113 under `--strict-data` when a card field the torque envelope needs is
`assumed` (repair: a card version in which the field is measured or stated, or the same call without the flag,
which returns an `Estimated` table), and the budget refusal of every `run` verb. These inputs and the two chapter
refusals are the row of VERBS-module (DESIGN, because a table that quietly rests on an assumed torque limit is
the thing an agent screening assemblies most needs to be able to refuse); the generator appends the `run`
kind's codes and, for the file forms of the module reference and of `--box`, 734 and 828.

**The inner-in-outer checker.** `cargo run -p frob-analyze --example capability_check -- --table <id>
--directions <n> --seed <s>` (an example of the owning crate, BD-025's rule for a harness driver of another
subsystem; it prints one JSON object and exits non-zero on a violation): for each pose cell it draws n random
directions from the seed and asserts that the inner support max over vertices of uᵀw never exceeds the outer
support computed from the rows, reporting the first violating cell and direction with both values. N14b-32 runs
it over every archetype module.

**Cost (TARGET, unmeasured).** One module in seconds on the CPU: 64 pose cells × 26 directions = 1,664 small
programs.

**Layout.** `crates/frob-analyze/src/capability/{table.rs, characterize.rs, validity.rs}`; the table's schema
`frob.capability/1` travels in the common artifact envelope.

- [ ] The one-joint leg gives 40 N down and 0 N up, to the rounding direction (outer ≥ 40, inner ≤ 40).
- [ ] Every outer row is rounded outward and every inner vertex is attained: a sampled true optimum never
      exceeds its outer row, and each stored vertex is reproduced by the module's own inverse statics within
      limits.
- [ ] The validity record is present, and a query outside it is answered `unresolved` by consumers.
- [ ] `module.characterize` is reachable through `frob --json` with its schema; cancellation ends the job and
      leaves no partial table in the memo graph; one module characterizes within the stated seconds on the
      reference host, with the measured time recorded.

## Test plan

### Unit tests

- `one_joint_leg_support`: `leg-1r`, 0.25 m, 10 N·m → h(down) = 40 N (outer in [40, 40 + rounding]),
  h(up) = 0.
- `inner_in_outer_random_directions`: 10⁴ random u per module from a recorded seed, on `leg-1r` and
  `std/leg-3r-qdd`; max over inner vertices of uᵀw ≤ the outer support in direction u computed from the rows.
- `outer_contains_truth`: on `std/leg-3r-qdd`, 10³ random configurations inside a cell and random u: the true
  optimum at that configuration never exceeds the cell's row.
- `inner_vertices_attainable`: each stored vertex satisfies the torque boxes at every vertex of its cell.
- `edit_locality`: `set-param` inside one leg of `quad-tray` (the leg split from its mirror images, so that it
  is a module of its own) → exactly one table recomputed; the table of the three sibling legs is served from
  the memo graph with an identical digest. Before the split the four legs are uses of one module and share
  one table, by content: one characterization, and a `set-param` under the constructor recomputes that one.
- `strict_data_refuses_assumed_113`; `assumed_field_gives_estimated`; `digest_mismatch_114`.
- `key_changes_with_card_version`; `key_changes_with_box`.
- `validity_bound_formula`: the neglected inertial wrench bound equals port inertia upper bound times the
  acceleration bound, in consistent units.
- `torque_box_reads_envelope_at_speed`: raising the speed bound never enlarges a support value.

### End-to-end script and logging

`scripts/e2e/module_characterize.sh` (header `bead=N14b-28 milestone=M3 labels=skeleton,frontier,verb
gates=GATE-SKEL-09 seed=<s> needs=cpu,frobd plants=inward-outer,card-blind-key`), built on this bead's own
dependencies (the fixture `leg-1r` and ART-L2's `std/leg-3r-qdd` and `quad-tray`), sourcing the STD-E2E helper
and writing `target/e2e-logs/module_characterize/<utc>.ndjson` with a transcript beside it. Steps: (1) `frob
module characterize tests/fixtures/capability/four-leg/leg-1r.fmodule --key mc-<run>-leg-1r --json` (a result,
or exit 8 and `frob job wait <job>`): 26 directions, outer support downward at least 40 N, inner at most 40 N,
0 N upward, the validity record; the same call with the same key returns the same table identifier with
`idempotent_replay: true` and no new job; (2) `frob module characterize std/leg-3r-qdd --key mc-<run>-l3r
--json`, then `capability_check` on its table with 10⁴ directions per cell: zero violations; (3) the same
module with a card version whose torque-envelope field is `assumed`: with `--strict-data` exit 3,
`FROB-REF-113` naming the field; without it a table of class `Estimated` naming it (distinct keys); (4) a
reference whose digest does not match the catalog: exit 3, `FROB-REF-114`, repair naming `frob module show`;
(5) cancellation: `--sync-wait-ms 0` (exit 8, a job handle), `frob job cancel <job> --json`, then a fresh key:
no partial table is served from the memo graph. Each `cmd` line carries the exact command, exit code, wall
time and the envelope's `evidence` block; `metric` lines carry the table identifier, cells, directions,
programs solved, wall time against the stated seconds, largest and smallest support values, memo hits and
misses; on failure the cell, direction and the two values and the table's path. Declared plants
(`E2E_PLANT_FAILURE`): `inward-outer` (outer rows rounded inward; step 2 must catch it) and `card-blind-key`
(a key without card versions; a card bump then serves the old table, which step 3's `Estimated` table must
expose). The `summary` line gives assertions passed and failed and the gate touched; the script records no gate
value (N14b-32 records GATE-SKEL-09).

### Known answers and negative controls

- The one-joint leg: at most 40 N per foot.
- Negative controls: (a) outer rows rounded inward (a sampled true optimum exceeds a row); (b) inner vertices not
  shrunk for cell variation (a vertex violates a torque box at a cell corner); (c) a table key that omits the
  card versions (a card bump serves the old table); (d) a torque box read at zero speed regardless of the speed
  bound.
- Metamorphic: doubling every torque limit doubles every support value where no cone is active; mirroring a
  module mirrors its table.

## Considerations

- KILL-SKEL-CELL (decided at M4): if the screen built on these tables fails its comparison, tables remain as a
  sizing report for agents and nothing is discarded automatically. This bead's output is useful in either case.
- The direction set bounds how tight the outer set is: 26 directions leave a gap between inner and outer, and
  the share of `unresolved` verdicts follows from it. The pilot reports that share; a larger set costs
  proportionally more programs.
- A table says nothing about a limb in contact coupled through a light moving base, about momentum strategies or
  about anything above the validity regime. Those limits are part of the type (`validity`) so that consumers
  cannot ignore them.
- The shared-bus question is not answered by a table: peak demands are never added; the joint time-indexed
  schedule decides it.
