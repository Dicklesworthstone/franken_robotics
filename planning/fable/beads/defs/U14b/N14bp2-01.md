## Background

`frob-model` (Skeleton's compiler, layer 2, tier Solid) memoizes compilation per subterm: every compile product
records the fields of the design term it read (its influence record, ADR-SKEL-09), and the invalidation set of a
typed edit is the set of products whose read set meets the edit's write set. Two invariants make this safe:
INV-SKEL-02 (incremental compilation equals full compilation, bit for bit) and INV-SKEL-06 (the invalidation set
contains every product that differs after a full recompile; a product outside it is bit-identical). The mechanism
and its property tests over 10⁴ random designs and edits (GATE-SKEL-02) are BD-063.

BD-063 specified an end-to-end script that shows the same from the user's side, through `frob design new`, `frob
design edit` and `frob design show --products` with and without `--no-memo`. It could not run it: `design.new` and
`design.show` (N14a-21) depend on BD-063, because the `products` section and `--no-memo` read the memo graph. This
bead runs that script after both exist. It is the check that an agent who edits a design is told, through the
command line, exactly which products the edit made stale, and that nothing outside that list changed.

Terms. *Product*: a compile output (kinematic tree, a body's inertia, channels, budget summary, symmetry groups,
lowerings) with a digest, a memo key and a read set. *Served* or *computed*: whether `design.show --products`
answered a product from the memo graph or compiled it.

## Scope

In: the script `scripts/e2e/skel_incremental_compile.sh`, its log, its plant. Out: the memo graph, influence
records and invalidation (BD-063, which also delivers `fixtures/skel/quad-a.fbot` and
`fixtures/skel/incremental.expect.toml`); the verbs (BD-058, N14a-21); the per-row catalogue conformance
(N14a-17).

## Technical approach

`scripts/e2e/skel_incremental_compile.sh --seed <s>` (sources the STD-E2E helper; seed explicit; idempotent: a
fresh scratch namespace and a fresh memo directory per run).

| # | Command | Asserts |
|---|---|---|
| 1 | `frob design new quad-a --file fixtures/skel/quad-a.fbot --key ic-1 --json` | exit 0; `DesignId` d₀ |
| 2 | `frob design show quad-a --products --json`, then the same with `--no-memo` | every product digest equal; the first call computes, a repeat serves every product |
| 3 | `frob design edit quad-a set-param /limbs/of/of/chain/1/body/region/capsule/1 "0.24 m" --key ic-3 --json` | the answer's invalidation set equals the expected kinds of `incremental.expect.toml`; then `--products` equals `--no-memo` digest for digest |
| 4 | `set-fill` of the thigh to `{"shell":"2 mm"}` | invalidated: that body's inertial product, the mass roll-up on the path to the root, budgets; sibling legs' kinematic products served |
| 5 | `rename` of `torso` to `chassis` | invalidation set empty; `ModelId` unchanged; `DesignId` changed |
| 6 | `move-sensor lidar` by 0.04 m in z | invalidated kinds exactly sensor binding (extrinsics), Γ_obs, coverage views; kinematic and inertial digests unchanged |
| 7 | `swap-actuator --joints '*.knee' --to qdd-l` | binding, mass roll-up and bus products invalidated, as the expected file says |
| 8 | `add-payload` of 2 kg on the left side | whole-robot sums and both symmetry groups invalidated |
| 9 | an edit and its returned inverse | every product digest equals its value before the edit |

Steps 4 to 9 are written in the table by edit kind; each is one call `frob design edit quad-a <kind> <target>
<value…> --expected-parent <the DesignId the previous step returned> --key ic-<step> --json` (design.edit is a
`mutate` verb: a keyless call is `FROB-REF-805`; the expected parent makes a stale chain fail as 804 instead of
editing the wrong version), step 9 as two calls, the edit (`ic-9a`) and the inverse its answer returned
(`ic-9b`). Keys are fixed per step because every run opens a fresh namespace; a step repeated within one run is a
replay (`idempotent_replay: true`) and is logged as such. After each of steps 3 to 9 the script compares `frob design show quad-a
--products --json` with the same call under `--no-memo`, product by product.

Plant `stale-product` (STD-E2E `E2E_PLANT_FAILURE`, checked by `run-all.sh --verify-plants`): after step 4 the
script compares the served products against the pre-edit `--no-memo` compile; the digest assertion must fail and
name the thigh's inertial product.

Logging (charter section 6): NDJSON to `target/e2e-logs/skel_incremental_compile/<utc>.ndjson` with a transcript
beside it. Every line has `ts`, `script`, `bead: "N14bp2-01"` (and `under_test: "BD-063"`), `step`, `event`, the
exact command line, exit code, wall time, the envelope's `evidence` block (class, tier, determinism, `model_id`,
seed), the counts of products served and computed, the invalidation set with the invalidating field of each
entry, digests of every compared product; on failure the first differing product with both digests and the paths
of the two compile records. A final `summary` line gives assertions passed and failed and `gates:
["GATE-SKEL-02"]` (touched, not recorded: the gate is measured by BD-063's property tests).

## Acceptance criteria

- [ ] The script exists, is plain shell, seed-explicit and idempotent, sources the STD-E2E helper, and exits
      non-zero on any failed assertion.
- [ ] Steps 1 to 9 pass on Linux and macOS: after every edit, served products equal a `--no-memo` compile digest
      for digest, and each invalidation set equals its expected kinds.
- [ ] The plant `stale-product` makes the script fail and name the thigh's inertial product.
- [ ] The log validates against the STD-E2E schema and ends with a `summary` line.

## Test plan

### Unit tests

The script is the test; the crate-level twin of this sequence is BD-063's `edit_sequence_matches_full`, which
reads the same expected file, so the two cannot drift.

### End-to-end script and logging

As above: `scripts/e2e/skel_incremental_compile.sh`; logs under `target/e2e-logs/skel_incremental_compile/`.

### Known answers and negative controls

- KA-287 from the user's side: incremental equals full, bit for bit, after each of seven edits.
- KA-289 from the user's side: products outside each invalidation set are bit-identical.
- Hand-checkable expectations: `rename` invalidates nothing and keeps `ModelId`; `move-sensor` touches no
  kinematic or inertial product.
- Negative control: the `stale-product` plant.
- Determinism lanes: the same run twice gives the same digests; debug and release binaries; Linux and macOS.

## Considerations

- The expected kinds come from BD-063's file, not from the typed-edit catalogue's predictions; a disagreement
  with the catalogue is N14a-17's finding, never a failure of this script.
- Runtime target: under 30 s on a laptop; no GPU.
