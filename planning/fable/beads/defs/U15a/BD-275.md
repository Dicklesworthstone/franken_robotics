## Background

Nemesis is the subsystem that searches for worlds in which a candidate design violates its requirement, keeps only
worlds the candidate's own body could have solved, checks that a failure is not an artifact of the simulator,
shrinks it to the smallest world that still fails (a minimal counterexample world, file format `.fmcw`, schema
`frob.mcw/1`), and stores that world as a regression. The hard-world set is where those stored worlds live.

For each task family and robot class, Nemesis keeps a versioned set of minimal counterexample worlds, schema
`frob.hardset/1`, as a list of `.fmcw` identities with the failure mode each exposes. It is bookkeeping over
mechanisms that exist elsewhere (tier Solid), and its value is in what it forbids. ADR-NEMESIS-06: everything
Nemesis finds is discovery data. Hard worlds and counterexamples train and test designs; they are never a
confirmation sample. Reason: these worlds were selected because designs failed in them; a design tuned until it
passes them has been fitted to them, so passing them is evidence of repair, not of robustness, and using them to
confirm a claim or to bound a failure rate would bias the result in a direction nobody can correct afterwards.

Regression use is legitimate: a design that once failed a hard world is re-run on it after a repair, and the
result is labelled as a regression result, not as evidence of robustness.

## Scope

In: the set's schema, identity and versioning; admission and retirement rules; the four actions of
`nemesis.hardset` (the default `show`, and `add`, `retire`, `run` selected with `--action`); the discovery mark and the three refused uses; the `hard` battery's identity; the scorecard of
a run. Out: producing `.fmcw` files (seed BD-274, shrinking); the solvability oracle and the artifact guard that
give a world its witness class and its referee promotion (seeds BD-271, BD-272); the qualification lane, which
draws its own worlds and refuses any caller-offered world at its own commit (seed BD-259, N24b-16; this bead
depends on it and adds the discovery predicate to the citation check of a qualified result); the bound's lane
firewall and the rare-failure bound that raise the nominal-draw refusal FROB-REF-560 (N26a-23, seed BD-276):
they refuse hard-set episodes because those carry no nominal or bounded-weight draw record, and BD-276, which
comes after this bead, may also call the predicate defined here; scorecard accounting (seed BD-254).

## Technical approach

1. **Schema (DESIGN sketch; canonical JSON; the identity is the hash of the canonical bytes).**
   ```json
   { "schema": "frob.hardset/1", "id": "hs:…", "version": 7, "parent": "hs:…",
     "task_family": "payload-transport", "task": "t:kitchen-tray@88c1…", "robot_class": "quad-mammal",
     "worlds": [ { "mcw": "w:3fa9…", "failure_mode": {"class": "slip", "binding_atom": "upright"},
                   "oracle": "solvable-causal", "promotion": {"tier": "referee", "reproduced": true},
                   "found_against": {"model": "m:9f2c…", "controller": "c:5e02…"},
                   "added": {"decision": "…", "by": "…", "ledger_seq": "…"} } ],
     "retired": [ { "mcw": "w:51b0…", "reason": "…", "decision": "…" } ],
     "authorization": {"execution_authorized": false, "hardware_safety_signoff": false,
                       "sim_to_real_certified": false} }
   ```
   One set per (task family, task version, robot class). Every `add` or `retire` writes a new version whose
   `parent` is the previous identity; old versions stay readable. An entry of `worlds` may also hold the
   optional field `carried_from: { set, world, entry }`. No entry written by this bead has it: it is written
   only by the action `carry`, which N26b-23 adds at M4, and names the entry of another set from which the
   world was re-promoted. It is declared here so that the schema has one definition: when present it is part of
   the canonical bytes, and a reader of `frob.hardset/1` accepts entries with and without it.
2. **Admission (`add`).** A world enters the set only as `solvable-causal` or `plant-feasible` and only after
   promotion on the referee. Checked on the offered `.fmcw`: (a) it replays with identical digests on its
   originating backend (INV-NEMESIS-04); (b) its oracle class is `solvable-causal` (a controller using only the
   candidate's observation interface satisfies the requirement within every actuator and mission limit) or
   `plant-feasible` (a trajectory found with privileged state satisfies it within the body's limits); never
   `not-excluded` or `infeasible-for-candidate` (INV-NEMESIS-01: only solvable worlds count); (c) the artifact
   guard passed and the promotion record says tier `referee`, reproduced (INV-NEMESIS-05); a world labelled
   `artifact-candidate` is excluded; (d) the world is inside the legality profile; (e) its task version and robot
   class match the set (OPEN-NEMESIS-5's default); (f) it is not already present. A failed check refuses and
   names the check. Checks (b) and (c) are made twice (DESIGN: the set must not take a file's word for what
   only the oracle and the guard can grant). First on the file, by the format's reader (N26a-19), which rejects
   a file whose own blocks do not say solvable and promoted. Then against the oracle's and the guard's own
   records for the file's world and candidate, looked up in the ledger by identity and run with the hard-set
   target where no record exists: admission goes through the one function `oracle::admit_counterexample`
   (BD-271) on those records, never on the file's `oracle` and `promotion` blocks. A file that claims a
   promotion or a witness the records do not hold is refused, naming check (b) or (c) and the record it
   contradicts.
3. **Retirement (`retire`).** A world leaves the set by a recorded decision: the command requires a reason and a
   decision reference, moves the entry to `retired`, and writes a new version. Nothing is deleted.
4. **`show`.** The current version: identity, counts by failure class, each world with its failure mode, witness
   class and the candidate it was found against, the retired list, and the version lineage; paginated.
5. **`run`.** `nemesis.hardset --action run <design> [--set hs:…]` evaluates a design against the set of its class and
   returns a scorecard with the standard outcome columns: `satisfied`; `violated`, broken down by failure class;
   `undetermined`; `invalid` (numerical fault, counted, never dropped); `infeasible-for-candidate`;
   `infeasible-for-class`; `refused`. Every world lands in exactly one column, and success rates are printed with
   two denominators (all worlds; worlds not shown infeasible). The result carries the mark `discovery: hard-set`
   and, for a design with an earlier failure on a world, the label `regression result` per world. It is a long
   verb: it accepts a bounded synchronous wait and otherwise returns a job handle.
6. **The discovery mark and the three refused uses.** Every `.fmcw`, every world in a hard-world set and every
   search-selected world address is recorded in the ledger with origin `nemesis`, and
   `frob_nemesis::is_discovery_world(world) -> bool` answers from that record (INV-NEMESIS-06: hard-world and
   search-selected worlds are discovery data).
   - *As a confirmation sample:* refused with FROB-REF-567 ("a hard-world or search-selected world offered as a
     confirmation sample"). Raised when a qualification request, a confirmation family or a citation of a
     qualified result contains such a world, or when a hard-set run is cited as confirmation.
   - *As nominal draws for a bound:* refused with FROB-REF-560 ("a bound was offered episodes that were not drawn
     nominally or with recorded bounded weights").
   - *As the only content of a battery:* refused at battery definition, since a battery made of past failures
     overfits them; a battery may include hard worlds beside others, and a covering battery keeps one slot in five
     for held-out scenes. Where (DESIGN): a battery is defined by its manifest and membership events, which the
     loader of N24b-01 (`battery::resolve`) registers on first load; this bead adds to that load one check, which
     calls `is_discovery_world` on the world addresses of every item. A `listed` manifest whose every item is a
     discovery world, or an event that would leave it so, is refused with `hard-world-set-inadmissible` (failed
     check `only-hard-battery`, pointer at the manifest), and nothing is registered. The `hard` battery of step 7
     is not such a manifest: its selection is `hardset-ref`, it is the set itself read as a battery, and a run of
     it carries the mark and the per-world labels of `run` in step 5.
7. **The `hard` battery and identity.** Arena's battery `hard` is the current hard-world set of the robot class.
   A battery's identity is the hash of its content, so adopting a hard world into a regression battery changes
   the battery's identity, and so does every `add` or `retire`. Results are keyed by battery identity; ledgers
   that read a battery (fidelity, divergence, tier correction, exploitation detectors) never mix results across
   identities.
8. **Surface.** Verb `nemesis.hardset`, kind read for `show` (the default action) and kind run for the actions
   `add`, `retire` and `run`, as the verb registry VERBS-nemesis lists them; first
   milestone M3 (a fifth action, `carry`, of kind run, joins the same verb at M4 through N26b-23; it offers
   its re-promoted worlds to the `add` of this bead, so every admission check of step 2 applies to them); MCP tool `nemesis_hardset` in the `attack` cluster. The action is selected only with `--action <name>` (NJL-01
   action rule 1): `show` is the call with no `--action` and has no name to pass; an action word in a positional
   place (`frob nemesis hardset add …`) or `--action show` is FROB-REF-802. The three run actions each take an
   idempotency key (a call without one is FROB-REF-805); `add` and `retire` need the scope `nemesis:write`, `run`
   needs `nemesis:run`, `show` needs `nemesis:read`. Which set: `--set hs:…` names one; otherwise `--class <robot
   class> --task <t:…@version>` selects the current set of that class and task version (one set exists per task
   family, task version and robot class, so the class alone does not name a set; the registry row lists
   `--class` with `--task`, and `--set`). The default call with `--class <robot class>` alone answers with the
   list of the class's sets (identity, task, version, world count), which is what the registry's example call
   returns; a run action whose set is not determined is refused with FROB-REF-802 naming the missing `--task`.
   `--action add <.fmcw>` without `--set` takes the set from the file's task and the candidate's robot class;
   `--action run <design> --task <t>` without `--set` takes the set of the design's class for that task;
   `--action retire <world> --reason … --decision …` takes `--set`, or `--class` with `--task`. The dashboard's
   failures panel lists new minimal counterexample worlds from `show`.

## Acceptance criteria

- [ ] The seed's first condition: a hard world offered as a confirmation sample is refused with FROB-REF-567, at
      the qualification lane's commit and at citation.
- [ ] The seed's second condition: adopting a hard world into a regression battery changes the battery's identity;
      removing it restores the previous identity.
- [ ] `add` refuses a world that is `not-excluded`, `infeasible-for-candidate`, `artifact-candidate`, not promoted
      on the referee, not replaying, outside the legality profile, or of another class or task version; and
      admits a `solvable-causal` and a `plant-feasible` world that pass all checks. A file whose blocks claim a
      witness or a referee promotion that the oracle's and the guard's own records do not hold is refused.
- [ ] Every episode of a `nemesis.hardset --action run` is recorded with origin `nemesis`, the discovery mark and no
      nominal or bounded-weight draw record, and `is_discovery_world` is true for its world, which is what the
      bound's firewall reads; the refusal FROB-REF-560 when such episodes are offered to `nemesis.bound` (seed
      BD-276, a later bead) is asserted end to end by N15a-28.
- [ ] A battery whose content is only hard worlds is refused at definition; the same worlds beside other scenarios
      are accepted.
- [ ] `run` returns a scorecard whose columns sum to the set size, with both denominators and the discovery mark;
      a previously failing world that now passes is labelled a regression result.
- [ ] None of the planted artifact failures of the guard's gate appears in any set (the hard-set row of
      GATE-NEMESIS-06: 100 of 100 planted artifact failures labelled and none in the hard-world set).
- [ ] `retire` without a decision reference is refused; every version is reachable from `show`.
- [ ] The verb is reachable through `frob --json` and MCP with schemas and refusal lists; cancellation of `run` is
      tested; outputs carry the claim product and the three no-authorization flags.

## Test plan

### Unit tests
`crates/frob-nemesis/tests/hardset.rs`:
- `admission_checks`: one fixture `.fmcw` per failed precondition (seven) and two admissible ones; each refusal
  names its check and carries the slug `hard-world-set-inadmissible`.
- `forged_claim_refused`: the never-promoted fixture with its `promotion` block edited to claim tier `referee`,
  reproduced, and a `not-excluded` fixture edited to claim `solvable-causal`: both pass the reader and are
  refused by the admission against the guard's and the oracle's own records, naming the contradicted record.
- `set_selection`: with sets for two task versions of one class, the default call with `--class C` lists both;
  with `--class C --task t@v1` and with `--set hs:…` it returns one set in full; `--action run <design>` with
  neither `--task` nor `--set` is FROB-REF-802; `--action add <.fmcw>` lands in the set of the file's task and
  the candidate's class; the actions `add`, `retire` and `run` without a key are FROB-REF-805; the positional
  form `add <.fmcw>` and `--action show` are FROB-REF-802.
- `versioning_and_identity`: add, add, retire produce versions 1, 2, 3 with distinct identities and a parent
  chain; replaying the same `add` with the same idempotency key returns the same version.
- `battery_identity_changes`: the identity of a regression battery before and after adopting one hard world
  differs; after removal it equals the original (content addressing).
- `discovery_predicate`: `is_discovery_world` is true for set members, retired members and search-selected
  addresses, false for a nominal draw.
- `refusal_567_confirmation` (at the lane's commit and at citation of a qualified result that contains a hard
  world), `hardset_episodes_carry_no_nominal_record` (the record a bound's firewall reads: origin `nemesis`, no
  draw weight), `only_hard_battery_refused` (a `listed` manifest of two hard worlds is refused at load with
  `hard-world-set-inadmissible`, check `only-hard-battery`, and registers no identity; the same two beside one
  ordinary item load; a removal event that would leave only the hard worlds is refused; the `hardset-ref`
  manifest of the `hard` battery loads).
- `scorecard_columns_sum` (property over 100 random sets and outcome assignments): exactly one column per world.
- `regression_label`: a world failed by design A and passed by its repaired successor is labelled accordingly.

### End-to-end script and logging
`scripts/e2e/nemesis_hardset.sh` (bead N15a-28) drives `frob nemesis hardset` (the default `show`) and `frob
nemesis hardset --action add|retire|run`, a qualification
request that names a hard world, a bound request over hard-set episodes and a battery definition, on fixture
worlds. Logged per step: command, exit code, evidence block, set identity and version before and after, battery
identity before and after, refusal code and pointer, scorecard column counts.

### Known answers and negative controls
CX-294 ("a battery made of past failures is a good battery": it overfits them; the hard-world set is refused as
the only content of a battery, as a confirmation sample and as nominal draws for a bound). The planted artifacts
of the guard (a friction cone linearized as a box, which grants √2 times the friction coefficient along its
diagonals; penetration recovery that pumps energy into a hopping body) must never be admitted. Negative controls:
an admission path that skips the promotion check (a fast-tier-only failure enters; the test must catch it); a
battery identity computed from its name instead of its content (adoption does not change it); a qualification
lane that does not consult the discovery predicate (the confirmation refusal is missed). Determinism: set and
battery identities are exact (class D0) and identical across platforms; `run` inherits the class of the tier it
ran on.

## Considerations

- **Refusal codes not named by the plan.** FROB-REF-567 and FROB-REF-560 are named. No code is named for a failed
  admission check or for a battery made only of hard worlds. Both are refusals with exit code 3 and share one
  slug, `hard-world-set-inadmissible`, which the chapter's refusal registry (N26-REF) lists and the second
  allocation round of the refusal registry (N35x-02) has on file for a number in the `3xx` family. This bead
  proposes no number of its own: its tests assert the slug, exit code, pointer and failed check, and read the
  number from the allocation ledger once it is assigned.
- **OPEN-NEMESIS-5** (how a hard-world set is carried across a change of robot class or task version; owner:
  Arena lead; blocks nothing). Default: a set belongs to one class and one task version; worlds are re-promoted
  before they enter another. This bead enforces the first half (check (e) of `add`); the re-promotion path
  (`nemesis.hardset --action carry`, with `--refresh` for a kernel-version change in place) and the decision record are
  N26b-23.
- KILL-MCW (if fewer than half of shrunk worlds have at most three edits, or fewer than 90% replay, Nemesis ships
  full failing worlds with replay): the set then lists full failing worlds; nothing in this bead changes except
  the size of entries.
- A set can grow without bound; retirement by recorded decision and the `infeasible-for-class` column (evidence
  that a scenario should leave by decision, not attrition) are the pruning tools.
- Privacy: a hard world derived from a private scene inherits the private mark; `show` redacts accordingly.
