## Background

`explain.run` and `explain.design` (BD-112) are the studio's "explain" step: a token-budgeted account of what
happened in a run, or of what limits a design, ending in typed next actions. The seed condition for those verbs is
concrete: the explanation of a planted knee-thermal failure names the first cause and cites the telemetry channel
that shows it. A unit test can check the assembly logic; only a script that drives the real binary through the
studio's own sequence (check, explain design, simulate, explain run, follow the citation) shows that an agent
would actually get that answer. This bead is that script.

The planted failure is a member of the design corpus's family of planted defects ("an undersized knee actuator"):
a design whose label is fixed before any analysis is tuned. Here the defect is thermal: the knee's continuous
rating is below what the stair task asks of it. From cold the knee does not overheat within an episode; from the
default evaluation start `steady(task)` the run is refused, because the steady state lies above the winding
limit; from a declared warm start just below the first derating band the knee derates within seconds and the
robot falls. The script exercises all three.

## Scope

In: the planted design and its control twin; the script; its assertions; the log. Out: the verbs (BD-112); the
thermal model and duty-history start (BD-072, N15a-15); the taxonomy and its monitors (seed BD-094).

## Technical approach

1. **Fixtures** under `crates/frob-conformance/fixtures/explain/knee_thermal/`:
   - `quad_knee_undersized.fbot`: the dog-like quadruped archetype with the knee actuators bound to a fixture card
     whose thermal fields are those of the worked thermal card (R₀ = 0.20 Ω at 25 °C, α = 0.00393 K⁻¹,
     G = 0.80 W/K, C = 120 J/K, winding limit 155 °C, derating bands ending in a trip at the limit; continuous
     current 18.6 A) and whose torque constant is chosen so that the stair task's root-mean-square knee current is
     about 22 A, above the rating and below the 31.9 A runaway threshold. At 22 A the steady rise would be
     96.8/(0.80 − 0.380) = 231 K, far above the limit; from 135 °C the winding reaches a 140 °C band in about 12 s.
     Every fixture card field is `assumed` and labelled synthetic.
   - `quad_knee_ok.fbot`: the same design with the next catalog class at the knees (the control twin).
   - The stair task of the first archetypes; thermal starts `cold`, `soaked(135 °C)` and the default
     `steady(task)`.
2. **Steps.**
   1. `frob design check quad_knee_undersized --task <stairs> --json`: exit 2 or 3 with a knee finding from the
      actuator analysis (thermal equilibrium above the limit, FROB-REF-132 at stage 6 when the point is required).
   2. `frob explain design quad_knee_undersized --task <stairs> --budget 600 --json`: the first listed limit is the
      knee's thermal margin; the card fields it rests on are named with provenance `assumed`; `next_actions`
      contains `swap-actuator` and `regear` edits for the knees.
   3. `frob sim run quad_knee_undersized --task <stairs> --tier referee --level L2 --worlds 4 --seconds 20
      --thermal-start soaked:135degC --telemetry T2 --seed 7 --json` (a diagnostic run of a design the preflight
      flagged; if the build makes the preflight mandatory, the documented diagnostic override is used and the run
      is marked accordingly): the run completes with failures of class `fall`. The same command with the default
      start refuses with FROB-REF-132 and returns the largest sustainable load, which the script also asserts.
   4. `frob explain run <run> --budget 600 --json`: assertions on the JSON: (a) the first-cause section names
      class `thermal-limit` at a knee joint, with a time earlier than the fall; (b) it carries the label
      `Estimated`; (c) it cites a telemetry channel (the knee's winding temperature or derating channel) with
      world address and time window; (d) `next_actions` includes the knee edits; (e) the serialized output is
      within 600 tokens by the documented estimator.
   5. Execute the cited handle (`frob telemetry query …`): the returned samples cross the first derating band's
      temperature inside the cited window.
   6. Control A: the same run with `--thermal-start cold`: no world fails thermally within 20 s (a rise of about
      16 K from cold at 22 A on this card); `explain.run` names no thermal cause.
   7. Control B: `quad_knee_ok` under the default start `steady(task)`: the start is admitted, the knees stay
      below the first band, and no thermal cause is named.
   8. Control C: the same failing run at level L1 (no thermal state): `explain.run` names no thermal cause.
   9. Budgets: repeat step 4 at 200 and 2,000 tokens; the first-cause section is present at all three; omitted
      sections are listed with handles.
   10. Repeat step 4: byte-identical output.
3. **Idempotence.** The script works in a temporary workspace, is seed-explicit (seed 7), and re-runs to the same
   digests on the referee.

## Acceptance criteria

- [ ] Steps 1 to 5 pass: the first cause is named, labelled `Estimated`, and its citation resolves to samples that
      show the crossing.
- [ ] The three controls pass: no thermal cause is named when the episode starts cold, when the knee is adequate,
      or when the model has no thermal state.
- [ ] The output respects each budget and is byte-identical on repeat.
- [ ] The script exits non-zero on any failed assertion; a dry-run flag that swaps the expected class for
      `torque-saturation` makes it fail (the assertion is live).
- [ ] The log has the fields below and a final summary line.

## Test plan

### Unit tests
None beyond shell-lint and a test that the fixture design's computed root-mean-square knee current on the nominal
stair gait lies between the continuous rating (18.6 A) and the runaway threshold (31.9 A), so that the fixture
still plants the defect it is meant to plant after any change to the archetype or the gait.

### End-to-end script and logging
`scripts/e2e/explain_run_design.sh`. It sources the shared end-to-end helper and writes newline-delimited JSON to
`target/e2e-logs/explain_run_design/<utc-timestamp>.ndjson` with a transcript beside it. Each line: `ts`,
`script`, `bead` (BD-112, or N15a-15 and BD-072 on the control steps), `step`, `event`, the exact command line,
exit code, wall time, and the envelope's evidence block (claim, class, tier, determinism, `ModelId`, run identity,
seed). `metric` lines: first-cause time and fall time in seconds; the cited channel name and window; the winding
temperature at the citation in kelvin against the band threshold; the token count against the budget. Digests of
the two repeated explanations are logged. On failure: the first differing field of the explanation and the paths
of the run and the envelope. The `summary` line counts assertions passed and failed; no gate is claimed.

### Known answers and negative controls
Known answer: for the planted design the first cause is the thermal limit at the knee and the cited channel is the
knee's winding temperature. KA-312 underlies control A (20 s from cold at 20 A raises the winding by 12.8 K, far
short of the bands). Negative controls: controls A, B and C above; plus a mutant build of the explain assembly
that reports the terminal class as first cause, under which step 4(a) must fail. Determinism lanes: the referee
run twice with identical digests; the explanation byte-identical in debug and release.

## Considerations

- The fixture depends on the stair task and the first archetypes; if the stair task is not available at M1 for
  the quadruped, a single-leg repeated step-up rig with the same knee card is the fallback fixture, and the script
  says which it used.
- The override that lets a refused design be simulated for diagnosis must mark the run so that it can never be
  cited for a comparison; the script asserts that mark.
