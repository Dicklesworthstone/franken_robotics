## Background

The hard-world set (BD-275) is the versioned list of minimal counterexample worlds that Nemesis keeps per task
family and robot class. Its rules are mostly prohibitions: a world enters only with a solvability witness and
after promotion on the referee; the set is discovery data and may never serve as a confirmation sample
(FROB-REF-567), as the nominal draws of a failure-rate bound (FROB-REF-560), or as the only content of a battery.
Prohibitions are exactly what a busy implementation forgets to enforce at one of several doors, so they are tested
from the outside, through the same commands an agent would use, at every door: the hard-set verb, the
qualification lane, the bound verb and the battery definition. This bead is that script.

## Scope

In: fixture worlds; the script; assertions; the log. Out: the mechanisms behind each door (BD-275, and seeds
BD-259 for qualification, BD-276 for bounds, BD-254 for batteries, BD-272 for the artifact guard, BD-274 for
`.fmcw`).

## Technical approach

1. **Fixtures** under `crates/frob-conformance/fixtures/nemesis/hardset/` (synthetic worlds built on the
   threshold-delivery cart fixture so that they run in seconds on the CPU referee):

   | Fixture `.fmcw` | Property | Expected on `add` |
   |---|---|---|
   | `ok_causal` | `solvable-causal`, promoted on the referee, replays | admitted |
   | `ok_plant` | `plant-feasible`, promoted on the referee, replays | admitted |
   | `not_excluded` | oracle class `not-excluded` | refused: no witness |
   | `infeasible` | `infeasible-for-candidate` (a doorway narrower than the body) | refused: not a counterexample |
   | `artifact_box_cone` | failure exists only under a friction cone linearized as a box | refused: `artifact-candidate` |
   | `fast_tier_only` | found on a fast tier, never promoted | refused: no referee promotion |
   | `forged_promotion` | `fast_tier_only` with its `promotion` block edited to claim tier `referee`, reproduced | refused: the guard's own record holds no such promotion (the file's word is not taken) |
   | `stale_digest` | one state digest altered | refused: does not replay |
   | `illegal_edit` | an edit outside the legality profile | refused: outside legality |
   | `other_class` | a world of another robot class | refused: class mismatch |
2. **Steps.** The verb's action is selected only with `--action <name>` (NJL-01 action rule 1, BD-275): `show`
   is the call with no `--action`, and `add`, `retire` and `run` are run actions, each call with its own `--key`.
   1. `frob nemesis hardset --class <c> --task <t> --json` (the default `show`): an empty set at version 0 (or the
      existing one; the script works in a fresh namespace).
   2. `frob nemesis hardset --action add <ok_causal.fmcw> --key ha-1 --json` and the same for `ok_plant`
      (`--key ha-2`): versions 1 and 2; identities differ; the default `show` call lists both with their failure
      modes and witness classes. Repeating an `add` with the same key returns the same version
      (`idempotent_replay: true`).
   3. Each refusing fixture, through `frob nemesis hardset --action add <fixture.fmcw> --key ha-<fixture> --json`:
      exit 3, the slug `hard-world-set-inadmissible` and the failed check named in the refusal, the set's identity
      unchanged.
   4. `frob nemesis hardset --action run <design> --task <t> --key hr-1 --json` for a design that fails `ok_causal` and
      passes `ok_plant`: scorecard columns `satisfied` 1 and `violated` 1 (with the failure class), sum 2, both
      denominators printed, the mark `discovery: hard-set` present. Then the repaired design (`--key hr-2`):
      `satisfied` 2, and `ok_causal` labelled a regression result.
   5. Confirmation door: `frob eval qualify <design> --task <t> --claim <claim> --clusters <the set's hs:…>
      --key q-1 --json`, a request whose `clusters` name the hard-world set (a request may name no worlds of its
      own, only the campaign's sealed family), is refused with FROB-REF-567; citing the hard-set run as a
      qualified result is refused.
   6. Bound door: `frob nemesis bound <design> --task <t> --tier <tier> --target 1e-3 --mode certify --episodes
      <the run set of step 4> --key hb-1 --json` is refused with FROB-REF-560, exit 3, and draws no episode.
   7. Battery door (a battery is defined by its manifest and events under the namespace's `registries/batteries/`,
      registered when `battery::resolve` first loads it, N24b-01 with BD-275's check): a `listed` manifest
      `only-hard.<c>.toml` whose items are the two hard worlds, then `frob eval run <design> --battery only-hard
      --class <c> --tier referee --key bd-1 --json`: refused with `hard-world-set-inadmissible` (failed check
      `only-hard-battery`), exit 3, no identity registered. A regression battery `regress.<c>.toml` of three
      ordinary scenarios, run with `--key bd-2`: its `BatteryId` is read from `bound`; an event adopting
      `ok_causal` is appended and the run repeated (`--key bd-3`): a different `BatteryId` (logged before and
      after); a removal event with a reason and the run again (`--key bd-4`): the original `BatteryId`.
   8. `frob nemesis hardset --action retire <ok_plant> --class <c> --task <t> --key rt-0 --json` without a
      decision reference: refused; with `--reason … --decision … --key rt-1`: version 3, the world listed under
      `retired`, and `--action run` no longer evaluates it.
   9. Artifact row: one box-cone and one penetration-pump plant of the guard's planted registry (N26a-15) go
      through `frob nemesis search … --method given --worlds <the two plants> --step-plan <each plant's
      artifact plan> --key <k> --json` (the guard labels both `artifact-candidate`), then `frob nemesis hardset
      --action add` on each, with its own key (refused); the default `show` call lists neither. The artifact plans are conformance-only, so this step needs the
      `conformance` build and scope; where they are absent the step is logged as a skip with that reason
      (never as a pass), the summary does not list GATE-NEMESIS-06, and the same row is the one N26a-16
      measures at full size.
3. **Idempotence and seeds.** A fresh namespace per run; seeds explicit on every simulation step; every call of
   a run-kind action or verb (`add`, `retire`, `run`, `eval qualify`, `nemesis bound`, `nemesis search`)
   carries its own idempotency key; identities are content hashes and repeat exactly.

## Acceptance criteria

- [ ] Steps 1 to 9 pass; in particular a hard world offered as a confirmation sample is refused, and adopting one
      into a regression battery changes the battery's identity (the two conditions of the seed bead).
- [ ] Every refusing fixture leaves the set's identity unchanged and none yields exit code 1.
- [ ] Scorecard columns sum to the number of worlds in every `run`.
- [ ] The script exits non-zero on any failed assertion. Its header declares the plants
      `admit-unpromoted`, `qualify-skips-discovery` and `battery-identity-by-name` (the three conformance
      mutants of the negative controls below), and `run-all.sh --verify-plants` shows each making the script
      exit 1 with a failed assertion that names the plant (steps 3, 5 and 7).
- [ ] The log has the fields below and a final summary line naming `GATE-NEMESIS-06` for the artifact row when
      step 9 ran; no call of a run-kind action lacks `--key`.

## Test plan

### Unit tests
In `crates/frob-conformance/tests/nemesis_hardset_fixtures.rs`:
- `fixture_table_matches_directory`: each fixture is used once; each expectation has a fixture.
- `one_property_per_fixture`: every refusing fixture is derived from `ok_causal` and differs from it by exactly
  the property its row names (a structural diff of the parsed `.fmcw`: the oracle class for `not_excluded`, the
  doorway width for `infeasible`, the cone linearization for `artifact_box_cone`, the promotion record for
  `fast_tier_only`, one state digest for `stale_digest`, one edit for `illegal_edit`, the robot class for
  `other_class`), so each refusal in step 3 is for the named reason and not an accident of construction.
  `forged_promotion` is the one fixture derived from another refusing fixture: it differs from `fast_tier_only`
  by the `promotion` block alone, and parses as a valid `.fmcw`, so that only the admission against the
  guard's record can refuse it.
- `infeasible_fixture_is_infeasible`: the doorway of `infeasible` is narrower than the cart's swept width.
Plus a shell-lint of the script.

### End-to-end script and logging
`scripts/e2e/nemesis_hardset.sh`. It sources the shared end-to-end helper and writes newline-delimited JSON to
`target/e2e-logs/nemesis_hardset/<utc-timestamp>.ndjson` with a transcript beside it. Each line: `ts`, `script`,
`bead` (`N15a-28`, the script's own bead on every line, as the shared helper fixes it at start; the bead whose
mechanism a step exercises, BD-275, or BD-259, BD-276, BD-254 on the door steps, is in the step's title),
`step`, `event` (`start`, `cmd`, `assert`,
`metric`, `refusal`, `end`), the exact command line, exit code, wall time, and the envelope's evidence block
(claim, class, tier, determinism, identities, seed). `metric` lines: set version and identity before and after
each mutation; battery identity before and after adoption; scorecard column counts with the set size as the
threshold for their sum. `refusal` lines: code, pointer, the failed check. Digests are logged where identities are
compared. On failure: the first differing identity or count and the paths of the fixture and the envelope. The
`summary` line counts assertions and lists `GATE-NEMESIS-06`. The fixtures contain no private-scene data.

### Known answers and negative controls
CX-294. The refusing fixtures are the planted failures of this script. Negative controls under conformance
mutants: admission without the promotion check (`fast_tier_only` is admitted and step 3 fails); a qualification
lane that skips the discovery predicate (step 5 fails); a name-based battery identity (step 7 fails).
Determinism: identities byte-identical across two script runs; simulation steps run on the CPU referee with
identical digests on repeat.

## Considerations

- The step that offers hard worlds to the qualification lane needs a campaign; the script opens one with the admin
  scope in its own namespace and closes it at the end, so no real campaign's index is spent.
- A failed admission check and an only-hard battery share the uncoded refusal `hard-world-set-inadmissible` of
  the chapter's refusal registry (N26-REF), on file in the second allocation round (N35x-02). Until the ledger
  assigns its number the script asserts the slug, exit code 3 and the failed check's name for those steps, and
  afterwards reads the number from the ledger; FROB-REF-567 and FROB-REF-560 are asserted by number.
