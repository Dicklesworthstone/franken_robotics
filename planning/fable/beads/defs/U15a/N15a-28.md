## Background

The hard-world set (BD-275) is the versioned list of minimal counterexample worlds that Nemesis keeps per task
family and robot class. Its rules are mostly prohibitions: a world enters only with a solvability witness and
after promotion on the referee; the set is discovery data and may never serve as a confirmation sample
(FROB-REF-567), as the nominal draws of a failure-rate bound (FROB-REF-560), or as the only content of a battery.
Prohibitions are exactly what a busy implementation forgets to enforce at one of several doors, so they are tested
from the outside, through the same commands an agent would use, at every door: the hard-set verb, the
qualification lane, the bound verb and the battery definition. This bead is that script.

## Scope

In: fixture worlds; the script; assertions; the log. Out: the mechanisms behind each door (BD-275, and seeds
BD-259 for qualification, BD-276 for bounds, BD-254 for batteries, BD-272 for the artifact guard, BD-274 for
`.fmcw`).

## Technical approach

1. **Fixtures** under `crates/frob-conformance/fixtures/nemesis/hardset/` (synthetic worlds built on the
   threshold-delivery cart fixture so that they run in seconds on the CPU referee):

   | Fixture `.fmcw` | Property | Expected on `add` |
   |---|---|---|
   | `ok_causal` | `solvable-causal`, promoted on the referee, replays | admitted |
   | `ok_plant` | `plant-feasible`, promoted on the referee, replays | admitted |
   | `not_excluded` | oracle class `not-excluded` | refused: no witness |
   | `infeasible` | `infeasible-for-candidate` (a doorway narrower than the body) | refused: not a counterexample |
   | `artifact_box_cone` | failure exists only under a friction cone linearized as a box | refused: `artifact-candidate` |
   | `fast_tier_only` | found on a fast tier, never promoted | refused: no referee promotion |
   | `stale_digest` | one state digest altered | refused: does not replay |
   | `illegal_edit` | an edit outside the legality profile | refused: outside legality |
   | `other_class` | a world of another robot class | refused: class mismatch |
2. **Steps.**
   1. `frob nemesis hardset show --class <c> --task <t> --json`: an empty set at version 0 (or the existing one;
      the script works in a fresh namespace).
   2. `add ok_causal`, `add ok_plant` (each with an idempotency key): versions 1 and 2; identities differ; `show`
      lists both with their failure modes and witness classes. Repeating an `add` with the same key returns the
      same version (`idempotent_replay: true`).
   3. Each refusing fixture: exit 3, the failed check named in the refusal, the set's identity unchanged.
   4. `frob nemesis hardset run <design> --json` for a design that fails `ok_causal` and passes `ok_plant`:
      scorecard columns `satisfied` 1 and `violated` 1 (with the failure class), sum 2, both denominators printed,
      the mark `discovery: hard-set` present. Then the repaired design: `satisfied` 2, and `ok_causal` labelled a
      regression result.
   5. Confirmation door: an `eval qualify` request whose candidate world family names `ok_causal` is refused with
      FROB-REF-567; citing the hard-set run as a qualified result is refused.
   6. Bound door: `frob nemesis bound --mode certify` over the hard-set run's episodes is refused with
      FROB-REF-560.
   7. Battery door: defining a battery whose only content is the two hard worlds is refused; defining a regression
      battery of three ordinary scenarios, then adopting `ok_causal` into it, changes the battery identity (logged
      before and after); removing it restores the original identity.
   8. `retire ok_plant` without a decision reference: refused; with one: version 3, the world listed under
      `retired`, and `run` no longer evaluates it.
   9. Artifact row: run the guard's two planted artifacts through search, guard and `add`; neither is in the set.
3. **Idempotence and seeds.** A fresh namespace per run; seeds explicit on every simulation step; identities are
   content hashes and repeat exactly.

## Acceptance criteria

- [ ] Steps 1 to 9 pass; in particular a hard world offered as a confirmation sample is refused, and adopting one
      into a regression battery changes the battery's identity (the two conditions of the seed bead).
- [ ] Every refusing fixture leaves the set's identity unchanged and none yields exit code 1.
- [ ] Scorecard columns sum to the number of worlds in every `run`.
- [ ] The script exits non-zero on any failed assertion; flipping one expectation in dry-run mode makes it fail.
- [ ] The log has the fields below and a final summary line naming `GATE-NEMESIS-06` for the artifact row.

## Test plan

### Unit tests
None beyond shell-lint and the fixture–table agreement test (each fixture is used once; each expectation has a
fixture).

### End-to-end script and logging
`scripts/e2e/nemesis_hardset.sh`. It sources the shared end-to-end helper and writes newline-delimited JSON to
`target/e2e-logs/nemesis_hardset/<utc-timestamp>.ndjson` with a transcript beside it. Each line: `ts`, `script`,
`bead` (BD-275, or BD-259, BD-276, BD-254 on the door steps), `step`, `event` (`start`, `cmd`, `assert`,
`metric`, `refusal`, `end`), the exact command line, exit code, wall time, and the envelope's evidence block
(claim, class, tier, determinism, identities, seed). `metric` lines: set version and identity before and after
each mutation; battery identity before and after adoption; scorecard column counts with the set size as the
threshold for their sum. `refusal` lines: code, pointer, the failed check. Digests are logged where identities are
compared. On failure: the first differing identity or count and the paths of the fixture and the envelope. The
`summary` line counts assertions and lists `GATE-NEMESIS-06`. The fixtures contain no private-scene data.

### Known answers and negative controls
CX-294. The refusing fixtures are the planted failures of this script. Negative controls under conformance
mutants: admission without the promotion check (`fast_tier_only` is admitted and step 3 fails); a qualification
lane that skips the discovery predicate (step 5 fails); a name-based battery identity (step 7 fails).
Determinism: identities byte-identical across two script runs; simulation steps run on the CPU referee with
identical digests on repeat.

## Considerations

- The step that offers hard worlds to the qualification lane needs a campaign; the script opens one with the admin
  scope in its own namespace and closes it at the end, so no real campaign's index is spent.
- Until the registry owner assigns codes for a failed admission check and for an only-hard battery, the script
  asserts exit code 3 and the failed check's name for those steps, and FROB-REF-567 and FROB-REF-560 by number.
