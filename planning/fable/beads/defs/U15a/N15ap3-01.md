## Background

Several known answers are statements about a rig driven by a prescribed command, not by a feedback controller:
a torque ramp r·t on a joint at rest begins to move at t = τ_s/r; a slow sinusoid of the motor through a backlash
gap traces a loop of width β; a motor reversal smaller than the gap leaves the output at rest (the six cases of
GATE-SINEW-04, §15.6); a DC motor under a voltage or torque step shows its time constants (GATE-SINEW-01); a cart
driven along a scripted path stops in a doorway or cuts a corner (the Habitat fixtures of N19ax-01 and N19ax-02).
Each needs the same thing from `frob sim run`: a controller that ignores state and plays a declared command
schedule at the control ticks. The `--controller` row of the verb registry (VERBS-sim) names this bead the owner
of the form `open-loop:<schedule>`, with its refusals (a) to (d) below; the input `--controller` itself is
N16ap4-01's on the referee at M1. Tier Solid, crate `frob-control` (Reflex).

DESIGN, with the alternatives rejected. (a) A schedule file of its own schema, named like the fixture controllers
of N14b-06 (`fixtures/controllers/<name>.toml`), hashed into `ControllerId`: the schedule is then content-addressed,
reviewable and part of the run's identity. Rejected: a schedule given inline on the command line (long, quoted
expressions that an agent must escape; the identity would depend on spelling); a schedule as a policy checkpoint
(a policy needs a mapping table and a network file for what is a list of segments); a schedule inside each rig's
design file (the same rig is driven by several schedules, and a design edit would change every one of them).
(b) Commands enter at the actuator driver's input, never as forces applied past the actuator: an open-loop torque
is still limited by the card's current and voltage envelope, which is what the Sinew known answers measure.

## Scope

In: the schema `frob.openloop/1` and its loader; the controller `OpenLoopSchedule` implementing the `Controller`
trait of N22a-01; its `ControllerId` under N22a-07's rule; the parse of the prefix `open-loop:` in the
`--controller` input of `sim.run` on the referee at M1; the refusals of a schedule; two demonstration schedules and
a one-joint rig; the end-to-end script `scripts/e2e/sim_open_loop.sh`. Out: the input `--controller` itself and
its other forms (the input, `baseline` and a `ControllerId`, N16ap4-01 on the referee at M1 and N16b-25 on every
tier; `fixture:<name>`, N14b-06; `baseline+residual:`, N22a-16;
`backup`, N22bx-02); the schedules of the Sinew rigs (registered by N15a-12 and N15a-24) and of the Habitat
fixtures (N19ax-01, N19ax-02); evaluation on the batched tiers, which N16b-25's handler does through the
interface stated in step 6; the layer-tag telemetry (N22a-15).

## Technical approach

1. **Source.** `--controller open-loop:<schedule>` resolves `<schedule>` (letters, digits and hyphens) to the file
   `fixtures/controllers/open-loop/<schedule>.toml`, present in every build as the fixture controllers are (the
   registry's rule for `fixtures/controllers/`). Only names are accepted at M1 (DESIGN: a registered file has a
   reviewed identity; a path form is a later additive change that would take the artifact-input codes 734 and 828).
2. **Schema `frob.openloop/1`** (TOML; quantities are exact decimal strings with units, as cards write them):
   ```toml
   schema = "frob.openloop/1"
   name   = "jr-ramp"
   after  = "hold-last"                # or "zero": the command after the last segment ends
   [[channel]]
   joint   = "j1"                      # an actuated joint of the design
   command = "torque"                  # torque: τ_ff scheduled, k_p = k_d = 0
   segments = [ { kind = "ramp", from = "0 N·m", rate = "1 N·m/s", until = "2 s" } ]
   [[channel]]
   joint   = "j2"
   command = "position"                # q_des scheduled, q̇_des its exact derivative, τ_ff = 0
   kp = "40 N·m/rad"
   kd = "0.5 N·m·s/rad"
   segments = [ { kind = "sine", offset = "0 rad", amplitude = "0.10 rad", frequency = "0.1 Hz",
                  phase = "0 rad", until = "20 s" } ]
   ```
   Segment kinds: `hold {value}`, `ramp {from, rate}` (value from + rate·(t − t_start)), `sine {offset, amplitude,
   frequency, phase}` (offset + amplitude·sin(2π·frequency·(t − t_start) + phase)), each with `until`. Segments are
   contiguous: the first starts at t = 0 (episode start), each ends at its `until`, the `until` values strictly
   increase. A torque channel's values have the dimension of the joint's effort (N·m for a revolute joint, N for a
   prismatic one); a position channel's, of the joint coordinate. A position on a joint whose card reads the
   encoder on the motor side (`encoder_side: motor`, an L3 rig) is the joint-equivalent rotor angle θ/N, which
   is how a rig moves the rotor through a backlash gap.
3. **Evaluation (the controller).** At each control instant t of the clock contract (an exact rational) the
   controller returns, per scheduled joint, the driver input of the actuator level (BD-070's driver tick:
   τ_cmd = k_p·(q_des − q_enc) + k_d·(q̇_des − q̇_enc) + τ_ff): for `torque`, (k_p, k_d, τ_ff) = (0, 0, value);
   for `position`, (kp, kd) as written, q_des the value and q̇_des its derivative (0 for `hold`, `rate` for `ramp`,
   2π·frequency·amplitude·cos(…) for `sine`). `hold` and `ramp` are evaluated in exact rationals and converted to
   `f64` once; `sine` uses the referee's deterministic elementary functions (no platform `sin`). After the last
   segment: `hold-last` keeps the final value (and q̇_des = 0), `zero` commands τ_ff = 0 with k_p = k_d = 0. An
   actuated joint not named by any channel receives (0, 0, 0) and is listed in the run's output under
   `open_loop.unscheduled`. The controller reads no state and no observation; its only state is the schedule
   position, saved and loaded with every checkpoint (`save`, `load`), and its `phase_source` is `Clock`. The
   command goes through the actuator limiter like any other (N22a-01 rule 2), so the card's envelope binds.
4. **Identity.** `ControllerId` = N22a-07's content hash of the canonical record `{form: "open-loop", schedule:
   <canonical bytes of the file>}` (sorted keys, normalized quantity strings). It enters `RunId` through the
   manifest, which records `controller = "open-loop:<schedule>"` and the `ControllerId`.
5. **Refusals.** All are `FROB-REF-802` (exit 3, `retry: after-change`), which every verb lists, with `pointer`
   `/controller` and the schedule path and entry in `details`. DESIGN, reason: the schedule is part of the
   verb's input, so a schedule the design cannot accept is an invalid input and needs no code of its own. Cases:
   (a) no file of that name, with the registered names listed; (b) the file fails `frob.openloop/1` (unknown or
   missing key, an `until` that does not increase, a first segment not at 0, a unit of the wrong dimension, with
   the dimension found and required); (c) a channel names a joint the design lacks, a joint with no actuator, or
   a joint named twice; (d) `position` on an actuator at level L0, which has no driver loop. The exclusions of the
   registry row stay as they are: with `--policy`, or with a `--fixture` that declares its controller, 802. Each
   refusal is raised at admission, before any world is created.
6. **Tiers.** At M1 the referee (`sim.run` answers the other tiers with 724 until M2). For the batched tiers the
   controller exposes `fn commands_at(&self, t: RationalSeconds) -> &[DriverInput]`, a pure function of time, so
   N16b-25's handler evaluates it once per control tick on the host and writes the same values into every
   world's action buffer.

## Acceptance criteria

- [ ] `frob sim run fixtures/controllers/open-loop/rig-1dof.fbot --tier referee --actuator-level L1 --controller
      open-loop:demo-ramp --seconds 2 --telemetry T1 --seed 1 --key ol-ramp --json` exits 0; the manifest names
      the controller and its `ControllerId`; the realized torque at t = 0.3 s is 0.3 N·m within 10⁻⁹ relative
      (rig card latency 0, inside its limits).
- [ ] Each refusal (a) to (d) answers `FROB-REF-802`, exit 3, one envelope, no world created.
- [ ] `after = "zero"` commands zero after the last segment; `hold-last` keeps the final value.
- [ ] Two runs with the same schedule and seed (distinct keys) have identical state digests; changing one value
      in the schedule changes `ControllerId` and `RunId`.
- [ ] `frob-control/CONTRACT.md` documents the form, its schema and its refusals.

## Test plan

### Unit tests

`crates/frob-control/tests/open_loop.rs` (the real loader and controller; schedules written as TOML strings are
labelled `synthetic`):
- `ramp_exact`: ramp from 0 at 1 N·m/s, control period 1/500 s: tick 150 (t = 3/10 s) gives τ_ff = 0.3 N·m from
  the exact rational; tick 1,000 (2 s) gives 2.0 N·m; at tick 1,500 `hold-last` gives 2.0 and `zero` gives 0.
- `sine_values`: offset 0, amplitude 0.10 rad, 0.1 Hz: q_des at 2.5 s is 0.10 rad within 1 ulp; q̇_des at 0 s is
  0.10·2π·0.1 = 0.0628319 rad/s; identical bits on two runs and in debug and release.
- `segments_contiguous`: a first segment starting after 0, and an `until` equal to the previous one, each refuse
  with 802 and a pointer at the segment.
- `unit_dimension`: `value = "0.3 rad"` on a torque channel refuses with 802, found `rad`, required `N·m`.
- `unknown_joint`, `duplicate_joint`, `unactuated_joint`, `position_on_l0`: 802 each, pointer at the channel.
- `unscheduled_joint_zero`: a two-joint design with one channel: the other joint gets (0, 0, 0) and is listed in
  `open_loop.unscheduled`.
- `controller_id_content`: one changed digit changes `ControllerId`; reordered keys and whitespace do not.
- `save_load_resume`: a checkpoint at 1.234 s and a resume give the same commands at every later tick.

### End-to-end script and logging

`scripts/e2e/sim_open_loop.sh` (owned here; sources the STD-E2E helper; seed-explicit; idempotent; header
`bead=N15ap3-01 milestone=M1 seed=1`). Fixtures registered here, all `synthetic`: the rig
`fixtures/controllers/open-loop/rig-1dof.fbot` (one revolute joint, gravity off, an L1 card with every field
`assumed`, latency 0) and the schedules `demo-ramp` (the ramp above, `hold-last`), `demo-ramp-zero` (the same
with `zero`) and `demo-position` (the sine above on `j1`). Steps: (1) `frob doctor --json`; (2) the acceptance
run; `frob telemetry query <run> --channels actuator.torque --json`: assert 0.3 N·m at 0.3 s and 2.0 N·m at 2 s;
(3) the same run with `--key ol-ramp-2`: equal state digest; (4) `--controller open-loop:demo-ramp-zero
--seconds 3 --key ol-zero`: torque 0 after 2 s; `demo-ramp --seconds 3 --key ol-hold`: 2.0 N·m after 2 s;
(5) `demo-position --seconds 20 --key ol-pos`: exit 0 and a `ControllerId` different from step 2's; (6)
refusals with `e2e_expect_refusal FROB-REF-802 3`: `open-loop:no-such`, the planted `bad-joint` schedule (a
misspelt joint), and `open-loop:demo-ramp --policy zero`. Log: `target/e2e-logs/sim_open_loop/<utc>.ndjson` and
a transcript; every line has `ts`, `script`, `bead`, `step`, `event`, the exact command line, exit code, wall
time and the envelope's evidence block; `metric` lines give the torque samples with unit, expected value and
threshold; state digests for steps 2 and 3; refusals with code, pointer and first repair; on failure the first
differing sample and the run and schedule paths; a final `summary` line.

### Known answers and negative controls

Known answers: the ramp and sine values above (exact rationals; DESIGN fixture constants). Negative controls: a
mutant that evaluates the schedule at the previous control tick (one-tick lag) must fail `ramp_exact` (0.298 N·m
instead of 0.3 N·m) and step 2; a mutant that treats `hold-last` as `zero` must fail step 4. Determinism: commands
are D0 for `hold` and `ramp` (exact rationals) and D2 for `sine`; the run's digest lanes are those of `sim.run`.

## Considerations

- The command passes the actuator limiter and the card's envelope, so an open-loop torque above the card's
  current limit is clipped and reported, as for any controller; a known answer that needs an unclipped torque
  must choose a rig whose card admits it.
- Not a product controller: a schedule reads no state, so nothing it does is a claim about a design's control;
  runs under it carry `controller: open-loop:<name>` in the manifest, and its commands carry the nominal form of
  N22a-01's layer tag (rule 3), which prints the controller's kind, `open-loop`.
- Security: the loader reads only files under `fixtures/controllers/open-loop/` by name; no path from the caller
  is opened.
