## Background

A coupling transmission drives joints from motors through a matrix: a differential ankle, a wrist, a waist,
a tendon that spans two joints. The square, invertible case is handled with the other transmissions
(BD-074). This bead extends it to couplings that are **not square**, where one motor may drive several
joints, and fixes one way of writing the map so that every consumer agrees. Tier: Solid [S]. Owner
`frob-actuate`; consumers `frob-dyn`, `frob-control`, `frob-analyze`, `frob-mission`. Verb touched:
`actuator.envelope` (VERBS-actuator lists this bead as its extender); the signed motion witness of
`actuator.check` over a coupling matrix is N15b-12's.

**One map, written once.** A coupling is a matrix C(q) with motor rates θ̇ = C·q̇. Virtual work gives joint
efforts τ_joint = Cᵀ·τ_motor. Where the square matrix T of the earlier form (q̇ = T·θ̇) is invertible,
C = T⁻¹. Writing the map from joint rates to motor rates is the choice that stays defined when C has more
columns than rows.

**Rule 1: the feasible joint-torque set is an image.** With motor limits abs(τ_motor,k) ≤ τ_max,k it is the
zonotope Cᵀ·B, where B is the box of motor torques. It is not the box of per-joint limits. The shortcut is
wrong in a way that matters for control and for static screening: for one rotor with θ = 10·(q₁ + q₂) and
limit 0.1 N·m, the deliverable joint torques are (t, t) with abs(t) ≤ 1 N·m, while per-joint limits of
1 N·m would admit (1, −1) N·m, which no motor torque produces.

## Technical approach

**Type (DESIGN).**
```rust
pub struct CouplingMap { motors: Vec<ActuatorId>, joints: Vec<JointId>,
                         c: CouplingMatrix /* m × n: Constant(RationalMatrix) | Configured(ClosureJacobian) */ }
pub struct TorqueGenerator { motor: ActuatorId, g: Vec<Torque> /* length n */ }
impl CouplingMap {
    pub fn motor_rates(&self, q: &Config, qdot: &[AngVel]) -> Vec<AngVel>;          // θ̇ = C·q̇
    pub fn joint_torques(&self, q: &Config, tau_m: &[Torque]) -> Vec<Torque>;       // τ_joint = Cᵀ·τ_motor
    pub fn generators(&self, q: &Config, qdot: &[AngVel], cond: &Condition) -> Vec<TorqueGenerator>;
    pub fn contains(&self, gens: &[TorqueGenerator], tau: &[Torque]) -> Result<Vec<f64>, Separator>;
}
```

**Generators.** For motor k with available torque τ_max,k at its own speed θ̇_k = C_k·q̇ (from the
per-motor envelope of BD-073 at the stated winding temperature and bus voltage), the generator is
g_k = τ_max,k·C_kᵀ, where C_k is row k. The feasible set is { Σ_k λ_k·g_k : −1 ≤ λ_k ≤ 1 }. When the
positive and negative torque limits differ (voltage-limited in one direction), the generator carries an
interval [λ_k⁻, λ_k⁺] in place of [−1, 1].

**Membership and the separating witness.**
1. τ lies in the set iff the linear program "find λ in the box with Σ λ_k·g_k = τ" is feasible. It is
   solved in exact rationals for constant C (the small dense solver of BD-115), in double precision with a
   certified residual otherwise.
2. If infeasible, return a separator y with yᵀ·τ > h(y), where the support function is
   h(y) = Σ_k max(λ_k⁻·g_kᵀ·y, λ_k⁺·g_kᵀ·y). For the example, y = (1, −1) gives h(y) = 0.1·abs(10 − 10) = 0
   against yᵀ·τ = 2.
3. A torque command or a required operating point outside the set is refused with FROB-REF-131 (operating
   point outside the torque, speed and voltage envelope), returning the point, the separator, and the
   nearest point of the set.

**`actuator.envelope` output.** For an uncoupled joint the existing torque-against-speed boundary. For a
coupled group, an added object `joint_torque_set: { kind: "zonotope", joints: […], generators: [[…], …],
intervals: [[λ⁻, λ⁺], …], condition: {winding_temperature, bus_voltage, joint_rates} }`. The schema
`frob.actuator.envelope.out/1` gains the field; consumers must read it and may not rebuild a per-joint box.
A coupled group is addressed with the verb's existing input form `design:joint`, naming any joint of the
group (the verb takes a card or a `design:joint`, never a bare design); `joints` lists the group's joints in
the column order of C, whichever joint was named.
The input schema `frob.actuator.envelope.in/1` gains, for a coupled group, `--torque τ₁,…,τₙ` (a joint-torque
command for the group's joints, in joint order, at the condition's joint rates, rest by default), the vector
counterpart of BD-073's single-joint `--point τ,ω`. The verb's rule is unchanged: with `--require` an outside
command is refused with FROB-REF-131 (exit 3); without it the same fact is a finding (exit 2), carrying the
separator.

**Power identity.** For every q̇ and τ_motor: τ_jointᵀ·q̇ = τ_motorᵀ·C·q̇ = τ_motorᵀ·θ̇. Tested to 10⁻¹² on
random couplings and exactly in rationals for constant C.

**Consumers (their beads adopt; this bead supplies the data).** The cone solver carries τ_motor as
variables with the equality τ_joint = Cᵀ·τ_motor and box bounds on τ_motor, so force distribution and
whole-body control cannot ask for an unreachable joint torque. Static stability (A-08), task-wrench
attainability (A-24), the actuator-envelope analysis (A-11) and mission queries read the same generators.

**Evidence and determinism.** Generators inherit the class of the per-motor envelope (card provenance).
Constant-C results are D0.

## Test plan

### Unit tests
`crates/frob-actuate/tests/coupling_zonotope.rs`:
- `one_rotor_generator`: C = [10, 10], τ_max = 0.1 N·m: one generator (1, 1) N·m.
- `one_rotor_membership`: (0.5, 0.5) inside with λ = 0.5; (1, 1) on the boundary; (1, −1) outside with
  separator (1, −1); (1.2, 1.2) outside.
- `differential_generators`: q₁ = (θ₁ + θ₂)/2, q₂ = (θ₁ − θ₂)/2 gives C = [[1, 1], [1, −1]]; with limits
  (1, 1) N·m the generators are (1, 1) and (1, −1); the set is the diamond abs(τ₁) + abs(τ₂) ≤ 2, so
  (2, 0) is inside and (1.5, 1.5) is outside; the per-joint box [−2, 2]² would admit (1.5, 1.5).
- `power_identity_random` (10³ couplings, m ≤ 4, n ≤ 6).
- `asymmetric_limits`: a motor voltage-limited in one direction yields an interval [λ⁻, λ⁺] ≠ [−1, 1].
- `configured_coupling`: C(q) = [10 + 2·q₁, 10] with τ_max = 0.1 N·m, evaluated at q₁ = 0.5, gives the
  generator (1.1, 1.0) N·m.
- `separator_verifies`: for 10³ random outside points the returned y satisfies yᵀ·τ > h(y) exactly.
- `refusal_131_payload`.

## Considerations

- The zonotope has at most 2·C(m, n − 1) facets; consumers use the generator form and never enumerate
  facets.
- Transmission loss per motor (efficiency pair) shrinks each generator on the motoring side; the loss is
  applied per motor before the map.
- A consumer that keeps a per-joint box is wrong in both directions: it admits unreachable torques and
  rejects reachable ones (the diamond case). The consumers' adoption is carried by N15b-39, N15b-40 and
  N15b-41 and, for A-11, by BD-103.
