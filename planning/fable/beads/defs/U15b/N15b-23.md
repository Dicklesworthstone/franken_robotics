## Background

A kill gate is a decision named in advance, with its trigger, its milestone, the measurement that decides
it, its fallback, and what changes downstream. Each is recorded as an architecture decision record when
decided.

**KILL-SINEW-ROTOR**, as registered:

| Field | Value |
|---|---|
| Trigger | The hover known answer or the port balance fails, **or** the hybrid variant has no consumer at the milestone that funds frontier physics |
| Decided at | M6 |
| Measurement | The pilot record of N15b-22 (hover thrust and induced power by hand; ledger residual of the stepped hover with a climb); a consumer inventory for the aerial-terrestrial hybrid variant |
| Fallback | The rotor port and the variant are withdrawn |
| Downstream if it fires | The element N15b-36 is not built; the hybrid variant leaves the archetype catalog; a design that declares a rotor port is refused as a capability not implemented; reports name the withdrawal |

The rotor port is a Moonshot [M] item, off the critical path, and the scope statement of the plan admits it
only as a narrow exception to "no full aerodynamics, no flying robots". Withdrawing it costs nothing on the
critical path. This decision is one step more urgent than its milestone's default because the element bead
and the epic wait on it.

## Scope

In: collecting the pilot verdict and the consumer inventory; evaluating the trigger as written; the decision
record; updating the element bead, the epic and the status table. Out: running the pilot; building the
element.

## Technical approach

**Procedure.**
1. Read the pilot record: hand values reproduced, settled thrust and power, ledger residual against its
   registered tolerance, verdict, reviewer. A missing pilot counts as failed.
2. Consumer inventory: does any funded archetype, task family or owner-approved design at M6 use the hybrid
   variant? The answer is a list of identifiers or "none", supplied by the owner of the archetype catalog
   and dated.
3. Trigger: fired if (pilot falsified: the hover answer or the balance failed) or (inventory is "none").
4. Write `docs/adr/KILL-SINEW-ROTOR.md` (DESIGN path) with the inputs' digests, the evaluation, the
   outcome, the date and the deciding session.
5. If fired: close N15b-36 as withdrawn with the record as its typed reason; remove the hybrid variant from
   the catalog through a typed change; set the status table row to "rotor port: withdrawn
   (KILL-SINEW-ROTOR)"; tell the epic. If not fired: release N15b-36.
6. When the element is later built, the gate has a second reading: if the hover known answer or the port
   balance fails on the referee in production code, the gate fires then, and the same withdrawal applies.
   The record is amended by a new entry, never edited.

**Fail-closed default until decided.** Withdrawn: no rotor port is available, and a design declaring one is
refused (exit 5).

**Who decides.** The Sinew lead prepares the record; a fresh-context session that did not run the pilot
reviews it; the owner's choice of which Moonshot epics are funded at M6 (at most four active) can make the
"no consumer" clause true by itself.

## Acceptance criteria

- [ ] The decision record exists, cites the pilot record and the consumer inventory by digest, and states
  which clause decided.
- [ ] Exactly one of: N15b-36 released for work, or N15b-36 closed as withdrawn with the record as reason.
- [ ] The status table, the archetype catalog and the epic agree with the outcome.
- [ ] A design that declares a rotor port is refused whenever the outcome is "fired".
- [ ] The record predates the M6 exit review.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_gates.rs`:
- `kill_sinew_rotor_record_complete`: trigger, inputs, outcome, date, reviewer present.
- `no_consumer_fires`: with an empty inventory the derived outcome is "fired" whatever the pilot says.
- `withdrawn_rotor_port_refused`: when fired, lowering a design with a rotor port returns the capability
  refusal.

### End-to-end script and logging
`scripts/e2e/kill_sinew_rotor.sh` re-derives the outcome from the stored pilot verdict and inventory,
compares it with the record, and, when the outcome is "fired", runs `frob design check hybrid-rotor --json`
expecting exit 5. It sources the shared helper of STD-E2E and logs the inputs' digests, the derived and
recorded outcomes, the refusal, and a summary naming KILL-SINEW-ROTOR.

### Known answers and negative controls
The trigger's clauses are the known answers of the rule: failed hover answer → fired; failed balance →
fired; no consumer → fired; all three clear → not fired. Negative control: a record that says "not fired"
with an empty inventory must make the script fail.

## Considerations

- The second clause depends on a funding choice, not on physics; the record must keep the two apart so that
  a later consumer can reopen the item with the pilot's result still valid.
- Withdrawal must be visible by name: a capability that fell back at its kill gate is described by the name
  of the fallback, never left silently absent.
