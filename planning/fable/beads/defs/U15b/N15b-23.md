## Background

A kill gate is a decision named in advance, with its trigger, its milestone, the measurement that decides
it, its fallback, and what changes downstream. Each is recorded as an architecture decision record when
decided.

**KILL-SINEW-ROTOR**, as registered:

| Field | Value |
|---|---|
| Trigger | The hover known answer or the port balance fails, **or** the hybrid variant has no consumer at the milestone that funds frontier physics |
| Decided at | M6 |
| Measurement | The pilot record of N15b-22 (hover thrust and induced power by hand; ledger residual of the stepped hover with a climb); a consumer inventory for the aerial-terrestrial hybrid variant |
| Fallback | The rotor port and the variant are withdrawn |
| Downstream if it fires | The element N15b-36 and the hybrid variant template N14bp1-02 (both on the admitting branch only) are closed as withdrawn and never written; a design that declares a rotor component is refused; the status table and reports name the withdrawal |

The rotor port is a Moonshot [M] item, off the critical path, and the scope statement of the plan admits it
only as a narrow exception to "no full aerodynamics, no flying robots". Withdrawing it costs nothing on the
critical path. This decision is one step more urgent than the Moonshot default (priority 4, so priority 3)
because the element bead and the epic wait on it.

## Scope

In: collecting the pilot verdict and the consumer inventory; evaluating the trigger as written; the decision
record; the gate row's decision and the owner declaration; the synthetic fixture design
`assets/fixtures/sinew/rotor/hybrid-rotor.fbot` used by the refusal test; updating the element bead, the
variant bead, the epic and the status table. Out: running the pilot; building the
element.

## Technical approach

**Procedure.**
1. Read the pilot record: hand values reproduced, settled thrust and power, ledger residual against its
   registered tolerance, verdict, reviewer (the record in `crates/frob-conformance/registry/pilots.toml`).
   A missing pilot result is not a pass: the outcome is decided by step 3.
2. Consumer inventory: does any funded archetype, task family or owner-approved design at M6 use the hybrid
   variant? The answer is a list of identifiers or "none", supplied by the owner of the archetype catalog
   and dated.
3. Outcome, in the four names of the kill-gate record (N40-03): `fired` if the pilot was falsified (the
   hover answer or the balance failed) or the inventory is "none" (either clause decides alone);
   `not-fired` if the pilot's verdict is `falsifier-rejected` and the inventory names at least one consumer;
   `not-reached` if the pilot was never run because the owner did not fund the epic and the inventory names
   a consumer (an unfunded mechanism is recorded as unfunded, never as passed and never as killed; it does
   not exist and is not described); `deferred` only through an ADR that names the later exit and its reason.
4. Write `docs/adr/ADR-KILL-SINEW-ROTOR-M6.md` (the program's one directory for decision records) with the
   fields N40-03 requires: the kill gate; the milestone; the trigger as registered and the amendments
   applied; each input with its receipt hash beside the clause it decides (the pilot record's identifier
   and verdict, the accumulated residual against 10⁻⁶ of the shaft energy, the settled thrust against 10⁻⁶
   relative, the dated consumer inventory's digest); the outcome; the fallback in force and the name the
   capability carries from now on; the beads re-read (N15b-36, N14bp1-02 and the design-path script
   N15bp2-01: released, or superseded by this ADR); what changes downstream; the recording session, which did
   not run the pilot.
5. Registry: write the `decision` table (`outcome`, `adr`, `date`, `session`, and `receipts`, the hashes of the
   receipts the inputs cite, at least one for `not-fired`; N40-03's form) of the KILL-SINEW-ROTOR row that
   the fallback ledger N40-23 entered in `registries/gates.toml`, and the gate's owner declaration that the
   cross-check N40-30 compares with the ledger (`[[gate]]` with `role = "owner"`, the ledger's current
   `trigger`, `fallback`, `decided`, `mode` and `reads` copied, not restated, and `decision` with each
   measured value citing its receipt) in `frob-actuate`'s `contract.toml`.
6. If fired: close N15b-36 with reason `fallback` and N14bp1-02 and N15bp2-01 as `superseded`, each citing
   the ADR; set the status table row to "rotor port: withdrawn (KILL-SINEW-ROTOR)"; close the epic BD-419 with
   the ADR as its typed reason. If not fired: release N15b-36 (and through it N14bp1-02, then N15bp2-01). If
   not reached: none is started; all three close with the ADR as reason.
7. When the element is later built, the gate has a second reading: if the hover known answer or the port
   balance fails on the referee in production code, the gate fires then, and the same withdrawal applies.
   The decision becomes an array (N40-03): a second entry with its own ADR is appended; the latest entry is
   in force and the first is never edited.

**Fail-closed default until decided, and the refusal after a withdrawal.** No rotor port is available. A
design that declares a `rotor` component is refused at stage 1 with `FROB-REF-103` (unknown field, exit 3,
naming the key and its location): the component kind exists only in a build with the cargo feature
`variant-aerial`, which N14bp1-02 adds on the admitting branch alone, and that bead states the same refusal
for a build without the feature. DESIGN, choosing between two statements: this bead first said "exit 5,
capability not implemented", but that refusal (`FROB-REF-724`, N00-02) is raised by dispatch for a verb whose
capability is `not-in-build` or `killed`, not for a design field, and no bead on the withdrawing branch
writes code to recognize a withdrawn kind; the withdrawal is named instead by the status table and by the
ADR.

**Who decides.** The Sinew lead prepares the record; a fresh-context session that did not run the pilot
reviews it; the owner's choice of which Moonshot epics are funded at M6 (at most four active) can make the
"no consumer" clause true by itself.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_gates.rs`:
- `kill_sinew_rotor_record_complete`: trigger, inputs, outcome, date, reviewer present; the ADR's path is
  `docs/adr/ADR-KILL-SINEW-ROTOR-M6.md`.
- `kill_sinew_rotor_rule`: the pure rule on synthetic inputs: (pilot `falsifier-rejected`, inventory
  ["hybrid-survey-01"]) → `not-fired`; (pilot `falsifier-holds`, same inventory) → `fired`; (pilot
  `falsifier-rejected`, inventory "none") → `fired`; (no pilot result, inventory names a consumer) →
  `not-reached`; every returned outcome is one of N40-03's four.
- `no_consumer_fires`: with an empty inventory the derived outcome is `fired` whatever the pilot says.
- `withdrawn_rotor_port_refused`: on a build without `variant-aerial`, parsing the fixture design
  `assets/fixtures/sinew/rotor/hybrid-rotor.fbot` (`synthetic`: the `quad-mammal` term with one `rotor`
  component) returns `FROB-REF-103` naming the key `rotor`.

### End-to-end script and logging
`scripts/e2e/kill_sinew_rotor.sh` (header `# e2e: bead=N15b-23 milestone=M6 labels=sinew,kill-gate
gates=KILL-SINEW-ROTOR seed=0 needs=cpu plants=not-fired-with-empty-inventory`) re-derives the outcome from
the stored pilot verdict and inventory, compares it with the ADR and the gate row, runs
`cargo test -p frob-conformance --test kill_ledger` (asserting that no failure names KILL-SINEW-ROTOR),
and, when the outcome is not
`not-fired`, runs `e2e_expect_refusal FROB-REF-103 3 -- frob design new rotor-probe --file
assets/fixtures/sinew/rotor/hybrid-rotor.fbot --key ksr-1 --json`. It sources `scripts/e2e/lib.sh` (STD-E2E)
and writes `target/e2e-logs/kill_sinew_rotor/<utc>.ndjson`; every line carries `ts`, `script`, `bead`,
`step`, `event`, the exact command line, exit code and wall time; it logs each input with its digest and the
threshold of the clause it decides, the derived and recorded outcomes, the refusal with its code and exit,
and a `summary` naming KILL-SINEW-ROTOR. It writes nothing to the registry; the recording session does.

### Known answers and negative controls
The trigger's clauses are the known answers of the rule: failed hover answer → `fired`; failed balance →
`fired`; no consumer → `fired`; all three clear → `not-fired`; pilot never run with a consumer →
`not-reached`. Negative control (plant `not-fired-with-empty-inventory`): a record that says `not-fired`
with an empty inventory must make the script fail, and `kill_ledger` must report
`outcome-contradicts-measurement`.

## Considerations

- The second clause depends on a funding choice, not on physics; the record must keep the two apart so that
  a later consumer can reopen the item with the pilot's result still valid.
- Withdrawal must be visible by name: a capability that fell back at its kill gate is described by the name
  of the fallback, never left silently absent.
