## Background

A coupled transmission drives several joints from one or more motors: a differential ankle, wrist or waist, or a
tendon that spans two joints. The chapter on actuators writes every such coupling as one matrix C(q) with motor
rates θ̇ = C·q̇; virtual work then gives joint efforts τ_joint = Cᵀ·τ_motor. C need not be square. Two rules about
it bind the controllers.

1. *The feasible joint-torque set is an image.* With motor limits abs(τ_motor,k) ≤ τ_max,k it is the zonotope
   Cᵀ·B, where B is the box of motor torques. It is not the box of per-joint limits. The plan states the
   consequence for control: the cone solver carries τ_motor as variables with τ_joint = Cᵀ·τ_motor.
2. *Rotor inertia is pulled back once.* The rotors add Cᵀ·diag(J_r)·C to the joint-space mass matrix, with its
   off-diagonal entries, in one place, the model lowering, and never again in a controller's model.

The known answer that shows what a shortcut costs: one base-mounted rotor with θ = 10·(q₁ + q₂), torque limit
0.1 N·m and inertia 0.01 kg·m². The deliverable joint torques are (t, t) with abs(t) ≤ 1 N·m. Per-joint limits of
1 N·m admit (1, −1) N·m, which no motor torque produces. The reflected inertia is [[1, 1], [1, 1]] kg·m², not
diag(1, 1).

The map, its generators and exact membership are bead N15b-10; the single pull-back and the flag
`rotor_inertia: Included` on the model are bead N15b-11. Both say that the consumers adopt in their own beads.
This is the adoption in `frob-control`, whose M1 programs are the cone-program layer (N22a-08) and the stance
force distribution with its torque boxes (N22a-09). Tier: Solid. Without this bead a controller on a design with
a differential joint would command torques the motors cannot produce, and its certificates of infeasibility
would name a joint where the binding limit is a motor.

## Scope

In: one constraint builder for actuator torque rows, used by every control program, that introduces motor-torque
variables for coupled groups; its use in the stance force-distribution program and the static-support program;
certificates and flags that name motors; the controller model's assertion that rotor inertia is already in the
mass matrix, and the absence of any armature parameter in a controller record. Out, with the bead that has each:
the coupling map, the generators and membership (N15b-10); the pull-back in the lowering and the model flag
(N15b-11); the program layer, end states and certificate checking (N22a-08);
the force-distribution program itself (N22a-09); the whole-body program of M3 (N22a-14), the skill allocation
program of M4 (N22b-03) and the traction-at-wrench program of M2 (N24c-17), which call the same builder when
they are built; the same adoption in the static analyses (N15b-40) and in mission lowerings (N15b-41).

## Technical approach

1. **Builder (DESIGN).** In `crates/frob-control/src/program/torque_rows.rs`:
   ```rust
   pub struct TorqueRows { pub motor_vars: Vec<MotorVar>,          // one per motor of a coupled group
                           pub equalities: Vec<LinRow>,           // Cᵀ·τ_m − τ_joint = 0 on coupled joints
                           pub boxes: Vec<BoxRow> }               // per motor, and per uncoupled joint
   pub fn torque_rows(model: &RobotModel, q: &Config, qdot: &[AngVel], cond: &Condition) -> TorqueRows;
   ```
   For each coupled group the builder reads the group's `CouplingMap` from the model and the per-motor available
   torque at the motor's own speed θ̇_k = C_k·q̇ (the generators of N15b-10, at the stated winding temperature and
   bus voltage). It adds m variables τ_m, n equalities Cᵀ·τ_m = τ_joint, and m box rows
   λ_k⁻·τ_max,k ≤ τ_m,k ≤ λ_k⁺·τ_max,k (the interval is [−1, 1] unless the motor is voltage-limited in one
   direction). For an uncoupled joint the map is the scalar gear ratio and the builder emits the joint box
   directly, with no added variable, so programs for uncoupled designs keep their size.
2. **No other source of torque limits.** The builder is the only function in `frob-control` that reads actuator
   limits. A workspace test greps the crate: no other module calls the per-motor envelope, and no program
   constructs a per-joint box for a joint that belongs to a coupled group. A request to build such a box is
   refused with FROB-REF-131 (an operating point outside the envelope), returning the group and its generators.
3. **Stance force distribution.** The program of N22a-09 has rows −τ_max ≤ Jᵢᵀ·fᵢ ≤ τ_max componentwise. With the
   builder they become: τ_joint = −Jᵀ·f as before; for joints of a coupled group, Cᵀ·τ_m = τ_joint and boxes on
   τ_m. The program stays a cone program of the same class. The flag `stance-saturated` is raised when a motor
   box is active, and the result lists the active motors.
4. **Certificates.** An infeasibility certificate carries multipliers on the motor boxes; its binding set names
   the motor (`ActuatorId`), and the ranked repairs are `swap-actuator` and `regear` on that motor. The exact
   re-check of certificates is unchanged: the added rows are linear.
5. **One source of inertia.** `ControlModel::from_robot_model` asserts `rotor_inertia: Included` on the model and
   refuses to build otherwise (a model lowered by a version that predates the flag is a form error). The
   canonical controller record that is hashed into `ControllerId` has no reflected-inertia or armature field; a
   schema test forbids adding one. Every controller's mass matrix is the model's.
6. **Evidence and determinism.** Rows are exact rationals for constant C; for a coupling that varies with
   configuration the entries are the closure's Jacobian in double precision, with the same class as the program
   they enter. Nothing in the envelope changes for uncoupled designs.

## Acceptance criteria

- [ ] `torque_rows` exists and is the only reader of actuator limits in `frob-control` (workspace test).
- [ ] One-rotor fixture (θ = 10·(q₁ + q₂), limit 0.1 N·m): a required joint torque of (1, −1) N·m is reported
      `infeasible` with a certificate that names the motor; (0.5, 0.5) N·m is feasible with τ_m = 0.05 N·m.
- [ ] Differential fixture (two motors, limits 1 N·m each, θ₁ = q₁ + q₂, θ₂ = q₁ − q₂): joint torque (2, 0) N·m is
      feasible with τ_m = (1, 1); (1.5, 1.5) N·m is infeasible (it needs τ_m = (1.5, 0)).
- [ ] The static-support program of a stance whose ankle is that differential returns the motor, not a joint, in
      the binding set of its infeasibility witness.
- [ ] For a design with no coupled group the programs are bit-identical to those built before this bead (same
      variable count, same rows).
- [ ] `ControlModel` built from a model without the flag is refused; the controller record schema has no inertia
      field; the controller's mass matrix for the one-rotor fixture contains [[1, 1], [1, 1]] kg·m² from the
      rotor exactly once.
- [ ] The three negative controls below are caught.

## Test plan

### Unit tests
`crates/frob-control/tests/coupled_torque_rows.rs` (fixtures `synthetic`):
- `one_rotor_image`: the two commands of the second acceptance criterion; the separator y = (1, −1) has support
  value 0 against yᵀ·τ = 2.
- `differential_diamond`: the set is abs(τ₁) + abs(τ₂) ≤ 2 in joint torques; (2, 0), (0, −2) and (1, 1) are
  inside; (1.5, 1.5) and (2, 2) are outside.
- `uncoupled_unchanged`: row and variable counts and coefficients equal the pre-existing boxes on a quadruped
  with twelve independent joints.
- `asymmetric_interval`: a motor voltage-limited in one direction gives the box [λ⁻·τ_max, λ⁺·τ_max].
- `certificate_names_motor`, `flag_lists_active_motors`.
- `single_reader_of_limits` and `no_armature_field` (source and schema checks).
- `control_model_asserts_flag`, `rotor_inertia_once`.

### End-to-end script and logging
Fixture `slope-differential-ankle` (`synthetic`, owned here under `assets/fixtures/sinew/coupled-control/`, a
registered fixture supplying design, scene and task). No archetype can be the base: the `quad-mammal` template
of BD-109 has hip abduction, hip pitch and knee and no ankle, and four feet leave the foot loads free, so the
stance program could move load off the coupled leg. The design is therefore the three-legged body of N15b-40's
`a08-differential-ankle` (contact points A = (0.30, 0, 0), B = (−0.15, 0.20, 0), C = (−0.15, −0.20, 0) m in
the ground plane; legs B and C rigid with point feet rated 100 N; leg A rigid down to the two-axis ankle, q₁
pitch about +y and q₂ roll about +x, two motors of 1 N·m, C = [[1, 1], [1, −1]], both axes through
P = (0.25, 0.05, 0) m, so the contact is 0.05 m from each axis and only the normal force at A loads the
ankle: τ = (0.05·f_A, 0.05·f_A) N·m). Body and payload weigh 60 N with the centre of mass over the origin of
the contact frame at a height of 0.30 m; the scene is a plane inclined 10° with leg A downhill (μ = 0.8); the
task is to stand for 5 s. Normal loads: f_A = (0.30·60·sin 10° + 0.15·60·cos 10°)/0.45 = 26.64 N and
f_B = f_C = 16.22 N, so the stance needs ankle torques (1.332, 1.332) N·m: inside the bounding box ±2 N·m per
joint, outside the diamond (abs(τ₁) + abs(τ₂) = 2.664 > 2), requiring τ_m = (1.332, 0) of motor 1 (on flat
ground the same body needs (1, 1) N·m, on the diamond's boundary). The fixture records these values.

`scripts/e2e/sinew_coupled_control.sh`: `frob design check slope-differential-ankle --json` (exit 0 or 2;
the design is admitted, since the slope is the scene's), then `frob sim run --fixture slope-differential-ankle
--tier referee --seconds 5 --seed 3 --key cc-stand --json` (the design's baseline controller for the task,
whose stance program is N22a-09's with this bead's rows), then `frob telemetry query <run> --channel
actuator.torque,control.flags --json`. Asserts: no commanded motor torque exceeds its limit (motor 1 held at
1 N·m); `stance-saturated` lists motor 1, not a joint; whether the body then tips within the 5 s is logged and
not asserted, since the needed pair is outside the diamond; the same run in a build with
`mutant-control-bounding-box` (`--key cc-stand-m`) commands motor 1 at 1.332 N·m, above its limit, and is
caught. Sources the shared helper of STD-E2E and writes
`target/e2e-logs/sinew_coupled_control/<utc>.ndjson`: command, exit code, wall time, evidence block, the largest
abs(τ_m,k)/τ_max,k with threshold 1, the active-motor list, digests and seed.

### Known answers and negative controls
The one-rotor table of the coupled-transmission known answer (deliverable torques (t, t) with abs(t) ≤ 1 N·m;
reflected inertia [[1, 1], [1, 1]] kg·m²). Negative controls: `mutant-control-per-joint-box` (the builder emits
per-joint boxes of ±1 N·m for the one-rotor fixture and admits (1, −1)); `mutant-control-bounding-box` (the
differential fixture gets the bounding box ±2 N·m per joint and admits (1.5, 1.5)); `mutant-rotor-added-twice`
(the controller model adds the reflected rotor term on top of the model's matrix; the one-rotor inertia reads [[2, 2], [2, 2]]).
Metamorphic: permuting motors within a group permutes multipliers and changes no feasible set. Determinism:
exact for constant C; twice on one machine with identical program bytes.

## Considerations

- A coupled group with m motors and n joints adds m variables and n equalities per program; for the differential
  joints of a humanoid (ankles, wrists, waist) that is under twenty variables in total.
- Later programs (whole-body control at M3, skill allocation at M4, traction capacity at M2) must call the same
  builder; a second reader of actuator limits fails the workspace test, which is how the rule survives new code.
- The batched controllers of M2 lower the same rows to kernels; a coupling that varies with configuration then
  needs the closure Jacobian per world, which is an input the kernel already has from the lowering.
