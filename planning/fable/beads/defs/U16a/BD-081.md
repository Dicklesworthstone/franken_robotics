## Background

The referee adjudicates the fast tiers, so its step has two duties a throughput step does not have: a controller
must never observe a half-finished step, and a numerical difficulty must end in a clean retry or a named refusal,
never in an approximation that looks like physics (ADR-KIN-02). FrankenSim, which supplies the referee's dynamics
and contact solve through the airlock, has no persistent contact time stepper (its contact solve is an event
solve); time stepping, warm starts, friction memory and the commit fence are therefore this project's own
(FACT at the pinned commit; upstream work item FD-FSIM-02).

DESIGN: the `referee` profile and the `strict` profile of `batch-cpu` advance each world by one **transaction
per accepted physics interval** (one base interval [t0, t1), where t1 = min(t0 + h, next clock boundary)). A
transaction either commits a complete, checked interval or leaves no trace. Two invariants make that statement
testable:

- INV-KIN-01: no reader observes uncommitted state; every read names a `commit_epoch`.
- INV-KIN-02: a retry restores the whole restore set; a transaction that commits on attempt k from checkpoint S
  yields the same digest as a run that started from S with plan k.

Alternatives rejected: an in-place step with "undo" of selected fields (any omitted field makes a retried interval
differ from a first attempt); a per-subsystem rollback protocol (no single place proves completeness); letting
readers see the candidate "because it is usually committed" (a controller would then act on a state that a retry
later erases).

## Scope

In: the restore set and its registry; checkpoint and restore; the committed state with its monotone epoch and
the only read path; the transaction driver (steps T1, T2, T3, T6, T7 and the hook points for T4 and T5); the
`Faulted` outcome; the fault-injection harness and the 10⁵-fault test. Out: base intervals and the dyadic grid
(N16a-06); event location and the advance inside T4 (BD-082); island impulses (N16a-07); the checks of T5
(N16a-08); the retry ladder's plans and the refinement law for random inputs (BD-083); witness migration
(BD-093); the same transaction on `batch-cpu` kernels (BD-161); packet queues' own checkpoint code (BD-098).

## Technical approach

**The restore set.** A checkpoint taken at the start of a transaction, and restored in full on every retry,
contains the components below. Omitting any of them makes a retried interval differ from a first attempt.

| # | Component | Owner crate (implements `Restorable`) |
|---|---|---|
| 1 | Physical state (q, v) | `frob-dyn` |
| 2 | Actuator, thermal and battery states | `frob-actuate` |
| 3 | Contact memory: witness pairs, contact frames, tangential memory, the warm-start impulses and the active set | `frob-contact` |
| 4 | Per-contact film thickness (wet and greasy floors) | `frob-contact` (the slot exists from M1; populated when the film law lands) |
| 5 | Clock phases and packet queues | `frob-sense` |
| 6 | Controller and estimator states | `frob-control` |
| 7 | The ordinals of every sample-stamped random draw | `frob-dyn` (counters only: streams are counter-based and have no generator state) |
| 8 | Terrain edits | `frob-scene` |
| 9 | The accumulators of the energy ledger | `frob-chronicle` |
| 10 | Event counters | `frob-dyn` |
| 11 | The command cursor | `frob-dyn` |

```rust
// DESIGN. Defined in frob-dyn; higher crates implement and register (the layering rule for services above a crate).
pub trait Restorable {
    fn component(&self) -> ComponentId;                      // stable dotted name, e.g. "sense.packet-queues"
    fn checkpoint(&self, w: &mut CheckpointWriter);
    fn restore(&mut self, r: &mut CheckpointReader) -> Result<(), Refusal>;
    fn digest(&self, h: &mut Blake3Hasher);                  // canonical bytes of the live state
}
pub struct RestoreSet { parts: Vec<(ComponentId, Box<[u8]>)>, manifest: Blake3 }
pub struct CommitEpoch(pub u64);                             // monotone per world; 0 at reset
pub struct Committed { epoch: CommitEpoch, /* state, impulses, sensor inputs, diagnostics */ attempt: u8 }
pub struct EpochReader<'a> { /* borrows one Committed, never a candidate */ }
pub enum StepOutcome {
    Committed { epoch: u64, attempt: u8, events: Vec<EventRecord>, checks: CheckReport },
    Faulted { refusal: Refusal /* FROB-REF-220 or FROB-REF-221 */ },
}
```

Completeness is enforced, not trusted: a world is built from a `WorldManifest` listing every state-bearing
component; construction fails if a listed component has no registered `Restorable`, and the inventory test below
mutates each component after a checkpoint and requires `restore` to return the world digest to its checkpoint
value.

**The fence.** Committed state carries a monotone `commit_epoch`. Controllers, sensor samplers, telemetry and
snapshots read a named epoch through `EpochReader` and nothing else. A candidate interval is built beside the
committed state, in a `Candidate` object that no reader API can reach, and becomes visible only when the epoch
advances, in one step (a swap of the committed pointer; state, impulses, sensor inputs, diagnostics and the
attempt index are published together). On the lockstep tiers the same rule holds at the kernel-batch boundary: a
host reader sees a completed batch or the previous one (implemented with the batched step, BD-159).

**The driver.**

```text
DESIGN  transaction(X_committed, [t0, t1))        # t1 = min(t0 + h, next clock boundary)
T1  S ← checkpoint(X_committed)                   # the whole restore set
T2  for attempt in 0 ..= N_retry:                 # N_retry = 3; attempt selects a numerical plan only
T3    X ← restore(S); work ← [(t0, t1)]
T4    while work is not empty: advance one sub-interval, locating events          (BD-082, N16a-07, BD-093)
T5    checks on the candidate                                                       (N16a-08)
T6    if every check passes: COMMIT (advance commit_epoch; publish state, impulses, sensor inputs,
      diagnostics and the attempt index together) and return
T7  after the last attempt: restore(S); mark the world Faulted with cause numerical-fault (FROB-REF-221);
    publish nothing from the failed interval
```

1. The plan for an attempt comes from `trait PlanProvider { fn plan(&self, attempt: u8, state: &RestoreSet) ->
   NumericalPlan }`. This bead ships the provider for attempt 0 (the declared plan); the four-rung ladder is
   BD-083. The provider is a deterministic function of state, so a replay repeats the same attempts. Retries
   change numerical parameters only (ADR-KIN-05): the driver asserts the physical-parameter digest before and
   after (N16a-04). The ladder the driver must be able to host (DESIGN; implemented by BD-083): attempt 0 is
   the declared plan; attempt 1 halves the largest admitted sub-interval and forces bisection for event
   location; attempt 2 tightens the solver tolerance by ten, doubles the iteration cap and clears the warm
   start; attempt 3 switches the island solver (semismooth Newton to the fixed-point cone iteration).
2. The attempt that committed is part of the result (`StepOutcome::Committed.attempt`) and of the chunk record.
3. `FROB-REF-220` (event refinement limit) raised inside T4 ends the transaction at once, without further
   attempts: the checkpoint is restored and the world is `Faulted` with that refusal. `FROB-REF-221`
   ("Transaction exhausted: every numerical plan of the retry ladder failed its checks") is raised at T7;
   ranked repairs: teleport and inspect. Both exit with code 3 when they are the verb's outcome.
4. **A numerical failure is not a physical failure.** A world that exhausts its retries ends with
   `numerical-fault`, which the failure taxonomy keeps apart from `fall`, `slip` or `collision`. A design is
   never scored as having fallen because a solver gave up, and summary statistics state how many worlds were
   excluded for this cause (counterexample CX-150). A `Faulted` world refuses further steps with the stored
   refusal; its last committed epoch stays readable.
5. Order at a boundary: after COMMIT at t1 the boundary ordering rule of the clock contract runs on the
   committed state (close exposures, enqueue samples, deliver packets, run estimator and controller ticks,
   latch commands, open exposures), and the next transaction reads the commands latched there.
6. Cancellation: a cancellation request observed inside a transaction abandons the candidate, restores S and
   returns with the last committed epoch; request, drain, finalize.

**Fault injection (feature `chaos`, tests only).** Injection points: after every sub-interval of T4, between T5
and T6 (the gate's point), inside `checkpoint`, inside `restore`. Fault kinds: forced check failure, unwind of
the transaction task, cancellation, delay. A reader probe runs concurrently under a seeded deterministic
schedule, reads through `EpochReader`, and compares the digest of what it read with the digest recorded for that
epoch at commit. Any mismatch is an uncommitted read.

## Acceptance criteria

- [ ] Seed done-condition: zero uncommitted reads observed in 10⁵ injected faults (row of GATE-KIN-04, referee
      part at M1), with the measured count recorded in `registries/gates.toml`.
- [ ] The leaky-fence mutant (a reader handed the candidate) is caught by the same test.
- [ ] Inventory test: for each of the 11 components, a post-checkpoint mutation is undone by `restore`; a world
      with an unregistered state-bearing component fails to build.
- [ ] The omission mutants (packet queues left out; warm starts left out) change the digest of a forced retry
      and are caught (the digest-equality row itself closes with the retry ladder, BD-083).
- [ ] After T7 the world digest equals the checkpoint digest, the world is `Faulted` with cause
      `numerical-fault` and `FROB-REF-221`, and no chunk, impulse or sensor input of the failed interval exists.
- [ ] A `Faulted` world is counted under outcome kind `numerical` and never under `fall`, `slip` or `collision`.
- [ ] `commit_epoch` is strictly monotone per world; every read API takes or returns an epoch.
- [ ] Cancellation inside a transaction leaves the committed state byte-identical.
- [ ] `CONTRACT.md` lists INV-KIN-01 and INV-KIN-02 with these tests.

## Test plan

### Unit tests

- `txn::fence_zero_uncommitted_reads`: 10⁵ injected faults over random intervals of the reference quadruped and
  the G1 on the referee, seeds 0..99 × 1,000 faults; assert the probe's mismatch count is 0. Reports `faults`,
  `reads`, `uncommitted_reads`.
- `txn::leaky_fence_mutant_caught` (negative control, feature `mutant-leaky-fence`): mismatch count > 0.
- `txn::restore_inventory`: mutate each component (flip a warm-start impulse, enqueue a packet, advance a
  controller integrator, bump an energy accumulator, edit a terrain cell, advance the command cursor); restore;
  compare per-component and whole-world digests.
- `txn::unregistered_component_refused`: build refused, naming the component.
- `txn::omission_mutants`: with `sense.packet-queues` or `contact.warm-start` removed from the set, a forced
  retry's digest differs from the clean run.
- `txn::exhaustion_publishes_nothing`: a provider whose plans all fail a check; assert `Faulted`,
  `FROB-REF-221`, checkpoint digest restored, no chunk written, epoch unchanged.
- `txn::epoch_monotone` (property): epochs increase by one per commit and never on a retry.
- `txn::attempt_recorded`: a forced failure of attempt 0 and success of attempt 1 commits with `attempt = 1`.
- `txn::cancel_mid_transaction`: cancel at each injection point; committed digest unchanged; no leaked buffers.
- `txn::replay_repeats_attempts`: the same seed and state repeat the same attempt sequence.

### End-to-end script and logging

`scripts/e2e/kin_transaction_referee.sh` (bead N16a-10) runs `frob sim run g1 --tier referee --profile referee
--seconds 2 --seed 7 --json` twice and asserts equal digests and a monotone `commit_epoch` in telemetry, then
runs the chaos build's `frob sim run … --chaos faults=1000,seed=3` (DESIGN test-only flag) and asserts
`uncommitted_reads = 0`. Log lines: `event: "metric"` with `faults`, `uncommitted_reads` and threshold 0;
`event: "assert"` with both digests; on failure the first epoch and component whose digest differed and the path
of the saved checkpoint.

### Known answers and negative controls

- KA-342 (INV-KIN-01, GATE-KIN-04): faults between T5 and T6; zero uncommitted reads in 10⁵ faults; exact count;
  tier G4 on `referee` and `strict`; control: a reader that sees a candidate interval.
- KA-341 (INV-KIN-02): forced-retry digest equals the clean run with the same plan on 10⁴ random intervals;
  control: packet queues or warm starts omitted from the restore set (this bead supplies the controls; the row
  is measured with the ladder).
- CX-150: a world whose solver gave up is not a failed episode.
- Metamorphic: splitting a rollout at a snapshot and resuming equals running it whole; a retry equals a clean
  run with the same plan.
- Determinism lanes: twice on one machine; debug and release; the referee lane on one platform.

## Considerations

- The restore set crosses seven crates; the registry is the single place where completeness is proved, and a new
  stateful feature (a new sensor filter, a new actuator state) fails the build until it registers.
- Checkpoint cost is paid every transaction. At M1 worlds are few (one to a few dozen); the cost is measured and
  printed with the referee's real-time factor (TARGET at least 0.2 times real time for a humanoid on one core).
- OPEN-KIN-5 owns N_retry = 3 with L_max and E_max; the fail-closed default is refusal (decision bead N16a-09).
- Exit-code detail to confirm with the surface owner: in a multi-world run a faulted world is listed and counted
  and the run exits 2; a run whose every requested world faulted returns the refusal with exit 3.
- The `strict` rows of GATE-KIN-04 close at M2 when the same driver runs on this project's kernels (BD-161).
