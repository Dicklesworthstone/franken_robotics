## Background

A design studio rarely wants 4,096 copies of one robot. It wants a sweep: the same tree with different link
lengths, inertias, gear ratios, actuator-card parameters, foot radii and friction, or one design under
randomized card uncertainty. Level P-A of the three levels of variation is exactly this: values differ on one
tree; one structure table, one parameter table per model slot, no masks and no padding. (Level P-B, different
trees inside padded capacities, and level P-C, design families, are Frontier mechanisms of the Phylum chapter
and are not this bead.)

DESIGN: each world carries a `model_slot`, a `scene_slot`, a `task_slot` and an optional parameter row, exactly
as it already carries its address. Worlds whose slots point at models with the same tree and different
parameter values run in one batch with no masks and no padding. The parameter row carries per-world
randomization drawn from card uncertainty.

This is parity with incumbent practice and is stated as such: a leading incumbent already batches model fields
per world (FACT from the source register, to be re-read). It is not a differentiator; it is a requirement,
phrased as "no kernel compile and no graph capture per design".

What makes it worth a gate is exactness. GATE-KIN-06 (claim: Parity; M2; TARGET): a batch of 256 parameter
variants of each reference robot equals 256 homogeneous runs bit for bit on `batch-cpu` and on each GPU back
end. If a variant's digests depended on the other variants in its batch, a sweep could not be replayed one
design at a time and paired comparison across designs would lose its pairing (ADR-KIN-03).

## Scope

In: the slots and the parameter row on `batch-cpu`; how kernels read them; immutability within a step; the
`batch-cpu` rows of GATE-KIN-06; the per-parameter-row test of PO-KIN-01. Out: device rows of the gate (variants
on devices, BD-183); model variants with different trees (BD-170); drawing randomization from cards (BD-200);
size buckets and the planner (`phylum.plan`, BD-171); the performance row for variants on a device.

## Technical approach

```rust
// DESIGN. One row of indices per world, plus its address (the layout type is owned by the Phylum chapter).
pub struct WorldSlots { pub model: u32, pub scene: u32, pub task: u32, pub job: u32, pub addr: WorldAddr }
pub struct ParamRow<'a> { values: &'a [f32] /* or f64 */, layout: ParamLayoutId }   // per world, fixed length
pub struct ParamLayout { fields: Vec<ParamField> }   // name, offset, dimension, the kernel input it overrides
```

1. **Three places a parameter can live.** (a) In the model table of a model slot: one table per distinct design
   of the sweep; worlds of that design share it. (b) In the world's parameter row: values that differ world by
   world (randomization draws). (c) Nowhere, because it is structural (the tree, joint classes, sample lists):
   structural variation is level P-B. `single_structure = true` in the shape class marks a P-A cohort: one
   tree, unmasked path.
2. **Parameter layout.** A content-hashed list of fields with physical dimensions, for example
   `link[3].length (m)`, `link[3].inertia[0..10] (kg·m²…)`, `joint[5].gear_ratio (1)`,
   `actuator[5].k_t (N·m/A)`, `foot[2].radius (m)`, `pair[sole, floor].mu (1)`. The layout id is part of the
   shape class; the values are part of each world's `ModelId` (they are physical parameters), never of
   `StepPlanId`.
3. **Derived quantities are computed in the kernels.** A link length changes a joint placement; an inertia
   changes the ten-number inertia; a gear ratio changes the reflected inertia N²·J_rotor. Each kernel that
   consumes an overridable field reads either the model table's value or the parameter row's value through one
   accessor resolved at environment creation into a per-field index; there is no branch per world.
4. **Immutable within a step.** Parameter rows and model tables are written only at the fence (environment
   creation, reset under masks, admission of a new variant between chunks). Every kernel of a step reads the
   slab bound to the committed batch epoch; a host write during a step goes to the next epoch. This is what the
   gate's negative control attacks: "the parameter row read after its first use in the step".
5. **Randomization.** The row is filled by addressed draws (counter-based streams keyed by world address and a
   registered stream id per randomized parameter, keyed by the physical entity it perturbs), so a world's row
   is a function of its address and design alone.
6. **Convexity per parameter row (PO-KIN-01).** The lockstep objective must stay strictly convex for every
   admitted parameter row and lagged friction coefficient: A ≻ 0 and each ℓ_c convex. At row admission the
   bead checks the physical-consistency conditions that give A ≻ 0 (every link's pseudo-inertia positive
   definite, rotor inertias and dampings non-negative) and that each law parameter is inside the range over
   which the law's convexity is certified; a row outside is refused at admission with the offending field. The
   state-dependent friction coefficient is constant inside a solve (lagged).
7. **Gate harness.** For each reference robot: draw 256 parameter variants (lengths ± 10%, inertias ± 20%
   inside the consistent cone, gear ratios ± 15%, card torque constants ± 10%, foot radius ± 20%, friction
   0.3 to 1.0; DESIGN ranges) by address. Run (a) one batch holding all 256 variants; (b) 256 homogeneous
   batches, each holding one variant replicated. Compare each variant's per-step digest chain between (a) and
   its run in (b), over 1,000 steps under the baseline controller. Any differing bit fails, with the first
   differing step, stage and buffer.

## Acceptance criteria

- [ ] Seed done-condition: `batch-cpu` rows of GATE-KIN-06: 256 parameter variants equal 256 homogeneous runs
      bit for bit, for each reference robot, in `f32` and `f64`, recorded with counts.
- [ ] The late-read mutant (a kernel that re-reads the parameter row after a host write in mid-step) is
      registered and caught.
- [ ] No kernel compile and no step-plan rebuild occurs when variants are admitted: the `StepPlanId` of the
      256-variant batch equals that of each homogeneous batch, and the kernel cache reports zero new entries.
- [ ] Each variant's `ModelId` differs and is reported per world; results are keyed by world address, never by
      slot.
- [ ] A parameter row with a non-physical inertia or a law parameter outside its certified range is refused at
      admission, naming the field; every admitted row gives A ≻ 0 (Cholesky succeeds) on 10⁴ sampled states.
- [ ] `frob sim run <design> --designs <sweep file> --tier batch-cpu --json` runs the sweep in one batch and
      labels results `provisional`.

## Test plan

### Unit tests

- `variants::bit_equal_256` (reduced in CI to 32 variants × 200 steps; full size in the gate lane).
- `variants::late_read_mutant_caught` (negative control, feature `mutant-late-param-read`).
- `variants::no_recompile`: kernel-cache counters and `StepPlanId` equality.
- `variants::model_id_per_world`: 256 distinct `ModelId` values; one `StepPlanId`.
- `variants::row_is_function_of_address`: the same address in two different batches gets the same row.
- `variants::link_length_changes_fk`: doubling `link[3].length` in one world's row changes that world's foot
  position by the expected amount and no other world's bits (live-dependency proof).
- `variants::gear_ratio_reflected_inertia`: N from 9 to 12 with J_rotor = 10⁻⁴ kg·m² changes the joint's
  diagonal of A from +0.0081 to +0.0144 kg·m².
- `variants::admission_refuses_bad_row`: a negative principal inertia; friction μ = −0.1.
- `variants::convexity_per_row`: A ≻ 0 for every admitted row on sampled states.
- `variants::slot_permutation`: permuting which slot holds which variant permutes results and changes nothing
  else.

### End-to-end script and logging

`scripts/e2e/kin_param_variants.sh` (bead N16a-19) runs the 256-variant batch and the 256 homogeneous runs
through `frob sim run … --designs … --json`, compares digest chains variant by variant, and logs the count of
equal chains, the first difference if any, `step_plan_id` equality and the kernel-cache counters.

## Considerations

- Performance target (owned by the performance program, measured on a device): the reference quadruped with
  per-world parameter variants at 8,192 worlds runs at no less than 0.95 of identical worlds (ambition 0.98).
  The cost is the extra gathers through the per-field index.
- Memory: a parameter row of F fields costs 4·F bytes per world in `f32`; a model table is about 192 bytes per
  link per distinct design.
- A parameter that changes structure in disguise (a length of zero that merges two joints, a mass of zero) is
  refused by the admission checks rather than run.
- If the mixed-batch kill gates of the Phylum chapter fire, parameter variants are explicitly unaffected: they
  need no padding and no masks.
