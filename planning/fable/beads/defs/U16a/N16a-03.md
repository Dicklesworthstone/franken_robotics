## Background

A result must say exactly what computed it. FrankenRobotics splits that into two identities, both content hashes
(BLAKE3 through `fs-blake3`), carried by every result:

- `ModelId`: the world's own compiled model, that is, the physics that is being simulated (bodies, joints, cards,
  contact parameters, the clock contract);
- `StepPlanId`: the numerical plan that advanced it.

The rule (DESIGN): **a physics change changes one of the two identities; nothing else does.** World count, slot,
co-tenants, device ordinal, worker count and wall-clock are not inputs, because a world's trajectory is a function
of its address and identities only (ADR-KIN-03). Without the rule, two runs with different solver iteration counts
could be compared as if they were the same experiment, and a model-form check (which varies exactly one numerical
thing per arm) would have nothing to key its arms by. Each model-form variant (contact law, cone, stiffness, step,
tolerance) is by definition a different `StepPlanId`.

The alternative rejected is a free-form "settings" record attached to results: it is not an identity, cannot be
compared for equality, and silently grows fields that nobody hashes.

## Scope

In: the `StepPlan` descriptor, its canonical serialization and hash, the registry of which field belongs to which
identity, the tests of the two-identity rule, and the numerical-plan inputs of `sim.run` (`--step`,
`--newton-iterations`, `--warm-start`: VERBS-sim's step-plan row, owners this bead and N16a-04). Out: the
backend-neutral launch record `frob.stepplan/1` in `frob-kernels` (N21ap1-01, M2), and its CUDA and Metal
realizations (BD-172, BD-174); the shape-class type itself
(packed lowering, BD-148); per-world parameter rows, which belong to `ModelId` (BD-169).

**A name clash, kept apart on purpose.** Two types have the short name `StepPlan`: this numerical descriptor in
`frob_dyn::plan`, whose hash is `StepPlanId` (domain tag `"frob.stepplan.id/1"`), and the launch record
`frob_kernels::StepPlan` of N21ap1-01 (schema `frob.stepplan/1`, record hash with domain tag
`"frob.stepplan.record/1"`). The launch record carries this bead's `StepPlanId` as a digest supplied by its
builder's caller; `frob-kernels` neither recomputes it nor depends on `frob-dyn` (the dependency points the other
way). Documentation, schema names and every log line name the qualified path or the schema, never the bare short
name, and the record hash is never reported as `step_plan_id`.

## Technical approach

```rust
// DESIGN. Every field is hashed in this order through the canonical writer of frob-core.
pub struct StepPlan {
    pub profile: StepProfile,                 // lockstep | strict | referee
    pub tier_family: TierFamily,              // referee | batch | (the kernel library is shared by batch-cpu and gpu-*)
    pub precision: Precision,                 // f64 | f32
    pub shape_class: Option<Blake3>,          // lockstep only: BD-148's `ShapeClassId` (capacities n_v, links, depth,
                                              // samples, C, R, actuators), held as its 32 bytes: see below
    pub kernel_versions: Vec<(KernelName, KernelId)>,   // sorted by name; empty on the referee
    pub foundation_pin: Option<StackLockDigest>,        // referee only: the FrankenSim commit that computed the step
    pub contact_law: LawId,                   // CL-1 | CL-2 | CL-M | CL-H, with cone variant (elliptic | pyramid mutant)
    pub h: Ratio,                             // physics step, an exact rational number of seconds
    pub world_steps_per_control: Schedule,    // integer decimation, or the phase-accumulator schedule (see below)
    pub newton_iterations: u8,                // the lockstep iteration count, a class constant
    pub warm_start: WarmStart,                // on | off: whether the solve starts from the previous step's impulses
    pub solver_tolerance: TypedTol,           // dimensionless in scaled variables
    pub solve_path: SolvePath,                // dense | ancestor (two paths never mix in a study)
    pub jacobian_store: JacStore,             // dense | path-table (digest-identical once its gate passes)
    pub integrator: IntegratorId,             // semi-implicit-euler | variational
    pub txn: Option<TxnNumerics>,             // transactional profiles: L_max, E_max, N_retry, the retry ladder id
    pub execution_options: ExecOptions,       // options proven digest-neutral (row queues); hashed separately
}
pub struct StepPlanId(Blake3);
```

**Types this descriptor takes from other beads.** `LawId` is the contact chapter's (N18a-15, a dependency; this
crate defines no second law identifier). `ShapeClassId` is defined by the packed lowering (BD-148, M2), and
BD-148 depends on this bead through the transaction (BD-081, N16a-04), so that type does not exist when this
bead is built. DESIGN: the field is declared over the identifier's 32 bytes and written into the canonical
bytes as a digest; from M2 the value stored is BD-148's `ShapeClassId`, passed by the builder of the lockstep
descriptor (BD-159), which changes no canonical byte and no pinned id. This bead never computes a shape class
from capacities: its tests use fixed digests labelled `synthetic`, and that a capacity change moves `StepPlanId`
is tested where the class exists (N16a-14's `cap::override_option`, N21ap1-01's `stepplan_id_hash_inputs`).

1. **What the plan lists as hashed** (plan text, DESIGN): the shape class (the capacities), kernel versions,
   contact law, step profile, h, the number of world-steps per control interval, Newton iterations and tolerance.
   The solve path joins the hash by the rule that the two paths order their arithmetic differently and a study
   never mixes them. The remaining fields above (precision, warm start, integrator, transactional numerics,
   Jacobian store, the foundation pin) are added by this bead because each changes bits or events; leaving any
   of them out would let two different computations share an identity. Warm start in particular: with a fixed
   iteration count, starting from the previous impulses or from zero gives different iterates, and OPEN-KIN-1
   decides the iteration budget "with warm start" as one choice.
2. **World-steps per control interval.** Fixed at admission by the clock contract (rational periods with phase
   accumulators) and part of the hash. No schedule is required to be an integer ratio of the physics tick. On
   the lockstep tiers a control period that is not a multiple of h is served by its phase accumulator under the
   boundary ordering rule, with the quantization recorded: the field then holds the pair (control period in
   quanta, h in quanta) and the per-clock intra-step policy (`hold` or `interpolate`). Under a transactional
   profile every clock boundary is an exact sub-interval boundary, and the field holds the periods only.
3. **Execution options are a separate digest.** Options that are proved or gated to change no digest (queue
   membership and capacities of row-class solve queues, worker count, tile size) are recorded in the receipt as
   `exec_options_digest` and are *not* part of `StepPlanId`. An option that has not yet passed its digest gate on
   a backend is recorded with the label `experimental-execution`.
4. **Canonical form.** The descriptor is written with the canonical writer (sorted keys, rationals as reduced
   integer pairs, integers above 2⁵³ as strings) and hashed with a domain tag `"frob.stepplan.id/1"`.
5. **Identity registry.** `crates/frob-dyn/src/plan.rs` holds a table mapping every tunable of the step to
   `Model`, `StepPlan`, `ExecOptions` or `NotAnInput`. A new tunable does not compile until it is classified
   (an exhaustive match). `NotAnInput` entries: world count, slot, co-tenants, device ordinal, worker count,
   job, wall-clock.
6. **Where it travels.** In the `evidence` block of every envelope (`step_plan_id`), in every chunk record and
   snapshot header, and in every fidelity-ledger key. `sim.estimate` prints it without running physics.
7. **Capacity changes.** Raising a contact or row capacity is a new shape class and therefore a new
   `StepPlanId`; this is the repair "raise capacity" of the overflow refusal.
8. **The numerical-plan inputs of `sim.run`** (VERBS-sim's step-plan row, M1). `--step <duration>` sets h as an
   exact rational (`2ms` is 1/500 s); `--newton-iterations <n>` and `--warm-start on|off` set the two fields of
   those names. Each default is the profile's, each enters `StepPlanId` and never `ModelId`, and a value outside
   the profile's plan domain (`--step 0ms`, for instance) is `FROB-REF-802`, exit 3. `--step` changes h only:
   every clock keeps its period in seconds (N16a-04), so `world_steps_per_control` is recomputed from (control
   period, h).

## Acceptance criteria

- [ ] `StepPlanId` is stable across platforms, debug and release builds and repeated runs for one descriptor
      (digest pinned in a test vector file).
- [ ] Changing any single hashed field changes the identity; changing any `NotAnInput` quantity does not.
- [ ] A result of `frob sim run … --json` carries both `model_id` and `step_plan_id` in `evidence`.
- [ ] `frob sim run … --step 1ms --key <key> --json` reports a `step_plan_id` different from that of the same run
      at the default 2 ms and an equal `model_id`; `--step 0ms` is `FROB-REF-802`, exit 3.
- [ ] The pairing predicate `StepPlan::pairable(&a, &b)`, which every study calls before pairing two arms,
      returns a refusal naming both identities and the differing field when two descriptors differ in
      `solve_path` (two paths never mix in a study); the studies that call it are their own beads.
- [ ] The exhaustive classification test fails to compile when a new tunable is added without a class.
- [ ] The descriptor round-trips through the canonical writer and reader byte for byte.

## Test plan

### Unit tests

- `plan::field_sensitivity`: for each hashed field, flip it (h from 1/500 s to 1/1000 s; iterations 4 to 8;
  warm start on to off; tolerance ÷ 10; law CL-1 to CL-2; profile; the shape class, as two `synthetic` digests
  standing for C = 32 and C = 64; one `KernelId` byte) and assert a different id.
- `plan::pairable_refuses_solve_path`: dense against ancestor refused with both ids and the field name;
  two descriptors that differ only in `ExecOptions` are pairable.
- `plan::non_inputs`: the same descriptor run with 1, 256 and 8,192 worlds, any slot permutation and 1, 8 and 24
  workers yields one id.
- `plan::canonical_bytes`: key order and whitespace of the input do not change the id; a pinned test vector
  (`h = 1/500`, a fixed `synthetic` shape-class digest, 4 iterations, CL-1, `f32`) has a pinned id.
- `plan::schedule_non_integer`: physics 400 Hz with a 30 Hz controller (h = 3 quanta, period 40 quanta at
  Q = 1,200) hashes the pair (40, 3) and the policy `hold`; changing `hold` to `interpolate` changes the id.
- `plan::exec_options_excluded`: toggling worker count changes `exec_options_digest` only.
- `plan::verb_inputs`: `--step 2ms`, `--newton-iterations 4` and `--warm-start on` parse into h = 1/500 s, 4
  and `on` exactly; `--step 1ms` changes `step_plan_id` only; `--step 0ms` is refused with 802.
- `plan::two_identity_rule` (property test): random edits drawn from the registry; an edit classified `Model`
  changes `ModelId` only, `StepPlan` changes `StepPlanId` only, `NotAnInput` changes neither. One declared
  coupling is exempt and tested on its own: a clock is physical (N16a-04), so changing the control period changes
  `ModelId`, and it also changes `world_steps_per_control`, which the registry marks as derived from (control
  period, h); the test asserts that this field, and no other `StepPlan` field, moves with a clock edit.

### End-to-end script and logging

Exercised by `scripts/e2e/kin_lockstep_batch.sh` (N16a-18): the script runs the same fixture at two world counts
and asserts equal `step_plan_id` and equal per-world digests, then with `--newton-iterations 8` and asserts a
different `step_plan_id`. Each log line records both identities under `evidence.identities`.

### Known answers and negative controls

- Negative control: a build whose hash omits `newton_iterations`; `plan::field_sensitivity` must fail.
- Metamorphic relation: permuting world indices permutes results and changes neither identity.
- Determinism lanes: the pinned vector is checked twice on one machine, in debug and release, and on both
  platforms of the project (class D0: an integer hash).

## Considerations

- OPEN-KIN-1 (default h = 2 ms and 4 warm-started Newton iterations) decides two of the hashed defaults; a
  change of default changes every default `StepPlanId` and is announced as such.
- A physical parameter must never appear in this descriptor: stiffness, dissipation time and friction
  coefficients belong to `ModelId` (ADR-KIN-05). The stiction speed of a regularized friction law is a numerical
  parameter, is reported, and is part of the contact-law identity.
- If a field is later shown to be digest-neutral (the path-table Jacobian, once its gate records identical
  digests), it moves to `ExecOptions` by ADR, never silently.
