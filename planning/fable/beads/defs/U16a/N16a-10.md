## Background

The transactional step is the mechanism that lets the referee adjudicate the fast tiers: an interval either
commits complete and checked, or leaves no trace; events are located; retries restore everything and never
redraw randomness. Unit tests prove the pieces inside `frob-dyn`. This bead proves the capability from the
user's side: a shell script that drives the real `frob` binary on real fixtures and records, with structured
logs, the measured value of every referee row of GATE-KIN-04.

GATE-KIN-04 (claim: Known answer; TARGET thresholds; referee rows due at M1, `strict` rows at M2): the
transactional rows pass on the referee and on `strict`: impact time within 10⁻⁹ s; tied sliders exact to
10⁻¹² N·s; zero observed uncommitted reads in 10⁵ injected faults; forced-retry digests equal; refinement
statistics inside 3σ at 10⁶ draws; the redraw mutation caught. A gate passes only with a recorded measurement
against its threshold and with its registered negative controls shown to fail.

## Scope

In: the script `kin_transaction_referee.sh`, its fixtures, its assertions and its log for the rows of the
step itself (impact time, tied sliders, uncommitted reads) and for the refusals 220, 221, 222 and 721 as a
caller sees them; and the gate record that assembles all six referee rows of GATE-KIN-04. Out: the three retry
rows in depth (forced-retry digests on 10⁴ intervals, refinement statistics at 10⁶ draws, the redraw mutation
and the two restore-set mutants), which are the script `kin_retry_refinement.sh` of N16c-02: steps 8 to 10
below call that script and read its receipt, at smoke size in the per-change run and at gate size for the
record; the `strict` rows (the same two scripts re-run with `--tier batch-cpu --profile strict` when the strict
profile lands, BD-161); the thin-barrier and sill fixtures (BD-086); the unit-level tests of each mechanism.

## Technical approach

Script: `scripts/e2e/kin_transaction_referee.sh`. Plain shell; sources the shared helper of the end-to-end
harness (STD-E2E); idempotent; every seed explicit; exits non-zero on the first failed assertion after writing
the summary. Fixtures live in `crates/frob-conformance/fixtures/kin/` as small `.fbot` designs with their scenes;
each is labelled `synthetic` in its evidence.

Steps (each is one `step` value in the log):

1. `admission`: `frob sim run g1 --tier gpu-cuda --profile strict --json` → exit 3, `refusal.code =
   "FROB-REF-222"`, first repair names `--tier batch-cpu`. Then the same with `--tier referee --profile referee`
   → admitted.
2. `determinism`: `frob sim run g1 --tier referee --profile referee --seconds 2 --seed 7 --json` twice → equal
   state digests; `evidence.profile = "referee"`, `evidence.tier = "referee"`, both identities present.
3. `ballistic-drop`: `frob sim run …/ballistic-drop.fbot --scene plane --tier referee --profile referee
   --seconds 1 --seed 1 --json`. Sphere released at rest with gap z₀ = 1 m, g = 9.81 m/s², restitution 0.5.
   Assert: |t_refined − √(2·z₀/g)| ≤ 10⁻⁹ s (truth ≈ 0.4515236 s, taken from the derivation file to 15
   digits); outgoing speed = 0.5 × √(2·g·z₀) within the law's tolerance; second impact after 2·v⁺/g.
4. `ballistic-drop-endpoint-mutant`: the same fixture run with the registered control build
   (`FROB_CONTROL=NC-kin-endpoint-only`, a build feature that checks gaps at sub-interval ends only) → the
   assertion of step 3 must FAIL; the script records `control_caught: true`.
5. `tied-sliders`: `frob sim run …/tied-sliders.fbot --scene wall --tier referee --profile referee --seconds 1
   --seed 1 --json`. Two 1 kg sliders joined by a rigid tie reach a wall together at 1 m/s. Assert total wall
   impulse within 10⁻¹² N·s of 2 and both final speeds within 10⁻¹² m/s of 0.
6. `tied-sliders-sequential-mutant`: the control build that solves one contact and then imposes the tie → must
   report 1 N·s and 0.5 m/s into the wall; `control_caught: true`.
7. `fence-chaos`: the chaos build, `frob sim run g1 --tier referee --profile referee --seconds 2 --seed 3
   --chaos faults=100000,point=t5-t6 --json` → `uncommitted_reads = 0`; then the leaky-fence control build →
   `uncommitted_reads > 0`.
8. `forced-retry`: `frob sim run quad-mammal --scene plane --tier referee --profile referee --seconds 2 --seed 11
   --force-retry attempt=1,every=97 --json` and a clean run started from the same checkpoints with plan 1 →
   equal digests on every one of the forced intervals (10⁴ random intervals in the full gate run; 200 in the
   smoke run). Control: the build that omits packet queues from the restore set → digests differ.
9. `noise-refinement`: `frob sim run …/brownian-driver.fbot --tier referee --profile referee --seed 5
   --samples 1000000 --json` → for a parent interval of length ℓ, each half-interval increment has variance ℓ/2,
   the halves are uncorrelated and their sum equals the parent; every statistic inside 3σ at 10⁶ draws. Control:
   the redraw-on-rejection build → the sign fixture gives P(positive) = ¾ instead of ½ and the row fails.
10. `no-refinement-law`: a driver with no registered refinement law → exit 3, `FROB-REF-223`.
11. `accumulation`: restitution 0.5 from 1 mm → exit 3, `FROB-REF-220` with the event count.
12. `exhaustion`: the control fixture whose every plan fails a check → the world is `Faulted`, `FROB-REF-221`,
    `telemetry.failures` counts it under kind `numerical` and not under `fall`.
13. `indeterminate`: the Painlevé rod → `FROB-REF-224`, no number returned.
14. `referee-capacity`: a 22-contact island → exit 5, `FROB-REF-721`; with `--adjudicate strict` it is
    skipped at M1 and asserted at M2.
15. `checks-and-epochs`: `frob telemetry query <run> --fields commit_epoch,attempt,checks,events --json` →
    epochs strictly increasing by one; a `CheckReport` with eight passing results on every committed interval;
    sub-intervals summing exactly.
16. `gate-record`: writes the measured values of the referee rows to the gate registry entry and the bead log
    (`docs/delivery/logs/N16a-10.ndjson`), to be recorded as PASS by a session that did not implement the work.

Logging. Structured newline-delimited JSON to `target/e2e-logs/kin_transaction_referee/<utc-timestamp>.ndjson`
with a human-readable transcript beside it. Every line: `ts`, `script`, `bead` ("N16a-10"), `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the
envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and
thresholds, digests where state is compared, and on failure the first differing value and the artifact paths
needed to reproduce (run id, checkpoint, fixture path). The final `summary` line gives assertions passed and
failed, controls caught, and `gates: ["GATE-KIN-04"]` with the row-by-row table. No private-scene data appears
(all fixtures are synthetic).

## Acceptance criteria

- [ ] The script exits 0 on a clean build and non-zero when any one of the five control builds replaces the
      honest build in an honest step.
- [ ] Each referee row of GATE-KIN-04 has a `metric` line with measured value, unit and threshold: impact-time
      error (s, ≤ 10⁻⁹), impulse error (N·s, ≤ 10⁻¹²), uncommitted reads (count, = 0 in 10⁵ faults),
      forced-retry digest mismatches (count, = 0), refinement z-scores (≤ 3), redraw control caught (true).
- [ ] All five negative controls are recorded as caught in the summary.
- [ ] The log validates against the logging schema of STD-E2E; the transcript names the reproduction command of
      every failed assertion.
- [ ] Re-running the script produces identical digests and identical measured values (idempotence, same seeds).
- [ ] The smoke variant (`--smoke`: 10³ faults, 200 forced intervals, 10⁴ draws) runs in under two minutes on
      one core (TARGET) and is the variant in the `smoke` battery; the full variant is the gate run.

## Test plan

### Unit tests

The script's own helpers are tested in `scripts/e2e/tests/kin_transaction_referee.bats`-style shell tests
written against the STD-E2E harness: `parses_event_time`, `compares_digests`, `fails_on_missing_metric`,
`summary_counts`.

### End-to-end script and logging

This bead is the script; see Technical approach. It is run in three lanes: twice on one machine (digests
equal); debug and release builds (digests equal on the referee on one platform); and, at M2, again under
`--tier batch-cpu --profile strict`.

### Known answers and negative controls

| Row | Truth | Tolerance | Control that must fail |
|---|---|---|---|
| KA-338 ballistic drop | √(2·z₀/g); restitution; second flight | 10⁻⁹ s | Endpoint-only gap check |
| KA-339 tied sliders | 2 N·s; both at rest | 10⁻¹² N·s | Solve one contact, then impose the tie: 0.5 m/s into the wall |
| KA-340 noise refinement | Child variance ℓ/2; halves uncorrelated; sum equals the parent | 3σ at 10⁶ draws | Redraw on rejection: P(positive sign) = ¾ |
| KA-341 forced retry | Digest equals the clean run with the same plan | exact | Packet queues or warm starts omitted from the restore set |
| KA-342 fence | Zero uncommitted reads in 10⁵ faults | exact | A reader that sees a candidate interval |

Metamorphic relation checked by the script: a retry of a transactional step equals a clean run with the same
plan; the noise path is unchanged under split, rejoin, reject and checkpoint restart.

## Considerations

- The 10⁵-fault and 10⁶-draw rows take minutes on the referee; they run in the gate lane, not on every commit.
- Control builds are compiled once per run from registered features; the registry of negative controls holds
  one record per control with the gate it must fail, and a gate run in which a control was not caught is a
  FAIL whatever the passing assertions say.
- The referee claims same-platform determinism only; the script does not compare digests across platforms.
- If OPEN-KIN-5 changes L_max, E_max or the retry budget, the script's pinned `StepPlanId` expectations are
  regenerated in the same change.
