## Background

The transactional step is the mechanism that lets the referee adjudicate the fast tiers: an interval either
commits complete and checked, or leaves no trace; events are located; retries restore everything and never
redraw randomness. Unit tests prove the pieces inside `frob-dyn`. This bead proves the capability from the
user's side: a shell script that drives the real `frob` binary on real fixtures and records, with structured
logs, the measured value of every referee row of GATE-KIN-04.

GATE-KIN-04 (claim: Known answer; TARGET thresholds; referee rows due at M1, `strict` rows at M2): the
transactional rows pass on the referee and on `strict`: impact time within 10⁻⁹ s; tied sliders exact to
10⁻¹² N·s; zero observed uncommitted reads in 10⁵ injected faults; forced-retry digests equal; refinement
statistics inside 3σ at 10⁶ draws; the redraw mutation caught. A gate passes only with a recorded measurement
against its threshold and with its registered negative controls shown to fail.

## Scope

In: the script `kin_transaction_referee.sh`, its fixtures, its assertions and its log for the rows of the
step itself (impact time, tied sliders, uncommitted reads) and for the refusals 220, 221, 222 and 721 as a
caller sees them; and the tier receipts of all the referee rows of GATE-KIN-04, from which the referee part is
recorded (step 17). Out: the three retry
rows in depth (forced-retry digests on 10⁴ intervals, refinement statistics at 10⁶ draws, the redraw mutation
and the two restore-set mutants), which are the script `kin_retry_refinement.sh` of N16c-02: steps 8 to 10
below call that script and read its receipt, at smoke size in the per-change run and at gate size for the
record; the `strict` rows (the same two scripts re-run with `--tier batch-cpu --profile strict` when the strict
profile lands, BD-161); the randomized thin-barrier battery and the sill fixtures (BD-086), of which one
thin-plate run is kept here for the audit record of check 6; the unit-level tests of each mechanism.

## Technical approach

Script: `scripts/e2e/kin_transaction_referee.sh`. Plain shell; sources the shared helper of the end-to-end
harness (STD-E2E); idempotent; every seed explicit; exits non-zero on the first failed assertion after writing
the summary. Every run other than those of the catalogue model `g1` takes its design and environment from a
registered conformance fixture, `frob sim run --fixture <space>/<name>` (N24b-03's registry), whose static
environment is carried as primitives (BD-080's form): this is the M1 form, because `--scene` reaches `sim.run`
only at M2 (N16b-25). Each is labelled `synthetic` in its evidence. `kin/ballistic-drop` is N16c-02's (over
BD-082's design), `kin/tied-sliders` and `kin/unsolvable-island` are BD-083's, `traction/referee_capacity_22` is
BD-080's; the accumulation, Painlevé-rod and thin-plate fixtures of steps 11, 13 and 16 are this bead's, written
under `crates/frob-conformance/fixtures/kin/` and registered as `kin/accumulation`, `kin/painleve-rod` and
`kin/thin-plate`.

Control builds (steps 4, 6, 7 and 16): the `frob` binary built with `--features
gauntlet-mutations,frob-dyn/nc-<nnnn>` for one registered control (BD-025's form; never a product build): the
`endpoint-only-gap` control of KA-338 and the `sequential-impulse` control of KA-339 (N16c-03's records) and the
leaky-fence control of KA-342 (BD-081's). The script runs the honest step's assertion against it with
`e2e_expect_caught <NC-nnnn>`.

Steps (each is one `step` value in the log). Every `frob sim run` below also passes `--key kin-txn-<step>-<seed>`
(a second call of one step appends `-2`): `sim.run` is a job-submitting run verb, and a call without an
idempotency key is refused with `FROB-REF-805`, exit 3 (N32a-09), so a step that omitted it would assert the
wrong refusal.

1. `admission`: `frob sim run g1 --tier gpu-cuda --profile strict --json` → exit 3, `refusal.code =
   "FROB-REF-222"`, first repair names `--tier batch-cpu`. Then `--tier batch-cpu --profile strict`, a pair the
   matrix admits whose step is not in the M1 build → exit 5, `FROB-REF-724`, never `FROB-REF-222`, with
   `bound.profile = "strict"` echoed. The expected outcome is read from `frob capabilities --json` (the `strict`
   step listed as absent at M1, as implemented once BD-161 is built, when the M2 re-run expects admission) and
   both the report row and the outcome are logged, so the refusal and the report must agree. Then the same with
   `--tier referee --profile referee` → admitted.
2. `determinism`: `frob sim run g1 --tier referee --profile referee --seconds 2 --seed 7 --json` twice → equal
   state digests; `evidence.profile = "referee"`, `evidence.tier = "referee"`, both identities present.
3. `ballistic-drop`: `frob sim run --fixture kin/ballistic-drop --tier referee --profile referee
   --seconds 1 --seed 1 --json`. Sphere released at rest with gap z₀ = 1 m, g = 9.81 m/s², restitution 0.5.
   Assert: |t_refined − √(2·z₀/g)| ≤ 10⁻⁹ s (truth ≈ 0.4515236 s, taken from the derivation file to 15
   digits); outgoing speed = 0.5 × √(2·g·z₀) within the law's tolerance; second impact after 2·v⁺/g.
4. `ballistic-drop-endpoint-mutant`: the same fixture run on the control build of KA-338's `endpoint-only-gap`
   (gaps checked at sub-interval ends only) → the assertion of step 3 must FAIL; the script records
   `control_caught: true`.
5. `tied-sliders`: `frob sim run --fixture kin/tied-sliders --tier referee --profile referee --seconds 1
   --seed 1 --json`. Two 1 kg sliders joined by a rigid tie reach a wall together at 1 m/s. Assert total wall
   impulse within 10⁻¹² N·s of 2 and both final speeds within 10⁻¹² m/s of 0.
6. `tied-sliders-sequential-mutant`: the control build that solves one contact and then imposes the tie → must
   report 1 N·s and 0.5 m/s into the wall; `control_caught: true`.
7. `fence-chaos`: the chaos build, `frob sim run g1 --tier referee --profile referee --seconds 2 --seed 3
   --chaos faults=100000,point=t5-t6 --json` → `uncommitted_reads = 0`; then the leaky-fence control build →
   `uncommitted_reads > 0`. `--chaos` is a chaos-build-only input whose spelling BD-081 defines; the script
   asserts once that a release build answers it with `FROB-REF-802`.
8. `forced-retry`: runs `scripts/e2e/kin_retry_refinement.sh --tier referee --profile referee --seed <s>`
   (N16c-02; with `--smoke` in the per-change run, at gate size for the record) and reads its receipt: zero
   mismatches between forced-retry digests and plan-k digests (at least 10⁴ forced intervals at gate size, as
   KA-341 asks), and both restore-set controls caught (packet queues omitted, warm starts omitted → digests
   differ). On the forced runs named in the receipt the script then reads
   `frob telemetry query <run> --stream solver --channels attempt,physical_params_digest --json` and asserts, on every forced
   interval, that the digest of the committed attempt equals the attempt-0 digest (INV-KIN-07, N16a-04),
   logging both digests and the attempt index on an `assert` line.
9. `noise-refinement`: from the same receipt, the three refinement statistics (each half-interval increment has
   variance ℓ/2, the halves are uncorrelated, their sum equals the parent; inside 3σ at 10⁶ parents at gate size)
   and the redraw control (the redraw-on-rejection build gives P(positive) = ¾ instead of ½ on the fair-sign
   fixture and the row fails), each copied to a `metric` or `assert` line with the receipt hash.
10. `no-refinement-law`: from the same receipt, a driver with no registered refinement law → exit 3,
    `FROB-REF-223` with its two repairs.
11. `accumulation`: restitution 0.5 from 1 mm → exit 3, `FROB-REF-220` in the base interval [42, 44) ms that
    holds the accumulation time 42.835 ms; at the defaults the level clause fires (`observed` 17 against
    `required ≤ 16`) after about 14 located impacts (BD-082). The log records the clause, `observed`,
    `required`, the bracket, the base-interval id and the impacts located before the refusal.
12. `exhaustion`: `--fixture kin/unsolvable-island`, whose every plan fails a check → the world is `Faulted`, `FROB-REF-221`,
    `telemetry.failures` counts it under kind `numerical` and not under `fall`.
13. `indeterminate`: the Painlevé rod → `FROB-REF-224`, no number returned.
14. `referee-capacity`: `--fixture traction/referee_capacity_22`, a 22-contact island → exit 5, `FROB-REF-721` with `cause = "contact-cap"`,
    `observed` 22 against `required ≤ 21`, and the contact count at the airlock equal to the generated count
    (nothing truncated). With `--adjudicate strict-fallback` at M1 the route is taken and returns the same refusal with the
    repair `--profile strict` marked `not in this build` and `adjudicator: none` (N16a-05); completion on
    `batch-cpu:strict` is asserted at M2 by N16a-20.
15. `checks-and-epochs`: `frob telemetry query <run> --stream solver --channels commit_epoch,attempt,checks,events --json` →
    epochs strictly increasing by one; a `CheckReport` with eight passing results on every committed interval,
    logged as one `metric` line per check with `measured`, `unit`, `threshold` and `pass`, plus the audit record;
    sub-intervals summing exactly.
16. `thin-plate`: one run of the single thin-plate fixture (a 2 mm sphere at 5 m/s, 1 mm in front of a 2 mm
    plate) on the referee → one located touchdown event, `audit.missed = 0` in the `CheckReport` of that interval
    and check 6 passing; with the endpoint-only control build check 6 fails naming the plate pair and the
    bracket. The randomized thin-barrier battery (10⁶ crossings) and the sill stay with BD-086 and N18a-35.
17. `gate-receipts`: runs the referee rows in the Gauntlet's tier targets through the STD-E2E helper, each with
    its registered controls: `e2e_tier g1_known_answers kinesis::ka338 --mutations`, and the same for `ka339`
    and `ka340` (N16c-03's rows), `e2e_tier g5_determinism kinesis::ka341 --mutations` (N16c-03) and
    `e2e_tier g4_chaos kinesis::ka342 --mutations` (BD-081's entry), and lists the five receipt hashes in the
    summary. The script never runs
    `record_gate` and never writes `registries/gates.toml` or the bead log (the STD-E2E lint `self-recording`).
    The referee part is then recorded from each receipt by a session that did not implement the work:
    `cargo run -p frob-conformance --example record_gate -- --gate GATE-KIN-04 --part M1 --receipt <hash>`.

Logging. Structured newline-delimited JSON to `target/e2e-logs/kin_transaction_referee/<utc-timestamp>.ndjson`
with a human-readable transcript beside it. Every line: `ts`, `script`, `bead` ("N16a-10"), `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the
envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and
thresholds, digests where state is compared, and on failure the first differing value and the artifact paths
needed to reproduce (run id, checkpoint, fixture path). The final `summary` line gives assertions passed and
failed, controls caught, and `gates: ["GATE-KIN-04"]` with the row-by-row table. No private-scene data appears
(all fixtures are synthetic).

## Acceptance criteria

- [ ] The script exits 0 on a clean build and non-zero when any one of the six control builds replaces the
      honest build in an honest step (endpoint-only, sequential tie and leaky fence here; the two restore-set
      omissions and redraw-on-reject through N16c-02's script).
- [ ] Each referee row of GATE-KIN-04 has a `metric` line with measured value, unit and threshold: impact-time
      error (s, ≤ 10⁻⁹), impulse error (N·s, ≤ 10⁻¹²), uncommitted reads (count, = 0 in 10⁵ faults),
      forced-retry digest mismatches (count, = 0), refinement z-scores (≤ 3), redraw control caught (true).
- [ ] All six negative controls are recorded as caught in the summary.
- [ ] The log validates against the logging schema of STD-E2E; the transcript names the reproduction command of
      every failed assertion.
- [ ] Re-running the script produces identical digests and identical measured values (idempotence, same seeds).
- [ ] The smoke variant (`--smoke`: 10³ faults here, and N16c-02's script with its own `--smoke`: 200 forced
      intervals per fixture and rung, 10⁴ draws) runs in under two minutes on one core (TARGET) and is the
      variant in the `smoke` battery; the full variant is the gate run.

## Test plan

### Unit tests

The script's own helpers are tested in `scripts/e2e/tests/kin_transaction_referee.bats`-style shell tests
written against the STD-E2E harness: `parses_event_time`, `compares_digests`, `fails_on_missing_metric`,
`summary_counts`.

### End-to-end script and logging

This bead is the script; see Technical approach. It is run in three lanes: twice on one machine (digests
equal); debug and release builds (digests equal on the referee on one platform); and, at M2, again under
`--tier batch-cpu --profile strict`.

### Known answers and negative controls

| Row | Truth | Tolerance | Control that must fail |
|---|---|---|---|
| KA-338 ballistic drop | √(2·z₀/g); restitution; second flight | 10⁻⁹ s | Endpoint-only gap check |
| KA-339 tied sliders | 2 N·s; both at rest | 10⁻¹² N·s | Solve one contact, then impose the tie: 0.5 m/s into the wall |
| KA-340 noise refinement | Child variance ℓ/2; halves uncorrelated; sum equals the parent | 3σ at 10⁶ draws | Redraw on rejection: P(positive sign) = ¾ |
| KA-341 forced retry | Digest equals the clean run with the same plan | exact | Packet queues or warm starts omitted from the restore set |
| KA-342 fence | Zero uncommitted reads in 10⁵ faults | exact | A reader that sees a candidate interval |

Metamorphic relation checked by the script: a retry of a transactional step equals a clean run with the same
plan; the noise path is unchanged under split, rejoin, reject and checkpoint restart.

## Considerations

- The 10⁵-fault and 10⁶-draw rows take minutes on the referee; they run in the gate lane, not on every commit.
- Control builds are compiled once per run from registered features; the registry of negative controls holds
  one record per control with the gate it must fail, and a gate run in which a control was not caught is a
  FAIL whatever the passing assertions say.
- The referee claims same-platform determinism only; the script does not compare digests across platforms.
- If OPEN-KIN-5 changes L_max, E_max or the retry budget, the script's pinned `StepPlanId` expectations are
  regenerated in the same change.
