## Background

In the batched step every world carries a dense constraint Jacobian J of R rows by n_v columns. That one buffer
is 24 to 49% of the bytes of a world in every reference workload, so row capacity, not world count, decides
memory (arithmetic on the byte model below). Yet a contact or limit row attached to one link is nonzero only on
that link's ancestor coordinates: each contact row touches only the degrees of freedom on its support path. The
packed lowering of a model already carries a **path table** listing those coordinates for every link.

DESIGN: storing each row on its support path replaces R·n_v by about R·(6 + depth) values, and the path-table
storage becomes the default once GATE-KIN-05 shows identical digests with it. The gate's second clause is
exactly that: "the path-table Jacobian gives the same digests as the dense one".

Why the condition is digest identity and not a tolerance: the dense Jacobian is the reference storage that the
parity gates were recorded with; a second storage that changed a single bit would be a different kernel with a
new identity, an error bound and a fidelity run of its own. Demanding identical digests lets the cheaper storage
replace the dense one without touching any recorded gate.

Arithmetic (DESIGN estimates from the byte model, `f32`, 4 bytes per value): the reference quadruped
(n_v = 18, R = 160; a leg row touches 6 base coordinates and 3 leg coordinates) drops from 160·18·4 = 11,520 B to
160·9·4 = 5,760 B; the reference humanoid (n_v = 35, R = 320; an arm row touches 6 + 3 + 7 = 16 coordinates,
a leg row 12) drops from 44,800 B to at most 320·16·4 = 20,480 B.

This is storage and gather only. It does not change the order or the number of floating-point operations that
produce a result. Exploiting the same structure to skip work in assembly and factorization (ancestor-sparse
assembly, the tree-ordered factor) is a different, Frontier mechanism with its own gate and kill gate, and it
does *not* promise identical bits.

## Scope

In: the compact row layout, the gather used by the kernels that read J, the rule that makes digest identity
provable, the comparison test, and the switch of the default. Out: producing the path table (packed lowering,
BD-148); the row kernels themselves (BD-153, BD-155); rows that span two limbs (handled here only by falling
back to dense storage for that row class); the sparse solve route.

## Technical approach

1. **Layout.** For a row r attached to link ℓ(r): `path_len[r]` (≤ P_cap, the path capacity of the shape class:
   6 + maximum depth in coordinates) and `J_path[r, 0..P_cap]`, the row's values on the coordinates
   `path[ℓ(r)][0..path_len]` in ascending coordinate order; trailing entries hold the neutral element −0.0. The
   path table `path[link][k]` is read-only model data, fixed per model slot.
2. **Rows that are not single-link rows.** A self-contact row between two limbs, a closure row or a coupling
   row touches the union of two paths. DESIGN: such a row is stored in a small dense side buffer of capacity
   R_dense (a constant of the shape class) with its full n_v values; overflow of R_dense is a `Degraded`
   reason like any other capacity overflow, never a silent drop.
3. **The identity rule (DESIGN of this bead; the gate states the outcome, this is the route).** Every consumer
   of J computes each output as an anchored pairwise reduction over an ordered list of *contributing* terms,
   and the list is defined by structure, not by storage:
   - a product J·v for row r sums over the coordinates of the row's support path in ascending order;
   - an entry (i, j) of JᵀGJ sums over the rows whose support path contains both i and j, in ascending row
     order;
   - a product Jᵀ·λ for coordinate i sums over the rows whose support path contains i, in ascending row order.
   The dense implementation obeys the same lists by *selecting* support entries (a mask is a select) and never
   by multiplying stored zeros into a sum. Under this rule the two storages perform the same floating-point
   operations in the same order on the same operands, so every output bit is equal by construction. The reason
   the rule is needed: with stored zeros, a term 0·x is ±0.0 depending on the sign of x, and adding +0.0 to a
   partial sum that is −0.0 changes its bits; "it is only zeros" is not an argument in IEEE arithmetic.
4. **Kernel surface.** `K-jac-rows` gains a storage parameter (`dense` | `path-table`) that changes its write
   footprint only; `K-hess`, `K-linesearch`, `K-cone-eval` and the residual evaluation read rows through one
   accessor `row_terms(r)` that yields (coordinate, value) pairs in path order for either storage.
5. **Identity.** `jacobian_store` is a field of the step plan (N16a-03). Until this bead's gate clause is
   recorded on a backend the path-table store is opt-in (`--jacobian path-table`, DESIGN flag spelling) and
   results carry `experimental-execution`; after it, the store moves to the digest-neutral execution options by
   ADR and becomes the default.
6. **Comparison harness.** The digest harness of N16a-12 run twice, once per storage, on the same 1,000
   episodes per reference robot, comparing per-step and per-stage digests.

## Acceptance criteria

- [ ] Second clause of GATE-KIN-05 on `batch-cpu`: the path-table Jacobian gives the same digests as the dense
      one on 1,000 episodes per reference robot, in `f32` and `f64`, with the counts in the test's output
      (device rows close with the batch-composition invariance bead, BD-181). The gate's `batch-cpu` part is
      recorded only by N16a-18's recording session, from the receipt of its step 19; this bead records no gate.
- [ ] Per-stage digests of stages 7, 8 and 9 are equal between the two storages at every step of those
      episodes.
- [ ] The "multiply by stored zeros" mutant of the dense path produces at least one differing digest and is
      caught (negative control).
- [ ] Measured bytes per world with the path table match the arithmetic: the step allocates 5,760 B of Jacobian
      for the reference quadruped and at most 20,480 B for the reference humanoid (`jac::memory_arithmetic` on
      the two models). The figure `sim.estimate` prints for the store is N16b-26's bytes group, which does not
      depend on this bead; N16a-18's step `path-table` reads it.
- [ ] A self-contact row goes to the dense side buffer and the world's digests still match the all-dense run.
- [ ] The default switches only after the gate record exists; before it, results under the path table carry
      `experimental-execution`.
- [ ] The comparison harness reports the count of worlds that raised `dense-row-overflow` (a reason that exists
      only under the path-table store); the default switches for a shape class only when that count is zero
      on its episodes, and a world that raised it is reported, never silently compared.

## Test plan

### Unit tests

- `jac::row_terms_equal_views`: for random rows, `row_terms` yields identical (coordinate, value) sequences
  from both storages.
- `jac::jv_bits_equal`, `jac::jtgj_bits_equal`, `jac::jt_lambda_bits_equal` (property, 10⁵ random rows on the
  quadruped and humanoid trees).
- `jac::negative_zero_case`: a hand-built case in which a partial sum is −0.0 and a non-support entry would
  contribute +0.0: the rule-abiding dense path returns −0.0; the stored-zero mutant returns +0.0.
- `jac::self_contact_side_buffer`: a hand-on-thigh row (two paths) is stored dense; R_dense overflow marks the
  world `Degraded` with reason `dense-row-overflow`.
- `jac::path_capacity`: P_cap = 9 for the quadruped model and 16 for the humanoid model used in the tests.
- `jac::memory_arithmetic`: allocated Jacobian bytes equal R·P_cap·4 (+ R_dense·n_v·4).
- `jac::digests_equal_episodes` (reduced: 50 episodes per robot).

### End-to-end script and logging

`scripts/e2e/kin_lockstep_batch.sh` (N16a-18), step `path-table`: runs the same seeded quadruped and humanoid
batches with `--jacobian dense` and `--jacobian path-table`, compares the digest chains world by world, and logs
`assert` lines with both `step_plan_id` values, both digests, and the bytes per world reported by
`frob sim estimate … --json`. On mismatch: the first differing step, stage and world, and the replay command.

### Known answers and negative controls

- KA-344, second clause: the path-table Jacobian gives the same digests as the dense one; exact (digest);
  tier G5.
- KA-348's byte model is the reference for the memory figures: bytes per world in `f32` with a dense Jacobian
  are 4·(61·n_b + 17·n_v + 3·n_v² + 24·C + R·n_v + 12·R + 10·n_v); the path table replaces the term R·n_v by
  R·P_cap.
- Negative controls: the stored-zero mutant; a path table with one ancestor missing (a row then loses a
  contribution and the parity harness fails).
- Metamorphic: adding unused path capacity changes no digest (padding is −0.0 and trails the real entries).

## Considerations

- If the identity rule proves too costly for the dense path on a device (selects in the inner loop), the dense
  path may be retired there once the path table is the default; the `batch-cpu` dense path stays as the
  reference.
- Memory is the benefit; no throughput claim is made. Gathers through an index can cost time on a device that
  is bound by memory traffic, which is why the default waits for a measurement.
- The path capacity P_cap (at least the largest `path_cap` that BD-148's `PackedCounts` reports for a model of
  the class) and R_dense are capacities that exist only under the path-table store. They are therefore not
  fields of `ShapeClass`, whose thirteen fields and `ShapeClassId` BD-148 fixes, but are hashed with
  `jacobian_store` in the step-plan descriptor (N16a-03); when the ADR moves the store to the digest-neutral
  execution options, the two capacities move with it, or a digest-neutral option would still change
  `StepPlanId`.
- Digest identity holds while no row overflows R_dense. A dense store has no side buffer, so a world with more
  two-limb rows than R_dense is `Degraded` under the path table and not under dense storage: that is a
  storage-dependent result, and it is why the overflow count is part of the gate record and blocks the default
  switch for its shape class. Closure and coupling rows are static and known at admission, so R_dense is set at
  least to their number plus the self-contact rows the model's collision filter admits on the reference
  workloads; the open question on capacities (N16a-15) settles R_dense for the others.
- The open question on capacities for workloads other than the two reference ones covers P_cap and R_dense as
  well.
