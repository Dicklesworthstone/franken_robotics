## Background

GATE-KIN-03 (claim: Parity; earliest milestone M2; TARGET): `batch-cpu` in `f64` against `fs-mbd`: kinematics,
inverse dynamics, forward dynamics and mass matrix within 10⁻¹⁰ relative on 10⁴ states per reference robot.

The batched tiers do not call FrankenSim. They run this project's own derived kernels (forward kinematics and
twists by tree level, the recursive Newton–Euler pass, the composite-rigid-body pass, the solve) on packed
buffers. FrankenSim's `fs-mbd` is an independent implementation of the same equations and is already the
referee's foundation, so it is the natural pinned oracle for the kernels: `fs-mbd::articulated::
{forward_kinematics, inverse_dynamics, forward_dynamics, free_floating_forward_dynamics,
free_floating_momentum}` and `generalized::free_floating_terms` (mass matrix by a composite-rigid-body pass)
(FACT, re-checked by the admission test of the articulated module). The oracle's pin is the FrankenSim commit in
the stack lock.

Four quantities are compared, and four different beads produce the candidates: kinematics (the kernels
`K-fk-level` and `K-twist-level`), inverse dynamics and the mass matrix (`K-rnea-level` and `K-crba-level`,
BD-150), and forward dynamics (the contact-free solve of the batched step, BD-159). One shared harness keeps the
state sampling, the oracle calls, the conversions and the metric identical across them, so that a row passing in
one bead means the same as a row passing in another. That is the reason this is its own bead.

## Scope

In: the state sampler and its files; the oracle side (calls through the airlock, results cached with the
stack-lock digest); the metric; the comparison API the kernel beads call; the self-test and controls; the gate
record assembled from the four rows. Out: the kernels (BD-149, BD-150) and the step (BD-159); parity against an
external engine (GATE-KIN-02, BD-089); the device rows (CPU-versus-device check, BD-176).

## Technical approach

1. **Robots.** Each reference robot whose archetype exists at M2: the quadrupeds (Go1, Go2, A1, ANYmal B and C,
   Spot), the humanoids (H1, G1 and FrankenSim's 29-degree-of-freedom G1), the Stretch 3 base, the TIAGo base,
   the KUKA iiwa 7. The two reference workloads are the reference quadruped (18 velocity coordinates, 13 links)
   and the reference humanoid (35, 30).
2. **States.** 10⁴ per robot from a counter-based stream keyed by (`"kin03"`, robot, index): joint positions
   uniform inside limits, as unit-complex revolute coordinates with turn count zero; joint velocities uniform in
   ± 5 rad/s; joint accelerations (for inverse dynamics) uniform in ± 50 rad/s²; applied torques (for forward
   dynamics) uniform in ± the card limit; base pose and twist as in the oracle-parity bead; gravity
   (0, 0, −9.81) m/s². Written once to `crates/frob-conformance/fixtures/kin03/<robot>/states.bin` with a header
   (model digest, stream key, count, layout digest of the packed lowering).
3. **Oracle side.** `fn oracle_rows(robot, states) -> OracleRows` calls, through `frob-fsim`:
   forward kinematics (link poses and link twists), inverse dynamics τ = M·v̇ + h, the mass matrix M, and
   contact-free forward dynamics v̇ = M⁻¹(τ − h). Results are cached on disk keyed by (model digest, state file
   digest, stack-lock digest); the airlock never caches across pins.
4. **Candidate side.** `trait Kin03Candidate { fn kinematics(..); fn inverse_dynamics(..); fn mass_matrix(..);
   fn forward_dynamics(..); }`, implemented by the `batch-cpu` harness running the kernels in `f64` on the
   packed model with the 10⁴ states as 10⁴ worlds of one batch (which also exercises batching: the candidate is
   one launch per level, not 10⁴ calls).
5. **Conversions.** Poses: packed transforms to the airlock's motor type; twists and wrenches keep the
   convention (angular part first, body frame). The mass matrix is compared in the candidate's coordinate
   order after applying the lowering's permutation (links are numbered topologically with depth levels
   precomputed; the oracle uses its own order). The permutation comes from the packed lowering and is tested
   by reconstructing kinetic energy on both sides.
6. **Metric (DESIGN).** For a quantity x with oracle value x°: per state, e = ‖x − x°‖∞ / max(s, ‖x°‖∞), with
   the floor s equal to the quantity's natural scale for that robot (1 m for positions, 1 rad/s for twists,
   the largest diagonal entry of M° for the mass matrix, 1 N·m for torques, 1 rad/s² for accelerations).
   Rotations are compared by the rotation angle of R·R°ᵀ (rad). Pass: the maximum over 10⁴ states is at most
   10⁻¹⁰ for each of the four rows and each robot.
7. **Gate assembly.** The harness writes one record per (robot, row) and a combined record once all four rows of
   a robot exist. GATE-KIN-03 is recorded PASS when every robot has four passing rows and the controls were
   caught; the record names the bead that supplied each row.
8. **Self-test without any kernel.** The harness compares the oracle against itself through a second code path
   (inverse dynamics against M·v̇ + h assembled from the mass matrix and bias; forward dynamics against a dense
   solve) to 10⁻¹², so that the harness can be closed before the kernels exist and so that a broken conversion
   is found here and not blamed on a kernel.

## Acceptance criteria

- [ ] State files exist for every robot with header digests; regenerating them from the stream key reproduces
      them byte for byte.
- [ ] The self-test passes: the oracle's inverse dynamics equals M·v̇ + h, and its forward dynamics equals the
      dense solve, to 10⁻¹² relative on all states.
- [ ] The comparison API reports, per (robot, row): maximum error, 99th percentile, the state index and the
      entry at fault.
- [ ] The three planted candidates below fail the row they target and only that row.
- [ ] The gate record assembles from four rows and refuses to record PASS with a row missing.
- [ ] Results carry claim "Parity", tier `batch-cpu`, precision `f64`, the oracle pin and `reality: no-claim`.

## Test plan

### Unit tests

- `kin03::states_regenerate`: byte equality of regenerated state files.
- `kin03::oracle_self_consistency`: the two identities of item 8.
- `kin03::permutation_preserves_energy`: ½·vᵀ·M·v equal on both orderings to round-off.
- `kin03::metric_scales`: a mass-matrix error of 10⁻¹² kg·m² on a diagonal of 10 kg·m² is 10⁻¹³ relative.
- `kin03::planted_candidates`: (a) a candidate with one placement transform inverted fails kinematics;
  (b) one with the Coriolis term dropped fails inverse dynamics at non-zero velocity and passes at zero;
  (c) one with a non-symmetric mass matrix (the upper triangle filled from an uninitialized buffer) fails the
  mass-matrix row.
- `kin03::gate_needs_four_rows`: a record with three rows is `not run`, not `pass`.

### End-to-end script and logging

`scripts/e2e/kin_parity_fsmbd.sh`: runs the conformance binary per robot and row
(`cargo run -p frob-conformance --bin frob-parity -- kin03 --robot <name> --row <kinematics|rnea|crba|fd>
--json`) and asserts on the summary. Log lines: `metric` with `robot`, `row`, `states: 10000`,
`max_rel_error`, `threshold: 1e-10`, the stack-lock digest and the model digest; `assert` per control;
`summary` with `gates: ["GATE-KIN-03"]` and the table of robots by rows. Failure lines carry the state index,
the entry, both values and the replay command for that single state. Logs under
`target/e2e-logs/kin_parity_fsmbd/`.

### Known answers and negative controls

- KA-360: `batch-cpu` in `f64` against `fs-mbd`: kinematics, inverse dynamics, forward dynamics, mass matrix on
  10⁴ states per reference robot; agreement within 10⁻¹⁰ relative; tier G2 on the lockstep site. The suite
  states no control; this bead registers the three planted candidates.
- Structure identities used as cross-checks (KA-048): kinetic energy equals ½·vᵀ·M·v; Ṁ − 2C is skew.
- Live-dependency proof: changing one inertia in the model changes both sides and keeps them in agreement;
  changing it on one side only fails.
- Determinism lanes: the candidate rows are run across worker counts 1, 8 and 24 and must give identical bits
  (class D2 on `batch-cpu`).

## Considerations

- The oracle's joint classes are fixed, revolute, prismatic and helical; a robot with a spherical joint is
  compared after the same lowering on both sides. When FrankenSim gains more classes (FD-FSIM-01) this gate is
  re-run.
- FrankenSim calls platform `sqrt`, `sin` and `cos`; the comparison tolerance of 10⁻¹⁰ is far above that
  difference, but the oracle cache is per platform.
- 10⁴ states × 12 robots is a few seconds of oracle time; the cache keeps the harness inside a unit-test budget.
- The same state files feed the `f32` and device differential checks, where the tolerance is the class's
  envelope and not 10⁻¹⁰.
