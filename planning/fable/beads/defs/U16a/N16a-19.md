## Background

Per-world parameter variants let one batch hold many designs that share a tree and differ in values: link
lengths, inertias, gear ratios, actuator-card parameters, foot radii, friction. The capability is parity with
incumbent practice; what this project adds, and gates, is that a variant's result is exactly the result it would
have had alone. GATE-KIN-06 (claim: Parity; M2; TARGET): a batch of 256 parameter variants of each reference
robot equals 256 homogeneous runs bit for bit on `batch-cpu` and on each GPU back end.

This bead is the end-to-end script for that capability on `batch-cpu`: it drives the real `frob` binary on a
sweep, compares digest chains variant by variant, and catches the registered negative control (a kernel that
reads the parameter row after its first use in the step). The device rows are recorded by the device-variants
bead with the same script.

## Scope

In: the script, the sweep fixtures, assertions and logs; the tier receipt of the `batch-cpu` gate rows; the
`--select` input of `sim.run`. Out: the mechanism
(BD-169); devices (BD-183); different trees in one batch (level P-B).

## Technical approach

Script: `scripts/e2e/kin_param_variants.sh`; plain shell over the STD-E2E helper; idempotent; seeds explicit.

Robots: the reference robots whose asset beads exist at M2 (the eleven `ROBOT-…` dependencies, the same set as
the parity harness N16a-17); the KUKA iiwa 7 joins when ROBOT-iiwa7 lands at M3 and its rows are `pending:
asset` until then.

Fixtures: for each reference robot, a sweep file `crates/frob-conformance/fixtures/kin/sweeps/<robot>-256.json`
of 256 variants generated once from a counter-based stream keyed by (`"kin06"`, robot, index): link lengths
± 10%, inertias ± 20% inside the physically consistent cone, gear ratios ± 15%, torque constants ± 10%, foot
radius ± 20%, sole–floor friction 0.3 to 1.0 (DESIGN ranges). The file is checked in with its digest.

Idempotency keys: `sim.run` is a job-submitting run verb, and a call without `--key` is refused with
`FROB-REF-805` (exit 3). Every run below carries its own key, `--key kin06-<run>-<robot>-<precision>-<step>[-<i>]`,
where `<run>` names this invocation of the script (UTC start time and seed); keys are never reused across steps,
variants, precisions or repeated lanes, and every envelope must show `idempotent_replay: false`. A reused key
returns the stored envelope without running, so a comparison of step 1 with a replayed step 1 would compare one
run with itself and pass vacuously.

Steps:

1. `sweep-batch`: `frob sim run --designs <sweep file> --worlds 256 --scene plane --seconds 2
   --tier batch-cpu --seed 7 --key <key> --json` (no positional design: the sweep file's rows are the robot's 256
   variant designs, and a positional design beside `--designs` is 802, N16b-25) → one run id; 256 distinct
   `model_id` values; one `step_plan_id`; results `provisional`.
2. `homogeneous`: for i in 0..255, `frob sim run --designs <sweep file> --select <i> --worlds 256
   --scene plane --seconds 2 --tier batch-cpu --seed 7 --key <key>-<i> --json` (the batch holds variant i replicated in every
   slot, with the same world addresses as in step 1) → the `step_plan_id` equals step 1's.
3. `compare`: for each variant i, the digest chain of the world that carried variant i in step 1 against the
   chain of the world with the same address in homogeneous run i (`frob telemetry query <run> --world <addr>
   --stream provenance --channels state_digest --json`). Assert 256 of 256 equal, in `f32` and again with
   `--precision f64`.
4. `no-recompile`: `frob spark cache --json` before and after step 1 → zero new kernel entries; the receipt's
   `captures` count is unchanged between step 1 and step 2.
5. `slot-permutation`: step 1 with the sweep file's rows permuted → results keyed by address are identical.
6. `live-dependency`: one variant's `link[3].length` doubled → only that world's digests change.
7. `bad-row`: a sweep row with a negative principal inertia → refused at admission, exit 3, the field named;
   a row with friction −0.1 → the contact chapter's invalid-cone refusal `FROB-REF-240` (exit 3, repair "fix the
   card"), raised at admission so no world of the batch runs.
8. `late-read-control`: KA-347's control, BD-169's mutant `mutant-late-param-read` (the parameter row read again
   after its first use in the step), in a `frob` binary built with `--features gauntlet-mutations` and that
   mutant's feature (BD-025's control-build form: one control per build, never a product build), steps 1 and 2 run
   under `e2e_expect_caught mutant-late-param-read` → at least one chain differs between steps 1 and 2;
   `control_caught: true`.
9. `gate-receipts`: the G5 row of KA-347 through the STD-E2E helper with its control, `e2e_tier
   g5_determinism GATE-KIN-06 --mutations`, its receipt hash listed in the summary. The script never runs
   `record_gate` and never writes `registries/gates.toml` or the bead log (the lint `self-recording`); the
   `batch-cpu` part (M2) is recorded from the receipt by a session that did not implement the work, with `cargo
   run -p frob-conformance --example record_gate -- --gate GATE-KIN-06 --part M2 --receipt <hash>`.

Logging: newline-delimited JSON to `target/e2e-logs/kin_param_variants/<utc-timestamp>.ndjson` with a transcript
beside it; every line has `ts`, `script`, `bead` ("N16a-19"), `step`, `event`, the exact command line, exit
code, wall time, the `evidence` block (claim "Parity", class, tier, determinism, identities, seed), measured
values with units and thresholds (`equal_chains: 256/256`, `new_kernel_entries: 0`), the digests compared and,
on failure, the variant index, world address, first differing step, stage and buffer, and the replay command.
The `summary` line lists assertions, controls caught and `gates: ["GATE-KIN-06"]`.

## Acceptance criteria

- [ ] 256 of 256 digest chains equal for each reference robot, in `f32` and `f64`, on `batch-cpu`.
- [ ] The late-read control makes the comparison fail; the honest build passes.
- [ ] Every `sim.run` call carries a key of its own and every envelope shows `idempotent_replay: false`; a planted
      reuse of step 1's key in step 5 is detected as a replay and fails the step instead of passing it.
- [ ] `step_plan_id` is one value across steps 1 and 2; `model_id` takes 256 values; zero new kernel-cache
      entries.
- [ ] The log has one `metric` line per robot with `variants`, `steps`, `equal_chains`, and one `assert` line
      per control; it validates against the STD-E2E schema.
- [ ] A smoke mode (32 variants, 0.4 s) runs in under two minutes on eight cores (TARGET).

### Known answers and negative controls

- KA-347: a batch of P parameter variants of one tree (256 per reference robot at the gate) equals P homogeneous
  runs bit for bit; exact (bits); tier G5; control: the parameter row read after its first use in the step.
- Metamorphic relation: P parameter variants in one batch equal P homogeneous runs bit for bit; a world of a
  mixed cohort equals the same world in a homogeneous batch. Mutation that must break it: a parameter row read
  after its first use in the step.

## Considerations

- 256 homogeneous runs of 256 worlds each is 65,536 world-runs per robot per precision; at 2 s each it is
  minutes on `batch-cpu`. The count is part of the gate and is not reduced in the gate lane.
- The comparison is by address, never by slot: the same address must carry the same randomization draw in both
  runs, which is what makes the equality meaningful.
- `--select <i>` is the `sim.run` input this bead owns (VERBS-sim): the index of one variant of the
  `--designs` file, placed in every world slot with the world addresses unchanged; accepted only with
  `--designs`; an index outside the file is `FROB-REF-802`; written into the manifest. `--precision` is N35-04's
  row.
