## Background

`fidelity.coverage` answers a question every consumer of a referee-promoted result should ask first: how often
can the referee answer at all for this kind of robot, and if it could not, who adjudicated? The referee stands
on a contact solve that admits at most 21 contacts and keeps fixed witnesses, so its coverage differs by robot
class, and GATE-FID-03 requires the figure to be reported per class with its breakdown, the share the `strict`
profile completes instead, and the wall-clock of a promotion at the 50th and 95th percentiles, with the
adjudicator named wherever coverage is below 90%.

This bead is the end-to-end script for the capability: it runs the coverage campaign through the real binary on
fixtures whose expected columns are known by construction, reads the result back with the verb, and logs the
measured rows for the gate.

## Scope

In: the script, a reduced battery of known-outcome scenarios, assertions and logs, and the gate run's receipt
with the measured rows for the reference classes. Out: the mechanism and the ledger table (BD-213); the background
referee's own gate GATE-FID-07 and its script `background_referee.sh` (N16b-34), which asserts only that the
sampler's figure reaches a receipt; the full battery run at M2 exit, which uses the same script without `--reduced`.

## Technical approach

Script: `scripts/e2e/fidelity_coverage.sh`; plain shell over the STD-E2E helper; idempotent; seeds explicit;
exits non-zero on failure after the summary.

Reduced battery (fixtures under `crates/frob-conformance/fixtures/coverage/`, all `synthetic`), chosen so that
every column of the report has a scenario whose outcome is known in advance:

| Scenario | Expected on the referee | Expected on `strict` |
|---|---|---|
| Point-foot quadruped trotting on a plane (at most 4 contacts) | completed | not attempted |
| Quadruped with 16 foot samples standing (16 contacts) | completed | not attempted |
| Humanoid, 8 samples per sole, standing (16 contacts) | completed | not attempted |
| Humanoid, hands and knees down (more than 21 contacts) | refused, `contact-cap` | completed |
| Hexapod, six feet down with four samples each (24 contacts) | refused, `contact-cap` | completed |
| Tracked skid-steer driving straight (patch samples along two belts) | refused, `contact-cap` | completed |
| Wheel rolling over a sharp lip with witness migration disabled | refused, `fixed-witness-gate` | completed |
| A model with a planar joint the lowering is told not to lower | refused, `missing-joint-class` | completed |
| A four-bar closure requested as an exact loop | refused, `kinematic-loop` | completed |
| The accumulation fixture (restitution 0.5 from 1 mm) | `numerical-fault` (`FROB-REF-220`) | `numerical-fault` |

Steps:

1. `campaign`: `frob eval run --battery coverage-reduced --class <class> --tier referee --adjudicate
   strict-fallback --record coverage --key cov-<class> --json` for the classes quadruped, humanoid,
   hexapod, tracked (the options `--adjudicate` and `--record coverage` of `eval.run` are BD-213's, on
   VERBS-eval's row; the battery fixes the seeds) → a job that completes (exit 8, then `frob job wait`); each
   scenario's outcome in the result.
2. `read-class`: `frob fidelity coverage --class <class> --json` → asserts every field of the output schema is
   present; completed + refused by cause + numerical faults = scenarios; `strict.attempted` = scenarios not
   completed by the referee; the per-scenario outcomes equal the table above.
3. `adjudicator-rule`: for a class whose share is under 0.90 → `adjudicator = "batch-cpu:strict"`,
   `bet34 = "falsified"`; for the point-foot quadruped class (share 1.0 on this battery) →
   `adjudicator = "referee"`.
4. `percentiles`: `promotion_wall_clock_s.p50 ≤ p95`, both positive, `basis` present, `cores` equal to the
   cores the campaign used.
5. `read-run`: `frob sim run quad-mammal --tier batch-cpu --worlds 64 --seconds 2 --seed 7 --key cov-run
   --json`, then
   `frob fidelity coverage --run <id> --json` → `shadow.share = 0` (no background referee was started) and
   `referee_own` equal to the quadruped class row.
6. `no-physics`: the verb creates no run id and returns in under one second.
7. `stale`: the campaign's row is re-read after the test harness changes the recorded stack-lock digest in a
   scratch ledger → the row prints `stale`.
8. `truncation-control`: control (a) of GATE-FID-03 as BD-213 registers it (the referee build that truncates
   the contact set at 21 instead of refusing) → the hands-down humanoid is reported `completed`; the assertion
   against the table fails as required and the step records `control_caught: true`.
9. `unrun-strict-control`: control (b) of GATE-FID-03 as BD-213 registers it (refused scenarios scored as
   completed by `strict` without running them) → `strict` wall-clock records are missing; `control_caught: true`.
   Each of the two controls runs in a `frob` binary built with `--features gauntlet-mutations,<crate>/nc-<nnnn>`, the
   feature of the control's record (BD-025's form: one control per build, never a product build), under
   `e2e_expect_caught <NC-nnnn>`.
10. `sim-run-fallback`: the single-run route of N16a-05 at M2, `frob sim run --fixture traction/referee_capacity_22
    --tier referee --profile referee --adjudicate strict-fallback --seed 7 --key cov-fb-a --json` (BD-080's
    22-contact island, the fixture of N16a-10's step 14) →
    completes with `adjudicator = "batch-cpu:strict"` and `referee_refusal { cause: "contact-cap", limit:
    "contact-cap", upstream_reason }` attached, and the contact count at the airlock equal to the generated
    count; the same command with `--adjudicate referee-only` and its own key (`cov-fb-b`) exits 5 with
    `FROB-REF-721` (the values of `--adjudicate` are N16a-05's policy names). This is the M2 half of the step that
    N16a-10 runs at M1, where the route returns the refusal with the repair marked `not in this build`.
11. `mcp`: the same read through the MCP surface (`fidelity_coverage` tool) returns the same structured content.
12. `gate-receipt`: for the gate run (without `--reduced`), BD-213's Gauntlet entry on the frozen standard
    battery with its two controls, `e2e_tier g2_parity GATE-FID-03 --mutations`, its receipt hash logged on the
    `cmd` line and in the summary. The script never runs `record_gate` and never writes `registries/gates.toml`
    or the bead log (the lint `self-recording`); a session that did not implement the work records the gate from
    the receipt with `cargo run -p frob-conformance --example record_gate -- --gate GATE-FID-03 --receipt <hash>`.

Logging: newline-delimited JSON to `target/e2e-logs/fidelity_coverage/<utc-timestamp>.ndjson` and a transcript
beside it. Every line: `ts`, `script`, `bead` ("N16a-20"), `step`, `event` (`start`, `cmd`, `assert`, `metric`,
`refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim
"Fidelity", class, tier, determinism, identities including the battery identity and stack-lock digest, seed),
measured values with units and thresholds (`share` against 0.90, counts by cause, `strict_share`, `p50_s`,
`p95_s`), and on failure the scenario, its expected and observed outcome, the refusal code and cause, and the
replay command for that scenario. The `summary` line: assertions passed and failed, controls caught,
`gates: ["GATE-FID-03"]` with the class table.

## Acceptance criteria

- [ ] The script exits 0 on a clean build; each control build makes its step fail.
- [ ] Every scenario of the reduced battery lands in its expected column on both tiers.
- [ ] The log has one `metric` line per class with all fields of the report and one `refusal` line per refused
      scenario with code `FROB-REF-721` (or the scope refusal), cause and limit id.
- [ ] The gate run's receipt holds a row for every reference class; a class under 90% names its adjudicator.
- [ ] The log validates against the STD-E2E schema and contains no private-scene data.

## Test plan

### Unit tests

Helper tests under the STD-E2E harness: `partition_identity`, `reads_cause_columns`, `detects_missing_field`,
`fails_when_control_not_caught`.

### End-to-end script and logging

This bead is the script (Technical approach). Lanes: twice on one machine with identical tables; debug and
release; the referee lane on one platform.

### Known answers and negative controls

- CX-151: the referee cannot adjudicate every scenario the fast tiers run (16 contacts standing; 24 for six
  feet with four samples each; a tracked robot overflows in normal driving). The reduced battery turns each
  clause into a row.
- Controls: the truncating referee (reports full coverage); the campaign that does not run `strict`.
- Live-dependency proof inside the script: with the registered contact cap lowered to 16 in a scratch register,
  the standing humanoid moves to `contact-cap`.

## Considerations

- The reduced battery proves the report's mechanics, not the gate; the gate needs the frozen standard battery
  for every reference class, which is hours of referee time and runs once at M2 exit and at each release.
- The numbers this script records decide a stop decision of M2 (name an adjudicator, or restrict claims to the
  classes the referee covers) and the status of a thesis bet; they are recorded by a fresh session.
- If witness migration lifts a class's coverage, the `fixed-witness-gate` column should fall; the script keeps
  one scenario with migration disabled so the column stays testable.
