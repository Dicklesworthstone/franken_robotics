## Background

FrankenRobotics (a robotics simulation and design system) runs worlds through the verb `sim.run`
(`frob sim run`). At M0 the verb answers on the referee tier for the built-in model `g1` only (BD-024): one world,
a length, a seed, no task and no controller. Its full form on every tier, with the task's environment built through
the vectorized environment, is N16b-25's at M2. Between the two, M1 is the referee studio, and its gates call
`sim.run` with a task and a controller on the referee: GATE-REFLEX-01 runs `frob sim run <design> --tier referee
--task stand-10s --controller <ControllerId>` and the traverse task (N22a-11, N22c-01, the script BD-117 fixes);
GATE-REFLEX-03 runs estimated-state referee runs of a trot (N22a-05); the archetype catalog runs the standing rows
(N14b-06); the thermal start of a task is overridden on a referee run (N15a-29, N15a-27); the open-loop schedules
of N15ap3-01 are prefixed forms of `--controller`; and GATE-MARROW-06 selects the worlds A and B of a torsion-spring
rig with `--init` (N13-36). None of these inputs had an M1 owner, so every one of those scripts would have answered
`FROB-REF-802` (unknown parameter) on the real M1 binary.

This bead is that owner: the inputs `--task`, `--controller` (its values `baseline`, a `ControllerId` and a
registered controller name) and `--init` of `sim.run` on the referee tier at M1, with the spellings, domains,
defaults, identities and refusals of VERBS-sim's rows, which are the authority. It extends BD-024's handler and
reuses what M1 already has for the same purpose: the episode step of `eval.run` (N24c-04), the verdict evaluator
(N24c-02), the settled-pose cache (N24a-16), the task store and its static admission (BD-122) and the baseline
synthesis of `control.synth` (BD-118). Tier Solid; crates `frob-verbs` (the handler's composition code) and
`frob-dyn` (the referee run loop).

DESIGN, with the alternatives rejected: (a) one bead for the three inputs, because they share one admission path
(a task binds a controller and fixes the initial state of every episode); (b) the episode step of N24c-04 called,
not copied, so a `sim.run` task episode and an `eval.run` scenario at the same address are the same episode bit
for bit; (c) the referee only, because the batched tiers arrive at M2 with N16b-25, which extends these inputs to
every tier. Rejected: giving each input to the bead that first needs it (four crates would each patch the
handler, and the identity rules would be stated four times); running the M1 gates through `eval.run` (the gate
scripts read the run header, the per-tick telemetry and the state source of a single run, which a scorecard does
not carry); waiting for N16b-25 (moves three M1 gates to M2).

## Scope

In: the three inputs on `--tier referee` at M1, their validation, identity effects and refusals; the episode loop
of a task run on the referee (one episode per world, through N24c-04's step); the verdict of each episode in the
result; the binding of `baseline` and of a `ControllerId`; the selection of a named initial condition; the
generated input-schema entries; the unit tests and the end-to-end script below.

Out: the inputs on the other tiers, `--episodes`, `--scene`, the run-length forms `--steps` and `--intervals`,
`--on-overflow` and `--fail-fast` (N16b-25, M2); `--worlds` on the referee at M1 (BD-090) and stored designs on
the referee (N29ax-01, VERBS-sim's M1 owner of the positional design; both dependencies, since every run below
is on a stored design or a design path); the prefixed controller forms `fixture:` (N14b-06), `open-loop:` (N15ap3-01) and the later
ones; `--state` (N22a-03); `--thermal-start` (N15a-29); the task-file schema and its static checks (N24a-02,
BD-122); the declaration of named initial conditions in the design term (N14a-03's top-level block `init`); the
randomization plan of a task (BD-200, M2); the registered tasks themselves (BD-125 and the task-family beads).

## Technical approach

Layout (DESIGN): `crates/frob-verbs/src/verbs/sim_run/referee_task.rs` (admission and binding) and
`crates/frob-dyn/src/referee/episode_run.rs` (the loop over worlds); the handler is BD-024's
`crates/frob-verbs/src/verbs/sim_run.rs`, which dispatches to it when `--task`, `--controller` or `--init` is
present on `--tier referee`.

1. **`--task <task>`** (VERBS-sim's row; owner at M1 this bead). Domain: a registered task name (BD-125's
   `stand-10s` and `traverse-5m-flat`, and every task in BD-122's store), a `TaskId`, or the path of a task file
   (`.ftask`, the row's `artifact-input<task>` parameter). Resolution, before the request is digested: a name or
   identifier resolves through BD-122's store; a path is read and its canonical bytes hashed to a `TaskId` that
   must already be admitted (`task.check` passed). A name or identifier that resolves to nothing, or a file whose
   static admission fails, is `FROB-REF-802` (`pointer` `/task`), with the first failing check's code and pointer
   in `details` and the repair `frob task check <task>` (DESIGN: the run verb refuses the input; the task's own
   checks and codes belong to `task.check`, so `sim.run`'s list does not grow by the twenty task-admission codes).
   The `TaskId` is written into the manifest core (N29ax-01's identity block lists it).
2. **Admission of a task run.** In order, with zero worlds created: the controller binding (item 3); the
   settled-pose check of N24a-16 (no cache for this `ModelId` and task is `FROB-REF-529`, exit 3, with the
   command `frob task settle <task> --model <id>` in `next_actions`); the thermal start of the task where it
   declares one (N15a-29's resolution, its 132, when that bead is in the build).
3. **`--controller <c>`.** `baseline`, the default with `--task`: the design's baseline controller, bound by the
   binding N24c-04's step 1 makes (BD-118's synthesis for the design's morphology class on the referee, with its
   `ControllerId` recorded). A class whose route BD-118 has not built (`not-synthesizable`, reason
   `route-not-built`) is `FROB-REF-724`, exit 5, naming the class and the milestone BD-118 gives; any other
   `not-synthesizable` reason is 802 with BD-118's reason and the repair `--controller <ControllerId>`. A
   `ControllerId`: a controller record (`frob.control.id/1`) that `control.show` resolves; an unknown one is 802.
   A registered controller name resolves through the same store (names registered by their owners, such as
   N22c-29's `arm1-nominal-monitor` at M4). The prefixed forms are dispatched to their owners' loaders. The
   `ControllerId` enters the manifest and the run header; two runs that differ only in the controller have
   different `ControllerId`s and one `ModelId`. Without `--task`, `--controller` binds that controller for the
   run's length; without either, the run keeps BD-024's behaviour (the design's own actuator commands, no
   controller bound, no `ControllerId` in the header).
4. **`--init <name>[=<value>]`.** Selects a named initial condition that the design declares (N14a-03's top-level
   block `init`: each condition a name, joint coordinates and rates and the floating base's pose and twist, and at
   most one declared parameter with its dimension and domain, such as `drop` in `drop=0.1m`); a fixture selects
   through its design. Every world starts from it. The selected condition, with its value, enters the `ModelId`
   (so worlds A and B of N13-36 have distinct identities while their link poses agree). An undeclared name, a
   value without a declared parameter or outside its domain, or a unit of the wrong dimension is 802 naming the
   declared conditions. DESIGN at M1: `--init` with `--task` is 802 (`pointer` `/init`), because the task's reset
   and the settled pose fix every episode's initial state on the referee at M1; N16b-25 admits the combination
   when it extends the inputs to every tier.
5. **The episode loop.** For world i of `--worlds n` (BD-090's input; default 1), the address
   `(run_seed, i, 0)`; each world runs one episode through N24c-04's episode step (address-keyed draws, the
   settled pose, the bound controller, the referee step of BD-024 and BD-080) for the requested length, or, with
   no length input, to the task's horizon (DESIGN: BD-024's default of 2 s is for runs without a task; a task
   declares its own horizon). The episode is recorded in the run's `.frun` at the telemetry level of
   `--telemetry` (BD-090). N24c-02's evaluator then gives each episode's verdict (`frob.verdict/1`): `satisfied`,
   `violated` or `undetermined` when the length ended before a window closed.
6. **Result.** BD-024's result plus: the `TaskId`, the `ControllerId` and the outcome BD-118 reported for a
   `baseline` binding, the named initial condition, and per world its address, episode digest and verdict. The
   run's re-execution (BD-024, N29ax-01) covers the new fields, since they are in the manifest core.
7. **Schema.** The three inputs enter the generated `sim.run` input schema in the change that lands this bead
   (VERBS-sim's rule "How an input enters a row"); on `--tier batch-cpu`, `gpu-cuda` or `gpu-metal` at M1 the
   tier itself is 724 (BD-024).

## Acceptance criteria

- [ ] `frob sim run e2e-srm-quad --tier referee --task fixtures/sim/tasks/stand-2s.ftask --seed 1 --key srm-4
      --json` exits 0 with a `TaskId`, the `ControllerId` of `control.synth` for the design, one episode of 2 s
      and its `frob.verdict/1` record.
- [ ] The same request with `--worlds 4` gives four episodes at addresses (1, 0, 0) to (1, 3, 0) whose digests
      equal those of `frob eval run` in its single-task form on the same design, task and controller with
      `--worlds 4 --run-seed 1`.
- [ ] A model without a settled-pose cache for the task is refused with `FROB-REF-529`, exit 3, before any step,
      and the envelope's `next_actions` carries `frob task settle`.
- [ ] `--controller <ControllerId>` gives the digests of the `baseline` run; an unknown `ControllerId`, an
      unregistered task, an undeclared `--init` name and `--init` with `--task` are each `FROB-REF-802`, exit 3,
      one envelope, no world created; a design of a class whose route is not built answers `FROB-REF-724`, exit 5.
- [ ] `--init A` and `--init B` on the two-condition fixture give different `ModelId`s and the declared initial
      states at step 0.
- [ ] The generated `sim.run` input schema of the M1 build lists `task`, `controller` and `init` with VERBS-sim's
      domains, and VERBS-sim's `cluster_sim` tests pass on it.

## Test plan

### Unit tests

`cargo test -p frob-verbs --test sim_run_referee_m1` (the real handler, referee and stores; designs, tasks and
controller records written as fixtures are labelled `synthetic`):
- `task_resolves_name_id_and_file`: a registered name, its `TaskId` and its admitted file give one `TaskId` and
  equal episode digests; an unregistered name and a file that fails static admission (a window bound with no
  rounding declared) are 802, the second with the check's code in `details`, zero worlds created.
- `task_runs_to_horizon_with_verdict`: with no length input a task of horizon 2 s runs 2 s and carries one
  verdict per world; with `--seconds 1/2` the verdict is `undetermined` where a window of the requirement had not
  closed.
- `settled_pose_missing_529`: before `task.settle` the run is 529 with the repair command; after it, the run is
  admitted.
- `episode_equals_eval_run`: per world address, the episode digest of `sim.run --task` equals that of N24c-04's
  single-task form at the same address, controller and seed.
- `controller_baseline_and_id`: no `--controller` binds the baseline (`ControllerId` equal to `control.synth`'s);
  the same `ControllerId` given explicitly gives equal digests; a second controller changes `ControllerId` and
  not `ModelId`; an unknown identifier is 802; a `synthetic` design of a class with no route at M1 is 724.
- `init_named_condition`: on `fixtures/sim/init-two-states.fbot` (declares `A`, `B` and `drop` with domain 0 m to
  1 m), `--init A` and `--init B` differ in `ModelId` and in the step-0 state; `--init drop=0.1m` starts 0.1 m
  above the plane; `--init C`, `--init drop=2m` and `--init drop=0.1s` are 802 naming the declared conditions;
  `--init A --task <t>` is 802.
- `no_task_no_controller_unchanged`: a run with none of the three inputs has BD-024's manifest and digests.
- `reexecution_covers_task`: a second invocation of a task run with the same manifest reproduces it
  (`reproduced: true`), and one changed task byte changes `RunId`.

### End-to-end script and logging

`scripts/e2e/sim_run_referee_m1.sh` (owned here; sources the STD-E2E helper; seed from `FROB_E2E_SEED`, default
1; idempotent; every run under its own key; header `bead=N16ap4-01 milestone=M1 labels=kinesis,verb:sim.run
seed=1 needs=cpu plants=controller-ignored,init-ignored`). Fixtures registered here, all `synthetic`: the task
`fixtures/sim/tasks/stand-2s.ftask` (the stand requirement of BD-125's `stand-10s` with a 2 s horizon) and the
design `fixtures/sim/init-two-states.fbot`. Steps: (1) `frob design new e2e-srm-quad --template quad-mammal --key
srm-1 --json`; (2) `frob control synth e2e-srm-quad --tier referee --seed $SEED --key srm-2 --json`, keeping the
`ControllerId`; (3) `frob task new fixtures/sim/tasks/stand-2s.ftask --key srm-3a --json` and `frob task settle
<TaskId> --model e2e-srm-quad --key srm-3b --json` (waiting with `frob job wait` on exit 8); (4) the acceptance
run; (5) the same with `--worlds 4 --key srm-5` and `frob eval run e2e-srm-quad --task <TaskId> --tier referee --worlds 4
--run-seed $SEED --key srm-5e --json`: per-address digests equal; (6) `--controller <ControllerId> --key srm-6`:
digests equal to step 4's; (7) `frob sim run fixtures/sim/init-two-states.fbot --tier referee --init A --seconds
1/10 --seed $SEED --key srm-7a --json` and `--init B --key srm-7b`: different `ModelId`s; (8) refusals with
`e2e_expect_refusal`: `FROB-REF-802 3` for `--task no-such-task`, `--controller c:0000`, `--init C` and `--init A
--task <TaskId>`; `FROB-REF-529 3` for the task on a second design with no cache. Log:
`target/e2e-logs/sim_run_referee_m1/<utc>.ndjson` and a transcript; every line has `ts`, `script`, `bead`,
`step`, `event`, the exact command line, exit code, wall time and the envelope's evidence block; the identities
(`TaskId`, `ControllerId`, `ModelId`, `RunId`) and episode digests of each run; refusals with code, pointer and
first repair; on failure the first differing address and digest; a final `summary` line.

### Known answers and negative controls

Known answers: the identity relations above (equal digests across the `baseline` and explicit-identifier forms,
across `sim.run` and `eval.run` at one address; distinct `ModelId`s for A and B); exact. Negative controls: a
mutant that ignores `--controller` and always binds the baseline (`controller-ignored`) must fail
`controller_baseline_and_id` and step 6 when a second controller is given; a mutant that drops `--init`
(`init-ignored`) must fail `init_named_condition` and step 7. Determinism: referee class D2, as BD-024; the
identities are exact.

## Considerations

- Users at M1 that run these forms depend on this bead: N22a-11, N22a-05, N22c-01 (which runs BD-117's script),
  N14b-06, N13-36, N15a-27, N15a-29, N15a-12, N15a-24, N15ap3-01 (the property its prefixed form extends),
  N24a-42, N24b-05 and N24c-06. N16b-25 depends on it and extends the three inputs to every tier at M2.
- The baseline binding synthesizes on demand when no synthesis is memoized for the design; a script that compares
  runs should synthesize first and pass the `ControllerId`, so the synthesis cost is not inside the run.
- Risk: N14a-03's `init` block may name fields differently from item 4; the block's spelling then governs and
  this bead's reader follows it in the same change.
