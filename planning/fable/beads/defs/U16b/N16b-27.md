## Background

Every surface of the system (the CLI, the daemon protocol, the MCP tool definitions, the schemas, the refusal
table and the agent documentation) is generated from one registry, `registries/verbs.toml`, owned by
`frob-verbs`, so the surfaces cannot drift. A verb exists for an agent only if its registry entry exists with a
name, a kind, a capability list, input and output schemas, a refusal list, a cost model, a first milestone, task
clusters and examples.

The dynamics chapter owns nine rows of the verb table: three existing verbs that gain options or outputs
(`sim.run`, `sim.estimate`, `eval.promote`) and the `fidelity` cluster. The registry rows themselves are written
once, by the registry bead of each cluster (VERBS-fidelity for the five `fidelity.*` rows, VERBS-sim for
`sim.run` and `sim.estimate`, VERBS-eval for `eval.promote` and `eval.rank-agreement`); the executors behind
them are other beads again. What is left for the dynamics unit, and is this bead, is two things no registry bead
does: to check that those rows say what the dynamics chapter says (its verb table, its option and output-group
names, its refusal table), and to carry one question to the owner, because the plan names one of these verbs in
two ways.

Kinds: `read` returns stored or cheaply computed facts and changes nothing; `run` spends compute, takes an
idempotency key and a budget, accepts the bounded synchronous wait and otherwise returns a job handle with exit
8; `admin` cancels, stops, evicts or deletes and needs a capability scope.

## Scope

In: the chapter-against-registry check for the nine rows (kinds, first milestones, option names and values,
output-group names, refusal codes, task-cluster membership, capability scopes); the names of the Kinesis options
and output groups that the rows of other clusters must carry; the naming decision record, with its second note
on the first milestone of `fidelity.shadow`; the plants that keep the decision honest.

Out, with the bead that has it:
- the five registry entries of cluster `fidelity`, with every field, their MCP tool names, their schema
  snapshots and the cluster's conformance script: VERBS-fidelity, a dependency. This bead writes no row.
- the rows of `sim.run` and `sim.estimate`: VERBS-sim, a dependency. The rows of `eval.promote` and
  `eval.rank-agreement`: VERBS-eval, a dependency.
- the entry schema and the registry lints (NJL-01); the one-name lint (NJL-04); the task-cluster declarations
  and the size lint (NJL-05). This bead plants violations that those lints must catch on its rows and defines
  no lint.
- executors (the beads named per row below); the M2 and M3 roll-up of all verbs (BD-222, BD-312).

**The check (`crates/frob-verbs/tests/registry_fidelity.rs`).** It loads the real generated registry and asserts,
row by row, that the registry agrees with the table above and with the lists below. It asserts nothing about a
field the chapter does not speak of (examples, schema versions, cost models are the registry beads' own).

1. *Presence and kind.* The eight rows of the default (nine if the owner chooses the sixth `fidelity` verb) exist
   with the kinds above; `read` rows are idempotent and take no budget; `run` rows take a key and a budget; the
   admin row requires its scope.
2. *First milestones.* As in the table, with `fidelity.shadow` at M3 (see the second note) and, under the naming
   default, the tier-pair form of `eval.rank-agreement` answering from M3.
3. *Options and output groups (the Kinesis names; recorded here because the executors and the rows must use the
   same spellings).* `sim.run`: the inputs that VERBS-sim's input tables give to a bead of this chapter (owners
   N16a-*, N16b-*, N16c-*), with the tables' spellings and value sets, re-recorded from those tables: the
   positional `design`; `--select`; `--fixture` (N16c-41's part); `--scene`; `--task`; `--worlds`; `--seconds`,
   `--steps` and `--intervals` (exactly one); `--episodes`; `--world-addr`; `--init <name>[=<value>]`;
   `--controller` (default `baseline`); `--tier` with `referee`, `batch-cpu`, `gpu-cuda`, `gpu-metal`; `--profile`
   with exactly `lockstep`, `strict`, `referee`; `--law` in the law table's spelling (`CL-1`, `CL-2`, `CL-H`,
   `CL-M`, `CL-1R`, ...; the input is N18b-28's, admitted on every tier by N16b-25); `--designs` for per-world
   slots; `--step`, `--newton-iterations`, `--warm-start on|off`; `--substeps`, `--integration exact-hold`;
   `--txn l-max=<L>,e-max=<E>,retries=<N>`; `--adjudicate referee-only|patch-reduction|strict-fallback`;
   `--closures auto|rows`; `--capacity contacts=<C>[,rows=<R>]`; `--jacobian dense|path-table`; `--refine-step`;
   `--solve-path dense|ancestor|tree`; `--solve-queues off|auto|<q0,q1,q2>`; `--decouple [reference]` (M8);
   `--on-overflow refuse|reset|continue-flagged` (default `continue-flagged`); `--fail-fast`; `--present` (M3,
   N16b-24). The ruled-out spellings of these inputs that the table lists (`--law cl-h`, `--adjudicate strict`,
   `--variants`) are 802 with the replacement as first repair. The rest of `sim.run`'s tables (the other
   chapters' inputs, the operator-only, conformance-build, chaos-build and conditional inputs) is checked against
   the served schema by VERBS-sim's own conformance script (`verbs_cluster_conformance sim`); this check does not
   restate it. `sim.estimate`: the four output groups of the dynamics chapter in
   `frob.sim.estimate.out/1`, named `capacities`, `bytes` (with the fields `formula_bytes` and the base
   record's `per_world_bytes`, as N16b-26 fixes them), `degraded` and `referee_coverage` (DESIGN names for the
   groups; the snapshot of VERBS-sim pins them once N16b-26 lands). `eval.promote`: `--method` with exactly
   the values `paired`, `dr`, `multilevel`, `segment` (`segment` only while the pilot PILOT-KIN-01 of N16b-09 has
   not returned `falsifier-holds`; if it does, N16b-08 drops the value and this expected set shrinks with it, in
   the same change); `--adjudicator` with exactly `auto`, `referee`, `batch-cpu:strict`, and `--law` with `CL-1`,
   `CL-H` (BD-263); the outputs ρ and the higher-tier-only count replaced. `fidelity.modelform`: `--k`,
   `--budget-share`, and `--on-overflow` with exactly `refuse`, `continue-flagged` (default `refuse`).
   `fidelity.shadow`: the actions `start`, `stop`, `configure`, `status`, and `audit` once N16b-20 lands.
4. *Capability scopes (DESIGN, the same names as in VERBS-fidelity).* `fidelity:read` for the read verbs,
   `fidelity:run` for run verbs, `fidelity:admin` for `fidelity.shadow`.
5. *Schema names.* `input_schema` and `output_schema` of each row are `frob.<verb>.in/1` and `frob.<verb>.out/1`.
6. *Refusal codes (from the chapter's refusal table).* Each code below is in the refusal list of the row named,
   and the registry loader rejects an unknown code at load time. `sim.run`: 212, 220, 221, 222, 223, 224, 721,
   722, and 610 beside 722 (the same overflow on a device tier; both listed, neither merged, KNOWN_DRIFTS 6). The
   row's other codes (103, 136, 160, 245, 246, 247, 248, 457, 461, 464, 522, 530, 531, 601 to 609, 611 to 616,
   731, 733, 734, 816, and 790 appended by the generator from `needs_groups`) are other chapters' and are not
   asserted here. `eval.promote`: 561 (arms that cannot be paired: BD-263's undeclared solve-path mismatch), 811,

   not on the row: a referee refusal inside a promotion is routed to the strict adjudicator or ends
   `provisional: referee-unavailable`, never returned as 721.

   tier-pair rank verb: 537, 545, 548 (the rank-agreement refusals BD-265 raises, shared with the rung form) and

   610 and 722, both raised by the verb (722 on `batch-cpu`, 610 on a device tier, BD-266); 557 and 830 are not on

   chapter (the row's 840 belongs to the qualification campaign). `fidelity.shadow`: none of its own beyond the

7. *Task clusters.* A registry cluster is a namespace; what an agent lists at a time is a task cluster of at
   most seven tools. The task cluster `fidelity` (declared by NJL-05) holds the five `fidelity.*` verbs of the
   starting assignment (`fidelity_ledger`, `fidelity_energy`, `fidelity_coverage`, `fidelity_modelform`,
   `fidelity_shadow`) with `eval_promote` and `eval_rank_agreement`: seven. `fidelity_modelform` also sits in
   `inherit`; `sim_run` and `sim_estimate` in `simulate`; `eval_promote` in `compare`. The limit of seven
   applies to task clusters, the tools one agent session lists at a time, and not to registry clusters.

**Not yet implemented.** By the registry's convention (stated in each registry bead), an entry whose executor
has not landed answers `FROB-REF-724` (the verb is not implemented in this build; exit 5) with one envelope on
both surfaces, and `frob capabilities --json` lists it as absent, with its first milestone, so the registry is
complete from M2 while verbs arrive through M3. The check asserts this for the rows above whose executor is an
M3 bead.

**The naming question (owner decision, fail-closed default).** The chapter's verb table and one row of the
registry appendix name the tier-pair rank measurement `fidelity.rank` and count six verbs in the `fidelity`
cluster. The registry appendix's one-name-per-verb table, its task-cluster assignment ("its five verbs") and the
seed beads register the rank-agreement record "for rungs and for tier pairs" under `eval.rank-agreement`, and
state that the registry holds no alias and that a lint refuses a second spelling of a registered verb. Both
cannot be registered for one mechanism. Default until the owner decides: register `eval.rank-agreement` only,
accepting a rung pair or a tier pair (`--pair tier:<lo>,<hi>`), first milestone M3 for tier pairs and M4 for
rungs; `fidelity.rank` is not a verb; the `fidelity` registry cluster then has five verbs. If the owner chooses
`fidelity.rank`, it becomes a sixth entry (written by VERBS-fidelity: kind `run`, M3, executor BD-265, the
registry then holding 244 verbs) with the same executor, and `eval.rank-agreement` is restricted to rung pairs.
The decision is recorded in `docs/adr/ADR-VERB-rank-name.md`; the default costs nothing to reverse because the
executor (BD-265) is the same. The registry beads state the same default and point here for the record.

One consequence of the default for the row's owner, written into the same record: the row of
`eval.rank-agreement` prints one first milestone, M4, the milestone of the rung measurement (BD-328), and
VERBS-eval lists it among the rows that answer a reduced form before their first milestone: from M3 the verb
answers tier pairs with `form: "tier-pair"` (BD-265) and the fixture form (N23b-35), and a rung pair before
BD-328 answers `FROB-REF-724`. The check's item 2 asserts exactly that: first milestone M4, and the tier-pair form
answering from M3, never `FROB-REF-724`.

**Second note for the same record.** `fidelity.shadow` prints first milestone M3 in both verb tables of the plan,
while the M2 exit list and the seed bead (BD-214) deliver the sampled referee and the command at M2, and
GATE-FID-07 is recorded at the M2 exit. Default (DESIGN, the same statement in VERBS-fidelity): the registry
entry says M3, as printed; at M2 the verb is delivered behind the feature `frontier-shadow`, and a build
without that feature answers `FROB-REF-724`. Reason: the registry row is checked against the plan's inventory,
which prints M3 twice, and a feature-gated early delivery contradicts neither. The question for the owner is
whether to move the row to M2; if so, one field of the row and one test value change.

**Lints the plants exercise.** The lints are the registry's (NJL-01, NJL-04, NJL-05) and run in the registry
check: one name per verb; every verb in at least one task cluster; no task cluster above seven; every refusal
code exists; every entry has an example; kinds match behaviour (a `read` verb takes no idempotency key). This
bead adds planted violations on its own rows.

## Acceptance criteria

- [ ] `registries/verbs.toml` contains the eight or nine entries above (per the naming decision), written by the
      three registry beads, and loads; the check of this bead passes on every item 1 to 7.
- [ ] `frob capabilities --json` lists them with first milestones; an unlanded verb answers `FROB-REF-724`,
      exit 5, and is listed as absent.
- [ ] The MCP `tools/list` for the task cluster `fidelity` shows seven tools plus the three base tools, and the
      served list equals the registry (the surface-drift gate's diff is empty for these rows).
- [ ] The lints pass; a planted second spelling of one verb fails the one-name lint; a planted eighth tool in
      the `fidelity` task cluster fails the size lint.
- [ ] The naming ADR exists, states the default in force and what would change, carries the note on
      `fidelity.shadow` and the consequence for the first milestone of `eval.rank-agreement`, and is cited in the
      comment of the registry entries it concerns.
- [ ] Every refusal listed for a verb is produced by at least one test of its executor bead, or, for a code
      marked as raised by consumers, by a test of the consuming verb (cross-checked by a registry test that reads
      the executor crates' refusal tests).
- [ ] No row is defined in this bead's code: the test file reads the generated registry and holds only the
      chapter's expected values.

## Test plan

### Unit tests

`crates/frob-verbs/tests/registry_fidelity.rs`:
- `entries_present_and_complete`: each of the chapter's rows exists in the registry with every required field.
- `kinds_match`: read verbs have `idempotent = true` and no budget; run verbs take a key and a budget; the admin
  verb requires `fidelity:admin`.
- `milestones_match_chapter`: the first milestones of the table; `fidelity.shadow` at M3; `eval.rank-agreement`
  at M4 with its tier-pair form answering from M3.
- `kinesis_options_and_groups`: the `sim.run` inputs of item 3 with their value sets (`--profile` values, `--law`
  in the table's spelling with `cl-h` refused, `--on-overflow` values and default, exactly one length input), the
  four output groups of `sim.estimate`, the `--method`, `--adjudicator` and `--law` values of `eval.promote`, the
  `--on-overflow` values of `fidelity.modelform`.
- `chapter_refusals_present_in_rows`: the codes of item 6, row by row; `sim.run` includes 212 and both 610 and
  722; `eval.promote` includes 561 and not 721; the rank verb includes 545, 546 and 548; the refusal list of
  `fidelity.modelform` is exactly {610, 722}.
- `executor_names_current`: the implemented-by field of `fidelity.ledger` names N16bp1-01 (a row that still
  names only BD-212 fails).
- `shadow_actions`: the input schema of `fidelity.shadow` enumerates `start`, `stop`, `configure`, `status` (and
  `audit` when N16b-20 has landed).
- `task_cluster_fidelity_has_seven`.
- `one_name_lint`: adding `fidelity.rank` as a second name for the same executor while `eval.rank-agreement`
  accepts tier pairs fails.
- `unknown_refusal_code_rejected`: a planted `FROB-REF-999` in a list fails the load.
- `not_implemented_answers_724`.

### End-to-end script and logging

`scripts/e2e/kinesis_surface.sh` (N16b-35): `frob capabilities --json`, `frob schema fidelity.ledger --json`,
and an MCP `tools/list` under `session_focus {cluster: "fidelity"}`. Logged: the entries found, the tool count
against seven, the exit codes of unlanded verbs, and for each item of the check the observed and the expected
value.

### Known answers and negative controls

- The count of tools in the `fidelity` task cluster: seven.
- Negative controls: the second-spelling plant; the eighth-tool plant; the unknown refusal code; a registry in
  which `sim.run` lacks 212, which `chapter_refusals_present_in_rows` must catch; a registry in which
  `--profile` admits a fourth value, which `kinesis_options_and_groups` must catch.
- Determinism: the generated surfaces are byte-identical across two generations (the generated-files check).

## Considerations

- This is the bead where a contradiction in the plan is turned into a decision with a default; nothing else in
  the unit depends on which name wins.
- The refusal table of the chapter also lists the Cayley-bound refusal 212 as an existing code of the algebra
  subsystem; it appears in `sim.run`'s list and is not redefined here.
- Capability scope names are DESIGN defaults to be reconciled with the capability chapter's scope table when
  the full MCP surface lands at M3.
- Why a check and not rows: two beads that both write a row will sooner or later write it differently, and the
  places where that shows first are the ones the plan itself leaves open (the refusal list of
  `fidelity.modelform`, the first milestone of `fidelity.shadow`, whether `sim.run` lists 212). One bead writes
  each row; this one reads them.
