## Background

The dynamics subsystem meets its users through a small surface: `sim.run` with its profile, law and design
options; `sim.estimate`; the trust label on every result; and ten refusals, each with a stable code, a meaning
and ranked repairs. A refusal is part of the product: where the system cannot keep a promise it says so by name
and tells the caller what to do next. This bead is the end-to-end script that walks that surface from the
user's side, including every refusal of the chapter's table, so that a change to any step, verb or registry
entry that breaks the contract is caught by one script.

The ten refusals (code · name · raised when · ranked repairs):

| Code | Name | Raised when | Ranked repairs |
|---|---|---|---|
| `FROB-REF-212` | Cayley bound | ‖ω‖·h > 0.2 in a substep (existing code of the algebra subsystem) | Substep; use the exponential |
| `FROB-REF-220` | Event refinement limit | An event cannot be bracketed within L_max = 16 dyadic levels, or more than E_max = 64 events fall in one physics interval | Report the accumulation; switch law; shorten h |
| `FROB-REF-221` | Transaction exhausted | Every numerical plan of the retry ladder failed its checks | Teleport and inspect; the world is `Faulted` with `numerical-fault` |
| `FROB-REF-222` | Profile not available on tier | `strict` or `referee` requested on a GPU tier | Run on `batch-cpu` |
| `FROB-REF-223` | No refinement law | A stochastic driver without a registered refinement law under a transactional profile | Register the law; move the draw to a sample instant |
| `FROB-REF-224` | Indeterminate contact | No solution, or several distinct post-event motions | Report the configuration; do not return a number |
| `FROB-REF-721` | Referee capacity | An island exceeds the referee's contact cap, or FrankenSim's fixed-witness gate refuses | Patch reduction with its fixture; `--profile strict` |
| `FROB-REF-722` | Capacity overflow, refused | A world exceeds its contact or row capacity and the caller chose refuse | Raise capacity (new `StepPlanId`); reset; continue-flagged |
| `FROB-REF-820` | Label misuse | A result that is not `established` is cited as established, or a `model-conditional` ranking is used to authorize spend | Promote; run the settling experiment |
| `FROB-REF-821` | Envelope not frozen | Promotion requested for a quantity whose envelope is not hashed in the ledger | Freeze the envelope first |

Exit codes follow the envelope's table: 3 for refused input or question (the 2xx and 8xx codes here), 5 for the
72x codes.

## Scope

In: one script, its fixtures list, assertions, logging.
Out: the mechanisms behind each refusal (the transaction, retry ladder, batched step, labels, ledger beads).

## Technical approach

**Script.** `scripts/e2e/kinesis_surface.sh`; STD-E2E helper; scratch store under `target/e2e/kinesis_surface/`;
non-zero exit on failure; idempotent; `--seed 17`.

**Steps.**
1. `registry`: `frob capabilities --json` and `frob schema sim.run --json`. Assert the dynamics chapter's verbs
   are registered with kinds and first milestones, and that the `fidelity` task cluster lists seven tools.
2. `estimate`: `frob sim estimate` for the reference quadruped and humanoid. Assert C, R and bytes per world
   (32, 160, 31 kB; 64, 320, 92 kB), the `Degraded` field (measured or `unmeasured`, never a bare zero), both
   coverage figures, and that no physics step ran.
3. `run-matrix`: the 12 (tier, profile) pairs. Assert the five accepted pairs run (device pairs skipped with a
   logged reason on a machine without that device), `FROB-REF-222` on the four GPU pairs with `strict` or
   `referee`, and a schema refusal on the other three.
4. `labels`: a `batch-cpu` lockstep result prints `provisional`; a referee result does not.
5. `law`: `--law CL-2` (where admitted) changes the `StepPlanId` only.
6. `designs`: `--designs` with 8 parameter variants; each world's digest equals its homogeneous run's.
7. `overflow`: capacity forced to 8 under `refuse` (assert `FROB-REF-722`, exit 5, three repairs), `reset` and
   `continue-flagged` (assert `Degraded` counted, no contact unaccounted for).
8. `refusal-212`: a spinning body with ‖ω‖·h = 0.25 and substeps disabled. Assert code 212 and its repairs.
9. `refusal-220`: the accumulation fixture (a ball bouncing with restitution on the transactional profile until
   impacts accumulate). Assert code 220, the accumulation reported, no approximate state published.
10. `refusal-221`: a fixture built to exhaust the retry ladder. Assert the world is `Faulted` with cause
    `numerical-fault`, code 221, nothing published from the failed interval, and the outcome counted under
    `numerical`, not under `fall` or `collision`.
11. `refusal-223`: a custom stochastic driver with no registered refinement law under `--profile strict`.
    Assert code 223 and both repairs; the same driver under `lockstep` runs.
12. `refusal-224`: the rod fixture with no unique post-event motion. Assert code 224 and that no number is
    returned.
13. `refusal-721`: a humanoid crawl on the referee (more than 21 contacts in one island). Assert code 721, no
    truncated contact set, and that `--profile strict` completes the same scenario.
14. `refusal-820` and `refusal-821` (enabled at M3, when the first verb that requires established evidence and
    `eval.promote` exist; until then skipped with a logged reason and covered by the unit tests of N16b-04 and
    BD-212): cite a provisional result as established; promote in an unfrozen stratum.
15. `closures`: the parallel-knee template under the three profiles (bounded residual with compliance stated;
    exact closure; referee refusal with cause `kinematic loop`).
16. `pacing` (enabled when N16b-24 lands at M3; skipped with a logged reason until then): a paced single-world
    run against the unpaced one: identical digests.
17. `registers`: run the invariant and proof-obligation suites at reduced counts through the conformance
    harness. Assert eight invariants and five obligations pass and their planted violations are caught.
18. `docs-lint` (enabled with N16b-24): no real-time or hardware-in-the-loop claim in generated documentation.

**Logging.** NDJSON to `target/e2e-logs/kinesis_surface/<utc-timestamp>.ndjson` plus a transcript. Every line:
`ts`, `script`, `bead`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), command line,
exit code, wall time, the `evidence` block (claim, class, tier, determinism, identities, seed), measured values
with units and thresholds, digests where state is compared, and on failure the first differing value and the
artifact paths. Each refusal step logs the full refusal body (code, message, pointer, observed, required, unit,
affected claims, retry, ranked repairs). The `summary` line counts assertions and lists the refusal codes
exercised (eight expected at M2, ten from M3). No private-scene data.

## Acceptance criteria

- [ ] The refusal codes are produced by the real binary with the stated exit codes and ranked repairs: eight at
      M2 (212, 220 to 224, 721, 722) and all ten from M3, when 820 and 821 have a verb to raise them; the
      summary lists the codes exercised and the ones skipped with their reason.
- [ ] The run matrix behaves as specified; skipped device rows are logged with their reason.
- [ ] A numerical fault is never counted as a physical failure (step 10).
- [ ] The script passes on a machine with no GPU and fails when any one refusal's repair list is emptied
      (checked once by mutation of the registry).
- [ ] The log validates against the STD-E2E schema.
- [ ] Two consecutive runs give identical digests for every compared artifact.

## Test plan

### Unit tests

None of its own. Shell lint and dry-run per change; a small test asserts that the script's list of refusal
codes equals the chapter's ten (so a new refusal cannot be added without a step).

### End-to-end script and logging

As above. Commands: `frob capabilities`, `frob schema`, `frob sim estimate`, `frob sim run` with each option,
`frob eval promote`, a report verb that requires established evidence, the conformance harness runner.

### Known answers and negative controls

- KA-343: the dyadic event grid at L_max = 16 and ℓ₀ = 2 ms resolves 2 ms/2¹⁶ = 31 ns, so an approach at 3 m/s
  is located to within 0.1 µm (printed by step 9's refusal as the resolution reached).
- KA-349 (overflow flagged or refused), CX-150 (a solver that gave up is not a failed episode), CX-151 (the
  referee cannot adjudicate every scenario: 16 contacts standing, more in a crawl).
- Negative controls exercised: a build that truncates contacts silently; a build that scores a faulted world as
  a fall; a registry with a refusal's repairs removed.
- Determinism lanes: twice; across worker counts; debug and release in the nightly lane.

## Considerations

- OPEN-KIN-5 (L_max, E_max and the retry budget; defaults 16, 64 and 3; fail-closed default is refusal) changes
  the numbers printed by steps 9 and 10, not the behaviour asserted.
- Several fixtures here belong to other beads; the script only needs them to exist as named fixtures, which is
  why they are listed under `needs`.
- Exit code for the 72x refusals is 5 by the envelope's table, although they are capacity refusals and not
  missing capabilities; the script asserts the table as written.
