## Background

FrankenRobotics runs one robot model on three tiers: the slow, most trusted `referee`; `batch-cpu`, the CPU
reference of the batched step; and the GPU tiers. The **fidelity ledger** records how far a faster configuration
lands from a slower one on the standard battery (about 200 scenarios per robot class, frozen and addressed). Its
unit is the **pair row**: for one battery address, every ledger quantity on both tiers and their disagreement d.
N16b-02 defines the stratum key, the quantities, the pure comparison of two recorded episodes and the store.
N16bp1-01 freezes envelopes over complete strata. BD-212 measures the M2 numbers.

None of those says how a pair comes to exist. The comparator lives in `frob-dyn` (layer 3), and the layer rule
forbids a scheduler there: what is run on which tier is decided above the step, in the battery run of `frob-arena`
(the verb `eval.run`, "run a battery and record verdicts"). This bead is that piece: the hook in the battery run
that recognizes two runs of the same battery addresses on the two tiers of a pair and writes the pair rows.

A *world address* is `(run_seed, world, episode)`. Every random input of a world (scene draw, disturbances,
randomization, reset pose) is a function of its address and of nothing else, so two runs of one battery item with
one run seed, on two tiers, are the same scenario; no state is carried from one tier to the other. A *step plan*
is everything numerical that shaped a step (step size h, Newton iterations, warm start, capacities, profile, law,
kernel versions), hashed into `StepPlanId` (N16a-03).

Rejected: a separate verb `fidelity.measure` (the plan registers none, and a second way to run a battery would
split the battery's accounting); pairing by slot or by submission order (a slot is not an identity); teleporting
fast-tier states to the slow tier (that compares one step, not an episode's outcome; it is BD-204's tool for
examining one discordant pair afterwards). Tier Solid.

## Scope

In: the pairing hook of `eval.run` on a battery; the match rule; the routing of a named referee refusal to the
`strict` profile with the adjudicator recorded; the draining of the coefficient-lag accumulator into intrinsic
contributions; the `fidelity` block of the run's result; the completeness query the freeze uses; the step-plan
options of a battery run; cancellation behaviour; the script.
Out: quantities, d, the pair record's content, summaries and the store (N16b-02); envelopes, the freeze and the
verb `fidelity.ledger` (N16bp1-01, which depends on this bead); the battery and its identity (N38a-20, N24b-01);
`eval.run` itself and its verdict records (N24c-04); the `strict` profile (BD-161); the M2 measurement and the
gate (BD-212); the lag accumulator (N18a-29).

## Technical approach

1. **Tier pairs (DESIGN, a closed list in `frob-arena::fidelity`).** `(batch-cpu, referee)`, `(gpu-cuda,
   batch-cpu)`, `(gpu-metal, batch-cpu)`, ordered (fast, slow). A battery run on tier T takes part in every pair
   that names T.
2. **Match rule.** When an episode of a battery run commits, the hook looks up, at the store's committed frontier,
   an episode record on the partner tier with the same `BatteryId`, battery item, world address, `ModelId`,
   controller identity, scene and task identities. Tier, profile, law, kernel versions and `StepPlanId` are not
   part of the match: they are the components of the stratum the pair lands in. Either tier may run first.
3. **Write.** For a match the hook calls N16b-02's `fidelity::pair::compare(fast_record, slow_record)` and writes
   the `fidelity_pair` row through the evidence sink (idempotent on stratum key and address, so a repeated run adds
   nothing). A slow-tier episode that ended `numerical-fault` yields no pair and raises the stratum's `unpaired`
   count for that cause.
4. **Named referee refusal.** When the referee refuses an address by name (`FROB-REF-721`, the contact cap or
   FrankenSim's fixed-witness gate; a missing joint class; a kinematic loop), the slow run submits that address
   once more on `batch-cpu` with the `strict` profile (BD-161) inside the same job. The pair is then written with
   `adjudicator = batch-cpu:strict` and lands in the stratum of the profile pair (`lockstep`, `strict`); the
   refusal's code and limit are kept on the run record. A `strict` episode that ends `numerical-fault` is
   unpaired by cause. The referee is never retried with a changed physical parameter.
5. **Intrinsic contributions.** On a fast-tier `lockstep` run the hook drains the coefficient-lag accumulator
   (N18a-29) for each committed world address and writes its serialized histograms through the sink, keyed by
   address, coefficient law and contact mode, for N16b-02's intrinsic strata.
6. **Summaries and the result.** Stratum summaries are recomputed from pair rows when the job finalizes, never
   before, so a cancelled job publishes pair rows of committed episodes and no summary. The run's result gains
   `fidelity: { pairs_written, unpaired_by_cause, strata: [stratum key, n, complete], adjudicators: { referee,
   "batch-cpu:strict" }, intrinsic_addresses, tier_correction }` (VERBS-eval's block). `tier_correction: [{
   stratum, claim }]` has one element per tier-correction row that the run's committed pairs updated, as returned
   to the handler by the tier-correction store's import (N29b-07, which depends on this bead and attaches its
   import to this hook); `claim` is the identifier a caller passes to `evidence.trace`; the list is empty when no
   row was updated. `stratum_complete(stratum) -> bool` is true when every item of the stratum's battery has a
   pair row or an unpaired cause; N16bp1-01's `--freeze-envelopes` reads it.
7. **Step-plan options of a battery run (DESIGN).** `eval.run` forwards to the run's step plan the options that
   `sim.run` takes: `--profile` and `--law` (N16b-25), and the numerical-plan fields `--step <duration>`,
   `--newton-iterations <n>` and `--warm-start on|off` (the fields of N16a-03's `NumericalPlan`; the spellings are
   the ones `sim.run` uses). Defaults are the tier's. `--step` changes h only: every clock of the task keeps its
   period in seconds and the decimation is derived, by the normalization of N16c-43's `refine` helper (a task
   that states its control rate as "every k steps" keeps its period, not its k), so a battery run at h/2 is the
   same controller on a finer step. A changed option is a different `StepPlanId` and therefore a different
   stratum. This is how the default-step decision (N16a-16) and the created-energy bound (N16c-11)
   measure settings other than the default on the battery. `--profile strict` or `referee` on a GPU tier is
   `FROB-REF-222`, as on `sim.run`. The options are on `eval.run`'s row with this bead as their owner
   (VERBS-eval), in `sim.run`'s spellings (VERBS-sim). `eval.run` on the batched tiers is N24cp3-01's handler,
   which this bead extends.
8. **Layout.** `crates/frob-arena/src/fidelity/{pairing.rs, adjudicate.rs}`; the option forwarding in the
   `eval.run` handler.

Determinism: the match and the rows are class D0 given the two episode records; a pair row's bytes do not depend
on which tier ran first, on worker count or on slot.

## Acceptance criteria

- [ ] After `eval.run` of one battery with one run seed on `batch-cpu` and on `referee`, in either order, a pair row exists for every item whose two episodes ended with a non-numerical outcome, and the row bytes are identical for the two orders.
- [ ] An item the referee refuses with `FROB-REF-721` is adjudicated under `strict`; its pair has `adjudicator = batch-cpu:strict` and lies in the (`lockstep`, `strict`) stratum; a `numerical-fault` on the slow side yields no pair and one unpaired count by cause.
- [ ] Two runs that differ in run seed, in controller identity or in `BatteryId` are never paired.
- [ ] The result's `fidelity` block carries `tier_correction`, an empty list on a run whose pairs updated no
      tier-correction row.
- [ ] `--step 1ms` on the fast run puts its pairs in a stratum of their own (another `StepPlanId`); the default run's stratum is untouched.
- [ ] A run cancelled after half its items leaves pair rows for committed episodes only and no summary row; the same run completed later yields the same rows as an uninterrupted one.
- [ ] `stratum_complete` is false until every item has a pair or an unpaired cause, and true after.
- [ ] On a fixture with a speed-dependent friction law, the fast run writes intrinsic contributions for every committed address; without such a law it writes none.
- [ ] Negative controls caught: a hook that matches by slot index; a hook that writes summaries before the job finalizes.

## Test plan

### Unit tests

`crates/frob-arena/tests/fidelity_pairing.rs` (the real store in a temporary directory, the real `smoke` battery of
the quadruped on `batch-cpu` and `referee`; no mocks):
- `pairs_in_either_order`: fast then slow, and slow then fast, in two stores: equal pair-row digests for every item.
- `match_needs_same_address_and_identities`: a fast run of a scratch battery whose items are `smoke`'s at run seed 18 against the slow run of `smoke` (run seed 17) writes no pair; the same with another controller.
- `strict_adjudicates_named_refusal`: a fixture item with 24 simultaneous contacts (above the referee's cap of 21) is refused with `FROB-REF-721`, re-run under `strict`, and paired with `adjudicator = batch-cpu:strict`.
- `numerical_fault_is_unpaired`: a planted solver refusal on the slow side: no pair, `unpaired` raised by one for that cause.
- `step_plan_is_a_stratum`: `--step 1ms` and the default 2 ms give two strata with disjoint pair sets.
- `idempotent_repeat`: the slow run repeated under a new key adds no row.
- `cancel_writes_no_summary`; `stratum_complete_flag`.
- `intrinsic_contributions_drained`: a block-on-belt fixture with μ(v) = 0.3 + 0.2·v yields one histogram per committed address and (law, mode); the flat-friction twin yields none.
- `gpu_profile_refused_222`: `--profile strict --tier gpu-cuda` is refused before any world exists.
- Mutants `match_by_slot` and `summary_before_finalize`, each caught by the test named for it.

### End-to-end script and logging

`scripts/e2e/fidelity_pairing.sh` (plain shell, seed-explicit, idempotent in a scratch store, non-zero on
failure; the battery's items carry their own addresses, so no run seed is passed and the `BatteryId` from `bound`
is logged): (1) `frob eval run quad-a --battery smoke --class quadruped --tier batch-cpu --key fp-1 --json`,
asserting `fidelity.pairs_written = 0` and every stratum `complete: false`; (2) the same with `--tier
referee --key fp-2`, asserting one pair per item with a non-numerical outcome and the adjudicator counts; (3) in
a second scratch store the two runs in the reverse order, asserting equal pair-row digests (read with the
store-inspection helper of STD-E2E); (4) `--step 1ms --key fp-3` on the fast tier, asserting a second stratum;
(5) `--profile strict --tier gpu-cuda --key fp-4`, expecting `FROB-REF-222`, exit 3 (skipped with a logged reason
where no CUDA device is present); (6) the two mutants in a conformance build, each expected to fail its
assertion. Log: `target/e2e-logs/fidelity_pairing/<utc-timestamp>.ndjson` and a transcript; every line has `ts`,
`script`, `bead`, `step`, `event`; `cmd` lines the exact command line, exit code, wall time and the envelope's
evidence block (claim, class, tier, determinism, identities, seed); `metric` lines `pairs_written`,
`unpaired_by_cause`, `strata` with their completeness, adjudicator counts and the `StepPlanId` of each stratum;
digests of the pair rows compared; refusals with code and first repair; on failure the first item whose pair
differs with both row paths; a `summary` line with assertions passed and failed. The first battery read by
`scripts/e2e/fidelity_ledger.sh` (N16b-30) runs through this hook.

### Known answers and negative controls

- Known answer: the pairing of the `smoke` battery is a function of its manifest: one pair per item, the item
  list in manifest order.
- CX-150 (a world whose solver gave up can be scored as a failed episode): the unpaired test.
- Negative controls: the two mutants; a run paired across run seeds (must write nothing).
- Metamorphic: the order of the two runs, the worker count and a split of the fast run into two jobs change no
  pair row.
- Determinism lanes: twice on one machine; across worker counts; debug and release.

## Considerations

- Cost is the slow tier's: the hook adds one indexed lookup and one comparison per episode.
- An address refused by the referee is run twice on the slow side (the refused attempt and the `strict` run); the
  count of such addresses per class is the referee's coverage figure, which BD-213 reports.
- Pairing three-way (GPU, `batch-cpu`, referee) needs no extra rule: each run pairs with every partner present.
- Privacy: pair rows hold quantities and identities, never scene contents.
- Open question (owner: Kinesis lead): whether a battery run should refuse `--freeze-envelopes` when its step plan
  is not the class default. Fail-closed default: it freezes only the strata it completed, whatever their plan,
  and each envelope names its step-plan pair.
