## Background

A kill gate is a decision named in advance, with its trigger, its milestone, the measurement that decides it, its
fallback, and what changes downstream. Each is recorded as an architecture decision record when decided, by a
bead of the unit that owns the mechanism (the rule of the fallback ledger N40-23, followed by N40-24).

The plan gives the segment mode of the tier correction (`eval.promote --method segment`, built by N16b-08) a
pilot with a falsifier and a fallback and names no kill gate. The gate register carries one all the same:
**KILL-SEGMENT**, entered by N40-24 through an `introduce` amendment, so that the pilot `PILOT-KIN-01` (N16b-09)
has a stop rule to name and the pilot register (N38a-09) can accept its record. As registered:

| Field | Value |
|---|---|
| Trigger | The segment-mode pilot's falsifier holds (AUC lower bound at or below 0.5 in both reference classes) |
| Decided at | M3, mode `pilot-before-funding`: due when WP-50 asks to fund the segment mode, and at the latest at the M3 exit |
| Measurement (`reads`) | The record `PILOT-KIN-01` in `crates/frob-conformance/registry/pilots.toml`: per class (quadruped, humanoid) and pooled, the AUC of the episode predictor S with its 95% bootstrap interval, the counts of positives and negatives, the verdict |
| Fallback | No segment mode; whole-episode promotion only |
| Downstream if it fires | N16b-08 builds no segment mode; `--method segment` stays refused (`FROB-REF-724`, as without the feature); the status table names the fallback |

Without this bead the row has no decider: at the M3 exit the kill ledger (N40-30) would find no owner declaration
for KILL-SEGMENT (`owner-declaration-missing`), and N16b-08 would build or drop the segment mode on the pilot's
verdict alone with no decision record. Tier of the mechanism: Frontier [F].

## Scope

In: reading the pilot record; evaluating the trigger exactly as registered; the decision record
`docs/adr/ADR-KILL-SEGMENT-M3.md`; the row's `decision` entry and the owner declaration; the status table. Out:
running the pilot (N16b-09); building the segment mode (N16b-08); entering the row (N40-24).

## Technical approach

**Procedure.**
1. Read `PILOT-KIN-01` (N16b-09): per class the AUC, the interval's lower and upper bounds, the positives and
   negatives, the pooled figures, the verdict (`falsifier-holds` or `falsifier-rejected`), the reviewer, the
   receipt and the `protocol_blake3`, which must equal the registered hash (a result whose hash differs is not a
   result of this protocol and decides nothing). A missing result is not a pass: step 3 decides it.
2. Evaluate the trigger from the record alone: it holds when the lower bound is at or below 0.5 in the quadruped
   class **and** in the humanoid class. The pooled interval is reported and decides nothing. Check that the
   recorded verdict agrees with this evaluation; a disagreement stops the bead and is reported to the pilot's
   owner, since the verdict sets funding (N38a-09).
3. Name the outcome in N40-03's four: `fired` if the trigger holds; `not-fired` if the pilot has a result and
   the trigger fails (one class above 0.5 suffices); `not-reached` if WP-50 never asked to fund the segment mode
   and the pilot has no result by the M3 exit; `deferred` only through an ADR naming the later exit and its
   reason.
4. Write `docs/adr/ADR-KILL-SEGMENT-M3.md` with the fields N40-03 requires: the kill gate; the milestone; the
   trigger as registered and the `introduce` amendment that entered it; each input with its receipt hash beside
   the clause it decides (per class the lower bound against 0.5); the outcome; the fallback in force and the name
   the capability carries from now on ("tier correction: whole-episode promotion only"); the beads re-read, each
   with N40-03's status (N16b-08: "stands on the fallback" for its segment mode on `fired` or `not-reached`, its
   two other methods unchanged; released for the segment mode on `not-fired`); what changes downstream; the
   recording session, which neither ran the pilot nor implements N16b-08.
5. Registry: the `decision` entry of the KILL-SEGMENT row in `registries/gates.toml` (`outcome`, `adr`, `date`,
   `session`, `receipts`, N40-03's form; for this `pilot-before-funding` row `receipts` holds the `receipt` hash of
   the `[[pilot.result]]` read in step 1, committed at `receipts/pilots/<hash>.json` by N38a-09's rule, and is
   empty only on `not-reached`), and the owner declaration that N40-30 compares with the ledger (`[[gate]]`
   with `role = "owner"`, the ledger's current `trigger`, `fallback`, `decided`, `mode` and `reads` copied, and
   `decision` with each measured value citing its receipt) in `frob-opt`'s `contract.toml`.
6. If `fired` or `not-reached`: N16b-08 drops the segment mode from its scope, citing the ADR (its two other
   methods are untouched); the status table row reads "segment mode: fallback (KILL-SEGMENT)". If `not-fired`:
   the segment mode is released to N16b-08 behind `frontier-tier-variants`, with the rule that segment results
   never promote.

**Fail-closed default until decided.** No segment mode exists: `--method segment` is refused, and tier
corrections use whole episodes.

**Who decides.** The Kinesis lead prepares the record; a fresh-context session that did not run the pilot
reviews and records it, as exit reviews are.

## Acceptance criteria

- [ ] `docs/adr/ADR-KILL-SEGMENT-M3.md` exists with N40-03's required fields, cites `PILOT-KIN-01` by digest, and
  gives both classes' lower bounds beside 0.5; the outcome is one of N40-03's four.
- [ ] The KILL-SEGMENT row carries the `decision` entry, and `cargo test -p frob-conformance --test kill_ledger`
  (N40-30) passes for this gate (owner declaration present, trigger and fallback equal to the ledger's, outcome
  consistent with the measured values).
- [ ] The outcome is reproducible from the pilot record alone by a reader with no other context.
- [ ] Exactly one of: N16b-08's segment mode dropped citing the ADR, or released with the ADR cited.
- [ ] The record is in place before N16b-08 builds the segment mode and before the M3 exit review (BD-319).

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_gates.rs`:
- `kill_segment_record_complete`: trigger, inputs, outcome, date and session present; the ADR's path is
  `docs/adr/ADR-KILL-SEGMENT-M3.md`.
- `kill_segment_rule`: the pure rule on synthetic records: lower bounds 0.47 (quadruped) and 0.53 (humanoid) →
  `not-fired`; 0.47 and 0.50 → `fired` (at or below is inclusive); 0.51 and 0.52 → `not-fired`; no result at the
  M3 exit and no funding request → `not-reached`; every returned outcome is one of N40-03's four.
- `kill_segment_pooled_does_not_decide`: lower bounds 0.46 and 0.49 with a pooled lower bound of 0.55 → `fired`.
- `kill_segment_protocol_hash`: a result whose `protocol_blake3` differs from the registered hash → refused as
  input, naming the field.

### End-to-end script and logging
`scripts/e2e/kill_segment.sh` (header `# e2e: bead=N16bp4-01 milestone=M3 labels=kinesis,kill-gate
gates=KILL-SEGMENT seed=0 needs=cpu plants=not-fired-with-both-classes-at-chance`) re-derives the outcome from the
stored record (the identifier the row's `reads` names), compares it with the ADR and the gate row, and runs `cargo
test -p frob-conformance --test kill_ledger` (asserting that no failure names KILL-SEGMENT) and `cargo test -p
frob-conformance --test kill_gates -- kill_segment`. It exits non-zero on disagreement. It sources
`scripts/e2e/lib.sh` (STD-E2E) and writes `target/e2e-logs/kill_segment/<utc>.ndjson`; every line carries `ts`,
`script`, `bead`, `step`, `event`, the exact command line, exit code and wall time; it logs the record's digest,
per class the AUC and interval against 0.5, the derived and recorded outcomes, and a `summary` with assertions
passed and failed naming KILL-SEGMENT. It writes nothing to the registry; the recording session does.

### Known answers and negative controls
The rule's known answers are the trigger's two-class conjunction above. Negative control (plant
`not-fired-with-both-classes-at-chance`): a decision entry `not-fired` while the stored record shows both lower
bounds at or below 0.5 makes the script fail, and `kill_ledger` reports `outcome-contradicts-measurement`.

## Considerations

- The pilot has about ten positives per class before enrichment; the interval is wide by design. The rule reads
  the registered interval and never a recomputed or narrower one.
- A `not-fired` decision says the segment score predicts episode exceedance better than chance in one class; it
  does not make a segment result an episode-level estimate, and N16b-08's rule that segment results never promote
  stands.
- A fired gate costs a diagnostic, not a capability: whole-episode promotion answers every promotion question.
