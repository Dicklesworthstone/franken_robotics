## Background

GATE-KIN-04 is the known-answer gate of the transactional step: "the transactional rows pass on the referee and on `strict`: impact time within 10⁻⁹ s; tied sliders exact to 10⁻¹² N·s; zero observed uncommitted reads in 10⁵ injected faults; forced-retry digests equal; refinement statistics inside 3σ at 10⁶ draws; the redraw mutation caught" (TARGET thresholds; earliest M1 on the referee, M2 on `strict`). Three of those rows belong to the retry ladder and the refinement law (BD-083, N16c-01). This bead is their end-to-end script: it drives the real `frob` binary from the user's side, on real fixtures, and proves that what the unit tests assert inside `frob-dyn` is also what a caller observes through the verb surface, the telemetry and the evidence block.

Why a separate script. A gate is recorded from the outside: the harness calls the verbs as an agent would, writes a hash-named receipt, and a session that did not implement the work enters the row in `registries/gates.toml`. A row that passes only inside the crate that implements it is self-certification.

Terms. A *forced retry* is a transaction whose checks are made to fail for attempts below k by the fault-injection seam of the `chaos` build, so that it commits on attempt k. A *clean run with plan k* starts the ladder at rung k. A *digest* is the BLAKE3 hash of the committed snapshot (state, contact memory, clock phases and packet queues, energy accumulators).

## Scope

In: the script, its fixtures, its assertions and its log; the three rows (forced-retry digests, refinement statistics, the redraw mutation) on `--tier referee`; the `FROB-REF-221` and `FROB-REF-223` paths as seen by a caller. Out: the impact-time, tied-slider and uncommitted-read rows and the assembled gate record of all six referee rows (script `kin_transaction_referee.sh`, bead N16a-10, which calls this script for the three retry rows and reads its receipt); the `strict` repeat at M2 (BD-161 re-runs this script with `--tier batch-cpu --profile strict`; the script takes the tier and profile as parameters for that purpose).

## Technical approach

**Script.** `scripts/e2e/kin_retry_refinement.sh [--tier referee|batch-cpu] [--profile referee|strict] [--seed N] [--smoke]`. Plain shell, idempotent, seed-explicit (default seed 16083), exit non-zero on the first failed assertion after logging it. It sources the shared helper from STD-E2E. Every `frob sim run` it issues passes `--key kin-retry-<step>-<fixture>-<seed>[-k<k>]`: `sim.run` is a job-submitting run verb, and a call without an idempotency key is refused with `FROB-REF-805`, exit 3 (N32a-09).

**Sizes.** Gate size (the default, used for the record): steps 2 and 3 run for seeds $SEED to $SEED+5, 500 steps each, 200 chosen intervals per (seed, fixture, k), so 6 × 200 × 3 fixtures × 3 rungs = 10,800 forced intervals, above the 10⁴ of KA-341; step 5 uses 10⁶ parents. `--smoke` (the per-change run that N16a-10 calls): seed $SEED only (1,800 forced intervals) and 10⁴ parents, with the 3σ bounds widened by √100 = 10 (variance within 4.24 × 10⁻² relative, correlation within 3 × 10⁻², redraw P(positive) within 1.5 × 10⁻² of 0.75); a smoke receipt is labelled `smoke` and is never cited as the gate row.

**Fixtures** (all `synthetic`, built in, no private scene data; each is run as `--fixture <name>` of N24b-03's registry, the M1 form, because `--scene` reaches `sim.run` only at M2; `kin/tied-sliders` and `kin/unsolvable-island` are registered by BD-083 for its own script and reused here; `kin/ballistic-drop` wraps the `.fbot` file of `crates/frob-conformance/fixtures/kin/` that BD-082, N16a-07 and N16a-10 use, with its scene, and the last three are registered here):

| Fixture | Content | Used for |
|---|---|---|
| `kin/tied-sliders` (BD-083: `tied-sliders.fbot`, scene `wall`) | Two 1 kg sliders joined by a rigid tie approaching a wall at 1 m/s | A step with one located event and a coupled impulse; retried under plans 1 to 3 |
| `kin/ballistic-drop` (`ballistic-drop.fbot`, scene `plane`) | A sphere dropped from z₀ = 1 m on a plane, restitution 0.5; 500 steps of 2 ms end at 1 s, before the bounces accumulate at 1.3546 s, so no interval ends in `FROB-REF-220` | Several base intervals with one event each |
| `kin/quad-stand-noise` | The reference quadruped standing, with a Brownian base-force driver of intensity 5 N/√Hz registered as `BrownianDyadic`, and packet queues for its IMU | Noise under retry; restore-set members |
| `kin/noise-unregistered` | The same with the driver's law removed | `FROB-REF-223` |
| `kin/unsolvable-island` (BD-083) | The tied-slider island with a declared solver tolerance of 10⁻²⁰ N·s on impulses of order 1 N·s, below the `f64` resolution of 2.2 × 10⁻¹⁶ relative, so the solver-residual check fails under every rung (rung 2's tenfold tightening cannot help). Not inconsistent ties: a configuration with no solution is indeterminate and ends at once with `FROB-REF-224` without consuming attempts, which would test the wrong path | `FROB-REF-221` after exactly four attempts |

**Steps.**

1. `frob doctor --json`; record build identity, features (`chaos` required) and the fingerprint digest.
2. Clean reference: `frob sim run --fixture <f> --tier referee --profile referee --seed $SEED --seconds 1 --key kin-retry-ref-<f>-$SEED --json` for the first three fixtures (500 steps of 2 ms; `--steps` reaches `sim.run` only at M2); read the run summary with `frob telemetry summary <run> --json` (the run positional) and the per-interval digests and attempts with `frob telemetry query <run> --stream solver --channels attempt,state_digest,physical_params_digest --json` (the channels BD-083 records).
3. Forced retry, k = 1, 2, 3: two runs per (fixture, seed, k), each under its own key, with the chaos-build inputs BD-083 defines: the forced run, `--chaos-plan retry-k<k>.toml --key kin-retry-forced-<f>-<seed>-k<k>`, which fails the checks of the 200 chosen intervals for attempts below k; and its clean plan-k twin, `--chaos-plan retry-k<k>.toml --numerical-plan-floor <k> --key kin-retry-floor-<f>-<seed>-k<k>`, which starts the same intervals at rung k without forced failures. Two runs with the same seed, not two worlds of one run: two worlds have two addresses and so two noise paths. Assert: per-interval `state_digest` equal between the forced run and its twin; the committed `attempt` equals k on the chosen intervals and 0 elsewhere.
4. Noise under retry: on `quad-stand-noise`, read the per-interval noise increments from T1 telemetry for the clean run and for the k = 1 forced run. Assert: increments over each base interval are bit-equal; on retried intervals the two half-increments sum to the base increment.
5. Refinement statistics: `FROB_TEST_SEED=$SEED cargo test -p frob-conformance --test g1_known_answers -- GATE-KIN-04::refinement --nocapture` (10⁶ parents, ℓ = 2 ms). Parse its receipt: sample variance of each half within a relative 4.24 × 10⁻³ of ℓ/2; correlation within 3 × 10⁻³ of zero; sum identity. Log the three measured values with their bounds.
6. Controls: `FROB_TEST_SEED=$SEED cargo test -p frob-conformance --features gauntlet-mutations --test g1_known_answers -- GATE-KIN-04`. The control runner (N38b-04) rebuilds the tier target once per registered control of the three rows, each a `cfg(feature = "nc-<nnnn>")` mutant in `frob-dyn` built with `--features gauntlet-mutations,frob-dyn/nc-<nnnn>`: `redraw-on-reject` (CX-144), `restore-omit-warm-starts` and `restore-omit-packet-queues` (KA-341's two controls; the second registered by N16c-03 once BD-098 has landed). Assert each is `caught` for its stated reason: the redraw row **fails** with the measured P(positive) on the fair-sign fixture within 1.5 × 10⁻³ of 0.75; each restore-set mutant makes at least one forced-retry digest differ, and the log names the first differing interval and field. A mutant is never driven through the `frob` binary: chaos inputs are absent from conformance builds.
7. Release check: the release binary answers `--chaos-plan retry-k1.toml` with 802 and its build reports neither `chaos` nor an `nc-*` feature.
8. Refusals as a caller sees them: `noise-unregistered` returns `ok: false`, code `FROB-REF-223`, exit 3, repairs listing "register the law" then "move the draw to a sample instant"; `unsolvable-island` returns a world `Faulted` with `numerical-fault`, `FROB-REF-221`, zero published state from the failed interval, and the world listed under `excluded.numerical_fault` in the summary, absent from `fall`, `slip` and `collision`.
9. Repeatability: the k = 2 forced run of `tied-sliders` again with the same seed under a second key, `kin-retry-forced-tied-sliders-<seed>-k2-r` (`sim.replay` reaches the surface only at M2, BD-203); assert equal attempt sequences and per-interval digests.
10. Emit the `summary` line and the receipt path for the recording session; the receipt names its size (`gate` or `smoke`), the counts of forced intervals and parents, and the run ids of the forced runs, which N16a-10 reads for its INV-KIN-07 check of `physical_params_digest`.

**Logging.** NDJSON at `target/e2e-logs/kin_retry_refinement/<utc-timestamp>.ndjson` with a human transcript beside it. Every line: `ts`, `script`, `bead` ("N16c-02"), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and thresholds, digests where state is compared, and on failure the first differing value and the artifact paths (run identifier, snapshot, chaos plan) needed to reproduce. The final `summary` line gives assertions passed and failed and `gates: ["GATE-KIN-04"]`.

## Acceptance criteria

- [ ] `scripts/e2e/kin_retry_refinement.sh` exists, is executable, sources the STD-E2E helper and exits 0 on a correct build at seed 16083.
- [ ] Forced-retry digests equal the plan-k digests on 200 intervals × 3 fixtures × k ∈ {1, 2, 3} × 6 seeds (10,800 forced intervals at gate size; 1,800 under `--smoke`): zero mismatches (TARGET), each compared digest logged.
- [ ] The three refinement statistics are logged with thresholds and pass.
- [ ] The control runner reports each of the three controls (`redraw-on-reject`, `restore-omit-packet-queues`, `restore-omit-warm-starts`) `caught` for its stated reason, and the log names the first differing value.
- [ ] `FROB-REF-223` and `FROB-REF-221` appear in the log with their exit codes and repairs exactly as specified.
- [ ] Two consecutive runs produce identical assertion outcomes and identical digests (idempotence).
- [ ] The script leaves a hash-named receipt with the three rows' measured values, its size (`gate` or `smoke`) and the forced runs' identifiers; the script writes nothing to `registries/gates.toml` (N16a-10 reads the receipt and records GATE-KIN-04 with `record_gate`, convention 9).
- [ ] With `--tier batch-cpu --profile strict` the script runs unchanged once BD-161 lands (checked there).

## Test plan

### Unit tests

The script's own helpers are tested by `scripts/e2e/tests/kin_retry_refinement.bats` (or the harness's equivalent): digest comparison reports the first differing interval on a hand-made pair of telemetry files; the statistics parser rejects a receipt with a missing bound.

### End-to-end script and logging

This bead is the script. It asserts the ten steps above and logs as specified. Run time TARGET under 5 minutes on the CPU tier with `--smoke`, statistics row included; the gate-size run (six seeds, 10⁶ parents) is measured and logged, TARGET under 30 minutes.

### Known answers and negative controls

- KA-341 (forced retry digest equals the clean run with the same plan; exact). Controls: packet queues omitted; warm starts omitted.
- KA-340 (child variance ℓ/2, zero covariance, sum equals the parent; 3σ at 10⁶ draws). Control CX-144: redraw on rejection, P(positive) = ½ + ½·½ = ¾.
- CX-150: an exhausted world is `numerical-fault`, not a failed episode.
- Determinism lanes: the script is run twice on one machine, in debug and release, and with 1 and 24 workers; digests are compared against class D2.

## Considerations

- The `chaos` feature must never be present in a release build; step 1 fails the script if the release channel reports it.
- The mutant builds are produced only by the control runner, one `nc-<nnnn>` feature of `frob-dyn` per build under `gauntlet-mutations` (N38b-04); an `nc-*` feature without the umbrella, or under the release profile, does not compile, and no mutant build is published.
- If FrankenSim's contact step keeps state the airlock does not expose, step 3 fails with a digest mismatch; that is an upstream work item, and the gate row stays open until it lands.
- Logs contain fixture names, digests and statistics only.
