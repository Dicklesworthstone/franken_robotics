## Background

Row-class solve queues regroup worlds of a lockstep batch by the work their constraint solve needs (kernels: N16c-13; step plan: N16c-14). This bead is the user-visible part: how a caller turns the option on, what a planner tells them beforehand, what a receipt says afterwards, and what label a result carries while the option is unqualified.

Four surfaces are named for the mechanism:

1. the option `--solve-queues` of `sim.run` (run worlds under a profile, a law and per-world designs) and of `phylum.sweep` (run a population of designs in mixed batches);
2. `phylum.plan` (a read verb that never runs physics: buckets, padding overhead, bytes, the machine that fits a population) prints the speedup bound of the mechanism for the population in hand;
3. the placement receipt (`frob.placement/1`, one row per stage with requested and actual backend) records whether queues ran;
4. until GATE-KIN-08 has passed on a backend, a run with queues carries the label `experimental-execution` and is refused as promotion evidence ("execution option not yet qualified on this backend").

The reason for the label: the claim that queues change no digest is exactly what the gate tests. Until it has passed on a backend, a result produced with queues there has not earned the determinism class that pairing, promotion and attribution rely on, so it may be looked at but not cited.

## Scope

In: the option on both verbs with its schema; the `phylum.plan` bound; receipt and disclosure fields; the label and the refusal; `sim.estimate` printing whether queues would be used. Out: kernels and the step plan; the gate run (N16c-16); arm E of the mixed-batch head-to-head (run in N16c-16).

## Technical approach

**Option (DESIGN).** `--solve-queues <mode>` with `off` (default until the gate passes on the backend, and after a kill), `auto` (planner capacities from the previous chunk's histogram), or `q0,q1,q2` (explicit capacities, multiples of 32, each at most the world count). Input schema field `execution.solve_queues`; verb registry rows in `registries/verbs.toml` for `sim.run` and `phylum.sweep` gain the option, and the command-line and tool surfaces are generated from the registry. On a tier where the option has no meaning (`referee`, or `batch-cpu` under `strict`) the option is refused as an invalid argument for that profile (the profile-admission refusal, exit 3), not ignored.

**`phylum.plan` output (read; never runs physics).** For the population in hand it prints:

- f, the solve share of step time, from the most recent profile for this shape class and fingerprint (or `unmeasured`);
- ℓ, the active-and-live share of launched lane-time, from the live-fraction counters of the most recent run of this class (or `unmeasured`);
- h, the added relative overhead: (added launches × measured launch cost) ÷ (worlds × time per world-step);
- the bound 1/(1 − f + f·ℓ + h), with the statement of which inputs are measured and which are hypotheses, and the batch size at which the bound crosses 1.15 if any.

Known values the printout must reproduce from inputs: f = 0.47 with ℓ = 0.5 and h = 0.07 gives 1.20; ℓ = 0.25 and h = 0.15 gives 1.25; at 65,536 worlds with h = 0.009, ℓ = 0.25 gives 1.52. With any input unmeasured the bound is printed as a range over the documented hypothesis interval and marked HYPOTHESIS.

**Placement receipt.** The rows for stages 7 and 8 gain `execution: "masked" | "queued"`, `queue_capacities`, `generation`, `class_world_steps[3]`, `general_lane_world_steps`, `regroup_every`; the header gains `execution_qualified: true | false` for this backend (true only if the gate row for this backend is `pass` under the current fingerprint).

**Disclosure block.** Adds the live fraction per Newton iteration index and the active-contact class occupancy whenever a performance figure is quoted for a run, with queues on or off (these counters are kept even if the mechanism is killed).

**Label and refusal.** A result envelope of a queued run on an unqualified backend carries `labels: ["experimental-execution"]` in its evidence block. By the claim product the label propagates to anything derived from it (the weakest label among a result's inputs is the label of the result). Offering such a result to `eval.promote`, or citing it as established, is refused: message "execution option not yet qualified on this backend", pointer to the run and the backend, repairs ranked (1) re-run on the masked path, (2) qualify the backend (pass GATE-KIN-08 there). Interim code `FROB-REF-820` (label misuse) until the refusal registry assigns the dedicated code; exit 3; retry `after-change`.

**`sim.estimate`.** Reports for the class whether queues are qualified on the backend, the bound, and the expected general-lane share.

## Acceptance criteria

- [ ] `frob sim run --solve-queues auto --json` and `frob phylum sweep --solve-queues auto --json` run on `batch-cpu` and on each device with queues, and their receipts show `execution: "queued"` for stages 7 and 8 with capacities and generation.
- [ ] With the option absent, receipts show `masked` and results are bit-identical to those of a queued run of the same addresses.
- [ ] `frob phylum plan` prints f, ℓ, h and the bound, reproduces the three known values from their inputs, never runs physics (no world-step counter moves), and marks unmeasured inputs.
- [ ] A queued run on a backend without a passed GATE-KIN-08 carries `experimental-execution`; `frob eval promote` on it returns the refusal with both repairs; after the gate row is `pass` for that backend and fingerprint the label is absent.
- [ ] A changed fingerprint (driver or compiler change) returns the backend to unqualified until the gate is re-run.
- [ ] `--solve-queues` under `--profile strict` or `--tier referee` is refused.
- [ ] Schemas, examples and the refusal list for the option are in the verb registry; `frob schema sim.run` shows the field.

## Test plan

### Unit tests

- `solve_queues_option_parses`: `off`, `auto`, `64,32,32`; rejects `33,0,0` (not a multiple of 32) and capacities above the world count.
- `plan_bound_known_values`: the three values above; and with ℓ unmeasured, the printed range for ℓ ∈ [0.25, 0.5].
- `receipt_records_execution`.
- `label_propagates_by_claim_product`: a scorecard derived from a labelled run is labelled.
- `promotion_refuses_experimental_execution` (negative control: a build that drops the label on derived results must fail the test).
- `fingerprint_change_unqualifies_backend`.

### End-to-end script and logging

Covered by `scripts/e2e/kin_rowqueue_gate.sh` (N16c-16), which calls the three verbs from the user's side. For this bead it asserts: the option is accepted and recorded; `phylum plan` output fields and values; the label on an unqualified backend; the refusal's code, message, repairs and exit code. The log lines carry the command line, exit code, wall time, the evidence block including `labels`, the receipt's stage rows, and on failure the differing field.

### Known answers and negative controls

The bound's known values; the label-dropping mutant; a planted receipt that reports `masked` for a queued run must be caught by comparing the receipt with the step plan's launch count. Determinism: `phylum.plan` is class D0 given its inputs.

## Considerations

- A label that is easy to shed is worthless: qualification is per backend and per fingerprint, and is read from the gate registry, never from a flag on the command line.
- The interim use of `FROB-REF-820` blurs that code's meaning; a dedicated code is requested in the refusal registry bead.
- After KILL-ROWQUEUE the option is removed from the registry (a verb argument that does nothing is not kept), and `phylum.plan` stops printing the bound.
