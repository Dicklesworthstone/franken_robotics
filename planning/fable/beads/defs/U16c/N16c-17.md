## Background

A kill gate is a condition written in advance under which a mechanism is abandoned for a named fallback, so that the decision is made by a measurement and not by attachment to work already done. ✖ KILL-ROWQUEUE governs row-class solve queues: the Frontier mechanism that regroups lockstep worlds by the work their constraint solve needs (three row classes by active contact count, reassigned every step and regrouped on the `done` masks every second Newton iteration), exposed as `--solve-queues` on `sim.run` and `phylum.sweep`.

**Trigger** (any one):

1. the pilot's falsifier holds: the predicted bound 1/(1 − f + f·ℓ + h) is below 1.15 at every batch size the design campaigns use (f the solve's share of step time, ℓ the share of launched lane-time that is an active row of a live world, h the added relative overhead);
2. the measured 95% lower bound of the paired whole-step ratio against the masked path is below 1.15;
3. h ≥ f·(1 − ℓ) on the measured profile (the overhead eats the whole saving: the bound is then at most 1);
4. a digest mismatch against the masked path survives one repair cycle.

**Fallback.** The masked lockstep solve alone, with the live-fraction counters kept in the disclosure block.

**Milestone.** M2, the milestone of GATE-KIN-08 (a kill gate with no milestone of its own is decided at the milestone of the gate beside it). It is decided one step more urgently than its milestone's default because three mechanism beads exist only on its "keep" branch.

The decision has two points. Point A, after the pilot (N16c-12): if trigger 1 holds, the kill fires before any kernel is written; it is taken by N16cp3-01, on which the mechanism beads depend. Point B, after the gate run (N16c-16): triggers 2, 3 and 4; it is this bead. DESIGN (polishing round 3, the split already made for KILL-STEPADJOINT and KILL-INTERACT): this bead depends on the gate run, which exists only when point A released the mechanism, so a single bead for both points could never record a kill at the pilot. This bead exists only on point A's release branch; on `fired` it is closed `superseded` by N16cp3-01's ADR.

## Scope

In: point B: re-reading trigger 1 from point A's record and evaluating triggers 2 to 4 on recorded numbers; the decision entry and the ADR; closing or keeping the dependent beads; setting the default of the option. Out: producing the measurements (N16c-12, N16c-16); point A and the owner declaration (N16cp3-01); the decision-record schema (N40-03).

## Technical approach

**Inputs (all from records, none re-measured here).** The pilot record `PILOT-KIN-13` in `crates/frob-conformance/registry/pilots.toml` (or the number the register assigned: f, ℓ, h, predicted bounds per batch size, verdict) with point A's release in its `consequence` (N16cp3-01); the GATE-KIN-08 receipt per backend (digest mismatches, general-lane share, mixed-cohort ratio, paired lower bound with its n, mean and standard deviation, and f, ℓ, h measured on the same runs); the repair-cycle log if a digest mismatch occurred.

**Procedure.**

1. Trigger 1 (the pilot, decided at point A by N16cp3-01): re-read and cited, never re-evaluated on new numbers. A record without point A's release is refused as out of order.
2. Point B, per backend: evaluate triggers 2, 3, 4. "One repair cycle" is N40-03's: one bounded attempt to find and fix the cause of a mismatch, opened by a log line naming the failed receipt, with its own re-run of clause 1; a second mismatch fires the trigger.
3. Outcome. The KILL-ROWQUEUE row has no `scope_kind` in the register, so the decision is one entry: `fired` when any trigger fires on CUDA (the first backend), otherwise `not-fired`. Per backend the ADR states `kept`, or `not admitted` (Metal with unmeasured dispatch cost, or a backend where the gate's performance clause fails while CUDA passes): such a backend's GATE-KIN-08 part is not `pass`, so its qualification flag stays off, the `experimental-execution` label stays and the option reports "not qualified on this backend"; that is the gate's per-backend status, not a kill outcome.
4. Record: `docs/adr/ADR-KILL-ROWQUEUE-M2.md` with N40-03's required fields (the kill gate; the milestone; the trigger as registered and the amendments applied; each measured value with its receipt hash beside 1.15, f·(1 − ℓ) and 0; the outcome; the fallback in force and the name the capability carries; the beads re-read, N16c-13 to N16c-15, each "stands on the fallback" or "superseded by this ADR"; what changes downstream; the per-backend table; the recording session, which did not implement the mechanism), and the entry `decision = { outcome, adr = "docs/adr/ADR-KILL-ROWQUEUE-M2.md", date, session, receipts }` in the KILL-ROWQUEUE row of `registries/gates.toml`, `receipts` listing the GATE-KIN-08 receipt hashes (at least one, as `not-fired` requires). The draft identifier ADR-KIN-14 is withdrawn. Point A wrote no entry on its release branch, so this is the row's only entry and carries no `reading`.

**What changes downstream.**

- On `fired`: beads N16c-13, N16c-14 and N16c-15 close with reason `fallback` (if finished) or `superseded` (if not started), naming the masked solve; `--solve-queues auto` and explicit capacities answer `FROB-REF-724`, exit 5, the reason naming the ADR, on `sim.run`, `phylum.sweep` and `eval.run` (the schema keeps the option, as every input behind a kill gate does), and `off` stays accepted; `phylum.plan` stops printing the bound; the live-fraction counters and the active-contact class occupancy stay in the disclosure block; arm E is withdrawn from the head-to-head record with a note; the counterexample rows of the mechanism stay in the registry as a killed-idea record with the calculation.
- On `not-fired`: `--solve-queues auto` may become the default on the qualified backend only by a separate, explicit change of default recorded in the same ADR; the `experimental-execution` label no longer applies there; the interaction with design-family lanes is measured each alone and both together when lanes exist, and the simpler configuration that reaches the larger measured gain is kept.

## Test plan

### Unit tests

`crates/frob-conformance/tests/kill_rowqueue_point_b.rs`, on scratch copies of the registry files:

- `kill_rule_is_pure`: the outcome is a function of the two records. Cases: a pilot record without point A's release → refused as out of order (point A's own cases are N16cp3-01's tests); measured bound 1.14 → `fired`; (f, ℓ, h) = (0.47, 0.5, 0.24) → h ≥ f·(1 − ℓ) = 0.235 → kill; one mismatch repaired and clean on re-run → no trigger; mismatch on re-run → `fired`; CUDA clear and Metal's measured bound 1.10 → `not-fired`, Metal not admitted; all clear → `not-fired`.
- `fallback_refuses_option`: with the kill recorded, `--solve-queues auto` is 724 with exit 5 and the ADR named, and `off` is accepted.
- `entry_form`: the entry carries `outcome`, `adr`, `date`, `session` and `receipts`; `keep`, `kill` or `not-admitted` as an outcome fails the register's load check; a `not-fired` entry without a receipt fails it.

### End-to-end script and logging

`scripts/e2e/kin_rowqueue_decision.sh` (owned by this bead) reads the pilot record from the register and the gate receipts by digest (`frob artifact read <digest> --json`), runs `FROB_TEST_SEED=0 cargo test -p frob-conformance --test kill_rowqueue_point_b` and `cargo test -p frob-conformance --test kill_ledger` (N16cp3-01's owner declaration unchanged), evaluates the rule, prints the decision table and verifies the downstream state (`frob schema sim.run --json`; a fresh run, `frob sim run quad-a --tier batch-cpu --profile lockstep --seconds 1 --solve-queues auto --key krd-q-1 --json`, which on `fired` must be `e2e_expect_refusal FROB-REF-724 5` naming the ADR, and `--solve-queues off --key krd-m-1`, whose disclosure block carries the counters). NDJSON at `target/e2e-logs/kin_rowqueue_decision/<utc-timestamp>.ndjson` with a transcript, through the STD-E2E helper (every line: `ts`, `script`, `bead`, `step`, `event`, the exact command line, wall time): the inputs with their hashes, one `assert` line per trigger with measured value and threshold, the outcome per backend, the commands that verify the fallback or the kept state with exit codes, and a `summary` line with `gates: ["KILL-ROWQUEUE", "GATE-KIN-08"]`.

### Known answers and negative controls

The inequality of trigger 3 is the bound's break-even: 1/(1 − f + f·ℓ + h) ≤ 1 exactly when h ≥ f·(1 − ℓ). Negative control: a planted record with a digest mismatch and a passing speed ratio must produce `kill`, not `keep` (speed never buys back determinism).

## Considerations

- The expected outcome is uncertain by design: predicted bounds at 8,192 worlds straddle 1.15. Either outcome is a result.
- Sunk-cost guard: the rule is evaluated on records by a fresh session; no threshold is renegotiated after the numbers exist.
- If the measured gain is real only at batch sizes no campaign uses, trigger 1's wording (every batch size the campaigns use) decides: kill.
