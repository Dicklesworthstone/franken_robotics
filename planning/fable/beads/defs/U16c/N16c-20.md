## Background

The tile planner (N16c-19) says, for each interval between synchronization points, which islands of a multi-robot world provably cannot interact. This bead acts on that plan. Inside a certified tile each island is stepped **as its own single-robot world**, in a slot of an ordinary single-robot cohort (the same shape classes, kernels and launch graphs that exist for one robot, each robot in its own size bucket). Islands whose pair is not certified are stepped **together** for that tile as one coupled group. The multi-robot world itself exists as a ledger over these pieces: the *tile ledger*.

The mechanism is Moonshot [M], off the critical path, and exists for admission: without it a fleet scene needs a multi-robot bucket padded to N times the largest robot, or it must run entirely under the slow transactional profile. It is not a throughput lever (against a comparator that factors island by island the saving is the cross-island broad phase alone, below 1.05).

Two design rules carry the correctness.

1. **A robot's randomness does not depend on how it was stepped.** Its streams keep the multi-robot world's address, with the island as the perturbed entity. Rejected: giving a decoupled island a fresh single-world address, which would change its draws at every merge and split.
2. **Mode switches happen only at tile boundaries**, where all islands are synchronized, and each switch is recorded with the pair, the gap and the clause that ended certification. Rejected: merging mid-tile on a proximity trigger, which would make the step depend on a floating comparison inside an interval.

The reference against which the mechanism is judged steps the same islands in one world with island-wise solves on `batch-cpu`; every robot's digests must equal that reference.

## Scope

In: the stepping loop over tiles; slotting islands into single-robot cohorts that share the world's scene slot; the coupled-group path; state hand-over at boundaries; stream addressing; the tile ledger and the `--table tile-ledger` option of `telemetry.summary`; the `--decouple` option of `sim.run`, with its `reference` mode and the interaction witness that the gate audits with; the fallback path used after a kill; the fleet fixtures `fleet/rest-gap-0p10`, `fleet/head-on-3m`, `fleet/warehouse-16-sparse` and the `synthetic` `fleet/planted-touch`, which the gate (N16c-21) reuses; this bead's own script. Out: the planner; the gate script and its 10⁶ audited robot-steps; the handoff, message, lidar and thrown-prop fixtures (N16c-21); multi-robot mission semantics (the mission chapter).

## Technical approach

**Loop per multi-robot world.**

1. At a tile boundary t all islands are committed at t. Call the planner: islands, tile end t′, pair certificates, groups.
2. For each singleton group (an island certified against every other): write the island's state into a slot of the single-robot cohort for its shape class, with `scene_slot` = the multi-robot world's scene slot and `addr` = the multi-robot world's address plus the island identifier. Step it under the `lockstep` profile for the world-steps of [t, t′) (or under `strict` if the run asked for a transactional profile).
3. For each group of two or more islands: step the group together for [t, t′) as one coupled system, under the `strict` profile on `batch-cpu` with an island-wise solve (each island its own block; cross-island contact rows couple blocks only where a contact exists), or in a multi-robot shape class on a lockstep tier where one is admitted.
4. At t′ read every island back, commit the world at t′, append the tile's row to the ledger, and repeat. A switch between decoupled and coupled stepping therefore happens only at a boundary.

**State hand-over.** An island's state is its restore set restricted to its bodies: (q, v), actuator, thermal and battery states, contact memory against the static scene and against its own carried props, clock phases and packet queues of its own sensors and links, controller and estimator states, energy-ledger accumulators. Hand-over between the decoupled slot and the coupled group copies exactly this set; a digest of the island taken before and after a hand-over with no stepping in between is unchanged (tested).

**Random streams.** Stream key = (multi-robot `WorldAddr`, step, `stream_id`, island identifier as the perturbed entity). A gust that is a world field stays keyed by time and place, not by island. The single-robot cohort's own address plays no part.

**Profiles and the determinism claim.** Digest equality with the coupled reference is claimed on `batch-cpu` (class D2): the same kernels, the same per-island arithmetic, island-wise solves. On device tiers the decoupled islands are D2 per backend, and equality with a `batch-cpu` reference holds only where the device attains bit equality with the CPU reference (class D1); otherwise the comparison is a tolerance comparison with the decision-level test and the result says so.

**What the reference is, exactly (DESIGN).** The reference runs the same planner on the same committed states, so it makes the same group decisions tile by tile (the planner is a pure function of committed state, cards and clocks). It steps every singleton under the same profile the decoupled run used and every group the same way (under `strict` with an island-wise solve, or in the same multi-robot shape class), all inside one world on `batch-cpu` with island-wise solves and island-local arithmetic: under a transactional profile each island locates its own events and splits only its own sub-intervals, so an event in one island never splits another's interval. The only difference from the decoupled run is where a singleton is stepped (in a slot of a single-robot cohort, against inside the one world). Digest equality therefore tests that slotting, cohort co-tenancy and hand-over are invisible, which is INV-KIN-04 applied to islands. Whether a certified tile was truly free of interaction is tested separately, by a fine-step re-check of every certificate (N16c-21).

**Two profiles in one trajectory.** A robot whose island merges for some tiles is stepped under `lockstep` in its decoupled tiles and under `strict` in its coupled tiles (unless a multi-robot shape class is admitted, or the run asked for `strict` throughout). Its result therefore carries every `StepPlanId` it ran under, with the world-steps under each, in its evidence block; its determinism class and label are the weakest among them by the claim product, and a paired study that pairs it against a single-profile run is told so.

**Tile ledger** (a table of `telemetry.summary`, read with `frob telemetry summary <run> --table tile-ledger --json`; this bead adds the option `--table` to `telemetry.summary` with the one value `tile-ledger`, from M8, as the verb's row in VERBS-telemetry lists it, naming this bead the extender): one row per tile: start, end, ending clause (control tick, sensor instant, message arrival, possible contact), islands with shape class and slot, groups, per uncertified pair its d, radii, speeds, caps and γ, the mode of each group (`decoupled` or `coupled:<profile>`), and running totals: robot-tiles certified, the certified share of robot-time, merges and splits.

**Verb surface.** `frob sim run --scene <multi-robot scene> --decouple --key <k> --json` (`sim.run` is a run verb: every call carries an idempotency key, and a decoupled run and its reference carry distinct keys). `--decouple reference` runs the reference described above (same planner and profiles, every island inside one world with island-wise solves) and turns on the **interaction witness**: at every world-step, the cross-island broad and narrow phase, a ray cast of every exteroceptive sensor against the other islands at its sample instants, and the tracking of every message between islands, each inter-island event recorded with its exact time and tile in the run's telemetry and never applied as a response. It is a test mode: slower, labelled `reference` in the evidence block, and used by the gate (N16c-21) as the witness that no interaction happened inside a certified tile. Without `--decouple` a multi-robot scene runs as one coupled world under `strict` with island-wise solves and fixed decimation (this is also the fallback after KILL-INTERACT). The envelope reports the certified share, the count of merges, and for each robot its own digests and scorecard. A fleet scene whose coupled group exceeds the admitted capacity is refused under the capacity rule (`FROB-REF-721` on the referee; on a lockstep tier with the refuse policy the tier's overflow code, `FROB-REF-722` on `batch-cpu` and `FROB-REF-610` on the GPU tiers, which are not merged; repairs: a documented patch reduction, fewer robots in the group, raise the capacity).

**Fleet fixtures made here** (fleet scenes `frob.scene.fleet/1` of N25cx-01, stored under `fixtures/fleet/` beside N25cx-01's four and named as those are, `fleet/<name>`, which is the scene name `--scene` takes; the gate N16c-21 reuses them unchanged). Each is built on the pack, geometry and roster of one of N25cx-01's fixtures (`fleet/two-at-rest`, `fleet/head-on`, `fleet/sparse-warehouse-16`) with the policies, sensors and channel stated here, so it is its own document with its own `FleetSceneId`. `fleet/rest-gap-0p10`: two robots at rest, 0.10 m between bounding spheres, acceleration caps 5 m/s², both commanded toward each other at the cap from t = 0 (contact at √0.02 = 0.1414 s), controller at 50 Hz. `fleet/head-on-3m`: two robots approaching head-on at speed caps 1.5 m/s from a 3.0 m gap. `fleet/warehouse-16-sparse`: sixteen robots on the route graph of the warehouse archetype (`frob scene gen --family warehouse`, BD-225) with dwell points, one lidar each and one shared message channel. `fleet/planted-touch` (`synthetic`): two islands that touch inside a tile, with the planner's certificate forced on for the witness test.

**Faults and cancellation.** A robot `Faulted` or `Degraded` inside a tile is reported for that robot; the world continues for the others unless the caller's policy says otherwise. Cancellation is at a tile boundary: drain the tile, commit, finalize.

## Acceptance criteria

- [ ] `frob sim run --scene … --decouple --key … --json` runs a two-robot and a 16-robot scene; the tile ledger is readable through `frob telemetry summary <run> --table tile-ledger --json`, and the generated verb registry lists `--decouple` on `sim.run` and `--table` on `telemetry.summary` with this bead as implementer.
- [ ] Every robot's digests under `--decouple` equal those of the island-wise coupled reference on `batch-cpu`, tile by tile, on `fleet/rest-gap-0p10`, `fleet/head-on-3m` and `fleet/warehouse-16-sparse` over 10³ tiles. (The gate's second clause, on the two-carrier handoff fixture and over 10⁶ audited robot-steps, is measured in N16c-21.)
- [ ] A hand-over with no stepping leaves an island's digest unchanged; 10⁴ random merge and split sequences preserve digests against the always-coupled reference.
- [ ] A robot's random draws are identical whether its island is stepped apart or in a group (stream-level test).
- [ ] Mode switches occur only at tile boundaries and each is in the ledger with pair, gap and clause.
- [ ] Without `--decouple` the scene runs coupled under `strict`; a group above capacity is refused with the capacity code of its tier (721 on the referee, 722 on `batch-cpu`, 610 on a GPU tier) and the repairs.
- [ ] `scripts/e2e/sim_decouple.sh` exits 0.
- [ ] Negative controls caught: `fresh-address-on-split` (an island gets a new address when decoupled) changes digests; `mid-tile-merge` is detected by the ledger check.
- [ ] `--decouple reference` gives digests equal to `--decouple` on the two-robot fixture, and its witness records the contact of a planted pair that touches inside a tile (a `synthetic` scene with the planner's certificate forced on), at the right time and tile.

## Test plan

### Unit tests

- `handover_roundtrip_preserves_digest`.
- `decoupled_equals_coupled_reference_two_robots` (batch-cpu, 10³ tiles, robots far apart throughout).
- `merge_split_sequences_preserve_digests` (property, 10⁴ sequences driven by a scripted approach and retreat).
- `streams_keyed_by_world_and_island`: draws for island 2 are equal in decoupled and coupled modes; adding a third robot changes no draw of the first two.
- `switch_only_at_boundary`.
- `island_local_event_splitting`: under `strict`, an impact located inside island A's interval leaves island B's sub-interval list and digest unchanged against B stepped alone.
- `mixed_profile_evidence`: a robot that merges for 3 of 50 tiles carries both step-plan identities with world-step counts summing to the run's total, and the weaker determinism class.
- `capacity_refusal_on_oversized_group`.
- Mutants `fresh_address_on_split_caught`, `mid_tile_merge_caught`.

### End-to-end script and logging

`scripts/e2e/sim_decouple.sh` (owned by this bead; seed printed; idempotent; distinct keys per run). Steps:
1. `hand-cases`: `frob sim run --scene fleet/rest-gap-0p10 --decouple --tier batch-cpu --key sd-rest-<s> --json` and the same with `--decouple reference --key sd-rest-ref-<s>`; then `frob telemetry summary <run> --table tile-ledger --json`: the first 20 ms tile is certified with γ = 0.098 m and the planner then denies; on `fleet/head-on-3m`, 49 decoupled tiles, then a merge recorded with pair, gap and clause.
2. `digests`: `frob telemetry divergence <decoupled run> <reference run> --mode exact --json` on each hand-case fixture and on `fleet/warehouse-16-sparse` (16 robots, 10³ tiles): no divergence.
3. `witness`: `--decouple reference` on `fleet/planted-touch` (`synthetic`; the planner's certificate forced on): the witness records the contact at its time and tile.
4. `fallback-and-capacity`: the 16-robot scene without `--decouple` runs coupled under `strict`; a scene whose coupled group exceeds the admitted capacity is refused with the tier's code and the repairs (on `batch-cpu` 722 with the refuse policy, on the referee 721; on a GPU tier 610 when one is present, otherwise logged `not-run` with the reason).
5. `mutants`: `FROB_TEST_SEED=<s> cargo test -p frob-conformance --features gauntlet-mutations --test g5_determinism -- GATE-KIN-09`, under which the control runner builds `fresh-address-on-split` and `mid-tile-merge` (each a `cfg(feature = "nc-<nnnn>")` branch in `frob-dyn` with its `[[control]]` record, one control per build, N38b-04), which must fail the digest comparison of step 2 and the hand case of step 1 respectively and be reported `caught`.
It sources the STD-E2E helper and writes `target/e2e-logs/sim_decouple/<utc>.ndjson` with a transcript beside it. Every line carries `ts`, `script`, `bead` (`N16c-20`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code and wall time; per run the evidence block (tier, profile, determinism class, every `StepPlanId` with its world-steps, identities, seed), the certified share, merges and splits, ledger excerpts; per robot the digest comparison with the reference (on failure the first differing robot, tile and stage, with the run identifiers and fixture path to reproduce); refusal lines with the code and repairs; a `summary` with assertions passed and failed, naming GATE-KIN-09. The gate script of N16c-21 reruns these fixtures at scale; that check is N16c-21's.

### Known answers and negative controls

The two hand cases as scenarios (rest at 0.10 m: decoupled for 20 ms tiles until the planner denies; head-on from 3.0 m: 49 decoupled tiles then a merge; the plan's "fifty" counts the tile starting at 0.98 s, whose γ is exactly 0 and which the strict predicate does not certify). The two mutants. Metamorphic: relabeling robots permutes results; splitting one long certified stretch into more tiles (a shorter control period held fixed across arms) changes no digest. Determinism lanes: twice on one machine; 1 and 24 workers; debug and release; `batch-cpu` against D2; devices against their class.

## Considerations

- Sharing a scene slot across cohorts needs the scene to be resident for every shape class involved; memory is the scene once plus per-robot state, which is the point of the mechanism.
- A prop pushed by one robot toward another is its own island with acceleration cap g while free; it must merge before impact, which the planner guarantees and the gate checks.
- The value is bounded by the certified share; in a crowded doorway the world is coupled and runs at the transactional profile's speed.
- KILL-INTERACT fallback: this bead's coupled path alone, with `--decouple` removed.
