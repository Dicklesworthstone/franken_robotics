## Background

The lockstep solve factors, per world and per Newton iteration, the matrix H = A + JᵀGJ (A the mass-like matrix, J the constraint rows, G the row curvatures) by a batched **dense** Cholesky. For a robot, though, H has structure. A contact or limit row attached to one link has a Jacobian row that is nonzero only on that link's **ancestor** coordinates (the joints between the link and the root), so JᵀGJ has the same branch-induced sparsity as the mass matrix of a tree, and a factorization ordered leaves first has no fill. The Frontier mechanism "ancestor-sparse assembly" exploits that in four operations of every Newton iteration.

The sparsity is carried **as data**: ancestor lists and depths in the model table, fixed per shape class, so every lane of a bucket still runs one static launch graph and nothing needs a compile per design. This bead produces that data and the exact operation counts that follow from it. It is deliberately small and comes first, because the mechanism's pilot (the solve-stage ledger, N16c-36) needs both.

**Definitions.** n is the number of coordinates (degrees of freedom). The depth d_k of coordinate k is the number of its ancestors, itself included (the root's first coordinate has depth 1). The depth d_r of a row r is the depth of the last coordinate of the link the row is attached to.

**Operation counts per Newton iteration (multiply-adds).**

| Operation | Dense | Ancestor-sparse |
|---|---|---|
| One row's contribution to JᵀGJ | n·(n + 1)/2 | d_r·(d_r + 1)/2 |
| Factor of H, ordered leaves first, no fill | (n³ − n)/6 | Σ_k d_k·(d_k − 1)/2 |
| Two triangular solves | n² | Σ_k (2·d_k − 1) |
| One row's residual and line-search evaluation | n | d_r |

For a single chain d_k = k and every sparse count equals its dense count: there is nothing to exploit, and the route must report that instead of running.

## Scope

In: per-coordinate parent and depth; per-link ancestor coordinate lists in a packed form; the count functions; chain detection; the per-shape-class summary; padding rules. Out: instrumenting the solve (N16c-36); the sparse kernels (N16c-37); rows touching two limbs (detected at run time in N16c-37).

## Technical approach

**Coordinates, not links.** A joint with k active screw columns (1 for revolute, prismatic and helical; 2 for cylindrical and universal; 3 for spherical and planar; a floating base contributes 6) contributes k consecutive coordinates. Within one joint the coordinates are chained: the first has the joint's parent's last coordinate as parent, each next one has the previous as parent. Coordinates are numbered so that a parent's index is smaller than its child's (the tree's level order gives this).

**Data added to the packed model (DESIGN).**

```rust
pub struct AncestorTable {             // per model slot; read-only in a rollout
    pub coord_parent: Vec<u16>,        // parent coordinate, or NONE for a root coordinate
    pub coord_depth: Vec<u8>,          // d_k, ancestors including itself
    pub link_last_coord: Vec<u16>,     // last coordinate of each link's joint
    pub anc_start: Vec<u16>,           // per coordinate: start into `anc`
    pub anc: Vec<u16>,                 // ancestor coordinates, root first, self last (length Σ_k d_k)
    pub is_chain: bool,                // d_k = k for all k
}
```

`anc` has Σ_k d_k entries: 6·7/2 + 4·(7 + 8 + 9) = 21 + 96 = 117 for the reference quadruped and 21 + 2·57 + 24 + 2·91 = 341 for the humanoid (two bytes each). Padded coordinates (a model in a larger bucket) are appended after the real ones as root coordinates of depth 1 with no descendants, so they add identity rows and nothing else; counts are computed over real coordinates.

**Count functions (host, exact integers).** `factor_ops_dense(n) = (n³ − n)/6`; `factor_ops_sparse = Σ_k d_k·(d_k − 1)/2`; `solve_ops_dense(n) = n²`; `solve_ops_sparse = Σ_k (2·d_k − 1)`; `row_ops_dense(n) = n·(n + 1)/2`, `row_ops_sparse(d_r) = d_r·(d_r + 1)/2`; `row_eval_dense = n`, `row_eval_sparse = d_r`. A summary record per model: the four counts both ways, their ratios, the maximum depth, and `is_chain`.

**Known answers (hand-checkable).**

- Quadruped, n = 18: a six-coordinate base and four three-coordinate legs, so the depths are 1 to 6 once and 7, 8, 9 four times. Factor: 35 + 4·(21 + 28 + 36) = 375, against (18³ − 18)/6 = 969: a ratio of 2.58. A foot row has d_r = 9: 45 against 171, a ratio of 3.8. Solves: 36 + 4·(13 + 15 + 17) = 216 against 324. Row evaluation: 9 against 18.
- Humanoid, n = 35: a six-coordinate base, two six-coordinate legs (depths 7 to 12), a three-coordinate waist (7 to 9) and two seven-coordinate arms beyond the waist (10 to 16). Factor: 35 + 2·251 + 85 + 2·560 = 1,742, against (35³ − 35)/6 = 7,140: a ratio of 4.10. A foot row has d_r = 12: 78 against 630, a ratio of 8.1. Solves: 36 + 2·108 + 45 + 2·175 = 647 against 1,225. A hand row has d_r = 16: 136 against 630.
- A single chain (d_k = k) gives a ratio of exactly 1 in every row of the table; for n = 12: 286 and 286, 144 and 144.
- The three-coordinate case (a one-coordinate base with two one-coordinate limbs): depths (1, 2, 2); factor 2 against 4; solves 7 against 9.

**Where it is computed.** In the packed lowering of the compiled model (the step that already emits depth levels and path tables), memoized per model; the table's digest is part of the layout digest. The existing path table (each contact row touches only the degrees of freedom on its support path) and the ancestor table agree by construction: a row's support path is the ancestor list of its link's last coordinate; a test asserts it.

## Acceptance criteria

- [ ] `AncestorTable` is emitted for every compiled model and included in the packed layout; the layout digest is stable across platforms.
- [ ] The count functions return 375 and 969, 1,742 and 7,140, the row counts 45 and 171, 78 and 630, and the solve counts 216 and 324, 647 and 1,225 for the reference quadruped and humanoid, exactly.
- [ ] A chain model reports `is_chain = true` and ratio 1 in all four operations.
- [ ] For 10³ random trees, the sparse factor count equals the number of multiply-adds actually performed by a reference leaves-first factorization instrumented on the host (counted, not timed), and the dense count equals an instrumented dense Cholesky's.
- [ ] Padding to a larger bucket changes no count and no ancestor entry of a real coordinate.
- [ ] The path table and the ancestor table agree for every link of every archetype that exists.
- [ ] `frob design check --json` (or the model summary it prints) shows maximum depth and the factor ratio for the design.
- [ ] Negative control: a table built with depth excluding the coordinate itself (an off-by-one) fails the quadruped known answer (it would give 4·(15 + 21 + 28) + 20 = 276 instead of 375).

## Test plan

`cargo test -p frob-model ancestors::`

- `counts_quadruped`, `counts_humanoid`, `counts_chain`, `counts_three_coordinate`.

- `path_table_equals_ancestor_list`.

- Mutant `depth_off_by_one_caught` (276 ≠ 375).

### End-to-end script and logging

`scripts/e2e/kin_ancestor_tables.sh` runs `frob design check --json` on the reference quadruped, the reference humanoid, a 12-joint serial arm and the three-coordinate fixture, and compares the printed counts with the known answers. NDJSON at `target/e2e-logs/kin_ancestor_tables/<utc-timestamp>.ndjson` with a transcript: command, exit code, wall time, evidence block (class `Tested`, tier `static`, determinism exact, `ModelId`), each count with its expected value, and a `summary` line.

### Known answers and negative controls

The values above; counterexample row K12 of the Kinesis registry (a chain gains nothing). Negative control: the off-by-one depth. Determinism: the table and counts are class D0.

## Considerations

- The table costs a few hundred bytes per model slot; it rides in the model table, which is already read-only data per slot.
- Mechanisms above about 60 coordinates and padded buckets are where the original tree-operator route was aimed; these counts serve that route too, whatever the ledger decides for 18 to 35 coordinates.
- Fewer operations are not a faster step: on a device the step is bound by memory traffic and launch structure as much as by arithmetic. This bead makes no speed claim.
