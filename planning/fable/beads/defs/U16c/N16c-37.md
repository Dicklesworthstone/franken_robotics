## Background

Per Newton iteration the lockstep solve assembles H = A + JᵀGJ from the constraint rows, factors it, solves two triangular systems, and evaluates each row's residual and line-search terms. The dense path does each on all n coordinates. For a row attached to one link the Jacobian row is nonzero only on that link's ancestor coordinates, so JᵀGJ has the branch-induced sparsity of a tree's mass matrix and a factorization ordered leaves first has no fill. The **ancestor-sparse path** performs the four operations on ancestors only. Counts (multiply-adds), with d_k the depth of coordinate k and d_r the depth of row r's link: row contribution d_r·(d_r + 1)/2 against n·(n + 1)/2; factor Σ_k d_k·(d_k − 1)/2 against (n³ − n)/6; two solves Σ_k (2·d_k − 1) against n²; row evaluation d_r against n. For the reference quadruped the factor is 375 against 969 and for the humanoid 1,742 against 7,140.

The sparsity is carried as data (the ancestor table of N16c-35), so every lane of a bucket still runs one static launch graph. The price is gathers through an index and shorter, irregular inner loops; whether that is faster on a device is the gate's question, not this bead's. This bead builds the path; it starts only when the point-A decision of KILL-ANCESTOR (N16cp3-03) has released the mechanism after the ledger pilot (N16c-36) for the 18-to-35-coordinate range.

**The counterexample that bounds the route.** A row between two limbs (a hand on a thigh, one foot on the other) is nonzero on both ancestor chains, and its product couples the two limbs: the leaves-first order then has fill. Smallest case: a one-coordinate base with two one-coordinate limbs (n = 3; coordinates 1 base, 2 and 3 limbs with parent 1). Rows on single limbs give H the arrow pattern with a zero at the (limb 1, limb 2) entry; one row touching both limbs fills that entry, and a factor that skips it is wrong. Numbers: A = [[4, 1, 1], [1, 2, 0], [1, 0, 2]] plus one row J = (0, 1, 1) with curvature 1 gives H = [[4, 1, 1], [1, 3, 1], [1, 1, 3]]; for b = (0, 1, 0) the solution is (−1/14, 11/28, −3/28), while a factor that skips the (2, 3) entry returns (−1/10, 11/30, 1/30): the third component has the wrong sign. Such a world takes the **dense path for that step under a flag**, and the share of world-steps that do so is a reported number.

## Technical approach

**Storage.** H keeps its dense n × n block per world (no shape change); the sparse path reads and writes only entries (i, j) with j an ancestor of i. Entries outside the pattern are never read on the sparse path.

**1. Row assembly (`K-hess-anc`).** For each active row r with link ancestor list a₁ < a₂ < … < a_{d_r} (root first) and nonzero Jacobian entries J_r[a_i]: for i ≥ j add g_r·J_r[a_i]·J_r[a_j] to H[a_i][a_j]: d_r·(d_r + 1)/2 multiply-adds. A row is *single-limb* when its nonzero coordinates form one ancestor chain. Rows are accumulated per world in row-index order by a fixed tree over rows per entry, so the sum's grouping does not depend on capacity (padding rows contribute −0.0).

**2. Leaves-first factorization (`K-chol-anc`).** With coordinates numbered parents before children and parent(·) from the ancestor table (0 for none), compute H = LᵀL in place, eliminating from the highest index down:

```text
for k = n down to 1:
    H[k][k] ← sqrt(H[k][k])
    i ← parent(k)
    while i ≠ 0:  H[k][i] ← H[k][i] / H[k][k];  i ← parent(i)
    i ← parent(k)
    while i ≠ 0:
        j ← i
        while j ≠ 0:  H[i][j] ← H[i][j] − H[k][i]·H[k][j];  j ← parent(j)
        i ← parent(i)
```

Coordinate k performs d_k − 1 divisions and (d_k − 1)·d_k/2 multiply-adds, which sums to Σ_k d_k·(d_k − 1)/2. No entry outside the ancestor pattern is created (no fill) provided every row is single-limb. Diagonal scaling is applied first in the same scaled variables as on the dense path; a non-positive pivot marks the world `Faulted` exactly as on the dense path.

**3. Solves (`K-solve-anc`).** Lᵀ·y = b: for k = n down to 1: y[k] ← b[k]/H[k][k], then for each proper ancestor i of k: b[i] ← b[i] − H[k][i]·y[k]. L·x = y: for k = 1 to n: x[k] ← (y[k] − Σ over proper ancestors i of k of H[k][i]·x[i])/H[k][k]. Together 2·Σ_k (d_k − 1) multiply-adds and 2n divisions by the diagonal.

**Counting convention (the plan's table, made exact).** Factor, row contribution and row evaluation are counted in multiply-adds. The two triangular solves are counted as their multiply-adds plus one diagonal operation per coordinate, which is the convention under which the table's dense figure is n² and a chain's sparse figure equals it: Σ_k (2·d_k − 1) = 2·Σ_k (d_k − 1) + n. The instrument reports multiply-adds and divisions separately and the table's figure is formed from them: quadruped 198 + 18 = 216 against 306 + 18 = 324; humanoid 612 + 35 = 647 against 1,190 + 35 = 1,225. (With the LᵀL factor the substitutions divide twice per coordinate; the second division is not counted, by this convention, so that the sparse and dense figures stay comparable.)

**4. Row evaluation (`K-row-eval-anc`).** J_r·v, the residual and the line-search terms of row r use its d_r ancestor entries only.

**5. Two-limb detection and the dense fallback.** At row construction each row carries a one-bit flag `two_limb` set when its nonzero coordinates are not one ancestor chain (self-contact between limbs; a closure row between branches). Per world and per step, `any_two_limb` is the OR over active rows (an integer reduction). A world with the bit set runs that step's solve on the dense kernels; others run the sparse kernels. Both kernel sets are launched every step over all worlds under the mask (a static launch graph; the masked-out set returns at once per world). The world's step is flagged `solve-path: dense-fallback` in telemetry and the share of such world-steps is counted.

**6. Padding.** Padded coordinates are root coordinates of depth 1 with identity rows and zero right-hand side; they contribute a square root of 1 and nothing else, and they follow every real coordinate in index order, so the real part of the factor is unchanged (the padded-Cholesky leading-block property carries over: a leaves-first factor eliminates padded coordinates first and they touch no real entry).

**Arithmetic order and determinism.** The sparse path performs a subset of the dense path's operations in a different order (the dense kernel eliminates columns in ascending order; the sparse one eliminates leaves first). Each path is class D2 on its own (bit-identical run to run, across co-tenants, slots and capacities). Across the two paths results agree to tolerance only, never bit for bit; the comparison between them is the decision-level equivalence test. That is why the path is part of the `StepPlanId` (N16c-38).

**CPU reference.** `batch-cpu` implements the same four kernels in Rust on the tile program and is the bit-level reference for the devices' sparse path.

## Acceptance criteria

- [ ] The four kernels exist on `batch-cpu`, CUDA and Metal from one dialect source with manifests; lint and dimension checks pass.
- [ ] In `f64` on `batch-cpu`, for 10⁴ random battery states per reference robot with single-limb rows only: the sparse solve's solution equals the dense solve's to 10⁻¹² relative, and LᵀL reconstructs H on the ancestor pattern to 10⁻¹³ relative.
- [ ] Instrumented counts equal the count functions under the counting convention above: 375 (quadruped) and 1,742 (humanoid) multiply-adds per factorization; per solve pair 198 and 612 multiply-adds with 36 and 70 divisions, that is 216 and 647 in the table's convention (dense: 306 and 1,190 multiply-adds, 324 and 1,225); 45 and 78 per foot row; a chain model runs with counts equal to the dense path's and the path reports "nothing to exploit".
- [ ] The three-coordinate fill case takes the dense path and is flagged; with the fallback disabled (mutant `skip-fill`) the solution for b = (0, 1, 0) is (−1/10, 11/30, 1/30) instead of (−1/14, 11/28, −3/28) and the test fails.
- [ ] The sparse path's digests are independent of co-tenants, slot and capacity (1,000 episodes at capacities 32, 64 and 128 with random co-tenancies, per backend).
- [ ] The share of world-steps on the dense fallback is counted and reported per run.
- [ ] A non-positive pivot faults the world on the sparse path in the same cases as on the dense path (same world, same step, on a fixture with a deliberately singular A).
- [ ] Negative controls: `skip-fill`; `ascending-elimination` (eliminating roots first on the sparse pattern, which creates fill that is then dropped) fails the reconstruction test. Each is a `cfg(feature = "nc-<nnnn>")` branch in `frob-kernels` with a `[[control]]` record (BD-025's schema), built one per build by the control runner with `--features gauntlet-mutations,frob-kernels/nc-<nnnn>` (N38b-04), and the runner reports both `caught`.
- [ ] `scripts/e2e/ancestor_solve.sh` exits 0.

## Considerations

- A humanoid with frequent self-contact (hands on thighs, crossed feet) spends its steps on the dense fallback; above 20% of battery world-steps the kill gate fires.
- Launching both kernel sets under masks costs launches; the alternative (regrouping worlds by path) is the row-class queue idea and is not combined here.
- The path does not need the path-table Jacobian to be the default, but benefits from it: rows already stored on their support path avoid a gather.
- Fallback after KILL-ANCESTOR: the dense path for 18 to about 60 coordinates; the tree route only where the tree-operator kill gate leaves it (mechanisms above 60 coordinates and padded buckets).
