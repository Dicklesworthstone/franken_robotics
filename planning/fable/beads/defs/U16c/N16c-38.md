## Background

The ancestor-sparse solve path (N16c-37) performs the constraint solve's assembly, factorization, triangular solves and row evaluations on ancestor coordinates only. It computes the same mathematical quantities as the dense path but **orders its arithmetic differently**, so the two paths do not produce the same bits. Each path alone is deterministic (class D2: the same bits run to run, across co-tenants, slots and capacities on one backend); across paths, results agree only inside a tolerance and at the level of decisions.

That has a consequence for evidence. Paired comparison, counterfactual forks, memoized episodes and replay all rest on bit-level reproducibility of a world. If one arm of a study ran on the dense path and the other on the ancestor path, the difference between the arms would contain a solver-path difference that grows through contact like any other perturbation, and the pairing would be an illusion. So the design fixes three things, which this bead implements:

1. the verb option `sim.run --solve-path {dense, ancestor}` selects the path;
2. the `StepPlanId` includes the path (a physics-relevant change of arithmetic is an identity change);
3. a study never mixes them: a request that would is refused with the two step-plan identities.

The contrast with row-class solve queues is deliberate: queues change which lanes do arithmetic and no bits, so they stay outside the `StepPlanId`; the solve path changes bits, so it is inside.

## Scope

In: the option and schema; the path in the step-plan identity; default selection; the study-mixing refusal; receipts and disclosure; `sim.estimate`; this bead's script. Out: the kernels (N16c-37); the gate measurement (N16c-39).

## Technical approach

**Option (DESIGN).** `--solve-path dense|ancestor` on `sim.run` (and inherited, as one value for every world of the request, by verbs that run worlds through it: `eval.run`, by which the standard battery is run, `phylum.sweep`, `train.start`, `eval.compare`; the study manifest read by `study.plan` gains an optional per-arm field `solve_path` for the case where a caller wants to state the path arm by arm). Default: `dense` until GATE-KIN-12 has passed and the kill decision (N16c-40) records `not-fired`; after that the default per shape class is chosen by the planner (`ancestor` where the model is not a chain and its factor ratio from the ancestor table is at least 1.5; `dense` otherwise), and the chosen value is always written into the step plan, never implicit. On a chain model `--solve-path ancestor` is accepted, runs with operation counts equal to the dense path's, and the envelope carries the note "nothing to exploit: chain" so that nobody mistakes it for a speed setting.

**Identity.** The `StepPlanId` is the content hash of the shape class, kernel versions, contact law, step profile, h, world-steps per control interval, Newton iterations and tolerance; this bead adds `solve_path`. Two runs that differ only in the path have different `StepPlanId`s, different memo keys and different fidelity-ledger strata. The per-world, per-step dense fallback inside the ancestor path (a world whose step has a two-limb row) does not change the identity: it is part of what "ancestor path" means, it is a deterministic function of the world's own state, and it is flagged per step.

**Inside a study the default is uniform (DESIGN: a default that leads straight into a refusal is a trap for the user).** After a `not-fired` decision the per-shape-class rule above would give a serial arm `dense` and a quadruped `ancestor`, so a plain paired comparison of the two would mix paths by default. When a request pairs or pools arms and states no path, the planner therefore gives every arm one path: `ancestor` only if every arm's shape class would get `ancestor` by the rule above, otherwise `dense`; the plan output states the path with the reason `study-uniform`. The refusal below is reached only when paths are stated per arm, or when existing runs, snapshots or memo entries made under different paths are combined.

**The mixing refusal.** At admission of any request that pairs or pools worlds as one study (a paired comparison, a promotion that re-evaluates addresses on another tier with the same nominal plan, a memo reuse, a fork from a snapshot, a step-refinement study), the planner compares the `solve_path` of every arm. If they differ the request is refused: message "study mixes solve paths", `observed` the two step-plan identities and their paths, `pointer` the arms, ranked repairs (1) re-run one arm on the other's path, (2) declare the comparison unpaired (it then runs as two independent samples and says so). Exit 3; retry `after-change`. It is N16-REF's row `solve-path-mixed-study` (block `5xx`, evaluation protocol), numbered by N35-33's first-round run at M0, before this bead lands, and raised behind one named constant with this message, never as the paired-statistics code `FROB-REF-561`.

What is *not* refused: a cross-tier promotion in which the tiers legitimately differ in step plan (fast tier against referee) is already a tolerance comparison under the fidelity ledger; the solve path is one more recorded difference of the tier pair, and the ledger stratum is keyed by it.

**Receipts and disclosure.** The placement receipt's solve-stage rows carry `solve_path`, the dense-fallback world-step count and share. The disclosure block of any performance figure names the path. `sim.estimate` prints, per class, the factor and row operation ratios from the ancestor table, the expected dense-fallback share from the last battery run, and which path the planner would choose.

**Decision-level equivalence between the paths.** The gate requires the two paths to pass the decision-level equivalence test on the standard battery: on a frozen ensemble of addresses with frozen policies, compare state error at checkpoints, impulse and work residuals, event times and task decisions; the pair is decision-equivalent when the one-sided 95% upper bound on the rate of discordant decisions is at most 1%, the net one-sided rate at most 0.5%, continuous outcomes are equivalent by two one-sided tests inside the fidelity-ledger margins, and the top of the design ranking agrees. This bead provides the invocation by which that test is run on the two paths: `frob spark check --decisions --pair solve-path:dense,ancestor --backend <backend> --workload <Q|H> --battery standard --key <k> --json`. `--decisions`, `--workload` and the verdict record are those of the decision-level test's own bead (BD-177), whose pairs are two placements `<A>:<B>`. Two things are added here (DESIGN), and the registry row of `spark.check` lists both with this bead as extender: the pair form `solve-path:dense,ancestor`, which names two step plans on the one backend given by `--backend` that differ only in `solve_path`, entered in `registries/placement_pairs.toml` so that its verdict has a row; and `--battery standard`, which takes as the frozen ensemble the standard battery's addresses for the workload with its frozen baseline controllers (at least 4,096 addresses per workload, content-hashed and never edited, as BD-177's own ensembles are), because the gate states the test "on the standard battery". Exit 0 on `equivalent`, exit 2 with the discordant worlds listed on `not-equivalent`, as BD-177 defines.

## Acceptance criteria

- [ ] `frob sim run quad-a --seconds 1 --solve-path ancestor --key spa-anc-<tier> --json` and the same with `--solve-path dense --key spa-dense-<tier>` run on `batch-cpu` and each device; the evidence block shows two different `StepPlanId`s that differ only in the path field.
- [ ] A paired comparison whose arms differ in solve path (`frob study plan` on a manifest whose two arms state `solve_path` `dense` and `ancestor`) is refused with both step-plan identities, both repairs and exit 3; the same comparison with matching paths is admitted.
- [ ] A paired study of a chain model against the quadruped that states no path is admitted with one path for both arms (`dense`) and the reason `study-uniform` in the plan; it is not refused.
- [ ] Memoized episodes are not reused across paths (a run on one path never returns a cached result of the other).
- [ ] Each path alone is bit-reproducible: two runs give identical digests; across paths digests differ (asserted, so that a silent aliasing of the two paths is caught).
- [ ] A chain model under `--solve-path ancestor` carries the "nothing to exploit" note.
- [ ] Receipts, the disclosure block and `sim.estimate` show the path and the dense-fallback share.
- [ ] `frob spark check --decisions --pair solve-path:dense,ancestor --backend batch-cpu --workload Q --battery standard --key <k> --json` runs the decision-level equivalence test and reports discordant decisions with margins; `frob eval run <design> --battery standard --solve-path ancestor --key <k> --json` runs the battery on the stated path and its receipt shows it.
- [ ] The verb registry row, schema and examples document the option and the refusal.
- [ ] `scripts/e2e/sim_solve_path.sh` exits 0.

### Unit tests

- `stepplan_id_includes_solve_path`.
- `mixing_refused_with_both_identities`; `matching_paths_admitted`; `unpaired_declaration_admitted`.
- `memo_key_includes_solve_path`.
- `paths_differ_in_bits_but_each_is_reproducible`.
- `chain_note_present`.
- `planner_default_rule`: factor ratio 2.58 (quadruped) → `ancestor`; ratio 1 (chain) → `dense`.
- `study_default_is_uniform`: arms (quadruped, humanoid) with no path stated → both `ancestor`; arms (chain, quadruped) → both `dense` with reason `study-uniform`; neither is refused.
- Negative control: a build in which the path is omitted from the `StepPlanId` must fail `mixing_refused…` and `memo_key…`. The mutant is a `cfg(feature = "nc-<nnnn>")` branch in `frob-dyn` with a `[[control]]` record (BD-025's schema), built by the control runner with `--features gauntlet-mutations,frob-dyn/nc-<nnnn>` (N38b-04); the umbrella feature alone plants nothing.

The planner rule on the known ratios (2.58, 4.10, 1); the identity mutant; the decision-level arithmetic (with zero discordant worlds the 95% bound is about 3/n, so at least 300 worlds are needed to show 1%). Determinism lanes per path: twice on one machine; 1 and 24 workers; debug and release; each device against D2.

## Considerations

- The design text says the two paths "agree inside determinism class D2 and not bit for bit". Read literally that is contradictory (D2 is bitwise). It is implemented as: each path is D2 by itself; the two agree with each other only at class D3 (tolerance plus decisions). The ambiguity is recorded for the plan's next revision.
- Changing a default path after results exist would silently split a campaign; the default is fixed per shape class at the kill decision and changes only with a new step-plan generation recorded in the ledger.
- Fallback after KILL-ANCESTOR at point B (N16c-40): the value `ancestor` is no longer admitted for 18 to about 60 coordinates and the path field takes the single value `dense` there; the identity field stays so that old results remain readable. A request for `ancestor` in that range is refused at admission as N16-REF's row `ancestor-path-after-kill`, held in the `8xx` block and therefore raised as `FROB-REF-802` with `detail: "ancestor-path-after-kill"`, the coordinate count and the admitted range in `observed`, behind one named constant, exit 3, repair `--solve-path dense` or omit the option; never silently run dense.
