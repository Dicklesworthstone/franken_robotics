## Background

The batched step (tiers `batch-cpu` and `gpu-*`) runs ten stages as kernels over all worlds with fixed buffer
shapes. A **shape class** is the set of capacities one static step plan is built for; its hash, the
`ShapeClassId`, is part of the `StepPlanId` that every result carries. A **cohort** is a set of model slots and
worlds running under one step plan. To put different robots in one batch (ADR-PHYLUM-02: morphology is table data
inside padded capacities; no interpreter and no compile per design), each design must be assigned to a shape class
whose capacities it fits. Kernels read capacities from the step-plan header, so a new class needs new buffers and
a new static launch graph but no kernel compile; that is why the fit, not a compiler, decides how fast a new
design reaches its first step.

Three levels of variation exist in a batch: P-A, parameter values on one tree (one structure table, a parameter
table per model slot, no masks and no padding; Solid); P-B, different trees inside padded capacities with masks
(Frontier); P-C, P-B plus family lanes (Frontier). Fitting also decides the level: a cohort whose members all share
one tree takes the unmasked P-A path.

The alternative rejected is fitting by a single scalar (degrees of freedom only). Homogeneity by morphology is not
homogeneity by work: a tracked base with 12 degrees of freedom needs 64 contacts while a 12-joint quadruped with
18 needs 32, so a fit on degrees of freedom alone either overflows contact capacity or pads every small robot to
the track's rows. The requirement is therefore a vector and every component must fit.

## Technical approach

Types (DESIGN: fixes intent and layout, not signatures). `ShapeClass` is the union of the two printed sketches
under one set of names; it is restated here because the fit is written against it, and it is defined in
`frob-model` (BD-148, which governs where the two differ), because the kernels, the device arena and this crate
all read it and it sits in the lowest crate that produces it. `Requirement` and `FitState` are this crate's:

```rust
pub struct ShapeClass {           // frob_model::packed::ShapeClass, re-exported (BD-148)
    pub n_v: u16,                 // degree-of-freedom capacity: the bucket size (default set 12, 18, 24, 36, 48, 64)
    pub links: u16,               // link capacity
    pub depth: u8,                // maximum tree depth
    pub samples: u16,             // collision samples tested per world
    pub contacts: u16,            // C: active-contact capacity
    pub rows: u16,                // R: constraint-row capacity
    pub actuators: u16,
    pub sensor_layout: SensorLayoutId,
    pub policy_layout: LayoutId,
    pub contact_law: LawId,
    pub precision: PrecisionProfile,   // default | stiff
    pub iterations: u8,           // lockstep Newton iteration count, a class constant
    pub single_structure: bool,   // P-A: one tree, unmasked path
}
pub struct Requirement { n_v: u16, links: u16, depth: u8, samples: u16, contacts: u16, rows: u16, actuators: u16,
                         sensor_layout: SensorLayoutId, structure: StructureHash }
pub enum FitState { Resident(CohortId), Known, New }     // warm, cool, cold-or-cool admission paths
```

Requirement of one lowered model (`RobotModel` after packed lowering). Items 1 to 3 and the sensor layout are
read from the model's `ShapeSummary`, which the model compiler computed (N14a-12); they are stated here so that
the meaning of each field is on the page, and they are not counted a second time:

1. `n_v` = number of velocity coordinates, floating base included (a 12-joint quadruped has 18; a 29-joint
   humanoid 35; an 18-joint hexapod 24; a four-wheel base 10). From `ShapeSummary.n_v`.
2. `links` = bodies of the lowered model after the model compiler's fixed-joint fold (a child on a fixed joint
   has its pseudo-inertia summed into its parent and its named attachments re-parented, so a welded foot is not a
   link); `depth` = longest root-to-leaf path in links after the fold; `actuators` = actuated joints. From the
   summary's fields of the same names, never re-derived here. DESIGN: the count after the fold governs, because a
   class's link capacity bounds the rows of the model table, which holds folded links only: the reference
   quadruped has 1 + 4 × 3 = 13 links and depth 3 (torso at depth 0), the n_b = 13 of the byte model (N17a-07).
   N14a-12's worked `quad-a` prints 17 links and depth 4, counting the fixed foot attachment as a body; a summary
   counted before the fold would over-state the requirement by one link per welded body, and the fit test below
   (`requirement_counts_after_fold`) fails on it.
3. `samples` = collision samples and primitives tested per world. From `ShapeSummary.samples_static_max`.
4. `contacts` C = the design's declared active-contact capacity (from its contact sites and the workload's
   capacity table; DESIGN defaults: quadruped 32, hexapod 32, humanoid 64, wheeled base 16, wheel-leg 32).
5. `rows` R = four rows per contact (normal, two tangential, spin; the spin row is masked where the effective
   radius is zero) plus one limit row and one stiction-or-backlash row per actuated joint, plus the rows of every
   kinematic loop closure and rolling constraint, rounded up to a multiple of 8, unless the workload's row of the
   single capacities table (`registries/capacities.toml`, N16a-14, frozen by N21b-18) states a raised value, which
   is then read, not recomputed: the reference quadruped Q's 152 is already a multiple of 8 and is raised to 160
   by the reference-workload decision. Loops and rolling constraints are
   rows of the coupled solve, never model-table entries. Checks: quadruped 4·32 + 12 + 12 = 152 (raised to 160 from its table row); humanoid
   4·64 + 29 + 29 = 314 → 320; hexapod 4·32 + 18 + 18 = 164 → 168; wheeled base 4·16 + 4 + 4 = 72.
6. `structure` = hash of the tree in canonical link order (parents, joint classes as column counts k ∈ {1, 2, 3},
   level ranges); two models with equal `structure` differ only in parameter values.

Admitted classes. The registry `registries/shape_classes.toml` (DESIGN) holds the admitted degree-of-freedom sizes,
by default {12, 18, 24, 36, 48, 64}, and for each resident or previously built class its full capacity row. The
other capacities of a class are taken from its largest member (the fail-closed default of OPEN-PHYLUM-5: one bucket
axis on degrees of freedom), rounded up so that classes recur: C to the next of {16, 32, 48, 64, 96}, R to a
multiple of 8, links and samples to a multiple of 8 (DESIGN rounding, frozen with the bucket set at M2).

Fit, for one model against the classes in force for a population (output of the bucket planner):

1. Select classes with equal `sensor_layout`, `policy_layout`, `contact_law`, `precision` and `iterations`.
2. Among them keep those with `n_v`, `links`, `depth`, `samples`, `contacts`, `rows`, `actuators` each at least
   the requirement. For the five counts a compiled model knows, this is `frob_model`'s
   `fits(&ShapeSummary, &ShapeCapacity)` with the class converted by `ShapeCapacity::from(&ShapeClass)`; its
   `Fits { padding }` is the padding reported per field. `contacts` and `rows` are compared here.
   DESIGN (the conflict settled, stated identically in N14a-12): N14a-12's draft took `&ShapeClass`, a type that
   exists only from M2 (BD-148), one milestone after N14a-12, and this bead recounted what that bead counts. One count and one comparison: the counts are the summary's; `fits` compares
   them with a plain `ShapeCapacity`; this crate converts its class, calls `fits`, and compares C and R itself.
3. Choose the one with the smallest `n_v`, ties broken by the smallest padded bytes per world, then by
   `ShapeClassId`. The choice is a pure function of the model and the class set (determinism class D0).
4. Report `FitState`: `Resident` if a running cohort of that class exists on the target device (the warm admission
   path), `Known` if the class has cached kernels but no resident environment (cool path: buffers and one
   launch-graph capture), `New` otherwise (cold path if the kernel cache is empty).
5. If no class fits because `n_v`, `links` or `depth` exceed the largest admitted size, refuse with
   `FROB-REF-160` unless the tree-operator route is enabled (that route, for larger mechanisms, is a separate
   Frontier pilot).

Level decision for a cohort: `single_structure = true` exactly when every model slot has the same `structure`
hash. Then no link is padding, no mask is applied and the P-A path is used. Otherwise P-B: padding links are
identity transforms with zero inertia appended after the real links and masked out of every sum, and padded
degrees of freedom get identity rows.

Refusal `FROB-REF-160`, "No shape class": raised when a design exceeds the largest admitted bucket and the
tree-operator route is off. Envelope fields: `pointer` (the design), `observed` (the requirement vector),
`required` (the largest admitted class), `retry: after-change`. Ranked repairs: (1) enable the tree-operator route;
(2) run on `batch-cpu` with the design's own unpadded model; (3) simplify the design (fold fixed joints, reduce
collision samples). Exit code 3 (refused input).

## Acceptance criteria

- [ ] `Requirement` (n_v, links, depth, samples, C, R, actuators) of the reference quadruped is
      (18, 13, 3, 24, 32, 160, 12), its n_v, links, depth and actuators read from the folded model's
      `ShapeSummary`; the reference humanoid is (35, 30, ·, 40, 64, 320, 29) with depth as its summary reports;
      the row counts 152 (read as 160 from the quadruped's capacity-table row), 314 → 320, 164 → 168 and 72
      reproduce.
- [ ] With classes at 18, 36 and 64 in force, the quadruped fits 18, the humanoid 36 and a 50-DoF design 64; a
      70-DoF design refuses `FROB-REF-160` with the three repairs in order; with the tree-operator flag set the same
      design is routed, not refused.
- [ ] A design whose degrees of freedom fit a class but whose contact or row requirement does not is never placed
      in that class (the tracked-base control: n_v = 12, C = 64 does not fit a class with n_v = 12, C = 32).
- [ ] `single_structure` is true for 256 parameter variants of one tree and false as soon as one member differs in
      structure; a P-A cohort has zero padding links and applies no mask.
- [ ] The fit is identical for any ordering of the class set and of the population (property test), and identical
      on Linux and macOS, debug and release.
- [ ] `FitState` is `Resident`, `Known` or `New` consistently with the device's environment table and kernel cache
      (checked against a `synthetic` cache state).
- [ ] The fit returns the `FROB-REF-160` refusal value with the registry's exit code 3; its reachability through
      `frob phylum plan --json` and `frob phylum sweep --json` is asserted by the beads that add those verbs
      (`refusal.160` in N17a-08's script; N17b-04 for the sweep), which depend on this bead.

## Test plan

### Unit tests

- `requirement_reference_robots`: quadruped and humanoid vectors as above; hexapod (24, 19, ·, 32, 32, 168, 18);
  wheeled base n_v 10, samples 32, C 16, R 72, 4 actuators, links and depth as its folded summary reports; for
  each, the n_v, links, depth and actuators fields are asserted equal to the compiled model's `ShapeSummary` (no
  second count).
- `requirement_counts_after_fold`: a quadruped with a welded foot body on each leg has 13 links and depth 3, the
  same requirement as without the feet; a summary that counts the four welded feet (17 links, depth 4) is caught.
- `rows_formula_rounding`: R = roundup8(4·C + 2·actuated + closure rows); 152 → 152 (already a multiple of 8; the
  quadruped's requirement then reads 160 from its capacity-table row, and a requirement that keeps 152 for Q is
  caught), 314 → 320, 164 → 168, 72 → 72;
  one planar four-bar closure adds its rows before rounding.
- `fit_smallest_class`: classes {18, 36, 64}; sizes 12 → 18, 18 → 18, 19 → 36, 35 → 36, 37 → 64, 64 → 64, 65 → refuse.
- `fit_all_components`: requirement exceeding only `contacts` skips the class; exceeding only `depth` skips it.
- `fit_order_invariance` (property): shuffling classes and models changes no assignment.
- `single_structure_flag`: equal structure hashes → true; one changed parent index → false.
- `layout_mismatch_never_fits`: a different `sensor_layout` or `contact_law` excludes a class whatever its sizes.
- `refusal_160_shape`: code, pointer, observed, required, retry and the three ranked repairs; exit code 3.

### End-to-end script and logging

Covered by `scripts/e2e/phylum_plan.sh` (bead N17a-08), which runs `frob phylum plan` on a population containing
one design above the largest bucket and asserts the `FROB-REF-160` envelope, and on mixed populations whose
per-design class assignments it compares with pinned expectations. This bead contributes the assertions
`fit.class`, `fit.state` and `refusal.160` to that script's log (events `assert` and `refusal`, each with the
observed requirement vector, the class chosen and the evidence block).

### Known answers and negative controls

Known values: the capacity rows above (DESIGN defaults, TARGETs until the M2 battery records overflow rates).
Negative controls registered in the control registry: (1) a fit that compares degrees of freedom only, caught by
the tracked-base case; (2) a requirement that omits closure rows, caught by an overflow flag on a four-bar
fixture; (3) a fit that depends on class order, caught by the order-invariance property. Metamorphic relation: a
model fits the same class before and after renaming its bodies (names are read by no mechanical product).
Determinism lanes: twice on one machine, debug and release, Linux and macOS, class D0.

## Considerations

- OPEN-PHYLUM-5 (owner: Phylum lead; decided by overflow and padding statistics at M2): whether contact capacity
  needs its own bucket axis. Fail-closed default: no; one axis on degrees of freedom with the other capacities
  taken from the largest member. If the answer becomes yes, the class set gains a contact axis and step 3 of the
  fit minimises padded bytes first.
- OPEN-PHYLUM-1 (owner: Phylum lead; decided by the M1 pilot): the registered default set {12, 18, 24, 36, 48, 64}.
  One printed sketch of the type lists 32 in place of 36; 36 is used here, with the chapter and the open-question
  register.
- TARGET tied to capacities: under the default capacities, world-steps marked `Degraded` for capacity are at most
  10⁻⁴ of all world-steps per robot class on the standard battery, and every one is flagged. A class whose members
  overflow more often has its capacity raised, which changes `ShapeClassId` and re-runs the fit.
- A world's `StepPlanId` contains the shape class, so the same world run in two classes has two `StepPlanId`s and
  identical state digests. Comparisons across classes compare digests, never plan identities.
- Performance envelope: fitting is host arithmetic, microseconds per design; it is on the warm admission path whose
  median target is 0.1 s, so it must not compile or allocate device memory.
