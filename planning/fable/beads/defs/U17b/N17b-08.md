## Background

The head-to-head experiment (bead BD-186) has four arms. Two of them are incumbents: arm C is an incumbent's own
mixed-topology batch, run out of process at its pinned version; arm D is the leading incumbent run design by design
with warm caches, parallel compilation and per-world parameter batching wherever the tree is shared. The plan
commits in advance to what follows if arm C ties or beats the cohort: the two performance differentiators are
withdrawn. A comparison of that weight is only as good as the rival it is run against, and two of the project's
hygiene rules apply: the incumbent is measured before a mechanism is funded against it, with versions pinned and
the strongest warm configuration recorded; and no paired run happens before every arm in it has a published freeze
manifest.

OPEN-PHYLUM-4 is the open question: which incumbents and versions fill arms C and D. Owner: the Gauntlet lead.
Decided: frozen with the rival audit of the ten-fold test, before any run. Fail-closed default: none, and the arms
report `not run`.

## Scope

In: choosing the engine, solver and revision for each of the two arms; tuning each on the development half of the
mutation corpus; the two freeze manifests; the rule that nothing changes after the freeze.
Out: the runners that execute the frozen arms (N17b-09); the experiment (BD-186); the program-level rival audit.

## Technical approach

**Candidates.** FACT (releases read at plan time; each is re-pinned by revision before the freeze): MuJoCo and
MuJoCo Warp 4.0.1, Newton 1.8.0, Isaac Lab 3.0.0, Genesis 1.4.7, Drake 1.58.0, ManiSkill 3.0.1. What the plan says
about them: batching different trees is not available in the leading reduced-coordinate incumbent, whose
structural arrays carry no world dimension; mixed topologies in one batch exist in one manipulation simulator and
in two solvers of another engine; one of those solvers publishes a mixed batch of three body plans at 86 k
samples/s, 0.86 of the harmonic mean of its homogeneous rates, is maximal-coordinate, is documented as not
deterministic, and is reported as slower than the reduced-coordinate solvers of its framework.

- *Arm C* is filled by the incumbent whose solver accepts the 512 topologies of the workload in one batch and
  finishes the development workload soonest: an engine with a heterogeneous-batch solver, or the manipulation
  simulator with mixed topologies.
- *Arm D* is filled by the leading reduced-coordinate incumbent, configured with warm compilation caches, parallel
  compilation of designs on the CPU while earlier designs step, and its per-world model fields so that designs
  sharing a tree run as parameter variants of one environment.

**Procedure (numbered).**

1. List the candidates with their licences and the capabilities each documents (mixed topologies, per-world model
   parameters, state-preserving model edits, opt-in run-to-run determinism, warm caches).
2. For each candidate, run the development workload (the 512 designs and the development half of the mutation
   corpus) on the Linux machine with two RTX 4090 in its documented configurations; keep the configuration that
   finishes soonest. Tuning uses development material only. A documented capability left unused is justified in
   writing.
3. Choose one frozen configuration per arm. It is one configuration for the whole experiment, never a per-design
   choice.
4. Write a freeze manifest per arm: `{ arm, engine {name, revision, licence}, solver, configuration script hash,
   caches {compile: warm}, deterministic modes available and which accept a heterogeneous batch, tuning log hash,
   development scores, statement that this is the strongest configuration the budget allowed and what more budget
   would have added, hardware fingerprint, frozen_at, manifest_hash }`. The manifest is content-addressed and
   published in the experiment's registration.
5. After the freeze nothing changes in any arm, the cohort arm included. A defect found in a frozen arm after the
   sealed edits are opened voids the affected cells, which are re-run at the next milestone; it is never patched
   mid-experiment.
6. If no candidate can be frozen for an arm (none accepts the workload; a licence forbids the use; the revision
   cannot be pinned), the arm is recorded `not run` with the reason. That is the default and it is a finding, not
   an omission.

**Recording.** A decision record naming both manifests or the `not run` reasons, signed off by the Gauntlet lead,
cited by BD-186's registration and by the latency gate BD-184, which measures the same incumbents.

## Acceptance criteria

- [ ] Each arm has a published, content-addressed freeze manifest, or a recorded `not run` with its reason.
- [ ] Every engine named is pinned by revision; changing a revision changes the harness identity and invalidates the manifest.
- [ ] The tuning log shows development material only; no sealed edit was read before the freeze (checked against the key-access log of the corpus).
- [ ] The manifest lists the deterministic modes of arm C's solver and which of them accept a heterogeneous batch (needed by the experiment's fifth measure).
- [ ] The harness refuses to start a paired run in which any arm lacks a manifest.
- [ ] Licences of every engine and asset used are recorded.

## Test plan

### Unit tests

- `freeze_manifest_schema`: a manifest missing `revision`, `licence` or `manifest_hash` is rejected.
- `freeze_identity_changes_with_revision`: the same configuration at two revisions has two manifest hashes, and a run registered under one refuses to execute under the other.
- `paired_run_requires_all_manifests`: a registration with arm D's manifest absent and no `not run` reason fails validation.
- `not_run_is_explicit`: an arm with `not_run: { reason }` validates and the experiment's report prints the reason in that arm's column.
- `tuning_log_development_only`: a tuning log that references a sealed-corpus entry is rejected.

### End-to-end script and logging

`scripts/e2e/phylum_h2h_freeze.sh` sources the helper of `STD-E2E`; log
`target/e2e-logs/phylum_h2h_freeze/<utc>.ndjson`. For each arm it validates the manifest, starts the out-of-process
incumbent at the pinned revision on one design of the workload, records the version strings the engine reports and
asserts that they match the manifest (`cmd`, `assert` events with exit codes and wall time), then attempts to start
a paired run with one manifest removed and asserts the refusal. The `summary` lists assertions; no gate is claimed.

### Known answers and negative controls

- Known answer: the published figure the manifest's development score is compared with (0.86 of the harmonic mean for a three-body-plan mixed batch); a development score far below a published figure on comparable hardware is explained in writing before the freeze.
- Negative controls: a manifest edited after `frozen_at` must fail its hash; an engine upgraded in place must be detected by the version check.
- Determinism: validation results are identical run to run.

## Considerations

- An under-built rival makes the experiment worthless. The builders of the cohort arm may object in writing before the freeze that a rival is under-built, and the Gauntlet lead rules.
- If arm C is `not run`, the pre-declared outcome that depends on it (withdrawing the two performance differentiators if C ties or wins) cannot be evaluated; the status table then says the comparison against an incumbent mixed batch does not exist, and no claim is made against it.
- Licences: an engine whose licence forbids benchmarking publication cannot fill an arm.
- The same revisions should serve the program's ten-fold comparison; a second set of pins for the same engines would be a defect of process.
