## Background

A limb-archetype kernel (tier Frontier) is specialized to a limb's joint-class sequence and depth and reads every
value from the model table, so it is compiled once per kernel version and never per design. Ownership is split:
crate `frob-kernels` owns the kernels (bead N17b-26); crate `frob-phylum` owns decomposing a model table into a
base and archetype instances. This bead is the Phylum half: the registry of archetypes, the decomposition, the
instance tables the kernels iterate over, and the coverage report.

The rules the chapter fixes: at most 16 archetypes, drawn from the limbs of the project's eighteen robot
archetypes; a limb is an instance when its joint-class sequence and depth match after the canonical ordering of the
design language; a design with any limb outside the registry stays whole on the table-driven kernel; worlds are
grouped so that one execution group holds instances of one archetype; the port is the only interface; a design
moves between the two paths without a new step-plan identity. Exposure: the option `--limb-kernels` of
`phylum.sweep`, and `phylum.plan` reports the archetype coverage of a population.

This work exists only on the funding branch of the kill gate KILL-LIMBKERNEL (first reading: N17b-28).

## Scope

In: the registry file and loader; the archetype key; the decomposition algorithm; the per-model limb plan; the
per-cohort instance tables and their update at admission; the coverage fields of `phylum.plan`; the rule that a
partly covered design stays whole on the generic path.
Out: the kernels and their bit identity (N17b-26); the gate (N17b-27); the tree-operator route's port packets (a
later Frontier pilot).

## Technical approach

**Archetype key and registry (DESIGN).** A key is `(depth k, column counts c₁…c_k)`, where cⱼ is the number of
active columns of joint j's 6 × 3 screw basis (1 for revolute, prismatic and helical; 2 for cylindrical and
universal; 3 for spherical and planar), listed from the port outward. Names such as "serial three-revolute leg",
"four-joint wheel-leg", "seven-revolute arm" and "track flipper" are labels of keys. The registry
`registries/limb_archetypes.toml` holds at most 16 entries `{ id, name, depth, columns, drawn_from }`, where
`drawn_from` names the robot archetype whose limb supplied the key; a loader error rejects a 17th entry, a
duplicate key or an entry drawn from none of the eighteen. `ArchetypeId` is the hash of the key; the kernel version
is carried separately by the kernel.

**Decomposition of a model table (numbered).**

1. Count children per real link. Padding links take no part.
2. From each leaf link, walk toward the root while the parent has exactly one child and is not the root. The links
   collected, ordered from the port outward, are a limb; the first link not collected is its *port link*, and the
   limb's first joint placement is its mechanical port.
3. Everything not in a limb is the base (the root, branching links, chains between branching links).
4. Order limbs by the design's canonical limb order, so that equal designs produce equal plans.
5. Look up each limb's key. If every limb's key is registered, emit the plan below. If any limb's key is not
   registered, emit `LimbPlan::Whole`: the design runs entirely on the table-driven kernel.
6. Store the plan beside the model table. It is derived data: a pure function of the table and the registry
   version, and it never enters the table digest.

```rust
pub struct LimbInstance { pub archetype: ArchetypeId, pub port_link: u16,
                          pub links: Vec<u16>,       // the limb's k link indices in the table, port outward
                          pub dof_index: Vec<u16> }  // where each joint's coordinates sit in the model's vector
pub enum LimbPlan { Whole, Split { base_links: Vec<u16>, instances: Vec<LimbInstance> } }
```

The model table orders links by depth level, so a limb's links are not contiguous in it; the instance therefore
carries its link and coordinate indices explicitly, and the archetype kernel addresses the table through them.

**Instance tables per cohort.** For each registered archetype present in a cohort, an instance table lists
`(world, model slot, limb index)` for every instance, in ascending world order, in a buffer whose capacity is fixed
at environment creation (worlds × the largest limb count the shape class admits); unused entries are null
instances that do no work. Kernels launch once per archetype over its table with a fixed grid, so the launch graph
stays static and one execution group holds instances of one archetype. A model on `LimbPlan::Whole` has no entries
and its worlds are processed by the generic level kernels under a per-world flag in the variant view.

**Admission.** When a design is admitted into a running cohort its plan is computed on the host and its instances
are written into the instance tables at the same chunk boundary as its model table. No kernel is compiled: the
archetype kernels of the shape class were built with the environment. This is what the gate's clause "zero kernel
compiles while 1,000 corpus edits are admitted" measures.

**Identity.** The step-plan identity hashes kernel versions, and the archetype kernels are members of the kernel
set from the start, so switching a design between `Whole` and `Split` (for example by a registry change, or by
turning the option off) changes no step-plan identity. Which path ran is recorded in the placement receipt.

**Coverage report.** `phylum.plan` gains `archetype_coverage = { registry_version, limbs: {matched, total},
joints: {matched, total}, designs: {fully_covered, total}, missed_keys: [{key, count}] }`. Design coverage is the
figure that predicts how much of a population takes the fast path.

**Layout.** `crates/frob-phylum/src/limb/{registry.rs, decompose.rs, instances.rs}`.

## Acceptance criteria

- [ ] The registry loads with at most 16 entries, each drawn from one of the eighteen archetypes; violations are load-time errors.
- [ ] Decomposition reproduces the fixtures below exactly and is a pure function of table and registry version (identical on Linux and macOS).
- [ ] A design with one unregistered limb gets `LimbPlan::Whole`; no partially split design is ever emitted.
- [ ] Instance tables have fixed capacity, null padding and ascending world order; one launch per archetype covers them.
- [ ] Admitting a design writes its instances at a chunk boundary and triggers zero kernel compiles (counter read from the kernel cache).
- [ ] The step-plan identity is unchanged when a design's plan switches between `Whole` and `Split`.
- [ ] `phylum.plan` prints the coverage block with all three figures and the missed keys.
- [ ] The limb rule and key rule equal those registered by the paper pilot N17b-23 (the same fixtures pass in both).

## Test plan

### Unit tests (`cargo test -p frob-phylum limb`)

- `decompose_quadruped`: 13 links in level order (torso; four hips 1 to 4; four thighs 5 to 8; four shanks 9 to 12) → base {0}; four instances of key (3; 1, 1, 1) with link lists {1, 5, 9}, {2, 6, 10}, {3, 7, 11}, {4, 8, 12} in canonical limb order and coordinate indices {6, 10, 14}, {7, 11, 15}, {8, 12, 16}, {9, 13, 17} (after the six base coordinates).
- `decompose_hexapod`: six instances of (3; 1, 1, 1).
- `decompose_humanoid`: the three-joint waist stays in the base; two legs of key (6; 1×6) and two arms of key (7; 1×7).
- `decompose_wheel_leg`: four instances of (4; 1, 1, 1, 1).
- `unregistered_limb_whole`: a design with one nine-joint limb and a registry without (9; 1×9) → `Whole`.
- `registry_limits`: 17 entries → error; duplicate key → error; `drawn_from = "none"` → error.
- `plan_not_in_table_digest`: the model table digest is equal with and without a registry.
- `instance_table_layout`: 96 worlds of quadrupeds → 384 instances in world order; capacity beyond 384 holds null instances.
- `admission_writes_instances_no_compile`: admit a hexapod into a running quadruped cohort of the 24 bucket: six instances per world appear at the chunk boundary; the compile counter is unchanged.
- `step_plan_identity_stable`: the identity before and after toggling the plan is equal.
- `coverage_block`: on a five-design fixture with 18 limbs of which 16 are registered and both misses in one design: limbs 16/18, designs 4/5.

### End-to-end script and logging

`scripts/e2e/phylum_limb_plan.sh` sources the helper of `STD-E2E`; log
`target/e2e-logs/phylum_limb_plan/<utc>.ndjson`. It runs
`frob phylum plan --designs @workload:h2h-512 --json` and logs the coverage block as `metric` events (limb, joint
and design coverage with the thresholds 0.80 and 0.90); admits 32 development-corpus edits into a running
`batch-cpu` cohort with `frob design edit` followed by `frob phylum sweep` and asserts from the cache counters that
no kernel was compiled; prints the plan of three fixture designs and asserts the expected instances. `cmd` events
carry exact commands, exit codes, wall time and `evidence` blocks; on failure the first design whose plan differs
from its fixture is logged with both plans. The `summary` lists assertions and `gates: []`.

### Known answers and negative controls

- Known answers: the decomposition fixtures above (exact structures and offsets).
- Negative controls: a decomposition that splits a partly covered design must fail `unregistered_limb_whole`; a rule that treats a branching subtree as a limb must fail the humanoid fixture; an instance table ordered by arrival must fail the layout test under a permuted admission order.
- Hand control kept in view: a point mass on a massless leg standing on a floor. Nothing in a limb plan may be read as permission to close the base equation without the contact rows; the plan carries no dynamics.
- Determinism lanes: plans and tables are exact (class D0), identical across platforms and build profiles.

## Considerations

- Design-level coverage can be far below limb-level coverage. The report prints both so that an expectation built on the gate's limb figure is not carried over to throughput.
- The capacity of instance tables is a property of the shape class; a design with more limbs than the class admits for an archetype is put on `Whole`, never truncated.
- The registry is small on purpose: every entry is a kernel pair to derive, certify and keep bit-identical. Adding an entry needs the same bit-identity evidence as the first sixteen.
- If the kill gate fires at its final reading, this code stays only as the coverage statistic of `phylum.plan`.
