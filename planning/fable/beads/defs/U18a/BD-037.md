## Background

FrankenRobotics consumes sibling repositories that belong to the same owner (frankensim, frankentorch, frankensympy,
franken_lean, franken_numpy, asupersync, fastmcp_rust, frankensqlite, frankentui, franken_textiles, franken_threed,
franken_drone_geometry_reconstruction, franken_surveillance_system). Where a sibling has a limitation, a defect or a
mismatch, the rule (DESIGN) is that this program changes the sibling in the sibling's own repository, under that
repository's `AGENTS.md`, gates and conventions. Such a change is an **upstream work item**. It is tracked three
ways at once: a bead in this graph with the label `upstream` (key `FD-…`), a mirrored bead in the sibling's own
tracker, and a row in `registries/upstream.toml`.

Two things make the scheme safe. Every item carries an **interim posture** (what FrankenRobotics does until the
change lands) and a **switch-over rule** (what is re-run when it lands), so no milestone waits on a sibling. And a
defect found in a sibling becomes an admission test here first and an upstream work item there second: the
admission test records what the pinned commit does, the work item describes the change.

Alternatives rejected: a local patch or a fork of a sibling (it hides drift and breaks the single stack lock; a
sibling's newer clean head is never rolled back locally); making a milestone wait for a sibling change (M1 depends
only on FrankenSim, asupersync and FrankenSQLite, and no upstream item is on its critical path); tracking the items
only in prose (nothing could check that each has a fixture and a posture).

This bead is the M0 bookkeeping that makes the 53 items real. Two items are priority P0 and are executed at M0 by
other beads: FD-ASUP-01 (one asupersync version across the consumed siblings, in BD-008) and FD-FMCP-01
(fastmcp_rust on the one toolchain T, in BD-023).

## Scope

In: the schema and contents of `registries/upstream.toml` (53 rows); its loader and validation test; one failing
fixture per item; one bead per item in this graph (reserved keys `FD-FSIM-01` … `FD-F3D-01`, label `upstream`) and
one mirrored bead in the sibling's tracker; the procedure for a switch-over.

Out: doing the upstream changes (each `FD-…` bead); the admission tests that record the defects (BD-033 planar
drive, BD-034 PPO probes, BD-035 fixed witness and capacity, BD-036 strides); the two P0 changes (BD-008, BD-023).
Third-party gaps are not upstream work items: the `cudarc` bindings for graph capture and asynchronous pools
(OPEN-SPARK-4) are confirmed or refuted at INT-CUDA-01 and the CUDA annex binds the driver directly if a binding is
missing.

## Technical approach

**Registry schema (DESIGN), `registries/upstream.toml`, schema name `frob.upstream/1`.** One `[[item]]` per work
item with: `id`; `repo` (one or more sibling names); `change`; `priority` (`P0`…`P3`: the value of the item to
this project and its order in this program's queue, never a reason for a milestone to wait); `interim_posture`;
`switch_over` (the gates and tests to re-run); `fixture` (repository path of the reproducible failing fixture);
`admission_test` (an `INT-…` identifier where one exists); `bead` (the key in this graph); `mirror` (the bead
identifier in the sibling's tracker); `status` (`open`, `landed`, `adopted`); `observed_at` (sibling commit at which
the fixture was last seen to fail). The loader lives with the other registry loaders in `frob-core`; an unknown
field, a duplicate `id` or a missing required field is a load-time error.

**Rules every item obeys.**
1. Additive only: a new mode, entry point, type or feature, never a change to existing behaviour; any lossiness is
   self-described.
2. The sibling's rules bind the work. For FrankenSim: its layer checks, its contracts, its unsafe-capsule
   discipline, its ban on in-process foreign kernels in production paths, and its ban on branches and worktrees.
   The change lands on the sibling's `main` through the sibling's own gates.
3. Other agents work in the same siblings: before an upstream change edits a file it reserves that file through
   Agent Mail and follows the sibling's coordination rules.
4. Switch-over is a compatibility train: move the pin, write a new resolution receipt, re-run the admission and
   parity gates named in `switch_over`, relock. `status` becomes `adopted` only after that. Neither a pin nor the
   toolchain moves during the ten-fold tournament.

**Fixture rule.** Each item has exactly one fixture under `tests/upstream/<id>/` that fails at the pinned commit
and would pass after the change: for a defect, the smallest reproducing case; for a missing capability, a test that
asserts the typed refusal or the absent entry point and states the argument or result that is needed. Fixtures for
the reported foundation defects (each is FACT to recheck, recorded by its admission test before anything cites it):
- FD-FSIM-10 (`fs_g1_train::ppo_update`): with advantage Â = −1 and clip ε = 0.2, at ratio ρ = 0.5 the surrogate
  terms are −0.5 and −0.8 (gradient must be zero, the code lets it flow) and at ρ = 2 they are −2 and −1.2 (the
  unclipped term must carry the gradient, the code clips); finite differences 0, −0.5, −1 at ρ = 0.5, 1, 2 against
  the code's −0.25, −0.5, 0; critic output 2 with stored value and return 0 gives code gradient 0 where 2 is
  correct; two reset one-step episodes give a second likelihood ratio of 1.582459 where 1 is correct.
- FD-FSIM-11 (`fs-mbd::planar_drive`): heading 32 rad, wheel speeds 1 and 1 + 6·10⁻¹³ m/s, track 0.5 m, 400 steps
  of 1/400 s return zero translation where the closed form Δp = v·Δt·sinc(δ/2)·(cos(θ + δ/2), sin(θ + δ/2)), with
  δ = ω·Δt and sinc(0) = 1, gives about (0.83422336, 0.55142668) m. Mechanism: ω·Δt = 3·10⁻¹⁵ rad is below half
  the spacing of doubles at 32 (2⁻⁴⁸ ≈ 3.55·10⁻¹⁵), so θ + ω·Δt rounds to θ.
- FD-FNP-01 (strides): a contiguous 2×2 `f32` view has strides (8, 4) in bytes and (2, 1) in elements; copying

- FD-FSIM-33 (`fs-mbd::Wrench`): a body frame rotated 90° about z; a body-frame force (1, 0, 0) N copied

**Procedure.** (1) Write the registry and its loader test. (2) For each row author the fixture and record the commit
at which it fails. (3) Open the bead here (label `upstream`, the sibling repository name as a label, the row as its
body). (4) Open the mirrored bead in the sibling's tracker under that sibling's rules and store its identifier in
`mirror`. (5) Link each item to its admission test where one exists. Determinism: the registry is data, class D0.

## Test plan

### Unit tests
- `upstream_registry_loads_53`: parse the file; assert the item count and the two count vectors above.
- `upstream_registry_rejects_incomplete`: three planted files (missing `switch_over`, duplicate `FD-FSIM-11`, unknown key `owner`) each fail with the field named.
- `upstream_fixture_exists_for_every_item`: every `fixture` path exists and contains a test tagged with its `id`.
- `upstream_priority_never_blocks`: no bead outside the `upstream` label lists an `FD-…` key as a blocking dependency without also naming its interim posture (a graph lint over exported bead data; `synthetic` graph fixture for the negative case).

### End-to-end script and logging
`scripts/e2e/upstream_registry.sh`: runs the loader through `frob doctor --json` (the registry section), then runs
each fixture and asserts that it fails with the recorded signature at the pin. Logging per STD-E2E: NDJSON to
`target/e2e-logs/upstream_registry/<utc>.ndjson` with `ts`, `script`, `bead`, `step` (one per item id), `event`,
the command, exit code, wall time, the envelope's evidence block, the observed failure signature against the
recorded one, the sibling commit digest, and a final `summary` line with assertions passed and failed.

### Known answers and negative controls
The hand cases listed under the fixture rule are the known answers (PPO terms, the planar-drive displacement, the
stride element indices, the 22-contact refusal, the 0.6655 sign agreement). Negative controls: a fixture edited to
pass at the pin must make the script fail ("fixture no longer demonstrates the limit"); a registry row whose
`status` is `adopted` without a newer resolution receipt is rejected. Determinism lane: the loader output is
byte-identical on Linux and macOS.

## Considerations

- Risk: an upstream item collides with another agent's work in the sibling; mitigation is file reservation and the sibling's own coordination rules. Cost, order and collisions are carried as program risks.
- Risk (RISK-24): a reported foundation defect is relied on before it is rechecked; every reported number stays a report until its admission test records it.
- Hygiene: a registry that no verb or gate reads must be deleted. The readers here are the loader test, `frob doctor` and the switch-over procedure; if `frob doctor` does not adopt the section, the lead must name another reader.
- If no upstream item ever lands, the program still ships; the costs are the interim postures and the fallbacks of KILL-FSIM, KILL-METAL and KILL-MCP.
- FD-FSS-01 is conditional and is opened only if the inspection pilot finds the landmarks missing; its row exists with status `open` and a note.
