## Background

Three user-visible capabilities of the contact subsystem answer one question for an agent: "can I trust this
comparison between bodies with different numbers of contacts?" `contact.capacity` says before any run whether a
design fits each solver's contact capacity. `contact.audit` says after a run how many contacts the fast tier
missed against a certified detector. The capacity-bias rule says whether a comparison's arms were simulated
equally, and refuses to let a biased comparison be cited.

Unit tests prove the parts. This bead is the end-to-end script that drives the real `frob` binary (and the
daemon and the MCP surface where a step says so) on real fixtures, the way an agent would, and leaves a
structured log that a later reader can audit without re-running anything. It is one script for the capability,
not one per mechanism. A capability is implemented only when it is reachable through `frob --json` with a
documented schema and exit code, and this script is the evidence for that condition.

## Scope

In: one shell script, its fixtures and its log. Out: the mechanisms (N18b-20 to N18b-23), the gate records
(BD-168), the swept-bound gate rows (N18b-44).

## Technical approach

**Script.** `scripts/e2e/contact_capacity_audit.sh`, plain shell, sourcing the shared helper of the end-to-end
harness. Idempotent (every `run` verb is called with an explicit idempotency key derived from the script name,
the step and the seed), seed-explicit (`SEED` defaults to 1337 and is printed), exits non-zero on the first
failed assertion after writing the summary line.

**Steps.**

1. `frob doctor --json`: environment sanity; records the build identity and the hardware fingerprint.
2. *Static capacity.* `frob contact capacity quad-mammal --json` → exit 0; assert `stance` 16 and `prone` 24
   against a referee cap of 21. `frob contact capacity humanoid --json` → `stance` 16, `prone` 40, referee
   `fits: false` for `prone`, exit 2. `frob contact capacity tracked-flipper --json` → `belt` class above 21.
3. *Refusal instead of truncation.* `frob sim run --tier referee` on the humanoid crawl scenario → exit 5,
   `FROB-REF-721`; assert the refusal's ranked repairs name the patch reduction and `--profile strict`.
4. *Qualified patch reduction.* The same with `--patch-reduction sole-4` → completes; assert the
   `patch-reduced` condition and the qualification receipt identity. With an unqualified name → refusal.
5. *Forced overflow on a lockstep tier.* `frob sim run --tier batch-cpu --profile lockstep --contact-cap 8
   --on-overflow continue-flagged` on the tracked base → exit 2; assert worlds flagged `Degraded` with a
   capacity reason and that the per-world contact list digest equals the detected set (nothing dropped). The
   same with `--on-overflow refuse` → exit 5, `FROB-REF-722`.
6. *Capacity-biased comparison.* The fixture `fixture:capacity-bias` (tracked against point-foot, 256 worlds per
   arm, cap 8) through the study verbs → assert condition `capacity-biased`, `verdict: null`, both arms'
   overflow shares printed and their difference above the one-point threshold.
7. *Citation refused.* A report or promotion request citing the comparison of step 6 → exit 3, `FROB-REF-822`,
   repairs "raise capacity" and "apply a qualified patch reduction to both arms".
8. *Clean comparison.* Step 6 at the default capacity → no label, a verdict present.
9. *Tunnelling audit, negative control.* A lockstep job on the thin-barrier scene with the speculative margin
   disabled (a test-only plan flag), then `frob contact audit --run <id> --p 1 --detector strict --json` →
   assert misses greater than zero, all attributed to `margin`.
10. *Tunnelling audit, real.* The same scene with the margin enabled, and the battery subset `smoke` → assert
    the rate is below 1 per 10⁶ audited world-steps or that n is too small to say so, in which case the script
    asserts that the envelope reports the upper bound and does not claim the gate.
11. *Determinism.* Steps 6 and 10 repeated; assert identical result digests. Steps 6 and 10 with a different
    worker count; assert identical digests.
12. *MCP parity.* `contact_capacity` and `contact_audit` called through `frob-mcp` with the same arguments;
    assert the structured content equals the CLI envelope apart from transport fields.
13. *Cancellation.* A long audit is started, cancelled through `job.cancel`, and found by `job.find` with its
    idempotency key; assert one job and no leaked device resources.

**Logging.** Structured newline-delimited JSON to `target/e2e-logs/contact_capacity_audit/<utc-timestamp>.ndjson`
and a human-readable transcript beside it. Every line has `ts`, `script`, `bead` (`N18b-24`), `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, the exit code, wall time, the
envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and
thresholds (contact counts, overflow shares in percentage points, missed contacts per 10⁶ world-steps, audited
world-steps, the upper bound), digests where state is compared, and on failure the first differing value and
the artifact paths needed to reproduce (run identity, world address, step, replay command). A final `summary`
line gives the counts of assertions passed and failed and the gates touched (GATE-TRAC-03, GATE-TRAC-06). Logs
never contain private-scene data: fixtures are public synthetic scenes and the helper redacts any path under a
private namespace.

## Acceptance criteria

- [ ] The script exists, is executable, sources the shared helper and passes on a clean checkout with only
      `batch-cpu` available; device steps are skipped with a logged reason when no device is present.
- [ ] Every step above has at least one logged `assert` event with the measured value and the threshold.
- [ ] Exit codes observed: 0 (clean), 2 (findings or flags), 3 (`FROB-REF-822`), 5 (`FROB-REF-721`,
      `FROB-REF-722`), 8 where a job handle is returned; exit code 1 never appears.
- [ ] The negative controls are caught: the margin-disabled run produces misses; the contacts-removed mutant
      build (run by CI with a feature flag) makes step 5 fail.
- [ ] Running the script twice produces the same assertions and the same result digests; the second run reports
      `idempotent_replay: true` where the stored answer was returned.
- [ ] The log validates against the harness's log schema and contains the `summary` line.

## Test plan

### Unit tests

None of its own: the script is the test. A shell-level self-test (`scripts/e2e/selftest/contact_capacity_audit.bats`
or the harness equivalent) checks that the script fails when an expected value is altered, so that the script is
shown able to fail.

### End-to-end script and logging

As specified above: `scripts/e2e/contact_capacity_audit.sh`, driving `frob contact capacity`, `frob sim run`,
the study verbs, `frob contact audit`, `frob job cancel` and `frob job find`, and the same verbs through
`frob-mcp`.

### Known answers and negative controls

KA-420 (capacity-bias fixture), KA-408 (thin barrier), KA-349 (forced overflow flagged or refused), CX-151 (21
contacts), CX-169 (endpoint tests), CX-180 (dropped contacts). Planted failures the script must catch: margin
disabled; contacts removed to fit; an altered expected count in the self-test. Determinism lanes: twice on one
machine; two worker counts; debug and release builds in CI.

## Considerations

- Step 10 cannot by itself establish GATE-TRAC-03, which needs at least 3·10⁶ audited world-steps per scene
  class for its bound; the gate record is produced by the conformance run of BD-168. The script proves the path
  and the reporting.
- Run time target: under ten minutes on `batch-cpu` (TARGET), so that it can run on every change that touches
  contact.
- The script must not depend on wall-clock timing or on device availability for its pass or fail decision.
