## Background

Three user-visible capabilities of the contact subsystem answer one question for an agent: "can I trust this
comparison between bodies with different numbers of contacts?" `contact.capacity` says before any run whether a
design fits each solver's contact capacity. `contact.audit` says after a run how many contacts the fast tier
missed against a certified detector. The capacity-bias rule says whether a comparison's arms were simulated
equally, and refuses to let a biased comparison be cited.

Unit tests prove the parts. This bead is the end-to-end script that drives the real `frob` binary (and the
daemon and the MCP surface where a step says so) on real fixtures, the way an agent would, and leaves a
structured log that a later reader can audit without re-running anything. It is one script for the capability,
not one per mechanism. A capability is implemented only when it is reachable through `frob --json` with a
documented schema and exit code, and this script is the evidence for that condition.

## Scope

In: one shell script, its fixtures and its log. Out: the mechanisms (N18b-20 to N18b-23), the gate records
(BD-168), the swept-bound gate rows (N18b-44).

## Technical approach

**Script.** `scripts/e2e/contact_capacity_audit.sh`, plain shell, sourcing the shared helper of the end-to-end
harness. Idempotent (every `run` verb is called with an explicit idempotency key derived from the script name,
the step and the seed), seed-explicit (`SEED` defaults to 1337 and is printed), exits non-zero on the first
failed assertion after writing the summary line.

**Steps.** Four mechanism beads own a script each, written and passed when the mechanism landed; this script
runs them as stages, reads the `assert`, `refusal` and `summary` lines of their logs (a called script that exits
0 with a failed `assert` line fails the stage: the log is trusted, not only the exit code), and contains no
second copy of their commands. Its own steps are those that need more than one mechanism or the battery of
BD-168.

1. `frob doctor --json`: environment sanity; records the build identity and the hardware fingerprint.
2. *Static capacity* (`capacity`): runs `scripts/e2e/contact_capacity.sh` (N18b-20). What it asserts:
   `frob contact capacity crates/frob-conformance/fixtures/capacity/quadruped.fbot --json` → `stance` 16 and
   `prone` 24, each `fits` as m ≤ C against the referee cap read from the printed `referee_cap` (21 at the pinned
   revision: `stance` fits, `prone` does not), so exit 2 under the verb's exit rule;
   `crates/frob-conformance/fixtures/capacity/humanoid.fbot` → `stance` 16, `prone` 40, referee `fits: false`
   for `prone`, exit 2; `crates/frob-conformance/fixtures/capacity/tracked-2f.fbot` → the `belt` class of 80
   samples against the printed `referee_cap`; the six reference workloads of N18b-20 against the capacity table;
   MCP parity for `contact_capacity`.
3. *Refusal instead of truncation, and the qualified patch reduction* (`reduction`): runs
   `scripts/e2e/patch_reduction.sh` (N18b-21). What it asserts: `frob sim run --tier referee` on the humanoid
   crawl scenario → exit 5, `FROB-REF-721`, ranked repairs naming the patch reduction and `--profile strict`;
   the same with `--patch-reduction sole-4` → completes with the `patch-reduced` condition and the
   qualification receipt identity; an unqualified name → the `patch-reduction-unqualified` refusal, exit 3.
4. *Forced overflow on a lockstep tier* (own step). `frob sim run
   crates/frob-conformance/fixtures/capacity/tracked-2f.fbot --scene plane --init flippers-down --tier batch-cpu
   --profile lockstep --on-overflow continue-flagged --seed $SEED --key <k> --json` (N18b-20's two-flipper tracked
   fixture, not the M3 zoo archetype `zoo/tracked-flipper.fbot`; `flippers-down`: the named initial condition
   `tracked-2f.fbot` declares, `sim.run`'s `--init` of N16b-25) with both flippers down on the flat floor, so that all 80 belt and flipper stations touch against the default
   C = 64 of its shape class (the overflow is forced by the fixture at the registered capacity, not by lowering
   it with N16a-14's `--capacity` override, so the step checks the capacity every user runs at) → exit 2; assert worlds flagged `Degraded` with a capacity reason and that the
   per-world contact list digest equals the detected set (nothing dropped). The same with `--on-overflow refuse`
   under a distinct key → exit 5, `FROB-REF-722` (the `batch-cpu` code; on a GPU tier the code is `FROB-REF-610`,
   not exercised here).
5. *Capacity-biased comparison, citation, clean comparison* (`bias`): runs `scripts/e2e/capacity_bias.sh`
   (N18b-22). What it asserts: the fixture `fixture:capacity-bias` (tracked against point-foot, 256 worlds per
   arm, cap 8) through the study verbs → condition `capacity-biased`, `verdict: null`, both arms' overflow
   shares printed and their difference above the one-point threshold; a citing verb asked to cite it → exit 3,
   `FROB-REF-822`, repairs "raise capacity" and "apply a qualified patch reduction to both arms" (each citing
   verb from its landing on; before, skipped with a logged reason and never counted as passed); the default
   capacity → no label, a verdict present.
6. *Tunnelling audit, negative control and causes* (`audit`): runs `scripts/e2e/contact_audit.sh` (N18b-23).
   What it asserts: the thin-barrier job (plate 3 mm ahead at 5 m/s) under the test-only controls
   `margin-base-only` and `endpoint-only-thin` together (either alone is caught by the other protection), then
   `frob contact audit --run <id> --p 1 --detector strict --key <k> --json` → misses greater than zero, all
   attributed to `margin`; none on the production build; N18b-45's arc hand instance on `strict` under the
   chord-only control (plant `N18b-43:trac-arc`) ending with `FROB-REF-221` whose check report names check 6, never
   committed with its contact unlisted, and committed with no miss on the production build; capacity overflows under `capacity` only; MCP parity for `contact_audit`; cancellation
   through `job.cancel` and recovery by `job.find` with its
   idempotency key (one job, no leaked device resources).
7. *Tunnelling audit on the battery* (own step). `frob contact audit --battery smoke --tier batch-cpu --profile
   lockstep --p 1 --detector strict --seed $SEED --key <k> --json` on the `smoke` battery of N24b-01 (the per-change
   battery; BD-168 records GATE-TRAC-03 on N38a-20's `standard` battery, which this script does not run), the production margin in force → assert the rate is below 1 per 10⁶ audited
   world-steps or that n is too small to say so, in which case the script asserts that the envelope reports the
   upper bound and does not
   claim the gate.
8. *Determinism* (own step). Stage 5's biased study and step 7's audit repeated under new keys (a repeated key
   returns the stored answer and proves nothing about determinism); assert identical result digests. The same
   with a different `batch-cpu` worker count, set through the pool configuration (`contact.audit` has no worker
   input), again under a new key; assert identical digests.

**Logging.** Structured newline-delimited JSON to `target/e2e-logs/contact_capacity_audit/<utc-timestamp>.ndjson`
and a human-readable transcript beside it. Every line has `ts`, `script`, `bead` (`N18b-24`), `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, the exit code, wall time, the
envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and
thresholds (contact counts, overflow shares in percentage points, missed contacts per 10⁶ world-steps, audited
world-steps, the upper bound), digests where state is compared, and on failure the first differing value and
the artifact paths needed to reproduce (run identity, world address, step, replay command). A final `summary`
line gives the counts of assertions passed and failed and the gates touched (GATE-TRAC-03, GATE-TRAC-06). Logs
never contain private-scene data: fixtures are public synthetic scenes and the helper redacts any path under a
private namespace.

## Acceptance criteria

- [ ] The script exists, is executable, sources the shared helper and passes on a clean checkout with only
      `batch-cpu` available; device steps are skipped with a logged reason when no device is present.
- [ ] Every step above has at least one logged `assert` event with the measured value and the threshold.
- [ ] Exit codes observed: 0 (clean), 2 (findings or flags), 3 (`FROB-REF-822`), 5 (`FROB-REF-721`,
      `FROB-REF-722`), 8 where a job handle is returned; exit code 1 never appears.
- [ ] The negative controls are caught: the run under `margin-base-only` with `endpoint-only-thin` produces
      misses; the contacts-removed mutant (the control of CX-180, plant `N18b-22:cx-180`, built with `--features
      gauntlet-mutations,<crate>/<feature>` exactly as its control record writes it, BD-025) makes step 4 fail
      through `e2e_expect_caught`.
- [ ] Stages 2, 3, 5 and 6 run the scripts of N18b-20, N18b-21, N18b-22 and N18b-23 and contain no second copy of
      their commands; a called script that exits 0 with a failed `assert` line in its log fails its stage.
- [ ] Running the script twice produces the same assertions and the same result digests; the second run reports
      `idempotent_replay: true` where the stored answer was returned.
- [ ] The log validates against the harness's log schema and contains the `summary` line.

## Test plan

### Unit tests

None of its own: the script is the test. A shell-level self-test (`scripts/e2e/selftest/contact_capacity_audit.bats`
or the harness equivalent) checks that the script fails when an expected value is altered (the `prone` count of
the quadruped changed from 24 to 21 through the expected-value override of the STD-E2E helper, passed to
`contact_capacity.sh`), and that a called script whose log holds a failed `assert` fails its stage even when it
exits 0, so that the script is shown able to fail.

### End-to-end script and logging

As specified above: `scripts/e2e/contact_capacity_audit.sh`, running the four owned scripts and driving `frob
doctor`, `frob sim run` and the battery audit itself, with the same verbs through `frob-mcp` in the called
scripts.

### Known answers and negative controls

KA-420 (capacity-bias fixture), KA-408 (thin barrier), KA-349 (forced overflow flagged or refused), CX-151 (21
contacts), CX-169 (endpoint tests), CX-180 (dropped contacts). Planted failures the script must catch: base-only
margin with endpoint-only thin tests; contacts removed to fit; an altered expected count in the self-test. Determinism lanes: twice on one
machine; two worker counts; debug and release builds in CI.

## Considerations

- Step 7 cannot by itself establish GATE-TRAC-03, which needs at least 3·10⁶ audited world-steps per scene
  class for its bound; the gate record is produced by the conformance run of BD-168. The script proves the path
  and the reporting.
- Run time target: under ten minutes on `batch-cpu` (TARGET), so that it can run on every change that touches
  contact.
- The script must not depend on wall-clock timing or on device availability for its pass or fail decision.
