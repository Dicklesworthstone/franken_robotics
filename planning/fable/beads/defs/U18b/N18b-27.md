## Background

A proposal considered for the contact solve was to factor the per-world Hessian H in half precision on matrix
accelerators (tensor cores) and recover accuracy by iterative refinement in single precision. The proposal is
rejected (decision ADR-TRAC-07; hypothesis H-15, refuted), and the rejection is recorded as a calculation so that
nobody rebuilds it. A killed idea stays on the page with the arithmetic that killed it, and that arithmetic is
part of the known-answer suite.

The refuting calculation has three parts.

1. *Conditioning.* Half precision has unit round-off u₁₆ = 2⁻¹¹ ≈ 4.9·10⁻⁴. Refinement on a low-precision factor
   contracts only if κ·u₁₆ < 1. Take a rank-one contact operator W with the proximal shift ρ = 10⁻²·tr(W)/48 for
   16 contacts (48 rows): the largest eigenvalue of W is tr(W), so κ(W + ρ·I) = (tr(W) + ρ)/ρ = 1 + 48/0.01 =
   4,801 and κ·u₁₆ = 2.34. FACT (emulated in software on three reference models; to be re-run before a gate cites
   it): after unit-diagonal scaling, κ·u₁₆ ≥ 1 in 37 to 64% of sampled contact states, and a half-precision
   factor with single-precision refinement fails outright in 9 to 18% of them.
2. *Cost.* A single-precision Cholesky costs n³/3 flops and each refinement step about 3n², so k steps cost
   9k/n times the factor they replace: 2.3 at n = 27 with seven steps, 1.5 at n = 35 with six, 3.0 at n = 18
   with six. Refinement alone costs more than the factorization it was meant to cheapen; with six steps the
   ratio falls below a quarter only above 216 unknowns.
3. *Hardware.* Matrix accelerators speed large products. A per-world matrix of 18 to 64 rows is smaller than one
   panel, and Apple GPUs have no such units. The published four- to five-fold gains were measured against double
   precision at about 22,000 unknowns, and theory promises at most a factor of two against a single-precision
   baseline (FACT about the published source, to be re-read).

Nothing about contact solves survives. What is used instead: single precision in power-of-two scaled variables
(BD-156, N18b-25), with admission by scaled κ·u (N18b-26). Matrix accelerators are likewise not adopted for
policy networks of a few hundred units: learner and inference together are about 13% of training wall-clock on
one incumbent stack, so their removal gains at most 1.15.

## Scope

In: the refusal `FROB-REF-245` wherever a half-precision solve or state buffer could be requested; the refuting
calculation as executable known answers; the registry entry for the rejected mechanism. Out: any half-precision
kernel (none is built); the device matrix path inside the labeled D4 training profile, which belongs to the
learning subsystem and is a different mechanism.

## Technical approach

**Where the refusal fires (DESIGN).** Three entry points can carry a precision request and each validates it
against a closed enumeration:

- the step plan: `ShapeClass.precision` is the enumeration `default | stiff`; the tier's element type is `f32`
  on devices and `f32` or `f64` on `batch-cpu`. Any other value is unrepresentable in the type;
- the surface: `frob sim run --precision <p>` and the corresponding field of every `run` verb that creates an
  environment. The strings `f16`, `half`, `fp16`, `mixed` and `mixed-f16` are parsed to a `RequestedPrecision`
  and rejected with `FROB-REF-245`. A misspelt or unknown value is the generic misspelt-parameter refusal, not
  this one: the half-precision spellings are recognized on purpose so that the caller learns why;
- the kernel manifest: a manifest whose element type for a solve or state slab is a 16-bit float fails
  registration with the same code at build time.

**The refusal.** Code `FROB-REF-245`, name "Half precision", raised when a half-precision solve or state buffer
is requested. Exit code 3. `retry` = `never`. Ranked repairs: none; the capability is not offered. The message
cites the calculation: "κ·u₁₆ ≥ 1 on 37 to 64% of sampled contact states; refinement costs 9k/n times the factor
it replaces". `pointer` names the field that carried the request.

**The calculation as code (DESIGN).** `frob-conformance/registry/known_answers.toml` rows with one derivation
file `docs/derivations/half-precision.md`; a host test evaluates each number in exact rational arithmetic where
it is rational (κ = 4,801; the cost ratios 63/27, 54/35, 54/18; the break-even 36·k) and in `f64` otherwise
(κ·u₁₆ = 4,801/2,048 = 2.344).

**Emulation fixture (DESIGN).** A software half-precision type (round-to-nearest-even conversion of each
operation result to 11 significand bits, exponent range of IEEE binary16) used only in the test crate. On the
rank-one fixture it factors W + ρ·I, runs single-precision refinement and records that the iteration does not
contract. On sampled contact states of the reference robots it reproduces the share of states with κ·u₁₆ ≥ 1;
the measured share replaces the recorded FACT once it has been re-run at a pinned commit.

## Acceptance criteria

- [ ] `frob sim run --precision f16 --json` (and `half`, `fp16`, `mixed-f16`) returns one envelope with
      `ok: false`, `FROB-REF-245`, exit code 3, `retry: never`, an empty repair list and the pointer to the field.
- [ ] No type in `frob-kernels`, `frob-contact` or the device annexes can express a 16-bit float solve or state
      slab; a manifest that tries is rejected at registration (compile-fail or load-fail test).
- [ ] The known-answer rows reproduce: κ = 4,801; κ·u₁₆ = 2.34; cost ratios 2.3, 1.5, 3.0; break-even at 216
      unknowns for six steps.
- [ ] The emulation fixture shows non-contraction on the rank-one case and reports the measured share of sampled
      contact states with κ·u₁₆ ≥ 1 with its sample identity.
- [ ] `registries/refusals.toml` carries the code with its meaning and "repairs: none"; the rejected mechanism is
      listed in the killed-idea register with this bead's derivation file.

## Test plan

### Unit tests

`crates/frob-contact/tests/half_precision.rs` and `crates/frob-conformance/tests/` (host).

- `kappa_rank_one`: W = w·wᵀ with ‖w‖² = tr(W) = 48, ρ = 0.01: eigenvalues of W + ρ·I are 48.01 and 0.01;
  κ = 4,801 exactly in rationals.
- `kappa_u16`: 4,801·2⁻¹¹ = 2.344 (reported as 2.34); assert > 1.
- `cost_ratios`: 9·7/27 = 7/3 ≈ 2.33; 9·6/35 ≈ 1.54; 9·6/18 = 3; assert each within 0.05 of 2.3, 1.5, 3.0.
- `break_even`: the least n with 9·6/n < ¼ is 217 (ratio equals ¼ at n = 216).
- `refine_does_not_contract`: emulated binary16 factor of the rank-one fixture; the refinement error ratio per
  step is at least 1 over 10 steps.
- `refusal_spellings`: each of the four spellings yields `FROB-REF-245`; `--precision f31` yields the misspelt-
  parameter refusal instead.
- `manifest_rejects_f16`: a manifest fixture declaring a binary16 state slab fails registration.

### End-to-end script and logging

`scripts/e2e/half_precision_refusal.sh` (helper of STD-E2E): issues the four refused requests through `frob
--json` and one through `frob-mcp`, asserts exit code 3 and the refusal block on each, then runs the host
known-answer target. Each NDJSON line carries the command, exit code, wall time, the refusal block and, for the
known-answer step, each computed value against its expected value. `summary` counts assertions.

### Known answers and negative controls

KA-423 (κ = 4,801, κ·u₁₆ = 2.34, the three cost ratios, the refusal). CX-176 (the shortcut "a half-precision
factor with single-precision refinement cheapens the contact solve") with its numbers. Negative control: a
planted permissive parser that maps `f16` to `f32` silently must fail the refusal test (a misspelt or
unsupported parameter is a refusal, never a default).

## Considerations

- The emulated shares (37 to 64%, 9 to 18%) are a recorded FACT from a small program and are re-run here before
  any document cites them as this project's measurement.
- What would reopen the decision: contact systems above about 200 unknowns per world solved as one dense block
  (not in scope: the dense path is capped at 64 degrees of freedom), or a device with fast correctly rounded
  half-precision panels smaller than 64 rows. Neither exists in the target hardware.
- Bet BET-08 (single precision is adequate on the GPU given anchored coordinates, group-preserving updates,
  diagonal scaling and guarded comparisons) is the positive statement this refusal protects.
