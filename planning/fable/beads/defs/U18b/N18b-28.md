## Background

Which contact law produced a number decides what the number means. Penetration is an error under the hard-
contact law and a state under the compliant laws; creep below the friction threshold is zero under one law and
bounded by a stiction speed under another; an evaluator must be told which law produced a gap. The law is
therefore part of the identity every result carries (`StepPlanId`), and an agent needs one place to ask which
laws exist, where each may run, and with which parameters.

The laws (each a named law of the contact solve):

| Law | Contents | Tier |
|---|---|---|
| CL-1 | Linear compliant normal with a dissipation time; regularized Coulomb friction with a stated stiction speed | Solid; default on lockstep tiers |
| CL-2 | Hunt–Crossley normal law and regularized friction in convex form | Frontier |
| CL-M | A mapping of an incumbent engine's soft-contact parameters, for importing reference models; lossy, and the loss report says so | Solid; parity only |
| CL-H | Hard contact: Signorini complementarity on the normal, Coulomb friction with maximum dissipation on the four-dimensional cone, non-associated | Solid as the referee's written specification; Frontier as a batch law |

Every law except CL-H is a convex potential ℓ_c whose negative gradient is the impulse; CL-H is a
complementarity problem and says so. Further laws attach to the same table as they land: the film-friction row,
tyre laws, the belt law, soil laws.

A law is **admitted** on a (tier, profile) pair only after its gate has passed there. Requesting a law where it
is not admitted is a refusal (`FROB-REF-246`), not a silent substitution of the default law, because a silent
substitution would return a result under an identity the caller did not ask for. `contact.laws` is the read
verb that prints the table. Tier Solid.

## Scope

In: the registry file `registries/contact_laws.toml` and its loader over the types of N18a-15; the admission
status of each (law, tier, profile) cell derived from recorded gates; the refusal `FROB-REF-246` as an envelope
payload with its repairs, wired into every verb that creates an environment; invariant INV-TRAC-01 as a
registration rule with its tests; the verb `contact.laws` at M1 (referee) with the growth path to later tiers;
the input `--law` of `sim.run` at M1 (VERBS-sim's row: this bead at M1, admitted on every tier by N16b-25 at M2);
the conformance-build-only input `--conformance-admit-pending <gate>` by which a gate's measuring runs reach a
`pending` cell.

Out: the `ContactLaw` trait, `LawId` and `LawDescriptor`, the typed parameter classes, the gap-provenance rule
and the in-code admission check this bead calls (N18a-15, a dependency); the laws' mathematics and kernels
(N18a-16, N18a-18, N18a-20, N18a-21, BD-386); interface cards (BD-167 adds the cards in use to the verb's
output at M2); the per-law convexity certificates, their receipts and the lookup that step 1a calls (N12-51,
M2); the probe verb (N18b-29).

## Technical approach

**Registry (DESIGN).** `registries/contact_laws.toml`, loaded by `frob-contact`; an unknown law name is a
load-time error.

```toml
[[law]]
id = "CL-1"
kind = "convex-potential"          # or "complementarity" (CL-H only)
tier = "S"
parameters = [
  { name = "stiffness",        class = "physical",  unit = "N/m" },
  { name = "dissipation_time", class = "physical",  unit = "s" },
  { name = "mu",               class = "physical",  unit = "1" },
  { name = "stiction_speed",   class = "numerical", unit = "m/s" },
]
admission = [                      # no status key: status is derived (below)
  { tier = "batch-cpu", profile = "lockstep", gate = "GATE-TRAC-01", part = "M2" },
  { tier = "batch-cpu", profile = "strict",   gate = "GATE-TRAC-01", part = "M2" },
  { tier = "gpu-cuda",  profile = "lockstep", gate = "GATE-TRAC-01", part = "M2" },
  { tier = "gpu-metal", profile = "lockstep", gate = "GATE-TRAC-01", part = "M2" },
]
# a row may add kill = "<kill row>" (CL-H's batch rows: KILL-HARDCONTACT; the film row's lockstep rows: KILL-FILM)
```

Parameter classes: **physical** (stiffness, dissipation time, friction coefficients, restitution, film and soil
parameters), which come from cards and are never changed by a retry, a step variant or a tolerance variant; and
**numerical** (the stiction speed of a regularized law, regularization rates, pass counts, residual
tolerances), which are reported and belong to the step plan. Tiers: `referee`, `batch-cpu`, `gpu-cuda`,
`gpu-metal`. Profiles: `referee`, `strict` (transactional, `batch-cpu` only), `lockstep`.

**Admission status (DESIGN: derived, never hand-edited).** A gate's record in `registries/gates.toml` carries
its status per milestone part (`[[gate.part]]`, statuses `not-run`, `pass`, `fail`, `killed`, `blocked`,
`no-claim`, `superseded`), not per tier, so each admission row names the `gate` and the `part` (milestone) that
measures its tier and profile. The loader derives each (law, tier, profile) cell in this order:

1. No admission row for the cell → `not-built`.
1a. (A cell of profile `lockstep` whose law is of kind `convex-potential`, from M2.) The law has no `LawConvexity`
   receipt whose definition hash equals the law's current definition hash → `not-certified`, evaluated before
   the gate-derived steps 2 to 5, so a passing gate cannot admit an uncertified law. The receipts and their
   lookup are N12-51's admission guard (M2, which depends on this bead): the derivation takes the lookup as an
   input, `certified: &dyn Fn(LawId, DefinitionHash) -> bool`, and N12-51 links it. DESIGN: the M1 build has no
   lookup and skips the step, which cannot admit an uncertified law, because no lockstep cell can pass before
   GATE-TRAC-01's M2 part; from M2 every build links it, and a receipt store that cannot be read makes every
   such cell `not-certified` (fail closed). A `complementarity` law (CL-H) is covered by the residual rule of
   INV-TRAC-01 below, not by a certificate.
2. The row's `kill` names a kill row whose decision in force has outcome `fired` (N40-03; the gates it reads
   then show `killed`), or the named part is `killed` → `fallback`, with the kill row's `fallback` text (taken
   from the part's `detail` when the row names no kill).
3. The named part is absent, `not-run`, `blocked` (the OPEN identifier from its `detail` is carried),
   `no-claim` or `superseded` → `pending`.
4. The named part is `fail` → `failed` for a tier whose rows include a failure in the part's row-by-tier
   results, `pending` for its other tiers.
5. The named part is `pass` → `admitted` when the part's row-by-tier results (stored with the gate record by the
   bead that records the part; for GATE-TRAC-01, BD-085 the M1 referee rows, and BD-168, which assembles the M2
   part, the `strict` rows BD-161 measured and the batched rows) show every row the battery marks for that tier and profile as passed. A tier with no results under a passing
   part (a GPU tier not available when the part was recorded) stays `pending`: no tier is admitted on another
   tier's evidence.

A row never carries a `status` key: the loader rejects one as a load error `law-status-hand-edited` naming the
row, so a hand edit cannot change admission and fails CI. Initial rows and their gates: CL-1 on every lockstep
tier and on `strict` by GATE-TRAC-01 (part M2); CL-H as the referee's specification on `referee`, a row with no
gate that is `admitted` whenever the referee step (BD-080) is in the build; CL-H on `strict` and as a batch law
on `batch-cpu` by GATE-TRAC-09 (part M5; its GPU rows part M6), with `kill = "KILL-HARDCONTACT"` on the
lockstep rows only (that fallback keeps CL-H as a model-form arm under `strict`); CL-2 on
`batch-cpu` after its pilot and a recorded pass of the battery rows under it; CL-M on the tiers of CL-1, with
CL-1's gate parts, labelled parity-only; the film row by GATE-TRAC-05 (lockstep rows with `kill = "KILL-FILM"`);
soil, belt and tyre laws by GATE-TRAC-08 (with `kill = "KILL-SOIL"`).

**Refusal.** Any verb that creates an environment with `--law <id>` (for example `sim.run`) checks the table
at plan admission (`admit` of N16a-02), after the profile-by-tier matrix (`FROB-REF-222`) and before the build
check (`FROB-REF-724`, an admitted pair whose step is not in the build). DESIGN order: a law that is
`not-built` on a tier refuses with 246 naming that status, not with a generic capability error.
Not admitted → `FROB-REF-246`, "Law not admitted", exit code 3, `observed` = (law, tier, profile, status),
`required` = the gate that must pass, `retry` = `after-change`, ranked repairs: (1) the admitted law for that
tier and profile; (2) `--profile strict` on `batch-cpu` where the law is admitted there. A law of status
`fallback` names the fallback in the message.

**Requested and default laws (DESIGN).** The check is made for the law a request names (`--law <id>`; plan
§18.14: "a law requested on a tier or profile where its gate has not passed"). A request that names no law runs
the default law of its (tier, profile), chosen by `admit` (N16a-02), and a named law equal to that default is
treated the same way: the cell's status is written into the manifest and the evidence block; on a `pending` cell
the run proceeds and every result carries the condition `law-pending` with the gate and part (the runs by which
BD-161 and BD-168 measure GATE-TRAC-01 are such runs, so the gate can be measured before its part is recorded);
on a `failed`, `fallback` or `not-certified` cell the default is refused with 246 exactly as a named law is.
Reason: a measurement must run before its record exists, and a recorded failure must not be run around.

**Measuring runs of a pending cell (`--conformance-admit-pending <gate>`, DESIGN).** A gate part is measured by
runs of the cells it admits, so a named, non-default law on a `pending` cell must be runnable by those runs and by
nothing else. A binary built with the feature `conformance` (VERBS-sim's table of conformance-build-only inputs;
in a release build the input is absent from the schema and answers `FROB-REF-802`) accepts
`--conformance-admit-pending <gate>` on `sim.run`: the named law is admitted on a cell whose status is exactly
`pending` and whose admission row names that gate; on a cell that is `failed`, `fallback`, `not-built` or
`not-certified`, or whose row names another gate, the check returns 246 as it does without the input. The input
is written into the manifest and `StepPlanId`, so such a run never shares an identity with an ordinary one, and
every result carries `law-pending` with the gate and part. The beads that measure GATE-TRAC-09's batch and device
rows (N18a-40, BD-386, N18ax-02, N18ax-03) and CL-2's rows (N18a-18) name it in their measuring runs and assert
246 without it. A law of status `not-certified` adds to `observed` the definition
hash that has no receipt, and its repairs are ranked (1) regenerate and check the certificate, (2) the admitted
law, (3) the referee (N18-REF's row; the same law stays usable on the referee).

**INV-TRAC-01 as a registration rule.** "Every law on a lockstep tier is a convex potential, or is CL-H and
reports its residual." Enforced three ways: (1) a law of kind `convex-potential` must supply a potential whose
Hessian block is positive semidefinite by construction (a sum of positive semidefinite terms; theorem card
T-08), with a property test over its parameter range; (2) a law of kind `complementarity` must write its
natural-map residual ‖λ − Π_𝒦(λ − û)‖ into every step receipt, and a receipt without it fails schema
validation; (3) the registry loader rejects a lockstep admission row for a law that is neither.

**Verb.** `contact.laws`, kind `read`, first milestone M1, cluster `contact`, MCP tool `contact_laws`,
capability `contact:read`, chapter refusal `FROB-REF-246`: these are the fields of its row in the registry of
record (VERBS-contact), which this bead implements and does not redefine (registry example: `frob contact laws
--tier referee --json`). Idempotent, static cost.

- Input `frob.contact.laws.in/1`: optional `tier`, `profile`, `law`, `design` (to show the laws and cards a
  design's end effectors bind).
- Output `frob.contact.laws.out/1`: per law its kind, tier label, parameters by class with units; per (tier,
  profile) the status, the gate and the receipt of its PASS; the default law per (tier, profile); for a design,
  per end effector the bound law, r_eff source and (from M2) the interface cards with provenance; the
  stiffness-admission figure where one exists.
- At M1 the table has the referee rows populated and every batched row `not-built` or `pending`; the verb's
  shape does not change later.
- Evidence: *pass-through*, as the registry row states: the verb passes through the claim product of the
  stored objects it reads (gate receipts, cards) and adds no claim of its own; the read itself is `exact`.

## Acceptance criteria

- [ ] `frob contact laws --json` lists the four laws with parameters split into physical and numerical, and the
      admission table per tier and profile with gate and status.
- [ ] The law-admission check returns `FROB-REF-246` for (CL-H, `batch-cpu`, `lockstep`) before GATE-TRAC-09 has
      a recorded PASS, with both repairs, and admits it after a PASS is recorded in a fixture registry; (CL-2,
      `referee`) returns it with status `not-built`. The check is the function that plan admission calls, reached
      from the command line by `sim.run --law`, an input of this bead at M1 (VERBS-sim; N16b-25 admits it on every
      tier at M2): this bead's script asserts the referee forms (`--law CL-2 --tier referee` → 246 with
      `not-built`; a misspelt `--law CL-9` → 802; `--law CL-H --tier referee` runs), and N18b-30 asserts the
      `batch-cpu` form (`--law CL-H --tier batch-cpu --profile lockstep`) at M2.
- [ ] A request that names no law (or names the cell's default) on a `pending` cell runs with `law-pending`, the
      gate and the part in its manifest and results; on a `failed` cell it returns 246. With
      `--conformance-admit-pending <gate>` in a `conformance` build, a named law on a `pending` cell whose row
      names that gate is admitted, labelled `law-pending`, with the input in the manifest and `StepPlanId`; any
      other status or gate still returns 246; a build without the feature has no such input (802).
- [ ] Status is computed from the gate registry by the five-step rule: a fixture gate registry flips a cell
      only through the part its row names; a tier with no results under a passing part stays `pending`; a
      `status` key written into the law registry is rejected by the loader (`law-status-hand-edited`), so a
      hand edit cannot change admission.
- [ ] With a certificate lookup given (step 1a), a lockstep cell of a convex law without a receipt for its
      current definition hash is `not-certified` even under a passing gate part, and the check returns
      `FROB-REF-246` with that status, the hash and the three repairs in order; the real receipts and the
      plan-admission test on them are N12-51's (`uncertified_law_not_admitted`).
- [ ] The law check sits between the matrix and the build check: (CL-H, `gpu-cuda`, `strict`) gives
      `FROB-REF-222`; (CL-2, `referee`, `referee`) gives 246 with `not-built`, never 724.
- [ ] INV-TRAC-01: the property test passes for every registered convex law; a planted non-convex potential
      (a friction term with a negative curvature region) fails registration; a lockstep admission row for a law
      that meets neither branch of the invariant is a load error; a CL-H receipt without a residual fails
      schema validation.
- [ ] The law identity appears in `StepPlanId`: two step plans built by plan admission that differ only in the
      law have different plan identities, and the `--law CL-H --tier referee` run of this bead's script carries
      the law in its manifest and `StepPlanId`.
- [ ] The verb is in `registries/verbs.toml`, served by CLI and MCP from that entry, with examples and its
      refusal list.

### Known answers and negative controls

CX-181 (the convex associated model is not Coulomb friction: dropping μ·‖u_T‖ gives a sliding contact a
separation velocity μ·‖u_T‖; CL-1 has that artifact in compliant form), which is why the law identity must
travel with every result. Negative controls: silent substitution of the default law for a refused one; a
hand-edited `admitted` status; the non-convex planted law.

## Considerations

- OPEN-KIN-4: which law the `strict` profile runs by default once CL-H is admitted (default CL-1 with located
  events, CL-H as a named variant); the table's default column is where that decision lands.
- KILL-CONTACT changes the default law of the lockstep tiers to CL-2 at a published lower throughput (N18b-33);
  the default column and every `StepPlanId` built from it change with it, and that is recorded as an ADR.
- The registry is read by a verb and checked by a refusal, which is the condition for a registry to exist at
  all; it holds no data that the gate registry already holds.
