## Background

On the throughput tiers everything static is a distance field: a scene compiles to a signed-distance field that
answers "how far, and which way" in constant time for any query point, which is what thousands of worlds need
(decision ADR-TRAC-01). The field is stored in **bricks**: small dense blocks of samples (8³ voxels), reached
through a directory. Two storage designs are on the table:

- **Dense bricks**: a dense directory of brick slots per scene variant over a shared brick pool, with a coarse
  outer level so that empty space far from surfaces costs little. Solid tier; the default.
- **A sparse brick tree**: a hierarchy that stores bricks only near surfaces. Frontier.

Open question OPEN-TRAC-1: **dense bricks or a sparse brick tree for interior scenes at 1 cm resolution.**
Default: dense bricks with a coarse outer level; revisit with measured memory at M3. Owner: Traction lead. It
blocks nothing: the default is fully specified and every gate runs on it.

Why it is open: memory. FACT (arithmetic, to be re-run on compiled packs): a dense directory with 4-byte slots
is 63 × 63 × 19 = 75,411 slots (0.3 MB) for a 10 × 10 × 3 m interior at 2 cm; 587,500 slots (2.3 MB) for a
60 × 40 × 8 m warehouse at 4 cm; 18.8 MB for that warehouse at 2 cm. The directory is under 1.5% of the scene it
indexes, so the directory is not the issue; the bricks are. At 1 cm the brick count grows by about eight
against 2 cm in the worst case, and whether the dense pool with a coarse outer level still fits the device
budget alongside a resident world bank is unmeasured. A related rejected idea stays rejected: minimal perfect
hashing or succinct structures for the directory add a second, verifying read to every lookup for no memory
that matters.

The dense layout in numbers: a coarse lattice over the whole scene (16 cm indoors by default); a fine level at
one eighth of that (2 cm) that exists only in band bricks, 8³ fine samples (1,024 bytes of distances plus 128
bytes of region labels) for each coarse cell within the truncation distance of a surface; and a per-variant
directory with one 32-bit pool slot per coarse cell. Halving the fine spacing to 1 cm (to hold smaller features
without overlays) makes the coarse spacing 8 cm, gives the directory eight times as many cells and the band
about four times as many bricks.

Predicted magnitudes (DESIGN arithmetic from stated assumptions, to be checked, not results): a 10 m × 10 m ×
3 m room has about 320 m² of surface; with a band two coarse cells thick that is about 25,000 bricks (28.8 MB)
at 2 cm and about 100,000 bricks (115 MB) at 1 cm. A 50 m × 30 m × 6 m floor of a plant at 8 cm coarse spacing
has 17.6 million directory cells, 70 MB per scene variant before any brick, so at 1 cm the statement that the
directory is not the issue is itself one of the things measured.

This bead is the experiment that settles the question by measurement at M3, when the interior archetypes and
their compiled packs exist. It doubles as the paper-scale pilot the Frontier tree needs before any work on it
is funded, and is registered as one.

## Scope

In: the measurement on real compiled packs (directory, bricks, labels and overlays counted separately); a
paper-scale prototype of the sparse tree on the host, sufficient to measure its memory and lookup cost; the
paired narrow-phase stage timing on `batch-cpu`; the decision record. This is the only bead for OPEN-TRAC-1:
an earlier draft of the same experiment (N18a-09) is superseded by this bead and its content is folded in here.

Out: building the sparse tree as a production path (a Frontier mechanism that would need its own kill gate if
the decision goes that way, with this measurement as its pilot); the scene compiler; the brick pool itself;
the world bank's admission arithmetic (BD-236).

## Technical approach

**Registration.** The question, the decision rule below and the scene identities are registered in
`frob-conformance/registry/pilots.toml` before anything is measured.

**What is measured (on `batch-cpu`, from compiled packs; no simulation needed for memory).**

1. For each of the seven interior archetypes compiled at 2 cm and at 1 cm (and the warehouse at 4 cm for
   reference): the number of bricks that hold a surface within the truncation band, the number of bricks in
   the dense pool including the coarse outer level, directory bytes, pool bytes, label bytes, the overlay
   count, the occupancy (band cells over all coarse cells) and total bytes per scene variant, each read from
   the pack manifest and the buffer sizes. Field values are stored in a narrow band with a per-brick scale
   (sixteen bits over a ±10 m range would resolve only 0.3 mm, which is 30 N at a stiffness of 10⁵ N/m), so
   bytes per brick are those of the quantized band representation.
2. The same scenes in the prototype sparse tree: node bytes, brick bytes, total. The prototype (DESIGN) is a
   two-level tile tree over the same bricks, built on the host: a root table of 32³ tiles pointing at 8³
   directories only where the band is non-empty, so a lookup is two dependent loads where the dense directory
   needs one.
3. Lookup cost: mean and worst-case memory reads per field query at a boundary cell (the dense design needs up
   to eight directory lookups for a query in a boundary cell when bricks carry no apron) and per query in the
   sparse tree (depth of descent), measured with the narrow-phase kernel's reference path on 10⁶ query points
   sampled from robot trajectories of the battery.
4. Fit against budgets: bytes per scene variant times the number of resident variants of the world bank at its
   admission cap, against the device memory budget on each machine class. Device memory, not host memory, is
   the binding constraint.
5. Stage time: the narrow-phase stage timed on `batch-cpu` with each directory on the reference quadruped and
   humanoid batteries, as a paired measurement on identical worlds.

**Decision rule (DESIGN, fixed before measuring).** Keep dense bricks (the default) unless both hold: (a) at
1 cm the dense design for the largest interior archetype exceeds the per-variant memory share that the
world-bank admission cap allows on the smaller device class; and (b) the sparse tree reduces total pack bytes
by at least a factor of two on at least two archetypes, at no more than 1.5 times the reads per query and no
more than 10% more narrow-phase stage time. If only (a) holds, the answer is "dense
bricks, 1 cm restricted to regions of interest (analytic overlays and thin primitives elsewhere)". If both
hold, the sparse tree is proposed for those archetypes as a Frontier mechanism with this measurement as its
pilot and with its own kill gate, and the dense design remains the fallback.

**Record.** An ADR with the measured table, the decision, the alternatives, and what would reopen it (a new
device class, a change of brick size, scenes above warehouse scale).

## Acceptance criteria

- [ ] The memory table exists for the seven interior archetypes at 2 cm and 1 cm, for both storage designs,
      from compiled packs whose `SceneId`s are recorded.
- [ ] Reads per query are measured for both designs on 10⁶ trajectory-sampled points, and the two narrow-phase
      stage times are measured as a pair on identical worlds.
- [ ] The table has one row per archetype and spacing with directory, brick, label and overlay bytes, the
      occupancy, the tree bytes, and the bytes against the default device budget.
- [ ] The predicted magnitudes of the Background are compared with the measured ones and the differences are
      explained.
- [ ] The dense and tree directories return bit-identical field values and region labels at 10⁶ sample points
      per scene.
- [ ] The decision rule was registered before measuring; the ADR states the decision and cites the table.
- [ ] If the decision keeps dense bricks, nothing changes and the default is confirmed in the registry of open
      questions as decided; if it proposes the sparse tree, a pilot bead and a kill gate are opened before any
      production work.
- [ ] The arithmetic FACTs above are reproduced from the compiled packs (directory slot counts for the two
      reference scenes).

## Test plan

### Unit tests

`crates/frob-scene/tests/brick_memory.rs` (host).

- `directory_slots`: 10 × 10 × 3 m at 2 cm with 8³-voxel bricks → 63 × 63 × 19 = 75,411 slots (0.3 MB at
  4 bytes); 60 × 40 × 8 m at 4 cm → 188 × 125 × 25 = 587,500 slots (2.3 MB); at 2 cm → 375 × 250 × 50 =
  4,687,500 slots (18.8 MB).
- `band_brick_count`: on a synthetic box room the number of surface bricks scales with surface area over brick
  face area, within 20%.
- `sparse_equals_dense`: the prototype tree returns the same field values as the dense design on 10⁶ points
  (bit-identical where both store the same brick).
- `reads_per_query`: counted reads match the analytic maximum (eight directory lookups at a boundary cell with
  no apron).
- `dense_bytes_match_manifest`: the counted bytes equal the manifest's figures.
- `occupancy_arithmetic`: a `synthetic` empty box room of known dimensions gives the brick count predicted by
  surface area over coarse-cell area, within one layer.

### End-to-end script and logging

`scripts/e2e/open_trac_1.sh` (helper of STD-E2E): `frob scene gen` and `frob scene compile` for each of the
seven archetypes at both resolutions, `frob scene show --json` for the memory figures, the measurement binary
for reads per query, and the paired stage timing through `frob sim run --tier batch-cpu`. Metrics logged with
their thresholds: `tree_saving_ratio` against 0.5, `reads_ratio` against 1.5, `stage_time_ratio` against 1.10.
Generated scenes only; no private-scene data. NDJSON lines
carry command, exit code, wall time, `SceneId`, bytes by component for each design, reads per query, the budget
comparison, and the decision the rule returns. `summary` states the decision.

### Known answers and negative controls

The directory arithmetic above. Negative control for the comparison: a sparse tree that silently drops bricks
far from the sampled trajectories would look small; `sparse_equals_dense` on uniformly sampled points (not only
trajectory points) must catch it. A tree prototype that drops empty tiles incorrectly must fail the same
bit-identity test, and a measurement at one spacing presented as both must be caught by the scene-identity
check.

## Considerations

- A related open question asks whether bricks should carry a one-sample apron, which removes neighbour lookups
  and costs 42% more memory (default: no apron); this experiment reports the reads that question depends on.
- The decision is about memory, not accuracy: both designs store the same samples with the same interpolation
  bound.
- Thin features (thinner than two fine voxels) are routed to thin primitives or the mesh path whatever the
  storage; a finer brick is one of the repairs of the thin-feature refusal and its memory cost is what this
  experiment quantifies.
- Fail-closed default: dense bricks; a `finer brick` repair for a thin feature is priced with these numbers.
- A tree breaks nothing in determinism if its iteration order is fixed. FACT (to be re-checked at the pinned
  commit before it is cited): the sibling suite's sparse tile tree has a deterministic iteration order.
