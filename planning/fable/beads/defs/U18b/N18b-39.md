## Background

At a converged step of the convex contact solve, the Hessian H = A + JᵀGJ has been factored. A **response
batch** reuses that factor to solve many right-hand sides at once: counterfactual impulses ("what if this foot
were pushed by 1 N·s?"), adjoint columns, the columns of a finite-difference design stencil at one state. It
is a Frontier mechanism and a diagnostic query, not a stepping path. Against a baseline that also factors once
it saves nothing in flops; what it adds is a certified error bound per column and a guard that sends any
column crossing a stick, slip or open boundary back to the full solve. Against a full re-solve per query the
flop ratio is about 14 for 64 columns at 96 rows, and only for queries of that shape.

The mechanism's first paragraph left four things unspecified: the identity a batch is bound to, the tests a
column must pass, the source of the eigenvalue bound, and a gate. This bead specifies and builds the first:
the **anchor**.

The danger an anchor removes is silent staleness. A factor is valid for exactly one matrix. If the
configuration, the mass matrix, the constraint Jacobian, the regularization, a cone parameter or the active
set changes, the stored factor answers a different question, with no error and a plausible number. A batch is
therefore keyed by an anchor digest over everything its factor depends on, at one converged step of one world,
and is served only against the anchor it was factored for. Any other request refactors, or is refused.

## Scope

In: the anchor's contents and digest; its capture at a converged step; the check on every batch request; the
stale-anchor refusal; anchor lifetime. Out: per-column acceptance (N18b-40); the eigenvalue certificate
(N18b-41); the verb, factor reuse and the reroute pilot (BD-367); the gate measurement (N18b-42).

## Technical approach

**What the anchor covers (DESIGN).** At one converged step of one world, the digest is BLAKE3 over a canonical
serialization of:

1. the world address, the step index and the `commit_epoch` of the committed state the step started from;
2. the configuration q (all generalized positions) as raw bits;
3. the mass matrix term A as raw bits (lower triangle, the capacity's real block);
4. the constraint Jacobian J for every active row group (raw bits, in row order), with the row-to-contact map;
5. the regularization: the proximal or compliance terms entering G, and the diagonal scaling exponents of the
   stage-8 scaling;
6. the cone parameters per row group (μ, anisotropy, r_eff, lagged coefficients of film, tyre or soil rows as
   they were held inside that solve);
7. the **active set with a mode label per row**: `open`, `stick` or `slip` for friction rows; active or
   inactive for unilateral rows (limits, backlash);
8. the `StepPlanId` (which fixes the contact law, the precision profile and the iteration count), the
   `ModelId` and the kernel versions.

Items 3 to 6 determine H; item 7 determines the frozen set on which the linear response is defined; items 1, 2
and 8 bind the anchor to one moment of one world under one plan. The serialization is fixed-order and
length-prefixed so that two different anchors cannot collide by concatenation.

```rust
// DESIGN sketch
pub struct ResponseAnchor {
    pub id: AnchorId,                 // BLAKE3 of the canonical serialization
    pub world: WorldAddr, pub step: u64, pub commit_epoch: u64,
    pub step_plan: StepPlanId, pub model: ModelId,
    pub active: ActiveSet,            // per row: Open | Stick | Slip | LimitActive | LimitInactive
    pub factor: FactorHandle,         // the Cholesky factor of the scaled Hessian, owned by the anchor
    pub precision: Precision,         // precision of the step that produced the anchor
}
```

**Capture.** An anchor is taken only from a step that converged (final scaled gradient norm at or below the
plan's tolerance) and was not flagged `Degraded`. A request to anchor an unconverged or degraded step is
refused, because the factor then belongs to an iterate, not to the solution. The capture copies the factor
and the active set out of the step's buffers at the commit fence (the same fence that snapshots use), so a
later step cannot overwrite them.

**Serving.** Every batch request names an `AnchorId`. The server recomputes nothing: it compares the named
identity with the identity of the anchor it holds. If they are equal the batch is served against the stored
factor. If the request instead names a world state (address, step) without an anchor, the server captures a
fresh anchor (re-running the step to convergence from a snapshot if needed), factors, and returns the new
`AnchorId` with the result. If the request names an anchor that no longer matches the state it is asked about
(the caller passes a state digest alongside, or the world has advanced and the caller asks for "current"),
the request refactors when the caller allowed it (`on_stale: refactor`, the default for interactive use) and
is refused otherwise.

**The refusal.** "Response batch requested against a stale anchor": raised when a batch is requested against
an anchor other than the one it was factored for and the caller did not allow refactoring. It has no code in
the refusal registry at the time of writing; this bead appends one in the `2xx` family (numerics and
integrator admission). Exit code 3; `observed` = the requested anchor and the first component that differs
(configuration, mass matrix, Jacobian, regularization, cone parameters or active set); `required` = the
current anchor identity; `retry` = `after-change`; ranked repairs: (1) refactor for the new anchor
(`on_stale: refactor`); (2) request against the current anchor.

**Lifetime and memory.** An anchor owns one factor (n_v² entries) and one active-set record; anchors are held
in a bounded per-job table (DESIGN default 64) with least-recently-used eviction, and an evicted anchor is
simply stale. Nothing about a response batch is written into stepping state, so serving batches cannot change
a world's digests.

## Acceptance criteria

- [ ] `ResponseAnchor` and its canonical digest exist in `frob-contact`; the digest changes when any single
      covered component changes (one test per component) and is unchanged by a run of the same step twice.
- [ ] An anchor can be captured only from a converged, non-degraded step.
- [ ] A batch requested against a changed anchor is refused (the last clause of GATE-TRAC-11), or refactored
      when the caller allowed it, and the response names which component changed.
- [ ] Serving batches leaves the world's state digests unchanged (bitwise) and does not perturb later steps.
- [ ] The refusal is registered with a new code, exit code 3 and both repairs.
- [ ] Anchor capture and serving are cancellable without leaking the factor buffer.

## Test plan

### Unit tests

`crates/frob-contact/tests/response_anchor.rs`.

- `digest_sensitivity`: flipping one bit of q, of A, of J, of a regularization term, of μ, or one mode label
  (stick to slip) each changes the digest; reordering two row groups changes it (order is part of identity).
- `digest_stable`: the same world, step and plan produce the same `AnchorId` twice and across worker counts.
- `no_concatenation_collision`: two serializations that differ only in where a boundary between fields falls
  have different digests (length prefixes).
- `capture_requires_convergence`: an unconverged step and a `Degraded` step are refused.
- `stale_refused`: advance the world one step, request against the old anchor with `on_stale: refuse` → the
  refusal, naming `configuration` as the first differing component.
- `stale_refactors`: the same with `on_stale: refactor` → a new `AnchorId` and a served batch.
- `serving_is_side_effect_free`: digests of 100 subsequent steps are identical with and without a batch served
  between them.
- `eviction_makes_stale`: the 65th anchor evicts the first; a request against it is stale.

### End-to-end script and logging

Covered by `scripts/e2e/contact_response.sh` (bead N18b-42), stage `anchor`: `frob contact response` against a
fresh state (returns an anchor), again against the same anchor (served), then after `frob sim run` advances
the world (refused, exit 3) and with `--on-stale refactor` (served under a new anchor). NDJSON lines carry
command, exit code, wall time, the `evidence` block, anchor identities, the differing component and the
refusal block.

### Known answers and negative controls

The clause of GATE-TRAC-11: "a batch requested against a changed anchor is refused". Negative controls: an
anchor keyed by (world, step) only, which serves a stale factor after a parameter edit and must be caught by
`digest_sensitivity`; a server that silently refactors when the caller asked for refusal.

## Considerations

- The active set in the anchor is the set at convergence under the law's regularization; a row inside its
  stiction band is `stick`. Its definition must match the one the per-column guards use, or the two beads
  disagree about what "crossing a boundary" means.
- Kill gate KILL-RESPONSE (guards reroute more than half the columns on battery states; or a bound violation
  or a false mode acceptance that survives one repair cycle) falls back to full solves per query; anchors are
  then unused and removed.
- The precision recorded in the anchor matters: the acceptance tests of a column are evaluated in the precision
  of the step that produced the anchor.
