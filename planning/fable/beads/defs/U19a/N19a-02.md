## Background

Agents reach Habitat only through verbs of the `frob` command line and the MCP server; both surfaces are generated
from one verb registry. Each Habitat verb is implemented by the bead that owns its mechanism. What no mechanism bead
owns is the family as a whole: that the registry lists exactly the verbs below, each with its kind, its first
milestone and the shape of what it returns, that a verb which has not yet landed is visibly "not implemented"
rather than absent, and that the four verbs which can run long behave as long tools. This bead owns that.

Terms. A verb's kind is `read` (changes nothing), `run` (spends compute, takes an idempotency key and a budget,
accepts a bounded synchronous wait), `mutate` (changes a named object) or `admin`. The bounded synchronous wait
(`sync_wait_ms`) is how a long tool behaves: it waits up to the stated time and, if the work is not finished,
returns a job handle with exit code 8 ("accepted and still running", not a failure). Reason for the rule (DESIGN):
most studio verbs finish inside the wait, and a script must be able to tell "done" from "admitted and running"
without parsing the result.

## Scope

In: Habitat's side of the family: the map from each registered scene verb to the bead and handler that
implement it; the dispatch table of `frob-scene` and the test that it and the registry rows agree one to one;
the long-tool behaviour of the cluster's `run` verbs, with the progress denominators of the four that can run
long; `scene.list` as an MCP resource.

Out, with the bead that has it: the registry rows themselves. The registry bead VERBS-scene, a dependency, is the
only bead that enters rows of cluster `scene` in `registries/verbs.toml`: the thirteen entries, their kinds,
first milestones, schema names, capability scopes, refusal lists, examples, MCP tool names, the answer of a verb
before its milestone, and the parity, conformance and schema-snapshot checks. This bead was drafted with its own
copy of twelve rows and now enters none; the table below is the handler map, and where its kind or milestone
column repeats a row it is that row's value. Also out: each verb's mechanism (named per row below), the MCP
clustering of all verbs (BD-298), `scene.purge` (the thirteenth row: implemented by the privacy bead N37-19,
extended by BD-305, as the registry row records).

## Technical approach

1. The handler map. The rows are in `registries/verbs.toml`, entered by VERBS-scene (the registry loader is
   `frob-verbs`); this bead registers one handler in `frob-scene`'s dispatch table per row and records which
   bead supplies it:

| `scene.gen` | run | M2 terrain, M3 interiors | A pack from (family, parameters, seed) | BD-165, BD-225, BD-226 |
| `scene.compile` | run | M2 | A pack from source geometry, with compile receipts | BD-163 |
| `scene.import` | run | M3 assets, M5 real places | A pack with a loss report, a scale label and an unknown mask | N19a-46 (assets), BD-398 (real places) |
| `scene.accept` | run | M3 | The acceptance report | BD-228 |
| `scene.list` | read | M2 | The scene catalog (also an MCP resource) | BD-163 |

| `scene.hazards` | read | M3 | The hazard registry of an archetype with the provenance of every dimension | BD-227 |
| `scene.fit` | run | M3 | A feasibility witness, an impossibility cut or `unresolved` for a footprint family and a route | N19b-32 (capstone BD-233), BD-398 (real places, M5) |
| `scene.retrofit` | run | M3 in the row, answering from M4 (the chapter's verb table and the appendix print M3, and VERBS-scene keeps `first_milestone = "M3"` because that field is pinned to the appendix; the gate register places GATE-HAB-11 and the retrofit catalog at M4, so the handler lands with BD-369 at M4 and the verb answers `FROB-REF-724` until then, as a declared late row) | The cheapest building amendment that flips a failing verdict, beside the cheapest redesign | N19b-40 (capstone BD-369) |

| `scene.bank` | read, admin | M3 | The resident set on a device, an admission estimate, eviction | BD-236 |

   (`scene.list` and `scene.show` are two verbs; the family is eleven rows in the chapter's table and twelve verb
   names. With `scene.purge` the registry cluster has thirteen rows.)
2. Schema names, refusal lists, capability scopes and worked examples are fields of the rows and are VERBS-scene's.
   The schema names are `frob.scene.<verb>.in/1` and `frob.scene.<verb>.out/1` by the registry's rule; this
   bead's draft had named them `frob.scene.gen.request/1` and `frob.scene.gen.result/1`, which are not used.
3. Long tools. Every verb of kind `run` accepts `sync_wait_ms` (default 5,000, maximum 30,000, 0 for an
   immediate handle; out of range is `FROB-REF-802`, exit 3; on the CLI the default is to wait to completion with
   progress events and `--sync-wait-ms` bounds the wait), so in this
   cluster `scene.gen`, `scene.compile`, `scene.import`, `scene.accept`, `scene.fit` and `scene.retrofit` do.
   Four of them can run long and are the ones this bead gives a progress model: `scene.gen`, `scene.compile`,
   `scene.fit` and `scene.retrofit`. Within the wait they return the full envelope (exit 0 or 2); otherwise an
   envelope whose `job` block carries `id`, `state`, `progress {done, total, unit}`, `eta_s` with its interval,
   `poll_after_ms` and `last_committed`, with exit 8. Progress always has a denominator (stages completed of
   eleven for a compile; scenes of N for a batch gen; route cells decided of the total for a fit; kits tried of
   the catalog's candidates for a retrofit).
4. A verb whose handler is not in the build is present in the registry and returns exit 5 with `FROB-REF-724`,
   one envelope, on both surfaces, and `frob capabilities --json` lists it as absent; it is never an unknown verb.
   Whether a verb answers is decided by its handler being in the build, never by comparing the build's milestone
   with the row's `first_milestone` (the registry's rule, NJL-01): `scene.retrofit` shows why, since its row says
   M3 and its handler lands at M4. The refusal's `required` field names the milestone at which the implementing
   bead lands (M4 for `scene.retrofit`, read from the handler map above, not from the row). The rule and its check
   per row are VERBS-scene's; this bead's dispatch table supplies the landing milestone and tests two cases.
5. Every result carries the envelope's `evidence` block (claim kinds, class, tier, determinism, identities, seed)
   and, on exporting verbs, the three no-authorization flags, each `false`.
6. `scene.list` is also exposed as an MCP resource; private packs are absent from it.

## Acceptance criteria

- [ ] The dispatch table of `frob-scene` has exactly one handler for each of the twelve Habitat rows of cluster
      `scene` in the registry (the thirteenth, `scene.purge`, is handled by the privacy bead N37-19), with the kinds and
      milestones of those rows; this bead adds no row to `registries/verbs.toml`.
- [ ] Each of the four long verbs declares its progress unit and denominator in its handler (`stages` of 11 for
      `scene.compile`; `scenes` of N for a batch `scene.gen`; `cells` of the route total for `scene.fit`; `kits`
      of the candidates for `scene.retrofit`), and the long-tool adapter turns a handler that outlives
      `sync_wait_ms` into an exit-8 envelope with the `job` block. `scene.import` and `scene.accept` accept
      `sync_wait_ms` as every `run` verb does. The behaviour on a real compile (exit 8, `job.wait`, the same
      `SceneId` as a waited run) is asserted by N19a-42, because the compile handler (BD-163) lands after this
      bead and depends on it.
- [ ] A verb whose handler is not in the build exits 5 with `FROB-REF-724` naming the milestone at which its implementing bead lands (`scene.probe-request`: M5; `scene.retrofit`: M4, although its row's `first_milestone` is M3).
- [ ] Every scene verb's envelope validates against `frob.envelope/1` and carries `evidence`.
- [ ] The registry conformance test fails if a verb is added to the code and not to the registry, or the reverse.

## Test plan

### Unit tests

- `scene_handlers_cover_registry_rows`: loads the registry's cluster `scene`; asserts that the handler set of
  `frob-scene` equals the twelve Habitat rows and that each handler's kind is its row's.
- `run_verbs_accept_sync_wait`: `sync_wait_ms` is accepted by the six `run` verbs of the family and by no `read`,
  `mutate` or `admin` verb; `long_tools_have_progress_model`: exactly `scene.gen`, `scene.compile`, `scene.fit`
  and `scene.retrofit` declare a progress unit and denominator.
- `unlanded_verb_refuses_with_milestone`: invokes `scene.probe-request` in an M2 build; expects exit 5,
  `FROB-REF-724` and M5 in `refusal.required`; invokes `scene.retrofit` in a build without its handler; expects
  M4 there (the landing milestone of BD-369), not the row's M3.
- `registry_code_bijection` (negative control): a test build with one handler unregistered fails.
- `progress_has_denominator`: the declared progress model of `scene.compile` has unit `stages` and total 11; of
  `scene.fit`, unit `cells`; every declared total is positive.
- `adapter_returns_job_after_wait`: the long-tool adapter driven by a handler that blocks on a test barrier
  (a real handler of the test build, not a mock of the adapter) with `sync_wait_ms = 0` yields exit 8 with `job.id`,
  `progress {done, total, unit}` and `poll_after_ms`; with the barrier released before the wait ends it yields
  the handler's own exit.
- `sync_wait_bounds`: `sync_wait_ms` above 30,000 or negative is refused with `FROB-REF-802` (exit 3); absent
  on MCP, the default is 5,000; on the CLI the default is to wait to completion with progress events, and
  `--sync-wait-ms` bounds the wait.

### End-to-end script and logging

`scripts/e2e/scene_verb_family.sh` (sources the `STD-E2E` helper): `frob --json capabilities` and asserts the
thirteen rows of cluster `scene` with their kinds and milestones; `frob --json schema frob.scene.<verb>.in/1` for
each of the twelve Habitat verbs (exit 0, the schema printed); each verb that `frob --json capabilities` lists as
absent invoked once with a minimal valid input (and `--key svf-<verb>` for a `run` or `mutate` verb), expecting
exit 5 with `FROB-REF-724` and the landing milestone named; `frob
--json scene list` expecting exit 0 (an empty or fixture catalog once BD-163 lands; exit 5 before). Logs per
step: `cmd` (exact command line, exit code, wall time), `assert` (expected and observed exit codes, the refusal
code and milestone, row counts), the envelope's `evidence` block, and the final `summary` with counts. The compile
leg with `--sync-wait-ms 0`, `job wait` and the identity comparison runs in `scripts/e2e/scene_compile.sh`
(N19a-42).

### Known answers and negative controls

Known answer: thirteen registry rows in the cluster, twelve with handlers here. Negative controls: the
unregistered handler; a handler whose declared kind differs from its row (the bijection test names it); a
progress model with total 0 (refused by the adapter's check). Determinism lane: the script runs twice and
compares the two logs' digests.

## Considerations

- `scene.retrofit` is printed at M3 in the chapter's verb table while the gate register places its catalog and
  its gate (GATE-HAB-11) at M4. The register governs when the capability is due; the registry row keeps the
  appendix's `first_milestone = "M3"` (VERBS-scene, correcting an earlier text that entered M4: the field is
  pinned to the appendix, whose per-milestone counts are known answers), the row is one of the declared late rows
  of the coverage check, and until BD-369 lands the verb answers `FROB-REF-724` naming M4.
- If KILL-RETROFIT fires the search verb is withdrawn; the registry row is then removed by an ADR, not left as a
  permanent exit 5.
- The limit of seven verbs per MCP task cluster means the scene family spans two clusters; clustering is BD-298.
