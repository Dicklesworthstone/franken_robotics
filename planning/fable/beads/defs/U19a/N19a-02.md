## Background

Agents reach Habitat only through verbs of the `frob` command line and the MCP server; both surfaces are generated
from one verb registry. Each Habitat verb is implemented by the bead that owns its mechanism. What no mechanism bead
owns is the family as a whole: that the registry lists exactly the verbs below, each with its kind, its first
milestone and the shape of what it returns, that a verb which has not yet landed is visibly "not implemented"
rather than absent, and that the four verbs which can run long behave as long tools. This bead owns that.

Terms. A verb's kind is `read` (changes nothing), `run` (spends compute, takes an idempotency key and a budget,
accepts a bounded synchronous wait), `mutate` (changes a named object) or `admin`. The bounded synchronous wait
(`sync_wait_ms`) is how a long tool behaves: it waits up to the stated time and, if the work is not finished,
returns a job handle with exit code 8 ("accepted and still running", not a failure). Reason for the rule (DESIGN):
most studio verbs finish inside the wait, and a script must be able to tell "done" from "admitted and running"
without parsing the result.

## Scope

In: the registry rows, their schemas' names, the long-tool behaviour of four verbs, the not-yet-implemented
behaviour, and a conformance test that registry and implementation agree. Out: each verb's mechanism (named per row
below), the MCP clustering of all verbs (BD-298), `scene.purge` (the privacy bead BD-305).

## Technical approach

1. Add these rows to `registries/verbs.toml` (the registry loader is `frob-verbs`):

| Verb | Kind | First milestone | Returns | Implemented by |
|---|---|---|---|---|
| `scene.gen` | run | M2 terrain, M3 interiors | A pack from (family, parameters, seed) | BD-165, BD-225, BD-226 |
| `scene.compile` | run | M2 | A pack from source geometry, with compile receipts | BD-163 |
| `scene.import` | run | M3 assets, M5 real places | A pack with a loss report, a scale label and an unknown mask | N19a-46 (assets), BD-398 (real places) |
| `scene.accept` | run | M3 | The acceptance report | BD-228 |
| `scene.list` | read | M2 | The scene catalog (also an MCP resource) | BD-163 |
| `scene.show` | read | M2 | A manifest, the hazards drawn, the feasibility tag | BD-163 |
| `scene.hazards` | read | M3 | The hazard registry of an archetype with the provenance of every dimension | BD-227 |
| `scene.fit` | run | M3 | A feasibility witness, an impossibility cut or `unresolved` for a footprint family and a route | N19b-32 (capstone BD-233) |
| `scene.retrofit` | run | M4 (the chapter's table prints M3; the gate register places the catalog and GATE-HAB-11 at M4, and the register governs) | The cheapest building amendment that flips a failing verdict, beside the cheapest redesign | N19b-40 (capstone BD-369) |
| `scene.probe-request` | read | M5 | The measurements that would settle an unresolved answer | N19c-05 (probe design from BD-291) |
| `scene.split` | mutate | M3 | A split over scene groups, with feasibility counts | BD-235 |
| `scene.bank` | read, admin | M3 | The resident set on a device, an admission estimate, eviction | BD-236 |

   (`scene.list` and `scene.show` are two verbs; the family is eleven rows in the chapter's table and twelve verb
   names.)
2. Each row names its input schema and result schema (`frob.scene.gen.request/1`, `frob.scene.gen.result/1`, and so
   on; DESIGN naming), its refusal list (subset of `FROB-REF-301` to `-317`), its required capability scope and at
   least one worked example.
3. Long tools: `scene.gen`, `scene.compile`, `scene.fit` and `scene.retrofit` accept `sync_wait_ms`. Within the wait
   they return the full envelope (exit 0 or 2); otherwise an envelope whose `job` block carries `id`, `state`,
   `progress {done, total, unit}`, `eta_s` with its interval, `poll_after_ms` and `last_committed`, with exit 8.
   Progress always has a denominator (stages completed of eleven for a compile; scenes of N for a batch gen).
4. A verb whose first milestone has not been reached is present in the registry and returns exit 5 with a refusal
   that names the milestone; it is never an unknown verb.
5. Every result carries the envelope's `evidence` block (claim kinds, class, tier, determinism, identities, seed)
   and, on exporting verbs, the three no-authorization flags, each `false`.
6. `scene.list` is also exposed as an MCP resource; private packs are absent from it.

## Acceptance criteria

- [ ] `frob --json verbs --cluster scene` (or the registry dump) lists exactly the twelve verb names with the kinds
      and milestones above.
- [ ] Each of the four long verbs, run with `sync_wait_ms=0` on a fixture that takes longer than zero, exits 8 with
      a job handle; `job.wait` on the handle returns the same result as a run with a long wait.
- [ ] A verb before its milestone exits 5 with a refusal naming the milestone.
- [ ] Every scene verb's envelope validates against `frob.envelope/1` and carries `evidence`.
- [ ] The registry conformance test fails if a verb is added to the code and not to the registry, or the reverse.

## Test plan

### Unit tests

- `scene_family_is_twelve_names`: loads the registry; asserts the exact set and each kind.
- `long_tools_are_four`: asserts `sync_wait_ms` is accepted by exactly `scene.gen`, `scene.compile`, `scene.fit`,
  `scene.retrofit` in this family.
- `unlanded_verb_refuses_with_milestone`: invokes `scene.probe-request` in an M2 build; expects exit 5 and the
  milestone in `refusal.required`.
- `registry_code_bijection` (negative control): a test build with one handler unregistered fails.
- `progress_has_denominator`: a job envelope from `scene.compile` has `progress.total = 11`.

### End-to-end script and logging

`scripts/e2e/scene_verb_family.sh`: for each verb, `frob --json <verb> --help-schema`; then `frob --json scene
compile fixtures/scenes/unit-box.src --sync-wait-ms 0` expecting exit 8, `frob --json job wait <id>`, and a second
run with `--sync-wait-ms 60000` expecting exit 0 and the same `scene_id`. Logs per step: `cmd` (exact command line,
exit code, wall time), `assert` (expected and observed exit codes, the two `scene_id` digests), the envelope's
`evidence` block, and the final `summary` with counts. Fixtures are synthetic and labelled so.

### Known answers and negative controls

Known answer: the two compile runs return one `SceneId` (identity is independent of whether the caller waited).
Negative controls: the unregistered handler; an idempotency key reused with different content must exit 7.
Determinism lane: the script runs twice and compares the two logs' digests.

## Considerations

- `scene.retrofit` first appears at M3 in the verb table while its gate (GATE-HAB-11) is at M4; the registry row is
  M3 and the gate's milestone governs acceptance of the mechanism.
- If KILL-RETROFIT fires the search verb is withdrawn; the registry row is then removed by an ADR, not left as a
  permanent exit 5.
- The limit of seven verbs per MCP task cluster means the scene family spans two clusters; clustering is BD-298.
