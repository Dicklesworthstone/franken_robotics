## Background

A `ScenePack` is the one object every subsystem reads when it touches a world. It is immutable and
content-addressed: its identity `SceneId` is a hash of its content, and any change produces a new identity
(INV-HAB-01). The format bead BD-162 defines the manifest schema `frob.scene/1`, the distance bricks and the range
rule. This bead fixes the complete list of what a pack contains, so that no consumer has to keep scene data
somewhere else, and it implements the parts of that list that no other bead owns: semantic labels, spawn regions,
goals, task regions and route graphs.

Reason for one inventory (DESIGN): a pack that omits, say, spawn regions forces the task layer to store positions
that depend on the scene outside the scene's identity, and then the same `SceneId` can mean two different
experiments.

## Scope

In: the inventory table and its validation (every section present or explicitly absent); the semantic-label,
spawn, goal, task-region and route-graph sections; the interface side of the region table at M2 (a material and a
condition per region, the M2 part of compile stage 7); the manifest example as a round-trip fixture. Out: bricks and
field (the manifest BD-162, the codec N19b-01, emission BD-163), overlays (N19a-16, N19a-17), the optical map, the
two card references of a region and the shared latents with their conditionals (BD-229, N19a-06, M3), fixtures and
movables (N19a-07, N19a-08), per-world state (N19a-09), provenance block (N19a-05), living-world mechanics
(BD-230, BD-231 and the Frontier epics), clearance (BD-233), ingestion fields' producers (BD-398).

## Technical approach

1. **Inventory.** A pack contains, and its manifest declares, each of:

| # | Content | Where it is defined |
|---|---|---|
| 1 | A truncated signed-distance field in bricks, 16-bit, fine near surfaces and coarse everywhere, plus an optional heightfield for open terrain | BD-162, N19a-27 |
| 2 | Analytic overlays: boxes, rounded boxes, wedges, cylinders, periodic bar patterns, each exact to round-off | N19a-16, N19a-17 |
| 3 | Interface map: per surface region a material and a condition (dry, wet, greasy, dusty) selecting contact cards | this bead at M2 (the two fields in the region table); BD-229 from M3 (both card references, latents) |
| 4 | Optical map: per region an optical card; a list of optical volumes with an extinction coefficient | N19a-06, BD-229 |
| 5 | Shared latents: named scalars per region (for example wetness) driving interface condition and optical response through separately recorded conditionals | BD-229 |
| 6 | Semantic labels: room type, object class, traversability class | this bead |
| 7 | Articulated fixtures (doors, drawers, cabinet doors, swing gates, lifts, carts), each with its parameter table | N19a-07 |
| 8 | Movable objects (boxes, totes, chairs, pallets, toys), each with a declared behaviour | N19a-08 |
| 9 | Moving surfaces (conveyors, escalators): contact surfaces with prescribed tangential velocity | N19a-08 |
| 10 | Living-world declarations: film patches, sloshing payloads, cords and rugs, each at a declared tier | schema here; mechanics elsewhere |
| 11 | Spawn regions, goals, task regions and route graphs | this bead |
| 12 | A visual mesh in GLB for the viewer, never read by physics or sensors | N19a-23 |
| 13 | For ingested scenes: a three-valued occupancy mask (free, occupied, unknown), per-region confidence, the registration residual and a scale label | schema here; producer BD-398 |
| 14 | An acceptance report and a feasibility tag for the nominal footprint | BD-228, BD-234 |
| 15 | Provenance | N19a-05 |

3. **Semantic labels (DESIGN).** A region table row carries `room_type` (closed list per archetype: hallway,
   kitchen, aisle, dock, lobby, …), `object_class` (wall, floor, door-leaf, jamb, rack, counter, …) and
   `traversability` (`floor`, `ramp`, `stair`, `keep-out`, `non-walkable`, `unknown`). Labels are identifiers from
   `registries/scene-labels.toml`; an unknown label is a load error. The bottleneck of a clearance cut is reported
   through these labels ("door D3"), so every door, threshold and aisle has a stable name unique in the pack.
   **The interface side at M2 (DESIGN, added in polishing round 2).** The contact tier binds a model to a scene at
   M2 by looking up one interface card for every (collision sample material, region material, region condition)
   triple that can meet (BD-167), and the M2 record of GATE-HAB-01 runs a block on a compiled floor; the bead that
   owns the full region table with both card references and the shared latents (BD-229) is M3. So the region table
   this bead writes at M2 already carries, beside the semantic labels, the interface side as the source declares it:
   `material` (an identifier of the material registry the interface cards use) and `condition` (`dry`, `wet`,
   `greasy` or `dusty`). Generators emit both per region; an import takes them from its sidecar. A region of a part
   tagged `support`, `keep-out` or `transparent` with no declared material and condition fails validation with
   `FROB-REF-303` naming the region (`observed: missing-member`): there is no default material, for the reason there
   is no default optical card. This is the M2 part of compile stage 7; BD-229 extends the same rows at M3 with the
   optical card reference, the latents and their conditionals, and from then on emits the table.
4. **Spawn regions, goals, task regions.** Each is a named box or polygonal prism in the scene frame with an
   allowed heading interval. Spawn and goal regions lie on a `floor` or `ramp` region, never in or adjacent to
   `unknown` space. "Adjacent" is the rule of the unknown-space treatment table of N19c-03, which owns it: a spawn
   or goal whose footprint, inflated by one coarse cell, touches unknown space. At validation, before any pose is
   chosen, this bead applies it to the whole region: the region dilated by the nominal footprint's reference radius
   ρ (every pose's footprint lies within ρ of its reference point) and by one coarse cell S (the pack's coarse
   spacing, 0.16 m by default) must not touch a region labelled `unknown`. A spawn or goal region that does is
   refused with `FROB-REF-305` ("A required route, spawn or contact lies in an unknown region"; exit 3; repairs:
   emit a probe request for the named box; choose another route). Whether the nominal footprint can actually stand at a pose
   of the region (interference, keep-out and support under the base, step and slope) is decided pose by pose at
   compile stage 9 (N19a-19, which depends on this bead). Task regions (keep-out zones, delivery zones, docking
   zones) carry a kind and are what requirement predicates reference by name.
5. **Route graphs.** Nodes are named places (room centres, door thresholds, docks); edges are either `planar`
   (within one height slab) or a `transition` with a kind (`threshold`, `ramp`, `stair`, `lift-sill`,
   `dock-plate`, `door`) and the dimensions a capability predicate needs (rise, slope, gap width, closer torque).
   The graph is data for the clearance verb and the tasks; the predicates themselves belong to the clearance bead.
6. **Living-world declarations.** Schema only: `kind` (`film-patch`, `slosh-payload`, `cord`, `rug`), `tier`
   (`S`, `F`, `M`), the region or body it attaches to and its parameters. A declaration at a tier whose feature is
   not built is a load refusal ("capability not implemented"), never silently downgraded.
7. **Validation.** `ScenePack::validate` checks that every inventory section is present or marked
   `absent: <reason>` (for example no fixtures in an open terrain), that counts in the manifest equal the lengths
   of the tables, and that every name referenced (regions by fixtures, nodes by edges) resolves. A reference that
   does not resolve is `FROB-REF-303` ("a reference does not resolve"; exit 3) naming the referring entry and the
   missing name; a count mismatch or a missing section is the same code, `FROB-REF-303` (the pack reader's one
   code for a pack that cannot be decoded as written; N19-REF lists these triggers), with `pointer` naming the
   section and `observed` and `required` carrying the two numbers, or `observed: missing-member` for a section
   that is neither present nor marked absent.

## Acceptance criteria

- [ ] The manifest fixture `manifest-galley.fscene` (the example in BD-162's full schema) parses, validates and re-serializes to identical canonical bytes; the abbreviated example as printed is refused with `FROB-REF-303` naming its first missing member.
- [ ] A pack missing any inventory section without an `absent` mark fails validation with `FROB-REF-303` and names the section.
- [ ] Every region of a collidable part carries `material` and `condition` in the M2 region table, readable through the pack's typed region reader (the two fields the model-and-scene binding of BD-167 looks up; the binding on a compiled pack is exercised by the ripple run of N19a-42, which depends on both beads); a collidable region without them is refused with `FROB-REF-303` naming the region.
- [ ] A spawn or goal region inside `unknown`, or whose dilation by ρ + S touches it, is refused with
      `FROB-REF-305` naming the region (a region wholly on `keep-out` is refused pose by pose at stage 9, N19a-19).
- [ ] An edge naming a missing node, or a fixture naming a missing region, fails validation with `FROB-REF-303`.
- [ ] `frob --json scene show <id>` prints the labels, spawn regions, goals and route graph of a pack.
- [ ] Changing one label changes the `SceneId` (INV-HAB-01).

## Test plan

### Unit tests

- `inventory_sections_fifteen`: the validator's section list equals the table above.
- `manifest_roundtrip_bytes`: parse then write the fixture; byte equality.
- `count_mismatch_refused`: manifest says `fixtures: 14`, table has 13; validation fails with `FROB-REF-303`, `observed` 13 and `required` 14.
- `abbreviated_example_refused`: the example as printed above (bare counts, no `compiler`) is refused with `FROB-REF-303`; the full fixture passes.
- `region_interface_side_required`: a floor region with `material: "concrete"`, `condition: "dry"` validates and its row round-trips; the same region with no `material` is refused with `FROB-REF-303` naming it; a region of an `optical-only` part needs neither.
- `spawn_inside_unknown_refused`, `spawn_adjacent_unknown_refused` (a region 0.50 m from an unknown box with a
  0.43 m footprint radius and S = 0.16 m: 0.50 < 0.59; code `FROB-REF-305`); `spawn_beyond_radius_and_cell_accepted`
  (0.60 m away). The first case was accepted under the earlier reading "within one footprint radius" and is the
  negative control of that reading.
- `dangling_route_edge_refused` (code `FROB-REF-303`, naming edge and node).
- `label_change_changes_id`: flip one `room_type`; the two `SceneId`s differ.
- `unknown_label_is_load_error`.
- Property test `validate_is_idempotent_and_order_free`: permuting table rows before canonicalization leaves the
  `SceneId` unchanged.

### End-to-end script and logging

`scripts/e2e/scene_pack_inventory.sh` (sources the `STD-E2E` helper): `frob --json scene compile
fixtures/scenes/unit-room.src --key spi-1` (`synthetic`), then `frob --json scene show <id>`; asserts every inventory
section appears in the output, present or `absent: <reason>`, and that each region row prints its semantic labels,
`material` and `condition`; then compiles a fixture with a spawn region adjacent to an unknown box (`--key spi-2`;
exit 3, `FROB-REF-305`), one with a dangling route edge (`--key spi-3`; exit 3, `FROB-REF-303`) and one whose floor
region declares no material (`--key spi-4`; exit 3, `FROB-REF-303` naming the region); compiles the first fixture
again under a new key (`--key spi-5`, since a call that repeats a key returns the stored receipt of the first)
and compares `scene_id`. Every line carries the charter fields: `ts`, `script`, `bead`,
`step`, `event`, the exact command line, exit code, wall time, the envelope's `evidence` block; `assert` lines
with section name and present or absent; the two `scene_id` digests; `refusal` events with code, pointer and the
first repair; on failure the first missing section and the fixture path. Final `summary` with counts.

### Known answers and negative controls

No numeric known answer. Negative controls: the missing section, the dangling edge and the miscount. Determinism:
compile twice on one machine, in debug and release; the `SceneId` is identical (class D0 for the manifest).

## Considerations

- Route-graph transitions carry dimensions that are `assumed` in generated scenes; they count toward
  `dimensions_assumed` (N19a-05).
- The living-world and ingested-scene sections are declared now so that the schema does not change identity rules
  later; their producers land at M3 and M5.
- Label vocabularies will grow with archetypes; additions are registry changes, never free strings.
