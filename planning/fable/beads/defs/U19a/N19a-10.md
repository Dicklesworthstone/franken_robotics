## Background

The scene compiler is a CPU job with eleven fixed stages; each stage writes a receipt into the acceptance report.
Stage 1 reads source bytes: constructive solids emitted by generators, and meshes with scene graphs from imports
(GLB and similar). Source files are untrusted input: an agent or a download supplies them. A scene file can be
built to exhaust memory (millions of instanced nodes), to escape the pack (a reference to `../../secret`), or to
hide a unit conversion. Stage 1 exists so that nothing downstream ever sees an unbounded or unresolved input.

Decision (DESIGN): limits come from a named **import profile**, not from constants in code, so that a refusal can
say which limit was hit and how to raise it deliberately. Alternative rejected: best-effort decoding that truncates
oversized input; a truncated scene is a different scene with the same name.

## Scope

In: the import profile, bounded decoding, reference resolution inside the pack, the record of missing assets and
unit conversions, the stage receipt, the refusal. Out: the transform graph (N19a-11); tagging (N19a-12);
fuzzing of the importer and the hostile-input corpus (BD-307); the untrusted-text mark on echoed strings (BD-304).

## Technical approach

1. **Import profile.** A named record in `registries/import-profiles.toml` (DESIGN) with: `max_bytes`,
   `max_instance_depth` (nesting depth of instances), `max_polygons`, `max_textures`, `max_materials`,
   `max_nodes`, `max_string_len`. Profiles `default`, `large-building` and `fuzz` ship; values are DESIGN defaults
   recorded with their reason in the registry (for example `default`: 512 MiB, depth 32, 20 M polygons; labelled
   DESIGN, to be confirmed against the first real assets). The profile name and digest enter the compile settings
   and therefore the `SceneId`. The file is the one registry of import profiles: N37-05 keeps the per-importer
   rows of the robot-description and mesh importers in it under the same three names, and later beads add the
   profiles of their sources to it, never to a file of their own: `asset-default` (N19a-46, M3),
   `scene-collection` (NEG-22), `articulated-object` (NEG-24) and `generic` (NEG-25) at M3; at M5
   `populated-interior` (NEG-18), `small-rigid` (NEG-19), `kitchen-fixture` and `kitchen-layout` (NEG-20), and the
   scan profile `hm3d-scan` (NEGp1-52). Each added row has the fields above and its reason, and is read by this
   bead's loader like the three it ships.
2. **Bounded decode.** The decoder counts as it goes and stops at the first exceeded limit; it never allocates from
   a length field before checking it against the profile; recursion over instances is explicit with a depth
   counter. Decoding is streaming where the format allows.
3. **References.** Every relative reference (a texture, a sub-asset, an external buffer) resolves inside the pack
   root through a retained directory handle; an absolute path, a parent-directory escape or a link that leaves the
   root is refused. A reference that does not resolve is refused unless the source marks the asset optional, in
   which case it is recorded as missing.
4. **Records.** The stage writes into its receipt: bytes read, node, polygon, texture and material counts against
   their limits; the list of missing optional assets; every unit conversion applied (source unit, factor, where
   declared); the source format and version; the digest of every source file.
5. **Refusal.** `FROB-REF-303` "A decode limit is exceeded or a reference does not resolve". Ranked repairs: raise
   the limit in the import profile; supply the asset. Exit 3. The refusal carries `pointer` (the file and node),
   `observed`, `required` and `unit` (for example observed 21,400,000 polygons, required at most 20,000,000). An
   import over its size, depth or polygon limit at the safety boundary is the same event; the scene verbs report
   303.
6. **Strings.** Names read from source files are data: they are length-bounded, stored verbatim and carried only in
   fields marked untrusted when echoed.
7. **Cancellation.** The stage checks the job context between files and between chunks; a cancel leaves no partial
   pack.

Receipt (DESIGN): `{ "stage": 1, "name": "decode", "profile": "default", "profile_digest": "b3:…", "bytes":
…, "nodes": …, "polygons": …, "textures": …, "materials": …, "missing": [...], "unit_conversions": [...],
"sources": [{"path": …, "digest": …}], "wall_ms": … }`.

## Acceptance criteria

- [ ] Each limit is reached by a crafted file and refused with `FROB-REF-303` naming the limit, the observed value
      and the allowed value.
- [ ] A reference outside the pack root, by absolute path, by `..` and by a swapped link, is refused.
- [ ] A missing optional asset is recorded in the receipt and the compile continues; a missing required asset is
      refused.
- [ ] Every unit conversion appears in the receipt with its factor.
- [ ] Peak memory during decode of a file at the limit stays within a stated multiple of `max_bytes` (measured and
      recorded, TARGET at most 2×).
- [ ] Changing the import profile changes the `SceneId`.
- [ ] Cancel during decode leaves no file in the output root.

## Test plan

### Unit tests

- `limit_bytes`, `limit_depth`, `limit_polygons`, `limit_textures`, `limit_materials`: one crafted source each
  (labelled `synthetic`), one over by one unit; expect 303 with `observed = limit + 1`.
- `depth_bomb`: an instance that references itself through 33 levels under depth 32; refused without stack
  overflow.
- `length_field_lie`: a buffer header claiming 2⁴⁰ bytes in a 1 kB file; refused before allocation.
- `ref_escape_dotdot`, `ref_escape_absolute`, `ref_escape_symlink`: each refused.
- `optional_missing_recorded`, `required_missing_refused`.
- `unit_conversion_recorded`: a source in millimetres yields a receipt entry with factor 0.001.
- `at_limit_passes`: a file exactly at each limit compiles.
- `profile_in_identity`: same source under `default` and `large-building` gives different `SceneId`s.
- `added_profile_is_read`: a scratch copy of the registry with a fourth profile (`synthetic-extra`, `max_polygons`
  1,000) admits a 1,000-polygon source under it and refuses a 1,001-polygon one with 303 naming the profile; a
  profile name absent from the registry is refused naming it, never replaced by `default`.

### End-to-end script and logging

`scripts/e2e/scene_compile_decode.sh` (sources the `STD-E2E` helper): runs `frob --json scene compile` on the
at-limit fixture (exit 0), on each over-limit fixture (exit 3, code 303, `observed = limit + 1`), on the escape
fixtures (exit 3), on the optional-missing fixture (exit 0 or 2, the asset listed in the receipt), and with
`--sync-wait-ms 0` then `frob --json job cancel` on the at-limit fixture (no file in the output root). Every compile
call carries its own idempotency key (`--key dec-<fixture>`; the cancelled call a key of its own, so that it is not
answered from the stored receipt of the earlier at-limit compile), and the import profile is named with `--profile`.
The verb
`scene.compile` is BD-163's, which depends on this bead: until BD-163 is closed the steps are logged with
`e2e_skip "needs BD-163"` (never counted as a pass), and the compile end-to-end bead N19a-42 requires this script
to run them and pass. Every line carries the charter fields (`ts`, `script`, `bead`, `step`, `event`, exact
command line, exit code, wall time, the envelope's `evidence` block); `refusal` lines carry code, pointer,
observed, required and unit; `metric` lines give the stage-1 receipt counts against their limits and the peak
resident memory against 2 × `max_bytes`; on failure the first differing field and the fixture path. Final
`summary` with counts.

### Known answers and negative controls

Known answers: `observed = limit + 1` in each over-limit case. Negative control: a build with the polygon check
removed must fail `limit_polygons`. Chaos (tier G4): cancellation between chunks; truncated files at every byte
boundary of a small fixture never panic. Determinism: receipts are byte-identical across two runs and across
platforms except `wall_ms`, which is excluded from the report hash.

## Considerations

- Security: this stage is the first line against hostile assets; the fuzz campaign (at least 10⁷ executions per
  importer with no panic, each limit reached by a crafted file and refused) is the safety gate GATE-SAFE-07, owned
  by BD-307 and run against this code.
- Limits that are too tight refuse real buildings; the `large-building` profile exists so the caller raises a limit
  knowingly rather than the default creeping up.
- `wall_ms` is telemetry, not identity; it must never enter the report hash.
