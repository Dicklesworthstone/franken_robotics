## Background

Locomotion is learned and tested on graded terrain: a policy starts on easy ground and is moved to harder ground as
it succeeds. That needs terrain generators that are deterministic functions of (family, parameters, seed) with a
scalar difficulty, and a way to lay many terrains side by side so that thousands of worlds can be distributed over
them in one scene. The families are: flat ground, slopes, stairs (rise and run), single steps, gaps, stepping
stones, rough ground (band-limited noise), rubble (random boxes), ramps and curbs. Families tile into a curriculum
grid in the manner of the legged-locomotion benchmarks.

The generator framework (the function signature, the verb `scene.gen`, cross-platform identity) is the terrain seed
bead BD-165. This bead supplies what the framework generates: the definition of each family, its difficulty map and
the grid.

Determinism requirement that shapes every definition here: the same seed must give the same `SceneId` on Linux and
macOS, so a family may use only addressed integer draws, rational arithmetic and the deterministic elementary
functions; no platform `sin`, no thread-local random source.

## Scope

In: per-family parameter schemas, difficulty maps, generation rules, which parts become heightfield and which
overlays, the grid layout with its tile table, spawn regions and seams. Out: the framework and verb (BD-165); the
heightfield representation (N19a-27); the mixed-route family (N19a-29); the known-answer battery and end-to-end
script (N19a-30); curriculum promotion logic, which belongs to the task and learning layers (BD-201, BD-198).

## Technical approach

1. **Common form.** `generate(family, params, seed) → SceneSource` (constructive solids, heightfield samples,
   overlays, regions, spawn and goal regions, the resolved-value table). Each family accepts either explicit
   parameters or a scalar difficulty d in [0, 1] that maps to parameters by the table below. All numeric ranges
   are DESIGN defaults with provenance `assumed`, to be tuned at M2 on the reference quadruped task; they are
   registry data (`registries/terrain/<family>.toml`), not constants in code.

| Family | Parameters | Difficulty map (DESIGN default) | Representation |
|---|---|---|---|
| `flat` | none | none | Heightfield at z = 0 |
| `slope` | grade, direction | grade = 0.5·d (0 to 50%), pyramid up or down | Heightfield |
| `stairs` | rise, run, step count, up or down | rise = 0.05 + 0.18·d m; run = 0.31 − 0.06·d m | Overlays with exact nosings on a flat heightfield |
| `step` | height, up or down | height = 0.30·d m | One box overlay |
| `gap` | width, depth | width = 0.60·d m; depth 1 m | Heightfield with a trench bounded by box overlays |
| `stones` | stone size, spacing, height jitter | size = 0.60 − 0.40·d m; spacing = 0.05 + 0.35·d m; jitter = 0.05·d m | Box or cylinder overlays over a pit |
| `rough` | RMS amplitude, shortest and longest wavelength | amplitude = 0.10·d m; wavelengths 0.2 m to 2 m | Heightfield |
| `rubble` | box count per m², box size range, maximum height | density = 2 + 6·d; size up to 0.30·d m | Box overlays (static) on a flat heightfield |
| `ramp` | grade, length, platform height | grade = 0.25·d; length 3 m | Wedge overlay and platform box |
| `curb` | height, approach angle | height = 0.20·d m; angle drawn in ±30° | Box overlay |

   The stairs range contains the interior hazard range for stairs (riser 150 to 200 mm, tread 230 to 300 mm).
2. **Band-limited noise for `rough`.** Built from integer-lattice gradient noise: for each octave with wavelength
   λ_k between the shortest and longest wavelength, a lattice of pseudo-random gradients indexed by integer hash of
   (seed, octave, i, j), interpolated with the quintic fade 6t⁵ − 15t⁴ + 10t³; octaves summed with weights
   normalized so the RMS equals the amplitude parameter. Only integer hashing, addition and multiplication are
   used, so the samples are bit-identical across platforms. No octave has wavelength below the shortest
   wavelength, which is the band limit; the shortest wavelength must be at least four heightfield cells.
3. **Rubble.** Box centres, sizes and yaws are addressed draws; yaw is drawn from a fixed table of exactly
   representable rotations (multiples of 15° stored as rational sine and cosine approximations with the rotation
   re-orthonormalized in exact arithmetic), so overlay poses are identical across platforms. Boxes are static
   overlays; free rubble is a later option through the movable table.
4. **Draws by address.** Every random quantity is drawn from the counter-based generator at an address
   (seed, family, quantity name, index), never from a stream whose position depends on evaluation order.
5. **Curriculum grid.** A grid scene is R rows by C columns of square tiles of side L_tile (DESIGN default 8 m)
   with a flat border of 1 m at z = 0 around each tile so that neighbouring tiles join without a seam. Row r has
   difficulty d_r = r/(R − 1); column c is a family or a seed variant. The manifest carries a tile table: for each
   tile its bounds, family, parameters, difficulty, seed, spawn region (the tile centre, or its uphill edge for
   descending families) and goal directions. A 10 × 20 grid of 8 m tiles is 80 m × 160 m: at 2 cm, 4,000 × 8,000
   heights, 64 MB.
6. **Tile addressing.** A world is assigned a tile index by the task layer; `frob-scene` exposes
   `tile(index) → TileInfo` and nothing about promotion. Tile index and difficulty are recorded in each episode.
7. **Validity constraints per family.** Stones: spacing less than a declared reach; stairs: run at least a
   declared minimum; gap depth at least a declared fall height; each violated constraint is a generation error,
   not a silently adjusted parameter.

## Acceptance criteria

- [ ] Each of the ten families generates from (family, parameters, seed) and from (family, difficulty, seed); the
      resolved parameters are in the resolved-value table.
- [ ] For each family the difficulty measure (grade, rise, height, width, spacing, amplitude, density) is
      non-decreasing in d on a sweep of 11 values.
- [ ] `rough` terrain's spectrum has no power at wavelengths shorter than the shortest wavelength (beyond
      numerical leakage, measured) and its RMS equals the amplitude within 1%.
- [ ] A 10 × 20 grid compiles; its tile table has 200 rows; borders between tiles are continuous in height (the
      tile-continuity fixture passes).
- [ ] The same seed gives the same `SceneId` on Linux and macOS for every family and for the grid.
- [ ] Parameter ranges live in `registries/terrain/` with provenance `assumed`, and the pack's assumed count
      includes them.
- [ ] A violated validity constraint is an error naming the constraint.

## Test plan

### Unit tests

- `difficulty_monotone_<family>`: one per family with a difficulty map.
- `stairs_params_at_d`: d = 0.5 gives rise 0.14 m and run 0.28 m; d = 1 gives 0.23 m and 0.25 m.
- `slope_grade_at_d`: d = 0.4 gives a 20% grade (11.31°).
- `rough_rms_and_band`: amplitude 0.05 m; measured RMS in [0.0495, 0.0505]; power below the 0.2 m wavelength
  under 10⁻⁶ of total.
- `noise_is_integer_only`: the noise module uses no floating-point elementary function (a lint over its source).
- `rubble_density`: density 5 per m² on an 8 m tile interior of 36 m² gives 180 boxes.
- `grid_tile_table`: 10 × 20 gives 200 tiles with d_r = r/9.
- `border_is_flat`: heights within 1 m of every tile edge are zero.
- `evaluation_order_free`: generating tiles in reverse order gives identical samples (addressed draws).
- `stream_rng_mutant` (negative control): a generator using a sequential stream produces different tiles when the
  order changes and fails the previous test.
- `constraint_violation_is_error`: stones spacing above reach.

### End-to-end script and logging

`scripts/e2e/scene_gen_terrain.sh` (the script owned by N19a-30) is this bead's end-to-end test: it runs `frob
--json scene gen --family terrain/<family> --difficulty <d> --seed 1001` for each of the ten families at five
difficulties, generates the 10 × 20 grid, reads the resolved parameters and the tile table with `frob --json scene
show`, and measures the compiled field with distance probes. For this bead it asserts that the resolved parameters
equal the difficulty maps above, that each family's measure is non-decreasing in d, that the grid has 200 tiles
with flat, continuous borders, and that identities repeat. It logs, per the shared helper, one line per command
(exact command line, exit code, wall time, the envelope's `evidence` block with seed and identities), one `assert`
line per measured parameter with its unit and expected value, and a final `summary`. The unit tests here run under
`cargo test -p frob-scene terrain::`.

### Known answers and negative controls

Known answers: the parameter values at stated difficulties; 180 rubble boxes; 200 tiles; 64 MB for the grid's
heights. Negative control: the stream-generator mutant. Metamorphic relations: mirroring a family's direction
parameter mirrors the heights; scaling tile count leaves each tile's content unchanged. Determinism lanes: twice
on one machine; across worker counts; debug and release; Linux and macOS.

## Considerations

- The difficulty maps are starting points; changing one changes scene identities, so they are versioned registry
  data and a change is recorded in the generator version.
- A grid is one large scene; on a 24 GB card it competes with interiors for memory, and the world bank's
  admission estimate applies.
- The scalar difficulty is a convenience for curricula; evaluation batteries should cite explicit parameters, not
  d, so that results survive a retuning of the maps.
