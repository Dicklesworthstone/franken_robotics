## Background

`scene.gen` is the verb by which an agent obtains a terrain: a pack from (family, parameters, seed). Its promise
has three parts that only an end-to-end run can check. First, what comes out is the terrain that was asked for: a
staircase requested with a 0.17 m rise has a 0.17 m rise in the compiled field that contact and sensors read, not
only in the generator's parameters. Second, it is deterministic: the same request gives the same `SceneId` twice,
in debug and release, with any worker count, and on Linux and macOS (INV-HAB-10). Third, scenes cross machines as
seeds and identities, never as voxels (ADR-HAB-12): each machine compiles what it needs and checks the `SceneId`,
so a second machine given only the request regenerates a pack with the same identity. That only works if the
same (family, parameters, seed, compiler version) gives the same `SceneId` on Linux and on macOS. A unit test on
one machine cannot show that; an end-to-end script run on both machines against one pinned file can.

This bead is the end-to-end script for terrain generation with its structured log, and the battery of geometric
known answers it measures. It drives the real `frob` binary on real fixtures; nothing is mocked. It is the
evidence for the done-condition of the terrain-generator seed bead (BD-165).

There is one script `scripts/e2e/scene_gen_terrain.sh` and this bead owns it. A second draft of the same script
(N18a-41) is superseded by this bead; its pinned-identity procedure, its three-seed and 1,000-seed lanes, its
refusal and cancellation steps, its two generator mutants and its checks of `scene show` are folded in below.

## Scope

In: the script, the measurement probes, the expected values, the determinism lanes, the pinned identity file and
the cross-machine check, the refusal and cancellation steps, the negative controls. Out: the generators (BD-165,
N19a-28), the representation (N19a-27), the compile pipeline's own script (N19a-42), interiors (N19a-45; their
identity row closes at M3 with the interior gate).

## Technical approach

1. **Script.** `scripts/e2e/scene_gen_terrain.sh [--record] [--seeds N] [--quick] [--self-test]`, plain shell,
   sources the shared helper from STD-E2E, is idempotent (it writes to a scratch store and to
   `target/e2e-logs/`) and seed-explicit (seeds are literals in the script: 1001, 1002, 1003 by default; `--seeds
   N` uses 1001 to 1000 + N), exits non-zero on the first failed assertion after writing the summary. The
   gate-quality lane is `--seeds 1000` (1,000 seeds per family); it is run for the close of BD-165 and nightly.
   `--self-test` runs steps (a), (e) and (h) for the `stairs` family only. `--quick` runs three families at one
   difficulty for use in the `smoke` battery and says so in its summary line.
2. **Steps.**
   a. For each of the ten families and difficulties d ∈ {0, 0.25, 0.5, 0.75, 1} and each seed: `frob --json scene
      gen --family terrain/<family> --difficulty <d> --seed <s> --sync-wait-ms 30000 --key
      sgt-<family>-<d>-<s>-<lane>` (30,000 ms is the largest value the long-verb contract admits; above it the call
      is refused with `FROB-REF-802`; the idempotency key is unique per call and carries the lane, so that the
      regeneration of step (e) and the reruns of step (g) are computed again and not answered from the stored
      receipt of step (a)). Assert exit code 0
      (or 8 followed by `frob job wait` to completion), one envelope with the evidence block, and a manifest of
      schema `frob.scene/1`. Also `terrain/stairs` with explicit `--param rise=0.20 --param run=0.23 --param
      steps=10` (the steepest interior stair, outside the difficulty map's run range: top height 2.00 m). The mixed-route family, whose outdoor half exists at M2, is generated in the same loop
      as `--family terrain/mixed-route` (BD-165's name) and takes part in the identity steps (e), (g) and (h); it
      has no row in the measurement table.
   b. `frob --json scene show <id>`: read the manifest, the resolved parameters, the tile table. Assert the
      family, the seed, the resolved randomized quantities with their provenance, and `dimensions_assumed` equal
      to the count of entries whose provenance is `assumed`.
   c. Measure the compiled field with distance probes (`frob --json scene show <id> --probe <points.json>`): a
      vertical probe line finds surface height at chosen (x, y); a horizontal sweep finds edges. Geometric
      measurements are made on seed 1001.
   d. Compare each measurement with the value implied by the resolved parameters (table below), check that the
      resolved parameters equal N19a-28's difficulty maps at each d, and that each family's measure is
      non-decreasing over the five difficulties.
   e. Regenerate every scene a second time, one scene per family in a fresh store, and compare `scene_id` and the
      manifests byte for byte.
   f. Generate the 10 × 20 curriculum grid with `frob --json scene gen --grid fixtures/terrain/grid-10x20.json
      --seed 1001 --key sgt-grid-<lane>` (a `frob.scene.grid/1` file of this bead: `levels = 10`, twenty columns,
      `tile_m = "8"`); check that it is one pack, the tile table (a spawn region and a goal per tile) and border
      continuity (heights on shared tile edges bit-identical). The same checks on a small 4 × 3 grid
      (`fixtures/terrain/grid-4x3.json`) run first, so that a defect of the tiling is found in seconds.
   g. Determinism lanes: rerun step (a) with `--workers 1` and `--workers 16` (the operator-only option of the
      compile job that BD-163 defines and `scene.gen` passes through; it is outside every identity); with the debug
      binary and the release binary; compare identities.
   h. Cross-machine: compare each `scene_id` with the pinned identity file (item 3).
   i. Refusal: `--difficulty 1.2`; assert `FROB-REF-802` with exit code 3 and a pointer that names the field
      (`e2e_expect_refusal FROB-REF-802 3`); the same for `terrain/stones` with an explicit spacing above its
      declared reach, whose pointer names the constraint.
   j. Cancellation: `frob --json scene gen --grid fixtures/terrain/grid-10x20.json --seed 1002 --sync-wait-ms 0
      --key sgt-grid-cancel` (exit 8, a job handle), then `frob --json job cancel <job>` and `frob --json job wait
      <job>`; assert the job ends cancelled and that no partial pack remains in the store (`frob --json scene list`
      before and after: the same packs, none from the cancelled request).
   k. Negative controls (run against test builds or planted fixtures; see below).
3. **The pinned identity file.** `fixtures/identity/terrain_ids.json`, beside the identity files of the other
   scene scripts: rows of (family, difficulty, seed, compiler version, `SceneId`) for the same requests as step
   (a), recorded on the other platform. It is written only by the explicit pin mode `--record`, which is a
   deliberate, logged act on one platform with the compiler version recorded; the result is reviewed and
   committed, and thereafter the file is only compared, on both platforms. A normal run never writes it. It is
   regenerated only with a recorded reason (a compiler-version change alters every identity by design); the
   script prints the compiler version and refuses to compare across versions.
   DESIGN: the superseded draft kept the same rows as `tests/fixtures/scene_ids/terrain.tsv`; one file is kept,
   at the path the sibling scene scripts use (`fixtures/identity/…`), so that all pinned identities are in one
   directory.
4. **Measurements and expected values.**

| Family | Measurement | Expected (from resolved parameters) | Tolerance |
|---|---|---|---|
| `flat` | Height at 100 points | 0 | Tile bound |
| `slope` | Height difference over a 2 m run | 2 m × grade | Tile bound |
| `stairs` | Height of each tread; horizontal position of each riser | k × rise; k × run | Round-off (overlays are exact) |
| `step` | Height difference across the edge | height | Round-off |
| `gap` | Width between the two edges at ground level | width | Round-off |
| `stones` | Centre spacing of adjacent stones; top heights | spacing; within ± jitter | Round-off |
| `rough` | RMS height over the tile; power below the shortest wavelength | amplitude; under 10⁻⁶ of total | 1% of amplitude |
| `rubble` | Count of boxes; maximum top height | density × area; at most maximum size | Exact; round-off |
| `ramp` | Height at the platform; grade along the ramp | grade × length; grade | Round-off |
| `curb` | Height difference across the curb | height | Round-off |

   The family the seed bead and the superseded draft called `stepping-stones` is `stones` in the verb
   (`terrain/stones`), as the generator bead N19a-28 registers it.
5. **Logging.** Structured newline-delimited JSON to `target/e2e-logs/scene_gen_terrain/<utc-timestamp>.ndjson`
   and a human-readable transcript beside it. Every line has `ts`, `script`, `bead` ("N19a-30"), `step`, `event`
   (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the
   envelope's `evidence` block (claim, class, tier `static`, determinism `exact`, identities, seed), measured
   values with units and their thresholds, the `scene_id`, the manifest digest and the expected identity where
   identity is compared, the counts of overlays and regions, the platform triple, and on failure the first
   differing value (for an identity mismatch: the first differing manifest field and the first differing
   component digest among manifest, heightfield, overlays, maps, with the paths of both manifests) and the
   artifact paths needed to reproduce. A final `summary` line gives counts of assertions passed and failed, the
   controls caught and the platform. Generated terrain only: no private-scene data is involved.

## Acceptance criteria

- [ ] All 50 family-by-difficulty scenes generate for each seed, and every measurement in the table is within
      tolerance; resolved parameters equal the difficulty maps of N19a-28 and each family's measure is
      non-decreasing in d (the assertions N19a-28 names as its end-to-end test); the explicit 0.20 m / 0.23 m
      staircase generates with a top height of 2.00 m.
- [ ] Every scene regenerates to the same `SceneId` with a byte-identical manifest; identities are equal across
      worker counts, across debug and release, and equal to the identities pinned on the other platform.
- [ ] The script passes on Linux and on macOS against one committed pinned file.
- [ ] The 1,000-seed lane passes on both platforms and its two logs are cited in the close reason of BD-165.
- [ ] The grid has 200 tiles in one pack, with a spawn region and a goal per tile; borders are continuous.
- [ ] `scene show` reports the family, seed and resolved quantities with provenance, and `dimensions_assumed`
      equals the count of `assumed` entries.
- [ ] The refusal step and the cancellation step behave as asserted.
- [ ] Each negative control is caught: the script, pointed at the planted build or fixture, exits non-zero and the
      log names the failed assertion.
- [ ] The log validates against the STD-E2E schema; the transcript is readable without the JSON.
- [ ] The script is idempotent: a second run reuses compiled packs (verification, not rewrite) and passes.

## Test plan

### Unit tests

The probe utilities used by the script have their own tests in `crates/frob-scene/tests/`:
- `edge_finder_locates_step`: on an analytic 0.17 m step at x = 1.000 m the horizontal sweep returns 1.000 m to
  round-off.
- `rms_of_known_sinusoid`: amplitude A sinusoid has RMS A/√2.
- `spectrum_band_test`: a signal with one component at 0.1 m wavelength fails the band check at a 0.2 m limit.

For the script's own files:
- `e2e_log_schema_scene_gen_terrain`: the log validates against the STD-E2E line schema.
- `pinned_table_wellformed`: the pinned file has one row per (family, difficulty, seed) and no duplicate
  identity.

### End-to-end script and logging

As specified above; this bead is the script. Expected runtime target on the reference host: under ten minutes
(TARGET) for the default run, dominated by the grid compile; the 1,000-seed lane is minutes of CPU per family.

### Known answers and negative controls

Known answers: for seed 1001 and d = 0.5, stairs rise 0.14 m and run 0.28 m; slope grade 0.25 (0.5 m over a 2 m
run); step 0.15 m; gap 0.30 m; curb 0.10 m; ramp grade 0.125; rough amplitude 0.05 m. The stairs rise at d = 0,
0.5 and 1 is 0.05, 0.14 and 0.23 m. KA-464's identity statement (the same family, parameters, seed and compiler
version give the same `SceneId` on Linux and macOS), here for terrain. Negative controls:
- a generator build that draws from a time-seeded source (the test-only mutant `wall-clock-seed`): identities
  differ between runs;
- a generator build that calls the platform's sine in place of the deterministic one (the test-only mutant
  `platform-sin`): the regeneration or the cross-machine comparison fails;
- a generator that ignores the seed: seeds 1001 and 1002 give one identity (the script asserts they differ);
- a staircase compiled through bricks only: tread edges smear and the riser-position check fails;
- a pinned identity file with one entry altered: the cross-machine comparison fails and names the family.
Metamorphic relations: difficulty monotonicity per family; changing the seed changes the identity and leaves the
resolved difficulty parameters unchanged for deterministic families (`slope`, `step`, `gap`, `curb`, `ramp`).
Determinism lanes: twice on one machine; across worker counts; debug and release; across platforms (class D0 for
integer-built families; the whole identity is required to be equal).

## Considerations

- The cross-platform comparison is only as good as the pinned file; pinning is a deliberate, logged act on the
  other machine with the compiler version recorded, and a compiler version change requires re-pinning.
- If the cross-platform identity fails, the per-component digests in the log localize the cause (heightfield
  samples against overlay parameters against manifest formatting).
- Runtime grows with the grid; a `--quick` mode runs three families at one difficulty for use in the `smoke`
  battery and says so in its summary line.
- The pinned file couples to the compiler version; the script prints the version and refuses to compare across
  versions.
