## Background

An evaluation battery is a chosen set of scenes. A battery is only as good as the failures it can provoke: one made
of ten kitchens with no wet floor says nothing about slip. The studio selects batteries from a scene-by-failure-mode
incidence table (a matrix whose rows are scenes and whose columns are failure modes, weighted by frequency,
severity and designs affected), by a greedy coverage selection that carries a certificate. The hazard registries
supply the rows of that table: each scene knows which hazards it drew, and each hazard names the failures it
provokes. Because of that link, a battery can be asked which hazards it leaves uncovered.

This bead builds the Habitat side of the link: for any scene or set of scenes, the list of hazards drawn, the
failure modes those hazards provoke, and the complement, the hazards of the archetype that no scene in the set
contains.

## Scope

In: the typed list of hazards drawn in each pack, the export of incidence rows, the uncovered-hazard query (which
hazards of an archetype no scene of a battery contains), their exposure through `scene.show` and the two
options `--uncovered-by` and `--incidence` of `scene.hazards`, and the generator parameter `hazards.exclude`
with the `structural` mark of the grammars. Out: the registry schema, the base verb and the exclusion hook of
the draw (BD-227); the per-archetype rows and bindings (N19a-31 to N19a-37); the
weighted matrix, the selection and its certificate (the battery decision core and the coverage verb: BD-254,
BD-278, BD-309); adding observed failures to the matrix (Nemesis and Autopsy); whether a hazard that a battery
does contain would be noticed when it defeats a robot: the cover map from each hazard to a requirement, a
shield or a refusal, the check that each cover exists and can fire, and the per-battery report of hazards that
are present and unguarded (NEG-29, which depends on this bead and takes its hazard-by-scene matrix from this
export).

**Three words for three things (DESIGN, stated identically in NEG-29; both beads had used "uncovered" and
"covered").** A hazard is *uncovered by a battery* when no scene of the battery contains it: this bead's
query, in the plan's own phrase ("a battery can be asked which hazards it leaves uncovered"), with the two
reasons `never-drawn` and `not-represented`; a hazard some scene contains is *drawn*. A hazard *has a cover*
when the cover map gives it a requirement template, a shield or a refusal that has landed (NEG-29's check).
A hazard is *unguarded in a battery* when it is drawn in the battery's scenes and none of its covers is in
force for the battery's tasks (NEG-29's report). A scorecard prints the first and the third as two counts
with these two names and never adds them.

## Technical approach

1. **Hazards drawn.** When a generator draws a hazard row, the pack's resolved-value table records the row
   identifier (for example `commercial-kitchen.wet-floor`), the mechanism actually used and its tier (Solid alternative or
   Frontier), the drawn dimensions and the region or object that carries it. A row that the generator skipped
   because its only mechanism is not built is recorded as `not-represented`. `scene.show` prints this list as
   "the hazards drawn". What exists before this bead and what it adds: the row identifier, the value and the
   provenance of each draw are recorded by BD-227's draw; the `not-represented` record of a Frontier-only row
   and the region label `hazard:<row identifier>` are written by the seven archetype bindings (N19a-31 to
   N19a-37); this bead adds, per drawn row, the mechanism used with its tier, the Frontier mechanism beside a
   Solid alternative as `not-represented` with the failure identifiers only it can provoke, the state
   `excluded`, and the one typed list (`HazardsDrawn`, schema `frob.scene.hazards-drawn/1`) that `scene.show`
   prints and the export reads, so that no consumer parses the resolved-value table itself.
2. **Failure identifiers.** Each registry row lists the failures it provokes (the `provokes` entries of BD-227's
   schema); their kebab-case forms are the failure identifiers. These are mapped to the failure taxonomy of
   telemetry by a table `registries/hazards/failure-map.toml` (DESIGN): for example `small-wheel-stall` →
   mechanical class `stuck`; `slip-that-depends-on-dwell-time-and-load` → `slip`; `depth-dropout` → a sensor mask
   reason. An
   identifier with no mapping is a load error, so every hazard's failure is something telemetry can report.
3. **Incidence row of a scene.** For scene S: the set H(S) of hazard rows represented in it, and the set
   F(S) = ∪ over h in H(S) of failures(h). The export is a table of (scene identity, hazard identifier, failure
   identifier, tier, dimensions) rows in canonical order, as an artifact with its own digest. It states the
   identities it was built under: the registry version, the generator version and the `SceneId`s.
4. **What the row asserts.** Presence, not rate: "this scene contains a feature that can provoke this failure". It
   is `potential` incidence. Observed incidence (a failure actually occurred for some design) is added by the
   consumers from runs; the two are kept in separate columns so that a potential that never materializes is
   visible.
5. **Uncovered-hazard query.** For a set of scenes B of one archetype A: uncovered(B) = rows(A) ∖ ∪ H(S) for S in
   B, split into `never-drawn` (the row is representable and no scene of B drew it) and `not-represented` (the
   row's mechanism is not built at this milestone). Exposed as `frob scene hazards <archetype> --uncovered-by
   <scenes>` and, for the export of step 3, `frob scene hazards <archetype> --incidence <scenes>` (DESIGN: two
   options this bead adds to BD-227's `scene.hazards`, with its input schema changed additively and its
   help-schema snapshot updated; the registry bead VERBS-scene is asked to list them). `<scenes>` is a
   comma-separated list of scene names or `SceneId`s, or `@<file>` with one per line (a path under the session's
   roots; a path that leaves them is `FROB-REF-734`); a battery is passed as its scene list, so this bead needs
   no battery type. A scene of another archetype in the list, or an unknown scene, is `FROB-REF-802` naming it.
   Both forms are reads: they compile nothing and take no key. The generator parameter
   `hazards.exclude=<row identifier,…>` (DESIGN: `frob scene gen … --param
   hazards.exclude=commercial-kitchen.wet-floor`) withholds rows so that a battery can be built without them.
   This bead parses the parameter and passes the set to the exclusion hook of BD-227's draw, through which all
   seven archetype bindings draw, so no binding changes; an excluded row is recorded as `excluded`, never
   silently, and because streams are addressed every other draw of the seed is unchanged. A row the family's
   grammar cannot do without (a dimension no scene exists without: the aisle of a warehouse, the hallway of a
   home, a door's clear width; this bead adds the mark `structural` to those productions of the seven grammars
   and a test that every unmarked hazard row can be excluded without a constraint violation) cannot be excluded:
   the request
   is refused as an out-of-range family parameter is (exit 3), naming the row, with the repair "pin the
   dimension with its own parameter instead". An identifier that names no row of the family's registry is
   refused the same way.
6. **Coverage summary.** For a battery: per archetype, the count of rows drawn, never drawn and not
   represented, of the archetype's total (10, 5, 7, 10, 8, 8 and 11 rows for `home`, `apartment`, `office`,
   `warehouse`, `manufacturing-plant`, `retail-store` and `commercial-kitchen`, the registry names of BD-227; 59 in
   all). The three states are spelled `drawn`, `never-drawn` and
   `not-represented`. A row drawn through its Solid alternative is `drawn` with that tier, and the Frontier
   mechanism beside it is listed `not-represented` together with the failure identifiers that only that
   mechanism can provoke; those failures are absent from the row's incidence and are not counted as drawn
   (rigid ballast standing in for hot liquid cannot spill).
7. **Privacy and identity.** The export of a private scene inherits its mark; exports cite scene identities, not
   geometry.

## Acceptance criteria

- [ ] Every generated interior pack lists the hazards it drew, with mechanism, tier and dimensions, and
      `frob --json scene show <id>` prints them.
- [ ] Every failure identifier in the seven registries maps to the telemetry taxonomy; an unmapped one fails the
      load.
- [ ] The incidence export of a set of scenes is deterministic (identical bytes on two runs and two platforms)
      and names the registry version and scene identities.
- [ ] `--uncovered-by` on a battery of kitchens generated with the wet-floor row excluded reports
      `commercial-kitchen.wet-floor` as `never-drawn`.
- [ ] `frob --json scene hazards commercial-kitchen --incidence <scenes>` returns the export with its digest;
      both options appear in the verb's help-schema snapshot; neither form compiles a scene.
- [ ] `--param hazards.exclude=<row>` records the row `excluded` and leaves every other draw of the seed
      unchanged; excluding a row marked `structural`, or an identifier that names no row, is refused with exit 3
      and the row named; every hazard row not marked `structural` can be excluded with no constraint violated.
- [ ] At M3 the three rows whose only mechanism is Frontier (pets in the home, floor vibration in the plant,
      shoppers in the retail store: rows 9, 39 and 48 of the consolidated table) are reported
      `not-represented`, never as drawn. For a row drawn through its Solid alternative, the Frontier mechanism
      beside it is listed `not-represented` with the failures only it can provoke (the slosh model of the
      hot-liquid row, the strip curtain of the cold-room row, the hinged plates of the rug and of the
      stretch-wrap debris, the chain cord, forklifts as actors), and none of those failures is counted as
      drawn.
- [ ] The row totals per archetype are 10, 5, 7, 10, 8, 8 and 11 (59).

## Test plan

### Unit tests

- `hazards_drawn_recorded`: a kitchen scene's list equals the rows its resolved-value table names.
- `row_totals_59`: the seven registries sum to 59 rows with the stated split.
- `failure_map_total`: every failure identifier resolves; a planted unknown identifier is a load error.
- `incidence_rows_canonical`: export of scenes in two orders gives identical bytes.
- `uncovered_complement`: for a synthetic archetype with rows {a, b, c} and a battery drawing {a}, uncovered is
  {b, c}; with c's mechanism not built, c is `not-represented` and b is `never-drawn`.
- `potential_not_observed`: the export has no observed-failure column filled by Habitat.
- `silent_cover_mutant` (negative control): a build that counts `not-represented` rows as drawn fails the
  uncovered test.
- `solid_alternative_lists_frontier_part`: a kitchen with the hot-liquid row drawn as rigid ballast reports the
  row `drawn` (tier Solid alternative), the slosh model `not-represented`, and no spill failure in its
  incidence.
- `private_export_marked`.
- `exclude_passes_through_hook`: `hazards.exclude=commercial-kitchen.wet-floor` on seed 7: the wet-floor row is
  `excluded`, and the resolved values of all other rows equal those of seed 7 without the exclusion.
- `structural_rows_cannot_be_excluded`: `warehouse.aisle`, `home.hallway` and `commercial-kitchen.galley-aisle`
  are refused; `unmarked_rows_can_be_excluded`: for each of the 59 rows that is not marked `structural`, 20
  seeds generated with the row excluded have zero violated constraints.
- `scene_list_forms`: a comma list and an `@file` list of the same scenes give the same export digest; a scene of
  another archetype in the list is refused naming it.

### End-to-end script and logging

`scripts/e2e/scene_hazard_incidence.sh` (header: `bead=N19a-38 milestone=M3
labels=habitat,scene,verb:scene.hazards seed=1 needs=cpu plants=silent-cover`; it sources `scripts/e2e/lib.sh`):
for seeds 0 to 19, `frob --json scene gen --family kitchen-commercial/galley --seed <s> --param
hazards.exclude=commercial-kitchen.wet-floor --key shi-x-<s>` (set X) and the same seeds without the exclusion
under other keys (`--key shi-a-<s>`, set A; single-seed calls, each with its own key); `frob --json scene show
<id>` on each (the hazards drawn, with mechanism, tier and dimensions; `excluded` recorded for the wet-floor
row in set X; for one seed, every draw other than the excluded row equal in X and A); `frob --json scene
hazards commercial-kitchen --uncovered-by @<list file>` for each set, asserting that X reports
`commercial-kitchen.wet-floor` as `never-drawn` and A does not, and that both report the strip curtain and the
slosh model `not-represented` beside their drawn Solid rows with no spill failure counted; `frob --json scene
hazards commercial-kitchen --incidence @<list file>` on set A twice and once with the list reversed (three
equal digests); `--param hazards.exclude=commercial-kitchen.galley-aisle` (a structural row: refused, exit 3,
the row named) and `hazards.exclude=commercial-kitchen.no-such-row` (refused); then for seeds 0 to 19 `frob
--json scene gen --family home --seed <s> --key shi-h-<s>` and `frob --json scene hazards home --uncovered-by
@<list file>` (`home.pets` `not-represented`); and the planted build `silent-cover` through `e2e_expect_caught`
(`not-represented` rows counted as drawn: the pets assertion fails). Every line carries the charter fields
(`ts`, `script`, `bead`, `step`, `event`, exact command line, exit code, wall time, the envelope's `evidence`
block); `metric` lines give the drawn, never-drawn and not-represented counts against 11 (and 10 for the home),
the export digest and the registry version; on failure the first differing row identifier and the scene list.
The `summary` gives assertion counts, refusals expected and controls caught; the script claims no gate.

### Known answers and negative controls

Known answer: 59 rows in seven archetypes (10, 5, 7, 10, 8, 8, 11), every one `assumed`. Negative control: the
silent-cover mutant. Determinism: exports are exact (class D0).

## Considerations

- A hazard present in a scene may be off the route of a given task; incidence by presence over-counts coverage for
  that task. Consumers that weight by task should intersect with the route; the export carries the region so they
  can.
- The battery selection reserves one slot in five for random held-out scenes; coverage of hazards is never the
  only criterion.
- The registries are also the scene-edit vocabulary of adversarial search; a counterexample that edits a hazard
  dimension cites the same row identifier, which is what lets observed failures join the table.
- Legality bounds of adversarial edits and the realism of a counterexample depend on the same `assumed`
  dimensions (an open question owned with the dimension-norm question).
