## Background

Generated interiors use dimensions (door widths, threshold heights, closer torques) chosen to make scenes valid.
Validity needs no source; a claim that a scene is representative of real buildings does. The decision
(ADR-HAB-11) is that every dimension a generator draws carries provenance, and its provenance is `assumed` until a
cited norm or a measurement is recorded. Today every one of the 59 hazard rows is `assumed`: no building code,
workplace regulation or product standard has been read for them, and none is cited.

Two mechanisms follow. First, a pack counts the `assumed` dimensions it used (`dimensions_assumed` in the
manifest), and a report that claims a scene is representative of real buildings is refused while that count is
non-zero. Second, there must be exactly one controlled way for a row to stop being `assumed`: a row's provenance
changes to `norm: <citation>` or `measured: <dataset>` only when the source is recorded in the source register.
The count and the refusal are the hazard-registry seed bead's done-condition (BD-227); this bead builds the
promotion path and the report-side check, so that nobody can "fix" a refused report by editing a string.

The pre-mortem names the failure this guards: "interiors were toy boxes and results did not transfer to real
places", watched through the share of dimensions labelled `assumed`.

## Scope

In: the full provenance value grammar (source identifier and clause; dataset identity); what the source register
must hold for a reference to be usable (a read date; an admitted dataset); the promotion procedure and its
record; the effect of a promotion on scene identities; the report side of the realism claim (what counts as
making the claim, which verbs must call the check, how the cited scenes are collected, the count printed when no
claim is made); the list of assumed rows that `--strict-data` reads; the lint over the repository.

Out, with the bead that has it (the report verbs that carry the flag are BD-302's; this bead adds the flag and
the routing to them):

- the registry schema with one `provenance` field per row, the loader and its base rule (a `norm:` or
  `measured:` reference must be an entry of the source register), the row identifier `<archetype>.<slug>`, what
  a draw returns, the verb `scene.hazards`, and the realism-claim function
  `frob_scene::hazards::claim::realism_claim_admissible` with the refusal `FROB-REF-312` (its text, exit code
  and ranked repairs): BD-227. This bead tightens the base load rule and calls that function; it defines no
  second check and no second refusal row (an earlier draft named its own `frob_scene::realism_check`);
- the provenance block of the manifest, the counting rule of `dimensions_assumed` and the recount on load that
  detects an edited count (N19a-05);
- the consolidated index, which a promotion updates in the same change (NEG-28); report rendering (BD-302);
  finding and reading the norms, which is the owner decision OPEN-HAB-1.

## Technical approach

1. **Provenance grammar.** `assumed` | `norm: <source-id> [<clause>]` | `measured: <dataset-id>`. `<source-id>` is
   an identifier in the source register (`registries/sources.toml`), which records for each source its title,
   publisher, edition or date, where it was read, the date it was read and a digest or location of the copy read.
   `<dataset-id>` is the identity of a dataset admitted through the ground-data admission path.
2. **Load check.** The hazard registry loader of BD-227 resolves every `norm:` and `measured:` reference against
   the source register, and an unresolved reference is a load error (BD-227's base rule and test). This bead
   adds two conditions to the resolver the loader calls: a source whose register entry lacks a read date is not
   usable ("to be re-read before a gate cites it" is enforced as: no read date, no promotion), and a
   `measured:` reference must name a dataset admitted through the ground-data admission path.
3. **Promotion procedure.** A promotion is a registry change with a record: the row identifier
   (`<archetype>.<slug>`), the old range and distribution of each of the row's dimension entries, the new range
   and distribution as stated by the source, the source reference and clause, who made the change and when. The
   new values come from the source, never from the old range relabelled: a promotion whose record shows an
   unchanged range must state that the source confirms it. Provenance is one field per row (BD-227), so a
   promotion covers every dimension entry of the row; a source that covers only some of them does not promote
   the row, which stays `assumed`. The same change updates the row in the consolidated index (NEG-28), whose
   agreement check otherwise fails.
4. **Effect on identities.** The registry version is part of the generator version and therefore of every
   `SceneId`. Promoting a row changes the scenes generated afterward; packs generated earlier keep their count and
   their identity. No pack's `dimensions_assumed` is ever edited after the fact.
5. **Mixed scenes.** A pack's count is the number of distinct `assumed` rows among its draws (rule in the
   provenance-block bead). A scene whose doors are from a norm and whose thresholds are assumed has a non-zero
   count and remains refused for realism claims.
6. **The realism-claim check, report side.** A report or verb that asserts representativeness of real buildings
   (a field `claims_realism: true` on a report request, or the wording of a Reality-flavoured statement about
   places) collects two things and calls `frob_scene::hazards::claim::realism_claim_admissible(manifests,
   task_rows)` of BD-227, the one implementation of the check: the manifests of every scene it cites, and
   `task_rows`, the hazard row identifiers that the randomization plans of the runs it cites drew with
   provenance `assumed` (read from each run's resolved randomization list, where BD-227's source kind
   `registry:hazards` records the row identifier and provenance of every task-file draw; empty for a run whose
   task draws from no hazard row). If any cited scene has `dimensions_assumed > 0`, or `task_rows` is not empty,
   the result is BD-227's refusal `FROB-REF-312` "A realism claim cites a scene with `assumed` dimensions"
   (ranked repairs: record a norm or a measurement; drop the claim; exit 3), which lists the scenes with, per
   scene, the assumed row identifiers, and the runs with, per run, the assumed rows its task drew. What this
   bead adds is the calling side: the request field and the flag `--claims-realism` on the report verbs of
   BD-302 (`report.run`, `report.design` and `report.mission` at M3, and `report.campaign` when it first
   answers; each is a `read` verb, and the flag is an additive input whose help-schema snapshot changes with
   this bead; the registry bead VERBS-report is asked to list it), the rule that every verb able to carry the
   claim routes through the function (a report path
   that skips it is BD-227's planted control 2; a collection that leaves out the task rows is its control 1),
   and the collection of cited scenes and runs across a report that spans several runs.
7. **Strict data.** Under `--strict-data` a verb that would return a verdict depending on an `assumed` dimension
   says so in its findings; this bead supplies the per-scene list of assumed rows that the flag reads.
8. **Reports without the claim.** A report that makes no realism claim is not refused; it prints the count
   ("23 dimensions assumed") beside every scene it cites.

## Acceptance criteria

- [ ] A registry row with `norm: <id>` loads only when `<id>` is in the source register with a read date; an
      unknown source is a load error by BD-227's base rule, and an undated source, or a `measured:` reference to
      a dataset that was not admitted, is a load error by this bead's.
- [ ] No function other than BD-227's `realism_claim_admissible` decides a realism claim (a source scan finds no
      second comparison of `dimensions_assumed` with zero on a report path).
- [ ] A report request with a realism claim over a scene with a non-zero count is refused with `FROB-REF-312`
      listing the assumed rows; the same request without the claim succeeds and prints the count.
- [ ] A report request with a realism claim over a run whose task drew an `assumed` hazard row is refused with
      `FROB-REF-312` listing that row under the run, even when every cited pack has count zero.
- [ ] After a (synthetic, test-only) promotion of every row an archetype uses, a newly generated scene has count
      zero and the realism claim is admitted; a previously generated pack still has its old count.
- [ ] Editing a pack's manifest to set the count to zero is detected (the recount on load, N19a-05, fails), so
      the claim check cannot be passed by editing the number it reads.
- [ ] Every promotion has a record with old and new ranges and the source reference.
- [ ] The repository at M3 contains no `norm:` or `measured:` provenance without a register entry (lint).

## Test plan

### Unit tests

- `provenance_grammar_parses`: the three forms; a malformed form is rejected.
- `norm_requires_read_date`; `measured_requires_admitted_dataset`. (The entry-exists rule is tested in BD-227 as
  `norm_requires_source_register_entry`.)
- `realism_claim_refused_312`: a report request with `claims_realism: true` over a scene with count 23 reaches
  BD-227's function; the refusal lists 23 row identifiers; exit 3.
- `claim_spanning_two_runs_collects_both_scenes`: one clean scene and one with count 2 → refused, listing only
  the second scene's two rows.
- `no_claim_no_refusal`: the same scene, no claim; success; output shows "23 dimensions assumed".
- `claim_collects_task_rows`: a `synthetic` pack with count 0 and a run whose resolved randomization list names
  `commercial-kitchen.wet-floor` as `assumed`: refused, the row listed under the run; with a task that draws
  only from cards: admitted. `task_rows_skipped_mutant` (negative control, BD-227's control 1 seen from the
  calling side): a collection that passes an empty `task_rows` admits the first case and fails this test.
- `promotion_record_required`: a registry diff with a provenance change and no record fails the lint.
- `relabel_without_source_mutant` (negative control, exercising BD-227's base load rule through the promotion
  path): a row changed from `assumed` to `norm: fake` with no register entry fails the load.
- `partial_source_does_not_promote`: a source that states the stair riser and not the tread leaves `home.stairs`
  `assumed`.
- `old_packs_keep_count`: generate, promote (synthetic), regenerate: old pack count unchanged, new pack count
  lower, identities differ.
- `mixed_scene_still_refused`: one assumed row left gives count 1 and a refusal.
- `count_edit_detected`.

### End-to-end script and logging

`scripts/e2e/scene_realism_claim.sh` (header: `bead=N19a-39 milestone=M3
labels=habitat,scene,report,verb:report.run seed=3 needs=cpu plants=relabel-without-source,edited-count`; it
sources `scripts/e2e/lib.sh` and works in the harness's scratch root, whose copy of the registries it may
edit). Every `run` verb call carries its own `--key`; the report verbs are reads and take none. Every `sim run`
below is preceded by `e2e_scene_ready <id>` on its pack, after the explicit `scene accept` the step names (from
BD-228 the linter rule `scene-ready-before-run` fails a script whose run has no such line).

1. `frob --json scene gen --family home --seed 3 --key src-gen-3`; `frob --json scene accept <id> --key
   src-acc-3` (a run needs an accepted pack, BD-228); `frob --json sim run quad-a --scene <id> --tier referee
   --seconds 2 --key src-run-3` (`quad-a` is the reference quadruped of the verb registry's examples).
2. `frob --json report run <run> --claims-realism` (the report verb of BD-302, through which the claim is routed
   here): exit 3, code 312, the assumed row identifiers listed under the scene, the repairs in rank order.
3. The same without the flag: exit 0 or 2, and "N dimensions assumed" beside the scene.
4. Seed 4 generated, accepted and run the same way (`src-gen-4`, `src-acc-4`, `src-run-4`); `frob --json report
   design quad-a --claims-realism`, whose package spans both runs: refused, both scenes collected and listed.
5. A copy of the seed-3 pack in the scratch store whose manifest count is edited to zero: `frob --json scene
   show <copy>` is refused on load by the recount (N19a-05), so the edited pack is never admitted to a claim.
6. In the scratch registries, every row the seed-3 pack draws from promoted through the promotion procedure to
   `norm: test-norm`, a `synthetic` entry of the scratch source register with a read date (clearly labelled,
   never shipped); `frob --json scene gen --family home --seed 3 --key src-gen-3b`: a new `scene_id`, count
   zero; accepted and run (`src-acc-3b`, `src-run-3b`); the claimed report on that run passes and names the
   source, while the old pack of step 1 keeps its count and its report of step 2 is still refused.
7. The step-6 pack run under `fixtures/tasks/hazard_draw_home.ftask` (`synthetic`: its randomization section
   draws from a scratch row `home.test-ridge` left `assumed`; `frob --json sim run quad-a --scene <id> --task
   fixtures/tasks/hazard_draw_home.ftask --tier referee --seconds 2 --key src-run-3c`), then the claimed
   report: exit 3, code 312, `home.test-ridge` listed under the run and nothing under the scene.
8. The two planted cases through `e2e_expect_caught`: `relabel-without-source` (a row changed to `norm: fake`
   with no register entry: the registry-load refusal of BD-227, never a passing claim) and `edited-count`
   (step 5 with the recount disabled: the claim would pass, so the assertion of step 5 fails).

Every line carries the charter fields (`ts`, `script`, `bead`, `step`, `event`, exact command line, exit code,
wall time, the envelope's `evidence` block); the `refusal` block with the assumed rows per scene and per run;
the counts before and after; the old and new `scene_id`; on failure the first differing row identifier and the
report path. The `summary` gives assertion counts, refusals expected and controls caught; the script claims no
gate.

### Known answers and negative controls

Known answer: at plan time 59 hazards in seven archetypes, every one `assumed`, so every generated interior has a
non-zero count. Negative controls: the relabel mutant; the edited count. Determinism: checks are exact (class D0).

## Considerations

- Open question OPEN-HAB-1: which published building and workplace norms supply the dimension distributions.
  Default: generic ranges labelled `assumed`, and realism claims refused. Owner: project lead. It blocks the
  interior gate for claims of realism, not for validity. The companion question on retrofit prices and legality
  (OPEN-HAB-4) is handled the same way: prices `assumed`, constraints marked unchecked in every report, no claim
  about cost in a published report.
- Norms differ by country and building type; a promotion records which norm, so two registries for two
  jurisdictions are two registry versions, not one row with a wider range.
- A norm states what is permitted, not what is common; using a norm as a distribution is itself an assumption and
  the record must say which reading was taken.
- The synthetic source used by tests must be impossible to ship: the release lint rejects any register entry
  labelled `synthetic`.
