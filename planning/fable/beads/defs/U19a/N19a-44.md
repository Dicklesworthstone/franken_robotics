## Background

Contact properties and optical properties of a surface are two maps, joined only by declared shared latent
variables. The reason is that a glossy tile can produce a bad depth sample and low traction for unrelated reasons,
and a model that ties them together fabricates a correlation. Three checks enforce the decision. Changing the
optical card of a region leaves every physics digest unchanged in a run whose controller does not consume
exteroception. Changing the interface card of a region leaves every ray-kernel output unchanged. Changing a shared
latent changes both in the recorded direction. The fixture is one floor tile in four states: matte dry, glossy dry,
matte wet, glossy wet.

The gate GATE-HAB-05 (Known answer, M3) requires that the four-state tile behaves so on every tier, bit for bit
within the determinism class. "Bit for bit" is what makes this an end-to-end test: the claim is about digests of
real runs on the referee, on `batch-cpu`, on CUDA and on Metal, not about the structure of a data type.

## Scope

In: the script, the tile fixture and its four variants plus the latent variant, the digest comparisons per tier,
the negative control, the structured log and the gate receipt. Out: the region table and latents (BD-229); optical
cards (N19a-06); ray kernels (BD-187); the divergence search used to localize a failure (BD-206).

## Technical approach

1. **Fixture** (`fixtures/scenes/tile4/`, `synthetic`). A 4 m × 4 m floor with one 1 m × 1 m tile region at the
   centre. Cards: optical `matte` (class `diffuse`) and `glossy` (class `specular-floor`, low `roughness`, higher
   `r0`); interface condition `dry` and `wet` on one floor material. Five scene variants:

| Variant | Optical card | Interface condition | Latent |
|---|---|---|---|
| MD matte dry | matte | dry | none |
| GD glossy dry | glossy | dry | none |
| MW matte wet | matte | wet | none |
| GW glossy wet | glossy | wet | none |
| L(w) latent | from `wetness` by its optical conditional | from `wetness` by its interface conditional | `wetness` = w, for w ∈ {0, 1} |

2. **Runs.** On each variant and each tier: (P) a physics run: a 10 kg block with four contact samples is pushed
   across the tile by an open-loop force script for 500 steps (no controller reads any sensor), recording the
   per-step state digest; (R) a ray run: a fixed depth camera and a fixed lidar scan the tile for 50 frames with
   no body moving, recording ranges, intensities and mask reasons and their digest.
3. **Comparisons.**

| Check | Compare | Expected |
|---|---|---|
| (a) optical change, physics unchanged | P(MD) against P(GD); P(MW) against P(GW) | Digests equal at every step |
| (a′) optical change is visible | R(MD) against R(GD) | Digests differ (so (a) is not vacuous) |
| (b) interface change, rays unchanged | R(MD) against R(MW); R(GD) against R(GW) | Digests equal for every frame |
| (b′) interface change is felt | P(MD) against P(MW) | Digests differ; slide distance on wet exceeds dry |
| (c) latent changes both, in the recorded direction | P and R of L(0) against L(1) | Friction coefficient offered to the cone falls; specular return weight rises; L(0) equals the corresponding dry and matte-side values of its conditionals |

4. **Tiers and classes.** Referee; `batch-cpu` in `f64` and `f32`; CUDA; Metal. "Equal" means bit equality of
   digests within one tier (class D2: the same bits run to run on one backend). Across tiers the comparison is
   not required to be bitwise; each tier is judged on its own pair of runs. Each pair is also run with the two
   variants as co-tenant worlds of one batch and in separate batches, to show that the equality does not depend
   on batch composition.
5. **Commands.** Every `run` verb call carries its own key, and the two runs of each compared pair carry distinct
   keys. `frob --json scene compile fixtures/scenes/tile4/<variant>.src --key t4-cmp-<variant>`; `e2e_scene_ready
   <id>` (`frob --json scene accept <id> --key e2e-ready-…`: a run refuses an unaccepted pack with `FROB-REF-318`,
   BD-228); `frob --json sim run fixtures/scenes/tile4/push-block.fbot --scene <id> --task
   fixtures/tasks/tile-push.ftask --tier <tier> --seed 5 --key t4-p-<variant>-<tier>` (the design is the 10 kg
   block with its four contact samples; the open-loop force script is in the task); `frob --json sim run
   fixtures/scenes/tile4/scan-rig.fbot --scene <id> --task fixtures/tasks/tile-scan.ftask --tier <tier> --seed 5
   --key t4-r-<variant>-<tier>` (the fixed depth camera and lidar); the co-tenant runs of item 4 carry their own
   keys (`t4-p-cotenant-<pair>-<tier>`); `frob --json telemetry
   divergence <runA> <runB> --mode exact` (expected: no divergence, or the first divergent step and quantity).
   (`--seed` is `sim.run`'s input of BD-024, the `run_seed` of every world address, which VERBS-sim now lists;
   it stays in the commands because the run's world draws must be pinned.)
6. **Logging.** Newline-delimited JSON to `target/e2e-logs/scene_four_state_tile/<utc-timestamp>.ndjson` with a
   transcript. Per line: `ts`, `script`, `bead` ("N19a-44"), `step`, `event`, the exact command line, exit code,
   wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), the two run
   digests compared, measured slide distances in metres and friction coefficients, the specular weights, and on
   failure the first differing step, the differing quantity and the paths of both runs. Final `summary`: counts
   of assertions and the gate touched (GATE-HAB-05).
7. **Gate receipt.** Per tier: the outcome of checks (a), (a′), (b), (b′), (c) with the digests; commit, hardware
   fingerprint, seed. PASS only if every check holds on every tier present; absent tiers are listed as `not run`.
   The script writes the receipt and the log; it never writes the gate's status (KNOWN_DRIFTS 9). A session that
   did not implement BD-229 records the value with `cargo run -p frob-conformance --example record_gate -- --gate
   GATE-HAB-05 --receipt <hash>`; this bead is the gate's one recorder, and BD-229 records nothing of it.

## Acceptance criteria

- [ ] On every tier present, checks (a) and (b) hold bit for bit, and (a′), (b′) show the changes are real.
- [ ] Check (c) holds: with the latent at 1 the friction coefficient is lower and the specular weight higher than
      at 0, matching the recorded directions of the two conditionals.
- [ ] The equalities hold with the two variants in one batch and in separate batches.
- [ ] The negative control (a build that derives friction from `r0`) fails check (a) and the log shows the first
      divergent step.
- [ ] GATE-HAB-05 recorded with digests, commit, hardware fingerprint and seed; this record, with CUDA and Metal
      among the tiers, closes the done-condition of the seed BD-229, which runs the referee and `batch-cpu`
      checks itself.
- [ ] The wet variants run with the film law (BD-230, film patch N19b-05) on and off, and checks (a) and (b) hold
      in both.
- [ ] The script is idempotent and its log validates against the STD-E2E schema.

## Test plan

### Unit tests

Helpers: `digest_pair_comparator` (equal digests pass; one flipped bit fails and reports the step);
`vacuity_guard` (a pair whose "must differ" runs are equal fails the script: guards against comparing a scene
with itself).

### End-to-end script and logging

`scripts/e2e/scene_four_state_tile.sh`, as specified above. Runtime target under ten minutes per tier (TARGET).

### Known answers and negative controls

KA-436 (one floor tile in four states: an optical change leaves every physics digest unchanged in a run whose
controller does not consume exteroception; an interface change leaves every ray-kernel output unchanged; the
latent changes both in the recorded direction; exact, bit for bit within the determinism class; control: a build
that derives friction from `r0` fails). CX-199 (gloss and friction sharing one material property). Second negative
control: a build in which the ray kernel reads the interface condition (for example darkening wet floors from the
contact card) fails check (b). Metamorphic relations: optics is a noninterfering input to physics and the contact
card a noninterfering input to rays. Determinism lanes: each pair twice on one machine; across worker counts;
across batch composition; each backend against its class.

## Considerations

- The physics run must be open-loop. With a controller that consumes exteroception an optical change may
  legitimately change physics through the controller; that case is outside the gate's wording and the script
  refuses to run check (a) with a closed-loop task.
- The film-friction law, when enabled on the wet variants, reads film thickness and the card's roughness on the
  contact side only; it must not read the optical card. The script runs the wet variants with the film law on and
  off.
- If bit equality fails only on one device backend, the divergence output localizes the kernel; the cause is
  usually a shared buffer layout in which an optical field reorders a contact field's memory.
