## Background

The M6 milestone ("frontier physics": admit the physics and sensing that make more failures visible, behind feature flags
and off the critical path) lists "RGB and splat scenes" among its epics, in the work package for frontier physics and
sensing. The plan says little more, and what it says constrains the epic tightly:

- **What RGB is, where the plan mentions it.** Cameras are modelled in tiers. Solid from M2: per-row sample instants
  (rolling shutter), exposure by its midpoint, depth and identifier images from ray kernels on the collision field.
  Frontier: "radiometric RGB: shot and read noise, glare, lens distortion; rasterized textured meshes for policies. Not
  needed by any task before M5." The plan adds that the Frontier sensor models are on no task's path before M5, that each
  is funded only when a registered task needs it, names one analytic fixture as its pilot when it is, has no speed
  benefit to claim, and falls back to the mask-only model under the same cost rule (more than 25% added ray cost kills).
- **What a splat scene is.** The plan does not define it. Read in context (this epic depends on real-place ingestion), it
  is an appearance representation of a captured place as a set of oriented, coloured Gaussian primitives, rendered to
  produce RGB observations. Its tier is unstated; until the short plan fixes it, it is treated as Moonshot (fail-closed).
- **NONGOAL-01.** A photorealistic renderer is a non-goal: sensors need geometry-correct depth, timing and labels first;
  hero images come from the sibling's offline path tracer. Nothing in this epic may be described as photorealism.
- **ADR-HAB-04 and INV-HAB-02.** The visual mesh is read by the viewer only; physics, sensors and stills read only the
  collision field, the overlays and the maps; no code path carries visual-mesh data into a result. RGB for policies would
  be a result computed from appearance data, so it cannot be fed from the viewer's mesh: it needs an appearance asset that
  is inside the scene's identity, licensed, and marked private when the place is.
- **Privacy.** A pack built from a scan of a real place is private, stored outside the repository; everything derived
  from it inherits the mark, including (by default) policy weights trained in it.

Each M6 epic needs its own short plan, its paper-scale pilot and its kill gate before work starts; an epic stops when its
pilot's falsifier holds or its kill gate fires. This seed bead's done-condition is exactly that preparation: a short plan
exists and its pilot has run; a kill gate and its fallback are written before any work package is funded. No mechanism is
built under this epic until then.

## Scope

In (children): the short plan with the kill gate and fallback written and registered (N19b-23); the paper-scale pilot
(N19b-24).

Out: any renderer, splat importer or RGB kernel (work packages are created only after the pilot passes, the kill gate is
registered and the owner funds the epic); stills for agents and pixel inspection (Solid, exist from M2); optical failure
modes of depth sensors (Solid and Frontier beads of the sensing chapter); asset-populated interiors (M5).

## Technical approach

The preparation, in order:
1. **Write the short plan (N19b-23).** It must answer: which registered task needs RGB and what decision changes with it;
   where appearance lives in the scene pack so that INV-HAB-02 still holds; how appearance is registered to the collision
   field and what the acceptance check is; how rasterization and splat compositing stay inside the determinism classes;
   the radiometric model; the privacy and licence handling of captured appearance; the cost model; the tier of each part.
2. **Write the kill gate and its fallback (N19b-23).** The plan names none for this epic. The proposal to register:
   trigger: the mechanism breaks the fixed launch shape or the determinism class of a batch, or adds more than 25% to the
   ray-stage cost, or changes no registered task's outcome on its battery; fallback: the mask-only model (geometry-correct
   depth, timing, labels and optical classes from the collision field). It enters the gate register by a dated amendment.
3. **Run the pilot (N19b-24).** Paper-scale, hand-checkable: which hazard-registry failure classes and registered tasks
   need colour or texture that depth, intensity and labels do not already expose; and one analytic fixture each for a
   radiometric pixel and for one projected Gaussian primitive. Falsifier: the list of tasks that need RGB is empty.
4. **Hand the result to the owner** for the funding decision; only then are work-package beads written.

## Acceptance criteria

- [ ] A short plan exists and is on file in the delivery log (N19b-23), answering every question listed above (seed done-condition).
- [ ] A kill gate with its trigger, its numbers and its fallback is written and registered in the gate register by a dated amendment, before any work package is funded (seed done-condition).
- [ ] The pilot has run and its result, including a negative one, is in the pilot register (N19b-24) (seed done-condition).
- [ ] No code for RGB or splat rendering exists in the product before these three are on record; a check in the M6 exit review confirms it.
- [ ] If the pilot's falsifier holds, the epic closes with reason `fallback` (the mask-only model) and no work package is created.

## Test plan

### Unit tests
The pilot's analytic fixtures are tested in N19b-24 (pixel statistics of the radiometric model; the projected footprint of one Gaussian primitive).

### End-to-end script and logging
`scripts/e2e/rgb_splat_preparation.sh` (STD-E2E helper; NDJSON under `target/e2e-logs/rgb_splat_preparation/`) checks the three records exist in the right order (plan and kill gate registered before the pilot's result; pilot result before any work-package bead), that `registries/gates.toml` has the new kill-gate row with status `not run`, and that `frob capabilities --json` lists no RGB or splat capability. Lines log each check as an `assert` with the record's identity and commit; the summary names the kill gate registered.

### Known answers and negative controls
A planted work-package bead dated before the pilot's result must make the ordering check fail.

## Considerations

- The strongest risk is scope: an RGB path invites a renderer. NONGOAL-01 stands; the plan must state what is not built.
- Determinism is the hard constraint: hardware texture filtering is banned (manual interpolation in kernel source), floating-point atomics are banned, sorting must be stable with total-order keys. Splat compositing depends on a depth sort and on blending order; if it cannot be made bitwise per backend it is class D3 at best and its uses shrink accordingly.
- A captured appearance is private data. Stills, replays, reports and policy weights derived from it inherit the mark; logs must never contain it.
- Appearance must never become a second geometric authority: the collision field stays the only geometry in the model identity, and the collision-to-appearance deviation is measured and reported like the collision-to-visual deviation.
- No North-Star scenario is tagged M6; the epic's plan must name its own acceptance story.
