## Background

A clearance complex is worth storing: one complex answers every margin query for a footprint family, every start and goal
in its slab, and it is read by several consumers. The format registry gives it a row: identifier `FMT-FCLEAR`, extension
`.fclear`, schema `frob.clearance/1`, owner crate `frob-scene`, produced by `frob-scene` from a scene and a footprint
family, consumed by `frob-analyze` (the clearance analysis and the place stage of preflight), `frob-mission` (route
feasibility in mission queries) and `frob-lemma` (certificate bundles), and classed "canonical and derived: reproducible
from the identities of its inputs". The registry's rules (ADR-WS-03) apply: one owner holds the schema, the
canonicalization, the reference reader and the version refusal; no other crate parses the bytes; identity is the BLAKE3
hash of the canonical bytes under a domain string equal to the schema name; large data are blobs addressed by hash; a
manifest never embeds a machine path. (Some chapter prose wrote the schema as `frob.fclear/1`; the format registry owns
schema names, so it is `frob.clearance/1`.) The scene manifest's `feasibility.fclear` field holds the hash of the
nominal-footprint complex computed at compile.

Tier Frontier (the mechanism is Frontier), feature `frontier-fclear`.

## Scope

In: the manifest schema and typed value; the cell blob layout; the refinement-patch table; canonical writer and reference
reader; the derived-identity rule and its check; refusals; the registry row; round-trip and mutation tests.

Out: computing cell values (N19b-26); sweeps and answers (N19b-28); refinement logic (N19b-29); certificates and their
bundle kind (N19b-31); the thirteen-format campaign of the format gate (BD-410).

## Technical approach

**1. Manifest (canonical JSON), fields all required unless noted.**

| Field | Meaning |
|---|---|
| `schema` | Exactly `frob.clearance/1` |
| `fclear_id` | The identity; checked against a recomputation on read; excluded from the hashed body |
| `scene_id` | The scene pack this complex is about |
| `footprint` | Outline vertices and reference point as exact decimal strings in metres; `rho_m`; a family name |
| `slab` | `z_lo_m`, `z_hi_m`, and the envelope they were derived from |
| `modes` | The assignment of fixture modes (for example door D3 `open`), sorted by fixture identifier |
| `movables` | `excluded` or `as-placed` |
| `lattice` | `origin_m`, `delta_m`, `nx`, `ny`, `headings`; ψ is periodic |
| `error` | `eps_field_mm`, `u_reg_mm`, the raster pitch, and e for the base lattice in millimetres |
| `unknown` | Whether the scene has an unknown mask and that it was applied as blocked-inner, free-outer |
| `cells` | Blob reference: hash and byte length of the base lattice values |
| `patches` | Refinement patches: each a box of base cells, a subdivision level per axis, and a blob reference |
| `producer` | `frob-scene` version and the settings that affect values |
| `authorization` | The three no-authorization flags, all `false` |

**2. Cell blob.** Base lattice: for each cell, `c_lo_mm` then `c_hi_mm` as little-endian `i16` (four bytes per cell), in
index order x fastest, then y, then ψ. c_lo is a rounded-down lower bound, c_hi a rounded-up upper bound; `i16::MAX` in
c_hi means unbounded above; `c_lo ≤ c_hi` always. A refinement patch replaces the base cells it covers with a denser
block in the same order at its own Δ and δ; patches may nest by level but never overlap at one level.

**3. Typed value (DESIGN).**

```rust
pub struct FclearId(Blake3);
pub struct ClearanceComplex { manifest: FclearManifest, base: CellBlock, patches: Vec<Patch> }
pub struct Patch { region: BaseBox, level: [u8; 3], cells: CellBlock }   // level per axis: x, y, ψ
impl ClearanceComplex {
    pub fn cell(&self, addr: CellAddr) -> CellValue;        // resolves through patches to the finest covering cell
    pub fn neighbours(&self, addr: CellAddr) -> impl Iterator<Item = CellAddr>;  // face adjacency, ψ periodic, mixed levels
}
```

**4. Identity.** `FclearId` = BLAKE3 under the domain `frob.clearance/1` of the canonical manifest bytes without
`fclear_id`. Because the manifest contains the blob hashes, the identity covers every cell value. "Derived" means more:
the complex must be reproducible from the identities of its inputs. Two complexes built from the same (`scene_id`,
footprint, slab, modes, movables setting, lattice, producer settings, refinement request) must be byte-identical; the
reader offers `verify_derivation(scene)` which recomputes and compares, and the conformance battery uses it.

**5. Reader admission order.** Raw-byte validation (a repeated member name is refused before any digest); schema and
major version (`FROB-REF-891` for an unknown major version or unknown required field); required fields; blob references
resolve and sizes equal the lattice arithmetic (nx·ny·headings·4 bytes), else `FROB-REF-303`; value invariants
(c_lo ≤ c_hi; patches inside the lattice and not overlapping); recomputed identity equals `fclear_id`, and every blob's
recomputed hash equals its reference (otherwise an **integrity fault**: the refusal row `scene-pack-identity-mismatch`
of N19c-42 (row 4, family `9xx`, class `integrity`, exit 9, retry `never`), which covers every content-addressed
Habitat artifact; the reader raises it through the constant `IDENTITY_MISMATCH` of
`crates/frob-scene/src/refusal/late.rs` with block fields `artifact = "fclear"`, `stated`, `recomputed`, `blob` (the
reference that failed, or `manifest`) and `path_class` (never a private path). It is an alarm, never an input error;
its ranked repairs are the row's: regenerate the complex from its scene and query and compare identities; run the
store check on the blob named; keep both hashes and file the mismatch. The code is cited by slug: its number is
whatever the ledger assigns, and no number is typed here). The cited `scene_id` must be the scene the caller bound, else
the complex is refused as stale. A view
offered as an identity is `FROB-REF-892`; a `.fclear` that reaches a verb without passing this reader is `FROB-REF-893`.

**6. Numbers.** Lengths in the manifest are exact decimal strings (so identity does not depend on a float parser);
integers are JSON integers below 2⁵³; no NaN or infinity.

**7. Classes.** D0: bytes and hashes exact, and values exact by N19b-26.

## Acceptance criteria

- [ ] `registries/formats.toml` has the `FMT-FCLEAR` row and `schemas/` regenerates unchanged.
- [ ] 10,000 seeded round trips canonical → value → canonical give zero byte differences; every one of 10,000 single-byte mutations either fails to parse or changes the identity.
- [ ] The base blob of a 240 × 160 × 32 lattice is exactly 4,915,200 bytes (4.69 MiB).
- [ ] Rebuilding from the same inputs on Linux and macOS yields the same `FclearId`; `verify_derivation` rejects a blob with one altered cell even when hashes are made consistent.
- [ ] A complex bound to a different `scene_id` is refused as stale; unknown major version returns `FROB-REF-891`; a blob of the wrong length returns `FROB-REF-303`; a blob with one flipped byte, or a manifest whose recomputed identity differs from `fclear_id`, is refused with `scene-pack-identity-mismatch` (class `integrity`, exit 9, `artifact = "fclear"`) naming the failing reference.
- [ ] A manifest with a repeated member name is refused before any digest; two respellings of one manifest (reordered keys, other whitespace) bind one identity.
- [ ] Lookups through nested patches return the finest covering cell, and `neighbours` is symmetric (if A lists B, B lists A) on mixed levels.

## Test plan

### Unit tests
`crates/frob-scene/tests/fclear_format.rs`, `cargo test -p frob-scene --features frontier-fclear --test fclear_format`.
- `roundtrip_seeded_10k`; `mutation_changes_identity_or_fails`.
- `blob_length`: 1,228,800 cells → 4,915,200 bytes.
- `c_lo_le_c_hi_enforced`: a cell with c_lo > c_hi is refused.
- `patch_rules`: overlapping patches at one level refused; a patch outside the lattice refused; nested levels accepted.
- `neighbour_symmetry_mixed_levels`: a base cell next to a level-2 patch lists the patch's face cells, and each of them lists the base cell.
- `psi_wraps`: heading index 0 and index headings − 1 are neighbours.
- `derived_identity`: two builds from equal inputs are byte-equal; a changed raster pitch changes the identity.
- `stale_scene_refused`; `version_891`; `view_892`; `bypass_893`.
- `integrity_fault_exit_9`: one flipped byte in a cell blob gives the row `scene-pack-identity-mismatch` (the code the
  constant `IDENTITY_MISMATCH` holds), class `integrity`, exit 9, `artifact = "fclear"`, `blob` naming that blob and
  both hashes in `stated` and `recomputed`; an altered manifest field with the blob hashes intact gives `blob: manifest`.
- `duplicate_member_refused`: a manifest with `lattice` twice is refused at raw-byte validation, before any digest.
- `key_order_one_identity`: the manifest with its members in reverse order and with extra whitespace reads to the same
  value and the same `FclearId` (the format's known answer: hashing the file as written is the counterexample).

### Known answers and negative controls
- KA-450: 240 × 160 × 32 = 1,228,800 cells, 4.69 MiB at four bytes per cell.
- Format known answers: reordered keys give one identity; hashing the file as written is the counterexample.
- Negative controls: a reader that tolerates an unknown required field must fail `version_891`; a writer that emits `c_hi` rounded down must be caught by the one-sidedness test of N19b-26 run on the round-tripped complex.
- Determinism lanes: twice on one machine; debug and release; Linux and macOS: identical bytes.

## Considerations

- Size: a warehouse floor (60 m × 40 m) at the default lattice is 30.7 million cells, 117 MiB; the world bank holds complexes among its resident data, so the size is reported by `sim.estimate` and the manifest.
- A complex is bound to one scene identity. A retrofit or any scene edit produces a new scene and therefore needs a new complex; only untouched regions' values coincide, and no reuse across scene identities is claimed.
- Private scenes: a `.fclear` of a private pack inherits the private mark and stays under the private root.
- Schema evolution: adding an optional field keeps the major version; migration is a typed edit producing a new artifact.
