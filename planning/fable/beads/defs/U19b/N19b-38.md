## Background

Every repair a design loop normally searches lives in the robot. Some failures are caused by one feature of the building
that costs little to change: a threshold, a door closer, an exposed cord, a glass door with nothing on it. ADR-HAB-09:
the building is a design variable; scene edits are typed and priced, and a retrofit is compared with a robot redesign in
one budget. Reason: a failure caused by a 20 mm threshold may be cheaper to remove from the building than from the robot.
Rejected alternative: free-form scene editing by an agent, which has no price, no install constraint and no declared
effect, and so cannot enter a budget or be audited.

This bead is the catalog. The edit machinery it instantiates (the closed set of edit kinds, their application to an
immutable pack, the lineage record and the declared-aspect check) is Solid work at M3 in N19b-44, because the
adversarial search and the split rules need edits a milestone before the catalog; steps 3 and 4 below restate it as
the catalog uses it. `registries/retrofits.toml` lists typed building amendments, about forty
at first (TARGET). Each entry is a typed scene edit with its parameters, the hazards it applies to, a price with
provenance, an install class (`renter-safe`, `landlord`, `contractor`), constraints on its parameters, and a declaration
of which aspects of the scene it changes (geometry, material, optics, clocks, actors). Ownership: `frob-scene` owns the
catalog, the typed scene edits and the enumeration of kits; it links no crate above layer 2. The same typed edits are
the vocabulary the adversarial search uses to mutate scenes, which is also the fallback use if KILL-RETROFIT fires.
Tier Frontier, feature `frontier-retrofit`; funded after the pilot (N19b-37).

## Scope

In: the registry schema and loader; catalog entries as instances of the typed edit kinds, with their parameters,
hazard links and declared aspects; the constraint language; install classes and mission permission; prices and their
provenance; the declared-aspect check run over every entry as a load-time test; the sixteen listed entries and the
extension toward forty; kit validation and `FROB-REF-313`; catalog queries for other consumers, including the handler
of the `retrofits` kind of the resource `frob://catalog/{kind}` (section 7).

Out: the edit type, the closed set of kinds, `apply`, lineage and the aspect digests (N19b-44, M3); localization and kit
enumeration (N19b-39); the search verb (N19b-40); price sourcing (N19b-43); the adversarial search's own edits beyond
the shared vocabulary (BD-270).

## Technical approach

**1. An entry** (the plan's example, verbatim in form):

```toml
[[retrofit]]
id          = "threshold-ramp"
edit        = { kind = "add-overlay", shape = "wedge", params = ["rise_m", "run_m", "width_m"] }
applies_to  = ["threshold", "sliding-door-track", "dock-plate-lip"]
install     = "renter-safe"
cost        = { value = 12, currency = "USD", provenance = "assumed" }
constraints = [{ expr = "run_m >= 12 * rise_m", provenance = "assumed" }]
changes     = ["geometry"]
```

**2. The first sixteen entries** (edit kind in the closed set of step 3; `changes` as the plan gives them):

| Amendment | Scene edit | Changes | Hazard it addresses |
|---|---|---|---|
| Threshold ramp | Add a wedge overlay | Geometry | Threshold, door track, dock lip |
| Door-closer adjustment | Lower the closer torque parameter | Actors | Door the robot cannot push |
| Door holder | Fix a door's mode to open | Actors, geometry | Door on the route |
| Cord raceway | Replace a cord by a low bevelled cover | Geometry | Cord across a path |
| Rug gripper | Fix a rug slab; raise rug-to-floor friction | Material, actors | Rug that slides or folds |
| Fiducial marker | Add an optical marker region | Optics | Localization alias |
| Glass-door decal band | Change a band of a glass region to `diffuse` | Optics | Glass not seen by optical ranging |
| Motion-activated light | Raise the lighting level in a zone | Optics | Long exposure, blur |
| Floor mat on a wet zone | Change the interface card of a region | Material | Film on tile |
| Finer drain cover | Reduce the slot pitch of a grate overlay | Geometry | Castor drop |
| Anti-slip tape on a ramp | Change the interface card of a strip | Material | Ramp traction |
| Cable bridge | Add a bevelled overlay over a tray | Geometry | Cable tray |
| Dock leveller plate | Add a hinged plate over a lip | Geometry, actors | Dock lip |
| Docking guide | Add guide geometry at a dock | Geometry | Docking tolerance |
| Bump-stop absorber | Add a compliant fixture at an impact point | Geometry, material | Impact energy at a known stop |
| Aisle marker | Add distinguishing optical regions per aisle | Optics | Identical aisles |

The remaining entries toward forty are drafted from the pilot's list of uncovered hazards; each new entry must name at
least one hazard-registry row.

**3. Edit kinds (the closed enum of N19b-44, thirteen kinds; an unknown kind is a load error; the catalog uses these).** `add-overlay` (wedge, box, rounded box, bevel,
cylinder, bar pattern); `set-overlay-param`; `replace-with-overlay` (a movable or proxy replaced by a fixed overlay);
`add-fixture` (an articulated or compliant fixture from the fixture models); `set-fixture-param`; `set-fixture-mode`;
`fix-movable`; `set-interface-card` and `set-interface-param` (on a region or strip); `set-optical-card` (on a region or
band); `add-optical-region`; `set-lighting` (a zone's level); and `set-source-param` (a structural change such as an
opening's width; none of the first sixteen entries uses it). Aspect vocabulary: `geometry`, `material`, `optics`,
`clocks`, `actors`; it maps onto the adversarial search's edit classes as geometry ↔ Geometry, material ↔ Material,
optics ↔ Optics, actors ↔ Fixture, clocks ↔ Clock and link.

**4. Applying an edit, as numbered steps** (the function is N19b-44's; step 1 and the catalog version in step 4 are what
this bead adds). `apply(scene, instantiated_edits) -> ScenePack`:
1. Validate each instantiated amendment (step 5).
2. Apply the edits to the scene's source description (overlay list, region tables, fixture tables, movable tables,
   lighting), never to bricks directly; a scene is immutable, so the result is a new scene.
3. Recompile only what the edits touch: an overlay edit changes the overlay list and index; a card change changes a
   region table row; a geometry edit that needs bricks recomputes the bricks within the truncation distance of the change.
   The variant shares all untouched bricks with its base through the pool.
4. Re-run the acceptance fixtures that the touched aspects can affect; record the edit list, the base `SceneId` and the
   catalog version in the variant's provenance; keep the base's split group and licence entries.
5. **Declared-aspect check:** compare base and variant: an edit that declares only `optics` must leave every
   physics-relevant table byte-identical; one that declares only `material` or `geometry` must leave the optical map
   byte-identical unless it also declares `optics`; a mismatch is a catalog defect and a load-time test failure.

**5. Constraints, install classes, validation.** A constraint is an expression over the entry's parameters: comparisons
(`>=`, `<=`, `>`, `<`, `==`) between sums and products of parameters and decimal literals, evaluated in exact rational
arithmetic; parameter names carry their unit as a suffix (`_m`, `_nm`, `_deg`). Each constraint has a provenance
(`assumed` until a source is recorded; reports mark such constraints unchecked). Install classes are ordered
`renter-safe` < `landlord` < `contractor`; a mission states the highest class it permits. A **kit** is a set of at most
three instantiated amendments. A kit is valid when every parameter is in its declared range, every constraint holds, every
install class is permitted, and no two amendments edit the same target incompatibly. A request to apply or evaluate a kit
that violates a constraint or uses an install class the mission does not permit is refused with `FROB-REF-313` (repairs:
choose another amendment; widen the permitted class); exit code 3.

**6. Prices.** `cost = { value, currency, provenance }`; one currency per catalog; a kit's price is the sum. Prices and
legality constraints are `assumed` until a source is recorded (OPEN-HAB-4); every report that prints a price prints its
provenance, and `--strict-data` refuses a cost verdict built on `assumed` prices with the refusal row
`retrofit-cost-on-assumed-prices` of N19c-42 (row 9: family `3xx`, exit 3, retry `after-change`, block
`assumed_prices[]` (each catalog entry or bill line with its field) and `comparison` (the two options); repairs: record
a cited source or quote for each price named, with its date; ask without `--strict-data` and get the verdict labelled
`prices: assumed`; ask only for the flip verdict, which needs no price). It is raised through the constant
`RETROFIT_COST_ASSUMED_PRICES` and cited by slug, never by a typed number. This bead provides the predicate the check
reads (`Kit::assumed_prices() -> Vec<PriceRef>`, empty when every price has a recorded source); the comparison step
that raises it is N19b-40's.

**7. Queries.** `catalog.addressing(hazard_key) -> Vec<RetrofitId>` (used by the place stage of preflight to name "the
retrofit that removes" a bottleneck); the catalog as an MCP resource; `scene.show` lists a variant's applied edits.
The resource is the `retrofits` kind of N32a-25's `frob://catalog/{kind}`. No verb lists the catalog (`scene.retrofit`
reads it from the registry and is not a listing), so N32a-25's rule "a catalog kind whose listing verb does not exist
yet is served when that verb lands" never serves it; this bead adds the kind's hand-written `#[resource]` handler in
`frob-mcp` (the generation rule permits hand-written resource handlers): it reads the catalog through this bead's
loader, pages it with N32a-25's one cursor implementation, authorizes the read with `scene:read` (the scope of
`scene.list`, the scene cluster's catalog verb) and returns each entry as the registry holds it, so its content is
the loader's output byte for byte.

**8. Determinism and evidence.** Loading, validation and pricing are exact (D0). A variant's `SceneId` is a function of
the base identity and the instantiated edits on every platform (INV-HAB-10 applies to variants).

## Acceptance criteria

- [ ] `registries/retrofits.toml` loads with the sixteen entries above and every further entry naming a hazard row; an unknown edit kind, aspect or hazard key is a load error.
- [ ] Applying `threshold-ramp` with rise 0.020 m, run 0.240 m gives a new `SceneId`, the same split group, shared untouched bricks, and a variant whose provenance lists the edit.
- [ ] `run_m = 0.200` at `rise_m = 0.020` violates `run_m >= 12 * rise_m` and returns `FROB-REF-313` with both repairs; a `contractor` amendment under a mission permitting `renter-safe` returns `FROB-REF-313`.
- [ ] The declared-aspect check passes for all entries and fails for a planted entry that declares `optics` and changes a friction card.
- [ ] Kit price equals the sum of entry prices; provenance `assumed` is printed; `Kit::assumed_prices` lists exactly the entries whose price has provenance `assumed` (the input of the `retrofit-cost-on-assumed-prices` refusal that N19b-40 raises under `--strict-data`).
- [ ] The same base and edits yield the same variant `SceneId` on Linux and macOS.
- [ ] `resources/read` of `frob://catalog/retrofits` through `frob-mcp` returns the sixteen entries (and any further ones), paged to completion, equal to the loader's output; a session without `scene:read` is refused.

## Test plan

### Unit tests
`crates/frob-scene/tests/retrofit_catalog.rs`, `cargo test -p frob-scene --features frontier-retrofit --test retrofit_catalog`.
- `load_sixteen`: ids, kinds, aspects and hazard links as in the table.
- `constraint_eval_exact`: `run_m >= 12 * rise_m` at (0.24, 0.02) true, at (0.2399, 0.02) false, in rationals.
- `constraint_parser_rejects`: unknown identifier, missing operator, unit-less parameter name.
- `install_class_order`.
- `apply_threshold_ramp`: overlay count +1; bricks unchanged (overlay-only edit); new `SceneId`; group kept.
- `apply_closer_adjustment`: only the fixture table row changes; physics-irrelevant maps untouched.
- `declared_aspects_all_entries`: property over all entries on a fixture scene.
- `planted_wrong_aspect_caught`.
- `kit_conflict`: two edits setting the same door's mode differently make the kit invalid.
- `variant_inherits_licences_and_group`.
- `ref_313_cases`.
- `assumed_prices_listed`: a kit of `threshold-ramp` (price `assumed`) and an entry given a cited price lists exactly the first under `assumed_prices`; a kit of cited prices lists none.
- `retrofits_resource` (`crates/frob-mcp/tests/catalog_retrofits.rs`, `cargo test -p frob-mcp --features frob-scene/frontier-retrofit catalog_retrofits`): reading `frob://catalog/retrofits` with a page limit of 5 pages to completion with no entry repeated or skipped and equals the loader's list; a session token without `scene:read` is refused.

### End-to-end script and logging
`scripts/e2e/retrofit_catalog.sh` (STD-E2E helper; NDJSON under `target/e2e-logs/retrofit_catalog/`): the unit tests above by name (`cargo test -p frob-scene --features frontier-retrofit --test retrofit_catalog`, one `assert` line per test, `load_sixteen` giving the entry count); the catalog as the MCP resource `frob://catalog/retrofits` read through `frob-mcp` (`resources/read`, the handler of section 7; sixteen or more entries, equal to the loader's output; there is no `artifact.read` form for a resource URI); `frob --json scene compile --base <fixture> --edits <file> --key rc-der-1` with the `threshold-ramp` entry instantiated at door D1 (the edit list written by `apply_threshold_ramp`; the derived form of N19b-44), asserting a new `SceneId`, one more overlay, shared bricks and the edit in the lineage; then, through the verb, `frob scene retrofit --apply threshold-ramp:rise_m=0.02,run_m=0.24,width_m=0.9 --at door:D1 --scene <fixture> --key rc-app-1 --json` (variant identity, edit list); the same with `run_m=0.20` and `--key rc-app-2` (exit 3, `FROB-REF-313`); `frob scene show <variant> --json` (applied edits and base identity). `scene.retrofit` is N19b-40's verb, which depends on this bead through N19b-39: until N19b-40 is closed the two `scene retrofit --apply` steps are logged with `e2e_skip "needs N19b-40"` (never counted as a pass), and N19b-40's acceptance requires them to run and pass. Lines log the command, exit code, wall time, evidence block, identities of base and variant, the kit's price with provenance, the refusal code with pointer and repairs, and the first differing table on failure.

### Known answers and negative controls
- KA-454: with forty entries and kits of at most three, the unfiltered kit count is 40 + 780 + 9,880 = 10,700 (asserted on a forty-entry synthetic catalog).
- KA-453 arithmetic behind the ramp entry's constraint: a 1:12 wedge needs a friction coefficient of 1/12.
- Negative controls: an edit applier that writes bricks in place (the base `SceneId` would change: caught by an identity check on the base after apply); a catalog entry with a wrong `changes` list (caught by the declared-aspect check); a constraint evaluator in floating point that accepts 0.2399 ≥ 0.24 by rounding (caught by the exact test).
- Metamorphic: applying two independent edits in either order yields the same variant identity (the edit list is canonically sorted).
- Determinism lanes: twice on one machine; debug and release; across platforms.

## Considerations

- OPEN-HAB-4 (sources for retrofit prices and legality constraints; default prices `assumed`, constraints marked unchecked in every report; owner project lead; blocks any claim about cost in a published report) is carried by N19b-43.
- BET-37's falsifier includes "an accepted kit violates a dimensional norm from its cited source": constraints with a cited source are binding, which is why each carries its own provenance.
- A retrofit variant belongs to its base's split group; scoring a policy on a variant of a training scene is leakage and is refused by the split check.
- The `clocks` aspect has no entry among the first sixteen; it is kept for timing amendments (an automatic door's opening delay) so that the vocabulary matches the adversarial search's.
- The mission layer's facility grammar (Moonshot, M8) reads further properties of a world edit: installation time, access constraints, calibration, part tolerances and future maintenance. They are not fields of version 1 of the catalog. DESIGN: an entry may carry an optional `facility` table for them, ignored by the kit search and by every `scene.retrofit` report except one asked for with `--facility` (N19bx-01, M8, which defines the table), so that adding them later is an additive change and not a new format version.
- Risk: catalog growth without hazard links; the loader's hazard-key check is the guard.
