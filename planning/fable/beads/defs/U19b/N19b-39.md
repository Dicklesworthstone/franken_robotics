## Background

The retrofit search (verb `scene.retrofit`) takes a failing verdict with its evidence and looks for the cheapest set of
building amendments that flips it. Its input evidence is one of three kinds: an impossibility cut from a clearance
complex (which names a bottleneck feature), a minimal counterexample world from the adversarial search (a base scene plus
a short list of typed edits under which the candidate fails), or an alias witness from the sensing analyses (two admitted
worlds that produce the same observation transcript and need different actions). The plan's procedure has five steps;
this bead is the first two, which need no simulation and belong to `frob-scene`:

1. **Localize.** Only amendments whose `applies_to` matches a feature named by the evidence, and whose patch touches the
   bottleneck region, are candidates.
2. **Enumerate kits** of at most three amendments in order of price. With forty entries the unfiltered space is
   40 + 780 + 9,880 = 10,700 kits; after localization it is typically tens.

Why localize: an unfiltered search would re-run a full evaluation ten thousand times; the evidence already says where the
failure is. Why at most three: the answer is meant to be a small, purchasable kit, and the bet behind the mechanism
(BET-37) is stated for kits of at most three items. Ownership: `frob-scene` owns the catalog, the typed scene edits and
the enumeration of kits; applying kits to re-decide a verdict is done by the verb implementation through the owner of
the failing verdict, because `frob-scene` links no crate above layer 2. Tier Frontier, feature `frontier-retrofit`.

## Scope

In: a neutral, typed description of failing evidence that the upper layers fill in; localization; parameter
instantiation from the feature's dimensions; kit enumeration in non-decreasing price with deterministic ties; the
"no kit" result with the bottleneck.

Out: the catalog and edit application (N19b-38); re-deciding verdicts, the redesign arm and the report (N19b-40);
producing cuts, counterexample worlds or alias witnesses (their own beads).

## Technical approach

**1. Evidence, as `frob-scene` sees it (DESIGN; defined here so that layers above can construct it without `frob-scene`
linking them).**

```rust
pub struct FailingEvidence {
    scene: SceneId,
    features: Vec<FeatureRef>,       // named features the evidence blames: door D3, threshold T2, floor patch galley-2
    region: Vec<Box3>,               // the bottleneck region(s) in scene coordinates
    aspects: Vec<Aspect>,            // which aspects the failure runs through, when the evidence declares them
    kind: EvidenceKind,              // Cut | CounterexampleWorld | AliasWitness
}
```

- From a **cut**: the feature is the bottleneck's named feature (or the failed transition); the region is the bottleneck
  cell's footprint swept over its pose box, inflated by the band; aspects: geometry, or actors for a door transition.
- From a **counterexample world**: one feature per edit whose path names a building feature (for example
  `/floor/patch[galley-2]/film`, `/fixtures/door[pass]/closer_torque`); edits to the robot's payload or to clocks name no
  building feature; aspects are the edits' declared aspects.
- From an **alias witness**: the places the two worlds share and the features that differ between them; aspect optics.

**2. Localize, as numbered steps.**
1. For each feature, read its hazard keys from the pack's record of hazards drawn: the slugs of BD-227's hazard rows,
   which are the vocabulary of the catalog's `applies_to` (a threshold is `threshold`; an office door with a closer is
   `door-closer`; a home interior door is `interior-door`).
2. Candidate amendments are those whose `applies_to` intersects the feature's hazard keys.
3. Instantiate each candidate at the feature (step 3 below) and compute its **patch**: the scene region its edits touch.
   Keep the candidate only if its patch intersects the bottleneck region.
4. If the evidence declares aspects, drop candidates whose `changes` do not intersect them (a friction failure is not
   repaired by an optics-only amendment).
5. Result: the candidate list, and for each feature the reason every non-candidate was dropped (kept for the report).
If the list is empty, the search returns **the bottleneck and no kit**. That is a first-class result and the control
case of the bet: a failure that no listed retrofit can fix must return the bottleneck and no kit.

**3. Parameter instantiation.** Each amendment's parameters are bound from the feature's recorded dimensions and the
entry's constraints: for `threshold-ramp` at a threshold of height h and a door of clear width W, `rise_m = h`,
`width_m = W`, `run_m` = the smallest value satisfying the constraints (12·h under the default constraint: 228 mm for a
19 mm threshold, 240 mm for 20 mm); for `door-closer-adjustment`, the new closer torque is the largest value at or below
the body's push capability when the evidence states it, else the lowest setting in the entry's range. A parameter with
no determining dimension takes a short declared list of values, each giving a distinct instantiated candidate. An
instantiation that cannot satisfy the constraints is dropped with its reason.

**4. Enumerate kits.** Over the instantiated candidates: all subsets of size 1, 2 and 3 that are valid kits (every
constraint holds, install classes permitted by the mission, no two members editing one target incompatibly, no two
instantiations of the same amendment at the same feature), ordered by total price ascending; ties broken by size
(smaller first), then by the lexicographic order of the members' identifiers and parameter tuples. The enumeration is a
lazy iterator so the verb can stop at the first kit that flips the verdict. With n candidates the count is at most
n + n·(n − 1)/2 + n·(n − 1)·(n − 2)/6.

**5. Output (DESIGN).** `KitPlan { candidates, dropped_with_reasons, kits: impl Iterator<Item = Kit> }` where
`Kit { members: Vec<InstantiatedAmendment>, price: Money, install_max: InstallClass, changes: AspectSet }`.

**6. Determinism.** Exact arithmetic for prices and constraints; total order on kits: D0. The same evidence and catalog
give the same sequence on every platform.

## Acceptance criteria

- [ ] From a cut that names a 20 mm threshold at door D1, the candidates include `threshold-ramp` instantiated with rise 0.020 m and run 0.240 m, and exclude amendments whose hazards do not match or whose patch does not touch the doorway.
- [ ] From a counterexample world with edits to a floor film, a door closer and a tray fill, the features are the patch and the door; the tray edit names no building feature and yields no candidate.
- [ ] Evidence that names only a payload or a clock returns the bottleneck and no kit.
- [ ] On a forty-entry synthetic catalog with localization disabled, the kit count is exactly 10,700; with n = 6 candidates it is 6 + 15 + 20 = 41.
- [ ] Kits are produced in non-decreasing price with the documented tie order; invalid kits (constraint, install class, conflict) never appear.
- [ ] The sequence is identical across runs and platforms.

## Test plan

### Unit tests
`crates/frob-scene/tests/retrofit_kits.rs`, `cargo test -p frob-scene --features frontier-retrofit --test retrofit_kits`.
- `localize_from_cut`: threshold bottleneck → {threshold-ramp}; a glass door elsewhere in the scene contributes nothing.
- `localize_from_mcw`: the three-edit example → features floor patch and door; candidates {floor-mat-on-wet-zone, door-closer-adjustment, door-holder}.
- `localize_from_alias`: a T-junction alias → {fiducial-marker, aisle-marker}.
- `aspect_filter`: a friction failure drops optics-only amendments.
- `no_kit_result`: payload-only evidence → empty candidates and the bottleneck echoed.
- `instantiate_ramp`: h = 0.019 → run 0.228; h = 0.020 → run 0.240; width from the door's clear width.
- `count_unfiltered_40`: 40 + 780 + 9,880 = 10,700.
- `order_by_price_then_ties`: prices (12, 12, 30) → kits: {a}, {b}, {a, b} at 24, {c} at 30, …, with a before b lexicographically.
- `conflict_and_class_filter`: door-holder and door-closer-adjustment on one door are incompatible when the holder fixes the mode; a `contractor` member is excluded under a `landlord` mission.
- `lazy_enumeration`: taking the first kit instantiates no further subsets.

### End-to-end script and logging
Exercised through `scene.retrofit` in `scripts/e2e/scene_retrofit_gate.sh` (N19b-41). A dry-run mode of the verb, `frob scene retrofit --evidence <id> --plan-only --key <k> --json` (a `run` verb: each of the four calls carries its own key, `rp-cut`, `rp-mcw`, `rp-alias`, `rp-nokit`), prints the candidates, the dropped amendments with reasons and the first twenty kits with prices; `scripts/e2e/retrofit_plan.sh` (STD-E2E helper; NDJSON under `target/e2e-logs/retrofit_plan/`) runs it on the three evidence kinds and on the no-kit control. The dry-run mode belongs to N19b-40's verb, which depends on this bead: until N19b-40 is closed the script runs `cargo test -p frob-scene --features frontier-retrofit --test retrofit_kits -- --nocapture` and logs each test's result as an `assert` line, and logs the four `--plan-only` calls with `e2e_skip "needs N19b-40"` (never counted as a pass); N19b-40's acceptance requires them to run and pass. Lines log the command, exit code, wall time, evidence block, `candidates`, `kits_total`, the first kit and its price with provenance, and the first differing kit on failure.

### Known answers and negative controls
- KA-454: 10,700 unfiltered kits for forty entries and kits of at most three (exact).
- The control of the bet: a failure that no listed retrofit can fix returns the bottleneck and no kit.
- Negative controls: localization that ignores the patch-touches-region rule (a ramp at the wrong door becomes a candidate: caught); an enumeration ordered by size before price (a cheaper pair after a dearer single: caught by `order_by_price_then_ties`); nondeterministic tie order (caught by the repeat-run digest).
- Determinism lanes: twice on one machine; debug and release; across platforms.

## Considerations

- Localization can be wrong in the other direction: the true cheapest fix may lie away from the named bottleneck (a different route altogether). The report therefore states that the search is local to the evidence, and the dropped-with-reasons list is part of the answer.
- Parameter instantiation from recorded dimensions depends on hazard provenance being in the pack; an ingested scene without labelled features yields no candidates and says why.
- Kits of more than three are out of scope by decision; if two bottlenecks on one route need four amendments, the search is run per bottleneck.
- Prices are `assumed` (OPEN-HAB-4); the price order is still well defined, and its provenance is printed.
