## Background

Habitat (crate `frob-scene`, workspace layer 2) owns every part of a world that is not the robot, and it "supplies the
objects other subsystems read and the typed scene edits they apply". A **scene pack** is the compiled, immutable form
of one place (manifest `.fscene`, identity `SceneId`; invariant INV-HAB-01: any change produces a new `SceneId`). A
**typed scene edit** is one atomic, named change to a place in authored units: add a wedge at a threshold, lower a
door closer's torque, swap the interface card of a floor strip, mark a glass door with a diffuse band. Applying edits
to a pack never mutates it: the result is a new pack, a **variant**, that records where it came from.

Three consumers need this at M3, a milestone before the priced retrofit catalog (M4) that is the best-known user of
the same machinery:

- the adversarial search builds candidate worlds as a base scene plus typed edits, and must know which causal paths
  each edit can change;
- train and test hygiene keeps a base scene and every variant derived from it in one split group, which requires the
  variant to carry its lineage;
- the hygiene gate GATE-HAB-14 plants a "retrofit variant" across a split at M3 and expects a refusal.

Decision behind it (ADR-HAB-09): the building is a design variable; scene edits are typed, and later priced, so that
a change to the place can enter a budget beside a change to the robot and be audited. Rejected alternatives:
free-form scene editing by an agent or a search (no declared effect, so no audit and no legality check); editing
bricks or tables in place (breaks immutability and every identity that cites the base); defining edits only inside
the retrofit catalog (the catalog is Frontier, behind a pilot and a kill gate at M4, while the search and the split
rules are Solid at M3 and would have no edit to apply). Tier Solid; no feature flag.

## Scope

In: the edit type `frob.scene.edit/1` and its closed set of kinds; the format row of the edit-list document in
`registries/formats.toml` with its harness wiring; the refusal `scene-edit-invalid`; target references and their resolution against a
base pack; the aspect vocabulary and the per-aspect digests of a pack; `apply` (base pack plus edits gives a variant
pack); partial recompilation and sharing of untouched bricks; the lineage record of a variant; the declared-aspect
check; the canonical order of an edit list; the `derived` source form of `scene.compile` and the `lineage` and
`aspects` blocks of `scene.show`.

Out: the retrofit catalog, its prices, hazard links, constraints, install classes, kits and `FROB-REF-313` (N19b-38,
M4, which instantiates these kinds); localization and kit search (N19b-39) and the verb `scene.retrofit` (N19b-40);
how a variant's group is derived from its lineage (N19c-11) and the split refusal (BD-235); the adversarial search's
world model, causal paths and legality profile (the Nemesis beads N26a-02 and BD-270, which call `apply`); overlay
primitives and their emission (N19a-16, N19a-17); fixture and movable models (N19a-07, N19a-08); the acceptance
fixtures themselves (BD-228).

## Technical approach

**1. Types (DESIGN sketch).**

```rust
pub struct SceneEdit { kind: EditKind, target: TargetRef, params: BTreeMap<ParamName, Quantity>, aspects: AspectSet }
pub enum TargetRef { Region(RegionId), Fixture(FixtureId), Movable(MovableId), Overlay(OverlayId), Zone(ZoneId),
                     Label(SemanticLabel) /* "door:D1", resolved against the base pack */, At(Pose /* new geometry */) }
pub struct Lineage { derived_from: SceneId, edits: Vec<SceneEdit> /* canonical order */, edit_schema: SchemaId }
pub struct AspectDigests { geometry: Blake3, material: Blake3, optics: Blake3, clocks: Blake3, actors: Blake3 }
pub fn apply(base: &ScenePack, edits: &[SceneEdit], sink: &mut dyn BrickSink, svc: &dyn SceneServices,
             job: &dyn JobContext) -> Result<ScenePack, EditError>;
```

Parameter names carry their unit as a suffix (`_m`, `_nm`, `_deg`) and are typed quantities, never bare numbers.

**The edit-list document is a registered format.** `scene.compile` takes it by path (its `edits` parameter is
`artifact-input<frob.scene.edit/1>`), so by N34-27's fail-closed rule `fmt.param-without-row` it needs a row: this
bead enters the row of `registries/formats.toml` (DESIGN values: `id = "FMT-FEDIT"`, extension `.fedit`, schema
`frob.scene.edit/1`, owner `frob-scene`; producers hand-written lists, the retrofit catalog's instantiation and the
adversarial search; consumer `scene.compile`; canonical form canonical JSON, with the edits in canonical order (step 4.2);
`decision` = `docs/adr/ADR-WS-06-format-rows.md`, N34-27's decision record, whose table lists `FMT-FEDIT` as an added
format entered by this bead at M3, as every row beyond the thirteen cites it; a `.json` file whose top-level
`schema` member is `frob.scene.edit/1` is routed to the same reader) and wires the shared round-trip, refusal and fuzz
harness of N34-22 for it (the clauses of GATE-WS-02 for an added format). A document that fails the schema (an
unknown kind or aspect, a parameter without a unit suffix) is `FROB-REF-802` with the pointer at the field; an
unknown major version is `FROB-REF-891`.

**2. Edit kinds (a closed enum; an unknown kind is a load error).** `add-overlay` (wedge, box, rounded box, bevel,
cylinder, bar pattern); `set-overlay-param`; `replace-with-overlay` (a movable or a proxy replaced by a fixed
overlay); `add-fixture` (an articulated or compliant fixture from the fixture models); `set-fixture-param`;
`set-fixture-mode`; `fix-movable`; `set-interface-card` and `set-interface-param` (on a region or a strip);
`set-optical-card` (on a region or a band); `add-optical-region`; `set-lighting` (a zone's level); and
`set-source-param` (one named parameter of the scene's source description, for example the position of a wall or the
width of an opening; DESIGN addition, so that a structural change is also an edit with lineage and not an unrelated
scene). Each kind declares the aspects it may change and the ranges of its parameters. Adding a kind is a schema
version change.

**3. Aspects.** `geometry`, `material`, `optics`, `clocks`, `actors`. They map onto the adversarial search's edit
classes as geometry ↔ Geometry, material ↔ Material, optics ↔ Optics, actors ↔ Fixture, clocks ↔ Clock and link. The
digest of an aspect is the BLAKE3 hash of the manifest's blob hashes that belong to it, in a fixed order: geometry =
brick directory, pool membership and overlay list; material = interface map and the interface cards it references;
optics = optical map, optical cards, optical volumes and zone lighting; clocks = the schedules of fixtures, moving
surfaces and volumes; actors = fixture, movable and behaviour tables. Digests are a pure function of the manifest, so
they need no new stored field.

**4. Applying edits, as numbered steps.**
1. Resolve every target against the base pack; check each parameter against its kind's range. An unresolved target,
   a parameter out of range, or two edits that set the same field of the same target differently is an `EditError`
   (typed: `UnresolvedTarget`, `ParamOutOfRange`, `Conflict`); nothing is written.
2. Sort the edit list into canonical order (kind, target, parameter names and values), so that independent edits
   commute and the same set gives the same variant.
3. Apply the edits to the scene's source description (overlay list, region tables, fixture tables, movable tables,
   lighting, source parameters), never to bricks directly.
4. Recompile only what the edits touch: an overlay edit changes the overlay list and its index; a card change changes
   one region-table row; a change that needs bricks recomputes the bricks within the truncation distance of the
   change. The variant shares every untouched brick with its base through the pool.
5. Re-run the acceptance fixtures that the touched aspects can affect; a variant whose acceptance fails is a pack
   with a failed report, not an error of `apply`.
6. Write the lineage record into the variant's provenance (`derived_from`, the canonical edit list); keep the base's
   licence entries; the group follows from the lineage by the group rule.
7. Freeze. The variant's `SceneId` is a function of the base identity and the canonical edit list on every platform.

**5. Declared-aspect check.** After step 4, compare the aspect digests of base and variant: an aspect the edit list
does not declare must be byte-identical. An edit that declares only `optics` and changes a friction card is a defect
of the edit's definition and fails `apply` with `EditError::UndeclaredAspect`, naming the aspect and the table.

**6. Surface.** No new verb (the chapter's verb table has none for edits). `scene.compile` gains a third source
form, `derived`, with a base `SceneId` and an edit list (`frob --json scene compile --base <id> --edits edits.json
--key <k>`; `--base` and `--edits` together, exclusive with a source path, `FROB-REF-802` otherwise);
`scene.show` gains a `lineage` block (parent, edits) and an `aspects` block (the five digests). An `EditError` on that
path is the worded refusal `scene-edit-invalid` (N19-REF's row: family `3xx`, exit 3, retry `after-change`; `detail` the
variant, `UnresolvedTarget`, `ParamOutOfRange`, `Conflict` or `UndeclaredAspect`; `pointer` the offending edit;
`observed` and `required` the value and the kind's range where one applies; ranked repairs: name a target that resolves
in the base, the nearest labels listed; bring the parameter into its kind's range; drop one of the conflicting edits;
correct the edit's declared aspects). It is raised through the constant `SCENE_EDIT_INVALID` of
`crates/frob-scene/src/refusal/late.rs` and cited by slug, never by a typed number: N19-REF lists `scene-edit-invalid`
among the chapter's refusals implied and not numbered and enters its row (`3xx`, exit 3, §19.2) under the number its
N35x-02 ledger row assigns, and VERBS-scene lists it on `scene.compile`. Callers with their own refusals map an `EditError` themselves (the
catalog to `FROB-REF-313`, the adversarial search to its legality refusal).

**7. Classes and layout.** Edit application is deterministic data processing plus the compiler: pack bytes D0;
INV-HAB-01 and INV-HAB-10 hold for variants. `crates/frob-scene/src/edit/{kind.rs, target.rs, apply.rs, aspects.rs,
lineage.rs}`; nothing above layer 2 is linked (acceptance fixtures that need higher layers come through the service
trait the compiler driver is given).

## Acceptance criteria

- [ ] The thirteen kinds load as a closed set; an unknown kind, an unknown aspect or a parameter without a unit suffix is refused at load (`FROB-REF-802` with the pointer at the field).
- [ ] `registries/formats.toml` has the `FMT-FEDIT` row with its `decision` field, and the shared harness's round-trip (canonical → value → canonical), single-byte-mutation and fuzz clauses pass for it; `cargo xtask check-contracts` reports no `fmt.param-without-row` for `scene.compile`.
- [ ] `add-overlay` of a wedge (rise 0.020 m, run 0.240 m, width 0.90 m) at a labelled doorway gives a variant with a new `SceneId`, one more overlay, byte-identical bricks shared with the base, and a lineage record naming the base and the edit.
- [ ] The base pack is byte-identical after `apply` (its `SceneId` recomputes to the same value).
- [ ] Two independent edits applied in either order, or in one call, give the same variant `SceneId`; two conflicting edits are refused with `scene-edit-invalid`, `detail: Conflict`, exit 3, and nothing is written.
- [ ] The declared-aspect check passes for one fixture edit of every kind and fails for a planted edit that declares `optics` and changes an interface card.
- [ ] A chain base → variant → variant of variant resolves `derived_from` to the root, and each pack's aspects block changes only in the declared aspects.
- [ ] The same base and edits give the same variant `SceneId` on Linux and macOS, and under 1 and 16 workers.
- [ ] `frob --json scene compile --base <id> --edits <file> --key <k>` and `frob --json scene show <variant>` expose the derived form, the lineage block and the aspects block with documented schemas; cancellation leaves no partial variant.
- [ ] `CONTRACT.md` of `frob-scene` lists the kinds, the aspect mapping and the rule that no edit mutates a pack.

## Test plan

### Unit tests
`crates/frob-scene/tests/scene_edit.rs`; real compiler and pool; fixtures labelled `synthetic`.
- `kinds_are_closed`: the enum round-trips through `frob.scene.edit/1`; `"kind": "paint-wall"` fails to load.
- `apply_threshold_wedge`: overlay count +1; brick digests unchanged; new `SceneId`; lineage recorded.
- `apply_closer_torque`: only the fixture-table row of the named door changes; geometry, material and optics digests equal the base's.
- `apply_floor_mat`: `set-interface-card` on a strip changes the material digest only.
- `apply_decal_band`: `set-optical-card` on a band of a glass region changes the optics digest only; physics digests of a short run on base and variant are equal.
- `base_untouched`: the base's manifest and blobs hash to the same values after ten applies.
- `order_independence`: all orders of three independent edits give one identity.
- `conflict_refused`, `unresolved_target_refused`, `param_out_of_range_refused`: each through `scene.compile`'s derived form gives `scene-edit-invalid` (the code `SCENE_EDIT_INVALID` holds) with its variant in `detail`, the edit in `pointer` and the repairs in order; exit 3.
- `fmt_fedit_roundtrip` and `fmt_fedit_refusals` in `crates/frob-scene/tests/conformance.rs` (the names N34-09's contract check looks for), through N34-22's harness: canonical bytes round-trip, reordered keys bind one identity, an unknown major version is `FROB-REF-891`, an unknown kind is `FROB-REF-802`.
- `source_param_recompiles_locally`: moving a wall by 0.16 m recomputes only bricks within the truncation distance of the old and new positions; the variant shares the rest.
- `planted_wrong_aspect_caught` (negative control): the mislabelled edit fails with `UndeclaredAspect`.
- `lineage_chain`: three generations; the root is found; every generation keeps the base's licence entries.

### End-to-end script and logging
`scripts/e2e/scene_edit.sh` (sources the STD-E2E helper; NDJSON to `target/e2e-logs/scene_edit/<utc>.ndjson` with a
transcript). Steps: `frob --json scene compile fixtures/hab/kitchen_k3.src --key se-base` (a compile takes no seed; BD-163); `frob --json scene
compile --base <id> --edits fixtures/hab/edits/threshold_ramp.json --key se-der-1`; `frob --json scene show <variant>`
(lineage and aspects); `frob --json scene show <base>` (identity unchanged); the same derived compile again with a
distinct key, `--key se-der-2`, so that it recompiles instead of returning the stored receipt (same variant identity);
the conflicting-edits file (exit 3, `scene-edit-invalid`, `detail: Conflict`); the mislabelled edit (exit 3,
`scene-edit-invalid`, `detail: UndeclaredAspect`); then the format rows by name (`cargo test -p frob-scene --test
conformance -- fmt_fedit_roundtrip fmt_fedit_refusals`, one `assert` line each).
`scene.compile` is a `run` verb, so every call carries its own key; the `derived` source form (`--base`, `--edits`,
the `edits` parameter an `artifact-input<frob.scene.edit/1>`) is in the row of VERBS-scene, whose help-schema snapshot
pins it. Each
line carries `ts`, `script`, `bead` (`N19b-44`), `step`, `event`, the exact command, exit code, wall time and the
evidence block; `metric` events carry the counts of bricks recomputed and shared; `assert` events carry the two
identities and the five aspect digests of base and variant with the first differing one named on failure. The
`summary` line counts assertions passed and failed.

### Known answers and negative controls
- Known answer: a wedge of rise 20 mm and run 240 mm added at a threshold is an overlay-only edit: zero bricks recomputed, one overlay added, geometry digest changed, the four other digests equal.
- Negative controls: an applier that writes bricks in place (the base's identity check then fails); the mislabelled edit; an applier that keeps insertion order instead of the canonical order (`order_independence` then fails).
- Metamorphic: applying an edit and then its inverse parameter change gives a pack whose aspect digests equal the base's, with a different `SceneId` (the lineage differs); translating the base by a whole number of coarse cells and translating the edit's target with it gives a variant with the same recomputed and shared brick counts.
- Determinism lanes: twice on one machine; worker counts; debug and release; Linux and macOS.

## Considerations

- The kind list is the one the retrofit catalog was drafted with, plus `set-source-param`. If the adversarial search needs a kind that is not here, it is added by a schema version, never by a private edit in another crate.
- A variant is cheap only when the edit is local: an overlay or a table row costs no bricks; `set-source-param` on a long wall recompiles a band of bricks along it. The receipt reports both counts so that a search can budget.
- Acceptance is re-run per touched aspect, not in full; the map from aspects to fixtures is data in this bead and must be widened when a fixture is added.
- Hygiene depends on lineage being impossible to drop: `apply` is the only constructor of a pack with `derived_from`, and a pack whose edit list is non-empty with no parent fails to load.
- If KILL-RETROFIT fires at M4 the catalog's search verb is withdrawn; this bead is unaffected and remains the edit vocabulary of the adversarial search, which is the fallback the plan names.
- Privacy and licences: a variant of a private pack is private; a variant keeps every licence entry of its base.
