## Background

A scene's static geometry is a truncated signed-distance field stored at two levels: a dense coarse lattice (spacing
S, default 16 cm) and, only near surfaces, **band bricks** of 8³ fine samples (spacing s = S/8, default 2 cm), each
1,024 bytes of 16-bit distances plus 128 bytes of two-bit region selectors and an 8-byte palette. Memory, not
compute, limits how many distinct places a device can hold: a 10 × 10 × 3 m home at 2 cm is 75 MB dense, a
60 × 40 × 8 m warehouse 4.8 GB. Per-world state is tiny by comparison (about 20–53 kB for a quadruped), so memory never
limits the number of worlds; it limits the number of places.

**ADR-HAB-05: one scene serves many worlds.** A device holds K scene variants in a shared brick pool and every world
indexes one. One scene per world is not offered. Reason (counterexample CX-197): 8,192 worlds each with its own 2 cm
home is 8,192 × 75 MB = 614 GB, 26 times a 24 GB card and more than twice the working set of the large-memory machine.

This bead builds the pool. The **pool** is a device buffer of band bricks addressed by slot. Bricks are
content-addressed at compile time, so identical bricks are stored once. A **scene variant** is a directory and a coarse
lattice: one 32-bit slot and one 16-bit coarse sample per coarse cell, 6 bytes per cell (0.44 MB for the home, 28 MB
for the warehouse at the default spacings). A world holds a 16-bit variant index, which may change at reset. Three
kinds of sharing follow:

- **Movable clutter costs nothing.** Movable objects are rigid bodies, not field. Variants that differ only in where
  totes, chairs and carts stand share every brick and differ only in their movable tables.
- **Repeated modules inside a scene.** A truncated field in a brick depends only on geometry within T of that brick, so
  modules placed on the coarse lattice with identical neighbourhoods produce identical bricks: an aisle of identical
  rack bays stores one bay.
- **Variants of a base scene.** A retrofit, a moved wall or a different fixture changes only the bricks within T of the change.

HYPOTHESIS: the unique-brick count of a warehouse or retail scene is a small fraction of its band bricks, and a layout
variant adds a few percent. Illustration under that assumption, not a result: a warehouse base of 2.5 GB whose
variants each change 5% of bricks costs 125 MB + 28 MB per variant, so about 88 variants fit beside the base in 16 GB
where three dense copies would. Scans share least. The test is the measured occupancy and deduplication of compiled
scenes (GATE-HAB-13). **Kill gate, named in advance (KILL-POOL):** if measured deduplication on the archetype battery
is below 1.5, variants fall back to private per-variant fields behind the same directory interface, and the dense
scene counts apply as written.

Alternative rejected (CX-227): minimal perfect hashing or succinct structures for the directory. A dense directory
with 4-byte slots is 63 × 63 × 19 = 75,411 slots, 0.3 MB, for the home at 2 cm and 18.8 MB for the warehouse: under
1.5% of the scene it indexes, and a hash would add a second, verifying read to every lookup.

## Scope

In: brick content addressing; the pack-local pool and directory written at compile time; the device pool image with
slot table, reference counts, admit and release of variants; the per-variant directory and coarse lattice behind the
`BrickDirectory` trait; variant indices; the private (non-shared) mode that is the KILL-POOL fallback; occupancy and

## Technical approach

**1. Brick identity.** `BrickHash = BLAKE3("frob.brick/1" ‖ record bytes)`, over the full 1,160-byte record (distance
samples, selectors, palette) after quantization. Two bricks are the same slot only if every byte agrees. Because the
palette is part of the record, repeated modules deduplicate only if their region identifiers agree; DESIGN rule:
generators assign region identifiers per module type and surface, not per placed instance (the instance is recovered
from the coarse cell through the region table). The statistics of item 6 report deduplication both for full records
and for distance blocks alone, so the cost of this rule is measured.

**2. On disk: pack-local pool and directory (DESIGN).** A pack's `field.pool` blob is the ordered list of its unique
bricks in first-use order (lexicographic z, y, x over coarse cells); its `field.directory` blob holds, per coarse
cell, a 32-bit **pack-local** brick index or a sentinel, and `field.coarse` the 16-bit coarse samples. Sentinels
(DESIGN values): `0xFFFF_FFFF` far outside (every sample +T), `0xFFFF_FFFE` deep inside (every sample −T). A pack is
therefore self-contained and its `SceneId` does not depend on which other variants are resident anywhere. Bricks also
live in the content store keyed by `BrickHash`, so a variant compiled later reuses stored bricks without copying.

**3. On a device: the pool image.**

```rust
pub struct PoolImage { device: DeviceId, slots: SlotTable /* BrickHash -> (slot: u32, refcount: u32) */,
                       free: BTreeSet<u32>, bytes_bricks: u64, mode: PoolMode }
pub enum PoolMode { Shared, PrivateBand, PrivateDense }       // the last two are the KILL-POOL fallback
pub struct ResidentVariant { index: u16, scene: SceneId, dims: [u32; 3], origin_cell: [i32; 3],
                             directory: DeviceSlice /* u32 device slots */, coarse: DeviceSlice /* u16 */ }
impl PoolImage {
    pub fn admit(&mut self, pack: &ScenePack) -> Result<ResidentVariant, PoolError>;   // upload new bricks, remap directory
    pub fn release(&mut self, v: ResidentVariant);                                    // decrement; free slots at zero
    pub fn stats(&self) -> PoolStats;
}
impl BrickDirectory for ResidentVariant { fn slot(&self, coarse: [i32; 3]) -> Slot { /* Brick(u32) | FarOutside | DeepInside */ } }
```

Admit, as numbered steps: (1) for each brick of the pack in order, look up its hash; if present increment the
reference count, else take the lowest free slot (or append), upload the record and insert; (2) rewrite the pack-local
directory into device slots in one pass and upload it with the coarse lattice into the directory slab; (3) assign the
lowest free 16-bit variant index; (4) return the handle. Release reverses it. Slot numbers never influence a field
value (only content does), so results are independent of admission order; the lowest-free-slot rule only makes images
reproducible for debugging. Variants that differ only in movables resolve to the same directory hash and share one
device directory. In `PrivateBand` the slot table is bypassed and every variant uploads its own bricks; in
`PrivateDense` every coarse cell of the variant gets a brick (far cells hold ±T), the storage the dense memory table
counts. All three modes implement the same trait, so kernels, the sampler and every consumer are unchanged.

**4. Device layout.** One pool buffer in two sections (distance samples, then selector-and-palette records), slot-indexed,
and one directory slab holding the directories and coarse lattices of the resident variants, located through an offset
table in the kernel parameter buffer (index: variant, value: offset and dims). A world reaches its field through
`WorldRow.scene_variant` (16 bits) → offset table → directory entry → slot. A query in a boundary cell makes up to
eight directory lookups (no brick apron by default, OPEN-HAB-2).

**5. Sharing across a base and its variants.** A variant derived by a typed edit recompiles only the coarse cells
whose band test or samples can change: cells within T + (√3/2)·S of changed geometry. Edits that add an analytic
overlay (a threshold ramp) change no brick at all; edits to movables change neither bricks nor directory.

**6. Statistics (`PoolStats`, also written to the compile receipt).** `coarse_cells`, `band_bricks` (with
multiplicity), `unique_bricks`, `occupancy = band_bricks / coarse_cells`, `dedup = band_bricks / unique_bricks`,
`dedup_distance_only`, `bytes_dense`, `bytes_band`, `bytes_pooled`, `directory_bytes = 6 × coarse_cells`, and for a
set of variants `marginal_bytes` per added variant.

**7. Classes.** Pool contents and directories are D0 (bytes). The pooled field equals the dense field bit for bit, so
the pool adds no error term and no evidence class of its own.

**8. Layout.** `crates/frob-scene/src/pool/{hash.rs, pack_pool.rs, image.rs, directory.rs, stats.rs}`; device upload
goes through the backend trait of the Spark crates; `frob-scene` holds no GPU code.

## Acceptance criteria

- [ ] GATE-HAB-13, bit-equality clause (TARGET): on every scene of the M2 battery the pooled field equals the dense field bit for bit at 10⁶ points per scene, through the CPU reference sampler; the device rows are measured by N19c-17.
- [ ] Occupancy and deduplication ratios are computed and written to every compile receipt and to `PoolStats`.
- [ ] Directory size is 6 bytes per coarse cell: 0.44 MB for a 300 m³ home and 28 MB for a 19,200 m³ warehouse at S = 16 cm (KA-462).
- [ ] Field values are identical under any admission order, any slot permutation and all three `PoolMode`s.
- [ ] Variants that differ only in movables share every brick and one directory; a variant that adds an overlay adds zero bricks.
- [ ] Release frees exactly the slots whose reference count reaches zero; admit after release reuses them; no leak over 10⁴ random admit and release operations.
- [ ] Both branches of KILL-POOL exist and are tested: `Shared`, and the private modes behind the same directory interface.
- [ ] Seed done-condition ("GATE-HAB-13; KILL-POOL decided"): this bead supplies the mechanism, both branches and the statistics; the gate's record on a running system is N19c-17 and the decision is N19c-18. The capability is reported as implemented only when those two are closed.
- [ ] `CONTRACT.md` records the layout, the sentinels, the identity rule and the statistics' definitions.

## Test plan

### Unit tests
`crates/frob-scene/tests/pool.rs`; real compiler output on fixtures labelled `synthetic`.
- `identical_bricks_one_slot`: two bricks with equal bytes get one slot and reference count 2; one differing sample gives two slots.
- `rack_aisle_stores_one_bay`: twelve identical bays placed at multiples of S: unique bricks equal those of one interior bay plus the two end bays; `dedup ≥ 4`.
- `off_lattice_bay_does_not_share`: the same bays shifted by 0.05 m between copies: `dedup < 1.2` (why the grammar places modules on the coarse lattice).
- `pooled_equals_dense_1e6`: 10⁶ seeded points per scene on a box room, a rack aisle and a terrain tile: `to_bits` equality of value, and equal region and saturation.
- `slot_permutation_invariance`: admit A then B, and B then A; all samples identical.
- `clutter_variant_shares_directory`: two variants with different movable tables: one directory blob, zero new bricks.
- `overlay_edit_adds_no_brick`; `moved_wall_changes_local_bricks_only`: a wall moved 0.5 m changes only bricks in cells within T + (√3/2)·S of the old or new wall.
- `directory_bytes`: 73,242 cells × 6 = 439,452 bytes (unrounded 300 m³); the 63 × 63 × 19 lattice gives 75,411 cells and 452,466 bytes.
- `refcount_no_leak`: 10⁴ random operations end with zero live slots after releasing everything.
- `private_modes_same_values`: `PrivateBand` and `PrivateDense` return the same bits as `Shared`.
- `sentinel_matches_dense_far_brick`: a far cell's sentinel and a dense brick of +T give equal samples.

### End-to-end script and logging
The gate's script is its own bead (N19c-17, `scripts/e2e/brick_pool_gate.sh`). This bead adds
`scripts/e2e/brick_pool_smoke.sh` (STD-E2E helper): `frob --json scene compile` a rack-aisle fixture and a variant,
`frob --json scene show <id> --receipts`, and assert from the receipts `dedup`, `occupancy`, `directory_bytes` and the
marginal bytes of the variant; NDJSON lines carry command, exit code, wall time, evidence block, the metrics with
units, and the digests of pool and directory; logs under `target/e2e-logs/brick_pool_smoke/`.

### Known answers and negative controls
- KA-463 (pooled equals dense bit for bit at 10⁶ points per scene; exact). KA-462 (6 bytes per coarse cell: 0.44 MB and 28 MB). KA-461 and CX-197 (614 GB for one scene per world). CX-227 (dense directory, 75,411 slots).
- MR-30 (metamorphic): the pooled field equals the dense field bit for bit; a scene regenerated from its seed has the same `SceneId` on both machines.
- Negative controls: a directory remap with an off-by-one slot must fail `pooled_equals_dense_1e6`; a hash that ignores the palette must fail a region-equality check on a fixture where two bricks differ only in palette; a release that frees at reference count 1 must fail `refcount_no_leak` (a live variant reads another's brick).
- Determinism lanes: twice on one machine; admission orders; debug and release; Linux and macOS.

## Considerations

- **KILL-POOL** (decided at M2, N19c-18): trigger, measured deduplication on the archetype battery below 1.5; fallback, private per-variant fields behind the same directory interface, with the dense scene counts as the planning figure. The interior archetypes land at M3, so the M2 decision is taken on the M2 battery and re-read on the seven archetypes (N19c-19).
- The palette rule of item 1 is a DESIGN completion; if it costs too much sharing, addressing the distance block and the label block separately is the alternative, at the price of a second slot per cell.
- A 32-bit slot addresses 4.29 × 10⁹ bricks (about 5 TB of bricks), far above any device; a 16-bit variant index allows 65,535 variants per bucket.
- Segmenting a pool across buffers (largest-buffer limits, the Metal argument limit) is the world bank's concern (N19c-20); this bead's image is one segment.
- OPEN-HAB-2: an apron (9³ samples per brick, 42% more memory) would remove neighbour lookups and would also reduce sharing, since an apron sample depends on the neighbour; measured in N19c-31.
- Scans share least; the statistics make that visible per pack.
