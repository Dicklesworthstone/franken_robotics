## Background

An ingested place is known only as well as it was captured. When an answer about it cannot be decided, the studio does
not guess. It says what to measure. Verb: `scene.probe-request`. When a clearance verdict is `unresolved` because of
registration or scale uncertainty, when the inner and outer answers of a mission query differ because of an unknown
region, or when a decision reverses inside the interval of an `assumed` card, the studio emits a request that names the
three-dimensional box to rescan or the surface to probe, the quantity needed and the accuracy that would settle the
decision ("the clear width of door D3 to ±5 mm"). **The request is the output; nothing is assumed in its place.**

Why this design: the alternative, picking the nominal value and running, turns an unknown into a silent assumption that
later reads as a result. A request converts uncertainty into the cheapest next action for a person with a tape measure
or a phone. It is the scene-level form of the rule that a measurement is asked for when, and only when, it can change a
decision: measuring the target directly at mission conditions is always an admitted probe, whereas designing an
instrument that separates competing mechanisms is the separate verb `mission.distinguish`. This verb designs nothing;
it names the quantity. Tier Frontier, first milestone M5, kind `read`.

## Scope

In: the request record and its schema; the three triggers and the function each calls; the accuracy rule; standing
requests per scene and their closure; the verb. Out: probe and instrument design (`mission.distinguish`, BD-291);
deciding clearance (N19b-32) and mission answers; performing or importing a measurement (a re-import through N19c-04,
or the Reality lane).

## Technical approach

**1. The record** (`frob.scene.probe-request/1`).

```json
{ "schema": "frob.scene.probe-request/1", "id": "pr:b3:…", "scene": "b3:9c1e…", "private": true,
  "trigger": "clearance-unresolved",
  "target": { "kind": "box", "feature": "door D3", "box_m": [[4.10, 2.00, 0.00], [5.10, 2.30, 2.10]] },
  "quantity": "clear_width", "unit": "m",
  "current": { "nominal": "0.812", "interval": ["0.790", "0.834"], "limited_by": ["u_reg", "scale"] },
  "threshold": "0.800", "decides": { "below": "impossibility cut at door D3", "above": "witness" },
  "accuracy": "0.005", "settles": "ref to the unresolved answer", "status": "open" }
```

`target.kind` is `box` (rescan this volume) or `surface` (probe this region). Quantities (closed list, extensible by
registry): `clear_width`, `clear_height`, `step_height`, `gap_width`, `occupancy` (rescan), `scale` (add a witness),
`friction` with a condition, `compliance`, an optical-card field, a fixture parameter (closer torque, latch force).

**2. The three triggers.**
1. **Clearance unresolved by registration or scale.** After local refinement, a clearance answer stays `unresolved`
   when the band cannot shrink below the floor 2·(ε_field + u_reg) (about 2 mm in a generated scene, tens of
   millimetres in a scan). The fit code then calls `request_for_clearance(answer)`: the target is the bottleneck's
   named feature and its bounding box; the quantity is the dimension the bottleneck cell constrains (clear width for a
   doorway, step height for a threshold); if the limiter is the scale interval the quantity is `scale`.
2. **Mission answers differ because of unknown space.** When a mission query's inner answer (unknown treated as
   blocked) and outer answer (unknown treated as free) differ, `request_for_unknown(region)` names the unknown box
   that separates them, quantity `occupancy`, with the coverage and resolution a rescan must reach.
3. **A decision reverses inside an assumed card's interval.** When a comparison, a verdict or a mission answer takes
   both values as a card field ranges over its `assumed` interval, `request_for_assumed(region, field, interval,
   reversal)` names the surface, the field, the reversal value and what each side decides.
A refusal `FROB-REF-305` (a required route, spawn or contact in unknown space) carries a request of kind 2 as its
first repair.

**3. The accuracy rule (DESIGN).** Let x̂ be the nominal value, t the decision threshold, s = x̂ − t the nominal slack
and ε_irr the error the model cannot remove by measurement of this quantity (the field bound, the complex's finest
cell). The requested accuracy is a = |s|/2 − ε_irr: a measurement to ±a of a truth at the nominal value leaves the
threshold outside the measured interval. Worked case: door D3, nominal clear width 0.812 m, the body needs 0.800 m,
ε_irr = 1 mm: a = 12/2 − 1 = 5 mm, the "±5 mm" of the example. If a ≤ 0 the request is marked `threshold-tie`: no
measurement is promised to settle it, and the record says that a design change which moves the threshold is the
alternative. For `occupancy` the accuracy is a coverage threshold and a spatial resolution equal to the margin in
question. For an assumed interval [lo, hi] with reversal r, the accuracy is (hi − lo)/20, so that at most a tenth of
the prior interval stays ambiguous (DESIGN default), and r is printed.

**4. Standing requests.** Packs are immutable, so requests live in the ledger keyed by `SceneId`, deduplicated by
(target, quantity, threshold). A re-import that records the measurement produces a new pack; requests on the old pack
whose target and quantity the new record covers are closed with a link to the new `SceneId`. Requests inherit the
privacy mark of their scene.

**5. The verb.** `frob scene probe-request --scene <id> [--status open|closed|all]` lists standing requests;
`frob scene probe-request --for <answer-ref>` returns the requests derived from one unresolved answer (computing them
if absent; a read that derives is idempotent and writes only the request record). Result schema
`frob.scene.probe-request.list/1`. Exit 0 with requests, 0 with an empty list for a resolved answer; a `--for`
reference that is not unresolved returns exit 2 with a finding "nothing to settle". Evidence: a request is a statement
about the model's uncertainty, class `Certified` relative to the stated bounds where the limiting answer is a
certificate, otherwise `Estimated`; Reality `no-claim`.

**6. Layout.** `crates/frob-scene/src/ingest/probe.rs`; verb handler `crates/frob-verbs/src/scene/probe_request.rs`.

## Acceptance criteria

- [ ] Each of the three triggers yields a request with target, quantity, unit, current interval, threshold, accuracy and what each side decides.
- [ ] The door example returns "clear width of door D3 to ±0.005 m" from nominal 0.812 m, threshold 0.800 m, ε_irr 0.001 m.
- [ ] A clearance answer limited by the scale interval yields a `scale` request ("add a scale witness"), not a width request.
- [ ] `FROB-REF-305` carries a request for the unknown box as repair 1, and the box equals the one in the refusal.
- [ ] No code path substitutes a nominal value for an unresolved quantity: after a request is emitted the originating answer is still `unresolved`.
- [ ] Re-importing with the measurement closes the request and the same query then resolves.
- [ ] `frob --json scene probe-request` is reachable with its schema and through `frob-mcp`; private requests need the private scope.
- [ ] At least one probe request is emitted for the real place of the ingestion gate (a clause of that gate).

## Test plan

### Unit tests
`crates/frob-scene/tests/probe_request.rs`; fixtures `synthetic`.
- `accuracy_rule_door`: x̂ = 0.812, t = 0.800, ε_irr = 0.001 → a = 0.005.
- `accuracy_threshold_tie`: x̂ = 0.801, t = 0.800, ε_irr = 0.001 → `threshold-tie`, no accuracy promised.
- `clearance_trigger_names_bottleneck`: an unresolved doorway fit on an ingested fixture names the door feature and its box.
- `scale_limited_requests_scale`: with ε_c = 5% the request's quantity is `scale`.
- `unknown_trigger_names_box`: inner and outer answers differ on the half-observed corridor; the request's box is the unseen half.
- `assumed_trigger_interval`: friction interval [0.2, 1.0], reversal 0.45 → accuracy 0.04, both decisions named.
- `dedup_standing_requests`: the same unresolved answer asked twice yields one record.
- `closure_on_reimport`: a new pack recording the width closes the request and links the new `SceneId`.
- `originating_answer_stays_unresolved`.

### End-to-end script and logging
`scripts/e2e/scene_probe_request.sh` (STD-E2E helper) on the synthetic ingested room: `frob --json scene fit` on door
D3 with a body whose margin is inside the registration band (expect `unresolved`), `frob --json scene probe-request
--for <answer>` (expect one request, accuracy 0.005 m), re-import with the measured width, repeat `scene fit` (expect
a witness) and `scene probe-request --scene <old id> --status closed`. NDJSON lines: command, exit code, wall time,
evidence block, the request fields with units, verdicts before and after, digests; logs under
`target/e2e-logs/scene_probe_request/`.

### Known answers and negative controls
- Known answer: the door example (±5 mm).
- Negative controls: a build that resolves the fit by taking the nominal width must fail `originating_answer_stays_unresolved`; a build that asks for an accuracy looser than |s| must fail a check that the measured interval at the nominal truth excludes the threshold; a request without a threshold must be rejected by the schema.
- Determinism: the same answer yields the same request identifier (content hash).

## Considerations

- The accuracy rule and the 1/20 default are DESIGN proposals; the first real place will show whether requests are actionable with ordinary tools (tape, caliper, a pull test).
- A request can be unanswerable by measurement (`threshold-tie`); saying so is the honest output.
- Probe synthesis is conditional on the admitted mechanisms and is Frontier work of the mission subsystem; this verb only asks for direct measurements, which are always admitted.
- Requests name features of a private place; they are private and never appear in shared catalogs.
- If the ingestion kill gate fires and places are authored as surveyed proxies, requests still apply: a survey is a list of answered requests.
