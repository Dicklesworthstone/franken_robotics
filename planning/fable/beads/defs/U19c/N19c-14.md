## Background

An honest split still leaks if an agent may look at the held-out scenes, or may submit fifty candidates to the same
held-out scenes until one passes. The project's answer on the evaluation side is the **blinded qualification lane**: a
confirmation service inside the daemon owns a sealed family of worlds and runs registered requests against it; for
each request it derives fresh **clusters** (a cluster is the unit that shares a generator draw, such as one building
with its materials) from a sealed key, the campaign identifier, the request index and a cluster counter; the agent
receives a receipt (decision, index, level spent, units used, a hash) and nothing else; when the campaign closes the
key is revealed, the clusters become readable, and the family is retired into discovery and never serves as a
confirmation family again.

Habitat's part of that design is one rule of train and test hygiene: **scene families used by the blinded
qualification lane are generated from sealed seeds that discovery cannot enumerate; Habitat exposes such a family only
through a handle that returns scores, never scenes.** This bead builds the handle and the sealing of everything a
scene would otherwise reveal (identity, manifest, geometry, catalog rows, stills, bank listings).

Why a handle and not a permission check on each verb: a permission check must be remembered by every present and
future verb that touches a scene; a type that has no method returning a scene cannot leak one. Rejected alternatives:
a held-out split that agents are asked not to read; encrypting packs at rest only (the running system would still
answer `scene.show`).

## Scope

In (Habitat's side of a sealed family): the sealed family descriptor as `frob-scene` sees it; the handle type and
what it can and cannot do; the sealed pack wrapper and the store namespace; the entry through which the
confirmation service turns one cluster seed into a sealed scene pack, with the generator streams derived from
that seed; the scene-side predicate that says whether a cluster collides with discovery data; what happens to
the packs when the family is revealed or retired.

Out, with the bead that has it: the sealed key, its commitment, the derivation of a cluster seed from the key,
the campaign, the request index and the cluster counter, the freshness ledger with the skip of a colliding
cluster, its counter, its record and its limit, refusal `FROB-REF-844`, family capacity, the close-time reveal
and retirement as protocol steps, audited clusters and the lineage mark (N24b-17, in `frob-arena`, which
depends on this bead and calls the entry and the predicate defined here). This bead holds no key and defines
no key-derivation function: the one commitment and the one derivation are N24b-17's. Also out: the confirmation protocol, error budget and receipts
(BD-259 and the qualification-lane beads); capability scopes and the dispatcher's refusal `FROB-REF-840` (the
safety unit, BD-261); scoring itself (Arena).

## Technical approach

**1. Descriptor and commitment (DESIGN).**

```rust
pub struct SealedFamily { id: SealedFamilyId, family: String /* e.g. home/hallway */, params: ParamRanges,
                          commitment: Blake3 /* the key commitment C of N24b-17, copied, never computed here */,
                          state: SealState /* Sealed | Retired */, revealed: bool }
/// Defined here and implemented by the confirmation service of `frob-arena` (layer 4): `frob-scene` (layer 2)
/// reaches the service only through this trait it defines itself (L-1, L-10), and never names Arena's types.
pub trait SealedScorer: Send + Sync {
    type Request;                                              // the lane's committed request (N24b-16)
    type Receipt;                                              // decision, index, level spent, units, hash
    type Refusal;                                              // the lane's refusal envelope
    fn score(&self, family: SealedFamilyId, req: Self::Request) -> Result<Self::Receipt, Self::Refusal>;
}
pub struct SealedFamilyHandle<S: SealedScorer> { id: SealedFamilyId, scorer: Arc<S> } // the only value discovery code holds
impl<S: SealedScorer> SealedFamilyHandle<S> {
    pub fn describe(&self) -> PublicDescription;               // family name, parameter ranges, commitment, state
    pub fn score(&self, req: S::Request) -> Result<S::Receipt, S::Refusal>; // forwards to the scorer, nothing else
}
```

The key is 256 random bits held only by the confirmation service (N24b-17 draws it at campaign opening and
publishes the commitment C = BLAKE3("frob.qual.keycommit/1" ‖ campaign id ‖ K), so that the reveal at close can
be verified). One sealed family serves one campaign and is retired with it, so the commitment of the campaign
is the commitment `describe()` shows. DESIGN, stated the same way in N24b-17: there is one commitment formula
and one cluster-seed derivation, both N24b-17's; this bead's earlier formulas (`BLAKE3(key ‖ nonce)` and a
64-bit `KDF(key, "frob.sealed/1" ‖ q ‖ i ‖ c)`) are not used, because two derivations of the same clusters
could not both replay from the revealed key.

**2. From a cluster seed to a sealed pack.** The cluster seed of request i and counter j is the 256-bit value
seed(i, j) = BLAKE3-keyed(K; "frob.qual.cluster/1" ‖ campaign id ‖ u32(i) ‖ u32(j)) that N24b-17 derives.
`frob-scene` never sees K. The service calls `sealed::generate(family, seed) -> Sealed<ScenePack>`, which
derives the generator's streams from the cluster seed alone: the structural seed is the first 64 bits of
BLAKE3-keyed(seed; "frob.sealed.stream/1" ‖ "structure"), and the clutter and condition streams use the same
construction with their stream names (DESIGN: streams hang off the cluster seed, so that Habitat needs no key
and a revealed key replays every stream through one chain). Without the key the seeds cannot be enumerated or
predicted, and no cluster serves two requests, because seed(i, j) includes i.

**3. What the handle exposes: nothing of a scene.** Scenes of a sealed family are compiled inside the confirmation
service's namespace as `Sealed<ScenePack>`, a wrapper with no public accessor, no serializer outside the service and
no `SceneId` accessor. Sealed packs live in a store namespace that the public resolver of `frob-scene` has no path
into. Consequences, each a test of this bead: such packs are absent from `scene.list` and the catalog resource; the
handlers of `scene.show`, `scene.fit`, `scene.probe-request`, stills, replays and telemetry, given the identity of a
sealed pack, cannot resolve it and answer exactly as for an identity that does not exist (no field of the pack, and
no answer that tells a sealed identity from a missing one); the world-bank listing (the default action `show` of
`scene.bank`, the call `frob scene bank` with no `--action`, whose output variant is `status`) lists their bytes as
one opaque `sealed` line with no identities; world addresses, per-unit outcomes, telemetry and stills of confirmation runs are
in the receipt's `sealed_until_close` list. The discovery lane can obtain only `describe()` and receipts.
The session-level answer a discovery session sees is `FROB-REF-840` (a session without `qual:admin` asks for sealed
confirmation data before close, exit 5), raised by the dispatcher of BD-261 before any handler runs; that bead
depends on this one (through N24b-17) and its sealed-field audit and firewall steps (N24b-24's
`arena_qualification_lane.sh`) test 840 on the paths this bead closes. This bead's guarantee is the layer below:
a handler that the dispatcher failed to stop still returns nothing of a sealed scene.

**4. Disjointness: the predicate.** `sealed::collides_with_discovery(&Sealed<ScenePack>) -> Option<Collision>`,
callable only inside the service, answers for one generated cluster: (a) whether its group is in the index of
discovery scene groups, which includes every group of the candidate's or the baseline's effective training
manifest (the leak check of N24a-31, run where the groups are visible); (b) whether its exact layout fingerprint
equals that of any discovery pack in the store (N19c-11). It returns the reason and the colliding group or pack.
What is done with a collision is N24b-17's freshness check: the cluster is skipped, the cluster counter
advances, the skip is written to the sealed ledger with its reason (visible at close), and more than its
declared share of skips refuses the draw. That is the one place a draw is replaced, and it is recorded, because
a confirmation cluster that discovery has seen would void the request.

**5. Reveal and retirement: the scene side.** The protocol steps are N24b-17's (the `key-revealed` ledger
record at close; early retirement without reveal). Their effect here: when the `key-revealed` record exists,
`revealed` becomes true, `SealState` becomes `Retired`, and `sealed::unseal` turns the family's packs into
ordinary packs with ordinary groups, readable under the usual rules; anyone can then recompute every seed from
the key and check the commitment and the receipts' hashes (N24b-17's replay). A family retired early without
reveal becomes `Retired` with `revealed = false`: its packs stay wrapped. A retired family cannot serve again:
`sealed::generate` on it returns the typed error `SealedError::Retired` and generates nothing, and the handle's
`score` on it returns the scorer's refusal without a draw (the verb-level refusal and its code are the
confirmation service's, N24b-17 step 3: "opening a campaign on a retired family is refused"). The groups of a
revealed family are discovery groups for every later split and leak check.

**6. Privacy and exports.** Sealed is orthogonal to private; a sealed family built on private scenes is both. No
report, export or log may contain a sealed identity before close; log lines print the family identifier only.

**7. Layout.** `crates/frob-scene/src/split/sealed.rs` (types, derivation, wrapper); the test scorer behind the
feature `sealed-test-scorer` (shared by the unit tests and `crates/frob-scene/examples/sealed_case.rs`); the service
that holds keys is Arena's. Determinism: derivation is exact (D0).

## Acceptance criteria

- [ ] No handler or public function of `frob-scene` returns a `SceneId`, manifest field, geometry, still, world address or per-unit outcome of a sealed pack: the handler-level test enumerates every scene-touching handler from the verb registry (not a hand list), calls each below the dispatcher with a sealed identity, and finds each answer byte-identical to the answer for a random identity that does not exist. (The session-level audit with `FROB-REF-840` is BD-261's and runs over the same handlers.)
- [ ] `SealedFamilyHandle` has exactly the two operations above and reaches the service only through the `SealedScorer` trait defined in `frob-scene`; `frob-scene` has no dependency on `frob-arena` (the workspace's layer check passes); a compile-fail test shows a sealed pack cannot be serialized or inspected outside the service crate.
- [ ] The generator streams of two cluster seeds are separated: changing the seed or the stream name changes the stream; the same cluster seed gives the same `Sealed<ScenePack>` bytes (the statistical test on derived cluster seeds, and "two requests never receive the same cluster", are N24b-17's).
- [ ] The predicate reports a cluster whose group or fingerprint collides with a discovery scene, with the reason; a cluster that collides with nothing returns none.
- [ ] After the `key-revealed` record exists, the packs appear in the catalog with groups, `sealed::generate` on the family returns `SealedError::Retired` and `score` returns the scorer's refusal without a draw; after an early retirement without reveal the packs stay sealed and the same two hold.
- [ ] `frob scene bank` (the default `show`, its `status` output) shows sealed residents as one opaque line with bytes and no identities.

## Test plan

### Unit tests
`crates/frob-scene/tests/sealed.rs`; a test-only in-process confirmation service stands in the same crate boundary as the real one (it is the real code path with a test key, not a mock of it).
- `streams_from_cluster_seed_separated`: the same cluster seed gives the same structural, clutter and condition streams; changing the seed or the stream name changes them; over 10⁶ cluster seeds the structural seeds have no collision. (The derivation of the cluster seed from the key is tested by N24b-17.)
- `handle_has_no_scene_accessors` (compile-fail tests via trybuild): `handle.scene_id()`, `serde::Serialize` for `Sealed<ScenePack>`.
- `scene_handlers_cannot_resolve_sealed`: for each handler of the scene, telemetry and artifact families in the verb registry, a direct call (below the dispatcher) with a sealed identity returns the same bytes as the call with a random absent identity; a handler added to the registry later is picked up by the same loop.
- `no_arena_dependency`: `cargo metadata` for `frob-scene` lists no `frob-arena` in its dependency closure; the test service implements `SealedScorer` from the test crate.
- `list_excludes_sealed`; `bank_status_opaque`.
- `collision_predicate_reports_fingerprint_and_group`: plant a discovery pack with the fingerprint of the pack generated from one cluster seed, and a second whose group is in the discovery index; the predicate returns each reason; an unrelated seed returns none. (The skip, the advancing counter and the ledger row are N24b-17's `fresh_skips_discovery_collision`.)
- `unseal_on_reveal_only`: with the `key-revealed` record the packs become ordinary and list with groups; with early retirement and no reveal they stay wrapped.
- `retired_family_cannot_score`: after reveal, and after early retirement without reveal, `sealed::generate` returns `SealedError::Retired` and the handle's `score` returns the test scorer's refusal with zero clusters drawn.

### End-to-end script and logging
`scripts/e2e/sealed_family.sh` (STD-E2E helper), with the daemon running, uses only what exists when this bead
closes; the qualification verbs (`eval.qualify`, campaign close) come later and depend on this bead, so the script
drives the sealed side through this bead's test-support example (there is no `frob conformance` command):
`cargo run -p frob-scene --features sealed-test-scorer --example sealed_case -- <step> --store <daemon store root>
--admin-out <file>` (DESIGN: the example runs the real `sealed::generate` with the test scorer of the unit tests and
a published test key, writes into the store's sealed namespace as an admin-scoped writer, and writes sealed
identities only to the admin-scoped file; the feature `sealed-test-scorer` is refused in release builds by the
crate's feature lint): (1) step `generate`: three sealed packs from three cluster seeds and one short recorded run
on one of them; the log gets only the family identifier and the pack count; (2) from a discovery session run
`frob --json scene list`, `scene show <id>` for each sealed identity (read by the script from the admin-scoped file,
never printed to the log) and for a random absent identity, `frob --json scene bank` (the default `show`; `frob
scene bank show` with the action word in a positional place is `FROB-REF-802`), and `telemetry stills` on the
example's run; assert that no sealed identity appears in any listing, that each `scene show` answer equals the
absent-identity answer in exit code and bytes after removing the request identifier, and that the bank listing shows one
`sealed` line with bytes and no identities; (3) step `collide`: plant a discovery pack with the fingerprint of one
sealed pack and assert the predicate reports it; (4) step `reveal`: write the test `key-revealed` record and assert
that the three packs now list with groups and that the test key reproduces their streams and `SceneId`s; (5) step
`regenerate` on the retired family: assert `SealedError::Retired`.
The full path through `eval.qualify`, `FROB-REF-840`, close and replay is N24b-24's `arena_qualification_lane.sh`.
NDJSON lines: `ts`, `script`, `bead`, `step`, `event`, the command, exit code, wall time, evidence block, the counts
of handlers tried and of answers equal to the absent answer, the bank line's bytes, the predicate's reason, and on
failure the handler name and the first differing byte offset (never the sealed bytes); before step 4 the log contains
no sealed identity (a scrub check with the case's sealed-value dictionary asserts this); a final `summary` line. Logs
under `target/e2e-logs/sealed_family/`.

### Known answers and negative controls
- Known answer: every registered scene-touching handler answers a sealed identity exactly as an absent one.
- Negative controls: a planted handler that resolves the sealed namespace and returns the manifest of a sealed pack must fail `scene_handlers_cannot_resolve_sealed`; a handler that answers a sealed identity with a distinct "forbidden" message (an existence oracle) must fail the same test; a generator that ignores the stream name must fail `streams_from_cluster_seed_separated`; a predicate that compares fingerprints only must miss the planted group collision and fail its test. (The controls on the derivation itself, a derivation that omits the request index and a service that reuses a collided cluster, are N24b-17's `reuse-clusters` mutant and its skip test.)
- Determinism: the same key and inputs give the same seeds and `SceneId`s on Linux and macOS.

## Considerations

- A new verb that touches scenes must be added to the audit's list by the registry conformance test, or the audit goes stale; the audit therefore iterates the registry, not a hand list.
- Side channels remain (timing of a request reveals scene size); receipts are returned with coarse timing, and the residual is recorded as a known gap.
- The sealed key's custody (who can open a campaign, who can reveal) belongs to the qualification lane (N24b-17) and the safety unit.
- Sealed families consume bank memory invisibly; their bytes are in the admission ledger under an opaque owner.
