## Background

An **invariant** is a property that must hold in every state the system can reach; a **proof obligation** is a
mathematical statement the design relies on, with a stated way of verifying it. The Habitat chapter (scenes, living
worlds, clearance, retrofits; crate `frob-scene`) states ten invariants and seven proof obligations. Each is enforced
by a mechanism that some bead builds, and those beads are spread over three drafting units and four milestones. The
rule of the project is that every law, invariant and proof obligation has a property test, a certificate or a proof,
and that one which no mechanism bead carries gets its own test. This bead is the ledger that keeps the seventeen from
being lost: the statements, how each is verified, which bead carries the verification, and a mechanical audit that a
live test exists for each. It is a registry bead: data entry that is finished early, before the mechanisms, so that
every mechanism bead that carries a row depends on it and binds its tests to the row it carries. The crate-wide
structural tests of INV-HAB-01 and INV-HAB-02, which need the pack type and the compiler, are the test bead
N19cp1-01 (split from this bead in polishing round 1, so that the ledger depends on no mechanism).

## Scope

In: the seventeen rows as registry data; the binding audit; the report of obligations whose verification is not yet
in the class the plan asks for. Out: the mechanism-level tests (each row names its bead); the crate-wide structural
tests of INV-HAB-01 and INV-HAB-02 (N19cp1-01); known answers (N19-KA); counterexamples (N19-CX); refusals (N19-REF).

## Technical approach

1. **File.** `registries/invariants.toml`, section `habitat` (DESIGN: the one register file that the Spark and
   Chronicle registers also use, N21c-27 and N29bx-01, with their field names where the fields coincide; a file of
   Habitat's own beside the suite's registries would be a chapter's private file, which the registry lint of STD-TEST
   refuses). Fields: `id`,
   `statement`, `verification` (kind: `property-test`, `structural`, `certificate`, `written-proof`, `symbolic`,
   `interval-evaluation`, `exhaustive`), `class` (`Certified`, `Tested`), `test` (one or more test symbols),
   `negative_control` (the planted defects the tests must catch, by negative-control registry id `NC-nnnn`),
   `owner_bead` (one or more), `first_milestone`, `status` (`bound`, `pending`), and for a proof obligation
   `artifact` (the path of its derivation or proof file as the carrying bead files it, or its certificate's bundle
   identity).

|---|---|---|---|

4. **The audit** (`habitat_invariants_bound`, a test of `crates/frob-conformance/tests/habitat_invariants.rs`; it
   reads `registries/invariants.toml`, or the file named in the environment variable `FROB_INVARIANTS_FILE` when
   that is set, which is how the end-to-end script points it at a planted copy): for each row, every listed test
   symbol exists in the workspace's test list, or the row is `pending` and its `first_milestone` has not been
   reached. At a milestone exit the audit fails
   on any pending row whose milestone has passed. For proof obligations the audit also checks that the artifact of
   the stated kind exists: a derivation or proof file at the row's `artifact` path (the carrying beads file them at
   `crates/frob-scene/docs/PO-HAB-01.md`, N19a-14; `docs/proofs/po-hab-02.md`, N19b-26; `docs/proofs/po-hab-03.md`,
   N19b-28; `docs/proofs/po-hab-05.md`, N19b-09; the card document `docs/math/cards/po-hab-07.md`, N12x-03), a
   certificate in the bundle registry, or an interval-evaluation test. An obligation verified in a weaker class than stated (for example
   PO-HAB-01 only `Tested` on generated scenes) is reported as a downgrade and is not silently accepted.
5. **Rows that come due first.** The rows of INV-HAB-01 and INV-HAB-02 bind to the crate-wide tests of N19cp1-01
   (`pack_has_no_mutators`, `identity_changes_on_any_byte`, `glb_reachable_only_from_viewer`) and to the
   brick-level GLB-swap check of BD-163 and the consumer-level one of N19a-23; they are `pending` until M2 exit and
   M3 exit respectively. A mechanism bead that carries a row depends on this bead and, when it lands, replaces
   `pending` with its test symbols in the same change.
6. **Evidence.** The ledger itself is data (D0). The audit's result is part of every milestone exit review.

## Acceptance criteria

- [ ] The registry holds exactly INV-HAB-01 to -10 and PO-HAB-01 to -07 with statements identical to the tables above.
- [ ] Every row is bound to at least one existing test, proof file or certificate, or is `pending` before its milestone; the audit fails otherwise.
- [ ] Every row names at least one negative control (the planted defect its carrying test must catch); a row without one fails the audit.
- [ ] The ledger depends on no mechanism: it loads and its audit runs with every row `pending` on a workspace that has no `frob-scene` code yet.
- [ ] Each proof obligation's verification artifact is of the kind and class the table states, or a downgrade is listed in the audit's report.
- [ ] The audit runs in the conformance battery and its report is attached to the M2, M3, M4 and M6 exit reviews (the milestones at which Habitat rows come due).

## Test plan

### Unit tests
`crates/frob-conformance/tests/habitat_invariants.rs`.
- `ledger_rows_complete`: the seventeen identifiers, no others; statements byte-equal to the tables above.
- `habitat_invariants_bound`: the audit of item 4 itself, on the real register (or the file `FROB_INVARIANTS_FILE` names); it fails, naming the row, when a row does not hold.
- `audit_rules_synthetic`: the audit's function on a synthetic register and workspace test list, asserting its verdicts: a row naming an existing test passes; a row naming `no_such_test` fails; a bound proof-obligation row whose `artifact` file does not exist fails; a `pending` row before its milestone passes and after it fails.
- `all_pending_loads`: with every row `pending` and no `frob-scene` crate, the ledger loads and the audit reports seventeen pending rows and no failure before M2 exit.
- `row_without_control_fails`: a row whose `negative_control` list is empty fails the audit.
- `downgrade_is_reported`: a row whose artifact is a sampling test where interval evaluation is required appears in the report as a downgrade (PO-HAB-01 on a generated scene bound only to the 10⁶-sample test).

### End-to-end script and logging
`scripts/e2e/habitat_invariants_audit.sh` (STD-E2E helper): `cargo test -p frob-conformance --test
habitat_invariants` (the audit on the real register; there is no `frob conformance` command, and the audit is a
registry check, not a gate run), then, through `e2e_expect_caught`, `FROB_INVARIANTS_FILE=<scratch copy> cargo test
-p frob-conformance --test habitat_invariants -- habitat_invariants_bound` on a copy of the register with one
Habitat row pointed at a non-existent test (the planted defect: the run must exit non-zero and name the row). Every line carries `ts`, `script`, `bead`, `step`,
`event`, the exact command, exit code and wall time; one `assert` event per row with its identifier, verification
kind, class, the tests and controls found and their results, the registry digest, and `pending` or `downgrade` flags;
on failure the row, the missing symbol and the registry path. The `summary` gives rows bound, pending, downgraded and
failed. Logs under `target/e2e-logs/habitat_invariants_audit/`.

### Known answers and negative controls
- Each invariant's negative control is the one its carrying bead registers (a pool indexed without the world address for INV-HAB-03; a split by `SceneId` for INV-HAB-09; the masked non-conservative film update for INV-HAB-07; a generator reading an unseeded source for INV-HAB-10). The audit checks that each row names at least one control.
- This bead's own controls: a registry row pointing at a non-existent test (must fail the audit); a `pending` row past its milestone (must fail at the milestone exit); a row with no control (must fail); a downgraded obligation (must be reported). The crate-wide controls (a planted GLB import, a pack API with a setter) are N19cp1-01's.

## Considerations

- The plan asks for PO-HAB-02 and PO-HAB-07 as theorem cards. Lemma decides whether each becomes one: PO-HAB-02 through N12-52 (whose recommended disposition files it as not decidable, row ND-13 of `registries/not-decidable.toml`, `max_class` `Tested`, the written proof and the randomized check), PO-HAB-07 through N12x-03 (a card under the next free number at a dated amendment of N12-52's record, T-42 if its recommended dispositions stand). The ledger does not wait for either: both rows carry the written proof on file and their tests, the audit reports a row as "card pending" while no card number exists for it, and a row filed as not decidable names its ND row and its class `Tested` instead, which is not a downgrade.
- PO-HAB-03's "separation in the outer complex excludes every path" relies on cells being closed sets (a free configuration on a shared edge makes every cell containing it an outer cell); the written proof must state that.
- Several rows come due late (INV-HAB-07 at M6, INV-HAB-08 at M4); the ledger exists from M2 so that they cannot be forgotten.
- An invariant without a negative control is not accepted as tested.
