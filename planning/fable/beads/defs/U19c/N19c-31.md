## Background

Habitat stores a scene's signed-distance field in **band bricks**: 8³ fine samples (16 bits each, 1,024 bytes) per
coarse cell near a surface, reached through a per-variant directory. A field query interpolates trilinearly among the
eight samples around the point. When the point lies in the last fine cell of a brick along some axis, some of those
eight samples belong to the neighbouring brick, which costs extra directory lookups: **up to eight directory lookups
for a query in a boundary cell.**

**OPEN-HAB-2.** Whether bricks carry a one-sample apron. An apron stores 9³ samples per brick, so that every query is
answered from one brick; it removes neighbour lookups at brick faces and costs (9/8)³ − 1 = 42% more memory.
**Default (in force until decided):** no apron. **Owner:** Spark lead. **Decided by** the M2 profile; it blocks
nothing.

The question matters because the field is read in the hottest kernels (the distance-field narrow phase and every ray
kernel) and because memory is what limits the number of distinct scenes a device can hold. It is a measurable
trade, so it gets an experiment, not an argument.

DESIGN arithmetic that frames the measurement. Along each axis a query is in the boundary fine cell with probability
1/8. With k axes at the boundary the eight samples span 2ᵏ coarse cells: P(k = 0, 1, 2, 3) = 0.670, 0.287, 0.041,
0.002, so a uniformly placed query makes on average 0.670 + 2·0.287 + 4·0.041 + 8·0.002 = 1.42 directory lookups
instead of 1. An apron also makes a brick's content depend on its neighbours' first sample layer, which lowers
content-address sharing between bricks: a second memory cost, beyond the 42%, that only measurement can size.

## Scope

In: an apron variant of the brick layout behind a compile setting; the measurement on the M2 profile workloads; the
decision record. Out: adopting the apron throughout (if chosen, a follow-up change to the codec, pool and kernels
under the new layout version); the default spacings question (OPEN-HAB-3, N19c-32).

## Technical approach

1. **Apron variant (experiment build).** Compile setting `brick_layout = 9`: each brick stores samples (i, j, k) for
   i, j, k in 0..=8, the last layer duplicating the neighbour's first; 729 × 2 = 1,458 bytes of distance samples;
   selectors stay 8³. The reference sampler and the field kernel gain a branch-free path that reads one brick. The
   variant shares the directory, sentinels and pool code. It is selected per pack, so both layouts can be resident.
2. **Workloads (the M2 profile).** (a) The reference quadruped on rough terrain and on the stair family, 8,192 worlds
   (narrow phase against the field). (b) A height-scan and a depth-camera workload at the M2 sensor settings (ray
   kernels marching the field). (c) The synthetic rack-aisle and box-home scenes of the pool gate's battery.
3. **Measurements, each with and without the apron, on `batch-cpu`, `gpu-cuda` and `gpu-metal` where present.**
   - Time of the field-reading stages and of the full step, from the phase ledger of the performance harness, as
     paired measurements with a 95% lower bound on the ratio.
   - Directory lookups per query (a counter in a diagnostic build), against the 1.42 of the arithmetic.
   - Bytes per scene: band bytes, pooled bytes and the deduplication ratio under each layout; resident homes that
     fit a card's scene budget under each.
   - Bit-equality of field values between the two layouts at 10⁶ points per scene (the apron must change no value).
4. **Decision rule proposed to the owner (DESIGN, TARGET numbers).** Adopt the apron only if both hold: the full
   step's paired lower bound improves by at least 5% on workload (a) or (b) on the training tier; and the measured
   memory cost (the 42% plus the sharing loss) still leaves the world-bank target of 150 homes at 2 cm beside an
   8,192-world batch on one card. Otherwise keep no apron. Either way the default is written into the compile
   settings and the decision is recorded with its numbers.
5. **Record.** `docs/open/OPEN-HAB-2.md` (DESIGN path): the measurements with commit, fingerprints and seeds, the
   ruling by the Spark lead, and the layout version that is the default. If the apron is adopted, a follow-up bead is
   opened to make it the default layout and to re-run the pool gate and the KILL-POOL decision under it.

## Acceptance criteria

- [ ] Field values under the apron layout equal those under the default layout bit for bit at 10⁶ points per scene on every tier measured.
- [ ] The paired timing of field-reading stages and of the full step is recorded for workloads (a), (b) and (c) on each tier present, with the disclosure block (hardware, commit, settings).
- [ ] Measured directory lookups per query are recorded against the predicted 1.42; brick bytes show the 42% increase; deduplication under both layouts is recorded.
- [ ] The decision is recorded with the rule applied and the default layout version set accordingly; if no ruling exists at the M2 exit, the record states that the default (no apron) is in force.
- [ ] If the apron is adopted, the follow-up bead exists and names the gates to re-run.

## Test plan

### Unit tests
`crates/frob-scene/tests/brick_apron.rs`:
- `apron_bytes`: 9³ × 2 = 1,458 bytes; ratio 1,458 / 1,024 = 1.4238.
- `expected_lookups`: the closed-form expectation 1.4238 (the same number, since (9/8)³ expands to the same polynomial) and a Monte Carlo over 10⁶ addressed points within ±0.005 of it.
- `apron_equals_default_values`: 10⁶ points on a sphere scene and a box room; `to_bits` equality.
- `apron_last_layer_matches_neighbour`: for every brick, layer 8 equals the neighbour's layer 0, or the sentinel value where the neighbour is a sentinel.
- `apron_reduces_sharing`: on the rack-aisle scene, deduplication under the apron is at most the default's (measured, asserted as an inequality).

### End-to-end script and logging
`scripts/e2e/brick_apron_experiment.sh` (STD-E2E helper): compiles the workloads' scenes under both layouts
(`frob --json scene compile --brick-layout 8|9`), runs the performance harness's paired comparison
(`frob --json perf compare --arm layout8 --arm layout9 --workload …`), and the bit-equality case. NDJSON lines:
command, exit code, wall time, evidence block (claim Performance, tier, determinism), stage times with units, the
paired ratio and its lower bound against the 5% marker, lookups per query, bytes and deduplication per layout; logs
under `target/e2e-logs/brick_apron_experiment/`.

### Known answers and negative controls
- Known answers: 42% (1.4238) for memory; 1.42 for expected lookups (the two coincide by algebra: the sum over k of C(3, k)·(1/8)ᵏ·(7/8)³⁻ᵏ·2ᵏ equals (7/8 + 2/8)³ = (9/8)³).
- Negative controls: an apron build whose last layer is stale (copied before the neighbour was written) must fail `apron_last_layer_matches_neighbour` and the bit-equality case; a timing comparison run unpaired must be rejected by the harness.
- Determinism: the value-equality results are identical across platforms; timings are reported with their spread.

## Considerations

- The expected saving is bounded: 0.42 extra directory reads per query, in kernels where the samples themselves cost eight reads. The ceiling on the field-read stage is modest, and on the full step smaller still; the experiment may well confirm the default.
- A branchy neighbour path costs more on GPUs than its read count suggests (divergent lanes); that is why the question is measured on devices and not settled by the arithmetic.
- Adopting the apron interacts with the brick pool: lower sharing could move the deduplication statistic toward the kill threshold of 1.5.
- The layout version lives in the compile settings and therefore in `SceneId`; packs of both layouts can coexist during the experiment.
