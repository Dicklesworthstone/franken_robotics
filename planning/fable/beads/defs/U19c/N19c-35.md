## Background

Far-field field reuse lets a fork share its parent's field tiles and recompute only those whose inputs differ. The
tile keys, event digests and the store's interface belong to Habitat (`frob-scene`). What belongs to Chronicle
(`frob-chronicle`, the subsystem that owns telemetry, snapshots, replay and forks) is everything about **when the
parent's tile versions are kept, how much memory they may take, when reuse is switched on, and what a fork reports**.
The mechanism is Moonshot tier; it is reported by `run.fork` and adds no verb.

Terms. A **fork** is a parent episode, a fork tick and a change set; it starts at a lead before the failure taken
from the ladder 0.25, 0.5, 1 and 2 s, and by default runs to one second past the parent's failure time. The **fork
window** is that interval of the parent: at most 2 s of lead plus 1 s after the failure. A **tile version** is the
content of one field tile after one substep, identified by a key built from content digests and event digests. With
a the share of a fork's compute spent on tile updates, d the dirty fraction of those updates and b the bookkeeping
share, a fork costs (1 − a) + a·d + b of a full recomputation. The **phase ledger** attributes a world's step time
to stages.

Design rules taken from the plan: the store holds the parent's tile versions for the fork window only, one base
version per tile plus one version per tile-update that changed content; `sim.estimate` reports the bytes before a
fork batch is admitted; a store over its budget disables reuse for that batch, which then recomputes in full and
stays exact; every fork receipt carries `field_reuse` with the measured a, d and b and the counts of tiles referenced
and recomputed; `--no-field-reuse` forces full recomputation; reuse is enabled only for worlds whose phase ledger
shows a ≥ 0.8 (TARGET).

## Scope

In: populating the store over the parent's fork window; the byte model and its report through `sim.estimate`; the
budget and the disable rule; the enablement rule from the phase ledger; the `field_reuse` block of the fork receipt and
the `field_reuse` telemetry stream that carries the dirty-set trace; the `--no-field-reuse` flag and the reuse mode on `run.fork`; release of the store. Out: keys, digests, the
per-substep algorithm (N19c-34); forks, snapshots and classification (the fork bead of Chronicle); the gate (N19c-36).

## Technical approach

1. **Populating the store.** Tile versions exist only where a parent was replayed with capture on. When a fork batch
   is requested for a failing world, the parent is replayed from the snapshot at or before (failure − lead) to
   (failure + 1 s) with tile capture: the store receives one **base version** per allocated tile at the window's
   start and one version for each tile-update that changed the tile's content (an update that leaves content
   unchanged adds a key that points at the existing content, costing a key and no bytes). The replay is the
   continuation class of fork (bit for bit on the same backend), so the captured versions are the parent's.
2. **Byte model.** `bytes = tiles_allocated × tile_bytes + changed_updates × tile_bytes + keys × key_bytes`, with
   `tile_bytes` = 1,024 for a film tile of 16 × 16 cells at 4 bytes (or the field kind's size), `key_bytes` = 32 plus
   map overhead (DESIGN: 48 in total), and `changed_updates` bounded above by `tiles_allocated × substeps` and
   estimated from the parent's own dirty history (the parent run records how many tiles changed per substep).
   Worked case: a 6 m × 6 m floor fully wet is 361 tiles; a 3 s window at a 2 ms substep is 1,500 substeps; if every
   tile changed every substep the store would hold 361 × 1,501 × 1,024 bytes ≈ 555 MB, and if 5% changed, about 28 MB.
3. **`sim.estimate`.** Before a fork batch is admitted, the estimator reports the store's bytes (from the byte model
   and the parent's dirty history) beside the batch's own memory, and the admission compares them with the store
   budget (DESIGN default: 2 GiB per fork batch, a setting).
4. **Over budget.** A store over its budget disables reuse for that batch; the batch recomputes in full and stays
   exact. The receipt says `field_reuse: { enabled: false, reason: "store-over-budget", bytes_needed, budget }`.
   Nothing is partially reused.
5. **Enablement by the phase ledger.** Reuse is attempted only for worlds whose phase ledger shows a ≥ 0.8, where a
   is the share of step time in field tile updates measured on the parent over the fork window (spills across
   several rooms, steam, fluid islands on the evaluation tier). Below 0.8 reuse stays off with
   `reason: "a-below-threshold"` and the measured a, because the ceiling 1/((1 − a) + b) is then under 4.8 and the
   bookkeeping is not worth carrying. The threshold is a setting recorded in the receipt.
6. **Other disable reasons** (from the preconditions checked by the tile mechanism): determinism class D3 or D4;
   a field kind with no stencil in its contract; a build or kernel version that differs from the parent's.
7. **The receipt.** Every fork receipt carries

```json
"field_reuse": { "enabled": true, "mode": "auto", "a": "0.91", "d": "0.017", "b": "0.008",
                 "tiles_referenced": 529431, "tiles_recomputed": 9172, "recomputed_unchanged": 311,
                 "store_bytes": 31457280, "cost_ratio": "0.113", "reason": null }
```

   with a, d and b measured on this fork (a from the fork's own phase ledger; d = tiles recomputed over tile-updates;
   b = time in hashing and lookups over the estimated full cost) and `cost_ratio` = (1 − a) + a·d + b. Naked numbers
   never leave: the block travels inside the fork's envelope with its evidence. The fork's record also carries the
   dirty-set trace of N19c-34 (item 9) as the telemetry stream `field_reuse` (channels `substep`, `tile_x`,
   `tile_y`, `content_changed`; one row per recomputed tile; empty for a fork with reuse off), read with `frob
   --json telemetry query <fork> --stream field_reuse --world <w>`; the gate's known answers and cone check
   (N19c-36) read it, and its row count equals `tiles_recomputed`.
8. **The flag.** `frob run fork … --no-field-reuse` forces full recomputation (mode `off`); `--field-reuse require`
   refuses the fork if reuse cannot be used; the default is `auto`. The verb's schema documents the three modes.
   Under `require`, every reason that would disable reuse under `auto` refuses the fork before any world runs, with
   the one code `FROB-REF-322` (number proposed by N19c-42, exit 3) and `failed_precondition` naming the reason:
   `determinism-class` and `no-stencil` (raised by the tile mechanism, N19c-34), and, raised here,
   `store-over-budget` (with `bytes_needed` and `budget`), `a-below-threshold` (with the measured a and the
   threshold) and `version-mismatch` (with both versions). Its first repair is always "use mode `auto`". This
   bead's change appends the code to `run.fork`'s `refusals` list in `registries/verbs.toml` under the number the
   ledger assigns to N19c-42's row 3 (read through the constant `FIELD_REUSE_PRECONDITIONS`), as VERBS-run stages
   it (RL-06: the M1 entry lists only codes already registered).
9. **Release.** The store of a fork batch is released when the batch completes or is cancelled; it is not evidence
   (forks with and without reuse are identical), so it is never pinned by a verdict and never retained beyond the
   batch. Cancellation is tested: request, drain, release, with no store bytes left.
10. **Layout.** `crates/frob-chronicle/src/fork/field_reuse/{capture.rs, budget.rs, receipt.rs}`; the estimator
    hook in the estimator's byte model.

## Acceptance criteria

- [ ] A fork batch on the two-room fixture populates the store from a captured replay of the parent's fork window and releases it at completion; allocated store bytes return to zero.
- [ ] `sim.estimate` reports the store's bytes before admission, and the measured store bytes are at most the estimate.
- [ ] A store over its budget disables reuse for the batch; the forks' digests equal those of the same forks with reuse on (both equal full recomputation).
- [ ] Reuse is off with `reason: "a-below-threshold"` for a world whose measured a is 0.2, and on for one at 0.9.
- [ ] Every fork receipt has the `field_reuse` block with measured a, d, b, the two tile counts and the cost ratio; `cost_ratio` equals (1 − a) + a·d + b to the printed precision.
- [ ] The fork's `field_reuse` telemetry stream holds one row per recomputed tile with its substep and coordinates, readable through `telemetry query`, and its row count equals the receipt's `tiles_recomputed`.
- [ ] `--no-field-reuse` forces full recomputation; `--field-reuse require` refuses with `FROB-REF-322` (exit 3, no world run) when any precondition fails, naming it in `failed_precondition`; the same request with mode `auto` runs in full and records the reason.
- [ ] Cancelling a fork batch mid-window leaves no store bytes and no partial receipt.
- [ ] The fork path is reachable through `frob --json run fork` with the documented schema, and through `frob-mcp`.
- [ ] The options this bead adds are the ones its verb rows list with this bead under "Extended by" (KNOWN_DRIFTS 8 and 12): on `run.fork`, `--no-field-reuse` and `--field-reuse auto|require|off` (each `FROB-REF-724` before this bead's build) with the `field_reuse` block, and the code of N19c-42's row 3 appended to the row's `refusals`; on `run.show`, `--receipt` with the `field_reuse` block; on `sim.estimate`, `--fork-batch <run> --forks <n>` with the store bytes in the output. `run.show --phase-ledger`, from which this bead reads the parent's share a, is N21a-27's (a dependency; N19cp1-02 calls it before this bead exists), not this bead's.

### Known answers and negative controls
- Known answers: the byte-model case; the cost identity (0.079 at a = 0.95, d = 0.02, b = 0.01).
- Negative controls: a store that survives its batch (a leak test fails); a receipt that reports the threshold a instead of the measured a (caught by comparing with the phase ledger); a budget overrun that reuses "what fits" (partial reuse is forbidden: the test checks all-or-nothing).
- Determinism lanes: fork digests identical across the three modes on the same tier (the script's `telemetry divergence` step). The `determinism-class` refusal is held by `require_mode_refuses_under_d3` in process, since `run.fork` cannot be placed in class D3 from the command line (`fast-training`, and `cross-backend` without two named placements, are `FROB-REF-247` there).

## Considerations

- The captured replay of the parent costs one pass over the fork window; it is paid once per fork batch and is part of the measured b only if it would not have been run otherwise. The receipt separates capture time from per-fork bookkeeping.
- Rings of full snapshots exist only for a reservoir of worlds; other failing worlds are reconstructed by replay, which is where capture is added.
- The 2 GiB default budget and the key overhead are DESIGN values to be set from the pilot's measurements.
- If KILL-FARFIELD fires, the `field_reuse` block remains in the receipt schema as `enabled: false, reason: "withdrawn"`, so that readers of receipts need no version switch.
