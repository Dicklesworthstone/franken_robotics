## Background

A **refusal** is the answer a verb gives when it will not compute what was asked: a stable code, a message, the
offending value beside what was required, and ranked repairs (the typed changes that would make the request
admissible, best first). The machine-readable registry is `registries/refusals.toml`, loaded by `frob-core`; a code
with no row does not compile, an unknown code in a serialized refusal is a load-time error, and codes are never
reused. Exit codes follow the family of the code, by the registry's exit rule (data in the registry, owned by
N35-33): 3 for a refused input or question (`1xx` to `5xx`), 5 for a capability that is not implemented or not
admitted, 9 for an integrity fault (`9xx`, and the codes of `8xx` listed as integrity; the caller cannot know which
bytes are right; never retried blindly). A row whose exit differs from its family's fails the registry's load.

Habitat (crate `frob-scene`, the subsystem that owns every part of a world that is not the robot) defines seventeen
codes, `FROB-REF-301` to `-317`, and the registry bead N19-REF enters them. The chapter and the beads that implement
it also say, in words, that ten further situations are refused, and give none of them a code:

Rows 5 to 7 were added in polishing round 1 and rows 8 to 10 in round 2: other beads raised them without a code,
and a refusal without a registry row cannot be loaded, tested or repaired by code. They are decided in the same
record so that the scene family has one place where every uncoded refusal was numbered.

Terms. A **scene pack** is the compiled, immutable form of one place, with manifest `.fscene` and identity `SceneId`
(the hash of its canonical manifest, which carries the hash of every blob). The **acceptance report** is the record of
the fixtures a pack passed after compilation. A **pool segment** is one device buffer of distance bricks; a launch
binds one segment, and a world reads the variant its 16-bit index names. **Far-field reuse** lets a fork of a run
recompute only the field tiles whose inputs differ from its parent's. Determinism classes D3 and D4 do not promise
that a world's result is independent of the batch it ran in, so a reused tile could differ from a recomputed one.
The **nominal footprint** is the base shape and height a scene family declares as "a robot this family is meant
for". The **allocation ledger** is `registries/refusal_allocations.toml` (N35-33, second round N35x-02): one row per
uncoded refusal with its slug, family, optional proposed number and assigned number; a pure function assigns the
numbers, so that no chapter types one.

Why this is a bead of its own. Without rows these refusals cannot be loaded, tested or documented, and the drafting
units had each chosen a different stand-in (a precondition refusal with exit 3, a "not admitted" answer with exit 5, a
bare integrity fault). Rejected alternatives: inventing a number in each mechanism bead (drafters collide, and a
collision burns a number for ever); folding each case into an existing code (one meaning per code is the registry's
rule, and agents repair by code: "run `scene.accept`" is not a repair for a decode limit). The work is tier Solid,
data entry plus one owner confirmation, and is due at M2 because the manifest reader, the compiler driver and
compile stage 9 are the first to raise three of the ten.

## Scope

In: the decision record; the ledger rows for the requests this bead files; ten new rows of
`registries/refusals.toml` with message, trigger, refusal-block fields, `retry`, ranked repairs and exit code, under
the numbers the ledger assigns; the entries in the refusal lists of the verbs that can raise them; the binding test
of each row; removal of the "unnumbered" list from the Habitat registry's gap report.

Out: the seventeen coded rows and their binding check (N19-REF); the allocation rule, the exit rule and the ledger's
checks (N35-33, N35x-02); the mechanisms that raise the ten refusals (row 1: BD-228; row 2: N19c-22; row 3: N19c-34

N19c-13; row 8: N19a-19; row 9: N19b-38, N19b-40 and N19b-43; row 10: N38a-33); the run-admission path of the run

2. **Fail-closed default.** The rows are entered when this bead is worked, with the assigned numbers, so that every
   bead that raises one compiles against a registered code and the situation is refused from its first day (a pack
   that failed acceptance is never runnable, whatever the number). No mechanism bead writes a number of its own:
   each names its refusal through the constant of step 3. If the owner later renumbers a row, the old number is
   retired (never reused), the constant changes, and the old number stays loadable as an alias for one release so
   that stored refusals still parse. The ADR records the assigned numbers and whether the owner confirmed them; an
   unconfirmed row is listed as an open question at the M2 exit.
3. **Constants.** `crates/frob-scene/src/refusal/late.rs` holds one constant per row, the only place a Habitat

## Acceptance criteria

- [ ] The ADR exists with the ten slugs, their assigned numbers, the date, the reason for each family, and whether the owner confirmed them.
- [ ] `registries/refusal_allocations.toml` holds a row for each of the ten slugs (four filed by N35x-02, six by this bead); every one is `assigned` or `merged`; N35x-02's hold on 324, 325 and 327 is lifted once this bead's rows are filed; no row carries 323 or 326, which stay in N35-33's `retired` list as withdrawn proposals.
- [ ] `registries/refusals.toml` holds the ten rows with the content of the table under their assigned numbers; the loader accepts them; rows 1 to 3, 5, 6 and 8 to 10 are `3xx` rows with exit 3 and rows 4 and 7 are `9xx` rows with class `integrity` and exit 9; no `3xx` row has an exit other than 3.
- [ ] Each row is bound to a provoking test or marked `pending: <bead>`; at each milestone exit no row whose raising bead's milestone has passed is pending.
- [ ] For rows 1 to 3, 5, 6 and 8 to 10 the test applies the first repair and the same request is then admitted; for row 4 the test shows that the regenerated pack has the stated identity, and for row 7 that the rebuilt split recounts equal.
- [ ] The Habitat registry's gap report lists no unnumbered refusal once this bead is closed.
- [ ] The verb registry's refusal lists name the new codes for the verbs of step 6, and the refusal table that `frob --json schema` serves holds twenty-seven Habitat rows: the seventeen of N19-REF, eight of class `scene` and two of class `integrity` from this bead.
- [ ] No Habitat source file names one of the ten codes by number: each uses its constant of step 3 (a lint over `crates/frob-scene`).
- [ ] If the owner renumbers: the old numbers are marked retired, load as aliases for one release, and a test shows that no row reuses them.

## Test plan

### Unit tests
`crates/frob-conformance/tests/refusals_habitat_late.rs`, real registry and ledger, fixtures labelled `synthetic`:
- `ten_rows_load`: the registry contains the ten rows with the fields of step 4 under the ledger's assigned numbers; a duplicate of any of them fails the load.
- `exits_follow_families`: the exit map gives 3 for rows 1 to 3, 5, 6 and 8 to 10, and 9 for rows 4 and 7; rows 4 and 7 have codes in `9xx`.
- `integrity_row_in_3xx_does_not_load` (negative control for the family rule): a scratch registry with row 4 entered as `FROB-REF-323`, class `integrity`, exit 9 fails the load with the exit-rule error naming the row.
- `allocations_agree`: the ten slugs appear in `registries/refusal_allocations.toml` with the numbers `refusals.toml` uses; a scratch ledger in which another chapter's request is assigned 324 fails the test; no row of either file carries 323 or 326.
- `constants_match_registry`: each constant of `refusal::late` equals its row's code; a scratch source that names one of the codes as a literal number fails the lint.
- `unaccepted_pack_refused_318` (pending until M3): a fixture pack whose report lacks the measurement part for the tier in use; `sim.run` on it → row 1 with `missing_sections` naming that part; after `scene.accept` completes the report the same run is admitted. A second case with one failed fixture and no waiver lists it in `failed_fixtures`.
- `evicted_variant_refused_319` (pending until M3): a two-variant schedule; one variant evicted after admission; the next reset to it → row 2 naming variant and segment; after `scene.bank admit` the same schedule runs.
- `require_mode_refused_322` (pending until M6): a fork requested with reuse mode `require` under class D3 → row 3 with `failed_precondition: determinism-class`; the same with a store budget below the estimate → `store-over-budget`; with mode `auto` each fork runs and records the reason.

### End-to-end script and logging
`scripts/e2e/habitat_late_refusals.sh` sources the STD-E2E helper and drives the real `frob` binary on synthetic
fixtures; every run-kind call carries its own idempotency key (`--key hlr-<step>`). Steps: `frob --json scene
compile fixtures/hab/box_room --key hlr-1`, then `frob --json scene show <id>` on a copy with one flipped byte (row 4,
exit 9); `frob --json scene compile fixtures/scenes/spawn-blocked.src --key hlr-2` (row 8, exit 3), then the fixture
with the spawn region moved (`--key hlr-3`, the passing rerun); from M3, `frob --json sim run` on the box-room pack
before its acceptance report has the measurement part of the tier in use (row 1), then `frob --json scene accept <id>
--key hlr-4` and the passing rerun; from M3 the eviction case through `frob --json scene bank` (evict, then a
two-variant run: row 2; admit, then the passing rerun); from M3 the split cases through `frob --json scene split
add` (an unmatched warehouse scene: row 5; `--to train`, then the passing rerun), `frob --json scene split
move-group` on a cited held-out group (row 6), and `frob --json scene split check` on a copy of a split manifest
with one edited count (row 7, exit 9); from M4 `frob --json scene retrofit --strict-data` on the threshold fixture
with an `assumed` kit price (row 9), then without the flag, and `frob --json report mission <answer> --publish` on
the same comparison (row 9 without `--strict-data`; repair 2 there is to report without `--publish`); from M6 a fork
requested through `frob --json run fork … --field-reuse require` with the store budget set below the estimate
(row 3, `failed_precondition = "store-over-budget"`, then mode `auto` as the passing rerun; the D3 case cannot be
reached from the command line, where `run.fork` answers a `fast-training` or an unpaired `cross-backend` profile
with `FROB-REF-247`, and `require_mode_refused_322` holds it in process), and the registration of an
actor-subject column (row 10).
A step whose verb or mechanism is not in the build is logged with `e2e_skip "needs <bead>"` (an `assert` with
`status: "skip"`, never counted as a pass), and the raising bead's acceptance requires its step to run and pass.
Each step logs `ts`, `script`, `bead` (`N19c-42`), `step`, `event: refusal`, the exact command, exit code, wall time,
the refusal block (`code`, `pointer`, `observed`, `required`, `unit`, the row's own fields, `repairs`, `retry`), the
slug beside the code, then applies repair 1 and logs the passing rerun with its evidence block. Output goes to
`target/e2e-logs/habitat_late_refusals/<utc>.ndjson` with a transcript; the `summary` line counts rows exercised,
rows pending and assertions passed or failed. No private path or private-scene content is logged.

### Known answers and negative controls
- Known answer: the exit rule of the registry (3 for `3xx`, 9 for `9xx`) reproduces for the ten rows.
- Negative controls: a build whose run verb skips the acceptance check runs the unaccepted pack and must fail `unaccepted_pack_refused_318`; a reader that compares `SceneId` only when asked must fail `byte_flip_is_identity_mismatch`; a tile store that silently recomputes in mode `require` must fail `require_mode_refused_322`; a split handler that assigns an unmatched group to `train` must fail `unmatched_group_refused_324`; a split reader that trusts the stored counts without recounting must fail `split_recount_mismatch_exits_9`; a stage 9 that freezes a pack whose spawn region has no valid cell must fail `blocked_spawn_refused`; a strict-data path that only warns must fail `strict_data_cost_verdict_refused`; a registry with two rows under one number must fail to load; a `3xx` row with exit 9 must fail to load.
- Determinism: the refusal block of each case is byte-identical twice on one machine and on Linux and macOS (it is data; class D0).

## Considerations

- Rows 4 and 7 were first proposed as scene-family numbers with class `integrity`, on the reasoning that `frob-core` starts with no `9xx` row. The registry owner's rule settles it the other way (family by what is refused; exit by family), and following it is better for the caller: an agent can tell from the code alone that the answer is an alarm about stored bytes and not a request it can repair. Beads that printed `FROB-REF-323` or `FROB-REF-326` are asked to cite the slugs.
- Row 3 is not due before M6 (far-field reuse is a Moonshot item behind its pilot and KILL-FARFIELD), and row 10 not before M6 (actors are a Frontier item behind KILL-DRESSING). They are decided now so that one record covers every uncoded refusal of the chapter; if a kill gate fires the row stays in the registry as retired, never reused.
- Rows 5 to 7 are not in the chapter's refusal table: they guard the split verb's fail-closed rules (an unmatched group is never assigned silently; frozen evidence keeps its held-out part; a split's counts equal a recount, INV-HAB-05). If the owner prefers, row 6 can become a finding with exit 2 instead of a refusal; the default until then is the refusal.
- Row 8 refuses a compile; it does not hide an infeasible scene. A scene whose goal cannot be reached is kept, tagged and counted (ADR-HAB-06); a scene with nowhere to start cannot run one episode, and a generator that emits one has violated its own grammar constraints.
- Row 9 follows the fail-closed default of OPEN-HAB-4 (owner: project lead): until prices have sources, no cost claim is made under strict data or in a published report.
- Row 1 is the one that matters most: a pack that failed acceptance must not be runnable, and no flag skips the check, for a fixture pack no more than for any other. The check is by pack content, so a pack copied to another machine carries its refusal with it.
- Row 2 must not fire for a variant that is resident in another segment of the same job; that case is a hold, not a refusal, and the receipt counts held world-chunks.
- Security and privacy: row 4 never echoes a path under the private root; it reports `path_class: private` and the hashes.
- What would reopen this decision: a registry-wide renumbering of the scene family, or an eleventh uncoded refusal found in the chapter.
