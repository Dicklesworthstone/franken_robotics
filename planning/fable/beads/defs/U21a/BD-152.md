## Background

The kernel library of Spark (the subsystem between a derived kernel and a device result) has one family that every
other family leans on: the **utility kernels**. One exclusive scan (`K-scan`), one stable integer-key radix sort
(`K-sort`), one fixed-tree reduction (`K-reduce`), one segmented reduction (`K-seg-reduce`) and one
count-scan-write compaction (`K-compact`) serve every stage; no stage carries its own sort, scan or reduction. The
reason is determinism: order-dependent floating-point sums, floating-point atomics and unstable sorts are the
three ways a GPU batch stops being reproducible, and concentrating them in five kernels means the proof of
order-independence is done once.

The mechanisms are built in three beads: reductions and the shared conventions (N21a-07), scan and compaction
(N21a-08), the sort (N21a-09). This bead is the seed bead that downstream work depends on (the broad phase, the
batched step on `batch-cpu`, address-keyed random draws): it registers the five kernels in the library with their
manifests, and it owns the test battery that proves the family's two promises together, on real compositions and
not only kernel by kernel:

1. **Bitwise equal across worker counts** on `batch-cpu` (the tree shape and every placement are functions of
   logical index only; results are placed by index, never by arrival).
2. **Padding is neutral**: a world's result is the same bits at any capacity. The canonical trap is the sum:
   −0.0 is the neutral element of addition; +0.0 is not, because (−0.0) + (+0.0) = +0.0. Padding a reduction with
   +0.0 where −0.0 is required must be caught.

Wording note: the seed's one-line done-condition reads "padding a reduction with −0.0 as the neutral element is
caught". Read literally it contradicts the padding rule (−0.0 *is* the neutral for sums). It is taken here in the
only consistent sense: the −0.0 neutral-element case is the test, and a build that pads with anything else is
caught. Tier: Solid.

## Technical approach

**Registration.** Each kernel gets a manifest registered in `registries/kernels.toml` (its row in the library
index is added by N21a-04, which depends on this bead):

| Kernel | Class | Math mode | Determinism | Operators or parameters |
|---|---|---|---|---|
| `K-scan` | `exact` | `ExactInteger` | D0 | exclusive scan of `u32`, wrapping |
| `K-sort` | `exact` | `ExactInteger` | D0 | `key_bits` ∈ {8, 16, 24, 32}; stable; payload `u32` |
| `K-reduce` | `float` or `exact` per operator | `Ieee754Safe` or `ExactInteger` | D2 by design (D1 where the device's IEEE probe allows) for `f32`; D0 for integers | sum, product, min, max; `u32` addw, max, min, or; two-limb add |
| `K-seg-reduce` | as `K-reduce` | as `K-reduce` | as `K-reduce` | the same operators, per segment |
| `K-compact` | `exact` | `ExactInteger` | D0 | record width in words; capacity; overflow flag |

Every manifest states its read and write footprints per buffer in terms of capacities, aliasing (none), layout,
resource bounds (loop bounds, stack or thread-group words) and the numerical contract: the neutral element used
for padding (−0.0, 1.0, +∞, −∞, 0, 0xFFFFFFFF, (0, 0), or the padding record).

**Composed fixtures (DESIGN; all labelled `synthetic`).**
- *Scatter replacement*: n contributions (key = body index, value = `f32`), `K-sort` by key with index payload,
  then `K-seg-reduce` (sum) per key. The oracle is an exact-rational sum per key rounded once per tree node on the
  host, which reproduces the tree's rounding exactly.
- *Filter and reduce*: flags, `K-compact`, then `K-reduce` (max) over the compacted prefix.
- *Scan offsets*: per-segment counts, `K-scan`, then a gather through the offsets.
- *Signed-zero world*: a world whose only active value is −0.0, summed.

**Battery axes.** For every fixture and every kernel: worker counts {1, 2, 3, 5, 8} on `batch-cpu` (the default
compute envelope allows 8 cores); capacities {n, n + 1, 2n, 64, 256}; slot permutation (the same worlds placed in a
different order inside the batch: per-world outputs must be identical when re-indexed by world address); batch
sizes {1, 7, 256, 4,096}; debug and release builds; and each device against `batch-cpu` (byte equality for class
`exact`; inside the claimed class for `float`).

**Order-independence argument recorded in `CONTRACT.md`.** (a) Integer kernels: wrapping addition, max, min and or
are associative and commutative, so any schedule gives the same bytes. (b) Float reductions: the tree is fixed by
logical index; each node is one IEEE operation; x ∘ neutral = x bit for bit; so the result is a function of the
active values and their order alone. (c) Placement: every write position is computed (scan offsets, index), never
taken from arrival order.

## Acceptance criteria

- [ ] All five kernels are registered with manifests, CPU reference symbols and dialect sources; `frob spark check --kernel <name> --backend batch-cpu --key <k>` runs each.
- [ ] Bitwise equal across worker counts {1, 2, 3, 5, 8} for every kernel and every composed fixture (seed done-condition).
- [ ] The padding negative control is caught (seed done-condition): with the neutral table mutated so that sums pad with +0.0, the signed-zero world returns +0.0 at capacity 2 and −0.0 at capacity 1, and the capacity-invariance test fails naming the world and both bit patterns (0x00000000 against 0x80000000).
- [ ] Capacity invariance, slot-permutation invariance and batch-size invariance hold for every kernel and fixture.
- [ ] Integer kernels are byte-identical on `batch-cpu`, CUDA and Metal; float reductions agree inside each device's claimed class, and the result is entered in the divergence ledger.
- [ ] Every kernel source of the library at this bead's landing other than these five is free of a sort, scan or compaction loop pattern, checked by a review list in `CONTRACT.md`; the automated static check "no stage carries its own sort" is N21a-04's (it depends on this bead and runs over these five registrations).
- [ ] Each mutant in the negative-control list is caught by the named test.
- [ ] `scripts/e2e/spark_utility_kernels.sh` exits 0 and writes its structured log.

## Test plan

### Unit tests (`cargo test -p frob-kernels utility_battery`)
- `utility_manifests_complete`: five manifests; every required field present; class and math mode as in the table.
- `scatter_replacement_matches_exact_tree`: 10⁴ seeded cases; output equals the host oracle bit for bit.
- `scatter_replacement_input_order_free`: shuffling the contributions' input order (keeping each key's values' relative index payload) leaves every per-key sum bit-identical, because the sort restores (key, index) order.
- `filter_reduce_capacity_invariance`.
- `signed_zero_world_all_capacities`: −0.0 at capacities 1, 2, 8, 64.
- `positive_zero_padding_mutant_is_caught` (negative control).
- `tile_shaped_tree_mutant_is_caught` (negative control: a reduction whose pairing depends on the worker count fails the worker-count test on the fixture [2²⁴, 1, 1, 1], where the fixed tree gives 16,777,218 and a different grouping gives 16,777,216 or 16,777,220).
- `atomic_append_mutant_is_caught`, `unstable_sort_mutant_is_caught` (negative controls, re-exported from the sub-beads so the family battery fails if either regresses).
- `slot_permutation_invariance`: 256 worlds permuted by a seeded permutation; per-address outputs identical.
- `batch_size_invariance`: world 1337 alone and inside batches of 7, 256 and 4,096.

### End-to-end script and logging
`scripts/e2e/spark_utility_kernels.sh` (this bead owns it; sources the shared helper of STD-E2E, seed-explicit,
idempotent). Steps: `register` (`frob spark check --kernel <name> --backend batch-cpu --key <k> --json` for each
of the five names: each is found and attains its class; N21a-04 adds to this step the assertion that
`frob spark check --action list --json` shows the five), `scan`, `compact`, `sort`, `reduce_capacity`, `reduce_workers`,
`seg_reduce`, `two_limb`, `composed`, `padding_control` (runs the mutated build feature `neg-control-padding` and
expects failure), `devices` (skipped with a logged reason when no device is present). Each step runs
`frob spark check --kernel <name> --backend <b> --workers <w> --seed <s> --key <k> --json`, looping over the worker
counts {1, 2, 3, 5, 8} on `batch-cpu`; the capacity, slot-permutation and batch-size axes run in the unit battery
(`cargo test -p frob-kernels utility_battery`, invoked by the script with its summary logged), because the verb's
`--sweeps` option arrives later: steps `sweeps_capacity` and `sweeps_slots` (`frob spark check --kernel <name>
--backend <b> --sweeps capacity,slot --key <k> --json`; the axis is spelt `slot`, and a misspelt axis is
`FROB-REF-802`) are present from the start and log `skip` until N21b-33 lands; N21b-33 removes the skip guard and
activates the two steps in its own acceptance, so this bead's acceptance does not wait on it.
Each NDJSON line (in `target/e2e-logs/spark_utility_kernels/<utc>.ndjson`, with a transcript beside it) carries
`ts`, `script`, `bead`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command
line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed),
the axis values, output digests, and on failure the first differing world, lane and both bit patterns with the
artifact paths to reproduce. The final `summary` line counts assertions passed and failed. No scene data is logged.

### Known answers and negative controls
- (−0.0) + (+0.0) = +0.0 (the padding counterexample); [2²⁴, 1, 1, 1] → 16,777,218 by the fixed tree; scan of [1, 0, 2, 0, 1] → [0, 1, 1, 3, 3]; sort of [3, 1, 3, 0, 1] → payload [3, 1, 4, 0, 2]; two-limb (0xFFFFFFFF, 0) + (1, 0) = (0, 1).
- Counterexample behind the family: "99.9% of windows replay bitwise" gives 0.999¹⁰⁰⁰ = 0.37 (CX-230).
- Negative controls registered with the conformance harness: `padding-plus-zero`, `tile-shaped-tree`, `atomic-append`, `unstable-sort`, `silent-clamp`.
- Metamorphic: permuting worlds permutes outputs; appending neutral lanes changes nothing; scaling float inputs by a power of two scales sums exactly.
- Determinism lanes: twice on one machine; across worker counts; debug and release; across platforms; across backends, each against its class.

## Considerations

- The battery is the family's regression guard for every later optimization: a faster variant lands only with identical digests on this battery.
- Under the default compute envelope a test may use at most 8 cores; the 24- and 36-thread rows of the performance program re-run the worker-count test under an approved envelope and add those counts.
- Float reductions on devices are class D2 by design; equality with `batch-cpu` (D1) is a HYPOTHESIS measured by the IEEE probe per device family and is not assumed here.
- If the derivation toolchain is abandoned for arithmetic (kill gate KILL-KIR), nothing here changes: these are skeleton kernels, hand-written by design.
