## Background

Spark owns everything between a derived kernel and a device result. Its seam is the `KernelBackend` trait in the
core crate `frob-kernels`: compile a kernel library, allocate buffers, build a step plan, launch it, read back,
return a receipt. `batch-cpu` implements it with Rust functions and is the permanent CPU reference. This bead
makes the CUDA annex (`spark/frob-spark-cuda`, an annex workspace with its own lockfile and registered unsafe
capsules; the core never depends on a GPU crate) a full implementation: the ten-stage batched simulation step
runs on one RTX 4090 of the machine `trj`, from the same kernel sources and the same step plan as `batch-cpu`.

The execution model (DESIGN). Environment creation allocates every buffer, compiles or loads every kernel, and
builds a static **step plan**: an ordered list of launches with fixed grid sizes. A rollout is policy forward,
then the step plan repeated for the control decimation, then observation, all on the device; the host receives a
small statistics ring and snapshots on request. Nothing in a rollout may change a shape (ADR-SPARK-04: a batch is
a bucket of one shape class; no shape changes inside a running environment; reason: static shapes keep launch
graphs static). The price of ignoring that is published: another simulator's throughput falls to roughly a
quarter to a third when its launch graph is re-captured every step (FACT, source register).

FACT about the foundation: the suite's own GPU renderer pins `cudarc = "=0.19.9"` with features `driver`, `nvrtc`
and `dynamic-loading`; the driver and NVRTC load at run time, so the build needs no CUDA toolkit; dialect source
compiles per device architecture to a cached binary. The M0 admission bead (BD-015) established driver load,
NVRTC compile, a v0 cache and a single launch, and recorded whether the pinned `cudarc` binds graph capture and
stream-ordered pools. The cards on `trj` have no NVLink (the driver reports a PCI host bridge between two cards of
24,564 MiB each) and peer-to-peer transfer is unverified (OPEN-SPARK-6). Tier: Solid.

Rejected alternatives: re-capturing the graph when arguments change (the published slowdown); per-step host
synchronization (blocks the host and serializes device work); device allocation in the hot path (latency spikes
and leaks under cancellation); a second kernel source for CUDA (doubles the determinism surface).

## Technical approach

**1. The step plan (DESIGN; record `frob.stepplan/1`, type `StepPlan` in `frob-kernels`, defined by N21ap1-01 and
stated here so that this bead stands alone; this bead realizes it on CUDA).**

```text
header    schema, step_plan_id, shape class (capacities: n_v, links, depth, samples, contacts, rows, actuators;
          sensor and policy layouts; contact law; precision profile; lockstep iteration count)
          step profile (lockstep | strict), h (a rational number of seconds), world-steps per control interval d,
          Newton iterations and tolerance
kernels   per stage: kernel name, KernelId, class, CPU reference symbol
launches  ordered list; per launch: stage, kernel id, logical grid (worlds × lanes per world),
          argument bindings (slab, access read | write, footprint), epoch read, epoch written
chunk     control intervals per chunk; the rule that set it
bounds    per histogram: the largest number of increments one bin can receive in a chunk
resources totals from kernel metadata: buffer arguments per kernel, thread-group bytes, operation counts
```

`StepPlanId` is the content hash (BLAKE3 over canonical bytes) of the numerical descriptor of N16a-03: at least
the shape class, kernel versions (`KernelId`s), contact law, step profile, h, the number of world-steps per control
interval, Newton iterations and tolerance, plus the fields N16a-03 adds (precision, warm start, integrator, solve
path and the others it lists); the record carries it as supplied. A physics change changes this identity or a
world's model identity; nothing else does. The identity names no
device, slot or shard: the plan is backend-neutral, and a backend *realizes* it (rounds thread-group sizes to the
device's execution width, chooses block sizes). Building a plan validates every binding against the kernel's
stage signature (footprint inside the slab, no undeclared aliasing, epochs consistent) and refuses a plan in which
a statistics output reaches state.

**2. Device, context, thread.** Each device has one CUDA context and one host thread that owns it (a device
worker). Compile flags: the architecture (`-arch=sm_89`), `--fmad=false`, never fast math; every unit passes the
dialect lint before compilation (`FROB-REF-251` otherwise); compile failure returns `FROB-REF-603` with the
compiler diagnostics verbatim. Compiled binaries come from the kernel cache.

**3. Buffers.** `allocate` is called once at environment creation and creates every slab the plan binds, aligned
to 256 bytes, in device memory, zero-filled or uploaded once (scene fields, model tables). After creation no
device allocation occurs (INV-SPARK-03; the allocated-bytes counter is the evidence). Kernels index slabs by
buffer plus index.

**4. Launch graphs.** The step plan of a bucket is captured **once** as a launch graph spanning one control
interval (d world-steps, then observation): begin capture on the worker's stream, enqueue every launch of the
interval in plan order, end capture, instantiate. Thereafter each control interval is one graph replay.
HYPOTHESIS (measured by the hardware fingerprint): replaying a warm graph has near-constant host cost,
independent of its node count.
- *The control block.* Everything that varies between replays of the same graph (the step counter for random
  streams, the epoch, the cancel word, the decimation phase) lives in a small device buffer that the first kernel
  of the graph advances. The graph's arguments never change, so it is never re-captured.
- *Capture counter.* The backend counts captures per bucket; after warm-up the count must stay constant
  (INV-SPARK-05: no shape change inside a running environment; one graph capture per bucket). A request that would
  change a shape in a running environment is refused with `FROB-REF-611` (exit code 6; first repair: a new bucket).
  The invariant's row in the Spark register (`registries/invariants.toml`, section `spark`; N21c-27, a dependency)
  names its test `stepplan::one_capture_per_bucket` and its two planted violations, a reset that changes a grid
  size and a per-step re-capture; this bead writes the test under exactly that name and registers both controls,
  so the register's audit resolves the row to a live test.

**5. Stream-ordered pools.** The arena is one allocation made at environment creation. Transient device memory
(snapshot staging, readback) comes from a stream-ordered memory pool, so the allocations of a cancelled stream are
released in stream order and cannot leak. Three branches, decided by OPEN-SPARK-4 at the M0 admission:
(a) the pinned `cudarc` binds graph capture and the asynchronous pool calls: use them;
(b) it does not: the capsule declares the missing driver symbols itself, under its `SAFETY.md` and the capsule
    registry (under 300 lines, safe API);
(c) that is refused: transient buffers are preallocated in the arena and launches are submitted one by one, with
    the hot path's device-memory behaviour unchanged and the throughput cost disclosed in every disclosure block.
The fail-closed default until decided is (c).

**6. Synchronization.** No synchronization inside a control interval. The host synchronizes once per chunk of
control intervals; a synchronization counter per chunk must read zero inside the chunk. Timers cover completion,
never enqueue alone.

**7. Launch faults and the commit fence on CUDA.** A chunk reads its checkpointable state from the current one of
two committed slabs and ends with `K-commit`, which writes the new state to the other; only a completed chunk
makes the other slab current. If a launch or replay fails, the current slab was never written: restore from it and
resubmit, at most four attempts with growing waits, then refuse with `FROB-REF-607` "a launch or command buffer
failed after bounded retries" (exit code 6; first repair: resume from the last committed epoch). Every retry is
counted in the receipt. A replay from the committed slab is bit-identical because no kernel has data-dependent
scheduling.

**8. Snapshots.** A snapshot read copies the snapshot slab to the host through pool-staged memory under the lease
rules; each read is checked against the digest the device emitted for that epoch.

**9. Receipts.** Every chunk returns a receipt with the twelve accelerator evidence fields unchanged (device
identity; driver and runtime; compiler and backend; kernel source identity; kernel and workload identity; CPU axes;
reduction and determinism policy; CPU-versus-device comparison; the retained CPU reference; cancellation outcome;
phase attribution; go or no-go) and beside them: placement per stage, fingerprint digest, determinism class,
capacities, graph replays, captures, synchronizations, retries, pool bytes high-water mark, device seconds.

**10. Two cards.** Worlds are sharded across devices and only small statistics cross through the host (no link
between the cards). This bead makes each device worker independent and correct on its own; the sharded run and its
scaling gate belong to BD-199.

## Acceptance criteria

- [ ] The full ten-stage step for the reference quadruped workload (18 degrees of freedom, contact capacity 32, row capacity 160, step 2 ms, 4 Newton iterations, decimation 10) runs on one RTX 4090 at 8,192 worlds from the same step plan as `batch-cpu`, and a quadruped drops, stands and walks under the baseline controller (seed done-condition).
- [ ] `frob.stepplan/1` round-trips; `StepPlanId` is equal on `batch-cpu` and CUDA for the same job and changes when any hashed input changes (h, d, iterations, a `KernelId`, a capacity) and not when the device, slot count or shard count changes.
- [ ] GATE-SPARK-12, CUDA rows (TARGET, M2), each clause measured on `trj` by this bead's annex tests and logged with its value: zero graph captures after warm-up; zero synchronizations inside a chunk; no pool memory leaked after 10³ cancel cycles; 10⁵ snapshot reads each match the digest emitted for their epoch; the commit-fence known answer holds under 10³ injected launch faults (final digests equal those of the unfaulted run). The gate's record with these rows is written through the gate script, which is N21b-26's and depends on this bead: this bead closes on its own tests and its first-light script, and does not wait for that record (67 beads depend on this one, and none of them should wait on a bead that waits on it).
- [ ] Negative controls: a planted shape change mid-rollout is refused with `FROB-REF-611` and would otherwise raise the capture counter (the counter test catches a build that re-captures silently); a planted host synchronization inside a chunk is counted; with the commit fence disabled, injected faults produce a digest mismatch that the test detects; a planted leak of one pool allocation per cancel is caught after 10³ cycles.
- [ ] Per-world digests on CUDA are identical run to run (class D2) for 1,000 steps at 8,192 worlds; the comparison against `batch-cpu` is entered in the divergence ledger under the class the device attains (measured by BD-176, not asserted here).
- [ ] The OPEN-SPARK-4 branch in force is recorded in the receipt and the disclosure block; under branch (c) the same acceptance tests pass with per-launch submission.
- [ ] Every chunk receipt validates (twelve fields, fingerprint digest, counters); a result reaches `frob --json` with its evidence block.
- [ ] This bead's first-light script `scripts/e2e/spark_cuda_full_step.sh` exits 0 on `trj` (precompile, the 8,192-world run, the repeat under a second key with equal per-world digests, the annex tests) and writes its structured log; the capsule registry lists every unsafe capsule with its `SAFETY.md`. (The gate script `spark_gate12_launch_fence.sh` passing on CUDA is N21b-26's acceptance.)

## Considerations

- OPEN-SPARK-4: default is preallocated transient buffers and per-launch submission with the throughput cost disclosed; decided at INT-CUDA-01. Third-party gaps are not upstream work items: where a binding is missing the annex binds the driver directly inside a registered capsule.
- OPEN-SPARK-6: device-to-device access on `trj` is untested; default host-staged transfers of small statistics only; decided by the fingerprint.
- OPEN-SPARK-1: until ADR-SPARK-01 is ratified every device result is labelled exploratory; if it is never ratified, M2 exits in its no-GPU variant and this bead's gate is recorded `not run` with the reason.
- OPEN-SPARK-2: the default compute envelope allows one device for one hour per GPU job; 10⁶-step and 10³-cycle tests are sized to fit, or run under an approved gate-measurement envelope.
- A warm graph's replay cost being independent of node count is a HYPOTHESIS; if the fingerprint shows it grows with nodes, the interval is split into several graphs, which changes nothing in the plan identity.
- RISK-48 (a driver update changes kernel results): the cache key and the check currency depend on the driver; a fingerprint identity change makes this backend refuse to cite results until `spark check` is re-run.
- A compile takes about 5 s on an idle host and can take 15 minutes on a heavily loaded one (FACT); `trj` is often loaded, which is why precompilation and the cache are separate steps.
