## Background

A device can fail in ways a CPU run rarely does: the card disappears, a compile fails on one driver, a command
buffer is aborted because another process hung the GPU, a launch never returns, one world's arithmetic produces a
NaN among eight thousand that are fine. Spark's rule for all of them is the system-wide one: **refuse, never
truncate**; every fault is a typed refusal with a stable code, the fingerprint digest and ranked repairs, and
nothing partial is published as a result.

Cancellation is the same discipline from the other side. The definition of "implemented" for any capability
includes: cancellation is tested (request, drain, finalize) with no leaked device resources. The suite's
accelerator doctrine makes the evidence precise (FACT, `frankensim/docs/ACCELERATOR_DOCTRINE.md`, field AE-10):
cancellation is at the kernel-batch boundary, followed by request, drain and finalize evidence; the proof must be
**executor-minted** (FrankenSim's `fs_exec::DrainFinalizeReport`): a caller-authored cancelled flag or a dropped
device handle is not drain evidence. Spark's receipts carry that field unchanged.

Two design choices shape what can go wrong at all. The grid-wide barrier that stalls the suite's own renderer
about once per few hundred launches is excluded by a dialect rule (a stage that needs every world to finish is two
launches), so what remains is a command buffer that fails or one that never returns. And the unit of commit is
the chunk: state advances only when a chunk completes, so every recovery starts from a committed epoch and replays
bit-identically (no kernel has data-dependent scheduling). Tier: Solid.

Rejected alternatives: continuing a batch after a device fault with whatever state is in memory (a terminal state
other than completed invalidates every slab the batch could write); dropping a world that overflowed a capacity
(changes physics without a trace); treating a dropped handle as a cancellation; a watchdog that kills the process
(loses every other device's work).

## Technical approach

**1. Chunks (context).** The host synchronizes once per chunk of control intervals. The chunk length is the
shorter of one rollout segment and the number of intervals that fit the cancellation latency target (250 ms at
the 99th percentile, TARGET). A chunk reads checkpointable state from the current committed slab and ends with
`K-commit` writing the other; only a completed chunk makes the other slab current.

**2. Cancellation.** The job's capability context carries the cancel request (asupersync's `Cx`; the core defines
the trait, the daemon supplies it).
1. *Request*: the host sets the cancel word in the device control block; it is observed at the next kernel-batch
   boundary (the next graph replay on CUDA, the next batch on Metal). Nothing is interrupted inside a kernel.
2. *Drain*: batches already admitted run to their boundary; no new batch is admitted; stream-ordered pool
   allocations of the cancelled stream are released in stream order.
3. *Finalize*: the executor (not the caller) mints the drain report: batches admitted, batches drained, last
   committed epoch, resources released (pool bytes back to baseline, leases returned), and the outcome
   `completed | cancelled-drained | failed`. The report is evidence field AE-10 of the receipt.
A dropped handle is not a cancellation receipt: a job whose handle was dropped without a minted report is recorded
as `indeterminate` and must be recovered by key. Latency from request to finalize is measured against the 250 ms
target and reported as a distribution.

**3. Fault taxonomy and typed refusals (all exit code 6, the backend and device family; each carries the
fingerprint digest and ranked repairs).**

| Injected or real fault | Refusal | First repair offered |
|---|---|---|
| Device unavailable or lost (context creation fails; the device disappears mid-run) | `FROB-REF-601` | Rerun on another device, or on `batch-cpu` under `mixed-allowed` |
| The memory estimate exceeds the device budget at admission | `FROB-REF-602` | Fewer worlds, a smaller capacity, or the Mac |
| Kernel compile failure (diagnostics verbatim) | `FROB-REF-603` | Report; the generic kernel if a specialized one failed |
| A launch or command buffer failed after bounded retries | `FROB-REF-607` | Resume from the last committed epoch |
| Worlds marked `Faulted` exceed the caller's threshold | `FROB-REF-608` | Teleport a faulted world to `batch-cpu` |
| Capacity overflow under the `refuse` policy | `FROB-REF-610` | A larger capacity; `continue-flagged` |
| Device stalled (watchdog) | `FROB-REF-615` | Restart the device worker |

A run-time out-of-memory on a device should be unreachable (no allocation after creation; admission refuses
first); if a pool or driver call still reports it, it is surfaced as `FROB-REF-601` with the driver's message and
the run resumes from the committed epoch on restart.

**4. Retry rule (commit fence).** A terminal state other than completed invalidates every slab the batch could
write. FACT: "when another process hangs the GPU, macOS restarts it and aborts every command buffer in flight"
(`ft-kernel-metal` `lib.rs`). On failure the current committed slab was never written, so the arena restores from
it and resubmits: at most four attempts with growing waits (DESIGN: 10 ms, 40 ms, 160 ms between attempts), then
`FROB-REF-607`. Every retry is counted in the receipt.

**5. Per-world states.**
- *Faulted.* A world that produces a non-finite value is frozen and marked `Faulted` for teleport. Detection is an
  exact bit test at the end of each step (exponent bits all ones in any state word), written to the world's status
  word with an order-independent integer atomic or a per-world write; from the next step the world's state is
  copied forward under its mask, not recomputed. When the count of faulted worlds exceeds the caller's threshold
  (`--max-faulted`, default 0 for evaluation and paired comparison, a stated fraction for training), the chunk
  boundary raises `FROB-REF-608`.
- *Degraded.* A world that overflows a capacity is marked `Degraded` with the reason; the caller's policy chooses
  `refuse` (`FROB-REF-610` at the chunk boundary), `reset` (the world is reset at the next masked reset and the
  event counted) or `continue-flagged` (it continues, flagged, and its steps are counted separately).
- Steps of worlds marked `Degraded` or `Faulted` are counted separately and are never in the numerator of a rate.

**6. Stalls.** A watchdog on a second host thread marks the device `Stalled` (`FROB-REF-615`) when a chunk exceeds
the upper end of its predicted time by a set factor (DESIGN default: 4 times the upper end of the estimator's
interval for the chunk, never less than 2 s; a TARGET to be tuned on the M2 profile). The wait itself cannot be
interrupted on Metal today (a gateway limit; upstream work item FD-FT-01), so the supervisor restarts the device
worker and the job resumes from the last committed epoch; other devices' workers are untouched.

**7. Injection points (test builds only).** CUDA: a wrapper around launch, graph replay, context creation and
compile that fails on a scheduled call index. Metal: the gateway's own seam (FACT: `inject_command_buffer_faults`,
present in builds with debug assertions). Kernel level: a test kernel that writes a NaN into world k at step j; a
synthetic scene that forces contact overflow; a test kernel that spins for a configured time (stall). Admission: a
job sized over the budget. Injection is scheduled by seed, so every fault run is reproducible.

## Acceptance criteria

- [ ] GATE-SPARK-06 (TARGET, M2; the seed done-condition), recorded with measured values on CUDA and Metal: every injected fault yields its typed refusal (the seven rows above, each on each backend where it applies); no leaked device memory after 10³ cancel cycles (allocated and pool bytes return to baseline); the drain report is executor-minted.
- [ ] Negative controls: a dropped handle presented as a drain report is rejected (the receipt check distinguishes executor-minted from caller-authored); a build that leaks one transient allocation per cancel is caught by the 10³-cycle test; a fault with retries disabled yields `FROB-REF-607` immediately and a fault with the fence disabled yields a digest mismatch that the test detects.
- [ ] Recovery is exact: after an injected command-buffer or launch fault within the retry budget, final per-world digests equal those of the unfaulted run, and the receipt shows the retry count.
- [ ] A NaN planted in one world of 8,192 marks exactly that world `Faulted`, freezes it, leaves every other world's digest unchanged, and raises `FROB-REF-608` when the threshold is 0.
- [ ] A forced contact overflow marks the world `Degraded` with its reason; under `refuse` the run returns `FROB-REF-610`; under `continue-flagged` it completes with the flagged-step count reported and excluded from the rate.
- [ ] A stalled chunk is detected within the watchdog bound, reported as `FROB-REF-615`, the worker restarts, and the job resumes from the last committed epoch with digests equal to an unstalled run.
- [ ] Cancellation latency (request to finalize) is reported as a distribution against the 250 ms target at the 99th percentile over 10³ cycles.
- [ ] Every refusal envelope carries the fingerprint digest, the ranked repairs and exit code 6; the gate's end-to-end script exits 0 and writes its log.

## Test plan

### Unit tests
- `cancel_request_observed_at_batch_boundary`: the cancel word set during batch k is honoured before batch k + 1 and never inside k.
- `drain_report_is_executor_minted`: the type can be constructed only inside the executor module (a compile-fail test for construction elsewhere).
- `dropped_handle_is_indeterminate` (negative control).
- `retry_schedule`: failures at attempts 1 to 3 then success → three retries counted; four failures → `FROB-REF-607`.
- `faulted_world_frozen`: a NaN at step j in world k: status `Faulted`; state at step j + 10 equals state at step j; neighbours' digests equal the clean run.
- `faulted_threshold_608`: thresholds 0 and 1 with one faulted world.
- `non_finite_detection_is_bit_exact`: +∞, −∞, NaN with payload detected; the largest finite value not.
- `degraded_policies`: refuse, reset, continue-flagged.
- `degraded_steps_not_in_rate`.
- `watchdog_marks_stalled`: a kernel that spins for 3 times the bound → `FROB-REF-615`; one that takes 0.9 times the bound → no stall.
- `fault_to_code_table`: each injection point maps to the code in the table.
- Property test: for random schedules of faults within the retry budget and cancels, final digests of completed jobs equal the fault-free digests, and resource counters return to baseline.

### End-to-end script and logging
`scripts/e2e/spark_gate06_faults_cancel.sh` (carried by the end-to-end bead of this gate, drafted as N21b-25 by
the unit that owns the execution-model subsection; it sources the shared end-to-end helper, is seed-explicit and
idempotent, and uses the fault-injection test build of the `apps/` binaries). Steps, each on `gpu-cuda` and
`gpu-metal` where present: `baseline` (`frob sim run --workload Q --worlds 8192 --seconds 10 --seed <s> --json`,
digests saved), `fault_device_lost`, `fault_compile`, `fault_oversize`, `fault_launch_retry`,
`fault_launch_exhausted`, `fault_nan_world`, `fault_capacity_refuse`, `fault_capacity_flagged`, `fault_stall`,
`cancel_cycles` (10³ times `frob job submit … ; frob job cancel <id> ; frob job wait <id>`), `drain_report`
(reads AE-10 from each cancelled job's receipt). Every NDJSON line has `ts`, `script`, `bead`, `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the
envelope's `evidence` block, the refusal code with its repairs, counters (retries, faulted worlds, degraded
worlds, allocated bytes before and after, cancel latency percentiles against 250 ms), run digests, and on failure
the first differing world address and the artifact paths to reproduce. The final `summary` line lists assertions
and `gates: ["GATE-SPARK-06"]`; the gate receipt is written by
`cargo test -p frob-conformance --test g4 -- GATE-SPARK-06` from the collated output. No private-scene data.

### Known answers and negative controls
- KA-542: every injected fault yields its typed refusal; no leaked device memory after 10³ cancel cycles; the drain report is executor-minted.
- KA-537: commit fence under injected faults: digests equal the unfaulted run; at most four attempts; then `FROB-REF-607`; negative control: fence disabled.
- Negative controls: dropped handle; leak per cancel; retries disabled; fence disabled.
- Metamorphic: injecting a fault and recovering changes no digest; cancelling and resubmitting with the same idempotency key yields the same results as an uninterrupted job.
- Determinism lanes: fault runs repeated twice with the same seed give identical refusal sequences and digests.

## Considerations

- The watchdog factor trades false stalls against detection time; `trj` is often heavily loaded (FACT), which stretches chunk times, so the bound is derived from the estimator's interval for the current fingerprint and load, not from a constant.
- On Metal a stalled wait cannot be interrupted until upstream work lands; restart of the worker is the only recovery, which is why the Metal backend runs one worker per process and holds no uncommitted command buffer.
- A world that faults is evidence about the model or the kernel, not noise: it is teleported to `batch-cpu` for localization; training profiles may tolerate a fraction, evaluation and paired comparison tolerate none by default.
- OPEN-SPARK-2: 10³ cancel cycles and the fault runs fit the default envelope (one device, one hour); they are sized in the script.
- The chaos tier of the conformance harness reuses the same injection points with randomized schedules.
