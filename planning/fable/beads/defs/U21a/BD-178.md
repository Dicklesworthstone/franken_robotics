## Background

An agent that asks for a GPU run must be able to tell acceleration from a silent fallback. Engines that fall back
to the CPU for an unsupported stage, quietly, produce results that are slower than claimed, or are scored on a
different arithmetic path than requested, and nobody finds out. ADR-SPARK-05 (DESIGN): **placement is planned and
receipted per stage; a strict backend request fails before any scoring if a stage has no kernel there.**

`spark.place` turns a request into a plan before anything runs. For each stage of the batched step (kinematics;
collision geometry; broad phase; narrow phase; compaction; dynamics terms; constraint rows; solve; integrate and
energy ledger; sensors, observations, rewards and resets), and for the policy, the learner, the statistics and the
snapshot path, it chooses a backend and writes down why. The verb (kind `read`, milestone M2) returns the
placement plan and the residency map, before anything runs; the same record, filled with measured counters, is
the placement receipt attached to every device result (invariant INV-SPARK-02 requires it).

The planner also carries a lesson from a recorded pilot (FACT as recorded): a small integer predicate job, end to
end, took about 34 µs on the host against about 290 µs on Metal, of which under 13 µs was device time, and over
1.2 ms on one RTX 4090; two-card sharding was slower than one card. "It is a kernel, so it belongs on the GPU" is
false for small host-resident work; dispatch, transfer and synchronization dominate. So the planner has a cost
model and it keeps a small host-resident job on the host. Tier: Solid.

Rejected alternatives: best-effort fallback without a receipt; a global "use GPU" switch with no per-stage
record; counting only device kernel time in throughput (the denominator must be whole).

## Technical approach

**1. The record (DESIGN).**

```text
frob.placement/1 (one row per stage)
  stage, kernel ids, requested backend, actual backend, fallback reason, fallback count,
  transfer bytes host→device and device→host, synchronization count, resident duration,
  device seconds, command buffers or graph replays, retries
header: request mode (strict | prefer | mixed-allowed), fingerprint digest, shape class, bucket, capacities,
        determinism class attained, check currency per kernel
```

As a *plan* (before the run) the measured columns are empty and predicted costs are attached; as a *receipt*
(after the run) they are filled from backend counters. Rows exist for the ten step stages and for `policy`,
`learner`, `statistics` and `snapshot`.

**2. Request modes** (spelled as the value of `--tier <mode:backend>`, the grammar of N21b-29).
- `strict:gpu-cuda` or `strict:gpu-metal`: every stage must run on the named backend.
- `prefer:<backend>`: never mixes. If the named backend cannot run every stage, the whole plan moves to one
  backend that can, and the plan says so before the run starts.
- `mixed-allowed:<backend>`: a stage may fall back to `batch-cpu`; the receipt then shows actual differing from requested,
  the reason, and the bytes and synchronizations it cost.

**3. Planner rules.**
1. **Strict means strict.** Under a strict request, a stage with no kernel on that backend is `FROB-REF-604`
   "strict backend: a stage has no kernel on the requested backend" (first repair: `mixed-allowed`, or the other
   backend); a stale CPU-versus-device check under `--require-current-check` is `FROB-REF-605` (first repair:
   `spark check`); a missing arithmetic feature that a kernel declares (for example 64-bit integers) is
   `FROB-REF-616` (first repair: the 32-bit variant, or another backend). All are raised by the planner, exit code
   6. No world is stepped and nothing is scored.
2. **Mixed placement is opt-in.** Only `mixed-allowed` lets a stage fall back.
3. **The denominator is whole.** Transfers, synchronizations, compilation and retries are in the receipt and in
   every throughput figure derived from it.
4. **A cost model decides small jobs.** A job goes to a device only if its predicted device time including
   dispatch, transfer and synchronization is below its host time. Crossover sizes are calibrated per device family
   from the fingerprint.
5. **Each device closes its own loop.** A hybrid plan may claim acceleration only for stages that ran on the
   device and returned a device-timed receipt (on Metal: a completed command buffer with start and end times from
   the device).

**4. Planning algorithm.**
1. Resolve the job to a shape class, bucket and step plan; list the kernels of each stage.
2. For each stage and candidate backend, check: a registered kernel with a dialect source for that backend
   (library index); resource bounds within the backend's limits; arithmetic features against the fingerprint;
   check currency if required.
3. Apply the mode: strict → refuse on the first failing stage with the stage and kernel named (all failing stages
   are listed in the refusal's detail); prefer → choose the single backend that passes every stage, preferring the
   named one; mixed-allowed → per stage, the requested backend if it passes, else `batch-cpu`, with the reason.
4. For jobs and auxiliary paths small enough for the cost model: predicted device time =
   launches × launch cost + encode or replay cost + transfer bytes / bandwidth + synchronizations × commit-and-wait
   cost + kernel time; predicted host time from the `batch-cpu` calibration; place on the host unless the device
   time is lower. A predicate whose inputs are host-resident stays on the host; one whose inputs are already
   resident on the device may run there.
5. Compute predicted transfers per stage boundary where the backend changes (a mixed plan pays a transfer and a
   synchronization at each such boundary) and attach them to the plan.
   From M3, when a bucket's model variants span several segments of the world bank, the planner calls
   `launch_groups(bucket, &VariantSegmentMap)`, which N19c-20 adds to this module (it depends on this bead), and
   issues each field-reading stage once per launch group and every other stage once; at M2 every bucket is one
   group and the call is absent.
6. Emit the plan with the header, including the determinism class the placement can attain (the weakest among
   its kernels and backends) and each kernel's check currency.

**5. Counters and the shim.** Each backend increments counters at its only transfer and synchronization entry
points (upload, readback, snapshot staging, chunk synchronization). For the gate, an **instrumented shim** wraps
the real driver calls underneath (a counting pass-through, not a stand-in: every call still reaches the driver or
gateway) and counts independently; receipt counters must match the shim's within one count.

**6. The verb.** `frob spark place --tier <mode:backend> (--workload Q|H | --design <id> --task <id>) --worlds N
[--require-current-check] [--need-class D0|D1|D2|D3] [--env <id>] --json` (N21b-29's grammar) returns the plan and the residency map: per slab, where it lives, its size, its last committed epoch and
who may read it. It runs nothing. On refusal the envelope carries the refusal with every failing stage listed.
`sim.run` and the job verbs call the same planner and attach the filled record to their receipts.

## Acceptance criteria

- [ ] GATE-SPARK-09's clauses (TARGET, M2; the seed done-condition) hold with measured values on CUDA and Metal in this bead's own tests: for **every** stage, withholding its device kernel under a strict request yields `FROB-REF-604` with zero worlds stepped (the step counter and the episode count are zero and no result artifact exists); receipt counters for transfers and synchronizations match the instrumented shim within one count. The gate row is recorded from the user-side script by N21b-31, which depends on this bead.
- [ ] Negative control (KA-534): the same request under `mixed-allowed` completes and its receipt shows actual ≠ requested for the withheld stage, with the reason, the bytes and the synchronizations.
- [ ] INV-SPARK-07: a strict request never scores on a fallback: the property test `placement::strict_withheld_kernel_zero_worlds` (the name the Spark invariant register N21c-27 binds to this invariant) over random subsets of withheld kernels finds no strict run with a non-empty result, and catches its planted violation, a planner that silently runs a withheld stage on `batch-cpu` under `strict:gpu-cuda`.
- [ ] `prefer` never mixes: with one stage unavailable on the preferred backend, the whole plan moves to a single backend and the plan states it before the run.
- [ ] `--require-current-check` with one stale kernel check yields `FROB-REF-605`; a kernel declaring 64-bit integers on a device whose fingerprint lacks them yields `FROB-REF-616`.
- [ ] Cost model: the recorded pilot's case (a 65,536-row integer predicate with host-resident inputs) is placed on the host on both machines; the same predicate with device-resident inputs inside a device job is placed on the device; the predicted and measured times are within the model's stated interval.
- [ ] `frob.placement/1` round-trips; every device result's receipt contains it; `frob spark place --json` returns one envelope with the plan and the residency map and exit code 0, or a refusal with exit code 6.
- [ ] A throughput figure computed from a receipt includes compile, transfer, synchronization and retry time (checked against a figure that omits them: the harness refuses the latter).
- [ ] This bead's script `scripts/e2e/spark_place_smoke.sh` exits 0 on each device backend present and writes its structured log (the gate script `spark_gate09_placement.sh` passing is N21b-31's acceptance).

## Test plan

### Unit tests (`cargo test -p frob-kernels placement`)
- `strict_refuses_missing_kernel_per_stage`: fourteen cases (ten stages, policy, learner, statistics, snapshot), each → `FROB-REF-604` naming the stage.
- `strict_refusal_lists_all_failing_stages`.
- `mixed_allowed_records_fallback`: actual = `batch-cpu`, reason "no kernel on gpu-metal", fallback count 1.
- `prefer_moves_whole_plan`.
- `require_current_check_605`; `missing_feature_616`.
- `plan_predicts_boundary_transfers`: a mixed plan with one CPU stage between device stages predicts two transfers and two synchronizations per step.
- `cost_model_small_job_stays_on_host`: with fingerprint figures (launch 10 µs, commit and wait 250 µs, bandwidth as recorded) and a 34 µs host time, the device prediction exceeds the host time.
- `cost_model_crossover`: increasing the row count by powers of two finds a crossover size; below it host, above it device.
- `receipt_counters_fill_plan_rows`.
- `attained_class_is_weakest`.
- `placement_record_roundtrip`.
- Property test `placement::strict_withheld_kernel_zero_worlds` (INV-SPARK-07; N21c-27's row): random withheld sets under strict → refusal and zero steps; under mixed-allowed → actual ≠ requested exactly for the withheld stages; with the silent-fallback planner mutant enabled the test fails.

### Known answers and negative controls
- KA-534: strict placement with one device kernel withheld, for every stage: refusal before any world is stepped; zero episodes; counters match the shim within one count; negative control: `mixed-allowed` must show actual ≠ requested.
- CX-217: a kernel does not belong on the GPU because it is a kernel (34 µs host; about 290 µs Metal with under 13 µs device time; over 1.2 ms on one RTX 4090).
- Negative controls: a planner mutant that falls back silently under strict is caught by `placement::strict_withheld_kernel_zero_worlds` and by the script's `strict_run` step (a run appears: the step counter and the placement row); a receipt that drops one synchronization is caught by the shim comparison; a cost model that omits the transfer and dispatch terms (N21b-30's `transferless_model_mutant_detected`) places the 65,536-row predicate on the device and is caught by `cost_model_small_job_stays_on_host`, which is the test the counterexample registry binds to CX-217.
- Determinism: planning is a pure function of the request, the library index, the fingerprint and the check ledger (class D0); the same inputs give the same plan on both platforms.

## Considerations

- A mixed plan can be slower than either pure plan because every backend boundary costs a transfer and a synchronization; the plan shows the predicted cost before the run so an agent can choose.
- The cost model is only as good as the fingerprint; when the fingerprint identity changes, crossover sizes are recalibrated and plans made under the old identity are refused as evidence (`FROB-REF-606`).
- Under the fail-closed default for the annex ratification question, every device plan is marked exploratory; under the no-GPU variant of M2 every plan resolves to `batch-cpu` and strict device requests refuse.
- Placement across the two machines (which machine runs a job) is the fleet policy's concern; this planner places stages on backends within one machine.
- The M2 verb set exposes `spark.place` with schema, examples and refusal list; long residency maps are paginated.
