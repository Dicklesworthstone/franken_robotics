## Background

In Spark a design is data: a world indexes a model variant inside padded capacities, so one generic kernel set
serves every design in a bucket and nothing is compiled per design. A **specialized kernel** is the generic
kernel with one design's constants folded in and its loops unrolled (padding removed). It may replace the
table-driven kernel for designs that survive several rounds of a race and will run for a long time.

**Ceiling, stated first.** FACT (an incumbent's own event trace of a humanoid at 8,192 worlds, source register):
of 262 ns per world-step, the stages a design-specialized recursion could touch (kinematics, centre-of-mass terms,
composite inertia, bias forces, forward acceleration) sum to 53 ns, 20% of the step; the solve is 124 ns and
constraint construction 38 ns. An infinitely fast recursion would give 262/209 = 1.25; a recursion twice as fast
gives 1.11; a manipulation scene gives a share of 16% and a ceiling of 1.19. Generated code also does not reliably
beat a good generic library. The expected gain is therefore 1.05 to 1.15 and the cap is near 1.2. An incumbent's
cold kernel compilation takes about 96 s, which is why per-design kernels as the default path are rejected
outright.

**ADR-SPARK-08** (DESIGN): per-design kernel specialization is built for survivors only, only if our own profile
justifies it, and only bit-identical to the generic kernel. Sparsity in constraint assembly and solve is carried
as data and is measured separately; it is not this mechanism.

**KILL-SPECIALIZE.** Trigger: in the pilot the specialized arm over the unpadded data-driven arm is below 1.2 on
the whole step, or the specialized kernel takes more than 60 s to compile; or the M2 profile shows a specializable
share under one third (the share at which the ceiling 1/(1 − s) reaches 1.5). Fallback: data-driven kernels only;
derivation stays for correctness, certificates and the derivative kernels of CPU solvers, where rigid-body
derivatives dominate. The profile clause can fire at M2 before any pilot is funded; the decision point for the
work package is M4. Tier: Frontier. This bead exists only on the branch where the gate does not fire; if it
fires, the bead is closed `not built` with the decision record as its reason.

## Technical approach

**Design rules (all DESIGN, from the plan).**
- Specialization is never the default and never part of the edit loop.
- It is built only for the survivors of a tournament that go on to finalist training, and only if the M2 profile
  shows a specializable share of at least one third of the step.
- A specialized kernel must be bit-identical to its generic kernel: unrolling keeps the operation order and only
  exact constant operations are folded. `spark check` enforces it; a mismatch is `FROB-REF-613` "a specialized
  kernel is not bit-identical to its generic kernel" (exit code 6; first repair: the generic kernel).
- Survivor cohorts move to specialized kernels only at an acknowledged chunk boundary, with a versioned state
  map, and the specialized kernel is another cache entry.

**1. The specializer (in `frob-kir`).** Input: a generic kernel program P (bounded loops over capacities, loads
from the model variant table) and one design's table values. Output: a program P_d.
1. *Bind constants*: every load from a read-only model-table slot is replaced by a `Const` holding the design's
   exact bit pattern for that entry.
2. *Unroll*: each loop whose bound is a capacity is unrolled to the design's active count (padding iterations
   are removed; this is legitimate because padding holds neutral elements and masked lanes copy forward, so
   removing them changes no active value); iterations are emitted in index order, so the operation order of the
   surviving arithmetic is exactly the generic order.
3. *Resolve data-as-code*: selects whose predicate is now a constant (joint class masks, active-column masks) are
   simplified by the exact rule select(true, a, b) → a.
4. *Fold exactly*: only operations on constants whose mathematically exact result is representable fold (the
   exact rewrite table of the IR; no reassociation, no distribution, no x·0 → 0, no fused multiply-add). A
   multiplication of a state value by a design constant stays a multiplication.
5. *Share and schedule*: common-subexpression sharing and live-range scheduling (both bit-exact).
6. Emit the rule trace of steps 3 to 5 for the independent trace checker. The resulting program has a new content
   hash: a specialized kernel is a new `KernelId` whose manifest records `specialized_from = <generic KernelId>`
   and `design = <ModelId>`.
Why bit identity holds by construction: every surviving operation of P_d is an operation of P on the same
operands in the same order; removed operations are those whose results were masked out or neutral; folded
operations are exact. Why it is still tested: the argument assumes padding neutrality and an exact rule table,
and both are code.

**2. Compile and cache.** P_d is emitted to Rust and dialect, linted, resource-checked (an unrolled kernel has
more live values; the resource metadata must fit the backend), compiled, and stored as an ordinary kernel-cache
entry keyed like any other. Compile time is capped at 60 s per design on CPU workers; a compile that exceeds the
cap is abandoned and the survivor keeps the generic kernel. A compile failure of a specialized kernel is
`FROB-REF-603` with first repair "the generic kernel if a specialized one failed".

**3. Promotion rule.** A survivor is promoted when T_remaining·(1 − 1/g) exceeds the compile cost, with
T_remaining the device time the design is still expected to run and g the measured whole-step gain of
specialization for its bucket. With g = 1.2 and a 60 s compile, promotion needs T_remaining > 360 s; with g = 1.1,
T_remaining > 660 s. Below the threshold nothing is built.

**4. Bit-identity enforcement.** Before a specialized kernel may run in a cohort: `spark check` runs it and its
generic kernel on 10⁶ states of that design (drawn by address from the cohort's own state distribution plus the
edge set) on the target device and compares outputs byte for byte. Any difference quarantines the kernel
(`FROB-REF-613`), the cohort stays generic, and the difference is recorded with its first differing input. A
kernel that reproduces the generic digests on the pinned corpus is interchangeable with it: results carry the
generic step plan's identity plus the specialized kernel's id in the receipt.

**5. Switch-over.** A cohort changes kernels only at an acknowledged chunk boundary (the device has committed
epoch e; the host has acknowledged it), with a versioned state map from the generic layout (padded) to the
specialized layout (unpadded) and back, itself an exact copy. The first chunk after the switch is compared by
digest against a generic shadow of the same worlds; a mismatch reverts the cohort and quarantines the kernel.

**6. What the gate measures.** GATE-SPARK-14 (Performance, Frontier, M4): a specialized kernel is bit-identical
to its generic kernel and at least 1.2 times as fast on the whole step, with compile time at most 60 s. "Faster"
is the one-sided 95% paired lower bound of the whole-step ratio (at least ten pairs, randomized order, the full
denominator), on the reference quadruped at 8,192 worlds, against the **unpadded data-driven** kernel as the
comparison arm, with the disclosure block.

## Acceptance criteria

- [ ] KILL-SPECIALIZE is decided with its three readings recorded (seed done-condition): the M2 profile's specializable share against one third; the pilot's whole-step ratio of the specialized arm over the unpadded data-driven arm against 1.2; the pilot's compile time against 60 s. If any clause fires, this bead closes `not built`, citing the record, and data-driven kernels remain the only path.
- [ ] If built, GATE-SPARK-14 (TARGET, M4; seed done-condition) is recorded with measured values: bit-identical outputs on 10⁶ states; paired lower bound of the whole-step speed ratio at least 1.2; compile time at most 60 s.
- [ ] INV-SPARK-09: for every specialized kernel admitted to a cohort, the byte comparison on 10⁶ states passes; the receipt names both kernel ids.
- [ ] Negative control (KA-538): a reassociated variant (one sum regrouped during specialization) is refused with `FROB-REF-613`; a variant that folds an inexact constant product is refused; a variant that drops a masked-but-active lane is refused.
- [ ] The specializer's rule trace replays in the independent checker; a trace with a rule outside the exact table is rejected.
- [ ] Promotion arithmetic: a survivor with T_remaining = 300 s at g = 1.2 and a 60 s compile is not promoted; with 400 s it is.
- [ ] Switch-over happens only at an acknowledged chunk boundary; per-world digests of a cohort across a switch equal those of an all-generic run; a planted mismatch reverts the cohort.
- [ ] A specialized kernel whose resource bounds exceed a backend limit is refused at build time for that backend and the survivor stays generic there.
- [ ] Specialization is off by default: no specialized kernel is built in the edit loop or for a design that is not a named survivor (asserted from cache contents after a standard campaign).

## Test plan

### Unit tests (`cargo test -p frob-kir specialize`, `cargo test -p frob-kernels specialize`)
- `specialize_binds_constants_as_bit_patterns`.
- `specialize_unroll_preserves_order`: a loop summing 3 active of 8 lanes left to right becomes three additions in index order; outputs bit-identical to the generic loop on [2²⁴, 1, 1] (16,777,216 in both).
- `specialize_removes_padding_exactly`: with padding holding −0.0 the generic and specialized sums agree bit for bit, including for an active set whose sum is −0.0.
- `specialize_folds_exact_only`: constant 0.5 × constant 4 folds to 2; state × constant does not fold; constant 0.1 × constant 3 does not fold.
- `specialize_select_resolution`: a constant joint-class mask removes the unselected arm.
- `specialized_equals_generic_1e6_states` (gate lane): byte comparison.
- `reassociated_variant_refused_613`, `inexact_fold_refused`, `dropped_lane_refused` (negative controls).
- `specialized_kernel_id_and_manifest`: new id; `specialized_from` and `design` recorded.
- `promotion_rule_arithmetic`: thresholds 360 s (g = 1.2) and 660 s (g = 1.1) for a 60 s compile.
- `compile_cap_abandons`: a synthetic slow compile is stopped at 60 s and the survivor keeps the generic kernel.
- `switch_only_at_acknowledged_boundary`; `switch_digest_shadow_detects_mismatch`.
- Property test: for random generic programs within the IR's loop forms and random designs, the specialized program's outputs equal the generic program's on random states, bit for bit, in the reference interpreter.

### End-to-end script and logging
`scripts/e2e/spark_specialize.sh` (owned by this bead; sources the shared end-to-end helper; seed-explicit;
idempotent; runs only if the decision record says proceed, otherwise logs the decision and exits 0). Steps:
`decision` (reads the three readings), `build` (`frob spark precompile --specialize <design> --backend gpu-cuda
--json`; asserts compile seconds ≤ 60), `identity` (`frob spark check --kernel <specialized> --against-generic
--states 1000000 --json`), `controls` (the three planted variants, each expecting `FROB-REF-613`), `speed` (paired
whole-step runs of the specialized and the unpadded data-driven kernels on the reference quadruped at 8,192
worlds), `switch` (a cohort switch inside a running job, digests compared with an all-generic run). Every NDJSON
line has `ts`, `script`, `bead`, `step`, `event`, the exact command line, exit code, wall time, the envelope's
`evidence` block, measured values with thresholds (mismatched states 0; compile seconds against 60; the paired
lower bound against 1.2), kernel ids, digests, and on failure the first differing state. The final `summary` line
lists assertions and `gates: ["GATE-SPARK-14", "KILL-SPECIALIZE"]`; the gate receipt is written by
`cargo test -p frob-conformance --test g5 -- GATE-SPARK-14` from the collated output.

### Known answers and negative controls
- KA-538: specialized against generic on 10⁶ states: bit-identical; negative control: a reassociated variant must be refused (`FROB-REF-613`).
- KA-549: the ceiling arithmetic (53 of 262 ns → 1.25 and 1.11; 16% → 1.19; one third → 1.5).
- CX-224 (per-design specialized kernels as the default path) and CX-164 (a kernel specialized to one design gives a large step speedup) are the shortcuts this bead's rules refuse.
- Metamorphic: specializing for a design and then running a different design through the generic kernel changes nothing for the second design; specializing twice for the same design yields the same kernel id.
- Determinism lanes: specialized kernels hold every lane the generic kernel holds (twice on one machine; across worker counts on `batch-cpu`; across backends per class), and are compared with the generic kernel in each.

## Considerations

- The whole mechanism rests on two upstream facts that can change: an exact, closed rewrite table and padding neutrality. If the derivation route is killed (KILL-KIR) and arithmetic becomes hand-written, there is no program to specialize mechanically and this bead is closed with that reason.
- A specialized kernel that is not bit-identical is not "a slightly different kernel": it would be a new kernel version that owes the fidelity battery (the Phylum invariant); this project chooses not to take that road, and refuses instead.
- The comparison arm matters: against the padded generic kernel a specialized kernel also collects the padding saving, which data alone (an unpadded data-driven kernel, or a tighter bucket) can deliver without compilation. The gate uses the unpadded arm so that it measures specialization and nothing else.
- Compile cost on a loaded host can exceed the cap by load alone; compiles run on CPU workers of the less-loaded machine and the cap is wall time there.
- OPEN-SPARK-2 (compute envelope): the gate's paired runs fit one device for one hour.
- Expected outcome, stated honestly: the ceiling arithmetic makes it more likely than not that the profile clause fires at M2 and this bead is never built.
