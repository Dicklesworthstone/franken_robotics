## Background

FrankenRobotics has an explicit owner mandate for CUDA and low-level Metal. The suite it builds on has a doctrine
that points the other way. FACT (`frankensim/docs/ACCELERATOR_DOCTRINE.md`): "FrankenSim does not ship an
accelerator backend"; it requires a "Permanent CPU reference"; it defines twelve evidence fields (AE-01 to AE-12)
for any device run; and in-process foreign kernels are forbidden in FrankenSim's production paths. The suite's
working GPU code lives outside FrankenSim's workspace in what its manifests call the engine-kit pattern, and in
FrankenTorch's `ft-kernel-metal`, which FrankenTorch calls its sanctioned unsafe boundary (FACT:
`frankentorch/crates/ft-kernel-metal/src/lib.rs`).

**ADR-SPARK-01** (DESIGN) meets the mandate without weakening the core:

- The core workspace is `unsafe_code = "deny"` with Franken-only runtime dependencies and never depends on a GPU
  crate (invariant INV-SPARK-01).
- GPU backends live in **annex workspaces** under `spark/`, each with its own lockfile and a registry of unsafe
  capsules with a `SAFETY.md` each. They build on T, the one toolchain of the build graph; the boundary exists for
  the unsafe and foreign-interface policy, not for a different compiler.
- Binaries that use a GPU are built from an `apps/` workspace that links the core and an annex.
- Every device run emits a receipt with FrankenSim's twelve evidence fields, unchanged; FrankenRobotics adds fields
  beside them and never renames or drops one (bead N21a-02 and the backend-trait bead BD-014).
- The CPU reference is permanent.

Owner ratification is open question OPEN-SPARK-1; the fail-closed default is that GPU results are labelled
exploratory until ratified. Risk carried: the GPU mandate and the suite's no-foreign-kernel doctrine are never
reconciled and work stalls on policy; the mitigation is this annex design, putting the question to the owner at
M0, and a variant of milestone M2 that exits with no GPU.

Rejected alternatives: a GPU crate inside the core (breaks the Franken-only rule, the unsafe ban and the suite
doctrine); no GPU at all (contradicts the mandate); `wgpu` as the only layer (hides launch graphs, allocators and
barriers; no doubles on Metal); a Metal binding of our own beside FrankenTorch's gateway (not built without an
owner decision; missing gateway features are upstream work in FrankenTorch's repository); wrapping an incumbent
simulator's GPU stack (an anti-goal; incumbents are oracles and parity baselines only). Tier: Solid.

## Scope

In: the directory and workspace layout for the annexes and `apps/`; lockfile and toolchain rules; the capsule
registry format and `SAFETY.md` template; the planted violations that prove the checks bite; documentation in
`AGENTS.md` and the admission file.
Out: the implementation of `xtask check-layers`, `check-deps` and `check-unsafe` themselves (BD-003, BD-004); the
v0 backends that populate the annexes (BD-015 CUDA, BD-016 Metal) and the derivation annex (BD-019); receipts
(BD-014, N21a-02); the ratification decision (the OPEN-SPARK-1 bead).

## Technical approach

**Layout (DESIGN).**

```text
Cargo.toml                 core workspace: crates/*, surface/frob-mcp, xtask      unsafe_code = "deny"
spark/frob-spark-cuda/     annex workspace, own Cargo.toml + Cargo.lock; depends on core crates by path, on cudarc
spark/frob-spark-metal/    annex workspace, own lockfile; depends on core crates by path, on ft-kernel-metal by path
derive/frob-derive/        annex workspace (build-time derivation; FrankenSymPy by path)
apps/frob-cuda/            binary workspace member: links frob-cli (core) + frob-spark-cuda
apps/frob-metal/           binary workspace member: links frob-cli (core) + frob-spark-metal
registries/capsules.toml   one row per unsafe capsule in any annex
```

Rules, each enforced by an existing check (no seventh `xtask` subcommand is added; the workspace caps `xtask` at
six):
1. **Core never depends on an annex or a GPU crate** (INV-SPARK-01; layer rule L-3). Enforced by `check-deps` and
   `check-layers` over `cargo metadata` of the core workspace: none of `cudarc`, `metal`, `objc2-metal`,
   `ft-kernel-metal`, `wgpu`, or any crate under `spark/` or `apps/` may appear in the core's resolved graph.
2. **Backends implement core traits.** An annex depends on the core (downward edge only); the core reaches a
   backend only through the `KernelBackend` trait it defines.
3. **One toolchain.** Each annex has no `rust-toolchain.toml` of its own; it inherits T from the repository root.
   The Metal annex repeats FrankenTorch's `block` patch at its own root (a `[patch]` entry is not inherited across
   workspaces).
4. **Lockfiles are committed** for the core, each annex and `apps/`; `check-stack` compares them with the stack
   lock.
5. **Capsules.** Every `unsafe` block in an annex belongs to a capsule: a module of under 300 lines behind a safe
   API, registered in `registries/capsules.toml` with `name`, `path`, `lines`, `purpose`, `safety_doc`, and a
   `SAFETY.md` that states the invariants the safe API upholds, what the foreign side may do, and the tests that
   exercise the boundary. Unsafe is never used to work around a lifetime, aliasing, cancellation or
   synchronization problem. `check-unsafe` reports the count per capsule; no total is promised for the annexes.
6. **GPU-enabled binaries come from `apps/`.** `apps/frob-cuda/src/main.rs` and `apps/frob-metal/src/main.rs` are
   thin: they construct the backend and call the core's command-line entry with it registered. The core's own
   `frob` binary has `batch-cpu` only and stays fully functional (the no-GPU variant).

**Fail-closed default for OPEN-SPARK-1.** A registry flag `registries/decisions.toml: adr-spark-01 = "unratified"`
(DESIGN) is read by the backend registration code; while it is not `"ratified"`, every device result is produced
with `exploratory: true`, no Performance or Parity claim may rest on it, and milestone M2 exits in its no-GPU
variant. Flipping the flag is a recorded owner decision, never a code change by an agent.

**What is claimed, and what is not.** Compiling one kernel source for several backends is prior art (Warp for CPU
and CUDA; Genesis's compiler for CUDA, Metal and others; FACT from the source register) and is not claimed as new.
The claim Spark may make, once the three-backend agreement gate GATE-SPARK-02 has passed, is narrower: kernel
arithmetic is derived once and emitted for a CPU reference, CUDA and Metal, and the measured cross-backend
disagreement is stored per kernel.

## Acceptance criteria

- [ ] The directories and workspace manifests above exist; `cargo metadata` succeeds for the core, each annex and `apps/`.
- [ ] INV-SPARK-01: the resolved dependency graph of the core contains no GPU crate; `xtask check-deps` passes on the clean tree.
- [ ] Negative control: a fixture copy of the tree with a planted `cudarc` dependency in a core crate fails `check-deps` (and no other check); a planted core-to-annex path dependency fails `check-layers`.
- [ ] Negative control: an annex `unsafe` block outside a registered capsule fails `check-unsafe`; a capsule with no `SAFETY.md`, and one over 300 lines, each fail.
- [ ] The core `frob` binary builds and runs with no GPU crate linked; `apps/frob-cuda` builds on `trj` and `apps/frob-metal` on this Mac without a CUDA toolkit installed at build time (the driver and NVRTC load at run time).
- [ ] With `adr-spark-01 = "unratified"`, a device result's envelope carries `exploratory: true`; with a planted `"ratified"` in a test fixture the flag is absent.
- [ ] The `SAFETY.md` template and the capsule registry schema are checked in; `AGENTS.md` states the annex rule and the claim wording.

## Test plan

### Unit tests
- `core_graph_has_no_gpu_crate` (`cargo test -p xtask`): parses `cargo metadata` of the core; asserts the deny list is absent.
- `planted_gpu_edge_fails_check_deps`, `planted_annex_edge_fails_check_layers`: run the checks on fixture trees under `xtask/tests/fixtures/`; expect failure with the edge named.
- `capsule_registry_schema`: rows parse; `lines` under 300; `safety_doc` path exists.
- `unregistered_unsafe_fails`, `capsule_without_safety_md_fails`, `oversized_capsule_fails`.
- `annex_inherits_toolchain`: no annex contains a toolchain file; the Metal annex root has the `block` patch.
- `exploratory_default_is_fail_closed`: missing decisions file, unreadable file, and `unratified` all yield `exploratory: true`.

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `annex_policy`: runs `cargo xtask check-deps`,
`check-layers`, `check-unsafe` on the tree, then `frob doctor --json` from the core binary and from the `apps/`
binary on the machine at hand, asserting that the core lists `batch-cpu` only and the app lists its device
backend. Logged per line: command, exit code, wall time, the check name, the number of capsules and lines per
capsule, the backends listed, and for a failure the offending edge or file.

### Known answers and negative controls
- Negative controls are the four plants above; each must be caught by the check that owns it and by no other (the workspace gate that plants seven violations expects exactly this).
- Determinism: the checks are pure functions of the tree; identical results on Linux and macOS.

## Considerations

- OPEN-SPARK-1 blocks the M2 exit; default: exploratory label. If it is never ratified, M2 exits in the no-GPU variant: everything lands on `batch-cpu` on the 36 cores of the Mac and the CPU of `trj`, device gates are recorded `not run` with the reason, and any device result that exists is labelled exploratory.
- OPEN-SPARK-5: what Spark does if the Metal gateway admission fails or until upstream work item FD-FT-01 lands. Default: stay inside the gateway's limits; no Metal binding of our own without an owner decision.
- Supply chain: annex lockfiles and kernel-cache integrity are also covered by the supply-chain bead (BD-306).
- Path dependencies on sibling repositories bring their transitive closures; "Franken-only" describes direct edges of the core.
- The annex caps are 8 thousand lines (CUDA), 7 thousand (Metal), 14 thousand (derive); `check-contracts` reports them.
