## Background

A number that reaches an agent from a GPU must say what produced it. FACT: FrankenSim's accelerator doctrine
(`frankensim/docs/ACCELERATOR_DOCTRINE.md`) defines twelve evidence fields for any device run. In order, with the
requirement each carries:

| Field | Name | Requirement |
|---|---|---|
| AE-01 | device identity | vendor, architecture, model, stable device identifier, memory topology, capability fingerprint |
| AE-02 | driver and runtime version | exact driver, userspace runtime, backend API and enabled feature versions |
| AE-03 | compiler and backend identity | compiler, code-generation backend, flags, target features, build identity |
| AE-04 | kernel source identity | content hash of the canonical kernel source and of the generated or embedded device binary |
| AE-05 | kernel and workload identity | versioned kernel, dimensions, units, dataset, phase and denominator |
| AE-06 | CPU machine identity and measured axes | CPU topology fingerprint plus measured bandwidth and compute axes |
| AE-07 | reduction and determinism policy | fixed-order reduction topology or a versioned tolerance policy, with accumulation type and tie breaking |
| AE-08 | CPU-versus-device numerical comparison | per quantity: CPU and device values with units, uncertainty, acceptance envelope, corpus identity |
| AE-09 | permanent CPU reference | the CPU implementation and the exact comparison run are retained |
| AE-10 | cancellation, drain and finalize outcome | executor-minted proof that every admitted kernel batch observed request, drained and finalized |
| AE-11 | phase wall-time and energy attribution | end-to-end phase totals, kernel shares, transfer and synchronization costs, energy provenance, named gaps |
| AE-12 | go or no-go decision | the profile, thresholds, top-three ranking and terminal decision |

ADR-SPARK-01 (DESIGN) binds FrankenRobotics to carry all twelve **unchanged** on every device run and to add its own
fields beside them (placement per stage, fingerprint digest, determinism class, capacities); it never renames or
drops one. Invariant INV-SPARK-02 states the consequence: every device result carries AE-01 to AE-12, a placement
receipt and a fingerprint digest, verified by a schema check at the agent boundary. The receipt type and its own
`validate()` live with the backend trait (BD-014). This bead is the boundary: the verb dispatcher in `frob-verbs`
refuses to hand an agent a device result that is not fully receipted, and it stamps the **exploratory** label that
holds while ADR-SPARK-01 is unratified (open question OPEN-SPARK-1).

Why at the boundary and not only in the backend (DESIGN): results reach agents through many verbs (`sim.run`,
`spark.probe`, `spark.check`, training and evaluation verbs). A check inside one backend can be bypassed by a new
verb; a check in the one dispatcher cannot. Rejected: trusting each verb to attach evidence (the failure this
invariant exists to prevent is a naked number). Tier: Solid.

## Scope

In: the dispatcher check for device-backed results; the envelope fields that expose the receipt; the exploratory
label and its effect on the claims list; tests with planted incomplete receipts.
Out: the receipt type and backend-side validation (BD-014); the placement receipt's content (BD-178); fingerprint
currency (`FROB-REF-606` logic); the disclosure block for Performance claims (BD-216); the claim product in general
(BD-308).

## Technical approach

**Marking a result as device-backed.** A verb executor returns `ResultWithEvidence { result, evidence, receipts:
Vec<ReceiptRef> }`. Any receipt whose backend family is not `batch-cpu` makes the result device-backed. Verbs
cannot opt out: the receipt list is filled by the backend trait's `launch`, not by the verb.

**The boundary check (run once, in the dispatcher, before the envelope is serialized).** For a device-backed result:
1. Every receipt has all twelve AE fields present and non-empty (a field may hold the typed value `not-assessed`
   where the doctrine allows it, for example AE-12 outside a funding decision; it may not be absent).
2. The receipt carries a fingerprint `digest`; the fingerprint's `identity` equals the live machine's. Missing or
   changed → `FROB-REF-606` "fingerprint missing, or changed since admission" (exit code 6; first repair
   `frob spark fingerprint`; retry `after-change`).
3. From milestone M2: the receipt carries a placement receipt (requested and actual backend per stage, fallback
   count, transfer bytes, synchronization count). At M0 the field is present with the single-stage placement of the
   kernel harness.
4. A failure of 1 or 3 is our own defect, not the caller's: the dispatcher emits no result and returns an
   integrity fault in the internal family (exit code 9, "never retry blindly"), naming the missing field. The
   run's artifacts are kept for diagnosis.
5. On success the envelope's `evidence` block gains `device: { receipts: [ids], fingerprint_digest,
   determinism_attained, exploratory }`. The full record is stored in the ledger under its id; from M1 the verb
   `artifact.read` returns it, and at M0 the spark verbs accept `--emit-receipts <dir>`, which writes each full
   record as a file.

**The exploratory label.** While the decision record says ADR-SPARK-01 is unratified (the fail-closed default; also
when the record is missing or unreadable), every device-backed envelope has `exploratory: true` and the dispatcher
removes `Performance` and `Parity` from the `claims` list of the evidence block, so no such claim can rest on a
device result. The other evidence (class, tier, determinism) is unchanged. Under the no-GPU variant of milestone
M2 the label stays on any device result that exists.

**Schema.** The device block is added to `frob.envelope/1`'s evidence schema as an optional object that is
required whenever any receipt is device-backed (a conditional schema rule, tested both ways).

**Upstream posture.** FrankenSim has no home for device receipts in its evidence types (upstream work item
FD-FSIM-09, priority P3, in FrankenSim's repository under its rules). Interim posture: local types with the
doctrine's field names. Switch-over rule: replace the local types when the upstream types land, and re-run this
bead's tests.

## Acceptance criteria

- [ ] A device-backed result with a complete receipt passes; the envelope shows the device block.
- [ ] Negative controls: for each i in 1 … 12, a receipt with AE-i removed makes the dispatcher return the integrity fault naming `AE-i`, with exit code 9 and no `result` field; twelve tests, twelve catches.
- [ ] A receipt without a fingerprint digest, and one whose `identity` differs from the live machine, each yield `FROB-REF-606` with exit code 6 and the repair `frob spark fingerprint`.
- [ ] A `batch-cpu`-only result is not subject to the device check and carries no device block.
- [ ] With the decision record `unratified`, missing or unreadable: `exploratory: true` and no `Performance` or `Parity` in `claims`; with a `ratified` fixture: `exploratory` absent and the claims untouched.
- [ ] No verb can emit a device number without receipts: a test verb that returns a device-computed value with an empty receipt list is refused (integrity fault).
- [ ] The conditional schema rule is in the generated schema; `frob schema frob.envelope/1` shows the device block.

## Test plan

### Unit tests (`cargo test -p frob-verbs device_boundary`)
- `complete_receipt_passes`.
- `missing_ae_field_is_integrity_fault_{01..12}` (twelve negative controls).
- `empty_ae_field_is_integrity_fault`: AE-04 present but an empty string.
- `not_assessed_is_allowed_for_ae12_only_where_declared`.
- `missing_fingerprint_is_606`, `changed_identity_is_606`.
- `cpu_result_has_no_device_block`.
- `exploratory_defaults_true` (three cases: unratified, missing, unreadable), `ratified_clears_label`.
- `exploratory_strips_performance_and_parity_claims`.
- `naked_device_number_is_refused`: the planted verb.
- `placement_required_from_m2`: with the M2 feature on, a receipt without a placement block is an integrity fault.
- Property test (INV-SPARK-02): for random subsets of receipt fields removed, the dispatcher emits a result if and only if the subset is empty.

### End-to-end script and logging
Exercised by `scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `device_boundary`, on a machine with a device:
`frob spark check --kernel K-selftest --backend gpu-cuda|gpu-metal --json` must return an envelope whose evidence
block has the device block and whose receipt files (written with `--emit-receipts <dir>`) hold the twelve AE fields; then the same
command with the environment's fingerprint record moved aside must return `FROB-REF-606`, exit 6. Logged per line:
command, exit code, wall time, the evidence block, the list of AE fields found, the refusal code and repair, and
on failure the missing field. The step is skipped with a logged reason on a host with no device.

### Known answers and negative controls
- The twelve field-removal controls; the missing-fingerprint control; the naked-number control.
- Determinism: the check is a pure function of the envelope and the decision record.

## Considerations

- OPEN-SPARK-1 (owner ratification of ADR-SPARK-01): default exploratory label; blocks the M2 exit. This bead implements the default, not the decision.
- AE-08 (the CPU-versus-device comparison) is present on every receipt but may say "no current check"; citing such a result is refused separately (`FROB-REF-864`, and `FROB-REF-605` under a strict request). Presence and currency are different checks.
- AE-10 must be executor-minted; a caller-authored cancelled flag or a dropped handle is not drain evidence. The fault and cancellation bead (BD-175) tests that; here only presence is checked.
- Receipts can be large; the envelope carries identifiers and the digest, never the whole receipt.
- Privacy: receipts name devices and hosts; exported envelopes use the salted identifiers of the fingerprint.
