## Background

In Spark a **kernel** is three things kept together: a manifest, its arithmetic, and its sources. The manifest
holds the `KernelId` (a content hash), the kernel's class (floating, exact-integer, guarded or statistics), its
inputs and outputs with shapes and physical dimensions, the determinism class it claims, the identities it
declares (certificates attach here), whether a derivative program exists (the doctrine rule that every kernel ships
its adjoint or a recorded reason it does not), the symbol of its CPU reference, and a stage signature (read and
write footprints, aliasing rules, layout, ownership epochs, resource bounds and the numerical contract).

The library at milestone M2 has ten families. They are implemented by many beads across chapters (dynamics,
contact, sensing, learning, replay). Nothing guarantees that the union of those beads is the library the plan
describes, that names are consistent, or that every kernel has the pieces the definition of "implemented" demands
(a CPU reference path, and where a GPU path is claimed, a retained differential check against the CPU path for
the same kernels). This bead is the index that makes the library enumerable and the check that makes
incompleteness visible. It also enforces one structural rule of the library: one stable integer-key radix sort
(`K-sort`) and one count, exclusive-scan, write compaction (`K-compact`) serve every stage; no stage carries its
own sort. Tier: Solid.

## Scope

In: `registries/kernels.toml` and its loader in `frob-kernels`; the naming convention; the family table with the
carrier bead of each kernel; the completeness check; the single-sort lint; a listing reachable from the command
line.
Out: the kernels themselves (their carrier beads); the manifest type; the per-kernel CPU-versus-device check
(`spark check`).

## Technical approach

**Naming (DESIGN).** `K-<family>-<role>` in lower case with hyphens; a wildcard in the plan (`K-fk-*`) means a
small set of roles (`K-fk-level`). Exact-integer kernels are `K-x-<role>`; guarded kernels `K-g-<role>`.

**Families at M2 (the registry's initial content; `carrier` is the bead that implements the kernel).**

**Registry row (DESIGN).** `name`, `family`, `class`, `kernel_id` (filled from the manifest at build),
`math_mode`, `determinism_claimed`, `cpu_reference` (Rust symbol), `dialect_source` (path or `none`),
`generated_body` (path or `hand-written`), `derivative` (`present` | `excused: <reason>`), `carrier`,
`status` (`planned` | `cpu` | `cpu+cuda` | `cpu+cuda+metal`). The loader refuses an unknown family or class.

**Completeness check (a conformance test, run at every milestone exit).** For each row with status beyond
`planned`: (1) a manifest with that `KernelId` is registered; (2) the CPU reference symbol resolves and the kernel
runs on `batch-cpu` through the kernel harness; (3) if a device status is claimed, dialect source exists, passes
the dialect lint, and a CPU-versus-device check record exists for the device family; (4) `derivative` is present
or excused; (5) footprints, layout, resource bounds and the numerical contract are present in the manifest.
At the M2 exit every row of the table above must be at least `cpu`; a row still `planned` fails the exit check
unless a recorded kill decision removes it.

**The single-sort lint.** A static scan of all kernel sources (Rust skeletons in `frob-kernels` and dialect files)
flags, outside the five utility kernels: (a) a loop nest that swaps or scatters elements of a buffer by comparing
keys (comparison-sort shape), (b) a histogram-then-scatter pair (radix shape), (c) a running counter used as a
write index under a predicate (append-compaction shape). A flagged kernel must call `K-sort`, `K-scan` or
`K-compact` instead, or carry a reviewed waiver row in the registry (`own_sort_waiver = "<reason>"`); the default
build has zero waivers. `K-bp-sort` is the broad phase's key construction followed by a call to `K-sort`, not a
second sort.

**Surface.** `frob spark check --list --json` prints the index (name, family, class, status, check currency per
device family). The listing is paginated and says so.

## Acceptance criteria

- [ ] `registries/kernels.toml` holds every kernel of the family table with its carrier; an unknown family or class is a load-time error.
- [ ] At M2 exit: every row is at least `cpu`; the completeness check passes for every row at its claimed status.
- [ ] Negative controls: a row claiming `cpu+cuda` with no check record fails; a row with no CPU reference symbol fails; a row with neither a derivative nor an excuse fails; a registered manifest with no row fails (no kernel outside the index).
- [ ] The single-sort lint passes on the library and flags a planted bubble sort in a skeleton, a planted private radix sort, and a planted atomic-append compaction.
- [ ] `frob spark check --list --json` returns the index with one envelope, exit code 0.
- [ ] The registry is covered by the generated-artifact check where fields are derived (the `kernel_id` column).

## Test plan

### Unit tests (`cargo test -p frob-kernels library_index`)
- `index_loads_and_rejects_unknown_family`.
- `index_rows_match_registered_manifests`: bijection between rows beyond `planned` and registered manifests.
- `index_family_table_is_complete`: the set of names equals the family table (wildcards expanded to the registered roles, at least one per wildcard).
- `completeness_fails_without_cpu_reference`, `completeness_fails_without_check_record`, `completeness_fails_without_derivative_or_excuse`, `unindexed_manifest_fails` (negative controls on fixture registries).
- `single_sort_lint_flags_bubble_sort`, `single_sort_lint_flags_private_radix`, `single_sort_lint_flags_atomic_append`, `single_sort_lint_accepts_bp_sort`.
- `list_is_paginated`: a page size of 10 over the library returns a cursor.

### End-to-end script and logging
`scripts/e2e/spark_utility_kernels.sh` (owned by BD-152), step `register`, and the M2 conformance wiring (BD-223)
run `frob spark check --list --json` and assert, per row: status, class, and check currency. Logged per line:
command, exit code, wall time, evidence block, the number of rows per family and per status, and for a failure
the first incomplete row with the missing piece.

### Known answers and negative controls
- The family table is the known answer. Negative controls: the four completeness plants and the three sort plants.
- Determinism: the index and its check are pure functions of the tree; the listing is identical on Linux and macOS.

## Considerations

- The index is where a kill decision shows: if KILL-KIR fires, `generated_body` becomes `hand-written` across the library and the completeness check then requires a differential test in place of a certificate.
- The lint's shape detection is heuristic; a false negative is covered by review at each exit and by the determinism battery, a false positive by the waiver field. Zero waivers is the default and a waiver is visible in the listing.
- Later families (film friction `K-film`, the energy ledger `K-ledger-step`, the energy monitor, sampling-control kernels) add rows at their milestones; the check applies to them unchanged.
- The dialect line cap for the whole library is 20 thousand lines; the index reports the running total.
