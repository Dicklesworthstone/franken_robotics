## Background

A device kernel is only as safe as what the host believes about its buffers. One belief is easy to get wrong
without any fault: how a multi-dimensional view steps through memory. Two array libraries of the suite use
different conventions (FACT to recheck at the admission tests INT-FNP-01 and INT-FT-01: the pinned FrankenNumPy
uses **signed byte strides** and the pinned FrankenTorch **unsigned element strides**; confirmed in source at
`fnp-ndarray/src/lib.rs:258, :390` and `ft-core/src/lib.rs:397, :2460`). Neither library is wrong alone; the trap
is at the boundary.

The smallest case that breaks a naive hand-off: a 2 × 2 contiguous `f32` view has strides (8, 4) under the byte
convention and (2, 1) under the element convention. Copying (8, 4) verbatim as element strides onto a 16-element
buffer reads element 8 + 4 = 12 at index [1, 1], where element 3 belongs, and both reads are in bounds, so nothing
faults. A second case: a view with byte origin 4 and strides (8, −4) addresses elements (1, 0, 3, 2), which
unsigned strides cannot express at all.

DESIGN rule: a view crossing that boundary carries its stride unit and signedness; a view the receiver cannot
represent is **materialized** (copied into a layout the receiver can represent) with the copy charged to the
receipt, or **refused** under a zero-copy contract with `FROB-REF-617`. The typed converter at the interchange
boundary is built by the admission bead BD-036; this bead applies the rule where Spark's kernels meet tensors:
the stage signature's layout field, the binding step of the backend, and the receipt. Upstream work item FD-FNP-01
(priority P2, in the FrankenNumPy and FrankenTorch repositories under their own rules) asks for a named
conversion between the two conventions with the unrepresentable cases refused; the interim posture is our typed
converter and no bare stride tuple crossing the boundary; the switch-over rule is to replace the local converter
and re-run INT-FNP-02. Tier: Solid. Rejected alternative: normalizing every view to one convention by silent
copy (hides cost in a throughput figure whose denominator must be whole).

## Scope

In: the layout descriptor used in stage signatures; the binding-time check between a host view and a kernel
argument; the materialize-and-charge path; the zero-copy contract and `FROB-REF-617`; tests.
Out: the converter type itself and INT-FNP-01/-02 (BD-036); tensor views for learners (BD-193); the placement
receipt's own format (BD-178); the upstream change (FD-FNP-01).

## Technical approach

**Layout descriptor (DESIGN; the manifest's `layout` per argument).**

```rust
pub struct Layout {
    pub elem: ElemTy,            // f32 | u32 | f32dd | packed record of w words
    pub extents: Vec<u32>,       // logical shape
    pub stride_unit: StrideUnit, // Bytes | Elements
    pub stride_signed: bool,     // whether negative strides are representable
    pub strides: Vec<i64>,       // in `stride_unit`
    pub origin: u64,             // logical origin, in `stride_unit`, from the allocation start
    pub alloc_extent: u64,       // allocation extent, in `stride_unit`
}
```

A kernel's declared layout is what its source indexes with: Spark's kernels use unsigned element strides,
contiguous, origin at a slab-relative offset (kernels index buffer plus index; the dialect has no pointer
arithmetic beyond that).

**Binding algorithm (at step-plan construction, never in the hot path).** For host view V offered for argument A:
1. Convert V's strides to A's unit with the typed converter: byte strides divide by the element size (a remainder
   is unrepresentable); negative strides are unrepresentable when A is unsigned.
2. Check the address set: for every index in `extents`, origin + Σ indexᵢ·strideᵢ must fall inside
   [0, alloc_extent) and the resulting element order must equal A's expected order. (Checked symbolically from the
   extreme indices, not by enumeration.)
3. If V is representable as A's layout without moving data: bind zero-copy.
4. Otherwise, if the caller's contract is `zero-copy`: refuse with `FROB-REF-617` "a view cannot cross a stride
   convention without a copy, under a zero-copy contract" (exit code 6; first repair: allow the copy; retry
   `after-change`), naming both layouts.
5. Otherwise materialize: allocate at environment creation (never later) a slab in A's layout, copy V into it in
   logical index order, bind the slab, and add the copied byte count to the receipt's transfer counter with the
   reason `stride-materialization`. A per-step materialization is not allowed; a view that changes every step
   must be produced in the kernel's layout at its source.

**Receipt.** The placement receipt row of the stage shows the bytes and the count of materializations, so every
throughput figure derived from it carries the cost.

## Acceptance criteria

- [ ] The 2 × 2 case: binding a byte-stride (8, 4) view to an element-stride argument reads element 3 at index [1, 1] (the converter yields (2, 1)).
- [ ] Negative control: a build with the converter bypassed (strides copied verbatim) reads element 12 on the 16-element buffer and is caught by the test, although no bounds check fires.
- [ ] The negative-stride view (origin 4 bytes, strides (8, −4)) is materialized into (1, 0, 3, 2) order with 16 bytes charged, or refused with `FROB-REF-617` under a zero-copy contract.
- [ ] A byte stride not divisible by the element size is refused as unrepresentable (materialize or `FROB-REF-617`).
- [ ] A materialization shows in the receipt (bytes, count, reason); a zero-copy bind shows zero.
- [ ] No materialization occurs after environment creation: the allocated-bytes counter is flat across steps with a materialized view bound.
- [ ] The refusal envelope names both layouts (unit, signedness, strides, origin, extent) and the repair.

## Test plan

### Unit tests (`cargo test -p frob-kernels layout`)
- `stride_2x2_bytes_to_elements`: (8, 4) bytes, element size 4 → (2, 1); index [1, 1] → element 3 (KA-532).
- `stride_verbatim_copy_reads_12` (negative control with the bypass feature): asserts the wrong read is element 12 and that the test detects it by value, not by fault.
- `stride_negative_materializes`: byte origin 4, strides (8, −4), 2 × 2 → element order (1, 0, 3, 2); 16 bytes charged.
- `stride_negative_refused_zero_copy`: same view, contract `zero-copy` → `FROB-REF-617`.
- `stride_indivisible_is_unrepresentable`: byte strides (6, 4) on `f32`.
- `address_set_within_allocation`: a view whose last element lies outside `alloc_extent` is rejected before binding.
- `materialization_only_at_creation`: an attempt to bind a non-representable view after creation is refused.
- Property test: for random shapes up to rank 4 and random admissible strides in either convention, the element addressed at every index through the bound layout equals the element addressed through the original view.

### End-to-end script and logging
Exercised through the placement gate's end-to-end script (`scripts/e2e/spark_gate09_placement.sh`, whose steps
BD-178 lists), step `stride_handoff`: a synthetic job feeds a byte-strided host array to a device kernel under `mixed-allowed`,
then repeats with `--zero-copy`. Asserts: first run completes and the receipt row shows the materialized bytes;
second run exits 6 with `FROB-REF-617`. Logged per line: command, exit code, wall time, evidence block, transfer
bytes, the refusal code and repair, both layouts.

### Known answers and negative controls
- KA-532: index [1, 1] reads element 3; negative control: a verbatim stride copy reads element 12, in bounds.
- CX-218: strides cannot be copied verbatim between array libraries.
- Metamorphic: converting bytes → elements → bytes returns the original strides for every representable view.
- Determinism: binding is a pure function of the two layouts (class D0).

## Considerations

- The wrong read is in bounds, so no sanitizer or bounds check will ever report it; only a value test does. This is why the negative control asserts on the value 12.
- Until FD-FNP-01 lands, any sibling-library update can change a convention; the admission tests are re-run on every pin move, and this bead's tests run in the same train.
- A materialization charged at creation is amortized over a run, but it still belongs in cold-start figures.
- Metal buffers bind at offset zero today (a gateway limit), so slab-relative origins are carried in the layout and applied by the kernel's offset table, not by the binding.
