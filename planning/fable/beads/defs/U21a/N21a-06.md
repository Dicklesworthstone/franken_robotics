## Background

Every kernel manifest in Spark carries a **stage signature**: per buffer, the read footprint and the write
footprint as index ranges in terms of shape-class capacities, the aliasing rules (which arguments may be the same
slab; none by default), layout, ownership epochs, resource bounds and the numerical contract. The host trusts
these declarations when it decides which slabs a launch may touch, when it leases a slab to a reader, when it
orders launches, and when it claims that worlds are independent.

A declaration can be wrong. FACT: the Metal gateway Spark uses (`ft-kernel-metal`) checks read and write
declarations for aliases against **each other**; it does not check them against the kernel source. So if a kernel
writes one element past what it declared, nothing in the suite notices. Proof obligation **PO-SPARK-04** therefore
falls to this project: declared read and write footprints contain the IR's load and store sets. Its verification
has two halves: footprints are *derived* for generated bodies, and a *lint* covers hand-written skeletons.

The same machinery discharges the static half of invariant **INV-SPARK-04**: no kernel reads or writes another
world's rows, except statistics (`stat`) kernels, whose outputs never feed state. That invariant is the first of
the design conditions behind the project's strongest determinism property (a world's trajectory does not depend on
the batch it ran in). Its dynamic half is a gate measured elsewhere; a static check finds the defect before any
run. Tier: Solid. Rejected alternative: trusting hand-written declarations with review only (the failure is
silent, in bounds and data-dependent).

## Scope

In: footprint derivation from IR load and store operations; the skeleton footprint lint for Rust and dialect
skeletons; the containment check at manifest registration; the world-isolation check; a dynamic cross-check on
`batch-cpu` with guard regions; planted violations.
Out: the manifest type and the declaration-versus-declaration alias check (the manifest bead); the run-time
batch-composition gate (BD-181); the rule that `stat` outputs never feed state (N21a-22).

## Technical approach

**Footprint language (DESIGN).** A footprint is a set of affine index ranges over a slab:
`{ slab, world: Own | All, lanes: [lo, hi) with lo, hi affine in capacities and literals, fields: set }`.
`world: Own` means the access is to the row of the world the lane belongs to; `All` is allowed only in a manifest
whose class is `stat`.

**Half 1: derived footprints for generated bodies.** In the IR, memory is touched only by
`load(slot, lane, offset)` and `store(slot, lane, offset, v)`, where `offset` is a literal and `lane` is the loop
index or an affine expression of loop indices with literal coefficients (loops have literal or capacity bounds).
1. Walk the program; for each load or store collect (slot, lane expression, offset) with the enclosing loop
   bounds.
2. Evaluate the lane expression's range by interval arithmetic over the loop bounds (exact for affine
   expressions).
3. The union per slot is the derived read set or write set, emitted into the manifest as the footprint. A generated
   body thus has no hand-written footprint at all, and containment holds by construction; the check still runs to
   catch an emitter defect.

**Half 2: the skeleton lint.** Skeletons index buffers as `buf[base + i]` (dialect rule: no pointer arithmetic
beyond buffer plus index; loop bounds literal or capacity constants; unsigned 32-bit indices).
1. Parse each skeleton into its loop nests and buffer accesses (the dialect's restricted grammar makes this
   tractable; the Rust skeletons are held to the same shapes: indexed slices, `for` loops over literal or capacity
   ranges, no iterator adaptors that hide indices in kernel bodies).
2. For each access derive an index interval from loop bounds and the base (a world's row base is the named
   constant `ROW(world, capacity)`); an index expression the lint cannot bound (data-dependent gather) must be
   declared with an explicit clamp `FROB_CLAMP_INDEX(i, lo, hi)`, whose range the lint then uses.
3. Compare with the declared footprint: every derived interval must lie inside a declared range of the same
   access kind. A violation is a build-time failure of the kernel's registration, naming buffer, declared range and
   derived range. The refusal code is the banned-construct build error `FROB-REF-251` (exit code 3; repair: widen
   the declaration or fix the index; retry `after-change`).
4. World isolation: any access whose row base is not the current world's (`ROW(w′, …)` with w′ ≠ the lane's
   world, or an index range that crosses a row boundary) fails unless the manifest class is `stat`.

**Dynamic cross-check on `batch-cpu` (debug harness).** The kernel harness can allocate each slab with guard
regions and a shadow bitmap; it runs the kernel on seeded inputs at two capacities and records the set of touched
addresses, then asserts touched ⊆ declared for reads and writes separately. This catches what a static bound
over-approximated or a lint missed, and it is the oracle for the lint's own tests.

**Resource interaction.** The derived footprints also give the buffer argument count per kernel, which the
resource-metadata bead (N21a-18) checks against backend limits (31 buffer arguments on a Metal compute function).

## Acceptance criteria

- [ ] Generated bodies carry derived footprints; no generated kernel has a hand-written footprint.
- [ ] Every hand-written skeleton in the library (Rust and dialect) passes the footprint lint, and its declared footprints contain the touched sets observed by the dynamic cross-check at two capacities.
- [ ] Negative controls, each caught statically: a skeleton that writes `out[ROW(w, C) + C]` (one past its row); one that reads the next world's first element; one whose loop bound is `C + 1`; a gather without `FROB_CLAMP_INDEX`.
- [ ] Negative control caught dynamically: a data-dependent gather whose clamp range is wider than declared.
- [ ] World isolation: a non-`stat` kernel with a cross-world access fails registration; the same access in a `stat` manifest passes.
- [ ] The property test for PO-SPARK-04 passes on 10⁴ random IR programs: derived footprint ⊇ touched set from the reference interpreter.
- [ ] The failure message names the kernel, the buffer, the declared range and the derived range.

## Test plan

### Unit tests (`cargo test -p frob-kir footprint`, `cargo test -p frob-kernels footprint_lint`)
- `derive_footprint_straight_line`: loads at offsets {0, 1, 2} of slot A lane i, store at offset 0 of slot B → read A[i][0..3), write B[i][0..1).
- `derive_footprint_loop`: `for j in 0..N { load(A, j, 0) }` → read A[0..N).
- `derive_footprint_affine_lane`: lane 2·j + 1 for j in 0..4 → [1, 8).
- `lint_accepts_reference_skeletons`: all checked-in skeletons.
- `lint_rejects_off_by_one_write`, `lint_rejects_cross_world_read`, `lint_rejects_loop_bound_plus_one`, `lint_rejects_unclamped_gather` (negative controls).
- `lint_allows_cross_world_for_stat_only`.
- `dynamic_touched_subset_declared`: guard-region harness on `K-compact`, `K-sort`, `K-reduce` at capacities C and 2C.
- `dynamic_catches_wide_clamp` (negative control).
- Property test (PO-SPARK-04): random programs with loads, stores and bounded loops; interpreter-touched ⊆ derived.
- Property test (INV-SPARK-04, static): random non-`stat` programs never produce a derived footprint with `world: All`.

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `footprints`: runs the lint over the library through
`cargo test -p frob-kernels footprint_lint`, then over a directory of planted bad skeletons expecting one failure
each, then the dynamic cross-check through `frob spark check --kernel <name> --backend batch-cpu
--footprint-audit --json`. Logged per line: command, exit code, wall time, kernel name, buffer, declared and
derived ranges, the count of kernels audited, and on failure the first address outside the declaration.

### Known answers and negative controls
- Known answers: the three derivation fixtures above.
- Negative controls: the five planted violations.
- Determinism: lint and derivation are pure functions of the source (class D0); the dynamic audit is run twice with identical touched sets.

## Considerations

- Interval bounds over-approximate data-dependent gathers; the clamp macro makes the over-approximation explicit and costs one select per gather. The M2 profile will show whether any clamp is hot.
- The lint depends on skeletons staying inside the restricted shapes; a skeleton that needs more (for example a thread-group parallel scan) is audited by the dynamic check and carries a reviewed annotation of its footprint proof.
- The device backends cannot run guard-region audits cheaply; the audit is a `batch-cpu` property, and equality of device and CPU outputs under the CPU-versus-device check carries it across.
- Ownership epochs (which committed slab a kernel reads and which it writes) are declared in the same signature; their enforcement is the lease mechanism of the arena bead (BD-173).
