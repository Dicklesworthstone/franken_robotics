## Background

In Spark the mathematical body of a kernel (a Cayley step, an adjoint transport, a cone projection, a Jacobian row)
is **derived once**: produced at build time by the annex `derive/frob-derive` using FrankenSymPy (the suite's
symbolic algebra system), lowered to a program in the kernel IR `frob-kir`, and emitted as Rust and as text in the
shared GPU dialect, together with its derivative programs and its certificates (construction C-14). The M0 spike
(BD-019) derives two kernels. At M2 the library has dozens of derived bodies, and three properties of the pipeline
must hold at that scale or the whole route fails its kill gate:

1. **Generated source is checked in with its digest; CI regenerates and compares; generated code is never edited
   by hand** (invariant INV-SPARK-08, enforced by `xtask check-generated`). Without it the Rust and the dialect
   can drift apart silently, and a hand edit would break the certificate bound to the program hash.
2. **Derivation is per kernel body, never per whole robot.** This keeps expressions small. FACT (source
   register): a published attempt to expand a humanoid mass matrix symbolically ran for over an hour and crashed.
   Risk RISK-07: FrankenSymPy budgets block derivations or certificates by expression swell on a 29-joint
   humanoid; mitigation: derive per kernel body and per limb. FACT: FrankenSymPy's bytecode interpreter caps an
   expression at 8,192 operations.
3. **A hang is contained.** If FrankenSymPy hangs on a derivation it runs in an isolated worker with a time and
   memory cap; a derivation that exceeds its cap is a reported failure of that kernel, not a stuck build.

Each kernel also records its register and stack pressure, its rewrite fuel and its expression size, and
derivation is capped on all of them. Tier: Frontier (the derivation route is under kill gate KILL-KIR; this bead
is part of what BD-221 measures). Rejected alternatives: deriving at run time (puts a symbolic engine in the
product path); generating without checking in (no reviewable diff, no offline build); one derivation per robot
(expression swell).

## Scope

In: the derivation manifest (`derive/kernels.toml`); the worker process with caps; budgets and their refusals; the
generated-file header and digest scheme; the regeneration procedure used by `check-generated`; the report of
sizes and times per kernel body.
Out: the derivations' mathematics (the kernel beads); the IR and emitters (BD-018, N21a-16 to N21a-21);
certificates' content (the certificate beads); the measurement against KILL-KIR (BD-221).

## Technical approach

**Derivation manifest (DESIGN).** One row per kernel body: `name`, `source` (the derivation script module),
`inputs` with dimensions, `outputs`, `budget = { nodes, wall_seconds, memory_bytes, rewrite_fuel }`,
`derivative = forward | transposed | both | excused(<reason>)`, `certificates = [claim ids]`. Defaults (DESIGN,
TARGET): 8,192 symbolic operations per expression (the engine's own cap), 60 s of wall time, 4 GiB of memory,
rewrite fuel 10⁵ rule applications; a row may lower them, and raising them needs a recorded reason.

**Worker isolation.**
1. `frob-derive` runs each row in a child process (`frob-derive-worker`), started with the row's caps: a wall-clock
   deadline enforced by the parent (kill on expiry), an address-space or resident-memory limit set before `exec`,
   no network, a scratch directory removed afterwards.
2. The child writes its result (IR bytes, certificate inputs, statistics) to a pipe; the parent validates the IR
   (type check, dimension check), computes hashes and writes files. A child that dies, times out or exceeds memory
   yields a typed build failure for that kernel naming the cap and the observed value; other kernels proceed.
3. Derivation is deterministic: the child sets a fixed seed for any randomized simplification and sorts every
   unordered collection before emission; two runs produce byte-identical IR. This is tested, not assumed.
4. The derivation annex is build-time only. Nothing in the core workspace depends on it; the core consumes the
   checked-in generated files.

**Generated files.** For kernel `<k>`: `crates/frob-kernels/src/generated/<k>_body.rs`,
`crates/frob-kernels/dialect/generated/<k>_body.h`, `crates/frob-kernels/generated/<k>.kir` (canonical IR bytes),
and for derivatives the same with `_jvp` and `_vjp` suffixes. Each text file starts with a header: generator
version, IR content hash (BLAKE3), FrankenSymPy pin, the manifest row's digest, and the line
`GENERATED: do not edit`. `crates/frob-kernels/generated/DIGESTS.toml` lists every file with its BLAKE3 digest.

**Regenerate and compare (the `check-generated` contract for kernels).**
1. Run every manifest row in a temporary tree.
2. Compare each produced file byte for byte with the checked-in file, and each digest with `DIGESTS.toml`.
3. Any difference fails, naming the file and the first differing line. A file present in the tree with the
   generated header but absent from the manifest also fails (an orphan).
4. A hand edit is therefore caught two ways: the digest no longer matches, and regeneration differs.

**Statistics report.** Per kernel body: symbolic operation count, IR node count before and after
common-subexpression elimination, live-value and stack bounds, wall time, peak memory, rewrite fuel used. Written
to `target/derive/report.json` and summarized by `frob-derive --report`. This is the input to the M2 measurement
of the expressible share (BD-221) and to the early warning for RISK-07.

**Failure codes.** Budget excess and worker death are build failures of the derivation annex (not agent-facing
refusals); they are reported with the kernel name and are entered in the library index as
`generated_body = "failed: <cap>"`, which the completeness check treats as missing.

## Acceptance criteria

- [ ] Every derived kernel body in the M2 library has a manifest row, generated Rust, dialect and IR files with headers, and a `DIGESTS.toml` entry.
- [ ] `xtask check-generated` regenerates all bodies and passes on a clean tree; the run fits the default compute envelope (16 GiB, 8 cores, one hour).
- [ ] Negative controls: a one-character hand edit of a generated Rust file fails `check-generated` naming the file; an edited digest fails; an orphan generated file fails; a manifest row whose output dimension is wrong fails with the dimension error before any file is written.
- [ ] Determinism: two regenerations on the same machine and one on the other platform produce byte-identical files (INV-SPARK-08's premise).
- [ ] Containment: a planted derivation that loops forever is killed at its deadline and reported with the cap `wall_seconds`; one that allocates without bound is stopped at the memory cap; in both cases the build continues with the other kernels and exits non-zero at the end.
- [ ] A derivation above 8,192 symbolic operations is refused with the node budget named, and the report shows which sub-expression grew.
- [ ] The statistics report exists and lists every body.

## Test plan

### Unit tests (`cargo test` in `derive/frob-derive`)
- `manifest_row_roundtrip` and `manifest_rejects_unknown_field`.
- `worker_timeout_is_reported`: a test derivation that sleeps beyond a 2 s cap → failure naming `wall_seconds` and the observed time; no orphan process remains.
- `worker_memory_cap_is_reported`: a derivation that builds an exponentially growing expression under a 256 MiB cap.
- `worker_crash_is_contained`: a derivation that aborts.
- `regeneration_is_deterministic`: run twice, compare bytes.
- `header_fields_present`: generator version, IR hash, pin, manifest digest, the do-not-edit line.
- `digest_mismatch_fails`, `hand_edit_fails`, `orphan_file_fails` (negative controls on a fixture tree).
- `node_budget_refusal_names_subexpression`.
- `per_body_not_per_robot`: the manifest loader rejects a row whose inputs are a whole-robot state larger than a declared per-body bound (a guard against a mass-matrix-of-the-robot derivation).

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), steps `regenerate` and `derive_containment`: runs
`cargo xtask check-generated`, then the three containment fixtures through `frob-derive --manifest
tests/fixtures/bad.toml`. Asserts exit codes and that the report names each failed kernel and cap. Logged per
line: command, exit code, wall time, per-kernel node counts and times, the digests compared, and on failure the
file and first differing line.

### Known answers and negative controls
- Known answer: regenerating `K-cay-step` reproduces the checked-in sources bit for bit (the M0 condition, kept as a regression).
- Negative controls: hand edit, digest edit, orphan, infinite loop, unbounded allocation, oversized expression.
- Determinism lanes: twice on one machine; Linux and macOS.

## Considerations

- KILL-KIR (decided at M2): if the toolchain cannot express or emit more than 20% of kernel arithmetic, or emitted kernels miss the speed bound of bet BET-01 (more than 1.3 times slower than hand-tuned equivalents after one optimization pass), arithmetic is hand-written and bound by differential tests. This bead's manifest then records `hand-written` rows and the regeneration check covers only what stays generated.
- Upstream work item FD-FSYM-01 (multi-output straight-line code generation with common-subexpression elimination in FrankenSymPy, and lifting the 8,192-operation cap; priority P2) would move part of this upstream; interim posture: `frob-kir` owns code generation; switch-over: regenerate and compare digests.
- A FrankenSymPy pin change regenerates everything; the comparison then shows exactly which kernels changed arithmetic, and those kernels' CPU-versus-device checks go stale.
- Derivation machines: the plan assigns derivation, certificates and symbolic work to the Mac; `trj` builds from checked-in files and needs no symbolic engine.
