## Background

Spark has three arithmetic classes for kernels. Floating kernels (`f32`) carry the physics. **Exact-integer**
kernels carry everything that must be the same bytes on every backend: strict predicates, digests, counts and
scans, sort keys, histogram bins, random streams and phase accumulators. Guarded kernels combine an `f32` residual
with an exact-integer fallback. Exact kernels are determinism class D0 (exact) on CPU, CUDA and Metal, because
unsigned 32-bit wrapping arithmetic has one meaning everywhere.

That only holds if the integer operations are chosen so that no undefined or implementation-defined behaviour is
reachable. In both source languages (CUDA C++ and Metal Shading Language) signed overflow is undefined and a shift
by 32 or more is undefined. The dialect rule (rule 7) is therefore: integer arithmetic in exact kernels is
unsigned and 32 bits wide; shift counts are masked; 64-bit integers and atomics are used only where the hardware
fingerprint records them for every device family in use; a count that can pass 2³² uses two limbs.

Version 0 of the kernel IR `frob-kir` (bead BD-018) has floats only; the M0 exact probe kernels (BD-030) are
hand-written. This bead adds the integer operators and the `ExactInteger` math mode to the IR, so that exact
kernels and the exact fallbacks of guarded predicates (BD-053, which depends on this bead) are generated,
type-checked and emitted like everything else. The crate map assigns "the exact-integer kernel class" to
`frob-kir`. Tier: Solid. Rejected alternatives: signed integers (undefined overflow); 64-bit integers as the
default width (no 64-bit atomics on Metal, FACT to recheck by the fingerprint; and OPEN-MARROW-3's default is
32-bit limbs everywhere so the three backends run the same integer program); leaving exact kernels hand-written
(three copies to keep identical by hand).

## Scope

In: the type `u32` and its operators; `bool` logic; integer comparisons; bit views between `f32` and `u32`; the
exact conversion `u32` → `f32` for values below 2²⁴; the `ExactInteger` math mode and its rules; emitters;
multi-limb helper subprograms.
Out: predicate classes, guards and bit budgets (BD-053); the digest mix (N21a-23); the sort, scan and reduce
kernels that use these operators (N21a-07 to N21a-09); Philox itself (BD-180); 64-bit operations (not provided;
a kernel that declares them is refused on a device that lacks them with `FROB-REF-616`, raised by the planner).

## Technical approach

**Operators (the IR's integer row).** `and or xor shl shr addw mulw mulhi` on `u32`, wrapping, shift counts
masked. Defined precisely:

| Operator | Result |
|---|---|
| `addw(a, b)` | (a + b) mod 2³² |
| `subw(a, b)` | (a − b) mod 2³² (written `addw(a, addw(not(b), 1))`; provided as an operator for clarity) |
| `mulw(a, b)` | (a·b) mod 2³² (the low word) |
| `mulhi(a, b)` | ⌊a·b / 2³²⌋ (the high word of the 64-bit product) |
| `and`, `or`, `xor`, `not` | bitwise |
| `shl(a, n)`, `shr(a, n)` | a ≪ (n mod 32), a ≫ (n mod 32) (logical) |
| `cmp_u(op, a, b)` | unsigned comparison → `bool`; op in lt, le, eq, ne, ge, gt |
| `select(p, a, b)` | on `u32` and `bool` as on floats |
| `bits(x: f32) → u32`, `float_from_bits(u: u32) → f32` | reinterpretation, no arithmetic |
| `u24_to_f32(u)` | exact conversion; defined only when the value is provably below 2²⁴ (a static range check), otherwise a build error |

`mulhi` is what makes multi-limb arithmetic possible without a 64-bit type; it exists identically on the CPU, on
CUDA (`__umulhi`) and on Metal (`mulhi`), each wrapped by a prelude macro `FROB_MULHI_U32`.

**The `ExactInteger` math mode.** A program declares `math_mode = ExactInteger`. In that mode: no `f32` or `f64`
arithmetic node may appear (bit views and `u24_to_f32` at outputs are allowed, so an exact kernel can read float
bit patterns and emit an exact uniform); every value is `u32` or `bool`; the determinism class claimed is D0; the
emitted dialect unit carries the directive that makes the dialect lint apply rule 7. A program in mode
`Ieee754Safe` may contain integer nodes (an index computation, a mask), but its class is then decided by its
floating part.

**Emission.** Rust: `wrapping_add`, `wrapping_mul`, `((a as u64 * b as u64) >> 32) as u32`, `<<`/`>>` with
`& 31` on the count, `to_bits`/`from_bits`. Dialect: `u32` arithmetic (unsigned arithmetic wraps by definition in
both languages), `FROB_MULHI_U32`, `FROB_SHL`/`FROB_SHR` (the prelude's masked shifts), bit views through the
prelude's `FROB_BITS_F32`/`FROB_F32_FROM_BITS` (CUDA: a `memcpy`-free intrinsic view; Metal: `as_type<uint>`).
One operation per statement, as for floats.

**Multi-limb subprograms (used by guarded fallbacks and wide sums).**
- `add2((lo, hi), (lo′, hi′))` = ((lo + lo′) mod 2³², hi + hi′ + carry), carry = 1 if (lo + lo′) mod 2³² < lo.
- `mul32x32(a, b)` = (mulw(a, b), mulhi(a, b)).
- `addn`, `subn`, `muln` for n limbs (n a literal up to 8, that is 256 bits), by schoolbook carries; `sign_n` for
  a two's-complement n-limb value; `cmp_n`.
A predicate fallback whose bit budget exceeds 256 bits is refused at build time (`FROB-REF-215`, raised by
BD-053).

**Exact uniform conversion (a law carried here).** For any `u32` x, u = `u24_to_f32(shr(x, 8))·2⁻²⁴` is exact and
lies in [0, 1): x ≫ 8 is below 2²⁴, every such integer is representable in `f32`, and multiplying by a power of
two is exact. This is how a random draw stays class D0 up to and including its conversion to a uniform float.

**Dimension typing.** Integers and booleans carry no physical dimension; `u24_to_f32` yields a dimensionless
float; `float_from_bits` yields a float whose dimension is declared at the call site and recorded.

## Acceptance criteria

- [ ] All operators exist in the IR, the reference interpreter, the Rust emitter and the dialect emitter; emitted dialect passes the lint under rule 7.
- [ ] Edge semantics: `addw(0xFFFFFFFF, 1)` = 0; `mulw(0x10000, 0x10000)` = 0; `mulhi(0xFFFFFFFF, 0xFFFFFFFF)` = 0xFFFFFFFE; `shl(1, 32)` = 1 and `shl(1, 33)` = 2 (masked counts); `shr(0x80000000, 31)` = 1.
- [ ] An `ExactInteger` program containing a float arithmetic node is rejected at build time; a program in that mode claims class D0 in its metadata.
- [ ] `u24_to_f32` is rejected when the static range of its argument is not provably below 2²⁴.
- [ ] The uniform-conversion law holds exhaustively for all 2²⁴ values of x ≫ 8 and on 10⁸ random x: the result equals the exact rational (x ≫ 8)/2²⁴ and is below 1.
- [ ] Multi-limb helpers match arbitrary-precision arithmetic on 10⁶ random operands for 2, 4 and 8 limbs.
- [ ] Emitted exact programs return identical bytes on `batch-cpu`, CUDA and Metal on 10⁶ seeded inputs (through BD-030's harness and `spark probe`).
- [ ] Negative control: an emitter variant that writes an unmasked shift is caught by the `shl(1, 32)` case in the reference comparison and by the dialect lint.

## Test plan

### Unit tests (`cargo test -p frob-kir exact`)
- `addw_mulw_mulhi_edges`: the values in the acceptance list, plus `mulhi(0x80000000, 2)` = 1.
- `shift_counts_are_masked`: counts 0, 31, 32, 33, 63, 64.
- `bit_views_roundtrip`: `float_from_bits(bits(x))` has the same bits for −0.0, a NaN with payload, a subnormal.
- `u24_to_f32_exact_all`: exhaustive over 0 … 2²⁴ − 1; `u24_to_f32_rejects_unbounded` (build error).
- `uniform_conversion_law`: (x ≫ 8)·2⁻²⁴ ∈ [0, 1), exact; largest value (2²⁴ − 1)/2²⁴ = 1 − 2⁻²⁴.
- `exact_mode_rejects_float_node` (negative control).
- `add2_carry`: (0xFFFFFFFF, 0) + (1, 0) = (0, 1).
- `mul32x32_matches_u64`: 10⁶ random pairs.
- `limbs_match_bigint`: n ∈ {2, 4, 8}; add, sub, mul, sign, compare.
- `strict_predicate_2p24`: the comparison 16,777,216 < 16,777,217 written with `cmp_u` is true (KA-529 in the IR's own operators).
- `emit_rust_equals_interpreter` and `emit_dialect_lint_clean` on 10⁴ random integer programs.
- `unmasked_shift_emitter_mutant_is_caught` (negative control).

### End-to-end script and logging
`scripts/e2e/spark_probe.sh` (bead N21b-40), step `exact_ops`: a generated probe kernel applying every
operator to a seeded slab is run with `frob spark probe --suite exact-ops --device
batch-cpu|gpu-cuda:0|gpu-cuda:1|gpu-metal --json`; asserts the four output digests are equal. Logged per line:
command, exit code, wall time, evidence block (determinism `exact`), operator count, digests, and on failure the
first lane and operator where two backends differ with both words.

### Known answers and negative controls
- KA-529 (2²⁴ < 2²⁴ + 1 is true in exact arithmetic); the two-limb answer (0xFFFFFFFF, 0) + (1, 0) = (0, 1); `mulhi(0xFFFFFFFF, 0xFFFFFFFF)` = 0xFFFFFFFE; the uniform maximum 1 − 2⁻²⁴.
- Negative controls: float node in exact mode; unmasked shift; an unbounded `u24_to_f32`.
- Metamorphic: `addw` and `mulw` are commutative and associative bit for bit; `xor` with a constant twice is the identity.
- Determinism lanes: byte equality twice on one machine, debug and release, across platforms and across the three backends (class D0).

## Considerations

- OPEN-MARROW-3: whether exact fallbacks may use 64-bit integers where a backend offers them. Default: 32-bit limbs everywhere. Owner: Marrow lead. A 64-bit variant would be a second emitted form selected per device by the fingerprint, with byte equality against the limb form as its test.
- A device that lacks a declared arithmetic feature refuses the kernel with `FROB-REF-616` (first repair: the 32-bit variant, or another backend); with this bead's default no kernel declares one.
- Integer division and remainder are deliberately absent (slow, and their GPU semantics for edge cases differ); where needed they are written as multiplication by a precomputed reciprocal with `mulhi`, or done on the host.
- Placement lesson recorded with the class: a small integer job whose inputs live on the host is faster on the host than on any device (about 34 µs against about 290 µs on Metal and over 1.2 ms on one RTX 4090 in the recorded pilot); the class makes results identical wherever they run, so placement is free to follow the data.
