## Background

The kernel intermediate representation of Spark (`frob-kir`: typed single assignment with bounded loops, from
which kernel arithmetic is emitted as Rust and as GPU dialect text) merges two requirements: every value carries a
physical dimension, and every program carries the resource facts a backend needs **before it compiles anything**.
The plan states it as a rule: resource metadata is a proof obligation, not a comment (**PO-SPARK-03**: resource
bounds in the manifest (live values, stack bytes, loop bounds, argument count) hold and fit each backend's limits;
computed by the IR, checked by the emitter). The emitter refuses a program whose bounds exceed a backend limit,
for example the 31 buffer arguments of a Metal compute function.

Why it matters. A kernel that needs more registers than a device thread has spills to memory and loses most of
its speed without any error. A kernel with more buffer arguments than Metal's gateway accepts fails only at
pipeline creation on the Mac, after it has passed every test on CUDA. A kernel whose thread-group memory exceeds
the device limit fails at launch. Each is knowable from the program. FACT: the Metal gateway accepts at most 31
buffer arguments per kernel (`MAX_ARGUMENTS` in `ft-kernel-metal`), binds buffers at offset zero, and reports
`max_threadgroup_memory`; the suite's own renderer refuses a block needing more than 48 KiB of shared memory.
The derivation doctrine also says each kernel records its register and stack pressure, its rewrite fuel and its
expression size, and derivation is capped on all of them. Tier: Frontier with the rest of the IR (kill gate
KILL-KIR); the checks themselves are ordinary static analysis. Rejected alternative: discovering limits by
compiling on each backend (late, device-specific, and impossible on a host without that device).

## Scope

In: computation of each metadata field; live-range scheduling to cap register pressure; the backend limit table;
the emitter's refusal; the manifest fields; tests with programs built to sit exactly at and just over each limit.
Out: footprints (N21a-06); operation-count use by the performance profile (N21a-27); the Metal packing of many
arrays into few slabs with an offset table (the Metal backend bead), which is how real kernels stay under 31.

## Technical approach

**Metadata fields (all computed, none hand-written).**

| Field | Definition | How computed |
|---|---|---|
| `op_counts` | Number of executions of each operator type per kernel invocation | Sum over nodes, multiplied through enclosing loop bounds (bounds are literals or capacities; capacities are kept symbolic and evaluated per shape class) |
| `loop_bounds` | Every loop's bound, literal or capacity name, and nesting depth | Read from the program |
| `max_regs` | The maximum number of scalar values simultaneously live at any program point, after scheduling | Liveness analysis on the scalar-lowered program: a value is live from its definition to its last use; loop-carried values are live across the whole loop; the maximum over program points of the live-set size |
| `max_stack_bytes` | Bytes of local array storage a thread needs (scratch arrays, unrolled composite temporaries the backend cannot keep in registers) | Sum of declared local arrays plus max(0, `max_regs` − register budget of the target) × 4 |
| `buffer_args` | Number of distinct buffer slots the kernel binds | Count of slots in the header |
| `group_shared_bytes` | Thread-group shared memory the skeleton declares | Sum of `FROB_GROUP_SHARED` declarations at the shape class's capacities |
| `expr_nodes`, `rewrite_fuel_used` | Size before and after rewriting; rule applications consumed | From the build |

**Scheduling by live range (the one transformation here).** Independent operations may be reordered to shorten
live ranges and lower `max_regs`. Rules: only operations with no data dependence between them are reordered (two
operations that touch one buffer with at least one store count as dependent); no operation's operands change;
evaluation order of dependent operations is untouched; so the result is bit-identical (a class-E rewrite: it
changes no bit under round-to-nearest with contraction off). Algorithm (DESIGN): a greedy topological order that,
among ready nodes, prefers the one that kills the most live values and, on ties, the lowest original index
(deterministic). The schedule is part of the canonical program, so the hash covers it. The reordering is
recorded in the program's rule trace `frob.kir.trace/1` (N21a-19's format) as `schedule` steps: the sequence of
exchanges of two adjacent independent operations of one block that turns the definition order into the schedule
(any dependence-respecting order decomposes so, since a dependent pair never changes its relative order). Replaying
the trace from the unscheduled program then reproduces the scheduled program's hash, so the independent checker
N12p2-02 can certify a scheduled kernel; without these steps its target fails `rewrite.target-hash`.

**Backend limit table (DESIGN; values are data, read from the admission records and the fingerprint, not
constants in code).**

| Limit | CUDA | Metal (through the gateway) |
|---|---|---|
| Buffer arguments per kernel | no practical limit recorded | 31 (FACT) |
| Thread-group shared memory | the suite's renderer refuses above 48 KiB (FACT); the device's own limit otherwise | `max_threadgroup_memory` read from the device |
| Register budget per thread (a TARGET for the spill estimate, not a hard device limit) | 63 (DESIGN default; settled by the M2 profile) | 63 (DESIGN default) |
| `f64` | allowed in principle, not used | not available: refuse |
| Reserved fixed-point types | refuse | refuse |

**The check (in the emitter and again at manifest registration).** For target backend B and shape class S:
evaluate the symbolic fields at S; compare with B's limits; on any excess refuse emission with a build-time error
naming the field, the value, the limit and the kernel. A kernel that fits CUDA and not Metal is refused for Metal
only; the library index then shows it as CPU and CUDA only, and a strict Metal placement request for a stage that
needs it is refused by the planner (`FROB-REF-604`). Soft bound: `max_regs` above the register budget is a
recorded warning with the estimated stack bytes, and a hard error only above a configured multiple (default 4×).

**Where the numbers go.** Into the kernel manifest's resource-bounds field (the stage signature), into the IR
metadata block (`max_regs; max_stack_bytes; operation counts by type; loop bounds; buffer argument count`), and
into the derivation statistics report.

## Acceptance criteria

- [ ] Every program in the library has all metadata fields, computed by the build; none is hand-written (a manifest whose resource field differs from the computed one fails registration).
- [ ] PO-SPARK-03, exactness: on 10⁴ random programs, `op_counts` equals the count observed by the reference interpreter, and the interpreter's observed maximum number of simultaneously live values never exceeds `max_regs`.
- [ ] A kernel with 31 buffer slots is emitted for Metal; the same kernel with 32 is refused for Metal with the field `buffer_args`, value 32, limit 31, and is still emitted for CUDA.
- [ ] A skeleton declaring thread-group memory one byte over the target's limit is refused; at the limit it is accepted.
- [ ] Scheduling: for a program with a known optimal order, `max_regs` after scheduling equals the hand-computed minimum; the scheduled program's outputs are bit-identical to the unscheduled program's on 10⁵ inputs; every scheduled program's trace carries its reorderings as `schedule` steps and replays from the unscheduled program to the scheduled program's hash in N21a-19's reference replayer.
- [ ] Negative control: a scheduler mutant that reorders two dependent operations is caught by the bit comparison; a metadata mutant that under-reports `max_regs` by one is caught by the interpreter's live-set observation.
- [ ] Limits come from data: changing the Metal argument limit in the recorded admission data (fixture) changes the refusal threshold with no code change.

## Test plan

### Unit tests (`cargo test -p frob-kir resources`)
- `op_counts_straight_line`: 3 adds, 2 muls, 1 sqrt → exactly those counts.
- `op_counts_nested_loops`: bounds 3, 4, 5 around a body of 2 muls → 120 muls.
- `op_counts_symbolic_capacity`: a loop over `links` reports `2·links` muls and evaluates to 26 at links = 13.
- `max_regs_chain`: a chain v₁ = a + b, v₂ = v₁·c, v₃ = v₂ + d with inputs dead after use → hand-computed live maximum.
- `max_regs_wide_then_narrow`: eight independent products summed pairwise; scheduled order needs fewer live values than definition order; both counts hand-computed and asserted.
- `schedule_is_bit_identical`: outputs equal before and after scheduling.
- `schedule_is_deterministic`: same program, same schedule, same hash.
- `schedule_trace_replays`: the `schedule` steps of `max_regs_wide_then_narrow`'s scheduled program replay from the definition order to the scheduled hash; deleting one step fails the replay; a step that exchanges a load and a store of one buffer is rejected.
- `buffer_args_31_ok_32_refused_metal`.
- `group_shared_limit_boundary`.
- `f64_refused_for_metal`; `reserved_fixed_point_refused`.
- `underreported_max_regs_is_caught`, `dependent_reorder_is_caught` (negative controls).
- `limits_are_data`: fixture limit tables.

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `resources`: builds a fixture kernel with 32 buffer slots
and asks for both dialect targets through the build; asserts CUDA emission succeeds and Metal emission is refused
with the named field; then, for every library kernel, reads the metadata from the IR metadata block of its
checked-in generated program and from the resource-bounds field of its manifest in `registries/kernels.toml`,
logs both and asserts they agree (the library listing `frob spark check --action list` belongs to N21a-04, which is not a
dependency of this bead, and the verb has no resources option). Logged per line: command, exit code, wall time, kernel name, each metadata field with its limit, and for
a refusal the field, value and limit.

### Known answers and negative controls
- Known answers: the counts and live-set sizes of the hand-built fixtures; 31 accepted, 32 refused.
- Register binding: the Spark invariant register (N21c-27, a dependency) binds the IR side of PO-SPARK-03 to `buffer_args_31_ok_32_refused_metal` and to the control `underreported_max_regs_is_caught`; both keep these names.
- Negative controls: under-reported `max_regs`; a dependent reorder; a hand-edited resource field in a manifest.
- Metamorphic: unrolling a loop multiplies no count (the looped and unrolled programs report equal `op_counts`).
- Determinism: metadata and schedule are pure functions of the program (class D0), identical across platforms.

## Considerations

- The register budget is a model, not a device fact; its purpose is to make spill pressure visible before the profile exists. The M2 profile replaces the default with measured values per device family.
- Real kernels stay under Metal's 31 arguments by packing arrays into a few slabs indexed through an offset table in a parameter buffer; this check is what tells a kernel author, on any host, that packing is needed.
- Upstream work item FD-FT-01 (in FrankenTorch's repository) asks for relief from the 31-argument limit and binding at a byte offset; when it lands, the limit table changes by data and INT-FT-01 and the Metal gates are re-run.
- The fused per-world step kernel studied as a Moonshot is bounded by thread-group memory (one quadruped world's working set is about 35 kB against a 48 KiB ceiling); this bead's `group_shared_bytes` is the number that study reads.
