## Background

A compiler pass that "simplifies" floating-point arithmetic changes bits. Spark's kernel arithmetic must give the
same bits from the Rust emitted for the CPU reference and from the dialect text compiled for CUDA and Metal, so
the kernel intermediate representation `frob-kir` (typed single assignment with bounded loops) allows only
rewrites that are **exact in IEEE arithmetic**, and it draws the line by class (construction C-14):

- **Class E** changes no bit under round-to-nearest with contraction off: commutation, common-subexpression and
  dead-code elimination, scaling by a power of two, scheduling. A class-E rewrite ships a rule trace that an
  independent checker replays (theorem card T-27: a class-E rewrite trace maps the source program to the target
  program using only rules of the closed table).
- **Class R** is equal over the reals only: reassociation, distribution, fused multiply-add. A class-R rewrite
  makes a *different kernel* with a new identity, an error bound and a fidelity run. It is never applied as a
  rewrite.

The rewrites allowed by the IR, as the plan lists them: bounded common-subexpression elimination, dead-code
removal, commutation of + and ×, x·1, x + (−0), double negation, select simplification, and folding of exact
constant operations. Reassociation and distribution are not rewrites; a Horner form is chosen at derivation time,
before the program is fixed. Scheduling by live range reorders independent operations only (N21a-18). Extraction
over an e-graph, if the M2 profile ever asks for it, is restricted to the same exact rules under a node budget
(N21a-15).

The smallest case that shows why: in `f32` with a = 10⁸, b = −10⁸, c = 1, (a + b) + c is 1 and a + (b + c) is 0.
A reassociation filed as class E must be rejected by the trace checker. Version 0 of the IR (BD-018) has only
hash-consing; this bead builds the full table, the traces, and the refusals. Tier: Frontier with the IR (kill gate
KILL-KIR). Rejected alternatives: trusting the device compiler with a relaxed mode (the three compilers would
choose differently); an open-ended rule set (unreviewable; one bad rule poisons every kernel).

## Scope

In: the rule table with preconditions; the rewrite engine with fuel; rule traces and their format; the refusal of
class-R requests; exact constant folding (including the form specialization needs); tests of every rule on the
non-finite and signed-zero edge set.
Out: scheduling (N21a-18); e-graph extraction (N21a-15); the independent trace checker in the certificate crate
(its own bead; this bead ships a reference replayer for tests and the trace format); differentiation (N21a-20).

## Technical approach

**The closed table (class E).** Each rule has a precondition that makes it bit-exact for every input, including
NaN, ±∞ and ±0.

| Rule | Rewrite | Precondition and note |
|---|---|---|
| E1 share | two nodes with the same operator and operands → one | bounded table (default 65,536 entries) |
| E2 dead | remove a node with no use and no store | — |
| E3 comm-add | a + b → b + a | IEEE addition is commutative bit for bit (NaN payload choice aside: payloads are not part of any digest that feeds state; a world with a NaN is `Faulted`) |
| E4 comm-mul | a·b → b·a | as E3 |
| E5 mul-one | x·1 → x; 1·x → x | exact for all x |
| E6 add-negzero | x + (−0) → x; (−0) + x → x | exact for all x, including x = −0 and x = +0. The rule for +0 does **not** exist: (−0) + (+0) = +0 |
| E7 neg-neg | −(−x) → x | exact (sign bit flips twice) |
| E8 select-same | select(p, a, a) → a | — |
| E9 select-const | select(true, a, b) → a; select(false, a, b) → b | the predicate is a constant |
| E10 fold-exact | op(c₁, c₂) → c for constants | only when the operation is **exact**: the mathematically exact result is representable in the type (checked in exact rational arithmetic at build time); division and square root fold only when exact; an inexact constant operation stays in the program |
| E11 pow2-scale | x·2ᵏ·2ᵐ → x·2ᵏ⁺ᵐ | only when no intermediate or final result can overflow or underflow for the declared input range (a range proof is attached); otherwise not applied |

Rules that look harmless and are **excluded** (each with its counterexample, kept as a negative test):
x·0 → 0 (∞·0 is NaN); x − x → 0 (∞ − ∞ is NaN); x + 0 → x for +0 (x = −0 gives +0); x/x → 1 (0/0 is NaN);
(a + b) + c → a + (b + c) (the 10⁸ case); a·(b + c) → a·b + a·c; a·b + c → fma(a, b, c); folding an inexact
constant operation (0.1·3 is not the float nearest 0.3).

**Engine.** A worklist over nodes, applying the first applicable rule in table order, with **fuel**: a maximum
number of rule applications per program (default 10⁵, recorded in metadata as `rewrite_fuel_used`); on exhaustion
the engine stops with the current (still equivalent) program. Deterministic: worklist order is node index order.

**Rule traces.** Every application appends `{rule, node, operands_before, result_node}` to the trace. The trace
format `frob.kir.trace/1` is canonical bytes with a BLAKE3 digest; the pair (source hash, trace digest) is stored
with the target program. Replaying the trace on the source program with only table rules must reproduce the
target program's hash. The reference replayer lives in `frob-kir`'s tests; the independent checker (a different
implementation, in the certificate crate) is what a certificate cites.

**Class R requests.** The API has no reassociation or distribution rule. A derivation that wants a different
association produces a different source program (a new content hash, hence a new kernel identity) and owes that
kernel its own error bound and fidelity run; the library index records the relation `derived_from` for audit. A
trace containing a rule outside the table is rejected by the replayer.

**Folding for specialization.** Per-design specialization (for survivors only) folds a design's constants into a
generic kernel. It may use E10 only: a multiplication by a design constant folds only where the operation on
constants is exact; everything else keeps the generic kernel's operation order. This is what makes "a specialized
kernel is bit-identical to its generic kernel" a property of the rule table instead of a hope.

## Acceptance criteria

- [ ] The engine implements exactly rules E1 to E11; a compile-time enumeration test asserts the rule count is eleven and that no rule named reassociate, distribute, fuse or mul-zero exists.
- [ ] Each rule is verified bit-exact on the full edge set (±0, ±∞, NaN, subnormals, largest finite, 1, −1) crossed with 10⁴ random values, by comparing the rewritten and original programs in the reference interpreter.
- [ ] Each excluded rule has a test that shows the counterexample differs in bits (for example x = −0 under x + (+0) → x).
- [ ] The reassociation control: a trace that claims (a + b) + c → a + (b + c) is rejected by the replayer; and the two programs evaluate to 1 and 0 at a = 10⁸, b = −10⁸, c = 1.
- [ ] Every rewritten program in the library has a trace that the reference replayer accepts; deleting, reordering or altering one step makes the replay fail.
- [ ] E10 folds 0.5·4 → 2 and 1/4 → 0.25, and leaves 0.1·3 and 1/3 in the program.
- [ ] Fuel: a program that would exceed the fuel stops at the limit with an equivalent program and `rewrite_fuel_used` equal to the limit.
- [ ] Rewriting is idempotent (a second pass applies zero rules) and deterministic (same hash on Linux and macOS).

## Test plan

### Unit tests (`cargo test -p frob-kir rewrite`)
- `rule_table_is_closed`: eleven rules, by name.
- `e5_mul_one_all_edges`, `e6_add_negzero_all_edges` (including x = −0 → −0 and x = +0 → +0), `e7_neg_neg`, `e8_e9_select`.
- `e6_plus_zero_is_not_a_rule` (negative control): x = −0, x + (+0) = +0 ≠ x.
- `no_mul_zero`: ∞·0 → NaN preserved.
- `no_x_minus_x`: ∞ − ∞ → NaN preserved.
- `no_reassociation`: the 10⁸ case; both programs kept distinct with different hashes.
- `no_distribution`: a·(b + c) and a·b + a·c differ in bits on a found `f32` triple checked in as a fixture.
- `e10_exact_folding`: the four constant cases; a fold whose exact result is not representable is refused.
- `e11_pow2_scale_needs_range_proof`: without a declared range the rule does not fire; with a range that could overflow it does not fire.
- `trace_replays`; `trace_truncated_fails`; `trace_foreign_rule_fails` (negative controls).
- `rewrite_idempotent`; `rewrite_deterministic`; `fuel_stops`.
- Property test (T-27): for 10⁴ random programs, replay(source, trace) hash = target hash, and interpreter outputs of source and target are bit-identical on 10² inputs each, including edge values.

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `rewrites`: regenerates the library with rewriting on,
verifies every trace with the replayer through `cargo test -p frob-kir rewrite_library_traces`, and runs the
rewritten against unrewritten kernels through `frob spark check --kernel <name> --backend batch-cpu --compare
unrewritten --json` for bit equality. Logged per line: command, exit code, wall time, per-kernel node counts
before and after, rule application counts by rule, trace digests, and on failure the first differing output or
the first unreplayable step.

### Known answers and negative controls
- Known answer: in `f32`, (10⁸ + (−10⁸)) + 1 = 1 and 10⁸ + ((−10⁸) + 1) = 0.
- Negative controls: each excluded rule; trace tampering; a planted twelfth rule (x·0 → 0) must fail `rule_table_is_closed` and the edge-set test.
- Metamorphic: rewriting commutes with renaming inputs; applying the engine to an already rewritten program is the identity.
- Determinism lanes: rewritten kernels are bit-identical to unrewritten ones in every lane the unrewritten kernel holds (twice on one machine, worker counts, debug and release, across backends per class).

## Considerations

- Commutation interacts with NaN payload propagation on some hardware; payloads never feed a digest that matters because any NaN marks its world `Faulted`. If a device is found where commutation changes a non-NaN result, rules E3 and E4 are removed for that family by data and the library is regenerated.
- The rule table is the trust base for specialization and for any future extraction; adding a rule is an ADR with its edge-set proof and a new checker version, never a quiet change.
- Derivations choose algebraic forms (Horner, factorizations) before the program is fixed; that choice is where arithmetic cost is really decided, and it is outside the rewrite engine by design.
- If KILL-KIR fires, the table still governs any generated kernels that remain and the specialization route's bit-identity requirement.
