## Background

Many parts of the system need derivatives of kernel arithmetic: the Newton solve's Jacobian rows, sensitivities
for design gradients, trajectory optimization with design variables, the gradient of a gait's return map,
controller synthesis. Writing each derivative by hand in three languages (Rust, CUDA dialect, Metal dialect) is
exactly what Spark's derivation route replaces. Construction C-14 states it: derivative programs, a forward
product J·v and a transposed product Jᵀ·w, come from automatic differentiation of the straight-line program. The
kernel IR `frob-kir` (typed single assignment with bounded loops) is small enough that differentiation is an exact
program transformation: a loop bound is a literal or a capacity, so every program has a finite, known operation
count **and a derivative program by the same transformation**.

Two doctrine rules govern derivatives. **D-8: every domain ships its adjoint or its excuse**: a kernel either has
a derivative program or a recorded reason it does not, with the estimator that replaces it; the kernel manifest
has a field for this. **D-15: a derivative carries its validity label**: every derivative that leaves a kernel
says where it is valid, because a select, a clamp or a contact switch makes the function only piecewise smooth.

The plan's honest limit: derivation is kept for correctness, certificates and CPU derivative kernels, where
rigid-body derivatives dominate; it is not claimed as a GPU throughput lever. Tier: Frontier with the IR (kill
gate KILL-KIR; if it fires, derivative kernels for CPU solvers are the part of derivation that stays). Rejected
alternatives: finite differences as the production derivative (cost scales with input count, and step-size error);
dual numbers at run time on devices (doubles the state and needs a second type in every kernel); symbolic
differentiation of whole expressions (expression swell: a published attempt to expand a humanoid mass matrix
symbolically ran for over an hour and crashed).

## Scope

In: the forward-mode transformation (JVP); the reverse-mode transformation (VJP) including loops with carried
values; the validity label each derivative program carries (one of the closed set, below); the dimension rules for
tangents and cotangents; emission through the ordinary emitters; the manifest's derivative field, of which this
bead is the one definition (its two forms, the closed list of excuse reasons and the admitted estimators); tests
against dual numbers, finite differences and adjoint duality on the programs it generates.
Out: the doctrine check over the whole manifest and over every boundary (N10a-04 in `frob-conformance`, which
depends on this bead and uses this field as spelled here: exactly one of the two forms per kernel, a valid excuse,
duality passed by every registered pair, no derivative leaving a kernel, an analysis or a verb without a label,
and the weakest-label order for composites); the closed set of validity labels and the refusal near grazing as a
contract (N10b-01, with SPEC-C-16); the statement and the tolerance of the duality law (SPEC-C-14); which kernels
need derivatives and how solvers use them (their own beads); derivatives through events and
contact switches (the gait and contact beads); second derivatives (not provided; a JVP of a VJP may be formed by
applying the transformations in sequence where a bead needs it, and is tested there).

## Technical approach

**Inputs.** A primal program P with float inputs x (some marked `active`), outputs y, and possibly loads and
stores. Integer and boolean values are never active; predicates are treated as constants of the linearization.

**Forward mode: P ↦ P_jvp(x, ẋ) → (y, ẏ).** One tangent node (or none, if inactive) per primal node, emitted
right after it, in the same single-assignment order:

| Primal | Tangent |
|---|---|
| y = a + b; a − b | ẏ = ȧ + ḃ; ȧ − ḃ |
| y = a·b | ẏ = ȧ·b + a·ḃ |
| y = a/b | ẏ = (ȧ − y·ḃ)/b |
| y = √a | ẏ = ȧ/(2·y) |
| y = −a | ẏ = −ȧ |
| y = abs(a) | ẏ = select(a < 0, −ȧ, ȧ); label: kink at a = 0 |
| y = min(a, b), max(a, b), clip | ẏ = the tangent of the arm the primal selected, by the same predicate; label: kink where the arms cross |
| y = select(p, a, b) | ẏ = select(p, ȧ, ḃ); label: switching set {p changes} |
| load(slot, lane, k) | load from the slot's tangent slab, same lane and offset |
| store(slot, lane, k, v) | store v̇ to the tangent slab |
| loop with carried (a = a₀) | the tangent ȧ is a second carried value, initialized to ȧ₀ |

**Reverse mode: P ↦ P_vjp(x, w) → (y, x̄ = Jᵀ·w).** For straight-line code: run the primal; initialize adjoints of
outputs to w; walk nodes in reverse index order accumulating adjoints (for y = a·b: ā += ȳ·b, b̄ += ȳ·a; for
y = a/b: ā += ȳ/b, b̄ −= ȳ·y/b; for y = √a: ā += ȳ/(2·y); selects route the adjoint to the selected arm). Each
accumulation is one single-assignment node (a new name per update), so the result is again a valid program.
For a loop `for i in 0..N carry (a) { … }`: the VJP program has a forward loop that runs the primal and stores each
iteration's carried values and the intermediate values the reverse sweep needs into a local array of N records
(the *tape*; its size is known statically because N is a literal or a capacity, and it is reported as stack bytes
by the resource metadata), then a second loop of the same bound that visits iterations in reverse
(index N − 1 − i), reading the tape. Nested loops nest tapes. No dynamic allocation exists anywhere.
The accumulation order of adjoints is fixed by reverse node index, so the VJP is as deterministic as the primal.

**Validity labels (D-15).** The transformation collects, per derivative program, the list of switching
predicates (from `abs`, `min`, `max`, `clip`, `select`) and emits a `validity` record whose label is one of the
closed set of nine that the hybrid-orbit contract owns (N10b-01; the D-15 check of N10a-04 admits no other):
`smooth` if the list is empty, otherwise `fixed-mode` with the predicates named as its frozen mode sequence.
DESIGN: an earlier form of this bead called the second case `piecewise`, which is not in the set and would fail
the boundary check; `fixed-mode` is the label of the set that says what the transformation computes, the
derivative conditional on the mode being held fixed (predicates are constants of the linearization), valid only
while no switching surface is crossed. At run time the derivative kernel also outputs a mask bit per lane,
"within a declared band of a switching surface", when the manifest asks for it (the band is a guarded predicate of
BD-053, a dependency). A consumer that needs a derivative across a switch (an event, a contact change) must use the
labelled-event machinery of its own domain; this kernel's label and mask tell it when.

**Dimensions (theorem T-09 applies to derivative programs too).** A tangent has the dimension of its primal
value when ẋ has the dimension of x. In reverse mode, with w of dimension dim(L)/dim(y) for a scalar pairing L,
each adjoint has dimension dim(L)/dim(value). The type checker verifies both programs as ordinary programs:
every accumulation sums homogeneous terms. A derivative program that fails typing indicates a defect in the
transformation and is a build error.

**Identity and manifest.** Derivative programs are programs: content-hashed, rewritten only by the exact rule
table, scheduled, resource-checked, emitted to Rust and dialect. The primal's metadata carries
`derivative program: {jvp: hash, vjp: hash}`. The kernel manifest's derivative field has two forms, defined here
and nowhere else (DESIGN; the plan's manifest names the entry "derivative program" and the doctrine rule D-8
requires "a derivative program or a recorded reason it does not, with the estimator that replaces it"): `derivative = present { jvp: <program hash>, vjp: <program hash> }` (a forward product J·v and a transposed product Jᵀ·w, each a content-hashed program) or `derivative = excused { reason, estimator }`, where `reason` is one of a closed list (`integer-valued`, `discrete-selection`, `event-driven`, `not-requested-by-any-consumer`, `budget`) and `estimator` names what replaces the derivative (`finite-difference` with step and scheme, `smoothed` with its parameter, `none-needed`).
The library index prints the first word (`present` or `excused`) with the reason. The doctrine check of N10a-04
reads this field under this spelling.

**Cost.** JVP: at most about 3 times the primal's operations; VJP: at most about 5 times plus the tape traffic.
The counts are in the metadata, so a derivative kernel that will not fit a backend's limits is refused at build
time like any other.

## Acceptance criteria

- [ ] `P_jvp` and `P_vjp` are generated for every operator of the IR and for loops with carried values and nesting; both type-check, hash canonically and emit to Rust and dialect.
- [ ] Forward mode agrees with `fs-ad` dual numbers to at most 2 ulp per output on 10⁵ seeded inputs for each fixture kernel; and with central finite differences in `f64` to a relative 10⁻⁶ away from switching surfaces.
- [ ] Adjoint duality: ⟨J·v, w⟩ = ⟨v, Jᵀ·w⟩ on 10⁵ random (x, v, w) for every derivative pair in the library, within the tolerance the contract SPEC-C-14 sets for this law (the plan leaves it "to set"): 64 ulp of the sum of absolute terms of the two pairings in `f64`, and 10⁻⁵ relative in `f32`. The same law function and the same numbers are used by the doctrine check of N10a-04; an earlier figure in this bead, 16 ulp of the pairing's magnitude, is withdrawn because it is not defined when the pairing cancels to near zero.
- [ ] Negative controls: a VJP with one adjoint accumulation negated fails duality; a JVP that differentiates `select` through the wrong arm fails the dual-number comparison; a loop VJP that reads the tape in forward order fails duality on a fixture with a non-commuting recurrence.
- [ ] Validity: a program with no switching operator is labelled `smooth`; one with `abs` is `fixed-mode` with the predicate listed as its frozen sequence; no program carries a label outside the closed set of nine; the run-time mask flags a lane placed inside the band and not one outside.
- [ ] The tape size of a loop VJP equals bound × record size and appears in `max_stack_bytes`; a loop whose tape exceeds a backend limit is refused for that backend at build time.
- [ ] D-8: every kernel in the library index has `derivative = present { jvp, vjp }` with hashes, or `derivative = excused { reason, estimator }` with a reason from the closed list and an estimator of an admitted form.

## Test plan

### Unit tests (`cargo test -p frob-kir derivative`)
- `jvp_product_rule`: y = a·b at (3, 4), tangents (1, 0) → ẏ = 4; (0, 1) → 3.
- `jvp_quotient_sqrt`: y = √(a/b) at (8, 2): y = 2; ∂y/∂a = 1/(2·y·b) = 0.125; ∂y/∂b = −y/(2·b) = −0.5.
- `vjp_product_rule`: w = 1 → (ā, b̄) = (4, 3).
- `vjp_fanout_accumulates`: y = a·a at a = 3, w = 1 → ā = 6 (two accumulations, 3 + 3).
- `jvp_select_follows_primal_arm`; `jvp_abs_kink_label`.
- `loop_jvp_recurrence`: s ← s·x + 1 for 3 iterations from s = 0 gives s = x² + x + 1; ds/dx = 2x + 1; at x = 2: s = 7, ṡ = 5.
- `loop_vjp_recurrence`: the same program in reverse mode: x̄ = 5 for w = 1; tape of 3 records.
- `loop_vjp_forward_tape_order_is_caught` (negative control).
- `duality_random_programs`: property test over 10⁴ random programs (bounded loops ≤ 6, no switching operators) with random v, w.
- `jvp_matches_dual_numbers`; `jvp_matches_finite_differences_f64`.
- `derivative_programs_type_check`: tangents and cotangents carry the stated dimensions; a seeded transformation bug that drops a factor with a dimension is rejected with `FROB-REF-250`.
- `tape_bytes_in_metadata`.
- `negated_adjoint_is_caught`, `wrong_select_arm_is_caught` (negative controls).

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `derivatives`: regenerates the derivative programs of the
fixture kernels, runs `frob spark check --kernel <name>-jvp --backend <backend> --key d-<name>-jvp-<backend> --json`
and the same for `<name>-vjp` on `batch-cpu`, `gpu-cuda` and `gpu-metal` (an absent device is logged `not-run`),
and the duality test through the kernel harness with a stated seed. Logged per line: command, exit code,
wall time, evidence block, program hashes, operation counts of primal, JVP and VJP, the duality residual against
its tolerance, the validity label, and on failure the first input where the residual exceeds the tolerance.

### Known answers and negative controls
- Known answers: the product, quotient and recurrence cases above (ẏ = 4 and 3; 0.125 and −0.5; s = 7, ṡ = 5).
- Negative controls: negated adjoint; wrong select arm; forward tape order.
- Metamorphic: differentiating an unrolled loop gives a program with outputs bit-identical to the looped derivative; JVP is linear in v (scaling v by a power of two scales ẏ exactly).
- Determinism lanes: derivative kernels hold the same lanes as primals (twice on one machine, debug and release, across platforms, across backends per class).

## Considerations

- A derivative through a select is the derivative of the selected branch; it is silent about the jump. Consumers that optimize through contact or events must not treat these kernels as gradients of the event-crossing map; the label and mask exist to make misuse visible.
- Reverse mode's tape is memory traffic; on devices the step is expected to be bound by memory bandwidth, so VJP kernels are intended first for CPU solvers. A device VJP is admitted per kernel by its measured cost.
- Guarded predicates inside a primal stay exact in the derivative program (the predicate is recomputed, not differentiated).
- If KILL-KIR fires for arithmetic in general, this transformation is the part that stays (derivative kernels of CPU solvers), applied to hand-written bodies expressed through the IR builder.
