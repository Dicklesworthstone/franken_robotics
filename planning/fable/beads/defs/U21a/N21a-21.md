## Background

Devices run single precision: Metal has no double type, and an RTX 4090 runs double precision at about 1/64 of its
single-precision rate (FACT, from the suite's renderer documentation). Most of the simulation step is kept
adequate in `f32` by other measures (anchored positions, group-preserving updates, fixed-order sums, scaled
solves). A few **accumulators** need more: time offsets, odometry, the energy ledger. For those the kernel IR
`frob-kir` has the type `f32dd`, a **double-float pair** (hi, lo) of two `f32` values whose unevaluated sum
represents a number to about 48 bits, with |lo| at most half a unit in the last place of hi.

Double-float arithmetic is built from **error-free transformations**: sequences of ordinary rounded operations
that recover the exact rounding error of a sum or a product. The suite's own renderer builds its product on a
fused multiply-add (FACT). Spark does not: **ADR-SPARK-10** (DESIGN): double-float accumulators use the split
product, not a fused multiply-add, and every device proves at start-up that its compiler kept the error-free
transformations. Reasons: a fused operation is banned in batched kernels on every backend (it is the main way a
compiler changes bits between devices), and an error-free transformation is fragile in the opposite direction: a
compiler that "simplifies" the error term algebraically folds it to zero and the accumulator silently loses its
low word. The cost of the decision is stated: the split product takes 17 operations instead of 3.

This bead builds the type in the IR and its lowering to scalar operations for Rust and the dialect. The device
canaries are a separate bead of the precision subsection; this bead supplies their arithmetic and proves it on the
CPU. Tier: Solid. Rejected alternatives: `f64` on devices (absent on Metal; 1/64 rate on the RTX 4090); the fused
product (banned); half precision anywhere in the step (refuted elsewhere by its conditioning arithmetic).

## Scope

In: the type in the IR; the error-free sum and the split product as IR subprograms; pair addition,
pair-times-scalar, pair-times-pair, renormalization, conversions; lowering and emission; the rule that the rewrite
engine never touches the transformations; CPU tests of the two canary values; the compensated-sum operator used by
`K-reduce`.

Out: the hand-written `f32dd` primitives in the shared dialect and in Rust, the start-up canary kernel `K-canary`
on devices, the device flag it sets and `FROB-REF-609` (N21b-36, an M0 dependency: the lowering here must emit
code that is bit-equal to those primitives and passes the same canaries); which kernels use the pair (their own
beads: the energy ledger BD-208, the precision battery BD-179).

## Technical approach

**Notation.** fl(·) is one correctly rounded `f32` operation (round to nearest, ties to even). All operations
below are separate IR nodes; none may be contracted.

**Error-free sum (`two_sum`, 6 operations).** For any a, b: s = fl(a + b); bb = fl(s − a);
e = fl(fl(a − fl(s − bb)) + fl(b − bb)). Then s + e = a + b exactly.
When |a| ≥ |b| is known (`fast_two_sum`, 3 operations): s = fl(a + b); e = fl(b − fl(s − a)).

**Split (4 operations).** With the splitter C = 4097 = 2¹² + 1 for `f32` (24-bit significand):
t = fl(C·a); a_hi = fl(t − fl(t − a)); a_lo = fl(a − a_hi). Then a = a_hi + a_lo exactly and each half has at most
12 significant bits, so products of halves are exact. Precondition: |a| < 2¹¹⁵ so that C·a does not overflow; the
type checker requires a declared range or inserts a scaled path.

**Error-free product by the split (`two_prod`, 17 operations).** p = fl(a·b) (1); split a (4); split b (4);
e = fl(fl(fl(fl(fl(a_hi·b_hi) − p) + fl(a_hi·b_lo)) + fl(a_lo·b_hi)) + fl(a_lo·b_lo)) (8: four products, one
subtraction, three additions). Then p + e = a·b exactly, absent underflow. With a fused multiply-add the same
result would be p = fl(a·b), e = fma(a, b, −p); that form is forbidden.

**Pair operations (each ends with a renormalization so that |lo| ≤ ½ ulp(hi)).**
- `dd_from(x: f32)` = (x, 0).
- `dd_add_f(a: dd, x: f32)`: (s, e) = two_sum(a.hi, x); e′ = fl(e + a.lo); result = fast_two_sum(s, e′).
- `dd_add(a: dd, b: dd)`: (s, e) = two_sum(a.hi, b.hi); e′ = fl(e + fl(a.lo + b.lo)); result = fast_two_sum(s, e′).
- `dd_mul_f(a: dd, x: f32)`: (p, e) = two_prod(a.hi, x); e′ = fl(e + fl(a.lo·x)); result = fast_two_sum(p, e′).
- `dd_mul(a: dd, b: dd)`: (p, e) = two_prod(a.hi, b.hi); e′ = fl(e + fl(fl(a.hi·b.lo) + fl(a.lo·b.hi)));
  result = fast_two_sum(p, e′).
- `dd_to_f(a)` = fl(a.hi + a.lo).
Comparison of pairs for a strict predicate is not provided in floating form; a predicate on an accumulator goes
through the exact or guarded classes.

**In the IR.** `f32dd` is a composite of two `f32` components with one dimension (both components share it). The
pair operators lower to the scalar sequences above before emission. Three protections keep the transformations
intact:
1. The lowered nodes carry the attribute `eft` and the exact rewrite engine applies **no** rule to them or across
   them (common-subexpression sharing included), and scheduling keeps each transformation's nodes in their order.
2. The emitters write each `eft` node as its own statement; the compile options keep contraction off; no fast
   mode exists.
3. The start-up canaries (their own bead) run the same emitted sequences on each device and refuse the device for
   double-float kernels if a value is wrong: `FROB-REF-609` "a double-float canary failed" (exit code 6; first
   repair: run without double-float kernels, labelled; file the compiler evidence).

**The two canary values (what this bead proves on the CPU and hands to the device canary).**
- Sum: `two_sum(1, 2⁻³⁰)` must return the pair (1, 2⁻³⁰). A compiler that simplifies the error term algebraically
  returns (1, 0).
- Product: `two_prod(1 + 2⁻¹², 1 + 2⁻¹²)` must return (1 + 2⁻¹¹, 2⁻²⁴), since the exact product
  1 + 2⁻¹¹ + 2⁻²⁴ is a tie that rounds to even.

**Compensated reduction.** The operator `sum_dd` of the reduction kernels (N21a-07) carries a pair through the
fixed pairwise tree: leaves are `dd_from(x)`, nodes are `dd_add`; its neutral element is (−0.0, −0.0), which
`dd_add` returns unchanged.

**Determinism.** The pair operations are fixed sequences of correctly rounded operations: class D2 on every device
by construction, D1 where the device's IEEE probe passes. Results are evidence class `Tested`.

## Acceptance criteria

- [ ] `f32dd` and the six pair operations exist in the IR, lower to scalar nodes, and emit to Rust and dialect; the dialect text passes the lint (no `fma`).
- [ ] The operation count of `two_prod` in the lowered program is exactly 17 and of `two_sum` exactly 6 (asserted from the metadata).
- [ ] On `batch-cpu`: `two_sum(1, 2⁻³⁰)` = (1, 2⁻³⁰) and `two_prod(1 + 2⁻¹², 1 + 2⁻¹²)` = (1 + 2⁻¹¹, 2⁻²⁴), bit for bit.
- [ ] Exactness: for 10⁶ random pairs in range, s + e = a + b and p + e = a·b verified in exact rational arithmetic; `dd_add` and `dd_mul` results are within 2⁻⁴⁴ relative of the exact value.
- [ ] Negative controls: a lowering that lets the rewrite engine share or simplify inside a transformation returns (1, 0) for the sum canary and is caught; a product built on a fused operation is rejected by the dialect lint and by the Rust kernel lint (`mul_add`); a build of the CPU fixture with a fast-math-like simplification of e (replacing e by 0) is caught by both canary tests.
- [ ] Renormalization invariant: after every pair operation |lo| ≤ ½ ulp(hi) on 10⁶ random inputs.
- [ ] `sum_dd` over [2²⁴, 1, 1, 1] returns the pair representing 16,777,219 exactly ((16,777,220, −1) after renormalization), where the plain `f32` tree returns 16,777,218.
- [ ] The canary sequences are exported as a kernel body the device canary bead can run unchanged.

## Test plan

### Unit tests (`cargo test -p frob-kir dd`, `cargo test -p frob-kernels dd`)
- `two_sum_canary`: (1, 2⁻³⁰).
- `two_prod_canary`: (1 + 2⁻¹¹, 2⁻²⁴).
- `split_halves_exact`: for 10⁶ values, a_hi + a_lo = a and each half has at most 12 significant bits.
- `two_sum_exact_random`, `two_prod_exact_random`: against exact rationals.
- `two_prod_op_count_is_17`, `two_sum_op_count_is_6`.
- `dd_add_renormalized`, `dd_mul_renormalized`.
- `dd_accumulates_small_increments`: adding 2⁻³⁰ to 1 one thousand times gives a pair whose value is 1 + 1000·2⁻³⁰ exactly, where plain `f32` stays at 1.
- `dd_sum_tree_fixture`: [2²⁴, 1, 1, 1] → value 16,777,219.
- `eft_nodes_are_not_rewritten`: the rewrite engine's application count on an `eft` block is zero; `eft_simplified_mutant_is_caught` (negative control).
- `fma_product_rejected_by_lints` (negative control).
- `split_overflow_precondition`: an input declared up to 2¹²⁰ is refused or routed through the scaled path.
- `dd_dimension_shared`: both components carry one dimension; adding pairs of different dimensions → `FROB-REF-250`.

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `double_float`: runs `frob spark check --kernel dd-suite
--backend batch-cpu --json` (the two canary values and the accumulation fixture), and, where a device is present,
the same suite on the device, logging whether the device's canaries passed. Logged per line: command, exit code,
wall time, evidence block, each returned pair as two bit patterns against the expected patterns, and on failure
which component differed. A device canary failure is logged as a `refusal` event with `FROB-REF-609`, not as a
script failure of this bead's CPU assertions.

### Known answers and negative controls
- KA-527 (sum canary: (1, 2⁻³⁰); a simplifying compiler returns (1, 0)); KA-528 (product canary by the split product with splitter 4097: (1 + 2⁻¹¹, 2⁻²⁴)); negative control for both: a build with fast math on.
- CX-220: a double-float accumulator does not "work on any compiler".
- Negative controls: the simplified error term; the fused product.
- Metamorphic: `two_sum(a, b)` and `two_sum(b, a)` return the same pair; scaling both inputs of `two_prod` by powers of two scales (p, e) exactly (within range).
- Determinism lanes: bit-identical twice on one machine, debug and release, across platforms on `batch-cpu`; devices per their class and only after their canaries pass.

## Considerations

- Underflow breaks exactness of the product's error term for tiny operands; accumulators here hold quantities far from underflow, and the type checker requires a declared range that excludes it.
- On a device that flushes subnormals (the Metal specification permits it), a lo component that would be subnormal becomes zero; ranges are chosen so that lo stays normal, and the device canary bead adds a subnormal case to the fingerprint record.
- 17 operations per product is acceptable because pairs are used for a handful of accumulators per world, not for state.
- OPEN-NUM-1 (whether an explicit fused multiply-add is ever admitted): default no. If it were admitted with a probed rounding record, the product could drop to the fused form on devices that pass; the split form would remain the reference.
