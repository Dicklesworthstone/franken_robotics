## Background

Spark's kernels come in arithmetic classes. **Exact** kernels use unsigned 32-bit integers and must return the
same bytes on every backend; **guarded** kernels evaluate an `f32` residual, decide when its magnitude exceeds a
certified error bound, and otherwise fall back to an exact integer evaluation, so their decisions are also exact.
The class exists because a strict inequality decided in bare floating point is wrong exactly where it matters
(16,777,216 < 16,777,217 is false in `f32`, since the second number rounds to the first).

The evidence for the class is, so far, a plan-time pilot (FACT as recorded, run outside this repository): a
one-inequality boundary classifier with inputs on a grid of 2⁻²⁸, run as a real Metal command buffer on the M5
Ultra and as a CUDA kernel on each RTX 4090 of `trj`, with readback and independent integer checking. On a
65,536-row grid dense near the boundary the bare `f32` sign of the residual gave 452 false inclusions and 23,438
false exclusions, identically on every device; the exact kernel returned every label correctly on all three GPUs
with identical bytes; the guarded kernel, deferring whenever the absolute residual was at most 2⁻²¹ (its error
bound is 5·2⁻²⁵), decided none of the dense grid on the device and 58,254 of 65,536 rows of a more widely spaced
grid, with no error after fallback. The plan requires these numbers to be **reproduced at GATE-SPARK-08 before any
gate cites them**.

**GATE-SPARK-08** (known answer, TARGET, milestone M0): exact and guarded kernels pass the boundary corpus and the
strict-predicate case on `batch-cpu`, both RTX 4090 and Metal, with identical bytes; the guarded kernel's fallback
fraction is reported. It is an M0 exit condition for Spark. This bead is the end-to-end script that measures the
gate from the user's side, through the `frob` binary, on both machines, and records it. Tier: Solid.

## Scope

In: `scripts/e2e/spark_exact_guarded.sh`; the per-machine run, the cross-machine collation, the gate record; the
negative controls run from the command line; later steps that extend the same script when their kernels land.
Out: the kernels and the corpus (BD-030); the probe verb (BD-017); the IR-generated versions (BD-053, N21a-17);
the contact-battery gate for guarded predicates (BD-182).

## Technical approach

**Placements.** Four: `batch-cpu` (on each machine), `gpu-cuda:0` and `gpu-cuda:1` (the two RTX 4090 of `trj`),
`gpu-metal` (this Mac). Bytes cannot be compared inside one process across machines, and the project's rule is
that only seeds, recipes, receipts, digests and summaries cross machines. So the script has two modes:

1. `run` (on each machine): for each local placement, execute the suite and write
   `target/e2e-logs/spark_exact_guarded/<utc>/digests.json` holding, per placement and per kernel, the BLAKE3
   digest of the output label bytes, the counts, the fallback count and the fingerprint digest.
2. `collate <digests-a.json> <digests-b.json>` (on either machine): assert that for the exact and guarded kernels
   all placements across both files have equal output digests, then write the gate record.

**Suite steps (each a `frob spark probe … --json` call; seed-explicit; idempotent).**

| Step | Command (per placement B) | Asserts |
|---|---|---|
| `strict_predicate` | `frob spark probe --suite strict-2p24 --backend B --json` | Exact and guarded kernels answer "true" for 16,777,216 < 16,777,217; the bare `f32` control answers "false" (KA-529) |
| `boundary_exact` | `frob spark probe --suite boundary --kernel K-x-pred --backend B --json` | Zero errors on all 2 × 65,536 rows against the host's independent integer labels; output digest recorded |
| `boundary_guarded` | `… --kernel K-g-pred …` | Zero errors after fallback; fallback count and evaluation count recorded; the fallback fraction is in the receipt |
| `boundary_bare_control` | `… --kernel K-f32-pred-control --expect-errors …` | The bare `f32` kernel mislabels at least one row; false inclusions and false exclusions counted and compared with the pilot's 452 and 23,438 on the dense grid |
| `pilot_reproduction` | computed from the three steps above | Guarded kernel decides 0 rows of the dense grid on the device and 58,254 of the wide grid; a difference from the recorded pilot is reported with both numbers and does not by itself fail the gate (the gate's thresholds are zero errors and identical bytes), but it blocks citing the pilot's numbers |
| `receipts` | the same probe call with `--emit-receipts <dir>` for one run per placement | The receipt file has the twelve evidence fields, the fingerprint digest and the kernel class |
| `collate` | collation mode | Identical bytes for exact and guarded kernels on all four placements |

Extension steps, appended to the same script by later beads and skipped with a logged reason until their kernels
are registered: `exact_ops` (N21a-17), `classes` (N21a-22), `digest` (N21a-23), and the IR-generated predicate
kernels of BD-053 re-run through the same suite.

**Gate record.** The conformance harness has no agent verb and no `xtask` subcommand by design (a harness driven
through the surface it judges is a path to self-certification). `collate` therefore ends by running
`cargo test -p frob-conformance --test g5 -- GATE-SPARK-08` with the collated file as input; that test target
re-checks the thresholds, writes a hash-named receipt, and the recording session enters the row of
`registries/gates.toml` that cites it. The receipt holds: measured values (errors per kernel per placement, digests, fallback
fraction per placement), thresholds (0 errors; equal digests), the commit, both fingerprint digests, the seed, and
the negative controls caught. A gate record without a caught negative control is refused by the registry.

**Compute envelope.** Each machine's run uses one device at a time and finishes in minutes; it fits the default
envelope (16 GiB, 8 cores, one hour, one device).

## Acceptance criteria

- [ ] `scripts/e2e/spark_exact_guarded.sh run` exits 0 on this Mac (`batch-cpu`, `gpu-metal`) and on `trj` (`batch-cpu`, `gpu-cuda:0`, `gpu-cuda:1`); `collate` exits 0 and writes the GATE-SPARK-08 record.
- [ ] GATE-SPARK-08 thresholds, recorded as measured values: exact kernel 0 errors on 2 × 65,536 rows on each of the four placements; guarded kernel 0 errors after fallback on each; output digests of each kernel equal across the four placements; the strict-predicate case true on each; the guarded fallback fraction reported per placement.
- [ ] Negative controls caught and named in the record: the bare `f32` kernel mislabels at least one row and answers "false" on the strict case; a planted exact-kernel mutant (one comparison made signed) is caught by the boundary step; a planted digest mismatch (one placement's file edited) is caught by `collate`.
- [ ] The pilot's numbers are either reproduced (452, 23,438, 0, 58,254) or the differences are recorded with both values and the citation of the pilot is marked blocked.
- [ ] The script is idempotent and seed-explicit: two runs with the same seed give identical digests; logs are written to `target/e2e-logs/spark_exact_guarded/<utc>.ndjson` with a transcript beside them.
- [ ] On a host with no device the script runs the `batch-cpu` steps, logs the device steps as skipped with the reason, and `collate` refuses to record the gate as passed with fewer than four placements.

## Test plan

### Unit tests
The script's helpers are tested in the shared end-to-end library; this bead adds:
- `collate_equal_digests_passes`, `collate_unequal_digests_fails` (fixture JSON files, label `synthetic`).
- `collate_requires_four_placements`.
- `gate_record_requires_negative_control`: a record with an empty `negative_controls` list is refused.

### End-to-end script and logging
`scripts/e2e/spark_exact_guarded.sh` sources the shared helper of the end-to-end standard. Every NDJSON line has
`ts`, `script`, `bead` (`N21a-24`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the
exact command line, exit code, wall time, the envelope's `evidence` block (claim, class `Tested`, tier,
determinism `exact`, identities, seed), measured values with units and thresholds (rows, errors, false
inclusions, false exclusions, fallbacks, fallback fraction), the output digests, and on failure the first
mislabelled row with its inputs and the artifact paths needed to reproduce (the corpus digest, the kernel ids).
The final `summary` line gives counts of assertions passed and failed and `gates: ["GATE-SPARK-08"]`. The corpus
is synthetic integer data; no private-scene data can appear in the log.

### Known answers and negative controls
- KA-529: 2²⁴ < 2²⁴ + 1 is true in the exact and guarded kernels; negative control: the bare `f32` kernel answers false.
- KA-530: boundary corpus; exact: zero errors, identical bytes on every backend; guarded: zero errors after fallback; negative control: the bare `f32` kernel must mislabel at least one row (pilot: 452 false inclusions, 23,438 false exclusions).
- KA-531: the guard's bound 5·2⁻²⁵ against the deferral threshold 2⁻²¹ (checked exhaustively on the corpus by BD-053 when the generated kernel replaces the hand-built one).
- CX-216 (a strict inequality by bare `f32` comparison), CX-217 (placement: the host loop was fastest end to end).
- Determinism lanes: twice on one machine with equal digests; `batch-cpu` across worker counts {1, 2, 8}; debug and release; across the two platforms and the three device placements (class D0).

## Considerations

- The gate says nothing about speed. The same pilot is a negative placement result: end to end the host integer loop took about 34 µs against about 290 µs on Metal (under 13 µs of it device time) and over 1.2 ms on one RTX 4090, and two-card sharding was slower than one card. The script logs per-step wall and device seconds so that this is visible, and the placement planner's cost model uses it as its cautionary case.
- If a device cannot run the suite at all (admission failure of its backend), the gate is recorded `not run` for that placement with the reason, and the milestone's stop rule applies: a device family that can hold no controlled determinism class is dropped from M2.
- `trj` is often heavily loaded; the gate has no timing threshold, so load cannot fail it.
- KILL-MARROW-GUARD (a fallback rate above 10⁻² on the contact battery on either GPU backend, or an exact path that cannot be made bit-identical across backends) is decided later at M2; this gate's identical-bytes clause is its first data point.
