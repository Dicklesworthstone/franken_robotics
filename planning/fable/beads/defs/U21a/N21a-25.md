## Background

Spark's kernel toolchain is a pipeline with a build-time half and a run-time half. Build time: a kernel body is
derived symbolically (annex `derive/frob-derive`), lowered to the kernel IR (`frob-kir`), type-checked by physical
dimension, rewritten only by exact rules, emitted as Rust and as shared-dialect text, checked in with digests, and
linted. Run time: the emitted Rust is the CPU reference of the kernel on the `batch-cpu` backend; the dialect text
is compiled by a device backend. Each stage has a way to fail that is silent unless a tool objects: a generated
file edited by hand, a dimension error, a banned construct, a footprint wider than declared, a rewrite that
changes bits, a resource bound a device cannot hold.

The unit tests of each stage live with that stage. What no unit test shows is that the stages are wired together
in the order a contributor meets them, and that each planted defect is stopped by the stage that owns it when the
whole pipeline is driven from the outside. That is this bead: one end-to-end script, run from the user's side
with the real `cargo`, `xtask` and `frob` binaries on the real repository, with structured logs, that walks the
pipeline for the M0 kernel and then feeds it one defect per stage. The script grows by steps as later beads land
(each step is skipped with a logged reason until its mechanism exists), so that at M2 it is the regression guard
for the whole toolchain and the input to the kill decision on the derivation route. Tier: Solid (the script);
the toolchain it exercises is Frontier under kill gate KILL-KIR.

## Scope

In: `scripts/e2e/kernel_toolchain.sh` with its steps; the planted-defect fixtures under
`scripts/e2e/fixtures/kernel_toolchain/`; the structured log; the step registry that later beads extend.
Out: device runs for gates (GATE-SPARK-00 by BD-020; GATE-SPARK-08 by N21a-24); the mechanisms themselves.

## Technical approach

**Rules of the script.** Plain shell; sources the shared end-to-end helper; exits non-zero on the first failed
assertion after logging it; idempotent (works in a scratch copy of the generated directories, never edits the
checked-in tree); seed-explicit (`--seed`, default 20260101); every `frob` call uses `--json` and the envelope is
parsed by the helper; a step whose mechanism is not yet built logs `event: "skip"` with the reason and the bead
that will add it.

**Steps at M0 (the pipeline for `K-cay-step`).**

| Step | What it runs | What it asserts |
|---|---|---|
| `annex_policy` | `cargo xtask check-deps`, `check-layers`, `check-unsafe`; `frob doctor --json` | All pass; the core binary lists `batch-cpu` only (N21a-01) |
| `regenerate` | `cargo xtask check-generated` | Regenerating `K-cay-step` and `K-normalize` reproduces the checked-in Rust, dialect and IR files bit for bit (digests logged) |
| `hand_edit_refused` | Copy the tree to scratch, change one character of a generated Rust file, run `check-generated` there | Fails, naming the file (INV-SPARK-08) |
| `kir_emit` | `cargo test -p frob-kir`; then `frob spark check --kernel K-cay-step --backend batch-cpu --json` | The emitted Rust passes its fixtures: (1, 0, 0, 0) with a = (0, 0, 1.5) → unnormalized (1, 0, 0, 0.75), d = 1.5625; normalized (0.8, 0, 0, 0.6) |
| `kir_dimension_refusal` | Build the fixture program `p + a` (metres plus a dimensionless value) through the derivation test entry | Refused with `FROB-REF-250`, node named |
| `dialect_lint` | `cargo test -p frob-kernels dialect_sources_are_clean`; the lint over `fixtures/…/bad_dialect/*.h` | Library clean; each bad file refused with `FROB-REF-251` and the rule in its first line: a transcendental (rule 3), a floating-point atomic (rule 2), an explicit fused multiply-add and the option `--fmad=true` (rule 4), a raw intrinsic (rule 1), a spin loop (rule 6) |
| `device_boundary` | On a host with a device: `frob spark check --kernel K-selftest --backend <device> --emit-receipts <dir> --json`, then again with the fingerprint record moved aside | First: the envelope has the device block and twelve evidence fields; second: `FROB-REF-606`, exit code 6 (N21a-02) |
| `decisions` | `cargo test -p frob-conformance decisions` | Ten decision files, each bound to an enforcement (N21a-03) |
| `kir_pilot` | The three pilot bodies through `frob spark check` and the timing comparison | The pilot record is written with values (N21a-13) |

**Steps added at M1 and M2 (each by the bead named).** `exact_ops` is in the exact-kernel script; here:
`kir_v1` (looped fixture; data-dependent bound refused; N21a-16), `resources` (32 buffer slots refused for Metal,
accepted for CUDA; N21a-18), `rewrites` (every trace replays; rewritten equals unrewritten bit for bit; N21a-19),
`derivatives` (duality residual within tolerance; N21a-20), `double_float` (the two canary values on the CPU;
N21a-21), `det_functions` (the `det_*` suite digest; N21a-11), `footprints` (planted off-by-one write refused;
N21a-06), `dialect_lint_full` (the full bad corpus; a device backend refuses to compile a bad unit; N21a-10),
`derive_containment` (a looping derivation killed at its cap; N21a-12), `egraph_pilot` (only if built; N21a-15).

**Fixtures.** One file per planted defect, each starting with a comment line that states the expected refusal
code and rule, which the script reads; adding a defect is adding a file. Fixtures are synthetic by nature and are
labelled so.

**Machines.** The script runs on both machines. Without a device it runs every CPU step and logs device steps as
skipped; with one it also runs `device_boundary`. It needs no network and fits the default compute envelope.

## Acceptance criteria

- [ ] `scripts/e2e/kernel_toolchain.sh` exits 0 on a clean tree on this Mac and on `trj`, with all M0 steps run (or `device_boundary` skipped with a reason on a host with no device).
- [ ] Every planted defect of the M0 steps is refused by the stage that owns it, with the expected code: hand edit (`check-generated`), dimension violation (`FROB-REF-250`), five dialect defects (`FROB-REF-251`), missing fingerprint (`FROB-REF-606`).
- [ ] Negative control of the script itself: with the expected-refusal comment of one fixture changed to a wrong rule, the script fails on that fixture (the assertions are not vacuous); with a fixture that contains no defect, the script fails because no refusal occurred.
- [ ] The log exists at `target/e2e-logs/kernel_toolchain/<utc>.ndjson` with a transcript beside it and a final `summary` line; every assertion line can be joined to a known-answer row or a fixture file.
- [ ] Re-running with the same seed yields the same digests and the same assertion count; the checked-in tree is unmodified afterwards (`git status` clean, asserted by the script).
- [ ] Each later step listed above is present as a skip entry naming its bead until that bead lands, and becomes a real step when it does (checked at the M2 conformance wiring).

## Test plan

### Unit tests
- The helper functions this script adds to the shared library (`expect_refusal`, `expect_digest_equal`, `skip_until`) are tested there with fixture envelopes: `expect_refusal_matches_code_and_exit`, `expect_refusal_fails_on_success_envelope`, `skip_until_logs_reason`.
- `fixture_headers_parse`: every file under the fixtures directory has a well-formed expectation line.

### End-to-end script and logging
The script is the deliverable. Every NDJSON line has `ts`, `script` (`kernel_toolchain`), `bead` (the bead that
owns the step), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `skip`, `end`), the exact command
line, exit code, wall time, the envelope's `evidence` block where a `frob` call produced one (claim, class, tier,
determinism, identities, seed), measured values with units and thresholds (digests, node counts, operation
counts, counts of findings), the refusal code, rule and repair for refusals, and on failure the first differing
value and the artifact paths needed to reproduce (scratch tree path, fixture path, emitted file digests). The
final `summary` line gives assertions passed and failed, steps skipped with reasons, and the gates touched (none
directly; the pilot record and the toolchain's kill-gate inputs are named). Kernel fixtures are synthetic; no
private-scene data exists in this script.

### Known answers and negative controls
- KA-525 (CPU half: the emitted `K-cay-step` matches its Rust reference fixtures); KA-526 (the contraction detector text is linted and its planted fused variant refused); KA-533 (select with an infinity; added with the full lint step).
- Negative controls: every fixture; the two controls of the script itself.
- Determinism lanes: the script is run twice on one machine and on both platforms; digests of regenerated files must be equal everywhere.

## Considerations

- The script deliberately duplicates assertions that unit tests already make; its value is the wiring and the outside view, and it is the first thing run after a toolchain pin change (a FrankenSymPy, NVRTC or Metal gateway update).
- Generated-file comparison depends on deterministic derivation; if a pin change legitimately alters arithmetic, the `regenerate` step fails by design and the change is reviewed kernel by kernel, with the affected kernels' device checks marked stale.
- The M2 measurement of the derivation route (the share of kernel arithmetic expressed and emitted, and the speed against hand-written twins) reads this script's logs for its inventory; the kill decision itself is BD-221's.
- Runtime budget: the M0 steps take minutes; the full M2 step list must stay inside the default envelope's hour, so exhaustive tests (for example all 2³² inputs of a function) stay in their own gate lanes and are not called from here.
