## Background

The kernel IR of Spark (`frob-kir`) emits kernel arithmetic for a CPU reference and two GPU backends, all in
IEEE single precision or exact unsigned 32-bit integers. A robot's own controller often runs on a microcontroller
without a floating-point unit, in fixed-point arithmetic. If the project ever exports firmware (a Moonshot epic of
the manufacturing chapter), the control kernels it has derived, typed and tested would have to be lowered to
fixed point. Building a second IR for that would fork every guarantee.

The plan's decision (DESIGN): fixed-point types `q16_16` and `q32_32` are **reserved words** of `frob.kir/1` with
defined wrapping and saturation semantics. No kernel in the library uses them through milestone M5. They exist so
that a later embedded target [M] lowers the same programs without a second IR; the exported artifact would carry
the no-authorization flags (the three flags, all false, that say an artifact authorizes no physical action,
no deployment and no safety claim). The IR's math-mode list already contains `FixedPoint (reserved)`, and the
parser accepts the words while every emitter refuses to lower them (bead N21a-16).

Tier: Moonshot, reserved; priority 4; off every critical path. The project's rule for Moonshot work is that a
paper-scale pilot with a falsifier and a ceiling stated in advance runs before any work is funded. The plan names
no pilot for this row, because it reserves the words and stops. This bead therefore does two things and no more:
it writes the semantics down so that the reserved words mean something definite, and it defines and runs the
smallest pilot that could justify or refuse a lowering, on the CPU only. Lowering to a real embedded target is
not in this bead.

Rejected alternatives: leaving the words undefined until needed (a reserved word with no semantics invites two
incompatible later definitions); a separate fixed-point IR (forks the type checker, the rewrite table and the
certificates); emitting fixed point for GPUs (no use: devices have `f32`).

## Scope

In: the semantics of `q16_16` and `q32_32` (representation, each operator, wrapping and saturation modes,
conversions, dimension typing); a reference interpreter for them; the pilot on one control kernel with its
falsifier; the record of the decision.
Out: any emitter for an embedded target; any use in the kernel library; firmware export; the continued refusal to
lower these types on `batch-cpu` and GPU emitters stays in force (N21a-16).

## Technical approach

**Representation.** `q16_16`: a signed two's-complement 32-bit integer v representing v·2⁻¹⁶ (range
[−32,768, 32,768 − 2⁻¹⁶], resolution 2⁻¹⁶ ≈ 1.53·10⁻⁵). `q32_32`: a signed 64-bit integer representing v·2⁻³²,
stored as two 32-bit limbs (lo, hi) so that the IR's 32-bit integer operators carry it (resolution 2⁻³² ≈
2.33·10⁻¹⁰). Signed values are represented in the IR as unsigned words with two's-complement interpretation,
because the IR's integer arithmetic is unsigned by rule.

**Overflow modes (a property of each operation, chosen in the program, never global).**
- `wrap`: the result is reduced modulo 2³² (or 2⁶⁴); defined, never undefined behaviour.
- `sat`: the result is clamped to the representable range; for `q16_16`, to [0x80000000, 0x7FFFFFFF] as signed.
Every arithmetic operator exists in both forms: `q_add_wrap`, `q_add_sat`, and so on.

**Operators (`q16_16`; `q32_32` is analogous with limb arithmetic).**

| Operator | Definition |
|---|---|
| `q_add`, `q_sub` | integer add or subtract of the raw words, then the overflow mode |
| `q_mul` | the 64-bit signed product of the raw words, rounded to nearest with ties toward +∞ (add 2¹⁵, then an arithmetic shift right by 16), then the overflow mode; built from `mulw`, `mulhi` and sign corrections |
| `q_div` | (a·2¹⁶) / b rounded toward zero, with division by zero a build-time refusal when b's range includes zero and a saturating result otherwise by declared mode; implemented by long division in limbs on the CPU reference |
| `q_neg`, `q_abs` | two's-complement negate; `sat` maps the most negative value to the most positive |
| `q_cmp` | signed comparison through the bias trick (xor with 0x80000000, then unsigned compare) |
| `q_from_f32`, `q_to_f32` | host-side only (conversion at the boundary of an exported artifact); round to nearest, saturating; never inside an exported kernel |
| `q_sqrt` | integer square root of the radicand v·2¹⁶ (v·2³² for `q32_32`) by the digit-by-digit method, one result bit per iteration and a fixed iteration count equal to the result width: 24 for `q16_16` (the radicand has up to 47 bits, so the root has 24) and 48 for `q32_32`; exact floor |

**Dimension typing.** A fixed-point value carries a physical dimension exactly as a float does, plus a declared
*scale* (the unit of one least-significant step, for example 2⁻¹⁶ rad): the type checker requires equal dimension
and equal scale for sums, and computes the scale of products. Homogeneity is still decided exactly.

**Reference interpreter.** In `frob-kir`, test-only until a lowering is funded: evaluates programs in mode
`FixedPoint` using 64-bit host integers as the oracle for the limb forms.

**The pilot (paper scale, CPU only, one engineer-week at most).**
- Object: one already-derived control kernel that a microcontroller would run: a geometric proportional-derivative
  joint controller for one revolute joint represented as a unit complex number (cosine, sine), with gains and
  limits from a reference actuator card.
- Procedure: express the kernel in mode `FixedPoint` (`q16_16` with declared scales), run it in the reference
  interpreter against the `f32` kernel on 10⁶ states sampled over the joint's declared operating range, and
  compute the worst-case and root-mean-square difference in commanded torque as a fraction of the actuator's
  continuous torque; count saturation events.
- **Ceiling, stated first:** a fixed-point controller can at best match the `f32` controller to within its
  resolution; the benefit sought is only that the exported kernel is the same program, not a faster or better one.
- **Falsifier:** the pilot fails if the worst-case torque difference exceeds 1% of continuous torque anywhere in
  the operating range, or if any saturation event occurs inside the operating range, with `q16_16`; it is then
  repeated once with `q32_32`, and if that also fails the row is closed: fixed-point lowering is not funded and
  the firmware epic must carry floats or an external toolchain.
- **Kill and fallback:** on failure, the reserved words stay reserved and unlowered (the state of record); nothing
  else in the project changes.

**Decision record.** One record in the pilot register `crates/frob-conformance/registry/pilots.toml` (schema
`frob.gauntlet.pilot/1`, N38a-09; the program has one pilot register, so no private file), registered with its
protocol hash before the first comparison runs, under the next free identifier the register assigns (DESIGN:
proposed `PILOT-KIR-01`, a new set): mechanism "fixed-point lowering of `frob.kir/1`", tier [M], the protocol
(kernel, operating range, 10⁶ states, seed), the falsifier, the ceiling, the fallback (the reserved words stay
unlowered) with `fallback.kill_gate = "to-register"` (the plan names no kill gate for this row), the cost; then
the result: the measured differences, saturation counts, the verdict in the register's words (`falsifier-rejected`,
reported as "fund a lowering study"; or `falsifier-holds`, reported as "row closed"; the record's status follows
it), and the commit.

## Acceptance criteria

- [ ] The semantics above are written in `crates/frob-kir/CONTRACT.md` under "reserved fixed-point types", and the reference interpreter implements every operator in both overflow modes.
- [ ] Known-answer arithmetic passes: in `q16_16`, 1.5 × 2.25 = 3.375 exactly (raw 0x00018000 × 0x00024000 → 0x00036000); 32,767.5 + 1.0 wraps to −32,767.5 in `wrap` and clamps to 32,768 − 2⁻¹⁶ in `sat`; `q_sqrt(4.0)` = 2.0; `q_mul` of the two smallest positive values (raw 1 × raw 1 = 2⁻³², far below half a step) rounds to zero.
- [ ] Limb forms of `q32_32` match 64-bit host integers on 10⁶ random operand pairs per operator.
- [ ] Emitters still refuse to lower a `FixedPoint` program for `batch-cpu`, CUDA and Metal (the test of N21a-16 is unchanged and green).
- [ ] The pilot is registered in `crates/frob-conformance/registry/pilots.toml` before it runs, and recorded there with its measured worst-case and root-mean-square torque differences and saturation counts, and a verdict by the stated falsifier; the register's tests (`cargo test -p frob-conformance pilots_registry`) pass on the record.
- [ ] Negative control: a fixed-point kernel with one scale declared wrong (2⁻¹⁵ where 2⁻¹⁶ is meant) is rejected by the scale check; a planted `wrap` where `sat` is required produces a sign flip at the range edge that the pilot's comparison catches.

## Test plan

### Unit tests (`cargo test -p frob-kir fixed_point`)
- `q16_mul_exact_case`: 0x00018000 × 0x00024000 → 0x00036000.
- `q16_add_wrap_and_sat`: 0x7FFF8000 + 0x00010000 → wrap 0x80008000; sat 0x7FFFFFFF.
- `q16_neg_most_negative`: `q_neg_sat(0x80000000)` = 0x7FFFFFFF; `q_neg_wrap` = 0x80000000.
- `q16_mul_rounding_ties`: raw 1 × raw 0x8000 (2⁻¹⁶ × 0.5) → 2⁻¹⁷ is a tie → rounds toward +∞ to raw 1; raw −1 × raw 0x8000 → −2⁻¹⁷ is a tie → rounds toward +∞ to raw 0.
- `q16_sqrt_floor`: `q_sqrt` of 4.0 (raw 0x00040000 → 0x00020000), 2.0 (→ raw 92,681, the floor of 1.41421…·2¹⁶), 0, and the largest value 0x7FFFFFFF (→ raw 11,863,283 = 0xB504F3, a 24-bit root; a 16-iteration variant is caught here).
- `q16_cmp_signed`: −1.0 < 1.0 through the bias trick.
- `q32_limbs_match_i64`: add, sub, mul, compare on 10⁶ pairs.
- `q_scale_mismatch_rejected` (negative control); `q_dimension_checked`: adding metres to radians in fixed point → `FROB-REF-250`.
- `fixed_point_not_lowered`: emitters refuse.

### End-to-end script and logging
`scripts/e2e/kir_fixed_point_pilot.sh` (owned by this bead; sources the shared end-to-end helper; runs only the
test binary and a small `frob-kir` example program, since no verb reaches fixed point by design). Steps:
`semantics` (`cargo test -p frob-kir fixed_point`), `pilot` (`cargo run -p frob-kir --example fixed_point_pilot --
--seed <s> --states 1000000`, the 10⁶-state comparison with an explicit seed, first with `q16_16` and, if that
fails, once with `q32_32`), `controls` (the wrong-scale kernel and the planted `wrap`, each of which must be
caught), `record` (`cargo test -p frob-conformance pilots_registry` on the register entry). Writes
`target/e2e-logs/kir_fixed_point_pilot/<utc>.ndjson` with a transcript beside it. Logged per line: `ts`, `script`,
`bead` (`N21a-26`), `step`, `event`, the exact command line, exit code, wall time, the evidence block (claim Design
comparison, class Tested, tier host, determinism D0, seed), the worst-case and root-mean-square torque differences
with units (fraction of continuous torque) and the 1% threshold, the saturation count against the threshold 0,
and on failure the state with the largest difference and the fixture path. The final `summary` line carries the
verdict and the register status.

### Known answers and negative controls
- Known answers: the arithmetic cases above.
- Negative controls: the wrong scale; `wrap` in place of `sat`.
- Determinism: integer arithmetic; byte-identical on every platform (class D0).

## Considerations

- This is the lowest-priority bead of the unit and may never be executed. It exists so that the reserved words have one meaning and so that the question "should firmware share the kernel IR" has a defined, cheap test.
- An exported fixed-point kernel is an exported artifact: it would carry the no-authorization flags and a claim product no stronger than `Tested`, and it is not a safety-rated controller.
- Timing, interrupts and sensor quantization on a real microcontroller are outside the IR entirely; a passed pilot says only that the arithmetic can be shared.
- If the firmware epic is never funded, the only cost carried by the rest of the project is two reserved words in the parser.
