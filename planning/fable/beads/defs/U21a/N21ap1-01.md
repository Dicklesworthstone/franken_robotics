## Background

Spark's execution model (DESIGN) builds, at environment creation, a static **step plan**: an ordered list of
launches with fixed grid sizes, built once per shape class. Every backend runs the same plan: `batch-cpu` with Rust
functions, CUDA as a captured launch graph, Metal as encoded batches. The plan is backend-neutral and a backend
only *realizes* it (it rounds thread-group sizes to its execution width and chooses block sizes); the plan's
identity names no device, slot or shard. Nothing in a running environment may change a shape (ADR-SPARK-04), which
is what keeps launch graphs static.

The record that writes this plan down, `frob.stepplan/1`, was drafted inside the CUDA backend's capstone bead
(BD-172). Many beads need only the record and its validation, not a working CUDA step: the Metal backend, the
statistics data-flow check of the kernel classes (N21a-22), the no-wrap bound for device counters (N21c-39), the
batch-independence audit over step plans (N35-14), the placement record (N21b-28), and the lockstep step on
`batch-cpu`. Holding the record in the CUDA capstone made every one of them wait for the whole CUDA backend. This
bead is that record, its builder and its validation, in `frob-kernels`, with the CUDA realization left to BD-172.

Two identities are kept apart. `StepPlanId` is the content hash of everything numerical that shaped a step; its
descriptor, field registry and hash belong to N16a-03 in `frob-dyn`. This record carries that identity as a
digest supplied by its builder's caller; `frob-kernels` does not recompute it and does not depend on `frob-dyn`
(which depends on `frob-kernels`). Tier: Solid.

## Scope

In: the type `StepPlan` in `frob-kernels` (the launch record; not to be confused with the numerical descriptor of
the same short name in `frob-dyn`, N16a-03) and its schema `frob.stepplan/1`; its canonical bytes and round trip;
the builder behind `KernelBackend::plan` (BD-014), replacing the M0 flat list; validation of every launch at
construction (bindings through N21b-01's binding rules, epochs, stage order, resource totals against the backend
limits from N21a-18's metadata); the realization block a backend attaches without changing the backend-neutral
bytes; the per-launch read and write slab sets that later checks consume; the schema registration for
`frob schema frob.stepplan/1`; tests; the `stepplan` step of the kernel toolchain script.

Out: the `StepPlanId` descriptor, its field registry and hash (N16a-03, a dependency); the manifest, stage
signature, footprints and the binding rules themselves (N21b-01, a dependency); the CUDA realization, launch-graph
capture, pools and receipts (BD-172, which depends on this bead); the Metal realization (BD-174); the statistics
data-flow refusal ("a `stat` output reaches state"), which N21a-22 adds to plan construction over this record's
slab sets; the chunk-length rule from the 250 ms cancellation target (N21b-22), which fills the `chunk` field;
the per-counter no-wrap bounds (N21c-39), which fill the `bounds` field; the batch-independence audit (N35-14).

## Technical approach

**1. The record (DESIGN; schema `frob.stepplan/1`).**

```text
header    schema, step_plan_id (32-byte digest from the caller, N16a-03), shape class (capacities: n_v, links,
          depth, samples, contacts, rows, actuators; sensor and policy layouts; contact law; precision profile;
          lockstep iteration count), step profile (lockstep | strict), h (a rational number of seconds),
          world-steps per control interval d, Newton iterations and tolerance
kernels   per stage: kernel name, KernelId, class, CPU reference symbol
launches  ordered list; per launch: stage, kernel id, logical grid (worlds × lanes per world),
          argument bindings (slab, access read | write, footprint), epoch read, epoch written
chunk     control intervals per chunk; the rule that set it (`fixed` until N21b-22 supplies its rule)
bounds    per histogram or counter: the largest number of increments one bin can receive in a chunk (empty until
          N21c-39)
resources totals from kernel metadata: buffer arguments per kernel, thread-group bytes, operation counts
realization (not part of the backend-neutral bytes) backend family, rounded thread-group sizes, block sizes
```

**2. The builder.** `StepPlan::build(stages: &[Stage], class: &ShapeClass, header: PlanHeader) ->
Result<StepPlan, Refusal>` is what `KernelBackend::plan` calls on every backend. Steps:
1. Order launches by stage order, then by the stage's declared kernel order; a stage list out of the batched
   step's stage order is refused with the two stages named.
2. Fix each logical grid from the shape-class capacities: worlds × lanes per world, where lanes per world is a
   literal or a capacity constant of the manifest (never read from a buffer).
3. Validate every binding with N21b-01's binding rules (footprint inside the slab range, no undeclared alias,
   access matching the signature); a failure is refused with the kernel, argument and slab named.
4. Validate epochs over one control interval: a launch that reads a slab at epoch k must follow, in plan order, a
   launch that writes it at epoch k, or the slab must be a chunk input at the committed epoch; no slab is written
   twice at the same epoch unless the later writer also reads it (a declared read-modify-write chain); a slab
   tagged `committed` is written only by the launch the header designates as the commit launch.
5. Sum resource totals from each kernel's metadata block (N21a-18) and refuse a plan in which any kernel exceeds
   the target backend's limits (for Metal, more than 31 buffer arguments), naming the field, value and limit.
6. Record the per-launch read and write slab sets, the input of N21a-22's statistics data-flow check and of
   N35-14's audit.

**3. Canonical bytes.** Written with the canonical writer of `frob-core` (sorted keys, rationals as reduced
integer pairs, integers above 2⁵³ as strings). The backend-neutral bytes exclude the `realization` block; two
backends realizing one plan produce identical backend-neutral bytes. The record hash (BLAKE3 over those bytes,
domain tag `"frob.stepplan.record/1"`) identifies the record; it is not `StepPlanId`, which hashes the numerical
descriptor only.

**4. Where the record lives.** In the environment for its lifetime (it is never rebuilt while the environment
runs); written beside every run's receipts as an artifact; cited by its record hash and its `step_plan_id` in every
chunk receipt.

## Acceptance criteria

- [ ] `frob.stepplan/1` is registered; `frob schema frob.stepplan/1 --json` prints it; a record built for the self-test stage list round-trips byte for byte.
- [ ] `KernelBackend::plan` on `batch-cpu` builds its plan through this builder; the M0 flat list is gone.
- [ ] For a ten-stage fixture stage list shaped like the batched step (synthetic kernels, labelled `synthetic`, with the reference quadruped's capacities: 18 degrees of freedom, contact capacity 32, row capacity 160, decimation 10) at 8,192 worlds, every launch's logical grid equals worlds × lanes per world from the manifests, and launches are in stage order. (The real stage list is BD-159's, which builds its plan through this builder.)
- [ ] Planted plans are refused at construction, each naming what is wrong: a footprint outside its slab; an undeclared alias; a read at epoch k before any write at epoch k; two writes at one epoch without a read-modify-write chain; a stage list out of order; a kernel with 32 buffer arguments for Metal.
- [ ] The same plan realized for two backends has identical backend-neutral bytes and record hash, and differs only in the `realization` block.
- [ ] Through the `frob-dyn` integration test, the record's `step_plan_id` equals N16a-03's hash of the descriptor and changes when h, d, the iteration count, a `KernelId` or a capacity changes, and not when the device, slot count or shard count changes.
- [ ] The kernel toolchain script's `stepplan` step exits 0 and writes its structured log.

## Test plan

### Unit tests (`cargo test -p frob-kernels stepplan`)
- `stepplan_roundtrip`: build, write, read, compare bytes.
- `stepplan_launch_order_is_stage_order`; `stepplan_out_of_order_stage_refused`.
- `stepplan_grid_from_capacities`: 8,192 worlds × 1 lane → 8,192; 8,192 worlds × 32 lanes → 262,144.
- `stepplan_rejects_bad_binding`: a footprint outside its slab; an undeclared alias (each through N21b-01's rule, the refusal naming kernel, argument and slab).
- `stepplan_epoch_read_before_write_refused`; `stepplan_double_write_refused`; `stepplan_rmw_chain_accepted`; `stepplan_commit_slab_single_writer`.
- `stepplan_resource_limit_metal`: 31 buffer arguments accepted, 32 refused for Metal and accepted for CUDA.
- `stepplan_realization_excluded`: two realizations, equal backend-neutral bytes and record hash.
- `stepplan_slab_sets_exposed`: the read and write sets of each launch equal the bindings.
- In `frob-dyn` (`cargo test -p frob-dyn stepplan_record_id`): `stepplan_id_hash_inputs` (each hashed field changes the id; device, slot count and shard count do not), checked through the record built for the ten-stage fixture with N16a-03's descriptor of the reference quadruped.
- Property test: for random stage lists over the self-test kernels with random bindings, the builder accepts exactly the plans whose bindings and epochs satisfy the rules (ground truth from a brute-force checker).

### End-to-end script and logging
`scripts/e2e/kernel_toolchain.sh` (bead N21a-25), step `stepplan`, added by this bead to the script's M2 list:
runs `cargo test -p frob-kernels --test stepplan_record -- --nocapture`, which builds the plan of the self-test
stage list and of the ten-stage fixture on `batch-cpu`, writes each record to the scratch
directory and its digest to the result file; the step then validates each record with
`frob schema frob.stepplan/1 --json` and the canonical reader, and builds the six planted plans, expecting each
refusal. Logged per line: `ts`, `script`, `bead`, `step`, `event`, the exact command line, exit code, wall time,
the record hash, `step_plan_id`, launch count, per-launch grid, resource totals against limits, and for each
planted plan the refusal with the kernel, argument, slab or epoch named; on failure the first launch that differs
from the expected plan. The final `summary` counts assertions.

### Known answers and negative controls
- Grid sizes: 8,192 × 1 = 8,192 and 8,192 × 32 = 262,144 logical lanes.
- Metal's argument limit: 31 accepted, 32 refused (FACT: `ft-kernel-metal` `MAX_ARGUMENTS`).
- Negative controls: the six planted plans; a builder mutant that includes the `realization` block in the backend-neutral bytes is caught by `stepplan_realization_excluded`; a mutant that reads a lane count from a buffer is refused (grid from capacities only).
- Determinism: the builder is a pure function of stages, shape class and header (class D0); the record bytes are identical on Linux and macOS and in debug and release.

## Considerations

- The statistics data-flow check is deliberately not here: it needs the kernel classes (N21a-22), and N21a-22 runs it inside this builder once it lands; until then a plan containing `stat` kernels is accepted with the check recorded as `not-run` in the record's validation list.
- Two types named `StepPlan` exist (the descriptor in `frob-dyn`, the launch record here); documentation and the schema name (`frob.stepplan/1` for this record, `frob.stepplan.id/1` as the descriptor hash's domain tag) keep them apart.
- If a later backend needs a launch shape the record cannot express (for example the fused per-world plan of N21c-23), the schema version is raised; the backend-neutral rule stays.
