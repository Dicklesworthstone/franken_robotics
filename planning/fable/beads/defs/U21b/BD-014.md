## Background

Spark is the subsystem between a derived kernel and a device result. Its first artifact is the seam every tier is
driven through: a trait that says how a set of kernels is compiled, given buffers, turned into a static list of
launches, launched, read back and receipted. Three implementations will exist: `batch-cpu` (Rust symbols, in the
core), CUDA (`spark/frob-spark-cuda`, an annex workspace) and Metal (`spark/frob-spark-metal`, an annex workspace).
This bead builds the trait, the receipt type and the first implementation, `batch-cpu`, plus the harness that runs
one kernel on any backend. Everything later in Spark (the IEEE probe, the CPU-versus-device check, the placement
planner, the device backends) is written against this seam.

Why a trait in the core and backends in annexes (ADR-SPARK-01, DESIGN). The project has an owner mandate for CUDA
and low-level Metal, and the suite's doctrine forbids in-process foreign kernels in production paths. Both are met
by keeping the core workspace `unsafe_code = "deny"` with Franken-only runtime dependencies and no GPU crate
(INV-SPARK-01), and placing each GPU backend in its own annex workspace with its own lockfile and a registry of
unsafe capsules, linked with the core only in the `apps/` workspace. The trait therefore names no GPU type.
Owner ratification of this arrangement is OPEN-SPARK-1; until it is ratified every device result that reaches an
agent carries the exploratory label (the fail-closed default). The label is not a receipt field: it is attached at
the agent boundary as `evidence.device.exploratory` by N21a-02, which reads the decision record at emission, so a
receipt never needs relabelling when the owner decides. Rejected alternatives: `wgpu` as the only layer (hides launch
graphs, allocators and barriers; no doubles on Metal); a third backend through `wgpu` is possible because the
dialect is small, is tier Frontier, is not planned and is not admitted as a dependency; `rust-gpu`, CubeCL and Burn
(alpha or a large dependency tree, in conflict with the Franken-only core); wrapping an incumbent simulator
(anti-goal).

Why `batch-cpu` is a backend and not a special case (DESIGN). FACT: FrankenSim's accelerator doctrine
(`frankensim/docs/ACCELERATOR_DOCTRINE.md`) requires a permanent CPU reference and twelve evidence fields (AE-01 to
AE-12) on any device run. If the CPU path goes through the same trait, one harness drives every tier, the CPU
reference of every kernel is exercised by the same code as its device twin, and a receipt has one shape. The strict
profile of `batch-cpu` (transactional, event-located; bead BD-161) is a different step plan on the same backend,
not a different backend.

Terms. A *kernel* is a manifest, its arithmetic and its sources (bead N21b-01 defines the manifest). A *step plan*
is an ordered list of launches with fixed grid sizes, built once per shape class. A *receipt* is the record a
launch returns. Tier: Solid.

## Scope

In: the `KernelBackend` trait and its companion types in `frob-kernels`; the device receipt with the twelve
evidence fields and the FrankenRobotics fields beside them; the `batch-cpu` backend; the kernel harness; a self-test
kernel; the schema check of INV-SPARK-02 on receipts.

Out: the manifest and the stage signature (N21b-01, a dependency); the shared-dialect prelude and its lint
(BD-013); the kernel IR and emitters (BD-018); the CUDA and Metal v0 backends (BD-015, BD-016); the hardware
fingerprint (BD-029); the arena, leases and cache (N21b-10, N21b-11, N21b-12); the step-plan record
`frob.stepplan/1` in full (BD-172); the placement receipt (N21b-28).

## Technical approach

**Module layout (DESIGN).** `crates/frob-kernels/src/backend.rs` (trait and types), `receipt.rs`, `cpu/mod.rs`
(`BatchCpu`), `harness.rs`, `selftest.rs`; `CONTRACT.md` with the ten sections (purpose, inputs, outputs,
invariants, refusals, determinism class, evidence class of outputs, validity domain, oracles, known gaps).

**The trait (DESIGN; intent, not final signatures).**

```rust
/// Where kernels run. `batch-cpu` implements it with Rust symbols.
pub trait KernelBackend {
    fn compile(&mut self, lib: &KernelLibrary) -> Result<CompiledLibrary, Refusal>;
    fn allocate(&mut self, layout: &BufferLayout) -> Result<BufferSet, Refusal>;
    fn plan(&mut self, stages: &[Stage], class: &ShapeClass) -> Result<StepPlan, Refusal>;
    fn launch(&mut self, plan: &StepPlan, bufs: &mut BufferSet, cx: &Cx<'_>) -> Result<Receipt, Refusal>;
    fn read_back(&mut self, bufs: &BufferSet, slab: SlabId, out: &mut [u8]) -> Result<(), Refusal>;
    fn identity(&self) -> BackendIdentity;      // family, device, driver, runtime, compiler
}
```

- `KernelLibrary`: a set of kernel manifests with their sources (a Rust symbol for `batch-cpu`; dialect text for the
  device backends). `compile` on `batch-cpu` resolves symbols and checks every manifest (N21b-01); on a device it
  compiles or loads binaries.
- `BufferLayout` / `BufferSet`: named slabs with element type, extent and alignment. `allocate` is called once, at
  environment creation; the trait offers no other allocation call, so that "no device allocation after environment
  creation" (INV-SPARK-03) is a property of the interface.
- `Stage`: a named stage of the batched step with the kernel ids it chains and the slabs each argument binds to.
  `plan` validates every binding against the kernel's stage signature and fixes grid sizes from the `ShapeClass`
  capacities. At M0 the plan is a flat list with one bucket; the content-hashed record is BD-172's.
- `launch` runs the whole plan once. `cx` is the asupersync capability context; cancellation is observed at the
  boundary between launches (request, drain, finalize), never inside a kernel.
- `read_back` copies a slab to the host after the launch that last wrote it has completed. At M2 it is narrowed to
  an epoch-fenced lease (N21b-11); the M0 form may only be called between launches.

**The receipt (DESIGN).** Every launch returns one. FACT: the doctrine's twelve fields are, in order: device
identity (AE-01), driver and runtime (AE-02), compiler and backend (AE-03), kernel source hash (AE-04), kernel and
workload identity (AE-05), CPU axes (AE-06), reduction and determinism policy (AE-07), CPU-versus-device comparison
(AE-08), the retained CPU reference (AE-09), cancellation outcome (AE-10), phase attribution (AE-11), and a go or
no-go decision (AE-12). Rule: the field names are copied verbatim from the doctrine file at the pinned FrankenSim
commit; FrankenRobotics never renames or drops one. FrankenRobotics fields sit beside them: placement per stage
(empty until N21b-28), fingerprint digest (empty until BD-029), determinism class claimed and attained, shape-class
capacities, launch count, retries, device seconds and wall seconds (no `exploratory` field: the label belongs to the
envelope, N21a-02). Until FrankenSim's evidence types
have a home for device receipts (upstream work item FD-FSIM-09, priority P3), the type is local with the doctrine's
field names; the switch-over rule is to replace the local type.

On `batch-cpu`: AE-01 is the CPU model, AE-02 the operating-system build, AE-03 the Rust toolchain and
`batch-cpu`, AE-04 the `KernelId`s, AE-06 the worker count and vector width in use, AE-07 "fixed-order trees, no
atomics, class D2", AE-08 `self` (the backend is the reference), AE-09 the Rust symbol of each kernel, AE-10 one of
`completed | cancelled-drained | failed`, AE-11 seconds per phase (compile, allocate, launch, read back), AE-12
`not-assessed` (the doctrine's funding screen, top three kernels at least 50% of wall time and the candidate at
least 15%, is applied by the performance program, not by the harness).

**Schema check (INV-SPARK-02).** `Receipt::validate()` fails if any of the twelve fields is absent. At the agent
boundary a device result must also carry a placement receipt and a fingerprint digest; a result without a current
fingerprint digest is refused as evidence with `FROB-REF-606` (fingerprint missing or changed since admission; exit
code 6; first repair `frob spark fingerprint`). `batch-cpu` harness receipts at M0 are valid records and are marked
`citable: false` until the fingerprint exists.

**`BatchCpu`.** Kernels are Rust functions `fn(&KernelArgs, lanes: Range<u32>)` registered under their `KernelId`.
Buffers are `Vec`-backed slabs aligned to 256 bytes. Launch order is plan order; parallelism over worlds uses a
fixed partition by logical index, so results are placed by index and never by arrival (class D2: identical bits run
to run and across worker counts). Arithmetic is `f32` or `f64` per the manifest's precision profile; no
`mul_add`, no platform transcendental (the lint of BD-013 covers the Rust of this crate).

**The harness.** `Harness::run(backend, kernel, inputs, shape) -> (outputs, Receipt)`: builds a one-stage plan,
allocates, uploads seeded inputs, launches, reads back, validates the receipt. Inputs come from an explicit seed
and world addresses, never from call order. It is the only way tests, `spark.probe` and `spark.check` execute a
single kernel, so a kernel that passes on `batch-cpu` is run on a device by changing one argument.

**Self-test kernel.** `K-selftest` (DESIGN): for each lane i, `out_f[i] = a[i] + b[i]` in `f32` and
`out_u[i] = addw(x[i], y[i])` in wrapping `u32`. It exercises both arithmetic modes, two input slabs and two output
slabs, with padding lanes that hold −0.0 and 0.

**Refusals reachable here.** `FROB-REF-601` device unavailable or lost (exit 6); `FROB-REF-603` kernel compile
failure with compiler diagnostics verbatim (exit 6); `FROB-REF-606` as above. A manifest that fails validation is a
registration error (N21b-01), not a run-time refusal.

**Determinism and evidence.** `batch-cpu` outputs are class D2 (D0 for exact-integer kernels). Harness results are
evidence class `Tested`.

## Acceptance criteria

- [ ] `K-selftest` runs through the harness on `batch-cpu` and returns outputs equal to a scalar Rust loop bit for bit, with a receipt whose twelve evidence fields are all present (seed done-condition, first half).
- [ ] A manifest whose write footprint aliases a buffer it does not declare is refused when the library is compiled, with an error naming the kernel and the buffer; no launch occurs (seed done-condition, second half; validation by N21b-01).
- [ ] `Receipt::validate()` rejects a receipt with any one of AE-01 to AE-12 removed (twelve negative controls).
- [ ] The trait has no allocation entry point other than `allocate`; a compile-fail test shows a kernel cannot allocate.
- [ ] Two runs with 1 and 8 workers give identical output bytes; debug and release builds give identical bytes.
- [ ] Cancellation requested between two launches returns AE-10 `cancelled-drained`; no buffer is left borrowed.
- [ ] `crates/frob-kernels/CONTRACT.md` exists with its ten sections; `xtask check-deps` shows no GPU crate in the core (INV-SPARK-01).
- [ ] The harness is the execution path used by BD-015 and BD-016 for their first device kernel (checked by those beads).

## Test plan

### Unit tests
- `selftest_matches_scalar_loop`: 4,096 lanes, seed 1; `a[i] + b[i]` in `f32` and `x[i] +w y[i]` in `u32`; byte equality with the loop.
- `selftest_wraps`: `x = 0xFFFF_FFFF`, `y = 1` gives 0.
- `receipt_has_twelve_fields`: every AE field non-empty; names equal the doctrine's list read from a pinned copy in `tests/fixtures/` (labelled with the FrankenSim commit).
- `receipt_missing_field_rejected`: for k in 1..=12, deleting AE-k makes `validate()` fail and names AE-k.
- `undeclared_alias_refused`: a manifest declaring write `[0, n)` on `out` whose binding also covers `a` is refused at `compile`.
- `plan_rejects_bad_binding`: a stage that binds an `f32` slab to a `u32` argument is refused by `plan`.
- `worker_count_invariance`: workers 1, 2, 8, 36; identical digests of every output slab.
- `cancel_between_launches`: a two-launch plan cancelled after the first; AE-10 `cancelled-drained`; second launch not run.
- `read_back_only_after_completion`: calling `read_back` during a launch does not compile (borrow), or returns an error where the borrow cannot express it.
- Property test (INV-SPARK-02): any receipt produced by `launch` validates.

### End-to-end script and logging
This bead has no verb of its own: the first user-visible path to the harness is `frob spark check` (N21b-32), and
N21b-32 depends on this bead, so a script here that called that verb could never pass before this bead closes
(DESIGN: the order of work decides where the script lives). Therefore:
- This bead's own end-to-end lane is the integration test `crates/frob-kernels/tests/harness_e2e.rs`, run as
  `cargo test -p frob-kernels --release --test harness_e2e`. It drives `Harness::run` on `BatchCpu` exactly as the
  verb will (seed 1, 4,096 lanes of `K-selftest`), with 1, 2, 8 and 36 workers, and writes one NDJSON line per step
  to `target/e2e-logs/spark_harness_selftest/<utc-timestamp>.ndjson` in the STD-E2E line format (`ts`, `script`,
  `bead` = `BD-014`, `step`, `event`, worker count, wall time, the receipt's twelve evidence fields, the output
  digests, and on failure the first differing lane index and the paths of both output dumps), ending with a
  `summary` line of assertions passed and failed.
- The shell script `scripts/e2e/spark_harness_selftest.sh` is specified here and delivered by N21b-32: it runs
  `frob spark check --kernel K-selftest --backend batch-cpu --key hs-<run> --json` twice and with `--workers 1` and
  `--workers 8`, each run with its own idempotency key (`spark.check` is a `run` verb: a keyless call is
  `FROB-REF-805`, and a repeated key returns the stored result without running), and asserts exit 0, equal output
  digests across the four runs, and twelve non-empty evidence fields in the envelope's receipt. N21b-32's acceptance lists it, so the shell lane of this bead is closed there.

### Known answers and negative controls
- Known answers: wrapping add (0xFFFFFFFF + 1 = 0); `f32` −0.0 + (−0.0) = −0.0 in padding lanes.
- Negative controls: the undeclared alias; the twelve field deletions; a planted worker-order dependence (results
  written by arrival) must change the digest across worker counts and fail `worker_count_invariance`.
- Determinism lanes: twice on one machine; worker counts; debug and release; macOS and Linux (class D2 for the
  `f32` lane where both use correctly rounded addition; D0 for the integer lane).

## Considerations

- OPEN-SPARK-1 (owner; ratification of the annex design; blocks M2 exit): until decided, device results are
  labelled exploratory at the agent boundary (N21a-02, from the ADR-SPARK-01 row of `registries/decisions.toml`).
  The receipt deliberately carries no copy of the label, so that nothing stored must be relabelled when the owner
  decides.
- The trait will be tested hardest by Metal: the gateway's completion is synchronous and takes at most 31 buffer
  arguments per kernel (FACT, `ft-kernel-metal`), so `launch` must not assume asynchronous completion, and
  `BufferLayout` must be able to express a few large packed slabs with offset tables (N21b-05).
- Do not add a per-kernel allocation hook or a "run arbitrary closure on device" escape hatch; either breaks
  INV-SPARK-03 or the manifest discipline.
- A third backend through `wgpu` is Frontier, unplanned and unadmitted; nothing here should preclude it or prepare
  for it.
- Line-count cap of `frob-kernels` (§34) is 26 thousand lines; the backend seam should stay under about 1,500.
