## Background

The project has two machines with different jobs. `trj` (two RTX 4090) is the training tier. This Mac (an M5 Ultra
with 36 CPU cores, an 80-core GPU and 256 GB of unified memory) holds the world bank and large scenes, does proof
and symbolic work, hosts the referee and replay, and is meant to carry a **Metal rollout tier** whose throughput is
a measured number, not a first. BET-09 states the bet: Metal on Apple silicon is a real rollout tier, not a demo;
falsified below 25% of one RTX 4090 at matched settings. The Metal backend is tier Frontier under KILL-METAL: if
GATE-SPARK-04 fails after one optimization pass, or the backend cannot hold run-to-run determinism, Metal becomes a
development and replay tier (single-device debugging, small batches, the viewer), CUDA is the training tier, and
the Mac trains on `batch-cpu` using its 36 cores. The paper-scale pilot that precedes this work is N21b-04.

How Metal is reached (ADR-SPARK-09). Through FrankenTorch's `ft_kernel_metal::compute::Gateway`, which FrankenTorch
calls its sanctioned unsafe boundary. Missing gateway features are upstream work items done in FrankenTorch's
repository (FD-FT-01, priority P1), never a local patch or a second binding; until they land Spark works inside the
gateway's limits. Reason: the gateway is changed where it lives. Alternatives considered and not taken: Spark's own
Metal binding beside the gateway (possible, since the suite's piano renderer binds `metal` directly; not built
without an owner decision, OPEN-SPARK-5, bead N21b-09); `wgpu` as the layer (hides launch graphs, allocators and
barriers); Slang as the kernel language (its Metal target is experimental; revisit when it is not).

The gateway as it exists (FACT, `frankentorch/crates/ft-kernel-metal` 0.1.3, `src/compute.rs`, `src/lib.rs`):
`Gateway::open` returns the process-wide device and command queue; `library` compiles Metal Shading Language under
`MathMode::Safe`, which disables fast math (`library_with` selects otherwise); `Library::pipeline` builds a compute
pipeline and exposes `max_threads_per_threadgroup` and `thread_execution_width`; buffers are `StorageModeShared`
allocations made by `buffer_f32`, `buffer_u32` and `buffer_zeroed`, read by `read_f32`, `read_u32` and `read_u8`
and rewritten in place by `write_f32` and `write_u32`; `Gateway::batch` encodes several kernels in order into one
serial compute encoder of one command buffer, checks read and write declarations for aliases, borrows every output
exclusively until `submit` returns, and returns a `Receipt` with the kernel count and the device's execution time;
the gateway reports `max_buffer_length`, `recommended_working_set_bytes`, `allocated_bytes` and
`max_threadgroup_memory`. State is resident: a buffer persists across command buffers. The `metal` 0.33 binding
under it is deprecated by its maintainers; it is pinned as FrankenTorch pins it and its migration is part of
FD-FT-01.

## Scope

In: this is the capstone of the Metal backend. It integrates the packing scheme (N21b-05), the batch-per-chunk
loop and readback rules (N21b-06) and the commit fence (N21b-07) behind the `KernelBackend` trait; compiles the M2
kernel library through the Metal prelude; creates an environment; runs the ten-stage batched step and rollouts;
returns Spark receipts; wires `--tier gpu-metal` into `sim.run`; and owns the end-to-end script that shows the full
step running on this Mac.

Out: the M0 spike and admission (BD-016, BD-028); the arena planner, leases and kernel cache as shared mechanisms
(N21b-10, N21b-11, N21b-12); the CPU-versus-device check (BD-176); throughput and GATE-SPARK-04 (BD-217); the
watchdog (N21b-24); cancellation (N21b-22); the kill decision (N21b-08); upstream gateway work (FD-FT-01).

## Technical approach

**Trait implementation.** `MetalBackend: KernelBackend` in `spark/frob-spark-metal`:
1. `compile`: expand each kernel's dialect text (shape-class `#define` block, Metal prelude, body), look the
   expanded text up in the kernel cache by its BLAKE3 key, and compile through `Gateway::library` under
   `MathMode::Safe`. A compile failure is `FROB-REF-603` with the compiler diagnostics verbatim. Build one pipeline
   per kernel and read its execution width. Run the start-up canaries (N21b-36); a failure sets the device's
   `double_float` capability to `fail`.
2. `allocate`: take the arena layout (N21b-10), check the total against the device budget before allocating
   anything (the working-set limit less a host reserve, by default 85% of `recommended_working_set_bytes`, about
   189 GiB on this machine; over budget is `FROB-REF-602`, first repair: fewer worlds or a smaller capacity), check
   that no slab exceeds `max_buffer_length`, then allocate every slab once with `buffer_zeroed` and upload tables.
   `allocated_bytes` is recorded; it must not change afterwards (INV-SPARK-03).
3. `plan`: build the static step plan from the stage list of the batched step; validate bindings against stage
   signatures (N21b-01); fix thread-group sizes as multiples of the execution width; refuse any kernel above the
   31-argument limit.
4. `launch`: one chunk as one batch (N21b-06), under the commit fence (N21b-07).
5. `read_back`: under a lease, after completion (rules R1 and R3).

**The step.** The ten stages of the batched step run in the same order as on `batch-cpu`: (1) kinematics down the
tree; (2) collision geometry poses; (3) broad phase by deterministic sort; (4) narrow phase; (5) contact compaction
by count, exclusive scan and write, with overflow flagged; (6) dynamics terms; (7) constraint rows; (8) the solve:
diagonal scaling, then Newton on the convex objective with Cholesky and exact line search, all worlds in lockstep
for a fixed iteration count under per-world `done` masks; (9) integration on the group and the energy ledger;
(10) sensors, observations, rewards and masked resets. Every stage is a named kernel or short chain from the
kernel library, the same dialect text the CUDA backend compiles. No data-dependent control flow crosses worlds; no
floating-point atomics; no grid-wide barrier.

**Receipts.** Every chunk returns a Spark receipt with the twelve evidence fields, device seconds from the device
(rule R4), encode and blocked seconds, dispatches, bytes copied each way, one synchronization per chunk, retries,
the execution width read, the fingerprint digest and `exploratory: true` until OPEN-SPARK-1 is ratified.

**Surface.** `frob sim run --tier gpu-metal` (the verb belongs to its own bead; this bead registers the backend
with the tier name and makes the strict request `strict:gpu-metal` meaningful to the planner).

**Residual limits recorded as known gaps in `CONTRACT.md`.** Synchronous completion (one blocked host thread);
source-only compilation (a warm start recompiles from cached source, so "zero compiler invocations on a warm
start" is reported on Metal as zero *cache misses*, with the recompile time disclosed); no per-kernel timing
outside profiling mode; an uninterruptible wait.

## Acceptance criteria

- [ ] The full batched step runs on this Mac's Metal device through `frob sim run --tier gpu-metal`: the reference quadruped drops, stands and walks under the baseline controller for 10 s of simulated time at 1,024 and at 8,192 worlds, with no world marked `Faulted` (seed done-condition).
- [ ] Two identical runs give identical per-world digests (run-to-run determinism on Metal, class D2).
- [ ] Every stage's kernel on Metal agrees with `batch-cpu` in `f32` inside the class the family holds (byte equality if the probe attained D1; at most 4 ulp per kernel output otherwise), spot-checked here on 10⁴ worlds for one step and checked in full by BD-176.
- [ ] `allocated_bytes` is identical after environment creation and after 10⁵ steps.
- [ ] No kernel binds more than 31 buffers; no slab exceeds `max_buffer_length`; a request above the device budget is refused with `FROB-REF-602` before any allocation.
- [ ] Every receipt is device-timed and carries the twelve evidence fields, the placement fields and the fingerprint digest.
- [ ] A kernel source with a planted grid-wide barrier or a fused multiply-add fails the build (dialect lint).
- [ ] The annex has its own lockfile, a `SAFETY.md` for each registered capsule, and the core still has no GPU dependency (INV-SPARK-01); `CONTRACT.md` lists the known gaps above.
- [ ] Cancellation at a chunk boundary leaves `allocated_bytes` unchanged and the committed epoch readable.

## Test plan

### Unit tests
- `metal_backend_selftest`: `K-selftest` through `MetalBackend` equals `batch-cpu` byte for byte.
- `metal_step_one_world`: one world of the reference quadruped, 1,000 steps, per-stage outputs compared with `batch-cpu` through the harness; class attained recorded per stage.
- `metal_run_to_run_digest`: 1,024 worlds, 2,000 steps, twice; identical digests.
- `metal_allocated_bytes_flat`: counter equal at creation and after 10⁵ steps.
- `metal_budget_refusal_602`: a world count whose estimate exceeds the budget is refused with zero bytes allocated.
- `metal_compile_error_603`: a kernel with a syntax error returns the compiler's diagnostics verbatim.
- `metal_safe_math_mode`: the library is built through `library` (safe), never `library_with` in a fast mode; a build that tries the fast mode for a production kernel fails a test.
- `metal_argument_limit_all_kernels`.
- `metal_cancel_at_chunk_boundary`.

### End-to-end script and logging
`scripts/e2e/spark_metal_full_step.sh`. Steps: `devices` (`frob spark devices --json`: one Metal device with a
current fingerprint); `layout` (`frob spark place --tier gpu-metal --workload Q --worlds 8192 --json`: slab table,
argument counts); `run_small` and `run_large` (`frob sim run --tier gpu-metal --workload Q --worlds 1024|8192
--seconds 10 --seed 1 --json`); `repeat` (the same again, digests equal); `cpu_spot` (`frob spark check --step
--backend gpu-metal --worlds 10000 --steps 1 --json`); `chunks`, `snapshots`, `profile` (as in N21b-06);
`alloc_flat`. Assertions: exit codes; no `Faulted` worlds; digest equality between repeats; device-timed receipts;
flat allocation. Logging through the STD-E2E helper: every `cmd` with command line, exit code and wall time; the
envelope's evidence block (claim, class, tier `gpu-metal`, determinism, identities, seed); `metric` lines for
world-steps per second (logged as data, with decimation; no threshold here), device seconds, blocked seconds,
dispatches, bytes copied, allocated bytes, retries; digests where state is compared; on failure the first differing
world address and step with the snapshot paths. The `summary` line counts assertions. No scene or design contents
are logged.

### Known answers and negative controls
- Known answers: the batched step's own battery on `batch-cpu` is the oracle (a quadruped that drops, stands and
  walks); the M0 spike's result (a kernel matching a Rust loop bit for bit on 10⁶ quaternions) must still hold.
- Negative controls: the barrier kernel and the fused kernel refused at build (CX-221); a run with the commit
  fence disabled under faults diverges (N21b-07); a receipt without device times is not labelled native.
- Determinism lanes: twice on this machine; at 1,024 and 8,192 worlds for the same world addresses (a world's
  digest must not depend on the batch it ran in; the full test is GATE-SPARK-15); Metal against `batch-cpu` in the
  class the probe attained.

## Considerations

- KILL-METAL (decision bead N21b-08; decided at M2): trigger and fallback as stated in the Background. If it fires,
  this backend stays, with the scope of a development and replay tier, and nothing above is wasted.
- RISK-08: launch counts and blocked host time per chunk are the early signals; both are in every receipt.
  Mitigations already in the design: packed slabs and offset tables, one batch per chunk.
- OPEN-SPARK-1 (owner): device results are exploratory until the annex design is ratified. OPEN-SPARK-2 (owner):
  until an envelope is approved a GPU job is limited to one device and one hour, which admits everything here.
- FD-FT-01 switch-over rule: when gateway changes land, move the pin through the compatibility train (move the
  pin, write a new receipt, rerun the admission and parity gates, relock) and re-run INT-FT-01, INT-FT-02,
  GATE-SPARK-02 and GATE-SPARK-04.
- Subnormals: Metal permits flushing and offers no control (FACT); if the probe shows flushing, the family is D2
  for itself and D3 against others and this bead's cross-backend criterion uses the 4-ulp form.
- Memory: on unified memory the CPU's allocations compete for the same pool, hence the 85% rule; the M5 Ultra's
  throughput at very large populations is unmeasured, and "fits" is a statement about memory only.
