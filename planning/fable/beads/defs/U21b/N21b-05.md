## Background

Metal is reached only through FrankenTorch's `ft_kernel_metal::compute::Gateway` (ADR-SPARK-09). Missing gateway
features are upstream work items done in FrankenTorch's repository (FD-FT-01), never a local patch or a second
binding; until they land Spark works inside the gateway's present limits. Five of those limits (FACT, read from
`frankentorch/crates/ft-kernel-metal` version 0.1.3, `src/compute.rs` and `src/lib.rs`) shape how data is laid out
for every Metal kernel:

| Limit today | Consequence for Spark (DESIGN) |
|---|---|
| At most 31 buffer arguments per kernel (`MAX_ARGUMENTS`) | Arrays are packed into a few slabs; kernels index through an offset table in a parameter buffer, as the suite's piano renderer does with its `P[P_*]` slots |
| Buffers bind at offset zero | Slab-relative indexing inside kernels; no sub-buffer views |
| Host data is copied in and out; typed helpers exist for `f32`, `u32` and bytes out (`buffer_f32`, `buffer_u32`, `buffer_zeroed`, `read_f32`, `read_u32`, `read_u8`, `write_f32`, `write_u32`) | Scene fields and tables upload once; 16-bit fields are packed into `u32` words; rings are read by copy |
| Compilation from source only; no function constants; no binary archive | Shape-class constants are `#define` lines prepended to the dialect text; a warm start recompiles from cached source |
| A device has a largest single buffer (`max_buffer_length`; about 167.0 GiB on this Mac) | No slab exceeds it; the arena splits slabs |

The step has dozens of logical arrays (state, caches, rows, contacts, variant and scene tables, rollout storage,
weights, the statistics ring, the two committed slabs, the snapshot slab, the control block). Bound one per
argument, a kernel of the contact solve would exceed 31. This bead is the packing scheme that makes every kernel
fit, expressed so that the **kernel body text is identical on CUDA and Metal** (the one-source rule). Tier:
Frontier, as part of the Metal rollout tier under KILL-METAL (pilot N21b-04, a dependency of this bead and of the capstone BD-174).

## Scope

In: the slab packing convention; the parameter buffer and its offset table; the accessor macros of the shared
dialect; `#define` generation for shape-class constants; packing of 16-bit fields; the per-kernel argument budget
of the M2 library (at most 28 on Metal) and the test that the packed library passes the argument-limit check;
upload of read-only tables.

Out: which slabs exist and their sizes (the arena layout planner, N21b-10); the argument-limit refusal itself
(PO-SPARK-03: in the emitter, N21a-18, a dependency; at manifest registration, N21b-01), which this bead's
packing must pass and must not bypass; the workload record of Q (N36-02, a dependency); batches, receipts and
readback (N21b-06); the commit fence (N21b-07); the kernel cache entry for expanded source (N21b-12); gateway
changes (FD-FT-01).

## Technical approach

**Packing convention (DESIGN; part of the shared dialect, used by both device backends and mirrored by `batch-cpu`
so that one body text serves all).** The arena layout planner (N21b-10) assigns every logical array to one of a
small number of **packed slabs** by element type and access pattern:

- `F_STATE`, `F_CACHE`, `F_ROWS`, `F_TABLES`, `F_ROLLOUT` (`f32`); `U_STATE`, `U_TABLES`, `U_STATS` (`u32`);
  the two committed slabs and the snapshot slab; `CTL` (the control block); `P` (the parameter buffer, `u32`).
- A kernel binds only the packed slabs it touches. The planner guarantees every kernel of the library binds at most
  31 minus a reserve of 3 (DESIGN reserve for `P`, `CTL` and one future argument).
- Inside a packed slab each logical array occupies a contiguous range aligned to 256 bytes; per-world arrays are
  laid out structure-of-arrays: element (world w, index i) of array X is at `off(X) + w·stride(X) + i`.

**Offset table.** `P` holds, for every logical array X, three `u32` words at a fixed slot `P_X`: offset, stride and
extent, all in elements of the slab's type. It also holds the bucket's run-time values that must not force a
recompile: world count, model-variant count, scene-variant count. Kernels read `P` and never write it.

**Accessor macros (dialect prelude, identical expansion on CUDA and Metal).**

```text
AT_F(SLAB, X, w, i)   →  SLAB[P[P_X + 0] + (w) * P[P_X + 1] + (i)]          // f32 arrays
AT_U(SLAB, X, w, i)   →  the same for u32 arrays
EXTENT(X)             →  P[P_X + 2]
U16_LO(word)          →  ((word) & 0xFFFFu)
U16_HI(word)          →  (((word) >> 16) & 0xFFFFu)
```

Indices are unsigned 32-bit; the expression is "buffer plus index" only, as the dialect rules require. A debug
build of each backend adds a bounds assertion that compares the computed index with the slab extent; the
`batch-cpu` twin always checks.

**Shape-class constants.** Capacities of the shape class (`NV_CAP`, `LINK_CAP`, `DEPTH_CAP`, `CONTACT_CAP`,
`ROW_CAP`, `SAMPLE_CAP`, `ACTUATOR_CAP`, the lockstep iteration count, the execution-width multiple) are emitted
as `#define` lines, in a fixed order, prepended to the dialect text before the prelude. Loop bounds in kernels are
these constants or literals (dialect rule 5), so every loop has a known bound at compile time. The expanded text
(defines + prelude + body) is what the kernel cache hashes; on Metal the cache value is that text and its digest,
because the gateway compiles from source only.

**Sixteen-bit fields.** Tables whose natural element is 16 bits (parent indices, level starts, actuator slots,
variant indices) are stored two per `u32` word, low half first, and read with `U16_LO` and `U16_HI`. Shift counts
are literals, as exact-kernel rules require.

**Upload.** Read-only tables and scene fields are uploaded once at environment creation through the gateway's
typed helpers. Model-variant rows are rewritten in place between chunks under a host-write lease (N21b-11).

**Argument limit (PO-SPARK-03).** Resource metadata is a proof obligation, not a comment. The refusal is not
defined here: N21a-18's emitter check refuses a program whose buffer argument count exceeds the backend's limit
(31 on Metal, field `buffer_args`, before anything is compiled, naming the kernel and the count), and N21b-01's
manifest check repeats the comparison at registration. This bead's packing is what makes every real kernel pass
both with the reserve of 3 to spare, and its tests send packed kernels through those two checks, so a packing
path that bypassed them would be caught.

**Size rule.** No packed slab may exceed the device's `max_buffer_length`; the planner splits a slab group into
several buffers when it would (the split point falls between worlds, so `w·stride` indexing is unchanged within a
part and the offset table gains one row per part).

## Acceptance criteria

- [ ] Every kernel of the M2 library binds at most 28 buffer arguments on Metal (31 less the reserve), reported per kernel by a test that reads the manifests.
- [ ] The kernel body text using the accessor macros is byte-identical in the CUDA and Metal builds; only the prelude differs.
- [ ] A synthetic kernel binding 32 packed slabs (labelled `synthetic`), built through this bead's packing path, is refused for Metal by N21a-18's emitter check and by N21b-01's manifest check, and accepted for `batch-cpu` (PO-SPARK-03 negative control: the packing path cannot bypass the limit).
- [ ] Offsets, strides and extents read through `P` reproduce, for 10⁶ random (array, world, index) triples, the element the `batch-cpu` layout holds (byte-equal after upload and readback).
- [ ] Sixteen-bit packing round-trips every value 0 to 65,535 in both halves.
- [ ] Changing the world count or a variant count changes only `P` and triggers no recompile (compiler-invocation counter unchanged); changing a capacity changes the `#define` block and therefore the cache key.
- [ ] A slab group larger than a (test-lowered) maximum buffer length is split and every kernel still reads the right elements.
- [ ] A debug-build out-of-range index is caught by the bounds assertion on `batch-cpu` and named with array, world and index.

## Test plan

### Unit tests
- `offset_table_roundtrip`: build a layout for workload Q (18 degrees of freedom, 13 bodies, C = 32, R = 160) at 8,192 worlds; for each array check `off + w·stride + i` against the planner's map.
- `accessor_macro_expansion_equal`: the preprocessed body under both preludes differs only in address-space qualifiers and the kernel signature.
- `u16_pack_unpack_exhaustive`: all 65,536 values in both halves.
- `argument_budget_per_kernel`: maximum over the library at most 28.
- `packing_path_cannot_bypass_argument_limit`: a `synthetic` kernel binding 32 packed slabs goes through the packing path into N21a-18's emitter and N21b-01's registration; both refuse it for Metal with `buffer_args` 32 against limit 31; the same kernel for `batch-cpu` is accepted.
- `defines_are_ordered_and_hashed`: the `#define` block is stable across runs and its hash changes when `ROW_CAP` changes from 160 to 168.
- `no_recompile_on_world_count_change`.
- `split_slab_group`: with the maximum buffer length set to 64 MiB in a test configuration, a 200 MiB group becomes four parts and reads agree with the unsplit layout.
- `bounds_assertion_fires`: index `EXTENT(X)` is rejected.

### End-to-end script and logging
The packing becomes visible through `frob` only once the Metal backend (BD-174) and `spark.place` (N21b-29) exist,
and both are built on this bead. The shell lane is therefore the `residency` step of
`scripts/e2e/spark_gate09_placement.sh` (bead N21b-31): `frob spark place --tier strict:gpu-metal --workload Q
--worlds 8192 --json` prints the residency map with every packed slab, its size, and the per-kernel argument
counts; the step asserts a maximum of 28 arguments, that no slab exceeds the device's largest buffer, and that the
per-world total is within 5% of the byte model. Before that, this bead's own end-to-end lane is the device
integration test `cargo test -p frob-spark-metal --release --test packing_e2e` on this Mac: it builds the layout of
Q at 8,192 worlds, uploads it through the gateway, reads back 10⁶ random (array, world, index) triples through the
accessor macros in a probe kernel, and writes NDJSON lines in the STD-E2E format to
`target/e2e-logs/spark_metal_packing/<utc-timestamp>.ndjson`: the slab table as `metric` lines (bytes, with the
device limits as thresholds), the per-kernel argument counts (threshold 28), the expanded-source digest, the number
of mismatching triples (threshold 0), and on failure the first mismatching (array, world, index) with both values;
a final `summary` line.

### Known answers and negative controls
- Known answer: the byte model of Q gives about 35 kB per world, so 8,192 worlds are about 0.28 GB of per-world
  slabs; the planner's total must be within 5% of the byte model plus alignment.
- Negative controls: 32 arguments; an offset table with one stride off by one (must fail the 10⁶-triple
  comparison). A kernel that uses a sub-buffer view at a non-zero offset is out of convention; its rejection is the
  dialect lint's pointer-arithmetic rule, N21a-10's control `rule5_rejects_pointer_arithmetic`, which this bead does
  not wait on.
- Determinism: the layout and the expanded source are pure functions of the shape class and the library; identical
  digests on repeated runs and on both hosts.

## Considerations

- RISK-08 (the gateway is synchronous, takes at most 31 buffer arguments, binds at offset zero and compiles from
  source only; medium): this bead is the mitigation for the argument and offset limits. Its cost is one extra
  indexed read of `P` per access, which the compiler usually hoists; the M2 profile measures it.
- FD-FT-01 (upstream, FrankenTorch, priority P1) asks for binding at a byte offset, relief from the 31-argument
  limit, typed buffers beyond `f32` and `u32`, and function constants. Interim posture: this scheme. Switch-over
  rule: re-run INT-FT-01, INT-FT-02, GATE-SPARK-02 and GATE-SPARK-04; the packing may then be relaxed on Metal only
  if the body text stays shared.
- A few large slabs push against the largest-buffer limit; the split rule exists for the M5 Ultra's large-memory
  jobs (a population of 524,288 worlds in the 64 bucket is about 117 GB and fits in one buffer under 167 GiB).
- Keep the reserve: three arguments are cheap insurance against a later stage that needs one more slab.
- Private scene data may be in uploaded tables; logs print sizes and digests, never contents.
