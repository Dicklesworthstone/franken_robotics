## Background

On Metal a rollout chunk is one command buffer. That follows from how FrankenTorch's gateway works today (FACT,
`ft-kernel-metal` 0.1.3): `Gateway::open` returns the process-wide device and command queue; `Gateway::batch`
encodes several kernels in order into one serial compute encoder of one command buffer, checks the read and write
declarations for aliases, borrows every output exclusively until `submit` returns, and returns a `Receipt` with the
kernel count and the device's execution time; `dispatch` and `submit` block until the command buffer finishes.
State is resident: a buffer persists across command buffers. All storage is `StorageModeShared`.

The limits that bind here, each with the consequence the plan draws from it (DESIGN):

| Limit today (FACT) | Consequence |
|---|---|
| Completion is synchronous | One `Batch` per chunk of control intervals; one blocked host thread per device; host work overlaps device work only on other threads |
| One device and queue per process; the queue holds 64 command buffers | One Metal worker per process; no uncommitted command buffer is ever held |
| Shared storage only; no private storage, blit or heap | Readback is a host copy after completion |
| The receipt has a kernel count and device seconds only | Per-kernel timing needs one batch per kernel in a profiling mode |
| The wait cannot be interrupted | A watchdog marks the device stalled and the supervisor restarts the worker (N21b-24) |
| A failed batch is reported and not re-run; its outputs are undefined | The commit fence (N21b-07) |

This bead builds the Metal execution loop inside those limits and implements five of the six **Metal readback
rules** (R2, the commit fence, is N21b-07). The rules exist because unified memory tempts a shortcut that is wrong:
reading live GPU state from the CPU with zero copy. Shared storage must be quiescent before the other processor
reads it (FACT: Apple's documentation), and the data are tiny anyway: a humanoid's integration state is about 540
bytes, so shadowing 256 worlds at 50 Hz moves 6.9 MB/s (CX-229). Fenced snapshots are used on every backend.

Tier: Frontier, as part of the Metal rollout tier (KILL-METAL).

## Technical approach

**The Metal worker (DESIGN).** One thread per process owns the `Gateway`, its compiled `Library`, every pipeline
and every device buffer. Other threads send it typed requests through a bounded channel: `RunChunk`, `Snapshot`,
`WriteRows` (host-write lease), `Profile`, `Shutdown`. Because `submit` blocks, the worker thread is blocked for
the device time of each chunk; policy, logging and ledger work run on other threads. The worker never holds an
uncommitted command buffer and never has more than one in flight, which keeps it far inside the queue's limit of
64.

**One batch per chunk.** For a chunk of k control intervals with decimation d and a step plan of L launches per
world-step, the worker (1) writes the control block in place with `write_u32` (epoch, chunk index, cancel word;
shared storage makes this a plain host write between batches), (2) opens one `Batch`, (3) encodes
k × (policy forward + d × L launches + observation) dispatches in plan order, each declaring the packed slabs it
reads and writes, (4) appends `K-commit` (N21b-07) and then the **dispatch tail**: the snapshot copies requested
for this chunk, which read the newly committed slab and write only the snapshot slab (`K-snapshot` once N29ap1-02
registers it; in this bead's own tests a `synthetic` row-copy probe kernel of the same footprint), (5) calls `submit` and blocks,
(6) maps the gateway receipt into Spark's receipt. No kernel uses a grid-wide barrier (dialect rule 6): a stage
that needs every world to finish before the next begins is two dispatches, which the serial encoder orders.

**Thread groups (rule R6).** The device's thread execution width is read from each pipeline
(`thread_execution_width`), never assumed; thread-group sizes are multiples of it, capped by
`max_threads_per_threadgroup`; worlds of one variant are laid out in runs that are multiples of the same width
(the layout itself is N21b-15's), so lanes of one group share control flow. The width read is recorded in the receipt and compared with the
fingerprint's value; a difference refuses the run with `FROB-REF-606` (fingerprint changed since admission).

**Rule R1: read only after completion.** The host reads a device slab only after the command buffer that last
wrote it has completed and returned its receipt. Under the gateway today that is a compile-time fact: a batch holds
each output by exclusive borrow until `submit` returns (FACT: compile-fail tests in the gateway's `compute.rs`).
Spark's read API takes a `SlabLease` (N21b-11) that can only be minted from a completed receipt, and adds its own
compile-fail tests so the property survives a gateway change.

**Rule R3: no blit to forget, today.** All storage is shared, so no blit and no managed-resource synchronization
exist to be forgotten; snapshots and the statistics ring are read by host copy (`read_f32`, `read_u32`, `read_u8`)
from the snapshot slab and from the previous slot of the double-buffered ring. When private storage arrives through
FD-FT-01, results are blitted to a shared snapshot slab **inside the same command buffer** and read under R1;
managed storage is not used. The read path is written against a `SnapshotSource` trait with one implementation
today (`SharedCopy`) so that the blit variant is an addition, not a rewrite.

**Rule R4: what "native" means.** A run is labelled native on a device only if its receipt carries a completed
command buffer with start and end times from that device (FACT: `Receipt.device_seconds` spans Metal's
`GPUStartTime` to `GPUEndTime`). A receipt without device times cannot support a claim of acceleration; a hybrid
plan may claim acceleration only for stages that ran on the device and returned a device-timed receipt.

**Rule R5: timers cover completion.** Wall timers start before encoding and stop after `submit` returns; no
throughput figure is computed from enqueue time alone. Spark's receipt records, per chunk: encode seconds, blocked
seconds, device seconds, kernel count, dispatches, bytes copied host to device and device to host, synchronization
count (one per chunk), retries.

**Profiling mode.** Because the gateway's receipt has no per-kernel time, the worker's `Profile` request submits
one batch per kernel, attributing device seconds per kernel. It is selected on `sim.run` by the boolean option
`--profile-kernels` (DESIGN; accepted on `--tier gpu-metal` from BD-174, which wires this backend into `sim.run`;
N21a-27 extends it to CUDA and `batch-cpu` and builds the profile record on it; on a tier that does not yet support it the option is refused with
`FROB-REF-802`, exit 3). The option is outside every identity (it enters no `StepPlanId`, state digest or result
identity, and the receipt echoes it). Results from this mode carry `profiling: true`, change no digest, and are
never used for a throughput figure (the extra command buffers are overhead).

**Snapshots and the ring.** The dispatch tail copies chosen worlds' rows into the snapshot slab as the last
dispatches of a batch; the host reads them after completion under a host-read lease, through the `SharedCopy`
implementation of `SnapshotSource`. The statistics ring is double-buffered: the device writes slot e mod 2 during
epoch e while the host reads the other slot, which holds epoch e − 1.

## Acceptance criteria

- [ ] A chunk of k control intervals is exactly one command buffer: the receipt's command-buffer count equals the chunk count over a rollout of 10³ chunks, and the synchronization count is one per chunk.
- [ ] Compile-fail tests show that a slab written by a batch cannot be read before `submit` returns (R1), in Spark's API as well as the gateway's.
- [ ] Every receipt of a Metal run carries device seconds from the device; a planted receipt with device seconds removed is refused the `native` label (R4).
- [ ] Reported throughput uses completion time; a planted timer that stops at enqueue is caught by a test that compares it with the device-timed interval (R5).
- [ ] Thread-group sizes are multiples of the pipeline's reported width, and the width is read at run time (a test with a mocked-up pipeline description is not acceptable: the test reads the real pipeline and checks the arithmetic) (R6).
- [ ] 10⁴ snapshot reads through the dispatch tail (the `synthetic` row-copy probe) return bytes whose host-side BLAKE3 equals that of the same rows read on `batch-cpu` at the same epoch, for runs in a class where bit equality is claimed, and the snapshot path is behind the `SnapshotSource` trait (R3).
- [ ] The worker's `Profile` request submits one batch per kernel. (Selecting it with `--profile-kernels` through `sim.run --tier gpu-metal`, and the option's `FROB-REF-802` on a tier that does not yet support it, are BD-174's criteria: the verb reaches this backend only through BD-174, which depends on this bead.)
- [ ] The profiling mode attributes device seconds to each kernel and changes no state digest.
- [ ] No more than one command buffer is ever in flight (counter), and no uncommitted buffer exists at any await point.

## Test plan

### Unit tests
- `chunk_is_one_command_buffer`: counters over 10³ chunks.
- `read_before_completion_does_not_compile`: `trybuild` compile-fail cases for reading an output slab inside the batch closure and for holding a lease across `RunChunk`.
- `receipt_requires_device_times_for_native`.
- `timers_cover_completion`: wall interval ≥ device interval for every chunk; the planted enqueue-only timer violates it.
- `threadgroup_multiple_of_width`: for the real pipeline of `K-selftest` and of three M2 kernels.
- `control_block_written_between_batches`: epoch and chunk index observed by the first kernel equal the host's values for 10³ chunks.
- `ring_double_buffer_reads_previous_epoch`: a `synthetic` probe kernel writes its epoch number into ring slot e mod 2; the host read during epoch e returns e − 1, for 10³ epochs.
- `snapshot_tail_after_commit`: the tail's probe copy reads the newly committed slab (its rows equal `C[new]`, not `W` mid-chunk) and writes only the snapshot slab (BLAKE3 of every other slab unchanged by the tail).
- `profile_mode_digests_unchanged`.
- `single_inflight_command_buffer`.

### End-to-end script and logging
`frob sim run --tier gpu-metal` exists only with BD-174, which is built on this bead, so this bead's own lane is
the device integration test `cargo test -p frob-spark-metal --release --test chunk_e2e` on this Mac. It drives the
Metal worker directly on a `synthetic` stateful workload (per world, a unit quaternion and an angular velocity
advanced by `K-cay-step` and `K-normalize`, BD-020's kernels, with the probe tail copying 64 worlds each chunk):
10³ chunks of 10 control intervals at 8,192 worlds, then the same with the `Profile` request, then the same twice
more for the determinism lane. It writes NDJSON in the STD-E2E format to
`target/e2e-logs/spark_metal_chunks/<utc-timestamp>.ndjson`: per chunk, encode, blocked and device seconds,
dispatches and kernel count (`metric` lines with units); bytes copied each way; synchronization count against its
threshold of one per chunk; command buffers in flight against the threshold of one; the execution width read and
the fingerprint's value; snapshot digests; the state digests of the profiled and unprofiled runs; on failure the
chunk index and the receipt dump path; a final `summary` line. The shell lane is the `chunks` and `profile` steps
of `scripts/e2e/spark_metal_full_step.sh` (BD-174): `frob sim run --tier gpu-metal --workload Q --worlds 8192
--intervals 1000 --seed 1 --key metal-chunks-r1 --json` and the same with `--profile-kernels` under `--key
metal-profile-r1`, asserting the counters above and that the profiled run's final digests equal the unprofiled
run's.

### Known answers and negative controls
- KA-544 (10⁵ snapshot reads each match the digest emitted for their epoch; zero synchronizations inside a chunk):
  the read path and the zero-synchronization counter are built and tested here; the digest comparison needs the
  in-kernel digest (N29ap1-01) and `K-snapshot` (N29ap1-02), so the Metal half is measured in N21b-26.
- CX-229 (zero-copy CPU reads of live GPU state on unified memory): the negative control is a read of an output
  slab during a batch, which must not compile; CX-221 (grid-wide barrier): the dialect lint rejects it, and a
  planted barrier kernel is refused at build.
- Negative controls: the enqueue-only timer; the receipt without device times; a thread-group size that is not a
  multiple of the width (refused at plan time).
- Determinism lanes: the same chunk sequence twice gives identical state digests (D2 on Metal); with and without
  profiling mode; with snapshot requests on and off.

## Considerations

- RISK-08's early signal is measured here: launch counts and blocked host time per chunk on Metal. Both are receipt
  fields from the first run.
- FD-FT-01 (upstream, P1): asynchronous completion with several command buffers in flight, an interruptible wait,
  per-kernel timing in the receipt, private storage with blits, Metal 4 command allocators, migration from the
  deprecated `metal` 0.33 binding to `objc2-metal`. Interim posture: this bead. Switch-over: re-run INT-FT-01,
  INT-FT-02, GATE-SPARK-02 and GATE-SPARK-04; the profiling mode and the single blocked thread can then be
  retired.
- The number of dispatches per batch can be tens of thousands (60 launches × decimation 10 × intervals per chunk);
  encode cost per dispatch is a first-order term of Metal throughput (pilot N21b-04).
- When another process hangs the GPU, macOS restarts it and aborts every command buffer in flight (FACT: the
  gateway's `lib.rs`); the worker must treat any terminal state other than completed as invalidating every slab the
  batch could write (N21b-07).
- OPEN-SPARK-5 (owner): no second Metal binding beside the gateway without an owner decision.
