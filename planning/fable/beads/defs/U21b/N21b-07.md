## Background

A device can fail in the middle of a rollout through no fault of the program. FACT (`ft-kernel-metal`'s `lib.rs`):
"when another process hangs the GPU, macOS restarts it and aborts every command buffer in flight", and the gateway
reports a failed batch without re-running it, leaving its outputs undefined. If a failed chunk had been updating
world state in place, part of the state would be new, part old, and a retry would diverge from the run that never
failed. The plan's rule (the hazard table of the numerics chapter) is absolute: **a retry restores the whole
committed state**; a retried step that keeps part of its state diverges.

Metal readback rule R2 (DESIGN) is the mechanism: a terminal state other than `Completed` invalidates every slab
the batch could write. The unit of commit is therefore the **chunk**, which on Metal is one command buffer. A chunk
reads its checkpointable state from the *current* one of two **committed slabs** and ends with the kernel
`K-commit`, which writes the new state to the *other*. Only a `Completed` receipt makes the other slab current. On
failure the current slab was never written, so the arena restores from it and resubmits, at most four attempts with
growing waits, then refuses with `FROB-REF-607`. Every retry is counted in the receipt. A replay from the committed
slab is bit-identical because no kernel has data-dependent scheduling.

The same fence serves CUDA (a failed launch or graph replay), teleport and forks (they start from committed
state), leases (the host may read only committed epochs, INV-SPARK-06) and crash-consistent jobs. It is the device
twin of the referee tier's transactional step with its restore set and `commit_epoch` (BD-081). Tier: the protocol
is Solid in design; this bead is labelled Frontier with the Metal tier whose fault seam tests it.

## Scope

In: the definition of checkpointable state for the fence; the two committed slabs and the working copy; the
`K-commit` copy kernel; the epoch flip; the retry ladder; `FROB-REF-607`; retry accounting in the receipt; fault
injection through the gateway's seam; the fence-disabled negative control; the CUDA hook.

Out: in-kernel digests emitted at commit, `K-snapshot`, and replay (BD-203, which extends `K-commit`); leases
(N21b-11); the stall watchdog for a command buffer that never returns (N21b-24); cancellation (N21b-22); the
gate assembly (N21b-26).

## Technical approach

**Checkpointable state (DESIGN).** The slabs a chunk must be able to restart from: configuration, velocity and
anchored cell indices; solver warm starts and contact feature memory; actuator and battery state; clock phase
accumulators and packet queues; controller and policy recurrent state; the control block (its step counter indexes
the random streams; there is no other generator state); scene state the robot can change. Everything else on the
device (kinematic and dynamic caches, rows, contacts, solver vectors) is scratch that every step recomputes from
state, and is not fenced. The list is declared once, in the arena layout (N21b-10), as the `committed` slab group;
a kernel manifest that writes a `committed`-group array outside `K-commit` is refused (stage-signature epoch
fields, N21b-01).

**Slabs.** `C[0]` and `C[1]`, each holding the whole checkpointable state for all worlds; `W`, the working copy the
step plan reads and writes; an index `cur ∈ {0, 1}` and the committed epoch `e`, both held by the host and
mirrored in the control block.

**Protocol (one chunk).**
1. Host writes the control block: `epoch = e + 1`, chunk index, cancel word.
2. First dispatch `K-restore`: copy `C[cur]` → `W`. (On the first chunk after a successful one this is redundant
   but keeps a retry identical to a first attempt: same dispatches, same order, same inputs.)
3. The chunk's control intervals run on `W`.
4. Last dispatch `K-commit`: copy `W` → `C[1 − cur]` and write the epoch word `e + 1` into the slab's header.
5. Submit and wait for the terminal state.
6. On `Completed`: the host sets `cur ← 1 − cur`, `e ← e + 1`. Leases on the old epoch expire (N21b-11). The chunk
   is published.
7. On any other terminal state: nothing is flipped. `W`, `C[1 − cur]`, the statistics-ring slot of this epoch and
   this chunk's rollout segment are treated as undefined. The host waits, then resubmits the identical chunk from
   step 1 with the same epoch number.
8. Attempts: at most four in total. Waits before attempts 2, 3 and 4 grow (DESIGN defaults 10 ms, 100 ms, 1 s;
   configurable; the values in force are in the receipt). After the fourth failure the run refuses with
   `FROB-REF-607` (a launch or command buffer failed after bounded retries; exit code 6; first repair: resume from
   the last committed epoch, which the refusal names together with the fingerprint digest).

`K-restore` and `K-commit` copy raw 32-bit words (class `exact`, D0), so no floating-point canonicalization can
touch a NaN payload or a signed zero. Both copies together move twice the checkpointable state per chunk: for the
reference quadruped about 4 kB per world, 33 MB per copy at 8,192 worlds, well under a millisecond at device
bandwidth against a chunk of tens of milliseconds. An optimization that reads the first step from `C[cur]`
directly and skips `K-restore` is allowed only with identical digests and a paired lower bound of at least 1.03
(the plan's rule for optimizations).

**Why a replay is bit-identical.** Launch order is the plan order; no kernel has data-dependent scheduling; random
draws are functions of (world address, step, stream), and the step counter is restored with the slab; reductions
have fixed shapes. So the retried chunk computes the same bits as the failed one would have.

**Receipt.** Per chunk: attempts, the terminal state of each attempt, waits, device seconds of each attempt (failed
attempts count in every throughput denominator), and the epoch committed. Totals appear in the `frob.placement/1`
row (`retries`).

**Fault injection.** FACT: `ft-kernel-metal` has a fault-injection seam for an aborted command buffer
(`inject_command_buffer_faults`, present in builds with debug assertions). The conformance harness schedules faults
by chunk index from a seeded plan (so a failing schedule is reproducible), including consecutive faults up to
three (recoverable) and four (must refuse). On CUDA the hook is a test-only launch wrapper in the annex that
returns a driver error for scheduled launches.

**Negative control: fence disabled.** A test configuration steps state in place with no committed slabs
(`K-restore` and `K-commit` removed, retry re-running from whatever `W` holds). Under injected faults its final
digests must differ from the unfaulted run, and the test asserts that this mismatch is detected.

## Acceptance criteria

- [ ] With 10³ injected command-buffer faults over a rollout on Metal (never more than three in a row), the final per-world digests equal those of the unfaulted run; the receipt counts every retry (KA-537).
- [ ] Four consecutive faults on one chunk produce `FROB-REF-607` naming the last committed epoch; resuming from that epoch completes and matches the unfaulted run's digests from there on.
- [ ] With the fence disabled, the same fault schedule yields a digest mismatch, and the test detects it (negative control).
- [ ] After a failed attempt nothing the host can lease has changed: reads of the committed slab, the snapshot slab and the previous ring slot return the same bytes before and after the failed attempt.
- [ ] A manifest that writes a `committed`-group array outside `K-commit` is refused at registration.
- [ ] Failed attempts' device seconds appear in the receipt and in the throughput denominator.
- [ ] The same protocol passes on CUDA with scheduled launch errors.
- [ ] `K-restore` and `K-commit` have manifests, CPU twins and rows in `registries/kernels.toml`; on `batch-cpu` the fence runs with a fault hook and gives the same results.

## Test plan

### Unit tests
- `fence_flip_only_on_completed`: terminal states `Completed`, `Error`, `Aborted` (injected); `cur` and `e` change only on the first.
- `retry_is_identical_submission`: the dispatch list, arguments and control block of attempt 2 equal those of attempt 1 (hash comparison).
- `retry_ladder_four_attempts`: faults on attempts 1 to 3 then success commits; faults on 1 to 4 refuse with `FROB-REF-607`; waits recorded equal the configured ladder.
- `committed_slab_untouched_by_failed_attempt`: BLAKE3 of `C[cur]` before and after.
- `commit_copies_bits`: a state word holding a signalling-NaN pattern and one holding −0.0 survive `K-restore` and `K-commit` bit for bit.
- `fence_disabled_diverges` (negative control).
- `batch_cpu_fence_equivalence`: `batch-cpu` with the fence and a seeded fault plan equals `batch-cpu` without faults.
- `scratch_slabs_not_fenced`: corrupting a scratch slab between chunks changes no committed digest (it is recomputed).
- Property test: for random fault schedules with at most three consecutive faults, final digests equal the unfaulted run.

### End-to-end script and logging
`scripts/e2e/spark_gate12_launch_fence.sh` (bead N21b-26), step `commit_fence`: a debug-assertions build runs
`frob sim run --tier gpu-metal --workload Q --worlds 1024 --intervals 5000 --inject-faults seed=7,count=1000 --json`
and the same without faults, and compares final digests; then `--inject-faults consecutive=4` and asserts exit 6
with `FROB-REF-607`. Logged per the STD-E2E helper: fault schedule seed, attempts per chunk, retries total, waits,
final digests of both runs, the refusal envelope (code, last committed epoch, fingerprint digest), and on failure
the first chunk whose digest differs with the paths of both snapshot dumps.

### Known answers and negative controls
- KA-537 (commit fence under injected command-buffer faults: final digests equal those of the unfaulted run; at
  most four attempts with growing waits, then `FROB-REF-607`; every retry counted in the receipt; exact under 10³
  injected faults; negative control: with the fence disabled the mismatch must be detected).
- Metamorphic: moving a fault from chunk i to chunk j changes no final digest; doubling the chunk length changes no
  final digest.
- Determinism lanes: the faulted run twice with the same schedule (identical receipts apart from wall times);
  Metal against `batch-cpu` with the same schedule, in the class the family holds.

## Considerations

- The fault seam exists only in builds with debug assertions (FACT), so the fault tests run a debug-assertions
  build of the Metal annex; the release build's fence is the same code and is covered by the equivalence of the
  unfaulted runs.
- A command buffer that never returns is not handled here: the gateway's wait cannot be interrupted, so that case
  belongs to the watchdog and supervisor (N21b-24), which restart the worker and resume from the last committed
  epoch, the same recovery point.
- Memory: the fence triples the checkpointable state (two committed slabs and the working copy). For the reference
  workloads that is a few percent of the per-world bytes; the arena estimate includes it.
- BD-203 extends `K-commit` to emit the in-kernel state digest for the committed epoch; snapshot reads are checked
  against that digest (10⁵ reads at GATE-SPARK-12).
- RISK-08 and KILL-METAL: a Metal tier that needs frequent retries pays for them in its throughput denominator;
  the retry count is therefore part of GATE-SPARK-04's disclosure.
