## Background

Spark reaches Metal only through FrankenTorch's gateway (`ft_kernel_metal::compute::Gateway`). ADR-SPARK-09: missing
gateway features are upstream work items done in FrankenTorch's repository (FD-FT-01), never a local patch or a
second binding; until they land Spark works inside the gateway's present limits. The governing rule of the program
is that every sibling repository is the owner's own project, so a limitation is fixed in the sibling, under that
repository's own instructions, gates and conventions, and no milestone waits on an upstream change landing: each
upstream item carries an interim posture and a switch-over rule.

OPEN-SPARK-5 is the open question this leaves: **what does Spark do if the admission test INT-FT-01 fails, or until
FD-FT-01 lands; in particular, may a Metal binding of Spark's own be built before the gateway's upstream work
lands?** Owner: the project owner. Blocks: KILL-METAL (bead N21b-08), because an own binding is the one thing that
could change that gate's outcome from outside the gateway. The fail-closed default, in force until the owner
decides otherwise: **no. Spark stays inside the gateway's limits and accepts KILL-METAL's fallback** (Metal as a
development and replay tier; CUDA trains; the Mac trains on `batch-cpu`); a Metal binding of Spark's own is not
built without an owner decision.

Consequence of the default: the Mac may end up a development and replay tier only. An earlier fallback of a direct
binding was withdrawn from the plan; that a direct binding is possible at all (next item) is why this is a decision
and not a technical impossibility.

Facts the owner needs (all from the plan, to be refreshed with measurements):
- It is technically possible: the suite's piano renderer binds `metal` directly (FACT).
- The gateway's limits today: synchronous completion; at most 31 buffer arguments per kernel; binding at offset
  zero; shared storage only; copies in and out through typed helpers for `f32`, `u32` and bytes; compilation from
  source only with no function constants and no binary archive; one device and queue per process with 64 command
  buffers; an uninterruptible wait; a failed batch is reported and not re-run; the receipt has a kernel count and
  device seconds only; the `metal` 0.33 binding under it is deprecated by its maintainers.
- FD-FT-01 (priority P1) asks FrankenTorch for: asynchronous completion with several command buffers in flight; an
  interruptible wait; typed buffers beyond `f32` and `u32`; binding at a byte offset; relief from the 31-argument
  limit; function constants; a binary archive and ahead-of-time compilation; private storage with blits; per-kernel
  timing in the receipt; Metal 4 command allocators; migration to `objc2-metal`. Part of this is wrapping and not
  new binding work: the `metal` 0.33.0 binding already exposes indirect thread-group dispatch and thread-group
  memory length, and is reported to expose blit encoders and binary archives (FACT to recheck).

**The gateway as it exists (FACT, read in source, version 0.1.3) and what Spark does inside each limit.**

| Limit today | Consequence for Spark | Covered by FD-FT-01 |
|---|---|---|
| Completion is synchronous: dispatch and submit block | One batch per chunk of control intervals; one blocked host thread per device | Yes |
| At most 31 buffer arguments per kernel | Arrays packed into a few slabs; kernels index through an offset table in a parameter buffer | Yes |
| Buffers bind at offset zero | Slab-relative indexing; no sub-buffer views | Yes |
| Shared storage only | Readback is a host copy after completion | Not needed |
| Host data copied in and out; typed helpers for `f32`, `u32`, bytes | Scene fields upload once; 16-bit fields packed into `u32` words | Yes |
| Compilation from source only; no function constants; no binary archive | Shape-class constants as `#define` lines; a warm start recompiles from cached source | Yes |
| One device and queue per process; 64 command buffers | One Metal worker per process | Not needed |
| The wait cannot be interrupted | A watchdog marks the device stalled; the supervisor restarts the worker | Yes |
| A failed batch is reported and not re-run | The commit fence | Not needed |
| The receipt has a kernel count and device seconds only | Per-kernel timing needs one batch per kernel in profiling mode | Yes |
| The underlying `metal` 0.33 binding is deprecated by its maintainers | Pinned as FrankenTorch pins it; migration is part of the work item | Yes |

FD-FT-01's switch-over rule: re-run the two gateway admission tests (INT-FT-01, INT-FT-02) and the fidelity and
Metal-throughput gates (GATE-SPARK-02, GATE-SPARK-04).

## Scope

In: the default as an enforced fact; the two contingency branches (admission fails; upstream work pending); what an
owner "yes" would authorize and require; preparing the decision brief with measured evidence; presenting the options with their costs; recording the
owner's decision as an ADR; applying its consequences to the beads it touches.

Out: doing the upstream work (the FD-FT-01 bead, in FrankenTorch's repository under its rules); building any
binding; the Metal backend (BD-174); the KILL-METAL decision itself (N21b-08). This is the one decision bead for
OPEN-SPARK-5.

## Technical approach

**Evidence gathered for the brief.**
1. INT-FT-01's result (BD-016): does the gateway build in the Metal annex, with FrankenTorch's `block` patch
   repeated at the annex root, and run a kernel on this Mac; and INT-FT-02's (BD-028): resident buffers and device
   completion receipts.
2. The pilot's verdict and binding term (N21b-04): the predicted throughput interval against 0.5 M world-steps/s,
   and the share of step time spent in the launch term at central values.
3. Once BD-174 has run: measured launch counts and blocked host time per chunk (the early signal of RISK-08), and
   the share of wall time attributable to each gateway limit (encode per dispatch, the single blocked thread,
   source recompilation on warm start), read from the receipts BD-174's script stored. Before that, the
   per-dispatch encode cost and the commit-and-wait cost from the fingerprint's launch block (N21c-01), and
   GATE-SPARK-04's ratio if it has been measured. This bead does not depend on BD-174, because under option D (the
   gateway fails admission) BD-174 is never built and the decision must still be taken.
4. The status of FD-FT-01 in FrankenTorch's tracker: which parts are wrapping of existing binding features and
   which are new, with an estimate from the people doing that work.

**Options put to the owner.**

| Option | What happens | Cost and risk | Effect on KILL-METAL |
|---|---|---|---|
| A. Default | Stay inside the gateway; FD-FT-01 proceeds at its own priority | None beyond the measured throughput | Decided on the gateway as it is |
| B. Prioritize upstream | The gateway changes of FD-FT-01 that the evidence names (for example several command buffers in flight, per-dispatch cost, a binary archive) are done now in FrankenTorch's repository, under its rules, with file reservations and its gates | Engineering time in a sibling; the switch-over rule must be run (re-run INT-FT-01, INT-FT-02, GATE-SPARK-02, GATE-SPARK-04) | The one optimization pass KILL-METAL allows may be spent on the upgraded gateway |
| C. Own binding | A Spark-owned Metal binding is built in the Metal annex as registered unsafe capsules | A second binding of the same deprecated crate or a parallel migration to `objc2-metal`; a second unsafe boundary to audit; contradicts ADR-SPARK-09, which must then be amended; duplicated maintenance on every operating-system release | Could rescue the tier independently of FrankenTorch |
| D. If INT-FT-01 failed outright | No Metal tier at M2; the Mac runs `batch-cpu`; M2's no-GPU variant applies to the Mac only | The Metal half of several gates is `not run` | KILL-METAL's measurement cannot be made, so N21b-08 records it `not-run` (register outcome `deferred`, reason `INT-FT-01 failed`, revisited at FD-FT-01's switch-over) with the fallback in force for planning; its trigger (a throughput or determinism failure) is not met by an admission failure, so it is not recorded `fired` |

The brief states plainly which option the evidence favours. The plan's doctrine favours B over C: the gateway is
changed where it lives. Option C is authorized only with a written **scope** (which gateway limits the binding
removes) and a **sunset rule** (it is retired when FD-FT-01 lands and its switch-over tests pass). It means a
second unsafe capsule with its `SAFETY.md`, a second code path that every device test must cover, and a divergence
from the gateway that must later be merged upstream or maintained. If the owner chooses C, the deny rule below is
lifted for the named scope only, and a bead set is created for the binding with the same obligations as any
backend (receipts, the CPU-versus-device check, fault and cancellation tests, the fingerprint, the canaries, the
IEEE probe and the commit fence), with the sunset rule recorded beside it.

**Recording.** `docs/adr/ADR-SPARK-OPEN5.md` (the format of N21a-03: headings Status, Decision, Reason,
Alternatives rejected, Enforcement, Governed beads, Revisit when) with the evidence, the owner's choice, the date
and what must be re-run, and a row of `registries/decisions.toml`, the program's one decision file (the file
N21a-03 creates and N21c-34 extends; there is no `registries/owner_decisions.toml`, and N21c-34's registry lint
refuses one): `id = "OPEN-SPARK-5"`, `status = "open" | "no" | "upstream-first" | "own-binding"`, `date`,
`reference`, `scope`, `sunset`, `enforcement = ["metal_annex_single_binding_lint", "no_local_gateway_patch_lint"]`
(DESIGN field values). Option A is `no`, B is `upstream-first`, C is `own-binding`, and D is `no` with the
admission-failed branch below in force. A non-`open` status needs a reference (an owner-authored commit or
record); the status `own-binding` needs `scope` and `sunset`. When the status leaves `open`, the question's row
OPEN-SPARK-5 in `registries/open.toml` (N41-OPEN3) is closed with the same date and reference. The upstream work item's interim posture and
switch-over rule are written beside the row, and the KILL-METAL decision (N21b-08) cites this record. If the choice is C, ADR-SPARK-09 is amended in the same change and new beads are opened for the binding
with their own pilot and unsafe-capsule registration; nothing of option C is built under this bead. If the choice
is B, the FD-FT-01 bead is re-prioritized and split as needed in both trackers.

**Fail-closed behaviour until decided.** The build has no code path that binds Metal outside the gateway; a
dependency lint in the Metal annex fails if any crate other than `ft-kernel-metal` (and what it brings) provides
Metal symbols. Concretely, while the registry state is not `own-binding`, the dependency policy denies `metal` and
`objc2-metal` as direct dependencies of the Metal annex (the deny rule of the routes-not-taken record, N21c-24),
and no patch of the gateway exists in this repository: a lint forbids a `[patch]` entry for `ft-kernel-metal`
other than the one FrankenTorch itself requires at the annex root.

**Branch: the gateway fails admission (option D).** No Metal backend is linked; `spark.devices` lists the Metal
device as `not-linked` with the admission record's reason; the Mac runs `batch-cpu` on its 36 cores; Metal gates
are recorded `not run: INT-FT-01 failed`; the defect is filed upstream under FD-FT-01. No local workaround.

**Branch: admission passes, upstream work pending (options A and B).** Spark runs inside the limits (the middle
column of the table above); KILL-METAL decides the tier on measured throughput and determinism; when FD-FT-01
lands, its switch-over rule re-runs the admission tests and the two gates, and a pass may reopen the kill
decision.

## Acceptance criteria

- [ ] The decision brief exists with the four evidence items, each a measured value or `not yet available` with the bead that will produce it.
- [ ] The owner's decision is recorded as an ADR naming one of the options A to D and as the `status` of the OPEN-SPARK-5 row of `registries/decisions.toml`; OPEN-SPARK-5 is marked decided in the open-question register `registries/open.toml` with the same date and reference.
- [ ] Until that record exists, the annex dependency lint proves there is no second Metal binding, and KILL-METAL (N21b-08) is evaluated under the default.
- [ ] If the decision is B or C, the follow-on beads exist in this graph (and, for B, in FrankenTorch's tracker) with the switch-over rule attached.
- [ ] The honest-status table states the Metal tier's posture in the words of the chosen option.
- [ ] The decision brief exists before the M2 exit review, with the measured leading indicators and the state of the upstream work item, and has been put to the owner (a dated record).
- [ ] With the registry row `open` or `no`, a planted direct dependency of the Metal annex on `metal` fails the dependency check, and a planted local patch of the gateway fails the lint.
- [ ] With admission failed (simulated by a build without the Metal annex), `frob spark devices --json` shows the Metal device `not-linked` with a reason, and the CPU tiers work.
- [ ] Changing the row to `own-binding` without `scope` and `sunset` fails the registry lint.
- [ ] The upstream work item's interim posture and switch-over rule are written beside the row, and the KILL-METAL decision cites this record.

## Test plan

### Unit tests
- `metal_annex_single_binding_lint`: the annex's dependency graph contains exactly one provider of Metal bindings; adding a second (a test fixture manifest) fails the lint. This is the negative control of the fail-closed default.
- `upstream_registry_entry_complete`: the `registries/upstream.toml` entry for FD-FT-01 has its five required things: the change, a priority, the interim posture, the switch-over rule, and one reproducible failing fixture.
- `owner_decision_row_states`: the OPEN-SPARK-5 row of `registries/decisions.toml` parses with each of the four statuses; `own-binding` requires scope and sunset; any non-`open` status requires a reference; a planted `registries/owner_decisions.toml` fails N21c-34's registry lint.
- `no_local_gateway_patch_lint`: a `[patch]` of `ft-kernel-metal` pointing at a local path fails.
- `devices_not_linked_when_admission_failed`: a build without the Metal annex lists the device `not-linked` with the reason.
- `switch_over_rule_lists_four_reruns`: the record names the two admission tests and the two gates to re-run.

### End-to-end script and logging
`scripts/e2e/open_spark5_evidence.sh`: collects the evidence into one JSON document: runs `frob spark devices
--json` and `frob spark fingerprint --device metal:0 --soak 20m --key open5-fp-<utc-timestamp> --json` on this Mac
(a `run` verb, so it carries a key, and the key carries the script run's timestamp so a re-run measures again
rather than replaying the stored envelope; `--device` takes a device identifier, BD-029's row; the post-soak
figures are the ones the pilot N21b-04 uses), reads the pilot's register entry, and, where BD-174's script `spark_metal_full_step.sh` has
stored its receipts, reads them with `frob artifact read <receipt> --json` to extract dispatches, encode seconds
and blocked seconds per chunk, each logged with its receipt identity and age (absent receipts are logged as `not
yet available: BD-174`, never as zero). It also runs `cargo xtask check-deps` on the real
workspace and on the two planted fixtures (a direct `metal` dependency; a local gateway patch), runs `frob spark
devices --json` from a binary built without the Metal annex, and prints the decision row; these steps need no
device. Logged with the STD-E2E helper: each evidence value with
unit and source, the fingerprint digest, and a `summary` stating which evidence items are present. The script
asserts only that the evidence is well formed; the decision is the owner's.

### Known answers and negative controls
- Negative control: the second-binding fixture must fail the lint.
- Negative controls: the planted local patch of the gateway; a registry row authorizing a binding with no sunset.
- The measurements in the brief come from the fingerprint and the throughput gate and inherit their controls.
- Known answer: the upstream registry rejects an entry missing its failing fixture.

## Considerations

- This is an owner decision: the bead is done when the decision is recorded, whichever way it goes. It must not be
  closed by assuming the default silently; the default is recorded as a decision if the owner confirms it.
- Timing: the question falls due before the M2 exit, because KILL-METAL is an M2 decision and the owner's answer is
  one of its inputs.
- Security and supply chain: option C adds an unsafe foreign-interface surface in an annex; each capsule would need
  a `SAFETY.md`, registration, and a size under the capsule rule.
- If Apple's binding landscape changes (the deprecated `metal` crate, `objc2-metal`), FD-FT-01's migration item
  covers it for the gateway; an own binding would have to repeat that work.
- The default trades Mac GPU throughput for a single Metal code path owned where it lives; the cost is bounded by
  KILL-METAL's fallback, under which the Mac still serves the world bank, proof, replay and CPU training.
- A binding of Spark's own would also need the canaries, the IEEE probe and the commit fence re-established on it;
  none of those transfer automatically from the gateway.
- This decision does not block M2: both branches of KILL-METAL have a defined outcome under the default.
