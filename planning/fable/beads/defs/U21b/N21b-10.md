## Background

ADR-SPARK-06 decides that a device run has **one arena per bucket, allocated once**, read by the host only under a
lease, with compiled binaries in a content-addressed cache. The reason is twofold: no allocation in the hot path
(an allocator call inside a rollout is a synchronization point and a source of run-to-run variation), and a memory
footprint that can be computed, admitted or refused before anything runs. A *bucket* is one shape class on one
device: one arena, one compiled kernel set, one step plan, one launch graph. The *arena* is the set of device
buffers that hold every per-world quantity as structure-of-arrays slabs.

The seed bead BD-173 owns the arena, the leases and the kernel cache as integrated device services and records
GATE-SPARK-11. This bead is the backend-independent half of the arena that both annexes and `batch-cpu` share: the
**layout planner**, which turns a shape class and a world count into a concrete, content-hashed buffer layout, and
the machinery that makes "no device allocation after environment creation" (INV-SPARK-03) checkable. It is also
what the Metal packing scheme (N21b-05), the leases (N21b-11), the commit fence (N21b-07) and the residency map
printed by `spark.place` (N21b-29) all read.

Tier: Solid. Crate: `frob-kernels`.

## Scope

In: the slab catalogue; the byte model as exact element counts; alignment; grouping into packed buffers; the
checks against backend limits (argument count, largest buffer, device budget); `BufferLayout`, `LayoutId` and the
residency map as data; the allocation counter interface and the post-creation allocation guard.

Out: allocating on a device and stream-ordered pools (BD-172, BD-173); the Metal accessor macros and offset table
(N21b-05); leases (N21b-11); the time and memory estimator verb `sim.estimate` and its calibration (BD-219: it
calls this planner for bytes); the capacity defaults themselves (OPEN-SPARK-3, N21b-18).

## Technical approach

**Slab catalogue (DESIGN).** Every array the step touches is declared once in `frob-kernels` with: name; group;
element type; per-world element count as an expression in capacities (or a global extent for tables); whether it
is fenced. Groups and their contents, from the plan:

| Group | Contents | Fenced by the commit fence |
|---|---|---|
| `state` | Configuration, velocity, anchors (cell indices and offsets), warm starts, actuator and battery state | Yes (working copy) |
| `cache` | Kinematic and dynamic cache | No (scratch) |
| `rows`, `contacts` | Constraint rows, contact records, solver vectors | No (scratch) |
| `tables` | Model-variant tables, scene-variant tables and the brick directory | Read-only in a rollout |
| `rollout` | Rollout storage for learning | Per segment |
| `weights` | Policy weights and optimizer state | With the learner's commit |
| `stats` | The statistics ring, double-buffered | No; read one epoch behind |
| `committed` | The two committed slabs | They are the fence |
| `snapshot` | The snapshot slab | Read under lease |
| `control` | The control block | Yes |

**Byte model (DESIGN, `f32`; the planner computes exact element counts and this table is its check).** With n
degrees of freedom, b bodies, contact capacity C and row capacity R, per world:

| Term | Bytes | Q: n = 18, b = 13, C = 32, R = 160 | H: n = 35, b = 30, C = 64, R = 320 |
|---|---|---|---|
| Kinematic and dynamic cache | 4·(61·b + 17·n) | 4,396 | 9,700 |
| Mass matrix, Hessian and factor | 12·n² | 3,888 | 14,700 |
| Dense constraint Jacobian | 4·R·n | 11,520 | 44,800 |
| Row records | 48·R | 7,680 | 15,360 |
| Contact records | 96·C | 3,072 | 6,144 |
| State, warm starts, solver vectors, actuator state | estimate | about 4,000 | about 6,000 |
| Total | | about 35 kB | about 97 kB |

So 8,192 worlds of Q are 0.28 GB and of H 0.79 GB. Rollout storage for PPO is 4·T·(observations + privileged
observations + actions + 4) bytes per world: at T = 24 with 48 observations, a 187-ray height scan and 12 actions,
4·24·251 = 24,096 bytes. A model-variant table is about 192 bytes per link: about 12 kB for a 64-link variant and
about 3 MB for 256 variants. The committed slabs and the working copy triple the fenced state.

**Planner algorithm.**
1. Instantiate the catalogue for the shape class, world count, model-variant count, scene-variant count and task
   layouts; compute each array's element count exactly.
2. Assign arrays to packed buffers by element type and group (`F_STATE`, `F_CACHE`, `F_ROWS`, `F_TABLES`,
   `F_ROLLOUT`, `U_STATE`, `U_TABLES`, `U_STATS`, the two committed buffers, the snapshot buffer, `CTL`, `P`).
3. Inside a buffer, place arrays in catalogue order, each at an offset aligned to 256 bytes; per-world arrays are
   structure-of-arrays with stride equal to the per-world element count.
4. For each kernel manifest, count the packed buffers it binds; fail if any kernel exceeds the tightest backend
   limit the layout is being planned for. The limit is an input of the planner (a field of the backend's
   capability record), not a constant of this bead: on Metal it is 28, the gateway's 31 buffer arguments less the
   DESIGN reserve of 3 that the Metal packing bead N21b-05 (which is built on this planner) keeps for `P`, `CTL`
   and one future argument.
5. If any buffer exceeds the device's largest single buffer (from the fingerprint; about 167.0 GiB on this Mac),
   split it between worlds into parts and record the split in the offset table.
6. Sum the bytes and compare with the device budget before anything is allocated: on Metal the working-set limit
   less a host reserve (by default 85% of the limit, about 189 GiB here, because on unified memory the CPU's
   allocations compete for the same pool); on an RTX 4090 a configured usable figure (16 to 19 GB of 24 GB is the
   planning assumption). Over budget is `FROB-REF-602` (the memory estimate exceeds the device budget at admission;
   exit code 6), raised with the fields the refusal registry row (N21-REF) requires: `pointer` the slab class that
   exceeds (`worlds`, `scenes`, `frames`, `rollout`; the class whose bytes are largest when several scale), `observed`
   the total bytes, `required` the budget, and the repairs of that class in the registry's order (for `worlds` and
   `rollout`: fewer worlds, with the largest count that fits computed exactly by the planner and named; a smaller
   capacity; the Mac. For `scenes`: fewer distinct scene variants; a coarser scene; the Mac, never fewer worlds).
   The planner provides the byte figure and the largest-fitting count; the estimator verb (BD-219) and admission
   (BD-173) raise the same code from the same function.
7. Emit `BufferLayout` (buffers, arrays, offsets, strides, extents), `LayoutId` (BLAKE3 of the canonical layout),
   and the **residency map**: for each slab, where it lives (device or host), its size, its group and who may read
   it; the last committed epoch is filled in at run time by the backend.

The layout is a pure function of its inputs: the same inputs give the same `LayoutId` on every host.

**No allocation after environment creation (INV-SPARK-03).** The planner is the only source of allocation
requests, and `KernelBackend::allocate` is the only call that consumes them. Each backend exposes
`allocated_bytes()` (Metal: the gateway's figure; CUDA: the annex's own counter over every allocation call site,
cross-checked with the driver's free-memory query; `batch-cpu`: its slab allocator's counter). After creation the
environment enters a state in which any allocation request is a bug: debug builds abort on it, release builds
count it in `post_creation_allocations`, which the receipt carries and which must be 0. Transient memory for
snapshots and readback is reserved at creation (on CUDA the stream-ordered pool is created with a fixed capacity;
under the OPEN-SPARK-4 fallback transient buffers are part of the arena), so the allocated-bytes figure is flat by
construction.

## Acceptance criteria

- [ ] For workloads Q and H the planner's per-world bytes for the five formula terms equal the table above exactly, and its totals at 8,192 worlds are within 5% of 0.28 GB and 0.79 GB plus alignment and the fence copies.
- [ ] Every array offset is a multiple of 256 bytes; no two arrays overlap; every kernel's binding count is within the limit planned for.
- [ ] `LayoutId` is identical on macOS and Linux for the same inputs and changes when any capacity changes.
- [ ] A request whose total exceeds the device budget is refused with `FROB-REF-602` and zero bytes allocated; the refusal carries the slab-class pointer, the total (`observed`), the budget (`required`), the fingerprint digest and the registry's repairs for that class; for pointer `worlds` the named largest world count plans within budget and one more world does not.
- [ ] With the largest-buffer limit lowered in a test configuration, an oversized buffer is split between worlds and all arrays remain addressable.
- [ ] `post_creation_allocations` is 0 and `allocated_bytes` is constant over 10⁶ steps on `batch-cpu` here, and on each device in N21b-14 (INV-SPARK-03, KA-543).
- [ ] A planted allocation inside a kernel launch path is caught: the debug build aborts and the release counter is non-zero (negative control).
- [ ] The residency map lists every slab with location, bytes, group and readers, and is the data `spark.place` prints.

## Test plan

### Unit tests
- `byte_model_q_and_h`: 4,396, 3,888, 11,520, 7,680, 3,072 for Q; 9,700, 14,700, 44,800, 15,360, 6,144 for H.
- `rollout_storage_bytes`: T = 24, 48 + 187 + 12 + 4 = 251 columns gives 24,096 bytes per world.
- `variant_table_bytes`: 64 links at 192 bytes is 12,288 bytes; 256 such variants are 3,145,728 bytes.
- `alignment_and_disjointness`: property test over random shape classes and world counts.
- `layout_id_stable`: golden `LayoutId` for Q at 8,192 worlds checked in; a capacity change alters it.
- `argument_budget`: with the limit set to 28 (Metal: 31 less the reserve of 3), the maximum bindings per kernel of the Q and H layouts are at most 28; a `synthetic` kernel manifest binding 29 packed buffers is refused with the kernel named.
- `split_at_world_boundary`: split parts begin at whole worlds.
- `budget_refusal_602`: 0.5 M worlds of H against a 16 GB budget is refused (0.5 M × 97 kB is about 48 GB) with pointer `worlds`; the named largest count (below 16·10⁹ / 97 kB ≈ 164,900 worlds, because the fence copies and tables add to the per-world bytes; the test computes the expected count independently from the catalogue) fits and that count plus one does not.
- `budget_refusal_scenes_602`: a scene-variant table set larger than the budget is refused with pointer `scenes` and no "fewer worlds" repair.
- `no_allocation_after_creation`: 10⁶ steps on `batch-cpu`; counter 0.
- `planted_allocation_caught`.
- Property test: total bytes equal the sum of array bytes plus alignment padding, and padding is less than 256 bytes per array.

### End-to-end script and logging
The shell lanes come after this bead, because the verbs that expose the planner are built on it:
`scripts/e2e/spark_gate11_arena_cache.sh` (bead N21b-14), step `alloc_flat`, and the `residency` and `over_budget`
steps of `scripts/e2e/spark_gate09_placement.sh` (bead N21b-31), which print the residency map and the
`FROB-REF-602` envelope through `frob spark place --json`. This bead's own end-to-end lane is the integration test
`cargo test -p frob-kernels --release --test layout_e2e`: it plans Q and H at 8,192 worlds and H at 0.5 M worlds
against a 16 GB test budget, allocates the Q layout on `batch-cpu`, runs 10⁶ steps of the harness workload and
writes NDJSON lines in the STD-E2E format to `target/e2e-logs/spark_layout/<utc-timestamp>.ndjson`: the layout as
`metric` lines (bytes per buffer against the device's largest-buffer limit; total against the budget; each
byte-model term against its expected value), `LayoutId`, the refusal envelope of the over-budget plan, allocated
bytes at creation and at the end with `post_creation_allocations` (threshold 0), and a `summary` line.

### Known answers and negative controls
- KA-543 (allocated device bytes are flat over 10⁶ steps; INV-SPARK-03; exact).
- Known answers: the byte-model figures above; 8,192 homes at 75 MB would be 614 GB, which is why scenes are shared
  variants and never one per world (the planner refuses a per-world scene layout).
- Negative controls: the planted allocation; a layout with one array misaligned by 4 bytes (rejected); a per-world
  scene request (rejected).
- Determinism: the planner is integer arithmetic; identical output twice, across hosts, in debug and release.

## Considerations

- Memory never binds ordinary world counts (one RTX 4090 holds about 0.46 to 0.55 M worlds of Q before rollout
  storage); row capacity dominates the bytes (the dense Jacobian is 24 to 49% of them). The planner must therefore
  make the Jacobian's share visible, since the path-table Jacobian (R·(6 + depth) instead of R·n) is the lever that
  shrinks it once its digests are shown identical.
- The optional hard-contact law forms an R × R operator (102 kB per world of Q, 410 kB of H); it is budgeted
  separately and is not in the default catalogue.
- GATE-SPARK-22 (the estimator within 5% of measured high-water marks) is the performance program's gate on the
  same numbers; a disagreement between this planner and measured bytes is a defect here.
- The split rule matters only for very large populations on the Mac; it must not change any index a kernel
  computes within a part.
- Private data: the residency map prints names and sizes, never contents.
