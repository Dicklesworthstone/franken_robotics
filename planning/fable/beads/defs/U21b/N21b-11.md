## Background

World state lives on the device. The host still needs to look at it (diagnostics, snapshots, telemetry, teleport)
and occasionally to change it (resets issued by the host, admission of a model variant into a free slot). The
tempting shortcut on a machine with unified memory is to read live GPU state from the CPU with zero copy. It is
wrong: shared storage must be quiescent before the other processor reads it (FACT: Apple's documentation), and it
buys nothing, because the data are tiny: a humanoid's integration state is about 540 bytes, so shadowing 256
worlds at 50 Hz moves 6.9 MB/s (CX-229). A host that reads a slab while a chunk is writing it sees a state that no
committed epoch ever contained; a digest, a snapshot or a decision taken from it cannot be reproduced.

DESIGN: a slab is touched by the host only under an **epoch-fenced lease**.

```rust
// DESIGN: intent, not signatures.
pub enum Access { Device, HostRead, HostWrite }
pub struct SlabLease { slab: SlabId, epoch: u64, access: Access }   // valid only while `epoch` is the committed epoch
```

The commit fence (N21b-07) gives the epochs: a chunk writes epoch e and only a completed chunk makes e committed.
This bead builds the lease type, the rules for when each kind may be minted, their enforcement on each backend, and
the refusal for a violation. It carries the invariant INV-SPARK-06: the host reads only committed epochs. Tier:
Solid.

## Scope

In: the lease type and its lifetime rules in `frob-kernels`; minting from the environment's epoch state; the
host-read and host-write rules; enforcement on Metal (borrows), CUDA (run-time epoch checks around stream-ordered
copies) and `batch-cpu`; `FROB-REF-614`; the last-committed-epoch column of the residency map.

Out: the commit fence that advances epochs (N21b-07); the arena layout (N21b-10); device-resident tensor views for
the learning interface with their ownership epochs (BD-193, which builds on these leases); the chunk protocol's
leases on the CPU record side (BD-091, a different lease: a writer's fencing token); the verb that prints the map
(N21b-29).

## Technical approach

**Which slabs a host-read lease may name.** Exactly three: (1) the *current committed slab*; (2) the *snapshot
slab*, after the chunk whose `K-snapshot` filled it has completed; (3) the *previous slot of the double-buffered
statistics ring*. So diagnostics read epoch e − 1 while the device writes epoch e. A request for a host-read lease
on any other slab (working state, caches, rows, the non-current committed slab, the ring slot being written) is
refused.

**When a host-write lease may exist.** Only **between chunks**, and only for the purposes the plan names: resets
issued by the host, and admission of a model variant into a free slot (a write of that variant's table rows).
While a chunk is in flight no host-write lease can be minted. A host write is applied to the current committed slab
and to the tables it names, and becomes visible to the next chunk through the fence's restore step; it bumps a
`host_write_seq` recorded in the receipt, so a replay knows the write happened and where.

**Validity.** A lease carries the epoch at which it was minted. It is valid only while that epoch is the committed
epoch. When a chunk commits, every outstanding lease of the old epoch expires. Using an expired lease, or a lease
whose access kind does not permit the operation, is a violation.

**Enforcement per backend.**
- *Metal.* The lease is the borrow the gateway already enforces: a batch borrows every output exclusively until
  `submit` returns, so a host-read lease is a shared borrow that cannot coexist with a running batch on the same
  buffers, and a host-write lease is an exclusive borrow taken between batches. The lease type is parameterized by
  a lifetime tied to the environment's "no chunk in flight" token; holding a lease across a chunk submission does
  not compile. Compile-fail tests assert it.
- *CUDA.* Completion is asynchronous, so lifetimes cannot express the rule. The lease is checked at run time: every
  host copy is a stream-ordered copy wrapped by `check(lease)`, which compares the lease's epoch with the committed
  epoch and its slab with the three permitted ones, before enqueueing the copy and again when the copy completes.
- *`batch-cpu`.* The same run-time check, so that tests of host-side code behave identically without a GPU.

**Violation.** `FROB-REF-614`: host access to a slab outside its lease. Exit code 6. First repair offered: read the
committed or snapshot slab. The refusal names the slab, the lease's epoch, the committed epoch and the access
requested, and carries the fingerprint digest. Internal code paths that hit it in tests are bugs; the code exists
because verbs that read device state (`telemetry` reads, snapshot export, the learning interface's host views) can
be driven by an agent into asking for a slab that is not readable yet.

**Residency map.** For each slab the environment tracks the last committed epoch at which it was written and the
set of lease kinds currently permitted; `spark.place` prints these beside location and size.

**API sketch (DESIGN).**

```rust
impl Environment {
    pub fn lease_read(&self, slab: SlabId) -> Result<ReadLease<'_>, Refusal>;       // committed | snapshot | previous ring slot
    pub fn lease_write(&mut self, slab: SlabId) -> Result<WriteLease<'_>, Refusal>; // between chunks only
    pub fn read(&self, lease: &ReadLease<'_>, out: &mut [u8]) -> Result<(), Refusal>;
    pub fn write(&mut self, lease: &mut WriteLease<'_>, rows: RowRange, data: &[u8]) -> Result<(), Refusal>;
}
```

## Acceptance criteria

- [ ] A host-read lease can be obtained for the current committed slab, the snapshot slab and the previous ring slot, and for nothing else; each other slab returns `FROB-REF-614`.
- [ ] On Metal, code that holds a read or write lease across a chunk submission does not compile (compile-fail tests); on CUDA and `batch-cpu` the same misuse returns `FROB-REF-614` at run time (INV-SPARK-06).
- [ ] A lease minted at epoch e is refused after the chunk for epoch e + 1 commits.
- [ ] A host-write lease requested while a chunk is in flight is refused; between chunks it succeeds, and the written rows are visible to the next chunk and recorded in the receipt.
- [ ] Reading through a valid lease while the device steps the next chunk returns bytes whose BLAKE3 equals the digest of epoch e − 1, over 10⁴ reads (the data never show a torn or newer state).
- [ ] A planted direct read of the working state slab during a chunk (bypassing the lease API in a test build) yields bytes that do not match any committed digest in at least one of 10⁴ trials on a device, demonstrating why the rule exists (negative control), and is impossible through the public API.
- [ ] The residency map reports, per slab, the last committed epoch and the permitted lease kinds.

## Test plan

### Unit tests
- `read_lease_only_three_slabs`: enumerates every slab of a layout for workload Q.
- `lease_expires_on_commit`: mint at e, commit e + 1, use: `FROB-REF-614` with both epochs in the refusal.
- `write_lease_only_between_chunks`.
- `metal_lease_across_submit_does_not_compile`: `trybuild` cases for read and write leases.
- `cuda_epoch_check_before_and_after_copy`: a commit injected between enqueue and completion of a copy invalidates the copy's result.
- `ring_previous_slot`: during epoch e the readable ring slot holds epoch e − 1's statistics.
- `host_write_visible_next_chunk`: a reset written between chunks takes effect at the next chunk's first step and not before.
- `refusal_614_fields`: slab, epochs, access and fingerprint digest present; exit code 6.
- Property test: for random interleavings of `lease_read`, `lease_write`, `run_chunk`, `commit`, every successful read returns a committed epoch's bytes.

### End-to-end script and logging
Exercised in `scripts/e2e/spark_gate12_launch_fence.sh` (bead N21b-26), step `snapshot_reads` (10⁵ snapshot reads,
each matching the digest emitted for its epoch), and in `scripts/e2e/spark_gate09_placement.sh` (bead N21b-31),
step `residency`. An additional step `lease_violation` runs `frob telemetry` on a slab that is not yet readable and
asserts exit 6 with `FROB-REF-614`. Logged per the STD-E2E helper: command, exit code, wall time, the refusal
fields, epochs, digests compared, and on failure the first read whose digest did not match with its epoch.

### Known answers and negative controls
- CX-229 (live zero-copy CPU reads of GPU state on unified memory) is the planted direct read.
- KA-544 (10⁵ snapshot reads each match the digest emitted for their epoch) is assembled in N21b-26.
- Metamorphic: taking or not taking read leases changes no state digest (reading is free of side effects).
- Determinism lanes: reads at the same epochs on two identical runs return identical bytes.

## Considerations

- The Metal enforcement rests on a FACT about the gateway (exclusive borrows until `submit` returns, with its own
  compile-fail tests). If the gateway gains asynchronous completion (FD-FT-01), borrows no longer cover it and the
  CUDA-style run-time check must be enabled on Metal; the lease API is written so that both mechanisms can be
  active at once.
- A host-write lease is the only way a new model variant enters a running bucket; it writes table rows only and
  cannot change a capacity. A request that would change a shape is `FROB-REF-611` (a shape change was requested
  inside a running environment; first repair: a new bucket).
- Leases must not become a performance problem: a read lease costs an epoch comparison; the copy is the cost, and
  it is charged to the receipt as transfer bytes device to host.
- Security: a lease exposes world state of the caller's own job only; under slot dispatch the row range of a lease
  is restricted to the job's worlds (the daemon's capability scopes decide which).
