## Background

Device kernels are compiled from dialect source at run time: NVRTC on CUDA, the Metal gateway's `library` call on
Metal. Compilation is slow and variable. FACT (`frankensim/apps/instrument-lab/render-gpu`): a compile takes about
5 s on an idle host and can take 15 minutes on a heavily loaded one, and `trj`'s CPU is often heavily loaded; an
incumbent's cold kernel compilation has been reported at about 96 s against a cached start of about 0.9 s. A cache
of compiled binaries is therefore part of the path from an edit to the first GPU step, which is one of the few
differentiators the project still claims.

A cache is also a place where a stale artifact can hide. FACT: the suite's piano renderer caches CUBINs under a key
built from Rust's default hasher over source and options plus the architecture name, written aside and renamed
(`cuda.rs`). The default hasher is not stable across toolchains, and that key does not include the compiler or the
driver. ADR-SPARK-06 decides: compiled binaries live in a **content-addressed cache keyed by the hardware
fingerprint's compiler and driver identities**, so that no stale binary is loaded after a driver change. The plan's
hazard table states the consequence: toolchain and driver changes move code generation, so the kernel cache is
keyed by compiler and driver, and a change re-runs `spark check`.

The seed bead BD-173 integrates arena, leases and cache and records GATE-SPARK-11. This bead is the cache itself.
Tier: Solid.

## Scope

In: the key; the entry format for CUDA and for Metal; lookup with digest verification; write-aside-and-rename;
the size cap and eviction order; the compiler-invocation counter; `FROB-REF-612`; copying the directory between
hosts; the link from a key change to check staleness.

Out: the verbs `spark.cache` and `spark.precompile` (N21b-13); the fingerprint record (BD-029); check currency
(BD-176); supply-chain policy on cache integrity at the installation level (BD-306); the edit-to-first-step latency
measurement that uses the warm path (BD-184).

## Technical approach

**Key (DESIGN).** `key = BLAKE3(expanded dialect text ‖ compile options ‖ prelude version ‖ compiler identity ‖
device architecture ‖ driver version)`, each field length-prefixed in a fixed order.
- *Expanded dialect text*: the shape-class `#define` block, the backend prelude and the kernel body, byte for byte
  as handed to the compiler.
- *Compile options*: the full option list in canonical order (fusion off, no fast math, architecture).
- *Prelude version*: the prelude's own content hash.
- *Compiler identity*: NVRTC's version string on CUDA; the Metal Shading Language compiler and operating-system
  build on Metal; both come from the fingerprint.
- *Device architecture*: for example `sm_89` for an RTX 4090; the Apple GPU family on Metal.
- *Driver version*: from the fingerprint.
Rust's default hasher is not used anywhere in the key.

**Whose identities enter the key (DESIGN).** The last three fields are those of the device that will *load* the
entry. For a device of this host they are its live identity (the fields the fingerprint's identity subset
holds). For a fill made for another host (an architecture target with no device of that architecture visible to
the process) there is no local driver to ask, and an empty or local stand-in would produce keys the target never
computes, so every copied entry would be dead weight. The fill therefore takes a `TargetIdentity { architecture,
compiler, driver }` read from a `frob.fingerprint/1` record of the host that will load the cache (fingerprint
records are receipts and may be copied between machines). Two checks guard it: the record's device architecture
must equal the requested one, and the identity of the compiler library loaded here must equal the record's
compiler identity, because a binary from another compiler must not be stored under the target's key. Either
mismatch, or a fill for an absent architecture with no record given, is `FROB-REF-606` (fingerprint missing or
changed; exit code 6; `pointer` the differing field, `observed` the local value, `required` the record's; first
repair: `frob spark fingerprint` on the target host, then pass its record). Rejected: leaving the driver out of
the key for cross-host fills (the plan's key contains it, and a driver change must change the key).

**Value.**
- CUDA: the CUBIN bytes.
- Metal: the expanded source and its digest, because the gateway compiles from source only (a precompiled binary
  archive is part of upstream work item FD-FT-01). A Metal "hit" therefore means "this exact text was compiled
  successfully for this compiler and driver before": it skips nothing in compile time, but it proves the text is
  the one that was checked, and its recompile time is recorded and disclosed. When FD-FT-01 delivers a binary
  archive the value becomes the archive and the hit skips compilation.

**Entry layout (DESIGN).** `<cache>/<first two hex digits of key>/<key>.bin` and `<key>.meta.json` with: the six
key inputs (or their hashes), the BLAKE3 digest of the value, value size, backend, compile seconds measured when
the entry was made, creation time, last-used time. An entry is written to a temporary name in the same directory,
flushed, and renamed into place, so a crash leaves either no entry or a whole one.

**Lookup.**
1. Compute the key. If no entry exists: miss.
2. Read the value and recompute its BLAKE3. If it differs from the recorded digest, or the metadata does not parse,
   the entry is **corrupt and is treated as a miss**: it is moved aside to `<key>.corrupt` for inspection and never
   loaded.
3. On a hit, load the value and update last-used.
4. On a miss, compile; on success write the entry. Each compile increments `compiler_invocations`, a counter in the
   receipt and in the placement record.
5. If a miss occurs on a host that cannot recompile (no compiler available, or an explicit `--offline` mode), the
   request refuses with `FROB-REF-612`: kernel cache entry corrupt and recompilation unavailable (exit code 6;
   first repair: `frob spark precompile` on a build host, then copy the cache directory). A plain missing entry in
   offline mode is reported with the same code and the detail `missing`.

**Portability.** The directory is content-addressed and holds no absolute paths or host names inside hashed
content, so it may be copied between hosts; an entry is used on another host only if that host computes the same
key, which requires the same compiler, architecture and driver. This bead provides the entry point
`KernelCache::precompile(target: &TargetIdentity, kernel_set)`; the verb `frob spark precompile sm_89` (N21b-13,
built on this bead) wraps it and fills the cache in a process that sees no GPU (the recipe FrankenSim's
`render-gpu --precompile` uses; the driver and NVRTC are loaded at run time, so no CUDA toolkit is needed to
build, and NVRTC compiles without a device). Which host can do this: one where the NVRTC library loads, that is
`trj` itself with its devices hidden from the process, or a Linux build host with NVRTC installed. This Mac
cannot fill a CUDA cache: NVRTC is published for Linux and Windows and not for macOS (FACT to recheck at
INT-CUDA-01); on the Mac the Metal entries are filled, and a request for `sm_89` there is refused with
`FROB-REF-601` (BD-015's rule: a missing driver or compiler library is `FROB-REF-601`, never a panic).

**Size cap and eviction.** The directory is capped at 4 GiB by default (DESIGN; configurable). When a write would
exceed the cap, entries are evicted until it fits, **preferring entries that are cheap to recompile**: ascending by
recorded compile seconds, ties broken by least recently used. Metal source entries are small and are evicted last
among equals. Eviction never removes an entry in use by a live environment (entries are pinned by an in-process
reference count).

**Staleness of the check.** A change of compiler or driver changes every key, so an old binary is never loaded. The
same change makes the CPU-versus-device check stale for those kernels: the cache exposes the (compiler, driver)
pair under which each kernel was last compiled, and the check-currency key (BD-176) includes the same identities,
so the planner sees `check: stale` without any extra bookkeeping.

**Specialized kernels** (survivor specialization, M4) are ordinary entries: another text, another key.

## Acceptance criteria

- [ ] A one-byte change to the dialect text, to the options, to the compiler identity string or to the driver version string each produces a different key and a miss (four cases, KA-536).
- [ ] A warm start of the M2 kernel library on CUDA loads every kernel with `compiler_invocations == 0`; on Metal it reports zero cache misses and records the recompile seconds.
- [ ] A corrupted entry (one byte flipped in the value) is detected by digest, moved aside, treated as a miss and recompiled; with `--offline` the same corruption yields `FROB-REF-612`.
- [ ] A process killed between the temporary write and the rename leaves no partial entry (tested with a kill at 100 random points).
- [ ] With a test cap of 8 MiB and entries of known compile times, eviction removes the cheapest-to-recompile entries first and never an in-use entry.
- [ ] A cache directory filled by `KernelCache::precompile(target, …)` for `sm_89` in a process that sees no CUDA device (on `trj` with `CUDA_VISIBLE_DEVICES` empty, or on a Linux build host with NVRTC and no GPU), with `target` read from `trj`'s fingerprint record, then copied to another path and used on `trj`, gives a warm start with zero compiler invocations. The same fill with a record whose compiler identity differs from the loaded NVRTC's, or with no record, is refused with `FROB-REF-606` and writes no entry. The same through the verb is step `arch_fill` of N21b-14's script.
- [ ] No use of `std::collections::hash_map::DefaultHasher` (or any unstable hasher) in key computation, enforced by a lint in the annex.
- [ ] A compiler or driver identity change changes the (compiler, driver) pair the cache reports for every affected kernel, which is the input BD-176's currency key reads; that the planner then prints `check: stale` is asserted downstream (N21b-31, step `stale_check`), because the planner is built on this bead.

## Test plan

### Unit tests
- `key_changes_on_each_input`: six inputs, each perturbed by one byte: six distinct keys; unperturbed inputs give a golden key checked into the tests.
- `key_field_boundaries`: moving one byte from the end of one field to the start of the next changes the key (length prefixes work).
- `hit_verifies_digest`, `corrupt_entry_is_miss`, `corrupt_entry_offline_refuses_612`.
- `write_is_atomic`: fault injection between write and rename.
- `eviction_prefers_cheap`: entries with compile seconds 1, 5, 60, 600: the 1 s and 5 s entries go first.
- `eviction_spares_pinned`.
- `metal_value_is_source_and_digest`: the stored value equals the expanded text; its digest matches.
- `compiler_invocation_counter`: cold start equals the number of kernels; warm start equals 0 (CUDA).
- `portable_directory`: an entry created under one path is a hit when the directory is mounted at another.
- `target_identity_from_record`: a fill for `sm_89` given a `synthetic` fingerprint record (driver `D1`, compiler equal to the loaded one) produces the keys a device with driver `D1` computes; the same fill with driver `D2` in the record produces different keys; with a compiler identity that differs from the loaded library's, or with no record and no local device of the architecture, the fill is refused with `FROB-REF-606` naming the field and the directory is unchanged.
- Property test: lookup after write of random values returns the same bytes; lookup under any perturbed key input misses.

### End-to-end script and logging
The shell lane is `scripts/e2e/spark_gate11_arena_cache.sh` (bead N21b-14, which comes after the verbs built on
this bead), steps `cold`, `warm`, `perturb_source`, `perturb_options`, `perturb_compiler`, `perturb_driver`,
`corrupt`, `offline`. This bead's own end-to-end lane is the device integration test `cargo test -p
frob-spark-cuda --release --test kernel_cache_e2e` on `trj` and its twin in `frob-spark-metal` on this Mac: a cold
fill of the M2 kernel library, a warm start, the four perturbations, a flipped byte, the offline refusal and, on
`trj`, a fill for `sm_89` with the devices hidden and `trj`'s own fingerprint record as the target identity,
copied to a second path and loaded with the devices visible, writing NDJSON lines in the STD-E2E format to
`target/e2e-logs/spark_kernel_cache/<utc-timestamp>.ndjson`. Both lanes log per the STD-E2E helper:
command, exit code, wall time, `compiler_invocations` with its threshold (0 on warm), hits and misses, keys before
and after each perturbation, compile seconds, the refusal envelope for the offline case.

### Known answers and negative controls
- KA-536 (binary kernel cache: a one-byte change of source, options, compiler or driver identity is a miss; a warm
  start loads every kernel with zero compiler invocations; negative control: a corrupted entry must be rejected by
  digest).
- Negative controls: the corrupted entry; a key computed without the driver version (a test-only variant) must
  produce a false hit after a simulated driver change and be caught by the perturbation test.
- Determinism: keys are identical across hosts for identical inputs; cache presence never changes a result digest
  (cold and warm runs give identical state digests).

## Considerations

- The cache is an integrity boundary: a tampered CUBIN is executable code. The digest check defends against
  corruption, not against an attacker who can rewrite both files; installation-level policy (who may write the
  directory; integrity of copied caches) is BD-306's.
- Cold and warm paths are never averaged: cold compile times are reported separately in every latency figure.
- On Metal, until FD-FT-01's binary archive exists, "warm" still pays compilation; the disclosure block says so
  (`cache state: warm, recompiled from source`).
- RISK-48 (a driver, system or binding update changes kernel results): keyed entries plus stale checks are the
  mitigation; the early signal is a fingerprint change.
- Disk: 4 GiB holds thousands of CUBINs of this size; the cap exists so that survivor specialization at M4 cannot
  grow the directory without bound.
