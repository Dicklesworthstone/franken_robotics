## Background

GATE-SPARK-11 (Known answer, M2, TARGET) is the gate of the device arena and the binary kernel cache: allocated
device bytes are flat over 10⁶ steps; a warm start loads every kernel with zero compiler invocations; each cache
control of the chapter's known-answer table is caught. It measures two design decisions. First, one arena per
bucket allocated once, with no device allocation after environment creation (INV-SPARK-03): an allocation in the
hot path is both a synchronization point and a leak risk. Second, compiled binaries in a content-addressed cache
keyed by source, options, prelude, compiler, architecture and driver, so that a warm start compiles nothing and a
stale binary is never loaded.

This bead is the end-to-end script that measures the gate on running systems, from the user's side, on both device
families and on `batch-cpu`. The mechanisms are the arena layout planner (N21b-10), the cache (N21b-12), the two
verbs (N21b-13) and the integrating seed bead BD-173. Tier: Solid.

## Scope

In: the script, its steps, assertions, structured log, and the gate receipt.

Out: any mechanism; latency percentiles for edit-to-first-step (BD-184, which reuses the cold and warm steps'
method).

## Technical approach

**Invocation.** `scripts/e2e/spark_gate11_arena_cache.sh [--tier gpu-cuda|gpu-metal|batch-cpu] [--workload Q|H]
[--worlds N] [--steps N] [--seed N] [--cache-dir <dir>]`. Defaults: the device tiers present on the host, workload
Q at 1,024 worlds, 10⁶ steps of the batch, seed 1, and a fresh cache directory under the script's scratch area (so the run never
depends on, or damages, the user's cache). Conformance build. Every `sim run`, `spark precompile` and `spark cache`
call names the step's directory with `--cache-dir <dir>` (the conformance-build-only input: on `sim.run` N21b-39's,
on the two spark verbs N21b-13's; the scratch area is created under the session's export root, so it lies under
the session's roots as `--cache-dir` requires (734 otherwise), and `artifact export --out` may write there). Every `run`
command (`sim run`, `spark precompile`, `artifact export`) carries its own idempotency key
`g11-<run-id>-<step>-<n>-<tier>-s<seed>` (`<run-id>` the script run's UTC timestamp, `<n>` numbering the commands
of a step), so no two commands share a key, within one script run or across two; every envelope must show
`idempotent_replay: false` except in the `replay` step. Without keys each call would be refused with
`FROB-REF-805` (N32a-09's admission, from M1) before the cache is touched. `frob spark cache` is not a `run` verb:
its `read` forms and its `evict` action (kind `admin`, scope `spark:admin`) take no key.

**Steps and assertions.**

| Step | Commands | Assertions |
|---|---|---|
| `cold` | Fresh cache directory. `frob spark cache --json`; `frob sim run --tier <t> --workload Q --worlds 8192 --steps 1000 --key … --json`; `frob spark cache --json` | Cache empty before; the run's receipt has `compiler_invocations` equal to the kernel count (environment creation compiled every kernel); after: one entry per kernel |
| `cold_precompile` | A second fresh cache directory. `frob spark precompile <device> --workload Q --key … --json` | Every kernel `compiled`; `compiler_invocations` equals the kernel count; one entry per kernel |
| `warm` | On the `cold_precompile` directory: `frob spark precompile <device> --workload Q --key … --json`; then `frob sim run --tier <t> --workload Q --worlds 8192 --steps 1000 --key … --json` | Every kernel `hit`; the run's receipt has `compiler_invocations == 0` (on Metal: zero cache misses, with recompile seconds recorded) |
| `replay` | The `warm` step's `spark precompile` repeated with the same key | `idempotent_replay: true`; the stored envelope is returned byte-equal apart from the replay flag; compiler invocations and cache hit counters unchanged |
| `no_key` | `frob spark precompile <device> --workload Q --json` without `--key` | Exit 3 with `FROB-REF-805`; cache counters unchanged |
| `alloc_flat` | `frob sim run --tier <t> --workload Q --worlds 1024 --steps 1000000 --key … --json` (8,192 worlds under an approved envelope) | The receipt's allocated device bytes at environment creation equal the figure at the end; `post_creation_allocations == 0`; on CUDA the driver's own free-memory figure before the first step and after the last differ by 0 bytes when no other process holds the card (the script logs the card's process list before and after; if another process appeared, the driver figure is logged and not asserted, and the annex's own counter decides) |
| `perturb_source` | Rebuild the kernel library with one comment byte changed in one dialect body (test fixture); `frob spark precompile <device> --workload Q --key … --json` (the form of every `spark precompile` in the rows below) | That kernel is a miss with a new key; all others hit |
| `perturb_options` | `spark precompile` with one compile option changed through the test-only override | Every kernel misses |
| `perturb_compiler`, `perturb_driver` | `spark precompile` with the compiler identity string, then the driver version string, overridden by the test-only fingerprint shim | Every kernel misses in each case; no old entry is loaded |
| `corrupt` | Flip one byte in one entry's value; `frob spark cache --verify --json`; `spark precompile` | `--verify` exits 2 and names the entry; the entry is not served; it is recompiled |
| `offline` | Corrupt an entry; `frob spark precompile <device> --workload Q --offline --key … --json` | Exit 6 with `FROB-REF-612`; first repair names `spark precompile` on a build host |
| `evict` | With the step's cache filled beyond 8 MiB, `frob spark cache --action evict --to-bytes 8388608 --cache-dir <dir> --json` under a token with `spark:admin` (VERBS-spark's evict action; the cache's cap is not an input, so the target size is how a script reaches eviction), then `frob spark cache --json` | Size at or under 8 MiB; evicted entries are those with the smallest compile seconds; none in use (an entry pinned by a running job is listed `skipped: in use`) |
| `digests_unchanged` | Compare state digests of the `cold` and `warm` runs' first 1,000 steps | Identical: the cache never changes a result |
| `arch_fill` | On `trj` (or a Linux build host with NVRTC), a third fresh cache directory, with the CUDA devices hidden from the process (`CUDA_VISIBLE_DEVICES` empty): `frob spark precompile sm_89 --workload Q --target-fingerprint <file> --key … --json`, where `<file>` is `trj`'s current fingerprint record (the digest `frob spark devices --json` prints for `cuda:0`, written to the scratch area with `frob artifact export <digest> --out <scratch>/ --key … --json`); the same without `--target-fingerprint`; then the directory copied to a second path and, with the devices visible, `frob sim run --tier gpu-cuda --workload Q --worlds 8192 --steps 1000 --key … --json` on the copy | With the record: exit 0, every kernel `compiled`, no device opened (the receipt lists none). Without it: exit 6 with `FROB-REF-606` and no entry written. The run on the copied directory has `compiler_invocations == 0`: a cache filled where no GPU is visible, and moved, is a warm start on the target. Recorded `not run` with the reason on a host where NVRTC cannot be loaded (this Mac) |
| `gate` | `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers --features gauntlet-mutations -- GATE-SPARK-11` (there is no test target named `g1`; the feature builds the registered controls, the corrupted entry and the planted allocation, so they are caught in the same run) | A hash-named receipt with the measured values, its hash in the `summary`. The script stops there: it never runs `record_gate` (convention 9). The recording session, which did not implement the work, then enters the row from the receipt outside the script with `cargo run -p frob-conformance --example record_gate -- --gate GATE-SPARK-11 --receipt <hash>` |

The perturbation steps `perturb_options`, `perturb_compiler` and `perturb_driver` use N21b-12's conformance-build
key-input override, the cache's test seam that substitutes the compile options, the compiler identity string or
the driver version string entering the key; it is compiled only into the conformance build and cannot be enabled
in a release binary (`fingerprint_shim_absent_in_release` asserts its absence there).

**Pass rule for the gate.** On each device family present: flat allocation over 10⁶ steps; zero compiler
invocations on a warm start (CUDA), or zero cache misses with the recompilation disclosed (Metal, until the
gateway has a binary archive); and each cache control caught: the four one-byte perturbations and the corrupted
entry. A family that is absent is recorded `not run` with the reason.

**Logging.** The script sources the STD-E2E helper and writes
`target/e2e-logs/spark_gate11_arena_cache/<utc-timestamp>.ndjson` and a transcript. Every line has `ts`, `script`,
`bead`, `step`, `event`. `cmd` lines carry the exact command line, exit code and wall time; result lines copy the
envelope's `evidence` block (claim known-answer, class, tier, determinism, identities including the fingerprint
digest, seed). `metric` lines: allocated bytes at creation and at the end (threshold: equal); post-creation
allocations (threshold 0); compiler invocations (threshold 0 on warm); hits and misses per step; cache bytes
against the cap; compile seconds. `assert` lines: expected and observed. On failure: the first sample at which
allocated bytes changed (step index, bytes before and after), or the key and the field that failed to change it,
plus the cache directory path and the receipt path. A final `summary` gives assertion counts and the gate touched.
No scene or design data appears in the log.

## Acceptance criteria

- [ ] The script exits 0 on this Mac (Metal and `batch-cpu`) and on `trj` (each RTX 4090 and `batch-cpu`), and non-zero when any assertion fails.
- [ ] GATE-SPARK-11's three clauses are each measured with a number: bytes delta over 10⁶ steps (0), warm compiler invocations (0), cache controls caught (5 of 5).
- [ ] Every `run` command carries a distinct key; the `replay` step returns the stored envelope with `idempotent_replay: true` and compiles nothing; the `no_key` step is refused with `FROB-REF-805`.
- [ ] `arch_fill` on `trj`: the cache filled for `sm_89` with no device visible and `trj`'s fingerprint record as the target identity gives zero compiler invocations when loaded from a copy with the devices visible; the same fill with no record is `FROB-REF-606`.
- [ ] Each negative control in the script is demonstrably able to fail: with the allocation guard disabled and a planted per-step allocation, `alloc_flat` fails; with a key that omits the driver version (test-only variant), `perturb_driver` fails.
- [ ] The log validates against the STD-E2E line schema and ends with a `summary`.
- [ ] Two runs with the same seed produce the same assertions and the same digests.
- [ ] The gate receipt names the commit, the hardware fingerprint digest and the seed.

## Test plan

### Unit tests
- `e2e_log_schema_gate11`: log validation.
- `fingerprint_shim_absent_in_release`: the override symbol is not present in a release build of `frob`.
- `scratch_cache_isolated`: the script never reads or writes the user's default cache directory (checked by running with the default directory made read-only).

### End-to-end script and logging
This bead is the script. A reduced mode `--steps 10000` exists for continuous integration on `batch-cpu`; it runs
every step, asserts everything except the 10⁶-step horizon, and records no gate.

### Known answers and negative controls
- KA-543: allocated device bytes are flat over 10⁶ steps (INV-SPARK-03), exact.
- KA-536: a one-byte change of source, options, compiler or driver identity is a miss; a warm start loads every
  kernel with zero compiler invocations; a corrupted entry must be rejected by digest.
- Negative controls: the planted allocation; the driver-less key; a `--verify` that checks sizes only.
- Determinism lanes: cold against warm digests; twice on one machine; both hosts for `batch-cpu`.

## Considerations

- The gate counts **steps of the batch**, that is step-plan executions. 10⁶ of them at 8,192 worlds are 8.2·10⁹
  world-steps, about 68 minutes on one RTX 4090 at the interim floor of 2.0 M world-steps/s. That exceeds the
  default envelope of one device for one hour (OPEN-SPARK-2), so the script accepts `--worlds` and the gate run
  uses 1,024 worlds (about 9 minutes at the same rate) unless a larger envelope is approved; the allocation
  invariant does not depend on the world count.
- On Metal, "zero compiler invocations" cannot literally hold until FD-FT-01 provides a binary archive; the gate is
  recorded with the disclosed variant (zero cache misses) and re-run under the upstream item's switch-over rule.
- A leak that only shows after many cancel cycles is not this gate's concern (GATE-SPARK-06 and GATE-SPARK-12 run
  10³ cancel cycles).
- `trj`'s load varies; compile seconds are logged as data and never asserted.
