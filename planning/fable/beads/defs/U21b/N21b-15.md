## Background

ADR-SPARK-04: a batch is a bucket of one shape class. Each world indexes one of K model variants and one of K scene
variants inside padded capacities. No shape changes inside a running environment. Reason: a population of designs
is the studio's main workload, and static shapes keep launch graphs static. A **bucket** is one shape class on one
device: one arena, one compiled kernel set, one step plan, one launch graph. A **world** is a row of indices into
the bucket's tables.

How worlds are laid out inside a bucket decides two things at once: whether the device executes them efficiently
(lanes that execute together should share control flow), and whether a world's result is independent of the batch
it ran in (the property the whole studio rests on: replay of one world alone, forks, teleport, slot dispatch and
paired statistics all need it). This bead fixes the layout rules and the device-side types, and tests them at
kernel level. The system-level test of batch-composition invariance is GATE-SPARK-15 (BD-181).

Two counterexamples show the rules are not pedantry. Padding with +0.0 is not neutral: the sum of the single
active element −0.0 is −0.0 alone and +0.0 when one +0.0 lane is appended, because (−0.0) + (+0.0) = +0.0; the
values compare equal, the bits differ, and a digest over bits changes with capacity. And a mask applied as an
arithmetic blend m·a + (1 − m)·b turns an infinity in the unselected arm into a NaN, since 0·∞ is NaN (CX-219).

Tier: Solid for the rules; they are exercised by parameter variants [S] and by topology variants [F].

## Scope

In: the device-side `ShapeClass` view, `Bucket` and `WorldRow`; the run allocator; the padding and mask rules as
checks on manifests and as kernel-level tests; keying of results by world address.

Out: the owning definition of `ShapeClass` and `ModelTable` and the packed lowering (BD-148, and the Phylum beads);
parameter rows on `batch-cpu` (BD-169) and model variants with masks on `batch-cpu` (BD-170); variant tables on
devices and admission (N21b-16); the gate runs (BD-183, BD-181); reductions' tree shape (the utility kernels,
BD-152).

## Technical approach

**Types (DESIGN; intent, not signatures).** The type sketch registry holds one definition of the shape class,
under the names of the Phylum chapter (`n_v`, `links`, `depth`, `samples`, `contacts`, `rows`, `actuators`,
`sensor_layout`, `policy_layout`, `contact_law`, `precision`, `iterations`, `single_structure`). The device-side
view names the capacities with a `_cap` suffix and adds nothing:

```rust
struct ShapeClass {                 // content-hashed; one kernel set and one launch graph per class per device
    nv_cap: u16,                    // degrees of freedom: one of 12, 18, 24, 36, 48, 64 by default
    link_cap: u16, depth_cap: u8,
    contact_cap: u16, row_cap: u16, sample_cap: u16, actuator_cap: u16,
    sensor_layout: LayoutId, policy_layout: LayoutId,
    contact_law: LawId, precision: PrecisionProfile, iterations: u8,
    single_structure: bool,         // P-A: one tree, unmasked path; part of the hash like every other field
}
// The hash is BD-148's: BLAKE3 over `frob.shape-class/1`, a zero byte and the fields in BD-148's order (n_v, links,
// depth, samples, contacts, rows, actuators, ...), not in this sketch's order.
struct Bucket { class: ShapeClass, device: DeviceId, model_variants: u16, scene_variants: u16, worlds: u32 }
struct WorldRow { model_variant: u16, scene_variant: u16, task: u16, job: u16, addr: [u32; 4] }   // 8 + 16 = 24 bytes
```

`WorldRow` is the device form of the host's `WorldSlots { model, scene, task, job, addr }` with bucket-local 16-bit
indices. `addr` is the world address: the identity every result, random draw and digest is keyed by. Slot index is
never an identity.

**Rule L1: runs.** Worlds of one model variant are contiguous and allocated in multiples of the device's execution
width (32 on both device families today: FACT for CUDA warps, and the gateway's own note for Apple silicon; the
width is read from the device, never assumed), so that lanes of one wave share control flow and the per-level
kinematic loop does not diverge inside a group. OPEN-PHYLUM-2 owns the run length (16 or 32; default 32 on CUDA,
the device's reported width on Metal; decided by the M2 profile). The run allocator takes (variant, world count)
pairs, rounds each count up to a multiple of the width, and returns slot ranges; the lanes added by rounding are
**inactive worlds**: masked, holding identity state, placed after the variant's active worlds.

**Rule L2: padding trails and is neutral.** Padding (padded links, padded degrees of freedom, padded contacts and
rows, inactive worlds) follows the active entries and holds the neutral element of the operation that will consume
it: −0.0 for sums, 1.0 for products, +∞ and −∞ for minimum and maximum, and identity rows with zero right-hand
side in the factorization, which follow every active row and so never enter an active entry. This makes a world's
result independent of the capacity of the bucket it ran in (padding neutrality: outputs of active lanes are
bit-identical at any capacity at or above the active count).

**Rule L3: masks apply to every kernel, to rewards and to gradient accumulation.** A padded contact that stays
active would change the physics; a padded world that contributes to a reward sum or a gradient would change
learning. Every kernel's manifest declares the mask it applies; the layout check refuses a kernel that writes
state without one.

**Rule L4: a mask is a select.** `select(pred, a, b)`, never an arithmetic blend.

**Rule L5: no cross-world reads or writes.** A kernel touches only its own world's rows; statistics across worlds
are computed by `stat` kernels whose outputs never feed state (the stage-signature check of N21b-01).

**Rule L6: results by address.** Everything read back (digests, statistics rows, snapshots, verdicts) is keyed by
world address. Sorting the output of any run by address must give the same bytes whatever slots the worlds
occupied.

**Checks.** (a) A layout validator over a bucket's `WorldRow` table: runs contiguous, lengths multiples of the
width, inactive lanes trailing in each run, every variant index below its count. (b) A manifest check: every
padded output names its consumer and neutral element (N21b-01 rule 6), and every state-writing kernel names its
mask. (c) Kernel-level metamorphic tests, run through the harness on `batch-cpu` and on each device: capacity
change, slot permutation, co-tenant change.

**What the tests run on.** The device kernel libraries come from the CUDA and Metal full-step beads (BD-172,
BD-174) and the model-variant tables with masks on `batch-cpu` from BD-170; all three are dependencies, so the
per-kernel sweeps cover the real M2 library on both device families and the variant-mix property test uses real
variant rows. The rules themselves (the allocator, the validator, the manifest checks) do not depend on them and
may be written first.

## Acceptance criteria

- [ ] `WorldRow` is 24 bytes with the stated fields; `ShapeClass` hashes to the same `ShapeClassId` as the host-side definition for the same capacities.
- [ ] The run allocator returns contiguous runs whose lengths are multiples of the device's reported execution width, with inactive lanes trailing; the validator rejects a table with a split run, a run of non-multiple length or an inactive lane in the middle.
- [ ] For every kernel of the M2 library with padded inputs, outputs of active lanes are bit-identical at capacities c, 2c and 4c (padding neutrality at kernel level) on `batch-cpu` and on each device.
- [ ] The sum of the one active element −0.0 is −0.0 at every capacity; with +0.0 padding planted it becomes +0.0 and the test fails (negative control).
- [ ] `select` with an infinity in the unselected arm returns the selected arm unchanged; the planted blend returns NaN and the test fails (KA-533).
- [ ] Permuting the slots of a batch leaves the address-sorted outputs byte-identical.
- [ ] A state-writing kernel with no declared mask is refused by the manifest check; a planted padded contact left active changes a world's digest and is caught.
- [ ] The rules are documented in `frob-kernels`' `CONTRACT.md` under invariants.

## Test plan

### Unit tests
- `world_row_layout`: size 24, field offsets 0, 2, 4, 6, 8.
- `run_allocator_multiples`: counts (16, 33, 1, 64) at width 32 give runs of 32, 64, 32, 64 with 16, 31, 31, 0 inactive lanes.
- `layout_validator_rejects`: three planted defects.
- `padding_neutral_sum`: active {−0.0} with 0, 1, 7 and 31 padding lanes of −0.0: result bits 0x80000000 each time.
- `padding_plus_zero_breaks` (negative control): padding +0.0 gives 0x00000000.
- `neutral_elements_table`: product padding 1.0, minimum padding +∞, maximum padding −∞ leave results unchanged for 10⁴ random active sets.
- `select_not_blend`: a = 1.5, b = +∞, pred true: select gives 1.5; blend 1·1.5 + 0·∞ gives NaN.
- `capacity_invariance_per_kernel`: each M2 kernel at three capacities.
- `slot_permutation_invariance`: random permutations of 4,096 worlds; address-sorted digests equal.
- `padded_contact_active_detected` (negative control).
- Property test: for random variant mixes, every world's kernel outputs equal those of the same world in a homogeneous batch of its own variant.

### End-to-end script and logging
The shell lane is `scripts/e2e/spark_gate10_variants.sh` (bead BD-183), step `layout`: `frob spark place --tier
strict:<backend> --design <population> --task <id> --worlds 8192 --json` prints the bucket's run table (variant,
first slot, active worlds, inactive lanes, width; N21b-29's residency map carries it), and the script asserts rules
L1 and L2 on it. This bead's own end-to-end lane is the device integration test `cargo test -p frob-kernels
--release --test layout_rules_e2e` (with device variants on `trj` and this Mac): it builds a 4,096-world bucket of
three model variants, runs every M2 kernel with padded inputs at capacities c, 2c and 4c and under 10 random slot
permutations, and writes NDJSON lines in the STD-E2E format to
`target/e2e-logs/spark_layout_rules/<utc-timestamp>.ndjson`: the run table as `metric` lines, the execution width
read from the device against the fingerprint's value, per-kernel address-sorted digests for each capacity and
permutation (mismatches threshold 0), the inactive share, and on failure the kernel, the world address and the
first differing word; a final `summary` line.

### Known answers and negative controls
- KA-533 (mask with an infinity in the unselected arm: `select` returns the selected arm unchanged; the blend
  returns NaN). CX-219 is its negative control.
- The padding counterexample: (−0.0) + (+0.0) = +0.0. KA-346 (a power-of-two-aligned pairwise sum with trailing
  −0.0 entries equals the sum over the real prefix, for every capacity) and CX-146 (a reduction that groups by
  capacity: in `f32` with a = 10⁸, b = −10⁸, c = 1, (a + b) + c = 1 and a + (b + c) = 0).
- Metamorphic relations: capacity, slot permutation, co-tenant variants.
- Determinism lanes: `batch-cpu` across worker counts; each device twice; devices against `batch-cpu` in the class
  the family holds.

## Considerations

- Homogeneity by morphology is not homogeneity by work: contact counts differ inside a run, which is why the
  contact and solve stages are compacted and masked per world. Runs help the kinematic and dynamic stages; they do
  not remove masks.
- Rounding every variant up to a multiple of the width wastes lanes when a population has many variants with very
  few worlds each (256 variants of one world each at width 32 would use 8,192 lanes for 256 worlds). The run
  allocator therefore reports the inactive share, `phylum.plan` prints it, and OPEN-PHYLUM-2's choice of 16 or 32
  is decided on it together with the profile.
- The execution width is a property of the device read at run time; a width different from the fingerprint's
  refuses the run (`FROB-REF-606`).
- The address is four 32-bit words; counts and digests never use 64-bit device integers, which Metal lacks.
- KILL-BUCKET does not change these rules: per-family templates are homogeneous environments and satisfy them
  trivially.
