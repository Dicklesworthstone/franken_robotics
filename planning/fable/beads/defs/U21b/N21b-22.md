## Background

A rollout on a device is policy forward, then the step plan repeated for the control decimation, then observation,
all on the device; the host receives a small statistics ring and snapshots on request. How often the host
synchronizes with the device decides three things at once: throughput (a synchronization inside a control interval
stalls the pipeline; the design allows none), how stale the host's view is, and how quickly a cancellation can take
effect. The plan fixes the unit: the **chunk**.

- **Chunks.** The host synchronizes once per chunk of control intervals. The chunk length is the shorter of one
  rollout segment and the number of intervals that fit the cancellation latency target (250 ms at the 99th
  percentile, TARGET).
- **Cancellation** is at the kernel-batch boundary: request, drain, finalize, with an executor-minted report
  (evidence field AE-10, the cancellation outcome, of the twelve fields every device run carries). A dropped
  handle is not a cancellation receipt.

Cancellation is one of the eight conditions of "implemented" for any capability in this project: request, drain,
finalize, with no leaked device resources. On Metal the constraint is hard: the gateway's wait cannot be
interrupted (FACT), so a chunk, once submitted, runs to its end; the only way to bound cancel latency is to bound
the chunk. On CUDA a cancel word in the control block turns already-enqueued replays into masked no-ops.

The seed bead BD-175 owns device faults and cancellation as a whole and records GATE-SPARK-06. This bead specifies
the chunk-length rule and the cancellation protocol in the detail an implementer needs. Tier: Solid.

## Scope

In: the chunk-length rule and its inputs; the conformance-only knob `--chunk-intervals N` on `sim.run` and
`spark.place` that pins it; the synchronization-per-chunk discipline; the three-phase cancellation
protocol on both backends and on `batch-cpu`; the drain report; the rule about dropped handles; leak accounting
across cancel cycles.

## Technical approach

**Chunk length (algorithm).**
1. Inputs: the rollout segment length S in control intervals (for example a PPO horizon of 24); the cancellation
   latency target T_c = 250 ms at the 99th percentile; an estimate t₉₉ of the 99th-percentile time of one control
   interval for this bucket on this device (from the running latency histogram of completed chunks; before the
   first chunk, from the fingerprint's launch costs and the estimator; never from a mean).
2. k = min(S, max(1, floor(T_c / t₉₉))).
3. k is recomputed only at segment boundaries, never inside a segment, so that a segment's chunking is a function
   of data recorded in the receipt and a replay can reproduce the same chunk boundaries (the chunk length in force
   is a receipt field and part of the replay recipe; digests do not depend on k, which is tested).
4. If t₉₉ > T_c, k = 1 and the receipt carries `cancel_latency_target: unattainable` with the measured t₉₉; this
   is a disclosure, not a refusal.

Worked value: at 2.0 M world-steps/s with 8,192 worlds and decimation 10, one batch step takes 4.096 ms and one
control interval 41 ms, so k = floor(250/41) = 6 intervals per chunk; a 24-interval segment is four chunks.

**The arrangement knob `--chunk-intervals N` (DESIGN; conformance build only; this bead owns it because it
overrides this rule).** On `sim.run` and `spark.place`, in a build with the `conformance` feature, `--chunk-intervals
N` pins k = N for every chunk of the run in place of steps 2 to 4 (the last chunk of a segment or of the run is
shorter when fewer intervals remain). N is an integer from 1 to 2³² − 1; 0 or a larger value is `FROB-REF-808`.
The length in force is the receipt field `chunk_intervals` (on `spark.place`, the plan field of the same name),
beside `chunk_pinned: true`; the pinned run's request-to-drain latencies are logged but never enter the latency
histogram the rule reads, so a pinned run cannot move the chunk length of ordinary runs; and when N × t₉₉ exceeds
the target the receipt carries `cancel_latency_target: unattainable`, as in step 4. The knob is written into the
manifest; it changes no state digest (the test `digests_independent_of_chunk_length` pins k through it). A pinned
length is not shortened by the no-wrap bound of N21c-39: a pinned length that would let a device count wrap is
refused with that bead's code (`FROB-REF-619` as proposed) before any world is stepped. The knob does not exist in
a release build's input schema (802 there), and it is not the release option `--chunk-len` (N29b-18), which is a
different input with its own rules. Users: N21b-39 (lane `chunk`), N35-03, N21c-39 and N21c-43. VERBS-sim and
VERBS-spark list it as a conformance-only input with this bead as owner.

**One synchronization per chunk.** The device worker enqueues or encodes every control interval of the chunk, then
synchronizes once: on CUDA one stream synchronization after the last replay and the commit; on Metal the single
`submit` of the chunk's batch. Readback (statistics ring, snapshots) happens at that point under leases. The
counter `sync_in_chunk` (N21b-02) must stay 0, and `syncs == chunks` over a run.

**Cancellation protocol.**
1. *Request.* The caller cancels through the job handle (which carries the asupersync capability context). The
   worker records the request with the index of the chunk in flight. On CUDA it also enqueues the cancel-word
   write, so replays enqueued behind it do no work.
2. *Drain.* The chunk in flight runs to its end and passes through the commit fence. If it completed normally its
   epoch is committed and published; if the cancel word cut it short (CUDA), the partially stepped working state is
   discarded and the last committed epoch stands. No new chunk is submitted. In-flight host copies complete or are
   abandoned in stream order.
3. *Finalize.* Transient device memory of the cancelled work is released (stream-ordered pool on CUDA; nothing on
   Metal, where storage is the arena); leases are revoked; the committed frontier is published to the record; if
   the environment is not persistent, the arena is freed.
4. *Report.* The **executor** (the device worker, not the caller) mints the drain report and stores it with the
   receipt as AE-10: request time and chunk index; the epoch drained through; chunks discarded; for each world the
   last committed step; transient bytes released; allocated device bytes before the job and after finalize;
   outcome `cancelled-drained`. The measured request-to-drain latency goes into the latency histogram that the
   chunk-length rule reads.

**A dropped handle is not a cancellation receipt.** If the caller drops the handle (process exit, lost
connection), the job is not thereby cancelled in the record: the worker still drains and finalizes when told to by
the supervisor, and until an executor-minted report exists the job's state is `abandoned`, not `cancelled`. No
result or resource-release claim is derived from the absence of a handle.

**`batch-cpu`.** The same protocol with tiles in place of launches; cancellation is observed between tile batches
through the capability context's checkpoints.

**Leak accounting.** After finalize, allocated device bytes must equal the pre-job figure for a non-persistent
environment, or the environment's baseline for a persistent one; the pool's outstanding bytes must be 0. The
figures are in the drain report, so 10³ cancel cycles can be checked by reading 10³ reports.

## Acceptance criteria

- [ ] The chunk length equals min(S, max(1, floor(250 ms / t₉₉))) for the recorded t₉₉, is constant within a segment, and is in the receipt.
- [ ] Per-world digests are identical for chunk lengths 1, 2, 6 and S on the same run (chunking is invisible to results).
- [ ] `syncs == chunks` and `sync_in_chunk == 0` over 10³ chunks on each backend.
- [ ] Request-to-drain latency at the 99th percentile over 10³ cancellations is at most 250 ms on each device family at the gate's workload, or the receipt carries `cancel_latency_target: unattainable` with the measured interval time.
- [ ] After each of 10³ cancel cycles, allocated device bytes return to the baseline and pool outstanding bytes are 0 (no leaked device memory).
- [ ] Every cancellation has a drain report minted by the worker; a planted caller-side report (a client writing its own "cancelled" record) is rejected by the schema check, which requires the worker's identity (negative control).
- [ ] Dropping the handle without cancel leaves the job `abandoned` until a drain report exists.
- [ ] A cancelled run resumed from its last committed epoch reaches the same digests as an uncancelled run.

## Test plan

### Unit tests
- `chunk_length_rule`: S = 24, t₉₉ = 41 ms gives 6; t₉₉ = 300 ms gives 1 with the `unattainable` note; t₉₉ = 5 ms gives 24.
- `chunk_length_constant_within_segment`.
- `chunk_intervals_knob`: in a conformance build `--chunk-intervals 2` on `sim.run` gives `chunk_intervals: 2` and `chunk_pinned: true` in the receipt and the same per-world digests as the unpinned run; on `spark.place` the plan shows 2; `--chunk-intervals 0` is `FROB-REF-808`; a release build's schemas of both verbs have no `chunk_intervals` input (802); the pinned run's latencies do not change the histogram the rule reads.
- `digests_independent_of_chunk_length`: k ∈ {1, 2, 6, 24} on `batch-cpu` and on each device.
- `sync_counters`.
- `cancel_three_phases`: state transitions `Requested → Draining → Finalized`; no chunk submitted after the request.
- `drain_report_fields_and_minter`: every field present; minter is the worker identity; a report from any other identity fails validation.
- `dropped_handle_is_abandoned`.
- `cancel_cycles_no_leak`: 10³ cycles on `batch-cpu`; device variants run in the script.
- `resume_after_cancel_matches`: cancel at a seeded chunk, resume, compare final digests with the straight run.
- `cuda_cancel_word_noop`: replays behind the cancel write change no state digest.

### End-to-end script and logging
`scripts/e2e/spark_gate06_faults_cancel.sh` (bead N21b-25), step `cancel_cycles`: 10³ iterations of
`frob sim run --tier <t> --workload Q --worlds 1024 --key g06-<run-id>-cancel-<cycle>-<t>-s<seed> --json`
returning a job handle (each cycle its own key, and `<run-id>` the script run's timestamp: a reused key would
return the first cycle's job and cancel nothing new), `frob job cancel <id> --json` at a seeded delay, `frob job
status <id> --json` until the drain report appears. Logged per the STD-E2E helper: per cycle the
chunk index at request, request-to-drain milliseconds against the 250 ms threshold, allocated bytes before and
after, pool outstanding bytes (threshold 0), the report's minter; the 99th percentile over the cycles as a final
`metric`; on failure the cycle index and the report path.

### Known answers and negative controls
- KA-542 (cancellation and fault injection on a device: every injected fault yields its typed refusal; no leaked
  device memory after 10³ cancel cycles; the drain report is executor-minted) and KA-544 (zero synchronizations
  inside a chunk; no pool memory leaked after 10³ cancel cycles).
- Known answer: the chunk-length worked value (6 intervals at 41 ms per interval).
- Negative controls: the caller-minted report; a chunk-length rule that uses the mean interval time instead of the
  99th percentile (must violate the latency criterion on a workload with a heavy tail, planted by a synthetic
  latency histogram); a finalize that skips releasing the pool (leak counter non-zero).
- Determinism lanes: results independent of chunk length; cancel-and-resume against the straight run; twice with
  the same cancel schedule.

## Considerations

- The 250 ms figure is a TARGET for latency at the 99th percentile; it binds the chunk length, and through it the
  frequency of host synchronization. A shorter target costs throughput on Metal (more command buffers, each with a
  commit-and-wait cost) and is a knob the performance program may revisit with measurements.
- On Metal the wait cannot be interrupted, so worst-case cancel latency is one chunk; FD-FT-01's interruptible
  wait would allow longer chunks at the same latency.
- A chunk is also the unit of commit and of retry; the fence, the leases and the published record all advance once
  per chunk, which is why its length is recorded and replayable.
- Persistent environments (slot dispatch) cancel a job by releasing its slots at the next chunk boundary; the
  environment itself is not finalized.
- The drain report contains world identifiers and steps, never state contents.
