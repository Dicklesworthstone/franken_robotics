## Background

GATE-SPARK-12 (Known answer, M2, TARGET): zero graph captures after warm-up and zero synchronizations inside a
chunk; no pool memory leaked after 10³ cancel cycles; 10⁵ snapshot reads each match the digest emitted for their
epoch; the commit-fence known answer holds under 10³ injected faults.

Each clause checks one promise of the device execution model. **Zero captures after warm-up**: the step plan of a
bucket is captured once as a launch graph, and everything that varies between replays lives in a control block,
because re-capturing every step costs a factor of three to four in throughput on a published incumbent (invariant:
no shape change inside a running environment; one graph capture per bucket). **Zero synchronizations inside a
chunk**: the host synchronizes once per chunk of control intervals. **No pool leak**: transient device memory comes
from a stream-ordered pool, so the allocations of a cancelled stream are released in stream order. **Snapshot
reads match their epoch's digest**: the host reads a device slab only under a lease on a committed epoch, after the
command buffer that wrote it has completed, so what it reads is exactly the state whose digest the device emitted
for that epoch. **The commit fence**: a chunk that fails is retried from the committed slab and the final result is
bit-identical to the run that never failed.

This bead is the end-to-end script for the gate, run on CUDA (`trj`) and on Metal (this Mac). The mechanisms are
the CUDA backend (BD-172) with its control block and counters (N21b-02), the Metal batch loop (N21b-06), the commit
fence (N21b-07), leases (N21b-11), chunks and cancellation (N21b-22) and the in-kernel digests and snapshots
(BD-203). Tier: Solid.

## Scope

In: the script, its steps, assertions and structured log; which clause applies to which backend; the gate receipt.

Out: mechanisms; the fault-refusal table and the device-memory leak check of GATE-SPARK-06 (N21b-25); arena and

## Technical approach

**Invocation.** `scripts/e2e/spark_gate12_launch_fence.sh [--tier gpu-cuda|gpu-metal] [--workload Q] [--worlds N]
[--seed N]`. Conformance build (fault seams). Defaults: device tiers on the host; workload Q at 1,024 worlds (8,192
under an approved envelope); seed 1.

**Steps and assertions.**

| Step | Commands | Assertions | Backends |
|---|---|---|---|
| `warmup` | `frob sim run --tier <t> --workload Q --worlds N --intervals 100 --json` | Completes; record `graph_captures` (CUDA) or step-plan builds (Metal) after warm-up as the baseline | both |
| `captures` | The same for 10⁵ control intervals | CUDA: `graph_captures` unchanged from the baseline (that is, zero captures after warm-up); `launch_args_hash` constant. Metal: zero re-plans, one batch per chunk. Under the OPEN-SPARK-4 fallback (no graph capture available) the clause is recorded `not applicable: per-launch submission` with the disclosed reason | CUDA (Metal by analogy) |
| `sync` | Read the receipt of `captures` | `sync_in_chunk == 0`; synchronizations equal chunks | both |
| `cancel_cycles` | 10³ cycles of run, `frob job cancel`, wait for the drain report | CUDA: stream-ordered pool outstanding bytes 0 after every cycle and device free memory at the end equal to the start. Metal: allocated bytes equal the arena baseline after every cycle (there is no pool: storage is the arena) | both |
| `snapshot_reads` | `frob sim run ... --snapshot-every 1 --intervals <enough for 10⁵ snapshots across worlds> --json`, then `frob artifact read` on each snapshot | For each of 10⁵ snapshot reads: the host-computed in-kernel-equivalent digest of the bytes read equals the digest the device emitted for that world at that epoch | both |
| `commit_fence` | Run A: no faults. Run B: `--inject-faults seed=7,count=1000` (never more than three in a row). Compare final digests. Run C: four consecutive faults on one chunk | A and B have identical final per-world digests; B's receipt counts 1,000 retries; C exits 6 with `FROB-REF-607` naming the last committed epoch | Metal (the gateway's fault seam); CUDA with the annex's launch-error wrapper |
| `fence_disabled` | Run B with the conformance flag that disables the fence | Final digests differ from run A and the script asserts that the mismatch is detected | Metal |
| `lease_violation` | A read of a slab that is not committed, snapshot or previous ring slot | Exit 6 with `FROB-REF-614` | both |
| `gate` | `cargo test -p frob-conformance --test g4 -- GATE-SPARK-12` | Hash-named receipt with the measured values; registry row entered by a recording session that did not implement the work | — |

**Snapshot digest comparison, in detail.** At each commit the device's digest kernel folds the raw bit patterns of
a world's canonical state slabs into four `u32` words in slab order and stores them with the epoch. A snapshot read
returns the same slabs' bytes for chosen worlds. The host recomputes the same integer fold over the bytes it read
(the fold is exact integer arithmetic, so the host twin is bit-identical by construction) and compares the four
words. A mismatch means the host read something other than the committed state of that epoch: a torn read, a wrong
epoch, or a lease bug.

**Pass rule.** Every applicable clause holds on each device family present. Clauses that do not apply to a backend
are recorded with the reason, not silently skipped.

**Logging.** The script sources the STD-E2E helper and writes
`target/e2e-logs/spark_gate12_launch_fence/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
`bead`, `step`, `event`. `cmd` lines: exact command line, exit code, wall time. Result lines carry the envelope's
`evidence` block (claim known-answer, class, tier, determinism, identities with the fingerprint digest, seed).
`metric` lines: `graph_captures` before and after (threshold: equal); `sync_in_chunk` (threshold 0); pool
outstanding bytes per cycle (threshold 0); snapshot reads compared and mismatching (threshold 0); retries; final
digests of runs A and B. On failure: the first interval at which a counter moved, the first snapshot whose digest
mismatched (world address, epoch, both digests), or the first world whose final digest differs between A and B,
with the artifact paths needed to reproduce (receipt, snapshot files, fault schedule). The `summary` line counts
assertions and names the gate. Snapshot contents are compared and never logged.

## Acceptance criteria

- [ ] On CUDA: zero graph captures after warm-up over 10⁵ control intervals; zero synchronizations inside a chunk; zero outstanding pool bytes after each of 10³ cancel cycles.
- [ ] On Metal: one batch per chunk with zero re-plans; one synchronization per chunk; allocated bytes at the arena baseline after each of 10³ cancel cycles.
- [ ] 10⁵ snapshot reads on each backend each match the digest emitted for their epoch.
- [ ] The commit-fence known answer holds under 10³ injected faults; four consecutive faults give `FROB-REF-607`; with the fence disabled the mismatch is detected.
- [ ] Each negative control can fail the script: a planted argument change forces a re-capture and fails `captures`; a planted in-chunk synchronization fails `sync`; a planted torn read (a snapshot taken through a test-only path that bypasses the lease) fails `snapshot_reads`; a pool free out of stream order fails `cancel_cycles`.
- [ ] The log validates against the STD-E2E schema; the gate receipt names commit, fingerprint digest and seed; inapplicable clauses carry their reason.

## Test plan

### Unit tests
- `host_digest_twin_matches_kernel`: on `batch-cpu`, the host fold over snapshot bytes equals the kernel's four words for 10⁴ random states, including states with NaN payloads and signed zeros.
- `e2e_log_schema_gate12`.
- `clause_applicability_table`: the script's per-backend clause table is consistent with the backend's reported capabilities (graph capture present or not).

### End-to-end script and logging
This bead is the script. A reduced mode (10³ intervals, 20 cancel cycles, 10³ snapshot reads, 20 faults) runs on
`batch-cpu` in continuous integration, exercising the fence, leases and digest twin without a GPU, and records no
gate.

### Known answers and negative controls
- KA-544 (launch graphs, pools and snapshot reads: zero graph captures after warm-up; zero synchronizations inside
  a chunk; no pool memory leaked after 10³ cancel cycles; 10⁵ snapshot reads each match the digest emitted for
  their epoch; exact).
- KA-537 (commit fence under injected command-buffer faults: final digests equal those of the unfaulted run; at
  most four attempts with growing waits, then `FROB-REF-607`; every retry counted; negative control: with the fence
  disabled the mismatch must be detected).
- Negative controls: listed in the acceptance criteria.
- Determinism lanes: runs A and B (faulted against unfaulted); each run twice; snapshot digests across repeats.

## Considerations

- 10⁵ control intervals of Q at 1,024 worlds are 10⁶ batch steps, about 9 minutes at the interim floor rate on one
  RTX 4090; the whole script fits the default envelope of one device for one hour. At 8,192 worlds it does not,
  and that variant needs an approved envelope (OPEN-SPARK-2).
- The device digest is a tripwire classed `Tested`: a 128-bit integer mix is not an identity. Identities in the
  record are BLAKE3 hashes computed by the host over committed snapshots. This gate uses the tripwire for exactly
  what it is for: detecting that a read is not the committed state.
- If OPEN-SPARK-4 ended in per-launch submission, the capture clause does not apply on CUDA and the gate record
  says so; the throughput cost is disclosed elsewhere.
- Metal's fault seam needs a debug-assertions build of the annex (FACT).
