## Background

ADR-SPARK-05: placement is planned and receipted per stage; a strict backend request fails before any scoring if a
stage has no kernel there. Reason: an agent must be able to tell acceleration from a silent fallback. A system that
quietly runs a stage on the CPU when its device kernel is missing reports a "GPU result" that is partly a CPU
result, at a throughput nobody can interpret, in a determinism class nobody declared. The remedy has two halves: a
planner that decides and explains before anything runs (the seed bead BD-178 and the verb bead N21b-29), and a
**record of what was requested against what actually ran, with every cost counted**. This bead is the record.

"The denominator is whole" (rule 3 of the planner): transfers, synchronizations, compilation and retries are in
the receipt and in every throughput figure derived from it. This is the suite doctrine's rule (account for the
whole workflow) made checkable. And rule 5: each device closes its own loop: a hybrid plan may claim acceleration
only for stages that ran on the device and returned a device-timed receipt. Counters that a backend reports about
itself are only as trustworthy as the backend, so the gate (GATE-SPARK-09) requires that receipt counters for
transfers and synchronizations match an **instrumented shim** within one count. Tier: Solid.

## Scope

In: the `frob.placement/1` schema; the run-time accumulation of per-stage counters in each backend; the header
fields; derivation of the attained determinism class; the instrumented shim in `frob-conformance`; the rule that
throughput figures are computed from the receipt's whole denominator.

Out: the planner's decisions and refusals (BD-178, N21b-29); the cost model (N21b-30); check currency's definition
(BD-176); the disclosure block's assembly (BD-216), which embeds this record.

## Technical approach

**Record (DESIGN: `frob.placement/1`).**

```text
header: request mode (strict | prefer | mixed-allowed), requested backend,
        fingerprint digest, shape class, bucket, capacities,
        determinism class attained, check currency per kernel (current | stale | absent, with the ledger row id)
rows (one per stage of the batched step, plus policy, learner, statistics, snapshot path):
        stage, kernel ids, requested backend, actual backend, fallback reason, fallback count,
        transfer bytes host→device, transfer bytes device→host, synchronization count, resident duration,
        device seconds, command buffers or graph replays, retries
totals: compile seconds and compiler invocations, admission seconds, wall seconds, device seconds,
        bytes each way, synchronizations, retries, stalls
```

The stages are the ten of the batched step (kinematics; collision geometry; broad phase; narrow phase; contact
compaction; dynamics terms; constraint rows; solve; integrate and energy ledger; sensors, observations, rewards and
resets) and four service rows (policy forward, learner, statistics, snapshot path). The record has two forms with
one schema: the **plan** (counters zero, written before anything runs) and the **receipt** (counters filled,
attached to every result).

**Field semantics.**
- *requested backend / actual backend*: equal under `strict` always; may differ under `mixed-allowed` for a
  fallen-back stage; under `prefer` all rows share one actual backend, which may differ from the requested one.
- *fallback reason*: one of `no-kernel`, `stale-check`, `missing-arithmetic-feature`, `cost-model`, `device-lost`;
  empty when actual equals requested.
- *fallback count*: how many launches of this stage ran on the fallback.
- *transfer bytes*: every host-to-device and device-to-host copy attributable to the stage, including the copies a
  fallback causes (state moved to the host for a CPU stage and back).
- *synchronization count*: synchronizing calls attributable to the stage (one per chunk for the chunk's commit,
  attributed to the snapshot path row; any extra one a fallback forces is attributed to the stage that forced it).
- *resident duration*: wall seconds the stage's data stayed resident on its actual backend between transfers.
- *device seconds*: from device-side timers (on Metal the command buffer's start-to-end interval; on CUDA
  event-timed intervals). A row without device seconds cannot support a claim of acceleration.
- *command buffers or graph replays*: the unit of submission on the backend.
- *determinism class attained*: the weakest class among the kernels, placements, profile and inputs that produced
  the result (the weakest input wins; a class is never raised by relabeling). A fallback to `batch-cpu` in a
  family that holds only tolerance agreement with it lowers the attained class to D3.

**Accumulation.** Each backend increments the counters at the call sites that do the work: buffer uploads and
readbacks (bytes, direction), synchronizing calls, submissions, retries, compile invocations. Counters are plain
integers owned by the device worker; per-stage attribution uses the stage index carried by each launch. Device
seconds per stage come from the profiling mode on Metal (one batch per kernel) or are reported per chunk with
`per-stage: unavailable` in normal mode.

**Whole-denominator rule.** A throughput figure is computed only by a function that takes a receipt and divides
completed world-steps by wall seconds including compile (reported separately for cold and warm), admission,
transfers, synchronization waits, retries and stalls. There is no other code path that produces a rate for an
envelope; a test asserts that the rate printed by `sim.run` equals this function's value.

**Instrumented shim (`frob-conformance`).** A `KernelBackend` wrapper that forwards every trait call to a real
backend and counts independently: bytes passed to uploads and returned by readbacks, launches, and (through thin
counting wrappers at the annexes' lowest call sites, compiled only in conformance builds) the driver-level copy
and synchronization calls. After a run it compares its counts with the receipt's: transfers and synchronizations
must agree within one count per run (the allowance covers the final synchronization at shutdown, which may or may
not be attributed to the run). The shim runs the real backend on real fixtures: it observes, it does not replace.

**Schema check (INV-SPARK-02).** A device result without a placement receipt fails the schema check at the agent
boundary.

## Acceptance criteria

- [ ] `frob.placement/1` has a generated schema; plans and receipts validate; the record round-trips.
- [ ] Every result of `sim.run` on a device tier carries a placement receipt with all fourteen rows and the header; a result without one is rejected at the boundary.
- [ ] On workload Q for 10³ chunks, the receipt's transfer bytes each way and synchronization count equal the shim's independent counts within one count, on CUDA and on Metal.
- [ ] Under `mixed-allowed` with one stage's device kernel withheld, that stage's row shows actual ≠ requested, the reason `no-kernel`, a non-zero fallback count, and the extra bytes and synchronizations the fallback cost; the attained determinism class is lowered if the family does not hold D1.
- [ ] The rate in the envelope equals completed world-steps over the receipt's whole wall time; a planted rate computed from device seconds only is caught by the equality test.
- [ ] A planted undercount (a backend that skips counting one readback path) is caught by the shim (negative control).
- [ ] Compile seconds and compiler invocations appear in totals and are reported separately for cold and warm starts.

## Test plan

### Unit tests
- `placement_schema_roundtrip`.
- `rows_cover_all_stages`: ten step stages and four service rows, in a fixed order.
- `attained_class_is_weakest`: stage classes {D1, D1, D3} give D3; adding a `batch-cpu` fallback in a D3 family gives D3; all exact-integer stages give D0.
- `fallback_row_fields`: reason, count, bytes and synchronizations non-zero for the fallen-back stage and zero elsewhere.
- `throughput_from_whole_denominator`: a synthetic receipt (labelled `synthetic`) with 8.192·10⁶ world-steps, 3.0 s of stepping, 0.5 s of transfers and waits, 0.5 s of retries gives 2.048 M world-steps/s, not 2.73 M.
- `shim_counts_match_batch_cpu`: the shim around `batch-cpu` matches its receipt exactly.
- `undercount_detected` (negative control).
- `plan_form_has_zero_counters`.

### End-to-end script and logging
`scripts/e2e/spark_gate09_placement.sh` (bead N21b-31), step `counters`: runs
`frob sim run --tier strict:gpu-cuda|strict:gpu-metal --workload Q --worlds 1024 --intervals 1000 --json` under
the conformance shim and compares the receipt with the shim's counts. Logged per the STD-E2E helper: each counter
from both sources as paired `metric` lines with the allowed difference (1), the placement rows, the attained
class, and on failure the stage and counter that disagree.

### Known answers and negative controls
- Known answer: the synthetic throughput case (8.192·10⁶ / 4.0 s = 2.048 M; device-only would give 2.73 M).
- KA-534's counter clause: receipt counters for transfers and synchronizations match an instrumented shim within
  one count.
- Negative controls: the undercounting backend; a receipt whose rows omit a stage (schema failure); a rate computed
  from enqueue time (caught by the whole-denominator equality).
- Determinism: counters are integers and identical across repeats of the same run; device seconds vary and are
  outside any digest.

## Considerations

- The counters are cheap (integer increments at coarse call sites) and are always on; only the shim's driver-level
  wrappers are conformance-only.
- Per-stage device seconds are not available on Metal outside profiling mode (the gateway's receipt has a kernel
  count and device seconds only); the record says `unavailable` instead of estimating. Upstream work item FD-FT-01
  includes per-kernel timing.
- A performance figure without a complete disclosure block is refused (`FROB-REF-862`) and a device result cited
  without a current CPU-versus-device check is refused (`FROB-REF-864`); both read this record.
- RISK-48: a driver or binding update changes the fingerprint digest in the header, which is how a stale receipt
  is recognised (`FROB-REF-606`).
- The record names stages and kernels, never scene or design contents.
