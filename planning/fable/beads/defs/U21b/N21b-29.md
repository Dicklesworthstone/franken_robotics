## Background

`spark.place` turns a request into a plan before anything runs. For each stage of the batched step, for the
policy, the learner, the statistics and the snapshot path, it chooses a backend and writes down why. It also prints
the residency map: where each slab lives, its size, its last committed epoch and who may read it. The verb is how
an agent learns, before spending a device-hour, whether its request will run where it asked, in which determinism
class, and at what transfer cost; and how it learns afterwards what actually ran.

The decision behind it is ADR-SPARK-05: placement is planned and receipted per stage; a strict backend request
fails before any scoring if a stage has no kernel there, because an agent must be able to tell acceleration from a
silent fallback. The invariant it carries is INV-SPARK-07: a strict request never scores on a fallback.

The seed bead BD-178 owns the placement planner as a whole and records GATE-SPARK-09. This bead specifies the verb,
the three request modes with their exact semantics, the planner's refusals, and the residency map. The record
format is N21b-28 and the cost model for small jobs is N21b-30. Tier: Solid. Registry entry: `spark.place`, kind
`read`, first milestone M2, cluster `devices`: "the placement plan and the residency map, before anything runs".

## Scope

In: request syntax; the three modes; planning algorithm over stages; refusals `FROB-REF-604`, `FROB-REF-605`,
`FROB-REF-616`; the `--require-current-check` flag; the plan output; the residency map output; the same planning
call used by `sim.run` and every other run verb before stepping.

Out: the record schema and counters (N21b-28); the cost model's calibration (N21b-30); check currency's definition
and `spark.check` (BD-176); determinism-class licences for verbs (the numerics chapter's beads, BD-269); the
end-to-end gate script (N21b-31).

## Technical approach

**Request.** A placement request names a backend and a mode: `strict:gpu-cuda`, `strict:gpu-metal`,
`prefer:gpu-cuda`, `prefer:gpu-metal`, `mixed-allowed:gpu-cuda`, `mixed-allowed:gpu-metal`, or plain `batch-cpu`.
Optional: a device index; `--require-current-check`; the determinism class the caller needs.

**Planning algorithm (run by `spark.place`, and by every run verb before it steps a world).**
1. Resolve the shape class, bucket and kernel set for the request (design or workload, world count, task).
2. For each of the fourteen rows (ten step stages; policy; learner; statistics; snapshot path), look up, on the
   requested backend: (a) whether every kernel of the stage has a compiled or compilable source there; (b) whether
   the device records every arithmetic feature those kernels declare (for example 64-bit integers; double-float
   kernels need a passed canary); (c) the check currency of each kernel on this device family, driver and compiler
   (`current`, `stale`, `absent`).
3. Apply the mode's rule (below) to produce an actual backend per row, or a refusal.
4. Derive the determinism class attained (the weakest among rows) and compare it with the class the caller needs;
   if it is not attainable the plan is refused with the numerics code `FROB-REF-247`.
5. Estimate transfers and synchronizations per row from the layout (bytes that would cross for any fallen-back
   stage) and write the plan form of `frob.placement/1`.
6. Nothing has been allocated, compiled for execution, or stepped.

**Rule 1: strict means strict.** Under `strict:gpu-cuda` or `strict:gpu-metal`, any of the following is an error
raised by the planner, and no world is stepped and nothing is scored:
- a stage has no kernel on that backend: `FROB-REF-604` (first repair: `mixed-allowed`, or the other backend);
- a kernel's check is stale or absent and `--require-current-check` is set: `FROB-REF-605` (first repair:
  `frob spark check`);
- the device lacks an arithmetic feature a kernel declares: `FROB-REF-616` (first repair: the 32-bit variant, or
  another backend).
All three are exit code 6 and name the stage, the kernel and the fingerprint digest.

**Rule 2: mixed placement is opt-in.** Only `mixed-allowed` lets a stage fall back to `batch-cpu`. The plan (and
later the receipt) then shows, for that stage, actual differing from requested, the reason, and the bytes and
synchronizations it costs. `prefer` never mixes: if the named backend cannot run every stage, the whole plan moves
to one backend that can (the other device family if present and complete, otherwise `batch-cpu`), and the plan
says so before the run starts.

**Rule 3: the denominator is whole.** The plan's cost estimate, and every throughput figure later derived from the
receipt, includes transfers, synchronizations, compilation and retries.

**Rule 4: a cost model decides small jobs** (N21b-30): where the request leaves a choice, a job or a host-resident
stage goes to a device only if its predicted device time including dispatch, transfer and synchronization is below
its host time. The plan prints the prediction for both placements.

**Rule 5: each device closes its own loop.** The plan marks which rows will be able to claim acceleration: those
that run on a device and will return a device-timed receipt.

**Without `--require-current-check`.** A stale or absent check does not refuse the plan; it is printed per kernel,
the plan is labelled `check: not current`, and any result produced under it cannot be cited as evidence (the
evidence-and-protocol code `FROB-REF-864` refuses the citation later).

**Residency map.** For the request's bucket: every slab with its group, location (device and buffer, or host),
bytes, the last committed epoch, and the lease kinds currently permitted (host read on the committed slab, the
snapshot slab and the previous ring slot; host write between chunks); per-kernel buffer argument counts; totals
against the device budget and the largest-buffer limit. For a running environment the map is live; for a plan it
is the planned layout with epochs empty.

**Verb surface.**
`frob spark place --tier <mode:backend> (--workload Q|H | --design <id> --task <id>) --worlds N
[--require-current-check] [--need-class D0|D1|D2|D3] [--env <id>] --json`.
Output schema `frob.spark.place.out/1` (DESIGN name): the plan (`frob.placement/1` in plan form), the residency
map, the predictions of the cost model, and `next_actions` (for a refusal, the ranked repairs as commands). Kind
`read`: it changes nothing. Exit 0 for a clean plan; 2 for a plan with findings (a fallback under
`mixed-allowed`, a moved plan under `prefer`, a check that is not current); 6 for the three planner refusals and
for `FROB-REF-601` (device unavailable) and `FROB-REF-606` (fingerprint missing or changed); 3 for
`FROB-REF-247`. A misspelt mode or backend is a refusal, not a default.

## Acceptance criteria

- [ ] For every one of the fourteen rows, withholding its device kernel under `strict:<backend>` yields `FROB-REF-604` from the planner naming the row, with zero worlds stepped, zero bytes allocated on the device and nothing scored (INV-SPARK-07).
- [ ] The same request under `mixed-allowed` completes planning with that row's actual backend `batch-cpu`, reason `no-kernel`, and non-zero estimated transfer bytes and synchronizations; exit 2.
- [ ] Under `prefer` with one kernel withheld, every row's actual backend is the same single backend that can run all stages, and the plan states the move.
- [ ] A stale check with `--require-current-check` yields `FROB-REF-605` under strict; without the flag the plan is labelled `check: not current`.
- [ ] A kernel declaring 64-bit integers on a device whose fingerprint lacks them yields `FROB-REF-616`; a double-float kernel on a device with a failed canary is refused before any launch.
- [ ] A caller needing class D1 on a family whose probe attained only D2 is refused with `FROB-REF-247`.
- [ ] The residency map lists every slab with location, bytes, last committed epoch and permitted readers, and its totals equal the arena planner's.
- [ ] Run verbs call the same planning function: a strict `sim.run` with a withheld kernel returns the same refusal as `spark.place` and steps nothing.
- [ ] The verb is registered with schemas, examples and refusal list; one envelope per invocation.

## Test plan

### Unit tests
- `strict_refuses_per_row`: fourteen cases, one withheld kernel each: `FROB-REF-604` naming the right row.
- `mixed_allowed_falls_back_per_row`: the same fourteen cases: actual `batch-cpu` for that row only.
- `prefer_moves_whole_plan`.
- `stale_check_605_requires_flag`.
- `missing_feature_616`.
- `class_not_attainable_247`.
- `planner_allocates_nothing`: the planner cannot call `KernelBackend::allocate` or `launch` (it holds a read-only capability view of the backend).
- `residency_totals_match_arena`.
- `run_verbs_share_planner`: `sim.run` under strict with a withheld kernel: zero steps, identical refusal.
- `misspelt_mode_refused`: `strct:gpu-cuda` is a refusal.
- Property test: for random subsets of withheld kernels, strict refuses iff the subset is non-empty; mixed-allowed never refuses for `no-kernel`; prefer yields one actual backend.

### End-to-end script and logging
`scripts/e2e/spark_gate09_placement.sh` (bead N21b-31) drives this verb for every row and mode. Logged per the
STD-E2E helper: command, exit code, wall time, the refusal envelope or the plan rows, world-steps executed
(threshold 0 for refusals), device bytes allocated (threshold 0), the residency map totals.

### Known answers and negative controls
- KA-534 (strict placement with one device kernel withheld, for every stage: refusal by the planner with
  `FROB-REF-604` before any world is stepped; zero episodes; negative control: the same request under
  `mixed-allowed` must show actual ≠ requested).
- Negative controls: a planner variant that silently falls back under strict (the defect the design exists to
  prevent) must be caught by `strict_refuses_per_row` and by the step counter; a `prefer` variant that mixes must
  be caught by `prefer_moves_whole_plan`.
- Determinism: a plan is a pure function of the request, the kernel registry, the fingerprint and the ledger's
  currency rows; identical on repeat.

## Considerations

- OPEN-SPARK-1 (owner): until the annex design is ratified, any plan that places stages on a device labels the
  result exploratory; the plan prints the label.
- The kernel "withholding" used by tests is a conformance-only registry overlay; a release build cannot hide a
  kernel.
- `prefer` moving a whole plan to `batch-cpu` can turn a minutes-long job into hours; the plan prints the predicted
  time for the moved plan so that the agent can refuse it.
- The cross-machine role policy (which machine should run what) is not this verb's concern; it plans for the host
  it runs on. The fleet verbs consume its output.
- Paired statistics and attribution have their own minimum classes; this verb reports the class attained and the
  consuming verb enforces its licence.
