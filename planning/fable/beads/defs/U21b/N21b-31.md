## Background

GATE-SPARK-09 (Known answer, M2, TARGET): for every stage, withholding its device kernel under a strict request
yields the refusal with zero worlds stepped; receipt counters for transfers and synchronizations match an
instrumented shim within one count.

The gate protects the claim an agent relies on when it reads a throughput or a "ran on GPU" label: a strict
backend request never scores on a fallback (INV-SPARK-07), and the costs a receipt reports are the costs that
occurred. Its negative control is built in: the same request under `mixed-allowed` must show actual differing from
requested, which proves the test can distinguish a fallback from a refusal.

This bead is the end-to-end script that measures the gate through the user's surface on both device families. The
mechanisms: the planner (seed bead BD-178), the verb and modes (N21b-29), the record and the shim (N21b-28), the
cost model (N21b-30). Tier: Solid.

## Scope

In: the script, its steps and assertions, the structured log, and the gate receipt.

Out: mechanisms; refusal codes of the fault family (N21b-25).

## Technical approach

**Invocation.** `scripts/e2e/spark_gate09_placement.sh [--backend gpu-cuda|gpu-metal] [--seed N]`. Conformance
build of `frob`: it provides the registry overlay that withholds one kernel (`--withhold-kernel <name>`), the
counting shim, and the check-staleness override. Defaults: the device backends present on the host; workload Q;
1,024 worlds; seed 1.

**The fourteen rows.** The ten stages of the batched step (kinematics; collision geometry; broad phase; narrow
phase; contact compaction; dynamics terms; constraint rows; solve; integrate and energy ledger; sensors,
observations, rewards and resets) and the four service rows (policy forward; learner; statistics; snapshot path).
For each row the script picks the first kernel of that row from `frob spark place --json` output and withholds it.

**Steps and assertions.**

| Step | Commands (for each of the fourteen rows unless noted) | Assertions |
|---|---|---|
| `strict_plan` | `frob spark place --tier strict:<b> --workload Q --worlds 1024 --withhold-kernel <k> --json` | Exit 6; `FROB-REF-604`; the refusal names the row and kernel; first repair is `mixed-allowed`, or the other backend |
| `strict_run` | `frob sim run --tier strict:<b> --workload Q --worlds 1024 --intervals 100 --withhold-kernel <k> --json` | Exit 6; `FROB-REF-604`; `world_steps_executed == 0`; zero episodes recorded; device allocated bytes unchanged from before the command; no run record published as a result |
| `mixed_control` | The same run with `--tier mixed-allowed:<b>` | Completes (exit 0 or 2); the placement receipt's row for that stage shows actual `batch-cpu` ≠ requested, reason `no-kernel`, fallback count > 0, and transfer bytes and synchronizations > 0 for that row; other rows show actual equal to requested |
| `prefer_control` | The same with `--tier prefer:<b>` (three representative rows) | Every row's actual backend is one backend that can run all stages; the plan stated the move before the run started (checked by running `spark place` first and comparing) |
| `stale_check` | Mark one kernel's check stale through the conformance override; `strict:<b>` with `--require-current-check` | Exit 6; `FROB-REF-605`; first repair `spark check`; zero worlds stepped. Without the flag: completes, labelled `check: not current` |
| `missing_feature` | A kernel variant declaring 64-bit integers on a device whose fingerprint lacks them | Exit 6; `FROB-REF-616`; zero worlds stepped |
| `counters` | `frob sim run --tier strict:<b> --workload Q --worlds 1024 --intervals 1000 --json` under the counting shim (no kernel withheld) | Receipt transfer bytes host→device and device→host and the synchronization count each equal the shim's independent counts within one count |
| `counters_mixed` | The `mixed_control` run for one row under the shim | The same agreement, now with a fallback's extra transfers present in both counts |
| `cost_model` | As described in N21b-30 | Host placement predicted for the boundary screen; prediction within a factor of two of measurement |
| `residency` | `frob spark place --tier strict:<b> --workload Q --worlds 1024 --json` on a running environment | Every slab listed with location, bytes, last committed epoch and readers; totals equal the receipt's allocated bytes |
| `gate` | `cargo test -p frob-conformance --test g1 -- GATE-SPARK-09` over the script's result file | Hash-named receipt; registry row entered by a recording session that did not implement the work |

**Zero worlds stepped, measured three ways.** (1) The envelope's `world_steps_executed`; (2) the shim's launch
count, which must be 0; (3) the device's allocated bytes before and after, which must be equal (the planner
refuses before allocation). All three are asserted so that a planner that refuses late cannot pass.

**Pass rule.** For every one of the fourteen rows on each device family present: the strict refusal with zero
worlds stepped; the `mixed-allowed` control shows actual ≠ requested; and the counter agreement holds within one
count.

**Logging.** The script sources the STD-E2E helper and writes
`target/e2e-logs/spark_gate09_placement/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
`bead`, `step`, `event`. `cmd` lines: exact command line, exit code, wall time. `refusal` lines: code, message,
pointer (row and kernel), repairs, fingerprint digest. Result lines carry the `evidence` block (claim
known-answer, class, tier, determinism class attained, identities, seed). `metric` lines: world-steps executed
(threshold 0 on refusals), shim launch count (threshold 0), allocated bytes before and after, per-row requested and
actual backend, fallback count, transfer bytes and synchronization counts from receipt and shim with the allowed
difference of 1. On failure: the row, the expected and observed code or counter, and the envelope and receipt
paths. The `summary` counts assertions (fourteen rows times the steps) and names the gate.

## Acceptance criteria

- [ ] On CUDA and on Metal, all fourteen rows pass `strict_plan`, `strict_run` and `mixed_control`.
- [ ] Receipt counters match the shim within one count with and without a fallback.
- [ ] `stale_check` and `missing_feature` return `FROB-REF-605` and `FROB-REF-616` with zero worlds stepped.
- [ ] The script can fail: with the conformance flag that makes the planner fall back silently under strict, `strict_run` fails on the step counter and on the placement row; with a backend that skips counting one readback path, `counters` fails.
- [ ] The log validates against the STD-E2E schema; the gate receipt names commit, fingerprint digest and seed.
- [ ] A device family that is absent is recorded `not run` with the reason.

## Test plan

### Unit tests
- `e2e_log_schema_gate09`.
- `row_list_matches_plan_schema`: the script's fourteen rows equal the rows of `frob.placement/1`.
- `withhold_overlay_absent_in_release`: a release build rejects `--withhold-kernel`.

### End-to-end script and logging
This bead is the script. A reduced mode on `batch-cpu` alone (the "device" being a second `batch-cpu` instance
registered under a test backend name) exercises the planner's refusal, the mixed control and the shim comparison in
continuous integration without a GPU; it records no gate.

### Known answers and negative controls
- KA-534 (strict placement with one device kernel withheld, for every stage: refusal by the planner with
  `FROB-REF-604` before any world is stepped; zero episodes; receipt counters for transfers and synchronizations
  match an instrumented shim; exact for the refusal; within one count for the counters; negative control: the same
  request under `mixed-allowed` must show actual ≠ requested).
- Negative controls: the silent-fallback planner; the undercounting backend.
- Determinism lanes: refusal envelopes identical on repeat apart from timing; the `mixed_control` run's digests
  equal the fully-device run's digests where the family holds class D1 with `batch-cpu`, and are recorded with the
  attained class otherwise.

## Considerations

- Fourteen rows times three modes on two families is about a hundred short runs; all fit the default compute
  envelope.
- The withheld kernel is hidden by a registry overlay, not by deleting a binary, so the kernel cache and the real
  registry are untouched.
- The service rows (policy, learner, statistics, snapshot path) exist at M2 only where the learning stack is
  present; rows whose kernels are not yet in the library are reported `not present at this commit` and the gate
  stays open for them.
- OPEN-SPARK-1: device results in the control runs are labelled exploratory until ratification; the gate is a
  known-answer gate about refusals and counters and does not depend on the label.
