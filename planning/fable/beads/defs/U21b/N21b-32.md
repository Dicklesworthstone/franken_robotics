## Background

FrankenSim's accelerator doctrine, which FrankenRobotics adopts unchanged, makes a device result citable only when
a CPU-versus-device comparison exists for the same kernels (evidence field AE-08) and a CPU reference is retained
(AE-09). Spark's instrument for this is `frob spark check`: run a kernel on `batch-cpu` in `f32` and on a device
from identical inputs, compare under the kernel's determinism class, and write the result to the **divergence
ledger**. The ledger is the "stored disagreement record" behind the one claim Spark may make about its toolchain
once GATE-SPARK-02 has passed: kernel arithmetic is derived once and emitted for a CPU reference, CUDA and Metal,
and the measured cross-backend disagreement is stored per kernel. (Compiling one kernel source for several backends
is prior art and is not claimed.)

The first user is at M0: GATE-SPARK-00 (bead BD-020) must record the agreement of `K-cay-step` across three
backends "in the divergence ledger", so the ledger and the single-kernel form of the verb must exist at M0. This
bead builds exactly that minimum: the comparator, the ledger row, and `spark.check` for one kernel on a pair of
placements. The M2 form (every kernel, the full step, check currency as a gate on citing results, invariance
sweeps, first-divergence search) is BD-176 and N21b-33.

Rule kept from the plan's hygiene list: a ledger exists only because a named verb reads it or a named gate checks
it. This ledger is written by `spark.check`, read by `spark.place` (check currency per kernel), by the placement
planner's strict mode, by `fidelity.ledger`, and checked by GATE-SPARK-00 and GATE-SPARK-02.

Tier: Solid. Crates: `frob-kernels` (comparator, verb body) and `frob-conformance` (fixtures, negative controls).

## Scope

In: the ulp distance and integer histogram; class comparators for D0, D1, D2 and D3 at kernel level; the ledger row
and its storage; the verb `spark.check` for `--kernel`; a planted-divergence fixture.

Out: `--all` and `--step` over the M2 kernel set, currency enforcement, `FROB-REF-605` (BD-176); sweeps over batch
size, slot, capacity, co-tenants and shards and the bisection over the digest chain (N21b-33); the decision-level
equivalence test for D3 at step level (BD-177); device backends (BD-015, BD-016).

## Technical approach

**Units in the last place, as integers (DESIGN).** For a finite `f32` x with bit pattern b, let
m(x) = b if the sign bit is clear, and −(b AND 0x7FFF_FFFF) otherwise. m is monotone in x, and +0 and −0 both map
to 0. The ulp distance of two finite values is |m(a) − m(b)|, computed in `i64`. Non-finite cases are classified,
not measured: `nan_mismatch` (exactly one is NaN), `inf_mismatch` (exactly one is infinite or the infinities
differ in sign), `signed_zero` (both zero, signs differ; distance 0 but bytes differ).

**Histogram.** Integer counts in fixed bins: 0, 1, 2, 3, 4, 5–8, 9–16, 17–32, …, doubling to 2²⁰, and one bin
above; plus the three class counters. Bins are integers and merge by addition, so the histogram is identical
whatever order chunks arrive in (the same rule the plan applies to every statistic that crosses shards).

**Class comparators.**
- D0 (exact-integer kernels and the decisions of guarded kernels) and D1 (bitwise across backends): byte equality
  of every output slab; any non-zero bin, any class counter, or a signed-zero difference fails.
- D2 (bitwise per backend): the same placement run twice gives byte-equal outputs.
- D3 (tolerance): at kernel level, every output within 4 ulp and no NaN or infinity mismatch. (At step level D3
  also needs statistical equivalence of 1,000-step rollouts and the decision-level test; those are not in v0.)
- The **class attained** by a pair is the strongest class whose comparator passes; it is recorded even when it
  is weaker than the class the manifest claims, in which case the check completes with a finding.

**Inputs.** Generated from an explicit seed and lane index (address-keyed, never by call order), with a fixed share
of edge lanes per kernel declared by its fixture: zeros of both signs, the largest and smallest magnitudes in the
kernel's validity domain, values at its refusal boundary. Identical bytes are uploaded to both placements; the
input set has an identity (generator id, seed, count) that is stored in the row.

**Ledger row (DESIGN; record name `frob.divergence/1`, see Considerations).**

```text
kernel id, kernel name, kernel class
reference placement: backend family, device, driver, runtime, compiler, fingerprint digest (when one exists)
candidate placement: the same fields
class claimed (from the manifest), class attained
input set identity: generator, seed, lane count
per output slab: ulp histogram (integer bins), nan / inf / signed-zero counters
worst case: output slab, lane, ulp distance, the input values of that lane as bit patterns, both output bit patterns
currency key: BLAKE3(kernel id ‖ candidate device family ‖ driver ‖ compiler ‖ fingerprint digest)
row id: BLAKE3 of the canonical row (no wall-clock time inside the hash)
```

Rows are appended through the ledger opened by the M0 admission of FrankenSQLite (BD-009); the table joins
`frob-chronicle`'s schema when that lands at M1 (BD-090). A later row with the same currency key supersedes an
earlier one for currency and both are kept.

**Verb (kind `run`; first milestone M0; cluster `devices`).**
`frob spark check --kernel <name> --backend <batch-cpu|gpu-cuda[:n]|gpu-metal> [--reference batch-cpu] [--seed N]
[--lanes N] --json`. Output schema `frob.spark.check.out/1` (DESIGN name): one entry per kernel with claimed and
attained class, the histogram, the worst case and the row id. Exit 0 when every kernel attains its claimed class;
exit 2 when the check completes with findings; exit 6 with `FROB-REF-601` (device unavailable or lost),
`FROB-REF-603` (compile failure, diagnostics verbatim) or `FROB-REF-606` (fingerprint missing or changed since
admission, once fingerprints exist). The envelope's evidence block carries the determinism class attained and
evidence class `Tested`.

**Planted-divergence fixture.** `frob-conformance` holds a twin of `K-selftest` whose constant is perturbed by one
unit in the last place (a `batch-cpu` mutant, so the fixture needs no GPU). Comparing the two must produce a
non-zero bin 1 and a worst case that names the lane.

## Acceptance criteria

- [ ] `frob spark check --kernel K-selftest --backend batch-cpu --json` exits 0, attains its claimed class and writes one ledger row; the row round-trips and its id is stable.
- [ ] The one-ulp mutant is reported: bin 1 non-zero, class attained D3 at best, exit 2, and the worst case reproduces when its recorded input bits are replayed.
- [ ] A signed-zero difference alone fails D1 and passes D3 (distance 0, bytes differ).
- [ ] One NaN against a finite value fails every class.
- [ ] Histograms built from 1, 4 and 64 chunks of the same lanes are byte-identical.
- [ ] The verb, its schemas and its refusals are in `registries/verbs.toml`; the output carries the claim product (class, tier, determinism class, identities, seed).
- [ ] With a device backend present (BD-015 or BD-016), the same command runs against it unchanged (exercised by BD-020).

## Test plan

### Unit tests
- `ulp_distance_cases`: 1.0 against the next float up is 1; −1.0 against the next float toward zero is 1; +0.0 against −0.0 is 0 with `signed_zero = 1`; the largest finite against +∞ is `inf_mismatch`; 1.0 against 1.0 + 4 ulp is 4 and against 1.0 + 5 ulp is 5 (bin 5–8).
- `ulp_distance_across_zero`: the smallest positive subnormal against the smallest negative subnormal is 2.
- `histogram_merge_is_addition`: random partitions of 10⁶ lanes give the same histogram.
- `comparators`: a table of (histogram, counters) cases against the class each must attain.
- `row_canonical_and_id`: field order fixed; permuting slab insertion order leaves the id unchanged.
- `currency_key_changes`: changing the driver string, the compiler string or the kernel id changes the key.
- `worst_case_replays`: feeding the recorded worst-case input bits back through both kernels reproduces both recorded outputs.
- `planted_one_ulp_detected`: the mutant fixture.

### End-to-end script and logging
`scripts/e2e/spark_check_v0.sh`: (1) `frob spark check --kernel K-selftest --backend batch-cpu --json`, assert
exit 0 and class attained; (2) the same against the mutant library, assert exit 2 and a non-zero bin 1;
(3) `frob artifact`-level read of the stored row (or a direct ledger query until `artifact.read` exists at M1),
assert the row id matches the envelope. Logged with the STD-E2E helper: command, exit code, wall time, the evidence
block, the histogram as measured values with the threshold for the claimed class, the row id, and on failure the
worst-case lane with its input bits and the path of both output dumps. Final `summary` line with assertion counts.

### Known answers and negative controls
- Known answers: the ulp distances listed above; (1 + 2⁻²³) − 1 is one ulp at 1.
- Negative controls (registered with the conformance registry): the one-ulp mutant; a comparator that measures
  absolute difference instead of ulp distance must fail `ulp_distance_cases` at large magnitudes; a histogram that
  averages instead of counting must fail the merge test.
- Determinism lanes: the row id is identical when the check is repeated on one machine, across worker counts, and
  in debug and release builds (the hash covers no time and no host name beyond the placement identity).

## Considerations

- The plan names the ledger and its contents but not a schema identifier. `frob.divergence/1` is this bead's
  proposal; schema names are owned by the format registry (`registries/formats.toml`), which decides the final
  name.
- `FROB-REF-864` (a device result cited without a current CPU-versus-device check; an evidence-and-protocol code)
  and `FROB-REF-605` (the check is not current for a kernel in the plan) both read the currency key defined here;
  v0 records the key and enforces nothing.
- Four ulp is the plan's kernel-level tolerance for class D3 (a TARGET); OPEN-NUM-2 owns the decision-level
  thresholds, not this one.
- The check costs a `batch-cpu` run of every kernel it covers. At M0 that is one kernel on 10⁶ lanes; at M2 the
  cost is budgeted by BD-176.
- A kernel whose outputs include a digest or a predicate must be class `exact` or `guarded` and is compared for byte
  equality on every backend, never under a tolerance.
