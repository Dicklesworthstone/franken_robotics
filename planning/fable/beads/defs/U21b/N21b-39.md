## Background

**The requirement.** Run-to-run determinism per device family is a design requirement of Spark (the subsystem
that owns everything between a derived kernel and a device result): the same job on the same device family, driver
and compiler gives the same bits every time. It is the first half of determinism class D2 ("bitwise per backend:
the same bits run to run and across worker counts on one device family, driver and compiler"). The second half,
independence of a world from the batch it ran in, is measured by GATE-SPARK-15 (BD-181) and by the sweeps of the
CPU-versus-device check (N21b-33). This bead measures the first half on real devices and records the result.
Classes, for reference: D0 exact; D1 bitwise across backends (a HYPOTHESIS under KILL-D1); D2 bitwise per backend;
D3 agreement inside a recorded envelope plus agreement of task decisions; D4 unspecified, never cited as evidence.
The weakest input wins, and a class is never raised by relabeling.

**Parity, not novelty.** FACT: two incumbents (Newton 1.8 for five solvers; Isaac Lab 3.0 on PhysX for rigid
bodies and articulations) document opt-in bitwise run-to-run determinism for the same batch on the same GPU model,
driver, toolkit and build. The property must still hold here, because everything stronger rests on it: a paired
comparison on common world addresses, an attribution, a counterfactual fork, a memoized episode and a teleport all
assume that re-running a world gives the world back.

**How the design delivers it (DESIGN; the rules whose violation the lanes detect).** No floating-point atomics
(integer atomics only for maximum, minimum, bitwise or and wrapping add); no grid-wide barrier; masks are selects;
trailing padding with the consumer's neutral element. One stable integer-key radix sort with total-order keys
(value, then index) and one count, exclusive-scan, write compaction serve every stage. Reductions are pairwise
trees anchored at index 0, shaped by logical index only (never by tile boundaries, worker count or thread-group
size). Results are placed by index or address, never by arrival; hash-map iteration order may not affect an output;
random draws are functions of (address, step, stream). No kernel has data-dependent scheduling, so a chunk replayed
from the committed slab is bit-identical; a retry restores the whole committed state; warm-start buffers are part
of every snapshot. The kernel cache is keyed by compiler and driver.

**Why "almost always" is a failure.** The plan rejects unordered floating-point scatter "accepted if 99.9% of
windows replay bitwise" with one line: 0.999¹⁰⁰⁰ = 0.37, so a campaign of a thousand windows would replay exactly
about one time in three (CX-230). Rare scheduling effects on a GPU are real: the suite's piano renderer has a
grid-wide barrier that leaves a thread group unscheduled "about once per few hundred launches" on Metal (FACT;
CX-221). A determinism test must therefore state how rare a defect it could have missed.

**Who consumes the result.** (1) KILL-METAL fires if GATE-SPARK-04 fails after one optimization pass **or the Metal
backend cannot hold run-to-run determinism**; the decision bead N21b-08 takes its second input from here. (2) The
KILL-D1 decision (N21b-34) first needs to know that a family holds class D2 at all. (3) The M2 stop decision: M2
exits in its no-GPU variant if no device family holds a controlled class. (4) GATE-GAUNT-07 (the conformance
battery's determinism tier G5: every kernel and verb meets its declared class twice on one machine, across worker
counts, in debug and release, across platforms and across backends): this bead supplies its device rows for the
first three lanes. Tier: Solid.

## Technical approach

**Run equality (DESIGN).** Two runs A and B of the same job (workload, designs, policy weights, scene, seed, world
addresses, profile `device-replay`, precision profile, fingerprint digest) are *run-to-run equal* when all of:
1. for every world address the final identity is equal: BLAKE3 computed by the host over the committed snapshot
   (the record's identity; the device digest is only a tripwire);
2. at every common commit tick the per-world device digests are equal (four `u32` words per world from the
   in-kernel integer fold over the canonical state slabs, compared by address, never by slot), and so is the run
   digest (the wrapping sum of per-world digests keyed by address);
3. the logical event streams are byte-equal after sorting by (address, tick): terminations with cause, resets,
   `Faulted` and `Degraded` marks with reasons, capacity flags, guarded-predicate fallback counts;
4. the counters that are functions of the job are equal: world-steps executed, episodes completed, capacity
   high-water marks.
Excluded, by an explicit list: wall time, device seconds, encode and blocked seconds, retries (in the fault lane),
dispatch and synchronization counts when the chunk length differs. Anything not on the list is compared.

**Configurations (DESIGN sizes).** Short: workloads Q (the reference quadruped) and H (the reference humanoid),
4,096 worlds, 2,000 control intervals, seed 1. Long: workload Q, 8,192 worlds, 10⁴ control intervals. Common commit
ticks when chunk lengths differ: the multiples of 64 intervals and the final interval (for 2,000 intervals: 31
multiples and the end, 32 comparison points).

**Lanes.** Each lane runs arrangements A and B and compares them by the relation above.

| Lane | Arrangement A | Arrangement B | Defect it exists to catch |
|---|---|---|---|
| `repeat` | A run in one process | The same run again in the same process, in a new environment (also the long configuration) | A racy reduction or compaction; uninitialized device memory; state leaking between environments |
| `restart` | A run in one process | The same run in a fresh process | Hash-map iteration order with a per-process seed; ordering by pointer value; leftover device state |
| `cache` | Kernels compiled into an empty cache directory | Kernels loaded from the warm cache (CUDA: the cached binary; Metal: recompiled from cached expanded source) | A compiler that emits different code for one key; a binary loaded under a wrong key |
| `workers` | 1 host worker thread | 8 host workers, and all cores | Host-side assembly by arrival (uploads, reset writes, ring and snapshot readback) |
| `build` | Release build of the host binary | Debug build, same kernel binaries | Host arithmetic in table preparation that changes with optimization |
| `chunk` | 64 control intervals per chunk | 8 per chunk, and 1 per chunk | State held only on the host between chunks; a control block (step counter, epoch, decimation phase) advanced wrongly |
| `group` | Thread groups (CUDA blocks) of one execution width | Two and four execution widths, where the pipeline's maximum allows | A reduction whose order depends on group size or on which lanes share a wave |
| `card` | RTX 4090 number 0 | RTX 4090 number 1, same driver and compiler | A per-card difference; the precondition of sharding worlds across the two cards |
| `resume` | Uninterrupted | Cancelled at five seeded chunk boundaries and resumed each time from the last committed epoch | State missing from the snapshot (warm starts, actuator and battery state, the control block) |
| `fault` | No faults | 100 injected launch or command-buffer faults (seeded, never four in a row) | A retry that keeps part of its state |
| `load` | An idle device | The device shared with a second process running a synthetic compute load, and the host CPU loaded | Scheduling-dependent results under contention |
| `soak` | The run at the start of a session | The same run after 20 minutes of sustained load on the device | Anything but time changing with thermal state |

`card` applies to CUDA on `trj` only; on Metal it is recorded `not-applicable: one device per process`. Every other
lane applies to both families. Under the OPEN-SPARK-4 fallback (no launch-graph capture) the lanes are unchanged:
they compare results, not launch mechanics.

**Procedure for one lane.**
1. Run arrangement A with digests at every commit; keep the run's identifier. Run arrangement B likewise.
2. Compare by the run-equality relation. Equal: the lane is `pass`.
3. Unequal: locate the first divergence by binary search over the chunk digest chain, then by step, stage, kernel
   and quantity (the procedure of N21b-33; the verb is `telemetry.divergence` in exact mode), store the
   first-divergence record in the divergence ledger, and mark the lane `fail`.
4. Record M, the number of device launches (dispatches or graph-node executions) executed by both arrangements
   and compared, read from the receipts, and the world-steps compared.

**The stated detection bound.** If a defect makes any one launch diverge with probability q independently, two
runs of M launches differ with probability 1 − (1 − q)^M. Zero differences over M compared launches therefore
bound q below 3/M at 95% confidence (the rule of three). The lane row stores M and 3/M. Planning figure
(HYPOTHESIS: about 60 launches per physics step, decimation 10): the short configuration is 1.2·10⁶ launches, a
bound of 2.5·10⁻⁶ per launch; the long one 6·10⁶ launches, 5·10⁻⁷. Measured counts replace the planning figure.
The bound is reported; it is never described as proof, which rests on the design rules and their lints.

**Arrangement knobs (conformance build only; none exists in a release build).** `--chunk-intervals N` (overrides
the chunk-length rule; the chunk length in force is a receipt field and digests must not depend on it);
`--group-multiple N` (thread-group size as a multiple of the execution width read from the pipeline);
`--workers N`; `--device gpu-cuda:0|1`; `--cache-dir <path>`; `--inject-faults seed=S,count=N`;
`--cancel-at seed=S,count=N` with automatic resume; `--mutant <name>` (N21b-42).

**The lanes record (DESIGN; record name `frob.determinism.lanes/1`, stored through the divergence ledger).**

```text
family, devices, driver, runtime, compiler, fingerprint digest
profile, precision profile, seed; per configuration: workload, worlds, intervals
per lane: arrangements A and B; result (pass | fail | not-run: reason | not-applicable: reason);
          launches compared M; world-steps compared; bound 3/M;
          first divergence (world address, interval, step, stage, kernel, quantity, both bit patterns)
negative controls: per mutant: caught (yes | no | not-discriminating), trial pairs, the lane that caught it
outcome: d2_run_to_run = holds | fails | not-established
row id: BLAKE3 of the canonical record (no wall-clock time inside the hash)
```

**Outcome rule (enumerated before any data are read).** `fails` if any applicable lane failed. Otherwise
`not-established` if any applicable lane was not run or a deterministic negative control was not caught. Otherwise
`holds`. The record is current only for its fingerprint digest: a driver, runtime or compiler change makes it
stale and the lanes run again.

**Consequences of `fails` for a family (no new refusal code).** The family's attainable class in device evidence
becomes D4 until a named defect is repaired and the lanes re-run. Through the existing class checks, a verb that
needs class D2 on that placement refuses with `FROB-REF-247` (the class a verb requires is not attainable on the
requested placement), a paired statistic with an arm there with `FROB-REF-561`, and attribution or a
counterfactual fork with `FROB-REF-562`. For Metal this is the determinism trigger of KILL-METAL (the decision
allows the repair of a named defect before the M2 exit and waives no unexplained difference). For CUDA the family
holds no controlled class and is dropped from M2 under the stop decision; if neither family holds one, M2 exits in
its no-GPU variant.

**The script.** `scripts/e2e/spark_determinism_lanes.sh [--tier gpu-cuda|gpu-metal] [--lanes all|<list>]
[--seed N] [--long]`. Conformance builds, release and debug. Defaults: each device tier of the host, all lanes,
short configuration; `--long` adds the long `repeat` pair.

| Step | Commands | Assertions |
|---|---|---|
| `devices` | `frob spark devices --json` | The family's devices are present with a current fingerprint; the record's key is that digest |
| `lane_<name>` (per lane and workload) | `frob sim run --tier <t> --workload Q --worlds 4096 --intervals 2000 --seed 1 --determinism device-replay <knobs of A> --json`; the same with the knobs of B; `frob telemetry divergence <runA> <runB> --mode exact --json` | Both runs exit 0 with no `Faulted` world; the comparison reports no divergence; M and 3/M logged |
| `long_repeat` (with `--long`) | The `repeat` pair at 8,192 worlds and 10⁴ intervals on Q | Equal |
| `in_process` | `frob spark check --rollout 2000 --backend <b> --workload Q --worlds 4096 --json` | The check's class D2 comparator (the same placement run twice gives byte-equal outputs) passes |
| `mutant_<name>` (per mutant) | The catching lane's two runs with `--mutant <name>` | The comparison reports a divergence; `nonce-in-state` is localized to its address, interval 1,000, kernel and quantity |
| `record` | `cargo test -p frob-conformance --test g5 -- determinism_lanes` over the lane results | One hash-named `frob.determinism.lanes/1` record per family; outcome computed by the rule; rows entered by a recording session that did not implement the work |

**Logging.** The script sources the STD-E2E helper and writes
`target/e2e-logs/spark_determinism_lanes/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
`bead`, `step`, `event`. `cmd` lines: exact command line, exit code, wall time. Result lines carry the envelope's
`evidence` block (claim known-answer, class, tier, determinism class, identities with the fingerprint digest,
seed). `metric` lines per lane: launches compared with the bound 3/M, world-steps compared, differing worlds
(threshold 0), differing commit ticks (threshold 0), both run digests at the final tick. On failure: the first
differing world address, interval, step, stage, kernel and quantity with both bit patterns, and the artifact paths
needed to reproduce (both run identifiers, the snapshot before the divergent step, the arrangement knobs). The
`summary` line counts assertions and names KILL-METAL (on Metal) and GATE-GAUNT-07. Digests are logged; state,
scene and design contents never are.

## Acceptance criteria

- [ ] On this Mac (Metal) and on `trj` (CUDA, both cards) every applicable lane passes on workloads Q and H in the short configuration: zero differing worlds and zero differing commit ticks, with M and the bound 3/M recorded per lane.
- [ ] The long `repeat` pair (8,192 worlds, 10⁴ intervals, workload Q) is equal on each family, or is recorded `not-run` with the reason if no envelope admits it.
- [ ] One `frob.determinism.lanes/1` record per family exists with outcome `holds`, `fails` or `not-established` computed by the enumerated rule, keyed by the fingerprint digest; a changed driver string makes it stale.
- [ ] Every deterministic mutant of N21b-42 is caught by its lane in the same session that passes the real lanes; each racy mutant is caught or recorded `not-discriminating`, never silently skipped.
- [ ] The comparison excludes only the listed timing fields: a planted difference in world-steps executed, in one event's termination cause or in one capacity high-water mark fails the lane.
- [ ] With a forced `fails` outcome (a mutant left enabled in a conformance configuration): a request needing class D2 on that placement returns `FROB-REF-247`; a paired comparison with an arm there returns `FROB-REF-561`; attribution returns `FROB-REF-562`.
- [ ] The Metal record is sufficient for the KILL-METAL decision (pass or fail, with the first divergence if it failed); each family's record supplies the class D2 input of the KILL-D1 decision and the device rows of GATE-GAUNT-07.
- [ ] The script exits 0 only when the outcome is `holds` for every family present; its log validates against the STD-E2E schema.

## Test plan

### Unit tests
- `lane_matrix_per_family` (`frob-conformance`): CUDA with two cards has 12 applicable lanes; Metal has 11 and `card` is `not-applicable: one device per process`; the reduced `batch-cpu` mode has 6 (`repeat`, `restart`, `workers`, `build`, `chunk`, `resume`).
- `common_commit_ticks`: chunk lengths 64, 8 and 1 over 2,000 intervals give 32 comparison points (64, 128, …, 1,984 and 2,000).
- `run_equality_exclusion_list`: two receipts differing only in wall time, device seconds and blocked seconds are equal; differing in world-steps executed, or in one termination cause, they are not.
- `detection_bound`: M = 1,200,000 gives 2.5·10⁻⁶; M = 6,000,000 gives 5·10⁻⁷; M = 0 gives `not-established`.
- `outcome_rule_enumeration`: all pass gives `holds`; one `fail` gives `fails` whatever else is missing; one `not-run` with no failure gives `not-established`; an uncaught deterministic mutant gives `not-established`.
- `resume_points_are_seeded`: seed 7 and count 5 give the same five chunk indices on every call, all strictly inside the run.
- `record_roundtrip_and_stable_id`: the record round-trips and its id does not change when only wall-clock fields change.
- `record_stale_on_fingerprint_change`.

### End-to-end script and logging
This bead is the script. A reduced mode runs the six `batch-cpu` lanes on workload Q at 256 worlds and 200
intervals with the deterministic mutants in continuous integration; it records no device outcome. The device mode
runs on both machines before the M2 exit and after any fingerprint change.

### Known answers and negative controls
- Known answers: the class D2 statement itself (identical bytes run to run and across worker counts); the commit
  fence's known answer (KA-537: final digests under injected faults equal those of the unfaulted run); the run
  digest under slot permutation (KA-535: unchanged, a wrapping sum keyed by address), which is why digests are
  compared by address.
- Counterexamples carried: CX-230 (0.999¹⁰⁰⁰ = 0.37) and CX-221 (a barrier stalling about once per few hundred
  launches).
- Negative controls: the ten mutants of N21b-42, each by its lane; a comparator that ignores the event stream
  (conformance variant; it must miss a planted termination-cause difference and so fail its own test).
- Metamorphic relations: equality must hold under each arrangement change the design declares irrelevant (chunk
  length, group size, worker count, build, card). MR-01 (batch-composition invariance) is BD-181's.
- Determinism lanes: this bead is the device half of them. Device against `batch-cpu` is N21b-35, each family
  against the class it holds.

## Considerations

- Cost. One short run is 8.2·10⁷ world-steps for Q (4,096 worlds, 2,000 intervals, decimation 10): about 41 s at
  the planning rate of 2.0 M world-steps/s on one RTX 4090 and about 164 s at a quarter of that on Metal (planning
  figures, not measurements; H is slower and its rate is not assumed). About fifty jobs per family, each within
  the default compute envelope of one device and one hour (OPEN-SPARK-2); the long pair on Metal may need an
  approved envelope and is otherwise `not-run`.
- A pass is a tripwire result with a stated bound. The design rules and their lints are the argument; the lanes
  check that the argument was implemented. Reports say "no difference observed in M launches", never "verified".
- `load` on the Mac may provoke a real GPU restart by the operating system, which aborts command buffers in flight
  (FACT from the gateway's documentation). That is the commit fence's case: the run must still end equal, with the
  retries counted. A `FROB-REF-607` after four attempts is recorded as a fault outcome and the lane is re-run once;
  it is not a determinism failure.
- NVRTC or the Metal compiler may emit byte-different binaries for identical source on two cold compiles. That
  alone is not a failure here (results are what is compared) but it is logged: the `cache` lane exists to show
  that results do not move with it.
- RISK-48 (a driver, system or binding update changes kernel results): the record is keyed by the fingerprint
  digest and goes stale with it. RISK-04 concerns cross-backend equality and belongs to KILL-D1.
- OPEN-SPARK-1: until the annex design is ratified every device result here is labelled exploratory; the lanes
  still run, since the kill decisions need them.
- If KILL-METAL fires on throughput alone, these lanes stay required for Metal as a development and replay tier.
