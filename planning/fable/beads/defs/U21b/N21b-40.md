## Background

`frob spark probe` is the user-visible capability that answers, for one device, three questions an agent or an
engineer must be able to ask before trusting a number from it: does its floating-point arithmetic match the CPU
reference bit for bit (and if not, where), do exact and guarded predicate kernels give identical decisions on it,
and did its compiler keep the error-free transformations that double-float accumulators need. Milestone M0's
deliverable list says in so many words that `frob spark probe` runs on both device families, and that the exact
and guarded predicate kernels give identical bytes on all placements. Two machines are involved: this Mac (an M5
Ultra; backend `gpu-metal`) and `trj` (a Linux host with two RTX 4090 and no link between them; backend
`gpu-cuda`). No single process can see all three GPUs, so the gate is assembled from two runs of one script and an
exchange of small report files.

Why the predicate classes need a gate of their own. **Exact** kernels use unsigned 32-bit integers and must return
the same bytes on every backend; **guarded** kernels evaluate an `f32` residual, decide when its magnitude exceeds
a certified error bound, and otherwise fall back to an exact integer evaluation, so their decisions are also
exact. The class exists because a strict inequality decided in bare floating point is wrong exactly where it
matters (16,777,216 < 16,777,217 is false in `f32`, since the second number rounds to the first). The evidence so
far is a plan-time pilot (FACT as recorded, run outside this repository): a one-inequality boundary classifier
with inputs on a grid of 2⁻²⁸, run as a real Metal command buffer on the M5 Ultra and as a CUDA kernel on each
RTX 4090 of `trj`, with readback and independent integer checking. On a 65,536-row grid dense near the boundary
the bare `f32` sign of the residual gave 452 false inclusions and 23,438 false exclusions, identically on every
device; the exact kernel returned every label correctly on all three GPUs with identical bytes; the guarded
kernel, deferring whenever the absolute residual was at most 2⁻²¹ (its error bound is 5·2⁻²⁵), decided none of the
dense grid on the device and 58,254 of 65,536 rows of a more widely spaced grid, with no error after fallback. The
plan requires these numbers to be **reproduced at GATE-SPARK-08 before any gate cites them**. GATE-SPARK-08 (known
answer, TARGET, M0) is an M0 exit condition for Spark.

This bead is the end-to-end script for that capability and the place where GATE-SPARK-01 and GATE-SPARK-08 are
assembled across hosts. It is the one end-to-end bead for both gates. The mechanisms are BD-017 (IEEE suite and the verb), BD-030 (boundary suite) and N21b-36
(canary suite). Tier: Solid.

## Scope

In: the script, its steps and assertions, its structured log, the peer-report exchange between the two hosts, the
two gate records, the reproduction of the recorded boundary pilot, and the later steps that other beads append to
this script when their kernels land.

Out: any kernel or comparison logic (in the three mechanism beads); the hardware fingerprint gate GATE-SPARK-07
(BD-029).

## Technical approach

**Invocation.** `scripts/e2e/spark_probe.sh [--quick] [--seed N] [--peer-report <file>] [--out <dir>]`. The script
discovers the devices of its host with `frob spark devices --json` and is otherwise identical on both machines. It
is idempotent (every `frob` call carries an idempotency key derived from the seed, the host and the step) and
seed-explicit (default seed 1; the seed is in every log line's evidence block). `--quick` runs the reduced suites
and can never record a gate.

**Steps.**

| Step | Commands | Assertions |
|---|---|---|
| `devices` | `frob spark devices --json` | At least `batch-cpu`; on this Mac one Metal device; on `trj` two CUDA devices. A missing family is logged as `not run` with the reason and fails the gate assembly, not the script's other steps |
| `canary` | `frob spark probe --suite canary --device <d> --json` for every device, then with the two folded mutant libraries, then the fast-math build | Four bit patterns equal 0x3F800000, 0x30800000, 0x3F801000, 0x33800000; each mutant fails; the fast-math outcome is logged as data |
| `ieee` | `frob spark probe --suite ieee --device <d> --json` | Completes (exit 0 or 2); mismatch counts per operation and stratum logged against threshold 0; contraction detector value logged; attainable class logged |
| `ieee_control` | the same with the contraction-on prelude; with the explicit fused kernel | Detector returns 2⁻²⁴ (bit pattern 0x33800000) and the report says `contraction: detected` |
| `boundary` | `frob spark probe --suite boundary --device <d> --json` for every device and for `batch-cpu`; on `trj` also the two-shard placement | Exact and guarded kernels: zero errors against the integer truth; bare kernel: at least one error; label digests equal across the host's placements |
| `strict` | part of `boundary`: the pair (2²⁴, 2²⁴ + 1) | Exact and guarded: true; bare: false (KA-529) |
| `pilot_reproduction` | computed from the `boundary` results of every device | The bare kernel's false inclusions and false exclusions on the dense grid are compared with the pilot's 452 and 23,438; the guarded kernel decides 0 rows of the dense grid on the device and 58,254 of the wide grid. A difference from the recorded pilot is reported with both numbers and does not by itself fail the gate (the gate's thresholds are zero errors and identical bytes), but it blocks citing the pilot's numbers |
| `receipts` | one probe call per placement with `--emit-receipts <dir>` (the M0 route to full receipts, N21a-02) | The receipt file has the twelve evidence fields, the fingerprint digest and the kernel class |
| `peer` | read `--peer-report` | Label digests, tie digests and the `batch-cpu` reference digest of the IEEE suite equal the peer host's |
| `report` | write `<out>/spark_probe_report.<host>.json` | The file holds the digests, counts, classes and probe digests of this host: bytes to kilobytes, the only thing that crosses machines |
| `gates` | `cargo test -p frob-conformance --test g0 -- GATE-SPARK-01 GATE-SPARK-08` with the two report files as inputs | With a peer report present the run writes a hash-named receipt holding the measured values of GATE-SPARK-01 per family and of GATE-SPARK-08 with the four placements' digests. The row in `registries/gates.toml` is entered by a recording session that did not implement the work; `pass` is refused if any registered control was not caught in the same run |

**Extension steps.** Later beads append steps to this same script; each is skipped with a logged reason until its
kernels are registered: `exact_ops` (N21a-17: every exact-integer operator on a seeded slab, suite `exact-ops`),
`classes` (N21a-22: the class of every kernel and the planted statistics feed), `digest` (N21a-23: per-world and
run digests, suite `digest`), and the IR-generated predicate kernels of BD-053 re-run through the `boundary`
suite.

**Compute envelope.** Each machine's run uses one device at a time and finishes in minutes; it fits the default
envelope (16 GiB, 8 cores, one hour, one device).

**Gate assembly rule.** GATE-SPARK-01 is a per-family known-answer gate: it is recorded when the full `ieee`
suite has completed on a family and its outcome (the mismatch counts and the attainable class) is stored. A family
that cannot hold bit equality still records the gate, with the outcome that feeds KILL-D1; the gate fails only if
the probe cannot be completed, its negative controls are not caught, or its host reference digests disagree between
the two machines. GATE-SPARK-08 passes only with zero errors and identical bytes on `batch-cpu`, both RTX 4090 and
Metal, and the guarded kernel's fallback fraction reported. The gate assembly refuses to record GATE-SPARK-08 as
passed with fewer than four placements. The receipt holds the measured values (errors per kernel per placement,
digests, fallback fraction per placement), the thresholds (0 errors; equal digests), the commit, both fingerprint
digests, the seed and the negative controls caught; a gate record without a caught negative control is refused by
the registry.

**Logging.** The script sources the shared helper of STD-E2E and writes newline-delimited JSON to
`target/e2e-logs/spark_probe/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line has
`ts`, `script`, `bead` (this key, and the mechanism bead of the step), `step`, `event` (`start`, `cmd`, `assert`,
`metric`, `refusal`, `end`). `cmd` lines: the exact command line, exit code, wall time. Every result line copies
the envelope's `evidence` block (claim, class, tier, determinism, identities, seed). `metric` lines: mismatch
counts with threshold 0 and unit `lanes`; the detector value; fallback fraction; device seconds, end-to-end
seconds, transfer bytes and synchronization count for the boundary suite; label digests. On failure: the first
differing value (for the IEEE suite the input bits, device bits and reference bits; for the boundary suite the row
(a, b, R) and both labels) and the artifact paths needed to reproduce (the report file, the dumped result chunk).
The final `summary` line gives assertions passed and failed and the gates touched. The corpus is synthetic integer
data; nothing private is logged.

**Exit status.** Non-zero if any assertion fails or any step cannot run; a host with a missing device family exits
non-zero after completing what it can, so that the log shows exactly what was and was not measured.

## Acceptance criteria

- [ ] The script runs to completion on this Mac and on `trj`, each producing a report file and a log that validates against the STD-E2E line schema.
- [ ] With each host's report given to the other as `--peer-report`, the `peer` step passes: identical label and tie digests on `batch-cpu`, both RTX 4090, the two-shard placement and Metal.
- [ ] GATE-SPARK-01 is recorded for the CUDA family and the Metal family with measured mismatch counts and the attainable class; GATE-SPARK-08 is recorded with the four digests and the fallback fractions.
- [ ] Every negative control in the script is caught: both folded canary mutants, the contraction-on prelude, the explicit fused kernel, the bare `f32` predicate.
- [ ] `--quick` completes in under five minutes on each host and records no gate.
- [ ] Running the script twice with the same seed produces identical report files apart from timing fields (which are outside the digest).
- [ ] A deliberately corrupted peer report (one digest changed) makes the `peer` step fail and names the placement.
- [ ] GATE-SPARK-08 thresholds are recorded as measured values: exact kernel 0 errors on 2 × 65,536 rows on each of the four placements; guarded kernel 0 errors after fallback on each; output digests of each kernel equal across the four placements; the strict-predicate case true on each; the guarded fallback fraction reported per placement.
- [ ] A planted exact-kernel mutant (one comparison made signed) is caught by the `boundary` step and named in the record.
- [ ] The pilot's numbers are either reproduced (452, 23,438, 0, 58,254) or the differences are recorded with both values and the citation of the pilot is marked blocked.
- [ ] On a host with no device the script runs the `batch-cpu` steps, logs the device steps as skipped with the reason, and the gate assembly refuses to record GATE-SPARK-08 as passed with fewer than four placements.

## Test plan

### Unit tests
- `e2e_log_schema_spark_probe`: a produced log validates against the STD-E2E line schema (every required key on every line; a final `summary`).
- `report_file_is_small_and_complete`: the report is under 64 kB and contains every digest the `peer` step reads.
- `peer_mismatch_detected`: the corrupted-report case.
- `script_is_idempotent`: a second run returns stored envelopes (`idempotent_replay: true`) for completed steps.
- `gate08_requires_four_placements`: two report files that together hold fewer than four placements cannot produce a passing GATE-SPARK-08 record (fixture JSON files, label `synthetic`).
- `gate_record_requires_negative_control`: a record with an empty list of caught negative controls is refused.

### End-to-end script and logging
This bead is the script. Its dry run on a host with no GPU exercises `batch-cpu` only: `devices`, `canary`,
`ieee` (the backend against its scalar twin), `boundary`, `report`; the gate steps log `not run: no device`.

### Known answers and negative controls
- KA-526 (contraction detector: 0 without contraction, 2⁻²⁴ with), KA-527 and KA-528 (canaries (1, 2⁻³⁰) and
  (1 + 2⁻¹¹, 2⁻²⁴)), KA-529 (2²⁴ < 2²⁴ + 1), KA-530 (boundary corpus, zero errors, identical bytes), KA-531 (guard
  bound 5·2⁻²⁵ under threshold 2⁻²¹), KA-540 (IEEE probe).
- Negative controls: listed in the acceptance criteria; each is an `assert` line with `expect: failure`. For the
  boundary corpus the bare `f32` kernel must mislabel at least one row (pilot: 452 false inclusions, 23,438 false
  exclusions) and answer false on the strict case.
- Counterexamples exercised: CX-216 (a strict inequality by bare `f32` comparison) and CX-217 (placement: the host
  loop was fastest end to end).
- Determinism lanes exercised by the script: twice on one machine (report equality); `batch-cpu` across worker
  counts {1, 2, 8}; debug and release; across the two hosts and three GPUs (digest equality for class D0 outputs;
  recorded class for `float` probes).

## Considerations

- `trj`'s CPU is often heavily loaded (FACT): the script asserts bits and counts, never time; times are logged as
  data only.
- The full IEEE suite moves tens of gigabytes between host and device memory; on `trj` it needs about 1 GiB of
  free device memory per card and is refused by admission if a card is busy (`FROB-REF-602`, the memory estimate
  exceeds the device budget; repair: fewer lanes per chunk).
- The default compute envelope (one device, one hour per GPU job, until the owner approves another; OPEN-SPARK-2)
  is ample for this script.
- GATE-SPARK-08 says nothing about speed. The same pilot is a negative placement result: end to end the host
  integer loop took about 34 µs against about 290 µs on Metal (under 13 µs of it device time) and over 1.2 ms on
  one RTX 4090, and two-card sharding was slower than one card. The script logs per-step wall and device seconds so
  that this is visible, and the placement planner's cost model (N21b-30) uses it as its cautionary case.
- KILL-MARROW-GUARD (a fallback rate above 10⁻² on the contact battery on either GPU backend, or an exact path
  that cannot be made bit-identical across backends) is decided later at M2; this gate's identical-bytes clause is
  its first data point. The contact-battery gate for guarded predicates is BD-182.
- The re-run of the plan-time boundary screen in guarded single precision (BD-043) uses the same corpus rule; its
  counts and this script's `pilot_reproduction` step must agree before any gate cites the pilot.
- If one device family fails its admission test at M0 (INT-CUDA-01 or INT-FT-01), the script still runs on the
  other and the gates are recorded `not run` for the missing family with the reason; M0's stop rule then decides
  whether that family is dropped from M2.
