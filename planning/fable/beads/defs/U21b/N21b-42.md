## Background

The project's rule for every gate is that a gate nothing can fail validates nothing: each gate carries at least
one negative control, a planted defect that the test must catch. The rule bites hardest on determinism tests. A
run-to-run comparison passes when two runs are equal, and two runs are also "equal" when the comparison forgot a
field, compared a run with itself, or never varied the thing the lane claims to vary. A lane that cannot be made
to fail has shown nothing.

The device determinism lanes (N21b-39) compare two arrangements of the same job on one device family and demand
identical bits: `repeat`, `restart`, `cache`, `workers`, `build`, `chunk`, `group`, `card`, `resume`, `fault`,
`load`, `soak`. This bead supplies their planted defects. Each mutant models a defect the plan names as a hazard
of device determinism (order of a reduction, results placed by arrival, draws consumed in sequence, a retry that
keeps part of its state, toolchain changes, hash-map iteration order, thread scheduling), and each is **keyed to
exactly the arrangement variable its lane varies**, so that it differs between the lane's two arrangements and
nowhere else. That gives two checks for the price of one: the lane catches its mutant (sensitivity), and other
lanes do not (the lanes are not twelve copies of one test).

Two kinds of defect need different treatment (DESIGN):
- *Deterministic* mutants differ with certainty when their key differs. They must always be caught.
- *Racy* mutants reproduce the real mechanism of GPU nondeterminism (FACT: floating-point atomics are its main
  source; a compaction that takes output positions from an atomic counter is the other classic). Their outcome
  depends on the scheduler, so a single equal pair proves nothing either way. They are admitted per device family
  only after they have shown they discriminate there.

The plan's own arithmetic says why rarity is no excuse: if 99.9% of windows replay bitwise, a campaign of a
thousand windows replays exactly about one time in three (0.999¹⁰⁰⁰ = 0.37; CX-230). Tier: Solid. Subsystem:
Spark, with the mutants living in the conformance crate so that no production crate contains a defect.

## Scope

In: the thirteen mutants (kernel variants in the shared dialect with Rust twins for `batch-cpu`; host variants
behind the conformance build); the `--mutant` loader; registry rows; the admission procedure for racy mutants;
the lint waivers; the guarantee that no mutant can reach a release build or a citable result.

Out: the lanes, their comparison and their record (N21b-39); the fence-disabled seam itself, which already exists
(N21b-07) and is registered here; planted defects of batch-composition invariance (N21b-33, BD-181); the other
Spark negative controls of the chapter's table (contraction, bare `f32`, strides, placement, cache bytes), which
their own beads carry.

## Technical approach

**Loader (DESIGN).** In a conformance build, `--mutant <name>[:<key>]` on `frob sim run` and `frob spark check`
either substitutes a variant kernel for one kernel of the step plan or flips one host seam. A variant kernel has
its own manifest and therefore its own `KernelId` and cache key, so it can never be served from, or pollute, a
production cache entry. Every receipt and envelope of a mutant run carries `conformance_mutant: <name>` and the
ledger stores the run as non-citable; a release build has neither the flag nor the variants.

**The mutants.** `n` below is the key the harness passes; "A" and "B" are the two arrangements of the lane.

| Mutant | What is planted | Keyed on | Lane that must catch it |
|---|---|---|---|
| `environment-nonce` | Kernel `K-mut-nonce`, inserted after integration, reads a `nonce` word the host writes into the control block from the count of environments created in this process, and at control interval 1,000 replaces the bit pattern b of velocity component 0 of one registered world address by b XOR (nonce AND 3) | Environment count in the process (1 for A, 2 for B) | `repeat` |
| `process-order` | Table preparation sums a registered three-term `f32` fixture in an order chosen by the process nonce: ((1 + 2⁻²⁴) + 2⁻²⁴) for an odd nonce, (1 + (2⁻²⁴ + 2⁻²⁴)) for an even one, and uploads the sum as a table constant that scales one joint's damping | Process launch (the harness passes nonce 1 to A and 2 to B; it stands for a hash-map's per-process seed) | `restart` |
| `compile-nonce` | A `#define` constant taken from a compile counter is prepended to one kernel's expanded source without entering the cache key | Cold compiles (0 for the first cold compile, 1 for the second) | `cache` (first cold compile against a second cold compile into another empty directory; the warm load of the first must equal the first) |
| `worker-keyed-draws` | Reset draws are taken from one sequential stream per host worker instead of from the stream keyed by (address, step, stream) | Host worker count | `workers` |
| `debug-fold` | The same three-term fixture summed in the first order under `cfg(debug_assertions)` and the second otherwise | Build profile | `build` |
| `counter-reset` | The control block's step counter, which keys the random streams, restarts from zero at each chunk start | Chunk length | `chunk` |
| `group-tree` | A per-world sum is taken sequentially inside each thread group and pairwise across groups, instead of by the fixed tree anchored at index 0 | Thread-group size | `group` |
| `card-constant` | The damping table constant of `process-order` chosen by the parity of the device ordinal | Device ordinal | `card` |
| `snapshot-without-warm-start` | The solver's warm-start slab is left out of the checkpointable state copied by the commit kernel | Whether a resume happened | `resume` |
| `fence-disabled` | A failed chunk is resubmitted without restoring the committed slab (the existing seam of the commit fence) | Whether a fault was injected | `fault` |
| `time-adaptive-iterations` | The host lowers the solver's iteration count by one for the next chunk whenever the previous chunk took more than 1.5 times its unloaded median | Chunk duration | `load`, `soak` |
| `float-atomic-sum` | A per-world sum of 4,096 addends of mixed magnitude (addend i is ±2^((i mod 24) − 12), signs alternating) accumulated into one cell by a compare-and-swap loop on the `u32` bit pattern of the running `f32` sum, and fed into state | Scheduling (racy) | `repeat`, within five trial pairs |
| `arrival-compaction` | Contact output positions taken from the value returned by an integer atomic wrapping add on a per-world counter, instead of from the count, exclusive-scan, write compaction | Scheduling (racy) | `repeat`, within five trial pairs |

**Worked values the tests assert.**
- The order-sensitive fixture, in `f32`: 1 + 2⁻²⁴ is a tie that rounds to even, giving 1; adding 2⁻²⁴ again gives
  1. In the other order 2⁻²⁴ + 2⁻²⁴ = 2⁻²³, and 1 + 2⁻²³ is the next float above 1. So the two orders give bit
  patterns 0x3F800000 and 0x3F800001, one unit in the last place apart.
- `environment-nonce` with nonces 1 and 2 gives b XOR 1 and b XOR 2. Their ulp distance is 1 when the low two bits
  of b are 00 or 11, and 3 when they are 01 or 10. The lane's first-divergence record must name that world
  address, control interval 1,000, kernel `K-mut-nonce` and velocity component 0, with one of those distances.
  With 6 intervals per chunk, interval 1,000 lies in chunk 167 (intervals 997 to 1,002, counting from 1).

**Specificity (DESIGN).** Each deterministic mutant is run through its own lane, which must fail, and through
`repeat`, which must pass for every mutant except `environment-nonce` (their keys do not change inside one
process, one build, one chunk length, one group size and one card). `environment-nonce` must pass `restart`
(both processes create their first environment). A mutant that fails a lane it is not keyed on is itself
defective and is rejected by its own test.

**Timing mutant.** `time-adaptive-iterations` is deterministic given chunk durations and is caught only if the
lane's load pushes at least one chunk past the threshold. The lane logs how many chunks crossed it. If none did,
the control is recorded `not-discriminating: load too light` and the lane's load generator is strengthened; it is
not counted as caught.

**Admission of a racy mutant (per device family).**
1. Run 20 trial pairs of the short configuration with the mutant.
2. If at least 19 pairs differ, register it for that family with the observed rate.
3. Otherwise record `not-discriminating` on that family with the rate, and do not count it for or against any
   lane there. (A serial encoder may execute a race reproducibly; that is a fact about the family worth
   recording, not a defect of the lane.)
4. Re-run admission after any fingerprint change.

**Lint waivers.** The dialect lint bans floating-point atomics and permits integer atomics only for maximum,
minimum, bitwise or and wrapping add. `float-atomic-sum` uses a compare-and-swap, which the lint rejects;
`arrival-compaction` uses only a permitted operation but uses its returned value as an index, which makes the
output depend on arrival order. Both carry a waiver marker that the lint honours only inside
`crates/frob-conformance/`. Whether the lint rejects `arrival-compaction` without the waiver is recorded as a
finding for the lint's owner (BD-013): if it does not, the lint has a gap that this mutant documents.

**Layout.** `crates/frob-conformance/src/mutants/determinism/` (host seams and Rust twins),
`crates/frob-conformance/kernels/mut/` (dialect variants), rows in `registries/negative_controls.toml` (id, plant,
key, expected lane, expected localization where one exists, tier G5, backends, owner test), run by
`frob-conformance::negctl::run(id)`.

## Acceptance criteria

- [ ] Thirteen rows exist in `registries/negative_controls.toml`, each with plant, key, expected lane, backends and owner test; the `fence-disabled` row is the commit fence's existing row (registry id `spark.fence-disabled`, registered by N21c-31 for the seam of N21b-07) with its lane added, not a duplicate.
- [ ] On `batch-cpu`, on CUDA and on Metal, every deterministic mutant applicable to the backend is caught by its lane and passes the lane named in the specificity rule.
- [ ] `environment-nonce` is localized exactly: the registered world address, control interval 1,000, kernel `K-mut-nonce`, velocity component 0, ulp distance 1 or 3.
- [ ] The two fixture orders produce 0x3F800000 and 0x3F800001 on every backend and in the host table code.
- [ ] Each racy mutant has an admission record per device family: registered with at least 19 differing pairs of 20, or `not-discriminating` with its observed rate.
- [ ] A release build rejects `--mutant` as an unknown parameter (a refusal, not a default), contains no variant kernel in its registry, and the dialect lint fails on both racy sources when they are placed outside the conformance crate.
- [ ] A mutant run's envelope carries `conformance_mutant` and the result cannot be cited as evidence or served from the kernel cache under a production key.

## Test plan

### Unit tests
- `fixture_orders_differ_by_one_ulp`: the two sums give 0x3F800000 and 0x3F800001, in Rust and through each dialect prelude.
- `nonce_xor_distances`: for b with low bits 00, 01, 10, 11 the distances between b XOR 1 and b XOR 2 are 1, 3, 3, 1.
- `nonce_chunk_arithmetic`: interval 1,000 with 6 intervals per chunk is chunk 167.
- `mutant_kernel_ids_distinct`: every variant's `KernelId` and cache key differ from those of the kernel it replaces.
- `mutant_keys_are_single_variable`: table-driven; for each deterministic mutant, changing only its key changes the output and changing any other arrangement variable does not (on `batch-cpu`).
- `worker_keyed_draws_differ`: 1 worker against 8 workers gives different reset states for the same addresses; the address-keyed production path gives identical ones.
- `counter_reset_depends_on_chunk_length`: chunk lengths 64 and 8 give different draws at interval 9 under the mutant (counter 8 against counter 0) and identical draws in production.
- `group_tree_depends_on_group_size`: group sizes 32 and 64 give different sums on the registered 64-addend fixture under the mutant; the production tree gives the same sum.
- `warm_start_omitted_changes_resume`: one cancel and resume changes the next step's solver output under the mutant only.
- `racy_admission_rule`: 18 differing pairs of 20 leaves a mutant unregistered; 19 registers it.
- `release_build_has_no_mutants`: the release binary's capability listing and kernel registry contain no mutant name.
- `lint_rejects_racy_sources_outside_conformance`.

### End-to-end script and logging
The mutants run inside `scripts/e2e/spark_determinism_lanes.sh` (N21b-39), steps `mutant_<name>`, on each device
family, and in that script's reduced `batch-cpu` mode in continuous integration (deterministic mutants only). Each
step logs through the STD-E2E helper: the two command lines with exit codes and wall times, the mutant and its
key in each arrangement, the envelope's `evidence` block with `conformance_mutant`, whether a divergence was
reported (expected: yes), the first-divergence record against the expected localization, and for racy mutants the
trial count and differing count against the admission threshold (19 of 20). A mutant that is not caught fails the
script with the lane named.

### Known answers and negative controls
- Known answers: the fixture bit patterns; the XOR distances; the chunk index of interval 1,000.
- Counterexamples carried: CX-230 (0.999¹⁰⁰⁰ = 0.37); the sequential-draw case of the numerics chapter (one extra
  draw shifts every later draw, which is what `worker-keyed-draws` and `counter-reset` reproduce).
- Controls on the controls: a mutant whose plant is compiled out (an empty variant) must be reported as not
  caught; the specificity rule rejects a mutant that fails a lane it is not keyed on.
- Determinism lanes: every deterministic mutant gives the same divergence record on repeat; racy mutants are
  exempt by definition and say so in their rows.

## Considerations

- The mutants are deliberately small edits of real kernels and seams, so they keep working as the step evolves;
  each has an owner test that fails loudly if the kernel it patches is renamed or restructured.
- `float-atomic-sum` on Metal: the shading language's atomic types are integer; the compare-and-swap on a bit
  pattern is the way to plant the defect in both source languages with one text. If a backend's compiler rejects
  the construct, the mutant is recorded `unavailable` on that family with the diagnostic.
- The racy mutants must feed state, not statistics, or the comparison of state digests would not see them; they
  therefore run only in conformance jobs and never beside a citable job in one environment.
- Mutant runs consume device time: thirteen mutants times two short runs, plus 20 trial pairs for each racy one
  per family at admission. All fit the default compute envelope of one device and one hour per job
  (OPEN-SPARK-2).
- Security and supply chain: variants are source in the repository, compiled only by a conformance build; nothing
  is fetched, and the kernel cache of a production installation never receives a variant's entry.
- U21c's negative-control beads register the mutants of the chapter's own known-answer table (among them the
  disabled fence). The fence seam is one mechanism with one registry row; this bead references that row for the
  `fault` lane and does not create a second.
