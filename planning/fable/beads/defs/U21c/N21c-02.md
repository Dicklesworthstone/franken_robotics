## Background

The hardware fingerprint (`frob.fingerprint/1`) has, per device, an `arithmetic` block:

```text
arithmetic: IEEE probe digest and attainable class; subnormals (ieee | flush | mixed);
            64-bit integers (yes | no); 64-bit atomics (yes | no); canaries (pass | fail)
```

These are discrete facts, and other mechanisms branch on them:

- **Dialect rule 7.** Integer arithmetic in exact kernels is unsigned and 32 bits wide. Sixty-four-bit integers and
  atomics are used only where the fingerprint records them for *every device family in use*. A device lacking a
  feature a kernel declares is refused with `FROB-REF-616` (first repair: the 32-bit variant, or another backend).
- **Counts beyond 2³².** Histogram bins are 32-bit and are drained by the host because 64-bit atomics cannot be
  assumed. FACT to recheck (a reported compile probe on the M5 Ultra): Metal Shading Language 3.2 and 4.0 offer no
  64-bit integer atomic add and no 64-bit compare-and-swap. The fingerprint is the place where that report is
  re-run and becomes a measurement.
- **Language version.** FACT (read in source): the `metal` 0.33.0 binding under `ft-kernel-metal` 0.1.3 ends its
  language-version enumeration at Metal Shading Language 3.1; dialect sources therefore use no construct newer
  than 3.1, and the admission test of the gateway records the version it compiles under.
- **Determinism class.** Whether a device family can hold bit equality with the CPU reference (class D1) is set by
  the IEEE probe; whether it flushes subnormals is recorded, never assumed (Apple confirmed that Metal offers no
  control over rounding mode or subnormal handling; FACT).
- **Double-float accumulators.** A device whose compiler folds an error-free transformation fails a start-up canary
  and is refused for double-float kernels (`FROB-REF-609`).

Rejected alternative: reading feature support from documentation or from a device-family table. A table goes stale
with a driver or operating-system update; a compile-and-run probe cannot.

## Scope

In: the compile-and-run probes for 64-bit integers and 64-bit atomics on CUDA and Metal; recording the language
version; copying the IEEE probe digest, attainable class, subnormal class and canary results into the `arithmetic`
block by reference to their reports. Out: the IEEE probe itself (`spark.probe`, BD-017); the canary kernels; the
record schema and verb (BD-029); the enforcement of rule 7 at plan time (N21c-42).

## Technical approach

DESIGN, in `frob-kernels::fingerprint::features` with annex implementations.

1. **Baseline probe.** `P-u32-atomic`: 4,096 threads each perform one wrapping atomic add of 1, one atomic max
   with their index and one atomic or with 1 ≪ (index mod 32) on three `u32` cells. Expected (4096, 4095,
   0xFFFFFFFF). If this fails to compile or returns anything else, every feature below is `unavailable` with the
   reason "baseline atomic probe failed": a broken harness must never be read as a missing feature.
2. **64-bit integers.** `P-u64-arith` computes, in 64-bit unsigned arithmetic, 0xFFFFFFFF + 1 and
   0xFFFFFFFF × 0xFFFFFFFF and stores the low and high 32-bit words. Expected (0, 1) and (1, 0xFFFFFFFE).
   Result `yes` if it compiles and matches; `no` with the digest of the compiler diagnostic if it does not compile
   or mismatches.
3. **64-bit atomics.** `P-u64-atomic-add`: a 64-bit cell initialized to 2³² − 8; 16 threads each atomic-add 1;
   expected 2³² + 8, read as words (8, 1). `P-u64-atomic-cas`: 16 threads loop compare-and-swap to increment a
   64-bit cell from 2³² − 8; same expectation. The field is `yes` only if both compile and both return the expected
   words in 100 repetitions; otherwise `no`, with which of the two failed and the diagnostic digest. The probe is
   compiled at the language version the gateway uses, and, where the binding allows a newer version, at each
   newer version, recording per version.
4. **Language version.** On Metal the version passed to the compiler by the gateway; on CUDA the NVRTC version and
   target architecture (for example `sm_89`). Stored in the device's `compiler` field and repeated here.
5. **IEEE probe, subnormals, class.** The `spark.probe` report is content-addressed; this bead stores its digest,
   the attainable class it concluded (D1 if every compared operation was bit-equal to `batch-cpu`, otherwise the
   best class it supports) and its subnormal verdict: `ieee` (subnormal results and operands handled per IEEE),
   `flush` (results or operands flushed to zero), `mixed` (differs by operation; the list is in the report). If no
   probe report exists for the current driver and compiler the fields are `unavailable: probe not run`.
6. **Canaries.** `pass` only if both hold on this device and build: the error-free sum of 1 and 2⁻³⁰ returns the
   pair (1, 2⁻³⁰); the error-free product of 1 + 2⁻¹² with itself by the split product (splitter 4097 = 2¹² + 1)
   returns (1 + 2⁻¹¹, 2⁻²⁴).
7. **Family view.** A helper `features_common(devices) -> FeatureSet` returns the intersection over a set of
   devices; it is what a mixed run consults.

Every field is `yes`, `no`, a value, or `unavailable` with a reason. Outputs are exact (class D0): two runs on one
machine state must agree on every field.

## Acceptance criteria

- [ ] On the M5 Ultra and on each RTX 4090 the `arithmetic` block is complete: each field measured or `unavailable` with a reason.
- [ ] The 64-bit atomic field on Metal is a measured `yes` or `no` with the compiler diagnostic digest; the reported absence is confirmed or contradicted in writing in the admission record.
- [ ] Two runs agree on every field of the block (the discrete half of GATE-SPARK-07).
- [ ] The Metal language version and the 64-bit atomic result are present in the record (the fingerprint clause of GATE-WS-06).
- [ ] The lost-update mutant is reported `no`; the unrelated-syntax-error mutant is reported `unavailable`, not `no`.
- [ ] `features_common` over {cuda, metal} returns `no` for a feature that either lacks.

## Test plan

### Unit tests

- `u64_arith_words`: host reference gives (0, 1) and (1, 0xFFFFFFFE).
- `u64_atomic_expected_words`: 2³² − 8 + 16 = 4,294,967,304 = words (8, 1).
- `features_intersection`: {yes, no} gives no; {yes, unavailable} gives unavailable.
- `baseline_failure_masks_features`: with the baseline probe forced to fail, all three feature fields are `unavailable`.
- On device: `probe_u32_atomic_baseline`, `probe_u64_arith`, `probe_u64_atomic_add`, `probe_u64_atomic_cas`, each asserting the words above or the recorded `no`.

### End-to-end script and logging

Steps of `scripts/e2e/spark_fingerprint.sh` (N21c-06): `frob spark fingerprint --device all --json`; `assert`
events compare the `arithmetic` block of two runs field by field; a `metric` event per probe gives the returned
words and the expected words; a compile failure logs the diagnostic digest and the artifact path of the diagnostic.

### Known answers and negative controls

Known answers: the words above; canaries KA-527 (1, 2⁻³⁰) and KA-528 (1 + 2⁻¹¹, 2⁻²⁴). Negative controls: a prelude
that implements the "64-bit atomic add" as a plain load, add and store under contention (lost updates give a count
below 2³² + 8; must be `no`); a probe source with an unrelated syntax error (must be `unavailable`); a build with
fast math on (canaries must report `fail`). Lanes: twice on one machine; debug and release; both backends.

## Considerations

- The answer on Metal may change with an operating-system release; the fingerprint's identity fields include the
  build, so a change produces a new record and re-runs the probe.
- A `yes` on one family does not license a kernel in a mixed run; only `features_common` does.
- The canary result is also checked at every device start-up; this bead records the fingerprint-time value.
