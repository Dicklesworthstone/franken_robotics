## Background

`spark.devices` is one of Spark's seven verbs (with `spark.fingerprint`, `spark.probe`, `spark.check`,
`spark.precompile`, `spark.place`, `spark.cache`). The verb registry describes it as: kind `read`, first milestone
M0, "devices with capabilities, ceilings and current fingerprint digests". `spark.fingerprint` writes the hardware
fingerprint record; `spark.devices` lists devices with their current digests. It is the first thing an agent calls
to learn what hardware a session has, and the dashboard's Devices panel is built on it together with `job.list`.

Why it exists as its own verb: the project's rule is that an agent must be able to tell acceleration from a silent
fallback before anything runs, and that a receipt whose fingerprint no longer matches the machine is refused as
evidence (`FROB-REF-606`). An agent therefore needs a cheap, read-only way to see, per device, whether a current
fingerprint exists, which determinism class the device can attain and what its memory ceilings are, without
spending the twenty minutes a full fingerprint costs.

Build fact that shapes the verb (DESIGN of the workspace): the core workspace never depends on a GPU crate
(INV-SPARK-01). Device backends live in annex workspaces (`spark/frob-spark-cuda`, `spark/frob-spark-metal`) and
binaries that use a GPU are built from an `apps/` workspace that links the core and an annex. A binary built
without an annex still answers this verb, with the CPU backend only.

## Scope

In: the verb's registry entry, schemas, handler, CLI rendering, exit codes and tests. Out: measuring a fingerprint
(BD-029, N21c-01, N21c-02); the staleness rule itself (N21c-05); the residency map of slabs (`spark.place`);
cache contents (`spark.cache`); queue and role information for two machines (`fleet.status`, N21c-15).

## Technical approach

**Registry entry** (`registries/verbs.toml`). The row is VERBS-spark's, a dependency, and the fields below repeat
it: owner `frob-cli`, MCP tool `spark_devices`, purpose "Devices with capabilities, ceilings and current
fingerprint digests", task clusters `devices`, `fleet`; if the two ever differ, the registry row governs. The
optional inputs `device` and `recheck` below are this bead's DESIGN, and VERBS-spark's row lists both.

```toml
[[verb]]
name = "spark.devices"
cluster = "spark"
kind = "read"
tier = "S"
capabilities = ["spark:read"]
input_schema = "frob.spark.devices.in/1"
output_schema = "frob.spark.devices.out/1"
refusals = []
idempotent = true
cost_model = "static: under 1 s; no kernel is launched"
first_milestone = "M0"
task_clusters = ["devices", "fleet"]
owner = "frob-cli"
purpose = "Devices with capabilities, ceilings and current fingerprint digests"
examples = ["frob spark devices --json"]
```

**Input.** Optional `device` (an identifier such as `cuda:0`, `cuda:1`, `metal:0`, `batch-cpu`); optional
`recheck` (default true): re-read the cheap identity fields from the live machine before reporting currency.

**Output (`result`).** `machine` (host, operating-system build, CPU model, performance and efficiency core counts,
memory) and `devices[]`, each with:

| Field | Content |
|---|---|
| `id`, `family`, `name`, `stable_id`, `architecture` | `cuda` or `metal` or `cpu`; the driver's name; a stable identifier; for example `sm_89` |
| `driver`, `runtime`, `compiler` | Versions as the fingerprint records them |
| `state` | `available`, `lost`, `stalled` or `not-linked` (the annex is not in this binary) |
| `memory` | total, free now, working-set limit, largest single buffer, and the **device budget** used at admission: on the Mac 85% of the working-set limit by default (a host reserve, since CPU allocations share the pool); on a card the usable figure the estimator uses |
| `ceilings` | largest single buffer; buffer arguments per kernel (31 on Metal today); execution width; thread-group memory limit; worlds of the reference quadruped and humanoid workloads that fit by the byte model (about 35 kB and 97 kB per world) |
| `capabilities` | the `arithmetic` block: attainable determinism class, subnormals (`ieee`, `flush`, `mixed`), 64-bit integers, 64-bit atomics, canaries; peer access |
| `fingerprint` | `digest` of the stored record or null; `status`: `current`, `stale` (with the first identity field that differs and both values) or `missing`; `measured_at` |
| `thermal` | the state read now (the Mac's thermal state; a card's temperature) |
| `annexes_linked` | which backends this binary contains |

**Behaviour.**
1. Enumerate the CPU backend and every linked annex's devices. A device that the driver reports but that fails to
   open is listed with `state: lost`; the verb does not refuse.
2. For each device load the stored fingerprint record for this host, if any; if `recheck`, re-probe identity fields
   only (no rates, no kernels) and compute `status` with the rule of N21c-05.
3. Exit 0 when every listed device is `available` with a `current` fingerprint; exit 2 (completed with flags) when
   any device is `lost`, `stalled`, `stale`, `missing` or has failed canaries, with one `warnings[]` entry per
   flag and a `next_actions[]` entry `frob spark fingerprint --device <id>` for each stale or missing one.
4. The envelope's `evidence` block: class `Tested` for discrete fields copied from a current fingerprint, tier
   `static`, determinism `exact`; `claims` empty; `reality: no-claim`.
5. Without the daemon the verb runs in process and the envelope says so; with the daemon it reads the daemon's
   device table (the daemon owns devices).

Human rendering: one line per device with family, name, memory, class, fingerprint status. `--json` writes exactly
one envelope. Nothing is written to the ledger (a read verb changes nothing).

## Acceptance criteria

- [ ] `frob spark devices --json` on the Mac lists `batch-cpu` and `metal:0`; on `trj` it lists `batch-cpu`, `cuda:0` and `cuda:1`; a binary without annexes lists `batch-cpu` and `annexes_linked: []`.
- [ ] Each device's `fingerprint.digest` equals the digest of the record written by `spark.fingerprint`; with no record the status is `missing` and the exit code is 2.
- [ ] After a simulated driver-version change the status is `stale`, naming `driver` with both values.
- [ ] The Mac's ceilings reproduce the starting values: a working-set limit of about 222.7 GiB and a largest single buffer of about 167.0 GiB; each card reports about 24 GB (24,564 MiB).
- [ ] The verb launches no kernel and allocates no device memory (allocated-bytes counter unchanged); it returns in under 1 s (TARGET).
- [ ] The MCP tool `spark_devices` returns the same envelope; the verb is in the registry-generated refusal table with an empty chapter list, so its generated refusals are exactly the surface-wide codes appended to every verb (`FROB-REF-720`, 723, 724 and 802; its inputs have no `int53` property, so no 808); output validates against `frob.spark.devices.out/1`.
- [ ] This bead's own script `scripts/e2e/spark_devices.sh` passes on the Mac and on `trj`.

## Test plan

### Unit tests

`cargo test -p frob-kernels devices` and `-p frob-verbs spark_devices`:
- `devices_cpu_only_when_no_annex`.
- `devices_status_missing_current_stale`: three stored-record fixtures (`synthetic` records) give the three statuses; the stale one names the differing field.
- `devices_budget_is_85_percent_of_working_set`: a working-set limit of 222.7 GiB gives a budget of 189.3 GiB.
- `devices_world_ceilings`: a budget of 189.3 GiB (203.3 GB) and 35 kB per world give about 5.8 M worlds; at 97 kB about 2.1 M.
- `devices_exit_code_2_on_flag`, `devices_schema_roundtrip`, `devices_lost_device_is_listed_not_refused`.

### End-to-end script and logging

This bead's own script, `scripts/e2e/spark_devices.sh`, built only on its dependencies (the verb `spark.fingerprint`
of BD-029 and the currency rule and debug seam of N21c-05), on the run's own empty state root (`e2e_init` exports
`FROB_STATE`), debug build, one device `<id>` of the host (`metal:0` on the Mac, `cuda:0` on `trj`):
(1) `frob spark devices --json`: exit 2, every device `fingerprint.status: missing`, one `warnings[]` entry per
device and a `next_actions[]` entry `frob spark fingerprint --device <id>`; (2) `frob spark fingerprint --device
<id> --no-soak --key sd-fp-<run-id> --json` (a `run` verb, keyed); (3) `frob spark devices --device <id> --json`:
exit 0, `current`, `fingerprint.digest` equal to the record's `digest`; (4) the same call under N21c-05's seam
`FROB_INJECT_IDENTITY=driver=0.0.0-planted`: exit 2, `stale`, naming `driver` with both values; without the seam
it is `current` again; (5) around every call the device's allocated-bytes counter is unchanged and the wall time
is under 1 s. Logged through the STD-E2E helper to `target/e2e-logs/spark_devices/<utc>.ndjson` with a transcript:
`ts`, `script`, `bead` ("N21c-04"), `step`, `event`, the exact command line, exit code, wall time, the envelope's
`evidence` block, each device's `state` and `fingerprint.status`, the digests compared, the allocated bytes before
and after, on failure the first differing field and the state root's path, and a `summary` line. The full lifecycle
on both machines with full fingerprints (steps 2, 9 and 11 of `scripts/e2e/spark_fingerprint.sh`) is N21c-06's,
which depends on this bead.

### Known answers and negative controls

KA-546 for the starting values. Negative controls: a planted handler that reports `current` without re-probing
identity must fail the stale-driver step; a planted handler that launches a kernel must fail the allocation and
latency assertions. Lanes: twice on one machine with identical output apart from `free now` and `thermal`.

## Considerations

- `free now` and `thermal` are live readings and are excluded from any digest or equality assertion.
- The usable-memory figure on a card (16 to 19 GB of 24) is an assumption until the estimator's high-water marks
  are measured at M2; the verb prints what the estimator uses and labels it.
- Multi-agent use: the verb exposes no other agent's jobs; slot and job information is `job.list`'s.
