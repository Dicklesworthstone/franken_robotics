## Background

GATE-SPARK-07 (claim: Known answer; earliest milestone M0) reads: fingerprints of both machines are **complete**
(every field measured, or `unavailable` with a reason), **repeatable** (two runs agree on every discrete field and
within 5% on every rate), and **reproduce the starting values**. The starting values are the only hardware facts
the plan records about its two machines (FACT, read from the machines):

- the Mac Studio: an M5 Ultra with 36 CPU cores, an 80-core GPU and 256 GB of unified memory; its Metal device
  reports a working-set limit of about 222.7 GiB and a largest single buffer of about 167.0 GiB;
- the Linux host `trj`: two RTX 4090 of 24 GB each (the driver reports 24,564 MiB), with no link between them;
- 64-bit atomics are reported absent on Metal, to be re-run by the fingerprint.

Everything else about the machines (bandwidth, launch costs, compile times, peer access) is unmeasured and is not
assumed anywhere. The gate matters beyond itself: the eighth condition of "implemented" for every capability is a
recorded PASS in a receipt that names the commit, the **hardware fingerprint** and the seed, so no later gate on a
device can be recorded before this one.

This bead is the end-to-end script that drives the fingerprint from the user's side on each machine, covers the
whole lifecycle (missing, measured, listed, re-measured, changed, refused), and produces the gate record. It is the
one script for the capability "know your hardware": the verbs `spark.fingerprint` and `spark.devices` and the
refusal `FROB-REF-606`.

## Scope

In: the script, its assertions, its negative controls, the combination of the two machines' receipts into one gate
record. Out: the probes and verbs it drives (BD-029, N21c-01 to N21c-05).

## Technical approach

**Script.** `scripts/e2e/spark_fingerprint.sh --host mac|trj [--quick] [--state-root DIR]` and
`scripts/e2e/spark_fingerprint.sh --combine <mac.receipt.json> <trj.receipt.json>`. Plain shell over the real
`frob` binary from the `apps/` workspace of the host's annex; sources the shared helper of the end-to-end harness;
idempotent (a scratch state root under `target/e2e-state/spark_fingerprint/`, removed at start); seed-explicit
(probes take no random input; the seed field is logged as `none`). `--quick` skips the 20-minute soak and can never
record the gate.

**Steps on one host.**

1. `frob doctor --json`: build identity, annexes linked.
2. `frob spark devices --json` on the empty state root: expect exit 2, every device `fingerprint.status: missing`.
3. A small device job before any fingerprint (`frob spark check --kernel K-cay-step --device <id> --json`): expect
   exit 6, `FROB-REF-606`, first repair `frob spark fingerprint`. Then `frob spark probe --device <id> --json`:
   expect it to run (the two measuring verbs are exempt, because the fingerprint cites the probe report) and to
   cite the live identity.
4. `frob spark fingerprint --device all --json` (run A, full, with soak). Store the record and its `digest` and
   `identity`.
5. `frob spark fingerprint --device all --json` (run B).
6. **Completeness.** Walk every leaf of both records against the schema: a leaf is a value, or `unavailable` with a
   non-empty reason. Count measured and unavailable leaves.
7. **Repeatability.** `identity` of A equals `identity` of B and every discrete field is equal. For every rate
   (median figures), relative difference |a − b| ÷ ((a + b)/2) ≤ 0.05.
8. **Starting values.** On `mac`: performance plus efficiency cores = 36; GPU cores = 80; memory = 256 GB as
   reported; working-set limit within 0.1 GiB of 222.7 GiB; largest single buffer within 0.1 GiB of 167.0 GiB;
   64-bit atomics is a measured `yes` or `no` (a `no` confirms the report; a `yes` is logged as a contradiction of
   the report and does not fail the gate). On `trj`: exactly two `cuda` devices; each total 24,564 MiB; `peer`
   block present.
9. `frob spark devices --json`: expect exit 0, `current`, digest equal to run B's.
10. The same small device job: expect exit 0 and a receipt citing run B's digest.
11. Plant an identity change (debug build seam `FROB_INJECT_IDENTITY=driver=0.0.0-planted`): `frob spark devices`
    reports `stale` naming `driver`; the device job refuses with `FROB-REF-606`.
12. Write the host receipt `target/e2e-logs/spark_fingerprint/<utc>.<host>.receipt.json`: commit, both digests,
    counts, the largest rate difference with its field, the starting-value comparisons.

**Combine.** Reads the two host receipts (receipts are a transfer class that may cross machines), checks both are
full runs of the same commit, and records the gate through the conformance target
(`cargo test -p frob-conformance --test g1 -- GATE-SPARK-07`), which writes the row in `registries/gates.toml` with
measured values, not targets.

**Logging.** Newline-delimited JSON at `target/e2e-logs/spark_fingerprint/<utc-timestamp>.ndjson` with a transcript
beside it. Every line: `ts`, `script`, `bead` ("N21c-06"), `step`, `event` (`start`, `cmd`, `assert`, `metric`,
`refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block, measured values
with units and thresholds (each rate pair with its relative difference against 0.05; each starting value against
its expected value and tolerance), the digests compared, and on failure the first differing field with both values
and the paths of both records. Final `summary`: assertions passed and failed, measured and unavailable leaf counts,
`gates: ["GATE-SPARK-07"]`, the host.

## Acceptance criteria

- [ ] The script exits 0 on the Mac and on `trj` in full mode, and `--combine` records GATE-SPARK-07 with the measured values of both machines.
- [ ] Every leaf of both machines' records is measured or `unavailable` with a reason; the counts are in the receipt.
- [ ] Discrete fields agree between runs A and B; the largest relative rate difference is at most 5% and is recorded with its field name.
- [ ] The starting values are reproduced within the tolerances of step 8.
- [ ] Steps 2, 3 and 11 return exit codes 2, 6 and 6 with `FROB-REF-606` where stated.
- [ ] All four negative controls below are caught (the script's `--self-test` mode exits 0 only if each mutant fails its assertion).
- [ ] A `--quick` run ends with `summary.gate_recordable: false`.

## Test plan

### Unit tests

Helpers in the script's support library (`scripts/e2e/lib/fingerprint_checks.sh` with a small Rust helper in
`frob-conformance`): `rel_diff` (100 and 105 give 0.0488, pass; 100 and 106 give 0.0583, fail); `leaf_walk` counts
leaves of a `synthetic` record with three `unavailable` fields; `starting_value_check` accepts 222.68 GiB and
rejects 221.9 GiB.

### End-to-end script and logging

This bead is the script, as specified. Run time TARGET: under 50 minutes per host in full mode (two soaks), under
3 minutes with `--quick`.

### Known answers and negative controls

Known answer KA-546 (the starting values; two runs agreeing on every discrete field and within 5% on every rate).
Negative controls, run by `--self-test` against `synthetic` mutant records derived from run A: (1) one field
silently omitted (completeness must fail); (2) one rate changed by 6% (repeatability must fail); (3) largest single
buffer set to 160.0 GiB (starting value must fail); (4) a field `unavailable` with an empty reason (completeness
must fail). Determinism lanes: the script is run twice on each machine; debug and release agree on discrete fields.

## Considerations

- `trj` is often heavily loaded; a contended run fails repeatability honestly. The script logs host load and the
  gate needs a quiet window, not a wider tolerance.
- The gate is per machine state: an operating-system or driver update makes the stored fingerprint stale, and the
  gate row then names a superseded identity until the script is re-run.
- Exit review of M0 is done by a fresh-context session that reads this script's log and receipt.
