## Background

The fleet scheduler [F] assigns jobs across the two machines. Its owner is the daemon; **Spark supplies the
resource model**, because every quantity the scheduler needs to know about a job and a device is a device fact
that Spark already measures or decides: memory from the estimator's byte model, shape class from the lowered model,
determinism class from the IEEE probe and the CPU-versus-device check, the compute envelope, and the cost interval
of `sim.estimate`. The outline says: "a job carries a resource vector (device family or any, memory, shape class,
determinism class required, envelope class), a role tag, and the cost interval of `sim.estimate`."

Terms. A *shape class* is the content-hashed set of capacities (degrees of freedom, links, depth, contacts, rows,
samples, actuators, layouts, contact law, precision, iterations) for which one kernel set and one launch graph
exist per device. *Determinism classes*: D0 exact; D1 the same bits on `batch-cpu` (`f32`), CUDA and Metal; D2 the
same bits run to run on one device family, independent of batch composition; D3 agreement inside a recorded
envelope with decision-level equivalence; D4 unspecified (never evidence). *Envelope classes* (proposed, pending
the owner): E0 default (16 GiB, 8 cores, 1 hour, one device), E1 a named gate measurement (both machines, 2 hours
per run, 12 device-hours per gate), E2 a design campaign (48 device-hours), E3 pretraining of one family policy
(500 device-hours). The *cost interval* is conformal: a point prediction ŷ per stratum (verb, tier, device family,
shape class) widened by the ⌈(n + 1)(1 − α)⌉-th smallest absolute log residual q of the last n finished jobs to
[ŷ·e^(−q), ŷ·e^(q)]; a stratum is calibrated from n = 19; below that the interval is `uncalibrated` and admission
uses a fixed factor of 2.

Rejected alternative: letting the agent state what its job needs. Sizes and classes come from the system's own
estimate, never from the caller, for the same reason size classes do.

## Scope

In: the record `frob.fleet.job/1`; the device capability view; the feasibility predicate with its typed reasons;
the per-device cost interval and the work measure the scheduler sorts by. Out: queues and assignment (N21c-13);
drop-out, idempotency and balance (N21c-14); verbs (N21c-15, BD-370).

## Technical approach

Module `frob-kernels::fleet::model` (core).

```rust
// DESIGN: intent, not signatures.
struct FleetJob {                       // frob.fleet.job/1, content-addressed
    spec: Hash,                         // canonical request digest of the job specification
    resources: ResourceVector,
    role: RoleTag,                      // from role_of(verb, args, estimate); never caller-supplied
    scope: EnvelopeScope,               // the approved scope the demand belongs to, by N36-20's order: the
                                        // launcher's token, the cited `envelope_scope`, the verb's own scope,
                                        // otherwise `adhoc`
    cost: Vec<(DeviceId, CostInterval)>,// one interval per feasible device, from sim.estimate
}
struct ResourceVector {
    family: FamilyReq,                  // Cuda | Metal | Cpu | Any
    memory_bytes: u64,                  // exact, from the byte model and the plan's live intervals
    shape_class: Option<ShapeClassId>,
    determinism: Class,                 // the minimum class the verb requires
    envelope: EnvelopeClass,            // E0 | E1 | E2 | E3: the class the job needs
}
struct DeviceView {                     // built from the fingerprint, the check ledger and the daemon's state
    id: DeviceId, machine: MachineName, family: Family,
    budget_bytes: u64, free_bytes: u64,
    attained: Class,                    // best class this family holds for the job's kernels
    fingerprint: Status, check_current: bool,
    resident_shape_classes: Vec<ShapeClassId>,
}                                       // no envelope field: the class in force belongs to the job's scope,
                                        // not to a device
struct CostInterval { lo_s: Rational, point_s: Rational, hi_s: Rational, calibrated: bool }
```

**`fits(job, device) -> Result<(), Unfit>`**, checked in this order; the first failure is the reason:
1. `Family`: the job's family requirement excludes the device.
2. `Role`: affinity `no`, or a `limited` condition is not met.
3. `Memory`: `memory_bytes` exceeds `budget_bytes` (if no device of the fleet fits, the job is refused at admission
   with `FROB-REF-602`: fewer worlds, a smaller capacity, or the Mac).
4. `Determinism`: the device's attained class is weaker than required (`FROB-REF-247` if no device fits).
5. `Envelope`: the class the job needs exceeds the class in force for its scope, `class_in_force(scope, registry,
   today)` (N21c-35; E0 for `adhoc` or with no approved row), which is the same for every device, so a job unfit
   here is unfit everywhere (`FROB-REF-761`). A `campaign`-class job with no approved envelope never reaches this
   predicate: the daemon's size classifier refuses it with `FROB-REF-704` when it is submitted (BD-296).
6. `Fingerprint`: missing or stale (`FROB-REF-606`); `Check`: not current when the job requires it
   (`FROB-REF-605`).

**`candidates(job, devices) -> Vec<Candidate>`**: every device that fits, each with its affinity (`yes` or
`limited`), its cost interval and whether its shape class is already resident (a resident environment avoids a
compile and a graph capture). **Work measure:** the point estimate `point_s` on that device, in device-seconds;
admission tests use `hi_s`. An `uncalibrated` interval sets `hi_s = 2·point_s`.

**Class order** used in step 4: D0 > D1 > D2 > D3 > D4 as guarantees; a requirement of D2 is met by D2, D1 or D0 on
that family; D1 is a property of a family pair with the CPU reference and is read from the check ledger, never
assumed.

All arithmetic is integer or rational; the model is a pure function of its inputs and of registry digests.

## Acceptance criteria

- [ ] `frob.fleet.job/1` round-trips canonically and its content hash is stable across platforms.
- [ ] `fits` returns the first failing reason in the stated order for each of the six cases, and `Ok` otherwise.
- [ ] In a scope whose class in force is E1 (a `synthetic` approved row), a job of 524,288 worlds at 85 kB per world (44.6 GB) fits no card (`Memory`) and fits the Mac; in scope `adhoc` (class in force E0, 16 GiB) it is `Memory` on the cards and `Envelope` on the Mac; 8,192 quadruped worlds (0.28 GB of state plus 0.20 GB of rollout storage, inside E0) fit every device.
- [ ] A job that requires class D1 is unfit on a family whose check ledger records D3.
- [ ] A job needing E2 whose scope's class in force is E0 (an `adhoc` scope) is unfit everywhere and maps to `FROB-REF-761`; the same job citing a scope whose approved row is E2 fits on every device that passes the other steps.
- [ ] Each candidate carries a cost interval per device; an uncalibrated stratum yields `hi = 2 × point` and `calibrated: false`.
- [ ] The caller cannot set the role, the memory or the envelope class.

## Test plan

### Unit tests

`cargo test -p frob-kernels fleet::model`:
- `fits_order_of_reasons`: a job failing family, memory and envelope at once reports `Family`.
- `fits_memory_boundary`: memory equal to the budget fits; one byte more does not.
- `fits_population_44_6_gb`: 524,288 × 85,000 = 44,564,480,000 bytes; unfit on a 24 GB card; fit on a 203 GB budget.
- `fits_determinism_weakest_wins`: required D2, attained D3 → `Determinism`; required D3, attained D1 → fits.
- `fits_envelope`: a job needing E2 in scope `adhoc` is `Envelope` on every device; the same job in scope `campaign:<id>` with a `synthetic` approved E2 row in the envelope registry fits.
- `fits_stale_fingerprint`, `fits_role_no`.
- `cost_interval_conformal` (`synthetic` residuals): ŷ = 100 s, n = 19, α = 0.10, the 18th smallest residual 0.2231 → [80.0, 125.0] s.
- `cost_interval_uncalibrated_factor_two`.
- Property tests: `fits` is deterministic; adding memory to a job never turns an unfit device into a fit one.

### End-to-end script and logging

This bead's own lane, before any fleet verb exists: `scripts/e2e/fleet_model.sh` runs, through the real binary,
`frob sim estimate <design or --designs list-file> --scene <scene> --worlds <n> --tier <tier> --json` (the inputs
of VERBS-sim's `sim.estimate` row; each fixture fixes the design or design list, scene and world count) for two
fixture requests (the 524,288-world population at 85 kB per world, 8,192 quadruped worlds) and, for a proof job,
which `sim.estimate` does not price, the run verb's own estimate as N21c-07's script takes it, `frob prove bundle
<a:… of a fixture mission answer> --out <scratch>/ --estimate --key fleet-model-prove-<run-id> --json` (nothing is
run or written under `--estimate`), then `cargo run -p frob-kernels --example fleet_fits -- --estimate <envelope>
--scope <scope> --envelopes fixtures/fleet/envelopes_e1_gate.toml --devices fixtures/fleet/devices_two_machines.json`
(an example target of this bead; the device fixture holds the five device views of the two machines, `synthetic`,
with the estimator's budgets, and the envelope fixture one approved E1 row for `gate:GATE-SPARK-13`, `synthetic`)
on each saved envelope, once with `--scope adhoc` and once with `--scope gate:GATE-SPARK-13`, and asserts per
device `fits` or the typed reason of the acceptance criteria, and `calibrated` with the cost interval. It sources the
STD-E2E helper and writes `target/e2e-logs/fleet_model/<utc>.ndjson` with a transcript: `ts`, `script`, `bead`,
`step`, `event`, exact commands, exit codes, wall times, the estimate envelopes' `evidence` blocks, memory bytes
against each budget, the reasons, the cost intervals with units, the registry digests, on failure the first
differing device and reason, and a `summary` line. The shell lane through the verb comes after this bead (it builds
on it): step `fits` of `scripts/e2e/fleet_plan.sh` (BD-370) prints the same reasons through `frob fleet plan --job
… --explain --json`.

### Known answers and negative controls

Known values: 44.6 GB for the large population; ⌈(19 + 1)·0.9⌉ = 18; e^(0.2231) = 1.25. Negative controls: a
`fits` that checks memory against free bytes instead of the budget (the boundary test must fail when free memory is
low but the budget suffices; free memory is the scheduler's concern, the budget is admission's); a model that
accepts a caller-supplied role (the type test must fail to compile or the schema must reject the field).

## Considerations

- The usable budget of a card (16 to 19 GB of 24) is an assumption until measured high-water marks exist; the model
  reads it from the estimator, never from a constant.
- D1 across families is a HYPOTHESIS until its gates; until then cross-family candidates for a D1 job are empty,
  which is the fail-closed outcome.
- Exists only if KILL-FLEET does not fire at first reading.
