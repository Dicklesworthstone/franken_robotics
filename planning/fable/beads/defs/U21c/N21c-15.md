## Background

Spark's verb list ends with two fleet verbs, both of kind `read`, first milestone M4: "`fleet.status`, `fleet.plan`:
roles and queues of the two machines; the assignment by role affinity and estimated work". The chapter's mechanism
register ties `fleet.status` to the **Solid** half of the two-machine design: "roles and seeds-only transfer; owner:
the daemon; verb: `fleet.status`; test: scene identity across machines; gate: GATE-SPARK-13". `fleet.plan` belongs
to the Frontier scheduler.

The distinction matters because the scheduler has a kill gate whose fallback is "the machines run standalone; jobs
are assigned by the role table through ordinary `job.*` verbs; the seeds-only rule stays". Under that fallback an
agent still needs one place to read which machine does what, what is queued where, how many bytes have crossed
between the machines in each transfer class against the allowance of 1 GB per campaign-hour, and whether scenes
regenerated on the other machine arrived at the same `SceneId`. That place is this verb. It must work with the
scheduler funded, not funded, or not yet decided, and with one machine unreachable.

## Scope

In: the registry entry, schemas, handler, rendering, redaction, exit codes, tests and the end-to-end script. Out:
the assignment itself (`fleet.plan`, BD-370; N21c-13); device details (`spark.devices`); job details (`job.list`).

## Technical approach

**Registry entry (DESIGN).**

```toml
[[verb]]
name = "fleet.status"
cluster = "fleet"
kind = "read"
tier = "S"
capabilities = ["fleet:read"]
input_schema = "frob.fleet.status.in/1"
output_schema = "frob.fleet.status.out/1"
refusals = []
idempotent = true
cost_model = "static: under 1 s; one round trip on the peer link if configured"
first_milestone = "M4"
task_clusters = ["devices", "operate"]
examples = ["frob fleet status --json", "frob fleet status --campaign c:7f… --json"]
```

**Input.** Optional `machine` (`mac`, `trj`), optional `campaign` (restricts the transfer block).

**Output (`result`).**

| Block | Content |
|---|---|
| `machines[]` | name, host, `link`: `up`, `down` (with seconds since the last heartbeat) or `standalone`; fingerprint digest and status per device; the daemon's configuration digest |
| `roles` | the seven role rows with the affinity of each machine (`yes`, `limited` with its condition, `no`), the registry digest and the by-hand rule |
| `scheduler` | `funded`, `by-hand` (KILL-FLEET fired, or the link is not built) or `undecided`; the kill gate's recorded state |
| `queues[]` | per device lane (`trj/cuda:0`, `trj/cuda:1`, `trj/cpu`, `mac/metal:0`, `mac/cpu`): queue length, backlog as an interval in seconds, the running job's role and estimated remaining time, estimate bias, the share of the last 50 jobs over twice their estimate, `estimates: reliable` or `unreliable`, utilization |
| `waiting[]` | jobs that are not placed, each with `why`: `machine-down`, `role`, `class`, `indeterminate`, `pair-group` |
| `transfer` | per campaign: bytes and items per transfer class in each direction, the total, bytes per campaign-hour against the target of 1 GB, `over_target`, and the count of refused attempts by class (`FROB-REF-618`) |
| `scene_identity` | regenerations checked across machines: count equal, count mismatched, the last mismatch's recipe and both identities |

**Behaviour.**
1. Read the local daemon's fleet state; if a peer link is configured and up, ask the peer for its half; otherwise
   mark the peer's blocks `unavailable` with the reason. The verb never refuses because a machine is unreachable.
2. Redaction: jobs of other principals appear with role, size class and estimate only; identifiers and names are
   shown only inside the caller's namespace.
3. Exit 0 when both machines are up (or one is `standalone` by configuration), no job waits on `machine-down`,
   nothing is over target and no identity mismatch is on record; exit 2 with one `warnings[]` entry per flag
   otherwise. `next_actions[]` suggests `frob spark fingerprint` for a stale device and the by-hand machine for a
   waiting job.
4. Evidence block: class `Tested`, tier `static`, determinism `exact` for the role table and the integer meter;
   queue estimates are intervals with their calibration flag. `reality: no-claim`.
5. Nothing is written. Without a daemon the verb reports roles and the stored transfer rows only and says so.

Human rendering: a two-column role table, one line per device lane, the transfer total against the target.

## Acceptance criteria

- [ ] `frob fleet status --json` returns the seven roles with the 14 affinity cells of the policy table and the registry digest.
- [ ] With two daemons linked it lists five device lanes with queue lengths that equal `job.list` counts per device; with the peer killed it marks that machine `down`, exits 2 and still reports the local half.
- [ ] The `transfer` block's per-class bytes equal the ledger's meter rows exactly; a campaign at 1.2 GB per campaign-hour shows `over_target: true`.
- [ ] After a planted scene-identity mismatch the `scene_identity` block reports it with both identities.
- [ ] With KILL-FLEET recorded as fired, `scheduler` is `by-hand` and the verb's other blocks are unchanged.
- [ ] Another principal's job identifiers never appear in the output of a caller without that namespace.
- [ ] The MCP tool `fleet_status` returns the same envelope; the output validates against `frob.fleet.status.out/1`; the verb allocates no device memory.

## Test plan

### Unit tests

`cargo test -p frob-verbs fleet_status` and `-p frob-cli fleet::status`:
- `status_roles_block_matches_registry`.
- `status_peer_down_is_flag_not_refusal`: exit 2, `link: down`, local queues present.
- `status_transfer_block_exact`: `synthetic` meter rows of 12,288, 3,145,728 and 1,048,576 bytes total 4,206,592.
- `status_redacts_other_principals`.
- `status_scheduler_states`: `funded`, `by-hand`, `undecided` from three gate-registry fixtures.
- `status_schema_roundtrip`, `status_waiting_reasons_exhaustive` (an unknown reason fails to serialize).

### End-to-end script and logging

`scripts/e2e/fleet_status.sh`: two `frobd` processes on separate state roots (and the real pair of machines where
both are reachable). Steps: `frob fleet status --json` (assert roles, lanes, `link: up`); submit three `synthetic`
jobs of roles `train`, `derive-prove` and `eval-large` through the job verbs and assert the lanes' queue lengths;
export a recipe and a weights file across (assert the meter); attempt a forbidden export (assert the refused count
rises by one); kill the peer (assert exit 2, `down`, waiting reasons); restart it (assert exit 0). Logs per the
end-to-end standard: command lines, exit codes, wall times, the evidence block, queue lengths and byte totals with
units and expectations, registry and configuration digests, and on failure the first differing field with both
values. Final `summary` with assertion counts.

### Known answers and negative controls

Known answers: the 14 cells; the meter arithmetic; KA-539 through the `scene_identity` block. Negative controls: a
handler that refuses when the peer is down (the down step must fail); a handler that reads queue lengths from its
own cache instead of the job ledger (the equality with `job.list` must fail after a submit); a meter block that
omits the incoming direction (the total must fail). Lanes: twice on one machine; Linux and macOS.

## Considerations

- The verb is Solid although its registered milestone is M4; the role table and the meter it prints exist from M2
  and are readable until then through their own records and the export envelope.
- "Standalone" is a configuration, not a fault: OPEN-TETHER-5's default is standalone machines.
- Queue contents reveal load; redaction keeps identities private while keeping the counts honest.
