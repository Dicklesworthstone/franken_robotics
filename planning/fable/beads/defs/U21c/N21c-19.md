## Background

A specialized kernel is the generic kernel with one design's constants folded in and its loops unrolled. The rule
that makes it safe to use is absolute: **a specialized kernel must be bit-identical to its generic kernel**
(INV-SPARK-09; ADR-SPARK-08). Unrolling keeps the operation order and only exact constant operations are folded;
reassociation and distribution are never rewrites, because reassociation changes bits. `spark check` enforces the
rule; a mismatch is `FROB-REF-613` ("a specialized kernel is not bit-identical to its generic kernel"; first
repair: the generic kernel). Known answer: specialized against generic on 10⁶ states, bit-identical; the negative
control is a reassociated variant, which must be refused. Gate GATE-SPARK-14 repeats the requirement beside its
speed and compile-time thresholds.

Why bit identity and not a tolerance: survivor cohorts switch to specialized kernels in the middle of training and
evaluation. If the bits changed, per-world digests, paired comparisons, memoized episodes and replays would all
split into "before" and "after" populations, and a specialized kernel would be a new kernel version owing the whole
fidelity battery. Requiring identical bits makes the two interchangeable, so a specialization is purely a
performance change with a behaviour proof.

## Scope

In: the pairing metadata; the static (IR) comparison; the dynamic comparison on 10⁶ states; the currency row; the
quarantine of a failing entry; the refusal and its repair; the related repair of `FROB-REF-603` (a specialized
kernel that fails to compile falls back to the generic one). Out: producing specialized kernels (BD-371); switching
cohorts (N21c-20); speed measurement (BD-371's gate).

## Technical approach

**Pairing (DESIGN).** A specialized kernel's manifest adds `specializes: KernelId` (its generic kernel), `variant:
digest of the design's model-table row`, and inherits class, footprints and determinism claim from the generic
manifest. It is another entry of the binary kernel cache (its key already differs, since the expanded dialect text
differs).

**Static comparison (`frob-kir`).** Where both kernels have IR programs: substitute the variant's constants into
the generic program, unroll its bounded loops, then normalize both programs with the exact rewrite set only
(bounded common-subexpression elimination, dead-code removal, commutation of + and ×, x·1, x + (−0), double
negation, select simplification, folding of constant operations whose result is exactly representable in the
kernel's type). The two normal forms must be equal as directed acyclic graphs. A difference names the first node
that differs. This catches a reassociation without running anything. A constant fold whose result would need
rounding is not an exact fold and is rejected here (DESIGN reading of "exact constant operations": no rounding
occurs, so no backend's rounding behaviour can matter).

**Dynamic comparison (`spark check --specialized <KernelId>`).**
1. Draw 10⁶ input states for the variant by address-keyed streams, plus a fixed edge set: all-zero state, every
   joint at each limit, the largest admitted velocities, signed zeros in every slot.
2. Run the generic kernel (reading the variant's table row) and the specialized kernel on the same device from
   identical inputs; compare every output buffer byte for byte, including the sign of zero. Repeat on
   `batch-cpu`.
3. Identical everywhere: write a currency row `(specialized, generic, device family, driver, compiler) → identical,
   states, output digest`. Any difference: record the first differing state, output slot and both bit patterns.

**Fence.** A specialized kernel may enter a step plan only with a current `identical` row for the device it will
run on. Otherwise the planner refuses that kernel with `FROB-REF-613`, exit 6, `pointer`: the kernel pair,
`observed`/`required`: the differing bit patterns or "no current check", `retry: after-change`, repairs: 1. use the
generic kernel (the cohort simply stays on it); 2. `frob spark check --specialized <id>` if the row is merely
stale; 3. report the specializer defect with the first differing node. A failing entry is **quarantined** in the
cache: it is never loaded again under that key. A fingerprint identity change stales the row like any other check.

**Who asked decides what the caller sees (DESIGN).** The fence's verdict is the same in both cases; its surface
differs by who chose the specialized kernel, so that no request is silently substituted and no caller is refused
for a choice it did not make:
- *Explicit request* (`sim.run --kernel-set specialized`, or a step plan that names the specialized kernel): the
  run is refused with `FROB-REF-613`, exit 6, before any world is stepped, with the repairs above (repair 1 is
  the same run with `--kernel-set generic`). This is the rule of strict placement: a request is never scored on
  something else.
- *System choice* (the survivor switch-over of N21c-20, which proposes a specialized kernel for a cohort): the
  cohort stays on the generic kernel and the run continues; the placement receipt and the cohort record carry
  `specialized: refused` with the code `FROB-REF-613`, the kernel pair and the first differing state or "no
  current check"; nothing is returned to the caller as a refusal.

**Compile failure.** A specialized kernel that fails to compile raises `FROB-REF-603` with the compiler
diagnostics verbatim; its first repair is "the generic kernel if a specialized one failed", and the run continues
on the generic kernel.

Determinism: the check is exact (byte comparison). Evidence class `Tested`. The currency row and any quarantine
are written to the divergence ledger.

## Acceptance criteria

- [ ] A correct script-written specialization of the three-link chain and of the reference quadruped's kinematics passes both comparisons with 10⁶ identical states on `batch-cpu` and on each available device.
- [ ] A reassociated variant ((a + b) + c rewritten as a + (b + c)) is rejected by the static comparison, naming the node, and by the dynamic comparison, naming the first differing state. Requested explicitly, the run is refused with `FROB-REF-613`, exit 6, zero worlds stepped; proposed by the survivor switch-over, the cohort stays on the generic kernel and the receipt records `specialized: refused` with the code.
- [ ] A variant with a rounded constant fold is rejected by the static comparison.
- [ ] A specialized kernel without a current row cannot be placed; after `spark check` it can.
- [ ] A failing entry is quarantined and is not loaded on the next start.
- [ ] A specialized kernel that fails to compile yields `FROB-REF-603` and the run continues on the generic kernel, with the fallback visible in the placement receipt.
- [ ] INV-SPARK-09 has a property test; the fence is in the `CONTRACT.md` of `frob-kernels`.

## Test plan

### Unit tests

`cargo test -p frob-kir specialize_normal_form`, `-p frob-kernels specialize_fence`:
- `normal_form_equal_for_exact_rewrites`: commuting a product and removing x·1 leave the normal form unchanged.
- `normal_form_detects_reassociation`; `normal_form_detects_distribution` (a·(b + c) against a·b + a·c).
- `fold_exact_only`: 0.5·4.0 folds to 2.0; 0.1·3.0 (not exactly representable) is not folded.
- `dynamic_compare_signed_zero`: outputs +0.0 and −0.0 are a mismatch.
- `fence_requires_current_row`, `fence_quarantines_failure`.
- `fence_explicit_request_refused`: `--kernel-set specialized` with the reassociated fixture → `FROB-REF-613`, exit 6, stepped-world counter zero, repair 1 the generic kernel set.
- `fence_system_choice_stays_generic`: a plan proposing the same fixture with `origin: system` (the switch-over's path) → the generic kernel is placed, exit 0, and the placement receipt carries `specialized: refused` with `FROB-REF-613`.
- Property test `specialized_bit_identical` (INV-SPARK-09; the test name the invariant register N21c-27 binds): for random straight-line programs and random constant substitutions, the unrolled program evaluated on `batch-cpu` is bit-identical to the loop program on 10⁴ random inputs.

### End-to-end script and logging

`scripts/e2e/specialize_fence.sh --seed <s>`: first installs the two fixture kernels (the script-written unit
files `quad-kin-unrolled` and `quad-kin-reassociated`, whose manifests carry `specializes` and `variant`; their
paths printed by `e2e_fixture`) as cache entries for each target with `frob spark precompile <target> --unit <path>
--key sf-pc-<fixture>-<target>-<run-id> --json` (N21a-10's option) and reads each entry's `KernelId` from the cache
receipt; `--specialized` takes that `KernelId`, not a path, so an `@fixture:` reference there would be the schema
refusal 802. Then `frob spark check --specialized <unrolled KernelId> --backend <b> --seed <s> --key
sf-ok-<b>-<run-id> --json` for `batch-cpu` and each available device (expect identical, 10⁶ states, a current row),
the same on the reassociated kernel's `KernelId` with `--key sf-bad-<b>-<run-id>` (expect exit 6, `FROB-REF-613`,
the first differing state), then, with the reassociated kernel installed as the reference quadruped's specialized
cache entry, `frob sim run --workload Q --worlds 64 --seconds 1 --tier batch-cpu
--kernel-set specialized --key sf-run-<run-id> --json` (expect exit 6, `FROB-REF-613`, zero worlds stepped, repair 1
the same run with `--kernel-set generic`), then that repair (expect exit 0), then a restart of the daemon and the
check that the quarantined entry is not loaded. The system-choice surface (`specialized: refused` in the receipt,
exit 0) is asserted here by `fence_system_choice_stays_generic`; from the user's side it is asserted by the
switch-over's script (N21c-20), which proposes the kernel and depends on this bead. `--specialized` on
`spark.check` and `--kernel-set generic|specialized` on `sim.run` are options this bead adds (DESIGN; registered
with this bead as owner on their rows in VERBS-spark and VERBS-sim, `--specialized` answering 724 while this bead
is not in the build). Logs through the STD-E2E helper to
`target/e2e-logs/specialize_fence/<utc>.ndjson` with a transcript: `ts`, `script`, `bead`, `step`, `event`, command
lines, exit codes, wall times, the evidence block, states compared against 10⁶, the output digest, the first
differing state with both bit patterns, the refusal with its repairs, the stepped-world counter (threshold 0), and a
`summary` line.

### Known answers and negative controls

KA-538 (bit-identical on 10⁶ states; control: a reassociated variant must be refused). Negative controls: the
reassociated variant; the rounded fold; a fence that compares under a 1-ulp tolerance (the signed-zero and
reassociation fixtures must then pass wrongly and the tests must fail). Lanes: `batch-cpu`, CUDA, Metal; twice on
one machine; debug and release.

## Considerations

- 10⁶ random states do not prove identity; the static normal-form comparison is the argument and the dynamic
  comparison is its test. Hand-written skeleton parts have no IR and rely on the dynamic comparison alone.
- If KILL-SPECIALIZE fires, this bead is not built and `FROB-REF-613` stays a registered code without a raising
  site.
