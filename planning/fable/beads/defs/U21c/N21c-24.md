## Background

Spark (GPU backends and the kernel toolchain) chose one route: a small shared C-dialect source for hand-written
kernel skeletons plus derived arithmetic, compiled for a CPU reference, for CUDA through a pinned `cudarc`, and for
Metal through FrankenTorch's `ft-kernel-metal` gateway, with GPU code confined to annex workspaces. Eight other
routes were researched and not taken. A future contributor will meet each of them again as a tempting shortcut, so
the reasons must travel with the code, and the ones that are dependency choices must be enforced by a build check
and not by memory.

FACT from the research pass (state in late 2026), with the decision:

| Route | State in late 2026 | Decision | Revisit when |
|---|---|---|---|
| `wgpu` as the only layer | 30.x; portable; hides launch graphs, allocators and barriers; no doubles on Metal | Not the primary; possible third backend; **not admitted** as a dependency | Other hardware must be served and the dialect proves small enough to port; needs its own admission test |
| Slang as the kernel language | CUDA target supported; Metal and WGSL targets experimental | Not taken | Its Metal target is no longer experimental |
| NVIDIA's Rust-to-PTX compiler | Early alpha, Linux and NVIDIA only | Watch | It reaches a stable release and a second vendor |
| `rust-gpu`, CubeCL and Burn | Alpha, or a large dependency tree | Not taken: conflicts with the Franken-only core | Never for the core; an annex-only proposal would need the owner |
| Python kernel compilers of incumbent simulators (one source lowered to CPU and CUDA, or to CUDA, Metal and others) | Mature; the reason single-source kernels are prior art | Design references; **not dependencies** | Not applicable |
| Wrapping MuJoCo Warp, Newton or Genesis | Python ecosystems; Newton is CPU-only on macOS; Genesis has a Metal path through its own compiler | Anti-goal; used as oracles, as parity baselines and as design references, out of process | Not applicable |
| An IR with built-in sine and cosine, fusion of multiply-adds and an approximate mode | Convenient; incompatible with a three-way parity gate | Not taken (ADR-SPARK-02) | An explicit fused operation is admitted (an open numerics question whose default is "no") |
| Our own Metal binding beside the gateway | Possible (the suite's piano renderer binds `metal` directly; FACT) | Not taken by default; an owner decision (OPEN-SPARK-5) | The owner decides, or the gateway's upstream work item fails |

The governing invariant is **INV-SPARK-01: the core workspace never depends on a GPU crate**, verified by a
dependency lint in `xtask`. It comes from ADR-SPARK-01: the core workspace is `unsafe_code = "deny"` with
Franken-only runtime dependencies; GPU backends live in annex workspaces under `spark/`, each with its own lockfile
and a registry of unsafe capsules; binaries that use a GPU are built from an `apps/` workspace that links the core
and an annex.

## Scope

In: the decision record (one entry per route, with the revisit trigger); the Spark rows of the dependency policy
consumed by `xtask check-deps`; fixture workspaces with planted violations; the end-to-end check. Out: the
`check-deps` engine itself (BD-003) and the workspace table that holds the one forbidden-package list (N34p4-02);
the test of INV-SPARK-01 on the real resolved graph of the core, and the assertion that the real CUDA annex
(BD-015) requires `cudarc` at an exact pin (both N21a-01, which depends on this bead for the allow-list rule:
`core_graph_has_no_gpu_crate`, `cuda_annex_pin_exact_on_tree`); the invariants section of the contracts, which
N21c-27 generates from its INV-SPARK-01 row (that row names this bead's `deps_policy_spark::core_denies_gpu_crates`
beside N21a-01's test); the dialect and IR lints that ban built-in transcendentals and fused operations in kernel
source (BD-013, BD-018, N21a-10).

## Technical approach

1. **Record.** `docs/adr/spark-routes-not-taken.md`, generated from `registries/routes_not_taken.toml` (DESIGN):
   one row per route with `state_as_of`, `decision`, `reason`, `revisit_when`, and `enforced_by` (a deny-rule
   identifier or `none`). The README's honest-status table links it. A registry test requires every row to have a
   reason and a revisit trigger.
2. **Deny rules for the core workspace (INV-SPARK-01).** No package of the core workspace may depend, directly or
   transitively, on any of: `cudarc`, `metal`, `objc2-metal`, `ft-kernel-metal`, `wgpu` and its backends, `ash`,
   `vulkano`, `opencl3`, `cubecl`, `burn` and its crates, `spirv-std` (the `rust-gpu` runtime), Slang bindings, or
   a Python embedding (`pyo3`). Where the names live (DESIGN, one copy): the forbidden-package list of the
   workspace table of N34p4-02 (`crates/xtask/src/workspaces.rs`), which `check-deps`, N34p4-02's lockfile grep and
   N21a-01's test all read. N34p4-02's list holds the annex crates (`cudarc`, the Metal crates and `block`, `wgpu`,
   the Python bindings, `fsym-*`, every crate under `spark/`, `apps/`, `derive/`, `bindings/`); this bead adds
   the routes-not-taken names (`ash`, `vulkano`, `opencl3`, `cubecl`, `burn*`, `spirv-std`, Slang bindings) as
   entries of that same list, each entry `{ package, why = { route = "<route id>" } }` carrying the identifier of
   the route row that justifies it (N34p4-02's entry form), and keeps
   no second list. A new GPU crate is added there by name, and a catch-all heuristic flags any dependency whose
   `links` key names a GPU driver library.
3. **Allow-lists for the annexes.** `spark/frob-spark-cuda` may depend on the core crates and on `cudarc` at its
   exact pin (FACT: the suite's renderer pins `cudarc = "=0.19.9"` with features `driver`, `nvrtc`,
   `dynamic-loading`; the driver and NVRTC load at run time, so no CUDA toolkit is needed to build) and on nothing
   else that binds a device. This bead writes the rule and proves it on fixture annexes; a workspace row whose
   root has no manifest is skipped as `absent` (N34p4-02), so the rule is applied to the real CUDA annex when that
   annex exists, and N21a-01 asserts it there. `spark/frob-spark-metal` may depend on the core crates and on `ft-kernel-metal`, and
   **not** on `metal` or `objc2-metal` directly: a second binding beside the gateway is denied until OPEN-SPARK-5
   is decided otherwise. `wgpu` is denied in annexes too (not admitted).
4. **Incumbents stay out of process.** The policy denies linking an incumbent simulator or its language runtime
   anywhere in the build graph; the incumbent harness is an out-of-process tool.
5. **Failure output.** A violation prints the offending package, the dependency path, the rule identifier and the
   registry row that explains the decision, and exits non-zero.

## Acceptance criteria

- [ ] The record lists the eight routes with state, decision, reason and revisit trigger, and is linked from the status table.
- [ ] `cargo xtask check-deps` passes on the real workspaces and fails, naming the rule, on each planted violation: a core crate depending on `wgpu`; a core crate depending on `cudarc` transitively through a dev-dependency promoted to a normal one; the Metal annex depending on `metal` directly; any crate depending on `pyo3`.
- [ ] In a fixture CUDA annex a caret `cudarc` requirement fails the check, naming the rule, and the exact pin `=0.19.9` passes (the real annex's pin is asserted by N21a-01).
- [ ] Each deny entry this bead adds to N34p4-02's forbidden-package list names the route row that justifies it; an added entry with no row, and a row marked enforced with no entry, both fail the registry test; no second deny list exists outside the workspace table.

## Test plan

### Unit tests

`cargo test -p xtask deps_policy_spark`:
- `core_denies_gpu_crates`: for each denied name, a `synthetic` fixture workspace with that dependency fails.
- `core_denies_transitive`: a path core → helper → `cudarc` fails and prints the path.
- `metal_annex_denies_direct_binding`; `cuda_annex_requires_exact_pin`; `links_heuristic_flags_unknown_gpu_crate`.
- `routes_registry_complete`: eight rows, each with reason and revisit trigger; `enforced_by` identifiers resolve.

### End-to-end script and logging

`scripts/e2e/spark_deps_policy.sh`: runs `cargo xtask check-deps` on the repository (expect exit 0), then on each
fixture workspace under `tests/fixtures/deps/` (expect non-zero and the rule identifier in the output). Logs per the
end-to-end standard: each command line, exit code and wall time, the rule identifier matched, the dependency path
reported, and a `summary` line with the count of violations caught. No device is needed.

### Known answers and negative controls

The four planted violations are the negative controls of INV-SPARK-01: a gate that nothing can fail validates
nothing. A fifth control: removing `wgpu` from the deny list must make its fixture pass, which the test suite
detects as a missing rule. Lanes: Linux and macOS (the Metal annex's graph is resolved on both; it builds only on
macOS).

## Considerations

- The deny list names crates; a renamed or forked GPU crate slips past names, hence the `links` heuristic and the
  review of every new dependency through the admission document.
- `ft-kernel-metal` is denied in the core but allowed in the annex; `apps/` binaries link both, which is the
  design, not a violation.
- The record is a decision log, not a ban on thinking: each row says what would reopen it.
