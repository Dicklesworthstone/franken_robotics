## Background

Spark (GPU backends and the kernel toolchain) states ten invariants and four proof obligations. An invariant is a
property that must hold at all times in the running system; a proof obligation is a property that must be
established (computed, derived or proved) before an artifact is admitted. The project's testing rule is that every
invariant and proof obligation has a property test, and every check has at least one negative control: a planted
defect it must catch, because a check that nothing can fail validates nothing. Each of the fourteen is constrained
by a mechanism owned by some bead; several of those beads are written by other drafting units. This bead is the
register that keeps the fourteen from being lost between units: one machine-readable row per identifier, the name
of the test that verifies it, the planted violation that test must catch, and a build-time check that every row
resolves to a test that exists and has run.

## Scope

In: the fourteen registry rows; the registry check (resolution of test names, presence of a negative control,
last-run status); the crate contract's invariants section generated from the rows; an end-to-end run of the whole
set. Out: the tests themselves where another bead owns the mechanism (named per row); three rows have dedicated
beads (INV-SPARK-01: N21a-01 on the resolved graph and N21c-24 on fixture workspaces; INV-SPARK-02: N21c-28;
PO-SPARK-04: N21a-06).

Why an M0 bead (DESIGN): six of the fourteen rows concern M0 mechanisms (INV-SPARK-01, the static half of
INV-SPARK-04, INV-SPARK-08, PO-SPARK-01, the manifest side of PO-SPARK-03, and PO-SPARK-02 at M0 and M1), and the
mechanism beads that own a row's test depend on this register so that they write the test under the name the row
binds. A register at M2 could not be a dependency of those beads. The check is staged by each test's
`first_milestone` (rule 3 below), so tests of later milestones are `pending` until then. The owners of four rows'
M0 tests (INV-SPARK-04's static half, INV-SPARK-08, PO-SPARK-01, PO-SPARK-03's manifest side), BD-004, N21b-01 (through BD-014, which this bead needs because it
creates `crates/frob-kernels/CONTRACT.md`, whose invariants section is generated here) and BD-018 (whose place on
the derivation path must not wait for this register), do not depend on it; for their rows the register adopts the
test names those beads give, and the registry check is what enforces resolution. A row whose owner had not yet
named its test is the register's to name, and the owner is asked to use that name.

**Registry check** (in `frob-conformance`, run by the `check-contracts` step of `xtask`; no new subcommand):
1. every identifier `INV-SPARK-nn` and `PO-SPARK-nn` that appears in the crate contracts or in kernel manifests has
   a row, and every row's `test` resolves to a test function in the workspace or an annex;
2. every row names a negative control registered in the negative-control registry, and that control's last run
   was caught. A row cites the one record of its planted violation: the record N38b-05 seeds from a known-answer
   row or catalogue entry, or the record the planting bead registers (N21c-30's `spark.guard-below-bound`,
   `seed = "PO-SPARK-02"`, for PO-SPARK-02); a planted violation that no record carries is appended by this bead
   under BD-025's rules with `seed` the row's identifier (`INV-SPARK-nn` or `PO-SPARK-nn`, the form N32b-22 and
   N29b-15 use for their sections), naming the owner bead's plant, so that no row's check waits on a record nobody
   writes and no plant has two records;
3. a row whose `first_milestone` has passed and whose test has no recorded run in the current build fails the
   check; a row may be `pending` only before its milestone, and is then printed in the honest-status table. The
   rule applies to each test at its own `first_milestone`: at the M0 exit the M0 tests of INV-SPARK-04 and
   PO-SPARK-03 must have run and passed while their M2 tests are `pending (M2)`, so a split row neither fails the
   M0 exit for a test that cannot exist yet nor passes it with an M0 test unrun.

**Contract generation.** The invariants section of `crates/frob-kernels/CONTRACT.md` and of each annex's contract
is generated from these rows, so the wording cannot drift from the register.

## Acceptance criteria

- [ ] The fourteen rows exist with statement, verification, test, negative control, tier, first milestone and owner.
- [ ] Each row cites exactly one control record of `controls.toml`; the records this bead appends (seed `INV-SPARK-nn` or `PO-SPARK-nn`) cover only planted violations no seeded or registered record carries, and load under BD-025's loader.
- [ ] The registry check fails when: a row's test name does not resolve; a negative control is missing; a control was not caught on its last run; a passed-milestone row has no run.
- [ ] At the M0 exit the tests whose first milestone is M0 (including the M0 halves of INV-SPARK-04 and PO-SPARK-03) show a passing run and a caught control and every other test is `pending (Mn)`; at the M2 exit the rows whose first milestone is M0, M1 or M2 (all but INV-SPARK-09 and INV-SPARK-10's gate clause) do.
- [ ] Every row names test functions that its owner bead's test plan names; a row whose owner names its test differently is updated, never duplicated (every row now uses its owners' names: INV-SPARK-01, -02, -04, -08, -10 and PO-SPARK-01, -03, -04 as before; INV-SPARK-03, -07 and -09 as BD-173, BD-178 and BD-371, which depend on this register, write them; INV-SPARK-05 as BD-172 and BD-183; INV-SPARK-06 as N21b-11 defines it and BD-173 and BD-174 re-run it; PO-SPARK-02 as BD-030 and BD-053).
- [ ] The generated contract sections list the same fourteen statements.
- [ ] The status table shows, per row, `passing`, `pending (milestone)` or `failing`; nothing is reported as passing without a run.

## Test plan

### Unit tests

`cargo test -p frob-conformance invariants_spark`:
- `register_has_fourteen_rows`; `register_ids_unique`.
- `check_fails_on_unresolved_test` (a `synthetic` registry with a misspelt test name).
- `check_fails_on_missing_control`, `check_fails_on_uncaught_control`, `check_fails_on_stale_row`.
- `check_stages_split_row_per_test`: a `synthetic` row with one M0 test and one M2 test passes an M0-stage check with the M0 test run and the M2 test `pending (M2)`, and fails it when the M0 test has no run.
- `contract_section_generated_matches_register`.
- For the rows owned here, the tests named in the table (see N21c-24, N21c-28, N21a-06, N21c-19, N21c-08).

### End-to-end script and logging

`scripts/e2e/spark_invariants.sh`: runs `cargo xtask check-contracts`, then every registered test of the section on
`batch-cpu` and on each available device (`cargo test … -- <test name>`), then each negative control through the
conformance harness (expecting each to be caught). Logs per the end-to-end standard: one `assert` event per row
with identifier, test name, result, the control's result, the tier and the device; on failure the first failing
row with the artifact paths; a final `summary` with counts of passing, pending and failing rows.

### Known answers and negative controls

The fourteen planted violations of the table are the negative controls; twelve of them coincide with controls
already required by the chapter's known-answer table and gates (the per-chunk allocation, the withheld kernel,
the reassociated variant, the forbidden transfer, and so on) and are registered once. Lanes: the register check on Linux and macOS;
device rows on each backend against its determinism class.

## Considerations

- The register does not prove an invariant; it guarantees that a named test exists, runs and can fail.
- Rows owned by other units name the test this register expects; if an owner chooses another name the row is
  updated, not duplicated.
- INV-SPARK-09 and the gate clause of INV-SPARK-10 exist only if their Frontier mechanisms are funded; their rows
  then read `not applicable (kill gate fired)` with the decision's identity.
