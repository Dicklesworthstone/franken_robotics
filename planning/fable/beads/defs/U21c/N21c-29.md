## Background

A kernel is a manifest, its arithmetic and its sources. The manifest holds a **stage signature**, "because a device
kernel is only as safe as what the host believes about its buffers": the read footprint and the write footprint
per buffer, as index ranges in terms of capacities; aliasing rules (which arguments may be the same slab; none by
default); layout; the ownership epoch read and written; resource bounds; the numerical contract. Leases, the commit
fence, the alias check of the Metal gateway and the invariant that no kernel touches another world's rows
(INV-SPARK-04) all reason from those declarations.

**PO-SPARK-04:** declared read and write footprints contain the IR's load and store sets. Verification: derived
for generated bodies; a lint for skeletons. FACT: the Metal gateway checks declarations against each other (it
refuses a batch whose read and write declarations alias), not against the kernel source, "so this obligation is
ours". A kernel that writes one element past what its manifest says would corrupt a neighbouring slab on the
device with no fault, and every safety argument built on the manifest would be false while every test still
passed.

Kernel sources have two layers. *Arithmetic* is derived and lowered to the kernel IR, whose memory operations are
`load(slot, lane, offset)` and `store(slot, lane, offset, v)` with a literal offset and whose loops have literal or
capacity bounds, so its access sets are computable exactly. *Skeletons* (loops, gathers, scans, sorts) are written
by hand twice: in Rust for `batch-cpu` and in the shared dialect, under rules that make analysis feasible: explicit
loop bounds that are literals or capacity constants, unsigned 32-bit indices, no recursion, no pointer arithmetic
beyond buffer plus index.

## Scope

In: footprint derivation from IR; the manifest comparison; the skeleton lint (interval analysis of index
expressions in the dialect subset); the access recorder on `batch-cpu`; world-locality checking for INV-SPARK-04;
build-time failures. Out: the manifest schema and the alias rules themselves; the batch-invariance gate; leases.

## Technical approach

1. **Access sets from IR (`frob-kir::footprint`).** For a program, walk every `load` and `store`: the slot is a
   buffer argument; the lane is the world's own lane or a loop variable with a known bound; the offset is a literal
   or literal plus a bounded loop variable. The result per slot is an exact set of (lane class, offset interval)
   pairs, expressed in capacities, split into reads and writes. Lane class is `own-world` or `range(capacity)`.
2. **Generated bodies.** The emitter writes the derived footprints into the manifest (so nobody types them) and
   `check-generated` regenerates and compares. A manifest footprint narrower than the derived set is a build
   error.
3. **Skeleton lint (`xtask` lint pass over dialect sources).** Parse the skeleton in the dialect subset; for every
   indexed access `buf[expr]`, bound `expr` by interval analysis over loop variables (bounds are literals or
   capacity constants), unsigned arithmetic and the prelude's indexing macros. Outcomes per access: *contained* (the
   interval lies inside the declared range of that buffer and direction); *violation* (it does not: build error
   naming file, line, buffer, the computed interval and the declared range); *unbounded* (the index is
   data-dependent, such as a gather through a parent table). An unbounded access must carry an annotation
   `// footprint: <buffer> <read|write> [lo, hi) via <table>` whose range is checked against the manifest and whose
   truth is checked at run time by step 4. An unbounded access without an annotation is a build error. A store to
   a buffer the manifest declares read-only, or to a buffer it does not declare, is a build error.
4. **Access recorder (the dynamic half).** The `batch-cpu` harness can run any kernel's Rust skeleton through an
   instrumented accessor that records every (buffer, element index, direction) touched. In the kernel's
   known-answer tests and in a randomized battery (random states, capacities at their bounds, worlds at the first
   and last lane) the recorded set must be contained in the manifest's footprints, and every recorded lane must be
   the kernel's own world unless the kernel's class is `stat`. This validates the annotations of step 3 and the
   Rust skeleton, which the dialect lint does not read.
5. **Twin check.** The Rust and dialect skeletons of one kernel must declare the same footprints (one manifest
   serves both); the recorder's set on `batch-cpu` is also compared with the lint's intervals for the dialect
   text, and a disagreement in either direction beyond the over-approximation is reported.
6. **Failure mode.** All failures are build-time (lint or test), with a message that names the kernel, the buffer,
   the access and both ranges. No kernel with a failing containment check enters the kernel library's registry.

Determinism: the analyses are exact integer interval arithmetic.

## Acceptance criteria

- [ ] For every generated kernel body in the library, manifest footprints equal the footprints derived from its IR (regenerate-and-compare passes).
- [ ] For every skeleton, each indexed access is contained, or annotated and validated by the recorder; the lint reports zero violations on the library.
- [ ] The recorder battery runs for every kernel on `batch-cpu` and finds every access inside the declared footprints and inside the kernel's own world (or the kernel is `stat` and its outputs feed no state slab).
- [ ] Each planted defect below is caught at build or test time with a message naming the buffer and both ranges.
- [ ] PO-SPARK-04 is listed in the `frob-kernels` contract with this check as its verification.

## Test plan

### Unit tests

`cargo test -p frob-kir footprint`, `-p xtask skeleton_lint`, `-p frob-kernels access_recorder`:
- `ir_footprint_cay_step` (`synthetic` program): reads of two state slots and one write give exactly those three entries with `own-world` lanes.
- `ir_footprint_loop_bound`: a loop `for i in 0..link_cap` with `load(s, lane, 4·i + 2)` gives the offset interval [2, 4·link_cap − 2].
- `lint_contained_simple_loop`; `lint_off_by_one_violation` (a loop to `≤ cap` reads index `cap`, outside [0, cap)).
- `lint_store_to_undeclared_buffer`; `lint_store_to_read_only`.
- `lint_unbounded_requires_annotation`; `lint_annotation_range_checked_against_manifest`.
- `recorder_catches_cross_world_write`: a planted skeleton that writes lane w + 1 is caught.
- `recorder_validates_gather_annotation`: a parent table containing an index outside its annotated range is caught.
- Property test (PO-SPARK-04): for random IR programs, the set of elements touched when the program is interpreted on random inputs is a subset of the derived footprint.

### End-to-end script and logging

`scripts/e2e/kernel_footprints.sh`: runs the lint (`cargo xtask check-generated` and the skeleton pass) over the
real kernel library, then the recorder battery (`cargo test -p frob-kernels -- access_recorder`), then the planted
fixtures under `tests/fixtures/footprints/` expecting each to fail. Logs per the end-to-end standard: per kernel
the number of accesses classified contained, annotated and violating; for each planted fixture the message
matched; the kernel library's registry digest; a `summary` line with counts.

### Known answers and negative controls

Negative controls (each must be caught): a skeleton that stores to a buffer its manifest does not declare; an
off-by-one loop bound; a gather without an annotation; a manifest footprint hand-narrowed below the derived set; a
`float`-class kernel that reads another world's row. Metamorphic: enlarging a capacity enlarges derived intervals
monotonically. Lanes: host only for the lint; the recorder on `batch-cpu` at 1 and 24 workers.

## Considerations

- Interval analysis over-approximates; a skeleton may need a tighter loop or an annotation to pass. That cost is
  accepted: a declared footprint that cannot be justified is the defect this obligation exists to find.
- The lint reads the dialect; device compilers may still miscompile. The CPU-versus-device check and the digest
  tripwire cover that; this obligation is about what the source says.
- Skeleton sources are few (one sort, one compaction, one segmented reduction serve every stage), which keeps the
  annotated set small enough to review by hand.
