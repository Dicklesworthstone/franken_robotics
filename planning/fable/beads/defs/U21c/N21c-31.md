## Background

Every gate must have a planted defect it catches. Spark's known-answer table names twelve controls; the first six
are due at M0 and are registered by the companion bead. This bead registers the six that guard the M2 and M4
gates, plus the planted overflow of the wide-count rule:

| # | Known answer | Expected | Negative control that must be caught |
|---|---|---|---|
| 7 | Strict placement with one device kernel withheld | Refusal before any world is stepped; zero episodes | The same request under `mixed-allowed` must show actual ≠ requested |
| 8 | Run digest under slot permutation | Unchanged | A digest that chains in slot order |
| 9 | Kernel cache | A one-byte change of source, options, compiler or driver identity is a miss | A corrupted entry must be rejected by digest |
| 10 | Commit fence with injected command-buffer faults | Final digests equal those of the unfaulted run | With the fence disabled the mismatch must be detected |
| 11 | Specialized against generic kernel on 10⁶ states | Bit-identical | A reassociated variant must be refused |
| 12 | Scene regenerated on the other machine from its seed | Same `SceneId` | A generator with one changed constant |
| 13 | A step plan whose histogram bin could receive 2³² or more increments in one chunk | Refused at plan time | A mutant plan that lets one bin receive 2³² + 5 increments in a chunk reads 5 on the device |

Context for each. (7) A strict backend request (`strict:gpu-cuda`, `strict:gpu-metal`) with a stage that has no
kernel there is `FROB-REF-604`, raised by the planner before any scoring; only `mixed-allowed` lets a stage fall
back to `batch-cpu`, and the receipt must then show it. The control proves the receipt can tell the two apart.
(8) A run digest is the wrapping sum of per-world digests keyed by address, which is independent of slot order.
(9) The cache key is BLAKE3 over expanded dialect text, compile options, prelude version, compiler identity, device
architecture and driver version; a hit is checked against its digest before use and a corrupt entry is a miss
(offline, `FROB-REF-612`). (10) Rule R2: a terminal state other than completed invalidates every slab the batch
could write; a chunk reads from one committed slab and commits to the other; on failure the arena restores and
resubmits, at most four attempts with growing waits, then `FROB-REF-607`. (11) `FROB-REF-613`. (12) Scenes cross
machines only as recipes. (13) A 32-bit bin wraps at 2³² = 4,294,967,296 increments.

## Scope

In: the seven registry rows, their mutants or injections, expected detections, per-backend applicability, and the
end-to-end run. Out: the known-answer tests and mechanisms (placement, digests, cache, fence, specialization fence,
regeneration, the no-wrap bound).

## Technical approach

Rows in `registries/negative_controls.toml`, run by `frob-conformance::negctl::run(id)` (pass only if the guarded
test fails in the expected way; a surviving mutant blocks its gate).

| id | Plant (DESIGN) | Expected detection | Guards |
|---|---|---|---|
| `spark.mixed-allowed-counterpart` | Test manifest filter `--withhold <kernel>` removes one stage's device kernel; the run is repeated under `mixed-allowed` | Under strict: `FROB-REF-604`, zero worlds stepped, zero episodes. Under `mixed-allowed`: the receipt's row for that stage has actual backend `batch-cpu` ≠ requested, a fallback reason, and non-zero transfer bytes and synchronizations. A receipt that shows actual = requested fails the control | KA-534, GATE-SPARK-09, INV-SPARK-07 |
| `spark.digest-slot-chain` | Test feature `mutant-digest-slot-chain`: the run digest folds per-world digests in slot order instead of summing them by address | Under a random slot permutation the run digest changes; the permutation test fails | KA-535 |
| `spark.cache-corrupt` | Flip one byte in the middle of one cache entry's file between a cold and a warm start | The entry's digest check fails; it is treated as a miss and recompiled (compiler invocations = 1 for that kernel); with the compiler made unavailable (`--offline`), `FROB-REF-612`. Loading the corrupted binary fails the control | KA-536, GATE-SPARK-11 |
| `spark.fence-disabled` | The one registry row for the fence seam: the seam is built by N21b-07, and N21b-26 and N21b-42 cite this row without adding a second. Test feature `mutant-no-commit-fence` (the arena treats a failed chunk's target slab as current) together with injected command-buffer faults (the gateway's seam on Metal; an injected launch failure on CUDA) | Final per-world digests differ from the unfaulted run's and the comparison reports the first differing world and chunk. With the fence enabled the same injections give identical digests and counted retries | KA-537, GATE-SPARK-12 |
| `spark.specialized-reassociated` | A script-written specialized kernel in which one sum (a + b) + c is emitted as a + (b + c) | The bit-identity fence refuses it with `FROB-REF-613` (statically by normal form, dynamically by the first differing state) and the generic kernel is used | KA-538, GATE-SPARK-14, INV-SPARK-09 |
| `spark.generator-constant` | Test feature `mutant-generator-constant`: one numeric constant of a scene generator changed in its last digit | The regenerated `SceneId` differs from the recipe's expected identity and the scene is refused | KA-539 |
| `spark.plan-overflow` | A test-only plan builder that skips the no-wrap admission check and sizes a chunk so that one bin receives 2³² + 5 increments | The device bin reads 5 at the drain while the CPU `u64` reference reads 4,294,967,301: the totals differ. The unmutated planner refuses the same plan at admission | GATE-SPARK-23 |

**Applicability and milestones.** Rows 7 to 10, 12 and 13 are due at M2 (row 12 for terrain generators at M2 and
again for interior generators at M3). Row 11 is registered now and marked `pending (M4)`; it is activated with the
specialization fence and is `not applicable` if the specialization kill gate fires. Rows 8, 9 and 13 run on
`batch-cpu`, CUDA and Metal; row 10 needs a fault seam on each device family (where a seam does not exist in a
release build, the control runs in the debug build and says so).

**Cost of row 13.** 2³² + 5 increments must really be executed once per backend: at 2.0 M world-steps/s with 16
samples per interval and decimation 10 this is minutes, inside the default compute envelope; the control uses a
dedicated increment-only kernel so that it does not need a physics run.

## Acceptance criteria

- [ ] Seven rows exist with plant, expected detection, tier, backends, milestone and owner test.
- [ ] Each due control is reported caught on every applicable backend, with the recorded evidence: the refusal code and zero stepped worlds, and the `mixed-allowed` receipt row; two differing run digests; one recompile or `FROB-REF-612`; the first differing world under the disabled fence; `FROB-REF-613`; two differing `SceneId`s; device total 5 against reference 4,294,967,301.
- [ ] GATE-SPARK-09, -11, -12, -14 and -23 cannot be recorded as passed unless their controls' last runs were caught.
- [ ] No mutant feature is enabled in a shipped profile (the no-ship lint of the companion bead covers these features).
- [ ] The run log records commit, fingerprint digest, backend and build profile for every control run.

## Test plan

### Unit tests

`cargo test -p frob-conformance negctl_spark_m2`:
- `slot_chain_digest_is_order_dependent_host`: a chained fold of four `synthetic` per-world digests differs under a swap of two worlds; the wrapping sum does not.
- `wrap_arithmetic`: (2³² + 5) mod 2³² = 5.
- `cache_entry_digest_mismatch_is_miss` (host, on a `synthetic` entry).
- `withhold_filter_removes_exactly_one_kernel`.
- `row_11_pending_until_m4`: the registry check accepts `pending` before M4 and rejects it after.

### End-to-end script and logging

`scripts/e2e/spark_negative_controls.sh --milestone m2 --backend all` (the script of the companion bead): for each
row the commands that plant and detect it, for example `frob sim run … --tier strict:gpu-cuda --withhold K-hess
--json` then the same with `--tier mixed-allowed:gpu-cuda`; `frob spark cache --json` before and after the byte
flip; the faulted and unfaulted runs with `frob telemetry divergence --exact`. Logs per the end-to-end standard:
control id, build features, command lines, exit codes, expected and observed detection with digests or refusal
codes, the first differing world, chunk or state, backend and fingerprint digest, and a `summary` line with caught
and not-caught counts and the gates guarded.

### Known answers and negative controls

KA-534 to KA-539 with the values above and the wide-count known answer (a planted overflow reads 5). CX-229
(live reads) and CX-230 (unordered scatter) are neighbours guarded elsewhere. The harness's own control is the
companion bead's `negctl_passes_only_on_expected_failure`. Lanes: each backend; twice on one machine; debug build
for the fault seams.

## Considerations

- The fence control depends on a fault seam; if a device family offers none, the control is weaker there and the
  gate's record says which injections ran.
- The cache control must flip a byte that the loader would execute, not padding; the plant chooses an offset inside
  the code section recorded in the entry's metadata.
- A control that becomes impossible to plant (a mechanism removed by a kill gate) is closed as `not applicable`
  with the decision's identity, never deleted.
