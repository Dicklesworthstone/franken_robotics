## Background

**The question.** OPEN-SPARK-1: owner ratification of ADR-SPARK-01. Owner: the project owner. Due: put to the owner
at M0; it blocks the M2 exit. **Fail-closed default: GPU results are labelled exploratory until ratified.**
Consequence of the default: no Performance or Parity claim rests on a device result, and M2 exits in its no-GPU
variant.

**Why it is a question at all.** FACT: the sibling simulation suite's accelerator doctrine states that it "does not
ship an accelerator backend", requires a permanent CPU reference, defines twelve evidence fields for any device
run, and forbids in-process foreign kernels in its production paths; its working GPU code lives outside its
workspace, and FrankenTorch's `ft-kernel-metal` is that project's sanctioned unsafe boundary. FrankenRobotics has an
explicit owner mandate for CUDA and low-level Metal. ADR-SPARK-01 is the proposal that meets the mandate without
weakening the core:

- the core workspace is `unsafe_code = "deny"` with Franken-only runtime dependencies and never depends on a GPU
  crate;
- GPU backends live in **annex workspaces** under `spark/`, each with its own lockfile and a registry of unsafe
  capsules with a `SAFETY.md` each; they build on the one toolchain of the build graph; the boundary exists for the
  unsafe and foreign-interface policy;
- binaries that use a GPU are built from an `apps/` workspace that links the core and an annex;
- every device run emits a receipt with the suite's twelve evidence fields unchanged, with FrankenRobotics' fields
  beside them;
- the CPU reference is permanent.

The pre-mortem names the failure this bead prevents: "the GPU mandate and the suite's no-FFI doctrine were never
reconciled, and work stalled on policy" (leading indicator: this question still open at M2). The design lets work
proceed under a label while the owner decides.

## Scope

In: the decision packet for the owner; the machine-readable decision record; the fail-closed default as code (the
`exploratory` label and the refusals it causes); the switch when the decision is recorded. Out: the annex design
itself (the workspace and backend beads); the dependency lint (N21c-24); the device-receipt check (N21c-28).

## Technical approach

1. **Decision packet** (a document for the owner, generated from the registries so that it cannot drift): the
   five clauses above; the list of unsafe capsules in each annex with their `SAFETY.md`; the dependency-policy
   rows that enforce the boundary; what the owner is asked to choose: (a) ratify as written; (b) ratify with
   amendments (for example an out-of-process device worker in place of in-process linking in `apps/`); (c) decline,
   in which case the product is CPU-only and the device beads close `withdrawn` citing the ADR-SPARK-01 row
   (N41-17: a bead only on the branch not taken). Each option lists what changes downstream.
2. **Decision record: one place, the one the M0 code already reads (DESIGN).** The decision is the `status` of the
   ADR-SPARK-01 row of `registries/decisions.toml`, the row N21a-03 creates with `status = "unratified"` and the
   annex policy of N21a-01 reads at backend registration. This bead extends that row's vocabulary and fields:
   `status = "unratified" | "ratified" | "ratified-amended" | "declined"`, with `date`, `reference` (the owner's
   commit or record) and `amendments` (with the bead key of each). The question's own record, OPEN-SPARK-1 in
   `registries/open.toml` (N41-OPEN3, "decided in N21c-34"), is closed with the same date and reference when the
   status leaves `unratified`. No third file exists: an earlier draft of this bead had
   `registries/owner_decisions.toml`, which would have let two readers consult two files for one decision. Only an
   owner-authored commit may change the status (the registry lint checks that `reference` is non-empty when the
   status is not `unratified`). Below, "open" means status `unratified`.
3. **The default as code.** While the status is not `ratified` (also when the file or row is missing or
   unreadable): every envelope whose result is a device result carries `exploratory: true` and
   `exploratory_reason: "OPEN-SPARK-1"` in the device block of its evidence (`evidence.device.exploratory`, the one
   spelling, attached only in N21a-02's dispatcher hook, which also strips `Performance` and `Parity` from that
   envelope's `claims` at emission). This bead supplies the one predicate both enforcement points call,
   `frob_core::decisions::exploratory_blocks(claim_kind, receipt) -> Option<Blocked>` (DESIGN), which reads the
   row at call time: true for a `Performance` or `Parity` claim resting on a device receipt while the status is not
   `ratified`. (a) A verb that would cite such a result for a Performance or Parity claim or publish a throughput
   figure refuses with the claim-product refusal `FROB-REF-819` (a result cited above its claim product), whose
   `pointer` names `evidence.device.exploratory` and whose `observed` names OPEN-SPARK-1 and the row's status;
   each citing verb's bead calls the predicate (the first is `report.run`, BD-302, M3), and this bead proves the
   refusal through a test verb.
   (b) The gate recorder (N38b-19, a Cargo example target and not a verb, so it has no `FROB-REF` code) refuses to
   record a Performance or Parity gate part whose evidence is such a receipt with its refusal `evidence-unresolved`,
   cause `exploratory: OPEN-SPARK-1 <status>`; this bead registers the predicate as a check of the recorder's
   step-7 hook list (`register::record::CHECKS`, the extension point N38b-19 owns; check `exploratory_not_cited`,
   DESIGN, a pure function of the candidate row and the resolved evidence), and the M2 no-GPU variant (N40-33,
   test `exploratory_not_citable`) relies on it. Known-answer gates (for
   example GATE-SPARK-00, -01, -07, -08) are not blocked: the label restricts claims, not measurements. Both checks
   read the decision registry at citation time, not a stored flag, so ratification lifts them for results already
   stored (the label states a policy status, not a property of the numbers).
4. **Outcomes.** `ratified`: the label is no longer attached. `ratified-amended`: the label stays until every
   amendment has a bead key recorded in `amendments`, after which the owner records `ratified` with the
   amendments listed (the annex policy of N21a-01 lifts the label only on `ratified`). `declined`: device verbs
   answer the capability refusal `FROB-REF-724` (exit 5), applied in the same dispatcher hook of N21a-02 before
   the verb runs, so CLI and MCP answer alike; device gates are recorded `not run: OPEN-SPARK-1 declined`.
5. **M2 exit.** If the status is `unratified` at the M2 exit review, the review applies the no-GPU variant: everything
   lands on `batch-cpu`, device gates are `not run` with the reason, and any device result that exists is labelled
   exploratory.

## Acceptance criteria

- [ ] The decision packet exists at M0, lists the five clauses, the capsules and the options with their consequences, and has been put to the owner (a dated record of the request).
- [ ] With the ADR-SPARK-01 row of `registries/decisions.toml` at `unratified` (or missing, or unreadable), a device result's envelope carries `evidence.device.exploratory: true` with `exploratory_reason: "OPEN-SPARK-1"` on both surfaces (CLI and MCP), the one spelling of N21a-02; no file `registries/owner_decisions.toml` exists.
- [ ] With the row `unratified`: the gate recorder refuses to record a Performance gate part (a fixture row in a scratch copy of `registries/gates.toml`, standing for GATE-SPARK-03 before M2) whose evidence is a device receipt, with `evidence-unresolved` and the cause naming OPEN-SPARK-1; a Known-answer gate part citing the same receipt records normally; the test verb citing a device throughput for a Performance claim is refused with `FROB-REF-819` (`pointer` `evidence.device.exploratory`). The same refusal on `frob report run <id> --claim performance` (M3) is asserted by the verb's bead, BD-302, which calls this predicate; this bead does not depend on it (convention 7) and its script does not call it.
- [ ] Changing the row to `ratified` (with a reference) removes the label from new and stored device results and closes OPEN-SPARK-1 in `registries/open.toml` with the same reference; changing it without a reference fails the registry lint; `ratified-amended` keeps the label until the owner records `ratified`.
- [ ] With the row `declined`, `frob sim run <design> --tier gpu-cuda --key os1-declined-<run-id> --json` and `frob spark check --kernel K-cay-step --backend gpu-cuda:0 --key os1-declined-ck-<run-id> --json` return `FROB-REF-724` (exit 5) before the verb runs, and the same runs on `batch-cpu` are unaffected.
- [ ] The M2 exit checklist reads this row and applies the no-GPU variant when it is `unratified`.

## Test plan

### Unit tests

`cargo test -p frob-core decisions_adr_spark_01`, `-p frob-verbs exploratory_label`, `-p frob-conformance
exploratory_hook`:
- `label_attached_while_open`; `label_absent_when_ratified`; `label_evaluated_at_citation_time` (a stored result gains and loses the label with the registry).
- `performance_claim_refused_on_exploratory` (`FROB-REF-819`, `pointer` naming the label and `OPEN-SPARK-1`), through a test verb that cites a device receipt for a Performance claim.
- `gate_pass_refused_on_exploratory` (in `exploratory_hook`): the recorder, run in the test on a scratch register, refuses a Performance part on a device receipt with `evidence-unresolved` at the `exploratory_not_cited` check and writes nothing; `known_answer_gate_not_blocked`: a Known-answer part on the same receipt records.
- `exploratory_blocks_truth_table`: claim kinds {Performance, Parity, Known answer, Fidelity} × statuses {unratified, ratified-amended, declined, ratified, missing} × {device receipt, `batch-cpu` receipt}; blocked exactly for the first two kinds on a device receipt under any status but `ratified`.
- `declined_makes_device_verbs_724`.
- `registry_requires_reference_for_non_open_state` (any status other than `unratified` without a reference fails).
- `amended_keeps_label_until_ratified`; `open_question_closed_with_decision` (the OPEN-SPARK-1 record of `registries/open.toml` is closed with the row's date and reference).
- `one_spelling_of_the_label`: the envelope schema has `evidence.device.exploratory` and `exploratory_reason` and no `labels` entry for it, and the receipt type has no `exploratory` field; a planted `registries/owner_decisions.toml` fails the registry lint.
- `cpu_results_never_labelled_by_this_rule`.

### End-to-end script and logging

`scripts/e2e/open_spark_1.sh`: under `e2e_registries_scratch` (the one way a script changes a registry; the
summary then carries `gates_claimable: false`), with the scratch copy's ADR-SPARK-01 row of
`registries/decisions.toml` set to each of its four statuses in turn (and once deleted), runs
`frob spark check --kernel K-cay-step --backend <gpu-cuda:0|gpu-metal> --key os1-<status>-<run> --json` on the CLI
and the same call as the MCP tool `spark_check` through `frob-mcp` over stdio (asserting equal device blocks), then
the recorder's check on the scratch `registries/gates.toml` holding one Performance fixture row and one
Known-answer fixture row that cite the run's receipt: `FROB_OS1_RECEIPT=<hash> cargo test -p frob-conformance
exploratory_hook` (DESIGN input variable; a filter without `--test`, legal under BD-025's command lint), which runs
the recorder's step 7 on the two fixture rows and writes nothing. The script never runs `record_gate`: STD-E2E's
self-recording lint exempts only the recorder's own scripts (N38b-19, N38b-21). Then the citation through the test
verb (`cargo test -p frob-verbs exploratory_label -- performance_claim_refused_on_exploratory`, with the same
receipt); `frob report run`'s citation is asserted by BD-302's own script. It asserts the label, the recorder
outcome and the refusal per status (`declined`: `spark.check` itself answers `FROB-REF-724`). Logs through the STD-E2E helper to
`target/e2e-logs/open_spark_1/<utc>.ndjson`: the registry status, command lines, exit codes, wall time, the
evidence block with the device block, refusal codes with pointers and repairs, the recorder's reason and cause
from the test's output, and a `summary` line. Where no device is present the script uses the `batch-cpu` backend posing as a device tier in the
conformance profile and marks the run `no-device`.

### Known answers and negative controls

Negative controls: an envelope builder that drops the label on the MCP surface only (the parity check between
surfaces must fail); a registry row set to `ratified` with an empty reference (the lint must fail); a report that
strips labels when summarizing (the citation must still be refused, because the label is re-evaluated from the
registry).

## Considerations

- This is a policy label; it is independent of determinism classes, of the CPU-versus-device check and of the Metal
  kill gate, each of which can restrict device results further.
- The default costs nothing technically: all device work proceeds, measured and receipted; only claims wait.
- Division with the M0 beads (one statement each): N21a-01 reads the row at backend registration and fails closed;
  N21a-02 stamps `evidence.device.exploratory` with its reason, strips the two claim kinds at emission and
  applies the `declined` answer; N21a-03 creates the row and checks that the ADR file's Status mirrors it; this
  bead owns the packet, the status vocabulary beyond `unratified`, the `exploratory_blocks` predicate and the two
  citation refusals (819 for verbs, `evidence-unresolved` in the gate recorder), the outcomes and the M2 exit
  rule. The other Spark owner decision, OPEN-SPARK-5 (N21b-09, N21c-38), is a row of the same file,
  `id = "OPEN-SPARK-5"` with its own status vocabulary (N21b-09), as the numerics decisions OPEN-NUM-2 and
  OPEN-NUM-4 are.
- If the owner amends the design toward an out-of-process worker, the device receipts and the fingerprint are
  unchanged; the linking model and the launch-cost figures change and are re-measured.
