## Background

**The question.** OPEN-SPARK-2: a compute envelope for gate measurements and training campaigns. Owner: the project
owner. Due at M0. It blocks GATE-SPARK-03, GATE-SPARK-04, GATE-SPARK-20 and GATE-SPARK-21 as specified (the
throughput, scaling and incumbent-parity gates), the mixed-batch head-to-head and every campaign.

**Fail-closed default (class E0).** FACT: the sibling simulation suite's machine rule caps any run at 16 GiB of
memory, 8 cores or one hour of wall time without written approval, and builds and tests count. FrankenRobotics
inherits that rule for CPU work and limits a GPU job to **one device and one hour** until the owner approves an
envelope. Nothing above E0 runs until the proposal below is ratified or amended.

**What the default cannot run, by arithmetic.** One device-hour at 50 to 500 k env-steps/s is 0.18 to 1.8·10⁹
env-steps. The performance gates themselves exceed it: one throughput row uses 24 threads, the strong- and
weak-scaling rows use two devices, and the world bank holds far more than 16 GiB. The rank-agreement experiment
between evaluation rungs needs about forty per-design trainings: about 45 device-hours, or 5 to 7.5 where
specialists are reused. Pretraining a family policy at published sizes: 1.6·10⁹ steps are 0.9 to 9 device-hours;
5·10⁹ are 2.8 to 28; 2·10¹² are 1,100 to 11,000 device-hours, which is 23 to 230 days on two cards and is not
planned in any envelope.

**The proposal to the owner.**

| Class | Scope | Proposed limits |
|---|---|---|
| E0 | Default | 16 GiB, 8 cores, 1 hour, one device |
| E1 | A named gate measurement | Both machines, all cores, memory up to the device budget, 2 hours per run, 12 device-hours per gate |
| E2 | A design campaign | 48 device-hours |
| E3 | Pretraining of one family policy | 500 device-hours, approved per run with its ceiling and kill rule written first |

RISK-10 (likelihood high): no compute envelope is approved, so the performance gates, the rank-agreement experiment
and pretraining cannot run as specified. Leading indicator: this question still at E0 when M1 opens. Mitigation:
the classes are proposed at M0; every work package above E0 names its budget; M2 and M4 have variants that fit E0.

## Scope

In: the decision on OPEN-SPARK-2 itself. That is: the packet that asks the owner to ratify or amend the classes
E0 to E3; the one record of classes and approvals, `registries/compute_envelope.toml`, with the schema of both
of its tables, its loader and its lint; the class tables of that file (limits, state, reference) as this bead's
content; the default as a tested fact of the record (E0 in force for every scope that has no approved row); the
function `class_in_force`; the reason text a gate records when its class is not approved; what a ruling changes.

Out, with the bead that has it:
- The per-package requests and their not-approved fallbacks, both as `[[request]]` rows of the same file and as
  the list put to the owner, are N44-01: one list, kept there. This bead's packet attaches that list and
  restates no row of it; N44-01 depends on this bead for the file and the classes its rows name.
- Enforcement is N36-20: the demand vector, the needed-class computation (which needs the meter's consumption
  per scope), the device-hour meter, the admission check on every path that starts work, the timeout, refusal
  `FROB-REF-761` and every test of it, and the envelope arithmetic as the tested known answer KA-823. N36-20
  depends on this bead and reads the record only through the loader built here; it never writes the record.
- The estimator's cost model (BD-219); the daemon's `campaign` size class and `FROB-REF-704` (BD-296); the
  script guard for lanes outside the daemon, which reads the same request rows (N34-15).

## Technical approach

1. **Decision packet** for the owner (`docs/decisions/OPEN-SPARK-2.md`, DESIGN path): the class table above; the
   arithmetic above, quoted as text (it is checked as known answer KA-823 by the enforcement bead N36-20); what
   each ruling changes (point 5); and, attached, the request register of N44-01 with its total in that bead's three
   parts: the eleven rows R1 to R11 that N44-01 writes at M0 (the ten rows of the plan's work-package table with
   class asked and not-approved fallback, and R11, the two-card fingerprint and peer experiment of GATE-SPARK-07:
   E1 for `gate:GATE-SPARK-07`, N21c-03 and N21c-06; not approved, they run per card under E0 and the peer block
   reads `untested`); the fifteen reserved rows R12 to R26 at their stated estimates, each filed later by the bead
   its reservation names (R12 the fleet gate's campaigns, GATE-SPARK-13, filed by BD-370: E1 at about 13 to 16
   minutes per run by its sizing rule, or E2; R13 to R18 the Cortex pilots and the measurement of GATE-CORTEX-22;
   R19 to R26 the further pilots and gate runs N44-01 lists, new requests taking R27 onward); and R13, the one
   request no class covers. Silence on a reserved row at M0 is not a ruling on it. The packet asks one
   question of its own: ratify or amend the limits of E1, E2 and E3.
   The rulings on the individual requests are recorded by N44-01 and by the decision bead of each request's own
   open question.
2. **Decision record: one file (DESIGN).** `registries/compute_envelope.toml`, schema `frob.compute_envelope/1`,
   is the only record of envelope classes and of approvals. Reason: admission by the verbs (N36-20) and the
   script guard (N34-15) must reach the same verdict for the same run, and two approval files can disagree; so
   no `registries/envelopes.toml` and no per-script approval file exists. The file has two tables.

   ```
   schema = "frob.compute_envelope/1"
   in_force = "E0"                  # the class in force for a scope with no approved request row

   [class.E0]
   scope = "default"
   limits = { mem_gib = 16, cores = 8, wall_s_per_run = 3600, devices = 1 }
   state = "approved"               # the inherited machine rule; it needs no ruling
   reference = "frankensim/AGENTS.md rule 1.1; OPEN-SPARK-2 default"

   [class.E1]
   scope = "a named gate measurement"
   limits = { machines = "both", cores = "all", mem = "device budget", wall_s_per_run = 7200, device_hours = 12 }
   state = "proposed"               # proposed | approved | amended
   reference = ""                   # the owner's decision record under docs/adr/; required for any state other than proposed

   [class.E2]
   scope = "a design campaign"
   limits = { device_hours = 48 }
   state = "proposed"
   reference = ""

   [class.E3]
   scope = "pretraining of one family policy"
   limits = { device_hours = 500 }
   per_run = true                   # approved per run, with ceiling and kill rule written first
   state = "proposed"
   reference = ""

   [[request]]                      # rows are N44-01's content; the fields are fixed here
   id = "R6"                        # stable; a new request takes the next number
   parent = ""                      # for a per-run approval under a standing E3 request: that request's id
   packages = ["WP-60"]
   scope = "the rank-agreement pilot; the partial gate's campaigns"   # prose, for the owner
   admits = ["campaign:rank-agreement"]   # admission scopes this row covers: gate:<id>, campaign:<id>, pretrain:<run>
   class = "E2"
   limits = { device_hours = 48 }   # equal to the class's unless the owner amends this row
   not_approved_fallback = "cheap rungs are `uninformative`; the partial gate runs its CPU strata"
   open_question = "OPEN-PROG-4"
   status = "requested"             # requested | approved | amended | declined
   approved_by = ""                 # required when status is approved or amended
   date = ""                        # ISO date of the ruling
   decision = ""                    # path of the owner's ruling, a decision record under docs/adr/ (convention 4; the packet put to the owner may sit under docs/decisions/)
   token = ""                       # hash of that decision record; set with the ruling
   expires = ""                     # the gate, campaign or date after which the approval lapses
   ceiling = ""                     # E3 only: the run's ceiling in device-hours, written before approval
   kill_rule = ""                   # E3 only: the rule that stops the run, written before approval
   ```

   A per-run approval for E3 is a `[[request]]` row of its own (`parent` names the standing request, `admits`
   holds one `pretrain:<run>` scope, `ceiling` and `kill_rule` are filled); the earlier sketch of a separate
   list of E3 run approvals (`run`, `ceiling`, `kill_rule`, `reference`) is this row. The loader
   (`frob_core::envelope::registry`, with the other registry loaders) rejects: an unknown key; a class state
   other than `proposed` without `reference`; a row with status `approved` or `amended` without `approved_by`,
   `date`, `decision` and `token`, or whose `decision` is not a path under `docs/adr/`; an approved or amended E3 row without `ceiling` and `kill_rule`, or with a
   ceiling above the class limit; a row with an empty `not_approved_fallback`; a row whose `class` is not a
   class of the file; a row naming a package key that does not exist; two approved rows that admit the same
   scope; and a `[[request]]` row not written one `key = value` per line (so that the POSIX guard of N34-15 can
   read a row without a TOML parser).
3. **The default as code: the class in force.** `frob_core::envelope::class_in_force(scope, registry, today)`
   (DESIGN, a pure function of its arguments) returns the class and limits of the one `[[request]]` row that
   lists `scope` in `admits`, has status `approved` or `amended`, has not expired, and names a class whose own
   state is `approved` or `amended`; the limits are the row's. In every other case (no row, a row still
   `requested` or `declined`, an expired row, a class still `proposed`, the scope `adhoc`, a missing or unreadable
   file) it returns `in_force`, which is E0 and cannot be set higher by the file: the loader rejects any other
   value. So with no approval on record the class in force is E0 for every job, and nothing above E0 runs
   until a ruling is recorded. `sim.estimate` prints the class a job needs and a job above the class in force is
   refused before it starts (`FROB-REF-761`, exit 4, first repair: a smaller job; second: request the class):
   that computation and refusal are N36-20's, on top of this function.
4. **What a gate records.** A gate whose measurement needs a class that is not in force for its scope is
   recorded `not run` with the reason "OPEN-SPARK-2: class E<n> not approved", never as failed and never as
   passed. This bead supplies the reason text as a constant (`frob_core::envelope::NOT_APPROVED_REASON`) and the
   test that the gate recorder's state machine rejects `fail` or `pass` with that cause.
5. **Outcome handling.** `approved` or `amended`: the limits and state in the class table change, with the
   reference, and nothing else does; every request row is then re-read against the new limits by N44-01. A
   refusal by the owner of a class leaves the fallbacks of the rows that asked for it in force: a bead that exists
   only under the approval closes `withdrawn` citing the row as the decision (N41-17; for example `withdrawn: not
   run: no envelope, R13`), never `fallback` or a free-text reason.

## Acceptance criteria

- [ ] The decision packet exists at M0 with the table, the arithmetic and, attached, N44-01's register of per-package requests and fallbacks, and has been put to the owner (a dated record).
- [ ] `registries/compute_envelope.toml` is committed with the four class tables above (E0 `approved`, E1 to E3 `proposed`), loads, and is the only envelope record in `registries/`: no `envelopes.toml` exists.
- [ ] With no approval on record, `class_in_force` returns E0 for every scope, including a gate scope whose row is still `requested`; with E1 ratified and a row approved for `gate:GATE-SPARK-21` in a scratch registry it returns E1 for that scope and E0 for every other.
- [ ] A file with `in_force` set to anything but `E0` fails to load; an E3 approval without a ceiling and kill rule fails the lint; an approved row whose class is still `proposed` gives E0.
- [ ] Recording GATE-SPARK-03 or GATE-SPARK-04 when its runs need an unapproved class yields `not run` with the reason; `fail` and `pass` with that cause are rejected.
- [ ] The refusal of a job above the class in force (`FROB-REF-761` before any allocation for a two-device job; admission of a one-device job estimated under one hour; admission of the two-device job once E1 is approved for its scope) is shown by N36-20's tests, which read this record through this bead's loader. The daemon's `FROB-REF-704` for a campaign-class job is BD-296's.
- [ ] The performance chapter's restatement of the question points to this record (one question, one record).

## Test plan

### Unit tests

`cargo test -p frob-core envelope::registry`:
- `default_in_force_is_e0`: the committed file, every scope → E0.
- `in_force_cannot_be_raised`: `in_force = "E1"` → load error naming the key.
- `class_in_force_cases`: scratch registries: (row `requested`) → E0; (row `approved`, class `proposed`) → E0; (row `approved`, class `approved`, scope listed in `admits`) → that class with the row's limits; (same, another scope) → E0; (row expired) → E0; (`adhoc`) → E0; (file missing) → E0.
- `e3_requires_ceiling_and_kill_rule`; `e3_ceiling_above_class_limit_rejected` (ceiling 600 against 500); `non_proposed_state_requires_reference`; `approved_requires_record` (status `approved`, empty `approved_by`); `decision_under_docs_adr` (an approved row whose `decision` is `docs/decisions/R6.md` is rejected, `docs/adr/ADR-OPEN-PROG-4.md` accepted); `row_requires_fallback`; `unknown_class_rejected`; `two_approved_rows_for_one_scope_rejected`; `request_row_one_key_per_line`.
- `class_limits_committed`: E0 = 16 GiB, 8 cores, 3,600 s, 1 device; E1 = 7,200 s per run and 12 device-hours per gate; E2 = 48 device-hours; E3 = 500 device-hours.
- `gate_not_run_reason`: the reason text, and the recorder's rejection of `fail` and `pass` with that cause.

The needed-class cases, the upper-end rule and the device-hour arithmetic (KA-823) are tested in N36-20
(`needed_class_cases`, `upper_end_not_point`, `device_hour_arithmetic`).

### End-to-end script and logging

`scripts/e2e/open_spark_2.sh`: runs the registry check of the `frob` skeleton (`frob doctor --json`, BD-022)
against four scratch copies of `registries/`, each made with `e2e_registries_scratch` (the one way a script
changes a registry; the summary then carries `gates_claimable: false`): the committed default; E1 ratified with
one row approved (its `decision` a path under `docs/adr/`); an E3 row approved without a kill rule; `in_force`
raised by hand. It asserts, per copy, the loader's verdict, the class in force reported for the scopes `adhoc`,
`gate:GATE-SPARK-21` and `campaign:rank-agreement`, and the exit code. Logs through the STD-E2E helper to
`target/e2e-logs/open_spark_2/<utc>.ndjson`: registry state and its hash, command lines, exit codes, the class in
force per scope, the loader's first error with its key, and a `summary` line. The script spends no device time
and submits no job. The submission path (`frob sim estimate @fixture:two-card-train --json` and
`frob train start @fixture:two-card-train --json`, asserting needed class, refusal code and exit code per
registry state) is a step of N36-20's script `scripts/e2e/perf_envelope_meter.sh`.

### Known answers and negative controls

Known values: the committed class limits; E0 for every scope by default. The device-hour arithmetic of the
packet is known answer KA-823, tested by N36-20. Negative controls: a loader that returns the class of a row
whose class is still `proposed` (must fail `class_in_force_cases`); a loader that accepts `in_force = "E1"`; a
gate recorder that writes `fail` for an unapproved envelope (the state machine must reject it). The control "an
admission path that checks the point estimate instead of the interval's upper end" (a point of 50 minutes with
an upper end of 70 must still be refused) is N36-20's `upper_end_not_point`.

## Considerations

- The default is strict on purpose: it keeps the program honest about what it has permission to spend.
- The envelope is a ceiling on spend, not a schedule; an approved E2 does not make a campaign cheap.
- Host load on `trj` and thermal state on the Mac affect how much work a device-hour buys; the envelope counts
  device-hours regardless.

- One record instead of two is a DESIGN choice of this bead, N44-01, N36-20 and N34-15 together: the classes
  and the per-scope approvals are read by the same admission decision, so they live in one file under one
  loader. If the owner prefers to rule in a document only, the registry row still has to be written from it
  before anything above E0 is admitted.
