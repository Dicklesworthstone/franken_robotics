## Background

**The question.** OPEN-SPARK-2: a compute envelope for gate measurements and training campaigns. Owner: the project
owner. Due at M0. It blocks GATE-SPARK-03, GATE-SPARK-04, GATE-SPARK-20 and GATE-SPARK-21 as specified (the
throughput, scaling and incumbent-parity gates), the mixed-batch head-to-head and every campaign.

**Fail-closed default (class E0).** FACT: the sibling simulation suite's machine rule caps any run at 16 GiB of
memory, 8 cores or one hour of wall time without written approval, and builds and tests count. FrankenRobotics
inherits that rule for CPU work and limits a GPU job to **one device and one hour** until the owner approves an
envelope. Nothing above E0 runs until the proposal below is ratified or amended.

**What the default cannot run, by arithmetic.** One device-hour at 50 to 500 k env-steps/s is 0.18 to 1.8·10⁹
env-steps. The performance gates themselves exceed it: one throughput row uses 24 threads, the strong- and
weak-scaling rows use two devices, and the world bank holds far more than 16 GiB. The rank-agreement experiment
between evaluation rungs needs about forty per-design trainings: about 45 device-hours, or 5 to 7.5 where
specialists are reused. Pretraining a family policy at published sizes: 1.6·10⁹ steps are 0.9 to 9 device-hours;
5·10⁹ are 2.8 to 28; 2·10¹² are 1,100 to 11,000 device-hours, which is 23 to 230 days on two cards and is not
planned in any envelope.

**The proposal to the owner.**

| Class | Scope | Proposed limits |
|---|---|---|
| E0 | Default | 16 GiB, 8 cores, 1 hour, one device |
| E1 | A named gate measurement | Both machines, all cores, memory up to the device budget, 2 hours per run, 12 device-hours per gate |
| E2 | A design campaign | 48 device-hours |
| E3 | Pretraining of one family policy | 500 device-hours, approved per run with its ceiling and kill rule written first |

RISK-10 (likelihood high): no compute envelope is approved, so the performance gates, the rank-agreement experiment
and pretraining cannot run as specified. Leading indicator: this question still at E0 when M1 opens. Mitigation:
the classes are proposed at M0; every work package above E0 names its budget; M2 and M4 have variants that fit E0.

## Scope

In: the decision packet; the decision record; the default as a tested fact (E0 in force with no record); the
per-package requests; what each gate records when its envelope is not approved. Out: the estimator and the
admission check that enforce a class (the performance chapter's bead), which read this record.

## Technical approach

1. **Decision packet** for the owner: the table above; the arithmetic above; the per-package requests: incumbent
   and parity measurements on both cards and all cores (E1 per gate; if not approved, single-card and eight-core
   rows only, the others recorded `not run`); training to threshold on two cards and the scaling rows (E1; else one
   card and the scaling gate `not run`); the head-to-head on 512 topologies with four arms (E1, repeated per arm;
   else decided on its pilot); the world bank resident on the Mac far above 16 GiB (E1 with memory to the device
   budget; else a bank that fits the default); certifying a failure rate of 10⁻⁶ (E2; else certify to 10⁻⁵); the
   rank-agreement pilot and the partial ten-fold gate's campaigns (E2; else cheap rungs are `uninformative`);
   pretraining of one family policy (E3 per run; else the variant with no family policy); design campaigns for the
   cascade and the surface comparison (E2 per campaign); the tournament (E2 per campaign, E3 where an arm
   pretrains); the fleet gate's campaigns (E1 at about 15 minutes per run, or E2).
2. **Decision record.** `registries/compute_envelope.toml`: `in_force = "E0"` and, per class, its limits and state
   (`proposed`, `approved`, `amended`), plus per-run approvals for E3 (`run`, `ceiling`, `kill_rule`, `reference`).
   The registry lint requires a reference for any state other than `proposed` and refuses an E3 approval without a
   written ceiling and kill rule.
3. **The default as code.** With no approval on record the class in force is E0. `sim.estimate` prints the class a
   job needs; a job above the class in force is refused before it starts (`FROB-REF-761`, exit 4, first repair: a
   smaller job; second: request the class); a `campaign`-class job without an approved envelope is `FROB-REF-704`.
   A gate whose measurement needs a class that is not approved is recorded `not run` with the reason
   "OPEN-SPARK-2: class E<n> not approved", never as failed and never as passed.
4. **Class computation (shared with the estimator).** needed class = the smallest class whose limits contain the
   job's estimated memory, cores, devices, wall time (the interval's upper end) and cumulative device-hours for its
   gate or campaign.
5. **Outcome handling.** `approved` or `amended`: the limits in the registry change and nothing else does. A
   refusal by the owner of a class leaves the listed fallbacks in force.

## Acceptance criteria

- [ ] The decision packet exists at M0 with the table, the arithmetic and the per-package requests and fallbacks, and has been put to the owner (a dated record).
- [ ] With no approval on record, `frob sim estimate` for a two-device job prints `needs: E1` and submitting it returns `FROB-REF-761` before any allocation; a one-device job estimated under one hour is admitted.
- [ ] A campaign-class job returns `FROB-REF-704` until an envelope is approved.
- [ ] Recording GATE-SPARK-03 or GATE-SPARK-04 when its runs need an unapproved class yields `not run` with the reason.
- [ ] Approving E1 in a scratch registry admits the two-device job; an E3 approval without a ceiling and kill rule fails the lint.
- [ ] The performance chapter's restatement of the question points to this record (one question, one record).

## Test plan

### Unit tests

`cargo test -p frob-core compute_envelope`:
- `default_in_force_is_e0`.
- `needed_class_table`: (8 GiB, 8 cores, 1 device, 40 min) → E0; (2 devices, 90 min) → E1; (30 device-hours campaign) → E2; (300 device-hours pretraining) → E3; (600 device-hours) → above every class, refused.
- `device_hour_arithmetic`: 500,000 env-steps/s × 3,600 s = 1.8·10⁹; 50,000 × 3,600 = 1.8·10⁸; 2·10¹² ÷ (500,000 × 3,600) = 1,111 device-hours.
- `e3_requires_ceiling_and_kill_rule`; `non_proposed_state_requires_reference`.
- `gate_not_run_reason`.

### End-to-end script and logging

`scripts/e2e/open_spark_2.sh`: with scratch registries (default; E1 approved), runs `frob sim estimate @fixture:two-card-train
--json` and `frob train start @fixture:two-card-train --json`, asserting class, refusal code and exit code per
registry state. Logs per the end-to-end standard: registry state, command lines, exit codes, the estimate's
interval and needed class, refusal codes with repairs, and a `summary` line. The fixtures are `synthetic` job
specifications; no device time is spent, because the refusal precedes admission.

### Known answers and negative controls

Known values: the device-hour arithmetic above. Negative controls: an admission path that checks the point estimate
instead of the interval's upper end (a job whose upper end exceeds one hour must still be refused; the test plants
a point of 50 minutes with an upper end of 70); a gate recorder that writes `fail` for an unapproved envelope (the
state machine must reject it).

## Considerations

- The default is strict on purpose: it keeps the program honest about what it has permission to spend.
- The envelope is a ceiling on spend, not a schedule; an approved E2 does not make a campaign cheap.
- Host load on `trj` and thermal state on the Mac affect how much work a device-hour buys; the envelope counts
  device-hours regardless.
