## Background

**The question.** OPEN-SPARK-5: what Spark does if the Metal gateway's admission test (INT-FT-01) fails, or until
the upstream work item FD-FT-01 lands; equivalently, whether a Metal binding of our own may be built before the
gateway is extended. Owner: the project owner. Due: M2, with the Metal kill gate. **Fail-closed default: no.** Spark
stays inside the gateway's present limits and accepts the Metal kill gate's fallback; a Metal binding of our own is
not built without an owner decision. Consequence of the default: the Mac may end up a development and replay tier
only.

**The decision it guards (ADR-SPARK-09).** Metal is reached through FrankenTorch's `ft-kernel-metal`
(`ft_kernel_metal::compute::Gateway`). Missing gateway features are upstream work items done in FrankenTorch's
repository, never a local patch or a second binding; until they land Spark works inside the gateway's limits. The
reason is the program's standing rule that a sibling is changed where it lives. An earlier fallback of a direct
binding was withdrawn.

**The gateway as it exists (FACT, read in source, version 0.1.3) and what Spark does inside each limit.**

| Limit today | Consequence for Spark | Covered by FD-FT-01 |
|---|---|---|
| Completion is synchronous: dispatch and submit block | One batch per chunk of control intervals; one blocked host thread per device | Yes |
| At most 31 buffer arguments per kernel | Arrays packed into a few slabs; kernels index through an offset table in a parameter buffer | Yes |
| Buffers bind at offset zero | Slab-relative indexing; no sub-buffer views | Yes |
| Shared storage only | Readback is a host copy after completion | Not needed |
| Host data copied in and out; typed helpers for `f32`, `u32`, bytes | Scene fields upload once; 16-bit fields packed into `u32` words | Yes |
| Compilation from source only; no function constants; no binary archive | Shape-class constants as `#define` lines; a warm start recompiles from cached source | Yes |
| One device and queue per process; 64 command buffers | One Metal worker per process | Not needed |
| The wait cannot be interrupted | A watchdog marks the device stalled; the supervisor restarts the worker | Yes |
| A failed batch is reported and not re-run | The commit fence | Not needed |
| The receipt has a kernel count and device seconds only | Per-kernel timing needs one batch per kernel in profiling mode | Yes |
| The underlying `metal` 0.33 binding is deprecated by its maintainers | Pinned as FrankenTorch pins it; migration is part of the work item | Yes |

FD-FT-01 (priority P1) asks for: asynchronous completion with several command buffers in flight; an interruptible
wait; typed buffers beyond `f32` and `u32`; binding at a byte offset; relief from the 31-argument limit; function
constants; a binary archive and ahead-of-time compilation; private storage with blits; per-kernel timing in the
receipt; newer command allocators; migration to a maintained binding. Part of it is wrapping, since the binding
under the gateway already exposes indirect thread-group dispatch and thread-group memory length. Its switch-over
rule: re-run the two gateway admission tests and the fidelity and Metal-throughput gates.

FACT: a direct binding is possible; the suite's piano renderer binds `metal` directly. That is why this is a
decision and not a technical impossibility.

## Scope

In: the decision packet; the decision record; the default as enforced fact; the two contingency branches
(admission fails; upstream work pending); what an owner "yes" would authorize and require. Out: the upstream work
itself (FD-FT-01, in FrankenTorch's repository under its rules); the Metal backend; the kill-gate decision.

## Technical approach

1. **Decision packet** for the owner, with measurements where they exist: the table above; the leading indicators
   measured on the Mac (step-plan launch counts, blocked host time per chunk, per-dispatch encode cost and
   commit-and-wait cost from the fingerprint); GATE-SPARK-04's ratio if measured; the state of FD-FT-01 in
   FrankenTorch's tracker. Options: (a) **no** (default): stay inside the limits, pursue FD-FT-01 upstream, accept
   the kill gate's fallback; (b) **raise FD-FT-01's priority** and fund it first, keeping (a) meanwhile; (c)
   **yes, a binding of our own** in the Metal annex: a second unsafe capsule with its `SAFETY.md`, a second code
   path that every device test must cover, a divergence from the gateway that must later be merged upstream or
   maintained; authorized only with a written scope (which gateway limits it removes) and a sunset rule (retired
   when FD-FT-01 lands and its switch-over tests pass).
2. **Decision record.** `registries/owner_decisions.toml` row `OPEN-SPARK-5 = { state: "open" | "no" |
   "upstream-first" | "own-binding", date, reference, scope, sunset }`; a non-`open` state needs a reference; the
   state `own-binding` needs `scope` and `sunset`.
3. **The default as enforced fact.** While the state is not `own-binding`, the dependency policy denies `metal` and
   `objc2-metal` as direct dependencies of the Metal annex (the deny rule of the routes-not-taken record), and no
   patch of the gateway exists in this repository (a lint forbids a `[patch]` entry for `ft-kernel-metal` other
   than the one FrankenTorch itself requires at the annex root).
4. **Branch: the gateway fails admission.** No Metal backend is linked; `spark.devices` lists the Metal device as
   `not-linked` with the admission record's reason; the Mac runs `batch-cpu` on its 36 cores; Metal gates are
   recorded `not run: INT-FT-01 failed`; the defect is filed upstream under FD-FT-01. No local workaround.
5. **Branch: admission passes, upstream work pending.** Spark runs inside the limits (the right-hand column
   above); the Metal kill gate decides the tier on measured throughput and determinism; when FD-FT-01 lands, its
   switch-over rule re-runs the admission tests and the two gates, and a pass may reopen the kill decision.
6. **If the owner says yes to (c).** The deny rule is lifted for the named scope only; a bead set is created for
   the binding with the same obligations as any backend (receipts, the CPU-versus-device check, fault and
   cancellation tests, the fingerprint), and the sunset rule is recorded with it.

## Acceptance criteria

- [ ] The decision packet exists before the M2 exit review, with the measured leading indicators and the state of the upstream work item, and has been put to the owner (a dated record).
- [ ] With the registry row `open` or `no`, a planted direct dependency of the Metal annex on `metal` fails the dependency check, and a planted local patch of the gateway fails the lint.
- [ ] With admission failed (simulated by a build without the Metal annex), `frob spark devices --json` shows the Metal device `not-linked` with a reason and CPU tiers work.
- [ ] Changing the row to `own-binding` without `scope` and `sunset` fails the registry lint.
- [ ] The upstream work item's interim posture and switch-over rule are written beside the row, and the kill-gate decision cites this record.

## Test plan

### Unit tests

- `owner_decision_row_states`: the four non-open states parse; `own-binding` requires scope and sunset; any non-open state requires a reference.
- `metal_annex_denies_direct_binding_while_not_authorized` (shared with the dependency policy tests).
- `no_local_gateway_patch_lint`: a `[patch]` of `ft-kernel-metal` pointing at a local path fails.
- `devices_not_linked_when_admission_failed`.
- `switch_over_rule_lists_four_reruns`: the record names the two admission tests and the two gates to re-run.

### End-to-end script and logging

`scripts/e2e/open_spark_5.sh`: runs `cargo xtask check-deps` on the real workspace and on the two planted fixtures,
`frob spark devices --json` from a binary built without the Metal annex, and prints the decision row. Logs per the
end-to-end standard: command lines, exit codes, the rule identifiers matched, the device state and reason, the
registry row, and a `summary` line. No device is required.

### Known answers and negative controls

Negative controls: the planted direct binding; the planted local patch; a registry row authorizing a binding with
no sunset. The measurements in the packet come from the fingerprint and the throughput gate and inherit their
controls.

## Considerations

- The default trades Mac GPU throughput for a single Metal code path owned where it lives; the cost is bounded by
  the kill gate's fallback, under which the Mac still serves the world bank, proof, replay and CPU training.
- A binding of our own would also need the canaries, the IEEE probe and the commit fence re-established on it;
  none of those transfer automatically from the gateway.
- This decision does not block M2: both branches of the Metal kill gate have a defined outcome under the default.
