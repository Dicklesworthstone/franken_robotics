## Background

Dialect rule 7: "Integer arithmetic in exact kernels is unsigned and 32 bits wide; shift counts are masked. Signed
overflow is undefined in both source languages and is therefore unreachable by construction. Sixty-four-bit
integers and atomics are used only where the fingerprint records them for every device family in use. A count that
can pass 2³² follows the two-limb rule." The wide-count section draws the consequence: FACT to recheck (a reported
compile probe on the M5 Ultra, re-run by the fingerprint): the Metal shading language offers no 64-bit integer
atomic add and no 64-bit compare-and-swap; "by rule 7 a kernel may use 64-bit atomics only if every device family
in use records them, so no kernel of a mixed run uses them". The gate of that section requires that "the dialect
lint finds no 64-bit atomic in any kernel source".

The refusal is `FROB-REF-616`: "the device lacks an arithmetic feature the kernel declares (for example 64-bit
integers)"; first repair: the 32-bit variant, or another backend. Under a strict backend request a missing
arithmetic class is an error raised by the planner, like a missing kernel (`FROB-REF-604`) or a stale check
(`FROB-REF-605`): no world is stepped and nothing is scored.

Why a build-time lint and a plan-time check both: the lint keeps a feature out of sources where it can never be
admissible (64-bit atomics); the plan-time check handles features that are admissible on some machines and not
others (64-bit integers; a double-precision kernel, since the kernel IR's `f64` is for CPU targets only and Metal
has no double type), using the measured fingerprint and never a table.

## Scope

In: the feature vocabulary (`arith_features`); derivation of a kernel's declared features from its source or IR
and the manifest check; the library-level configuration of dialect rule 7 (an empty feature set for 64-bit atomics
over the whole kernel library and its preludes, so that none is admitted); the rule that a kernel family using
64-bit integers registers a 32-bit variant; the plan-time intersection over the device families in use; variant
selection; the refusal `FROB-REF-616`; receipt fields.

Out: the lint engine and rule 7 itself, with its diagnostics and planted-defect corpus (N21a-10, a dependency:
this bead calls that rule and adds no second lint); the probes that measure features (N21c-02); the two-limb
operator (N21a-07, N21c-41) and the drain (N21c-40), which make the 32-bit variants possible; the planner's
raising site for strict requests (N21b-29, under BD-178); the double-float canary refusal (`FROB-REF-609`, a
start-up check, N21b-36).

## Technical approach

1. **Vocabulary (DESIGN).** `arith_features` of a kernel manifest is a set over: `u64-int` (uses 64-bit integer
   types), `u64-atomic` (uses a 64-bit atomic operation), `f64` (uses double precision), `f32dd` (uses the
   double-float pair type, which needs passing canaries). The set is **derived**, not typed by hand: from the IR
   for generated bodies (operation counts by type are IR metadata) and by a scan of the dialect text for skeletons;
   the manifest check fails if a declared set differs from the derived one.
2. **Lint (build time).**
   - A 64-bit atomic operation in any kernel source of the library is an error, on every backend's text, including
     through a prelude macro. Diagnostic: file, line, the construct; code `FROB-REF-251` (a banned operation in
     kernel source).
   - A 64-bit integer type is allowed only in a kernel whose family registers a 32-bit variant computing the same
     values (for sums, the two-limb form); a 64-bit-only kernel family is an error.
   - A floating-point atomic stays banned by the existing rule; an integer atomic other than maximum, minimum, or
     and wrapping add stays banned.
3. **Device families in use.** For a run: the families of every device in the placement plan, plus the CPU
   reference; for a fleet job or a comparison across machines: the families of every machine that will run an arm.
   `features_common` is the intersection of their fingerprints' `arithmetic` blocks; a feature recorded
   `unavailable` counts as absent (fail closed).
4. **Variant selection (plan time, before anything runs).** For each kernel family in the step plan, choose the
   variant whose `arith_features` is a subset of `features_common`; among admissible variants prefer the one the
   manifest marks preferred for that backend. All device families of one run use the same variant of a family, so
   that results and digests are comparable. The chosen variant is written in the plan and the placement receipt.
5. **Refusal.** If a kernel family has no admissible variant on a device the plan needs:
   `FROB-REF-616`, exit 6, raised by the planner before any world is stepped; `pointer`: the kernel and the
   feature; `observed`: the device's recorded value (`no`, or `unavailable` with its reason); `required`: `yes`;
   `retry: after-change`; ranked repairs: 1. the 32-bit variant (named, if one exists but was excluded by a pinned
   request); 2. another backend that records the feature; 3. `frob spark fingerprint` if the feature is
   `unavailable` because the probe has not run. It carries the fingerprint digest.
6. **Staleness.** The decision depends on the fingerprint identity; an identity change (for example an operating
   system update that changes atomic support) re-runs the selection at the next plan.

Determinism: exact; the selection is a pure function of manifests and fingerprints.

## Acceptance criteria

- [ ] The dialect lint reports zero 64-bit atomics over every kernel source of the library and its preludes, and rejects a planted one (directly and through a macro).
- [ ] A kernel family that uses 64-bit integers has a registered 32-bit variant; the two variants return identical bytes on 10⁶ random inputs.
- [ ] In a run whose families are CUDA (64-bit integers recorded) and Metal (not recorded, or `unavailable`), the planner selects the 32-bit variant on both and says so in the plan.
- [ ] A planted 64-bit-only kernel in such a run is refused with `FROB-REF-616` and zero worlds stepped; an `f64` kernel placed on Metal is refused the same way.
- [ ] Declared and derived feature sets agree for every kernel; a hand-edited manifest that drops `u64-int` fails the manifest check.
- [ ] The refusal lists its three repairs in order and the receipt of an admitted run records the chosen variants.

## Test plan

### Unit tests

`cargo test -p frob-kir dialect_lint_u64` (the lint is a library module of `frob-kir`, N21a-10), `-p frob-kernels
arith_gating`:
- `lint_rejects_u64_atomic_direct`, `lint_rejects_u64_atomic_via_macro`, `lint_accepts_u32_atomic_add_max_min_or`.
- `lint_requires_32bit_variant_for_u64_int_kernel`.
- `derived_features_match_declared` (property over the library's manifests).
- `features_common_intersection`: {cuda: yes, metal: no} → no; {cuda: yes, metal: unavailable} → absent.
- `variant_selection_mixed_run_picks_32bit`; `variant_selection_single_family_may_pick_64bit`.
- `refusal_616_before_any_world`: the stepped-world counter is zero; `pointer` names the kernel and `u64-int`.
- `f64_kernel_on_metal_is_616`.
- `selection_is_pure`: same manifests and fingerprints, same plan bytes.

### End-to-end script and logging

Steps of `scripts/e2e/spark_wide_counts.sh` (bead N21c-43): the lint over the kernel library (`cargo xtask
check-generated`, which calls the dialect lint of `frob-kir`) expecting zero 64-bit atomics; `frob spark place @fixture:u64-only-kernel
--tier strict:gpu-metal --json` expecting `FROB-REF-616`; `frob spark place @fixture:hist-run --tier
mixed-allowed:gpu-cuda --json` showing the chosen variants. Logged with command lines, exit codes, the lint's
counts, the feature intersection, the chosen variants, the refusal's fields and repairs.

### Known answers and negative controls

Known answer: zero 64-bit atomics in kernel sources (a clause of GATE-SPARK-23). Negative controls: the planted
64-bit atomic; a planner that consults only the device it is about to run on and not every family in use (a mixed
run then picks the 64-bit variant on CUDA; the mixed-run test must fail); a fingerprint with the feature
`unavailable` treated as present. Lanes: host for the lint; both backends for the variant identity.

## Considerations

- If a later Metal release adds 64-bit atomics, the fingerprint will record it; the lint rule stays until the
  owner of the dialect decides to relax it, because a rule that depends on the newest operating system would make
  kernel sources unportable across the fleet.
- Variant selection must not become a silent fallback: it is decided at plan time, printed before the run, and the
  same on every family of the run.
- `f32dd` is listed for completeness; its device check is the start-up canary, not the fingerprint alone.
