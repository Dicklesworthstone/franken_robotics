## Background

GATE-SPARK-23 (claim: Known answer; milestone M2) closes the design for device-side counting without 64-bit
atomics: "On CUDA and on Metal a histogram run of 10¹⁰ increments, concentrated in one bin, matches a CPU `u64`
reference in every bin; the boundary plan is refused and its neighbour admitted; the dialect lint finds no 64-bit
atomic in any kernel source; the two-limb reduce matches `u64` addition on 10⁶ random pairs."

The design it tests: exact kernels are 32 bits wide; histogram bins are `u32` cells incremented by an
order-independent integer atomic add; at each chunk commit the host drains the committed bins into `u64` totals in
the ledger and the next chunk starts from zeroed bins; a step plan is admitted only if no bin can receive more
than 2³² − 1 increments within one chunk (otherwise the chunk is shortened or the plan refused); sums wider than
32 bits are reduced as two-limb values with an unsigned-comparison carry. 10¹⁰ is more than twice 2³² =
4,294,967,296, so a correct run must cross at least two chunk boundaries with drains, and a run that kept its
count on the device would visibly wrap.

The section's three known answers: two-limb add (0xFFFFFFFF, 0) + (1, 0) = (0, 1); the boundary of the bound
(65,536 worlds × 4,096 intervals × 16 samples is exactly 2³² and is refused; one fewer is admitted); the planted
overflow (a mutant plan that lets one bin receive 2³² + 5 increments in a chunk reads 5 on the device).

This bead is the end-to-end script that measures the four clauses from the user's side and produces the receipt
from which the gate is recorded.

## Scope

In: the script, the increment fixture, the four clauses, the three known answers, the negative controls, the gate's
tier run and receipt (the recording happens outside the script). Out: the mechanisms (N21c-39 to N21c-42) and the registered mutant (N21c-31).

## Technical approach

**Script.** `scripts/e2e/spark_wide_counts.sh --backend batch-cpu|gpu-cuda|gpu-metal [--seed S]`; sources the shared
end-to-end helper; idempotent (scratch state root); seed-explicit (default 2126; the histogram fixture itself is
constant-valued, the reduce pairs are drawn from an address-keyed stream with the seed). Below, `<tier>` is
`batch-cpu` when `--backend batch-cpu` and `strict:<backend>` otherwise (a planner mode prefixes only a device
backend).

**Fixture `@fixture:hist-one-bin` (`synthetic`).** An increment-only design run under the task
`@fixture:hist-probe` (the fixtures of N21c-39's lane): one histogram channel fed a constant sample, so every sample
of every world lands in one bin, and a 20 ms control period. 100,000 worlds (a multiple of the execution width of
32) × 32 samples per control interval × 3,125 control intervals (62.5 simulated seconds) = 10¹⁰ increments
exactly. The no-wrap bound gives
n_max = ⌊4,294,967,295 ÷ 3,200,000⌋ = 1,342 intervals per chunk, so the run has at least three chunks (1,342 +
1,342 + 441) and three drains.

**Steps.**
1. `frob doctor --json`, `frob spark devices --json`: build identity; fingerprint current; record whether each
   family reports 64-bit atomics (context for clause 3, not a condition).
2. **Clause 3, lint.** `cargo xtask check-generated` with the dialect pass over every kernel source and prelude:
   assert zero 64-bit atomic constructs; then `cargo test -p frob-kir --release dialect_lint_u64` on the planted
   source (`tests/fixtures/lint/u64_atomic.kernel`): assert it is rejected with `FROB-REF-251`.
3. **Clause 2, boundary.** (This step runs the conformance build, the only build with the arrangement knob
   `--chunk-intervals`; the log names the build.) `frob spark place --tier <tier> --design
   @fixture:hist-boundary --task @fixture:hist-probe --worlds 65536 --chunk-intervals 4096 --json` (16 samples:
   exactly 2³²): assert exit 6, the code of N21-REF's `device-count-wrap` row (proposed 619; the script reads the
   assigned number from `registries/refusals.toml`), `observed` 4,294,967,296, `required` at most 4,294,967,295;
   then `frob sim run @fixture:hist-boundary --task @fixture:hist-probe --worlds 65536 --seconds 82 --tier <tier>
   --chunk-intervals 4096 --key wc-bound-<backend>-<run-id> --json`: the same refusal at
   admission, `world_steps_executed` 0. `frob spark place --tier <tier> --design @fixture:hist-neighbour
   --task @fixture:hist-probe --worlds 65535 --chunk-intervals 65537 --json` (65,535 × 65,537 × 1 = 2³² − 1):
   assert admission. The boundary fixture without `--chunk-intervals`: assert admission with the chunk shortened
   to 4,095.
4. **Clause 4, two-limb reduce.** `spark.probe` takes only a device and runs the IEEE probe, so this clause runs
   through the annex integration tests N21c-41 adds (`tests/wide_counts.rs`), which drive the registered kernel `K-seg-reduce` with operator `add2` on the
   named device over 10⁶ pairs from the address-keyed stream with the script's seed (pair 0 is the known answer):
   `FROB_TEST_DEVICE=<id> cargo test -p frob-spark-cuda --release --test wide_counts add2_pairs` on `trj` (each card)
   and `cargo test -p frob-spark-metal --release --test wide_counts add2_pairs` on the Mac, each writing its output
   bytes and digest as a receipt, beside `cargo test -p frob-kernels --release add2_matches_u64_random` on
   `batch-cpu`. Assert the output bytes equal the `u64` oracle's and the `batch-cpu` run's and that pair 0 reads
   (0, 1). Then, from the user's side, `frob spark check --kernel K-seg-reduce --backend <backend> --seed <s> --key
   wc-check-<backend>-<run-id> --json`: assert the check is current and attains bit equality (class D0) for the
   kernel.
5. **Clause 1, the run.** `frob sim run @fixture:hist-one-bin --task @fixture:hist-probe --worlds 100000
   --seconds 62.5 --tier batch-cpu --key wc-ref-<run-id> --json` (the reference, accumulated in `u64`), then the
   same with `--tier <tier>` and `--key wc-dev-<backend>-<run-id>` (distinct keys: a reused key would
   return the reference's stored receipt). `frob telemetry histogram <run> --channel probe --json` for both. Assert: the hot bin's total is 10,000,000,000 and every other bin is 0, bin for bin equal to
   the reference; chunks ≥ 3 and drains = chunks; the conservation check held at every drain; the placement
   receipt shows the chunk length in force.
6. **Planted overflow.** Run control `spark.plan-overflow` through the negative-control runner
   (`FROB_TEST_SEED=<s> cargo test -p frob-conformance --test negctl -- spark.plan-overflow`, and through the
   annex test binaries on each device): a mutant plan that
   skips the admission check and delivers 2³² + 5 increments in one chunk must read 5 on the device while the
   reference reads 4,294,967,301; the control passes only if the difference is detected.
7. **Gate run.** `e2e_tier g1_known_answers GATE-SPARK-23` (the gate's claim is Known answer; the helper runs
   `FROB_TEST_SEED=<s> cargo test -p frob-conformance --test g1_known_answers -- GATE-SPARK-23`) reads the
   script's receipts for the CPU reference and each device family and writes the hash-named receipt, which the
   `cmd` line carries as `receipt`. The script stops there: it never runs `record_gate` (STD-E2E's
   self-recording lint; convention 9). The measured values enter the gate row afterwards, outside the script,
   through `cargo run -p frob-conformance --example record_gate -- --gate GATE-SPARK-23 --receipt <hash>`, run by
   a session that did not implement the work.

**Logging.** Newline-delimited JSON at `target/e2e-logs/spark_wide_counts/<utc-timestamp>.ndjson` with a
transcript beside it. Every line: `ts`, `script`, `bead` ("N21c-43"), `step`, `event`, the seed as a decimal
string; on `cmd` lines the exact command line, exit code and wall time, the envelope's `evidence` block (claim
Known answer, class `Tested`, tier, determinism `exact`, identities, seed) and, for step 7, the `receipt`;
measured values with units and thresholds (increments delivered and read, as strings; chunks; drains; lint count
against 0; pairs compared against 10⁶; the bound against 4,294,967,295), output digests where bytes are compared,
the planted overflow as an `assert` of kind `negative-control` with `nc` and `caught`, and on failure the first
differing bin, epoch or pair with both values and the run and plan identities needed to reproduce. Final
`summary`: assertions passed and failed, `controls_caught`, `controls_missed`, `gates[{id: "GATE-SPARK-23",
measured_ok, controls_caught}]`, `gates_claimable`, the receipts, the backend.

## Acceptance criteria

- [ ] The script exits 0 on `batch-cpu`, on CUDA (at least one RTX 4090; both where available) and on Metal.
- [ ] Clause 1: 10,000,000,000 in the hot bin and 0 elsewhere on each device family, equal to the CPU `u64` reference in every bin, with at least three drains.
- [ ] Clause 2: the 2³² plan refused before any world is stepped; its neighbour admitted.
- [ ] Clause 3: zero 64-bit atomics found in kernel sources; the planted one rejected.
- [ ] Clause 4: 10⁶ random pairs identical to `u64` addition and across backends.
- [ ] The planted overflow reads 5 on the device and is detected; the carry-dropped reduce and the double-drain mutants are caught.
- [ ] The script's tier run writes GATE-SPARK-23's receipt with measured values, commit, fingerprint digests and seed, and the script itself records nothing; recorded from that receipt by a session that did not implement the work, the gate row carries those values; without the Metal run the gate is `not-run` for Metal with the reason, not passed.
- [ ] `run-all.sh --verify-plants` reports each declared plant (`carry-dropped`, `double-drain`, `skip-zeroing`) making the script fail.

## Test plan

### Unit tests

Script helpers (`frob-conformance::wide_counts`): `fixture_arithmetic` (100,000 × 32 × 3,125 = 10¹⁰; n_max =
1,342; chunks 1,342 + 1,342 + 441); `bins_equal_reference` reports the first differing bin; `strings_for_big_ints`
(10,000,000,000 is compared as a string, since it exceeds 2³² but not 2⁵³, and the comparison must not pass
through a float).

### End-to-end script and logging

This bead is the script, as specified. Run time TARGET: under 10 minutes per backend; it fits the default compute
envelope (one device, well under an hour).

### Known answers and negative controls

Known answers: the three of the section, with the values above. Negative controls: (1) the planted overflow plan;
(2) a reduce whose carry is dropped ((0xFFFFFFFF, 0) + (1, 0) then gives (0, 0)); (3) a drain performed twice for
one epoch (the hot bin would read above 10¹⁰); (4) zeroing skipped at a chunk start (the second drain would then
re-add the first chunk's counts); (5) the planted 64-bit atomic for the lint. (1) and (5) are run in every pass
(steps 6 and 2); (2), (3) and (4) are the script's declared plants (header `plants=carry-dropped,double-drain,
skip-zeroing`, each injected under `e2e_plant <name>`), and `run-all.sh --verify-plants` requires each to make the
script exit 1 with a failed assertion. Metamorphic: chunk lengths 1, 16 and 1,342 give identical totals; one and two shards give
identical totals. Determinism lanes: twice on one machine; debug and release; across backends byte-identical
totals (class D0).

## Considerations

- 10¹⁰ contended atomic increments on one cell is a worst case for throughput and is not a performance figure; no
  timing from this script is evidence.
- Metal's answer on 64-bit atomics does not change the gate: the design must pass whether or not a backend has
  them.
- If slot dispatch later lets several jobs share the bucket, the bound already uses world capacity, so this gate's
  result carries over.
