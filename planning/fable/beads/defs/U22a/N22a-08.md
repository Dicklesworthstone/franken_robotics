## Background
The force-distribution and predictive programs of the baseline controllers are small dense conic programs: tens to a few hundred variables, with friction cones, actuator boxes and equality rows from the equations of motion. The plan's decision (ADR-REFLEX-02): control programs, force distribution, skill allocation and shield projection all use the one symmetric-cone solver that `frob-algebra` provides to the contact solve, with a fixed iteration count and a mandatory optimality check. Reason: one kernel family serves physics and control, and one dual-certificate format serves every infeasibility report. The programs are compiled as kernels so the baseline controller runs batched on any tier.

The solver runs a fixed number of iterations in lockstep across worlds and ends in one of three states per world, which the caller must inspect:

| State | Meaning | What is returned |
|---|---|---|
| `optimal` | Primal feasibility, dual feasibility, complementarity and stationarity all within tolerance | The solution and the four residuals |
| `infeasible` | A dual certificate was found | A vector y with Aᵀy in the dual cone K* and bᵀy < 0 |
| `unconverged` | Neither of the above within the iteration budget | The last iterate, marked unusable; the caller takes its fallback |

Why three and not two. For a program "find x in K with A·x = b", a vector y with Aᵀy ∈ K* and bᵀy < 0 proves that no solution exists, because 0 ≤ ⟨Aᵀy, x⟩ = yᵀb < 0 would follow. An unconverged run has no such vector and proves nothing. Reporting "no solution" when the solver merely failed to converge is the tempting shortcut this bead forbids: it turns a numerical accident into a statement about the robot's body.

The certificate is rounded to rationals and re-checked exactly (proof obligation PO-REFLEX-03: every infeasibility certificate checks in exact rational arithmetic, Aᵀy ∈ K* and bᵀy < 0), which is what makes an infeasibility report class `Certified` for the stated program.

This bead is the control-side layer over the solver of BD-115: how a control program is stated, how its outcome must be consumed, what the fallback is, and how a certificate is read as physics. Tier: Solid. Crate: `frob-control` (module `program`).

## Scope
In: the `ControlProgram` builder and its standard forms; the must-inspect outcome type; the fallback contract; the certificate record, its exact re-check call and its physical reading (which actuator or contact binds); the friction-certificate fixture; lockstep semantics per world.
Out: the solver, its iteration, its residual definitions and its certificate search (BD-115); the cone trait (BD-050); specific programs (stance force distribution N22a-09, whole-body inverse dynamics N22a-14, predictive N22a-21); layer records and fallback telemetry (N22a-15); certificate bundles for the offline auditor and the gate (BD-251); cone kernels on batched tiers (BD-153, used by N22a-13).

## Technical approach
**Standard forms.**
- Feasibility form (the plan's): find x ∈ K with A·x = b, K a product of orthants and second-order cones. Certificate of infeasibility: y with Aᵀ·y ∈ K* and bᵀ·y < 0.
- Program form: minimize ½·xᵀ·Q·x + cᵀ·x subject to A·x = b and h − G·x ∈ K. Certificate of infeasibility: (y, z) with z ∈ K*, Aᵀ·y + Gᵀ·z = 0 and bᵀ·y + hᵀ·z < 0. The four optimality residuals are stationarity ‖Q·x + c + Aᵀ·y + Gᵀ·z‖, primal feasibility, dual feasibility (z ∈ K*) and complementarity ⟨h − G·x, z⟩, each scaled by its data norm.
- Cones: the nonnegative orthant and the second-order cone are self-dual. The friction cone {‖fₜ‖ ≤ μ·fₙ} has dual {(a, c) : a ≥ μ·‖c‖}. The four-dimensional contact cone (normal, two tangential, spin) is a second-order cone after scaling the tangential and spin components by the friction coefficient and the effective patch radius: (μ·λₙ, λ_t1, λ_t2, λ_s/r).

**Builder (DESIGN).** `ControlProgram::new(name)` with typed blocks: `var(name, n)`, `eq(row_name, A, b)`, `box_(var, lo, hi)` (orthant rows), `friction(contact, mu, normal, tangential)` (cone block), `task(priority, weight, J, target)` (least-squares cost row), `iterations(n)`, `tolerances(…)`, `fallback(Fallback)`. Every row keeps its name: certificates are reported against names (a contact identity, an actuator identity), not indices. The program's structure hash, iteration count, tolerances and fallback go into the `ControllerId`.

**Outcome type.**
```rust
#[must_use]
pub enum SolveOutcome<'a> {
    Optimal { x: Solution<'a>, residuals: Residuals },
    Infeasible { certificate: Certificate },      // already exactly checked, or it is not this variant
    Unconverged { last: Unusable<'a>, residuals: Residuals },
}
```
There is no accessor that returns a solution without a `match`. `Unusable` has no conversion to a command. A caller that needs a command from an `Unconverged` or `Infeasible` world takes its fallback, by construction.

**Fallback contract.** Each program declares one: `LastFeasible` (re-issue the last command that came from an `Optimal` solve, valid for a declared number of ticks) or `Backup` (hand over to the class's backup controller). An infeasible program returns its active inequalities, its residuals, the dual certificate and the prescribed fallback; the controller records every fallback as an event with its reason (`fallback:infeasible:<program>`, `fallback:unconverged:<program>`). A controller with neither a valid last command nor a backup is refused at synthesis (FROB-REF-424: a control program is infeasible and the controller has no admissible fallback; repairs in order: read the dual certificate, relax the task, change the binding actuator or contact; exit code 3).

**Certificates.**
1. The solver returns a floating candidate (y, z).
2. Rounding: each component is replaced by a nearby rational with a bounded denominator (continued fractions, denominator at most 2²⁰), then the cone part is pulled into the dual cone if rounding pushed it out (the normal component is increased by the smallest amount that restores membership).
3. Exact check, on A, G, b, h taken as the exact rationals of their stored floating values: membership in K* by exact comparison (for a second-order block, a ≥ 0 and a² ≥ μ²·c·c, no square root), the equality Aᵀ·y + Gᵀ·z = 0 exactly (or the feasibility-form condition), and strict negativity of the separation value.
4. If the exact check fails, the world's outcome is `Unconverged`, never `Infeasible`.
5. The `Certificate` record: program name and structure hash, the rational vector, the separation value with units, and the *binding set*: the named rows and cones on which the certificate has support. Reading: the certificate is a linear combination of constraints that every admissible point satisfies and the task violates; the rows with nonzero weight are the binding actuator or contact that a report names.

**Smallest case, by hand (the fixture).** A body of weight 50 N must be pushed along level ground with a horizontal force of 30 N through one contact with μ = 0.5. Unknown x = (fₙ, fₜ) with |fₜ| ≤ μ·fₙ, and the task fixes x = (50, 30), so A = I and b = (50, 30). Take y = (0.5, −1). Then y lies in the dual cone {(a, c) : a ≥ μ·|c|} (0.5 ≥ 0.5·1), and yᵀb = 25 − 30 = −5 < 0. Read as physics: every admissible contact force has 0.5·fₙ − fₜ ≥ 0, and the task needs −5 N. The set of valid certificates is the cone {a ≥ 0.5·|c|, 50·a + 30·c < 0}; the test accepts any member and checks this one exactly.

**Lockstep semantics.** In a batch every world runs the same fixed number of iterations under a mask; a world that reaches `optimal` early is copied forward. A world's outcome and solution are functions of that world's data only, bit for bit, whatever the other worlds in the batch do.

**Determinism and evidence.** `f64` on the referee path, `f32` or `f64` in kernels: class D2. An `Optimal` solution is `Tested` (residuals within tolerance). An `Infeasible` verdict with its exactly checked certificate is `Certified` for the stated program; the statement is about the program as written, with its model, cones and limits as inputs, and inherits their class.

## Acceptance criteria
- [ ] The friction fixture returns `Infeasible`; the solver's certificate passes the exact check; the hand certificate y = (0.5, −1) passes it with separation −5 N; the binding set names the contact's friction cone and the tangential task row.
- [ ] A certificate nudged outside the dual cone, y = (0.5 − 10⁻⁹, −1), fails the exact check (the registered negative control).
- [ ] The feasible variant x = (50, 20) returns `Optimal` with all four residuals inside tolerance; the boundary variant x = (50, 25) is never reported `Infeasible` (no strict certificate exists).
- [ ] With the iteration budget cut to one, a program that needs more returns `Unconverged`, the controller takes its declared fallback, and a fallback event with its reason is emitted; a build that maps `Unconverged` to `Infeasible` fails the test suite.
- [ ] Using a solution without matching on the outcome does not compile; `Unusable` cannot become a command.
- [ ] A controller synthesized with a program that has no admissible fallback is refused with FROB-REF-424 and its three ranked repairs.
- [ ] In a batch of 64 worlds with mixed outcomes, each world's outcome and bytes equal its single-world run.
- [ ] Program structure hash, iteration count, tolerances and fallback appear in the controller record; changing any of them changes the `ControllerId`.

### Known answers and negative controls
- KA-556 (the friction certificate: y = (0.5, −1) in the dual cone, yᵀb = 25 − 30 = −5 N; the program is `infeasible`, class Certified; exact by rational re-check), KA-083 (optimality residuals of every control program inside tolerance).
- Counterexample carried: CX-235 (reporting "no solution" when the cone solver fails to converge).
- Negative controls: the nudged certificate; the `Unconverged`-to-`Infeasible` mutant; a dual cone taken as {a ≥ |c|/μ} instead of {a ≥ μ·|c|} (for μ = 0.5 it rejects the hand certificate, since 0.5 < 2, and leaves no certificate at all for this infeasible program; the fixture fails); a non-strict separation test (accepts a zero separation on the boundary variant).
- Metamorphic: scaling b by t > 0 scales the separation by t and keeps the verdict; scaling y by t > 0 keeps a certificate valid; permuting contacts permutes the binding set.
- Determinism: twice on one machine; debug and release; batch against single world.

## Considerations
- A certificate proves the program as stated is infeasible. If the program's limits came from an `assumed` card, the report's class is the weakest of its inputs; the arithmetic is exact, the premises may not be.
- The fixed iteration count is a determinism requirement (the launch graph has a static shape), so "iterate until converged" is not available; a program that is regularly `Unconverged` is a synthesis finding and shows in the fraction of ticks spent in fallback.
- Rational growth in the exact check is bounded by the program size (a few hundred rows of 53-bit rationals); exceeding the crate's rational budget is the exact-evaluation refusal, and the world is then `Unconverged`.
- Until the conic proof kind exists in the offline checker, only certificates that are linear (planar friction, boxes) can travel in bundles; the in-process exact check still stands for all.
