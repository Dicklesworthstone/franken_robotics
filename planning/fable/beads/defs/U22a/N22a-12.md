## Background
When a design fails to move under a synthesized controller, there are three different things that may have happened, and an agent that cannot tell them apart will draw the wrong conclusion about the body. The plan's rule: `control synth` returns one of three outcomes, never a bare failure: `not-synthesizable` with the reason (for example no gait in the atlas satisfies static stability with these leg counts), `synthesized-failed` with the failure taxonomy of the telemetry chapter, or `ok`. A design that fails under its baseline is not thereby a bad design, and the report says that.

Additions the plan makes to each outcome (DESIGN):
- `not-synthesizable` carries a witness whenever the reason is a program: the dual certificate for a force or torque demand that the body cannot meet, with the binding actuator or contact named.
- `synthesized-failed` carries the fallback log, the first layer that failed, and the next rung of the control ladder with the evidence that rung requires.
- `ok` carries the saturation report, the fraction of ticks spent in each layer, and the standing of the result: a baseline score is `screening` until rank agreement with trained specialists has passed for the design's class and task family (GATE-REFLEX-04).

This bead is the report as a type and a schema: what each outcome must contain, so that no controller class can return less. The verb that serves it is a separate seed bead. Tier: Solid. Crate: `frob-control` (module `report`).

Why a type and not a convention: the program's first failure story for this subsystem is "baseline controllers failed on new morphologies, so every design needed training after all", and its earliest signal is the share of designs reported `not-synthesizable`. That share is only meaningful if the three outcomes are never conflated: a numerical solver failure counted as a body failure inflates it, and a backup controller's success counted as `ok` hides it. Alternatives rejected: a boolean success with a message (unusable by an agent and by the corpus statistics); an error for "cannot synthesize" (it is an answer about the design, with a witness, not a malfunction).

## Scope
In: the `SynthesisReport` type and its three variants with required payloads; the schema `frob.control.synth.out/1`; the validation episode that separates `ok` from `synthesized-failed`; the mapping from telemetry failure classes and outcome kinds to report fields; the wording rule; exit codes; unit tests.
Out: the verb, its registry entry and `control.show` (BD-118); class detection and the class controllers (BD-116, BD-117, and the archetype unit's beads); certificates (N22a-08, N22a-09); layer records at telemetry level (N22a-15); the standing's dependence on rank agreement (N22a-17); the ladder verb (N22a-18).

## Technical approach
**Type (DESIGN).**
```rust
pub enum SynthesisReport {
    NotSynthesizable { class: Option<MorphologyClass>, reason: NoRouteReason, witness: Option<Witness>, routes: Vec<Route> },
    SynthesizedFailed { controller: ControllerId, failure: FailureSummary, fallback_log: FallbackLog,
                        first_failed_layer: Layer, next_rung: RungAdvice, body_note: BodyNote },
    Ok { controller: ControllerId, saturation: SaturationReport, layer_fractions: LayerFractions,
         standing: Standing, evidence_for_next: Vec<EvidenceItem> },
}
```
No variant has optional payloads except where marked; a controller class cannot construct `Ok` without layer fractions or `SynthesizedFailed` without a first failed layer.

**`NotSynthesizable`.**
- `reason`: one of `no-class` (the model matches no morphology class), `no-gait` (no gait in the table satisfies static stability with these leg counts), `static-support` (the body cannot be held at the nominal stance), `demand-exceeds-body` (a force or torque demand of the class's reference behaviour cannot be met), `missing-port-or-sensor` (the class needs a port or sensor the design lacks), `speed-out-of-range` (for example a Froude number above the baseline's limit), `tier-missing-law` (the contact law of the class does not exist on the requested tier yet), `route-not-built` (the class is detected but its baseline route lands at a later milestone; the witness is that milestone, for example the biped-balance class at M1), `not-admitted-on-device` (the class row's controller is not admitted on the requested device tier while an open question's fail-closed default holds; the witness names the question, for example OPEN-REFLEX-1 for the predictive legged controller of N22a-21, with N22c-50's decision record once it exists).
- `witness`: required when the reason is `static-support` or `demand-exceeds-body`: the exactly checked dual certificate with its separation value and its binding set (the named actuator box or contact cone). For the other reasons the witness is the data that decided it (the leg count and the table rows tried; the missing port).
- `routes`: what to try instead, in order: add the ports or sensors the class requires; admit the sampling controller for screening; go to the specialist rung. When no route at all is admitted for the detected class, the verb turns this into refusal FROB-REF-421 (no synthesis route exists for the detected morphology class and no fallback is admitted; exit code 3) with the same three repairs.

**The validation episode.** A controller that synthesizes is run before it is reported: the class's reference behaviours (stand for 10 s; traverse 5 m of flat ground at the class's nominal speed) on the tier the caller names (default: the fastest tier on which the class's contact law exists; the referee at M1), with one seed per behaviour by default and the seeds in the report. The episode is short on purpose: synthesis plus validation is meant to cost seconds on a batched tier.

**`SynthesizedFailed`.**
- `failure`: the terminal failure class from the telemetry taxonomy (`fall`, `stuck`, `collision`, `self-collision`, `slip`, `torque-saturation`, `speed-saturation`, `thermal-limit`, `limit-impact`, `timeout`, `numerical-fault`, and the world and perception classes when their features are on), its outcome kind (`physical`, `numerical`, `budget`, `protocol`), and the first cause with its timestamp (labelled `Estimated`, a description and not an attribution).
- A `numerical` outcome leaves the verdict unknown: the report's `failure.kind` is `numerical`, the design is not counted as failing under its baseline, and the corpus statistics keep it in the denominator as unknown.
- `fallback_log`: every fallback event of the episode with its tick and reason.
- `first_failed_layer`: the first of the controller's layers whose own check failed (state source invalid; body feedback saturated; stance program infeasible or unconverged; swing tracking error above its bound; limiter clipping above the duty rating).
- `next_rung`: the next rung of the control ladder for the class and the evidence that rung requires, read from the class table (for the legged class: whole-body inverse dynamics plus a learned residual for trot; evidence required first: foot slip, friction margin, recovery after a payload shift). An escalation is offered only when the failure has a control cause; a design refusal is not escalated.
- `body_note`: the fixed sentence "A design that fails under its baseline controller is not thereby a bad design", followed by what the evidence does and does not show (for example: the stance program was feasible on every tick, so the body could carry itself; the failure began in swing tracking).

**`Ok`.**
- `saturation`: per joint, the fraction of ticks the limiter clipped and the longest continuous clip against the card's duty rating; per foot, friction utilization statistics.
- `layer_fractions`: the fraction of ticks whose command came from each layer (`baseline`, `baseline+residual`, `shield-filtered`, `fallback:<reason>`, `backup`). If the fallback and backup fractions together exceed 5% of ticks (DESIGN default, in the report's manifest) the outcome is not `Ok`: it is `SynthesizedFailed` with first failed layer set, because "it worked" is not a result if the backup controller did the work.
- `standing`: `screening` by default; the other values and their conditions are N22a-17's.
- `evidence_for_next`: the measurements the next rung asks for, already collected (so that escalation does not need a second run).

**Wording rule.** The words "bad design", "failed design" and "works" do not appear in any generated text of the report other than the fixed `body_note` sentence, which says the opposite ("… is not thereby a bad design") and is a constant of the crate, compared byte for byte; a lint over the message templates enforces the rule on every other template. The report speaks about the controller, the tier and the behaviour tested.

**Exit codes and evidence.** `ok` with no flag: exit 0; `ok` with a saturation or clamp flag (any `stance-saturated` or `footstep-clamped` tick, or limiter clipping in the saturation report), `synthesized-failed` and `not-synthesizable`: exit 2 (completed with findings); FROB-REF-421 and FROB-REF-424: exit 3. Evidence block: class `Tested` (a `not-synthesizable` with a checked certificate is `Certified` for the stated program, capped by its weakest input), the tier of the validation episode, its determinism class, identities, seeds; `reality: no-claim`.

## Acceptance criteria
- [ ] The schema `frob.control.synth.out/1` is registered and every variant validates; constructing a variant without a required payload does not compile.
- [ ] A static-support decision whose stance program is infeasible because an actuator box cannot hold the load (a `synthetic` program built and solved through N22a-08's program layer) yields `NotSynthesizable { reason: static-support }` with the certificate whose exact check passed and a binding set naming the actuator; a no-gait decision for three legs yields `reason: no-gait` with the rows tried.
- [ ] A validation-episode record that ends in a fall (a `synthetic` record written through BD-094's real taxonomy and first-cause ordering) yields `SynthesizedFailed` with class `fall`, kind `physical`, a first cause with timestamp, a fallback log, a first failed layer, the next rung with its required evidence, and the body note.
- [ ] The same outcomes on real synthesis of real designs are asserted after this bead, by BD-118's tests (which depend on this bead and on the class controllers) and by N22a-11's script; this bead's criteria use only its own dependencies.
- [ ] An episode ended by a solver fault yields kind `numerical`; it is not counted as a physical failure and it is not dropped: a corpus tally over (ok, failed-physical, unknown-numerical, not-synthesizable) sums to the number of designs.
- [ ] A run that completes the behaviour with more than 5% of ticks in fallback or backup is reported `SynthesizedFailed`, not `Ok`.
- [ ] `Ok` always carries the saturation report, the layer fractions summing to one, and standing `screening` unless N22a-17's condition holds.
- [ ] The message lint rejects a template containing "bad design"; exit codes follow the table.

## Test plan
### Unit tests
`crates/frob-control/tests/synthesis_report.rs`; no mocks. The class controllers and the synthesis verb come after this bead (BD-116, BD-117, BD-118), so the reports are built from what its dependencies deliver: certificates and end states from real solves of `synthetic` programs through N22a-08's program layer, and validation-episode records written through BD-094's real failure taxonomy, outcome kinds and first-cause ordering, all labelled `synthetic`.
- `variants_validate_against_schema`; `missing_payload_does_not_compile` (compile-fail).
- `static_support_reason_has_certificate`; `no_gait_reason_lists_rows`; `no_route_becomes_refusal_421`.
- `fall_is_physical_with_first_cause`; `numerical_fault_is_unknown_not_failure`; `corpus_tally_sums`.
- `backup_did_the_work_is_not_ok` (an episode record that completes a stand with 6% of its ticks in `fallback:unconverged:stance`, the end state of a stance program starved of iterations in N22a-08's layer, is reported `SynthesizedFailed`; at 4% it is `Ok`).
- `ok_has_saturation_layers_standing`; `layer_fractions_sum_to_one`.
- `next_rung_read_from_class_table` (legged: whole-body inverse dynamics plus residual; evidence list of three items).
- `message_lint_rejects_bad_design` (a template other than the body note containing "bad design" is rejected; the body-note constant passes and is byte-equal to the fixed sentence); `exit_codes_by_outcome`.
### End-to-end script and logging
Served through `frob control synth` (BD-118, after this bead); the legged script of N22a-11 asserts each outcome on a real design and on its planted variants, and the corpus validation of BD-249 tallies them. This bead's runner `scripts/e2e/reflex_synthesis_report.sh` executes the test binary and writes the shared newline-delimited JSON log to `target/e2e-logs/reflex_synthesis_report/<utc>.ndjson` with a transcript: one `assert` line per outcome fixture with the variant, its payload digests and the exit code; the tally; a `summary` line.
### Known answers and negative controls
- No numbered known answer; the outcomes are verdict-valued. The certificate inside `not-synthesizable` has the form of KA-556.
- Counterexample carried: CX-235 (an unconverged solve reported as "no solution"): here, a `numerical` outcome reported as a body failure.
- Negative controls: a controller class that returns `Ok` without layer fractions (compile-fail); a report that maps `numerical` to `fall` (the tally test fails); a report that calls a backup-driven completion `ok` (the 5% rule test fails).
- Determinism: a report is a function of the design, the controller record, the tier and the seeds; twice-run reports are byte-identical in canonical JSON.

## Considerations
- The 5% threshold for fallback and backup ticks is a default of this bead; it is in the report's manifest and may be set by a task. Zero would make every transient solver hiccup a failure; a large value would let the backup pass as the baseline.
- The validation episode is a smoke check, not an evaluation: `ok` means the reference behaviours were completed once on the stated tier, and the standing says how little that licenses.
- Risk: baseline controllers mask design flaws or create false ones. This report is one of the three countermeasures (with the estimator comparator and rank agreement before a rung may eliminate): it keeps "the controller failed" apart from "the body cannot".
- The first-cause ordering is a heuristic; attribution by intervention belongs to the counterfactual-debugging subsystem.
