## Background

Training a policy per candidate body costs minutes to an hour. Reflex exists to give an agent answers about a
new body in seconds, without training. For skills (behaviours stated at the task boundary, such as "push this
cart with this wrench profile") the answer is the **exact layer**: for a body and a contact mode, the
equations of motion with the mode's contact constraints give an affine map from actuator effort to the
task-space quantity, w = w₀(q, v) + B_m(q)·u; an allocation cone program over actuator boxes, contact cones
and support limits then returns either a feasible allocation that replays or a checked infeasibility witness
(direction, support value, gap, binding actuator or contact). The witness arrives before any training and
tells the agent what to change: regear, reshape, or change the wrench profile.

This bead is the user-visible capability: three verbs on the `frob` surface, assembled from the format
(N22b-01), the map (N22b-02), the program and witnesses (N22b-03) and the refinement check with the artifact's
limits (N22b-04), and measured at the gate GATE-REFLEX-08. It serves the goal that every new design can be
judged at once (GOAL-13) and the idea "skill transport through a task-space interface" in its Solid form. The
learned residual that moves a skill between bodies is a separate Moonshot item (N22b-07) and is not needed
here; `mission.transport` (Augur) is a different verb that moves a certified claim through an interface map.

Tier: Solid [S]. Crate: `frob-control` (layer 4). Evidence: per-state infeasibility witnesses are Proof claims
of class `Certified` about the declared model; a verdict over sampled states is `Tested`; the weakest input
(for example an `assumed` friction coefficient) sets the class of anything said about the robot.

## Scope

In: the three verbs with schemas, envelopes, refusals, memoization and cancellation; the fixture set of the
gate; the gate measurement and its record. Out: `skill.transport` (N22b-07); static attainability analysis
A-24, which calls the same program without a skill (BD-348); the end-to-end script (N22b-05).

## Technical approach

**`skill.compile`** (kind `run`, first milestone M4). Input schema `frob.skill.compile.in/1`: a skill (path or
`SkillId`), a design (`DesignId`), optional mode list, optional state-sampling specification. Steps:

1. Resolve names to immutable identities and echo them in `bound`.
2. Resolve `task_frame` and the observables against the design and the task; an unresolved name is a refusal
   with a pointer. DESIGN default for its code, and for a `.fskill` that fails the format's validation
   (N22b-01): the surface's schema refusal FROB-REF-802, exit 3, with a JSON pointer to the field and the
   admissible names listed. No skill-specific code is invented; if the refusal registry later assigns one, the
   row of `skill.compile` gains it in the same change.
3. For each phase, enumerate the contact modes it can be in (declared by the phase, or derived from the
   design's contact roles and the phase's reference) and classify scope (N22b-04).
4. For each in-scope (phase, mode) build the map object (N22b-02) and the allocation program (N22b-03) with
   its fixed iteration count. The pair is a `CompiledSkill` entry with a `ProgramId` (content hash of the
   program structure, tolerances and iteration count).
5. Output schema `frob.skill.compile.out/1`: `CompiledSkillId`, per phase and mode the map digest, program
   identity, condition notes and scope findings. The result is content-addressed and memoized on
   (`SkillId`, `ModelId`).

**`skill.check`** (kind `run`, M4). Input `frob.skill.check.in/1`: a compiled skill (a `CompiledSkillId`, or a
skill with `--design <design>`, in which case the verb compiles first or reuses the memoized compilation: the
form of the registry's example, `frob skill check carry.fskill --design quad-tray --key skc-1 --json`) and a
set of states, given
as (a) the samples of each phase's reference at the skill's clock rate (the default), (b) a recorded run
(`--run <run | file.frun>`, the registry's `run` artifact input), or (c) a grid over the assumption box
(`--grid <N>`, N states over friction from `mu_min` upward, payload range, slope up to `slope_max`), the
spellings of the VERBS-skill row; `--run` with `--grid` is FROB-REF-802; `--refinement` adds the refinement check. Per state and mode the outcome is `feasible` with a witness,
`infeasible` with a witness, or `unknown`. Output `frob.skill.check.out/1`: counts of the three outcomes, the
first infeasible state with its failure report (contact mode, requested wrench, support function in the
failing direction, re-runnable counterexample), the refinement verdict, `sufficiency: "necessary-only"`, and
certificate bundle references. Any infeasible state makes the verb refuse with FROB-REF-448; a failed
refinement refuses with FROB-REF-444. `--replay` re-applies each feasible witness on the referee for one step
from its state and compares the realized task quantity with the commanded one.

**`skill.show`** (kind `read`, M4). Input: a skill or compiled skill. Output `frob.skill.show.out/1`: the
artifact, its phases and assumptions, the five limit texts, the evidence block and the flags; for a compiled
skill also the modes and program identities.

**Common surface rules.** Cluster `skill`. With `--json` each verb writes exactly one envelope
(`frob.envelope/1`) with `evidence` computed as a claim product, `bound`, `cost`, `budget`, `next_actions`
(for a refusal: the ranked repairs as commands where a typed edit exists). The run verbs take an idempotency
key and a budget, accept the bounded synchronous wait and otherwise return a job handle with exit code 8.
Exit codes: 0 completed; 2 completed with findings (for example `out-of-scope` phases or `unknown` states); 3
refusal. Cancellation: request, drain at a state-batch boundary, finalize; nothing partial is published as a
verdict.

**Refusals.**

| Code | Meaning | Trigger | Ranked repairs |
|---|---|---|---|
| FROB-REF-448 | A skill's task wrench lies outside the body's attainable set | An accepted infeasibility witness at a sampled state | The witness names the binding actuator or contact: regear, reshape, or change the wrench profile |
| FROB-REF-444 | A transported skill does not refine its specification | A refinement counterexample | The counterexample names the uncovered successor: add a guard or narrow the entry set |

**The gate fixtures (DESIGN where the plan names only a count).** GATE-REFLEX-08 asks for "both hand
fixtures", "4 of 4 infeasible bodies" and "the {stable, fall} refinement". The two hand fixtures are read as
the two-link arm witness (binding actuator) and the friction-push certificate (binding contact). The four
infeasible bodies are fixed here and registered in `frob-conformance`:

| Body | Request | Expected refusal content |
|---|---|---|
| `arm-2r-weak`: planar arm, links 0.4 m and 0.3 m at angles 0 and π/2, limits 2.5 N·m | Tool force (10, 0) N | c = (1, 0), support 25/3 N, gap 5/3 N, binding joint 2 |
| `pusher-50N`: weight 50 N, one ground contact, μ_min = 0.5 | 30 N horizontal | y = (0.5, −1), yᵀb = −5 N, binding contact cone |
| `cart-tip`: a planar wheeled base that pushes at its own handle: weight 196.2 N (20 kg), wheelbase 0.4 m, centre of mass midway between the axles, wheel radius 0.1 m, front and rear wheel both driven and each limited to 10 N·m, handle 0.8 m above the ground, μ_min = 0.4 | 60 N horizontal at the handle | Support 49.05 N, binding front support (unilateral): the reaction at the handle unloads the front wheel by 2 N per newton of push, 98.1 − 2·F, which reaches zero at 196.2·0.2/0.8 = 49.05 N, before traction (0.4·196.2 = 78.5 N) or torque (4.9 N·m needed) binds |
| `wheel-speed`: wheel radius 0.1 m, stall torque 10 N·m, no-load speed 20 rad/s, at 12 rad/s | 60 N | Support 40 N, binding actuator (speed-dependent box) |

Feasible counterparts (witnesses must replay): the arm with 3.5 N·m limits (u = (−3, −3) N·m); the pusher at
20 N; the cart at 40 N; the wheel at 4 rad/s.

**Gate record.** GATE-REFLEX-08 is measured by its tier run, `FROB_TEST_SEED=<seed> cargo test -p
frob-conformance --test g1_known_answers --features gauntlet-mutations -- GATE-REFLEX-08`, which drives the
fixture table above and the refinement pair, catches the registered controls in the same run (the space-frame
Jacobian mutant, the fixed-base pullback on the floating-base cart, the nudged certificate, the "select the
stable branch" checker) and writes a hash-named receipt. A session that did not implement the skill layer
enters it through the gate recorder (N38b-19): `cargo run -p frob-conformance --example record_gate -- --gate
GATE-REFLEX-08 --receipt <hash>`. The row carries the commit, the hardware fingerprint, the seed, the four
refusals with their numbers, the auditor's verdict per certificate, the replay errors and the controls caught.

## Acceptance criteria

- [ ] `frob skill compile`, `frob skill check`, `frob skill show` exist, are generated from the verb registry,
      validate against their schemas, and are reachable through `frob --json` and `frob-mcp`.
- [ ] GATE-REFLEX-08 (TARGET, known-answer claim, M4) is recorded with measured values: both hand fixtures
      reproduce (25/3 N from joint 2; y = (0.5, −1) with −5 N); 4 of 4 infeasible bodies are refused with
      certificates that the offline auditor accepts in exact arithmetic; every feasible witness replays on the
      referee within the recorded tolerance; the {stable, fall} refinement is refused with FROB-REF-444.
- [ ] Negative controls caught: the space-frame Jacobian mutant gives a different bound on the arm; a nudged
      certificate is rejected; the "select the stable branch" mutant is detected.
- [ ] Every output carries the claim product, the model identity, the determinism class and the three
      no-authorization flags; an exported `.fskill` carries the flags in its header.
- [ ] `CONTRACT.md` of `frob-control` covers the skill surface (purpose, inputs, outputs, invariants,
      refusals, determinism class, evidence class, validity domain, oracles, known gaps).
- [ ] A CPU reference path exists for every computation; cancellation is tested on `skill.check`.
- [ ] Seed done-condition: GATE-REFLEX-08 has a recorded `pass` naming the commit, the hardware fingerprint and
      the seed, entered through the gate recorder from a receipt in which every registered control of the gate
      is `caught`, by a session that did not implement the skill layer.
- [ ] The registry's examples run as written: `frob skill check <skill.fskill> --design <design> --key <k>
      --json` compiles or reuses the compilation and checks; a call without `--key` on `skill.compile` or
      `skill.check` is FROB-REF-805; an unresolved `task_frame` is FROB-REF-802 with a pointer to the field.

## Test plan

### Unit tests

`crates/frob-control/tests/skill_verbs.rs`; the gate's fixture rows and controls are the GATE-REFLEX-08 entry
of the `g1_known_answers` tier target of `frob-conformance` (no private gate test file; the gate record above).

- `compile_memoized`: two calls with equal identities return the same `CompiledSkillId` and the second is a
  cache hit; changing a card value changes the identity.
- `check_arm_weak` / `check_pusher` / `check_cart_tip` / `check_wheel_speed`: the four rows above, with the
  listed numbers; each emits a bundle accepted by `frob-verify`.
- `check_feasible_replay`: the four feasible counterparts; `--replay` error below tolerance.
- `check_unknown_counted`: with the iteration budget forced to 1, states are `unknown`, exit code 2, and no
  FROB-REF-448 is raised.
- `show_limits`: all five limit texts and three flags are present.
- `refusal_envelope_448`: `pointer`, `observed` = 25/3, `required` = 10, `unit` = N, three repairs in order.
- `cancel_check`: cancel during a 10⁵-state check; no partial verdict; no leaked resources.
- `check_accepts_skill_and_design`: the `.fskill --design` form gives the same `CompiledSkillId` and outcome
  table as compiling first; `unresolved_task_frame_802`: pointer `/task_frame`, the design's frame names listed.

### End-to-end script and logging

`scripts/e2e/skill_exact_layer.sh` (bead N22b-05) drives the three verbs on the registered fixtures and
writes the NDJSON log and transcript; its `summary` line names GATE-REFLEX-08.

### Known answers and negative controls

KA-565 (two-link arm witness), KA-556 (friction certificate), KA-566 (refinement refusal), KA-567 (4 of 4
refused; witnesses replay). CX-236, CX-242, CX-243 as planted mutants. Determinism lanes: the gate runs twice
on one machine and across worker counts with identical outcomes and certificate bytes (rational checks D0,
numeric solves D2); debug and release builds agree on every verdict.

## Considerations

- The plan does not list the four infeasible bodies or say which two fixtures "both hand fixtures" are; the
  choices above are this bead's DESIGN, recorded in the coverage notes so the gate register can adopt or amend
  them before the gate runs.
- A skill verdict is instantaneous and local to sampled states; `sufficiency: "necessary-only"` is printed on
  every result.
- KILL-SKILL concerns only the learned residual. If it fires, this exact layer and its witnesses are what
  remains; nothing here depends on the residual.
- Open point for the verb registry: capability scope names for the `skill` cluster.
- Performance envelope (TARGET, to measure): `skill.check` over 10⁴ states and 4 modes under 10 s on the CPU.
