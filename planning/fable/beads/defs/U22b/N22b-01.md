## Background

Reflex is the subsystem that owns every closed loop that needs no learning. One of its objects is the **skill**:
a behaviour stated at the task boundary (the handle of a cart, a tray, a tool point), independent of the body
that performs it. A skill says "apply this wrench profile to the cart handle until the goal is 0.15 m away"; it
does not say which joints do it. The same skill can then be compiled against many candidate bodies, and for
each body and contact mode an exact program (other beads) either returns an actuation that realizes the task
command or a checked proof that this body cannot. That refusal is available before any training, which is the
point: an agent comparing designs learns that a body is too weak for a push from a dual vector that names the
binding actuator, not from a failed training run.

This bead defines the file that carries a skill: format identifier FMT-FSKILL, extension `.fskill`, schema
`frob.skill/1`. FACT (the format registry of the plan): owner crate `frob-control`; producers are controller
synthesis in `frob-control` and `frob-learn` (weights by reference only); consumers are `frob-control`,
`frob-learn`, `frob-arena` and `frob-shield`; the format is canonical (one byte representation per value);
weights are blobs addressed by hash, never inlined.

DESIGN decision and reason. The skill is a typed, content-addressed document and not a controller object,
because three different consumers read it (the compiler, the evaluator, the shield fitter) and each must be
able to cite exactly which behaviour it judged. Rejected: storing skills as controller code (not comparable
across bodies, not hashable by meaning); storing them inside the task file (a skill outlives one task and is
transported between bodies).

Terms. *Task frame*: the frame at which the command is expressed. *Phase*: a segment of the skill with one
reference profile and one exit predicate. *Exact layer*: the model-based part (map plus allocation program),
tier Solid. *Residual*: an optional learned correction in task space, tier Moonshot, absent (`null`) in every
artifact this bead's milestone produces. *No-authorization flags*: three constants,
`execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`, all `false`, carried by every
exported artifact; no constructor produces `true`.

## Scope

In: the schema, the Rust types, validation, canonical serialization, `SkillId`, the limits block, the header
flags, the registry row content, round-trip and fuzz tests. Out: the per-mode map (N22b-02), the allocation
program and witnesses (N22b-03), the refinement check (N22b-04), the verbs (BD-336), the learned residual
(N22b-07).

## Technical approach

**Document (DESIGN sketch; values illustrative).**

```json
{ "schema": "frob.skill/1",
  "name": "push-cart-level",
  "task_frame": "cart_handle",
  "interface": { "command": "wrench", "observables": ["handle_pose", "handle_twist"], "clock_hz": "50/1" },
  "phases": [
    { "id": "approach", "exit": "contact(handle)", "reference": "twist-profile#a1" },
    { "id": "push", "exit": "distance_to_goal < 0.15 m", "reference": "wrench-profile#p1" } ],
  "assumptions": { "mu_min": 0.4, "payload_kg": [0, 40], "slope_max": 0.05 },
  "secondary_costs": ["electrical_power", "winding_temperature"],
  "exact_layer": { "map": "constrained-mass-solve", "allocation": "cone-program", "witness": "dual" },
  "residual": null,
  "limits": ["instantaneous", "scope", "floating-base", "refinement", "on-failure"],
  "evidence": { "class": "Tested" },
  "authorization": { "execution_authorized": false, "hardware_safety_signoff": false,
                     "sim_to_real_certified": false } }
```

**Fields and rules.**

| Field | Type | Rule |
|---|---|---|
| `name` | identifier | Unique in the caller's namespace; not part of the hash of meaning (see `SkillId`) |
| `task_frame` | frame name | Resolved against the design or the scene at compile time; an unresolved frame is a compile refusal, not a format error |
| `interface.command` | `wrench` \| `twist` \| `acceleration` | The task-space quantity the phases command |
| `interface.observables` | list of channel names | What the skill may read; each must exist in the task's delivered observations |
| `interface.clock_hz` | rational string `"n/d"` | A rational control rate in the clock contract; a decimal is refused |
| `phases[].exit` | predicate text | Parsed by the requirement language of `frob-spec` (unit-normalized atoms such as `distance_to_goal < 0.15 m`, event atoms such as `contact(handle)`); stored in parsed canonical form |
| `phases[].reference` | `<profile-id>#<fragment>` | A content-addressed profile (twist, wrench or acceleration over phase time) and a segment within it; the kind must match `interface.command` or be `twist` for an approach phase |
| `assumptions` | `mu_min`, `payload_kg` [lo, hi], `slope_max` | The world box under which the skill is stated; `mu_min` is the friction coefficient used for forces the robot commands |
| `secondary_costs` | closed vocabulary | `electrical_power`, `winding_temperature`, `friction_utilization`, `torque_margin` (DESIGN: the first two are from the plan; the list is closed and versioned with the schema) |
| `exact_layer` | three enumerated strings | Version 1 admits only `constrained-mass-solve`, `cone-program`, `dual` |
| `residual` | `null` or `{ "weights": "<blake3>", "manifest": "<blake3>" }` | Non-null only for layer 2 [M] |
| `limits` | the five identifiers, all present | DESIGN: the plan requires five limits "written into every artifact"; a reader refuses a document that lacks one |
| `evidence.class` | `Tested` or `Estimated` | Never above `Tested`: a skill verdict over sampled states is a test |
| `authorization` | three `false` constants | A missing or `true` flag is rejected |

The five limits, as the fixed texts the identifiers stand for (shown by `skill.show`):

1. *instantaneous*: a feasible witness at each sampled state of a reference is necessary and not sufficient;
   the map cannot show multi-step dynamic feasibility such as capture-point recovery or a momentum-assisted
   jump.
2. *scope*: task-space skills of wheeled, wheel-legged and manipulating robots, and the stance phases of
   legged ones; legged locomotion needs a phase sequence to transfer, which gait orbits and policy inheritance
   address, not this format.
3. *floating-base*: a fixed-base pullback τ = JᵀF is wrong for a floating-base robot; the map must come from
   the contact-consistent constrained solve.
4. *refinement*: a transported skill refines its specification only if, for every admitted target state, every
   abstract command and every target disturbance, each target successor is related to an allowed abstract
   successor, with the command chosen from information available before the disturbance.
5. *on-failure*: a failure report returns the contact mode, the requested wrench, the support function of the
   attainable set in the failing direction, and a counterexample that re-runs.

**Types (DESIGN, `crates/frob-control/src/skill/format.rs`).**

```rust
pub struct Skill { name: Ident, task_frame: FrameName, interface: Interface, phases: Vec<Phase>,
                   assumptions: Assumptions, secondary_costs: Vec<SecondaryCost>, exact_layer: ExactLayer,
                   residual: Option<ResidualRef>, limits: Limits, evidence: SkillEvidence,
                   authorization: NoAuthorization }
pub struct Phase { id: Ident, exit: Predicate /* frob-spec */, reference: ProfileRef }
pub struct SkillId(Blake3);   // hash of the canonical bytes with `name` removed
```

**Canonical form.** Canonical JSON as used by every FrankenRobotics format: keys sorted, no insignificant
whitespace, numbers in shortest round-trip form, quantities normalized to SI with the unit kept as text,
rationals reduced, predicates printed from their parsed form. `SkillId` is the BLAKE3 of the canonical bytes
with `name` removed, so renaming does not change identity and any change of behaviour does.

**Validation order.** (1) schema and unknown fields; (2) units and rationals; (3) predicates parse; (4) phase
identifiers unique, at least one phase; (5) `limits` complete; (6) flags present and false; (7) `residual` null
unless the caller holds the Moonshot feature. A violation is a typed refusal with a JSON pointer to the field,
exit 3: an unknown field, or a `schema` major version this build does not read, is FROB-REF-891 from the version
gate of the format registry's owner trait (N34-19; this chapter has no code of its own for it); a missing or
non-false flag is FROB-REF-816 from the shared reader check (N37-23, through N37p1-01's contract row); every
other step's violation is the surface's schema refusal FROB-REF-802.

**Determinism and evidence.** Parsing and hashing are class D0 (exact). The document itself makes no claim; its
`evidence.class` is an upper bound that verbs lower by the claim-product rule (the weakest input wins).

## Acceptance criteria

- [ ] `crates/frob-control/src/skill/format.rs` holds the types, reader, writer and `SkillId`; the crate's
      `CONTRACT.md` describes the format in its ten sections.
- [ ] The sketch above parses, re-serializes to identical canonical bytes, and has a stable `SkillId` pinned in
      a golden file.
- [ ] A document missing any of the five limits, with a `true` or missing flag, with a decimal `clock_hz`, with
      an unknown field, or with `evidence.class` above `Tested` is refused with a pointer to the field.
- [ ] Renaming a skill leaves `SkillId` unchanged; changing `mu_min` from 0.4 to 0.5 changes it.
- [ ] The registry row for FMT-FSKILL (owner, producers, consumers, canonical, weights by hash) is supplied and
      the registry's round-trip check passes for `.fskill`.
- [ ] The reader has a fuzz target and a size limit; no input panics.

## Test plan

### Unit tests

`crates/frob-control/tests/skill_format.rs`.

- `roundtrip_sketch`: the document above → parse → write → bytes equal; `SkillId` equals the golden value.
- `rename_keeps_id` / `assumption_changes_id`: as in the acceptance list.
- `limits_required`: remove each of the five identifiers in turn; five refusals, each pointing at `/limits`.
- `flags_must_be_false`: set each flag to `true`; remove each; six refusals.
- `clock_is_rational`: `"50/1"` and `"100/2"` parse to 50 Hz (the second is rewritten reduced); `"50.0"` is
  refused.
- `predicate_canonical`: `distance_to_goal < 15 cm` and `distance_to_goal < 0.15 m` give the same canonical
  bytes.
- `reference_kind`: a `wrench` skill whose push phase cites a twist profile is refused.
- `residual_gated`: a non-null `residual` without the Moonshot feature is refused.
- Property test `parse_write_identity`: for generated valid skills, parse(write(s)) = s and write is idempotent.

### End-to-end script and logging

`scripts/e2e/skill_format.sh` (this bead's own; it sources the STD-E2E helper library). The format has no verb
of its own (`skill.show` is BD-336's), so the script drives the module through the test binary and one example
program, built only on this bead's dependencies. The sketch above is committed as
`crates/frob-control/tests/golden/skill/push-cart-level.fskill` beside its golden `SkillId`. Steps: (1)
`cargo test -p frob-control --test skill_format` through `e2e_cmd`; (2) `cargo run -p frob-control --example
skill_format -- show <golden file> --json`: asserts the phases, the assumptions, the five limit texts, the
three flags `false` and `evidence.class = "Tested"`, and `e2e_assert_eq` of the printed `SkillId` with the
golden value; (3) round trip: `-- roundtrip <golden file> --out work/rt.fskill --json`, then
`e2e_assert_digest_eq` of the canonical bytes before and after; (4) identity: a copy with `name` changed gives
the same `SkillId` and a copy with `mu_min` 0.5 a different one (each copy written under `work/` by the
example's `-- edit <file> --set <pointer>=<value> --out <path>`); (5) negative controls, each `e2e_expect_caught
<name> --` the example's `-- check <copy> --json` on a copy carrying the defect: `limit-missing` (one of the
five identifiers dropped), `flag-true` (`/authorization/execution_authorized` set to `true`), `clock-decimal`
(`"50.0"`), `field-renamed` (`mu_minimum`), `residual-inlined` (a weight array in `residual`); each must print
its typed refusal with the pointer of the failing validation step and exit 3: FROB-REF-816 with fault
`true:execution_authorized` for `flag-true`, FROB-REF-891 for `field-renamed`, FROB-REF-802 for the other
three. No `frob` verb is
called, so the evidence block is recorded as absent with reason `no-verb`. Log
`target/e2e-logs/skill_format/<utc>.ndjson` with a transcript: per line `ts`, `script`, `bead` (`N22b-01`),
`step`, `event`, the exact command, exit code and wall time; the `SkillId`, the canonical digests, each
refusal's code and pointer; on failure the first differing byte offset and the paths of the files compared; a
final `summary`. The verb-level path (`frob skill show` on the same document, an export round trip) is step 2
and 3 of `scripts/e2e/skill_exact_layer.sh` (N22b-05), which depends on BD-336 and runs after this bead.

### Known answers and negative controls

No numeric known answer belongs to the format itself. Negative controls (planted defects the tests must
catch): a missing limit; a `true` flag; a renamed field (`mu_minimum`); an inlined weight array in `residual`
(must be refused: weights are by hash). Determinism lane: the canonical bytes are identical in debug and
release builds and on both development platforms.

## Considerations

- The plan's sketch writes the flags as a placeholder inside `evidence`; this bead places them in a top-level
  `authorization` object, matching the output envelope and the other formats. Recorded in the unit's coverage
  notes.
- The `limits` field is this bead's realization of "limits written into every artifact"; the alternative
  (printing them only in `skill.show`) was rejected because an exported file would then travel without them.
- The format has no skill-specific refusal code (DESIGN, shared with BD-336's `skill.compile` step 2): a
  `.fskill` that fails validation is refused, exit 3, with the JSON pointer of the validation step that failed,
  under the code the registries assign to the condition (FROB-REF-891 for an unknown field or version, N34-REF;
  FROB-REF-816 for a flag, N37-REF; FROB-REF-802 for the rest), so an agent repairs the field it names.
- The no-authorization flags of this format follow the flag-carrier contract for kinds that land after M2
  (N37p1-01, a dependency: it holds the contract row for `.fskill`, carrier `header`, since M4, and the
  generated banner). This bead writes the header so that the row's sweep finds the three flags; it needs the
  contract, not the M3 sweep over the exporting verbs (BD-303).
- Privacy: a skill may name frames of a private scene; the artifact inherits the private mark of anything it
  references.
- Revisit if a skill needs concurrent phases or branching; version 1 is a linear phase list.
