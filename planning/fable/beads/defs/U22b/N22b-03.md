## Background

Given the per-mode map w = w₀ + B_m·u of a body (bead N22b-02), a skill's commanded task quantity w* is
attainable at a state if some admissible actuator effort u produces it while every contact force stays inside
its limits. This bead poses that question as a small cone program in the shared symmetric-cone solver of
`frob-algebra` and returns one of two checkable objects:

- a **feasible-allocation witness** (u, f_c), which can be replayed; or
- an **infeasibility witness**: a direction c in task space, the support value max cᵀ(w₀ + B_m·u) over
  admissible u, which is below cᵀw*, the gap, and the binding actuator or contact.

The second object is available before any training. It is the same dual certificate that every infeasible
control program returns, so one certificate format and one exact checker serve control, skills and static
attainability analysis (ADR-REFLEX-02: control programs, force distribution, skill allocation and shield
projection all use the one cone solver with a fixed iteration count and a mandatory optimality check; the
reason is one kernel family for physics and control and one dual-certificate format for every infeasibility
report).

Why a certificate and not "the solver failed". An unconverged solve proves nothing. A dual vector y with
Aᵀy in the dual cone K* and bᵀy < 0 proves that "find x in K with A·x = b" has no solution, because
0 ≤ ⟨Aᵀy, x⟩ = yᵀb < 0 would follow. Rounded to rationals and re-checked exactly, it makes the infeasibility
report a Proof claim of class `Certified` for the stated program at the stated state.

## Scope

In: the program, its two outputs, the exact re-check, the support value and binding constraint, the refusal
FROB-REF-448 and the failure report. Out: the map (N22b-02); the refinement check (N22b-04); the verbs and the
gate (BD-336); the solver itself (BD-115) and the four-dimensional contact cone (BD-154).

## Technical approach

**Unknowns.** Actuator efforts u; contact forces f_c (eliminated through f_c = F₀ + F_u·u when the mode is
uniquely constrained, kept as free variables with the dynamics as equalities when the map is marked
`non-unique`).

**Constraints.**

1. Actuator boxes lo ≤ u ≤ hi, read from each actuator card's torque–speed envelope at the state's joint
   speed (the box shrinks as speed rises).
2. Contact cones for forces the robot commands, with the skill's `mu_min`: the four-dimensional contact cone
   (normal, two tangential, spin), a second-order cone after scaling the tangential and spin components by
   the friction coefficient and the effective patch radius; in the plane, |f_t| ≤ μ_min·f_n.
3. Unilateral support limits: f_n ≥ 0 at every support, and f_n ≤ the support's rated load where the card
   states one.

**Objective.** Minimize ‖B_m·u − (w* − w₀)‖² + Σ ρ_k·cost_k(u), where the secondary costs are those the skill
lists (electrical power, winding temperature, ...) with declared weights ρ_k small against the task term.

**Procedure per state and mode.**

1. *Feasibility solve.* Solve the program with the task as an equality, B_m·u = w* − w₀. The solver runs a
   fixed number of iterations (part of the program's identity) and ends in `optimal`, `infeasible` or
   `unconverged`.
2. `optimal`: run the optimality check (primal feasibility, dual feasibility, complementarity, stationarity,
   each within the declared tolerance). Emit `FeasibleAllocation { state, mode, u, f_c, residuals }`. Then
   re-solve with the secondary costs to pick the reported allocation.
3. `infeasible`: the solver returns y. Rationalize y (continued fractions to a bounded denominator), then
   check in exact rational arithmetic that Aᵀy ∈ K* and bᵀy < 0 (proof obligation PO-REFLEX-03). If the
   rounded vector fails, tighten the rounding once; if it still fails, the state is `unknown`.
4. From an accepted y, read the task-row part as the direction c (normalized to unit length in the task
   metric). Compute the support value σ(c) = max cᵀ(w₀ + B_m·u) over the admissible set by one more cone
   program, with its own optimality check, and the gap cᵀw* − σ(c) > 0.
5. *Binding constraint.* The constraint with the largest multiplier at the support optimum, named as
   `Actuator(joint)`, `Contact(id, cone)` or `Support(id)`; ties are all listed.
6. `unconverged`: neither witness; the state is `unknown` and is counted as such, never as feasible and never
   as infeasible.

**Outputs (DESIGN).**

```rust
pub enum AllocationOutcome { Feasible(FeasibleAllocation), Infeasible(InfeasibilityWitness), Unknown(Reason) }
pub struct InfeasibilityWitness { state: StateDigest, mode: ContactMode, requested: TaskQty,
    direction: TaskVec, support: Qty, required: Qty, gap: Qty, binding: Vec<Binding>,
    certificate: DualCertificate /* rational y, kind lp-farkas or conic-farkas */ }
```

**The refusal.** FROB-REF-448: *a skill's task wrench lies outside the body's attainable set.* Trigger: an
accepted infeasibility witness at any sampled state of a phase's reference. Envelope: exit code 3; `pointer`
names the phase and state; `observed` is the support value, `required` the requested component, `unit` the
task unit. Ranked repairs: (1) regear or replace the binding actuator; (2) reshape the body or the contact
(the binding contact or support); (3) change the wrench profile. The failure report carries the contact mode,
the requested wrench, the support function of the attainable set in the failing direction, and a
counterexample state that re-runs.

**Claim and class.** A per-state infeasibility witness is a Proof claim, class `Certified`, about the declared
model; the weakest input rule then applies, so a friction coefficient or torque limit taken from a card field
marked `assumed` makes any statement about the robot `Estimated`. A feasible witness is checked by exact
substitution into the equations (the `lp-primal` pattern) and is `Certified` for that state. A verdict over a
sampled set of states is `Tested`.

**Batched form.** States are worlds; the fixed iteration count lets the solve run in lockstep across states.

## Considerations

- The outer and inner friction cones differ: forces the robot commands use `mu_min`. Using a larger
  coefficient would admit allocations that slip.
- Strictness: only a strict certificate (bᵀy < 0) is accepted; a boundary case with no strict witness is
  `unknown`.
- The witness is instantaneous; a skill that passes at every sampled state can still fail dynamically, and the
  artifact's limits say so.
- Risk: rationalization of an ill-scaled y. Mitigation: equilibrate the program before solving and check the
  certificate against the unscaled data.
- A-24 (task-wrench attainability) calls this procedure without a skill; keep `TaskQty` independent of the
  skill format.
