## Background

A skill is a specification at the task boundary: from an abstract state, under an abstract command, only
certain successors are allowed (for example "after `push`, the cart is `stable`"). When a skill is compiled
for a body, or moved to another body, the body's closed-loop behaviour must **refine** that specification.
The tempting shortcut is to say the target refines the specification if it *can* reach an allowed successor.
That is wrong whenever the environment, not the controller, chooses among successors.

Counterexample (CX-242, known answer KA-566): the specification's transition has the single successor
`stable`. The target body, under the command the interface selects, has successors {`stable`, `fall`}
depending on a disturbance the controller does not see beforehand. Selecting the `stable` branch is not
something a controller can do. The target does not refine the specification, and the check must refuse it
(FROB-REF-444) naming `fall` as the uncovered successor.

The correct relation is an alternating simulation: the controller chooses first, from information available
before the disturbance; then the environment chooses; every outcome must be allowed. This is the same
quantifier order that the rest of the system enforces (one command for every admitted disturbance, never a
command chosen after the disturbance is seen).

The second job of this bead is to make the five limits that every `.fskill` carries operative: each limit is
either enforced by a check or printed on every result that could be misread without it.

## Scope

In: the finite refinement checker, its counterexample output, FROB-REF-444, and the enforcement points of the
five limits. Out: building target abstractions for the learned-residual layer at scale (N22b-07); the
certified interface map between two bodies (`mission.transport`, Augur); the verbs (BD-336).

## Technical approach

**Objects (DESIGN, `crates/frob-control/src/skill/refine.rs`).**

- Abstract specification 𝒜 = (S_A, C_A, δ_A): abstract states (phases refined by the predicates their exits
  name), abstract commands, and the allowed-successor relation δ_A ⊆ S_A × C_A × S_A. Derived from the
  `.fskill` phases; a hand-written 𝒜 may be supplied for fixtures.
- Target 𝒯 = (S_T, U_T, D_T, step): target states (a declared finite set, or the sampled states of a check),
  target commands, an admitted disturbance set D_T (finite, or drawn by address from the skill's assumption
  box), and the successor function step(x, u, d).
- Relation R ⊆ S_T × S_A: a target state is related to an abstract state compatible with its observable
  history (evaluated through the skill's observables and predicates).
- Interface κ(c, info(x)) → u: the target command for abstract command c, a function of delivered information
  only. Its signature does not take d; a κ that needs the disturbance cannot be written.

**Check.**

1. For every (x, a) ∈ R and every abstract command c enabled at a:
2. compute u = κ(c, info(x));
3. for every d ∈ D_T compute x′ = step(x, u, d);
4. require some a′ with (a, c, a′) ∈ δ_A and (x′, a′) ∈ R.
5. On the first failure return `RefinementCounterexample { x, a, c, u, d, x_prime, allowed: Vec<a′> }` and
   refuse with FROB-REF-444.
6. If every case passes on a finite enumerated 𝒯, the verdict is `refines` for that 𝒯. If D_T was sampled,
   the verdict is `refines (sampled)` and its class is `Tested`.

Preservation clauses checked alongside (each a separate reported row): initial states are related;
observations, task outputs, timing and target progress are preserved across a step within the declared error
and timing budgets.

**The refusal.** FROB-REF-444: *a transported skill does not refine its specification.* Exit code 3. The
envelope's `pointer` names the phase and abstract transition; the counterexample names the uncovered
successor. Ranked repairs: (1) add a guard that excludes the state from the entry set; (2) narrow the entry
set (the assumptions box). Retry: `after-change`.

**Enforcement of the five limits.**

| Limit | Enforcement |
|---|---|
| Instantaneous | Every `skill.check` result carries `sufficiency: "necessary-only"`; no verb reports a skill as dynamically feasible on witnesses alone |
| Scope | `skill.compile` classifies each phase and mode. Phases of wheeled, wheel-legged and manipulating robots and stance phases of legged robots are in scope. A legged swing or flight phase is reported `out-of-scope: needs a phase sequence` (a finding, exit code 2) and receives no witness |
| Floating base | The only map constructor for a model with an unactuated base is the constrained solve of N22b-02; a fixed-base pullback constructor exists only for fixed-base models (type-level) |
| Refinement | The check above, run by `skill.check --refinement` and always on a skill compiled for a body other than the one it was authored on |
| On failure | The failure report type has four mandatory fields: contact mode, requested wrench, support function in the failing direction, re-runnable counterexample; a report lacking one does not serialize |

**Determinism and class.** The enumerated check is class D0 when step is exact (finite fixtures); with
simulated steps it inherits the tier and determinism of the runs and is `Tested`.

## Acceptance criteria

- [ ] The {stable, fall} fixture is refused with FROB-REF-444 and `x_prime = fall`, `allowed = [stable]`.
- [ ] A target whose successors are all `stable` is accepted on the same specification.
- [ ] A mutant checker that requires only *some* disturbance to lead to an allowed successor accepts the
      {stable, fall} fixture; the test suite detects the mutant (it is registered as a negative control).
- [ ] An interface that reads the disturbance cannot be expressed through the public API (compile-fail test),
      and a test double that smuggles d through `info` is rejected by the delivered-information check.
- [ ] Each of the five limits has its enforcement point implemented and one test.
- [ ] `CONTRACT.md` of `frob-control` states the relation, its quantifier order and what `refines (sampled)`
      does not establish.

## Test plan

### Unit tests

`crates/frob-control/tests/skill_refine.rs`.

- `stable_fall_refused`: S_A = {start, stable}; C_A = {push}; δ_A = {(start, push, stable)}. Target:
  S_T = {x₀, stable_T, fall_T}; D_T = {d₁, d₂}; step(x₀, u, d₁) = stable_T, step(x₀, u, d₂) = fall_T;
  R = {(x₀, start), (stable_T, stable)}. Expected: refusal, counterexample d₂, x′ = fall_T.
- `all_stable_accepted`: step(x₀, u, d₂) = stable_T. Expected: `refines`.
- `exists_mutant_caught`: run the mutant (∃d) on `stable_fall_refused`; it accepts; the registry entry asserts
  the production checker and the mutant disagree.
- `clairvoyant_interface_rejected`: trybuild compile-fail for κ taking d; runtime test for an `info` that
  differs between d₁ and d₂ before the step.
- `scope_swing_phase`: a quadruped skill with a swing phase reports `out-of-scope`, exit code 2, no witness.
- `fixed_base_constructor_absent`: compile-fail on calling the fixed-base constructor with a floating-base
  model type.
- `failure_report_complete`: constructing a report without a counterexample fails to compile.
- Property test: for random finite 𝒜 and 𝒯, the checker agrees with a brute-force evaluation of the
  definition.

### End-to-end script and logging

`scripts/e2e/skill_refine.sh` (this bead's own; it sources the STD-E2E helper library). The checker has no verb
of its own (`skill.check --refinement` is BD-336's), so the script drives the module through the test binary and
one example program, built only on this bead's dependencies, on the finite fixtures of the unit tests. Steps:
(1) `cargo test -p frob-control --test skill_refine` through `e2e_cmd` (it includes the compile-fail tests);
(2) `cargo run -p frob-control --example skill_refine -- --fixture stable-fall --json`: the typed refusal
FROB-REF-444 with the pointer at the phase and abstract transition, the counterexample d₂, x′ = `fall_T`,
`allowed = [stable]`, retry `after-change` and the repairs in order (add a guard; narrow the entry set); (3)
`--fixture all-stable`: verdict `refines`; (4) `--fixture all-stable --sampled 200 --seed $SEED`: verdict
`refines (sampled)` with the draw count and seed address printed and class `Tested`, never the bare word
`refines`; (5) `--fixture quad-swing`: the scope classifier reports `out-of-scope: needs a phase sequence` and
no witness; (6) negative control `e2e_expect_caught exists-mutant -- cargo test -p frob-control --features
refine_by_selecting_branch --test skill_refine`: the feature is the `feature` of the control's record in
`registry/controls.toml`, which for a control seeded from the catalogue is its plant's name (CX-242's plant,
N22-CX; N38b-04 and N38b-05: `nc-<nnnn>` names only a control a bead registers directly); this bead, which owns
the checker, declares it in `frob-control` as implying the crate's `conformance` feature. The ∃d mutant of
CX-242 accepts the stable/fall fixture, so the suite run on it must fail. No `frob` verb is called, so the evidence
block is recorded as absent with reason `no-verb`. Log `target/e2e-logs/skill_refine/<utc>.ndjson` with a
transcript: per line `ts`, `script`, `bead` (`N22b-04`), `step`, `event`, the exact command, exit code and wall
time; each verdict, the counterexample fields and the refusal's code, pointer and repairs; on failure the first
differing field and the fixture; a final `summary`. The verb-level path (`frob skill check --refinement` on the
registered pair, exit 3 with FROB-REF-444) is step 7 of `scripts/e2e/skill_exact_layer.sh` (N22b-05), which
runs after this bead.

### Known answers and negative controls

KA-566 (the {stable, fall} target is refused with the uncovered successor named). CX-242 (selecting the good
branch) is the `exists_mutant_caught` control. Related quantifier control: a certificate proved in the order
"for every disturbance there is a command" is rejected elsewhere in the system (CX-075); this checker's API
makes that order unwritable.

## Considerations

- A `refines (sampled)` verdict says nothing about disturbances that were not drawn; the result prints the
  number of draws and the seed address, and never the bare word `refines`.
- Approximate relations (error and timing budgets) must be small enough to preserve the mission's acceptance
  predicates; choosing those budgets belongs to the task, and an unset budget defaults to exact equality of
  abstract labels.
- A successful refinement of one skill segment does not certify the remainder of a mission.
- The certified interface map between two bodies is Augur's `mission.transport` [F]; a skill moved by the
  learned residual carries no certified claim unless that verb issued the interface certificate for the same
  pair of bodies. Neither verb stands in for the other.
