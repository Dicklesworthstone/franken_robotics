## Background

A runtime shield projects a proposed command onto barrier rows inside the actuator box. With one row and a
diagonal metric the projection is exact (bead N22b-22). With two to four rows there is no such closed form;
the shield then runs a **fixed number of iterations** of the workspace's shared cone solver and must decide
what to do with the result. An iterative solver stopped after a fixed budget may not have converged, and a
partially converged iterate can violate a row. Sending such an iterate to a driver would be the worst kind of
failure: an unsafe command stamped as filtered.

The plan's rule, which this bead implements: after the iterations, a **mandatory optimality check**: primal
feasibility of rows and box, nonnegative multipliers, complementarity and stationarity, each within a stated
tolerance. If any part fails, or the rows conflict, the step invokes the backup controller **atomically**. A
partially converged iterate never reaches a driver: only a `Checked<Command>` can be passed on. This is
proof obligation PO-SHIELD-03 (no command leaves the filter without passing the optimality check or coming
from the backup; verified by type-state in the API, a compile-fail test and a planted non-convergent
instance) and invariant INV-SHIELD-01 (a filtered command satisfies the actuator box exactly and the active
rows within tolerance, or the backup controller is running).

More than four coupled rows are refused when the shield is fitted (FROB-REF-454). The cap keeps the solve a
fixed, small program whose behaviour can be exhausted by tests and, later, exported.

Why one solver. ADR-REFLEX-02: control programs, force distribution, skill allocation and shield projection
all use the one symmetric-cone solver of `frob-algebra`, with a fixed iteration count and a mandatory
optimality check, so that one kernel family serves physics and control.

## Scope

In: the multi-row solve; the optimality check for one to four rows; the type-state; the atomic hand-over to
the backup; the coupling rule and FROB-REF-454; event records; the conformance-only plant kind
`shield-iterations`. Out: the single-row algorithm (N22b-22); the
backups (N22b-24); row construction (N22b-20); fitting and verbs (BD-338).

## Technical approach

**Problem.** minimize ½·(u − u_π)ᵀ·R·(u − u_π) subject to A·u ≥ c (k rows, 2 ≤ k ≤ 4) and lo ≤ u ≤ hi.

**Solve.** Pose it as a small program over the nonnegative orthant (slacks for rows and both box sides) in
the shared solver; run N_it iterations (N_it is part of the shield's identity; DESIGN default 12, to be set
from measurement); read the last iterate (u, λ) and the solver's end state. Clip u to the box as the last
operation, so the box holds exactly.

**Optimality check** (always run, whatever the end state; tolerances declared in the shield's identity):

1. *Primal, rows*: aᵢᵀu − cᵢ ≥ −tol_p for every row.
2. *Primal, box*: lo ≤ u ≤ hi exactly (true by the final clip; asserted).
3. *Dual*: λᵢ ≥ −tol_d.
4. *Complementarity*: λᵢ·(aᵢᵀu − cᵢ) ≤ tol_c for every row.
5. *Stationarity*: with r = R·(u − u_π) − Aᵀλ: for a coordinate strictly inside the box |rⱼ| ≤ tol_s; at its
   lower bound rⱼ ≥ −tol_s; at its upper bound rⱼ ≤ tol_s.

All five pass → `Checked<Command>`. Any failure, an `infeasible` end state, or an `unconverged` end state
whose iterate fails the check → the backup.

**Type-state (DESIGN, `crates/frob-shield/src/filter/checked.rs`).**

```rust
pub struct Unchecked<C>(C);                 // an iterate; has no method that yields a driver command
pub struct Checked<C> { cmd: C, source: CommandSource, residuals: KktResiduals }   // private fields
pub enum CommandSource { PassThrough, Projected { rows: u8 }, Backup(BackupKind) }
impl Unchecked<Command> {
    pub fn check(self, problem: &RowProblem, tol: &Tolerances) -> Result<Checked<Command>, CheckFailure>;
}
// The only other constructor of Checked<Command> is BackupController::command, inside its declared domain.
// The driver interface takes Checked<Command>; no conversion from Unchecked or from a raw Command exists.
```

**Atomic hand-over.** Within one tick and one world: on `CheckFailure` or row conflict the stage calls the
fitted backup's `command(x̂)`, emits `ShieldEvent::Backup(kind)` with the reason (which check failed, or
`rows-conflict`, or `row-infeasible`), sets the tick's layer record to `backup`, and returns the backup's
`Checked<Command>`. There is no state in which the tick has neither a checked projection nor a backup
command. In a batch, the selection between projection and backup is a per-world mask applied after both
candidates exist, so one world's failure does not disturb its neighbours (lockstep).

**Events.** `ShieldEvent::Projected { rows }` when the applied command differs from the proposed one,
`Backup(kind)` as above, and nothing when the proposed command passed unchanged. Every event carries the
tick, the world address and the residuals.

**Coupling rule and refusal.** Two rows are *coupled* if they share an actuator channel with non-zero
coefficients; coupling is the transitive closure. Rows in different components are independent problems and
are solved separately (often by the exact single-row method). At fit time, a component with more than four
rows is refused: FROB-REF-454, *a shield's rows have no common admissible command on the calibration set, or
more than four are coupled*; exit code 3; ranked repairs: reduce the row set; widen the actuator box; lower
the speed limit.

**Run-level plant (DESIGN; conformance builds only).** A script must be able to force a non-convergent solve
at a chosen tick of a real run (N22b-32 step 6), and no product build may carry a switch for it. This bead
registers the plant kind `shield-iterations` in N29a-25's section registry `registries/plant-kinds.toml` (kind
`shield-iterations`, owning bead N22b-23, crate `frob-shield`, admission function the checks below, hook the
entry of this bead's batched multi-row solve, which already receives each world's address and tick for its
events, so the plant acts in any stage that calls the solve, BD-338's included). A section entry `{ "world": <index>, "tick": <control tick>,
"iterations": <n> }` makes that world's multi-row solve at that tick run n iterations in place of N_it. It
travels in the file of `--conformance-plant <file>` (schema `frob.conformance-plant/1`) on `sim.run`, and the
file's common rules apply: its canonical bytes enter `StepPlanId`, the receipt lists the plant `applied` or
`skipped`, and without `frob-shield`'s `conformance` feature the hook compiles to nothing and the kind is a
typed test error naming it. Admission refuses, naming the field: a world or tick outside the run, n outside
1 ≤ n ≤ N_it, and a run with no shield stage. A plant whose world has fewer than two coupled active rows at
that tick is `skipped`, never counted as applied. Reason: the optimality check and the atomic hand-over are
then exercised on the production path by the product's own check. Rejected: an environment variable or a
hidden option read by `frob` (a release binary would carry it).

## Acceptance criteria

- [ ] `project_n` and the checker exist; the driver-facing API accepts only `Checked<Command>`.
- [ ] Compile-fail tests show that an `Unchecked<Command>` or a raw `Command` cannot be passed to the driver
      interface and that `Checked` has no public constructor.
- [ ] The tier-3 specification's law `checked_command_only` (N10c-02, PO-SHIELD-03 and INV-SHIELD-01; logged
      `pending` there until this bead lands) is discharged here: its compile-fail case, an unchecked iterate
      passed to the driver interface of this production API, is in `crates/frob-shield/tests/compile_fail/`
      and fails to compile with the expected diagnostic; the specification's `multi_row_kkt_failure_invokes_backup`
      and `five_rows_refused` laws pass against `project_n`. N10c-02's log line changes from `pending` to `pass`.
- [ ] A planted non-convergent multi-row instance (iteration budget forced to 1) invokes the backup, emits
      `Backup` with reason `stationarity` or `primal`, and the driver receives the backup's command.
- [ ] Conflicting rows and rows infeasible within the box invoke the backup with the right reason.
- [ ] On 10⁵ random feasible instances with k from 2 to 4, every `Checked` result satisfies the box exactly
      and each row within tol_p, and agrees with a reference solve within tolerance; every instance that the
      reference marks infeasible ends in the backup.
- [ ] A shield with five coupled rows is refused at fit with FROB-REF-454; five rows in two components of
      sizes 3 and 2 are accepted.
- [ ] Batch test: forcing one world of a batch into the backup leaves every other world's digest unchanged.
- [ ] The plant kind `shield-iterations` is in `registries/plant-kinds.toml`; in the batched solve a planted
      (world, tick) runs the planted iteration count and hands over to the backup while every other world's
      result is unchanged; the admission function refuses an entry naming a world or tick outside the given
      run shape, or n outside 1 ≤ n ≤ N_it; without the `conformance` feature the hook does not exist. (That
      a real run's receipt lists the plant `applied` is asserted by N22b-32 step 6, after BD-338 has wired the
      stage.)

## Test plan

### Unit tests

`crates/frob-shield/tests/project_n.rs`, `crates/frob-shield/tests/compile_fail/*.rs`.

- `two_rows_hand`: R = I, u_π = (0, 0), box [0, 1]², rows u₁ ≥ 0.5 and u₁ + u₂ ≥ 1.2. Solution
  u = (0.6, 0.6), multipliers λ = (0, 0.6). Check: r = u − Aᵀλ = (0.6, 0.6) − 0.6·(1, 1) = 0; row 1 slack
  0.1 with λ₁ = 0; row 2 active.
- `two_rows_both_active`: rows u₁ ≥ 0.8 and u₁ + u₂ ≥ 1.2 from u_π = (0, 0): u = (0.8, 0.4),
  λ = (0.4, 0.4): r = (0.8, 0.4) − (0.4 + 0.4, 0.4) = 0.
- `conflicting_rows`: u₁ ≥ 0.8 and −u₁ ≥ −0.5 → backup, reason `rows-conflict`.
- `box_infeasible`: u₁ + u₂ ≥ 2.5 in [0, 1]² → backup, reason `row-infeasible`.
- `planted_nonconvergent`: an ill-conditioned three-row instance with N_it = 1 → check fails → backup.
- `partial_iterate_never_escapes`: instrument the driver sink; over 10⁵ instances with random iteration
  budgets from 1 to 12, every command reaching the sink has `source` `PassThrough`, `Projected` with passing
  residuals, or `Backup`.
- `coupling_components`: rows on channels {1,2}, {2,3}, {4}, {4,5}, {5}: components of sizes 2 and 3.
- `five_coupled_refused`, `five_in_two_components_accepted`.
- `compile_fail_unchecked_to_driver`, `compile_fail_construct_checked` (trybuild).
- `lockstep_mask`: the batch test of the acceptance list.
- `plant_shield_iterations` (with `--features conformance`; the batched solve called directly over 8 worlds
  and 100 ticks of the ill-conditioned three-row instance, no physics): the plant `{world 3, tick 50,
  iterations 1}` makes world 3 emit `Backup` at tick 50 with a reason from the check and report `applied`,
  and the other seven worlds' results equal the unplanted call's bit for bit; the admission function refuses
  `{world 9, …}` for a shape of 8 worlds and `iterations 0`, naming the field; on a tick where world 3 has
  one active row the plant reports `skipped`.

### Known answers and negative controls

The two hand cases above (hand-derived here). Negative controls registered: the planted non-convergent
instance (named in GATE-SHIELD-02); a mutant that returns the last iterate when the check fails (must be
caught by `partial_iterate_never_escapes`); a mutant that checks primal feasibility only (accepts a feasible
but non-optimal point; caught by the stationarity test). Determinism: fixed iteration count gives class D2
results; identical across worker counts and batch positions.

## Considerations

- Tolerances trade false backups against row violations; they are declared numbers in the shield identity,
  and the rate of backup invocations is reported so an over-tight tolerance is visible.
- A backup invoked because the solver did not converge is a telemetry event with its reason. "It worked" is
  not a result if the backup did the work (ADR-REFLEX-08).
- The four-row cap is the plan's; lifting it would need its own evidence that the fixed-iteration solve and
  the check remain reliable.
- If KILL-SHIELD fires, this code is not shipped as a shield; rows become penalties and alarms.
