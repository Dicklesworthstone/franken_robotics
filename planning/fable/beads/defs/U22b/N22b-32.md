## Background

A runtime shield is a filter between a policy and the actuators that projects commands onto barrier rows
written on a reduced-order template, with a measured margin, a backup controller and assumption monitors.
Its parts have their own tests and its gates have their own campaign scripts. This bead is the user-side
proof that the capability hangs together: one shell script that fits a shield, runs with it, checks the run,
reads the report and provokes each failure path through the real `frob` binary, with structured logs. Every
assertion group has a planted defect that must make the script fail, since a test that nothing can fail
validates nothing.

## Scope

In: one script, its fixtures, its planted defects, its logs. Out: the 10⁶-instance projection suite, the
5,000 + 5,000 campaign and the 10⁴ coverage run, which have their own scripts (BD-338's gate target,
`gate_shield_03.sh`, `gate_shield_04.sh`); the energy tier (N22b-18).

## Technical approach

**Location and conventions.** `scripts/e2e/shield_runtime.sh`, POSIX shell, sourcing the shared helper of
the end-to-end harness; idempotent; seeds explicit; non-zero exit after the summary on any failed group.
Fixtures in `fixtures/shield/runtime/` (`synthetic`): a differential-drive design with its baseline
controller; the task `keepout-and-door` (one keep-out disc of radius 0.5 m, a door swept region, a speed
limit of 1 m/s); a low-friction variant of the world (μ = 0.3 where μ_min = 0.5 is assumed); a three-row
coupled task for the multi-row path; a five-row coupled task; the hand instance file for the projection
example.

**Steps.**

1. `frob doctor --json`: record build and fingerprint.
2. `frob shield fit --design dd-base --controller baseline --task keepout-and-door --tier batch-cpu --json`.
   Assert: template `unicycle`; rows listed with their three margin parts and sources; a margin with n ≥ 999
   and α from the registry; backup `damping-injection` with a gain at or below M̄_min/h; five monitors with
   latencies; `evidence.class = "Tested"`; three flags `false`; a stable `ShieldId` on a second call
   (idempotent replay).
3. Projection example through the verb surface: `frob shield check --instance
   fixtures/shield/runtime/row1.json --json` with R = I, u_π = (1, 0), box [0, 1]², row u₁ + u₂ ≥ 1.5.
   Assert the applied command (1, 0.5) and λ = 0.5.
4. Shielded run: `frob sim run --design dd-base --task keepout-and-door --shield <id> --tier batch-cpu
   --worlds 256 --seed 11 --json`. Assert from `frob shield report <id> --run <run> --json`: zero ticks
   with the true base inside the keep-out disc (from the evaluator's truth stream); intervention fraction
   above zero and below the `shield-dominated` fraction; every tick has a control layer.
5. `frob shield check <run> --shield <id> --json`: assert `holds`; box violations 0; largest row residual
   within tolerance; every projected tick's command matches the independent reference.
6. Multi-row path: the three-row task with the test switch that forces the iteration budget to 1 at tick 50
   in world 3: assert a `Backup` event at that tick with reason from the optimality check, layer `backup`
   from then on in that world, and unchanged digests for the other worlds against a run without the switch.
7. Refusals: `frob shield fit` on the five-row coupled task → exit code 3, FROB-REF-454, repairs "reduce
   the row set", "widen the actuator box", "lower the speed limit". `frob shield fit --reuse-margin <id>`
   with another controller identity → exit code 3, FROB-REF-457, repair "recalibrate…".
8. Monitor and backup: run the low-friction world; assert an `Alarm` from the friction monitor, hand-over
   to the backup in the same tick, and from `frob telemetry energy <run> --json` that the stored energy at
   ticks is non-increasing from the hand-over (within the ledger's residual bound).
9. Drift: a stream of four batches, the last two on a world family with torque limits reduced by 30%:
   assert the drift statistic crosses its threshold in the last two batches and not before, the regime is
   retired, and a new `frob shield fit` produces a new margin and regime.
10. Bound and report: on 500 episodes with hidden-state labels, `frob shield report --json` prints the three
    numbers with intervals, the label source `hidden-state`, the scope key, and a separate row for the
    low-friction family with no bound.
11. Training bookkeeping: a short `frob train start --shield <id>` (explicit seed, a few updates); assert
    the rollout record has `sampled_action`, `log_prob`, `applied_action`, `control_layer`, `shield_events`.
12. Determinism: repeat step 4 with `--workers 1` and `--workers 8`; assert identical run digests.
13. Cancellation: start `frob shield fit` with a large calibration count, cancel it, assert no shield record
    was published.

**Logging.** NDJSON to `target/e2e-logs/shield_runtime/<utc-timestamp>.ndjson` with a transcript beside it.
Every line: `ts`, `script`, `bead` (`N22b-32`), `step`, `event` (`start`, `cmd`, `assert`, `metric`,
`refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim,
class, tier, determinism, identities, seed). `metric` lines: the projection result against (1, 0.5); box
violations against 0; row residual against tolerance; intervention and backup fractions; alarm tick and
hand-over tick; the drift statistic against its threshold per batch; the three numbers of the bound with
intervals; run digests where state is compared. `refusal` lines: code, pointer, observed, required,
repairs. On failure: the first differing value and the paths of the shield record, the run and the instance
file. Final `summary`: assertions passed and failed and `gates: ["GATE-SHIELD-02", "GATE-SHIELD-04"]`
(touched at smoke scale; the gate receipts come from the gate scripts).

## Acceptance criteria

- [ ] The script exists and passes on a clean checkout on `batch-cpu`.
- [ ] It fails (non-zero) under each planted defect, enabled by an environment switch: the
      project-then-clip projection; a filter that returns the last iterate when the optimality check fails;
      a labeller that takes breaches from the monitor's own log; a margin lookup that ignores the policy
      component of the key; a damping gain above the sampled bound.
- [ ] Every assertion of steps 2 to 13 is logged with measured and expected values.
- [ ] Two consecutive runs give identical assertion outcomes, `ShieldId` and run digests.
- [ ] The log validates against the harness's schema; no scene content appears in it.

## Test plan

### Unit tests

`scripts/e2e/tests/shield_runtime_selftest.sh`: runs the script against a recorded envelope set in which the
projection result is (1, 0.25); asserts a non-zero exit and a log line naming the first differing value and
the instance file.

### End-to-end script and logging

As above. Commands: `frob doctor`, `frob shield fit`, `frob shield check` (run and `--instance` forms),
`frob shield report`, `frob sim run --shield`, `frob telemetry energy`, `frob eval run`, `frob train start
--shield`, `frob job cancel`.

### Known answers and negative controls

KA-571 (projection (1, 0.5)), KA-572 (backup energy non-increasing), KA-573 (policy change trips
FROB-REF-457; drift trips the alarm). CX-240 (project then clip), CX-241 (self-labelling). Determinism
lanes: twice on one machine; across worker counts; debug and release (via `FROB_BIN`); on a device where one
is present, with the filter's decisions compared at the class the backend attains.

## Considerations

- The script is a smoke test of every path, sized to finish in a few minutes on a CPU; it does not replace
  the gate campaigns and its `summary` says "smoke".
- If KILL-SHIELD fired for the wheeled class, the script's fit and report steps assert the monitor-set
  wording and the absence of a bound instead; the projection, backup and monitor steps still run because
  those parts remain in use.
- The low-friction world of step 8 violates in the monitor-only reading by design of the chapter's
  aliasing fixture; this script asserts only the alarm and the hand-over, and leaves the timeliness
  consequences to that fixture's own gate.
