## Background

A runtime shield is a filter between a policy and the actuators that projects commands onto barrier rows
written on a reduced-order template, with a measured margin, a backup controller and assumption monitors.
Its parts have their own tests and its gates have their own campaign scripts. This bead is the user-side
proof that the capability hangs together: one shell script that fits a shield, runs with it, checks the run,
reads the report and provokes each failure path through the real `frob` binary, with structured logs. Every
assertion group has a planted defect that must make the script fail, since a test that nothing can fail
validates nothing.

## Scope

In: one script, its fixtures, its planted defects, its logs. Out: the 10⁶-instance projection suite, the
5,000 + 5,000 campaign and the 10⁴ coverage run, which have their own scripts (BD-338's gate target,
`gate_shield_03.sh`, `gate_shield_04.sh`); the energy tier (N22b-18).

## Technical approach

**Location and conventions.** `scripts/e2e/shield_runtime.sh`, bash under STD-E2E's script rules (its `lib.sh`
is bash, so a `#!/bin/sh` script cannot source it), sourcing the shared helper of
the end-to-end harness; idempotent; seeds explicit; non-zero exit after the summary on any failed group.
Fixtures in `fixtures/shield/runtime/` (`synthetic`): a differential-drive design with its baseline
controller; the task `keepout-and-door` (one keep-out disc of radius 0.5 m, a door swept region, a speed
limit of 1 m/s); a low-friction variant of the world (μ = 0.3 where μ_min = 0.5 is assumed); a three-row
coupled task for the multi-row path (`three-row-coupled`) with its plant file `iter1-w3-t50.json` (schema
`frob.conformance-plant/1`, one `shield-iterations` entry: world 3, tick 50, iterations 1; N22b-23's plant
kind); a five-row coupled task (`five-row-coupled`); the hand instance file `row1.json` for the projection
example. The script's working directory is the run's scratch `work/` (STD-E2E), so a fixture is named as
`@fixture:shield/runtime/<file>` where `frob` resolves it and through `e2e_fixture` elsewhere, never by a path
relative to the repository.

**Steps.**

Every call of a `run` verb carries `--key` (`sr-<step>-<n>`); runs that a step compares (step 6's switched
and unswitched runs, step 12's two worker counts, step 9's four batches) carry distinct keys, and the
idempotent-replay check of step 2 is the one place a key is deliberately repeated. Spellings follow the
VERBS rows and the mechanism beads: the design is positional; `--shield <id>` attaches a shield to `sim.run`,
`eval.run` and `train.start` (BD-338; the VERBS-sim, VERBS-eval and VERBS-train rows carry it).

1. `frob doctor --json`: record build and fingerprint.
2. `frob shield fit dd-base --controller baseline --tasks keepout-and-door --tier batch-cpu --key sr-2-1
   --json`.
   Assert: template `unicycle`; rows listed with their three margin parts and sources; a margin with n ≥ 999
   and α from the registry; backup `damping-injection` with a gain at or below M̄_min/h; five monitors with
   latencies; `evidence.class = "Tested"`; three flags `false`; a stable `ShieldId` on a second call with
   the same key (idempotent replay returns the stored envelope) and on a third with a new key `sr-2-2` (the
   same inputs give the same content-addressed `ShieldId`).
3. Projection example through the verb surface: `frob shield check --instance
   @fixture:shield/runtime/row1.json --key sr-3 --json` with R = I, u_π = (1, 0), box [0, 1]², row
   u₁ + u₂ ≥ 1.5. Assert the applied command (1, 0.5) and λ = 0.5.
4. Shielded run: `frob sim run dd-base --task keepout-and-door --shield <id> --tier batch-cpu --worlds 256
   --seed 11 --key sr-4 --json` (`--seed` as BD-024 defines it for `sim.run`). Assert from
   `frob shield report <id> --run <run> --json`: zero ticks
   with the true base inside the keep-out disc (from the evaluator's truth stream); intervention fraction
   above zero and below the `shield-dominated` fraction; every tick has a control layer.
5. `frob shield check <run> --shield <id> --key sr-5 --json`: assert `holds`; box violations 0; largest row residual
   within tolerance; every projected tick's command matches the independent reference.
6. Multi-row path: `frob shield fit dd-base --controller baseline --tasks three-row-coupled --tier batch-cpu
   --key sr-6-fit --json` (giving `<id3>`), then, with the conformance build of `frob` (the only build whose
   `sim.run` has `--conformance-plant`, N29a-25; no product build carries a switch for this), `frob sim run
   dd-base --task three-row-coupled --shield <id3> --tier batch-cpu --worlds 8 --seed 11 --conformance-plant
   "$(e2e_fixture shield/runtime iter1-w3-t50.json)" --key sr-6-plant --json`, whose plant forces the iteration
   budget to 1 at tick 50 in world 3 (N22b-23's plant kind `shield-iterations`), and the same run without the
   option (`--key sr-6-clean`): assert the plant listed `applied` in the receipt, a `Backup` event at that tick
   with reason from the optimality check, layer `backup` from then on in that world, and unchanged digests for
   the other worlds against the run without the plant.
7. Refusals: `frob shield fit dd-base --controller baseline --tasks five-row-coupled --key sr-7-1 --json`
   → exit code 3, FROB-REF-454, repairs "reduce the row set", "widen the actuator box", "lower the speed
   limit". `frob shield fit dd-base --controller other-baseline --tasks keepout-and-door --reuse-margin <id>
   --key sr-7-2 --json` (another controller identity) → exit code 3, FROB-REF-457, repair "recalibrate…".
8. Monitor and backup: run the low-friction world (`frob sim run dd-base-lowmu --task keepout-and-door
   --shield <id> --tier batch-cpu --key sr-8 --json`); assert an `Alarm` from the friction monitor,
   hand-over to the backup in the same tick, and from `frob telemetry energy <run> --json` that the stored
   energy at ticks is non-increasing from the hand-over (within the ledger's residual bound).
9. Drift: a stream of four `frob eval run dd-base --controller baseline --battery <family> --tier batch-cpu
   --shield <id> --key sr-9-<b> --json` batches (the controller and tier of the shield's scope key, without
   which the shield is refused with FROB-REF-457), the last two on a world family with torque limits reduced by 30%: assert the drift statistic
   crosses its threshold in the last two batches and not before, the regime is retired, and a new
   `frob shield fit … --key sr-9-refit` produces a new margin and regime.
10. Bound and report: on 500 episodes with hidden-state labels, `frob shield report <id> --json` prints the
    three numbers with intervals, the label source `hidden-state`, the scope key, and a separate row for the
    low-friction family with no bound.
11. Training bookkeeping: a short `frob train start dd-base --task keepout-and-door --backend batch-cpu
    --shield <id> --worlds 1000 --seed 11 --steps <few> --key sr-11 --json` (the backend is the tier of the
    shield's key; a training job is checked on design class, task family and tier, and the controller the
    shield was fitted for is recorded, not compared: N22b-31); assert the rollout record has `sampled_action`,
    `log_prob`, `applied_action`, `control_layer`, `shield_events`, the manifest's `shield_fitted_for` and the
    label `shield: training-stage`.
12. Determinism: repeat step 4 with `--workers 1 --key sr-12-w1` and `--workers 8 --key sr-12-w8`; assert
    identical run digests (distinct keys, so that the second is a new run, not the first one's receipt).
13. Cancellation: start `frob shield fit … --calibration 20000 --key sr-13 --json` (job handle, exit code 8),
    cancel it with `frob job cancel <job> --json`, assert no shield record was published.
14. Levels (the M4 continuation of the OPEN-SHIELD-2 script of N22b-27): assert step 2's output echoes α,
    the budget, the confidence level and their source as `cargo run -p frob-conformance --example
    shield_levels -- --json` (N22b-27; there is no `frob conformance` command) prints them; `frob shield fit
    … --calibration 998 --key sr-14-998` exits 3 with `insufficient-calibration` and the needed count 999,
    and `--calibration 999 --key sr-14-999` fits with the conformal index 999 (the largest score).
    Single source, as the script's last part: `e2e_registries_scratch` (STD-E2E: the one way a script changes
    a registry; it copies `registries/` into the run's scratch root, exports `FROB_REGISTRIES_ROOT` at the copy
    and marks the run `registries: "override"`, `gates_claimable: false`), the copy's entry edited to α = 10⁻²
    and a budget of 10⁻² (the example reads the same directory with `--root`, N22b-27; N32ax-03's scratch mark
    is on every envelope from here on);
    assert all four consumers change together: `frob shield fit` echoes 10⁻² and refits (key
    `sr-14-scratch`); the stored margin of step 2 offered with `--reuse-margin` is refused with FROB-REF-457,
    `pointer` `alpha`; `frob shield report` prints the budget 10⁻² beside the bound; the `shield_levels`
    example the gate scripts use prints 10⁻². Restore: with `FROB_REGISTRIES_ROOT` removed from the command's
    environment (`env -u`), `frob shield fit` with the inputs of step 2 (key `sr-14-restore`) gives step 2's
    `ShieldId` again.

**Logging.** NDJSON to `target/e2e-logs/shield_runtime/<utc-timestamp>.ndjson` with a transcript beside it.
Every line: `ts`, `script`, `bead` (`N22b-32`), `step`, `event` (`start`, `cmd`, `assert`, `metric`,
`refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim,
class, tier, determinism, identities, seed). `metric` lines: the projection result against (1, 0.5); box
violations against 0; row residual against tolerance; intervention and backup fractions; alarm tick and
hand-over tick; the drift statistic against its threshold per batch; the three numbers of the bound with
intervals; run digests where state is compared. `refusal` lines: code, pointer, observed, required,
repairs. On failure: the first differing value and the paths of the shield record, the run and the instance
file. Final `summary`: assertions passed and failed and `gates: ["GATE-SHIELD-02", "GATE-SHIELD-04"]`
(touched at smoke scale; the gate receipts come from the gate scripts). Step 14 puts the run under scratch
registries, so its summary says `registries: "override"` and `gates_claimable: false`: no assertion of this
script carries a `--gate` tag, which STD-E2E's linter would fail as `scratch-registries`.

## Acceptance criteria

- [ ] The script exists and passes on a clean checkout on `batch-cpu`.
- [ ] It fails (non-zero) under each of its declared plants (STD-E2E: header `plants`, switched by
      `E2E_PLANT_FAILURE` and injected by the script, checked by `run-all.sh --verify-plants`), each feeding a
      step the output of one defect: the project-then-clip result (1, 0.25) in place of step 3's; a command
      record whose projected tick carries an unchecked last iterate in place of step 6's backup; a report whose
      silent-breach count is taken from the monitor's own log (step 10); a reuse under another controller
      identity that is not refused (step 7); a reuse under the scratch α that is not refused (step 14); a
      stored-energy series that rises after the hand-over (step 8). The code mutants themselves are caught
      where they live (N22b-22, N22b-23, N22b-26, N22b-29, N22b-24) and in GATE-SHIELD-02's tier run: no product
      build can enable a mutation's feature (N38a-14).
- [ ] Every assertion of steps 2 to 14 is logged with measured and expected values, and step 14's lines carry
      `alpha`, `violation_budget`, `confidence`, `source` and the registries root in use.
- [ ] Two consecutive runs give identical assertion outcomes, `ShieldId` and run digests.
- [ ] The log validates against the harness's schema; no scene content appears in it.

## Test plan

### Unit tests

`scripts/e2e/tests/shield_runtime_selftest.sh`: runs the script against a recorded envelope set in which the
projection result is (1, 0.25); asserts a non-zero exit and a log line naming the first differing value and
the instance file.

### End-to-end script and logging

As above. Commands: `frob doctor`, `frob shield fit`, `frob shield check` (run and `--instance` forms),
`frob shield report`, `frob sim run --shield`, `frob telemetry energy`, `frob eval run --shield`, `frob train
start --shield`, `frob job cancel`, and `cargo run -p frob-conformance --example shield_levels -- [--root
<dir>] --json` (N22b-27). Every `run` call carries its own `--key`, logged on its `cmd` line.

### Known answers and negative controls

KA-571 (projection (1, 0.5)), KA-572 (backup energy non-increasing), KA-573 (policy change trips
FROB-REF-457; drift trips the alarm). CX-240 (project then clip), CX-241 (self-labelling). Determinism
lanes: twice on one machine; across worker counts; debug and release (via `FROB_BIN`); on a device where one
is present, with the filter's decisions compared at the class the backend attains.

## Considerations

- The script is a smoke test of every path, sized to finish in a few minutes on a CPU; it does not replace
  the gate campaigns and its `summary` says "smoke".
- If KILL-SHIELD fired for the wheeled class, the script's fit and report steps assert the monitor-set
  wording and the absence of a bound instead; the projection, backup and monitor steps still run because
  those parts remain in use.
- The low-friction world of step 8 violates in the monitor-only reading by design of the chapter's
  aliasing fixture; this script asserts only the alarm and the hand-over, and leaves the timeliness
  consequences to that fixture's own gate.
