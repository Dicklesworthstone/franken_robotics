## Background

Reflex has two kinds of control program. The **single-step program** (force distribution over friction cones at
the current instant) is a small dense conic program; the **predictive controller** (centroidal single-rigid-body
model-predictive control over contact cones, Frontier) solves a larger program over a horizon at each tick.
Both use the one shared symmetric-cone solver, compiled as kernels, with a fixed number of iterations in
lockstep across worlds and three end states per world (`optimal`, `infeasible`, `unconverged`).

Open question OPEN-REFLEX-1: **whether the predictive controller runs on device** (on a GPU inside the batched
step) or only on CPU tiers. Owner: the Reflex lead. Decided at M3. Fail-closed default until then: the
single-step program runs on every tier; the predictive controller runs on CPU tiers only until measured. The
question matters because a controller that runs only on the CPU cannot be used in device-resident training or
large sweeps without moving state between the device and the host every tick.

## Scope

In: one measurement of the predictive controller as device kernels against the CPU reference; the measurement
harness that runs those kernels on a device before they are admitted there; the decision rule fixed before the
measurement; the recorded decision. Out: the predictive controller itself (its pilot is
N22c-05, its mechanism is N22a-21, on which this experiment depends, and its integration is in seed bead
BD-247).

## Technical approach

1. **Register the rule first** (committed as the ADR `docs/adr/ADR-OPEN-REFLEX-1.md` with status `proposed`,
   the rule and its date, before the first measured run; DESIGN defaults, to be confirmed or changed by the
   Reflex lead before data):
   the predictive controller is admitted on a device family if all hold on the standard battery's legged
   scenarios: (a) decision-level agreement with `batch-cpu`: the same end state per world and tick in at least
   99.9% of program solves, and the same task verdict in every episode; (b) the controlled worlds' digests are
   identical run to run and across batch sizes on that device; (c) the added cost of the control stage is no
   more than 25% of the step time at the reference batch size; (d) the program's memory per world fits the
   declared device budget.
2. **Workload.** The reference quadruped under the predictive controller: horizon 0.5 s in 10 steps, the
   decision variables and cones of the pilot; 4,096 worlds; 20 s episodes; `f32` on device, `f64` and `f32` on
   `batch-cpu`.
   **Route of the runs.** The controller is made once on the CPU tier, `frob control synth <ns>-quad --class
   legged-predictive --tier batch-cpu --key or1-synth --json` (N22a-21), on the design `<ns>-quad` instantiated
   with `frob design new <ns>-quad --template quad-mammal --key or1-design --json`. The product cannot run it on a
   device before this decision (the refusal in the acceptance criteria), so the arms run through the
   measurement harness this bead builds, `crates/frob-control/examples/open_reflex_1.rs`: `cargo run -p
   frob-control --release --example open_reflex_1 -- --backend batch-cpu|gpu-cuda|gpu-metal --precision f64|f32
   --controller <ControllerId> --worlds 4096 --seconds 20 --seed <s> --stage on|off --out <dir>`. It drives the
   backend's batched step (BD-159, BD-172, BD-174) with N22a-21's lockstep kernels outside synthesis and writes
   per-world end-state arrays per tick, per-world digests, step times with the control stage on and off, and
   bytes per world. The harness is not a verb, is not in the capability table and changes no product
   behaviour. Its `batch-cpu` arm is tied to the product: `frob sim run <ns>-quad --controller <ControllerId>
   --tier batch-cpu --precision f64 --worlds 4096 --task <scenario> --seed <s> --key or1-tie-<scenario> --json`
   must give the same per-world digests bit for bit.
3. **Measure.** End-state counts per backend; the first tick at which any world's end state differs between
   backends; task verdicts; paired step time with the control stage on and off; memory per world; the residuals
   of `optimal` solves in `f32` against `f64`.
4. **Decide.** Apply the rule per device family (CUDA, Metal). Record `on-device: admitted` or `CPU tiers only`
   per family as an ADR, `docs/adr/ADR-OPEN-REFLEX-1.md` (every decision record lives in `docs/adr/`), with the
   rule as registered, the measured values with their run identities and hardware disclosure, the decision per
   family, the date and the recording session.
5. **If not admitted**, state the cause (precision of the solve in `f32`; lockstep divergence; cost) and what
   would reopen the question (for example a diagonally scaled or iteratively refined solve).

## Acceptance criteria

- [ ] The decision rule is on record, dated before the measurement.
- [ ] End-state agreement, digest invariance, added step cost and memory are recorded per device family with the hardware disclosure.
- [ ] An ADR states the decision per family; the verb registry's capability table shows the predictive controller's tiers accordingly.
- [ ] Until the ADR exists, a request to run the predictive controller on a device tier is answered as the mechanism bead N22a-21 specifies, one behaviour in both beads: `control.synth --class legged-predictive --tier <gpu tier>` returns the outcome `not-synthesizable` (exit 2, a result, as every synthesis answer is) with the reason `not-admitted-on-device` and OPEN-REFLEX-1 named; the controller never runs on the device silently.
- [ ] The single-step program is shown running on every tier in the same run (the default's first half).

## Test plan

### Unit tests
In `crates/frob-control/tests/open_reflex_1.rs`:
- `predictive_device_request_not_admitted_by_default`: before the ADR, `not-synthesizable` with reason `not-admitted-on-device`, exit 2, with the open question named; after an `admitted` ADR for a family the same request synthesizes on that family only.
- `end_state_agreement_metric`: synthetic end-state arrays with 3 differences in 10⁴ give 0.9997.
- `rule_table`: (0.9995, digests equal, 0.18, fits) → admitted; (0.995, …) → CPU only; (0.9995, digests differ) → CPU only; (0.9995, equal, 0.31) → CPU only.

### End-to-end script and logging
`scripts/e2e/open_reflex_1_predictive_on_device.sh` (sources the shared helper of STD-E2E; header `plants=
nondeterministic-reduction,rule-after-data`): checks that the proposed ADR's commit predates the first harness
output; synthesizes the controller as above; asserts the refusal before the decision (`frob control synth
<ns>-quad --class legged-predictive --tier gpu-cuda --key or1-refuse-cuda --json`, and the same on `gpu-metal`:
outcome `not-synthesizable`, exit 2, reason `not-admitted-on-device`, OPEN-REFLEX-1 named); runs the harness on
`batch-cpu` in both widths and on each available device family, each arm with an explicit seed and its own
output directory, twice and at batch sizes 1,024 and 4,096 on each device; runs the tie run above; then
compares. A family with no device present is logged `not run: no <family> device` and its decision stays the
default, never `admitted`. Log `target/e2e-logs/open_reflex_1_predictive_on_device/<utc>.ndjson` with a
transcript: every line with `ts`, `script`, `bead`, `step`, `event`; `cmd` lines with the exact command, exit
code, wall time and the evidence block with the device fingerprint; metrics `end_state_agreement` (threshold
0.999), `verdict_agreement` (every episode), `digest_invariant` (true), `tie_digests_equal` (true),
`added_step_cost` (threshold 0.25), `bytes_per_world` against the declared budget, `first_divergent_tick`, the
decision per family; on failure the first differing world and tick and the output paths; a `summary` line with
assertions passed and failed and the decision per family. Plants: `nondeterministic-reduction` (kind
`mutation`, the device build of the negative control below: the digest-invariance assertion must fail) and
`rule-after-data` (a copy of the proposed ADR dated after the first harness output: the ordering assertion must
fail).

### Known answers and negative controls
Solver known answer: the friction certificate (weight 50 N, push 30 N, μ = 0.5: y = (0.5, −1), yᵀb = −5 N) must
be returned identically on every backend. Negative control: a device build with a non-deterministic reduction
in the solver must fail the digest-invariance clause.

## Considerations

- The thresholds in the rule are DESIGN defaults proposed here; the question's owner may replace them, but only
  before the measurement.
- Single-precision conditioning of contact-like programs can be poor near rigid limits; a failure here is
  informative for the contact solver as well.
- Nothing on the critical path waits on this: the default (CPU tiers only) is sufficient for the predictive
  class's gate rows.
