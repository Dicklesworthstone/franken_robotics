## Background

Reflex has two kinds of control program. The **single-step program** (force distribution over friction cones at
the current instant) is a small dense conic program; the **predictive controller** (centroidal single-rigid-body
model-predictive control over contact cones, Frontier) solves a larger program over a horizon at each tick.
Both use the one shared symmetric-cone solver, compiled as kernels, with a fixed number of iterations in
lockstep across worlds and three end states per world (`optimal`, `infeasible`, `unconverged`).

Open question OPEN-REFLEX-1: **whether the predictive controller runs on device** (on a GPU inside the batched
step) or only on CPU tiers. Owner: the Reflex lead. Decided at M3. Fail-closed default until then: the
single-step program runs on every tier; the predictive controller runs on CPU tiers only until measured. The
question matters because a controller that runs only on the CPU cannot be used in device-resident training or
large sweeps without moving state between the device and the host every tick.

## Scope

In: one measurement of the predictive controller as device kernels against the CPU reference; the decision rule
fixed before the measurement; the recorded decision. Out: the predictive controller itself (its pilot is
N22c-05 and its integration is in seed bead BD-247).

## Technical approach

1. **Register the rule first** (DESIGN defaults, to be confirmed or changed by the Reflex lead before data):
   the predictive controller is admitted on a device family if all hold on the standard battery's legged
   scenarios: (a) decision-level agreement with `batch-cpu`: the same end state per world and tick in at least
   99.9% of program solves, and the same task verdict in every episode; (b) the controlled worlds' digests are
   identical run to run and across batch sizes on that device; (c) the added cost of the control stage is no
   more than 25% of the step time at the reference batch size; (d) the program's memory per world fits the
   declared device budget.
2. **Workload.** The reference quadruped under the predictive controller: horizon 0.5 s in 10 steps, the
   decision variables and cones of the pilot; 4,096 worlds; 20 s episodes; `f32` on device, `f64` and `f32` on
   `batch-cpu`.
3. **Measure.** End-state counts per backend; the first tick at which any world's end state differs between
   backends; task verdicts; paired step time with the control stage on and off; memory per world; the residuals
   of `optimal` solves in `f32` against `f64`.
4. **Decide.** Apply the rule per device family (CUDA, Metal). Record `on-device: admitted` or `CPU tiers only`
   per family as an ADR, with the measured values.
5. **If not admitted**, state the cause (precision of the solve in `f32`; lockstep divergence; cost) and what
   would reopen the question (for example a diagonally scaled or iteratively refined solve).

## Acceptance criteria

- [ ] The decision rule is on record, dated before the measurement.
- [ ] End-state agreement, digest invariance, added step cost and memory are recorded per device family with the hardware disclosure.
- [ ] An ADR states the decision per family; the verb registry's capability table shows the predictive controller's tiers accordingly.
- [ ] Until the ADR exists, a request to run the predictive controller on a device tier is refused with the capability-not-admitted refusal (exit 5) naming OPEN-REFLEX-1.
- [ ] The single-step program is shown running on every tier in the same run (the default's first half).

## Test plan

### Unit tests
- `predictive_device_request_refused_by_default`: before the ADR, exit 5 with the open question named.
- `end_state_agreement_metric`: synthetic end-state arrays with 3 differences in 10⁴ give 0.9997.
- `rule_table`: (0.9995, digests equal, 0.18, fits) → admitted; (0.995, …) → CPU only; (0.9995, digests differ) → CPU only; (0.9995, equal, 0.31) → CPU only.

### End-to-end script and logging
`scripts/e2e/open_reflex_1_predictive_on_device.sh`: runs the workload on `batch-cpu` and on each available
device with `frob sim run`, then compares. Logged per the shared standard: commands, exit codes, evidence
blocks with device fingerprints, `end_state_agreement` (threshold 0.999), `digest_invariant` (true),
`added_step_cost` (threshold 0.25), `bytes_per_world`, `first_divergent_tick`, the decision per family.

### Known answers and negative controls
Solver known answer: the friction certificate (weight 50 N, push 30 N, μ = 0.5: y = (0.5, −1), yᵀb = −5 N) must
be returned identically on every backend. Negative control: a device build with a non-deterministic reduction
in the solver must fail the digest-invariance clause.

## Considerations

- The thresholds in the rule are DESIGN defaults proposed here; the question's owner may replace them, but only
  before the measurement.
- Single-precision conditioning of contact-like programs can be poor near rigid limits; a failure here is
  informative for the contact solver as well.
- Nothing on the critical path waits on this: the default (CPU tiers only) is sufficient for the predictive
  class's gate rows.
