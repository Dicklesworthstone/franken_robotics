## Background
Training on a GPU simulator is fast because nothing leaves the device: the simulator writes observations into device buffers and the policy reads them there. That only works if the policy's forward pass, the backward pass and the optimizer also run on the device.

Decision **ADR-CORTEX-04**: the policy, the backward pass and the optimizer run on the device as kernels in the shared kernel dialect; the suite's Torch-like library, FrankenTorch, is the CPU trainer, the gradient oracle and the interchange format. Reason (FACT, read in `frankentorch/crates/ft-core`, `ft-nn`, `ft-optim`, `ft-serialize` at commit `8165d6a18028`): its tensors execute on the CPU only; `Device::Cuda` and `Device::Metal` are metadata; it has a reverse-mode tape with higher-order gradients, Linear, GRU, LSTM and attention modules, Adam and gradient clipping, a passing end-to-end MLP-with-Adam training test, safetensors and a limited ONNX export; it has no PPO and no `vmap`. A device tag there earns no GPU operator coverage, so the on-device learning kernels are this project's to write. An upstream work item (FD-FT-02) adds real device execution to FrankenTorch; when it lands, the on-device trainer switches to it (rule below).

The kernels are named in the kernel library's learning family: `K-gemm` (matrix product), `K-act-fn` (activation functions), `K-adam` (the optimizer step). They are written once in the shared dialect and run on three backends: `batch-cpu` (Rust symbols; the CPU reference path every capability must have), CUDA and Metal. Proof obligation **PO-CORTEX-06**: on-device backward kernels equal the FrankenTorch oracle; its verification is gate GATE-CORTEX-02.

**Precision.** Networks run in single precision. Half-precision and tensor-core paths are rejected for contact in the device chapter, and they are not adopted for policies of a few hundred units either: the arithmetic is too small to repay the risk.

Tier Solid, with kill gate **KILL-LEARNKERN** (decided in bead N23a-16, which depends on this bead's measurements). Rejected alternatives: reading observations back to the host every step and training on the CPU (loses the main source of throughput; it survives only as the kill-gate fallback with one read-back per rollout); binding a third-party GPU tensor library (violates the workspace's dependency rule and brings its own determinism behaviour).

## Scope
In: the three kernels with their manifests; the backward kernels (gradient of a matrix product, of each activation, of the losses' leaf operations); composition into forward and backward programs for dense layers; Adam with bias correction and global-norm clipping; the differential test against FrankenTorch autograd; the measurement of GATE-CORTEX-02; recording the inputs of KILL-LEARNKERN. Out: network architectures and the GRU composition (N23a-12); the PPO loss (N23a-10); the oracle bridge itself (N23a-15); the kill decision (N23a-16) and its fallback (N23a-17); wall-clock parity (GATE-CORTEX-05, another unit).

## Technical approach
**Kernel manifests.** Each kernel declares, as every kernel in the library does: its stage signature (buffers read and written with dtype, extents and the ownership epoch it reads and writes), resource bounds, the numerical contract (single precision; reduction order; neutral elements for padding) and its determinism class.

**`K-gemm`.** Y[b, o] = Σ_i X[b, i]·W[o, i] + bias[o] for a batch b of worlds (and its transposed and accumulate variants for the backward pass). The inner reduction has a *fixed order* (index order, with a declared pairwise tree for wide layers) so the result is class D2 per backend and, where the backend's algebraic kernels are bit-equal, D1. A device matrix-product path with unspecified order is allowed only under the labeled nondeterministic training profile and is a different kernel variant with its own manifest. Rows of padding worlds are masked on output (select), never skipped by branching.
**`K-act-fn`.** Elementwise ELU, tanh, sigmoid and ReLU (selected by a function constant), and their derivatives expressed in terms of the forward output where possible (tanh′ = 1 − y²; sigmoid′ = y·(1 − y); ELU′ = y + α for y < 0, 1 otherwise). Elementary functions are the backend's deterministic set.
**`K-adam`.** m ← β₁·m + (1 − β₁)·g; v ← β₂·v + (1 − β₂)·g²; m̂ = m/(1 − β₁ᵗ); v̂ = v/(1 − β₂ᵗ); θ ← θ − η·m̂/(√v̂ + ε_adam), with defaults β₁ = 0.9, β₂ = 0.999, ε_adam = 10⁻⁸, preceded by an optional global-norm clip g ← g·min(1, c/‖g‖₂) whose norm is a fixed-order reduction. The step count t and η are scalars in the control block.

**Backward programs.** For a dense layer Y = X·Wᵀ + b with upstream gradient G = ∂L/∂Y: ∂L/∂W = Gᵀ·X (a `K-gemm` over the batch with masked rows, *summed*, not averaged: the division by the valid count happens once, after cross-shard reduction), ∂L/∂b = Σ_b G, ∂L/∂X = G·W. Activations multiply by their derivative. The host side in `frob-learn` assembles a network's forward and backward as an ordered list of kernel stages in the step plan (no tape on the device): the order is derived from the `NetworkSpec` at build time, so there is no dynamic graph. Gradients are accumulated as sums with the valid-sample count carried beside them.

**The parity test (GATE-CORTEX-02).** For 10³ random batches: random layer widths (1 to 512), batch sizes (1 to 4,096), activation choice, weights from a seeded generator, random inputs and a random scalar loss head (weighted sum, squared error, or a PPO loss instance). Compute gradients with the device backward program and with FrankenTorch autograd on the CPU on the same values (transferred through the typed stride converter). Metric: max over parameters of |g_dev − g_ref| / max(|g_ref|, ‖g_ref‖_∞·10⁻³), threshold 10⁻⁵ (TARGET), for each backend including `batch-cpu`. Forward outputs are compared at the same threshold. The Adam step is compared after 10 consecutive steps.

**Switch-over rule for FD-FT-02.** Interim posture: the kernels of this bead. When FrankenTorch gains device execution for tensors and autograd, re-run GATE-CORTEX-02 with FrankenTorch on the device as the trainer under test and these kernels as the reference; if it passes and training-time parity holds, the trainer switches and these kernels remain as the differential check. No milestone waits on the upstream item.

**Kill-gate inputs.** KILL-LEARNKERN fires if GATE-CORTEX-02 fails after one repair cycle, or if the training-time parity gate (wall-clock to the return threshold at most 1.25 times an incumbent's) is missed by more than two times after one optimization pass. This bead records the first input: pass or fail, whether a repair cycle was used, and the worst relative error per backend.

**Determinism and evidence.** D2 per backend in the default variants. Evidence class `Tested`; the gate receipt names commit, hardware fingerprint and seed.

## Acceptance criteria
- [ ] GATE-CORTEX-02 (Parity, M2, TARGET) is measured and recorded with measured values: on-device backward kernels match FrankenTorch autograd within 10⁻⁵ relative on 10³ random batches, on `batch-cpu`, CUDA and Metal (the seed bead's done-condition, first half).
- [ ] The inputs of KILL-LEARNKERN from this bead are recorded (gate outcome, repair cycle used or not, worst error per backend); the decision itself is recorded as an architecture decision record by bead N23a-16, which depends on this bead (the seed bead's done-condition, second half).
- [ ] Each kernel has a manifest, a `batch-cpu` symbol and one dialect source that compiles for CUDA and Metal; a retained differential check compares each device against `batch-cpu` on the same inputs.
- [ ] `K-gemm` is bit-reproducible run to run and across worker counts and batch regroupings on each backend (class D2).
- [ ] Padding rows contribute exactly zero to every gradient sum.
- [ ] Ten Adam steps match the reference within 10⁻⁵ relative; the bias-correction terms are exercised at t = 1.
- [ ] Cancellation during an update drains and leaves no leaked device resources; weights are either the pre-update or the post-update set, never a mixture.
- [ ] Negative controls caught: a backward `K-gemm` that averages per batch instead of summing (fails parity by the batch factor); a tanh derivative using the pre-activation; Adam without bias correction (fails at t = 1); a reduction that reorders with worker count (fails the D2 lane).

## Test plan
### Unit tests
`gemm_forward_matches_reference`; `gemm_fixed_order_reproducible`; `gemm_masked_rows_zero`; `act_fn_{elu,tanh,sigmoid,relu}_forward_and_derivative` against double-precision references at 10⁴ points including zero and large magnitudes; `dense_backward_fd` (finite differences in double precision on `batch-cpu`, 10⁻⁶); `adam_ten_steps_match_reference`; `adam_bias_correction_at_t1`; `global_norm_clip_fixed_order`; `parity_1000_random_batches_{batch_cpu,cuda,metal}` (the gate loop); `device_vs_batch_cpu_differential`; `update_cancellation_atomic`.
### End-to-end script and logging
`scripts/e2e/cortex_train.sh` (bead N23a-35), step `gradient-parity`: `frob spark check --kernels learning --oracle frankentorch --batches 1000 --json` on every available backend; NDJSON `metric` lines per backend (worst relative error against threshold 10⁻⁵, batches run, failures), the hardware fingerprint, the pinned sibling commit, the seed, and on failure the batch index, layer shape and the parameter with the largest error plus a dump path for the two gradient tensors; the `summary` names GATE-CORTEX-02 and the recorded kill-gate inputs.
### Known answers and negative controls
The oracle is FrankenTorch autograd at its pinned commit, never regenerated from the candidate. The four planted defects above are registered against GATE-CORTEX-02. Metamorphic relations: scaling the loss by c scales every gradient by c; permuting batch rows leaves summed gradients unchanged bit for bit (fixed-order reduction over logical ids). Determinism lanes: twice; worker counts; debug and release on `batch-cpu`; each device in D2; cross-backend in D3 with the envelope recorded (D1 where the algebraic kernels are bit-equal).

## Considerations
- The oracle must have been admitted: the gradient-oracle use of FrankenTorch's CPU autograd is established by N23a-15; a failed admission leaves finite differences in double precision as the weaker oracle and the gate is recorded as measured against it.
- The 31-argument limit of the Metal gateway constrains how many buffers one kernel binds; weights and optimizer state are packed into few slabs.
- Wide layers and large batches make `K-gemm` the learner's hot spot; a faster nondeterministic variant exists only under the labeled D4 profile, whose results are re-evaluated before they are cited.
- If the kill gate fires, the forward kernels of this bead stay in use (the forward pass stays on the device); only the backward pass and optimizer move to the CPU.
