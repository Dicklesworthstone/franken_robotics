## Background
This is the first time the whole learning stack is asked to produce a learned behaviour: the vectorized environment, device-resident views, on-device networks and optimizer, and PPO under its rules, driven through the verbs `train.start`, `train.status`, `train.stop` and `train.export`. The task is the reference quadruped's flat velocity task: the reference quadruped template (18 degrees of freedom, 13 bodies; the workload called Q in the performance chapter) tracks a commanded planar velocity on flat ground, with joint position targets through the actuator driver loop at a 50 Hz control rate and ten physics steps per control interval.

Decision **ADR-CORTEX-08**: a training gate tests learned behaviour against negative controls, never plumbing. Reason (FACT, read in the sibling simulator's training crate): the exported checkpoint of the suite's only PPO has an all-zero policy head, and its own tracker entry says it proves model, training and export plumbing, not learned humanoid locomotion. A test that a training loop runs, exports and reloads is a plumbing test and satisfies no gate. The lesson is the gate rule (counterexample CX-257): a training gate record must hold a zero-weight policy and a random policy that both fail the same threshold, and a replay of the exported checkpoint that reproduces the behaviour.

Gate **GATE-CORTEX-01** (Known answer; M2; TARGET): PPO on the reference quadruped's flat velocity task reaches the return threshold on `batch-cpu` and on each GPU backend; a zero-weight policy and a random policy both fail the same threshold; the exported checkpoint, reloaded on `batch-cpu`, reproduces the return inside the class-D3 envelope, and its policy head is not zero.

This also demonstrates a North-Star scenario (NS-10, "the same task on a Mac"): the quadruped task trains on the Mac through Metal, results agree with the CUDA run inside the declared determinism class, and the report says which class.

Tier Solid. Wall-clock parity with an incumbent (at most 1.25 times, published context about 410 s on one RTX 4090) is a separate gate measured by another bead; this gate is about whether the behaviour is learned at all, on every backend.

## Scope
In: the training configuration for the reference task; the return threshold and its registration; the three training runs (`batch-cpu`, CUDA, Metal); the negative controls; the export, reload and replay check; the cross-backend evaluation with its declared class; the gate record. Out: the verbs themselves (N23a-14, N23a-13); the task family and its reference scorecard (BD-201, a later seed that is related and not a dependency: until it lands the task is a `.ftask` written with the task terms of BD-194, and the family's scorecard record is attached when it exists); the settled-pose cache (BD-195); wall-clock parity (GATE-CORTEX-05, BD-218) and two-card scaling (BD-199). Used here and built elsewhere: the gate-record type and its validator (N23b-15); the attainment procedure with the `crossing` and `attained` fields (N23b-33); the five-seed evaluation report with its interquartile mean, bootstrap interval and estimated-state twin (N23b-09); the sampler qualification receipt that `train.start` requires before it admits a run (written by the battery N23b-30 for the sampler N23b-29).

## Technical approach
**Configuration (DESIGN defaults; every value is in the run manifest).** Network `mlp:256,256,128`, ELU, asymmetric critic reading the task's `critic-only` channels; action law: the registry default; β = 0.5025 /s, κ = 2.565 /s (γ = 0.99, λ = 0.95 at the 20 ms interval); ε = 0.2, c_V = 0.5, five epochs, four minibatches; 24 control intervals per collection; KL-adaptive step size. Worlds: 4,096 on a GPU backend (the parity rows use 8,192 for physics-only throughput), 256 on `batch-cpu` with a correspondingly longer step budget. Reset mode explicit; profile `device-replay` (class D2). Episodes start from the settled-pose cache; randomization comes from the cards.

**The return threshold.** Registered before any gated run, in the task family's scorecard record: the mean episodic return, on the fixed development stream (held-out seeds and scenes, disjoint from training worlds, at least five seeds), that corresponds to the task's requirement being satisfied (velocity-tracking error within the task's declared scale for the declared dwell) in at least the task's target fraction of episodes. Procedure (DESIGN): the threshold value is fixed from the baseline controller's scorecard on the same stream (the synthesized legged baseline is the reference behaviour that already satisfies the requirement) as a stated fraction of its return, recorded with the baseline's identity; it is not chosen after looking at the learned policy's curve. The gate uses the attainment rule (error control over evaluation looks), not the first crossing.

**The three runs.** `frob train start quad-ref --task quad-flat-velocity --backend {batch-cpu | gpu-cuda | gpu-metal} --seed s --key bd198-tr-<backend>-<s> --json` (the design is positional and the key distinct per backend and seed, as the train.start row has them) for five seeds per backend (TARGET; `batch-cpu` may use fewer seeds at the owner's discretion, recorded). Each run ends at attainment or at its budget.

**Negative controls (same evaluation, same threshold, same stream).**
1. *Zero-weight policy*: the same network with every weight and bias zero (the action-mean output is identically zero, so the commanded joint targets are the nominal pose). Must fail the threshold.
2. *Random policy*: the same network freshly initialized from a different seed, never trained. Must fail the threshold.
3. *Replay of the exported checkpoint*: `train.export`, then load on `batch-cpu` and evaluate on the development stream. Must reproduce the device return inside the D3 envelope recorded for the backend pair (state tolerance and agreement of task decisions), and its `policy_head_norm` must be greater than zero.
A fourth check guards the controls themselves (a control that cannot fail is useless): the baseline controller on the same stream *passes* the threshold, showing the threshold is attainable and the evaluation discriminates.

**Cross-backend evaluation.** The policy trained on CUDA is evaluated on Metal and on `batch-cpu` (and the Metal-trained one on CUDA), each in a declared determinism class: D1 if the algebraic kernels are bit-equal for that pair, otherwise D3 with the decision-level agreement test; the report names the class. Only seeds, weights and receipts cross between machines.

**Estimated-state twin.** Each reported return has its twin evaluated with estimated state (the estimator in the loop) instead of privileged state where the task's actor schema allows; the gap is part of the result.

**The record (`GATE-CORTEX-01` row).** Per backend: seeds, environment steps and wall-clock to attainment (with both throughput units and the learner's share), final return with a stratified bootstrap interval of the interquartile mean, the requirement pass rate; the three controls' returns against the threshold; export digests and `policy_head_norm`; the replay return and the D3 envelope; the cross-backend classes; commit, hardware fingerprints, seeds. The record is assembled as N23b-15's training-gate record and passed through its validator; no script writes a gate status. The full-mode run of N23a-35's step `reference-training` produces the receipt, and a fresh-context session that did not implement the work enters the gate from it with `cargo run -p frob-conformance --example record_gate -- --gate GATE-CORTEX-01 --receipt <hash>`; this bead is the one that measures GATE-CORTEX-01, and N23b-15's own script tests the checker and claims no gate. A record lacking a control is refused by the gate-record rule (FROB-REF-544).

**Determinism and evidence.** Training under `device-replay` is class D2 per backend: the same seed gives the same weights digest twice. Evidence class `Tested`; nothing here is a claim about hardware.

## Acceptance criteria
- [ ] GATE-CORTEX-01 is recorded with measured values on `batch-cpu` and on each GPU backend: the trained policy attains the registered return threshold; the zero-weight and random policies both fail it; the exported checkpoint reloaded on `batch-cpu` reproduces the return inside the D3 envelope and has a non-zero policy head (the seed bead's done-condition).
- [ ] The threshold and the evaluation cadence were registered before the gated runs (the registration's commit precedes the runs' start times), and the baseline controller passes the threshold on the same stream.
- [ ] The same seed trained twice on one backend gives identical weights digests (class D2).
- [ ] The CUDA-trained policy evaluated on Metal agrees inside the declared class, and the report states the class (the North-Star scenario's check).
- [ ] Each return is reported with its estimated-state twin and the gap.
- [ ] `train.status` during the runs shows both throughput units, the learner share and the failure counts; no charged copies per step.
- [ ] Negative controls of the gate itself are caught: (a) an exported all-zero policy head presented as the trained policy fails the replay and the head-norm check; (b) a record assembled without the zero-weight control is refused; (c) a threshold lowered until the random policy passes is detected because the control then passes (the gate fails by its own rule).

## Test plan
### Unit tests
`zero_weight_policy_outputs_nominal_pose`; `random_policy_differs_from_trained_by_seed_address`; `threshold_registration_precedes_runs` (record timestamps and commits); `replay_within_d3_envelope` (on a short fixture run); `head_norm_nonzero_for_trained_zero_for_control`; `same_seed_same_weights_digest`; `estimated_state_twin_reported`; `gate_record_requires_controls` (a record object without a control fails the validator of N23b-15).
### End-to-end script and logging
`scripts/e2e/cortex_train.sh` (bead N23a-35), step `reference-training`, per available backend: `frob train start …` as above (exit 8, a job), `frob job wait`, `frob train status <job> --json`, `frob train export <job> --out policies/ --json`, `frob eval run --policy <id> --task quad-flat-velocity --tier batch-cpu --stream dev --state privileged --key bd198-ev-<id> --json`, its estimated-state twin (the same with `--state estimated`, key `bd198-ev-<id>-est`), then the control evaluations `frob eval run --policy zero:<id> …` and `--policy random:<id>:<seed> …` (N23b-15's forms; keys `bd198-ev-zero-<backend>`, `bd198-ev-random-<backend>`), the baseline evaluation, the live-dependency perturbation (the same evaluation with `--policy masked:<id>:<commanded-velocity role>`, N23b-15's form, under key `bd198-ev-masked-<backend>`), and the cross-backend evaluation. Assertions: attainment (the `attained` field, not `crossing`), both controls below threshold, baseline above, replay inside the envelope, head norm > 0, the estimated-state gap reported, the perturbed return different from the unperturbed one. NDJSON per command: exact command line, exit code, wall time, the envelope's evidence block (class, tier, determinism, identities, seed), `metric` lines with units and thresholds (return, pass rate, steps and seconds to attainment, env-steps/s and world-steps/s, learner share), digests, and on failure the first failing assertion with the run and checkpoint identifiers needed to reproduce; `summary` with counts and the gate touched. A reduced mode (`E2E_SMALL=1`) runs `batch-cpu` only with a short budget and asserts the mechanics, not attainment, and labels itself so.
### Known answers and negative controls
KA-590 (training gate controls: zero-weight, random and shuffled-label policies fail the return threshold; an exported all-zero policy head passes a plumbing test and fails this one; PPO has no teacher labels, so this gate measures the zero-weight and random clauses, and the shuffled-label clause is the distillation gate's, BD-323); CX-257. Live-dependency proof: perturbing the policy input (evaluating with the commanded velocity channel zeroed) must change the return. Determinism lanes: twice on one machine; across worker counts on `batch-cpu`; each backend against its class; cross-backend in D3 or D1 as attained.

## Considerations
- Compute: training to threshold on a GPU is minutes; on `batch-cpu` it is the slowest lane and may need the owner's approval above the default envelope of one device for one hour; if not approved, the `batch-cpu` row is recorded with a smaller world count and the attainment as measured or `not run`.
- Risk (program level): engine throughput or training time below the parity band; the kill gate for the learner kernels and the parity gate handle that, not this gate.
- The Metal row and KILL-METAL: the decision (N21b-08) depends on this bead's Metal row through BD-217, so at this bead's first run there is no decision on record and the Metal row is run and recorded if the backend exists (with whatever device label N21a-02 attaches); a later re-run reads the decision, never re-deciding it: after `fired`, the Metal row is recorded as `not run` with the ADR identifier and the gate is evaluated on the remaining backends, described by the fallback's name.
- A return is not an acceptance: acceptance of a policy is the requirement verdict in the blinded qualification lane; this gate shows only that learning works and is not an artifact of plumbing.
