## Background
A known answer is a case whose correct result is known independently of the code under test: from a closed form, an exact enumeration or a hand calculation. The program's rule is that every capability has known-answer tests against a pinned oracle that was never regenerated from the candidate, and that every gate has at least one negative control (a planted defect the test must catch; a gate that nothing can fail validates nothing). This bead is the registry of the learning subsystem's known answers: eighteen rows, KA-576 to KA-593, each with its case, its truth with the formula or value, its tolerance, the test tier and its negative control. Mechanism beads cite these numbers and also state the values inline; this registry is where they are held once, as data, so that a test, a gate record and a report all quote the same figure.

Tiers named in the rows: G1 is the known-answer tier of the conformance harness (exact or closed-form truths), G3 the convergence tier; "host" means plain host arithmetic, "lockstep" the batched tier in lockstep mode, "referee" the reference tier, "cuda" a CUDA device, "all tiers" every stepping tier. Where the source table gives the tolerance as "to set", the tolerance column below keeps that status and proposes a value (DESIGN) that the owning bead fixes when it first records its gate.

## Scope
In: the eighteen rows as machine-readable data in the suite's one registry file; the five known answers that the late subsections state without a number, entered under provisional tags KA-23-L1 to L5 with a block request for their numbers; the derivation files of the rows; a completeness test tying each row to a runner entry and each negative-control cell to a registered control. The row schema, the loader and its rules are N38a-12's (a dependency), and the number blocks are N38a-40's (a dependency); this bead writes no second loader and no file of its own. Out: the tests themselves (owned by the beads in the last column; the battery that executes every row from the user's side is N23b-18); counterexamples (N23-CX); refusal codes (N23-REF).

## Technical approach
**Storage.** The rows are appended to the suite's one physical file, `crates/frob-conformance/registry/known_answers.toml` (no chapter keeps a file of its own: the suite loader fails with `ka-second-file` on any other file named `known_answers*.toml` or any `.toml` file under a directory named `known_answers`; an earlier draft of this bead kept a chapter file of its own under such a directory, which that check refuses). One `[[ka]]` record per row, in the suite's row schema: `id`; `section` (`§23.21`, or the late subsection) with `owner` (the gate, invariant or obligation the row serves); `fixture` and `same_as`; `case`; `truth` (`kind` and `value`); `tolerance` (`exact`, `abs`, `rel`, `printed-digits`, `gate` or `to-set`); `tier` and `sites`; `control` (`text`, and the `nc` identifiers once the seeding tool has written them); `derivation` (`docs/derivations/cortex/<fixture>.md`, the chapter's subdirectory under `docs/derivations/`, which N23b-17 also writes to: it states the model, the derivation, the value with its digits and the error budget, and its front matter lists the KA identifiers it serves; rows that share a physical case share the file); `label`; `due`; `printed`; `slug`. Values that are exact are stored as exact strings (rationals such as `"4/3"`, `"32/9"`; decimals as printed). The columns of the tables below map onto the record as follows: the case → `case`; the truth → `truth`; tolerance → `tolerance` (a row printed "to set" is entered `to-set`, its DESIGN proposal goes into its derivation file, and the row is an obligation, never a pass, until the owning bead fixes the value there); tier → `tier` and `sites` (`host`, `lockstep`, `referee`, `cuda`; "all tiers" is every stepping site); negative control → `control.text`; "carried by" is not a field of the record: it names the beads that bind the row's runner entry `ka:<id>@<site>` and stays in this table and in the derivation file. KA-589 states no control; it is entered with `control.text = "none stated"` and is an obligation row that supports no gate until a control is registered. Identifiers are append-only and never renumbered.

### End-to-end script and logging
`scripts/e2e/cortex_ka_registry.sh` (header `bead=N23-KA milestone=M2 labels=cortex,registry gates=`; sources the
STD-E2E helper; NDJSON to `target/e2e-logs/cortex_ka_registry/<utc>.ndjson` with a transcript beside it). It runs
`cargo test -p frob-conformance --test registry_check` and `cargo test -p frob-conformance --test

The scripts copy it into their NDJSON `assert` lines as `ka: "KA-5xx"`, which lets a reviewer trace a log line back to this table.
### Known answers and negative controls
This bead *is* the list. Negative control for the registry itself: a planted edit of one expected value (for example 9.9 → 9.8) must make this bead's recomputation test fail, and, once the owning fixture exists (BD-192, on which this bead does not depend), that fixture too, because it reads the row through `assert_ka` and holds no copy of the value; a planted deletion of a row must make the completeness test fail.
