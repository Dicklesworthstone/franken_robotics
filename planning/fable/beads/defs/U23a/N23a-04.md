## Background
A vectorized environment steps thousands of worlds at once. Three things go wrong when worlds are identified by their position in a batch: results change when the batch is split across devices or reordered; a world cannot be replayed alone; and state that lives outside the physics (a recurrent policy's hidden state, a sensor's packet queue) is forgotten when a world is saved or reset. Rule **E-7** of the environment contract fixes identity and order:

- Worlds have *logical ids* and *per-world seeds*.
- A batch split across two devices returns in the caller's order.
- Recurrent hidden state is reset only for worlds that ended, and it is part of every checkpoint and snapshot.

`snapshot(worlds)` and `restore(snapshot)` are two of the four operations of `VecEnv` (with `reset` and `step`). They are what make replay, teleport to another tier and forks possible: a failure found in a batch of 8,192 worlds can be re-run alone, on the referee, from the tick before it went wrong.

This bead builds the identity, ordering and snapshot layer under the environment (Solid tier; `frob-learn::env`). It relies on two facts of the layers below: random draws are made *by address* (a counter-based generator keyed by the world's logical address, the stream and the draw index, so a draw does not depend on batch position, co-tenant worlds or device), and the batched step is class D2 including independence from batch size, slot, co-tenants, bucket capacity and shard count. Without those, logical identity would be a label with nothing behind it.

Rejected alternatives: identifying a world by `(device, slot)` (not stable under sharding or admission into a free slot); snapshotting physics state only (a restored recurrent policy would start from a zero hidden state and diverge; a restored world would re-deliver or lose in-flight sensor packets).

## Scope
In: `WorldId`, `WorldAddr`, `WorldMask`, `SeedPlan`; the slot table that maps logical ids to (shard, slot) and the gather that returns results in caller order; the hidden-state store and its masked reset; `Snapshot` contents, `snapshot`, `restore`, their refusals and their digest. Out: the device-side snapshot kernel and replay verbs (BD-203, BD-204); forks (BD-205); the two-device update rule (N23a-19, BD-199); the step itself (BD-192).

## Technical approach
**Identity (DESIGN).**
```rust
pub struct WorldId(pub u32);                       // logical index within a run, chosen by the caller
pub struct WorldAddr { run_seed: u64, world: u32, episode: u32 }   // names no device, shard, slot or retry
pub struct SeedPlan { run_seed: u64, per_world: SeedRule /* derived by address | explicit list */ }
pub struct WorldMask { /* bitset over logical ids, in caller order */ }
```
The episode counter of a world increments at each reset, so the address of every draw in an episode is `(run_seed, world, episode, stream, index)`. Two runs that reset worlds in a different wall-clock order therefore draw the same numbers for the same logical episode.

**Order.** The environment holds a slot table `logical id → (shard, slot)`. Every view returned to the caller (`ResetView`, `StepView`) is indexed by logical id in the caller's order: on one device this is an indexed view; across shards it is a gather into a caller-ordered staging buffer on the requesting device or, for host readers, a single ordered read. The table is part of the run manifest. Padding slots (present because a bucket's capacity exceeds the number of live worlds) have no logical id and never appear in a view.

**Recurrent state.** `HiddenStore` holds one hidden vector per world per recurrent network, on the device, in the arena's rollout slab. At a reset of mask M only the rows of worlds in M are set to the network's declared initial state; other rows are untouched. The store is included in (a) every policy checkpoint taken mid-run, (b) every snapshot, and (c) the rollout storage as the hidden state at the start of each stored step, so a minibatch that begins mid-episode can be evaluated with the right history.

**Snapshot contents.** For each requested world: physics state at the last commit fence (configuration, velocity, anchors, contact warm starts, actuator and battery state); the sensor and command packet queues with their in-flight packets and arrival instants; clock accumulators; the episode counter and the per-stream draw indices; the task program's accumulators (reward integrals for the open interval, event identities already counted, past-time monitor windows); `needs_reset` and the three flags; the final observation if the world has ended; the recurrent hidden state; the observation normalizer's version and digest (by reference); and the identities that bind the snapshot: model, scene, task, kernel library, step plan. A snapshot has a digest (BLAKE3 over a canonical encoding) and an evidence block with the tier and determinism class.

**Operations.**
1. `snapshot(&self, worlds) -> Result<Snapshot, Refusal>`: valid only at a commit fence (between steps). On a device tier the copy is the device's indexed snapshot blit, read under a host-read lease of the committed epoch.
2. `restore(&mut self, &Snapshot) -> Result<(), Refusal>`: refuses if any bound identity differs (a snapshot taken under another model, scene, task or kernel library cannot be restored), if the target slots are not free or not reset, or if the tier cannot represent the state exactly (a tolerance restore to another tier is a different operation, teleport, owned by the replay beads). After `restore`, stepping with the same actions reproduces the original digests in class D2.
3. `reset(mask, seeds, cx)`: sets flags, increments episode counters for the masked worlds, re-seeds by address, resets hidden rows, and loads the settled initial pose selected by an addressed draw.

**Determinism and evidence.** D2 per backend for snapshot-then-restore-then-step. The snapshot's digest, the slot table and the seed plan go to the ledger.

## Acceptance criteria
- [ ] Rule E-7 fixture, order: a batch of 4,096 worlds stepped on one shard and the same batch split 1,024/3,072 across two shards of `batch-cpu` return identical tensors in the caller's order for 100 steps (bitwise); a random permutation of slot assignment changes nothing in the returned views.
- [ ] Rule E-7 fixture, hidden state: with a GRU policy, resetting world 7 clears only row 7 of the hidden store; a snapshot taken mid-episode and restored reproduces the next 50 commands bit for bit; the same restore with the hidden state zeroed diverges (negative control).
- [ ] Snapshot, restore, step equals uninterrupted stepping: per-step state digests identical for 200 steps on 64 worlds, including worlds with in-flight sensor packets and an open past-time monitor window.
- [ ] A snapshot offered to an environment with a different model, task or kernel-library identity is refused with the identity that differed named.
- [ ] Per-world seeds: the same logical world in two runs with different batch sizes (64 and 8,192) and different reset orders has identical first-episode and third-episode trajectories.
- [ ] Negative controls caught: seeds derived from slot index (fails the batch-size fixture); a snapshot that omits packet queues (fails on the first late packet); a reset that clears every hidden row (fails the hidden-state fixture).

## Test plan
### Unit tests
`caller_order_across_two_shards`; `slot_permutation_invariance`; `padding_slots_never_in_views`; `hidden_reset_only_masked_rows`; `snapshot_restore_bit_equal_200_steps`; `snapshot_contains_packet_queues` (a packet sampled before the snapshot and arriving after it is delivered exactly once after restore); `snapshot_contains_monitor_windows`; `restore_refuses_identity_mismatch_{model,scene,task,kernels}`; `seed_by_address_batch_size_invariance`; `episode_counter_in_address` (third episode equal across reset orders); property test `snapshot_digest_stable_under_world_order` (the digest of a snapshot of a set of worlds does not depend on the order in which they were requested).
### End-to-end script and logging
`scripts/e2e/cortex_env.sh` (bead N23a-34), step `identity-and-snapshot`: `frob sim run --tier batch-cpu --worlds 64 --steps 100 --snapshot-at 50 --json`, then `frob sim replay --from <snapshot> --steps 50 --json`, comparing the digest chains; then the same run with `--shards 2`. NDJSON `metric` lines carry the two digest chains' heads and the first differing step on failure, the slot table's digest, the seed, and the evidence block (tier, determinism D2).
### Known answers and negative controls
The digests of uninterrupted and restored runs must be equal (exact). The three negative controls above are registered against GATE-CORTEX-06 (rule E-7). Determinism lanes: twice on one machine; across worker counts 1, 8 and all cores; debug and release on `batch-cpu`; on CUDA and Metal once the device snapshot kernels exist, each within class D2 of its own backend.

## Considerations
- Snapshot size grows with open monitor windows (up to 4,096 ticks per operator node) and packet queues; the snapshot reports its byte size, and a caller that snapshots thousands of worlds every step is steered to the chunked record instead.
- Admission of a new model variant into a free slot between chunks changes the slot table; the table's version is in every view's header so a stale table is detected.
- An asynchronous sharded collection would break caller order unless results are keyed by logical id; that variant is Frontier and outside this bead.
