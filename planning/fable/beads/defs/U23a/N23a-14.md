## Background
Training is reached through four verbs of the command surface: `train.start` (algorithm, network, devices, tying and profile are arguments), `train.status`, `train.stop` and `train.export`. The environment has no verb of its own; `train.*`, `eval.*` and `sim.run` reach it. Every verb is callable as `frob <verb> --json`, returns exactly one envelope, and is generated into the agent-facing tool surface from the same registry. This bead builds the first three (the fourth, `train.export`, is bead N23a-13) and the training job that ties collection, update, checkpoints and reporting together.

Registry rows (the verb registry of the specification): `train.start`: kind run, first milestone M2, "start training; algorithm, network, devices, tying and profile are arguments". `train.status`: kind read, M2, "return, steps, learner share and flags of a training run". `train.stop`: kind admin, M2, "stop a training run at a commit boundary". A `run` verb waits synchronously for a bounded time and otherwise returns a job handle with process exit code 8 (accepted and still running).

**Algorithms.** PPO with generalized advantage estimation, value normalization and an adaptive step size is Solid and is the only algorithm admitted at M2. The others named by the specification are Frontier: SAC; TD3; evolution strategies (which would use the sibling simulator's derivative-free optimizers through the single consumption boundary, for small policies and for tuning a handful of baseline-controller gains); teacher-student distillation from privileged to proprioceptive observations; behaviour cloning from the baseline controller as a warm start (the baseline supplies demonstrations for free). Each has a pilot against PPO on the reference task at equal wall-clock and a kill gate (KILL-ALTALGO: if the arm beats PPO neither in time to the threshold nor in final requirement pass rate, that algorithm is not built and PPO remains the trainer). The registry built here is how that rule is enforced in code: an algorithm without a recorded passed pilot cannot be started.

Tier Solid. Rejected alternatives: a long-lived interactive trainer process driven by ad hoc commands (not recoverable after a crash, not idempotent); exposing hyperparameters as free-form key-value text (unvalidated, undocumented).

## Scope
In: the three verbs with their input and output schemas; the training job on the crash-consistent job protocol (chunks, leases, cancel, restart); the algorithm registry and its admission rule; device and backend selection through the placement planner; checkpoint cadence; progress events; refusals; idempotency. Out: the PPO implementation (BD-197 and its subtasks); `train.export` and the manifest (N23a-13); placement policy, precision and the labeled profile's citation rule (N23a-18); the statistical attainment rule with the `crossing` and `attained` fields and the look table of `train.status` (N23b-33, which extends this verb's output and depends on this bead); the action sampler, its manifest and the qualification-receipt check that `train.start` calls at admission (N23b-29, a dependency; receipts are written by the battery N23b-30); the build of any algorithm other than PPO (SAC N23a-37, TD3 N23a-38, evolution strategies N23a-39, asynchronous sharding N36-12, adaptive randomization N23b-04, each behind its row of KILL-ALTALGO, decided by N23b-23); the reference training gate (BD-198); `train.family`, `train.inherit`, `train.distill` (their own beads).

## Technical approach
**`train.start` inputs (schema `frob.train.start.request/1`, DESIGN).**
| Argument | Meaning | Default |
|---|---|---|
| `task`, `design` (or `model`), `scenes` | Identities; mutable names are resolved to immutable identifiers and echoed in `bound` | required |
| `algo` | Algorithm name from the registry | `ppo` |
| `network` | `mlp:<widths>` or `gru:<hidden>`; actor/critic split from the task's access classes | `mlp:256,256,128` |
| `devices`, `backend` | `batch-cpu`, `gpu-cuda[:0,1]`, `gpu-metal`; strict or planner-chosen | planner |
| `trainer` | `device` (kernels) or `frankentorch` (CPU learner) | `device` |
| `tying` | `none`, `augmentation`, `equivariant` (the last two arrive with the symmetry beads) | `none` |
| `profile` | Determinism profile: `device-replay` (class D2) or the labeled `fast-training` (class D4) | `device-replay` |
| `action_law` | `latent-then-limit` or `clipped-with-endpoint-mass` | the registry default |
| `worlds`, `steps_per_collection`, `budget` (environment steps and/or wall seconds and/or GPU seconds) | Sizes and stop conditions | task-family defaults |
| `seed`, `idempotency_key` | Run seed; a repeated key with the same content returns the same job | required key |
| `eval_cadence`, `target` | The registered development-stream cadence and the target return or success rate | task-family defaults |
| `resume` | A mid-run checkpoint to continue from | none |

**Admission (before any device work), each failure a refusal with repairs.** The task passes the term contract; the settled-pose cache exists for the model (else the cache's refusal); the algorithm is in the registry with status `admitted`; the action sampler has a qualification receipt for the pinned kernel (the joint-law rule); the placement fits the device budget (the cost model's estimate is printed); `resume` storage was collected under the same action law (else FROB-REF-527); the profile is permitted for the caller's scopes; the budget does not exceed the session's.

**Algorithm registry (`registries/algorithms.toml`).** Rows: `name`, `tier`, `status` (`admitted` | `pilot-pending` | `killed`), `pilot` (record identifier), `kill_gate`. At M2: `ppo` admitted; `sac`, `td3`, `es`, `teacher-student`, `bc-warmstart`, `adaptive-randomization`, `async-sharding` are `pilot-pending`. Starting a `pilot-pending` or `killed` algorithm is refused as capability-not-admitted (process exit code 5) with the pilot's identifier and falsifier in the message. A row moves to `admitted` only by a recorded passed pilot.

**The job.** A training run is a job whose unit of work is one *iteration* (a collection plus a complete update plus publication of weights). The state machine `Collecting → Updating → Publishing` commits at iteration boundaries: each commit publishes a chunk record (iteration index, weights digest, statistics, digests of the environment state) under the writer's lease. A crash or a cancellation resumes from the last committed iteration and reproduces the same digests (class D2 under `device-replay`). Checkpoints (mid-run form) are written every `checkpoint_every` iterations and at stop.

**`train.status` output (schema `frob.train.status/1`).** `state`; `progress {done, total, unit}` in environment steps (always with a denominator); `eta_s` with its interval; throughput in **both units**, `env_steps_per_s` and `world_steps_per_s`; `learner_share` (fraction of wall-clock in the update, for the phase ledger); mean return and episode length on the training stream (labelled descriptive; never evidence under the D4 profile); per-look development-stream scores with the fields `crossing` and `attained` (computed by the attainment rule); counts of valid, invalid and padded samples and per-cause failures; clip fraction, KL, learning rate; charged copies per collection; flags (`trained_under: D4`, `clock-hidden`, `defaults-used`, saturation share); last committed iteration and latest checkpoint identifier; the evidence block.

**`train.stop`.** Kind admin. Requests a stop; the run finishes its current iteration (collection and update complete, weights published), writes a checkpoint and ends in state `stopped`. `--now` cancels at the next commit boundary inside the iteration and discards the partial iteration; nothing partial is ever published as a result. Idempotent.

**Envelope and exit codes.** 0 completed; 2 completed with flags; 3 refused input (the Cortex refusals 521–554); 4 budget; 5 not admitted or out of scope; 6 backend unavailable; 7 idempotency conflict; 8 accepted and still running.

**Determinism and evidence.** Under `device-replay` the run is class D2 per backend; the envelope's evidence block names class, tier, determinism, identities and seed. Under `fast-training` every output is tagged D4 and the citation rule applies.

## Acceptance criteria
- [ ] The three verbs are in the verb registry with request and response schemas, examples and refusal lists, reachable through `frob --json` and generated into the agent tool surface.
- [ ] `train.start` returns exit code 8 with a job handle within the synchronous wait bound; a repeated call with the same idempotency key and content returns the same job; the same key with different content is refused (exit code 7).
- [ ] Each admission failure listed above returns its refusal with at least one repair, before any device allocation (verified by the device allocation counter).
- [ ] Starting `algo = sac` at M2 is refused with exit code 5 and names its pilot and kill gate; `ppo` starts.
- [ ] `train.status` reports both throughput units, the learner share, the failure counts and progress with a denominator; the two throughput figures differ by exactly the task's decimation.
- [ ] `train.stop` ends the run at an iteration boundary with a loadable checkpoint; `--now` leaves no partial iteration published.
- [ ] Kill the worker process mid-iteration 100 times: the job resumes from the last committed iteration every time and the final weights digest equals the uninterrupted run's (class D2).
- [ ] Cancellation is tested: request, drain, finalize, with no leaked device resources.
- [ ] Negative controls caught: a status that reports a single unlabeled "steps per second"; a stop that publishes a half-updated weight set; an algorithm row marked admitted without a pilot record (the registry loader refuses the registry).

## Test plan
### Unit tests
`train_start_schema_validation` (each argument: type, range, unknown field refused); `train_start_idempotent_replay`; `train_start_key_conflict_exit_7`; `admission_refusals_before_allocation` (parameterized over the seven failures); `algorithm_registry_refuses_pilot_pending_exit_5`; `algorithm_registry_admitted_requires_pilot_record`; `status_both_throughput_units`; `status_progress_has_denominator`; `status_learner_share_sums` (collection share + update share + other = 1 within 1%); `stop_at_iteration_boundary`; `stop_now_discards_partial`; `crash_resume_same_digest`; `cancellation_no_leak`.
### End-to-end script and logging
`scripts/e2e/cortex_train.sh` (bead N23a-35), steps `verbs-lifecycle` and `verbs-refusals`: `frob train start --task <reference> --design <reference quadruped> --backend batch-cpu --worlds 256 --budget env_steps=200000 --seed 7 --idempotency-key e2e-1 --json` (expects exit 8); `frob train status <job> --json` polled with `frob job wait`; `frob train stop <job> --json`; a kill-and-resume cycle; then the refusal cases (`--algo sac`, a non-finite budget, a missing settled-pose cache, a resume under a different action law). NDJSON per call: exact command line, exit code, wall time, the envelope's evidence block, `metric` lines (both throughput units, learner share, failure counts), `refusal` lines (code, pointer, repairs), digests compared after resume with the first differing iteration on failure; `summary` with assertion counts.
### Known answers and negative controls
The decimation identity between the two throughput units is exact. Negative controls as listed, registered against GATE-CORTEX-01 (the gate's record is produced through these verbs). Determinism lanes: the same start twice gives the same final digest; across worker counts; kill-and-resume against uninterrupted.

## Considerations
- A training curve is a descriptive event stream; acceptance of a policy is the requirement verdict in the blinded qualification lane, never a return printed by `train.status`.
- Budgets: the default compute envelope is one device for one hour; a run that would exceed the session's envelope is refused at admission with the estimate, not stopped half-way.
- The `devices` argument with two cards uses the global normalization rule of the multi-device update; an asynchronous variant is Frontier and is refused until its pilot passes.
- Security: `train.start` accepts no code; custom reward terms are not admitted (an open safety question's default), so the task file is the only source of terms.
