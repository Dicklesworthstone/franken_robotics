## Background
FrankenTorch is the suite's Torch-like library, a sibling project consumed by path and never forked. FACT about it (read in `frankentorch/crates/ft-core`, `ft-nn`, `ft-optim`, `ft-serialize` at commit `8165d6a18028`; re-read at admission): tensors execute on the CPU only; `Device::Cuda` and `Device::Metal` are metadata; it has a reverse-mode tape with higher-order gradients, Linear, GRU, LSTM and attention modules, Adam and gradient clipping, a passing end-to-end MLP-with-Adam training test, safetensors and a limited ONNX export; it has no PPO and no `vmap`.

DESIGN: because it cannot run on a device today, the policy's forward pass, backward pass and optimizer on the device are this project's own kernels, and **FrankenTorch has three jobs**:
1. the **CPU trainer** for small runs and tests;
2. the **gradient oracle** against which the on-device backward kernels are differentially tested (the gradient-parity gate);
3. **policy interchange** through safetensors.

This bead builds the bridge that makes those three jobs possible, in `frob-learn::torch` behind the cargo feature `frankentorch`. It is Solid tier and sits at an interchange boundary with a known hazard: the suite's NumPy-like library uses signed byte strides and FrankenTorch uses unsigned element strides (FACT, confirmed in both sources); a verbatim copy of stride numbers reads the wrong element in bounds. Every tensor that crosses the bridge therefore goes through the typed stride converter admitted at M0 (bead BD-036), and no bare stride tuple crosses.

An upstream work item, **FD-FT-02** (repository: frankentorch; under that repository's own rules; priority P2): real device execution for tensors and autograd. Interim posture here: on-device learning kernels in the shared dialect, with FrankenTorch as CPU trainer, gradient oracle and interchange format. Switch-over rule: when it lands, run the gradient-parity gate with it, then switch the trainer. No milestone waits on it.

Rejected alternatives: writing an in-house reverse-mode autograd as the oracle (an oracle written by the same hands as the candidate shares its mistakes; an independent implementation from a sibling is the stronger check); using FrankenTorch as the device trainer today (it has no device execution; a device tag earns zero operator coverage).

## Scope
In: the feature-gated dependency and its admission record; tensor conversion host ↔ FrankenTorch through the stride converter; building a FrankenTorch module from a `NetworkSpec` and loading/saving its parameters; the CPU learner adapter (a loss built on FrankenTorch's tape from a pluggable loss function, an optimizer step, parameter publication), proven on a supervised fixture; the oracle interface `reference_gradients(spec, params, batch, loss) -> Gradients`; safetensors read and write with metadata; the no-sibling fallback; the record of FD-FT-02's posture and switch-over rule. Out: the PPO loss written on the tape (N23a-10, which adds it as the reference implementation of its own formulas) and the selectable CPU trainer in `train.start` (N23a-14); the device kernels (BD-196); the network description (N23a-12); the manifest content stored in the metadata (N23a-13); the kill-gate fallback trainer that uses this bridge in production (N23a-17).

## Technical approach
**Admission (never inherited).** The Metal gateway of FrankenTorch was admitted at M0 by its own tests; the host crates used here are a different surface, first relied on at M2, and are admitted at M2 by a test of their own (the rule of the suite chapter: a foundation first used at a milestone is admitted at that milestone). The admission test in `crates/frob-learn/tests/admit_frankentorch.rs` records, against the pinned commit in the stack lock: (a) the stride convention (a 2 × 2 contiguous `f32` tensor reports element strides (2, 1)); (b) reverse-mode gradients of a two-layer MLP with tanh match central finite differences in double precision within 10⁻⁶; (c) Adam's first ten steps on a quadratic match the closed-form recurrence; (d) a safetensors round trip preserves bytes and metadata; (e) GRU forward on fixed weights matches a hand-computed two-step example. A failed item is the result: the interim posture below applies and the item is filed as an upstream work item with its failing fixture.

**Conversion.** `to_ft(view: &TensorView, lease: HostRead) -> ft::Tensor` and `from_ft(&ft::Tensor) -> HostTensor`: the view is read once under its lease, converted to the unsigned-element convention (materializing with a charged copy when a stride is negative, or refusing with FROB-REF-547 under a zero-copy contract), dtype-checked (`f32` policies; `f64` only for the oracle's double-precision mode) and wrapped. No function in this module accepts raw stride numbers.

**Module twin.** `to_torch(spec, params)` builds the FrankenTorch module with the same layer order and parameter names as the device parameter layout, so that a parameter set is one ordered list of named tensors on both sides. `from_torch(module) -> params` is the inverse.

**CPU learner adapter.** `CpuLearner { module, optimizer }` with `step(batch, loss_fn) -> StepReport`: moves a host batch onto FrankenTorch tensors, evaluates `loss_fn` on the tape, back-propagates, clips by global norm, steps `ft-optim`'s Adam and returns the new parameters in device order. The loss is pluggable: this bead proves the adapter on a supervised regression fixture; bead N23a-10 supplies the PPO loss on the tape from the same formulas as the device loss (the clipped surrogate selected by the comparison of its two terms; the value loss on the current output; masked sums divided by the valid count), and bead N23a-14 exposes the result as `--trainer frankentorch`. The assembled CPU trainer is what small runs, tests and the kill-gate fallback use. Its results are class D2 on one machine.

**Oracle.** `reference_gradients` evaluates a given network and loss on given inputs on the CPU in single precision (and optionally double precision for diagnosing a disagreement) and returns gradients in the device parameter order. The oracle is pinned by the stack lock; its outputs are never regenerated from the candidate.

**Safetensors.** `write_safetensors(params, metadata: BTreeMap<String, String>, path)` and `read_safetensors(path)`, through `ft-serialize`. The metadata carries the policy manifest (schema `frob.policy/1`) as a JSON string under one key and its BLAKE3 digest under another; tensors are written in the canonical layout order with little-endian `f32`. A file whose metadata is missing or whose digest does not match is not loadable as a policy (the checkpoint bead enforces this; the bridge exposes the check).

**No-sibling fallback (interim posture if the dependency is refused or the feature is off).** The CPU trainer uses the in-house kernels on `batch-cpu`; the oracle is central finite differences in double precision on `batch-cpu`; interchange uses an in-house safetensors writer of the same layout (the format is a small, documented container). The gradient-parity gate is then recorded as measured against the weaker oracle, and the receipt says so.

**Determinism and evidence.** The oracle and CPU trainer are class D2 on one machine; outputs carry evidence class `Tested` with the sibling's commit in their identities.

## Acceptance criteria
- [ ] The admission test passes against the pinned FrankenTorch commit and its five items are recorded with measured values; the commit is in the stack lock.
- [ ] `cargo build -p frob-learn` (feature off) links no FrankenTorch crate; with the feature on, `xtask check-deps` accepts the added crates and the single shared async-runtime version rule of the workspace still holds.
- [ ] Converting the 2 × 2 fixture reads element 3 at index [1, 1]; a negative-stride view is materialized with a charged copy or refused under zero copy.
- [ ] A parameter set round-trips device → FrankenTorch → safetensors → FrankenTorch → device bit for bit, with metadata intact.
- [ ] The CPU learner adapter fits the supervised fixture (a two-layer MLP regressing a known smooth function of 8 inputs, labelled `synthetic`) to a mean squared error below 10⁻³ in a fixed number of steps, while a zero-weight network and a network trained on shuffled targets both stay above 10⁻¹ (behaviour, not plumbing).
- [ ] `reference_gradients` agrees with finite differences in double precision within 10⁻⁶ on 100 random small networks.
- [ ] With the feature off, the fallback trainer and finite-difference oracle run the same tests and the receipts label the weaker oracle.
- [ ] The posture and switch-over rule of FD-FT-02 are recorded in the crate contract and in the upstream bead's mirror.

## Test plan
### Unit tests
`admit_ft_stride_convention_elements_2_1`; `admit_ft_autograd_matches_fd`; `admit_ft_adam_ten_steps`; `admit_ft_safetensors_roundtrip`; `admit_ft_gru_two_step_hand_example`; `to_ft_reads_element_3`; `to_ft_negative_stride_materializes_or_refuses`; `params_roundtrip_bitwise`; `module_twin_parameter_order_matches_layout`; `cpu_learner_fits_regression_with_controls` (zero-weight and shuffled-target controls fail the same threshold); `oracle_matches_fd_100_networks`; `feature_off_fallback_paths`.
### End-to-end script and logging
`scripts/e2e/cortex_train.sh` (bead N23a-35), step `torch-bridge`: once the training verbs exist it runs `frob train start --backend batch-cpu --trainer frankentorch --task <reference task> --steps <small budget> --json`, `frob train export`, then a reload, and asserts the bit-exact weight round trip and the metadata digest; before that, the step runs the admission test binary and the round-trip test and logs them the same way. NDJSON: `cmd` lines, `metric` lines (the five admission items with measured values; round-trip digest equality; regression error of the fitted network and of the two controls against their thresholds), the sibling commit, seed and evidence block.
### Known answers and negative controls
The stride fixture (element 3, not 12) is the known answer of the interchange boundary. Negative controls: a verbatim stride copy (reads element 12); a safetensors file with edited metadata (digest mismatch, refused); a module twin with two layers exchanged (parameter-order test fails). Determinism lanes: twice on one machine; across worker counts; debug and release.

## Considerations
- FrankenTorch must share the workspace's single async-runtime version and toolchain; both are settled by M0 work items, and this bead only consumes the result.
- The M4 milestone also relies on FrankenTorch for policy interchange; its fallback there is that policies are exchanged in the native checkpoint format only.
- The limited ONNX export is not used; safetensors is the only interchange format.
- Risk: an oracle and a candidate that share a wrong formula (for example a loss transcribed identically on both sides) agree and are both wrong; the PPO battery's finite-difference and hand-table fixtures exist to break that symmetry.
