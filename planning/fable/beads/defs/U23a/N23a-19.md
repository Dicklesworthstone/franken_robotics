## Background
With two GPUs, each device holds a *shard* of the batch: complete worlds, replicated immutable packs (model, scene, task tables) and frozen behaviour weights. The update must be the same update a single device would have made on the whole batch. Two tempting shortcuts make it a different update:

- *Average the shard means.* One sample with gradient 1 and three with gradient 0 have global mean 0.25. On shards of sizes 1 and 3 the shard means are 1 and 0, and their average is 0.5 (counterexample CX-253).
- *Normalize with each shard's own statistics.* Shards {0, 0} and {4} have global mean 4/3 and variance 32/9; each shard's own variance is 0, so per-shard normalization divides by zero or by an arbitrary floor (counterexample CX-254).

Both errors are silent, both depend on how worlds happen to be distributed across devices (which changes with bucket sizes, invalid worlds and padding), and both make results irreproducible across layouts.

**The normalization rule** (Solid tier):
1. Each shard returns sums, not means: the sum of per-sample loss gradients and its count of valid samples.
2. Sums are reduced across shards in a fixed order and divided by the global valid count. An empty shard contributes zero and still takes part. If the global count is zero the update is skipped.
3. Advantage and observation statistics are merged from per-shard triples (n, mean μ, sum of squared deviations S) by the exact pairwise formula: n = n_a + n_b, d = μ_b − μ_a, μ = μ_a + d·n_b/n, S = S_a + S_b + d²·n_a·n_b/n. No shard normalizes with its own statistics.
4. Weights are published only after a complete update. Minibatch order is frozen for equivalence checks. An asynchronous variant needs a stated bound on version lag and is Frontier.

Proof obligation **PO-CORTEX-03**: the update is invariant to the partition into shards inside the class-D3 envelope, empty shards included; verified on 10³ random partitions. Determinism: with a fixed shard layout and reduction order the update is class D2 per backend; across layouts it is D3, with the envelope recorded.

Scaling target, for context (measured by BD-199, not here): at least 1.25 times from one RTX 4090 to two at constant global workload and equal task quality, also measured at constant load per device; the ambition is 1.6, which is also the funding threshold of the sharding kill gate. Below that, further sharding is not funded, and the second card runs independent seeds or a second design. Published context: an incumbent's own two-card run takes about 325 s against about 410 s on one card, a gain of 1.26, because compilation is not shared, the learner runs on one stream and sample efficiency falls with batch size (counterexample CX-379, "two cards train twice as fast").

Rejected alternatives: synchronizing by averaging parameters after independent updates (a different algorithm with different convergence); per-shard normalization with a correction factor (still wrong for higher moments and for empty shards).

## Technical approach
**Types (DESIGN).**
```rust
pub struct StatTriple { pub n: u64, pub mean: f64, pub ssd: f64 }     // per component, accumulated in f64
pub struct ShardSums { pub shard: ShardId, pub valid: u64, pub grad_sum: ParamVec, pub loss_sums: LossSums, pub kl_sum: f64 }
pub fn merge(a: StatTriple, b: StatTriple) -> StatTriple;             // the exact pairwise formula; identity if n = 0
pub fn reduce(shards: &[ShardSums], order: &ShardOrder) -> Option<Reduced>;  // None if the global valid count is 0
```
`merge` with n_a = 0 returns b and with n_b = 0 returns a (so an empty shard is the identity); otherwise n = n_a + n_b, d = μ_b − μ_a, μ = μ_a + d·n_b/n, S = S_a + S_b + d²·n_a·n_b/n. Variance is S/n (population form, stated in the receipt). Triples are accumulated in double precision on each shard from fixed-order masked reductions; the merge itself runs on the host in double precision in shard-id order.

**One update, numbered steps.**
1. *Freeze.* All shards hold the same behaviour weights (same digest) and finish collection; storage stays on each device.
2. *Statistics pass.* Each shard computes advantages locally, then returns `StatTriple`s for advantages (one), returns (one) and each observation component it contributed, over its valid samples only. The host merges them in shard-id order into global statistics and broadcasts (μ_A, σ_A), the value normalizer update and the observation normalizer update (the latter applies from the next collection: the normalizer is frozen during collection).
3. *Gradient passes.* For each epoch and minibatch: the global minibatch is a set of logical sample ids drawn by address (independent of the shard layout); each shard evaluates the loss on its members with the *global* normalization constants and returns `ShardSums` (sum of per-sample gradients, count of valid members, loss sums). A shard with no members returns zeros and count 0 and still replies.
4. *Reduce.* The host adds `grad_sum` across shards in shard-id order, adds counts, divides by the global valid count, clips by global norm, and performs the Adam step once (on the host, or on one device and broadcast). If the global count is zero the step is skipped and counted.
5. *Publish.* After the last minibatch of the last epoch, the new weights are written to every shard and the behaviour slot is swapped. No shard collects with unpublished weights.
The frozen minibatch order (step 3) is what makes a two-shard run comparable with a one-device run sample for sample.

**Equivalence classes.** For a fixed shard layout and reduction order: class D2 per backend (bit-identical run to run). Across layouts (one device against two shards; different splits): the sum over a different grouping differs in the last bits, so the class is D3; the envelope (maximum relative difference of the reduced gradient and of the merged statistics, and agreement of the resulting update's task decisions over a short training fixture) is recorded with the gate.

**Fixtures.**
- Gradient: per-sample gradients (1, 0, 0, 0) → 0.25 on one device and on shards of sizes 1 and 3; the mean of shard means would be 0.5.
- Statistics: shards {0, 0} and {4}: triples (2, 0, 0) and (1, 4, 0) merge to n = 3, d = 4, μ = 0 + 4·1/3 = 4/3, S = 0 + 0 + 16·2·1/3 = 32/3, variance (32/3)/3 = 32/9, exactly in rationals; each shard's own variance is 0.
- Empty shard: shards {1, 0, 0, 0} and {} give 0.25 and the same statistics as one device.
- Zero global count: all samples invalid → update skipped, counted, weights unchanged.

**Gate.** GATE-CORTEX-08 (Parity and Performance; M2; TARGET): two-shard and one-device updates agree inside the D3 envelope on 10³ random batches, an empty shard included; the 0.25 and 32/9 fixtures; strong scaling of at least 1.25 times at constant global workload and equal task quality (1.6 is the ambition and the funding threshold of the sharding kill gate). This bead measures and records the parity clauses; the scaling clause is measured by BD-199, which depends on this one.

## Acceptance criteria
- [ ] The gradient fixture returns 0.25 on one device and on shards of sizes 1 and 3; the statistics fixture returns mean 4/3 and variance 32/9 (exact against the rational values to double-precision round-off).
- [ ] PO-CORTEX-03: on 10³ random partitions of random batches into 1 to 4 shards (empty shards included, random numbers of invalid and padded samples), the reduced gradient and merged statistics agree with the one-device result inside the recorded D3 envelope (TARGET: relative difference at most 10⁻⁵ in single-precision gradients, 10⁻¹² in the double-precision statistics).
- [ ] The parity clauses of GATE-CORTEX-08 are recorded with measured values (maximum differences, number of batches, the envelope), on simulated shards on `batch-cpu` and on two physical cards where available.
- [ ] With a fixed layout and order, two runs give bit-identical reduced gradients (class D2).
- [ ] An empty shard takes part and changes nothing; a zero global count skips the update without a division by zero.
- [ ] No code path normalizes with a shard's own statistics (a structural test: the shard-side loss function takes normalization constants as arguments and has no access to local statistics).
- [ ] Negative controls caught: the mean of shard means (0.5 on the fixture); per-shard variance (0 on the fixture, or a wrong normalized advantage); a reducer whose order depends on reply arrival (fails the D2 lane); weights published to one shard before the update completes (the freeze check fails).

## Considerations
- Host-side reduction costs one transfer of a parameter-sized vector per shard per minibatch; for policies of about 10⁵ parameters that is negligible, for a multi-million-parameter transformer it is not, and the profile of BD-199 will show it.
- The statistics pass is an extra round trip per update; it can be fused with the advantage computation.
- The risk register lists the loss of two-card scaling under transfer cost as a medium risk; if the sharding kill gate fires, the two cards run as independent job lanes and this rule remains correct for any synchronous use.
- The asynchronous variant (shards delivering segments and gradient sums out of step, with a declared bound on version lag) is Frontier, runs only under the labeled nondeterministic profile and has its own pilot.
