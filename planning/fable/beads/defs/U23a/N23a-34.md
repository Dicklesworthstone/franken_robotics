## Background
The vectorized environment has no verb of its own: users and agents reach it through `sim.run`, `eval.*` and `train.*`. Its contract (explicit reset; the final observation preserved; termination distinct from truncation; invalid physics as a study error; actions checked before state changes; typed spaces; identity and order; access classes; causality), the device-resident tensor views (one stride convention; unrepresentable views; epoch-fenced reads) and the term contract (what a task must declare) are each built and unit-tested in their own beads. Unit tests prove the pieces; they do not prove that a user who runs the real binary on a real task gets those semantics. This bead is the end-to-end script that does, for one user-visible capability: *stepping worlds through the environment with correct gym semantics*.

It also shows two gates from the user's side. Each gate is measured by its Gauntlet entries (bound by the mechanism beads BD-192 and BD-193) and recorded from that run's receipt by a session that did not implement the work; this script runs those entries, repeats from the `frob` binary every check a verb can reach, and its log is cited as an evidence item of each gate's row. **GATE-CORTEX-06** (Known answer; M2; TARGET): rules E-1 to E-9 each pass their fixture; the final observation is retrievable in both reset modes; the 0 and 9.9 bootstrap fixture; the 500 against 1,000 reward fixture is invariant under rate terms. **GATE-CORTEX-09** (Known answer; M2; TARGET): the stride fixture reads element 3; the negative-stride view is materialized or refused; a stale-epoch read is refused.

Testing standard this script follows: plain shell driving the real `frob` binary on real fixtures; exit non-zero on failure; idempotent and seed-explicit; structured logs; every gate has at least one negative control, a planted defect the test must catch, because a gate that nothing can fail validates nothing.

## Scope
In: the script, its fixtures (small `.ftask` files and the reference robot), the runs of the Gauntlet entries of GATE-CORTEX-06 and GATE-CORTEX-09 with their controls, the logging, the evidence it hands to the two gate records. Out: the mechanisms themselves; the PPO and training script (N23a-35); the E-10 steps (the script of N23b-32); the Gymnasium adapter's parity run (BD-301); the fixture battery that executes every known answer of the chapter (N23b-18).

## Technical approach
**Layout.** `scripts/e2e/cortex_env.sh`; fixtures under `fixtures/cortex/env/` (tasks: `deadline-8s.ftask` with a mission deadline and terminal reward 0; `continuing-cut.ftask` with an external collection limit at the same instant; `rate-penalty-50hz.ftask`, `rate-penalty-100hz.ftask`, `step-penalty-50hz.ftask` and `step-penalty-100hz.ftask`, one file per control rate, because the control rate is the task's and `sim.run` has no input that sets it (N23b-18 runs the rate-penalty pair by these names); for the term contract, one defective task per finding of N23a-05's table (fourteen) and one task with three defects at once; the reference quadruped design). The Gauntlet has no `frob` command; the entries of a gate are run as `FROB_TEST_SEED=$E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test g1_known_answers -- <gate>` through `e2e_cmd`, and the script reads the hash-named receipt under `target/gauntlet/receipts/` (one entry per fixture with its measured value and threshold, one line per control with `caught` or `missed`). Every `frob` call of a run-kind verb carries `--key` (two runs that are compared carry distinct keys) and `--seed $E2E_SEED`. Which checks go where (DESIGN): a rule whose fixture needs a host caller of the API (stepping an ended world, injecting a non-finite action, a two-shard layout, a stale-epoch read) is asserted from the receipt, because no verb of the product does those things; everything a user can see through a verb is asserted through that verb as well.

**Steps (each a named `step` in the log).**
1. `crate-contract`: `cargo xtask check-contracts --json` (the check runs over every workspace member and takes no crate argument, N34-08; the step asserts that no finding names `frob-learn`); `frob schema --verb train.start --json` shows that verb's refusal list with the Cortex codes its registry row carries, each with exit code 3.
2. `gate-fixtures`: `FROB_TEST_SEED=$E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test g1_known_answers -- GATE-CORTEX-06`. From the receipt the script asserts one entry per rule E-1 to E-9 and per fixture, each `pass`, and in particular the three that only a host caller can provoke: `e1-explicit-reset` (a step on a batch that holds an ended world is refused with FROB-REF-521 naming the world ids; state digest unchanged); `e5-action-check` (a NaN on one channel of one world is refused with FROB-REF-522 naming world and channel; digest unchanged); `bootstrap` (targets 0 and 9.9 with V = 10 and γ = 0.99, and 0 with both flags).
3. `e2-final-observation`: the same seeded episode twice, `frob sim run <reference quadruped> --task continuing-cut --tier batch-cpu --worlds 8 --seconds 10 --reset-mode explicit --seed $E2E_SEED --key e2-explicit --json` and the same with `--reset-mode autoreset-masked --key e2-masked` (the input `reset_mode` of BD-192, a dependency, on the `sim.run` row); `frob telemetry query <run> --channels obs,final_obs --json` (no `--stream`: there is no `env` stream among N24a-36's nine, and the row lets the stream be omitted when the named channels belong to one, which `bound` echoes) extracts the ended world's `obs` (explicit) and `final_obs` (masked); they must be bit-equal, and both must differ from the post-reset `obs`. Both run manifests must state their `reset_mode`.
4. `e3-termination-vs-truncation`: `frob sim run` as in step 3 on `deadline-8s` and on `continuing-cut` (keys `e3-deadline`, `e3-cut`); from `frob telemetry query <run> --stream task --channels terminated,truncated --json` (the `task` stream carries termination against truncation, BD-090) the ended worlds of the first carry `terminated` and those of the second `truncated`. The bootstrap targets computed from those flags are the receipt entry `bootstrap` of step 2.
5. `e4-invalid-physics`: `frob sim run <reference quadruped> --task @fixture:planted-fault --tier batch-cpu --worlds 8 --seconds 2 --seed $E2E_SEED --key e4 --json` (a fixture parameter drives one world's solver to a fault) shows `invalid` for that world and counts it among the numerical faults of the outcome summary, apart from physical failures; a world that falls shows `terminated` only. That the invalid world has weight zero in a learner's statistics is the receipt entry of rule E-4.
6. `e5-action-bounds`: on a fixture task with tight action bounds, `frob sim run … --key e5` under the design's baseline controller drives one bounded channel out of range; the telemetry holds the proposed and the applied value for that channel and they differ. (The refusal of a non-finite action is the receipt entry `e5-action-check` of step 2.)
7. `typed-spaces` (E-6): `frob sim run <reference quadruped> --task <reference task> --tier batch-cpu --worlds 8 --seconds 1 --seed $E2E_SEED --key e6 --json`; the run manifest's space descriptor has unit, frame, representation, period and access class for every channel; ages across a 1/10 s sensor and a 1/50 s policy read 0 to 4 control periods.
8. `identity-and-snapshot` (E-7): `frob sim run <reference quadruped> --task <reference task> --tier batch-cpu --worlds 64 --seconds 2 --seed $E2E_SEED --key e7-run --json` (100 control intervals at 50 Hz); `frob sim replay --run <run> --world 7 --capture snapshots --key e7-snap --json` returns the snapshot hashes; `frob sim replay --run <run> --world 7 --from-snapshot <hash at interval 50> --key e7-restore --json` must exit 0 with `Bitwise` (the digest chain of the restored 50 intervals equals the original's); `frob sim replay --run <run> --world 7 --alone --key e7-alone --json` must also be `Bitwise` (the world alone against the world in its batch); and the first run repeated with `--workers 1 --key e7-w1` must give the same state digests. The two-shard caller-order fixture and the recurrent hidden state across snapshot and restore are receipt entries of rule E-7 in step 2 (a two-shard layout and a GRU policy are not reachable from `sim.run`).
9. `access-classes` (E-8): `frob train start <reference quadruped> --task <reference task> --actor-channels +friction_true --dry-run --key e8 --json`, an actor specification that names a `critic-only` channel (the input `actor_channels` of N23a-03) → exit code 3, FROB-REF-524 naming the channel; the same call without the option is admitted.
10. `causality` (E-9): `frob sense causal-test <reference quadruped> --task <reference task> --tier batch-cpu --twins all --seeds 100 --key e9 --json` (the actor is the design's baseline controller for the task, the verb's default; the twin set covers the three perturbation families: future terrain, hidden friction, undelivered measurements): verdict `pass`, zero differing commands.
11. `reward-rate`: `frob sim run <reference quadruped> --task fixtures/cortex/env/rate-penalty-50hz.ftask --tier batch-cpu --worlds 1 --seconds 10 --seed $E2E_SEED --key rr-rate-50 --json`, and the same with `rate-penalty-100hz.ftask` (key `rr-rate-100`), `step-penalty-50hz.ftask` (key `rr-step-50`) and `step-penalty-100hz.ftask` (key `rr-step-100`); the reward totals of the outcome summary are equal for the rate term and are 500 and 1,000 in magnitude for the per-step term over 10 s. KA-578 is a G3 row of N23-KA (a relation under a change of control rate), so its Gauntlet entry runs as `FROB_TEST_SEED=$E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test g3_metamorphic -- KA-578`, whose receipt entry the step compares with the four totals.
12. `throughput-units`: the receipt's `env_steps` and `world_steps` differ by exactly the decimation.
13. `tensor-views` (GATE-CORTEX-09), on `batch-cpu` and on each available device backend, through the commands of BD-193: `frob spark check --kernel view-fixtures --backend <b> --key views-<b> --json` (`<b>` in the row's spellings, `batch-cpu`, `gpu-cuda[:n]` or `gpu-metal`, mapped from the `E2E_DEVICES` entries `cpu`, `cuda:<n>` and `metal`) (the 2 × 2 fixture reads element 3; the view with byte origin 4 and byte strides (8, −4) enumerates (1, 0, 3, 2); its conversion to the unsigned-element convention is materialized with one charged copy under the default contract and is FROB-REF-547 under `zero_copy`; a host read at a not-yet-completed epoch is refused with the device layer's lease refusal FROB-REF-614, surfaced unchanged, and succeeds after the completion receipt); then the user-side refusal, `frob train start <reference quadruped> --task @fixture:reversed-channel --trainer frankentorch --zero-copy --key views-zc --json` (exit code 3, FROB-REF-547) and the same without the flag (key `views-copy`; accepted; one charged copy per collection, `charged_copies` in the `rollout` block of `frob train status`, N23a-06 and N23a-14), `--zero-copy` being BD-193's input on the `train.start` row; then `FROB_TEST_SEED=$E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test g1_known_answers -- GATE-CORTEX-09` for the gate's receipt.
14. `term-contract`: on the fourteen single-finding tasks, `frob train start <reference quadruped> --task <fixture> --dry-run --key tc-<fixture> --json` is the assertion site of the term contract, because N23a-05's admission pass runs at `train.start` and the `task.check` row does not raise `term-contract-unmet`: eleven expect exit code 3 with the refusal `term-contract-unmet` and their finding; the future-time online reward expects FROB-REF-554 with "30000"; the missing settled-pose cache expects FROB-REF-529 (an admission refusal of `train.start`); the task that names no action law is admitted with `action_law: latent-then-limit` and its default label in the envelope (N23a-05). `frob task check <fixture>.ftask --json` runs on the same fixtures first: it asserts FROB-REF-554 with "30000" on the future-time fixture (a compile-time refusal that the `task.check` row lists, BD-194), and on any fixture whose defect the row's own checks already refuse (a missing scale, FROB-REF-520) the same code at both commands, as N23a-05 states; otherwise it only logs its exit code and findings, which are BD-122's static checks and not the term contract. Then the three-defect task (all three findings in one `train.start` refusal) and the sound task (exit 0 at both commands).
15. `negative-controls`: the planted defects below cannot be built into the `frob` binary (a default or release build with the mutation umbrella enabled does not compile), so they are run by the Gauntlet: the receipt of step 2, the receipt of the same command with `-- GATE-CORTEX-09`, and the receipt of `-- GATE-CORTEX-10`, in which the 554 fixture of N23a-05 is the only entry due at M2. The script asserts with `e2e_expect_caught` that each of the eight controls has a line `caught` with its intended measured value, and exits 1 on any `missed`.
16. `gate-records`: the script writes no gate status. It prints the receipt hashes of GATE-CORTEX-06 and GATE-CORTEX-09 and the digest of its own log, which the recording session passes to `cargo run -p frob-conformance --example record_gate -- --gate <id> --receipt <hash>` and cites as evidence; it exits 1 if any control was not caught, and a disagreement between a value read through a verb and the same fixture's receipt entry is itself a failure.

**Negative controls (each a planted mutation of the owning crate behind its own Cargo feature under the `gauntlet-mutations` umbrella, which does not compile in a default or release build).** `defect-single-done` (one flag: bootstrap 0 for both cases); `defect-post-reset-only` (no final observation: the truncation fixture fails); `defect-action-check-late` (digest changes before the refusal); `defect-seed-by-slot` (batch-size invariance fails); `defect-early-delivery` (causality fails); `defect-verbatim-strides` (reads element 12); `defect-enqueued-epoch` (a stale read returns old bytes); `defect-truncate-future-window` (the 554 fixture is admitted). Each is a control of its gate in the negative-control registry with its expected failure (the first seven of GATE-CORTEX-06 and GATE-CORTEX-09; the last of GATE-CORTEX-10, N23a-05).

**Logging (the shared helper of `STD-E2E`).** NDJSON at `target/e2e-logs/cortex_env/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line: `ts`, `script`, `bead` (the bead whose mechanism the step exercises, e.g. `BD-192`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and thresholds (targets 0 and 9.9; totals 500 and 1,000; element 3; copies charged; differing commands against 0), digests where state is compared, and on failure the first differing value and the artifact paths needed to reproduce (run identifier, snapshot, the two digests). A final `summary` line gives counts of assertions passed and failed, controls caught, and the gates touched. Logs never contain private-scene data (fixtures are synthetic and labelled so).

**Modes.** Default: `batch-cpu` only, small world counts, a few minutes. With devices named in the harness's device list (for example `E2E_DEVICES=cpu,cuda:0,metal`) the script adds CUDA and Metal lanes for steps 3, 8 and 13, each against its determinism class. Seeds are explicit (`E2E_SEED`, default 20261122) and printed.

## Acceptance criteria
- [ ] The script exits 0 on a correct build and non-zero if any step fails; running it twice with one seed produces identical assertion results and identical compared digests.
- [ ] Every step above is present, logs its commands with exit codes and wall time, and asserts the stated expected values.
- [ ] The script's `summary` names the receipt hashes of GATE-CORTEX-06 and GATE-CORTEX-09 with `measured_ok: true` only when all assertions pass and all eight controls are caught; every value read through a verb agrees with the receipt entry of the same fixture; the script itself records no gate.
- [ ] Each of the eight controls is reported `caught` with the intended measured value (for example `defect-verbatim-strides` → element 12; `defect-single-done` → 0 and 0), and the harness's planted failure `E2E_PLANT_FAILURE=missed-control` (one control line rewritten to `missed` in a scratch copy of the receipt) makes the script exit 1 at step 15.
- [ ] With a GPU named in `E2E_DEVICES`, the device lanes run and each compares within its declared class; on a machine without one they are recorded as `not run` with the reason, not as passed.
- [ ] The NDJSON validates against the logging schema of the shared helper; the `summary` names both gates.
- [ ] Cancellation (SIGINT) during a step leaves no leaked device resources and a log whose last line is an `end` event with status `cancelled`.

## Test plan
### Unit tests
The script's own helpers are tested by the shared harness's self-tests; in addition `cortex_env_fixture_tasks_parse` (all fixture `.ftask` files parse; the defective ones fail admission with their intended finding) and `cortex_env_entries_complete` (the tier table has an entry naming GATE-CORTEX-06 for every rule E-1 to E-9 and for the bootstrap and reward fixtures, and an entry naming GATE-CORTEX-09 for each view fixture) run under `cargo test -p frob-conformance`.
### End-to-end script and logging
This bead is the script: `scripts/e2e/cortex_env.sh`, as specified above; run in CI in its default mode and on both machines with their devices listed in `E2E_DEVICES` before the gates are recorded by a fresh-context session.
### Known answers and negative controls
KA-576 (bootstrap 0 and 9.9), KA-577 (final observation equal across modes), KA-578 (rate totals equal; per-step totals 500 and 1,000), KA-580 (element 3; order (1, 0, 3, 2); verbatim copy reads 12), KA-581 (margins 0.5 and 1.2, in the term-contract step); counterexamples CX-246, CX-247, CX-255, CX-256. The eight negative controls above. Metamorphic relations exercised: permuting worlds permutes views only; doubling substeps leaves rate totals unchanged; re-authoring lengths in millimetres leaves the binding predicate unchanged. Determinism lanes: twice on one machine; worker counts 1 and all cores; debug and release builds of `frob`; device lanes within D2, cross-backend within D3 or D1 as attained.

## Considerations
- The script is the single place where the environment's gates are measured from the user's side; mechanism beads cite its steps instead of duplicating shell.
- Device lanes depend on hardware; a gate recorded on `batch-cpu` alone states that the device rows are `not run`.
- Fixture tasks are deliberately tiny so that the whole script stays in the fast test tier; the reference quadruped is used only where a real robot is needed (ages, causality, snapshots).
