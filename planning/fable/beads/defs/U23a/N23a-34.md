## Background
The vectorized environment has no verb of its own: users and agents reach it through `sim.run`, `eval.*` and `train.*`. Its contract (explicit reset; the final observation preserved; termination distinct from truncation; invalid physics as a study error; actions checked before state changes; typed spaces; identity and order; access classes; causality), the device-resident tensor views (one stride convention; unrepresentable views; epoch-fenced reads) and the term contract (what a task must declare) are each built and unit-tested in their own beads. Unit tests prove the pieces; they do not prove that a user who runs the real binary on a real task gets those semantics. This bead is the end-to-end script that does, for one user-visible capability: *stepping worlds through the environment with correct gym semantics*.

It also re-measures two gates from the user's side and appends confirming receipts to their records (the first record of each is made by the mechanism bead through the conformance battery). **GATE-CORTEX-06** (Known answer; M2; TARGET): rules E-1 to E-9 each pass their fixture; the final observation is retrievable in both reset modes; the 0 and 9.9 bootstrap fixture; the 500 against 1,000 reward fixture is invariant under rate terms. **GATE-CORTEX-09** (Known answer; M2; TARGET): the stride fixture reads element 3; the negative-stride view is materialized or refused; a stale-epoch read is refused.

Testing standard this script follows: plain shell driving the real `frob` binary on real fixtures; exit non-zero on failure; idempotent and seed-explicit; structured logs; every gate has at least one negative control, a planted defect the test must catch, because a gate that nothing can fail validates nothing.

## Scope
In: the script, its fixtures (small `.ftask` files and the reference robot), the conformance battery `cortex-env` it invokes, the negative-control builds, the logging, the two gate records. Out: the mechanisms themselves; the PPO and training script (N23a-35); the E-10 steps (another unit); the Gymnasium adapter's parity run.

## Technical approach
**Layout.** `scripts/e2e/cortex_env.sh`; fixtures under `fixtures/cortex/env/` (tasks: `deadline-8s.ftask` with a mission deadline and terminal reward 0; `continuing-cut.ftask` with an external collection limit at the same instant; `rate-penalty.ftask` and `step-penalty.ftask` at 50 Hz and 100 Hz; eleven defective tasks for the term contract; the reference quadruped design); the battery `cortex-env` registered in `frob-conformance` and runnable as `frob eval run --battery cortex-env [--rules …] --json`, returning one row per fixture with expected, measured, tolerance and pass.

**Steps (each a named `step` in the log).**
1. `crate-contract`: `cargo xtask check-contracts -p frob-learn`; `frob schema refusals --json` lists the twelve Cortex refusal codes with exit code 3.
2. `e1-explicit-reset`: `frob sim run --tier batch-cpu --task deadline-8s --worlds 8 --policy zero --until all-ended --json`, then one more step request without reset → exit code 3, refusal FROB-REF-521 naming the world ids; state digest unchanged.
3. `e2-final-observation`: the same seeded episode in `--reset-mode explicit` and `--reset-mode autoreset-masked`; `frob telemetry query` extracts the ended world's `obs` (explicit) and `final_obs` (masked); they must be bit-equal, and both must differ from the post-reset `obs`.
4. `e3-termination-vs-truncation` and `bootstrap`: on `deadline-8s` the flags are `terminated`; on `continuing-cut` they are `truncated`; `frob eval run --battery cortex-env --rules bootstrap` returns targets 0 and 9.9 (V = 10, γ = 0.99) and 0 with both flags.
5. `e4-invalid-physics`: a run with a planted faulting world (a fixture parameter that drives one world's solver to a fault) shows `invalid` for that world, weight zero, and the world counted in the failure summary; a world that falls shows `terminated` only.
6. `e5-action-check`: a policy file that emits NaN on one channel of one world → exit code 3, FROB-REF-522 naming world and channel; digest unchanged. A bounded channel driven out of range logs proposed and applied values.
7. `typed-spaces` (E-6): the run manifest's space descriptor has unit, frame, representation, period and access class for every channel; ages across a 1/10 s sensor and a 1/50 s policy read 0 to 4 control periods.
8. `identity-and-snapshot` (E-7): one shard against two shards, in caller order (digest chains equal); snapshot at step 50, replay 50 steps, digests equal; a GRU policy's hidden state survives snapshot and restore.
9. `access-classes` (E-8): a training start whose actor names a `critic-only` channel → exit code 3, FROB-REF-524.
10. `causality` (E-9): `frob sense causal-test --task <reference> --policy <checkpoint or zero> --tier batch-cpu --seeds 100 --json` with the three perturbation families (future terrain, hidden friction, undelivered measurements): zero differing commands.
11. `reward-rate`: `rate-penalty` totals equal at 50 Hz and 100 Hz; `step-penalty` totals 500 and 1,000 over 10 s.
12. `throughput-units`: the receipt's `env_steps` and `world_steps` differ by exactly the decimation.
13. `tensor-views` (GATE-CORTEX-09), on `batch-cpu` and on each available device backend: the 2 × 2 fixture reads element 3; the view with byte origin 4 and byte strides (8, −4) enumerates (1, 0, 3, 2) and is materialized with one charged copy, or refused with FROB-REF-547 under `--zero-copy`; a read at a not-yet-completed epoch is refused and succeeds after the completion receipt.
14. `term-contract`: `frob task check` and `frob train start --dry-run` on the eleven defective tasks (each expects its finding and exit code 3; the future-time online reward expects FROB-REF-554 with "30000") and on the sound task (exit 0).
15. `negative-controls`: re-run the relevant steps against the planted-defect builds (below) and assert that each is caught.
16. `gate-records`: append this run's measured values as a confirming receipt to the GATE-CORTEX-06 and GATE-CORTEX-09 rows (first recorded by the environment and tensor-view beads through the conformance battery) through the conformance recorder; the script refuses to write a receipt if any control was not caught, and a disagreement between this run and the first record is itself a failure.

**Negative controls (test-only variants behind `frob-conformance` features; never in a release build).** `defect-single-done` (one flag: bootstrap 0 for both cases); `defect-post-reset-only` (no final observation: the truncation fixture fails); `defect-action-check-late` (digest changes before the refusal); `defect-seed-by-slot` (batch-size invariance fails); `defect-early-delivery` (causality fails); `defect-verbatim-strides` (reads element 12); `defect-enqueued-epoch` (a stale read returns old bytes); `defect-truncate-future-window` (the 554 fixture is admitted). Each is registered in the negative-control registry with its gate and expected failure.

**Logging (the shared helper of `STD-E2E`).** NDJSON at `target/e2e-logs/cortex_env/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line: `ts`, `script`, `bead` (the bead whose mechanism the step exercises, e.g. `BD-192`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and thresholds (targets 0 and 9.9; totals 500 and 1,000; element 3; copies charged; differing commands against 0), digests where state is compared, and on failure the first differing value and the artifact paths needed to reproduce (run identifier, snapshot, the two digests). A final `summary` line gives counts of assertions passed and failed, controls caught, and the gates touched. Logs never contain private-scene data (fixtures are synthetic and labelled so).

**Modes.** Default: `batch-cpu` only, small world counts, a few minutes. `E2E_DEVICES=1`: adds CUDA and Metal lanes for steps 3, 8 and 13 where the hardware is present, each against its determinism class. Seeds are explicit (`E2E_SEED`, default 20261122) and printed.

## Acceptance criteria
- [ ] The script exits 0 on a correct build and non-zero if any step fails; running it twice with one seed produces identical assertion results and identical compared digests.
- [ ] Every step above is present, logs its commands with exit codes and wall time, and asserts the stated expected values.
- [ ] Confirming receipts for GATE-CORTEX-06 and GATE-CORTEX-09 are appended with measured values, the commit, the hardware fingerprint and the seed, only when all assertions pass and all eight controls are caught; they agree with the rows first recorded by the mechanism beads.
- [ ] Each of the eight planted-defect builds makes the script fail at the intended step with the intended measured value (for example `defect-verbatim-strides` → element 12; `defect-single-done` → 0 and 0).
- [ ] With `E2E_DEVICES=1` on a machine with a GPU, the device lanes run and each compares within its declared class; on a machine without one they are recorded as `not run` with the reason, not as passed.
- [ ] The NDJSON validates against the logging schema of the shared helper; the `summary` names both gates.
- [ ] Cancellation (SIGINT) during a step leaves no leaked device resources and a log whose last line is an `end` event with status `cancelled`.

## Test plan
### Unit tests
The script's own helpers are tested by the shared harness's self-tests; in addition `cortex_env_fixture_tasks_parse` (all fixture `.ftask` files parse; the defective ones fail admission with their intended finding) and `cortex_env_battery_rows_complete` (the battery returns a row for every rule E-1 to E-9, the bootstrap, reward and view fixtures) run under `cargo test -p frob-conformance`.
### End-to-end script and logging
This bead is the script: `scripts/e2e/cortex_env.sh`, as specified above; run in CI in its default mode and on both machines with `E2E_DEVICES=1` before the gates are recorded by a fresh-context session.
### Known answers and negative controls
KA-576 (bootstrap 0 and 9.9), KA-577 (final observation equal across modes), KA-578 (rate totals equal; per-step totals 500 and 1,000), KA-580 (element 3; order (1, 0, 3, 2); verbatim copy reads 12), KA-581 (margins 0.5 and 1.2, in the term-contract step); counterexamples CX-246, CX-247, CX-255, CX-256. The eight negative controls above. Metamorphic relations exercised: permuting worlds permutes views only; doubling substeps leaves rate totals unchanged; re-authoring lengths in millimetres leaves the binding predicate unchanged. Determinism lanes: twice on one machine; worker counts 1 and all cores; debug and release builds of `frob`; device lanes within D2, cross-backend within D3 or D1 as attained.

## Considerations
- The script is the single place where the environment's gates are measured from the user's side; mechanism beads cite its steps instead of duplicating shell.
- Device lanes depend on hardware; a gate recorded on `batch-cpu` alone states that the device rows are `not run`.
- Fixture tasks are deliberately tiny so that the whole script stays in the fast test tier; the reference quadruped is used only where a real robot is needed (ages, causality, snapshots).
