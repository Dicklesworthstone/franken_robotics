## Background
The learning stack's user-visible capability at M2 is: *start a training run, watch it, stop it, export the policy, reload it and get the same behaviour*, on the CPU reference backend and on each GPU backend, with the evidence that the behaviour was learned and is not an artifact of plumbing. The pieces (device kernels with backward passes, PPO under its eleven rules, the training verbs, checkpoints with manifests, the multi-shard update) each have unit tests and each first-record their own gate. This bead is the single end-to-end script for the capability. It drives the real `frob` binary on the real reference task, and re-measures four gates from the user's side:

- **GATE-CORTEX-07** (Known answer): the PPO battery P-1 to P-11 passes for our implementation, and three planted defects that reproduce the sibling's errors each fail it.
- **GATE-CORTEX-02** (Parity): on-device backward kernels match the reference autograd within 10⁻⁵ relative on 10³ random batches.
- **GATE-CORTEX-01** (Known answer): PPO on the reference quadruped's flat velocity task reaches the return threshold on `batch-cpu` and on each GPU backend; a zero-weight policy and a random policy both fail the same threshold; the exported checkpoint, reloaded on `batch-cpu`, reproduces the return inside the class-D3 envelope, and its policy head is not zero.
- **GATE-CORTEX-08**, parity clauses only: two-shard and one-device updates agree inside the D3 envelope, an empty shard included; the 0.25 and 32/9 fixtures. (Strong scaling on two cards is measured by the performance chapter's sharding bead.)

The rule that shapes the script (the behaviour-not-plumbing rule): a training gate is a claim about learned behaviour; its record must hold a zero-weight policy and a random policy that both fail the same threshold and a replay of the exported checkpoint that reproduces the behaviour. A test that a training loop runs, exports and reloads is a plumbing test and satisfies no gate. The script therefore never asserts "the command succeeded" as evidence of training; it asserts returns against a registered threshold with failing controls.

## Scope
In: the script; its battery invocations; its reduced and full modes; negative-control builds; logging; confirming receipts for the four gates. Out: the mechanisms; the environment script (N23a-34); wall-clock parity (BD-218); two-card scaling (BD-199); the sampler qualification battery (N23b-30, whose receipt this script needs before `train.start` admits a run) and the cadence gate (N23b-34), each with its own script; M4 capabilities (N23a-36).

## Technical approach
**Layout.** `scripts/e2e/cortex_train.sh`. The unit-level batteries are Gauntlet entries, not `eval.run` forms (KNOWN_DRIFTS 1; `eval.run` evaluates a candidate on scenarios and has no `--battery cortex-ppo`, `--rules`, `--backend` or `--impl` form, VERBS-eval): the PPO battery `cortex-ppo` is the entries of GATE-CORTEX-07 in the known-answer tier (BD-197: the rows KA-576, KA-579 and KA-582 to KA-588), run as `FROB_TEST_SEED=$E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test g1_known_answers -- <row or gate>`; the gradient-parity battery `cortex-grad` of BD-196 is the entries of GATE-CORTEX-02 in the parity tier, `FROB_TEST_SEED=$E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test g2_parity -- GATE-CORTEX-02` (oracle FrankenTorch autograd at its pinned commit, with the network cases `mlp-twin` and `gru-twin` added by N23a-12; one entry per site, `host` for `batch-cpu`, `cuda` and `metal`, a site whose device is absent `Skipped` and never passed). Each run writes a hash-named receipt under `target/gauntlet/receipts/` (one entry per fixture and site with its measured value and threshold, one line per control, `caught` or `missed`), from which the steps below assert. The device-against-CPU kernel check runs with N21b-32's flag set (`frob spark check --kernel <k> --backend <b> --key ct-sc-<k>-<b> --json` for `K-gemm`, `K-act-fn` and `K-adam`; `spark check` has no oracle flag, which is why the oracle comparison is a Gauntlet entry); the reference task and robot from the task subsystem's M2 families, `quad-ref` and `quad-flat-velocity`. Every run verb carries its own `--key` (one per step, backend and seed; two runs that are compared never share one), and every training call names the design positionally and `--task`.

**Steps (each a named `step`).**
1. `rollout-storage`: a 2,000-step run with a padded bucket and one planted invalid world; assert zero charged copies of observations or actions, the invalid count 1 and the padded count in `train.status`, and statistics equal to a dense reference run.
2. `bootstrap-and-discount`: rules P-1 and P-7, `-- KA-576` and `-- KA-579`: targets 0 and 9.9; both flags 0; γ = 0.99000 and 0.99499 at 20 and 10 ms for β = 0.5025 /s; constant-rate value 2.000·r and 1.995·r.
3. `action-law`: rule P-3, `-- KA-582` (3.15149 and 1.64872; entropy of the clipped law against quadrature), and `-- KA-586`, whose receipt carries rule P-11's part here and the P-2, P-8, P-9 and P-10 parts asserted in steps 4 and 5; from the user's side a resume under a different action law, `frob train start quad-ref --task quad-flat-velocity --resume <checkpoint> --action-law clipped-with-endpoint-mass --key ct-al-resume --json` on a checkpoint collected under `latent-then-limit` → exit code 3, FROB-REF-527.
4. `ppo-update`: rules P-4 and P-5, `-- KA-583` and `-- KA-584`, with P-2, P-9 and P-10 from the receipt of KA-586: finite differences 0, −0.5, −1 for a negative advantage (and +0.25, +0.5, 0 for a positive one); critic gradient 4·c_V; an update attempted mid-collection refused; a planted `Faulted` world changes no gradient; normalizers round-trip.
5. `sequences-and-time`: rule P-6, `-- KA-585`, with P-8 from the receipt of KA-586: two packed one-step episodes give ratios 1 and 1; 10⁴ random packings with zero non-unit ratios; value at the deadline equals the terminal reward with the clock exposed; the hidden-clock label.
6. `ppo-battery`: the whole battery, `-- GATE-CORTEX-07`, on every built site, with the planted-defect variants as the gate's controls under `gauntlet-mutations` (reversed branch → measured −0.25, −0.5, 0; stored-value critic → 0; packed-sequence read → a second ratio ≠ 1; single `done` → 0 and 0): the script asserts with `e2e_expect_caught` that each control line is `caught` with its intended measured value and exits 1 on any `missed`.
7. `gradient-parity`: `-- GATE-CORTEX-02` in `g2_parity` on `batch-cpu` and each built device site, and the three `spark check` kernel comparisons per device: worst relative error ≤ 10⁻⁵ over 10³ random batches; ten optimizer steps compared; the oracle used (FrankenTorch, or the finite-difference fallback with the gate read `not run: oracle absent`) named in every row.
8. `networks`: dry runs for `mlp:256,256,128` and `gru:128` asserting parameter counts computed in the script from the widths and schema sizes, and layout digests.
9. `torch-bridge`: the CPU trainer path (`--trainer frankentorch --backend batch-cpu`) for a short budget; export; bit-exact weight round trip through safetensors with metadata digest check.
10. `verbs-lifecycle`: `frob train start <reference quadruped> --task <reference> … --key e2e-1 --json` (exit 8); `frob train status` polled through `frob job wait`; a kill of the worker mid-iteration and a resume to the same digest as an uninterrupted twin; `frob train stop` at an iteration boundary with a loadable checkpoint; replay of the same key returns the same job. Then the verb stage of N23b-30's `sampler_joint_law.sh` (its stage 3, which that script logs `skipped` because the training verbs come after it): `frob train start quad-ref --task quad-flat-velocity --backend batch-cpu --budget env_steps=<one collection> --seed $E2E_SEED --key ct-sjl-start --json` with the qualified sampler, asserting that the job starts and that the envelope names the sampler manifest.
11. `verbs-refusals`: `--algo sac` → exit 5 naming the pilot; a non-finite budget; a missing settled-pose cache; an actor reading a privileged channel (524); an unknown field.
12. `reference-training` (GATE-CORTEX-01), per available backend: train to attainment of the registered threshold (`frob train start quad-ref --task quad-flat-velocity --backend <b> --seed <s> --key ct-ref-<b>-<s> --json`, attainment read by N23b-33's rule); evaluate the trained policy (`frob eval run quad-ref --policy <id> --task quad-flat-velocity --stream dev --key ct-ev-<b>-<s> --json`), a zero-weight policy and a random policy (`--policy zero:<id>` and `--policy random:<id>:<seed>`, N23b-15's forms, each under its own key) and the baseline controller (the same call with no `--policy`) on the development stream; export, reload on `batch-cpu`, evaluate; assert attainment, both controls below threshold, baseline above, replay inside the D3 envelope, `policy_head_norm` > 0; the same seed twice gives the same weights digest; cross-backend evaluation states its class.
13. `export-and-bind`: the exported policy evaluated on the same design with joints re-ordered (equal return) and on a design with a changed actuator direction (exit 3, FROB-REF-531).
14. `placement-and-profiles`: runs N23a-18's own script `scripts/e2e/learn_placement_profiles.sh` as a stage (its log is linked from this one), which asserts: a run under the labelled fast profile is tagged D4, made at M2 through N23a-18's `d4_job` example (no verb accepts `--determinism fast-training` until N35-06 adds it at M3; after that the step uses `frob train start … --determinism fast-training --knob learner_reduction=arrival --key ct-d4 --json`); citing its training return is refused with FROB-REF-861 at every site, before and after re-evaluation (a number observed during the D4 run); offering the un-re-evaluated policy to the training-gate record builder (N23a-18's `gate_record` example binary) is refused with FROB-REF-867; after an `eval.run` of the same weights under `device-replay` the re-evaluated figure is citable; physics digests equal across profiles; learner and inference shares reported from device receipts.
15. `two-shard-update` (GATE-CORTEX-08 parity clauses): runs N23a-19's own script `scripts/e2e/learn_shard_merge.sh` as a stage (the fixtures `-- KA-587` and `-- KA-588`, 0.25 and mean 4/3 with variance 32/9, and `-- GATE-CORTEX-08` in `g2_parity`, the tier of a parity gate), then the user-side comparison that needs `train.start`: `frob train start quad-ref --task quad-flat-velocity --backend batch-cpu --shards 2 --worlds 512 --budget env_steps=100000 --seed 7 --key shard-2 --json` beside the same with `--shards 1 --key shard-1` (each followed by `frob job wait`; and `--backend gpu-cuda:0,1 --shards 2` where both cards are present), comparing per-update reduced-gradient digests inside the recorded D3 envelope and final returns; an empty shard included.
16. `negative-controls`: the gate-level controls: an all-zero policy head exported as trained (fails replay and head-norm); a record assembled without the zero-weight control (refused); a backward kernel that averages instead of summing (fails parity, a control line of step 7's receipt); the mean of shard means (0.5 on the fixture, a control line of step 15's receipt).
17. `gate-records`: the script writes no gate record (KNOWN_DRIFTS 9). Each gate is recorded by its carrier in the register (N23b-16): GATE-CORTEX-01 by BD-198, -02 by BD-196, -07 by BD-197, the parity clauses of -08 by N23a-19, each from a receipt by a session that did not implement the mechanism, with `cargo run -p frob-conformance --example record_gate -- --gate <id> --receipt <hash>`. The script prints the hashes of the receipts it produced (the Gauntlet receipts of steps 2 to 7 and 15, and in full mode the training-gate receipt of step 12) with its log's digest, for those sessions to record or cite as confirming evidence; it exits 1 if any control was not caught or if a measured value disagrees with the gate's first record.

**Modes.** `E2E_SMALL=1` (default in CI): `batch-cpu` only; steps 1 to 11 and 13 to 16 in full; step 12 with a short budget that asserts the mechanics (controls evaluated; export, reload and replay equal; head norm > 0) and labels its result `mechanics-only: threshold not asserted`; no gate receipt for GATE-CORTEX-01 is written in this mode. Full mode (`E2E_SMALL=0`, on the two machines): all backends, training to attainment, five seeds on GPU backends. Seeds explicit (`E2E_SEED`).

**Logging (the shared helper of `STD-E2E`).** NDJSON at `target/e2e-logs/cortex_train/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`, `bead` (the bead whose mechanism the step exercises), `step`, `event`, the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and thresholds (returns against the registered threshold; steps and seconds to attainment; `env_steps_per_s` and `world_steps_per_s`; learner share; worst gradient error against 10⁻⁵; fixture values against their expected numbers), digests where state is compared (weights, storage, resume), and on failure the first differing value and the artifact paths needed to reproduce (run, checkpoint and policy identifiers; the fixture inputs). A final `summary` gives assertions passed and failed, controls caught and gates touched. Training curves are logged as descriptive metrics and are never asserted on under the fast profile. No private-scene data is logged.

## Acceptance criteria
- [ ] The script exits 0 on a correct build in both modes and non-zero if any step fails; two runs with one seed in small mode give identical assertion results and identical compared digests.
- [ ] Every step is present with its commands, exit codes, wall time and the stated assertions.
- [ ] In full mode, the script's receipts for GATE-CORTEX-01, -02, -07 and the parity clauses of -08 carry measured values, commit, hardware fingerprints and seeds, agree with the first records, and are printed for the carriers' recording sessions; the script itself writes no gate record.
- [ ] Each planted-defect build fails the script at the intended step with the intended measured value.
- [ ] The small mode never writes a GATE-CORTEX-01 receipt and labels its training step as mechanics-only.
- [ ] Cancellation during training drains and finalizes: no leaked device resources, a resumable job, and a log ending in a `cancelled` end event.
- [ ] The NDJSON validates against the shared logging schema and its `summary` names the gates touched.

## Test plan
### Unit tests
`cortex_ppo_battery_rows_complete` (a row for every rule P-1 to P-11 and each control); `cortex_train_fixture_identities_resolve` (the reference task, robot and scenes exist and are admitted); `parameter_count_formula_in_script_matches_library` (the script's arithmetic for the two networks equals the library's count).
### End-to-end script and logging
This bead is the script: `scripts/e2e/cortex_train.sh`, as specified; small mode in CI, full mode on both machines before the gates' confirming receipts are written by a fresh-context session.
### Known answers and negative controls
KA-576, KA-579, KA-582, KA-583, KA-584, KA-585, KA-586, KA-587, KA-588, KA-590; counterexamples CX-246, CX-248 to CX-254, CX-257. Negative controls: the four battery defects, the four gate-level controls of step 16. Live-dependency proof in step 12: evaluating the trained policy with the commanded-velocity channel zeroed (`--policy masked:<id>:<commanded-velocity role>`, N23b-15's form, key `ct-ev-masked-<b>`) must change the return. Determinism lanes: twice on one machine; worker counts; debug and release; each backend within D2; cross-backend D3 or D1 as attained; kill-and-resume against uninterrupted.

## Considerations
- Full mode needs GPU time (training to threshold on each backend, several seeds) and, for `batch-cpu`, possibly the owner's approval above the default envelope; rows that cannot run are recorded `not run` with the reason.
- If the learner-kernel kill gate fired (N23a-16's ADR reads `fired`), the script's device-trainer steps run with the fallback trainer (`--trainer cpu-readback`, N23a-17) and say so in every line's evidence block; the gradient-parity step still runs as a differential test. The script reads the outcome from `registries/defaults.toml` `train.trainer`, so it runs before the decision (its first records feed it) and after it.
- The script is the place where a plumbing-only "success" would be most tempting to accept; its small mode is explicitly barred from writing the behavioural gate's receipt.
