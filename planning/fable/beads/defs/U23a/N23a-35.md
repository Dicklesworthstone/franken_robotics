## Background
The learning stack's user-visible capability at M2 is: *start a training run, watch it, stop it, export the policy, reload it and get the same behaviour*, on the CPU reference backend and on each GPU backend, with the evidence that the behaviour was learned and is not an artifact of plumbing. The pieces (device kernels with backward passes, PPO under its eleven rules, the training verbs, checkpoints with manifests, the multi-shard update) each have unit tests and each first-record their own gate. This bead is the single end-to-end script for the capability. It drives the real `frob` binary on the real reference task, and re-measures four gates from the user's side:

- **GATE-CORTEX-07** (Known answer): the PPO battery P-1 to P-11 passes for our implementation, and three planted defects that reproduce the sibling's errors each fail it.
- **GATE-CORTEX-02** (Parity): on-device backward kernels match the reference autograd within 10⁻⁵ relative on 10³ random batches.
- **GATE-CORTEX-01** (Known answer): PPO on the reference quadruped's flat velocity task reaches the return threshold on `batch-cpu` and on each GPU backend; a zero-weight policy and a random policy both fail the same threshold; the exported checkpoint, reloaded on `batch-cpu`, reproduces the return inside the class-D3 envelope, and its policy head is not zero.
- **GATE-CORTEX-08**, parity clauses only: two-shard and one-device updates agree inside the D3 envelope, an empty shard included; the 0.25 and 32/9 fixtures. (Strong scaling on two cards is measured by the performance chapter's sharding bead.)

The rule that shapes the script (the behaviour-not-plumbing rule): a training gate is a claim about learned behaviour; its record must hold a zero-weight policy and a random policy that both fail the same threshold and a replay of the exported checkpoint that reproduces the behaviour. A test that a training loop runs, exports and reloads is a plumbing test and satisfies no gate. The script therefore never asserts "the command succeeded" as evidence of training; it asserts returns against a registered threshold with failing controls.

## Scope
In: the script; its battery invocations; its reduced and full modes; negative-control builds; logging; confirming receipts for the four gates. Out: the mechanisms; the environment script (N23a-34); wall-clock parity (BD-218); two-card scaling (BD-199); the sampler qualification battery (N23b-30, whose receipt this script needs before `train.start` admits a run) and the cadence gate (N23b-34), each with its own script; M4 capabilities (N23a-36).

## Technical approach
**Layout.** `scripts/e2e/cortex_train.sh`; the conformance battery `cortex-ppo` (`frob eval run --battery cortex-ppo [--rules …] --json`); the kernel check `frob spark check --kernels learning --oracle frankentorch --batches 1000 --json`; the reference task and robot from the task subsystem's M2 families.

**Steps (each a named `step`).**
1. `rollout-storage`: a 2,000-step run with a padded bucket and one planted invalid world; assert zero charged copies of observations or actions, the invalid count 1 and the padded count in `train.status`, and statistics equal to a dense reference run.
2. `bootstrap-and-discount`: battery rules P-1 and P-7: targets 0 and 9.9; both flags 0; γ = 0.99000 and 0.99499 at 20 and 10 ms for β = 0.5025 /s; constant-rate value 2.000·r and 1.995·r.
3. `action-law`: battery rules P-3 and P-11: 3.15149 and 1.64872; entropy of the clipped law against quadrature; a resume under a different action law → exit code 3, FROB-REF-527.
4. `ppo-update`: battery rules P-2, P-4, P-5, P-9, P-10: finite differences 0, −0.5, −1 for a negative advantage (and +0.25, +0.5, 0 for a positive one); critic gradient 4·c_V; an update attempted mid-collection refused; a planted `Faulted` world changes no gradient; normalizers round-trip.
5. `sequences-and-time`: battery rules P-6 and P-8: two packed one-step episodes give ratios 1 and 1; 10⁴ random packings with zero non-unit ratios; value at the deadline equals the terminal reward with the clock exposed; the hidden-clock label.
6. `ppo-battery`: the whole battery on each available backend, then the planted-defect builds (reversed branch → measured −0.25, −0.5, 0; stored-value critic → 0; packed-sequence read → a second ratio ≠ 1; single `done` → 0 and 0), each of which must fail at its rule.
7. `gradient-parity`: the kernel check on `batch-cpu` and each device: worst relative error ≤ 10⁻⁵ over 10³ random batches; ten optimizer steps compared.
8. `networks`: dry runs for `mlp:256,256,128` and `gru:128` asserting parameter counts computed in the script from the widths and schema sizes, and layout digests.
9. `torch-bridge`: the CPU trainer path (`--trainer frankentorch --backend batch-cpu`) for a short budget; export; bit-exact weight round trip through safetensors with metadata digest check.
10. `verbs-lifecycle`: `frob train start … --idempotency-key e2e-1 --json` (exit 8); `frob train status` polled through `frob job wait`; a kill of the worker mid-iteration and a resume to the same digest as an uninterrupted twin; `frob train stop` at an iteration boundary with a loadable checkpoint; replay of the same key returns the same job.
11. `verbs-refusals`: `--algo sac` → exit 5 naming the pilot; a non-finite budget; a missing settled-pose cache; an actor reading a privileged channel (524); an unknown field.
12. `reference-training` (GATE-CORTEX-01), per available backend: train to attainment of the registered threshold; evaluate the trained policy, a zero-weight policy, a random policy and the baseline controller on the development stream; export, reload on `batch-cpu`, evaluate; assert attainment, both controls below threshold, baseline above, replay inside the D3 envelope, `policy_head_norm` > 0; the same seed twice gives the same weights digest; cross-backend evaluation states its class.
13. `export-and-bind`: the exported policy evaluated on the same design with joints re-ordered (equal return) and on a design with a changed actuator direction (exit 3, FROB-REF-531).
14. `placement-and-profiles`: a run under the labelled fast profile is tagged D4; citing its training return is refused (FROB-REF-867) until a re-evaluation under the deterministic profile exists; physics digests equal across profiles; learner and inference shares reported from device receipts.
15. `two-shard-update` (GATE-CORTEX-08 parity clauses): battery rule P-10 fixtures (0.25; mean 4/3 and variance 32/9); a 512-world training with `--shards 2` against `--shards 1` on `batch-cpu` (and `gpu-cuda:0,1` where both cards are present): reduced-gradient differences inside the recorded envelope; an empty shard included.
16. `negative-controls`: the gate-level controls: an all-zero policy head exported as trained (fails replay and head-norm); a record assembled without the zero-weight control (refused); a backward kernel that averages instead of summing (fails parity); the mean of shard means (0.5 on the fixture).
17. `gate-records`: append confirming receipts for GATE-CORTEX-07, -02, -01 and -08 (parity clauses) with measured values; refuse to write if any control was not caught or if this run disagrees with the first record.

**Modes.** `E2E_SMALL=1` (default in CI): `batch-cpu` only; steps 1 to 11 and 13 to 16 in full; step 12 with a short budget that asserts the mechanics (controls evaluated; export, reload and replay equal; head norm > 0) and labels its result `mechanics-only: threshold not asserted`; no gate receipt for GATE-CORTEX-01 is written in this mode. Full mode (`E2E_SMALL=0`, on the two machines): all backends, training to attainment, five seeds on GPU backends. Seeds explicit (`E2E_SEED`).

**Logging (the shared helper of `STD-E2E`).** NDJSON at `target/e2e-logs/cortex_train/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`, `bead` (the bead whose mechanism the step exercises), `step`, `event`, the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with units and thresholds (returns against the registered threshold; steps and seconds to attainment; `env_steps_per_s` and `world_steps_per_s`; learner share; worst gradient error against 10⁻⁵; fixture values against their expected numbers), digests where state is compared (weights, storage, resume), and on failure the first differing value and the artifact paths needed to reproduce (run, checkpoint and policy identifiers; the fixture inputs). A final `summary` gives assertions passed and failed, controls caught and gates touched. Training curves are logged as descriptive metrics and are never asserted on under the fast profile. No private-scene data is logged.

## Acceptance criteria
- [ ] The script exits 0 on a correct build in both modes and non-zero if any step fails; two runs with one seed in small mode give identical assertion results and identical compared digests.
- [ ] Every step is present with its commands, exit codes, wall time and the stated assertions.
- [ ] In full mode, confirming receipts for GATE-CORTEX-01, -02, -07 and the parity clauses of -08 are appended with measured values, commit, hardware fingerprints and seeds, and agree with the first records.
- [ ] Each planted-defect build fails the script at the intended step with the intended measured value.
- [ ] The small mode never writes a GATE-CORTEX-01 receipt and labels its training step as mechanics-only.
- [ ] Cancellation during training drains and finalizes: no leaked device resources, a resumable job, and a log ending in a `cancelled` end event.
- [ ] The NDJSON validates against the shared logging schema and its `summary` names the gates touched.

## Test plan
### Unit tests
`cortex_ppo_battery_rows_complete` (a row for every rule P-1 to P-11 and each control); `cortex_train_fixture_identities_resolve` (the reference task, robot and scenes exist and are admitted); `parameter_count_formula_in_script_matches_library` (the script's arithmetic for the two networks equals the library's count).
### End-to-end script and logging
This bead is the script: `scripts/e2e/cortex_train.sh`, as specified; small mode in CI, full mode on both machines before the gates' confirming receipts are written by a fresh-context session.
### Known answers and negative controls
KA-576, KA-579, KA-582, KA-583, KA-584, KA-585, KA-586, KA-587, KA-588, KA-590; counterexamples CX-246, CX-248 to CX-254, CX-257. Negative controls: the four battery defects, the four gate-level controls of step 16. Live-dependency proof in step 12: evaluating the trained policy with the commanded-velocity channel zeroed must change the return. Determinism lanes: twice on one machine; worker counts; debug and release; each backend within D2; cross-backend D3 or D1 as attained; kill-and-resume against uninterrupted.

## Considerations
- Full mode needs GPU time (training to threshold on each backend, several seeds) and, for `batch-cpu`, possibly the owner's approval above the default envelope; rows that cannot run are recorded `not run` with the reason.
- If the learner-kernel kill gate fired, the script's device-trainer steps run with the fallback trainer and say so in every line's evidence block; the gradient-parity step still runs as a differential test.
- The script is the place where a plumbing-only "success" would be most tempting to accept; its small mode is explicitly barred from writing the behavioural gate's receipt.
