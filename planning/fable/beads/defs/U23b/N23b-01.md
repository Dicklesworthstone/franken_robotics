## Background

Every Frontier and Moonshot mechanism of FrankenRobotics has a pilot: a small experiment with existing tools,
outside the workspace, that runs before the mechanism's work package is funded. A pilot record states the
mechanism and tier, the protocol frozen before execution, the falsifier, the computed ceiling of the benefit, the
fallback and kill gate, the cost, the tool and its pin, and then the result. A work package whose pilot's
falsifier holds is not funded and its fallback ships. The reason for the rule: in every pilot run at planning time
the strong baseline tied or won, so a mechanism is not assumed to pay.

This pilot is for the geometric-algebra tree policy, a Moonshot variant of the family policy in which link tokens
carry multivector features and layers are equivariant to gravity-preserving rigid motions and to relabelling, with
message passing along the kinematic tree (epic BD-439). The published evidence gives no reason to expect more
than 1.3 times, and several reasons to expect nothing: such layers ran 1.4 to 7.5 times slower per epoch, a pure
geometric-algebra network converged too slowly as a control network, and canonical inputs with augmentation
recover most of the invariance (FACT, source register; to be re-read).

## Scope

In: the frozen protocol, the three arms, the run on an incumbent learning stack and simulator at pinned
revisions, the record, and the reading of the falsifier.
Out: any code in the FrankenRobotics workspace; the comparison at scale on our engine (BD-439); the decision
(N23b-02).

## Technical approach

**Protocol (frozen in the pilot record before the first run).**

1. *Embodiment set.* One morphology class (quadruped-like legged). A training set of generated designs and a
   held-out set, both from one stated distribution (class template, limb lengths and masses perturbed within ±20
   to ±30%); the same sets for every arm. Where the family-policy pilot N23b-19 has run, its design sets and its
   arm-A network are reused, which also makes arm A the strongest available control.
2. *Arms.* A (control): the plain morphology transformer with one token per link, heading normalization and
   convention augmentation (training across equivalent descriptions: axis conventions, joint order). B: A with a
   geometric-algebra encoder and decoder only. C: full geometric-algebra tree message passing.
3. *Budget.* The same wall-clock per arm and seed, about 10 GPU-hours (DESIGN estimate), three seeds per arm:
   about 90 GPU-hours in total. Equal wall-clock, not equal parameters and not equal steps.
4. *Measures.* (a) Time to a registered return threshold, with the threshold and the evaluation cadence fixed in
   advance and attainment judged with error control over all looks (the rule of N23b-33, applied by hand here:
   level αₖ = α/[k·(k + 1)] at look k); (b) return with no adaptation on the held-out designs; (c) retention
   under re-description: the ratio of return on equivalently re-described robots to return on the originals.
5. *Falsifier.* Neither B nor C is 1.3 times faster than A to the threshold, nor better with no adaptation beyond
   seed spread (the spread being the range of arm A's three seeds).
6. *Ceiling.* 0 to 1.3 times on an amortized pretraining run. The pilot cannot show more than the ratio of times
   to threshold.
7. *Fallback and kill gate.* Arm A; KILL-GATREE.
8. *The six parts of a method experiment* are all present: ceiling (6), competing arms (A against B and C, A
   being the strongest conventional alternative and also the fallback), potency control (below), a paired lower
   bound where seeds are paired, the pre-declared fallback (7) and the reachability statement (with three seeds
   per arm the comparison can return "faster by 1.3", "not faster", or "undetermined: seed spread overlaps").

**Tools.** An incumbent GPU simulator and a standard PPO implementation at pinned revisions from the incumbent
harness (BD-039), with the layers of arms B and C written in that stack. Nothing is linked into the workspace.

**Record.** One entry in `frob-conformance/registry/pilots.toml` with the fields above, the three-by-three table
of results, the disclosure block of the hardware (device, driver, versions, world count, step, decimation, whether
policy and learning are included, warm-up and duration) and the result: `falsified`, `not-falsified` or
`undetermined`, with the numbers.

## Acceptance criteria

- [ ] The protocol is committed to the pilot register before the first run; a threshold edited after the first result is refused by the record's hash.
- [ ] All nine runs (three arms by three seeds) completed at equal wall-clock, or the record states which did not and why.
- [ ] The record holds, per arm: median time to threshold with its attainment look, zero-shot return on held-outs, retention under re-description, and the seed range.
- [ ] The falsifier is read mechanically from the record and its outcome is on file.
- [ ] The potency control and the A/A control are in the record with their outcomes.
- [ ] No file of the workspace other than the register entry and the pilot's log changed.

## Test plan

### Unit tests

`cargo test -p frob-conformance pilots_registry`: `pilot_ga_tree_schema` (the entry parses and has every required
field); `pilot_protocol_hash_frozen` (changing the threshold after `result` is set changes the hash and fails);
`falsifier_reading` (synthetic result tables: B at 1.35 times → `not-falsified`; B and C at 1.1 times with
overlapping zero-shot ranges → `falsified`; B at 1.35 times on one seed and slower on two → `undetermined`).

### End-to-end script and logging

`tools/pilots/cortex_ga_tree/run.sh` (a development-time script, outside the product). It sources the logging
helper of `STD-E2E` so that its log has the standard form: newline-delimited JSON at
`target/e2e-logs/pilot_cortex_ga_tree/<utc>.ndjson` with a transcript beside it; one `cmd` event per training and
evaluation command with the exact line, exit code and wall time; `metric` events for each time to threshold,
return and retention with units and thresholds (1.3 times; the seed range); `assert` events for the falsifier
clauses; a `summary` with assertions passed and failed and `gates: []`. It ends by validating the register entry
with the registry test above.

### Known answers and negative controls

- Potency control: arm A run with a planted 1.3 times slowdown (every third step repeated) must be reported 1.3 times slower than A, within the seed spread; otherwise the timing harness cannot see the effect it is asked to judge.
- A/A control: two runs of arm A with different seeds must not differ by 1.3 times; if they do, the seed count is too low for the falsifier and the result is `undetermined`.
- Re-description control: an arm that reads tokens in file order must lose return on re-described robots (published context: 3.6% of return kept without convention training, 80.6% with it).
- Zero-weight and random policies fail the return threshold in every arm.

## Considerations

- The pilot is expensive for what it can show and sits last in the learning queue; it is run only when an envelope exists and cheaper pilots have run.
- Three seeds give a weak reading; the record must report `undetermined` and not round it to a verdict.
- A result on an incumbent stack does not transfer automatically to our engine; it decides funding only. The gate at scale is measured on our engine by the epic.
