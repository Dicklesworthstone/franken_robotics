## Background

FACT that motivates this bead (read in a sibling project at a pinned commit, to be re-read at admission): the
suite's only PPO implementation hand-rolls training with manual backpropagation; its exported checkpoint has an
all-zero policy head; and its own work item says it "proves model/training/export plumbing, not learned humanoid
locomotion". Plumbing tests did not find three errors in its update either. A test that a training loop runs,
exports and reloads can pass while nothing was learned.

The rule adopted in FrankenRobotics (ADR-CORTEX-08): a training gate tests learned behaviour against negative
controls, never plumbing. A training gate is a claim about learned behaviour. Its record must hold:

- a zero-weight policy and a random policy that both fail the same threshold;
- a shuffled-label student where distillation is involved;
- a replay of the exported checkpoint that reproduces the behaviour.

A record without them is refused (FROB-REF-544: "a training gate record without its negative controls"; repair:
add the zero-weight, random and shuffled-label controls; exit 3). INV-CORTEX-05: every training gate record
contains its negative controls. A plumbing test satisfies no learning gate.

This bead builds the record type and its checker, used by every learning gate of Cortex: the reference training
gate, the distillation gate, the family-policy, inheritance and equivariance comparisons, the adapter's
external-learner clause, the tree-policy and short-horizon gates.

Tier: Solid. Crates: `frob-learn` (type and builders), `frob-conformance` (the check inside the gate recorder).

## Scope

In: the `TrainingGateRecord` type; builders for the three kinds of control and the checkpoint replay, with the
`zero:` and `random:` forms of `eval.run --policy` that reach them, and the `masked:` form for the live-dependency
perturbation; the
checker and the refusal; registration of the controls in the negative-control registry; tests.
Out: the training runs that fill records (BD-198 and the Frontier gates); the general gate recorder and status
registry (N38b-18 for the row, N38b-19 for the recorder); the method-gate statistics for comparisons (N23b-10).

## Technical approach

**Type (DESIGN sketch).**

```rust
pub struct TrainingGateRecord {
    gate: GateId, task: TaskId, threshold: Threshold,          // metric, unit, value, direction
    trained: PolicyEval,                                       // policy id, evalreport hash, score, verdict
    zero_weight: ControlEval,                                  // the same network with every weight zero
    random: ControlEval,                                       // the same network at its random initialization
    shuffled_label: Option<ControlEval>,                       // required iff the gate involves distillation
    checkpoint_replay: ReplayEval,                             // exported, reloaded on batch-cpu, re-evaluated
    head_nonzero: HeadCheck,                                   // norm of the policy head's weights, > 0
    tiers: Vec<TierId>, determinism: DeterminismClass, seeds: Vec<Seed>,
}
pub struct ControlEval { policy: PolicyId, score: Qty, fails_threshold: bool, evalreport: Hash }
pub struct ReplayEval { checkpoint: Hash, score: Qty, within_envelope: bool, envelope: Hash }
```

**Controls, defined.**

1. *Zero-weight policy.* The gate's network with every parameter set to zero, the observation normalizer kept.
   Its action is the bias-free output, zero in the latent; it is evaluated by the same evaluation as the trained
   policy (same task, split, seeds, tier).
2. *Random policy.* The same network at its seeded random initialization, never updated.
3. *Shuffled-label student* (distillation gates only). A student trained by the gate's distillation procedure
   on teacher labels permuted across states by a keyed permutation, with everything else equal.
4. *Checkpoint replay.* The exported checkpoint (with its `frob.policy/1` manifest and mapping table) reloaded
   on the CPU reference tier `batch-cpu` and re-evaluated; its score must lie inside the recorded D3 envelope of
   the trained policy's score; and the policy head (the last layer that produces action means) must have a
   non-zero weight norm.

**Policy references for the controls (DESIGN).** The builders are reachable from the command line as two forms
this bead adds to `eval.run --policy` (N23b-09): `zero:<spec>` (control 1) and `random:<spec>:<seed>` (control 2),
where `<spec>` names the trained policy whose network spec and observation normalizer the control copies, and
`<seed>` the initialization seed, which the record stores (BD-198 draws it different from the training seed); a
malformed form is `FROB-REF-802`. The evaluation of a control is otherwise the trained policy's evaluation: same
task, split or stream, seeds and tier. A third form serves the live-dependency proof that the training-gate scripts
run beside the controls (§38: perturb the input and require the output to change): `masked:<spec>:<role>`, the
trained policy itself with the actor observation channels of one role of its mapping table (for example the
commanded velocity) held at the observation normalizer's mean, so that their normalized input is zero; a role
that is not among the policy's actor channels is `FROB-REF-802` with the actor roles listed. It is not a control
(no threshold is asserted on it) and the record does not hold it; the scripts assert that its score differs from
the trained policy's.

**Checker.** `check(record) -> Result<(), Refusal>` refuses with FROB-REF-544, naming the first missing or
vacuous element, when: a required control is absent; a control did not fail the threshold (`fails_threshold` is
false: the threshold is then not a test of learning, and the gate fails, which is a different outcome from a
refusal and is recorded as FAIL); the control was evaluated on a different task, split, seed list or tier than
the trained policy; the replay is absent; the head norm is zero. The gate recorder calls the checker before it
accepts PASS for any gate whose claim is about a trained policy.

**Verdict logic.** PASS needs: trained policy meets the threshold on every listed tier; both (or all three)
controls fail it; the replay is inside the envelope with a non-zero head. If the trained policy passes and a
control also passes, the gate is FAIL with reason `threshold-not-discriminating`.

**Registry.** The controls are registered once per gate in the negative-control registry (`kind =
"planted-design"`, `seed = "CX-257"`), so the recorder's general rule "a control not caught in the same run fails
the gate" also covers them.

**Evidence.** The record is content-addressed, stored in the ledger, and cited by the gate row.

## Acceptance criteria

- [ ] `TrainingGateRecord`, its builders and its checker exist; `frob-conformance`'s recorder calls the checker for every learning gate.
- [ ] A record missing the zero-weight policy, the random policy, the shuffled-label student (for a distillation gate) or the checkpoint replay is refused with FROB-REF-544 naming the missing element.
- [ ] A record in which a control passes the threshold is recorded as FAIL with `threshold-not-discriminating`.
- [ ] A checkpoint whose policy head is all zero fails the record even when a plumbing test (run, export, reload) passes.
- [ ] Controls evaluated on a different task, split, seed list or tier than the trained policy are rejected.
- [ ] A plumbing-only test offered as evidence for a learning gate is rejected by the recorder.
- [ ] A record assembled by the end-to-end script from a short real training run on `batch-cpu` (trainer BD-197, export N23a-13, evaluation N23b-09) validates under this checker, and the three planted submissions are refused or failed. The full reference record on `batch-cpu` and each device backend is BD-198's acceptance; BD-198 depends on this bead and uses this checker unchanged.

## Test plan

### Unit tests

`cargo test -p frob-learn gate_record`:
- `missing_zero_weight_refused`, `missing_random_refused`, `missing_replay_refused`: each returns FROB-REF-544 with the element named.
- `shuffled_label_required_for_distillation`: required for the distillation gate, optional for the reference training gate.
- `control_passes_means_fail`: a synthetic record whose random policy meets the threshold yields FAIL `threshold-not-discriminating`.
- `zero_head_fails`: a synthetic checkpoint with a zero policy head and a passing plumbing flag fails.
- `control_evaluation_matched`: a control evaluated with a different seed list is rejected.
- `replay_envelope`: a replay score outside the D3 envelope fails; inside passes.
- `zero_weight_policy_construction`: every parameter tensor has norm 0 and the normalizer digest equals the trained policy's.
- `control_policy_forms_parse`: `zero:<id>` and `random:<id>:7` resolve to the builders with the trained policy's spec and normalizer; `random:<id>` without a seed and `zero:` without a policy are FROB-REF-802; `masked:<id>:<role>` holds exactly that role's actor channels at the normalizer mean (the other inputs and every weight unchanged, checked on a fixture observation), and a role outside the actor schema is FROB-REF-802 listing the actor roles.
- Property test (INV-CORTEX-05): over 10³ randomly generated records, the recorder accepts PASS only for records that contain all required controls, all failing.

### End-to-end script and logging

`scripts/e2e/training_gate_record.sh` (helper of `STD-E2E`; newline-delimited JSON at
`target/e2e-logs/training_gate_record/<utc>.ndjson` with a transcript). On `batch-cpu` with a small budget: `frob
train start quad-ref --task quad-flat-velocity --backend batch-cpu --seed 1 --steps <small budget> --key tgr-tr-1
--json`; `frob job wait`; `frob train export`; evaluation of the trained, zero-weight and random policies with
`frob eval run --policy <id> | zero:<id> | random:<id>:2 --task quad-flat-velocity --stream dev --tier batch-cpu`
under the keys `tgr-ev-trained`, `tgr-ev-zero`, `tgr-ev-random`; replay of the exported checkpoint (reloaded on
`batch-cpu`, key `tgr-ev-replay`); assembly of the record
and its submission to the recorder in a scratch copy of the workspace's registries, never the committed
`registries/gates.toml` (one recorder per gate, KNOWN_DRIFTS 9: GATE-CORTEX-01 is recorded from BD-198's receipt);
then three planted submissions to the same scratch copy (no controls; zero head; a plumbing-only record), each
asserted to be refused or failed with the stated code or reason, and the committed registry's digest asserted
unchanged at the end. `cmd` events carry the exact command, exit
code, wall time and evidence block (claim, class, tier, determinism, identities, seed); `metric` events carry
each score against the threshold; `assert` events carry expected and observed outcomes, and on failure the
first missing or vacuous record element and the record's hash. `summary`: assertions passed and failed; `gates:
[]` with the label `smoke` (the record is `synthetic` in its evidence). This script tests the checker. The
full-budget record that measures GATE-CORTEX-01 is written by `scripts/e2e/cortex_train.sh` (N23a-35, step
`reference-training`, for BD-198), so two scripts never claim one gate.

### Known answers and negative controls

- KA-590 (zero-weight, random and shuffled-label policies fail the return threshold; negative control: an exported all-zero policy head passes a plumbing test and fails this one); CX-257.
- Negative controls of this bead's own checker: the three planted submissions above; a planted recorder that skips the checker must be caught by the property test.
- Live-dependency proof: perturbing the trained policy's weights to zero must change the record's verdict from PASS to FAIL.
- Determinism lanes: the checker is a pure function of the record; control evaluations are identical twice on one machine under a D2 profile.

## Considerations

- A threshold that the random policy passes is a task defect, not a learner success; the FAIL reason says so and points at the task's scorecard.
- The zero-weight control is cheap; the shuffled-label student costs one distillation run and is required only where distillation is part of the claim.
- This record does not replace the comparison statistics of a design-comparison gate; those gates carry both this record and the method-gate record of N23b-10.
- The rule generalizes the project's guard against false progress: a gate's PASS is recorded by a fresh-context session that did not implement the capability, with its controls caught in the same run.
