## Background

A known answer is a case whose truth is known by derivation, with a tolerance and a negative control: a planted
wrong implementation that the case must catch. FrankenRobotics keeps them in a suite grouped by chapter and runs
them as batteries. Cortex (the learning subsystem: the vectorized environment, PPO, tensor views, multi-device
updates, requirement terms, detectors, family policies) lists fifteen fixtures in its chapter, each with an
expected answer and a negative control, and its late sections add five more. The fixtures are implemented by the
beads that own the mechanisms. This bead is the capability-level end-to-end test for the chapter: one battery
and one script that run every fixture against the real components and assert both halves of each row, the
answer and the caught control. It exists so that "do Cortex's known answers hold?" has one command and one log.

## Scope

In: the battery definition (which fixture, which command, expected value, tolerance, tier, control); the
script and its log; skip rules for rows whose mechanism belongs to a later milestone.
Out: the mechanisms and their own unit tests; the invariant battery (N23b-17); gate measurements (each gate's
carrier).

**Battery definition (DESIGN).** `crates/frob-conformance/batteries/cortex_fixtures.toml`: one entry per row
with `id`, `ka` (or the provisional late identifier), `command` (a `frob` invocation where the answer is
user-visible, otherwise the conformance test target), `expect`, `tolerance`, `tiers`, `control` (the registry
identifier of the planted defect) and `first_milestone`. A row whose `first_milestone` is later than the build's
capability set is logged `skipped: capability absent`; it is never counted as passed.

**Two halves per row.** The answer half runs the real component and compares with `expect`. The control half
runs the same check against the build or input with the planted defect and requires the check to fail with the
stated wrong value where one is given (for example 0.5 in row 9, element 12 in row 11).

## Acceptance criteria

- [ ] The battery file lists the 15 chapter fixtures, KA-586, KA-592, KA-593 and the five late fixtures, each with command, expected value, tolerance, tier and control.
- [ ] At M2 the script passes rows 1 to 11, 13, 15, KA-586 and L1 to L3 on `batch-cpu`, rows 2, 3, 9, 10 and 13 also on each device backend, and logs rows 12, 14, KA-592, KA-593, L4 and L5 as skipped with their milestone; at M3 rows 12, 14, KA-592, KA-593 and L4 pass.
- [ ] Every passing row shows both halves: the answer within tolerance and the control caught.
- [ ] The "to set" tolerances (rows 3, 6, 8) are set in the battery file with a recorded reason before the first recorded run, and are not edited after a result without a new registration.
- [ ] The battery is part of the Gauntlet's known-answer run, and its status feeds the gate rows that cite these answers.

## Test plan

### Unit tests

`cargo test -p frob-conformance cortex_fixtures`: `battery_file_schema` (every row has all fields);
`battery_covers_suite` (every known-answer identifier of the chapter, KA-576 to KA-593, appears in a row);
`arithmetic_rows` (rows 4 and 15 and L3, L5 recomputed: 0.99 and 0.99499; 2.000, 1.995, 1.990; 585.4, 133.3,
66.7; 0.90497, 0.0303, 0.78548; 36, 46, 74, 103; 12.9, 167, 7.8 × 10⁸); `skip_is_not_pass` (a skipped row counts
in `skipped`, not in `passed`).

### End-to-end script and logging

`scripts/e2e/cortex_fixtures.sh` sources the helper of `STD-E2E` and writes newline-delimited JSON to
`target/e2e-logs/cortex_fixtures/<utc>.ndjson` with a human-readable transcript beside it. For each row and tier:
a `cmd` event with the exact command (for example `frob sim run --task @fixture:bootstrap-deadline --json`,
`frob train start --task @fixture:clip-surrogate --updates 0 --probe finite-difference --json`, `frob eval
preanalyze --cadence 50x30 --target 0.90 --true-rate 0.89 --json`), exit code, wall time and the envelope's
evidence block (claim, class, tier, determinism, identities, seed); a `metric` event with the measured value,
its unit and its tolerance; an `assert` event for the answer half and another for the control half; `refusal`
events where the expected outcome is a refusal (rows 5 and KA-593), with the code. On failure the log gives the
first differing value and the fixture path needed to reproduce. The final `summary` gives rows passed, failed
and skipped per tier and `gates: []`. The script is idempotent, seed-explicit and exits non-zero on any failed
row. Logs contain fixture data only, never private-scene data.

### Known answers and negative controls

- The rows are the known answers: KA-576 to KA-593, with CX-246 to CX-258 as the seeds of their controls.
- Battery-level negative control: a planted battery entry whose control cannot be caught (an expected wrong value that the planted defect does not produce) must fail the control half, showing that the control half is checked and not assumed.
- Metamorphic relations exercised by the rows: unit scaling (row 12), control-rate change (rows 3 and 4), shard partition (rows 9 and 10), packing order (row 8).
- Determinism lanes: the battery runs twice on one machine and across worker counts with identical logs on asserted fields (host rows are exact; tiered rows are class D2 per backend); debug and release agree; across backends the tiered rows agree inside their envelopes.

## Considerations

- Row 15 has no negative control in the plan; it is arithmetic on published inputs, and its figure is a planning value, not a measurement.
- The tolerances marked "to set" are a real gap: a tolerance chosen after seeing the result would be a forking path. They are fixed in the battery file before the first recorded run.
- The five late fixtures are not yet in the numbered suite; when they receive numbers the battery file is updated and `battery_covers_suite` extends its range.
