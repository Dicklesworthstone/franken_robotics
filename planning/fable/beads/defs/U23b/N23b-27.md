## Background

The Gymnasium-compatible adapter (BD-301) lets Python learning stacks drive the Rust vectorized environment.
Two open questions decide its shape, and both have fail-closed defaults that the adapter is built on:

- **OPEN-CORTEX-4, the transport.** Shared device views, or one copy per step across a process boundary. Owner:
  Tether lead. Blocks the adapter's gate (GATE-CORTEX-16). Default: one charged copy per step.
- **OPEN-WS-5, the binding.** Whether the adapter binds in process (the Python interpreter loads a native
  extension that contains the environment) or across a process boundary. Owner: Cortex lead. Default: across a
  process boundary with shared array files, so that no interpreter is ever in a `frob` binary.

A third question belongs to the project owner and is recorded here because it changes how much either answer
matters: whether the adapter ships as a supported public binding (default: no; it is built and gated for the
ten-fold test and for conformance only).

Why the defaults are the conservative pair: the core rule that a Python interpreter is forbidden everywhere
except the adapter annex is easiest to guarantee when the interpreter lives in another process; and a copy per
step is always correct, is charged honestly to the receipt, and costs throughput only on the rival's learner
path, which is not a path our own method gates use.

## Scope

In: the decision record for the two questions; the measurements that inform it; the consequences of each
combination; the owner's ruling recorded.
Out: building either transport (BD-301 builds the default; N23b-12 builds device views if chosen).

## Technical approach

**Options and consequences.**

| Binding | Transport | What it needs | Consequence |
|---|---|---|---|
| Process boundary (default) | One charged copy per step (default) | Shared array files; a control socket | Always available; the copy is device-to-host plus the learner's host-to-device if it trains on a device; overhead measured per step |
| Process boundary | Shared device views | Export and import of a device buffer between two processes on one device; the typed stride conversion; leases with epochs across processes | No copy for representable views; unrepresentable views are materialized (charged) or refused under a zero-copy contract (FROB-REF-547); only when the learner is on the same device |
| In process | Either | A native extension module loaded by the interpreter | Lowest overhead; the interpreter and the environment share an address space, so a crash or a stray write in the learner can corrupt the stepping authority; the "no interpreter in a production graph" rule then rests on build-graph separation alone |

**Measurements that inform the decision (from the pilot and from BD-301's first runs).** (1) The copy's cost:
bytes per step for the reference task (observation, reward, flags and `info` arrays for the world count) and
microseconds per step, as a share of the environment step. Planning arithmetic: at 4,096 worlds and 48
observation channels of `f32`, observations are 4,096 × 48 × 4 = 786,432 bytes per step, under a megabyte; at
tens of gigabytes per second of host memory bandwidth the copy is tens of microseconds, against an environment
step of the order of ten milliseconds at 400 k environment steps per second (4,096 worlds / 400,000 per second
= 10.2 ms). The copy is then well under 1% of the step. (2) The external learner's own overhead per step, which
dominates if it is not on the device. (3) Whether the rival freeze of the ten-fold test asks for device views
(a rival advocate may request the transport that favours the rival).

**Rule for the decision (DESIGN).** Keep the defaults unless the measured copy exceeds 5% of the environment
step on the reference task, or the rival freeze requests device views; in either case build N23b-12 and keep
the process boundary. In-process binding is chosen only by an explicit ruling of the Cortex lead and the
workspace owner together, with the build-graph check extended to prove that no core binary links the extension.

**Record.** The two answers with their owners; the measured copy share; the rival's request if any; the
owner's ruling on support status; the consequences: which beads build what, and the adapter's `CONTRACT.md`
statement of transport and binding.

## Acceptance criteria

- [ ] The decision record states transport and binding, each with its owner, the measured copy share on the reference task and the rule applied.
- [ ] Until decided, the adapter is built on the defaults (process boundary; one charged copy per step), and `xtask check-deps` shows no interpreter in any core binary.
- [ ] If device views are chosen, N23b-12 is opened for work; if not, it is closed with "default transport in force".
- [ ] The owner's ruling on support status (or its default) is recorded with its consequence for documentation and release.
- [ ] The copy-share arithmetic is reproduced by a test with the reference task's actual shapes.

## Test plan

### Unit tests

`cargo test` in the adapter annex: `copy_bytes_per_step` (for the reference task's declared shapes the charged
bytes per step equal the sum of the exported arrays' sizes; for 4,096 worlds and 48 `f32` observation channels
the observation part is 786,432 bytes); `receipt_states_transport` (every run's receipt names `transport` and
`binding`); `decision_rule` (copy share 0.8% and no rival request → defaults; 6% → device views; a rival request
→ device views).

### End-to-end script and logging

`scripts/e2e/gym_adapter_transport_probe.sh` (helper of `STD-E2E`; newline-delimited JSON at
`target/e2e-logs/gym_adapter_transport_probe/<utc>.ndjson` with a transcript): runs the reference task through
the adapter for a fixed number of steps with a null learner (random finite actions), reads the receipt, and logs
`metric` events for bytes per step, copy microseconds per step, environment-step microseconds and the copy
share against the 5% rule; `cmd` events carry the exact command, exit code, wall time and evidence block;
`summary`: counts and `gates: []`.

### Known answers and negative controls

- Arithmetic known answer: 786,432 bytes of observations per step at the stated shapes; 10.2 ms per step at 400 k environment steps per second with 4,096 worlds.
- Negative control: a planted adapter that copies twice per step and charges once must fail `copy_bytes_per_step` against the measured traffic.
- Negative control for the binding default: a planted build graph in which a core binary links the Python extension must fail `xtask check-deps`.

## Considerations

- The transport matters most for the rival arm's throughput; choosing the faster transport for the rival is fair play in the ten-fold test and is why a rival request alone triggers it.
- Device views across processes depend on the device backend exporting buffers; on the Metal machine the question is separate and defaults to the copy.
- If the adapter's kill gate fires, both questions are closed as moot: there is no adapter.
