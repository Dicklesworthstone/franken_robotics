## Background

A **refusal** is the answer a verb gives when it will not compute what was asked: a stable code, a message,
the offending value beside what was required, and ranked repairs. The machine-readable registry is
`registries/refusals.toml`; a code with no row does not compile, an unknown code in a stored refusal is a
load-time error, and codes are never reused. The chapter that defines a refusal governs its meaning and
repairs; numbers are allocated by one ledger so that two chapters cannot take the same one.

The learning subsystem (Cortex) has a rule with no number. Randomization is how a policy is trained and
evaluated over the uncertainty of the hardware, and the rule is: "Every randomized parameter traces to an
uncertainty on a card (actuator, interface, material, sensor). There are no free-floating ranges." A card
field carries a nominal value, an uncertainty (an interval, an absolute or relative half-width, a normal
law with its σ, or `exact`) and a provenance. A task entry that asks to randomize a field whose uncertainty
is `exact` or absent has no range to draw from. The seed bead for randomization (BD-200: "a card field with
no interval refuses") raises that refusal, and its done-condition depends on it. The chapter's refusal
table has twelve codes and none for this; Appendix O has none; the Cortex registry bead lists five other
late refusals and not this one; the allocation ledger's first round includes "the refusal to randomize a
numerical parameter", which is a different condition (a time step or an iteration count is not a card field
at all). So BD-200 raises its refusal under the provisional name `randomize-no-interval`, and the delivery
registers list that name as awaiting a code.

Why a bead of its own: a refusal without a row cannot be loaded, tested or documented, and an agent repairs
by code. Rejected alternatives: inventing a number inside BD-200 (numbers are allocated by the ledger, and a
collision burns a number for ever); folding the case into FROB-REF-113 ("an actuator card with a required
field of class `assumed` when the caller asked for `--strict-data`": a different defect with a different
repair, since an `assumed` field has an interval and an `exact` field does not); folding it into the
unknown-field refusal 103 (the field exists; it has no interval); silently drawing a zero-width range (the
task would claim a randomization that never happens). Tier Solid: data entry plus one owner confirmation.

## Scope

In: the allocation request; the proposed number and the default that holds until it is confirmed; the row
with message, trigger, block fields, retry, ranked repairs and exit code; the neighbour table that says
which code fires; the verbs' refusal lists; the binding test; removal of the provisional name from the
delivery registers' pending list.

Out: the mechanism that detects the condition and builds the randomization plan (BD-200, which owns its
emit site and trigger fixture); the card band accessor (N15b-06); the twelve coded Cortex rows and the
five other late refusals, among them the refusal for randomizing a numerical parameter (N23-REF, its own
request in the ledger); the allocation function and the registry-wide checks (N35-33); exposure-domain refusals of
the task compiler (N24c-36).

## Technical approach

**1. Allocation request** (a row appended to `registries/refusal_allocations.toml`, schema
`frob.refalloc/1`): `request = "randomize-no-interval"`, `requested_by = "BD-200"`, `defined_in = "§23.15"`,
`condition = "randomization is requested on a card field whose uncertainty is exact or absent"`,
`family = "5xx"`, `proposed = 571`, `interim = none`, `status = "requested"`. The interim is `none` (N35-33
rule 7: an interim is an existing code raised with `detail`, or `none`; a bare slug such as the symbolic name
BD-200 uses behind its constant is not one, and neither is the proposed number): the request is in the ledger's
first round, which assigns it at M0, before BD-200 (M2) raises the refusal. Why 571 (DESIGN proposal): in the `5xx` family the
numbers through 557, 560 to 569 and 580 to 587 are printed in the plan; 558, 559 and 570 are the Cortex
registry's proposals for three of its late refusals; 571 is the lowest number above them that is free (and
572, the next, is the Cortex registry's proposal for the numerical-parameter refusal). The
ledger's rule decides: a proposal is a preference, processed in order of the defining subsection, and the
allocation is a pure function of ledger and registry. If the ledger assigns another number, that number is
used and 571 is not burned unless it was ever written into the registry.

**2. Fail-closed default until the number is assigned.** The row is entered in `registries/refusals.toml` only
with the assigned number; a proposed number is never written or raised (N35-33 rule 7). BD-200 compiles against
one named constant (`frob_learn::refusal::RANDOMIZE_NO_INTERVAL`) that holds the assigned code. Were the request
still unassigned when BD-200 lands, `interim = none` keeps BD-200 open on that point: the mechanism still refuses
the draw (it never draws a zero-width range) and is not shipped as passing. A milestone exit with the request
still unassigned is a finding of the registry check.

**3. The row** (field names as in the Cortex registry N23-REF, which follows the registry-wide checks of N35-33:
`code`, `name`, `family`, `message_template`, `exit`, `retry`, `repairs`, `defined_in`, `raised_by`, `related`,
`first_milestone`; the trigger and the block fields below are documentation of the raising site).

| Field | Value |
|---|---|
| `code` | `FROB-REF-571` (proposed) |
| `name` | `randomize-no-interval` |
| `family` | `5xx` (learning and evaluation protocol) |
| `message_template` | Randomization requested on a card field with no interval |
| `defined_in` | `§23.15` |
| `related` | 572 (`randomize-numerical-parameter`, N23-REF: the parameter is of class `numerical`), 103, 113, each with the sentence of step 4 |
| `trigger` | While a verb that creates an environment compiles a task's `randomization` section against a design, an entry resolves to a card field (or a design override) whose uncertainty is `exact` or absent |
| `block` beyond the common four (`pointer`, `observed`, `required`, `unit`) | `draw` (the entry's name), `card` (identifier and version), `field` (path), `uncertainty` (`exact` or `absent`), `provenance` |
| `pointer`, `observed`, `required` | The path of the entry in the task; the field with its provenance; "an interval, a half-width or a law on the card field" |
| `repairs`, ranked | 1. State an uncertainty on the card: a new card version with provenance. 2. Override the field in the design with provenance `designed` and an interval. 3. Remove the entry from the task's `randomization` |
| `retry` | `after-change` |
| `exit` | 3 (the `5xx` family's exit) |
| `raised_by` | BD-200 |
| First milestone | M2 |

Each repair is a typed change: (1) a card edit that yields a new card identity; (2) a typed design edit;
(3) a task edit that yields a new `TaskId`. The refusal names all drawable fields of the same card so that
an agent can see what it could randomize instead.

**4. Which code fires (one condition, one code).**

| Situation | Code |
|---|---|
| The entry names a card field with uncertainty `exact` or none | This row |
| The entry names a numerical parameter (time step, iteration count, stiction speed, regularization) | The separate request `randomize-numerical-parameter` (proposed 572) of the Cortex registry N23-REF, raised by N23b-03; never this row |
| The entry names a field that does not exist on the card | 103 (unknown, misspelt or duplicate field) |
| A required card field is `assumed` and the caller asked for `--strict-data` | 113 |
| The entry declares no exposure domain, or an undeclared event | The task compiler's exposure refusals |
| A range wider than the card's support is requested by adaptive randomization | Not a refusal: the result is labelled `beyond-card` and cannot be cited for the carded hardware |

**5. Verb refusal lists.** `sim.run`, `eval.run` and `train.start` (every verb that creates an
environment) and `task.check` in its `--design` form gain the code; the generated agent documentation
shows message and repairs.

**6. Binding.** One test provokes the row through a public verb and asserts the code, exit 3, the block
keys, and that the first repair, applied, makes the same request admissible. Until BD-200 lands the row is
`pending: BD-200` and is reported, not failed.

**7. Record.** One ADR (`docs/adr/ADR-CORTEX-refusal-no-interval.md`, DESIGN name) with the request, the
assigned number, its date and whether it was confirmed or defaulted; the delivery registers' list of
"refusals used under provisional names" loses this entry in the same change.

## Acceptance criteria

- [ ] The ledger holds the request with `defined_in = "§23.15"`, `interim = none` and a status of `assigned` (the first round runs at M0); were it still `requested`, no row is entered, BD-200 stays open on the number, and the question is listed open at the M2 exit.
- [ ] `registries/refusals.toml` has the row with every field of the table; the registry's uniqueness, family-exit and neighbour checks pass.
- [ ] No source file contains the literal `randomize-no-interval` outside the registry row's `name` and the ledger's `request` field; BD-200 raises the code through the one constant.
- [ ] The binding test passes: a task that randomizes a rotor inertia whose card states no uncertainty is refused through `frob sim run <design> --task <task>` (the verb whose registry row already carries this refusal for its `--task` form) with the code, exit 3, the block keys and zero worlds created; after repair 1 (a new card version stating ±10% on that field with provenance `assumed`) the same command is admitted. A gear ratio fixed by tooth counts (`exact`) is refused the same way.
- [ ] The four neighbour situations of step 4 each raise their own code and not this one.
- [ ] The verbs' refusal lists and the generated documentation include the code; the delivery registers' pending list no longer names it.
- [ ] If the ledger assigned a number other than 571, the constant, the row and the documentation show the assigned number, and 571 appears in `retired` only if it was ever committed to the registry.

## Test plan

### Unit tests
`cargo test -p frob-core refusals::cortex_no_interval` and `cargo test -p frob-learn randomize::refusal`:
- `row_loads_and_is_unique`: the registry loads; the code is in no other row and not in `retired`.
- `exit_follows_family`: exit 3.
- `repairs_are_ranked_and_typed`: three repairs in the stated order, each a typed change.
- `exact_field_refused`: gear ratio fixed by tooth counts → this row, with `uncertainty = "exact"`.
- `absent_uncertainty_refused`: a field with a nominal value and no uncertainty → this row, with `uncertainty = "absent"`.
- `numerical_parameter_is_other_code`, `unknown_field_is_103`, `strict_data_assumed_is_113`.
- `zero_width_interval_is_not_exact`: an interval [a, a] written on the card is drawable (a constant) and is not refused; the plan reports width zero.
- `allocation_is_order_independent`: the ledger's function run with this request inserted at 100 random positions gives the same assignment.

### End-to-end script and logging
Steps added to `scripts/e2e/cortex_refusals.sh` (the Cortex registry's script), under the step names `no_interval_*`:
1. `frob sim run quad-ref --task fixtures/tasks/randomize_exact_field.ftask --tier batch-cpu --worlds 1 --seconds 1 --key no-interval-1 --json`: exit code 3, the code, the block keys, three repairs, and no world created (the randomization plan is compiled at environment admission, before any world exists).
2. `frob task check fixtures/tasks/randomize_exact_field.ftask --design quad-ref --json`: the same refusal.
3. Apply repair 3 (remove the entry) and re-run step 1 with `--key no-interval-3`: admitted.
4. `frob robot-docs --json`: the code appears with message and repairs.
Logged per STD-E2E: command, exit code, wall time, a `refusal` event with code, pointer, observed,
required and repairs, the registry and ledger digests, and the final summary with assertion counts.

### Known answers and negative controls
- Known answer: the refusal block for the gear-ratio case (pointer `/randomization/gear-ratio`, uncertainty `exact`, provenance `designed`).
- Negative controls: a build that draws a zero-width range for an `exact` field (the binding test fails: the request is admitted); a registry in which the row shares its number with another (the uniqueness check fails at load); a raising site that returns 113 for the `exact` case.
- Determinism: registry load, allocation and the refusal are exact; identical in debug and release and across platforms.

## Considerations

- Only the number is open. Meaning, trigger and repairs are fixed here from the chapter's rule and the seed bead's done-condition, so a change of number is a one-line change.
- A second request from the same subsection (the numerical-parameter refusal, carried by N23-REF with the proposal 572) is in the ledger's first round; the allocation order is by position in the subsection's text, and the two must not be merged, because their repairs differ. If the ledger's order gives the numerical-parameter request the lower number, the two proposals swap and both beads change one constant.
- Stored refusals: no proposed number is ever raised, so none is stored; if an assigned number is later replaced, the old one stays loadable as an alias for one release, as for every renumbered row.
- Owner: the keeper of the refusal registry in `frob-core`, with the Cortex lead. Silence is not a decision; the ADR says whether the number was confirmed or only defaulted.
