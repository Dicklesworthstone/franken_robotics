## Background

A task is data. Everything that determines what a robot is asked to do and how the answer is judged is in one file,
the task file `.ftask` (format identifier FMT-FTASK, schema `frob.task/1`), and the hash of that file is the task's
identity. This is what makes a verdict a pure function of a trace and a `TaskId` (INV-ARENA-01), what lets an
evaluation be reproduced from four identifiers (task, scene, model, seed; GATE-ARENA-01), and what makes "the
curriculum quietly changed the pass criterion" impossible: a change to an atom, a scale or a window is a different
file and therefore a different task.

DESIGN decisions carried by this bead:

- The canonical form is JSON, and its BLAKE3 hash, under a domain string equal to the schema name, is the `TaskId`.
  An S-expression view is lossless in both directions and optional, exactly as for designs; a view is never hashed,
  signed or cited (N24a-03 owns the view). Rejected alternatives, each with its counterexample: hashing the file as
  written (two files that differ in key order or whitespace would be two tasks and every memoized result of one would
  miss on the other); hashing the in-memory value (a hash of a struct layout changes with the compiler); hashing
  whichever of view or canonical arrived first (one task, two cache entries and two citable verdicts).
- One owner. `frob-spec` holds the schema, the canonicalization rule, the reference reader and the version refusal.
  No other crate parses the bytes; `frob-learn`, `frob-arena`, `frob-opt` and `frob-nemesis` receive typed values.
- A task has exactly nine sections. The names and contents of the sections and the grammar of `requirements` are
  fixed; keywords inside the other eight sections are owned by the subsystem that defines their semantics.

## Scope

In: the typed model of a task, the canonical JSON reader and writer, the `TaskId`, structural validation (all nine
sections present, references between sections resolve), and the version refusal.

Out: the S-expression view and the requirement grammar parser (N24a-03); semantic checks of requirements (N24a-05,
N24a-06, N24a-09, N24a-12); the verbs `task.new`, `task.show`, `task.list`, `task.check` (BD-122); the meaning of
term fields (Cortex, BD-194); the meaning of scene families and splits (Habitat); the format-registry row and the
10,000-round-trip gate GATE-WS-02 (BD-141), which this bead's reader must pass.

## Technical approach

**The nine sections.**

| Section | Contents | Semantics defined by |
|---|---|---|
| `interface` | Required ports (mechanical, electrical, payload); observation and action layouts with units, frames and rates; the registered action law | Cortex |
| `clocks` | Named clocks, each a rational period in seconds and a rational phase | The clock contract (Sensorium) and N24a-06 |
| `terms` | Observation, action, reward and termination terms, each with unit, noise, delay and the representation under which it transforms (trivial, pseudovector, permutation, invariant, …) | Cortex |
| `signals` | The telemetry channels that requirements read: name, unit, channel kind, clock, and the declared reduction onto the requirement clock | Chronicle and N24a-06 |
| `requirements` | Atoms with scales, online signals, the verdict formula, labelled examples | The requirement language (BD-121) |
| `randomization` | Draws, each traced to an uncertainty on a card or a hazard-registry row, and bound to a named random stream | Sinew cards, Cortex randomization |
| `reset` | The settled-pose cache specification: count, speed bound, hold time, penetration bound, first-impulse bound | N24a-16 |
| `world` | A scene family or scene set with its split, the grouping unit (for example `building`), and the episode horizon | Habitat |
| `study` | Default study type, effect margin, rule, level and budget | The two study types |

**Types (DESIGN; intent, not signatures).**

```rust
pub struct Task {
    name: Ident, schema: SchemaVersion,            // "frob.task/1"
    interface: Interface, clocks: Vec<ClockDecl>, terms: Vec<Term>, signals: Vec<SignalDecl>,
    requirements: Requirements,                    // the tree of N24a-04
    randomization: Vec<Draw>, reset: ResetSpec, world: WorldSpec, study: StudyDefault,
}
pub struct ClockDecl  { name: Ident, period: Ratio /* seconds */, phase: Ratio }
pub struct SignalDecl { name: Ident, unit: Unit, kind: ChannelKind, clock: Ident, reduce: Option<Reduction>,
                         source: SignalSource /* Truth when not written; Delivered(SensorId); N24a-06 */ }
pub enum   Reduction  { Last, Min, Max }
pub struct Draw       { name: Ident, from: UncertaintyRef /* card field or registry row */, stream: StreamId }
pub struct ResetSpec  { count: u32, speed_below: Qty, hold: Qty, penetration_max: Qty, first_impulse_within: Ratio }
pub struct WorldSpec  { scenes: SceneFamilyOrSet, split: SplitId, group_by: Ident, horizon: Qty }
pub struct StudyDefault { kind: StudyKind, n: Option<u32>, margin: Ratio, rule: RuleId, level: Ratio, budget: Budget }
pub struct TaskId(Blake3);                         // displayed as t:<name>@<hash prefix>
```

**Canonical bytes and identity.**

1. Canonical JSON follows the workspace's canonical-JSON rule (the one `frob-core` provides for every format):
   object keys in sorted order, no insignificant whitespace, UTF-8, no duplicate keys.
2. No floating-point literal enters the identity. Quantities are written as a value string and a unit
   (`"0.10 m"`, `"1/500 s"`, `"5 deg"`); values are decimal or rational strings parsed to exact rationals. Integers
   that can exceed 2⁵³ are strings. The one number rule of this format (the format registry requires each owner to
   name one, DESIGN, the printing rule of design quantities in N14a-01): the magnitude is written as the shortest
   decimal equal to the exact rational, with no exponent, no leading `+`, no trailing fraction zeros, one leading
   zero before a point and `-0` written `0`; a rational whose reduced denominator has a prime factor other than 2
   or 5 is written `p/q`, reduced, with the sign on p. One space, then the unit as authored (authored units are
   identity-bearing for tasks, N24a-03), spelt as `frob_core::qty` prints that unit. So `0.1 m`, `0.10 m` and
   `1/10 m` are all written `"0.1 m"`; `1/500 s` is written `"0.002 s"`; `1/30 s` stays `"1/30 s"`; `1e-3` is
   written `"0.001"`.
3. `TaskId = BLAKE3(domain = "frob.task/1", canonical bytes)`. The display form is `t:<name>@<first hex digits>`,
   for example `t:cart-sill-dock@6be1…`. The name is a label; the hash is the identity. Two tasks with one name and
   different bytes are different tasks.
4. The identity covers all nine sections, the labelled example references (by trace digest), the exposure table and
   the information-contract digest when those two exist. A view has no identity (refusal FROB-REF-892 when a view is
   offered where an identity is required).

**Structural validation at load** (each failure is a refusal with a pointer to the field, exit code 3):

1. All nine sections present; an unknown major schema version or an unknown required field is refused
   (FROB-REF-891). Adding an optional field keeps the major version. A member the schema does not list (a misspelt
   name, for instance) and a duplicate key are refused as FROB-REF-103 (unknown, misspelt or duplicate field), as
   the design reader does (BD-054), never defaulted or dropped; `task.new` carries both codes (VERBS-task).
2. Every name is unique within its section; every reference resolves: a signal's clock is a declared clock; an atom's
   signals are declared signals; an online or verdict formula's atoms are declared atoms; a `terminate … :on
   (decided <verdict> satisfied|violated)` names the declared verdict; a draw names a registered stream.
3. Exactly one verdict formula per requirement block; at least one atom; a clock named `req`, on which the
   requirements are evaluated (the reserved name is N24a-06's DESIGN rule; pointer `clocks.req` when absent).
4. The file is never repaired silently: the reader returns the typed task or a refusal, nothing in between.

A missing section or required field, a repeated name, a dangling reference and a wrong count (items 1 to 3, other
than the two numbered codes) carry one refusal, registered under the symbolic name `task-structure-invalid` in
N24-REF's table (the plan gives these rules no number; the registry owner numbers it at implementation, exit 3),
with the pointer at the field and the kind of failure (`missing`, `duplicate-name`, `dangling`, `count`) in
`observed`.

**Versioning.** The schema name carries the major version. A reader refuses what it does not understand; it does not
tolerate unknown required fields (counterexample: a reader that ignores an unknown required field such as a
contact-law selector would evaluate a different task and report it under the same identity).

**The worked task (golden file).** This bead commits the worked task in two files under
`crates/frob-spec/tests/golden/`: `kitchen-tray.ftask.sexp`, the authored text below, and
`kitchen-tray.ftask.json`, its canonical JSON written by hand from that text with every magnitude in the number
rule above (`1/500 s` becomes `"0.002 s"`, `1/50 s` `"0.02 s"`, `1/10 s` `"0.1 s"`, `1/20 s` `"0.05 s"`); the view
parser of N24a-03 comes later and must reproduce it. The keywords inside the eight sections other than `requirements` are proposals
confined to the section contents of the table above; the section names and the requirement grammar are fixed.
The plan prints its identity as `t:kitchen-tray@88c1…`, a placeholder: the test pins the hash this bead computes,
not that prefix.

```lisp
(task "kitchen-tray" :schema "frob.task/1"
  (interface
    (ports (mech base) (elec bus) (payload tray))
    (observation proprio-and-scan :frame base :rate 50 Hz
      (joint-pos 12 rad) (joint-vel 12 rad/s) (base-gyro 3 rad/s) (gravity-dir 3 1)
      (scan 64 m) (goal-vec 2 m) (sample-age 2 s))
    (action joint-targets 12 rad :rate 50 Hz :law latent-then-limit))
  (clocks
    (physics 1/500 s :phase 0 s) (imu 1/500 s :phase 0 s) (policy 1/50 s :phase 0 s)
    (lidar 1/10 s :phase 1/20 s) (req 1/50 s :phase 0 s))
  (terms
    (obs joint-pos    :unit rad   :noise encoder-14b :delay 1 ms :rep trivial)
    (obs base-gyro    :unit rad/s :noise imu-generic :delay 2 ms :rep pseudovector)
    (obs scan         :unit m     :noise lidar-2d-generic :delay 30 ms :rep permutation)
    (reward progress  :unit 1/s   :rep invariant)        ; integrated over simulated time
    (reward tray-calm :unit 1/s   :rep invariant)
    (terminate success :on (decided delivered satisfied))
    (terminate failure :on (decided delivered violated)))
  (signals
    (dist_to_pass     m     :kind state            :clock physics :reduce last)
    (base_speed       m/s   :kind state            :clock physics :reduce max)
    (tilt             deg   :kind interval-extremum :clock physics :reduce max)
    (tray_tilt        deg   :kind interval-extremum :clock physics :reduce max)
    (tray_acc         m/s^2 :kind interval-extremum :clock physics :reduce max)
    (clearance_min    m     :kind interval-extremum :clock physics :reduce min)
    (winding_temp_max K     :kind state            :clock physics :reduce max)
    (spill_events     1     :kind count            :clock physics :reduce last))
  (requirements
    (atom at-pass    (>= (- 0.15 m dist_to_pass) 0 m)        :scale 0.15 m)
    (atom settled    (>= (- 0.05 m/s base_speed) 0 m/s)      :scale 0.05 m/s)
    (atom upright    (>= (- 12 deg tilt) 0 deg)              :scale 12 deg)
    (atom tray-level (>= (- 8 deg tray_tilt) 0 deg)          :scale 8 deg)
    (atom gentle     (>= (- 3 m/s^2 tray_acc) 0 m/s^2)       :scale 3 m/s^2)
    (atom clear      (>  clearance_min 0 m)                  :scale 0.05 m)
    (atom cool       (>= (- 383 K winding_temp_max) 0 K)     :scale 20 K)
    (atom no-spill   (=  spill_events 0)                     :exact)
    (online placed   (H (0 s 1 s) (and at-pass settled tray-level)))
    (online carrying (and upright tray-level gentle))
    (verdict delivered (U (0 s 20 s) (and upright tray-level gentle clear cool no-spill) placed))
    (example trace:b3:1c0a… satisfied) (example trace:b3:77e2… satisfied)
    (example trace:b3:a04f… violated)  (example trace:b3:5d19… violated))
  (randomization
    (draw floor-friction :from card:rubber-60a/tile:uncertainty :stream world.material)
    (draw film           :from registry:hazards/commercial-kitchen:wet-floor :stream world.film)
    (draw closer-torque  :from registry:hazards/commercial-kitchen:swing-door :stream world.fixture)
    (draw tray-fill      :from registry:hazards/commercial-kitchen:hot-liquid :stream world.payload)
    (draw imu-bias       :from card:imu-generic:uncertainty :stream sensor.imu))
  (reset
    (settled-pose :count 64 :speed-below 1e-3 :for 0.2 s :penetration-max 0.5 mm :first-impulse-within 5 %))
  (world
    (scenes :family kitchen-commercial/galley :split split:b3:60d3… :group-by building)
    (horizon 22 s))
  (study
    (default :type fixed-n :n 64 :margin 0.05 :rule paired-clopper-pearson/1 :level 0.05)
    (budget :gpu-s 600)))
```

The four example digests are placeholders until the four labelled traces are recorded (N24a-12 records them);
until then the golden file carries synthetic traces of the same labels, marked `synthetic`, and their digests. The
facts this file is meant to exhibit, each later checked by `task.check`: seven scaled atoms and one `:exact` atom on
a count; every signal reduced from the 1/500 s physics clock to the 1/50 s requirement clock; window bounds of 1 s
and 20 s, which are 50 and 1,000 ticks of 1/50 s; both online signals past-time; reach 20 s against a horizon of
22 s; a lidar clock at 1/10 s with phase 1/20 s that is not an integer multiple of any other clock.

## Acceptance criteria

- [ ] The worked task "kitchen tray delivery" (nine sections, eight atoms, two online signals, one until-verdict,
      four examples, five draws, a 64-state reset spec, a split with `group-by building`, a fixed-n default study)
      loads, re-serializes to identical canonical bytes and yields a stable `TaskId`.
- [ ] `{"b":1,"a":2}`-style reorderings and whitespace changes of a task file give the same `TaskId`; changing one
      scale from `0.10 m` to `0.11 m`, one window bound, or one comparator gives a different `TaskId`.
- [ ] A file with a missing section, a duplicate atom name, a signal on an undeclared clock, two verdict formulas, no
      `req` clock, or schema `frob.task/2` is refused with the field named.
- [ ] The golden pair `kitchen-tray.ftask.sexp` / `kitchen-tray.ftask.json` is committed; the JSON loads with the
      counts of the first criterion and every signal resolves to source `truth`.
- [ ] 10,000 seeded round trips canonical → value → canonical have zero byte differences; each of 10,000 single-byte
      mutations either fails to parse or changes the identity (the reader's share of GATE-WS-02).
- [ ] The reader is the only code path from bytes to `Task`; a grep-level lint finds no other `.ftask` parser.
- [ ] `scripts/e2e/spec_ftask_format.sh` passes. (The same identity through `frob task new` and `frob task show
      --json`, with `bound.task` equal to the `TaskId`, is asserted by BD-122 and by the `ftask-*` steps of N24a-42,
      which depend on this bead.)

## Test plan

### Unit tests

- `canonical_roundtrip_seeded`: 10,000 generated tasks; bytes equal after value round trip.
- `key_order_is_not_identity`: the same task serialized with shuffled keys and extra whitespace; one `TaskId`.
- `scale_edit_changes_id`, `window_edit_changes_id`, `comparator_edit_changes_id`, `example_edit_changes_id`:
  one field changed; the identity differs.
- `nine_sections_required`: nine cases, each removing one section; each refused with the section named.
- `dangling_references_refused`: undeclared clock, undeclared signal in an atom, undeclared atom in a formula,
  unregistered stream, missing `req` clock; five refusals with pointers, each `task-structure-invalid` with its
  kind (`dangling`, and `missing` for the `req` clock).
- `unknown_major_version_refused`: `frob.task/2` → FROB-REF-891.
- `misspelt_and_duplicate_fields_refused`: `:scael 0.10 m` in an atom, an unknown optional key in `world`, and a
  JSON object with the key `horizon` twice → FROB-REF-103 each, with the pointer to the field; none is dropped.
- `no_float_on_identity_path`: quantities written `0.1 m`, `0.10 m` and `1/10 m` give one identity (all parse to
  the rational 1/10 and are written back in one normal form); the value `0.10000000149011612 m`, which is what a
  single-precision round trip of 0.1 prints, is a different rational and a different identity, so no writer may pass
  a quantity through a float.
- `number_rule_printing`: 1/500 s → `"0.002 s"`; 1/30 s → `"1/30 s"`; −3/4 → `"-0.75"`; 1e-3 → `"0.001"`; −0 m →
  `"0 m"`; 100 mm stays `"100 mm"` (the unit is not converted); reading each printed string back gives the same
  rational.
- `mutation_changes_or_fails`: 10,000 single-byte mutations of a canonical file.

### End-to-end script and logging

`scripts/e2e/spec_ftask_format.sh [--seed S]` (owned by this bead; default seed 2402; idempotent; sources the
STD-E2E helper). The task verbs come after this bead (BD-122), so the script drives the reader through its tests
and one example program, on this bead's own dependencies. Steps:

1. `unit`: `FROB_TEST_SEED=$SEED cargo test -p frob-spec ftask::` (the unit tests above, including the 10,000
   seeded round trips and the 10,000 single-byte mutations).
2. `golden`: `cargo run -p frob-spec --example ftask_id -- crates/frob-spec/tests/golden/kitchen-tray.ftask.json
   --json` prints the `TaskId`, the canonical-bytes digest and the section, atom, online, example and draw counts;
   the script asserts the counts of the first acceptance criterion and that re-serialization is byte-identical.
3. `identity`: the same example on a key-shuffled copy and a whitespace-padded copy written under `work/` (same
   `TaskId`), and on copies with one scale (`0.10 m` → `0.11 m`), one window bound and one comparator changed (three
   different identities).
4. `refusals`: the example on planted files (missing section, duplicate atom name, signal on an undeclared clock,
   two verdict formulas, no `req` clock, `frob.task/2`, a misspelt field, a duplicate key): each exits 3 with its
   code (`task-structure-invalid` with its kind, FROB-REF-891, FROB-REF-103) and the pointer to the field.
5. `controls`: the two negative controls below through `e2e_expect_caught`, each its planted-defect build running
   the test that must fail.

NDJSON under `target/e2e-logs/spec_ftask_format/<utc>.ndjson` with a transcript beside it; every line carries
`ts`, `script`, `bead` (`N24a-02`), `step`, `event`, the exact command line, exit code and wall time, the evidence
block (class D0 identity), the `TaskId` values compared as digests, the refusal block (code, pointer, kind) of
each planted file, round-trip and mutation counts against 0 differences, and on failure the first differing byte
offset with the file path; a final `summary` line. The same checks through `frob task new` and `frob task show
--json` (both envelopes carrying the same `bound.task`) are the `ftask-*` steps of
`scripts/e2e/arena_requirement_pipeline.sh` (N24a-42), a script with steps of its own that does not run this one
(its one stage is BD-121's campaign script).

### Known answers and negative controls

- Format known answer: the objects `{"b":1,"a":2}` and `{"a":2,"b":1}` have one identity.
- Negative control (the control of GATE-WS-02): a reader built with key-order canonicalization disabled must fail
  `key_order_is_not_identity`.
- Negative control: a reader that tolerates unknown required fields must fail `unknown_major_version_refused`'s
  sibling case with an unknown required field.
- Metamorphic relation MR-35 (canonical bytes): key order and whitespace do not change an identity; canonical →
  value → canonical is exact.
- Determinism: identity is class D0; the test runs in debug and release and on both operating systems and compares
  the `TaskId` of the worked task.

## Considerations

- The exposure-domain declaration of each draw and the information-contract digest are defined by other beads and
  enter the identity when they land; adding them as required fields is a major-version question that must be settled
  before the first release of the format (otherwise every `TaskId` changes once).
- Optional fields that later beads of the chapter add to `frob.task/1`, each as an optional addition that keeps
  the major version and enters the identity only when present: the `:intent` tag on an online signal (N24c-21);
  `wrench_command` (N24c-18); `:domain` with its keys on a randomization draw and `:alternatives` for a draw with
  more than one legal keying (N24c-36, N24c-40); the `stages` list inside the `study` section that names reporting
  stages by atom or online-signal identifier (N24a-11); the reward-term kind that references an online requirement signal,
  which exists only if KILL-SPEC-REWARD does not fire (N24a-14, N24a-15). A reader that does not know one of them
  refuses the file as written by a newer minor version; it never drops the field.
- Labelled examples are referenced by trace digest, so a task's identity depends on its examples. That is intended:
  an example added by a task audit yields a new `TaskId`, so results always cite the task they ran under.
- Fuzzing of the reader (10⁷ executions with zero panics before the format's first release) is scheduled with the
  importer fuzz targets and limits; this bead supplies the fuzz entry point.
- Privacy: a task file may name a private scene family; the `TaskId` and file are then private by inheritance, and
  logs print identifiers only.
