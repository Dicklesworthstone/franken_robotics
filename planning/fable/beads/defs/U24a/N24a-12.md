## Background

A requirement is written by a person or an agent, and writers of temporal logic are often wrong. FACT (source
register): a 2023 language model translated natural-language statements into temporal-logic formulas with 77.7%
accuracy over 300 samples. A formula that parses, type-checks and has consistent units can still say the wrong
thing: "eventually in the goal" where "in the goal and stopped" was meant; `<` where `>` was meant; a hard limit that
no trace can ever violate because its signal is constant.

The unit checker cannot see such errors, because they are errors of meaning. The remedy is to make the writer state
the meaning twice, once as a formula and once as examples, and to refuse the requirement when the two disagree.
DESIGN: a requirement is admitted only with labelled example traces: at least two satisfying and two violating, with
one near the boundary of each comparator. `task.check` runs the monitors on the examples and refuses a requirement
whose labels disagree (FROB-REF-539). It also runs a mutation check: reversing a comparator or deleting an atom must
change the label of at least one example. An atom that no example can distinguish is reported as vacuous, and a
vacuous hard-limit atom is a refusal.

The mutation check is the important half. Examples that all sit far from every boundary agree with almost any
formula; they test nothing. Requiring that each atom, mutated, flips at least one example forces the example set to
exercise each atom, in the same way that a negative control forces a gate to be able to fail.

This mechanism is the checkable core behind the requirement-writing gate (GATE-ARENA-09: on 50 scripted mission
statements at most 20% of first-draft requirements mislabel a trajectory, and `task.check` rejects every draft that
does).

## Technical approach

**Example traces.** An example is `(example <TraceRef> satisfied|violated)`, where `TraceRef` is the digest of a
trace in the content store. A trace is either a recorded episode (`.frun`) or an authored synthetic trace: a `.frun`
fragment holding only the Task-stream channels the requirement reads, on their declared clocks, marked `synthetic`
in its manifest (so a requirement can be written before any simulator run exists). An example must cover the reach of
the verdict; one that evaluates to `undetermined` is refused as an example (`undetermined` and `invalid` never
agree with a label). A trace is a table with one column per signal the requirement reads, sampled on each signal's
own clock, with the clock table and the horizon. Traces are stored in the task registry of `frob-arena` by hash;
the task file holds only hashes. Example traces may come from private scenes: a trace inherits the private mark,
and the report never echoes sample values from a private trace.

**Admission rules, in order.** Each failure is FROB-REF-539 with a pointer and repairs.

1. *Counts.* At least two examples labelled `satisfied` and two labelled `violated`.
2. *Agreement.* Every example is evaluated by the definitional evaluator (N24a-04) and by the offline evaluator
   (N24a-09). If the two evaluators disagree with each other the result is an internal fault, not a refusal. If
   they agree with each other and disagree with the label, the requirement is refused; the report names the example,
   the label, the monitor's verdict, the margin, the binding atom and its time, so the writer sees whether the
   formula or the label is wrong.
3. *Near the boundary of each comparator.* For each atom, let m be the smallest |ρ| the atom attains, over all
   examples, at ticks the verdict reads. DESIGN (this bead's elaboration of "near"): the atom has a near-boundary
   example if m ≤ 0.1, that is, some example comes within a tenth of the atom's scale of its threshold; `:exact`
   atoms are exempt from the distance (their margin is ±1) and instead need the examples to show both sides: the
   atom's truth value changes at some tick of one example, or it is true in one example and false in another at
   ticks the verdict reads. A missing near-boundary example is a refusal (FROB-REF-539) for every comparator, hard
   limit or not, because the rule of admission is "one near the boundary of each comparator". (One draft of this
   stage refused only for hard-limit atoms and reported the others with exit code 2; that softening is not adopted,
   and the requirement-writing pilot N24a-33 is where it would be reconsidered if the strict rule refuses correct
   drafts.) The threshold 0.1 is a task-level setting recorded in the check report.
4. *Mutation check.* For each atom that the verdict formula references, directly or through an online signal it
   names, two mutants of the requirement are formed: (a) the comparator reversed (`>` ↔
   `<`, `>=` ↔ `<=`; for `=`, the atom negated: the direction is reversed and the strictness kept, where the other
   draft exchanged `>` with `<=`, which is the logical negation and differs only on the boundary itself); (b) the
   atom deleted, meaning replaced by the neutral element of the connective it sits under, in the position where it
   occurs: the constant true (margin +∞) under `and` and as the sole operand of a temporal operator, the constant
   false (margin −∞) under `or`. Each mutant is evaluated on every example. A mutant is *killed* if at least one
   example's verdict differs from its label under the mutant. The result is a kill matrix (atom × mutant → the
   examples that kill it).
5. *Vacuity.* An atom neither of whose mutants is killed is vacuous with respect to the examples: no example can
   distinguish the requirement from one without it. An atom whose reversal is killed and whose deletion is not is
   *redundant* in these examples (no violating example fails on this atom alone); that is reported and is not a
   refusal. Vacuous atoms are reported; a vacuous hard-limit atom is a refusal (FROB-REF-539,
   detail `vacuous-hard-limit`); any other vacuous atom is a finding (exit code 2). An atom both of whose mutants
   are killed is `exercised` (the other draft's word was `distinguished`). Hard-limit atoms are those of the
   verdict's invariant part, as derived in N24a-13 (every atom in the left operand of an outermost until, and every
   atom in the body of an outermost always whose window starts at 0), plus any atom the task marks as shared with a
   runtime shield. The definition is syntactic: a task that writes hard limits in another form should mark them
   explicitly, and the report says which atoms were treated as hard limits. Atoms read only by online signals that the verdict does not
   reference (in fixture 1, `saturated` and `advancing`, which serve the `stalled` signal) are listed `online-only`
   and are outside the mutation check, because no change to them can change a verdict.

**Ranked repairs for FROB-REF-539.**

| Cause | Repairs, in order |
|---|---|
| No examples, or too few of one label | Record or author the missing examples; the report lists how many of each label exist |
| Label disagreement | (1) Correct the formula at the binding atom named in the report; (2) correct the label if the trace was mislabelled |
| No near-boundary example for an atom | Add an example within the stated distance of the atom's threshold, on the side named |
| Vacuous hard-limit atom | Add a violating example in which only this atom fails; or remove the atom if it is not intended |

FROB-REF-539 reads "A requirement has no labelled examples, or the monitor disagrees with a label"; exit code 3,
`retry: after-change`.

**Arithmetic.** Every evaluation follows the evaluators' rule that an atom inside the guard band of 2⁻²¹ around zero
is re-evaluated with its declared comparator in exact or double-precision arithmetic (N24a-10). Evidence of the
report: class `Tested`, tier `static`.

**Cost.** For A atoms and E examples the check performs (1 + 2·A)·E offline evaluations plus E definitional ones;
with A = 8 and E = 4 on 20 s traces at 50 Hz this is 68 evaluations of 1,000 ticks, well under a second.

**Report (part of the `task.check` result).** Per atom: scale, hard-limit or not, nearest example and its m, kill
matrix row, classification (`exercised`, `redundant`, `vacuous`). Per example: label, verdict, margin, binding atom
and time, decided-at. The report is a pure function of the task and the example traces (class D0 for exact atoms, D2
otherwise) and is memoized on the `TaskId`.

## Acceptance criteria

- [ ] A task with no examples, with one satisfying example, or with an example that does not cover the reach is
      refused with FROB-REF-539 (an example row of GATE-ARENA-03).
- [ ] The goal-region case: requirement `(F (0 s 10 s) in_goal)` with a sled trace (constant 1 m/s through a goal
      region x ∈ [4.9, 5.1] m, inside it for t ∈ [4.9, 5.1] s) labelled `violated` is refused, with the report
      showing the monitor's `satisfied`; the amended `(F (0 s 10 s) (H (0 s 2 s) in_goal))` agrees with that label
      (the sled's longest stay is 0.2 s < 2 s) and with a `satisfied` label on a body at rest at x = 5 m from
      t = 6 s (satisfied from t = 8 s).
- [ ] On the fixture 1 requirement with two satisfying and two violating examples, none of the five verdict atoms
      (`tilt-ok`, `current-ok`, `no-strike`, `cleared`, `upright`) is `vacuous`, and `saturated` and `advancing` are
      listed `online-only`.
- [ ] A planted requirement with a hard-limit atom on a constant signal is refused as vacuous; the same atom outside
      the invariant part is reported and the check exits with code 2.
- [ ] A comparator reversal on any atom of the kitchen-tray requirement is killed by at least one of its four
      examples.
- [ ] The kill matrix is identical on repeat and across platforms.
- [ ] A requirement with one label flipped is refused with FROB-REF-539, naming the example and the binding atom; a
      requirement with one comparator reversed is refused (some example disagrees) whenever the atom is not vacuous.
- [ ] A comparator with no near-boundary example is refused, with the atom and the side named.
- [ ] On the extended set of the requirement-writing pilot (N24a-33), every draft that mislabels one of its 20
      hidden trajectories is rejected once those trajectories are supplied as examples (the `task.check` clause of
      GATE-ARENA-09).
- [ ] Reachable through `frob task check --json`; cancellation between examples leaves no partial report.

## Test plan

### Unit tests

- `counts_rule`: (0, 0), (1, 2), (2, 1) refused; (2, 2) passes rule 1.
- `label_disagreement_reports_binding_atom`: the sled case; asserts refusal, monitor verdict `satisfied`, binding
  atom `in_goal`.
- `amended_requirement_agrees`: the dwell form; sled `violated`, resting body `satisfied` decided at 8 s.
- `near_boundary_rule`: an atom with m = 0.08 passes; m = 0.3 is refused, hard limit or not; an example set whose
  smallest |margin| of `cleared` is 0.4 is refused, and adding a trace that clears by 5 mm (margin 0.05) admits it;
  an `:exact` atom with examples on one side only is refused.
- `mutants_formed_correctly`: reversal of `(>= (- 5 deg tilt) 0 deg)` is `(<= …)`; deletion replaces the atom by
  true under `and` and by false under `or`, in every formula that references it.
- `examples_agree_cart`: two docking traces and two failing traces (one strike, one timeout) against `docked`; all
  four agree.
- `flipped_label_refuses_539`: a satisfied trace labelled `violated`.
- `reversed_comparator_detected`: `upright` written `(<= (- 5 deg tilt) 0 deg)`; a satisfied example becomes
  violated.
- `vacuous_atom_reported`: add `(atom cool (>= (- 383 K temp) 0 K) :scale 20 K)` to the hard limits with examples
  in which temperature never exceeds 320 K; `cool` is vacuous and, being a hard limit, refuses.
- `deleted_atom_changes_label`: deleting `no-strike` turns the strike example from violated to satisfied.
- `undetermined_never_agrees`: a trace 6 s long under the 8 s until.
- Property `mutation_check_is_sound`: for random formulas and traces, an atom reported `exercised` has, for each
  mutant, an example whose verdict changes.
- `kill_matrix_small`: two atoms a, b; verdict `(G (0 s 3 s) (and a b))`; examples: all-good (satisfied), a fails
  (violated), b fails (violated), both fail (violated). Deleting a is killed by "a fails"; deleting b by "b fails".
  Remove the "b fails" example → b becomes `vacuous`.
- `redundant_atom`: b implies a on every example → a's deletion mutant survives and its reversal is killed.
- `evaluator_disagreement_is_internal_fault`: a test build with a broken offline evaluator.
- `undetermined_example_refused`.

### End-to-end script and logging

Steps `examples-*` of `scripts/e2e/arena_requirement_pipeline.sh` (N24a-42): `frob task check` on (i) the fixture 1

(iv) the planted vacuous hard-limit task, expecting exit 3. NDJSON lines carry the command, exit code, wall time,

### Known answers and negative controls

- Hand case (goal region): dwell of the sled 0.2 s; amended requirement violated by the sled and satisfied by the
  resting body from t = 8 s. Exact.
- Negative control (seed of a registry entry for GATE-ARENA-03 and GATE-ARENA-09): a `task.check` build that skips
  the mutation check must accept the planted vacuous hard-limit task; the gate run must catch that build.
- Negative control: a build that compares labels using the sign of the margin only must mis-handle an example whose
  margin is exactly zero under a strict comparator.
- Metamorphic relation: permuting the order of examples leaves the classification of every atom unchanged.
- Known answer KA-594 (normalised margins 0.2 and 0.3, clearance binding in metres and in millimetres) fixes the
  margins the near-boundary rule reads.
- Negative controls: a check that counts examples without running them passes the flipped label; a mutation check
  that only deletes atoms misses the reversed comparator on an atom guarded by another; a monitor that pads a
  short window agrees with the 6 s trace. Each must be caught.
- Metamorphic relation: re-expressing a trace and the task in millimetres changes no label, margin or binding atom.
- Determinism: the report bytes are compared twice on one machine and across debug and release.

## Considerations

- Examples are identity-bearing: adding one changes the `TaskId`. That is intended (results cite the task they ran
  under, examples included).
- The near-boundary threshold is a judgment; 0.1 is a starting value and the pilot of the requirement-writing gate
  (N24a-33) is where it is first exercised against real drafts.
- The check is only as good as its examples. It catches formulas that disagree with what the writer showed, not
  formulas that agree with a wrong belief; the task audit with foil bodies attacks the latter.
- Synthetic example traces are labelled `synthetic` and cannot serve as evidence for anything but admission.
- Alternative rejected: trusting review of the formula text. The 77.7% figure is the measured quality of exactly
  that.
- If the pilot shows that drafts pass their own examples and still fail hidden trajectories at a high rate, the
  admission rule is tightened (more near-boundary examples per comparator) before M3.
