## Background

An episode that starts with a foot 2 mm inside the floor begins with an impulse that no robot would feel, and a
paired comparison in which one design starts settled and the other does not compares spawn artifacts. Both are common
in batched simulators: a robot is spawned at a nominal height, falls or is pushed out of the ground in the first
steps, and the first transitions of every episode contain a transient that depends on the design's geometry. A
learner exploits it, and a paired study measures it.

DESIGN: episodes start from precomputed quasi-static poses. For each design a small cache of states that were
simulated to rest in double precision is built once, keyed by content, and every episode begins from one of them,
chosen by the world's address.

This bead builds the mechanism on the CPU at M1, because the first fixture needs it there: the cart of fixture 1
starts "stationary, centred and parallel to the lane, front axle at x = −0.50 m, settled under gravity from the reset
cache, separately for each design". The batched tiers, the vectorized environment and the gate GATE-ARENA-08 on all
reference robots follow at M2 (BD-195).

## Scope

In: the cache key and entry; the settling procedure and criterion; the store as a memo-graph node with invalidation;
selection by addressed stream; the rule that a state is never transported between designs; refusal FROB-REF-529;
the verb `task.settle` on the CPU.

Out: settling on `batch-cpu` and loading on device tiers; the `Degraded: unsettled` world flag at reset inside the
vectorized environment; GATE-ARENA-08 on every reference robot (all BD-195).

## Technical approach

**Contents.** For each (`ModelId`, spawn specification, contact law, kernel versions) the cache holds K = 64 settled
states (TARGET). A state holds: the configuration (group elements for the base and joints); contact warm starts
(feature pairs, witness points, normal and tangential multipliers); actuator states at rest (currents, winding and
thermal node temperatures at ambient, brake state); and the estimator's initial state. Velocities are zero.

```rust
// DESIGN: intent, not signatures.
pub struct SettleKey(Blake3);   // H("frob.settle/1" ‖ ModelId ‖ SpawnSpecId ‖ ContactLawId ‖ kernel versions ‖ criterion ‖ K)
pub struct SettledState {
    config: Configuration, contacts: Vec<ContactWarmStart>, actuators: Vec<ActuatorRest>, estimator: EstimatorInit,
    penetration_max: Qty, support_ratio: f64, settle_time: Qty, digest: Blake3,
}
pub struct SettleCache { key: SettleKey, states: [SettledState; 64], settled_on: Tier, receipt: Receipt }
```

**The criterion** comes from the task's `reset` section, for example
`(settled-pose :count 64 :speed-below 1e-3 :for 0.2 s :penetration-max 0.5 mm :first-impulse-within 5 %)`. TARGET
values: base and joint speeds stay below 10⁻³ in SI units (m/s for linear, rad/s for angular coordinates) for
0.2 s, with maximum penetration at most 0.5 mm. The first contact impulse after loading a cached state on any tier
must lie within 5% of the static support force.

**Settling procedure, for state i = 0 … 63.**

1. Draw the spawn perturbation i from the spawn specification (position inside the spawn region, heading, nominal
   posture perturbation, payload placement where the spawn specification varies it) on a counter-based stream keyed
   by (`SettleKey`, i). The draw does not depend on any world address: the cache is shared by every world.
2. Place the model at that pose with zero velocity and a small drop clearance above its support (DESIGN: 5 mm), with
   actuators at rest as the spawn specification says: brakes as carded, or the baseline controller's hold-posture
   command.
3. Step in double precision with the task's contact law. Interim posture at M1 (DESIGN): the only double-precision
   stepping tier that exists at M1 is the referee, so M1 settles on the referee; from M2 the settler is `batch-cpu`
   in `f64`, as the design specifies, and BD-195 rebuilds every cache there. `settled_on` records which.
4. Track the speeds and the maximum penetration over a sliding window of 0.2 s. Stop when the criterion holds, or
   at a time limit (DESIGN: 5 simulated seconds).
5. On success: zero the residual velocities, record the state, and compute `support_ratio` = ‖J/h‖ / (m·‖g‖), where
   J is the total contact impulse of one further step of length h from the recorded state, m the total mass and g
   gravity. The state is accepted only if |support_ratio − 1| ≤ 0.05 and the direction of J opposes gravity within
   the same tolerance.
6. On failure (time limit, a fall, a strike): the state is recorded as failed with its reason.
7. A cache is complete only with 64 accepted states. An incomplete cache is not usable: `task.settle` returns exit
   code 2 with the finding "the design does not come to rest at spawn in n of 64 draws", the failed draws and their
   reasons, and tasks that need the cache are refused (FROB-REF-529).

**Identity and invalidation.** The key is a content hash, so the cache is a node of the memo graph: its key is
derived from its declared inputs, never written by hand. A design edit that changes mass, geometry or contact
surfaces changes the `ModelId` and therefore the key: the old cache is simply never found again. A property test
perturbs every declared input (model, spawn specification, contact law, each kernel version, each criterion field,
K) and requires the key to change; a live-dependency test perturbs each model field the settler reads and requires
the key to change or the states to be bit-identical.

**Selection.** At reset, world w draws its pose index from a counter-based stream keyed by the world address under
the registered stream name for reset poses: index = draw mod 64 (64 is a power of two, so the reduction is
unbiased). Two designs paired on one address therefore start from the same spawn specification and the same index,
each in its own settled state. The initial equilibrium is recomputed for each design; a state is never transported
from one design to another. Loading a state whose `SettleKey` does not match the world's model is refused (the same
defect as grafting state from one model onto another in a fork).

**Refusal.** FROB-REF-529: no settled-pose cache for this model and task. Raised at admission of a run, an
evaluation or a study, before any stepping. Ranked repairs: (1) run `frob task settle <task> --model <id>` (the
envelope's `next_actions` carries the exact command); (2) if settling fails, the finding from step 7 names the spawn
draws to fix.

**The verb `task.settle`** (kind `run`; a long tool: it accepts a bounded synchronous wait and otherwise returns a
job handle, exit code 8). Input: task, model, optional `--refresh`. Output: the `SettleKey`, counts of accepted and
failed states, per-state `penetration_max`, `support_ratio` and `settle_time`, the tier settled on, and the receipt.
It is idempotent: a complete cache under the same key returns the stored receipt without stepping. Evidence block:
class Tested, tier `referee` (M1), determinism class D2, the no-authorization flags.

## Acceptance criteria

- [ ] `frob task settle` builds a complete 64-state cache for the fixture 1 cart, design A and design B separately;
      every state has penetration at most 0.5 mm and `support_ratio` within 5% of 1; the two caches have different
      keys.
- [ ] A second `task.settle` with the same inputs performs no stepping and returns the same receipt.
- [ ] Changing the front-wheel radius (design A to design B), the payload mass, a contact-law parameter or a kernel
      version changes the key; changing a controller gain that is not part of the model does not.
- [ ] A run of a task whose cache is missing is refused with FROB-REF-529 before any step, with the repair command.
- [ ] Two designs paired on the same 64 world addresses receive identical pose indices.
- [ ] Loading design A's state into design B is refused.
- [ ] The first step after loading any cached state on the referee produces a contact impulse within 5% of static
      support (for design A: 8.000 kg × 9.81 m/s² = 78.48 N; for design B: 8.225 kg × 9.81 m/s² = 80.69 N).
- [ ] Cancellation of `task.settle` mid-build leaves no partial cache visible; a resumed build completes.

## Test plan

### Unit tests

- `key_changes_with_each_input`: one test case per declared input of the key.
- `key_ignores_controller_gain`.
- `index_stream_is_address_keyed`: indices for addresses (17, k, 0), k = 0 … 63, are identical for two models and
  differ from the indices under another run seed; adding an unrelated random stream changes none of them.
- `index_mod_is_unbiased`: over 2²⁰ addresses each of the 64 indices occurs within exact binomial bounds.
- `box_on_plane_settles`: a 1 kg uniform box on a level plane under the compliant contact law: comes to rest;
  penetration equals the law's static value m·g/k for the law's normal stiffness k (hand calculation) and is below
  0.5 mm; `support_ratio` = 1 within 10⁻⁶.
- `unsettled_spawn_is_caught` (the motivating case): a body placed 2 mm inside the floor with no settling: the first
  impulse exceeds static support by far more than 5%; the acceptance test of step 5 rejects it.
- `incomplete_cache_is_unusable`: a design that tips over in 3 of 64 draws → exit code 2, 3 failed draws listed,
  FROB-REF-529 for a dependent task.
- `no_transport_between_designs`.
- `idempotent_build`.

### End-to-end script and logging

`scripts/e2e/task_settle.sh`: `frob task settle fixture:cart-sill-dock --model <A>` and `<B>`; `frob sim run --tier
referee` of the nominal case for each; `frob telemetry query` for the first-step contact impulse; then a planted run
against a model with no cache (expects exit 3, FROB-REF-529), and a re-run of `task settle` (expects
`idempotent_replay` or an unchanged receipt). NDJSON under `target/e2e-logs/task_settle/` records: command, exit
code, wall time, the evidence block, per-state penetration (mm, threshold 0.5), support ratio (threshold 1 ± 0.05),
settle time, both cache keys, and the refusal block of the planted run.

### Known answers and negative controls

- KA-601 (stated for the gate at M2): on all 64 states, penetration at most 0.5 mm and first impulse within 5% of
  static support; negative control: a design edit must invalidate the cache. This bead meets the row for the cart
  on the referee.
- Fixture 1 mass roll-up (KA-602) supplies the static support forces: 8.000 kg and 8.225 kg.
- Negative control: a cache keyed by design *name* (not content) must fail `key_changes_with_each_input` when the
  wheel radius changes under the same name.
- Negative control: the warm start of the 60 mm design grafted onto the 75 mm design (the fork known answer of the
  record subsystem) must be refused here too.
- Determinism lanes: the cache digest is identical when built twice on one machine, in debug and release, and with
  different worker counts (class D2 on the referee).

## Considerations

- Tension recorded for the lead: the design says states are settled on `batch-cpu`, which does not exist until M2,
  while fixture 1 needs the cache at M1 on the referee. The interim posture above (settle on the referee at M1,
  rebuild on `batch-cpu` at M2) keeps both statements true at their milestones.
- Per-world randomization (friction, payload shift) can make a cached state slightly out of equilibrium in a given
  world; that is what the first-impulse check at load and the `Degraded: unsettled` count are for (BD-195).
- A design that cannot stand at spawn is a finding about the design, reported before any episode is spent on it.
- Memory: 64 states of a 30-body robot are a few hundred kilobytes; the cache is negligible against scene data.
- K = 64 and the three thresholds are TARGET values; they live in the task's `reset` section, so changing them is a
  new `TaskId` and a new key.
