## Background

A scorecard is what an agent reads to decide whether a design is good, and so it is the thing an optimizing agent
will learn to game. The cheapest way to raise a success rate is to shrink its denominator: let the hard scenarios
fault numerically and drop them, mark impossible scenarios as "not applicable" and forget them, or quietly remove a
scenario from the battery. Risk RISK-15 names it: agents optimize the scorecard instead of the robot, including by
moving failures out of the denominator; its trigger is scorecard columns that do not sum to the battery size, or a
battery whose identity changed.

Decision ADR-ARENA-09: an infeasible scenario is kept and counted. A failure is a failed cell, never an excluded
cell, and a suite that sheds its impossible cases reports a success rate over a population nobody declared.

DESIGN: a scorecard is a table of metrics by scene class with intervals, normalized against the reference robot of
the same class. No single scalar is reported unless the task defines one. Every scenario of a battery lands in
exactly one outcome column (INV-ARENA-03: every scenario of a battery appears in exactly one outcome column, and the
columns sum to the battery size). Success rates are printed with two denominators, all scenarios and scenarios not
shown infeasible, side by side. Removing a scenario from a battery is a recorded event with a reason and changes the
battery's identity.

The normalization against a reference robot is there for the reader: every number has a familiar baseline beside
it, so "cost of transport 0.42" reads as "1.3 times the reference quadruped on the same stairs".

## Scope

In: the scorecard data model and schema; the seven outcome columns and the classification rule that puts each
scenario in exactly one; the two denominators; rows by scene class with intervals; normalization against the
reference robot; the "no single scalar" rule; the scorecard's binding to one battery identity (the manifest,
`BatteryId` and removal events themselves are N24b-01's); the accounting invariants as property tests from M1.

Out: metric definitions (N24a-17 to N24a-21); the batteries `smoke`, `fixtures`, `standard`, `full`, `hard`,
`covering` and the recording of GATE-ARENA-07 at M3 (BD-254); the infeasibility witnesses (the solvability oracle of
the adversarial-search subsystem); the verbs `eval.run` and `eval.scorecard`.

## Technical approach

**1. Outcome columns.**

| Column | Meaning |
|---|---|
| `satisfied`, `violated` | Verdicts, the second broken down by failure class |
| `undetermined` | The trace did not cover a window; the reason is listed |
| `invalid` | Numerical fault. Counted as a study error and as a failure of the tier, never dropped |
| `infeasible-for-candidate` | A checked necessary condition shows that this body cannot satisfy the requirement in this world; the witness is attached |
| `infeasible-for-class` | The same for every body of the declared class; evidence that the scenario should leave the suite by a recorded decision, not by attrition |
| `refused` | The run was not admitted; the refusal code is listed |

**2. Exactly one column: the classification rule** (DESIGN; evaluated per scenario, first match wins):

1. The run was not admitted → `refused` (with its refusal code).
2. A class-level infeasibility witness exists for (task, scenario, declared class) → `infeasible-for-class`.
3. A candidate-level witness exists for (task, scenario, model) → `infeasible-for-candidate`.
4. Otherwise by the verdict record's value: `invalid`, `undetermined`, `violated`, `satisfied`.

An infeasibility column needs a *checked necessary condition* with its dual vector or bottleneck named; a failed
search, a refusal or a simulator fault is never a witness. If a scenario with a witness nevertheless has a
`satisfied` verdict, it stays in its infeasible column and carries the flag `satisfied-despite-witness`: either the
witness or the simulation is wrong, and neither possibility may add a success. A scenario of the battery with no
record at all (not yet run) makes the scorecard `incomplete`; an incomplete scorecard prints its progress with a
denominator and no rates.

**3. Two denominators.** With N the battery size and the column counts as above:

    success over all scenarios           = satisfied / N
    success over not-shown-infeasible    = satisfied / (N − infeasible-for-candidate − infeasible-for-class)

Both are printed side by side, each with its exact interval. Nothing else is ever subtracted from a denominator:
`invalid`, `undetermined` and `refused` scenarios stay in both.

**4. Rows and cells.** Rows are scene classes (a terrain family, an interior archetype, or the fixture's
conditions). Columns are the metrics the task lists, each cell holding: value, unit, interval, n, and the same
metric for the reference robot of the class on the same scenarios with the ratio candidate/reference. The reference
robot is the imported public model on file for the design's archetype; twelve of the eighteen archetypes have no
permissively licensed reference model, and for those the baseline is the archetype's own template (OPEN-ARENA-2
tracks the hexapod). Intervals: exact Clopper–Pearson for rates; the stratified bootstrap of the evaluation protocol
for continuous metrics, with strata equal to the rows and resampling by addressed streams; clusters as units where
scenarios share one.

**5. No single scalar.** The scorecard has no "overall score" field. If and only if the task defines a score, the
scorecard prints it, labelled as the task's score, beside (never instead of) the columns. An API consumer that needs
one number must name the metric.

**6. Battery identity.** The manifest, `BatteryId` and the membership events are N24b-01's (a dependency), which
governs; restated so that this bead reads alone. A battery is a set of scenarios (items), each identified by the
hash of its canonical form (`ItemId`: task, world with its addresses, disturbance law, family of initial
conditions); `BatteryId` is the BLAKE3 hash of the canonical JSON of `{schema, name, robot_class, lane, selection,
items: [ItemId sorted]}`, so the order of items does not matter and any change to the set changes the identity.
Removing a scenario is done only through a recorded event (`frob.battery.event/1`: the old and new `BatteryId`,
the items added and removed, a non-empty reason, the actor, the ledger sequence), declared in the events file
beside the manifest and written to the ledger before the first run on the new identity; a manifest whose items
differ from the last registered identity with no declared event is refused at load (`battery-manifest-invalid`,
kind `no-event`, exit code 3), so no run and no scorecard exists for a silently shortened battery. What this bead
adds: a scorecard cites the `BatteryId` and the item list of the run record it was computed from, and n is checked
against that list; the constructor takes run records of one `BatteryId` and returns an error for records of two
(the refusal the verb shows for it is `eval.scorecard`'s, N24c-04), so two scorecards over differently sized
batteries cannot be confused.

**7. Schema and type (DESIGN).**

```rust
pub struct Scorecard {
    battery: BatteryId, task: TaskId, model: ModelId, controller: ControllerId, tier: Tier,
    outcomes: OutcomeCounts, n: u32, success_all: Rate, success_not_infeasible: Rate,
    rows: Vec<SceneClassRow>, task_score: Option<ScoreCell>, metrics_registry_version: Blake3,
    reference: Option<ReferenceBaseline>, frontier: CommitSeq, evidence: ClaimProduct, no_authorization: NoAuthorization,
}
pub struct OutcomeCounts {
    satisfied: u32, violated: Map<FailureClass, u32>, undetermined: Map<Reason, u32>, invalid: u32,
    infeasible_for_candidate: u32, infeasible_for_class: u32, refused: Map<RefusalCode, u32>,
}
```

Schema name `frob.scorecard/1`. Constructor invariant (checked, not assumed): the column counts sum to n, and n
equals the battery size; a violation is an internal fault that refuses to print. The scorecard names the committed
frontier it was computed at and carries the claim product of its inputs (the weakest evidence class, tier and
determinism class among its verdicts) and the three no-authorization flags.

Members that later beads add to `frob.scorecard/1`, each an optional addition that keeps the major version and that
this bead's schema and type reserve: in the metadata block, each metric's `smoothness`, the attribute of its record
in `registries/metrics.toml` (N24ax-04, M2); in the header, the `unmonitored` stamps of the run's results, each
`{class, pending, episodes}` (the failure class, the bead whose monitor is pending, and the count of episodes the
stamp covers; N24a-38, M3, which also extends this constructor so that results stamped under the monitor waiver
flag are rejected, while results under a `pending` row are admitted and stamped); the hazard counts
`hazards_drawn_unguarded` and `hazards_uncovered` with the row identifiers behind each (NEG-29); and the labels
`in-sample` (N24a-31) and `baseline-only: unranked` (N22c-51). A scorecard that lacks a member whose bead is in the
build fails the schema test of that bead.

## Acceptance criteria

- [ ] On 100 random batteries with random outcomes (including every column), the columns sum to the battery size and
      each scenario appears in exactly one column (INV-ARENA-03).
- [ ] A planted infeasible scenario appears in its column and in the all-scenario denominator, and is absent from the
      second denominator only.
- [ ] A scenario with a numerical fault appears under `invalid` and in both denominators; a build that drops it is
      caught.
- [ ] A battery shortened by one scenario without the recorded event cannot be scored: the load is refused
      (`battery-manifest-invalid`, kind `no-event`) and the refusal prints the computed identity, which differs from
      the registered one (a silently shortened battery changes identity); with the event, the scorecard cites the
      new `BatteryId` and n = N − 1, and the event is in the ledger. Run records of two `BatteryId`s cannot be
      built into one scorecard.
- [ ] Both success rates are present in every scorecard, each with an exact interval; no "overall score" exists
      unless the task defines one.
- [ ] Every cell carries unit, n, interval and the reference robot's value. (The reference baseline scorecards of
      the M1 task families are recorded by BD-125, which depends on this bead through the verbs.)
- [ ] A scorecard serializes to `frob.scorecard/1` with the evidence block and the frontier and validates against
      the schema (`cargo test -p frob-arena scorecard`); `scripts/e2e/arena_scorecard_table.sh` passes; the same
      object through `frob eval scorecard --json` is asserted by the verb's bead (N24c-04) and by the `scorecard-*`
      steps of N24ap1-01, which depend on this one.

## Test plan

### Unit tests

- `columns_sum_to_battery_size`: property test over 100 random batteries (the gate's figure) and 10⁴ further ones.
- `exactly_one_column`: scenarios with overlapping conditions (refused and with a class witness; with a candidate
  witness and a `violated` verdict; with a witness and a `satisfied` verdict) land where the rule says; the last
  carries `satisfied-despite-witness` and is not a success.
- `two_denominators`: N = 20: 12 satisfied, 4 violated, 1 undetermined, 1 invalid, 2 infeasible-for-candidate →
  12/20 = 0.600 and 12/18 = 0.667.
- `invalid_never_dropped`: the same battery with the invalid scenario removed from the input must fail the size
  check (n = 19 ≠ 20).
- `removal_changes_identity`: a three-item manifest (labelled `synthetic`) with item 2 removed and no event →
  `battery::resolve` returns `battery-manifest-invalid` (`no-event`) whose `observed` identity differs from the
  registered one; with the declared event → a new `BatteryId`, the ledger row present, and the scorecard built from
  the new run cites it with n = 2.
- `scorecard_one_battery`: the constructor given run records carrying two different `BatteryId`s returns an error
  naming both identities and builds nothing.
- `no_overall_scalar`: schema has no such field; a task-defined score appears only when declared.
- `incomplete_scorecard_prints_progress_only`: 17 of 20 run → "17 of 20", no rates.
- `reference_normalization`: candidate cost of transport 0.42, reference 0.32 on the same scenarios → ratio 1.3125,
  both raw values present.
- `failure_class_breakdown_sums`: the per-class counts under `violated` sum to the `violated` total.

### End-to-end script and logging

`scripts/e2e/arena_scorecard_table.sh [--seed S]` (owned by this bead; default seed 2422; idempotent; sources the
STD-E2E helper). `eval.run` and `eval.scorecard` come after this bead (N24c-04), so the script drives the
scorecard through its tests, N24b-01's example `battery_resolve` and this bead's example `cargo run -p frob-arena
--example scorecard_build -- --battery <name> --records <dir> [--registries <dir>] --json`, which resolves the
battery, builds the scorecard from stored verdict records (N24a-11's `frob.verdict/1`) and prints
`frob.scorecard/1` or the error as JSON. Steps:

1. `unit`: `FROB_TEST_SEED=$SEED cargo test -p frob-arena scorecard` (the property tests over 100 random batteries
   and 10⁴ further ones, the schema validation and the unit tests above).
2. `accounting`: `scorecard_build` on a 20-scenario fixture battery (`synthetic`, in a scratch registry copy made
   with `e2e_registries_scratch`) and its 20 planted records under `crates/frob-arena/tests/fixtures/scorecard/twenty/`:
   15 `satisfied`, 2 `violated` (one `fall`, one `collision`), one numerical fault (`invalid`), one refused scenario
   with its code, and one doorway narrower than the body whose witness is a fixture record labelled `synthetic`
   (the checked necessary condition "body width 0.62 m > doorway width 0.55 m" with the bottleneck named); asserts
   the seven column counts summing to 20, success 15/20 = 0.750 and 15/19 = 0.789 each with its exact interval,
   the witness reference in `infeasible-for-candidate`, and no overall scalar.
3. `bare-label`: the same with the doorway's witness replaced by a bare "infeasible" label: the classifier rejects
   it as a witness and the scenario lands in its verdict's column.
4. `identity`: in the scratch registry the battery's manifest missing one scenario under the same name:
   `battery_resolve` refuses it (`battery-manifest-invalid`, kind `no-event`) naming a computed `BatteryId`
   different from the registered one; with the removal declared as an event with a reason, the new `BatteryId`
   resolves and `scorecard_build` on the 19 remaining records cites it with n = 19; given records of both
   identities it builds nothing and names both.
5. `controls`: `e2e_expect_caught` on the three planted-defect builds registered against GATE-ARENA-07 (features
   `nc-subtract-invalid`, `nc-second-denominator-only`, `nc-identity-is-name`), each running the test that must
   fail.

NDJSON under `target/e2e-logs/arena_scorecard_table/<utc>.ndjson` with a transcript beside it; every line carries
`ts`, `script`, `bead` (`N24a-22`), `step`, `event`, the exact command, exit code, wall time, the evidence block,
the seven column counts, N, both rates with intervals, both `BatteryId`s as digests, a `refusal` event with name,
kind and pointer, and on failure the first differing column with the fixture path; a final `summary` line naming
GATE-ARENA-07 (its clauses are exercised here; BD-254 records the gate at M3). The same accounting through `frob
eval run` and `frob eval scorecard --json` is the `scorecard-*` steps of `scripts/e2e/arena_scorecards.sh`
(N24ap1-01, a script with steps of its own that does not run this one); from M3 that step obtains the doorway's witness from `frob nemesis
oracle` (BD-271) and asserts that the two witnesses name the same bottleneck.

### Known answers and negative controls

- KA-600 (scorecard accounting on 100 random batteries): a planted infeasible scenario appears in its column and in
  the all-scenario denominator; columns sum to the battery size; exact. Negative control: a silently shortened
  battery must change identity.
- Negative controls registered against GATE-ARENA-07: (1) a builder that subtracts `invalid` from the denominator;
  (2) a builder that reports only the second denominator; (3) a battery whose identity is its name.
- Adversarial-search known answer that feeds this bead: a planted impossible trap (a doorway narrower than the body)
  is `infeasible-for-candidate` with the bottleneck named, never a counterexample.
- Metamorphic relation: permuting the scenarios of a battery (with the same set) changes no count; the identity
  uses a canonical order.
- Determinism: counts are class D0 given the verdict records; compared across debug, release and platforms.

## Considerations

- GATE-ARENA-07 is recorded at M3 with the batteries (BD-254); this bead makes its three clauses true by
  construction from M1 and keeps them as property tests.
- `infeasible-for-class` is evidence that a scenario should leave the suite; leaving is a recorded decision by
  whoever owns the battery, not an automatic step.
- A scorecard over a private scene family is private; receipts of the blinded qualification lane never contain a
  scorecard row.
- What would make us revisit: a need for composite scores in optimization. The optimizer may define an objective,
  but it is the optimizer's, is named, and is not printed as a property of the design.
