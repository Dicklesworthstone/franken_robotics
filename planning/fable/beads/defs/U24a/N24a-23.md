## Background

Arena defines what a robot is asked to do. Tasks are grouped into families: sets of tasks that share a purpose, a
requirement shape and a kind of scene, and that arrive together at a milestone. The families are the vocabulary of
every later comparison: the scorecards are per family, the rank-agreement records are per morphology class and task
family, and the sealed mission suite of the ten-fold test draws its cells from robot class × world type using these
families.

| Family | Example tasks | First milestone | Bead that ships it |
|---|---|---|---|
| Stand and recover | Stand for 10 s; recover from a push of stated impulse | M1 | BD-125 |
| Threshold delivery | A loaded cart crosses a door sill and docks on the run-out (fixture 1) | M1, CPU | BD-125 with BD-123 |
| Timed docking | Reach a pose with zero velocity by a deadline under a hidden plant gain (the exact mission slice; its boundary case is a known answer of this chapter) | M1, CPU | BD-125 |
| Velocity tracking | Commanded planar velocity and yaw rate on flat and rough ground | M2 | BD-201 |

| Split-grip landing | A quadruped climbs a ramp onto a landing with a low-grip strip (fixture 2) | M2 | BD-202 |
| Interior navigation | Point goal through doors and thresholds in each archetype | M3 | BD-253 |
| Payload transport | Carry or tow a stated mass along a warehouse route, including a ramp | M3 | N24a-26 |

The rule of the chapter: every family ships at least one task with a requirement, labelled example traces and a
reference-robot baseline scorecard. The reason for making it a mechanical rule: a family that exists only as a
reward function and a success flag is the thing this subsystem replaces, and "we will add the requirement later" is
how such families stay. A family is not listed as available until the three artifacts exist.

## Scope

In: the registry file and loader; the family record; the completeness check; where task files live; the catalog an
agent reads; the common task skeleton that family beads fill.

Out: the content of each family (the beads in the table); fixtures 1 and 2 (their own seed beads); the verbs
`task.list` and `task.show` (BD-122), which read this registry.

## Technical approach

**1. The registry.** `registries/task-families.toml`, one record per family:

```toml
[[family]]
id              = "velocity-tracking"
name            = "Velocity tracking"
first_milestone = "M2"
robot_classes   = ["legged", "wheeled"]                # which morphology classes the family applies to
scene_classes   = ["terrain/flat", "terrain/rough"]
requirement_shape = "always(hard limits and (settling or tracking))"
tasks           = ["t:velocity-track-flat@…", "t:velocity-track-rough@…"]     # TaskIds, content addresses
baselines       = [{ task = "t:velocity-track-flat@…", robot = "ref:quadruped", scorecard = "sc:b3:…" }]
status          = "available"                           # planned | partial (missing items named) | available
```

The registry exists because three things read it: `task.list` (grouping by family), the completeness check below,
and the catalog resource. It is schema-valid from the workspace bootstrap and filled by the family beads.

**2. The completeness check** (a test in `frob-arena` and a step of the reproducibility harness; it is not a new
`xtask` subcommand). For every family whose status is `available`, at least one listed task must have:

1. a requirement that passes every static check of the language (units, clocks, windows, reach against horizon);
2. labelled example traces that pass admission: at least two satisfying and two violating, one near the boundary of
   each comparator, labels agreeing with the monitors, the mutation check passed with no vacuous hard-limit atom
   (N24a-12);
3. a recorded baseline scorecard for the reference robot of each applicable robot class (or the archetype's own
   template where no reference model is on file), with its `TaskId`, `SceneId`s, `ModelId`, controller identity,
   seed and tier, so that it can be reproduced (N24a-24).

A family missing any item has status `partial` with the missing items named; reports and the catalog say `partial`,
never `available`. A task listed in a family must exist in the content store under its `TaskId`.

**3. Where tasks live.** Authored task files are in `assets/tasks/<family>/<name>.ftask` (canonical JSON, with the
S-expression view beside it for reading); fixtures are registered in `frob-arena`. Each task directory also holds its
labelled example traces (referenced by digest) and a short `README` stating what the family tests in a robot and
which failure quantities it exposes. A task is identified by its content address; a name is a label.

**4. The common skeleton.** Every family task fills the nine sections of the task file. The registry fixes four
conventions so that families are comparable:

- *Requirement shape.* Hard limits as the invariant part of an until or an always, so that hard-limit atoms are
  derivable and early termination has a decision signal; a goal as a past-time dwell, so that it cannot latch.
- *Randomization.* Every draw traces to an uncertainty on a card or a row of a hazard registry and is bound to a
  named stream; there are no free-floating ranges.
- *World.* A scene family with a split, grouped by the unit that shares a generator draw (a building, a terrain
  tile set); evaluation uses the held-out side.
- *Study default.* The task names its default study type, effect margin, rule, level and budget; where the default
  is fixed-n the task records the reachable verdicts at that n (for the paired rule of fixture 1 at level 0.05: no
  practical tie is reachable at n = 64; at n = 128 the rule can return all four verdicts).

**5. The catalog.** The MCP resource `frob://catalog/tasks` and `frob task list --json` return, per family: status,
tasks with their `TaskId`s, applicable robot classes, baselines with scorecard handles. Paged against a committed
frontier like every catalog.

**6. Relation to the coverage grid.** The sealed mission suite later draws cells from robot class (legged, wheeled,
tracked, hybrid) × world type (open terrain and the seven interior archetypes) using these families; the registry's
`robot_classes` and `scene_classes` fields are what that grid is computed from. Nothing in this bead builds the
suite.

## Acceptance criteria

- [ ] `registries/task-families.toml` lists the thirteen families with their first milestones; the three M1
      families have status `available` once BD-125 lands and the others `planned`.
- [ ] The completeness check fails when a family marked `available` lacks a requirement, has fewer than two examples
      of either label, or has no recorded baseline scorecard (three negative controls).
- [ ] `frob task list --json` groups tasks by family and prints `partial` with the missing items for a family that
      lacks one.
- [ ] A registry row naming a `TaskId` that is not in the content store fails the check.
- [ ] The status of a family is computed, never hand-set: editing `status` to `available` without the artifacts
      fails the check.

## Test plan

### Unit tests

- `thirteen_families_listed`: ids and first milestones match the table.
- `completeness_requires_requirement`, `completeness_requires_examples`, `completeness_requires_baseline`: one
  planted family each.
- `status_is_computed`: a hand-edited status is overridden and flagged.
- `dangling_task_id_fails`.
- `partial_names_missing_items`: a family with a requirement and examples and no baseline reports exactly
  "baseline scorecard: missing for ref:quadruped".
- `catalog_pagination_pinned`: the catalog read in two pages during a concurrent registry update shows each family
  once.

### End-to-end script and logging

Step `families-registry` of `scripts/e2e/gate_arena_01_reproducibility.sh` (N24a-24): `frob task list --json`,
assert the family count and each family's status against the milestone being exercised, then run the completeness
check through `cargo test -p frob-arena family_completeness`. NDJSON lines carry the command, exit code, the family
table (id, status, task count, baseline count) as measured values, and the list of `partial` families with their
missing items.

### Known answers and negative controls

- Known answer: the table above (thirteen families; three at M1, three at M2, four at M3, three at M4).
- Negative controls: the three planted incomplete families; a family whose only "requirement" is a reward threshold
  (a task file with an empty `requirements` section) must be refused by the task reader before it reaches the
  registry.
- Determinism: the registry and the catalog are class D0; their bytes are identical across platforms.

## Considerations

- OPEN-ARENA-1 (which public task definitions to mirror for comparability; default: mirror the reward terms of the
  public velocity-tracking tasks and make no claim of score parity; owner Arena lead; due M2) decides the reward
  terms of the velocity-tracking family, not its requirement.
- OPEN-ARENA-2 (a permissively licensed hexapod reference model; default: none, the template stands alone; due M4)
  decides which baseline a hexapod family row uses.
- Process is not the product: this registry is kept only because `task.list`, the completeness check and the
  catalog read it. If a field is read by nothing it is deleted.
- Families are not a closed set; adding one is a registry row plus the three artifacts.
