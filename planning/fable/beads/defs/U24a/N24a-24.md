## Background

A task result that cannot be reproduced is an anecdote. GATE-ARENA-01 (claim: Known answer; earliest milestone M2):
every task is reproducible inside its determinism class from its `TaskId`, `SceneId`, `ModelId` and seed;
reference-robot baseline scorecards are recorded. The four identifiers are content addresses (of the task file, the
scene pack, the compiled model) plus the run seed from which every world address and therefore every random draw
derives; nothing else may influence an episode.

"Inside its determinism class" has a precise meaning. Every result records its class:

| Class | Guarantee |
|---|---|
| D0 Exact | Integer, rational or symbolic results |
| D1 Bitwise across backends | The same bits on `batch-cpu` (`f32`), CUDA and Metal, where a device family attains it |
| D2 Bitwise per backend | The same bits run to run and across worker counts on one device family, driver and compiler; and across batch size, slot, co-tenant worlds, bucket capacity and shard count |
| D3 Tolerance | Agreement inside a recorded envelope, and agreement of task decisions |
| D4 Unspecified | None; never cited as evidence |

So the gate asks: twice on one backend, identical bits (D2); across backends, identical bits where D1 holds and
otherwise agreement inside the envelope with equal task decisions (D3). The weakest input wins: a task's class is the
weakest class among the kernels, placements, profile and inputs that produced it.

This bead is the end-to-end harness that measures the gate for whatever families exist, and the script that
exercises metrics and scorecards from the user's side. It is one capability-level test bead: the family beads
(BD-201, BD-253, BD-368 and their sub-beads) register tasks; this bead runs them.

## Scope

In: `scripts/e2e/gate_arena_01_reproducibility.sh` (the gate, for every family on the batched tiers from M2) and
`scripts/e2e/arena_scorecards.sh` (metrics and scorecard checks that the metric beads contribute steps to); the
comparison rules per class; live-dependency checks; the recording of reference-robot baseline scorecards; negative
controls; the gate record, which takes its referee rows for the M1 families from `scripts/e2e/arena_m1_families.sh`.

Out: the M1 families' own script and the referee rows it records (N24c-07); the tasks themselves; the determinism
machinery (digests, replay, batch-composition invariance: the Spark, Kinesis and Chronicle beads); the scene-split
gate (N24a-31).

## Technical approach

**1. What "reproduce" means, per task.** For each task in the family registry with status `available`, each
applicable reference robot, and each tier present:

1. *Run A.* `frob eval run --task <TaskId> --scene <SceneId> --model <ModelId> --seed <s> --tier <tier> --worlds
   <n>` in a fresh process with empty caches (`--no-memo`), recording verdict records, per-world state digests at
   the chunk boundaries and the scorecard.
2. *Run B, same backend.* The same command in a second fresh process with a different worker count and a different
   batch composition (the same worlds placed in other slots, among other co-tenants). Compare with run A:
   verdict records byte-identical; state digests identical per world; scorecard byte-identical. This is the D2 row.
3. *Run C, another backend* (where present). Compare with run A under the class the pair holds: bit equality where
   D1 is attained; otherwise the decision-level comparison: every verdict value equal, margins inside the recorded
   envelope, and the first divergence kept. This is the D1 or D3 row, labelled as such.
4. *Referee row* for tasks that run on the referee: twice on the referee, identical bits.

**2. Live-dependency checks** (a gate that claims dependence on an input must show the output changes with it).
Change the seed: digests change. Change the `SceneId` (another seed of the scene family): digests change. Change the
`ModelId` (a 1% mass edit): digests change. Change nothing but the process, the worker count, the slot assignment,
the host name or the wall-clock time: nothing changes.

**3. Reference-robot baseline scorecards.** For each family and reference robot (or the archetype's template where
no reference model is on file), the harness runs the family's baseline battery under the synthesized baseline
controller, writes the scorecard (`frob.scorecard/1`) with its identities to the content store, and enters its
handle in the family registry. A baseline is reproducible by construction: the harness re-derives it in run B.

**4. The scorecard script.** `arena_scorecards.sh` drives the fixture batteries of the metric and scorecard beads:
steps `metrics-core-*` (N24a-17), `metrics-energy-*` (N24a-18), `metrics-motion-*` (N24a-19), `metrics-contact-*`
(N24a-20), `metrics-maneuver-*` (N24a-21, from M3) and `scorecard-*` (N24a-22). Each step runs `frob eval run` and
`frob eval scorecard --json` on a fixture with hand-computed answers and asserts them. At M1 the script runs its
referee steps; from M2 the batched ones.

**5. The gate record.** Per task, robot and tier pair: the class claimed, the comparison performed, counts of worlds
compared, mismatches (0 required for D0 to D2 rows), for D3 rows the envelope and the decision agreement. Measured
values, the commit, the hardware fingerprint and the seeds are in the receipt; the registry row is entered by a
session that did not implement the tasks.

## Acceptance criteria

- [ ] GATE-ARENA-01: for every `available` task, runs A and B on each backend agree bit for bit (verdicts, digests,
      scorecard); cross-backend rows agree in their class; reference-robot baseline scorecards are recorded and
      listed in the family registry.
- [ ] The four live-dependency checks behave as stated (three change, the fourth does not).
- [ ] Each negative control below is caught by the script.
- [ ] Both scripts exit non-zero on any failed assertion, are idempotent and seed-explicit, and write the structured
      log described below.
- [ ] The gate can be run per family (`--family <id>`), so that the M3 and M4 family beads re-use it unchanged.
- [ ] The receipt carries measured values (mismatch counts, envelopes), not targets.

## Test plan

### Unit tests

The harness is shell plus small helpers; its helpers have unit tests in `frob-conformance`:

- `compare_verdict_records_bytes`: two record sets differing in one margin bit are reported with the world address
  and field.
- `class_dispatch`: a D2 pair is compared bitwise; a D3 pair by decisions and envelope; a D4 input is refused as
  evidence.
- `baseline_handle_roundtrip`: a recorded scorecard handle resolves to identical bytes.
- `slot_permutation_helper`: generates a co-tenancy that places each world in a different slot than run A.

### End-to-end script and logging

`scripts/e2e/gate_arena_01_reproducibility.sh [--family <id>] [--tier <tier>]`:

1. `frob task list --json` and the family completeness check (N24a-23).
2. For each task, robot and tier: runs A, B and (where present) C as above, each a `frob eval run … --json` with an
   idempotency key derived from the step name, followed by `frob job wait` when the envelope returns a job handle
   (exit code 8).
3. `frob telemetry divergence <runA> <runB>` must report no divergence for D2 pairs; for D3 pairs its first
   divergence is recorded.
4. The live-dependency runs.
5. The negative-control runs.
6. `frob eval scorecard --json` for each baseline; write handles into the registry.

Logging: sources the STD-E2E helper; NDJSON to `target/e2e-logs/gate_arena_01_reproducibility/<utc>.ndjson` and a
transcript beside it. Every line has `ts`, `script`, `bead`, `step`, `event` (`start`, `cmd`, `assert`, `metric`,
`refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier,
determinism, identities, seed), measured values with units and thresholds (worlds compared, mismatches against 0,
envelope widths), the digests compared, and on failure the first differing world address, tick and field with the
artifact paths needed to reproduce. A final `summary` line gives assertions passed and failed and names
GATE-ARENA-01. Scene data from private families is never logged; identifiers and digests only.
`scripts/e2e/arena_scorecards.sh` logs in the same form under its own directory.

### Known answers and negative controls

- Negative control 1 (planted nondeterminism): a build in which one task's command stream is seeded from wall-clock
  time; run B differs and the script must fail at the D2 comparison.
- Negative control 2 (batch dependence): a build with a batch-wide normalizer in an observation term; run B, with
  another co-tenancy, differs.
- Negative control 3 (hidden input): a task that reads an environment variable for a threshold; the
  "change nothing but the host environment" check must flag it.
- Negative control 4: a baseline scorecard edited after recording; its handle no longer resolves to the recorded
  digest.
- Metamorphic relations: batch-composition invariance (MR-01); permuting world indices permutes results and changes
  nothing else; a draw depends on (address, step, stream) only, and adding a stream changes no other stream
  (MR-03).
- Determinism lanes exercised: twice on one machine; across worker counts; debug and release builds of `frob`
  (verdict records and digests equal); across platforms and backends, each against its class.

## Considerations

- If a device family cannot hold bit equality with `batch-cpu`, it is class D2 for itself and D3 against others;
  the gate still passes, with those rows labelled tolerance rows. Results under D4 never enter the gate.
- No-GPU variant of M2: the gate runs on the referee and `batch-cpu`; device rows are recorded `not run` with the
  reason.
- Cost: the gate re-runs every baseline twice per backend; batteries for the gate are the families' `smoke`-sized
  sets (a handful of scenarios per task), not the full batteries.
- RISK-44 (adaptation or tuning leaks into the final evaluation) is addressed by identities frozen in requests; this
  gate is what makes "the same identities give the same result" true.
