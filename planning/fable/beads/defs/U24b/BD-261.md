## Background

The blinded qualification lane controls error across an agent's adaptive retries only if no retry is informed
by the worlds that judged the last one. Freshness of clusters alone controls the error rate; **blinding**
protects the claim's population: if an agent could read confirmation worlds they would inform its next
candidate, the held-out family would stop being held out, and a promotion would describe worlds the design was
fitted to. So discovery cannot read confirmation worlds (INV-QUAL-01; the safety chapter states the same as
INV-SAFE-03: no discovery session can obtain any per-world datum of a confirmation run): no verb returns a
sealed address, outcome, trace or still to a session without `qual:admin` before the campaign closes, and an
attempt is refused and logged (FROB-REF-840).

The counterexample the firewall answers (CX-384): if `eval.qualify` returned which worlds failed, an agent
could run an adversarial search near those worlds, patch for them, and resubmit; the α_i schedule would then
bound an error rate for a procedure that is no longer the one being run.

ADR-SAFE-02 (decision): isolation of confirmation worlds is enforced by capability, by a separate store and by
address namespace, all three. Reason: statistical error control across adaptive retries is void if one read
path exists. Three independent layers mean that a defect in one is not a leak. The mechanism is on by default
and has no off switch below an owner-held configuration.

Gates (TARGET). GATE-QUAL-02 (Known answer, M3): 10⁴ fuzzed read attempts across every verb return no sealed
field; a planted leak path is found by the audit; receipts contain only the listed fields. GATE-SAFE-03 (Known
answer, M3): a session holding every discovery scope attempts at least 25 enumerated read paths against a
confirmation run; all return FROB-REF-840; negative control: a test build that leaks per-world outcomes is
detected by the adaptive-retry gate of the qualification lane. The seed done-condition is both gates.

## Scope

In: the two scopes and what each permits; the three layers; the `Sealed` type and the serializer rule; the
refusal and its logging; the enumerated read paths; the fuzz campaign; the static and dynamic sealed-field
audit; the planted leak; the owner's audit scope; the sealed objects of battery campaigns, the admin action
`seal` and the read-form input `--read-sealed` of `eval.ledger`; the records of both gates. Out: the lane's protocol and
receipt (BD-259); cluster derivation and the namespace field (N24b-17); the general capability system, session
budgets and path jail (BD-258); the 500-retry gate (BD-260).

## Technical approach

**Scopes.**

| Scope | Permits | Does not permit |
|---|---|---|
| `qual:run` | Submitting a committed request with `eval.qualify`; reading receipts and `eval.ledger` | Opening or closing a campaign; any sealed read |
| `qual:admin` | Opening and closing campaigns; holding the owner's audit scope that can open one confirmation cluster before close (which retires that cluster); writing and, before close, reading the sealed objects of a battery campaign | Being derived by attenuation from any agent token: it is minted only from the owner-held configuration |

No scope grants reading a confirmation world. A derived token never has more scopes than its parent; `qual:admin`
cannot be obtained by derivation. Default under OPEN-ARENA-3: the owner alone holds `qual:admin`.

**Who may be granted `qual:admin`.** The capability registry reads the holder roles from the qualification
lane's configuration `config/qualification.toml` (`qual_admin_holders`, written by the OPEN-ARENA-3 decision,
N24c-13), and mints `qual:admin` only for a session whose role is listed there. A session has the role `owner`
when it is the root session of the principal `owner`, minted from the table `principal.owner` of `safety.toml`
(N37-02; the one table allowed to list owner-only scopes) and only through the command-line adapter, never over
MCP and never by derivation (N32b-01). This bead's script, N32b-05's confirmation-run helper and N32b-37's
sealing open the owner's session that way: `frob session open --principal owner --scopes eval:read,qual:admin
--key <k> --json` on the command line. A missing or malformed file
loads as the fail-closed default (holders = owner, `decided: false`), never as an open configuration. A file
whose holder list names a role that also designs candidates on a claim family (one that holds `design:write`,
`train:run` or `qual:run`) is rejected at load and the registry keeps the previous valid holder list: the plan
requires that the capability never be held by a session that also designs candidates.

**Layer 1: capability.** `eval.qualify` returns a decision, counts of units and a receipt. Every other verb
that could expose a world refuses a confirmation run, campaign or address with FROB-REF-840, and no token an
agent can hold or derive changes that. The check sits in the verb dispatcher, before the handler: any argument
that resolves to an object carrying the confirmation mark (a run, job, episode, artifact, address or scene of
an open campaign) is refused unless the verb is `eval.qualify`, `eval.ledger` or a job-control verb acting on
the caller's own qualification job (and those return only progress with a denominator).

**Layer 2: store.** Confirmation chunks (episodes, telemetry, stills, per-unit outcomes, the sealed key) live
under a separate root with a separate key, opened only by the qualification executor inside the daemon. A
discovery handler has no handle to it: the handle type is not constructible outside the executor module
(visibility enforced by the crate structure and a lint).

**Layer 3: address.** Confirmation worlds are drawn from a sealed seed in their own address namespace; the
samplers of discovery verbs reject any address in that namespace, so no discovery run can coincide with a
confirmation world by construction (PO-SAFE-02: the namespaces are disjoint; exact, an integer field
comparison).

**The `Sealed` type (DESIGN).** Per-world confirmation data is carried as `Sealed<T>`, a wrapper with no
serialization implementation. The only ways out are: (a) reduction inside the executor to the receipt's fields
through a function whose return type is the receipt; (b) `reveal(campaign_closed_proof)`, which needs the
ledger's close record. The envelope serializer therefore cannot be handed sealed data by mistake; a handler
that tries does not compile. Error paths are covered: a numerical fault on a sealed world is reported to the
agent as a count inside `inconclusive` handling, never with an address or a trace reference.

**Refusal.** FROB-REF-840: "a session without `qual:admin` asks for sealed confirmation data before close".
Exit code 5 (outside the session's scopes). `retry: after-change` (after the campaign closes). The refusal
names the campaign and nothing about the world. Every attempt is written to the ledger as a
`sealed-read-attempt {session, verb, campaign, ledger_seq}` record, visible to the owner.

**The enumerated read paths (at least 25, derived from the verb registry, never a hand list).** The path set is
computed from the verb registry: every verb (and every MCP resource template) whose input schema has an
identifier-typed argument that can resolve to a run, job, episode, artifact, address, scene or campaign. It is
the same registry-derived enumeration of handlers that the sealed-scene bead N19c-14 uses for the layer below
(a sealed identity answers, below the dispatcher, exactly as an absent identity), so a verb added to the
registry later is picked up by both loops at once, and the two tests cannot drift apart: this bead asserts the
session-level refusal on that list, N19c-14 the handler-level answer. The verbs below are the minimum known
members; a check fails if any of them is missing from the derived set:
`telemetry.summary`, `telemetry.query`, `telemetry.energy`, `telemetry.failures`, `telemetry.histogram`,
`telemetry.divergence`, `telemetry.stills`, `telemetry.inspect-pixel`, `telemetry.export-html`, `sim.replay`,
`run.fork`, `run.show`, `run.list`, `autopsy.intervene`, `autopsy.attribute`, `autopsy.repair`,
`autopsy.rerun`, `autopsy.show`, `nemesis.search` (seeded near a confirmation address), `nemesis.shrink`,
`nemesis.oracle`, `explain.run`, `explain.compare`, `artifact.read`, `artifact.list`, `artifact.export`,
`evidence.trace`, `task.verdict`, `eval.scorecard`, `report.run`, `job.status` and `job.wait` on the
qualification job (must return progress only), `store.status` (must not list confirmation chunks), `scene.show`
on a sealed scene, and MCP resource listings. Each is attempted by a session holding every discovery scope and
`qual:run`, against an open campaign's run.

**The fuzz campaign (GATE-QUAL-02).** 10⁴ generated read attempts across every verb in the registry: for each
verb, arguments are drawn from its input schema with every identifier-typed argument substituted, in turn, by
identifiers of confirmation objects (campaign, request, job, run, episode, artifact, address, scene), by
near-miss identifiers, and by valid discovery identifiers. The oracle scans each response (envelope, progress
events, error text, MCP structured content and text) for any byte sequence from a dictionary of sealed values
built by the executor for the test campaign (addresses, cluster digests, per-unit outcome vectors, trace
digests, still digests, the key). Expected: zero hits.

**The sealed-field audit.** Static: every output schema in the registry is walked; a field whose type can
carry a world address, an episode reference, a trace or a per-unit outcome must be declared either
`discovery-only` (guarded by the dispatcher check) or absent from confirmation responses; an unclassified field
fails the build. The receipt schema is checked to contain exactly: campaign, index, level, cumulative level,
decision, units used, the sealed-field list, the receipt hash and the authorization flags. Dynamic: the fuzz
above. **Planted leak** (a `cfg(feature = "nc-<nnnn>")` branch in the handler's crate, built only with
`--features gauntlet-mutations,<crate>/nc-<nnnn>`, never shipped; its control record in `controls.toml`, gate
GATE-QUAL-02, is registered by this bead): a handler path that copies one sealed address into a warning
string. The audit must find it (the fuzz oracle reports the hit with the verb and argument that produced it).
This plant is also the planted leak of the chaos tier N38a-26, which plants no second one and adds GATE-GAUNT-06
to this record's `gate` list beside GATE-QUAL-02 (and the identifier to that gate row's `controls`), so the
control runs whenever either gate runs.

**Sealed objects of a battery campaign (DESIGN; the request of the diagnosis battery, N32b-37).** The firewall
also holds sealed data that are not worlds, so that a second sealing mechanism is never built. A battery
campaign (N24b-15's kind `battery`) holds named byte objects, such as the thirty answer keys of one
instantiation of the diagnosis battery. `SealedStore::put(campaign, name, bytes)` writes one into the
confirmation store (layer 2) as a `Sealed<Object>` carrying the confirmation mark; it is reachable only from a
session holding `qual:admin` and only while the campaign is open, through the admin action `seal` of
`eval.ledger` (capabilities `["eval:read", "qual:admin"]`; `frob eval ledger <campaign> --action seal --name
<name> --file <path> --json`; over MCP `"action": "seal"` with `name` and `file`, the seal action's own input
properties; returns the object's name and digest; `--file` takes a path, so 734 and 828 are appended by field; a
`seal` of a campaign that is not open is `campaign-not-open`, exit 3). Being of kind `admin` the action takes no
idempotency key (`--key` is 802) and is idempotent by its effect: a `seal` of a name already sealed in the campaign
writes nothing; with the same bytes it returns the stored name and digest, and with other bytes it is refused with
`sealed-object-exists` (pending, convention 5; exit 7; `observed` the name and the stored digest, `required` a new
name), so a sealed object is never overwritten.
Reading an object is not an action but the input `--read-sealed <name>` of the verb's read form (MCP property
`read_sealed`; VERBS-eval's row, which gives the reason: its kind is the entry's own `read`, and after close it
answers with `eval:read` alone): `frob eval ledger <campaign> --read-sealed <name> --json` returns the object's
bytes. Before close the dispatcher's sealed-object check (layer 1) admits it only for a session holding
`qual:admin` and writes each such read to the ledger as `sealed-admin-read {session, campaign, name,
ledger_seq}`. Every other read (`artifact.read` of the object's digest, a `store.status` listing, an MCP
resource, `--read-sealed` from a session without `qual:admin`) is refused by the dispatcher with FROB-REF-840,
exit 5, and logged as a `sealed-read-attempt`. Layer 3 does not apply (an object has no address). After close
the objects are revealed through `reveal(campaign_closed_proof)` and `--read-sealed` answers any session holding
`eval:read`. The objects' bytes and digests enter the fuzz dictionary, and the static audit classifies the
output field `--read-sealed` returns as sealed until close.

**Audit scope.** With `qual:admin`, the owner may open one confirmation cluster before close. The act is
logged, retires the cluster (never drawn again), and marks everything derived from it with the family's
lineage mark (which later refuses a tainted candidate with FROB-REF-843).

**Gate records.** GATE-QUAL-02: fuzz count, hits (zero), the planted leak found, the receipt-field check.
GATE-SAFE-03: the enumerated paths (count at least 25), all returning FROB-REF-840, and the negative control:
the build `leak-per-world-outcomes` run under the campaign simulator (N24b-18) is detected. This bead is the one
recorder of both gates: the known-answer target runs each (`FROB_TEST_SEED=<seed> cargo test -p frob-conformance
--test g1_known_answers --features gauntlet-mutations -- GATE-QUAL-02`, and the same for GATE-SAFE-03) and
writes a receipt, and a session that did not implement the firewall records each from its receipt with `cargo
run -p frob-conformance --example record_gate -- --gate <id> --receipt <hash>`. No script writes either row;
N24b-24's user-side log is evidence beside the record, not a second recorder.

## Acceptance criteria

- [ ] A session with every discovery scope and `qual:run` attempts each read path of the registry-derived set (at least 25, the same handler set N19c-14 iterates) against an open campaign: every attempt returns FROB-REF-840 with exit code 5 and no partial data (GATE-SAFE-03).
- [ ] 10⁴ fuzzed read attempts across every verb return no sealed field (GATE-QUAL-02).
- [ ] The planted leak path is found by the audit; the leaking-receipt build is detected by the simulator's receipt-shape assertion.
- [ ] The receipt contains only the listed fields (schema check and a byte-level check of real receipts).
- [ ] `qual:admin` cannot be derived from any agent token; opening or closing a campaign without it is refused.
- [ ] `qual:admin` is minted only for a role listed in `config/qualification.toml`; a missing file yields the owner-only default; a file listing a candidate-designing role is rejected at load.
- [ ] The confirmation store handle cannot be constructed outside the executor (compile-fail test); a discovery sampler rejects a confirmation-namespace address.
- [ ] Every refused attempt is in the ledger as `sealed-read-attempt`; an audit-scope read retires its cluster.
- [ ] After close, the same read paths succeed for the revealed data.
- [ ] A battery campaign's sealed object, written by an owner session, is readable before close only through
      `--read-sealed` with `qual:admin` (each read in the ledger); every other read path returns FROB-REF-840,
      exit 5, and is logged; `seal` without `qual:admin` is FROB-REF-720 and after close is `campaign-not-open`;
      `seal` with `--key` is 802; a repeated `seal` of one name with the same bytes writes nothing and returns the
      stored name and digest, and with other bytes is `sealed-object-exists`, exit 7, the stored object unchanged;
      the fuzz finds no byte of the object; after close it is readable with `eval:read`; `--read-sealed` is an
      input of the read form (MCP property `read_sealed`) and `seal` the one action this bead adds to the entry.
- [ ] GATE-QUAL-02 and GATE-SAFE-03 are recorded with measured counts and their controls caught (the seed done-condition).

## Test plan

### Unit tests
- `sealed_has_no_serializer`: compile-fail test that `Sealed<WorldAddr>` cannot be placed in an envelope.
- `dispatcher_refuses_confirmation_objects`: one case per verb of the registry-derived path set (not a hand table), expecting FROB-REF-840 and exit code 5; a test-only verb registered with an identifier argument and no classification is picked up by the loop and fails it.
- `read_path_set_contains_known_members`: the derived set contains every verb of the minimum list above and has at least 25 members; it equals, verb for verb, the handler set N19c-14's handler-level test iterates.
- `job_status_progress_only`: the status of a qualification job has `progress {done, total, unit}` and no outcome counts.
- `store_status_hides_confirmation_root`.
- `token_attenuation_cannot_reach_admin`: derive from a token with all agent scopes; `qual:admin` absent; a forged scope string is rejected.
- `admin_holders_from_config`: holders = [owner] mints `qual:admin` for the owner role and not for an agent role; a deleted or malformed file loads as holders = [owner], `decided: false`; a file naming a role that holds `qual:run` among the holders is rejected at load and the previous holder list stays in force.
- `sampler_rejects_confirmation_namespace` (PO-SAFE-02).
- `receipt_schema_exact_fields`.
- `refused_attempt_logged`.
- `audit_scope_retires_cluster`.
- `post_close_reads_succeed`.
- `static_audit_unclassified_field_fails_build`: add a schema field of type world address without a classification; the audit fails.
- `battery_object_sealed`: an owner session seals a 1 KiB object in `q:battery-test/1`; an agent session with every discovery scope gets FROB-REF-840 from `--read-sealed` (and from `read_sealed` over MCP), from `artifact.read` of its digest and from the MCP resource listing; `store.status` does not list it; the owner's `--read-sealed` returns the bytes and writes one `sealed-admin-read` record; `seal` from an agent session is FROB-REF-720.
- `battery_object_seal_idempotent`: the owner seals `key-1` twice with the same bytes: one stored object, one
  ledger write, the second call returns the same name and digest; a third `seal` of `key-1` with one byte changed
  is `sealed-object-exists`, exit 7, naming the stored digest, and `--read-sealed key-1` still returns the first
  bytes; `seal` with `--key` is 802 and stores nothing.
- `battery_object_revealed_after_close`: after the owner's close the agent's `--read-sealed` returns the bytes with `eval:read` alone; a `seal` after close is refused with `campaign-not-open`.
- `read_sealed_is_read_form_input`: the generated entry of `eval.ledger` declares `read_sealed` as an input property of the read form and `seal` as an admin action with `["eval:read", "qual:admin"]`; no action named `read-sealed` exists.
- `battery_object_in_fuzz_dictionary`: the dictionary built for a battery campaign contains each object's bytes and digest.

### End-to-end script and logging
This bead's own script, `scripts/e2e/qualify_firewall.sh [--long] [--mutants] [--mcp]` (header `bead=BD-261
milestone=M3 gates=GATE-QUAL-02,GATE-SAFE-03`), sources the STD-E2E helper and drives the real `frob` binary and
the MCP server against a daemon with an open test campaign, using only this bead's dependencies (the campaign
opened by the owner's root session, principal `owner`, with `frob eval ledger --action open --task <TaskId>
--world-family <family> … --json`, N24b-15, an admin action with no key; one committed request through `frob eval
qualify … --key …`, BD-259). Steps: `firewall_paths` (the registry-derived set, its size and digest logged, every
attempt FROB-REF-840 with exit 5 and a `sealed-read-attempt` row), `firewall_fuzz` (1,000 attempts by default, 10⁴
with `--long`), `admin_paths` (`qual:admin` not derivable; a holder file naming a `qual:run` role rejected at
load), `planted_leak` (with `--mutants`, the `gauntlet-mutations,<crate>/nc-<nnnn>` build: the fuzz reports the
hit with verb and argument, `e2e_expect_caught`), `battery_sealed_objects` (a battery campaign opened by the
owner, `frob eval ledger --action open --kind battery --label e2e-fw --json`; `frob eval ledger <campaign> --action
seal --name key-1 --file <scratch object> --json` by the owner, no key, repeated with the same file (the same name
and digest, nothing written) and with a changed file (`sealed-object-exists`, exit 7); `--read-sealed key-1` by
`agent`, 840; by `owner`, the first bytes and one `sealed-admin-read`), `close_and_post_close_reads` (the owner's
`frob eval ledger <campaign> --action close --json` on both campaigns; the same paths now answer), and `receipt` (`e2e_tier g1_known_answers GATE-QUAL-02
--mutations` and `e2e_tier g1_known_answers GATE-SAFE-03 --mutations`; the receipt hashes logged for the
recorder, no gate row written). Logged per STD-E2E: per attempt the verb, exit code and refusal code; fuzz totals and hits
against the threshold 0; for the planted leak, the verb and argument that exposed it; the gates touched. The log
itself is scanned with the sealed-value dictionary at the end of the script and must contain none of it before
the close step. N24b-24's qualification-lane script runs this one as a stage.

### Known answers and negative controls
KA-623 (10⁴ fuzzed read attempts across every verb return no sealed field; control: a planted leak path is
found by the audit). CX-384. Negative controls: the planted leak; the leaking-receipt build; a build in which
one enumerated verb skips the dispatcher check (the path table must fail on that row). Metamorphic: a
confirmation read attempt returns the same refusal whatever the campaign's content. Determinism: the fuzz is
seeded and replays; refusals are D0.

## Considerations

- Chaos tier: the firewall is one of the Gauntlet's chaos subjects; the fuzz runs under injected faults (a cancelled job, a daemon restart mid-request) to check that error and recovery paths release nothing sealed.
- Side channels accepted and documented: total compute cost and `units_used`; a running e-process stopping early reveals that evidence crossed a threshold, which the receipt reveals anyway.
- Trust: whoever holds `qual:admin` is trusted; a local user with root is outside the threat model.
- Private places and licences are separate marks with their own refusals; a sealed family built on a private scan needs both to pass.
- New verbs: the build fails until a new verb's output schema is classified, so the path list cannot silently fall behind the registry.
- RISK-34 (qualification gamed by a leak from sealed worlds) and pre-mortem item "qualification was gamed" name this firewall as mitigation.
