## Background

Arena (crates `frob-spec` and `frob-arena`, layer 4) defines what a robot is asked to do and how an answer is
scored. A **battery** is a named, versioned list of scenarios that a design is run against. Six batteries exist:

| Battery | Content | When it runs | First milestone | Content owner |
|---|---|---|---|---|
| `smoke` | Every design template (archetype) and every reference robot on a handful of scenarios; minutes of wall clock | Every change | M1 | this bead |
| `fixtures` | The analytic layers of the two registered fixtures (`fixture:cart-sill-dock`, `fixture:quad-split-grip`) and the known answers of the requirement monitors | Every change that touches contact, actuators, clocks or `frob-spec` | M1 (fixture 2 joins at M2) | this bead |
| `standard` | The fidelity battery: about 200 scenarios per robot class (TARGET) | Fidelity ledger, divergence ledger, detectors | M2 | the Gauntlet (BD-212) |
| `full` | Every task family across every archetype with the full randomization | Releases, scorecards | M3 | BD-254 |
| `hard` | The hard-world set of the robot class (minimal counterexample worlds found by adversarial search). Discovery data, never a confirmation sample | Regression after a repair | M3 | BD-275 |
| `covering` | A scene set chosen by submodular coverage selection, with one slot in five drawn at random from held-out scenes | Budgeted evaluation | M3 | BD-278 |

Why a battery needs an identity. A success rate is a count over a declared population. If a scenario can leave a
battery without trace, an optimizing agent (or a tired engineer) improves the rate by shedding the cases that fail,
and the number then describes a population nobody declared (ADR-ARENA-09: an infeasible scenario is kept and
counted; RISK-15: agents optimize the scorecard instead of the robot, including by moving failures out of the
denominator). The plan's rule: removing a scenario from a battery is a recorded event with a reason and changes
the battery's identity, and a silently shortened battery must change identity (measured later by GATE-ARENA-07 in
BD-254). This bead builds the mechanism that makes that true for all six batteries, and ships the content of the
two that exist at M1. Rejected alternative: batteries as directories of files discovered at run time. Rejected
because the set that ran is then whatever happened to be on disk, and two runs "of the same battery" need not be
comparable.

Terms. A *scenario* (also called an item) is one (task, scene or world family, disturbance law, family of initial
conditions) tuple, identified by content hash. `TaskId` is the BLAKE3 hash of a task file's canonical JSON. A
*robot class* is a morphology class such as `quad-mammal` or `diff-drive`. The *ledger* is the append-only
evidence store of `frob-chronicle`.

## Scope

In: the manifest format and its canonical form; `BatteryId`; the event log of membership changes; the loader and
the resolution of a battery name to an identity at run time, with its extension point `battery::load_checks`; the
example targets `battery_resolve` and `battery_triggers`; the lane flags; the path-trigger table that decides
when `smoke` and `fixtures` run; the content of `smoke` and `fixtures` at M1.

Out: scorecard columns and the accounting gate (BD-254); the `standard` battery's scenarios and freeze (BD-212);
the hard-world set (BD-275); the covering selection (BD-278); wiring batteries into the Gauntlet's tiers (BD-146
for M1, BD-223 for M2, BD-318 for M3); the fixtures themselves (N24b-03, BD-123, BD-202); the path list of the
`fixtures` trigger row beyond the list committed here, and the test that the trigger map is complete (N38a-22,
which depends on this bead).

## Technical approach

**Files (DESIGN).** `registries/batteries/<name>.<robot-class>.toml`, one per battery and class; `smoke` and
`fixtures` have one file each with class `all`. Code in `crates/frob-arena/src/battery/{manifest,identity,events,
trigger}.rs`.

**Manifest, schema `frob.battery/1` (DESIGN).**

```toml
schema = "frob.battery/1"
name = "smoke"                 # smoke | fixtures | standard | full | hard | covering
robot_class = "all"
lane = "discovery"             # every battery is discovery data; no battery is a confirmation sample
selection = "listed"           # listed | hardset-ref | covering-ref
[[item]]
task = "t:stand-10s@…"         # TaskId
world = { scene = "s:flat-plane@…", addresses = [[17, 0, 0], [17, 1, 0], [17, 2, 0]] }   # (run_seed, world, episode)
disturbance = "none"           # or a named law from the task's randomization section
initial = "settled"            # family of initial conditions
```

Canonical form: items sorted by their own content hash; within an item, keys sorted; integers as integers;
addresses as triples. `ItemId` is the BLAKE3 hash of one canonical item. `BatteryId` is the BLAKE3 hash of the
canonical JSON of `{schema, name, robot_class, lane, selection, items: [ItemId sorted]}`. Consequences, each a
test: reordering items does not change the identity; adding, removing or editing one item does.

**Membership events.** Every change of a manifest's item set is an event row in the ledger, schema
`frob.battery.event/1`: `{battery, robot_class, from: BatteryId, to: BatteryId, added: [ItemId], removed:
[ItemId], reason: string (required, non-empty), actor, ledger_seq}`. The loader refuses to run a manifest whose
`BatteryId` has no event chain back to a registered identity (the first registration is an event with `from`
empty), and refuses a removal with an empty reason.

**The loader's refusal (DESIGN).** The plan states the rule (a removal is a recorded event with a reason and
changes the identity) and names no code, and the refusal registry has no code for an invalid registry file. Every
load that fails is therefore refused under one symbolic name, `battery-manifest-invalid`, registered in the Arena
refusal registry's table of unnumbered refusals (N24-REF; family `5xx`, exit code 3, `retry: after-change`; the
registry owner assigns the number at implementation and until then tests match the name). `observed` names the
kind, `pointer` the manifest or events file and, where one exists, the first `ItemId` present on one side only:

| Kind | Trigger | First repair |
|---|---|---|
| `no-event` | The manifest's `BatteryId` is not reached from the last registered identity by the declared events (an item added, removed or edited by hand) | Append an `[[event]]` with `from`, `to`, the item under `added` or `removed`, and a reason; or restore the registered item set |
| `event-mismatch` | An event's `to` is not the identity computed from its item set, or its `from` is not the previous identity | Correct the event's identities (the refusal prints the computed ones) |
| `empty-reason` | An event whose `reason` is empty or white space | Give the reason |
| `record-edited` | An event already recorded in the ledger was edited or deleted in the events file | Restore the recorded line; declare the correction as a new event |
| `schema` | A missing field, a `lane` other than `discovery`, an unknown `selection`, an item whose `task` resolves to no task file (below), an item with both or neither of `task` and `ka`, or a `ka` or `fixture` value not of its form (the `fixtures` items below) | Correct the field named by the pointer |

An unknown or misspelt key and a duplicate key are FROB-REF-103 (unknown, misspelt or duplicate field; exit code
3), as in every reader of this system; nothing is defaulted.

How an event is made (DESIGN). The author of a change declares it in the append-only file beside the manifest,
`registries/batteries/<name>.<robot-class>.events.toml`: one `[[event]]` per change with `from`, `to`, `added`,
`removed` and `reason` (the declaring commit is the author's record). On load, the loader checks that the chain
of declared events leads from the last identity registered in the ledger to the manifest's `BatteryId` (each
event's `to` equal to the identity computed from the manifest as of that event's item set), and records each
not-yet-recorded event as a `frob.battery.event/1` ledger row (with `actor` the session whose call caused the
load and `ledger_seq`) in its own transaction before the first run that uses the new identity. A manifest
whose identity is not reached by the chain, an events file in which a line was edited or deleted (detected by
comparing the recorded rows with the file's prefix), or an event with an empty reason is refused with
`battery-manifest-invalid` and its kind. Nothing else writes these rows.

**Run-time resolution.** This bead provides `battery::resolve(name, class) -> Result<Resolved, LoadError>` with
`Resolved { battery_id: BatteryId, items: Vec<ItemId>, manifest_path, event_seq }`, and the run-record field
`battery: { id, items }`. `items` is in canonical (identity) order, and `battery::item(&Resolved, ItemId) -> &Item`
returns the canonical item (task, world, disturbance, initial) that the scenario loop runs; the run record stores
the `ItemId`s only. An item's `task` is a `TaskId`: the loader finds its canonical bytes in the task registry
(BD-122) or, for a task that static admission refuses and the registry therefore does not hold (the smoke refusal
item below), among the task files shipped under `assets/tasks/`, by hashing their canonical bytes; a `TaskId` found
in neither is the `schema` kind above. `eval.run --battery <name> [--class C]` (verbs `eval.run` and `eval.scorecard` at M1
are bead N24c-04, which depends on this one) calls it once, before the request is digested, echoes the
`BatteryId` in the envelope's `bound` block (the rule for mutable names) and stores `Resolved` in the run
record, so a scorecard can prove which population it counted.

**Checks that later beads add to the load (extension point).** `battery::resolve` runs its own checks (the kinds
above) and then every check registered in `battery::load_checks`, a list of `fn(&Manifest, &[PendingEvent]) ->
Result<(), Refusal>` that later beads append to, in a fixed order, before anything is registered; a refusal from
one of them registers no identity and writes no event row, like the loader's own. This bead ships the list empty
and tests it with a synthetic check. The one known extension: BD-275 (M3, the hard-world set) adds the check
`only-hard-battery`, which calls `frob_nemesis::is_discovery_world` on the world addresses of every item; a
`listed` manifest whose every item is a discovery world, or an event that would leave it so, is refused with
`hard-world-set-inadmissible` (N26-REF, family `3xx`, exit 3; failed check `only-hard-battery`, pointer at the
manifest) and nothing is registered. The `hard` battery itself (selection `hardset-ref`, the set read as a
battery) is exempt. The check, its slug and its tests are BD-275's.

**Which designs run a battery.** A battery is a population of scenarios, not of designs: the design is an
argument of the run. "Every template and reference robot" for `smoke` is the CI job's design list, resolved at
run time from the template registry (the first archetypes, BD-109) and the reference-robot asset tree
(`assets/robots/`, NEG-15), recorded in each run record and in the job's log, and not part of `BatteryId`.

**Lane flags.** `lane = "discovery"` on every battery. A request that offers any battery item as a confirmation
sample is refused by the qualification lane; for `hard` and `covering` the refusal is FROB-REF-567 (a hard-world
or search-selected world offered as a confirmation sample; exit code 3; repair: draw confirmation worlds from a
sealed family through `eval.qualify`).

**`smoke` content at M1 (DESIGN default: three scenarios per robot).** For each of the four first archetypes
(`quad-mammal`, `humanoid`, `diff-drive`, `mecanum`) and each reference robot on file for them: (1) stand or hold
for 2 s from the settled pose, verdict `satisfied`; (2) one short family task on flat ground under the baseline
controller (wheeled: drive 1 m; legged: stand and recover from a push of the task's stated impulse); (3) one
deliberate refusal case (a task whose episode horizon is shorter than the reach of its verdict), expecting
FROB-REF-526 and landing in the scorecard's `refused` column. The three smoke tasks are authored by this bead as
`.ftask` files under `assets/tasks/smoke/` (they cannot be BD-125's task families, which depend on this bead
through the scorecard). Budget TARGET: the whole battery in minutes on the referee tier with 8 cores.

**`fixtures` content.** One item per analytic row of fixture 1 (ten rows, bead N24b-04 on the host and BD-123 on
the referee), one per limiting-model row of fixture 2 from M2 (N24b-12), and the monitor known answers
(normalization, joint stage accounting, online and offline agreement; owned by the requirement-language beads).
Items of this battery are `task.fixture` invocations, not episodes of a robot class, so they have their own item
form (DESIGN): `[[item]] ka = "KA-602"`, with `fixture = "fixture:cart-sill-dock"` when the record is a fixture's
row; an item has either `ka` or `task`, never both, and its `ItemId` is the hash of the canonical item as for any
other. The loader checks the form only (`ka` of the form `KA-<n>`, `fixture` of the form `fixture:<name>`); whether
the record and the fixture exist is checked when the battery runs (`task.fixture --battery fixtures`, N24c-10, and
N24-KA's completeness test), so this bead needs neither the fixture registry nor the known-answer records. The M1
manifest lists the records of the M1 rows N24c-10 runs as this battery: KA-594 to KA-596, KA-598, KA-602 to
KA-615, KA-618 and KA-619 (twenty items); KA-616 and KA-599 join at M2 by a recorded addition event.

**Path triggers (DESIGN).** `registries/batteries/triggers.toml` is the one trigger table: this bead owns the
file, its format (`[[trigger]]` rows of `battery`, `paths` as glob patterns, `reason`), its loader and the `smoke`
row (`paths = ["**"]`: every change). The `fixtures` row's path list is owned by N38a-22 and is the union of this
bead's list and the Gauntlet's: `crates/frob-contact/**`, `crates/frob-actuate/**`, `crates/frob-sense/src/clock*`,
`crates/frob-sense/src/clock/**`, `crates/frob-sense/src/packet/**`, `crates/frob-spec/**`, `crates/frob-dyn/**`,
`crates/frob-arena/src/fixtures/**`, `kernels/**` (contact, actuator and clock kernels), `assets/cards/**`,
`assets/fixtures/**` and `crates/frob-conformance/registry/known_answers.toml`; a missing pattern skips a required
run, an extra one only costs a run. This bead commits the row with that list so that the loader and its tests have
content at M1, and N38a-22 adds or justifies every later pattern. A change is the set of paths that differ from the
merge base. The table is data so that CI, a local pre-push check, the M1 conformance runner (BD-146) and the
Gauntlet run schedule (N38b-25) read one source. The trigger loader, `trigger::load(repo_root)`, refuses a second
file named `triggers.toml` under `registries/` or `crates/` of the repository root it is given (the two trees
where a table could be placed; `target/` and vendored sources are not searched, so a dependency's file of that name
is neither walked nor a false refusal), and a row naming a battery that has no manifest. The trigger loader is
called by CI, the pre-push check and the conformance runner, not by a verb: its errors are `LoadError` values that
those callers print with the offending path before exiting non-zero.

Determinism class of identities: D0 (exact; hashes of canonical bytes). Evidence of this bead's outputs: none
cross the agent boundary as numbers; identities and events are ledger facts.

## Acceptance criteria

- [ ] `frob.battery/1` manifests for `smoke` and `fixtures` exist, load, and resolve to a `BatteryId`; the `fixtures` manifest holds the twenty `ka` items listed above.
- [ ] Permuting the items of a manifest leaves `BatteryId` unchanged; removing one item changes it (property test over 1,000 random manifests).
- [ ] A manifest whose item set differs from the last registered identity with no event row is refused at load with `battery-manifest-invalid`, kind `no-event`, exit code 3, the first repair naming the event to append; with an event row and a reason it loads.
- [ ] A removal event with an empty reason is refused (kind `empty-reason`); an edited recorded event is refused (kind `record-edited`); a misspelt manifest key is FROB-REF-103.
- [ ] `battery::resolve("smoke", "all")` returns the registered `BatteryId` and its item list; the run-record field round-trips. (The verb-level echo of the `BatteryId` in `bound` by `eval.run` is asserted by N24c-04 and by the end-to-end step `battery_identity`.)
- [ ] The three smoke task files pass `frob task check`; the refusal item is refused with FROB-REF-526.
- [ ] Every shipped manifest carries `lane = "discovery"` and its items are readable by the lane's guard through `battery::resolve`. (The refusal FROB-REF-567 of a `hard` or `covering` item offered as a confirmation sample is the qualification lane's, N24b-16, asserted end to end by N24b-24 step 7a; it is not a check of this bead.)
- [ ] A check appended to `battery::load_checks` runs after the loader's own checks and before registration; when it refuses, no identity and no event row are written.
- [ ] `scripts/e2e/battery_manifests.sh` passes on a clean checkout at M1.
- [ ] The trigger table selects `fixtures` for a change under `crates/frob-contact`, `crates/frob-sense/src/packet`, `assets/cards` or to `crates/frob-conformance/registry/known_answers.toml`, and not for a change under `docs/`; `smoke` is selected for every change.
- [ ] There is one trigger table: a second file named `triggers.toml` (for instance under `crates/frob-conformance/registry/`) is refused by the loader, naming it.
- [ ] `crates/frob-arena/CONTRACT.md` documents the manifest, the identity rule, the event log and the lane flag in its ten sections.

## Test plan

### Unit tests
- `battery_id_is_order_independent`: two manifests with the same three items in different order hash equal.
- `battery_id_changes_on_removal`: removing item 2 of 3 changes the hash; the test stores both hashes as constants of a synthetic manifest (labelled `synthetic`).
- `battery_event_required`: load of a shortened manifest without an event fails with `battery-manifest-invalid`, `observed.kind = "no-event"`, the pointer at the removed `ItemId`; with `{removed: [ItemId], reason: "scene retired: duplicate of s:…"}` it succeeds.
- `battery_event_reason_nonempty`: `reason = ""` and `reason = "  "` fail with kind `empty-reason`.
- `battery_event_mismatch`: an event whose `to` is the identity of a different item set fails with kind `event-mismatch`, printing the computed identity.
- `battery_manifest_schema`: `lane = "confirmation"` fails with kind `schema`; a key `iteem` fails with FROB-REF-103 and the pointer at the key.
- `battery_event_file_recorded`: a shortened manifest with one `[[event]]` appended to its events file loads; the ledger then holds one `frob.battery.event/1` row whose sequence precedes the first run record citing the new `BatteryId`; loading again writes no second row; editing the recorded event's `reason` in the file afterwards is refused at load.
- `battery_item_canonical_roundtrip`: TOML → canonical JSON → TOML is the identity on 1,000 random items.
- `battery_fixture_items`: a `ka` item with and without `fixture` loads with no task file present; an item with
  both `ka` and `task`, one with neither, `ka = "602"` and `fixture = "cart-sill-dock"` each fail with kind
  `schema` and the pointer at the field; adding `ka = "KA-616"` to the shipped `fixtures` manifest changes its
  `BatteryId` and needs an addition event.
- `battery_lane_is_discovery`: every shipped manifest has `lane = "discovery"`; a manifest with another lane fails to load.
- `trigger_table_matches_paths`: table-driven test of twelve paths against expected battery sets, including
  `crates/frob-sense/src/clock/phase.rs` (matched by both `clock*` and `clock/**`), `crates/frob-sense/src/packet/rx.rs`,
  `assets/cards/rubber-60a.fcard` and `docs/index.md` (smoke only).
- `trigger_table_single_file`: a planted second `triggers.toml` is refused at load with its path; a row naming an
  unknown battery is refused.
- `battery_resolve_returns_current`: after a recorded removal event, `resolve` returns the new `BatteryId`, the shortened item list and the event's ledger sequence.
- `smoke_refusal_item_526`: checking the smoke refusal task returns FROB-REF-526 (horizon shorter than the verdict's reach).
- `battery_load_checks_extension`: a synthetic check appended to `battery::load_checks` that refuses any manifest named `synthetic-refuse` is called after the loader's own checks; the refused load registers no identity and writes no event row; the shipped list is empty.

### End-to-end script and logging
This bead's own script, `scripts/e2e/battery_manifests.sh` (header `bead=N24b-01 milestone=M1`), sources the
STD-E2E helper and uses only this bead and its dependencies: the verb `task.check` (BD-122) and this bead's
example target `cargo run -p frob-arena --example battery_resolve -- <name> <class> [--registries <dir>]`, which
calls `battery::resolve` against a state root and prints the `Resolved` value or the `LoadError` as JSON (name,
kind, pointer, first repair) with exit 3 on a refusal, and `--example battery_triggers -- <path>…`, which prints
the batteries the trigger table selects. Steps:
1. `smoke_tasks`: `frob task check <file> --json` on the three files under `assets/tasks/smoke/`: two admitted,
   the refusal item refused with FROB-REF-526 (`e2e_expect_refusal`).
2. `resolve_registered`: `battery_resolve smoke all` and `battery_resolve fixtures all`; the `BatteryId`s equal the
   registered ones and the item counts are logged.
3. `permuted`: in a scratch registry copy (`e2e_registries_scratch`), the items of `smoke` permuted: same identity.
4. `shortened`: one item deleted with no event: refused, `battery-manifest-invalid`, kind `no-event`, pointer at
   the removed `ItemId`; the event appended with a reason: a new identity, one `frob.battery.event/1` row in the
   scratch state's ledger, none on a second load; the recorded reason edited in place: kind `record-edited`; an
   event with reason `"  "`: kind `empty-reason`; a key `iteem`: FROB-REF-103.
5. `triggers`: the twelve paths of `trigger_table_matches_paths`; a planted second `triggers.toml` refused with its
   path.
Logged per STD-E2E: NDJSON lines with `ts`, `script`, `bead`, `step`, `event`, the exact command, exit code, wall
time, the `BatteryId`, the item count, digests of the manifest before and after the planted removal, a `refusal`
event with the name, kind, pointer and first repair, and on failure the first differing `ItemId` and the scratch
registry path; a final `summary` line. Later scripts repeat the control from the user's side through `eval.run`,
which depends on this bead: `scripts/e2e/arena_fixture_cart_sill_dock.sh` (N24b-20, step `fixtures_battery`),
`scripts/e2e/arena_scorecards.sh` (N24ap1-01, step `scorecard-identity`) and, at M3 with the scorecard's new
size, `scripts/e2e/arena_scorecard_batteries.sh` (N24b-23, steps `battery_identity` and `battery_shortened`).

### Known answers and negative controls
- Negative control (seed of the GATE-ARENA-07 control): a manifest with one item deleted by hand and no event. The loader must refuse it; if the deletion is accompanied by an event the identity must differ from the original.
- Metamorphic: renaming a manifest file without changing content changes nothing; changing one world address changes the identity.
- Determinism lanes: identities are D0; the same manifest hashes identically twice, in debug and release, and on both machines.

## Considerations

- The `fixtures` battery's identity changes at M2 when fixture 2's rows join. That is a recorded addition event, not a defect.
- The `covering` battery falls back to `standard` whenever the model class, tier, kernel versions or failure taxonomy changed since its incidence matrix was built (BD-278); the fallback is a new resolution, echoed in `bound`.
- A battery made only of past failures overfits them; `hard` is never the only content of a battery (enforced by BD-275's check `only-hard-battery` in `battery::load_checks`).
- OPEN-NEMESIS-5 (owner: Arena lead; blocks nothing): how a hard-world set is carried across a change of robot class or task version. Fail-closed default: a set belongs to one class and one task version.
- Runtime of `smoke` is a TARGET; if it exceeds minutes the scenario count per robot drops before any scenario kind is removed, and the drop is an event.
