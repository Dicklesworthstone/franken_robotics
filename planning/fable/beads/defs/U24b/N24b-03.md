## Background

A **fixture** is a small registered task whose answers are known before any run: a closed form, an enumeration
or a hand derivation. Two full fixtures exist, `fixture:cart-sill-dock` (a loaded cart crosses a door sill and
docks) and `fixture:quad-split-grip` (a quadruped on a landing with a low-grip strip). Each has an *analytic
layer* (limiting rigs whose expected values are derived on paper), a *development batch* (a frozen set of
randomized conditions on which two designs are compared) and a decision *rule* with its pre-analysis. The
analytic layers run on every change that touches contact, actuators, clocks or the requirement language.

ADR-ARENA-10 (decision): **a fixture is complete before its first run.** Every mass, constant, seed and rule of
a fixture is recorded and hashed before either design runs, with a derivation on file for each analytic answer.
Reason: a fixture whose constants can move after the outcome is seen is a tuning harness. The invariant that
enforces it is INV-ARENA-04: a fixture's constants, seeds, input table and rule are hashed into the ledger
before its first run. Rejected alternative: fixtures as ordinary tests with constants in source code. Rejected
because a source edit after a failing run is invisible to anyone reading the result, and because the same
constants would then be duplicated between the test, the task file and the derivation (ADR-GAUNT-06: one fixture
identity per physical case).

This bead builds the registry and the verb that every fixture uses. It contains no physics. `task.fixture` is
the verb of kind `run`, first milestone M1, that "runs a registered fixture's analytic layer or batch and
reports every row against its known answer".

## Scope

In: the fixture manifest format and `FixtureId`, with the declared inputs and the declared free parameters; the
pre-run ledger record and its enforcement (INV-ARENA-04); refusal FROB-REF-530; the verb `task.fixture` with its
schemas, layers, row report, control runs and exit codes; the check of `sim.run --fixture <name>` (VERBS-sim's
option, owned here at M1); the convention for derivation files; registration in the verb registry.

Out: the content of fixture 1 (N24b-04, N24b-05, BD-123, N24b-07) and of fixture 2 (N24b-12, BD-202, N24b-13);
the study rule and its pre-analysis (N24b-06); the `fixtures` battery (N24b-01); the run axes and row selectors
(N24bx-01) and `--battery fixtures` (N24c-10), which extend this verb; the listing of fixtures, which is
`task.list` with `kind = "fixture"` (N24bx-01); `sim.run --param` itself (N22c-29, M4), whose relation to the
recorded hash this bead states; the registry rows themselves (VERBS-task, VERBS-sim).

## Technical approach

**Manifest, schema `frob.fixture/1` (DESIGN).** `assets/fixtures/<name>/fixture.toml`, with sections:

| Section | Content |
|---|---|
| `identity` | `name` (`fixture:<name>`), `version`, `kind` (`synthetic` or `measured`), the question the fixture answers |
| `constants` | Every numeric constant with unit and label: masses, geometry, motor and loop constants, friction, gravity, clock periods, thresholds of the requirement. Exact decimal strings |
| `designs` | The `DesignId`s compared (for example design A and design B), and the frozen `ControllerId` where one applies |
| `task` | The `TaskId` of the fixture's task file (the requirement is part of it) |
| `inputs` | Which run inputs the fixture declares, each `declared` with its identity or `open`: `scene`, `task`, `controller` (and `designs`, always declared). A declared input is fixed by the fixture; an open one is the caller's to give |
| `free` | The declared free parameters, each with `name`, `dimension` (its unit), `domain` (an interval or a finite set, exact strings), `default`, and the side that declares it (`design` or `controller`). Absent when the fixture has none |
| `rows` | The analytic layer: per row `id`, `statement`, `expected` (value or values, unit), `tolerance` per tier, `tiers`, `rig` (the rig that realizes it, or `host`), `derivation` (path and BLAKE3 of the file), `ka` (the known-answer number), `control` (the registered negative control, if any) |
| `batches` | Per batch: `master_seed`, the world addresses, the stream names with their distributions, the generator pin, the mapping from generator output to each draw, and the hash of the resolved input table |
| `rule` | The study rule identifier and parameters (for fixture 1: `paired-clopper-pearson/1`, level 0.05, margin 0.05) and the hash of its pre-analysis |

`ConstantsHash` is the BLAKE3 hash of the canonical `constants` and `free` sections. `FixtureId` is the BLAKE3
hash of the canonical manifest with the derivation and input-table hashes included. A measured profile replaces a
synthetic one only under a new fixture name or version, hence a new `FixtureId`.

**Declared inputs (the rule VERBS-sim states for `sim.run --fixture <name>`).** A run of a fixture through
`sim.run --fixture <name>` takes its designs, the input table and every input the `inputs` section declares from
the fixture; giving a declared input again (`--scene`, `--task` or `--controller`) is FROB-REF-802, and a
positional design or `--designs` is 802 always. An input the section leaves `open` may be given (N22c-29 and
N22c-46 choose the controller of a fixture design this way); its identity is recorded in the run record and in
the run's `ModelId` or `ControllerId`, and it does not enter `FixtureId`. The fixture-run check below compares
the declared inputs only. Fixture 1 declares all of them (its manifest is N24b-05's).

**Free parameters and the recorded hash (DESIGN; the interim rule N22c-29 uses).** The `free` declarations
(name, dimension, domain, default) are part of `ConstantsHash`; a run's values for them are not. A run that gives
`--param <name>=<value>` (VERBS-sim's option, N22c-29) with a value inside the declared domain matches the
recorded hash and is not FROB-REF-530: the value is recorded in the run record and enters the run's `ModelId` or
`ControllerId`, so two runs at different values are different runs of one fixture. A value outside the declared
domain is FROB-REF-530 (as an axis value the manifest does not declare is, VERBS-task), with the pointer at
`free.<name>.domain`; a name the fixture does not declare, or one it fixes in `constants`, is 802 (VERBS-sim).
Changing a declared domain or default changes `ConstantsHash`, so every later run of that version is
FROB-REF-530 and the change needs a new version. Absent `--param`, the default is used and recorded.

**Pre-run record (INV-ARENA-04).** Algorithm of every `task.fixture` invocation:

1. Load and canonicalize the manifest; compute `FixtureId`, `ConstantsHash`, each derivation hash and each batch's input-table hash (the table is resolved from the seed and the mapping, without running any episode).
2. Look up the ledger record `fixture-registered {fixture, FixtureId, ConstantsHash, input_tables, rule_hash, derivations, ledger_seq}`.
3. No record for this fixture name and version: write it, in its own transaction, before any episode or rig is scheduled. The first run of any design therefore has a ledger sequence number greater than the record's.
4. A record exists and every hash matches: proceed.
5. A record exists and any hash differs: refuse with FROB-REF-530.

Episodes produced by a fixture run carry `fixture: FixtureId` in their run record. Any run that claims to be a
fixture run (for example a `sim.run` with `--fixture`, or an import of a `.frun` file) is checked the same way:
its task, designs, constants and input row must match the recorded hashes.

**Refusal.** FROB-REF-530: "a run offered as a fixture run does not match the fixture's recorded hash". Exit
code 3 (refused input). The refusal names the first differing hash (`pointer`), the recorded and observed values,
`retry: after-change`, and ranked repairs: (1) restore the recorded constants; (2) register the changed fixture
under a new version, which starts a new record and leaves earlier results attached to the old identity. The
refusal for a missing settled start state is FROB-REF-529 (no settled-pose cache for this model and task; exit
code 3; repair: run `task.settle`).

**Derivation files.** `docs/derivations/<fixture-name>/<row-id>.md`, one per analytic row: the symbols, the
free-body or algebraic argument, the substituted numbers and the result, hand-checkable. The manifest stores
each file's hash, so a changed derivation is a changed fixture. DESIGN: the hash covers the file's body below its
front matter, not the front matter. The front matter is where N24-KA's rule lists, for each KA identifier the
row serves, the test that checks it (crate, test name, owning bead, or `pending: <bead>` until that bead lands);
the tests that check a row are added by later beads (BD-123's rigs, N24b-09's batch tiers), and a derivation is
the same derivation whoever tests it. Hashing the whole file would turn each such addition into FROB-REF-530 on
a fixture whose physics did not change. The front matter's KA identifiers are checked against the manifest's
`ka` column by the loader, so a row cannot silently move to another known answer.

**The verb.** The row of record is the `task` cluster registry's (VERBS-task, a dependency); this bead implements
the handler against it. The row: `name = "task.fixture"`, `cluster = "task"`, `kind = "run"`, tier S, capabilities
`["task:run"]` (the cluster rule `<cluster>:<read|run|write|admin>`, a proposal until the capability bead BD-258
fixes the scope registry; `sim:run` is not required), input schema `frob.task.fixture.in/1`, output schema
`frob.task.fixture.out/1`, chapter refusals `["FROB-REF-529", "FROB-REF-530"]`. The surface-wide refusals are
appended by the generator for the kind `run` and are not listed in the row: 720 (scope missing), 723, 724 (not
implemented in this build, which is also what a release build answers to `control`), 802 (schema failure,
including an unknown parameter), 701 to 704 and 761 (budget and admission), 803 and 805 (idempotency key reused
with different content; key missing). It is a long tool: it accepts a bounded synchronous wait (`sync_wait_ms`)
and otherwise returns a job handle with exit code 8; it takes an idempotency key (`--key`) and a budget.

Input: `fixture` (the registered name; DESIGN: `fixture:cart-sill-dock` and the bare `cart-sill-dock` name the
same fixture, because the registry example and the fixture scripts use both spellings, and the output always
prints the prefixed form), `layer` (`analytic`, `rigs`, `batch` or `all`), `rows`
(optional subset), `tier` (`host`, `referee`, `batch-cpu`, `cuda`, `metal`), `designs` (optional subset for a
batch), `control` (optional: the name of a registered negative control; accepted only in a build with the
`mutants` feature). The run axes and row selectors (`--actuator-level`, `--precision`, `--seed`, `--profile`,
`--variant`, `--set`, `--reflect`, `--law`, `--measure`, `--report`) are added by N24bx-01, and `--battery
fixtures` by N24c-10; the input schema is built so that they are additive. The verb has no listing option: the
registered fixtures are listed by `frob task list --kind fixture --json` (N24bx-01).

Output `frob.task.fixture.out/1`: `fixture`, `fixture_id`, `registered_seq` (a string), and
`rows: [{id, ka, statement, expected, measured, unit, tolerance, pass, tier, boundary_flag, derivation}]`; for
a batch, the pair counts with the accounting identity, the rule's verdict and the pre-analysis hash (filled by
the batch bead); `controls: [{name, caught: bool}]`. Envelope evidence: claim Known answer; class `Tested`
(`Certified` never; a host row computed in exact rationals is still reported `Tested` unless a certificate
exists); tier as run; determinism D0 for host rows in exact arithmetic, D2 per backend otherwise; the fixture
kind `synthetic` propagates as a label. Exit code 0 when every requested row passes; 2 when at least one row is
out of tolerance (a finding, with the row listed); 3 on refusal.

**Negative controls.** A control is a named planted defect (a mutant integrator, a removed geometric feature).
Mutants compile only under the cargo feature `mutants`; a release binary refuses `control` with FROB-REF-724
(the capability is not implemented in this build; exit code 5; repair: run the control from a `mutants` build). Under a control the expected result is that the named row **fails**; the verb reports
`caught: true` when it does.

**Cancellation.** Request, drain, finalize: a cancelled fixture job discards rigs in flight, keeps completed
rows in the job's partial state, publishes nothing as a result, and leaves the pre-run record in place.

## Acceptance criteria

- [ ] `frob task fixture fixture:<name> --layer analytic --key <k> --json` returns one row object per manifest row with expected, measured, tolerance and pass; the bare name `<name>` selects the same fixture; a session without `task:run` is refused with FROB-REF-720 (exit code 5).
- [ ] The first invocation writes `fixture-registered` before any episode: the record's ledger sequence is smaller than that of the first run record (asserted in a test).
- [ ] Changing one constant in the manifest after registration makes every later invocation refuse with FROB-REF-530, exit code 3, naming the constant's hash; registering a new version succeeds.
- [ ] A `.frun` file whose constants differ from the recorded fixture, offered as a fixture run, is refused with FROB-REF-530.
- [ ] A changed derivation body changes `FixtureId` and is refused the same way; adding a test name to a derivation file's front matter leaves `FixtureId` unchanged.
- [ ] On a synthetic fixture that declares `task` and leaves `controller` open, the fixture-run check refuses a `sim.run --fixture` request that also gives `--task` with FROB-REF-802 and admits one that gives `--controller`, recording the controller; with one declared free parameter, an in-domain value matches the recorded hash and is recorded, an out-of-domain value is FROB-REF-530 with the pointer at the domain, an undeclared name is 802, and a changed default in the manifest is FROB-REF-530 (in process at M1; through the binary once N16b-25 and N22c-29 add the options).
- [ ] `scripts/e2e/fixture_registry.sh` passes on a clean checkout at M1.
- [ ] `control` is refused in a release build and reported `caught` in a `mutants` build when the row fails.
- [ ] The verb's entry in `registries/verbs.toml` equals VERBS-task's row (capability `task:run`, chapter refusals 529 and 530, the appended codes by kind); it is reachable through `frob --json` and as the MCP tool `task_fixture` generated from the registry, with schemas and its refusal list.
- [ ] Cancellation test: request, drain, finalize; no orphaned job; the pre-run record remains.

## Test plan

### Unit tests
- `fixture_id_changes_with_any_constant`: property test, mutating each constant of a synthetic manifest (labelled `synthetic`) changes `ConstantsHash` and `FixtureId`.
- `fixture_prerun_record_precedes_first_run`: run a one-row synthetic fixture; assert `registered_seq < first_run_seq`.
- `fixture_changed_after_registration_refused`: edit `g` from "9.81" to "9.80665"; expect FROB-REF-530 with `pointer = constants.g`.
- `fixture_new_version_registers`: bump `version`; expect success and a second record.
- `fixture_derivation_hash_enters_identity`: append a byte to a derivation file's body; expect a different `FixtureId`; add a test name (or replace `pending: <bead>` by one) in its front matter; expect the same `FixtureId`; change a front-matter KA identifier to one the manifest's row does not carry; expect a load error naming the row.
- `fixture_declared_inputs`: a synthetic fixture with `inputs = {scene = declared, task = declared, controller = open}`; the check of a `sim.run --fixture` request refuses `--task` and `--scene` with 802 and admits `--controller`, whose identity is in the run record and not in `FixtureId`.
- `fixture_free_parameters`: a synthetic fixture declaring `mu` (dimensionless, domain ["0.3", "1.2"], default "0.8"); `--param mu=0.5` matches the recorded hash and records 0.5; `--param mu=1.5` is FROB-REF-530 with `pointer = free.mu.domain`; `--param nu=1` is 802; the domain changed to ["0.3", "1.0"] in the manifest changes `ConstantsHash` and the next run is FROB-REF-530; no `--param` records the default.
- `fixture_row_report_schema`: output validates against `frob.task.fixture.out/1`; `registered_seq` is a string.
- `fixture_control_requires_mutants_feature`: without the feature the call is refused with FROB-REF-724 and exit code 5; with it, a row planted to fail reports `caught: true`.
- `fixture_exit_codes`: all rows pass → 0; one row planted out of tolerance → 2; changed constant → 3.
- `fixture_row_matches_registry`: the generated entry has capabilities `["task:run"]` and chapter refusals exactly `["FROB-REF-529", "FROB-REF-530"]`; 724 appears only among the codes the generator appends for the kind.
- `fixture_name_spellings`: `fixture:cart-sill-dock` and `cart-sill-dock` resolve to one `FixtureId`; the output's `fixture` field is `fixture:cart-sill-dock` for both.

### End-to-end script and logging
This bead's own script, `scripts/e2e/fixture_registry.sh` (header `bead=N24b-03 milestone=M1`), sources the
STD-E2E helper and runs on the `synthetic` fixture `fixture:registry-demo` that this bead ships under
`assets/fixtures/registry-demo/` (two host rows with derivation files, one declared free parameter, `task`
declared and `controller` open); every edit is made to a scratch copy of the manifest, never to the shipped one:
1. `register`: `frob task fixture fixture:registry-demo --layer analytic --tier host --key "$(e2e_key reg-1)"
   --json`; both rows pass; `registered_seq` precedes the first run record; the bare name under a new key gives
   the same `fixture_id`.
2. `refuse_changed_constant`: one constant edited in the scratch copy; `e2e_expect_refusal FROB-REF-530 3` with
   the pointer at the constant; the version bumped: a second record.
3. `derivation`: a byte appended to a derivation body: FROB-REF-530; a test name added to its front matter:
   the same `fixture_id` and exit 0.
4. `inputs_and_params`: `frob sim run --fixture registry-demo --key "$(e2e_key fx-run-1)" --json` runs with the
   declared inputs and the default of the free parameter recorded; then, each under its own key, `--task <t>`
   (802), `--controller <c>` (runs, the controller in the run record), and `--param` in domain, out of domain and
   undeclared (runs, 530, 802). `--task` and `--controller` are N16b-25's (M2) and `--param` N22c-29's (M4): until
   `frob sim run --help --json` lists an option, its sub-step is `e2e_skip` with the reason, never a pass, and the
   check itself is covered in process by `fixture_declared_inputs` and `fixture_free_parameters`.
5. `exit_codes`: a row planted out of tolerance: exit 2 with the row listed; on the release binary `--control
   <name>`: FROB-REF-724, exit 5; a session without `task:run`: FROB-REF-720, exit 5.
6. `cancel`: the long layer cancelled during a rig: no orphaned job, the pre-run record remains.
Logged per STD-E2E: the exact command, exit code, wall time, the envelope's evidence block, `fixture_id`,
`registered_seq`, one `assert` event per row with expected, measured, unit and tolerance, a `refusal` event with
the code, pointer and first repair, on failure the first differing row or hash with the scratch manifest's path,
and a final `summary` line. The same steps on `fixture:cart-sill-dock` are N24b-20's (`register`,
`refuse_changed_constant`, `analytic_host`), which runs this script as a stage.

### Known answers and negative controls
- Negative control for INV-ARENA-04: a build in which the pre-run record is written after the first episode (mutant `late-registration`); the ordering test must fail.
- Negative control for FROB-REF-530: the edited-constant manifest above.
- Determinism: `FixtureId` is D0; identical twice, in debug and release, and across platforms.

## Considerations

- The record is per fixture name and version, not per machine: a second machine with the same ledger lineage must see the same hashes or refuse.
- Tolerances that the plan prints as "to set" are fixture constants: they are written into the manifest, and hence hashed, before the first run of the tier they apply to. A tolerance cannot be loosened after a failure without a new fixture version.
- The verb reports rows; it records no gate. Gates are recorded by the Gauntlet's test targets, which call this verb exactly as an agent would.
- Security: manifest strings are data; a fixture name is an identifier and never a path component supplied by the caller.
