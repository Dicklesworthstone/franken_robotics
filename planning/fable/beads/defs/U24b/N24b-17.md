## Background

The blinded qualification lane bounds the chance of any false promotion in a campaign by α, for any number of
adaptive retries, provided three things hold: each request is fixed before its worlds are drawn, the worlds are
fresh, and the level is spent regardless of the answer. This bead builds the second: **fresh sealed clusters**.

Protocol step 3 (Draw): the service derives fresh world clusters for request i from a sealed key, the campaign
identifier, the index i and a cluster counter. A **cluster** is the unit that shares a generator draw, such as
one building with its materials; clusters, not episodes, are the units of inference. No cluster serves two
requests and none has appeared in any discovery dataset (INV-QUAL-02: confirmation clusters are fresh: no
cluster serves two requests, and none is in any discovery dataset before the campaign closes). Protocol step 6
(Close): when the campaign closes, the key is revealed, the clusters and their episodes become readable, and
the family is retired into discovery; it never serves as a confirmation family again.

Two different protections are at work and the plan keeps them apart. Freshness alone controls the error rate.
Blinding protects the claim's population: if an agent could read confirmation worlds, they would inform its
next candidate, the held-out family would stop being held out, and a promotion would describe worlds the design
was fitted to. If a reversal on a sealed family is ever used to inform training or selection, that family is
retired at once. ADR-SAFE-02: isolation of confirmation worlds is enforced by capability, by a separate store
and by address namespace, all three; this bead owns the address part and the derivation, bead BD-261 the
capability and store parts and the audit.

Rejected alternative: a fixed held-out set that every request reuses. Rejected because a decision on reused
worlds is correlated across requests and an adaptive agent fits the set; the negative control of the lane's
gate is exactly that configuration (reused clusters at a constant level: a false promotion in more than 99% of
simulated campaigns).

## Scope

In: the sealed key and its commitment; the derivation function; the confirmation address namespace; the
freshness ledger and refusal FROB-REF-844; family capacity; the close-time reveal; retirement of a family and
of an audited cluster; the lineage mark that FROB-REF-843 consults. Out: commitment (N24b-16); running episodes
on the clusters and the receipt (BD-259); the capability and store layers and the fuzz audit (BD-261); offline
replay of the derivation (BD-383).

## Technical approach

**Sealed key.** At campaign opening the daemon draws a 256-bit key K from the operating system's entropy source
inside the qualification executor, stores it only in the confirmation store (a separate root with a separate
key, opened only by the executor), and writes to the ledger the commitment C = BLAKE3("frob.qual.keycommit/1" ‖
campaign id ‖ K). The key never appears in an envelope, a log line or a job record before close. The key is the
one deliberate source of non-reproducibility in the system before close; after close everything derived from
it replays exactly.

**Derivation (DESIGN).** For request i and cluster counter j = 0, 1, …:

    seed(i, j) = BLAKE3-keyed(K; "frob.qual.cluster/1" ‖ campaign id ‖ u32(i) ‖ u32(j))      (256 bits)

The world family's generator maps a seed to a cluster: a scene instance with its materials and the cluster's
world addresses, all in the confirmation namespace: address = (namespace = confirmation, campaign serial, i, j,
world-in-cluster k). Each cluster has a content digest `ClusterDigest` = BLAKE3 of its canonical generator
output. Distinct (i, j) give independent seeds by construction, so a request's clusters are independent of
everything any agent saw before it.

**Ledger order.** Derivation for request i is permitted only after the request's commit transaction has
committed (N24b-16). It writes one record `clusters-derived {campaign, index, count, digests_root, ledger_seq}`,
whose sequence number exceeds the commit's (INV-QUAL-04). `digests_root` is the Merkle root of the cluster
digests, so the set is fixed without being revealed.

**Freshness checks (INV-QUAL-02), each cluster.**

1. *Not used before in confirmation.* Table `qual_clusters_used (world_family, ClusterDigest)` with a unique
   key across all campaigns of the family. An insert that collides refuses with FROB-REF-844.
2. *Not in any discovery dataset.* The cluster's scene identity and the identity of its scene group (a base
   scene and everything derived from it: mirrored layouts, clutter variants, retrofit variants, scans of one
   building) are checked against the index of discovery scene groups. A hit is skipped: the counter j advances,
   the skip is recorded with the counter value (so the derivation stays replayable), and the cluster is not
   used. More than a declared number of skips per request (DESIGN: 1% of the request's clusters) refuses the
   request's draw with FROB-REF-844 and flags the family for the owner.
3. *Namespace disjointness (PO-SAFE-02: the address namespaces of discovery and confirmation are disjoint;
   exact, the namespace is a field of the address compared as integers).* Every derived address carries the
   confirmation namespace; discovery samplers reject any address in it, so no discovery run can coincide with a
   confirmation world.

FROB-REF-844: "a cluster would be used twice". Exit code 3. It can arise from a replayed index, from a
re-execution that tries to re-derive instead of reading the stored derivation, or from a generator collision.
Repairs: read the stored derivation for a committed request (idempotent re-execution); never reuse a counter;
if a collision is genuine, the cluster is skipped and recorded.

**Capacity.** A family declares how many clusters it can supply. Default under OPEN-ARENA-3: one sealed family
per task family, sized for 20 requests at 256 clusters (5,120 clusters). A request that would exceed the
remaining capacity is refused before commitment (N24b-16, FROB-REF-842 with the capacity named), so no level is
spent on a draw that cannot be served.

**Close, reveal, retire.**

1. `close` (needs `qual:admin`) marks the campaign closed and writes `key-revealed {campaign, K}` to the ledger.
2. From that record on, the clusters, their episodes, telemetry and stills are readable by discovery sessions,
   and the derivation can be replayed by anyone: recompute C from K, recompute every seed(i, j), every
   `ClusterDigest` and each request's `digests_root`.
3. The world family is retired: recorded in the registry of retired families, marked as discovery data, and
   never accepted again as a confirmation family (opening a campaign on a retired family is refused).
4. Early retirement: the same step 3 is taken at once, without revealing K to agents, if a reversal on the
   family is used to inform training or selection, or if the lane's firewall is found breached; the campaign is
   then closed.

**Audited clusters.** An owner-held audit scope can open one confirmation cluster before close. Using it
retires that cluster (it is never drawn from again) and marks everything derived from the opened data with the
family's lineage mark.

**The lineage mark.** Every artifact derived from a cluster before close (episodes, telemetry, stills, and any
design, controller or policy whose lineage includes them) carries the mark `sealed-family:<world_family>`,
propagated through lineage as a join (nothing derived can be less restricted than an input). The admission
check behind FROB-REF-843 (N24b-16) reads this mark.

Code: `crates/frob-arena/src/qualify/{key,derive,fresh,close}.rs`.

## Acceptance criteria

- [ ] Over 10⁴ derived clusters across 40 requests of one campaign, no `ClusterDigest` repeats and every address is in the confirmation namespace.
- [ ] A forced reuse (re-deriving for a second request with the first request's counters) is refused with FROB-REF-844.
- [ ] A planted discovery scene group that collides with a derived cluster is skipped and recorded; the request still receives its full count of fresh clusters.
- [ ] No derivation record precedes its request's commit record in ledger order.
- [ ] A discovery sampler given a confirmation-namespace address rejects it; the lane given a discovery address as a sample rejects it.
- [ ] After close, recomputation from the revealed key reproduces the key commitment, every seed, every cluster digest and every `digests_root`.
- [ ] A retired family cannot be attached to a new campaign; an audited cluster is never drawn again.
- [ ] Before close the key appears in no envelope, log or job record (searched by the firewall audit of BD-261).

## Test plan

### Unit tests
- `derive_is_function_of_key_campaign_index_counter`: changing any one of the four inputs changes the seed; the same inputs give the same seed.
- `derive_no_collisions`: 10⁴ clusters, all digests distinct.
- `derive_namespace_field`: every address has namespace = confirmation; PO-SAFE-02 as an integer comparison.
- `fresh_refuses_reuse_844`: unique-key violation maps to FROB-REF-844 with exit code 3.
- `fresh_skips_discovery_collision`: a synthetic generator (labelled `synthetic`) that emits one scene group present in the discovery index: counter advances, skip recorded, replay reproduces the skip.
- `fresh_skip_limit`: more than 1% skipped refuses the draw.
- `order_commit_before_derive`: property test with interleaved writers.
- `capacity_refused_precommit`: 21st request of 256 clusters on a 5,120-cluster family is refused with nothing spent.
- `close_reveals_and_replays`: full replay from K.
- `retired_family_refused`; `audited_cluster_retired`; `lineage_mark_joins`: a policy trained on an episode of an audited cluster carries the mark.

### End-to-end script and logging
`scripts/e2e/arena_qualification_lane.sh` (bead N24b-24), steps `draw_is_after_commit`, `close_and_reveal` and
`replay_derivation`: after a request, `frob eval ledger` shows the derivation record's sequence above the
commit's; with an admin session the campaign is closed; then the script recomputes the derivation from the
revealed key with a standalone tool and compares digests. Logged per STD-E2E: ledger sequences, the count of
clusters, the Merkle root, skip records, and after close the recomputed roots. Before the close step the log
holds no address and no digest of an individual cluster.

### Known answers and negative controls
KA-622's negative control is built from this bead's mutant: `reuse-clusters` (the derivation ignores the index
i, so every request sees the same clusters), used with a constant level by the campaign simulator (N24b-18) to
show a false promotion in more than 99% of campaigns. KA-623 (after close, the cluster derivation replays; a
reused cluster is rejected). CX-267. Negative controls here: the forced reuse (must raise FROB-REF-844); a
build whose discovery sampler accepts the confirmation namespace (the namespace test must fail). Metamorphic:
the clusters of request i do not depend on the number or content of other requests. Determinism: given K, the
derivation is D0.

## Considerations

- OPEN-ARENA-3 (owner: project lead; blocks GATE-QUAL-01): family size and composition. Fail-closed default as above; no result is called qualified until a family exists.
- Entropy: K comes from the operating system; a test build may inject a fixed key through an admin-only test hook so that end-to-end tests replay, and that hook is absent from release builds.
- Private places: a sealed family built from a private scan inherits the private mark as well; reveal at close does not lift privacy.
- OPEN-SAFE-4: retired clusters are kept sealed indefinitely by default; storage for them is budgeted.
- The reveal makes every per-cluster outcome public to agents on the machine. That is intended: after close the family is discovery data, and the next campaign uses a new family.
