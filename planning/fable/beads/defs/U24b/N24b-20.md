## Background

Unit tests show that pieces work. An end-to-end script shows that a user or an agent driving the real `frob`
binary gets the same answers, with the evidence attached, and that failures are reported in a form someone can
act on. This script covers the user-visible capability "run a registered fixture and see every row against its
known answer" for `fixture:cart-sill-dock`: a loaded cart with 60 mm front wheels (design A) or 75 mm front
wheels (design B) crosses a 12 mm sill and docks. It composes the own scripts of the fixture's beads into one run
from registration to the development batch's report, and adds the steps no single bead owns: the user-side
registration and refusal on the real fixture, the `fixtures` battery through `eval.run`, and the batch.

It records no gate. GATE-ARENA-04 (fixture 1: every analytic row within tolerance on the referee and inside the
fidelity envelope on the batch tiers; the creep rigs flip at the stated thresholds; both negative controls are
caught) is recorded by its measuring beads from tier receipts: the M1 part by BD-123 (`--part M1`) and the M2 part
by BD-212 (`--part M2`). This script's log is user-side evidence beside those records (convention 9).

## Scope

In: one script, its stages and steps, assertions, negative controls, structured log, idempotence and seed
handling. Out: the fixture and its mechanisms (their beads); the batch tiers (N24b-09's own script) and the
variants (N24b-08), M2 work that this M1 script does not depend on and does not drive.

## Technical approach

**Path and invocation.** `scripts/e2e/arena_fixture_cart_sill_dock.sh [--mutants] [--long]`. Plain shell; exits
non-zero on any failed assertion; idempotent (it writes only under `target/e2e-logs/arena_fixture_cart_sill_dock/`
and a scratch store it creates and removes); every random input is named by an explicit seed printed in the log
(master seed 17 for the batch). Every call of a run verb (`task.fixture`, `sim.run`, `eval.run`, `task.settle`)
carries `--key "$(e2e_key <label>)"`, and two runs the script compares carry distinct labels (convention 5).

**Stages (the own scripts of the dependencies, each run whole; a stage that fails fails this script).**

0. `registry`: N24b-03's `scripts/e2e/fixture_registry.sh` (the registry and `task.fixture` on its synthetic
   fixture).
1. `analytic_host`: N24b-04's `scripts/e2e/arena_fixture1_host.sh` (the ten analytic rows on the host against the
   values of its table: 8.000 and 8.225 kg; 40 N and 32 N; 222.22 and 142.22 N per m/s; 36.000 and 40.694 mm;
   0.7500, 0.6459, 0.7332, 0.6351 and 1.270 N·m; 24/23 = 1.043, 0.887, and 34.2 N against the 32 N cap; 23.0 mm
   and 1.13%; 0.471 J against 0.360 + 0.018 J; 1.4820, 0.9207, 2.6917, 2.7075; 9 W, 0.375 A, 8 V, 16 W, 20 W, 4 W).
2. `model`: N24b-05's `scripts/e2e/arena_fixture1_model.sh` (its steps `check_task`, `settle` for designs A and B,
   `nominal` through the example target and through `frob sim run <A|B> --task <TaskId> --tier referee`).
3. `rigs`: BD-123's `scripts/e2e/arena_fixture1_rigs.sh`, with `--mutants` passed through (the rig rows on
   the referee, the six creep brackets 0.74/0.76, 0.64/0.66, 0.72/0.74, 0.63/0.65, 1.03/1.05, 0.88/0.90, the
   `boundary` flags, the release refusal of `--control`, and with `--mutants` the two controls
   `euler-current-then-wheel` and `rear-lip-removed` caught on a `gauntlet-mutations` build).

**Steps of this script (each a `step` value in the log).**

4. `register`: `frob task fixture cart-sill-dock --layer analytic --tier host --key "$(e2e_key reg-1)" --json` on
   a fresh store; assert `registered_seq` is present and smaller than the sequence of any run record.
5. `refuse_changed_constant`: copy the manifest to scratch, change g from 9.81 to 9.80665, run again under
   `--key "$(e2e_key reg-2)"`; assert refusal `FROB-REF-530`, exit code 3, pointer at the constant, and that the
   registered fixture is untouched.
6. `fixtures_battery`: `frob eval run <A> --battery fixtures --key "$(e2e_key fx-batt)" --json` (design A's
   `.fbot` positional; the verb is N24c-04's, the battery and its resolver `battery::resolve` N24b-01's); assert
   the run record's `battery: {id, items}` equals what `battery::resolve("fixtures", "all")` returns and that the
   envelope's `bound` block echoes the resolved `BatteryId`.
7. `batch_register`, `batch_run`, `batch_report` (referee; behind `--long`): `frob task fixture cart-sill-dock
   --layer batch --tier referee --key "$(e2e_key batch-1)" --json`, waiting on the job handle; assert the input
   table's registration precedes the first episode, 128 verdict objects exist, the accounting identity sums to 64,
   the reported interval and verdict equal a recomputation from the counts with `frob eval preanalyze`'s rule
   (KA-612), and both energy-per-completion figures are printed.
8. `determinism`: `frob task fixture cart-sill-dock --layer analytic --tier host` under two distinct keys
   (`det-1`, `det-2`): identical row values and `fixture_id`; with `--long`, the batch report recomputed from the
   stored run twice: identical bytes.

**Logging (the standard of the shared helper from STD-E2E).** The script sources the helper and writes
newline-delimited JSON to `target/e2e-logs/arena_fixture_cart_sill_dock/<utc-timestamp>.ndjson` and a
human-readable transcript beside it. Every line has `ts`, `script`, `bead`, `step`, `event` (`start`, `cmd`,
`assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the envelope's `evidence`
block (claim, class, tier, determinism, identities, seed), measured values with units and their thresholds,
digests where state is compared, and on failure the first differing value and the artifact paths needed to
reproduce (the `.frun` episode, the rig file, the friction value and world address). Per batch condition a
`metric` line records the address (17, k, 0), the four drawn values, both verdicts, margins and reasons. Each
stage logs under its own script's directory and this log records the stage's exit code and log path. A final
`summary` line gives counts of assertions passed and failed, controls caught, and the gate touched
(GATE-ARENA-04, referee rows); the script writes no gate row. Logs contain no private-scene data (the fixture is
synthetic).

## Acceptance criteria

- [ ] The script exists, is executable, and passes on a clean checkout at M1, its four stages included.
- [ ] Every step emits `start`, at least one `cmd`, its `assert` events and `end`; the `summary` counts equal the number of assertions executed.
- [ ] Every run-verb call carries `--key`, and compared runs carry distinct keys (a lint over the script's command lines finds no run-verb call without one).
- [ ] With `--mutants`, the rig stage reports each of the two controls caught; with a mutant made ineffective the script fails.
- [ ] Step 5 produces FROB-REF-530 and leaves the registered fixture untouched.
- [ ] Running the script twice gives identical digests for every compared step (determinism lane: twice on one machine).
- [ ] The script writes no gate row, and its `summary` names GATE-ARENA-04 as touched.
- [ ] Cancelling the script during `batch_run` leaves no partial store and no orphaned job.

## Test plan

### Unit tests
The script is itself a test; its helper functions are covered by the tests of STD-E2E. A dry mode
(`--list-steps`) prints the stage and step names, and a small test asserts the list above so that a silently
dropped step is caught.

### End-to-end script and logging
This bead is the script. Commands driven from the user's side: `frob task fixture`, `frob eval run`, `frob eval
preanalyze`, and through the stages `frob task check`, `frob task settle`, `frob sim run`, `frob task verdict`.
Assertions and log content are listed above.

### Known answers and negative controls
KA-602 to KA-611 (the analytic rows, through the host and rig stages), KA-612 (the rule at 64 pairs: 521, 521, 0,
1,103, used to recompute the batch verdict), KA-598 (energy figures). CX-262, CX-263, CX-265. Negative controls
exercised: the changed constant (FROB-REF-530); the two registered mutants (through the rig stage); a third
self-check, in which the script is run with an expected value deliberately altered in its own table (`--selftest`)
and must report a failed assertion, showing that its assertions can fail. Determinism lane: twice on one machine.

## Considerations

- Runtime: the analytic and rig steps take minutes on the referee; the batch (128 episodes of 8 simulated seconds) is the long step and runs behind `--long` in routine CI and always in the M1 exit run.
- If the referee refuses a step at the lip in some rig or trial, the script reports the refusal as a `refusal` event with the world and does not retry with other settings.
- The script never edits the fixture manifest in place; the changed-constant case uses a scratch copy.
- The batch tiers and the variants are not driven here: they are M2 work that this M1 script cannot depend on; N24b-09's own script runs the rigs on the batch tiers.
