## Background

A success rate is a count over a declared population. This script shows, from the user's side with the real
`frob` binary, that the population cannot shrink quietly and that every scenario is counted exactly once. It
covers the capability "run a battery and read a scorecard with full denominators": battery identity and
membership events, the seven outcome columns, the two denominators, the planted infeasible scenario, the
metric figures with their rules, and the design corpus's label freeze. It is the user-side evidence for
GATE-ARENA-07 (claim: Known answer; M3; TARGET: a planted infeasible scenario appears in its column and in the
all-scenario denominator; columns sum to the battery size on 100 random batteries; a silently shortened battery
changes identity); the gate's one recorder is BD-254, which measures it and records it from its known-answer
receipt (convention 9), and this script writes no gate row.

## Scope

In: one script, its steps, assertions, negative controls and structured log, and the stage runs of the
mechanism scripts it builds on (`scripts/e2e/arena_scorecard_m3.sh` of BD-254, `scripts/e2e/battery_manifests.sh`
of N24b-01, `scripts/e2e/corpus_registry.sh` of N24b-02). Out: the mechanisms (BD-254, N24b-01, N24b-02,
N24b-11), their own scripts, and the content of the batteries.

## Technical approach

**Path and invocation.** `scripts/e2e/arena_scorecard_batteries.sh [--tier referee|batch-cpu|gpu-cuda|gpu-metal]
[--mutants]`; `--tier` (default `batch-cpu`, spelled as in the `eval.run` row) is passed to every `eval.run` call,
and the steps that compare two runs use the same tier for both. Plain shell; non-zero exit on a failed assertion; idempotent (writes only under
`target/e2e-logs/arena_scorecard_batteries/` and a scratch store and scratch registry copy); seeds printed.

**Steps.**

0. `stages`: `scripts/e2e/battery_manifests.sh` (N24b-01), `scripts/e2e/corpus_registry.sh` (N24b-02) and
   `scripts/e2e/arena_scorecard_m3.sh` (BD-254), each run as a stage (with `--mutants` passed through), their log
   paths, digests and receipt hashes logged.
1. `battery_identity`: `frob eval run REF --battery smoke --key bi-1 --json`, then the same with the manifest's
   items permuted in the scratch copy and the distinct key `bi-2` (a reused key would return the first run's
   stored receipt); assert the echoed `BatteryId` is identical and the item count matches. REF is the reference
   quadruped's `DesignId`, positional as in the `eval.run` row.
2. `battery_shortened`: delete one item from the scratch manifest with no event; `frob eval run REF --battery
   smoke --key bs-1 --json` must be refused at load before any episode with the symbolic refusal
   `battery-manifest-invalid` (N24-REF; returned through `eval.run`), `observed` kind `no-event`, exit 3; assert
   the name and the kind and log the pointer. Append the removal as an `[[event]]` with a reason to the scratch
   events file (N24b-01); `--key bs-2` must proceed; assert a `frob.battery.event/1` row precedes the run record
   in the ledger, the `BatteryId` differs from step 1 and the scorecard reports the new size. Then edit the
   recorded event's reason in place; the next load (`--key bs-3`) must be refused with `battery-manifest-invalid`,
   kind `record-edited`; assert the name and the kind.
3. `scorecard_reference`: `frob eval run REF --battery standard --key sc-std-1 --json` then `frob eval scorecard
   <run> --json`; assert the seven columns sum to the battery size, both denominators are
   printed, each of the fourteen metrics is present with unit, and ratios to the reference are 1 for the
   reference itself.
4. `planted_infeasible`: a scratch battery containing one scenario whose world makes the task infeasible for
   the candidate by a checked necessary condition (a doorway narrower than the body, classified with `frob
   nemesis oracle REF --task <task> --world <world> --key pi-oracle-1 --json`), run with `--key pi-1`; assert the scenario is in `infeasible-for-candidate` with its witness, is counted in the
   all-scenario denominator and is absent from the second.
5. `random_batteries`: the accounting row on 100 random batteries, `e2e_tier g1_known_answers
   scorecard_accounting` (with `--mutants`, `--mutations`); assert from the receipt that the count of batteries is
   100 and failures 0, and log the receipt hash.
6. `columns_each_exercised`: a scratch battery built so that every column is non-empty (a refused run via a
   horizon shorter than the verdict's reach; a truncated trace for `undetermined`; a planted numerical fault
   for `invalid`); assert each column's count and the sum.
7. `energy_and_quantiles`: on a recorded two-trial example assert 10 J against 12 J and 30 J against 12 J; on a
   five-episode run assert the 99th-percentile cell is withheld as `{status: "not-observable", n: 5, p_max:
   0.5493, n_needed: 299}` with no value (BD-254's rule: 1 − 0.99⁵ = 0.049 is below 0.95).
8. `hard_not_confirmation`: with an `owner` session (the owner's root session on the command line, the holder
   role of the default `config/qualification.toml`: `e2e_session grant owner --scopes eval:read,qual:admin` before
   `frobd` starts, then `e2e_session open owner --principal owner --scopes eval:read,qual:admin`) opening a
   synthetic campaign (`frob eval ledger --action open --task <synthetic TaskId> --world-family <family> --json`,
   an admin action with no key) and an `agent` session holding `qual:run`, offer an item of the `hard` battery as the sample
   (`frob eval qualify REF --task <the campaign's TaskId> --claim '…' --clusters <the hard item> --key "$(e2e_key hard-1)"
   --json`; the qualification lane, BD-259, and the hard-world set's guard, BD-275, are dependencies); assert
   refusal `FROB-REF-567`, exit 3, before any commitment (`frob eval ledger <campaign> --json` shows index 0).
9. `covering_slots`: `frob eval run REF --battery covering --key cov-1 --json` (the covering selection,
   BD-278, is a dependency); assert one slot in five is marked held-out in the manifest and the echoed identity
   changes when the incidence is rebuilt.
10. `corpus_freeze`: the stage run of N24b-02's script in step 0 covers the freeze on the `synthetic` 12-entry
    corpus (the `CorpusId` matching the freeze record, a copy with one label flipped refused); this step reads
    that stage's log for both assertions and runs `frob design check <entry> --json` on one planted-defect entry.
11. `negative_controls` (with `--mutants`): a scorer that drops `invalid` episodes (step 6's sum must fail); a
    scorer that removes infeasible scenarios from the first denominator (step 4 must fail).
12. `determinism`: step 3's scorecard computed twice from the stored run; assert identical bytes.

**Logging.** Per the shared helper of STD-E2E: newline-delimited JSON at
`target/e2e-logs/arena_scorecard_batteries/<utc-timestamp>.ndjson` with a transcript; every line has `ts`,
`script`, `bead`, `step`, `event`, the exact command line, exit code, wall time, the envelope's `evidence`
block, the `BatteryId` and size, the column counts and their sum against the size, both denominators, metric
values with units, refusal codes, and on failure the first scenario found in zero or two columns with its
`ItemId`. The `summary` line gives assertion counts, controls caught and the gate touched (GATE-ARENA-07).
Scenes used are synthetic or redistributable fixtures; no private-scene data is logged.

## Acceptance criteria

- [ ] The script exists, is executable and passes on a clean checkout at M3.
- [ ] Each clause of GATE-ARENA-07 has a logged assertion with measured counts: steps 2, 4 and 5.
- [ ] Every outcome column is exercised at least once and the sum equals the battery size in every scorecard the script reads.
- [ ] With `--mutants`, both planted scorer defects are caught.
- [ ] The script writes no gate row; its `summary` line names GATE-ARENA-07 as touched, and the three stage scripts pass (BD-254 records the gate from its own receipt).
- [ ] Every step runs unconditionally: the qualification lane and the hard-world guard (step 8) and the covering
      selection (step 9) are dependencies of this bead, so no step is skipped.

## Test plan

### Unit tests
`--list-steps` and its asserting test; `--selftest` alters the expected sum in step 3 by one and must fail.

### End-to-end script and logging
This bead is the script. Commands from the user's side: `frob session open`, `frob eval run`, `frob eval
scorecard`, `frob nemesis oracle`, `frob eval ledger`, `frob eval qualify`, `frob design check`; `e2e_tier` for
the accounting row; the three stage scripts. Assertions and log content as above.

### Known answers and negative controls
KA-600 (accounting on 100 random batteries; control: a silently shortened battery must change identity),
KA-598 (energy figures; control: dropping failed attempts). CX-261. Negative controls: the hand-shortened
manifest; the two mutant scorers; the self-test. Determinism: a scorecard is a deterministic function of a
stored run.

## Considerations

- The reference scorecard's metric values are not asserted against numbers here (they are baseline records, written by the task-family beads); only presence, units and accounting are.
- Runtime is dominated by step 3 (about 200 scenarios); on a fast tier it takes minutes.
