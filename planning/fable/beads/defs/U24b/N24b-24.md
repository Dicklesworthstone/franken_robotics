## Background

The blinded qualification lane is the path by which a design comparison becomes a claim: a campaign owns a
sealed family of worlds; request i is committed before any confirmation world exists, receives the level
α_i = α/[i·(i + 1)], runs on fresh sealed clusters, and returns only a receipt; discovery sessions cannot read
confirmation worlds before the campaign closes. This script drives the whole protocol from the user's side
against a real daemon (`frobd`), the real CLI (`frob`) and the MCP server (`frob-mcp`), with no mocks. It is
the user-side evidence for the firewall gates (GATE-QUAL-02: 10⁴ fuzzed read attempts across every verb return
no sealed field; a planted leak path is found by the audit; receipts contain only the listed fields;
GATE-SAFE-03: at least 25 enumerated read paths all return FROB-REF-840, and a leaking test build is detected),
whose one recorder is BD-261 (it measures them and records them from its known-answer receipts, convention 9),
and it exercises the power half and the negative control of GATE-QUAL-01 at reduced scale. The full
2,000-campaign run of GATE-QUAL-01 and its record are BD-260's. This script writes no gate row.

## Scope

In: one script with the steps below, its sessions and scopes, its sealed-value scan, negative controls and
structured log, and the stage runs of the mechanism scripts the lane is built from. Out: the mechanisms
themselves and their own scripts (`scripts/e2e/qualify_ledger.sh` of N24b-15, `qualify_commit.sh` of N24b-16,
`qualify_clusters.sh` of N24b-17, `qualify_simulator.sh` of N24b-18, `qualify_standing_bundle.sh` of N24b-19,
`qualify_executor.sh` of BD-259, `qualify_firewall.sh` of BD-261, `arena_fixture1_holdout.sh` of N24b-10);
offline replay by `frob-verify` (N24b-25).

## Technical approach

**Path and invocation.** `scripts/e2e/arena_qualification_lane.sh [--long] [--mutants] [--mcp]`. Plain shell;
non-zero exit on a failed assertion; idempotent: it starts a daemon on a scratch store and a scratch
confirmation root, uses a fixed test key through the admin-only test hook so that runs replay, and removes
both stores at the end. Three sessions are opened: `owner` (holds `qual:admin`), `agent` (every discovery
scope and `qual:run`), `bystander` (discovery scopes only).

**Steps.**

00. `stages`: the eight mechanism scripts named under Scope, each run as a stage on its own scratch store
   (`--mutants` and `--long` passed through where the stage takes them), their log paths, digests and receipt
   hashes logged; the steps below then compose the lane on one daemon.
0. `config`: read `config/qualification.toml` (N24c-13) and log the regime the campaigns run under: holder
   roles, families per task family, requests per family, clusters per request, `decided`, the ADR identifier
   and the file's hash; assert that `agent`'s role is not among the holders.
1. `open_campaign`: as `agent`, attempt to open a campaign (`frob eval ledger --open …`; expect FROB-REF-720,
   exit code 5); as `owner`, open `q:e2e-coin/1` on the synthetic family (`frob eval ledger --open --task <coin
   task> --world-family <coin family> --slug e2e-coin --clusters-per-request 200 --key e2e-open-coin --json`) and
   `q:e2e-cart/1` on the cart fixture's sealed family at α = 0.05 (`--baseline-class <class of A>`, key
   `e2e-open-cart`), the open and close actions of N24b-15; assert each campaign record carries the
   configuration's hash and its capacity; assert a second open on the same claim family is refused with exit code
   7 (`campaign-already-open`) naming the open campaign, and that the same open repeated under its own key returns
   the stored record.
2. `dry_run`: the minimal submission of the worked agent session, `frob eval qualify <coin candidate> --task <coin
   task> --claim '<the absolute claim template naming the coin task's requirement, p = 0.05>' --dry --key e2e-dry
   --json` (the design positional, as in the verb's registry example; single quotes, since the template's backticks
   would be command substitution in double quotes); assert the
   preview fields of N24b-16: `campaign` = `q:e2e-coin/1`, `index_if_committed` = 1, `alpha_total` = `0.05`,
   `alpha_i` = `0.05/2`, `clusters` = 200, `preanalysis.qualified_reachable_with_failures_at_most` = 3 with
   bounds 0.0432 and 0.0504, the note "nothing was committed and no level was spent", the filled defaults
   echoed; and that the ledger sequence is unchanged.
3. `commit` and `receipt`: a committed request (`frob eval qualify … --key e2e-q1 --json`); assert the receipt
   has exactly the listed fields, `alpha_spent` = `0.05*1/2`, the three authorization flags false, evidence class
   `Tested`.
4. `replay_same_key` and `conflict_same_key`: the same key and content returns `idempotent_replay: true` and
   no new index; the same key with a changed n is refused with FROB-REF-803, exit code 7, no index assigned.
5. `ledger_after_requests`: `frob eval ledger q:e2e-coin/1 --json`; assert index, level strings and receipt
   hashes; after three more requests (keys `e2e-q2` … `e2e-q4`) assert the cumulative spend `0.05*4/5`.
5a. `ledger_invariants` (N24c-09's step): six more requests make ten; `frob eval ledger q:e2e-coin/1 --json`;
   assert indices 1 … 10 with no gap, each level `0.05/<i·(i+1)>` equal as a rational to α/[i·(i + 1)], and the
   running sum `0.05*10/11`; log each level against its expected value and, on failure, the first index whose
   level differs.
6. `draw_is_after_commit`: assert each request's derivation record has a ledger sequence above its commit's.
7. `refuse_842`, `refuse_843`, `refuse_841`, `refuse_844`: planted cases: a budget for 64 clusters at a level
   that needs more; a candidate whose lineage carries the family's mark (made by reading one cluster under the
   owner's audit scope and deriving a design note from it); a request body tampered between commit and run (a
   test hook); a forced counter reuse (a test hook). Assert each code and exit code 3.
7a. `refuse_567`: an item of the `hard` battery (BD-275) and an item of the `covering` battery (BD-278), both
   dependencies, and the cart fixture's development addresses (17, k, 0) (N24b-10), each offered to `frob eval
   qualify … --clusters <the named worlds> --key …` as a confirmation sample; assert FROB-REF-567, exit code 3,
   nothing committed (the check N24b-01's acceptance assigns to this script).
8. `firewall_paths`: as `agent`, run each read path of the registry-derived set against the open campaign's
   run. The set is computed at run time from the verb registry (every verb and MCP resource template with an
   identifier-typed argument that can resolve to a run, job, episode, artifact, address, scene or campaign),
   the same enumeration BD-261's dispatcher test and N19c-14's handler-level test iterate, never a list kept in
   the script; the step fails if the set has fewer than 25 members or lacks any of BD-261's named minimum
   members, and logs the set's size and digest. Assert every attempt returns `FROB-REF-840` with exit code 5
   and no partial data, and appears in the ledger as `sealed-read-attempt`. With `--mcp`, repeat through the
   MCP tools.
9. `firewall_fuzz`: 1,000 generated read attempts by default, 10⁴ with `--long`, across every verb in the
   registry; assert zero hits of the sealed-value dictionary in any response.
10. `planted_leak` (with `--mutants`, which builds the daemon with `--features
    gauntlet-mutations,<crate>/nc-<nnnn>` for each control in turn): against the build with BD-261's planted
    leak, the fuzz must report at least one hit naming the verb and argument; against N24b-18's build
    `leak-per-world-outcomes`, the receipt-shape assertion of step 3 must fail. Both recorded as caught.
11. `simulator`: reduced campaigns through the verb on the synthetic family: planted gain (assert at least 80%
    promoted within 10 requests) and, with `--mutants`, the reused-cluster constant-level lane on N24b-18's
    `absolute-above` world (assert more than 99% of campaigns show a false promotion; on the paired worlds the
    fraction is compared with N24b-18's computed expectation, not with 0.99).
12. `fixture1_dry`, `fixture1_commit`, `fixture1_receipt`: the cart fixture's holdout request sized at its
    level on `q:e2e-cart/1`, the commands of N24b-10's script (`--dry`, `frob eval preanalyze … --level 0.05/2`,
    the committed request, `frob eval ledger`) under this script's keys.
13. `cite_without_receipt`, `bundle_open`: a promoting receipt cited for another design, and a design whose
    stored comparison was edited to `qualified` on disk, are each refused by `frob prove bundle` with
    `FROB-REF-845`, exit 3 (N24b-19's cases); `frob prove bundle --design … --receipt … --out open.frobcert --key e2e-b-open --json` writes
    a pre-close bundle; assert the sealed-value scan of the bundle finds nothing and `frob prove verify
    open.frobcert --json` accepts it with the note that the decision is not recomputed.
14. `cap`: a campaign opened with `--max-requests 3` refuses a fourth request before commitment (exit code 3,
    `campaign-request-cap`, N24b-15) with no index assigned and nothing spent.
14a. `battery_sealed_objects` (BD-261): as `owner`, `frob eval ledger --open --kind battery --label e2e --key
    e2e-open-bat --json` and `frob eval ledger q:battery-e2e/1 --seal key-1 --file <scratch object> --key
    e2e-seal-1 --json`; as `agent`, `--read-sealed key-1` and `artifact.read` of the object's digest each return
    FROB-REF-840, exit 5, and appear as `sealed-read-attempt`; as `owner`, `--read-sealed key-1` returns the bytes
    and writes a `sealed-admin-read` record; after the owner's close, `agent`'s `--read-sealed` returns the bytes.
15. `close_and_reveal`, `post_close_reads`, `replay_derivation`, `bundle_closed`, `fixture1_close`: as
    `owner`, close the campaigns (`frob eval ledger <campaign> --close --key e2e-close-<n> --json`); assert the key
    is revealed, the read paths of step 8 now succeed for the revealed data, a recomputation of the cluster
    derivation from the revealed key and the derivation records (N24b-17's example target `qualify_derive`,
    subcommand `replay --revealed <file>`, fed the revealed records at the location `frob eval ledger <campaign>
    --json` returns after close) matches the recorded roots, the receipt's decision equals a recomputation
    from the revealed counts at α_i, the family is retired (a new campaign on it is refused with FROB-REF-886,
    N24b-17), and the post-close bundle (`frob prove bundle … --out closed.frobcert --key e2e-b-closed --json`)
    is accepted by `frob prove verify closed.frobcert --json` with the decision recomputed.
16. `log_scan`: the script scans its own log and transcript up to the first close step with the sealed-value
    dictionary and asserts no hit.

**Logging.** Per the shared helper of STD-E2E: newline-delimited JSON at
`target/e2e-logs/arena_qualification_lane/<utc-timestamp>.ndjson` with a transcript; every line has `ts`,
`script`, `bead`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command
line, the session used, exit code, wall time, the envelope's `evidence` block, request hashes and ledger
sequences (strings), level strings, receipt fields, refusal codes with pointers and repairs, fuzz totals and
hits against the threshold 0, campaign statistics with their thresholds (0.80, 0.99), and on failure the
campaign, index and the artifact needed to reproduce. The sealed-value dictionary itself is never written to
the log. The `summary` line gives assertion counts, controls caught and the gates touched (GATE-QUAL-01 power
half and control; GATE-QUAL-02; GATE-SAFE-03).

## Acceptance criteria

- [ ] The script exists, is executable and passes on a clean checkout at M3 against a real daemon.
- [ ] Every protocol step (commit, spend, draw, run, answer, close) has at least one logged assertion.
- [ ] Each refusal 840 to 845 is triggered and logged with its exit code, as are 567 (step 7a), 720 and the second-open conflict `campaign-already-open` (step 1), 803 (step 4), the cap refusal (step 14) and 886 (step 15).
- [ ] The ten-request ledger of step 5a matches α/[i·(i + 1)] and `0.05*10/11` exactly; a battery campaign's sealed object is refused to `agent` before close and readable after (step 14a).
- [ ] The read-path set of step 8 is derived from the registry at run time; its size and digest are logged and equal the set BD-261's dispatcher test iterates.
- [ ] The firewall steps cover at least 25 read paths and, with `--long`, 10⁴ fuzzed attempts with zero hits; with `--mutants` the planted leak and the leaking receipt are caught.
- [ ] The log before the close step contains no sealed value (step 16).
- [ ] The script writes no gate row; its `summary` line names the gates touched, and the eight stage scripts pass (BD-261 records GATE-QUAL-02 and GATE-SAFE-03 from its own receipts; BD-260 records GATE-QUAL-01).
- [ ] Killing the script mid-request leaves the job recoverable by its idempotency key with one index or none, and a re-run completes.

## Test plan

### Unit tests
`--list-steps` and its asserting test. `--selftest` plants one sealed address into a scratch response file and
asserts that the scan of step 9 reports it, showing the oracle can fail.

### End-to-end script and logging
This bead is the script. Commands from the user's side: `frob session open`, `frob eval qualify`, `frob eval
ledger` with its admin actions `--open` and `--close` under the owner's session (N24b-15) and `--seal` and
`--read-sealed` (BD-261), `frob eval preanalyze`, the enumerated read verbs, `frob prove bundle`, `frob prove
verify`, and the MCP tools of the same verbs (`eval_ledger` with `action`). Every run-verb call and every admin
action carries its own `--key`. Assertions and log content as above.

### Known answers and negative controls
KA-619 (levels: `0.05/2`, `0.05*4/5`), KA-620 (fourteen nulls give 51%, printed by the dry run's help text),
KA-621, KA-622 (reduced), KA-623 (firewall). CX-267, CX-384. Negative controls: the planted leak; the leaking
receipt; the reused-cluster constant-level lane; the self-test. Metamorphic: the decision of the first request
is the same whether or not later requests are made (the script records it before and after step 5).
Determinism: with the fixed test key the whole script replays with identical request hashes, cluster roots and
decisions.

## Considerations

- The fixed test key is injected through an admin-only hook that exists only in test builds; the script asserts that a release build refuses the hook.
- Runtime: the default lane takes minutes; `--long` (10⁴ fuzz attempts and larger campaign counts) mirrors the scale of BD-261's recorded receipts.
- OPEN-ARENA-3 default applies: only the owner session opens and closes campaigns.
- Chaos: a variant of steps 3 and 8 runs under an injected daemon restart mid-request and asserts that recovery releases nothing sealed.
