## Background

A reader of a qualified result should not have to trust the daemon that kept the books. The receipts, the
ledger of levels and, after close, the cluster derivation of a qualification campaign travel in a `.frobcert`
bundle, and the offline auditor `frob-verify` (a single binary built from the standard library alone, with no
simulator, GPU or network) replays them. This script runs that replay from the user's side on a machine state
that has neither the daemon nor the agent's session: it is the user-side evidence for GATE-QUAL-03 (claim:
Known answer; M5; TARGET: `frob-verify` replays the levels, the commitments and, after close, the cluster
derivation of a campaign; a reordered index, a changed request and a reused cluster are each rejected), whose one
recorder is BD-383 (it measures the gate and records it from its own receipt, convention 9); this script writes
no gate row.

## Scope

In: one script: building the auditor alone, replaying accepted bundles, generating and checking mutants, the
structured log. Out: the checker (BD-383), the bundle writer (N24b-19), the lane.

## Technical approach

**Path and invocation.** `scripts/e2e/qualification_replay_verify.sh [<bundle-dir>] [--mutants-per-kind N]`.
Plain shell; non-zero exit on a failed assertion; idempotent (writes only under
`target/e2e-logs/qualification_replay_verify/` and a scratch directory). The bundles come from step 0 on a clean
checkout; `<bundle-dir>` may add more, such as bundles written with `frob prove bundle` from a campaign of the
500-retry gate's run (BD-260); the mutant generator is seeded and the seed is printed.

**Steps.**

0. `bundles`: N24b-19's `scripts/e2e/qualify_standing_bundle.sh` runs as a stage (the daemon it starts is
   stopped before step 1) and its pre-close and post-close bundles are copied to the scratch directory with their
   digests logged; the bundles of `<bundle-dir>`, if given, are added.

1. `build_auditor`: build `frob-cert` alone on its own stable toolchain from an empty environment (no
   workspace features); assert the dependency listing shows the standard library only; record the binary's
   hash.
2. `accept_preclose`: `frob-verify <pre-close bundle>`; assert `accept` with the note that derivation and
   arithmetic are not yet replayable; assert the output lists levels and commitments as checked.
3. `accept_postclose`: `frob-verify <post-close bundle>`; assert `accept`; assert the report lists, for each
   request, the level α/[i·(i + 1)], the cumulative spend, the commitment check, the key check, the cluster
   derivation check and the recomputed decision equal to the receipt's.
4. `levels_printed`: for the stage's campaign (α = 1/20) assert, for every index i in the post-close bundle's
   ledger, that the printed level is the reduced exact rational 1/(20·i·(i + 1)) and the cumulative spend
   i/(20·(i + 1)), in the canonical form BD-383's format rule prints (reduced, positive denominator), so the
   comparison is of exact strings and not of decimals: index 1 gives `1/40` and `1/40`; index 7, when the
   campaign reached it, `1/1120` and `7/160` (α/56 and α·7/8). The number of indices checked is logged.
5. `reject_named_mutations`: three mutants made from the post-close bundle: a reordered index (two ledger rows
   swapped), a changed request (n altered, body hash recomputed), a reused cluster (one digest copied between
   requests, Merkle root fixed). Assert `reject` for each, with the failing rule named.
6. `reject_corpus`: N seeded mutants (default 200) for each of the twelve mutation kinds of the checker's
   corpus (the three above plus: constant level, missing index, overspend, key mismatch, draw sequenced before
   commit, flipped decision, flipped outcome, authorization flag true, class presented as `Certified`); assert
   zero accepted.
7. `roundtrip`: `frob-verify <post-close bundle> --reserialize <scratch path>` (the binary's one write path,
   defined by BD-026); assert the written bytes equal the input bundle's and that `frob-verify` on the
   re-serialized copy gives the same verdict and report digest (the metamorphic relation of BD-383).
8. `budget`: assert the replay of the largest campaign (500 requests) finishes within the checker budget
   (TARGET: under 10 s) and log the time; when no 500-request bundle was supplied through `<bundle-dir>`, the
   step times the largest bundle present, logs its request count, and records the 500-request assertion as
   `e2e_skip` with that reason (BD-383's own tests replay m = 500).
9. `second_host` (when a second machine is configured): repeat steps 2 and 3 there; assert identical verdicts
   and report digests.

**Logging.** Per the shared helper of STD-E2E: newline-delimited JSON at
`target/e2e-logs/qualification_replay_verify/<utc-timestamp>.ndjson` with a transcript; every line has `ts`,
`script`, `bead` (`N24b-25`), `step` (the step names above), `event` (`start`, `cmd`, `assert`, `metric`,
`refusal`, `end`), the exact command line, exit code, wall time, the mutant generator's seed, the auditor's verdict and
first failing rule, bundle digests, per mutation kind the counts generated and accepted (threshold 0), and on a
wrongly accepted mutant its kind, seed and file path so it can be reproduced. The evidence block of this
script's assertions: claim Known answer, determinism exact; the trusted base printed by the auditor (the
binary, the standard library and compiler) is copied into the log. The `summary` line gives assertion counts
and the gate touched (GATE-QUAL-03).

## Acceptance criteria

- [ ] The script exists, is executable and passes at M5 on bundles produced by the lane.
- [ ] The auditor is built alone with no dependency outside the standard library, and its hash is logged.
- [ ] Pre-close and post-close bundles are accepted with the checks listed; the three named mutations are rejected with their failing rules.
- [ ] Zero of at least 200 mutants per kind are accepted across twelve kinds.
- [ ] The script writes no gate row; its `summary` line names GATE-QUAL-03 as touched (BD-383 records the gate with `record_gate` from its own known-answer receipt).
- [ ] Steps 1 to 9 need no daemon, no GPU and no network; they pass with networking disabled (step 0's stage runs before and stops its daemon).
- [ ] On a clean checkout with no `<bundle-dir>` the script passes on the bundles of step 0.

## Test plan

### Unit tests
`--list-steps` and its asserting test. `--selftest` feeds the script an unmutated bundle labelled as a mutant
and asserts that the script reports a wrongly accepted mutant, showing its oracle can fail.

### End-to-end script and logging
This bead is the script. Commands from the user's side: N24b-19's script as a stage, the standalone build of
the auditor and `frob-verify <bundle>`. Assertions and log content as above.

### Known answers and negative controls
KA-623 (replay; controls: a reordered index, a changed request and a reused cluster are each rejected), KA-619
(level series, tier including the auditor). Negative controls: the twelve mutation kinds; the self-test.
Determinism: verdicts and report bytes identical twice and on two hosts.

## Considerations

- When `<bundle-dir>` supplies bundles from the 500-retry gate's campaigns on the synthetic family, the level series is exercised up to m = 500 here as well; without them it is exercised to that depth by BD-383's own tests.
- A mutant that happens to be semantically valid (for example swapping two byte-identical rows) would be a false alarm; the generator checks that each mutant differs semantically and regenerates otherwise, logging the count.
- The auditor cannot attest that episodes ran; the script's summary repeats that the replay is of arithmetic and ordering, class at most `Tested`.
