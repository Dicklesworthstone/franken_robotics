## Background

A requirement is a formula somebody wrote, and formulas are written wrongly. FACT (source register): a 2023
language model translated natural-language statements into temporal-logic formulas with 77.7% accuracy over 300
samples, so roughly one draft in four mislabels something. The static checks of the task file (units, clocks,
windows, reach) cannot see that a formula is well-formed and means the wrong thing. The defence is to admit a
requirement only together with **labelled example traces**: recorded or synthetic trajectories that the author
states satisfy or violate the mission, which the monitors must agree with.

Two further failure modes are caught mechanically. A formula can pass its examples because the examples do not
exercise it: an atom that no example distinguishes is **vacuous**. And a comparator can point the wrong way without
any example noticing. The **mutation check** reverses each comparator and deletes each atom in turn; at least one
example must change label under each mutation.

This is the second half of `task.check` (the first half, static admission, is BD-122). It is Solid tier, lives in
`frob-spec` (evaluation) and `frob-arena` (trace storage and the verb), and is what the requirement-writing gate
GATE-ARENA-09 relies on: "`task.check` rejects every draft that mislabels a trajectory".

Alternative rejected: trusting review of the formula text. The 77.7% figure is the measured quality of exactly that.

## Scope

In: the example-trace format and its storage by content hash; the admission rule on examples; running the offline
evaluator on each example; FROB-REF-539 for a missing set or a disagreeing label; the mutation check; the vacuity
report and the refusal for a vacuous hard-limit atom; the report these produce.
Out: the evaluators themselves (BD-121); static checks (BD-122); the coupling test `task.check --coupling` (N24c-37);
the wrench-slice rule on scorecards (N24c-18); foil traces added by a task audit (N24c-22).

## Technical approach

**Example traces.** An example is `(example <TraceRef> satisfied|violated)`. `TraceRef` is the content hash of a
trace: a table with one column per signal the requirement reads, sampled on each signal's own clock, with the
clock table and the horizon. A trace is either cut from a recorded episode (the signal columns of a `.frun`) or
authored directly; an authored trace is labelled `synthetic`. Traces are stored in the task registry of
`frob-arena` by hash; the task file holds only hashes.

**Admission rule (DESIGN).** At least two examples labelled `satisfied` and two labelled `violated`; and for every
comparator in the requirement at least one example **near its boundary**, meaning an example in which that atom's
normalised margin comes within 0.1 of zero at some requirement tick (the margin of an atom with expression e and
scale s is e/s, a pure number). The threshold 0.1 is a DESIGN default of this bead; the plan fixes only that one
example lies near the boundary of each comparator. An `:exact` atom is near its boundary in an example where its
truth value changes at some tick.

**Algorithm of the example stage.**
1. Load every example trace; refuse with FROB-REF-539 if the set is missing or too small (the static half already
   refuses the empty set).
2. For each example run the offline two-pass evaluator on the verdict formula and each online signal. Compare the
   verdict with the label. `undetermined` (a window the trace does not cover) or `invalid` never agrees with a
   label. A disagreement refuses with FROB-REF-539, naming the example, the monitor's verdict, the binding atom
   and the tick at which it was decided.
3. **Mutation check.** For each atom a: build mutant M₁(a) with the comparator reversed (`>` ↔ `<=`, `>=` ↔ `<`,
   `=` ↔ its negation) and mutant M₂(a) with the atom deleted (replaced by true under `and`, by false under `or`,
   in the position where it occurs). Evaluate every example under each mutant. An atom is **distinguished** if
   under each of its two mutants at least one example's verdict differs from its label.
4. **Vacuity.** An atom that is not distinguished is reported `vacuous` with the mutants that survived. A vacuous
   atom that is a **hard limit** refuses (FROB-REF-539, detail `vacuous-hard-limit`); any other vacuous atom is a
   finding (exit code 2). Hard-limit atoms are the atoms of the left operand of the outermost until, or of an
   outermost always, in the verdict (DESIGN: this is the syntactic form in which hard limits are written, as in
   `(U (0 s 8 s) (and tilt-ok current-ok no-strike) dwell)`), plus any atom the task marks as shared with a
   runtime shield.
5. Report: per example the label, the monitor verdict, margin, binding atom and time; per atom the two mutation
   outcomes; the near-boundary coverage per comparator.

Cost: (2·A + 1) evaluations per example for A atoms; an offline evaluation is linear in trace length times formula
size. All arithmetic follows the evaluators' rule that an atom inside the guard band of 2⁻²¹ around zero is
re-evaluated with its declared comparator in exact or double-precision arithmetic.

**Refusal.** FROB-REF-539: "A requirement has no labelled examples, or the monitor disagrees with a label". Exit
code 3, `retry: after-change`. Ranked repairs: correct the formula at the binding atom named; correct the label if
the trace was mislabelled; add an example near the uncovered comparator.

**Outputs.** `frob.task.check.out/1` gains `examples[]`, `mutations[]`, `vacuous[]`. Evidence class `Tested`, tier
`static`, determinism `exact` for the report (the evaluators are bit-identical across backends by construction).

## Acceptance criteria

- [ ] A task whose examples all agree, with every atom distinguished, passes; the cart reference task with its four examples passes.
- [ ] A requirement with one label flipped is refused with FROB-REF-539, naming the example and the binding atom.
- [ ] A requirement with one comparator reversed is refused (some example disagrees) whenever the atom is not vacuous.
- [ ] An atom that no example distinguishes is reported `vacuous`; a vacuous hard-limit atom refuses.
- [ ] A comparator with no near-boundary example is reported, and the admission rule refuses the task.
- [ ] On the 50-statement pilot set of the requirement-writing gate, every draft that mislabels one of its 20 hidden trajectories is rejected once those trajectories are supplied as examples (the `task.check` clause of GATE-ARENA-09).
- [ ] Reachable through `frob task check --json`; cancellation between examples leaves no partial report.

## Test plan

### Unit tests
`cargo test -p frob-spec examples`:
- `examples_agree_cart`: two docking traces and two failing traces (one strike, one timeout) against `docked`; all four agree.
- `flipped_label_refuses_539`: a satisfied trace labelled `violated`.
- `reversed_comparator_detected`: `upright` written `(<= (- 5 deg tilt) 0 deg)`; a satisfied example becomes violated.
- `vacuous_atom_reported`: add `(atom cool (>= (- 383 K temp) 0 K) :scale 20 K)` to the hard limits with examples in which temperature never exceeds 320 K; `cool` is vacuous and, being a hard limit, refuses.
- `deleted_atom_changes_label`: deleting `no-strike` turns the strike example from violated to satisfied.
- `near_boundary_rule`: an example set whose smallest |margin| of `cleared` is 0.4 is refused; adding a trace that clears by 5 mm (margin 0.05) admits it.
- `undetermined_never_agrees`: a trace 6 s long under the 8 s until.
- `hand_case_dwell`: the trace of a body moving at a constant 1 m/s through the goal region x ∈ [4.9, 5.1] m is `satisfied` under `(F (0 s 10 s) in_goal)` and `violated` under `(F (0 s 10 s) (H (0 s 2 s) in_goal))`.
- Property `mutation_check_is_sound`: for random formulas and traces, an atom reported distinguished has, for each mutant, an example whose verdict changes.

### End-to-end script and logging
Steps `examples_ok`, `flipped_label`, `reversed_comparator`, `vacuous_hard_limit` of
`scripts/e2e/arena_task_file.sh` (bead N24c-06): `frob task check <file> --json` on four prepared task files; the
log records per step the command, exit code, the refusal code observed and expected, the example hash, the
monitor verdict against the label, the binding atom and tick, wall time and the `evidence` block.

### Known answers and negative controls
Known answers: KA-594 (normalised margins 0.2 and 0.3, clearance binding in metres and in millimetres) fixes the
margins the near-boundary rule reads; the dwell hand case above (0.2 s inside the region against a 2 s dwell).
Negative controls: a check that counts examples without running them passes the flipped label; a mutation check
that only deletes atoms misses the reversed comparator on an atom guarded by another; a monitor that pads a short
window agrees with the 6 s trace (must be caught). Metamorphic: re-expressing a trace and the task in millimetres
changes no label, margin or binding atom. Determinism: reports byte-identical twice on one machine and across
platforms.

## Considerations

- The check proves agreement on the examples, nothing more. Its strength is the examples' strength, which is why the near-boundary rule and the mutation check exist and why the requirement-writing gate measures drafts on trajectories the author did not see.
- If the paper pilot of the requirement-writing gate (N24c-11) shows that drafts pass their own examples and still fail hidden trajectories at a high rate, the admission rule is tightened (more near-boundary examples per comparator) before M3.
- Example traces may come from private scenes; a trace inherits the private mark and the check report never echoes sample values from a private trace.
- The definition of a hard-limit atom is syntactic; a task that writes hard limits in another form should mark them explicitly, and the report says which atoms were treated as hard limits.
