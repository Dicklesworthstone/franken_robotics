## Background

`eval.run` runs a battery of task scenarios for one candidate and records one verdict per scenario; the plan's
verb table gives it first milestone M2 for its full form. Its M1 referee form is N24c-04: the battery and
single-task forms, the class-only battery form, the outcome columns, the reproducibility contract and the
scorecard, all on the referee tier. At M2 the verb must run the same batteries on the batched tiers
(`batch-cpu`, `gpu-cuda`, `gpu-metal`): the M2 task families (BD-201), GATE-ARENA-01 across tiers (N24a-24),
GATE-KIN-07 on the standard battery (N16b-03) and cross-tier pairing (N16bp2-01) all call `frob eval run --tier
<batched tier>`. Two shared mechanisms of M2 must then govern the verb rather than be re-implemented in it: the
determinism and precision profiles with their admission (N35-04: one parser and one admission step for every
verb that runs worlds) and the evaluation policy for faulted and overflowing worlds (N21b-23: one function that
raises `FROB-REF-608` and `FROB-REF-610` on the device tiers and `FROB-REF-722` on `batch-cpu`).

DESIGN, why a bead of its own: N24c-04 is an M1 bead and cannot depend on the M2 mechanisms (N35-04, N21b-23,
the batched step and the tier caches); folding this work into it would either break the time rule or leave the
M2 tier form of the verb with no owner, which is what the users at M2 above need. Rejected: each M2 caller
running worlds through `sim.run` and evaluating them itself (the battery identity, outcome columns and
scorecard accounting of `eval.run` would be lost or duplicated). Crate `frob-arena` (the handler), with the
batched step of `frob-dyn` and `frob-kernels` reached through `sim.run`'s tier path. Tier: Solid.

## Scope

In: the values `batch-cpu`, `gpu-cuda` and `gpu-metal` of `eval.run`'s `tier`; grouping battery items into
batched runs; the telemetry selection `task-all` on every such run and the host verdicts of N24cx-01; the
settled-pose cache per tier (BD-195); the options `determinism`, `precision` and `on_degraded` through N35-04's
shared parser and admission (no second parser); the option `on_overflow` and the evaluation fault policy
through N21b-23's function; the device refusals 601 and 602 at admission; the conformance-only input
`conformance_plant` on `eval.run` (N29a-25's plant file, as on `sim.run`); the evidence and standing of
batched-tier results; `eval.scorecard` on such runs.
Out: the M1 referee form, battery resolution, the class-only form, outcome columns and scorecard (N24c-04); the
step-plan options `profile`, `law`, `step`, `newton_iterations`, `warm_start` and the cross-tier pair rows
(N16bp2-01); the fidelity options `adjudicate`, `record coverage` (BD-213) and `freeze_envelopes` (N16bp1-01);
the policy form (N23b-09); the profiles, classifier and licences themselves (N35-04, N35-02, N35-07); the fault
states, sentinel and plant kinds (N21b-23, N29a-25); the full metric set (BD-254, M3).

## Technical approach

**Inputs added to the row's M1 form** (spellings as in VERBS-eval's `eval.run` row): `tier` ∈ {`referee`,
`batch-cpu`, `gpu-cuda`, `gpu-metal`}; `determinism` (`reference-replay`, `device-replay`, `cross-backend`;
`fast-training` is selectable only on the training verb); `precision` (`default`, `stiff`, `f32`, `f64`);
`on_degraded` (`refuse`, the default, or `continue-flagged`); `on_overflow` (`refuse`, the default for
evidence-bearing evaluation, `reset` or `continue-flagged`); in a conformance build only, `conformance_plant
<file>` (absent from a release build's schema, where it is FROB-REF-802). Every run call carries `--key`, and
two runs a test compares carry distinct keys.

**Steps** (after N24c-04's step 0, resolution, which is unchanged):
1. *Profile admission.* The handler passes `determinism`, `precision` and `on_degraded` to N35-04's shared
   parser and admission step in `frob-verbs` and keeps no parser of its own: a half-precision spelling is
   FROB-REF-245; `fast-training`, or a profile whose class is not attainable on the placement (for example
   `reference-replay` on a device tier without class D1), is FROB-REF-247 with the applicable profiles listed; a
   precision with no step kernel on the tier is FROB-REF-604 (exit 6, zero worlds stepped). Defaults per tier:
   `reference-replay` on `referee` and `batch-cpu`, `device-replay` on the GPU tiers; `precision default`. The
   resulting `ProfileRecord` (profile, precision, width, degraded policy, class ceiling, `pins_digest`) is written
   into the run record.
2. *Device admission* (GPU tiers): device unavailable or lost is FROB-REF-601; a memory estimate above the device
   budget is FROB-REF-602; both before any world is stepped (N21b-23's device refusals).
3. *Caches.* Each (model, task) needs the settled-pose cache that BD-195 loads on the tier; without it the item is
   FROB-REF-529 with `frob task settle <task> --model <m> --key <k>` as `next_actions[0]`, landing in the
   `refused` column (N24c-04's rule: the run continues).
4. *Batching.* Items are grouped by (task, design, controller); each group is one batched run on the tier through
   `sim.run`'s tier path (N16b-25; BD-159 on `batch-cpu`), its worlds the group's world addresses in address
   order, with the address-keyed streams of M1, so a battery run on `referee` and on a batched tier address the
   same worlds (the precondition of N16bp2-01's pairing). The telemetry selection is always `task-all` (N24cx-01:
   the decision columns of the task for every world), sized before the run: worlds × requirement ticks × columns
   × 4 bytes, refused by the budget (701) when it exceeds it.
5. *Faults and overflow.* The run calls N21b-23's evaluation-policy function with threshold 0 for `Faulted`
   worlds and the caller's `on_overflow`. One `Faulted` world on a GPU tier ends the run at the next chunk
   boundary with FROB-REF-608 (exit 6; `observed` the count, `required` 0, the faulted addresses with stage and
   step; first repair: teleport a faulted world to `batch-cpu`). An overflow under `refuse` is FROB-REF-610 on
   `gpu-cuda` and `gpu-metal` (exit 6) and FROB-REF-722 on `batch-cpu` (exit 5), with the same `pointer` (the
   capacity) and needed count (KNOWN_DRIFTS 6: the two codes are not merged). Under `reset` the world's episode
   is recorded `invalid` and counted; under `continue-flagged` every result derived from it carries the flag.
   An ill-conditioned world under `on_degraded refuse` is FROB-REF-248 (N35-04). A run ended by a refusal
   publishes no scorecard and no partial result.
6. *Verdicts.* The host evaluation of N24cx-01 on the `task-all` columns gives one `frob.verdict/1` per world
   (`evidence.tier` the tier that produced the trace, `evaluated_on: host`), which N24c-04's step 4 assigns to
   exactly one outcome column.
7. *Evidence.* The claim product of the episodes: class `Tested` at best, the tier, the class attained on the
   placement, standing `provisional` on `batch-cpu` and the GPU tiers until promoted; `eval.scorecard` reads such
   runs with N24c-04's handler unchanged, and the tier and standing pass through.

**Refusals this bead raises through the row:** 245, 247, 529 (per tier), 601, 602, 604, 608, 610, 722 (chapter
codes of VERBS-eval's `eval.run` row), 248 (N35-04's degraded refusal, listed on the row), 701 (the kind's
budget code).

## Acceptance criteria

- [ ] `frob eval run <design> --battery smoke --class quadruped --tier batch-cpu --key <k> --json` completes with the same `BatteryId`, `ItemId`s and world addresses as the referee run, columns summing to the battery size, a `ProfileRecord` with `reference-replay` and a `pins_digest`, and standing `provisional`; the same call under a second key gives identical episode digests and verdict records.
- [ ] The profile options are N35-04's: the generated input properties `determinism`, `precision` and `on_degraded` of `eval.run` equal `sim.run`'s byte for byte, `--precision half` is FROB-REF-245 and `--determinism fast-training` FROB-REF-247, each with `sim.run`'s message and repairs.
- [ ] In a conformance build, a `nan` plant in one world of a GPU-tier battery run gives FROB-REF-608, exit 6, the world's address listed and no scorecard published; an `overflow` plant under the default policy gives FROB-REF-610 on each GPU tier present and FROB-REF-722, exit 5, on `batch-cpu`, with the same pointer and needed count; under `--on-overflow reset` the episode is `invalid` and counted.
- [ ] Every world of a batched run has a verdict record evaluated on the host from `task-all` columns; a missing settled-pose cache is FROB-REF-529 in the `refused` column with the settle command offered.
- [ ] `eval.run` is a long tool on these tiers: with a bounded `--sync-wait-ms`, exit 8 with a job handle past it (the CLI default waits to completion); cancellation drains and publishes nothing partial; a tier with no device present is reported skipped with its reason, never passed.

## Test plan

### Unit tests

`cargo test -p frob-arena eval_run_tiers` (the real handler, step and evaluator; plant files are `synthetic`
fixtures under `crates/frob-arena/tests/fixtures/eval_run/`; device cases run where the device exists and are
reported `skipped: no-device` otherwise):
- `same_addresses_across_tiers`: `smoke` for one quadruped on `referee` and `batch-cpu`: equal `ItemId`s and world
  addresses per scenario, and equal verdicts on the analytic smoke items.
- `batch_cpu_reproducible`: two runs under distinct keys, `reference-replay`: identical episode digests.
- `profile_defaults_per_tier`: `batch-cpu` → `reference-replay`, `gpu-cuda` → `device-replay`, `precision
  default`, `on_degraded refuse`, recorded in the `ProfileRecord`.
- `profile_options_shared`: the three properties of the generated `eval.run` schema equal `sim.run`'s; 245 and 247
  as in the acceptance criteria; `--precision f64` on a tier without an f64 step is 604 with zero worlds stepped.
- `evaluation_policy_608_610_722`: as in the acceptance criteria (threshold 0, default `refuse`), plus `reset`
  (one `invalid`, columns still summing to the battery size) and `continue-flagged` (the flagged count printed).
- `degraded_refuse_248`: a world planted ill-conditioned (κ̂·u above 0.1) under `refuse` is 248 with nothing
  published; under `continue-flagged` it is counted as flagged.
- `cache_per_tier_529`: a batched run on a model with no cache gives 529 for each of its items, the run continues.
- `task_all_always`: every batched run's manifest carries `task-all`; a 64-world batch yields 64 verdict records.
- `plant_input_absent_in_release`: a release build's `eval.run` schema has no `conformance_plant` (802).

### End-to-end script and logging

`scripts/e2e/eval_run_tiers.sh` (header `bead=N24cp3-01 milestone=M2 labels=arena,verb:eval.run seed=17
needs=cpu,gpu? plants=nan,overflow`), sourcing the shared helper of STD-E2E: (1) `frob design new erb-quad
--template quad-mammal --key erb-0 --json`; (2) `frob task settle <smoke task> --model erb-quad --key erb-1-<task> --json` for each admitted smoke task
of `assets/tasks/smoke/` (N24b-01; the CLI waits to completion); (3) `frob eval run erb-quad --battery smoke --class
quadruped --tier referee --key erb-2 --json` (the battery form takes no seed: its items carry their world
addresses); (4) the same with `--tier batch-cpu --key erb-3` and again with
`--key erb-4`: identical digests, the referee run's addresses, standing `provisional`; (5) `--precision half
--key erb-5` and `--determinism fast-training --key erb-6`: `e2e_expect_refusal FROB-REF-245 3` and
`FROB-REF-247 3`; (6) on a conformance build, `--conformance-plant fixtures/arena/eval-run-overflow.plant.toml
--tier batch-cpu --key erb-7`: `e2e_expect_refusal FROB-REF-722 5`; (7) for each GPU tier present, the `nan` and
`overflow` plants (`erb-8-<tier>`, `erb-9-<tier>`): FROB-REF-608 and FROB-REF-610, exit 6, and no scorecard;
(8) `frob eval scorecard <run of step 4> --json`: tier `batch-cpu`, standing `provisional`, columns summing to
the battery size. Log `target/e2e-logs/eval_run_tiers/<utc>.ndjson` with a transcript: per line `ts`, `script`,
`bead`, `step`, `event`, the exact command, exit code, wall time, the envelope's `evidence` block (claim, class,
tier, determinism, identities, seed) and the `ProfileRecord`; metrics with units (worlds, column counts against
the battery size, `task-all` bytes against the budget); digests of every episode compared; refusals with code,
exit and first repair; device steps skipped with their reason; on failure the first differing world address,
both digests and the `.frun` paths; a final `summary` with assertions passed and failed.

### Known answers and negative controls

Known answers: the forced overflow gives 610 on each device and 722 on `batch-cpu` with the same needed count
(KA-349's device rows, met by 610); a 64-world batch yields 64 verdicts. Negative controls: a handler with its
own option parser whose default differs (`profile_options_shared` fails on the schema difference); one code for
both overflows (`evaluation_policy_608_610_722` fails); a run that publishes a scorecard after 608 (caught by the
same test); a batch that draws its world addresses from a batch index instead of the address (caught by
`same_addresses_across_tiers`). Determinism lanes: twice on one machine and across worker counts on `batch-cpu`
(class D2 under `reference-replay`); device tiers inside their attained class.

## Considerations

- Memory: `task-all` costs worlds × requirement ticks × columns × 4 bytes (262 MB for 4,096 worlds, 20 s at
  100 Hz and 8 columns, N24cx-01); it is sized before the run and refused by budget, never truncated.
- A GPU absent from the machine leaves the device rows `skipped` with the reason; KILL-METAL's fallback removes
  `gpu-metal` from the tier list without changing this bead's other rows.
- Determinism: a batched result is a statement inside its tier's class; comparing tiers is N16bp2-01's paired
  comparator, never a digest equality across tiers.
