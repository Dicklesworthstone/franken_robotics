## Background

FrankenRobotics is a robotics simulation and design studio whose central promise is that every number it prints
says what kind of claim it is and how strongly it is supported. That promise has to hold for the project's own
status as well. The first commit therefore ships the documents and registries from which every later status
statement is generated, before any crate exists. A sibling project of the suite shipped its companion documents
with its plan and recorded that as worth repeating (FACT, FrankenTextiles); another sibling found admission
records for crates that were never in its build (FACT, FrankenMining), which is why admission records here must
cite a commit and a lockfile.

The piece that carries the weight is the **honest-status table** in `README.md`. It is generated from
`registries/gates.toml` and from nothing else (invariant INV-GAUNT-06: status tables are generated from the gate
registry and never edited). A gate is a named, numbered pass criterion; the plan defines 421 of them (FACT at
plan time). The failure this bead exists to prevent is a table in which a gate reads as passed because somebody
typed "pass", or because a threshold (a TARGET) was copied into the measured column. DESIGN: a gate whose record
has no measured value prints as `open`, never as passed, whatever its `status` field says.

Rejected alternatives. (1) A hand-maintained status section: it drifts, and the drift is always optimistic.
(2) Generating status from test results at build time: a test that passes is not a gate that was measured with a
caught negative control by a session other than the implementer. (3) Populating `gates.toml` with all 421 rows
at the first commit marked `pass: false`: rows arrive with the beads that own them, so that a row never exists
without an owner; the registry starts schema-valid and empty.

This is workspace infrastructure (tier Solid), layer zero of the delivery: it serves every milestone exit, which
is defined as a query over `gates.toml`.

## Scope

In: the content rules of `AGENTS.md`; `README.md` with the generated table and its generator;
`DEPENDENCY_ADMISSION.md` as it is shipped at the first commit (its header, which states the two rules and the
fields a record shows, and no record); the registry files with their schemas (all empty except `formats.toml`,
which carries thirteen rows); the schemas of `demos/<demo_id>/demo.yaml` and of each crate's `contract.toml`.
Out: `Cargo.toml`, the toolchain file, `franken-stack.lock` and the first resolution receipt (BD-001); the six
`xtask` checks themselves (BD-003, BD-004); the base gate record's types, field meanings and the contract of the
four conditions that refuse `pass` (N38b-18, which owns the schema `frob.gates/1` this bead first ships); the
register layer's fields and the validator that checks every cross-field rule (N40-01); the recorder that writes a
row from a receipt and refuses a self-certified pass (N38b-19); the negative-control registry (BD-025); round-trip tests of the thirteen formats (BD-141, BD-410); the initial beads. Also out: the register
of generated views, the further columns and content rules of the status table (the controls column, the footer of
totals), the gate section of the release rubric and the dashboard feed, which are N38b-20's. That bead depends on
this one and extends the generator shipped here; it keeps this block's markers, its ordering by gate identifier
and its printing rule, and ships no second generator for the README block. Also out, and all in
N33a-07, which depends on this bead: the machine form of an admission record (schema `frob.admission/1`, one
canonical JSON file per record), its writer and validator, the generator that renders `DEPENDENCY_ADMISSION.md`
from the record files once the first gate has run, and the check that an admission is never inherited.

## Technical approach

1. **`AGENTS.md`** states the working rules every implementing agent follows (FACT: adopted from the machine-level
   instructions and from `frankensim/AGENTS.md`): cargo runs through the build-offload shim and is never invoked
   by absolute path; projects stay under `~/projects`; isolated target directories use
   `${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/<name>`; a disk preflight precedes heavy lanes; no run uses more than
   16 GiB of memory, 8 cores or one hour of wall time without the owner's written approval given before it starts,
   and a run longer than a few minutes starts under a timeout; no file is deleted without explicit permission; no
   branches and no worktrees (work lands on `main`; file reservations through Agent Mail replace branches); `ubs`
   runs on changed files, and formatting, lints and tests run, before a commit; beads are managed with `br` and
   triaged with `bv --robot-*`; source that was never compiled does not land, and the commit message carries the
   commands and their results; code is changed by focused patches, never by scripts or broad regular-expression
   rewrites; before a build failure is blamed on this repository `xtask check-stack` runs, and a sibling checkout
   is never moved back to its pin to make a check pass; process is never the product (before non-product work an
   agent answers: which capability, defect or blocker does this address, is it the smallest direct action, is it
   worth its cost now).
2. **`registries/`** (TOML, each with a JSON-Schema file under `schemas/registries/`): `verbs.toml`,
   `refusals.toml`, `kernels.toml`, `gates.toml`, `formats.toml`, `upstream.toml`, `lifts.toml`, `capsules.toml`,
   and the directory `cards/`. Every file parses and validates; every file except `formats.toml` has zero rows.
3. **`registries/gates.toml` record** (the base record of N38b-18, schema `frob.gates/1`; this bead ships its
   first-commit JSON-Schema with exactly these fields, and N38b-18 and N40-01 extend that one file additively,
   never reshape it):
   ```toml
   [[gate]]
   id = "GATE-ARENA-05"; claim = "known-answer"   # proof | known-answer | parity | fidelity |
                                                  # design-comparison | reality | performance
   claim_id = "clm:…"; section = "24.17"; threshold = "…"; milestone = "M1"; tier = ["G1:host"]
   controls = ["NC-0398"]          # registered negative controls
   [[gate.part]]                   # one per milestone at which a part of the gate is due; most gates have one
   milestone = "M1"
   status = "not-run"              # not-run | pass | fail | killed | blocked | no-claim | superseded
   measured = ""                   # the value with its unit and interval, or the count
   evidence = []                   # ledger sequence numbers and trace identifiers
   recorded = { date = "", session = "", implemented_by = "" }   # implemented_by: sorted, comma-joined sessions
   ```
   Status is recorded per part (DESIGN of N38b-18: a gate due at two milestones has a part at each, which one
   status per gate cannot record without a premature or a late pass); a gate's own status is derived and never
   stored: `not-run` when no part is recorded, otherwise the status of its latest due part. Schema rules checked
   from the first commit (N40-01's validator later checks every cross-field rule): `claim` is one of the seven
   kinds; a part's `pass` is invalid when the gate's `controls` is empty, when `measured` is empty, or when
   `recorded.session` is one of the sessions in `recorded.implemented_by` (a co-implementer is refused as much as
   the sole implementer, N38b-18 rule 3(c)); `killed` names the kill gate that fired and
   the fallback in force; `blocked` names the open question that blocks the gate; `no-claim` is a terminal status
   for Reality gates. These tokens are the file's spelling of the gate register's status words: `not run` is
   `not-run`; `killed: fallback adopted` is `killed` with its kill gate and fallback recorded; `blocked: ⟨open
   question⟩` is `blocked` with the question's identifier. A bead that tests "the gate's status is `killed:
   fallback adopted`" tests the token `killed` and the presence of the recorded fallback.
4. **`registries/formats.toml`**: thirteen rows, each with identifier, extension, schema name, owner crate,
   producers, consumers, and canonical-or-view. Identifier → extension → schema → owner: FMT-FBOT `.fbot`
   `frob.design/1` `frob-design`; FMT-FMODULE `.fmodule` `frob.module/1` `frob-design`; FMT-FCARD `.fcard`
   `frob.card/1` `frob-actuate` (kinds: actuator, transmission, battery, interface, material, soil, optical,
   sensor, payload); FMT-FSCENE `.fscene` `frob.scene/1` `frob-scene`; FMT-FCLEAR `.fclear` `frob.clearance/1`
   `frob-scene`; FMT-FTASK `.ftask` `frob.task/1` `frob-spec`; FMT-FMISSION `.fmission` `frob.mission/1`
   `frob-spec`; FMT-FENERGY `.fenergy` `frob.energy/1` `frob-shield`; FMT-FSKILL `.fskill` `frob.skill/1`
   `frob-control`; FMT-FMCW `.fmcw` `frob.mcw/1` `frob-nemesis`; FMT-FRUN `.frun` `frob.run/1` `frob-chronicle`;
   FMT-FBUILD `.fbuild` `frob.build/1` `frob-foundry`; FMT-FROBCERT `.frobcert` `frob.cert/1` `frob-cert` (schema
   and reader; the writer is `frob-lemma`). Registry rules recorded in the file's header: one owner per format;
   identity is the BLAKE3 hash of canonical bytes under a domain string equal to the schema name; a reader refuses
   an unknown major version and an unknown required field; integers above 2⁵³ travel as strings; large payloads
   are blobs addressed by hash; an exported artifact carries the three no-authorization flags.
5. **The generator.** A function `status_table(gates: &GateRegistry) -> String` (DESIGN: a module of `xtask`;
   `gates.toml` is read with `frob-core`'s strict TOML-subset reader, N34p2-01; no seventh subcommand is added).
   BD-004 wires it into `check-generated`, whose `--write` mode then rewrites the block. Until that check exists,
   the block is written and checked by the test `readme_block_is_current` below, which compares the committed
   block with the generator's output and, run with `FROB_BLESS=1`, rewrites the bytes between the markers and
   nothing else; the first commit's block is written that way, never by hand.
   The README holds the block between `<!-- status:begin -->` and `<!-- status:end -->`. One row per gate, printed
   from its derived status and the part that gives it (a gate with no part prints `open`). Columns: gate, claim,
   milestone, status, measured, recorded. Printing rule, in order: `measured` empty ⇒ `open` (also when `status`
   says `pass`, in which case generation fails with a schema error naming the row); `pass` with a valid record ⇒
   `pass` with the measured value; `fail`, `killed` (with the kill gate and fallback), `blocked` (with the open
   question), `no-claim`, `superseded` as written. A summary line counts rows by printed status. Output is byte-deterministic: rows sorted by `id`,
   fixed column widths, `\n` endings.
6. **`DEPENDENCY_ADMISSION.md` (first-commit form).** The first commit carries the document's header and no
   records. The header states, in this order: what the file is (a foundation, a sibling library consumed here, is
   not used above the airlock crate until its admission gate has a record in this file); the validity rule (a
   record is valid only if it cites a commit of this repository whose tracked `Cargo.lock` contains the
   foundation, with the command, its output and the receipt hash); that there is one record per admission gate
   run, passing or failing; the fields a record shows (gate identifier, the commit of this repository whose
   tracked `Cargo.lock` contains the foundation, the command, its output, the receipt hash, measured values
   against TARGET thresholds, date); and the rule that an admission is never inherited: a crate first used at a
   later milestone gets its own record then, at the pin of that day. DESIGN, so that the document has one
   definition: this bead writes the header and nothing else. The machine form of a record, the writer, the
   validator and the generator belong to N33a-07; from the day that bead lands, the file is rendered from the
   record files by its generator, which prints this header unchanged as its preamble, and the file comes under
   the generated-files check. Until then the file is this header, and a record is never typed into it by hand.
7. **Schemas.** `schemas/demo.schema.json` for `demo.yaml`. Required keys: `demo_id`, `claim_ids` (each must
   exist in `gates.toml`), `commands` (a list of command lines, each finishing in under 60 s on the CPU tier,
   TARGET), `checksums` (a map from a command line to `b3:` followed by the BLAKE3 hash in hexadecimal of that
   command's canonical `result`). Optional keys, admitted because one executor (N00-29) reads the scenarios' and
   the release demos' files alike and the static check of N34-09 refuses an unknown key: `tier` (`cpu` or a
   device tier); the four per-command expectations `expect_exit` (integer exit code), `expect_refusal` (a refusal
   code), `compare` (a list of `result` fields compared exactly instead of a checksum) and `expect` (a path to a
   JSON subset the envelope must contain), each a map keyed by the command line exactly as `checksums` is; and
   `title` (string), `milestone` (`M0`…`M8`), `actors` (list of strings), `lane` (`cpu` | `device` | `long`),
   `fresh_agent` (boolean) and `not_evidence_for` (the constant `numbers`). Any other key is refused
   (`additionalProperties: false`). DESIGN: the schema admits these keys and checks their types; what they mean
   at run time is the executor's (N00-29) and the demo runner's (N34-12).
   `schemas/contract.schema.json` for `contract.toml`: crate layer and rank, determinism class (D0 to D4),
   evidence class of outputs, budgets, feature flags with their tiers, safe mode (what the crate does when a
   budget is exhausted or a calibration check fails: fall back to its reference path, or refuse by name). A
   crate's `CONTRACT.md` has ten sections: purpose, inputs, outputs, invariants, refusals, determinism class,
   evidence class of outputs, validity domain, oracles, known gaps.

## Acceptance criteria

- [ ] `AGENTS.md`, `README.md`, `DEPENDENCY_ADMISSION.md`, the nine registry entries and the two schemas exist
      at the repository root paths named above.
- [ ] `DEPENDENCY_ADMISSION.md` at the first commit holds the header (the validity rule, one record per gate run
      passing or failing, the seven fields of a record, the never-inherited rule) and zero records.
- [ ] Every registry file validates against its schema; eight are empty; `formats.toml` has exactly thirteen rows
      with thirteen distinct identifiers, extensions and schema names.
- [ ] The status table regenerates from `registries/gates.toml` byte for byte (seed done-condition).
- [ ] A gate with no measured value prints as `open`, never as passed (seed done-condition); a row with
      `status = "pass"` and `measured = ""` makes generation fail and names the row.
- [ ] A `pass` part of a gate with empty `controls`, or whose `recorded.session` is one of the sessions in
      `recorded.implemented_by`, fails schema validation.
- [ ] Editing the README block by hand makes `readme_block_is_current` fail, naming the first differing line. The
      same edit failing `check-generated` (first clause of GATE-GAUNT-10) is asserted by BD-004, which wires this
      generator into that check and depends on this bead.
- [ ] A `demo.yaml` naming a `claim_id` absent from `gates.toml` fails validation.
- [ ] The demo schema admits a file using every optional key (`tier`, `expect_exit`, `expect_refusal`,
      `compare`, `expect`, `title`, `milestone`, `actors`, `lane`, `fresh_agent`, `not_evidence_for`) and refuses
      a file with an unknown key or a missing required key (the cross-key check that a map names only lines of
      `commands` is N34-09's `demo.orphan-checksum`).

## Test plan

### Unit tests

Beside the generator (`cargo test -p xtask status_table`):
- `empty_registry_prints_header_and_zero_counts`: empty `gates.toml` ⇒ header, no rows, summary "0 gates".
- `not_run_prints_open`: a `not-run` row ⇒ status cell `open`.
- `pass_without_measured_is_error`: `status = "pass"`, `measured = ""` ⇒ error naming the gate id.
- `pass_with_measured_prints_value`: `measured = "561 of 561 cells"` ⇒ cell contains that text.
- `killed_prints_kill_gate_and_fallback`; `no_claim_is_terminal`.
- `generation_is_deterministic`: two permutations of the same rows give identical bytes.
- `readme_block_is_current`: the bytes between `<!-- status:begin -->` and `<!-- status:end -->` in the committed
  `README.md` equal `status_table` over the committed `registries/gates.toml`; on a difference it fails naming
  the first differing line; with `FROB_BLESS=1` it rewrites only those bytes (a hash of the rest of the file is
  unchanged, asserted).
- `formats_registry_has_thirteen_unique_rows`; `every_registry_validates`.
- `self_certified_pass_fails_schema`: a `pass` part with `session = "session:b"` and `implemented_by =
  "session:a,session:b"` fails (a co-implementer), as does `implemented_by = "session:b"`; `session:c` validates.
  `pass_with_no_controls_fails_schema`.
- `one_row_per_gate_from_parts`: a gate with no part prints `open`; a gate whose one part (M1) is a valid `pass`
  prints `pass` with its measured value; a fixture of three gates holding five parts prints three rows.
- `demo_schema_admits_every_optional_key`: the `ns-01` style file (required keys plus all eleven optional keys)
  validates; `demo_schema_refuses_unknown_key`: the same file with `colour: red` added fails naming `colour`;
  `demo_schema_requires_checksums`: the file without `checksums` fails; `demo_lane_enum`: `lane: gpu` fails.

### End-to-end script and logging

`scripts/e2e/status_table.sh`: copies the repository to a scratch directory and replaces `registries/gates.toml`
with a `synthetic` fixture (five rows: not-run; valid pass; pass with empty `measured`; killed; no-claim), runs
`FROB_BLESS=1 cargo test -p xtask readme_block_is_current` there and asserts the generation error naming the
pass row with empty `measured`; removes that row, blesses again and asserts the printed statuses (`open`, `pass`,
`killed`, `no-claim`); runs the test without `FROB_BLESS` (exit 0); then edits the block by hand and asserts a
non-zero exit with the first differing line. BD-004 adds to the same script the steps through
`cargo xtask check-generated --write` and `cargo xtask check-generated` once that check exists; before then they
are logged `not due`. Logs newline-delimited JSON through the shared helper
of STD-E2E to `target/e2e-logs/status_table/<utc>.ndjson`: one `cmd` line per command with exit code and wall
time, one `assert` line per expectation with the first differing line on failure, the digest of the generated
block, and a `summary` line naming GATE-GAUNT-10.

### Known answers and negative controls

Known answer: the five-row fixture prints exactly open, pass, (error), killed, no-claim. Negative controls: the
hand-edited table; the pass with no measured value; the self-certified pass; a fourteenth format row with a
duplicate extension. Determinism: generated bytes identical twice on one machine and across platforms (class D0).

## Considerations

- The generator must not read anything but `gates.toml`: reading test output or logs would let a green test
  print as a passed gate.
- `xtask` has exactly six subcommands and a test asserts it; the generator is a mode of `check-generated`.
- RISK-54 (the plan and the registries drift apart): the register of gates in the plan is a printout of
  `gates.toml`; where a chapter and the register differ, the register governs.
- The crate caps, the `claim_id` text form and the artifact-graph resolution of `evidence` are enforced by later
  beads; here `evidence` is validated only syntactically.
