## Background

FrankenRobotics is a robotics simulation and design studio whose central promise is that every number it prints
says what kind of claim it is and how strongly it is supported. That promise has to hold for the project's own
status as well. The first commit therefore ships the documents and registries from which every later status
statement is generated, before any crate exists. A sibling project of the suite shipped its companion documents
with its plan and recorded that as worth repeating (FACT, FrankenTextiles); another sibling found admission
records for crates that were never in its build (FACT, FrankenMining), which is why admission records here must
cite a commit and a lockfile.

The piece that carries the weight is the **honest-status table** in `README.md`. It is generated from
`registries/gates.toml` and from nothing else (invariant INV-GAUNT-06: status tables are generated from the gate
registry and never edited). A gate is a named, numbered pass criterion; the plan defines 421 of them (FACT at
plan time). The failure this bead exists to prevent is a table in which a gate reads as passed because somebody
typed "pass", or because a threshold (a TARGET) was copied into the measured column. DESIGN: a gate whose record
has no measured value prints as `open`, never as passed, whatever its `status` field says.

Rejected alternatives. (1) A hand-maintained status section: it drifts, and the drift is always optimistic.
(2) Generating status from test results at build time: a test that passes is not a gate that was measured with a
caught negative control by a session other than the implementer. (3) Populating `gates.toml` with all 421 rows
at the first commit marked `pass: false`: rows arrive with the beads that own them, so that a row never exists
without an owner; the registry starts schema-valid and empty.

This is workspace infrastructure (tier Solid), layer zero of the delivery: it serves every milestone exit, which
is defined as a query over `gates.toml`.

## Scope

In: the content rules of `AGENTS.md`; `README.md` with the generated table and its generator; the format of
`DEPENDENCY_ADMISSION.md`; the registry files with their schemas (all empty except `formats.toml`, which carries
thirteen rows); the schemas of `demos/<demo_id>/demo.yaml` and of each crate's `contract.toml`.
Out: `Cargo.toml`, the toolchain file, `franken-stack.lock` and the first resolution receipt (BD-001); the six
`xtask` checks themselves (BD-003, BD-004); the runner that records gate results and refuses a self-certified
pass (BD-025); round-trip tests of the thirteen formats (BD-141, BD-410); the initial beads.

## Technical approach

1. **`AGENTS.md`** states the working rules every implementing agent follows (FACT: adopted from the machine-level
   instructions and from `frankensim/AGENTS.md`): cargo runs through the build-offload shim and is never invoked
   by absolute path; projects stay under `~/projects`; isolated target directories use
   `${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/<name>`; a disk preflight precedes heavy lanes; no run uses more than
   16 GiB of memory, 8 cores or one hour of wall time without the owner's written approval given before it starts,
   and a run longer than a few minutes starts under a timeout; no file is deleted without explicit permission; no
   branches and no worktrees (work lands on `main`; file reservations through Agent Mail replace branches); `ubs`
   runs on changed files, and formatting, lints and tests run, before a commit; beads are managed with `br` and
   triaged with `bv --robot-*`; source that was never compiled does not land, and the commit message carries the
   commands and their results; code is changed by focused patches, never by scripts or broad regular-expression
   rewrites; before a build failure is blamed on this repository `xtask check-stack` runs, and a sibling checkout
   is never moved back to its pin to make a check pass; process is never the product (before non-product work an
   agent answers: which capability, defect or blocker does this address, is it the smallest direct action, is it
   worth its cost now).
2. **`registries/`** (TOML, each with a JSON-Schema file under `schemas/registries/`): `verbs.toml`,
   `refusals.toml`, `kernels.toml`, `gates.toml`, `formats.toml`, `upstream.toml`, `lifts.toml`, `capsules.toml`,
   and the directory `cards/`. Every file parses and validates; every file except `formats.toml` has zero rows.
3. **`registries/gates.toml` record** (DESIGN):
   ```toml
   [[gate]]
   id = "GATE-ARENA-05"; claim = "known-answer"   # proof | known-answer | parity | fidelity |
                                                  # design-comparison | reality | performance
   claim_id = "clm:…"; section = "24.17"; threshold = "…"; milestone = "M1"; tier = ["G1:host"]
   controls = ["NC-0398"]          # registered negative controls
   status = "not-run"              # not-run | pass | fail | killed | no-claim | superseded
   measured = ""                   # the value with its unit and interval, or the count
   evidence = []                   # ledger sequence numbers and trace identifiers
   recorded = { date = "", session = "", implemented_by = "" }
   ```
   Schema rules: `claim` is one of the seven kinds; `pass` is invalid when `controls` is empty, when `measured` is
   empty, or when `recorded.session` equals `recorded.implemented_by`; `killed` names the kill gate that fired and
   the fallback in force; `no-claim` is a terminal status for Reality gates.
4. **`registries/formats.toml`**: thirteen rows, each with identifier, extension, schema name, owner crate,
   producers, consumers, and canonical-or-view. Identifier → extension → schema → owner: FMT-FBOT `.fbot`
   `frob.design/1` `frob-design`; FMT-FMODULE `.fmodule` `frob.module/1` `frob-design`; FMT-FCARD `.fcard`
   `frob.card/1` `frob-actuate` (kinds: actuator, transmission, battery, interface, material, soil, optical,
   sensor, payload); FMT-FSCENE `.fscene` `frob.scene/1` `frob-scene`; FMT-FCLEAR `.fclear` `frob.clearance/1`
   `frob-scene`; FMT-FTASK `.ftask` `frob.task/1` `frob-spec`; FMT-FMISSION `.fmission` `frob.mission/1`
   `frob-spec`; FMT-FENERGY `.fenergy` `frob.energy/1` `frob-shield`; FMT-FSKILL `.fskill` `frob.skill/1`
   `frob-control`; FMT-FMCW `.fmcw` `frob.mcw/1` `frob-nemesis`; FMT-FRUN `.frun` `frob.run/1` `frob-chronicle`;
   FMT-FBUILD `.fbuild` `frob.build/1` `frob-foundry`; FMT-FROBCERT `.frobcert` `frob.cert/1` `frob-cert` (schema
   and reader; the writer is `frob-lemma`). Registry rules recorded in the file's header: one owner per format;
   identity is the BLAKE3 hash of canonical bytes under a domain string equal to the schema name; a reader refuses
   an unknown major version and an unknown required field; integers above 2⁵³ travel as strings; large payloads
   are blobs addressed by hash; an exported artifact carries the three no-authorization flags.
5. **The generator.** A function `status_table(gates: &GateRegistry) -> String` (DESIGN: a module of `xtask`,
   called by `check-generated`; `check-generated --write` rewrites the block; no seventh subcommand is added).
   The README holds the block between `<!-- status:begin -->` and `<!-- status:end -->`. Columns: gate, claim,
   milestone, status, measured, recorded. Printing rule, in order: `measured` empty ⇒ `open` (also when `status`
   says `pass`, in which case generation fails with a schema error naming the row); `pass` with a valid record ⇒
   `pass` with the measured value; `fail`, `killed` (with the kill gate and fallback), `no-claim`, `superseded`
   as written. A summary line counts rows by printed status. Output is byte-deterministic: rows sorted by `id`,
   fixed column widths, `\n` endings.
6. **`DEPENDENCY_ADMISSION.md`.** One record per admission gate run, passing or failing: gate identifier, the
   commit of this repository whose tracked `Cargo.lock` contains the foundation, the command, its output, the
   receipt hash, measured values against TARGET thresholds, date. The first commit carries the format and no
   records. An admission is never inherited: a crate first used at a later milestone gets its own record then.
7. **Schemas.** `schemas/demo.schema.json` for `demo.yaml`: `demo_id`, `claim_ids` (each must exist in
   `gates.toml`), `commands` (each finishing in under 60 s on the CPU tier, TARGET), `checksums` of outputs.
   `schemas/contract.schema.json` for `contract.toml`: crate layer and rank, determinism class (D0 to D4),
   evidence class of outputs, budgets, feature flags with their tiers, safe mode (what the crate does when a
   budget is exhausted or a calibration check fails: fall back to its reference path, or refuse by name). A
   crate's `CONTRACT.md` has ten sections: purpose, inputs, outputs, invariants, refusals, determinism class,
   evidence class of outputs, validity domain, oracles, known gaps.

## Acceptance criteria

- [ ] `AGENTS.md`, `README.md`, `DEPENDENCY_ADMISSION.md`, the nine registry entries and the two schemas exist
      at the repository root paths named above.
- [ ] Every registry file validates against its schema; eight are empty; `formats.toml` has exactly thirteen rows
      with thirteen distinct identifiers, extensions and schema names.
- [ ] The status table regenerates from `registries/gates.toml` byte for byte (seed done-condition).
- [ ] A gate with no measured value prints as `open`, never as passed (seed done-condition); a row with
      `status = "pass"` and `measured = ""` makes generation fail and names the row.
- [ ] A `pass` row with empty `controls`, or with `session` equal to `implemented_by`, fails schema validation.
- [ ] Editing the README block by hand makes `check-generated` exit non-zero (first clause of GATE-GAUNT-10).
- [ ] A `demo.yaml` naming a `claim_id` absent from `gates.toml` fails validation.

## Test plan

### Unit tests

Beside the generator (`cargo test -p xtask status_table`):
- `empty_registry_prints_header_and_zero_counts`: empty `gates.toml` ⇒ header, no rows, summary "0 gates".
- `not_run_prints_open`: a `not-run` row ⇒ status cell `open`.
- `pass_without_measured_is_error`: `status = "pass"`, `measured = ""` ⇒ error naming the gate id.
- `pass_with_measured_prints_value`: `measured = "561 of 561 cells"` ⇒ cell contains that text.
- `killed_prints_kill_gate_and_fallback`; `no_claim_is_terminal`.
- `generation_is_deterministic`: two permutations of the same rows give identical bytes.
- `formats_registry_has_thirteen_unique_rows`; `every_registry_validates`.
- `self_certified_pass_fails_schema`; `pass_with_no_controls_fails_schema`.

### End-to-end script and logging

`scripts/e2e/status_table.sh`: copies a `synthetic` fixture `gates.toml` (five rows: not-run; valid pass; pass
with empty `measured`; killed; no-claim) into a scratch workspace, runs `cargo xtask check-generated --write`
and `cargo xtask check-generated`, asserts the printed statuses (`open`, `pass`, error, `killed`, `no-claim`),
then edits the block by hand and asserts a non-zero exit. Logs newline-delimited JSON through the shared helper
of STD-E2E to `target/e2e-logs/status_table/<utc>.ndjson`: one `cmd` line per command with exit code and wall
time, one `assert` line per expectation with the first differing line on failure, the digest of the generated
block, and a `summary` line naming GATE-GAUNT-10.

### Known answers and negative controls

Known answer: the five-row fixture prints exactly open, pass, (error), killed, no-claim. Negative controls: the
hand-edited table; the pass with no measured value; the self-certified pass; a fourteenth format row with a
duplicate extension. Determinism: generated bytes identical twice on one machine and across platforms (class D0).

## Considerations

- The generator must not read anything but `gates.toml`: reading test output or logs would let a green test
  print as a passed gate.
- `xtask` has exactly six subcommands and a test asserts it; the generator is a mode of `check-generated`.
- RISK-54 (the plan and the registries drift apart): the register of gates in the plan is a printout of
  `gates.toml`; where a chapter and the register differ, the register governs.
- The crate caps, the `claim_id` text form and the artifact-graph resolution of `evidence` are enforced by later
  beads; here `evidence` is validated only syntactically.
