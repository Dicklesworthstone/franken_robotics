## Background

In a mission query every execution must progress to the horizon or to a declared terminal outcome before its
acceptance predicate means anything. Simulators and solvers fail in many ways that are not statements about the
robot: a step does not converge, an event is not located, a budget runs out. If any of those is recorded as
"the design fails", the outer set O shrinks without a proof and the answer becomes unsound. The opposite error
is as bad: an execution that stops early, or accumulates infinitely many events in finite time, must not be
counted as a success because nothing bad happened before it stopped.

**ADR-AUGUR-07: unknown is a verdict.** A cell is inner, excluded or unresolved. Solver failure, timeout, an
enclosure that straddles a threshold and a mode sequence that cannot be enclosed all yield unresolved. Nothing
converts unresolved into either of the other two. Reason: a three-valued answer is the only one that stays true
when the tools are imperfect. Rejected: a two-valued answer with "fail" as the default (turns tool failures
into impossibility claims); a confidence score per cell (cannot be audited and invites thresholds).

The second subject of this bead is comparators. Strict, non-strict and equality atoms are distinct, and the
boundary of a feasible family often sits exactly on a comparator: in the docking family (three unit ticks,
hidden gain g ∈ {1, 2}, one velocity reading with error radius ε, actuator bound U) a robust causal policy
exists exactly when ε < (U + 1/2)/4, equality excluded. A kernel that evaluates `<` as `≤` admits the equality
case, which is false.

## Scope

In: the outcome type and its classification into contributions to a verdict; the comparator semantics on exact
values, on enclosures and on sets with open or closed ends; the rule for several objectives; the type-level
ban on exclusions built from failures.
Out: locating events or completing Zeno executions (the dynamics owners); the search that decides what to try
next on an unresolved cell (the worklist beads); budget stops at the verb level (BD-135).

## Technical approach

1. **Outcomes.** DESIGN:
   ```rust
   pub enum ExecutionOutcome {
       Completed { terminal: TerminalState },
       ModelDeadlock { argument: ProofRef },        // shown from the declared hybrid model, exact or enclosed
       ModelZeno { accumulation: Ratio, argument: ProofRef, completion: Option<CompletionRef> },
       UndefinedDynamics { at: StateRef },          // T(d, π, w) is empty
       NumericalFailure { kind: NumericalKind },    // NonConvergence | StepSizeCollapse | RetryBudgetExhausted
   }                                                // | NaN | EventNotLocated | Timeout
   pub enum Contribution { Accepts, Rejects { why: RejectReason }, Unknown(Explanation) }
   ```
2. **The six rules**, as `fn classify(o: &ExecutionOutcome, a: &Predicate) -> Contribution`:
   1. *Deadlock, undefined dynamics and Zeno behaviour without an admitted completion cannot earn success.*
      `ModelDeadlock`, `UndefinedDynamics`, and `ModelZeno` with `completion: None` give `Rejects`.
   2. *A model-level failure of progress is a failing execution.* When deadlock or a Zeno accumulation is a
      property of the declared hybrid model, shown by an exact or enclosed argument, it blocks inclusion; when
      it is shown for every admitted policy it supports exclusion (through an exclusion proof kind, never
      directly).
   3. *An admitted completion restores evaluation.* If the mission model declares what follows an accumulation
      point (a bouncing contact that comes to rest and enters a declared resting mode), the predicate is
      evaluated on the completed execution.
   4. *A numerical failure is unknown.* Every `NumericalFailure` gives `Unknown(SolverFailure)` or
      `Unknown(BudgetExhausted)`, and the cell stays unresolved, unless independent evidence (a checked
      exclusion certificate for the cell, or a checked witness) establishes the verdict under the mission model.
      A solver error is never an exclusion.
   5. *Comparators are evaluated as declared* (step 3).
   6. *Scalarization is the caller's decision.* Several objectives are not combined into one number. With more
      than one objective and no declared scalarization the answer returns bounds per objective; a supplied
      scalarization is recorded in the answer's assumptions.
3. **Comparators.** An atom is `lhs cmp rhs` with `cmp ∈ {<, ≤, =}` and units. Let δ = lhs − rhs.
   - Exact value: `<` holds iff δ < 0; `≤` iff δ ≤ 0; `=` iff δ = 0.
   - Enclosure δ ∈ [lo, hi] (outward rounded): `<` holds iff hi < 0, fails iff lo ≥ 0, otherwise the atom
     straddles and the contribution is `Unknown(StraddlesThreshold)`. `≤` holds iff hi ≤ 0, fails iff lo > 0.
     `=` holds only when lo = hi = 0 exactly and fails iff 0 ∉ [lo, hi].
   - Universal statement over a set with stated ends: for S with lower end a, "∀ x ∈ S, x > c" holds iff
     a > c, or a = c and the lower end of S is open. On 0 < w ≤ 1 every realization has w > 0 although the
     infimum is 0. A uniform positive lower bound is sufficient for strict feasibility and is not necessary;
     when the caller wants that stronger property it is stated in `predicates.margins`, never assumed.
4. **Explanations** on an unresolved cell: `StraddlesThreshold`, `ModeSequenceUnenclosed`, `SolverFailure`,
   `BudgetExhausted`, `CompetingMechanisms(Vec<MechanismRef>)`, `NeedsMeasurement(MeasurementRef)`. A cell may
   carry several.
5. **No exclusion from a failure, by construction.** `Verdict::Excluded` is built only from `ProofRef`s whose
   kind is an exclusion kind; there is no path from `Contribution::Unknown` or from a `NumericalFailure` to it
   (invariant INV-AUGUR-06: no numerical failure, timeout or failed search is recorded as an exclusion). The
   standing rules of the subsystem follow: a failed training run is never an exclusion; a solver failure is
   never an exclusion; an unresolved cell is never reported as either verdict.

Determinism: classification is a pure function (D0). The contribution feeds the verdict of a cell; it carries no
claim of its own.

## Acceptance criteria

- [ ] At U = 3/4 and ε = 5/16 the docking separation is exactly zero and the strict predicate fails; at
      ε = 5/16 − 1/1024 it holds; a mutant that evaluates `<` as `≤` admits the equality case and is caught.
- [ ] "∀ w ∈ (0, 1], w > 0" evaluates to true; "∀ w ∈ [0, 1], w > 0" evaluates to false.
- [ ] Every `NumericalKind` yields an unresolved cell with a matching explanation; none yields an exclusion
      (property test over 10⁴ generated outcome sequences).
- [ ] The bouncing-ball fixture is rejected without a declared completion and accepted with one.
- [ ] A straddling enclosure yields `Unknown(StraddlesThreshold)`, never a verdict.
- [ ] A numerical failure on a cell that also has a checked exclusion certificate leaves the cell excluded.
- [ ] `scripts/e2e/mission_progress_rules.sh` passes, with the log described below.

## Test plan

### Unit tests

`crates/frob-mission/tests/progress.rs`:
- `docking_equality_fails_strict`: readings are centred at p and 2p with radius ε; the gap between the reading
  sets is p − 2ε; with the best admissible first command p = (U + 1/2)/2 = 5/8 and ε = 5/16 it is 0, and both
  worlds can read 15/16 (5/8 + 5/16 and 5/4 − 5/16).
- `open_end_strictness`: the two set statements above.
- `enclosure_three_way`: δ ∈ [−2, −1] holds; δ ∈ [1, 2] fails; δ ∈ [−1, 1] straddles; for `≤`, δ ∈ [−1, 0]
  holds and for `<` it straddles.
- `zeno_ball_without_completion_rejects` (`synthetic`; gravity stipulated as 10 m/s²): a ball dropped from
  1.25 m hits at 0.5 s with speed 5 m/s; with restitution 1/2 the flights last 1/2, 1/4, 1/8, … s, so impacts
  accumulate at 1.5 s. The mission "at rest on the floor at 2 s" is `Rejects` with `completion: None` and
  `Accepts` when the model declares the resting mode after 1.5 s.
- `deadlock_rejects`: a two-mode automaton whose only guard is never enabled stops before the horizon.
- `undefined_dynamics_is_not_vacuous_success`.
- `numerical_failures_are_unknown`: one case per `NumericalKind`.
- `independent_exclusion_overrides_failure`.
- `no_exclusion_constructor_from_failure` (compile-fail).
- `two_objectives_are_not_summed`.

progress_rules -- --json`, which prints one line per case with the outcome, the predicate and the
contribution: the docking separation at U = 3/4 with ε = 5/16 (`Rejects`, gap 0) and with ε = 5/16 − 1/1024
(`Accepts`, gap 1/512), the two open-end statements, the three enclosures of `enclosure_three_way` under `<`
and under `≤`, the bouncing ball without and with its completion (accumulation at 3/2 s), the deadlocked
automaton, and one line per `NumericalKind`; the script asserts each contribution and that the debug and the
release output are the same bytes; (3) the three mutants of the negative controls below (`<` evaluated as `≤`;
`Timeout` mapped to `Rejects`; a Zeno accumulation treated as completion), each built with its cargo feature
of `frob-mission`: `e2e_expect_caught <control> -- cargo test -p frob-mission --features <feature> --test
progress`. Log `target/e2e-logs/mission_progress_rules/<utc>.ndjson` through the STD-E2E helper, with a
transcript: `ts`, `script`, `bead`, `step`, `event` on every line; each `cmd` line the exact command, exit
code and wall time; one `assert` line per case with the observed and the expected contribution and, for the
docking and ball cases, the exact rationals (tags `--ka KA-637`, `--cx CX-275`); one `negative-control` line
per mutant with `caught`; the digests of the debug and release outputs; on a failure the first differing case;
a `summary`.

The user-visible half is in the later script `scripts/e2e/mission_budget_stops.sh` (bead N25a-24): an
exhausted budget and a planted solver failure both return unresolved cells with their explanations
(`BudgetExhausted`, `SolverFailure`), with the exit code of BD-135's budget-stop rule (2 with the flag
`resolution-unmet` when the unresolved set exceeds the query's `resolution`, 0 otherwise), and no excluded
cell appears without a proof reference; its log records, for each unresolved cell, its explanation list.

### Known answers and negative controls

platforms.

## Considerations

- "Independent evidence" must itself be a checked certificate; a second simulator's failure is not one.
- A cell that stays unresolved costs coverage where a definitive answer was required, and nothing else; a
  truthful unresolved cell is never a false certificate.
- The exact docking boundary is a strict-comparator fixture for bulk evaluation as well: on devices a strict
  predicate needs the exact-integer class or a guard band with exact fallback (bead BD-355).
- OPEN-AUGUR-5: sound reachable tubes for contact-rich cells do not exist in the suite, so most such cells
  will carry `ModeSequenceUnenclosed`; that is the expected state, revisited at M4.
