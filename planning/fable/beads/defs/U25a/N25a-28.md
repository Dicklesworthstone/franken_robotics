## Background

A mission query over a family of designs wants many related designs evaluated in one batch, on a GPU where the
data lives there. The mission answer's verdicts turn on strict predicates, and a strict predicate evaluated in
bulk in ordinary single precision is wrong near its boundary. On the docking family (a cart that must dock in
three ticks from one early velocity reading, with actuator bound U and read-error radius ε) a robust causal
policy exists exactly when ε < (U + 1/2)/4, equality excluded. FACT from the plan-time native pilot on a
65,536-row boundary screen: unguarded single precision gave 452 false admissions and 23,438 false exclusions
on the near-boundary grid; guarded single precision with an exact host fallback, and an exact-integer kernel,
gave identical decision bytes on every placement with no final error.

Two rules follow and BD-355 implements them for mission screens: strict predicates on a device use the
**exact-integer** kernel class or the **guarded** class (single precision with a guard band derived from an
error bound, and an exact fallback for rows inside the band); and device labels are proposals that schedule
work, never verdicts, until the CPU checker accepts a certificate.

GATE-AUGUR-15 (claim Parity; milestone M4; TARGET): inner, excluded and unresolved labels for the 65,536-row
screen and for one 1,024-design family batch are identical on `batch-cpu`, CUDA and Metal under the
exact-integer or guarded class, with zero final errors against exact CPU arithmetic. This script measures it
through the public verb on the two machines that have the hardware and merges the two site records.

## Scope

In: the script with its site mode and merge mode; both fixtures on every backend and placement; the refusal of
the unguarded class and of an undersized guard; the proof that no cell is decided from a device label; the
gate record. Out: the screens and their unit tests (BD-355); the kernels and their error-bound derivation
(BD-053, BD-182); variants on devices (BD-183); any speed claim.

## Technical approach

Script `scripts/e2e/mission_family_screens.sh --site host | linux-cuda | mac-metal` and
`scripts/e2e/mission_family_screens.sh --merge <site-record>…`. A site run writes
`target/e2e-logs/mission_family_screens/<utc>.<site>.json` (label digests, counts, receipts, hardware
fingerprint). The merge mode produces the gate row only when a `linux-cuda` record and a `mac-metal` record
exist for the same commit and fixture digests; a missing site leaves the gate `not run`, never passed.

**Fixture 1: the 65,536-row screen** (exact definition, generated by the script from integers). S = 2²⁸,
H = 2²⁷. For i = 0 … 65,535: U_i = H + (i·65,537 mod (H + 1)) and E_i = floor((U_i + H)/4) + ((i mod 9) − 4)·k,
with k = 1 (near grid) and k = 2,048 (separated grid). U_i/S is the actuator bound in [1/2, 1] and E_i/S the
error radius. A row is admitted when 4·E_i < U_i + H; equality is excluded. Expected on each grid: 34,590
admitted and 30,946 excluded, of which 1,820 are exact ties; label digest (SHA-256 of the ordered label bytes
after fallback) `c789e496d4a2e51be10ec0764991fb30a309d3f25522f3e7129410ca93f6e115` for both grids.
Under `guarded` (residual r = (float(U)·2⁻²⁸ + 0.5) − 4·(float(E)·2⁻²⁸), label 1 if r > 2⁻²¹, 0 if r < −2⁻²¹,
otherwise unknown and decided by the exact host comparison): near grid, 0 direct decisions and 65,536
fallbacks; separated grid, 58,254 direct decisions (29,128 positive, 29,126 negative) and 7,282 fallbacks;
zero wrong direct decisions.

**Fixture 2: the 1,024-design docking batch.** Cells on a 32 × 32 lattice: U ∈ [(32 + a)/64, (33 + a)/64],
ε ∈ [e/64, (e + 1)/64], a, e = 0 … 31. Per cell eight logical worlds (worst and best corner, each under gains
1 and 2 and both error vertices) run the three-tick closed loop in exact integer ticks. Labels: `inner` when
the worst corner is admitted (4·(e + 1) < 64 + a), `excluded` when the best corner is not (4·e ≥ 65 + a),
`unresolved` otherwise. Expected: 616 inner, 368 excluded, 40 unresolved.

Site steps (every site runs `batch-cpu`; the device rows are added by the site that has the hardware).
1. Build `frob` with the feature `frontier-family-gpu` and the standalone `frob-verify`. Record the hardware
   fingerprint and the toolchain.
2. Generate both fixtures and compute the reference labels with the exact CPU evaluator of
   `frob-conformance` (BD-355's example target: `cargo run -p frob-conformance --example family-screens --
   reference --out <dir> --json`); assert the counts and the screen digest above.
3. For each backend and placement available at the site (`batch-cpu`; on `linux-cuda`: each RTX 4090 alone and
   the two-shard placement; on `mac-metal`: Metal on the M5 Ultra) and each kernel class (`exact-integer`,
   `guarded`), run both fixtures through `frob mission synthesize <fixture>.fmission --tier <t> --placement
   <p> --kernel-class <c> --key fam-<fixture>-<t>-<p>-<c>-<run> --json`, with `<t>` one of `batch-cpu`,
   `gpu-cuda`, `gpu-metal`; every run carries its own key, because the runs are compared and a repeated key
   would return the first run's stored receipt (the options are N25c-09's, registered on the
   `mission.synthesize` row of VERBS-mission from M4). (DESIGN, the same in
   N25c-09, which owns the placement these options select: the execution tier is chosen with `--tier`, the
   option every verb that runs on a tier uses; an earlier draft of this script wrote `--backend`, and N25c-09
   wrote `--profile`, which names a step profile.) Assert: label counts; ordered label bytes equal to the reference (digest and
   a full byte compare on mismatch); for `guarded` the fallback counts and zero wrong direct decisions; the
   placement receipt shows the requested and actual placement and they agree.
4. **Zero final errors.** For every run, compare each final label with the exact CPU label: the count of
   differences is the measured value (threshold 0).
5. **Device labels do not decide cells.** For the batch, inspect the answer: every inner and excluded cell
   carries proof references, and the bundle is accepted by `frob-verify`; the 40 unresolved cells are in the
   unresolved list with the explanation `StraddlesThreshold` and a next test that names an exact split. Then
   run the mutant build that publishes cells from device labels alone (BD-355's `publish_from_device_labels`,
   built with `--features gauntlet-mutations`): the script must exit non-zero at this step (an inner cell
   without a proof).
6. **Refusals.** Through the verb, `--kernel-class unguarded` is refused with `FROB-REF-802` (pointer
   `/kernel_class`, exit 3): the `mission.synthesize` row admits only `exact-integer` and `guarded`, so no
   unguarded screen can feed a verdict from the public surface, and the row sets no guard width. The screen
   interface's own refusal, `FROB-REF-252` (BD-053's select lint), for an unguarded request that feeds a verdict
   and for a declared guard of 2⁻²⁶, below the derived error bound 5·2⁻²⁵, is asserted by BD-355's tests
   `unguarded_refused_for_verdict` and `undersized_guard_refused`, whose results the script reads from the
   site's test receipt and logs. BD-355's comparison entry point `cargo run -p frob-conformance --example
   family-screens -- unguarded --tier <t> --grid near --json` (runs the unguarded kernel for comparison and
   publishes nothing) shows false admissions and false exclusions on the near grid against the reference; the
   counts are logged against the pilot's 452 and 23,438 and any non-zero count satisfies the control.
7. **Host placement rule.** With `--placement auto` the small host-resident screen is placed on the host
   integer path and the receipt says so and why.
8. **Cancellation.** Start the batch on each device with `--sync-wait-ms 0` (exit 8, a job handle) and a
   fresh key, cancel it with `frob job cancel j:… --json` after its first progress report (`frob job status
   j:… --json`; the job verbs of N29a-23): the job drains, checked cells are kept, no partial label digest is
   published, and the device memory in use returns to its level before the run (no leaked resource).
9. **Determinism.** Each run twice; worker counts 1 and 8 on `batch-cpu`; all digests equal.
10. Write the site record. In merge mode: assert equal reference digests across sites, equal label digests
    across all backends, placements and classes, put the values in the merged receipt (label differences
    against exact CPU arithmetic (0), placements compared, classes compared, the controls caught) and enter
    the row with `cargo run -p frob-conformance --example record_gate -- --gate GATE-AUGUR-15 --receipt
    <hash>` (N38b-19); with one site missing no row is entered and the gate stays `not run`.

Device and transfer times, and the checker queue's time, are written to the disclosure block of each run and
support no claim.

## Acceptance criteria

- [ ] GATE-AUGUR-15: for the 65,536-row screen (both grids) and the 1,024-design batch, labels are identical on
      `batch-cpu`, CUDA (each card and the two-shard placement) and Metal under both kernel classes, with zero
      final errors against exact CPU arithmetic; the merged row carries the digests and counts.
- [ ] Screen: 34,590 admitted, 30,946 excluded, 1,820 ties, and the stated digest on every placement.
- [ ] Guarded class: fallback counts 65,536 (near) and 7,282 (separated); zero wrong direct decisions.
- [ ] Batch: 616 inner, 368 excluded, 40 unresolved on every placement.
- [ ] No answer cell is decided without a checked certificate; the mutant that publishes from labels is caught.
- [ ] The unguarded class is refused for a verdict (802 at the verb, whose row has no such value; 252 at the
      screen interface) and shows errors on the near grid; the undersized guard is refused with 252.
- [ ] A site without the hardware records its device rows as `not run`; the merge refuses to produce a pass
      from one site.
- [ ] Cancellation leaks no device resource; repeated runs give equal digests.

## Test plan

### Unit tests

None of its own; the fixtures' host tests are in BD-355 (`crates/frob-conformance/tests/family_screens.rs`,
`crates/frob-mission/tests/family_gpu.rs`). The merge logic is a small function with shell tests on recorded
site files under `scripts/e2e/fixtures/family_screens/`: `merge_needs_both_sites`,
`merge_rejects_different_commits`, `merge_rejects_unequal_digests`.

### End-to-end script and logging

This bead is the script. Log `target/e2e-logs/mission_family_screens/<utc>.ndjson` through the helper of
STD-E2E, with a transcript beside it. Per run a `cmd` line (exact command, exit code, wall time, the envelope's
evidence block with claim Parity, class, tier G5, determinism class, mission and answer identities) and
`metric` lines: admitted, excluded and tie counts; inner, excluded and unresolved counts; fallback count; wrong
direct decisions (threshold 0); label differences against the CPU reference (threshold 0); the label digest.
Also logged: backend, placement receipt (requested and actual), kernel class, device-active time, transfer
time and checker-queue time (disclosure only), and the hardware fingerprint. On a mismatch: the first
differing row index with its integers and both labels, and the paths of the label files. Final `summary`:
assertions passed and failed and the gate GATE-AUGUR-15 with its status (`pass`, `fail` or `not run`).

### Known answers and negative controls

KA-656 (guarded strict predicate on 65,536 rows of the docking boundary: 34,590 admitted and 30,946 excluded,
of which 1,820 are exact ties; no error after exact fallback; identical bytes on all placements; tier G5 on
host, CUDA and Metal; negative control: unguarded single precision, 452 false admissions and 23,438 false
exclusions on the near grid). KA-637 (the family boundary ε < (U + 1/2)/4 with a strict comparator). CX-284.
Hand checks: on the 32 × 32 lattice the corner rule 4·e < 64 + a admits 648 lattice points and has 8 ties;
the batch counts 616, 368 and 40 sum to 1,024. Negative controls: the label-publishing mutant; the unguarded
kernel; the undersized guard; a merge from one site. Determinism lanes (tier G5): twice on one machine; worker
counts; across the three backends and the shard placements; debug and release on `batch-cpu`.

## Considerations

- No speed is claimed. At this size the host integer path was the fastest in the pilot (23 to 35 µs on the
  Mac's CPU against 209 to 309 µs through Metal); dispatch and transfer dominate a small host-resident job.
  Any timing quoted from a family batch first needs a registration admitted by the ceiling check.
- The gate needs two machines. The merge step is what turns two partial records into one row, and the
  compute envelope for the device runs must be approved before the script is scheduled.
- The contents of the 1,024-design batch are this unit's choice (the plan fixes its size, labels, classes and
  backends); a different batch needs its own expected counts and its own record.
- The guarded class's error bound holds for the declared chart and operation order only.
- The counts 452 and 23,438 are the pilot's, at its pin; the control is satisfied by any non-zero error count
  of the unguarded kernel, and the observed counts are recorded beside the pilot's.
