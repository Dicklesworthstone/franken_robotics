## Background

After an edit, the revalidation engine (BD-292) decides for every obligation of every stored verdict whether it
is still proved. Four grades of reuse exist: (1) identity, the obligation's full key is unchanged; (2)
dependency, every changed field lies outside the obligation's recorded dependency support; (3) implication, a
changed field lies inside the support and a polarity rule of the assumption lattice preserves the obligation;
(4) none, rerun with its cost. Grades 1, 2 and 4 are Solid and are BD-292's. This bead is grade 3: the
Frontier part, behind the flag `frontier-revalidate-implication`, off by default.

**The governing rule (doctrine D-11): a hash identifies; only an implication licenses skipping a recheck.** A
polarity rule is such an implication, stated once and checked every time it is used. Assumption sets are
ordered by inclusion of admitted worlds and commands; the feasible family is antitone in the world set,
monotone in the policy class and monotone in the acceptance predicate ordered by implication. So narrowing the
disturbance set preserves an inclusion (a universal guarantee with the same witness), and enlarging it can
preserve an exclusion only when the exclusion's witness lies in the old set and the policy class and
information contract are unchanged. Each such statement is one rule, with side conditions that are exact
checks.

Why a registry and not code paths: KILL-AUGUR-REUSE (standing from M3) says that one incorrectly inherited
verdict from an implication rule removes that rule, and reuse falls back to the dependency-keyed memo graph
(grades 1 and 2). That fallback must be executable per rule, at once, without a code change: a row's status in
a registry is the switch. Rejected alternatives: one global on/off for implication reuse (one bad rule would
remove every good one); trusting the caller's description of the edit's direction (the engine classifies the
edit from the two documents); composing per-field rules on an edit of two fields that share support (per-field
monotonicity rarely proves an interaction: a larger motor relaxes a torque limit and also changes mass and
rotor inertia).

The plan's seed row for the revalidation engine lists monotone transport (BD-288) as a prerequisite because of
its polarity part. That part is this bead, so the dependency is carried here: the side conditions of a
polarity rule reuse the exact inclusion and sign checks that BD-288's sub-certificates define, and the
monotone-transport proof kind and its checker must exist before a rule may cite them.

What the plan-time pilot showed (FACT): on a four-state camera-delivery fixture a correctly keyed dependency
graph did exactly the work of a richer semantic receipt, so a reuse advantage is not claimed; what grade 3 can
add is a physical non-dependence or polarity argument cheap enough to matter. The polarity pilot PILOT-C-18
(N10b-07) and the frozen 30-amendment campaign with its separately built incumbent (N25a-17) are this bead's
pilots.

## Scope

In: the rule registry file and its schema; the `PolarityRule` trait that owner crates implement; the grader
that BD-292's hook calls (the `ImplicationGrader` implementation); the pure-change rule; the joint-edit rule;
the licence record of a grade-3 survival; the disablement path and its effect on the next call; fail-closed
loading. Out: the engine, the verdict record, the edit classifier, grades 1, 2 and 4, masks and eligibility
(BD-292); the six mission rules and the optimality obligations (N25a-16); grade-3 rules for non-mission
verdicts and the sixteen-rule polarity table (BD-347, N28b-34); the kill-gate decision (N25a-19); the
false-certificate procedure that reports a false reuse (N25b-03); the campaign measurement (N25a-26).

## Technical approach

1. **Registry.** `registries/revalidation-rules.toml` with a JSON Schema under `schemas/registries/`
   (DESIGN name), one row per rule:
   ```toml
   [[rule]]
   name = "narrow-disturbance"        # unique; the name a licence cites
   version = 1                        # bumped when the side conditions change
   component = "world.disturbance"    # the assumption component the edit must change
   direction = "Narrowed"             # one pure direction of BD-292's classifier
   verdict_kind = "inclusion"         # inclusion | exclusion | comparison | optimum | estimate
   side_conditions = ["new-world-set-within-old"]
   status = "enabled"                 # enabled | disabled
   disabled_by = ""                   # counterexample or withdrawal id when disabled
   owner = "frob-mission"             # the crate that implements the rule
   ```
   The file starts with zero rows; owner beads add theirs (N25a-16 adds six).
2. **Trait** (DESIGN, in `frob_verbs::revalidate::implication`):
   ```rust
   pub trait PolarityRule: Send + Sync {
       fn name(&self) -> &'static str;
       fn version(&self) -> u32;
       fn applies(&self, component: ComponentId, dir: Direction, kind: VerdictKind) -> bool;
       fn check(&self, ob: &Obligation, old: &AssumptionSet, new: &AssumptionSet)
           -> Result<Vec<SideConditionCheck>, SideConditionFailure>;
   }
   ```
   Owner crates register implementations at link time; the grader matches registry rows to implementations by
   `name` and `version`.
3. **Grading an obligation not kept by grades 1 and 2.** Given the classified edit from BD-292:
   1. Let C be the edited components whose support intersection with the obligation is non-empty.
   2. If any component of C is `Mixed`, return no licence (grade 4).
   3. If |C| ≥ 2 and any two of their support intersections share a field, return no licence (joint check,
      grade 4).
   4. For each component in C, find the enabled rows with that component, its pure direction and the
      obligation's verdict kind; run each matching implementation's `check` until one passes. If none passes
      for some component, return no licence.
   5. Otherwise return one licence per component; the obligation is grade 3.
4. **Licence.** `ImplicationLicence { rule, rule_version, component, direction, old_assumptions: Digest,
   new_assumptions: Digest, relation, checks: Vec<SideConditionCheck> }`, where `relation` is the order
   relation used (for example "new world set ⊆ old world set") and each check records its inputs and outcome.
   BD-292 stores it verbatim in the mask; for a mission answer N25a-16 hands it to the bundle writer as an
   implication record so the auditor re-checks it.
5. **Disablement.** A row with `status = "disabled"` is never consulted; its former survivals are graded 4 on
   the next call and listed with the reason `rule-disabled: <name> (<disabled_by>)`. Disabling is a reviewed
   registry edit that names the counterexample; the false-certificate procedure (N25b-03) and the
   KILL-AUGUR-REUSE decision (N25a-19) are the only producers of such edits. A rule is re-enabled only with a
   bumped `version` and its fixture re-run.
6. **Fail-closed loading.** A row whose `name` and `version` no linked crate implements, a duplicate name, or
   a row that fails the schema disables grade 3 for the whole call: every obligation not kept by grades 1 and
   2 is graded 4, and the envelope carries the warning `revalidation-rules-invalid` with the offending row.
   With the flag off no grader is registered and the registry is not read.
7. **Determinism.** The grader is a pure function of the obligation, the two assumption sets and the
   registry (D0); rows are tried in name order, so the licence chosen is reproducible.

## Acceptance criteria

- [ ] A `Mixed` component is never given grade 3; an edit of two components whose support intersections share
      a field is never given grade 3; two pure edits on disjoint support intersections, each licensed, give
      grade 3 with two licences.
- [ ] Disabling a rule in the registry turns its grade-3 survivals into grade-4 reruns on the next call, each
      listed with `rule-disabled` and the counterexample id.
- [ ] An unknown, duplicate or schema-invalid row disables grade 3 for the call with the warning
      `revalidation-rules-invalid`; no obligation is given grade 3 by it.
- [ ] With the flag off, results are byte-identical to BD-292 with no grader registered.
- [ ] Every grade-3 survival carries a licence with rule name and version, both assumption digests, the
      relation and every side-condition check.
- [ ] The planted unsound rule (below) inherits a stale verdict and is caught by comparison with full
      recomputation; after it is disabled the same call grades the obligation 4 and matches recomputation.

## Test plan

### Unit tests

`crates/frob-verbs/tests/revalidate_grade3.rs` (real engine, real ledger in a temporary root; the rules used
are real implementations defined in the test file over the docking answer of the first slice, labelled
`synthetic` because they stand in for the owner crates' rules):
- `pure_change_rule_licenses`: a test rule "inclusion survives a narrowed read-error interval" on the docking
  inclusion at (U, ε) = (3/4, 1/4), edit ε → 1/8: grade 3, one licence, relation "new error interval ⊆ old".
- `mixed_component_goes_to_grade_4`: torque limit raised together with mass: no licence.
- `joint_edit_shared_support_goes_to_grade_4`: ε and the packet arrival changed together, both read by the
  same observation obligation: no licence.
- `joint_edit_disjoint_supports_composes`: two edits whose support intersections are disjoint, each licensed:
  grade 3 with two licences.
- `side_condition_failure_goes_to_grade_4`: ε → 3/8 (an enlargement) offered to the narrowing rule: no licence.
- `disabled_rule_is_not_consulted`; `disabled_rule_reason_listed`.
- `unknown_rule_row_fails_closed`; `duplicate_rule_row_fails_closed`; `schema_invalid_row_fails_closed`.
- `flag_off_identical_to_no_grader` (byte-identical results).
- `licence_records_everything`; `rows_tried_in_name_order`.
- `planted_unsound_rule_caught`: a test rule "inclusion survives an enlarged hidden-gain set" applied to the
  docking inclusion at (3/4, 1/64) after gain 33/32 is added; fresh evaluation withdraws it (with gains 1 and
  33/32 the reading (65/64)·p is shared for every p, and the least worst-case terminal error is 1/65 m), so the
  comparison fails naming the cell; disabling the row makes the next call grade it 4 and agree.

### End-to-end script and logging

`scripts/e2e/revalidate_grade3_framework.sh`, sourcing the STD-E2E helper. With `frob` built with the flag:
(1) `frob result revalidate` on the docking answer after ε falls to 1/8 with the shipped (empty) registry:
every obligation not kept by grades 1 and 2 is graded 4 and the result equals full recomputation; (2) the same
with a scratch registry (`--registries-root <scratch>`) holding a row no crate implements: exit 0, warning
`revalidation-rules-invalid`, zero grade-3 licences; (3) a schema-invalid row: same outcome; (4) the build
without the flag: byte-identical `result` to step (1). Positive grade-3 survivals through the public verb are
asserted by N25a-16's tests and N25a-26's campaign, after the mission rules exist. Logs to
`target/e2e-logs/revalidate_grade3_framework/<utc>.ndjson`: per command the exact line, exit code, wall time
and evidence block; per call the counts by grade, licences issued, warnings, the digests of old and new
answers; on failure the first differing obligation and the paths to reproduce; a `summary` line naming
KILL-AUGUR-REUSE.

### Known answers and negative controls

Known answers: the docking boundary ε < (U + 1/2)/4 decides every test rule's expected outcome; the third-gain
withdrawal at (3/4, 1/64) with worst-case error 1/65 m (KA-638, KA-701). Negative controls registered: a mutant
grader that ignores `Mixed`; a mutant that composes rules on shared support; a mutant that consults a disabled
row; a mutant loader that skips the unknown row instead of failing closed; the planted unsound rule.
Metamorphic: MR-11 (polarity directions) on the test rule; MR-12 (incremental equals full) with the flag on.
Determinism lanes: twice on one machine; worker counts 1 and 8; debug and release.

## Considerations

- KILL-AUGUR-REUSE: trigger, one incorrectly inherited verdict from an implication rule; fallback, that rule is
  removed (its row disabled) and reuse falls back to grades 1 and 2 of BD-292. This bead makes the fallback a
  registry edit.
- The rules are only as good as their side conditions; the planted unsound rule is the reminder that the
  campaign comparison (N25a-26), not the rule's derivation, is what catches a wrong one.
- Performance: a side-condition check is an exact inclusion or a bounds check, far cheaper than a rerun; no
  speed is claimed (the pilot tied).
- OPEN-ATEL-4 (two verbs over one engine, default): nothing here depends on its outcome.
- Open question: whether a rule may be re-enabled after a repair within the same milestone; fail-closed
  default: only with a bumped version and its fixture re-run, recorded in the registry row.
