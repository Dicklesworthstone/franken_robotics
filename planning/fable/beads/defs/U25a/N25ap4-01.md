## Background

`mission.synthesize` answers which members of a family of robot designs can do a mission. Behind the verb, a
driver walks the cells of the design domain (N25a-12). For each cell it asks a family's **lowering** to propose
an inclusion, an exclusion or nothing. A lowering is the translation of one mission template into equations a
solver can decide: the stance family (BD-130), the docking family (BD-129) and the pusher battery (BD-131) at M1.

This bead fixes the interface between the two sides: the `Lowering` trait, the `Proposal` it returns, the budget
meter a lowering charges, and the registry through which a family registers its lowerings. It was split from
step 1 of N25a-12 in polishing round 4. DESIGN, with the reason: the family beads only implement and register a
lowering, and their tests call the lowering directly. Making them wait for the whole driver (worklist, paving,
point and existence queries, refinement) delayed every bead behind them for an interface of one page. The driver
and the families now depend on this bead, and the families no longer depend on the driver.

PO-AUGUR-01 (N25d-34) requires a second, independently written lowering per template, compared exactly with the
first. The registry therefore knows two roles, `primary` and `second`. The verb selects a lowering with
`--lowering primary|second|<lowering name>` (VERBS-mission; N25c-20 registers `scenario-tree` for docking). The
answer records the name of the lowering that ran.

Rejected alternatives: registration by link-time constructors (the order of registration would depend on the
linker, and the answer bytes must not); one lowering per template with no roles (PO-AUGUR-01's comparison would
then need a second code path outside the registry).

## Scope

In: the `Lowering` trait and the contract of each method; `Proposal`; the `Budget` meter passed to `propose`; the
registry (`LoweringEntry`, `Role`, construction and validation, selection by role or by name); a partition helper
that family beads use to test `exact_boundary` without the driver.

Out: the driver (N25a-12: worklist, deciding a cell from its vertices, paving, point and existence queries,
refinement, response selection, scheduling invariant); each family's lowering and its registration entries
(BD-129, BD-130, BD-131, N25c-20); the verb, its `--lowering` option and how the verb reports a selection error
(BD-135, N25c-20, N25d-34); the register of lowering pairs `crates/frob-conformance/registry/lowerings.toml` and
the exact comparison of the two roles (N25d-34); what a budget stop returns (BD-135).

## Technical approach

1. **The trait** (module `frob_mission::lowering`; DESIGN):
   ```rust
   pub trait Lowering {
       fn fragment(&self) -> Fragment;                         // linear-static | finite-game | interval | …
       fn applies(&self, m: &AdmittedMission) -> bool;
       fn exact_boundary(&self, m: &AdmittedMission, cell: &Cell) -> Option<Vec<Cell>>;  // exact split, if any
       fn propose(&self, m: &AdmittedMission, cell: &Cell, budget: &mut Budget) -> Proposal;
   }
   pub enum Proposal { Inner(Vec<ProofObject>), Excluded(Vec<ProofObject>), Undecided(Vec<Explanation>) }
   ```
   `Fragment` and `AdmittedMission` are N25a-02's. `Cell` and `Explanation` are BD-128's, and `ProofObject` is
   N25b-01's, which BD-128 depends on. The trait is object-safe, so the registry holds `Box<dyn Lowering>`.
2. **The contract of each method.** Each family bead's unit tests check it:
   - `fragment` returns one of the classes of N25a-02's fragment classification. It is constant for a lowering.
   - `applies` is pure and total: it reads only the admitted mission and never solves anything.
   - `exact_boundary` returns `Some(cells)` only when the cells partition `cell` exactly: their union is `cell`,
     no two share a point, and every cut has the open or closed end that its ownership gives (BD-128's `Cell`).
     The partition helper of step 5 checks this. `None` means the lowering knows no exact split, and the driver
     falls back to its paving.
   - `propose` returns `Inner` or `Excluded` only with proof objects whose `cell` is this cell and whose
     `establishes` prefix is the mission's prefix. A failed search, a timeout or a solver error is
     `Undecided(vec![SolverFailure])` and never `Excluded` (INV-AUGUR-06, BD-128 rule 2). When the meter reports
     exhaustion, the lowering returns `Undecided(vec![BudgetExhausted])` and charges nothing further.
3. **The budget meter** (DESIGN, the smallest form the trait needs; the driver builds it from the call, and BD-135
   decides what a stop returns): `Budget` holds one remaining amount per budget line of the call (the keys of
   `--budget`, such as `wall_s`, `cpu_core_s` and `gpu_s`, N32a-15). `charge(key, amount) -> Result<(), Exhausted>`
   subtracts, or returns `Exhausted { key }` and changes nothing when the amount exceeds what remains.
   `remaining(key)` reads a line. A line the call did not set is unlimited. Amounts are exact (integer
   milliseconds of the line's unit), so a meter never goes negative and two runs with equal charges stop at the
   same call.
4. **The registry.**
   ```rust
   pub enum Role { Primary, Second }
   pub struct LoweringEntry { name: &'static str, template: TemplateId, role: Role,
                              make: fn() -> Box<dyn Lowering> }
   pub enum LoweringChoice { Primary, Second, Named(String) }
   ```
   - `TemplateId` is the template's registered name as `mission.new --template` takes it (`stance-family`,
     `docking`, `pusher`; BD-126), which is also the key of the template's record in N25d-34's register. It
     labels entries and plays no part in matching: whether a lowering runs on a query is decided by `applies`
     alone, so a query written as a file, with no template named, is served like one made from the template.
   - Each family module exports `pub fn entries() -> Vec<LoweringEntry>`. `frob_mission::lowering::builtin()`
     concatenates them in one function, in a fixed order (by template, then role). Adding a family is one line
     there.
   - `Registry::new(entries) -> Result<Registry, RegistryError>` refuses a duplicate `name`
     (`DuplicateName`) and a second entry of the same role for one template (`DuplicateRole { template, role }`).
     A template may have a primary with no second until N25d-34's register lists its pair.
   - `select(&self, m, choice) -> Result<Vec<(&'static str, &dyn Lowering)>, SelectError>` returns the
     entries for the choice that apply to `m`, in registry order, each with its name so that the answer records
     the lowering that ran. `Primary` and `Second` filter by role and by `applies`. An empty result is not an
     error: the driver then answers every cell unresolved (N25a-12 step 1), and a query is never refused only
     because no lowering applies. `Named(n)` returns the one entry named `n`. A name that no entry has is
     `SelectError::UnknownLowering { name }`, and an entry whose `applies` is false for `m` is
     `SelectError::NotApplicable { name, template }`.
5. **Partition helper.** `frob_mission::lowering::check_partition(cell, &cells) -> Result<(), PartitionError>`
   names the first gap, the first overlap or the first wrong end. Family beads use it in their unit tests of
   `exact_boundary`, and the driver uses it before it accepts a split.

Determinism: the registry order is fixed by `builtin()`, selection is a pure function of the mission and the
choice, and the meter is exact (D0).

## Acceptance criteria

- [ ] The trait, `Proposal`, `Budget`, `Role`, `LoweringEntry`, `LoweringChoice`, `Registry` and
      `check_partition` exist in `frob_mission::lowering` with the contract above; `Box<dyn Lowering>` compiles.
- [ ] `Registry::new` refuses a duplicate name and a second primary (or a second `second`) for one template.
- [ ] `select` by role filters by `applies`, keeps registry order and returns the names; `Named` with an unknown
      name or an inapplicable entry returns the typed error; a mission that no lowering applies to selects none
      and is not an error.
- [ ] The meter refuses a charge beyond what remains without changing it, and an unset line is unlimited.
- [ ] `check_partition` accepts [2, 14/3] with (14/3, 6] as a partition of [2, 6] and refuses a gap, an overlap
      and a cut owned by both sides.
- [ ] `builtin()` constructs without error. It is empty when this bead closes; each family bead adds its line
      and re-runs `builtin_registry_is_valid` in its own change.
- [ ] `scripts/e2e/mission_lowering_registry.sh` passes, with the log described below.

## Test plan

### Unit tests

`crates/frob-mission/tests/lowering_registry.rs`. The tests use one small exact lowering written in the test
file, over a `synthetic` template `toy-threshold` (one free parameter x ∈ [0, 5], feasible exactly when x ≤ 3):
its `exact_boundary` splits at 3, and its `propose` returns an `lp-primal` proof on [0, 3] and an `lp-farkas`
proof on (3, 5]. It is a real implementation of the trait, not a stand-in for a family.
- `trait_is_object_safe`.
- `duplicate_name_refused`; `two_primaries_for_one_template_refused`; `primary_without_second_allowed`.
- `select_primary_filters_by_applies` (the toy applies to `toy-threshold` and not to a mission of another
  template); `select_keeps_registry_order_and_names`.
- `select_named_unknown_refused`; `select_named_not_applicable_refused`; `no_applicable_lowering_selects_none`.
- `toy_exact_boundary_is_a_partition` (through `check_partition`); `toy_proposals_match_their_cells`.
- `partition_helper_cases`: [2, 14/3] and (14/3, 6] pass; [2, 4] and (5, 6] report the gap (4, 5]; [2, 5] and
  [4, 6] report the overlap [4, 5]; [2, 14/3] and [14/3, 6] report the end 14/3 owned twice.
- `budget_charge_exhausts` (`cpu_core_s` = 2 s: charges of 1.5 s and 0.4 s succeed, a further 0.2 s is
  `Exhausted` and leaves 0.1 s); `unset_line_is_unlimited`.
- `builtin_registry_is_valid` (the shipped list constructs; names are unique).
- `registry_order_is_stable` (two constructions give the same order; the order does not depend on hashing).

### End-to-end script and logging

`scripts/e2e/mission_lowering_registry.sh` (header `bead=N25ap4-01 milestone=M1 labels=augur,mission gates=
seed=0 needs=cpu`), written by this bead and built only on its dependencies (the trait and the registry have no
verb of their own, so the script drives them through cargo targets): (1) `cargo test -p frob-mission --test
lowering_registry`, in debug and in release; (2) `cargo run -p frob-mission --example lowering_registry --
--json`, which builds a registry from the toy lowering of the tests, prints the entries in registry order (name,
template, role), the selection for `primary`, `second`, the toy's name and an unknown name on the toy mission,
the result of `check_partition` on the four cases of `partition_helper_cases`, and the meter's state after the
three charges of `budget_charge_exhausts`; the script asserts each printed value and that two runs print the
same bytes. Log `target/e2e-logs/mission_lowering_registry/<utc>.ndjson` through the STD-E2E helper, with a
transcript: `ts`, `script`, `bead`, `step`, `event` on every line; each `cmd` line the exact command, exit code
and wall time; one `assert` line per printed value with observed and expected (the gap (4, 5], the overlap
[4, 5], the doubly owned end 14/3, the remaining 0.1 s); the digests of the two runs; on a failure the first
differing value and the path of the example's output; a `summary`. The user-visible path,
`frob mission synthesize --lowering primary|second|<name> --key … --json` with the name of the lowering that ran
in the answer, is driven by the scripts of later beads: `scripts/e2e/mission_stance.sh` (N25a-21), N25c-20's
`scripts/e2e/mission_docking_lowerings.sh` and N25d-34's comparison of the two roles, which log the selected
lowering's name on each `cmd` line.

### Known answers and negative controls

No known-answer row of its own; the stance boundary 14/3 per metre (KA-624) appears here only as partition test
data. Negative controls in the tests above: a registry with two primaries for one template; a split with a gap,
an overlap or a doubly owned end; a charge beyond the remaining budget.

## Considerations

- The trait is the contract three family beads build against at M1. A change to it after they land changes all
  of them, so a new need (for example a lowering that proposes transports) is added as a new method with a
  default body, never as a change of an existing signature.
- The meter is deliberately small. Stops, the flag `resolution-unmet` and exit codes are BD-135's. Which lines
  a lowering charges, and how much, is each family's decision, stated in its bead.
- `scenario-tree` (N25c-20) is registered with role `second` for the docking template, so `--lowering second`
  and `--lowering scenario-tree` select the same program, as N25c-20 states.
