## Background

Lemma is the subsystem that owns evidence classes, theorem cards, certificate bundles and the routes by which a
statement becomes `Certified` or `Proved`. Its producer crate is `frob-lemma` (layer 6). This bead is the first
version of that crate, built at M0 with the smallest content that retires a real risk: can a derived kernel carry
an offline-checkable certificate of an algebraic identity at all. Tier: Solid.

Terms. A kernel is a small numerical routine emitted from a straight-line program (a list of arithmetic
assignments with no branches) by the derivation annex `derive/frob-derive`. An instance certificate is a statement
about one such kernel at one content hash, accepted by a checker with an offline-verifiable witness; its class is
`Certified`. The four evidence classes, weakest first, are `Estimated`, `Tested`, `Certified`, `Proved`; `Proved`
is reserved for a general statement accepted by a Lean kernel. A theorem card is a statement the project wants,
with its route and tier.

Decision ADR-LEMMA-01 (the algebraic route first): what is certified is formulated as a polynomial or rational
identity, an exact rational inequality or an interval enclosure, because that is what both proof tools can check
today; analytic statements about exp, log and manifolds wait. FACT (audit of `frankensympy` at `29f847c1`):
FrankenSymPy has exact polynomial identity checking with an offline verifier (`fsym-proof-kernel`,
`fsym-capsule-consumer`), interval certificates and exact rational linear algebra; it has no Lie algebras,
quaternions or noncommutative symbols, so every identity is written in scalar coordinates. FrankenSymPy is a
build-time tool reached from `derive/`; it is never linked into a `frob` binary.

The three identities of M0 (each HYPOTHESIS until its certificate replays):

- T-01. For skew-symmetric Ω, cay(Ω)ᵀ·cay(Ω) = I and det cay(Ω) = 1, on the Cayley step kernel `K-cay-step`.
- T-03. The quaternion update preserves the norm: ‖q·c‖² = ‖q‖²·‖c‖², on `K-cay-step`, the M0 kernel that
  forms the product q′ = q ⊗ c (BD-019), with its normalization clause on `K-normalize`.
- T-04. Ad(g·h) = Ad(g)·Ad(h), and the group coadjoint is the inverse transpose, on the SE(3) adjoint program.

This bead serves BET-11 (proof-carrying kernels are affordable; falsifier: certificates cover fewer than 80% of
derived kernels within FrankenSymPy's budgets) with its first three data points, and it supplies the mechanism
half of GATE-LEMMA-06 (no constructor of proof evidence outside `frob-lemma`).

Rejected alternatives. (1) Certify by random testing at M0: that is class `Tested` and proves nothing about the
program text; it is kept as the named fallback of a later kill gate, not as the first route. (2) Certify the
textbook formula in place of the kernel: the certificate would be about a formula nobody runs; the identity is
extracted from the kernel's own straight-line program. (3) Drive Lean from the build: FrankenLean does not
elaborate tactic proofs today (ADR-LEMMA-02); the general statements are separate later work.

## Technical approach

1. Data model (DESIGN; `crates/frob-lemma/src/claim.rs`, `cert.rs`):

```rust
pub struct KernelClaim {                 // what is asserted, about what
    card: CardId,                        // "T-01"
    kernel: KernelId,                    // content hash of the kernel's straight-line program
    identity: Identity,                  // lhs, rhs as polynomial expression DAGs over ℚ, in the kernel's symbols
    side_relations: Vec<Relation>,       // t² = radicand for each square root; relations such as RᵀR = I
    side_conditions: Vec<Text>,          // nonvanishing denominators, stated and justified (D ≥ 4 for T-01)
}
pub struct InstanceCertificate {         // the file K-<name>.cert, canonical JSON
    claim: KernelClaim,
    checker: CheckerRef,                 // "fsym-proof-kernel", build, the rule it applied
    witness: Witness,                    // normal forms, and cofactors where the identity holds modulo relations
    receipt: ReceiptId,                  // BLAKE3 of the canonical bytes
}
```

2. Statement extraction. `derive/frob-derive` executes the kernel's straight-line program (the `frob-kir`
   program whose content hash is the `KernelId`) symbolically and emits the identity in cleared-denominator form.
   In the kernel's symbols (BD-019) ω below stands for the dimensionless increment a = h·ω, so that every sum in
   a statement is homogeneous:
   - T-01: with D = 4 + ω₁² + ω₂² + ω₃² and N = D·I + 4·ω̂ + 2·ω̂² (so that the rotation is N/D), the statements
     are NᵀN = D²·I (nine entries, degree 4) and det N = D³ (degree 6); the side condition D ≠ 0 holds over the
     reals because D ≥ 4. On `K-cay-step` these are BD-019's R(c)ᵀ·R(c) = d²·I and det R(c) = d³ for the
     increment c = (1, a/2) the program forms and its output d, since N = 4·R(c) and D = 4·d.
   - T-03, on `K-cay-step`: (q₀c₀ − q₁c₁ − q₂c₂ − q₃c₃)² + (q₀c₁ + q₁c₀ + q₂c₃ − q₃c₂)² + (q₀c₂ − q₁c₃ + q₂c₀ +
     q₃c₁)² + (q₀c₃ + q₁c₂ − q₂c₁ + q₃c₀)² = (q₀² + q₁² + q₂² + q₃²)·(c₀² + c₁² + c₂² + c₃²), instantiated at the
     program's c = (1, a/2): ‖q′‖² = ‖q‖²·d, seven variables (BD-019's norm identity).
   - T-03's normalization clause, on `K-normalize`: the square root is replaced by a witness symbol t with the
     side relation t² = n (n the input's squared norm, in the kernel's association), and the statement is
     Σ outᵢ² = 1, cleared of the denominator t²: (Σ outᵢ²)·t² − t² = n − t², zero modulo t² − n with cofactor −1.
     (The form (Σ outᵢ²)·t² = n holds for any t and would certify nothing; without the side relation the
     statement is false, which is the missing-relation control.)
   - T-04: for g = (R_g, p_g), h = (R_h, p_h), with Ad_g(ω, v) = (R·ω, R·v + p × R·ω): the block identities
     R_{gh} = R_g·R_h and (R_g·p_h + p_g)^·R_g·R_h = p̂_g·R_g·R_h + R_g·p̂_h·R_h, and for the coadjoint
     Ad_g⁻ᵀ(τ, f) = (R·τ + p × R·f, R·f) the identities that make it the inverse transpose. With R given by a
     quaternion they are plain polynomial identities after clearing ‖q‖²; with R given by entries they hold modulo
     RᵀR = I and det R = 1 and carry explicit cofactors.
   BD-019 derives `K-cay-step` and `K-normalize` and checks the same identities, built from its symbolic
   expressions, with FrankenSymPy's proof kernel in its own tests (INT-FSYM-01's first half); it writes no
   certificate file. This bead extracts them from the lowered program instead, binds each to its card and writes
   the certificate files, so a certificate is about the program that ships. No M0 seed derives a kernel whose
   program is the adjoint action, so this bead adds a three-assignment program `K-ad-se3` to the derivation list
   for T-04 (DESIGN; recorded in the coverage file as a gap that was filled).
3. Certification stage (`derive/frob-derive`, stage `certify`, build time). For each claim: submit to
   FrankenSymPy's proof kernel as an algebraic-identity claim decided by polynomial normal form; on acceptance
   write the certificate into `K-<name>.cert` beside the kernel with the kernel's content hash inside (DESIGN:
   one file per kernel holding one `InstanceCertificate` per card claimed on it, in card order, so that
   `K-cay-step.cert` holds T-01 and T-03, `K-normalize.cert` T-03's normalization clause and `K-ad-se3.cert`
   T-04: four certificates for three cards); on rejection or budget exhaustion write nothing and fail the build
   step with the residual polynomial's leading terms. The files join the `check-generated` comparison, so
   regeneration must reproduce them bit for bit. Record time and peak memory per identity (the first
   measurements for RISK-07: FrankenSymPy budgets block derivations or certificates by expression swell).
4. Loading and binding (`frob-lemma`). `InstanceCertificate::load(path, kernel_id)` refuses a certificate whose
   embedded kernel hash differs from the kernel it sits beside. A certificate certifies one `KernelId`; a changed
   kernel has no certificate until the stage runs again.
5. Issuing evidence. `frob_lemma::issue::proof_evidence(cert: &InstanceCertificate, verdict: CheckVerdict)`
   returns `Evidence<Proof>` with class `Certified`, the receipt hash and the checker identity. It is the only
   function in the workspace that yields evidence for the Proof claim.
   Exclusivity mechanism (DESIGN). Rust has no crate-scoped friend visibility, so two layers are used. (a) Type
   privacy: `Evidence<K>` in `frob-core` has private fields, no setter for `class`, and no public constructor
   that takes a class. (b) One doorway: the raw constructor for the Proof marker is a hidden function in
   `frob-core` marked deprecated with the note "only frob-lemma issues Proof evidence"; the workspace lint table
   denies deprecated uses; exactly one allow exists, on `frob_lemma::issue`, and the workspace checks fail if a
   second appears. A call from any other crate is a compile error, which is what the compile-fail case asserts.
   If the owner of `frob-core` chooses another sealing mechanism, the acceptance criterion is unchanged.
6. Wording rules carried by the crate: no artifact prints `Proved` or `Certified` without the certificate's
   content hash and the checker's identity (INV-LEMMA-01); the word "verified" is not used for results; every
   certificate record carries the sentence that it is about the program over ℚ with square roots and says nothing
   about floating-point results.
7. Ledger: each certificate's receipt, kernel hash, card, checker build, time and memory are written to the
   evidence ledger; the card's route status moves from `hypothesis` to `checked`.

Determinism class D0: the certificate bytes are a function of the kernel program and the checker build.

## Acceptance criteria

- [ ] `crates/frob-lemma/` exists with `CONTRACT.md` (ten sections); it does not depend on `frob-cert`.
- [ ] `K-cay-step.cert` (T-01 and T-03), `K-normalize.cert` (T-03's normalization clause) and `K-ad-se3.cert`
      (T-04) are produced by the `certify` stage, each certificate with the kernel content hash inside and
      accepted by FrankenSymPy's proof kernel (the seed's condition: the three identities certify); regenerating
      them reproduces the checked-in files bit for bit.
- [ ] A mutated coefficient is rejected: for each kernel, a build in which one coefficient of the program is
      changed (the ½ of the increment c = (1, a/2) written as ⅜, which turns the 4·ω̂ of the Cayley numerator
      into 3·ω̂ while the program's d stays 1 + a·a/4; one sign flipped in the quaternion product; p × R·ω
      replaced by R·ω × p in the adjoint) fails the `certify` stage, and no certificate file is written.
- [ ] Constructing `Evidence<Proof>` outside `frob-lemma` fails to compile (the compile-fail case
      `construct_proved_outside_lemma`), and so does building the struct literally.
- [ ] A certificate placed beside a kernel with a different content hash is refused on load.
- [ ] Time and peak memory of each certification are recorded in the ledger.
- [ ] GATE-LEMMA-00 (TARGET, M0, claim Proof): T-01, T-03 and T-04 certified by FrankenSymPy for the M0 kernels;
      the offline replay half is closed by BD-027 and recorded by the end-to-end run N12-33.
- [ ] Closing rule: this bead closes on its own tests; the gate rows are written by the dependent end-to-end
      beads.

## Test plan

### Unit tests

`crates/frob-lemma/tests/` and `derive/frob-derive/tests/`; real FrankenSymPy, no mocks.
- `t01_identity_extracted_from_slp`: symbolic execution of `K-cay-step` yields N and D with NᵀN − D²·I equal to
  the zero polynomial in ten checked entries (nine plus the determinant).
- `t01_numeric_spot_check` (host arithmetic, exact rationals): Ω from ω = (1, 2, 3) gives D = 18 and
  NᵀN = 324·I.
- `t03_norm_multiplicative`: q = (1, 2, 3, 4), c = (2, −1, 0, 5): ‖q‖² = 30, ‖c‖² = 30, ‖q·c‖² = 900.
- `t03_extracted_from_cay_step`: symbolic execution of `K-cay-step` yields ‖q′‖² − ‖q‖²·d equal to the zero
  polynomial in (q, a); `t03_normalize_clause`: symbolic execution of `K-normalize` with the witness t yields
  (Σ outᵢ²)·t² − t² equal to zero modulo t² − n, with cofactor −1 recorded, and rejected when the relation is
  removed.
- `t04_composition_blocks`: the two block identities reduce to zero modulo the rotation relations with the
  recorded cofactors.
- `mutant_cayley_coefficient_fails`, `mutant_quaternion_sign_fails`, `mutant_adjoint_cross_order_fails`.
- `cert_binds_kernel_hash`: loading against another `KernelId` is refused.
- `evidence_class_is_certified_not_proved`: issued evidence has class `Certified`; no path yields `Proved`.
- Compile-fail cases under `crates/frob-lemma/tests/compile_fail/`, run by `cargo test -p frob-lemma --test
  compile_fail`: `construct_proved_outside_lemma.rs` (construction outside the crate, and the struct literal)
  and `set_class.rs` (a class setter). This bead writes the runner (`tests/compile_fail.rs`, trybuild-style:
  each case is a tiny crate that must fail to compile with the diagnostic recorded beside it) together with
  these cases, because its own acceptance needs them; the GATE-LEMMA-06 suite (N12-11) is built later on the
  same runner and directory and adds its further cases there, without a second runner or a second copy.

### End-to-end script and logging

`scripts/e2e/lemma_kernel_cert.sh` (bead N12-33) drives this bead from the user's side: it regenerates the M0
kernels, runs the certification stage, lists the cards with `frob prove list --json`, replays each certificate in
the standalone auditor and logs one `assert` line per identity with the certificate hash, the checker build and
the verdict, plus the three mutant rejections.

### Known answers and negative controls

KA-211 (T-01 for the M0 Cayley kernel: accept; one changed coefficient gives reject), KA-220 (T-01, T-03 and T-04
certified and replaying offline). CX-112: a kernel certificate does not show that the kernel's floating-point
output satisfies the identity; the test asserts that the certificate text says so and that the floating-point
residual is covered by a separate round-off test. Negative controls: the three coefficient mutants and the
wrong-hash certificate. Metamorphic relation: renaming the program's symbols leaves the verdict unchanged.
Determinism lanes: twice on one machine and on the two hosts give byte-identical certificate files.

## Considerations

- If FrankenSymPy cannot be consumed by path on the workspace toolchain (admission gate INT-FSYM-01), M0's
  posture is "CLI only; no kernel certificates" and GATE-LEMMA-00 is recorded `not run`, which is not a pass.
- RISK-07: expression swell. The M0 identities are tiny; the budgets recorded here are the baseline against
  which the M5 coverage gate (at least 80% of derived kernels) is planned. Kill gate named in advance:
  KILL-LEMMA (coverage below 50% after one repair cycle; fallback: exact-rational randomized identity tests
  recorded as `Tested`, and the word "certificate" removed from kernel manifests).
- The doorway mechanism depends on the workspace lint table; a crate that opts out of workspace lints would
  bypass it, so the lint-table doorway scan of `xtask check-unsafe` (N34-07, a dependency: it fails when a crate
  opts out of workspace lints or when a second `allow(deprecated)` on the Proof doorway appears) is part of the
  mechanism, not an extra.
- The value of a certificate to a design decision is unproven (OPEN-LEMMA-5); nothing here is on the critical
  path of the simulator.
