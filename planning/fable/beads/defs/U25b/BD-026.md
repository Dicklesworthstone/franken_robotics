## Background

FrankenRobotics answers design questions with certificates: a kernel carries a certificate of an algebraic identity,
and a mission query (a question about a whole family of robot designs) returns cells of designs that provably work
or provably cannot work. Every such certificate travels in a `.frobcert` bundle and is re-checked by an independent
auditor before anyone relies on it. This bead builds the ground the auditor stands on: the crate `frob-cert`
(layer 6, subsystem Lemma) and its binary `frob-verify`, written against the Rust standard library and nothing
else. Tier: Solid.

Why a separate, dependency-free crate (DESIGN, with its reasons):

- ADR-WS-02: `frob-cert` and its binary depend on the standard library and on nothing else, and no proposer
  depends on them. A certificate is only as good as the independence of what checks it. If the checker shares a
  parser, a hash implementation, an arithmetic library or a units crate with the code that produced the bundle, one
  defect can make both agree.
- ADR-LEMMA-03: one portable bundle format and one auditor built from the standard library only, because a positive
  or negative answer must be readable on a machine that has neither the agent, a GPU nor the simulator.
- ADR-AUGUR-04 and ADR-AUGUR-05: a proposer may use single precision on a GPU, a floating-point solver, a learned
  heuristic or an agent's guess, and nothing it says is believed; a cell changes status only when the checker
  accepts a certificate, on the CPU, in exact or outward-rounded arithmetic. The checker shares no code with the
  proposer: a Monte Carlo run and a solver that share one mistranslated model agree on the wrong answer.

Rejected alternatives. (1) Reuse `frob-core`'s hashing and canonical JSON in the checker. Counterexample: a
canonicalization defect in `frob-core` that drops a field before hashing would be reproduced by the checker, and a
bundle whose statement differs from the one the proposer evaluated would pass; with two implementations the hashes
disagree and the bundle is rejected. (2) Link a published big-number or JSON crate: the dependency count must be
zero, and JSON library features unify across a build graph (the `preserve_order` and `arbitrary_precision`
features of `serde_json` are enabled by sibling projects and would change how maps and numbers are read). (3) Build
the auditor on the workspace nightly: the workspace toolchain T is a nightly coupled to sibling projects; the
auditor carries its own stable toolchain file so that a copy of its directory builds anywhere.

This is the M0 floor. The proof-kind registry, the bundle schema, the per-kind checkers and the report contract are
separate beads that build on it (keys in `needs` and `related`).

## Technical approach

Layout (DESIGN):

```
crates/frob-cert/
  Cargo.toml             # [dependencies] empty; no `workspace = true` key anywhere; edition and version literal
  rust-toolchain.toml    # one stable release (OPEN-WS-3: the newest stable on the day of the first commit,
                         # moved afterwards only by ADR)
  CONTRACT.md            # ten sections: purpose, inputs, outputs, invariants, refusals, determinism class,
                         # evidence class of outputs, validity domain, oracles, known gaps
  src/lib.rs             # #![forbid(unsafe_code)]
  src/json.rs  src/blake3.rs  src/bigint.rs  src/rational.rs  src/interval.rs  src/limits.rs
  src/bin/frob-verify.rs
  tests/
```

The code compiles on the named stable release (a copy of the directory alone, `cargo build --release --offline`)
and on the workspace toolchain T (as a member). It therefore uses stable language features only.

1. Canonical JSON reader (`json.rs`). Input is UTF-8 without a byte-order mark. The reader builds a value tree of
   `Null | Bool | Int(i64) | Str | Arr | Obj(ordered pairs)` and enforces, in this order:
   a. grammar; depth at most 64 and file size at most 64 MiB (DESIGN limits, reported with rule `limits.exceeded`);
   b. member names compared after escape decoding at every nesting level; a repeated name is refused (smallest
      case: `{"wheel_radius_mm": 60, "wheel_radius_mm": 75}`: a first-wins reader and a last-wins reader would
      audit two different bundles with one hash);
   c. numbers: only integers with magnitude at most 2⁵³ − 1, no leading zero, no fraction, no exponent. Every exact
      quantity in a bundle travels as a string; a JSON number with a fraction or an exponent is refused
      (`num.float-in-bundle`), so no verdict depends on a float parser;
   d. canonicity: keys in ascending Unicode code-point order (equal to byte order in UTF-8), no insignificant
      white space, minimal string escapes (`\"`, `\\`, and `\u00XX` in lower-case hexadecimal for code points
      below 32; nothing else escaped). The check is "re-serialize and compare bytes", so the re-serializer is the
      same code path and re-serializing an accepted bundle returns identical bytes.
2. Exact numbers from strings. Integer: optional `-`, digits, no leading zero, `-0` refused. Rational, two
   encodings the formats use: a pair of integer strings `["p", "q"]` (the bundle container) and a slash string
   `"p/q"` with `"p"` alone for a whole number (the embedded `.fmission` statement). Both require q > 0 and
   gcd(|p|, q) = 1; a non-reduced or negative-denominator rational is refused (`num.rational-form`,
   FROB-REF-849: certificate arithmetic is malformed; repairs: re-encode; or split the cell). This is the
   reader's half of ADR-AUGUR-11: a mission statement is canonical JSON with exact numbers as strings, its
   identity is the BLAKE3 hash of the canonical bytes, and integers above 2⁵³ never travel as JSON numbers.
3. BLAKE3 (`blake3.rs`): the portable reference construction (7-round compression, 1,024-byte chunks, binary tree,
   root output), with the plain hash, keyed hash and derive-key modes and arbitrary output length. Identities in
   this project are BLAKE3 of canonical bytes under a domain string equal to the schema name (DESIGN: derive-key
   mode with the schema name as the context string; the convention is fixed by `frob-core`, and the two
   implementations are compared on a golden corpus by the conformance crate).
4. Integers (`bigint.rs`): sign and magnitude, little-endian `u32` limbs. Operations: comparison, addition,
   subtraction, schoolbook multiplication, division with remainder (Knuth's algorithm D), greatest common divisor,
   small powers, decimal parse and print. No operation allocates beyond the declared limit: an operand or result
   above 16,384 bits (DESIGN default) returns `limits.exceeded`. A certificate beyond the limits is refused, never
   approximated.
5. Rationals (`rational.rs`): a reduced pair with positive denominator; addition, subtraction, multiplication,
   division, negation, sign, comparison by cross-multiplication. No floating point appears anywhere in the crate.
6. Intervals (`interval.rs`): endpoints are dyadic numbers m·2⁻ᵖ with integer m and a precision p declared by the
   bundle ("outward-rounded intervals with a declared implementation and precision"; the implementation name is
   `frob-cert/dyadic-1`). Every operation computes the exact rational bounds of the result and then moves the lower
   end down and the upper end up to the grid (floor and ceiling), so each operation widens by at most one unit in
   the last place per side and never narrows. Operations at M0: addition, subtraction, multiplication (four
   products), division by an interval that excludes zero, integer powers (even powers of an interval containing
   zero start at 0), square root by integer square root with outward rounding, absolute value, minimum, maximum.
   An expression node outside this set makes a checker return `unsupported`, not a guess.
7. `limits.rs`: one compiled table (bits per integer 16,384; numeric entries per payload 10⁶; nesting 64; file
   size 64 MiB), printed in every report so that a rejection for size can be reproduced.
8. `frob-verify` (`src/bin/frob-verify.rs`): reads only the files named on its command line, reads no environment
   variable, opens no socket, spawns no process, writes only to standard output and to an explicit
   `--reserialize` path. At M0 it parses, checks canonicity and hashes, dispatches on the proof kind (unknown kind:
   reject) and prints the verdict `accept`, `reject` or `unsupported` with the first failing rule. Determinism
   class D0: the same bytes give the same verdict and rule on every machine.

Evidence: the auditor produces verdicts, not claims; the class of an accepted bundle is the class the bundle
states, capped by its kind. Its trusted base, stated in every report, is the binary, the Rust standard library and
the compiler.

## Acceptance criteria

- [ ] `cargo tree -p frob-cert` prints one line; `crates/frob-cert/Cargo.toml` has an empty `[dependencies]` table,
      no dev-dependency outside the standard library, and no key inherited from the workspace.
- [ ] A copy of `crates/frob-cert/` alone builds with `cargo build --release --offline` on the stable release its
      toolchain file names; the same sources build as a workspace member on T.
- [ ] `#![forbid(unsafe_code)]` at the crate root; no use of `std::env`, `std::net` or `std::process::Command`
      (a source scan in the crate's own tests).
- [ ] BLAKE3 matches every published test vector (all input lengths of the official vector file, in hash, keyed
      and derive-key modes, including extended output).
- [ ] GATE-WS-03, M0 clauses (TARGET; claim Known answer): dependency count zero; the copied directory builds
      with no network access; a system-call trace of an audit shows no socket and no child process. The fourth
      clause (the standalone binary and the in-daemon verb return identical verdicts on the whole conformance
      corpus) is measured at M1 when that corpus exists; the gate's row stays `not run` until then.
- [ ] PO-AUGUR-02 (the checker's big-integer and rational arithmetic is exact): an in-crate differential test
      against a second, independently written schoolbook implementation in the test module agrees on 10⁶ seeded
      random operations and on every number in the fixture certificates.
- [ ] PO-AUGUR-03 (the interval arithmetic is outward-rounded using the standard library only): a property test
      shows that for random rational inputs inside the operand intervals the exact rational result lies inside the
      computed enclosure, for every operation, and that each side is within one grid unit of the exact bound.
- [ ] Negative controls caught: a build with key-order checking disabled accepts `{"b":1,"a":2}` and fails the
      canonicity test; a build whose interval multiply rounds to nearest fails the enclosure property; a
      first-wins duplicate-key reader fails the duplicate test.
- [ ] `CONTRACT.md` exists with its ten sections; determinism class D0 is stated.
- [ ] Closing rule: this bead closes on its own tests and the M0 clauses above; the gate record is written by the
      end-to-end run of N25b-05.

## Test plan

### Unit tests

In `crates/frob-cert/tests/` and inline modules; no mocks; fixtures are files on disk.
- `json_duplicate_key_refused`: the wheel-radius object above is refused; `{"a":1,"a":2}` is refused (equal
  after escape decoding).
- `json_canonical_roundtrip`: `{"a":2,"b":1}` re-serializes to identical bytes; `{"b":1,"a":2}`, `{ "a":2 }` and
  `{"a":2.0}` are refused with rules `json.key-order`, `json.whitespace` and `num.float-in-bundle`.
- `json_integer_bounds`: 9007199254740991 accepted; 9007199254740992 as a number refused; the same value as a
  string parses to a big integer.
- `rational_forms`: `["3","14"]` accepted; `["6","28"]`, `["3","-14"]`, `"6/28"`, `"3/1"` and `"-0"` refused;
  `"14/3"` and `"3"` accepted.
- `blake3_empty`: the hash of the empty input is
  `af1349b9f5f9a1a6a0404dea36dcc9499bcb25c9adc112b7cc9a93cae41f3262`; `blake3_vectors` runs the official vector
  file checked in under `tests/vectors/`.
- `bigint_divrem_identity` (property): a = q·b + r with 0 ≤ r < |b| for random operands up to 4,096 bits;
  `bigint_limit`: a product above the bit limit returns `limits.exceeded`.
- `rational_field_laws` (property): associativity, distributivity and a·(1/a) = 1 on random rationals;
  `rational_order`: 14/3 < 5, 841/800 > 1, 165 > 160.
- `interval_encloses_exact` (property, PO-AUGUR-03) and `interval_width_one_ulp`.
- `interval_stance_dual`: with v ∈ [14/3, 6] at precision 2⁻⁴⁰ the enclosure of 90 + 15·v − 160 has lower end at
  most 0 (the value is exactly 0 at v = 14/3), so "fails over the closed cell" is not provable and "fails" is
  provable on [47/10, 6], where the lower end is 1/2.
- `verify_reads_only_named_files`: run under a temporary directory with an unreadable sibling file; the audit
  succeeds.

### End-to-end script and logging

`scripts/e2e/auditor_independence.sh` (bead N25b-05) drives this bead from the user's side: it copies the crate
directory, builds it offline on the stable toolchain, runs `frob-verify` with a cleared environment under a
system-call trace, and logs one `assert` line per clause with the measured value (dependency count, sockets
opened, child processes) against its threshold of zero.

### Known answers and negative controls

KA-223 (the auditor's BLAKE3 equals the published vectors), KA-222 (re-serializing gives identical bytes). The
format-registry known answer: `{"b":1,"a":2}` and `{"a":2,"b":1}` have one identity, and only the second is
canonical. Counterexamples protected: "reuse the proposer's hashing in the checker" (the dropped-field case
above); "hash the file as written" (two files that differ in key order would be two bundles). Metamorphic
relation: parse, re-serialize, parse again gives an equal tree and equal bytes. Determinism lanes: twice on one
machine; debug and release; the Mac and the Linux host; all give identical verdicts and digests (class D0).

## Considerations

- RISK-36 (the proposer and the checker share a defect; severity High) is the risk this bead exists to prevent.
  Nothing in this crate may be copied from `frob-core`, `frob-lemma`, `frob-mission` or any sibling library.
- The auditor's size is capped at 12,000 lines (TARGET) so that a person can read it; the arithmetic here should
  stay near 2,500 lines. Karatsuba multiplication and faster division are not built unless a certificate's check
  time breaches its budget.
- OPEN-WS-3 (which stable release the toolchain file names; owner: Lemma lead): default the newest stable on the
  day of the first commit, then moved only by ADR.
- The auditor does not model floating point; kernel certificates are about programs over ℚ with square roots.
- Performance envelope: every certificate of the first mission slice must check in under 10 s in total on a host
  with no GPU (the threshold of a later gate), so no operation may be quadratic in file size.
- Transcendental functions are not in the interval set at M0. A constraint that needs them is rewritten by the
  producer in polynomial form (for example with cosine and sine as variables tied by c² + s² = 1) or the checker
  answers `unsupported`.
