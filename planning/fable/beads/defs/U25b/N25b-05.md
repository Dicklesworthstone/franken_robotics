## Background

The offline auditor `frob-verify` is the one program whose word turns a proposal into `Certified` evidence. Its
independence is a structural claim (ADR-WS-02): the crate `frob-cert` and its binary depend on the Rust standard
library and on nothing else, and no proposer depends on them. If the checker shared a parser, a hash
implementation or an arithmetic library with the code that produced a bundle, one defect could make both agree.

GATE-WS-03 (claim Known answer; due at M1 in the gate register) states what must be measured: the dependency
count of `frob-cert` is zero; the copied directory builds on its stable compiler with no network access; the
standalone binary and the in-daemon verb return identical verdicts on the whole conformance corpus; and a
system-call trace of an audit shows no network and no process creation. Three of the four clauses can be
measured at M0, as soon as the crate exists, and the seed work for the crate asks for exactly those. This bead is
the end-to-end script that measures them from the outside, the way a third party holding only the crate
directory would, and the assembler of the gate's receipt. The fourth clause is N12-34's result, an M1 bead that
this M0 bead cannot wait on, so the M1 run of this script with all four clauses and the recording of the gate's
one part (M1) are N25bp4-01's, which depends on this bead and on N12-34. Tier: Solid.

It also demonstrates INV-AUGUR-08 (a `.frobcert` family payload is self-contained: checking needs no network, no
GPU, no simulator and no producer) and INV-WS-02 (`frob-cert` has no dependency and no proposer depends on it).

## Scope

In: `scripts/e2e/auditor_independence.sh`; its two host profiles (Linux and macOS); the fixtures it audits; its
self-test, including the third plant of CX-362 (`shared-canonicalizer-drops-field`, N34-CX); the assembler of
the receipt from which GATE-WS-03 is recorded, built from the gate's four clauses (three measured at M0, the
fourth read when it exists; this script is the gate's one measuring script), with the conditions under which
the row may read `pass`. Out: the M1 run with the fourth clause and the gate's record (N25bp4-01).
Out, with the bead that has it: the every-commit guard (N34-25, a dependency of this bead): the auditor rules of
`cargo xtask check-deps`, the shared-source scan, and clause (a) of the gate as a fact of the check's report.
This script runs that check as one of its steps and reads its facts; N34-25 writes no gate row. Also out: the
crate under test (BD-026) and the checkers (BD-027, BD-132); the corpus-wide verdict comparison, which another
script performs and whose result this script reads at M1 (N12-34).

## Technical approach

The script is plain shell (`set -euo pipefail`), sources the shared end-to-end helper, is idempotent and writes
only under `target/`. Steps:

1. `start`: record commit, the stable release named in `crates/frob-cert/rust-toolchain.toml`, host fingerprint.
2. Dependency count. Run `cargo tree -p frob-cert --edges normal,build,dev` in the workspace; assert exactly one
   line. Parse `crates/frob-cert/Cargo.toml`; assert the `[dependencies]`, `[build-dependencies]` and
   `[dev-dependencies]` tables are empty or absent and that no key is inherited from the workspace.
3. Reverse edges. Run `cargo tree -i frob-cert`; assert that the only dependents are `frob-verbs`, `frob-cli`
   and `frob-conformance` (rule L-9: no crate that produces a claim or a certificate depends on the auditor).
3a. The every-commit guard. Run `cargo xtask check-deps --json` (the auditor rules of N34-25) and assert its
   auditor facts: dependency count 0, a stable channel named in the crate's toolchain file, zero shared-source
   findings, no finding of any `cert.*` rule. The dependency count from this report and the one counted in step
   2 must agree; both are logged as the gate's clause (a).
4. Copy and offline build. Copy `crates/frob-cert/` alone into a fresh temporary directory outside the
   repository. Build there with `cargo build --release --offline` on the toolchain its own file names, with the
   network unreachable (Linux: inside an empty network namespace with `unshare -n`; macOS: under a sandbox
   profile that denies all network operations). Assert success and record the binary's digest and size.
5. Empty-environment audit. Run the copied binary with `env -i` on each fixture bundle: the three M0 kernel
   bundles (expected `accept`) and three mutants (one changed coefficient, a flag set to `true`, an unknown
   kind; expected `reject`). Assert the verdicts and the exit codes.
6. System-call trace. Linux: run step 5 under `strace -f -e trace=network,process` and assert zero `socket`,
   `connect`, `bind`, `sendto` and `recvfrom` calls and zero `clone`, `fork`, `vfork` and `execve` calls after
   the initial program start. macOS: run step 5 under a sandbox profile that denies `network*`, `process-fork`
   and `process-exec`, and assert the audit still completes with the same verdicts (a deny profile that does not
   change the outcome shows that neither was needed).
7. File access. Linux: from the same trace, assert every `openat` path is either a file named on the command
   line or a system library path; assert no environment variable was read (the run is under `env -i`, and a
   source scan asserts `std::env` does not appear in the crate).
8. Read-only inputs. Make the fixture directory read-only and repeat one audit; assert success (the auditor
   writes nothing unless `--reserialize` names an output).
9. Fourth clause, a stage. When the recorded result of the corpus-wide comparison exists (N12-34, M1, which is
   not a dependency of this bead: identical verdicts from the standalone binary and the in-tree verb on every
   specimen and mutant), read it and include it as the fourth clause; when it does not, write the clause as
   `not run`. This bead's own runs are at M0, where it is `not run`; the run at M1 is N25bp4-01's.
10. `summary` and receipt: measured values against thresholds (dependencies: 0 against 0; sockets: 0 against
    0; child processes: 0 against 0; offline build: success), the binary digest, and the status of the fourth
    clause, written as one hash-named receipt. The script writes no gate row: GATE-WS-03, whose one part is due
    at M1, is recorded from an M1 receipt by N25bp4-01 with `cargo run -p frob-conformance --example record_gate
    -- --gate GATE-WS-03 --receipt <hash> --part M1` (N38b-19), in a session that implemented none of the four
    clauses. The four clauses: (a) the
    dependency count of `frob-cert` is zero (steps 2 and 3a); (b) the copied directory builds on its stable
    compiler with no network access (step 4); (c) the standalone binary and the in-daemon verb return identical
    verdicts on the whole conformance corpus (step 9, from N12-34, at M1); (d) a system-call trace of an audit
    shows no network and no process creation (step 6). At M0 the receipt carries the three measured clauses and
    its line for the gate is `not-eligible` with the missing clause named, so the recorder writes nothing
    (N38b-19, step 3) and the part stays `not-run` (printed "not run" and shown as open, never as passed). At M1 it is `pass` only when
    all four clauses have measured values under the same resolution receipt, no clause was measured on a dirty
    tree, and the row is recorded by a session that implemented none of the four; otherwise `fail` with the
    failing clause, or still `not-run` with the missing clause named. The script refuses to assemble a receipt
    from clauses of different resolution receipts or from a dirty tree, so the recorder never sees one. DESIGN:
    one assembler of the clauses, one recorder of the row (N38b-19) and one status word before completion (an
    earlier draft of the check-deps bead also assembled the row and called the interim state `open`; `not-run`
    is the register's status and "open" is how it is displayed).

Logging: newline-delimited JSON at `target/e2e-logs/auditor_independence/<utc-timestamp>.ndjson` with a
human-readable transcript beside it. Every line has `ts`, `script`, `bead` (`N25b-05`), `step`, `event`
(`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code and wall time; for the
audits, the verdict, the first failing rule and the bundle digest; for the trace, the counts per system call;
on failure the first offending system call with its arguments and the path of the saved trace file. The
auditor's output carries no envelope, so the evidence block is recorded as "auditor verdict; class as stated by
the bundle". A final `summary` line gives assertions passed and failed and the gate touched.

## Acceptance criteria

- [ ] The script exits 0 on a clean checkout on the Linux host and on the Mac, and non-zero if any assertion
      fails.
- [ ] `cargo tree -p frob-cert` prints one line (the seed's wording), and the reverse-edge list contains only the
      three permitted crates.
- [ ] The copied directory builds with no network access on its stable compiler.
- [ ] The system-call trace of an audit shows no socket and no child process (Linux), and the deny-profile run
      completes with identical verdicts (macOS).
- [ ] At M0 the receipt carries the measured values of clauses (a), (b) and (d) and the fourth clause as
      `not run`; its gate line is `not-eligible` naming clause (c), and the part of GATE-WS-03 stays `not-run`.
      The assembler implements the conditions of step 10 and refuses two planted inputs (one clause from another
      resolution receipt; one clause measured on a dirty tree). The M1 run and the record are N25bp4-01's.
- [ ] The check-deps step agrees with step 2 on a dependency count of 0 and reports no `cert.*` finding.
- [ ] The log validates against the shared log schema and ends with a `summary` line.
- [ ] Negative controls (the self-test): (a) a scratch copy of the crate with one added dependency makes step 2
      fail; (b) a scratch auditor that resolves a host name makes step 6 fail; (c) a scratch auditor that spawns
      a child process makes step 6 fail; (d) a scratch auditor that reads `HOME` is caught by the source scan;
      (e) `shared-canonicalizer-drops-field` (CX-362, plant 3, a registered `mutation` control seeded from N34-CX
      with gates GATE-WS-03 and GATE-AUGUR-06): a scratch auditor that hashes with `frob-core`'s canonical writer,
      built with the mutation that drops the `assumptions` field before hashing, and a producer built with the
      same mutation; the producer writes a bundle whose `assumptions` differ from those it evaluated, the scratch
      auditor accepts it (one shared defect, both sides agree) while the genuine copied auditor rejects it with a
      hash rule (two implementations disagree); the main script pointed at the scratch variant fails at step 2
      (the dependency on `frob-core`) and, run with that bundle among the step 5 fixtures, at step 5. Run at gate
      time, not on every commit (N34-CX: the defective shared canonicalizer is expensive to build).

## Test plan

### Unit tests

`scripts/e2e/tests/auditor_independence_selftest.sh` builds the five scratch variants above, (a) to (d) from
small patches kept under `scripts/e2e/tests/patches/` and (e) with the mutation's feature, and asserts that the
main script fails at the stated step for each, with the first offending value in the log; `--variant <name>`
runs one variant alone (BD-136 runs (e) at M1 under GATE-AUGUR-06). For (e) it also logs both verdicts on the
drifted bundle (scratch `accept`, genuine `reject` with its rule) and the two digests that disagree. The trace
parser has its own test on two recorded trace files (one clean, one with a `connect` call).

### End-to-end script and logging

This bead is the script; the steps and the logging are above. It is run at M0 after the crate lands; the run at
M1 with the fourth clause, and the gate's record, are N25bp4-01's; it runs at every later milestone exit as part
of the certifier self-tests.

### Known answers and negative controls

Known answer: `cargo tree -p frob-cert` prints one line. KA-223 (the auditor's BLAKE3 against the published
vectors) and KA-211 (the Cayley certificate: accept; one changed coefficient: reject) are exercised by the audits
of step 5; KA-214 (a flag set to true: reject) and KA-215 (an unknown kind with consistent hashes: reject) by
the mutants. Counterexample protected: CX-362, "reuse the proposer's hashing in the checker", where a
canonicalization defect that drops a field before hashing would be reproduced by the checker (its plants 1 and 2
are N34-25's on every commit; plant 3 is variant (e) here). Negative controls: the five scratch variants. Determinism lanes: the copied build's binary digest is recorded per host; verdicts are identical on
both hosts and in debug and release builds (class D0).

## Considerations

- The macOS half is weaker than the Linux half: a deny profile shows the audit does not need the network or a
  child, not that it never tried. The Linux trace is the record of the gate; the Mac run is supporting evidence.
- `strace` and network namespaces need no elevated rights on the Linux host for an unprivileged user namespace;
  if they are unavailable the step is recorded `not run`, which is not a pass.
- The script must not fetch a toolchain: the stable release named by the crate must already be installed, and a
  missing toolchain is a failed precondition reported before step 4.
- RISK-36 (the proposer and the checker share a defect) is the risk; the seeded-fault campaign and the
  shared-source-file check complement this script at M1.
