## Background

When the studio cannot decide, the honest output is a request for the measurement that would decide, not a
guess. `scene.probe-request` is that output for questions about a place. The verb registry lists it as a read
verb at M5: "the measurements that would settle an unresolved answer". Three situations produce a request:

- a clearance verdict is `unresolved` because of registration or scale uncertainty;
- the inner and outer answers of a mission query differ because of an unknown region;
- a decision reverses inside the interval of an `assumed` interface card.

The request names the three-dimensional box to rescan or the surface to probe, the quantity needed and the
accuracy that would settle the decision, for example "the clear width of door D3 to ±5 mm". The request is the
output; nothing is assumed in its place.

Why it sits with probe design: it is the scene-side twin of `mission.distinguish`. That verb designs an
instrument to separate mechanisms; this one names the survey that separates worlds. Both follow the same rule
(partition by the decision each possibility implies, and ask only for what can change the decision), and both
feed `experiment.suggest` as `measure` proposals. Materials are never inferred from appearance: an unprobed
surface carries a card of class `assumed` with a wide friction interval, and a request is the way to narrow it.

The verb lands at M5 with real-place ingestion. The request record it returns is produced earlier, inside
unresolved mission answers (as the `NeedsMeasurement` explanation), so authored scenes with `assumed` cards can
already yield requests through `mission.distinguish` and `experiment.suggest` at M3 and M4.

## Scope

In: the `ProbeRequest` record; the three triggers; the computation of the requested accuracy; the verb, its
envelope and its privacy handling; the hand-off from unresolved mission cells. Out: ingestion, scale labels and
the unknown mask themselves (BD-398 and the Habitat beads); clearance complexes (BD-233); the retrofit catalogue;
taking the measurement (the reality chapter).

## Technical approach

**Record (DESIGN).**

```rust
pub struct ProbeRequest {
    scene: SceneId,
    reason: ProbeReason,                 // RegistrationUncertainty | ScaleUncertainty | UnknownRegion | AssumedCardReversal
    region: Option<Box3>,                // box to rescan, in the scene's gravity frame, metres
    surface: Option<SurfaceRef>,         // surface to probe, for a card quantity
    quantity: QuantityRef,               // e.g. clear width of door D3; friction coefficient of floor patch F2
    unit: Unit,
    current: Interval,                   // what is known now
    thresholds: Vec<(Ratio, DecisionRef)>, // values at which a decision changes, and what changes
    accuracy: Ratio,                     // half-width that would settle the decision
    settles: Vec<VerdictRef>,            // the unresolved cells or verdicts this measurement would close
    text: String,                        // "the clear width of door D3 to ±5 mm"
}
```

**Algorithm.**

1. Collect the unresolved items for the scene: clearance verdicts whose inner and outer complexes disagree; cells
   of a mission answer whose inner and outer sets differ and whose explanation is `NeedsMeasurement` or names an
   unknown region; decisions that reverse inside an `assumed` card's interval.
2. For each, find the scene quantity the disagreement depends on (the actionable residual): the one width,
   height, gap or card field on which the two candidate answers differ. This is read from the dependency support
   of the two competing certificates or witnesses.
3. Compute the decision thresholds of that quantity inside its current interval: the values at which some cell
   changes verdict or some design ordering reverses.
4. Requested accuracy (DESIGN): with two or more thresholds inside the current interval, half the smallest gap
   between adjacent thresholds; with one threshold, the declared margin of the predicate that reads the
   quantity, or, if none is declared, one tenth of the current interval's width. The result is rounded down to
   the instrument ladder (1, 2, 5, 10, … in the quantity's unit) and capped by the current half-width. The
   request states that a reading within the accuracy of a threshold leaves that decision unresolved.
5. Locate the measurement: the bounding box of the unknown or uncertain geometry in the gravity frame, or the
   surface patch for a card quantity.
6. Merge requests that name the same quantity; order by the number of verdicts each would settle.

**Rules.** An unseen gap beneath a shelf has possible geometry, not assumed geometry: the request, not a default
value, is returned. A scene with scale label `relative-only` yields a scale request before any other. No
friction, compliance or optical value is estimated from an image.

**Surface.** `frob scene probe-request <scene> [--answer a:…] --json`. Kind `read`. The envelope's result is the
list of requests; evidence class is that of the inputs; `reality: no-claim`. For a private pack the result is
stored outside the repository and the envelope carries the privacy mark.

## Acceptance criteria

- [ ] The record type is defined once in `frob-core` and emitted by `frob-mission` (unresolved cells) and `frob-scene` (clearance, cards); the verb is in the registry at M5 with schema, examples and refusals.
- [ ] The doorway fixture returns one request: quantity "clear width of door D3", thresholds 800 mm and 812 mm, accuracy ±5 mm, with the box of the doorway.
- [ ] The friction fixture returns a request for the floor patch's friction coefficient with the reversal threshold.
- [ ] A scene with nothing unresolved returns an empty list with exit 0; a `relative-only` scene returns a scale request first.
- [ ] No value is assumed in place of a request: the mission answer keeps the cell unresolved until a measurement is admitted.
- [ ] Logs and envelopes for a private pack contain no private-scene data beyond identifiers.

## Test plan

### Unit tests

- `doorway_two_thresholds` (synthetic): door D3 clear width known to [795, 825] mm; design A needs at least
  812 mm, design B at least 800 mm. Thresholds 800 and 812; half the gap is 6 mm; ladder gives ±5 mm.
- `single_threshold_margin` (synthetic): a sill height known to [10, 16] mm with a crossing limit of 12 mm and
  a declared margin of 1 mm: accuracy ±1 mm.
- `single_threshold_no_margin`: the same without a margin: one tenth of 6 mm is 0.6 mm; ladder gives ±0.5 mm.
- `assumed_card_reversal` (synthetic): friction in [0.3, 0.9] on an `assumed` card; design ordering reverses at
  μ = 0.5: one request for the surface with threshold 0.5.
- `merge_same_quantity`: two unresolved cells that depend on the same door width produce one request listing
  both in `settles`.
- `unknown_region_box`: the request's box contains the unknown voxels and nothing beyond their bounding box
  plus the registered clearance.

### End-to-end script and logging

`scripts/e2e/scene_probe_request.sh`: builds the doorway scene with an uncertain width, runs `frob mission
synthesize carrier.fmission --json` (two designs, the door in the route), then `frob scene probe-request
<scene> --answer <a> --json`, then admits a measurement of 806 mm ± 5 mm through the scene edit verbs and
re-runs the query. It asserts: one request with the values above; after the measurement, design B is inner and
design A excluded; no private data in the log. It sources the shared end-to-end helper and writes NDJSON to
`target/e2e-logs/scene_probe_request/<utc>.ndjson`: `ts`, `script`, `bead`, `step`, `event`, the exact command,
exit code, wall time, the evidence block, the request's quantity, thresholds and accuracy against expected
values, answer digests before and after, and the first differing field on failure. The summary line counts
assertions; no gate is attached.

### Known answers and negative controls

- Known answers: the four synthetic fixtures above (±5 mm; ±1 mm; ±0.5 mm; threshold 0.5).
- Negative control: a mutant that fills the unknown door width with the interval's midpoint (810 mm) and returns
  a verdict instead of a request must be caught: the mission answer would then wrongly exclude design A or admit
  it without a measurement.
- Negative control: a request that names a quantity on which the competing answers do not differ (a different
  door) is rejected by the dependency-support check.
- Determinism: the request list is a deterministic function of the scene and the answer.

## Considerations

- The accuracy rule is a DESIGN default; the plan gives the example, not a formula. If field use shows it asks
  for too much or too little, the rule changes by an amendment to the verb's contract.
- A request can be unanswerable on site (the gap really is inaccessible). Then the cell stays unresolved and the
  mission carries the uncertainty; the retrofit catalogue may offer an edit that removes the dependence.
- Upstream: if the twin package lacks the landmarks or scale witness the import needs, the first deliverable is
  an upstream work item, and this verb serves authored scenes only.
