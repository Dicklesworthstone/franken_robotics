## Background

Product-system dominance (BD-359) compares two robots under "the same" world. What "the same" means is the
substance of the mechanism. Two tyres following different paths over the same floor need not receive equal
friction samples at corresponding ticks. The product uses one space-indexed material field and each robot's
actual contact point. Shared latent lighting produces different sensor residuals once the cameras diverge.

This is where the product differs from pairing episodes by world address, which the comparison studies use:
pairing by address shares seeds, and a seed indexed by tick is not a field indexed by position. A product coupled
by tick and not by position reports a false regression or hides a true one.

It is also the part of the mechanism that survives the kill gate. The fallback of KILL-AUGUR-DOMINANCE reads:
paired comparison by replay under the comparison studies; the product lowering is kept only as the rule for
space-indexed shared inputs. So this bead must stand on its own: a lowering rule that any paired comparison of
two bodies can use, with or without box closure.

## Scope

In: the taxonomy of shared inputs and their index; compilation of a space-indexed field read at each robot's
contact point; shared latent states seen through each robot's own sensors; the projection check and the
common-variable check; domain splitting at mode transitions; the replay route for unenclosable branches; the use
of the rule by paired replay. Out: box closure and proof objects (BD-359); the gate script (N25c-26); the scene
and card formats that hold the fields; the paired study machinery itself.

## Technical approach

**Shared-input taxonomy (DESIGN).**

```rust
pub enum SharedInput {
    SpaceField { quantity: QuantityRef, field: FieldRef },      // friction, compliance, height: indexed by position
    LatentState { quantity: QuantityRef, value: ParamRef },     // lighting state, payload mass, ambient temperature
    TimeProcess { quantity: QuantityRef, process: ProcessRef }, // an exogenous event at a physical time
    ClockLaw { law: ClockRef },                                 // controller and sensor timing, shared by declaration
}
```

Every disturbance of the comparison is declared as one of these (coupled) or as independent (duplicated, one copy
per robot). Nothing is coupled by default.

**Compilation rules.**

1. *Space-indexed fields.* One field instance exists in the product. Each robot's contact kernel evaluates it at
   that robot's actual contact point at the instant of contact. A random field is realized by address: its value
   in a position cell is a function of the scene identity and the cell, so both robots read the same value at
   the same place whatever their ticks, batches or slots.
2. *Latent states.* One variable exists in the product; each robot's sensor model maps it through that robot's
   own pose and optics. Two cameras see one lighting state and produce different residuals once they diverge.
3. *Time processes.* Indexed by physical time, not by step count: two robots with different step sizes or event
   times see the same process value at the same instant.
4. *Clock law.* Shared by declaration: both closed loops obey the same schedule definition, each with its own
   packet queues.
5. *Independent inputs.* Duplicated; every combination of their values is retained in a worst-case assertion.

**Checks (run by the checker on the proof object's primitive equations).**

- *Projection.* Each projection of the product solves its original plant: deleting B's state and equations
  leaves exactly A's plant under the same inputs, and conversely. Tested operationally by digest equality between
  a projected product run and a solo run of that robot on the same world.
- *Common variables.* The declared shared inputs are literally one variable each in the product's equations (not
  two copies constrained to be equal after the fact), and they express the requested physical comparison: a
  field declared shared is indexed by position in both robots' contact equations.

**Splitting and replay.** The initial domain is split where a mode transition could break relational invariance:
at parameter values where either robot's contact point crosses a boundary of the field, or where either robot's
branch set changes. A numerical branch that cannot be enclosed goes to per-case replay, where both robots are run
on the same compiled world.

**Use by paired replay.** The comparison studies pair episodes by world address. When the two designs differ in
body, the address must resolve to a compiled world whose shared inputs follow the rules above. This bead exports
that resolution as a library call used by the paired-study planner: given a world address and two designs,
return one compiled world with the shared inputs instantiated once.

**Evidence and determinism.** A compiled product world has an identity (a digest over the field identities, the
latent values and the clock law). Results on it follow the tier's determinism class; the pairing itself is exact.

## Acceptance criteria

- [ ] Code in `crates/frob-mission` (`dominance/shared_inputs.rs`), with the library call used by the paired-study planner; `CONTRACT.md` states the four rules.
- [ ] The edge fixture reports the regression cell that tick pairing hides, with the exact label table and the 8% share.
- [ ] The false-regression fixture reports no regression under position indexing and a (1, 0) outcome under tick indexing (the planted defect).
- [ ] Projection digests equal solo-run digests for both robots on 1,000 random worlds.
- [ ] An undeclared disturbance is treated as independent, never as shared.
- [ ] A shared lighting state produces different residuals for two cameras at different poses and identical residuals at identical poses.

## Test plan

### Unit tests

- `edge_fixture_labels` (synthetic): friction μ₁ = 0.5 for x < x_e and μ₂ beyond; contact points 0.30 m (A,
  grip factor 1) and 0.34 m (B, grip factor 1.25); success when friction × factor ≥ 0.4. On
  x_e ∈ [0.25, 0.40] m, μ₂ ∈ [0.2, 0.6]: label (1, 0) exactly on 0.30 < x_e ≤ 0.34 and μ₂ < 0.32; shares
  (0, 0) 0.100, (0, 1) 0.0667, (1, 0) 0.080, (1, 1) 0.7533 under a uniform law.
- `tick_pairing_hides_regression`: with one friction sample per tick shared by both robots, (1, 0) is
  unreachable on the same fixture; the test asserts that the compiled product does not behave this way.
- `tick_pairing_false_regression` (synthetic): identical soles on the same path over one patch with friction
  0.5 everywhere; A reaches the patch at tick 4 and B at tick 5 because their step timing differs. A tick-indexed
  sample sequence (z₄ = 0.5, z₅ = 0.2) yields (1, 0); the position-indexed field yields (1, 1).
- `field_by_address`: the field value in a position cell is identical across batch slot, shard and tick.
- `latent_lighting`: one lighting value, two camera poses, two different residuals; equal poses, equal residuals.
- `projection_equals_solo`: digest equality for A and for B.
- `undeclared_is_independent`: an input with no declaration appears twice in the product.

### End-to-end script and logging

`scripts/e2e/mission_dominance.sh` (bead N25c-26) includes the edge fixture and the false-regression fixture:
it runs the dominance query, then replays draws for both designs on the compiled world and compares labels. It
logs the compiled world's identity, the shared inputs and their index kinds, per-draw labels under position
indexing, and, for the negative control build, the labels under tick indexing with the first differing draw.

### Known answers and negative controls

- Known answers: the edge fixture's table and shares; the false-regression fixture's (1, 1).
- Negative control (the planted defect): a build flag that indexes the shared field by tick must change the
  edge fixture's regression share from 0.080 to 0 and the false-regression fixture's label to (1, 0); both
  assertions must fail under that flag.
- Negative control: a product in which the shared field is two copies constrained equal only at ticks fails the
  common-variable check.
- Metamorphic: translating both robots and the field by the same offset leaves labels unchanged; changing either
  robot's step size leaves the field values it reads unchanged.

## Considerations

- A field is only as shared as its scene model says. If the scene carries friction as one scalar per world, the
  product degenerates to a latent state and position effects are invisible; the answer's assumptions say which.
- Real-place fields are private data and inherit the scene's mark.
- If the kill gate fires, this bead is what remains of the mechanism, used by paired replay.
