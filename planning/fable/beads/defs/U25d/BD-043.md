## Background

Before any FrankenRobotics code existed, a set of paper-scale pilots was run on the mission-query ideas of the
Augur subsystem (mission queries and inverse design: questions about a whole family of robot designs, answered
with an inner set I of designs proved to work, an outer set O outside which designs are proved not to work, and
unresolved cells between). The pilots are small Python programs on small models, with protocols frozen before
execution and independent rechecks. They live in one reproduction archive. Every number the plan quotes from them
is a FACT about a small program, not a measurement of this product. The program's hygiene rule is that such a
number becomes this repository's own only after it has been re-run here and recorded; until then no gate may cite
it (GATE-GAUNT-08: the plan-time pilots re-run at M0 and reproduce every count exactly and every timing ratio
inside its recorded band).

Two sibling seed beads re-run the docking pilot (BD-041) and the static stance pilot (BD-042). This bead re-runs
everything else in the Augur pilot table: nine groups. The device screen of 65,536 rows is re-run natively by the
exact-integer kernel probe (BD-030) and is out of scope here.

Why it matters beyond bookkeeping. One row is the origin of a program-wide rule. A specialized solver was timed
against a composed conventional one and came out 1.345 times faster warm and 1.088 times cold. An audit then showed
that 575.7 µs of each specialized batch is work the solver does not touch (parsing, assembly, checking,
serialization, harness), so a solver of zero cost could not have exceeded about 1.46. The speed test had no power.
Hence the rule "compute the ceiling before running a speed test" (ADR-GAUNT-05; the ceiling-before-speed check of
BD-354). This bead recomputes that ceiling on this machine before any speed figure is quoted anywhere.

What the pilots did not do is part of what must be recorded (four statements, carried verbatim in substance):
(1) none used FrankenSim dynamics, FrankenSim contact or a real sensor pipeline; (2) the integrated agent interface
(one scoped query returning checked inclusions, exclusions, unresolved cells and a distinguishing intervention)
remains a HYPOTHESIS: the pilots show individual witness types can be computed, none runs a combined interface,
certifies an acquired physical capability or measures authoring cost; (3) every pilot's strong baseline tied or
won (a lifted linear program tied the projection; a programmed expert tied the probe generator and direct
measurement beat both on the withheld law; exact Bayes tied the sensor calculation; a scenario tree tied docking;
a dependency graph tied the receipt; quantifier elimination produced the pusher answers), so what survives is an
interface and a discipline of counterexamples, which is why ADR-AUGUR-03 (conventional formulations first) and
ADR-AUGUR-09 (a rival's answer goes through the same checker) exist; (4) no physical claim follows: the material
laws are artificial, the loads stipulated, the plants scalar.

Rejected alternative: re-deriving the numbers by hand only (done for several values during planning) leaves the
bundle unexecuted in this repository; the rule asks for execution.

**The archive (FACT, observed 2026-11-22, to be re-observed).** The single `.zip` in
`/Users/jemanuel/projects/franken_robotics/planning/` is `astra-10x-reproduction.zip`. The plan's source register
records 241,568 bytes and SHA-256 `0326e89d76b88a2aa7d198d53556f80ab131fe5a902113dd37f7f32e93b09a4f`. The file on
disk at drafting time is 275,178 bytes with SHA-256
`9620da42ec82c175209bbcea21ec71d376da31b687f4f2729e36c20476cd7980`: a later revision (commit `47e8e89`, 179
entries). The recorded pair is the revision at commit `a635b91` (161 entries), recoverable with
`git show a635b91:planning/astra-10x-reproduction.zip`; every driver named in the table below is present in it
(FACT, re-observed at review). The rule is the one of the source record `SRC-REC-05` (NAB-15) and of BD-041 and
BD-042: a recorded value is compared with the output of the **cited** revision first; a run on the working-tree
revision is a second result. The archive carries its own `SHA256SUMS`, `README.md`, `verify.py`,
`verify_negative.py`.

**Procedure (numbered).**
1. Compute size and SHA-256 of the working-tree archive and of the cited revision (written by `git show` to a
   scratch file); record both and compare each with its recorded pair; a difference is written into the review
   log with both digests, never adjusted. If history is unavailable (a shallow clone), the cited-revision result
   is `not-run` with that reason and the working-tree result alone does not reproduce the record.
2. Extract each revision into a new empty directory `target/pilots/<first-16-hex-of-digest>/` (never inside the
   source tree; the archive is data, and nothing in it is imported by workspace code). Steps 3 to 6 run on the
   cited revision, whose output is compared with the recorded values, and again on the working-tree revision as a
   second result; if the two revisions print different output for one driver, the row is `differs` until the
   write-up explains it.
3. Record the interpreter and library versions. Recorded environment: CPython 3.15.0, NumPy 2.5.4, SciPy 1.18.1
   with its bundled HiGHS, Z3 4.15.4, arm64 macOS. Other environments may differ in last-place floating output;
   counts and rationals must not.
4. From the extraction root run `python3 -B verify.py` (standard library only), then `python3 -B verify.py --all`
   (needs NumPy, SciPy and `z3` on PATH), then `python3 -B verify_negative.py` (deliberate omissions, corrupted
   labels, a malformed controller witness, and the refusal of optimized Python: one `Rejected …` line per caught
   defect; the script raises on any accepted defect). The number of `Rejected` lines is counted and recorded, not
   assumed (a static reading of the source finds 29 call sites, three inside loops). Assertions stay enabled (no
   `-O`).
5. Run each row's own driver (table) and compare with the expected values. Counts, verdicts and rationals compare
   exactly. Printed decimals compare to the printed digits. Timing ratios compare against a band (step 7).
6. Recompute the pusher ceiling from this run's own medians (formula below).
7. Timing band (DESIGN, since the plan states no band): the band of a ratio is the minimum to maximum of the
   per-trial ratios in the original receipt (`pusher/PILOT_RUN.json`: nine warm and nine fresh-process pairs). A
   re-run median outside the band is recorded as a difference with both values; it does not fail the bead.
8. Append one result per row to its record in the plan-time pilot ledger (the `plan_time = true` block of the
   pilot register, owned by N38a-10): material probe `PILOT-PT-03`, pad family `-04`, sensor aliasing `-05`,
   pusher `-08`, pusher audit `-09`, labels and deadlines `-10`, decision reuse `-11`, shared bus `-12`, sill
   `-16`. The admission fixtures have no row among the ledger's twenty; their result is appended to the
   supplementary record `PILOT-PT-S3` (covers `SRC-CHK-13`), which N38a-10, a dependency of this bead, seeds.
   Each result carries, as the ledger requires, the commit, the hardware fingerprint, the seed, the archive
   revision (digest actually used), the command, the environment and the observed values; the ledger derives
   `reproduced` or `differs` from them (never this bead) and copies into the result the three common limits and
   the record's `limits_extra`, the fourth, Augur-specific limit (the integrated interface remains a HYPOTHESIS),
   which N38a-10 seeds on every record this bead appends to. This bead writes no limit text of its own (one stored
   text, so the registers cannot drift). Then write one entry into the review log (`docs/delivery/review-log.md`,
   the in-repository continuation of the plan's review record; DESIGN path).
9. Ten rows in nine groups: the pusher and its audit are one group with two records.
10. Counterexample re-run receipts. The sill row is the FACT source of three entries of the counterexample
    catalogue (`crates/frob-conformance/registry/counterexamples.toml`, N38b-05's schema), each written with
    `rerun = false` until this re-run: CX-195 (N19-CX: a static rejection settles whether a wheel can climb),
    CX-263 (N24-CX: the planar sill pilot of 156 rows) and CX-283 (N25-CX: a static rejection is a rejection).
    The sill result appended to `PILOT-PT-16` carries the register's `receipt = "blake3:…"`. When
    `pilots::rerun_status("PILOT-PT-16")` reads `reproduced` (7 pass both, 87 fail both, 62 static rejections
    succeed dynamically, of 156, on the cited revision), that receipt licenses the three entries: a recording
    session that did not perform the re-run sets `rerun = true` and `rerun_receipt = "<receipt hash>"` on each of
    the three that is present in the catalogue, changing no other field, and re-runs N38b-05's seeding tool
    (`cargo test -p frob-conformance --test seed_controls -- --ignored seed`), which turns their controls runnable
    under unchanged `NC-` numbers. The three registry beads belong to M1 and M2 and may write their entries after
    this bead closes; this bead does not wait on them: its review-log entry names the receipt hash and the three
    entry ids, and an entry written later carries `rerun = true` with the receipt of the `PILOT-PT-16` result
    (its writer's step). If the record reads `differs` or `not-run`, the three stay `rerun = false` (obligations
    that make no gate eligible) and the difference, with both values, is reported to N19-CX, N24-CX and N25-CX.

**The ceiling formula.** residual = (specialized full-batch median) − (specialized solve-only median);
ceiling = (composed full-batch median) ÷ residual. Recorded: 610.1 − 34.4 = 575.7 µs; 842.8 ÷ 575.7 ≈ 1.46;
solve-only ratio 189.0 ÷ 34.4 ≈ 5.49; cold ceiling about 1.0034 (the cold receipt of 1.088 is noise-dominated).
The re-run reports its own four medians, its own residual and ceiling, and the sentence "no solver could have
shown more than ⟨ceiling⟩ on this harness".

**The control of CX-283** (plant `BD-043:cx-283`, kind `mutation`, named by N25-CX; built under `--features
gauntlet-mutations` in `frob-conformance` only, never in a product binary; its per-control feature takes the
`NC-` number the seeding tool allocates when N25-CX's entry is seeded, BD-025). The sill comparison reads the
driver's 156 cases as pairs (static verdict, dynamic outcome) and derives the four counts from the pairs. The plant
takes a static rejection as final: every statically rejected case's dynamic outcome is replaced by `fail`. The
counts then read 7 pass both, 149 fail both, 156 agree and 0 static rejections that succeed dynamically, so the
sill row must report `differs` with first differing value `fail both: expected 87, observed 149`. When the plant
is built, the entry's `plant` is completed with the code path and the feature (the CX number and every other
field unchanged).

Determinism: counts and rationals are class D0 (exact); timings are host-dependent and carry the disclosure of
host, load and repetitions. Evidence class of the record: `Tested`, tier `paper-scale`, marked `synthetic`
(artificial laws, scalar plants). No output of this bead supports a product claim.

## Test plan

### Unit tests

`crates/frob-conformance/tests/pilots_rerun.rs` (no mocks; reads the real outputs of the re-run):
- `expectations_table_is_complete`: ten rows, each with path, command, comparison kind and expected value.
- `compare_exact_counts`: 675/675, 0/225, 900/900, 20/20, 6/6, 94/156, 7, 87, 62 are compared as integers, and the
  sill identity 7 + 87 + 62 = 156 holds on the observed pairs.
- `compare_rationals`: 27/32, 459/512, 3807/4096, 9/10, 16/5, 3/32, 7/32, 11/32 are compared as reduced pairs.
- `ceiling_formula`: inputs 610.1, 34.4, 842.8 give residual 575.7 and ceiling 1.4640 (to four digits).
- `band_from_receipt`: the band of the warm ratio is the min and max of the nine recorded pairs.
- `differs_is_reported`: an expected 676/675 yields `differs`, not a pass.
- `rows_map_to_ledger`: the ten rows map to `PILOT-PT-03`, `-04`, `-05`, `-08`, `-09`, `-10`, `-11`, `-12`, `-16`
  and the admission-fixtures record `PILOT-PT-S3`, each once; a result appended without commit, fingerprint, seed or digest is
  rejected by the ledger's check.
- `fourth_limit_present`: every result appended by this bead carries the record's `limits_extra` (the
  integrated-interface HYPOTHESIS), equal to N38a-10's stored text, and no limit text of the bead's own.
- `sill_receipt_licenses_entries`: on a scratch copy of the catalogue holding CX-195, CX-263 and CX-283 with
  `rerun = false`, a `reproduced` `PILOT-PT-16` result sets the three to `rerun = true` with its receipt hash and
  changes no other field; with the record `differs` the three stay `rerun = false`; a scratch entry with
  `rerun = true` and no `rerun_receipt` is refused by N38b-05's loader.
- `cx283_static_rejection_taken_as_final_is_caught`: under the plant, the sill counts read 7, 149, 156 and 0 and
  the row reports `differs` with first differing value 87 → 149; without it, 7, 87, 94 and 62.

### End-to-end script and logging

`scripts/e2e/pilots_rerun_augur.sh`: performs steps 1 to 10, sources the shared logging helper and writes
`target/e2e-logs/pilots_rerun_augur/<utc>.ndjson` with one `cmd` line per driver (command, exit code, wall time),
one `assert` line per expected value (expected, observed, comparison kind), `metric` lines for the four medians,
the residual and the ceiling (µs, with the band), the digest and revision of each archive run (the cited
`a635b91` first, then the working tree), and a `summary` with assertions passed and
failed, the counts reproduced and differing, and the gate touched (GATE-GAUNT-08). Every line carries `ts`,
`script`, `bead = BD-043`, `step` (the procedure step number) and `event`. On a difference the `assert` line holds
the first differing value (expected, observed, comparison kind), the archive member path, the extraction
directory and the exact command that reproduces it. The interpreter and library versions and the host
fingerprint are logged once at `start`. The script then runs `cargo test -p frob-conformance --test
pilots_rerun` against the appended results and logs its outcome, and logs at step 10 the sill receipt hash and,
for each of CX-195, CX-263 and CX-283, one line with its state (`set`, `absent: written later by <registry bead>`
or `left false: <derived status>`). The script is idempotent (a second run on the
same digest appends nothing new and logs `unchanged`) and exits non-zero only on a harness error or an
unrecorded difference.
