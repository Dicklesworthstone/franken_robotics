## Background

Augur is the subsystem for mission queries: questions about a whole family of robot designs, answered with an
inner set of designs proved to work, an outer set outside which designs are proved not to work, and unresolved
cells between, with certificates an independent checker accepts. It is the most speculative part of the
program's case for an order-of-magnitude faster design loop, and every plan-time pilot of it ended in a tie
with a conventional method. So its delivery is ordered by one aim: **find the first class of amended
engineering decisions where the whole workflow can be an order of magnitude faster, starting where correctness
is independently decidable, and extending to high-dimensional contact, vision and learning only after a cost
has been located that survives strong baselines.**

The order is a sequence of five working slices. Each has evidence that buys the next investment and a decision,
fixed in advance, for the case where its test fails. Those decisions are not kill gates of single mechanisms;
they redirect the chapter. They need a home where they cannot be forgotten: a register that the milestone exit
reviews read.

The same section fixes how Augur's capabilities may be described at release: **a release cell names its
capability and its limit**, for example "exact static family with independent active vertical reactions",
"time-bounded sensor game certificate", or "empirical mobile-manipulator ranking in the sealed kitchen setup".
No cell is described more broadly than the fixture that qualified it. "Mission synthesis" is not a release cell.

## Scope

In: the slice register as data, with carriers; the rule that ties each stop decision to an exit review; Augur's
release cells and the breadth rule; their tests. Out: doing the slices' work (N25d-27 to N25d-30 and the beads
of other units named as carriers); the release manifest's schema and generic checks (N41-29).

**Rule for the decisions.** At the exit review of a slice's milestone the reviewer reads the slice's record and
its carriers' gate rows and writes an ADR in `docs/adr/` (DESIGN name `ADR-AUGUR-SLICE-<order>.md`):
`evidence-met` with the evidence's ledger identifiers, or `stopped`
with the pre-declared decision now in force. A slice with no ADR blocks the exit review. A slice that spans
milestones (slice 2, M1–M3) is decided at the review of its last milestone; at the earlier review its record
shows the carriers' progress and no ADR is due. So four exit reviews decide slices: M1 (slice 1), M3 (slices 2
and 3), M4 (slice 4) and M8 (slice 5). The blocking is a check, not a reminder (DESIGN): `cargo run -p
frob-conformance --example augur_slices -- --exit <milestone>` reads the register and fails (exit 1, naming the
slice) when a slice due at that milestone has no `adr`, when the `adr` path does not resolve, or when the ADR's
disposition is not `evidence-met` or `stopped`; the exit reviews (BD-147, BD-319, BD-378, BD-442) run it as one
item of their checklists. DESIGN, where it lives: `xtask` holds exactly its six checks (BD-004, INV-WS-05), and
this check is neither a verb nor one of them, so it is an example target of `frob-conformance`, beside the
crate's other register queries (`--example pilots`, `--example bets`). The
decision text is not editable after the first carrier has produced a measurement (the same rule as a kill gate:
no quiet re-scoping). Slice 1's record also carries the first reading of the tie rule (a short conventional program
reaching the same checked scope ships behind the same verbs).

**Release cells of Augur** (entries of the release manifest, each with: `cell`, `capability`, `limit`,
`qualifying_fixture`, `gate`, `evidence_kind`, `class`). Initial cells, each enabled only when its gate has a
recorded pass:

| Cell | Capability and limit, as it may be printed | Qualifying fixture | Gate |
|---|---|---|---|
| `augur.static-family` | Exact static family with independent active vertical reactions | The four-foot stance family (400 N, ratings 160 N) | GATE-AUGUR-02 |
| `augur.sensor-game` | Time-bounded sensor game certificate (three ticks, one velocity packet, two gains) | The docking family | GATE-AUGUR-03 |
| `augur.quantifier-order` | Per-build against shared command sets on a scalar pusher | The pusher battery | GATE-AUGUR-04 |
| `augur.offline-check` | Certified cells re-checked offline with no GPU | The bundles of the three fixtures above | GATE-AUGUR-05 |
| `augur.empirical-ranking` (template) | Empirical ranking of a named robot class in a named sealed setup, class `Estimated` or `Tested` | The sealed setup it names | The qualification gate that sealed it |

**The breadth rule (added to the manifest check for cells with prefix `augur.`).** A cell is refused when its
`capability` text omits its limit, when its `qualifying_fixture` is empty, or when its text matches the
blocklist of unqualified phrases ("mission synthesis", "inverse design", "certified design" with no fixture
named). A cell whose gate row is not `pass` prints as `not released`.

## Acceptance criteria

- [ ] The register file exists with five records whose `evidence` and `if_fails` texts equal the table; a test
      fails if a record is removed or a decision text is changed after a carrier has a recorded measurement.
- [ ] `cargo run -p frob-conformance --example augur_slices -- --exit <milestone>` fails on a register copy whose slice due at that milestone has
      no ADR, an unresolvable ADR path or a disposition other than `evidence-met` or `stopped`, and passes when
      each due slice has one; at M1 it requires slice 1 only (slice 2 is due at M3).
- [ ] The release manifest contains the Augur cells; every enabled cell cites a gate row with status `pass` and
      a qualifying fixture.
- [ ] Negative controls: a cell named "mission synthesis" with no fixture is rejected; a cell whose gate is
      `not-run` prints `not released`; a cell that widens "four-foot stance family" to "legged robots" is
      rejected by the fixture-text check.
- [ ] `xtask check-contracts` on the real manifest reports every Augur cell with its limit, its qualifying
      fixture, its gate's status and its printed state (`not released` while the gate is not `pass`). (`frob
      capabilities --json` prints capability records, gates and devices, N00-02 and N32b-19, not release cells.)

## Test plan

### Unit tests
`crates/frob-conformance/tests/augur_delivery.rs`: `slices_register_complete` (five records, orders 1 to 5,
milestones M1, M1–M3, M3, M4, M8); `decision_text_frozen_after_measurement`; `cell_requires_fixture_and_limit`;
`cell_blocklist`; `cell_status_follows_gate` (toggle a gate row between `not-run` and `pass` in a test copy);
`slice_adr_due` (on register copies: slice 1 without `adr` fails `--exit M1`; slice 2 without `adr` passes
`--exit M1` and fails `--exit M3`; an `adr` path to a missing file fails; an ADR that records only an
experiment disposition (`tied`) and no slice decision fails, since only `evidence-met` and `stopped` close a
slice).

### End-to-end script and logging
`scripts/e2e/augur_release_cells.sh`: runs the manifest check of `xtask check-contracts` on the real manifest
and on a copy of it with each planted bad cell, and `cargo run -p frob-conformance --example augur_slices --
--exit M1` on the register and on a copy with slice 1's ADR removed. It sources the STD-E2E helper and writes
`target/e2e-logs/augur_release_cells/<utc>.ndjson` with a transcript beside it; every line has `ts`, `script`,
`bead`, `step`, `event`, the exact command line, exit code and wall time; per cell it logs text, fixture, gate
status, evidence kind and the check's verdict; per planted cell or register copy the refusal or failure line
with the first offending field; a final `summary` with assertions passed and failed. It runs at every
release.

### Known answers and negative controls
The three planted cells above. The register's negative control is the frozen-text test.

## Considerations

- Slices 3 and 5 are carried entirely by other beads; this bead only makes their stop decisions explicit and
  checkable.
- Tied, infeasible, incomparable and inconclusive are complete dispositions of a slice's experiments; the
  register records them under those names.
- If a slice is stopped, later slices are not automatically cancelled: slice 4's timing question stands even
  if slice 3 finds no reversal.
