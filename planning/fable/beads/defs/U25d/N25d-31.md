## Background

A refusal in this program is a typed answer, not an error string: a stable code, a message, the field at fault
and ranked repairs, so that an agent can fix its request without guessing. Mission and certificate refusals of
Augur (the subsystem for queries over families of designs) are in the `8xx` family (evidence and protocol).
The chapter says it uses the block 840 to 859; six of its twenty codes carry numbers from 868 to 887 because
codes are never reused and those slots were what remained. The table below governs.

Beside the codes stand four rules that are not codes but shape every answer: a failed training run is never an
exclusion; a solver failure is never an exclusion; an unresolved cell is never reported as either verdict; and
a query whose estimate exceeds its budget is refused under the budget family with the estimate attached. They
exist because the easiest way for a design tool to mislead is to let "we could not find a controller" read as
"no controller exists". Under an existential quantifier over policies, a finite failed search discharges
nothing.

Reason for one bead: the raise sites are spread over admission, the semantic core, the certificate path and
the lanes, written by different hands; without one place that fixes the payload of each code and the tests of
the standing rules, repairs drift and a solver error eventually leaks out as an exclusion.

## Scope

In: one constructor per code that cannot be called without its pointer and first repair; the repair payload
types; the mapping to exit codes and the `retry` field; type-level and run-time enforcement of the four
standing rules; documentation in `CONTRACT.md`. Out: the mechanisms that detect each condition (admission,
proof rules, transports, region certificates, synthesis caps, composition, experiments: their own beads); the
registry rows (see `needs`); the end-to-end battery (N25d-32).

## Technical approach

Module `crates/frob-mission/src/refusal.rs` (DESIGN). The envelope's `refusal` object has `code`, `message`,
`pointer` (the field or part at fault), `observed`, `required`, `unit`, `affected_claims`, `retry` (`never`,
`after-change`, `backoff`) and ranked `repairs`. Every code here exits 3 (refused input or question) with
`retry: after-change`.

**Constructors.** `Refusal::r868(pointer, diff: SchemaDiff)`, and so on: each takes the data of its first
repair as a typed argument, so a raise site cannot produce the code without the repair. Further repairs may be
appended in rank order. Repair types carry a ready `command` where one exists (for example
`frob mission revalidate a:… --after-edit e:…` for 854). `observed` and `required` are filled where the
condition is a comparison (855: profiles found against the one declared).

**The four standing rules, enforced.**
1. *A failed training run is never an exclusion.* A learning or search lane returns
   `Explanation::CompetingMechanisms` or `BudgetExhausted` for a cell; it has no access to the constructor of
   `Verdict::Excluded`, which requires at least one proof reference whose kind can establish an exclusion.
2. *A solver failure is never an exclusion.* Non-convergence, step-size collapse, an exhausted retry budget, a
   NaN or an event the integrator cannot locate map to `Explanation::SolverFailure` and `Verdict::Unresolved`.
   The mapping is one function (`from_numerical_outcome`) with no branch that yields `Excluded`.
3. *An unresolved cell is never reported as either verdict.* The answer has three separate lists. Printers and
   reports take a `Verdict` and have no code path that renders `Unresolved` with a pass or fail word; an
   existence query returns `unknown` with the reason. A budget stop that leaves the unresolved set larger than
   `resolution` allows returns exit 2 with the flag `resolution-unmet` (the default under the open question on
   that exit code).
4. *Over budget is refused under the budget family.* When the estimate's upper end exceeds the remaining
   budget, the verb returns `FROB-REF-701` (exit 4) with the estimate attached, split into admission,
   lowering, proposing and checking, before any work runs.

**Auditor codes.** When the independent checker rejects a bundle it names its own rule and code (unknown proof
kind 823; prefix, domain or assumption mismatch 826; missing side condition or wrong frame, sign or unit 829;
class above the weakest input 834). DESIGN default until the registry owners rule otherwise: the verb surface
reports the Augur code of the table above as `refusal.code` when the condition was detected by `frob-mission`
before the checker ran, and the auditor's code with its rule identifier when the checker detected it; the
envelope carries the other in `refusal.related` so neither is lost.

## Acceptance criteria

- [ ] Twenty constructors exist; none compiles without its pointer and first-repair argument.
- [ ] Every code maps to exit 3 and `retry: after-change`; the budget refusal maps to exit 4 with an estimate.
- [ ] No function in `frob-mission`, `frob-synth` or the learning lanes can construct an exclusion from a
      numerical failure or a failed search (compile-fail tests and a search of the public API).
- [ ] No printer renders an unresolved cell with a verdict word (golden-output test over every report shape).
- [ ] `CONTRACT.md` of `frob-mission` lists the twenty codes with their repairs and the four rules.
- [ ] The registry check passes: every code used is present in `registries/refusals.toml`; an unknown code is
      a load-time error.

## Test plan

### Unit tests
`crates/frob-mission/tests/refusals.rs`:
- one test per code that builds the refusal from the smallest triggering input and asserts code, pointer and
  the first repair's kind (for example `r884_missing_persistence`: a hidden gain with no persistence
  declaration; repair lists `fixed-per-execution` and `resampled` and names the out-and-back fixture, whose net
  displacement is 0 with a fixed gain g ∈ {1, 2} and {−1, 0, 1} when resampled);
- `r846_marginals_multiplied`: two stages at 19/20 offered as 0.9025 without a dependence assumption (the
  truth is 18/20 if the failed worlds differ and 19/20 if they coincide);
- `r853_unattained_infimum`: the docking repair at read error 5/16 needs U > 3/4; reporting 3/4 as attained
  is refused; the repair is `feasible-candidate` with its gap;
- `r881_clairvoyant`: per-world optimal commands offered for a robust claim on the pusher
  (y = max(0, g·u − d): per-build command set [1/2, 2], shared set empty);
- `solver_failure_is_unresolved`; `training_failure_is_unresolved`; `unresolved_has_no_verdict_word`;
  `over_budget_refused_701`.
- Property test: for random numerical outcomes `from_numerical_outcome` never returns an exclusion.

### End-to-end script and logging
`scripts/e2e/augur_refusals.sh` (bead N25d-32).

### Known answers and negative controls
KA-628, KA-630, KA-631 as the fixtures behind 881, 884 and 846; CX-272, CX-275, CX-276. Controls: a build in
which a timeout yields `Excluded` (caught by rule 2's test); a printer that prints "fail" for an unresolved
cell (caught by the golden test); a constructor without a repair (does not compile).

## Considerations

- Two code families describe overlapping conditions (the chapter's and the auditor's); the default above keeps
  both visible. The owners of the two registries should confirm or replace it before M1 exit.
- The open question on the exit code of a budget stop with certified cells has the default "exit 2 with
  `resolution-unmet`"; this bead implements the default behind one constant.
- Six of these codes can first be raised only when their mechanisms exist (transports, revalidation, region
  certificates, synthesis, composition, experiments); their constructors exist from M1.
