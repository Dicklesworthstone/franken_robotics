## Background

Augur's refusals are part of its contract with an agent: twenty codes of the evidence-and-protocol family,
each returned with the offending field and ranked repairs (N25d-31 fixes their payloads), plus four standing
rules (a failed training run is never an exclusion; a solver failure is never an exclusion; an unresolved cell
is never reported as either verdict; an over-budget query is refused under the budget family with the estimate
attached). A refusal that is specified and never triggered from the outside is untested. This battery triggers
every code from the user's side, through `frob --json`, with the smallest input that should cause it, and
checks what comes back.

Sixteen codes have at least one trigger that is reachable with the M1 mission slice. Four need mechanisms that
arrive later, and so does the second trigger of one more (856); their fixtures are written now and reported
`pending` until the verb that can raise them exists. A pending row can never read as a pass, and the battery is
re-run at the M3 and M4 exit reviews, where pending rows must have become asserted.

One trigger is asserted by one script (DESIGN: this battery and the admission script of N25a-23 had each
fired the admission refusals from the command line). The triggers that are single-field mutations of a
mission query belong to `scripts/e2e/mission_admission.sh` (N25a-23), a dependency of this bead; three
document-level triggers belong to `scripts/e2e/mission_check_echo.sh` (N24b-26), which owns the
`mission.check` echo; and the reuse trigger of 854 belongs to `scripts/e2e/mission_docking_family.sh`
(N25c-22), whose fixtures it needs. This battery keeps the table of all twenty codes, runs every trigger that
belongs to no other script, and for the others reads the owning script's log and cites the case or step.

## Scope

In: the completeness table of the twenty codes; one fixture per trigger this battery runs; the script; the
staged `pending` rule; the standing-rule checks from the outside. Out: the payload types and the rule
enforcement in code (N25d-31); the checker's mutation corpus of at least 60 mutated queries and certificates
and its gate (BD-136); the registry rows (N25-REF); the query-mutation triggers of codes 868, 874, 877, 881,
884, 887, 846, 847, 853, 855 and 856, with their generated fixtures, the identity checks of `MissionId` and
the shortcut catalogue (N25a-23, cases a2 to a20: asserted there, read here); the unlabelled `clairvoyant`
policy class (887) and the two 868 documents outside N25a-23's table (N24b-26, steps 5 and 7); the reuse of
the two-gain docking bundle on the three-gain mission (854; N25c-22, step 9).

## Technical approach

**Fixtures** in `crates/frob-conformance/fixtures/augur/refusals/<code>/`, each with `input` (a `.fmission`, a
bundle or a command line), `expect.json` (code, exit, pointer, the kind of the first repair, `retry`) and a
one-line reason.

The column "Asserted by" names the script that fires the trigger. "N25a-23, aN" means the case of that number
in `scripts/e2e/mission_admission.sh`; "N24b-26, step N" the step of that number in
`scripts/e2e/mission_check_echo.sh`; "N25c-22, step 9" that step of `scripts/e2e/mission_docking_family.sh`.
This battery does not run such a trigger again; it reads the case's or step's `refusal` line from that
script's last log, checks the code, and fails if the line is absent or the case failed.

**Script.** For a row asserted by another script (N25a-23, N24b-26 or N25c-22): read the named case or step
from that script's last log (the battery runs that script first when no log of the current commit exists),
check `refusal.code` and `refusal.pointer` against the row, and log the row as `asserted-by: <bead>/<case or
step>`. For each
fixture of this battery: run its command (`frob mission check`, `frob mission synthesize`, `frob mission
refute`, as the fixture says) with `--json`, every run verb with its own key `--key augur-ref-<code>-<n>-<run>`
(n the trigger's number in its row), so that no trigger returns another's stored receipt; assert `ok: false`,
the exit code (3), `refusal.code`, `refusal.pointer`, the kind of `refusal.repairs[0]`, `retry: after-change`,
and that exactly one envelope was written. The certificate and bundle triggers (848, 849, 850, 851, the further
triggers of 853 and the second trigger of 881) are mission codes: the auditor's verbs `frob prove verify` and
`frob-verify` always report the Lemma column (823, 826, 829 or the rule only), and the mission code is returned
only when the evidence is supplied by the caller to a mission verb (BD-133, step 7). So each such fixture is
offered to the mission verb as caller-supplied evidence (`frob mission synthesize q:… --reuse <bundle>` or
`frob mission refute q:… --from a:…`, with its key), which must refuse with the row's code and exit 3; the same
bundle is then run through `frob prove verify <bundle> --json`, and its code is logged beside the mission code
and asserted equal to BD-133's Lemma column for that rule area. For a `pending` fixture: probe whether its verb or option exists
(`frob capabilities --json`); if not, log `pending`; if it exists and the refusal does not appear, fail.

**Standing rules, checked from outside.**
- Solver failure: a mission whose lowered program is deliberately ill-conditioned so that the proposer does not
  converge within its iteration cap returns the cell in `unresolved` with explanation `SolverFailure`; the cell
  is not in `excluded`.
- Failed search: a fixture where a policy search is given a zero budget returns `unresolved`, not `excluded`.
- No verdict for unresolved: `frob mission show <answer> --set unresolved` and the mission report print no
  pass or fail word for those cells; an existence query on it returns `unknown`.
- Budget: `frob mission synthesize q:… --budget wall_s=0 --key augur-ref-701-1-<run>` is refused with
  `FROB-REF-701`, exit 4, the estimate attached and split by stage; nothing is published.

## Acceptance criteria

- [ ] Sixteen codes have at least one trigger asserted at M1 with its pointer and first repair (856 among
      them, by its admission trigger, and 854 by the docking reuse step); four codes (852, 859, 857, 858) and
      the second trigger of 856 are `pending` with their fixtures present and their probes working.
- [ ] Every (code, trigger) row of the table is asserted by exactly one script: the rows marked N25a-23,
      N24b-26 or N25c-22 are read from those scripts' logs and not run here, and no fixture directory of this
      battery repeats one of them; a planted removal of case a20 from N25a-23's script makes the 877 row fail
      here, and a log of N25c-22's script without step 9's `refusal` line makes the 854 row fail.
- [ ] A `pending` row is counted neither as passed nor as failed; the summary prints asserted, pending and
      failed separately.
- [ ] The four standing-rule checks pass.
- [ ] Every refusal maps to exactly one exit code; exactly one envelope per invocation.
- [ ] At the M3 exit review 852 and 859 are asserted; at the M4 exit review 857 and the
      region-certificate trigger of 856; 858 when stage composition lands. The script's last log is cited by each review.
- [ ] Negative controls: a build that returns 868 without a pointer fails the script; a build that turns the
      ill-conditioned cell into an exclusion fails it; a fixture whose expected code is deliberately wrong
      (849 expected where 850 is returned) makes the harness report the mismatch.

## Test plan

### Unit tests
`crates/frob-conformance/tests/augur_refusal_fixtures.rs`: every code of the table has at least one row, and
every row a fixture here or a case or step of the script it cites (N25a-23's case list, N24b-26's steps 5
and 7, N25c-22's step 9) that exists there; each `expect.json`
validates; the pusher fixture's arithmetic (g·u = 1 gives y ∈ [3/4, 1]; a shared u would need u ≥ 2 and
u ≤ 5/8); the stance conflict (200 < 400), as the expected value of case a20; the wholly pending codes are
the four above and 856 has one asserted and one pending row.

### End-to-end script and logging
`scripts/e2e/augur_refusals.sh [--milestone M1|M3|M4]`. It sources the STD-E2E helper and logs to
`target/e2e-logs/augur_refusals/<utc>.ndjson` with a transcript beside it; every line carries `ts`, `script`,
`bead`, `step`, `event` and the envelope's evidence block; per fixture the exact command line (key included),
exit code, wall time, a `refusal` line with code, pointer, first repair kind, `retry` and the message (for the
certificate triggers, the mission code and the `prove verify` code side by side); `assert` lines with expected and observed; `pending` rows as events of their
own; for the standing rules the cell's list membership and explanation; on failure the envelope path; a
`summary` with counts asserted, pending and failed. No private scene data appears: fixtures are synthetic.

### Known answers and negative controls
KA-628 (pusher: per-build set [1/2, 2], shared set empty), KA-630 (persistent gain), KA-631 (twenty worlds),
KA-637 (docking equality case); CX-272, CX-276. The three controls above. Determinism: refusal payload bytes
identical twice on one machine, debug and release.

## Considerations

- The same conditions are also exercised inside the checker's mutation corpus; this battery differs in going
  through the verbs and in asserting repairs, which the corpus does not.
- Code 856 has two triggers: the admission rule of N25a-02 raises it at M1 for a query that asks for a joint
  paving, which is why the code has an asserted row at M1 here; the region-certificate trigger arrives at M4. The
  refusal registry (N25-REF) dates the row M1, M3 and M4 and names both raising sites, and its own test
  `two_triggers_of_856` holds it there.
- MCP parity is asserted by the failure-class battery of the surface; this script may be run with
  `--surface mcp` once that exists.
