## Background

Augur's refusals are part of its contract with an agent: twenty codes of the evidence-and-protocol family,
each returned with the offending field and ranked repairs (N25d-31 fixes their payloads), plus four standing
rules (a failed training run is never an exclusion; a solver failure is never an exclusion; an unresolved cell
is never reported as either verdict; an over-budget query is refused under the budget family with the estimate
attached). A refusal that is specified and never triggered from the outside is untested. This battery triggers
every code from the user's side, through `frob --json`, with the smallest input that should cause it, and
checks what comes back.

Fourteen codes are reachable with the M1 mission slice. Six need mechanisms that arrive later; their fixtures
are written now and reported `pending` until the verb that can raise them exists. A pending row can never read
as a pass, and the battery is re-run at the M3 and M4 exit reviews, where pending rows must have become
asserted.

## Scope

In: one fixture per code (two where the code has two triggers); the script; the staged `pending` rule; the
standing-rule checks from the outside. Out: the payload types and the rule enforcement in code (N25d-31); the
checker's mutation corpus of at least 60 mutated queries and certificates and its gate (the mutation-corpus
bead); the registry rows.

## Technical approach

bundle or a command line), `expect.json` (code, exit, pointer, the kind of the first repair, `retry`) and a
one-line reason.

**Script.** For each fixture: run its command (`frob mission check`, `frob mission synthesize`,
`frob mission refute`, `frob prove verify`, as the fixture says) with `--json`; assert `ok: false`, the exit
code (3), `refusal.code`, `refusal.pointer`, the kind of `refusal.repairs[0]`, `retry: after-change`, and
that exactly one envelope was written. For a `pending` fixture: probe whether its verb or option exists
(`frob capabilities --json`); if not, log `pending`; if it exists and the refusal does not appear, fail.

**Standing rules, checked from outside.**
- Solver failure: a mission whose lowered program is deliberately ill-conditioned so that the proposer does not
  converge within its iteration cap returns the cell in `unresolved` with explanation `SolverFailure`; the cell
  is not in `excluded`.
- Failed search: a fixture where a policy search is given a zero budget returns `unresolved`, not `excluded`.
- No verdict for unresolved: `frob mission show <answer> --set unresolved` and the mission report print no
  pass or fail word for those cells; an existence query on it returns `unknown`.
- Budget: `frob mission synthesize --budget wall_s=0` is refused with `FROB-REF-701`, exit 4, the estimate
  attached and split by stage; nothing is published.

## Acceptance criteria

- [ ] Fourteen codes are asserted at M1 with their pointer and first repair; six are `pending` with their
      fixtures present and their probes working.
- [ ] A `pending` row is counted neither as passed nor as failed; the summary prints asserted, pending and
      failed separately.
- [ ] The four standing-rule checks pass.
- [ ] Every refusal maps to exactly one exit code; exactly one envelope per invocation.
- [ ] At the M3 exit review 852, 854 and 859 are asserted; at the M4 exit review 856 and 857; 858 when stage
      composition lands. The script's last log is cited by each review.
- [ ] Negative controls: a build that returns 868 without a pointer fails the script; a build that turns the
      ill-conditioned cell into an exclusion fails it; a fixture whose expected code is deliberately wrong
      (849 expected where 850 is returned) makes the harness report the mismatch.

## Test plan

### Unit tests
`crates/frob-conformance/tests/augur_refusal_fixtures.rs`: every code of the table has at least one fixture;
each `expect.json` validates; the pusher fixture's arithmetic (g·u = 1 gives y ∈ [3/4, 1]; a shared u would
need u ≥ 2 and u ≤ 5/8); the stance conflict (200 < 400); the pending list equals the six codes above.

### End-to-end script and logging
`scripts/e2e/augur_refusals.sh [--milestone M1|M3|M4]`. Log at `target/e2e-logs/augur_refusals/<utc>.ndjson`:
per fixture the exact command line, exit code, wall time, a `refusal` line with code, pointer, first repair
kind, `retry` and the message; `assert` lines with expected and observed; `pending` rows as events of their
own; for the standing rules the cell's list membership and explanation; on failure the envelope path; a
`summary` with counts asserted, pending and failed. No private scene data appears: fixtures are synthetic.

### Known answers and negative controls
KA-628 (pusher: per-build set [1/2, 2], shared set empty), KA-630 (persistent gain), KA-631 (twenty worlds),
KA-637 (docking equality case); CX-272, CX-276. The three controls above. Determinism: refusal payload bytes
identical twice on one machine, debug and release.

## Considerations

- The same conditions are also exercised inside the checker's mutation corpus; this battery differs in going
  through the verbs and in asserting repairs, which the corpus does not.
- MCP parity is asserted by the failure-class battery of the surface; this script may be run with
  `--surface mcp` once that exists.
