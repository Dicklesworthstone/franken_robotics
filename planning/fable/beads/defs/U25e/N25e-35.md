## Background

The label query of Augur asks how much a factory must tell a shared controller: the minimum number of distinct
calibration labels that lets one controller serve all admitted variants and payloads by a common commitment
deadline. Variants can share a label exactly when their command sets have a common point; the least number of
labels is the chromatic number of the conflict hypergraph. A label that arrives after a decision is committed has
zero value for it.

That query counts labels. But a label is a message. The factory must also deliver the label by the commitment
deadline over a real channel, and a count that ignores the channel can promise an operation the wire cannot
support. This bead adds the second declaration a guarantee about information must carry: a label count states the
channel that carries the label and the length of the message. Tier Solid [S]; owner `frob-mission`; verb
`mission.synthesize`.

Known answers for the three labels of the one-label-map fixture (variants A, B, C and three public readings that
require opposite command bits for A and B at the first, B and C at the second, C and A at the third: two labels
suffice at each reading and a fixed map needs three):

| Channel | Least length | Code | Why no shorter |
|---|---|---|---|
| `clean` | 2 bits | 00, 01, 10 | One bit has two words |
| `erasures(1)` | 3 bits | 000, 011, 101 (pairwise distance 2) | Any three words of length 2 include a pair at distance 1 |
| `flips(1)` | 5 bits | 00000, 00111, 11001 (distances 3, 3, 4) | Distance at least 3 for each pair needs the three distances to sum to 9; each bit position adds at most 2 to that sum, since three binary symbols cannot differ pairwise; four bits give at most 8 |

A transmission deadline of four bit times therefore admits guaranteed operation under one erasure and excludes it
under one flip. Rejected alternatives: assuming a clean channel silently (the count would then be a promise the
wire may not keep); importing a coding-theory library (the caps are small; exhaustive search and a counting
argument are enough and are checkable).

## Scope

In: the channel field, the search for the least length, the code witness, the lower bound, the deadline check, the
proof objects. Out: the colouring that produces the label count (BD-363); the joint error law of reads (N25e-34);
the gate script (N25e-37).

## Technical approach

1. Query fields (DESIGN). The label query gains `channel`, one of `clean`, `erasures(e)` (up to e known positions
   lost) and `flips(t)` (up to t unknown bit errors), for a one-shot binary message of fixed length with no
   feedback, and a `bit_time` with its unit. No default: a label query with a commitment deadline and no
   channel is refused as an invalid query (`FROB-REF-868`, pointer at the missing field).
2. Requirement. For L labels the least length n is the least n that admits a binary code of L words with minimum
   Hamming distance d = 1 (`clean`), e + 1 (`erasures(e)`) or 2t + 1 (`flips(t)`).
3. Search (module `crates/frob-mission/src/labels/channel.rs`). For L ≤ 16 and n ≤ 12 (DESIGN caps) the least
   length is found by exhaustive search: for n = ⌈log₂ L⌉ upward, a backtracking search for L words with pairwise
   distance at least d, with the first word fixed to zero and words taken in increasing order (symmetry
   breaking). The first n that succeeds is the answer; the code found is the upper-bound witness.
4. Lower bound. For each shorter length the bound is the exhausted search (a certificate that records the search
   tree's size and a digest, re-run by the checker within its caps) or a counting argument where one exists.
   Counting arguments implemented: the pigeonhole bound L ≤ 2ⁿ; the sphere-packing bound L·Σ_{i ≤ t} C(n, i) ≤ 2ⁿ
   for flips; and the distance-sum bound: over all pairs, Σ d(u, v) ≤ n·⌊L/2⌋·⌈L/2⌉ (each position contributes at
   most the number of unequal pairs of an L-symbol binary column), so a code needs C(L, 2)·d ≤ n·⌊L/2⌋·⌈L/2⌉. For
   L = 3, d = 3: 9 ≤ 2n, so n ≥ 5.
5. Answer. The label count, the length n, a code, the lower-bound argument, and the check n × bit time ≤ time to
   commitment. If the check fails the cell is excluded for that channel with the argument attached, and
   `mission.refute` names the repairs: a longer deadline, a faster or cleaner channel, fewer labels (with the
   payload width that fewer labels can serve).
6. Proof objects. Inclusion: the code as a witness; the checker enumerates the received-word sets under the
   declared channel and verifies that they are disjoint (for `erasures(e)`: for every set of at most e erased
   positions the punctured words are distinct; for `flips(t)`: the Hamming balls of radius t are disjoint;
   for `clean`: the words are distinct). Exclusion: the counting inequality in exact integers, or the exhausted
   search re-run by the checker. Beyond the caps (L > 16 or n > 12) the query returns the counting bounds as a
   lower and an upper length and `unresolved` between them.
7. Evidence: `Certified` on both sides within the caps; determinism D0.

## Acceptance criteria

- [ ] The three label rows return 2, 3 and 5 bits with codes whose received-word sets are disjoint: {00, 01, 10}; {000, 011, 101}; {00000, 00111, 11001} or codes equivalent under coordinate permutation and translation.
- [ ] The four-bit request under `flips(1)` returns an exclusion with the counting argument (9 ≤ 2·4 is false).
- [ ] A deadline of four bit times admits operation under `erasures(1)` and excludes it under `flips(1)`.
- [ ] On 20 generated instances with L ≤ 8 and e, t ≤ 2 the least length equals an independent brute force in `frob-conformance`.
- [ ] A label query with a deadline and no channel is refused; beyond the caps the answer is an interval with `unresolved`, never a guess.
- [ ] Every code and every exclusion is accepted by `frob-verify`; a code with one word altered so that two received-word sets intersect is rejected.
- [ ] Reachable through `frob --json`; `CONTRACT.md` documents the channel models and caps.

## Test plan

### Unit tests

`crates/frob-mission/tests/label_channel.rs`: `clean_three_labels_two_bits`; `erasure1_three_labels_three_bits`
(distances 2, 2, 2); `flip1_three_labels_five_bits` (distances 3, 3, 4); `flip1_four_bits_excluded_by_distance_sum`;
`erasure1_two_bits_excluded` (any three words of length 2 include a pair at distance 1);
`sphere_packing_bound` (L = 4, t = 1, n = 4: 4·5 = 20 > 16, excluded; n = 5: 4·6 = 24 ≤ 32, and a code exists:
00000, 00111, 11011, 11100 with minimum distance 3); `received_sets_disjoint_checker`; `deadline_check`
(n × bit time against time to commitment in exact rationals); `caps_return_interval` (L = 17);
`eight_labels_two_flips` (L = 8, t = 2, d = 5: least length 10, checked against brute force);
property test `least_length_matches_bruteforce` on 200 random (L ≤ 8; e, t ≤ 2).

lengths, codes, bounds and verdicts with the STD-E2E helper.

## Considerations

- One-shot, fixed-length, no-feedback is the modelled channel; acknowledgements and retransmission change the
  answer and need their own model and deadline accounting.
- The caps bound the search: 2¹² words and 16 labels; the worst case is small enough for the checker to re-run.
- The channel parameters (e, t, bit time) are measured facts about a factory link; their provenance is carried
  with the query like any card field.
- The upstream premise still applies: if the factory cannot identify the variant by the labelling deadline, no
  code length helps (the encoder premise of the label chapter).
