## Background

The label query asks how many distinct calibration labels a factory must deliver so that one controller serves
every variant by a commitment deadline. A label is a message: it must arrive over a real channel in time. With the
channel declared (`clean`, `erasures(e)` with up to e known positions lost, `flips(t)` with up to t unknown bit
errors; a one-shot binary message of fixed length with no feedback, and a bit time), the least message length for
L labels is the least n that admits a binary code of L words with minimum distance 1, e + 1 or 2t + 1.

GATE-AUGUR-33, label rows (claim: Known answer; M4; thresholds TARGET): the three label rows return 2, 3 and 5 bits
with codes whose received-word sets are disjoint; the four-bit request under `flips(1)` returns an exclusion with
the counting argument. On 20 generated instances with L ≤ 8 and e, t ≤ 2 the least length equals brute force. The
gate's other half (the joint error law of repeated reads) is recorded at M3 by N25e-36.

The three labels are those of the one-label-map fixture: variants A, B and C with three public readings that need
opposite command bits for A and B at the first, B and C at the second, C and A at the third, so that two labels
suffice at each reading and a fixed map needs three. This bead is the script. Rejected alternative: checking the
lengths only (a length without a code and a lower bound is an assertion, not a certificate).

## Scope

In: `scripts/e2e/augur_label_channel.sh`; the fixture queries; the 20 generated instances and their brute-force
truth; the gate record for the label rows. Out: the mechanism (N25e-35); the colouring (BD-363).

## Technical approach

Fixtures (`fixtures/augur/label-channel/`): `map3-clean.fmission`, `map3-erasure1.fmission`,
`map3-flip1.fmission` (the three-reading label-map query with the channel declared and a bit time of 1 ms),
`map3-flip1-deadline4.fmission` (the same with a commitment deadline of four bit times), and
`map3-erasure1-deadline4.fmission`. Generated instances: `gen/<i>.fmission` for i = 0..19, each a label query with
supplied command sets producing L ∈ [2, 8] labels and a channel with e or t in {0, 1, 2} (seed pinned); the truth
for each (least length) is computed by the independent brute force in `frob-conformance` and pinned in
`truth.json`.

Steps (plain shell, idempotent):
1. `start`: commit, host, generator seed.
2. Three rows: `frob mission synthesize …/map3-<channel>.fmission --json`. Assert `labels: 3` and `length` 2, 3
   and 5; read the returned code.
3. Code check by the script's own helper (independent of the product): pairwise Hamming distances at least 1, 2
   and 3 respectively; received-word sets disjoint (for `erasures(1)`: every puncturing of one position leaves
   the three words distinct; for `flips(1)`: the radius-1 balls, 6 words each, are disjoint: 18 distinct words).
   The expected codes are {00, 01, 10}, {000, 011, 101} and {00000, 00111, 11001}; any code that passes the
   helper is accepted.
4. Lower bounds: assert each answer carries a lower-bound argument for length n − 1 (`pigeonhole`, `exhausted
   search` or `distance-sum`), and that `frob-verify` accepts the bundle (`frob prove bundle`, then the auditor
   under `env -i`).
5. Four bits under flips: `frob mission synthesize …/map3-flip1-deadline4.fmission --json`. Assert an exclusion
   whose proof is the counting argument (three pairwise distances of at least 3 need a sum of 9; each of four
   positions adds at most 2; 8 < 9), and repairs that include a longer deadline and a cleaner channel.
   `…/map3-erasure1-deadline4.fmission`: assert inclusion with length 3 ≤ 4.
6. Generated instances: run each; assert `length` equals `truth.json`; tally 20 of 20.
7. Mutant code: a bundle in which the word 00111 of the `flips(1)` code is changed to 00011, which lies at
   distance 2 from 00000, so two radius-1 balls share the word 00001; assert `frob-verify` rejects it.
8. `summary` and the gate row for GATE-AUGUR-33 (label rows, M4).

Logging (STD-E2E): `target/e2e-logs/augur_label_channel/<utc-timestamp>.ndjson` and a transcript. Every line:
`ts`, `script`, `bead` (`N25e-37`), `step`, `event`, exact command, exit code, wall time, the envelope's `evidence`
block. `metric` lines: channel, labels, length against its expected value, the code, the minimum distance, the
lower-bound kind, the tally of generated instances against 20. On failure: the first instance whose length
differs from brute force, with both values and the instance path.

## Acceptance criteria

- [ ] GATE-AUGUR-33, label rows (TARGET, M4) recorded: 2, 3 and 5 bits with codes whose received-word sets are disjoint; the four-bit request under `flips(1)` excluded with the counting argument; 20 of 20 generated instances equal to brute force.
- [ ] A deadline of four bit times admits `erasures(1)` and excludes `flips(1)`.
- [ ] Every inclusion and exclusion bundle is accepted by `frob-verify`; the mutant code is rejected.
- [ ] The script exits 0 from a clean checkout on a host with no GPU and non-zero on any failed assertion.
- [ ] Negative control: a build that ignores the channel returns length 2 for all three rows and fails step 2.

## Test plan

### Unit tests

Script self-tests in `scripts/e2e/tests/`: `label_channel_selftest_helper.sh` (the helper accepts {000, 011, 101}
for one erasure and rejects {000, 001, 110}, whose first two words collide when the last position is erased);
`label_channel_selftest_truth.sh` (a truth value lowered by one fails with both values);
`label_channel_selftest_balls.sh` (the three radius-1 balls of the flip code contain 18 distinct words of 32).
Brute-force tests in `crates/frob-conformance/tests/code_bruteforce.rs`: `three_words_distance_3_needs_5`;
`four_words_distance_3_needs_5`; `eight_words_distance_5_needs_10`.

### End-to-end script and logging

This bead is the script; steps and logging as above.

### Known answers and negative controls

2 bits (00, 01, 10); 3 bits (000, 011, 101; pairwise distance 2); 5 bits (00000, 00111, 11001; distances 3, 3, 4);
four bits under one flip excluded. Base rows: KA-645, KA-647. Negative controls: the channel-blind build; the
mutant code; a lower bound claimed by "search exhausted" with a wrong digest (must be rejected by the checker's
re-run). No Appendix M number exists yet for these rows. Determinism lanes: twice on one machine; debug and
release; both hosts; identical codes and digests.

## Considerations

- The generated instances stay within L ≤ 8 and e, t ≤ 2, where brute force is immediate; the mechanism's caps
  (L ≤ 16, n ≤ 12) are wider and are exercised by unit tests.
- The label query has its own kill gate for extraction of command sets from contact (KILL-AUGUR-LABELS); this
  gate concerns supplied sets only.
