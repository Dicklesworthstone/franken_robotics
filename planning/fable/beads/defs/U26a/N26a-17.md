## Background

ADR-NEMESIS-04: smallest, not worst. The smallest change that flips a verdict is more informative than the world
with the lowest score, so every failure is shrunk before it is reported. Shrinking is delta debugging over the
edit list of a failing world w = base ⊕ {e₁ … e_n} whose base passes. Delta debugging is a search driven by one
question asked many times: does this subset of the edits still fail? Everything the result can claim depends on
how that question is defined. This bead defines it; the search that asks it is a separate bead (N26a-18), and
the verb and gate belong to the shrinker's seed bead (BD-274).

Three things make the question harder for physical worlds than for programs. A contact-rich episode is
sensitive: one seed's failure may be luck, so the relation is asked on paired seeds. A smaller world may fail
for a different reason, which is a different finding and must not be allowed to hijack the shrink. And a subset
of edits may not be a legal world at all.

Frontier: delta debugging is established for programs; its yield on physical worlds is unmeasured (pilot
N26a-06; gate GATE-NEMESIS-03; kill gate KILL-MCW).

## Scope

In: the relation `fails(S)` with its three outcomes; the paired seed set; the mechanism identity; separate
findings; the result cache and test count; the base-world check; batching.
Out: the search over subsets, bisection and the pair check (N26a-18); the file (N26a-19); the verb, the gate and
the kill decision (BD-274).

## Technical approach

1. **The original mechanism.** From the promoted failure: `Mechanism { atom: the violated requirement atom
   (the binding atom), class: the failure class }`. It is fixed for the whole shrink.
2. **Paired seeds.** `SeedSet`: 64 world addresses derived from the failing world's address by a keyed stream on
   the registered stream `nemesis-shrink` (the original address is seed 0). The stream registry's first rows
   hold four Nemesis streams (`nemesis-search`, `nemesis-audit`, `nemesis-cover-heldout`, `nemesis-certify`)
   and not this one: this bead appends its row to `registries/streams.toml` under N35-23's append rule (name
   `nemesis-shrink`, domain `engine`, entity the hash of the failing world's address, tick the seed index 1 to
   63, used for "the paired seed set of a shrink", owner `frob-nemesis`), so that the draw uses a generated
   constant and no literal identifier. The same 64 are used for every
   subset, so two subsets are compared on common random numbers. The set is fixed and hashed before the first
   test.
3. **The relation.** `fails(S) -> TestOutcome` for a subset S of the edit list:
   1. S is closed under edit dependencies (an edit inside an object another edit added needs that edit);
      otherwise `Inadmissible`.
   2. The world base ⊕ S is legal on the final world (the legality check); otherwise `Inadmissible`.
   3. The candidate is replayed on the 64 seeds on the originating backend. Replay is deterministic: the run of
      seed 0 of the full edit set must reproduce the recorded state digests, and any seed run twice gives equal
      digests; a mismatch aborts the shrink (the failure does not replay: refusal FROB-REF-564).
   4. Count k = the seeds on which the verdict is `violated` with the original atom and class.
      `Fails` when k ≥ 48 of 64 (TARGET).
   5. Otherwise count k′ = the seeds on which the verdict is `violated` with some one other (atom, class) pair.
      If k′ ≥ 48: `DifferentMechanism { atom, class }`. A subset that fails by a different mechanism is not a
      pass and not the same failure: it is recorded as a separate finding with its own classification, and the
      shrink continues on the original mechanism (for the search it counts as "does not fail").
   6. Otherwise `Passes` (few or no violations) or `Unstable { k }` when 16 ≤ k < 48: a world that fails on
      some seeds only. `Unstable` counts as "does not fail" and is listed in the result.
   Seeds that end `invalid` (a numerical fault) or `undetermined` are neither violations nor passes; if more
   than 8 of 64 are such, the outcome is `Unstable` with the reason.
4. **Preconditions on the input.**
   - The failure is promoted (the guard passed it); an `artifact-candidate` or a failure that does not replay is
     refused with FROB-REF-564 (ranked repairs: rerun the guard after the simulator defect is fixed; replay on
     the originating backend and profile; shrink a different failure; exit 3).
   - The base passes: `fails(∅)` must be `Passes`. If the candidate fails in the base world there is nothing to
     shrink and the base is the counterexample (returned as a zero-edit result).
   - The full set fails: `fails(E)` must be `Fails`. If the full world fails on fewer than 48 of 64 seeds the
     failure is seed-fragile; the shrink stops and returns the full world unshrunk, labelled
     `non-minimal(n)` with the reason `seed-fragile` and the count (DESIGN: the unshrunk world with its edit
     list is the named fallback artifact of the construction).
5. **Separate findings.** Each `DifferentMechanism` subset is written to the campaign's findings with its world
   identity, atom, class and count, marked `found-while-shrinking`; it enters the normal pipeline (oracle, guard)
   as a new candidate failure and may be shrunk in its own right.
6. **Cache and count.** Outcomes are memoized by the subset's bitmask; `tests` in the result is the number of
   distinct subsets evaluated. Each test costs 64 episodes; subsets waiting together are run as one mixed batch.
   The memo entry of every evaluated subset is a record, not only the outcome: k, k′ with its mechanism, the
   counts of invalid and undetermined seeds, and the mean and minimum over the 64 seeds of the original binding
   atom's margin. The margins are what the KILL-MCW fallback ranks single-edit contrasts by (N26a-18), and they
   cost no extra episode.
7. **Evidence.** The relation's outcome is a tested statement about 64 addresses on one backend and profile; the
   result records `seeds_failing: "61/64"` for the final world.

## Acceptance criteria

- [ ] `fails` returns `Fails` at 48 of 64 and `Unstable` at 47 of 64 (boundary asserted with a scripted outcome
      source in a test binary, real pipeline).
- [ ] A subset violating a different atom on 60 of 64 seeds returns `DifferentMechanism`, is written to the
      findings, and is treated as not failing by the search.
- [ ] An illegal subset and a dependency-open subset return `Inadmissible` without running an episode.
- [ ] A failing world whose base also fails returns the base as the counterexample with zero edits.
- [ ] A seed-fragile full world (30 of 64) returns unshrunk with `non-minimal(n)` and the reason.
- [ ] A failure that does not reproduce its recorded digests, or that the guard labelled an artifact candidate,
      is refused with FROB-REF-564, exit 3.
- [ ] The same 64 addresses are used for every subset of one shrink (asserted from episode records); the seed
      set's hash is in the result; the row `nemesis-shrink` is in `registries/streams.toml` and N35-23's loader
      accepts the file with it appended.
- [ ] `tests` equals the number of distinct subsets evaluated; a repeated query costs no episode.

## Test plan

### Unit tests
`crates/frob-nemesis/tests/shrink_relation.rs`:
- `threshold_48_of_64`; `different_mechanism_recorded`; `unstable_band`; `invalid_seeds_counted_apart`.
- `inadmissible_illegal`, `inadmissible_dependency`: the added-cart and cart-mass edits; the subset with only the
  mass edit is not run.
- `base_fails_returns_base`; `seed_fragile_returns_unshrunk`.
- `replay_mismatch_refused_564`: a recorded digest altered by one bit.
- `seed_set_fixed`: the 64 addresses are a function of the failing address and identical across calls.
- `cache_hits_cost_nothing`: 10 queries of one subset create 64 episodes, not 640.
- `subset_record_carries_margins`: the memo record of a subset holds k, the invalid count and the mean and minimum
  margin of the original atom, equal to the values recomputed from the 64 episode records.
- `masking_edit`: a grease patch (edit 1) fails the design; a rug over the patch (edit 2) masks it: `fails({1})`
  is `Fails`, `fails({1, 2})` is `Passes` (real fixture on the CPU reference tier).

### End-to-end script and logging
Exercised through `frob nemesis shrink` by `scripts/e2e/nemesis_shrink.sh` (N26a-34) and by
`scripts/e2e/nemesis_loop.sh` (N26a-20). Logged per test: the subset as a bitmask and as edit paths, the outcome,
k of 64, the other mechanism if any, episodes run, cache hit or miss.

### Known answers and negative controls
The masking pair is the non-monotone control of the construction: {1} fails and {1, 2} passes, so failure sets
are not monotone and the relation never assumes they are. KA-144 (a stored counterexample world reproduces its
state hash) is the replay precondition. Negative controls: a relation that accepts any violation (the
different-mechanism test must catch it); a relation run on one seed (a planted seed-fragile world then shrinks
to a world that fails on 5 of 64 seeds; the test must reject it); fresh seeds per subset (the common-seed
assertion fails). Determinism lanes: outcomes identical twice on one machine and across worker counts.

## Considerations

- The 48-of-64 threshold is a TARGET. Too high and real failures become `Unstable` and unshrinkable; too low and
  the result is a world that mostly passes. The count is always printed with the result.
- 64 episodes per test and up to a few hundred tests per shrink: a shrink costs on the order of 10⁴ episodes on
  the fast tier; the verb's estimate says so before it runs.
- The kill gate of minimal counterexample worlds (KILL-MCW: on unplanted failures fewer than half of shrunk
  worlds have at most three edits, or fewer than 90% replay) keeps this relation: the fallback ships full
  failing worlds with replay and the single-edit contrasts ranked by margin, which are `fails(E ∖ {e})` queries.
- A shrinking run whose failure mechanism changes is reported as a different failure with a new event
  classification; minimization preserves the first cause or it starts a new counterexample.
