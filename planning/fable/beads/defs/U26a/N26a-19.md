## Background

A failing seed and a video are what an engineer usually gets when a simulated robot fails. A minimal
counterexample world replaces them with an object: the smallest world found that still breaks the design, with
everything needed to replay it, the evidence that the design's own body could have coped, and the neighbouring
worlds in which the failure disappears. The file is the unit of the hard-world set (the versioned regression set
per task family and robot class), the input of the counterfactual debugger (the failing world and its
one-edit-removed neighbours are interventional contrasts), the input of the retrofit question (does a cheap
amendment to the place fix the failure with the policy frozen?) and what an agent receives from `nemesis.shrink`.

Format identifier FMT-FMCW, extension `.fmcw`, schema `frob.mcw/1`, owned by `frob-nemesis`, written by the
shrinker, read by the evaluation crate (regression batteries), the counterfactual debugger, the mission crate
and the viewer. Its kind is canonical and derived: canonical bytes with a content hash, derived from runs.

INV-NEMESIS-04: a `.fmcw` replays with identical digests on its originating backend. The file carries what
replays it: identities, edits, addresses and state digests. A file that does not replay with identical digests
on its originating backend is invalid.

Frontier with the shrinker (kill gate KILL-MCW; under its fallback the format stays and carries full failing
worlds).

## Scope

In: the type, the schema, canonical serialization, reading and validation, the replay check, the neighbours, the
evidence and no-authorization fields.
Out: producing the content (the shrinker, BD-274, with N26a-17 and N26a-18); the hard-world set (BD-275); the
verb.

## Technical approach

1. **Type (DESIGN sketch).**
   ```rust
   pub struct CounterexampleWorld {
       id: WorldId, task: TaskId, requirement: Ident,
       candidate: Candidate,              // model, controller, policy
       base: BaseWorld,                   // a scene and a world address in which the candidate passes
       edits: Vec<WorldEdit>,             // op, path, from, to, and which aspects of the scene each changes
       minimality: MinimalityRecord,      // OneMinimal { pairs_exhausted } | NonMinimal(k); one_minimal_verified;
                                          // tests run; failing seeds
       contrasts: Option<Vec<Contrast>>,  // KILL-MCW fallback only: edit, seeds_failing_without, margin_gain, ranked
       failure: Failure,                  // class, binding atom, margin, time
       replay: Replay,                    // backend, determinism class, state digests
       promotion: Promotion,              // tier, reproduced, numerical variants tried
       oracle: OracleResult,              // solvable-causal with a witness controller, or plant-feasible
       legality: Legality,                // the profile's identity; inside it; bounds touched, with provenance
       prior: Prior,                      // log₁₀ density ratio against the nominal world law
       neighbours_passing: Vec<WorldId>,  // the worlds with one edit removed
       evidence: ClaimProduct, no_authorization: NoAuthorization,
   }
   ```
2. **On the wire (a two-edit example).**
   ```json
   { "schema": "frob.mcw/1", "id": "w:3fa9…", "task": "t:kitchen-tray@88c1…", "requirement": "delivered",
     "candidate": {"model": "m:9f2c…", "controller": "c:5e02…", "policy": "p:11d0…"},
     "base": {"scene": "s:kitchen-17@a4e0…", "world": {"run_seed": 901, "world": 5120, "episode": 3}},
     "edits": [
       {"op": "set", "path": "/floor/patch[galley-2]/film", "from": "dry", "to": "grease", "changes": ["material"]},
       {"op": "set", "path": "/fixtures/door[pass]/closer_torque", "from": "14 N·m", "to": "19 N·m",
        "changes": ["fixture"]} ],
     "minimality": {"kind": "1-minimal", "pairs_exhausted": true, "one_minimal_verified": true, "tests": 37,
                    "seeds_failing": "61/64"},
     "failure": {"class": "slip", "binding_atom": "upright", "margin": -0.42, "time_s": "11.3"},
     "replay": {"backend": "gpu-cuda", "class": "D2", "state_digests": "b3:0c55…"},
     "promotion": {"tier": "referee", "reproduced": true,
                   "variants": ["half-step", "iterations-x2", "law-2", "tol-div-10"]},
     "oracle": {"class": "solvable-causal", "controller": "c:77e1…", "margin": 0.18, "trace": "b3:a9d2…"},
     "legality": {"profile": "kitchen-commercial/default@b3:…", "inside": true,
                  "touched": [{"bound": "closer_torque", "provenance": "assumed"}]},
     "prior": {"log10_density_ratio": -3.9},
     "neighbours_passing": ["w:51b0…", "w:e7c4…"],
     "evidence": {"class": "Tested", "tier": "referee", "standing": "established"},
     "authorization": {"execution_authorized": false, "hardware_safety_signoff": false,
                       "sim_to_real_certified": false} }
   ```
   Times and other exact quantities are strings; margins are numbers; identities are prefixed content hashes.
3. **Identity.** `id` is the world identity (`w:`): the hash of the canonical base, edits, disturbances and
   parameters (N26a-02). It names the world, which is what replays and what `neighbours_passing` refers to. The
   file as an artifact is addressed by the hash of its canonical bytes in the artifact graph, like every
   canonical format; two candidates that fail in one world give two files with one `id`.
4. **Writer.** Canonical JSON (sorted keys, the shared number and string rules), written through the canonical
   writer; serializing, parsing and serializing again gives identical bytes.
5. **Reader and validation (`mcw::read` returns a validated value or a structured error naming the field).**
   1. Schema and version (`frob.mcw/1`); unknown fields are an error.
   2. `id` equals the recomputed world identity of (base, edits).
   3. Every edit passes the declaration check; the final world is inside the legality profile that
      `legality.profile` names (the profile's name and content address, BD-270; a profile that does not resolve
      is the reader's error naming that field), and `legality.touched` equals the recomputed list. DESIGN:
      `legality.profile` is added to the plan's printed file, which names no profile; reason: this rule cannot
      be checked without it, and BD-270 puts the profile identity in every result.
   4. `oracle.class` is `solvable-causal` or `plant-feasible` (a counterexample is kept only with a witness;
      INV-NEMESIS-01). Under the KILL-MCW fallback the same rule holds.
   5. `minimality` is consistent: `1-minimal` requires `neighbours_passing` to have exactly one identity per
      edit, each equal to the world identity of the edit list with that edit removed; `non-minimal(k)` requires
      k to equal the number of edits. `one_minimal_verified` is required: it is true with `1-minimal`; with
      `non-minimal(k)` it tells a verified 1-minimal world of more than three edits (true: one passing neighbour
      per edit, as above) from an unfinished shrink or a fallback file (false: `neighbours_passing` may list
      fewer identities, each still a single-removal world).
   5a. `contrasts` is optional and admitted only with `non-minimal(k)` and `one_minimal_verified: false` (the
      file the KILL-MCW fallback writes, N26a-35). When present it has one entry per edit (`edit` index,
      `seeds_failing_without`, `margin_gain`) in non-increasing order of `margin_gain`.
   6. `promotion.reproduced` is true and lists the variants; `evidence.class` is `Tested`; the three
      no-authorization flags are present and all false (a file with any flag true or missing is rejected).
      A verb that loads a `.fmcw` (`sim.replay <file.fmcw>`, `nemesis.hardset add`, the regression battery
      loader) surfaces this last rejection as FROB-REF-816, the safety chapter's code for an artifact whose
      authorization flags are missing or not `false` (exit 3); the other rules reach the caller as the
      reader's structured error with the field named, under the refusal the loading verb's own bead assigns to
      an invalid file.
6. **Replay check.** `mcw::verify_replay(file, backend) -> ReplayReport`: realize the world, run the candidate
   at the recorded address on the originating backend and numerical profile, and compare the chain of state
   digests with `replay.state_digests`. Equal: valid. Different: the file is invalid; the report names the first
   differing step. On another backend the comparison is a tolerance replay at the decision level and cannot
   validate or invalidate the file; the report says so. The hard-world set's `add`, the regression battery
   loader and `sim.replay` call this function.
7. **Neighbours.** Each passing neighbour is an interventional contrast: the failing world and the edit that
   removes the failure. The file lists identities only; the neighbour worlds are reconstructible from the file
   (drop one edit), so they need not be stored.
7a. **Resolving a world identity (DESIGN; the `w:<hash>` positional of `sim.replay`).** NS-15 replays each
   identity of `neighbours_passing` positionally, so `sim.replay` must turn a world identity into a run, a world
   and an episode. `mcw::resolve(identity) -> Resolved { run, world, episode, document, source }` does it, and
   `sim.replay w:<hash>` calls it before anything else (this bead extends that verb's positional; VERBS-sim):
   1. *The discovery record first.* Every world Nemesis evaluates is in `nemesis_worlds` (N26a-01) with its
      address and the ledger sequence of its episode, which names the run, the world index and the episode. The
      shrinker tests every single-removal subset of a 1-minimal file on its paired seeds, seed 0 being the
      parent's base address, so each passing neighbour of a shrinker-written file resolves here to that recorded
      episode, and the replay compares digests with it like any other replay.
   2. *Then the stored files.* A `.fmcw` in the artifact store or in a hard-world set whose `id` is the identity
      gives its base address and edits. A file whose `neighbours_passing` lists the identity gives its base
      address and its edit list less the one edit whose removal recomputes to that identity under N26a-02's
      identity function (the match is recomputed, not assumed; a listed identity that matches no single removal
      is the reader's rule-5 error). The address is part of the base, so a neighbour runs at its parent's base
      address. A world found this way with no recorded episode (a hand-written file, or a world never run on its
      own) resolves with `source: "file"` and no episode: `sim.replay` runs it on the file's originating backend
      and profile as a first run and reports its digests and outcome with comparison `none (first run)`, exit
      0, never as `Bitwise` (the output label of VERBS-sim's `sim.replay` row).
   3. *Neither.* An identity found in neither place is the missing identity of the `sim.replay` row (the
      surface's FROB-REF-802), with the identity in the pointer.
   The resolver reads; it writes nothing, and a private-marked world resolves only for a caller allowed the
   private root (item 8).
8. **Privacy.** A world derived from a private scene inherits the private mark; the file is stored under the
   private root and is not exported without the explicit flag.

## Acceptance criteria

- [ ] The two-edit example and the three-edit example of the worked-artifact appendix (grease film; closer
      torque 14 → 19 N·m; tray fill 0.50 → 0.80, tagged `payload`; three passing neighbours; 42 tests; 55 of 64
      seeds) parse, validate and re-serialize to identical bytes. The three-edit example is the resolved
      specimen of the golden fixture ART-L6, which carries `one_minimal_verified: true` in `minimality` and the
      profile `kitchen-commercial/default` with its address in `legality.profile`: the appendix's printed text
      predates both fields, and as printed (without `one_minimal_verified`) the file is rejected by rule 5, which
      is one of the planted violations below.
- [ ] Each validation rule rejects its planted violation, naming the field: a wrong `id`; an edit without
      `changes`; a world outside the profile (the planted case is the chapter's own two-edit text with closer
      torque 14 → 21 N·m, outside the kitchen swing-door bound of 5 to 20 N·m: rule 3 names
      `/fixtures/door[pass]/closer_torque`); `oracle.class: not-excluded`; a missing neighbour; a neighbour
      identity that is not a single-removal world; `reproduced: false`; a no-authorization flag set to true.
- [ ] A file without `one_minimal_verified` is rejected; a `1-minimal` file with the field false is rejected; a
      file with `contrasts` and `one_minimal_verified: true`, or with contrasts out of rank order, is rejected;
      the fallback file of the kill-gate decision bead (seven edits, ranked contrasts, two passing neighbours)
      validates and replays.
- [ ] `verify_replay` on the originating backend returns valid for a file written by the shrinker and invalid,
      with the first differing step, for a file whose digest was altered or whose edit value was changed
      without updating the digests.
- [ ] `verify_replay` on a different backend returns a tolerance report and neither validates nor invalidates.
- [ ] `mcw::resolve` maps the two-edit example's `id` and each identity of its `neighbours_passing` to a run, a
      world and an episode when the discovery record holds them, to the file's base address with exactly one
      edit dropped (`source: "file"`, no episode) when it does not, and an unknown identity to FROB-REF-802; a
      neighbour resolved from the file and replayed is reported as a first run, never as `Bitwise`.
- [ ] The format is registered in the format registry with its schema name, owner, writers and readers.
- [ ] A fuzzed corpus of malformed files (truncated, duplicated keys, wrong types, deep nesting) is rejected
      without a panic.

- `roundtrip_bytes_identical` (both examples); `canonical_key_order`.
- `id_recomputed`; `neighbours_are_single_removals`: for edits (e₁, e₂, e₃) the three neighbours are the
  identities of (e₂, e₃), (e₁, e₃), (e₁, e₂).
- `validation_rejects_each` (eight planted violations, one test each).
- `minimality_flag_required`, `one_minimal_needs_verified_true`, `contrasts_only_when_unverified`,
  `contrasts_rank_order`, `fallback_file_validates`.
- `authorization_flags_must_be_false`; `true_flag_surfaces_as_816`: `mcw::read` on a copy with
  `sim_to_real_certified: true` returns the flag error, and the verb-level mapping gives FROB-REF-816, exit 3.
- `replay_identical_digests` (a real world on the CPU reference tier; `inv_nemesis_04`).
- `replay_detects_altered_edit`: closer torque changed from 19 to 18 N·m in the file, with `id` and
  `neighbours_passing` recomputed so that the reader admits it (rules 2 and 5) and the digests left unchanged:
  `verify_replay` reports the digests differing at the first step the door is touched.
- `cross_backend_is_tolerance_replay`.
- `resolve_from_discovery_record`: a ledger fixture holding the two-edit example's world and both neighbours with
  their episodes: each identity resolves to that run, world and episode.
- `resolve_neighbour_from_file`: the same file with an empty discovery record: each neighbour resolves to the
  base address and the edit list with one edit dropped, recomputed identity equal, `source: "file"`, no episode.
- `resolve_unknown_is_802`: an identity in neither place returns the missing-identity error that the verb maps
  to FROB-REF-802.
- `fuzz_malformed` (a hostile-input corpus of at least 500 mutated files).

### End-to-end script and logging
`scripts/e2e/nemesis_loop.sh` (N26a-20) writes a `.fmcw` with `frob nemesis shrink`, replays it with
`frob sim replay`, and logs the file's content hash, the world identity, the digest comparison (equal, or the
first differing step), and the validation outcome. The shrinker's script (`scripts/e2e/nemesis_shrink.sh`,
N26a-34) measures the
replay row of its gate (every `.fmcw` replays with identical digests in 100 of 100).

### Known answers and negative controls
KA-144 (a stored `.fmcw` reproduces its state hash). INV-NEMESIS-04 as the replay test. Metamorphic relation of
the chapter: removing any edit of a 1-minimal world removes the failure (checked against the neighbours).
Negative controls: a reader that skips rule 4 (an impossible trap then enters as a counterexample); a replay
check that compares only the final digest (a mid-episode divergence that re-converges is missed; the test uses
the digest chain). Determinism: file bytes and identities are exact and equal across platforms.

## Considerations

- The digests bind the file to a backend, a numerical profile and kernel versions. A kernel change invalidates
  old files by design; the hard-world set then re-promotes its worlds.
- The file records a failure of one candidate. Running another design on the same world is a new episode with
  its own verdict; the file is not evidence about that design.
- The file authorizes nothing: no execution on hardware, no safety sign-off, no sim-to-real claim; the three
  flags are constant false and exist so that no reader can assume otherwise.
- Size: a few kilobytes; neighbours are identities, traces are referenced by hash.
- The two-edit example above uses closer torque 14 → 19 N·m, as the worked-artifact appendix does. The chapter's
  own text of the same file prints 21 N·m, which lies outside the legality registry's kitchen swing-door bound
  (5 to 20 N·m) and would be refused at legality (FROB-REF-360) and rejected by rule 3 here; the DESIGN
  correction is recorded in BD-270, and the 21 N·m text survives only as the planted out-of-profile case.
