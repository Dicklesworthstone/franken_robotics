## Background

The pieces of the adversarial-worlds subsystem are meant to be used as one loop:

**propose a design; search for violating worlds; classify; guard; shrink; update the hard-world set and the
region of worlds the design is known to handle; edit the design or the place; repeat.**

Two experiments are carried through every turn of the loop together: the failing world, and the edit that
removes the failure (a passing neighbour of the minimal world). The milestone that introduces the subsystem
lists its artifact from the user's side as `frob nemesis search`, `frob nemesis shrink` to a `.fmcw` file, and
`frob nemesis bound`; and the plan's worked agent session shows the loop: a search finds three failing worlds
inside the declared family; shrinking returns a world two edits from nominal (a counter lip raised from 18 to
22 mm and a wet strip 40 mm before it); an intervention on the failing run holds the strip's friction at its dry
value and removes the failure in 60 of 64 forks while a placebo flips 2 of 64; the design is edited (wheel
radius 0.055 to 0.065); revalidation says 14 of 19 prior results are inherited; and a second search finds none
in 4,096 worlds, "not a certificate".

Each mechanism has its own bead and tests. This bead is the capability an agent actually uses: the whole loop,
end to end on the real binary, with the one piece of state the loop needs and no other bead owns: the record of
what has been searched and survived for a design, the "region of worlds the design is known to handle".

## Scope

In: the handled-region record (`frob.nemesis.handled/1`) and its update rule; the script; its assertions and
logs.
Out: every mechanism the loop calls; the gates of those mechanisms; the statistical bound on failure rate
(`nemesis.bound`, BD-276), which is a different statement from "searched and found nothing".

## Technical approach

1. **The handled-region record (DESIGN).** One record per (design version, controller, task, legality profile),
   appended by `nemesis.search` on completion and by `nemesis.hardset run`:
   ```json
   { "schema": "frob.nemesis.handled/1", "design": "d:b77e…", "controller": "c:…", "task": "t:…",
     "profile": "kitchen-commercial/default", "mission_family": "q:5b1e…",
     "campaigns": [ { "campaign": "nem-2", "methods": ["cross-entropy", "grammar", "card-uniform"],
                      "tier": "gpu-cuda", "worlds_searched": 4096, "steps": 9830400,
                      "failures_promoted": 0, "not_counted": {"not_excluded": 1, "artifact_candidate": 0} } ],
     "hard_worlds_passed": ["w:3fa9…"], "hard_worlds_failed": [],
     "open_counterexamples": [], "certificate": false,
     "statement": "searched; no promoted failure found; this is not a bound and not a certificate" }
   ```
   Rules: the record is keyed by design version, so a design edit starts a new record that lists the previous
   one as `parent`; `hard_worlds_passed` holds regression results (a design that once failed a hard world and
   now passes it), labelled as regression results and never as evidence of robustness; `open_counterexamples`
   holds promoted failures not yet resolved for this version; `certificate` is the constant false. The record
   is discovery data. It is read by `nemesis.hardset show`, by the dashboard's failures panel and by reports,
   which must quote `statement` verbatim when they cite it.
2. **The script (steps; all commands with `--json`, each with an idempotency key).**
   1. `start`: build, seeds, the planted trap chosen (a T3 solvable trap of the planted registry whose cause is
      two edits), scopes `design:write, nemesis:run, autopsy:run, sim:run`.
   2. `frob nemesis search <design> --task <task> --legality <profile> --budget … --key nem-1` → wait on the job
      (exit 8, then exit 2). Assert: at least one promoted failure; `baseline_arm` present; every failure has an
      oracle class and a guard block; `certificate: false`.
   3. `frob nemesis oracle <design> --world <worst>` → assert class `solvable-causal` or `plant-feasible` with a
      witness controller and trace.
   4. `frob nemesis shrink <worst> --key shr-1` → assert exit 2; a `.fmcw` identity; at most three edits; label
      `1-minimal`; `neighbours_passing` has one identity per edit; `seeds_failing` at least 48 of 64; the
      planted cause's edits are exactly the result's edits.
   5. `frob sim replay <fmcw>` → assert identical state digests on the originating backend.
   6. `frob nemesis hardset add <fmcw> --key hs-1` → assert a new set version; `frob nemesis hardset show` lists
      it with its failure mode and witness class.
   7. Hand-off: `frob autopsy intervene <run> --key aut-1` on the failing run → assert it accepts the
      counterexample world's edits as declared interventions (the step is asserted for shape only: an
      intervention list equal to the edit list; attribution itself is tested by its owner).
   8. Repair: `frob design edit <design> set-param … --key ed-1` (the planted fix) → new design version;
      `frob result revalidate <design> --since <old>` → logged.
   9. `frob nemesis hardset run <new design>` → assert the hard world is now `satisfied` and labelled a
      regression result.
   10. `frob nemesis search <new design> … --key nem-2` → assert exit 0, `failures_promoted: 0`, the statement
       that this is not a certificate; assert the handled-region record of the new version has `parent` set,
       the campaign appended and `hard_worlds_passed` containing the world.
   11. Misuse probes: offer the `.fmcw` to `frob eval qualify` → assert `FROB-REF-567` (a hard-world or
       search-selected world offered as a confirmation sample); offer the second search's episodes to a bound
       with `frob nemesis bound … --episodes <the runs of campaign nem-2>` → assert `FROB-REF-560` (a bound
       was offered episodes that were not drawn nominally or with recorded bounded weights).
   12. `summary`.
3. **Logging.** `target/e2e-logs/nemesis_loop/<utc>.ndjson` and a transcript through the shared helper; every
   line with `ts`, `script`, `bead` (`N26a-20`), `step`, `event`, exact command, exit code, wall time and the
   envelope's evidence block (claim, class, tier, determinism, identities, seed). Step-specific fields: worlds
   searched and steps per arm; each failure's world identity, class, atom, margin, oracle class, guard status;
   the shrink's tests, label, seeds failing; digest comparison; hard-set version before and after; the
   handled-region record before and after; refusal codes of the misuse probes. On failure: the first assertion
   that failed with the job and world identities needed to replay. Summary: assertions passed and failed; gates
   touched: none recorded here (the gates are recorded by the mechanism scripts).
4. **Fixtures.** One generated commercial-kitchen scene, one reference robot with its baseline controller, one
   planted two-edit trap with a known design repair (a parameter change that removes the mechanism), all from
   the planted registry, seeds explicit. The script is idempotent: every mutating command carries a key and a
   rerun returns stored envelopes.

## Acceptance criteria

- [ ] `scripts/e2e/nemesis_loop.sh` exits 0 on a correct build and non-zero on any failed assertion.
- [ ] The shrunk world's edits equal the planted cause; the `.fmcw` replays with identical digests.
- [ ] After the design repair the hard world passes as a regression result and the second search reports no
      promoted failure with `certificate: false`.
- [ ] The handled-region record exists for both design versions, the second naming the first as parent, and no
      surface presents it as a bound (the two misuse probes are refused with FROB-REF-567 and FROB-REF-560).
- [ ] The same loop runs through the MCP surface in the `attack` cluster (`nemesis_search`, `nemesis_shrink`,
      `nemesis_oracle`, `nemesis_hardset`) with identical envelopes (surface parity).
- [ ] The log contains every command with its envelope fields and a final summary.

## Test plan

### Unit tests
`crates/frob-nemesis/tests/handled.rs`:
- `record_keyed_by_design_version`: an edit creates a new record with `parent`.
- `campaign_appended_once`: replaying a search with the same key does not append twice.
- `certificate_is_constant_false`: no constructor or setter can produce true.
- `regression_label`: a world failed by version 1 and passed by version 2 is in `hard_worlds_passed` of
  version 2 with the regression label.
- `statement_verbatim`: the report helper refuses to cite the record without the statement.

### End-to-end script and logging
This bead is the script, as above.

### Known answers and negative controls
The planted two-edit cause is the known answer of the loop (the shrunk world must equal it). Negative controls:
a build whose shrinker returns the unshrunk world (step 4's three-edit and planted-cause assertions fail); a
build whose handled-region record sets `certificate` from "no failures found" (the constant-false test fails);
skipping the guard (an artifact plant slipped into the search's given worlds then reaches the hard-world set;
the script's step 6 asserts it does not). Determinism lanes: the loop twice on one machine gives the same world
identities, the same `.fmcw` bytes and the same set versions.

## Considerations

- "Known to handle" is the plan's phrase for a region that was searched without a promoted failure. It is the
  weakest useful statement the subsystem makes, and the record's wording is fixed so that it cannot be read as
  more. A region certificate is a different object, produced and checked by the mission subsystem.
- The loop can end in a repair to the place instead of the design: the minimal world is the input of the
  retrofit question. That branch is scripted by its owner when the retrofit verb lands (a later milestone).
- If KILL-NEMESIS or KILL-MCW fires, the script still runs: with card-uniform search, and with full failing
  worlds and single-edit contrasts ranked by margin in place of a shrunk world; the affected assertions switch
  to the fallback's.
