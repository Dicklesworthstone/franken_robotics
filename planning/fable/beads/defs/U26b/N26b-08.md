## Background

Coverage selection chooses the scenes of a battery so that together they expose as much failure-mode weight as
possible. Its input is an **incidence**: a matrix of scenes against failure modes, built from the catalogue of
modes over a reference set of designs. A failure mode is the pair (failure class, binding requirement atom):
`slip` binding the atom `upright` and `slip` binding the atom `delivered` are two modes. A scene exposes a mode
when at least one reference design fails in that mode in that scene after the artifact guard (the three-way
replay that removes failures created by the simulator). Each mode has a declared weight: frequency × severity ×
number of designs affected.

The incidence is the whole truth the selection sees, so three things about it must be explicit. *What it was
built from*: only guard-passed, physical failures of named reference designs. *What each weight is*: three
integers, declared before any selection and hashed with the matrix. *Under which identities it was built*: the
plan's fallback trigger is "any identity change (model class, tier, kernel versions, taxonomy) since the
incidence was built", and the worked card adds that such a change voids the matrix and the standard battery
returns. A stale incidence is refused (FROB-REF-565).

The decision-core pipeline is one-way: failures found feed attribution, attributed modes feed the incidence, and
nothing flows back inside a campaign. Tier Solid: counting.

## Scope

In: the type, the canonical schema, the builder from catalogues, the weight rule, the cost per scene, the
identity block, the staleness predicate, the reader for supplied (synthetic) incidences.
Out: the catalogue and its guard-passed filings (N26a-27, BD-272); selection (N26b-09); the certificate
(N26b-10); the refusal at the verb and the fallback (BD-278, N26b-11).

## Technical approach

1. **Type (DESIGN sketch).**
   ```rust
   pub struct Incidence {
       id: IncidenceId,                      // `inc:` + hash of the canonical bytes
       robot_class: RobotClass, task_family: Ident,
       built_under: BuiltUnder,              // model class, tier, kernel versions, taxonomy version (the four the
                                             // plan names); severity table, task versions, reference set, legality profile
       scenes: Vec<SceneRow>,                // sorted by key
       modes: Vec<ModeCol>,                  // sorted by (class, atom)
       exposes: Vec<BitSet>,                 // per scene, the set of mode indices it exposes
       origin: Origin,                       // Catalogues { ids } | Synthetic
   }
   pub struct SceneRow { key: SceneKey, item: BatteryItem, cost_ms: u64, designs_failing: u32 }
   pub struct ModeCol { class: FailureClass, atom: AtomId, frequency: u64, severity: u32, designs: u32,
                        weight: u64, exploration_only: bool }
   ```
2. **Rows.** A row is a candidate battery item: the task, the world (the scene identity and world addresses),
   the disturbance law and the initial-condition family. For a failure found in an edited world (a base scene
   plus typed edits) the row is the realized, edited world, so that the battery re-runs the world that exposed
   the mode. `SceneKey` is the hash of the canonical item. Scenes that the reference designs ran and in which no
   reference design failed are kept as rows with an empty exposure set: the scene count is the count of scenes
   examined, not of scenes that happened to fail.
3. **Entries.** `exposes[s]` contains mode m exactly when at least one reference design has at least one filing
   of mode m in scene s in its catalogue. The catalogue files only failures that passed the artifact guard and
   whose outcome kind is `physical`; a numerical fault and an `artifact-candidate` never reach the matrix.
4. **Weights (DESIGN; integers, declared before selection).** For mode m over the reference set R:
   - frequency F_m = the number of filings of mode m across the catalogues of R (replays of one failure count
     once, as the catalogue files them);
   - severity V_m = the declared severity of the failure class, a positive integer from the table
     `registries/nemesis/severity.toml` (versioned; default 1 for every class until the owner of the failure
     taxonomy declares otherwise);
   - designs D_m = the number of distinct designs of R with at least one filing of mode m;
   - weight W_m = F_m × V_m × D_m, computed in 128-bit arithmetic and required to fit 64 bits (otherwise the
     build fails with the offending mode).
   The plan's "frequency" is a rate; the common denominator (failures filed in all) is dropped because it
   multiplies every weight equally and changes no selection, no ratio and no certificate. A mode whose filings
   all came from exploration laws (search, tilting, forks) is marked `exploration_only`: its frequency is a
   property of the explorer's stream, not of the nominal randomization, and results print that.
5. **Cost.** `cost_ms`: the median wall time of the reference designs' episodes in the scene on the tier in
   force, in integer milliseconds (from the run records; the estimate verb's model where no run exists). Used
   only by the cost-benefit variant.
6. **Identity block and staleness.** `built_under` records what was in force when the catalogues were read.
   `incidence::stale(&Incidence, &InForce) -> Option<Stale { field, built, in_force }>` returns the first
   difference among model class, tier, kernel versions and taxonomy version (the plan's four triggers), then
   severity-table version and task version (DESIGN additions: either changes what a weight or a mode means).
   The reference set and the legality profile are part of the identity but not staleness triggers.
7. **Canonical form.** Canonical JSON, schema `frob.nemesis.incidence/1`: sorted keys, scenes sorted by key,
   modes sorted by (class, atom), exposure as sorted index lists, weights and counts as integers (as strings
   above 2⁵³). `id` is the hash of those bytes; changing one weight changes the identity.
8. **Supplied incidences.** `incidence::read(file)` accepts a document with `origin: synthetic` (fixtures and
   gate instances). Every structural rule is checked (indices in range, weights positive or zero, weight equal
   to the product of its three factors when the factors are present, sorted order). A selection made from a
   synthetic incidence is itself marked synthetic and cannot be adopted as a battery.
9. **Size.** Modes are at most a few hundred (the taxonomy has 23 classes; atoms per task are few); scenes may
   reach 10⁴. Exposure sets are bit sets over modes; the whole matrix is a few megabytes at most.

## Acceptance criteria

- [ ] Built from three synthetic catalogues (three designs, four scenes) with known filings, the matrix, the
      counts and the weights equal the hand-computed ones: a mode with 5 filings, severity 2 and 3 designs has
      weight 30.
- [ ] A scene is marked as exposing a mode when exactly one of the three designs fails so; with no design
      failing it has an empty exposure set and is still a row.
- [ ] An `artifact-candidate` failure and a numerical outcome in a catalogue's input change no entry.
- [ ] `stale` returns the differing field for each of the four plan triggers and `None` when all identities
      match; a changed reference set changes the identity but is not stale.
- [ ] Canonical bytes round-trip; reordering input catalogues does not change the identity; changing one weight
      does.
- [ ] A supplied document with an index out of range, an unsorted list or a weight unequal to its factors'
      product is rejected with the field named.
- [ ] A mode found only under exploration laws carries `exploration_only: true`.

## Test plan

### Unit tests
`crates/frob-nemesis/tests/cover_incidence.rs` (catalogues are fixtures labelled `synthetic`):
- `build_from_three_catalogues` (the full expected matrix asserted); `weight_formula_5_2_3_is_30`.
- `exposure_is_any_design`; `empty_rows_kept`.
- `only_promoted_physical_failures` (an artifact candidate and a numerical outcome are planted in the input).
- `stale_on_each_trigger` (model class, tier, kernel versions, taxonomy, then severity table and task version);
  `reference_set_change_is_identity_not_staleness`.
- `canonical_roundtrip`; `order_independent_identity`; `identity_changes_with_weight`.
- `supplied_document_validation` (three planted defects, each rejected with its field).
- `weight_overflow_refused` (factors 2³², 2¹⁶, 2²⁰).
- `exploration_only_flag`.
- `worked_instance_loads`: the fixture `cover_worked_40x18` has 18 scenes, 40 modes and total weight 100.

### End-to-end script and logging
Exercised by `scripts/e2e/nemesis_cover.sh` (N26b-12): the script logs, for the live step, the incidence
identity, the number of scenes and modes, the total weight, the catalogues read, the identity block, and for the
staleness step the field that differed with both values.

### Known answers and negative controls
The hand-computed three-catalogue matrix is the known answer. Planted defects the tests must catch: a builder
that counts unguarded failures (the artifact-candidate test); a builder that sets exposure only when every
reference design fails; a weight that omits the number of designs; a staleness check that compares only the
taxonomy version. Metamorphic relations: duplicating a reference design under a new identity raises `designs`
and `frequency` for its modes and nothing else; permuting scenes or modes in the input leaves the identity
unchanged. Determinism: integer arithmetic; identical bytes on every platform.

## Considerations

- The reference set decides what the battery can see. A battery selected from the failures of three similar
  designs covers their failures; the result names the reference set and its size.
- Severity is a judgment the plan leaves undeclared. With the default of 1 the weight reduces to frequency ×
  designs affected. Changing the table is a new table version, which makes stored incidences stale by rule 6.
- Mode granularity follows the catalogue (class and atom). A finer key is a new catalogue identity and a new
  incidence.
- The incidence is discovery data: it is built from failures that were searched for, and nothing derived from it
  may serve as a confirmation sample or as nominal draws for a bound.
- Private scenes: a row derived from a private scene keeps its mark, and an incidence containing one is stored
  under the private root.
