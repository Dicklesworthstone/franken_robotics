## Background

Every capability of the program reaches a user or an agent through a verb, and every verb is one entry of the
registry `registries/verbs.toml`, owned by the crate `frob-verbs`. The command line, the daemon protocol, the MCP
tool definitions, the schemas, the refusal table and the generated agent documentation are all generated from
it, so the surfaces cannot drift (a parity gate diffs the served tool list against the registry). A capability
that is not in the registry does not exist for an agent, and a verb whose registry row is wrong is wrong on
every surface at once.

Nemesis (adversarial worlds and rare failures) owns seven verbs:

| Verb | Kind | First milestone | What it does |
|---|---|---|---|
| `nemesis.search` | run | M3 | Adversarial worlds inside a declared legality profile: candidate, task, legality profile, method, budget. Returns classified candidate failures and the baseline arm's count at equal budget |
| `nemesis.oracle` | run | M3 | Classifies one world for one candidate and returns the witness or the failed necessary condition |
| `nemesis.shrink` | run | M3 | Shrinks a promoted failure to a minimal counterexample world and writes the `.fmcw` |
| `nemesis.bound` | run | M3 | Modes `certify`, `refute` and `estimate` for a failure probability against a target, with the fixed decision table for rare failures |
| `nemesis.audit` | run | M4 | Audits a screening stage: stratified discards and a planted winner; the one screening audit, applied by the cascade |
| `nemesis.cover` | read | M3 | Selects a covering scene set and returns it with its certificate |
| `nemesis.hardset` | read, run | M3 | `show`, `add`, `retire` and `run` on the hard-world set of a class |

Kinds have fixed meanings: `read` returns stored or cheaply computed facts and changes nothing; `run` spends
compute, takes an idempotency key and a budget, accepts the bounded synchronous wait and otherwise returns a job
handle with exit code 8.

This bead writes the seven rows and their generated artifacts so that each implementing bead has a surface to
fill, and so that the registry lint, not memory, keeps kinds, milestones, refusal lists and clusters right.

## Scope

In: the seven registry rows; input and output schema names and files; refusal lists; capability scopes; cost
models; wait defaults; task-cluster assignment; examples; the registry tests; the not-implemented behaviour
before a verb's milestone.
Out: the handlers (BD-273, BD-271, BD-274, BD-276 with BD-277, N26b-05, BD-278, BD-275); the meanings and
repairs of the refusal codes (N26-REF); the generator and the envelope (seeds of the verb crate).

## Technical approach

1. **Row form (the registry's own; one of seven shown).**
   ```toml
   [[verb]]
   name = "nemesis.cover"
   cluster = "nemesis"
   kind = "read"
   tier = "S"
   capabilities = ["nemesis:read"]
   input_schema = "frob.nemesis.cover.in/1"
   output_schema = "frob.nemesis.cover/1"
   refusals = ["FROB-REF-565"]
   idempotent = true
   cost_model = "static: under 1 s for 10^4 scenes and 300 modes; no episodes"
   first_milestone = "M3"
   task_clusters = ["audit"]
   examples = ["frob nemesis cover --class quad-mammal --task-family payload-transport --slots 20 --json"]
   ```
2. **The seven rows.**

   | Verb | Kind | Tier | Scopes | Output schema | Refusals listed | Cost model | Task cluster |
   |---|---|---|---|---|---|---|---|
   | `nemesis.search` | run | F | `nemesis:run` | `frob.nemesis.search/1` | 360, 361, 362, 569 (method `splitting`), 840 | budgeted; half to the baseline arm | `attack` |
   | `nemesis.oracle` | run | S | `nemesis:run` | `frob.nemesis.oracle/1` | 360, 361, 362, 840 | up to 16 failing-episode equivalents plus 6 guard episodes per witness | `attack` |
   | `nemesis.shrink` | run | F | `nemesis:run` | `frob.nemesis.shrink/1` | 564, 360, 840 | at most `max-tests` × 64 episodes | `attack` |
   | `nemesis.bound` | run | S (splitting F) | `nemesis:run` | `frob.nemesis.bound/1` | 560, 563, 568, 569, 760, 840 | n nominal episodes; 29,956 for 10⁻⁴ at δ = 0.05 | `attack` |
   | `nemesis.audit` | run | S | `nemesis:run`; campaign administration for `--reveal` | `frob.nemesis.audit/1` | 566 | a tenth of the audited stage's spend | `ladder` |
   | `nemesis.cover` | read | S | `nemesis:read` | `frob.nemesis.cover/1` | 565 | static | `audit` (proposed) |
   | `nemesis.hardset` | read, run | S | `nemesis:read`; `nemesis:run` for `run`; `nemesis:write` for `add`, `retire` | `frob.hardset/1` and a scorecard | 567, 560 | `run`: one episode per world of the set | `attack` |

   Every row also lists the common codes of the surface (schema failure, missing scope, budget at admission,
   budget exhausted, not implemented in this build), which the generator adds to every verb of the kind.
   FROB-REF-567 is listed on `nemesis.hardset` and is also raised by the qualification lane's own verb when a
   hard-world or search-selected world is offered as a confirmation sample.
3. **Schemas.** One input and one output schema file per verb under `schemas/`, generated from the handler's
   request and result types and referenced by name in the row; `frob schema nemesis.cover` prints them. The
   output schemas are those the implementing beads define; this bead creates the files with the fields those
   beads list and a `"$comment"` naming the owning bead, and the generator check keeps them in step.
4. **Wait defaults (run verbs).** Wait to completion on the command line; 5,000 ms by default and at most
   30,000 ms on MCP, after which the envelope carries a job handle (exit 8) with progress that always has a
   denominator: worlds for `search`, witness runs for `oracle`, tests for `shrink`, episodes for `bound`, lane
   members for `audit`, worlds for `hardset run`.
5. **Task clusters (MCP).** A task cluster holds at most seven tools. The plan's cluster table puts
   `nemesis_search`, `nemesis_shrink`, `nemesis_bound`, `nemesis_oracle` and `nemesis_hardset` in `attack`
   (with `mission_separate` and `scene_show`, seven in all) and `nemesis_audit` in `ladder` (with `opt_cascade`,
   `eval_rank_agreement`, `cores_show`, `report_campaign`, `explain_compare`, `predict_report`, seven in all).
   It assigns `nemesis_cover` nowhere, and both of those clusters are full. DESIGN proposal, to be ruled on by
   the owner of the cluster table: `nemesis_cover` joins the task cluster `audit` (`task_audit`, `eval_items`,
   `module_characterize`, `sense_visibility`, `control_lift` and the verbs later subsections add), since
   choosing a battery is an act of auditing what an evaluation covers. Until the ruling the registry lint
   reports the verb as "assigned by proposal", the tool is served in that cluster, and the parity gate treats
   the row as any other.
6. **Before its milestone.** A verb whose handler is not implemented in the sense of the program's eight
   conditions answers with the capability refusal for "not implemented in this build" (FROB-REF-724, exit 5);
   `nemesis.audit` does so in M3 builds. A registered verb never answers "unknown verb".
7. **Agent documentation.** The generated `robot-docs` entry of each verb states its one-line purpose from the
   table above, its lane (discovery data: nothing these verbs return is a confirmation sample), its refusal
   list with first repairs, and one worked example.

## Acceptance criteria

- [ ] `registries/verbs.toml` holds seven `nemesis.*` rows whose kinds and first milestones equal the table
      (`search`, `oracle`, `shrink`, `bound` run at M3; `audit` run at M4; `cover` read at M3; `hardset` read
      and run at M3).
- [ ] Every refusal code named in a row resolves in `registries/refusals.toml`; the twelve codes the chapter
      defines (360, 361, 362, 560, 563, 564, 565, 566, 567, 568, 569, 760) each appear on at least one row.
- [ ] Each verb has an input schema, an output schema and at least one example that parses against the schema.
- [ ] `frob capabilities --json` lists the seven verbs with their kinds; the served MCP tool list equals the
      registry under the name map (`nemesis.cover` ↔ `nemesis_cover`), and no task cluster exceeds seven tools.
- [ ] In an M3 build `frob nemesis audit …` exits 5 with FROB-REF-724 and never with an unknown-verb error.
- [ ] The proposal for `nemesis_cover`'s cluster is recorded in the registry with its status.

## Test plan

### Unit tests
`crates/frob-verbs/tests/registry_nemesis.rs`:
- `seven_rows_kinds_and_milestones` (the table, asserted row by row).
- `refusal_lists_resolve_and_cover_twelve_codes`.
- `schemas_exist_and_examples_parse` (one example per verb).
- `run_verbs_have_wait_defaults_and_progress_units`.
- `task_clusters_at_most_seven`; `nemesis_cover_cluster_is_proposal`.
- `not_implemented_before_milestone` (handler table empty for `audit` in the M3 feature set → FROB-REF-724).
- `scopes_declared`: a session without `nemesis:run` calling `nemesis.oracle` gets the missing-scope refusal.

### End-to-end script and logging
`scripts/e2e/nemesis_refusals.sh` (N26b-14) begins with a surface check: `frob capabilities --json` and `frob
schema <verb>` for the seven verbs, and the MCP `tools/list`, logging each verb's kind, schemas and refusal list
and the diff against the registry (which must be empty). Each implementing bead's own script exercises its verb.

### Known answers and negative controls
The verb table of the chapter is the known answer. Planted defects the tests must catch: a row whose kind is
`read` for a verb that spends compute (the kind test); a refusal code on a row that is absent from the refusal
registry; an eighth tool in a cluster; a verb present in the handler table and absent from the registry (the
parity diff). Determinism: the registry and its generated files are bytes; regeneration is idempotent.

## Considerations

- Additions that the implementing beads need beyond the plan's verb notes are declared in their rows as DESIGN:
  the method `given` and the option `--first` on `nemesis.search`; `--episodes` on `nemesis.bound`; the two
  phases `prepare` and `run` on `nemesis.audit`; `--incidence`, `--algorithm` and `--greedy-only` on
  `nemesis.cover`. Each is flagged for the owner of the verb registry.
- The scope names (`nemesis:read`, `nemesis:run`, `nemesis:write`) follow the registry's `subsystem:action`
  form; their grant rules belong to the capability work of the daemon.
- A change to a row after its first milestone is a schema change with a version bump of the affected schema,
  never an in-place edit.
