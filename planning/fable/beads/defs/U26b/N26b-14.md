## Background

Nemesis defines twelve refusal codes. Each is the enforcement point of a rule a user will try to break, usually
without meaning to: a search that wanders outside the legal world set (FROB-REF-360), a realism claim on assumed
bounds (361), an edit that does not say which causal path it changes (362), exploration data offered to a
certification bound (560), importance sampling outside its admitted law (563), shrinking an artifact (564), a
coverage selection on a stale incidence (565), a planted winner nobody ever evaluated (566), a hard world
offered as a confirmation sample (567), a failure predicate changed after sampling began (568), splitting where
no randomness enters after the fork (569), a claim the budget cannot buy (760).

The scripts of the individual capabilities exercise the refusals that belong to their own gates. This script is
the cross-cutting conformance check: every Nemesis code, from the user's side, on both surfaces (command line
and MCP), with three assertions that the per-capability scripts do not make together. The code fires on its
planted request. Its **admissible twin** (the same request with the one fault removed) is not refused: a refusal
that fires on everything protects nothing. And the envelope is usable: exactly one envelope, the right exit
code, a pointer, ranked repairs, a retry class, and nothing charged or simulated for a refusal at admission.

The program distinguishes three failure classes that a caller can meet: domain (the verb was reached and it
refused), protocol (the request never reached a verb) and transport. Every refusal here is a domain failure:
envelope with `ok: false`, exit 3 or 4 on the command line, and on MCP a tool result with `isError: true` whose
structured content is the same envelope.

## Scope

In: the script; one planted request and one twin per code; the surface check of the seven verbs; logs.
Out: the registry rows (N26-REF); the mechanisms that raise the codes; the gates (none is recorded here), whose
own scripts also raise some codes inside a gate measurement and stay the record for that gate (N26a-05: 360,
361, 362; N26a-30: 560, 563, 568, 760; N26a-31: 569; N26a-34 and N26a-16: 564; N26a-20: 560, 567), while this
script is the one place where every code is fired once beside its admissible twin on both surfaces;
FROB-REF-566, which needs the M4 audit verb and is asserted at M4 by the audit script (N26b-07, step 7), with
this script recording it `not run` while the capability report lists `nemesis.audit` as absent (asserting
instead that `frob nemesis audit <campaign> --action prepare --stage <n> --key <k>` exits 5 with FROB-REF-724,
the verb being registered and not implemented); the row's stage is written now and runs by itself once the report lists the verb, but this bead
neither waits for that nor claims it (convention 7).

## Technical approach

1. **Surface check.** `frob capabilities --json`, `frob schema <verb>` for the seven `nemesis.*` verbs, MCP
   `tools/list`: assert the seven verbs, their kinds, their refusal lists equal to the registry's, and an empty
   parity diff between the two surfaces.
2. **One row per code (planted request → expected; twin → admitted).**

   | Code | Planted request | Twin |
   |---|---|---|
   | 360 | `nemesis oracle <candidate> --task <t> --legality kitchen-commercial/default --world` a world whose door-closer torque is 21 N·m in a kitchen whose profile bounds it at 5 to 20 N·m | the same world at 19 N·m |
   | 361 | the legal world above with `--require-cited`, the closer-torque bound being `assumed` | the same without `--require-cited` (admitted; the result says the bound is assumed) |
   | 362 | `nemesis oracle` on a world carrying a wet-film edit declared as `changes: ["material"]` only, whose optical class also changes | the same edit declared `["material", "optics"]` |
   | 560 | `nemesis bound --mode certify --episodes` a run set produced by `nemesis search` (tilted and search-selected episodes) | `nemesis bound --mode certify` sampling its own nominal episodes on the synthetic rate task |
   | 563 | `nemesis bound --mode refute --proposal` a proposal whose `fitted_on` campaign is the run it is applied to | the same proposal fitted on a separate completed pilot, sampled with a fresh key |
   | 564 | `nemesis shrink` on a planted artifact failure (traction from a box-linearized friction cone) | `nemesis shrink` on a genuine planted failure |
   | 565 | `nemesis cover --incidence` built under kernel versions other than those in force | the same incidence under matching identities |
   | 566 | `nemesis audit <campaign> --action prepare --plant` a design with no final-stage rank on record (from M4) | a planted winner of the design corpus with its record |
   | 567 | `eval qualify` with a request whose `clusters` names a world from a `.fmcw` file | the same request with `clusters` a count, the lane drawing its own worlds from a sealed family (on a scratch qualification campaign); a sealed family's worlds named by the caller would be 567 again |
   | 568 | after a bound on the task (`nr-568-pre`) has drawn its nominal episodes, the task's requirement comparator is edited and a new `nemesis bound` request on the edited task, under its own key, offers those episodes through `--episodes` | the same request on the edited task without `--episodes`, sampling fresh episodes under the new predicate (the first-ranked repair) |
   | 569 | `nemesis search --method splitting` on a task whose only randomness is static parameters | the same on a task with a per-step push disturbance |
   | 760 | `nemesis bound --mode certify --target 1e-5 --delta 0.05 --budget episodes=100000` | the same with `--budget episodes=375000` (admitted: 299,572 nominal episodes are needed, and the nominal share is 375,000 under `baseline` and in `shadow`, 300,000 under `table`) |

   Keys: every run-verb call (`nemesis oracle`, `search`, `bound`, `shrink`, `hardset`, `audit`, `eval
   qualify`) carries its own `--key nr-<code>-<planted|twin>-<cli|mcp>`, so a rerun returns stored envelopes,
   the twin is never the planted request's stored refusal, and the two surfaces are compared on two calls; the
   read verb `nemesis cover` takes none. A repeat of a request under the same key after the task was edited
   would be FROB-REF-803 (the task name resolves to a new identity, N32a-09), never 568, which is why the 568
   row uses a new request.

   Required inputs: every `nemesis bound` call names the candidate, `--task` and `--tier batch-cpu` (the row
   has no default tier) and carries `--finalist`, since the script's synthetic candidates are no finalist of a
   recorded campaign and the finalists-only rule (N26a-26) would otherwise answer `rare-bound-not-finalist`
   before any of the bound's coded checks; only the `rare-bound-not-finalist` request of item 6 omits it.
   The 360 to 362 rows go through `nemesis oracle`, which refuses an illegal world or an undeclared edit for the
   whole request with nothing simulated (BD-271); the same world in a `nemesis search --method given --worlds`
   file is not a refusal of the request (the search completes and lists the document under `refused` with
   its code, BD-273), which the script asserts once for the 360 world as an extra line.
3. **Assertions per planted request.** Exit code (3; 4 for 760); exactly one JSON envelope on stdout with `ok:
   false`; `refusal.code` equal to the row's code and `refusal.message` equal to the registry's meaning;
   `refusal.pointer`, `observed`, `required` present and of the documented form (for 360: the path
   `/fixtures/door[…]/closer_torque`, `21 N·m`, the bound `[5, 20] N·m` with provenance `assumed`; for 760:
   `required` 299,572, `observed` the nominal share of the acting policy that the record names (100,000 under
   `baseline` and in `shadow`, 80,000 under `table`; N26a-26), attachment `reachable_bound` 1 − 0.05^(1/n) at
   that share (2.996 × 10⁻⁵ at 100,000, 3.745 × 10⁻⁵ at 80,000)); `refusal.repairs` has
   the registry's entries in rank order; `refusal.retry` equals the registry's class; the ledger shows no
   episode and no charge attributable to the refused request (for the admission-time codes 360, 361, 362, 565,
   566, 569, 760); the same request through MCP yields `isError: true` with an envelope body byte-identical
   apart from the request key, timestamps and job identities.
4. **Assertions per twin.** Not refused: exit 0, 2 or 8 as the verb's contract says; where the twin is long it
   is submitted with `--estimate` or cancelled after admission, since the point is admission.
5. **The repair is real.** For three codes the script applies the first-ranked repair mechanically and re-runs:
   360 (the attached nearest legal value 20 N·m is substituted: admitted), 362 (the listed tags are added:
   admitted), 760 (the budget is raised to the required count divided by the nominal share the refusal used:
   299,572 under `baseline` and in `shadow`, 374,465 under `table`: admitted).
6. **Uncoded situations.** The script also pins the present behaviour of the seven refusal-like situations the
   plan gives no code (N26-REF's table): a failed hard-set admission (`hard-world-set-inadmissible`, exit 3); a
   non-finalist bound request (`rare-bound-not-finalist`, exit 3); `nemesis bound --mode certify --proposal`
   (`certify-by-importance-sampling`, exit 3, zero episodes drawn; twin: the same request in `--mode refute`,
   admitted); a bounded-weight run planned at 10⁶ + 1 evaluations (`importance-over-sibling-cap`, exit 4, zero
   episodes, the bound reachable at 10⁶ attached; twin: 10⁶ evaluations, admitted with `--estimate`); an audit
   without a pre-score commitment (completed `not-run`, exit 2; the audit verb is an M4 capability, so like
   566 this stage is recorded `not run` while the capability report lists `nemesis.audit` as absent, and
   N26b-07's step 6 asserts it at M4); shrinking without a witness (completed
   `not-shrunk`, exit 2); a failed certificate check (fallback battery with a flag, exit 2). Each must produce
   the documented slug or result, exit code and reason; where the allocation ledger (N35x-02) has assigned a
   number to a slug, the script reads the number from the ledger and asserts it, so a later assignment of codes
   is a visible change and never a literal edited into the script.
7. **FROB-REF-569 on `nemesis.bound`.** Under a scratch configuration in which the table policy acts
   (`nemesis.bound.policy = table`, N26a-26; as N26a-30's step 9 runs it: in `shadow` or under `baseline` the
   baseline acts, asks the splitting stage nothing and has no fallback to record), `nemesis bound --mode certify`
   on the 569 row's planted task (no per-step randomness after the earliest fork tick) completes (exit 0 or 2),
   with `fallback.trigger = "b"` and `fallback.code = 569` in the result and every episode crude nominal: 569 is
   the decision policy's fallback trigger there, never the verb's exit. If KILL-RARE has fired (`nemesis.rare.exploration = off`), the 569
   row's planted request answers FROB-REF-724 (exit 5, naming KILL-RARE and its ADR); the script records the row
   `removed by KILL-RARE`, asserts 724 instead, and counts 569 as exercised through this step only.
8. **Logging.** The script sources the shared helper of the end-to-end harness and writes
   `target/e2e-logs/nemesis_refusals/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
   `bead` (`N26b-14`), `step`, `event` (`start`, `cmd`, `assert`, `refusal`, `end`), the exact command line,
   exit code, wall time, and for each refusal the whole `refusal` block (code, message, pointer, observed,
   required, repairs, retry), the surface (`cli` or `mcp`), the twin's outcome, and the ledger's episode count
   before and after. On failure: the code whose planted request was admitted, or whose twin was refused, with
   both command lines. Final `summary`: codes exercised of twelve, twins admitted, assertions passed and failed;
   `gates: []`. Fixtures are synthetic or planted; no private-scene data appears.

## Acceptance criteria

- [ ] `scripts/e2e/nemesis_refusals.sh` exits 0 on a correct build and non-zero on any failed assertion.
- [ ] Eleven codes at M3 (all but 566) fire on their planted requests with the registry's message, exit code,
      repairs and retry class, on both surfaces, with envelope bodies identical apart from key, timestamps and
      job identities; 566 is recorded `not run` while `nemesis.audit` is absent, and `nemesis audit <campaign>
      --action prepare` then exits 5 with FROB-REF-724 (566 itself is asserted at M4 by N26b-07).
- [ ] Every twin is admitted.
- [ ] No refused admission-time request leaves an episode or a charge in the ledger.
- [ ] The first-ranked repair of 360, 362 and 760, applied mechanically, turns the refusal into an admission.
- [ ] The seven uncoded situations produce their documented slugs or results, exit codes and reasons (the
      audit's `not-run` from M4, recorded `not run` before); `certify-by-importance-sampling` and
      `importance-over-sibling-cap` leave zero episodes in the ledger.
- [ ] Every `nemesis bound` call names `--task` and `--tier` and carries `--finalist` except the
      `rare-bound-not-finalist` request; the 760 row's `observed` and `reachable_bound` match the nominal share
      the record names, and its twin is admitted under that share.
- [ ] `nemesis bound` on the no-fresh-randomness task completes with fallback trigger (b) and 569 in its
      `fallback` block, never exit 3; after KILL-RARE the splitting row answers FROB-REF-724 and is so recorded.
- [ ] The log has the per-refusal fields above and a final summary line naming the codes exercised.

## Test plan

### Unit tests
`scripts/e2e/tests/nemesis_refusals_selftest.sh`: runs the script against a build with the test feature
`nemesis-refusals-off` (legality, lane and staleness checks answer "admit") and requires a non-zero exit with
the first admitted planted request named; and against a build with `nemesis-refuse-all` (every Nemesis verb
refuses with 360) and requires the twin assertions to fail. A shell-lint pass of the script.

### End-to-end script and logging
This bead is the script.

### Known answers and negative controls
KA-659 (a planted illegal edit is refused with FROB-REF-360 and the bound named; control: a profile whose bound
is widened admits it): the 360 row and its twin. The values 299,572 and 2.996 × 10⁻⁵ of the 760 row are the
zero-failure rule at δ = 0.05 and its inverse. The twins are the negative controls of the refusals; the two
self-test builds are the negative controls of the script. Determinism lanes: refusals at admission are exact;
the script run twice gives identical envelopes apart from timestamps and job identities.

## Considerations

- Admission-time refusals must be cheap and side-effect free; the ledger assertion is what proves it.
- The 567 row needs a scratch qualification campaign; where the qualification lane is absent at the time of the
  run the row is recorded `not run` with the reason and counted as not exercised in the summary.
- This script records no gate. It is cited by the exit review as the evidence that the chapter's refusal table
  is implemented as written.
