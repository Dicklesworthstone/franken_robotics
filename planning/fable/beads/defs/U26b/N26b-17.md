## Background

The chapter closes its mechanisms with a table of eleven known answers: cases whose right result is known before
any code runs, each paired with a negative control, a planted wrong implementation or wrong input that must make
the row fail. The program's rules for such rows: a known answer has a derivation on file, a tolerance with a
reason, a negative control that is a mutation (not merely a boundary behaviour), and a tier and site (it runs
first on the weakest site that can decide it). A row whose control has not been shown to fail cannot support a
gate, and every convergence gate needs a registered control it catches.

The chapter adds a rule of its own: **a value that follows from a stated formula is a derived value and a known
answer; every other number carries its label** (FACT, TARGET, HYPOTHESIS). So the battery has two parts: the
eleven table rows, and a check that every derived number printed in the chapter's mechanisms is reproduced from
its formula.

The individual mechanism tests each cover their own rows. This bead is the battery as a whole: one registry
view, one runner, one log in which all eleven rows and all eleven controls appear with expected and observed
values, so that an exit review reads one table.

## Scope

In: the battery's registry view (row → test → control → tier and site); the runner script; the derived-value
check; the summary record.
Out: the registry of known answers itself (N26-KA); the tests that compute each row (the mechanism beads); the
gates (each has its own script); the derivation files (N26b-16).

   KA-668 is due with the audit at M4; before then the runner records it `not run` with the reason, which is not
   a pass. The other ten are due at M3.
2. **Registry view.** `crates/frob-conformance/registry/batteries/nemesis_known_answers.toml`: one entry per row
   with `ka`, `test` (crate and test name, or script and step), `control` (the mutant feature or the planted
   input and the assertion it must break), `tier`, `site`, `derivation` (the file under `docs/derivations/`),
   `due`. The conformance registry check fails if a row has no control, if a control has never been observed to
   fail, or if a named test does not exist.
3. **Runner, `scripts/e2e/nemesis_known_answers.sh` (numbered).**
   1. `start`: build identity, the registry view's hash, hardware fingerprint, the sites available.
   2. For each row due at the current milestone, on each site its tier names: run the row's test (a `cargo test`
      filter for the G0 and G1 rows that live in a crate; a `frob` command for rows defined on the surface, for
      example `frob nemesis cover --incidence cover_worked_40x18.json --slots 6 --greedy-only` for KA-669 and
      `frob nemesis bound --mode certify --target 1e-4 --delta 0.05 --estimate` for KA-664). Record expected and
      observed.
   3. For each row: run its control (the same test against the mutant build, or with the planted input) and
      require the row to fail there. A control that passes is a failure of the battery.
   4. Derived values: run `derivations_numbers` (the recomputation of every number the chapter's derivation
      files print) and list each value with its formula identifier.
   5. `summary` and the battery record.
4. **Derived values the check covers (beyond the eleven rows).** 12 + 66 = 78 pair-check tests; 75 s, 12.5 min
   and 2.1 h for the three counts at an illustrative 400 episodes per second (74.9 s, 748.9 s, 7,489 s) and 21 h
   at a tenth of that; the floor ln(1/δ)/(ε·n) = 1.0 × 10⁻³ at ε = 0.1 and n = 29,956; 6 × 10⁴ fragments against
   3 × 10⁶ episodes (fifty times fewer) and the coefficient of variation √(6 × 0.9/(0.1 × 10⁴)) = 7.3%;
   1 − 0.05^(1/30) = 0.0950 and ln(20)/30 = 0.0999 (the approximation that is not used); 86/98 = 0.878 and
   1 − 1/e = 0.632; √2 = 1.414 for the box cone.
5. **Logging.** The script sources the shared helper of the end-to-end harness and writes
   `target/e2e-logs/nemesis_known_answers/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
   `bead` (`N26b-17`), `step`, `event`, the exact command line, exit code, wall time, the evidence block where
   the row runs through a verb. Per row: the KA number, the case, the site and tier, expected and observed
   values with units and tolerance, the derivation file, and for the control the mutant or planted input and
   the assertion that failed. On failure: the first row whose observed value differs (with both values) or
   whose control passed. Final `summary`: rows passed, rows `not run` with reasons, controls caught, of eleven;
   `gates: []` (the battery records no gate; the gates' own scripts cite its rows).
6. **Record.** A battery record in the conformance ledger: the registry view's hash, the per-row outcomes, the
   per-control outcomes, the commit and fingerprint. The exit review cites it.

## Acceptance criteria

- [ ] The registry view has eleven entries, each with a test that exists, a control, a tier, a site and a
      derivation file; the registry check passes and fails when a control is removed.
- [ ] `scripts/e2e/nemesis_known_answers.sh` exits 0 at M3 with ten rows passed and KA-668 `not run`, and from
      M4 with eleven rows passed; it exits non-zero when any row fails or any control passes.
- [ ] Every control is observed to fail its row on the mutant build or planted input (eleven of eleven from M4).
- [ ] The derived-value check reproduces every number listed in point 4 and in the derivation files.
- [ ] Rows that name the referee or lockstep sites run there as well as on the host, and the log has one line per
      (row, site).
- [ ] The log has the per-row fields above and a final summary line.

## Considerations

- KA-661's control is an arm, not a mutant: card-uniform randomization at the same budget. The row is recorded
  as passed when the trap is found with a witness; the comparison of the two arms' counts is reported and is
  the business of the search's own gate, not of this battery.
- KA-667's interval coverage has no threshold in the plan; the runner records the measured share and pins it
  once measured, as the catalogue's bead specifies.
- A known answer that the code stops reproducing is a defect in the code, never a reason to edit the expected
  value; the registry's values change only with a derivation on file and a recorded reason.
