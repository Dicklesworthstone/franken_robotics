## Background

The chapter closes its mechanisms with a table of eleven known answers: cases whose right result is known before
any code runs, each paired with a negative control, a planted wrong implementation or wrong input that must make
the row fail. The program's rules for such rows: a known answer has a derivation on file, a tolerance with a
reason, a negative control that is a mutation (not merely a boundary behaviour), and a tier and site (it runs
first on the weakest site that can decide it). A row whose control has not been shown to fail cannot support a
gate, and every convergence gate needs a registered control it catches.

The chapter adds a rule of its own: **a value that follows from a stated formula is a derived value and a known
answer; every other number carries its label** (FACT, TARGET, HYPOTHESIS). So the battery has two parts: the
eleven table rows, and a check that every derived number printed in the chapter's mechanisms is reproduced from
its formula.

The individual mechanism tests each cover their own rows. This bead is the battery as a whole: one registry
view, one runner, one log in which all eleven rows and all eleven controls appear with expected and observed
values, so that an exit review reads one table.

## Scope

In: the runner's view of the battery (row → test → control → tier and site), a table of the script and not a
registry file; the runner script; the derived-value check; the summary record; the resolution of the two
registries' planned owner paths at the M3 exit; the observed-to-fail demonstration of every known-answer control
and of every counterexample control due at M3, recorded by the control runner (N38b-04) in the control history.
Out: the registry of known answers itself (N26-KA) and the counterexample registry (N26-CX), which depend on no
mechanism and so leave the demonstration to this runner; the tests that compute each row (the mechanism beads);
the gates (each has its own script); the derivation files (N26b-16); the four counterexample controls due at M4
(CX-293, `nemesis-late-01` to `-03`), demonstrated by the audit script's self-test (N26b-07).

2. **The runner's view (DESIGN: data of the script, not a registry file).** The suite has one physical file per
   registry (`crates/frob-conformance/registry/known_answers.toml`, `controls.toml`, …; STD-TEST), and a
   chapter's own file beside them is a lint failure, so the view is a table at the head of the runner script:
   one entry per row with `ka`, `test` (the bound test `ka_<nnn>_…` and its tier target, or the script and step
   for a row defined on the surface) and `control` (the control record `NC-nnnn` that the seeding tool of
   N38b-05 made from the row's `control.text`, or the planted input, and the assertion it must break). Truth,
   tolerance, tier, sites, derivation path and `due` are read from the row of `known_answers.toml` (N26-KA) at
   run time and are never repeated in the table; the runner fails on a `ka` that file does not hold. The
   runner also fails if a row has no control record, or, for a row due at the current milestone, if its
   control has never been observed to fail or its named test does not exist.
3. **Runner, `scripts/e2e/nemesis_known_answers.sh` (numbered).**
   1. `start`: build identity, the registry view's hash, hardware fingerprint, the sites available.
   2. For each row due at the current milestone, on each site its tier names: run the row's entry by the
      Gauntlet's run form (ADR-GAUNT-01, BD-025), `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test
      g0_laws|g1_known_answers -- KA-<nnn>`, which dispatches the binding `ka:<id>@<site>` to the owner's check
      function and writes a hash-named receipt (N38a-02, N38a-13); and, for rows defined on the surface, the
      `frob` command as well, for example `frob nemesis cover --incidence cover_worked_40x18.json --slots 6
      --greedy-only --json` for KA-669 (a read verb) and `frob nemesis bound quad-tray --task t:kitchen-tray
      --tier batch-cpu --target 1e-4 --delta 0.05 --mode certify --estimate --key nk-2-664 --json` for KA-664
      (the estimate prints the 29,956 the row expects). Record expected and observed, with the receipt hash.
   3. For each row: run its control through the control runner (N38b-04), the same entry with `--features
      gauntlet-mutations` and the row's mutant selected, or with the planted input, and require the row to fail
      there. A control that passes is a failure of the battery.
   4. Owner paths: run N26-KA's check `owner_paths_exist` and N26-CX's check `caught_by_exist`. At the M3 exit
      every known-answer row must be `resolved` except KA-668 (its owners N26b-02 and N26b-07 land by M4), and
      every counterexample entry due at M3 must have its `caught_by` `resolved`; a row still `planned` fails the
      runner with the row and its planned path named.
   5. Known-answer demonstration: each control run of step 3 goes through the control runner (N38b-04), which
      writes the control's `last_seen` and one `caught` or `missed` line (row, owning test, control, commit,
      run identity) of `crates/frob-conformance/registry/control_history.ndjson`, so that "observed to fail
      under its negative control" is on file per row and not only in a log; no field is written by hand.
   6. Counterexample controls: for each N26-CX entry due at M3 (CX-288 to CX-292, CX-294, CX-295, and the late
      entries `nemesis-late-04` to `-06`, cited by tag until the allocator issues their numbers), build or plant
      its mutant, run each `caught_by` test or end-to-end step against it through the control runner, and
      require it to fail; the runner's `caught` line is the record (what earlier forms called `first_caught` is
      the first such line). A `caught_by` that is a step of another
      chapter script (the bound script N26a-30 for CX-290 and CX-291, the guard script N26a-16 for CX-295, the
      shrink script N26a-34 for CX-288, the oracle script N26a-33 for CX-289, the exploration script N26a-31 for
      CX-292) is run through that script's mutant self-test; a `caught_by` in the hard-world-set bead (BD-275,
      for CX-294) or in the invariant ledger (N26b-15's crate-wide INV-NEMESIS-01 test, for CX-289) is run as
      its crate test. Where the mutant is shared with a known-answer
      control (for example `nemesis-oracle-point-robot` for CX-289 and KA-660) the one run serves both and is
      recorded in both.
   7. Derived values: run `derivations_numbers` (the recomputation of every number the chapter's derivation
      files print) and list each value with its formula identifier.
   8. `summary` and the battery record.
4. **Derived values the check covers (beyond the eleven rows).** 12 + 66 = 78 pair-check tests; 75 s, 12.5 min
   and 2.1 h for the three counts at an illustrative 400 episodes per second (74.9 s, 748.9 s, 7,489 s) and 21 h
   at a tenth of that; the floor ln(1/δ)/(ε·n) = 1.0 × 10⁻³ at ε = 0.1 and n = 29,956; 6 × 10⁴ fragments against
   3 × 10⁶ episodes (fifty times fewer) and the coefficient of variation √(6 × 0.9/(0.1 × 10⁴)) = 7.3%;
   1 − 0.05^(1/30) = 0.0950 and ln(20)/30 = 0.0999 (the approximation that is not used); 86/98 = 0.878 and
   1 − 1/e = 0.632; √2 = 1.414 for the box cone.
5. **Logging.** The script sources the shared helper of the end-to-end harness and writes
   `target/e2e-logs/nemesis_known_answers/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
   `bead` (`N26b-17`), `step`, `event`, the exact command line, exit code, wall time, the evidence block where
   the row runs through a verb. Per row: the KA number, the case, the site and tier, expected and observed
   values with units and tolerance, the derivation file, and for the control the mutant or planted input and
   the assertion that failed. On failure: the first row whose observed value differs (with both values) or
   whose control passed. Per counterexample entry: the CX or provisional number, the mutant, each `caught_by`
   test and its outcome under the mutant, and the control-history line written. Per registry row of either file: its
   owner path and `planned` or `resolved`. Final `summary`: rows passed, rows `not run` with reasons, controls
   caught, of eleven; counterexample controls caught, of ten due at M3; rows still `planned`; `gates: []` (the
   battery records no gate; the gates' own scripts cite its rows).
6. **Record.** A battery record in the conformance ledger: the registry view's hash, the per-row outcomes, the
   per-control outcomes, the commit and fingerprint. The exit review cites it.

## Acceptance criteria

- [ ] The runner's table has eleven entries, each with a control record; the ten due at M3 each name a test
      that exists, and KA-668 names its owners' planned test and step; every tier, site and derivation file the
      runner uses is read from `known_answers.toml`; the runner fails when a control is removed; no registry
      file of the chapter's own exists.
- [ ] `scripts/e2e/nemesis_known_answers.sh` exits 0 at M3 with ten rows passed and KA-668 `not run`; it exits
      non-zero when any row due fails or any of its controls passes. (Run at M4 or later it runs KA-668 too;
      that run is not a condition of this bead.)
- [ ] Every control of the ten rows due at M3 is observed to fail its row on the mutant build or planted input
      (KA-664's two undercount controls of N38b-57 among them), and the demonstration is a `caught` line of the
      control history per row (owning test, control, commit, run).
- [ ] At the M3 exit N26-KA's `owner_paths_exist` reports every row `resolved` except KA-668 (due at M4, where
      its owners N26b-02 and N26b-07 resolve it), and N26-CX's `caught_by_exist` reports every entry due at M3
      `resolved`.
- [ ] The ten counterexample controls due at M3 each make every one of their `caught_by` tests fail, and each
      has a `caught` line with commit and run in the control history.
- [ ] The derived-value check reproduces every number listed in point 4 and in the derivation files.
- [ ] Rows that name the referee or lockstep sites run there as well as on the host, and the log has one line per
      (row, site).
- [ ] The log has the per-row fields above and a final summary line.

## Considerations

- KA-661's control is an arm, not a mutant: card-uniform randomization at the same budget. The row is recorded
  as passed when the trap is found with a witness; the comparison of the two arms' counts is reported and is
  the business of the search's own gate, not of this battery.
- KA-667's interval coverage has no threshold in the plan; the runner records the measured share and pins it
  once measured, as the catalogue's bead specifies.
- A known answer that the code stops reproducing is a defect in the code, never a reason to edit the expected
  value; the registry's values change only with a derivation on file and a recorded reason.
