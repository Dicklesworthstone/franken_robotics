## Background

For each task family and robot class Nemesis keeps a versioned set of minimal counterexample worlds, the
hard-world set (schema `frob.hardset/1`): a list of counterexample-file identities with the failure mode each
exposes. A world enters the set only with a solvability witness (`solvable-causal` or `plant-feasible`) and only
after promotion on the referee; it leaves by a recorded decision. The set is the content of the battery `hard`
and is discovery data: never a confirmation sample, never nominal draws for a bound, never the only content of a
battery.

Every one of a hard world's credentials is tied to identities. The failure was a failure of one candidate, under
one task version's requirement, with a witness found for that candidate's body, replayed on one backend with one
set of kernel versions. Change the robot class and the witness says nothing (another body may not fit the
doorway at all). Change the task version and the requirement that was violated may no longer be the requirement.

**OPEN-NEMESIS-5. How a hard-world set is carried across a change of robot class or task version.** Owner: the
Arena lead. It blocks nothing. **Default (in force): a set belongs to one class and one task version; worlds are
re-promoted before they enter another.** The first half of the default is an admission check of the hard-world
set (a world of another class or task version is refused by `add`). This bead supplies the second half, the
re-promotion path, and the record of the decision.

Why not simply copy the worlds: a copied world would sit in a set as a "counterexample" with a witness for a
different body and a verdict under a different requirement, and the battery `hard` of the new class would count
failures in worlds that may be impossible for it. That is the shortcut ADR-NEMESIS-02 exists to block (only
solvable worlds count), reached by a side door.

Tier Solid: it composes the existing pipeline.

## Scope

In: the decision record; `nemesis.hardset carry`, the re-promotion path for both kinds of change; lineage
between the old and the new entry; what happens to worlds that do not survive.
Out: the set, its admission checks and its verb (seed BD-275); search, oracle, guard and shrinking (their own
beads); battery identity (Arena).

## Technical approach

1. **Decision record.** `docs/open/OPEN-NEMESIS-5.md`: the default; the Arena lead's ruling on the two choices
   the question leaves open, namely (a) whether carrying is offered at all or sets always start empty for a new
   class or task version, and (b) whether a carried world that still fails by a *different* mechanism is
   admitted as a new entry or dropped; and the consequences below. Until ruled: carrying is offered through
   re-promotion only, and a different mechanism yields a new, separately witnessed entry.
2. **`frob nemesis hardset carry --from <hs:…> --to-class <C′> | --to-task <t:…@v′> --candidate <design>
   [--worlds w:…,…] --key <k> --json`** (a sub-command of the existing verb `nemesis.hardset`; kind run).
   For each world of the source set (or the listed ones), numbered:
   1. *Rebuild the world.* Take the base scene and edit list from the counterexample file. For a task-version
      change, re-resolve the task; for a class change, the candidate is a design of the target class named by
      the caller (the source candidate is of another class and cannot be the subject).
   2. *Legality.* Check the final world against the target's legality profile. Outside → the world is not
      carried; reason `illegal-under-target-profile` with the bound named.
   3. *Does the candidate fail here?* Evaluate the candidate at the world's address on the fast tier under the
      target task version, on the 64 paired seeds of the shrink relation. Fewer than 48 of 64 violations by any
      one mechanism → not carried; reason `does-not-fail` (for a repaired design under a new task version this
      is the expected, good outcome, and it is reported as a regression result).
   4. *Guard and oracle, for the target.* The artifact guard with the hard-set target (one tier up, the four
      numerical variants, the energy audit, the referee) and the solvability oracle for the target candidate's
      body. `artifact-candidate` → not carried, written to the fidelity ledger. `infeasible-for-candidate` →
      not carried; counted in the infeasible column and, if every body of the class is excluded, flagged
      `infeasible-for-class`. `not-excluded` → not carried, reported.
   5. *Shrink again.* The edit list that was 1-minimal for one body and requirement need not be for another:
      run the shrinker on the carried failure. It writes a new counterexample file with new identities, digests,
      witness and passing neighbours.
   6. *Admit.* Offer the new file to the target set's `add` (all of its admission checks apply). The new entry
      records `carried_from: { set, world, entry }`; the source entry is untouched.
   The result lists, per source world, one of: `carried` (with the new world identity and whether the mechanism
   is the same or different), `does-not-fail`, `illegal-under-target-profile`, `infeasible-for-candidate`,
   `not-excluded`, `artifact-candidate`.
3. **Kernel-version changes are not this question.** A counterexample file binds to a backend, numerical profile
   and kernel versions; a kernel change invalidates stored digests by design, and the set re-promotes its
   members in place (same class, same task version). That path reuses steps 3 to 6 with the original candidate
   and is offered as `hardset carry --refresh`.
4. **Cost and estimate.** Per world: 64 episodes for step 3, six guard episodes, a witness search of up to 16
   failing-episode equivalents, and a shrink (up to the test budget × 64 episodes). `--estimate` prints the
   total before anything runs; the verb accepts the bounded wait and returns a job handle.
5. **Evidence and lanes.** Everything carried is discovery data with origin `nemesis`; the three refused uses
   of a hard world hold for carried entries; a carried set changes the identity of the battery `hard` of the
   target class.

## Acceptance criteria

- [ ] `add` of a world whose class or task version differs from the set's is refused (the default's first half,
      re-asserted here); `carry` is the only route by which such a world's content reaches the set.
- [ ] A carried entry has its own counterexample file, with digests, witness and promotion for the target
      candidate, and `carried_from` naming the source; no field is copied from the source's oracle or promotion
      blocks (checked by a field-by-field comparison on a fixture where they must differ).
- [ ] Each of the six outcomes is produced by its planted source world: a world the target also fails
      (`carried`); a world the repaired design passes (`does-not-fail`); a world with a 0.70 m doorway for a
      0.75 m target body (`infeasible-for-candidate`); a world outside the target profile; a world whose witness
      search is starved (`not-excluded`); a planted box-cone artifact.
- [ ] A world that fails by a different mechanism under the new task version is carried as a new entry with that
      mechanism and the note `mechanism: different`.
- [ ] `--refresh` after a kernel-version change re-promotes in place and leaves class and task version alone.
- [ ] The decision record exists with the ruling or the statement that the default is in force.
- [ ] Reachable through `frob --json` and MCP as a sub-command of `nemesis.hardset`; cancellation and resume by
      key are tested; outputs carry the claim product and the no-authorization flags.

## Test plan

### Unit tests
`crates/frob-nemesis/tests/hardset_carry.rs` (real pipeline on small fixtures, CPU tiers):
- `add_refuses_foreign_class_and_version`.
- `carry_six_outcomes` (one planted source world per outcome).
- `carried_entry_has_fresh_credentials` (witness controller, trace hash, digests and promotion differ from the
  source's; `carried_from` set).
- `reshrink_can_change_edit_list`: a source world of three edits that is 1-minimal for a wheeled base carries to
  a legged class as a two-edit world.
- `different_mechanism_is_new_entry`.
- `refresh_in_place_after_kernel_change`.
- `source_set_untouched` (the source set's identity is unchanged after a carry).
- `battery_identity_changes_for_target`.

### End-to-end script and logging
`scripts/e2e/nemesis_hardset_carry.sh` (shared end-to-end helper): builds a two-world source set for one class,
carries it to a second class and to a second task version with `frob nemesis hardset carry`, then `frob nemesis
hardset show` on both sets. Logged per source world: each step's outcome (legality, k of 64, guard verdict per
variant, oracle class, shrink summary), the final outcome, the new world identity and `carried_from`, and the
battery identities before and after. Logs under `target/e2e-logs/nemesis_hardset_carry/`; no gate is recorded.

### Known answers and negative controls
KA-660 (a doorway narrower than the body is `infeasible-for-candidate`, never a counterexample) is the reason a
copied world cannot be trusted. CX-289 (any world that defeats the design is a counterexample) and CX-294 (a
battery made of past failures). INV-NEMESIS-01, -04, -05 hold for every carried entry. Planted defects the tests
must catch: a carry that copies the source's witness block; a carry that skips the re-shrink and keeps an edit
list that is no longer 1-minimal; a carry that mutates the source set.

## Considerations

- The question blocks nothing, which is why this is priority 3 at M4: sets can always be rebuilt from scratch by
  searching again in the new class or task version. Carrying is a saving, and its size is unmeasured.
- A world that does not fail for the target is information: the report of a carry is also a small regression
  result for the target design, labelled as such and never as evidence of robustness.
- If the kill gate on minimal counterexample worlds fires (full failing worlds with ranked single-edit
  contrasts), step 5 becomes the contrasts computation and the rest is unchanged.
- Owner of the question: the Arena lead, because the set is the content of one of Arena's batteries.
