## Background

A **fork** is a parent episode, a fork tick and a change set: the simulated world is restored to a moment of a
recorded run, something is changed, and the run continues as a child. Forks are the instrument of counterfactual
debugging (the subsystem Autopsy, crate `frob-autopsy`), of rare-event splitting in the adversarial-world
subsystem (Nemesis) and of the sampling-based predictive controller, which forks planning worlds.

Three crates need one shared vocabulary for forks, and they sit on three layers:

- `frob-chronicle` (layer 6) owns the fork *mechanism*: snapshots, restore, the shared prefix and the verb
  `run.fork`;
- `frob-autopsy` (layer 5) owns the fork *semantics*: the five classes and the earliest tick at which a given
  change may be applied, the intervention vocabulary, attribution;
- `frob-nemesis` (layer 5) and `frob-control` (layer 4) are callers.

The workspace's layer rule L-1 says a crate depends only on lower crates (a lower layer number, or the same layer
and an earlier row of the crate map). `frob-autopsy` therefore cannot name a type of `frob-chronicle`. Rule L-10
gives the way through: a lower crate reaches a service that lives above it only through a trait it defines itself
or that `frob-core` defines. The standing inversions already include "the trace source, defined in `frob-core`,
implemented in `frob-chronicle`", and the rule states its purpose in so many words: it is what lets a layer-5 crate
such as `frob-autopsy` fork a recorded run without depending on layer 6.

DESIGN decision of this bead: the fork vocabulary (plain data types) and the fork-service trait live in
`frob-core`, module `fork`. Rejected alternatives: (a) types in `frob-chronicle`, which layer 5 could not name;
(b) types in `frob-autopsy` with `frob-chronicle` depending downward on it, which would make the replay path of
milestone M2 depend on a crate whose work package starts at M3 and would force the sampling controller (layer 4)
to depend on layer 5; (c) one copy of the types per crate with conversions, which invites the five classes
drifting apart: the gate register requires one set of five classes, defined once.

Tier: Solid. Everything here is data layout and a trait; no numerical method.

## Scope

In: the types below, their canonical JSON encodings, the trait `ForkService`, the total order on classes used to
classify a change *set*, and compile-time checks that the enum has exactly five variants.
Out: the classifier (N27a-02), fork points (N27a-03), address derivation and randomness modes as behaviour
(N27a-04), restore handling (N27a-05), the implementation of the trait and the verb (BD-205), the attribution
types `Contrast`, `CauseLabel`, `Attribution` (N27a-10, in `frob-autopsy`).

## Technical approach

DESIGN sketch (fixes intent, not signatures). Module `frob_core::fork`.

```rust
/// The classification every requested change receives before anything is restored. Exactly five.
pub enum ForkClass {
    Continuation,      // the null fork, a placebo, replay, teleport: restored bit for bit
    Exogenous,         // restart at the fork tick; nothing regenerated
    Information,       // fork tick; packet queues and filter state re-initialized; may be labelled diagnostic
    ContactAffecting,  // fork tick; contact memory discarded; first solve cold; labelled
    Structural,        // design parameters too: the authored initial condition, settled again
}
// Ord (DESIGN): Continuation < Exogenous < Information < ContactAffecting < Structural.

/// `do(factor := value)`. One declared mechanism; the model difference is stored with the fork.
pub struct Intervention { factor: FactorPath, value: Value, mechanism: MechanismId, model_diff: Blake3 }

pub struct FactorPath(String);   // "scene./floor/patch[galley-2]/film", "model.joint[*.knee].gear_ratio"
pub struct FieldPath(String);    // a field of a checkpoint: "checkpoint.contact.memory"
pub struct ForkId(Blake3);       // printed "f:<hex>"
pub struct ForkStep { fork: ForkId, child: u32 }
pub struct ForkPath(Vec<ForkStep>);              // one step per nesting level; empty for an ordinary world
pub struct ChildAddr { base: WorldAddr, path: ForkPath }   // WorldAddr = (run_seed, world, episode)

pub enum NullReplay { Bitwise, Mismatch { first_tick: Tick, stage: Option<StageId> }, NotRun }
pub enum ForkLabel { ContactMemoryDiscarded, ColdFirstSolve { iteration_cap: u32 }, InterventionFromTick,
                     Diagnostic, ForcedFork }

/// What a replicate changes beyond its intervention: nothing, one state coordinate, or one stream key.
pub enum Perturbation { None,
                        State { coord: CoordId, relative: Ratio /* 10⁻¹² or 10⁻⁷ of the coordinate's scale */,
                                sign: Sign },
                        Rekey { stream: StreamId } }

pub struct Classified { change: Intervention, class: ForkClass, earliest_valid_tick: Tick,
                        exogenous_until: Option<Tick>, forced_by: Vec<FieldPath>, labels: Vec<ForkLabel> }

/// A fork is a parent episode, a fork tick and a change set. It never mutates its parent.
pub struct Fork { parent: EpisodeId, tick: Tick, changes: Vec<Intervention>,
                  class: ForkClass, earliest_valid_tick: Tick, forced_by: Vec<FieldPath>,
                  addr: ChildAddr,            // the parent's address extended by a fork path
                  null_replay: NullReplay }   // Bitwise, or the record is unsound and nothing is attributed

pub struct ForkRequest { parent: EpisodeId, world: WorldAddr, at: ForkAt /* Tick | BeforeFailure { lead } */,
                         changes: Vec<Intervention>, classify_only: bool }
pub struct ChildSpec { changes: Vec<Intervention>, perturbation: Perturbation, horizon: Horizon }

pub trait ForkService {
    fn classify(&self, req: &ForkRequest) -> Result<Vec<Classified>, Refusal>;       // touches no state
    fn open(&self, req: &ForkRequest, cx: &JobCx) -> Result<ForkPoint, Refusal>;     // fork point + null replay
    fn spawn(&self, point: &ForkPoint, children: &[ChildSpec], cx: &JobCx) -> Result<ChildBatch, Refusal>;
    fn outcomes(&self, batch: &ChildBatch, cx: &JobCx) -> Result<Vec<ChildOutcome>, Refusal>;
}
```

Rules that belong to the types.

1. **Five classes and no sixth.** A unit test matches exhaustively on `ForkClass` and counts the variants; adding
   a variant fails the test and the contract check. The fork mechanism implements exactly these five and adds none.
2. **Class of a change set.** A request may carry several changes. Each change is classified on its own; the
   class of the set is the maximum under the order above, and the state handling of the set is the union of the
   handlings of its members (for example an information change together with a contact-affecting change
   re-initializes the packet queues and discards the contact memory). Reason for the order: it is the order of
   how much of the checkpoint survives. `Structural` is the top because nothing but the exogenous draws survives.
3. **`Intervention` is the same type as a requested change.** At M2 the verb `run.fork` accepts change sets whose
   elements are built from field paths; at M3 the intervention vocabulary of `frob-autopsy` produces the same
   type with the one-mechanism rule enforced. `model_diff` is the BLAKE3 hash of the canonical JSON of the
   difference record (which identities and compiled products the change alters).
4. **Addresses.** A child world's address is the parent's `WorldAddr` plus a non-empty `ForkPath`. The canonical
   byte encoding of `ChildAddr` is the encoding of `WorldAddr` followed by the length-prefixed steps; an ordinary
   world has an empty path and its `ChildAddr` encodes to the same bytes as its `WorldAddr`, so no existing
   address hash changes.
5. **`earliest_valid_tick` and `forced_by` are always present**, including on success, so a caller sees why a
   class was assigned. `exogenous_until` is the first tick at which recorded state depends on the changed field,
   when one exists: before it the change would have been exogenous.
6. **No physics in `frob-core`.** The trait's methods take and return identities, ticks, digests and outcome
   records. Outcome records (`ChildOutcome`) carry the verdict, failure class, binding atom, failure time and the
   chained state digest of the child; they are defined here because both `frob-autopsy` and `frob-nemesis` read them.
7. **Wire names.** The JSON spellings are fixed here: `continuation`, `exogenous`, `information`,
   `contact-affecting`, `structural`; null replay `bitwise`, `mismatch`, `not-run`.
8. **Determinism.** All of this is class D0 (exact): types, hashes and orders.

Layering as it ends up: `frob-chronicle` implements `ForkService`; the daemon hands an implementation to layer-5
crates through the job context; `frob-autopsy`, `frob-nemesis` and `frob-control` name only `frob_core::fork`.

## Acceptance criteria

- [ ] `frob_core::fork` exists with the types above; `xtask check-layers` passes with `frob-autopsy` (layer 5)
      depending on no layer-6 crate.
- [ ] `ForkClass` has exactly five variants; the exhaustiveness test fails when a sixth is added (checked by a
      planted patch in the test suite).
- [ ] The class of a change set equals the maximum of its members' classes under the stated order, for all 2⁵ − 1
      non-empty subsets of classes.
- [ ] `ChildAddr` with an empty path encodes to the bytes of its `WorldAddr`; two different fork paths never
      encode to the same bytes (property test).
- [ ] Round trip: every type serializes to canonical JSON and back to an equal value; the wire names are the
      seven strings fixed above.
- [ ] `frob-core`'s `CONTRACT.md` gains the fork vocabulary under inputs, outputs and invariants, and states
      that the trait is a standing inversion under rule L-10.

## Test plan

### Unit tests
`crates/frob-core/tests/fork_vocab.rs`:
- `five_classes_exactly`: an exhaustive `match` plus a variant count of 5.
- `class_order`: `Continuation < Exogenous < Information < ContactAffecting < Structural`.
- `set_class_is_max`: for each of the 31 non-empty subsets of classes, the set class is the maximum; for example
  {Exogenous, Information} → Information; {ContactAffecting, Structural} → Structural.
- `child_addr_encoding`: `WorldAddr (run_seed 901, world 5120, episode 3)` with an empty path encodes to exactly
  the canonical bytes of that `WorldAddr`; with path `[(f, 0)]` and `[(f, 1)]` the encodings differ; nested paths
  of depth 2 differ from depth 1.
- `fork_path_injective` (property, 10⁴ random paths): equal encodings imply equal paths.
- `json_round_trip` for `Intervention`, `Classified`, `Fork`, `Perturbation`, `NullReplay`.
- `wire_names`: the exact strings.
- `perturbation_sizes`: `State` accepts the relative sizes 10⁻¹² and 10⁻⁷ as exact rationals (1/10¹² and 1/10⁷).

### End-to-end script and logging
None of its own: the types are exercised from the user's side by `scripts/e2e/run_fork.sh` (N27a-08), which logs
the class strings, fork identities and child addresses it reads from envelopes.

### Known answers and negative controls
Negative controls: a patch that adds a sixth class; a patch that makes two different fork paths encode equally
(the injectivity property must fail). Determinism lanes: encodings are identical in debug and release and across
platforms (bytes compared against a committed vector).

## Considerations

- The type sketch in the plan's appendix carries a stale note saying one chapter lists five classes and another
  three; both chapters and the sketch itself now list five. This bead implements five.
- `Information` is placed below `ContactAffecting` in the order by this bead; the plan does not order the middle
  classes. Nothing depends on the relative order of those two except the single `class` field of a mixed set, and
  the per-change classes are always reported beside it.
- If the trait grows a method that needs a layer-6 type, the fix is a new plain type here, never a dependency.
