## Background

A design is never modified in place. Every typed edit or patch produces a new immutable version identified by
the hash of its canonical term (`DesignId`), so design versions form a content-addressed graph whose edges are
typed edits. That graph is the lineage. It is what lets an agent ask "what changed between these two designs?",
"which of my edits made the knee overheat?", and later (the fourth milestone) "which edit broke stair
climbing?" by bisection, and what lets several agents merge their work without caring who synchronized first.

This bead delivers the graph and the two read-only queries that need no simulation:

- `design.diff`: the structural and parameter difference of two versions, lowered to a list of typed edits,
  with the effect on the symmetry groups.
- `design.blame`: the edit that last changed a field or a derived quantity.

Two properties of the lineage are fixed here because later mechanisms rely on them. An edit returns its
invalidation set: `design.edit` takes the expected parent and an idempotency key, refuses a stale parent, and
returns the new version, the structural and parameter diff, the symmetry effect, and the set of derived assets
and stored verdicts whose dependency support the edit touches, so the agent sees what its change put in
question before it spends anything. And migration keeps old replay possible: a schema migration reads the old
object and writes a new one with migration provenance; the old version stays addressable and replayable with
the worker version that produced it.

Rejected: a linear undo history per agent (no branches, no merge); diff as a text diff of the file (order and
formatting noise, and no typed edits to replay); blame from timestamps (arrival order is not content).

Seed done-condition: blame on a three-edit lineage names the edit that changed a chosen field.

## Scope

In: the lineage tables and API in `frob-opt::lineage`, recording on every edit and patch, the diff algorithm,
the blame algorithm for source fields and derived quantities, both verbs. Out: typed edits, patches, stale-parent
refusal and idempotency (BD-058, BD-059); computing the invalidation set (BD-063); bisect and merge (BD-343);
revalidation of verdicts (BD-292, BD-347).

## Technical approach

1. **Graph (DESIGN; tables in the ledger).** `lineage_node {design_id, schema_version, canon_rev, created_seq}`;
   `lineage_edge {child, parent, patch_id, ops (the typed edits, canonical), kind: edit | patch | migrate |
   merge, idempotency_key, agent, session, invalidation_set_ref, symmetry_effect, seq}`. Nodes are keyed by
   content, so two different edit paths that reach the same term meet at one node (the graph is a directed
   acyclic graph, not a tree). A node may have many children (branches) and, from the fourth milestone, several
   parents (merge). Edges are append-only; `seq` is the ledger's commit sequence, never a wall-clock time.
2. **Recording.** `design.edit` and `design.patch` call `lineage::record(parent, child, ops, …)` inside the same
   ledger transaction that creates the version, so a version without an edge to its parent cannot exist (the
   root of a lineage is a `design.new` or an import, with a `root` marker and the import's loss-report id).
   A migration writes a `migrate` edge whose provenance names the migration and both schema versions; the old
   node stays.
3. **`design.diff A B [--as edits|summary] --json`.**
   1. If one version is an ancestor of the other, take the edge path between them, concatenate the edits and
      normalize: cancel an edit followed by its inverse; merge successive `set-param` on one path into one;
      drop edits whose net effect is nil. If several paths exist, take the one with the fewest edits (ties by
      canonical bytes).
   2. Otherwise compute a term diff on the two canonical terms: match subterms bottom-up by content hash
      (identical subtrees are skipped), then by path and constructor; emit `set-param`, `reshape`, `set-fill`,
      `set-material`, `set-limits`, `regear`, `swap-actuator`, `move-mount`, sensor and payload edits for
      matched nodes with different fields, and `add-limb`, `remove-limb`, `closure-add`, `closure-remove`,
      `mirror`, `radial` for unmatched structure.
   3. Verify: applying the emitted list to A must give exactly B's `DesignId`. If it does not, the verb returns
      the structural summary only and flags `edits: unavailable` with the first mismatching path; it never
      returns an edit list that does not reproduce B.
   4. Output: the edit list; a structural summary (bodies, joints, actuators, sensors added, removed, changed);
      a parameter table (path, old, new, unit); the symmetry effect: both symmetry groups (mechanical and
      observation-preserving) of A and of B and the generators gained or lost with their breakers; and the
      predicted invalidation scope per edit (which products the edit kind invalidates: the subterm and its
      dependents; the whole-robot sums; global).
4. **`design.blame <design> <target> --json`**, where the target is a source field path
   (`/limbs/…/body/region/capsule/1`) or a derived quantity (`mass.total`, `stability.tipover.lateral`,
   `envelope.knee.continuous-margin`).
   1. Source field: walk the lineage from the version toward the root (at a merge, into the parent whose value
      of the field equals the child's; if both do, the lower `DesignId`); return the most recent edge after
      which the field's value differs from its value before, i.e. the edit that introduced the present value.
   2. Derived quantity: the read set of the quantity (its influence record) gives the source fields it depends
      on; walk as above over edges whose write set meets the read set; for each candidate edge compare the
      quantity's value on parent and child (memoized analysis results; recomputed if absent) and return the
      most recent edge across which the value changed. An edge that wrote a read field without changing the
      value is listed as `touched-no-change`.
   3. Output: the edge (patch id, the typed edits, agent, session, sequence number), the value before and
      after, the number of versions walked, and the path. A field never changed since the root returns the
      root, labelled `since-root`.
5. **Verbs.** Both kind `read`, cluster `design`, first milestone M1, capability `design:read`, phase `review`
   (`diagnose` in the phase ledger), idempotent. Schemas `frob.design.diff.out/1`, `frob.design.blame.out/1`.
   Evidence: class `Tested` for source-field results (exact, D0); the class of the analysis for derived
   quantities. Exit 0; exit 2 for `edits: unavailable`; exit 3 for an unknown version or target.

## Acceptance criteria

- [ ] Every edit and patch creates exactly one lineage edge in the same transaction as its version; a crash
      between the two is impossible (tested under the ledger's fault injection).
- [ ] On a three-edit lineage (thigh length 0.21 → 0.24 m; knee ratio 1.55 → 1.8; shank material aluminium →
      carbon laminate), `design.blame` on the knee ratio names the second edit with values 1.55 and 1.8; on the
      thigh length it names the first; on a never-edited field it returns `since-root`.
- [ ] `design.blame` on `mass.total` names the third edit (the material change) and lists the first as a
      change too when asked for history; an edit that renamed a body is never named.
- [ ] `design.diff` between the root and the head returns three edits that reproduce the head's `DesignId`;
      between two branches it returns a term diff that reproduces the target; an edit followed by its inverse
      yields an empty diff and the same `DesignId`.
- [ ] The diff of a quadruped before and after `move-sensor` reports the mechanical group unchanged and the
      observation-preserving group recomputed, with the breaker.
- [ ] A migrated design has a `migrate` edge; the old version is still readable and diffable.
- [ ] Both verbs are reachable through `frob --json`, schema-valid, byte-identical on repeat.

## Test plan

### Unit tests

`crates/frob-opt/tests/lineage_basics.rs`:
- `edge_recorded_atomically`; `content_addressing_merges_paths`: edits a·b and b·a on disjoint fields reach one
  node with two incoming paths.
- `diff_ancestor_path_normalized`: set-param 0.21 → 0.22 → 0.24 becomes one edit 0.21 → 0.24; an edit and its
  inverse cancel.
- `diff_roundtrip_property`: for 10³ random pairs of versions from random edit sequences on the four templates,
  apply(diff(A, B), A) has B's `DesignId`, or the verb reports `unavailable`; the unavailable share is logged
  and must be zero for sequences without structural edits.
- `diff_structural_add_remove_limb`.
- `blame_three_edit_lineage` (the seed's condition); `blame_since_root`; `blame_derived_mass_total`;
  `blame_skips_rename`; `blame_touched_no_change`: a `set-fill` from solid to an equal-mass declared shell.
- `blame_through_migration`.
- `symmetry_effect_reported`.

### End-to-end script and logging

`scripts/e2e/atelier_lineage.sh` (bead N28a-31), M1 part: creates a design from the `quad-mammal` template,
applies the three edits with `frob design edit`, runs `frob design diff root head --json` and three
`frob design blame` calls, and asserts the named edits and values. Logged: each command, the `DesignId`s, the
edit lists, the blamed patch ids, before and after values, versions walked.

### Known answers and negative controls

Known answer: the three-edit lineage above (hand-specified). Negative controls: a mutant blame that returns the
most recent edit touching any field (names the third edit for the knee ratio; caught); a mutant diff that emits
edits without the verification step (caught by the round-trip property on a structural case); a lineage edge
written outside the version transaction (the fault-injection test finds a version with no parent edge).
Determinism: D0; results independent of the order in which agents' edges were appended.

## Considerations

- Blame on a derived quantity can cost one analysis per version walked; results are memoized per `ModelId`, and
  the verb takes `--max-versions` (default 64) and reports where it stopped.
- The minimal edit list between two unrelated designs is not unique; the verb returns a canonical one, and its
  only guarantee is that it reproduces the target.
- Names are not content: renaming a body changes the `DesignId` and no mechanical product; diff reports it and
  blame ignores it for derived quantities.
- Merge of lineages from several agents must be commutative, associative and idempotent (INV-ATEL-09); the
  append-only, content-keyed tables here are what make that possible at the fourth milestone.
