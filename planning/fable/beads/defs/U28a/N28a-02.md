## Background

The studio's loop is

```
 design ──► check ──► synth controller ──► simulate ──► explain ──► edit ──► compare ──┐
   ▲        (static,   (seconds)           (batch or     (telemetry,  (typed)  (anytime-  │
   │         seconds)                       GPU)          energy,              valid or   │
   │                                                      forks)               fixed-n)   │
   └── revalidate ◄── lineage, archive, ladder, cascade, optimize, train ◄────────────────┘
```

and its order is a rule, not a suggestion (ADR-ATEL-01): check before you simulate, simulate before you train,
train before you claim. Each stage is cheaper than the next by roughly an order of magnitude (HYPOTHESIS; the
phase ledger settles it), and each can refuse the next. A simulation of a design whose inertia is physically
inconsistent, or a training run on a design that cannot stand, spends the expensive stage to rediscover what the
cheap one already knew.

The invariant this bead enforces is INV-ATEL-01: **no stage of the loop runs on a design the previous stage
refused, unless the request carries an override that is recorded on every downstream result.** The override
exists because an agent sometimes needs to see a refused design fail (to debug the analysis, or to show that a
static exclusion was conservative); what must never happen is that a result obtained under an override looks like
an ordinary result.

Two things were added to the loop after its first formulation, and this bead wires the first of them into the
verbs: an edit does not only produce a new design, it produces an invalidation set (the verdicts and derived
assets the edit puts in question), and `result.revalidate` says which survive; and a population of designs does
not walk the loop one at a time, it climbs the evaluation ladder together in mixed batches, with the co-design
cascade deciding who climbs. Rejected alternative: a convention in documentation (agents skip conventions; a
precondition in the verb executor cannot be skipped).

## Scope

In: the stage-precondition check in the verb executor for `control.synth` and `sim.run` (M1), the override flag
and its propagation, the stored stage verdicts it reads, the hook that later verbs (`train.start`, `eval.compare`,
`opt.*`, claim-citing verbs) register with. It needs the stage records that the `design.check` runner writes
(N28ap1-01), not the analyses themselves, so it proceeds in parallel with them; the legs on real refused designs
run in the end-to-end script once the analyses are assembled (BD-110, N28a-29). Out: the analyses, the runner and
`design.check` (N28ap1-01, BD-110); invalidation sets (the
edit and compile beads; BD-063); revalidation (BD-292, BD-347); the ladder and the cascade (BD-329, BD-352).

## Technical approach

1. **Stage graph (DESIGN, data in `registries/loop.toml`).** Stages: `check`, `synthesize`, `simulate`, `train`,
   `claim`. The file declares, per verb, the stage it belongs to and the stage it requires: `[[verb]] name =
   "sim.run"`, `stage = "simulate"`, `requires = "check"` (likewise `control.synth` with `stage = "synthesize"`;
   `requires = "simulate"` for `train.start`; `requires = "train"` or `"simulate"` for a claim-citing verb, by
   claim kind), and a list `outside_loop` of the `run` verbs that belong to no stage (`artifact.export`,
   `run.export`, `spark.probe`, …). The declaration lives in this file and not in the verb's registry row,
   because the entry schema of `registries/verbs.toml` is closed and the loop is this subsystem's data. The
   build script of `frob-verbs` reads the file beside the registry and runs two lints: `loop-stage-undeclared`
   (an entry of kind `run`, or a `run` action, that is neither given a stage nor listed in `outside_loop`; so a
   new `run` verb cannot skip the rule by omission) and `loop-unknown-verb` (a name that is not a registry
   entry).
2. **Stored stage verdict.** For the bound `ModelId` (and task or scene where the request binds one), the
   executor looks up the preflight stage records in the ledger, as the `design.check` runner writes them
   (N28ap1-01): `{stage, model_id, verdict: passed | refused | undecided, codes, finding_ids, timings, budget}`,
   keyed by the model identity restricted to the fields the stage read, the analysis versions and the bindings,
   so an edit that does not touch those fields leaves the record valid. The loop stage `check` is read from them
   (DESIGN): `refused` if any applicable record (stages 1 to 6, and 7 and 8 when the request binds a scene) is
   `refused`; otherwise `absent` if any applicable record is missing; otherwise `undecided` if any is
   `undecided`; otherwise `passed`. The record named by a refusal is the earliest refused stage.
3. **Decision table.**

   | Previous stage record | No override | With `--override <stage>` |
   |---|---|---|
   | `passed` | run | run (the override is ignored and a warning says so) |
   | `absent` | run the previous stage first if it is of kind `read` and within budget (check is; under 2 s), then decide; otherwise refuse | run, flagged |
   | `undecided` (budget exhausted) | run, with the warning `previous-stage-undecided`; `undecided` is never a pass and never a refusal | run, flagged |
   | `refused` | refuse | run, flagged |

4. **The refusal.** The verb re-issues the first refusing finding of the previous stage: its original code (for
   example `FROB-REF-124`, a static margin not met), `pointer` to the stage and finding, `retry: after-change`,
   and ranked repairs = the finding's typed edits followed by "pass `--override check` to run anyway; every
   downstream result will carry the override". Exit code 3. DESIGN: no new refusal code is introduced here; the
   refusal registry defines none for this case.
5. **The override record.** `--override <stage>[,<stage>]` requires a free-text `--override-reason`. Both reach
   both surfaces by one generator rule, not by hand (INV-TETHER-01): every verb with a `requires` in
   `registries/loop.toml` gains the optional input properties `override` (array of stage names) and
   `override_reason` (string of at most 500 characters, DESIGN), and `override` without
   `override_reason` is `FROB-REF-802` with `pointer: /override_reason`. This is variation 10 of NJL-01's
   variation table (a field-driven variation beside `needs_groups` and `params`, appending no code), and this
   bead writes its arm in NJL-01's `derive.rs` in the same change that adds the two properties: the build script
   of `frob-verbs` reads `registries/loop.toml` for the arm, and the test `override_properties_generated` is the
   variation's test. The executor
   writes an evidence record `{override: [stages], reason, refused_codes, session}` and adds the condition
   `stage-override:<stage>` to the claim product of the result (the claim product is the typed statement of what
   a result asserts and how strongly; its `conditions` field is a union over inputs). Because conditions
   propagate by union through `ClaimProduct::combine`, every result that consumes the run (a summary, a
   comparison, a report, a policy trained on it) carries the condition without further code. A result with a
   `stage-override` condition names no claim in `evidence.claims` (it may not be cited for any of the seven claim
   kinds) and prints the override in reports.
6. **Edits.** After `design.edit` or `design.patch`, the new version has no stage records except those the
   invalidation set left untouched; the executor therefore re-runs or requires `check` for exactly the stages
   whose inputs changed.
7. **Envelope.** `warnings` carries `previous-stage-undecided` or `stage-override:<stage>`; `next_actions` on a
   refusal are the repairs. Determinism: the decision is a pure function of ledger state at a pinned frontier
   and the request.

## Acceptance criteria

- [ ] `frob sim run` and `frob control synth` on a design whose stored `check` stage record is `refused` (a
      record planted in a scratch ledger; the same on a real refusal in N28a-29's script) return exit 3 with the
      original refusal code, a pointer to the stage, and the override among the repairs.
- [ ] The same calls with `--override check --override-reason "…"` (and a fresh `--key`) run, and the run's
      envelope and a result combined from it by `ClaimProduct::combine` both carry `stage-override:check` and an
      empty `claims` list (the echo through `explain.run` is asserted by N28a-29's script, which depends on the
      explain verbs).
- [ ] An `undecided` check lets the run proceed with the warning and no override condition.
- [ ] A design with no stored check runs the check first (visible in the cost block) and then proceeds or refuses.
- [ ] After an edit that touches only a display name, the stored check record is reused (no re-check); after a
      mass edit it is not.
- [ ] A property test over random stage histories shows no path by which a result lacking the condition has a
      refused ancestor stage (INV-ATEL-01).
- [ ] A verb of kind `run` that is neither given a stage in `registries/loop.toml` nor listed in its
      `outside_loop` fails the build of `frob-verbs` with `loop-stage-undeclared`; a name absent from the
      registry fails with `loop-unknown-verb`.
- [ ] `frob schema --verb sim.run --in --json` and the MCP tool `sim_run` both show `override` and
      `override_reason`; a verb outside the loop shows neither.

## Test plan

### Unit tests

`crates/frob-verbs/tests/loop_order.rs`:
- `refused_check_blocks_sim`: a planted stage-3 record `refused` with code 124 (a top-heavy design) → `sim.run`
  exit 3, code 124; the same for `control.synth`.
- `check_verdict_aggregation`: records passed, passed, undecided → `undecided`; one refused → `refused`; a
  missing stage-4 record → `absent`; a scene-bound request with no stage-7 record → `absent`.
- `override_runs_and_marks`: same with override → exit 0 or 2; conditions contain `stage-override:check`.
- `override_propagates_through_combine`: a comparison built from one overridden and one clean run carries the
  condition; `claims` is empty.
- `undecided_is_neither`: a check stopped at budget → run proceeds, warning present, no condition.
- `absent_check_is_run_first`: cost block shows a `check` phase before `simulate`.
- `rename_keeps_stage_record`, `mass_edit_drops_stage_record`.
- `inv_atel_01_property`: 10⁴ random sequences of check, edit, override and run requests on a three-design
  fixture; for every produced result, either all ancestor stage records are `passed`/`undecided` or the
  condition is present.
- `override_without_reason_refused` (schema refusal `FROB-REF-802`, exit 3, `pointer: /override_reason`).
- `loop_lints`: a `synthetic` registry with a `run` entry absent from `registries/loop.toml` fails with
  `loop-stage-undeclared`; a `loop.toml` row naming `sim.rn` fails with `loop-unknown-verb`.
- `override_properties_generated`: the generated input schema of `sim.run` and `control.synth` has `override`
  and `override_reason`; that of `artifact.export` has neither.

### End-to-end script and logging

Part of `scripts/e2e/atelier_check.sh` (bead N28a-29): after the planted top-heavy design is refused by
`frob design check`, the script runs `frob sim run` (expects exit 3), then with the override (expects the
condition), then `frob explain run` on the overridden run (expects the condition echoed). Logged in the
script's NDJSON (STD-E2E fields: `ts`, `script`, `bead` = N28a-02, `step` = `loop_order`, `event`, the exact
command line, exit code, wall time, the envelope's `evidence` block): the refusal code and pointer, the
`conditions` array, the `claims` list, and the stage records read with their keys; on failure the first
differing value and the ledger path.

### Known answers and negative controls

Negative controls: a mutant executor that consults the stage record only for `sim.run` and not for
`control.synth` (the test for the second verb fails); a mutant `combine` that drops conditions (the propagation
test fails); a run on a refused design with the override flag stripped from the stored request (the property
test finds the unmarked result). Determinism: the same request at the same ledger frontier gives the same
decision on repeat and across worker counts.

## Considerations

- OPEN (owner: surface lead; fail-closed default in force): whether "previous stage refused" should have its own
  refusal code. The default re-issues the upstream code so that the agent's repair is the same typed edit either
  way.
- The automatic run of an absent check is limited to stages of kind `read` within their time budget; no verb
  silently starts a simulation to satisfy a training precondition.
- The blinded qualification lane refuses any candidate whose lineage carries a `stage-override` condition; that
  refusal belongs to the lane and is listed here so the condition's name stays stable.
- Risk: agents learn to pass the override routinely. The phase ledger and reports count overridden runs per
  session, and the report line makes them visible.
