## Background

`frob-analyze` holds 26 static analyses (A-01 mobility to A-26 regime atlas). They answer design questions in
seconds, before any simulation, and their main value is feedback an agent can act on: a typed problem with a
ranked list of typed edits that would fix it. This bead defines the one contract all of them implement, so that
`design.check`, the per-analysis verbs, the memo graph, the evaluation ladder and the reports can treat an
analysis result uniformly.

Every analysis returns its result with an evidence class (`Estimated` < `Tested` < `Certified` < `Proved`), the
model identity it was computed for, and, when it finds a problem, ranked repairs as typed edits. Four further
rules are part of the contract, each from a failure that was demonstrated:

1. **A bound says which side it is on.** A feasibility result is typed `exact`, `inner` (everything reported
   feasible is feasible) or `outer` (everything reported infeasible is infeasible), and it names the authority
   model it assumed. DESIGN, because the same body gives different answers under different load-sharing models:
   in an executed stance enumeration (FACT, plan-time pilot), under independently commanded foot forces a stance
   needs 155 N at the worst foot, and under equal passive springs the forces are (175, 115, 85, 25) N against a
   160 N cap. A result that omits the authority model would admit the body for a suspension that cannot hold it.
2. **An exclusion encloses every state and every energy source.** A static or energy argument may exclude a
   design only for a model whose states and energy sources it encloses. The standing example: lifting 8 kg over
   a 12 mm rise needs 0.94176 J; a 0.90 J budget excludes the passive crossing; 0.05 J of approach kinetic
   energy, absent from the budget, removes the exclusion.
3. **An analysis is a memo node.** Its key is the model identity restricted to the fields it reads, its own
   version and its parameters; its determinism class is D0 (exact) for the exact analyses. An edit that does not
   touch those fields recomputes nothing.
4. **A screening analysis is labelled as one.** Gait-orbit results (A-04), observability-Gramian conditioning
   (A-17) and regime-atlas regions (A-26) are screening signals. They may discard under the rules of the
   evaluation ladder and may not establish a comparison.

Rejected alternatives: free-text findings (an agent cannot apply prose); a boolean pass/fail (it hides which
side a bound is on); hand-written memo keys per analysis (a missing input in a key is exactly the failure that
serves a stale verdict).

## Scope

In: the types, the `Analysis` trait, the registration macro, the repair ranking rule, the bound typing and the
enclosure check with refusal FROB-REF-551, the declared read set and derived key, the screening label, the
serialized form `frob.finding/1`. Out: the analyses themselves; the memo store and shadow recomputation (BD-111);
`design.check` aggregation (BD-110); the verbs (N28a-05).

## Technical approach

**Types (DESIGN sketch; intent, not signatures).**

```rust
pub trait Analysis {
    const ID: AnalysisId;                 // "A-08"
    const VERSION: u32;                   // bumps invalidate memo entries
    type Params; type Output;
    fn reads() -> ReadSet;                // field paths of RobotModel, task, scene and budgets it may read
    fn encloses() -> Enclosure;           // the states and energy sources its model contains
    fn tier() -> Tier;                    // Solid | Frontier
    fn screening() -> bool;               // true for A-04, the Gramian part of A-17, A-26
    fn run(view: &ModelView, p: &Self::Params, cx: &JobCx) -> Result<AnalysisResult<Self::Output>, Refusal>;
}
pub struct AnalysisResult<T> {
    output: T, findings: Vec<Finding>,
    evidence: EvidenceClass, determinism: DetClass, model_id: ModelId,
    bound: Option<BoundSide>,             // for feasibility results
    authority: Option<AuthorityModel>,    // e.g. IndependentNormalForce | PassiveEqualSpring | Declared(name)
    screening: bool, achieved_error: Option<Qty>, status: Decided | Undecided { established: Vec<…> },
}
pub enum BoundSide { Exact, Inner, Outer }
pub struct Finding {
    code: FindingCode,                    // "A-11.knee.continuous": analysis, subject, kind
    severity: Info | Low | High | Refusing(RefusalCode),
    subject: FieldPath, message: String,
    observed: Qty, required: Qty, margin: Ratio,          // normalized margin; negative means violated
    repairs: Vec<Repair>,                 // ranked
}
pub struct Repair { edit: TypedEdit, predicted: Vec<(Metric, Delta)>, rank_key: RankKey, validity: Checked | Predicted }
```

**Repair ranking (DESIGN).** Repairs are ordered by (1) whether the predicted margin after the edit is
non-negative for the finding that produced it, (2) predicted margin gain per unit of the design's scarcest
budget (mass by default; the budget with the smallest remaining normalized slack otherwise), (3) fewest other
findings predicted to worsen, (4) the edit's canonical bytes, for a total order. A repair is `Checked` when the
analysis re-ran on the edited model inside its time budget, else `Predicted`. Repairs become the envelope's
`next_actions` as `frob design edit …` commands. An analysis that finds a problem and can name no repair says
so explicitly (`repairs: []` with `no_repair_reason`).

**Bound sides and authority.** An analysis that decides feasibility must set `bound` and, where load sharing or
actuation authority enters, `authority`. Consumers (the ladder's R0 rung, the cascade, mission queries) may
exclude a design only on an `Outer` or `Exact` infeasibility and admit only on an `Inner` or `Exact`
feasibility; anything else is `unresolved`. A result valid for one authority model is not transported to another
(the stance example above is the test).

**The enclosure rule and FROB-REF-551.** `Enclosure` lists state groups (rigid-body configuration and velocity,
actuator electrical and thermal state, battery state, contact memory) and energy sources (stored electrical,
injected electrical over the segment, gravitational potential, elastic, kinetic energy at the start of the
segment, external work). A request declares the sources present in its mission segment (from the task and the
design). When an analysis is about to return an exclusion and a declared state or source is not in its
enclosure, it refuses with **FROB-REF-551** ("an exclusion from an analysis whose model does not enclose a
declared state or energy source"), exit 3, with repairs ranked: (1) bind the missing source (for A-20: supply
the approach speed or energy), (2) accept `unresolved`. The analysis may still return findings of severity
`Info`; it may not return the exclusion.

**Memo key (rule 3).** `key = blake3(analysis id, VERSION, canonical(params), digest of the fields in reads()
taken from the model view, card versions those fields name)`. The key is derived by the framework from
`reads()`; an analysis cannot write its own. The model view handed to `run` is a capability: reading a field
outside `reads()` panics in debug and is a contract-test failure. Two property tests per analysis are generated
by the registration macro: perturbing every declared input must change the key; perturbing every field the
computation actually reads (traced by the view) must change the key or leave the output identical. Tolerance-level
reuse is allowed only for an analysis that records `achieved_error`.

**Screening label (rule 4).** `screening = true` is copied into the finding, the envelope (`evidence.screening`)
and the claim-product conditions (`screening-signal`). The comparison layer refuses to cite a screening result as
the basis of a `settled` verdict; the ladder treats it under its mode rules.

**Budget and `undecided`.** An analysis that exhausts its time budget returns `Undecided` with what it had
established. `undecided` is never a pass and never a refusal.

**Serialized form.** `frob.finding/1`, canonical JSON; quantities as decimal strings with units; stable across
platforms. Evidence classes: exact rational analyses are `Tested` by default and `Certified` when they emit a
certificate (for example the LDLᵀ certificate of inertia positivity); anything resting on an `assumed` or
`generic` card field is `Estimated`, because the class of a result is the minimum over its inputs.

## Acceptance criteria

- [ ] The trait, the types and the registration macro exist; a toy analysis registered in the crate's tests
      round-trips through `frob.finding/1` byte-identically.
- [ ] Repairs are totally ordered by the stated rule, and the same inputs give the same order on every platform.
- [ ] A feasibility analysis that returns without `bound` fails the contract test; one that reads load sharing
      without `authority` fails it.
- [ ] FROB-REF-551 fires when an exclusion is attempted with a declared source outside the enclosure, and its
      first repair names the missing source.
- [ ] The two generated property tests run for every registered analysis; a planted analysis that reads a field
      missing from `reads()` is caught.
- [ ] A screening result carries the label through the envelope and the claim product; an attempt to use it as
      the basis of a comparison verdict is refused by the consumer hook.
- [ ] A result resting on an `assumed` card field is classed `Estimated`.

### Known answers and negative controls

Known answers: the stance authority pair (155 N against (175, 115, 85, 25) N at a 160 N cap, KA-682) and the
energy pair (0.94176 J, 0.90 J, 0.05 J; KA-684) as contract-level fixtures. Negative controls: the undeclared
read; a mutant key that omits card versions (the generated key test fails when a card version changes); a mutant
that returns an exclusion with a missing source (551 expected); CX-306 (a quasi-static energy exclusion without
approach energy). Determinism lanes: D0, byte-identical across runs, worker counts, debug and release, and
platforms.

## Considerations

- The read set is the influence record the model compiler already keeps per product, extended to analyses; the
  invalidation set of an edit is the set of products whose read set meets the edit's write set.
- RISK-38 (an incomplete memo key serves a stale verdict) is the reason keys are derived and never written.
- The severity `Refusing(code)` is decided by `design.check` policy for the stage (BD-110); an analysis run as
  its own verb reports the same finding with exit 2 and does not refuse.
- If static verdicts turn out not to predict simulated failure (KILL-STATIC, decided at M3), every `Refusing`
  severity is downgraded to an advisory lint by one policy switch here; the contract is built so that switch is
  a table, not a code change.
