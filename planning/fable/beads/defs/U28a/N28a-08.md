## Background

A-21 answers: does the last informative observation arrive before the decision it must inform, on every
admitted schedule? A robot can have the right sensor, the right content in the packet and a correct controller,
and still fail because the packet arrives one tick after the command that needed it was issued. Timing is a
schedule, not a rate, and it is checkable statically from the clock contract.

The clock contract gives every observation and command seven distinct instants:

| # | Instant | Definition |
|---|---|---|
| 1 | Sample | The sensor's clock fires: the nominal trigger and the start of its exposure |
| 2 | Exposure | The close of the half-open window over which the instrument integrates (zero length for an instantaneous sensor) |
| 3 | Timestamp | The time the device writes on the packet, in its own clock; deliberately unconstrained |
| 4 | Arrival | The packet becomes readable by its consumer, after transport latency, jitter, loss and reordering |
| 5 | Decision | An estimator or controller tick reads its inputs |
| 6 | Command | The tick's output is issued, after compute latency |
| 7 | Actuation | The command takes effect at the actuator, after bus and driver latency, and holds over the following open interval |

Order constraints: sample ≤ exposure ≤ arrival; decision ≤ command ≤ actuation; and the rule this analysis
turns on: **a packet is used by a decision at t only if its arrival is at or before t.** At a boundary at time t
packets with arrival ≤ t are delivered before the ticks whose decision instant is t run, so a zero-latency loop
is legal, and a packet that arrives one quantum after t cannot influence the command decided at t.

The demonstrated failure this analysis prevents: a packet that arrives at tick 1 serves decisions that commit
at ticks 2 and 4; delayed to tick 3 it still serves the second and no longer serves the first. A check that
compares the content of observations and ignores arrival passes both cases. Tier Solid; exact; in `check`.

## Scope

In: composing instants along declared sense–decide–actuate chains, the worst case over admitted schedules,
per-decision verdicts with a witness schedule, findings and repairs. Out: the clock contract types and phase
accumulators (BD-078); packet queues (BD-098); observability, i.e. whether the information exists at all (A-17,
BD-120); the alias witness of the docking mission (BD-134); joining `check` (BD-108).

## Technical approach

Time is an integer count of quanta of 1/Q seconds, Q the least common multiple of the period denominators of
the run; no floating-point time is compared. The lattice is admitted by BD-078: a period that is zero or
negative, or a Q above its limit (2⁴⁰), is refused with `FROB-REF-440`, exit 3, with BD-078's pointer (the
offending clock) and ranked repair, before any enumeration. 440 is the one chapter code this analysis declares
to N28a-05's generator, so `analyze.deadlines` carries 440 and 551 as VERBS-analyze lists them; it is a refusal
of the request, not a finding.

1. **Chains.** From the task (or the controller's declared interface) collect, for each decision D that must be
   informed: the observation channel O, the consumer clock (period N_c, phase φ_c), the decision's commit
   instant or the event deadline T_D by which its actuation must take effect, compute latency c and actuation
   latency a (intervals when the cards give intervals), and what "informative" means: the latest sample instant
   s_req such that a sample taken at or after s_req carries the needed information (for example "a velocity
   reading taken after the first command took effect"). The sensor side gives: clock (N_s, φ_s), exposure
   length e, link latency interval [ℓ_min, ℓ_max], and the admitted loss pattern (at most k consecutive drops).
2. **Admitted schedules.** The set over which the answer must hold: every phase pair the contract admits (fixed
   phases, or all phases when the task randomizes them), every latency in its interval, every loss pattern
   within the bound, and rate error within its declared bound over the horizon. Because every quantity is an
   integer and the system is periodic with hyperperiod lcm(N_s, N_c), the worst case is found by exact
   enumeration over one hyperperiod, the interval endpoints and the loss patterns; nothing is sampled.
3. **Composition per sample j.** sample_j = φ_s + j·N_s; exposure_j = sample_j + e; arrival_j = exposure_j + ℓ
   (later still if dropped and re-sent, or absent). For decision D with decision instant t_D: the packet is
   usable iff arrival_j ≤ t_D. Then command = t_D + c and actuation = t_D + c + a.
4. **Verdict per decision.** `served` iff, on every admitted schedule, some sample with sample_j ≥ s_req has
   arrival_j ≤ t_D, and actuation ≤ T_D where a deadline is declared. Reported: the last informative sample
   that arrives in time, its age at the decision (decision − sample, in quanta and seconds), the slack
   t_D − arrival, the worst-case end-to-end latency sample → actuation, the margin T_D − actuation, and for
   `not-served` the witness schedule (phases, latency, loss pattern) that breaks it. The result is typed
   `exact` (a finite enumeration in rational time).
5. **Findings.** `A-21.<decision>.late` (High) with repairs ranked by the contract and verified by re-running
   the enumeration: `retime` (raise the sensor rate or shift a phase), swap the sensor or link card for one
   with lower latency, lengthen the window before the decision, or move the decision one tick later where the
   task allows. `A-21.<decision>.stale` (Low) when the decision is served but only by a sample older than a
   declared freshness bound. The code is analysis, subject, kind (N28a-04); `check`'s policy rows are keyed by
   analysis and kind, `A-21.late` and `A-21.stale` (N14bx-01, used by BD-108). Inside `check` the finding is
   reported with exit 2; DESIGN: it does not refuse, because the refusal registry holds no code for it (see
   Considerations).
6. **Class.** D0, `Tested`; budget 50 ms for up to 64 chains (TARGET).

## Acceptance criteria

- [ ] The three-state fixture: decisions at ticks 2 and 4, one packet. Arrival at tick 1: both `served`.
      Arrival at tick 2: both `served` (arrival at the decision instant counts). Arrival at tick 3: the first
      decision `not-served` with the witness, the second `served`.
- [ ] Rational clocks: physics at 400 Hz, a sensor at 100 Hz and a policy at 30 Hz give Q with base unit
      1/1,200 s and periods of 3, 12 and 40 units; the worst-case age of the sensor sample at a policy tick is
      computed by enumeration over the hyperperiod of 120 units and equals the hand value.
- [ ] A latency interval is evaluated at its worst endpoint and the witness names it; a loss bound of one drop
      moves the last-informative sample back by one sensor period.
- [ ] A zero-latency chain (sample, arrival and decision at the same instant) is `served`.
- [ ] Each repair offered, applied, makes the decision `served` (verified, not predicted).
- [ ] A task whose clock has period 0, or whose clocks give Q above 2⁴⁰, is refused with `FROB-REF-440`, exit 3,
      the pointer naming the clock; no verdict is computed.
- [ ] Contract conformance (reads only clock, latency and task-timing fields; D0); the verb
      `frob analyze deadlines --json` is schema-valid.

## Test plan

### Unit tests

`crates/frob-analyze/tests/a21_deadlines.rs`:
- `packet_tick_1_serves_2_and_4`, `delay_to_2_changes_nothing`, `delay_to_3_loses_first_only`.
- `arrival_equal_decision_is_usable`; `arrival_one_quantum_late_is_not`.
- `hyperperiod_enumeration_100_30`: sensor 100 Hz (period 12 units, phase 0), policy 30 Hz (period 40 units,
  phase 0), zero latency: over one hyperperiod of 120 units the policy ticks at 0, 40, 80 see samples of age
  0, 4 and 8 units; the worst-case age is 8 units = 1/150 s.
- `latency_interval_worst_endpoint`: ℓ ∈ [2, 9] units makes the worst-case age 8 + 12 = 20 units at the tick
  where the fresh sample misses by one unit (hand-enumerated table in the test).
- `one_drop_costs_one_period`.
- `actuation_deadline_margin`: c = 3, a = 2 units, deadline 6 units after the decision: margin 1; with a = 4:
  `not-served`.
- `repair_retime_verified`.
- `inadmissible_lattice_refused_440`: a sensor period of 0 and a pair of co-prime denominators giving
  Q = 2⁴⁰ + 1 are each refused with 440 (exit 3, pointer to the clock); the analysis's declared codes are
  exactly [440].
- Property: lowering any latency or raising the sensor rate by an integer factor never turns `served` into
  `not-served`.

### End-to-end script and logging

`scripts/e2e/analyze_deadlines.sh`, this bead's own script (convention 11; N28a-29's `atelier_check.sh` runs
it as a stage, and BD-108's script carries the `design check` leg). It sources the STD-E2E helper, stores the
docking-style design with `frob design new a21-dock --file <copy> --key "$(e2e_key new-dock)"` (N14a-21) and
its three timing variants (packet arrival at ticks 1, 2 and 3) as tasks with `frob task new <copy>
--name a21-arrive-<k> --key "$(e2e_key new-task-<k>)"` (BD-122; the document is positional, VERBS-task), and runs `frob analyze deadlines a21-dock --task
a21-arrive-<k> --json` on each (exit 0, 0 and 2 with `A-21.late` naming the first decision), then the
400/100/30 Hz clock fixture (worst-case age 8 units = 1/150 s). It logs per decision: sample, arrival and
decision instants (as integers and as seconds), slack, age, verdict, and the witness schedule for the failing
variant, on NDJSON lines at `target/e2e-logs/analyze_deadlines/<utc>.ndjson` (transcript beside it) with the
STD-E2E fields (`ts`, `script`, `bead` = N28a-08, `step` = `a21`, `event`, the exact command line, exit code,
wall time against 50 ms, the envelope's `evidence` block); on failure the first decision whose verdict differs
from KA-685 and the fixture path; a final `summary` line. Declared plant (STD-E2E header `plants`):
`content-only`, a build that ignores arrival, which the tick-3 step must catch (CX-310).

### Known answers and negative controls

KA-685: the answer changes only at the second delay (to tick 3) and only for the first decision; KA-201 (the
400/100/30 Hz clock arithmetic) for the quanta. Negative control CX-310: a mutant check that compares
observation content and ignores arrival reports all three variants `served` and must be caught; a second mutant
using `arrival < t` instead of `arrival ≤ t` fails the equality test. Determinism: D0, identical everywhere.

## Considerations

- OPEN (owner: surface lead): no refusal code exists for "a mandatory decision that no admitted schedule
  serves". Fail-closed default until one is registered: the finding is High, `design.check` exits 2, and a
  mission query that depends on the decision treats the cell as not proved.
- "Informative" is declared, not inferred: A-21 does not decide which sample matters; the observability and
  alias analyses do. A chain with no declared requirement is reported with its worst-case age only.
- Timestamps are what the device believes; this analysis never uses them, by design.
- Interaction with revalidation: delivery time is a dependency of a decision. An edit that delays a packet
  across a decision instant must invalidate verdicts that read it; the read set of this analysis is the list of
  fields such an edit touches.
