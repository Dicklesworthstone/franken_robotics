## Background

For each static analysis there is a plausible cheaper analysis that gives the wrong answer on a small,
hand-checkable case. The studio keeps those cases on purpose. They are the first seeds of the project's
negative-control registry: a gate that nothing can fail validates nothing, so each gate on an analysis must show
a planted wrong method being contradicted. This bead registers the nine shortcut cases as executable mutants
with their smallest breaking case, so that (a) the real analysis is tested against the case, and (b) the mutant
is run on the same case and observed to give the wrong answer. Both halves are needed: if the mutant gives the
right answer, the case no longer discriminates and the control is void.

Two of the nine concern analyses that other subsystems implement (symmetry, observability). They are registered
here as well, from the studio's side, because `design.check` is where an agent would be misled by them.

## Scope

In: the executable side of nine registered controls: the plants due at M1, built under N28-CX's plant
identifiers; the case fixtures; this bead's own test table with the truths and the mutants' answers; the runner
glue; the binding to the gates' rows; the script `scripts/e2e/atelier_shortcuts.sh`. Out: the analyses; the
full counterexample catalogue of the chapter (key `N28-CX`, a dependency: registries come first), which lists
these nine (CX-302 to CX-310), eight more (CX-311 to CX-318) and two late entries with their rules and plants;
the controls themselves, which N38b-05's seeding tool writes to `controls.toml` from those entries; the plants
whose analysis arrives later (row 3's curvature mutant with A-09, BD-243, M3; row 6's alias-search half with
BD-240, M3; row 8 with A-25, N28a-13, M4).

## Technical approach

**Where each part lives.** N28-CX enters the nine counterexamples CX-302 to CX-310 in the catalogue
`crates/frob-conformance/registry/counterexamples.toml`, each with its `control_kind`, `plant`, target, defect,
expected observation and `rule_ids`. The controls are not written by this bead: N38b-05's seeding tool turns
each entry into one control of `crates/frob-conformance/registry/controls.toml` (its `NC-` number, `seed` = the
CX number, the gates resolved from `rule_ids`, `kind`, `target`, `defect`, `expect`, the plant), and this bead
adds no field to that file. The executable parts stay in this bead's own test table, the `ROWS` constant of
`crates/frob-conformance/tests/atelier_shortcuts.rs`, one row per CX entry, joined to its control by the CX
number (the seed map gives the NC number): `cx`, `plant`, `analysis`, the case fixture path, `truth`,
`mutant_answer` and `first_milestone`. A mutation plant is a small alternative implementation in
`frob-conformance` behind the `gauntlet-mutations` feature (never in the product crates), callable through the
same analysis trait; a planted input is a fixture.

**The plants, under N28-CX's identifiers.** Built here, due at M1: `a08-polygon-screen` (row 1, CX-302,
mutation of A-08), `a23-additive-peak` (row 2, CX-303, mutation of A-23), `a03-tie-under-mechanical-group`
(row 4, CX-305, the planted input: a policy tie request under the four-element mechanical group),
`a20-no-approach-energy` (row 5, CX-306, mutation of A-20), `a22-instantaneous-current` (row 7, CX-308, mutation
of A-22) and `a21-content-only` (row 9, CX-310, mutation of A-21). Built by the bead of the analysis they
mutate, which cannot be reached from this M1 bead (no dependency on a later milestone), and listed here
`not-yet-due` until then: `a09-curvature-only` (row 3's mutant, CX-304, with A-09 in BD-243 at M3),
`a17-per-reading-accuracy` (row 6's mutant, CX-307, against the alias search of BD-240 at M3; row 6's
arithmetic is bound here at M1) and `a25-convenient-run` (row 8, CX-309, with A-25 in N28a-13 at M4). Each of
those beads binds its row of this table when its plant lands; the row's `cx`, `truth` and `mutant_answer` are
fixed here.

**Arithmetic kept in the registry for rows without a mechanism at M1.** Row 6: P(majority of 7 correct at
q = 3/4) = Σ_{k=4..7} C(7, k)·(3/4)ᵏ·(1/4)^{7−k} = (2,835 + 5,103 + 5,103 + 2,187)/16,384 = 3807/4096; the
test computes the sum in rationals and compares, and computes 27/32 for three reads and 459/512 for five. With a
shared fault bit all reads fail together and the success stays 3/4. Row 8: F at the four operating points, for
both μ.

**Runner.** In the form ADR-GAUNT-01 fixes (BD-025: there is no `frob conformance` command, verb or binary, and
BD-025's lint `no_conformance_command` fails a script that keeps the literal form), the rows run as the controls
of the gates they protect: `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --features gauntlet-mutations
--test <tier> -- GATE-ATEL-02` and the same with `-- GATE-ATEL-05`, with `<tier>` the test target named by each
gate record's `tier` field (written by N28c-25); the rows alone run with `cargo test -p frob-conformance
--features gauntlet-mutations --test atelier_shortcuts`. Each run executes, per entry bound at this build: the
real analysis on the case (must equal `truth`), the mutant on the case (must equal `mutant_answer`,
which differs from `truth`). An entry whose mutant agrees with the truth is reported `control-void` and fails
the run. Entries not yet bound print `not-yet-due (M3)` or `(M4)`.

## Test plan

### Unit tests

`crates/frob-conformance/tests/atelier_shortcuts.rs`: one test per row named `shortcut_<n>_caught`, each
asserting both halves; `majority_3807_4096`, `majority_27_32`, `majority_459_512`, `shared_fault_three_quarters`;
`drawbar_forces`: 3.33, 6.67, 3.33, 6.67 N in the torque-limited runs and 4 N against 8 N in the
traction-limited one; `control_void_detected` with a deliberately correct "mutant";
`controls_seeded_from_cx` (each of CX-302 to CX-310 has exactly one control in `controls.toml` whose plant equals
the catalogue entry's, and the control carries only the seeding tool's fields); `rows_join_by_cx` (every row of
the test table names a CX entry and its plant; no CX entry of the nine lacks a row); `plants_only_under_feature`
(without `gauntlet-mutations` the six M1 plants do not resolve).

### End-to-end script and logging

This bead owns `scripts/e2e/atelier_shortcuts.sh` (convention 11; N28a-29's `atelier_check.sh` runs it as a
stage of its gates step). Sourcing the shared helper of STD-E2E, it (1) runs the rows alone, `FROB_TEST_SEED=
$FROB_E2E_SEED cargo test -p frob-conformance --features gauntlet-mutations --test atelier_shortcuts`; (2) runs
them as the controls of the gates they protect, the same cargo form with `--test <tier> -- GATE-ATEL-02` and
`-- GATE-ATEL-05`, `<tier>` read from each gate record's `tier` field; (3) runs `cargo test -p frob-conformance
--test atelier_shortcuts -- plants_only_under_feature` without the feature and asserts that no plant resolves. It writes no gate row
(convention 9). It writes NDJSON to `target/e2e-logs/atelier_shortcuts/<utc>.ndjson`; every line carries the
STD-E2E fields (`ts`, `script`, `bead` = N28a-11, `step` = `rows`, `gates` or `no-feature`, `event`, the exact
command line, exit code, wall time). Logged per row: the CX number, the NC number and the plant identifier, the
case, the truth, the analysis's answer, the mutant's answer with units, `caught` (or `control-void`, or
`not-yet-due` with its milestone and the bead that builds its plant), and the gate row it protects; the
receipt hash of each gate run; on failure the row, both answers and the fixture path; a final `summary` line
listing the gates touched and the count caught.

## Considerations

- Mutants live outside the product crates so that no build can ship one; the conformance crate is layer 7.
- Row 4's refusal (a policy tied under the mechanical group) is implemented by the learning subsystem at M4;
  at M1 the check is that `analyze.symmetry` reports both groups and names the lidar mount as the breaker.
- If a later change makes a case non-discriminating (for example a better screen), the entry is replaced by a
  smaller breaking case, never deleted.
