## Background

`design.check` is the preflight of the studio: eight stages that run in order and stop at the first refusal.
Its first six stages (form, mass, mechanism, motion, structure, statics and sizing) are due at the first studio
milestone and are accepted by a gate with a planted-defect form: of 100 seeded defects, with at least two per
refusal code, all 100 are refused and at least 95 by the stage and code that own them; and there are zero
refusals on the archetypes and on 10³ random valid designs. The second half matters as much as the first: a
preflight that refuses sound designs trains agents to override it.

This bead builds the corpus as data before the runner is finished, so that the people who write the stages do
not also choose the defects that test them. It is a fixture bead: the gate is measured by the `design.check`
bead (BD-110), which depends on this one. Each defect is a typed edit applied to a valid design, so the corpus
is small, reviewable and reproducible, and each entry records which stage and which code must catch it.

## Scope

In: the defect catalogue, the generator of defective designs, the generator of random valid designs, the
expected-outcome table, the registry entries, a self-test that the corpus is well formed. Out: the stages and
the runner (BD-110 and the analysis beads); defects for stages 7 and 8 (place and information; 40 planted
cases, M3, seed BD-244); the design corpus of about 200 designs for validating static analysis against
simulation (BD-248).

## Technical approach

1. **Codes and owners for stages 1 to 6** (25 codes; "owner" is the stage that must issue the refusal):

   | Stage | Codes it owns | Meaning |
   |---|---|---|
   | 1 Form | 101 | Port type mismatch |
   | | 102 | Unit or dimension error |
   | | 103 | Unknown, misspelt or duplicate field |
   | | 105 | A body without a fill; a solid written as a shell |
   | | 111 | A lever outside its bounds; an edit to a locked field |
   | | 114 | Module digest or port signature mismatch |
   | | 121 | Contact law missing or incompatible with its end effector |
   | | 126 | A sensor without a parent frame, a rate or a clock |
   | | 130, 134 | A card that fails its own checks (not passive; no or inconsistent current convention) |
   | 2 Mass | 104 | Inertia not physically consistent |
   | | 106 | Declared mass properties violate the mass-support bound |
   | 3 Mechanism | 101 | Joint class and screw basis disagree |
   | | 107 | Empty joint range |
   | | 110 | A closure that over-constrains the mechanism (mobility below one) |
   | | 123 | Self-collision or interpenetration at the reference pose or over declared ranges |
   | 4 Motion | 118 | The base cannot produce a motion the task class requires |
   | 5 Structure | 109 | Declared symmetry differs from computed symmetry |
   | | 108 | Power sign mismatch, copied power port or algebraic loop |
   | 6 Statics and sizing | 124 | A static margin the task requires is not met |
   | | 116 | Co-design does not close: loop gain at or above one |
   | | 131 | A required operating point outside the torque, speed and voltage envelope |
   | | 132 | No stable thermal equilibrium, or one above a limit |
   | | 133 | The bus cannot supply the demand |
   | | 115 | A design budget exceeded |
   | | 113 | A card field `assumed` under `--strict-data` |

   Code 101 has two owners (stage 1 for ports, stage 3 for joint class); the corpus has at least two defects of
   each kind and the expected-outcome table names the stage.
2. **Composition.** 100 defects over the 25 codes: at least two per code, four where a code admits four
   distinct mutations, and the remainder given to the codes with the most distinct failure mechanisms (101,
   102, 104, 123, 131). Each entry:
   `{id, base_design, edit (typed edit or raw-file mutation for stage-1 syntax defects), expected_stage,
   expected_code, family, note}`. Bases are the four first archetypes (`quad-mammal`, `humanoid`, `diff-drive`,
   `mecanum`) and the cart of the first fixture.
3. **The first-rejection fixtures are in the corpus by name** (one per component family; a check that lets its
   fixture through is broken, whatever else it reports):

   | Family | Fixture | Caught by |
   |---|---|---|
   | Rigid link | Principal moments that violate the triangle inequalities | Stage 2 (104) |
   | Joint | A prismatic travel in millimetres read as radians | Stage 1 (102) |
   | Transmission | Reverse drive that produces free electrical energy | Card check (130) |
   | Actuator | Stall torque available indefinitely at high speed | Stage 6 (131) |
   | Drive wheel | A changed wheel that intersects the body at its nominal mount pose | Stage 3 (123) |
   | Foot | A point foot that silently acquires torsional support (a torsion radius above the foot's own contact radius) | Stage 1 (121) |
   | Sensor | Measurements with no timestamp or an unknown frame | Stage 1 (126) |
   | Wheeled base | A mecanum base with all four roller axes parallel | Stage 4 (118) |

   Three families are listed for completeness and are outside stages 1 to 6: a track turning in place at zero
   scrub work (the belt-law known answer of the contact subsystem), an empty battery that keeps supplying power
   (run-time refusal 135), and a payload swap that leaves assembly inertia unchanged (a model invariant).
4. **Masking rule.** A defect must be minimal: applied alone to its base it triggers its own code and no
   earlier stage's. The self-test applies each edit and checks, with the reference classifier described next,
   that no earlier-stage condition is violated. Where a defect necessarily trips an earlier stage, it is moved
   to that stage's list.
5. **Reference classifier (independent of the stages).** For each code a few lines of direct arithmetic on the
   edited design (for example for 104: the three principal moments and the triangle test; for 107: lower limit
   above upper), written in the conformance crate without calling `frob-analyze`. It is what makes the corpus
   an oracle and not a recording of the implementation.
6. **Valid designs.** A generator draws 10³ designs by keyed random typed edits within each archetype's lever
   bounds (limb lengths and masses within ±20%, actuator cards within one family, gear ratios within the card's
   range), keeps a design only if the reference classifier finds no defect, and records the key. Seed and
   generator pin are in the corpus manifest; the set is `synthetic`.
7. **Files.** `crates/frob-conformance/fixtures/preflight/defects.toml`, `valid.toml` (keys, not designs),
   `manifest.toml` (hash, generator pin, counts per code and stage).

## Acceptance criteria

- [ ] 100 defects; every one of the 25 codes has at least two; counts per code and stage are in the manifest.
- [ ] The eight first-rejection fixtures of stages 1 to 6 are present by name.
- [ ] The self-test passes: each edit applies to its base; the reference classifier confirms its code and no
      earlier stage's condition; no two defects are identical after canonicalization.
- [ ] The valid-design generator yields exactly 10³ designs from its key, reproducibly, each accepted by the
      reference classifier.
- [ ] The corpus hash is committed before the stage implementations it tests are merged (ordering recorded in
      the bead log); changing a defect changes the corpus identity.
- [ ] The corpus is registered as the negative-control set of GATE-SKEL-04 (stages 1 to 6).

## Test plan

### Unit tests

`crates/frob-conformance/tests/preflight_corpus.rs`:
- `hundred_defects_two_per_code`.
- `first_rejection_fixtures_present`.
- `defects_are_minimal`: reference classifier, earlier-stage conditions clean.
- `reference_classifier_examples`: moments (1, 1, 3) ⇒ 104; limits [0.5, 0.2] rad ⇒ 107; a 1 kg part with
  moments 0.008 kg·m² in a ball of radius 0.10 m ⇒ 106; a lever at 1.2 times its bound ⇒ 111.
- `valid_generator_reproducible`: same key, same 10³ `DesignId`s.
- `valid_designs_have_no_defect`.
- `corpus_identity_changes_on_edit`.

### End-to-end script and logging

`scripts/e2e/preflight_corpus.sh` runs the self-test and prints the per-code and per-stage table; when
`frob design check` exists it also runs the gate measurement of BD-110 (`frob conformance run --gate
GATE-SKEL-04 --stages 1-6 --json`). Sourcing the shared helper of STD-E2E, it logs per defect: id, expected
stage and code, observed stage and code, `refused` and `owned` booleans; and a summary with refused of 100,
owned of 100 (threshold 95), refusals on archetypes (threshold 0) and on the 10³ valid designs (threshold 0).

### Known answers and negative controls

KA-291: all 100 refused, at least 95 by the stage and code that own them; zero refusals on the archetypes and
on 10³ random valid designs. The seeded defects are themselves the negative controls of the preflight. Controls
on the corpus: a defect that trips an earlier stage (self-test fails); a "valid" design that the reference
classifier rejects (generator drops it); a duplicated defect. Determinism: the corpus and the generated sets
are byte-identical across platforms.

## Considerations

- The gate says "the eighteen archetypes"; four exist at this milestone. The zero-refusal half is recorded for
  the four and repeated for all eighteen at M3; the gate row says which.
- The 5% allowance (95 of 100 by the owning stage and code) exists because some defects legitimately surface at
  an earlier stage in a different base; it is not a tolerance for missed defects: all 100 must be refused.
- RISK-14 (a corpus tuned to the analyses) is the reason for the reference classifier and the commit ordering.
