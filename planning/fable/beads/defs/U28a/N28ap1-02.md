## Background

A-24, task-wrench attainability, is the last static analysis the studio itself implements. It answers: can
this body produce the wrench a skill or a task needs, inside torque, speed, friction and support limits? A
skill is a behaviour stated at the task boundary (push a cart handle with 40 N; hold a tray level), independent
of the body that performs it. Before any controller is synthesized or any policy trained, a cone program says
whether the body can exert the required wrench at the states the skill visits. If it cannot, the answer is not
"synthesis failed": it is a separating dual vector, which names the direction in task space the body cannot
reach, by how much it falls short, and which actuator or contact binds. A refusal that cites a separating
vector tells the agent which constraint to edit. The program is the one the contact solver and the control
programs already share (the small dense cone solver), so no second solver enters. Tier Solid; in `check`
when a skill or task wrench is bound; its verb is `analyze.wrench`.

Why its own bead. The seed that names A-24 (BD-348) also closes the second half of the gate GATE-ATEL-05,
which waits on A-25, A-26 (behind the KILL-ATLAS pilot and decision), A-17 to A-19 and A-16. The co-design
cascade needs A-24 at its stage 3 screen and the M4 verb registration needs `analyze.wrench`; neither needs
the regime atlas. Building A-24 here lets them start as soon as A-24 exists; BD-348 depends on this bead and
records its gate row.

Rejected: a fixed-base pullback τ = Jᵀ·F for a floating-base robot (it ignores that contact forces and base
acceleration share the actuator effort; a registered mutant); reporting `not-synthesizable` without a witness
(the agent cannot tell which constraint to edit).

## Technical approach

1. *Inputs.* The design; a wrench requirement: a `.fskill` phase with its wrench profile, or a task's declared
   wrench set at a task frame; the contact mode m for each phase; the states to test (the reference stance, the
   skill's sampled reference states, or a declared operating box); the minimum friction μ_min the skill
   assumes; actuator cards (with the joint-torque generators of coupled transmissions, N15b-40).
2. *Map.* For a morphology and a contact mode, the equations of motion M·v̇ + h = Sᵀ·u + J_cᵀ·f_c (M the
   joint-space mass matrix, h the bias forces, S the actuation selection, u the actuator effort, J_c the
   contact Jacobian, f_c the contact forces) with the mode's contact constraints give, after a constrained
   mass solve that eliminates v̇ and f_c, an affine map from actuator effort u to the task-space wrench:
   w = w₀(q, v) + B_m(q)·u. For a floating-base robot the map must come from this contact-consistent solve; a
   fixed-base pullback τ = Jᵀ·F is wrong and is a registered mutant.
3. *Program.* Minimize ‖B_m·u − (w* − w₀)‖² plus declared secondary costs, subject to: actuator boxes from
   the torque–speed envelope at the state's joint speeds; contact forces in their friction cones (with μ_min
   for forces the robot commands); unilateral support limits. A cone program in the shared solver (BD-115).
4. *Result.* Either a feasible-allocation witness (u, f_c) that replays on the referee; or an infeasibility
   witness: a direction c in task space, the support value h(c) = max cᵀ(w₀ + B_m·u) over admissible u, which
   is below cᵀ·w*, the gap cᵀ·w* − h(c), and the binding actuator or contact. The dual certificate is
   re-checked in exact rationals (strict separation only; a non-strict witness yields `unknown`). The witness
   is canonicalized (the lexicographically first optimal vertex of the dual), so it is identical across
   platforms.
5. *Typing.* Infeasibility at a state is an exclusion typed `outer` for the instantaneous model at that state
   and mode, with the authority model named (independently commanded contact forces unless a passive
   suspension is declared). Feasibility at every sampled state is necessary and not sufficient: the result is
   `instantaneously-attainable`, never `inner`; multi-step feasibility (a capture-point recovery, a
   momentum-assisted push) is outside the map and the output says so.
6. *Findings.* `A-24.unattainable` (subject: the skill phase) with the witness; inside `check`, when the
   request binds a skill or a task wrench, the refusing code is FROB-REF-448 (a skill's task wrench lies outside
   the body's attainable set), exit 3. Repairs ranked by the analysis contract and re-solved on the edited
   model: `regear` or `swap-actuator` on the binding joint, `reshape` or `move-mount` to change the lever, or
   change the wrench profile. A finding never says `not-synthesizable` without its witness.
7. *Registration.* Stage 6, after A-20, bound only when a skill or task wrench is bound (else `not-run:
   unbound` with the flag `--skill`), refusing only with 448, as N14bx-01's row says; the runner (N28ap1-01)
   takes order and binding from `plan_check`. Before this bead ships, `plan_check` lists A-24 `not-landed`.
8. *Budget and class.* Inside `check` the budget is N14bx-01's row: 100 ms at the 95th percentile, which covers
   the reference stance and up to 32 sampled states; a state set that exhausts it returns `undecided` with the
   states decided so far. The standalone verb covers 64 states inside 200 ms (TARGET). Double precision solve
   with exact certificate check; evidence `Certified` when the certificate is emitted, else `Tested`; D0 for
   the certificate check, deterministic double precision on one platform for the solve.
9. *Verb.* `frob analyze wrench <design> (--skill S | --wrench Fx,Fy[,Fz,Mx,My,Mz] --frame F) [--states …]
   --json`, generated from the analysis registry (N28a-05): kind `read`, capability `analyze:read`, first
   milestone M4, refusals its declared list plus FROB-REF-551; exit 0 when attainable at every state, 2 with an
   infeasibility witness (a finding outside `check`), 3 for an invalid request or a missing binding.

## Acceptance criteria

- [ ] Planar two-link arm, links 0.4 m and 0.3 m, joint angles 0 and π/2: tool point (0.4, 0.3) m, point
      Jacobian [[−0.3, −0.3], [0.4, 0.0]] m/rad; a tool force of (10, 0) N needs torques (−3, −3) N·m; with
      each actuator limited to 2.5 N·m the analysis returns infeasible with direction c = (1, 0), support value
      25/3 N against the requirement 10 N, gap 5/3 N, and binding actuator joint 2; at 3.5 N·m it returns a
      witness.
- [ ] The dual certificate re-checks in exact rationals; a perturbed multiplier is rejected; a non-strict
      witness yields `unknown`.
- [ ] The fixed-base pullback mutant gives the wrong answer on a floating-base fixture and is caught; so is the
      mutant that takes the lower rows of a space-frame screw Jacobian in place of the point Jacobian.
- [ ] Feasible results are labelled `instantaneously-attainable` and never `inner`.
- [ ] With a skill bound, `design check` refuses an unattainable wrench with FROB-REF-448 at stage 6 and the
      witness; with none bound, A-24 is listed `not-run: unbound`; inside `check` it keeps its 100 ms budget.
- [ ] `frob analyze wrench` is reachable through `frob --json` and MCP and is schema-valid; the witness is
      byte-identical across runs and platforms.

section of N28a-29's `atelier_check.sh`). It sources the STD-E2E helper, stores the two-link arm and the
tray-carrying quadruped on scratch copies with `frob design new arm-2r --file <copy> --key "$(e2e_key
new-arm)"` and `frob design new quad-tray --file <copy> --key "$(e2e_key new-quad)"` (N14a-21), and runs
`frob analyze wrench arm-2r --wrench 10,0 --frame tool --json` (exit 2, witness c = (1, 0), gap 5/3 N, joint
2), the same arm at the 3.5 N·m card (exit 0, a witness allocation), `frob design check quad-tray --skill
<copy>/push-cart-level.fskill --json` (a skill is a path or a `SkillId`, BD-336; exit 3, FROB-REF-448 at
stage 6 with the witness, or exit 0 or 2 when attainable, the branch logged), and the same without `--skill`
(A-24 `not-run: unbound`); then the planted mutants (the witness-less `not-synthesizable`, the two Jacobian
mutants, the perturbed certificate) through the Gauntlet, `FROB_TEST_SEED=$FROB_E2E_SEED cargo test -p
frob-conformance --features gauntlet-mutations --test g1_known_answers -- KA-690`, each of which must be
caught. NDJSON at `target/e2e-logs/analyze_wrench/<utc>.ndjson` with a transcript beside it. Each line carries
`ts`, `script`, `bead`, `step`,
`event`, the exact command line, exit code, wall time, the envelope's `evidence` block, the witness (direction,
support value with unit, requirement, gap, binding element), the certificate hash and check result, A-24's time
against 100 ms, each mutant with `caught`; on failure the first differing value and the paths to reproduce; a
final `summary` line.

## Considerations

- A static projection certifies neither run-up nor landing nor recovery; a design A-24 excludes may still do
  the task dynamically, and the enclosure rule of the analysis contract keeps the exclusion scoped to the
  instantaneous model.
- KILL-STATIC, if fired, makes FROB-REF-448 from `check` advisory for task wrenches; a certified infeasibility
  remains a proof about its stated model and keeps its standing in mission queries.
- Frontier part: the witness's use as a mission certificate is piloted and gated where the mathematics is
  owned (the contact and control chapter); this bead's Solid analysis does not wait on that pilot.
- The 64-state standalone budget and the 100 ms `check` budget are TARGETs; if the M4 measurement misses the
  `check` budget, the remedy is fewer sampled states inside `check`, recorded in N14bx-01's table.
