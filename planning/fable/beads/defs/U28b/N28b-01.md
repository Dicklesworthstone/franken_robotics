## Background

In the studio loop an edit does not only produce a new design. It produces an *invalidation set*: the derived
assets and stored verdicts that the edit puts in question. The plan's rule for lineage is that `design.edit`
takes the expected parent and an idempotency key, refuses a stale parent, and returns the new immutable
version, the structural and parameter diff, the symmetry effect, and the set of derived assets and stored
verdicts whose dependency support the edit touches, so that the agent sees what its change put in question
before it spends anything.

The compiler already returns the part of that set that concerns compile products: every product records the
fields it read, and the products whose read set meets the edit's write set are invalidated (BD-063). Two more
families of stored things depend on a design and are not compile products: memo-graph nodes downstream of the
model (analyses, synthesized controllers, episodes, comparisons) and verdict records, each of which carries
obligations with a recorded *dependency support* (the exact fields the obligation read). This bead extends the
edit's answer to those, with one index and no rerun. Tier: Solid. It serves decision ADR-ATEL-05: a hash
identifies; only an implication licenses skipping a recheck. The invalidation set is the cheap, conservative
half of that rule: it says what is *touched*. Whether a touched verdict survives is decided by
`result.revalidate`, not here.

Rejected alternatives: recomputing everything downstream at edit time (defeats the purpose: the agent wants to
know the cost before paying it); a hand-kept table "edit kind X invalidates verdict kind Y" (correct only until
a field or an analysis is added; a recorded support is correct by construction and testable by mutation);
reporting only a count (the agent cannot then choose between two edits by what each would cost).

## Scope

In: the support index; its maintenance when verdicts and memo nodes are written, pinned, tombstoned; the
lookup at edit time; the output record and its fields on `design.edit` and `design.patch`; pagination; the
completeness property and its test.

Out: read sets of compile products and their invalidation (BD-063); the grades of reuse and survival of a
touched obligation (BD-292, BD-347); memo keys (N28b-37); the lineage graph, diff and blame (BD-113).

## Technical approach

**1. The support index (DESIGN).** A ledger table `support_index` with rows `(subject, field_path, ref_kind,
ref)`: `subject` is the identity the support refers to (a `DesignId`-scoped path, a card, a scene cell, a
clock, a task field), `field_path` is the canonical path of one read field, `ref_kind` is `obligation` or
`memo-node`, and `ref` is `(verdict_id, obligation_index)` or a memo key. Rows are written in the same
transaction that stores the verdict or the memo node, from the support the producer recorded. A verdict
without a recorded support for one of its obligations is indexed under the wildcard path of its subject, so it
is always reported as touched (fail closed). Rows of a tombstoned verdict or evicted node are removed with it.

**2. The write set of an edit.** A typed edit declares the paths it changes (one leaf for `set-param`, a whole
subterm for `mirror`, the bus record for a shared-bus edit). The compiler's closure adds every compile product
the edit invalidates, each with the first invalidating field. The write set used here is the union: the
edit's paths and the output fields of the invalidated products (so an edit to a link length reaches an
obligation that read the roll-up mass through the mass product).

**3. The lookup (numbered).**
1. Resolve the parent version and check it equals the expected parent; a stale parent is exit 7 (conflict),
   as `design.edit` already specifies.
2. Apply the edit; obtain the compiler's `EditOutcome` (new `DesignId`, `ModelId`, invalidated and reused
   products).
3. For every path in the write set, read the index by prefix: collect obligations and memo nodes.
4. Group obligations by verdict; for each verdict report which obligations are touched, split into
   feasibility and optimality obligations, and how many are untouched.
5. Close memo nodes under the memo graph's dependency edges (a comparison that consumed a touched episode is
   touched).
6. Attach to each entry the field that touched it (the first in path order).

The lookup reads the ledger only. It runs no analysis and no simulation. Determinism class D0: the set is a
pure function of the two versions and the index at a pinned ledger frontier, which the output cites.

**4. The output (`frob.invalidation/1`, a field of the `design.edit` result).**

```json
{ "parent": "d:41aa…", "child": "d:77c0…", "frontier": "184467",
  "diff": { "structural": [], "parameters": [ { "path": "legs.*.knee.gear_ratio", "old": "9", "new": "11" } ] },
  "symmetry_effect": "preserved: C2xC2",
  "compile": { "invalidated": 3, "reused": 41 },
  "assets": [ { "kind": "analysis", "key": "k:…", "name": "A-11", "touched_by": "legs.lf.knee.gear_ratio" },
              { "kind": "episode-set", "run": "r:…", "episodes": 2048, "touched_by": "legs.lf.knee.gear_ratio" } ],
  "verdicts": [ { "verdict": "v:…", "claim": "c:…", "kind": "comparison",
                  "touched": [ { "obligation": 0, "role": "feasibility", "touched_by": "legs.lf.knee.gear_ratio" } ],
                  "untouched": 3 } ],
  "counts": { "assets": 2, "verdicts": 1, "obligations_touched": 1 } }
```

Integers that can exceed 2⁵³ are strings. When the set is large the lists are paginated against the pinned
frontier and the counts are always complete. `next_actions` offers `frob result revalidate <verdict>
--after-edit <edit>` for each touched verdict, ordered by the number of touched obligations.

**5. What "touched" promises.** *Completeness:* every obligation or asset whose content would differ under a
full recomputation for the child design is in the set. *No precision promise:* a touched item may still
survive (a later revalidation may show the changed field lies outside what the obligation needed, or that a
polarity rule preserves it). The set never claims that an untouched item is valid for the child for any reason
other than this: nothing it read changed.

**6. Surfaces.** No new verb. The fields are added to `design.edit` and `design.patch` (kind `mutate`), and
`design.diff` between any two versions of a lineage returns the same record with `--invalidation`: the input
property `invalidation` (a boolean, default false) of `design.diff`, which enters the row's generated input
schema with this bead's change at M3 (an additive change; before it the flag is an unknown parameter,
`FROB-REF-802`). For two versions with several edits between them the write set is the union of the write sets
of the edits on the lineage path from the first to the second. Layer: the index in `frob-chronicle`, the
lookup in `frob-verbs`.

## Acceptance criteria

- [ ] `design.edit` and `design.patch` return `frob.invalidation/1` with assets and verdicts, their touching
      fields and complete counts; the output cites the ledger frontier it read.
- [ ] Completeness holds on 10⁴ random (design, edit) pairs over the shipped templates with stored analyses,
      episodes and verdicts: every item that differs after full recomputation is in the set.
- [ ] A rename of a display label returns an empty set; a controller-only edit touches no model analysis; a
      mass edit touches every stored rollout of the design.
- [ ] A verdict stored without a support for one obligation is always reported as touched.
- [ ] Removing an input from one obligation's recorded support (a planted mutant) makes the completeness test
      fail.
- [ ] The lookup performs zero analysis or simulation calls (counted) and is idempotent under replay of the
      same idempotency key.
- [ ] A stale expected parent returns exit 7 and writes nothing to the index.
- [ ] Documented in the `CONTRACT.md` files of `frob-verbs` and `frob-chronicle`; reachable through
      `frob --json` and the MCP tools `design_edit`, `design_patch`, `design_diff`.

## Test plan

### Unit tests

`cargo test -p frob-verbs --test edit_invalidation`:

- `rename_touches_nothing`: `rename torso → chassis` on `quad-a`; counts all zero.
- `gear_ratio_touches_envelope_not_symmetry`: A-11 (actuator envelope) is listed; A-03 (symmetry) is not.
- `controller_only_edit_keeps_model_analyses`: no analysis asset is listed; episodes under the old controller
  are.
- `mass_edit_touches_all_rollouts`: every stored episode set of the design is listed.
- `comparison_closed_under_dependency`: a comparison built from touched episodes is listed.
- `feasibility_and_optimality_split`: widening only the relay's doorway in the cart-and-relay fixture (the
  cart's trace does not pass it) touches the optimality obligation of the cost-9 cart ("every cheaper rival is
  excluded" read that doorway) and not its feasibility obligations.
- `missing_support_fails_closed`; `tombstoned_verdict_not_listed`; `stale_parent_exit_7`.
- `paginated_counts_complete`: 5,000 touched obligations, page size 500; ten pages, each row once.
- `diff_invalidation_equals_edit`: `frob design diff <parent> <child> --invalidation --json` returns the
  `frob.invalidation/1` record the gear-ratio edit returned (same assets, verdicts and counts at the same
  frontier); over the two-edit path rename then gear ratio it returns the gear-ratio edit's set; without the
  flag the result has no such field.
- Property `touched_superset_of_changed`: 10⁴ random edits; mutant `support_missing_field_is_caught`.

### End-to-end script and logging

This bead writes the step `edit_invalidation` of the M3 section of `scripts/e2e/lineage_queries.sh`
(`--section m3`, beside N28b-05's `migration`), so the invalidation set has an end-to-end check at the
milestone it ships in; the e2e bead N28b-06 (M4) owns the whole script from then on and keeps the step
unchanged. The step stores an analysis,
a 64-world referee run and a comparison for a template, applies three edits (`rename`, a gear-ratio change, a
payload mass change) with `frob design edit … --json`, and asserts the three sets above; then it runs
`frob result revalidate` on a touched verdict to show the hand-off. Logged per STD-E2E: commands, exit codes,
wall time, the evidence block, the counts against expected values, the frontier, and on failure the first
item present after full recomputation and absent from the set.

### Known answers and negative controls

- The four-state camera fixture (KA-699): renaming a display label touches nothing; delaying delivery to tick
  2 touches the two decisions' obligations that read the delivery instant. Negative control (CX-315): an index
  built from supports that omit delivery time reports nothing touched at the delay to tick 3, and the
  completeness test must catch it.
- KA-700 / CX-316: widening only the relay's doorway touches only the cart's optimality obligation.
- Invariant INV-ATEL-07 (every reused verdict carries a grade and a licence): this bead supplies the
  "untouched" evidence that grade 2 cites; a property test checks that every obligation revalidation reports
  as grade 2 was absent from the touched list for the same edit.
- Determinism: identical sets twice, across worker counts, and with the index rebuilt from scratch.

## Considerations

- RISK-38 (an incomplete memo key or support serves a stale verdict; high; owner Atelier lead). The fail-closed
  wildcard and the mutation test are this bead's part of the countermeasure; shadow recomputation is the
  memo store's.
- Index size grows with obligations × support size; supports are stored as path prefixes where a producer read
  a whole subterm. A target for lookup latency is set after the first profile, since `design.edit` must stay
  interactive.
- The set can look alarming after a mass edit (every rollout is touched). That is the honest answer: the plan
  expects exact reuse after a dynamics-affecting edit to be at most about a tenth of compute.
- Private-scene supports are indexed by cell identity, never by content, so the output leaks no scene data.
