## Background

Design versions form a content-addressed graph whose edges are typed edits. `design bisect --predicate
"<task> succeeds"` walks a path of that graph by binary search, deciding each step with the anytime-valid
paired comparison, and returns the edit that changed the outcome. It is the studio's answer to "which of my
last thirty edits broke stair climbing?" (North-Star scenario NS-06). Tier: Solid.

Binary search is correct only for a predicate that is monotone along the path (once it fails it stays
failed). Design lineages are not like that: an edit breaks a task and a later edit repairs it.
Counterexample CX-313: outcomes along six versions are pass, fail, pass, pass, pass, fail. The midpoint
passes, the search goes right and reports the last edit, while the first edit also changed the outcome and the
second changed it back. A tool that calls its answer "the first bad edit" is then wrong, and nothing in its
output shows it.

The plan's rule is that bisect says only what it knows. It returns a pair of adjacent versions with different
decided outcomes, which is always a true statement, labelled `a-change`. It labels the result `first-change`
only after the prefix has been scanned (every earlier version decided) or when the caller declares the
predicate monotone, which is recorded as an assumption on the result. And bisect controls its own error: each
probe is an e-process at level α/⌈log₂ L⌉ for a path of L edits, so the whole search errs with probability at
most α by the union bound; an inconclusive probe ends the search with the bracket reached and the evidence so
far.

Rejected alternatives: refusing non-monotone lineages outright (monotonicity cannot be known before probing,
so the tool would refuse always or never); always scanning the whole prefix (linear cost where the caller only
needs one change to revert); a fixed episode count per probe with no error accounting (thirty probes at 5%
each are wrong somewhere with high probability).

## Scope

In: the search plan (which versions are probed, in what order, at what level); mapping a comparison verdict to
a probe outcome; the result record and its labels; the prefix scan; the declared-monotone assumption; refusal
`FROB-REF-550`; the union-bound derivation for proof obligation PO-ATEL-08.

Out: the verb, its job and budget handling and its memo use (BD-343); the paired comparison itself (BD-262);
the planted-lineage battery (N28b-03); lineage merge (N28b-04).

## Technical approach

**1. Inputs.** A lineage path v₀ … v_L (L edits; `good` = v₀, `bad` = v_L, which must descend from v₀; when
several paths join them, the one the caller names with `--via`, else the path with the fewest edits, ties by
canonical bytes, the rule the verb BD-343 exposes; the rule used is stated in the result as `path_rule`).
Migration edges whose record says `semantic: Identical` are contracted before planning by N28b-05's
`lineage::contract_identical_migrations` (they change no model, and probing them would spend error budget on
nothing), and L counts the remaining edits; a `Changed` migration stays on the path as a step. A predicate (a task, the success metric, a margin δ and the
world addresses to pair on); a total level α (default 0.05); a budget; two flags, `--scan-prefix` and
`--assume-monotone`; and an optional `--require first-change`, by which a caller says that an `a-change` is
not an acceptable answer.

**2. A probe.** The predicate is relative to the good endpoint: v₀ is the reference and its outcome is `pass`
by definition (it is never probed). Deciding any other version v is one paired study of type `anytime` between
v and v₀, on common world addresses, on the predicate's success indicator (its span, [−1, 1], is fixed by the
predicate before the first observation). The comparison's verdict maps to a probe outcome (the verb's words,
BD-343, in brackets):

| Comparison verdict | Probe outcome |
|---|---|
| `settled`, v worse than v₀ by more than δ | `fail` (`changed`) |
| `tied` within ±δ, or `settled` with v not worse than v₀ (a version better than v₀ by more than δ is `pass`, not undecided) | `pass` (`unchanged`) |
| `inconclusive` at budget, `incomparable`, `infeasible` | `undecided` (`inconclusive`) |

Episodes are consumed in address order, so a probe's e-value does not depend on completion order or memo hits
(INV-ATEL-02).

**3. The error budget (fixed before the first probe).** Let P be the number of probes the plan can make.
Without a prefix scan, P = ⌈log₂ L⌉ + e, where e = 1 when the bad endpoint has no stored decided outcome
against v₀ and 0 otherwise (the good endpoint is the reference and is never probed); with the bad endpoint
already decided this is the plan's α/⌈log₂ L⌉. With `--scan-prefix`, P is the
number of versions that may need deciding, the L − 1 interior versions plus e, so at most L (DESIGN: the plan states the binary-search budget;
the scan needs the same union bound over more probes, so its per-probe level is smaller). Each probe runs at
α_probe = α/P. If every probe errs with probability at most α_probe, the search errs with probability at most
P·α_probe = α.

**4. The search (numbered).**
1. Decide the bad endpoint v_L against v₀ if not stored. If it is decided `pass`, return label `no-change`
   (exit 2) with its probe record; if it is `undecided`, return label `bracket` with (lo, hi) = (0, L) and its
   record (exit 2). No interior version is probed in either case.
2. Keep (lo, hi) with outcome(v_lo) = `pass` and outcome(v_hi) = `fail`. Probe mid = ⌊(lo + hi)/2⌋; replace lo
   or hi. An `undecided` probe stops the search: return label `bracket` with (lo, hi), every probe's record
   and the e-values so far (exit 2).
3. When hi = lo + 1: the edit from v_lo to v_hi changed the decided outcome. Label `a-change`.
4. If `--scan-prefix`: decide v₁, v₂, … in ascending order up to v_lo, skipping versions already decided. The
   first version j decided `fail` gives the pair (v_{j−1}, v_j) with label `first-change` (every earlier
   version is decided `pass`). If none fails, the pair of step 3 is relabelled `first-change`. An `undecided`
   scan probe leaves the label `a-change` and reports how far the scan got.
5. If `--assume-monotone` (and no scan): label `first-change` and add the assumption `monotone-predicate
   (declared by caller)` to the result's assumptions; it travels with the result's claim product.
6. `--require first-change` with neither flag is refused before any probe: `FROB-REF-550` (`first-change`
   asked of bisect without a prefix scan or a declared monotone predicate; repairs, in order: scan; or declare
   and record the assumption; exit 3).

**5. The result (`frob.bisect/1`).** `{ path: [DesignId…], path_rule, predicate, alpha, probes_planned,
alpha_per_probe, probes: [ { version, outcome, verdict, e_value, pairs: {a_only, b_only, both, neither,
unscored, planned}, study } ], bracket: { lo, hi }, edit: EditRef | null, label: "a-change" | "first-change" |
"bracket" | "no-change", scanned_through: index | null, assumptions: [...], other_changes_possible: bool }`.
`other_changes_possible` is true exactly when the label is `a-change`. The result's evidence: claim kind
Design comparison (development result on discovery worlds), class Tested, with the tier and determinism class
of the probes.

**6. Worked case (the known answer).** Six versions with outcomes pass, fail, pass, pass, pass, fail; L = 5,
⌈log₂ 5⌉ = 3; the bad endpoint's outcome is stored (otherwise its decision is a fourth probe and P = 4). Probes: v₂ pass (lo = 2), v₃ pass (lo = 3), v₄ pass (lo = 4); bracket (4, 5); label `a-change`
at the fifth edit; three probes at α/3 each. With `--scan-prefix`: v₁ is decided `fail`, so the result is
`first-change` at the first edit, and the fifth edit is still listed among the changes found.

**7. Layout.** `crates/frob-opt/src/lineage/bisect/{plan.rs, probe.rs, result.rs}` (module
`frob-opt::lineage::bisect`, the target the counterexample registry N28-CX names for CX-313's control); the
derivation of the bound in `docs/derivations/po-atel-08.md`.

**8. The planted control `bisect-last-edit-first-change` (CX-313, N28-CX).** This bead builds the planted
variant as a `cfg(feature = "nc-<nnnn>")` branch in `frob-opt::lineage::bisect`, where `<nnnn>` is the `NC-`
number the seeding tool (N38b-05) assigns to N28-CX's entry: step 3 labels the bracket found by plain binary
search `first-change` with no prefix scan and no declaration. It is built only with `--features
gauntlet-mutations,frob-opt/nc-<nnnn>`, one control per build, never in a product build. On (pass, fail, pass,
pass, pass, fail) the variant reports `first-change` at the last edit; KA-702's test and the bisect row of
GATE-ATEL-04 must fail on it. Its row in `crates/frob-conformance/registry/controls.toml` is written by the
seeding tool from N28-CX's entry, not by hand; the battery N28b-03 runs it.

## Acceptance criteria

- [ ] On the six-version case the result is `a-change` at the last edit after exactly three probes; with
      `--scan-prefix` it is `first-change` at the first edit.
- [ ] `first-change` requested without scan or declaration returns `FROB-REF-550` with exit 3 and runs no
      probe.
- [ ] `--assume-monotone` yields `first-change` with the assumption recorded on the result and in its claim
      product.
- [ ] `alpha_per_probe` equals α divided by the planned probe count, fixed before the first probe and
      unchanged by early termination; with stored endpoints and no scan it is α/⌈log₂ L⌉.
- [ ] An `undecided` probe ends the search with label `bracket`, the bracket and all probe records.
- [ ] Equal endpoints return `no-change`.
- [ ] The written union-bound derivation exists and is cited by PO-ATEL-08's test (N28b-03).
- [ ] Every probe record satisfies the accounting identity a_only + b_only + both + neither + unscored =
      planned.

## Test plan

### Unit tests

`cargo test -p frob-opt --test bisect_rules` (probes answered by a `synthetic` outcome table, so the search
logic is tested exactly; the statistical behaviour is N28b-03's):

- `six_version_a_change`: outcomes (P, F, P, P, P, F) → probes at 2, 3, 4; label `a-change`; edit index 5.
- `six_version_scan_first_change`: same with scan → `first-change`, edit index 1, `scanned_through = 1`.
- `monotone_path_scan_agrees`: (P, P, P, F, F, F, F, F) → probes at 3, 1, 2; `a-change` at edit 3; with scan
  `first-change` at edit 3 and no extra probe (v₁ and v₂ were decided by the search and are skipped).
- `first_change_without_licence_refused_550`.
- `assume_monotone_records_assumption`.
- `alpha_split`: L = 30, bad endpoint stored → P = 5, α_probe = 0.01; L = 30 with scan, bad endpoint stored
  → P = 29, α_probe = 0.05/29; L = 5, bad endpoint not stored → P = 4; the good endpoint is never counted.
- `identical_migration_contracted`: a path of nine edits, one an `Identical` migration, plans ⌈log₂ 8⌉ = 3
  probes, not ⌈log₂ 9⌉ = 4; with a `Changed` migration it plans 4.
- `undecided_probe_returns_bracket`: the probe at v₃ is `undecided` → label `bracket`, (lo, hi) = (2, 5).
- `equal_endpoints_no_change`: v_L decided `pass` → `no-change`, no interior probe.
- `undecided_bad_endpoint_brackets`: v_L `undecided` → `bracket` (0, L), no interior probe.
- `better_version_is_pass`: a version settled better than v₀ by more than δ maps to `pass`.
- `path_rule`: with two paths from good to bad, `--via` selects the named one; without it the path with fewer
  edits is used (ties by canonical bytes) and `path_rule` says which rule applied; a `bad` that does not
  descend from `good` returns `NoPath` naming both versions and plans no probe (the verb reports it as invalid
  input).
- `verdict_mapping`: each comparison verdict maps to the outcome of the table in 2.
- Property `adjacent_pair_always_differs`: for random outcome tables with pass and fail endpoints, the
  returned pair is adjacent and its two outcomes differ.
- Property `first_change_is_first`: whenever the label is `first-change` after a scan, no earlier adjacent
  pair differs in the table.

### End-to-end script and logging

Covered by `scripts/e2e/lineage_queries.sh` (bead N28b-06), step `bisect`: a six-version lineage built with
`frob design edit` in which three edits are planted (the first, an actuator swap, breaks the task; the
second, a regear, repairs it; the fifth breaks it again), then `frob design bisect --good v0 --bad v5
--predicate succeeds --task stand-recover --level 0.05 --key <k> --json` (the verb's spellings, BD-343) with and
without `--scan-prefix` (distinct keys), and once with `--require first-change` alone (expecting 550, no probe). Logged per STD-E2E: commands, exit codes, wall time, evidence block, each probe's version, outcome,
e-value and pair counts, α per probe, the label, and on failure the first probe whose outcome differs from the
plant.

### Known answers and negative controls

- KA-702: outcomes pass, fail, pass, pass, pass, fail → an `a-change` at the last edit; no `first-change`
  without a scan of the prefix. Negative control: the planted variant `bisect-last-edit-first-change` of
  section 8 (`cargo test -p frob-opt --features nc-<nnnn> --test bisect_rules`) reports `first-change` at the last edit, and `six_version_a_change` and `first_change_is_first` must fail on
  it.
- CX-313: the same case, as the counterexample this rule protects against.
- PO-ATEL-08 (`design.bisect` errs with probability at most α and never reports `first-change` wrongly): the
  second half is discharged by the two property tests above; the first half by N28b-03.
- Determinism: the plan and the labels are pure functions of the probe outcomes; identical twice and across
  worker counts.

## Considerations

- The seed line for the bisect verb says "bisect on a non-monotone predicate is refused"; the chapter says a
  non-monotone lineage yields a true `a-change` and only an unlicensed `first-change` is refused. This bead
  follows the chapter. A blanket refusal could not be implemented, since monotonicity is unknown before the
  probes.
- A scan costs up to L probes; the estimate printed before the run states both costs so the caller chooses.
- Probes reuse stored episodes through the memo graph; a reused probe reaches the identical e-value.
- Bisect runs on discovery worlds. Its result is a development result and is not reported as a claim; a
  change that matters is confirmed through the blinded qualification lane.
- The margin δ decides what counts as "the outcome changed"; too small a margin makes probes inconclusive.
  The bracket result with its e-values tells the agent which probe needs more pairs.
