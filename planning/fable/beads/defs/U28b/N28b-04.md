## Background

Several agents work on one design problem at once, on two machines, and each grows its own lineage of design
versions and its own archive of good designs. When their work is combined the result must not depend on who
synchronized first; otherwise two replays of the same campaign give different archives, and "the best design
in cell (mass 12 to 14 kg, speed 1.0 to 1.2 m/s)" depends on message timing. The plan's rule: lineages and
archives from several agents merge as grow-only sets of versions and per-cell maxima under a total order
(fitness, then `DesignId`). The merge is commutative, associative and idempotent (invariant INV-ATEL-09), so
the result does not depend on arrival order. Tier: Solid.

FACT: FrankenSim's `fs-archive::MapElites::add` replaces an elite only on strict improvement, so on equal
fitness the first arrival stays. That makes the sibling's archive depend on arrival order whenever two designs
tie, which quantized scores make common. The total order removes that dependence.

The archive half (cells and elites, and the two-agent byte-equality check of the cascade gate) is built with
the quality-diversity archive (BD-342). This bead builds the lineage half and the shared machinery: one `Join`
abstraction, canonical serialization, and one law suite applied to both structures, so that "commutative,
associative, idempotent" is a tested property of the code that both use, not a sentence in two contracts.

Rejected alternatives: last-writer-wins on named heads (arrival-dependent by construction); a merge log
replayed in timestamp order (wall-clock time must never decide content); a central lock so that only one agent
writes (serializes the swarm and still fails when two machines are partitioned).

## Scope

In: the `Join` trait and law suite; the lineage graph as a grow-only set of versions, edges and migration
records; namespaced heads and the conflict rule; the total order used for ties, extended to be total on
records; canonical bytes of a merged lineage; absorption of another agent's lineage into a namespace.

Out: archive cells, descriptors and `opt.archive` (BD-342); the lineage graph's basic storage, diff and blame
(BD-113); bisect (BD-343, N28b-02); who is allowed to absorb what (the capability bead).

## Technical approach

**1. A join-semilattice (DESIGN).**

```rust
/// DESIGN. `join` must be commutative, associative and idempotent; the law suite checks it for every impl.
pub trait Join { fn join(&mut self, other: &Self); }
```

Implementations: `GrowSet<T: Ord>` (union); `MaxMap<K: Ord, V: Ord>` (per key, the greater value under V's
total order); products of the two. A structure is merged only through `join`; no code path inserts "if absent"
or "if strictly better".

**2. The lineage as grow-only sets.**

- `versions: GrowSet<DesignId>`; the bytes of a version are content-addressed, so two agents that produced the
  same design hold the same element.
- `edges: GrowSet<(DesignId parent, EditId, DesignId child)>`, with `EditId` the BLAKE3 of the typed edit's
  canonical bytes (kind, arguments, expected parent). Idempotency keys, timestamps, agent names and trace
  identifiers are metadata beside an edge and never part of an element, so the same edit applied by two agents
  to the same parent is one edge.
- `migrations: GrowSet<MigrationRecord>` (N28b-05).
- Edge metadata that differs between agents (who applied it, when) is itself a `GrowSet` of attestations per
  edge, so nothing is overwritten.

Nothing is ever removed by a merge. Retention removes objects through tombstones under its own rules, and a
tombstone is also an element of a grow-only set, so a deletion survives a merge with an agent that still holds
the object.

**3. Heads and names.** A head is a mutable pointer from a name to a version, and mutable pointers do not
merge as sets. Names are therefore namespaced (`<namespace>/<name>`): merging two namespaces' lineages unions
the versions and edges and keeps both sets of heads. Inside one namespace, two different targets for one name
at the same parent is a lineage conflict: the second writer gets exit code 7 (conflict: stale parent or
lineage conflict) and must rebase its edit on the current head, exactly as `design.edit` does for a stale
expected parent. A head update is `(name, expected_old, new)` and is refused unless `expected_old` is current.

**4. The total order for maxima.** A fitness is an exact value (a quantized integer or a reduced rational;
a design without a score is not a candidate for a maximum). Elites are compared by
`(fitness, DesignId, EvidenceId)`, lexicographically, where `EvidenceId` is the content hash of the evidence
the fitness came from. The plan fixes (fitness, then `DesignId`); the third component is added (DESIGN) so the
order is total even when the same design carries two fitness records from two runs, which would otherwise
leave the choice to arrival. Flags on an elite (`provisional`, rank-robustness type) travel with the record
chosen.

**5. Canonical bytes.** `Lineage::to_canonical_bytes` writes versions, edges, migrations, attestations and
heads sorted by their natural order, in canonical JSON, with no timestamps outside attestations. Two lineages
that are equal as sets have equal bytes. This is what "merge in both orders gives identical bytes" is checked
on.

**6. Absorption.** `Lineage::absorb(&mut self, other: &Lineage)` = `join` on every component, in one ledger
transaction, followed by an integrity check: every edge's parent and child are in `versions`; every head
points to a version. It is called when a campaign closes (the partial lineages of the workers on the two
machines are combined), when a session imports another namespace's lineage with the capability to read it,
and before `design.bisect` or `design.blame` runs over a path that crosses namespaces. No verb is registered
by this bead; the merged graph is what `design.diff`, `design.blame`, `design.bisect` and `opt.archive` read.

**7. Determinism.** D0: the merged lineage is a pure function of the set of inputs, whatever their order,
grouping or multiplicity.

## Acceptance criteria

- [ ] The law suite passes for `GrowSet`, `MaxMap`, the lineage and (through BD-342's type) the archive:
      join(a, b) = join(b, a); join(join(a, b), c) = join(a, join(b, c)); join(a, a) = a; bytes compared.
- [ ] Two agents' lineages built from disjoint and from overlapping edit sequences merge to identical
      canonical bytes in both orders, and merging a third in any of the six orders gives the same bytes.
- [ ] The same typed edit applied by two agents to the same parent yields one edge with two attestations.
- [ ] A tie in fitness between two designs resolves to the same elite in both merge orders; a variant that
      keeps the first arrival (the sibling's strict-improvement rule) fails the commutativity test.
- [ ] A second, different target for one head at the same expected parent returns exit 7 and changes nothing.
- [ ] After absorption every edge's endpoints and every head's target are present (integrity check).
- [ ] A tombstoned version stays tombstoned after merging with a lineage that still lists it.
- [ ] `frob-opt/CONTRACT.md` states INV-ATEL-09 and the order used.

## Test plan

### Unit tests

`cargo test -p frob-opt --test merge_laws`:

- `growset_laws`, `maxmap_laws`: property tests over 10⁴ random triples.
- `lineage_merge_commutes_bytes`: two lineages of 200 edits each sharing a 50-edit prefix; bytes equal in
  both orders.
- `lineage_merge_three_way_all_orders`: six orders, one byte string.
- `same_edit_two_agents_one_edge`: attestations = 2, edges = 1.
- `tie_break_by_design_id`: fitness 0.74 for designs d:aa… and d:bb…; the elite is d:bb… (the greater
  identifier) in both orders.
- `tie_break_by_evidence_when_same_design`: one design, two evidence records, equal fitness → the greater
  `EvidenceId`, in both orders.
- `strict_improvement_rule_is_not_commutative`: the mutant keeps different elites in the two orders (negative
  control).
- `head_conflict_exit_7`; `integrity_after_absorb`; `tombstone_survives_merge`.
- `timestamps_do_not_enter_bytes`: the same merge with different attestation times differs only inside the
  attestation set, and `EditId`s are unchanged.

### End-to-end script and logging

Step `merge` of `scripts/e2e/lineage_queries.sh` (bead N28b-06): two sessions in two namespaces each apply a
scripted sequence of `frob design edit` calls to the same template (ten shared edits, then five each); the
script absorbs A into B and B into A in two fresh stores, exports both lineages, and compares bytes; then it
runs `frob design blame` on a field changed by the other agent to show the merged graph is queryable. Logged
per STD-E2E: commands, exit codes, wall time, evidence blocks, the counts of versions, edges and attestations
against expected values (21 versions, 20 edges and 30 attestations for this script: the template, ten shared
edits attested twice, and five edits from each agent), the two digests, and on failure the first element
present in one merge and absent from the other.

### Known answers and negative controls

- INV-ATEL-09 (lineage merge and archive merge are commutative, associative and idempotent): the law suite is
  its property test.
- Negative controls: the strict-improvement mutant; a mutant that puts the idempotency key into `EditId` (two
  agents' identical edits then become two edges, and the byte comparison fails).
- Metamorphic: merging a lineage with a subset of itself changes nothing; splitting a lineage into any two
  covering parts and merging them reproduces it.
- Determinism: bytes identical twice, across worker counts and on both host platforms.

## Considerations

- The cascade's end-to-end gate checks that "merge of two agents' archives in both orders gives identical
  bytes"; this bead supplies the same guarantee for lineages so that the archive's elites always resolve to
  versions present in the merged lineage.
- Grow-only sets grow: storage is bounded by retention (tombstones), not by merge.
- Two namespaces can hold different private scenes; a lineage carries design identities only, so absorbing it
  moves no scene data. Whether an agent may read another's designs at all is a capability question.
- If two versions collide under BLAKE3 the store reports an integrity fault (exit 9); the merge never chooses
  between two byte strings with one identity.
