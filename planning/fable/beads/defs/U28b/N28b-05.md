## Background

Schemas change. The design language will gain fields, a verdict record will gain an obligation kind, a run
manifest will gain a channel attribute. If a migration rewrote stored objects in place, every identity that
was a content hash would silently name different bytes, every stored run would cite a design that no longer
exists in that form, and no old result could be replayed. The plan's rule for lineage: **migration keeps old
replay possible.** A schema migration reads the old object and writes a new one with migration provenance.
The old version stays addressable and replayable with the worker version that produced it. Tier: Solid.

This matters to the studio because its evidence is long-lived: a comparison promoted in one month is cited in
a report three months later, and "replay it" must still mean something after two schema revisions. It also
matters to lineage queries: a migration must not show up in `design blame` as the edit that introduced a
parameter value, and `design bisect` must not probe a migration step as if it were a design change.

Rejected alternatives: in-place upgrade (destroys identities); refusing to read old schemas (strands
evidence); keeping only the new object and a note (the old run then cannot be replayed bit for bit, because
its inputs are gone).

## Scope

In: the migration record and the treatment of `migrate` edges in the lineage graph; how diff, blame and bisect treat
migration edges; which evidence follows a migrated design and which does not; resolution of the producing
worker for replay of an old run; the refusal and the comparison-replay path when that worker is unavailable.

Out: the migrators' own correctness (the Skeleton unit's migration bead); replay mechanics (BD-203); worker
process plumbing (BD-038); retention (BD-209); format registry rows (BD-141).

## Technical approach

**1. The migration record (DESIGN).**

```rust
/// DESIGN. One per migrated object; an element of the lineage's grow-only `migrations` set.
pub struct MigrationRecord {
    old: ObjectId,                 // content hash of the object as stored under the old schema
    new: ObjectId,                 // content hash of the object written under the new schema
    kind: ObjectKind,              // Design | Verdict | RunManifest | Card | Scene | Task …
    from_schema: SchemaId,         // e.g. frob.design/1
    to_schema: SchemaId,           // e.g. frob.design/2
    migrator: MigratorId,          // dotted name, version, and BLAKE3 of the migrator's source
    semantic: SemanticEffect,      // Identical { model: ModelId } | Changed { fields: Vec<Path>, reason }
}
```

Migration is a pure function of the old bytes and the migrator: the same input gives the same `new`
(idempotent, D0). The old object is never modified, tombstoned or unpinned by a migration.

**2. In the lineage graph.** For designs, a migration is the typed edit `migrate` of the design language (its
declared symmetry effect is none by construction, and its invalidation scope is none when the migration is
certified meaning-preserving and global otherwise). It adds a `migrate` edge from `old` to `new`, which the
queries treat differently from every other edit kind:

- `design.diff` across a `migrate` edge reports `migration: frob.design/1 → frob.design/2` and, when
  `semantic` is `Identical`, an empty structural and parameter diff. When it is `Changed` (a migrator had to
  fill a field that has no default-free reading, for example a wall thickness that the new schema requires),
  the changed fields are listed with the migrator as their source.
- `design.blame` attributes a parameter value to the typed edit that introduced it, looking *through*
  migration edges. Only a field that a migration itself set is blamed on the migration, with its record.
- `design.bisect` contracts migration edges with `semantic: Identical` before planning (they change no model,
  and probing them would spend error budget on nothing). A `Changed` migration stays on the path as a step.

**3. Which evidence follows.** Identities are content hashes, and evidence is keyed by the identity it was
computed for. A migration changes the `DesignId` (the bytes changed). The compiled model may or may not
change:

- `semantic: Identical { model }`: the old and the new design compile to the same `ModelId`. Analyses,
  episodes and verdicts keyed by the model identity apply to both, with no pooling question, because it is one
  model.
- `semantic: Changed`: the `ModelId` differs. Evidence and calibration are never pooled across model
  identities (INV-ATEL-05): ledger rows keyed by the old model stay with the old model, and the new design
  starts its own. `result.revalidate` treats the migration as an edit with the listed changed fields.

**4. Replay of an old run with the worker that produced it.** A run manifest names kernel versions, the tier,
the determinism class and the *producer*: the worker build identity (commit, the toolchain, the hash of the
stack lock). `sim.replay` resolves the producer:

1. If the current build equals the producer, replay in process.
2. Else look up a worker binary of that build identity in the binary cache (workers are cached by build
   identity when they are built) and run the replay in a worker process of that build.
3. Else return a typed refusal that carries the producer's build identity and the exact command that builds
   it from its commit, and offer the alternative: a *comparison replay* under the current worker, whose
   result is labelled a comparison and never a continuation. A snapshot restored under another numerical
   profile and labelled a continuation is refused with `FROB-REF-894` (repair: request a comparison replay;
   exit 3).

The old design bytes, old kernels' sources and the old run's chunks are all content-addressed and are read as
they were written; nothing is migrated in order to replay.

**5. Store rule.** Readers accept every schema version with a registered migrator and present objects in the
current schema *as a view*; the stored bytes under the old identity are returned unchanged by
`artifact.read`. A schema with no registered migrator is refused on read with the schema identifier named.

**6. Layout.** `crates/frob-opt/src/lineage/migration.rs` (edge kind, query rules);
`crates/frob-chronicle/src/producer.rs` (producer resolution). Documented in both `CONTRACT.md` files.

## Acceptance criteria

- [ ] After migrating a design from schema 1 to schema 2, both `DesignId`s resolve; `artifact.read` of the old
      identity returns the original bytes; the lineage holds one `migrate` edge and one record.
- [ ] Migration is idempotent: migrating the same old object twice yields one `new` identity and one record.
- [ ] `design.diff` across an `Identical` migration is empty apart from the migration line; `design.blame` of
      a parameter set three edits before the migration names that edit, not the migration.
- [ ] `design.bisect` on a path with an `Identical` migration plans no probe for it (the planned probe count
      equals that of the path without it).
- [ ] With `Identical`, analyses stored for the old design are served for the new one (same `ModelId`); with
      `Changed`, none is, and the ledger rows are not pooled.
- [ ] A run recorded before a migration replays with identical digests through a cached worker of its
      producer build; with that worker absent the verb returns the refusal with the build command, and the
      comparison replay is labelled a comparison.
- [ ] A read of a schema version with no migrator is refused, naming the schema.

## Test plan

### Unit tests

`cargo test -p frob-opt --test lineage_migration` and `-p frob-chronicle --test producer`, using a `synthetic`
schema pair (`frob.design/1` and a test-only `frob.design/2-test` that renames one field and adds one
required field):

- `old_and_new_both_resolve`; `old_bytes_unchanged`; `migration_idempotent`.
- `diff_identical_migration_empty`; `diff_changed_migration_lists_fields` (the added required field is listed
  with the migrator as source).
- `blame_looks_through_migration`; `blame_names_migration_for_filled_field`.
- `bisect_contracts_identical_migration`: L = 8 with one identical migration → planned probes ⌈log₂ 7⌉ = 3.
- `evidence_follows_model_identity`: same `ModelId` → analysis memo hit; different → miss and no pooled row.
- `producer_resolution_order`: equal build → in process; cached build → worker; none → refusal with command.
- `comparison_replay_not_continuation`: a request to continue from an old snapshot under the current worker
  returns `FROB-REF-894`.
- `unknown_schema_refused`.

### End-to-end script and logging

Step `migration` of `scripts/e2e/lineage_queries.sh` (bead N28b-06): build the previous release's worker from
its tag into the binary cache (or use the cached one), record a 16-world referee run with it, apply the
test-only migration with `frob design edit <design> migrate --json`, then run `frob design diff`, `frob design blame`,
`frob sim replay <old run> --json` (expect identical digests, producer = old build) and the same replay with
the worker cache hidden (expect the refusal and its build command). Logged per STD-E2E: commands, exit codes,
wall time, evidence blocks, both design identities, the producer identity, digest comparisons, and on failure
the first differing chunk digest with the paths to replay it.

### Known answers and negative controls

- Negative controls: an in-place upgrade (a mutant store that rewrites the old object) makes
  `old_bytes_unchanged` and the replay digest test fail; a mutant that pools ledger rows across a `Changed`
  migration is caught by the INV-ATEL-05 property test (evidence and calibration are never pooled across
  model identities).
- Metamorphic: migrate then diff equals diff then migrate on both sides (the diff of two migrated designs
  equals the diff of the originals when both migrations are `Identical`).
- Determinism: migration and its record are D0; replay through the producer worker is in the run's own
  determinism class.

## Considerations

- Keeping old worker builds costs disk; the binary cache evicts workers no live claim's runs name, and the
  refusal tells the user how to rebuild one, so eviction never strands evidence permanently.
- A toolchain that can no longer build an old commit is a real risk for long-lived evidence; the stack lock
  hash in the producer identity makes the dependency explicit, and the comparison replay is the fallback.
- A migrator is code and can be wrong; its semantic claim (`Identical`) is checked by compiling both and
  comparing `ModelId`, never taken on trust.
- Private-scene objects migrate under their privacy class; a migration record holds identities only.
