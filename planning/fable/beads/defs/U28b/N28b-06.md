## Background

Lineage is a user-visible capability of the studio: an agent asks what changed between two versions, which
edit set a value, which edit broke a task, and what its own edit put in question, and it expects the same
answers whether it worked alone or beside another agent, before or after a schema revision. Each mechanism
behind those answers has its own unit tests. This bead is the end-to-end script that drives them together
through the real `frob` binary (and two `frob-mcp` sessions for the merge), on real fixtures, with structured
logging, so that after implementation one command shows the whole capability working. It carries North-Star
scenario NS-06 at small scale: a lineage of edits, a task that stopped succeeding, and the edit found.

This is the only end-to-end bead of the lineage queries (the key N28a-31 and its script name
`atelier_lineage.sh` were merged into it). The script has three sections, each written by the bead whose
mechanism ships at that milestone so that no mechanism waits for M4 to have an end-to-end check: an M1
section (`design.diff`, `design.blame` and the edit's envelope; written by BD-113), an M3 section (the edit's
invalidation set, written by N28b-01, and replay after migration, written by N28b-05), and an M4 section
(bisect, the planted bisect, two-agent merge and the gate query, with BD-343's own script
`scripts/e2e/design_bisect.sh` run as its first stage) added by this bead, which owns the whole script from M4
on and keeps the earlier steps unchanged; this bead is recorded at the milestone that completes it.

The verbs exercised and their registry entries: `design.diff` (read, M1: structural and parameter difference
of two versions, with the symmetry effect), `design.blame` (read, M1: the edit that last changed a field or a
derived quantity), `design.edit` (mutate, M1: one typed edit; returns the new `DesignId`, the symmetry effect
and the invalidation set), `design.bisect` (run, M4: find the edit in a lineage that changed a verdict, with
an anytime-valid comparison at each step).

## Scope

In: one script, `scripts/e2e/lineage_queries.sh [--section m1|m3|m4|all]`, its M4 steps and their
assertions, the integration of the M1 and M3 steps into one run; the stage that runs BD-343's script; the
fixture lineages it builds; its log; its self-test.

Out: the 100-lineage statistical battery (N28b-03), whose gate row this script only queries; the archive's
two-agent merge check (BD-342); unit tests of each mechanism (BD-113, BD-343, N28b-01, N28b-02, N28b-04,
N28b-05); the checks of `design.bisect` that BD-343's script makes (the twelve-edit lineage with
`--scan-prefix` and `--assume-monotone`, the refusals 550, 802 for a non-descendant and 543, the merge bytes),
which this script runs as a stage and does not repeat.

## Technical approach

The script is plain shell, idempotent (it works only in the run's own state root `FROB_STATE`, which STD-E2E's
`e2e_init` exports under `target/e2e-scratch/lineage_queries/<run_id>/state/`, with `work/` beside it as the
working directory and the place of the merge step's two stores; `frob` has no `--root` option and reads no
`FROB_HOME`), seed-explicit (`--seed 11` everywhere a seed is taken; `FROB_E2E_SEED` overrides it), and exits
non-zero on the first failed assertion after writing its summary. `--section m1` runs the steps `m1_edits`,
`diff` and `blame`; `--section m3` runs `edit_invalidation` and `migration`; `--section m4` runs
`design_bisect`, `bisect`, `bisect_planted`, `merge` and `gate_query`; `all` is the default at the fourth
milestone.

**Fixture built by the script.** From the template `quad-mammal`, six versions v₀ … v₅ by five typed edits:
e₁ swaps the knee actuators for a card with half the continuous torque (breaks "stand and recover"); e₂
regears the knees so the margin returns (repairs it); e₃ renames a link (inert); e₄ moves a payload mount by
5 mm (inert for the task); e₅ shortens the shank by 30% (breaks it again). Each edit is applied with
`frob design edit <name> <edit> … --expected-parent <id> --key <k> --json` (the spellings of the `design.edit`
row). Every call of the run verb `design.bisect` below carries its own `--key`; two bisect runs the script
compares (the plain and the fuzzed run, a run with and without a flag) carry distinct keys, so the second is
computed and not answered from the first one's stored receipt.

A second, three-edit lineage is used by the M1 section: from the same template, thigh length 0.21 → 0.24 m
(`set-param`), knee ratio 1.55 → 1.8 (`regear`), shank material aluminium → carbon laminate
(`set-material`). A third, twelve-edit lineage with one planted breaking edit (a regear that takes the knee
below the step-up torque at edit 7) and eleven neutral edits is used by `bisect_planted`. When the wheel-leg
archetype and its stair task exist the bisect scenarios use them; until then they use the quadruped template
and a step-up task.

**Steps and assertions.**

| Step | Commands | Asserts |
|---|---|---|
| `m1_edits` | `frob design new` from the template; the three `frob design edit` calls; then the second edit repeated against the root as expected parent | The four `DesignId`s recorded; each edit's envelope carries a diff, a symmetry effect and an invalidation set; the stale parent exits 7 with `FROB-REF-804` (the surface's stale parent; 112 is a patch document's) and the current head returned |
| `diff` | `frob design diff v0 v5 --json`; on the three-edit lineage `frob design diff <root> <head> --json`, its edits applied to a fresh copy of the root with `frob design patch`; a branch made from the second version by a different third edit, then `frob design diff <branch-a> <branch-b>` | The diff lowers to exactly the five edits' net parameter changes; the rename appears as structural-only; the symmetry effect is reported; the three-edit diff has three edits and the patched `DesignId` equals the head's (the diff round trip on the real binary); the branch diff's emitted edits reproduce branch b |
| `blame` | `frob design blame v5 <JSON pointer of the left-front knee's gear ratio> --json` (the field is the positional second argument of the `design.blame` row, as in its example `frob design blame quad-a /limbs/…/ratio --json`; there is no `--field`); on the three-edit lineage, blame of the knee ratio, the thigh length, a field never edited and `mass.total`; then a rename edit and `blame mass.total` again | Names e₂; blame of the shank length names e₅; blame of a field no edit touched names the template (`since-root`); on the three-edit lineage the knee ratio names the second edit with values 1.55 and 1.8 (the seed condition of the lineage bead), the thigh length the first, the derived quantity `mass.total` the third, and still the third after the rename |
| `edit_invalidation` | A stored A-11 analysis, a 64-world referee run and a comparison; then the edits again with `--json` | Rename: empty set; regear: A-11 and the run touched; counts complete; frontier cited (N28b-01) |
| `design_bisect` | The stage `scripts/e2e/design_bisect.sh` (owned by BD-343: its twelve-edit lineage with and without `--scan-prefix` and `--assume-monotone`, `--require first-change` alone, `--good v12 --bad v0`, a predicate on a metric with no declared span, two branches' lineages merged in both orders), run with the run's seed; the step reads the stage's `summary` line | The stage exits 0 with zero failed assertions; its refusals 550, 802 (pointer `/bad`) and 543 each with no probe; its log path is recorded |
| `bisect` | `frob design bisect --good v0 --bad v5 --predicate succeeds --task stand-recover --level 0.05 --key bis-a --json` and the same with `--scan-prefix` (key `bis-b`) | `a-change` at e₅ after the endpoint probe of v₅ and the interior probes v₂, v₃, v₄, each at α/4 (P = ⌈log₂ 5⌉ + 1: v₅ has no stored outcome; N28b-02); `first-change` at e₁ with the scan, the second and fifth edits in `further_changes` |
| `bisect_planted` | On the twelve-edit lineage: `frob design bisect --good v0 --bad v12 --predicate succeeds --task <step-up> --level 0.05 --key bp-1 --json` on `batch-cpu`; the same under `FROB_SCHEDULE_FUZZ=1` (`bp-4`) | The returned pair is (v6, v7); label `a-change`; the endpoint probe of v₁₂ and the interior probes v₆, v₉, v₇, each at level 0.05/5 (planned P = ⌈log₂ 12⌉ + 1 = 5, fixed before the first probe); the error statement; `provisional` on the probes; the fuzzed run gives the identical bracket and probe e-values |
| `merge` | Two sessions apply ten shared and five private edits each; absorb A into B and B into A in two stores; export; then a lineage merged with itself. The merge is a library operation with no verb in the registry, and the conformance crate has no command (ADR-GAUNT-01), so it runs through a subcommand of the studio's example target, added by this bead (DESIGN, the form N28c-06 fixes): `cargo run -p frob-conformance --example atelier_harness -- lineage.merge --into <store-b> --from <store-a> --json` and the reverse into a second fresh store, a thin parser over N28b-04's `Lineage::absorb` and `to_canonical_bytes` | Identical bytes and digests in both orders; 21 versions, 20 edges, 30 attestations; merging a lineage with itself changes nothing; `design.blame` works across namespaces; one namespace moved differently in two stores absorbs to the same `conflicted` head in both orders, an edit against it exits 7 and the resolving update clears it (N28b-04) |
| `migration` | A run recorded by the previous worker build; the test-only `migrate` edit; diff, blame, `frob sim replay` | Empty diff apart from the migration line; identical replay digests through the producer worker; the refusal with its build command when that worker is hidden (N28b-05) |
| `gate_query` | The gate register has no `frob` verb (ADR-GAUNT-01), so the step reads the bisect part of the GATE-ATEL-04 row of `registries/gates.toml` read-only, with the receipt file that N28b-03's battery (100 planted lineages, 20 non-monotone) wrote, and drives `frob evidence trace <claim_id> --json` (the `evidence.trace` row's form) on the claim the receipt cites; the battery itself runs for hours on `batch-cpu` and is not re-run here (it is N28b-03's `scripts/e2e/bisect_planted_lineages.sh`, recorded with `cargo run -p frob-conformance --example record_gate -- --gate GATE-ATEL-04 --receipt <hash>`) | At least 95 found and no wrong `first-change`; the receipt's counts, commit and frozen-instance manifest hash equal those of the receipt file; a receipt older than the commit of the bisect rules is reported stale and fails the step |

A stale-parent control runs inside `diff`: repeating e₃ with the old expected parent must exit 7 and change
nothing; repeating it with the same idempotency key must return the stored answer with `idempotent_replay:
true`.

## Acceptance criteria

- [ ] `scripts/e2e/lineage_queries.sh` exists, sources the shared helper, runs its steps against the real
      binary and exits 0 on a correct build and non-zero when any listed assertion fails. The M1 section
      passes at the first studio milestone and the whole script at the fourth.
- [ ] Each step asserts the values of the table, including exit codes and refusal codes.
- [ ] The script is idempotent and leaves nothing outside its temporary store and `target/e2e-logs/`.
- [ ] Planted failures are caught: with the bisect relabelling mutant (CX-313's plant,
      `frob-opt/bisect-last-edit-first-change`, N28b-02), the stale-support mutant and the strict-improvement
      merge mutant enabled one at a time (test-only features, each with `gauntlet-mutations`), the script fails
      in the step that owns the mechanism.
- [ ] The M4 section runs BD-343's `scripts/e2e/design_bisect.sh` as its stage `design_bisect` and fails when
      that stage fails; no step of this script repeats the stage's checks.
- [ ] The log has one line per command with the fields below and a final `summary` line; logs of two runs
      with one seed differ only in timestamps, wall times and costs.
- [ ] It exits non-zero under each planted regression of its self-test.

## Test plan

### Unit tests

The script is the test. A shell lint and a dry-run mode (`--list-steps`) are checked in continuous
integration so the script cannot rot unnoticed between milestones.

`scripts/e2e/tests/lineage_queries_selftest.sh`, one planted regression each: (a) blame returns the most
recent edit regardless of field (caught at `blame`); (b) diff emits unverified edits (caught at `diff`); (c)
bisect labels its result `first-change` by default (caught at `bisect`); (d) probes at level α instead of α
divided by the planned probe count (caught at the level assertion of `bisect_planted`); (e) merge keeps the
first arrival on equal fitness (caught at `merge`).

### End-to-end script and logging

`scripts/e2e/lineage_queries.sh` writes `target/e2e-logs/lineage_queries/<utc>.ndjson` and a human-readable
transcript beside it. Every line has `ts`, `script`, `bead` (the bead that owns the step's mechanism), `step`,
`event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time,
the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured values with
units and thresholds (probe count against 4 and 4 including the endpoint probe, α per probe against 0.05/4
and 0.05/5, version and edge
counts, found of 100 against 95, pairs per probe, episodes total), digests where state is compared (the
patched `DesignId` against the head; the two merged lineages; replay chunks), and on failure the first differing value and
the artifact paths needed to reproduce (the store directory is kept on failure). The final `summary` line
gives assertions passed and failed per step and the gates touched. No scene data is logged. Runtime target:
the M1 section under 30 s; the M4 section under 15 minutes on `batch-cpu` (TARGET), dominated by the bisect
probes of `bisect_planted`.

### Known answers and negative controls

- KA-702 / CX-313: the lineage's outcomes are pass, fail, pass, pass, pass, fail by construction; bisect
  returns an `a-change` at the last edit and no `first-change` without the scan.
- The three-edit lineage is hand-specified; the planted edit of the twelve-edit lineage is at position 7.
- The three mutants of the acceptance list and the five regressions of the self-test are the negative
  controls of the script itself.
- Determinism: the script is run twice in continuous integration and the two logs must agree on every digest
  and e-value; across worker counts (1 and 8) the same.

## Considerations

- The bisect step spends real episodes (four probes of a paired study, the endpoint probe included, on the
  referee or `batch-cpu`); the
  script prints the estimate first and uses the smallest budget at which the planted effects are decisive.
- Before M4 the script runs with `--section m1` (from M1) and `--section m1` plus `--section m3` (from M3);
  those are the regressions for diff, blame, the invalidation set and replay after migration.
- If a step's verb is not yet implemented the script reports exit code 5 from the binary as "not implemented"
  and fails; it never skips silently.
