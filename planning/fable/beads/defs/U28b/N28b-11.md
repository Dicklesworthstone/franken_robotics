## Background

GATE-ATEL-03 asks for a *pre-registered* A/B of agent surfaces with an anytime-valid verdict and an effect
size. Pre-registration is what separates an experiment from a demonstration: the arms, the briefs, the
statistic, the stopping rule and the exclusions are fixed and hashed before the first campaign, so that
nothing can be chosen after the outcomes are seen. The plan's guards against false progress apply in full: a
gate needs competing arms, a potency control it must catch, a clean case it must pass, a paired lower bound
and a fallback named in advance; and a rule that cannot return one of its verdicts at the planned sample size
is rejected before any data are collected. This bead writes that protocol and builds the machinery the run
needs but does not yet exist: the arms as enforceable capability profiles, the equalization of resources, the
reachability check of the decision rule, and the control. BD-374 executes it. Tier: Solid.

The comparison is BET-10's: the same agent with the full studio surface against the same agent with only
`sim run` and a scalar score, at equal compute and tokens. A third arm adds the one-call pipeline `solve.run`
and is read by the surface chapter's own gate; the plan insists there is one A/B, not two. The comparator on a
composed layer of incumbent tools belongs to the ten-fold test and is out of scope.

Rejected alternatives: restricting an arm by instruction ("please do not use other tools"), which an agent may
ignore and which cannot be audited (the restriction is enforced by the session token instead); giving the
minimal arm a deliberately poor prompt (the comparator must be the same agent, honestly equipped for its
surface); registering after a pilot on the sealed briefs (pilots run on development briefs only).

## Scope

In: the registration record and its freeze; the three capability profiles and the response filter of the
minimal arm; documentation given to each arm; resource caps; launch order; the reachability check; the power
statement; the planted-defect control's definition; the dry run on development briefs; refusal of deviations.

Out: the briefs and acceptance rule (N28b-10); the registered run, its analysis and gate record (BD-374);
`solve.run` and KILL-SOLVE (BD-372); the session recorder (ten-fold harness).

## Technical approach

**1. The registration record (`frob.registration/1`, canonical JSON; its BLAKE3 is written to the ledger and
the record cannot be edited afterwards).** Fields: the hypothesis and the gate; the arms with their profile
hashes; the agent model, version, sampling settings and the hash of each arm's system prompt and documents;
the sealed briefs consumed (by hash) and the campaign seeds; n briefs, c campaigns per brief per arm; the
deadline H per stratum; the resource caps; the launch-order key; the statistic (pair definition, span
[−c·H, H], the grid of ratios 1.0 to 3.0 in steps of 0.1, α = 0.05, pair consumption order); the stopping and
futility rules; the censoring and exclusion rules; the outcomes table with consequences; the analysis code's
hash; the power statement; the ceilings. A run whose manifest differs from the registration in any field is
refused by the harness, and the difference is printed.

**2. The arms as capability profiles (DESIGN: `registries/profiles/ab-*.toml`, applied by `session.open
--profile`).** A profile is a set of capability scopes and a response filter; the session token carries the
scopes, so a call outside them is refused by the surface with exit code 5 (outside the session token's
scopes), whatever the agent was told.

| Profile | Scopes | Tools listed | Response filter |
|---|---|---|---|
| `ab-minimal` (arm M) | `design:read`, `design:write`, `sim:run`, job and session base scopes, `qual:run` for submission | `design_new`, `design_show`, `design_edit`, `sim_run`, `eval_qualify`, and the three base tools | `sim.run` results are reduced to `{score}`; `next_actions`, ranked repairs, findings and telemetry handles are stripped; `ok`, `exit`, the refusal `code` and `message`, `job`, `cost` and `budget` are kept |
| `ab-full` (arm F) | Everything a design session normally has, except `solve:run` | The full surface in its task clusters of at most seven | None |
| `ab-solve` (arm S) | As `ab-full` plus `solve:run` | As arm F plus `solve_run` | None |

The scalar score of arm M is the brief task's scorecard total on development worlds, the same number arm F can
read among many others. Arm M therefore lacks nothing that "a simulator and a reward" would give, and has
nothing more.

**3. Documents.** Arm F and arm S receive the generated agent guide (`robot-docs`) and skill file. Arm M
receives a guide generated from the same registry restricted to its tools. All three receive the same brief
card. The hashes of all documents are in the registration.

**4. Equalization.** Per campaign and identical across arms: GPU-second and CPU-second budgets, the agent
token budget, the deadline, the device class, the warm state at start (kernels compiled; memo store holding
nothing of the brief's family), and zero human intervention. The session budget mechanism enforces compute;
the harness enforces tokens and stops a session that exhausts them (the clock keeps running to H). Campaigns
are launched in the order given by a keyed permutation of (brief, index, arm) so that no arm is systematically
later.

**5. The reachability check (run at registration, before sealing).** For the registered n, c, H and span,
compute the largest value the c = 1.5 e-process can reach under the most favourable admissible data (arm M
censored at H and arm F accepted at the smallest time the harness can record, in every pair). If that value
is below 1/α = 20 the rule cannot return PASS at the planned n and the registration is refused, with the
smallest n at which PASS becomes reachable. The same check is run for the futility verdict.

**6. The power statement.** From the dry run's times on development briefs (step 8), simulate the registered
rule under true ratios 1.0, 1.5, 2.0 and 3.0 with the observed dispersion, 10⁴ replications each, and record
the rejection frequency at c = 1.5. The registration states the power at ratio 2 (BET-10's aim). If it is
below 0.8 the registration says so in its first line; it is not refused for that, because the default compute
envelope may not allow more, and the result would then be reported as underpowered if it fails.

**7. Ceilings, stated before the run.** The ratio cannot exceed 1/q, with q the fraction of deadlines arm F
misses; nor H divided by arm F's smallest achievable time. For arm S against arm F, the ceiling is set by the
fraction of turns in recorded sessions that carry no decision: below 30% the ceiling is under 1.4-fold and the
one-call pipeline is not funded (the surface chapter's rule; restated because the third arm serves it).

**8. Dry run.** All three arms on the four development briefs, c = 2, with real agents: it sets H, feeds the
power statement, exercises exclusions, and checks that arm M's agents can complete a brief at all (an arm that
cannot act is not a comparator). An A/A run (arm F twice) checks that the harness has no order effect.

**9. The planted-defect control.** On the benchmark's four control briefs the outcome is the number of serial
agent turns from brief to an accepted repair, per arm. The registration fixes that it is reported beside the
main statistic and is not pooled into it.

## Acceptance criteria

- [ ] The registration record validates, is hashed into the ledger, and a run manifest that deviates in any
      field is refused with the differing field named.
- [ ] A session opened with `ab-minimal` lists exactly its tools, and a call to any other tool returns exit 5;
      its `sim.run` result contains `score` and none of the stripped fields.
- [ ] `ab-full` cannot call `solve.run` (exit 5); `ab-solve` can.
- [ ] Budgets, token caps, deadline and warm state are identical across arms for every brief, checked from
      the campaign records of the dry run.
- [ ] The reachability check refuses a registration with n too small and reports the first reachable n.
- [ ] The power at true ratio 2 is stated in the registration; the A/A dry run does not reject c = 1.0 beyond
      its nominal rate.
- [ ] Development and sealed briefs are disjoint, and the registration names only sealed briefs for the run.
- [ ] The outcomes table (PASS, FAIL with BET-10's fallback, `descriptive`) is part of the hashed record.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test surface_ab_protocol`:

- `registration_hash_changes_with_any_field`; `deviation_refused_names_field` (H changed from 10,800 s to
  9,000 s → refusal naming `deadline_s`).
- `profile_minimal_tool_list`: exactly eight tools (five verbs and three base tools).
- `profile_minimal_filters_response`: a `sim.run` envelope with findings and `next_actions` is reduced as
  specified; the refusal code and message survive.
- `profile_full_lacks_solve`; `profile_solve_has_solve`.
- `launch_order_is_keyed_permutation`: reproducible from the key and balanced (each arm first in one third of
  briefs to within one).
- `reachability_minimum_n`: with H = 10,800 s, smallest recordable time 60 s, α = 0.05 and the registered
  betting rule, the smallest n at which the c = 1.5 e-process can reach 20 is computed and asserted against a
  brute-force evaluation of the same rule.
- `power_simulation_reproducible`: the same seed gives the same rejection frequencies.

### End-to-end script and logging

`scripts/e2e/surface_ab_dryrun.sh` (shared with BD-374) includes the protocol steps: open one session per
profile over `frob-mcp`, list tools, attempt one withheld call per restricted arm (expect exit 5), run one
scripted campaign per arm on a development brief, write a dry-run registration and verify that a deliberately
altered manifest is refused. Logged per STD-E2E: commands, exit codes, wall time, evidence blocks, the tool
lists and their counts, the filtered and unfiltered field sets, budgets per arm, the registration hash, and on
failure the first field in which a manifest deviates.

### Known answers and negative controls

- Potency control (the plan's rule that a method gate must catch a planted effect): a scripted arm that
  submits the reference answer immediately must be detected as faster by the registered rule on the
  development briefs.
- Clean case: the A/A run.
- Negative controls: a profile enforced by prompt only (the scripted agent calls a withheld tool and
  succeeds; the test must fail); unequal token caps (caught by the equalization check); a registration
  written after the first campaign's clock event (refused by the ledger order check).
- Determinism: profiles, the launch order and the reachability result are D0.

## Considerations

- The surface is large even in clusters; arm F's agents can get lost. That is a possible result, recorded
  through turns and `session.focus` counts, and not something the protocol may engineer away by coaching.
- Provider-side nondeterminism and model updates are outside our control; the model version is pinned per
  brief and recorded per campaign, and a version change mid-run voids the affected pairs under the exclusion
  rule.
- Poisoned text in a brief or an imported file is not part of this experiment; the surface chapter's own
  gate carries that arm.
- If the owner does not approve class E2 compute, n stays at ten sealed briefs with c = 1 and the power
  statement will say what that can detect.
