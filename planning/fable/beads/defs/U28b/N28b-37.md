## Background

Memoization in the studio does not stop at the compiled model. One content-addressed graph covers everything
downstream of it: analyses, synthesized controllers, step plans, kernel binaries, compiled scenes, episodes,
and the comparisons and summaries derived from them. The `Memo` trait is declared in `frob-core`, wraps each
verb's executor in `frob-verbs`, and stores in `frob-chronicle`. Tier: Solid.

The whole value and the whole danger of a memo graph sit in its keys. A key with one input too many only
costs recomputation. A key with one input too few serves a stale result as if it were fresh, with every hash
consistent, and nothing downstream can tell. The plan's executed fixture shows it: an implementation whose
key omitted delivery time kept a stale promotion when a packet's delivery was delayed across a decision
instant (counterexample CX-315), and RISK-38 (an incomplete memo key serves a stale verdict) is rated high.
The store policy's first rule is therefore: **keys are derived, not written.** A key is generated from the
declared inputs of the node kind. Each kind has a property test that perturbs every declared input and
requires the key to change, and a live-dependency test that perturbs every field the computation reads and
requires the key to change or the output to stay the same. A missing input in a key is the failure this
policy exists to prevent.

Rejected alternatives: hand-written key functions per verb (the omission above is exactly what a hand-written
key allows); keying on the whole model identity (correct but useless: every edit would miss every node,
whereas the plan requires that an edit outside the fields an analysis reads recomputes nothing); time-based
invalidation (wall-clock time never enters an identity).

## Scope

In: the `Memo` trait; how a node record is filled; the registry of node kinds with their declared inputs and
serve classes; key derivation; the "model identity restricted to the fields read" (for an analysis, its
declared read set); the two tests every kind must ship, as a generated harness; the wrapper around verb

## Technical approach

**1. Node kinds (the registry; `registries/memo-kinds.toml` generates the Rust declarations).**

| Node kind | Key (declared inputs) | A hit is served within | Note |
|---|---|---|---|
| Subterm compile | Subterm content hash, compiler version, card versions | D0 | The incremental-compilation invariant of the design compiler |
| Analysis | The model identity restricted to the fields the analysis reads; analysis version; parameters | D0 | An edit outside those fields recomputes nothing |
| Controller synthesis | Model identity, task interface, synthesis version | D0 or same-backend D2 | |
| Step plan | Shape class: topology bucket, capacities, contact law, sensor layout | not applicable (a compiled artifact) | A parameter edit recompiles nothing; parameters are per-world data |
| Kernel binary | Kernel source hash, compiler, driver, device family | not applicable | The binary cache of the device layer |
| Scene compile | Scene identity, compiler version | D0 | |
| Episode | The full identity: model, scene, task, controller or policy, world address, tier, kernel versions, effort profile, device family | Same-backend D2; D1 where the device family holds it | Never across a D3 boundary |
| Comparison, summary | The identities of its inputs and the rule version | Derived | Recomputed from memoized episodes; it reaches the identical e-value |

The episode row is the minimum key. The episode kind is first served at M2 (BD-220), which completes its declared
inputs in this same registry row with the step-plan identity, the hardware fingerprint digest, the determinism
class attained for the kernel set and the stack-lock digest (thirteen inputs in all, the kind's version raised).
This bead registers the row with the inputs above so that the M1 live-dependency test already runs over the run
manifest; it does not define a second episode key.

**2. The trait and the record (DESIGN; names fix intent).**

```rust
pub trait Memo {
    type Inputs: DeclaredInputs;          // derive(DeclaredInputs) enumerates every field with its path
    type Output: Canonical;               // canonical bytes, so an output has a digest
    const KIND: MemoKind;                 // registry row: name, version, serve class
    fn compute(inputs: &Tracked<Self::Inputs>, cx: &Cx<'_>) -> Result<Self::Output, Refusal>;
}
```

The node record is N33b-15's `NodeRecord` (one struct in `frob-core`, shared by the memo graph and both store
implementations; there is no second node type). This bead
fills every field: `kind`; `key`, the bytes of the derived `MemoKey` (BLAKE3 of kind ‖ kind version ‖ canonical
bytes of the key inputs); `inputs`, the content hashes of the whole inputs in declared order; `reads`, every
field the computation actually read through the tracked view, with the hash of its value; `deps`, the keys of the
nodes whose outputs it consumed; `output`, the result's digest; `class`, the determinism class inside which a hit
is bit-identical; `device_family`; `achieved_error` where the kind records one; `cost`, the measured recompute
cost (CPU-seconds, GPU-seconds, bytes); and `stack_receipt`, the resolution receipt of the producing binary.

There is no API that accepts a key from a caller. `MemoKey` has no public constructor outside the derivation.

**3. Key derivation.** For a kind whose inputs are all "whole" (a scene identity, a compiler version), the key
is the hash of the declared inputs' canonical bytes. For a kind that reads *part* of a large input (an
analysis reading some fields of the model) the declared input is its read set, the field paths the analysis
declares in `reads()` (N28a-04's analysis contract): the restricted identity is the BLAKE3 of the sorted (path,
value hash) pairs of every declared field, taken from the model, and the key is the hash of (kind, kind version,
parameters, restricted identity, the card versions those fields name). Lookup is by that key alone. DESIGN,
the declared read set rather than the set actually read on one input (which would need a two-step lookup): the
plan generates keys from the declared inputs, the declared-input test of
item 4 is meaningful only for a declared set, and N28a-04 and BD-111 derive the analysis key the same way. The
computation still receives a `Tracked` view: a read outside the declared set panics in debug builds and fails
the contract test, and the fields actually read are recorded in the node's `reads`. A declared field that a
data-dependent computation did not read on some input stays in the key; that costs a recomputation, never a
stale hit. Module privacy makes an untracked read of the input a compile error.

**4. The two tests every kind ships (generated harness; a kind without both fails the contract check).**
- *Declared-input perturbation:* for each declared input field, change it to another admissible value and
  require the key to change. Run over at least 1,000 generated inputs per kind.
- *Live dependency:* for each field of the full input object (not only the declared or recorded ones), change
  it and require that either the key changes or the output's digest is unchanged. This is what catches a
  field the computation depends on but the key does not. For analyses it runs over every field of every
  template model; for episodes over every field of the run manifest, including clocks and delivery instants.
A third, cheap test guards the other direction for efficiency: for analyses, changing a field outside the
declared read set leaves the key unchanged (so an unrelated edit really recomputes nothing). This bead runs the
harness on test-only fixture kinds; BD-111 runs it over every analysis it wires and every template model.

**5. The wrapper.** `frob-verbs` wraps a verb's executor: derive the key; look up; on a hit that the store
policy allows to be served, return the stored output with `memo: { hit: true, key }` in the envelope's cost
block; otherwise compute under tracking, store the node with its reads, output digest, determinism class,
device family and measured cost, and link `deps`. `--no-memo` disables serving; nodes computed under it are still written, so the
flag can be used to refresh or to cross-check the store. The envelope always says whether a result was served or computed; a memo
hit is bit-identical to a recomputation inside its determinism class (INV-ATEL-08), so nothing else about
the answer differs.

**6. The store.** Nodes are stored through N33b-15's `Recompute` trait. FACT: `frankensim/crates/fs-recompute`
is a content-addressed Merkle graph with a skip oracle, pins that are never evicted and an independent checker.
It is consumed through N33b-15's airlock adapter if admission passes; otherwise N33b-15's local implementation
`LocalRecompute` in `frob-chronicle` stores the same `NodeRecord`, and it is the default until then
(OPEN-ATEL-3). Either way the trait, the derivation and the tests of this bead are ours and do not change.

**7. CX-315's plant.** This bead builds the plant `memo-key-no-delivery` of N28-CX's row CX-315 as the
`cfg(feature = "memo-key-no-delivery")` branch of `frob-core`, built one control per build (`--features
gauntlet-mutations,frob-core/memo-key-no-delivery`; a control seeded by N38b-05 has its feature named by its
plant, BD-025; the `controls.toml` row comes from N38b-05's seeding): the
episode kind's generated declaration drops the delivery instants from its declared inputs. On that build the
live-dependency test of the episode kind fails at `sensing.camera.delivery`, naming the field (the catch at
the level of the key, at M1). The same plant's observation on the four-state camera fixture (the promotion kept
at the fourth state, the recomputation count 0 where 1 is true) is caught through `result.revalidate` by
BD-292's KA-699 run at M3 and by BD-347.

**8. Layout and determinism.** `crates/frob-core/src/memo/{mod.rs, key.rs, tracked.rs}`; the derive in
`frob-core`'s companion macro crate; the wrapper in `crates/frob-verbs/src/memo.rs`; storage in
`frob-chronicle`. Key derivation is D0.

## Acceptance criteria

- [ ] The eight node kinds are registered with declared inputs and serve classes; the generated declarations
      match the registry (the generated-artifact check passes).
- [ ] No public function constructs a `MemoKey` from caller-supplied bytes (compile-fail test).
- [ ] Every kind ships the declared-input perturbation test and the live-dependency test; a kind missing
      either fails the contract check.
- [ ] CX-315's plant `memo-key-no-delivery`, built as `frob-core/memo-key-no-delivery`, fails the episode
      kind's live-dependency test naming `sensing.camera.delivery`; the test-only kind `EpisodeWithoutDelivery`
      fails the same test in the ordinary build.
- [ ] On the fixture analysis kinds, an edit to a field outside the declared read set is a hit and an edit to a
      declared field is a miss (the same check over every wired analysis and every template model is BD-111's).
- [ ] Data-dependent reads are sound: on a fixture analysis that declares fields A and B and reads B only when
      A is positive, changing B while A is negative is a miss whose output digest is unchanged, changing A is a
      miss, and a read of an undeclared field fails the call in a debug build.
- [ ] Every node written is N33b-15's `NodeRecord` with all its fields filled, stored through `Recompute`
      (`LocalRecompute` by default).
- [ ] The envelope reports `memo.hit` and the key for every wrapped verb; `--no-memo` computes.
- [ ] `scripts/e2e/memo_keys.sh` passes.
- [ ] `frob-core/CONTRACT.md` documents the trait, derivation, the two tests and the node kinds.

## Test plan

### Unit tests

`cargo test -p frob-core --test memo_keys` and `-p frob-verbs --test memo_wrapper`:

- `declared_input_perturbation_<kind>` for the eight kinds (1,000 generated inputs each).
- `live_dependency_fixture_analyses`: every field of the fixture model against the fixture analysis kinds (the
  run over every template and every wired analysis is BD-111's).
- `live_dependency_episode_manifest`: every manifest field, including the seven instants of every sensor
  channel.
- `stale_key_mutant_caught`: the test-only kind `EpisodeWithoutDelivery` fails `live_dependency` at
  `sensing.camera.delivery`; on the build with CX-315's plant the episode kind itself fails there.
- `restricted_identity_ignores_unread_fields`: a fixture kind declaring the mass roll-up's read set (masses,
  centres of mass, inertias, the tree) keeps its key when a controller gain changes.
- `data_dependent_reads`: as in the acceptance list.
- `declared_set_keys_analysis`: changing any declared field changes the key; `undeclared_read_fails_in_debug`.
- `no_public_key_constructor` (compile-fail).
- `key_stable_across_platforms`: pinned inputs give pinned keys on macOS and Linux, debug and release.
- `wrapper_reports_hit_and_key`; `no_memo_flag_computes`; `node_record_fields_filled` (kind, key, inputs,
  reads, deps, output, class, device family, achieved error, cost and stack receipt, through `LocalRecompute`).

### End-to-end script and logging

`scripts/e2e/memo_keys.sh`, this bead's own script, built only on its dependencies (the analyses are wired into
the memo graph by BD-111, and `scripts/e2e/memo_graph.sh` belongs to N28b-40; both depend on this bead). It
sources the shared helper of STD-E2E, works in the run's own empty state root `FROB_STATE` (which `e2e_init`
exports under `target/e2e-scratch/memo_keys/<run_id>/state/`; `frob` reads no `FROB_HOME`) and drives the wrapper
through the example program `cargo run -p frob-verbs --example memo_wrapper -- --model <fixture> --kind <fixture
kind> [--edit <path>=<value>] [--check live-dependency] [--no-memo] --json` (an example program, not a verb),
whose output is the envelope the wrapper builds. On a fixture model compiled by BD-063's compiler (labelled
`synthetic`): the mass-roll-up fixture kind twice (the second a hit, with `memo.hit: true` and the key); after
an edit to a controller gain (a hit: outside the declared set); after an edit to a link mass (a miss); the
data-dependent fixture kind with A negative and B changed (a miss, identical output digest); the same calls
with `--no-memo` (all computed, identical output digests, nodes still written); the node record read back
through `Recompute::get` with every field present; `--check live-dependency --kind episode` on the ordinary
build (passes) and on the build with CX-315's plant (fails, naming `sensing.camera.delivery`). Logged per
STD-E2E to `target/e2e-logs/memo_keys/<utc>.ndjson`: commands, exit codes, wall time, evidence blocks, per call
`memo.hit` and the key, output digests for the served and computed forms, the node record's fields, and on
failure the first call whose hit status or digest differs from the expectation; final `summary` line. The step
`keys` of `scripts/e2e/memo_graph.sh` (N28b-40) runs the same checks through `frob design check` on the
templates once BD-111 has wired the analyses.

### Known answers and negative controls

- CX-315 / KA-699: the four-state camera fixture; with the complete key the evaluations are 2, 0, 0, 1 and
  the recomputations 1, 0, 0, 1; the key without delivery time keeps a stale promotion when delivery is
  delayed to tick 3. The plant `memo-key-no-delivery` (item 7) reproduces the omission at the level of the key;
  the fixture's counts are BD-292's KA-699 row at M3.
- INV-ATEL-08 (a memo hit is bit-identical to a recomputation inside its determinism class): asserted in the
  script by comparing output digests with `--no-memo`; its production guard is shadow recomputation.
- Negative controls: a hand-written key path (rejected at compile time); a kind registered without its
  tests (rejected by the contract check).
- Metamorphic: reordering the fields of an input record, or renaming a design without changing a read field,
  leaves keys unchanged.
- Determinism: keys are identical twice, across worker counts and platforms.

## Considerations

- Tracking reads costs a little on first computation and nothing on hits; the cost is measured in the M1
  profile of `design check`.
- The live-dependency test is exhaustive over templates, not over all possible designs; a field that matters
  only for an archetype not yet shipped is caught when that archetype's template lands, because the test is
  generated over all templates.
- OPEN-ATEL-3 (owner: suite lead; blocks GATE-ATEL-12): whether `fs-recompute` passes admission. Default: the
  local node record.
- Step plans and kernel binaries are caches of compilation with their own owners; they are registered here so
  that one registry lists every memoized kind and one contract check covers their key tests.
