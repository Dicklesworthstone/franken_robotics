## Background

A memo graph that serves a wrong answer is worse than no memo graph, because it serves it instantly, with
consistent hashes, to every later verb. The studio's memo store therefore follows a written policy with a
loss model, a tripwire, a budget, and a rollback that is a flag. The plan fixes the policy's clauses; this
bead implements them as one module that every node kind goes through, so that no verb has its own idea of
when a cached result may be served. Tier: Solid.

The clauses, as the plan states them:

- *Hits are bit-identical or not served.* Results are placed by index and random streams are keyed by
  address, so a hit equals a recomputation bit for bit inside D0 and same-backend D2. Tolerance-level reuse
  is allowed only for analyses that record an achieved error, never for episodes.
- *Shadow recomputation.* One hit in 64 (DESIGN), chosen by key hash, is recomputed and compared. One digest
  mismatch stops serving that node kind and files a determinism violation.
- *Loss model.* States: valid hit, stale hit, miss. Actions: serve, recompute, shadow. A stale result served
  costs 100 units against the GPU-seconds of a needless recomputation (DESIGN ratio, recorded in the memo
  policy's contract).
- *Budget.* 64 GB by default (DESIGN). On exhaustion the store evicts and never blocks. Nodes in the
  evidence closure of a live claim are pinned.
- *Rollout and rollback.* Shadow, then D0 analyses, then D2 episodes. `--no-memo` disables serving; the
  store can be deleted at any time without losing a result that a claim cites, because cited evidence is
  pinned in Chronicle, not in the cache.
- *Baseline.* Full recomputation per verb with compile-only memoization.

FACTS about siblings the policy leans on: `fs-recompute::Store::can_skip` serves a node cached under a
looser requirement if it achieved enough (the tolerance-reuse pattern); its `StoreError::DeterminismViolation`
is the tripwire pattern; `frankensqlite/crates/fsqlite-pager/src/s3_fifo.rs` implements the three-queue
S3-FIFO eviction policy (a small admission queue, a main queue with bounded reinsertion, a ghost queue of
metadata, an adaptive small share between 5% and 30%), keyed on page numbers, so it is a pattern to follow
and an oracle to compare with, not code to instantiate over content hashes.

Rejected alternatives: serving within a tolerance for episodes (a comparison built on "nearly the same"
episodes is not the comparison that was planned, and its e-value would differ from a recomputation's);
recency-only eviction (a scan over many designs touches each key once and would flush the store); a blocking
store (a full cache must never stall a campaign).

## Technical approach

**1. The serve decision (numbered; evaluated on every candidate hit).**
1. Mode gate: the store's rollout mode must allow serving this kind (step 6).
2. Latch: the kind's stop latch must be clear.
3. Class gate: the node's determinism class and provenance must allow serving in the caller's context:

| Node's class | Served when |
|---|---|
| D0 (exact) | Always |
| D2 | Same backend and same device fingerprint as the caller's run profile |
| D1 | Same device family, where that family holds D1 for the kernels involved |
| D3 or D4 | Never (a result is never served across a D3 boundary; a D4 result is not memoized) |

4. Tolerance reuse (analyses only): a node that recorded an `achieved_error` may be served for a request
   whose required error is at least that achieved error (a node cached under a looser requirement is served
   if it achieved enough). Episodes, comparisons and controllers have no tolerance reuse.
5. Shadow selection (DESIGN; the one selector of the memo graph, implemented here in `shadow.rs` and called
   unchanged by BD-111's analysis wrapper, BD-220's episodes, N28b-41's digest classes and N17b-13's
   cross-design kinds). Each node has a durable hit ordinal n: the per-node hit counter that the ledger
   increments in the serve transaction, so it survives restarts and two processes never draw the same ordinal.
   Its phase is p = the low six bits of BLAKE3(kind ‖ kind version ‖ key). A hit is shadowed when
   (n + p) mod 64 = 0: the node is recomputed, the digests are compared, and the *recomputed* result is
   returned; otherwise the stored output is served. Consequences: every window of 64 consecutive hits of one
   node holds exactly one shadowed hit, so a stale node is found within 64 of its own hits however it is
   requested; among keys hit once each, a key's first hit (n = 0) is shadowed when p = 0, so one key in 64 is
   chosen by key hash, as the plan's clause says. Alternatives rejected, each with the case that breaks it: the
   key alone (low bits of the key's hash zero) leaves 63 of 64 nodes unshadowed however often they are served;
   one ordinal per *kind* with a phase from the kind gives one shadow per 64 hits of the kind but starves a
   node whose hits recur with a period sharing a factor with 64 (two keys of one kind requested alternately,
   as when an agent re-checks designs A and B in turn, put every hit of one key on even ordinals and every
   hit of the other on odd ones, so only one of the two is ever shadowed); and a fresh hash per hit (low bits
   of BLAKE3(key ‖ n) zero) has the right rate and no bound (a node goes 64 hits unshadowed with probability
   (63/64)⁶⁴ ≈ 0.365). For a batch planned in one go (BD-220), the planner reserves the ordinals of every node
   the batch will hit in one store transaction and assigns them to the batch's hits in (address, member)
   order, so the shadowed hits do not depend on the order in which workers finish.

**2. The stop latch.** On a shadow mismatch, in one ledger transaction: the kind's latch is set (no further
hit of that kind is served by any session from that commit on: "stops serving within one hit"); a
determinism-violation record is filed with the key, both digests, the two executions' trace identifiers and
device fingerprints; nodes of that kind written since the last clean shadow are marked suspect. The latch is a
ledger record and survives restarts. The same latch is set for the node kinds involved when the chunk publisher
finds different bytes for a committed chunk key (`FROB-REF-878`).

**The lift rule (DESIGN; the one re-enable rule of the memo graph).** A latched kind serves again only through
the explicit call `Memo::reenable(kind, explanation)`, which appends a `memo-reenable` ledger record. It is
accepted only when the explanation record names the violation it answers (by its record id), the cause and the
fix (for a key-schema defect, the new kind version, whose two key tests of N28b-37 pass; for a nondeterministic
computation, the changed code identity; for a cause outside the kind, such as a corrupted entry, the purge of the
offending entries), and carries a re-run of the mismatching node under the fixed code that equals the fresh
result byte for byte twice. A restart, a store deletion or a bare version bump does not lift it, and nothing lifts
it automatically (the loss model's consequence). The command-line surface of the call is not a registered verb
(OPEN, Atelier lead; fail-closed default: no surface, so a latched kind stays latched, which costs latency and
never correctness).

**3. The loss model (recorded in `frob-chronicle/CONTRACT.md` and in the policy record).** States: valid hit,
stale hit, miss. Actions: serve, recompute, shadow. Costs: a served stale result costs 100 units; a needless
recomputation costs its GPU-seconds (normalized so that one typical recomputation is 1 unit). Consequences
derived from it and stated in the contract: serving is rational only while the probability of staleness per
hit is below 1/100; the shadow rate of 1/64 detects a systematic defect in a kind (one that makes every
affected hit differ from its recomputation) within 64 such hits for certain when they repeat one node, and
within 300 such hits with probability about 0.99 ((63/64)³⁰⁰ ≈ 0.009) when they fall on distinct nodes; shadow
costs about 1/64 of the recomputation the store saves.
The ratio and the rate are DESIGN constants; changing either is a new policy version.

**4. Budget, admission, eviction, pins (the clause; its mechanism is N33c-18 and N33c-19).** The store has a
byte budget (default 64 GB; OPEN on the retention windows and budgets per machine has the same default).
Accounting is in bytes of stored outputs plus node records. On exhaustion the store evicts and never blocks: a
write that cannot be admitted is simply not cached, and the verb returns its computed result. Eviction follows
the S3-FIFO pattern; admission is weighted by recompute cost, because misses are not equally expensive (a cheap
entry may be refused admission in favour of keeping a costly one; that departure from the sibling's policy is
tested separately from the differential test against it). Fallback if the differential oracle fails:
least-recently-used with the same cost-weighted admission; never an unbounded store. Nodes in the evidence
closure of a live claim are pinned and are not eviction candidates; pinned bytes count against the budget and
are reported by `store.status`. The eviction state machine (N33c-18), byte accounting, the admission rule with
its θ and ghost path, pin handling and the LRU fallback (N33c-19) implement this clause and carry its tests;
this bead's serve path relies only on their interface, `admit(node) → Admitted | NotCached(reason)`, which never
waits. Until they land, the store this bead ships refuses admission once the budget is reached (it evicts
nothing and never blocks), so the bound and the never-block rule hold from the first commit.

**5. Deletion safety.** The cache directory can be deleted at any time. A result that a claim cites is not
lost, because evidence is pinned in Chronicle's content store (chunks, certificates, ledger rows), not in the
cache: after deletion, verbs recompute, and `evidence.trace` on every live claim still resolves.

**6. Rollout and rollback.** A store-wide mode in the configuration registry:

| Mode | Behaviour |
|---|---|
| `off` (the baseline) | Compile-only memoization; every verb recomputes |
| `shadow` | Every candidate hit is recomputed and compared; nothing is served; mismatch counts per kind are recorded |
| `analyses` | D0 analysis, compile and scene nodes are served; episodes are shadowed |
| `episodes` | D2 episodes are also served on the same backend and fingerprint |

Advancing a mode requires the previous mode's record: zero mismatches over at least 10⁴ shadowed hits per
kind being promoted (DESIGN threshold). The record is the release configuration's rollout record in the
configuration registry, accumulated from the per-kind shadow counters of stores running under the release
profile (counters from `test`-profile stores never count), not a property of one store, so a new or emptied store inherits the release's mode. Test
and end-to-end harnesses run temporary stores under the store profile `test`, which may set any mode
directly; every serve decision there carries `rollout: test-override`, and the release binary refuses that
profile. `--no-memo` on any verb disables serving for that call in any mode; setting the mode back is a
configuration change, not a code change.

**7. What is recorded.** Per call the envelope's cost block carries `memo: { hit, served, shadowed, key }`.
Per kind the ledger keeps counters (hits, served, shadowed, mismatches, admitted, refused admission,
evicted, pinned bytes). The reuse ledger's "exact reuse" column is computed from these counters and the
nodes' recorded costs.

**8. Layout and determinism.** `crates/frob-chronicle/src/memo/{policy.rs, shadow.rs, budget.rs, mode.rs}`.
Serve decisions are pure functions of the node record, the caller's profile, the mode and the latch state at
a ledger frontier; shadow selection is a function of the key and the node's hit ordinal, so the same hits
are shadowed on every machine that replays the same ledger.

## Acceptance criteria

- [ ] The class gate matches the table on every combination of node class and caller profile; no D3 or D4
      node is ever served.
- [ ] Tolerance reuse is available for analyses with a recorded achieved error and refused for every other
      kind.
- [ ] Shadow selection follows the stated rule: exactly one shadowed hit in every 64 consecutive hits of one
      node (also across store reopenings and concurrent processes), one key in 64 among first hits, and the
      same hits shadowed on every machine for the same ledger; a planted mismatch sets the latch, and no
      further hit of that kind is served afterwards (the next hit recomputes).
- [ ] A determinism-violation record with both digests is filed; only `Memo::reenable` with a complete
      explanation record lifts the latch; a restart, a store deletion and a bare version bump do not.
- [ ] At the byte budget a write that cannot be admitted returns the computed result uncached and never
      blocks (eviction, cost-weighted admission and pins are tested by N33c-18 and N33c-19).
- [ ] Deleting the cache directory loses no cited evidence: every live claim still resolves, and verbs
      recompute.
- [ ] Modes behave as tabled; advancing without the previous mode's shadow record is refused; `--no-memo`
      computes in every mode.
- [ ] The loss constants, shadow rate, budget and thresholds are in the contract; changing one bumps the
      policy version recorded on serve decisions.
- [ ] `scripts/e2e/memo_policy.sh` passes.

## Test plan

### Unit tests

`cargo test -p frob-chronicle --test memo_policy`:

- `class_gate_matrix`: 5 node classes × 4 caller profiles.
- `tolerance_reuse_analysis_only`: an analysis cached at achieved error 10⁻⁶ serves a request for 10⁻⁴ and
  not one for 10⁻⁸; an episode with any tolerance request is a miss.
- `shadow_rate`: over 2²⁰ generated keys hit once each, between 1/64 − 0.001 and 1/64 + 0.001 are selected
  (the binomial standard deviation is about 0.00012).
- `every_node_shadowed_periodically`: one key hit 6,400 times is shadowed exactly 100 times, once in every
  window of 64 consecutive hits. Mutants it must fail: the key-only selector (a key whose hash misses is
  shadowed 0 times); the per-kind ordinal (two keys of one kind requested alternately 6,400 times each: one of
  them is shadowed 0 times); the fresh hash per hit (some window of 64 holds no shadow).
- `shadow_ordinal_survives_restart`: 64 store reopenings with one hit of one node each give exactly one
  shadowed hit; two threads drawing 6,400 ordinals of one node concurrently get 6,400 distinct ordinals and
  exactly 100 shadowed hits.
- `batch_ordinals_in_address_order`: a batch of 300 hits (some nodes hit twice) planned once and served by 8
  workers finishing in random orders shadows the same hits in every run.
- `shadow_mismatch_latches_kind`: after the planted mismatch the very next candidate hit of that kind is
  recomputed; another kind is still served.
- `latch_set_by_chunk_conflict`.
- `reenable_lift_rule`: after a planted mismatch, a restart, a store deletion and a bare kind-version bump each
  leave the kind latched; `Memo::reenable` without an explanation record, or with one whose re-run still
  mismatches, is refused; with a complete record whose re-run equals the fresh result twice, the kind serves
  again and one `memo-reenable` record is in the ledger.
- `detection_probability`: (63/64)³⁰⁰ < 0.01.
- `budget_reached_not_cached_never_blocks`: writes at 100% of the budget return immediately with
  `NotCached(budget)` and the verb's computed result; byte accounting never exceeds the budget.
- `delete_cache_keeps_evidence`.
- `mode_table`; `advance_requires_shadow_record` (release profile: refused below 10⁴ clean shadowed hits
  per kind, accepted at 10⁴ with zero mismatches; test profile: accepted and every decision marked
  `test-override`; release binary: the test profile refused); `no_memo_flag`.
- `policy_version_on_decisions`.

### End-to-end script and logging

`scripts/e2e/memo_policy.sh`, this bead's own script, built only on its dependencies: the analyses' wiring
(BD-111) and the verb `store.status` that prints this bead's counters (BD-209, M2) both depend on this bead, so
the script drives the serve path through N28b-37's example program `memo_wrapper` on that bead's fixture kinds
and fixture model, and reads the per-kind ledger counters and sets the policy's settings with this bead's
example program `cargo run -p frob-chronicle --example memo_counters -- [--profile release|test] [--set-mode
<mode>] [--set-budget <bytes>] --json` (example programs, not verbs; `--set-mode` goes through the advance rule
of section 6 and prints the refusal, naming the missing shadow record, when the rule refuses; without a `--set-`
option it only prints the counters). It sources the shared helper of STD-E2E and works in the run's own empty
state root `FROB_STATE` (which `e2e_init` exports under `target/e2e-scratch/memo_policy/<run_id>/state/`; `frob`
reads no `FROB_HOME`). Steps:
1. Mode `shadow`: 64 calls of each fixture kind; counters served = 0, shadowed = hits, mismatches = 0.
2. Advancing to `analyses` under the release profile is refused (far fewer than 10⁴ shadowed hits).
3. `analyses` under the `test` store profile: served > 0, every decision marked `test-override`, and each node
   hit 64 times shadowed exactly once.
4. The planted nondeterministic fixture kind (its output depends on a counter; labelled `synthetic`) called
   until a shadow fires (at most 64 calls; the step fails if none fires); then the latch: the next call
   recomputes with `memo.served` false, the determinism-violation record holds both digests, another kind is
   still served, and a reopened store is still latched.
5. `--no-memo` computes in every mode.
6. A claim recorded before the deletion: a referee run `frob sim run g1 --tier referee --seconds 1 --seed 7
   --key mp-run --json`, then BD-095's test-support example `cargo run -p frob-chronicle --example graph_fixture
   -- --store "$FROB_STATE" --run <RunId>`, which records the fixture claim on that run's chunk range. The cache
   directory deleted: `frob evidence trace <claim> --json` (BD-095) still resolves that claim, and the next call
   recomputes.
7. With the byte budget set to the store's current size, the next write returns at once with `NotCached(budget)`
   and the computed result.
Logged per STD-E2E to `target/e2e-logs/memo_policy/<utc>.ndjson`: commands, exit codes, wall time, evidence
blocks, counters per kind, latch state, both digests of the mismatch, bytes used against the budget, and on
failure the first hit served after a latch; final `summary` line. The steps `policy` and `shadow` of
`scripts/e2e/memo_graph.sh` (N28b-40) later run the same checks through `frob design check`, and from M2 read
the counters with `frob store status`.

### Known answers and negative controls

- INV-ATEL-08 (a memo hit is bit-identical to a recomputation inside its determinism class): shadow
  recomputation is its production test; the planted nondeterministic analysis is the negative control it
  must catch.
- Interference rule with the decision cores (a hit is bit-identical to a recomputation, so no core can
  tell): a partly memoized comparison reaches the identical e-value; asserted in N28b-40 and by the
  composition bead.
- Negative controls: a store that serves a D2 episode on another fingerprint (the class gate test fails; the
  seed bead for episodes requires "an episode recorded on another fingerprint is not served"); a store that
  blocks at budget; a latch that only logs.
- Differential oracle (owned with the eviction gate): under a bijection from keys to page numbers the
  eviction sequence equals the sibling's on 10 recorded traces of at least 10⁵ accesses, and on the
  edit-loop trace the hit ratio is not below least-recently-used.
- Determinism: serve decisions identical twice and across platforms for the same ledger state.

## Considerations

- RISK-38 (an incomplete memo key serves a stale verdict; high; owner Atelier lead): keys are the first
  defence, this policy's shadow recomputation and latch the second, the revalidation gate the third.
- Where the reuse is, and is not: the comparison that follows a 2,048-world run of the previous version on
  the same scene reuses that version's episodes at the comparison's addresses; a controller-only edit reuses
  every model analysis; a mass or geometry edit reuses no rollout. The policy cannot change that; it only
  makes what reuse exists safe.
- Targets, unmeasured: `design check` after a one-parameter edit in 0.2 / 0.5 / 1.0 s at the 50th / 95th /
  99th percentile (TARGET). The policy's overhead (lookup, shadow) is part of that budget.
- Private-scene results inherit the scene's privacy class in the cache as in the evidence store; deleting a
  private scene purges its nodes.
