## Background

The memo graph promises two things that pull against each other: after an edit, recompute only what the edit
touched; and never return anything different from what a full recomputation would return. Proof obligation
PO-ATEL-07 states the second (incremental evaluation with the memo graph equals full recomputation) and says
how it is discharged: 10⁴ random edit sequences, and shadow recomputation in production. Gate GATE-ATEL-12
(known answer and performance) bundles it with the tripwire and the latency target: PO-ATEL-07 holds; a
shadow mismatch stops serving within one hit; `design check` after a one-parameter edit in 0.2 / 0.5 / 1.0 s
at the 50th / 95th / 99th percentile (TARGET). The gate has an analysis part at the first milestone and an
episode part at the second. This bead is the analysis part: the battery, the latency measurement and the
end-to-end script. The episode part is N28b-42. Tier: Solid.

Why random edit *sequences* and not single edits: staleness bugs live in histories. A key that is correct
after any one edit can still be wrong after "edit, edit back, edit something else", when an old node with a
matching key is served although an intermediate state changed something the key does not cover. The plan's
metamorphic relations name two members of this family: an edit followed by its inverse leads to zero
evaluations and the original answers; incremental equals full (mutation: an input missing from a key).

## Scope

In: the edit-sequence generator; the incremental-against-fresh comparison; the planted mutants; the latency
protocol and its record; `scripts/e2e/memo_graph.sh` with its M1 steps and the hooks for later steps; the M1
gate record.

Out: keys (N28b-37) and policy (N28b-38), which this bead tests; the memo graph's wiring in front of analyses
and the sibling's admission (BD-111); episodes and comparisons (N28b-42, N28b-39).

## Technical approach

**1. The edit-sequence generator (`frob-conformance::fixtures::edit_sequences(seed)`).** A sequence starts
from one of the shipped templates and applies between 1 and 20 typed edits drawn, with fixed weights, from
the whole edit vocabulary available at the milestone: parameter and lever moves; actuator and transmission
swaps; adding and removing a limb; moving a payload or a sensor mount; adding and removing a sensor; mirror
and radial constructors; shared-bus edits; renames and other display-only edits; locks and unlocks. With
probability 0.2 an edit is the inverse of an earlier edit in the sequence, and with probability 0.1 a
sequence revisits an earlier version exactly. Edits that the design language refuses are kept in the
sequence as refused steps (a refusal must also be identical in both lanes). The generator is a pure function
of its seed; the gate uses seeds 0 to 9,999.

**2. The comparison.** For each sequence two lanes run through the real `frob` binary's library entry
points:
- *incremental:* one persistent store under the `test` store profile (N28b-38), the memo mode set to
  `analyses`, `design.check` (all analyses marked
  for `check`, plus each registered analysis verb) after every step;
- *fresh:* a new empty store for every step, serving disabled.
After every step the two lanes' outputs are compared as canonical bytes: every finding, every ranked repair,
every evidence block field except cost and trace identifiers. Any difference fails the obligation and is
minimized (the sequence is shortened by delta debugging to a minimal failing sequence, which is stored as a
regression). Also recorded per step: analyses served and computed in the incremental lane, to check the
other direction (an edit-then-inverse step computes nothing; a rename computes nothing).

**3. Planted mutants (the battery must fail on each).**

| Mutant | Expected failure |
|---|---|
| One analysis's declared read set (`reads()`, the set its key is derived from, N28b-37) drops a field it reads (the actuator-envelope analysis without the gear ratio), in a release build where the tracked view's debug panic is off | A difference after the first gear-ratio edit |
| A node kind's version is not part of its key | A difference after the conformance fixture bumps that analysis's version mid-sequence |
| The tracked view is bypassed for one accessor (an untracked read) | A difference, or a compile error where privacy catches it; either counts |
| Hits are served across a changed card version | A difference after an actuator card is revised |

Each mutant is a per-control `<crate>/nc-<nnnn>` feature of the crate it changes (`frob-analyze` for the first,
`frob-core` for the second and third, `frob-chronicle` for the fourth), built one control per build as
`--features gauntlet-mutations,<crate>/nc-<nnnn>` and never in the umbrella feature (BD-025); its
`controls.toml` row comes from N38b-05's seeding.

**4. The tripwire clause.** With the conformance fixture's nondeterministic analysis registered (its output
depends on a counter), the store's shadow recomputation must detect the mismatch and set the kind's latch;
the test then asserts that the very next candidate hit of that kind is computed, not served ("stops serving
within one hit"), and that other kinds are unaffected.

**5. The latency protocol.** For each shipped template: warm the store (one full `design check`); then 1,000
one-parameter edits (a single lever moved by 1% within bounds, levers drawn round-robin), each followed by
`frob design check <design> --json` through the CLI, which at M1 runs the verb in process (the daemon `frobd`
arrives at M2 with N32a-14; each CLI process opens the persistent store, so the timing includes the store's
open); the wall time of each check is taken from the envelope's `cost.wall_ms` and cross-checked against the
script's own clock. Report the 50th, 95th and 99th percentiles per template and pooled, with the disclosure
block (hardware fingerprint, toolchain, execution mode `in-process`, store warm state, store mode). Thresholds
(TARGET): 0.2 s, 0.5 s, 1.0 s. The record also gives
the share of analyses served per check, since a latency met by serving nothing new would mean the edits did
not exercise the analyses.

**6. The script.** `scripts/e2e/memo_graph.sh`, steps at M1 (this bead's, built on BD-111's wiring, which the
mechanism beads' own scripts `memo_keys.sh` of N28b-37 and `memo_policy.sh` of N28b-38 cannot use):
- `keys` (the checks of N28b-37 on the templates): `frob design check quad-a --json` twice (the second a hit);
  `frob design edit quad-a rename … --expected-parent <id> --key mg-rename --json`, then check (a hit: the
  rename is outside every analysis's declared reads); `frob design edit quad-a set-param
  legs.*.knee.gear_ratio … --expected-parent <id> --key mg-gear --json`, then check (the actuator-envelope
  analysis misses, the symmetry analysis hits); the same checks with `--no-memo` (all computed, identical
  output digests).
- `policy` and `shadow` (the checks of N28b-38 through `frob design check` on the templates, with the
  per-kind counters read by N28b-38's example `memo_counters`, since `store.status` is BD-209's at M2): mode
  `shadow` (served 0, shadowed = hits); the refused advance under the release profile; `analyses` under the
  `test` profile (`test-override` on every decision); the planted nondeterministic analysis until a shadow
  fires, then the latch; the cache directory deleted with `frob evidence trace` still resolving a stored claim.
- `sequences` (a 200-sequence subset of the battery through the CLI) and `timing` (a 100-edit subset per
  template).
Steps added by later beads and skipped with an explicit "not yet available: exit 5" check until then:
`derived` (N28b-39), `digest` (N28b-41), `episodes` (N28b-42).

**7. The gate record (analysis part, M1).** The gate runs as `FROB_TEST_SEED=<seed> cargo test -p
frob-conformance --test <tier named by GATE-ATEL-12's record in registries/gates.toml> -- GATE-ATEL-12`
(there is no per-gate target; the mutants' rows run with `--features gauntlet-mutations,<crate>/nc-<nnnn>`, one
control per build), which writes the receipt: sequences run and equal (10,000 of 10,000); mutants caught (four
of four); the tripwire result; the three percentiles per template against their thresholds; commit, hardware
fingerprint, seed range. This bead is the recorder of the M1 part (N28c-25's declaration) and enters it from
that receipt with `cargo run -p frob-conformance --example record_gate -- --gate GATE-ATEL-12 --receipt <hash>`;
`scripts/e2e/memo_graph.sh` writes no gate record.

## Acceptance criteria

- [ ] PO-ATEL-07, analysis part: over seeds 0 to 9,999 the incremental and fresh lanes agree after every
      step of every sequence; the count is in the gate record.
- [ ] Each of the four mutants makes the battery fail, and each failure is minimized to a stored regression
      sequence.
- [ ] An edit followed by its inverse computes zero analyses and returns the original outputs; a rename
      computes zero analyses.
- [ ] A shadow mismatch stops serving within one hit on the planted nondeterministic analysis.
- [ ] `design check` after a one-parameter edit: 50th, 95th and 99th percentiles are measured over at least
      1,000 edits per template and recorded against 0.2 s, 0.5 s and 1.0 s with the disclosure block.
- [ ] GATE-ATEL-12's analysis part is recorded with measured values (not the targets), by this bead with
      `record_gate` from the receipt of the tier-target run; no script writes the record.

      land.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test memo_equivalence`:

- `generator_seed_deterministic`; `generator_covers_vocabulary` (over 1,000 seeds every edit kind appears,
  inverses appear in about a fifth of steps).
- `incremental_equals_full_smoke`: seeds 0 to 199 in the default test run; the full 10⁴ under the gate
  profile.
- `edit_inverse_zero_evaluations`: 100 sequences of the form (e, e⁻¹).
- `refused_edit_identical_in_both_lanes`.
- `mutant_missing_read_field_caught`; `mutant_version_not_in_key_caught`; `mutant_untracked_read_caught`;
  `mutant_cross_card_version_caught`.
- `failing_sequence_minimized`: a 17-step failing sequence from the first mutant reduces to at most 2 steps.
- `tripwire_stops_within_one_hit`.
- `percentile_computation`: on a fixed list of 1,000 synthetic durations the 50th, 95th and 99th percentiles
  equal hand-computed values.

### End-to-end script and logging

`scripts/e2e/memo_graph.sh` sources the shared helper of STD-E2E, points `FROB_HOME` at an empty scratch store,
fixes the generator seed at 17, and runs its steps against the real `frob` binary in process (there is no
daemon at M1). Log `target/e2e-logs/memo_graph/<utc>.ndjson` with a
transcript: per command `ts`, `script`, `bead` (the bead owning the step), `step`, `event`, the command line,
exit code, wall time, the envelope's `evidence` block, `memo.hit`, `memo.served`, `memo.shadowed` and the
key; per sequence the seed, the step count and the first differing output if any, with both digests; the
percentiles with units and thresholds (0.2, 0.5, 1.0 s) and the disclosure block; the latch state after the
planted mismatch; and on failure the minimized sequence and the store path to reproduce it. Final `summary` line naming GATE-ATEL-12 (analysis
part).

### Known answers and negative controls

- Metamorphic relations MR-10 (an edit and its inverse: zero evaluations, original answers) and MR-12
  (incremental equals full; mutation: an input missing from a key).
- INV-ATEL-08 (a memo hit is bit-identical to a recomputation inside its determinism class): every compared
  step is an instance.
- The four mutants and the nondeterministic analysis are the negative controls.
- The latency numbers are TARGETs, not known answers; the record holds what was measured.
- Determinism lanes: the battery twice on one machine; debug and release; macOS and Linux hosts (analyses
  are D0, so outputs must be byte-identical across all of them).

## Considerations

- 10⁴ sequences of up to 20 steps with a fresh lane per step is about 10⁵ full checks; at the 2 s target for
  a full `design check` that is two to three CPU-days single-threaded, so the gate profile runs lanes in
  parallel across cores and the default test profile runs 200 seeds.
- A latency miss at M1 is a finding, not a blocker for the equality clause; the gate record keeps the two
  clauses separate so that the correctness result is not hidden by a performance one.
- The battery covers the templates and the edit vocabulary of its milestone; it is regenerated when
  archetypes or edit kinds are added, with the same seeds.
- RISK-38 names the failure this battery hunts; the stored minimized regressions are the long-term asset.
