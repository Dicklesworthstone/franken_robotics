## Background

Atelier is the design studio of FrankenRobotics: the loop in which a robot design is checked, given a controller,
simulated, explained, edited and compared, and every rule that decides how evaluation effort is spent inside that
loop. Eleven decisions recur across the studio, and each one moves compute or changes what is reported as
established: promote a fast-tier result or not; which designs advance up the evaluation ladder; how wide a survivor
margin is; certify or refute a rare-failure bound; which experiment to buy next; which cause ranks first after a
failure; whether a simulated result may carry a reality band; which solver effort profile a run uses; which job
runs when; which scenes form a battery; whether a kernel rewrite is accepted. They are named DC-01 to DC-11
("decision cores"). ADR-ATEL-11 fixes the prefix DC: the letter D already names determinism classes D0 to D4 and
doctrine rules, and a second meaning would make "D2" ambiguous in exactly the sentences where both appear.

This bead builds the contract that every one of the eleven obeys. It is the piece other subsystems wait for: the
promotion rule (DC-01), the rare-failure policy (DC-04), the attribution model (DC-06), the reality band (DC-07),
the daemon's dispatcher (DC-09) and the battery selector (DC-10) each write a policy record against this contract.

Decisions that govern the design:

- ADR-ATEL-06: decision rules are compiled to tables. Every adaptive decision in the studio is compiled ahead of
  time into an integer guard table, an automaton or a monitor with a version, stored under `registries/cores/`,
  regenerated in continuous integration and diffed. The runtime evaluates tables. No decision reads the wall clock,
  device load or arrival order. Reason: replay, audit, and a rollback that is a configuration flag. Rejected:
  floating-point evidence evaluated at run time (not reproducible bit for bit, not auditable without the engine);
  rules written inline in each subsystem (no common fallback, no common record, no way to list what decided a
  verdict).
- ADR-ATEL-09 (the controller gate): no adaptive controller is enabled by default without a replay scenario,
  evidence records, a calibration report and a demonstrated fallback. Adoption is always shadow (report both rules,
  act on the old), then canary, then default; the incumbent in each shadow run is the plan's own reference path.
- ADR-ATEL-10 (two planes): kernels, step plans and physics never depend on the dispatcher, the memo policy or any
  estimator. The decision plane reads results and writes requests; it cannot change what a world computes.
- ADR-ATEL-03: one asymmetry governs every rule: reporting an artifact-dependent result as established, or
  eliminating the best design, costs far more than a wasted higher-rung episode. Every fallback is therefore a
  fixed, conservative rule that can only cost compute.

Status of the numbers: nothing about the cores is measured. Failure signatures are predicted, substituted numbers
are illustrative unless marked TARGET, every core ships in shadow behind its baseline and is re-examined against
the first throughput profile at milestone M2. Tier: Solid [S] for the contract itself.

## Scope

In: the record schema `frob.core/1`, the artifact schema `frob.core-table/1`, the Rust types, the loader, the
validation rules wired into the existing checks, the family and plane taxonomy, the three conventions.
Out: the compiler that generates tables (N28c-02); evidence records and adoption stages (N28c-03); the verb
`cores.show` (N28c-04); the contents of individual records (BD-309 for DC-01, DC-09, DC-10; BD-349 for the other
eight); the composition rules between cores (N28c-06, BD-350); the register of rejected methods (N28c-07).

## Technical approach

**1. The record.** One file per core, `registries/cores/dc-NN.toml`, schema `frob.core/1` (DESIGN sketch):

```toml
schema       = "frob.core/1"
id           = "dc-01"
decision     = "Promote a fast-tier result, reject it as tier-sensitive, or buy another pair"
owner_crate  = "frob-opt"                       # the crate whose code takes the action
governed     = ["eval.promote"]                 # verbs whose behaviour this core decides
timescale    = "per-episode-batch"              # one of the eleven ordered timescales (N28c-06)
plane        = "evidence"                       # evidence | failure | platform
family       = "sequential-evidence"            # one of eight, or "fixed-table"
tier         = "S"                              # S, or F for a Frontier core (then feature-gated, off by default)
policy       = { name = "atelier.dc01.promote", version = 3 }      # the DecisionPolicyId
status       = "shadow"                         # shadow | canary | default | fallback-only
[[artifact]]                                    # one per compiled artifact
kind = "guard-table"                            # guard-table | automaton | monitor | schedule | rule-table
schema = "frob.core-table/1"
path = "registries/cores/tables/dc-01/default.json"
version = 3
hash = "b3:…"
generator = "frob_opt::promote::table::generate"
[loss]
states  = ["faithful", "sensitive"]
actions = ["promote", "reject", "buy-pair"]
constants = { c = "2", C_fp = "2000", C_fn = "…", pi = "ledger:share-sensitive" }   # exact decimals as strings
obligations = ["PO-ATEL-01"]
[fallback]
rule = "fixed 30 pairs; promote on at most 2 exceedances"
triggers = ["missing-ledger-stratum", "identity-mismatch", "null-self-test-failed"]
[budget]
mode = "32 pairs per result; on exhaustion the result stays provisional"
[replay]
scenario = "conformance/cores/dc-01/replay.toml"      # a recorded decision sequence the core must reproduce
[calibration]
report = "conformance/cores/dc-01/calibration.json"   # null error rates, with the run that produced them
[demo]
manifest = "demos/dc-01/demo.yaml"                    # commands under 60 s, checksums, claim_ids supported
```

Field rules: `decision`, `owner_crate`, `timescale`, `family`, `loss`, `obligations`, `fallback` (rule and at least
one trigger), `budget`, `status`, `replay`, `calibration` and `demo` are all mandatory; a record missing one fails
to load. `obligations` lists proof-obligation identifiers that must exist in the obligations registry.
`loss.constants` holds every cost constant the thresholds are derived from. Parameters of fallbacks, triggers and
budgets (30 pairs, a quantum of 5 s, a 3% gain and the like) are DESIGN defaults recorded in the record.

**2. The compiled artifact, `frob.core-table/1`.** Canonical JSON (sorted keys, no insignificant whitespace,
integers above 2⁵³ and all rationals as strings), content-hashed with BLAKE3:

```json
{ "schema": "frob.core-table/1", "core": "dc-01", "kind": "guard-table",
  "policy": { "name": "atelier.dc01.promote", "version": 3 },
  "parameters": { "p0": "1/20", "p1": "3/10", "alpha_plus": "1/100", "alpha_minus": "1/20", "budget": 32 },
  "bound_to": { "stratum_key": "…", "envelope_id": "b3:…", "model_class": "…", "kernel_versions": "…",
                "effort_profile": "…", "battery_version": "…", "address_schedule_hash": "b3:…" },
  "generator": { "name": "frob_opt::promote::table::generate", "version": 3 },
  "rows": [ { "k": 0, "promote_at_n": 16, "reject_through_n": null }, … ] }
```

`bound_to` holds the identities the table was built under; a core whose inputs carry a different identity may not
use the table (trigger `identity-mismatch`, and INV-ATEL-05: evidence and calibration are never pooled across model
identities). Row shapes are per kind and per core; every cell is an integer, a rational string or an enumerated
action. No floating-point number appears in a table.

**3. Types (DESIGN, in `frob-opt::cores`; identifiers shared with other crates live in `frob-core`).**

```rust
pub struct CoreId(u8);                                   // 1..=11
pub enum Plane { Evidence, Failure, Platform }
pub enum Family { SequentialEvidence, ConformalRiskControl, ValueOfInformation,      // evidence
                  RareEventSimulation, CounterfactualForks, SubmodularCoverage,      // failure
                  Queueing, CertifiedRewrites,                                       // platform
                  FixedTable }                                                       // halving: a table, not a family
pub enum Adoption { Shadow, Canary, Default, FallbackOnly }
pub struct CoreRecord { id: CoreId, decision: String, owner_crate: CrateName, governed: Vec<VerbName>,
    timescale: Timescale, plane: Plane, family: Family, tier: Tier, policy: DecisionPolicyId,
    status: Adoption, artifacts: Vec<ArtifactRef>, loss: LossModel, obligations: Vec<ObligationId>,
    fallback: Fallback, budget: BudgetedMode, replay: PathBuf, calibration: PathBuf, demo: PathBuf }
pub struct CoreTable { header: TableHeader, rows: Vec<Row>, hash: Blake3 }
pub trait DecisionCore { type State; type Action;
    fn decide(&self, table: &CoreTable, state: &Self::State) -> Self::Action;        // pure; reads no clock
    fn fallback(&self, state: &Self::State) -> Self::Action;                          // deterministic
    fn triggers(&self, state: &Self::State) -> Vec<Trigger>; }
```

`DecisionPolicyId { name: DottedName, version: u32 }` is the artifact-graph identifier of a decision rule (it names
a rule, not a control policy; a control policy is identified by content hash elsewhere).

**4. Taxonomy fixed by the contract.** Eight families in three planes of at most three: evidence (sequential tests;
conformal prediction and risk control; value of information), failure (rare-event simulation; counterfactual
forks; submodular coverage), platform (queueing; certified rewrites). Successive halving is a fixed table, not a
family. The loader refuses a ninth family.

| Core | Decision | Family | Owner | Timescale | Tier |
|---|---|---|---|---|---|
| DC-01 | Promote, reject as tier-sensitive, or buy another pair | Sequential evidence | `frob-opt` (`eval.promote`) | Per episode batch | S |
| DC-02 | Which designs advance at a rung transition | Fixed halving table; conformal survivors; value of information for finalists | `frob-opt` | Per rung transition | S table, F adaptive |
| DC-03 | Survivor margin per rung pair and stratum; the mode of the rung | Split conformal prediction with an audit lane | `frob-opt` | Per generation | F |
| DC-04 | Certify, refute or stop on a failure-rate bound | Rare-event simulation | `frob-nemesis` | Per finalist | S bound, F splitting |
| DC-05 | Which experiment to buy next, or stop | Bayesian value of information | `frob-opt` (`experiment.suggest`) | Per experiment | F |
| DC-06 | Which cause and which repair edit rank first after a failure | Counterfactual forks with a placebo | `frob-autopsy` | Per failure cluster | S |
| DC-07 | Whether a simulated result may carry a reality band, and when the band is void | Conformal band with an exchangeability alarm | `frob-ground` | Per real batch | F |
| DC-08 | Which solver effort profile a run uses | Risk-controlled profiles | `frob-dyn` | At ledger refresh | F |
| DC-09 | Which job runs when on a device | Queueing with size classes and preempt-resume | `frobd` | Per quantum | S |
| DC-10 | Which scenes form a battery | Submodular coverage | `frob-arena` | Per battery revision | S |
| DC-11 | Whether a kernel rewrite is accepted | Certified rewrites | `frob-kir`, `derive/frob-derive` | At build | S exact class, F real class |

Where a core governs a mechanism another subsystem owns, the record fixes the decision rule (table, loss model,
obligations, fallback) and the owning subsystem fixes the mechanism.

**5. The three conventions, enforced by the loader and the checks.**
1. Changing any recorded parameter is a new version of the decision policy: `policy.version` must increase whenever
   the canonical bytes of the record's `loss`, `fallback`, `budget` or any artifact change (checked against the
   previous committed record).
2. For a Frontier core the fallback is also its kill fallback: if the core's calibration fails its gate after one
   repair cycle, `status` is set to `fallback-only` and stays there; the registry says so.
3. A core's pilot is its shadow run: a record with `status = "shadow"` acts on nothing (N28c-03).

**6. Validation, inside the existing six checks (no seventh check is added).**
- `xtask check-contracts`: every record parses; all mandatory fields present; `owner_crate` exists in the crate map;
  every `governed` verb exists in `registries/verbs.toml`; every obligation and refusal identifier exists in its
  registry; a core of tier F names a `frontier-*` feature of its owner crate that is off by default; the demo
  manifest's `claim_id`s exist in `registries/gates.toml`; `timescale` is one of the eleven; version monotonicity
  (convention 1).
- `xtask check-generated`: every artifact regenerates from its generator and compares byte for byte with the
  committed file and with the recorded hash (N28c-02).
- Load time (in the binary): a table that is missing, stale against its record (hash or version differs) or not the
  registry version is refused with `FROB-REF-871`; the core's fallback is in force meanwhile.

**7. Determinism and evidence.** Loading and validation are class D0 (exact). The contract produces no claim by
itself; a decision made under a core is recorded as evidence by N28c-03.

## Acceptance criteria

- [ ] `registries/cores/` holds a schema file for `frob.core/1` and `frob.core-table/1`, and the loader in
      `frob-opt::cores` reads a record and its tables into `CoreRecord` and `CoreTable`.
- [ ] A record missing any mandatory field (each of the twelve tested in turn) fails to load with the field named.
- [ ] `xtask check-contracts` fails on: an unknown verb in `governed`; an unknown obligation identifier; a Frontier
      core whose feature is on by default; a changed `fallback` with an unchanged `policy.version`; a ninth family.
- [ ] A table whose bytes differ from the recorded hash is refused at load with `FROB-REF-871`, exit 3, and the
      refusal carries the repair "regenerate; the fallback is in force meanwhile".
- [ ] Canonical form: serializing a loaded table reproduces the committed bytes (round trip), and the same table
      built on the Mac and on the Linux host hashes identically.
- [ ] A table containing a JSON floating-point literal is rejected by the reader.
- [ ] `CONTRACT.md` of `frob-opt` has the ten sections (purpose, inputs, outputs, invariants, refusals, determinism
      class, evidence class of outputs, validity domain, oracles, known gaps) and documents the two schemas.
- [ ] The eleven-row table above is generated from the records by `check-generated` into the crate documentation
      once all records exist; until then the generator lists the cores that have no record as `not registered`.

## Test plan

### Unit tests

`crates/frob-opt/tests/core_contract.rs`:
- `record_roundtrip`: parse the DC-01 fixture record, serialize, compare bytes.
- `missing_field_names_field`: twelve mutated records, each without one mandatory field; the error names it.
- `ninth_family_refused`: `family = "bandit"` fails to load.
- `version_must_increase`: previous record with fallback "30 pairs", new record with "25 pairs" and the same
  version: rejected; with version + 1: accepted.
- `table_no_floats`: a table with `"p0": 0.05` (a JSON number) is rejected; `"p0": "1/20"` is accepted.
- `stale_table_is_871`: flip one row; load returns `FROB-REF-871` with `retry: after-change`.
- `identity_mismatch_trigger`: a table bound to kernel version A, state carrying kernel version B: `triggers()`
  returns `identity-mismatch` and `decide` is not called.
- `frontier_feature_off_by_default`: a synthetic tier-F record whose feature is in the default feature set fails
  the contract check.
- `taxonomy_counts`: three planes, at most three families each, eight families in total plus `FixedTable`.

### End-to-end script and logging

Exercised by `scripts/e2e/decision_cores_m3.sh` (N28c-05), which runs `frob cores show dc-01 --json` and the
regeneration check. For this bead the script logs, through the shared STD-E2E helper, `assert` lines for: record
loaded, table hash equals recorded hash, schema names, and a `refusal` line for the planted stale table
(`FROB-REF-871`, exit 3) with the first differing byte offset.

### Known answers and negative controls

- Known answer: the DC-01 table at p₀ = 1/20, p₁ = 3/10, α⁺ = 1/100 has `promote_at_n` = 16 for k = 0 and 22 for
  k = 1 (KA-695); the fixture table used by these tests carries those rows.
- Negative controls (registered): a hand-edited table row; a record whose fallback changed without a version
  bump; a Frontier core enabled by default. Each must fail its check.
- Determinism lanes: twice on one machine; debug and release; the Mac and the Linux host (class D0: identical
  bytes).

## Considerations

- The contract check must not grow into a policy engine: it validates records against registries and regenerated
  bytes, and holds no decision logic (the workspace rule that `xtask` has exactly six checks and runs no physics).
- OPEN-ATEL-1 (owner: Atelier lead): the loss constants of DC-01 and the exchange rate of DC-05 are not decided;
  until they are, the affected records carry the illustrative constants, `status` stays `shadow` and the fixed
  fallbacks are in force (N28c-26).
- Layering: `frob-opt` is a layer-4 crate. Records for cores owned by higher crates (`frob-nemesis`,
  `frob-autopsy`, `frob-ground`) and by lower ones (`frob-dyn`, `frob-kir`) are data files; lower crates do not
  depend on `frob-opt`. A lower crate that evaluates a table (the effort profile of DC-08, the rewrite rules of
  DC-11) reads the artifact through types in `frob-core`, so `CoreTable` and `DecisionPolicyId` are defined there
  and re-exported.
- A record is small; the risk is drift between a record and the code that claims to implement it. The replay
  scenario (N28c-03) is the guard: the core must reproduce a recorded decision sequence from the table alone.
