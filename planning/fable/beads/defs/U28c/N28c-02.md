## Background

Every adaptive decision in the studio is compiled ahead of time into a small artifact (an integer guard table, an
automaton, a monitor, a schedule or a closed rule table) that the runtime only looks up (ADR-ATEL-06). The reason
is replay, audit, and a rollback that is a configuration flag: a decision that depends on floating-point evidence
computed at run time, on the wall clock or on arrival order cannot be reproduced, so a verdict that rests on it
cannot be traced to the exact rule that produced it. `frob-opt` holds "the compiler for the decision-core tables":
the common machinery that turns a core's declared parameters into its artifacts, hashes them, and proves in
continuous integration that the committed artifact is what the generator produces.

The first clause of gate GATE-ATEL-13 is measured here: "each decision core: its table regenerates
bit-identically". The refusal `FROB-REF-871` is defined here: a decision-core table that is missing, stale against
its contract, or not the registry version; repair: regenerate, and the fallback is in force meanwhile.

Rejected alternatives: generating tables at program start (start-up cost, and a silent change when a dependency's
arithmetic changes); checking tables into the repository without regeneration (a hand edit would go unnoticed);
storing floating-point thresholds (different bytes on different hosts). Tier: Solid [S].

## Scope

In: the generator registry and trait; exact arithmetic rules; canonical serialization and hashing; the
`check-generated` hook; the load-time staleness check and `FROB-REF-871`; the null self-test hook that a generator
may register; the diff report.
Out: the record schema (N28c-01); each core's own generator mathematics (DC-01 with the promotion rule; DC-09 with
the daemon; DC-10 with the battery selector; the other eight under BD-349); evidence records (N28c-03).

## Technical approach

Module `crates/frob-opt/src/cores/compile.rs`.

1. **Generator trait (DESIGN).**
   ```rust
   pub trait TableGenerator {
       fn core(&self) -> CoreId;
       fn name(&self) -> &'static str;             // matches `generator` in the record
       fn version(&self) -> u32;
       /// Pure and total: the same parameters give the same bytes on every host, in debug and release.
       fn generate(&self, params: &Parameters, bound_to: &Identities) -> Result<CoreTable, GenerateError>;
       /// Optional exact check run at generation and at load (for example a null error-rate bound).
       fn self_test(&self, table: &CoreTable) -> Result<(), SelfTestFailure> { Ok(()) }
   }
   ```
   Generators register in a static list. A generator owned by a crate above `frob-opt` in the layering (for
   example the rare-failure policy) registers through the same trait from its own crate; `frob-opt` never depends
   upward. A generator owned by a crate below `frob-opt` implements the trait where it lives, with the trait
   itself defined in `frob-core`.
2. **Exact arithmetic only.** Parameters are integers or rationals written as strings ("1/20"). Generators compute
   with arbitrary-precision integers and rationals. Where a rule is defined by logarithms (for example
   ln E⁺ = (n − k)·ln((1 − p₀)/(1 − p₁)) + k·ln(p₀/p₁) ≥ ln(1/α)), the generator uses the equivalent integer
   inequality (19^(n−k) ≥ 100·14^(n−k)·6^k at the default parameters), never a floating-point logarithm. A lint in
   the module forbids `f32` and `f64` in generator code; a quantity that is genuinely real-valued at run time (a
   conformal margin read from a ledger, a posterior variance) is not a table cell but a ledger value the table
   indexes, and the table stores the integer index rule (for the conformal margin, the rank ⌈(n + 1)(1 − α)⌉).
3. **Canonical bytes and hash.** `CoreTable::to_canonical_json()` writes sorted keys, no insignificant whitespace,
   integers as JSON integers up to 2⁵³ and as strings above, rationals as reduced "p/q" strings. The hash is
   BLAKE3 over those bytes. Wall-clock time, host name and trace identifiers never enter the bytes.
4. **Regeneration in CI.** `xtask check-generated` calls `frob_opt::cores::compile::regenerate_all()`: for each
   record, for each artifact, call the named generator with the recorded parameters and identities, compare the
   bytes with the committed file and the hash with the record. Any difference fails the check and prints a
   row-level diff: the first differing row with both values, the count of differing rows, and whether the
   difference is in the header (parameters, identities, generator version) or the body.
5. **Load-time check.** `CoreTable::load(record, path)` recomputes the hash and compares header fields with the
   record: wrong hash, wrong version, wrong core, missing file, or a `bound_to` identity that the caller's context
   does not match → `FROB-REF-871` (exit 3; `retry: after-change`; repairs ranked: 1. regenerate with
   `cargo xtask check-generated --write`; 2. continue on the fallback, which is already in force). The caller
   receives `CoreState::FallbackInForce { reason }` and takes the core's deterministic fallback action; it never
   proceeds with a stale table. Surface rule: a governed verb called normally completes on the fallback and
   carries the code in the envelope's `warnings` and in its decision record; a request that pins the rule
   (`--require-rule table`, used by canary audits and by replay scenarios) is refused outright with
   `FROB-REF-871` and exit 3, because the pinned rule cannot be evaluated.
6. **Self-test at generation and at load.** If the generator registers a self-test (DC-01 registers the exact
   dynamic-programming bound on wrong promotion and wrong rejection inside the budget), a failure at generation
   fails CI; a failure at load raises the trigger `null-self-test-failed` and puts the fallback in force.
7. **Per-stratum tables.** A core may have one table per ledger stratum. The arithmetic is shared; the header binds
   each to its stratum's identities. The compiler stores them under
   `registries/cores/tables/dc-NN/<stratum-digest>.json`; tables that depend on run-time ledger state (a stratum
   that appears during a campaign) are generated by the same pure function when the stratum is created, recorded
   in the ledger with their hash, and are not committed; `check-generated` covers the committed defaults and the
   replay scenario covers the run-time ones.
8. **Budget of the compiler.** Table generation for one core finishes in under 10 s on one CPU core (TARGET); a
   generator that cannot (for example a kernel rewrite search) has its own budget in its record (60 s of search
   per kernel for DC-11).

Determinism class D0. No claim is emitted. The regeneration report (per table: the hash in the record, the hash
regenerated, `identical`) is the measured value of GATE-ATEL-13's first clause for each core. This bead records
no gate value: the real tables belong to beads that depend on this one, and the gate's parts have one recorder
each, N28c-05 for the M3 part (DC-01, DC-09 and DC-10, BD-309's tables) and N28cp3-01 for the M4 part (the
other eight), each from the receipt of its tier run with `record_gate`.

## Acceptance criteria

- [ ] `xtask check-generated` regenerates every committed core table and compares bytes; a hand edit of one row
      fails the check with a row-level diff naming the row and both values.
- [ ] Two generations of the same table hash equal: twice on one machine, in debug and release, on the Mac and on
      the Linux host (recorded hashes equal).
- [ ] No `f32` or `f64` appears in generator modules (lint passes; a planted `as f64` fails it).
- [ ] A table that is missing, has a changed row, has a header version different from the record, or is bound to
      another identity is refused at load with `FROB-REF-871`, and the caller observes `FallbackInForce`.
- [ ] A generator whose self-test fails at load raises `null-self-test-failed`; the fallback is in force and an
      evidence record says which trigger fired.
- [ ] `regenerate_all` returns, per table, the recorded hash, the regenerated hash and `identical`, in the form
      the recorders of GATE-ATEL-13 cite for its first clause (N28c-05 at M3 for DC-01, DC-09 and DC-10;
      N28cp3-01 at M4 for the other eight). This bead closes on the toy table and the DC-01 fixture table and
      records no gate row: the real tables are built by beads that depend on it.
- [ ] Generation of the toy table and of the DC-01 fixture table completes in under 10 s on one core (TARGET;
      measured value recorded); the same measurement on the three M3 tables is N28c-05's.
- [ ] `scripts/e2e/core_contract.sh --phase compile` passes and its two planted edits (row, header) are caught.

## Test plan

### Unit tests

`crates/frob-opt/tests/core_compile.rs`:
- `regenerate_is_identity`: generate the synthetic table "toy" (rows n ↦ n² for n in 0..10), write, regenerate,
  bytes equal.
- `row_edit_detected`: change row 7 from 49 to 50; `regenerate_all` reports first differing row 7, expected 49,
  found 50, one differing row.
- `header_edit_detected`: change a parameter string from "1/20" to "1/21"; the diff says "header".
- `canonical_rationals_reduced`: "2/40" is written as "1/20".
- `big_integers_as_strings`: 2⁵³ + 1 is serialized as a string and parsed back exactly.
- `load_refuses_stale`: four planted defects (missing, row, version, identity), each `FROB-REF-871`.
- `self_test_failure_triggers_fallback`: a toy generator whose self-test rejects; load yields
  `FallbackInForce { reason: NullSelfTestFailed }`.
- `no_clock_in_bytes`: the generator API takes no clock, host or environment argument (asserted on the trait
  signature), and two generations separated by a real two-second sleep, with a different `TZ` and working
  directory, give equal bytes.
- `integer_inequality_matches_definition`: for the DC-01 parameters, for every (n, k) with n ≤ 64, the integer
  rule 19^(n−k) ≥ 100·14^(n−k)·6^k agrees with the exact rational comparison of the product
  (19/14)^(n−k)·(1/6)^k against 100.

### End-to-end script and logging

This bead adds the phase `compile` to `scripts/e2e/core_contract.sh` (written by N28c-01; `--phase compile` runs
alone and passes at this bead's close, on the synthetic toy generator and the DC-01 fixture generator. Their
records and tables are never written into the committed registry: the phase begins with
`e2e_registries_scratch`, which copies `registries/` into the run's `registries/` and exports

differing row, body; with the header parameter "1/20" changed to "1/21" the diff says "header"; generation run
twice, and in debug and release, gives equal hashes; `cargo xtask check-generated --write` restores the committed
bytes. Logged through the STD-E2E helper to `target/e2e-logs/core_contract/<utc-timestamp>.ndjson` (`bead`

### Known answers and negative controls

- KA-695: the DC-01 table has 16 at k = 0 and 22 at k = 1; exact.
- Negative controls: the hand-edited row; a generator that uses a floating-point logarithm (planted in a test
  generator: it produces 17 instead of 16 on a host with a perturbed `ln`, simulated by an injected rounding, and
  the integer-inequality cross-check catches it); a table bound to the wrong kernel version.
- Metamorphic relation: permuting the order in which strata are generated leaves every per-stratum table's bytes
  unchanged.
- Determinism lanes as in the acceptance criteria.

## Considerations

- Run-time tables for strata that did not exist at build time are the delicate part: they must be produced by the
  identical pure function and recorded with their hash before first use, or replay cannot reproduce the decision.
- A generator version bump changes bytes legitimately; the workflow is: bump `generator.version`, regenerate with
  `--write`, bump `policy.version` in the record, commit all three together. `check-contracts` (N28c-01) rejects a
  commit that changes a table without the version bump.
- Performance and memory: tables are kilobytes; the only large artifact is the DC-10 incidence matrix, which is
  stored by reference (digest) and not inlined.
- Security: tables are data loaded from the repository tree; the path is resolved inside the registry directory
  only.
