## Background

A decision core (one of the eleven recurring decision rules DC-01 to DC-11 of the design studio, each compiled
ahead of time into a table with a loss model, proof obligations, a deterministic fallback and a budgeted mode) is
only auditable if each decision it makes is written down with what it read. The contract says: every decision a
core makes is written as an evidence record: the identities it read, the table version, the ledger frontier, the
action taken, and, while in shadow, the action the baseline took. Each record carries the core's decision-policy
identifier and version, so any verdict can be traced to the exact rule that produced it.

Two further rules live here.

- ADR-ATEL-09, the controller gate: no adaptive controller is enabled by default without a replay scenario,
  evidence records, a calibration report and a demonstrated fallback. Adoption is always shadow (report both
  rules, act on the old), then canary, then default; the incumbent in each shadow run is the plan's own reference
  path. A core's pilot is its shadow run: it acts on nothing until the comparison of its actions with the
  baseline's has been read.
- INV-ATEL-06: a decision core's action is a pure function of its table version, the ledger state at a pinned
  frontier and addresses. It reads no clock.

Why a pinned frontier: the ledger grows while a core decides. If a core read "the ledger now", two replays would
read different rows and decide differently. A frontier is a commit sequence number of the ledger; a decision names
the frontier it read at, and a replay reads exactly the rows at or below it.

The last two clauses of gate GATE-ATEL-13 are served here: "its fallback is demonstrated by forcing each trigger;
its shadow run records both actions". Rejected alternatives: logging decisions as free text (not resolvable in the
artifact graph); enabling an adaptive rule directly behind a feature flag (no evidence that it would have agreed
or disagreed with the baseline before it acted). Tier: Solid [S].

## Scope

In: the decision evidence record and its schema; the frontier pin; the adoption state machine and what each state
does; the trigger-forcing interface used by tests and demonstrations; the replay scenario runner; the query that
lists the fallbacks that fired in a campaign.
Out: the record and table schemas (N28c-01); table generation (N28c-02); the content of each core (BD-309,
BD-349); the composition rules across cores (N28c-06, BD-350); campaign reports that print the fallback list
(N28c-19).

## Technical approach

Module `crates/frob-opt/src/cores/record.rs` and `adoption.rs`. `frob-opt` is below the ledger crate in the
layering, so records are written through the evidence-sink trait that `frob-core` defines and `frob-chronicle`
implements; `frob-opt` never names the ledger crate.

1. **The decision record (DESIGN), schema `frob.core-decision/1`.**
   ```rust
   pub struct DecisionRecord {
       policy: DecisionPolicyId,            // ("atelier.dc01.promote", 3)
       core: CoreId,
       table: TableRef,                     // version and BLAKE3 hash of the table evaluated, or None on fallback
       frontier: LedgerFrontier,            // commit sequence number the inputs were read at
       read: Vec<InputRef>,                 // identities read: model, scene, task, controller or policy, kernel
                                            // versions, effort profile, battery version, stratum key, world addresses
       state: CanonicalState,               // the integer state the table was indexed with (for DC-01: n and k)
       action: Action,                      // the action taken
       rule: RuleUsed,                      // Table | Fallback { trigger } | Budget
       baseline_action: Option<Action>,     // present in shadow and canary: what the reference rule did
       adoption: Adoption,                  // Shadow | Canary | Default | FallbackOnly
       claim_ids: Vec<ClaimId>,             // claims this decision decided ("decided-by" edges)
   }
   ```
   The record's `EvidenceId` is BLAKE3(kind ‖ payload hash) with kind `ledger row`; it is written before the action
   takes effect (write-ahead). Trace identifiers and wall-clock times identify executions and are stored beside the
   record, never inside the hashed payload, so two executions of the same decision produce the same evidence
   identifier.
2. **The decide path.** `cores::decide(core, ctx)`:
   1. Pin the frontier: `ctx.frontier = ledger.committed_frontier()` once per decision period (for a core with a
      period, such as "per generation", once per period: the mode automaton never changes inside a generation).
   2. Read inputs at the frontier only. Build the canonical integer state.
   3. Evaluate triggers. If any fires, or the table failed to load (`FROB-REF-871`), the rule used is
      `Fallback { trigger }`.
   4. Otherwise evaluate the table. If the budgeted mode is exhausted, the rule used is `Budget` and the action is
      the core's budget action (for DC-01: the result stays `provisional`).
   5. Compute the baseline action (the core's deterministic fallback, which is also the reference path).
   6. Choose the applied action by adoption state: `Shadow` → baseline; `Canary` → table action for the canary
      share, baseline otherwise; `Default` → table action; `FallbackOnly` → baseline.
   7. Write the record; then return the applied action.
3. **Adoption state machine.**
   - `Shadow`: both actions computed and recorded; the baseline acts. Exit condition to `Canary`: the calibration
     report exists, the replay scenario reproduces, every trigger has been forced and the fallback observed, and
     the shadow comparison (count of agreements, disagreements by kind, cost difference) has been read and
     recorded as an ADR.
   - `Canary`: the table acts on a keyed share of decisions (DESIGN default: one in eight, chosen by a hash of the
     decision's address, never by time or arrival order); both actions still recorded.
   - `Default`: the table acts; the baseline action is still computed and recorded for one decision in 64
     (DESIGN, by address hash) as a standing shadow sample.
   - `FallbackOnly`: reached from any state when a Frontier core's calibration fails its gate after one repair
     cycle, or by an operator rollback (a configuration flag `--core dc-NN=fallback`). The fallback acts; the
     registry record says so.
   A state change is a commit to the record (`status`) plus an ADR; nothing changes state at run time.
4. **Purity guard (INV-ATEL-06).** The `DecisionCore::decide` signature takes the table and the canonical state
   only. The context type handed to core code exposes no clock, no device load, no queue length and no arrival
   index (compile-time: those accessors do not exist on `CoreCtx`). A lint in `frob-opt::cores` forbids
   `std::time`, and the property test below re-runs decisions under shuffled wall-clock conditions.
5. **Forcing triggers.** `cores::testing::force(trigger)` (available to tests and to the demonstration manifest
   behind the `conformance` feature) makes the named trigger condition true for one decision by constructing the
   real condition, not by a flag: for `missing-ledger-stratum` it queries a stratum key that has no row; for
   `identity-mismatch` it presents a table bound to another kernel version; for `null-self-test-failed` it loads a
   table with one edited row. Each core lists its triggers in its record; the demonstration runs each.
6. **Replay scenario.** `conformance/cores/dc-NN/replay.toml` lists a frontier, an input set and the expected
   sequence of (state, action, rule). `cores::replay(scenario)` re-evaluates from the table and the recorded
   ledger rows and must reproduce the sequence exactly; a difference names the first differing decision.
7. **Queries.** `cores::fallbacks_fired(campaign) -> Vec<(CoreId, Trigger, count, first_record)>` and
   `cores::shadow_disagreements(core, range)`; used by reports and by `cores.show`.

Determinism class of a decision: D0 given the table and the ledger rows at the frontier. Evidence class of the
record: it is itself evidence (`ledger row`); a claim decided by a core carries a `decided-by` edge to the policy.

## Acceptance criteria

- [ ] Every call to `cores::decide` writes exactly one `frob.core-decision/1` record before its action takes effect
      (asserted by ledger sequence order), carrying policy name and version, table hash, frontier, inputs, state,
      action, rule used and, in shadow or canary, the baseline action.
- [ ] `frob evidence trace <claim_id>` on a claim decided by a core returns the decision record and the policy
      version in its closure.
- [ ] In `Shadow`, the applied action equals the baseline action in 100% of decisions while the table action is
      recorded beside it (checked on 1,000 synthetic decisions with a table that disagrees in about half).
- [ ] Purity: 10⁴ decisions replayed under 100 random schedules (random delays, reordered completion, different
      worker counts) produce identical records, byte for byte (INV-ATEL-06).
- [ ] Forcing each registered trigger of a core produces a record with `rule = Fallback { trigger }` and the
      fallback action; an unregistered trigger name is rejected.
- [ ] The replay scenario of each registered core reproduces; a planted change of one ledger row above the pinned
      frontier does not change any decision, and a change at or below it is detected as a replay mismatch.
- [ ] A canary share is selected by address hash: the selected set is identical across runs and independent of
      arrival order.
- [ ] `cores::fallbacks_fired` on a campaign with three forced triggers returns exactly those three with counts.
- [ ] Cancellation: a decision interrupted between record write and action is recovered by key on restart; no
      action is applied twice and no record is duplicated (tested under the simulation harness).

## Test plan

### Unit tests

`crates/frob-opt/tests/core_records.rs`:
- `record_written_before_action`: a probe action that reads the ledger sees its own record.
- `shadow_acts_on_baseline`: toy core, table says A, baseline says B; applied = B, record has both.
- `canary_share_keyed`: 8,000 addresses; the canary set has 1,000 ± 100 members and is the same in two runs with
  reversed arrival order.
- `default_keeps_shadow_sample`: one decision in 64 by address hash carries `baseline_action`.
- `frontier_pins_inputs`: write a row after the pin; the decision is unchanged; pin later; the decision changes.
- `no_clock_accessors`: a compile-fail test: core code that calls `ctx.now()` does not compile.
- `forced_triggers_take_fallback`: for the toy core's three triggers.
- `replay_reproduces` and `replay_names_first_difference` (planted difference at decision 17 is reported as 17).
- `evidence_id_ignores_trace`: two executions with different trace identifiers give equal evidence identifiers.
- `fallback_only_is_sticky`: after `FallbackOnly`, a table action is never applied.

### End-to-end script and logging

`scripts/e2e/decision_cores_m3.sh` (N28c-05) drives real verbs that are governed by DC-01, DC-09 and DC-10, forces
each trigger through the demonstration manifests, and reads the records back with `frob evidence trace`. Lines
logged for this bead: `metric` lines with decisions, records, shadow agreements and disagreements per core;
`assert` lines for "record precedes action" and "applied equals baseline in shadow"; on failure the first
decision whose record is missing, with the ledger sequence numbers.

### Known answers and negative controls

- Known answer: with the DC-01 default table, the state (n, k) = (16, 0) gives table action `promote` and the
  fixed-30-pair baseline gives `continue`; in shadow the applied action is `continue` and both are recorded.
- Negative controls (registered): a core implementation that reads the ledger tip instead of the pinned frontier
  (caught by the replay-under-growth test); a core that applies its table action in shadow; a canary selected by
  arrival order (caught by the reversed-arrival test); a record written after the action.
- Property test for INV-ATEL-06 as in the acceptance criteria. Determinism lanes: twice on one machine; across
  worker counts 1, 4 and 36; debug and release.

## Considerations

- The standing shadow sample in `Default` costs one baseline evaluation in 64; baselines are fixed tables, so the
  cost is negligible, and it is what detects drift between the adaptive rule and its reference after adoption.
- A shadow run of DC-09 (the dispatcher) cannot "act on the old rule" for the same job twice; its shadow mode
  records what the baseline would have dispatched and compares waits offline from the trace. Each core's record
  states how its shadow comparison is computed.
- Storage: one record per decision. DC-09 decides per quantum (at most 5 s), so its records are batched per
  quantum into one row holding the integer state and action; the batching is lossless.
- Privacy: records hold identities and integer states, never private-scene payloads.
- Revisit the design if a core needs state that cannot be expressed as integers at a frontier; that would be a
  new kind of artifact and a change to the contract.
