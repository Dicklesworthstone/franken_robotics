## Background

The design studio makes eleven recurring decisions through compiled decision cores (DC-01 to DC-11): for example
DC-01 decides whether a fast-tier result is promoted, DC-09 which job runs when, DC-10 which scenes form a
battery. Each core is a registry record with a compiled table, a loss model, proof obligations, a deterministic
fallback, a budgeted mode and an adoption status (`shadow`, `canary`, `default`, `fallback-only`). An agent or a
person reading a verdict needs to see the exact rule that produced it: which table, which thresholds, which
fallback was in force, and whether the adaptive rule was acting or only shadowing. `cores.show` is that window.
It is the one verb the decision-core section registers; every other effect of a core is seen through the verb it
governs (`eval.promote` for DC-01, the daemon's dispatch for DC-09, `nemesis.cover` for DC-10, and so on).

The verb is registered in the verb registry `registries/verbs.toml` (from which the command line, the daemon
protocol, the MCP tool definitions, the schemas and the refusal table are generated): name `cores.show`, kind
`read` (returns stored or cheaply computed facts and changes nothing), first milestone M3, cluster `cores`,
description "A decision core's table, loss model, obligations and fallback". Tier: Solid [S].

Design reason: a read verb, not a document, because the answer depends on the live registry and ledger (which
table version is loaded, whether it is stale, what the shadow comparison says so far). Rejected: printing tables
only in generated documentation (cannot show adoption state or staleness on this host); folding the information
into each governed verb's output (eleven different shapes, and no way to ask before running anything).

## Scope

In: the registry entry, input and output schemas, the command-line form, the output content, pagination of table
rows, the stale-table behaviour, the decision summary.
Out: the record and table formats (N28c-01); generation and the staleness check (N28c-02); decision records and
adoption (N28c-03); the records themselves (BD-309, BD-349).

## Technical approach

1. **Registry entry (DESIGN).**
   ```toml
   [[verb]]
   name = "cores.show"
   cluster = "cores"
   kind = "read"
   tier = "S"
   capabilities = ["cores:read"]
   input_schema = "frob.cores.show.in/1"
   output_schema = "frob.cores.show.out/1"
   refusals = ["FROB-REF-871"]
   ```
2. **Command-line forms.** `frob cores show dc-01 --json`; `frob cores show --all --json` (one summary line per
   core); options: `--stratum <key>` (the table bound to that ledger stratum; default: the committed default
   table); `--rows` (include table rows, paginated with a cursor pinned to the registry commit); `--decisions
   <campaign-or-run>` (summary of decisions the core made there); `--rejected` (the methods considered for this
   core and not built, with their reopen conditions, from the rejected-methods register).
3. **Input schema `frob.cores.show.in/1`.** `{ core: "dc-01".."dc-11" | null, all: bool, stratum: string | null,
   rows: bool, decisions: string | null, rejected: bool, cursor: string | null }`; exactly one of `core` and `all`.
4. **Output schema `frob.cores.show.out/1`.** For one core:
   - `id`, `decision`, `owner_crate`, `governed` (verbs), `timescale`, `plane`, `family`, `tier`;
   - `policy { name, version }`, `status` (adoption), `registered` (false when no record exists yet);
   - `artifacts[]`: `kind`, `version`, `hash`, `generator { name, version }`, `parameters` (exact strings),
     `bound_to` (identities), `state`: `loaded` | `stale` | `missing` | `not-registry-version`, and with `--rows`
     the rows (paginated);
   - `loss { states, actions, constants }` with each constant labelled `declared` or `open: OPEN-ATEL-1` where the
     owner has not decided it;
   - `obligations[]`: identifier, statement, how it is discharged, and the status of its last recorded discharge;
   - `fallback { rule, triggers[], in_force: bool, reason }`;
   - `budget { mode }`;
   - `replay { scenario, last_result }`, `calibration { report, summary }`, `demo { manifest, claim_ids }`;
   - with `--decisions`: `decisions { count, by_rule { table, fallback, budget }, fallbacks_fired[] { trigger,
     count, first_record }, shadow { agreements, disagreements, by_kind } }`;
   - with `--rejected`: `rejected[] { method, why_not, reopen_condition }`.
5. **Behaviour on a stale or missing table.** The verb does not refuse: inspection must work exactly when
   something is wrong. It completes with exit 2 (completed with findings), `artifacts[i].state = "stale"`,
   `fallback.in_force = true`, and a finding that carries the code `FROB-REF-871` with its repair ("regenerate;
   the fallback is in force meanwhile"). The governed verbs are where `FROB-REF-871` appears as a refusal or as a
   recorded fallback.
6. **Envelope.** Standard envelope `frob.envelope/1`: `evidence { class: "Tested", tier: "static",
   determinism: "exact", claims: [], reality: "no-claim" }`; `bound` holds the registry commit and the table
   hashes; `next_actions` suggests `cargo xtask check-generated --write` when a table is stale and the governed
   verb otherwise. Exit 0 when everything is loaded, 2 with findings, 3 for an unknown core identifier (schema
   refusal). Integers above 2⁵³ in rows are strings.
7. **Token budget.** Without `--rows` the answer for one core is under 2,000 tokens (TARGET); rows are paginated
   at 200 per page.
8. **Implementation.** Verb executor in `frob-verbs` calling `frob_opt::cores::{load_record, load_table,
   fallbacks_fired, shadow_disagreements}`; no computation beyond loading and hashing; class D0; memoizable on
   (registry commit, stratum, campaign frontier).

## Acceptance criteria

- [ ] `frob cores show dc-01 --json` returns every field of the output schema for a registered core, with the
      table hash equal to the registry's and `state: "loaded"`.
- [ ] `frob cores show --all --json` lists eleven cores; cores without a record show `registered: false`.
- [ ] With a planted stale table the verb exits 2, shows `state: "stale"`, `fallback.in_force: true` and a finding
      with `FROB-REF-871` and its repair.
- [ ] `--rows` paginates; concatenating all pages reproduces the committed table bytes after canonicalization.
- [ ] `--decisions <campaign>` on a campaign with three forced triggers lists exactly those triggers and counts,
      and the shadow agreement and disagreement counts equal a direct count over the decision records.
- [ ] An unknown identifier (`dc-12`) exits 3 with a schema refusal; exit code 1 never occurs.
- [ ] The verb is reachable through `frob --json` and through the MCP surface (tool generated from the registry;
      the served tool list matches the registry).
- [ ] The answer for one core without rows is under 2,000 tokens (measured value recorded).
- [ ] Output is byte-identical across two invocations at the same registry commit and ledger frontier.

## Test plan

### Unit tests

`crates/frob-verbs/tests/cores_show.rs`:
- `shows_all_contract_fields`: every mandatory record field appears in the output for the DC-01 fixture.
- `stale_table_is_finding_not_refusal`: exit 2, finding code `FROB-REF-871`.
- `unknown_core_exit_3`.
- `rows_paginate_and_reassemble`: 3 pages of 200 rows for a 450-row synthetic table reassemble exactly.
- `open_constants_labelled`: with OPEN-ATEL-1 undecided, `C_fp` and `C_fn` are labelled `open: OPEN-ATEL-1`.
- `decisions_summary_counts`: a fixture ledger with 40 decisions (30 table, 7 fallback by two triggers, 3
  budget) yields those counts.
- `rejected_lists_methods`: for `dc-09` the list contains "Mechanism design for the queue" and "Bandit
  allocation" with their reasons.
- `output_schema_validates`: the output validates against the generated JSON schema.

### End-to-end script and logging

`scripts/e2e/decision_cores_m3.sh` (N28c-05) calls the verb for `dc-01`, `dc-09`, `dc-10` and `--all`, with and
without `--rows` and `--decisions`. It logs the exact command lines, exit codes, wall times, the envelope's
`evidence` block, the table hashes compared with the registry (`digest` fields), token counts against the 2,000
threshold, and a `refusal` line for the unknown-core case.

### Known answers and negative controls

- Known answers shown by the verb: DC-01 rows 16 at k = 0 and 22 at k = 1 (KA-695); DC-10's certificate fields
  for the worked instance (covered 86 of 100, bound 98; KA-704).
- Negative controls: a verb implementation that reports `loaded` without recomputing the hash (caught by the
  planted stale table); one that reads the adoption status from the code default instead of the record (caught
  by a record set to `canary`).
- Determinism: twice on one machine; the Mac and the Linux host; class D0.

## Considerations

- The verb is read-only and cheap; it must never trigger generation or change adoption state.
- Capability scope `cores:read` is granted by default; there is no mutate verb for cores: adoption changes are
  commits with an ADR.
- Privacy: decision summaries print identities and counts only.
- If the eleven cores later need per-campaign overrides, that is a new input on the governed verbs, not on this
  one.
