## Background

Gate GATE-ATEL-13 (claim kind: Known answer) says of each decision core of the design studio: its table
regenerates bit-identically; its null calibration holds; its fallback is demonstrated by forcing each trigger; its
shadow run records both actions. The parts for DC-01 (promote a fast-tier result, reject it as tier-sensitive, or
buy another pair), DC-09 (which job runs when on a device) and DC-10 (which scenes form a battery) are due at
milestone M3; the other eight cores are due at M4. A decision core is a registry record under `registries/cores/`
with a compiled table (`frob.core-table/1`), a loss model, proof obligations, a deterministic fallback, a budgeted
mode and an adoption status; it ships in shadow, meaning it records what it would do and the fixed baseline acts.

This bead is the end-to-end script that measures the M3 part of the gate from the user's side, with the real
`frob` binary and the real daemon, and records it. A gate passes only with a recorded measurement against its
threshold, and only if a registered negative control was shown to fail; the script therefore runs the planted
defects as well as the clean case. Tier: Solid [S].

## Scope

In: the script, its fixtures, its assertions, its logging, the gate record for the three cores.
Out: the mechanisms and records under test (BD-309 and the beads it depends on); the M4 cores (the M4 conformance
beads and BD-349); the interference tests between cores (BD-350).

## Technical approach

`scripts/e2e/decision_cores_m3.sh`, plain shell, sources the shared STD-E2E helper, idempotent, seed-explicit
(`FROB_E2E_SEED`, default 20281101), exits non-zero on any failed assertion. Fixtures live under
`conformance/cores/`. Steps:

1. `start`: record commit, toolchain, host fingerprint, seed.
2. Regeneration, clean: `cargo xtask check-generated` → exit 0. For each of `dc-01`, `dc-09`, `dc-10`:
   `frob cores show <id> --rows --json`; assert `artifacts[].state == "loaded"` and hash equals the record's.
3. Regeneration, planted: in a scratch copy of `registries/cores/tables/`, change one row of the DC-01 table
   (promote_at_n for k = 0 from 16 to 15); `cargo xtask check-generated` → non-zero, diff names row k = 0 with 16
   expected and 15 found; `frob cores show dc-01 --json` against the scratch registry → exit 2 with
   `state: "stale"`, finding `FROB-REF-871`, `fallback.in_force: true`.
4. Known answers of the tables: from the `--rows` output assert DC-01 promote points (16, 0), (22, 1), (29, 2);
   from `frob cores show dc-09 --rows --json` assert the capacity rows at ρ = 0.7 (2,000.6 s; 620.9 s; 0.17 s,
   each within 0.5%); run `frob nemesis cover --instance conformance/cores/dc-10/worked.json --k 6 --json` and
   assert covered 86, bound 98.
5. Null calibration of DC-01: `frob-conformance run cores.dc01.null --runs 10000 --seed $SEED --json` drives the
   real table with simulated exceedance bits at rate p₁ = 0.30 under adversarial optional stopping (stop at the
   running maximum) and at p₀ = 0.05; assert wrong promotions ≤ 132 and wrong rejections ≤ the exact binomial
   acceptance bound for α⁻ = 0.05 at test level 0.001 (computed by the harness in exact arithmetic and logged).
   The bits are `synthetic` and labelled so.
6. Forced fallbacks through the governed verbs, one command per trigger:
   - DC-01 `missing-ledger-stratum`: `frob eval promote r:<fixture-result-in-unmeasured-stratum> --json` → the
     promotion receipt says `rule: "fallback"`, 30 pairs, promote on at most 2 exceedances.
   - DC-01 `identity-mismatch`: promote a result whose kernel version differs from the table header.
   - DC-01 `null-self-test-failed`: scratch registry with the edited table of step 3.
   - DC-09 `estimates-unreliable`: submit the fixture job set whose estimates are wrong by 3× for 12 of the last
     50 jobs; `frob job list --json` and the daemon's decision records show round-robin, run to completion.
   - DC-09 `resume-digest-differs`: the conformance build with the planted resume defect; assert the alarm and
     per-job dispatch.
   - DC-10 `identity-changed`: `frob nemesis cover` after a taxonomy version bump → the standard battery is
     returned and the record names the trigger.
   After each, `frob cores show <id> --decisions <run> --json` lists the trigger with count 1.
7. Shadow records: run `frob eval promote` on the honest fixture result with DC-01 in `shadow`; fetch the decision
   records with `frob evidence trace <claim_id> --json`; assert every record has both `action` and
   `baseline_action` and that the applied label follows the baseline. Same for one battery selection and for a
   two-job queue (DC-09's shadow comparison is computed from the trace: recorded baseline dispatch order beside the
   applied one).
8. Demonstration manifests: run `demos/dc-01/demo.yaml`, `demos/dc-09/demo.yaml`, `demos/dc-10/demo.yaml`; assert
   each under 60 s and checksums equal.
9. Determinism: repeat steps 2, 4 and 7 with `--workers 1` and `--workers 36`; assert identical table hashes and
   identical decision-record evidence identifiers.
10. `summary`: counts of assertions passed and failed; gates touched: `GATE-ATEL-13 (DC-01, DC-09, DC-10)`; write
    the measured values for the gate row.

**Logging.** Newline-delimited JSON to `target/e2e-logs/decision_cores_m3/<utc-timestamp>.ndjson` and a
human-readable transcript beside it. Every line: `ts`, `script`, `bead` (`N28c-05`; lines for a sub-check also
carry the bead under test, for example `BD-309`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`,
`end`), the exact command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier,
determinism, identities, seed), measured values with units and thresholds (null-run counts against bounds; waits
in seconds against known answers; demo wall time against 60 s), digests where state is compared (table hashes,
decision-record identifiers), and on failure the first differing value and the artifact paths needed to
reproduce (scratch registry path, the failing table row, the decision record). A final `summary` line. No
private-scene data is logged.

## Acceptance criteria

- [ ] The script exits 0 on a correct tree and writes the log and transcript at the stated path.
- [ ] Each of the six triggers is forced and the fallback action observed and logged.
- [ ] The planted row edit is caught twice: by `check-generated` and by the load-time refusal `FROB-REF-871`.
- [ ] Null-calibration counts are logged with their exact acceptance bounds and are within them.
- [ ] Shadow records carry both actions for 100% of decisions in the three shadow runs.
- [ ] Two runs with the same seed produce identical `assert` and `metric` values and identical digests.
- [ ] The gate registry row for GATE-ATEL-13 lists the three cores with measured values and the claim identifiers
      from the run; the row is recorded by a session that did not implement the cores.
- [ ] Negative controls: with any one of the planted defects below compiled in, the script exits non-zero and the
      log's first failing line names the defect's symptom.

## Test plan

### Unit tests

The script's helper functions are tested in `scripts/e2e/tests/decision_cores_m3.bats`-style shell tests run by
`cargo test -p frob-conformance --test e2e_scripts`: `parses_rows_output` (extracts (k, promote_at_n) pairs from a
recorded envelope), `binomial_bound_exact` (the harness's bound for N = 10⁴, α = 1/100, level 1/1000 is 132),
`summary_counts_match` (the number of `assert` lines equals passed plus failed in the summary).

### End-to-end script and logging

As specified above; this bead is the script.

### Known answers and negative controls

- KA-695, KA-703, KA-704 with the values stated in step 4.
- Planted defects the script must catch (registered in the negative-control registry with this gate): (a) the
  edited table row; (b) a core that applies its table action while in shadow; (c) a dispatcher build that orders
  by wall-clock arrival (decision-record identifiers differ between worker counts in step 9); (d) a battery
  certificate computed from stale gains (bound printed below the brute-force optimum on the 12-scene fixture);
  (e) an envelope replaced after the first outcome (the promotion must not be issued under the table rule).
- Determinism lanes: twice on one machine; worker counts 1 and 36; debug and release; the Mac and the Linux host,
  each against class D0 for tables and decisions.

## Considerations

- The daemon steps need `frobd` running with the CPU tier; the script starts a private daemon on a scratch state
  root and stops it at exit, so it does not disturb a developer's queue.
- Runtime budget of the whole script: under 10 minutes on the CPU tier (TARGET); the null runs dominate.
- The script must not weaken a failing assertion to a warning; a control that is not caught is a failure of the
  gate, whatever the clean case says.
