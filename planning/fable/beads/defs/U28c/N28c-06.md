## Background

The design studio runs eleven decision cores (DC-01 to DC-11: compiled decision rules with a table, a loss model,
obligations and a fallback) at eleven different rates, and several of them touch the same quantities: GPU-seconds,
which episodes run, the model identity under which evidence is pooled. Two controllers that act on one quantity
without a rule produce the classic failure of coupled control loops: each sees the other's action as a
disturbance, and results depend on timing. The plan prevents this by construction with three rules, and proves the
construction with nine interference tests (gate GATE-ATEL-14, measured by BD-350). This bead builds the three
rules as checkable data and the campaign fixture the tests replay.

The rules:

1. **Timescale order.** Slowest first: DC-11 at build; DC-10 per battery revision; DC-08 at ledger refresh; DC-07
   per real batch; DC-03 per generation; DC-02 per rung transition; DC-05 per experiment; DC-04 per finalist;
   DC-06 per failure cluster; DC-01 per episode batch; DC-09 per quantum. Each loop treats every slower one as a
   constant, and no loop writes a quantity that a faster loop is reading inside its own period.
2. **One owner per shared quantity.** Where two controllers touch the same quantity, one rule assigns it.
3. **One-way pipelines.** DC-04 → DC-06 → DC-10: failures found feed attribution, attributed modes feed the
   incidence matrix, and nothing flows back inside a campaign. The handover from the population layer (DC-02 with
   DC-03) to the finalist layer (DC-05) is also one-way.

Two tensions are reconciled by construction and are part of the same data. Conformal exchangeability against
drift: the exchangeability alarm ends the regime and calibration restarts inside the new one. A parametric model
(DC-05, value of information) beside distribution-free tests (DC-01 to DC-03): the parametric model never issues a
verdict (ADR-ATEL-07), so a wrong model costs efficiency and never validity.

Reason for making the rules data instead of prose: the nine tests show the rules hold on one campaign; the static
check shows that no later change to a core record can add a second writer or a back edge without failing the
build. Rejected alternative: a supervising "meta-controller" that arbitrates between cores at run time (a twelfth
controller on shared telemetry, with its own timing dependence). ADR-ATEL-10 (two planes) is the outer wall:
kernels, step plans and physics never depend on the dispatcher, the memo policy or any estimator. Tier: Solid [S].

## Scope

In: `registries/cores/composition.toml`; the static composition check; the run-time period snapshot; the
replayed-campaign fixture in two parts; the replay driver and its `cores.replay` subcommand of the example target
`atelier_harness`.
Out: the nine tests themselves and the gate record (BD-350); the cores (BD-309, BD-349); the cascade (BD-352).

## Technical approach

1. **Composition registry (DESIGN), `registries/cores/composition.toml`.**
   ```toml
   order = ["dc-11","dc-10","dc-08","dc-07","dc-03","dc-02","dc-05","dc-04","dc-06","dc-01","dc-09"]   # slowest first
   [[quantity]]
   name = "advance-requests"            # which designs run next
   owner = { population = ["dc-02","dc-03"], finalists = ["dc-05"] }
   rule = "one-way handover; no design receives requests from both layers"
   test = "IT-1"
   [[quantity]] name = "higher-rung-episodes"   owner = ["dc-03"]  readers = ["dc-01"]
                rule = "audit designs run at fixed n and are never cancelled"                       test = "IT-2"
   [[quantity]] name = "gpu-seconds-and-completion-order" owner = ["dc-09"] readers = ["dc-01","dc-02","dc-03","dc-05"]
                rule = "dc-09 decides when, never what; e-values consume episodes in address order" test = "IT-3"
   [[quantity]] name = "throughput"     owner = ["dc-09"] forbidden_readers = ["dc-08"]
                rule = "dc-08 never reads the wall clock and never changes inside a run"            test = "IT-4"
   [[quantity]] name = "model-identity" owner = ["dc-08","dc-11"] readers = ["dc-01","dc-02","dc-03"]
                rule = "an identity change resets evidence and calibration; a class-E rewrite changes no identity" test = "IT-5"
   [[quantity]] name = "sampled-scenes" owner = ["dc-04"] forbidden_readers = []   # dc-04 draws nominal episodes itself
                rule = "bounds use nominal draws only"                                              test = "IT-6"
   [[quantity]] name = "battery-scenes" owner = ["dc-10"] forbidden_readers = ["dc-04"]
                rule = "a certification bound never samples from a battery or a search selection"   test = "IT-6"
   [[quantity]] name = "real-episodes"  owner = ["dc-07"] readers = ["dc-05"]
                rule = "conditions come from a pre-registered draw; dc-05 chooses only how many"    test = "IT-7"
   [[quantity]] name = "race-error-rate" owner = ["dc-01"]
                rule = "mixture construction, or alpha/(N-1) per comparison"                        test = "IT-8"
   [[quantity]] name = "outcomes"       owner = ["memo-policy"] readers = ["*"]
                rule = "a hit is bit-identical to a recomputation, so no core can tell"             test = "IT-9"
   [[pipeline]] edges = [["dc-04","dc-06"],["dc-06","dc-10"]]  scope = "campaign"
   [[pipeline]] edges = [["dc-02","dc-05"],["dc-03","dc-05"]]  scope = "campaign"
   ```
   Each core record additionally declares `reads` and `writes` (quantity names). `forbidden_readers` names the
   cores whose rule is that they must not read the quantity at all (DC-08 must not react to queue load; DC-04
   must not take its sample from a battery): the interference the plan's rule forbids is then visible to the
   static check as a declared read, and not only to the replay test.
2. **Static check (inside `xtask check-contracts`; no new check).** It fails when: a core's `timescale` is absent
   from `order`; a quantity has no owner or no test; a core writes a quantity it does not own; a core declares a
   read of a quantity that lists it in `forbidden_readers`; a core writes a quantity that a faster core reads and
   the write is not declared `at-boundary`; the pipeline edges contain a cycle or an edge from a later stage to an
   earlier one; a test identifier does not resolve to a test of the interference suite
   (`crates/frob-conformance/tests/core_interference.rs`). The suite is BD-350's, which depends on this bead, so
   the last rule holds from the change in which that file exists: before it, the check lists the nine identifiers
   as `unresolved` in its report and does not fail on them, so this bead's own clean-tree run passes; BD-350's
   acceptance makes every identifier resolve (convention 7: no bead waits on what waits on it).
3. **Run-time period snapshot.** A core reads the outputs of every slower core through a snapshot pinned at the
   start of its own period (the same mechanism as the pinned ledger frontier of decision records). A slower core's
   write becomes visible to faster cores only at the slower core's next period boundary. Concretely: the effort
   profile table (DC-08) changes only at a ledger refresh and never inside a run; the mode automaton (DC-03)
   changes only at a generation boundary; the battery (DC-10) changes only at a battery revision. A write
   attempted inside a reader's period is queued to the boundary and the queueing is recorded.
4. **The replayed-campaign fixture, part A (decision plane, `synthetic`).** `conformance/cores/campaign-81/`: 81
   designs in one morphology class in three strata of 27; rungs R1 (shared policy), R2 (fine-tune) and R3
   (specialist) with 32 world addresses each, plus referee pairs for finalists; k = 3 finalists. Outcomes per
   (design, rung, address) are generated once from a seeded latent-quality model (design quality q_d; rung noise
   σ_R1 = 0.10, σ_R2 = 0.05, σ_R3 = 0.02 on a unit-scaled score; a per-stratum bias on R1), stored as ledger rows
   and labelled `synthetic`. A second variant, `campaign-81-null`, gives all 81 designs the same quality (the null
   race). The fixture also holds: the keyed audit-lane draw (a tenth of rung spend), a pre-registered draw of
   real-episode conditions for the reality band, a nominal episode set and a battery-selected episode set for the
   rare-failure bound, and the campaign manifest hash.
5. **The fixture, part B (real episodes), `conformance/cores/campaign-9/`.** A mini-campaign on `batch-cpu`: 9 template variants of the reference
   quadruped under the synthesized baseline controller, 32 addresses each, at class D2, and a 1,000-world run used
   for digest comparisons before and after a class-E kernel rewrite. Episodes are recorded with digests so that
   scheduling, memoization and rewrite tests compare real state, not synthetic labels.
6. **Replay driver.** `frob_conformance::cores::replay_campaign(fixture, schedule)` re-drives every core over the
   fixture's ledger rows with no further simulation for part A, under a schedule object that controls completion
   order, preemption points, co-tenancy and worker count; for part B it re-runs the real episodes under the
   schedule through the daemon. It returns all decision records, all verdicts with their statistics, and all
   digests, for comparison across schedules. It is exposed to scripts as a subcommand of an example target of
   the conformance crate (DESIGN):
   `cargo run -p frob-conformance --example atelier_harness -- cores.replay --fixture <dir> --schedule <file>
   [--force-trigger <core>:<trigger>] [--cores <list>] --json`. Forcing a trigger constructs its condition on
   the fixture's rows, as the row beads specify per trigger. The product verb `opt.cascade` carries no replay,
   schedule or forcing option; the cascade (BD-352) is not a prerequisite of the fixture.
   Why an example target: the conformance crate is a library with test targets and has no binary, verb or
   `xtask` subcommand (ADR-GAUNT-01, BD-025: a harness driven through the surface it judges is a path to
   self-certification), so a command `frob-conformance run …` cannot exist; what the crate allows beside its
   test targets are example targets (`record_gate`, `validate_register`, `registry_report`). The studio's
   parameterized harnesses that scripts drive (replays, null-calibration simulations, fixture readers) are
   subcommands of one example, `crates/frob-conformance/examples/atelier_harness.rs`: a thin argument parser
   over library functions of `frob_conformance`, printing one JSON object on standard output and exiting
   non-zero when its own assertions fail. Whichever bead lands first creates the file; each bead adds its own
   subcommand, and `cores.replay` is this bead's.

Determinism: part A is class D0 given the fixture; part B is class D2 on one backend.

## Acceptance criteria

- [ ] `registries/cores/composition.toml` lists the eleven cores in the stated order, the nine shared quantities
      of the plan (with `battery-scenes` as the second half of IT-6's) with one owner rule and one test each, the
      forbidden readers, and the two pipelines.
- [ ] `xtask check-contracts` fails on each planted defect: a second writer of `advance-requests`; a pipeline back
      edge `dc-10 → dc-04`; a core missing from `order`; a DC-08 write to `model-identity` (its effort profile,
      which the faster cores DC-01 to DC-03 read) not declared `at-boundary`; a quantity without a test; a DC-08
      record that declares `reads = ["throughput"]`.
- [ ] Period snapshot: in the replay driver, a DC-08 table change submitted mid-run is applied at the next ledger
      refresh and not before (the run's profile identity is constant from first to last step), and the deferral is
      recorded.
- [ ] Fixture part A regenerates from its seed to identical bytes; its manifest hash is committed; every outcome
      row is labelled `synthetic`.
- [ ] Fixture part B runs on `batch-cpu` in under 15 minutes on the M5 Ultra's CPU (TARGET; measured value
      recorded) and its digests are stable across two runs.
- [ ] The replay driver, given two different schedules on part A, returns identical decision records and
      verdicts (this is the harness's own A/A check; the nine tests are BD-350).
- [ ] A harness self-check with a planted clock-reading core produces different records under two schedules, so
      the driver is shown able to see an interference.

## Test plan

### Unit tests

`crates/frob-opt/tests/core_composition.rs`: `order_has_eleven`, `single_writer_enforced`,
`pipeline_is_acyclic` and `pipeline_back_edge_rejected`, `write_inside_reader_period_deferred`,
`forbidden_read_rejected` (DC-08 declaring a read of `throughput`, DC-04 of `battery-scenes`: both fail),
`every_quantity_has_test`, `snapshot_hides_slower_write_until_boundary` (a DC-03 mode change requested in the
middle of generation 4 is visible to DC-02 only at generation 5).
`crates/frob-conformance/tests/campaign_fixture.rs`: `fixture_regenerates` (seed 81 → committed hash),
`null_variant_all_equal`, `audit_draw_precedes_scores` (the draw's ledger sequence number is below every score
row), `replay_a_a_identical`, `planted_clock_core_detected`.

### End-to-end script and logging

This bead writes `scripts/e2e/decision_core_interference.sh` with its first phase, `fixture`, which runs alone
(`--phase fixture`) and passes at this bead's close; BD-350 adds the phases `IT-1` to `IT-9`. The phase regenerates
part A from seed 81 and compares its manifest hash with the committed one; runs `cargo xtask check-contracts` on
the clean tree (pass), then, after `e2e_registries_scratch` (the run's own `registries/`, exported as
`FROB_REGISTRIES_ROOT`, which `xtask` resolves, N32ax-03), on that root with each of the six planted composition
defects in turn (each fails, naming the quantity or edge); this marks the invocation's receipts `override`, so
BD-350's phase `gate` runs in an invocation of its own; starts a private `frobd` and runs
part B twice on `batch-cpu` (`cargo run -p frob-conformance --example atelier_harness -- cores.replay --fixture
conformance/cores/campaign-9 --schedule <file> --json` under two schedules), comparing digests; runs the A/A replay of part A under two schedules and the
planted clock-reading core (records must differ). It sources the STD-E2E helper and writes
`target/e2e-logs/decision_core_interference/<utc-timestamp>.ndjson` with a transcript; lines of this phase carry
`bead` `N28c-06`, `step` `fixture`, `event`, the exact command line, exit code, wall time and the `evidence` block
(D0 for part A, D2 for part B); `metric` lines carry part B's wall time against the 15-minute TARGET; `digest`
fields carry the fixture manifest hash and the record and verdict digests under the two schedules; on failure the
first differing decision index or world address and the schedule file; a `summary` line.

### Known answers and negative controls

- Known answer: the timescale order has DC-11 first and DC-09 last, eleven entries, no duplicates.
- Negative controls: the six planted composition defects; the planted clock-reading core.
- Metamorphic relation: renaming designs (a permutation of design identifiers applied consistently) permutes the
  decision records and changes no verdict.
- Determinism lanes: fixture generation twice on one machine and on both hosts (D0); part B across worker counts
  (D2).

## Considerations

- The static check can only see what records declare. A core that reads an undeclared quantity is caught by the
  replay tests (its decisions change under a schedule that perturbs that quantity), which is why both exist.
- The synthetic latent-quality model is a test fixture, not a model of robots; it must not be cited for any
  saving or agreement figure.
- DC-07's real episodes do not exist before calibration data is admitted; the fixture's pre-registered draw is
  synthetic and the corresponding test is repeated on the synthetic rehearsal dataset when that exists.
- If a twelfth core is ever proposed, it enters `order` and the quantity table first; the check makes that the
  first failing step.
