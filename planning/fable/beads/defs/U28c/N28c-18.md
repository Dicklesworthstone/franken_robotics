## Background

Registered predictions answer a question nothing else in the design studio does: whether an agent understands the
robot it is designing or is searching blindly. Before a run, an agent registers a prediction:
`frob predict register --metric cot-elec --interval 0.42 0.50 --confidence 0.8 --for <planned-run> --key <k>`. The
prediction is hashed and frozen before the run starts and scored afterwards with a proper scoring rule.
`frob predict report` shows each agent's calibration. The studio registers its own predictions under the same rule
(cost estimates, the outcome intervals of suggested experiments, the saving a race or a ladder expects); a refit
after scoring opens a new prediction version and the old one stays scored. Calibration is put to work in two
places: a miscalibrated agent is told so in `next_actions`, and the studio's own miscalibration is a fallback
trigger of the value-of-information decision core DC-05 (80% intervals covering outside 65 to 92% over 30
experiments).

Registry facts: `predict.register` is kind `mutate` (takes an idempotency key, `--key`), first
milestone M4, "register a prediction with an interval and a confidence before a run"; `predict.report` is kind
`read`, M4, "calibration of an agent's registered predictions"; cluster `predict`. The chapter's mechanism table
lists registered predictions as Solid [S] under gate GATE-ATEL-16 (the cascade end to end on a seeded population,
whose report prints every mode, every fallback and the phase ledger): the cascade registers its expected saving
and its suggestions' outcomes, and the campaign report shows their scores. This bead is the end-to-end script for
the capability; it contributes the prediction controls of that gate (below) and writes no gate row: GATE-ATEL-16
has one recorder, the cascade script's bead N28b-28, which enters it from the receipt of the gate's tier run.

## Scope

In: the script, fixtures, assertions and logging for the whole prediction capability from the command line.
Out: the verbs and ledger (BD-344); the studio hooks (N28c-14); the monitor (N28c-15); the cascade (BD-352).

## Technical approach

`scripts/e2e/predict_calibration.sh`: plain shell over the real `frob` binary and a private `frobd`, sources the
STD-E2E helper, idempotent, seed-explicit. This bead owns the script; two beads it depends on
contribute phases that run alone with `--phase <name>`: `hooks` (N28c-14, the three studio registration hooks)
and `monitor` (N28c-15, the hint and the DC-05 trigger). The steps below run the capability whole, from the
agent's side, and call those phases as steps 9 to 12 instead of repeating them. Fixture: the reference quadruped template on the flat velocity task at
the CPU tier, with a run of 64 world addresses whose electrical cost of transport is the metric `cot-elec`; and
prebuilt ledger snapshots for the calibration windows (N28c-15's, under `conformance/predict/`); "load a
snapshot" below means: empty the run's state root (`FROB_STATE`, exported by `e2e_init`) and restore the snapshot
into it (`frob` has no `--root` option and reads no other state, STD-E2E's isolation rule). The prediction target is `next`
(the caller's next run dispatched in the session, BD-344): no registered verb at M4 plans a run without starting
it, so the script does not invent one; the dispositions and the accounting identity are BD-344's.

Steps:
1. Preconditions: `frob capabilities --json` lists `predict.register` and `predict.report` as implemented; a
   registration on an undeclared metric (`--metric no-such-metric … --key k0`) is `FROB-REF-802`, exit 3, and
   stores nothing (the schema refusal the Considerations name, asserted once).
2. Register: `frob predict register --metric cot-elec --interval 0.42 0.50 --confidence 0.8 --for next --key k1
   --json` → exit 0; the envelope returns `prediction_id`, `registered_seq` and the target's freeze status (not
   yet bound: no run dispatched); the record's predictor is the session's agent identity and its hash is logged.
3. Idempotent replay: the same command with `k1` → same `prediction_id`. The same key with a different interval
   → `FROB-REF-803`, exit 7 (conflict).
4. Second prediction: `frob predict register … --interval 0.30 0.60 … --for next --key k2 --json` → accepted
   as a second, separate record (an agent may register several before the freeze); both will be scored; the
   report shows both. Immutability: `predict.register` only appends (its help schema has no option that edits a
   record), and the hash of the step-2 record read before step 5 equals the one read after step 7.
5. Run: `frob sim run quad-a --task flat-velocity --worlds 64 --seconds 10 --tier batch-cpu --seed <s> --key r1
   --json` → exit 8 with a job handle; `frob job status <job> --json` shows both prediction identifiers in the
   job's freeze set with its combined hash; `frob job wait <job> --json` until done.
6. Late registration: `frob predict register --metric cot-elec --interval 0.45 0.47 --confidence 0.8 --for
   <job> --key k3 --json` after the outcome exists → refused, exit 3, with the interim form BD-344 raises for a
   prediction registered after its outcome (`FROB-REF-883`, `detail = "registration-after-outcome"`, pointer
   `prediction.target`, the sequence number of the earliest outcome record); nothing is stored.
7. Report: `frob predict report --json` → both predictions of steps 2 and 4 are `scored` against the measured
   `cot-elec`; each shows covered or missed, the interval score, and the outcome's evidence reference; the
   missed ones are included; the accounting identity registered = scored + unresolved + pending holds.
8. A prediction for a run that is then cancelled: register `--for next --key k4`, `frob sim run … --key r2`,
   `frob job cancel <job>`, report → disposition `no-outcome: cancelled`, counted as unresolved, still listed.
9. Studio predictions: `frob predict report --predictor studio:estimate --json` lists the cost predictions of the
   run of step 5, registered before its first chunk (sequence numbers compared); submit a nine-candidate race on
   the fixture (`frob opt start --task flat-velocity --design quad-a --population 9 --race alpha=0.05,rounds=64
   --seed <s> --key race-1 --json`) and assert one `studio:saving` prediction registered at start and scored at
   close.
10. Calibration hint: load the ledger snapshot `agent-narrow-30` (30 scored predictions at 0.8 with 17 hits);
    `frob design check quad-a --json` → `next_actions` contains the miscalibration entry with "17", the band
    "20 to 27 of 30" and the direction; the exit code equals that of the same command on the `agent-ok-30`
    snapshot (24 hits), where no hint appears; with `agent-29` (29 scored) no hint appears.
11. DC-05 trigger: load `studio-suggest-17-of-30`; `frob experiment suggest <d1> <d2> --budget gpu_s=600 --json`
    → fixed order with the trigger named; load `studio-suggest-24-of-30` → ranked by value (or its shadow form,
    according to the core's adoption status, which the script reads from `frob cores show dc-05 --json`).
12. Versions: trigger a refit of the fixture value model (`cargo run -p frob-conformance --example
    atelier_harness -- predict.refit --json`, N28c-14's subcommand of the example target of N28c-06), register
    and score five more; the report shows two versions with their own counts; the window of the monitor reads
    the new version only.
13. Determinism: the hashes of the predictions of steps 2 and 4 are equal across two runs of the script with the
    same seed; the report envelope is byte-identical after removing `cost.wall_ms`.
14. `summary` with gates touched: `GATE-ATEL-16 (prediction controls)`; the script records nothing.

**Logging.** `target/e2e-logs/predict_calibration/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`,
`script`, `bead` (`N28c-18`), `step`, `event`, exact command line, exit code, wall time, the envelope's `evidence`
block; `metric` lines: the measured `cot-elec` with unit and the registered intervals, hit or miss, score, window
hits against the band [20, 27], ledger sequence numbers of registration and first outcome; `refusal` lines for
the late registration and the key conflict, each with code, pointer and repairs; `digest`
fields for prediction hashes; on failure the first differing value and the ledger snapshot path. Final `summary`.

## Acceptance criteria

- [ ] The script exits 0 on a correct tree; non-zero with any planted defect below.
- [ ] A prediction registered after its outcome exists is refused (step 6), and a report scores every registered
      prediction, the failed ones included (step 7): the two conditions of the seed bead for the verbs, asserted
      from the user's side.
- [ ] Idempotency: replay returns the stored answer; key reuse with different content is `FROB-REF-803`, exit 7.
- [ ] Both step-2 and step-4 predictions are in the run's freeze set; the cancelled run's prediction is
      `no-outcome: cancelled` and counted in the denominator; registered = scored + unresolved + pending holds.
- [ ] Immutability: no command changes a registered prediction's bytes (hash before and after the run equal).
- [ ] Studio predictions precede their outcomes by ledger sequence; the saving prediction is scored at close.
- [ ] Hint appears at 17 of 30, not at 24 of 30, not at 29 scored; exit codes unchanged by the hint.
- [ ] DC-05 follows the fixed order at 17 of 30 and says why.
- [ ] Two prediction versions are reported separately after a refit.
- [ ] Log and transcript at the stated path, with the `summary` line.

## Test plan

### Unit tests

Helper tests in `cargo test -p frob-conformance --test e2e_scripts`: `sequence_order_checker` (fails when the
prediction's sequence number is above the first outcome's on a recorded ledger excerpt);
`accounting_identity_checker`; `hint_parser` (extracts hits and band from the `why` text).

### End-to-end script and logging

This bead is the script, as specified.

### Known answers and negative controls

- Known answers: the band at confidence 0.8 over 30 is 20 to 27 hits inclusive (cuts at 19 and 28; Binomial(30,
  0.8) tails 0.0256 and 0.0442); the fixture windows have 17, 24 and 29-scored states.
- Planted defects the script must catch (registered in `controls.toml` against GATE-ATEL-16, so the gate's tier
  run by its recorder N28b-28 includes them): a ledger that
  accepts a prediction after the outcome; a report that omits missed predictions; a register verb that hashes
  the prediction after the run starts; a studio hook that registers the saving at close; a monitor that pools
  prediction versions.
- Determinism lanes: twice on one machine; worker counts 1 and 36; debug and release.

## Considerations

- The metric must have a declared unit and span in the task definition; a prediction on an undeclared metric is
  a schema refusal and the script asserts it once.
- The run in step 5 is real (CPU tier, 64 worlds of a small design, under two minutes, TARGET); everything about
  calibration windows uses ledger snapshots labelled `synthetic`.
- Prediction content is not private-scene data, but the planned-run identifier may refer to a private scene; the
  log prints identifiers only.
