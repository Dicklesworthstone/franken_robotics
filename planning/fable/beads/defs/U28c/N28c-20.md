## Background

`frob report design <id>` writes an evidence package for a design: the design and its lineage, every analysis,
scorecards, comparisons with their verdicts, certificates, device receipts and replay addresses, as a directory
with an HTML index. `frob report campaign <id>` adds the phase ledger, the screening audit, the planted-winner
outcome and the list of fallbacks that fired. Registry facts: `report.design` is kind `read`, first milestone M3,
"the evidence package of a design"; `report.campaign` is kind `read`, M4, "a campaign's modes, fallbacks, audits
and phase ledger". The rules a reader relies on: a report is generated from the artifact graph and prints nothing
it cannot resolve; each statement carries its claim type, claim identifier, the boundary of its claim product (the
weakest input), the mode of every ladder rung that selected it, its rank-robustness type, its qualification
receipt if it has one, and the no-authorization flags; reports are deterministic (the same graph produces the same
bytes); a losing experiment is reported with the same completeness as a winning one.

Gate GATE-ATEL-16 (Known answer; M4): the cascade end to end on a seeded population: stage controls all run; the
report prints every mode, every fallback and the phase ledger; merge of two agents' archives in both orders gives
identical bytes. The cascade bead measures the gate as a whole, and its script's bead N28b-28 is the gate's one
recorder. This bead is the end-to-end script for the report capability at M4: it measures the report clause from
the user's side, on two campaigns chosen to stress honesty: one that ends with a ranked result and one that ends
"every admitted alternative fails". It writes no gate row.

## Scope

In: the script, its two campaign fixtures, assertions, logging, and the report clause's measured counts in the
script's log and summary (the evidence the gate's recorder reads beside its receipt; the script writes no row).
Out: the report implementation (BD-302, N28c-19); the cascade and its controls (BD-352); the M3 evidence-package
script that already covers `report.run` and `report.mission`.

## Technical approach

`scripts/e2e/report_campaign_atelier.sh`: plain shell over the real `frob` binary and a private `frobd`; sources
the STD-E2E helper; idempotent; seed-explicit.

Fixtures (under `conformance/campaigns/`):
- `win-27/`: 27 designs in three strata from the seeded cascade population, a budget that lets three finalists
  reach the referee, one stratum measured `selective`, one `discard-only`, one unmeasured; a planted winner whose
  identity is sealed in the manifest; one finalist built to be `model-conditional` (its advantage comes from
  diagonal traction on a pyramidal friction cone, up to √2·μ); one design flagged `controller-limited`.
- `lose-27/`: the same population against a requirement no design meets (payload doubled), so the campaign ends
  "every admitted alternative fails".
- `win-27-noplant/`: `win-27/` without the earlier specialist result that makes a planted winner eligible, so
  the stage-3 control cannot run (step 6).

Steps:
1. Run both campaigns: `frob opt cascade --spec conformance/campaigns/win-27/spec.toml --population win-27
   --budget … --seed 27 --key win27-1 --json` (and `lose-27`; the registry form of the verb, VERBS-opt: the
   brief by `--spec`, the 27 candidates by `--population`, an idempotency key), wait for completion; record
   campaign identifiers.
2. `frob report campaign <win-id> --json` → exit 0 or 2; read `report.json` from the returned package path.
3. Resolution: for every number in the campaign sections call `frob evidence trace <claim_id or evidence_id>
   --json` and assert a resolvable closure whose hashes recompute; count numbers printed and numbers resolved
   (must be equal).
4. Modes and fallbacks: assert `ladder_modes` has one row per (rung pair, stratum), with the three expected modes;
   force one fallback during the run (the fixture's manifest makes the `selective` stratum's audit set fall to
   18 designs in generation 2) and assert it appears in `fallbacks_fired` with core `dc-02`/`dc-03`, the trigger
   and count; assert the list equals `frob cores show dc-03 --decisions <win-id> --json`.
5. Phase ledger: present; exclusive phases sum to the campaign clock within 2%.
6. Stage controls: all six listed; in `win-27` all `passed`. The variant fixture `win-27-noplant/` (the same
   specification and population where no planted winner is eligible for the class: no earlier specialist result
   is on file, the fail-closed case of the screening audit, BD-345; `opt.cascade` has no option that removes a
   control) runs as the phase `noplant`, which the script invokes after step 13 as a run of its own
   (`--phase noplant`): `e2e_init` gives that run its own empty `FROB_STATE`, into which the fixture restores
   the specification and population and no specialist result. A run has one state root and `frob` has no
   `--root` option (STD-E2E's isolation rule), so emptying this run's root mid-script would lose the campaigns
   that steps 7 to 12 read. The phase asserts that stage 3 prints `not-run` with the reason and that finalists
   are described as "k survivors".
7. Wording: grep the HTML index and JSON of `win-27`: finalists from the `discard-only` and unmeasured strata are
   "survivors"; the phrase "top 3" does not appear; the `controller-limited` design's row contains the flag and
   none of the forbidden words; the `model-conditional` finalist shows both orders.
8. Refusals: `frob report campaign <win-id> --compact --json` (a mode that would drop condition columns) → exit 3
   with `FROB-REF-557`; `frob report campaign <win-id> --cite <proposal-id>` with an advisory identifier → exit 3
   with `FROB-REF-872`.
9. Losing campaign: `frob report campaign <lose-id> --json`; assert `ending ==
   "every-admitted-alternative-fails"`, the key set of its `report.json` equals that of `win-27`'s (structural
   diff empty), every discarded design has a replay address, and the screening audit and phase ledger are
   present.
10. Design report: `frob report design <a finalist> --json` and `<a discarded design> --json`; assert each
    statement has claim type, claim identifier, claim-product boundary naming the weakest input, the modes of
    the rungs that selected it, rank-robustness type, and the three no-authorization flags, all `false`.
11. Determinism: regenerate each package; compare package digests; repeat with the private daemon's worker pool
    configured to 1 and to 36 workers (BD-160's pool configuration, set when the script starts `frobd`; no
    report verb takes a worker option).
12. Authorization and reality: every package carries `execution_authorized: false`,
    `hardware_safety_signoff: false`, `sim_to_real_certified: false`, and every statement's `reality` is
    `no-claim`.
13. `summary`: assertions passed and failed; gates touched: `GATE-ATEL-16 (report clause)`.

**Logging.** `target/e2e-logs/report_campaign_atelier/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`,
`script`, `bead` (`N28c-20`), `step`, `event`, exact command line, exit code, wall time, the envelope's `evidence`
block (claim, class, tier, determinism, identities, seed); `metric` lines: numbers printed against numbers
resolved (threshold: equal), modes by kind, fallbacks listed against fallbacks recorded, phase-ledger closure
against 2%, section key-set difference (threshold 0); `refusal` lines with code, pointer and repairs; `digest`
fields with package digests for each regeneration; on failure the first number without a closure with its JSON
path, or the first differing byte offset between two packages, and the package paths. Final `summary`. Reports
over the fixtures contain no private-scene data, and the log prints digests, not payloads.

## Acceptance criteria

- [ ] The script exits 0 on a correct tree and non-zero with any planted defect below.
- [ ] 100% of numbers in the campaign sections resolve through `evidence.trace`.
- [ ] Every mode, every fallback and the phase ledger are printed for `win-27` (the report clause of
      GATE-ATEL-16); the measured counts are `metric` lines of the log and appear in the `summary`; the script
      writes no gate row (GATE-ATEL-16's one recorder is N28b-28).
- [ ] The `not-run` control, the "k survivors" wording, the `controller-limited` flag and the both-orders display
      are asserted.
- [ ] `FROB-REF-557` and `FROB-REF-872` fire on their planted requests.
- [ ] The losing campaign's report has the same key set and evidence links as the winning one.
- [ ] Package digests are identical across regenerations and worker counts.
- [ ] Log and transcript at the stated path with the `summary` line.

## Test plan

### Unit tests

The script's three checks that a shell script cannot make are script checks (STD-E2E: each a function in
`crates/frob-conformance/src/e2e/checks/<name>.rs`, registered in `checks/mod.rs`, standard library and the
tool's JSON reader only), called from the script with `e2e_check <name>`: `number-walk` (step 3: every numeric
leaf of `report.json` with its JSON path, the list the script resolves through `evidence.trace`), `key-set-diff`
(step 9: the structural difference of two `report.json` key sets) and `wording-scan` (step 7: the forbidden
words in the rows where they are forbidden). Their tests, in the target `e2e_scripts` (`cargo test -p
frob-conformance --test e2e_scripts`): `number_walk_finds_every_numeric_leaf` (a recorded `report.json` with
nested arrays); `key_set_diff_reports_added_key`; `wording_scan_flags_top3_and_inferior_in_right_rows` (detects
"top 3" and "inferior" in the rows where they are forbidden and nowhere else).

### End-to-end script and logging

This bead is the script, as specified.

### Known answers and negative controls

- Known answers: the screening-audit bound printed for 30 audited discards is 9.5% (KA-706); the
  `model-conditional` finalist is the one planted with the pyramidal-cone advantage (KA-692).
- Planted defects the script must catch (registered against GATE-ATEL-16): a generator that reads a number from a
  log line instead of the graph; an omitted `fallbacks_fired` section; a package that embeds its generation time;
  a losing-campaign report without discarded designs' replay addresses; a compact mode that drops conditions.
- Determinism lanes: twice on one machine; worker counts 1 and 36; debug and release; the Mac and the Linux host.

## Considerations

- The two campaigns are small (27 designs) so the script finishes in under 20 minutes on the CPU tier (TARGET);
  the full seeded population is exercised by the cascade's own gate run.
- The script runs the cascade for real: the cascade (BD-352) is a prerequisite through N28c-19, and no replay
  mode of `opt.cascade` is assumed. Step 11's regenerations read the same artifact graph, so the worker-count
  comparison is about report generation; the campaign itself is run once per fixture.
- The phase `sections` of this script belongs to N28c-19 and runs on its smaller committed campaign; this bead
  runs it as well and adds the gate-scale fixtures above.
- A report is evidence that a path runs and that numbers resolve; it is never evidence for the numbers
  themselves, which come from the gates that measured them.
