## Background

An edit to a design, a card, a scene or a mission puts stored evidence in question. The studio's answer is
revalidation: which verdicts survive, which are revoked, and what the cheapest set of reruns is.
`frob result revalidate <verdict or claim> --after-edit <edit>` returns the surviving obligations with the licence
for each, the invalidated regions, and the required reruns with their cost. The mission-query subsystem has its
own verb, `mission.revalidate`, with the same shape for a mission answer (surviving certificates, invalidated
regions, reruns and their cost after an edit). The plan specifies that the mission verb is the studio's engine
applied to a mission answer.

OPEN-ATEL-4 asks whether they stay two verbs over one engine or become one verb. Owner: Tether lead. It blocks the
verb registry freeze at M3. Default: two verbs, one engine. The register of open questions notes that this default
is confirmed by the gate register and is open only to new evidence. This bead records that outcome properly: an
ADR with the reasons and the rejected alternative, a registry test that the two verbs cannot diverge, and the
conditions under which the question would be reopened. Without the record, the freeze would proceed on an
unstated assumption and a later contributor could split the engine.

Reasons for two verbs (DESIGN): the inputs differ in kind (a stored verdict or claim identifier against a mission
answer identifier with cells and certificates); the outputs differ in vocabulary (obligations and licences
against cells and certificate bundles); an agent working in the mission cluster should not need to leave it; and
the verb registry lists `mission.revalidate` as "one engine with `result.revalidate`", so the surfaces already
promise the relation. Reasons against merging: one verb with a polymorphic input would need a union schema whose
refusal list is the union of both, and its MCP tool description would exceed what an agent reads reliably.
Rejected alternative: one verb `result.revalidate` taking either identifier kind. Tier: Solid [S].

## Scope

In: the ADR; the registry entries' cross-reference; the test that both verbs call one engine and agree; the
reopening conditions.
Out: the engine and its grades (the revalidation beads); the mission verb's own schema (the mission-query
subsystem).

## Technical approach

1. **ADR `docs/adr/OPEN-ATEL-4.md`.** States: two verbs, one engine; `result.revalidate` (kind `run`, first
   milestone M1 for the mission slice with dependency grades 1 and 2 on mission cells, full at M4);
   `mission.revalidate` (kind `run`, M4); both call `frob_opt::revalidate::Engine`; neither has logic of its own
   beyond translating its input to the engine's request and the engine's result to its output schema. The
   open-question register row is tombstoned with this ADR and keeps its identifier.
2. **Registry cross-reference.** Each verb's registry entry gains `same_engine_as = "<the other verb>"`; the
   generated documentation prints the relation; both entries list the refusal `FROB-REF-870` (reuse of a verdict
   with no licence, or under a rule the registry does not know).
3. **Agreement test.** For any mission answer A and edit e, let V be the set of stored verdicts underlying A's
   cells. Then `mission.revalidate A --after-edit e` and the union of `result.revalidate v --after-edit e` over v
   in V must give the same surviving set, the same licences (grade and rule), the same invalidated set and the
   same rerun list and cost. The conformance test runs this on the docking and stance fixtures and on the
   30-amendment campaign when it exists.
4. **Single-engine guard.** A layer and dependency test asserts that `mission.revalidate`'s executor depends on
   `frob_opt::revalidate` and contains no polarity rule table, no dependency-support logic and no cost model of
   its own (checked by forbidding those module names in the mission crate's revalidation path).
5. **Reopening conditions (the "new evidence" that would reopen the question).** Either: agents in the M4 mission
   session measurably pick the wrong one of the two verbs (more than one misuse per ten sessions in the
   fresh-agent tests); or the two verbs' refusal lists or schemas are found to have drifted in a release. Either
   triggers a new decision bead, not a silent merge.

## Acceptance criteria

- [ ] The ADR exists and is dated before the M3 verb registry freeze; the open-question row cites it.
- [ ] Both registry entries carry `same_engine_as`, list `FROB-REF-870`, and the generated documentation shows the
      relation.
- [ ] The agreement test passes on the mission fixtures available at M3 (dependency grades 1 and 2): identical
      surviving sets, licences, invalidated sets, rerun lists and costs.
- [ ] The single-engine guard fails on a planted copy of the polarity table inside the mission crate.
- [ ] The frozen registry at M3 contains both verbs with the kinds and first milestones stated above.

## Test plan

### Unit tests

`crates/frob-conformance/tests/revalidate_two_verbs.rs`: `same_engine_registry_field`;
`agreement_on_docking_fixture` (the four-state camera fixture: states initial, label renamed, delivery delayed to
tick 2, delivery delayed to tick 3 → both verbs report 2, 0, 0, 1 scene-pair evaluations and 1, 0, 0, 1 verdict
recomputations); `agreement_on_doorway_fixture` (widening the doorway: feasibility preserved, optimality revoked,
identically from both verbs); `refusal_870_from_both` (an unknown rule name); `no_second_engine` (guard).

### End-to-end script and logging

`scripts/e2e/revalidate_two_verbs.sh`: runs `frob mission revalidate a:<answer> --after-edit e:<edit> --json` and
the corresponding `frob result revalidate` calls on the fixtures, canonicalizes both outputs to the engine's
result form and compares digests. Logs through the STD-E2E helper under
`target/e2e-logs/revalidate_two_verbs/`: commands, exit codes, surviving and invalidated counts from each verb,
digests, the first differing obligation on failure, and a `summary`.

### Known answers and negative controls

- KA-699 (the four-state camera fixture: 2, 0, 0, 1 and 1, 0, 0, 1) and KA-700 (the doorway: the cost-9 cart
  stays feasible; its optimality is revoked).
- Negative control: a mission verb that keeps a stale promotion at the fourth camera state because its own key
  omits delivery time (a second engine in disguise) must fail the agreement test.

## Considerations

- The decision costs nothing to implement if recorded now, and is expensive to discover late: two engines would
  drift exactly on the rules where reuse is unsafe.
- KILL-REUSE and the mission subsystem's KILL-AUGUR-REUSE both fall back to the dependency-keyed engine; with one
  engine both fallbacks are the same code path.
