## Background

The design studio's cheap evaluation rungs score a robot body together with a controller of fixed competence, so
a design that needs more controller effort is under-scored. Controller-budget curves (a Frontier mechanism,
funded only if its pilot shows that rankings change with budget) measure each design at several controller
budgets on the same world addresses and extrapolate how much better it would do with more effort. The first
thing that mechanism needs is a way to say "the same controller, at budget level b" as part of a controller's
identity.

A `ControllerId` is the content hash of the controller class, the derived gains, the programs and their iteration
counts, the planning configuration, the compute-latency model (the delay from decision to command) and the
symmetry group actually used; invariant INV-REFLEX-02 requires it to cover everything that affects the
controller's output. The plan extends it: `ControllerId` gains a budget coordinate b on a registered ladder
b₀ < b₁ < b₂ with a scalar effort c(b). For the sampling-based predictive controller (kind `mpc-sample`),
c = N_s·N_it·H model steps per tick (N_s samples, N_it annealing iterations, H planning steps over the horizon),
with the default ladder N_s ∈ {64, 256, 1,024}. For a learned policy, c is the fine-tuning fraction of specialist
steps, default {0, 0.05, 0.2}, which are the first two policy rungs of the ladder already defined, plus one
dearer point. A row is keyed by (design, world address, budget). Every budget runs on the same addresses, so
differences across budgets are paired.

Ownership: the controller subsystem (`frob-control`) owns the budget coordinate; the studio (`frob-opt`) owns the
fit, the index and the escalation rule; rows are stored by the record subsystem. Design reason for a coordinate
instead of three unrelated controllers: pairing. Without a shared family identity, nothing says that the
controller at 256 samples is "the same controller with more effort" as the one at 64, and budget differences
could not be paired or keyed. Rejected alternative: a free numeric effort field on results (unregistered values
cannot be compared across designs, and a typo would silently create a fourth budget).

## Scope

In: the ladder registry and types; the split of a controller identity into family and budget; default ladders;
nesting of planner samples across levels; the verb options that select a level; validation.
Out: storing budget-keyed rows (N28c-34); the fit and saturation index (N28c-35); the interval (N28c-36); the
escalation rule (N28c-37); the comparison verb (N28c-38).

## Technical approach

Module `crates/frob-control/src/budget.rs`, behind the feature `frontier-budget-curve` (off by default).

1. **Types (DESIGN).**
   ```rust
   pub struct BudgetLadderId(DottedName);      // "mpc-sample.ns-x4", "policy.finetune"
   pub struct BudgetLadder {
       id: BudgetLadderId, kind: ControllerKind,
       levels: Vec<BudgetLevel>,               // strictly increasing effort; at least three
       constant_ratio: Option<Ratio>,          // Some(4) when c(b_{i+1})/c(b_i) is the same for all i
   }
   pub struct BudgetLevel { index: u8, effort: Ratio, params: LevelParams }
   pub enum LevelParams { MpcSample { n_s: u32, n_it: u32, h: u32 }, FineTune { fraction: Ratio } }
   pub struct ControllerBudget { ladder: BudgetLadderId, level: u8 }
   pub struct ControllerFamilyId(Blake3);      // the hash of everything in the controller except LevelParams
   // ControllerId = BLAKE3(ControllerFamilyId ‖ ControllerBudget ‖ LevelParams)
   ```
   Two controllers that differ only in budget level share a `ControllerFamilyId`. A controller with no ladder has
   `budget: None` and its identity is unchanged from before this bead (no existing identifier moves).
2. **Registry `registries/budget_ladders.toml`** with the defaults:
   - `mpc-sample.ns-x4`: N_s ∈ {64, 256, 1,024}, N_it and H taken from the controller family (for the published
     quadruped configuration N_it = 2, H = 16, so efforts are 2,048, 8,192 and 32,768 model steps per tick);
     `constant_ratio = 4`.
   - `policy.finetune`: fractions {0, 1/20, 1/5} of specialist steps; `constant_ratio = None`.
   - The pilot's ladder `mpc-sample.pilot`: N_s ∈ {32, 128, 512}.
   Validation at load: levels strictly increasing in effort; at least three; `constant_ratio` matches the
   levels; every effort is non-negative; a ladder used for curve fitting must have a strictly positive base
   effort (see Considerations for the learned-policy ladder).
3. **Nested samples.** The planner draws its perturbations from counter-based streams keyed by (world address,
   tick, iteration, sample index). The sample index runs 0..N_s, so the 64 samples at b₀ are the first 64 of the
   256 at b₁: budgets are nested by construction, which removes independent sampling noise from differences
   across budgets. This is asserted, not assumed: a test checks the first 64 perturbations at N_s = 256 equal
   those at N_s = 64 for the same address and tick.
4. **Same addresses across budgets.** A request for a budget sweep carries one address list; the dispatcher
   expands it to (design, address, level) triples. A sweep whose levels would run on different address sets is
   refused at planning (a schema refusal), because unpaired budget differences are what the mechanism must never
   compute.
5. **Surface.** `frob control mpc <design> --task T --ladder mpc-sample.ns-x4 --level 1 --json` (one level) and
   `--levels all` (the sweep); `frob control show <controller> --json` prints `family`, `budget { ladder, level,
   effort }`; fine-tuned policies report their fraction as a level of `policy.finetune` when they are produced
   by the family-policy fine-tuning verb. With a ladder, `--episodes n` is the number of world addresses, each run once per requested
   level. The screening rule of the sampling controller is unchanged and is N22a-24's rule 1: at most three per
   design by default, counted on the ledger per design and task. A sweep is counted by address, not by episode,
   because the efforts of the default ladder sum to 2,048 + 8,192 + 32,768 = 43,008 model steps per tick, below
   the 65,536 of the class's registered setting: three addresses through three levels are nine episodes that cost
   less than three registered ones (the 0.65 GPU-minutes of step 6 against 0.99), which is the plan's statement
   that such an escalation is "inside the three-episode screening allowance". The same holds for the pilot's
   ladder. A sweep over more than three addresses names a paired comparison (`--compare`) or a registered
   protocol (`--protocol`, as the pilot N28c-32 does for its eight addresses); a ladder whose efforts sum to more
   than the registered effort is counted by episode. Such episodes are never the scoring source of acceptance,
   promotion or qualification.
6. **Cost accounting.** Effort is reported with every result (`controller.effort_steps_per_tick` or
   `controller.finetune_fraction`), so that the studio can compute the cost of an escalation. Arithmetic the
   surface must reproduce: with cost proportional to the sample count and the published quadruped row (0.33
   GPU-minutes per 20 s episode at 2,048 samples), a design run through all three default levels on three
   addresses costs 3 × (64 + 256 + 1,024)/2,048 × 0.33 = 0.65 GPU-minutes (DESIGN arithmetic on a published
   FACT; the measured cost replaces it).

Determinism: identities are content hashes (D0). Episodes under a ladder level are class D2 on one backend.

## Acceptance criteria

- [ ] `registries/budget_ladders.toml` loads with the three ladders above; a ladder with non-increasing efforts,
      fewer than three levels or a wrong `constant_ratio` fails to load.
- [ ] Two `mpc-sample` controllers that differ only in N_s have equal `ControllerFamilyId` and different
      `ControllerId`; a controller without a ladder has the same `ControllerId` as before this change (checked
      against a pinned identifier fixture).
- [ ] INV-REFLEX-02 still holds: changing any of N_s, N_it, H, the latency model or the group changes the
      `ControllerId` (property test perturbing each field).
- [ ] Nested samples: the first 64 perturbations at N_s = 256 equal the 64 at N_s = 64, for 100 random
      (address, tick, iteration) triples.
- [ ] A sweep runs every level on the identical address list; a request with per-level address lists is refused.
- [ ] `--levels all --episodes 3` on the default ladder is admitted (three addresses, nine episodes, counted as
      three); `--episodes 4` with no exception is refused with the worded refusal `mpc-episode-cap` naming the
      count by address; with `--protocol <id>` of a registered protocol declaring eight addresses it is admitted.
- [ ] `frob control show` prints family, ladder, level and effort; results carry the effort field.
- [ ] The cost arithmetic 0.65 GPU-minutes for three addresses through three levels is reproduced by the cost
      helper from the published row.
- [ ] With the feature off, no ladder option is accepted and no identifier changes.

(0.6497 → 0.65); `zero_base_effort_flagged` (the fine-tune ladder loads but is marked `fit: unavailable (base
effort is zero)`).

### End-to-end script and logging

`scripts/e2e/budget_curve.sh`, phase `ladder`. The script is shared by the budget-curve beads and split into phases,
each runnable alone with `--phase <name>`; the first bead to land creates it from the STD-E2E template, and N28c-39
owns the whole run and the gate record. This phase lands with this bead: it loads `registries/budget_ladders.toml` and
a scratch copy with each of the three planted defects (non-increasing efforts, two levels, wrong `constant_ratio`),
each of which must fail to load; runs `frob control mpc quad-a --task flat-velocity --ladder mpc-sample.ns-x4 --levels
all --episodes 3 --key bc-ladder-1 --json` on the reference quadruped template; then `frob control show` for each
resulting controller, asserting one family identifier, three controller identifiers and efforts 2,048, 8,192 and
32,768; and asks for per-level address lists (refused). It sources the STD-E2E helper and writes
`target/e2e-logs/budget_curve/<utc-timestamp>.ndjson` with a transcript; every line has `ts`, `script`, `bead`
(`N28c-33`), `step` (`ladder`), `event`, the exact command line, exit code, wall time and the envelope's `evidence`
block; `digest` fields carry the three controller identifiers, the family identifier and the address-list digest per
level (asserted equal); `metric` lines carry each effort with unit `model-steps/tick` and expected value, and wall
time per level; `refusal` lines carry the code, pointer and repairs; on failure the registry or ladder path; a phase
`summary` line.

### Known answers and negative controls

- Known answers: efforts 2,048, 8,192 and 32,768 for the default sampling ladder at N_it = 2, H = 16; cost 0.65
  GPU-minutes for the three-address escalation.
- Negative controls: a planner whose sample streams are keyed by budget level (samples not nested; the prefix
  test fails); a sweep that redraws addresses per level; a ladder edited to four levels without a new ladder
  identifier (identifiers of existing rows would silently change meaning; the registry check fails it).
- Determinism lanes: identifiers equal on both hosts; sweep digests equal twice on one machine and across worker
  counts (D2).

## Considerations

- The learned-policy ladder's base level is a fine-tuning fraction of 0, and the curve law is written in the
  ratio c(b)/c(b₀), which is undefined at zero base effort; its levels are also not in a constant ratio, so the
  closed three-point form does not apply to it either. This bead registers the ladder so that rows can be keyed
  and paired, and marks it `fit: unavailable` until an owner decision supplies a positive effort scale for the
  zero-shot level (for example an effort offset representing the family prior). Until then designs on that
  ladder are treated as "fit refused", which the escalation rule already handles safely: they are treated as
  unsaturated and escalate, and the rule reduces to the fixed table.
- OPEN-ATEL-6 (whether 5% is the right second policy rung) can change the fractions of the learned-policy
  ladder; a change is a new ladder identifier, never an edit in place.
- OPEN-REFLEX-4 (whether screening by the sampling controller needs a 4 ms planning step) changes H and
  therefore effort; the ladder takes H from the controller family, so the effort ratio is unaffected.
- Results under the sampling controller carry `model-privileged` unless the planning model's parameters were
  drawn independently of the plant's randomization; the budget coordinate does not change that flag.
