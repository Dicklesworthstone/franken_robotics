## Background

Controller-budget curves are a Frontier mechanism of the design studio: each design is scored at several
controller budgets (for example the sampling controller at 64, 256 and 1,024 samples per tick) so that a design
which merely needs more controller effort is not mistaken for a worse body. The plan fixes the data model in one
sentence: a row is keyed by (design, world address, budget), and every budget runs on the same addresses, so
differences across budgets are paired. Rows are stored by the record subsystem (`frob-chronicle`, which owns the
ledger, the episode files and the memo store); the controller subsystem owns the budget coordinate; the studio
owns the fit.

Pairing is the whole point. The score of one design at one budget on one world is noisy; the difference between
two budgets on the same world, with nested planner samples, is far less so. A store that let budgets drift onto
different address sets, or that averaged before differencing, would hand the fit unpaired numbers and the fit
would report noise as curvature. This bead builds the table, its completeness rule and the two queries the fit
needs (paired increments and paired noise), and nothing else.

Design choice: a budget row is an index over ordinary episodes, not a new kind of measurement. An episode run
under a controller at budget level b is a normal episode whose identity includes that controller's identifier, so
it is memoized, replayable and counted like any other; the row adds the (family, ladder, level) coordinates that
make "the same design and world at another budget" a single lookup. Rejected alternative: a separate result
store for sweeps (a second copy of scores that could disagree with the episode record). Tier: Frontier [F],
behind a feature; the table is inert when the feature is off.

## Scope

In: the row schema and table; insertion from completed episodes; the completeness rule; the curve query; paired
increments; the paired-noise estimate; retention and pinning behaviour.
Out: the budget coordinate and ladders (N28c-33); the fit (N28c-35); intervals (N28c-36); verbs (N28c-38).

## Technical approach

Module `crates/frob-chronicle/src/budget_rows.rs`, feature `frontier-budget-curve`.

1. **Row (DESIGN), schema `frob.budget-row/1`.**
   ```rust
   pub struct BudgetRowKey { design: DesignId, world: WorldAddr, family: ControllerFamilyId,
                             ladder: BudgetLadderId, level: u8 }
   pub struct BudgetRow {
       key: BudgetRowKey,
       scope: RowScope,            // model, scene, task, metric, tier, kernel versions, effort profile, device family
       score: Score,               // the task's declared metric, with its declared span
       effort: Ratio,              // c(b), copied from the ladder level
       episode: EvidenceId,        // the episode this row indexes
       cost: Cost,                 // attributable device-seconds and core-seconds
   }
   ```
   Uniqueness: one row per key and scope. A second episode for the same key and scope is the same episode by
   identity (a memo hit), so insertion is idempotent.
2. **Insertion.** On completion of an episode whose controller has a budget coordinate, the publishing
   transaction that commits the episode's chunks also inserts the row; a failed or numerically invalid episode
   inserts a row with `score: Invalid` (it is not dropped: a missing level must be visible as missing).
3. **Completeness.** For (design, family, ladder, scope) the *address set at level i* is the set of worlds with a
   valid row. The curve is `complete` when the address sets of all levels are equal and non-empty. The query
   returns, for an incomplete curve, exactly which (world, level) cells are missing or invalid; the paired
   queries below use only the worlds present at every level and report how many were dropped.
4. **Curve query.** `curve(design, family, ladder, scope) -> Curve { levels: [LevelSummary], worlds_used, complete
   }` with `LevelSummary { level, effort, mean_score, n }`, means taken over the common worlds in world-address
   order.
5. **Paired increments.** For consecutive levels i, i + 1 and each common world w: δᵢ(w) = score(w, i + 1) −
   score(w, i). `increments(…)` returns the per-world vectors and their means Δ₁ = mean δ₀, Δ₂ = mean δ₁.
6. **Paired noise.** For each increment the standard error se(Δᵢ) = sd(δᵢ)/√n over the n common worlds; for the
   curvature test the standard error of Δ₂ − Δ₁ from the per-world differences δ₁(w) − δ₀(w). With n < 2 the
   noise is `undefined` and callers must treat the fit as refused. The noise is returned with its degrees of
   freedom, never as a bare number.
7. **Cross-design pairing.** `contrast(design_a, design_b, level, …)` returns the per-world paired difference of
   two designs at one level on their common worlds, used to detect crossings and to form the measured contrast at
   the highest budget reached (the only quantity that can later become `established`, through the ordinary
   comparison and promotion path).
8. **Retention.** Rows are small and derived; they are rebuilt from episodes if lost. Episodes that a live claim
   cites are pinned by the record subsystem as usual; a row whose episode was collected reports
   `evidence: unavailable` and is excluded from curves, with the exclusion counted.
9. **Layering.** `frob-opt` (lower in the layering than the record crate) reaches these queries through a trait
   it defines (`BudgetRows`), implemented here and wired in the verb layer.

Determinism: queries are pure functions of ledger rows at a pinned frontier, with sums taken in world-address
order (class D0 given the rows).

## Acceptance criteria

- [ ] A sweep of 3 levels × 8 worlds for one design yields 24 rows; re-running the sweep inserts none (idempotent)
      and serves the episodes from the memo graph.
- [ ] The curve query returns means equal to an independent computation on the fixture, with `complete: true`;
      removing one row makes `complete: false`, names the missing cell, and the paired queries use 7 worlds and
      report 1 dropped.
- [ ] Paired increments and their standard errors match hand-computed values on the fixture below.
- [ ] A failed episode appears as a row with `score: Invalid` and is reported, not silently skipped.
- [ ] Results are independent of insertion order and of completion order (replay under 100 schedules gives
      identical query outputs).
- [ ] The contrast query for two designs at one level uses only common worlds and states the count.
- [ ] With the feature off no row is written and the table is absent from the schema.

### Known answers and negative controls

- Known answer: the four-world fixture above reproduces the worked means 0.61, 0.70, 0.72 with increments 0.09
  and 0.02.
- Negative controls: a store that averages each level over its own address set before differencing (on a fixture
  where level 2 lost its hardest world, the unpaired increment is inflated; the test compares against the paired
  value and must fail the planted store); a store that drops invalid episodes (the completeness test fails).
- Determinism lanes: twice on one machine; worker counts 1 and 36; debug and release.

## Considerations

- Standard errors from three or eight worlds are rough; the fit's refusals are phrased in terms of this noise
  with its degrees of freedom, and the calibrated interval of the ceiling does not rely on it.
- Private scenes: rows carry identifiers and scores; logs print digests only.
- If the mechanism is killed, the table remains useful as the store behind the descriptive saturation index, or
  is simply left unbuilt with the feature off.
