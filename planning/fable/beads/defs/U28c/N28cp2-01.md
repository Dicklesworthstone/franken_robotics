## Background

A proof obligation is a statement that a mechanism's guarantee rests on, with the way it is discharged: a written
derivation, an exact enumeration, or a simulation with a stated acceptance bound. The design studio (Atelier)
states ten, PO-ATEL-01 to PO-ATEL-10. They fall due at different milestones: the fixed-n rule's coverage and the
analysis part of memoized evaluation at M1, the episode part of memoization at M2, the promotion table and the
greedy certificate at M3, the rest at M4.

Each decision core of the studio is a registry record (`registries/cores/dc-NN.toml`) that lists the obligations
its rule rests on, and the contract check refuses a record that names an obligation the obligations registry does
not hold. The first core records land at M3 (DC-01 cites PO-ATEL-01, DC-10 cites PO-ATEL-05). The bead that keeps
the obligations ledger (N28c-23: derivations, discharge records, the due-date check) lands at M4, when the last
obligations fall due. Without this bead the registry rows would not exist when the M3 check needs them, and the
obligations due at M1 to M3 would have no row to write their discharge into. This bead is the data entry that
comes first: the ten rows, entered `open`, with statement, mechanism, due milestones and acceptance bound, in the
one obligations file the chapters share. Registries come before the mechanisms and tests that cite them.

DESIGN, file and schema: the plan names no file for proof obligations. The Gauntlet's registries live in
`crates/frob-conformance/registry/` (`controls.toml`, `known_answers.toml`, `relations.toml`), so the obligations
file sits there, and it is one file for every chapter (the record, supply and learning chapters' obligation beads
N29b-16, N31b-02 and N23b-17 write their rows to the same path). Rejected: a file per chapter (a core record or a
gate row could then cite an obligation that another file holds, and no single check would see all rows);
`registries/obligations.toml` in the product's registry directory (the product never reads obligations; only the
conformance crate and the contract check do). Tier: Solid [S].

## Scope

In: `crates/frob-conformance/registry/obligations.toml` with its schema header (created here if no other chapter's
bead has landed first; otherwise the ten rows are appended); the ten PO-ATEL rows; the loader and the row checks;
the `obligations` subcommand of the conformance crate's example target `registry_report`; the end-to-end script.
Out: writing the six derivations, recording discharges and the due-date check `obligations_atelier` (N28c-23,
which depends on this bead and completes the rows); the mechanisms that discharge the obligations (named per
row); the contract check of core records (N28c-01, which reads the `id` values of this file); other chapters'
rows.

## Technical approach

1. **File and row schema** (TOML; one `[[obligation]]` table per row; the union of the fields the chapters use):

   | Field | Content |
   |---|---|
   | `id` | `PO-<CHAPTER>-NN`, unique in the file |
   | `statement` | the obligation, one sentence |
   | `mechanism` | the bead keys of the mechanism it constrains |
   | `derivation` | path of the written derivation, or `none` |
   | `discharge` | the test names and the acceptance bound, with its numbers |
   | `due` | a milestone (`"M3"`), or for an obligation due in parts an array of `{ milestone, part }` |
   | `status` | `open`, `derivation-on-file`, `discharged` or `failed` |
   | `record` | path of a separate discharge record where a chapter keeps one, else `none` |
   | `claim_ids` | claim identifiers of the discharging runs (empty until discharged) |
   | `gate` | the gate that names the obligation, or empty |
   | `recorded_by` | the session that recorded the discharge (empty until then) |

2. **The ten rows**, entered with `status = "open"`, `record = "none"`, `claim_ids = []`, `recorded_by = ""`:

   | `id` | `statement` | `derivation` | `discharge` (acceptance bound) | `mechanism` | `due` | `gate` |
   |---|---|---|---|---|---|---|
   | PO-ATEL-01 | The DC-01 table keeps wrong promotion at most α⁺ and wrong rejection at most α⁻ under optional stopping | `docs/proofs/atelier/PO-ATEL-01.md` | 10⁴ null runs at p₁ and at p₀ with optional stopping: wrong promotions at most 132 of 10⁴ at α⁺ = 0.01, wrong rejections at most 569 of 10⁴ at α⁻ = 0.05 (exact binomial acceptance counts at test level 0.001); the table regenerated in CI and diffed | BD-309 | M3 | GATE-ATEL-13 |

   The six derivation paths are entered now and the files are written by N28c-23; until a file exists the row
   stays `open` (a row is `derivation-on-file` only when its path resolves).
3. **Loader and checks** (`frob_conformance::obligations`, test target `obligations_registry`): every row has the
   eleven fields; `id` is unique in the file and matches `PO-[A-Z]+-[0-9]{2}`; `status` is one of the four
   values; each `due` milestone is one of M0 to M8; a `discharged` row has at least one claim identifier; a
   `derivation-on-file` or `discharged` row whose `derivation` is a path has that file; `gate` is empty or a
   well-formed gate identifier (its resolution against `registries/gates.toml`, and the due-date rule, are the
   ledger check of N28c-23). The test pins the ten identifiers and their bounds, so a deleted or edited row
   fails.
4. **What the contract check reads.** `xtask check-contracts` (N28c-01) reads this file by path as plain TOML
   and takes the `id` values; it does not link the conformance crate. A core record that cites an identifier
   absent from the file fails that check, naming the identifier.
5. **Report.** `cargo run -p frob-conformance --example registry_report -- obligations --chapter 28 --json`
   prints one JSON object with, per row, every field above. The conformance crate has no binary, verb or
   `xtask` subcommand (ADR-GAUNT-01, BD-025); its registry reports are subcommands of the example target
   `crates/frob-conformance/examples/registry_report.rs` (N28-CX adds `controls`; whichever bead lands first
   creates the file).

Determinism class D0. No claim is produced: an obligation's discharge is a claim of its owner's run.

## Test plan

### Unit tests

`crates/frob-conformance/tests/obligations_registry.rs` (the committed file; planted registries are scratch
copies labelled `synthetic`): `ten_atelier_rows` (the ten identifiers, each `open`); `fields_complete` (a row
without `due` fails, naming the field); `ids_unique` (a duplicated `PO-ATEL-03` fails); `status_closed_set`
(`status = "done"` fails); `discharged_needs_claim` (a `discharged` row with `claim_ids = []` fails);
`derivation_on_file_needs_file`; `due_in_parts` (PO-ATEL-06 has two parts at M3 and M4, PO-ATEL-07 at M1 and
M2); `id_lookup` (`PO-ATEL-01` found, `PO-ATEL-11` not); `bounds_recompute` (the exact binomial acceptance
counts: the smallest c with P(X > c) ≤ 0.001 is 132 for Binomial(10⁴, 0.01), 569 for Binomial(10⁴, 0.05) and 42
for Binomial(512, 0.05); C(66, 2) = 2,145; C(88, 2) = 3,828; the root of 39x³⁸ − 38x³⁹ = 0.05 is 0.8840).

### End-to-end script and logging

`scripts/e2e/registry_n28_po.sh` (idempotent; no seed needed; it needs no Atelier mechanism, so it passes at this
bead's close): `cargo test -p frob-conformance --test obligations_registry`; `cargo run -p frob-conformance
--example registry_report -- obligations --chapter 28 --json`, asserting ten rows, all `open`, the dues M1, M3, M4
and the two rows due in parts, and the six derivation paths; then, on scratch copies of the file under
`target/e2e-scratch/registry_n28_po/` (never the committed file), four planted defects one at a time, each
rejected by the named test: a row deleted; a duplicated identifier; a `discharged` row with no claim identifier;
the bound of PO-ATEL-01 changed from 132 to 123. It sources the STD-E2E helper and writes
`target/e2e-logs/registry_n28_po/<utc-timestamp>.ndjson` with a transcript; every line has `ts`, `script`, `bead`
(`N28cp2-01`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `end`), the exact command line, exit code,
wall time and the evidence block (class Tested, determinism D0); `metric` lines carry the row count against 10
and the counts by status and by due milestone; per planted defect an `assert` with the expected and observed
failing test; on failure the first missing or differing row with the scratch path; a final `summary` line.

### Known answers and negative controls

- Known answers: the recomputed bounds above (132, 569, 42; 2,145 and 3,828; 0.8840).
- Negative controls: the four planted defects of the script; a second obligations file at
  `registries/obligations.toml` (the source scan must fail).
- Determinism lanes: the file's loader output and the report are byte-identical twice on one machine, in debug
  and release, and on both hosts.

## Considerations

- The file is shared by several chapters and by beads that land in parallel: rows are appended, never
  reordered, and the uniqueness check is over the whole file, so two chapters cannot take one identifier.
- Other chapters' beads drafted different row shapes for the same purpose; the schema here is the union that
  the record chapter's bead N29b-16 proposed, and a chapter that needs a further field adds it for every row
  with a default, in the same change as the loader.
- A status is a statement about evidence: only the bead that records a discharge sets `discharged`, with the
  claim identifiers of the run. This bead enters every row `open` and discharges nothing.
- Risk: a row whose bound drifts from the mechanism bead that tests it. The test pins the numbers, and N28c-23's
  table repeats them; a change to a bound is a change to both in one commit.
