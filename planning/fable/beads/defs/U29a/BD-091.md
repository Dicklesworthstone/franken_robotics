## Background

A simulation worker produces telemetry for thousands of worlds and must hand it to the record while crashes,
retries, device losses and re-sharding happen around it. The record must end up with each piece of each world's
history exactly once, in order, with no hole, whatever happened. The chunk protocol is the rule that achieves
this. It belongs to Chronicle, the record subsystem (crate `frob-chronicle`, tier Solid), and this bead builds
it on the CPU at milestone M1, where the only workers are the referee and in-process runners; the device
workers reuse it unchanged at M2.

A world's record is published in fixed logical chunks. Chunk i of episode e of world w on stream s covers
control ticks [i·L, (i + 1)·L), cut short only by the episode's terminal tick. L is fixed for the run at
admission (default 256). The key `(run, world, episode, stream, index)` names no device, shard, batch slot or
retry.

Decisions that govern the bead, with the alternatives they reject:
- **ADR-CHRON-02: the logical chunk partition is fixed per run and independent of device sharding.** Rejected:
  chunks keyed by the tick range a worker happened to produce. Counterexample: a retry splits a shard, and
  ranges [0, 100) and [50, 150) both cover ticks 50 to 99; with range keys both commit. With a fixed partition
  identical work always has an identical key, so a duplicate is detectable and a conflict is provable.
- **The episode index is part of the key.** Rejected: a key of (world, tick). Counterexample: a reset reuses
  tick zero and the second episode overwrites the first.
- **Publishing is one ledger transaction that does five things or nothing.** Rejected: write the file, then
  insert the row, then advance the frontier as separate steps; a crash between any two leaves a hole or a
  phantom.
- **A fencing token, not a lock.** A lock held by a stalled worker blocks everyone or expires while the worker
  still believes it holds it; a generation number checked inside the commit cannot be violated by a late writer.

Seed done-condition: the CPU rows of GATE-CHRON-04.

## Scope

In: the lease generation and its manager interface; the publishing transaction; the receipt; duplicate and
conflict handling; the terminal-tick rule; the run state `determinism-violated`; the three refusals; property
tests of the invariants.
Out: pinned pagination (N29a-04); stopping and terminal receipts (N29a-05); the gate's 10⁵-schedule battery and
planted violations (N29a-06); the asynchronous submit path under the lab runtime (BD-096); device workers,

latch that the quarantine row sets (N28b-38, which depends on this bead); the decisions on the chunk length L

bead is built on their defaults (L = 256 control ticks; one lease generation per run), and the gate rows
(N29a-06 on the CPU, N29a-24 on devices) wait for the decisions.

## Technical approach

**Types (DESIGN: intent, not signatures; the record fields are normative).**

```rust
struct ChunkKey { run: RunId, world: u32, episode: u32, stream: StreamId, index: u32 }
struct ChunkRecord {
    key: ChunkKey,
    content: Blake3,     // hash of the column file bytes
    prev: Blake3,        // chain digest of chunk index − 1; zero for index 0
    chain: Blake3,       // H(prev ‖ content ‖ key)
    state_digest: u128,  // in-kernel digest of the world's state at the chunk's last tick
    lease_gen: u64,      // fencing token of the writer
    commit_seq: u64,     // assigned inside the publishing transaction; a string on the wire
    gaps: Vec<Gap>,      // dropped intervals, each with a reason
}
struct Lease   { run: RunId, gen: u64, holder: WorkerId }
struct Receipt { key: ChunkKey, chain: Blake3, commit_seq: u64 }
enum Published { Committed(Receipt), Duplicate(Receipt) }      // Duplicate carries the original receipt
```

**What `state_digest` holds (DESIGN; the plan types it `u128` and defines the referee's state digest at M1 as a
32-byte BLAKE3).** The run manifest fixes a `digest_kind` for the run: `mix128` on the batched tiers (the
in-kernel 128-bit integer mix, M2) or `blake3-128` on the referee (the first 16 bytes, read little-endian, of the
32-byte BLAKE3 of the canonical referee-state byte string; the full 32 bytes are kept in the chunk's T0 row).
Digests of different kinds are never compared: a comparison across kinds is a tolerance or decision comparison,
never "equal" or "different" on digests. The transaction stores `state_digest` as given and does not interpret
it.

**Lease generation.** The `run` row holds `lease_gen`. `reassign(run)` increments it; it is called by whoever
assigns worlds to workers whenever the assignment changes: a retry, a shard split, a device loss. Every older
writer is thereby fenced out. `renew(lease)` returns a lease at the current generation if the holder is still
assigned; a healthy writer calls it at each chunk boundary before publishing. Default granularity: one
generation per run.

**`publish(lease, request)` is one ledger transaction.** The request carries the key, the tick range, a flag
`terminal`, the content hash of an already written column file, `prev`, `state_digest` and the gaps.

1. *Lease.* `lease.gen` must equal the run's current `lease_gen`. Otherwise refuse with FROB-REF-875 (a publish
   under a late lease; repair: re-acquire, then replay from the last committed tick). Nothing is written.
2. *Alignment.* The tick range must be exactly [i·L, (i + 1)·L), or [i·L, T) with T < (i + 1)·L and `terminal`
   set. Anything else is FROB-REF-885 (a chunk that is not a partition extent), so partially overlapping ranges
   cannot be committed. The first terminal chunk of an episode records the episode's terminal tick in the same
   transaction; a terminal chunk of another stream of that episode must end at the same tick.
3. *Duplicate or conflict* (key at or below the frontier of its (run, world, episode, stream)). Same content
   hash: return `Duplicate` with the original receipt; no row is written. Different bytes: mark the run
   `determinism-violated`, insert a quarantine row naming the run's node kinds so that serving from the memo
   graph stops for them, and refuse with FROB-REF-878 (different bytes for a committed chunk key; repair: stop
   the run and file the determinism violation with both hashes). The marking commits; the chunk does not.
4. *Predecessor* (key above the frontier). `index` must be the frontier plus one (0 when nothing is committed),
   `prev` must equal the chain digest at the frontier (32 zero bytes for index 0), and the sequence must not be
   closed by a terminal chunk. Otherwise FROB-REF-885 (predecessor is not the frontier; repair: publish in order
   on the fixed partition).
5. *Commit.* Compute `chain = BLAKE3(prev ‖ content ‖ key bytes)` (key bytes: the 32-byte run identity, then
   world, episode, stream and index as little-endian 32-bit integers); insert the row; advance the frontier to
   (index, chain); set `commit_seq` to the run's counter plus one and store the counter.

Steps 3 and 4 read the frontier row once; which of the two applies is decided by comparing `index` with it. The
column file is written to the content-addressed store before the transaction; a file whose row never commits is
an unattached object that restart ignores and retention sweeps.

**Three properties that follow.** (a) *Contiguous frontier:* for every (world, episode, stream) the committed
chunks are exactly indices 0 to the frontier. (b) *No collision at reset:* an episode that reuses tick zero has
a different key. (c) *A crash after commit and before the receipt reaches the writer is harmless:* the retry
finds the key committed with the same hash and gets the original receipt.

**Exit codes.** These refusals reach a worker, not an agent. The refusal registry (N29-REF) is the authority
for their exit codes: to a direct caller of the publishing interface 875 is exit 7 (DESIGN: a conflict with a
newer assignment), 885 is exit 3 and 878 is exit 9. Inside a job, 875 and 885 are recovered by the worker and
do not change the job's exit; 878 fails the job as indeterminate, and the surface reports the chunk conflict
with exit 9 (integrity), carrying 878 with both hashes as the cause.

**Layout.** `crates/frob-chronicle/src/{lease.rs, publish.rs, frontier.rs}`; `CONTRACT.md` gains the
transaction, the three properties and the refusals.

## Acceptance criteria

- [ ] Seed done-condition, with N29a-06: the CPU rows of GATE-CHRON-04 (TARGET): under 10⁵ seeded fault
      schedules the invariants INV-CHRON-01 to -04 hold in every one, and each planted violation (late lease,
      overlap, conflict, tick-zero reuse) is refused 100 of 100. This bead supplies the mechanism and its
      property tests; N29a-06 records the gate.
- [ ] Two identical publishes yield one row and one receipt (the second returns the first's).
- [ ] A crash injected at each of the transaction's statements leaves either the whole chunk committed or
      nothing; a retry after a crash following the commit returns the original receipt.
- [ ] A publish under a superseded generation writes nothing and returns FROB-REF-875.
- [ ] Ranges [0, 100) and [50, 150) at L = 256 are both refused with FROB-REF-885; index 2 published before
      index 1 is refused with FROB-REF-885.
- [ ] Different bytes for a committed key return FROB-REF-878 with both hashes, the run is marked
      `determinism-violated`, and the stored row is unchanged.
- [ ] Episode 1 of a world publishing its chunk 0 at tick zero does not touch episode 0's rows.
- [ ] `commit_seq` is strictly increasing per run and is a string in every JSON view.

## Test plan

### Unit tests

`cargo test -p frob-chronicle publish`:
- `publish_in_order_advances_frontier`: 3 worlds × 2 streams × 5 chunks; frontier 4 everywhere; chains verify.
- `duplicate_returns_original_receipt` (KA-711): same key and hash twice; one row; equal receipts.
- `crash_after_commit_then_retry` (KA-711): the receipt is dropped; the retry gets the same `commit_seq`.
- `crash_at_every_statement`: a fault injected before each ledger statement of the transaction, 100 seeds each;
  after recovery the row and the frontier are both present or both absent.
- `late_lease_refused_875`: `reassign` between `renew` and `publish`; no row; code 875.
- `healthy_writer_renews`: after a `reassign` that keeps a worker's worlds, its next `renew` succeeds and its
  publish commits.
- `non_extent_refused_885`: [0, 100) and [50, 150); `short_chunk_needs_terminal`: [0, 188) without the flag is
  refused, with it accepted and the sequence closed; a later index is then refused.
- `out_of_order_refused_885`; `wrong_prev_refused_885`.
- `conflict_marks_run_878`: both hashes in the refusal; run state; quarantine row present.
- `conflict_surfaces_as_810`: the 878 refusal value carries both hashes and resolves, through the registry row's
  `surfaces_as`, to FROB-REF-810 with exit 9 and retry `never`, so the job layer (BD-210) reports 810 with 878
  as its cause.
- `reset_reuses_tick_zero_no_collision`.
- `terminal_tick_agrees_across_streams`: a second stream ending at another tick is refused.
- Property `inv_chron_01_02`: for random sequences of publishes, duplicates, conflicts and reassignments by up
  to four writers (10⁴ cases), INV-CHRON-01 (a committed chunk key maps to one content hash for the life of the
  run) and INV-CHRON-02 (committed chunks are exactly the indices 0 to the frontier) hold after every operation.

### End-to-end script and logging

`scripts/e2e/chronicle_chunk_protocol.sh` (owned by N29a-06) drives a real referee run that publishes through
this transaction and replays the planted violations through the conformance harness; this bead's part is the
step group `publish-*`, whose lines carry the chunk key, the receipt, the frontier before and after, the lease
generation and, for a refusal, the code and both hashes.

### Known answers and negative controls

- KA-711: two identical publishes yield one row and one receipt; a crash after commit returns the original
  receipt. Negative controls: a late lease that writes; overlapping ranges that commit; a reset at tick zero
  that collides. Each is a mutant kept in the test tree (the lease check removed; alignment relaxed to "starts
  on a multiple of L"; the key without the episode index) that the tests above must fail.
- PO-CHRON-01 (the publishing transaction preserves INV-CHRON-01 to -03 under every fault of the simulation
  testing fault menu): discharged by deterministic simulation over 10⁵ schedules (N29a-06, BD-096), every
  failing schedule minimized and kept.
- Determinism: the chain and receipts are a pure function of the published content and order; the property test
  is run twice, in debug and release, and across worker counts.

## Considerations

- The lease check runs first even for a duplicate: a stale writer learns nothing from the store until it has
  re-acquired. A writer that crashed after a commit re-acquires and then receives its original receipt.
- The surface chapter describes the same event as "chunk conflict: different bytes for a committed extent"
  under its own code (810, exit 9), and says the surface owns leases and the publishing transaction. This bead
  places the transaction in the store, where its invariants are tested, and has the job engine call it; the
  store-level cause is 878. The division is recorded in the registries (DESIGN, N29-REF and N32-REF): 878 is the
  store's refusal to the publishing worker and its record of the conflicting key, with `surfaces_as =
  "FROB-REF-810"`; what the job and its caller see is 810, exit 9, with 878 and both hashes as its cause. A unit
  test (`conflict_surfaces_as_810`, below) checks that the surface mapping holds.
- OPEN-CHRON-2 (owner: Chronicle lead): L. Default 256 control ticks, a manifest field. OPEN-CHRON-5 (owner:
  Tether lead): lease granularity. Default one generation per run; a per-shard generation would let a healthy
  shard keep publishing through another shard's reassignment, at the price of a versioned world-to-shard map
  inside the transaction.
- The job ledger has a single writer (the daemon), because the engine's concurrent-writer mode is reported to
  have a snapshot-drift defect; the transaction does not rely on concurrent writers.
- Performance: one transaction per chunk per stream; at L = 256 and 50 Hz control that is one publish per
  (world, stream) every 5.12 s. Batching several chunks into one transaction is allowed as long as each chunk's
  five checks are applied in index order inside it.
