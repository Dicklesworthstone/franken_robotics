## Background

The system prints many statements to agents: "this design beats that one", "this gate passed", "this kernel
matches its oracle". Each is only as good as what supports it, and an optimizing agent will happily cite a
number whose support has been deleted, was produced by a different rule than it believes, or never existed. The
record subsystem (Chronicle) therefore keeps a graph that ties every claim to its evidence, to the version of
the rule that decided it, and to the executions that produced it, and it enforces one decision:

**ADR-CHRON-07: no claim without a trace.** Every claim that crosses the agent boundary has a `claim_id` that
resolves to evidence, to the version of the rule that decided it and to the executions that produced it. A
claim that does not resolve is not printed.

Four kinds of identifier do the tying:

```
ClaimId            BLAKE3( claim type ‖ subject identities ‖ statement ‖ scope )
EvidenceId         BLAKE3( kind ‖ payload hash )
                   kinds: episode set · chunk range · snapshot · certificate · receipt · ledger row · analysis result
DecisionPolicyId   ( dotted rule name, version )        e.g. ("atelier.dc01.promote", 3)
TraceId            128-bit, time-ordered identifier of the execution that produced an evidence item

edges   claim ──supported-by──► evidence          claim ──decided-by──► decision policy
        evidence ──produced-by──► trace            evidence ──derived-from──► evidence
        claim ──depends-on──► claim               (the weakest input bounds the claim)
```

FACT: the suite's async runtime ships a small kernel crate (`asupersync/franken_kernel/src/lib.rs`) that
defines `TraceId`, `DecisionId` and a `PolicyId` made of a dotted name and a version. That `PolicyId` names a
decision rule, while this project's `PolicyId` names a control policy by content hash. The decision-rule
identifier is therefore called `DecisionPolicyId` throughout, whichever crate supplies the type.

Rejected alternatives: provenance as free-text fields on results (cannot be checked or pinned); hashing the
execution into the evidence identifier (two runs of the same work would then be different evidence, and
reproduction could never be recognized). Seed done-condition: GATE-CHRON-10.

## Scope

In: the identifier types and their canonical encodings; the `claim`, `evidence` and `edge` tables' semantics;
recording functions; the closure algorithm; resolution and the `unavailable` state; the build-time check of the
gate registry and demonstration manifests; the verb `evidence.trace`.
Out: the per-bead log (N29a-09); the gate measurement and its script (N29a-10); retention and pins (BD-209);
reports generated from the graph (the report verbs); the claim-product arithmetic (the core types bead).

## Technical approach

**1. Identifiers (in `frob-core`, layer 0, by the default of OPEN-CHRON-3).**
- `ClaimId` = BLAKE3 over the domain tag `frob.claim/1`, a zero byte, and the canonical JSON of
  `{type, subjects, statement, scope}`: `type` is one of the seven claim kinds (`proof`, `known-answer`,
  `parity`, `fidelity`, `design-comparison`, `reality`, `performance`); `subjects` is the sorted list of content
  identities the claim is about; `statement` is the structured statement (a verdict record, a gate identifier
  with its threshold, a known-answer row), never prose; `scope` names the world family, tier and battery.
- `EvidenceId` = BLAKE3 over the kind tag (one byte, 1 to 7 in the order listed above) and the 32-byte payload
  hash. The payload hash is the content hash of what the evidence *is*: a sorted list of episode identities, a
  chunk range's chain head, a snapshot's content hash, a certificate bundle hash, a receipt hash, the canonical
  bytes of a ledger row, the canonical bytes of an analysis result.
- `DecisionPolicyId { name: DottedName, version: u32 }`.
- `TraceId(u128)`: 48 bits of milliseconds since the epoch followed by 80 random bits. **Trace identifiers and
  wall-clock times identify executions; they never enter a content hash**, so two executions of the same work
  produce the same evidence identifiers and different traces. The hasher's input trait is not implemented for
  `TraceId` or for time types.

**2. Recording.** `Graph::record_evidence(kind, payload, produced_by: TraceId, derived_from: &[EvidenceId])`
inserts the node and its edges idempotently (the same evidence from a second execution adds a second
`produced-by` edge and nothing else). `Graph::record_claim(claim, supported_by, decided_by, depends_on)` inserts
the claim; it refuses a claim with no `supported-by` edge and a claim whose evidence class exceeds the weakest
class in its support and dependencies. Both run inside the caller's ledger transaction through Chronicle's
writer handle, so a verdict and its claim commit together.

**3. Closure.** `closure(claim)`:
1. Start a work list with the claim; keep a visited set.
2. For a claim: collect its `decided-by` policies; push its `supported-by` evidence and its `depends-on` claims.
3. For an evidence item: collect its `produced-by` traces; push its `derived-from` evidence.
4. For every visited node check: the row exists (else *dangling*); no tombstone names its payload (else
   *tombstoned*).
5. Return nodes, edges, policies, traces and the lists of dangling and tombstoned nodes. Traversal order is by
   identifier bytes, so the output is canonical. Cycles cannot arise in `derived-from` or `depends-on`
   (identifiers are content hashes of their inputs), and the visited set makes the algorithm safe if one is
   ever planted.

**4. Resolution rule.** A claim *resolves* when its closure has no dangling and no tombstoned node. A claim
that does not resolve prints `evidence: unavailable` and cannot be cited: any verb asked to cite it refuses
with FROB-REF-869 (citing a claim whose evidence closure is dangling or tombstoned; repair: re-run the
evidence, the tombstone names what is missing; exit 3).

**5. Rules at the boundary.** An envelope that carries a claim carries its `claim_id` in `evidence.claims`. Each
row of `registries/gates.toml` with a recorded PASS lists the `claim_id`s the PASS rests on. Each demonstration
manifest lists the claims it supports with commands that run in under 60 s. The generated-artifact check
(`xtask check-generated`, extended here, no new tool) loads the graph export committed with the registry
(`registries/graph/claims.ndjson`, canonical) and fails the build if a listed identifier is absent or dangling.

**6. The verb `evidence.trace`** (read; M1; capability `evidence:read`; schema `frob.evidence.trace/1`).
`frob evidence trace <claim_id> [--verify] [--depth n] [--budget tokens] --json`. Output: the claim (type,
subjects, statement, scope, class), `resolved`, the evidence items (kind, payload hash, where it is stored),
the rule versions that decided, the executions (trace identifier, commit, host fingerprint, start instant), the
claims it depends on, and `unavailable` with each tombstone's class, time and reason. With `--verify` every
payload still stored is re-hashed and compared with its `EvidenceId`, and the `ClaimId` is recomputed from the
stored fields; a mismatch is an integrity fault (exit 9). Exit 0 when resolved; exit 2 when not (a finding).
Long closures are paged against the committed frontier.

**7. Layout.** `crates/frob-core/src/ids/graph.rs`; `crates/frob-chronicle/src/graph/{record.rs, closure.rs,
export.rs}`; `crates/frob-verbs/src/verbs/evidence_trace.rs`.

## Acceptance criteria

- [ ] Seed done-condition, with N29a-10: GATE-CHRON-10 (TARGET): every row of `registries/gates.toml` with a
      PASS resolves; a dangling identifier fails the build; `evidence.trace` on 100 random claims returns
      closures whose hashes recompute.
- [ ] INV-CHRON-10: every printed claim resolves in the artifact graph, and no trace identifier or wall-clock
      time enters a content hash (compile-fail test on the hasher; a run executed twice yields equal
      `EvidenceId`s and two traces).
- [ ] A claim recorded without support is refused; a claim whose class exceeds its weakest input is refused.
- [ ] Deleting one evidence row, or adding a tombstone for one payload, makes every claim that reaches it print
      `evidence: unavailable`, and citing it returns FROB-REF-869 with the missing node named.
- [ ] `evidence.trace --verify` detects one flipped byte in a stored payload (exit 9).
- [ ] The closure output is byte-identical on repeat and independent of insertion order.
- [ ] The verb is reachable through `frob --json` and MCP (`evidence_trace`).

## Test plan

### Unit tests

- `claim_id_canonical`: reordering `subjects` in the input or reformatting the statement's JSON does not change
  the identifier; changing the scope does.
- `evidence_id_ignores_execution`: the same payload recorded under two traces has one `EvidenceId` and two
  `produced-by` edges.
- `hasher_rejects_trace_and_time` (compile-fail).
- `closure_small_graph`: claim C supported by E1, E2; E2 derived from E3; C depends on C′ supported by E4;
  decided by ("atelier.dc01.promote", 3): the closure has 2 claims, 4 evidence items, 1 policy and the traces
  of each item.
- `closure_canonical_order`: 100 random insertion orders, equal bytes.
- `dangling_detected`, `tombstoned_detected`, `cite_unavailable_869`.
- `weakest_input_bounds_claim`: a claim of class `Certified` over an `Estimated` input is refused.
- `claim_without_support_refused`.
- `planted_cycle_terminates`.
- `verify_detects_flip`.
- `check_generated_fails_on_dangling_gate_row` (a planted identifier in a scratch registry).

### End-to-end script and logging

`scripts/e2e/evidence_trace.sh` (owned by N29a-10): record a known-answer result from a real referee run, read
its `claim_id` from the envelope, run `frob evidence trace <claim_id> --verify --json`, then tombstone one
chunk through the conformance harness and observe `unavailable` and FROB-REF-869. This bead's step group is
`graph-*`; its lines carry the claim identifier, node and edge counts, each recomputed hash against its
identifier, and the frontier.

### Known answers and negative controls

- KA-720: every gate row resolves to evidence and traces. Negative control: a claim printed after its evidence
  was collected (the tombstone case above; a mutant that skips the tombstone check must be caught).
- Negative controls: an evidence identifier that includes the trace (two executions then disagree; caught by
  `evidence_id_ignores_execution`); a closure that follows only `supported-by` (misses a tombstone behind a
  `derived-from` edge).
- Determinism: closure bytes on repeat, across platforms and in debug and release (class D0).

## Considerations

- OPEN-CHRON-3 (owner: suite lead): importing the identifier types would add the suite kernel to layer 0; the
  default keeps them local with the same layout so a later import is a type alias and no stored byte changes.
- RISK-39 (retention deletes the interval that explains a decision) is detected here (an unresolved closure)
  and prevented by the retention bead's pins.
- The graph export in the repository holds identifiers and edges only, never payloads; payloads stay in the
  store, so a fresh clone can check registry rows for dangling references without the store, and `--verify`
  needs the store.
- Graph size grows with claims, not with episodes: an episode set is one evidence item whose payload is the
  sorted list of episode identities.
