## Background

`frob-verify` is the project's offline auditor: a separate binary in the crate `frob-cert`, built with an empty
dependency table and its own stable toolchain, containing its own canonical-JSON reader, BLAKE3 and exact
arithmetic. Its value is independence: it shares no code with the system that produced the artifact it checks,
so a defect in the producer cannot hide itself in the check. The storage plan gives it one duty toward run
records: a `.frun` bundle (a run exported as a canonical-JSON manifest plus content-addressed column files) has
its hashes and chains checked by `frob-verify` with the standard library alone.

The in-tree function `frun::verify` (BD-090) performs the same check inside `frob-chronicle`. This bead is the
second implementation, written from the byte-level contract in `frob-chronicle`'s `CONTRACT.md` and from nothing
else. The two implementations must agree on every bundle and must not share a source file. Reason for the
duplication: later, qualification campaigns and Reality records are replayed by the auditor on a machine with
neither the agent nor a GPU, and they cite run bundles; the auditor has to be able to say "these bytes are the
record" without trusting the recorder.

Rejected alternative: have `frob-verify` link `frob-chronicle`'s reader. That would drag FrankenSQLite and the
whole foundation into the auditor's build graph and end its independence.

## Scope

In: a `.frun` reader in `frob-cert` (manifest, column-file header, no column decoding beyond the header); the
checks listed below; the command-line form and exit codes; the report format; mutation tests.
Out: producing bundles (N29a-02); the format's definition and in-tree reader (BD-090); checking the *physics*
of a run by replay (qualification replay, BD-383); certificate bundles (their own checkers).

## Technical approach

**Invocation.** `frob-verify <path>.frun [--json]`. Exit 0: every check passed. Exit 2: at least one check
failed (the first failure is reported in full, later ones are counted). Exit 3: the file is not a `.frun`, or
it carries a format version the auditor does not know (an unknown major version, or a minor version such as a
new column codec that has not yet reached the auditor; see Considerations).

**Checks, in order.**

1. *Manifest syntax.* Canonical JSON: UTF-8, object keys sorted, no insignificant whitespace, no floating-point
   literal (rationals are reduced integer pairs with a positive denominator), integers above 2⁵³ as decimal
   strings. Re-serializing the parsed manifest must reproduce the input bytes; a difference is a failure
   `non-canonical`.
2. *Schema.* `schema = "frob.run/1"`; required fields present: run identity; model, scene, task and policy
   identities; kernel versions; tier; determinism class; effort profile; chunk length L; channel schemas; chunk
   index; frontier; gaps; `origin`; the pin.
3. *Flags.* The three no-authorization flags are present and each is the literal `false`. A missing or `true`
   flag is a failure `authorization-flag` (the artifact rule that an artifact authorizes nothing).
4. *Run identity.* Recompute `RunId` as BLAKE3 of the canonical manifest core (identities, seed, tier, kernel
   versions, effort profile, chunk length, channel schemas) and compare.
5. *Column files.* For each chunk-index entry, read the named file and compare its BLAKE3 with `content`. Check
   the header: magic `FCOL`, a known format version, a tick range equal to the entry's, channel names and kinds
   equal to the manifest's channel schema for that stream, a row count consistent with the file length.
6. *Partition.* For chunk index i of a (world, episode, stream), the tick range is `[i·L, (i + 1)·L)`, or it
   ends earlier and the entry is the last of its sequence (the episode's terminal tick).
7. *Chains.* For each (world, episode, stream) in index order from 0: `prev` of index 0 is 32 zero bytes;
   `chain = BLAKE3(prev ‖ content ‖ key bytes)` where the key bytes are the run identity (32 bytes) followed by
   world, episode, stream and index as little-endian 32-bit integers; `prev` of index i + 1 equals `chain` of
   index i.
8. *Frontier and contiguity.* The indices present for each (world, episode, stream) are exactly 0 to the
   manifest's frontier for it, with no hole; every `commit_seq` in the index is at most the pin.
9. *Gaps.* Every gap lies inside the tick range of its chunk and carries a reason from the registered list of
   the format contract (BD-090's five at M1: `level-not-enabled`, `ring-overflow`, `budget-stop`, `cancelled`,
   `device-lost`; later beads add rows to that list, for example `collected` with retention at M2 (BD-209),
   `store-budget` with the retention decision (N29b-12) and `episode-incomplete` with peak capture (N29ax-02)).
   The auditor keeps its own copy of the list as data, never read from the producer at run time; a reason added
   to the contract reaches the auditor's copy in the same change, which a repository check enforces (below). An
   unknown reason is the failure `gap`, which is the fail-closed behaviour.
10. *Orphans.* A column file in the bundle that no index entry names is reported as a warning, not a failure.

**Check names and order (one vocabulary with BD-090's `frun::verify`).** `first_failure.check` takes exactly the
names of the in-tree verifier: `non-canonical` (check 1), `schema` (2), `authorization-flag` (3), `run-identity`
(4), `content` and `header` (the two halves of check 5: the file's BLAKE3 against the index, then the column
header), `partition` (6), `chain` (7), `frontier` (8: a hole in the indices, or an indexed `commit_seq` above the
pin) and `gap` (9). The order is BD-090's: the four manifest-level checks first; then, per chunk, sequence by
sequence in key order and index by index from 0, `content`, `header`, `partition`, `chain`; then `frontier` and
`gap`. The first failure is the first (chunk, check) pair in that order, so the differential compares like with
like. A chunk-level check against a missing predecessor compares with the entry before it in its sequence, so a
removed middle chunk fails `chain` at the next index before `frontier` counts the hole.

**Report (`--json`).** `{ "schema": "frob.verify.frun/1", "ok": bool, "bundle_hash": …, "run": …, "chunks":
n, "checked_bytes": n, "first_failure": { "check": …, "key": …, "expected": …, "observed": … } | null,
"failures": n, "warnings": […], "auditor": { "version": …, "toolchain": … } }`. The bundle hash is BLAKE3 over
the manifest bytes followed by the content hashes in index order, the same definition the exporter uses.

**Layout.** `crates/frob-cert/src/frun/{manifest.rs, column_header.rs, checks.rs}`; no dependency outside the
standard library and the crate's own BLAKE3 and JSON modules. A build-graph test asserts that `cargo tree -p
frob-cert` prints the crate alone.

## Acceptance criteria

- [ ] `frob-verify` accepts every bundle the exporter writes for the M1 fixtures and exits 0.
- [ ] Each of the fifteen mutations below is rejected with the named check as the first failure, on 100 seeds
      each where the mutation takes a random position: one flipped byte in a column file (`content`); two chunk
      files' bytes swapped (`content` at the lower index); two index entries of one stream exchanged (`header` at
      the lower index); a changed `prev` (`chain`); a removed middle chunk, entry and file (`chain` at the next
      index, the hole counted under `frontier`); an index entry whose tick range is shifted by one (`header`,
      which runs before `partition`); a middle chunk written short with consistent header, hashes and chain
      (`partition`); a flag set to `true` and a flag removed (`authorization-flag`); a re-ordered manifest key and
      an integer above 2⁵³ written as a number (`non-canonical`); a required field removed (`schema`); a changed
      seed with the manifest otherwise canonical (`run-identity`); a `commit_seq` above the pin (`frontier`); a
      gap with an unregistered reason (`gap`). Every one of the ten check names is the first failure of at least
      one mutation.
- [ ] On every bundle of the corpus (valid and mutated) the auditor's verdict equals `frun::verify`'s, and the
      two name the same first failing chunk key.
- [ ] `frob-cert` has no dependency: the build-graph test passes, and the binary builds on a machine with
      neither FrankenSim nor a GPU.
- [ ] The auditor shares no source file with `frob-chronicle` (a repository check on file hashes).

## Test plan

### Unit tests

`cargo test -p frob-cert frun`:
- `accepts_reference_bundle`: a `synthetic` 3-world, 2-episode, 700-tick bundle at L = 256 (chunks of 256, 256
  and 188 ticks) on four streams.
- `mutation_*`: the fifteen mutations, each asserting `first_failure.check` (the name of BD-090's vocabulary)
  and the key.
- `check_order_matches_frun_verify`: the bundle of BD-090's `check_order_is_fixed` (a non-canonical key order, a
  flipped body byte at index 3, a changed `prev` at index 1) reports `non-canonical` first and counts three
  failures, as `frun::verify` does.
- `chain_index0_prev_zero`; `terminal_chunk_may_be_short`; `hole_in_indices_fails_contiguity`.
- `canonical_roundtrip_exact`: parse then serialize equals input for 1,000 generated manifests.
- `big_integers_as_strings`: 2⁵³ + 1 as a number is rejected; as a string it round-trips.
- `orphan_file_is_warning`.
- `gap_reasons_match_contract` (repository check): the auditor's reason list equals the gap-reason list of
  `frob-chronicle`'s `CONTRACT.md`, compared as sorted strings; a reason present in one only fails (planted:
  a contract with `collected` and an auditor without it).
- `no_dependencies` (build-graph assertion).

### End-to-end script and logging

Steps `verify-*` of `scripts/e2e/chronicle_record_surface.sh` (N29a-08): `frob-verify exports/a.frun --json`
(exit 0, the export envelope's bundle hash), then for the five mutated copies of that group, made with standard
shell tools (one flipped byte → `content`; two chunk files swapped → `content` at the lower index; two index
entries exchanged → `header` at the lower index; a changed `prev` → `chain`; a flag edited to `true` →
`authorization-flag`), `frob-verify` must exit 2 naming the check. NDJSON lines carry the command, exit code, wall
time, bytes checked, the bundle hash, and on failure the chunk key with expected and observed hashes.

### Known answers and negative controls

- Known answer: the reference bundle's bundle hash and chain heads are committed constants computed once by an
  independent script (shell and a reference BLAKE3 tool), never regenerated from either implementation.
- Negative controls: the fifteen mutations; two deliberately weakened auditors kept as mutants in the test tree,
  so the cases stay live controls: one that skips the chain check must accept the changed-`prev` bundle (which
  only `chain` catches), so `mutation_changed_prev` fails against it; one without the header and partition checks
  must still reject the exchanged-index-entries bundle at the lower index, now by `chain` (the chain is the
  second, independent line, as in BD-090). A swapped-pair case is not a control for the chain check: under the
  fixed order `content` or `header` catches it first.
- Differential: `frob-verify` against `frun::verify` on 10⁴ random valid and mutated bundles.
- Determinism: the report is byte-identical across the Mac and the Linux host for the same bundle.

## Considerations

- The auditor does not decode column bodies; a bundle whose columns hold wrong numbers but right hashes passes.
  That is correct for this check: what it certifies is that the bytes are the recorded bytes.
- A registered format must have one owner's parser; this reader is the declared exception and is listed in the
  format registry row as the independent auditor implementation.
- A new minor version of the format (for example a column codec) must reach the auditor in the same change,
  otherwise the auditor refuses the bundle with exit 3, which is the fail-closed behaviour.
