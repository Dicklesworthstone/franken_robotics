## Background

Telemetry is read while it is being written. A query that returns its answer in pages must not be confused by
chunks that commit between two pages. The record subsystem (Chronicle) solves this in the store: a query fixes,
on its first page, the state of the record it is reading, and everything committed later is invisible to it.

The rule: on its first page a query fixes the run, the value of the run's commit sequence number at that moment,
its filters, and a total order (tick, world, episode, stream, sample identifier, so that samples with equal
timestamps are ordered). Rows committed later are invisible to that query. The cursor is the pin plus the last
order key. Appends between pages can therefore neither skip nor repeat a row. A summary statistic names the
frontier it was computed at, and a verdict cites the frontier it read.

Two shortcuts this replaces, each with its smallest counterexample:
- *Offset pagination.* Rows at t = 1, 2, 3, 4 with page size 2. Page one returns {1, 2}. A chunk from a slower
  world then commits a row at t = 1.5. Offset 2 now returns {2, 3}: row 2 is repeated.
- *A cursor on time alone.* Two worlds each have a sample at t = 2 and the page ends on the first; "after t = 2"
  skips the second.

This bead builds the store-level mechanism at M1. The verb that first uses it is `telemetry.query`; the surface
later wraps the cursor in an authenticated envelope and applies the same rule to every catalog. Tier Solid.

## Technical approach

**Pin (DESIGN).** `Pin { run: RunId, commit_seq: u64, filter: Blake3, order: OrderId }`. `filter` is the BLAKE3
of the canonical encoding of the resolved filters (worlds, episodes, streams, channels, tick range,
downsampling). `order` names the total order; version 1 is the only one.

**Visibility.** A chunk is visible at a pin iff its `commit_seq ≤ pin.commit_seq`. A row is visible iff its
chunk is. Because a frontier only grows and `commit_seq` is strictly increasing per run, the visible set of a
pin never changes.

**Order key.** `(tick: u64, world: u32, episode: u32, stream: u16, channel: u16, phase: u8, sample: u32)`.
`phase` is 0 for an ordinary sample, 0 and 1 for the `pre` and `post` rows of a jump at one tick; `sample`
counts events sharing every earlier component. The last three components are the "sample identifier". Canonical
bytes: the components in that sequence, big-endian, so that byte order equals key order. The surface describes
the same order as (instant, world address, channel, sample index).

**Cursor.** `Cursor { pin: Pin, last: OrderKey }`. On the wire it is opaque; integers above 2⁵³ are strings.

**`page(query, cursor, limit)`.**
1. No cursor: read the run's commit sequence number P, build the pin, start before the least key.
2. With a cursor: recompute the filter digest of the presented query and compare it, the run and the order with
   the cursor's pin. Any difference is FROB-REF-896 (a pagination cursor used with a different pin, filter or
   order; repair: restart the query; exit 3).
3. Collect the next `limit` visible rows strictly after `last` in key order. The scan visits, per selected
   (world, episode, stream), only chunks whose tick range reaches `last.tick` or later and whose `commit_seq ≤
   P`, and merges them by key.
4. Return the rows, the new cursor (or none at the end), and the pin's `commit_seq` as the answer's `frontier`.

**Frontier stamp.** Every aggregate computed through the store (a count, a histogram, a summary line) takes a
pin and returns it: `Stamped<T> { value, frontier: commit_seq }`. A verdict record stores the frontier it read.
No aggregate function accepts "the current state" without producing a stamp.

**Pins and collection.** `Store::open_pins(run)` lists the pins of live cursors with their expiry (a cursor
lives for a bounded time after its last use; DESIGN default 15 min). Collection (BD-209) must not remove a
chunk visible at an open pin. A cursor whose pin's chunks have been collected after expiry is refused at the
surface as expired.

**Why it is correct (written into `CONTRACT.md`).** Keyset pagination over a total order restricted to a fixed
set partitions that set: by induction on pages, page k returns the `limit` least visible keys greater than the
last key of page k − 1; the visible set is fixed by the pin; hence the concatenation of pages is the visible
set in key order, each row once. This is INV-CHRON-04.

**Layout.** `crates/frob-chronicle/src/page/{pin.rs, order.rs, cursor.rs, scan.rs}`.

## Acceptance criteria

- [ ] INV-CHRON-04 (a paginated query returns every row visible at its pin exactly once): 10⁴ rows read in
      pages of random size while chunks are appended between pages; the concatenated pages equal the set visible
      at the pin, in order, with no repeat and no skip.
- [ ] Rows that share a tick across two worlds are both returned exactly once when a page boundary falls
      between them.
- [ ] A cursor presented with a changed filter, a different run or another order is refused with FROB-REF-896;
      the same cursor with the unchanged query continues.
- [ ] Rows committed after the first page never appear in that sequence; a new query sees them and reports a
      larger frontier.
- [ ] Every aggregate returned by the store carries the frontier it was computed at; a compile-fail test shows
      that an unstamped aggregate cannot be returned.
- [ ] An open pin prevents collection of the chunks it can see (checked against the retention hook).
- [ ] `pre` and `post` rows of a jump are adjacent and in that order.

## Test plan

### Unit tests

- `pages_partition_snapshot` (KA-712): the 10⁴-row case with 200 appended chunks interleaved, 100 seeds.
- `equal_tick_rows_not_skipped`: two worlds with a sample at tick 2, page size 1.
- `offset_counterexample`: the four-row case above; the pinned query returns {1, 2} then {3, 4}; the row at
  t = 1.5 is absent from the sequence and present in a fresh query.
- `cursor_filter_mismatch_896`, `cursor_run_mismatch_896`, `cursor_order_mismatch_896`.
- `order_key_bytes_sort_like_keys`: 10⁵ random key pairs; byte comparison equals tuple comparison.
- `jump_rows_adjacent`.
- `aggregate_is_stamped` (trybuild compile-fail for the unstamped path).
- `open_pin_blocks_collection`; `expired_pin_releases`.
- Property `inv_chron_04`: random publishes, page sizes and filters (10⁴ cases): each visible row once.

### End-to-end script and logging

Step group `page-*` of `scripts/e2e/chronicle_chunk_protocol.sh` (N29a-06): a referee run of 64 worlds is
queried with `frob telemetry query <run> --stream kinematics --limit 500 --json` page after page while a second
process is still publishing; the script concatenates the pages and compares their digest with a single query
taken afterwards at the same frontier (`--at-frontier`). It then replays an old cursor with a changed
`--stream` and expects exit 3 with FROB-REF-896. Lines carry the cursor's pin, the page's row count, the
frontier, the running digest and, on failure, the first repeated or missing key.

### Known answers and negative controls

- KA-712: 10⁴ rows read in pages during concurrent appends; each row visible at the pin appears exactly once.
  Negative control: a query ordered by timestamp alone repeats or skips equal-time samples (kept as a mutant
  with the order key truncated to `tick`; `equal_tick_rows_not_skipped` must fail it).
- CX-323 (order paginated telemetry by timestamp): the same case, from the counterexample catalogue.
- Second mutant: visibility by "committed now" instead of by the pin; `pages_partition_snapshot` must fail it.
- The surface's gate for the same property (10⁴ seeded schedules of concurrent appends; concatenated pages
  equal the frontier snapshot, including rows with equal timestamps; a changed filter with an old cursor is
  refused) is recorded by the surface's bead against this mechanism.
- Determinism: page contents are a pure function of (pin, query, cursor); checked twice, debug and release.

## Considerations

- The store raises 896; the surface's 806 names the same mismatch one layer up and 807 covers an expired pin.
  Both layers keep their code; the mapping is 896 → 806 in the envelope's refusal, with 896 as the cause. The
  duplication is listed in the unit's coverage notes for the refusal registry to settle.
- A pin over a very long-running job holds chunks against collection; the expiry bounds that.
- The scan is bounded by the filters, not by the run size; a query with no world filter over a large device run
  is paged by world first (the key order makes this a seek, not a sort).
- `follow` (see later commits without restarting) is a surface option that issues a new pin and says so; it is
  never an implicit widening of an existing sequence.
