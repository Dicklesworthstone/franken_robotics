## Background

A run does not always reach its planned end. An agent cancels it, a budget runs out, the simulated robot falls,
or the solver refuses a world. What the record says afterwards decides whether later statistics are honest.
Three errors are common in simulators and each is excluded here by construction: partial work published as if
it were a result; a stopped run whose denominator quietly shrinks to the trials that finished; and a solver
fault booked as a robot failure.

The record subsystem (Chronicle, crate `frob-chronicle`) owns the rules for the *record* side of stopping:
- **Cancellation takes effect at safe boundaries.** The worker drains, discards unpublished state, and
  acknowledges with the last committed tick per world, the outstanding device work and the observed
  cancellation latency.
- **A budget stop publishes nothing partial as a result.** The chunks already committed remain as telemetry,
  and the terminal receipt says `budget-stop`.
- **Every terminal receipt counts completed, failed, refused and unstarted trials, and separates three things
  that must never be merged: a numerical refusal, a budget stop and a physical failure.**

A safe boundary on the CPU at M1 is the end of a control tick at which the worker holds no half-written chunk;
on devices it is the kernel-batch boundary, where the commit fence has made the device state consistent. A
dropped handle is not a cancellation receipt: only the acknowledgement described here is.

Rejected alternative: publish the partial chunk on stop "so that nothing is lost". A partial chunk is not a
partition extent, so it could never be distinguished from an overlapping range after a retry; and a result
computed from an episode that was cut short is a different quantity from the planned one.

## Scope

In: the stop request and its acknowledgement as store-level types (`StopCause`, `StopAck`); discarding
unpublished state; the terminal receipt type (`TerminalReceipt`, `KindCounts`) with its counting rules, which
are the one mapping of trial outcomes to the four counts in the program, and the sum identity its constructor
enforces; the three-way separation; what remains readable after a stop; tests of the identities.
Out, with the bead that has it: the job ledger in which the receipt is stored (the tables `job`, `job_event`,
`job_log`, `run_lease`), the job state machine that issues the stop and writes the terminal state, lease
generations and restart recovery (N32a-08, in `frob-verbs`, which depends on this bead, constructs these types
and defines no receipt or counting rule of its own); the same on devices (BD-210); who may cancel and how the
request travels (the job verbs, N29a-23); draining device work (BD-210,
BD-175); the failure taxonomy that classifies a trial (BD-094); the budget accounting that triggers a stop (the
surface's estimate and budget beads).

## Technical approach

**Types (DESIGN).**

```rust
enum StopCause { Cancel, BudgetStop { which: BudgetAxis } }       // wall, simulated time, GPU s, CPU core-s, …
struct StopAck {
    cause: StopCause,
    last_committed: Vec<(WorldAddr, StreamId, u64 /* last committed tick, exclusive end */)>,
    outstanding_at_request: Work,       // device or CPU work in flight when the request arrived
    latency: Duration,                  // request → acknowledgement, measured on the worker's clock
    discarded: u64,                     // ticks produced but never published
}
struct TerminalReceipt {
    planned: u64, completed: u64, failed: u64, refused: u64, unstarted: u64, interrupted: u64,
    by_kind: KindCounts,                // physical, numerical, budget, protocol
    stop: Option<StopCause>, frontier: u64 /* commit_seq */, state: JobEnd,   // complete | failed | cancelled
}
```

**Stopping, as numbered steps.**
1. The request sets the run's stop word; workers observe it at their next safe boundary.
2. The worker finishes or abandons the control tick in progress so that it stands at a boundary, then drains:
   it lets any publish already inside its ledger transaction finish (the transaction is atomic), and starts no
   new one for a chunk whose extent is incomplete.
3. It discards unpublished state: the buffered ticks of the open chunk of each (world, episode, stream) and
   their column buffers. A chunk whose extent was complete at the boundary is published before the
   acknowledgement; one that was not is discarded whole.
4. It builds the acknowledgement from the frontier rows (the last committed tick per world is read from the
   store, not from the worker's memory) and returns it.
5. The run's terminal receipt is written in one transaction with the run's terminal state.

**Counting rules** (DESIGN: the source text names the four counts and the three outcomes that must not be
merged, and does not say which outcome goes in which count. The mapping below follows the outcome kinds of the
failure taxonomy one to one, `physical` to `failed`, `numerical` and `protocol` to `refused`, `budget` to
`unstarted`, so that the three outcomes that must never be merged are three different counts. The job ledger
(N32a-08) first mapped a physical failure to `completed` and kept `failed` for faults; that mapping is
withdrawn in favour of this one, which both beads now state). A *trial* is one planned (world, episode). At
the terminal receipt each trial is in exactly one of four counts:

| Count | A trial is here when | Kind recorded |
|---|---|---|
| `completed` | It reached a terminal tick with a task outcome and no failure class | — |
| `failed` | It reached a terminal tick with a failure class of kind `physical` (the simulated robot failed) | `physical` |
| `refused` | The solver or integrator refused or faulted (`numerical`), or the request for it was invalid (`protocol`) | `numerical` or `protocol` |
| `unstarted` | It never started, or it was cut short by a cancel or a budget stop. The second case is also counted in `interrupted`, a sub-count of `unstarted` | `budget` for a budget stop |

A trial whose device was lost with no device of the same family and fingerprint free to resume it (BD-210) is
counted in `refused` with the device refusal's code; a trial of a job that could not start is `unstarted`.
Neither is a fifth count.

Identity (the receipt is refused by its constructor otherwise): `completed + failed + refused + unstarted =
planned`, and `interrupted ≤ unstarted`. The sub-count is DESIGN: the source text names four counts; an
interrupted trial has committed telemetry but no result, so it is counted as not having produced one and is
made visible rather than hidden.

**The three that are never merged.** The receipt has no field that adds a numerical refusal, a budget stop and
a physical failure together, and the constructor of `KindCounts` takes them as three typed arguments. A
`numerical` trial leaves its verdict unknown: it is not in `failed` and it is in `planned`. A `budget` stop
leaves its interrupted trials unknown and returns FROB-REF-702 with exit 4; the job's terminal state is then
`failed` with cause `budget-stop` (the state table of N32a-08), not `cancelled`, which is reserved for a
requested cancel. A `physical` failure is a result with findings (exit 2 at the surface).

**What remains readable.** Chunks committed before the stop stay as telemetry and are served by pinned queries.
An interrupted episode has no `episode` outcome row; a metric that needs its missing ticks is refused with
FROB-REF-888 (a metric computed over missing samples), never extrapolated. The gap records of the discarded
tail carry the reason `cancelled` or `budget-stop`.

**Layout.** `crates/frob-chronicle/src/{stop.rs, receipt.rs}`.

## Acceptance criteria

- [ ] After a cancel at a random tick, no chunk in the store has a tick range that is not a partition extent,
      and the acknowledgement's last committed tick per world equals the store's frontier for that world.
- [ ] After a budget stop the envelope refuses with FROB-REF-702, exit 4, the receipt says `budget-stop`, the
      committed chunks are still readable, and no scorecard or summary counts an interrupted trial as a result.
- [ ] For 10³ random run histories the four counts sum to the planned number; a receipt that does not is
      unconstructible (planted).
- [ ] A run with two planted solver faults, three falls and a budget stop that interrupts five trials reports
      refused 2 (numerical), failed 3 (physical), unstarted with interrupted 5 (budget), and no sum of the three.
- [ ] A dropped handle (the caller disappears without requesting a stop) produces no acknowledgement and no
      stop; the run continues.
- [ ] The acknowledgement reports the outstanding work at the request and the observed latency.
- [ ] A metric over an interrupted episode is refused with FROB-REF-888.

### End-to-end script and logging

Step group `stop-*` of `scripts/e2e/chronicle_chunk_protocol.sh` (N29a-06): a referee run of 32 worlds is
started in the background with `frob sim run g1 --tier referee --worlds 32 --seconds 40 --seed 11 --key
stop-cancel --json` (sized to last at least 20 s; `--worlds` above 1 on the referee at M1 as in N29a-06's step
1), and cancelled by the script after a seed-derived delay of 2 to 6 s (the assertions below are against the
store's frontier, so they hold wherever the stop lands). At M1 the job runs in that `frob` process and the job
ledger admits one writer process, so no second process can record a cancel request (it would be refused with
`retry: backoff`, N32a-08's `single_writer_lock`): the script sends the process an interrupt signal, which is
the in-process cancel request of N32a-08 (drain, receipt, one envelope with `job.state: cancelled`, exit 2). The
envelope is read and the script asserts the last committed ticks against `frob telemetry query`, the four counts
against the plan, and that a second run, `frob sim run g1 --tier referee --worlds 32 --seconds 40 --seed 12
--budget cpu_core_s=1 --key stop-budget --json`, ends with exit 4, FROB-REF-702 and `budget-stop`, its committed
chunks still readable (at M1 no estimate gates admission, so the run is admitted and stopped when its use reaches
the budget). The group calls only this bead's dependencies and N29a-06's. Two forms are other beads' because
their verbs come later and depend on this bead: the cancel of a job under `frobd` from a second process by
`frob job cancel` (N29a-23's `verbs-*` group in N29a-24's script, which asserts the acknowledged ticks against
the store's frontier), and, once admission compares the upper end of the estimate with the budget (N32a-15,
M2), the admitted-then-stopped run on N32a-15's slow fixture (that bead's script: 702 and no result object).
From that build on, the same `stop-budget` request is refused at admission; the group then asserts that refusal
in full instead (FROB-REF-701, exit 4, no job and no chunk committed under the key), and any third outcome fails
the step. Lines carry the acknowledgement, the receipt, each count against its expected value, the latency with
its unit, which budget outcome the build gave, and on failure the first world whose acknowledged tick differs
from the store.

### Known answers and negative controls

- Negative controls: a build that publishes the partial chunk (the extent check of the publishing transaction
  must refuse it, and this bead's test must see no such row); a build that drops interrupted trials from
  `planned` (the sum test fails); a build that books a solver fault under `failed`.
- The invariants of the surface that this bead supports: after a budget stop or a cancellation nothing partial
  is published as a result and the acknowledgement names the last committed tick; the four terminal counts of
  a job sum to its planned trials.
- Chaos lane: cancellation injected at every control-tick boundary of a small run under a deterministic
  schedule (the per-boundary injection of the verification program); every case ends in this bead's
  acknowledgement or in a completed run.
- Determinism: for a given stop tick, the set of committed chunks and the receipt are identical on repeat.

## Considerations

- Cancellation latency has a target on devices (250 ms at the 99th percentile); on the CPU it is the length of
  one control tick of the largest world and is reported, not gated.
- RISK-15 (failures moved out of the denominator) is mitigated here by the sum identity and by keeping
  numerical outcomes inside `planned`.
- A stop requested while a publish is inside its transaction waits for that transaction; this is bounded by
  one ledger commit.
- If the worker dies instead of acknowledging, there is no receipt from it: the job engine fences it by
  incrementing the lease generation and writes the receipt from the store's frontier.
