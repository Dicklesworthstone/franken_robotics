## Background

The chunk protocol is concurrent code whose failures are rare interleavings: a crash between two statements, a
writer that wakes up after its lease was taken, a retry that re-sends a chunk. Such defects are not found by
waiting for them. They are found by running the protocol under a scheduler that the test controls, with faults
injected at chosen points, many times, with a seed that reproduces any failure.

This bead is the measurement of the gate on the CPU:

> GATE-CHRON-04 (Known answer; M1 on the CPU, M2 on devices; TARGET): the chunk protocol under 10⁵ seeded fault
> schedules: INV-CHRON-01 to -04 hold in every one; each planted violation (late lease, overlap, conflict,
> tick-zero reuse) is refused, 100 of 100.

The four invariants are the oracles:
- INV-CHRON-01: a committed chunk key maps to one content hash for the life of the run.
- INV-CHRON-02: for every (run, world, episode, stream) the committed chunks are exactly the indices 0 to the
  frontier.
- INV-CHRON-03: one idempotency key yields one job, one budget charge and one receipt, under any crash or retry.
- INV-CHRON-04: a paginated query returns every row visible at its pin exactly once.

The mechanisms are built by other beads (the publishing transaction, pinned pagination, stopping). This bead
builds the scenarios, the oracles, the planted violations, the end-to-end script and the gate record. It is a
test bead: it implements no protocol logic. Tier Solid; verification tier G4 (chaos), site `daemon`.

## Scope

In: the scenario generator; the fault menu as applied to the publish path on the CPU; the four oracles; the four
planted violations with their 100 trials each; minimized regressions; the script `chronicle_chunk_protocol.sh`;
the gate row. Out: the harness itself and the submit path's own gate (BD-096: full await-point coverage and
minimization are GATE-CHRON-11); device rows of this gate (N29a-24).

## Technical approach

**1. Scenario.** A scenario is a pure function of a 64-bit seed: a run with W ∈ [1, 8] worlds, E ∈ [1, 3]
episodes, S ∈ [1, 4] streams, episode lengths in [1, 1,100] ticks at L = 256 (so sequences of one to five
chunks with a short terminal chunk in most), up to four writers, and a fake device whose chunk bytes are a pure
function of (world address, stream, index). Because the bytes are a function of the address, any correct
execution must end in the same store state, which is computed directly from the seed without running anything.

**2. Fault menu** (each fault is drawn by the seed and placed by the scheduler):
a crash at any statement boundary of the publishing transaction; a crash after commit and before the receipt is
delivered; a torn ledger write; duplicate delivery of a publish; reordered delivery; delay of a writer across a
reassignment (lease expiry and takeover by a second writer); a shard split that makes two writers produce
overlapping tick ranges; a reset that reuses tick zero; a full disk during the column write; a clock jump; a
cancellation at every boundary; a reader paging through the run while chunks are appended; a client that
disconnects with a submission in flight and reconnects by its key.

**3. Oracles, evaluated after every schedule and at every quiescent point.**
1. For each key, the set of content hashes ever committed has size at most one (INV-CHRON-01).
2. For each (run, world, episode, stream), the committed indices are {0, …, frontier} and each `prev` equals
   the previous `chain` (INV-CHRON-02).
3. For each submission key, the ledger holds at most one job, one charge and one receipt, and a retried
   submission returns that receipt (INV-CHRON-03).
4. For each reader, the concatenation of its pages equals the set visible at its pin, in order, each row once
   (INV-CHRON-04).
5. End state: when every writer has finished or been fenced and its worlds re-run, the store equals the state
   computed from the seed. A schedule that ends short of that (a permanent disk-full) must end in a typed
   refusal and a consistent prefix.

**4. Schedules.** 10⁵ seeds per gate run (TARGET). The first 10⁴ use lineage-driven selection: from the lineage
of a fault-free run of the same seed, the faults that could have broken its outcome are tried first; the rest
are random. A failing schedule is minimized to a seed, a fault list and a schedule of minimal length, stored
under `crates/frob-conformance/chaos/chunk/` as a regression that replays in under one second.

**5. Planted violations: four mutants, 100 trials each.** Each trial is a seeded scenario constructed so that
the violation occurs, run against the real protocol, which must refuse; and run against a mutant build of the
protocol with one check removed, on which the oracle must fire (so that each case is a live control).

| Violation | Construction | Expected from the real protocol | Mutant that must be caught |
|---|---|---|---|
| Late lease | Writer A renews, is paused; the run is reassigned; A publishes | FROB-REF-875; nothing written | Lease check removed: oracle 1 or 2 fires when B publishes the same extent |
| Overlap | After a shard split, writers publish [0, 100) and [50, 150) | FROB-REF-885 for both | Alignment relaxed: two rows cover ticks 50 to 99 and oracle 5 fires |
| Conflict | The fake device is perturbed to emit one different byte for a committed key | FROB-REF-878, both hashes, run marked `determinism-violated` | Conflict check replaced by overwrite: oracle 1 fires |
| Tick-zero reuse | Episode 1 starts at tick zero while episode 0 is committed | Both episodes committed under different keys | Key without the episode index: episode 0's chunk is overwritten and oracle 1 fires |

**6. Gate record.** The script writes no gate record (one recorder per gate). The tier run's receipt holds the
measured values: schedules run, schedules in which every oracle held, violations refused per kind (out of 100),
mutants caught per kind, regressions stored, the commit, the host fingerprint and the base seed; this bead
records the CPU rows from it with `cargo run -p frob-conformance --example record_gate -- --gate GATE-CHRON-04
--receipt <hash> --part M1` (N38b-19; the device part, M2, is N29a-24's), which writes the gate-registry row and the bead-log line, from a session that did
not implement the work.

## Acceptance criteria

- [ ] 10⁵ of 10⁵ schedules satisfy oracles 1 to 5 on the CPU; the count is recorded as measured, not as the
      target.
- [ ] Each of the four planted violations is refused in 100 of 100 trials by the real protocol, with the code
      and fields named above.
- [ ] Each of the four mutants is caught by an oracle in 100 of 100 trials.
- [ ] Any failing schedule found during development exists as a minimized regression that replays in under one
      second, and the regression suite passes.
- [ ] The run is reproducible: the same base seed gives the same per-schedule outcomes and the same store
      digests in two runs on one machine.
- [ ] The script exits non-zero if any count is below its threshold and prints the first failing seed.
- [ ] The gate row cites the claim identifiers of the run's evidence and they resolve in the artifact graph
      (BD-095; `frob evidence trace <claim> --verify` exits 0 for each).

## Test plan

### Unit tests

In `crates/frob-conformance/tests/g4_chunk_protocol.rs`:
- `scenario_is_pure`: the same seed gives the same scenario bytes; `expected_state_from_seed` matches a
  fault-free execution for 10³ seeds.
- `oracle_1_fires_on_two_hashes`, `oracle_2_fires_on_hole`, `oracle_3_fires_on_two_jobs`,
  `oracle_4_fires_on_repeat`, `oracle_4_fires_on_skip`: each oracle is shown to fire on a hand-built bad state
  (an oracle that cannot fail validates nothing).
- `planted_late_lease`, `planted_overlap`, `planted_conflict`, `planted_tick_zero`: 100 seeds each, real and
  mutant.
- `minimizer_shrinks_planted_failure`: a mutant's failing schedule minimizes to at most the planted fault plus
  the two operations it needs.
- `regressions_replay_fast`: every stored regression replays in under 1 s.

### End-to-end script and logging

`scripts/e2e/chronicle_chunk_protocol.sh` (this bead owns the script; step groups `publish-*`, `page-*` and
`stop-*` come from BD-091, N29a-04 and N29a-05):
1. `frob sim run g1 --tier referee --worlds 64 --seconds 12 --telemetry T2 --seed 11 --key ccp-run --json` (the
   positional catalog design; `--fixture` names a registered fixture, which `g1` is not; `--worlds` takes any
   count on the referee from M1, BD-090's part of VERBS-sim's row, each world at its own address), then
   `frob telemetry query` over every stream; assert a contiguous frontier per (world, episode, stream) and a
   verified chain (`frob run export <run> --out exports/ --key ccp-export --json` followed by `frob-verify`).
2. The pagination steps and the cancel and budget-stop steps.
3. `FROB_TEST_SEED=20261122 cargo test -p frob-conformance --test g4_chaos --features gauntlet-mutations --
   GATE-CHRON-04` (the entry fixes the 10⁵ schedules and runs the four planted violations against the real
   protocol and their mutant builds in the same run), reading its receipt.
4. The four planted-violation groups' outcomes, read from that receipt and logged one group per step.
It sources the shared helper and writes `target/e2e-logs/chronicle_chunk_protocol/<utc>.ndjson` and a
transcript. Every line has `ts`, `script`, `bead`, `step`, `event`, the command, exit code, wall time and the
evidence block; `metric` lines carry schedules run and passed, refusals per violation with the threshold 100,
and store digests; on failure the first failing seed, its minimized fault list and the path of the stored
regression. The final `summary` line lists assertions passed and failed and the gate touched.

### Known answers and negative controls

- KA-711 (two identical publishes yield one row and one receipt; a crash after commit returns the original
  receipt) and KA-712 (10⁴ rows read in pages during concurrent appends, each visible row once) are run inside
  the battery as fixed scenarios.
- Negative controls: the four mutants; the five oracle self-tests.
- PO-CHRON-01 (the publishing transaction preserves INV-CHRON-01 to -03 under every fault of the menu) is
  discharged by this battery: deterministic simulation over 10⁵ schedules, every failing schedule minimized and
  kept.
- Determinism lanes: the battery twice on one machine with equal outcome vectors; across worker counts of the
  test runner (schedules are independent); debug and release.

## Considerations

- Compute: 10⁵ schedules of a millisecond-scale simulation fit the default machine envelope (one hour, eight
  cores); the count is a TARGET and the measured count is what the row records.
- If the lab runtime cannot be admitted, the fallback is a hand-written virtual clock with the same fault menu
  and no schedule exploration; the gate then records the reduced method and its count.
- The fake device must stay honest: the dual-run check (the same small job against the fake and against
  `batch-cpu`, requiring the same ledger state) belongs to the simulation-testing gate and is a precondition
  for citing this battery on devices.
- OPEN-CHRON-2 (chunk length) blocks the gate's final record: the battery runs at the default L = 256 and is
  re-run if another value is chosen.
