## Background

Delivery work in this project is tracked in beads (work items). The project's standing risk is false progress:
a bead closed because its author says it is done. The countermeasure is that a bead closes only on evidence that
a different session recorded, and that the public status table is generated from those records and never
edited. The record subsystem (Chronicle) supplies the record: an append-only structured log per bead.

Every bead has a log, `docs/delivery/logs/<bead>.ndjson`, schema `frob.beadlog/1`, with one line per recorded
event:

```json
{"ts":"2027-02-11T09:14:03Z","bead":"BD-203","commit":"3f9c…","host":"m5u-01:fingerprint:8b1e…",
 "toolchain":"nightly-2026-07-06","determinism":"D2","state_hash":"u128:5a07…","claim_type":"Known answer",
 "claim_ids":["clm:7d21…"],"metrics":{"worlds_replayed":{"v":1000,"unit":"1"},"digest_mismatches":{"v":0,"unit":"1"}},
 "refusals":[],"verdict":"pass","recorded_by":"session:fresh-41","gate":"GATE-CHRON-01","receipt":"0d6b…"}
```

**The closing rule.** A bead closes only with a line whose verdict is `pass`, whose `claim_ids` resolve in the
artifact graph, and whose recording session is not the session that implemented the bead. The honest-status
table is generated from these logs and the gate registry. The check is part of the existing generated-artifact
check; it adds no new tool. The log has no verb: it is written by the gate recorder.

Rejected alternatives: closing on a free-text reason (not checkable); storing the log only in the ledger (the
ledger is machine-local, while the log must travel with the repository so that a fresh clone can regenerate the
status table); allowing an edit of a past line (the log would then record opinions about the past).

## Scope

In: the schema; the append function and its checks; append-only enforcement; the closing-rule evaluator; the
refusal; the generator input for the honest-status table; the event kinds beyond gate records.
Out: the artifact graph that resolves `claim_ids` (BD-095); the gate recorder and gate registry (the
verification-harness beads); the bead tracker itself; exit reviews.

## Technical approach

**1. Schema `frob.beadlog/1`.** One JSON object per line, keys in the order below, UTF-8, no trailing spaces.

| Field | Type | Rule |
|---|---|---|
| `ts` | RFC 3339 instant, UTC | Recorded for humans; never hashed |
| `bead` | string | The bead's key; must equal the file name |
| `event` | `gate-record` (default when absent), `implement`, `blocked`, `unblocked`, `note` | DESIGN addition, see 5 |
| `commit` | 40-hex commit of this repository | Must exist in the repository at append time |
| `host` | `<name>:fingerprint:<digest>` | The hardware fingerprint current at the run |
| `toolchain` | string | The toolchain the run was built with |
| `determinism` | `D0` … `D4` | The class of the recorded result |
| `state_hash` | `u128:<hex>` or `blake3:<hex>` | The digest the result is bound to (a run digest, a bundle hash) |
| `claim_type` | one of the seven claim kinds | — |
| `claim_ids` | array of `clm:<64 hex>` (the text form of `ClaimId` fixed by N34-11; the plan's bead-log example prints `c:`, which is already the prefix of a controller identity) | At least one for `verdict = pass` |
| `metrics` | object of `{ "v": number or string, "unit": string }` | Measured values, not targets; integers above 2⁵³ as strings |
| `refusals` | array of refusal codes met during the run | — |
| `verdict` | `pass`, `fail`, `not-run`, `fallback`, `superseded` | `fallback` and `superseded` name an ADR in `cause` |
| `recorded_by` | `session:<id>` | The session that ran the recorder |
| `implemented_by` | array of `session:<id>` | Absent from the recorder's input; filled by `append` with the rule of N38b-19: the union of the `Frob-Session:` trailers of the commits that touch the crates the bead names, from the bead's opening to the recorded commit, and every session of an `implement` line of the bead's log; sorted |
| `gate` | a gate, kill-gate or admission-gate identifier, or null | — |
| `receipt` | 64-hex BLAKE3, present exactly on `gate-record` lines | The hash of the Gauntlet receipt the recorder recorded from, or, for a part recorded from receipts of several tiers, of the receipt set `frob.gauntlet.receipt-set/1` (N38b-19: `gate`, `part`, `members`, the member receipt hashes in tier order); N38b-19 writes the same hash into the gate row. DESIGN addition: the closing rule for `recorded` (3 below) and the lifecycle check of N41-17 reach the receipt's controls through it, following a set to its members, and a repair cycle is ordered by it |
| `cause` | string, optional | For `blocked` and `unblocked`: a tag from the closed set of 5 below; for `fallback` and `superseded`: an ADR id; for `note`: free text, or the opening of a repair cycle in the form `repair-cycle: <failed receipt hash>: <hypothesis>` (N40-03 step 5), whose hash must be the `receipt` of an earlier `fail` gate-record line of the same log (`append` refuses the line otherwise); for a `fail` line appended by re-affirmation (N29bp1-01): `evidence-unavailable` |
| `sibling`, `primitive`, `upstream_item` | strings, present exactly when `cause = sibling-primitive-missing` | The sibling repository, the primitive it lacked, and the upstream work item `FD-…` that adds it |
| `reason` | string, present exactly when `cause = other` | The written reason |

**2. Appending.** `beadlog::append(bead, line)`:
1. Validate against the schema; `bead` equals the file's stem.
2. Check the commit exists and the host fingerprint string is well formed.
3. For `verdict = pass`: `claim_ids` is non-empty and each resolves in the artifact graph now, by BD-095's
   resolution rule (the citation guard N29b-10, which depends on this bead, later routes this check through its
   `cite`). Otherwise the line is written with `verdict = fail` and FROB-REF-869 in
   `refusals`, and `append` returns FROB-REF-869 to the recorder (exit 3): a pass that cannot be traced is not a
   pass, and the attempt stays in the log.
4. Open the file in append mode, write one line ending in a newline, flush, and record the file's new BLAKE3
   prefix chain value in the ledger (`ledger row` evidence), so that a later rewrite of an earlier line is
   detectable: line n's chain value is BLAKE3(chain of line n − 1 ‖ bytes of line n).
5. The repository check (part of `check-generated`) recomputes the chain from the file and fails on a mismatch
   with the last recorded value, and fails if the history of the file shows a removed or altered line.

**3. The closing-rule evaluator.** `beadlog::may_close(bead, close_type)` takes the typed close reason, one of
the six types `pass`, `recorded`, `fallback`, `superseded`, `duplicate`, `withdrawn` (the plan names the first,
third and fourth; the type table of N41-17's rule 2, which depends on this bead, states what each must carry,
and this evaluator accepts the log line each type cites). It returns `Ok(Some(line))`, `Ok(None)` or
FROB-REF-815 (closing a bead without a resolving log line from another session; repair: record the gate from a
fresh session; exit 3) with a reason:
- `pass`: the latest line that has `verdict = pass`, all `claim_ids` resolving, and `recorded_by ∉
  implemented_by`; otherwise 815 with `no-pass-line`, `claims-unresolved` (naming them) or `self-recorded`.
- `recorded`: a `gate-record` line with `verdict = fail` whose `gate` is in the `reads` of a kill row of the gate
  register (N40-03, through N38b-19), recorded by a session outside `implemented_by`, whose `receipt` resolves to
  a receipt listing every control of the gate's row `caught` (when the `receipt` is a receipt set, the set is
  followed to its members and the controls are counted across the members together: each control caught in at
  least one member); and, where the kill row's trigger text contains "repair cycle" or "optimization pass", an
  earlier `note` line opening the cycle whose failed receipt is the `receipt` of an earlier `fail` line of the
  same gate (a set's hash is matched as written, and the cycle's order follows the set to its members). Otherwise 815 with `recorded-invalid` and the part that
  is missing (`not-read-by-kill-gate`, `self-recorded`, `control-not-caught`, `no-repair-cycle`). No capability is
  claimed by such a close and the status inputs (4) never count it toward the gate.
- `fallback` and `superseded`: the latest line with that verdict and an ADR identifier in `cause` (a bead whose
  kill gate fired closes `fallback`; a dependent that needed the killed capability closes `superseded`);
  otherwise 815 with `no-decision-line`.
- `duplicate` and `withdrawn`: `Ok(None)`. They claim nothing and need no gate-record line; the pointer each
  carries (the surviving bead; the recorded reason or decision) is checked by the close audit of N38b-03 and by
  N41-17, not here.

The tracker's close command calls this evaluator through the delivery tooling; a close reason shared by several
beads is a failure signal that the exit review rejects.

**4. Feeding the status table.** `beadlog::status_inputs()` yields, per bead, its latest verdict, gate, measured
metrics and claim identifiers. The existing generator of the honest-status table reads these together with
`registries/gates.toml`; the table is regenerated in `check-generated` and a hand edit is a diff that fails the
check. A gate with no record has the status `not run`, which is not a pass.

**5. Other events (DESIGN).** `implement` lines record that a session worked on the bead (written by the session
harness when a session claims the bead; `recorded_by` is that session), so that a session whose work left no
commit trailer is still in `implemented_by`. `blocked` and `unblocked` lines carry a `cause` tag from the closed
set that the schedule gate of BET-12 attributes on (N40-11 owns the set and its meanings; this schema enforces
it): `sibling-primitive-missing` (a sibling library lacked a primitive the bead needs; the line also carries
`sibling`, `primitive` and `upstream_item`), `sibling-defect` (a sibling primitive exists and is wrong),
`owner-input` (waiting for an owner decision that had not reached its deadline), `compute` (waiting for an
approved compute envelope or a machine), `own-work` (the bead's own work or a dependency inside this
repository), `other` (with `reason`). A `blocked` line with no tag or a tag outside the set (the coarser
`upstream` and `defect` of an earlier draft included) is refused by `append`, naming the bead. A retag is a new
line, never an edit, so a cause changed after the fact stays visible. `note` lines carry free text in `cause`.
These lines have `verdict = not-run` and never satisfy the closing rule.

**6. Layout.** `crates/frob-chronicle/src/beadlog.rs`; `docs/delivery/logs/`; the schema file
`schemas/frob.beadlog.1.json`.

## Acceptance criteria

- [ ] The example line above validates; a line with a missing unit, a `bead` that differs from the file name, a
      non-existent commit, or a pass with an empty `claim_ids` is rejected.
- [ ] `may_close` returns the pass line for a bead recorded by another session, and FROB-REF-815 with the right
      reason in each of the three failing cases.
- [ ] A `recorded` close is accepted on a `fail` gate-record line of a gate a kill row reads, recorded by another
      session with every control caught and, for a trigger that names a repair cycle, preceded by the cycle's
      `note` line; each missing part gives 815 `recorded-invalid` naming it. `duplicate` and `withdrawn` need no
      line; `fallback` and `superseded` need their line with an ADR.
- [ ] A pass line whose claim is later tombstoned makes `may_close` fail with `claims-unresolved`.
- [ ] Editing or deleting an earlier line makes `check-generated` fail; appending does not.
- [ ] The honest-status table regenerated from the logs equals the committed one; a planted self-certification
      and a planted pass with an unresolved claim are both refused by the generator's input stage.
- [ ] `blocked` and `unblocked` lines round-trip and never count as a pass; a tag outside the closed set of
      N40-11, or a `sibling-primitive-missing` line without `sibling`, `primitive` and `upstream_item`, is refused.
- [ ] Every metric carries a unit and is the value the run measured; a line with a metric object lacking `unit`
      or carrying a threshold in place of a value (a field named `target`) is rejected by the schema.

## Test plan

### Unit tests

- `example_line_validates`; `schema_rejections` (the four cases).
- `pass_requires_resolving_claims`: with a dangling claim the line is stored as `fail` with 869 in `refusals`
  and `append` returns FROB-REF-869.
- `may_close_other_session_ok`; `may_close_self_recorded_815`; `may_close_no_pass_815`;
  `may_close_unresolved_815`.
- `fallback_and_superseded_lines`: accepted only with a `cause` naming an ADR.
- `may_close_recorded_on_fail_line`: a kill row with `reads = ["GATE-X"]` and a trigger naming one repair cycle;
  the log holds a `fail` line (receipt r1), the note `repair-cycle: r1: <hypothesis>`, and a `fail` line (receipt
  r2, every control caught) recorded by another session: `recorded` is accepted on the r2 line.
  `recorded_invalid_cases`: without the note (`no-repair-cycle`), for a gate no kill row reads
  (`not-read-by-kill-gate`), recorded by an implementing session (`self-recorded`), with a control `missed` in r2
  (`control-not-caught`).
- `recorded_with_receipt_set`: the r2 line's `receipt` is a receipt set of two members (tier order G1, G4); the
  gate's control NC-A is caught in the G1 member and NC-B in the G4 member: `recorded` is accepted; with NC-B
  `missed` in the G4 member and absent from the G1 member: 815 `recorded-invalid` (`control-not-caught`, naming
  NC-B); a set whose member hash resolves to no receipt is refused the same way.
- `duplicate_and_withdrawn_need_no_line`: both return `Ok(None)` on an empty log.
- `repair_cycle_note_form`: a note whose hash names no earlier `fail` line of the log, or a `pass` line, is
  refused by `append`; free-text notes are unaffected.
- `receipt_only_on_gate_record`: a `gate-record` line without `receipt`, or another event with one, is refused.
- `chain_detects_rewrite`: change one character of line 2 of a five-line log; the recomputed chain differs at
  line 2.
- `append_only_under_concurrent_writers`: two recorders append 100 lines each; 200 well-formed lines result
  (file locking through an exclusive create of a lock file).
- `status_inputs_latest_wins`.
- `blocked_unblocked_never_pass`.
- `blocked_cause_closed_set`: each of the six tags is accepted; `upstream`, `defect` and an untagged `blocked`
  line are refused naming the bead; `sibling-primitive-missing` with `sibling = "frankensim"`, `primitive =
  "contact cone rows"`, `upstream_item = "FD-FSIM-01"` is accepted and without `upstream_item` refused; `other`
  without `reason` is refused.
- `implemented_by_from_trailers_and_implement_lines`: commits with trailers `session:a` and `session:b` and an
  `implement` line by `session:c`: `implemented_by` = [a, b, c]; a pass recorded by `session:c` is refused as
  `self-recorded`.

### End-to-end script and logging

Step group `beadlog-*` of `scripts/e2e/evidence_trace.sh` (N29a-10). Every step of the group works in a scratch
clone of the repository under the run's `work/` (the recorder commits, so it needs a repository of its own, the
form of N38b-19's script) and never in the checkout of record, whose `docs/delivery/logs/` and
`registries/gates.toml` are read only for their digests, logged at the start and the end, and must be unchanged
(a script never writes a gate record, KNOWN_DRIFTS 9). In the clone the recorder is run from a second session
identity for a small known-answer test, the line is appended, `may_close` is queried through the delivery
tooling's dry-run, and then the same is attempted with the implementing session's identity, expecting
FROB-REF-815 and exit 3. On the clone's logs and gate register with a planted kill row reading a planted gate
whose trigger names one repair cycle, the dry run of a `recorded` close is accepted after a `fail` line, its
`repair-cycle` note and a second `fail` line from another session, and refused with 815 `recorded-invalid`
(`no-repair-cycle`) when the note is removed. Lines of the script's own log carry the bead, the appended line's
digest, the chain value, the resolver's answer per claim, the close type, the closing verdict and the two
digests of the checkout's logs and gate register.

### Known answers and negative controls

- Negative controls: self-certification (the same session implements and records); a pass with an unresolved
  claim; a rewritten line; a hand-edited status table. Each must be refused or fail the check.
- The status-accounting gate of the verification program (the README table equals a fresh generation from the
  gate registry; a planted self-certification and a planted PASS with an uncaught control are each refused)
  reads this log.
- Determinism: the generator's output is a pure function of the logs and the registry; bytes compared on repeat
  and across platforms.

## Considerations

- A closed bead is not acceptance; acceptance is the gate's row in the gate registry. The log is evidence for
  both.
- Session identity is whatever the recorder stamps; this bead trusts it as data and makes disagreement visible
  (commit trailers against `recorded_by`). It is a guard against carelessness and reward hacking, not against a
  determined forger.
- Logs live in the repository and must stay small: metrics and identifiers only, no traces and no scene data.
