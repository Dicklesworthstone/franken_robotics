## Background

The artifact graph ties every claim to its evidence, to the rule version that decided it and to the executions
that produced it. Its value is that the project's own status cannot outrun its evidence: every gate recorded as
passed must point at claims that still resolve. This bead measures that property:

> GATE-CHRON-10 (Known answer; M1; TARGET): the artifact graph: every row of `registries/gates.toml` with a
> PASS resolves; a dangling identifier fails the build; `evidence.trace` on 100 random claims returns closures
> whose hashes recompute.

It has three parts with three different failure modes. "Every PASS row resolves" guards against a status table
that cites evidence nobody can find. "A dangling identifier fails the build" guards against the first property
being checked only when someone remembers to run it. "100 random closures recompute" guards against a graph
whose identifiers are not actually the hashes of what they name.

The graph, the verb and the log are built by their own beads; this bead is the measurement, the planted
defects and the end-to-end script. It is a test bead. Tier Solid; verification tier G1, site `host`.

Terms. A claim *resolves* when its evidence closure (everything reachable over supported-by, derived-from and
depends-on edges) has no node that is missing (dangling) and no node whose payload retention has removed
(tombstoned). A closure *recomputes* when every stored payload hashes to its evidence identifier and the claim
identifier equals the hash of the claim's stored fields.

## Scope

In: the three measurements; the corpus of claims they run on at M1; the planted defects; the script
`scripts/e2e/evidence_trace.sh`; the gate row. Out: the mechanisms (BD-095, N29a-09); the referee run and the
chunk chain the fixture corpus is built from (`frob sim run`, BD-024; the publishing transaction that computes
each chunk's chain digest, BD-091); the retention gate that re-checks resolution under collection at M2
(BD-209); report generation.

## Technical approach

**1. Corpus at M1.** The gate needs real claims. At the time it is first recorded the store holds the claims
recorded by the M1 gates that ran before it (the referee energy-ledger closure, the chunk-protocol battery, the
known answers of the dynamics and actuator fixtures), plus a *fixture corpus* built by the script: 120 claims
from 30 small referee runs (seeds 0 to 29, the built-in humanoid for one second each), four claims per run:
a known answer on the final digest, a known answer on the chain head of the kinematics stream's chunks, a
parity claim (the forward-dynamics digest of G1's reference state at zero torque, computed in the run's process,
equals the oracle fixture's value of BD-007; the oracle is seedless, so the value is the same for every run and
each claim is bound to its own run's execution), and a design-comparison claim over the pair (run k, run k + 1
mod 30) that depends on the two known-answer claims. This gives closures with every edge kind, including
depends-on.

**2. Measurement A: every PASS row resolves.**
1. Parse `registries/gates.toml`; select rows with `status = "pass"`.
2. For each listed `claim_id` call the closure function; record `resolved`, node count and edge count.
3. The measured value is (rows resolving, rows with PASS). The threshold is equality. A PASS row with no
   `claim_id` counts as not resolving.

**3. Measurement B: a dangling identifier fails the build.**
1. Copy the registry and the committed graph export to a scratch tree.
2. Plant, in turn, three defects: a `claim_id` that is not in the graph; a `claim_id` whose supporting evidence
   row was removed from the export; a `claim_id` whose evidence carries a tombstone.
3. Run `cargo xtask check-generated` on the scratch tree. Each must fail and name the row, the identifier and
   the missing node. The unplanted tree must pass. Measured value: (defects caught, 3) and (clean tree passes).

**4. Measurement C: 100 random claims recompute.**
1. Draw 100 claims from the store with a recorded seed (uniformly over all claims, not only the fixture
   corpus).
2. For each run `frob evidence trace <claim_id> --verify --json`.
3. Assert exit 0, `resolved: true`, every payload hash equal to its identifier, the claim identifier equal to
   the recomputed one, and, by an independent recomputation in the test (a second, minimal implementation of
   the two hash definitions in the conformance crate), the same identifiers. Measured value: (closures that
   recompute, 100).

**5. Negative controls** (each must flip its measurement):
- A graph in which evidence identifiers include the trace identifier: measurement C's independent
  recomputation disagrees.
- A closure function that follows only supported-by edges: a tombstone planted behind a derived-from edge is
  missed by the mutant and found by the real function.
- A `check-generated` that only checks identifier syntax: measurement B's first defect passes it.
- KA-720's control: a claim printed after its evidence was collected. A chunk of one fixture run is tombstoned
  through the conformance harness; `frob evidence trace` must then exit 2 with `evidence: unavailable`, and a
  verb that tries to cite the claim must refuse with FROB-REF-869 (exit 3).

**6. Gate record.** The script writes no gate record itself (one recorder per gate): it produces a receipt
holding the measured values of A, B and C, the seed of the draw, the commit and the host fingerprint, and this
bead records the gate from that receipt with `cargo run -p frob-conformance --example record_gate -- --gate
GATE-CHRON-10 --receipt <hash>` (N38b-19), which writes the gate-registry row and the bead-log line. The row's
own `claim_id` is a known-answer claim over those values, so the gate that checks resolution is itself
resolvable.

## Acceptance criteria

- [ ] A: every PASS row of the gate registry resolves; the count is recorded (k of k).
- [ ] B: the three planted defects each fail `check-generated` with the row and node named; the clean tree
      passes.
- [ ] C: 100 of 100 randomly drawn claims return closures whose hashes recompute, by the verb and by the
      independent recomputation.
- [ ] The four negative controls are caught.
- [ ] The script exits non-zero when any measured value is below its threshold and names the first failing row
      or claim.
- [ ] The gate's own row resolves after it is written (checked by a second run of measurement A).
- [ ] Bead closure is exercised once end to end: the recorder appends the pass line from a second session and
      the closing-rule evaluator accepts it; from the implementing session it returns FROB-REF-815.

## Test plan

### Unit tests

In `crates/frob-conformance/tests/g1_artifact_graph.rs`:
- `independent_claim_id`: the conformance crate's minimal implementation agrees with `frob-core` on 1,000
  generated claims and disagrees when one byte of the scope changes.
- `independent_evidence_id`: the same for the seven evidence kinds.
- `measure_a_counts`: a scratch registry with 5 PASS rows of which one cites a dangling claim yields (4, 5).
- `measure_b_three_defects`.
- `measure_c_draw_is_seeded`: the same seed draws the same 100 claims.
- `fixture_corpus_shape`: 120 claims; every edge kind present; 30 depends-on pairs.

### End-to-end script and logging

`scripts/e2e/evidence_trace.sh`:
1. Build the fixture corpus: 30 × `frob sim run g1 --tier referee --seconds 1 --seed <k> --key g<k> --json`
   (the positional catalog design of BD-024; `--fixture` names a registered fixture, which `g1` is not), then
   the conformance harness records the four claims per run.
2. `graph-*` (BD-095): BD-095's own script `scripts/e2e/evidence_graph.sh` as a stage, then one `frob evidence
   trace <claim_id> --verify --json` on a design-comparison claim of the corpus; assert that the closure
   contains two dependent claims and their evidence.
3. `resolve-*`: measurement A through `FROB_TEST_SEED=20261122 cargo test -p frob-conformance --test
   g1_known_answers -- GATE-CHRON-10::rows`.
4. `build-*`: measurement B on the scratch tree.
5. `closure-*`: measurement C with `--seed 20261122`.
6. `collect-*`: the tombstone control, expecting exit 2 then exit 3 with FROB-REF-869.
7. `beadlog-*` (N29a-09): the recorder appends the gate line from a second session; the closing-rule dry run
   accepts it; the self-recorded attempt is refused with FROB-REF-815; on a scratch copy, a `recorded` close on a
   `fail` line after its repair-cycle note is accepted and without the note refused (815, `recorded-invalid`).
It sources the shared helper and writes `target/e2e-logs/evidence_trace/<utc>.ndjson` and a transcript. Lines
carry `ts`, `script`, `bead`, `step`, `event`, the command, exit code, wall time, the evidence block; `metric`
lines carry (resolving rows, PASS rows), (defects caught, 3) and (recomputed closures, 100) with their
thresholds; `assert` lines carry both hashes when two are compared; on failure the first failing row or claim,
the missing node and the paths of the scratch tree and the store. The `summary` line counts assertions and
names GATE-CHRON-10.

### Known answers and negative controls

- KA-720 (every gate row resolves to evidence and traces; control: a claim printed after its evidence was
  collected).
- INV-CHRON-10 (every printed claim resolves in the artifact graph; no trace identifier or wall-clock time
  enters a content hash): checked by C's independent recomputation and by re-running one fixture run under
  the distinct key `g0-rerun` (the same key would return the stored receipt) and observing equal evidence
  identifiers with a new trace.
- Negative controls as listed in the approach.
- Determinism lanes: the script twice on one machine, each time on a fresh store, gives equal claim and
  evidence identifiers and different trace identifiers; the Mac and the Linux host give equal identifiers for the hash definitions (class D0).

## Considerations

- At M1 few gates have passed, so measurement A runs over few rows; it is re-run at every milestone exit, where
  it grows. The exit review reads the latest record.
- RISK-39 (retention deletes the interval that explains a decision): its early signal is exactly a failure of
  measurement A or of a closure; the retention gate at M2 repeats the tombstone control under random
  collection.
- OPEN-CHRON-3 blocks the final record only if the identifier layout would change; the default (local types
  with the suite kernel's layout) keeps stored bytes stable under either answer.
