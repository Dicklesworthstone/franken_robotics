## Background

Three batteries of the record subsystem (Chronicle) and one of the counterfactual-debugging subsystem prove that
a search for the first difference between two runs returns the right place. Each needs a difference whose place
is known in advance: teleport (re-running one device world on the CPU) must name the step and stage of a planted
single-kernel divergence in 100 of 100 trials (GATE-CHRON-02); the first-divergence algorithm must return the
earlier of two planted ticks in 100 of 100 trials and never a later tick than the true one (GATE-CHRON-06,
proof obligation PO-CHRON-05: "the first-divergence algorithm never reports a tick later than the true first
divergence on exact classes; planted divergences at one tick and at two ticks, 100 trials each"); the other
subsystem repeats the battery over the same code (GATE-AUTOPSY-07). The project's rule is that a gate nothing
can fail validates nothing, so the plant is the negative control of all four, and it has to be exact: a
difference of one unit in the last place (one ulp: the next representable value) of one number, at one stage of
one step of one world, and nothing else.

Each of those beads assumes "the conformance fault hook of the step" and none builds it, and one describes its
own. This bead builds the one shared hook. Where it sits: the batched step is ten named stages run in a fixed
order on every world (`frob-dyn` drives them; the kernels are in `frob-kernels` and run on `batch-cpu`, CUDA and
Metal). The hook is a test facility of that step, tier Solid, compiled only under the `conformance` feature,
exactly as the planted solver mutations of the dynamics subsystem are (labelled step-plan options that no
default feature can enable).

Design reasoning. Rejected: perturbing a recorded trace after the run (it tests the comparison and not the
kernels, and a teleport would have nothing to localize); perturbing an input such as a seed or a parameter (the
difference then appears at an unknown stage and grows from tick zero); a relative perturbation such as 10⁻⁷
(not one ulp at every magnitude, and not representable identically in `f32` and `f64`); one hook per battery
(three definitions of "stage output" that drift). Chosen: a schedule of bit-level edits, applied between stages
by the step driver, addressed by world address and not by slot, and carried in the step plan so that a planted
run can never be mistaken for an honest one.

## Scope

In: the plant schedule type and its admission; the hook points between the stages of the batched step on
`batch-cpu` (both precisions) and on each device backend; the bit-level edit and the restore action; the exact
device kernel that applies it; the labels and identities of a planted run; the proof that an unarmed build and
an armed-but-empty run change nothing; the plant file `frob.conformance-plant/1` and the registry of plant kinds
through which other beads add their own kinds (the stiffness override of N18bx-03); unit tests.
Out: the batteries that use the hook (teleport, BD-204; first divergence, N29a-21 with the unit tests of BD-206;
the other subsystem's battery, N27a-09; the discharge record of PO-CHRON-05, N29b-16); the planted solver
mutations (N16b-15); device fault injection such as an aborted command buffer or a stalled worker (N21b-23 and
the device-fault beads); seeded fault schedules of the chaos tier (N38a-23); the referee tier, whose step is the
sibling simulator's and has no stage table of ours.

## Technical approach

**1. A plant (DESIGN).**

```rust
#[cfg(feature = "conformance")]
pub struct Plant {
    pub world: WorldAddr,        // (run seed, world, episode): never a slot index
    pub tick: u32,               // control tick
    pub substep: u16,            // physics step inside the control interval, 0-based
    pub stage: u8,               // 1..=10, the stage after whose kernels the edit is applied
    pub output: SlabName,        // a slab the stage writes, by its name in the step plan's slab catalogue
    pub element: u32,            // index inside the world's active lanes of that slab
    pub action: PlantAction,     // Ulp { n: i8 } | Restore
}
pub struct PlantSchedule { pub plants: Vec<Plant> }   // at most 8, sorted by (tick, substep, stage)
```

`Ulp { n }` moves the element n representable values away from zero for n > 0 and toward zero for n < 0
(|n| ≤ 4; the batteries use 1): on the element's bit pattern taken as an unsigned integer of the same width,
add n to the magnitude bits and keep the sign bit. `Restore` writes back the bits the same element had before
the most recent `Ulp` plant on it in this schedule; it is how a battery builds "differ at tick a, agree in
between, differ again at tick b" on an output that is recorded but not fed back (a held action the controller
overwrites at its next update). The hook does not judge whether a restore makes the runs agree again; the
batteries assert the shape of their own traces.

**2. Admission.** A schedule is a conformance-only step-plan option. It is checked before the run starts: the
stage exists; the slab is in the write footprint of that stage's kernels (from the kernel manifests); the
element is inside the world's active lanes (padding cannot be planted, because padding is not part of a world's
digest); `Restore` follows an `Ulp` on the same element. A violation is a typed test error naming the field, not
a refusal code: the option does not exist on the agent surface. At run time, a plant that meets a non-finite
value or would carry out of the magnitude bits is not applied and is recorded as `skipped` with the bits found,
and the battery counts the trial as invalid, never as passed.

**3. Where the edit happens.** After the kernels of stage `stage` of substep `substep` of tick `tick` have
written, and before the next stage reads. Stage 10 runs once per control interval; for it `substep` is the last
substep.
- `batch-cpu`: the driver edits the element in place in the world's row of the slab (`f32` or `f64`).
- Devices: the driver appends one launch of the exact-class kernel `K-x-plant` (integer bit views, wrapping
  `u32` arithmetic; two words for `f64` slabs) to that stage's launch group for that substep only. Its
  arguments are the slab, the world's row offset, the element and the signed step. The kernel is registered in
  the kernel library index with the mark `conformance-only` and is absent from every production kernel set.
- The edit is addressed by world address and resolved to a slot at launch, so the same schedule plants the same
  world under any batch composition, shard split or co-tenancy.

**4. Identity and labels.** The schedule's canonical bytes are hashed into the step plan identity, so a planted
run has a different `StepPlanId` from its honest twin and can never be served from a memo or cited in its
place. Its evidence block carries the label `synthetic` with the reason `planted-divergence`, and the run
receipt lists every plant with `applied` or `skipped`, the old bits and the new bits. Chunk digests of a planted
run are real digests of the planted state: that is what the batteries compare.

**5. Nothing changes when nothing is armed.** Without the `conformance` feature the hook points compile to
nothing and the option, the kernel and the types do not exist. With the feature and an empty schedule the launch
groups, kernel cache keys, state digests and digest chain equal those of a production build.

**6. The plant file and other plant kinds (DESIGN; shared with N18bx-03).** A conformance build of `frob` takes
one option, `--conformance-plant <file>`, on `sim.run`, `sim.replay` and the conformance harness. The file is a
canonical JSON document of schema `frob.conformance-plant/1` with one section per *plant kind*: `{"schema":
"frob.conformance-plant/1", "sections": {"ulp": [ …Plant… ], "stiffness": [ … ]}}`. This bead owns the file,
the section registry `registries/plant-kinds.toml` (kind, owning bead and crate, admission function, the step
hook it uses), the kind `ulp` above and the kind `shift` below. Another bead adds a kind by registering it there with its own admission
rules and hook, without changing this bead: the stiffness override of N18bx-03 is the kind `stiffness`. Rules
common to every kind: a section of an unregistered kind, or of a kind whose owning crate is not compiled with
`conformance`, is a typed test error naming the kind; sections are admitted independently by their owners and
the file is rejected if any section is; the canonical bytes of the whole file (sections sorted by kind) are
hashed into the `StepPlanId`; the receipt lists every plant of every kind with `applied` or `skipped`; plants of
different kinds never share a target element (checked at admission).

The kind `shift` (owned here) is for the tolerance batteries, which need a divergence of a stated physical size
rather than one unit in the last place (a 5 mm base offset at tick 200, N29a-20 and N29a-21). A `shift` plant has
the fields of `Plant` with the action `Shift { delta: f64 }`: after the named stage the element becomes the
element plus `delta`, computed as one IEEE addition in the slab's precision (`delta` first rounded to that
precision) with rounding to nearest even (the
same bits on every backend); `delta` is in the slab's SI unit, finite, nonzero and at most 0.1 in magnitude
(DESIGN bound; a larger value is a typed test error). Admission is that of `ulp` with one more rule: the slab
must be one of the step plan's canonical state slabs, so that the shift persists into the next tick. For an
anchored position the delta is added to the offset, and the step's own re-anchoring carries any cell change at
its usual point. On devices `K-x-plant` has a second mode for it (one floating addition in the slab's precision);
a result that is not finite is recorded `skipped`, like `ulp`.

**7. Layout.** `crates/frob-dyn/src/step/plant.rs` (types, admission, the `batch-cpu` edit, hook points in the
step driver; the plant file reader and the kind registry); `crates/frob-kernels/src/exact/plant.rs` (`K-x-plant`, Rust reference and dialect source);
`crates/frob-conformance/src/plant.rs` (schedule builders used by the batteries: `one_ulp_at`,
`two_tick_pair`, `shift_at`); all behind `#[cfg(feature = "conformance")]`.

## Acceptance criteria

- [ ] A plant `Ulp { n: 1 }` at (world w, tick t, substep j, stage s, output o, element i) changes exactly that
      element by one representable value at that point: against the honest twin, every slab of world w is
      bitwise equal before the edit, the planted element differs by one in its integer bit pattern after it, and
      every other world is bitwise equal for the whole run. Shown on `batch-cpu` in `f32` and `f64`, on CUDA and
      on Metal.
- [ ] For 1,000 seeded plants the bits written on each device equal the bits written by the `batch-cpu`
      reference for the same starting bits.
- [ ] A plant followed by `Restore` on an output that is not fed back gives a run whose state digest differs
      from the honest twin at the planted tick only.
- [ ] With the feature on and an empty schedule, 100 worlds over 400 control ticks have a digest chain equal to
      the production build's, and the kernel cache keys are equal.
- [ ] A binary built without the feature contains no `plant` symbol and no `K-x-plant` source, and rejects the
      option as an unknown parameter.
- [ ] A plant on a padding lane, on a slab outside the stage's write footprint, or a `Restore` with no earlier
      `Ulp` is rejected before the run; a plant that meets a non-finite value is recorded `skipped`.
- [ ] A planted run's `StepPlanId` differs from the honest twin's, its envelope is labelled `synthetic`, and a
      request to cite it as evidence is refused.
- [ ] The same schedule plants the same world address under three batch sizes, a permuted slot assignment and a
      two-shard split.
- [ ] The plant file `frob.conformance-plant/1` admits the registered kind `ulp` and a second registered kind
      (a test kind registered by the test tree) side by side; an unregistered kind is rejected naming it; the
      `StepPlanId` changes when any section changes.
- [ ] A `shift` plant adds its delta once at the named stage on `batch-cpu` and on each device family with
      bitwise equal results; a `shift` on a slab outside the canonical state list, or with |delta| > 0.1, is
      rejected before the run.

## Test plan

### Unit tests

`cargo test -p frob-dyn --features conformance plant::` and `-p frob-kernels --features conformance plant::`:
- `ulp_up_f32`: 1.0 (bits `0x3F800000`) becomes `0x3F800001`; −1.0 becomes `0xBF800001`; `n = −1` on 1.0 gives
  `0x3F7FFFFF`.
- `ulp_up_f64`: 1.0 (`0x3FF0000000000000`) becomes `0x3FF0000000000001`.
- `zero_and_subnormal`: +0.0 becomes the smallest subnormal `0x00000001`; the largest finite value with n = 1 is
  `skipped`; an infinity or a NaN is `skipped`.
- `plant_lands_at_named_stage`: for each of the ten stages, a raw slab dump taken after every stage shows the
  first difference from the honest twin at exactly that stage and substep.
- `restore_returns_bits`; `restore_without_ulp_rejected`; `padding_lane_rejected`; `foreign_slab_rejected`.
- `other_worlds_untouched` (property, 10³ schedules): all worlds but the planted one are bitwise equal.
- `empty_schedule_is_identity`; `hooks_absent_without_feature` (symbol search of the release binary).
- `device_matches_reference` (per device family): 1,000 seeded plants.
- `address_not_slot`: the planted world is the same under a permuted slot assignment.
- `plant_file_sections`: a file with sections `ulp` and a registered test kind is admitted and both receipts are
  written; a file with an unregistered kind `foo` is rejected naming `foo`; two kinds targeting one element are
  rejected; reordering sections in the file changes neither the canonical bytes nor the `StepPlanId`.
- `shift_adds_delta`: a base x-position of 1.0 m (`f32`) shifted by 0.005 m becomes `1.005f32` (bits
  `0x3F80A3D7`), once, at the named stage; `shift_state_slab_only` and `shift_bound` reject a non-state slab and
  delta = 0.2; `shift_device_matches_reference` (per device family, 1,000 seeded shifts).

### End-to-end script and logging

This bead has no script of its own. Its user-side check is the step group `plant-*` of
`scripts/e2e/sim_replay.sh` (owned by N29a-19): with the conformance build of `frob`, run a 64-world `batch-cpu`
job and its twin with `--conformance-plant fixtures/conformance/plant/one-ulp.json` (a `frob.conformance-plant/1`
file with one `ulp` section), export both, and assert
that the first chunk whose digest differs is the chunk of the planted tick and that the receipt lists the plant
as `applied` with old and new bits; repeat on each admitted device. Lines follow the shared helper's format
(`ts`, `script`, `bead`, `step`, `event`, the exact command, exit code, wall time, the evidence block with the
`synthetic` label and the seed) with `metric` lines for `first_differing_tick` against the planted tick and
`worlds_differing` against 1; on failure the first differing slab, element and both bit patterns, and the two
`.frun` paths. The `summary` line names no gate: the gates are recorded by the batteries.

### Known answers and negative controls

- Known answers: the bit patterns of the unit tests above.
- Negative controls (mutant hooks kept in the test tree, each caught by a named test): a hook that applies the
  edit one stage late (`plant_lands_at_named_stage`); a hook that perturbs by a relative 10⁻⁷ instead of one
  representable value (`ulp_up_f64`); a hook that addresses by slot (`address_not_slot`); a hook that also
  touches the next world's row (`other_worlds_untouched`).
- Metamorphic: `Ulp { n: 1 }` followed at the same point by `Ulp { n: −1 }` equals the honest run.
- Determinism lanes: twice on one machine; across worker counts on `batch-cpu`; debug and release; each device
  family against its declared class.

## Considerations

- The hook is a second code path through the step. The compile-to-nothing rule, the symbol search and the
  empty-schedule identity are what keep it from changing production behaviour; all three are acceptance
  criteria.
- On a device family that does not attain bit equality with `batch-cpu`, a teleport battery plants on one side
  of a `batch-cpu` pair instead; the hook is the same.
- A plant on a value that a later stage of the same substep overwrites disappears; the batteries choose
  outputs from a table of (stage, slab) pairs that survive to the digest, which this bead publishes with the
  schedule builders.
- The option is not a verb parameter and is not in the verb registry; the surface parity checks run on
  production builds, where it does not exist.
- Cost: one extra launch at the planted substep only; no cost when unarmed.
