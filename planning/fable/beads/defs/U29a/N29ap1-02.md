## Background

A stored state from which a world continues exactly as it would have is the base of replay, teleport, forks,
preempt-resume, the background referee and counterfactual debugging. Telemetry level T3 of the record
subsystem (Chronicle) is "full state snapshots at intervals, sufficient for exact restart". The container that
holds such a state, `frob.snapshot/1`, is defined by N29a-18; this bead produces snapshots on the batched tiers
and stores them: the kernel that copies chosen worlds' rows out of the committed state, the host side that
encodes, checks and stores them, and the schedule that decides which snapshots exist.

Why at the fence. On a device, state is consistent only at the commit fence: `K-commit` writes the
checkpointable state to the other of two committed slabs, and the host reads anything of a device chunk only
after its `Completed` receipt. A snapshot taken elsewhere could mix two ticks. Copying rows from the newly
committed slab, as the last dispatches of the chunk, gives a state that is exactly the committed one.

Why an index-driven copy. A snapshot of a few chosen worlds out of thousands must not read back the whole
batch. The kernel copies only the rows of an index vector of worlds into a separate snapshot slab, and the
column list is the step plan's canonical slab list, so a field added to the state is added to the copy by
construction. Rejected: copy-on-write forks of device state (state is write-dense: every step rewrites every
world's configuration, velocity, contacts and warm starts, so a fork has copied everything within one step;
counterexample CX-226 of the backend chapter); host-side read-back of whole slabs (bandwidth).

Why a host tripwire. The host recomputes the state digest from the bytes it received and compares it with the
digest the device emitted for that tick (N29ap1-01); a mismatch means the bytes do not represent the committed
state, and the snapshot is rejected rather than stored.

Split from seed BD-203 in polishing round 1: BD-203 keeps the replay engine and the verb; forks, the background
referee and the ring need snapshots without replay. Tier Solid. Crates `frob-kernels` (the kernel and its
dialect twins) and `frob-chronicle` (the host side).

## Technical approach

**1. `K-snapshot`.** Inputs: an index vector `src` of world slots (length n ≤ the snapshot slab's capacity) and
the newly committed slab set. For each j < n and each slab of the step plan's canonical slab list (and the
carried chain slab of N29ap1-01), row `src[j]` is copied to row j of the snapshot slab, active elements and
padding alike (the host drops padding when encoding). It runs as the last dispatches of the chunk's launch
sequence, after `K-commit`, reading the newly committed slab. It never writes the source (its manifest declares
the committed slabs read-only, and the footprint audit checks it). Kernel class `exact` (a copy of bits),
determinism D0. Per backend: on `batch-cpu` a row copy; on CUDA an explicit stream-ordered copy into the
snapshot slab followed by a readback after `Completed`; on Metal a copy into a shared-storage slab read by the
host after completion.

**2. Host side.** After the chunk's `Completed` receipt, under the read lease on the snapshot slab (N21b-11):
1. For each j, gather the world's rows of every canonical slab, keep only active elements, and encode them into
   the container (N29a-18) with the header fields: `EpisodeId` (below), address, control tick and substep,
   profile identity, model, scene, task and policy identities, the random-stream step counter, the command
   cursor, d and x at this tick.
2. Recompute d from the encoded bytes with the host reference (N29ap1-01) and compare it with the device's d for
   that world and tick. Unequal: write a row to the divergence ledger (world address, tick, both digests,
   backend, kernel versions) and reject the snapshot; it is never stored.
3. Store the object content-addressed (BLAKE3 over the canonical bytes) and insert the `snapshot` row
   `(content hash, episode, tick, kind, base, bytes, trigger)` in the same ledger transaction as the T0 row of
   the chunk, so a snapshot exists exactly when its chunk is committed.
4. Release the lease.

**3. `EpisodeId`.** BLAKE3 over the canonical list of the episode's committed snapshot content hashes and chunk
chain heads (in tick order, then stream order). It is fixed when the episode's last chunk commits; until then a
snapshot header carries the episode's provisional identifier (the address and run identity), and the container's
`EpisodeId` field is filled at that commit.

**4. T3 schedule (DESIGN defaults; the plan gives none).**
- Traced worlds (the address-keyed sample, N29a-12): one stored full snapshot at every logical chunk boundary
  (every L = 256 control ticks), and sparse differences at ring cadence where the ring is flushed.
- Failing worlds: the ring's snapshots, flushed on failure (N29a-11).
- Every world: tick zero is reproducible from the address and the settled-pose (reset) cache and is not stored.
- Any other tick is reached by replay from the nearest stored snapshot (BD-203).
The schedule is a run-manifest field (`t3.every_chunks`, default 1 for traced worlds), so a change is a different
run identity, not a silent change of what is stored.

**4a. The two `sim.run` inputs this bead owns** (their rows in VERBS-sim name it; it adds them to the verb's
input schema and handles them on the batched tiers):
- `--telemetry T3`, the level that records the schedule above on top of T2 (the value names the highest level
  recorded, BD-090's rule; until this bead the value is 724, BD-207). The level enters the manifest and the
  `RunId` and leaves the physics digests unchanged, as every level does.
- `--snapshot-every <chunks>` (DESIGN spelling, requested by the registry round and already used by N20a-45,
  N21b-26 and BD-172): sets `t3.every_chunks`, a positive integer, default 1; a traced world then has a stored
  full snapshot at every k-th logical chunk boundary. Zero, a negative or non-integer value is FROB-REF-802 with
  `pointer` `/snapshot_every`; the option given without `--telemetry T3` is FROB-REF-802 naming `--telemetry T3`
  in `repairs` (DESIGN: a schedule that stores nothing would still enter the run identity and a script would
  measure snapshots it never asked to record).

**5. Layout.** `crates/frob-kernels/src/util/k_snapshot.rs` with dialect twins;
`crates/frob-chronicle/src/{snapshot_store.rs, t3.rs}`.

## Acceptance criteria

- [ ] Every canonical slab is gathered: a sentinel value written into each slab of a `synthetic` world appears in
      the stored snapshot; a slab added to the canonical list without a registered container section fails the
      container's completeness check (planted).
- [ ] `K-snapshot` never writes its source: the committed slab's bytes are identical before and after, over
      1,000 snapshots on each backend present.
- [ ] 10⁵ snapshot reads, on `batch-cpu` and on each device family present, each match the digest emitted for
      their epoch (shared with the fence gate of the backend unit; this bead supplies the snapshot side).
- [ ] The tripwire: one bit changed in the snapshot slab after the device digest was taken is caught, the
      snapshot is rejected and a divergence-ledger row names the world and tick.
- [ ] A restore of a stored snapshot followed by 100 ticks gives the same d_t and x_t as the uninterrupted run
      (with the chain resumed from the header).
- [ ] `EpisodeId` is equal for two runs of the same episode and changes when any snapshot or chunk head changes.
- [ ] With the default schedule a traced world of 1,000 ticks has stored full snapshots at ticks 256, 512 and 768
      and the terminal tick's chunk end, and an untraced, unfailed world has none.
- [ ] The snapshot row commits in the same transaction as its chunk's T0 row: a crash between them leaves neither.
- [ ] `--telemetry T3` records the schedule, and with `--snapshot-every 2` a traced world of 1,000 ticks has
      stored snapshots at tick 512 and the terminal tick's chunk end only, with `t3.every_chunks = 2` in the manifest and a `RunId` different from the
      default's; `--snapshot-every 0` and `--snapshot-every` without `--telemetry T3` are FROB-REF-802.

## Test plan

### Unit tests

`cargo test -p frob-kernels k_snapshot` and `cargo test -p frob-chronicle snapshot_store`:
- `snapshot_gathers_every_canonical_slab`: a sentinel per slab; all present after encoding.
- `slab_without_section_fails` (negative control of the completeness check).
- `source_rows_untouched`: bytes of the committed slab hashed before and after.
- `index_vector_order`: `src` = [17, 3, 99] places world 17 in row 0, 3 in row 1, 99 in row 2.
- `host_digest_tripwire`: one bit flipped in the snapshot slab after the device digest → rejected, ledger row.
- `chain_resumes_from_snapshot`: x after restore at tick 200 and 100 more ticks equals the uninterrupted x.
- `snapshot_row_atomic_with_chunk`: a fault injected between the two inserts leaves neither row.
- `episode_id_canonical`: two runs, equal; one flipped chunk head, different.
- `t3_schedule_default`: the stored ticks for traced, failing and other worlds as above.
- `snapshot_every_option`: values 1 and 2 set `t3.every_chunks` and change the `RunId`; 0, `-1`, `1.5` and the
  option without `--telemetry T3` are 802 with the pointer or repair named above; physics digests equal across
  the three accepted runs.
- `padding_not_stored`: a world at bucket capacities 32 and 64 gives byte-identical snapshots.

### End-to-end script and logging

`scripts/e2e/snapshot_store.sh` has two stages. Stage `kernel` runs when this bead closes: `cargo test -p
frob-kernels k_snapshot` and `cargo test -p frob-chronicle snapshot_store` on `batch-cpu` and on each device
backend present, with every test's result logged. Stage `snapshot-store-*` is the user's path. It needs `sim.run`
on the batched tiers (N16b-25) and the device job protocol (BD-210), both of which depend on this bead, so it is
written here and first run by `scripts/e2e/sim_replay.sh` (N29a-19): `frob sim run quad-a --tier batch-cpu
--worlds 64 --seconds 6 --seed 11 --telemetry T3 --trace-rate 1/4 --key sn-1 --json` and the same with
`--snapshot-every 2 --key sn-2`; `frob artifact list --run
<run> --kind snapshot --json` and assert that
exactly the traced worlds have snapshots at the scheduled ticks; read one snapshot with `frob artifact read` and
check its content hash and header digest against the T0 row's d read with `frob telemetry query`; repeat on
`gpu-cuda:0` and `gpu-metal` where present; run the conformance-build tripwire (`--conformance-plant
fixtures/conformance/plant/snapshot-bitflip.json`, a plant file of N29a-25 with one section of the kind
`snapshot-bitflip`, which this bead registers: flip one named bit of one world's row in the snapshot slab after
`K-snapshot` and before the host reads it) and assert the rejection and the divergence-ledger row. Logs through the STD-E2E helper to
`target/e2e-logs/snapshot_store/<utc>.ndjson`: per line `ts`, `script`, `bead`, `step`, `event`, the command,

`scripts/e2e/sim_replay.sh` (N29a-19), beside the container's own group `snapshot-*` (N29a-18).

### Known answers and negative controls

- Known answer: the sentinel snapshot of the `synthetic` world has a checked-in content hash.
- Negative controls (registered): a snapshot copy that omits warm starts or packet queues (the continuation
  test differs); a copy that reads the previous committed slab instead of the new one (digest tripwire fires);
  a copy that writes its source (source test fails); padding stored (capacity test fails).
- Metamorphic: splitting a rollout at a snapshot and resuming equals running it whole.
- Determinism lanes: twice on one machine; across worker counts; debug and release on `batch-cpu`; each backend
  against itself (class D2 for state; D0 for the copy of given bits).

## Considerations

- Memory: the snapshot slab is sized to the largest index vector the schedule requests per device chunk; at the
  default 1/100 trace rate and 8,192 worlds, about 82 worlds per logical chunk, each about 35 kB (quadruped) or
  97 kB (humanoid), so under 8 MB per chunk. A request above the slab capacity is split over chunks, never
  dropped silently.
- A rejected snapshot is a finding about the device or the copy, not a retry trigger; the world keeps running and
  its next snapshot is attempted at the next scheduled boundary.
- The snapshot schedule interacts with retention: sampled traces are evicted under the store budget, failure
  captures and evidence-pinned snapshots are kept (BD-209).
