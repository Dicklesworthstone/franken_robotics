## Background

Failures are the episodes an agent most needs to see in full. On the batched tiers the record subsystem
(Chronicle) keeps a per-world device ring of the last seconds at telemetry levels T2 (control-rate traces) and
T3 (full-state snapshots) and flushes it when a world fails (N29a-11). Memory decides who holds a full ring: the
traced sample and a reservoir chosen by address. Every other failing world is "reconstructed by replay, at the
cost of one episode prefix on the CPU" (or on its originating backend): the ring writes a `reconstruct` marker
with the world's address and the tick range wanted, and a later replay produces the capture.

This bead is that consumer. It adds the capture kind `failure` to the replay engine and to the verb
`sim.replay` (BD-203): replay the world from its address or nearest stored snapshot on its originating backend
and profile, and record exactly the bytes the ring's flush would have recorded, into the original run's record,
so that `frob telemetry query` on that world returns the same window whether the ring held it or replay
reconstructed it.

Why a bead of its own (polishing round 1). The seed bead BD-203 carried `--capture failure` and its test against
a ring flush, while the ring (N29a-11) depended on BD-203 for the replay that honours its markers: each needed
the other. With the capture here, the ring needs only the digests and the snapshot kernel (N29ap1-01,
N29ap1-02), replay needs no ring, and this bead joins them. Tier Solid.

Terms. *Trigger tick* t*: the tick at which the ring's trigger fired (failure, mode change or requested tick).
*Window*: the ticks a ring capture covers, a function of t*, the ring depth, the post-window and the reset mode
(N29a-11). *Marker*: the `reconstruct` row the ring writes for a failing world with no T3 ring.

## Scope

In: the capture kind `failure` in `opts.capture` of the replay engine and in `sim.replay --capture`; reading
pending markers; computing the window with the ring's own function; recording the capture into the original
run's record through the same flush path as the ring, with the same leading gap record and the same snapshot
host side; clearing the marker in the same transaction; replaying many markers in one batch; comparison mode for
a world that already has a ring capture; refusals; tests and the step group `reconstruct-*`.
Out: the ring, its triggers, the marker's writing and the window function (N29a-11); the replay engine, its
start selection and the other capture kinds (BD-203); the snapshot kernel's host side and its digest tripwire
(N29ap1-02); retention of failure captures (BD-209); fork points built from captures (N27a-03); the failure
monitors that raise the failing bit (N29b-05).

## Technical approach

**1. Capture kind `failure`.** `opts.capture = Failure { world, episode }` or `FailureMarkers { run }`.
`frob sim replay --run <r> --world <w> [--episode <e>] --capture failure --key <k> --json` captures one world;
`frob sim replay --run <r> --capture failure --markers --key <k> --json` captures every pending marker of the run.
The replay runs on the run's recorded backend and profile (BD-203's rules for 601 and 606 apply unchanged).

**2. Window.** For a world with a marker, the window is the marker's tick range. For a world named without a
marker (the comparison case of 5), it is `ring::window(manifest, trigger)`, the one function N29a-11 uses, with
the trigger read from the world's T1 events. Under masked automatic reset the window ends at the terminal tick
and the +0.2 s still is reported unavailable, as for the ring.

**3. Replay and record.** The engine starts from the latest stored snapshot at or before the window's first tick
under the run's profile (or tick zero by address), steps to the window's end, and keeps in host buffers the T2
rows of the window and the full state at each tick of the ring's snapshot period. The capture is then recorded
by the ring's flush routine (`flush::record_capture` of N29a-11) fed from these buffers instead of from ring
slabs: T2 rows appended to the world's T2 streams as ordinary chunks, with the leading gap record of reason
`level-not-enabled` for the ticks before the window; each snapshot encoded into the container, its digest
recomputed and compared with the replay's d_t (the host side of N29ap1-02), stored with its BLAKE3 content hash;
the capture row with class `failure-capture`, its trigger and `source = replay`. The chunks are published into
the original run under a new lease generation held by the replay job (BD-091's transaction: they extend each T2
sequence of that world with a leading gap, the same extents the ring flush would have published at run time;
DESIGN: the run record stays the one place the window is found). The marker is cleared in the same ledger
transaction as the capture row.

**4. Batches and idempotency.** All pending markers of a run are replayed in one batch per shape class (world
digests do not depend on batch composition, INV-CHRON-08). A marker already cleared is skipped and its stored
capture returned; a chunk re-published by a retried capture is a duplicate and returns its original receipt. One
idempotency key yields one job.

**5. Comparison mode.** For a world that already has a capture (from its ring, or from an earlier replay),
`--capture failure` computes the capture, compares its T2 bytes and snapshot hashes with the stored ones, stores
nothing, and returns `Bitwise` (exit 0) or the first differing tick with both digests (exit 2, and a row in the
divergence ledger).

**6. Refusals.** FROB-REF-840 (sealed confirmation run, exit 3); FROB-REF-802 (no failure trigger for the named
world and no marker; or a missing identity, BD-203's form; exit 3); FROB-REF-601 and FROB-REF-606 (exit 6; the
marker stays pending and the refusal names it); FROB-REF-894 from the container if the only snapshot before the
window is bound to another profile and a continuation was asked (exit 3).

**7. Layout.** `crates/frob-chronicle/src/device/reconstruct.rs`; the `failure` arm of
`crates/frob-verbs/src/verbs/sim_replay.rs`.

## Acceptance criteria

- [ ] For every failing world of a device run that has a `reconstruct` marker, `sim.replay --capture failure
      --markers` produces a capture, and afterwards every failing world has a full capture (T2 for the window
      and the T3 snapshots of that window); no marker remains pending unless a refusal names it.
- [ ] A capture obtained from the ring and the same window obtained by replay from the address have identical
      T2 bytes and snapshot hashes on the same backend (a ring-holding world captured a second time in
      comparison mode returns `Bitwise`).
- [ ] `frob telemetry query <run> --stream kinematics --world <w>` returns the same window for a ring world and
      for a reconstructed world, each with its leading gap record.
- [ ] Replaying the markers twice stores one capture per world; the second call returns the stored captures.
- [ ] Fifty markers replayed in one batch give the same bytes as fifty single replays.
- [ ] A capture snapshot whose recomputed digest differs from the replay's d_t is rejected and recorded in the
      divergence ledger (planted bit flip).
- [ ] FROB-REF-840, -802, -601, -606 and -894 each give their code and exit; under 601 and 606 the marker stays
      pending.

## Test plan

### Unit tests

`cargo test -p frob-chronicle reconstruct` and `cargo test -p frob-verbs sim_replay::failure`:
- `capture_failure_equals_ring` (moved from BD-203): a ring-holding world's flush and a replay capture of the same
  world in a run with rings disabled give equal T2 bytes and snapshot hashes (`batch-cpu`; each device present).
- `reconstruct_marker_equals_ring` (moved from N29a-11): on `batch-cpu`, the marker of a world without a ring
  turns into bytes equal to the ring capture of the same address in a run where it held one.
- `window_matches_ring_function`: terminal event at tick 500, 50 Hz, depth 100 ticks, post-window 10 ticks: T2
  ticks 411 to 510 and snapshots at 415, 420, …, 510, from both paths.
- `masked_reset_window_ends_at_terminal`.
- `leading_gap_recorded`; `marker_cleared_in_capture_txn` (a fault between the capture row and the clear leaves
  neither).
- `markers_replayed_once`; `batch_equals_singles` (50 markers).
- `comparison_mode_stores_nothing`; `comparison_mode_mismatch_exit_2` (one planted byte in the stored capture).
- `capture_snapshot_tripwire`.
- `sealed_840`; `no_trigger_802`; `backend_unavailable_601_marker_pending`; `fingerprint_changed_606`;
  `profile_mismatch_894`.

### End-to-end script and logging

Step group `reconstruct-*` of `scripts/e2e/sim_replay.sh` (owned by N29a-19), after the `ring-*` group's
4,096-world device run with a planted failure cluster: `frob sim replay --run <r> --capture failure --markers
--key rc-1 --json`; for three worlds without a ring, `frob telemetry query <r> --stream kinematics --world <w>
--json` returns the last 2 s; for one ring world, `frob sim replay --run <r> --world <w> --capture failure --key
rc-2 --json` returns `Bitwise`; the same `--markers` call again under a new key, `--key rc-3` (the same key
would only return the stored receipt), stores nothing new and returns the stored captures. Logs through the STD-E2E helper
to `target/e2e-logs/sim_replay/<utc>.ndjson`: per line `ts`, `script`, `bead`, `step`, `event`, the command,
exit code, wall time, the evidence block, the world address, the marker's tick range, the source (`ring` or
`replay`), the window in ticks, the snapshot count, the T2 bytes digest and snapshot hashes, the comparison
result, and on failure the first differing tick with both digests; a `summary` line.

### Known answers and negative controls

- Known answer: the window arithmetic above (ticks 411 to 510, twenty snapshots) on both paths.
- Negative controls: a reconstruction whose window omits the post-window (the window test fails); a capture
  without the leading gap record (bytes differ from the ring's); a capture stored without clearing its marker
  (the idempotency test finds two captures); a replay started from a snapshot of another profile labelled a
  continuation (894).
- Metamorphic: replaying the markers in one batch or one by one gives the same bytes (INV-CHRON-08).
- Determinism lanes: twice on one machine; `batch-cpu` across worker counts; ring against replay on each
  backend (class D2).

## Considerations

- Cost: one episode prefix per reconstructed world on its originating backend, less where a stored snapshot
  precedes the window; markers of a run are batched, so a failure cluster costs one batched replay.
- Pending markers survive a daemon restart (they are ledger rows); a capture job interrupted by a restart is
  re-run under its key.
- Captures inherit the run's privacy class and are retained as `failure-capture` (BD-209).
- Publishing into a run after it completed is the same extent the ring would have published; a reader paging the
  run at an older pin does not see it (pinned pagination), and a new query does.
