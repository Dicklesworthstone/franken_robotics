## Background

GATE-SKEL-08 is a first-milestone (M1) gate of the design language with three clauses: a stale parent refuses
in 100 of 100 trials; a repeated idempotency key returns the same `DesignId`; and a schema migration leaves
forward kinematics and mass properties bit-identical **and old runs replayable**. The design chapter states
the reason for the last words: a major schema version needs a migration, which reads the old object, writes a
new one with a `migrate` lineage edge, and *leaves the old object in place so that old runs replay against
the compiler version that produced them*.

Nothing at M1 delivers the replay half. The verb `sim.replay` (reproduce a world from its address, with
in-kernel digests and fence snapshots) is a second-milestone capability (BD-203), and replay of an old run by
the worker version that produced it, across real schema revisions, is a third-milestone lineage capability
(N28b-05). Without an M1 carrier the gate's script (N14a-29, step 11) can only log the clause as `partial`,
and a gate that is logged partial is not recorded PASS, so M1 could not exit.

What M1 already has is enough to close the clause if it is made precise. The M0 form of `sim.run` (BD-024)
defines *re-execution*: a second invocation with the same manifest has the same `RunId`, runs again, compares
its chunk digests with the stored ones, and returns `reproduced: true` or the finding `digest-mismatch`. That
was specified for the built-in fixture `g1` only. This bead extends re-execution to a run on a stored design,
and adds the one rule that makes it survive a migration: **a recorded run names its inputs by content
identity and by the schema version they were read under, never by a name or by the head of a lineage.** A
replay that resolved the design by name would pick up the migrated object and silently re-run a different
document; a migration that rewrote the object in place would leave the old identity naming other bytes.

Terms. The *referee* is the double-precision reference tier. A `DesignId` is the BLAKE3 hash of a design's
canonical bytes; a `ModelId` is the hash of the compiled mechanical model. The *version triple* of a design
is (schema major, minor, canonicalization revision); the major number is inside the hashed bytes, the other
two are in the artifact envelope stored beside the object. A *state digest* at M1 is the 32-byte BLAKE3 of
the canonical referee-state byte string, taken at the end of each chunk of L = 256 steps (BD-024's chunking of
a referee run: chunk ends at steps 256, 512, 768 and 960 for 2 s at 1/480 s). The T0 record keeps the full 32
bytes and re-execution compares at that width (the chunk row's 16-byte field is the `blake3-128` truncation of
BD-091's `digest_kind` rule and is compared as well). Tier: Solid.

Rejected alternatives: waiting for `sim.replay` (moves an M1 gate clause to M2); comparing compile products
only (proves the model is unchanged, not that the run is reproducible: packet queues, settle state and seeds
are outside the model); re-running by design name (the defect this bead exists to exclude).

## Scope

In: the identity block of the M1 run manifest for a run on a stored design; the pinned `recorded_command`;
the re-execution path for such a run (resolution by hash, reader dispatch on the recorded version triple,
digest comparison); its refusals; the unit and end-to-end tests, including re-execution after the head of
the design's lineage has moved by an edit and by a migration.

Out: the `migrate` edit, the migration fixtures and the meaning-preservation certificate (N14a-18); the gate
script and the gate record (N14a-29, which calls this bead's path at its step 11); the verb `sim.replay`,
in-kernel digests, snapshots and replay of one world out of a batch (BD-203); producer-worker resolution
across real schema revisions and the comparison-replay path (N28b-05); the transactional referee step itself.

## Technical approach

Layout (DESIGN): `crates/frob-chronicle/src/reexec.rs`; the handler change is in
`crates/frob-verbs/src/verbs/sim_run.rs`. No new verb is added: re-execution stays what BD-024 defined, an
invocation of `sim.run` whose manifest equals a stored one.

1. **Identity block of the manifest (schema `frob.run/1`, manifest core, canonical JSON).** For a run on a
   stored design the core holds, beside what BD-024 lists (tier, step as a rational, step count, seed, chunk
   length, stack receipt hash, the no-authorization flags): `design` (the `DesignId`), `design_version`
   (`{major, minor, canon_rev}` copied from the object's envelope at admission), `model` (the `ModelId`),
   and the scene, task and policy identities where the run has them. `RunId` = BLAKE3 of the core. The name
   the caller typed and the lineage head at admission are written to the `execution` entry only; they never
   enter the core (INV-CHRON-10: no trace identifier or wall-clock time enters a content hash; a mutable
   name is the same kind of thing).
2. **The recorded command.** `recorded_command` in the envelope is the argument vector with every default
   explicit and with the design written as `design:b3:<hex>`, whatever the caller typed, and without the
   idempotency key (BD-024's rule: the key is not part of the manifest, and a re-execution passes a fresh
   `--key`, because the same key returns the stored receipt without running and the same key with another
   request is FROB-REF-803). Running it later under a new key reproduces the manifest byte for byte regardless
   of where the lineage head now points.
3. **Re-execution.** On an invocation whose `RunId` already exists:
   1. Load each pinned object from the content store by hash. Name lookup is not available on this path:
      the function takes identities only (a type-level rule; `resolve_head` is not imported by `reexec.rs`,
      checked by a lint in the crate's tests).
   2. Read the design with the reader for the recorded `design_version` (the version dispatch of the design
      crate), not the newest reader, and do not recompute its identity under newer byte rules.
   3. Compile; assert the compiled `ModelId` equals the recorded one before any step is taken. A difference
      is the finding `model-mismatch` (exit 2) naming the first differing section digest.
   4. Step on the referee from the recorded initial condition and seed, computing the state digest at each
      chunk end, and compare with the stored chunk digests in order.
   5. Equal: add an `execution` entry and return the stored result with `reproduced: true`. Unequal: exit 2,
      finding `digest-mismatch` with the first differing chunk index and both digests; the run is marked
      `determinism-violated`. Nothing stored is overwritten in either case.
4. **Refusals (existing codes; none is added).** The pinned object's version is not readable by this build:
   FROB-REF-125 (unsupported schema version), exit 3, `required` naming the versions this build reads; no
   automatic migration is attempted, because a migrated object is a different input. The pinned object has
   been collected: FROB-REF-869 (the store's refusal for a tombstoned node in an evidence closure), exit 3,
   carrying the tombstone's reason (the retention rule that a later citation of a collected object fails with
   that reason). A design whose runs exist is in the evidence closure of those runs' T0 records and is not
   collected while they live. Collection itself is M2 (BD-209); the M1 test plants the tombstone row in a
   scratch store.
5. **After a migration.** `frob design edit <d> migrate --to <v>` creates a new object with a new
   `DesignId` and moves the head. The old object, its envelope and its runs are untouched. Re-execution of an
   old run therefore takes path 3 with the old version triple. A *new* run on the migrated design has a
   different `RunId` (the design identity differs) even when the migration is certified meaning-preserving
   and both designs share one `ModelId`; the two runs' chunk digests are then equal, which the test below
   asserts as a second, independent check of the migration.
6. **Evidence.** Class `Tested`, tier `referee`, determinism "bitwise on the same platform and binary";
   `reality: "no-claim"`. Determinism class of the comparison itself: D0.
7. **Switch-over.** When `sim.replay` lands at M2, N14a-29's step 11 runs both paths and requires equal
   verdicts; this path remains as the whole-run check that needs no snapshot.

## Acceptance criteria

- [ ] A referee run on a stored design writes a manifest core containing `design`, `design_version` and
      `model`, and a `recorded_command` that contains `design:b3:` and no design name.
- [ ] Running the recorded command under a fresh key in a fresh process after the lineage head has moved (by
      one `design.edit`) returns the same `RunId`, the same chunk digests and `reproduced: true`.
- [ ] The same after `migrate` on both meaning-preserving migration fixtures (the test-only major version
      and the test-only recanonicalization): `reproduced: true`, zero differing chunks; and a new run on the
      migrated design has a different `RunId`, an equal `ModelId` and equal chunk digests.
- [ ] With the planted defect "re-execution resolves the design by name" the test after the lossy migration
      fixture fails with `model-mismatch`; with "migration rewrites the old object in place" it fails with a
      content-hash mismatch at load.
- [ ] A pinned version triple the build cannot read is refused with FROB-REF-125, exit 3, and no migration
      is attempted; a tombstoned design is refused with FROB-REF-869, exit 3, and the tombstone's reason.
- [ ] The clause "old runs replayable" of GATE-SKEL-08 can be measured at M1 through this path: N14a-29's
      step 11 logs a result, not `partial`.
- [ ] Reachable through `frob --json` and the MCP tool `sim_run`; one envelope per call; cancellation between
      chunks leaves no new `execution` entry marked complete.

## Test plan

### Unit tests

`cargo test -p frob-chronicle --test reexec` (real store in a temporary directory, real compiler, the
referee; fixtures labelled `synthetic` are the test-only migrations):

- `manifest_core_pins_identities`: the core of a run on design `quad-tray` has the three fields; changing the
  typed name to an alias of the same object leaves `RunId` unchanged.
- `recorded_command_has_no_name`: the string contains `design:b3:`, no design name and no `--key`, and
  round-trips to the same core bytes.
- `reexec_needs_fresh_key`: the recorded command under the recording run's key returns the stored receipt
  without stepping (no new `execution` entry); under a fresh key it re-executes and adds one.
- `reexec_after_head_moves`: record a 2 s run (960 steps at 1/480 s, chunks at 256, 512, 768, 960); apply
  `set-param` thigh 0.21 m → 0.24 m; re-execute; four equal digests, `reproduced: true`.
- `reexec_after_major_migration` and `reexec_after_recanonicalization`: the same after each fixture.
- `new_run_on_migrated_design_matches`: different `RunId`, equal `ModelId`, equal four digests.
- `reexec_uses_recorded_reader`: an object stored under canonicalization revision 1 is read under revision 1
  after revision 2 exists; its recomputed hash equals its `DesignId`.
- `unreadable_version_refuses_125`; `tombstoned_design_refuses_869_with_reason` (tombstone row planted in the
  scratch store).
- `stored_digest_altered_is_mismatch_not_overwrite`: one stored chunk digest changed in a scratch ledger gives
  exit 2 naming chunk 2 and both digests; the stored row is unchanged afterwards.
- `reexec_has_no_name_lookup`: the lint that `reexec.rs` does not reference the head-resolution function.

### End-to-end script and logging

`scripts/e2e/chron_reexec_migration.sh --seed <s>` (the same commands N14a-29 embeds as its step 11):
(1) `frob design new` the worked quadruped in a scratch namespace with `--key rx-des-<s>`; (2) `frob sim run
<name> --tier referee --seconds 2 --seed <s> --key rx-rec-<s> --json`, keep `recorded_command` (which carries
no key) and the digests; (3) `frob design edit <name> migrate --to <test-version> --key rx-mig-<s> --json`;
(4) run the recorded command in a second process with `--key rx-reexec-<s>` appended; assert `reproduced:
true` and four equal digests; (5) `frob sim run design:b3:<new> --tier referee --seconds 2 --seed <s> --key
rx-new-<s> --json` and assert a different `RunId` with equal digests; (6) the lossy fixture's migration, its
new run and the old run's re-execution under their own keys (`rx-lossy-mig-<s>`, `rx-lossy-new-<s>`,
`rx-lossy-reexec-<s>`): assert the new run's digests differ and the old run still reproduces; (7) the
unreadable-version control under `--key rx-125-<s>`: assert exit 3 and FROB-REF-125. Every `run` and `mutate`
call carries its own key (`design.new` and `design.edit` are `mutate` verbs, which the admission transaction
refuses without one, FROB-REF-805, NJL-01), so no comparison is answered by a stored receipt. NDJSON per STD-E2E to
`target/e2e-logs/chron_reexec_migration/<utc-timestamp>.ndjson` with a transcript: `ts`, `script`, `bead`,
`step`, `event`, the exact command, exit code, wall time, the evidence block, `DesignId` and `ModelId` before
and after, the version triple, every digest compared, and on failure the first differing chunk with both
digests and the store path. The `summary` line gives assertions passed and failed and
`gates: ["GATE-SKEL-08"]` (touched; the gate record itself is written by N14a-29).

### Known answers and negative controls

- KA-292 (the three clauses of GATE-SKEL-08, exact, tier G4 on the host): this bead supplies the third
  clause's measurement: differing chunk digests after migration = 0.
- Negative controls (each must make a test fail): resolution by name; in-place rewrite by the migration; a
  re-execution that recomputes the design's identity under the newest canonicalization revision (caught by
  `reexec_uses_recorded_reader`); a comparison that stops at the first chunk (caught by the altered digest in
  chunk 2).
- Metamorphic relation: re-execution commutes with any sequence of edits and migrations applied to the
  lineage after the run was recorded.
- Determinism lanes: twice on one machine; debug and release on one platform. No cross-platform bit claim is
  made for the referee at M1.

## Considerations

- "The compiler version that produced them" has two readings. At M1 one binary holds the readers of every
  version it has written under, so the recorded reader is a dispatch inside the process. Replay by an older
  *binary* (a retained worker) is the M3 mechanism of N28b-05; this bead does not claim it.
- Only test-only migrations exist at M1, because only schema version 1 exists. The path is real; the
  versions are synthetic and labelled so.
- A run pins its design, so retention must treat a design with live runs as pinned. That rule is retention's
  (M2); until it exists nothing collects designs, which is the fail-closed state.
- The stack receipt hash is in the manifest core: a re-execution under a different build has a different
  `RunId` and is a new run, not a reproduction. That is intended and is stated in the envelope's determinism
  field.
