## Background

The record subsystem (crate `frob-chronicle`) owns the failure taxonomy: every terminal outcome has a *class*
(what went wrong) and a *kind* (whose failure it was). Classes, mechanical: `fall`, `stuck`, `collision`,
`self-collision`, `slip`, `torque-saturation`, `speed-saturation`, `thermal-limit`, `limit-impact`, `timeout`,
`numerical-fault`. Classes for the world and for perception, reported only when the feature that can produce them
is on in the scene or the model: `film-slip`, `thermal-runaway`, `brownout`, `perception-dropout`,
`localization-alias`, `pinch`, `snag`, `slosh-tip`, `gait-instability`, `observation-alias`, `timing-race`,
`model-drift`. Kinds: `physical` (the simulated robot failed), `numerical` (the solver or integrator refused or
faulted), `budget` (a limit stopped the run), `protocol` (the request was invalid). A numerical outcome leaves the
verdict unknown; it is not counted as a physical failure and it is not dropped from the denominator. Monitors
timestamp their first anomaly; the earliest anomaly before the terminal event is reported as the first cause, an
ordering labelled `Estimated`, a description and not an attribution.

The taxonomy, its monitors as pure functions of committed telemetry, and the verb `telemetry.failures` are seed
bead BD-094, delivered on the referee at the first milestone. The gate GATE-CHRON-08 closes at the second
milestone on a running batched system: "each failure class's monitor fires on its planted fixture, and a numerical
fault is never counted as a physical failure or dropped from a denominator". On a batched tier the first-milestone
approach does not carry over unchanged, for one reason: control-rate traces (level T2) exist only for an
address-sampled subset of worlds and for worlds that fail, so a monitor that reads the trace cannot see the
*early* anomaly of a world that was not sampled; by the time the world fails, only the last seconds are in the
ring. This bead closes that gap.

Design decision (DESIGN) and alternatives. Each monitor gets a device-side **latch**: one unsigned integer per
world and class holding the first tick at which the class's anomaly predicate was true, updated with an integer
minimum. Integer minimum is one of the four device-side atomics the evidence path licenses (integer maximum,
minimum, or and add; decision ADR-CHRON-03), so the latch has the same bits under any scheduling. Rejected:
tracing every world at control rate (the telemetry budget of GATE-CHRON-13 is 3% of step time for levels T0 and T1
on every world); evaluating monitors only on sampled worlds (first cause would be `unavailable` for most
failures); a floating-point "anomaly score" per world (order-dependent and not an event).

## Scope

In: the latch array and its update kernel; in-kernel anomaly predicates for the classes available at the second
milestone; emission of level-T1 first-anomaly events; the ring-flush trigger; kind counts on terminal receipts
from batched runs; the differential check against the host monitors; planted fixtures on batched tiers (the
registered fixtures `chron08/<name>`: one batch per class, `fault-batch`, `untraced-failure`); the end-to-end script
`scripts/e2e/failures_batched.sh`; the failure-taxonomy rows of GATE-CHRON-08 on `batch-cpu` and each admitted
device back end (measured here; the gate's one record is N29b-06's, whose script runs this one as a stage).

Out: the device ring itself, its freeze and its flush mechanics (bead N29a-11 of unit U29a, on which this bead
depends: the ring tests its flush with a planted bit, and this bead supplies the real failing bit and checks the
flush end to end); the always-traced failing stratum of the trace sample (bead N29a-12); class and kind
definitions, thresholds, first-cause ordering and the verb (BD-094); the ten later world and
perception classes (bead N24a-38 of unit U24a, which follows the same latch pattern when their features exist);
stills around the terminal event (BD-191); the created-energy half of the gate (bead N29a-22 of unit U29a; N29b-02 to N29b-04; BD-208).

## Technical approach

**1. Latches.** Per world: `first_anomaly[c]: u32` for each class c available in the build, initialised to
`u32::MAX` at reset; `terminal: { class: u8, kind: u8, tick: u32 }`. Update, once per control tick in the last
stage of the step: `first_anomaly[c] = min(first_anomaly[c], pred_c(world) ? tick : u32::MAX)`. The predicates
are select-only expressions over quantities the step already has: base tilt and height, contact provenance bits
(which link touched what), per-actuator saturation bits and thermal state, limit-row impulses, the world's
`Faulted` bit. Predicates that need a duration ("saturated continuously for 0.5 s", "advance below 2 mm over
0.5 s") keep a small saturating counter per world and class. Thresholds are the registry defaults of BD-094 or the
task's overrides, lowered into the step plan as constants, so they are part of the identity every result carries.

**2. Kernel (DESIGN name `K-x-monitor`, to be confirmed against the kernel registry).** One fixed-shape kernel over
worlds × classes; no data-dependent control flow across worlds; exact integer outputs (determinism class D0 for
the latches given the same physics bits; the predicates' inputs are class D2 per backend). A CPU reference
implementation exists in `frob-kernels` and is the differential oracle for the device forms.

**3. Events.** When a latch first becomes finite, the host writes one level-T1 event `{ class, tick,
channel_hint }` for that world at the next chunk boundary. Level T1 is recorded for every world, so first cause is
available for every failing world without a trace.

**4. Terminal outcome.** At a world's terminal tick the terminal class and kind are written to the episode row
together with all finite latches. Mapping of kinds: the `Faulted` bit gives class `numerical-fault`, kind
`numerical`; a compute or wall-clock budget stop gives kind `budget` and no class; the task horizon reached
unsatisfied gives `timeout`, kind `physical`. A world marked `Degraded` (capacity overflow, continue-flagged) is
not a failure of any kind; its flag travels separately.

**5. Ring flush.** The per-world ring of level-T2 traces and level-T3 snapshots is frozen and flushed to the store
when the world's terminal kind is `physical` or `numerical`, so that failures are always recorded in full without
paying to record everything. A numerical fault flushes too: a world that faults must keep its trace. The flush is
published through the chunk protocol like any other chunk; if the ring could not be flushed (device loss), the
interval is recorded as a gap with its reason.

**6. Receipts.** The terminal receipt of a batched run counts completed, failed, refused and unstarted trials and
separates three things that are never merged: a numerical refusal, a budget stop and a physical failure. Counts
are integer sums over worlds.

**7. Differential check (the CPU reference path).** For every traced world, the host monitors of BD-094 are run on
the committed trace and their first-anomaly ticks are compared with the latches: equal for predicates evaluated at
control ticks. A mismatch is a defect recorded with the world address and class.

**8. Fixtures.** The planted fixture of each class from the first milestone is run as a batch of 64 worlds in
which exactly 8 addresses carry the plant, on `batch-cpu` (`f32` and `f64`) and on each admitted device back end.
Each is a fixture of N24b-03's registry, named `chron08/<name>`, with its manifest
`assets/fixtures/chron08/<name>/fixture.toml` (kind `synthetic`; the batch's world addresses, and which of them
carry the plant, are rows of its input table, hashed before the first run): `<class>-batch` for each class
available at the second milestone; `fault-batch` (64 worlds, 4 with planted solver exhaustion);
`untraced-failure` (planted failing worlds outside the traced sample).

**9. Ring-depth re-read (the provisional half of OPEN-CHRON-2).** The decision record of N29b-18
(`docs/adr/ADR-CHRON-13.md`) fixed the ring depth at the first milestone without devices and marked it
provisional. On the fixtures of item 8 on each admitted device back end, this bead measures ring bytes per world
as stored, the flush time of a failing world, and the share of failing worlds whose latched first-anomaly tick
lies inside the ring window before the terminal tick; it applies N29b-18's rule (the smallest of 1, 2, 4 s with
at least 95% inside; if none, keep 2 s and record that first cause comes from the latches) and appends the
outcome to that record, re-affirming or changing `ring_seconds` with the Chronicle lead's sign-off.

**10. Layout.** `crates/frob-kernels/src/monitor.rs` (kernel and CPU reference),
`crates/frob-chronicle/src/failures/batched.rs` (events, terminal rows, flush trigger, differential check).

## Acceptance criteria

- [ ] For each class available at the second milestone, the 8 planted addresses of its 64-world fixture fire that
      class's latch and the other 56 do not, on `batch-cpu` and on each admitted device back end.
- [ ] On a batch with 4 planted solver faults among 64 worlds: kind `numerical` count 4; the physical-failure count
      excludes them; every denominator is 64; their rings were flushed.
- [ ] First cause is reported for failing worlds that were *not* in the traced sample (the latch path), labelled
      `Estimated`.
- [ ] Latch ticks equal the host monitors' ticks on every traced world of the fixtures.
- [ ] Latches, terminal rows and receipt counts are identical under a different batch size, slot assignment and
      co-tenancy, and across shard splits.
- [ ] The batched failure-taxonomy measurements that GATE-CHRON-08's single row needs are produced on `batch-cpu`
      and each admitted device with the two negative controls caught (a faulted world reported as `fall`; faulted
      worlds filtered before counting). The row itself is written once, by N29b-06, which depends on this bead.
- [ ] The monitor kernel's cost per world-step is measured on the reference quadruped workload at 1, 64 and 2,048
      worlds (ns per world-step and share of step time, with the bench disclosure fields) and recorded as a line of
      the level-T0 and level-T1 budget, which GATE-CHRON-13 (N29a-17) holds to at most 3% of step time together
      with the rest of T0 and T1 (that bead measures the whole budget with this kernel in the step).
- [ ] The ring-depth re-read of item 9 is appended to ADR-CHRON-13 with its three figures per back end and the
      rule's outcome.
- [ ] `scripts/e2e/failures_batched.sh` exits 0 on a correct build and non-zero under each of its four plants,
      with the plant's named assertion failed; its log passes the shared lint.

## Test plan

### Unit tests

- `latch_is_integer_min`: predicate true at ticks 400 and 430 → 400; never true → `u32::MAX`.
- `duration_predicate_counter`: torque limit held for 24 ticks at 50 Hz (0.48 s) → no anomaly; 25 ticks → anomaly
  at the tick the 0.5 s completes.
- `fault_bit_maps_to_numerical`; `budget_stop_has_no_class`; `degraded_is_not_failure`.
- `first_cause_from_latches`: latches (thermal-limit 400, torque-saturation 430, fall 520), terminal fall at 520 →
  first cause thermal-limit, lead 120 ticks.
- `flush_on_physical_and_numerical_only`: completed and budget-stopped worlds do not flush.
- `receipt_counts_sum_to_planned`: 64 planned = completed + failed + refused + unstarted for random terminal
  states.
- Property: latches invariant under permutation of worlds within a batch and under batch size (seeded).
- `ring_share_rule`: shares inside the ring of 0.93, 0.97 and 0.99 for 1, 2 and 4 s select 2 s; shares of 0.80,
  0.90 and 0.94 keep 2 s and record "first cause from latches".

### End-to-end script and logging

`scripts/e2e/failures_batched.sh` (owned here; header `bead=N29b-05 milestone=M2 gates=GATE-CHRON-08 seed=<s>
plants=fault-as-fall,fault-filtered,latch-last-writer,flush-physical-only`; N29b-06's `gate_chron_08.sh` runs it
as its stage `failures-batched` and reads its summary). Per fixture `<f>` and lane `<l>`: `frob sim run --tier
<t> [--precision <p>] --worlds 64 --fixture chron08/<f> --seed <s> --key fb-<f>-<l> --json`, then `frob
telemetry failures <run> --json`. The lanes are `cpu64` (`--tier batch-cpu --precision f64`), `cpu32` (`--tier
batch-cpu --precision f32`), and `cuda` (`--tier gpu-cuda`) and `metal` (`--tier gpu-metal`) where the device
exists (otherwise the step is logged `not-run` with the reason); the lane is in the key because the two
precisions are two requests, and one key with other content would be refused (FROB-REF-803). Determinism repeats
carry their own keys (`fb-<f>-<l>-r2`, and `fb-<f>-<l>-b<n>` with another batch size), so no repeat receives the
first run's stored receipt. The options are the rows' (VERBS-sim): `--tier`, `--worlds` on the batched tiers
(N16b-25), `--precision` (N35-04), `--fixture` (N24b-03).
Asserts per-class counts 8 of 64, the kind split, the denominators, first cause on an untraced failing
world, the flush, and latches equal under the repeats. Each of the four plants (run with `E2E_PLANT_FAILURE`, the
conformance build) must fail its named assertion. NDJSON lines through the shared helper (`ts`, `script`, `bead`,
`step`, `event`): command, exit code, wall time, evidence block (tier, determinism class, seed), per-class counts as
"k of n", latch-against-host mismatches (expected 0), digests of the latch arrays compared across repeats; on
failure the first world address and class that differ and the chunk range holding its ring; a final `summary`
line with assertions passed and failed, controls caught and the gate touched. The script writes no gate record.

### Known answers and negative controls

- Gate text, second sentence of GATE-CHRON-08: each failure class's monitor fires on its planted fixture, and a
  numerical fault is never counted as a physical failure or dropped from a denominator.
- Negative controls: a faulted world reported as `fall`; faulted worlds filtered before counting; a latch updated
  with a last-writer-wins store instead of a minimum (order-dependent, caught by the permutation property); a
  flush only for `physical` kinds (the fault's trace is missing).
- Counterexample carried from the dynamics chapter (CX-150): a candidate with 2 successes in 2 valid trials and 98
  unresolved has a complete-case rate of 100% and a true rate anywhere in [2%, 100%].
- Determinism lanes: twice on one machine; across worker counts; `batch-cpu` against each device (latches exact
  wherever the physics bits agree; otherwise compared within the tolerance class by decision, that is, the same
  class at a tick within the declared envelope).

## Considerations

- Classes whose predicates need quantities that are not in the step (for example a localization alias) cannot be
  latched in-kernel; they stay host-side on sampled worlds and report `first cause: unavailable` elsewhere. The
  registry row of the class says which path it uses.
- Latch memory: classes × 4 bytes per world plus counters; 13 classes at the second milestone (the eleven
  mechanical classes, `thermal-runaway` and `brownout`) is 52 bytes of latches plus 2-byte duration counters for
  the classes that need them, about 100 bytes per world.
- The latch records the first anomaly, not every one; repeated saturation episodes are level-T1 events from the
  saturation channels themselves.
- Kernel naming is a proposal; the kernel registry's owner confirms it, and the step-plan identity changes when
  the monitor set changes.
- Risk RISK-15 (failures moved out of the denominator) is mitigated here on batched tiers by the receipt identity
  and its property test.
