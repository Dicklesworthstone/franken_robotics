## Background

The record subsystem's artifact graph ties every claim to its evidence with four kinds of identifier:

```
ClaimId            BLAKE3( claim type ‖ subject identities ‖ statement ‖ scope )
EvidenceId         BLAKE3( kind ‖ payload hash )
DecisionPolicyId   ( dotted rule name, version )        e.g. ("atelier.dc01.promote", 3)
TraceId            128-bit, time-ordered identifier of the execution that produced an evidence item
```

Two of the four have a ready-made counterpart in a sibling library. FACT (read at
`/Users/jemanuel/projects/asupersync/franken_kernel/src/lib.rs`): the crate `franken_kernel` defines `TraceId` (a
`u128` serialized as hex, with a UUIDv7-style layout: the high 48 bits are a millisecond Unix timestamp, saturated
to 2⁴⁸ − 1, and the low 80 bits are random), `DecisionId` (a `u128`, hex) and `PolicyId { name, version: u32 }`
serialized with the field names `n` and `v`, a dotted name such as "scheduler.preempt". Its only dependency is
`serde`. It has no claim or evidence identifier. The suite convention this project adopts (DESIGN) is that
`frob-core` mirrors the text form of the identifiers the sibling has, adds `ClaimId` and `EvidenceId` in the same
form, and offers the two new types upstream (upstream work item FD-FKER-01, priority P3; interim posture: local
types with the same text form; switch-over: replace the local types).

A naming trap is already resolved and binds either outcome: the sibling's `PolicyId` names a *decision rule*,
while this project's `PolicyId` (the identity table of the foundations chapter) names a *control policy* by
content hash. The decision-rule identifier is therefore called `DecisionPolicyId` throughout this project,
whichever crate supplies the type.

The open question OPEN-CHRON-3: are the identifier types **imported from `franken_kernel`** under the suite's
single-version rule for asupersync, or **defined locally with the same layout**? Owner: suite lead. It blocks
GATE-CHRON-10 (the artifact graph's gate, first milestone), because `ClaimId`s and trace identifiers are written
into `registries/gates.toml`, bead logs and every envelope from the first recorded gate onward, and changing
their wire form later would orphan recorded evidence.

**Fail-closed default that holds until this bead is closed: defined locally in `frob-core`**, with a wire layout
identical to the sibling's, so that a later switch to the import changes no stored byte and no hash.

## Scope

In: the comparison of the two options against stated criteria; a layout-compatibility test that makes the default
safe; the decision record; the consequences for `frob-core` and for the auditor crate.

Out: implementing the artifact graph and `evidence.trace` (seed BD-095); the `ClaimId` and `EvidenceId` preimages
(they are this project's own in both options; BD-095 and N29b-10).

## Technical approach

**1. Options.**

| | A: import from `franken_kernel` | B: define locally in `frob-core` (default) |
|---|---|---|
| Types affected | `TraceId`, and `DecisionPolicyId` as a newtype or alias of the sibling's `PolicyId`; `ClaimId` and `EvidenceId` too once FD-FKER-01 has landed upstream | All four local; `ClaimId` and `EvidenceId` are local in both options until FD-FKER-01 lands |
| Benefit | One definition across the suite; traces from the runtime's own instrumentation and ours are the same type with no conversion | `frob-core` keeps a dependency table it fully controls; no coupling of the identity layer to a sibling's release train |
| Cost | `frob-core` (the bottom layer, on which the standard-library-only auditor and every crate depend) gains a sibling dependency; a sibling version bump can touch the identity layer; the name `PolicyId` must be re-exported under `DecisionPolicyId` and the sibling name hidden | Two definitions that can drift; a conversion at the boundary where the runtime hands us a trace identifier |
| Failure it risks | A second asupersync-family package version in a workspace, which the dependency check forbids (RISK-03: two asupersync versions in one build) | Silent layout drift between the two definitions |

**2. Criteria, fixed before the decision (evidence decides where evidence exists).** Option A is chosen only if
all four hold; otherwise B stands.
1. `franken_kernel` can be depended on from `frob-core` without bringing the asupersync runtime, or any crate
   other than `serde`, into `frob-core`'s dependency closure (`cargo tree -p frob-core` shows exactly one added
   package), and `check-layers` and `check-deps` pass.
2. The single-version rule holds with the import in place: the admission check that every workspace contains
   exactly one asupersync package (seed BD-008) is green, and `franken_kernel` resolves from the same pinned
   source as the rest of the stack lock.
3. The auditor crate (standard library only, its own stable toolchain file) does not need the types: it reads
   identifiers as strings from canonical JSON. If it would need the import, A fails.
4. The sibling's wire forms are exactly the ones in item 3 below and are covered by the sibling's own tests, so a
   sibling release cannot change them unnoticed.

**3. The layout both options must satisfy (DESIGN, fixed now).**
- `TraceId`: `u128`; JSON form a 32-digit lowercase hexadecimal string; high 48 bits a millisecond timestamp, low
  80 bits random. It identifies an execution and **never enters a content hash**.
- `DecisionPolicyId`: `{ name: DottedName, version: u32 }`; JSON form `{"n": "<dotted name>", "v": <u32>}`;
  dotted names are lower-case ASCII segments separated by `.`, for example `atelier.dc01.promote`.
- `ClaimId`, `EvidenceId`: 32-byte BLAKE3 digests; text form `clm:<64 lowercase hex digits>` and
  `evd:<64 lowercase hex digits>`. The plan prints a claim identifier two ways: `clm:…` in the gate registry's
  example row and `c:…` in the bead-log example, and the artifact-graph and bead-log beads of unit U29a follow
  the second. `c:` is already the prefix of a controller identity in envelopes, so this decision fixes one form
  for every place a claim is printed, and `clm:` is the proposal (DESIGN). The parser of one kind rejects the
  text of another.
- Integers that can exceed 2⁵³ are strings in every JSON view (hex here).

**4. The compatibility test (makes the default reversible).** A dev-only test in `frob-core`
(`tests/kernel_layout_compat.rs`, enabled by a feature that adds `franken_kernel` as a dev-dependency at the
stack lock's pin) asserts, for 10³ seeded values: serialization of the local `TraceId` equals the sibling's byte
for byte; `from_parts(ts, random)` agrees, including saturation at 2⁴⁸ − 1; the local `DecisionPolicyId`
serializes to the same bytes as the sibling's `PolicyId` for the same name and version; ordering agrees. The
feature is off in release builds, so option B ships with no sibling dependency while the test keeps option A open.

**5. Procedure.** (a) Run the four criteria on the pinned stack; record `cargo tree` output, the two checks'
results and the compatibility test's result. (b) The suite lead decides. (c) Write `docs/adr/ADR-CHRON-10.md`
(proposed identifier): the option, the measurements, and what would reopen it (a sibling layout change; the
identity layer needing more of the sibling's vocabulary). (d) Tombstone OPEN-CHRON-3 in the open-question register
with the decision record's identifier; a closed question is tombstoned, not reused. (e) If A: replace the local
definitions by re-exports in one commit, with the compatibility test promoted to a permanent wire-format test.

## Test plan

### Unit tests

- `trace_id_layout`: `from_parts(1_700_000_000_000, 0xABCD_EF01_2345_6789_AB)` → high 48 bits equal the
  timestamp, low 80 bits equal the random value; hex round trip.
- `trace_id_saturates`: a timestamp of 2⁴⁸ + 5 stores 2⁴⁸ − 1 and leaves the random field intact.
- `decision_policy_id_wire`: `("atelier.dc01.promote", 3)` → `{"n":"atelier.dc01.promote","v":3}`.
- `claim_and_evidence_text_forms`: `clm:` and `evd:` prefixes with 64 hex digits; a `clm:` text is rejected by the
  `EvidenceId` parser and the reverse; `c:` is rejected as a claim.
- `dotted_name_grammar`: `a.b`, `atelier.dc01.promote` accepted; empty segment, upper case and whitespace refused.
- `kernel_layout_compat` (feature-gated): 10³ seeded values agree with the sibling byte for byte.
- `trace_id_not_hashable_into_content`: compile-fail test: a `TraceId` cannot be passed to the content-hash
  builder (the sealed trait for hash preimages is not implemented for it).

### End-to-end script and logging

A step `ids-wire` added to `scripts/e2e/evidence_trace.sh` (the script of bead N29a-10 for the artifact graph's
gate) reads one envelope, one gate row and one bead-log line and checks the four identifier forms with regular
expressions, logging each identifier class, its form and the layout version, per the shared logging helper
(command, exit code, wall time, the evidence block). No separate script: a decision has no runtime behaviour of
its own.

### Known answers and negative controls

- The doc-example value of the sibling type (`1_700_000_000_000`, `0xABCD_EF01_2345_6789_AB`) as the pinned known
  answer for the layout.
- Negative controls: the planted layout swap; a build in which `PolicyId` is re-exported under its sibling name
  (the lint must fail); a build in which a trace identifier is mixed into an `EvidenceId` preimage (the
  compile-fail test, and INV-CHRON-10: no trace identifier or wall-clock time enters a content hash).

## Considerations

- Why the default is B: the identity layer is the one place where an unplanned dependency change is most
  expensive, and the benefit of A is convenience at one boundary. The compatibility test costs little and removes
  the main argument against B (drift).
- Interim posture and switch-over rule: local types now; switch only by the procedure above; never both in one
  build.
- This decision blocks the first recorded gate, so it is one step more urgent than its milestone. The artifact
  graph bead proceeds on the default without waiting; what it must not do is record a gate with any other layout.
- `DecisionId` of the sibling (a `u128` per decision instance) has no counterpart in this plan's four identifiers;
  decisions of a decision core are ledger rows keyed by content. If a later bead wants per-decision instance
  identifiers it reopens this record rather than adding a fifth type ad hoc.
