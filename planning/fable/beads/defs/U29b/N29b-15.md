## Background

The record subsystem (crate `frob-chronicle`) states thirteen invariants. An invariant is a property that must
hold in every state the system can reach; the project's testing rule is that every invariant has a property test
and that every gate has at least one planted defect it must catch, because a gate that nothing can fail validates
nothing. The mechanisms these invariants constrain are spread over many beads and three milestones: the chunk
protocol, pagination, tracing by address, histograms, forks, digests, the energy ledger, the artifact graph,
summaries, retention and the tier-correction ledger. Each mechanism bead tests its own invariant where it can.

This bead exists so that no invariant depends on a mechanism bead remembering it. It is the single place where
all thirteen are written down as executable properties, each with a planted violation, registered in the
conformance harness with its verification tier and execution site, and run together. It is a test bead: it adds
no mechanism. Where a mechanism bead already owns a strong test, this suite calls it; where none does, the test
is written here.

The verification tiers referred to below: G0 laws and self-tests; G1 known answers; G2 parity; G3 metamorphic
relations; G4 chaos (faults, cancellation, crash consistency, deterministic simulation); G5 determinism (twice on
one machine; across worker counts; debug and release; across platforms and backends, each against its class).

## Scope

In: one test module per invariant under `crates/frob-conformance/tests/inv_chron/` (the target exists from the
first milestone with module 14, N29bx-01); one registered planted violation per invariant; the registry records,
including the thirteen rows of `registries/invariants.toml` section `chronicle` in the format of N29bx-01's row;
the staging of modules by milestone; the suite's own summary over fourteen modules.

Out: the mechanisms; the simulation harness (seed BD-096) and its scenario families (N29b-11: families P, R and
L serve modules 04, 12 and 01 to 03 at the second milestone), which this suite invokes for the fault-dependent
invariants; proof obligations (N29b-16); INV-CHRON-14, the fourteenth invariant, registered by
N29bx-01 in the same directory and the same staging; the round store's property behind INV-CHRON-13
(`no_order_violates_inv13`, N29b-08, third milestone), which module 13 calls once it exists; the control rows that
the seeding tool of N38b-05 writes from catalogue entries and known-answer cells (item "Registry").

## Technical approach

**The thirteen properties.**

| ID | Statement | How it is checked | Planted violation | Tier; from |
|---|---|---|---|---|
| INV-CHRON-01 | A committed chunk key maps to one content hash for the life of the run. | 10⁴ seeded publish sequences with duplicates, retries and crashes (simulation harness): for every key the set of committed content hashes has size 1; a second publish with other bytes is refused (FROB-REF-878) and marks the run `determinism-violated`. | A publisher that overwrites on conflict | G4 · daemon; M1 |
| INV-CHRON-02 | For every (run, world, episode, stream) the committed chunks are exactly the indices 0 to the frontier. | After every scenario and at every quiescent point: the index set equals {0, …, frontier}; out-of-order or misaligned chunks are refused (FROB-REF-885). | The frontier advanced before the row is durable (the lost-chunk plant) | G4 · daemon; M1 |
| INV-CHRON-03 | One idempotency key yields one job, one budget charge and one receipt, under any crash or retry. | Crash at every await point of submit; duplicate and reordered delivery; reconnect by key: counts of jobs, charges and receipts per key are (1, 1, 1). | A charge taken before the idempotency row commits | G4 · daemon; M1 |
| INV-CHRON-04 | A paginated query returns every row visible at its pin exactly once. | 10⁴ rows read in pages during concurrent appends; the multiset of returned rows equals the pinned set. | Ordering by timestamp alone | G4 · daemon; M1 host, M2 devices |
| INV-CHRON-05 | The set of traced worlds is a pure function of the run manifest and the addresses. | The traced set recomputed from the manifest alone equals the recorded set under 100 slot assignments, shard counts and co-tenancies. | Arrival-order reservoir sampling | G5 · all tiers; M2 |
| INV-CHRON-06 | Every evidence aggregate has the same bits under any permutation of worlds, shard split and merge order. | Every aggregate kind on the evidence path (counts, integer sums, minima, maxima, bitwise or, integer histograms, the quantized energy tables, flag counts, tier-correction moments) under 100 permutations and 10 shard splits. | An order-dependent quantile sketch on the evidence path; a floating-point cross-world sum | G5 · all tiers; M2 |
| INV-CHRON-07 | A fork with the empty change set equals the replay, bit for bit on the same backend. | 1,000 worlds: digests of `run.fork` with the empty change set equal `sim.replay`'s at every chunk. | A fork that re-initializes one warm start | G5 · per backend; M2 |
| INV-CHRON-08 | A world's digests do not depend on batch size, slot or co-tenants. | 1,000 worlds replayed alone, in a batch of another size and among other co-tenants: identical digests on the same backend. | A reduction whose tree depends on batch capacity | G5 · per backend; M2 |
| INV-CHRON-09 | The lines of the energy ledger, including the residual line, sum to zero; no physical term absorbs the residual. | On every committed interval of the fixtures: the signed sum of lines is zero within the tier's bound (10⁻⁹ relative on the referee, 10⁻³ in single precision), and the residual line equals the independently recomputed remainder. | The residual folded into contact dissipation; a sign error at one port | G1 · referee and lockstep; M1 referee, M2 batched |
| INV-CHRON-10 | Every printed claim resolves in the artifact graph; no trace identifier or wall-clock time enters a content hash. | Every envelope of a recorded session is scanned: each claim identifier resolves; the same work run twice gives equal evidence identifiers and different trace identifiers; compile-fail tests on the preimage builder. | A claim printed after its evidence was collected; a trace identifier mixed into a preimage | G1 · host; M1 |
| INV-CHRON-11 | Every summary states its denominator, and its counts sum to the planned total. | A schema-driven test over every verb whose output is marked `summary` in the registry: a denominator and a frontier are present; completed + failed + refused + unstarted = planned; for a paired study the five cells of its accounting identity sum to planned; progress is "k of n", never a bare percentage. | A summary that drops refused episodes; a bare percentage | G1 · host; M1 |
| INV-CHRON-12 | Collection never removes a pinned object, and every removal leaves a tombstone. | 10⁴ random collection cycles on the real collector and the retention scenarios of the simulation harness. | A sweep that does not re-check pins after the mark; a delete without a tombstone | G4 · daemon; M2 |
| INV-CHRON-13 | The audit set of a tier-correction round is fixed before any referee outcome of the round exists, and every audit probability is at least the floor. | Random operation sequences against the round store (N29b-08): no state has an outcome that precedes its round's assignment, and no stored probability is under 1/20. | Audit bits chosen after seeing fast-tier failures | G1 · host; M3 |

**Staging.** This suite lands at the second milestone. A module whose subject does not exist yet is registered
and reports `not exercised` with the milestone at which it becomes mandatory; the suite fails if a module is `not
exercised` after its milestone. At this bead's close (second milestone) modules 01 to 12 are mandatory: 01 to
04, 09, 10 and 11 on the host and referee (their subjects exist from the first milestone, where the mechanism
beads' own tests cover them; the "from" column says when each subject appeared), 05 to 08 and 12 on every tier
their row names, and the device rows of 04 and 09. Module 13 is written here as a thin call into the round
store's property and is registered `not exercised (due M3)`; bead N29b-08 (third milestone, which depends on this
one) turns it on, so no criterion of this bead waits for a later milestone.

**The summary-schema test of INV-CHRON-11.** Output schemas mark each summary field with the annotation
`x-frob-summary: true`, whose object is `{ value, planned, used, excluded: [{ reason, count }], denominator }`
(N35-28, which owns the annotation and FROB-REF-865; an earlier draft of this bead invented a separate
`summary = true` field on the verb entry, and one mark is enough). The test loads every schema with the
annotation and a recorded example output per verb and asserts the fields and identities above. A new summarizing
field without the mark is caught by a second rule: any output schema containing a field named `rate`, `share`,
`percent` or `progress` must either carry the annotation or an exemption with a reason.

**The aggregate inventory of INV-CHRON-06.** The test enumerates aggregate kinds from the channel and ledger
schemas rather than from a hand-written list, so a new aggregate is permuted without anyone adding it.

**Registry.** Every planted violation is a control in `crates/frob-conformance/registry/controls.toml` (the
record of BD-025: `id`, `seed`, `gate`, `kind`, `target`, `defect`, `expect`, and `feature` for a mutation),
attached to the gate that must catch it: GATE-CHRON-04 (01 to 04), GATE-CHRON-07 (05, 06), GATE-CHRON-05 (07),
GATE-CHRON-01 (08), GATE-CHRON-03 (09), GATE-CHRON-10 (10), GATE-CHRON-12 (12), GATE-CHRON-09 (13). Two sources,
one row per defect:
- *Plants that already have a control.* A plant that is a catalogue entry's or a known-answer cell's control is
  written by the seeding tool of N38b-05 from N29-CX's entry, never as a row here: 04 is CX-323's
  `mutant-chron-page-by-time`, 05 CX-325's `mutant-chron-arrival-reservoir`, 06 CX-319's
  `mutant-chron-order-sketch`, 10 the artifact graph's known-answer control (KA-720), 12's pin-after-verdict half
  the appended entry `chron-pin-after-verdict`, 13 CX-324's scripted auditor. The module builds the same feature
  or fixture and records the run against that control's `NC-` identifier; the linkage test of N29-CX checks the
  carrier.
- *Plants with no row yet.* 01 (overwrite on conflict), 02 (frontier advanced before the row is durable, when
  BD-096's lost-chunk control does not already name GATE-CHRON-04), 03 (charge before the idempotency row), 07,
  08, 09, 11 and 12's sweep-without-re-check and delete-without-tombstone halves get new `[[control]]` records
  here, `kind = "mutation"` with a `feature` in the target crate, `seed = "INV-CHRON-nn"` (DESIGN: the invariant
  the plant violates, as other units name a risk; flagged for BD-025's owner if the loader admits only CX and KA
  seeds) and `due` the module's milestone.
INV-CHRON-11 has no gate of its own in the register; its control is attached to GATE-CHRON-10's run as a recorded
check, and the missing gate is reported in the unit's coverage notes.

**Scale-down.** Each module takes its sample size from an environment variable with the stated value as default;
the per-change lane uses a tenth; the count used is logged.

## Acceptance criteria

- [ ] Thirteen modules exist and are registered with tier and execution site beside N29bx-01's module 14; the
      suite prints one line per invariant (fourteen) with status `pass`, `fail` or `not exercised (due M<n>)`;
      `registries/invariants.toml` section `chronicle` has fourteen rows.
- [ ] At the second-milestone exit, modules 01 to 12 pass on the host and on every admitted backend their row
      names; module 13 is registered and prints `not exercised (due M3)` (N29b-08 turns it on).
- [ ] Every planted violation of modules 01 to 12 is caught by its module (12 of 12), and each is recorded against
      the gate named above: through the seeded control's `NC-` identifier where one exists, through a new row
      here otherwise; no defect has two rows (a join of `controls.toml` on `feature` and `target` finds no
      duplicate).
- [ ] The summary-schema test covers every output field annotated `x-frob-summary: true` and fails when a
      planted verb omits its denominator or carries a `rate` field without the annotation or an exemption.
- [ ] The aggregate inventory is derived from schemas; adding a planted floating-point aggregate to a schema makes
      INV-CHRON-06's module fail without any edit to the test.
- [ ] No module is `not exercised` after its milestone.

## Test plan

### Unit tests

The modules are the tests: `inv_chron_01_one_hash_per_key` … `inv_chron_13_audit_fixed_first`. Each has a
`#[test]` for the property and a `#[test]` named `…_plant_is_caught` that builds the planted variant (behind the
`conformance` feature) and asserts the property test fails on it. Pinned small cases inside the modules: for 06
the compactor example (streams 1, 2, 3 and 3, 2, 1 give medians 1 and 2 under a capacity-two compactor that keeps
the lower of each sorted pair, while integer bin counts are 1, 1, 1 in both orders); for 04 rows at times 1, 2, 3,
4 with page size 2 and a late commit at 1.5 (offset paging repeats row 2); for 11 a run of 2,048 planned episodes
with 1,312 committed, printed "1,312 of 2,048".

### End-to-end script and logging

`scripts/e2e/chronicle_invariants.sh` runs `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test inv_chron
--features gauntlet-mutations` in the lane's configuration (the planted variants run in the same invocation) and
one user-side pass: it records a short session of real `frob` commands (a run, a summary, a histogram, a fork
with the empty change set, a collect) and replays the recorded envelopes through the scanners of modules 10 and
11. The session, each run-kind call under its own key: `frob sim run <reference quadruped> --tier batch-cpu
--worlds 16 --seconds 2 --telemetry T3 --seed <seed> --key inv-run --json` (T3, so that the fork starts from a
stored snapshot); `frob telemetry summary <run> --json`; `frob telemetry histogram <run> --channel <a declared
channel> --json` (the verb of N29a-15); `frob run fork <run> --world <w> --at <tick> --key inv-fork --json` with
no `--change`, which is the empty change set; `frob store collect --key inv-collect --json` (the key makes it a
real collection; without one the call is a dry run). NDJSON lines per the shared helper (`ts`, `script`, `bead`,
`step`, `event`): command,
exit code, wall time, per-invariant status, sample sizes used against their defaults, plants caught of plants run
with each control's `NC-` identifier, and for a failure the invariant, the first violating state, the seed and
the command that replays it. A `summary` line lists the gates whose controls were exercised and the modules still
`not exercised` with their due milestone.

### Known answers and negative controls

- The plants above (twelve run at this bead's close; the thirteenth with N29b-08); the pinned small cases
  (CX-319, CX-346's offset-paging case as cited from the surface chapter, the progress example).
- Known answers touched: KA-711, KA-712, KA-713, KA-714, KA-716, KA-707, KA-720, KA-719 (each owned by its
  mechanism bead; this suite asserts that the invariant behind it holds on more than the pinned case).
- Determinism lanes are the content of modules 05 to 08: twice on one machine; across worker counts; debug and
  release; `batch-cpu`, CUDA and Metal each against its class.

## Considerations

- Duplication with mechanism beads is deliberate and cheap: where a mechanism bead's own test exists, the module
  here is a thin call into it plus the plant, so there is one implementation of each property.
- INV-CHRON-03 is shared with the surface subsystem (one job and one charge per principal, verb and idempotency
  key); the module asserts Chronicle's half (one receipt, one set of chunks) and calls the surface's test for the
  charge.
- A module that passes trivially is the main risk of a suite like this. Rule of the control registry: a control
  that has never failed its gate in any recorded run is itself suspect and is reviewed at each milestone exit.
- Device rows need hardware; a host without a device logs the row `not-run` and the exit review decides coverage.
