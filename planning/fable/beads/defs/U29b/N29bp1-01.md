## Background

Decision ADR-CHRON-07 of the record subsystem (crate `frob-chronicle`): **no claim without a trace.** Every claim
that crosses the agent boundary has a `claim_id` that resolves in the artifact graph (the content-addressed graph
of claims, evidence items, decision rules and executions) to its evidence, to the version of the rule that decided
it and to the executions that produced it. A claim whose closure contains a dangling or tombstoned node prints
`evidence: unavailable` and cannot be cited (FROB-REF-869). Two records rest on such claims for the life of the
project: each part of a gate row in `registries/gates.toml` whose status is `pass` (the gate registry), and each
bead's closing line in its append-only log `docs/delivery/logs/<bead>.ndjson` (schema `frob.beadlog/1`), which
must carry `verdict = pass` and resolving `claim_ids`.

The citation guard (N29b-10) makes the rule hold at the moment a claim is printed or cited: the recorder cannot
write a `pass` part, and the bead log cannot take a closing line, whose claim does not resolve. A recorded PASS can
still become untraceable later: a claim is withdrawn (its pins released, its evidence then collected), a private
scene is purged with its lineage, a store is lost or rebuilt. The gate table and the honest-status table would
then go on showing a PASS that nothing supports, which is exactly the false progress the verification chapter's
premortem warns of (story 8: "the swarm closed beads that proved plumbing"). This bead is the pass that re-checks
every recorded PASS against the live store and demotes, visibly and without deleting anything, those that no
longer resolve.

Split from N29b-10 in polishing round 1: the guard is code in `frob-verbs` and `frob-chronicle` on the request
path; re-affirmation is a mode of the gate recorder in `frob-conformance` that runs at milestone exits and
releases, with its own inputs (the gate registry and the bead logs) and its own tests.

Rejected alternatives: deleting a PASS whose evidence is gone (the history of what was claimed is itself evidence,
and deletion hides the event); leaving the row and printing a warning (the status table is generated from the row,
so the warning is lost at the first regeneration); re-running the gate automatically (a re-run is a new
measurement by a fresh session, recorded through the recorder like any other; this pass only says the old one no
longer stands).

## Technical approach

**1. Inputs.** The gate registry `registries/gates.toml` in the schema of N38b-18: each gate has a gate-level
`claim_id` (`clm:<64 hex>`) and one `[[gate.part]]` per milestone with `status`, `measured`, `evidence` (ledger
sequence numbers and trace identifiers), `recorded = { date, session, implemented_by }` and `detail`. The bead logs
of N29a-09: per bead, the latest line with `verdict = pass` that closed it, with its `claim_ids`. The live store,
read through `state_of(claim, at, scopes)` of N29b-10 at the store's current frontier with the recorder's full
scope (so a private node is never a reason to demote; `PrivateNoScope` applies only to unscoped callers).

**2. The walk (`cargo run -p frob-conformance --example record_gate -- reaffirm --registry registries/gates.toml
--logs docs/delivery/logs --store <path> --json`: the mode word `reaffirm` of the recorder's example target.
There is no `frob-conformance` binary and no second recorder command; with no mode word the example records).**
1. For each gate, in identifier order, and each part with `status = "pass"`: compute the state of the gate's
   `claim_id` and resolve each evidence item of the part. The part stands if the claim is `Resolved` and every
   evidence item resolves.
2. For each bead whose latest decisive line is a closing line (`verdict = pass`): compute the state of each of
   its `claim_ids`. The closing stands if every one is `Resolved`.
3. Demote what does not stand (item 3); leave everything else byte-identical.
4. Write the report (item 4). Exit 0 when nothing was demoted; exit 2 (completed with findings) when something
   was.

**3. Demotion (nothing is deleted).**
- *Gate part.* `status` becomes `not-run` (in the registry's meaning: no current record, never shown as passed).
  The part's former `measured`, `evidence` and `recorded` move into `detail.demoted_from`, beside
  `detail.cause = "evidence-unavailable"`, the missing nodes `[{node, kind, why}]` (why ∈ dangling, tombstoned
  with the tombstone's class, time and reason, withdrawn, class-raised) and `detail.demoted = { date, session }`.
  The registry validator accepts the file (a `not-run` part with no current record), and the generated tables
  then print "not run" for it.
- *Closing line.* A new line is appended through `beadlog::append` with `verdict = fail`,
  `cause = "evidence-unavailable"`, the same `claim_ids`, the missing nodes in `refusals` (code FROB-REF-869), and
  `recorded_by` the re-affirming session. The line's other fields of `frob.beadlog/1` are filled so that it
  validates like any line: `event = gate-record`; `commit` the repository head at the run; `host` and `toolchain`
  of the re-affirming run; `claim_type`, `determinism`, `state_hash` and `gate` copied from the demoted closing
  line (the state the claim was bound to); `metrics` `{ "missing_nodes": { "v": <count>, "unit": "1" } }`.
  Earlier lines are never touched; the log's chain advances by one line.
  The honest-status table, which reads each bead's latest verdict, shows the bead as failing from then on.
- A part or a bead is demoted at most once per cause: a part already `not-run`, or a bead whose latest line is
  already this demotion for the same claims, is skipped, so a second run changes no byte.

**4. Report (`frob.reaffirm/1`).** `{ frontier, epoch, parts_checked, parts_demoted, lines_checked,
lines_appended, demotions: [{ gate | bead, part_milestone?, claim_id, missing: [...] }] }`, written beside the
milestone exit record and printed with denominators ("2 of 214 parts demoted"). Every count states its
denominator (INV-CHRON-11).

**5. When it runs.** Before every milestone exit review and every release, as a required step of the exit
procedure; and after any explicit claim withdrawal or scene purge (the operations that can make a pinned closure
unavailable). Because closures of live claims are pinned (BD-209, N29b-13), routine collection never causes a
demotion; a demotion is always the visible consequence of a withdrawal, a purge or a lost store, and the report
names which.

**6. Who may run it.** Any session: re-affirmation records no pass, so the fresh-session rule of the recorder
does not apply; the demoting session is recorded. Re-recording a demoted gate goes through the recorder with a
fresh session and a new measurement.

**7. Layout and properties.** `crates/frob-conformance/src/register/reaffirm.rs` (beside the recorder's
`register::record`, whose lock it takes), reached through the mode word of `examples/record_gate.rs`; tests
`crates/frob-conformance/tests/reaffirm.rs`. Determinism: D0 given the registry, the logs and the store state.
Evidence: the report is an analysis result of class Tested; it creates no claim.

## Acceptance criteria

- [ ] On a fixture registry with five `pass` parts, one of whose gate claims was withdrawn, `reaffirm` demotes
      exactly that part (status `not-run`, former record under `detail.demoted_from`, cause and missing nodes
      present) and leaves the other four parts and every other byte of the file unchanged; exit 2.
- [ ] A closed bead whose closing claim's evidence chunk was tombstoned gets one appended `fail` line with
      `cause = "evidence-unavailable"`; its earlier lines and their chain values are unchanged.
- [ ] Run on a clean tree it changes nothing and exits 0; a second run after a demotion changes no byte.
- [ ] The registry validator and the log's chain check pass after a demotion, and the generated status table
      prints "not run" for the demoted part and the latest verdict `fail` for the bead.
- [ ] The report states its denominators and is attached to the milestone exit record.

## Test plan

### Unit tests (`crates/frob-conformance/tests/reaffirm.rs`; real registry loader, real bead-log append, a
scratch store labelled `synthetic`)

- `reaffirm_demotes_only_unavailable`: 5 PASS parts, 1 with a withdrawn claim → 1 demoted, 4 unchanged.
- `reaffirm_part_level`: a gate with an M1 part and an M2 part, both `pass`; tombstoning an evidence item of the
  M2 part demotes the M2 part only; withdrawing the gate's claim demotes both.
- `reaffirm_moves_record_to_detail`: the demoted part's `measured`, `evidence` and `recorded` appear under
  `detail.demoted_from` byte for byte; the validator accepts the file.
- `reaffirm_bead_log_append`: one appended line, `verdict = fail`, cause and claims as specified, refusal code
  869, the copied fields equal the closing line's and the line validates against `frob.beadlog/1`; the chain
  recomputes.
- `reaffirm_idempotent`: a second run is a no-op (file digests equal).
- `reaffirm_clean_tree_noop`: exit 0, zero demotions, digests equal.
- `reaffirm_private_scope_not_demoted`: a claim whose closure holds a private node stays resolved for the
  recorder's full scope.
- `reaffirm_report_denominators`: counts equal the number of parts and lines walked.
- `reaffirm_mode_word_and_lock`: `record_gate -- reaffirm --registry <scratch> …` runs the walk and records
  nothing; started while a recorder process holds `gates.toml.lock`, it waits and then walks the file the
  recorder wrote; with the lock held past the timeout it refuses, naming the holder, and changes no byte.

### End-to-end script and logging

Step group `reaffirm-*` added to `scripts/e2e/record_gate.sh`, the recorder's own script (bead N38b-19, a
dependency). The place is forced: a log line that runs the `record_gate` example passes the harness lint
`self-recording` only in the recorder's own scripts, and N29a-10's gate script, where an earlier form put this
group, neither depends on this bead nor may run the example. The group works on the scratch registry and logs
of that script: beside the gate the script recorded, close a fixture bead on the same claim; tombstone one
evidence object of each through BD-095's test-support example (claim withdrawal through `store.collect` arrives
at the second milestone with N29b-13, whose own script exercises the demotion after a withdrawal); run `cargo
run -p frob-conformance --example record_gate -- reaffirm --registry <scratch registry> --logs <scratch logs>
--store <dir> --json`; and
check the part, the appended line, the report and a second no-op run. NDJSON lines per the shared helper (`ts`,
`script`, `bead`, `step`, `event`, the exact command line, exit code, wall time, the envelope's evidence block):
parts and lines checked and demoted with their denominators, the digests of the registry and log before and after,
the missing nodes; on failure the first part or line whose state differs from the expectation and the scratch
paths needed to reproduce; the script's `summary` line counts the step group's assertions.

### Known answers and negative controls

- KA-720: every gate row resolves to evidence and traces; this bead keeps it true over time. Its control, a claim
  printed after its evidence was collected, has the demotion as its later-time counterpart.
- Negative controls: a re-affirmation that deletes the part instead of demoting it (the row-count and
  history assertions fail); one that rewrites an earlier bead-log line (the chain check fails); one that reads a
  cached state from before the withdrawal (the demotion is missed; memoization is keyed by the tombstone epoch);
  one that demotes for `PrivateNoScope` (the private-scope test fails).
- Determinism lanes: twice on one machine; on a copy of the registry, logs and store exported and imported.

## Considerations

- Premortem story 8 of the risk chapter ("the swarm closed beads that proved plumbing"): its earliest signals are
  shared close reasons, a gate without a caught negative control, and a PASS recorded by the implementing session.
  This pass adds the later signal that a PASS stopped resolving, and makes it visible in the status table instead
  of leaving a stale PASS.
- RISK-39 (retention deletes the interval that explains a decision): pins prevent it in routine operation; a
  demotion here is the record that a deliberate withdrawal or purge took a decision's support away.
- A demotion is not a failure of the capability; it says the record no longer stands. The fix is a fresh
  measurement through the recorder.
- Concurrency: the command takes the recorder's registry lock and appends through `beadlog::append`, which is safe
  under concurrent writers; it never runs while the recorder is writing the same gate.
