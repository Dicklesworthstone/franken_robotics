## Background

Reality is one of the seven kinds of claim a result may make: that the simulation agrees with physical
measurement. It is the one claim the first release mostly cannot make. Four reasons make `no-claim` the normal
state, and they are stated here so that no later work argues around them.

1. **No data exists.** Nothing in this program has been compared with a physical robot (FACT). A measurement
   that has not been taken cannot be replaced by a larger batch of simulation.
2. **Agreement between tiers cannot reveal a wrong card.** Every simulation tier consumes the same actuator
   card (the immutable, content-addressed data sheet of a motor, with a provenance per field: `datasheet`,
   `measured`, `generic` or `assumed`). Through M4 the catalogue holds generic classes only. So a report that
   supports a benchmark claim prints the share of card fields whose provenance is `generic` or `assumed`
   (DESIGN: it is the one number that tells a reader how much of the model was guessed).
3. **A Reality result has a scope and no meaning outside it.** The scope is a cell: which physical units, which
   controller and firmware, which surface, which task family, inside which envelope of conditions.
4. **A design that was never built has no reality band.** Coverage of a band is a statement about draws
   exchangeable with the calibration draws. An unbuilt design is not such a draw.

The pre-mortem of the program names the failure this bead prevents: "sim-to-real was never tested and claims
overreached", with the earliest signal "any report without a `reality:` line". The line is therefore Solid
tier, lands at M1 before any of the calibration machinery, and its gate is re-run at every milestone exit.
`no-claim` is a legitimate terminal state, not a failure.

Rejected alternatives. A style rule ("reports should say when nothing was measured"): an optimizing agent finds
any path by which a simulated number can be read as measured, and a rule in a style guide is such a path.
Omitting the line when there is nothing to say: absence is then indistinguishable from an oversight. A boolean
`validated` field: it has no scope, and the word is banned from reports.

## Scope

This bead is the capstone of the M1 reality line: it puts the line on every report surface, guards it, and
closes GATE-GROUND-01. Two parts are built in their own beads, which are dependencies of this one:

- the crate `frob-ground`, its module layout, the dependency firewall and the Estimated class on every output:
  N30a-01;
- the status type with its payloads, the transition function and its ledger event, the combination rule, and
  the grammar, printer and parser of the line: N30a-02. Items 1 to 4 of the Technical approach below restate
  that type as the guard uses it; N30a-02 is where it is specified and built, and its grammar is the one
  printed.

In this bead: the modules `reality` (the guard) and `records` (the record tables the guard reads) added to the
crate; the guard that refuses a status or a band that no record supports; the guess-share line at M1 (the
count over bound cards and the `cards:` line on every claim-bearing result); the registry of report surfaces,
the lint and the CI check that every surface prints the line; the fifty registered misuses and their expected
refusals, as data with the code that plants each one; the gate's entry in the known-answer tier, which binds
KA-735 and measures GATE-GROUND-01 in process (item 9).

Out: admitting datasets and sealing (BD-387); issuing bands and writing band records (BD-393); retirement
(BD-394); the status `published-anchor` as produced by a comparison (BD-311); the rule for which M3 reports
support a benchmark claim, the by-kind breakdown and the trend record of the guess share (N30a-03); the
end-to-end script that runs the battery through the binary (N30b-01).

## Technical approach

1. **Statuses** (enum `RealityStatus`, owned by `frob-core` so every envelope can carry it; specified and built in N30a-02; DESIGN):

   | Status | Meaning | Rule |
   |---|---|---|
   | `no-claim` | Nothing measured supports the number | The default. A legitimate terminal state |
   | `synthetic` | The comparison ran against data generated by a simulator standing in for reality | Never promoted (invariant INV-GROUND-06) |
   | `published-anchor` | A simulated quantity was compared with a figure published for the same robot | A Parity result, never Reality: published test conditions are loose |
   | `candidate(cell)` | A posterior was fitted in this cell and has not been scored on sealed data | Changes no randomization width |
   | `calibrated(cell, n, level)` | A frozen prediction was scored on sealed data and a band is issued | Valid only inside the cell |
   | `retired(cell, reason)` | A drift monitor fired, the scope changed, or the calibration expired | Reverts to `no-claim` with the reason |

2. **The line.** Every report carries exactly one line
   `reality: <status> [cell=<id> n=<n> level=<1−α> band=<q̂ with unit> dataset=<hash prefix>]`.
   The bracketed fields appear for `candidate` (cell, dataset), `calibrated` (all five) and `retired` (cell and
   `reason=`). `synthetic` prints `dataset=`; `published-anchor` prints `source=`; `no-claim` prints no field,
   or `reason=` (with `cell=`) after a retirement. Fields keep the fixed order `cell`, `n`, `level`, `band`,
   `dataset`, `source`, `reason`. Examples:
   `reality: no-claim`; `reality: calibrated [cell=c:9f2c41aa07b1 n=20 level=0.90 band=0.07s dataset=5d10aa7c1e55]`
   (the grammar of N30a-02: the square brackets are literal, the band has no space before its unit, hash
   prefixes are 12 hex digits).
   `frob_core::reality::{render, parse}` are inverse on every valid value; `parse` rejects six malformed forms:
   a band with no unit, a level of 0, a level of 1.0 (a level outside (0, 1)), a `calibrated` status with a
   field missing, two lines in one document, and an unknown status word.
3. **Status of a combined result** (the function `combine` of N30a-02, which states this same rule; DESIGN; the claim-product rule "the weakest input wins" applied to this
   field). For parts with statuses s₁ … s_k: if any part is `synthetic` the result is `synthetic` (the label is
   sticky and can never be dropped or raised); otherwise if all parts are equal and name the same cell, band
   record and model identity, that status; otherwise `no-claim`. A part that is `retired` makes the result
   `no-claim` and adds the retirement reason to `warnings`. There is no input combination that yields
   `calibrated` from parts that are not all `calibrated` in one cell.
4. **Construction is closed.** Only `frob-ground` (through `status::advance` of N30a-02, fed by `frob_ground::records`) can construct `candidate`, `calibrated` and `retired`
   values, and only from a record it has read from the ledger; `frob-core` exposes `no_claim()` and `parse` (which
   returns an unverified value that must pass the guard before use). A compile-fail test pins that no other
   crate can build a `calibrated` value.
5. **Record tables** (`frob_ground::records`, schema `frob.ground.records/1`, in the ledger): `dataset` (id,
   origin, kind, licence class, private mark, units, design), `cell` (cell key hash and components), `band`
   (cell, metric, model identity, n, level, q̂ with unit, dataset, ledger sequence), `retirement` (cell, reason,
   sequence), `synthetic_chunk` (every chunk hash ever admitted under origin `synthetic`). At M1 the tables
   exist and are empty; the M5 mechanisms write them through the same API.
6. **The guard** (`frob_ground::reality::guard`), called by the envelope serializer, by every artifact reader
   and by every report renderer:
   - `status_for(inputs) → RealityStatus`: computes rule 3 from the inputs' lineage; with no dataset in the
     lineage the answer is `no-claim`.
   - `check(claimed, lineage)`: an artifact that arrives carrying a status must be re-derivable. Refusals (all
     exit 3): no band record for the cell, n below 19, a finite band at a level whose index ⌈(n+1)·(1−α)⌉
     exceeds n, or an unparsable line → FROB-REF-889; a design with no dataset of origin `real` naming a
     physical unit → FROB-REF-895; a cell with a retirement record → FROB-REF-897; a band record whose rows
     span cells, model identities or origins, or a chunk hash recorded as synthetic inside a `real` dataset →
     FROB-REF-814; a status or a `measured` card field naming no admitted dataset, or a dataset whose
     recomputed id differs → FROB-REF-873; a result of another claim kind offered as Reality →
     FROB-REF-819; an authorization flag absent or not the literal `false` → FROB-REF-816 (FROB-REF-833 inside
     a certificate bundle); an unknown parameter that tries to set a status → FROB-REF-802.
   - Check order (DESIGN, so that payloads are stable): flags, parse, origin, design built, cell record,
     retirement, counts.
7. **The guess share.** For every result whose envelope names a claim about a design or a model, and for every
   report that carries such a claim (a result with no bound model has no `cards:` line; N30a-03 fixes at M3
   which report kinds must carry it): directly under the reality line,
   `cards: guessed=<k>/<N> (<pct>%) [generic=<a> assumed=<b> synthetic=<f> datasheet=<c> measured=<d> candidate=<e>]`
   with k = a + b + f and the percentage printed with one decimal (the grammar N30a-03 fixes; at M1
   `synthetic`, `measured` and `candidate` are 0, and the `synthetic` column is printed all the same so that the
   grammar never changes), with `evidence.card_guess_share = {guessed: k, total: N}` in the envelope. N counts
   every field that carries a provenance on every card bound in the model identity, over the closed list of
   nine card kinds (actuator, transmission, battery, interface, material, soil, optical, sensor, payload); a
   field identified from a dataset of origin `synthetic` counts in the `synthetic` column and therefore as
   guessed, whatever its admission state. A model with no cards prints `cards: none`.
8. **Every report prints it.** The registry of report surfaces is data (`registries/verbs.toml`, field
   `reports = true`): at M1 every `--json` envelope (`evidence.reality`), the human rendering of every
   result-bearing verb (the evidence footer's last line), `explain.run`, `explain.design`, `eval.scorecard`, the
   manifest of a `.frun` episode bundle and of a `.frobcert` certificate bundle. Later surfaces register as
   they land: the four `report.*` verbs and the HTML replay at M3 and M4, the `.fbuild` build packet and the
   replication kit at M5. `xtask check-generated` fails if a verb with `reports = true` has an output schema
   without `evidence.reality`.
9. **The battery as data, and the gate's entry.** The fifty rows of the table below are data, not test code:
   `crates/frob-conformance/registry/ground_misuses.toml`, one `[[misuse]]` per row with `row` (1 to 50),
   `group`, `recipe` (the planted artifact or request, as named steps) and `expect` (the code and its exit
   code; for row 45 one pair per milestone: 724 with exit 5 before M5, 889 with exit 3 from M5). The library
   module `frob_conformance::ground_misuse` reads it: `rows()`; `plant(row, dir)`, which builds the row's planted artifact or request through the real record API in a
   temporary store (the planting code lives in the conformance crate, so no product crate carries it); and
   `offer(row)`, which gives the planted item to the guard or the dispatcher in process and returns the
   refusal. This bead adds the runner entry `ka:KA-735@host` to the known-answer tier (the binding rule of the
   known-answer runner N38a-13; the Ground known-answer registry N30-KA assigns KA-735 to this bead and
   N30a-02, and its derivation file names this entry's test; tier G1, site `host`, gate GATE-GROUND-01):
   it runs the registered example of every verb with `reports = true` in a fresh store and requires exactly one
   `reality: no-claim` line in each output, then offers the fifty rows and requires the registered code for
   each. Its controls are the three mutants of the test plan. The gate is run in the one form the conformance
   crate has, `FROB_TEST_SEED=<s> cargo test -p frob-conformance --test g1_known_answers --features
   gauntlet-mutations -- GATE-GROUND-01`, and the hash-named receipt of that run is what a recording cites.
   The script N30b-01 uses `plant` through an example target to run the same rows through the binary.

Determinism: the line and the guard are pure functions of the lineage (class D0). Evidence: the gate is a
Known-answer claim.

## Acceptance criteria

- [ ] GATE-GROUND-01 (TARGET): every report prints the `reality:` line; with no dataset it reads `no-claim`;
      the battery of 50 planted misuses is refused in full, 50 of 50, each with the code in the table below.
      Measured by this bead's runner entry `ka:KA-735@host` (item 9), whose receipt shows the gate line `pass`
      and the three controls `caught`.
- [ ] Invariant INV-GROUND-01 (every report prints a `reality:` line, and its default is `no-claim`): a CI job
      runs the registered example of every verb with `reports = true` in a fresh store with no dataset and finds
      exactly one line reading `reality: no-claim` in each output.
- [ ] `render` and `parse` round-trip on 10⁴ generated statuses; the six malformed forms of item 2 (band with no
      unit, level 0, level 1.0, `calibrated` with a field missing, two lines, unknown status word) are rejected.
- [ ] No crate other than `frob-ground` can construct `candidate`, `calibrated` or `retired` (compile-fail test).
- [ ] The guess-share line is present on every claim-bearing result, and equals a direct count over the bound
      cards of the reference quadruped (all fields `generic` at M1: k = N).
- [ ] `crates/frob-ground/CONTRACT.md` exists with its ten sections; the guard is reachable through every
      `frob --json` verb; the gate's M1 part is recorded from the receipt of item 9's run with the recorder's
      example target (`cargo run -p frob-conformance --example record_gate -- --gate GATE-GROUND-01 --receipt
      <hash> --part M1`) by a session that did not implement this bead, and each later milestone exit records
      its own part the same way (N30b-01 states the exit rule). No test or script of this bead writes the row.

## Considerations

- The battery must be runnable at M1, when no dataset can be admitted. Rows that need records (16 to 25, 29)
  plant them through the real record API in a temporary store and mark them `synthetic`. That mark is the
  fixture label (a `fixture = "synthetic"` column on the planted row: the test standard's label for made-up
  data), not the planted dataset record's `origin`. In rows 16 to 25 the planted dataset records have origin
  `real` and name a unit (row 23 adds its one synthetic part on purpose), because with origin `synthetic` the
  guard's earlier checks (origin, design built) would answer 814 or 895 before the check under test
  (retirement, pooling) is reached.
- Row 45 changes its expected code when `ground.band` lands at M5; the row records the build's milestone and
  the amendment is dated.
- Three checks reuse a broader code because the registry has no narrower one (an unparsable line under 889; an
  id mismatch and a sourceless anchor under 873). If the registry owner assigns codes, only the table changes.
- Risk: a new report surface ships without registering. Countermeasure: the lint keys on the output schema, not
  on a hand-kept list, and the exit review re-runs the gate.
- The dataset identity function and the record tables introduced here are the ones the admission bead builds
  on at M5; they are not duplicated there.
- The same statement holds for every exported artifact: no verb, flag or configuration produces
  `sim_to_real_certified: true`.
