## Background

GATE-GROUND-01 is the first gate of the subsystem that compares simulation with measured reality, and one of
four gates in the program that are re-run at every milestone exit after their first. Its claim kind is Known
answer. Its threshold (TARGET): every report prints the `reality:` line; with no dataset the line reads
`no-claim`; a negative battery of 50 planted misuses is refused in full. The mechanism (the status type, the
guard and the registered list of fifty misuses) is built by BD-139. This bead is the script that measures the
gate from the user's side, through the real `frob` binary and the MCP server, and that every exit review runs
again. An end-to-end measurement is needed because the property is about surfaces: a unit test can show the
guard refuses a forged status, and only a run through every registered report surface can show that none of
them forgot to call it.

The script grows with the product. The set of report surfaces is read from the verb registry (the field
`reports = true`), so a surface added at M3 or M5 is exercised at the next exit without editing the script.

## Scope

In: the script, its log, the example target through which it plants a misuse on disk, and the rule for how the
gate row is recorded at each exit.
Out: the guard, the battery's rows (`ground_misuses.toml`), the planting library, the gate's runner entry and
the three mutation controls (BD-139); the catalogue's counterexamples (N30-CX); the gate row's schema
(N30b-22).

## Technical approach

`scripts/e2e/ground_reality_line.sh`, header `bead=N30b-01 milestone=M1 labels=ground,e2e,gate
gates=GATE-GROUND-01 seed=1 needs=cpu,mcp plants=renderer-omits-line,guard-no-min-count,synthetic-not-sticky`.
It sources `scripts/e2e/lib.sh` and runs in the run's own state root, the empty `FROB_STATE` that `e2e_init`
exports (`frob` reads no `FROB_HOME`, which an earlier text of this bead set), so that "no dataset" is true by
construction.

1. **Step `surfaces`.** `frob capabilities --json` lists the verbs; the script filters those the registry marks
   as report surfaces and runs the registered example of each on the built-in fixtures (the reference cart and
   the reference quadruped). For each: `e2e_assert_json reality /evidence/reality "no-claim"`; for the human
   rendering (the same command without `--json`), exactly one line matching `^reality: no-claim$`. For artifact
   surfaces (`.frun` and `.frobcert` at M1; the `.fbuild` build packet and the replication kit when they
   register at M5) it exports one through the surface's registered example and greps the manifest. The same registered examples are then
   called as tools through `frob-mcp` over stdio, asserting `evidence.reality == "no-claim"` in each structured
   result (logged with `surface: mcp`). Count of surfaces exercised is a `metric` with the registry count as its
   threshold (equality).
2. **Step `guess-share`.** On a scorecard of the reference quadruped: directly under the reality line, the line
   `cards: guessed=<k>/<N> (<pct>%) [generic=<a> assumed=<b> synthetic=<f> datasheet=<c> measured=<d>
   candidate=<e>]` (the grammar of BD-139 and N30a-03, with k = a + b + f and one decimal in the percentage) is
   present with k = N, `(100.0%)` and `synthetic=0 measured=0 candidate=0` (the M1 catalogue is generic; the
   `synthetic` column is printed even when 0), and `evidence.card_guess_share` equals `{guessed: k, total: N}`.
   The script parses the line with the grammar's regular expression, so a line missing a column fails.
3. **Step `battery`.** For each row of `crates/frob-conformance/registry/ground_misuses.toml` (BD-139's fifty
   rows: row number, group, recipe, expected code and exit code): build the planted artifact or request on
   disk with this bead's example target, `cargo run -p frob-conformance --example ground_misuse -- plant <row>
   --out <dir>` (`examples/ground_misuse.rs`, declared here: a thin argument parser over BD-139's library
   function `frob_conformance::ground_misuse::plant`, printing one JSON object with the row, the paths written
   and the command to run; the conformance crate has no binary named `frob-conformance`, and an earlier text
   of this bead called one), then `e2e_expect_refusal <code> <exit> -- <command>` with the code and exit code
   of the row (exit 3, except row 45 before M5, which is FROB-REF-724 with exit 5). Rows that need records
   (16 to 25 and 29) plant them with the same call. Every planted row carries the fixture label `synthetic`
   (a `fixture = "synthetic"` column: the test standard's label for made-up data), which is not the planted
   dataset record's `origin`: in rows 16 to 25 the planted dataset records have origin `real` and name a
   unit, because with origin `synthetic` the guard's earlier checks would answer 814 or 895 before the
   retirement or pooling check under test is reached. Each row logs a `refusal` event with the row number,
   group, code, exit code, pointer, observed, required and repairs.
4. **Step `controls`.** `e2e_expect_caught <control> -- …` for the three mutation controls BD-139 registers
   for the gate, by plant label: `BD-139:renderer-omits-line`, `BD-139:guard-no-min-count` and
   `BD-139:synthetic-not-sticky` (their `NC-` numbers are the control registry's and are read from it, never
   typed here): each must make the corresponding check of step 1 or step 3 fail.
5. **Step `receipt`.** `e2e_metric misuses_refused <count> rows == 50 --gate GATE-GROUND-01`;
   `e2e_metric surfaces_with_line <count> surfaces == <registry count> --gate GATE-GROUND-01`; then the
   gate's tier entry through the shared helper, `e2e_tier g1_known_answers GATE-GROUND-01 --mutations` (that
   is `FROB_TEST_SEED=1 cargo test -p frob-conformance --test g1_known_answers --features gauntlet-mutations
   -- GATE-GROUND-01`, BD-139's entry `ka:KA-735@host`). The script asserts on the receipt (`e2e_get --file
   "$E2E_LAST_RECEIPT"`) that the gate line is `pass` and that the three controls are `caught`, logs the
   receipt hash, and ends with `e2e_gate GATE-GROUND-01`. It runs no recorder and writes no gate row.

Log: `target/e2e-logs/ground_reality_line/<utc-timestamp>.ndjson` and a transcript beside it, with on every line
`ts`, `script`, `bead`, `step`, `event`, the exact command, exit code, wall time and the envelope's `evidence`
block; on failure, the first surface or row that failed, the observed line or code against the expected one,
and the path of the planted artifact. The final `summary` line gives assertions passed and failed and
`gates: ["GATE-GROUND-01"]`. No private-scene data can appear: the store is empty and every fixture is built in.

Idempotent and seed-explicit: the script creates and removes its own store; planted artifacts are byte-identical
across runs.

**Exit rule.** GATE-GROUND-01 is recurring: its record in `registries/gates.toml` gains one part per milestone
exit and an earlier part is never overwritten. A part is entered from the receipt of step 5 by the gate
recorder, `cargo run -p frob-conformance --example record_gate -- --gate GATE-GROUND-01 --receipt <hash> --part
<milestone>`, in a session that implemented neither BD-139 nor this bead; the part then holds the commit, the
command, the counts (surfaces, 50 of 50), the receipt hash and the recording session. An exit with no new part
for this gate is incomplete.

## Acceptance criteria

- [ ] The script exits 0 on a correct build and non-zero when any surface lacks the line or any row is accepted.
- [ ] With `E2E_PLANT_FAILURE` set to each of the three plants of the header the script exits non-zero and
      names the control in the first failing assertion.
- [ ] The surface count equals the registry's count at the commit under test (no hand-kept list).
- [ ] The row counts are 50 planted and 50 refused, each with the registered code and exit code.
- [ ] Two consecutive runs produce logs that differ only in `ts` and wall-time fields.
- [ ] The log's `cmd` line of step 5 carries the receipt hash; the receipt's gate line is `pass` with three
      controls `caught`; the log holds no `record_gate` command (the harness lint `self-recording` passes).
- [ ] The gate's M1 part is recorded from that receipt by a session that implemented neither bead, and each
      later exit review adds its own part.

## Test plan

### Unit tests

`crates/frob-conformance/tests/ground_misuse_example.rs` (the rows and the planting library have their own
tests in BD-139's `ground_misuses.rs`): `example_plant_equals_library` (for every row the directory the
example target writes has the BLAKE3 of the library's `plant`); `example_prints_one_json_object` (row, paths,
command; exit non-zero on an unknown row); `command_of_every_row_parses` (each printed command parses against
the generated CLI of its verb); `header_plants_are_the_gate_controls` (the script header's three plants are
the labels of the three controls registered for GATE-GROUND-01 with `seed = "GATE-GROUND-01"`).

### End-to-end script and logging

This bead is the script; see the technical approach. It is also run by `scripts/e2e/run-all.sh --through M<n>`
at every exit, and by `--verify-plants`, which checks that each plant makes the script fail.

### Known answers and negative controls

KA-735 (the line on every report; `no-claim` with no dataset; 50 of 50 refused). Negative controls: the three
mutants above; a registry row with `reports = true` on a verb whose renderer omits the line (the surface step
fails and names the verb). Determinism lanes: twice on one machine; debug and release; macOS and Linux.

## Considerations

- Runtime target (TARGET): under two minutes on the CPU, so that it can sit in the `smoke` battery.
- `frob-mcp` is in the core graph from M0, so the MCP surface step and the battery's MCP row run over stdio.
  Only if KILL-MCP has fired are they run through the CLI's schema validator instead, with the log marking them
  `surface: cli-fallback`; the rows are still counted.
- One row's expected code changes at M5 (a band request on a cell with no record: not-implemented before, with
  exit code 5, the band refusal after, with exit code 3); the script reads the expected code and exit code
  from the row for the build's milestone.
