## Background

GATE-GROUND-01 is the first gate of the subsystem that compares simulation with measured reality, and one of
four gates in the program that are re-run at every milestone exit after their first. Its claim kind is Known
answer. Its threshold (TARGET): every report prints the `reality:` line; with no dataset the line reads
`no-claim`; a negative battery of 50 planted misuses is refused in full. The mechanism (the status type, the
guard and the registered list of fifty misuses) is built by BD-139. This bead is the script that measures the
gate from the user's side, through the real `frob` binary and the MCP server, and that every exit review runs
again. An end-to-end measurement is needed because the property is about surfaces: a unit test can show the
guard refuses a forged status, and only a run through every registered report surface can show that none of
them forgot to call it.

The script grows with the product. The set of report surfaces is read from the verb registry (the field
`reports = true`), so a surface added at M3 or M5 is exercised at the next exit without editing the script.

## Scope

In: the script, its fixtures, its log, and the rule for how the gate row is written at each exit.
Out: the guard and the battery definition (BD-139); the control records (N30-CX); the gate row's schema
(N30b-22).

## Technical approach

`scripts/e2e/ground_reality_line.sh`, header `bead=N30b-01 milestone=M1 labels=ground,e2e,gate seed=1`. It
sources `scripts/e2e/lib.sh` and runs in a fresh temporary store (`FROB_HOME` pointed at an empty directory), so
that "no dataset" is true by construction.

1. **Step `surfaces`.** `frob capabilities --json` lists the verbs; the script filters those the registry marks
   as report surfaces and runs the registered example of each on the built-in fixtures (the reference cart and
   the reference quadruped). For each: `e2e_assert_json reality /evidence/reality "no-claim"`; for the human
   rendering (the same command without `--json`), exactly one line matching `^reality: no-claim$`. For artifact
   surfaces (`.frun`, `.frobcert`) it exports one and greps the manifest. Count of surfaces exercised is a
   `metric` with the registry count as its threshold (equality).
2. **Step `guess-share`.** On a scorecard of the reference quadruped: the line
   `cards: k of N fields generic or assumed` is present and k = N (the M1 catalogue is generic).
3. **Step `battery`.** For each row of `frob-conformance/registry/ground_misuses.toml` (fifty rows: identifier,
   group, command template or artifact recipe, expected code): build the planted artifact or request with the
   conformance tool (`frob-conformance plant ground.misuse <id> --out <dir>`), then
   `e2e_expect_refusal <code> 3 -- <command>`. Rows that need records plant them, labelled `synthetic`, with the
   same tool. Each row logs a `refusal` event with the row identifier, group, code, exit code, pointer,
   observed, required and repairs.
4. **Step `controls`.** `e2e_expect_caught NC-GROUND-0101 -- …` for the three registered mutants (renderer
   without the line; guard without the minimum count; combiner in which `synthetic` is not sticky): each must
   make the corresponding check fail.
5. **Step `record`.** `e2e_metric misuses_refused <count> rows == 50 --gate GATE-GROUND-01`;
   `e2e_metric surfaces_with_line <count> surfaces == <registry count> --gate GATE-GROUND-01`; `e2e_gate
   GATE-GROUND-01`.

Log: `target/e2e-logs/ground_reality_line/<utc-timestamp>.ndjson` and a transcript beside it, with on every line
`ts`, `script`, `bead`, `step`, `event`, the exact command, exit code, wall time and the envelope's `evidence`
block; on failure, the first surface or row that failed, the observed line or code against the expected one,
and the path of the planted artifact. The final `summary` line gives assertions passed and failed and
`gates: ["GATE-GROUND-01"]`. No private-scene data can appear: the store is empty and every fixture is built in.

Idempotent and seed-explicit: the script creates and removes its own store; planted artifacts are byte-identical
across runs.

**Exit rule.** The row for GATE-GROUND-01 in `registries/gates.toml` is appended, not overwritten, at each
exit: commit, command, counts (surfaces, 50 of 50), the receipt hash and the session that ran it, which must not
be a session that implemented BD-139.

## Acceptance criteria

- [ ] The script exits 0 on a correct build and non-zero when any surface lacks the line or any row is accepted.
- [ ] With `E2E_PLANT_FAILURE` set to each of the three control names the script exits non-zero and names the
      control in the first failing assertion.
- [ ] The surface count equals the registry's count at the commit under test (no hand-kept list).
- [ ] The row counts are 50 planted and 50 refused, each with the registered code.
- [ ] Two consecutive runs produce logs that differ only in `ts` and wall-time fields.
- [ ] The gate row exists for M1 and a new row is added by each later exit review.

## Test plan

### Unit tests

`crates/frob-conformance/tests/ground_misuses.rs`: `fifty_rows_ten_groups_of_five`; `every_row_names_a_code_in_registry`;
`planted_artifacts_are_deterministic` (two builds, equal BLAKE3); `rows_needing_records_mark_them_synthetic`.

### End-to-end script and logging

This bead is the script; see the technical approach. It is also run by `scripts/e2e/run-all.sh --through M<n>`
at every exit, and by `--verify-plants`, which checks that each plant makes the script fail.

### Known answers and negative controls

KA-735 (the line on every report; `no-claim` with no dataset; 50 of 50 refused). Negative controls: the three
mutants above; a registry row with `reports = true` on a verb whose renderer omits the line (the surface step
fails and names the verb). Determinism lanes: twice on one machine; debug and release; macOS and Linux.

## Considerations

- Runtime target (TARGET): under two minutes on the CPU, so that it can sit in the `smoke` battery.
- Until the MCP server passes its admission the two MCP rows are run through the CLI's schema validator and the
  log marks them `surface: cli-fallback`; the row is still counted, and the note is dropped when the server
  lands.
- One row's expected code changes at M5 (a band request on a cell with no record: not-implemented before, the
  band refusal after); the script reads the expected code from the registry row for the build's milestone.
