## Background

A replication kit (BD-396) is a directory that carries a Ground result, the records behind it, the protocol by
which its data was acquired, expected outputs and the synthetic rehearsal. Ground is the subsystem that
compares simulation with measured reality. A kit makes a claim: that someone else can rebuild the numbers. This
bead is the part that tests the claim. A kit passes when a clean machine reproduces its numbers: bit for bit on
the same backend (determinism class D2: the same bits run to run on one device family, driver and compiler),
inside the recorded envelope otherwise (class D3: agreement inside a recorded tolerance and agreement of the
decisions the numbers lead to).

"Clean machine" has a precise meaning here (DESIGN): a checkout of the commit named in the kit, an empty store,
no network access, no file outside the kit directory and the checkout. If the check needs anything else, the
kit is incomplete, and that is the defect the check exists to find.

Rejected alternative: checking a kit on the machine that built it, in the store that built it. Every missing
file is then silently supplied by the store.

## Scope

In: the check form of the verb; the clean environment; replay of the analysis calls; comparison by class; the
check receipt; the gate measurement on the rehearsal. Out: building kits (BD-396); the kill decision (N30b-21).

## Technical approach

1. **Verb form.** `frob ground kit check <dir> [--store <empty-dir>] --json`; kind `run`; capability
   `ground:read`. It refuses to run in a store that is not empty unless `--store` names one (the refusal names
   the store's object count), so that the default is the honest test.
2. **Steps.**
   1. Verify the manifest: every listed file exists with its hash; the three authorization flags are present
      and `false`; the stack pin in `analysis/` equals the running build's, or the check is labelled
      `cross-build` and compared in class D3 throughout.
   2. Import the kit's inputs into the empty store through the ordinary readers (designs, cards, scene, task,
      predictions, records, the dataset or its stub, certificates).
   3. Regenerate the rehearsal from its recipe and seed, and compare dataset identifiers with the kit's.
   4. Replay each call in `analysis/` in order, with the recorded arguments and seeds.
   5. Compare each result with `expected/`: where the machine's backend and fingerprint family equal the
      recorded ones and the output's class is D2, by digest (bit equality); otherwise field by field inside the
      recorded tolerance, plus equality of every decision field (refused or not, admitted or not, band finite
      or not, retired or not). A decision that differs is a failure whatever the numbers say.
   6. Where the dataset is a stub, calls that need its bytes are skipped and listed `not-replayed: dataset not
      shipped`; the check's verdict is then `partial`, never `pass`.
3. **Receipt.** `frob.ground.kit.check/1`: kit identifier, commit, fingerprint, per call the comparison mode
   (`bit`, `envelope`), the result, the first differing field with expected and observed values, counts, and
   the verdict `pass`, `partial` or `fail`. Ledger event `ground.kit.checked`.
4. **Gate measurement.** The kit of the synthetic rehearsal is built on one machine and checked (a) in a fresh
   checkout and empty store on the same machine, expecting bit equality for class-D2 outputs, and (b) on the
   second platform, expecting agreement inside the envelope. The ensemble lane of identification is recorded
   per machine and compared in the envelope even on the same machine family when the fingerprint differs.

Determinism: the check is itself deterministic (class D0 for the comparison logic). Evidence: the receipt is a
Known-answer record on the rehearsal.

## Acceptance criteria

- [ ] GATE-GROUND-09, reproduction part (TARGET): a kit rebuilds the rehearsal on a clean machine inside its
      class. Measured: the number of calls compared by bit and by envelope, with zero failures; recorded with
      the fingerprints of both machines.
- [ ] A kit with one file removed, one hash altered, or one expected value perturbed by one unit in the last
      place of a class-D2 output fails, and the receipt names the file or field.
- [ ] A kit with a flag missing or `true` is refused before any replay.
- [ ] A check in a non-empty store is refused by default.
- [ ] A kit whose dataset is a stub checks as `partial` and lists what was not replayed.
- [ ] The check runs with the network disabled.
- [ ] A decision field that differs fails the check even when every number is inside tolerance.

## Test plan

### Unit tests

`crates/frob-ground/tests/kit_check.rs`: `manifest_hash_mismatch_fails`; `missing_file_fails_with_path`;
`flag_true_refused`; `nonempty_store_refused`; `bit_mode_on_same_fingerprint`; `envelope_mode_on_other_fingerprint`;
`one_ulp_perturbation_fails_bit_mode`; `decision_difference_fails_envelope_mode`; `stub_dataset_is_partial`;
`rehearsal_ids_regenerate`; `cross_build_is_labelled`; `receipt_names_first_difference`.

### End-to-end script and logging

`scripts/e2e/ground_kit.sh` (bead N30b-36) builds the rehearsal kit, copies it to a temporary directory, checks
it in a fresh clone with an empty store and the network disabled, and logs per call the comparison mode,
digests where compared, the first differing value on failure, and the verdict; a second invocation on the other
platform appends its receipt to the same gate row.

### Known answers and negative controls

The rehearsal's own known answers, replayed from the kit. Planted failures: a kit missing one card version (the
import step fails and names it); a checker that falls back to the building store when a file is missing (the
missing-file control passes when it must fail); an expected value regenerated from the candidate on the
checking machine. Determinism lanes: the check twice on one machine gives identical receipts apart from
timestamps; the two-platform lane is the gate itself.

## Considerations

- The referee tier's bit equality across platforms is an open upstream item, which is why cross-platform
  comparison is in class D3 and why the kit ships dataset bundles by content hash instead of relying on
  regeneration alone.
- If KILL-KIT fires, the build form survives as an archive of inputs, records and hashes, and this check form
  is reduced to step 1 (manifest verification), with no reproduction claim.
- Runtime: replaying the rehearsal's analysis is tens of minutes on a CPU (TARGET under one hour); the
  population battery is replayed on a sample of ten rigs by default and in full with `--full`.
