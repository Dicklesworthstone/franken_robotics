## Background

Ground is the subsystem that compares simulation with measured reality (crate `frob-ground`, layer 5). Seven
invariants state what must hold in every state of the system for a Reality result to mean what it says. Each
is small, each is carried by a mechanism bead that enforces it, and each has an attack that an optimizing agent
or a careless script would eventually find. This bead is the single battery that tests all seven together, as
properties over generated sequences of operations and with a planted violation per invariant, so that the
invariants are tested against each other and not only one at a time by the mechanism that owns them.

The seventh is different in kind. Decision **ADR-GROUND-01:** Ground is file-in, file-out; it never commands or
reads a device. Scope and safety: a simulator's gate cannot depend on hardware the project does not have, and a
calibration tool that can talk to a robot is a deployment stack by another name. The subsystem has no driver,
no bus, no real-time loop and no hardware-in-the-loop mode. That is enforced on the dependency graph, because a
rule about what code does not do is only checkable by what it cannot link.

## Scope

In: one property test and one planted violation per invariant; the firewall's planted violations as part of the invariant battery (the rule itself is built at M1 by
N30a-01, a dependency); the
model-based sequence generator. Out: the mechanisms themselves (named per row); the three proof obligations
(N30b-24).

## Technical approach

1. **The invariants, their tests and their owners.**

   | ID | Statement | Property test | Planted violation (must be caught) | Enforced in |
   |---|---|---|---|---|
   | INV-GROUND-01 | Every report prints a `reality:` line, and its default is `no-claim` | For every verb the registry marks as a report surface, in a store with no dataset, the output has exactly one line and it reads `no-claim` | A renderer that omits the line | BD-139 |
   | INV-GROUND-02 | A card is never mutated; a posterior is a new version with provenance and dataset hash | For any sequence of identify, score and retire operations, every card content address that existed before still resolves to the same bytes; every new version has `measured`, a dataset hash and a cell | A writer that updates a field in place | N30a-27 to N30a-30 |
   | INV-GROUND-03 | A prediction's ledger sequence precedes the first read of the sealed chunk it predicts | In the ledger's total order, for every `ground.sealed.read` event there is a `ground.prediction.frozen` event for the same chunks with a smaller sequence | A store that returns sealed bytes before the freeze | BD-387, BD-392, N30b-06 |
   | INV-GROUND-04 | A holdout chunk is scored at most once per cell and model lineage | Over random sequences with refits, the multiset of (chunk, cell, lineage) in `ground.holdout.spent` has no repeats | A spent table keyed by card version | N30b-06 |
   | INV-GROUND-05 | Randomization width from a card does not narrow without an admitted validation | The randomization block compiled for a model is byte-identical before and after any operation other than an admission; after retirement it returns to the prior's | A randomization compiler that reads `candidate` widths | N30a-27 to N30a-30 |
   | INV-GROUND-06 | Data of origin `synthetic` never yields a status other than `synthetic` | For any sequence of operations whose lineage contains a synthetic chunk, every output status is `synthetic`; a relabelled synthetic set fails its hash; its chunk hashes are refused in a `real` dataset | A combiner in which `synthetic` is not sticky; a relabelled manifest with a recomputed id | BD-139, BD-388, BD-387 |
   | INV-GROUND-07 | Ground performs no device input or output | The resolved dependency graph of `frob-ground` contains no crate from the banned list, and its sources contain no banned path | A dev build that adds a serial-port crate behind a feature | this bead |
2. **Sequence generator.** A model-based property test drives the real `frob-ground` API on `synthetic`
   bundles in a temporary store: operations {ingest, identify, predict, score, band, ingest-more, refit,
   retire, change-firmware, kit-build} are drawn at random (10³ sequences of up to 40 operations per run, seed
   explicit), with illegal orders included on purpose. Each operation calls the API of the bead that builds it,
   all of them dependencies: identify and refit BD-391; predict BD-392 and score N30b-06; band BD-393 and the
   retirement and scope-change triggers N30a-43 and N30a-40 (both reached through BD-394); kit-build BD-396;
   class cards N30a-30. After each operation the five state invariants (02 to
   06) are checked against the ledger and the store. A failing sequence is shrunk to a minimal one and written
   as a regression fixture.
3. **Dependency firewall (INV-GROUND-07).** The rule, its deny-list (`registries/deny/ground-io.toml`) and its
   tests (`xtask/tests/ground_firewall.rs`) are built at M1 by N30a-01; the list named below is that same file,
   and this bead adds to it and to that test file only what N30a-01 lacks (the `extern "C"` source check and
   the rule that an exception needs a named defect class). As N30a-01 specifies it, `xtask check-deps` gains a
   rule for `frob-ground`:
   - banned crates anywhere in its normal, build or dev graph (matched by name): serial and USB access
     (`serialport`, `rusb`, `hidapi`, `libusb*`), field buses (`socketcan`, `canopen*`, `ethercat*`, `modbus*`),
     device I/O (`i2c*`, `spidev`, `gpio*`, `linux-embedded-hal`, `embedded-hal*`), network clients and servers
     (`tokio` net features, `mio`, `socket2`, `hyper`, `reqwest`, `tungstenite`, `quinn`), middleware (`r2r`,
     `rclrs`, `zenoh*`, `dds*`);
   - banned source paths inside the crate: `std::net`, `std::os::unix::net`, `std::os::fd` raw descriptors
     opened on `/dev`, and any `extern "C"` block;
   - the list is data (`registries/deny/ground-io.toml`); adding an exception needs a named defect class, as
     for every check of that tool.
   File reads and writes go through the store and the session's path jail; no other I/O exists in the crate.
4. **Where they run.** `cargo test -p frob-ground --test invariants` for 02 to 06; the CI job of BD-139 for 01;
   `cargo xtask check-deps` for 07. All seven are also listed in the crate's `CONTRACT.md` under invariants.

## Acceptance criteria

- [ ] Seven tests exist, one per invariant, each named after its identifier, and each passes on the real build.
- [ ] Each of the seven planted violations is caught by its test (seven of seven). Each of the first six is a
      Cargo feature of the crate it breaks, enabled only through the umbrella `gauntlet-mutations` and never in
      a default or release build, and its test fails under it; those of 01 and 06 are BD-139's registered
      mutations `renderer-omits-line` and `synthetic-not-sticky`, reused and not declared twice. The seventh is
      the scratch manifest of `optional_serial_dependency_caught`, which needs no feature. Only BD-139's two are
      rows of `registry/controls.toml` (under GATE-GROUND-01); the other five are this battery's own controls and
      not register rows, since a control row needs a gate and this bead records none (an earlier text said each
      was registered).
- [ ] 10³ random operation sequences per run produce no invariant failure; a planted bug in any one mechanism
      produces a shrunk failing sequence of at most ten operations.
- [ ] `cargo tree -p frob-ground -e normal,build,dev` contains no banned crate; adding `serialport` as an
      optional dependency makes `xtask check-deps` fail and name it.
- [ ] The crate's sources contain no banned path (checked on the syntax tree, not by text search, so a comment
      does not trip it and an alias does not hide it).
- [ ] The seven invariants appear verbatim in `crates/frob-ground/CONTRACT.md`.

### End-to-end script and logging

This bead has no script of its own: it delivers property tests and a rule of `xtask check-deps`, which no
`frob` command reaches (KNOWN_DRIFTS 11); its tests above are its check. The invariants are asserted from the
user's side by the scripts of the capabilities they protect:
`ground_reality_line.sh` (01, 06), `ground_identify.sh` (02, 05), `ground_protocol.sh` (03, 04; N30a-35),
`ground_rehearsal.sh` (06 across the whole procedure) and `ground_firewall.sh` (07; N30a-01). Each logs the invariant identifier with the evidence
used: content addresses before and after, ledger sequences, digests of the randomization block, statuses.

### Known answers and negative controls

KA-734 (the protocol row: read before freeze, refit without a new version and holdout reuse are each refused)
is the hand case for 03 and 04. The seven planted violations above are the controls. Determinism lanes: the
sequence test with one seed gives the same sequences and the same verdict twice, in debug and release.

## Considerations

- Invariants are tested on `synthetic` data only; that is sufficient because they are statements about the
  mechanism's bookkeeping, not about the data.
- The firewall bans network crates outright. Ground's long jobs still reach the daemon, but through the verb
  layer above it, never from inside the crate. A network crate reached only through a lower-layer dependency
  (`frob-core`, the async runtime) is reported by the check as a finding against that crate's feature set and
  resolved there, not by an exception in Ground's list.
- If a later mechanism needs a new dependency, the firewall failure is the prompt to ask whether it belongs in
  Ground at all; the non-goal on deployment stacks stands.
