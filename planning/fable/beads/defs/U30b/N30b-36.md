## Background

GATE-GROUND-09 is the gate of the replication kit in Ground, the subsystem that compares simulation with
measured reality. A kit is a directory that lets a third party rebuild a result without access to the
originating machine or to anything private: inputs, records, the bench protocol, the analysis calls, expected
outputs with tolerances and determinism classes, cited certificates, the three no-authorization flags, and the
synthetic rehearsal. The gate (claim kind: Known answer; TARGET): a kit rebuilds the rehearsal on a clean
machine inside its class; a private input is refused. "Inside its class" means bit for bit on the same backend
(class D2) and inside the recorded envelope otherwise (class D3).

Its record is read by the kill decision KILL-KIT (fallback: the kit ships as an archive of inputs, records and
hashes, with no reproduction claim). The script measures the gate from the user's side, and it is the one
script of the subsystem that must run in two places: on the machine that built the kit and on the other
platform.

## Scope

In: the script; the build; the clean-machine check; the second-platform lane; the private-input refusal and the
licence cases; the tamper controls; the log and the gate record. Out: the mechanisms (BD-396, N30b-12).

## Technical approach

`scripts/e2e/ground_kit.sh`, header `bead=N30b-36 milestone=M5 labels=ground,e2e,gate seed=1`. It sources
`scripts/e2e/lib.sh`. Modes: default (build and check on this machine); `--check-only <kit-dir>` (the
second-platform lane, run on a kit copied from the first machine).

1. **Step `prepare`.** In a fresh store: generate the rehearsal, ingest, identify, predict, score and band the
   nominal rig (the calls of the pipeline script, without their assertions), so that a result with full
   lineage exists.
2. **Step `build`.** `frob ground kit build --result <score-id> --out $K --json`. Assert: the manifest lists
   every section (design, cards, scene, task, predictions including superseded versions, records, dataset,
   protocol, analysis, expected, certificates if cited, rehearsal, NOTICE); the three authorization flags are
   present and `false`; every file's hash matches; a second build gives the same manifest hash.
3. **Step `check-clean`.** Copy $K to a temporary directory; make a fresh checkout of the commit named in the
   manifest; `env -i` with an empty `FROB_HOME`; network disabled for the process;
   `frob ground kit check $K --json`. Assert the verdict `pass`, every class-D2 call compared by digest, zero
   failures. `e2e_metric calls_bit_equal <count> calls == <manifest count> --gate GATE-GROUND-09`.
4. **Step `check-other-platform`** (`--check-only`). On the second platform: verdict `pass` with class-D2
   outputs compared inside the recorded envelope and every decision field equal.
   `e2e_metric calls_in_envelope <count> calls == <manifest count> --gate GATE-GROUND-09`. The receipt is
   appended to the same gate row as the first machine's.
5. **Step `private-refused`.** Mark the rehearsal's log dataset private through the real marking API (it is
   still `synthetic`; the mark is planted for the test) and derive a score from it. `e2e_expect_refusal
   FROB-REF-899 3 -- frob ground kit build --result <that score> --out $P`. Assert the payload names the
   dataset and the lineage step that carries the mark to the score, that `$P` does not exist afterwards, and
   that `--allow-private` is refused as an unknown parameter.
6. **Step `licence-cases`.** With a dataset labelled `research-only`: the kit builds with a dataset stub
   (hash and acquisition protocol), the prediction records present, derived scores listed as withheld, and
   its check verdict is `partial`. With an `attribution` input: `NOTICE` holds its text. With an `unknown`
   licence on a non-dataset asset: 899.
7. **Step `losing-result`.** Build a kit for the rejected omitted-law candidate: same sections, manifest
   `outcome = "rejected"`.
8. **Step `tamper-controls`.** `e2e_expect_caught` for: one file removed; one hash altered; one expected value
   changed by one unit in the last place; a flag set to `true`; a check run in the building store; a builder
   that screens direct inputs only (the inherited private mark passes: CX-G-13); a builder that drops
   superseded prediction versions or refuses the losing result (CX-G-14: step 2's section list or step 7
   fails).
9. **Step `record`.** `e2e_gate GATE-GROUND-09`.

Log: `target/e2e-logs/ground_kit/<utc-timestamp>.ndjson` and a transcript. Per command: command line, exit
code, wall time, evidence block. For the build: manifest hash, file count, section list, substitutions. For
each check: machine fingerprint, comparison mode per call, digests where compared, failures, verdict. For the
refusal: code, offending input identifiers and the marking lineage path as identifiers only. On failure: the
first call that differed, with expected and observed values and the kit path. Summary: assertions passed and
failed and `gates: ["GATE-GROUND-09"]`. The log never contains dataset content, and the lint of the shared
harness checks that.

## Acceptance criteria

- [ ] The script exits 0 when the kit builds, checks `pass` on the clean machine, and the private input is
      refused with nothing written; non-zero otherwise.
- [ ] The gate record holds two receipts (same backend by digest; other platform inside the envelope), the
      refusal, and the controls caught; it is complete only when both receipts exist.
- [ ] With `E2E_PLANT_FAILURE` set to `screen-direct-only`, `check-uses-build-store`, `flag-true`,
      `expected-regenerated` or `omit-superseded`, the script exits non-zero and names the step.
- [ ] The clean check succeeds with the network disabled and with no file read outside the kit and the
      checkout (asserted with the session's path jail log).
- [ ] The record is written by a session that did not implement the measured beads.

### End-to-end script and logging

This bead is the script; see the technical approach.

### Known answers and negative controls

The rehearsal's known answers, replayed from the kit by the check. Planted failures as in the acceptance
criteria and step 8. Determinism lanes are the gate itself: same machine by digest; other platform inside the
envelope; and the build twice with identical manifest hashes.

## Considerations

- The identification's ensemble lane is recorded per machine fingerprint; on the second platform its outputs
  are compared inside the envelope even though other outputs of the same call may be bit-comparable. The
  receipt lists the mode per field.
- A second machine may not be available at the moment the first run finishes; the gate row then stays
  incomplete (`not run` for the second receipt), which blocks nothing but the kill decision.
- If KILL-KIT has fired, the script asserts the archive form: no `expected/`, `reproduction_claim = false`, and
  a check verdict of `verified-archive`.
