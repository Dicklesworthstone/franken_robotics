## Background

ADR-FOUNDRY-01: **Foundry's optimization and build output run after the design decision, on qualified
finalists.** The beam rung also runs at preflight and after the first rollouts as a validity check that can
block promotion. An exploratory run is allowed, is labelled, and cannot enter a build packet.

Reason. Three-dimensional optimization of 12 to 20 links is CPU-hours and each design gains finite-element
solves per link, while the gain is a few percent of robot mass. Spending that on candidates that will be
discarded lengthens the loop for nothing. A build packet for a design that never passed qualification would
also be an artifact that looks like a release of an untested machine. The rejected alternative, running the
topology rung inside screening, was dropped for cost; a second rejected alternative, forbidding any structure
run before qualification, was dropped because an engineer or agent exploring what structure would do to a
design is a legitimate question, provided the answer cannot leak into a packet.

"Qualified" means the design holds a verdict from the blinded qualification lane: sealed world clusters,
pre-committed requests, receipts. A verdict is bound to a `DesignId` (the content hash of the design term) and a
`ModelId` (the compiled model, including actuator and material card versions).

Refusal FROB-REF-166: **optimization or packet export for a design with no qualification verdict.** Repair
offered: qualify, or run with `--exploratory` (labelled; cannot enter a packet).

## Scope

In: the admission function used by `foundry.optimize` and `foundry.export`; the `Exploratory` label and its
propagation; the rule that binds a packet to the verdict of the exact design and model it describes; the
refusal payload of FROB-REF-166.
Out: the qualification lane itself (BD-259); the promotion guard on under-built links and the provisional-case
refusal (unit U31b); verbs that need no verdict (`foundry.loads`, `foundry.size`, `foundry.check`,
`foundry.tolerance` run on any design, and their outputs inherit `Exploratory` only if their inputs carry it).

## Technical approach

1. **Admission function** (`admission.rs`, DESIGN):
   ```rust
   pub enum Admission { Qualified { verdict: VerdictId }, Exploratory }
   pub fn admit(design: DesignId, model: ModelId, purpose: Purpose, exploratory_flag: bool)
       -> Result<Admission, Refusal>;       // Purpose: Optimize | ExportPacket | ExportGeometryOnly
   ```
   Rules, in order:
   1. Look up the qualification ledger for (design, model). A verdict with status `passed` gives
      `Qualified`. A verdict that exists but is `failed`, `withdrawn` or for a different `ModelId` does not.
   2. No verdict and `exploratory_flag` false → FROB-REF-166.
   3. No verdict and `exploratory_flag` true: `Purpose::Optimize` → `Exploratory`;
      `Purpose::ExportGeometryOnly` → `Exploratory` (loose mesh files stamped exploratory in their sidecar);
      `Purpose::ExportPacket` → FROB-REF-166 regardless of the flag. The exporter has no code path that writes
      a manifest with `"exploratory": true`: the manifest field exists so that a reader can assert it is false.
2. **The label travels.** Every artifact derived from an `Exploratory` admission (optimized geometry, check
   results, typed edit, the new design) carries `StructLabel::Exploratory` in its record and in the envelope's
   `evidence.conditions`. The typed edit that feeds mass and inertia back records the label in the lineage
   graph, so a design descended from an exploratory structure run is recognizable. The packet assembler refuses
   any input record that carries the label (FROB-REF-166, pointer to the record).
3. **A packet cites the verdict of what it describes.** The structure loop changes mass and inertia, which is a
   new `DesignId` and `ModelId`. The verdict that admitted the *starting* design to optimization does not cover
   the *final* design. Rule (DESIGN, following INV-FOUNDRY-04, "mass properties in the packet equal those of
   the model the evidence was computed with"): `ExportPacket` requires a `passed` verdict whose design and model
   identities equal the packet's. The repair list for the usual case, "optimized design not yet re-qualified",
   is: (1) `frob eval qualify <final design> --task <task> --claim '<claim>' --key <new key>`, with the task and
   claim of the request whose verdict admitted the starting design (`eval.qualify` is a `run` verb: the task,
   the claim and the key are required inputs of its row in VERBS-eval, so a repair without them would itself be
   refused); (2) export the packet of the pre-optimization design, whose links are then the beam-rung sections.
4. **Refusal payload.** `code: FROB-REF-166`, `pointer: design`, `observed: {verdict: null | "failed" |
   "other-model", design, model}`, `required: "a passed qualification verdict for this design and model"`,
   `retry: after-change`, `repairs`: ranked as above, each with the exact command. Exit code 3.
5. **Hook for further packet preconditions.** `admit` returns, for `ExportPacket`, a list of precondition
   checks to run on the assembled inputs (`fn(&PacketInputs) -> Result<(), Refusal>`). This bead registers the
   exploratory-label check; the provisional-load-case check is registered by its own bead.
6. **Recording.** The admission outcome, the verdict identifier and the ledger frontier it was read at are
   written into the job record and into the packet manifest field `qualification`.

## Acceptance criteria

- [ ] `admit` for `Optimize` and for `ExportPacket` on an unqualified design returns FROB-REF-166 with exit 3 and the two ranked repairs, each with its exact command.
- [ ] `admit(…, Optimize, exploratory_flag = true)` on the same design returns `Exploratory`, and every record derived from it (geometry, check result, typed edit, lineage entry) carries the label `exploratory`; the envelope condition is set by the verb layer from that label.
- [ ] `admit(…, ExportPacket, true)` returns FROB-REF-166; `admit(…, ExportGeometryOnly, true)` returns `Exploratory` and the sidecar writer stamps `exploratory`.
- [ ] The registered packet precondition refuses packet inputs that include one exploratory record, naming the record.
- [ ] The same refusals at the verbs (`foundry.optimize` and `foundry.export`, exit 3, `refusal.code`) are asserted by the beads that wire them, BD-403 and the export beads, and by the scripts of N31a-54 and N31a-57; this bead's checks are on `admit` and its hook.
- [ ] A packet request for an optimized design whose only verdict is for the pre-optimization design is refused, with the re-qualification repair first.
- [ ] A verdict for the same design under a different `ModelId` (a card revision) does not admit.
- [ ] No code path can serialize a manifest with `"exploratory": true` (compile-level: the field's type has one value).

`cargo test -p frob-foundry admission`:
- `qualified_admits`; `failed_verdict_refuses_166`; `other_model_verdict_refuses_166`.
- `exploratory_optimize_admits_with_label`; `exploratory_packet_refused`; `exploratory_geometry_only_stamped`.
- `label_propagates_through_edit`: a design produced by an exploratory loop carries the label in its lineage record.
- `packet_inputs_with_exploratory_record_refused` (names the offending record path).
- `stale_verdict_after_optimization_refused`: verdict for design d₀, packet for d₁ = edit(d₀): refused; repairs are ranked re-qualify, then export d₀.
- `manifest_exploratory_field_has_one_value` (compile-fail on `true`).
- Planted defects, each caught: `admit-any-verdict` (ignores status), `ignore-model-id`, `drop-label-on-edit`.

### End-to-end script and logging
`scripts/e2e/foundry_admission.sh` (this bead's own, built only on its dependencies; it sources the STD-E2E
helper library). Steps: (1) `cargo test -p frob-foundry -- admission` through `e2e_cmd` (including the three
planted defects); (2) `cargo run -p frob-foundry --example admission -- --json`, an example program of this
bead over a scratch qualification ledger holding a `passed` verdict for d₀, a `failed` verdict, a verdict for
d₀ under another `ModelId`, and the edited design d₁ = edit(d₀): for each (design, model, purpose, flag) case
of the acceptance criteria it prints the outcome, and the script asserts with `e2e_assert_eq` on the printed
JSON `Qualified`, FROB-REF-166 (with exit code 3, pointer `design`, `observed.verdict` and the two repairs in
order, each with its exact command), `Exploratory` with the label on the derived records, FROB-REF-166 for
`ExportPacket` with the flag, the sidecar stamp for `ExportGeometryOnly`, and for d₁ the re-qualification
repair first. No `frob` verb is called, so the evidence block is recorded as absent with reason `no-verb`. Logs
to `target/e2e-logs/foundry_admission/<utc>.ndjson` with a transcript: per line `ts`, `script`, `bead` =
N31a-03, `step`, `event`, the command, exit code and wall time, and per case the verdict state, the ledger
frontier read, the outcome, the code and the first repair; on failure the first differing field; a final
`summary`. The verb-level refusals are steps of `scripts/e2e/foundry_structure_loop.sh` (N31a-54) and
`scripts/e2e/foundry_export_packet.sh` (N31a-57), which depend on the verb beads that call `admit` and run this
script as a stage: `frob foundry optimize <unqualified fixture> --key "$(e2e_key optimize-unqualified)" --json`
asserting exit 3 and `refusal.code == "FROB-REF-166"`; the same with `--exploratory --key "$(e2e_key
optimize-exploratory)"` asserting that `evidence.conditions` contains `exploratory`; `frob foundry export
<result> --packet <dir> --key "$(e2e_key export-exploratory)" --json` asserting the refusal; each logged with
`event: "refusal"`, the code, the pointer and the first repair.

### Known answers and negative controls
The verdict-binding case: the same design term with a changed actuator card has a different `ModelId`, and a
verdict for one does not admit the other. Negative controls are the three planted defects. Determinism: the
function is a pure read of the ledger at a recorded frontier; the same frontier gives the same outcome.

## Considerations

- Re-qualification after optimization costs a qualification run. That is the price of a packet whose evidence
  is about the object in the packet; the alternative, transporting a verdict across a mass change, would need
  a monotone-transport argument that the plan does not make for structure.
- The qualification lane has an error budget per request; a re-qualification consumes one request. The repair
  text says so.
- The exploratory path is where an agent will try to route around the rule. The checks are on the record
  labels, not on the command line, so re-submitting exploratory artifacts under a clean command still refuses.
