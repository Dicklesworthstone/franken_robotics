## Background

Load extraction from telemetry is a Frontier mechanism with a kill gate. KILL-LOADS: if GATE-FOUNDRY-02 (the
free-body residual, superposition against direct solves, and refusal of the assembled-peak and equal-limb
mutations) fails after one repair cycle, the fallback is that **load cases are declared by hand from statics
with a stated dynamic factor; spectra and fatigue read `no-claim`.** The decision is taken at M5 and may be
recorded at M4.

The same path is needed even if the kill gate never fires. The paper-scale pilot of the structure loop has a
first stage that runs before any telemetry exists: three analytic envelope cases from stance and trot statics.
And the beam rung, which costs milliseconds, is asked for structural margins on designs that have no campaign
yet.

A declared case is honest about what it is: a statics calculation multiplied by a factor someone chose. It is
not an instant of an episode, so it is a different type from a campaign case, it carries its own label, and it
can never be mistaken for one. The rejected alternative, synthesizing fake "samples" so that the campaign
machinery could run unchanged, would have passed INV-FOUNDRY-02's replay test by construction and hidden the
difference.

## Scope

In: the declared-load file format; the generator from statics for stance patterns; the dynamic factor and its
provenance; the equilibrium check on declared cases; labels and what downstream stages do with them.
Out: the preflight-time bounded load set and its promotion rule (unit U31b); campaign cases (N31a-06 to
N31a-12); the beam criteria (BD-401).

## Technical approach

1. **Format** (`loads/declared.rs`; schema `frob.foundry.declared-loads/1`, DESIGN):
   ```json
   { "schema": "frob.foundry.declared-loads/1", "design": "DesignId", "model": "ModelId",
     "basis": "statics", "dynamic_factor": { "value": 3.0, "source": "archetype card: legged feet" },
     "cases": [ { "name": "trot-diagonal-FL-HR", "class": "lower-leg",
                  "instance": "FL.shank", "pose": "nominal-stance",
                  "ports": [ { "port": "knee", "force_N": [0, 0, -214.765635], "moment_Nm": [0, 0, 0] },
                             { "port": "foot", "force_N": [0, 0, 220.649625], "moment_Nm": [0, 0, 0] } ],
                  "body": { "a0": [0, 0, 29.41995], "alpha": [0, 0, 0], "omega": [0, 0, 0] } } ],
     "justification": "Stance and trot statics; factor from the archetype card." }
   ```
   The example is a 15 kg robot on a trot diagonal with k = 3 and a 0.2 kg shank held vertical, its knee, centre
   of mass and foot on one vertical line in the link frame: the ground pushes the foot up with
   3 × 15 × 9.80665/2 = 220.649625 N, the body load is −0.2 × 29.41995 = −5.88399 N, so the knee carries
   −214.765635 N and every moment is zero; the residual is exactly zero.
   Type `DeclaredCase`, distinct from `EnvelopeCase`: it has no world address and no trace digest.
2. **Generator** (`foundry.loads --declared statics [--dynamic-factor k] [--patterns …]`). For each support
   pattern of the design's archetype (all feet; each trot diagonal; each trot diagonal with traction; single
   support for a biped; wheels on the ground for a wheeled base; the rated payload at full reach for an arm).
   The traction pattern adds to each supporting foot a tangential force μ·N along the direction of travel, N
   the foot's normal force and μ the friction coefficient of the reference floor on the design's world card
   (its source recorded); it is generated as an effective gravity vector tilted so that its horizontal
   component is μ times its vertical one (the robot accelerating at μ·k·g along the direction of travel), so
   that every link stays in equilibrium as in step 3:
   1. solve the static support forces at the nominal pose; where the support is statically indeterminate (four
      feet) take the minimum-norm vertical distribution and state that rule in the file;
   2. compute joint constraint wrenches by inverse statics;
   3. apply the dynamic factor k as an effective gravity k·g (DESIGN): the statics of steps 1 and 2 are solved
      with gravity multiplied by k, which is the load state of the robot decelerating at (k − 1)·g on its
      supports. Support forces, joint wrenches and body loads all scale together, so every link, including the
      base, is in equilibrium in every case;
   4. for each link, write the port wrenches and the body field (a₀ = −k·g expressed in the link frame, g the
      effective gravity vector of the pattern, α = ω = 0). The file records the factor, μ for a traction
      pattern, and that both were applied as effective gravity.
   k defaults to the class load factor on the archetype card (DESIGN defaults: 3 for legged feet, 2 for
   wheels, 1.5 for manipulator ports with the rated payload added) and may be overridden; its source is
   recorded.
3. **Equilibrium check.** Every declared case, generated or hand-written, passes the free-body check of
   N31a-07 at tolerance 10⁻⁹ or the file is refused with FROB-REF-167 (the offending case and residual). A
   hand-written case is exactly where a sign or frame error hides.
4. **Labels and downstream behaviour.**
   - Every result computed from declared cases carries `loads: declared (factor k)` in its record and in the
     envelope's conditions.
   - There are no spectra: fatigue utilization is `fatigue: no-claim` with reason `declared-loads`.
   - Variants and frequency separation do not apply; the result says `impact: by factor only`.
   - The structure loop accepts a declared set in place of a campaign: the "campaign" stage regenerates the
     set for the edited design (statics change with mass), so the loop still closes.
   - A packet built on declared loads is permitted and says so in `structure/`; under KILL-LOADS this is the
     only kind.
5. **Agreement with the pilot.** Stage 1 of the structure-loop pilot (N31b-06, M4) runs before this bead and
   computes its three analytic cases for one quadruped lower-leg link by its own script: (a) four-leg stance,
   foot force W/4 along the leg's support direction; (b) trot diagonal, W/2; (c) trot with traction, W/2
   normal plus μ·W/2 tangential; each the foot-port wrench with the knee port as the statically determinate
   restraint and the body field of gravity alone, with no dynamic factor. This generator, run at k = 1 with the
   patterns all-feet, trot-diagonal and trot-traction on the pilot's frozen fixture, must reproduce those cases:
   the foot-port wrenches exactly (rational pose), and the knee reaction exactly for (a) and (b); for (c) it
   differs from the pilot's by the link's own tangential body load m_link·μ·g, because the generator keeps
   the whole robot in equilibrium where the pilot restrains one link at the knee; the test computes that term
   and asserts the difference equals it. A disagreement beyond that is a defect in one of the two and blocks
   the generator's use by the loop until reconciled.
6. **Class and determinism.** Estimated (a chosen factor is an assumption and is the weakest input); the
   statics are exact rational or `f64` deterministic; the file hash identifies the set.

## Acceptance criteria

- [ ] The generator (`declared::generate`, which `foundry.loads --declared statics` calls once BD-400 wires the verb) on the reference quadruped writes a schema-valid file with one case per support pattern and link class, each passing the equilibrium check at 10⁻⁹.
- [ ] For a 15 kg quadruped in a trot diagonal stance each supporting foot carries 15 × 9.80665/2 = 73.55 N before the factor and 220.65 N with factor 3.
- [ ] A hand-written case with one force sign flipped is refused with FROB-REF-167.
- [ ] Results from declared loads carry the label, `fatigue: no-claim`, and the factor with its source; no result from declared loads has a world address.
- [ ] The type system prevents passing a `DeclaredCase` where an `EnvelopeCase` is required without going through the labelled conversion (compile-fail test).
- [ ] The structure loop runs to convergence on declared loads for the planted-gain fixture.
- [ ] With the KILL-LOADS switch set in configuration, the campaign entry point (`campaign::submit` and the campaign reader, the bodies behind `foundry.loads --campaign`) refuses with FROB-REF-724 (the capability is not in this build; exit code 5) and a message naming the fallback, and `--declared statics` is the offered repair; the same refusal at the verb is asserted by BD-400's script.
- [ ] The generator reproduces the three stage-1 cases of the pilot N31b-06 on its frozen fixture: foot-port wrenches exactly, knee reactions exactly for the two vertical cases and within exactly the stated body-load term m_link·μ·g for the traction case.
- [ ] The trot-traction pattern gives each supporting foot a tangential force μ·N with μ and its source recorded, and every link passes the equilibrium check at 10⁻⁹.

## Test plan

### Unit tests
`cargo test -p frob-foundry loads::declared`:
- `trot_diagonal_support_force`: 73.55 N and 220.65 N.
- `four_foot_min_norm_distribution`: centre of mass centred: 147.09975/4 = 36.77 N per foot; shifted 0.05 m forward with a 0.40 m wheelbase: front feet 15 × 9.80665 × (0.25/0.40)/2 = 45.97 N, hind 27.58 N.
- `effective_gravity_keeps_every_link_in_equilibrium`: with k = 3 every link of the fixture, the base included, passes the free-body check at 10⁻⁹.
- `hand_case_sign_flip_refused_167`.
- `label_and_no_claim_propagate`.
- `declared_is_not_envelope_case` (compile-fail).
- `loop_closes_on_declared_loads`.
- `factor_source_recorded`.
- `trot_traction_tangential_force`: 15 kg robot, μ = 0.6, k = 1: each supporting foot carries 73.549875 N normal and 44.129925 N tangential, and every link passes the check at 10⁻⁹.
- `reproduces_pilot_stage1_cases` (the three cases of N31b-06 from its registered fixture file; the traction-case knee difference equals m_link·μ·g).
- `kill_loads_refuses_campaign_724`.
- `example_file_is_in_equilibrium`: the example above parses and its residual is exactly zero.
- Planted defects, each caught: `factor-on-support-forces-only` (scales the foot forces and leaves the body field at 1 g, so the base link fails the check), `declared-case-with-fake-address`.

### End-to-end script and logging
`scripts/e2e/foundry_declared_loads.sh` (this bead's own, built only on its dependencies; it sources the
STD-E2E helper library). Steps: (1) `cargo test -p frob-foundry -- loads::declared` through `e2e_cmd`
(including the two planted defects and the compile-fail test); (2) `cargo run -p frob-foundry --example
declared_loads -- --fixture <trot fixture> --factor 3 --out <scratch>/declared.toml --json`, an example program
of this bead calling `declared::generate`: assert 73.55 N per supporting foot before the factor and 220.65 N with
it, one case per support pattern and link class, every residual at most 10⁻⁹ (`e2e_assert_num`), the label,
`fatigue: no-claim` and the factor with its source, and no world address in the file; (3) the generator on the
frozen fixture of the pilot N31b-06: the three stage-1 cases reproduced (foot-port wrenches exactly; the
traction-case knee difference equal to m_link·μ·g); (4) a scratch copy of a hand-written case with one force
sign flipped, read back by the example's `--check`: exit 3 and FROB-REF-167; (5) with the KILL-LOADS switch set
in a scratch configuration, the example's campaign entry (`campaign::submit`): exit 5 and FROB-REF-724 with
`--declared statics` the offered repair. No `frob` verb is called, so the evidence block is recorded as absent
with reason `no-verb`. Logs to `target/e2e-logs/foundry_declared_loads/<utc>.ndjson` with a transcript: per
line `ts`, `script`, `bead` = N31a-13, `step`, `event`, the command, exit code and wall time; the factor, its
source and the per-case residual; on failure the first case out of equilibrium; a final `summary`. The
verb-level steps are in `scripts/e2e/foundry_loads.sh` (N31a-53, which owns that script and runs this one as
a stage): `frob foundry loads <design> --declared statics --key "$(e2e_key declared-statics)" --json`, then
`frob foundry size <design> --loads <file> --json` (a `read`, no key), asserting the label, the no-claim on
fatigue and exit code 2 or 0 according to the margins; and, with the KILL-LOADS switch set in a scratch
configuration, `frob foundry loads <design> --campaign <spec> --key "$(e2e_key campaign-killed)" --json`
exiting 5 with FROB-REF-724 and offering `--declared statics`.

### Known answers and negative controls
Statics: 15 × 9.80665 = 147.10 N; ÷ 2 = 73.55 N; × 3 = 220.65 N; the shifted-mass distribution above. Negative
controls: the two planted defects and the sign flip. Metamorphic: doubling the factor doubles every port wrench
and the a₀ of every body field. Determinism: the generated file is byte-identical on every platform when
the pose is given in rationals.

## Considerations

- A dynamic factor hides everything the campaign would have shown: which leg works hardest, which instant
  governs, whether the link rings. The label is what keeps a reader from treating the result as more.
- The factor defaults are DESIGN values on the archetype card, not standards; a team with its own design
  practice overrides them and the source field records that.
- If KILL-LOADS fires, analysis A-15 and the beam rung are unaffected; the topology rung can still run on
  declared cases, but its saving is then against a baseline sized to the same assumed loads, and BET-29's
  comparison says so.
