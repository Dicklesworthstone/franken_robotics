## Background

A build packet contains each made part's geometry in four formats: STEP for mechanical interchange, STL and
3MF for printing and quoting, GLB for viewing. Every one of them must be the same object that was checked and
weighed, or the packet's evidence is about something else (INV-FOUNDRY-04: mass properties in the packet equal
those of the model the evidence was computed with, tested by recomputing them from the exported geometry).

**Geometry export.** The extracted surface passes repair and validity checks (watertight, manifold, oriented)
through the quarantine path of the exchange sibling, then is written as STL, 3MF and GLB. (STEP has its own
bead because it needs a bound and a replay.) The sibling provides the exporters and quarantines every import;
its default limits admit 10⁶ instances per file.

"Bounded" in the title of this part of the chapter means that every export has a stated size limit and a stated
behaviour above it; nothing is truncated silently.

The design problem hidden in "four formats" is numeric: binary STL and GLB store vertex coordinates in single
precision, while 3MF and STEP store decimal text. If the checked polyhedron has double-precision vertices, the
single-precision files hold a slightly different polyhedron and the cross-export identity of 10⁻⁶ on mass
properties depends on luck and on how far the part sits from its origin. The decision here (DESIGN) is to make
the polyhedron *export-exact* before it is checked: its vertices are representable in single precision in a
part frame centred on the part, so all four formats carry bit-identical coordinates.

## Scope

In: the export-exact part frame and vertex rule; the canonical triangle order; the allowed canonicalizing
repairs; validity through the quarantine path; deterministic writers for STL, 3MF and GLB; read-back; triangle
counts; loose (non-packet) export with its sidecar.
Out: STEP and its bound (N31a-35); datums, fiducials, `mass.json` and the cross-export identity test (N31a-40);
the flags type (N31a-37); extraction and meshing (N31a-17).

## Technical approach

1. **Export-exact polyhedron** (`export/repair.rs`). For each made part:
   - the *part frame* has its origin at the centre of the part's bounding box and the axes of the link frame;
     the rigid transform to the link frame is recorded in `parts.json`;
   - every vertex coordinate, expressed in the part frame in metres, is rounded to the nearest value
     representable in single precision. For a 0.3 m part this moves a vertex by at most about 1.5 × 10⁻⁸ m.
   The extraction stage applies this rounding before validation and meshing, so the polyhedron that is
   meshed, checked and weighed is the one exported. This stage asserts the property and refuses a surface that
   lacks it (an internal error naming the first offending vertex), never rounding silently at export time.
2. **Canonical order.** Vertices sorted lexicographically by (x, y, z) bit patterns; triangles oriented outward
   and sorted by their smallest vertex index after rotation to start at that index. The same mesh therefore
   always serializes to the same bytes.
3. **Canonicalizing repairs** (the only ones allowed, each counted in the receipt): merging vertices with
   identical coordinates; removing triangles with two identical vertices; fixing orientation consistently
   outward. Anything else (holes, self-intersections, non-manifold edges) is not repaired here: the surface
   is rejected and the remedy is re-extraction at a finer grid.
4. **Validity through quarantine.** Each written file is immediately re-imported through the sibling's
   quarantine path, which returns a receipt (limits applied, counts, hash). The re-imported mesh must be
   watertight (every edge shared by exactly two triangles), manifold (the triangles around each vertex form
   one fan), oriented (each edge traversed once in each direction), and equal to the canonical mesh vertex
   for vertex and triangle for triangle. A mismatch fails the export of that part.
5. **Writers** (`export/mesh.rs`), all deterministic:
   - STL: binary, 80-byte header containing the ASCII text `frob-foundry export; units: metre` padded with
     zeros, normals recomputed from vertices, attribute bytes zero;
   - 3MF: unit `meter`, one object, vertices as shortest round-trip decimals of the single-precision values,
     a zip container with fixed entry order, fixed timestamps and stored (uncompressed) entries so the bytes
     do not depend on a compression library;
   - GLB: positions as a single-precision accessor, indices as 32-bit unsigned integers, no normals (viewers
     compute them), one mesh, one node, `asset.extras` holding the part identity; glTF's unit is the metre.
6. **Counts and hashes.** Per part and format: triangle count, vertex count, file size, BLAKE3. Counts are
   equal across formats by construction and the test asserts it.
7. **Loose export.** `foundry.export --geometry <part> --format stl|3mf|glb` outside a packet writes the file
   and a sidecar `<file>.flags.json` holding the file's hash, the design and model identities, the four
   no-authorization flags (all false), `units: "SI (metre)"`, and `exploratory` as admitted. The sidecar is
   what makes a loose file an artifact that "says so in machine-readable flags".
8. **Limits.** A mesh whose instance count would exceed the sibling's default limit in any format is refused
   for that format with the limit stated; the triangle bound that STEP imposes (about 285,000) is applied to
   the canonical mesh for all formats, so a part either exports in all four or in none.
9. **Class.** The files are views of a canonical object; they carry no evidence class of their own.

## Acceptance criteria

- [ ] The same part exported twice yields byte-identical STL, 3MF and GLB files (hash equality), on one machine and across platforms.
- [ ] Re-importing each file through quarantine gives a mesh identical to the canonical mesh (every coordinate bit and every index).
- [ ] An open shell (one triangle removed) is rejected with the open edges listed; a non-manifold fixture (two tetrahedra sharing one edge) is rejected.
- [ ] A surface with a vertex coordinate that is not single-precision-exact in the part frame is refused, naming the vertex.
- [ ] A mesh with inverted orientation is canonicalized and the receipt records one orientation repair.
- [ ] Triangle and vertex counts agree across the three formats, and for a tetrahedron are 4 and 4.
- [ ] A loose export writes its sidecar with the four flags false; removing the sidecar makes the file fail the reader's artifact check.
- [ ] The 3MF container's bytes do not change when the system clock or the compression library version changes (fixed timestamps; stored entries).

## Test plan

### Unit tests
`cargo test -p frob-foundry export::repair export::mesh`:
- `part_frame_is_bbox_centre`; `vertices_are_f32_exact`; `non_exact_vertex_refused`.
- `canonical_order_is_permutation_invariant`: shuffling the input triangles and vertices gives the same bytes.
- `allowed_repairs_only`: duplicate vertices merged; degenerate triangle removed; orientation fixed; a hole is not filled.
- `watertight_manifold_oriented_checks` on a tetrahedron, a cube (12 triangles) and a torus (genus 1).
- `open_shell_rejected`; `non_manifold_edge_rejected`.
- `stl_roundtrip_bit_exact`; `threemf_roundtrip_bit_exact`; `glb_roundtrip_bit_exact`.
- `deterministic_bytes_twice`; `threemf_zip_has_fixed_timestamps`.
- `counts_agree_across_formats`.
- `loose_export_sidecar_flags_false`.
- `euler_characteristic`: V − E + F = 2 for the cube (8 − 18 + 12) and 0 for the torus.
- Planted defects, each caught: `round-at-export-silently` (the exported mesh differs from the checked one; caught by the mass-property comparison and by the equality check), `stl-normals-from-stale-buffer`, `zip-with-wall-clock-timestamps` (hash differs between runs).

### End-to-end script and logging
`scripts/e2e/foundry_export_packet.sh` (bead N31a-57): `frob foundry export --geometry <part> --format stl`
(and `3mf`, `glb`) twice into two directories; asserts identical hashes, the sidecar's flags, and that
`frob foundry check <exported file>` reads it back; logs per format triangle count, bytes, hash, the quarantine
receipt's counts and the number of canonicalizing repairs.

### Known answers and negative controls
A tetrahedron has 4 vertices and 4 triangles; a triangulated cube 8 and 12; Euler characteristic 2 for a
sphere-like surface and 0 for a torus. Single-precision spacing near 0.15 m is 2⁻²⁶ m ≈ 1.5 × 10⁻⁸ m. Negative
controls: the three planted defects, the open shell and the non-manifold fixture. Metamorphic: translating the
link frame leaves the part-frame files unchanged; permuting input order leaves the bytes unchanged.
Determinism: byte identity is the test.

## Considerations

- Rounding vertices to single precision before the check changes the geometry by parts in 10⁷, far below any
  tolerance, and buys exact agreement among formats. The cost is a constraint on the extraction stage, which
  must produce export-exact vertices; this bead's refusal is what enforces it.
- 3MF and GLB have richer features (materials, colours, units other than metres); none is used. The files are
  evidence of shape.
- KILL-PACKET fallback keeps STL only; this bead's STL path is therefore the one that must not depend on the
  others.
- An exported mesh is not a release of anything. The flags and the sidecar say so, and the exporter has no
  path that writes them otherwise (ADR-FOUNDRY-09).
