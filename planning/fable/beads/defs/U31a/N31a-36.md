## Background

The build packet is what Foundry hands to people: everything needed to make and assemble the robot that was
qualified, with the evidence for each number and with flags that say it authorizes nothing. **The packet is
one directory written atomically and addressed by the hash of its manifest** (format FMT-FBUILD, schema
`frob.build/1`).

```
quad-a.fbuild/
  manifest.json         identities, flags, evidence classes, BLAKE3 of every file
  parts.json            made parts (geometry, material, process, mass) and purchased parts (card references)
  geometry/<part>.{step,stl,3mf,glb}      with triangle counts, datums and fiducials
  tolerances.json       per feature: tolerance, action, sensitivity, class; stack and robustness results
  mass.json             per part and assembly: mass, centre of mass, inertia, each with uncertainty
  harness.json          nets, connectors, conductor sizes, lengths with slack, checks
  schedule.json         actuator and sensor schedule
  structure/            load cases, utilizations, buckling factors, modes, loop convergence record
  fab.json              manufacturability report with repairs
  firmware/             optional; Moonshot; present only with feature firmware-export
  certs/*.frobcert      certificates the packet cites
```

```json
{ "schema": "frob.build/1", "design": "DesignId", "model": "ModelId", "qualification": "verdict id or null",
  "authorization": { "execution_authorized": false, "hardware_safety_signoff": false,
                     "sim_to_real_certified": false, "fabrication_released": false },
  "reality": "no-claim", "review": "no-claim", "units": "SI", "exploratory": false }
```

Two properties make it trustworthy as an object. It is content-addressed: the manifest lists the BLAKE3 hash of
every file, and the packet's identity is the hash of the manifest, so any change to any byte changes the
identity. And it is written whole or not at all (INV-FOUNDRY-05; tested by killing the writer at every file
boundary): a half-written directory that looks like a packet is worse than none.

A directory was chosen over an archive so that a person can open the STEP file or read a JSON section without
a tool, and so that downstream tools can address single files by path and hash.

## Scope

In: the directory layout; the manifest type, its canonical serialization and its hash; the atomic writer; the
reader with full verification; naming and addressing; idempotent re-export; the registry row's round trip.
Out: the content of each section (N31a-39 to N31a-43); the flags type (N31a-37); the offline audit by
`frob-verify` (N31a-38); geometry files (N31a-34, N31a-35); the firmware directory's content (N31a-44).

## Technical approach

1. **Manifest type** (`packet/manifest.rs`; DESIGN, following the plan's sketch):
   ```rust
   /// The manifest of a `.fbuild` directory, written atomically and addressed by the manifest hash.
   pub struct BuildPacket {
       schema: SchemaId, design: DesignId, model: ModelId,
       qualification: Option<VerdictId>,
       authorization: PacketAuthorization,     // four flags, all false, no setter
       reality: RealityStatus,                 // NoClaim until Ground supplies data
       review: ReviewStatus,                   // NoClaim until a review, a quotation or an inspection is imported
       units: UnitSystem, exploratory: bool,   // the writer's type admits only `false`
       profile: PacketProfile,                 // Full | Reduced (the KILL-PACKET fallback)
       evidence: Vec<SectionEvidence>,         // per section: weakest class and its input
       files: Vec<(RelPath, Blake3, u64)>,     // every file below the directory except the manifest itself
   }
   ```
   The schema name is `frob.build/1`: the format registry owns schema names, and an older note that calls it
   `frob.fbuild/1` is superseded.
2. **Canonical bytes.** `manifest.json` is canonical JSON (keys sorted, no insignificant whitespace, integers
   above 2⁵³ as strings, a trailing newline). `files` is sorted by path; paths use forward slashes, are
   relative, contain no `..`, and are lower-case ASCII. Packet identity = BLAKE3(manifest bytes), printed as
   `fbuild:<hex>`.
3. **Atomic write** (`packet/writer.rs`).
   1. Create a staging directory `.<name>.fbuild.staging-<job id>` beside the target, on the same filesystem.
   2. Write every section file, flushing and syncing each; compute its hash from the bytes written.
   3. Write `manifest.json` last; sync it; sync the staging directory.
   4. Rename the staging directory to `<name>.fbuild` (one atomic rename); sync the parent directory.
   If the target exists: when its manifest hash equals the new one the operation is an idempotent success and
   the staging directory is removed; otherwise the export is refused as a conflict (exit code 7) unless
   `--replace` names the old packet's identity, in which case the old directory is renamed aside before step 4
   and removed after. A crash at any point leaves either no target or a complete one; staging directories
   found at start-up are deleted.
4. **Reader** (`packet/reader.rs`). `BuildPacket::open(dir)` verifies, in order: `manifest.json` parses as
   canonical JSON and re-serializes to the same bytes; schema is `frob.build/1`; the authorization block has
   all four flags present and false (otherwise FROB-REF-860); `exploratory` is false; every listed file exists
   with the listed size and hash; no file exists that is not listed; every section file parses against its
   own schema and repeats the same `design` and `model`. Any failure is a refusal that names the path and the
   expected and observed values; the reader returns no partially verified packet.
5. **Addressing.** A packet is referred to by its identity; the directory name is a label. The ledger records
   (identity, design, model, verdict, job, time). `frob foundry export` prints both.
6. **Section evidence.** For each section the manifest carries the weakest evidence class among its numbers
   and the input that set it; the packet's own class is the weakest of those (Estimated whenever a material
   or process card field is). Classes are also printed per number inside the sections.
7. **Round trip (format registry).** Reading a packet and writing it again through the writer yields
   byte-identical files and the same identity.
8. **Determinism.** No timestamps, host names or absolute paths appear in any file; the job identity and time
   live in the ledger, not in the packet. The same inputs give the same identity on every platform.

## Acceptance criteria

- [ ] GATE-FOUNDRY-10, schema and hashes: a written packet validates against `frob.build/1`, and every file's BLAKE3 and size match the manifest.
- [ ] GATE-FOUNDRY-10, atomicity: with the writer killed after each file boundary in turn (every section file, the manifest, the rename), the target directory either does not exist or opens as a complete packet; in no case does a partial packet exist under the target name.
- [ ] Changing one byte of any file, adding a file, or removing a file makes the reader refuse, naming the path.
- [ ] Re-exporting identical inputs is an idempotent success with the same identity; different inputs to an existing name are a conflict (exit 7) without `--replace`.
- [ ] The manifest contains no timestamp, host name or absolute path; two exports on two machines give the same identity.
- [ ] Read-then-write reproduces every byte.
- [ ] A manifest listing a path with `..` or an absolute path is refused.
- [ ] Stale staging directories are removed at start-up and never opened as packets.

## Test plan

### Unit tests
`cargo test -p frob-foundry packet::manifest packet::writer packet::reader`:
- `manifest_canonical_and_stable_hash`; `files_sorted_and_relative`.
- `kill_at_every_boundary`: a fault-injecting filesystem wrapper aborts the writer at each of the N + 2 boundaries of a packet with N files; after each abort `open(target)` is either `NotFound` or a full success.
- `reader_detects_byte_change`; `reader_detects_extra_file`; `reader_detects_missing_file`; `reader_detects_size_mismatch`.
- `idempotent_reexport`; `conflict_without_replace_exit_7`; `replace_names_old_identity`.
- `no_timestamps_or_hosts` (a scan of every JSON value against patterns for dates, host names and absolute paths).
- `round_trip_is_bytewise_identical`.
- `path_traversal_refused`.
- `section_identities_must_match_manifest`: a `mass.json` naming another model is refused.
- `staging_cleanup`.
- Planted defects, each caught: `manifest-first` (writes the manifest before the sections; the kill test finds a directory that opens with missing files), `rename-file-by-file` (moves files into an existing target one at a time), `hash-of-intended-bytes` (hashes the in-memory buffer while a short write hit the disk).

### End-to-end script and logging
`scripts/e2e/foundry_export_packet.sh` (bead N31a-57): exports a packet, verifies it with `frob foundry check
<packet>` and with `frob-verify`, flips one byte in `mass.json` in a scratch copy and asserts the refusal, and
runs the kill lane (`FROB_TEST_KILL_AT=<n>` for each boundary) asserting no packet under the target name;
logs the identity, the file table with hashes, and per kill point the observed state.

### Known answers and negative controls
No numeric known answer; the properties are structural. Negative controls: the three planted defects and the
mutations of the reader tests. Metamorphic: renaming the packet directory changes nothing inside it and not
its identity; the order in which sections are produced does not change the identity. Determinism: identity
equality across runs, worker counts and platforms.

## Considerations

- Directory rename is atomic on the filesystems in use; on a filesystem where it is not, the writer refuses to
  export there (a probe at start writes and renames a scratch directory and checks the semantics it relies
  on).
- KILL-PACKET (M5): if GATE-FOUNDRY-09 or -10 fails after one repair cycle the packet is reduced to a parts
  list, mass properties and STL; `profile: Reduced` is that form, with the same container rules.
- The packet may contain data derived from a private scene (load cases). Logs carry identities and hashes
  only; the packet itself is the user's artifact.
- Review is an import lane: a human review, a quotation from a machine shop and a first-article inspection are
  records that may be imported as sidecars addressed by the packet identity; importing one changes no byte of
  the packet. Until one is, `review` reads `no-claim`.
