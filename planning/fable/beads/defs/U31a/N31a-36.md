## Background

The build packet is what Foundry hands to people: everything needed to make and assemble the robot that was
qualified, with the evidence for each number and with flags that say it authorizes nothing. **The packet is
one directory written atomically and addressed by the hash of its manifest** (format FMT-FBUILD, schema
`frob.build/1`).

```
quad-a.fbuild/
  manifest.json         identities, flags, evidence classes, BLAKE3 of every file
  parts.json            made parts (geometry, material, process, mass) and purchased parts (card references)
  geometry/<part>.{step,stl,3mf,glb}      with triangle counts, datums and fiducials
  tolerances.json       per feature: tolerance, action, sensitivity, class; stack and robustness results
  mass.json             per part and assembly: mass, centre of mass, inertia, each with uncertainty
  harness.json          nets, connectors, conductor sizes, lengths with slack, checks
  schedule.json         actuator and sensor schedule
  structure/            load cases, utilizations, buckling factors, modes, loop convergence record
  fab.json              manufacturability report with repairs
  firmware/             optional; Moonshot; present only with feature firmware-export
  certs/*.frobcert      certificates the packet cites
```

```json
{ "schema": "frob.build/1", "design": "DesignId", "model": "ModelId", "qualification": "verdict id or null",
  "authorization": { "execution_authorized": false, "hardware_safety_signoff": false,
                     "sim_to_real_certified": false, "fabrication_released": false },
  "reality": "no-claim", "review": "no-claim", "units": "SI", "exploratory": false }
```

Two properties make it trustworthy as an object. It is content-addressed: the manifest lists the BLAKE3 hash of
every file, and the packet's identity is the hash of the manifest, so any change to any byte changes the
identity. And it is written whole or not at all (INV-FOUNDRY-05; tested by killing the writer at every file
boundary): a half-written directory that looks like a packet is worse than none.

A directory was chosen over an archive so that a person can open the STEP file or read a JSON section without
a tool, and so that downstream tools can address single files by path and hash.

## Scope

In: the directory layout; the manifest type, its canonical serialization and its hash; the atomic writer; the
packet-manifest bundle `certs/packet.frobcert` written beside the manifest; the reader with full verification;
naming and addressing; idempotent re-export; the registry row's round trip; the differential test of the reader
against the offline auditor.
Out: the content of each section (N31a-39 to N31a-43); the flags type (N31a-37); the offline audit by
`frob-verify` and the layout of the bundle kind it checks (N31b-44, on which this bead depends); geometry files
(N31a-34, N31a-35); the firmware directory's content (N31a-44).

## Technical approach

1. **Manifest type** (`packet/manifest.rs`; DESIGN, following the plan's sketch):
   ```rust
   /// The manifest of a `.fbuild` directory, written atomically and addressed by the manifest hash.
   pub struct BuildPacket {
       schema: SchemaId, design: DesignId, model: ModelId,
       qualification: Option<VerdictId>,
       authorization: PacketAuthorization,     // four flags, all false, no setter
       reality: RealityStatus,                 // NoClaim until Ground supplies data
       review: ReviewStatus,                   // NoClaim until a review, a quotation or an inspection is imported
       units: UnitSystem, exploratory: bool,   // the writer's type admits only `false`
       selection: SelectionBlock,              // status ModelRobust | NoneRecorded (no third value), records, frontier
       profile: PacketProfile,                 // Full | Reduced (the KILL-PACKET fallback)
       evidence: Vec<SectionEvidence>,         // per section: weakest class and its input
       files: Vec<(RelPath, Blake3, u64)>,     // every file below the directory except the manifest itself
   }                                           // and the packet-manifest bundle (step 3)
   ```
   `qualification` is an `Option` only because the plan's JSON shape allows null: the writer always holds a
   verdict (a request without one is refused upstream with FROB-REF-166), and the reader refuses a null with
   the reason `no-verdict`.
   The schema name is `frob.build/1`: the format registry owns schema names, and an older note that calls it
   `frob.fbuild/1` is superseded.
   `selection` is the prototype-spend record: `{status: "model-robust" | "none-recorded", records: [ids],
   frontier}`. This bead declares the field, its two-valued type and the reader's rule on it, because the
   offline auditor's checker (N31b-44, a dependency) already rejects a manifest whose `selection.status` is
   absent or has another value, so a packet written without it would fail `frob-verify`; the precondition
   that finds the selection records and fills the block is N31ax-01's, which depends on this bead. Until
   that precondition is registered the caller passes `none-recorded` with an empty record list.
2. **Canonical bytes.** `manifest.json` holds exactly the canonical bytes of the program's canonical writer
   (N34-18, through N34-19's `Canon<F>`): members sorted by code point, no insignificant whitespace, no
   trailing newline, integers above 2⁵³ as strings. The offline auditor re-serializes the embedded bytes and
   compares them byte for byte (N31b-44 step 1), so any other layout, a trailing newline included, is
   rejected there. `files` is sorted by path; paths use forward slashes, are relative, contain no `..`, and
   are lower-case ASCII; each entry's hash is the plain BLAKE3 of the file's bytes (a blob hash, N34-19).
   Packet identity = the artifact identity of the manifest, `Canon<F>::id()` of N34-19: the BLAKE3 hash of the
   canonical bytes under the domain string `frob.build/1`, the schema name (the format registry's identity
   rule, which the auditor recomputes as `manifest_digest`, N31b-44 step 6), printed as `fbuild:<hex>`.
3. **Atomic write** (`packet/writer.rs`).
   0. *Export door.* The writer's entry takes an `ExportGrant`, which only `frob_verbs::export::admit(packet,
      kind packet, session)` of N37-18 produces (the grant type has no public constructor, so no code path
      reaches the disk without one). The door's checks run before anything is written, in its order: flags
      present (for a packet the chapter's own FROB-REF-860 answers; N31a-37), privacy (FROB-REF-731, exit 5),
      licence (FROB-REF-733, exit 5), the row's `export:packet` scope, and the path jail on the target and the
      staging directory (FROB-REF-734, exit 5). When the design's licence set is `attribution` the writer adds
      a `NOTICES` file, assembled by the door's deterministic rule (entries sorted by source then licence), as
      one more section file listed in the manifest with its hash.
   1. Create a staging directory `.<name>.fbuild.staging-<job id>` beside the target, on the same filesystem.
   2. Write every section file, flushing and syncing each; compute its hash from the bytes written.
   3. Write `manifest.json` last among the listed files; sync it. Then write `certs/packet.frobcert`, the
      bundle of kind `packet-manifest/1` defined by bead N31b-44, with the bundle writer of the certificates
      crate: it embeds the manifest's canonical bytes verbatim, the manifest digest, the file list with hashes
      and sizes, the header bytes of every JSON section and, per made part, the check-mesh and optimizer-grid
      hashes. It is the offline auditor's only input format, it is the one file the manifest does not list
      (listing it would be circular), and its own bundle digest is reported in the verb's envelope. Sync it;
      sync the staging directory.
   4. Rename the staging directory to `<name>.fbuild` (one atomic rename); sync the parent directory.
   If the target exists: when its manifest hash equals the new one the operation is an idempotent success and
   the staging directory is removed; otherwise the export is refused as a conflict (exit code 7) unless
   `--replace` names the old packet's identity, in which case the old directory is renamed aside before step 4
   and removed after. A crash at any point leaves either no target or a complete one; staging directories
   found at start-up are deleted. (`--replace <identity>` is this bead's option of `foundry.export`, listed
   in the VERBS-foundry row with this bead as the one that fixes its spelling.)
4. **Reader** (`packet/reader.rs`). `BuildPacket::open(dir)` verifies, in order: `manifest.json` parses as
   canonical JSON and re-serializes to the same bytes; schema is `frob.build/1`; the authorization block has
   all four flags present and false (otherwise FROB-REF-860); `exploratory` is false; `reality` and `review`
   are `no-claim` and `units` is `SI`; `selection.status` is present and is `model-robust` or `none-recorded`;
   every listed file exists
   with the listed size and hash; no file exists that is not listed, other than `certs/packet.frobcert`, which
   must exist and whose embedded manifest bytes must equal `manifest.json`; the bundle's `manifest_digest`
   equals the packet identity, its file list equals the manifest's, every made part has a check-mesh hash that
   is present and differs from its optimizer-grid hash, and the bundle's own three flags are present and false
   (otherwise FROB-REF-860: inside a packet the bundle is a member and its flags are the packet's, so the
   reader answers with the code every packet-reading verb lists, where the auditor reports its bundle code
   FROB-REF-833 with the same reason token); `qualification` is not null; every
   section file parses against its own schema, repeats the same `design` and `model`, and carries the four
   flags false in its header (otherwise FROB-REF-860). These are the auditor's checks (N31b-44 steps 1 to 10
   and its directory mode), implemented a second time on purpose, and each failure carries the auditor's
   reason token (`hash-mismatch`, `size-mismatch`, `unlisted-file`, `missing-file`, `not-canonical`,
   `schema-unknown`, `digest-mismatch`, `exploratory`, `no-verdict`, `selection-status`,
   `section-identity-mismatch`, `mesh-hash-missing`, `mesh-hash-not-independent`, `path-not-normalized`, and
   the flag tokens), so that the differential test compares the two verdicts token for token. A flag failure
   is FROB-REF-860 (`retry: never`); every other failure is the held refusal `packet-integrity-failed` of
   N31-REF's Table 3 (no fitting interim: exit 3, `detail: "packet-integrity-failed"` behind the named
   constant `PACKET_INTEGRITY_FAILED`, `retry: after-change`), with the path, the reason token and the
   expected and observed values; the reader returns no partially verified packet.
5. **Addressing.** A packet is referred to by its identity; the directory name is a label. The ledger records
   (identity, design, model, verdict, job, time). `frob foundry export` prints both.
6. **Section evidence.** For each section the manifest carries the weakest evidence class among its numbers
   and the input that set it; the packet's own class is the weakest of those (Estimated whenever a material
   or process card field is). Classes are also printed per number inside the sections.
7. **Round trip (format registry).** Reading a packet and writing it again through the writer yields
   byte-identical files and the same identity.
8. **Determinism.** No timestamps, host names or absolute paths appear in any file; the job identity and time
   live in the ledger, not in the packet. The same inputs give the same identity on every platform.
9. **The kill hook** (DESIGN; a test facility in `frob-foundry`'s `conformance` feature, which only the
   umbrella `gauntlet-mutations` enables, so no product binary has it, BD-025). In a build with the feature
   the writer reads `FROB_TEST_KILL_AT=<n>` and aborts the process (`std::process::abort`, so no destructor
   or clean-up runs) immediately after boundary n of the N + 3 boundaries, numbered from 1 in write order:
   the N listed files in path order, `manifest.json`, `certs/packet.frobcert`, the rename. Every envelope of
   such a build carries the warning `test-kill-hook`. A build without the feature never reads the variable:
   the export completes and the packet opens (a test asserts it). This is the hook the packet script's kill
   lane drives through a `frob` built with `--features gauntlet-mutations` (N31a-57 step 10, BD-408); the
   unit test `kill_at_every_boundary` uses the fault-injecting filesystem wrapper instead, in process.

## Acceptance criteria

- [ ] GATE-FOUNDRY-10, schema and hashes: a written packet validates against `frob.build/1`, and every file's BLAKE3 and size match the manifest.
- [ ] GATE-FOUNDRY-10, atomicity: with the writer killed after each file boundary in turn (every section file, the manifest, the rename), the target directory either does not exist or opens as a complete packet; in no case does a partial packet exist under the target name.
- [ ] Changing one byte of any file, adding a file, or removing a file makes the reader refuse, naming the path.
- [ ] Re-exporting identical inputs is an idempotent success with the same identity; different inputs to an existing name are a conflict (exit 7) without `--replace`.
- [ ] The manifest contains no timestamp, host name or absolute path; two exports on two machines give the same identity.
- [ ] Read-then-write reproduces every byte.
- [ ] A manifest listing a path with `..` or an absolute path is refused.
- [ ] Stale staging directories are removed at start-up and never opened as packets.
- [ ] Every written packet holds `certs/packet.frobcert`, whose embedded manifest bytes equal `manifest.json` byte for byte; the bundle is one more boundary of the kill test.
- [ ] A manifest with `exploratory: true` or `qualification: null` cannot be serialized by the writer and is refused by the reader (reasons `exploratory`, `no-verdict`).
- [ ] The reader and the offline auditor give the same verdict, with the same reason token, on every specimen of the auditor's set (bead N31b-44), the `selection.status` specimens included; `frob-verify --packet` accepts a packet this writer wrote, and its `manifest_digest` equals the identity the writer printed.
- [ ] `FROB_TEST_KILL_AT` aborts the writer at the named boundary only in a build with `frob-foundry`'s `conformance` feature; a build without it ignores the variable.
- [ ] The writer cannot be called without an `ExportGrant`; a target outside the session's export root is refused with FROB-REF-734 (exit 5) before a staging directory exists; an `attribution` licence set yields a listed `NOTICES` file and any other allowed set yields none.

## Test plan

### Unit tests
`cargo test -p frob-foundry -- packet::manifest packet::writer packet::reader`:
- `manifest_canonical_and_stable_hash` (no trailing newline; the identity equals `Canon<F>::id()` under the
  domain string `frob.build/1` and differs from the plain BLAKE3 of the same bytes); `files_sorted_and_relative`.
- `selection_block_two_values` (compile-fail on a third status); `reader_selection_status_rule` (absent and
  `model-conditional` refused with reason `selection-status`; the two values accepted).
- `kill_hook_absent_without_feature`: in a build without `conformance`, `FROB_TEST_KILL_AT=1` changes nothing.
- `kill_at_every_boundary`: a fault-injecting filesystem wrapper aborts the writer at each of the N + 3 boundaries of a packet with N listed files (each file, the manifest, the bundle, the rename); after each abort `open(target)` is either `NotFound` or a full success.
- `reader_detects_byte_change`; `reader_detects_extra_file`; `reader_detects_missing_file`; `reader_detects_size_mismatch`.
- `idempotent_reexport`; `conflict_without_replace_exit_7`; `replace_names_old_identity`.
- `no_timestamps_or_hosts` (a scan of every JSON value against patterns for dates, host names and absolute paths).
- `round_trip_is_bytewise_identical`.
- `path_traversal_refused`.
- `section_identities_must_match_manifest`: a `mass.json` naming another model is refused.
- `staging_cleanup`.
- `writer_requires_export_grant` (compile-time: the writer's entry takes the grant type); `target_outside_export_root_734_no_staging`; `attribution_notices_listed` (the `NOTICES` hash is in `files`); `no_notices_for_permissive_set`.
- `bundle_embeds_manifest_bytes`; `bundle_not_listed_in_manifest`; `reader_requires_bundle`; `null_verdict_refused`; `exploratory_true_refused`.
- Differential (`cargo test -p frob-foundry --test verify_differential`): for every specimen of the auditor's set, `BuildPacket::open` and `frob-verify --packet` give the same verdict.
- Planted defects, each caught: `manifest-first` (writes the manifest before the sections; the kill test finds a directory that opens with missing files), `rename-file-by-file` (moves files into an existing target one at a time), `hash-of-intended-bytes` (hashes the in-memory buffer while a short write hit the disk).

### End-to-end script and logging
`scripts/e2e/foundry_packet_container.sh` (this bead's own, built only on its dependencies; it sources the
STD-E2E helper library; header `bead=N31a-36 milestone=M5 gates=GATE-FOUNDRY-10 seed=0 needs=cpu`). Steps: (1) `cargo test -p frob-foundry --
packet::manifest packet::writer packet::reader` and `cargo test -p frob-foundry --test verify_differential`
through `e2e_cmd` (including the three planted defects); (2) `cargo run -p frob-foundry --example
packet_container -- --fixture packet-sections-min --out <scratch>/a --json` and the same
into `<scratch>/b`, an example program of this bead that writes a packet from a fixed set of section files
(`synthetic`: one made part with four placeholder geometry files, every JSON section with its header, the
four flags from N31a-37's type, `selection.status: "none-recorded"`) through the door of N37-18 under a
scratch session of the run's state root: the two identities equal, every listed file's BLAKE3 and size
logged and matching, the manifest without a trailing newline; (3) `frob-verify --packet <scratch>/a/<name>.fbuild
--json` run from an empty directory with a cleared environment: exit 0, the same identity; (4) on scratch
copies, one byte of `mass.json` changed, an unlisted file added, a listed file removed, `fabrication_released`
set to true: `--example packet_container -- --open <dir> --json` refuses with the reason token and path
(FROB-REF-860 for the flag) and `frob-verify --packet` rejects with the same token; (5) the kill lane, through
the same example built with `--features conformance`: for each boundary n from 1 to N + 3, the run with
`FROB_TEST_KILL_AT=n` leaves the target absent or opening as a complete packet, never a partial one; a
following run removes the stale staging directory; the example built without the feature ignores the
variable; (6) the same inputs again: idempotent success with the same identity; changed inputs to the same
name: exit 7; with `--replace <old identity>`: exit 0 and the new identity; (7) a target outside the export
root: FROB-REF-734, exit 5, no staging directory; an `attribution` section set: a `NOTICES` file listed with
its hash. No `frob` verb is called (`foundry.export` is BD-408's, which depends on this bead), so the
evidence block is recorded as absent with reason `no-verb`. Logs to
`target/e2e-logs/foundry_packet_container/<utc>.ndjson` with a transcript: per line `ts`, `script`, `bead` =
N31a-36, `step`, `event`, the command, exit code and wall time; the identity, the file table with hashes and
sizes, the reader's and the auditor's verdict and reason token per mutation, and per kill point the boundary
and the observed state (`absent`, `complete`); on failure the first differing file and byte offset and the
paths of the packet and the scratch copy; a final `summary` (the gate is touched, not recorded: N31a-57
records GATE-FOUNDRY-10). The verb-level steps are steps 6, 7 and 10 of `scripts/e2e/foundry_export_packet.sh`
(N31a-57), which runs this script as a stage: `frob foundry export quad-ref-final --packet out/quad-a --key
"$(e2e_key packet-a)" --json`, `frob foundry check out/quad-a.fbuild --key "$(e2e_key reader-a)" --json`, and
the kill lane with `FROB_TEST_KILL_AT=n` on a `frob` built with `--features gauntlet-mutations`, one label per
boundary.

### Known answers and negative controls
No numeric known answer; the properties are structural. Negative controls: the three planted defects and the
mutations of the reader tests. Metamorphic: renaming the packet directory changes nothing inside it and not
its identity; the order in which sections are produced does not change the identity. Determinism: identity
equality across runs, worker counts and platforms.

## Considerations

- Directory rename is atomic on the filesystems in use; on a filesystem where it is not, the writer refuses to
  export there (a probe at start writes and renames a scratch directory and checks the semantics it relies
  on).
- KILL-PACKET (M5): if GATE-FOUNDRY-09 or -10 fails after one repair cycle the packet is reduced to a parts
  list, mass properties and STL; `profile: Reduced` is that form, with the same container rules.
- The packet may contain data derived from a private scene (load cases). Logs carry identities and hashes
  only; the packet itself is the user's artifact.
- Review is an import lane: a human review, a quotation from a machine shop and a first-article inspection are
  records that may be imported as sidecars addressed by the packet identity; importing one changes no byte of
  the packet. Until one is, `review` reads `no-claim`.
