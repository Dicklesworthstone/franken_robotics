## Background

Foundry fabricates nothing, buys nothing, flashes nothing and signs nothing off. Every artifact it writes says
so in machine-readable flags (INV-FOUNDRY-01: every exported artifact carries the no-authorization flags, all
false; tested by the type having one value, and by a mutated packet being rejected by reader and auditor).

Every artifact in this program carries three flags, all false: `execution_authorized`,
`hardware_safety_signoff`, `sim_to_real_certified`. A build packet adds a fourth, `fabrication_released`. They
exist because a build packet looks like a release: it has drawings, a parts list and tolerances. A person or
an agent downstream must not be able to mistake it for permission to cut metal, and no agent upstream must be
able to produce one that says it is. ADR-FOUNDRY-09: every exported artifact carries the no-authorization
flags; the exporter has no code path that sets one true.

The mechanism is a type, not a convention (DESIGN; the plan's sketch fixes intent, not signatures):

```rust
pub struct NoAuthorization { _sealed: () }      // the only value; it serializes to the four false fields
impl NoAuthorization { pub const fn new() -> Self { Self { _sealed: () } } }
// No constructor, setter or deserializer yields `true`. A packet that parses with a flag absent or true is
// rejected by the reader and by `frob-verify` (FROB-REF-860).
```

Refusal FROB-REF-860: an export without the flags, or any attempt to produce a true flag. Repair offered: none.

Two neighbouring fields follow the same logic. `reality: "no-claim"` until the calibration subsystem supplies
data about a real robot; `review: "no-claim"` until a human review, a shop quotation or a first-article
inspection is imported (ADR-FOUNDRY-11: no gate depends on a reviewer, a machine shop or a board; those are
import lanes that rest at `no-claim`).

## Scope

In: the packet authorization type and its serialization; the deserializer that rejects absent or true flags;
where the flags appear in a packet and beside loose exports; the reality and review status types; the request
path that turns any attempt to obtain a true flag into FROB-REF-860; the audit event.
Out: the three-flag type of the core crate and the envelope's `authorization` block on exporting verbs
(BD-005, BD-303); the offline auditor's rule (N31b-44); the review-record protocol (unit U31b).

## Technical approach

1. **Type** (`packet/flags.rs`). `PacketAuthorization` (the plan's sketch names it `NoAuthorization`; the name
   is changed here to avoid a clash with the three-flag type of the core crate):
   ```rust
   pub struct PacketAuthorization { _sealed: () }
   impl PacketAuthorization { pub const fn new() -> Self { Self { _sealed: () } } }
   ```
   It has no fields to set. `Serialize` writes exactly
   `{"execution_authorized":false,"hardware_safety_signoff":false,"sim_to_real_certified":false,"fabrication_released":false}`.
   It does not implement `Default`, `Clone` is trivial, and there is no `From<bool>` or builder.
2. **Deserializer.** Accepts a JSON object with exactly these four keys, each the literal `false`. A missing
   key, an extra key, a `true`, a string `"false"`, a number or `null` is an error that the reader maps to
   FROB-REF-860 with the key and the observed token. There is no lenient mode.
3. **Where the flags sit in a packet.** The manifest root (`authorization`), and the header object of every
   JSON section file (`parts.json`, `tolerances.json`, `mass.json`, `harness.json`, `schedule.json`,
   `fab.json`, every file under `structure/`), which is where a bill of materials or a generated drawing would
   be read on its own. Non-JSON members (geometry files, certificates) are covered by the manifest entry that
   hashes them; a geometry file exported outside a packet gets a sidecar with the flags (the mesh-export
   bead). The generated firmware crate carries them as a constant and in its own manifest.
4. **Status types.**
   ```rust
   pub enum RealityStatus { NoClaim }                       // a second variant arrives only with Ground's band type
   pub enum ReviewStatus  { NoClaim }                       // an imported record is a sidecar, not a manifest value
   ```
   The writer can only write `"no-claim"`. An imported review is shown by a *view* that joins the packet with
   its sidecar record; the manifest bytes never change.
5. **Attempts to obtain a true flag.** The verb `foundry.export` has no parameter that names a flag. A request
   whose JSON contains any of the four keys, or the keys `released`, `authorized`, `signoff` at any depth, is
   refused before work starts with FROB-REF-860: `pointer` to the key, `observed` the value, `repairs: []`,
   `retry: never`, exit code 3. The refusal is recorded as every refused request is, by the job ledger's row
   `refused {session, verb, code}` (BD-258), so the attempt is findable with the session identity: the usual
   source is an agent trying to satisfy a user who asked for "a released packet". No separate audit log
   exists in the program, and the pipeline answers before any handler runs, so the handler writes nothing.
   Where the check sits (DESIGN). The verb layer's request pipeline (N32a-04) validates every request against
   its input schema and refuses an unknown parameter with FROB-REF-802 before any handler runs, so a handler
   check alone would never see these keys and the caller would get the wrong code. The input schema
   `frob.foundry.export.in/1` therefore declares the seven keys as a `forbidden_keys` set mapped to
   FROB-REF-860, and the pipeline's validation step tests that set, at any depth, before its unknown-parameter
   rule. The export row's input schema carries the set (VERBS-foundry, its test `export_forbidden_keys`), and
   the pipeline's ordering rule (a schema-declared forbidden key answers with its declared code ahead of 802,
   at every depth, free-form objects included) is step 2 of N32a-04, an M0 bead this one already rests on.
   Both exist before this bead (VERBS-foundry is a dependency, and validation runs before the pipeline's
   not-implemented step, so the refusal answers even before the export handler of BD-408 lands), so the
   handler carries no second check for these keys, and the test
   `request_with_flag_key_refused_860` is the gate on the ordering as it reaches this verb.
6. **Text rule.** No message, schema description or report produced by Foundry describes a packet as
   released, approved, certified or signed off; a lint over the message catalogue enforces it.
7. **Compile-time tests.** A set of compile-fail tests pins what does not exist: a public field; a constructor
   taking an argument; `Default`; a deserializer that yields a value from a `true` token (tested at run time);
   a conversion from the core three-flag type that could lose the fourth.

## Acceptance criteria

- [ ] INV-FOUNDRY-01: every JSON file of a written packet has the four flags, all false, and the manifest has them at its root; a test walks a packet and asserts it.
- [ ] GATE-FOUNDRY-10: a packet whose manifest has `fabrication_released: true` is refused by the reader with FROB-REF-860; so is one with the key removed, and one with the string `"false"`.
- [ ] The same mutations in a section file's header are refused.
- [ ] There is no way to construct or deserialize a `PacketAuthorization` that serializes a `true` (compile-fail tests and a fuzz test of the deserializer over 10⁵ generated objects).
- [ ] A request to `foundry.export` containing `"fabrication_released": true` anywhere is refused with FROB-REF-860, no repairs, exit 3, and a `refused` row of the job ledger naming the session, the verb and the code.
- [ ] `reality` and `review` can only be written as `no-claim`.
- [ ] The message-catalogue lint fails on a planted string "packet released for fabrication".

## Test plan

### Unit tests
`cargo test -p frob-foundry packet::flags`:
- `serializes_to_four_false_fields` (exact bytes).
- `deserialize_accepts_only_four_false`: 16 truth assignments, of which only all-false passes; plus missing key, extra key, string, number, null.
- `no_public_constructor_with_argument`, `no_default`, `no_field_access` (compile-fail).
- `deserializer_fuzz_never_yields_true`.
- `walk_packet_flags_everywhere`.
- `mutated_manifest_flag_refused_860`; `mutated_section_header_refused_860`; `flag_removed_refused_860`.
- `request_with_flag_key_refused_860` (a top-level `fabrication_released` answers 860, not the pipeline's 802); `request_with_nested_released_key_refused_860`; `unknown_non_flag_key_still_802` (the forbidden set does not swallow ordinary unknown parameters).
- `refused_row_in_job_ledger`: after the refused request the job ledger holds `refused {session, verb:
  "foundry.export", code: "FROB-REF-860"}` and nothing is charged.
- `status_types_have_one_value`.
- `no_release_wording_lint`.
- Planted defects, each caught: `lenient-deserializer` (treats a missing flag as false), `flag-struct-with-pub-bools`, `skip-section-header-check`.

### Known answers and negative controls
The exact serialized bytes of the four-flag object. Of the 16 assignments of four booleans exactly one is
accepted. Negative controls: the three planted defects and every mutation above. Determinism: host logic,
identical everywhere.

## Considerations

- "Repair: none" is deliberate. The usual envelope offers ranked repairs; here the only honest answer to "make
  it say released" is that this program cannot.
- A downstream system may wrap a packet in its own release record. That record is theirs; the packet inside
  remains flagged false, and its identity does not change.
- The fourth flag exists only on build packets and the firmware export. The recurring flags gate of the safety
  chapter covers every flag an artifact kind carries, so this type is exercised there too at every milestone
  exit.
- The flags are present in each JSON section so that a file copied out of the packet still says what it is.
