## Background

`frob-verify` is the program's independent offline auditor: a single binary built from the standard library and
nothing else, living in the crate `frob-cert`, able to check an artifact on a machine that has neither the
agent, nor a GPU, nor the rest of the workspace. Its independence is the point: the code that wrote an artifact
is not the code that accepts it.

A build packet is one of the artifact kinds it must judge. GATE-FOUNDRY-10 says so in two clauses: "flags
present and false" and "a mutated flag rejected by `frob-verify`". The plan's sealed-type sketch says the
same: a packet that parses with a flag absent or true is rejected by the reader and by `frob-verify`
(FROB-REF-860). For other artifact kinds the auditor's general code for a missing or true flag is
FROB-REF-833; for packets the code is the Foundry one.

The reader in `frob-foundry` (bead N31a-36) and this auditor check overlapping things on purpose. They share no
code: `frob-cert` may not depend on `frob-foundry` or on anything else, so the packet rules are implemented a
second time, from the schema, in the auditor.

## Scope

In: the `packet` artifact kind in `frob-verify`; the checks; the rejection reasons; the registered mutations
it must reject; the report format; the proof that the binary's dependency list is unchanged.
Out: the packet writer and in-workspace reader (N31a-36); the flag type (N31a-37); cross-consistency of the
packet's content, which needs the model and is done by the assembler and by `foundry.check <packet>`
(N31a-43 and unit U31b's mechanical pre-review); verification of each certificate kind (the Lemma units).

## Technical approach

1. **Surface.** `frob-verify packet <dir> [--json]`. Exit 0 accepted; exit 3 rejected with a reason list;
   exit 9 if the directory cannot be read. Output: packet identity, schema, design and model identities, the
   file table with pass or fail per file, the flag check, the certificate checks, and a one-line verdict.
2. **Checks, in order** (`crates/frob-cert/src/packet.rs`; standard library only, using the crate's own
   canonical JSON reader and BLAKE3):
   1. `manifest.json` exists, is canonical JSON, and re-serializes to the same bytes;
   2. `schema == "frob.build/1"`; an unknown schema version is a rejection, not a best effort;
   3. the `authorization` object has exactly the four keys `execution_authorized`,
      `hardware_safety_signoff`, `sim_to_real_certified`, `fabrication_released`, each the JSON literal
      `false` → otherwise FROB-REF-860;
   4. `exploratory == false`; `reality` and `review` are the string `no-claim`; `units == "SI"`;
   5. `qualification` is a verdict identifier, not null (a packet for a design with no qualification verdict
      should not exist; null is rejected with the reason `no-verdict`);
   6. for every entry of `files`: the path is relative and normalized, the file exists, its size and BLAKE3
      match;
   7. no file exists under the directory that the manifest does not list;
   8. every JSON section file parses as canonical JSON, has a header with the same `design`, `model` and the
      four flags false;
   9. every `certs/*.frobcert` verifies under its own proof kind with the auditor's existing checkers, and
      every certificate the sections cite by hash is present;
   10. every made part's structural evidence record names a check mesh hash, and that hash differs from the
       optimizer grid hash recorded beside it (the offline-checkable half of INV-FOUNDRY-03);
   11. the packet identity printed is BLAKE3 of the manifest bytes.
3. **Reasons.** Each rejection carries a stable reason token (`flag-true`, `flag-missing`, `flag-not-literal`,
   `hash-mismatch`, `unlisted-file`, `missing-file`, `schema-unknown`, `not-canonical`, `exploratory`,
   `no-verdict`, `section-identity-mismatch`, `cert-rejected`, `mesh-hash-missing`, `path-not-normalized`),
   the path, and expected and observed values. Flag reasons carry code FROB-REF-860.
4. **Registered mutations** (specimens under `crates/frob-cert/tests/specimens/packet/`; one accepted packet
   and at least these rejected ones, each derived from it by a recorded edit): each flag set to `true` (four
   specimens); a flag key removed; a flag as the string `"false"`; one byte changed in each kind of file
   (geometry, a JSON section, a certificate); a file added; a file removed; the manifest re-ordered
   (non-canonical); `exploratory: true`; `qualification: null`; an unknown schema `frob.build/2`; a section
   header naming another model; a certificate replaced by one for another statement with a consistent hash in
   the manifest; a path `../x`.
5. **Dependency proof.** The test that lists the auditor binary's dependencies (already part of the auditor's
   own gate) is re-run with the packet module compiled in and must still list the standard library only.
6. **What the auditor does not check, stated in its output.** That the mass properties match the geometry,
   that nets have two ends, that the verdict is for this design: these need the workspace and are checked by
   `foundry.check <packet>`. The auditor prints `content cross-consistency: not checked offline`.
7. **Determinism.** Pure function of the directory's bytes; identical output on every platform.

## Acceptance criteria

- [ ] GATE-FOUNDRY-10: the accepted specimen passes; each of the four flag-true specimens is rejected with FROB-REF-860 and reason `flag-true`, naming the flag.
- [ ] The flag-removed and flag-as-string specimens are rejected with FROB-REF-860.
- [ ] Every other registered mutation is rejected with its reason token (100% of the specimen set).
- [ ] The auditor's dependency listing shows no dependency outside the standard library with the packet module included.
- [ ] `frob-verify packet` runs on a machine with only the binary and the packet directory.
- [ ] The output names what is not checked offline.
- [ ] The auditor and the in-workspace reader agree on accept or reject for every specimen (a differential test run from the workspace side).

## Test plan

### Unit tests
`cargo test -p frob-cert packet`:
- `accepted_specimen_passes`.
- `flag_true_rejected_860` × 4; `flag_missing_rejected_860`; `flag_string_rejected_860`.
- `byte_flip_in_geometry_rejected`; `byte_flip_in_section_rejected`; `byte_flip_in_cert_rejected`.
- `unlisted_file_rejected`; `missing_file_rejected`.
- `non_canonical_manifest_rejected`; `unknown_schema_rejected`.
- `exploratory_true_rejected`; `null_verdict_rejected`.
- `section_identity_mismatch_rejected`.
- `swapped_certificate_rejected` (consistent hashes, wrong statement).
- `path_traversal_rejected`.
- `mesh_hash_missing_rejected`; `mesh_hash_equal_to_grid_hash_rejected`.
- `identity_is_blake3_of_manifest`.
- `binary_lists_std_only`.
- Differential (in the workspace, `cargo test -p frob-foundry --test verify_differential`): for every specimen, `BuildPacket::open` and `frob-verify packet` give the same verdict.
- Planted defects, each caught: `accept-flag-absent` (treats a missing flag as false), `hash-only-listed-files` (ignores extra files), `verify-links-frob-foundry` (the dependency test fails).

### End-to-end script and logging
`scripts/e2e/foundry_export_packet.sh` (bead N31a-57): copies the built `frob-verify` and a fresh packet into
an empty directory, runs it there with a cleared environment, asserts exit 0; applies the flag mutation and a
byte flip and asserts exit 3 with the reasons; logs the verdict, the reason tokens and the binary's hash.

### Known answers and negative controls
The specimen set is the known-answer set: one accept, the rest reject with named reasons. Negative controls:
the three planted defects. Determinism: outputs are compared byte for byte across platforms.

## Considerations

- Two implementations of the same rules can drift. The differential test is the guard, and a change to the
  packet schema is not complete until both sides and the specimens are updated.
- The auditor rejects an unknown schema version outright. A future `frob.build/2` needs a new auditor build;
  that is the intended coupling for an artifact people may act on.
- The recurring flags gate of the safety chapter re-runs the flag mutations at every milestone exit; this
  bead's specimens are registered there.
- KILL-PACKET fallback: a reduced packet (`profile: Reduced`) is audited by the same rules with fewer files.
