## Background

Firmware export is one of Foundry's two Moonshots: export of fixed-point controller code with overflow checks.
It lives behind the feature `firmware-export` (Cargo name `moonshot-firmware-export`, by workspace rule L-12; the
short name stays at the user surface), nothing depends on it, and the build packet does not depend on
it (ADR-FOUNDRY-12; INV-FOUNDRY-07). It is funded only after its pilot has run and its epic has a short plan.

**Ceiling, stated first: no speed claim.** The benefit is that the controller evaluated in simulation is,
integer for integer, the arithmetic that would be shipped. A controller tuned in floating point and re-typed
by hand into fixed point for a microcontroller is a different controller: its gains are rounded, its
intermediates can overflow, and none of the simulation evidence is about it.

**Scope.** Joint-level controllers and monitors only: a proportional–derivative or proportional–integral
loop, the energy-budget monitor, a shield projection with a few rows. Whole-body controllers and state
estimators in fixed point are out of scope.

**Output.** Source for a `no_std`, heap-free crate that forbids unsafe code and sits behind a caller-owned bus
trait; Q-format declarations; a test-vector manifest; overflow certificates; quantization error bounds; the
flags. **The exporter emits no register access, no bus driver and no stop-circuit code.** The flags sit in a
constant in the generated crate and in its manifest; the code compiles only against hardware interfaces the
caller supplies and never addresses a register, a bus socket or an emergency-stop relay.

A *Q format* Qm.n represents a real number as an integer scaled by 2ⁿ in a word of m + n bits (sign
included); Q15 is the 16-bit format with 15 fraction bits, covering [−1, 1 − 2⁻¹⁵].

Not claimed, ever, by this exporter: execution time, stack depth and behaviour on a board. `timing: no-claim`
until a receipt from a linked binary on real hardware is imported.

## Scope

In: deciding whether a controller is in the exportable set; lowering its kernel-IR program to a fixed-point
program given Q formats; emitting the crate; the bus trait; the denylist lint on generated source; the firmware
manifest; placement in the packet; determinism of generation.
Out: choosing Q formats and proving absence of overflow (N31a-45); quantization bounds, in-loop evaluation and
test vectors (N31a-46); the certificate format and its replay (CARD-T-14); anything that touches hardware.

## Technical approach

1. **Exportable set** (`firmware/scope.rs`). A controller program is exportable when its kernel-IR form uses
   only: fixed-size scalar state; addition, subtraction, multiplication, shifts by constants, comparison,
   select, clamp, and constant tables of bounded size; no loops with data-dependent bounds; no division by a
   non-constant; no transcendental function. The three named families satisfy this: a PD or PI joint loop
   (error, proportional term, derivative or integral state, clamp); the energy-budget monitor (an accumulator
   compared with a budget); a shield projection with at most 8 rows (DESIGN cap for "a few") applied as
   clamps on the command. Anything else is refused as an unsupported capability (the verb layer's
   not-implemented class, exit code 5) under the refusal `firmware-controller-not-exportable`: row 11 of the
   Foundry allocation decision N31b-45 and of N31-REF's Table 3, family `7xx`, decade `72x`, with no interim
   code (`interim = "none"`). The export refuses with exit 5, emits nothing, and carries `detail:
   "firmware-controller-not-exportable"` behind the named constant `FIRMWARE_CONTROLLER_NOT_EXPORTABLE`, the
   one place its number lands when the ledger assigns it (this bead invents no number): the payload names the
   first construct outside the set with its IR name and source position, and lists the three exportable kinds.
2. **Generated crate layout** (`firmware/emit.rs`), under `firmware/<controller>/` in a packet or a chosen
   directory:
   ```
   Cargo.toml            no dependencies; edition and name; no build script
   src/lib.rs            #![no_std] #![forbid(unsafe_code)]; pub const AUTHORIZATION; module declarations
   src/qformat.rs        one constant per signal and intermediate: word bits, fraction bits, range in counts
   src/controller.rs     State, Input, Output as plain integer structs; pub fn step(state, input) -> (State, Output)
   src/bus.rs            pub trait Bus { fn read(&mut self, ch: Channel) -> i32; fn write(&mut self, ch: Channel, v: i32); }
                         pub fn run_once<B: Bus>(state: &mut State, bus: &mut B)
   vectors/manifest.json, vectors/vectors.bin
   certs/*.frobcert
   bounds.json           quantization error bounds
   manifest.json         identities, hashes, flags, `timing: "no-claim"`, the Q-format table
   ```
   `step` is a pure function of integers: explicit wrapping or saturating operations only, exactly as the
   kernel IR's fixed-point semantics define them; no floating-point type appears anywhere in the crate; no
   allocation; no panic path (no slice indexing with computed indices, no integer division by a variable).
   `run_once` is the only place the caller-owned trait is used: it reads inputs through the trait, calls
   `step`, writes outputs through the trait. The implementation of `Bus` is the caller's.
3. **Flags in the crate.**
   `pub const AUTHORIZATION: Authorization = Authorization { execution_authorized: false,
   hardware_safety_signoff: false, sim_to_real_certified: false, fabrication_released: false };` with field
   types that admit only `false`, and the same block in `manifest.json`. The packet reader's rule applies:
   absent or true is FROB-REF-860.
4. **Denylist lint on generated source** (run on every emission over `Cargo.toml` and every file under `src/`;
   a hit is an internal error and nothing is written). The vector harness of N31a-46 is test code that may use
   the standard library; it is generated into a scratch build directory, never into the crate or the packet,
   and is outside the lint's scope. The tokens `unsafe`, `extern`, `asm!`, `core::ptr`, `read_volatile`, `write_volatile`,
   `as *const`, `as *mut`, `static mut`, `f32`, `f64`, `alloc`, `Box`, `Vec`, `panic!`, `unwrap`; any integer
   literal used as an address; any identifier containing `estop`, `relay`, `register`, `socket`.
5. **Firmware manifest** (`frob.foundry.firmware/1`): design and model, the controller's identity and
   kernel-IR hash, the hash of every generated file, the Q-format table, the list of certificates with the
   obligation each discharges, the vector manifest's hash, the quantization bounds, the flags, and the three
   no-claims: `timing`, `stack_depth`, `on_board_behaviour`.
6. **Placement.** `foundry.export --with-firmware` adds `firmware/` to a packet; the directory is optional and
   present only with the feature compiled in. The packet's other sections never reference it, and removing it
   (with its manifest entries) leaves a valid packet: this is the test of INV-FOUNDRY-07.
7. **Order of work inside an export.** Scope check → range analysis and Q formats (N31a-45) → overflow
   obligations (N31a-45) → emission → quantization bounds and vectors (N31a-46) → manifest. A refuted or
   undecided obligation stops before emission: no code is written for a controller that is not certified.
   This bead defines the emitter's input, an obligation table (one row per obligation with
   `status: certified | refuted | undecided` and the certificate or witness), and the emitter refuses to write
   unless every row is certified; N31a-45 produces the table, and N31a-46 closes the order with bounds,
   vectors and the completed manifest. The unit tests here build the table directly.
8. **Determinism.** Generation is a pure function of the IR program, ranges and Q formats: identifiers are
   derived from IR names, items are emitted in IR order, and the output is byte-identical across runs and
   platforms.

## Acceptance criteria

- [ ] A PI joint loop, the energy-budget monitor and a three-row shield projection are accepted by the scope check; a whole-body controller and a state estimator are refused, naming the construct.
- [ ] The generated crate builds for the host and for a `thumbv7em-none-eabi` target with no dependencies, with `#![no_std]` and `#![forbid(unsafe_code)]`.
- [ ] The denylist lint passes on every generated crate and fails on a planted emission containing a volatile write.
- [ ] No floating-point type and no allocation appears in the generated source (checked by the lint and by building without `alloc`).
- [ ] The crate's `AUTHORIZATION` constant and the manifest carry the four flags, all false; a mutated manifest is refused with FROB-REF-860.
- [ ] `manifest.json` lists `timing`, `stack_depth` and `on_board_behaviour` as `no-claim`.
- [ ] A packet written with the emitted `firmware/` directory and the same packet written without it (the container writer, the same inputs otherwise, the obligation table built directly) are both accepted by the reader and `frob-verify`, and their other section files are byte-identical. (Through the binary, as a re-export without `--with-firmware`, this is the `packet independence` stage of N31a-58, which depends on this bead.)
- [ ] A controller with an unrefuted-but-undecided or refuted obligation produces no source files.
- [ ] Two emissions of the same controller are byte-identical.

## Test plan

### Unit tests
`cargo test -p frob-foundry --features moonshot-firmware-export -- firmware::scope firmware::emit`:
- `pi_loop_is_exportable`; `energy_monitor_is_exportable`; `shield_three_rows_is_exportable`; `shield_nine_rows_refused`.
- `whole_body_controller_refused`; `estimator_refused`; `variable_division_refused` (each:
  `firmware-controller-not-exportable`, exit 5, `detail` equal to the named constant's value, no code, the
  construct named; for the division, the divisor's IR name).
- `generated_crate_builds_host_and_thumb` (the thumb build is a check, not a run).
- `denylist_clean`; `denylist_catches_volatile`; `denylist_catches_float`.
- `flags_constant_is_all_false`; `manifest_flags_all_false`.
- `step_is_pure_integer`: the function's signature and body contain only integer types (a syntax-level check).
- `bus_trait_only_in_run_once`.
- `no_claims_listed`.
- `emission_is_deterministic`.
- `nothing_written_when_obligation_open`.
- Planted defects, each caught: `emit-float-gain` (keeps a gain as `f32`), `emit-bus-driver-stub` (generates a default `Bus` implementation with register addresses), `emit-before-certification`.

### End-to-end script and logging
`scripts/e2e/foundry_firmware_emit.sh` (this bead's own, built only on its dependencies; it sources the STD-E2E
helper library; header `bead=N31a-44 milestone=M8 labels=foundry,moonshot seed=0 needs=cpu`). An export through the binary emits code
only once N31a-45 supplies the certified obligation table and N31a-46 closes the manifest, so this script drives
the emitter through an example program with the table built directly, as the unit tests do. Steps: (1) `cargo
test -p frob-foundry --features moonshot-firmware-export -- firmware::scope firmware::emit` through `e2e_cmd`
(including the three planted defects); (2) `cargo run -p frob-foundry --features moonshot-firmware-export
--example firmware_emit -- --controller knee-pi-clamped --obligations all-certified --out <scratch>/a --json`
and the same into `<scratch>/b`: the file set of step 2, `e2e_assert_digest_eq` on every file across the two
directories, the lint result clean, `AUTHORIZATION` and the manifest's flags all false, the three no-claims
present; (3) `cargo build --manifest-path <scratch>/a/knee-pi-clamped/Cargo.toml` for the host and `cargo check
--target thumbv7em-none-eabi` of the same crate, both through the build-offload shim; (4) `--controller
whole-body-controller` and `--controller estimator`: exit 5, `detail: "firmware-controller-not-exportable"`, the
first construct outside the set named, no file written; (5) `--obligations one-undecided`: no source file

`scope` (step 2), `emission` (step 9) and `packet independence` (step 12) of `scripts/e2e/foundry_firmware.sh`

<scratch>/fw-9-1 --with-firmware --controller knee-pi-clamped --key "$(e2e_key fw-9-1)" --json`.

### Known answers and negative controls
Q15 covers [−32768, 32767] counts, that is [−1, 1 − 2⁻¹⁵]. Negative controls: the three planted defects and the
refused controller families. Metamorphic: renaming an IR signal renames the corresponding identifiers and
changes nothing else; the generated `step` is independent of the `Bus` implementation. Determinism: byte
identity across platforms.

## Considerations

- KILL-FIRMWARE (M8): trigger GATE-FOUNDRY-11 fails. Fallback: controller parameters, Q formats and the
  test-vector manifest only; no code. The firmware manifest and `qformat.rs`'s content are designed so that
  the fallback is this bead's output minus `src/`.
- Emitting code that could run on a motor driver is the most safety-relevant thing Foundry does. The design
  keeps the exporter on the far side of every hardware boundary: the caller owns the bus, the stop circuit
  and the schedule, and the flags travel inside the crate.
- A caller could ignore the flags. They are information for people and tools downstream, not a lock; the
  program's commitment is that it never produces an artifact that says otherwise.
- At most four Moonshot items are active at once by program rule; this one is queued at M8.
