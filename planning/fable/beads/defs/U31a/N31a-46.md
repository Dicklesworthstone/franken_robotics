## Background

Absence of overflow says the fixed-point controller computes what its integer program says. Three more checks
connect that program to the controller that was simulated and to the code that was emitted.

**Checks, in order (the last three).**

4. **Quantization.** The difference from the real-valued controller is bounded by interval arithmetic, and its
   closed-loop effect is measured by running the fixed-point controller in the loop in the exact-integer
   kernel class, so the simulated controller computes the same integers on every backend. Class Tested.
5. **Vectors.** 10⁶ vectors agree bit for bit between the exported crate built for the host and the integer
   kernel (TARGET). That is a test, and it is not called equivalence.
6. **Not claimed.** Execution time, stack depth and behaviour on a board. `timing: no-claim` until a receipt
   from a linked binary on real hardware is imported.

The exact-integer kernel class is the simulator's guarantee that an integer program gives the same integers on
the CPU reference and on every device backend (determinism class D0). Running the exported controller's
integer program as such a kernel is what makes the sentence "the controller evaluated in simulation is,
integer for integer, the arithmetic that would be shipped" true rather than hoped for.

Why vectors are "a test, not equivalence": showing that a compiled lowering is equivalent to its source needs
a verified compiler and a model of the target, neither of which exists here; what stands in is an overflow
bound per function and parity tests. A million agreeing vectors is strong evidence and is named for what it
is.

Gate (TARGET): GATE-FOUNDRY-11, Known answer [M], M8: the fixed-point cases of the known-answer table; 10⁶
vectors bit-equal. Kill gate KILL-FIRMWARE: if it fails, the export is controller parameters, Q formats and
the test-vector manifest only; no code.

## Scope

In: the open-loop quantization bound and `bounds.json`; the in-loop run with the integer kernel and its paired
comparison against the real-valued controller; vector generation, the manifest, the host build of the
generated crate and the bit comparison; the no-claims; the fallback output; closing the export order of N31a-44
step 7 (bounds and vectors after emission, the firmware manifest completed last with their hashes).
Out: overflow certificates (N31a-45); code emission (N31a-44); anything on real hardware (an import lane).

## Technical approach

1. **Open-loop quantization bound** (`firmware/quant.rs`). Sources of difference between the fixed-point step
   and the real-valued step, each an interval: input quantization (±½ unit in the last place of the input
   format); gain rounding (|K_q − K| ≤ ½ unit in the last place of the gain format; computed exactly since
   gains are rationals); truncation after each product shift ([−1 unit, 0] for truncation, ±½ for rounding,
   as the IR operation says); saturation (zero inside the certified range). Propagating these through the
   step by interval arithmetic gives, per output, a bound ε_out on |y_fixed − y_real| for one step from equal
   states, and per state variable a bound ε_state on the state difference added in one step.
   For a stateful controller the one-step bound does not bound the difference over time (an integrator
   accumulates it); `bounds.json` therefore reports the one-step bounds and the bound over a declared horizon
   of N steps (N·ε_state for a pure integrator; the geometric sum for a leaky one), and says that the
   closed-loop effect is measured, not bounded.
2. **In-loop evaluation.** The lowered integer program is registered as an exact-integer kernel and used as
   the joint controller in rollouts of the qualified task set at the campaign's world addresses, on the CPU
   reference and, where available, on a device backend. Two things are recorded:
   - *integer identity across backends*: the per-tick controller outputs (as integers) have equal digests on
     every backend run;
   - *closed-loop effect*: a paired comparison, on the same addresses, between the real-valued controller and
     the fixed-point one: difference in task success and in the tracking metric, with its interval. Class
     Tested. A difference whose interval excludes zero by more than the task's practical-equivalence margin is
     a finding with the repair "more fraction bits at the named signal" (the signal with the largest
     contribution to ε_out).
3. **Vectors** (`firmware/vectors.rs`). 10⁶ steps in total, generated from a registered stream so that the
   set is a function of (seed, controller identity):
   - 50% inputs uniform over the declared ranges, as short sequences so that state evolves;
   - 25% boundary sequences: range ends, zero, ±1 count, sign changes, the certified invariant's ends;
   - 25% replayed sequences from the in-loop rollouts (real duty).
   Each record: input counts, state before, expected state after and output counts from the integer kernel.
   `vectors/manifest.json`: schema, seed, counts by category, record layout, BLAKE3 of `vectors.bin`, the
   kernel-IR hash and Q-format table hash. Counterexamples found during certification are included as extra
   vectors with their category.
4. **Host build and comparison.** The generated crate is built for the host with the pinned toolchain in a
   scratch directory (it has no dependencies); a generated test harness (standard library allowed, because it
   is test code; written beside the crate in the scratch directory, never into the crate's `src/` or the
   packet, so the denylist lint of N31a-44 does not see it) reads `vectors.bin`, calls `step`, and compares
   state and output with the expected values. Pass:
   10⁶ of 10⁶ bit-equal. The first mismatch, if any, is reported with its record index, inputs, both outputs
   and the IR operation at which a step-by-step trace first differs.
5. **No-claims.** The firmware manifest states `timing: no-claim`, `stack_depth: no-claim`,
   `on_board_behaviour: no-claim`. An imported receipt from a linked binary on real hardware would be a
   sidecar record; nothing in this program produces one.
6. **Fallback output (KILL-FIRMWARE).** With the kill switch set, or on request (`--firmware params-only`),
   the export writes the controller parameters as exact rationals, the Q-format table and the vector manifest
   with its vectors, and no `src/`. The manifest says `code: withheld (KILL-FIRMWARE)`.
7. **Gate receipt fields.** The three fixed-point cases' outcomes (from N31a-45), the vector count and
   mismatches, the cross-backend digest equality, the paired closed-loop difference, the toolchain identity of
   the host build. They enter the receipt of N31a-58's script, the one bead the gate register names for
   GATE-FOUNDRY-11, from which the value is recorded with `record_gate` (N38b-19); this bead records no gate
   value itself.

## Test plan

### Unit tests
`cargo test -p frob-foundry --features moonshot-firmware-export -- firmware::quant firmware::vectors`:
- `gain_rounding_error`: K = 3/10 in Q15: 0.3 × 32768 = 9830.4 → 9830 counts = 0.29998779; error 1.22 × 10⁻⁵, at most half a unit (1.53 × 10⁻⁵).
- `proportional_term_bound`: |e| ≤ 1, truncating product: |Δ| ≤ 1.22 × 10⁻⁵ + 2⁻¹⁵ = 4.27 × 10⁻⁵.
- `integrator_horizon_bound_is_linear`: ε_state per step times N.
- `observed_difference_within_bound` on 10⁵ random steps.
- `vector_mix_is_50_25_25`; `vectors_reproducible_from_seed`; `manifest_hash_matches_file`.
- `boundary_vectors_include_range_ends_and_invariant_ends`.
- `host_build_harness_bit_equal_small` (10⁴ vectors in the unit lane; the full 10⁶ in the gate lane).
- `planted_shift_miscompile_caught_and_localized`.
- `integer_kernel_digest_equal_across_backends` (CPU reference twice; device lanes where present).
- `params_only_has_no_src`.
- `export_order_end_to_end` (the stages in order on the clamped PI loop; manifest hashes equal the files); `harness_outside_crate_and_packet`.
- `no_timing_field_in_schema`.
- Planted defects, each caught: `compare-in-floating-point` (the harness converts outputs to real numbers and compares within a tolerance), `vectors-from-the-emitted-code` (expected values produced by the exported crate itself, so nothing can mismatch), `uniform-only-vectors` (no boundary category; the miscompile at the range end is missed).

### Known answers and negative controls
The gain-rounding and proportional-term bounds above; KA-749's cases through bead N31a-45. Negative controls:
the three planted defects and the planted miscompilation. Metamorphic: permuting the order of vectors changes
no result for stateless records and is forbidden inside a sequence; scaling a gain and inversely scaling its
input format leaves outputs unchanged in counts. Determinism: the vector file and the comparison are D0; the
in-loop integers are D0 across backends by the kernel class.

## Considerations

- A million vectors over three or four inputs is sparse coverage of the input space; the boundary category
  and the certificates carry the corner cases, and the wording "a test, not equivalence" is binding on every
  report.
- The host build uses the host's compiler; a cross-compiler for a microcontroller can differ. The manifest
  records the toolchain, and behaviour on a board stays `no-claim`.
- If the paired in-loop comparison shows a practical difference, the finding is about fraction bits, not
  about overflow; widening a format changes the certificates, which must be re-issued.
- This bead closes the Moonshot's gate; the epic's exit also needs the pilot and the kill-gate decision on
  record.
