## Background

Everything Foundry does is reached through verbs: named operations in the program's verb registry, from which
the command line, the daemon protocol, the MCP tool definitions, the schemas and the refusal table are
generated, so that the surfaces cannot drift. A capability counts as implemented only when it is reachable
through `frob --json` with a documented schema and exit code, and, where the registry exposes it to agents,
through the MCP server.

The Foundry cluster:

| Verb | Kind | First milestone | Does |
|---|---|---|---|
| `foundry.loads` | run | M4 | Runs or reads a load campaign; returns envelope cases, spectra and the free-body residual |
| `foundry.size` | read | M4 | Beam-rung sizing and the structural margin of analysis A-15 |
| `foundry.optimize` | run | M5 | Topology optimization of link classes with the loads–mass loop |
| `foundry.check` | run | M5 | Independent stress, buckling, modal, fatigue and manufacturability check of a geometry |
| `foundry.tolerance` | read | M5 | Sensitivity-driven allocation, stacks and the band-extreme check |
| `foundry.export` | run | M5 | Writes geometry and the build packet; `--with-firmware` under its feature |
| `foundry.lifecycle` | run | M8 | A lifecycle run under feature `lifecycle` |

**Seven verbs, the limit for a cluster. Long verbs take the bounded synchronous wait and otherwise return a
job handle.** Kinds: `read` returns stored or cheaply computed facts and changes nothing; `run` spends
compute, takes an idempotency key and a budget, accepts the bounded synchronous wait (`sync_wait_ms`) and
otherwise returns a job handle with exit code 8. (`foundry.loads` and `foundry.size` are dated M4 in the
registry; the subsystem and its gates land at M5, and the two verbs may ship as soon as their beads pass.
`foundry.lifecycle` is dated M8 in the registry while its work and gate are placed at M6.)

Each verb's behaviour is specified by the bead that implements it. This bead is the cluster's surface: one
consistent set of registry entries, schemas, examples and refusal lists, with the cross-cutting behaviour
(waiting, jobs, idempotency, cancellation, envelope evidence) tested once for all seven.

## Scope

In: the seven registry entries; input and output schema names and their top-level shape; the refusal list per
verb; examples; the wait and job behaviour; envelope evidence and flags; capability scopes; CLI and MCP
parity; the cluster's documentation page for agents.
Out: the mechanisms (the beads named in the table below); registration machinery (BD-409, BD-022); additions
by unit U31b to three verbs, which extend these entries.

## Technical approach

1. **Registry entries** (`registries/verbs.toml`, cluster `foundry`; schema names DESIGN):

   | Verb | Kind | Input / output schema | Capability | Implemented by |
   |---|---|---|---|---|
   | `foundry.loads` | run | `frob.foundry.loads.in/1` / `.out/1` | `foundry:run` | BD-400 with N31a-06 to N31a-13 |
   | `foundry.size` | read | `frob.foundry.size.in/1` / `.out/1` | `foundry:read` | BD-401 |
   | `foundry.optimize` | run | `frob.foundry.optimize.in/1` / `.out/1` | `foundry:run` | BD-403, BD-404 with N31a-05, N31a-14 to N31a-17, N31a-23 to N31a-25 |
   | `foundry.check` | run | `frob.foundry.check.in/1` / `.out/1` | `foundry:run` | BD-402, BD-405 with N31a-19 to N31a-22, N31a-26 to N31a-28 |

   | `foundry.export` | run | `frob.foundry.export.in/1` / `.out/1` | `foundry:export` | BD-407, BD-408 with N31a-34 to N31a-43; firmware N31a-44 to N31a-46 |
   | `foundry.lifecycle` | run | `frob.foundry.lifecycle.in/1` / `.out/1` | `foundry:run` | BD-423 with N31a-47 to N31a-50 |
2. **Refusal lists.** The chapter's verb table prints refusal numbers that the refusal registry assigns to
   other chapters (160, 161, 162 and 861 to 864: no shape class, group not observation-preserving, reuse
   without a dependency digest, and four numerics refusals). Read by position against the chapter's own
   refusal table they are the Foundry codes 166, 167, 169 and 818, 824, 827, 831. The registry governs, and
   the entries are written with the Foundry codes:

   | Verb | Refusals in the registry entry |
   |---|---|
   | `foundry.loads` | FROB-REF-167, -169, -262 |
   | `foundry.size` | FROB-REF-163 (and -167 for a load file that is not one instant) |
   | `foundry.optimize` | FROB-REF-166, -164, -260, -261 (and -167, -169, -262 from the campaigns it runs) |
   | `foundry.check` | FROB-REF-163, -261 (and -860 when the argument is a packet) |
   | `foundry.tolerance` | FROB-REF-165 |
   | `foundry.export` | FROB-REF-166, -860, -818, -824, -261; with `--with-firmware` also -827 |
   | `foundry.lifecycle` | FROB-REF-831 (and -169 for incomplete window traces) |
   All of these exit with code 3. Every verb can also return the feature- or group-absent refusal (exit 5)
   and the protocol refusals of the verb layer.
3. **Common envelope rules.** Exit codes: 0 completed; 2 completed with findings (a utilization above 1 on a
   hand-built part, manufacturability findings, features on worst-case boxes); 3 refusal; 4 budget; 5 not
   available; 7 conflict (an existing packet name with different content); 8 accepted and still running.
   `evidence`: class Estimated for every Foundry result (Certified only for the firmware instance
   certificates listed inside an export's result), tier and determinism from the inputs, `claims` empty
   except where a gate fixture is run, `reality: no-claim`, conditions carrying `exploratory`,
   `model-conditional`, `check: same-family`, `loads: declared`, `provisional`. `authorization`: the three
   flags, all false, on `foundry.export` (the packet adds its fourth inside the artifact). `bound`: the
   design, model, campaign and card identities every name resolved to. `next_actions`: the next verb of the
   loop with its exact command.
4. **Waiting and jobs.** The five `run` verbs accept `sync_wait_ms`. If the work finishes inside the wait the
   envelope is the result; otherwise the envelope carries a job handle (`id`, `state`, `progress` with a
   denominator in stages or link classes, `eta_s` with interval, `poll_after_ms`, `last_committed`) and exits
   8; `job.wait` continues. Progress units: `foundry.loads`: episodes; `foundry.optimize`: loop stages out of
   iterations × 8; `foundry.check`: cases; `foundry.export`: files; `foundry.lifecycle`: macro steps (with
   the horizon fraction reached).
5. **Idempotency and cost.** `run` verbs require an idempotency key; a repeat with the same key and content
   returns the stored envelope with `idempotent_replay: true`; the same key with different content is a
   conflict (exit 7). Before admission each `run` verb returns a cost estimate (CPU core-seconds, storage)
   from the size of the campaign, the number of link classes and the resolutions; a request over budget is
   refused at admission (exit 4) with nothing partial published.
6. **Cancellation.** `job.cancel` on any Foundry job drains at the documented boundary of that verb (kernel
   batch for campaigns; stage or sibling-job boundary for the loop and the checks; file boundary for export,
   where the atomic writer guarantees no packet) and acknowledges with the last committed unit.
7. **Surfaces.** CLI: `frob foundry <verb> …` with `--json`. MCP: `foundry_size`, `foundry_optimize`,
   `foundry_check`, `foundry_tolerance` and `foundry_export` in the `make` profile; `foundry_loads` and
   `foundry_lifecycle` are registered tools outside that profile. Both surfaces return the same envelope
   (the parity gate of the verb layer covers them). Each verb has two worked examples in the generated
   documentation: one success and one refusal with its repair.
8. **The seven-verb limit.** A test counts the cluster's verbs and fails above seven; additions arrive as
   flags or modes of these verbs (as unit U31b's three additions do).

## Acceptance criteria

- [ ] `registries/verbs.toml` has exactly seven `foundry.*` entries with kind, schemas, capability and the refusal lists above; the registry check passes.
- [ ] No Foundry entry lists a refusal code that the refusal registry assigns to another chapter's meaning (a test compares each listed code's registry row with the meaning used here).
- [ ] Every verb is reachable through `frob --json` and returns one envelope; the five `make`-profile tools are served by the MCP server with the same schemas.
- [ ] Each `run` verb honours `sync_wait_ms`: with a wait shorter than the work it exits 8 with a job handle whose progress has a denominator; `job.wait` then returns the same result as a long wait.
- [ ] A repeat with the same idempotency key returns the stored envelope and performs no work; the same key with other content exits 7.
- [ ] Cancellation of each `run` verb leaves no partial result: no stage record, no new design, no packet.
- [ ] Every Foundry envelope has class Estimated (or the stated exception), `reality: no-claim`, and the conditions present in its inputs.
- [ ] Each verb has a success example and a refusal example in the generated documentation, and both run as tests.
- [ ] The cluster-size test fails when an eighth verb is added.

## Test plan

### Unit tests
`cargo test -p frob-foundry verbs` and the registry tests of the verb crate:
- `cluster_has_seven_verbs`.
- `registry_entries_match_table` (kind, schema names, capabilities).
- `refusal_lists_use_foundry_codes`: for each listed code the registry row's "defined in" is the Foundry refusal table.
- `stale_numbers_absent`: none of 160, 161, 162, 861, 862, 863, 864 appears in a Foundry entry.
- `envelope_evidence_estimated` for each verb on a fixture.
- `conditions_propagate_to_envelope` (`exploratory`, `model-conditional`).
- `sync_wait_then_job_handle` × 5; `progress_has_denominator` × 5.
- `idempotent_replay` × 5; `key_conflict_exit_7`.
- `cancel_leaves_nothing` × 5 (one per `run` verb, at its boundary).
- `examples_execute` (14 examples).
- `mcp_and_cli_envelopes_equal` for the five profile tools.
- Planted defects, each caught: `eighth-verb`, `read-verb-that-writes` (a `read` verb creating a ledger row), `job-progress-without-total`.

### End-to-end script and logging
The seven scripts of the cluster (`foundry_loads.sh`, `foundry_size.sh` of BD-401, `foundry_structure_loop.sh`,
`foundry_check.sh`, `foundry_tolerance.sh`, `foundry_export_packet.sh`, `foundry_lifecycle.sh`) each begin with
a common preamble from this bead: `frob verbs list --cluster foundry --json` asserting the seven entries, and
for the verb under test one call with `sync_wait_ms=1` asserting exit 8 and a job handle; the preamble's lines
are logged with the registry hash.

### Known answers and negative controls
The mapping of the seven stale numbers to the seven Foundry codes is fixed here and tested. Negative controls:
the three planted defects. Determinism: registry generation is deterministic; envelopes for fixtures are
compared across two runs.

## Considerations

- The stale refusal numbers in the chapter's verb table are a transcription artefact of an earlier numbering;
  following them literally would make `foundry.export` raise numerics refusals. The mapping is recorded in
  this unit's coverage notes for the reviewer.
- `foundry.size` is called by preflight at an earlier milestone than the rest of the cluster; its registry
  entry must therefore exist as soon as the beam rung does, even while the other six are absent, and the
  cluster-size test is an upper bound, not an equality, until M5.
- Capability scopes separate reading results from spending compute and from writing artifacts; an agent
  session without `foundry:export` can analyse and cannot write a packet.
- Long verbs must never leave an agent guessing: a transport failure during a job is recovered by the
  idempotency key through `job.find`, never by resubmission.
