## Background

Everything Foundry does is reached through verbs: named operations in the program's verb registry, from which
the command line, the daemon protocol, the MCP tool definitions, the schemas and the refusal table are
generated, so that the surfaces cannot drift. A capability counts as implemented only when it is reachable
through `frob --json` with a documented schema and exit code, and, where the registry exposes it to agents,
through the MCP server.

The Foundry cluster:

| Verb | Kind | First milestone | Does |
|---|---|---|---|
| `foundry.loads` | run | M4 | Runs or reads a load campaign; returns envelope cases, spectra and the free-body residual |
| `foundry.size` | read | M4 | Beam-rung sizing and the structural margin of analysis A-15 |
| `foundry.optimize` | run | M5 | Topology optimization of link classes with the loads–mass loop |
| `foundry.check` | run | M5 | Independent stress, buckling, modal, fatigue and manufacturability check of a geometry |
| `foundry.tolerance` | read | M5 | Sensitivity-driven allocation, stacks and the band-extreme check |
| `foundry.export` | run | M5 | Writes geometry and the build packet; `--with-firmware` under its feature |
| `foundry.lifecycle` | run | M8 | A lifecycle run under feature `lifecycle` |

**Seven verbs, the limit for a cluster. Long verbs take the bounded synchronous wait and otherwise return a
job handle.** Kinds: `read` returns stored or cheaply computed facts and changes nothing; `run` spends
compute, takes an idempotency key and a budget, accepts the bounded synchronous wait (`sync_wait_ms`) and
otherwise returns a job handle with exit code 8. (`foundry.loads` and `foundry.size` are dated M4 in the
registry; the subsystem and its gates land at M5, and the two verbs may ship as soon as their beads pass.
`foundry.lifecycle` is dated M8 in the registry while its work and gate are placed at M6.)

Each verb's behaviour is specified by the bead that implements it. This bead is the cluster's surface
contract: one consistent set of repeated rows, schema shapes, examples and refusal lists, the cross-cutting
behaviour every handler must show (waiting, jobs, idempotency, cancellation, envelope evidence) stated once
for all seven, and the two things every cluster script needs before a handler exists: the named-fixture input
and the script preamble.

Why the contract and its tests are two beads. The handlers are built by the capstone beads BD-400 to BD-408,
and those depend on this bead (for the rows' contract, the named fixtures and the preamble). A test that
drives the common behaviour through the real handlers can therefore not be part of this bead: it would wait
on beads that wait on it. Those tests are bead N31ap3-51, split from this one in polishing round 3, as the
refusal battery N31ap1-51 was split from the payload types N31a-52. This bead closes on what exists before
the handlers; N31ap3-51 closes on the handlers.

## Scope

The seven rows of the cluster are entered once, by the registry bead VERBS-foundry (M4, a dependency of this
bead): name, kind, first milestone, tier, purpose, capabilities, schema names, task clusters, registry example,
the refusal list, `needs_groups` and the wait field of every row, with the parity check of the served surfaces,
the help-schema snapshots, the cluster's conformance script and the not-implemented answer a verb gives before
its milestone. This bead does not enter a row a second time. Where the two beads first disagreed (the refusal
lists of five verbs, the scope of `foundry.export`, the evidence class), they were reconciled and both now
state the same values; a later change to a row is made in the registry and repeated here.

In (this bead, at M5, before the handlers): the repeated rows and the tests that hold them equal to the
registry; the reasons for the refusal codes added to the plan's lists; the top-level shape of each input and
output schema as the implementing beads fix it; the contract of the behaviour common to the cluster, which
every handler implements: exit codes, the envelope's evidence, conditions, flags, `bound` and `next_actions`,
the bounded wait and the job handle with a progress denominator per verb, idempotent replay, the cost
estimate and admission, cancellation at each verb's boundary; the named-fixture input `--fixture` with its
index and resolver; two worked examples per verb as text in the generated documentation; the common preamble
of the cluster's end-to-end scripts; the cluster's documentation page for agents; this bead's own script on
what exists before a handler does.
Out: the mechanisms (the beads named in the table below); the registry rows and their checks (VERBS-foundry);
the registry skeleton and envelope (BD-022); the tests of the common behaviour through the real handlers
(wait and job handle, replay, cancellation, evidence, the execution of the worked examples, CLI and MCP
envelope equality on real results, the FROB-REF-790 answers of a build without the `structure` group), which
are N31ap3-51, after the capstones, with `foundry.lifecycle`'s share run in its feature lane by N31a-59; the
completeness check of the whole M5 verb set (BD-409, a capstone that depends on this bead and on the build
packet, so it is not a dependency here); additions by unit U31b to three verbs, which extend these entries.

3. **Common envelope rules** (steps 3 to 6 are the contract each handler implements; this bead publishes it
   and N31ap3-51 tests it through the handlers). Exit codes: 0 completed; 2 completed with findings (a
   utilization above 1 on a hand-built part, manufacturability findings, features on worst-case boxes); 3
   refusal; 4 budget; 5 not available; 7 conflict (an existing packet name with different content); 8
   accepted and still running.
   `evidence`: class Estimated for every Foundry result (Certified only for the firmware instance
   certificates listed inside an export's result), tier and determinism from the inputs, `claims` empty
   except where a gate fixture is run, `reality: no-claim`, conditions carrying `exploratory`,
   `model-conditional`, `check: same-family`, `loads: declared`, `provisional`. `authorization`: the three
   flags, all false, on `foundry.export` (the packet adds its fourth inside the artifact). `bound`: the
   design, model, campaign and card identities every name resolved to. `next_actions`: the next verb of the
   loop with its exact command.
4. **Waiting and jobs.** The five `run` verbs accept `sync_wait_ms`. If the work finishes inside the wait the
   envelope is the result; otherwise the envelope carries a job handle (`id`, `state`, `progress` with a
   denominator in stages or link classes, `eta_s` with interval, `poll_after_ms`, `last_committed`) and exits
   8; `job.wait` continues. Progress units: `foundry.loads`: episodes; `foundry.optimize`: loop stages out of
   iterations × 8; `foundry.check`: cases; `foundry.export`: files; `foundry.lifecycle`: macro steps (with
   the horizon fraction reached). The two `read` verbs create no job and write nothing.
5. **Idempotency and cost.** `run` verbs require an idempotency key; a repeat with the same key and content
   returns the stored envelope with `idempotent_replay: true`; the same key with different content is a
   conflict (exit 7). Before admission each `run` verb returns a cost estimate (CPU core-seconds, storage)
   from the size of the campaign, the number of link classes and the resolutions; a request over budget is
   refused at admission (exit 4) with nothing partial published.
6. **Cancellation.** `job.cancel` on any Foundry job drains at the documented boundary of that verb (kernel
   batch for campaigns; stage or sibling-job boundary for the loop and the checks; file boundary for export,
   where the atomic writer guarantees no packet; macro step for the lifecycle run) and acknowledges with the
   last committed unit. The table of progress units and boundaries is a constant of `frob-foundry`
   (in `verbs.rs`, the surface module of N31a-01's map; DESIGN: `CLUSTER_CONTRACT`, one entry per verb) that handlers read and the
   documentation page prints, so the page, the handlers and the tests of N31ap3-51 cannot state three tables.
7. **Surfaces.** CLI: `frob foundry <verb> …` with `--json`. MCP: every row is a tool, in the task clusters
   its row names (NJL-05): `foundry_size`, `foundry_optimize`, `foundry_check`, `foundry_tolerance` and
   `foundry_export` in `make`; `foundry_loads` and `foundry_lifecycle`, with `foundry_size`, `foundry_check`
   and `foundry_tolerance`, in `structure`. Both surfaces return the same envelope (the parity gate of the
   verb layer covers them). Each verb has two worked examples in the generated documentation: one success and
   one refusal with its repair, each naming the fixture it runs on; they are entered here as text and
   executed as tests by N31ap3-51.
   *Named fixtures* (DESIGN): every verb of the cluster accepts `--fixture <name>` in place of its positional
   argument (design, geometry or packet). The name resolves through the fixture index shipped with the
   conformance fixtures (`crates/frob-foundry/tests/fixtures/index.toml`: name, kind of positional it stands
   for, content hash, label `synthetic`; a mechanism bead adds the entries of its own fixtures), by the
   resolver `resolve_fixture` in `verbs.rs`, which runs in the verb layer's argument step before any handler, so the
   cluster scripts run against the released binary with no path guessing; an unknown name is the verb layer's
   unknown-argument refusal (FROB-REF-802), and a fixture and a positional together are refused the same way.
   The envelope's `bound` block names the fixture and its hash. Every row of VERBS-foundry lists the option,
   naming this bead.
8. **The seven-verb limit.** A test counts the cluster's verbs and fails above seven; additions arrive as
   flags or modes of these verbs (as unit U31b's three additions do).
9. **The script preamble** (`scripts/e2e/lib/foundry_preamble.sh`, a library under the rule of STD-E2E).
   `foundry_preamble <verb> -- <a call of that verb>`: (a) `frob capabilities --json`, asserting that the
   entries whose verb begins `foundry.` are exactly the seven of the table with their kinds, logged with the
   registry digest; (b) for a `run` verb, the given call with `sync_wait_ms=1`, asserting exit 8 and a job
   handle whose `progress` has a denominator, then `frob job wait`; for a `read` verb, that the call returns
   within the call and creates no job; (c) once per script, that a `run` call without a key is refused with
   FROB-REF-805 and that a repeat under the same key returns `idempotent_replay: true`.
   `foundry_key <label>` is the name the cluster's scripts use for the harness's key helper: it prints
   `e2e_key <label>` (STD-E2E: `e2e-<script>-<label>`, no run identifier and no time; a label is issued once
   per run, and `--again` is passed through for a deliberate replay). DESIGN correction: an earlier form
   derived the key from script, step and a digest of the call's inputs so that a re-run would replay stored
   envelopes; the harness gives every run its own state root, rejects a key derived by a helper from step
   data, and requires keys written with `e2e_key`, so the cluster helper is that function under the
   cluster's name and nothing more. Two runs a step compares use two labels.

## Acceptance criteria

- [ ] `registries/verbs.toml` has exactly seven `foundry.*` entries, as VERBS-foundry entered them, with the kind, schemas, capabilities, refusal lists and `needs_groups` of the tables above; the registry check passes, and a difference between a table of this bead and the registry fails a test naming the verb and the field.
- [ ] No Foundry entry lists a refusal code that the refusal registry assigns to another chapter's meaning (a test compares each listed code's registry row with the meaning used here).
- [ ] Every verb is reachable through `frob --json` and as the MCP tool of its row, and returns one envelope: before its handler lands, FROB-REF-724 with exit 5 on both surfaces.
- [ ] `--fixture <name>` is in the help schema of all seven verbs; a name resolves through the index to its kind, content hash and the label `synthetic`; an unknown name, and a fixture given with a positional, are refused with FROB-REF-802 before any handler runs.
- [ ] The preamble library exists with `foundry_preamble` and `foundry_key`; `foundry_key <label>` equals `e2e_key <label>` and a label issued twice in one run without `--again` is the harness error.
- [ ] `CLUSTER_CONTRACT` has a progress unit and a cancellation boundary for each of the five `run` verbs and neither for the two `read` verbs, and the cluster's documentation page prints the same table with the exit codes of step 3.
- [ ] Each verb has a success example and a refusal example in the generated documentation, each naming an index fixture; all fourteen parse against the generated CLI (their execution is N31ap3-51's).
- [ ] The cluster-size test fails when an eighth verb is added.

### End-to-end script and logging
`scripts/e2e/foundry_cluster_surface.sh` (this bead's own; header `bead=N31a-51 milestone=M5
labels=foundry,tether,verb:foundry.* gates= seed=1 needs=cpu,mcp`; sources the STD-E2E helper and the preamble
library; it needs no handler): (1) `frob capabilities --json`: the seven `foundry.*` entries with kind and
first milestone; (2) `frob schema --verbs --json`: each row's chapter codes equal the sorted lists of step 2,
and 790 is among the appended codes of exactly `foundry.check`, `foundry.tolerance`, `foundry.size` and
`foundry.optimize`; (3) per verb `frob foundry <verb> --help --json` lists `--fixture`; (4) per verb
`e2e_expect_refusal FROB-REF-802 3 -- frob foundry <verb> --fixture no-such-fixture --json` (with
`--key "$(foundry_key unknown-<verb>)"` on the `run` verbs) and the same for a fixture given with a
positional; (5) `foundry_key a` twice in a scratch run without `--again` exits 2, and with it prints the same
key; (6) the self-test of the preamble's assertion (a): against a scratch registry with an eighth `foundry.*`
row the listing check fails. NDJSON to `target/e2e-logs/foundry_cluster_surface/<utc-timestamp>.ndjson` with
a transcript: every line `ts`, `script`, `bead` (`N31a-51`), `step`, `event`, the exact command line, exit
code, wall time and the envelope's `evidence` block; per verb the expected and observed refusal lists and
the first differing code; the registry digest; refusals with code and first repair; on failure the first
differing verb and field with the path of the saved schema output; a `summary` line with assertions passed

## Considerations

- The stale refusal numbers in the chapter's verb table are a transcription artefact of an earlier numbering;
  following them literally would make `foundry.export` raise numerics refusals. The mapping is recorded in
  this unit's coverage notes for the reviewer.
- `foundry.size` is called by preflight at an earlier milestone than the rest of the cluster. The registry
  bead enters all seven rows when the cluster is first registered (M4); a verb whose bead has not landed
  answers the not-implemented refusal (`FROB-REF-724`, exit 5). So the cluster-size test is an equality from
  M4 on, and what varies until M5 is which verbs are implemented, not which rows exist. (This bead's first
  draft expected the other six rows to be absent until M5; the registry's rule governs.) The M3 preflight
  check calls the sizing kernel as a library routine and needs no registry row.
- Capability scopes separate reading results from spending compute and from writing artifacts; an agent
  session without `export:packet` can analyse and cannot write a packet.
- Long verbs must never leave an agent guessing: a transport failure during a job is recovered by the
  idempotency key through `job.find`, never by resubmission.
- A contract with no test would be a table nobody checks. The split keeps the check, one bead later: no
  handler closes without the preamble's assertions in its own script, and N31ap3-51 runs the whole contract
  on all six M5 handlers at once, which BD-409 then cites.
