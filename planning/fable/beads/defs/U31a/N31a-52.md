## Background

In this program a refusal is a result with a type: when a verb cannot honestly answer, it says why in a code,
points at the field or part at fault, states what was observed and what was required, and offers ranked
repairs an agent can act on. A numerical refusal, a budget stop and a physical failure of the robot are three
different outcomes; the first two are refusals and the third is a result with findings.

Foundry defines fourteen refusal codes:

| Code | Refused | Repair offered |
|---|---|---|
| FROB-REF-166 | Optimization or packet export for a design with no qualification verdict | Qualify, or run with `--exploratory` (labelled; cannot enter a packet) |
| FROB-REF-167 | A load case that is not one instant, or a campaign failing the free-body check | The offending samples and residuals |
| FROB-REF-169 | Telemetry without the traces or samples a load metric needs | The telemetry level and worlds required |
| FROB-REF-163 | A check whose material card lacks the field or provenance it needs | The missing field; `fatigue: no-claim` |
| FROB-REF-164 | An empty design region, or ports with no load path inside the envelope | The blocking keep-outs |
| FROB-REF-165 | An allocation with a zero or unknown sensitivity, or a failed band-extreme check | Worst-case boxes for the named features |
| FROB-REF-260 | A loads–mass loop that diverges, cycles or exceeds its iteration budget | λ̂, the last iterates, and the beam rung |
| FROB-REF-261 | An optimized part that fails the independent check | The governing case and location; tighter cap or length scale |
| FROB-REF-262 | Quasi-static superposition where the frequency separation fails | Enable the transient path for impact windows |
| FROB-REF-860 | An export without the flags, or any attempt to produce a true flag | None |
| FROB-REF-818 | A priced parts list without a pinned, licensed catalogue | Omit prices |
| FROB-REF-824 | A STEP export above its bounds or failing bit-exact replay | Decimate under a stated tolerance |
| FROB-REF-827 | A fixed-point obligation refuted or undecided within budget | The counterexample input, or a wider format |
| FROB-REF-831 | A lifecycle law outside its validity domain, or cited above class Estimated | The domain and the card needed |

The mechanism beads decide *when* each is raised. This bead makes them uniform: one Rust type per code with
its payload, one place that renders them into the envelope, and one battery that proves every code can be
reached through the real verbs and carries what its row promises. A refusal that exists in a table and that
no test can trigger is not a refusal the system has.

## Scope

In: `refusal.rs` with fourteen payload types and their rendering; the repair objects with exact commands; the
exit code and `retry` value per code; the `affected_claims` rule; the battery; the checks that a refusal is
never downgraded.
Out: the triggering logic (the mechanism beads); the registry rows themselves and the counterexample registry
(unit U31b's registry beads).

## Technical approach

1. **Payload types** (`refusal.rs`, DESIGN). One struct per code; each converts into the envelope's `refusal`
   object. All fourteen exit with code 3 (refused input or question).

   | Code | `pointer` | `observed` / `required` | `retry` | Ranked repairs (each with an exact command where one exists) |
   |---|---|---|---|---|
   | 166 | the design | verdict status (none, failed, other model) / a passed verdict for this design and model | after-change | 1 `eval qualify`; 2 `--exploratory` (not for packets); 3 export the pre-optimization design |
   | 167 | the link, or the case in a load file | residual share and worst samples, or per-component source ticks / one instant; dropped share at most 0.1% | after-change | 1 the offending samples with residuals; 2 declare a contact port (off-port contacts); 3 fix the frame or sign named by the median residual wrench |
   | 169 | the channel and worlds | telemetry level found, missing intervals / T2 on every world with the listed channels | after-change | 1 re-run the named worlds at T2 with the named channels; 2 read the missing limbs' traces (symmetric classes) |
   | 163 | the card field path | provenance found / the field with a source; for fatigue a curve valid for state, process, finish, orientation | after-change | 1 add the field; 2 a card that has it; 3 accept `fatigue: no-claim` (drop `--require fatigue`) |
   | 164 | the link class | region volume, component count / one connected region containing every port boss | after-change | 1 shrink or move the named obstacle by the stated amount; 2 narrow the named joint range; 3 enlarge the keep-in |
   | 165 | the feature and quantity | sensitivity (zero, unknown) or band-extreme discrepancy / a non-zero known sensitivity or a passing check | after-change | 1 worst-case boxes for the named features; 2 more episodes for the sensitivity estimate; 3 a wider margin or another process |
   | 260 | the governing link class and component | λ̂ history, last three iterates, reason (`diverged`, `cycling`, `budget-exhausted`) / contraction within five iterations | after-change | 1 the beam rung's section for the governing class; 2 fix the heavier of two cycling sizes; 3 reduce the governing load |
   | 261 | the part, location and case | utilization, buckling factor, first frequency or fatigue utilization with the limit / within limits on the independent mesh | after-change | 1 stress cap × 0.95/u*; 2 a larger minimum length scale; 3 the fillet radius for a singular corner |
   | 262 | the link class | f₁, f₉₉, their ratio / a ratio of at least 5 | after-change | 1 `--transient impact-windows`; 2 stiffen the link (tighten the mode floor); 3 a higher trace rate when under-sampled |
   | 860 | the flag key | the offending token or its absence / four flags present and false | never | none |
   | 818 | the request's price option | no catalogue record / a pinned, licensed catalogue | after-change | 1 omit prices |
   | 824 | the part and file | T, V, N against 10⁶ and the bound 285,712, or the first differing vertex / at most the bound; bit-exact replay | after-change | 1 `--decimate <tolerance>` with the smallest tolerance that reaches the bound (the result is re-checked) |
   | 827 | the intermediate | status (`refuted` with the counterexample, or `undecided`) / unsatisfiable within the budget | after-change | 1 the wider format named; 2 a clamp at the named point; 3 the largest safe input range; 4 a larger budget (undecided only) |
   | 831 | the law and card | quantity, range, observed extremes and share, or the class requested / inside the domain; class Estimated | after-change | 1 a card whose domain covers the range; 2 the design change that brings the quantity inside; 3 run without the law (`no-claim`) |
2. **`affected_claims`.** Each refusal lists what the caller cannot now claim: for 163 on fatigue, "fatigue
   utilization"; for 262, "stress and fatigue in impact windows"; for 166 and 860, "any packet"; and so on.
   The list is fixed per code and reason in a table next to the types.
3. **Rendering rules.** `message` is one sentence without advice; advice lives in `repairs`. `unit` is given
   whenever `observed` or `required` is a quantity. Private-scene data never appears in a payload: world
   addresses and counts do, coordinates of scene geometry do not. Every repair that is a command is checked
   to parse against the verb registry.
4. **Never downgraded.** No code path converts one of these refusals into a warning with a result. A compile-
   time marker type `MustRefuse` wraps each payload; the only consumers are the envelope renderer and the
   structure loop's documented automatic repairs (one automatic application of repair 1 for code 261 inside
   the loop; the under-relaxed step for cycling), both of which record the refusal they acted on.
5. **Codes of other chapters that Foundry verbs pass through** (listed so that the cluster's refusal lists
   are complete): the airlock's group-absent refusal (`FROB-REF-790`, exit 5) and stack-receipt mismatch
   (`FROB-REF-791`); the design language's mass-support refusal on declared inertia (`FROB-REF-106`) and the
   strict-data card refusal (`FROB-REF-113`); Chronicle's missing-samples refusal (`FROB-REF-888`), which
   Foundry's reader converts into FROB-REF-169 with the upstream code kept in the payload; the verb layer's
   protocol refusals (`FROB-REF-801`, `-802`).
6. **The battery** (`tests/refusal_battery.rs` and the script). One minimal trigger per code and per stated
   variant of its meaning, each through the real verb on a real fixture:

   | Code | Trigger fixtures |
   |---|---|
   | 166 | unqualified design to `optimize`; to `export`; exploratory record offered to a packet |
   | 167 | campaign with a sign-flipped joint reaction; a load file of assembled peaks |
   | 169 | a T2 chunk removed; a class envelope from one limb only |
   | 163 | card without yield; printed part with `--require fatigue` |
   | 164 | keep-out slab across the link; empty keep-in |
   | 165 | q = x² under `--method statistical`; an unknown simulated sensitivity |
   | 260 | planted gain 1.1; planted two-size cycle; a gain needing more than five iterations |
   | 261 | optimized part with a thin neck (stress); with a slender strut (buckling) |
   | 262 | soft link without the transient flag |
   | 860 | manifest flag set true; flag removed; a request carrying a flag key |
   | 818 | `--priced` without a catalogue |
   | 824 | open shell; 285,714 triangles; a planted replay mismatch |
   | 827 | Q15 product on the full range; an obligation timed out by a tiny budget |
   | 831 | a winding above its insulation class; a record edited to cite a lifecycle number as Tested |
   For each: exit code 3, the code, a non-empty `pointer`, `observed` and `required` present, the first
   repair as specified (or an empty list for 860), `retry` as specified, and, where the repair is a command,
   that running it changes the outcome (the repair works).

## Acceptance criteria

- [ ] Each of the fourteen codes is raised by at least one battery fixture through the `frob` binary, and each listed variant has its own fixture (30 fixtures in the table above).
- [ ] Every payload has `pointer`, `observed`, `required` (with `unit` where a quantity), `retry` and ranked `repairs` as in the table; code 860 has an empty repair list and `retry: never`.
- [ ] For every repair that is a command, executing it on the fixture changes the outcome from refusal to a result or to the next expected state.
- [ ] No Foundry code path turns one of these refusals into a warning (the marker-type test and a search of the crate for conversions).
- [ ] The fourteen codes exist in the refusal registry with meanings equal to the table's first column (a comparison test against the registry file).
- [ ] No payload contains scene geometry or other private-scene data (a scan of battery outputs against the fixtures' private fields).
- [ ] Pass-through codes keep their upstream code in the payload.

## Test plan

### Unit tests
`cargo test -p frob-foundry refusal` and `--test refusal_battery`:
- `payload_shapes` × 14 (schema validation of each rendered refusal).
- `exit_code_is_3_for_all`; `retry_values`; `repairs_ranked_and_parse`.
- `code_860_has_no_repairs`.
- `affected_claims_table_complete`.
- `must_refuse_cannot_be_dropped` (compile-fail: discarding a `MustRefuse` without rendering).
- `battery_<code>_<variant>` × 30.
- `repair_command_changes_outcome` for every fixture whose first repair is a command.
- `registry_meanings_match`.
- `no_private_data_in_payloads`.
- `chronicle_888_becomes_169_with_upstream_kept`.
- Planted defects, each caught: `refusal-as-warning` (code 262 rendered as a warning with quasi-static results), `repair-for-860` (offers "set the flag false" as a repair, implying a true flag was acceptable input), `wrong-exit-code` (code 260 exiting 2).

### End-to-end script and logging
The seven cluster scripts each contain the battery fixtures for the codes their verb can raise; this bead
supplies the shared helper `assert_refusal <code> <pointer-pattern> <first-repair-pattern>` and the summary
check that, across the seven scripts' logs of one run, all fourteen codes appear at least once
(`scripts/e2e/foundry_refusal_coverage.sh`, which reads the NDJSON logs and exits non-zero if a code is
missing). Each refusal is logged with `event: "refusal"`, code, pointer, observed, required and first repair.

### Known answers and negative controls
The battery is the known-answer set: each fixture has one expected code. Negative controls: the three planted
defects; and for each code a near-miss fixture that must *not* refuse (dropped share exactly 0.1%; a triangle
count of 285,712; a frequency ratio of exactly 5; λ̂ = 0.99 converging slowly inside the budget), which guards
against refusing too eagerly. Determinism: payloads are identical twice on one machine.

## Considerations

- The first repair is what an agent will run. A wrong first repair costs a loop iteration at best and
  teaches the agent to route around the check at worst; the "repair works" test exists for that reason.
- Code 860 is the only one with no repair, on purpose: there is no input change that makes a true
  authorization flag acceptable.
- Two codes have automatic handling inside the structure loop (261 once, cycling once); both are recorded, so
  a user sees that a refusal occurred and was repaired, not a silent success.
- The refusal table and the registry are owned by different beads; the comparison test is what keeps the
  types here and the rows there from drifting.
