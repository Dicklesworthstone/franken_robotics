## Background

In this program a refusal is a result with a type: when a verb cannot honestly answer, it says why in a code,
points at the field or part at fault, states what was observed and what was required, and offers ranked
repairs an agent can act on. A numerical refusal, a budget stop and a physical failure of the robot are three
different outcomes; the first two are refusals and the third is a result with findings.

Foundry defines fourteen refusal codes:

| Code | Refused | Repair offered |
|---|---|---|
| FROB-REF-166 | Optimization or packet export for a design with no qualification verdict | Qualify, or run with `--exploratory` (labelled; cannot enter a packet) |
| FROB-REF-167 | A load case that is not one instant, or a campaign failing the free-body check | The offending samples and residuals |
| FROB-REF-169 | Telemetry without the traces or samples a load metric needs | The telemetry level and worlds required |
| FROB-REF-163 | A check whose material card lacks the field or provenance it needs | The missing field; `fatigue: no-claim` |
| FROB-REF-164 | An empty design region, or ports with no load path inside the envelope | The blocking keep-outs |
| FROB-REF-165 | An allocation with a zero or unknown sensitivity, or a failed band-extreme check | Worst-case boxes for the named features |
| FROB-REF-260 | A loads–mass loop that diverges, cycles or exceeds its iteration budget | λ̂, the last iterates, and the beam rung |
| FROB-REF-261 | An optimized part that fails the independent check | The governing case and location; tighter cap or length scale |
| FROB-REF-262 | Quasi-static superposition where the frequency separation fails | Enable the transient path for impact windows |
| FROB-REF-860 | An export without the flags, or any attempt to produce a true flag | None |
| FROB-REF-818 | A priced parts list without a pinned, licensed catalogue | Omit prices |
| FROB-REF-824 | A STEP export above its bounds or failing bit-exact replay | Decimate under a stated tolerance |
| FROB-REF-827 | A fixed-point obligation refuted or undecided within budget | The counterexample input, or a wider format |
| FROB-REF-831 | A lifecycle law outside its validity domain, or cited above class Estimated | The domain and the card needed |

The mechanism beads decide *when* each is raised. This bead makes them uniform: one Rust type per code with
its payload, one place that renders them into the envelope, and the shared assertions with which every
script checks a refusal. The verbs that raise the codes are built by the capstone beads BD-400 to BD-408, and
those consume the types defined here (each lists this bead as a dependency for its typed payloads); the
battery that proves every code can be reached through the real verbs and carries what its row promises must
therefore come after them, and is the bead N31ap1-51. A refusal that exists in a table and that no test can
trigger is not a refusal the system has.

## Scope

In: `refusal.rs` with fourteen payload types and their rendering; the repair objects with exact commands; the
exit code and `retry` value per code; the `affected_claims` rule; the checks that a refusal is never
downgraded; the list of codes of other chapters passed through; the shared helper `assert_refusal` that every
cluster script uses; the coverage checker `scripts/e2e/foundry_refusal_coverage.sh` with its self-test on
recorded logs; the example renderer that emits one payload per code from constructed inputs.
Out: the triggering logic (the mechanism beads); the trigger battery through the real verbs, the per-code
binding tests `ref_<code>_<name>` and the repair-replay script `scripts/e2e/foundry_refusals.sh` that the
registry bead N31-REF names as the binding of each row (N31ap1-51, which depends on this bead and on the
verbs); the registry rows themselves (N31-REF, a dependency) and the counterexample registry (N31-CX); the
registry rows of the uncoded refusals (the decision bead N31b-45).

## Technical approach

1. **Payload types** (`refusal.rs`, DESIGN). One struct per code; each converts into the envelope's `refusal`
   object. All fourteen exit with code 3 (refused input or question). The ranked repairs of each code are
   the registry row's (N31-REF Table 1, the authority), all of them and in the row's order, each rendered
   with its exact command where one exists; the row carries the further repairs the mechanism beads name
   (those after the plan's own, numbered on from them in the table below). A repair that does
   not apply to the payload's `reason` (a decimation for an open shell; rebuilding a case from one sample for
   a free-body failure; accepting `fatigue: no-claim` for a missing yield strength) is omitted, and the others
   keep their relative order, so the first repair rendered is always the first applicable one of the row.

   | Code | `pointer` | `observed` / `required` | `retry` | Ranked repairs (each with an exact command where one exists) |
   |---|---|---|---|---|
   | 166 | the design | verdict status (none, failed, other model) / a passed verdict for this design and model | after-change | 1 `eval qualify`; 2 `--exploratory` (not for packets); 3 export the pre-optimization design |
   | 167 | the link, or the case in a load file | residual share and worst samples, or per-component source ticks / one instant; dropped share at most 0.1% | after-change | 1 rebuild the case from one sample (a case that is not one instant); 2 the offending samples with residuals: port map, frame, sign conventions (a free-body failure; when off-port samples are what exceed the budget, this repair is rendered as the change to the port map it points at, "declare a contact port on link L", N31a-07, and so is still the first rendered); 3 re-run the campaign on the referee for the named worlds; 4 fix the frame or sign named by the median residual wrench (for off-port samples instead: review the gait, since the task makes unplanned contact; N31a-07) |
   | 169 | the channel and worlds | telemetry level found, missing intervals / T2 on every world with the listed channels | after-change | 1 re-run the named worlds at T2 with the named control-rate channels; 2 restrict the metric to the covered worlds, stated in the result (not for a symmetric class's coverage rule); 3 read the missing limbs' traces (symmetric classes) |

   | 860 | the flag key | the offending token or its absence / four flags present and false | never | none |
   | 818 | the request's price option | no catalogue record / a pinned, licensed catalogue | after-change | 1 omit prices |
   | 824 | the part and file | T, V, N against 10⁶ and the bound 285,712, or the first differing vertex, or the sibling's reason (`open-shell`, `non-triangle-face`) / at most the bound; bit-exact replay; a closed shell of triangles | after-change | 1 `--decimate <tolerance>` with the smallest tolerance that reaches the bound (the result is re-checked; over-bound only); 2 close the shell (a repair outside Foundry; open shell or non-triangle face); 3 export the mesh formats only (`--geometry-only --format stl`, `3mf` or `glb`) |
   | 827 | the intermediate | status (`refuted` with the counterexample, or `undecided`) / unsatisfiable within the budget | after-change | 1 from the counterexample, a clamp or saturating operation at the named point, or the declared input range narrowed to the largest safe range found (one repair, both alternatives stated; N31a-45 step 7); 2 the wider format named; 3 a larger budget (undecided only) |
   | 831 | the law and card | quantity, range, observed extremes and share, or the class requested / inside the domain; class Estimated | after-change | 1 a card whose domain covers the range; 2 restrict the run to the domain, stated in the result; 3 the design change that brings the quantity inside; 4 run without the law (`no-claim`) |
2. **`affected_claims`.** Each refusal lists what the caller cannot now claim: for 163 on fatigue, "fatigue
   utilization"; for 262, "stress and fatigue in impact windows"; for 166 and 860, "any packet"; and so on.
   The list is fixed per code and reason in a table next to the types.
3. **Rendering rules.** `message` is one sentence without advice; advice lives in `repairs`. `unit` is given
   whenever `observed` or `required` is a quantity. Private-scene data never appears in a payload: world
   addresses and counts do, coordinates of scene geometry do not. Every repair that is a command is checked
   to parse against the verb registry.
4. **Never downgraded.** No code path converts one of these refusals into a warning with a result. A compile-
   time marker type `MustRefuse` wraps each payload; the only consumers are the envelope renderer and the
   structure loop's documented automatic repairs (one automatic application of repair 1 for code 261 inside
   the loop; the under-relaxed step for cycling), both of which record the refusal they acted on.
5. **Codes of other chapters that Foundry verbs pass through** (listed so that the cluster's refusal lists
   are complete): the airlock's group-absent refusal (`FROB-REF-790`, exit 5) and stack-receipt mismatch
   (`FROB-REF-791`); the design language's mass-support refusal on declared inertia (`FROB-REF-106`) and the
   strict-data card refusal (`FROB-REF-113`); Chronicle's missing-samples refusal (`FROB-REF-888`), which
   Foundry's reader converts into FROB-REF-169 with the upstream code kept in the payload; the verb layer's
   protocol refusals (`FROB-REF-801`, `-802`); on `foundry.export`, the label refusals FROB-REF-830 and -819
   (a `model-conditional` or `tier-sensitive` selection behind a packet; N31ax-01) and FROB-REF-820 as the
   interim code of the chapter's uncoded `provisional-load-case-in-packet` (N31b-36); on `foundry.loads`,
   FROB-REF-821 (re-extraction with `--for packet` against a wrench envelope that is not frozen; N31b-35) and
   -820 under `--admit packet`; on `foundry.export`, the export door's codes (N37-18): FROB-REF-731 (private
   artifact without the private scope and flag), -733 (licence set forbids the export) and -734 (path outside
   the session's export root), each exit 5 because they are capability refusals, and -816 (loose geometry
   without its three flags; exit 3). The chapter's uncoded refusals are rendered by the same machinery through
   one generic `NamedRefusal` type defined here (the payload fields of the table, and the exit its row in
   N31-REF's Table 3 states: 3, or 5 for the capability class of row 11), following the held
   rule of the decision bead N31b-45: a row held under a fitting interim renders that interim code with a
   `detail` naming the refusal, behind one named constant (row 3, `provisional-load-case-in-packet`, under 820;
   row 9, `firmware-receipt-mismatch`, under 890); the rows with no fitting interim (row 4,
   `review-record-packet-mismatch` of N31b-33; row 10, `packet-inconsistent` of N31a-43; row 11,
   `firmware-controller-not-exportable` of N31a-44, exit 5; and `packet-integrity-failed` of N31a-36's packet
   reader) render no code, only the `detail` constant naming the refusal, and their raising beads stay open on
   that point until the ledger assigns the number (N35x-01). When a number is assigned only the named constant
   changes.
6. **Shared assertions and coverage.** (a) `scripts/e2e/lib/foundry_refusal.sh` provides
   `assert_refusal <code> <pointer-pattern> <first-repair-pattern>`, which checks on an envelope: exit 3 (exit
   5 for the pass-through capability codes 731, 733 and 734 and for the uncoded
   `firmware-controller-not-exportable`, taken from the registry row's `exit`),
   `ok: false`, the code (or the uncoded name), a non-empty `pointer` matching the pattern, `observed` and
   `required` present with `unit` where a quantity, `retry` as the table says, the first repair matching the
   pattern (an empty list for 860), and writes one `event: "refusal"` NDJSON line. Every cluster script
   (N31a-53 to N31a-59) and the battery N31ap1-51 use it. (b) `scripts/e2e/foundry_refusal_coverage.sh` reads
   the NDJSON logs of one run of the cluster scripts and the battery and exits non-zero if a code of the
   required set is missing, naming it. The required set is the fourteen codes minus those whose feature the
   binary under test was built without, as the binary reports its features: 827 needs
   `moonshot-firmware-export`, 831 needs `moonshot-lifecycle`; so a default M5 build requires twelve, and the
   lanes with both features require fourteen. (c) `examples/render_refusals.rs` builds one payload of each
   code from constructed inputs and prints the fourteen rendered envelopes as JSON lines, so that the
   rendering can be checked before any verb exists.

## Acceptance criteria

- [ ] Every payload type renders `pointer`, `observed`, `required` (with `unit` where a quantity), `retry` and ranked `repairs` as in the table; code 860 has an empty repair list and `retry: never`; the fourteen rendered envelopes of the example renderer validate against the envelope schema.
- [ ] Every repair that is a command parses against the verb registry.
- [ ] Each code's rendered repairs are its N31-REF row's ranked repairs, all of them and in order (a repair not applicable to the payload's reason omitted), checked against `registries/refusals.toml`; a buckling 261 renders the length scale first and the buckling repairs 4 and 5, a modal 261 the length scale first and 6 to 8.
- [ ] No Foundry code path turns one of these refusals into a warning (the marker-type test and a search of the crate for conversions).
- [ ] The fourteen codes exist in the refusal registry with meanings equal to the table's first column (a comparison test against the registry file).
- [ ] No payload contains scene geometry or other private-scene data (a scan of rendered payloads built from fixtures with private fields).
- [ ] Pass-through codes keep their upstream code in the payload (888 converted to 169 with 888 kept).
- [ ] `assert_refusal` accepts a correct envelope and rejects each of: wrong code, exit 2, empty pointer, missing `required`, wrong first repair, a non-empty repair list on 860.
- [ ] The coverage checker passes on a complete recorded log set, fails naming the code when one is removed, requires twelve codes for a binary reporting neither Moonshot feature and fourteen for one reporting both.

## Test plan

### Unit tests
`cargo test -p frob-foundry refusal`:
- `payload_shapes` × 14 (schema validation of each rendered refusal, built from constructed inputs).
- `exit_code_is_3_for_all` (the fourteen Foundry codes; pass-through capability codes keep their own exit); `retry_values`; `repairs_ranked_and_parse`.
- `code_860_has_no_repairs`.
- `repairs_follow_registry_order`: for each code the rendered repairs equal the `repairs` of its row in `registries/refusals.toml`, in order, less those not applicable to the reason; a planted swap of 827's first two repairs fails naming the code.
- `inapplicable_repair_omitted`: an open-shell 824 renders "close the shell" first and no decimation; a buckling 261 renders repair 2 first, then 4 and 5, and no 1, 3 or 6 to 8; a 167 free-body failure renders the offending samples first; a 163 on the yield field (`structure.yield_Pa`, N31a-22's card path) renders no `fatigue: no-claim` repair.
- `affected_claims_table_complete`.
- `must_refuse_cannot_be_dropped` (compile-fail: discarding a `MustRefuse` without rendering).
- `registry_meanings_match`.
- `no_private_data_in_payloads`.
- `chronicle_888_becomes_169_with_upstream_kept`.
- `uncoded_name_rendered_until_coded` (`packet-inconsistent` renders with no code, its `detail` constant and exit 3; `firmware-controller-not-exportable` the same with exit 5; a code entered in a scratch registry replaces the constant's value); `held_row_renders_interim_with_detail` (`provisional-load-case-in-packet` renders FROB-REF-820 with `detail: "provisional-load-case-in-packet"`).
- `pass_through_exit_codes` (731, 733, 734 exit 5; 816 and 821 exit 3; upstream code kept in the payload).
- `assert_refusal_accepts_and_rejects` (the six rejections of the acceptance criteria); `coverage_required_set_follows_features` (12 and 14); `coverage_names_missing_code`.
- Planted defects, each caught: `refusal-as-warning` (code 262 rendered as a warning with quasi-static results), `repair-for-860` (offers "set the flag false" as a repair, implying a true flag was acceptable input), `wrong-exit-code` (code 260 exiting 2).

### End-to-end script and logging
`scripts/e2e/foundry_refusal_coverage.sh --self-test` (sources the STD-E2E helper): (1) runs
`cargo run -p frob-foundry --example render_refusals` and passes each of the fourteen envelopes through
`assert_refusal` with its expected code, pointer pattern and first repair; (2) runs the six rejection cases of
the helper on mutated copies (each must fail); (3) runs the coverage check on three recorded log sets under
`fixtures/foundry/refusal-logs/`: complete (pass), one with the 165 lines removed (must fail naming 165), and a
default-build set without 827 and 831 against a feature list lacking both Moonshot features (pass) and against
one with both (must fail naming 827 and 831). NDJSON to `target/e2e-logs/foundry_refusal_coverage/<utc>.ndjson`:
every line `ts`, `script`, `bead` (`N31a-52`), `step`, `event`, the exact command, exit code and wall time; per
envelope an `event: "refusal"` line with code, pointer, observed, required, retry and first repair; per log set
the required set, the codes found and the missing ones; a `summary` line with envelopes checked (14), helper
rejections caught (6 of 6) and coverage cases as expected (4 of 4). The cluster scripts and the battery
(N31ap1-51) run the same helper on real verbs.

### Known answers and negative controls
Each constructed payload has one expected code, pointer and first repair. Negative controls: the three planted
defects; the six helper rejections; the coverage cases that must fail. The near-miss fixtures that must not
refuse are the battery's (N31ap1-51). Determinism: payloads are identical twice on one machine.

## Considerations

- The first repair is what an agent will run. A wrong first repair costs a loop iteration at best and
  teaches the agent to route around the check at worst; the "repair works" test of the battery (N31ap1-51)
  exists for that reason, and the parse check here catches a repair that is not even a valid command.
- The types come before the verbs and the battery after them; a code whose payload type exists but that no
  verb can yet raise is reported by N31-REF's binding check as pending until the battery binds it.
- Code 860 is the only one with no repair, on purpose: there is no input change that makes a true
  authorization flag acceptable.
- Two codes have automatic handling inside the structure loop (261 once, cycling once); both are recorded, so
  a user sees that a refusal occurred and was repaired, not a silent success.
- The refusal table and the registry are owned by different beads; the comparison test is what keeps the
  types here and the rows there from drifting.
