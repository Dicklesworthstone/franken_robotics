## Background

Firmware export is one of Foundry's two Moonshots: from a joint-level controller it emits source for a
`no_std`, heap-free crate that forbids unsafe code and sits behind a caller-owned bus trait, with Q-format
declarations, overflow certificates, a test-vector manifest and the four no-authorization flags. **The exporter
emits no register access, no bus driver and no stop-circuit code**, and it never claims execution time, stack
depth or behaviour on a board: `timing: no-claim` until a receipt from a linked binary on real hardware is
imported. Decision ADR-FOUNDRY-11 gives the reason: no gate depends on a reviewer, a machine shop or a board;
those are import lanes that rest at `no-claim`, because a simulator cannot gate on what it lacks.

Three things about the far side of that boundary are stated in the plan and belong to no other firmware bead.

1. **A pattern to follow.** The sibling repository franken_firmware (FACT, suite survey: eighteen crates
   including `franken-hal`, `franken-control` and `franken-platform`; head `151f9ca991e7`; the source register
   lists only its toolchain file as read so far) is admitted as *Pattern [M]*: "the hardware-abstraction boundary for firmware
   export. Exported firmware never touches a register, a bus or a stop relay." Pattern means its design is
   read and imitated; it is never a Cargo dependency, and the dependency firewall fails any resolved graph
   that contains a package from that repository. The ledger gives it no admission gate until the M8 work
   package is funded, and its fallback is "no firmware export".
2. **A stable-only target.** The workspace builds on one pinned nightly toolchain because a sibling
   quantity crate needs a nightly feature. The plan lists three ways that coupling can bite; the third is
   "a stable-only target appears. Firmware export would be one; franken_firmware is on stable 1.99.0", the
   only stable pin in the suite. A crate generated for a microcontroller project must therefore build on a
   stable compiler, with nothing from the nightly side of the graph in it.
3. **The receipt lane.** The words "until a receipt … is imported" need a record format and an import
   path, so that an imported timing measurement means the same thing for every export and cannot be mistaken
   for a claim this program made.

Alternatives rejected: depending on the sibling's hardware-abstraction crate (forbidden by the firewall, and
it would put a hardware interface inside an artifact that must not address hardware); generating a default
bus implementation for convenience (it would be a bus driver); measuring timing in an instruction-set
simulator and printing it (a number about a model of a board, which the chapter's ceiling excludes).

## Scope

In: reading the sibling's boundary and recording facts; a conformance note mapping the generated bus trait to
that boundary; the stable build lane for generated crates and the rules that keep them stable-clean; the
receipt record, its import, its view and its refusal.
Out: code emission and the bus trait itself (N31a-44); overflow certificates (N31a-45); quantization bounds,
vectors and the host comparison (N31a-46); anything executed on hardware (nothing in this program does); the
suite survey and the firewall (the suite units).

## Technical approach

1. **Read the pattern** (`docs/siblings/franken_firmware.md`, DESIGN). At the head recorded in the stack
   lock, read the sibling's hardware-abstraction crate and record, as FACT with file paths: how a control
   routine receives its inputs and emits its outputs (trait names and signatures); who owns timing and the
   stop path; which integer types cross the boundary; what the crate forbids (unsafe code, allocation). Each
   recorded fact gets a probe: a small text check against the sibling's source at the pinned head, run in the
   lane that has the sibling checked out and skipped with a logged reason elsewhere. A probe that fails after
   a pin move reopens the conformance note.
2. **Conformance note.** A table with one row per element of the generated boundary
   (`trait Bus { fn read(&mut self, ch: Channel) -> i32; fn write(&mut self, ch: Channel, v: i32); }`,
   `run_once`, the plain-integer `State`, `Input` and `Output`) against the corresponding element of the
   pattern, with one of three verdicts: `same shape`, `adapter needed` (with a ten-line adapter shown as
   documentation, not shipped) or `deliberately different` with its reason. The note is evidence that a
   caller in that ecosystem can implement the trait without touching generated code; it changes no claim.
   If the pattern suggests a better boundary (for example separate read and write traits), the change is
   proposed to the emission bead; this bead does not edit emitted code.
3. **Stable-clean rules for generated crates.** Added to the emission lint: no `#![feature(…)]`, no
   attribute or syntax newer than the stable floor, no dependency of any kind (already required), and
   `rust-version = "1.99"` in the generated `Cargo.toml` (the floor is the sibling's pin; DESIGN). The floor
   is a constant with its provenance, re-read when the suite survey changes that row.
4. **The stable lane** (`xtask firmware-stable`). For every firmware fixture: emit the crate into a scratch
   directory outside the workspace (so that no workspace toolchain file applies), then with the stable
   toolchain at the floor run `cargo build` for the host and `cargo check --target thumbv7em-none-eabi`
   (a compile check, not a run), then the generated vector harness on the host. The lane asserts: both
   builds succeed with zero warnings; `cargo tree` of the generated crate prints one package; the 10⁶ vectors
   agree bit for bit under the stable compiler as they do under the workspace toolchain (the two host
   binaries' output digests are equal). The toolchain identity of each build goes into the firmware
   manifest's `built_with` list. The lane needs the stable toolchain installed; where it is absent the lane
   reports `not measured`, which this bead's script logs with the reason; the receipt of GATE-FOUNDRY-11
   (N31a-58's, measured on the workspace toolchain) does not depend on this lane.
5. **The receipt record** (schema `frob.firmware.receipt/1`, a sidecar addressed by the firmware manifest's
   digest; DESIGN):
   ```json
   { "schema": "frob.firmware.receipt/1", "firmware": "firmware manifest digest",
     "binary": { "blake3": "…", "target": "thumbv7em-none-eabihf", "toolchain": "1.99.0", "opt": "s" },
     "board": { "mcu": "…", "clock_hz": 168000000 },
     "measured": { "step_time_ns": { "max": 4200, "p99": 3900, "n": 100000 }, "stack_bytes_max": 312 },
     "vectors": { "manifest": "blake3", "agree": 1000000, "of": 1000000 },
     "method": "free text, untrusted", "by": { "independent": true }, "date": "YYYY-MM-DD" }
   ```
   Rules: `firmware` must equal the digest of an existing firmware manifest; `vectors.manifest` must equal
   that manifest's vector hash, and `agree` must equal `of` (a board whose integers differ from the kernel's
   has not run this controller); every measured quantity carries its unit in its name; free text is stored
   as untrusted data and never interpreted.
6. **Import and view.** `frob foundry check <packet or firmware directory> --firmware-receipt <file> --key <k>
   --json` (`foundry.check` is a run verb; each import carries its own key)
   validates the record, compares digests, and stores the canonical bytes keyed by (firmware digest, record
   digest). **Importing changes no byte of the packet or of the generated crate**; the firmware manifest
   still says `timing: "no-claim"`. The *view* then renders `timing: imported <record digest>` with the
   measured values, the board and the word `imported`. Imported values never enter a claim product, never
   raise a class and are never compared with a simulated control period by this program: whether 4.2 µs fits
   a 1 kHz loop is the reader's arithmetic on the reader's board. A digest mismatch, a vector disagreement
   or a missing unit is refused as `firmware-receipt-mismatch` (row 9 of N31b-45, whose number is held): until
   the ledger assigns it, the refusal is raised under the interim FROB-REF-890 (evidence recorded under another
   receipt offered as matching) with `detail: "firmware-receipt-mismatch"`, behind the one named constant
   `FIRMWARE_RECEIPT_MISMATCH`, so that only the constant changes when the number arrives. Block fields beyond
   the common four: `receipt_digest`, `export_digest`, `failed` (`digest`, `vectors` or `unit`); retry
   `after-change`; exit code 3; repair: re-issue the receipt against the right export. Nothing is stored.
7. **Wording.** No envelope, report or view may say an export "runs on", "meets timing on" or "was tested
   on" a board from an import; the fixed strings are `timing: no-claim` and `timing: imported`. The four
   flags stay false whatever is imported.

## Acceptance criteria

- [ ] `docs/siblings/franken_firmware.md` records the boundary facts with paths at the pinned head, each with a probe, and the files read are added to the source register.
- [ ] The conformance note has a verdict for every element of the generated boundary.
- [ ] No package from the sibling repository appears in any resolved graph (the firewall's check passes with the firmware feature on).
- [ ] Every firmware fixture's generated crate builds on stable 1.99.0 for the host and checks for `thumbv7em-none-eabi` with zero warnings and one package in its tree.
- [ ] The 10⁶ vectors agree under the stable build, and its output digest equals the workspace-toolchain build's.
- [ ] A planted emission containing `#![feature(core_intrinsics)]` is rejected by the lint before any file is written.
- [ ] Importing a valid receipt leaves every packet and crate hash unchanged and changes the view to `timing: imported`.
- [ ] A receipt with a wrong firmware digest, with 999,999 of 1,000,000 vectors agreeing, or with a unitless field is refused under the interim FROB-REF-890 with `detail: "firmware-receipt-mismatch"` and the matching `failed` field, exit 3.
- [ ] With a receipt imported, the envelope's class, claim product and flags are identical to those without it.

## Test plan

### Unit tests
`cargo test -p frob-foundry --features moonshot-firmware-export firmware::stable firmware::receipt`:
- `generated_manifest_has_rust_version_floor`; `lint_rejects_feature_attribute`; `lint_rejects_dependency_table`.
- `receipt_schema_round_trip`; `receipt_wrong_firmware_digest_refused`; `receipt_vector_disagreement_refused` (999,999 of 1,000,000); `receipt_unitless_field_refused` (each of the three: FROB-REF-890, `detail` `firmware-receipt-mismatch`, `failed` equal to `digest`, `vectors` and `unit` respectively, exit 3, nothing stored); `receipt_text_is_untrusted` (a `method` string containing an instruction is stored and rendered escaped).
- `receipt_refusal_uses_named_constant`: the code and detail come from `FIRMWARE_RECEIPT_MISMATCH` only (no other literal 890 in the module).
- `import_changes_no_byte`: hashes of the packet directory before and after are equal.
- `view_renders_imported_not_claimed`; `class_and_flags_unchanged_by_import`.
- `wording_scan_rejects_runs_on` (a planted report string "meets timing on" fails the scan).
- Planted defects, each caught: `receipt-raises-class` (an import that upgrades `timing` to Tested), `receipt-rewrites-manifest`, `stable-lane-uses-workspace-toolchain` (the scratch directory placed inside the workspace, detected by the recorded toolchain identity).
`cargo xtask firmware-stable` (the lane of step 4), and the sibling probes in the lane that has the checkout.

labelled so. NDJSON to `target/e2e-logs/foundry_firmware_hardware_side/<utc-timestamp>.ndjson` with a

on failure the first differing byte offset or field and the paths of the scratch crate and the receipt. The
`summary` lists no gate: this bead measures none.

### Known answers and negative controls
No numeric known answer of its own; it reuses the 10⁶-vector agreement of the firmware gate under a second
compiler. Negative controls: the three planted defects, the three bad receipts and the planted feature
attribute. Determinism: emission is byte-identical; the two host builds' vector outputs have equal digests.

## Considerations

- KILL-FIRMWARE (M8; trigger: GATE-FOUNDRY-11 fails): the fallback output is parameters, Q formats and the
  vector manifest with no code; the stable lane then has nothing to build, and the receipt lane is retired
  with the code.
- The stable floor follows one sibling's pin. If that pin moves, the floor is re-read; it is not a claim
  that every embedded toolchain accepts the crate, and a cross-compiler can still differ from the host one.
- An imported receipt is somebody else's measurement. Keeping it out of every class and claim product is what
  lets the lane exist without a hardware gate; the cost is that the program never says a controller is fast
  enough, which is the chapter's stated ceiling.
- The sibling's own asynchronous-runtime requirement is not yet read by the suite survey; nothing here links
  it, so it cannot conflict, and the survey bead records it.
- At most four Moonshot items are active at once by program rule; this one is queued with its epic at M8.
