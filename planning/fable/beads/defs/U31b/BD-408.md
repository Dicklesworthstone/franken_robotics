## Background

The design loop of this program ends with a scored, qualified robot design. The build packet is what turns
that into something a workshop could act on: one directory holding the parts list, the geometry of each made
part, tolerances, mass properties, a wiring harness, the actuator and sensor schedule, and the structural and
manufacturing evidence, every file hashed and every number carrying its evidence class. It is North-Star
scenario NS-20: before, the loop ends with a scored design; after, a qualified design and task yield a
`.fbuild` packet with a bill of materials, faceted solid geometry, a tolerance stack that closes, fatigue
margins computed from simulated load histories and one re-optimized link, with claim product Estimated
(because its material cards are) and all flags false.

What a packet is not. Foundry fabricates nothing, buys nothing, flashes nothing and signs nothing off. Every
artifact it writes says so in machine-readable flags (INV-FOUNDRY-01). ADR-FOUNDRY-09: every exported artifact
carries the no-authorization flags, and the exporter has no code path that sets one true, because a packet
must not be mistaken for a release. ADR-FOUNDRY-10: no priced bill of materials without a pinned, licensed
catalogue. ADR-FOUNDRY-11: no gate depends on a reviewer, a machine shop or a board; those are import lanes
that rest at `no-claim`. ADR-FOUNDRY-12: firmware export and lifecycle compression live behind features and
out of the packet's dependency graph (INV-FOUNDRY-07). Authorizing hardware is a human act outside this
project that leaves no trace in these artifacts.

Rejected alternatives: a single archive file (a directory addressed by its manifest hash lets large geometry
be hashed and replaced as blobs); flags as ordinary booleans (a boolean can be set; a type with one value
cannot); a packet for any design (only qualified finalists; an exploratory run is labelled and cannot enter a
packet).

Tier: Frontier [F]. Bet BET-29 is lost if the packet fails its geometry round trip or its tolerance closure.
The build-packet pilot (N31b-09) must have recorded its verdict.

## Technical approach

Modules (the crate's module map, N31a-01): `crates/frob-foundry/src/packet/{manifest,flags,writer,reader,parts,
geometry,mass,harness,schedule,evidence,assemble,consistency}.rs` (the snap and prune rule sit in `parts`, the
structure section in `evidence`).

**1. Layout.** One directory written atomically and addressed by the hash of its manifest (format
`FMT-FBUILD`, schema `frob.build/1`).

```
quad-a.fbuild/
  manifest.json         identities, flags, evidence classes, BLAKE3 of every file
  parts.json            made parts (geometry, material, process, mass) and purchased parts (card references)
  geometry/<part>.{step,stl,3mf,glb}      with triangle counts, datums and fiducials
  tolerances.json       per feature: tolerance, action, path, sensitivity, class; stack and robustness results
  mass.json             per part and assembly: mass, centre of mass, inertia, each with uncertainty
  harness.json          nets, connectors, conductor sizes, lengths with slack, checks
  schedule.json         actuator and sensor schedule
  structure/            load cases, utilizations, buckling factors, modes, loop convergence record
  fab.json              manufacturability report with repairs
  firmware/             optional; Moonshot; present only with feature firmware-export
  certs/*.frobcert      certificates the packet cites; certs/packet.frobcert, the auditor's bundle embedding the manifest
  NOTICES               only when the design's licence set is `attribution`: the notices block (N37-18)
```

**2. Manifest.**

```json
{ "schema": "frob.build/1", "design": "DesignId", "model": "ModelId", "qualification": "verdict id or null",
  "authorization": { "execution_authorized": false, "hardware_safety_signoff": false,
                     "sim_to_real_certified": false, "fabrication_released": false },
  "reality": "no-claim", "review": "no-claim", "units": "SI", "exploratory": false }
```

plus `files: [(relative path, BLAKE3)]`, the evidence class per section and the stack receipt of the writing
binary. Type sketch (DESIGN): `BuildPacket { schema, design, model, qualification: Option<VerdictId>,
authorization: PacketAuthorization, reality: RealityStatus, review: ReviewStatus, units, exploratory: bool,
files: Vec<(Path, Blake3)> }`. Identity: BLAKE3 of the manifest's canonical JSON under the domain string
`frob.build/1`. The writer's types are narrower than the JSON shape: `exploratory` has the single value `false` and
`qualification` always holds a verdict (the fields exist so that a reader can assert them; a manifest with
`exploratory: true` or `qualification: null` is rejected by the reader with the reasons `exploratory` and
`no-verdict`). A manifest never embeds a path of the writing machine. `reality` stays `no-claim` until the
calibration subsystem supplies data; `review` stays `no-claim` until a review, a quotation or an inspection is
imported.

**3. Flags.**

```rust
// DESIGN: fixes intent, not signatures.
pub struct NoAuthorization { _sealed: () }      // the only value; it serializes to the false fields
impl NoAuthorization { pub const fn new() -> Self { Self { _sealed: () } } }
// PacketAuthorization wraps it and serializes four fields, the fourth being fabrication_released: false.
// No constructor, setter or deserializer yields `true`. A packet that parses with a flag absent or true is
// rejected by the reader and by `frob-verify` (FROB-REF-860).
```

The flags sit at the manifest root, in the header of every generated drawing and bill-of-materials view, and
in the `authorization` field of the verb's envelope. Absence is not read as false.

**4. Sections and rules.**

| Section | Contents | Rules |
|---|---|---|
| Parts list | Made parts with geometry, material, process and mass; purchased parts by card reference and quantity | A continuous optimum snapped to a catalogue part, stock size or gear ratio is revalidated after the snap: hard constraints and the controller are re-checked on the snapped design, and the snap record names the design before and after and the verdict. A failed simulation removes a whole part family only when an algebraic bound shows the failure holds across the family. No prices without a pinned, licensed catalogue (FROB-REF-818) |
| Geometry | The four exports per made part; the datum scheme and at least three non-collinear fiducials per part | Datums and fiducials are placed at design time so that an as-built scan registers |
| Tolerances | The allocation report | Each tolerance carries its sensitivity and class |
| Mass properties | Mass, centre of mass and inertia per part and for the assembly, recomputed from the exported geometry | Must equal the model's values within 10⁻⁶ relative (TARGET): the cross-export identity (INV-FOUNDRY-04) |
| Wiring harness | A netlist from the electrical ports of the design; routes along the kinematic tree through declared cable ports; conductor size, length and slack per net | The kinematic tree makes the shortest connecting tree the union of paths, so no approximation is needed. Checks: voltage drop I·ρ·L/A against the bus budget; current density against a limit declared on the cable card; bend radius against the cable card; slack across a joint of at least ρ_c·Δθ for a cable at offset ρ_c from the axis and joint range Δθ. Sag and dynamic whip need a rod model and are `no-claim` |
| Actuator and sensor schedule | Per joint: actuator card, gear ratio, mounting interface, encoder, driver rate, limits, thermal derating. Per sensor: card, mount frame, extrinsic tolerance, clock contract (rational period and phase), cable | Every joint has an actuator card and every net has two ends |
| Structural and manufacturing evidence | The independent-check records, the load cases with their labels, the loop record, the fab report | Classes are printed per number; the manifest cites the mesh hash of each check (INV-FOUNDRY-03) |

**5. The prune rule and its counterexample.** Two gripper fingers each need one powered tick and the bus
powers one finger per tick. With a one-tick deadline no schedule works; with two ticks exactly two do, and the
motor limits are identical in both cases. A rule that adds both peaks prunes a feasible design. A prune is
rejected if any discarded design is independently feasible under the same mission.

**6. Admission.** `foundry.export` refuses: a design with no qualification verdict for this `DesignId` and
`ModelId` (FROB-REF-166; repair: qualify; `--exploratory` is offered for optimization and loose geometry only);
any input labelled exploratory; an envelope load case still `provisional` (the load-case promotion rule); a geometry
without an independent-check record on a mesh the optimizer did not use, or one whose check failed
(FROB-REF-261); a design whose selection rests on an unresolved `model-conditional` ranking (FROB-REF-830) or
a `tier-sensitive` one (FROB-REF-819), because a packet is prototype spend (N31ax-01); a priced request without
a catalogue (FROB-REF-818). `--exploratory` does not admit a packet: `foundry.export --exploratory` of a packet is refused
with FROB-REF-166, and the flag applies only to optimization and to a geometry-only export, whose loose files are
stamped `exploratory` in their sidecar (the admission function and the label are N31a-03's).

**7. The export door and atomic writing (INV-FOUNDRY-05).** The packet leaves the store through the one export
door of N37-18 (through the writer of N31a-36): before any byte is written the writer obtains an `ExportGrant`
from `frob_verbs::export::admit(packet, kind packet, session)`, the only producer of a grant, whose checks run
in order: flags present (for a packet the chapter's own check answers, FROB-REF-860, since the chapter governs
its own artifact; the door's FROB-REF-816 is for loose geometry, BD-407); privacy (FROB-REF-731, exit 5: a
private design or asset in its lineage without the private scope and flag); licence (FROB-REF-733, exit 5: a
`research-only`, `proprietary` or `unknown` asset in the design's lineage); the row's `export:packet` scope;
the path jail (FROB-REF-734, exit 5: a `--packet` directory outside the session's export root). For an
`attribution` licence set the packet gains a `NOTICES` file, assembled deterministically by the door's rule
and listed in the manifest with its hash. Then: (i) create a temporary sibling directory; (ii) write and fsync
each file; (iii) compute BLAKE3 of each; (iv) write `manifest.json` last among the listed files and fsync, then
`certs/packet.frobcert` (the auditor's bundle embedding the manifest bytes, N31a-36); (v) fsync the
directory; (vi) rename it to `<name>.fbuild` in one atomic rename; (vii) fsync the parent. A writer killed at
any file boundary (each file, the manifest, the bundle, the rename) leaves no packet; a leftover temporary
directory is removed at the next run and is never read.

**8. The reader.** `frob-foundry` is the only crate that parses packet bytes. It refuses an unknown major
schema version, an unknown required field, a missing or true flag (FROB-REF-860), a file whose hash differs
from the manifest, a directory whose manifest hash is not its address, and a packet reached through another
reader.

**9. The verb.** `foundry.export` (kind `run`, M5): writes geometry and the build packet; `--with-firmware`
under feature `firmware-export`. Output: the packet address, per-section evidence classes, the list of
`no-claim` items (reality, review, sag and whip, any fatigue no-claim). Inputs (schema
`frob.foundry.export.in/1`): the design (or `--fixture <name>`, the cluster's named-fixture input, N31a-51),
`--packet <directory>` (the packet's target), `--profile reduced` (the KILL-PACKET profile), `--replace
<identity>` (replace an existing packet of other content at the target, named by its identity; without it a
different packet there is a conflict, exit 7; N31a-36), `--priced` (refused without a catalogue),
`--strict-data` (a priced list whose catalogue is marked `assumed` is refused with 818; N31a-39),
`--with-firmware`, and the idempotency key `--key`; the seven flag keys are `forbidden_keys` of the input
schema, so a request naming one is refused with 860 (N31a-37); output schema `frob.foundry.export.out/1`. Refusals, the list of the verb registry row (VERBS-foundry,
`exports = true`): 166, 261, 818, 824 (from geometry export), 827 (with firmware), 860; 169 (a symmetric
class's load set that does not cover every instance); 820 (the interim code of
`provisional-load-case-in-packet`, N31b-36); 830 and 819 from the prototype-spend precondition of N31ax-01;
and the export door's 731, 733, 734 and 816 (N37-18). All exit 3 except 731, 733 and 734, which are
capability refusals and exit 5. `packet-inconsistent` (N31a-43) is still uncoded: row 10 of N31b-45 has no
fitting interim, so the assembler refuses with exit 3, nothing written and a `detail` behind a named
constant, and that point stays open until the ledger assigns its number. With `--with-firmware` (the Moonshot
of BD-438), `firmware-controller-not-exportable` (N31a-44, exit 5) is held the same way, row 11 of N31b-45.
Evidence: class Estimated, never above (INV-FOUNDRY-06), except instance certificates cited under `certs/`.

## Acceptance criteria

- [ ] GATE-FOUNDRY-10 (TARGET): the packet is schema-valid, every hash matches, the four flags are present and false, parts, geometry, nets and schedule are cross-consistent (every made part has its four geometry files, every purchased part resolves to a card, every joint has an actuator card, every net has two ends); a mutated flag is rejected by `frob-verify`; a writer killed at any file boundary leaves no packet.
- [ ] Mass properties in `mass.json` equal the model's and those recomputed from exported geometry within 10⁻⁶ relative.
- [ ] No source path sets a flag true: a build-graph test finds no constructor, setter or deserializer of the flag type that can yield `true`.
- [ ] A snapped part without a revalidation record is refused; the additive-peak prune is rejected on the two-finger bus fixture.
- [ ] An unqualified design is refused with FROB-REF-166; a priced request without a catalogue with FROB-REF-818; a provisional load case blocks the packet.
- [ ] `foundry.export --exploratory` of a packet is refused with FROB-REF-166; no code path serializes a manifest with `exploratory: true` or `qualification: null`, and the reader and the auditor each reject a manifest that carries either.
- [ ] The harness checks reproduce the voltage-drop and slack known answers; sag and whip read `no-claim`.
- [ ] The packet crate graph does not include `frob-lifecycle` or the firmware feature (INV-FOUNDRY-07).
- [ ] A packet is written only under an `ExportGrant` from the export door: a `--packet` directory outside the session's export root is refused with FROB-REF-734 (exit 5), a design with a `research-only` asset in its lineage with FROB-REF-733 (exit 5), and a private design without the private scope and flag with FROB-REF-731 (exit 5), each with nothing written; a design whose licence set is `attribution` yields a packet with a `NOTICES` file listed in the manifest with its hash.
- [ ] A design selected by an unresolved `model-conditional` ranking is refused with FROB-REF-830 and no packet directory is written (N31ax-01's fixture), and a failed independent check blocks its part with FROB-REF-261.
- [ ] NS-20 is demonstrated by the North-Star bead NS-20 and the gate receipt is handed to the KILL-PACKET decision (N31b-19).
- [ ] Standing conditions: the code is in `frob-foundry`; its `CONTRACT.md` covers this module in the ten sections (purpose, inputs, outputs, invariants, refusals, determinism class, evidence class of outputs, validity domain, oracles, known gaps); known answers run against the hand derivations, never against stored outputs of this code; every output carries its claim product and the no-authorization flags; the computation is CPU-only and claims no device path; the gate row carries measured values with commit, hardware fingerprint and seed.
- [ ] Cancellation of an export job (request, drain, finalize) leaves no packet and no temporary directory.

## Test plan

### Unit tests
`cargo test -p frob-foundry packet`:
- `flag_type_has_one_value`: serialization gives four `false` fields; deserializing `true` or a missing field fails with FROB-REF-860.

`scripts/e2e/foundry_export_packet.sh`. This is the script of bead N31a-57, which depends on this bead and

exploratory record among the inputs"), `frob foundry export --fixture quad-ref-final-exploratory --packet

directory exists. Step (5) covers only the `--exploratory` flag; step (7) covers the label on an input. Logs per STD-E2E to

### Known answers and negative controls
KA-746 (voltage drop; control: halving the area doubles the drop). KA-747 (cable slack 36 mm; supplied
control: halving the offset halves the slack). KA-744 (tube mass properties) through `mass.json`.
Counterexample CX-341 (two-finger bus). Metamorphic: writing the same inputs twice gives the same address;
renaming the output directory does not change the manifest. Determinism: the packet's bytes are identical
across two runs and across the two reference machines.

## Considerations

- KILL-PACKET (decided at M5): the geometry or packet gate fails after one repair cycle. Fallback: parts list, mass properties and STL only; STEP and the harness are deferred.
- OPEN-FOUNDRY-2 (catalogue and price data, under what licence): default, card references and no prices. OPEN-FOUNDRY-3 (which current-capacity table governs conductor sizing): default, current density against a limit declared on the cable card, with no capacity claim.
- The safety chapter defines a general code (816) for artifacts with missing or true flags and the certificates chapter one for bundles in the auditor (833); packets report 860. A reader treats any of them as foreign or tampered.
- A packet whose governing load case is `model-conditional` prints the label on the structural margin; it supports nothing stronger than Estimated.
- The offline auditor has no dependencies and reads only certificate bundles, so the packet's flags and hashes reach it through a bundle that embeds the manifest (N31b-44).
- Human review, a machine-shop quotation and a first-article inspection are import lanes; until one is imported `review` reads `no-claim`.
- `exploratory` in the manifest (DESIGN, for the owner to confirm). The plan says an exploratory run "cannot enter a build packet" and also prints a manifest with an `exploratory` field and a `qualification` that may be null. Two readings were drafted: a labelled exploratory packet (`exploratory: true`, `qualification: null`) that readers do not treat as a build packet, and the stricter one adopted here and in N31a-03, N31a-36 and N31a-43, in which no such packet is ever written and the two fields exist only to be asserted. The stricter reading is the fail-closed one and holds until the owner decides otherwise; if the other is chosen, this bead's admission rule, the type in N31a-36 and the auditor's two reasons in N31b-44 change together.
