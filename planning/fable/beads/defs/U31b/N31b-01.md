## Background

Foundry (structure, manufacture, lifecycle) writes artifacts that leave the tool: load cases, checked
geometry, a build packet. The chapter states seven invariants that must hold for every such artifact,
whatever path produced it. An invariant differs from a gate: a gate is measured once on fixtures and recorded;
an invariant is a property that every run must keep, so it is tested by properties over generated inputs and
by a planted violation that the test must catch.

Each invariant is also named in the test plan of the mechanism bead that enforces it. This bead exists so that
the seven are tested together, against one generated corpus, by code that did not write the mechanisms, and so
that a later refactor of one mechanism cannot silently drop its invariant. Tier: the invariants guard Frontier
mechanisms; the battery itself is ordinary test code.

## Scope

In: seven property tests with generators; nine planted violations; the compile-time checks for the flag type
and the evidence class; registration of the violations as negative controls under BD-025's rules.
Out: the mechanisms (BD-400, BD-402, BD-407, BD-408); the `xtask` rule that enforces INV-FOUNDRY-07
(N31b-03), which this battery only invokes; proof obligations (N31b-02).

## Technical approach

File layout (DESIGN): `crates/frob-foundry/tests/invariants.rs` for properties that need only the crate, and
`crates/frob-conformance/tests/foundry_invariants.rs` for those that drive verbs. Generators are seeded and
the seed is printed on failure.

| ID | Statement | Property tested | Planted violation that must be caught |
|---|---|---|---|
| INV-FOUNDRY-01 | Every exported artifact carries the no-authorization flags, all false | The flag type has exactly one value; for 1,000 generated packets and geometry-only exports every manifest, every view header and every envelope has the four fields `execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`, `fabrication_released`, each `false`. A mutated packet (one flag `true`; one flag removed) is rejected by the reader and by the offline auditor with FROB-REF-860 | A writer build that emits three flags; a hand-edited manifest with `fabrication_released: true` |
| INV-FOUNDRY-02 | A load case is a single instant of a single episode at a recorded world address | For every envelope case of generated campaigns: all ports and the body field share one (world address, episode, tick); replaying that address to that tick reproduces the stored wrenches | The `assemble-peaks` mutation (per-channel maxima joined) |
| INV-FOUNDRY-03 | No geometry enters a packet without passing the independent check on a mesh the optimizer did not use | For every geometry in generated packets: the manifest cites a check record whose mesh hash exists, differs from the optimizer's grid identity, and whose verdict is pass | A packet assembled with a check record whose mesh hash is the optimizer's grid; a packet with a geometry and no record |
| INV-FOUNDRY-04 | Mass properties in the packet equal those of the model the evidence was computed with | `mass.json`, the model identified by the manifest's `ModelId`, and values recomputed from each exported geometry file agree within 10⁻⁶ relative for mass, centre of mass and inertia | A packet whose `ModelId` is that of the previous loop iteration |
| INV-FOUNDRY-05 | A packet is written whole or not at all | For every file boundary of generated packets, a writer killed at that boundary leaves no `.fbuild` directory; a completed write leaves exactly one whose address is its manifest hash | A writer that renames before writing the manifest |
| INV-FOUNDRY-06 | Foundry and lifecycle results are at most class Estimated, except instance certificates of firmware export | Type level: Foundry result types take their evidence from one constructor whose class is capped at Estimated; a `compile_fail` test shows a Foundry result cannot be built with class Tested, Certified or Proved. Run time: for every Foundry verb's envelope over the fixture set, `evidence.class` is `Estimated` or weaker, except overflow certificates, which are `Certified` | A verb build that reports a structural margin as `Tested` |
| INV-FOUNDRY-07 | The build packet does not depend on `frob-lifecycle` or on the firmware feature | The crate graph of the packet path, built with default features, contains neither `frob-lifecycle` nor any item gated by the Cargo feature `moonshot-firmware-export`; a packet written by a default build is byte-identical to one written by a build with both features on and unused | A `Cargo.toml` edit that makes the packet module import `frob-lifecycle` |

**Registration (BD-025's rules; one plant has one record).** The table holds nine planted violations: two
each for INV-FOUNDRY-01 and -03, one for each other invariant. The plant of INV-FOUNDRY-02, the
`assemble-peaks` mutation, is the plant `BD-400:assemble-peaks` of the catalogue entry CX-336 (N31-CX), whose
record the seeding tool of N38b-05 issues: this battery lists that record and writes no second one. For the
six plants of INV-FOUNDRY-01, -03, -04 and -05 this bead appends a record to
`crates/frob-conformance/registry/controls.toml` (the negative-control registry and its runner, N38b-04) at the
next free `NC-` number, with `seed = "INV-FOUNDRY-0N"`, kind `mutation` or `planted-input`, the target module,
`defect`, `expect` (the observable) and `gate`, the gate whose test checks the invariant (INV-FOUNDRY-01, -03
and -05: GATE-FOUNDRY-10; INV-FOUNDRY-04: GATE-FOUNDRY-09), the rule's row of `registry/rule_gates.toml`
through which N38b-05's join resolves the seed, added here where the file lacks it. INV-FOUNDRY-06 and -07 are
checked by no gate of the register (N31b-12), and the loader refuses a record with no gate (`no-gate`): their
plants are negative controls of this battery's own tests (the planted verb build and the `compile_fail`
companion of `inv_foundry_06_class_capped`; for -07 the planted manifest edit, the fixture of N31b-03's
`r1_planted_edge_fails`), named in the receipt with no record. A mutation this bead registers is a
`cfg(feature = "nc-<nnnn>")` branch at its target site, named after its control as BD-025 admits for a record
its bead registers, compiled only with `--features gauntlet-mutations,<crate>/nc-<nnnn>`; such a build under
the release profile is a compile error, and the runner's `caught`, `missed` or `stale` outcome is what the
acceptance below reads.

**Features built later.** `foundry.lifecycle` (the crate `frob-lifecycle`, linked by the verb layer under the
Cargo feature `moonshot-lifecycle`, M6, Moonshot) and firmware export (the Cargo feature
`moonshot-firmware-export` of `frob-foundry`, M8, Moonshot) do not exist at this bead's milestone; `lifecycle`
and `firmware-export` are their names at the user surface only (N31a-01 step 1). Until they are built,
INV-FOUNDRY-06's run-time check asserts that the default binary answers `foundry.lifecycle` with FROB-REF-724
(status `not-in-build`, exit 5; N31a-50) and `foundry.export --with-firmware` with the feature-absent refusal
(exit 5), and INV-FOUNDRY-07's byte-identity clause compares a default build with a build whose feature list
names the two Cargo features as declared but empty; the full checks
switch on automatically when the features compile (the test reads `frob capabilities --json`), and the gate
scripts of those epics (N31a-58, N31a-59) re-run this battery.

**What a failure prints.** The invariant identifier, the generator seed, the artifact address, the first
offending field or file and both values.

## Acceptance criteria

- [ ] Seven property tests exist, one per invariant, each naming its identifier in the test name and the failure message.
- [ ] Each of the nine planted violations is caught by its test: for the seven with a record (CX-336's seeded record and the six this bead appends, each with a gate that exists in `registries/gates.toml`) the control runner reports `caught` with the stated observable in the receipt; for INV-FOUNDRY-06 and -07 the battery's own negative-control test fails as stated. This bead writes no `last_seen` (the recorder N38b-19 writes it from a gate receipt).
- [ ] INV-FOUNDRY-01: no constructor, setter or deserializer of the flag type yields `true` (source scan plus `compile_fail` test); absence of a flag is rejected, not read as false.
- [ ] INV-FOUNDRY-05 is exercised at every file boundary of at least three packets of different file counts.
- [ ] INV-FOUNDRY-06 holds for all seven Foundry verbs on the fixture set; the only `Certified` values are overflow certificates. Before the `lifecycle` and `firmware-export` features exist, their verbs return the feature-absent refusal (exit 5) and the test says which clauses were checked.
- [ ] The battery runs under `cargo test` in under ten minutes on the reference host (TARGET), with the long property counts behind an environment switch.

## Test plan

### Unit tests
`cargo test -p frob-foundry --test invariants` and `cargo test -p frob-conformance --test foundry_invariants`:
`inv_foundry_01_flags_all_false`, `inv_foundry_01_mutated_packet_rejected`, `inv_foundry_02_case_is_one_sample`,
`inv_foundry_02_case_replays`, `inv_foundry_03_mesh_hash_cited`, `inv_foundry_04_mass_identity`,
`inv_foundry_05_kill_at_every_boundary`, `inv_foundry_06_class_capped` (with its `compile_fail` companion),
`inv_foundry_07_firewall`. Expected values: four flags; relative mass difference at most 10⁻⁶; zero packets
left after any kill; zero forbidden crates in the graph.

### End-to-end script and logging
`scripts/e2e/foundry_invariants.sh`: runs both test targets, then repeats the verb-level checks from the
user's side on one real packet: `frob foundry export <qualified fixture design> --packet <scratch> --key
"$(e2e_key inv-export)" --json` (a `run` verb, so it carries a key written with STD-E2E's `e2e_key`), `frob-verify --packet` on it (the auditor's directory
mode, N31b-44), a flag mutation, a kill harness run, and `cargo xtask check-deps`. Logs per STD-E2E to
`target/e2e-logs/foundry_invariants/<utc-timestamp>.ndjson` with a transcript: every line has `ts`, `script`,
`bead` (`N31b-01`), `step`, `event`, the exact command line, exit code and wall time; per invariant an
`event: assert` with the identifier, the generator seed, the count of generated cases, the planted violation's
id and its runner outcome; the evidence block of each verb call; on a failure the invariant, the seed, the
artifact address, the first offending field or file with both values, and the command to reproduce. The
`summary` lists seven invariants passed, nine planted violations caught (seven through the runner, two in the
battery's tests), and the clauses skipped because a feature is not built.

### Known answers and negative controls
Known values: the four flag names; tolerance 10⁻⁶; the tube fixture's 0.0950 kg for INV-FOUNDRY-04. Negative
controls: the seven planted violations above. Metamorphic: every invariant is unchanged by re-running the
export, by renaming the output directory and by changing worker counts. Determinism: with a fixed generator
seed the battery's inputs and results are identical on every machine.

## Considerations

- INV-FOUNDRY-06's exception is narrow: an overflow certificate is `Certified` because an independent checker replays it; the quantization effect measured beside it is `Tested`, and nothing structural rises above Estimated.
- INV-FOUNDRY-03's independence is of mesh and formulation, not of codebase; if the same-family fallback of the open meshing question is in force, the record says `check: same-family` and the invariant test accepts that label and no other substitute.
- INV-FOUNDRY-02 needs replay on the backend that produced the case; on another backend it is a tolerance comparison and is reported as such.
- The battery must not share helper code with the mechanisms for computing hashes or mass properties; it recomputes them independently.
