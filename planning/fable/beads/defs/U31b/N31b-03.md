## Background

Foundry has a Frontier core (structure loop, manufacturability, tolerances, export, the build packet) and two
Moonshots: firmware export and lifecycle compression. Decision ADR-FOUNDRY-12 keeps the Moonshots behind
features `firmware-export` and `lifecycle`, the latter in its own crate `frob-lifecycle`, so that they stay
off the critical path and out of the build packet's dependency graph. Invariant INV-FOUNDRY-07 states the
consequence: the build packet does not depend on `frob-lifecycle` or on the firmware feature, tested by a
dependency firewall in `xtask`.

Why a mechanical firewall and not a convention: a Moonshot that fails its pilot is deleted (the workspace
rule for `frob-lifecycle` is deletion, not absorption). Deletion is only free if nothing on the packet path
imports it. An accidental import (a shared helper, a convenience re-export) is exactly the kind of edge that
appears during ordinary work and is found only when the crate is removed.

The workspace's layering rule already forbids `frob-foundry` from depending on `frob-lifecycle` (both are in
layer 5 and `frob-foundry` is the earlier row, and a crate depends only on lower crates). This bead adds what
that rule does not cover: the feature boundary inside `frob-foundry`, and the surfaces above both crates.

## Scope

In: the firewall rules in `xtask check-deps`; the feature layout of `frob-foundry` and `frob-lifecycle`; the
byte-identity test of packets across feature sets; the planted violation.
Out: the packet (BD-408); the Moonshot mechanisms (BD-423, BD-438); the other `xtask` checks.

## Technical approach

**1. Feature layout** (DESIGN). In `crates/frob-foundry/Cargo.toml`: default features are empty of
Moonshots; `structure` enables the airlock's structural group; the firmware exporter lives in the module
`frob-foundry::firmware` compiled only under the firmware feature. Cargo feature names follow the workspace
rule for tiers of ambition: `moonshot-firmware-export` in `frob-foundry` and `moonshot-lifecycle` in the
surface crates that expose `foundry.lifecycle`; the chapter's short names (`firmware-export`, `lifecycle`)
remain the names used in documentation, in the verb flag `--with-firmware` and in refusal messages. No default
build enables either. `frob-lifecycle` is linked only by the verb layer, under its feature.

**2. Rules added to `check-deps`** (data in the existing rule file; no new subcommand).
- R1 *forbidden edge*: no path in the normal dependency graph from `frob-foundry` (any feature set) to
  `frob-lifecycle`.
- R2 *forbidden edge under default features*: the default-feature graph of `frob-foundry`, `frob-verbs` and
  `frob-cli` contains no FrankenLean crate and no `frob-lifecycle`.
- R3 *forbidden configuration in a path*: no file under `crates/frob-foundry/src/packet/` or `src/export/`
  contains a `cfg` on the firmware feature. The packet writer reaches the firmware exporter only through one
  optional hook, `PacketExtension`, defined in `packet/` and implemented in `firmware/`; with the feature off
  the hook list is empty.
- R4 *no reverse import*: `frob-lifecycle` may depend on `frob-foundry`'s public structural types (damage
  counting, gauges), never on `packet` or `export` internals (checked by the list of imported paths).
Each rule failure prints the offending edge or file and line.

**3. Byte identity across feature sets.** A packet written for a fixture design by a default build equals,
byte for byte and therefore in address, the packet written by a build with both Moonshot features enabled and
`--with-firmware` not passed. With `--with-firmware` the only differences are the `firmware/` directory, its
entries in the manifest's file list, and hence the address.

**4. Deletion drill.** A script removes `crates/frob-lifecycle` and the firmware module from a scratch copy of
the workspace and builds and tests the packet path; it must pass unchanged. This is the practical meaning of
the invariant.

## Acceptance criteria

- [ ] `cargo xtask check-deps` enforces R1 to R4 and still has six subcommands in `xtask`.
- [ ] A planted import of `frob_lifecycle` in `frob-foundry::packet` fails R1 with the edge named; a planted `cfg` on the firmware feature inside `packet/` fails R3 with file and line.
- [ ] Packets from a default build and from an all-features build (without `--with-firmware`) have the same address on the fixture design.
- [ ] The deletion drill passes: the packet path builds and its tests pass with both Moonshots removed.
- [ ] The Cargo feature names are confirmed by the workspace owner or the default above is recorded as the decision.

## Test plan

### Unit tests
`cargo test -p xtask deps_foundry`: `r1_no_edge_to_lifecycle` (on the real graph); `r1_planted_edge_fails` (on
a fixture manifest set under `xtask/tests/fixtures/foundry-firewall/`); `r2_default_graph_clean`;
`r3_planted_cfg_fails`; `r4_lifecycle_imports_only_public_structural_types`; `subcommand_count_is_six`.
`cargo test -p frob-foundry packet_feature_identity`: `default_and_all_features_same_address`;
`with_firmware_differs_only_in_firmware_entries`.

### End-to-end script and logging
`scripts/e2e/foundry_firewall.sh`: (1) `cargo xtask check-deps`, assert success; (2) apply the planted import
in a scratch worktree, assert failure naming the edge; (3) build `frob` twice (default; all features), run
`frob foundry export --fixture packet-min --json` with each, compare addresses; (4) run the deletion drill.
Logs per STD-E2E to `target/e2e-logs/foundry_firewall/`: rule results R1 to R4, the two packet addresses, the
drill's build and test exit codes; the summary counts rules passed and controls caught.

### Known answers and negative controls
Known answer: zero forbidden edges; equal addresses. Negative controls: the planted import (R1), a planted
default feature that enables the firmware module (R2), the planted `cfg` (R3), a planted import of
`frob_foundry::packet` internals in `frob-lifecycle` (R4). Determinism: the check reads manifests and sources
only; identical on every machine.

## Considerations

- The chapter names the features `firmware-export` and `lifecycle`; the workspace rule requires the prefix `moonshot-` for Cargo features that gate Moonshots. This bead applies the workspace rule to Cargo names and keeps the chapter's names at the user surface; the owner may decide otherwise before M5.
- R3 is a source scan and can be evaded by indirection; the byte-identity test and the deletion drill are the behavioural backstops.
- If lifecycle compression fails its pilot the crate is deleted; R1, R2 and R4 then have nothing to check and are removed with it, by an ADR.
