## Background

Firmware export is a Moonshot of Foundry: fixed-point source for joint-level controllers with overflow
certificates decided by bit-vector queries, plus test vectors that agree bit for bit with the simulator's
integer arithmetic. It is off the critical path, behind a feature, and the build packet does not depend on
it. Like every Moonshot it has a kill gate whose fallback was named before any measurement, so that ending it
costs a capability and nothing else.

KILL-FIRMWARE. Trigger: GATE-FOUNDRY-11 fails. Fallback: controller parameters, Q formats and the test-vector
manifest only; no code. Decided at M8 and recorded as an ADR. This bead is that decision.

GATE-FOUNDRY-11 (Known answer, TARGET, M8): the fixed-point cases (each planted overflow found as a
counterexample; the clamped controller certified; a widened input range breaks a certificate); 10⁶ vectors
bit-equal between the exported crate built for the host and the integer kernel.

## Scope

In: reading the gate receipt and the pilot record; the decision; the content of the fallback export;
downstream changes; the ADR; the posture until decided.
Out: the measurement (N31b-20); the pilot (N31b-10); the mechanism.

## Technical approach

1. **What is read.** From the pilot record: missed overflows (0 required) and undecided obligations within
   the budget (0 required). From the gate row: the three refusals with counterexamples; the certified export
   with replayed proof streams; the widened-range control; vectors compared and mismatches; the artifact
   scan; undecided obligations.
2. **Decision.**
   - Pilot negative: the epic was never funded; record `killed: fallback adopted` on the pilot's record and
     GATE-FOUNDRY-11 as `not run: pilot negative`.
   - Gate measured and every clause passes: KILL-FIRMWARE does not fire.
   - Any clause fails (a missed overflow, an uncertified clamped controller, a certificate that survives the
     widened range, any vector mismatch, any undecided obligation on a fixture expected to certify): it
     fires. The gate grants no repair cycle. A run voided by a harness defect is repeated once.
3. **The fallback export** (if fired). `foundry.export --with-firmware` writes into `firmware/`: the
   controller's parameters (gains, limits, clamp values) as exact rationals; the Q-format declaration of
   every input, state and intermediate from the interval range analysis, labelled Estimated-by-interval and
   not certified; the test-vector manifest (inputs and the integer kernel's outputs and states, with the
   seed); the no-authorization flags. No source code, no certificates, no statement about overflow. The
   envelope says `firmware: "parameters-only (KILL-FIRMWARE)"`.
4. **What else changes downstream if it fires.** The bit-vector query builder, the emitter and their beads
   are closed as not built or removed; the feature keeps its name and its firewall rule; the theorem card for
   overflow freedom stays in the catalogue as not exercised; the refusal code for fixed-point obligations
   stays registered and unused; the open question on the per-obligation time budget is closed as moot.
   Unaffected: the exact-integer kernel class, the energy-budget monitor in simulation, the build packet.
5. **Until decided (fail-closed default).** `--with-firmware` is refused as a capability not built; no
   artifact of this project contains controller source for a microcontroller.
6. **Record.** `docs/adr/KILL-FIRMWARE.md` with the pilot's and the gate's values, the decision, the
   fallback's content list and the downstream list; the gate rows for KILL-FIRMWARE and GATE-FOUNDRY-11;
   written by a session that did not implement the exporter.

## Acceptance criteria

- [ ] The ADR exists at M8 with each clause of the gate, or the pilot's two falsifier counts, evaluated.
- [ ] The KILL-FIRMWARE row records `pass` on the gate with the kill not fired, or `killed: fallback adopted`.
- [ ] If fired: `frob foundry export <fixture> --with-firmware --json` writes exactly parameters, Q formats, the vector manifest and the flags, and no file with source code; the packet still verifies offline.
- [ ] If not fired: exported crates are admitted into `firmware/` only with their certificate identities in the manifest.
- [ ] On both branches no text states that exported or described code is safe to run on hardware, and `timing` reads `no-claim`.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_firmware.rs`: `decision_table` (all clauses pass → not fired; one vector
mismatch in 10⁶ → fired; one undecided obligation on `pi-clamped` → fired; pilot negative → `not run` and
fallback); `fallback_file_set_has_no_source` (no `.rs`, `.c` or `.h` under `firmware/`);
`fallback_q_formats_labelled_uncertified`.

### End-to-end script and logging
`scripts/e2e/kill_firmware.sh`: reads the pilot record and the gate receipt, evaluates the rule, prints the
decision; on a fixture registry with the kill fired runs the export and lists `firmware/`. Logs per STD-E2E
to `target/e2e-logs/kill_firmware/`: the clause values, the decision, the file list; `summary` with `gates:
["KILL-FIRMWARE", "GATE-FOUNDRY-11"]`.

### Known answers and negative controls
Known answer: the decision table. Negative controls: a receipt with the mismatch count field removed
(incomplete; no decision); a fallback build that leaves a generated source file behind; an ADR claiming
certification after a fired kill gate (rejected by the claim-resolution check).

## Considerations

- The fallback still has value: a firmware engineer gets ranges, formats and vectors to test a hand-written implementation against, with the same no-authorization flags.
- A Moonshot's kill decision is one step more urgent than its work: it frees a slot under the cap on active Moonshots.
- If the sibling proof tool later gains the proof-term step, that changes the class a certificate could reach, not this decision.
