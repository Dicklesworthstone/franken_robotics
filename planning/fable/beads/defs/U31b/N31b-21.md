## Background

Firmware export is a Moonshot of Foundry: fixed-point source for joint-level controllers with overflow
certificates decided by bit-vector queries, plus test vectors that agree bit for bit with the simulator's
integer arithmetic. It is off the critical path, behind a feature, and the build packet does not depend on
it. Like every Moonshot it has a kill gate whose fallback was named before any measurement, so that ending it
costs a capability and nothing else.

KILL-FIRMWARE. Trigger: GATE-FOUNDRY-11 fails. Fallback: controller parameters, Q formats and the test-vector
manifest only; no code. Decided at M8 and recorded as an ADR. This bead is that decision.

GATE-FOUNDRY-11 (Known answer, TARGET, M8): the fixed-point cases (each planted overflow found as a
counterexample; the clamped controller certified; a widened input range breaks a certificate); 10⁶ vectors
bit-equal between the exported crate built for the host and the integer kernel.

## Scope

In: reading the gate receipt and the pilot record; the decision; the content of the fallback export;
downstream changes; the ADR; the posture until decided.
Out: the measurement (N31a-58); the pilot (N31b-10); the mechanism.

## Technical approach

1. **What is read.** From the pilot record: missed overflows (0 required) and undecided obligations within
   the budget (0 required). From the gate row: the three refusals with counterexamples; the certified export
   with replayed proof streams; the widened-range control; vectors compared and mismatches; the artifact
   scan; undecided obligations.
2. **Decision** (outcomes in N40-03's names).
   - Pilot negative, or the owner did not fund the epic: `not-reached`. The epic was never funded; the
     capability does not exist and is not described; the ADR cites the pilot's `[[pilot.result]]`, and
     GATE-FOUNDRY-11 stays `not-run`.
   - Gate measured and every clause passes: `not-fired`, citing the gate receipt.
   - Any clause fails (a missed overflow, an uncertified clamped controller, a certificate that survives the
     widened range, any vector mismatch, any undecided obligation on a fixture expected to certify):
     `fired`. The gate grants no repair cycle. A run voided by a harness defect is repeated once.
   - The gate not measured by the M8 exit although the epic was funded: `deferred`, with the later exit and
     the reason in the ADR (N40-03 rule 3).
3. **The fallback export** (if fired). This is the parameters-only output of N31a-46 (its step 6, the kill
   switch set; its manifest says `code: withheld (KILL-FIRMWARE)`). `foundry.export --with-firmware` writes
   into `firmware/`: the
   controller's parameters (gains, limits, clamp values) as exact rationals; the Q-format declaration of
   every input, state and intermediate from the interval range analysis, labelled Estimated-by-interval and
   not certified; the test-vector manifest (inputs and the integer kernel's outputs and states, with the
   seed); the no-authorization flags. No source code, no certificates, no statement about overflow. The
   envelope says `firmware: "parameters-only (KILL-FIRMWARE)"`.
4. **What else changes downstream if it fires.** The bit-vector query builder, the emitter and their beads
   are closed as not built or removed; the feature keeps its name and its firewall rule; the theorem card for
   overflow freedom stays in the catalogue as not exercised; the refusal code for fixed-point obligations
   stays registered and unused; the open question on the per-obligation time budget is closed as moot.
   Unaffected: the exact-integer kernel class, the energy-budget monitor in simulation, the build packet.
5. **Until decided (fail-closed default).** Release builds do not compile the Cargo feature
   `moonshot-firmware-export` (`firmware-export` at the user surface, N31a-01 step 1), so
   `--with-firmware` there is refused with FROB-REF-724 (exit 5; the capability is not in this build); only the
   gate's measurement build (N31a-58) has it, and no artifact of this project contains controller source for a
   microcontroller.
6. **Record.** `docs/adr/ADR-KILL-FIRMWARE-M8.md` (the decision-record path of N40-03, under `docs/adr/`)
   with the fields N40-03 requires, and also the pilot's and the gate's values, each beside its receipt hash,
   the outcome, the fallback's content list and the downstream list; written by a session that did not
   implement the exporter. The KILL-FIRMWARE row of `registries/gates.toml` (entered by the fallback ledger
   N40-27) gains `decision = {outcome, adr, date, session, receipts}`; GATE-FOUNDRY-11 keeps the row its
   measuring session recorded from N31a-58's receipt, and on `fired` its failed part takes status `killed`
   through N40-03's propagation.

## Acceptance criteria

- [ ] The ADR exists at M8 with each clause of the gate, or the pilot's two falsifier counts, evaluated.
- [ ] The KILL-FIRMWARE row holds the decision with one of `not-fired`, `fired`, `not-reached` or `deferred`, at M8; `cargo test -p frob-conformance --test kill_ledger` passes for KILL-FIRMWARE.
- [ ] If fired: `frob foundry export quad-ref-final --packet <dir> --with-firmware --controller knee-pi-clamped --key <k> --json` writes exactly parameters, Q formats, the vector manifest and the flags, and no file with source code; the packet still verifies offline.
- [ ] If not fired: exported crates are admitted into `firmware/` only with their certificate identities in the manifest.
- [ ] On both branches no text states that exported or described code is safe to run on hardware, and `timing` reads `no-claim`.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_firmware.rs`: `decision_table` (all clauses pass → `not-fired`; one vector
mismatch in 10⁶ → `fired`; one undecided obligation on `knee-pi-clamped` → `fired`; pilot negative →
`not-reached`, the gate `not-run`; no gate receipt at the exit with the epic funded → `deferred`); `fallback_file_set_has_no_source` (no `.rs`, `.c` or `.h` under `firmware/`);
`fallback_q_formats_labelled_uncertified`.

### End-to-end script and logging
`scripts/e2e/kill_firmware.sh` (sources the STD-E2E helper): reads the pilot record and the gate receipt,
evaluates the rule, prints the decision, runs `cargo test -p frob-conformance --test kill_ledger`; on a
scratch gate register with the decision `fired`, in the gate's measurement build (the only one with the
feature), runs `frob foundry export quad-ref-final --packet <export root>/kfw --with-firmware --controller
knee-pi-clamped --key $(foundry_key kfw-fallback) --json` (the `foundry.export` row's form; the fixtures are
N31a-58's; the key from the cluster preamble of N31a-51, so the fired-switch run is not answered from a stored
receipt of an unfired one), lists `firmware/` of `<export root>/kfw.fbuild` (N31a-36's naming), and runs the
offline auditor `frob-verify --packet <export root>/kfw.fbuild --json` on the result. Logs to `target/e2e-logs/kill_firmware/<utc-timestamp>.ndjson` with a
transcript: every line has `ts`, `script`, `bead` (`N31b-21`), `step`, `event`, the exact command line, exit
code and wall time; the clause values with thresholds, the receipt hashes read, the decision, the file list
against the fallback set, the auditor's verdict; on a failed assertion the unexpected file (for example a
source file) or the missing one, with the path. The `summary` carries `gates: ["KILL-FIRMWARE",
"GATE-FOUNDRY-11"]`. Exit zero when the decision is computed, whatever it is.

### Known answers and negative controls
Known answer: the decision table. Negative controls: a receipt with the mismatch count field removed
(incomplete; no decision); a fallback build that leaves a generated source file behind; an ADR claiming
certification after a fired kill gate (rejected by the claim-resolution check).

## Considerations

- The fallback still has value: a firmware engineer gets ranges, formats and vectors to test a hand-written implementation against, with the same no-authorization flags.
- A Moonshot's kill decision is one step more urgent than its work: it frees a slot under the cap on active Moonshots.
- If the sibling proof tool later gains the proof-term step, that changes the class a certificate could reach, not this decision.
