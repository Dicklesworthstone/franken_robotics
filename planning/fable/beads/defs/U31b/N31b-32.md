## Background

The packet-review protocol separates what a program can check about a build packet from what only a person
can. This bead is the program's half: a mechanical pre-review that every packet goes through before any
reviewer's time is spent on it, and the only half that a gate covers. It is a mode of the existing verb
`foundry.check`: given a packet, it runs six items, each of which passes or fails and names the offending
file.

Why these six. A reviewer's minutes are wasted, and a review's meaning is diluted, if the packet's files do
not agree with each other, if a number has no stated basis, or if the packet cites a verdict for a different
design. Those defects are exactly the kind a program finds reliably and a person finds late. What the six do
not cover is the reason human review exists. Counterexample that must be kept: a two-part bracket whose
second fastener sits behind the first part once it is mounted. Each part passes the tool-access check as a
part, the packet passes M1 to M6, and the assembly cannot be completed in the listed order. A mechanical pass
is therefore never rendered as `review: accept`. Tier: Solid [S].

## Scope

In: items M1 to M6; the result record; the wording rule; the packet mode of the verb; the unit-suspicion
diagnostic.
Out: importing a human review record (N31b-33); the offline auditor's own packet check, which this item list
calls for M1 (N31b-44); the per-part manufacturability checks (BD-405).

## Technical approach

**The items.**

| Item | Check | Detail and failure output |
|---|---|---|
| M1 | Schema, every digest, the four flags present and false | The manifest and every section validate against `frob.build/1`; BLAKE3 of every file equals the manifest's entry; the directory's address equals the manifest hash; `execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified` and `fabrication_released` are present and `false` in the manifest and in every view header. Offending: the file whose hash differs, or the location of the flag |
| M2 | Cross-export identity | Mass, centre of mass and inertia agree within 10⁻⁶ relative (TARGET) among: the model the evidence used (the manifest's `ModelId`); `mass.json`; the values recomputed from each of the four geometry exports of each made part; and the URDF and MJCF exports of the design, per link. Units are checked: each source's declared unit is read, and a ratio of volumes or masses near a power of 10³ (or of 25.4) between sources is reported as a unit suspicion with the ratio and the file |
| M3 | Referential integrity | Every joint has an actuator card; every net has two ends; every made part has its geometry files; every purchased part resolves to a card. Offending: the joint, net, part or card reference |
| M4 | Every number carries a claim class and an evidence reference that resolves in the artifact graph | For every numeric field of every section: a class (Proved, Certified, Tested, Estimated) and an evidence identifier; `evidence.trace` on it returns a closure with no dangling or tombstoned node. Offending: the field path and file |
| M5 | The cited qualification verdict is for this `DesignId` and `ModelId` | The verdict record named in the manifest names the same two identities. A verdict for the pre-optimization or pre-snap design fails. A packet with `exploratory: true` fails M5 by definition |
| M6 | Every snapped part was revalidated after the snap | For every part whose continuous optimum was snapped to a catalogue part, stock size or gear ratio: a revalidation record naming the design before and after, the hard constraints and controller checks re-run on the snapped design, and their verdicts |

**Result record** (schema `frob.prereview/1`, name DESIGN): `{ packet: manifest digest, items: [{ id, pass,
offending: [{ file, pointer, observed, required }], detail }], pass_all, review: <unchanged from the
packet's view> }`. Exit 0 when all six pass, 2 when any fails (completed with findings). The record is stored
beside the packet as a sidecar addressed by the manifest digest; it changes no byte of the packet.

**Wording rule.** The record, the envelope and every rendered view use the words "mechanical pre-review:
passed" or "failed" and never "reviewed", "accepted" or "review: accept". A schema constant fixes the
allowed strings.

**Reduced packets.** Where the packet kill gate's fallback is in force (parts list, mass properties and STL
only), M2 compares the model, `mass.json`, the STL and the robot-description exports; M3 drops the net check;
the record states `reduced: true`.

**The verb.** `frob foundry check <packet.fbuild> [--json]` (kind `run`; the packet mode is read-only with
respect to the packet). Evidence: the pre-review's own claim is Tested (a deterministic check of files).

## Acceptance criteria

- [ ] On a clean fixture packet all six items pass; the record validates; the packet's bytes and address are unchanged.
- [ ] Known answers: the tube part (0.0950 kg) is reproduced from each of its four geometry exports within 10⁻⁶; a surface file written in millimetres and read as metres is reported by M2 with the ratio 10⁹ and the file named; a packet that cites a verdict for the pre-snap design fails M5.
- [ ] Each item has a planted failure that it alone catches: one altered byte in a geometry file (M1); one flag removed (M1); a millimetre STL (M2); a net with one end (M3); a number without an evidence reference, and one whose reference dangles (M4); a stale verdict (M5); a snapped gear ratio without a revalidation record (M6).
- [ ] The bracket fixture with the enclosed fastener passes M1 to M6, and the record still reads `review: no-claim`.
- [ ] No output string of the pre-review contains "reviewed" or "accept" (schema constant and a scan of the rendered views).
- [ ] The planted unit error and the planted stale verdict are each caught in 100 of 100 randomized placements (different parts, files and positions), as the gate requires.

## Test plan

### Unit tests
`cargo test -p frob-foundry prereview`: `m1_hash_mismatch_names_file`; `m1_flag_absent_fails`;
`m2_tube_identity_four_exports` (relative differences at most 10⁻⁶); `m2_unit_suspicion_1e9` (ratio reported
as 1.000 × 10⁹ with the STL's path); `m2_inch_suspicion` (ratio 25.4³ = 16,387.064 reported);
`m2_urdf_mjcf_per_link_identity`; `m3_net_one_end`; `m3_joint_without_card`; `m4_number_without_evidence`;
`m4_dangling_reference`; `m5_stale_verdict_fails`; `m5_exploratory_fails`; `m6_snap_without_revalidation`;
`bracket_passes_mechanically_and_review_stays_no_claim`; `wording_constants`.

### End-to-end script and logging
`scripts/e2e/foundry_prereview.sh`: `frob foundry check <clean packet> --json` (exit 0); then each planted
failure in a copy (exit 2, the expected item fails, the offending file is the planted one); then the
100-placement loops for the unit error and the stale verdict. Logs per STD-E2E to
`target/e2e-logs/foundry_prereview/`: per run the packet digest, the six item results, offending files;
metrics `mass_rel_diff_max` (1e-6), `unit_error_caught` (100 of 100), `stale_verdict_caught` (100 of 100);
digests of the packet before and after; the summary names GATE-FOUNDRY-13.

### Known answers and negative controls
The three known answers of the subsection (tube; 10⁹; pre-snap verdict). The counterexample "a mechanical
pass is not a review". Negative controls: the eight planted failures above; a renderer that prints `review:
accept` after six passes (rejected by the schema constant). Metamorphic: renaming or moving the packet
directory changes no item's result; re-running the pre-review gives the same record digest. Determinism:
exact for M1 and M3 to M6; M2 recomputes mass properties in double precision with a fixed summation order and
is identical across machines.

## Considerations

- M2's tolerance is tight for single-precision formats; it relies on the export rule that parts are written about their centroids.
- M4 can only check that an evidence reference resolves, not that the evidence is good; it is a check against naked numbers.
- The pre-review deliberately has no manufacturability item: per-part process checks are in `fab.json` with their own status, and assembly-level producibility is the reviewer's rubric item.
- The six items are fixed by number; adding one later is a new item number, never a change to the meaning of an existing one.
