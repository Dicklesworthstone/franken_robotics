## Background

The program has an offline auditor, `frob-verify`: a single binary built from the Rust standard library and
nothing else, living in the crate `frob-cert`, which has an empty dependency table and its own stable
toolchain file. It re-checks certificate bundles (`.frobcert`) independently of the code that produced them,
and it checks that every exported artifact carries the no-authorization flags, all false. It can check an
artifact on a machine that has neither the agent, nor a GPU, nor the rest of the workspace. Its independence
is the point: the code that wrote an artifact is not the code that accepts it, and a claim that only its
producer can check is not checked.

Build packets carry a fourth flag, `fabrication_released`, beside the three general ones
(`execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`). The packet gate
(GATE-FOUNDRY-10) says so in two clauses: "flags present and false" and "a mutated flag rejected by
`frob-verify`"; the packet invariant says a mutated packet is rejected by reader and auditor (FROB-REF-860).
But a workspace rule says that the auditor reads only certificate bundles and never another crate's format:
a bundle embeds the canonical bytes and hashes of the statements it is about, so the auditor never needs
another reader. This bead reconciles the two: the packet writer emits a small bundle that embeds the
manifest's canonical bytes, and the auditor gains one checker for it.

Two designs were drafted for this work and they are merged here. The other (bead N31a-38, superseded by this
one) gave the auditor a native reader of the packet directory, which parses `manifest.json` and every section
file inside `frob-cert`. It is rejected because it breaks the rule above (DESIGN: the rule is the format
registry's first, "one owner": only `frob-foundry` parses packet bytes). Everything that draft checked is
kept: what the auditor needs from a section file is embedded in the bundle by the writer, so the auditor still
reads one format. The reader in `frob-foundry` (bead N31a-36) and this checker test overlapping things on
purpose and share no code: the packet rules are implemented a second time, from the schema, in the auditor.

Tier: the auditor is Solid infrastructure; this checker serves a Frontier artifact and is listed under the
packet work package, which names `frob-cert` among its crates.

## Scope

In: the record kind and its bundle layout; the checker; the directory mode that recomputes file hashes; the
rejection reasons and the refusal mapping; the report format; specimens and the registered mutations; the
auditor's command line for packets; the proof that the binary's dependency list is unchanged.
Out: writing the bundle (the packet container N31a-36 writes `certs/packet.frobcert` with the bundle writer of
the certificates crate, and depends on this bead for the kind's layout); the in-workspace reader (N31a-36);
the flag type (N31a-37); cross-consistency of the packet's content, which needs the model and is done by the
assembler (N31a-43) and by the mechanical pre-review (N31b-32); verification of each other certificate kind
(the Lemma units). This bead does not depend on the container: its specimens are hand-built `synthetic`
bundles, and the differential test against real packets runs from the workspace side once N31a-36 exists.

## Technical approach

**1. Record kind** (DESIGN name `packet-manifest`, version 1, added to the closed registry of kinds by a
registry revision). A bundle of this kind states: "the build packet with manifest digest D has these
canonical manifest bytes; its four no-authorization flags are present and false; its files have these
BLAKE3 hashes and sizes; its section files carry these headers; its made parts were checked on these meshes".
Layout: `{ kind: "packet-manifest/1", schema: "frob.build/1", manifest_bytes (canonical JSON, embedded
verbatim), manifest_digest, files: [(relative path, blake3, size)], section_headers: [(path, header bytes)],
check_meshes: [(part, check_mesh_blake3, optimizer_grid_blake3)], flags: the three general flags of every
bundle, all false }`. `section_headers` embeds verbatim the canonical bytes of each JSON section's header
object (its `design`, `model` and four flags); `check_meshes` copies, for every made part, the two hashes
recorded in its structural evidence. The packet stores the bundle as `certs/packet.frobcert`. Its own bytes
are excluded from the manifest's file list to avoid a cycle; the bundle is covered by its own bundle digest,
which the envelope of `foundry.export` reports.

**2. The checker** (`crates/frob-cert/src/packet.rs`; standard library only; reuses the auditor's canonical
JSON reader and BLAKE3). In order:
1. Parse the embedded manifest bytes as canonical JSON; re-serialize; the bytes must be identical
   (non-canonical input is rejected).
2. `schema` is `frob.build/1`; an unknown schema version is a rejection, not a best effort.
3. The object `authorization` has exactly the four keys `execution_authorized`, `hardware_safety_signoff`,
   `sim_to_real_certified`, `fabrication_released`, each the JSON literal `false`. A missing key, an extra
   key, `true`, `null`, a string or a number rejects. Absence is not read as false.
4. `exploratory` is `false`; `reality` and `review` are the string `no-claim` (a review import changes a
   manifest view kept in a sidecar and never these bytes: N31b-33); `units` is `"SI"`; `selection.status` is
   present and is one of `model-robust` or `none-recorded` (the prototype-spend record of N31ax-01, which adds
   this rule to the checker and its specimens; absent, or any other value such as `model-conditional`,
   rejects with the reason `selection-status`).
5. `qualification` is a verdict identifier, not null: a packet for a design with no qualification verdict
   should not exist, and null is rejected with the reason `no-verdict`.
6. BLAKE3 of the embedded bytes under the domain string `frob.build/1` equals `manifest_digest`, and that
   digest is the packet identity the report prints.
7. The bundle's file list equals the manifest's file list; every path is relative and normalized (no `..`,
   no leading slash).
8. Every embedded section header names the manifest's `design` and `model` and has the four flags false.
9. For every made part the check-mesh hash is present and differs from the optimizer-grid hash recorded
   beside it (the offline-checkable half of INV-FOUNDRY-03: the optimizer never checks its own result).
10. The bundle's own three flags are present and false (the general rule for every bundle).
Outcome `accept`, or `reject` with the first failing step, the path and the expected and observed values.

**3. Directory mode.** `frob-verify --packet <dir> [--json]` (DESIGN; the superseded draft spelled it
`frob-verify packet <dir>`, and that spelling is not used) locates `certs/packet.frobcert`, runs the checker,
then reads each listed file as raw bytes and compares its size and BLAKE3 with the list; checks that the
directory's `manifest.json` bytes equal the embedded bytes; checks that each section file's leading header
bytes equal the embedded header (a byte comparison of a prefix, not a parse); and checks that no file is
present that the manifest does not list (other than the bundle itself and review sidecars stored outside the
packet). It runs the ordinary checkers on every other bundle under `certs/`, each under its own proof kind,
and requires every certificate that the manifest's file table lists to be present. It parses no geometry and
no section file. Exit: 0 accepted; 3 rejected with a reason list; 9 if the directory cannot be read (the
auditor's own convention, independent of the main binary's exit table). Output: packet identity, schema,
design and model identities, the file table with pass or fail per file, the flag check, the certificate
checks, and a one-line verdict.

**4. Reasons and refusal mapping.** Each rejection carries a stable reason token (`flag-true`, `flag-missing`,
`flag-not-literal`, `flag-extra-key`, `hash-mismatch`, `size-mismatch`, `unlisted-file`, `missing-file`,
`schema-unknown`, `not-canonical`, `digest-mismatch`, `exploratory`, `no-verdict`, `selection-status`,
`section-identity-mismatch`, `cert-rejected`, `mesh-hash-missing`, `mesh-hash-not-independent`,
`path-not-normalized`), the path, and expected and observed values. A flag failure in the embedded packet
manifest or in a section header is reported with the packet's code FROB-REF-860 (an export without the
flags, or any attempt to produce a true flag); a failure of the bundle's own three flags is reported with the
auditor's existing code for bundles (FROB-REF-833); other artifacts keep the general code (FROB-REF-816). The
output names which.

**5. Specimens and mutations** (the certificates chapter requires, for every kind in use, one specimen the
auditor accepts and at least three mutations it rejects; specimens under
`crates/frob-cert/tests/specimens/packet/`, each rejected one derived from the accepted one by a recorded
edit): each of the four flags set to `true` (four specimens); `fabrication_released` removed;
`execution_authorized: "false"` (a string); an extra key `authorization.override`; one file hash altered; the
manifest digest altered; one byte of whitespace added to the embedded manifest; the manifest re-ordered
(non-canonical); an unknown schema `frob.build/2`; `exploratory: true`; `qualification: null`;
`selection.status` removed, and set to `model-conditional` (beside the two accepted specimens with
`selection.status` `model-robust` and `none-recorded`; N31ax-01); a section
header naming another model; a check-mesh hash removed, and one equal to the grid hash; a path `../x`. In
directory mode: one byte changed in each kind of file (geometry, a JSON section, a certificate); a file
added; a file removed; `manifest.json` edited without the bundle; a certificate replaced by one for another
statement with a consistent hash in the manifest.

**6. What the auditor does not check, stated in its output.** That the mass properties match the geometry,
that nets have two ends, that the verdict is for this design: these need the workspace and are checked by
`foundry.check <packet>`. The auditor prints `content cross-consistency: not checked offline`.

**7. Dependency proof.** The test that lists the auditor binary's dependencies (already part of the auditor's
own gate) is re-run with the packet module compiled in and must still list the standard library only.

**8. Reproducibility and determinism.** Re-serializing the bundle with the auditor gives identical bytes (the
auditor's round-trip obligation for every bundle). The check is a pure function of the directory's bytes,
with identical output on every platform.

## Acceptance criteria

- [ ] GATE-FOUNDRY-10, auditor clause: `frob-verify certs/packet.frobcert` accepts the specimen; each of the four flag-true specimens is rejected with FROB-REF-860 and reason `flag-true`, naming the flag; the flag-removed and flag-as-string specimens are rejected with FROB-REF-860.
- [ ] Every other registered mutation is rejected with its reason token and the failing step named (100% of the specimen set).
- [ ] `frob-verify --packet <dir>` accepts the specimen packet directory; rejects it after one byte of any listed file is changed, after `manifest.json` is edited without the bundle, after a file is removed and after an unlisted file is added.
- [ ] `frob-cert` still has an empty dependency table with the packet module included, and builds with its own stable toolchain from an empty environment on a machine with no GPU; `frob-verify --packet` runs on a machine with only the binary and the packet directory.
- [ ] The kind is in the registry of proof kinds at a new registry version, and an older auditor rejects it as unknown (it does not ignore it).
- [ ] Re-serialization of the bundle is byte-identical.
- [ ] The output names what is not checked offline.
- [ ] The specimen set is published in the form the differential test of the in-workspace reader iterates over (that test, in which reader and auditor must agree on every specimen, is an acceptance criterion of N31a-36, which depends on this bead).

## Test plan

### Unit tests
`cargo test -p frob-cert packet_manifest` (specimens labelled `synthetic`):
- `specimen_accepted`; `flag_true_rejected_860` × 4; `flag_absent_rejected_860`; `flag_string_false_rejected_860`; `extra_authorization_key_rejected`.
- `file_hash_mismatch_rejected`; `manifest_digest_mismatch_rejected`; `non_canonical_manifest_rejected`; `unknown_schema_rejected`.
- `exploratory_true_rejected`; `null_verdict_rejected`; `section_identity_mismatch_rejected`; `path_traversal_rejected`.
- `selection_status_rule` (added with N31ax-01): `model-robust` and `none-recorded` accepted; absent and `model-conditional` rejected with reason `selection-status`, naming the field.
- `mesh_hash_missing_rejected`; `mesh_hash_equal_to_grid_hash_rejected`.
- `identity_is_blake3_of_manifest`; `bundle_own_flags_checked_833`; `roundtrip_bytes_identical`.
- Directory mode: `byte_flip_in_geometry_rejected`; `byte_flip_in_section_rejected`; `byte_flip_in_cert_rejected`; `unlisted_file_rejected`; `missing_file_rejected`; `manifest_edited_without_bundle_rejected`; `swapped_certificate_rejected` (consistent hashes, wrong statement).
- `dependency_table_empty` (reads `Cargo.toml`); `binary_lists_std_only`.
- Differential (in the workspace, `cargo test -p frob-foundry --test verify_differential`; run and required by N31a-36, listed here because it iterates over this bead's specimens): for every specimen, `BuildPacket::open` and `frob-verify --packet` give the same verdict.
- Planted defects, each caught: `accept-flag-absent` (treats a missing flag as false; the absent-flag mutation must expose it); `compare-flags-case-folded` (compares flags after lower-casing strings; the string mutation must expose it); `hash-only-listed-files` (ignores extra files); `skip-unopenable-files` (a deleted file must be a rejection, not a skip); `verify-links-frob-foundry` (the dependency test fails).

### End-to-end script and logging
`scripts/e2e/frob_verify_packet.sh`: builds `frob-verify` from an empty environment; assembles the specimen
packet directory from the specimen set (a `synthetic` packet built by the test kit, so that this bead does not
wait for the packet writer, which depends on it); copies the binary and the packet into an empty directory and runs
`frob-verify --packet` there with a cleared environment; applies each mutation to a copy and asserts
rejection with the expected step and reason; runs the previous release of the auditor (where one exists) and
asserts it rejects the kind as unknown; runs the five planted defects through the negative-control runner.
It sources the STD-E2E helper and logs to `target/e2e-logs/frob_verify_packet/<utc-timestamp>.ndjson` with a
transcript: every line has `ts`, `script`, `bead` (`N31b-44`), `step`, `event`, the exact command line, exit
code and wall time; the packet address and bundle digest; the binary's hash; per mutation its name, the
auditor's outcome, failing step, reason token and code; `mutations_rejected` against the size of the set; the
build's dependency listing (empty); per planted defect its id and outcome; on an unexpected outcome the
mutation, the expected and observed step and reason and the path of the mutated copy to repeat it. The
summary names GATE-FOUNDRY-10 (its auditor clause). The export script of bead N31a-57 runs the accept case
and the flag and byte-flip mutations again on a packet written by `frob foundry export`, as part of the packet
gate; that run on a real packet is where the gate's auditor clause is recorded.

### Known answers and negative controls
The specimen set is the known-answer set: four flag names; one accept; the rest reject with named reasons.
Negative controls: the five planted defects. Determinism: exact; outputs are compared byte for byte across
the platforms the auditor builds on.

## Considerations

- Three codes concern flags: the auditor's code for bundles, the safety chapter's code for artifacts in general, and Foundry's code for packets. This bead maps each to its artifact kind; the owners of the registry may prefer to fold them, and the checker's output is written so that folding changes a number and nothing else.
- The auditor proves nothing about a packet's content. It shows that the bytes are the ones the manifest names and that no flag claims an authorization. Everything else is the pre-review's and the reviewer's.
- Embedding the manifest and the section headers in a bundle duplicates a few kilobytes; the alternative (teaching the auditor to read packet directories natively) would break the rule that keeps it free of other crates' formats.
- Two implementations of the same rules can drift. The differential test is the guard, and a change to the packet schema is not complete until the reader, this checker and the specimens are updated.
- The auditor rejects an unknown schema version outright. A future `frob.build/2` needs a new auditor build; that is the intended coupling for an artifact people may act on.
- The recurring flags gate of the safety chapter (GATE-SAFE-01) re-runs the flag mutations at every milestone exit; this bead's specimens are registered there.
- If the packet kill gate's fallback is in force, the reduced packet (manifest `profile: "reduced"`, the `Reduced` profile of N31a-36; N31b-19) has the same manifest schema and the same bundle and is audited by the same rules with fewer files; the checker is unchanged.
- The registry revision that admits the kind `packet-manifest` belongs to the certificates owner; until it is recorded the kind is carried on a branch of the registry and this bead cannot close.
