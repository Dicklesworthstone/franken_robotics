## Background

The program has an offline auditor, `frob-verify`: a single binary built from the Rust standard library and
nothing else, living in the crate `frob-cert`, which has an empty dependency table and its own stable
toolchain file. It re-checks certificate bundles (`.frobcert`) independently of the code that produced them,
and it checks that every exported artifact carries the no-authorization flags, all false. Its independence
is the point: a claim that only its producer can check is not checked.

Build packets carry a fourth flag, `fabrication_released`, beside the three general ones
(`execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`). The packet gate requires that
"a mutated flag is rejected by `frob-verify`", and the packet invariant says a mutated packet is rejected by
reader and auditor. But a workspace rule says that the auditor reads only certificate bundles and never
another crate's format: a bundle embeds the canonical bytes and hashes of the statements it is about, so the
auditor never needs another reader. This bead reconciles the two: the packet writer emits a small bundle
that embeds the manifest's canonical bytes, and the auditor gains one checker for it.

Tier: the auditor is Solid infrastructure; this checker serves a Frontier artifact and is listed under the
packet work package, which names `frob-cert` among its crates.

## Scope

In: the record kind and its bundle layout; the checker; the directory mode that recomputes file hashes; the
refusal mapping; specimens and mutations; the auditor's command line for packets.
Out: writing the bundle (the packet writer, BD-408, uses the bundle writer of the certificates crate);
semantic checks of packet content (the mechanical pre-review, N31b-32).

## Technical approach

**1. Record kind** (DESIGN name `packet-manifest`, version 1, added to the closed registry of kinds by a
registry revision). A bundle of this kind states: "the build packet with manifest digest D has these
canonical manifest bytes; its four no-authorization flags are present and false; its files have these
BLAKE3 hashes". Layout: `{ kind: "packet-manifest/1", schema: "frob.build/1", manifest_bytes (canonical
JSON, embedded verbatim), manifest_digest, files: [(relative path, blake3)], flags: the three general flags
of every bundle, all false }`. The packet stores it as `certs/packet.frobcert`. Its own bytes are excluded
from the manifest's file list to avoid a cycle; the bundle is covered by its own bundle digest, which the
envelope of `foundry.export` reports.

**2. The checker** (standard library only; reuses the auditor's canonical JSON reader and BLAKE3). In order:
1. Parse the embedded manifest bytes as canonical JSON; re-serialize; the bytes must be identical
   (non-canonical input is rejected).
2. `schema` is `frob.build/1`; an unknown major version is rejected.
3. The object `authorization` has exactly the four keys `execution_authorized`, `hardware_safety_signoff`,
   `sim_to_real_certified`, `fabrication_released`, each the JSON literal `false`. A missing key, an extra
   key, `true`, `null`, a string or a number rejects. Absence is not read as false.
4. BLAKE3 of the embedded bytes under the domain string `frob.build/1` equals `manifest_digest`.
5. The bundle's file list equals the manifest's file list.
6. The bundle's own three flags are present and false (the general rule for every bundle).
Outcome `accept`, or `reject` with the first failing step, the path and the value found.

**3. Directory mode.** `frob-verify --packet <dir>` (DESIGN) locates `certs/packet.frobcert`, runs the
checker, then reads each listed file as raw bytes and compares its BLAKE3 with the list; checks that the
directory's `manifest.json` bytes equal the embedded bytes; and checks that no file is present that the
manifest does not list (other than the bundle itself and review sidecars stored outside the packet). It also
runs the ordinary checkers on every other bundle under `certs/`. It parses no geometry and no section file.

**4. Refusal mapping.** A flag failure in the embedded packet manifest is reported with the packet's code
FROB-REF-860 (an export without the flags, or any attempt to produce a true flag); a failure of the
bundle's own three flags is reported with the auditor's existing code for bundles (FROB-REF-833); other
artifacts keep the general code (FROB-REF-816). The checker's output names which. Exit code: the auditor's
own convention (accept 0; reject non-zero), independent of the main binary's exit table.

**5. Specimens and mutations** (the certificates chapter requires, for every kind in use, one specimen the
auditor accepts and at least three mutations it rejects): the specimen is the fixture packet's bundle;
mutations: `fabrication_released: true`; `fabrication_released` removed; `execution_authorized: "false"` (a
string); one file hash altered; the manifest digest altered; one byte of whitespace added to the embedded
manifest; an extra key `authorization.override`; an unknown schema major version.

**6. Reproducibility.** Re-serializing the bundle with the auditor gives identical bytes (the auditor's
round-trip obligation for every bundle).

## Acceptance criteria

- [ ] `frob-verify certs/packet.frobcert` accepts the specimen and rejects each of the eight mutations with the failing step named.
- [ ] `frob-verify --packet <dir>` accepts the fixture packet; rejects it after one byte of any listed file is changed, after `manifest.json` is edited without the bundle, and after an unlisted file is added.
- [ ] A packet whose flag is `true` or absent is rejected with FROB-REF-860 in the output.
- [ ] `frob-cert` still has an empty dependency table and builds with its own stable toolchain from an empty environment on a machine with no GPU.
- [ ] The kind is in the registry of proof kinds at a new registry version, and an older auditor rejects it as unknown (it does not ignore it).
- [ ] Re-serialization of the bundle is byte-identical.

## Test plan

### Unit tests
`cargo test -p frob-cert packet_manifest`: `specimen_accepted`; `flag_true_rejected_860`;
`flag_absent_rejected_860`; `flag_string_false_rejected`; `extra_authorization_key_rejected`;
`file_hash_mismatch_rejected`; `manifest_digest_mismatch_rejected`; `non_canonical_manifest_rejected`;
`unknown_major_version_rejected`; `bundle_own_flags_checked_833`; `roundtrip_bytes_identical`;
`dependency_table_empty` (reads `Cargo.toml`).

### End-to-end script and logging
`scripts/e2e/frob_verify_packet.sh`: builds `frob-verify` from an empty environment; writes the fixture
packet with `frob foundry export`; runs `frob-verify --packet`; applies each mutation to a copy and asserts
rejection with the expected step; runs the previous release of the auditor (where one exists) and asserts it
rejects the kind as unknown. Logs per STD-E2E to `target/e2e-logs/frob_verify_packet/`: the packet address
and bundle digest; per mutation its name, the auditor's outcome and failing step; `mutations_rejected` (8 of
8); the build's dependency listing (empty); the summary names GATE-FOUNDRY-10 (its auditor clause).

### Known answers and negative controls
Known answers: four flag names; accept on the specimen; the eight rejections. Negative controls: a checker
build that treats a missing flag as false (the absent-flag mutation must expose it); a checker that compares
flags after lower-casing strings (the string mutation must expose it); a directory mode that skips files it
cannot open (a deleted file must be a rejection, not a skip). Determinism: exact; identical on every
platform the auditor builds on.

## Considerations

- Three codes concern flags: the auditor's code for bundles, the safety chapter's code for artifacts in general, and Foundry's code for packets. This bead maps each to its artifact kind; the owners of the registry may prefer to fold them, and the checker's output is written so that folding changes a number and nothing else.
- The auditor proves nothing about a packet's content. It shows that the bytes are the ones the manifest names and that no flag claims an authorization. Everything else is the pre-review's and the reviewer's.
- Embedding the manifest in a bundle duplicates a few kilobytes; the alternative (teaching the auditor to read packet directories natively) would break the rule that keeps it free of other crates' formats.
- If the packet kill gate's fallback is in force, the reduced packet has the same manifest schema and the same bundle; the checker is unchanged.
