## Background

`frob` is the command line of FrankenRobotics and the first of its two agent-facing surfaces. This bead is the
spine every later verb hangs on: the crate `frob-verbs` at version 0 (registry table, envelope, exit codes,
dispatch) and the binary `frob` in the crate `frob-cli`, with the four **operator verbs** that let an agent find
its footing: `doctor` (is the installation sound), `capabilities` (what is really implemented), `schema` (what
does this input or output look like) and `robot-docs` (the guide for agents).

It sits at milestone M0, whose purpose is to retire architecture risk with the smallest amount of code. The M0
artifact requires that "`frob doctor` lists the admitted foundations with their records and the stack receipt"
and that "the M0 verbs answer through `frob --json` and through `frob-mcp`".

Why the skeleton is generic (ADR-TETHER-01): `frob-cli` contains no per-verb code. The parser is built at start-up
from the static registry table in `frob-verbs`, so adding a verb is adding a registry entry and a handler binding,
and the CLI and the MCP server cannot disagree about a flag. Alternative excluded: a derive-macro command enum per
verb in the CLI, which is pleasant to write and is exactly how two surfaces drift.

Honest status is a first-class answer. This project defines "implemented" by eight conditions (code in its mapped
crate; a `CONTRACT.md` with ten sections; known-answer tests against a pinned oracle; outputs carrying the claim
product; a CPU reference path; reachability through `frob --json` and, where exposed, `frob-mcp`; tested
cancellation; a recorded gate PASS with measured values). `capabilities` reports each verb against those eight
(the capability registry and the status function that evaluate them are N00-02's, built on this verb), and a
verb that is registered but has no handler in the build answers with refusal `FROB-REF-724` (exit 5).

## Scope

In: `frob-verbs` v0 assembled from the registry table, envelope and dispatch beads; the `frob` binary; the

Out: the registry format and lints (N32a-02); the derivation of the common properties, the appended refusals,

## Technical approach

**CLI grammar, generated (DESIGN).** `frob <cluster> <verb> [positionals] [--flags]`; an operator verb is a single
word (`frob doctor`). The verb `telemetry.inspect-pixel` is typed `frob telemetry inspect-pixel`. For each entry
the parser is derived from the input schema: each property becomes `--kebab-case`; properties listed in the
schema extension `x-frob-cli.positional` are positionals in that order; booleans are flags; arrays repeat or take
commas; objects take `k=v,k=v`. The common flags are not computed here. For each entry the parser calls
`entry.common_properties()` of NJL-01 (a dependency, which comes before both surfaces) and adds one flag per
returned property under its `cli_flag`: the property name in kebab case, with the two exceptions `--key` for
`idempotency_key` and `--estimate` for `estimate_only`, and `--action <name>` on an entry with an `actions` list
(never a per-action flag such as `--evict`). The MCP server builds its input schemas from the same member, so the
two surfaces read one derivation. The table below is the CLI spelling of NJL-01's kinds table and of its
variations, printed for the reader; where the two differ, NJL-01 governs:

| Flag | Kinds | Meaning |
|---|---|---|
| `--json` | all (process option) | Write exactly one envelope to standard output (progress events first for long jobs) |
| `--estimate` | every `run` verb, and verbs marked estimable | Return cost with an interval and run nothing |
| `--budget k=v,…` | `run` | Budget for this call, in named units (`gpu_s`, `cpu_core_s`, …) |
| `--key <string>` | `run`, `mutate` | Idempotency key; omitted is refusal `FROB-REF-805` once the binding exists (N32a-09, M1), except on a `key_optional` entry |
| `--expected-parent <id>` | `mutate` | The lineage head the caller believes is current (`FROB-REF-804` if stale) |
| `--sync-wait-ms <n>` | `run` | Bound the wait; exit 8 with a job handle if it elapses. The CLI default is to wait to completion |
| `--on-cancel leave\|cancel_job` | `run` | What an interrupted wait does to the job; default `leave` |
| `--action <name>` | an entry with an `actions` list | Selects the action; absent, the default action runs. The flags, the scope and the refusals follow the kind of the selected action |
| `--session <id>` | all (process option) | The session identifier `s:…`; also read from `FROB_SESSION`. It is not a credential (below) |
| `--limit`, `--cursor`, `--follow` | paginated `read` | Page size, continuation, and follow mode |

`--on-cancel` takes `leave` (default) and `cancel_job`, the values the cancellation bead N32a-17 serves. The
**process options** are accepted on every invocation whatever the verb and are not input properties: `--json` and
`--session` from this bead, `--registries-root` (N32ax-03) and `--session-token-file` (N32b-01) from theirs. They
are listed in NJL-01's constant `PROCESS_OPTIONS`, which its lint `common-property-shadowed` reads so that no row
can declare an input of the same name; a bead that adds a process option adds it to that list.

**`--session` carries an identifier, never a token (DESIGN, the rule of the token bead N32b-01).** An argument
vector is visible in the process table and is what every transcript and recorded command prints, so a credential
must not travel in one. `--session` and `FROB_SESSION` therefore carry the session identifier `s:…`, which selects
the session before tokens exist (M0, M1) and from M2 is optional and must equal the token's session. The session
token itself is read only from the environment variable `FROB_SESSION_TOKEN` or from the file named by
`--session-token-file` (N32b-01, M2, which also refuses a token-shaped value given to `--session` or found in
`FROB_SESSION` with `FROB-REF-802`, `pointer: /session`).

**Generated help (DESIGN).** `--help` after any command path is a built-in of the parser, not an input property:
it runs no handler and exits 0. For a person it prints the entry's purpose, flags, refusals and examples. With
`--json` it writes one envelope whose `result` is `{ entry, input_schema, output_schema, refusals, examples }`:
`entry` reproduces the registry row; `input_schema` is `entry.input_schema_with_common_fields()`;
`output_schema` is `entry.envelope_schema()`; `refusals` is `entry.all_refusals()`, ascending, one object per
code with `code`, `meaning`, `exit` and `repairs` from `registries/refusals.toml` and `source` (`chapter`,
`kind:<kind>` or `field:<field>`, with the action's name where the entry has actions). This is the form the
conformance harness NJL-02 reads for its parity and snapshot checks, and stage 3 of NJL-01's script asserts it.
`robot-docs` prints the same full list per verb, chapter codes and appended codes apart, each with its source.

The CLI owns its parser, so both protocol failures are envelopes: unknown verb → `FROB-REF-801`, exit 3;
arguments that fail the schema, including an unknown flag → `FROB-REF-802`, exit 3. Without `--json` the same
envelope is rendered for a person; the exit code is identical.

**Start-up, numbered.** (1) Install the panic hook that turns a panic into an exit-9 envelope. (2) Parse global
flags. (3) Look the verb up; build its parser from the entry; parse. (4) Hand the request to the dispatch
interface. (5) Print progress events as they arrive when `--json` is set and the job is long. (6) Print the one
envelope; exit with `envelope.exit`.

**The four operator verbs (all kind `read`, cluster `operator`, tier Solid, first milestone M0).**

| Verb | Input | Output (schema) | Refusals | Exit |
|---|---|---|---|---|
| `doctor` | `--section <name>` optional, repeatable | `frob.doctor.out/1`: `toolchain` (the compiler found against the pinned toolchain T), `stack` (one row per admitted foundation: name, posture, pin, on-pin, clean, admission gate, record status), `stack_receipt`, `upstream` (each upstream work item with status `open`, `landed` or `adopted`), `devices`, `kernel_cache`, `probes`, `daemon` (reachable, socket path, version), and the sections contributed by other crates through the section interface below | 802 (an unknown section name has `pointer: /section`) | 0 when every check passes; 2 with one finding per failed check, each with a repair |
| `capabilities` | `--verb` filter | `frob.capabilities.out/1` (schema owned by N00-02): the registry digest; per verb whether its handler is linked in this build and its `first_milestone`; the status words and the condition list come from N00-02's status function (below) | 802 | 0 |
| `schema` | at most one of: a positional schema identifier or verb name; `--verb <name>` (both schemas of the verb), optionally narrowed by `--in` or `--out`; a list form (`--refusals`, `--verbs`, `--path-args`); no argument, which is `--refusals` (the forms are below) | `frob.schema.out/1`: for an identifier or a verb, the JSON Schema and a minimal valid example that validates against it; for a list form, the one member of that form | 802; an unknown identifier or verb name is 802 with `pointer` and the three nearest names; two forms in one call are 802 | 0 |
| `robot-docs` | `--cluster <task cluster>` optional | `frob.robot-docs.out/1`: at v0 the generated reference: per verb its purpose, when to use it, kind, cost class, its full refusal list (`all_refusals()`, with sources) and one example; the envelope and exit tables | 802 | 0 |

**The doctor section interface (DESIGN).** `doctor` is assembled from sections, so that a later crate adds a
check without editing this bead's code: `pub trait DoctorSection { fn name(&self) -> &'static str; fn run(&self,
cx: &Cx) -> SectionReport }`, where `SectionReport` holds the section's rows, its `status` (`ok`, `findings`, `skipped` with a
reason) and its findings (each finding: `code` a stable slug, `severity` `info`, `low` or `high`, `message`,
`observed`, `required`, ranked `repairs` as commands; the form the complete `doctor` of N32b-20 keeps). Exit 0
when no finding is above `info`, 2 otherwise. Sections are listed in one static table in `frob-verbs::operator::doctor`, sorted by
name, and `--section <name>` runs one of them. The eight sections above are this bead's. Sections contributed
later, each by the bead that owns the crate: `kernels` (`frob-kernels`, N21b-01: the path and BLAKE3 digest of
`registries/kernels.toml`, the number of manifests, and one finding per manifest that fails static validation,
naming the kernel, the rule and the `ManifestError` variant; it compiles and launches nothing), `ledger` (N34-26:
read-only row counts per table and the commit sequence) and `registries` (N32ax-03: the registries root, its
kind and one digest per registry; its flag `frob doctor --registries` is the same as `--section registries`, a
shorthand the operator row of record registers). A section never writes, never launches a device probe and never takes longer
than 2 s (TARGET); a section that times out is a finding, not a hang.

**The forms of `schema` (the row of record is VERBS-operator's; DESIGN where the plan says only "a schema and a
minimal valid example").**
1. *Identifier or verb name.* A positional argument that contains `/` is a schema identifier (an identifier
   always carries `/<major version>`, `frob.envelope/1`); one without is a verb name (`sim.run`, `doctor`) and is
   the same request as `--verb <name>`: the handler rewrites `{id: X}` with no `/` in X to `{verb: X}` before
   anything else, so the two spellings return byte-identical envelopes. Reason: the two kinds of name cannot
   collide, and a dozen scripts of other beads call `frob schema <verb>` positionally. `--in` and `--out` narrow
   either spelling of a verb. An unknown name of either kind is `FROB-REF-802` with `pointer` (`/id` or `/verb`)
   and the three nearest names of either kind in `refusal.observed`.
2. *The refusal table*, `--refusals`, and also the call with no argument at all (several registry beads read the
   table each way). Member `refusals`: one row per code of `registries/refusals.toml`, ascending, with `code`,
   `name`, `message`, `exit`, `retry`, ranked `repairs`, `defined_in` and `raised_by`; and beside it the list
   `interims`, one row per request of the allocation ledger `registries/refusal_allocations.toml` (N35-33, a
   dependency) that is not yet settled (status `requested` or `held`): `request` (the slug), `interim` (the
   existing code under which the refusal is raised meanwhile, or `none`), the `detail` or `pointer` value that
   tells it apart from the code's ordinary use, `owner` (the bead that owns the interim use) and `status`. A
   held request with no interim is listed with `none`, never omitted.
3. *The verb table*, `--verbs`. Member `verbs`: one row per registry entry with `verb`, `kind`, `capabilities`,
   `actions` (each with its kind and scopes), `chapter_refusals` (the row's own list) and `appended_refusals`
   (what `all_refusals()` adds, each with its source). Codes only: a refusal still held in the ledger appears as
   its interim code, never as a slug or a proposed number. Read by N28cx-01 (M1), N28c-29 and N37-15.
4. *The path arguments*, `--path-args`. Member `path_args`: one row per input property, at any depth of any
   entry's input schema, that carries the annotation `x-frob-path` (`{root: project|export|private, access:
   read|create|replace, kind: file|dir}`; the annotation and the argument type `frob.path/1` are the path jail's,
   N37-11, M1): `verb`, `argument` (the JSON pointer of the property), `root`, `access`, `kind`, and `param_kind`
   where the entry's `params` table names the property. The listing is a walk of the embedded schemas, so it is
   empty until a schema carries the annotation and cannot fall behind the schemas afterwards. Read by N37-12.

**The schema listing interface (DESIGN).** The list forms are assembled like the `doctor` sections, so that a
later bead adds one without editing this handler: `pub trait SchemaListing { fn member(&self) -> &'static str;
fn build(&self, reg: &Registries) -> Value }`, in one static table in `frob-verbs::operator::schema` sorted by
member name. A listing's flag is its member name in kebab case (`path_args` → `--path-args`), a boolean property
that the contributing bead adds to `frob.schema.in/1`; its output is one optional member of `frob.schema.out/1`
(members are added and never changed, so the row keeps one output schema at major version 1). A listing reads
only the registries and schemas embedded in the binary (a test passes a scratch `Registries`), takes no further
argument and writes nothing. A list form whose bead is not in the build is an unknown parameter, 802. Listings
contributed later: `list` (N32b-20, M2), `exports` (N37-23, M1) and `echoing` (BD-304, M3).

`doctor` reads; it repairs nothing. `capabilities` never reports a verb as implemented on the strength of its
registry entry. The handler reads its status through one interface, `trait StatusSource { fn status(&self,
verb: &VerbEntry) -> VerbStatus }`, and this bead ships only the fail-closed source: a verb with no linked
handler is `not-in-build` (condition 1 missing, with its `first_milestone`); a linked verb is `partial` with
conditions 2 to 8 listed as `not-evaluated`; nothing is ever `implemented`. N00-02 (M0, which depends on this
bead) installs the registry-driven source, the one definition of the status words, the eight conditions and
the records; the verb's code does not change. Evidence on all four: class `Tested`, tier `static`, determinism `exact`, `claims: []`,
`reality: no-claim`.

**M0 registry entries added here.** `doctor`, `capabilities`, `schema`, `robot-docs` (implemented);
`session.open`, `session.show`, `session.focus`, `session.close` (declared; they answer 724 until BD-138). Other
M0 verbs (`sim.run`, `spark.devices`, `spark.probe`, `spark.check`, `spark.fingerprint`, `prove.kernel`,
`prove.verify`, `prove.list`) are added by their own beads through the same file.

**Exit 8 and exit 4 at M0.** The value, the `Deferred` envelope form and the CLI's handling exist and are
golden-tested. No daemon exists at M0, so a real `run` verb waits to completion in process, and no estimable `run`
verb exists in this bead's dependencies. Both paths are therefore exercised with a test-only overlay (DESIGN): the
cargo feature `synthetic-verbs` of `frob-verbs` compiles two extra entries of the reserved cluster `synthetic`
from `crates/frob-verbs/tests/synthetic_verbs.toml` (labelled `synthetic`): `synthetic.deferred` (kind `run`; its
handler returns a deferred outcome with `progress {done: 0, total: 4, unit: "episodes"}`) and
`synthetic.estimable` (kind `run`, `estimable = true`; its estimate is a fixed point of 1 CPU core-second with
the uncalibrated interval [0.5, 2] core-seconds, the rule `point ÷ 2` to `point × 2` of the budget bead N32a-15,
here applied in the overlay's fixed estimate since that bead lands at M2). With `--budget cpu_core_s=0.5` the upper end 2 exceeds the budget, so
the call is refused `FROB-REF-701`, exit 4, with the estimate attached. The feature is enabled only in the test
lane; `xtask check-generated` fails if a release binary contains the cluster `synthetic`. When `sim.run` lands
(BD-024) its own script repeats the over-budget row on a real verb.

**The component scripts are run here.** The envelope bead N32a-03 and the dispatch bead N32a-04 author
`scripts/e2e/tether_envelope_exit.sh` and `scripts/e2e/tether_dispatch.sh` with their fixtures; both drive the
`frob` binary, which first exists in this bead, so this bead's acceptance runs them green against it.

## Acceptance criteria

- [ ] GATE-TETHER-03 (TARGET) on these verbs: for malformed, unknown and over-budget inputs the output is exactly one schema-valid envelope with the expected refusal and exit code; the measured table is recorded.
- [ ] `frob doctor --json` lists every admitted foundation with its record and the stack receipt; the `stack` section, run on a scratch copy of `franken-stack.lock` with one pin moved (the unit test passes the scratch path to the section), reports exit 2 with one finding naming the foundation.
- [ ] `frob doctor --section <name>` runs exactly that section for each of the eight sections of this bead; an unknown section is `FROB-REF-802` with `pointer: /section`; a section registered by a synthetic test crate appears in the full report without a change to `frob-cli`.
- [ ] `scripts/e2e/tether_envelope_exit.sh` (N32a-03) and `scripts/e2e/tether_dispatch.sh` (N32a-04) pass against the `frob` binary built here, the latter with the operator verbs in process and with `FROB_DISPATCH=socket`.
- [ ] `frob capabilities --json` lists the four operator verbs as linked (`partial`, conditions 2 to 8 `not-evaluated`) and the four declared session verbs as `not-in-build` with condition 1 missing and their `first_milestone`; no verb is `implemented` under this bead's source; `frob session show --json` returns `FROB-REF-724`, exit 5.
- [ ] `frob schema frob.envelope/1 --json` returns a schema whose example validates; so does `frob schema --verb doctor --out --json`; `frob schema --verb doctor --json` returns both of the verb's schemas; `frob schema doctor --out --json` equals `frob schema --verb doctor --out --json` byte for byte.
- [ ] `frob --json schema` and `frob schema --refusals --json` return byte-identical envelopes whose `refusals` member has one row per code of `registries/refusals.toml` and whose `interims` list has one row per unsettled request of the allocation ledger, a request without an interim listed with `none`; steps (2) and (4) of N35-33's `scripts/e2e/refusal_registry.sh` (the served comparison of the table and of the interim list, which that registry bead authors and cannot run before this binary exists) pass against the binary built here.
- [ ] `frob schema --verbs --json` has one row per registry entry with chapter codes and appended codes apart; `frob schema --path-args --json` lists exactly the input properties annotated `x-frob-path`; two list forms in one call are `FROB-REF-802`; a listing registered by a synthetic test crate is served without a change to the handler.
- [ ] The common flags of every entry are exactly the `cli_flag`s of `entry.common_properties()`; `frob-cli` and the operator module hold no second table of them (source scan). `frob <cli path> --help --json` exits 0 with one envelope whose `input_schema` equals `entry.input_schema_with_common_fields()` and whose `refusals` equal `entry.all_refusals()` with each code's source, for one verb of each kind present (a declared verb without a handler included, since help runs no handler).
- [ ] `frob robot-docs --json` lists every registered verb once, and its content is regenerated byte-identically from the registry.
- [ ] `frob-cli` contains no verb-name literal outside generated code (the lint of ADR-TETHER-01).
- [ ] Each operator verb has a schema, an example and a refusal list in the registry; `CONTRACT.md` exists for `frob-verbs` and `frob-cli`; a CPU path is the only path; cancellation (Ctrl-C during `doctor`) yields one envelope and no stray output.
- [ ] The human rendering and `--json` exit with the same code for every fixture row.

### End-to-end script and logging
`scripts/e2e/frob_operator_verbs.sh` (plain shell, idempotent, seed-free): runs the four verbs with `--json`,
validates each envelope against `frob schema … --out`, then runs the exit-code fixture of malformed, unknown and
over-budget inputs (the over-budget row is `frob synthetic estimable --budget cpu_core_s=0.5 --key "$(e2e_key
over-budget)"` on the test-lane binary built with `synthetic-verbs`; a `run` call carries a key from the first
script on, so the row still passes once the binding of M1 refuses a missing one), then a Ctrl-C test, then `frob
doctor --section <name>` for each section with the section's wall time as a `metric` against the 2 s target.
Then the forms added to `schema` and the help: `frob doctor --help --json` (exit 0, the refusal list with
sources logged); `frob schema doctor --out --json` compared byte for byte with `frob schema --verb doctor --out
--json`; `frob --json schema` compared byte for byte with `frob schema --refusals --json`, with the row count as
a `metric` against the rows of `registries/refusals.toml` and the interim count against the unsettled requests
of the ledger; `frob schema --verbs --json` with its row count against the registry's entry count; `frob schema
--path-args --json` with its count logged; `frob schema --refusals --verbs --json` (`e2e_expect_refusal
FROB-REF-802 3`).
It sources the shared helper and writes `target/e2e-logs/frob_operator_verbs/<utc>.ndjson` plus a transcript. Each
line has `ts`, `script`, `bead` (`BD-022`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`,
`end`), the exact command line, exit code, wall time and the envelope's `evidence` block; `metric` lines give the
wall time of each verb (recorded, no threshold at M0) and the registry digest; on failure the first differing
field and the saved envelope path. The final `summary` gives assertions passed and failed and names
GATE-TETHER-03.

### Known answers and negative controls
- KA-755 (exact): malformed → 802, exit 3; unknown → 801, exit 3; over-budget → 701, exit 4. The unscoped (720, exit 5) and conflicting (803, exit 7) rows are present in the fixture and recorded `not exercised` until tokens and the idempotency binding land.
- Negative controls: a build with the unknown-verb envelope disabled (the fixture must fail); a planted wrong exit for 802 (must fail); a verb-name literal planted in `frob-cli` (the lint must fail).
- Determinism lanes: `robot-docs` and `schema` outputs byte-identical twice on one machine, in debug and release, on both hosts.

## Considerations

- The registry dates the session verbs at M0 while their handlers are scheduled with the M1 MCP work; they are registered here as declared so that the tool list is stable from the first smoke test.
- `doctor` must stay fast and side-effect free; device checks call `spark.devices` and never launch a probe.
- The guide grows into the full `robot-docs` with worked sessions at M3; v0 is reference material only, so the fresh-agent gates do not apply yet.
- If the kill gate KILL-MCP fires, nothing here changes: the CLI is complete on its own and is the last fallback.
