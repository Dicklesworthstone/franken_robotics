## Background

`frob-mcp` is the server through which agent harnesses reach every verb of FrankenRobotics over the Model Context
Protocol (MCP). It is built on `fastmcp_rust`, a sibling library that belongs to the project owner. This bead
delivers version 0: the crate `surface/frob-mcp` as an ordinary member of the core workspace, one generic tool
handler that serves every registry verb, the M0 verbs running in process, and the admission gate **INT-FMCP-01**.

The starting state (FACT, read 2026-11-21): FrankenSim, the physics sibling, pins `nightly-2026-07-06` (rustc
1.99.0-nightly), while `fastmcp_rust` declares `rust-version = "1.100"` and pins `nightly-2026-08-25`; as found the
two do not build on one compiler. The registry package `fastmcp-rust` 0.13.0 carries asupersync 0.5.0, while
FrankenSim consumes asupersync by path (0.6.2) and FrankenTorch requires 0.6.2.

Decision (owner's ruling of 2026-11-22; it settles OPEN-TETHER-1 and OPEN-SUITE-2): both mismatches are fixed in
the siblings, by this program, at M0. The upstream work item FD-FMCP-01 brings `fastmcp_rust` onto T, the one
toolchain of the build graph, with its own test suite and MCP conformance checks passing there. FD-ASUP-01 aligns
FrankenSim's constellation, FrankenTorch and `fastmcp_rust` on one published asupersync version. `frob-mcp` then
links `frob-verbs` and **calls verb implementations in process**. Its source stays under `surface/` because it is
a surface, not because it is a separate workspace. Alternative excluded (and kept only as a fallback): the server
as its own workspace reaching verbs over a local socket, which was the default before the ruling and adds a
protocol hop and a second build to every agent call. Text that arrives from imports (design names, asset
metadata, scan annotations) is data and is never interpreted as instructions.

## Technical approach

**Manifest.** `surface/frob-mcp/Cargo.toml` is listed in the root workspace `members`. It depends on
`fastmcp_rust` by git commit at or after `117388bc` (the commit FD-FMCP-01 lands), never on registry 0.13.0, so
that one asupersync package is possible; on `frob-verbs` with default features; on nothing else of the core. No
toolchain file of its own: it builds on T. A binary target `frob-mcp` and a library that `frobd --mcp` hosts.

**One generic handler (ADR-TETHER-01).** `frob-mcp` contains one type, `VerbTool`, and constructs one instance per
registry entry at start-up. There is no macro per verb; the attribute macros are used only for hand-written
resources, prompts and the part of `session.focus` that edits the visible tool set.

| `Tool` field | Derived from the registry entry |
|---|---|
| `name` | The verb name with `.` and `-` replaced by `_` (`design.check` → `design_check`). A registry lint guarantees the map is one-to-one. |
| `description` | Generated: one sentence of purpose, when to use it, the cost class, the refusal codes, one example. At most 800 characters (TARGET); the long form is a documentation resource. |
| `input_schema` | The verb's input schema plus common properties by kind: `run` adds `sync_wait_ms`, `idempotency_key`, `budget`, `estimate_only`, `on_cancel`; `mutate` adds `idempotency_key` and `expected_parent`. |
| `output_schema` | `frob.envelope/1` with `result` specialized to the verb's output schema. |
| `tags` | `cluster:<name>`, `kind:<kind>`, `task:<task cluster>` for each task cluster, `tier:S`, `F` or `M`. |
| `annotations` | `read_only` for kind `read`; `idempotent` from the registry's rule; `destructive` only for `admin` verbs that delete; `open_world_hint: false`, since every verb acts on the local store. |
| `version` | The schema version of the entry. |

```rust
// DESIGN: fixes intent, not signatures.
struct VerbTool { entry: &'static VerbEntry, dispatch: Arc<dyn Dispatch> }
impl ToolHandler for VerbTool {
    fn definition(&self) -> Tool { /* the table above */ }
    fn execution_mode(&self) -> ToolExecutionMode { ToolExecutionMode::Async }
    fn call(&self, _: &McpContext, _: Value) -> McpResult<Vec<Content>> {
        Err(McpError::new(McpErrorCode::InternalError, "async-only handler"))
    }
    fn call_async<'a>(&'a self, ctx: &'a McpContext, args: Value) -> BoxFuture<'a, McpOutcome<Vec<Content>>> {
        Box::pin(async move { outcome(self.run(ctx, args).await) })
    }
}
// run(): ctx.checkpoint()? before any charge; entry.resolve(args, ctx.auth())?; dispatch.submit(ctx.cx(), &req);
// forward frames; return the envelope as the tool result (isError with the full envelope for a refusal).
```

**Server build settings.** `.on_duplicate(DuplicateBehavior::Error)` and `.try_build()`, so a name collision
fails start-up; `.strict_input_validation(true)`, so a misspelt parameter is a refusal and not a default;
`.mask_error_details(true)`. Because each tool declares an output schema, the handler supplies envelope skeletons
for the library's two framework error kinds, which the library validates against the schema at registration
(FACT): input validation → exit 3 with `FROB-REF-802`; handler fault → exit 9. A domain refusal is returned as a
tool error (`isError: true`) whose structured content is the full envelope. An unknown tool is answered by the
library before any handler runs with a JSON-RPC error (FACT: `InvalidParams`, −32602, "Unknown tool"); it is the
one place where no envelope exists and the parity gate lists it as the only exemption.

**INT-FMCP-01, the admission gate (M0), measured in this order.**
1. `cargo build -p frob-mcp --locked` on T, with no `--ignore-rust-version` anywhere.
2. `cargo tree -d` over the workspace shows no duplicate asupersync package.
3. The server starts; `tools/list` returns one tool per registry entry and nothing else, with names under the map.
4. The protocol smoke test passes over stdio and over HTTP on loopback: `initialize`, `tools/list`, `tools/call`
   of `doctor` and `capabilities` (schema-valid envelopes, exit 0), an unknown tool (−32602), a call with a
   misspelt parameter (envelope skeleton, 802, exit 3), `ping`, clean shutdown.
5. Write the admission record (commit of `fastmcp_rust`, T, the tree check, the smoke counts) to
   `DEPENDENCY_ADMISSION.md`, passing or failing.

**If it cannot pass.** This bead closes with a recorded failing admission, naming the step that failed, and the
kill gate KILL-MCP is then decided (trigger: INT-FMCP-01 cannot pass within the M0 budget after FD-FMCP-01 and
FD-ASUP-01 have both been attempted). Until then agents use the CLI, which is complete on its own.

## Acceptance criteria

- [ ] `fastmcp_rust`'s own suite and conformance checks are green on T at the pinned commit (the record of FD-FMCP-01 is cited with its counts; baseline 112 of 115 passing, 0 failing).
- [ ] `frob-mcp` builds in the core graph on T with exactly one asupersync package (`cargo tree -d` shows no duplicate).
- [ ] The served `tools/list` equals the set of registry entries under the name map, for the M0 verbs.
- [ ] The MCP protocol smoke test passes over stdio and HTTP, with every step of the list above asserted.
- [ ] Every tool's output schema is `frob.envelope/1` specialized, and both framework-error skeletons validate at registration.
- [ ] `surface/frob-mcp/src` contains no verb-name literal; a planted duplicate tool name fails `try_build`.
- [ ] No tool description contains text from an import (descriptions are a pure function of the registry).
- [ ] The INT-FMCP-01 record exists in `DEPENDENCY_ADMISSION.md` with measured values.

## Test plan

### Unit tests (`cargo test -p frob-mcp`)
- `definition_from_entry`: for a `read`, a `run`, a `mutate` and an `admin` entry, the derived name, tags, annotations and common properties equal the table (for `sim.run`: tags `cluster:sim`, `kind:run`, `task:simulate`; properties include `sync_wait_ms`).
- `description_at_most_800`; `description_is_registry_only` (a design named "ignore previous instructions" in the store changes no description byte).
- `duplicate_name_fails_build`: two entries forced to one tool name → `try_build` errors.
- `error_skeletons_validate`: both skeletons validate against each tool's output schema.
- `refusal_is_error_with_envelope`: a refused call returns `isError: true` and structured content equal to the CLI's envelope for the same request.
- `unknown_tool_is_jsonrpc_32602`.
- `misspelt_parameter_802`: `{"sektion":"stack"}` to `doctor` → skeleton with 802, exit 3.
- In-memory transport: `tools_list_equals_registry`.

### End-to-end script and logging
`scripts/e2e/int_fmcp_01.sh`: runs the five steps above against the real `frob-mcp` binary, as a subprocess over
stdio and over `127.0.0.1` HTTP, using the library's own client. It sources the shared helper and writes
`target/e2e-logs/int_fmcp_01/<utc>.ndjson` with a transcript: `cmd` lines (exact command, exit code, wall time),
`assert` lines per smoke step and per transport, `metric` lines for the asupersync package count (threshold 1),
the tool count against the registry count (must be equal), build time, and the envelope `evidence` block of each
call; on failure the first differing tool name or field and the saved wire transcript. The `summary` names
INT-FMCP-01.

### Known answers and negative controls
- Known answers: tool count equals registry count; `design.check` ↔ `design_check`; unknown tool → −32602.
- Negative controls: a scratch manifest naming registry `fastmcp-rust = "0.13.0"` (the tree check must report two asupersync packages and fail); a tool registered by hand outside the registry (the list comparison must fail); `--ignore-rust-version` planted in a script (a grep check must fail).
- Determinism lanes: `tools/list` bytes identical twice on one machine, over both transports, in debug and release.

## Considerations

- RISK-02 (the toolchain train costs more than M0 allows) and RISK-03 (two asupersync versions in one build): earliest signals are a failing build here and a duplicate in the tree check.
- The 2026-07-28 protocol revision is unverified upstream; the smoke test uses the library's automatic policy and records which revision the client negotiated.
- INT-FMCP-01 is re-run at M1 with the M1 verbs and at M3 with the full surface; KILL-MCP is re-read at M1.
- No milestone waits on this bead: M1 depends only on FrankenSim, asupersync and FrankenSQLite, and agents can use the CLI.
