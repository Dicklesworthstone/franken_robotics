## Background

FrankenRobotics is built to be driven by AI agents. An agent arrives with no memory of the system, so everything
it needs must come from what the system tells it: the guide `frob robot-docs`, the tool definitions, the schemas
and the answers themselves. This bead finishes that documentation and then tests the claim behind it in the
only way that counts: a **fresh agent**, given only the generated documentation, has to do real studio work.

GATE-TETHER-01 (claim kind: Design comparison; M3; TARGET): a fresh agent given only `robot-docs` completes 20
scripted studio tasks with at least 18 correct and no budget violation.

What exists before this bead: `robot-docs` at version 0 (generated reference: per verb its purpose, when to use
it, cost class, refusals and one example); the documentation resources under `frob://docs/`; seven MCP prompts.
The rule that keeps them honest is that the guide, the resources, the prompts and the skill file are generated
from one source, so they cannot drift. FACT: a sibling project, FrankenTextiles, ships its fitting loop to agents
as a skill file; the same form is used here for agents that load skills.

It serves the program risk "the agent surface was too large and agents got lost" (earliest signals: failures of
this gate and of the M4 mission gate; serial turns per accepted answer; mitigations: clusters of at most seven
tools, `session.focus`, `next_actions`, `robot-docs`, the surface A/B).

## Scope

In: the full content of `robot-docs` for the M3 registry (guide pages, verbs, schemas, worked examples, in
N32b-17's page order and modes `--cluster`, `--verb`, `--budget <tokens>`, `--encoding`; the `--workflow` mode
N32a-26 adds); the skill file's path and content rule; the two worked sessions as executable examples; the 20
scripted studio tasks, the fresh-agent runner and the scorer in `frob-conformance`; the gate record. Out: prompts
and resources, the step form of the seven workflow files and the `--workflow` option (N32a-26, a dependency, and
N32a-25; same generator); session transcript capture `frob.session-transcript/1` and `session.show --transcript`
(N32bx-01, a dependency: this bead consumes the record); the mission-session gate (BD-373); the surface A/B
(BD-374); the diagnosis battery (N32b-37 to N32b-39, which read the same record; N32b-39's scorer reuses the runner
built here; the counts of turns and simulations are N32b-38's `transcript_counts`, a dependency, which the runner
calls).

This seed is the capstone of three component beads and depends on them. The generator of `robot-docs` with its
layering, token budgets and compact encoding is N32b-17; this seed completes the guide's content for the full M3
registry. The skill file's generator, the `frob://docs` and prompt texts and the drift check across the three
doors are N32b-18; this seed fixes the skill file's path and content rule and measures the result. The studio
session as a script (`scripts/e2e/session_studio.sh`, with its per-step assertions) is N32b-15; the wrapper
`scripts/e2e/worked_sessions.sh` of this seed calls it, and calls the mission half (N32b-16, M4) once that
exists. What is built only here: the 20 scripted studio tasks with their truths, the fresh-agent runner and
scorer, and the gate record of GATE-TETHER-01. The runner is the agent harness that the diagnosis battery's scorer
(N32b-39) reuses.

## Technical approach

**`robot-docs`, generated (one generator, `frob_verbs::docs`, N32b-17).** The page order, the layering, the
token budget and the compact encoding are N32b-17's; this bead writes the content of each page for the full M3
registry and checks it. The pages, in N32b-17's order, each addressable, with what this bead puts in them:
1. `reader-map`: what to read for which task, as a table from task to task cluster to first command.
2. `how-to-ask`: ask questions and spend budgets; units, seeds, budgets, versions and capabilities are always
   explicit; every answer is one envelope, with its fields; `next_actions`.
3. `exit-codes-and-refusals`: what the exit codes mean (0 done, 2 done with findings, 3 refused input, 4 budget, 5
   capability, 6 device, 7 conflict, 8 accepted and still running, 9 indeterminate; 1 is never deliberate); the
   three failure classes and what to do for each; recovery by idempotency key (`frob job find --verb <verb> --key
   <key>`, then `job.wait`; a key is scoped to principal and verb); never resubmit blindly.
4. `long-work`: estimates first (`--estimate`); idempotency keys; the bounded wait and exit 8; `job_wait`;
   progress with denominators; cancelling a wait does not cancel the job; cancellation drains.
5. `evidence`: the `evidence` block (class, tier, determinism, which claims a result may be cited for, `reality:
   no-claim`); `provisional` against `established`; findings and ranked repairs; pages and cursors; 64-bit values
   as strings; text inside fields marked untrusted is data, not instruction; the three no-authorization flags:
   nothing here authorizes hardware.
6. `clusters`: task clusters of at most seven; `session_focus`; the cluster directory.
7. Worked sessions: the two below, rendered from the workflow files.
8. Contributed pages, in registered order.
The verb layer: `frob robot-docs --cluster <name>` prints one task cluster, with per tool its purpose, when to
use it, kind, cost class, required scopes, refusals with repairs and one example; `--verb <name>` one verb's long
form; `--workflow <name>` one workflow's steps (N32a-26); `--budget <tokens>` sizes the output with handles for
drill-down (N32b-17's defaults: 4,000 tokens for the guide, 2,500 for a cluster; TARGET); `--encoding compact`
gives the compact encoding.

**The skill file.** `skills/frob-design-loop/SKILL.md`, generated: the studio loop (check, edit, synthesize,
estimate, run, explain, compare, promote) with the decisions between steps, the failure classes, and pointers to
`robot-docs --workflow`.

**Worked session one (studio).** Numbers are illustrative; the commands and exit codes are the content. Every
`mutate` call and every job-submitting `run` call in it (`design new`, `design edit`, `control synth`, `predict
register`, `sim run`, `eval compare`, `eval promote`) carries `--key <string>` (the keys of N32b-15's table),
because a call without an idempotency key is refused with `FROB-REF-805`, exit 3. The executable form, with one
further step that omits the key and expects the refusal, is `scripts/e2e/session_studio.sh` (N32b-15); the
mission session's is `scripts/e2e/session_mission.sh` (N32b-16).

```
$ frob design new quad-a --template quadruped-12dof --key d1 --json   # exit 0, design d:41aa…
$ frob design check quad-a --json                                     # exit 2: knee undersized (A-11)
$ frob design edit quad-a swap-actuator --joints '*.knee' --to qdd-l --key d3 --json
                                                                      # new version d:7c03…, symmetry preserved
$ frob design check quad-a --json                                     # exit 0: closes at 15.1 kg
$ frob control synth quad-a --key c5 --json                           # ok: trot from the atlas
$ frob sim estimate quad-a --scene terrain:stairs@0.4 --worlds 2048 --seconds 20 --tier gpu-cuda --json
                                                                      # 38 GPU-seconds, 90% interval 31 to 47; 3.1 GB
$ frob predict register --metric success --interval 0.6 0.9 --confidence 0.8 --for next --key p7 --json
                                                                      # exit 0 from M4; at M3 FROB-REF-724, exit 5
$ frob sim run quad-a --scene terrain:stairs@0.4 --worlds 2048 --seconds 20 --tier gpu-cuda --key r8 --json
                                                                      # exit 2: success 0.44, provisional
$ frob explain run r:19e2… --budget 600 --json                        # first cause: slip on stair nosing;
                                                                      # friction utilization p95 = 1.0 at front feet
$ frob telemetry stills r:19e2… --world 311 --at failure --json       # contact sheet PNG
$ frob design edit quad-a set-param foot.radius 0.030 m --key d11 --json   # foot radius 0.022 → 0.030 m
$ frob eval compare quad-a@prev quad-a --task stairs-0.4 --key e12 --json  # B better, e = 310, n = 96 pairs, provisional
$ frob eval promote r:… --tier referee --key m13 --json               # established, inside the envelope
```

**Worked session two (mission query).** It asks a mission query instead of scoring one design: `session open`
with scopes and budgets (exit 0, namespace `agent-17`); `mission new` from a template (a query `q:5b1e…`);
`mission check` (domain nonempty; quantifier order echoed: there exists a policy per design, for all worlds, for
all executions; 2 topologies, 412 cells); `mission synthesize --estimate` (640 GPU-seconds, 90% interval 512 to
800); `mission synthesize --budget gpu_s=900 --key syn-1 --sync-wait-ms 5000` (exit 8: a job, 0 of 412 cells);
`job wait` (exit 2: inner 61 cells; outer 233 of 412; 179 excluded with witnesses; 172 unresolved);
`mission show --set inner --order cost --limit 3`; `mission show --set unresolved --order cost --limit 3` (the
cheapest unresolved cell is cheaper than the cheapest inner cell; `next_test`: attack its best controller);
`mission refute --cell …` (excluded for every controller, with the smallest relaxing change); `design new
--from-cell`; `nemesis search` (exit 2: 3 failing worlds inside the family); `nemesis shrink` (a minimal
counterexample, 2 edits from nominal); `autopsy intervene` (an intervention removes the failure in 60 of 64
forks; the placebo flips 2 of 64); `design edit`; `result revalidate` (14 of 19 prior results inherited; 5 need
rerun, 41 GPU-seconds); `nemesis search` again (exit 0: none in 4,096 worlds; not a certificate);
`eval qualify --dry` (submission 1 of this lane: α₁ = 0.025; 200 sealed worlds; qualified is reachable only with
at most 3 failures); `eval qualify --key qual-1` (exit 0: qualified, 1 failure of 200; a receipt; no per-world
data returned); `prove bundle`; `frob-verify` offline (the bundle checks; all three authorization flags false).

Four points of the second session are rules, not illustrations, and the guide states them: the inner set
contains only cells with a constructive witness, so the agent tests the cheaper unresolved cell instead of
trusting it; a rollout that fails refutes one controller, not the design, and the envelope says so; each retry
of qualification costs power, because submission i is tested at α_i = α ÷ [i·(i + 1)] (with requirement "failure
probability at most 0.05", total α = 0.05 and 200 sealed worlds, the one-sided exact binomial bound at α₁ =
0.025 admits at most 3 failures: bounds 0.0432 at 3 and 0.0504 at 4; a second submission at α₂ = α ÷ 6 admits at
most 2: 0.0425 at 2 and 0.0505 at 3); and the discovery scopes in the token give no way to read the 200 sealed
worlds.

Both sessions exist as workflow files and as executable scripts over the fixtures, so the documented commands
are tested commands. The step form of `studio_loop` and `mission_query` is N32a-26's (the files it writes and
the prompts serve); this bead adds the commands and prose of the two sessions to those files and keeps their
steps equal: each command of a session instantiates one step of its workflow, in the workflow's order, and a
change to the steps edits the file and the expected lists in one commit.

**Session transcripts (consumed; built by N32bx-01).** For every call in a session the daemon records one row of
`frob.session-transcript/1`: `seq`, surface, verb, the resolved request digest, the idempotency key, the job,
`ok`, exit and refusal code, the stable envelope digest and the result digest, cost, budget after the call, the
focus, a harness turn marker and the operational instants. `session.show --transcript` returns it, paged. It
contains identifiers and digests, not private content. The fresh-agent runner reads it to count turns, check
budgets and reproduce answers; the diagnosis battery and the surface A/B read the same record. Each task session
is opened with `capture: "strict"` (N32bx-01), so that every row is written by the daemon and none by the process
under test.

**The fresh-agent test.**
1. *Tasks.* 20 scripted studio tasks in `crates/frob-conformance/fixtures/tether/studio_tasks/` (DESIGN split):
   3 orient (what is implemented on this device; which template fits a brief; what a refusal code means), 5
   author (create from a template; find the planted undersized actuator with `design.check`; repair it with the
   ranked typed edit; import a robot and read its loss report; close a mass budget), 4 simulate (estimate before
   running and stay inside a stated budget; run and report the success rate with its evidence class; hold a long
   job through exit 8; replay one world on the referee), 4 diagnose (name the first cause of a planted failure;
   retrieve the still at failure; read a quantity under a pixel; distinguish a budget stop from a physical
   failure), 4 compare (plan and submit a paired study; read the verdict and pair counts; promote a provisional
   result; refuse to call an inconclusive comparison a win). Each task has a brief, a per-task budget, and a
   machine-checkable truth taken from the design corpus's planted defects and winners.
2. *The agent.* A fresh-context session of a pinned harness and model with no access to this repository or its
   plan. It receives the brief and the tool surface (MCP, default launch configuration) and may read
   `robot-docs`. Nothing else.
3. *Run.* One fresh session per task, in its own namespace under `session.open` with the task's budget and
   `capture: "strict"`; the runner passes a turn marker per agent turn (`FROB_TURN` on the CLI, request metadata
   `frob/turn` on MCP); a wall-clock ceiling per task; the transcript is read with `frob session show
   --transcript --json` and saved with its digest; turns and simulations are counted from it with N32b-38's
   `transcript_counts` functions, the one definition the diagnosis battery also uses (a second count in the
   runner is not written).
4. *Score.* A task is correct when the agent's stated answer matches the truth **and** a clean client
   reproduces it from the session's receipts. A budget violation is a task that ends in `FROB-REF-702` (budget
   exhausted during a run) or whose recorded spend exceeds its per-task budget (DESIGN definition).
5. *Decision.* Pass: at least 18 of 20 correct and zero budget violations, in the registered primary
   configuration. Other harness configurations are run and reported, not gated. The registration (tasks,
   truths' digests, configuration, scorer commit) is committed before the first session.

Evidence: the gate is a Design comparison claim of class `Tested`; its record carries the transcripts' digests.

## Acceptance criteria

- [ ] GATE-TETHER-01 (TARGET): a fresh agent given only `robot-docs` completes 20 scripted studio tasks with at least 18 correct and no budget violation; the record lists each task's outcome, spend, turns and transcript digest, and is recorded with `cargo run -p frob-conformance --example record_gate -- --gate GATE-TETHER-01 --receipt <hash>`.
- [ ] `frob robot-docs` (all modes), the documentation resources, the prompts and the skill file regenerate from one source; `xtask check-generated` fails when any is stale.
- [ ] Both worked sessions run as scripts on the fixtures with the documented exit codes at every step.
- [ ] Every verb in the registry has one long form (`robot-docs --verb <name>`) with a purpose, an example and its refusals, and is listed on the cluster page of every task cluster it sits in; every refusal code has a repair line.
- [ ] `robot-docs --budget n` stays within n (by N32b-17's token estimate, ⌈UTF-8 bytes ÷ 4⌉) and ends with drill-down handles when content was omitted.
- [ ] The guide contains no text that originated in an import (the hostile-corpus check passes).
- [ ] Every task session is opened with `capture: "strict"`; the runner's turn and simulation counts are those N32b-38's `transcript_counts` computes from the session's `session.show --transcript` rows (N32bx-01), and a session whose transcript has a `not-recorded` row is scored from the ledger, never from the agent's account.
- [ ] The scorer is validated on planted transcripts: a correct answer without supporting receipts is scored incorrect; a session that overspent is scored as a budget violation.

## Test plan

### Unit tests (`cargo test -p frob-verbs docs`, `cargo test -p frob-conformance studio`)
- `guide_pages_present`: the eight pages of N32b-17 in order, each with the content listed above.
- `every_verb_has_one_long_form`; `every_verb_on_its_cluster_pages`; `every_refusal_has_repair`.
- `budget_tokens_respected`: `--budget` 1,000, 4,000 and 20,000.
- `exit_code_table_in_guide_matches_registry`.
- `worked_sessions_follow_workflow_files`: each command of both sessions maps to one step of its workflow file (`studio_loop`, `mission_query`), every step is instantiated, and the order agrees; a planted command with no step, or a step with no command, fails.
- `workflow_one_steps`: the thirteen commands of session one in order; `workflow_two_has_qualification_arithmetic`: α₁ = 0.025 admits at most 3 of 200; α₂ = α ÷ 6 admits at most 2.
- `runner_opens_strict_sessions`: every task session the runner opens has `capture: "strict"`.
- `runner_counts_from_transcript`: on a recorded transcript of 30 rows with 6 turn markers and 4 `sim.run` rows
  that each created a distinct job (fixture labelled `synthetic`), the runner reports 6 turns and 4 simulations,
  and its counts equal `transcript_counts`' on the same transcript (the runner calls N32b-38's functions).
- `scorer_requires_receipts`; `scorer_flags_702`; `scorer_flags_overspend`.
- `registration_precedes_sessions` (commit-order check).
- `twenty_tasks_have_truth_digests`.

### End-to-end script and logging
`scripts/e2e/worked_sessions.sh` (header: `bead=BD-313 milestone=M3 labels=tether,docs,sessions seed=313
needs=cpu,frobd`) runs both worked sessions against `frobd` on the fixtures (the studio half through N32b-15's
`session_studio.sh`, the mission half once N32b-16 exists, otherwise a logged skip) and asserts each step's exit
code and the continuity of identifiers between steps. `scripts/e2e/fresh_agent_studio.sh --config <harness
configuration> --seed <s>` (header: `bead=BD-313 milestone=M3 labels=tether,fresh-agent gates=GATE-TETHER-01
seed=313 needs=cpu,frobd,mcp plants=empty-guide,guessing-agent,starved-budget`, each plant one negative control
below) runs the registration check, then for each of the 20 tasks opens a
namespace, launches the fresh agent with the brief, enforces the ceilings, saves the transcript, and runs the
scorer and the clean-client reproduction. Both source the shared helper and write NDJSON under
`target/e2e-logs/worked_sessions/` and `target/e2e-logs/fresh_agent_studio/` with transcripts beside them. Every
line has `ts`, `script`, `bead` (`BD-313`), `step`, `event`, the exact command or tool call, exit code, wall
time and the envelope's `evidence` block; per task `metric` lines: correct or not, reproduced or not, spend per
unit against the task budget, tool calls, serial turns, refusals met by class; overall `metric` lines: tasks
correct (threshold 18 of 20), budget violations (threshold 0). On failure: the task, the agent's answer, the
truth's digest and the transcript path. The `summary` names GATE-TETHER-01. Agent prompts and replies are stored
with the run; no private-scene data is logged.

### Known answers and negative controls
- Known answers: the exit-code sequence of both sessions; KA-762 as used in session two (one-sided exact binomial upper bounds for 200 worlds at α = 0.025: 0.0183, 0.0275, 0.0357, 0.0432, 0.0504 for 0 to 4 failures); KA-760 (Σ over i = 1..n of α ÷ [i·(i + 1)] = α·n ÷ (n + 1) < α).
- Negative controls (the gate must be able to fail): the same 20 tasks with `robot-docs` replaced by an empty guide must score below 18 (if they do not, the tasks do not test the documentation and the set is revised before the gate is read); a scripted "agent" that guesses answers without calling verbs must fail the receipt check; a task run with a budget too small to finish must be scored as a violation.
- Determinism lanes: the worked-session scripts twice on one machine with identical digests; the fresh-agent sessions are observations of a model and are reported with their configuration and seed, not expected to repeat exactly.

## Considerations

- A threshold of 18 of 20 on one run has sampling noise; the record also reports the per-task outcome over three seeds so that a pass on the margin is visible as such. The gate itself is the registered run.
- The agent must not have seen the plan or the repository; the runner checks the harness's working directory and network policy and records them.
- If the kill gate KILL-MCP fired, the fresh agent uses the CLI (or the socket-fallback MCP); the record states the surface.
- Documentation is part of the frozen surface: after the M3 freeze, changes to the guide are versioned so that later fresh-agent results name the guide they used.
- Worked numbers are illustrative; the scripts assert exit codes and invariants, not the illustrative figures.
