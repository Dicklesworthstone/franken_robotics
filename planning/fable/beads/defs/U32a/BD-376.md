## Background

Milestone M4 adds amortized control, co-design and mission queries at scale to FrankenRobotics: family policies
and inheritance, the evaluation ladder and the six-stage cascade, gait orbits with continuation, skill artifacts
and runtime shields, optimization with lineage, registered predictions, experiment suggestion, wheels, tracks
and soil. This bead registers their verbs: every verb whose first milestone is M4 becomes an entry of
`registries/verbs.toml` (compiled into the static table of the crate `frob-verbs`, from which the CLI, the MCP
tools, the schemas and the agent guide are generated) with an input schema, an output schema, at least one
runnable example and a refusal list, and the surface parity gate is recorded for the M4 set.

As before this is integration work: each verb's computation is built by its subsystem's bead (this bead's
dependencies), and gets here its thin binding, registry entry, schemas, golden envelope and honest status. Two
things are particular to M4. Many M4 verbs are tier Frontier, so their status depends on a pilot and a
kill-gate decision being on record (a Frontier capability is "implemented" only then, and one that fell back at
its kill gate is described by the name of its fallback). And one verb defined by the surface chapter has no
other home and is built here: `result.show`.

GATE-TETHER-02 (Known answer, TARGET): the CLI and MCP surfaces are generated from the registry and their parity
diff is empty; every verb has a schema, an example and a refusal list; the served `tools/list` equals the
registry under the name map (`.` and `-` replaced by `_`).

## Scope

In: registry entries (those no cluster registry bead enters), schemas, examples, refusal lists, bindings, golden
envelopes and status for the M4 set; the check that each M4 verb is seated in NJL-05's task-cluster assignment
(the assignment and its lints are NJL-05's, a dependency); the handler of `result.show`; tier and fallback status for Frontier verbs; the M4
additions to the freeze; the M4 parity record. Out: each other verb's computation; `solve.run` itself (BD-372);
the surface A/B and the mission-session gate.

## Technical approach

**The checklist per verb** (unchanged): a complete entry; two schemas whose integers are only `int53`, `u64str`
or `i64str`, with units on quantities and the untrusted mark on fields that echo imported text; a runnable
example; a refusal list (the handler's chapter codes; the generator appends the codes of its kind and of its
fields, NJL-01's variations, as BD-312 lists them, and no row repeats them); a golden envelope; a binding with no
computation; a truthful `capabilities` row.

**`result.show` (read; cluster `result`; task cluster `proofs`; tier Solid).** Purpose: a stored result with its
claim product and dependencies, so that an agent can see what an answer rests on before citing it. The row
(capability `result:read`, output schema `frob.result.show.out/1`, `paginated = true`, example `frob result show
a:8b27 --json`) is VERBS-result's, a dependency; this bead builds the handler it names and enters no second row.

| Aspect | Rule |
|---|---|
| Input | `result` (the identifier of a stored result: a run summary, a study answer, a mission answer, a promotion, a campaign result); optional `depth` (default 1) for the dependency listing |
| Output | The result as stored (the same bytes its producing verb returned); its claim product in full (kind, class, the weakest input that set the class, tier, determinism, reality scope, conditions); `inputs`: every consumed artifact with its own claim product, paged; `standing`: `current`, or `invalidated` with the change that invalidated it and the cost of the rerun, as the revalidation engine reports it |
| Reads | The result store and the memo graph's derived-key edges (BD-111) for `inputs` to `depth`; the revalidation engine at grades 3 and 4 (BD-347) for `standing`. Nothing else |
| Refusals | Chapter codes of the row: the sealed-read refusal `FROB-REF-840` (N39-REF) for a result of the blinded lane beyond its verdict and receipt; `FROB-REF-869` (N29a-10's rule) for a result whose evidence closure is dangling or tombstoned. Appended for a paginated `read`: 720 (the row's `result:read`; the handler also checks `<cluster>:read` of the result's producing cluster, with `required` naming it), 723, 724, 802, 806, 807, 808 |
| Evidence | The stored result's own (pass-through); `result.show` adds none |
| Property | `result.show` never recomputes: a test asserts no job is created and the returned result bytes equal the stored bytes |

**Frontier status.** For each Frontier verb of the set the `capabilities` row states one of: `implemented`
(pilot and kill decision on record, and all eight conditions of the plan's definition of "implemented" hold: code
in its mapped crate; a `CONTRACT.md` with its ten sections; known-answer tests against a pinned oracle; the claim
product on every output that reaches an agent; a CPU reference path, with a retained differential check where a
GPU path is claimed; reachable through `frob --json` and `frob-mcp` with a schema and exit code; cancellation
tested; a recorded gate PASS with measured values), `fallback: <name>` (its kill gate fired), or
`not implemented` with the missing conditions. The registry's `tier` field is checked against the mechanism's
tier in its bead.

**`solve.run` and the freeze.** The M4 entries are added to the freeze file at the end of this bead. KILL-SOLVE
is read in two clauses: clause 1 (N32ap1-01, a dependency) before the verb is built, clause 2 and the final status
(N32a-32) after the A/B. NJL-05's rule governs both: if KILL-SOLVE fires, the `solve.run` row is withdrawn from
the registry, the name `solve.run` moves to NJL-04's retired-name table with `use = ["opt.cascade"]`, and
`opt_cascade` takes the vacated seat in `search`, which keeps seven tools (`opt.cascade`'s `task_clusters` gains
`search`; it keeps its seat in `ladder`). This bead records the withdrawal. If clause 1 fired, the entry is never
frozen: the retired name and the seat swap are in the M4 freeze from the start. If clause 1 read `proceed` and the
final status is still pending, the entry is frozen as Frontier, and its later withdrawal, should clause 2 fire,
is a recorded change in `registries/verbs.changes.toml` together with the retired name and the seat swap. Either
way the measured registry counts are lowered by one verb under NJLx-51's counting rule. (An earlier draft of this
bead left `search` at six tools; NJL-05 rejected that.)

**Task clusters** (as NJL-05's assignment seats the M4 verbs; that table governs and this bead checks it).
`search` (`opt_start`, `opt_status`, `opt_archive`, `design_bisect`, `design_blame`, `solve_run`,
`experiment_suggest`; under KILL-SOLVE `opt_cascade` in place of `solve_run`); `compare` gains
`experiment_suggest` and `predict_register`; `gaits`, `shield`, `inherit`, `ladder` and `families` fill as
assigned; `proofs` gains `result_show`.

**Gate run.** `scripts/e2e/tether_parity.sh --through M4`.

## Test plan

### Unit tests (`cargo test -p frob-verbs handlers_m4 result_show`)
- `every_m4_entry_complete` (table-driven checklist).
- `result_show_bytes_equal_stored`; `result_show_creates_no_job`; `result_show_inputs_paged`.
- `result_show_standing_after_edit`: a result that depends on a design edited afterwards shows `invalidated` with the edit's identifier.
- `result_show_sealed`: a qualification result returns its verdict and receipt only; asking for its inputs beyond them → `FROB-REF-840`.
- `result_show_tombstoned_869`: a result whose evidence closure holds a tombstoned artifact → `FROB-REF-869`, exit 3.
- `result_show_producing_cluster_scope`: a session holding `result:read` but not `nemesis:read` asks for a `nemesis.search` result → 720 with `required: "nemesis:read"`.
- `result_show_inputs_from_memo_graph`: `depth` 1 and 2 list exactly the derived-key edges of the memo graph for a planted three-level result.
- `claim_product_fields_complete`: kind, class, weakest, tier, determinism, reality, conditions all present.
- `frontier_status_three_forms`: a synthetic Frontier verb with no pilot record is `not implemented`.
- `strategy_enum`: `codesign`, `linkage`, `refine` accepted; `continuation` is declared for a later milestone and answers 724; `foo` is 802.
- `search_cluster_follows_kill_decision`: with a clause-1 entry `fired: ceiling`, `search` lists seven tools with `opt_cascade` and no `solve_run`, `opt.cascade`'s `task_clusters` holds `search` and `ladder`, and `frob solve run` answers `FROB-REF-801`, exit 3, with `refusal.repairs[0]` naming `opt.cascade` (NJL-04's retired-name rule); with `proceed`, seven tools with `solve_run`; the registry count differs by exactly one verb between the two.
- `declared_verbs_724`: `foundry.loads`, `foundry.size`, `analyze.structure`, `ground.excite` (the four M4 rows of `LATE_ROWS`).

### End-to-end script and logging
`scripts/e2e/m4_verbs.sh` (header: `bead=BD-376 milestone=M4 labels=tether,registry,verbs gates=GATE-TETHER-02
seed=376 needs=cpu,frobd,mcp plants=show-recomputes,frontier-unpiloted,predict-as-read,unseated-verb`, each plant
one negative control below; `frobd` running with tokens): `frob predict register --metric success --interval 0.6
0.9 --confidence 0.8 --for next --key p1 --json`; `frob opt start --task stairs-0.4 --design quad-a --levers
thigh,knee_ratio --method cma-es --population 16 --budget gpu_s=600 --key o1 --sync-wait-ms 0 --json` (exit 8);
`frob opt status <campaign> --json`; `frob job wait <job> --json`; `frob opt archive --campaign <campaign> --top 3
--json`; `frob experiment suggest --study <plan> --json`; `frob result show <result> --json` before and after a
`frob design edit quad-a set-param foot.radius 0.030 m --expected-parent <head> --key e1 --json`; `frob result revalidate quad-a
--since <version> --key rv1 --json`; `frob predict report --json`; then the parity script. It sources the shared
helper and writes `target/e2e-logs/m4_verbs/<utc>.ndjson` plus a
transcript: `cmd` lines with exit code and wall time; the envelope's `evidence` block per call; `assert` lines
for expected exits, for `result.show` byte equality and standing, for job-handle continuity; `metric` lines for
estimate against actual; a `summary` naming GATE-TETHER-02 (M4).

### Known answers and negative controls
- Known answers: empty diff with one exemption; registry, CLI and MCP counts equal for the M4 set.
- Negative controls (each must be caught): a `result.show` that recomputes a summary (the no-job assertion and the byte-equality assertion); a Frontier verb reported implemented without a pilot record; a `predict.register` registered as `read`; an M4 verb in no task cluster.
- Determinism lanes: generated documentation, the freeze file and golden envelopes identical twice on one machine, in debug and release, on both hosts.

## Considerations

- No seed bead names `result.show`; the verb appendix attributes its definition to the surface chapter, so its handler is carried here as a pure read over the result store.
- OPEN-ATEL-4 was decided at the M3 freeze (default: `result.revalidate` and `mission.revalidate` are two verbs over one engine); the M4 grades extend the engine, not the surface.
- Verbs first due at M6 and M8 (`control.lift`, `foundry.lifecycle`, `mission.transport` beyond its static core, `skill.transport`) have no verb-set bead of their own; they are registered as declared by the M5 verb-set bead so that the registry is complete, and their handlers come with their epics.
- With about forty dependencies, entries are registered as declared early and flipped as handlers land; the gate is recorded when the last M4 handler lands.
