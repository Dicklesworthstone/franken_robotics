## Background

Tether is the surface through which agents and people reach every other subsystem of FrankenRobotics (a robotics
simulation and design system whose users are mostly AI agents). It owns the verb registry, the result envelope,
sessions and capability tokens, the job ledger and the daemon's dispatcher, the MCP server (MCP is the Model
Context Protocol, the tool-calling protocol agent harnesses speak), the terminal dashboard and the viewer. It owns
**no physics and no statistics**: a verb's handler lives in the crate of the subsystem that answers the question.
Tether fixes how the question is asked, what it may cost, how the answer is labeled, and what happens when a
client, a connection or the daemon fails.

Because Tether is a thin layer that every other subsystem passes through, its design decisions are easy to erode
one convenient exception at a time (a verb with hand-written MCP code, a dashboard that reads the ledger file
directly, a retry that rebinds a moved name). This bead writes the decisions down once, as records in the
repository, and binds each to the test or lint that fails when the decision is violated. It carries no mechanism of
its own; the mechanisms are in the beads named in the tables.

A "verb" is one named operation of the system (`design.check`, `sim.run`). The "registry" is the file
`registries/verbs.toml` that defines every verb once. The "envelope" is the single JSON object every verb returns.
The "daemon" is the process `frobd` that owns devices and long-running jobs.

## Scope

In: the ownership map; the six principles; the eleven architecture decision records with reason, excluded
alternative, enforcing check and governing bead; a machine-readable index and the test that every record names a
live check. Out: every mechanism (the beads named below); the dashboard and viewer decisions' implementation (the
other Tether unit); the invariant and proof-obligation tests themselves, which live in the mechanism beads.

## Technical approach

**Files (DESIGN).** `docs/adr/ADR-TETHER-NN.md`, one per decision, each with the sections Decision, Reason,
Alternative excluded, Enforced by, Revisit when. `docs/adr/TETHER-PRINCIPLES.md`. `docs/adr/TETHER-OWNERSHIP.md`.
Every decision record of the program lives directly in `docs/adr/` (one place to look); a per-chapter
subdirectory such as `docs/adr/tether/` is not used.
An index `registries/adr/tether.toml` (schema `frob.adr-index/1`): one row per record with `id`, `status`
(`accepted`, `superseded`), `enforced_by` (a list of test or lint identifiers), `bead`.

**The six principles (each with its check).**

1. *One verb registry.* The registry defines each verb once: name, cluster, kind (`read`, `run`, `mutate`,
   `admin`), required capabilities, input and output schema identifiers, possible refusals, idempotency rule, cost
   model and examples. The CLI, the MCP tools, the schemas and the agent documentation are generated from it, and a
   parity gate diffs them. FACT: this is the design the sibling project FrankenMining adopted. Check: the parity
   harness (GATE-TETHER-02).
2. *Agents ask questions and spend budgets; they do not drive solvers.* A verb takes a question, a confidence or
   tolerance where relevant, and a budget; it answers, or it refuses and says what would make the question
   answerable. FACT: FrankenSim addendum proposal 8. Check: registry lint "no verb exposes a solver iteration, a
   step call or a kernel launch as its unit of work".
3. *The Five Explicits.* Units, seeds, budgets, versions and capabilities are never implicit (FACT: FrankenSim
   principle P10). Check: schema lint (every quantity field has a unit; every stochastic verb has a seed input and
   echoes it; every `run` verb has a budget property; every schema has a version; every entry lists capabilities).
4. *One application service, two adapters.* The CLI and the MCP server both link `frob-verbs` and call the same
   handlers in process through the same dispatch interface, and both hand long work to the daemon as jobs.
   Simulation ticks run inside a worker owned by the daemon; calls on the control plane act on whole designs, jobs,
   chunks and queries, never on single steps. DESIGN reason: a per-step remote call would put the agent's latency
   inside the physics loop. Check: `check-layers` (no per-verb code in `frob-cli` or `frob-mcp`), parity harness.
5. *Every answer says what changed.* After a run the envelope names the change the agent made, the first physical
   consequence of it, and the evidence for the comparison. Check: envelope conformance on `run` verbs.
6. *What is claimed for this surface.* MCP access to a simulator is prior art (FACT: one incumbent ships an MCP
   server for documentation lookup, and a community server exposes 42 tools that drive that simulator; neither
   documents compute budgets, provenance or a typed refusal taxonomy). The claim made here is narrower: every verb
   carries a compute budget, provenance and a typed refusal, and both surfaces are generated from one registry.
   Check: a documentation lint that the README and `robot-docs` use this wording and no broader one.

**The eleven decisions.**

| ADR | Decision | Reason | Alternative excluded | Enforced by | Governing bead |
|---|---|---|---|---|---|
| ADR-TETHER-01 | The registry is compiled into a static table in `frob-verbs` by its build script. Neither `frob-cli` nor `frob-mcp` contains per-verb code, with one exception: the MCP half of `session.focus`. | Parity by construction; the parity gate then checks the served surfaces, not the generator's intentions. | A hand-written command or tool per verb in each adapter. | Lint: a verb name literal in `frob-cli` or `frob-mcp` outside the one allowlisted file fails. | N32a-02 |
| ADR-TETHER-02 | `frob-verbs` has a `registry-only` feature with no dependency on any physics crate or on the airlock crate `frob-fsim`. | It is what the first fallback of KILL-MCP links: `frob-mcp` built as its own workspace must still share the table, the schemas and the envelope types. In the default build `frob-mcp` links `frob-verbs` whole. | A copy of the registry types in a second crate. | `cargo tree -p frob-verbs --no-default-features --features registry-only` lists no physics crate. | N32a-02 |
| ADR-TETHER-03 | `frob-mcp` is a protocol adapter with one dispatch trait and two back ends: in-process handlers (the default) and a local socket to `frobd`. In the default build it links `frob-verbs`, runs verbs in process and hands long work to `frobd` as a job. The socket-only form is complete on its own and is the first fallback of KILL-MCP. | The daemon owns devices and jobs in any case; a killed adapter must never own a job; the fallback must be reachable without redesigning the adapter. | An MCP server that owns device work, or one that can only work across a process boundary. | Kill tests (INV-TETHER-10); the socket back end passes the same conformance suite. | N32a-04 |
| ADR-TETHER-04 | Long tools take a bounded synchronous wait, `sync_wait_ms`, and otherwise return a job handle. | Most studio verbs finish inside the wait (TARGET: `design check` under 2 s, `control synth` under 5 s), and an agent turn is believed to cost 30 to 120 s of thinking (HYPOTHESIS, measured in GATE-TETHER-13), so an avoided poll saves more than the compute it waits for. | Always block to completion; always return a handle at once. | GATE-TETHER-12 (return within the wait plus 500 ms). | N32a-16 |
| ADR-TETHER-05 | Wire cancellation of a waiting call ends the wait, not the job. `job.cancel` cancels the job. | A client timeout is not a decision to discard admitted, charged work; the job is recoverable by its key. | Cancel the job whenever the caller goes away. | INV-TETHER-11 tests. | N32a-17 |
| ADR-TETHER-06 | The MCP Tasks extension is an optional adapter over the job ledger, never the primary contract. | The library labels it experimental and provisional (FACT); the handle contract works on every client and protocol era. | Tasks as the only way to hold a long job. | The handle contract passes with the Tasks adapter compiled out. | N32a-30 |
| ADR-TETHER-07 | The daemon dispatches episodes into slots of a persistent environment per device and shape class, not one environment per job. | One paired comparison fills about 2.3% of a batch; without sharing, the rest of the device idles. | One environment per job (kept as the fallback of KILL-SLOT). | GATE-TETHER-09. | BD-295 |
| ADR-TETHER-08 | The scheduler decides when work runs and never what is computed. No wall-clock quantity enters a result. | Feedback from load into results breaks replay and makes verdicts depend on who else was running. | Load-adaptive solver effort or sample counts. | INV-TETHER-09 tests; GATE-TETHER-10 (digests identical under random preemption). | N32a-21, BD-296 |
| ADR-TETHER-09 | Integers that can exceed 2⁵³ − 1 travel as decimal strings; counts are range-checked numbers. | Clients that decode JSON numbers as doubles silently change larger values. | Every integer as a JSON number; every integer as a string. | Schema lint; GATE-TETHER-07. | N32a-07 |
| ADR-TETHER-10 | The dashboard and the viewer are ordinary clients. Each value they show is obtainable by a named verb. | No private interface means no unaudited path to state, and agents without eyes lose nothing. | A dashboard that reads the ledger or device state directly. | GATE-TETHER-14 (every displayed number reproduced by its source verb); INV-TETHER-12. | N32b-06 (the dashboard core) and N32b-10 (the viewer page); measured by N32b-09 and N32b-14 |
| ADR-TETHER-11 | Mutating and job-submitting verbs bind immutable identifiers. A mutable name is resolved once, before the request is digested, and the resolution is echoed. | Otherwise a retry after a name has moved would mean a different request under the same key. | Digest the request as typed, names included. | Idempotency tests with a moved name; the `bound` field of the envelope. | N32a-09 |

**The check that binds them.** `crates/frob-conformance/tests/adr_tether.rs` loads the index, asserts that the
eleven identifiers are present exactly once, that each `enforced_by` entry names a test, lint or gate that exists
in the conformance registry at the current milestone (entries for later milestones are marked `pending` with the
milestone), and that no record is `accepted` with an empty `enforced_by`. The checks the records name are built by
the beads that make the crates they guard, all of which depend on this one: the verb-literal lint of
ADR-TETHER-01 and its planted test `verb_literal_lint_catches_plant` (BD-022 for `frob-cli`, BD-023 for
`frob-mcp`), the crates' `CONTRACT.md` files citing the records that constrain them (BD-022 for `frob-verbs` and
`frob-cli`, BD-023 for `frob-mcp`), and the assertion that `robot-docs` states the surface in principle 6's
wording (BD-022's script). This bead's index lists them `pending` until those beads land; it builds none of them.

Determinism class: not applicable (documents and a registry file). Evidence class of the check: Tested.

## Acceptance criteria

- [ ] Eleven ADR files `docs/adr/ADR-TETHER-01.md` to `-11.md` exist with all five sections; `docs/adr/TETHER-PRINCIPLES.md` holds the six principles with their FACT and DESIGN labels; `docs/adr/TETHER-OWNERSHIP.md` holds the seven-row map with tiers and first milestones; no directory `docs/adr/tether/` exists.
- [ ] `registries/adr/tether.toml` validates against `frob.adr-index/1` and lists ADR-TETHER-01 to -11.
- [ ] `cargo test -p frob-conformance --test adr_tether` passes, and fails when an `enforced_by` entry is removed or names a missing check (negative control).

## Test plan

### Unit tests
- `adr_index_complete`: the index has exactly ADR-TETHER-01 … -11; a duplicate or a gap fails.
- `adr_enforced_by_resolves`: every entry resolves to a registered check or a `pending` entry with a milestone no later than the record's own first milestone.
- `principle_lints_registered`: the four lints named under the principles are registered in the lint table.
- `ownership_map_matches_crate_map`: every crate named in `docs/adr/TETHER-OWNERSHIP.md` exists in the workspace manifest once the crate lands (skipped with a recorded reason before that).

### End-to-end script and logging
`scripts/e2e/tether_adr_record.sh`: runs the conformance test and logs, per record, the check it resolved or its
`pending` milestone (the guide's wording of principle 6 is asserted by BD-022's script, which builds `robot-docs`;
this bead runs no `frob` command). Logging per the shared helper:
NDJSON to `target/e2e-logs/tether_adr_record/<utc>.ndjson` with `ts`, `script`, `bead`, `step`, `event`, the
command line, exit code, wall time; one `assert` line per record with the resolved check; a final `summary` with
counts. No private-scene data.

### Known answers and negative controls
- Known answer: the index count is 11; the principle count is 6; the ownership rows are 7.
- Negative controls: delete one `enforced_by` entry (the test must fail and name the record); mark a record `accepted` while its check is `pending` beyond its milestone (the test must fail). (The planted verb literal is BD-022's and BD-023's control.)
- Determinism lane: the generated index digest is identical twice on one machine and on both hosts.

## Considerations

- OPEN-TETHER-1 (whether `frob-mcp` can link handler crates in process) is decided, by the owner on 2026-11-22: `frob-mcp` is a member of the core graph and runs verbs in process, once the upstream work item FD-FMCP-01 has brought `fastmcp_rust` onto the one toolchain T. The record of ADR-TETHER-03 states this and names the fallbacks of KILL-MCP.
- A record is never deleted: a changed decision gets status `superseded` and a successor.
- Revisit triggers to write into the records: KILL-MCP firing (ADR-02 and -03 become the design of record for the fallback); KILL-SLOT firing (ADR-07 is superseded by per-job dispatch); KILL-MCPTASKS firing (ADR-06 loses its adapter and keeps its rule).
- The crate split of the daemon (process shell in `frob-cli`, job engine library in `frob-verbs`) reconciles two statements of the plan (the ownership table names `frob-cli`; the crate map gives `frob-verbs` the job engine); it is recorded in `docs/adr/TETHER-OWNERSHIP.md` as DESIGN.
