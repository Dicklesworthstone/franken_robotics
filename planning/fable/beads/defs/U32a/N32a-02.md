## Background

FrankenRobotics exposes every capability as a **verb**: one named operation with a typed input, a typed output and
a list of typed refusals. There will be about 243 of them in about 44 clusters (FACT about the plan's inventory:
163 verbs in 34 clusters found mechanically, 55 named by chapters, and 25 further `analyze` verbs; a recount of the
chapter list gives 56, so the registry's own count is authoritative and no test hard-codes 243 or 44). Two surfaces serve them: the
command line `frob` and the MCP server `frob-mcp`. If each surface described its verbs by hand they would drift:
a flag present on one and missing on the other, a refusal documented and never returned.

The decision (ADR-TETHER-01) is that the file `registries/verbs.toml` defines each verb once, and that a build
script in the crate `frob-verbs` compiles it into a static table. The CLI parser, the MCP tool definitions, the
JSON schemas, the refusal lists and the agent documentation are all read from that table. Neither `frob-cli` nor
`frob-mcp` contains per-verb code, with one exception: the MCP half of `session.focus`, which edits the visible
tool set. Reason: parity by construction, so the parity gate (GATE-TETHER-02) checks the served surfaces and not
the generator's intentions. Alternative excluded: a hand-written command or tool per verb in each adapter (the
usual design, and the source of drift).

A second decision (ADR-TETHER-02): `frob-verbs` has a feature `registry-only` with no dependency on any physics
crate or on the airlock crate `frob-fsim` (the one crate through which FrankenSim, the sibling physics library, is
reached). Reason: it is what the first fallback of the kill gate KILL-MCP links. If the MCP server cannot join the
core build graph it is built as its own workspace, and it must still share the table, the schemas and the envelope
types. In the default build `frob-mcp` links `frob-verbs` whole.

Terms. A **cluster** is a namespace (`design`, `sim`). A **kind** is one of `read` (returns stored or cheaply
computed facts and changes nothing), `run` (spends compute, takes an idempotency key and a budget, accepts the
bounded synchronous wait and otherwise returns a job handle with exit code 8), `mutate` (creates or changes a
named object in the caller's namespace and takes an idempotency key and an expected parent), `admin` (cancels,
stops, evicts or deletes and needs a capability scope). A **task cluster** is a set of at most seven tools chosen
for one activity, which is what an agent sees listed at a time.

## Scope

In: the registry file format and its schema; the schema of one `[[verb]]` entry, field by field (the one
definition of it); the name grammar, the CLI path and the name map to MCP tool names; schema identifiers and the
place of schema files; the build script and the generated table with its emitted type; task-cluster
declarations; every build-time registry lint with its planted registry; the `registry-only` feature and its
dependency test.

This bead and NJL-01 had each specified the entry schema, the name rules, the emitted type and the lints. They
are stated once, here, because this bead is the component of the seed BD-022 that the loader is built on and
therefore lands first. NJL-01, which follows this bead and comes before both surfaces (the CLI of BD-022 and the
MCP server of BD-023 call its members), keeps what is derived from an entry by its kind: the common input
properties and the surface-wide refusals the generator adds, the dispatch of two-kind verbs, the wait default as
served and the answer of an unimplemented verb; its checks on the served surfaces are stages of its script that
later beads run. The row beads (`VERBS-<cluster>`) depend on NJL-01 and through it on this bead.

Out:
the envelope types (N32a-03); the generator rules by kind and the behaviour on the served surfaces (NJL-01); the integer schema types and their lint (N32a-07); the dispatch interface (N32a-04);
the entries of each milestone (BD-022 for M0, BD-137, BD-222, BD-312, BD-376, BD-409); the parity harness that

## Technical approach

**One entry (schema `frob.verbs/1`; the first block is the plan's example, the rest DESIGN).**

```toml
[[verb]]
name = "design.check"
cluster = "design"
kind = "read"
tier = "S"                                   # S, F or M
capabilities = ["design:read"]
input_schema = "frob.design.check.in/1"
output_schema = "frob.design.check.out/1"
refusals = ["FROB-REF-101", "FROB-REF-104", "FROB-REF-107", "FROB-REF-110"]
idempotent = true
cost_model = "static: under 2 s for template-sized designs"
first_milestone = "M1"
task_clusters = ["author", "places"]
examples = ["frob design check quad-a --json"]
# DESIGN additions
purpose = "Run the preflight stages and the analyses marked for check; return findings with ranked repairs."
use_when = "After any edit and before any simulation."
owner = "frob-design"    # the crate whose handler answers (illustrative here)
schema_version = 1
paginated = false
exports = false          # true: the envelope carries the three no-authorization flags
estimable = false        # true: accepts --estimate / estimate_only
```

A `run` verb adds `wait = { cli = "to-completion", mcp_ms = 5000, mcp_max_ms = 30000 }` (the per-surface default
is a registry field so the parity gate knows about it). An `admin` verb adds `destructive = true|false`. A verb
with more than one action has one `kind`, the kind of its default action, and an `actions` list for the others,
for example `actions = [{ name = "evict", kind = "admin", capabilities = ["spark:admin"] }]`; the invoked action
is the input property `action`, and the common properties and required capabilities are those of the selected
action (how that is served is NJL-01's). The plan prints three verbs with two kinds (`nemesis.hardset` read and
run, `scene.bank` read and admin, `spark.cache` read and admin); the cluster rows add nine more that use the
same form (NJL-01 lists the same nine): `session.show` (`audit`, a second `read` action with its own scope
`session:audit`), `sense.symmetry` (`test`, `run`), `design.diff` (`run-control`, `run`, from M3), `ground.band`
(`retire`, `admin`), `nemesis.audit` (`prepare`, a second `run` action), `spark.check` (`list`, `read`, scope
`spark:read`, with its own `paginated = true`), `task.check` (`coupling`, `run`, scope `task:run`, from M2),
`eval.ledger` (default `read`; `open`, `close`, `seal`, each `admin` with `eval:read` and `qual:admin`,
VERBS-eval) and `scene.split` (default `create`, a `mutate`; `add` and `move-group`, `mutate` with
`scene:write`, and `show`, `check`, `part-of`, `audit`, `read` with `scene:read`, VERBS-scene). An action entry
may repeat its entry's kind when only the scope differs. The default action has no name: it is the call without
`action` (NJL-01 action rule 1). Rejected: two registry names per verb (it would add a
spelling the chapters do not use).

An action table has the members `name`, `kind` and `capabilities`, and two optional ones (DESIGN, requested by
the cluster rows and by NJL-01's annotation rule). `paginated` (bool, default `false`, a `read` action only,
lint `RL-23`): the action returns pages, so the generator gives that action `cursor`, `limit` and `follow` and
appends 806 and 807 to it, as the entry-level field does for a `read` entry. `destructive` (bool, an `admin`
action only, lint `RL-08`; default `true`): feeds the MCP annotation `destructive` of the entry. The default is
`true` because the annotation is a hint to a client to ask for confirmation, and the safe default for an
action that cancels, evicts or deletes is to ask; an `admin` action that removes nothing writes `destructive =
false`.

**The fields of one entry.**

| Field | Type | Rule |
|---|---|---|
| `name` | string | Unique. Grammar below. The name its owner chapter gives the verb; no second spelling exists (NJL-04). |
| `cluster` | string | The registry namespace. Equals the part of `name` before the dot; the four operator verbs (`doctor`, `capabilities`, `robot-docs`, `schema`) have no dot and `cluster = "operator"`. |
| `kind` | `read` \| `run` \| `mutate` \| `admin` | The four kinds are defined in the Background; what the generator adds for each kind (common input properties, appended refusals) is the kinds table of NJL-01. |
| `tier` | `S` \| `F` \| `M` | Maturity of the mechanism. An `F` or `M` verb is listed by `frob capabilities` with its pilot and kill gate. |
| `capabilities` | list of scopes | Scopes of the session token the verb needs. Every scope must exist in the scope registry; a call without one is `FROB-REF-720`, exit 5. |
| `input_schema`, `output_schema` | schema identifiers | `frob.<cluster>.<verb>.in/1` and `.out/1` (operator verbs: `frob.<verb>.in/1`), or a named artifact schema where the verb returns an artifact (`frob.verdict/1`, `frob.plan/1`). The trailing integer is the major version. |
| `refusals` | list of codes | The chapter-specific refusals the verb may raise. Each must exist in `registries/refusals.toml`. Surface-wide refusals are appended by the generator by kind and are not repeated per row (the kinds table of NJL-01). |
| `idempotent` | bool | `true` when repeating the call changes nothing (every `read`; an `admin` cancel or stop). For `run` and `mutate` it is `false` and the generator adds the required `idempotency_key`: a retry with the same key and the same resolved content returns the stored receipt. |
| `cost_model` | string | `static: <bound>` for a verb with a stated bound, or the name of the estimator `--estimate` uses. Never empty. |
| `first_milestone` | `M0`…`M8` | The milestone the appendix gives the verb. Whether a verb answers is decided by its handler being in the build, never by this field (NJL-01): a verb without a handler answers `FROB-REF-724`, and a reduced form that lands earlier answers. |
| `task_clusters` | list | The task clusters that list the tool. At least one; `["base"]` for the three always-listed base tools. |
| `examples` | list | At least one complete command line that the end-to-end script of the cluster runs verbatim after the example-identity substitution of the conformance harness NJL-02: an abbreviated identity as the plan prints it (`r:19e2`, `d:7a3e`, a job handle `j:77c0`) is replaced by the full identity that `fixtures/verbs/identities.toml` gives it, and nothing else of the line changes. |
| `purpose`, `use_when` | strings | DESIGN additions (the appendix shows no field for them, but the generated tool description needs one sentence of purpose and when to use the tool). `purpose` ≤ 200 characters. |
| `owner` | crate name | DESIGN addition: the crate whose handler answers. Used by the layer check (a handler lives in the subsystem crate, never in `frob-cli` or `frob-mcp`). |
| `wait` | table, `run` only | The per-surface default of the bounded synchronous wait: `{ cli = "to-completion", mcp_ms = 5000, mcp_max_ms = 30000 }`. A registry field so that the parity check knows the one sanctioned per-surface difference. |
| `actions` | list of tables | Only for a verb with two kinds (above): one table per further action, `{ name, kind, capabilities }` with the optional members `paginated` and `destructive`. |
| `released` | bool, default `false` | DESIGN addition used by the workspace contract check (N34-09): `true` once a release lists the verb as a released capability. A released verb must have a demo whose commands invoke it; the check reads this mark until the release manifest lists released capabilities, and the manifest governs from then on. |
| `params` | table, optional | DESIGN addition owned by the artifact-input stage of `frob-verbs` (N34-24): for each input property that takes an artifact or a foreign file, its parameter kind: `artifact-input<F>` (any spelling or a registered view, read by the format's owner), `artifact-ref<F>` (an identity or a name resolved in the store), `artifact-identity<F>` (an identity or exactly canonical bytes; a view is refused with `FROB-REF-892`) or `foreign-file` (bytes of a format this project does not own, carrying the untrusted mark), with F a registered format. |
| `schema_version` | integer, default 1 | The major version of the entry's own schemas; equals the trailing integer of `input_schema` and `output_schema`. |
| `paginated` | bool, default `false` | A `read` that returns pages; the generator then adds `cursor`, `limit` and `follow` and the codes 806 and 807 (NJL-01's variation 1, which applies to the `read` kind only: a second call of a `run`, `mutate` or `admin` verb with a cursor would be a second job or change, not the next page). Allowed only on an entry whose default action is `read` (lint `RL-23`). A paginated action carries its own `paginated` member (the action table above). |
| `exports` | bool, default `false` | `true`: the envelope carries the three no-authorization flags. |
| `estimable` | bool, default `false` | `true`: the verb accepts `--estimate` / `estimate_only`. |
| `destructive` | bool, `admin` only | Feeds the MCP annotation of the same name. |
| `public` | bool, default `false` | Must be `true` when `capabilities` is written as an empty list (lint `RL-10`). |
| `key_optional` | bool, default `false` | DESIGN addition for the two exemptions from the mandatory idempotency key (N32a-09): a `mutate` verb whose result identifier is the content address of its resolved request (`study.plan`), and `session.focus`, whose mutation sets the caller's focus to the requested cluster, so a repeat changes nothing (the plan's worked session calls `session_focus {cluster}` with no key). The key stays accepted; the appended refusal list of such an entry omits `FROB-REF-805`. Lint `RL-21`. |
| `option_capabilities` | map from input property to list of scopes, default `{}` | DESIGN addition requested by the token beads (N32b-01, N32b-04): the scopes one input option needs in addition to `capabilities`, for example `session.show` has `option_capabilities = { all = ["session:read"] }`, so reading one's own session needs no scope while listing every session does. The token check of N32b-01 applies an option's scopes when the option is present in the request; the scope-catalogue lint counts a scope used only by an option as used. Lint `RL-22`. |
| `spends_physics` | bool, optional | DESIGN addition requested by the diagnosis battery (N32b-38): `true` when a call can create a job that runs physics (`sim.run`, `eval.run`, `eval.compare`, `study.submit`, …), `false` for a `run` or `mutate` verb that cannot (`sense.causal-test`, the estimate verbs). Optional here; N32b-38's lint `spends-physics-declared` (M3) makes it required on every `run` verb and every `mutate` verb that can create a job, and this build script runs that lint once N32b-38 lands. |
| `conformance_only` | list of input property names, default `[]` | DESIGN addition requested by the Spark rows (`--mutant`, `--withhold-kernel`, `--chunk-intervals`, `--kernel-set`): input properties that exist only in a conformance build, that is a build of `frob-verbs` with its feature `conformance`, which only the umbrella feature `gauntlet-mutations` of the conformance crate (BD-025) enables and which a release build cannot enable. In every other build the build script removes the named properties from the embedded input schema before anything is generated, so the CLI has no such flag, strict validation answers `FROB-REF-802` as for any unknown parameter, and `--help --json` (hence the help snapshots, which are taken from the release build) does not show them. `REGISTRY_DIGEST` covers the entries, not the embedded schemas, and is the same in both builds. Lint `RL-24`. |

- *Field spellings.* `use_when` (this bead had `when`); `wait = { cli = "to-completion", mcp_ms, mcp_max_ms }`
  (this bead had `{ cli = "complete", mcp_default_ms, max_ms }`); one `kind` with an `actions` list for a verb
  with two kinds (this bead had `kind = ["read", "run"]` with an `[verb.actions]` table). The spellings chosen
  are NJL-01's, because the row beads of the clusters were written against them (45 of them carry the `wait`
  table in that form) and the plan fixes none of the three.
- *Fields each draft lacked.* `owner`, `actions`, `released` and `params` come from NJL-01's draft;
  `schema_version`, `paginated`, `exports`, `estimable`, `destructive` and `public` from this bead's. All are in
  the one table above.
- *Schema files.* Under `schemas/`, named by the schema identifier with `/` replaced by `.`
  (`schemas/frob.verbs.entry.1.json`). This bead had `registries/schemas/` with `/` written as `@`; the plan's

- *Two schema identifiers, both kept.* `frob.verbs/1` is the schema of the registry file; `frob.verbs.entry/1` is

**Task clusters** are declared in the same file: `[[task_cluster]] name = "author"`, `activity = "Make and change
a design"`, `default = false`, with the `tools` list that the assignment bead NJL-05 defines. Three **base tools**
are always listed and are not counted: `session_focus`, `job_wait`, `job_cancel`. Exactly one cluster has
`default = true` (`orient`). Staging (DESIGN, as the cluster registries and NJL-05 have it): the tables, their
assignment and their own lints (`default-cluster-unique`, `unknown-verb-in-cluster`, `task-cluster-mismatch`
and the others) are NJL-05's and are declared at M1. At M0 no table exists; the rows registered then already
name their task clusters, `RL-04` checks only what the entries themselves state, and `TASK_CLUSTERS` is emitted

**The MCP name map.** Tool name = verb name with `.` and `-` replaced by `_`: `design.check` → `design_check`,
`telemetry.inspect-pixel` → `telemetry_inspect_pixel`, `robot-docs` → `robot_docs`. No registry name contains an
underscore, and a lint checks that the map is one-to-one.

**Names, in full.**
1. Grammar: `segment ::= [a-z][a-z0-9]*("-"[a-z0-9]+)*`; a cluster verb is `segment "." segment`; an operator
   verb is one `segment`. No registry name contains an underscore.
2. CLI path: the segments in order, `frob design check …`, `frob telemetry inspect-pixel …`, `frob doctor`.
3. MCP tool name: the verb name with `.` and `-` replaced by `_` (`telemetry.inspect-pixel` →
   `telemetry_inspect_pixel`).
4. The map must be one-to-one **on the registered set**, checked on the image, not argued from the grammar.
   Counterexample: the operator verb `robot-docs` and a hypothetical cluster verb `robot.docs` both map to
   `robot_docs`; neither contains an underscore.


**Build script (`crates/frob-verbs/build.rs`), numbered.**
1. Read `registries/verbs.toml` and every schema file under `schemas/` (`<schema id with / replaced by .>.json`).
   The script reads the path in `FROB_VERBS_REGISTRY` instead when it is set; that override exists for the
   negative-control lane only, and the generated-file check fails if a release build was made with it (the rule
   inside `xtask check-generated` is BD-022's, below).
2. Parse strictly: an unknown key is an error (a misspelt field must not be ignored).
3. Run every lint below; on the first failure print the entry name, the lint identifier and the offending value,
   and fail the build.
4. Emit `$OUT_DIR/verbs_table.rs`: `pub static VERBS: [VerbEntry; N]`, sorted by name so lookup is a binary search;
   `pub static TASK_CLUSTERS: [TaskCluster; K]`; `pub static SCHEMAS: [(SchemaId, &str); S]` with each schema's
   canonical JSON text embedded; `pub const REGISTRY_DIGEST: [u8; 32]`, the BLAKE3 digest of the canonical
   serialization of all entries, which every envelope's producer can report and which `capabilities` prints.
5. Emit nothing that depends on the build machine: no timestamps, no absolute paths; iteration is over sorted
   keys, so two runs emit the same bytes. The rule of `xtask check-generated` (BD-004's check) that re-runs this
   script and compares bytes, and fails a build made with `FROB_VERBS_REGISTRY`, is added by BD-022, which
   depends on this bead and on BD-004; this bead needs neither the check nor `xtask`.
6. Hooks for later beads, each wired in the change of the bead named and absent before it. The script compiles

**Registry lints (identifier: rule).**
- `RL-01` name grammar: `^[a-z][a-z0-9]*(-[a-z0-9]+)*(\.[a-z][a-z0-9]*(-[a-z0-9]+)*)?$`; no underscore; the part before the dot equals `cluster` (operator verbs have no dot and cluster `operator`).
- `RL-02` the tool-name map is one-to-one over all entries and the three base tools.
- `RL-03` one name per verb: no entry's name appears in the `[[retired_name]]` table (rows `name`, `use`, `reason`), which holds every second spelling the plan retired (for example the separating-pair search is `mission.separate`, forks are `run.fork`, first divergence is `telemetry.divergence`, the screening audit is `nemesis.audit`, the model-form check is `fidelity.modelform`, the rank-agreement record is `eval.rank-agreement`, the pre-analysis is `eval.preanalyze`, the self-contained replay is `telemetry.export-html`, the cascade is `opt.cascade` with `solve.run` as its agent-facing caller); and no two entries share both schema identifiers.
- `RL-04` every verb names at least one task cluster, and no task cluster name is carried by more than seven verbs (the base tools apart). From M1, when NJL-05 declares the `[[task_cluster]]` tables, its lints add that every cluster a verb names is declared, that each table's `tools` equal the memberships, and that exactly one cluster is the default.
- `RL-05` every schema identifier resolves to a schema file; identifiers match `^frob(\.[a-z0-9-]+)+/[0-9]+$`.
- `RL-06` every refusal code resolves in the refusal registry of `frob-core` (an unknown code is a load-time error there), and the full refusal list of every verb (its chapter codes plus the codes the generator appends by kind) is non-empty. A chapter list may be empty (`refusals = []`, as for `doctor` and `capabilities`, whose only refusals are the appended surface-wide ones). DESIGN: the internal fault `FROB-REF-990` (N32a-03: a handler panicked or returned an unhandled error, exit 9) is the one code outside every list: any handler can raise it, it describes a defect and not the question, and listing it on 243 rows would add the same words to every tool description. It is never written in a chapter list and never appended by kind; the envelope's exit table and `robot-docs` state it once, and the conformance check "a verb raises only codes of its full list" exempts exactly this code.
- `RL-07` at least one example; each example parses under the CLI grammar generated from the entry and its arguments validate against the input schema. An abbreviated identity in an example (a registered identity prefix followed by fewer hexadecimal digits than a full digest, `r:19e2`) is checked by its prefix: the lint replaces it by the well-formed identity of that prefix with an all-zero digest before validating, since the build cannot read the fixture store; that each abbreviation resolves to a stored object is the conformance harness's check (NJL-02, `example-unresolved`).
- `RL-08` kind rules: `mutate` and job-submitting `run` verbs have the common idempotency-key property; `read` verbs have none and are `idempotent = true`; `admin` verbs list at least one capability; `destructive` appears only on an `admin` entry or an `admin` action.
- `RL-09` `run` verbs declare `wait` with `0 ≤ mcp_ms ≤ mcp_max_ms ≤ 30000` (30000 is OPEN-TETHER-3's fail-closed maximum; N32a-33's decision moves this bound and the server's request timeout together).
- `RL-10` `capabilities` is present on every entry (an empty list must be written explicitly together with `public = true`).
- `RL-11` the generated MCP description (purpose, when, cost class, refusal codes, one example) is at most 800 characters (TARGET). The description is NJL-01's `short_doc`, so the lint and its planted registry are wired in the change that lands NJL-01's `derive.rs` (build-script step 6); this bead reserves the identifier and the error name, and no second copy of the description rule exists here.
- `RL-12` `first_milestone` is one of M0 … M8, and `tier` is S, F or M.
- `RL-13` unknown field: the entry schema is closed, and a misspelt field is a refusal, never a default.
- `RL-14` duplicate name: no two entries have the same `name`.
- `RL-15` unknown scope: every scope in `capabilities` and in an action exists in the scope catalogue `registries/scopes.toml` (a warning until the catalogue lands at M2 with the token bead N32b-01, and an error after; BD-258 adds the `<cluster>:admin` scopes to the same file at M3).
- `RL-22` option capabilities: every key of `option_capabilities` is a property of the entry's input schema (or of one of its actions), and every scope in it passes `RL-15`; a key that is not an input property fails as `unknown-option`.
- `RL-21` optional key: `key_optional = true` appears only on a `mutate` entry whose output schema declares `x-frob-identity: "request-digest"` (its result identifier is the content address of the resolved request, as for `study.plan`), or on `session.focus` (a set-to-value mutation of the caller's own session, the one verb ADR-TETHER-01 already names); anywhere else it fails as `key-optional-not-content-addressed`.
- `RL-16` an example's command path is the verb's own CLI path.
- `RL-17` `cost_model` is never empty.
- `RL-18` `wait` appears only on an entry or action of kind `run`.
- `RL-19` `owner` is a subsystem crate, never `frob-cli` or `surface/frob-mcp`.
- `RL-20` `purpose` is at most 200 characters.
- `RL-23` pagination on reads only: an action's `paginated = true` appears only on an action of kind `read`, and an entry's own `paginated = true` only on an entry whose default action is `read` (NJL-01's variation 1 applies to the `read` kind only); either violation fails as `action-paginated-not-read`.
- `RL-24` conformance-only inputs: every name in `conformance_only` is a property of the entry's input schema (or of one of its actions), is not in the schema's `required` list and is not a positional; anything else fails as `conformance-only-not-an-input`.
- `RL-INT` a schema may use only the integer types `int53`, `u64str` and `i64str`; the lint is N32a-07's and is run by this build script from M1.

Every lint fails the build of `frob-verbs` with a named error; a registry that loads is a registry that passed
all of them. The error names are the ones NJL-01's draft used, kept so that messages and planted fixtures have

`run-without-wait` and `mcp-wait-out-of-range` (`RL-09`), `description-too-long` (`RL-11`), `milestone` and

`owner-is-surface` (`RL-19`), `purpose-too-long` (`RL-20`), `integer-type` (`RL-INT`): the 22 names of that

**Files.** `registries/verbs.toml`; `crates/frob-verbs/build.rs` (parse, lint, emit `verbs_table.rs` into
`OUT_DIR`); `crates/frob-verbs/src/registry/{entry,lint,names,schema_id}.rs`. Budget: the whole build script
under 1 s for 300 entries, since the registry is a build input of every binary.

**The `registry-only` feature.** With `--no-default-features --features registry-only` the crate compiles the
table, the schemas, the name map, the envelope and refusal types and the request canonicalizer, and nothing else:
no handler module, no dependency on `frob-fsim` or any subsystem crate. Default features add `handlers`.

Determinism: the generated table is a pure function of the registry and schema files (class exact). Refusals
this bead introduces: none at run time; every failure here is a build failure.

## Considerations

- The registry is large even in clusters (program risk: the agent surface is too large and agents get lost). The lints on cluster size and description length are the structural defence; the fresh-agent gates measure whether it worked.
- Entries may be present before their handler exists; such a verb answers with `FROB-REF-724` (not implemented in this build, exit 5) and `capabilities` lists it as not implemented. The milestone verb-set beads add entries.
- OPEN-ATEL-4 (whether `result.revalidate` and `mission.revalidate` stay two verbs over one engine; default two verbs, one engine; owner: Tether lead; due at the registry freeze of M3) is a registry question; `RL-03` permits the pair because their schemas differ.
- OPEN-AUGUR-7 (exit code of a mission query that stops on budget with certified cells; default exit 2 with `resolution-unmet`) is recorded on the `mission.synthesize` entry by the M1 verb-set bead.
- The treatment of two-kind verbs is DESIGN; the plan lists three and does not say how one entry carries two kinds.
- The fields `purpose`, `use_when`, `owner`, `wait` and `actions` are DESIGN additions to the entry the appendix prints; they are confined to what the generated surfaces already need.
- Capability scope names in rows are proposals until the scope catalogue `registries/scopes.toml` exists (N32b-01, M2); `RL-15` is therefore a warning until M2 and an error after (BD-258 only adds the `<cluster>:admin` scopes at M3).
- The plan's mechanical inventory has 163 verbs in 34 clusters; with the verbs the chapters name the registry reaches about 243 verbs in 44 clusters as the cluster beads enter them. No test hard-codes either count.
