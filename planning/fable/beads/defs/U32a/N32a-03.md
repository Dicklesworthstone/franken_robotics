## Background

Every verb of FrankenRobotics answers with one JSON object, the **envelope**. An agent that calls two hundred
different verbs should have to learn one answer shape: where the result is, how strong the evidence behind it is,
what it cost, what is left of the budget, why a call was refused and what to do next. The envelope is also where
the project's honesty rules become mechanical: no naked number reaches an agent, because the only way to put a
result into an envelope is to attach its **claim product** (the weakest proof class, physics tier and determinism
class among everything the result was computed from).

The envelope lives in `frob-verbs` (layer 6, tier Solid) and is shared by the CLI `frob`, the daemon `frobd` and
the MCP server `frob-mcp`. It serves the principle "every answer says what changed" and the condition, part of
what "implemented" means in this project, that a capability is reachable through `frob --json` with a documented
schema and exit code.

Design choices and their reasons (DESIGN):
- *One envelope even for failures.* Malformed input and unknown verbs produce the envelope too, so a script never
  has to parse two formats. Alternative excluded: plain error text on standard error with exit 1.
- *Exit code 1 is never emitted on purpose*, so a 1 always means an unhandled failure.
- *Exit code 8 means "accepted and still running"* and is not a failure. It exists because of the bounded
  synchronous wait on long verbs: a script must be able to tell "done" from "admitted and running" without
  parsing the result.
- *A numerical refusal, a budget stop and a physical failure of the robot are three different outcomes.* The first
  two are refusals; the third is a result with findings (exit 2).

## Scope

In: the envelope types and serializer; its JSON Schema and the per-verb specialization; the exit-code table and
the mapping from refusal code to exit code; the refusal, job, cost, budget and next-action blocks; the progress
event stream that precedes the envelope of a long job; the one-envelope rule; golden envelopes; the conformance
fixture. Out: the registry (N32a-02); number types inside schemas (N32a-07); cursors (N32a-10); the claim-product
type itself (BD-005); the operator verbs and the CLI parser that produce `801`/`802` (BD-022).

## Technical approach

**Shape (the plan's example, kept verbatim as the first golden file).**

```json
{ "schema": "frob.envelope/1", "verb": "design.check", "ok": true, "exit": 2,
  "result": { "mass_kg": 14.2, "closure": "closed", "symmetry": "C2xC2",
              "findings": [ { "code": "A-11.knee.continuous", "severity": "high",
                              "message": "Knee continuous torque demand exceeds the card by 31% in crouch.",
                              "repairs": [ { "edit": "swap-actuator", "args": {"joints": "*.knee", "to": "qdd-l"},
                                             "predicted": {"mass_kg": "+0.9", "margin": "+46%"} },
                                           { "edit": "regear", "args": {"joints": "*.knee", "ratio": 1.9} } ] } ] },
  "evidence": { "class": "Tested", "tier": "static", "model_id": "m:9f2c…", "determinism": "exact",
                "claims": [], "reality": "no-claim" },
  "bound": { "design": "d:41aa…" },
  "cost": { "wall_ms": 412, "cpu_core_s": 0.4, "gpu_s": 0 },
  "budget": { "gpu_s_left": 600, "cpu_core_s_left": 7199.6 },
  "warnings": [], "next_actions": [ { "command": "frob design edit quad-a swap-actuator --joints '*.knee' --to qdd-l",
                                      "why": "Largest predicted margin gain per kilogram." } ] }
```

**Field rules.**

| Field | Rule |
|---|---|
| `schema`, `verb`, `ok`, `exit` | Always present. `exit` equals the process exit code on the CLI. |
| `result` | Present when `ok` is true and the verb completed (exit 0 or 2). Its schema is the verb's output schema. |
| `evidence` | A serialized claim product: the weakest proof class (`Proved`, `Certified`, `Tested`, `Estimated`), tier and determinism class among the inputs. `claims` names which of the seven claims (Proof, Known answer, Parity, Fidelity, Design comparison, Reality, Performance) the result may be cited for, and is empty for most studio answers. `reality` is `no-claim` unless calibration data has been supplied. Also `model_id`, and where they apply `seed` (a decimal string), `weakest` (the input that set the class) and `conditions`. On every envelope, refusals included, `stack_receipt`: the `sr:` form of the receipt of the dependency stack the binary was built under (N33a-06's `BUILT_UNDER`), with `stack_dev: true` beside it when that identity is `dev`; this serializer is the envelope's stamping site of N33a-06. The serializer accepts evidence only as a claim-product value; that type has no constructor from literals outside its owning crate and no conversion toward a stronger class. |
| `bound` | The immutable identifiers every mutable name was resolved to (ADR-TETHER-11). Also `bound.fixtures` (N34p3-01, whose resolver fills it): an array, in parameter order then file order, of `{param, reference, path, digest}` for each `@fixture:` reference the request named (`path` relative to the workspace, `digest` the BLAKE3 of the file's bytes, or for a directory of its sorted `<relative path> <digest>` lines); present on every envelope issued after the Resolve step, a refusal of a later stage included. |
| `refusal` (when `ok` is false) | `code`, `message`, `pointer` (the field or part at fault), `observed`, `required`, `unit`, `affected_claims`, `retry` (`never`, `after-change`, `backoff`), ranked `repairs`, and `detail` (optional string, BD-005's `Refusal`): absent when unset, which is every raise of a code under its own meaning, and present on every interim raise, equal to the ledger request's slug or its `interim_detail` (N35-33 rule 7). |
| `job` (exit 8, and job verbs) | `id`, `state`, `progress {done, total, unit}`, `eta_s` with its interval, `poll_after_ms`, `last_committed`. Progress always has a denominator. |
| `cursor`, `frontier` | Present on paginated results. A long answer is paginated and says so; it is never cut silently. |
| `idempotent_replay` | `true` when the envelope is the stored answer to an earlier request with the same key. |
| `authorization` | On every verb that exports an artifact: `execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`, all the constant `false`; the export of a build packet adds a fourth, `fabrication_released`, also `false` (BD-408). |
| `cost`, `budget` | What this call spent and what the session has left, each in named units. |
| `warnings` | Machine-readable notes that do not change `exit`, including `executor: in-process` when a CPU-tier verb ran without the daemon. |
| `next_actions` | Ranked `{command, why}` pairs. A `command` never contains text that originated in an import (INV-TETHER-13). |
| `delta` (DESIGN name) | After a `run`: the change the agent made since the compared run, the first physical consequence of it, and the evidence for the comparison. Required by the principle "every answer says what changed"; field names are DESIGN. |

**Exit codes.**

| Exit | Meaning | Failure class |
|---|---|---|
| 0 | Completed, nothing to flag | none |
| 2 | Completed with findings or flags | none |
| 3 | Refused input or question (`FROB-REF-1xx` to `5xx`, and `8xx`, apart from the exception lists below) | Domain |
| 4 | Budget: refused at admission or stopped; nothing partial is published as a result (`70x`, `74x`, `76x`) | Domain |
| 5 | Capability not implemented, not admitted, or outside the session token's scopes (`72x`, `73x`, `79x`; and 840) | Domain |
| 6 | Backend or device unavailable (`6xx`) | Domain |
| 7 | Conflict: idempotency key reuse with different content, stale parent, or lineage conflict (112, 803, 804, 809) | Domain |
| 8 | Accepted and still running: the envelope carries a job handle. Not a failure | none |
| 9 | Indeterminate. Never retry blindly; recover by key | Transport; also integrity faults (`FROB-REF-810`, `9xx`) |

The exit code of a refusal is a field of its row in the refusal registry, and that row is authoritative. The
rule the registry checks rows against is N35-33's `[exit_rule]` (data in `registries/refusals.toml`, read by
BD-005's loader): one exit per range (`1xx` to `5xx` → 3; `6xx` → 6; `70x`, `74x`, `76x` → 4; `72x`, `73x`, `79x`
→ 5; `8xx` → 3; `9xx` → 9) and three exception lists that override the range whatever the family (`conflict` →
7: 112, 803, 804, 809; `integrity` → 9: 810; `capability` → 5: 840); a row whose exit differs fails the load, and
a `7xx` decade holding a code and no rule row fails it too. The table above is that rule as the surface prints it. The eighteen codes
this chapter defines: 701 → 4, 702 → 4, 703 → 4, 704 → 4, 720 → 5, 723 → 5, 724 → 5, 725 → 5, 801 → 3, 802 → 3,
803 → 7, 804 → 7, 805 → 3, 806 → 3, 807 → 3, 808 → 3, 809 → 7, 810 → 9; and the internal fault 990 → 9 below.

**Output discipline (INV-TETHER-02).** With `--json`, every invocation writes exactly one envelope to standard
output. A long job first writes newline-delimited progress events (`{"schema":"frob.progress/1","job":…,
"done":…,"total":…,"unit":…,"state":…}`, DESIGN) and then the envelope, which is always the last line. Standard
error carries diagnostics only. A panic is caught at the top of `main` (and around every handler call in a
long-lived process), converted to an envelope with `ok: false`, exit 9 and the refusal `FROB-REF-990`
(`internal-fault`, N32-REF's DESIGN row, assigned by N35-33's first round: the refusal registry's first commit
has no `9xx` row and the plan names exit 9 for a handler fault without a code; 990 is in the `9xx` internal family and clear of the proposed 901 to
907 and of the test sentinel 999). Its block: `retry: never`; `pointer` names the verb; repairs, ranked: (1) when
the call carried an idempotency key, `frob job find --verb <verb> --key <key>`, because a job may have been
admitted before the fault; (2) `frob doctor`; the diagnostic file path is in `observed`. An unhandled abort is the
only source of exit 1.

**Three standing rules at this boundary.** Refuse, never truncate. A budget stop publishes nothing partial as a
result. A misspelt parameter is a refusal, not a default.

**Types (DESIGN).** `Envelope<R>` with `Outcome::{Completed{result, findings}, Refused(Refusal), Deferred(JobHandle)}`;
`ExitCode` is an enum with exactly the nine values above and no `From<i32>`; `Envelope::deferred(handle)` builds
the exit-8 form; `Envelope::from_refusal(r)` reads the exit from the registry. `envelope_schema(entry)` returns
`frob.envelope/1` with `result` specialized to the verb's output schema; both surfaces use it.

Determinism: serialization is canonical (sorted keys, NFC strings, the number rules of the integer bead) so that
equal envelopes are equal bytes; `cost.wall_ms` is the only wall-clock field and never enters a digest or an
evidence record (INV-TETHER-09).

## Acceptance criteria

- [ ] GATE-TETHER-03 (TARGET, M0): envelope and exit-code conformance on malformed, unknown and over-budget inputs: each yields exactly one schema-valid envelope with the expected `refusal.code` and `exit` (802 → 3, 801 → 3, 701 → 4).
- [ ] Every refusal code in the registry maps to exactly one exit code; the lint fails on a row with none or two.
- [ ] No code path constructs exit 1; a planted panic yields an exit-9 envelope.
- [ ] The envelope serializer has no entry point that takes evidence as plain strings (compile-fail test).
- [ ] Golden envelopes for completed, completed-with-findings, refused, deferred (exit 8), paginated and idempotent-replay forms validate against the schema and round-trip byte-identically.
- [ ] An exporting verb's envelope without the three `false` flags fails schema validation.
- [ ] Every envelope (completed, refused, deferred and exit 9 alike) carries `evidence.stack_receipt` equal to the `sr:` form of `BUILT_UNDER`, and `evidence.stack_dev: true` exactly when that identity is `dev`.
- [ ] `CONTRACT.md` of `frob-verbs` documents the envelope with the field and exit tables.

## Test plan

### Unit tests (`cargo test -p frob-verbs envelope`)
- `golden_design_check_roundtrip`: the example above parses and re-serializes to canonical bytes.
- `exit_table_exact`: for each of the eighteen codes above and 990, `Envelope::from_refusal(code).exit` equals the listed value.
- `exit_fixture_rows`: every row of `exit_table.toml` names a registered code whose exit equals the row's `exit`, and the refused envelope built for it validates against `frob.envelope/1`.
- `one_code_one_exit`: over the whole refusal registry, no code has zero or two exits.
- `exit_rule_from_registry`: a synthetic `FROB-REF-771` row (a `7xx` decade with no rule row) fails the load; a synthetic `FROB-REF-741` row with exit 3 fails (its range gives 4); 112 → 7 and 840 → 5 load by the exception lists, and `Envelope::from_refusal` returns those exits.
- `deferred_has_denominator`: `Envelope::deferred` refuses a progress block without `total`.
- `no_exit_one`: a source scan and a type test (`ExitCode` has no variant with value 1).
- `panic_becomes_exit_9`: a handler that panics yields one envelope, `ok: false`, exit 9, `refusal.code` = `FROB-REF-990`, `retry` = `never`.
- `evidence_only_from_claim_product` (compile-fail): building `evidence` from a string literal does not compile.
- `export_flags_constant_false`: an envelope with `execution_authorized: true` is rejected by the reader.
- `stack_receipt_on_every_envelope`: the golden forms and a panic envelope each carry `evidence.stack_receipt` equal to `BUILT_UNDER`'s `sr:` text; a build with a `dev` identity adds `stack_dev: true`, and one without adds no `stack_dev` field.
- `ndjson_then_envelope`: a long job's standard output is zero or more `frob.progress/1` lines and then one envelope.
- Property `one_envelope_always` (10⁴ random argument vectors, including invalid UTF-8 and empty input): standard output parses as at most the progress lines and exactly one envelope.

### End-to-end script and logging
`scripts/e2e/tether_envelope_exit.sh` and its fixture are authored in this bead. The script drives the real `frob`
binary, which is assembled on this crate by BD-022, so it is first run green in BD-022's acceptance; until then
this bead runs the fixture's expected codes through `Envelope::from_refusal` and the schema validator in the unit
test `exit_fixture_rows`. The script runs the fixture
`crates/frob-conformance/fixtures/tether/exit_table.toml` (rows: argument vector, expected `ok`, `exit`,
`refusal.code`), compares the process exit code with `exit`, validates each output against the schema, and writes
NDJSON to `target/e2e-logs/tether_envelope_exit/<utc>.ndjson`: per row a `cmd` line with the exact command, exit
code and wall time, an `assert` line with expected and observed code and exit, the envelope's `evidence` block,
and on failure the first differing field and the saved output path; a final `summary` with counts and
GATE-TETHER-03.

### Known answers and negative controls
- KA-755: the exit-code table on a fixture of malformed, unknown, over-budget, unscoped and conflicting inputs gives 802 → 3, 801 → 3, 701 → 4, 720 → 5, 803 → 7 (exact). Rows whose mechanism has not landed (unscoped, conflicting, before M2) are recorded `not exercised`, never `pass`.
- Negative controls for GATE-TETHER-03: a build flag that prints a bare error for unknown verbs (the one-envelope property must fail); a refusal row with a wrong exit (the fixture must fail); a second envelope printed after the first (must fail).
- Metamorphic relation: reordering flags of a valid command leaves the envelope bytes unchanged except `cost`.
- Determinism lanes: golden bytes identical in debug and release and on both hosts.

## Considerations

- Other chapters asked for explicit exit codes where the family rule was silent (`74x` admission refusals, `76x`, `79x` stack and worker refusals). N35-33's `[exit_rule]` settles them (`74x` and `76x` → 4, `79x` → 5, each confirmed against its defining registry bead); this bead reads the rule and chooses no value.
- OPEN-AUGUR-7: a mission query that stops on budget with certified cells exits 2 with `resolution-unmet` and returns the certified cells and the unresolved remainder (default; owner: Tether lead).
- Citing a result above its claim product is refused elsewhere (`FROB-REF-819`); the envelope only guarantees the product is present and weakest-wins.
- Envelope size: a result that would exceed the surface's size limit is paginated or refused, never truncated.
- Adding a field is a compatible change; removing or retyping one needs `frob.envelope/2`.
