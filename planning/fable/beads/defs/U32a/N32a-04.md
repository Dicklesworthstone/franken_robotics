## Background

FrankenRobotics has two agent-facing surfaces, the command line `frob` and the MCP server `frob-mcp`, and a
daemon, `frobd`, that owns devices and long jobs. The principle is **one application service, two adapters**: both
surfaces link the crate `frob-verbs` and call the same handlers in process through the same dispatch interface,
and both hand long work to the daemon as jobs. Simulation ticks run inside a worker owned by the daemon; calls on
the control plane act on whole designs, jobs, chunks and queries, never on single steps (DESIGN reason: a per-step
remote call would put the agent's latency inside the physics loop).

ADR-TETHER-03 fixes the shape: one dispatch trait with two back ends, in-process handlers (the default) and a
local socket to `frobd`. In the default build an adapter links `frob-verbs`, runs verbs in process and hands long
work to `frobd` as a job. The socket-only form is complete on its own and is the first fallback of the kill gate
KILL-MCP (the MCP server built as its own workspace, reaching verbs only through the daemon). Reasons: the daemon
owns devices and jobs in any case; a killed adapter must never own a job; and the fallback must be reachable
without redesigning the adapter. Alternatives excluded: adapters that each implement verbs (drift); an adapter
that owns device work (a killed adapter would strand a device); a process boundary as the only route (a protocol
hop on every call, which the owner's ruling of 2026-11-22 removed from the default).

"A verb's handler lives in the crate of the subsystem that answers the question": the computation is a function
in `frob-design`, `frob-analyze` and so on. `frob-verbs` holds only the thin binding per verb (decode the typed
input, call the function, assemble the claim product), generated or declared in `frob-verbs::handlers`.

## Scope

In: the request pipeline; the `Dispatch` trait; the in-process back end; the socket back end and the wire framing
`frob.rpc/1`; the handler table and its registration; the no-daemon posture; conformance tests that run one suite
over both back ends. Out: the daemon process itself and its job queue (N32a-14); the admission transaction
(N32a-09); the bounded wait (N32a-16); the CLI parser and the MCP handler that call this interface (BD-022,
BD-023).

## Technical approach

**The request pipeline (the same on every surface; numbered).**
1. *Locate.* Look the verb up in the static table. Unknown: on the CLI, refusal `FROB-REF-801`, exit 3.
2. *Validate.* Validate the arguments against the input schema plus the common properties of the verb's kind.
   Unknown or misspelt parameter, wrong type, out-of-range `sync_wait_ms`: `FROB-REF-802`, exit 3. Nothing is
   charged for steps 1 and 2.
3. *Authorize.* Check the session token's scopes against the entry's `capabilities` (`FROB-REF-720`, exit 5, once
   tokens exist at M2; before that every local caller has the full local scope set, and the envelope says so).
4. *Resolve.* Resolve every mutable name to an immutable identifier, fill defaults, and record the resolutions for
   the envelope's `bound` field (ADR-TETHER-11).
5. *Digest.* Serialize the resolved request canonically and take its BLAKE3 digest (used by idempotency).
6. *Implemented?* If the build has no handler for the entry: `FROB-REF-724`, exit 5.
7. *Route.* `read` and `mutate` verbs and CPU-tier `run` verbs under the in-process limit run through the handler
   table. Long or device work is submitted to the daemon as a job. Every route returns a stream of frames ending
   in one envelope.

```rust
// DESIGN: intent, not signatures.
pub trait Dispatch: Send + Sync {
    /// Submit a resolved request. Replay-safe: the same idempotency key returns the same job.
    fn submit<'a>(&'a self, cx: &'a Cx, req: &'a ResolvedRequest) -> BoxFuture<'a, Result<JobStream, Refusal>>;
    /// Re-attach to a job by identifier (job.wait) or by idempotency key (job.find).
    fn attach<'a>(&'a self, cx: &'a Cx, job: JobRef) -> BoxFuture<'a, Result<JobStream, Refusal>>;
}
pub enum Frame { Progress(Progress), Envelope(Envelope) }
pub struct JobStream { /* next_frame(cx, deadline) -> Option<Frame>; handle() -> JobHandle */ }

pub struct InProcess { table: &'static HandlerTable, daemon: Option<DaemonClient> }   // default back end
pub struct Socket { client: DaemonClient }                                            // fallback back end

pub trait VerbHandler: Send + Sync {
    fn run(&self, cx: &Cx, req: &ResolvedRequest, sink: &mut dyn ProgressSink) -> Outcome;
}
```

**Back end 1, in process (default).** Verbs run in the calling process. Work that needs a device or exceeds the
in-process limit is handed to `frobd` through `DaemonClient`. With no daemon reachable: CPU-tier verbs still run
in process and the envelope carries the warning `executor: in-process`; a verb that needs a device is refused with
the backend-unavailable family (`FROB-REF-6xx`, exit 6) and a repair naming `frobd`. The adapter never owns a job
record: a job exists only in the daemon's ledger.

**Back end 2, socket.** Every request after step 2 is forwarded to `frobd`, which performs steps 3 to 7. It is
selected by configuration, by the `registry-only` build (which has no handler table), or by the fallback of
KILL-MCP.

**Wire framing `frob.rpc/1` (DESIGN).** A Unix-domain socket under the daemon's state root, mode 0600. Newline-
delimited JSON, one object per line, UTF-8, at most 4 MiB per frame (TARGET; a larger payload is read through
`artifact.read` by byte range). Per call: one request frame, zero or more progress frames, one envelope frame.

```
→ {"rpc":"frob.rpc/1","id":"7","session":"<token or null>","verb":"design.check",
   "args":{…},"common":{"idempotency_key":null,"budget":null,"sync_wait_ms":null,"estimate_only":false,"on_cancel":"leave"}}
← {"rpc":"frob.rpc/1","id":"7","progress":{"job":"j:77c0…","done":512,"total":4096,"unit":"worlds","state":"running"}}
← {"rpc":"frob.rpc/1","id":"7","envelope":{ …frob.envelope/1… }}
```

`id` is a decimal string chosen by the client and echoed. A malformed frame closes the connection after an
envelope with `FROB-REF-802`. A client that disconnects mid-call leaves any admitted job running. The server loop
is a library function (`frob_verbs::rpc::serve`) so that the daemon and the tests run the same code.

**Cancellation.** Every handler receives the caller's asupersync `Cx` and observes cancellation at its own
checkpoints. The dispatch layer calls no device API.

**Control-plane granularity lint.** No registry entry's unit of work is a single step, tick or kernel launch; the
lint inspects each `run` verb's input schema for a required duration, count or horizon field.

Determinism: for the same resolved request the two back ends return byte-identical envelopes apart from
`cost.wall_ms` and the `executor` warning. Evidence class of outputs: whatever the handler's claim product says;
dispatch adds no evidence.

## Acceptance criteria

- [ ] One conformance suite (`tests/dispatch_conformance.rs`) runs every M0 verb through `InProcess` and through `Socket` (against the real server loop on a real socket in a temporary directory) and compares envelopes: identical after masking `cost.wall_ms` and the `executor` warning.
- [ ] With no daemon, a CPU-tier verb answers in process with the `executor: in-process` warning; a device verb is refused with exit 6 and a repair naming the daemon.
- [ ] Steps 1 and 2 charge nothing: the session budget is unchanged after 1,000 malformed and unknown calls.
- [ ] `frob-verbs` built with `registry-only` exposes `Socket` and not `InProcess`, and the conformance suite passes with it.
- [ ] Killing the client at any frame boundary leaves the server loop serving other connections and leaves no half-written state.
- [ ] The socket file is created with mode 0600 and refused if it already exists with other permissions or another owner.

## Test plan

### Unit tests (`cargo test -p frob-verbs dispatch rpc`)
- `pipeline_order`: an unknown verb with malformed arguments reports 801, not 802; a known verb with a misspelt parameter reports 802 with `pointer` naming the parameter.
- `misspelt_parameter_is_refusal`: `--wrolds 16` on `sim.run` is refused; the default world count is not used.
- `resolution_echoed`: `design.check quad-a` returns `bound.design` equal to the head identifier at call time.
- `not_implemented_724`: an entry without a handler returns 724, exit 5.
- `frame_roundtrip`: request, progress and envelope frames parse and re-serialize to identical bytes; `id` is echoed.
- `oversize_frame_refused`: a 5 MiB request line is refused with 802 and the connection closes.
- `malformed_frame_gets_envelope`: `{"rpc":"frob.rpc/2"}` yields one envelope and a closed connection.
- `client_drop_leaves_server_alive`: 100 connections dropped at random byte offsets; the 101st call succeeds.
- `socket_mode_0600`; `socket_wrong_owner_refused`.
- `two_backends_equal` (the conformance suite), for each M0 verb and for one refusal per exit code available at M0.
- `granularity_lint_catches_step_verb`: a synthetic entry `sim.step` with no duration or count field fails.

### End-to-end script and logging
`scripts/e2e/tether_dispatch.sh`: starts the server loop (through `frobd` once it exists; before that through the
test binary `frob-rpc-serve` built from the same library function), runs `frob doctor --json` and
`frob capabilities --json` once in process and once with `FROB_DISPATCH=socket`, diffs the masked envelopes, kills
the client mid-call 20 times, and checks the server still answers. NDJSON log per the shared helper under
`target/e2e-logs/tether_dispatch/`: `cmd` lines with exit codes and wall time, `assert` lines with both envelope
digests, `metric` lines for round-trip latency (no threshold; recorded), a final `summary`.

### Known answers and negative controls
- Known answer: the two back ends agree byte for byte on masked envelopes for every M0 verb.
- Negative controls: a handler that reads a process-global instead of its request (the two back ends must differ and the suite must fail); a build that lets the adapter insert a job row (the kill test must find an orphan and fail); a synthetic step-granular verb (the lint must fail).
- Determinism lanes: the suite twice on one machine; debug and release; both hosts.

## Considerations

- The socket back end exists from M0 so that the fallback of KILL-MCP is exercised before it is needed. If the fallback is adopted, this back end becomes the only route for `frob-mcp` and the round-trip latency recorded here becomes a budgeted quantity.
- The in-process limit (which CPU-tier `run` verbs may run in the caller's process) is a registry field per verb, defaulting to "under the bounded wait"; long CPU work still becomes a job so that it survives the caller.
- Before tokens exist (M0, M1) there is one local principal; the pipeline's step 3 is present and tested with a synthetic restricted token so that adding real tokens changes no control flow.
- `frobd --mcp` hosts the MCP server inside the daemon: the same `InProcess` back end, with the daemon client replaced by a direct call into the job engine.
