## Background

A **kill gate** in this project is a decision written before the work starts: a trigger with its measurement, the
milestone at which it is read, and a fallback that is named in advance, so that a failed bet costs a planned
detour and not a re-plan. This bead is the decision for KILL-MCP.

The design of record is that the MCP server `frob-mcp` is an ordinary member of the core workspace build graph on
the one toolchain T, built on the sibling library `fastmcp_rust`, linking `frob-verbs` and running verbs in
process. That design depends on two upstream work items, both done by this program in the siblings' repositories
at M0 with priority P0: FD-FMCP-01 (bring `fastmcp_rust` onto T, with its own tests and MCP conformance checks
passing there) and FD-ASUP-01 (one published asupersync version across FrankenSim's constellation, FrankenTorch
and `fastmcp_rust`). The admission gate INT-FMCP-01 proves the result: `frob-mcp` builds in the core graph on T
with exactly one asupersync package (`cargo tree -d` shows no duplicate), lists the tools generated from the verb
registry, and passes the MCP protocol smoke test over stdio and HTTP.

KILL-MCP is a true fallback, not a default. Before the owner's ruling of 2026-11-22 the process boundary was the
default, because `fastmcp_rust` declared a newer Rust version (1.100) than FrankenSim's pin (a 1.99.0 nightly);
the ruling is that a mismatch with a sibling is fixed in the sibling. OPEN-TETHER-1 (whether `frob-mcp` can link
handler crates in process) and OPEN-SUITE-2 (whether the core moves to a toolchain that admits it) are both
decided accordingly and are kept as recorded decisions; INT-FMCP-01 confirms them.

Why a kill gate is still needed. FACT, the starting state (observed 2026-11-21): FrankenSim pins
`nightly-2026-07-06`, which its toolchain file identifies as rustc 1.99.0-nightly; `fastmcp_rust` declares
`rust-version = "1.100"` and pins `nightly-2026-08-25`; as found, the two do not build on one compiler. The
library's published package 0.13.0 carries asupersync 0.5.0 while its source tree pins 0.6.2; FrankenSim consumes
asupersync by path and FrankenTorch requires 0.6.2. Both mismatches are fixed in the siblings by this program
(every sibling is the owner's). If that work cannot be finished inside M0, the program must not wait on it: that
is the one case the gate exists for.

## Scope

In: the gate's definition as registered; the decision function and the decision procedure; reading the
measurement, deciding, recording the decision as an ADR, re-reading at M1, and stating what changes downstream on
each branch; the standing demonstration that fallback 1 is reachable without redesign; the switch-back rule.
Out: the measurement itself (BD-023); the upstream work (FD-FMCP-01, FD-ASUP-01 through BD-008); the register
row's format and its entry before any measurement (N32b-25); building the fallback (N32a-06, which exists only if
this gate fires); the exit review itself (BD-044, which records this decision's outcome).

## Technical approach

**The gate, stated once.**

| Item | Value |
|---|---|
| Trigger | INT-FMCP-01 cannot pass within the M0 budget after FD-FMCP-01 and FD-ASUP-01 have both been attempted |
| "M0 budget" | The decision is taken at the M0 exit review. M0's planning estimate is 2 elapsed weeks for a swarm (an estimate that exists to make the schedule bet testable, not acceptance evidence); the trigger is "still failing when the exit review is held", not a stopwatch |
| Milestone | Decided at M0, between M0 and M1; re-read at M1 with the M1 verbs |
| Measurement | The INT-FMCP-01 admission record: build on T; the asupersync package count from `cargo tree -d`; `tools/list` against the registry; the smoke test over stdio and over HTTP. Plus the state of each upstream item (`open`, `landed`, `adopted`) with the failing step if one failed |
| Fallback 1 | `frob-mcp` as its own workspace, linking `frob-verbs` with the `registry-only` feature and talking to `frobd` over a local socket in newline-delimited JSON |
| Fallback 2 | Agents use the CLI, which is complete on its own |
| Decided on | INT-FMCP-01 alone; no second trigger |
| Fail-closed default until decided | No MCP surface is advertised to agents; the CLI is the surface |

**Decision function** (DESIGN; pure; its inputs are records, not opinions). It lives as tested code in
`crates/frob-conformance` and the recorded branch must equal its output on the recorded inputs.

```
decide(int_fmcp_01: {pass | fail | not-run, clauses: [bool; 3]},   // build with one asupersync; tools/list; smoke
       fd_fmcp_01_attempted: bool, fd_asup_01_attempted: bool, at_exit_review: bool)
  -> does-not-fire | fires(fallback-1) | fires(fallback-2) | undecided
```

- `int_fmcp_01 = pass`: does not fire.
- Not passed and not yet at the exit review: `undecided` (the budget has not run out).
- At the exit review, not passed, and either upstream item has no recorded attempt (a landed change, or a
  documented blocker with its evidence): `undecided`, escalated to the owner. The gate cannot fire on work that
  was never tried.
- At the exit review, not passed, both attempted: classified by steps 3 and 4 of the procedure below, which
  decide between not firing with a repair, fallback 1 and fallback 2.

**Decision procedure, numbered.** The trigger and the two fallbacks are the plan's; the classification in steps 3
and 4 is DESIGN, a reading of the trigger that the exit review may overrule in the ADR.
1. Read the INT-FMCP-01 record. If every step passed: record `KILL-MCP: not fired` with the record's hash, and
   stop. The design of record stands.
2. If a step failed, confirm both upstream items were *attempted*: each has a mirrored bead in its sibling's
   tracker and either a landed commit or a recorded failing step. If one was not attempted, the gate cannot fire
   yet: the outcome is `undecided`, the owner is told, and the item is attempted first.
3. Classify the failure: (a) toolchain (the library does not build on T, or builds only by ignoring a declared
   minimum, which is never accepted); (b) a second asupersync package remains in the tree; (c) the library builds
   but the smoke test fails on one transport; (d) the tool list differs from the registry (a defect in this
   repository, which is repaired, not a reason to fire).
4. For (a) or (b): fire, adopt fallback 1. For (c) on HTTP only: do not fire; ship stdio, record HTTP as not
   offered, and open a repair. For (c) on both transports: fire, adopt fallback 1 if the socket form passes the
   same smoke test, otherwise fallback 2.
5. Write the ADR at `docs/adr/ADR-KILL-MCP-M0.md`, the one form of a kill-gate decision (N40-03: every decision
   record lives directly in `docs/adr/`, named `ADR-<gate-name>-<milestone>.md`), with the required fields of
   that form: the gate and the milestone; the trigger as registered; each measured value with its receipt hash
   beside the trigger (the three clause results of INT-FMCP-01, the state of the two upstream items); the
   classification; the outcome; the fallback now in force and its consequences; the beads re-read; what is
   retried and when (the next toolchain train); the recording session. The outcome is one of the registered
   values: `not-fired`; `fired`, with fallback 1 or fallback 2 named as the fallback in force; or `deferred`,
   with `deferred_to` and a reason, which is how the decision function's `undecided` is recorded (an upstream
   item never attempted). Update the kill-gate register row (`decision = { outcome, adr, date, session,
   receipts }`) and the ownership record. The ADR and the register row are entered by a session that did not
   do the upstream work; the recorder refuses an entry from the session that did.
6. Re-read at the M1 exit with the M1 verbs: if the gate fired at M0 and the upstream items have since landed,
   re-run INT-FMCP-01 and return to the design of record; if it did not fire, confirm the M1 tool list. The
   switch-back is one change (the workspace membership of `surface/frob-mcp` and the default dispatch back end).
   The re-read is its own record, `docs/adr/ADR-KILL-MCP-M1.md`, and a second entry of the register row's
   `decision` array with `exit = "M1"` (the row is registered `rolling` with `reread = ["M1"]`); the M0 entry
   is kept and never edited.

**Reachability of fallback 1, demonstrated before it is needed.** The adapter has one dispatch interface with two
back ends (ADR-TETHER-03) and `frob-verbs` has the `registry-only` feature (ADR-TETHER-02). Two checks run in the
default build at M0 whatever the gate decides, so that firing costs configuration and not design: a test that
runs the protocol smoke test with `frob-mcp --dispatch=socket` against a running verb-serving loop, and a build
check that compiles `frob-mcp` against `frob-verbs` with `registry-only` and no physics crate. In the design of
record `frob-mcp` does not reach verbs through its socket back end, which stays a tested spare; the daemon's
socket itself remains in use by the CLI for device work and by the dashboard, and is not what this gate decides.

**What changes downstream.**

| Branch | Consequence |
|---|---|
| Not fired | Nothing. `frob-mcp` runs verbs in process; `frobd --mcp` can host it; with no daemon running, CPU-tier verbs run in process over MCP and the envelope says so; the socket back end stays a tested spare. |
| Fallback 1 | `surface/frob-mcp` leaves the root workspace `members` and gets its own lockfile, with exactly one asupersync package of its own; it links `frob-verbs` with `registry-only` (the verb table, schemas and envelope types, no physics crate), so the parity gate still compares the served tool list with the registry; every call is forwarded to `frobd` over `frob.rpc/1`, so a daemon able to serve verbs is needed from the milestone at which MCP is offered (the verb-serving loop is brought forward from the M2 daemon). CPU-tier verbs no longer run inside the MCP process: with no daemon running the server answers only the operator verbs it can serve from the registry. `frobd --mcp` is not offered. The MCP half of every "runs in process" statement in the documentation is removed. Round-trip latency over the socket becomes a recorded quantity. The security statement "an MCP client is bounded by the session's scopes and the generated tool set" and the surface invariants (a killed adapter never owns a job) are unchanged. The upstream work items stay open and their switch-over rule applies. |
| Fallback 2 | No MCP surface. Agents drive `frob --json` with the skill file. The beads that build MCP tools, task clusters, the bounded wait on MCP, resources, prompts and the Tasks adapter are closed as not built, each closing reason naming the fallback. The MCP-only gates (the list comparison of GATE-TETHER-02, GATE-TETHER-12) are recorded `killed` in the gate register with KILL-MCP and the fallback's name in the row's detail; CLI gates are unaffected. Fresh-agent gates run through the CLI. `frob capabilities` reports the MCP surface as killed. |

Neither fallback blocks a milestone: M1 depends only on FrankenSim, asupersync and FrankenSQLite.

## Acceptance criteria

- [ ] `docs/adr/ADR-KILL-MCP-M0.md` exists with the required fields of a kill-gate decision (N40-03) and the outcome `not-fired`, `fired` (naming fallback 1 or fallback 2 as the fallback in force) or `deferred` (with `deferred_to` and its reason), citing the INT-FMCP-01 record by hash and the status of FD-FMCP-01 and FD-ASUP-01; no file exists under `docs/adr/tether/`.
- [ ] The kill-gate register row carries the decision, the date and the commit.
- [ ] If fired, the bead for the adopted fallback is unblocked and the affected gates are marked with their consequence from the table.
- [ ] The decision is handed to the M0 exit review and re-read at the M1 exit; both readings are recorded.
- [ ] The rehearsal passes: with the fallback forced by configuration in a scratch checkout, `frob-mcp` over the socket back end passes the smoke test (fallback 1 really is an exit).
- [ ] The decision function exists as tested code in the conformance crate and is applied to the recorded inputs; its output equals the recorded branch.
- [ ] The socket smoke test and the `registry-only` build check pass in the default build at M0, whatever the decision.
- [ ] On a firing branch, the beads that exist only on the in-process branch are closed with the fallback's name, and `frob capabilities` reports the MCP surface accordingly.
- [ ] The M1 re-reading is recorded as `docs/adr/ADR-KILL-MCP-M1.md` and as a second `decision` entry of the register row (`exit = "M1"`) with the M1 verb set's result; the M0 entry is unchanged.
- [ ] The M0 exit review can read the outcome (clause results, upstream states, branch) without opening build logs.

## Test plan

### Unit tests
- `crates/frob-conformance/tests/kill_mcp.rs`: `decide_pass_does_not_fire`; `decide_before_exit_is_undecided`; `decide_unattempted_upstream_is_undecided` (not passed, one upstream item unattempted); `decide_fires_fallback_1_when_socket_form_passes`; `decide_fires_fallback_2_otherwise`; `duplicate_runtime_fails_clause_one` (a fixture `cargo metadata` with two asupersync packages gives clause 1 false).
- `surface/frob-mcp/tests/socket_backend_smoke.rs`: the protocol smoke test (initialize, `tools/list`, one `tools/call` of `capabilities`, shutdown) over stdio with the socket back end.
- `kill_mcp_adr_schema`: the ADR's front matter parses; its outcome is one of `not-fired`, `fired`, `deferred`; a `fired` record names fallback 1 or fallback 2; a `deferred` one has `deferred_to` and a reason; its path is `docs/adr/ADR-KILL-MCP-M0.md` (the M1 re-read: `-M1.md`), and a record under `docs/adr/tether/` fails.
- `decision_table_total`: a table-driven test of the classification: inputs (build ok?, duplicate count, stdio smoke, HTTP smoke, list equal?) → branch; for example (ok, 1, pass, pass, equal) → not fired; (fail, –, –, –, –) → fallback 1; (ok, 2, …) → fallback 1; (ok, 1, pass, fail, equal) → not fired with HTTP not offered; (ok, 1, fail, fail, equal) → fallback 1 or 2 by the socket smoke; (ok, 1, pass, pass, differs) → not fired, repair.

### End-to-end script and logging
`scripts/e2e/kill_mcp_rehearsal.sh`: builds the fallback-1 configuration in `target/kill-mcp-scratch/` (own
workspace, `registry-only`), starts the verb-serving loop (`frobd` once it exists; at M0 the test server
`frob-rpc-serve` of N32a-04, which runs the same library server loop), runs the MCP smoke test through the socket
back end, and compares each envelope with the in-process one. NDJSON under `target/e2e-logs/kill_mcp_rehearsal/`
with `cmd` lines, `assert` lines per smoke step, `metric` lines for socket round-trip latency against in-process
latency (recorded), the asupersync package count in the scratch workspace (threshold 1), on failure the first
differing envelope field and the saved wire transcripts of both runs, and a `summary` naming KILL-MCP.

`scripts/e2e/kill_mcp_decision.sh`: runs `cargo tree -d -p frob-mcp` and counts asupersync packages; starts
`frob-mcp` over stdio and over loopback HTTP and runs the smoke test in process; repeats it with
`--dispatch=socket`; diffs the served tool list, under the name map, against the verb list of `frob capabilities
--json` (which carries the registry digest); recomputes the decision from the
recorded inputs and compares it with the record. NDJSON lines through the shared helper (`ts`, `script`, `bead`,
`step`, `event`, command, exit code, wall time, the `evidence` block of each envelope): package count against 1,
tools listed against the registry's count for the milestone, smoke steps passed, the recomputed branch against
the recorded one; the `summary` line names KILL-MCP and INT-FMCP-01.

### Known answers and negative controls
- Known answer: the six rows of the classification table.
- Known answer: `capabilities` over MCP returns the same envelope as `frob capabilities --json`, in process and through the socket back end.
- Negative controls: an ADR with outcome `not-fired` while the cited record shows a failing step (the consistency test must fail); a rehearsal in which the scratch workspace still depends on a physics crate (the dependency check must fail).
- Negative control: a decision recorded as fired while an upstream item has no attempt record is rejected by the recomputation.
- Negative control: a build that pulls the library's published package 0.13.0 (which carries asupersync 0.5.0) shows two asupersync packages and fails clause 1.
- Negative control: a decision entered by the session that did the upstream work is refused by the recorder.

## Considerations

- RISK-02: the toolchain train costs more than M0 allows or breaks a sibling; earliest signal is a failing cell in the toolchain matrix or FD-FMCP-01 still open at the exit review. RISK-03: three siblings still pin asupersync 0.5.0; a surface that still brings a second package is exactly the case fallback 1 exists for.
- A fired gate is not permanent: the upstream items stay open and are retried at the next toolchain train; the M1 re-read is the first chance to return.
- `--ignore-rust-version` is never a way to pass: a build that passes by ignoring a declared constraint proves nothing about the sibling.
- Neither a pin nor T moves during the ten-fold tournament of M7, so the branch in force at the freeze is the branch the tournament uses.
- Fallback 1 gives one workspace its own lockfile again, and its own toolchain file if the library still cannot build on T; the one-toolchain rule withdrew exactly that, and its cost is the reason this is a fallback and not the default.
- The library states its own limits (its newest protocol era is under implementation and unverified; wire cancellation is only partly qualified; one measured conformance run passed 112 of 115 named server checks and is not a conformance claim). None is a trigger here; they bound what the MCP acceptance gate (GATE-TETHER-12) can claim later.
- `xtask check-deps` forbids a second asupersync package in any binary; fallback 1 is the escape if a surface still brings one.
