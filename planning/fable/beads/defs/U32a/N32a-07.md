## Background

FrankenRobotics identifies worlds, seeds, ticks and instants with 64-bit integers, and it sends answers as JSON.
Many clients decode every JSON number as an IEEE double. A double tells consecutive integers apart only up to
magnitude 2⁵³ − 1 = 9,007,199,254,740,991 (FACT). The smallest case that breaks the obvious design "send integers
as JSON numbers" (counterexample CX-348): 2⁵³ + 1 = 9,007,199,254,740,993 decodes to 9,007,199,254,740,992. A
world address or a seed changed by one is a different world, silently; a replay keyed by it reproduces something
else.

Decision (ADR-TETHER-09): integers that can exceed 2⁵³ − 1 travel as decimal strings; counts are range-checked
numbers. Two schema types therefore replace "integer" everywhere in the verb schemas, and a lint forbids any
other integer type. Alternatives excluded: every integer as a number (the defect above); every integer as a
string (counts would lose arithmetic convenience and every client would parse strings for small numbers); a
vendor "bigint" extension (not understood by ordinary JSON decoders).

FACT: the MCP library `fastmcp_rust` builds `serde_json` with `arbitrary_precision` and keeps progress values'
original numeric spelling, so the server side loses nothing. The rule exists for the client's decoder, which this
project does not control.

This mechanism lives in `frob-verbs` (tier Solid) and is measured by GATE-TETHER-07 at M1.

## Scope

In: the three types with their serializers and validators; the refusal `FROB-REF-808`; the schema lint; the
assignment of every existing integer field to a type; the double-decoding harness and the golden envelope set;
the gate record. Out: floating-point canonicalization (the workspace's canonical writer); digests (hexadecimal
strings already); the M2 re-measurement on the daemon's full surface (BD-211).

## Technical approach

**The types.**

| Type | Wire form | Range and rule | Used for |
|---|---|---|---|
| `int53` | A JSON number with no fraction and no exponent | Within ±(2⁵³ − 1). The serializer refuses to emit a value outside it (a programming error surfaced as the internal fault `FROB-REF-990`, exit 9, defined by the envelope bead N32a-03; never a clipped number). An input outside it is refused with `FROB-REF-808` (exit 3) | Counts: episodes, pairs, steps, bytes, worlds, pages, progress numerators and denominators |
| `u64str` | A decimal string matching `^(0|[1-9][0-9]{0,19})$` | 0 to 18,446,744,073,709,551,615. A string that matches the pattern but exceeds the range (for example twenty nines) is refused with `FROB-REF-802` | World addresses, seeds and stream counters, tick indices, commit sequence numbers, nanosecond instants |
| `i64str` | A decimal string matching `^(0|-?[1-9][0-9]{0,19})$` | −9,223,372,036,854,775,808 to 9,223,372,036,854,775,807. `"-0"` is refused by the pattern itself, so that each value has one spelling (DESIGN, needed for request digests), and a client validating against the published schema refuses it too; a string that matches but is out of range is refused with `FROB-REF-802` | Signed offsets and differences of the above |

No leading zeros, no plus sign, no whitespace, no exponent: one spelling per value, so canonical request digests
are stable.

```rust
// DESIGN: intent, not signatures. The newtypes are the only way an integer enters a schema-typed struct.
pub struct Int53(i64);                 // TryFrom<i64> checks |v| ≤ 9_007_199_254_740_991
pub struct U64Str(pub u64);            // Serialize as a decimal string; Deserialize by the pattern, then range
pub struct I64Str(pub i64);
```

**JSON Schema form.** Shared definitions in the schema `frob.common/1`, file `schemas/frob.common.1.json` (the
place and file naming of N32a-02: under `schemas/`, the identifier with `/` replaced by `.`):
`int53` = `{"type":"integer","minimum":-9007199254740991,"maximum":9007199254740991}`;
`u64str` = `{"type":"string","pattern":"^(0|[1-9][0-9]{0,19})$"}`;
`i64str` = `{"type":"string","pattern":"^(0|-?[1-9][0-9]{0,19})$"}`. Verb schemas refer to these by `$ref`.

**The schema lint (`RL-INT`, run by the registry build script).** For every schema reachable from a registry
entry, walk the tree. Any node whose `type` is or includes `"integer"` fails, naming the schema and the JSON
pointer, unless it is the `int53` definition itself in `frob.common/1`. An integer field is a node with a `$ref` to
`int53` and no `type` of its own; it may narrow the range with `minimum`, `maximum`, `exclusiveMinimum`,
`exclusiveMaximum` or `multipleOf` inside ±(2⁵³ − 1) (for example `sync_wait_ms`, 0 to 30,000), and a bound outside
that range fails. Any `"type":"number"` node must carry the extension
`x-frob-float: true`, which asserts the field is a real quantity and not a count or an identifier; a `number`
whose name ends in `_id`, `_seed`, `_tick`, `_ns`, `_addr`, `_seq` or `_index` fails. Rust side: a companion
source lint forbids `u64`, `i64`, `u128`, `usize` fields in any type that derives the envelope serializer unless
wrapped in one of the three newtypes.

**Input handling.** Decoding uses arbitrary precision. A number literal in an `int53` field outside the range, or
with a fraction or exponent, is `FROB-REF-808` with `pointer` naming the field, `observed` the literal as typed,
`required` "integer within ±9007199254740991", and a repair "send this field as a decimal string if its schema
type is `u64str`". A number where a `u64str` is required is `FROB-REF-802` (wrong type).

**The double-decoding harness (`frob-conformance::double_client`).** A decoder that reads a JSON text, converts
every number literal to an IEEE double and back to the shortest decimal that round-trips, and yields a value
tree. `assert_survives(text)` decodes the same text once exactly and once through the double decoder and requires
the two trees to be equal. The **golden envelope set** (`crates/frob-conformance/fixtures/tether/golden_envelopes/`)
holds at least one envelope per registered verb plus boundary envelopes: seeds and world addresses at 2⁵³ − 1,
2⁵³, 2⁵³ + 1 and 2⁶⁴ − 1; counts at 2⁵³ − 1; tick indices above 2⁵³.

**The control of GATE-TETHER-07 (M1).** This bead builds CX-348's plant under the plant identifier
`schema-bare-int64` of its catalogue entry in the counterexample registry N32-CX (the build flag that serializes
seeds as JSON numbers; a schema with a bare `"type":"integer"`) and catches it in its own tests. The control row in
`crates/frob-conformance/registry/controls.toml` (`seed` = the CX number, `kind = "mutation"`, gate
GATE-TETHER-07) is derived from that entry by the seeding tool of N38b-05, which also allocates its `NC-` number:
this bead writes and allocates no row, and binds its catching tests to the seeded control by the name prefix
`nc_<nnnn>_`. The gate's record is printed `pass` only when that control is caught in the same run (STD-TEST's
`GateReport`; a gate with no control is `not-eligible`). N32b-24 binds its binary-level test
`cx_348_double_decoder_envelope` to the same control at M2.

Determinism: exact. Evidence class of the gate: Tested (known answer).

- [ ] GATE-TETHER-07 (TARGET, M1): the golden envelope set passes through the double-decoding client with no changed value, and the schema lint finds no bare 64-bit integer; the measured counts (envelopes, fields checked, lint findings) are recorded.
- [ ] 9,007,199,254,740,993 as `int53` input is refused with `FROB-REF-808`, exit 3; as `u64str` (`"9007199254740993"`) it is preserved exactly through serialization, the double client and deserialization.
- [ ] The serializer cannot emit an out-of-range `int53` (property test over the full `i64` range).
- [ ] Every integer field of every schema registered at M1 is assigned one of the three types; the assignment table is in `CONTRACT.md`.
- [ ] The lint fails on each planted violation: a bare `"type":"integer"`; a `number` named `world_addr`; a raw `u64` field in an envelope struct; an `int53` reference narrowed to a maximum above 2⁵³ − 1. It passes on `int53` references narrowed inside the range.
- [ ] The control seeded for CX-348 (by the tool of N38b-05, from N32-CX's entry; this bead writes no row of `controls.toml`) is caught in the run that records the gate, by this bead's tests on the plant `schema-bare-int64`, which carry the control's name prefix `nc_<nnnn>_`.

## Test plan

### Unit tests (`cargo test -p frob-verbs numbers`, `cargo test -p frob-conformance double_client`)
- `int53_bounds`: 9,007,199,254,740,991 accepted; 9,007,199,254,740,992 refused; the same for the negatives.
- `int53_rejects_fraction_and_exponent`: `1.0`, `1e3` in an `int53` field → 808.
- `u64str_pattern`: `"0"`, `"18446744073709551615"` accepted; `"01"`, `"+1"`, `" 1"`, `""`, `"1e3"`, `"18446744073709551616"`, `"99999999999999999999"` refused.
- `i64str_pattern`: `"-9223372036854775808"` accepted; `"-0"` refused by the published pattern (a standard JSON Schema validator refuses it too); `"-9223372036854775809"` refused by the range check.
- `double_client_changes_2p53_plus_1`: the bare number 9007199254740993 comes back as 9007199254740992 (this is the harness's own known answer; if it does not, the harness is not decoding as doubles).
- `u64str_survives_double_client`: `"9007199254740993"` is unchanged.
- `golden_set_survives`: every file in the golden set.
- `lint_bare_integer`, `lint_number_named_like_identifier`, `lint_raw_u64_in_envelope`, `lint_int53_bound_out_of_range`: each planted violation is reported with its pointer. `lint_bare_integer` and the mutant run of `golden_set_survives` are the catching tests of CX-348's plant and carry the prefix `nc_<nnnn>_` of its seeded control (nnnn is the `NC-` number the seeding tool issued).
- `lint_allows_narrowed_int53`: `{"$ref":"frob.common/1#/$defs/int53","minimum":0,"maximum":30000}` passes; the `int53` definition itself is not reported.
- `gate_07_needs_caught_control`: with the CX-348 control row removed from a scratch registry the gate record is `not-eligible`; with the mutant flag forced off (the control not caught) it is `fail`.
- Property `roundtrip_u64`: 10⁵ random `u64` values serialize and parse to themselves; the same for `i64`.
- `emit_out_of_range_is_990`: a handler that returns a count of 2⁵³ in an `int53` field yields one envelope with exit 9 and `FROB-REF-990`, never the number.

### End-to-end script and logging
`scripts/e2e/tether_integers.sh` (header `bead=N32a-07 milestone=M1 labels=tether,gate`): runs every registered
verb's example with `--json` on the real `frob`, pipes each envelope through the double client, and compares; then
sends the four boundary inputs to a verb with a seed argument (`frob sim run … --seed <value> --key "$(e2e_key
seed-<i>)" --json`, one key per value, since `sim.run` is a `run` verb) and checks the echoed seed;
then rebuilds with CX-348's mutant flag and expects the golden-set comparison to fail (`expected: fail`). It
sources the STD-E2E helper and writes `target/e2e-logs/tether_integers/<utc>.ndjson` with a transcript; every line
has `ts`, `script`, `bead`, `step` (the verb or boundary value), `event`: `cmd` lines with the exact command line,
exit code and wall time, `assert` lines with the field pointer and both values on any difference, one
negative-control line for the mutant run (`caught` or not), `metric` lines for envelopes checked, numeric fields
checked, lint findings (threshold 0), the BLAKE3 digest of the golden set; on failure the verb, the first changed
pointer with its exact and double-decoded values and the saved envelope path; and a `summary` naming
GATE-TETHER-07.

### Known answers and negative controls
- KA-756 (exact): 2⁵³ + 1 = 9,007,199,254,740,993 through a double-decoding client is refused as `int53` (`FROB-REF-808`) and preserved exactly as `u64str`; as a bare JSON number it decodes to 9,007,199,254,740,992.
- CX-348 (catalogue entry of N32-CX, plant `schema-bare-int64`; its control is seeded by N38b-05 and not written here): a schema with a bare integer type must fail the lint; a build flag that serializes seeds as numbers must make `golden_set_survives` fail on the boundary envelopes.
- Metamorphic relation: for any envelope, exact decode equals double decode (the harness's invariant).
- Determinism lanes: golden bytes identical in debug and release and on both hosts.

## Considerations

- INV-TETHER-07: no integer travels as a JSON number unless its schema type is `int53` and its value is within ±(2⁵³ − 1). This bead's property tests are its proof by test.
- The pattern admits twenty-digit strings above the 64-bit range; the range check after the pattern is mandatory and tested.
- Progress events use `int53` for `done` and `total`; a count that could exceed the range must be redesigned as a string field, not clipped.
- Subsystem schemas written before this lint exists will fail it; the fix is in the schema, and the lint has no allowlist.
- The gate is first recorded here at M1 on the M1 surface and re-read at M2 on the daemon's surface with the job, cursor and chunk fields.
