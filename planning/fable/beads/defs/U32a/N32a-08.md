## Background

Anything in FrankenRobotics that takes longer than an agent should wait is a **job**: a study of paired episodes,
a mission synthesis, a training run. A job must survive everything around it: the client that submitted it may be
killed, the connection may drop, the daemon may restart, a device may be lost. The crash-consistent job protocol
makes three promises: an admitted job is never lost and never duplicated; nothing partial is ever published as a
result; and every terminal state accounts for every planned trial.

This bead is the core of that protocol on the Tether side (tier Solid): the **job ledger** and the **job state
machine**, in the crate `frob-verbs`. Telemetry and results are published in chunks whose format and store belong
to Chronicle (the telemetry subsystem); Tether owns the leases and the transaction discipline those publishes run
under. The M1 form runs on the CPU with no daemon; the same code is hosted by the daemon `frobd` from M2.

Design decisions (DESIGN):
- *The ledger is a FrankenSQLite database under the state root, with exactly one writer.* FACT to recheck at the
  pin: the suite's mail server warns of a snapshot-drift defect in the engine's concurrent-writer mode and
  defaults to a single writer (`mcp_agent_mail_rust/crates/mcp-agent-mail-server/src/lib.rs`). From M2 the writer
  is the daemon. At M1, with no daemon, the `frob` process that runs a job takes an exclusive lock file under the
  state root for the duration of its writes; a second writer waits or is refused with `retry: backoff`.
  Alternatives excluded: replicated consensus, gossip membership and escrow counters (one daemon per host; nothing
  is replicated; they solve a problem this system does not have).
- *Job logs persist independently of any client connection.*
- *Every transition is identified by (job, logical world, episode, tick)*, never by wall-clock time, slot or
  device, so a replayed job produces the same transition records.

## Scope

In: the ledger tables for jobs, events, logs and leases; the state machine and its legal transitions; trial
accounting and terminal receipts; lease generations; the cancellation receipt; restart recovery; the `job` block
of the envelope. Out: the admission transaction and idempotency binding (N32a-09); the chunk-publishing
transaction and the chunk tables (BD-091, BD-210); the job verbs `job.list`, `job.status`, `job.wait`, `job.find`,
`job.cancel` as registry entries (BD-210); budgets (N32a-15); dispatch and preemption policy (BD-295, BD-296).

## Technical approach

**States and transitions.**

| From | To | Cause | Recorded with |
|---|---|---|---|
| (submission) | `refused` | Admission refused (budget, guard, scope, schema). No job identifier, no binding, no charge | the refusal envelope only |
| (submission) | `admitted` | The admission transaction committed | job row, binding, reservation |
| `admitted` | `running` | First start record | (job, world, episode, tick 0) |
| `admitted` | `failed_to_start` | Environment or device could not be opened | the refusal |
| `admitted` | `cancelled` | Cancelled before starting | cancel receipt |
| `running` | `preempted` | Parked at a snapshot boundary by the scheduler | checkpoint event with its digest |
| `preempted` | `running` | Resumed | resume event; the digest must equal the checkpoint's |
| `running`, `preempted` | `cancelled` | `job.cancel`, drained | cancel receipt |
| `running` | `complete` | All planned trials accounted for, nothing failed the job | terminal receipt |
| `running`, `preempted` | `failed` | Budget stop, device fault beyond retry, chunk conflict (`FROB-REF-810`, indeterminate), a resume digest that differs | terminal receipt with the refusal |

Terminal states: `refused`, `failed_to_start`, `cancelled`, `complete`, `failed`. Any other transition is a bug
and is rejected by the engine before it reaches the ledger.

**Trial accounting (INV-TETHER-04).** A job has `planned` trials (episodes, pairs, cells; the unit is in the
plan). Each trial ends in exactly one of four counts: `completed` (it produced a result, including a result in
which the robot failed physically), `failed` (a fault: device loss, a non-finite state, an integrity fault),
`refused` (a numerical or capacity refusal of that trial), `unstarted` (never started: budget stop, cancellation,
failure to start). Every terminal receipt carries the four counts and they sum to `planned`. A numerical refusal,
a budget stop and a physical failure are never merged into one count or one message.

**Tables (DESIGN; integer columns that can exceed 2⁵³ − 1 are strings on the wire).**

```
job(id PK, principal, namespace, verb, request_digest, state, planned, completed, failed, refused, unstarted,
    unit, run, size_class, reservation, admitted_seq, receipt_json)
job_event(job, seq, kind, world, episode, tick, payload_json)      -- PK (job, seq); kind: start, checkpoint,
                                                                   -- resume, preempt, trial_end, cancel_request,
                                                                   -- cancel_ack, terminal, recovery
job_log(job, seq, line)                                            -- survives every client
run_lease(run PK, lease_gen)                                       -- the fencing token of the current writer
```

**Leases.** Each run has a lease generation. The engine increments it, in a ledger transaction, whenever worlds
are reassigned to workers: a retry, a shard split, a device loss, a resume after restart. The chunk-publishing
transaction (owned by the Chronicle beads, running in this same database) checks the writer's generation against
`run_lease`, the expected predecessor and the contiguous commit frontier, and publishes the checked payload
hashes, the index and the logical frontier together; an older writer is fenced out and writes nothing. Each
(world, episode) has a fixed logical chunk partition that does not depend on how the device was sharded: chunk k
covers ticks [k·C, (k + 1)·C). A duplicate identical chunk reuses its original receipt; different bytes for a
committed extent are a replay error (`FROB-REF-810`, exit 9) and this engine then moves the job to `failed` as
indeterminate.

**Cancellation.** At the documented safe boundary (the kernel-batch boundary of the device layer): (1) record
`cancel_request`; (2) stop dispatching new work for the job; (3) drain in-flight device work; (4) discard
unpublished state; (5) record `cancel_ack` with the last committed tick per (world, episode); (6) write the
receipt: outstanding device work at the moment of the request (worlds and kernel batches in flight), the observed
cancellation latency, the four trial counts. A dropped handle is not a cancellation receipt: only step 6 is. The
latency is operational metadata and enters no digest.

**Budget stop.** The same drain as cancellation, ending in `failed` with `FROB-REF-702`. Nothing partial is
published as a result (INV-TETHER-03): committed chunks remain as telemetry and the receipt says `budget-stop`.

**Restart recovery, numbered.** (1) Open the ledger and take the writer lock. (2) For every job in `admitted`
with no start record: enqueue it. (3) For every job in `running` or `preempted`: ignore chunks that are not
attached to a committed frontier, increment the run's lease generation, and rebuild from the last committed
checkpoint. (4) For every job with `cancel_request` and no `cancel_ack`: complete the drain bookkeeping and write
the receipt. (5) Record a `recovery` event per job touched. Garbage collection is bounded and respects retained
checkpoints and the frontiers pinned by open cursors.

**The `job` block of the envelope.** `id`, `state`, `progress {done, total, unit}` (always with a denominator),
`eta_s` with its interval, `poll_after_ms`, `last_committed`.

Determinism: the event log of a job is a pure function of the job's request and identities (class exact for the
log's content; wall-clock fields are excluded from its digest). Evidence class: Tested.

## Acceptance criteria

- [ ] Every legal transition of the table is reachable in a test; every other pair is rejected before any write.
- [ ] For 10⁴ seeded jobs with random trial outcomes, cancellations and budget stops, the four terminal counts sum to `planned` (KA-766).
- [ ] After a kill at each of the engine's write points and a restart, the ledger passes its consistency check, every `admitted` job is enqueued exactly once and every running job resumes from its last committed checkpoint with a new lease generation.
- [ ] A cancel returns a receipt naming the last committed tick per world, the outstanding device work and the observed latency; dropping the handle produces no receipt and leaves the job running.
- [ ] After a budget stop or a cancellation no result object exists for the job; committed telemetry chunks remain readable.
- [ ] A late writer (an older lease generation) is refused and writes nothing; a chunk conflict moves the job to `failed` with `FROB-REF-810`, exit 9.
- [ ] A second writer process cannot open the ledger for writing.
- [ ] `CONTRACT.md` documents the state machine, the receipt and the recovery steps.

## Test plan

### Unit tests (`cargo test -p frob-verbs jobs`)
- `transition_table_exhaustive`: all 10 × 10 state pairs; exactly the legal ones succeed.
- `counts_sum_to_planned` (property, 10⁴ cases): `completed + failed + refused + unstarted == planned` at every terminal state.
- `three_outcomes_not_merged`: a job with one numerical refusal, a budget stop and one physical failure reports 1 in `refused`, the remainder in `unstarted`, the physical failure inside `completed`, and three distinct messages.
- `cancel_receipt_fields`; `dropped_handle_is_not_cancel`.
- `budget_stop_publishes_no_result`.
- `restart_enqueues_admitted_once`: 50 admitted jobs, kill, restart twice: each has exactly one start record.
- `restart_resumes_from_checkpoint`: lease generation goes from g to g + 1; chunks beyond the committed frontier are ignored.
- `late_lease_writes_nothing`; `chunk_conflict_fails_job_810`.
- `progress_always_has_denominator`.
- `single_writer_lock`: a second process attempting a write is refused with `retry: backoff`.
- `event_identity`: every event row has (job, world, episode, tick) and no wall-clock column in its digest.

### End-to-end script and logging
`scripts/e2e/job_state_machine_cpu.sh`: on the CPU with the built-in fixture, submits a job with `frob … --json`,
kills the process at three points (after admission, mid-run, during cancel drain), restarts, and reads the job
back by identifier; then runs a cancel and a budget stop. NDJSON under
`target/e2e-logs/job_state_machine_cpu/`: `cmd` lines with exit codes, `assert` lines for the state after each
restart, the four counts and their sum, the last committed tick against the chunk frontier, ledger consistency;
`metric` lines for cancellation latency (recorded); on failure the job's event log path. The `summary` names
GATE-TETHER-08 (CPU rows).

### Known answers and negative controls
- KA-766 (exact): the completed, failed, refused and unstarted counts of a terminal receipt sum to the planned number.
- KA-765 (exact), consumed here through the lease and conflict rules: with the fixed partition [k·C, (k + 1)·C) per (world, episode), a retried shard's second extent is a duplicate (original receipt) or a conflict (`FROB-REF-810`); a reset that reuses tick zero does not overwrite the first episode.
- Negative controls (CX-349, CX-350 seed them): a build that keys chunks by tick range, in which ranges [0, 100) and [50, 150) both commit; a build that keys by (world, tick), in which the second episode overwrites the first; a build that enqueues `admitted` jobs on restart without checking for a start record (a job runs twice). Each must be caught.
- Determinism lanes: the event log digest identical twice on one machine, across worker counts, in debug and release.

## Considerations

- The chunk conflict code differs between two chapters of the plan: the surface chapter calls it `FROB-REF-810` (exit 9) and the telemetry chapter lists `FROB-REF-878` for different bytes under a committed chunk key. This bead uses 810 for the job-level failure the caller sees; the publisher's own refusal code is the Chronicle bead's. The registry owner must confirm whether they are one code or two.
- OPEN-CHRON-5 (lease granularity: one generation per run, or one per shard with a versioned world-to-shard map; default one per run; owner: Tether lead) is a parameter here.
- The lab-runtime exploration of this state machine (crash at every await point, torn writes, clock jumps) is the simulation-testing bead; this bead's kill tests are the deterministic subset that runs on every commit.
- The mapping of trial outcomes to the four counts is DESIGN where the plan names only the counts.
