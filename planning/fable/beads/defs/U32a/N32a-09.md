## Background

An agent's call can fail in a way that hides the outcome: the connection drops after the daemon has accepted the
work and before the answer arrives. If the agent simply calls again, a naive system runs the work twice and
charges the budget twice. **Idempotency** is the property that calling again with the same key is safe: one job
and one budget charge exist per (principal, verb, idempotency key), under any interleaving and any crash point
(INV-TETHER-05).

Every `mutate` verb and every job-submitting `run` verb takes an idempotency key; omitting it is a refusal
(`FROB-REF-805`, exit 3). The protocol binds, **in one transaction of the job ledger**, six things: the caller's
principal and namespace, the verb, the key, the canonical request digest, the budget reservation and the job
identifier.

Why one transaction (counterexample CX-345, the obvious shortcut "look up the key, then insert, in two
statements"): requests A and B carry the same key and payload. A looks up and misses; B looks up and misses; A
inserts; B inserts. Two jobs run and the budget is charged twice. The single transaction with a unique index on
(principal, verb, key) leaves one.

Why immutable identifiers (ADR-TETHER-11): mutating and job-submitting verbs bind immutable identifiers. A mutable
name (`quad-a`) is resolved once, before the request is digested, and the resolution is echoed in the envelope's
`bound` field. Otherwise a retry after the name has moved to a new version would mean a different request under
the same key.

FACT: the suite's mail server records a key, a payload fingerprint and the serialized result inside the
mutation's own transaction, with a 24 h default window
(`mcp_agent_mail_rust/crates/mcp-agent-mail-tools/src/idempotency.rs`). This is the same pattern with the
reservation and the job added.

Tier Solid, crate `frob-verbs`. The M1 form runs in process on the CPU; the gate GATE-TETHER-05 is closed on the
daemon at M2.

## Technical approach

**The protocol, numbered (the plan's four steps).**
1. Resolve names to immutable identifiers and fill defaults. Serialize the resolved request canonically (sorted
   keys, no insignificant whitespace, NFC strings, numbers by the integer rules: counts as range-checked numbers,
   64-bit values as decimal strings) and take its BLAKE3 digest.
2. Begin an **immediate** transaction. Look up (principal, verb, key).
3. *Found with the same digest:* return the stored receipt with `idempotent_replay: true`. *Found with a different
   digest:* refuse with `FROB-REF-803`, exit 7, showing both resolutions (the stored `bound` map and the new one).
   *Not found:* insert the binding, debit the reservation and insert the job row in state `admitted`, all in this
   transaction.
4. Commit. **Only then** enqueue the job and return the receipt.

A crash after step 4's commit and before the receipt reaches the caller is the transport failure class: the retry
with the same key finds the binding and returns the original job. On restart the daemon enqueues every `admitted`
job that has no start record.

**What the digest covers (DESIGN).** The verb name, the resolved arguments, the budget, and `expected_parent` for
a `mutate` verb. It excludes the key itself and the transport-only properties `sync_wait_ms`, `on_cancel` and
`estimate_only`, so that a retry with a longer wait finds the same job. An `estimate_only` call submits nothing
and binds nothing.

**Table (DESIGN).**

```
idem_binding(principal, namespace, verb, key, request_digest, bound_json, reservation, job, receipt_json,
             created_seq, expires_seq)
UNIQUE (principal, verb, key)
```

`receipt_json` is, for a job, the job handle and the first envelope; for a `mutate` verb that creates no job, the
serialized result envelope. Admission refusals (over budget, missing scope, admission guard) are decided before
the insert and bind nothing: the same key may be retried after the cause is repaired.

**Scope and retention.** Keys are scoped to (principal, verb): the same key under another verb or another
principal is a different binding. A binding is kept as long as its job record. For `mutate` verbs that create no
job the retention is 24 h (TARGET), measured on the ledger's commit sequence against a recorded clock reading at
insert; after expiry the key may be reused and is then a new request.

**Stale parent.** For a `mutate` verb with `expected_parent`, step 3's "not found" branch also checks, inside the
same transaction, that the expected parent is the head of the lineage; otherwise `FROB-REF-804`, exit 7, with the
actual head, and nothing is inserted.

**Lookup by key.** `find_by_key(principal, verb, key) -> Option<Receipt>` is a read used by `job.find`; it is the
recovery path after a transport failure and never creates anything.

**Proof obligation PO-TETHER-01: the admission transaction yields INV-TETHER-05.** Verification: exhaustive
interleavings of two submitters and one crash over the four steps on a deterministic runtime; the two-statement
variant must fail (negative control). Concretely: each submitter is four step functions executed in order; two
submitters give C(8, 4) = 70 interleavings; a crash is injected after any of the 8 steps or not at all (9
choices), giving 630 schedules; after each schedule both submitters retry to completion with the same key. The
oracle: exactly one job row, exactly one debit, both callers end holding the same job identifier, at most one of
the two first answers lacks `idempotent_replay`. The same enumeration is run with a changed payload for the second
submitter: one job, one debit, the second caller holds `FROB-REF-803`.

Determinism: the outcome set is independent of the schedule; which submitter wins is schedule-dependent and is
the only freedom. Refusals: `FROB-REF-803` (exit 7), `-804` (exit 7), `-805` (exit 3).

## Acceptance criteria

- [ ] PO-TETHER-01: all 630 enumerated schedules with identical payloads leave one job, one charge and a replayed receipt for the loser; all 630 with a changed payload leave one job, one charge and `FROB-REF-803` for the other caller.
- [ ] The two-statement variant (test-only build flag: look up and insert as separate statements, no unique index) produces two jobs and two charges on at least one schedule, and the test reports that schedule (negative control caught).
- [ ] 1,000 seeded concurrent races of two identical submissions, and 1,000 with a changed payload, each leave exactly one job and one charge (the M1, in-process rows of GATE-TETHER-05).
- [ ] A crash injected at every commit point leaves one job, one charge and a replayed receipt on retry.
- [ ] A `mutate` or job-submitting `run` call without a key is refused with `FROB-REF-805` before anything is charged.
- [ ] A retry after the bound name has moved returns the original job, and `bound` shows the original resolution.
- [ ] A retry that differs only in `sync_wait_ms` or `on_cancel` is a replay, not a conflict.
- [ ] A stale `expected_parent` is refused with `FROB-REF-804` and inserts nothing.

### Known answers and negative controls
- KA-763 (exact): requests A and B with the same key and payload, interleaved, give one job and one budget charge; the retry returns the stored receipt with `idempotent_replay: true`; the same key with a different digest is refused (`FROB-REF-803`, exit 7).
- CX-345, entered in the negative-control registry: look up, then insert, in two statements: two jobs run and the budget is charged twice.
- Metamorphic relation: permuting which submitter is "A" leaves the final ledger digest unchanged.
- Determinism lanes: the 630-schedule results identical twice on one machine, in debug and release, on both hosts.

## Considerations

- Whether the budget belongs in the digest is DESIGN (it is part of the question); a retry with a different budget is therefore a conflict, and the refusal's repair says "use a new key for a new budget".
- One narrow exemption from the mandatory key: a `mutate` verb whose result identifier is the content address of its resolved request (`study.plan`) is idempotent by construction and its registry entry may mark the key optional; a registry lint restricts the exemption to such verbs.
- Keys are caller-chosen strings; they are length-capped and never interpreted. A key is not a secret and gives no authority: scopes do.
- The 24 h window uses a recorded clock reading only to expire bindings; no result depends on it.
- If the single-writer rule of the ledger is ever relaxed, this bead's proof must be redone: the immediate transaction is what serializes the two submitters.
