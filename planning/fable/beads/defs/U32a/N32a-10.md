## Background

Many answers are too long for one reply: a telemetry query, the cells of a mission answer, a job list, a catalog.
They are returned in pages. The store they are read from keeps growing while the agent is paging, because other
worlds and other jobs are still publishing. A pagination scheme must therefore answer one question precisely:
*pages of what?* The answer here is: of the rows that were committed at the moment of the first page, in one
total order. That is INV-TETHER-06: the pages of one cursor sequence, concatenated, equal the query's rows at the
pinned frontier, none skipped, none repeated.

Two tempting shortcuts fail, and each fixes one design choice:
- *Offset pagination* (counterexample CX-346). Rows at t = 1, 2, 3, 4, page size 2. Page one returns {1, 2}. A
  chunk from a slower world then commits a row at t = 1.5. Offset 2 now returns {2, 3}: row 2 is repeated. Hence
  pages are pinned to a **committed frontier**.
- *A cursor on time alone* (CX-347). Two worlds each have a sample at t = 2 and the page ends on the first; "after
  t = 2" skips the second. Hence the cursor holds a **total-order key**, not a timestamp.

FACT: the suite's mail server already distinguishes an expired cursor from one ahead of the durable tail
(`mcp_agent_mail_rust/crates/mcp-agent-mail-tools/src/messaging.rs`, `fetch_inbox_events`).

The "committed frontier" is the commit sequence number of the ledger at a moment: every chunk and every row
carries the sequence number of the transaction that committed it, and committed rows never change. Tier Solid,
crate `frob-verbs`; the M1 form serves `telemetry.query` and `mission.show` on the CPU; GATE-TETHER-06 is closed on
the daemon at M2.

## Technical approach

**What the first page fixes.** Four things, encoded in an opaque, authenticated cursor (`frob.cursor/1`):
1. the **query digest**: the run or object, the filters and the ordering, canonically serialized and digested;
2. the **committed frontier** of the store at that moment;
3. the **total-order key** of the last row returned;
4. the **schema version** of the rows.

**The order key.** For a telemetry row: (instant, world address, channel, sample index), so rows that share a
timestamp still have one order. For other sources the row source declares its key; a source whose natural order
has ties must append a unique tiebreak (for `mission.show --order cost`: (cost, cell identifier); for `job.list`:
(admission sequence, job identifier)). A source without a declared total order cannot be registered as paginated.

**Page algorithm, numbered.**
1. *First page* (no cursor): compute the query digest Q; read the frontier F; take a pin on F; select the first
   L rows with commit sequence ≤ F that match the filters, in key order; emit them with a cursor
   (Q, F, key of the last row, schema version) and `frontier: F`.
2. *Later page* (cursor c): verify c's authentication tag; recompute Q from the request's filters and ordering; if
   Q ≠ c.Q refuse with `FROB-REF-806` (cursor does not match the query, exit 3); if F is no longer retained refuse
   with `FROB-REF-807` (cursor expired, exit 3); select the first L rows with commit sequence ≤ c.F, matching the
   filters, with key **strictly greater** than c.key; emit them with the advanced cursor.
3. *Last page:* when fewer than L rows remain the envelope carries no cursor (or, under `follow`, a follow
   cursor) and states `complete_at_frontier: F`.

Chunks committed after the first page are invisible to that sequence. A client that wants them starts a new
query, or passes `follow`.

**`follow` (DESIGN detail of the plan's rule that "the answer states the new frontier").** When a sequence is
exhausted and `follow` is set, the next call opens a new *segment*: it reads the current frontier F′, and the
segment's rows are exactly those with F < commit sequence ≤ F′, in key order (for telemetry: a new pin at F′
with the store's exclusive lower bound `after_commit_seq = F`, N29a-04). The envelope states the new
`frontier: F′` and the segment number. Rows are ordered by (segment, key): a late row at t = 1.5 appears in the
second segment and is never spliced into the first, so nothing already delivered is contradicted.

**Cursor encoding (DESIGN).** Canonical JSON `{ "v": "frob.cursor/1", "q": <hex digest>, "f": <u64str frontier>,
"k": <key, as an array of typed components>, "s": <schema version>, "p": <principal>, "seg": <int53> }`, followed
by a keyed BLAKE3 tag under the daemon key (`daemon.key` in the state root, mode 0600; at M1, with no daemon,
the first process that issues a cursor creates it atomically, and from M2 the daemon adopts the same file, N32a-14,
so a cursor saved by one process verifies in a fresh one); the whole is base64url. Clients treat it as opaque. A cursor with a
bad tag, an unknown version or another principal is refused with `FROB-REF-806`. The cursor carries no row data
and no path.

**Pins.** A first page registers a pin (frontier, expiry). Garbage collection is bounded and respects the
frontiers pinned by open cursors; when a pin expires and collection removes rows at or below that frontier, the
cursor is answered with `FROB-REF-807` and a repair "start a new query". For telemetry the pin is an entry of
the store's pin table (N29a-04), and the expiry rule is the one stated there, with two parameters of the
retention policy (DESIGN, replacing this bead's earlier single lifetime of 3,600 s and the store's earlier 15
minutes after last use by one rule that keeps both figures): a pin expires `pin_idle_s` = 900 s after its last
use and in any case `pin_max_s` = 3,600 s after its first page. Other paginated sources use the same two
parameters. The number of live pins per principal is capped at 256 (TARGET, DESIGN): a first page beyond the cap
expires that principal's least recently used pin early, whose cursor then answers `FROB-REF-807` with the repair
"start a new query"; no first page is refused for the cap, and no other principal's pins are touched.

**Store and surface refusals.** A cursor whose query digest differs from the request is refused here with
`FROB-REF-806` before the store is called. The telemetry store has its own check of the same mismatch
(`FROB-REF-896`: a cursor used with a different pin, filter or order); if it fires for a call that came through
this layer, the envelope's refusal is 806 with 896 as its cause, so a client sees one code for one mistake.

**Mutable sources.** For a source whose rows have mutable fields (`job.list`: a job's state changes), membership
and order are pinned to F; mutable fields are read at page time and the row carries `as_of` (the commit sequence
it was read at). The invariant concerns membership and order, which is what skipping and repeating are about.

**Proof obligation PO-TETHER-02: keyset pagination over a total order restricted to a fixed frontier partitions
the snapshot.** Written in `CONTRACT.md` as an induction on pages. Let S be the set of rows with commit sequence
≤ F that match the filters; S is fixed, because F is fixed and committed rows are immutable and retained while
the pin lives. Let k be the total-order key and k₀ = −∞. Page i returns the first L rows of S with key > kᵢ₋₁ and
sets kᵢ to the last key returned. Claim: after page i the concatenation equals {r ∈ S : k(r) ≤ kᵢ} in key order,
without repetition. Base: empty. Step: page i adds exactly the next L rows above kᵢ₋₁; strict inequality and
totality of the order exclude a repeat and a skip. Termination: a page shorter than L is the last, and the
concatenation is S.

Determinism: for a fixed frontier the pages are a pure function of the query and the page size. Evidence: Tested.

## Acceptance criteria

- [ ] PO-TETHER-02 is written in the crate's `CONTRACT.md` and a property test checks it under random appends: for 10⁴ seeded schedules (the in-process rows of GATE-TETHER-06), concatenated pages equal the frontier snapshot, including rows with equal timestamps.
- [ ] A changed filter or ordering with an old cursor is refused with `FROB-REF-806`; a cursor whose frontier was collected is refused with `FROB-REF-807`; both exit 3.
- [ ] A cursor altered by one byte, or presented by another principal, is refused.
- [ ] The worked case returns page two = {3, 4} after a row at t = 1.5 commits; two samples at t = 2 from two worlds are both returned exactly once across a page boundary.
- [ ] `follow` returns the late rows in a second segment and states the new frontier; nothing from segment one reappears.
- [ ] A paginated verb never truncates: when more rows exist the envelope has a cursor; when none remain it says so.
- [ ] Registering a paginated source without a total-order key fails at build time.
- [ ] The offset plant (CX-346, plant identifier `cursor-offset`) and the time-only plant (CX-347, `cursor-time-only`) each fail `pages_partition_snapshot`. The catching tests are bound, by the name prefix `nc_<nnnn>_`, to the two controls that the seeding tool of N38b-05 derives from N32-CX's catalogue entries (gate GATE-TETHER-06); this bead writes and allocates no row of `controls.toml`.

## Considerations

- The two chapters that describe this mechanism spell the telemetry order key differently: (instant, world address, channel, sample index) here and (tick, world, episode, stream, sample identifier) in the chunk protocol. They are one order if a world address carries world and episode and a channel is a column of a stream; the row source's declared key is authoritative and this bead only requires that it be total.
- A cursor is not a capability: holding one grants nothing beyond what the principal's scopes allow at each page.
- Pins cost retention. The cap on live pins and the lifetime are the levers; an agent that pages slowly gets 807 and a repair, never a silent gap.
- The `follow` segment rule is DESIGN; the alternative (splice late rows into key order) would contradict rows already delivered.
