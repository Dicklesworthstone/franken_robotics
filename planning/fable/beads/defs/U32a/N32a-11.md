## Background

FrankenRobotics serves its verbs on two surfaces, the command line `frob` and the MCP server `frob-mcp`, and both
are generated from one registry (`registries/verbs.toml`, compiled into a static table in the crate `frob-verbs`).
Generation makes drift unlikely; it does not make it impossible. A surface can still differ from the registry
because of a hand-added tool, a flag the parser accepts and the tool schema lacks, a per-surface default that
nobody declared, or a library that rewrites a schema on the way out. INV-TETHER-01 states the rule: every surface
is generated from the registry; no verb, flag, schema or refusal exists on one surface and not the other, except
per-surface defaults declared in the registry and the unknown-verb case.

GATE-TETHER-02 (Known answer; earliest M1; TARGET) measures it: *the CLI and MCP surfaces are generated from the
registry and their parity diff is empty; every verb has a schema, an example and a refusal list; the served
`tools/list` equals the registry under the name map.* The design point (ADR-TETHER-01) is that the gate checks the
**served** surfaces, what a client actually receives, and not the generator's intentions.

This bead builds the gate's harness once. The five milestone verb-set beads (M1 to M5) each close their part of
the gate by running it on their verbs. It lives in `frob-conformance`, the test-harness crate (layer 7, tier
Solid).

One parity implementation exists (DESIGN: this bead and the registry unit's NJL-02 had each drafted a harness
that diffs the served CLI and MCP against the registry for this gate). The tool is `frob-surface-diff` of
NJL-02 (M0), whose `parity` check lists the surfaces, compares fields and runs three behavioural spot checks,
and which also owns the record schema `frob.verbs.parity/1`, the closed list of accepted differences and the
independent reader of the registry file. This bead depends on it and is the gate-grade extension of that
check from M1: the further checks listed below, the gate's script and per-milestone report, and the negative
controls registered for GATE-TETHER-02. It adds modules to the same tool and defines no second diff, schema
or exemption list.

## Scope

In: what this bead adds to the `parity` check of `frob-surface-diff`: the probe of the flags the CLI parser
really accepts; the cross-check of the schemas served by `frob schema`; the normal form for schema comparison
and the flag-to-property map; the detection of undeclared per-surface defaults; completeness (schema, example,
refusal list) reported by verb; behavioural parity on each verb's first example; the in-memory MCP transport
beside stdio and loopback HTTP; the assertion that the gate has exactly one exemption; the six negative
controls; the script `scripts/e2e/tether_parity.sh` and the per-milestone report.

Out, with the bead that has it: the tool itself, its reading of the registry file with a reader that shares
no code with the generator, the listing and set differences of the two surfaces, the field comparison, the
spot checks (misspelt parameter, missing idempotency key, verb before its milestone), the record schema, the
closed list of accepted differences, the e2e-coverage lint, the help-schema snapshots and the cluster scripts'
shell library (NJL-02); the registry lints that run at build time (N32a-02); the content of the verbs (the
verb-set beads); focus and task-cluster behaviour beyond what the list comparison needs (BD-138);
documentation parity of prompts and resources at M3 (BD-298 extends the harness with those two extractors).

## Technical approach

**Three extractors, each producing the same normal form.**

```rust
// DESIGN: intent, not signatures.
pub struct SurfaceVerb {
    pub verb: String,                       // registry name
    pub input: CanonSchema,                 // verb input plus the common properties of its kind
    pub output: CanonSchema,                // frob.envelope/1 specialized
    pub refusals: BTreeSet<RefusalCode>,
    pub examples: Vec<String>,
    pub kind: Vec<Kind>, pub idempotent: bool, pub destructive: bool,
    pub defaults: BTreeMap<String, Value>,  // per-surface defaults
}
```

1. *Registry extractor.* The reference is the registry file `registries/verbs.toml`, read by the tool's own
   strict reader (NJL-02), not the static table compiled into `frob-verbs`: a generator defect that corrupts
   the table must not be able to hide by being its own reference (DESIGN; an earlier draft of this bead read
   the static table). That the compiled table equals the file is a build-time lint (N32a-02).
2. *CLI extractor.* Runs the real binary. From the tool as NJL-02 builds it: `frob robot-docs --json` for the
   verb list, purposes, refusals and examples, and `frob <cli path> --help --json` for the entry and its
   schemas. Added here: `frob schema --verb <verb> --in --json` and `--out --json` (the verb form of `schema`,
   BD-022; a positional verb name is the same request), whose schemas must equal the ones
   `--help --json` returned (two served paths to one schema); and, for each verb, a generated probe that
   passes every declared flag once and one undeclared flag (which must be refused with `FROB-REF-802`), so
   that the flags the parser really accepts are observed and not assumed.
3. *MCP extractor.* Starts the real server over stdio and over loopback HTTP as the tool does, and in addition
   on the library's in-memory transport; calls
   `tools/list` (following `nextCursor` to the end, with the server launched to list every cluster); maps each
   tool name back through the name map (`_` to the registered name by table lookup, never by string surgery);
   reads `inputSchema`, `outputSchema`, `annotations`, tags and description; parses the refusal codes from the
   description's line `Refusals (FROB-REF-): n, n, …` (the form of NJL-01's `short_doc`: the full list as
   three-digit numbers, ascending, comma separated) and the example from its `Example: ` line, and reads both
   again from the long-form documentation. A description without exactly one such line is a finding.

**Normal form.** Schemas are canonicalized (sorted keys, `$ref` resolved, descriptions dropped) before
comparison. CLI flag names are mapped to property names by the generator's own rule (`--kebab-case` ↔
`snake_case`), and the common flags to the common properties through the `cli_flag` field of
`entry.common_properties()` (NJL-01), never through a table kept by hand in the harness: a hand table of the
two exceptions (`--key` ↔ `idempotency_key`, `--estimate` ↔ `estimate_only`) would be a second copy of the rule
and would miss `--action` and every flag a later variation adds (`--engine`, `--override`). Only the naming is
read from the derivation; which properties a kind must have stays the tool's own field comparison (NJL-02).

**The diff, numbered.**
1. Verb sets: registry = CLI = MCP under the name map. An extra or missing verb on any surface is a finding. The
   one MCP-only tool `verb_invoke` and the three base tools are in an allowlist of exactly four names: with
   every cluster listed, `verb_invoke` is the only served tool that maps to no registry verb (the tool's
   declared difference `verb-invoke`); the base tools `session_focus`, `job_wait` and `job_cancel` are
   registry verbs, and the allowlist says which names a listing focused on one task cluster may hold beyond
   that cluster.
2. Per verb: input schema, output schema, refusal list, examples, kind, idempotency and destructive flags are
   equal across the three.
3. Per-surface defaults: any difference between CLI and MCP defaults must be declared in the entry's `wait`
   table (the bounded wait: wait to completion on the CLI; 5,000 ms on MCP, at most 30,000). An undeclared
   difference is a finding.
4. Completeness: every verb has at least one schema pair, one example and a non-empty full refusal list (its
   chapter codes plus the codes the generator appends for its kind, N32a-02 RL-06). The chapter list alone may be
   empty (`doctor`, `capabilities`), so the check reads the full list as served (the generated description and
   `frob robot-docs --json`), not the registry field.
5. Behavioural parity on examples: for each `read` verb, and for each estimable `run` verb in estimate-only mode,
   run its first example on the CLI and the equivalent call over MCP and compare envelopes after masking
   `cost.wall_ms`; a refusal case per verb (a misspelt parameter) is compared the same way. Each example is
   first passed through the example-identity substitution of NJL-02 (the same function and the same
   `fixtures/verbs/identities.toml` that the cluster scripts and BD-137's `examples_run` use), on both
   surfaces: an example names stored objects by abbreviated identities (`r:19e2`), which no input schema
   accepts, so without it the comparison would be of two `FROB-REF-802` refusals. An abbreviation with no row
   is reported as `example-unresolved` in `example_diffs`, never skipped.
6. The single exemption: the unknown-verb case. On the CLI it is an envelope with `FROB-REF-801`; on MCP the
   library answers before generated code runs (a JSON-RPC error −32602, "Unknown tool"), so no envelope exists.
   The harness asserts exactly this pair of behaviours and lists it as the only exemption; any second exemption
   is a failure of the gate. The list is the tool's closed list of accepted differences (NJL-02): its one row
   of class exemption is `unknown-verb`, and its three rows of class declared difference are not exemptions
   of the gate: `wait-default` is item 3 above, `verb-invoke` is the one name of item 1's allowlist that is
   not a registry verb, and `session-focus-mcp` is the declared hand-written handler of `session.focus`. The
   report's `exemptions_used` must equal [`unknown-verb`].

**Report.** `target/parity/<milestone>.json`: the tool's parity record for the whole registry through that
milestone, in the tool's one schema `frob.verbs.parity/1` (NJL-02; an earlier draft of this bead named a
second schema, `frob.parity/1`). It holds the registry digest, the counts, the difference lists of the tool
(`missing_cli`, `missing_mcp`, `extra_cli`, `extra_mcp`, `field_diffs`, `behaviour_diffs`) and the lists this
bead's checks add (`flag_diffs` for item 2 of the CLI extractor, `default_diffs` for item 3 of the diff,
`example_diffs` for item 5), every one of which must be empty; `exemptions_used` (must equal the one above);
the transports measured; and the configuration (in-process design of record, or the socket fallback if
KILL-MCP fired). "The diff is empty" means all of those lists are. The gate recorder stores it per milestone.
The script's flag `--through <milestone>` is passed to the tool as `--milestone <milestone>`.

Determinism: the report is a pure function of the binaries and the registry (class exact).

## Acceptance criteria

- [ ] GATE-TETHER-02 machinery: on a tree with no planted defect the diff is empty, the exemption list has exactly one entry, and the served `tools/list` equals the registry under the name map on all measured transports.
- [ ] The checks run inside `frob-surface-diff parity` (NJL-02) and the report is that tool's record in schema `frob.verbs.parity/1`; no second diff tool, record schema or exemption list exists in the tree (a source scan), and the reference is the registry file read by the tool's own reader.
- [ ] Every verb in the measured set has a schema, an example and a refusal list; a verb lacking any of the three is reported by name.
- [ ] Each negative control below is caught and named in the report.
- [ ] The harness accepts a milestone filter (`--through M1`) and records one result per milestone; a verb whose handler is absent is compared on its definition only and listed as declared.
- [ ] The harness runs unchanged against the socket-fallback configuration of the MCP server.
- [ ] The tool-name reverse map is by table lookup; a test proves that `telemetry_inspect_pixel` maps to `telemetry.inspect-pixel` and not to `telemetry.inspect.pixel`.

## Test plan

### Unit tests (`cargo test -p frob-conformance parity`)
- `normal_form_ignores_key_order_and_descriptions`.
- `flag_property_map`: `--sync-wait-ms` ↔ `sync_wait_ms`; `--key` ↔ `idempotency_key`; `--estimate` ↔ `estimate_only`; `--action` ↔ `action` on a two-kind entry, each read from `common_properties()`; the harness source holds no literal of a common flag (source scan).
- `refusals_parsed_from_short_doc`: the description of the specimen `design.check` yields exactly {101, 104, 107, 110, 720, 723, 724, 802}; a description with the line removed, or with two such lines, is a finding.
- `examples_substituted_before_parity`: a `synthetic` `read` entry whose example is `frob result show r:19e2 --json`, with a row for `r:19e2` in a scratch identities file, is run with the full identity on both surfaces and compares equal; with the row removed it is reported `example-unresolved`.
- `reverse_name_map_by_lookup` (the case above).
- `allowlist_is_four`: in a listing focused on one task cluster the only names beyond the cluster are `session_focus`, `job_wait`, `job_cancel` (registry verbs, listed whatever the focus) and `verb_invoke` (the one tool that is no registry verb); a fifth extra tool is a finding.
- `schema_paths_agree`: for every verb, `frob schema --verb <verb> --in --json` and `--out --json` equal the schemas of `frob <cli path> --help --json` in normal form; a planted difference is a `field_diffs` entry.
- `declared_default_difference_ok`: CLI waits to completion, MCP 5,000 ms, declared → no finding.
- `undeclared_default_difference_found`: a synthetic entry whose CLI default page size is 100 and MCP 50 with no declaration → finding.
- `unknown_verb_exemption_exact`: CLI 801 envelope; MCP −32602; a server build that wraps unknown tools in an envelope changes the exemption and fails.
- `missing_example_reported`; `empty_refusal_list_reported` (a synthetic entry with an empty chapter list under a scratch kinds table that appends nothing is reported; `doctor`, whose chapter list is empty and whose served list holds its kind's appended codes, is not).

### End-to-end script and logging
`scripts/e2e/tether_parity.sh --through <milestone>`: builds `frob` and `frob-mcp`, runs `frob-surface-diff
parity --milestone <milestone>` with this bead's checks on the real binaries (MCP in memory, over stdio and
over loopback HTTP), writes the report, then applies each negative control in a scratch build and asserts a
non-empty diff naming it. (The registry-wide script of NJL-02, `scripts/e2e/verbs_registry.sh`, runs the
tool's three checks without the gate's negative controls; this script is the one the milestone verb-set beads
run to close their part of the gate.) It sources the STD-E2E helper (header `bead=N32a-11 milestone=M1
labels=tether,gate`) and writes `target/e2e-logs/tether_parity/<utc>.ndjson` with a transcript; every line has
`ts`, `script`, `bead`, `step` (the verb, transport or negative control), `event`: `cmd` lines with the exact
command line, exit code and wall time; one negative-control line per plant with the finding that named it; the
BLAKE3 digests of the registry file and of the report; `metric`
lines for verbs in the registry, on the CLI and on MCP (all three must be equal), diff entries (threshold 0),
exemptions (must equal 1), examples executed, envelopes compared; `assert` lines per verb on failure with the
first differing schema pointer and both values; a `summary` naming GATE-TETHER-02 and the milestone.

### Known answers and negative controls
- Known answer: empty diff; one exemption; the three verb counts equal.
- Negative controls, registered for GATE-TETHER-02 (a gate that nothing can fail validates nothing):
  1. a tool registered by hand in `frob-mcp` that is not in the registry;
  2. a CLI flag accepted by the parser and absent from the schema;
  3. a refusal code present in the registry and stripped from the generated description;
  4. a schema property renamed on the MCP side only;
  5. an undeclared per-surface default;
  6. a verb with no example.
- Metamorphic relation: reordering registry entries changes neither the report nor its digest.
- Determinism lanes: report bytes identical twice on one machine, across the two MCP transports, in debug and release.

## Considerations

- The extractor for the CLI probes flags by running the binary, which costs one process per verb; with about 243 verbs this is seconds, and it runs in the per-commit lane.
- A focused MCP session lists only one task cluster; the harness therefore asks the server for the full catalogue (a launch option that lists every cluster) and separately checks that the union over clusters equals the registry.
- If the MCP library changes how it serializes schemas, the diff will show it; the remedy is in the generator or upstream, never an allowlist entry.
- Program risk "the agent surface is too large and agents get lost" is not measured here; this gate measures agreement, the fresh-agent gates measure usability.
