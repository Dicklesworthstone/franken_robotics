## Background

`frob-mcp`, the MCP server of FrankenRobotics, shows an agent one **task cluster** at a time: at most seven tools
for one activity, plus three base tools (`session_focus`, `job_wait`, `job_cancel`). The agent switches cluster
with `session_focus`, which enables the target cluster's tools and disables the previous one's on that
connection; the server library (`fastmcp_rust`) then omits disabled tools from `tools/list`, refuses a direct
call to one, and emits a catalog-changed notification. This keeps an agent's context small (TARGET: the base
tools plus one cluster occupy at most 12 kB of `tools/list`) while the registry holds about 243 verbs.

That primary mechanism assumes three things about the client, the agent harness: that its connection has session
state on the server side; that it speaks a protocol revision the library serves (the library's automatic policy
serves MCP 2026-07-28 and the exact 2024-11-05 handshake, FACT); and that it re-lists tools when told the
catalogue changed (a harness that lists tools once at start-up and never again would keep showing the old cluster
and never see the new one). Open question **OPEN-TETHER-2** records that none of the three has been measured: *do the
agent harnesses in use speak one of the two protocol eras the library serves, and act on catalog-changed
notifications?* Owner: the Tether lead. It blocks GATE-TETHER-12 (the MCP surface gate at M3). Fail-closed
default until decided: **static clusters by launch flag, plus `verb_invoke`**.

This bead builds the three fallbacks the design names, in their order, runs the experiment that answers the
question, and records the decision. Tier Solid.

## Scope

In: the tag-filter route; the `--clusters` launch flag; the compatibility tool `verb_invoke`; the probe suite and
the frame recorder; the compatibility matrix experiment, the list of harnesses probed and how they are recorded;
the decision rule from probe results to a focus mode per harness; the client table `registries/mcp_clients.toml`
and the documentation page generated from it; the decision record; the default launch configuration that follows
from it; the effect on how the M3 gate's focus clause is measured. Out: the primary focus mechanism (BD-138);
transports and authentication (N32a-27); the M3 gate itself (BD-298); the bounded-wait defaults (N32a-33, which
takes each harness's tool-call timeout from this bead's table).

## Technical approach

**The four focus modes, best first.**

| Mode | How the visible set changes | Needs from the client |
|---|---|---|
| `dynamic` | `session_focus` enables and disables tools per session; the list changes | Session state on the connection; re-listing after the catalog-changed notification |
| `tag-filter` (fallback 1) | The client lists with `includeTags: ["task:<cluster>"]`; `session_focus` returns the names and one-line purposes of the cluster's tools | The ability to pass list filters; no notification handling |
| `static` (fallback 2) | The server is launched with `--clusters a,b`; the listed set is fixed for the process | Nothing; the operator picks clusters per agent role |
| `invoke` (fallback 3) | One generic tool `verb_invoke {verb, arguments}`, validated against the verb's schema, beside the base tools; the agent reads `robot-docs` for what exists | Nothing |

In every mode authority is the capability token, not the visible set.

**Fallback 1: filter by tag.** FACT: when a connection has no session state, `disable_tool` reports failure.
`session_focus` then returns its normal list of the target cluster's tools together with a warning
`focus: client-side` and the tag to use. Every tool carries the tag `task:<cluster>` for each task cluster it
belongs to, and FACT: `tools/list` honours the request's `includeTags` (all of) and `excludeTags` (any of). The
client lists with `includeTags: ["task:author"]`; the base tools carry every `task:` tag so that they survive
any filter (DESIGN).

**Fallback 2: a fixed listed set.** `frob-mcp --clusters orient,author,simulate` fixes the listed set when the
server is built, as the suite's mail server does: only the tools of the named clusters and the base three are
registered. `--clusters all` registers everything (used by the parity harness). `session_focus` still records
focus and returns the purposes, with the warning `focus: static`.

**Fallback 3: one generic tool.** `frob-mcp --compat-verb-invoke` exposes `verb_invoke {verb, arguments}` for
clients that never re-list. It exists on MCP only.

| Aspect | Rule |
|---|---|
| Input | `verb` (a registered verb name, in registry spelling), `arguments` (an object), and the common properties, which this bead never lists by hand: they come from NJL-01's derivation. The tool's own input schema carries the union, over the registry's entries, of what `VerbEntry::common_properties()` returns (deduplicated by name, each with its generated schema and description); at call time the accepted set is exactly what `common_properties()` returns for the target entry (today: for a `run` entry `sync_wait_ms`, `idempotency_key`, `budget`, `estimate_only`, `on_cancel`, `envelope_scope` (convention 14); for a `mutate` entry `idempotency_key`, `expected_parent`; `cursor`, `limit`, `follow` on a paginated entry; `action` on an entry with actions; and whatever a later variation of NJL-01's table adds) |
| Validation | `arguments` together with the given common properties is validated against the target entry's `input_schema_with_common_fields()` (NJL-01) with strict validation; a common property the target entry does not have is `FROB-REF-802` with `pointer` at it; an unknown verb is `FROB-REF-801` inside an envelope (here generated code does run, so the envelope exists); a schema failure is `FROB-REF-802` |
| Authority | Identical to a direct call: the session token's scopes are checked against the target verb's capabilities |
| Output | The target verb's envelope, unchanged |
| Annotations | `read_only: false`, `idempotent: false`, `destructive: true`, since it can reach any verb (conservative, DESIGN) |
| Description | Generated: how to find verbs (`robot_docs`, the resource listing the clusters) and one example |

`verb_invoke` is not a second implementation: it resolves the entry and calls the same dispatch path as
`VerbTool`.

**The experiment (answers OPEN-TETHER-2), numbered.**
1. List the agent harnesses the program runs (every harness in use by the owner's swarm tooling at the time of
   the experiment; the same list the fresh-agent gates and the ten-fold test use), each recorded by name, pinned
   version and launch configuration; at least the two most used over stdio and one over loopback HTTP. The list
   is data in the result, not fixed here.
2. For each harness and each offered transport (stdio; loopback HTTP), connect to the real `frob-mcp` with the M1
   verbs through the frame recorder and run the nine probes of the table below.
3. Run each of 5 scripted two-cluster tasks (author then simulate) per harness under each mechanism (dynamic
   focus, tag filter, static clusters, `verb_invoke`) and record completion and the number of tool-definition
   bytes the harness was sent.
4. Decide by the rules below and write the record `docs/adr/OPEN-TETHER-2.md` (every decision record lives in
   `docs/adr/`) and the client table.

**Probe suite** (`surface/frob-mcp/tests/client_probe/`, plus a recorder that sits between a real harness and the
server and logs JSON-RPC frames).

| Probe | Observation recorded |
|---|---|
| P1 handshake | The protocol version the client offers and the one negotiated, or the failure; whether the 2024-11-05 handshake is exact |
| P2 initial list | Whether the client pages `tools/list` (follows `nextCursor`) when the server's page size is small |
| P3 re-list on notification | Whether the connection has session state (`disable_tool` succeeds); after `session_focus` and the catalog-changed notification, whether a new `tools/list` arrives within 10 s (observed on the server), and whether the model's next call can use a newly enabled tool without restarting the harness |
| P4 stale call | Whether the harness still offers a disabled tool to the model, and what it does with the refusal |
| P5 list filters | Whether the harness can be configured to send `includeTags` |
| P6 progress | Whether it sends a progress token and surfaces progress notifications |
| P7 cancellation | Whether its own tool-call timeout or a user interrupt sends a wire cancellation; its tool-call timeout in seconds |
| P8 resources and prompts | Whether it lists and reads resources, subscribes to `frob://job/{id}`, and exposes prompts |
| P9 structured content | Whether it passes `structuredContent` (the envelope) to the model, or only text |

**Decision rule per harness (written before the data; a pure function of the probe record).**
1. P1 fails (neither era): the harness cannot use `frob-mcp`; it is recorded as unsupported over MCP and uses the
   CLI with the skill file.
2. P3 passes in at least 5 of 5 trials and P4 shows no stale offers: `dynamic`.
3. Else P5 passes: `tag-filter`.
4. Else: `static`, with `invoke` enabled in addition if the agent's role needs verbs outside its static clusters.

Secondary settings recorded from the probes: if P9 fails, the server's text content carries a compact rendering
of the envelope (exit, refusal code, `next_actions`) for that harness; if P7's timeout is below the maximum
bounded wait plus margin, the harness's row caps `sync_wait_ms` (an input to N32a-33); if P6 fails, progress is
read with `job_wait`.

**Decision rule for the default launch mode (written before the data).** Dynamic focus is the default launch mode
only if every harness in the list negotiates a served revision, has session state and re-lists after the
notification in at least 5 of 5 trials. Otherwise the default is static clusters by launch flag plus
`verb_invoke` (the fail-closed default), and dynamic focus is a per-harness opt-in for the harnesses that
passed. A harness absent from the table, or at a version the table does not hold, is launched in the fail-closed
default.

**Outputs.** (a) `registries/mcp_clients.toml`: one row per harness and version with the nine observations, the
chosen mode and the launch line. (b) A page contributed to `robot-docs` ("connecting your harness"), generated
from that table. (c) The decision record closing OPEN-TETHER-2, with the table's digest. (d) For the MCP surface
gate (GATE-TETHER-12): the focus clause is measured in `dynamic` mode on the in-memory transport (the server's
behaviour) and, for each harness in the table, in its chosen mode (what an agent actually sees); both are
recorded.

Determinism: not applicable to harness behaviour (the trials are observations of third-party clients; the record
is class `Tested`, with versions pinned). The three fallbacks themselves are deterministic.

## Acceptance criteria

- [ ] With session state absent, `session_focus` returns the warning and `tools/list` with `includeTags: ["task:author"]` returns exactly the `author` tools plus the base three.
- [ ] `frob-mcp --clusters orient,author` lists exactly those clusters' tools plus the base three; a call to a tool outside them is an unknown tool.
- [ ] `verb_invoke` returns, for each of 20 sampled verbs, an envelope byte-identical (after masking `cost.wall_ms`) to the direct tool's; a missing scope is refused identically; a schema failure is 802; an unknown verb is 801 inside an envelope.
- [ ] `verb_invoke` is absent unless the compatibility flag is set, and is the one name of the parity harness's four-name allowlist (N32a-11) that maps to no registry verb; the other three are the base tools, which are registry verbs.
- [ ] The compatibility matrix is recorded for every harness in the list and both transports, with the nine probe observations each and a frame log per probe.
- [ ] The decision record for OPEN-TETHER-2 exists, cites the matrix, and sets the default launch configuration; the default is the fail-closed one unless the rule's condition is met.
- [ ] `registries/mcp_clients.toml` exists with a row per harness and version: nine observations, mode, launch line; the per-harness rule is tested code and each row's mode equals the rule applied to its observations.
- [ ] For each harness, an end-to-end focus switch in its chosen mode shows the model able to call a tool of the new cluster, with at most seven cluster tools plus the base three visible (or, in `invoke` mode, the generic tool).
- [ ] A harness absent from the table is launched in `static` mode with `invoke`, and the generated "connecting your harness" page says so.

## Test plan

### Unit tests (`cargo test -p frob-mcp fallbacks`)
- `tag_filter_lists_cluster`: in-memory transport without session state; `includeTags` → 7 + 3.
- `base_tools_survive_any_task_tag`.
- `clusters_flag_registers_subset`: `--clusters orient` → 7 + 3 tools; `design_check` → JSON-RPC −32602.
- `clusters_all_registers_everything`: count equals the registry count plus the base three.
- `verb_invoke_equals_direct`: for `design.check`, `sim.estimate`, `session.show`, envelopes equal.
- `verb_invoke_unknown_verb_801`, `verb_invoke_bad_arguments_802`, `verb_invoke_checks_scope_720`.
- `verb_invoke_uses_registry_spelling`: `design_check` as the `verb` value is 801 with a repair naming `design.check`.
- `verb_invoke_common_properties_from_registry`: for a `run` target (`sim.run`), a `mutate` target and a paginated `read` target, the accepted common properties equal that entry's `common_properties()` names in order; `sync_wait_ms` given with a `read` target is 802 with `pointer: /sync_wait_ms`; the tool's schema properties beyond `verb` and `arguments` equal the union computed from the registry, so a build with a hand-written list (planted: one that omits `action`) fails.
- `focus_warning_states_mode`: `focus: client-side` or `focus: static` as applicable.
- `crates/frob-conformance/tests/open_tether_2.rs`: `rule_dynamic` (P1 ok, P3 ok, P4 clean gives `dynamic`); `rule_tag_filter` (P3 fails, P5 ok gives `tag-filter`); `rule_static_default` (P3 and P5 fail gives `static`); `rule_cli_only` (P1 fails); `table_rows_match_rule` (every row of the registry file).
- `surface/frob-mcp/tests/focus_modes.rs` (in-memory transport, real server): `dynamic_list_changes_and_notifies`; `tag_filter_lists_seven_plus_base`; `static_clusters_fixed`; `verb_invoke_validates_against_schema` (a misspelt argument is refused with `FROB-REF-802`); `disabled_tool_call_refused`.

### End-to-end script and logging
`scripts/e2e/mcp_focus_fallbacks.sh`: runs the server in the four modes over stdio and loopback HTTP with the
library's own client (configured once with session state and once without), exercising the three fallbacks; and
`scripts/e2e/mcp_harness_matrix.sh <harness-config>`: launches the recorder and `frob-mcp`, drives one pinned
harness through a scripted prompt (list tools, focus on `author`, call `design_check`), the nine probes and the
5 scripted tasks per mechanism, and writes the observations with the chosen mode. Both source the shared helper
and write NDJSON under
`target/e2e-logs/mcp_focus_fallbacks/` and `target/e2e-logs/mcp_harness_matrix/`: `cmd` lines; `metric` lines for
the negotiated revision, re-list latency after the notification (seconds, recorded), tool-definition bytes sent
per turn under each mechanism, tasks completed of 5; `assert` lines for the list contents; a `summary` naming
GATE-TETHER-12 (precondition) and OPEN-TETHER-2. Each probe line carries the JSON-RPC method, the observation
with its threshold (re-list within 10 s; visible tools against 7 + 3) and, on failure, the frame log's path. The
scripted prompts and every JSON-RPC frame are logged; a model's free text is not logged beyond its tool calls;
no private-scene data.

### Known answers and negative controls
- Known answers: `--clusters orient` lists the seven `orient` tools; the tag filter for `author` equals the `author` row.
- Known answer (server side): after `session_focus {cluster: "mission"}` in `dynamic` mode the list holds `mission_new`, `mission_check`, `mission_synthesize`, `mission_refute`, `mission_distinguish`, `mission_show`, `result_revalidate` and the three base tools.
- Negative controls: a harness stub that never re-lists must be classified as not acting on the notification (the classifier is tested on it) and is given `static` or `tag-filter`, never `dynamic`; a `verb_invoke` build that skips the scope check must fail `verb_invoke_checks_scope_720`.
- Negative control: a scripted client that offers a stale disabled tool must fail P4.
- Negative control: a server build with a cluster of eight tools must fail the visible-set assertion.
- Determinism lanes (fallbacks only): list bytes identical twice on one machine and on both transports.

## Considerations

- `verb_invoke` gives up the benefit of small, typed tool definitions: the model sees one loose schema. It is a compatibility measure, off by default unless the experiment says a harness needs it, and its use is counted in session records so that the fresh-agent gates can report results with and without it.
- The experiment observes third-party software at pinned versions; when a harness updates, the row is re-measured, and the default changes only by a new record.
- If no harness passes, GATE-TETHER-12's focus clause ("at most seven tools plus the base three after `session_focus`") is still measurable with the library's client; what changes is the default launch mode, not the gate.
- The library marks its support for the newer protocol revision as unverified upstream; a failure of probe P1 may be the library's, and is then recorded as an upstream work item, not worked around here.
- Harnesses change faster than this project's milestones. The table is keyed by version, the probe is cheap to re-run, and an unknown version gets the default.
- `static` mode with role-specific clusters is not a degraded experience for a swarm in which each agent has one job; the suite's mail server runs that way (FACT). The cost falls on a single generalist agent.
- `invoke` mode gives up per-tool schemas in the tool list, so the model relies on `robot-docs` and on refusals to learn argument names; it is the last resort for that reason.
