## Background

A **study** in FrankenRobotics is a declared statistical comparison: two designs (or a design and a requirement)
run on common world addresses, with a stopping rule fixed in advance. Studies are how the system supports the
claim "design B is better than design A", and they are expensive, so the surface splits them into two phases.

`study.plan` binds a trial manifest to immutable designs, scene, task, seed protocol, budget, backend and **one**
declared study type: anytime-valid or fixed-n exact, never both in one study. It returns a plan identifier that
is the content address of the resolved manifest, the cost estimate with its interval, and, for a fixed-n study,
the pre-analysis of which verdicts are reachable at that n (computed by `eval.preanalyze`). Planning runs no
physics and is idempotent by construction. `study.submit` takes the plan identifier and an idempotency key and
returns a job. `study.compare` reads a study and returns, per metric, a verdict. `eval.compare` remains as the
one-call form: it plans and submits an anytime-valid paired study with defaults.

DESIGN reason for two phases: the agent sees cost and reachable verdicts before any budget is spent, and the
submitted object cannot drift from the planned one. Alternative excluded: a single `compare` call with many
options, where the agent learns the cost after paying it and a retry may bind a design that has since moved.

The planning, submission and status verbs are built on the CPU at M1 by another bead. This bead completes the
contract on the surface side: the two verbs that bead leaves out (`study.compare` as a registered read verb over
the device-era comparison engine, and `study.cancel`), the refusal for a plan that is missing or superseded, and
the accounting invariant every comparison answer must satisfy. Tier Solid; crate `frob-verbs`.

## Scope

In: registry entries, schemas, examples, refusal lists and bindings for `study.compare` and `study.cancel`; the
plan-binding rules checked at `study.submit` time on the daemon; `FROB-REF-809`; the pair-accounting invariant
enforced in the envelope type; conformance of `eval.compare` as plan-then-submit. Out: the e-process and the
exact fixed-n rule (the Arena and Atelier beads); `eval.preanalyze`; the cost model and its interval (BD-219,
BD-297); the CPU study verbs themselves.

## Technical approach

**Plan identity.** A plan is the canonical serialization of the resolved manifest: design identifiers (not
names), scene pack identifier, task identifier, seed protocol (root seed as a decimal string, address scheme),
budget, backend and tier, the study type and its parameters (level α, the pair cap for anytime-valid; n for
fixed-n), and the metric list. `plan_id = "p:" + BLAKE3(canonical bytes)`. Two calls with the same resolved
manifest return the same identifier; `study.plan` therefore needs no idempotency key for safety (its registry
entry marks the key optional because the result is content-addressed, the only case where a `mutate` verb may do
so; DESIGN).

**Submission checks (inside the admission transaction), numbered.**
1. Load the plan by identifier. Missing: `FROB-REF-809`, exit 7, repair "run `study.plan` again".
2. Re-validate every bound identity against the store: a design, scene, task or backend identity that has been
   superseded in a way that invalidates the plan (a retired scene pack, a purged private scene, a backend whose
   fingerprint changed its determinism class) is `FROB-REF-809`, exit 7, naming the stale identity and the
   current one. A design that merely has newer versions is not superseded: the plan binds the old version on
   purpose.
3. Bind (principal, `study.submit`, key, digest of (plan_id, key-independent options), reservation, job) atomically.

**`study.compare` (read, first milestone M3).** Input: a study or job identifier, optional metric filter. Output
per metric:

| Field | Rule |
|---|---|
| `verdict` | One of `settled`, `tied`, `inconclusive`; or `incomparable` or `infeasible` where the study could not be scored |
| `interval`, `evidence` | The interval for the difference and the e-value or exact interval, as produced by the engine |
| `failures` | Failure counts by class for each arm |
| `first_divergence` | The first divergent event between the arms on a common address (world address, tick, event) |
| `pairs` | `a_only`, `b_only`, `both`, `neither`, `unscored`, `planned`, all `int53` |
| `frontier` | The committed frontier the answer was computed at |

**The accounting invariant (INV-TETHER-04, second half).** `a_only + b_only + both + neither + unscored =
planned`. It is enforced where the envelope is built: the `PairCounts` type has a single constructor that takes
the five counts and `planned` and returns an integrity fault if they do not sum; no other code can produce the
block. A comparison stopped early (anytime-valid stop, cancel, budget stop) reports the pairs not run inside
`unscored`.

**`study.cancel` (admin).** Input: a study or job identifier. It requires the scope `job:cancel`. It asks the job
engine to cancel the study's job: drain at the safe boundary, discard unpublished state, acknowledge with the
last committed tick per world. Result: the cancellation receipt and the pair counts at the frontier (the
invariant still holds, with the remainder in `unscored`). A study that is already terminal returns its terminal
receipt with a warning, not a refusal. Refusals: 802, 720, 809 (unknown study).

**`eval.compare` conformance.** The one-call form must be observationally a `study.plan` with defaults followed
by a `study.submit` under the caller's key: the envelope of `eval.compare` carries the `plan_id` it created, and
`study.status` and `study.compare` work on its job.

**A study that declares both types** is refused at planning (this is the planning bead's refusal; restated here
because `study.compare`'s schema has no way to represent a mixed study).

Determinism: `plan_id` and the answer of `study.compare` at a fixed frontier are pure functions of their inputs.
Evidence: the claim product of the study's episodes; claim kind Design comparison; class `Tested` or `Estimated`.

## Acceptance criteria

- [ ] `study.compare` and `study.cancel` are registered with schemas, examples and refusal lists and pass the parity harness.
- [ ] On a planted comparison the five pair counts sum to `planned` (KA-757); no code path outside the `PairCounts` constructor can build the block (compile-fail test).
- [ ] `study.submit` with an unknown plan, and with a plan whose scene pack was retired after planning, is refused with `FROB-REF-809`, exit 7, naming the stale identity; nothing is charged.
- [ ] `study.plan` twice with the same resolved manifest returns the same `plan_id`; changing the seed protocol changes it.
- [ ] A plan made for `quad-a` at version d:41aa… still submits and runs that version after `quad-a` has been edited; `bound` shows d:41aa….
- [ ] `study.cancel` on a running study returns a receipt with the last committed tick and pair counts that sum to `planned`; on a finished study it returns the terminal receipt with a warning.
- [ ] `eval.compare` returns a `plan_id`, and `study.compare` on its job returns the same verdicts.

## Test plan

### Unit tests (`cargo test -p frob-verbs study`)
- `plan_id_is_content_address`: identical manifests → identical identifiers; field order in the request does not matter.
- `pair_counts_constructor_checks_sum`: (10, 12, 60, 8, 6, planned 96) accepted; (10, 12, 60, 8, 5, 96) rejected as an integrity fault.
- `pair_counts_only_via_constructor` (compile-fail).
- `submit_missing_plan_809`; `submit_superseded_scene_809`; `submit_newer_design_version_ok`.
- `early_stop_remainder_is_unscored`: an anytime-valid study that settles at 40 of 96 pairs reports 56 in `unscored`.
- `cancel_requires_scope_720`; `cancel_terminal_returns_receipt`.
- `eval_compare_equals_plan_then_submit`: same seed protocol, same addresses, same verdict and counts.
- `compare_verdict_vocabulary`: the schema admits exactly the five verdict words.

### End-to-end script and logging
`scripts/e2e/study_two_phase.sh`: `frob study plan … --json` (assert a `plan_id`, an estimate with an interval
and, for a fixed-n plan of 30 pairs, the reachable verdicts); `frob study submit <plan_id> --key s1
--sync-wait-ms 0 --json` (exit 8); `frob job wait …`; `frob study compare <job> --json` (assert the sum); the
same submit again (replay); a second plan on a retired scene (809); a second study cancelled mid-run with
`frob study cancel`. It sources the shared helper and writes `target/e2e-logs/study_two_phase/<utc>.ndjson` plus
a transcript: `cmd` lines with exit code and wall time; the envelope `evidence` block (claim Design comparison,
class, tier, determinism, seed); `assert` lines with the five counts and their sum against `planned`; `metric`
lines for estimated against actual cost; on failure the first differing count. Final `summary` with counts.

### Known answers and negative controls
- KA-757 (exact): pair accounting on a planted comparison: `a_only + b_only + both + neither + unscored = planned`.
- Negative controls: a build that drops unscored pairs from the block (the constructor must reject it); a submit path that re-resolves names instead of using the plan's identifiers (the moved-design test must fail); a plan store that accepts an edited manifest under an old identifier (the content-address test must fail).
- Metamorphic relation: permuting the order of metrics in the plan changes the `plan_id` only if the canonical form says so (it does not: metrics are sorted).
- Determinism lanes: `plan_id` and the compare answer identical twice on one machine, across worker counts, in debug and release.

## Considerations

- "Superseded" is deliberately narrow. If it included "a newer design version exists", every plan would be invalidated by the next edit and two-phase planning would be useless.
- The optional key on `study.plan` is an exception to "every `mutate` verb takes an idempotency key"; it rests entirely on content addressing and is limited by a registry lint to verbs whose result identifier is the digest of the resolved request.
- No seed bead names `study.cancel`; it is carried here so that the registered verb has an implementation.
- A paired comparison with an arm under an uncontrolled determinism class is refused by the engine; the surface only passes the refusal through.
