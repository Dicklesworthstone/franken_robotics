## Background

`frobd` is the daemon of FrankenRobotics. It owns the things that must outlive any one client and must have one
owner: the devices (GPUs), the compiled-kernel caches, and the job queue, with fair sharing between agents. The
command line `frob` and the MCP server `frob-mcp` both hand long work to `frobd` as jobs. Without the daemon both
still run CPU-tier verbs in process, and say in the envelope that they did. `frobd` can also host the MCP server
itself (`frobd --mcp`), so that one process serves the job queue and the MCP transports.

Design decisions (DESIGN):
- *One daemon per host, and nothing is replicated.* Consensus protocols solve a problem this system does not
  have. The job ledger has a single writer, and that writer is the daemon.
- *A local socket, not a network service.* It listens on a Unix-domain socket under its state root, mode 0600,
  and speaks newline-delimited JSON (`frob.rpc/1`): a request frame, zero or more progress frames, one envelope.
- *A killed client never owns a job* (ADR-TETHER-03, INV-TETHER-10): killing `frob`, `frob-mcp` or the dashboard
  at any instant leaves the ledger consistent and every admitted job discoverable by its idempotency key.

This bead is version 1, at M2: the process, its service loop and a job queue in which **each job gets its own
environment** and jobs are queued per device. Sharing one persistent environment between jobs (slot dispatch) and
size-class scheduling with preemption come at M3; the per-job mode built here remains afterwards as
`frobd --dispatch=per-job`, the fallback of the kill gate KILL-SLOT. The process shell is in the crate
`frob-cli`; the job engine, ledger and admission code it hosts are libraries in `frob-verbs` so that they can be
tested without a process.

## Technical approach

**State root (DESIGN layout).** `$FROB_STATE` (default: the platform's per-user state directory, `frob/`), mode
0700: `frobd.lock` (exclusive lock; proves one daemon per host and user), `frobd.sock` (mode 0600), `daemon.key`
(mode 0600; authenticates tokens and cursors), `ledger.db` (FrankenSQLite; job, binding, budget and chunk-index
tables), `store/` (the telemetry and result store of the Chronicle subsystem), `logs/` (job logs mirrored from
the ledger), `exports/` (per-session export roots).

**Start-up, numbered.**
1. Take `frobd.lock`. If held: exit 6 with an envelope naming the holder's process identifier.
2. Verify the directory and file modes and the owner; refuse to start on a mismatch.
3. Open the ledger as the single writer; run the recovery procedure of the job engine (enqueue every `admitted`
   job with no start record; for `running` and `preempted` jobs ignore unattached chunks, bump the lease
   generation and rebuild from the last committed checkpoint; finish any half-acknowledged cancellation).
4. Enumerate devices through the backend trait; open device contexts; load kernel caches lazily.
5. Compute the **configuration digest**: BLAKE3 of the canonical serialization of the dispatch mode, the
   scheduler's guard table and its parameters, the registry digest and the stack receipt. It is reported by
   `doctor` and recorded in every job receipt, so a result names the configuration it ran under.
6. Bind the socket and serve.

**Service loop.** One task per connection, running the library server loop: read a request frame, run the
dispatch pipeline (locate, validate, authorize, resolve, digest, implemented?, route), stream progress frames,
write the envelope. The daemon checks peer credentials on accept (same user) in addition to the file mode
(DESIGN). A connection may carry many calls in sequence; frames carry the caller-chosen `id`.

**Queue and execution at M2 (per-job dispatch).** Each device has a queue of admitted jobs. A job opens its own
environment (worlds, model and scene buffers) on its device, runs to completion or to a stop, and closes it.
Between agents (principals) the next job is chosen round-robin over agents with queued work, first-admitted
first within an agent. CPU-tier jobs run on a bounded worker pool sized by the machine envelope. The scheduler
decides only when a job runs: world addresses, seeds and results do not depend on queue position (INV-TETHER-09).

**Shutdown.** On a termination signal: stop accepting new submissions (new calls are refused with the
backend-unavailable family, exit 6, `retry: backoff`); ask each running job to stop at its next safe boundary
(the kernel-batch boundary), publish what is complete, record a checkpoint; close devices; release the lock.
Jobs so parked resume on the next start. A second signal skips the drain; recovery then handles it as a crash.

**Client side.** `frob` and `frob-mcp` look for the socket under the state root. Found and answering: long and
device work goes to the daemon. Not found: CPU-tier verbs run in process with the warning `executor: in-process`,
and device verbs are refused with exit 6 and the repair "start `frobd`". `--no-daemon` forces the in-process
route. If the daemon dies while a client waits, the CLI exits 9 (indeterminate): the caller must not resubmit
blindly and recovers with `job.find` by key.

**Version agreement.** On connect the client sends its registry digest; a mismatch (client and daemon built from
different registries) is answered with one envelope whose finding names both digests, and no verb runs.

**`frobd --mcp`.** Loads the `frob-mcp` library in process and serves its HTTP transport on loopback beside the
socket; the MCP adapter then calls the job engine directly instead of through the socket.

Determinism: the daemon adds no nondeterminism to results; wall-clock quantities appear only in `cost`, logs and
operational receipts. Evidence class of daemon-level checks: Tested.

## Acceptance criteria

- [ ] `frobd` starts, serves `frob doctor --json` through the socket, and a second `frobd` on the same state root exits 6 naming the first.
- [ ] The socket and key files are mode 0600 and the root 0700; a start with looser modes is refused.
- [ ] After `kill -9` of the daemon at 50 seeded points during a mixed workload and a restart, the ledger passes its consistency check, every admitted job is found by its key, and no job runs twice.
- [ ] Killing `frob` or `frob-mcp` at 100 seeded points during waits leaves every admitted job running or recoverable and the daemon serving (INV-TETHER-10).
- [ ] With two agents each queuing 10 jobs on one device, starts alternate between agents.
- [ ] A graceful stop parks running jobs at a safe boundary and they resume after restart with identical digests.
- [ ] Without the daemon a CPU-tier verb answers with `executor: in-process`; a device verb is refused with exit 6.
- [ ] A registry-digest mismatch between client and daemon runs no verb and is reported.
- [ ] No device memory, file handle or lease is leaked across 1,000 job starts and stops (the daemon's resource counters return to baseline).
- [ ] The configuration digest appears in `doctor` and in each job receipt and changes when a scheduler parameter changes.

## Test plan

### Unit tests (`cargo test -p frob-cli daemon`, `cargo test -p frob-verbs rpc`)
- `second_daemon_refused`; `loose_mode_refused`; `wrong_owner_refused`.
- `peer_credentials_checked`: a connection from another user (simulated with a credential shim on the accepted socket; labelled `synthetic`) is closed.
- `round_robin_between_agents`: start order A, B, A, B, … for two agents.
- `shutdown_drains_then_parks`; `second_signal_skips_drain`.
- `digest_mismatch_runs_nothing`.
- `config_digest_changes_with_parameter`: changing the worker pool size leaves it unchanged (not a result-affecting field); changing the dispatch mode changes it.
- `in_process_warning_without_daemon`; `device_verb_exit_6_without_daemon`.
- `resource_counters_return_to_baseline` on `batch-cpu` for 1,000 jobs.
- `daemon_death_gives_cli_exit_9`.

### End-to-end script and logging
`scripts/e2e/frobd_lifecycle.sh` (seed-explicit, idempotent, its own scratch state root): start `frobd`; run
`frob doctor --json`; submit 20 jobs from two sessions with keys; kill clients at random; `kill -9` the daemon
mid-run; restart; `frob job find --key …` for each; wait for completion; graceful stop; restart; compare digests
of a parked and resumed job with an uninterrupted run. It sources the shared helper and writes
`target/e2e-logs/frobd_lifecycle/<utc>.ndjson` plus a transcript: `cmd` lines with exit code and wall time;
`assert` lines for ledger consistency, one job per key, digest equality; `metric` lines for recovery time,
restart-to-first-step time, leaked resources (threshold 0), jobs run twice (threshold 0); the envelope `evidence`
block of each result; on failure the job's event log path. The `summary` names GATE-TETHER-08 (daemon rows).

### Known answers and negative controls
- Known answer: a job parked by a graceful stop and resumed has the same per-world digests as the same job run without interruption.
- Negative controls: a daemon build that enqueues on restart without checking for start records (a job must be seen to run twice and the script must fail); a build that lets a client connection own the job task (killing the client must be seen to kill the job, and the test must fail); a build without the lock file (two daemons must be detected by the ledger's single-writer check).
- Determinism lanes: the parked-and-resumed digest comparison on `batch-cpu` twice, across worker counts, in debug and release; on each device family once the backends exist.

## Considerations

- The machine envelope bounds what one job may take (default 16 GiB, 8 cores, one hour, one device until the owner approves another compute class); the daemon enforces it on its worker pool and refuses larger work.
- The daemon is a single point of failure by design; its answer to failure is fast, exact recovery, not redundancy.
- Per-job dispatch wastes most of a device on small jobs (a 96-pair comparison fills 192 of 8,192 slots, 2.3%); that is the motivation for the M3 work, and the reason this mode is kept only as a fallback.
- Security: the socket is local and user-private. Authority within the user is the session token (later bead); before tokens exist, any process of the same user has full local scope, and the envelope says so.
- If the kill gate KILL-MCP fires, a reduced form of this service loop is needed earlier, for the socket-only MCP fallback.
