## Background

Some verbs of FrankenRobotics finish in a second and some run for an hour. An agent calling a tool faces a
choice the surface must make for it: block until done, or get a handle and poll. Both extremes are bad. Blocking
ties up the agent's turn (and many clients time out). Always returning a handle forces an extra round trip for
every call, and an agent turn is believed to cost 30 to 120 s of thinking (HYPOTHESIS; measured at the M4
fresh-agent gate), so an avoided poll saves more than the compute it waits for.

Decision ADR-TETHER-04: long tools take a **bounded synchronous wait**, `sync_wait_ms`, and otherwise return a
job handle. Most studio verbs finish inside the wait (TARGET: `design check` under 2 s, `control synth` under
5 s). The envelope then carries the result; if the timer wins it carries exit code 8, "accepted and still
running", which is not a failure and lets a script tell "done" from "admitted and running" without parsing the
result.

The values are DESIGN and are the subject of open question OPEN-TETHER-3: default 5,000 ms, maximum 30,000 ms,
0 for an immediate handle. Tier Solid. The mechanism spans the three surface crates and is measured by the first
clause of GATE-TETHER-12 at M3.

## Scope

In: the `sync_wait_ms` common property and CLI flag; the wait loop in the generic MCP handler and in the CLI;
the deferred envelope; `job.wait` semantics; the remaining-time interval and `poll_after_ms`; the server's
request timeout; the per-surface default as a registry field; the timing test. Out: progress reporting and what
cancellation of a waiting call does (N32a-17); the job engine (N32a-08); the measurement that re-tunes the
default and maximum (N32a-33).

## Technical approach

**The parameter.** Every tool whose registry kind is `run`, and `job_wait`, accepts `sync_wait_ms`: an `int53`
in [0, 30,000], default 5,000 on MCP; 0 asks for an immediate handle. Out of range is `FROB-REF-802` (exit 3).
`read`, `mutate` and `admin` verbs do not accept it (an unknown parameter is 802). On the CLI the default is to
wait to completion with progress events; `--sync-wait-ms <n>` bounds the wait and exits 8. The per-surface
default is the registry field `wait = { cli = "complete", mcp_default_ms = 5000, max_ms = 30000 }`, so the parity
gate knows about the difference and does not report it.

**The wait, numbered (MCP handler; the CLI runs the same loop through the same dispatch interface).**
1. `ctx.checkpoint()?`: a cancellation point before any charge.
2. Resolve the request (names to identifiers, defaults, digest) and read `sync_wait_ms`. Start the deadline
   clock now, at receipt, so the caller's bound includes admission.
3. `dispatch.submit(cx, &req)`: one atomic binding under the idempotency key; replay-safe.
4. Loop on `job.next_frame(cx, &deadline)`: a progress frame is forwarded as progress; an envelope frame is
   returned as the tool result (exit 0 or 2, or an error result carrying a refusal).
5. If the deadline passes first, return `Envelope::deferred(job.handle())`: exit 8, the job handle with its
   progress, an interval for the time remaining, `poll_after_ms`, and `next_actions` naming `job_wait`.

```rust
// DESIGN: the plan's sketch of the loop, kept as the reference for intent.
let wait = req.sync_wait_ms();                               // 0..=30_000, default 5_000
let mut job = self.dispatch.submit(ctx.cx(), &req).await?;  // one atomic binding; replay-safe
let deadline = Deadline::after_ms(wait);
while let Some(frame) = job.next_frame(ctx.cx(), &deadline).await? {
    ctx.checkpoint()?;                                       // a cancelled wait leaves the job running
    match frame {
        Frame::Progress(p) => ctx.report_progress_with_total(p.done, p.total, Some(&p.unit)),
        Frame::Envelope(e) => return e.into_tool_result(),  // exit 0 or 2, or isError with a refusal
    }
}
Envelope::deferred(job.handle()).into_tool_result()          // exit 8
```

**The deferred envelope (the plan's worked example).**

```json
{ "verb": "nemesis.search", "ok": true, "exit": 8,
  "job": { "id": "j:77c0…", "state": "running", "progress": { "done": 512, "total": 4096, "unit": "worlds" },
           "eta_s": 190, "poll_after_ms": 5000, "last_committed": "tick 10000" },
  "next_actions": [ { "command": "job_wait j:77c0…", "why": "Accepted and still running." } ] }
```

`eta_s` carries an interval: the cost estimate's interval scaled by the fraction of work remaining,
(1 − done ÷ total) × [lo, hi], marked `uncalibrated` when the stratum is (DESIGN). `poll_after_ms` is the lower
end of that interval clamped to [1,000, 30,000], or 5,000 when no estimate exists (DESIGN). Progress always has
a denominator.

**`job.wait` (read).** Input: `job`, `sync_wait_ms` (same rules). It attaches to the job and runs steps 4 and 5.
When the job is terminal it returns the job's final envelope, whose `verb` is the verb that created the job, so
an agent can hold a job with a sequence of bounded waits (`job_wait {job, sync_wait_ms: 30000}` repeated). A
terminal job answers immediately on any later wait: the result is durable in the ledger, so a completion that
races the timer can never be lost.

**The server's request timeout.** `frob-mcp` is built with `.request_timeout(40)` seconds. DESIGN reason: the
library's default ceiling of 30 s would coincide with the maximum wait; 10 s of margin covers admission and
serialization.

**Timing budget.** A `run` tool returns within its `sync_wait_ms` plus 500 ms with a result or a handle (the
gate's clause). The 500 ms covers validation, the admission transaction, and serialization; admission latency is
therefore measured and reported per call (`cost.admission_ms`, operational, never in a digest).

Determinism: the timer decides *when* the caller gets an answer, never *what* the job computes: the job's
digests are identical for any `sync_wait_ms` (INV-TETHER-09). Evidence: the deferred envelope carries no
`evidence` block (no result yet); the final one carries the job's claim product.

## Acceptance criteria

- [ ] For every registered `run` tool, with a job that outlives the wait, the call returns exit 8 with a handle within `sync_wait_ms` + 500 ms for waits of 0, 1,000, 5,000 and 30,000 ms (first clause of GATE-TETHER-12; measured maxima recorded).
- [ ] A job that finishes inside the wait returns its result (exit 0 or 2) in the same call, with no handle round trip.
- [ ] `sync_wait_ms` of −1 or 30,001 is refused with `FROB-REF-802`; on a `read` verb the parameter is an unknown parameter (802).
- [ ] `job_wait` on a running job returns exit 8 again within its bound; on a terminal job it returns the final envelope with the original verb name, immediately and repeatably.
- [ ] The job's per-world digests are identical for `sync_wait_ms` 0, 5,000 and 30,000 and for CLI wait-to-completion.
- [ ] The CLI waits to completion by default, prints progress events with `--json`, and exits 8 under `--sync-wait-ms` when the timer wins.
- [ ] The deferred envelope always has `progress.total`, an `eta_s` interval and `poll_after_ms` within [1,000, 30,000].
- [ ] The server's request timeout is 40 s and a 30,000 ms wait is never cut off by it.

## Test plan

### Unit tests (`cargo test -p frob-mcp wait`, `cargo test -p frob-verbs wait`)
- `finishes_inside_wait_returns_result`: a 200 ms job with the default wait → exit 0, no `job` handle required.
- `timer_wins_returns_exit_8`: a 60 s job on the lab clock with wait 5,000 → exit 8 at virtual time 5,000 ms.
- `zero_wait_immediate_handle`: wait 0 → exit 8 after admission only.
- `wait_bounds_802`: −1, 30,001, `"5000"` (a string) → 802.
- `read_verb_rejects_sync_wait`.
- `job_wait_chain`: three waits of 30,000 ms on a 70 s job → 8, 8, then the result.
- `terminal_job_answers_immediately`: a wait on a completed job returns within the margin, twice.
- `race_completion_and_timer` (lab runtime, 10³ seeds): the caller receives either the result or a handle whose next wait returns the result; never neither, never a lost result.
- `eta_interval_scales_with_progress`: estimate 100 to 200 s, 25% done → 75 to 150 s.
- `poll_after_clamped`: lower end 0.2 s → 1,000; 300 s → 30,000; no estimate → 5,000.
- `digests_independent_of_wait`.
- `registry_wait_defaults_declared`: every `run` entry has the `wait` table.

### End-to-end script and logging
`scripts/e2e/bounded_wait.sh`: against a real `frobd` and `frob-mcp` (stdio and loopback HTTP), for a fast verb
and a slow fixture job: call with waits 0, 1,000, 5,000, 30,000; chain `job_wait`; repeat on the CLI with and
without `--sync-wait-ms`. It sources the shared helper and writes `target/e2e-logs/bounded_wait/<utc>.ndjson`
plus a transcript: `cmd` lines with the exact call, exit code and wall time; `metric` lines for return time
minus `sync_wait_ms` (threshold 500 ms), admission latency, the number of round trips to completion; `assert`
lines for exit codes and digest equality across waits; the final envelope's `evidence` block; a `summary` naming
GATE-TETHER-12 (wait clause).

### Known answers and negative controls
- Known answers: the deferred envelope above validates against the schema; a 30,000 ms wait under a 40 s request timeout returns exit 8, not a transport error.
- Negative controls: a server built with the library's default 30 s request timeout (the 30,000 ms wait must be seen to fail as a transport error, and the test must catch it); a wait loop that starts the clock after admission (a slow-admission fixture must exceed the 500 ms margin); a handler that waits to completion ignoring the timer (the timing assertion must fail).
- Determinism lanes: digest equality across waits on `batch-cpu`, twice, in debug and release; on devices once available.

## Considerations

- OPEN-TETHER-3 (the default and maximum of `sync_wait_ms` against measured agent turn time and measured verb latency; owner: Tether lead; blocks GATE-TETHER-13; fail-closed default 5,000 and 30,000) is decided by a later measurement; the values are registry and configuration fields so that changing them is not a code change.
- If the MCP server runs in the socket-fallback configuration, the socket hop is inside the 500 ms margin and must be measured there.
- Clients with their own shorter tool timeout will cancel the call on the wire before the wait elapses; what that does is the next bead's subject (the job keeps running and is recoverable by key).
- A wait is a wall-clock mechanism by nature; it is kept out of every digest and every evidence record.
