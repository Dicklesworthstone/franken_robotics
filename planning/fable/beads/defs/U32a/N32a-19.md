## Background

A caller of FrankenRobotics, human or agent, meets exactly three kinds of failure, and each demands a different
reaction. Mixing them up is how agents waste budgets (resubmitting work that is already running) or loop forever
(retrying a call that can never succeed).

| Class | What happened | CLI | MCP | What the caller does |
|---|---|---|---|---|
| **Domain** | The verb was reached and it refused, stopped on budget, lacked a capability or a device, or met a conflict | Envelope with `ok: false`; exit 3, 4, 5, 6 or 7 | Tool result with `isError: true` whose structured content is the same envelope | Read `refusal.repairs` and `retry` |
| **Protocol** | The request never reached a verb: unknown verb, or arguments that fail the schema | Envelope, exit 3, `FROB-REF-801` or `-802` (the CLI owns its parser) | Unknown tool: a JSON-RPC error from the library before any handler runs (FACT: `InvalidParams`, −32602, "Unknown tool"). Schema failure: the library's input-validation error, mapped to an envelope skeleton with exit 3 by the registration-time error hook | Fix the call; nothing was charged |
| **Transport** | The connection, the client or the daemon died, or a deadline passed before a receipt arrived. The job may be running | Exit 9 if the CLI survives the daemon; otherwise whatever the shell reports | No result. The library may deliver a request-cancelled error (FACT: −32004) or nothing | Never resubmit blindly. Reconnect and call `job.find` with the idempotency key; one job and one charge exist or none do (INV-TETHER-05) |

Inside the Domain class three outcomes must stay distinct: a numerical refusal and a budget stop are refusals; a
physical failure of the robot is a **result with findings** (exit 2), not a refusal.

The one permitted difference between the surfaces is the unknown-verb case in the Protocol row: on MCP the
library answers before generated code runs, so no envelope exists. The parity gate lists it as the only
exemption.

GATE-TETHER-04 (Known answer; earliest M2; TARGET): each of the three failure classes is exercised on both
surfaces; every refusal code maps to exactly one exit code; a killed connection during a wait leaves the job
recoverable by key in 100 of 100 trials. This bead builds the fixture and the script and records the gate at M2
on the surface that exists then. The seed bead for the gate re-runs it at M3 over the full surface, with real
capability tokens.

## Scope

In: the failure-class fixture; the cross-chapter check that every refusal code has exactly one exit code; the
kill harness for connections, clients and the daemon; the recovery-by-key procedure as a script; the M2 gate
record. Out: the envelope and exit table (N32a-03); the mechanisms that produce each refusal; the M3 re-run with
tokens, resources and prompts (BD-299).

## Technical approach

**Fixture (`crates/frob-conformance/fixtures/tether/failure_classes.toml`).** Each row: `class`, `surface`
(`cli`, `mcp-stdio`, `mcp-http`), `stimulus` (a command or a tool call), `expect` (exit, refusal code,
`isError`, JSON-RPC code, or "no result"), `charged` (must be `false` for Protocol rows).

| # | Class | Stimulus | Expected on the CLI | Expected over MCP |
|---|---|---|---|---|
| D1 | Domain, exit 3 | A cursor reused with a changed filter | `FROB-REF-806`, exit 3 | `isError: true`, same envelope |
| D2 | Domain, exit 4 | A run whose estimate's upper end exceeds the remaining budget | `FROB-REF-701`, exit 4, estimate attached | same envelope |
| D3 | Domain, exit 4 | A run on a slow fixture under a low call budget | job ends `failed` with `FROB-REF-702`; no result object | same envelope from `job_wait` |
| D4 | Domain, exit 5 | A registered verb with no handler in this build | `FROB-REF-724`, exit 5 | same envelope |
| D5 | Domain, exit 5 | An admin verb under a synthetic token without the scope | `FROB-REF-720`, exit 5 | same envelope |
| D6 | Domain, exit 6 | A device-tier run with the device made unavailable | a `6xx` refusal, exit 6 | same envelope |
| D7 | Domain, exit 7 | The same idempotency key with a changed payload | `FROB-REF-803`, exit 7, both resolutions shown | same envelope |
| D8 | Domain, three outcomes | One job with a planted numerical refusal on one trial, and one episode in which the robot falls | exit 2: the fall is a finding; the trial refusal is counted in `refused`; neither is a job refusal | same envelope |
| P1 | Protocol | An unknown verb | `FROB-REF-801`, exit 3, envelope | JSON-RPC −32602, no envelope (the exemption) |
| P2 | Protocol | A misspelt parameter | `FROB-REF-802`, exit 3 | envelope skeleton, 802, exit 3, `isError: true` |
| P3 | Protocol | `sync_wait_ms` = 30,001 | `FROB-REF-802`, exit 3 | same as P2 |
| T1 | Transport | The client's connection is closed during a wait | not applicable (the CLI is the client) | no result; job recoverable by key |
| T2 | Transport | The client process is killed during a wait | the shell's signal status | no result; job recoverable by key |
| T3 | Transport | The daemon is killed while the CLI waits | exit 9, one envelope | no result, or −32004 |

**Code-to-exit check.** A test loads the whole refusal registry (all chapters) and asserts that each code has
exactly one `exit`, that the value is in {3, 4, 5, 6, 7, 9}, and that it agrees with the family default where
the family has one (`1xx` to `5xx` → 3; `6xx` → 6; `70x` → 4; `72x`, `73x` → 5; `8xx` → 3 except conflicts → 7
and the chunk conflict → 9; `9xx` → 9). Families without a default must state their exit explicitly.

**Recovery by key, as the caller's procedure (numbered; the script and the generated guide use the same text).**
1. After a call with idempotency key k ends without a result, do not call the verb again.
2. Reconnect. Call `job.find` with (verb, k).
3. If a job is returned: hold it with `job.wait`. If none is returned: the request was never admitted; call the
   verb again with the same key k.
4. Either way exactly one job and one charge exist at the end.

**Kill harness (`frob-conformance::kill`).** For each trial: submit a slow fixture job with key `t-<seed>` and a
5,000 ms wait; at a seeded offset in [0, 5,000) ms after the request is written, apply the kill (close the
socket; signal the client process; or signal the daemon and restart it); run the recovery procedure; assert one
job row for the key, one reserve event, and that the job reaches `complete` with the digests of an uninterrupted
run.

Determinism: kill offsets are seeded; outcomes (one job, one charge) are offset-independent. Evidence: Tested.

## Acceptance criteria

- [ ] GATE-TETHER-04 at M2 (TARGET): every fixture row passes on the CLI, on MCP over stdio and on MCP over loopback HTTP; every refusal code maps to exactly one exit code; a killed connection during a wait leaves the job recoverable by key in 100 of 100 trials. Measured counts are recorded.
- [ ] Protocol rows charge nothing: the session budget and the ledger's job count are unchanged after P1 to P3.
- [ ] For every Domain row the MCP structured content equals the CLI envelope after masking `cost.wall_ms`.
- [ ] D8 shows the three outcomes as three different things: exit 2 with a finding, a `refused` trial count, and (in D3) a budget-stop refusal.
- [ ] T2 and T3 each pass 100 of 100 seeded trials as well as T1; no trial leaves two jobs or two charges.
- [ ] The exemption list of the surfaces has exactly one entry (P1).

## Test plan

### Unit tests (`cargo test -p frob-conformance failure_classes`)
- `fixture_rows_parse_and_cover`: at least one row per class per surface; Domain rows cover exits 3, 4, 5, 6, 7.
- `code_exit_map_total`: over the whole registry: one exit per code; allowed values only.
- `code_exit_map_family_defaults`: `FROB-REF-701` → 4, `-720` → 5, `-801` → 3, `-803` → 7, `-804` → 7, `-809` → 7, `-810` → 9.
- `planted_double_exit_caught`: a synthetic registry overlay giving one code two exits fails.
- `recovery_procedure_no_job_case`: kill before admission → `job.find` returns none → resubmit with the same key → one job.
- `recovery_procedure_job_case`: kill after admission → `job.find` returns the job.
- `mcp_error_hook_skeleton`: an input-validation error from the library is mapped to an envelope with 802 and exit 3.

### End-to-end script and logging
`scripts/e2e/failure_classes.sh --surface cli|mcp-stdio|mcp-http --trials 100 --seed <s>`: starts `frobd` and,
for MCP, `frob-mcp`; runs each fixture row; runs the kill harness for T1, T2 and T3. It sources the shared helper
and writes `target/e2e-logs/failure_classes/<utc>.ndjson` plus a transcript. Every line has `ts`, `script`,
`bead`, `step`, `event`, the exact command or tool call, exit code, wall time, and the envelope's `evidence`
block where an envelope exists; `refusal` lines carry code, exit, `retry` and the first repair; `metric` lines
give rows passed per surface, codes checked, codes with one exit (must equal codes checked), recoveries by key
(threshold 100 of 100 per kill kind), jobs per key (exactly 1), charges per key (exactly 1); on failure the
seed, the kill offset, the first differing field and the ledger copy path. The `summary` names GATE-TETHER-04.

### Known answers and negative controls
- KA-755 (exact): on a fixture of malformed, unknown, over-budget, unscoped and conflicting inputs the codes and exits are 802 → 3, 801 → 3, 701 → 4, 720 → 5, 803 → 7.
- KA-763 (exact), consumed by the transport rows: one job and one charge per key; the retry is a replay.
- Negative controls (each must be caught): a client script that resubmits blindly with a new key after a kill (two jobs must be observed and the assertion must fail); a server build that wraps a domain refusal as a successful tool result (`isError` false); a registry overlay with a code lacking an exit; a CLI build that exits 1 on daemon death.
- Determinism lanes: the fixture twice on one machine; the kill harness with the same seeds gives the same outcome set; both hosts.

## Considerations

- The gate register dates this gate at M2 while its seed bead sits at M3 behind the full MCP surface; recording it here on the M2 surface and again at M3 honours both.
- Before real capability tokens exist, D5 uses a synthetic restricted token; the M3 re-run replaces it and adds `FROB-REF-723` (invalid or widened token) and `-725` (write outside the namespace).
- On transports where the library cannot deliver a cancelled error, "no result" is the expected observation; the harness distinguishes it from a hang by its own deadline.
- A deadline that passes before a receipt arrives is treated exactly as a kill: the procedure is the same.
