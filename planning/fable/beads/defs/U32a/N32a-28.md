## Background

FrankenRobotics holds long work as **jobs** in the daemon's ledger, and gives a caller a job handle (exit code 8
and a `job_wait` tool) when a call's bounded wait elapses. That handle contract works on every client and every
protocol era. The MCP protocol revision 2026-07-28 adds an extension, **Tasks**, with which a client can display
and manage long-running tool calls natively. The plan proposes an optional adapter that also surfaces a `run`
tool's job as an MCP Task, through an application-owned store backed by the job ledger, so that task identifiers
survive a restart of the MCP server.

This is a Frontier mechanism, and the project's rule is that a Frontier mechanism names its ceiling and a
paper-scale pilot with a falsifier before its work is funded.

- **Ceiling, stated before any test:** no compute is saved; the benefit is client-native progress display,
  bounded by the number of long jobs in a session.
- **Pilot:** 20 scripted jobs over the in-memory transport, comparing Task states with the ledger.
- **Falsifier:** one disagreement falsifies it.
- **Kill gate:** KILL-MCPTASKS (trigger: the pilot fails, or the extension changes incompatibly; fallback: job
  handles only). The handle contract remains in every case (ADR-TETHER-06: the Tasks extension is an optional
  adapter over the job ledger, never the primary contract, because the library labels it experimental and
  provisional).

FACT about the library (`fastmcp_rust`, to re-read at the pin): the 2026-07-28 Tasks methods `tasks/get`,
`tasks/update` and `tasks/cancel` run on a process-local in-memory store unless `final_tasks` supplies one, and
task creation needs `task_supervisor`; `#[tool]` accepts a `tasks` attribute; the README calls the extension
experimental and the implementation provisional, and says that 2026-07-28 support "is under implementation and
remains unverified".

## Scope

In: a throwaway prototype of the store adapter, sufficient for the script; the 20-job script; the state mapping
under test; the comparison harness; the pilot record with its verdict. Out: the production adapter (N32a-30,
which depends on this pilot); the decision (N32a-29); anything on a real transport or a real harness.

## Technical approach

**Prototype (kept under `surface/frob-mcp/pilots/tasks/`, not built by default).** A minimal implementation of
the library's task-store interface whose every read is a read of the job ledger: the Task identifier is the job
identifier; the Task's state is computed from the job's state; `tasks/cancel` issues the job engine's cancel.
Nothing is cached in the MCP process, so a restart of the server loses nothing.

**State mapping under test (HYPOTHESIS: the extension's state names are read from the library at the pin; the
table gives the intended correspondence).**

| Job state in the ledger | Task state expected |
|---|---|
| `admitted`, `running`, `preempted` | the extension's non-terminal "working" state |
| `complete` | completed, with the final envelope as the Task's result |
| `failed`, `failed_to_start` | failed, with the refusal envelope |
| `cancelled` | cancelled |
| (submission `refused` at admission) | no Task exists; the tool call returns the refusal directly |

**The script: 20 jobs, each a row with its expected state trace (run on the lab clock, seed 1).**
1 to 4: complete inside the wait; complete after one wait; complete after three waits; complete with findings
(exit 2). 5 to 7: budget stop (`FROB-REF-702`); device fault; failure to start. 8 to 10: cancelled through
`tasks/cancel`; cancelled through `job_cancel`; wait cancelled on the wire with the job left running. 11 and 12:
preempted and resumed once; preempted and resumed three times. 13 and 14: MCP server restarted mid-job (the
identifier must still resolve); daemon restarted mid-job. 15: refused at admission (no Task). 16: the same
idempotency key submitted twice (one job, one Task identifier). 17: key reuse with a changed payload (conflict,
no second Task). 18: `tasks/get` for an unknown identifier. 19: `tasks/cancel` of a terminal Task (no state
change). 20: two clients observing one job.

**Comparison.** After every ledger transition and at 10 sampled instants per job, the harness calls `tasks/get`
and the ledger's read, maps the job state through the table, and compares. A disagreement is any mismatch of
state, any Task for which no job exists, any job with a Task-eligible call and no Task, any identifier that
fails to resolve after a restart, or a result that differs from the job's final envelope.

**Verdict rule (written before the run).** Zero disagreements over the 20 jobs: the pilot passes and the adapter
may be funded. One or more: the pilot fails, the falsifier has fired, and the kill gate is decided on it. If the
library at the pin cannot accept an application-owned store at all, or its Task surface differs from the facts
above in a way that makes the mapping impossible, the pilot is recorded as failed with that reason (this is the
"extension changes incompatibly" trigger).

**Record.** One `[[pilot]]` row of the pilot register `crates/frob-conformance/registry/pilots.toml` (schema
`frob.gauntlet.pilot/1`, owner N38a-09, a dependency; an earlier draft wrote a file of its own under
`registries/pilots/`): `id = "PILOT-TETHER-01"` (DESIGN identifier in the register's mnemonic form),
`mechanism` the MCP Tasks adapter, `tier = "F"`, `bead = "N32a-28"`, `work_package = "WP-26"`, the frozen
protocol (this bead's script and mapping table, with their digest), the falsifier ("one disagreement over the
20 scripted jobs"), the ceiling ("no compute saved; client-native progress display, bounded by the long jobs in a
session", value `none on speed` with that reason), `fallback = { ships = "job handles only", kill_gate =
"KILL-MCPTASKS" }`, the library pin in `tool`. The run appends one `[[pilot.result]]`: the library commit, the
20 rows with their traces as a content-addressed artifact named by its digest, the number of comparisons, the
number of disagreements as `values`, the verdict (`falsifier-rejected` on zero disagreements, `falsifier-holds`
otherwise) and the receipt.

## Acceptance criteria

- [ ] The ceiling and the falsifier are committed in the register row (status `registered`, protocol frozen) before the script is run; the register's validator accepts the row.
- [ ] All 20 scripted jobs run on the in-memory transport and the result's trace artifact lists, per job, the ledger trace, the Task trace and the comparisons made.
- [ ] The verdict is appended as `falsifier-rejected` (pass: zero disagreements) or `falsifier-holds` (fail, with the first disagreement), together with the library commit and its Task state names as read.
- [ ] The harness itself is validated: a planted disagreement (a prototype that caches Task state in memory and is restarted) is detected in row 13.
- [ ] No production code depends on the prototype; the default build does not compile it.

## Test plan

### Unit tests (`cargo test -p frob-mcp --features pilot-tasks pilot`)
- `mapping_table_total`: every job state maps to exactly one expected Task state or to "no Task".
- `script_has_20_rows_with_traces`.
- `comparison_detects_state_mismatch`, `comparison_detects_orphan_task`, `comparison_detects_missing_task`, `comparison_detects_result_difference` (each on a synthetic pair of traces).
- `restart_resolves_identifier`: row 13 with the ledger-backed prototype.
- `in_memory_store_fails_row_13`: the same row with the library's default process-local store loses the Task (this is the reason the adapter must own the store).

### End-to-end script and logging
`scripts/e2e/pilot_mcp_tasks.sh --seed 1` (header: `bead=N32a-28 milestone=M3 labels=tether,mcp,pilot
gates=KILL-MCPTASKS seed=1 needs=cpu,mcp plants=cached-task-state,preempted-as-failed,comparison-off`, each plant
one negative control below and each must be caught): checks the register row's ceiling and falsifier are
committed before the run; builds with the pilot feature; runs the 20 rows on the in-memory transport under the
lab clock, each job submitted under its own key (`mt-<row>`) except rows 16 and 17, which reuse a key on purpose;
appends the result to the register row. It
sources the shared helper and writes `target/e2e-logs/pilot_mcp_tasks/<utc>.ndjson` plus a transcript: `cmd`
lines; one `assert` line per comparison with the job state, the Task state and the expected mapping; `metric`
lines for jobs run (20), comparisons made, disagreements (threshold 0), identifiers resolved after restart; a
`summary` naming KILL-MCPTASKS and the verdict.

### Known answers and negative controls
- Known answer: with the ledger-backed prototype, a Task identifier created before a server restart resolves after it; with the default in-memory store it does not.
- Negative controls: the caching prototype (must fail row 13); a prototype that reports `preempted` as failed (must fail rows 11 and 12); a harness run with the comparison disabled (the record schema requires a non-zero comparison count).
- Determinism lanes: the 20 traces identical twice on one machine with the same seed.

## Considerations

- The pilot measures agreement, not usefulness: whether any harness displays Tasks is part of the harness compatibility experiment, and the ceiling already says the benefit is display only.
- The upstream extension is unverified; a pass here is a pass at one library commit and is re-run when the pin moves.
- A failed pilot costs nothing downstream: the handle contract is complete without Tasks.
- State names are HYPOTHESIS until read at the pin; if the extension has states with no ledger counterpart (for example one that asks the user for input), they are never produced and the record says so.
