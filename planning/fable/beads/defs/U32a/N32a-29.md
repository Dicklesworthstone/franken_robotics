## Background

A kill gate in this project is a decision written before the work starts: a trigger with its measurement, a
milestone, and a fallback named in advance. This bead is the decision for **KILL-MCPTASKS**.

The mechanism at stake is an optional adapter in the MCP server `frob-mcp` that surfaces a long-running job as an
MCP Task (an extension of protocol revision 2026-07-28), through an application-owned store backed by the
daemon's job ledger. Its ceiling was stated before any test: no compute is saved; the benefit is client-native
progress display, bounded by the number of long jobs in a session. The decision of record (ADR-TETHER-06) is
that the extension is never the primary contract: every client, on every protocol era, can hold a job with the
handle contract (a call whose bounded wait elapses returns exit code 8 and a job handle with progress, an
interval for the time remaining and `poll_after_ms`; `job_wait` continues the wait). The upstream library labels
its Tasks support experimental and provisional (FACT, read 2026-11-21, to re-read at the pin: the 2026-07-28
Tasks methods `tasks/get`, `tasks/update` and `tasks/cancel` run on a process-local in-memory store unless an
application store is supplied through `final_tasks`, and task creation needs a `task_supervisor`). The gate
exists to stop a provisional protocol feature from becoming a second job model with its own states and failure
modes.

## Scope

In: the gate's definition as registered; the decision function; reading the pilot, deciding, recording, the
standing re-read whenever the library pin moves, and the consequences on each branch. Out: the pilot, its 20
scripted jobs and its state mapping (N32a-28); the adapter (N32a-30, which exists only if this gate does not
fire); the register row's format and its entry before any measurement (N32b-25); the bounded wait and job
handles, which exist on both branches.

## Technical approach

**The gate.**

| Item | Value |
|---|---|
| Trigger | The pilot fails (one disagreement between Task states and ledger states over 20 scripted jobs on the in-memory transport); or the extension changes incompatibly |
| Milestone | M3; and a standing re-read at every move of the `fastmcp_rust` pin thereafter |
| Measurement | The pilot record: comparisons made, disagreements, identifiers resolved after a server restart, the library commit and the Task state names as read. The 20 scripted jobs cover: completes inside the wait; completes after it; fails; is cancelled by `job.cancel`; is cancelled through the Task; survives a restart of `frob-mcp` mid-run; is refused at admission (no Task is created; the call returns the refusal envelope); stops on budget. The sequence of Task states the client observes is compared with the job's ledger states under the pilot's fixed mapping (`admitted`, `running`, `preempted` → working, with progress numerator, denominator and unit; `complete` → completed, result = the job's envelope; `failed`, `failed_to_start` → failed, with the envelope's refusal; `cancelled` → cancelled, with the last committed tick); the adapter defines no state of its own. Incompatibility: after a pin advance of the library, the adapter fails to compile or the pilot fails |
| Fallback | Job handles only |
| Fail-closed default until decided | Job handles only |

**Decision function** (DESIGN; pure; tested code in `crates/frob-conformance`).

```
decide(pilot: {jobs: u32, comparisons: u32, disagreements: u32, restart_survived: bool} | not-run,
       extension_incompatible: bool)
  -> does-not-fire | fires | undecided
```

- `extension_incompatible`: fires (at any time, including after a "does not fire").
- `pilot = not-run`, `jobs < 20` or `comparisons = 0`: `undecided` (an invalid or incomplete record decides nothing).
- `disagreements ≥ 1` or `restart_survived = false`: fires, subject to the single repair of step 2 (a).
- Otherwise: does not fire.

**Decision procedure, numbered.**
1. Read the pilot record: the row `PILOT-TETHER-01` of the pilot register
   `crates/frob-conformance/registry/pilots.toml` (N32a-28, schema `frob.gauntlet.pilot/1`) and its appended
   result. Confirm the pilot was registered before it ran and that its negative control was caught (an adapter on
   the library's default in-memory store loses its tasks on restart, so the restart case must fail there).
   Verdict `falsifier-rejected` (pass) with zero disagreements and a non-zero comparison count: not fired.
   Verdict `falsifier-holds` (fail): fired.
2. Classify a failure for the record: (a) a mapping defect in the prototype (repairable here: one repair and one
   re-run are allowed, since the falsifier is about the mechanism, not about a typing error in the prototype;
   DESIGN); (b) the library cannot host an application-owned store, or loses identifiers across a restart
   despite one; (c) the extension's surface differs incompatibly from what the design assumed. For (b) and (c)
   the gate fires without a re-run and an upstream work item is opened in the library's repository if the
   defect is the library's.
3. Write the kill-gate ADR `docs/adr/ADR-KILL-MCPTASKS-M3.md` (every decision record lives in `docs/adr/`, named
   by gate and milestone, with N40-03's required fields; a later re-read at a pin move that fires writes the
   record of its own milestone) with the record's hash, the 20 jobs' outcomes, the
   disagreement count, the library commit, the classification and the branch. The ADR and the register row are
   written by a session that did not build the adapter or its prototype.
4. Standing re-read: the compatibility train re-runs the pilot script whenever the library pin moves. A later
   failure fires the gate then (the "extension changes incompatibly" clause), and the adapter's feature is
   turned off in the same change. A killed adapter is then removed from the tree with its cargo feature, not left
   dormant; if the extension stabilizes later with different semantics, re-opening is a new decision record.

**What changes downstream.**

| Branch | Consequence |
|---|---|
| Not fired | The adapter bead is funded, behind the cargo feature `mcp-tasks`, off by default until the MCP surface gate (GATE-TETHER-12) has passed with it on. `run` tools may surface their job as a Task, and advertise task support, only for clients that negotiated the extension. The handle contract is unchanged, remains what every gate measures and is what the documentation teaches first |
| Fired | The adapter is not built; if it was, its cargo feature is disabled in the same change and its code and feature are then removed from the tree, not left dormant. `frob-mcp` does not advertise the Tasks capability to any client and registers no task supervisor. `frob capabilities` reports the capability `killed` with the fallback "job handles only". Nothing else changes: `sync_wait_ms`, exit 8, `job_wait`, `job_cancel`, progress notifications and resource subscriptions on `frob://job/{id}` are complete without it and independent of Tasks. The MCP surface gate has no Tasks clause, so it is unaffected; its record states which branch was in force when it was measured. The generated guide omits any mention of Tasks |

- [ ] The kill-gate register row carries the decision, date and commit.
- [ ] The compatibility train's gate list includes the pilot script, so that a pin move re-reads the gate.
- [ ] If fired: `frob-mcp` built by default advertises no Tasks capability (checked on the wire), and the handle-contract tests pass unchanged.
- [ ] If not fired: the adapter bead is unblocked and names this ADR; the default build has the feature off until the MCP surface gate has passed with it on.
- [ ] The decision function is tested code and, applied to the pilot's stored record, returns the recorded branch.
- [ ] If fired: no served tool advertises task support (checked on the served tool list for a client that negotiates the extension), `frob capabilities` reports the capability `killed`, and once the removal has landed the feature does not exist in `Cargo.toml`.

- `capability_not_advertised_when_fired`: the initialize result of a default build contains no Tasks capability.

### Known answers and negative controls
- Known answer: the six rows of the decision table.
- Known answer: the handle contract on both branches: a job that outlives the wait returns exit 8 with a denominator in its progress, and `job_wait` later returns the result.
- Negative control: the adapter on the library's in-memory store, restarted mid-job: the Task is gone while the ledger job runs on; the pilot must count a disagreement.
- Negative control: a mapping that shows a preempted job as failed; the pilot must count a disagreement.
- Negative control: a decision recorded `not fired` from a pilot of 12 jobs is rejected.
- Negative controls: a record with zero comparisons labelled `pass` (must be rejected as invalid); an ADR `not fired` citing a failing record (the consistency test must fail); a fired branch in which the server still advertises the capability (the wire check must fail).

## Considerations

- The gate is cheap to fire and cheap to reverse: the adapter is behind a cargo feature and the fallback is the system's ordinary behaviour.
- One repair of the prototype before firing is DESIGN; the plan's falsifier ("one disagreement falsifies it") is applied strictly to the repaired prototype.
- Whether any harness in use displays Tasks is a separate observation of the harness compatibility experiment; if none does, the adapter may be left unbuilt even when the gate does not fire, and the ADR says so.
- The value at stake is small by the ceiling's own statement; firing costs a display convenience and nothing else.
- Wire cancellation of a Task follows the surface's rule for waits: cancelling the wait is not cancelling the job, unless the call asked for that; cancelling a Task is defined as `job.cancel` and drains (INV-TETHER-11). The pilot covers both.
