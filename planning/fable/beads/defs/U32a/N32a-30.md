## Background

This bead exists only if the kill gate KILL-MCPTASKS does not fire: its pilot (20 scripted jobs on the in-memory
transport, Task states compared with ledger states, one disagreement falsifies) must be on record as passed.

FrankenRobotics holds long work as jobs in the daemon's ledger. The MCP protocol revision 2026-07-28 adds an
extension, Tasks, by which a client can show and manage long-running tool calls in its own interface. Where a
client negotiates that extension, a `run` tool may also surface its job as an MCP Task through an
**application-owned store backed by the job ledger**, so that task identifiers survive a restart of `frob-mcp`.

Tier Frontier. Ceiling, stated before any test: no compute is saved; the benefit is client-native progress
display, bounded by the number of long jobs in a session. Decision ADR-TETHER-06: the extension is an optional
adapter over the job ledger, never the primary contract, because the library labels it experimental and
provisional and the handle contract (exit code 8, `job_wait`, `job_cancel`) works on every client and protocol
era. Alternative excluded: letting the library's default store hold Tasks. FACT: without `final_tasks` the task
methods run on a process-local in-memory store, so a restart of the server would orphan every Task while the
jobs kept running in the daemon.

## Scope

In: the store, the supervisor wiring, the state mapping, cancellation through the extension, capability
negotiation, the cargo feature and its default, conformance on real transports. Out: the handle contract and the
wait (N32a-16); the job ledger (N32a-08); the pilot and the decision.

## Technical approach

**Feature.** Cargo feature `mcp-tasks` on `surface/frob-mcp`, off by default until the kill-gate ADR says `not
fired` and the MCP surface gate (GATE-TETHER-12) has passed with the feature on; then on by default. With the
feature off, no Tasks capability is advertised and no supervisor is registered. If the kill gate fires later (an
incompatible change found when the library pin moves), the feature is turned off in the same change and the
adapter's code and feature are then removed from the tree, not left dormant.

**Store (the only state is the ledger).**

```rust
// DESIGN: intent, not signatures; the trait is the library's task-store interface as read at the pin.
struct LedgerTaskStore { dispatch: Arc<dyn Dispatch> }   // no cache, no map, no clock
// get(task_id)    -> read the job by identifier; map its state; attach progress and, if terminal, the envelope
// cancel(task_id) -> the job engine's cancel (same as job.cancel), after the scope check
// update(task_id) -> refused: a job's state is changed only by the job engine
// create(call)    -> performed by VerbTool after admission: task_id = job id; nothing else is stored
```

**Identifier.** The Task identifier is the job identifier (`j:77c0…`). It is created by the same admission
transaction that binds the idempotency key, so the idempotency properties carry over: one key, one job, one
Task; a replayed submission returns the same Task.

**State mapping** (the extension's state names are those of the library at the pin).

| Job state | Task state | Task content |
|---|---|---|
| `admitted`, `running`, `preempted` | non-terminal ("working") | progress `{done, total, unit}`; `poll_after_ms` as the suggested poll interval |
| `complete` | completed | the job's final envelope as structured content |
| `failed`, `failed_to_start` | failed | the refusal envelope |
| `cancelled` | cancelled | the cancellation receipt |

A submission refused at admission creates no Task; the tool call returns the refusal as usual.

**Tool behaviour when the client negotiated Tasks.** A `run` tool call still honours `sync_wait_ms`. If the job
finishes inside the wait, the result is returned directly and no Task is surfaced (the client never needs it).
If the timer wins, the call returns the deferred envelope (exit 8) exactly as without the extension, and in
addition the response carries the Task reference in the form the extension defines, so a Tasks-aware client
tracks it natively while any client can still call `job_wait`. Both routes read the same ledger row.

**Cancellation.** `tasks/cancel` requires the scope `job:cancel` (without it: `FROB-REF-720`, exit 5, `required:
"job:cancel"`, carried in the extension's error form, and nothing is cancelled) and performs a job cancel: the daemon drains at
the kernel-batch boundary and the receipt names the last committed tick per world. It is a cancel of the job,
unlike wire cancellation of a waiting call, which only ends the wait.

**Restart.** Because the store holds nothing, restarting `frob-mcp` loses nothing: `tasks/get` for a previously
issued identifier reads the ledger. Restarting the daemon follows the job engine's recovery; the Task shows the
recovered state.

**Authorization and isolation.** A Task is visible to the principal that owns the job (and to holders of a
scope that can read that namespace's jobs); `tasks/get` for another principal's job is answered as unknown.

Determinism: Task states are a pure function of ledger state. Evidence: the Task result is the job's envelope,
with its claim product.

## Acceptance criteria

- [ ] The pilot's 20 scripted jobs pass against the production adapter (not the prototype) on the in-memory transport, on stdio and on loopback HTTP: zero disagreements between Task states and ledger states.
- [ ] A Task identifier issued before a restart of `frob-mcp`, and before a restart of `frobd`, resolves afterwards to the correct state.
- [ ] With the feature off, the handshake advertises no Tasks capability and every handle-contract test passes; with it on, every handle-contract test still passes unchanged.
- [ ] One idempotency key yields one job and one Task identifier under 1,000 seeded races.
- [ ] `tasks/cancel` without `job:cancel` is refused with `FROB-REF-720` and the job keeps running; with it, the job ends `cancelled` with a receipt naming the last committed tick per world.
- [ ] `tasks/update` is refused and changes nothing.
- [ ] A principal cannot observe another principal's Task.
- [ ] The adapter holds no state: a test asserts the store type has no interior mutability and no collection fields.

## Test plan

### Unit tests (`cargo test -p frob-mcp --features mcp-tasks tasks`)
- `task_id_is_job_id`.
- `state_mapping_table`: each job state → the expected Task state.
- `finished_inside_wait_surfaces_no_task`.
- `timer_wins_returns_exit_8_and_task_reference`.
- `get_after_server_restart`; `get_after_daemon_restart`.
- `cancel_requires_scope`; `cancel_drains_and_names_ticks`.
- `update_refused`.
- `replay_same_task_id`; `conflict_no_second_task`.
- `other_principal_sees_unknown`.
- `store_is_stateless` (a compile-time and reflection-style test on the type's fields).
- `feature_off_no_capability`.

### End-to-end script and logging
`scripts/e2e/mcp_tasks_adapter.sh` (header: `bead=N32a-30 milestone=M3 labels=tether,mcp,tasks
gates=KILL-MCPTASKS seed=30 needs=cpu,frobd,mcp plants=cached-state,cancel-ends-wait-only,task-before-admission`,
each plant one negative control below and each must be caught): builds `frob-mcp` with and without the feature;
with it, runs the 20-row script over stdio and loopback HTTP against a real `frobd` with the library's client
negotiating the extension, each job under a key naming its transport and row (`ta-<transport>-<row>`; rows 16 and
17 reuse a key on purpose), so that the second transport runs its own jobs rather than receiving the first one's
stored receipts;
restarts the server and the daemon mid-run; runs the handle-contract smoke both ways. It sources the shared
helper and writes `target/e2e-logs/mcp_tasks_adapter/<utc>.ndjson` plus wire transcripts: `cmd` lines with exit
code and wall time; one `assert` line per comparison (job state, Task state, expected); `metric` lines for
comparisons, disagreements (threshold 0), identifiers resolved after restart (all), races and Tasks per key
(1); the final envelopes' `evidence` blocks; a `summary` naming KILL-MCPTASKS (standing re-read).

### Known answers and negative controls
- Known answer: Task state equals mapped job state at every sampled instant; the identifier survives both restarts.
- Negative controls (each must be caught): an adapter that caches the last state in memory (stale after a daemon-side transition during a server restart); an adapter whose `tasks/cancel` only ends the wait (the job is still running and the receipt is missing); an adapter that creates a Task before admission commits (a refused submission leaves an orphan Task).
- Determinism lanes: the 20 traces identical twice on one machine per transport.

## Considerations

- The extension is unverified upstream; the pilot script is part of the compatibility train, and a later incompatible change turns the feature off under the kill gate without touching anything else.
- No harness may be required to use Tasks; the generated guide describes the handle contract first and mentions Tasks as an optional display aid.
- If no harness in use displays Tasks, this adapter has no user; the decision record may leave it unbuilt.
- Resource subscriptions on `frob://job/{id}` already give push updates to clients that support them; Tasks and subscriptions must agree because both read the ledger.
