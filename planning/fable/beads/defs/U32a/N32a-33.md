## Background

Every long-running tool of the FrankenRobotics MCP surface takes a **bounded synchronous wait**, `sync_wait_ms`:
the call blocks for at most that long and then returns either the result or a job handle (exit code 8), which
the agent holds with `job_wait`. The design values were chosen without data: default 5,000 ms, maximum 30,000
ms, 0 for an immediate handle. The reasoning behind having a wait at all (decision ADR-TETHER-04) rests on two
claims: most studio verbs finish inside the wait (TARGET: `design check` under 2 s, `control synth` under 5 s),
and an agent turn costs 30 to 120 s of thinking (HYPOTHESIS), so an avoided poll saves more than the compute it
waits for.

Open question **OPEN-TETHER-3** records that both the values and the hypothesis need measuring: *the default and
maximum of `sync_wait_ms` against measured agent turn time and measured verb latency.* Owner: the Tether lead.
It blocks GATE-TETHER-13, the mission-session gate at M4, which is also where the agent-turn hypothesis is to be
measured. Fail-closed default until decided: **5,000 and 30,000**.

This is an experiment bead. It measures two distributions from sessions that already exist, evaluates a small
pre-registered grid of (default, maximum) pairs against them, and records a decision. The values are registry
and configuration fields (`wait = { mcp_default_ms, max_ms }` on each `run` entry and the server's request
timeout), so adopting a change is not a code change.

## Scope

In: the two measurements; the cost model of a wait policy; the grid; the constraint from harness tool timeouts;
the decision rule; the decision record; the configuration change, if any, including the server's request
timeout. Out: the wait mechanism (N32a-16); the harness compatibility matrix (N32a-12, consumed); the gate
(BD-373).

## Technical approach

**Measurements (from session transcripts and the job ledger; no new runs are needed).**
- *Agent poll-turn time* T_poll: for every exit-8 answer in a recorded MCP session, the wall time from the moment
  the deferred envelope was sent to the moment the same session's next call arrived. Reported per harness
  configuration: median, quartiles, 95th percentile.
- *Agent decision-turn time* T_turn: the same for answers that were results. This is the quantity the
  hypothesis "30 to 120 s" is about; its median and quartiles are reported and the hypothesis is marked
  supported or not.
- *Verb latency* D: for every `run` call, the wall time from admission to the job's terminal state, per verb and
  tier, from the ledger. Reported as a distribution per verb family, with the fraction finishing under 2, 5, 10,
  15, 30 and 60 s.
- *Harness tool timeout* H: per harness configuration, the client-side timeout after which the harness abandons
  a tool call (from the compatibility matrix, measured by a call that never answers).

Sufficiency: at least 500 `run` calls and at least 50 exit-8 answers, from at least 2 harness configurations
(DESIGN thresholds). Below that the defaults hold and the record says `insufficient data`.

**Cost model of a wait policy (w_default, w_max).** For a call whose job lasts D, under a policy in which the
first call waits w_default and each `job_wait` waits w_max (the agent guide's advice):

    rounds(D) = 0 if D ≤ w_default, else ⌈(D − w_default) ÷ w_max⌉
    time_to_result(D) = D + rounds(D) × T_poll        (the agent adds a poll turn per extra round)
    blocked_time(D) = min(D, w_default)               (time the first call holds the agent's turn)

The objective is the mean of time_to_result over the recorded distribution of D, with T_poll at its measured
median for the harness. A second figure, reported and not optimized, is the mean blocked_time, because a long
default wait holds an agent that could have done something else in parallel.

**Grid (registered before the data is read).** w_default ∈ {2,000, 5,000, 10,000, 15,000} ms; w_max ∈ {30,000,
60,000} ms: eight pairs.

**Constraint.** w_max + 10,000 ms ≤ min over harness configurations of H (the server's request timeout is
w_max + 10 s of margin for admission and serialization, and no harness in use may abandon the call first). A
pair that violates it for a harness in use is excluded for that harness; if every w_max does, the default for
that harness is lowered to the largest admissible value and the record says so.

**Decision rule.** Adopt the admissible pair with the lowest mean time_to_result, but only if its improvement
over (5,000, 30,000) is at least 5% and a bootstrap 95% lower bound of the improvement (10,000 resamples over
sessions) is above zero. Otherwise keep the defaults. A change of w_max changes the server's request timeout to
w_max + 10 s in the same configuration commit.

**Record (`docs/adr/tether/OPEN-TETHER-3.md`).** The four measurements, the eight results, the chosen pair, the
bootstrap bound, the verdict on the 30-to-120 s hypothesis, and the commit that changes the registry field (or a
statement that the defaults stand).

Determinism: the analysis is a pure function of the transcripts and ledger extracts; evidence class
`Estimated`, stated in the record.

## Acceptance criteria

- [ ] The registration (measurements, cost model, grid, constraint, rule) is committed before the extracts are read; the script checks commit order.
- [ ] The data meets the sufficiency rule, or the record says `insufficient data` and confirms 5,000 and 30,000.
- [ ] The record reports T_poll and T_turn (median, quartiles, 95th percentile) per harness configuration, the latency distribution per verb family, and H per harness.
- [ ] The hypothesis that an agent turn costs 30 to 120 s is marked supported, or not, from the measured T_turn.
- [ ] All eight pairs have a mean time_to_result and a mean blocked_time; inadmissible pairs are marked with the violated timeout.
- [ ] The decision follows the rule; if a pair is adopted, the registry's `wait` fields and the server's request timeout are changed together and the parity harness still reports no undeclared difference.
- [ ] The analysis recovers a planted optimum on a synthetic data set (durations concentrated at 8 s with T_poll = 60 s → a 10,000 ms default must win over 5,000 ms).

## Test plan

### Unit tests (`cargo test -p frob-conformance open_tether_3`)
- `rounds_formula`: (D, w_default, w_max) → rounds: (3 s, 5 s, 30 s) → 0; (5 s, 5 s, 30 s) → 0; (6 s, 5 s, 30 s) → 1; (35 s, 5 s, 30 s) → 1; (36 s, 5 s, 30 s) → 2.
- `time_to_result_example`: D = 8 s, policy (5, 30), T_poll = 60 s → 68 s; policy (10, 30) → 8 s.
- `constraint_excludes`: H = 60 s → w_max = 60 s is inadmissible (70 s > 60 s); w_max = 30 s is admissible.
- `rule_keeps_defaults_below_5_percent`.
- `rule_requires_positive_bootstrap_bound`.
- `planted_optimum_recovered` (synthetic, labelled `synthetic`).
- `poll_turn_extraction`: from a synthetic transcript with an exit 8 at t = 100 s and the next call at t = 147 s → T_poll = 47 s.
- `sufficiency_rule`.

### End-to-end script and logging
`scripts/e2e/open_tether_3.sh --sessions <dir> --seed 1`: checks the registration's commit order; extracts the
measurements from the transcripts and the ledger; evaluates the grid; applies the rule; writes the record and,
if a change is adopted, a patch to the registry defaults. It sources the shared helper and writes
`target/e2e-logs/open_tether_3/<utc>.ndjson` plus a transcript: `cmd` lines; `metric` lines for T_poll and
T_turn quantiles per harness, the fraction of `run` calls finishing under each threshold, H per harness, and per
grid pair the mean time_to_result, mean blocked_time, rounds per call and admissibility; `assert` lines for
sufficiency and the planted-optimum check; a `summary` naming OPEN-TETHER-3 and GATE-TETHER-13 (precondition).
Session content is referenced by digest only.

### Known answers and negative controls
- Known answers: the rounds and time-to-result examples above.
- Negative controls: a grid edited after the extracts were read (the registration digest must not match); an adopted w_max that exceeds a harness timeout minus 10 s (the constraint check must reject it); T_poll computed across sessions instead of within one (the extraction test must fail).
- Determinism lanes: the analysis identical twice on one machine with the same seed.

## Considerations

- The cost model assumes an agent polls promptly with the maximum wait; agents that do other work between polls make the wait matter less, which only strengthens the case for keeping the defaults.
- A longer default helps when many jobs end just after 5 s and hurts when it holds turns for jobs that will take minutes; that is why blocked time is reported beside the objective.
- The per-surface default is a registry field so the parity gate treats the CLI's wait-to-completion and MCP's bounded wait as a declared difference; this bead must keep it declared.
- If the measured agent turn is far below 30 s for the harnesses in use, the premise of the bounded wait weakens; the mechanism stays (it is harmless), and the record says the avoided-poll saving is smaller than assumed.
