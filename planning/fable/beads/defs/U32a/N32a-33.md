## Background

Every long-running tool of the FrankenRobotics MCP surface takes a **bounded synchronous wait**, `sync_wait_ms`:
the call blocks for at most that long and then returns either the result or a job handle (exit code 8), which
the agent holds with `job_wait`. In detail: the handler submits the job under its idempotency key, then waits on
the job's completion against a timer; if the job finishes, the envelope carries the result (exit 0 or 2); if the
timer wins, the envelope carries exit 8 and a job handle with progress, an interval for the time remaining and
`poll_after_ms`, and `next_actions` names `job_wait`, which takes the same parameter. The design values were
chosen without data: default 5,000 ms, maximum 30,000 ms, 0 for an immediate handle; a value out of range is
refused as a schema failure (`FROB-REF-802`). The server's request timeout is 40 s, so that 10 s of margin cover
admission and serialization. On the command line the default is to wait to completion. The reasoning behind
having a wait at all (decision ADR-TETHER-04) rests on two
claims: most studio verbs finish inside the wait (TARGET: `design check` under 2 s, `control synth` under 5 s),
and an agent turn costs 30 to 120 s of thinking (HYPOTHESIS), so an avoided poll saves more than the compute it
waits for.

Open question **OPEN-TETHER-3** records that both the values and the hypothesis need measuring: *the default and
maximum of `sync_wait_ms` against measured agent turn time and measured verb latency.* Owner: the Tether lead.
It blocks GATE-TETHER-13, the mission-session gate at M4, which is also where the agent-turn hypothesis is to be
measured. Fail-closed default until decided: **5,000 and 30,000**.

This is an experiment bead. It measures two distributions from sessions that already exist, evaluates a small
pre-registered grid of (default, maximum) pairs against them, and records a decision. The values are registry
and configuration fields (`wait = { cli = "to-completion", mcp_ms, mcp_max_ms }` on each `run` entry, the
spelling of N32a-02, and the server's request timeout), so adopting a new default is not a code change. A new
maximum also moves two constants in the same commit: the upper bound of N32a-02's lint `RL-09` (`mcp_max_ms ≤
30000`, the fail-closed maximum) and the request timeout `frob-mcp` is built with (N32a-16's `.request_timeout(40)`).

## Scope

In: the measurements and the records they come from; the cost model of a wait policy in two forms (a closed form

## Technical approach

**Measurements (from session transcripts and the job ledger; no new runs are needed).**
- *Agent poll-turn time* T_poll: for every exit-8 answer in a recorded MCP session, the wall time from the moment
  the deferred envelope was sent to the moment the same session's next call arrived. Reported per harness
  configuration: median, quartiles, 95th percentile.
- *Agent decision-turn time* T_turn: the same for answers that were results. This is the quantity the
  hypothesis "30 to 120 s" is about; its median and quartiles are reported and the hypothesis is marked
  supported or not.
- *Verb latency* D: for every `run` call, the wall time from admission to the job's terminal state, per verb and
  tier, from the ledger. Reported as a distribution per verb family, with the fraction finishing within 1, 2, 5,
  10, 15, 20, 30 and 60 s (the waits of the grid below).
- *Harness tool timeout* H: per harness configuration, the client-side timeout after which the harness abandons
  a tool call (from the compatibility matrix and client table of N32a-12, measured by a call that never answers).

Turn times are intervals from the delivery of one call's result to the arrival of the next call, never call to
call (which would include the previous call's latency), as recorded by the daemon's request log; this is
wall-clock operational data and never enters a result. Sources: the transcripts of the fresh-agent runs of the
studio gate and at least 20 further recorded sessions per harness, on the workloads of those sessions (not
synthetic). The distributions are also reported at the 5th, 25th, 50th, 75th and 95th percentiles per harness
and overall, and latency per `run` verb and stratum (verb, tier, device family, shape class) as the share
finishing within the same eight thresholds.

Sufficiency: at least 500 `run` calls and at least 50 exit-8 answers, from at least 2 harness configurations
(DESIGN thresholds). Below that the defaults hold and the record says `insufficient data`.

**Cost model of a wait policy (w_default, w_max).** For a call whose job lasts D, under a policy in which the
first call waits w_default and each `job_wait` waits w_max (the agent guide's advice):

    rounds(D) = 0 if D ≤ w_default, else ⌈(D − w_default) ÷ w_max⌉
    time_to_result(D) = D + rounds(D) × T_poll        (the agent adds a poll turn per extra round)
    blocked_time(D) = min(D, w_default)               (time the first call holds the agent's turn)

The closed form is an upper bound that is easy to audit: it charges a whole poll turn per extra round even when
the job ends while the agent is thinking.

**Event simulation of one call (the faithful model; it decides).** Policy (w_default, w_max). For a call with
latency D and independent turn times T₁, T₂, … drawn from the measured distribution:
- If D ≤ w_default: wall time = D; turns = 1.
- Else the handle returns at w_default; the agent thinks T₁ and calls `job_wait` at time w_default + T₁. If the
  job is already done the call returns at once; otherwise it waits up to w_max, and so on. Wall time is the
  instant the result is delivered; turns counts the calls.

Outputs per policy, averaged over the empirical (verb mix, D, T): mean wall time to result, mean turns per call,
and mean idle agent time (time the agent is blocked in a wait with nothing to decide). The first favours long
waits when T is large; the third penalizes long waits when an agent could have done something else, which
matters only for harnesses that issue parallel tool calls (recorded per harness). Consistency of the two models:
for one call with a constant turn time T, the simulated wall time never exceeds the closed form's
time_to_result with T_poll = T (the result is delivered at D or at the end of the think in which the job ended,
so at most D + T). The check is per call, not on means, because the closed form is evaluated at the median
T_poll and the simulation draws T from its whole distribution.

The objective is the simulated mean wall time to result over the recorded distribution of D and T for the
harness; the closed-form mean is reported beside it. A second figure, reported and not optimized, is the mean
blocked_time (and the simulation's idle time), because a long default wait holds an agent that could have done
something else in parallel.

**Grid (registered before the data is read).** w_default ∈ {0, 1,000, 2,000, 5,000, 10,000, 15,000, 20,000,
30,000} ms; w_max ∈ {30,000, 60,000} ms: sixteen pairs.

**Constraint.** w_max + 10,000 ms ≤ min over harness configurations of H (the server's request timeout is
w_max + 10 s of margin for admission and serialization, and no harness in use may abandon the call first). A
pair that violates it for a harness in use is excluded for that harness; if every w_max does, the default for
that harness is lowered to the largest admissible value and the record says so. The per-harness cap is
1,000 × (H − 10 s) ms, rounded down to a whole second and never below 5,000 ms; it is written in that harness's
row of the client table, and the global maximum stays at the largest value every listed harness accepts.

**Decision rule.**
1. Adopt the admissible pair with the lowest objective, but only if its improvement over (5,000, 30,000) is at
   least 5% and a bootstrap 95% lower bound of the improvement (10,000 resamples over sessions) is above zero.
   Otherwise keep the defaults. Among admissible pairs within 2% of the minimum, choose the one with the smallest
   default (shorter waits keep the agent responsive at no measurable cost).
2. A change of w_max changes, in the same commit, the `wait` fields, the bound of `RL-09` to w_max and the server's
   request timeout to w_max + 10 s; the request timeout is never less than the maximum plus 10 s, and `RL-09`
   never admits a maximum the request timeout does not cover.
3. The choice is one default per surface (one number for MCP). A per-verb override is allowed only where a verb's
   median latency exceeds the default by a factor of four or more; its registry entry then sets its own
   `wait.mcp_ms` (and the parity harness reads it as that entry's declared default).
4. Cheap turns: if the measured median T_turn is below 5 s, the hypothesis behind the bounded wait fails. The
   default is then set to the 50th percentile of D across calls (rounded up to a whole second, capped by the
   maximum), whatever rule 1 says, and the finding is attached to the inputs of the KILL-SOLVE decision
   (N32a-32), whose benefit depends on the same quantity.

**Recording.** The chosen default and maximum go into the registry's per-surface `wait` fields through the
generator (so the parity gate knows about them, and the schema bound of the `FROB-REF-802` check follows). Until
the decision record exists the values are 5,000 and 30,000.

**Confirmation run.** The studio and mission session scripts (N32b-15, N32b-16) are re-run over MCP with the
chosen values and with the old ones, by a scripted client whose think time is drawn from the measured T, on an
idle daemon; mean turns per session and wall time are compared. This is a smoke check that the change does what
the model predicted, not a new gate.

**Record (`docs/adr/ADR-OPEN-TETHER-3-M4.md`, the directory and naming N40-03 gives every decision record,
including one that records an open question's default).** The four measurements, the sixteen results (closed form and
simulation), the chosen pair, the bootstrap bound, the verdict on the 30-to-120 s hypothesis, any per-harness cap
and per-verb override, the confirmation comparison, and the commit that changes the registry field (or a
statement that the defaults stand).

Determinism: the analysis is a pure function of the transcripts and ledger extracts; evidence class
`Estimated`, stated in the record.

**The harness.** Extraction, the grid with both models, the rule and the record are one example of the
conformance crate over the module the unit tests call (the crate ships examples, not a command of its own):
`crates/frob-conformance/examples/open_tether_3.rs`, run as `cargo run -p frob-conformance --example open_tether_3
-- <extract | grid | decide | record> --sessions <dir> --state-root <path> --seed <s>`.

## Acceptance criteria

- [ ] The registration (measurements, cost model, grid, constraint, rule) is committed before the extracts are read; the script checks commit order.
- [ ] The data meets the sufficiency rule, or the record says `insufficient data` and confirms 5,000 and 30,000.
- [ ] The record reports T_poll and T_turn (median, quartiles, 95th percentile) per harness configuration, the latency distribution per verb family, and H per harness.
- [ ] The hypothesis that an agent turn costs 30 to 120 s is marked supported, or not, from the measured T_turn.
- [ ] All sixteen pairs have a closed-form mean time_to_result, a simulated mean wall time, mean turns per call and a mean blocked_time; inadmissible pairs are marked with the violated timeout; for a constant turn time no simulated call exceeds its closed-form value.
- [ ] The simulation and the decision rule are tested code; the recorded default and maximum equal the rule's output on the recorded data.
- [ ] If a pair is adopted, `frob schema sim.run --in --json` shows the new bound and a `sync_wait_ms` above the new maximum is refused with `FROB-REF-802`; the server's request timeout is at least the maximum plus 10 s.
- [ ] OPEN-TETHER-3 is closed by the decision record, and the values in force are in the registry's `wait` fields, where the mission-session gate (BD-373, which depends on this bead) reads and cites them.
- [ ] The measured T_turn, and the finding of rule 4 if it applied, are stated in the decision record in the form the KILL-SOLVE decision (N32a-32, which reaches this bead through BD-373) cites.
- [ ] The confirmation run is recorded for both session scripts with the old and the chosen values.
- [ ] The decision follows the rule; if a pair is adopted, the registry's `wait` fields, `RL-09`'s bound (when the maximum changes) and the server's request timeout are changed together, the registry lints pass on the changed registry, and the parity harness still reports no undeclared difference.
- [ ] The analysis recovers a planted optimum on a synthetic data set (durations concentrated at 8 s with T_poll = 60 s → a 10,000 ms default must win over 5,000 ms).

## Test plan

### Unit tests (`cargo test -p frob-conformance open_tether_3`)
- `rounds_formula`: (D, w_default, w_max) → rounds: (3 s, 5 s, 30 s) → 0; (5 s, 5 s, 30 s) → 0; (6 s, 5 s, 30 s) → 1; (35 s, 5 s, 30 s) → 1; (36 s, 5 s, 30 s) → 2.
- `time_to_result_example`: D = 8 s, policy (5, 30), T_poll = 60 s → 68 s; policy (10, 30) → 8 s.
- `constraint_excludes`: H = 60 s → w_max = 60 s is inadmissible (70 s > 60 s); w_max = 30 s is admissible.
- `rule_keeps_defaults_below_5_percent`.
- `rule_requires_positive_bootstrap_bound`.
- `planted_optimum_recovered` (synthetic, labelled `synthetic`).
- `poll_turn_extraction`: from a synthetic transcript with an exit 8 at t = 100 s and the next call at t = 147 s → T_poll = 47 s.
- `sufficiency_rule`.
- `cost_model_fast_job` (simulation): D = 2 s, default 5 s: wall 2 s, 1 turn.
- `cost_model_slow_job_one_poll`: D = 20 s, default 5 s, T₁ = 60 s, maximum 30 s: the handle returns at 5 s, the poll at 65 s finds the job done: wall 65 s, 2 turns (the closed form gives 80 s, an upper bound).
- `cost_model_slow_job_long_wait`: the same job with a 30 s default: wall 20 s, 1 turn.
- `cost_model_very_slow_job`: D = 200 s, default 5 s, T = 60 s each, maximum 30 s: polls at 65 s (waits to 95 s), 155 s (waits to 185 s), 245 s (done): wall 245 s, 4 turns.
- `simulation_never_above_closed_form`: on 1,000 seeded (D, T) draws with T constant within a call, simulated wall time ≤ D + rounds(D) × T.
- `rule_picks_smallest_within_two_percent`.
- `max_respects_harness_timeout`: a harness with a 25 s tool timeout yields a per-harness cap of 15,000 ms.
- `max_change_moves_lint_and_timeout`: a record adopting (5,000, 60,000) yields a patch that sets `mcp_max_ms =
  60000`, `RL-09`'s bound 60,000 and a request timeout of 70 s; the same `wait` patch without the other two fails
  the generated-file check.
- `cheap_turns_trigger_rule_4`: median T = 3 s.
- `turn_time_extraction`: on a stored request log, the interval is result-delivery to next-call arrival, not call to call.

### End-to-end script and logging
`scripts/e2e/open_tether_3.sh --sessions <dir> --seed 1`: checks the registration's commit order; then, each
through the `open_tether_3` example, extracts the measurements from the transcripts and the ledger (`extract`);
evaluates the grid (`grid`); applies the rule (`decide`); writes the record and, if a change is adopted, a patch
to the registry defaults (`record`). It sources the shared helper and writes
`target/e2e-logs/open_tether_3/<utc>.ndjson` plus a transcript: `cmd` lines; `metric` lines for T_poll and
T_turn quantiles per harness, the fraction of `run` calls finishing under each threshold, H per harness, and per
grid pair the mean time_to_result, mean blocked_time, rounds per call and admissibility; `assert` lines for
sufficiency and the planted-optimum check; a `summary` naming OPEN-TETHER-3 and GATE-TETHER-13 (precondition).
The script prints the grid table (default, maximum, mean wall, mean turns, mean idle), then runs the confirmation
comparison over MCP and logs the `evidence` block of each tool result in it, and the chosen values against the
defaults. Session content is referenced by digest only; transcripts are read as records and no prompt or model
output is logged.

### Known answers and negative controls
- Known answers: the rounds and time-to-result examples above; the four hand-computed simulation cases.
- Negative control: a turn-time extractor that measures call-to-call intervals (including the previous call's latency) inflates T; `turn_time_extraction` fails it.
- Negative control: a rule that picks the largest wait within tolerance; the tie-break test fails it.
- Negative control: a registry default changed by hand without the decision record fails the generated-file check.
- Negative controls: a grid edited after the extracts were read (the registration digest must not match); an adopted w_max that exceeds a harness timeout minus 10 s (the constraint check must reject it); T_poll computed across sessions instead of within one (the extraction test must fail).
- Determinism lanes: the analysis identical twice on one machine with the same seed.

## Considerations

- The cost model assumes an agent polls promptly with the maximum wait; agents that do other work between polls make the wait matter less, which only strengthens the case for keeping the defaults.
- A longer default helps when many jobs end just after 5 s and hurts when it holds turns for jobs that will take minutes; that is why blocked time is reported beside the objective.
- The per-surface default is a registry field so the parity gate treats the CLI's wait-to-completion and MCP's bounded wait as a declared difference; this bead must keep it declared.
- If the measured agent turn is far below 30 s for the harnesses in use, the premise of the bounded wait weakens; the mechanism stays (it is harmless), and the record says the avoided-poll saving is smaller than assumed. Below a median of 5 s rule 4 applies.
- T differs by harness and by model; the default is one number per surface, so it is set for the mix actually observed and revisited when the mix changes. The data and the rule are kept so that revisiting is a re-run.
- A wire-cancelled wait leaves the job running (the surface's rule), so a harness whose own timeout is shorter than the wait loses nothing but the result of that call, which `job_wait` retrieves; the per-harness cap exists to avoid that wasted turn, not to protect state.
- Both models ignore queueing delay before a job starts; under load the interval estimate in the handle is what the agent should read, and the confirmation run is done on an idle daemon.
