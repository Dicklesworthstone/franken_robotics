## Background

This bead exists only if the owner decides `build` on open question OPEN-TETHER-5, after the pilot (a week of
both machines' queue traces replayed on paper) shows at least 10% overlap between the time one machine idles and
the time the other queues. The fail-closed default is standalone machines, in which case this bead is closed
`withdrawn` citing the decision record (N41-17's typed close) and none of it is built.

FrankenRobotics runs a daemon, `frobd`, on each of two machines: a Linux host with two RTX 4090 cards and a Mac
with a large unified memory. There is one daemon per host and nothing is replicated. The **peer link** lets one
daemon forward a whole job to the other when the other can run it and has room. Tier Frontier. Its ceiling is
the device time one machine idles while the other queues, and nothing more.

The rule that makes a link between unequal machines safe is about what may travel. **What crosses:** seeds and
scene recipes (bytes to kilobytes), design and module differences (kilobytes), model-variant tables (kilobytes
to megabytes), policy weights (megabytes), receipts, digests and telemetry summaries. **What never crosses:**
compiled scene fields, world state, rollout buffers, and any object carrying the private mark (weights trained in
a private scene inherit it): a job with a private-marked input runs on the machine that holds it. A scene is regenerated on the receiving machine from its
seed with the pinned generator and must arrive at the same scene identifier. TARGET: at most 1 GB crosses per
campaign-hour, metered per transfer class.

Design decisions (DESIGN): the link forwards *jobs*, never ledger rows; each daemon remains the single writer of
its own ledger; a forwarded job is an ordinary admitted job on the receiving machine under an attenuated token
of the originating session; nothing here is consensus, and a partition simply means no forwarding.
Alternative excluded by the plan: replicated consensus, gossip membership and escrow counters for the daemon.

## Scope

In: the peer protocol and its authentication; the forwardable job record; what is transferred and metered; the
receiving side's admission; budgets and principals across the link; status and receipts flowing back; failure
handling (a peer drops out); observability; the link's kill gate, which the owner's `build` ruling requires
(N41-12: the link is switched on only once that gate's first measurement is recorded with clauses (a) and (b)
not triggered; a kill record has no pass). Out: deciding *which* jobs to forward
(the fleet scheduler); the scheduler inside each daemon; the pilot and its memo (N32a-34); the owner's decision
and the configuration key `fleet.peer_link` (N41-12).

## Technical approach

**Transport (DESIGN).** A mutually authenticated, encrypted connection between the two daemons, configured
explicitly with the peer's address and public key (no discovery). Newline-delimited JSON frames `frob.peer/1`,
plus content-addressed blob transfer for the allowed classes. The peer listener is off by default and is the
only network-facing listener in the system; it accepts exactly one configured peer.

**The forwardable job record (`frob.peerjob/1`).** A content-addressed record: the verb; the resolved request
with every object named by content address; the seed protocol; scene recipes (generator identifier, parameters,
seed) instead of scene packs; design and module versions as differences against bases the peer already holds
(or whole documents when it holds none); policy weights by digest; the determinism class required; the resource
vector (device family or any, memory, shape class, compute class); the role tag; the cost interval; the
originating idempotency key and principal; an attenuated capability token for the receiving daemon.

**Forwarding, numbered.**
1. *Offer.* A job any of whose inputs carries the private mark is never offered: it runs where the object is,
   and a submission that asks for it on the other machine is `FROB-REF-731` (observed `not-on-holder`, N37-REF).
   The originating daemon sends the record's digest and resource vector. The peer answers `accept`,
   `need <digests>` (objects it lacks, restricted to the allowed transfer classes) or `decline <reason>` (role
   table, memory, class, admission guard).
2. *Transfer.* Only objects of the allowed classes are sent, each checked against its digest on arrival and
   metered by class. A request to send a compiled scene field, a world state or a rollout buffer is refused on
   both sides (`FROB-REF-618`), and so is an object carrying the private mark (`FROB-REF-731`, `not-on-holder`);
   there is no code path that serializes them for the link.
3. *Regenerate.* The peer regenerates each scene from its recipe and compares the scene identifier with the one
   in the record; a mismatch declines the job (the generators are not the same pin) and raises an alarm.
4. *Admit.* The peer runs its ordinary admission transaction under the originating key and principal: one job
   per (principal, verb, key) on the peer too, so a re-sent offer is a no-op that returns the existing job.
5. *Bind at the origin.* The originating daemon records, in its own ledger and in the same transaction that
   binds the caller's key, that the job is forwarded: the job row stays in the state machine of N32a-08 (it is
   `running` from the peer's acceptance) and gains the columns `forwarded_to` (the peer's key fingerprint) and
   `peer_job` (the peer's job identifier); no ninth state is added. The caller's
   handle is the originating job; `job.status`, `job.wait` and `job.cancel` on it are relayed.
6. *Return.* Progress frames, the terminal receipt, digests and telemetry summaries flow back. Bulk telemetry
   stays on the executing machine and is read there (or a failing world is replayed on the other machine from
   its address, design, policy weights and scene recipe: exact or a tolerance replay according to the
   determinism class attained).

**Budgets and principals.** The originating session's budget is reserved at the origin at the interval's upper
end before the offer. The token sent to the peer is attenuated: fewer scopes (only what the verb needs) and a
budget equal to the reservation; a token can never be widened (`FROB-REF-723`). The peer's charge, reported in
its receipt, is settled against the origin's reservation; the peer's own budget ledger shows the forwarded
principal with a zero balance at the end.

**Paired comparisons.** A comparison whose arms ran on different device families is unpaired unless the
cross-family bitwise class holds. The link therefore forwards a study whole or not at all; it never splits the
two arms of one study across machines.

**A peer drops out.** The originating job stays `running` with `forwarded_to` set and `last_committed` from the
last receipt. After a
timeout (configuration; DESIGN default 120 s without a heartbeat) the origin marks it `peer-unreachable` in the
job's progress, never as failed: the peer may still be running it. On reconnection the origin asks the peer for
the job by key. Re-queueing the job locally is the fleet scheduler's decision, allowed only where role and
class permit, and only after the peer confirms it holds no running job for that key (otherwise two machines
would run one key). The scheduler's drop-out rule (N21c-14, which depends on this bead) reads the peer's answer
by key: a finished job is adopted, a running one is kept, and only a key the peer reports absent or cancelled
is re-queued, with its epoch advanced. A machine that does not come back leaves the job `peer-unreachable`; the
caller's repair is to resubmit under a new key.

**Shared views.** The shared archive is a grow-only set keyed by content address, merged by union; the
leaderboard breaks ties by a total order (metric, then content address), so two daemons that merge reach the
same view. The link carries the archive's new content addresses and summaries, not its payloads.

**Kill gate KILL-PEERLINK (DESIGN name; the plan requires a kill gate of every Frontier mechanism and names none
for the link).** Its record must exist before this bead is ready: the pilot register funds a Frontier mechanism
only once its kill gate is in the gate register (N38a-09), and PILOT-PEER-01 registers it `to-register`
(N32a-34), so the row is entered, in the wording below, in the change that records the owner's `build` ruling,
which also sets the pilot record's `fallback.kill_gate` to `KILL-PEERLINK` (N41-12's acceptance); this bead checks
the row before the first forwarded job and owns its measurements and decision. The record is a
`kind = "kill"` row of `registries/gates.toml` in the fallback ledger's format (N40-03's kill row, as N40-27
writes the others): `trigger` (below), `fallback`, `decided = "M4"`, `mode = "standing"` (clauses (a) and (b)
are evaluated at every event and at every exit from M4 on), owner §32.11, consumers §21.17, `reads` (the
acceptance campaign's record and the link's transfer meter), and an empty `decision`. N32b-25 lists it as the
eighth Tether kill gate with this bead as its decision bead and creates no record of it. Trigger: (a) one key admitted twice, or charged twice, across the two daemons, in the 1,000-schedule
campaign of the acceptance or at any time in operation; (b) any byte of a forbidden class (compiled scene field,
world state, rollout buffer) or of private-marked data observed on the wire; (c) over the first four weeks of
operation, recovered device time (device-hours of forwarded jobs run on the idle machine) below 10% of the
device-hours used on both machines, the pilot's own threshold now measured on the link instead of replayed.
Clauses (a) and (b) have zero tolerance and fire at once; (c) is read once, at four weeks. Fallback: standalone
machines (`fleet.peer_link = false`; the listener is not started; forwarded jobs in flight finish on the peer and
are found by key). The campaign of the acceptance criteria is the gate's first measurement: entered with clauses
(a) and (b) not triggered, it is the condition under which N41-12 accepts `fleet.peer_link = true`. That entry
is a measurement, not a decision. The decision is an array of N40-03 entries `{outcome, adr, date, session,
exit, scope}`, one scope per clause (`clause:a`, `clause:b`, `clause:c`), each with its ADR
`docs/adr/ADR-KILL-PEERLINK-<milestone>.md` carrying N40-03's fields (trigger as registered, measured values
with receipt hashes, outcome, fallback, beads re-read, recording session). At the M4 exit, (a) and (b) are
`not-fired` or `fired` on the record so far. Clause (c) is `not-fired` or `fired` at the four-week reading; if
the four weeks end after the M4 exit review, the M4 entry for (c) is `deferred` to the named next exit, with the
reading date as its reason. A `fired` entry puts the fallback in force at once: `fleet.peer_link = false`, this
bead closes `fallback` (N41-17 rule 5), and N21c-14 and every other dependent are re-read against the ADR.

Determinism: a forwarded job's digests on the peer are those the job would have on that machine locally; whether
they equal the origin machine's is a statement about determinism classes, not about the link. Evidence: the
receipt names the executing machine's hardware fingerprint and configuration digest.

## Acceptance criteria

- [ ] The owner's `build` decision is on record and cited; otherwise this bead is closed `withdrawn` citing the decision record.
- [ ] A job forwarded from A to B is admitted exactly once on B under any re-send, reconnect or crash of either daemon (1,000 seeded fault schedules on the lab runtime with two daemon instances): one job per key on each side, one charge.
- [ ] Only allowed transfer classes cross: an attempt to send a compiled scene field, a world state or a rollout buffer is refused with `FROB-REF-618` on both sides; a wire capture of a full forwarded campaign contains none.
- [ ] A job with a private-marked input is never offered, a planted transfer of a private-marked object is refused with `FROB-REF-731` on both sides, and the wire capture of a full forwarded campaign holds no private-marked byte.
- [ ] Every scene regenerated on the peer has the scene identifier named in the record; a planted generator-pin mismatch declines the job.
- [ ] Transfer volume is metered per class and stays at or under 1 GB per campaign-hour on the reference campaign (TARGET; measured value recorded).
- [ ] The originating session's budget shows one reservation and one settlement equal to the peer's reported charge; the peer's token cannot be used for another verb or a larger budget.
- [ ] `job.status`, `job.wait` and `job.cancel` on the originating handle behave as for a local job, including a drained cancel with the last committed tick.
- [ ] With the peer unreachable, the job shows `peer-unreachable`, is never reported failed, and is recovered by key on reconnection; a local re-queue is refused while the peer still holds a running job for the key.
- [ ] The two arms of a study are never split across machines.
- [ ] The peer listener is off by default, accepts only the configured peer's key, and passes the threat review's checklist.
- [ ] KILL-PEERLINK's kill row is in `registries/gates.toml` in N40-03's format (trigger, fallback, `decided` M4, mode `standing`, reads, the four-week reading date) before the first forwarded job; the acceptance campaign's record is its first measurement, entered with (a) and (b) not triggered; a planted double admission or forbidden-class byte makes the decision function return `fired` for its clause; the outcomes used are only N40-03's (`not-fired`, `fired`, `not-reached`, `deferred`).
- [ ] The linked stage of N21c-15's `scripts/e2e/fleet_status.sh --stage linked` passes: five lanes across the two linked daemons and `link: up`; with the peer killed, that machine `down`, exit 2 and the local half still reported.
- [ ] A forwarded job's row on the origin is in one of N32a-08's eight states at every instant (the ledger consistency check passes on both daemons after every fault schedule).

## Test plan

### Unit tests (`cargo test -p frob-verbs peer`, `cargo test -p frob-cli peer`)
- `peerjob_record_is_content_addressed`: the same resolved request gives the same digest on both machines.
- `allowed_classes_only`: a blob tagged `scene-field` is rejected by the sender and by the receiver.
- `private_input_never_offered`: a job whose policy weights were trained in a private scene is not offered, and a `need` naming a private-marked object is refused `FROB-REF-731` by the sender and by the receiver.
- `offer_need_accept_roundtrip`; `decline_reasons`: role table, memory, class, guard.
- `scene_identifier_mismatch_declines`.
- `resend_is_noop`: the second offer of the same record returns the existing peer job.
- `attenuated_token_scopes_and_budget`: the peer token has only the verb's scopes and the reserved budget; an attempt to widen is 723.
- `settlement_equals_peer_charge`.
- `relay_wait_and_cancel`.
- `peer_unreachable_is_not_failed`; `no_local_requeue_while_peer_holds_job`.
- `study_never_split`.
- `listener_off_by_default`; `unknown_peer_key_rejected`.
- `archive_union_commutes`: merging A into B and B into A gives the same set and the same leaderboard order.
- `forwarded_job_keeps_eight_states`: an origin row with `forwarded_to` set moves only by N32a-08's legal transitions; a peer timeout changes its progress, not its state.
- `kill_peerlink_decision`: (double admissions, forbidden bytes, recovered share, weeks observed) → entries by clause: (0, 0, 0.12, 4) → a, b and c `not-fired`; (1, 0, 0.30, 1) → a `fired`; (0, 1, 0.30, 1) → b `fired`; (0, 0, 0.09, 4) → c `fired`; (0, 0, 0.05, 2) → no entry for c (it is read at four weeks), and at an exit review before the four weeks c is `deferred` with the reading date.
- `kill_peerlink_record_format`: the row entered with the `build` ruling loads under N40-03's schema with every kill field and an empty decision; an outcome outside N40-03's four is rejected, and so is a `pass` on the row.

### End-to-end script and logging
`scripts/e2e/peer_link.sh --seed <s>`: starts two daemons with separate state roots (two hosts where available;
two instances on one host for the per-commit lane), configures them as peers, submits jobs on A that the role
table makes eligible for B, forces forwarding, kills and restarts each daemon and the link at seeded points,
cancels a forwarded job, and captures the wire. Every submitted job carries its own idempotency key
(`--key "$(e2e_key pl-<step>-<n>-s<seed>)"`, step names with `-` for `_`); a re-send reuses its key on purpose,
with `e2e_key pl-<step>-<n>-s<seed> --again`. Further steps: `kill_record` (the
KILL-PEERLINK row read back from `registries/gates.toml` before the first forward), `fleet_status_linked`
(N21c-15's `scripts/e2e/fleet_status.sh --stage linked` against the two daemons), and `decision` (the campaign's
first-measurement entry and the decision function's entries by clause, in N40-03's outcomes). It sources the
shared helper and writes
`target/e2e-logs/peer_link/<utc>.ndjson` plus a transcript: `cmd` lines with exit code and wall time; the
envelope's `evidence` block (including the executing machine's fingerprint); `metric` lines for jobs per key on
each side (exactly 1), charges per key (exactly 1), bytes transferred per class and per campaign-hour (threshold
1 GB), forbidden-class transfers (0), private-marked transfers (0), scene identifier mismatches (0), recovery by key after link loss (all);
`assert` lines for budget settlement and relay behaviour; on failure the seed, the fault schedule, the key and
both ledgers' copies; a `summary` with counts naming KILL-PEERLINK (first measurement) and the decision
function's entries by clause.

### Known answers and negative controls
- Known answer: a scene regenerated from the same recipe on both machines has the same scene identifier; a world replayed on the other machine from its address, design, policy weights and recipe reproduces the failure (exactly, or within the tolerance of the class attained).
- Negative controls (each must be caught): a build with a serializer for world state on the link (the wire capture check); a sender that ignores the private mark (`private_input_never_offered` and the wire check); a receiver that admits by peer job identifier instead of the originating key (a re-send creates a second job); an origin that re-queues locally on timeout (two machines run one key); a token forwarded unattenuated (the scope test).
- Determinism lanes: the two-instance script twice on one machine with identical outcome sets; the two-host run recorded with both fingerprints.

## Considerations

- This is the only mechanism in the surface chapter that opens a network listener. It stays off unless the owner's decision is `build`, and it is the reason a threat review is a prerequisite.
- The link recovers idle time; it does not make either machine faster. If the fleet scheduler's kill gate fires, there is nothing to decide what to forward, and the link is not built.
- Bulk telemetry does not cross, so an agent diagnosing a forwarded job either reads summaries or opens a session on the executing machine; the generated guide must say so.
- Clocks differ between machines; nothing in the protocol compares timestamps across them. Ordering is by each ledger's own sequence.
