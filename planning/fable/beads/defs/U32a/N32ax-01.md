## Background

FrankenRobotics is reached through verbs (`sim.run`, `study.submit`, …) declared once in `registries/verbs.toml`
and served by the command line `frob`, the daemon `frobd` and the MCP server `frob-mcp`. A verb of kind `run` spends
compute: it is **admitted** (checked, bound to an idempotency key, charged a budget reservation and given a job row
in the daemon's ledger) and then executed as a job. Tether, the surface subsystem, owns admission; it owns no
physics. The handlers and the facts they depend on live in the subsystem crates.

Several subsystems hold **standing refusals**: facts on record, established before the run is asked for, that make
a class of runs pointless or forbidden until something changes. Two are specified and need a place to act:

- *The standing impossibility cut* (Habitat, `FROB-REF-309`, exit 3). `scene.fit` can prove that a footprint family
  cannot pass a route of a compiled scene. From then on any run whose task binds that scene and route, for a design
  at least as large, is refused at admission: training or evaluating a body on a route it provably cannot pass
  spends device time on a foregone answer. Repairs: read the cut; edit the design; run `scene.retrofit`; pass an
  explicit diagnostic override.
- *The unaccepted scene pack* (Habitat, proposed `FROB-REF-318`, exit 3). A compiled scene is not usable until its
  acceptance report is complete; a run, a training job or a study on a pack whose report is incomplete or has a
  failed fixture is refused with a pointer to `scene.accept`. This check cannot be skipped by a flag.

Others of the same shape exist or will (a scene variant that is not resident on the job's device, `FROB-REF-319`;
a retired calibration; a kernel whose CPU-versus-device check is not current). Without one mechanism each
subsystem would patch its test into each run verb's handler, the five run verbs would drift apart, a verb added
later would silently miss a check, and a refusal raised inside a handler would arrive after the budget was
reserved and a job row written. DESIGN: admission consults one table of **admission checks**; a subsystem
registers a check; Tether runs every applicable check before anything is bound or charged. Rejected: checks
inside handlers (late, and a refusal there is a failed job, not an admission refusal); a hook the subsystem calls
on itself (nothing proves that every run verb calls it); checks in the surface crates (`frob-cli`, `frob-mcp`
contain no per-verb code, and the socket fallback of kill gate KILL-MCP has no handler crates at all).

Tier Solid. Crate `frob-verbs` (interface, table, ordering); the daemon in `frob-cli` hosts it.

## Scope

In: the check interface and its declaration; the registry table and the lints that tie checks to verbs; where the
checks run in the admission order; consistency with the admission transaction; the diagnostic override; what is
recorded; behaviour under `estimate_only`, without a daemon and on the socket back end. Out: the checks
themselves and their indices (the standing cut: N19b-32; pack acceptance: BD-228 with the refusal row decided in
N19c-42; a non-resident variant: N19c-22); budget admission and `FROB-REF-701` (N32a-15); size classes, the
admission guard and `FROB-REF-703`, `-704` (BD-296); the compute envelope and `FROB-REF-761` (N36-20, which keeps
its own function `admit_run`; this bead only fixes its position in the order); the idempotency binding (N32a-09).

## Technical approach

**1. The interface (DESIGN sketch; fixes intent, not signatures).**

```rust
pub struct AdmissionCheckDecl {
    pub id: &'static str,                    // "habitat.standing-cut": <subsystem>.<name>, registry name grammar
    pub owner: &'static str,                 // implementing crate; never frob-cli or surface/frob-mcp
    pub verbs: &'static [&'static str],      // run verbs it guards
    pub refusals: &'static [RefusalCode],    // every code it may raise
    pub override_name: Option<&'static str>, // "standing-cut"; None: cannot be overridden
    pub basis: &'static [&'static str],      // names of the standing indices it reads
}
pub trait AdmissionCheck: Send + Sync {
    fn decl(&self) -> &'static AdmissionCheckDecl;
    fn evaluate(&self, cx: &Cx, req: &ResolvedRequest, view: &AdmissionView) -> CheckOutcome;
}
pub enum CheckOutcome { Pass, NotApplicable, Refuse(Refusal) }
```

`ResolvedRequest` is the request after every mutable name has been replaced by an immutable identifier (design,
scene, task, route, backend). `AdmissionView` is a read-only view of the ledger at one commit sequence and of the
store at its committed frontier. A check has no clock, no device and no network; it is a pure function of the
resolved identities and the view, so the same request against the same records gets the same verdict on every
machine (determinism class D0). `evaluate` observes cancellation through `cx`.

**2. Registry form.** Checks are declared in `registries/verbs.toml` beside the verbs, so that the generated
surfaces know them:

```toml
[[admission_check]]
id = "habitat.standing-cut"
owner = "frob-scene"
verbs = ["sim.run", "eval.run", "train.start", "opt.start", "study.submit"]
formats = ["<the scene-pack format identifier of registries/formats.toml>"]
refusals = ["FROB-REF-309"]
override = "standing-cut"
basis = ["scene_standing_cuts"]
first_milestone = "M3"
```

The verb entry schema (closed; a new field is added with its lint) gains the derived, generator-written field
`admission_checks` and, for a verb guarded by at least one overridable check, the input property
`diagnostic_override` (an array of override names, restricted to those of its checks; CLI `--diagnostic-override
a,b`). It is not one of the five common properties of kind `run`: a verb with no overridable check does not have
it. The field, the property and the appending of each guarding check's `refusals` to the verb's generated list
are one arm of NJL-01's derivation (`crates/frob-verbs/src/registry/derive.rs`), written by this bead in the
change that adds the `[[admission_check]]` table, with its test, as NJL-01 requires of a field a later bead adds
(requested of NJL-01: a row for this arm in its variation table, which is the one list of what the generator
adds). Lints, each failing the build of `frob-verbs` by name: `admission-check-id` (grammar, uniqueness);
`admission-check-on-non-run` (a guarded verb that is not a job-submitting `run` verb); `admission-check-refusal`
(a code that is not in `registries/refusals.toml`, or not appended to a guarded verb's refusal list);
`admission-check-coverage` (every job-submitting `run` verb with a parameter of a format named in `formats` is in
`verbs`, or in an `exempt` list with a written reason); `admission-check-unbound` (a declared check with no
linked implementation at or after its `first_milestone`, or an implementation with no declaration);
`override-name-collision`.

**3. Where the checks run.** For a job-submitting `run` verb the dispatch pipeline is: locate, validate
(`FROB-REF-802`), authorize (`-720`), resolve, digest, implemented (`-724`), then admission in five stages:

| Stage | What | Refusal | Owner |
|---|---|---|---|
| A | Preconditions: every applicable admission check | The check's own code | This bead |
| B | Estimate; the interval's upper end against the remaining budget | `FROB-REF-701` | N32a-15 |
| C | Size class (assigned and recorded; it refuses nothing at submission), then the compute envelope | `FROB-REF-761` (a campaign-class submission without an approved class included) | BD-296, N36-20 |
| D | Admission guard: utilization and the per-environment job cap | `FROB-REF-703`, `retry: backoff` | BD-296 |
| E | The admission transaction: binding, reservation, job row | `FROB-REF-803`, `-805` | N32a-09 |

DESIGN reason for A first: a standing refusal is repaired by changing the question, never by more budget or by
waiting, so reporting it first saves the agent a repair loop on B to D; the transient refusal (D) is last so that
no caller backs off and retries a request that would be refused anyway. Within stage A the checks run in
ascending `id`; all are evaluated; the envelope's `refusal` is that of the first refusing check and each further
one is listed in `warnings` as `also-refused: <code> by <id>`, so that one answer shows everything to repair. A
refusal in stages A to D binds nothing, reserves nothing and writes no job row: the same idempotency key may be
retried after the cause is repaired.

**Which stages exist at this bead's milestone.** At M2 the pipeline holds stage A (this bead), stage B (the
budget admission of N32a-15, a dependency, which this bead moves into its position), the envelope half of stage
C (`admit_run` of N36-20, `FROB-REF-761`) and stage E (N32a-09). The size classifier and the admission guard
(`FROB-REF-703`) are BD-296's and arrive at M3. At submission the classifier only assigns and records the class:
a campaign-class job without an approved compute class is the envelope's `FROB-REF-761`, never `FROB-REF-704`,
which is the dispatcher's code when the same classifier runs again at dispatch or resume (N36-20's division,
which BD-296 follows), outside this pipeline. The pipeline is an ordered list of named stage
slots, `preconditions`, `budget`, `size_class`, `envelope`, `guard`, `transaction`; the two slots of BD-296 are
present and empty until that bead registers into them, so that filling them changes no position and no other
stage's code. This bead tests the order of what exists and the position of the two empty slots (with a
`synthetic` stage, below); the order tests against the real size classifier and the real guard are BD-296's
(filed as a request).

**4. Consistency with the transaction.** Stage A can be slow the first time (a check may derive a memoized fact
about a bound identity), so it runs outside any ledger transaction, and a standing fact could be recorded between
stage A and stage E. Each standing index has a version counter in the ledger table `admission_basis(name,
version)`; the owner of the index increments it in the same transaction that changes the index. Stage A records
the versions it read. Stage E compares them inside its immediate transaction; on a difference it aborts and
stages A to E run again. Each repetition needs a committed change to a standing index in between; after four
repetitions the daemon, which is the ledger's only writer, evaluates stage A while holding the writer, which
ends the loop.

**5. The diagnostic override.** Naming an override whose check would have passed changes nothing. Naming one whose
check refuses admits the job and records `diagnostic_overrides: [{check, code, basis versions}]` in the job row
and in the run manifest; the envelope carries the warning `diagnostic-run: <names>` and an empty `claims` list.
The override list is part of the resolved request and therefore of its digest: the same key with and without the
override is `FROB-REF-803`. An unknown name, or the name of a check that declares no override, is `FROB-REF-802`
with `pointer: /diagnostic_override`. What may be done with a diagnostic run's results belongs to the owner of
the check; the daemon counts overrides per session and `session.show` prints the count.

**6. Other paths.** `estimate_only` (CLI `--estimate`): stage A runs and its refusals are returned as findings
under `result.admission.would_refuse` with exit 2; nothing is refused, so an agent sees the standing fact before
it spends. Without a daemon, a CPU-tier verb run in process passes the same stage A against the store (the
version comparison is skipped; there is no concurrent writer). On the socket back end and under the
`registry-only` build the adapter has no checks linked; the daemon runs them. A verb that submits child jobs
(`eval.compare`, `opt.cascade`, `solve.run`) is checked itself and each child passes admission again.

**7. Record.** Every admitted job row carries `admission: [{check, version, outcome}]` with outcome `pass`,
`not-applicable` or `overridden`; the terminal receipt repeats it. A refusal appends one row to
`admission_refusals(seq, session, verb, request_digest, check, code)`; `frob capabilities --json` lists the
checks linked in this build with their verbs, codes and override names.

## Acceptance criteria

- [ ] A check registered for `sim.run` that refuses makes `frob sim run …` return one envelope with the check's code and exit, `ok: false`, and the ledger shows no binding, no reservation and no job row; the same key is admitted after the standing fact is removed.
- [ ] The same refusal is returned on the CLI, over MCP (`isError: true` with the same envelope) and through the socket back end, for each of `sim.run`, `eval.run`, `train.start`, `opt.start` and `study.submit` that exists in the build.
- [ ] Stage order holds: a request that would fail a precondition and the budget is refused with the precondition's code; one that passes preconditions and exceeds the budget gets `FROB-REF-701`.
- [ ] Two refusing checks yield the lower `id` as the refusal and the other under `warnings`.
- [ ] A standing fact committed between stage A and stage E is honoured: over 1,000 seeded interleavings no job is admitted that the final state of the index refuses.
- [ ] An overridable check with its override named admits the job, labels it (`diagnostic_overrides` in the manifest, the warning, empty `claims`), and the override count of `session.show` rises by one; a check without an override cannot be bypassed by any flag (`FROB-REF-802`).
- [ ] `--estimate` reports the standing refusal as a finding with exit 2 and creates nothing.
- [ ] Each of the six lints fires on its planted registry and names it; the clean registry builds.
- [ ] `crates/frob-verbs/CONTRACT.md` states the interface, the stage order, the override rule and the recorded fields.

## Test plan

### Unit tests

`cargo test -p frob-verbs admission_checks` (the real dispatcher and a real ledger in a temporary state root; the
checks used are test fixtures labelled `synthetic`, compiled under the feature `conformance-fixtures`):
- `refusal_binds_nothing`: ledger digest before equals digest after a stage-A refusal; counters for bindings, reservations and job rows unchanged.
- `stage_order_precondition_before_budget`: a request that fails a check and exceeds the budget is refused with the check's code; with the check passing, `FROB-REF-701`. `stage_order_envelope_after_budget`: over budget and over the compute envelope → 701; within budget and over the envelope → 761.
- `stage_slots_fixed`: the pipeline's slot list is exactly `preconditions`, `budget`, `size_class`, `envelope`, `guard`, `transaction`, with `size_class` and `guard` empty in a build without BD-296. A `synthetic` stage that refuses with a marker code, registered in turn into `size_class` and into `guard`, is reached only when every earlier slot passes: with a refusing check, or over budget, the answer is the earlier stage's code, never the marker; registered into `guard` with the request also over the envelope, the answer is 761.
- `first_refusal_by_id_others_listed`: checks `a.one` and `b.two` both refuse → refusal from `a.one`, warning names `b.two`.
- `not_applicable_is_pass`: a request that binds no scene passes a scene check with outcome `not-applicable`.
- `basis_version_race`: a standing row inserted after stage A and before stage E → the transaction aborts, stage A reruns and refuses; property over 1,000 seeded schedules on the deterministic runtime.
- `rerun_terminates`: a writer that changes the index on every pass → admission completes on the fifth pass under the writer hold.
- `override_admits_and_labels`; `override_changes_digest` (same key with and without → 803); `override_unknown_name_802`; `override_on_non_overridable_802`.
- `estimate_reports_would_refuse`: exit 2, `result.admission.would_refuse[0].code` equals the check's code, no job row.
- `in_process_no_daemon_runs_checks`; `socket_backend_daemon_runs_checks`.
- `child_jobs_pass_admission_again`: a composite verb whose child binds a refused identity fails at the child with the check's code.
- `lint_<name>` for the six lints, one planted registry each.
- `derive_admission_check_arm`: with the synthetic check registered for `sim.run` (overridable, `standing`) and a second, non-overridable synthetic check for `eval.run`, the generated `sim.run` entry has `admission_checks`, the property `diagnostic_override` whose values are exactly `["standing"]`, and the check's code in its full refusal list; `eval.run` has the code and no `diagnostic_override`; a run verb guarded by no check has neither.

### End-to-end script and logging

`scripts/e2e/admission_preconditions.sh` (header: `bead=N32ax-01 milestone=M2 labels=tether,admission seed=1
needs=cpu,frobd,mcp plants=handler-check,skip-version`). With `frobd` built with `conformance-fixtures`, which
links the synthetic check `conformance.standing` (it refuses any guarded run whose bound design identity is in the
fixture table, with the registered code stored in the row, here `FROB-REF-309`, and declares the override name
`standing`): (1) `frob session open --key ap-s1 --json` (a `mutate` verb, so it carries a key); (2)
`frob sim run <fixture> --key k1 --json` → admitted; (3) plant a standing row for the design; (4) the same command
with `--key k2` → `e2e_expect_refusal FROB-REF-309 3`, and `frob job find --verb sim.run --key k2` finds nothing
(the job verbs are N29a-23's, a dependency; the ledger counts of the `assert` lines say the same from the inside); (5) `frob sim
run … --estimate --json` → exit 2 with `would_refuse`; (6) `--diagnostic-override standing` with `--key k3` →
admitted, warning present, `frob run show` prints `diagnostic_overrides`; (7) the same call as the MCP tool
`sim_run`; (8) from M3, steps `real-309` and `real-318` repeat (4) with a real standing cut and a real unaccepted
pack, logged `skipped: capability absent` before those checks exist, never as passed. Logs go through the shared
helper to `target/e2e-logs/admission_preconditions/<utc>.ndjson` with a transcript: every `cmd` with exit code and
wall time, each `refusal` with code, check id and first repair, `assert` lines with ledger counts before and
after (bindings, reservations, job rows), the envelope's `evidence` block, `metric` lines for checks evaluated and
reruns, and the `summary`.

### Known answers and negative controls

- Known answer: the stage table above as an exit-code fixture
  (`crates/frob-conformance/fixtures/tether/admission_stage_order.toml`): for the three conditions that exist at
  M2 (standing refusal, over budget, over envelope), planted singly and in pairs, the code returned is that of
  the earliest stage (`FROB-REF-309` from the synthetic check, then 701, then 761; six rows). The rows for a
  campaign-class job whose approval lapses before dispatch (704, raised at dispatch, not by this pipeline) and
  for the guard (703), which complete the five conditions singly and in pairs (fifteen rows), are added to the
  same fixture by BD-296 at M3; until then the fixture's loader reports them `not yet
  due`, never `pass`.
- Negative controls: `handler-check` (a build in which the check runs inside the handler: the ledger shows a job
  row and a reservation, and `refusal_binds_nothing` must fail); `skip-version` (stage E does not compare
  versions: `basis_version_race` must find an admitted job); a registry with a new `run` verb that takes a scene
  and is absent from the check's `verbs` (the coverage lint must fail).
- Metamorphic: the order in which checks are registered does not change any answer; adding a check that always
  passes changes no envelope apart from the `admission` list.
- Determinism lanes: twice on one machine, debug and release, both hosts; verdicts are exact.

## Considerations

- A check is on the admission path of every guarded run, so its cost is everyone's latency. Budget: stage A adds
  at most 20 ms at the 95th percentile with warm memos (TARGET); a check that needs more precomputes its fact when
  the standing index is written.
- The table must not become a place for policy that belongs in budgets or scopes. A check may refuse only for a
  recorded fact about bound identities; it may not read load, time or the caller.
- Overrides are a way to spend compute on a foregone answer. They are counted and visible; if a session's count
  grows, the repair is in the check's index, not here.
- The `formats` coverage lint depends on the artifact-input parameter kinds of the entry schema (field `params`);
  until those are filled for every run verb the lint runs on the explicit `verbs` lists and reports unfilled
  entries as findings.
- If kill gate KILL-MCP fires, nothing changes: the daemon evaluates the checks.
