## Background

Many agents share one daemon (`frobd`), one pair of machines and one store. Tether, the surface subsystem, gives
each agent a **session** holding a **capability token**: a tamper-evident statement of what the session may read,
spend and publish. Authority lives in the token and nowhere else. The MCP server's task clusters change which
tools an agent sees, never what it may do; a verb hidden by focus is still refused or allowed by the token alone.

Three acts are kept apart because they fail differently: reading an existing record (cheap, can leak), allocating
a job (spends shared compute) and publishing an export (leaves the system). Budgets are scopes too: a session can
spend only what its token grants. One class of data is reachable by no token an agent can hold: the sealed worlds
of the blinded qualification lane. The statistics of that lane hold only if no retry is informed by the worlds
that judged the last one, so the scope catalogue contains no scope that grants such a read.

Design decision (DESIGN) and alternatives. The token is a bearer credential minted by the daemon and authenticated
with a daemon-held key; the daemon's ledger holds the session row (state, budgets, parent). Rejected: (a) access
control lists keyed by process or user: every agent on the host runs as the same user, so the operating system
cannot tell them apart; (b) offline-attenuable chained tokens (macaroon style): attenuation here must debit the
parent's budget, which needs the ledger in any case, so offline derivation buys nothing and adds a second
verification path; (c) scopes with wildcards: attenuation must be decidable by set inclusion, and a wildcard would
silently widen as the registry grows.

Milestone note: `session.open` exists from M0 as a namespace and bookkeeping call; tokens and budgets are enforced
from M2 (this bead); attenuation, namespaces and shared views follow at M3 (N32b-02, N32b-03).

principal's grant in the owner-held configuration (the `principal.<id>` tables of N37-02, which owns the file); the

where a token travels; the daemonless posture; secrecy of tokens in logs and envelopes.
Out: attenuation and budget debit (N32b-02); namespaces and lineage ownership (N32b-03); the `session.open` and

verification order without changing them, and this bead is their one definition.

## Technical approach

**1. Scope catalogue** (`registries/scopes.toml`, compiled into `frob-verbs` beside the verb table; DESIGN layout).

| Kind | Scopes | Grants |
|---|---|---|
| Read | `<cluster>:read` for every registry cluster (`design:read`, `telemetry:read`, `job:read`, `session:read`, …) | `read` verbs of the cluster |
| Spend | `<cluster>:run` (`sim:run`, `train:run`, …), and the named spend scopes `study:submit`, `mission:run`, `nemesis:run`, `autopsy:run`, `qual:run` | `run` verbs: allocating a job |
| Write | `<cluster>:write` for every cluster whose `mutate` verbs cite it (`design:write`, `study:write`, `task:write`, `mission:write`, `predict:write`, …), and the named write scopes `scene:import`, `ground:import`, `cert:write` | `mutate` verbs that create or change named objects |
| Publish | `export:report`, `export:packet`, `export:policy` | Verbs that write an artifact under the export root |
| Private | `private:read`, `private:export` | Reading or exporting objects derived from a private scene |
| Admin | `job:cancel` (`job.cancel` and other `admin` verbs of the job cluster); `<cluster>:admin` for every other cluster whose `admin` verbs cite it (`train:admin` and `store:admin` at M2; `scene:admin`, `fidelity:admin` from M3); named admin scopes added under the named-scope rule (N32bx-02, `ground:retire`) | `admin` verbs |
| Budget | `gpu:seconds=N`, `cpu:core_seconds=N`, `disk:bytes=N` (N an `int53` count) | Spending up to N of the unit |

No scope grants reading a confirmation world. `qual:admin` and the confirmation audit scope are owner-held and are
not mintable through `session.open` by an agent. Each verb's registry entry lists its `capabilities`, and may list
`option_capabilities` (a map from an input option to the scopes it additionally needs, for example `session.show`'s
`all` needs `session:read`; DESIGN, so that reading one's own session needs no scope while listing every session
does); the lint requires every listed capability to be a catalogue scope and every catalogue scope to be used by
some verb or verb option. The
generated scopes `<cluster>:read`, `<cluster>:run`, `<cluster>:write` and `<cluster>:admin` exist exactly for the
(cluster, kind) pairs that some registry row of that cluster cites in its `capabilities` or
`option_capabilities`, so the second half of the lint holds by construction for them. Each catalogue row carries a flag
`owner_only` (true for `qual:admin` and the confirmation audit scope); `session.open` refuses to mint an
`owner_only` scope for an agent principal with `FROB-REF-723` (a widening request). From M3 the firewall (BD-261)
mints `qual:admin` only for the holder roles listed in `config/qualification.toml` and refuses, in dispatch, any
argument that resolves to an object carrying the confirmation mark (`FROB-REF-840`); this catalogue adds no scope
that the firewall's table lists as permitting a sealed read.
Grammar of a scope string: `^[a-z][a-z0-9-]*:[a-z][a-z0-9_-]*(=[0-9]+)?$`; the `=N` part is allowed only on
budget scopes. A string that fails the grammar, or passes it and is not in the catalogue, is not a scope: a
registry entry citing it fails the build, and a token carrying it is invalid (`FROB-REF-723`).
The catalogue grows with the surface: a registry row that cites a generated scope adds it, and a named scope is
added by its chapter's bead under the named-scope rule (N32bx-02). DESIGN: the `<cluster>:write` and
`<cluster>:admin` forms are generated here, at M2, and not left to the capstone of the capability layer (BD-258,
M3), because the verb registry already cites them on verbs of the second milestone (`train.stop` and
`store.collect` are `admin` verbs of M2 citing `train:admin` and `store:admin`; `study.plan` is a `mutate` verb of
M2 citing `study:write`), while the specification's list names only `design:write` and `job:cancel` of the two
kinds; without them those rows fail this lint or are unreachable. BD-258 keeps the act lint over the M3 surface
and defines no second catalogue.

**Implied read (the rule is the decision of the capstone BD-258; the function is written here, because minting
is here and precedes that bead).** `<cluster>:run` and `<cluster>:write` each imply `<cluster>:read`: a session
that may run or edit a cluster's objects sees them through the result anyway. The rule goes by the spelling of
the scope (DESIGN, made precise here): a scope spelled `<c>:run` or `<c>:write` whose `<c>` is a registry
cluster implies `<c>:read`, whether the catalogue lists it among the generated forms or among the named
spending and write scopes (`mission:run`, `nemesis:run`, `autopsy:run`, `qual:run` and `cert:write` have that
spelling; the plan's worked session holds `mission:run` and no `mission:read` and reads its mission answers).
Every other scope implies nothing: `study:submit`, `scene:import`, `ground:import`, `job:cancel` and the other
named admin scopes, `<cluster>:admin`, `export:*`, `private:*` and the budget scopes (an admin act, an import or
a publication needs its own grant). The implication is applied when a scope set is stored,
never when it is checked: `Scopes::close_implied(set)` (in the scope type's module of `frob-verbs`) adds
`<c>:read` for every `<c>:run` and `<c>:write` in the set, provided `<c>:read` is a catalogue scope (a cluster
with no `read` row has none, and nothing is added), and is idempotent. Minting calls it on the requested set
before the session row is inserted and before the tag is computed, so every token's `scopes` is closed and the
check of step 5 below stays plain set inclusion and reads no rule. N32b-02's derivation (M3) calls the same
function on the child's request before its subset test; BD-258 defines no second copy.

**2. Token** (`frob.token/1`; DESIGN).

```rust
// DESIGN: intent, not signatures. Owned by frob-verbs (type) and frobd (key, minting).
pub struct CapabilityToken {
    session: SessionId,            // "s:2f6a…", content address of the session row
    principal: PrincipalId,        // the root session's identity; inherited by derived sessions
    namespace: Namespace,          // "agent-17"
    parent: Option<SessionId>,     // set for a derived token
    scopes: BTreeSet<Scope>,       // sorted; budget scopes included
    issued_ns: U64Str, expires_ns: U64Str,   // wall-clock instants; authorization only, never in a result
    key_id: KeyId,                 // first 8 bytes of BLAKE3(daemon key), hex
    tag: [u8; 32],                 // BLAKE3 keyed hash of the canonical JSON of all fields above
}
```

Wire form: `frobtok1.<base64url(canonical JSON payload)>.<base64url(tag)>`. This is the one definition of
`frob.token/1` (DESIGN; the plan says only that tokens are minted by the daemon and authenticated with a
daemon key). The capstone BD-258 restates it and adds nothing: its earlier draft used other names (`not_after`,
`mac`, a stored `id`, a `budgets` object, a namespace prefixed `ns:`) and has been brought to this layout.
Three things that draft carried are fixed here so that they are not lost. (1) Budgets travel as budget scopes
inside `scopes` (`gpu:seconds=N`, `cpu:core_seconds=N`, `disk:bytes=N`); there is no `budgets` field, and the
amounts left are in the session row, never in the token. A budget unit that is not a scope of the catalogue
(the trace-byte budget of the session budget ledger) is a cap of the session row set from the principal's
grant, not a token field. (2) The token identifier is derived, not stored: `tk:` followed by the BLAKE3 of the
canonical payload bytes. It may appear in logs and refusals beside the session identifier, because it does not
yield the tag. (3) The namespace is written as the namespace bead (N32b-03) writes it, `agent-17`, with no
prefix.

Canonical JSON is the project's one
serialization (sorted keys, no insignificant whitespace, NFC strings, integers above 2⁵³ as strings). The daemon
key is 32 bytes from the operating system's entropy source, created on first start at `<state root>/keys/token.key`
with mode 0600; rotating it invalidates every outstanding token (documented, and the only revocation that needs
no ledger). It is the token key only (DESIGN): the key that tags pagination cursors is another file,
`<state root>/daemon.key` (N32a-10, N32a-14), which an ordinary in-process `frob` may create at M1, before any
daemon exists. Two files, for two reasons: only a daemon may bring a token key into existence (a process that
cannot mint must not be able to create the key that authenticates minting), and rotating the token key to
revoke every token must not also expire every open cursor. Neither key verifies the other's tags. Default lifetime 24 h, maximum 7 days (DESIGN defaults, part of the daemon's configuration digest).

**3. Minting.** A root token is minted from its principal's **grant**, read from the owner-held safety
configuration `safety.toml` (N37-02, a dependency): one table `principal.<id>` per agent principal (DESIGN of
N37-02), with `scopes` (catalogue scopes, budget scopes such as `gpu:seconds=600` included), `namespace`,
`trace_bytes` (the session's trace-byte cap) and `max_lifetime_s`. The daemon reads the tables once at start; a
table with a scope outside the catalogue, or with an `owner_only` scope, is a start-up error of `frobd` naming the
table and the scope (N37-02's check, which reads this catalogue from M2). In the `session.open` transaction:

1. Choose the principal (DESIGN): the `principal` input when given; when omitted, the one principal of the
   configuration if it grants exactly one; when it grants several, `FROB-REF-802` with `pointer: /principal`
   (the input is required) and the granted identifiers in the repair, which are names and not credentials. A
   principal with no table, and any root call when the configuration grants none, is `FROB-REF-723` with
   `observed` the principal and the repair "the owner adds a `principal.<id>` table to `safety.toml`": there is
   nothing to mint from, and nothing is written.
2. Take the request (DESIGN): authority is always named, so omitted `scopes` means no non-budget scope (the
   session can call only `public` verbs and read itself), never the whole grant; this is also what the
   named-scope rule of N32bx-02 requires (a named scope such as `ground:retire` is in no default set). An omitted
   budget unit means the grant's amount of that unit, so that a session is never silently unable to spend what
   the owner granted; omitted `ttl_s` means the default lifetime below, capped at `max_lifetime_s`. The result
   echoes the scopes and amounts granted, so nothing stays implicit.
3. Close the requested scope set under the implied-read rule (`Scopes::close_implied`) and check it against the
   grant closed the same way: a scope outside it, a budget above the grant's amount or a unit the grant lacks, a
   lifetime above `max_lifetime_s`, or a `namespace` other than the grant's when the table names one, is
   `FROB-REF-723` with `observed` each widening element and `required` the grant's value (the same refusal and
   the same form as a widening derivation, N32b-02). An `owner_only` scope asked by an agent is the same refusal.
4. Insert the session row (state `open`, the principal, the closed scopes, budget caps, the trace-byte cap from
   the grant, namespace, expiry), compute the tag over the closed set and return the token once.

The ledger stores the session, never the token string. The grant is a bound, not an authentication: every agent
on the host runs as the same user, so a caller naming a principal is believed (the threat boundary of
Considerations), and what the owner controls is the most any session of that principal can hold. A change to the
tables takes effect at restart, like every key of the file.

A root call that presents a valid token (in `FROB_SESSION_TOKEN`, `--session-token-file` or the transport's
bearer) is `FROB-REF-723` with the repair "derive (`derive: true`), or open a root session without a token"
(DESIGN): a holder narrows by derivation and never opens a second root beside its token, which would let a
sub-agent holding a derived token, or an MCP agent, mint its principal's whole grant again (the plan's "never a
wider one"). Over MCP, where every tool call carries a token (N32a-27), `session_open` is therefore derive-only;
root sessions are opened on the command line by whoever starts the agent, and the token is handed to the agent's
harness. A token-less process with a shell can still open a root session: that is the host-user boundary of
Considerations, not a gap of this check. Owner-only scopes are never minted for an agent principal: an agent's
table cannot list one (start-up error) and a request for one is `-723`. The owner's own session, which holds them
(`qual:admin` for the holders of `config/qualification.toml`, BD-261; `session:audit`, N32bx-01), is the open
point of Considerations.

**4. Verification, in dispatch, before `resolve` and before any handler.**

A request that presents no token while a daemon is reachable has no session and holds no scope (DESIGN; the
plan does not say). On the command line a `session.open` without `derive` goes to minting (item 3). A verb
whose row is `public` and that reads no session (the operator verbs `capabilities`, `schema`, `doctor` and
`robot-docs`) is served, so that a person can still ask what is wrong and how to open a session. Every other
call, the other three session verbs and `derive: true` included, is `FROB-REF-723` with `observed: "no token"`
and the first repair `frob session open`: nothing runs without a session to charge and a namespace to act in.
(N32a-27 gives the same refusal to every tool call of a stdio server started without a token, a root
`session_open` among them, since that server could not use a token it minted; it is asked to serve the four
operator tools there too, so that the surfaces agree.) A request that presents a token goes through the steps
below.

1. Parse the three parts; decode the payload. Malformed: `FROB-REF-723`. A payload with an unknown field, or
   with a scope string that fails the grammar or is not in the catalogue, is malformed.
2. Recompute the tag with the key named by `key_id`; compare in constant time. Mismatch or unknown key: `-723`.
3. `expires_ns` at or before now: `-723` with `observed` the expiry.
4. Read the session row: missing or `closed`: `-723`.
5. For each capability in the verb's registry entry, and in its `option_capabilities` for each option present in
   the request: absent from `scopes` gives `FROB-REF-720` with `pointer: /session/scopes` (or the option's
   pointer), `observed` the held scopes, `required` the missing scope, the two repairs of the registry row and
   `retry: after-change`.
6. Budget scopes are not checked here; admission checks them against the estimate.

Because the check precedes the handler, a refused call has produced no partial data, created no object and made
no charge. Both refusals exit 5. A refusal names the session identifier, never the token.

**5. Where a token travels.** The CLI and the stdio MCP server read `FROB_SESSION_TOKEN` from the environment, or a
file named by `--session-token-file`; the HTTP transport takes a bearer token. DESIGN: a token is never an
argument value, because an argument vector is visible in the process table and is what every transcript and
recorded command prints. The common flag `--session` and the variable `FROB_SESSION` of the CLI skeleton
(BD-022) therefore carry the session *identifier* (`s:…`), which is not a credential: before M2 it selects the
session; from M2 it is optional, and when given beside a token it must name the token's session. A value that
parses as a token (`frobtok1.…`) passed to `--session` or found in `FROB_SESSION`, and an identifier that
differs from the token's session, are refused with `FROB-REF-802` (pointer `/session`; the repair names
`FROB_SESSION_TOKEN` and `--session-token-file`), so that a mistaken paste cannot put a credential into a
transcript unnoticed. (Beads that describe `--session` or `FROB_SESSION` as taking the token itself, BD-022,
BD-138 and N32a-27, are asked to align; the gate recorder's `FROB_SESSION=session:…` label is this identifier
use.) A token never appears in an
envelope other than the `session.open` result, never in a log line, a job record, a progress frame or an
end-to-end transcript; fields that hold one are marked `x-frob-secret` in their schema and the log helper redacts
them.

**6. Without a daemon.** CPU-tier verbs run in process and say so in the envelope. No token can be minted or
verified there, so the process runs as the built-in principal `local` in namespace `local`, with no device budget.
If a token is presented and no daemon is reachable to verify it, the call is refused with `-723` rather than run
with unverified authority (fail closed).

## Acceptance criteria

- [ ] `registries/scopes.toml` exists; the lint passes; a verb entry citing an unknown scope fails the build.
- [ ] A session opened with scopes S can call exactly the verbs whose capabilities are subsets of S; every other
      verb returns `FROB-REF-720`, exit 5, with one envelope and no `result` field.
- [ ] Every minted token's `scopes` is closed under the implied-read rule: a session opened with `sim:run`
      alone holds `sim:read` and can call the `read` verbs of `sim`; one opened with `train:admin` or
      `export:report` alone gains no `:read` scope.
- [ ] A root token is minted only from a `principal.<id>` grant of `safety.toml`: an unlisted principal, or a
      root call when no principal is granted, returns `FROB-REF-723` and mints nothing; a request beyond the
      grant (a scope, a budget amount, a lifetime or a namespace) returns `FROB-REF-723` naming the widening
      element; with several principals granted, a root call without `principal` returns `FROB-REF-802`
      (pointer `/principal`); omitted `scopes` yields no non-budget scope, and an omitted budget unit the
      grant's amount; a root call that presents a valid token returns `FROB-REF-723` (a holder derives).
- [ ] With the daemon reachable and no token presented: a root `session open` mints; `doctor`, `capabilities`,
      `schema` and `robot-docs` answer; every other verb returns `FROB-REF-723` with `observed: "no token"`.
- [ ] After a `-720` or `-723` refusal the ledger shows no new job, binding, reservation or artifact.
- [ ] A token with one flipped bit in payload or tag, an expired token, a token of a closed session and a token
      naming an unknown scope each return `FROB-REF-723`, exit 5.
- [ ] The derived token identifier `tk:…` is the BLAKE3 of the canonical payload, is the same on every use of a
      token, and appears in refusals and logs where the token itself never does.
- [ ] `qual:admin` and the audit scope are `owner_only`, and `session.open` refuses to mint an `owner_only` scope
      for an agent (catalogue lint and minting test at M2; the run-level refusal of a sealed read,
      `FROB-REF-840`, is BD-261's at M3 and is replayed by N32b-05).
- [ ] No token string appears in any log, ledger row or envelope other than the `session.open` result (searched).
- [ ] A token string given as the value of `--session` or of `FROB_SESSION` is refused with `FROB-REF-802` and is
      not echoed in the refusal; a cursor tagged with `daemon.key` presented as a token, and a token presented
      as a cursor, each fail verification (`-723`; `FROB-REF-806`).
- [ ] `frob-verbs` `CONTRACT.md` records the token format, the catalogue and the verification order.
- [ ] `scripts/e2e/tether_tokens.sh` passes at M2 with the logging below.

- `token_never_logged`: a run with trace logging on; the token bytes do not occur in any log file.
- `owner_only_not_mintable`: `qual:admin` and the audit scope carry `owner_only = true`; `session.open` for an
  agent principal asking for `qual:admin` returns `-723` and mints nothing (ledger digest unchanged).
- `scope_grammar_property`: 10,000 random strings; every string accepted by the grammar and present in the
  catalogue round-trips through a token unchanged; every other string makes the token invalid.
- `daemonless_presented_token_refused`.
- `token_on_argv_refused`: `frob design show x --session frobtok1.<payload>.<tag>` and the same string in
  `FROB_SESSION` → `FROB-REF-802`, pointer `/session`, and the token bytes occur nowhere in the envelope or the
  logs; `--session s:<other session>` beside a valid token → 802; `--session s:<the token's session>` beside it
  is accepted.
- `token_and_cursor_keys_are_separate`: `keys/token.key` and `daemon.key` hold different bytes after first
  start; a cursor payload re-tagged under `daemon.key` in the token's wire form → `-723`; rotating
  `keys/token.key` refuses every outstanding token and leaves a cursor issued before the rotation valid.

### End-to-end script and logging
`scripts/e2e/tether_tokens.sh` (header `bead=N32b-01 milestone=M2 labels=tether,safety`), on a temporary state
root with `frobd` on `batch-cpu` and a `safety.toml` (mode 0600) granting one principal `principal.agent-a`
{ scopes `design:read`, `sim:run`, `gpu:seconds=600`; `max_lifetime_s` 86,400 }: open a session with
`--scopes design:read,sim:run --budget gpu_s=60 --key s-1` (minted for `agent-a`, the one granted principal);
ask for `--principal agent-z --key s-2` (`-723`, nothing minted) and for `--scopes design:write --key s-3`
(`-723`, `observed` `design:write`); a root open with the first token in `FROB_SESSION_TOKEN` (`--key s-4`,
`-723`);
call an admitted verb (`frob design show`) and an unadmitted one (`frob design edit … --key e-1`, expecting
`FROB-REF-720`, exit 5); replay with a token with one flipped tag byte and with a token naming `design:everything`
(both `-723`); open a session with a 1 s lifetime, wait 2 s, call (`-723`, `observed` the expiry); stop `frobd`
and present a token (`-723`, daemonless fail-closed); then grep every log, ledger dump and transcript for the
token bytes (none found). It sources the STD-E2E helper and writes
`target/e2e-logs/tether_tokens/<utc-timestamp>.ndjson` and a transcript; every line has `ts`, `script`, `bead`,
`step`, `event`, the exact command line with the token redacted to its `tk:` identifier, exit code, wall time, the
envelope's `evidence` block, the refusal code against its expected value, ledger digests before and after each
refused call, and on failure the first differing field and the state-root path; a final `summary`. N32b-05's
many-agent script (M3) runs these steps again as its group `token-*`.

### Known answers and negative controls
- Known answer: the exit and refusal codes of the unscoped row of KA-755 (`FROB-REF-720`, exit 5).
- Negative control 1: a dispatcher that checks scopes after the handler (planted): `refusal_before_handler` fails.
- Negative control 2: a tag compared on a truncated prefix (first 8 bytes): the tamper test must find a passing
  forgery among flips in the tail.
- Negative control 3: a catalogue with a planted wildcard scope `*:read`: the lint must reject it.
- Determinism: token bytes are a function of the session row and the key; with a fixed key and injected clock the
  minted token is byte-identical twice and across platforms.

## Considerations

- Threat boundary: a token protects agents from each other and bounds a prompt-injected agent; it is not a defence
  against a process with the host user's file permissions, which can read the key. That boundary is stated in the
  contract.
- Wall-clock time enters expiry only. No result, digest or evidence record reads it (the scheduler invariant
  INV-TETHER-09 is unaffected).
- Key rotation closes every session; running jobs continue, because a job is owned by the daemon, not by a token.
- Open point (owner: Tether lead; fail-closed default: 24 h): whether long campaigns need renewable sessions. Until
  decided, an expired session is replaced by a new one and jobs are found again by idempotency key.
- Open point (owner: Tether lead with the project owner): how the owner's session, the one holder of owner-only
  scopes, is told apart from an agent's, when a caller naming a principal is believed. Fail-closed default
  (DESIGN): the principal `owner` is granted only by a table `principal.owner` of `safety.toml`, the one table
  allowed to list owner-only scopes (asked of N37-02, whose check otherwise makes such a table a start-up
  error), and a root call naming it is minted only when it arrives through the command-line adapter (surface
  `cli`), never over MCP (where root opens are refused anyway, item 3) and never by derivation. Until N37-02
  admits the table, no session holds an owner-only scope, and BD-261's owner acts and N32bx-01's audit read
  wait for it.
