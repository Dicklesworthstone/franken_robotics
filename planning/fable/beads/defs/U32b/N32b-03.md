## Background

A swarm of agents designs robots on one daemon (`frobd`) and one store. Three properties make that safe and
useful. First, each agent has its own design **namespace** and **lineage**: the history of how its designs came to
be is its own, and no agent can rewrite another's. Second, agents can still see what others achieved: a shared
**archive** and a **leaderboard** exist as read-only views. Third, agents coordinate with tools they already have:
a lineage identifier is usable as a thread identifier in the suite's agent mail system, so "about this design
line" is an address.

Terms. A *namespace* is the scope of mutable names (a design called `quad-a` is `agent-17/quad-a`). A *lineage* is
the append-only graph of patches from which a design's versions descend; its *head* is the latest version. A
*content address* is the hash of an immutable object. The surface rule that makes names safe (decision
ADR-TETHER-11): mutating and job-submitting verbs bind immutable identifiers; a mutable name is resolved once,
before the request is digested, and the resolution is echoed in the envelope's `bound` field.

Design decisions (DESIGN). (1) Ownership is by namespace and is checked at the surface, so every `mutate` verb is
covered by one rule. (2) The shared archive is a grow-only set keyed by content address and merged by union; the
leaderboard is a view ordered by a total order (metric, then content address). Reason: two daemons (the two
machines of the fleet) that exchange entries in any order must reach the same view, and a grow-only set under
union is the simplest structure with that property. Rejected: a mutable shared table with last-writer-wins (a
late writer could erase another agent's entry); tie-breaking by arrival time (see the counterexample below).

## Technical approach

**1. Namespaces.** Grammar `^[a-z][a-z0-9-]{0,31}$`. A root `session.open` may request one; otherwise the daemon
assigns `agent-<n>` with n the next free integer. The ledger binds namespace to principal (one owner per
namespace; a second principal asking for a taken namespace is refused with `FROB-REF-725`). `local` is reserved for
the daemonless mode. Derived sessions inherit the parent's namespace.

**2. Name resolution.** An unqualified mutable name resolves in the caller's namespace. A qualified name
`<namespace>/<name>` may be read by any session holding the cluster's read scope, unless the object is private.
Resolution happens once, before the request digest is taken; the envelope's `bound` echoes the immutable
identifier (`"design": "d:41aa…"`).

**3. The ownership check** (in dispatch, after token verification and name resolution, before the handler). For a
verb of kind `mutate`: every mutable name it creates or changes and every lineage it appends to must be owned by
the token's namespace. Otherwise: `FROB-REF-725` (a write outside the caller's namespace or lineage), exit 5,
`pointer` at the offending argument, `observed` the owning namespace, repairs: (1) fork into your own lineage with
`design new <name> --from <content address>`; (2) ask the owner, using the lineage identifier as the mail thread.

**4. Forking instead of rewriting.** `design.new --from <address>` creates a new lineage in the caller's namespace
whose root records the source address and its lineage, so provenance survives and `design.blame` crosses the
boundary read-only. Lineage records are append-only for their owner too: a patch needs `expected_parent` equal to
the head.

**5. Jobs of other principals.** `job.list` shows the caller's jobs in full and other principals' jobs as counts
by size class and state, with no names, designs or scenes. A session holding `job:read` for operator use (the
dashboard) sees identifiers and agents; nothing grants another principal's results.

**6. Lineage identifiers.** `lin-<namespace>-<16 lowercase hex digits of the root patch address>`, matching
`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. FACT to verify at implementation: the suite's mail server accepts this grammar
as a thread identifier; if its validation is narrower, the lineage grammar is narrowed to match, never mapped.

**7. Shared archive.** A set A of entries `(content address of the design, content address of the scored record)`.
An entry is added by the daemon when a result with a scorecard is recorded in any namespace; agents hold no verb
that writes to it. Merge of two daemons' sets: A ∪ B. Union is commutative, associative and idempotent, so any
exchange order converges. Entries are never removed by merge; removal happens only through the store's purge path
with a receipt.

**8. Leaderboard.** For a metric m with a declared direction, the leaderboard is the archive sorted by the key
(value of m in the better-first direction, then content address in ascending byte order). The key is a total
order on entries, so the view is a function of the set. Each row carries the entry's evidence block (class, tier,
determinism); rows are never compared across evidence classes without the label showing.

Counterexample that fixes the tie-break: entries P and Q have equal metric. Daemon X saw P then Q; daemon Y saw Q
then P. Ordered by arrival, the merged boards differ; ordered by content address they are identical.

**9. Private objects** never enter the shared archive or the leaderboard, and are absent from catalogs.

## Acceptance criteria

- [ ] Two sessions with different namespaces each create a design `quad-a`; both exist; each `design.show quad-a`
      returns its own.
- [ ] A `design.edit` by agent B on `agent-a/quad-a` returns `FROB-REF-725`, exit 5, and leaves A's lineage head
      and the ledger unchanged.
- [ ] `design.new --from <A's address>` by B succeeds and records the source address and lineage.
- [ ] `job.list` by B shows A's jobs as counts by class and state only.
- [ ] Merge is convergent: for random entry sets and random exchange orders, both daemons' archive digests and
      leaderboard digests are equal.
- [ ] A private design scored in a private scene is absent from the archive and the leaderboard.
- [ ] Every lineage identifier produced matches the grammar.

## Test plan

### Unit tests
`crates/frob-verbs/tests/namespaces.rs`, `crates/frob-cli/tests/shared_views.rs`:
- `unqualified_resolves_in_own_namespace`; `qualified_read_needs_read_scope`.
- `write_outside_namespace_is_725`: pointer, observed owner, two repairs present.
- `namespace_single_owner`: a second principal requesting a taken namespace is refused.
- `fork_records_provenance`: the new lineage root holds the source address and lineage identifier.
- `foreign_jobs_are_counts_only`: no field of another principal's job other than class, state and count.
- `lineage_id_grammar`: 10³ generated identifiers match the pattern.
- `archive_union_laws` (property): A ∪ B = B ∪ A; (A ∪ B) ∪ C = A ∪ (B ∪ C); A ∪ A = A.
- `leaderboard_total_order`: 10⁴ random entry sets with planted ties; the sort key has no equal distinct pair.
- `merge_order_independent`: entries {P: 0.81, Q: 0.81, R: 0.92}, "higher is better": both daemons list R, then P
  and Q by address, whatever the arrival order.
- `private_excluded_from_views`.

### End-to-end script and logging
`scripts/e2e/tether_capabilities.sh` (N32b-05), steps `ns-*`: two sessions as two agents; the same design name
in both; a cross-namespace edit (expect exit 5, `FROB-REF-725`); a fork; `frob job list --json` from the other
agent. Lines log the command, exit code, refusal code against expected, the `bound` identifiers, lineage head
digests before and after, and the `evidence` block.

### Known answers and negative controls
- Known answer: the three-entry leaderboard above.
- Negative control (registered as `tether-leaderboard-arrival-order`): a leaderboard that breaks ties by arrival
  sequence must fail `merge_order_independent`.
- Negative control: a dispatcher that checks ownership on the name string before resolution (so
  `agent-a/../agent-b/x`-style or aliasing names slip through): `write_outside_namespace_is_725` runs with aliased
  spellings and must fail the mutant.
- Negative control: a last-writer-wins archive loses an entry under one exchange order; `archive_union_laws` fails.

## Considerations

- The read rule for qualified names is permissive on purpose: a shared archive is useless if designs cannot be
  read. What is protected is history and spend, not visibility; privacy is a separate mark with its own scope.
- Leaderboards invite overfitting to a metric. The view shows evidence class and whether a result is provisional;
  qualification is only ever claimed from the blinded lane.
- Open point (owner: Tether lead; fail-closed default: no cross-namespace write of any kind): whether a parent
  agent may be granted write access to a collaborator's lineage. Until decided, forks are the only path.
