## Background

`frob-tui` is the terminal dashboard of FrankenRobotics: six panes that let a person watch a campaign of agents
(races, budgets, devices, the queue, failures, evidence) plus a view of gate status. It is part of Tether, the
surface subsystem, and it is optional: nothing depends on it, no claim and no agent workflow needs it, and its
kill gate KILL-TUI has the fallback "no dashboard" (the verbs `job.list` and `session.show` carry the same
numbers). That ceiling bounds the effort.

It is built on FrankenTUI, the suite's terminal UI library. FACT (read 2026-11-21 from its README and manifests):
workspace version 0.10.0 on `nightly-2026-08-31`; an Elm-style runtime (`Model`, `Cmd`) in `ftui-runtime`; an
inline mode (`ScreenMode::Inline`) that keeps scrollback; a pane workspace (`PaneTree` in `ftui-layout`); widgets
`Table`, `Sparkline`, `ProgressBar`, `Tree`, `Tabs`, `LogViewer`, `JsonView` and `StatusLine` in `ftui-widgets`;
`BarChart` and `LineChart` in `ftui-extras`; a test harness with shadow-run comparison and determinism fixtures in
`ftui-harness`. FACT: `ftui-runtime` has an optional `asupersync-executor` feature pinned exactly to asupersync
0.5.0. The whole build graph of this project holds one asupersync package, so that feature stays off.

Governing decision (ADR-TETHER-10): the dashboard and the viewer are ordinary clients; each value they show is
obtainable by a named verb. Reason: no private interface means no unaudited path to state, and agents without
eyes lose nothing. Rejected: a dashboard that reads the ledger database directly (faster to write, and it becomes
a second reader of the ledger with its own idea of what a number means).

This bead is the core: the program structure every pane plugs into. The panes are N32b-07 and N32b-08; the
conformance run is N32b-09; the admission and gate record is seed BD-300.

## Technical approach

**Dependencies.** `frob-verbs` with `registry-only` (verb table, envelope types, schemas); the socket dispatch
back end; FrankenTUI with default features off and `runtime` and `native-backend` on. No physics crate, no
airlock group, no direct ledger access; `xtask check-deps` enforces it and refuses the executor feature.

**Structure (DESIGN).**

```rust
// DESIGN: intent, not signatures.
struct Model { sources: BTreeMap<SourceKey, Latest>, events: Ring<Event>, layout: PaneTree, focus: PaneId,
               modal: Option<Modal>, session: SessionView, status: Status }
struct SourceKey { verb: &'static str, args_digest: Blake3 }
struct Latest { envelope: Envelope, seq: u64 }                 // the last envelope of that source
struct Cell  { text: String, src: SourcePtr }                  // every displayed number
struct SourcePtr { key: SourceKey, pointer: String }           // JSON pointer into the source envelope
enum Msg { Envelope(SourceKey, Envelope), Event(Event), Key(KeyCode), PollDue(SourceKey), Resize(u16, u16) }
fn update(model: Model, msg: Msg) -> (Model, Vec<Cmd>);        // pure
fn view(model: &Model) -> Frame;                               // pure; reads the model only
```

Rules that make it testable. (1) `update` and `view` are pure functions; all input arrives as `Msg`. (2) No frame
is drawn without a message. (3) `view` never reads a clock: ages and waits shown are differences of instants
supplied by the daemon in envelopes and events. (4) Every numeric cell holds a `SourcePtr`; a pane cannot display
a number it computed without declaring the formula and its source cells (derived cells list their inputs).

**Sources and polling.** Each pane declares its sources: verb, arguments, minimum poll interval. One poller per
distinct source issues the verb through the socket back end under the dashboard's session token. The next poll is
due after max(the pane's minimum, the `poll_after_ms` of the last envelope); when the event stream reports a
change affecting a source (a job state transition, a commit), its poll is brought forward. A source whose verb
answers `FROB-REF-724` (not implemented in this build) or `FROB-REF-720` (scope missing) is shown as such in its
pane, with the code, and is polled no more than once a minute.

**Event stream.** The daemon's event stream is itself a verb, so that the dashboard keeps no private interface
(ADR-TETHER-10): DESIGN, the read verb `job.list` with `follow: true` (and `all_agents: true` under the operator
scope `session:read`, N32b-03) answers its first page and then keeps the `frob.rpc/1` request open, sending one
progress frame per job event (admitted, refused, started, chunk committed with progress `done/total` and unit,
estimate updated, preempted, resumed, cancelled, completed, failed; each with job, world, episode and tick identity
where they apply, and the daemon's instant) until the client closes; the same stream printed as line-delimited
JSON is KILL-TUI's fallback. The `follow` option and the `all_agents` projection exist when this bead starts:
they are part of `job.list` as the job verbs' bead delivers it (N29a-23, M2, a dependency), and this bead
consumes them and defines neither. Where the stream cannot be had (a daemon that answers `follow` with
`FROB-REF-802`, or a connection that drops and cannot be reopened), the dashboard polls `job.list` at its
`poll_after_ms` and the panes are unchanged, only slower to react (the fail-closed behaviour, tested by
`no_follow_falls_back_to_polling`). Events are kept in a bounded ring (10,000, DESIGN) for the log viewer and used to schedule
polls. They are never the source of a displayed total: totals come from verb envelopes.

**Read-only rule.** The dashboard issues `read` verbs only, with one exception: `job.cancel` for a selected job,
issued only after a confirmation modal that shows the job identifier, owner, state and last committed tick, and
only if `session.show` lists the scope `job:cancel` (the action is hidden otherwise; the daemon remains the
authority and its refusal `FROB-REF-720` is displayed if it comes). A cancelled job drains at the kernel-batch
boundary; the modal then shows the receipt's last committed tick.

**Modes.** Full screen with the pane workspace and tabs; `--inline` (scrollback kept); `--record <file>` writes
every `Msg` that came from outside as a line of `frob.tui-trace/1` (sequence number, kind, source key, canonical
JSON body); `--replay <file>` feeds a trace to `update` with no daemon; `--dump <dir>` renders each pane's frame
to a text file and each pane's cells with their source pointers to JSON, then exits.

**Failure behaviour.** Daemon unreachable: a status line says so and the last envelopes stay on screen marked
stale with their daemon instants. The dashboard owns no job and no device: killing it at any instant leaves the
ledger consistent and every admitted job discoverable by its key (invariant INV-TETHER-10).

## Acceptance criteria

- [ ] `frob-tui` builds in the core workspace on the one toolchain; `cargo tree -d -p frob-tui` shows one
      asupersync package or none; `check-deps` passes and fails on a planted physics dependency and on the
      executor feature.
- [ ] `--replay` of a recorded trace followed by `--dump` produces byte-identical output on two runs.
- [ ] 10⁴ `PollDue`-free idle iterations draw zero frames; idle processor use over 60 s is at most 2% of one core
      (TARGET, the admission gate's figure).
- [ ] Every numeric cell in a dump has a source pointer that resolves in the recorded envelope.
- [ ] Only `read` verbs are issued in a session without `job:cancel` (checked from the daemon's request log);
      with the scope, `job.cancel` is issued only after confirmation.
- [ ] Killing `frob-tui` with signal 9 during a poll and during a cancel confirmation leaves the ledger consistent.
- [ ] The crate ships `CONTRACT.md` with its ten sections; "known gaps" names the panes not yet backed by an
      implemented verb.

## Test plan

### Unit tests
`crates/frob-tui/tests/core.rs` (FrankenTUI's headless harness; real envelopes from fixtures, no mocks):
- `update_is_pure`: the same message sequence yields equal models (canonical bytes) twice.
- `view_reads_no_clock`: one trace replayed with the injected process clock at two instants a year apart; the
  dumps are identical.
- `no_redraw_without_message`.
- `poll_interval_respects_poll_after_ms`: envelope says 2,000 ms, pane minimum 500 ms: next poll at 2,000 ms.
- `event_brings_poll_forward`.
- `no_follow_falls_back_to_polling`: against a daemon whose `job.list` refuses `follow` with `FROB-REF-802`, the
  dashboard polls at `poll_after_ms` and the dumps after the same envelopes are identical to the streaming case.
- `refused_source_shows_scope`: a source answering `FROB-REF-720` renders the code and the missing scope named in
  the envelope's `required`, not a blank.
- `unimplemented_source_shown_with_code`: a source answering `FROB-REF-724` renders the code, not a blank.
- `cells_have_source_pointers`.
- `cancel_hidden_without_scope`; `cancel_requires_confirmation`; `cancel_refusal_displayed`.
- `trace_roundtrip`: record then replay gives the same final model.

### End-to-end script and logging
`scripts/e2e/tui_panes.sh` (owned by N32b-09), steps `core-*`: start `frobd` on a temporary state root, run
`frob-tui --record` against a seeded job set for 30 s, replay and dump twice, compare; read the daemon's request
log for verb kinds. NDJSON lines carry the command, exit code, wall time, idle CPU percent against 2, frames drawn
against 0 in the idle window, the asupersync package count against 1, dump digests, and the first differing cell
on failure.

### Known answers and negative controls
- Negative control: a pane that formats a locally measured elapsed time; `view_reads_no_clock` must fail.
- Negative control: a poller that ignores `poll_after_ms` and polls every 50 ms; the idle CPU assertion and the
  poll-interval test must fail.
- Negative control: a build that issues `job.cancel` on the key press without the modal;
  `cancel_requires_confirmation` must fail.
- Determinism lanes: replay and dump twice on one machine; on Linux and macOS (rendering is to a virtual buffer).

## Considerations

- KILL-TUI (decided at the third milestone, bead N32b-31): fires if FrankenTUI cannot be admitted with one
  asupersync package or the snapshot tests cannot be made stable; fallback: no dashboard, the same events as
  line-delimited JSON, `job.list` and `session.show` carry the numbers. If FrankenTUI does not build on the
  project toolchain, the remedy is an upstream change there or the toolchain train; the crate gets no toolchain
  of its own.
- Privacy: job and scene names appear on screen; objects of a private scene are absent unless the dashboard's
  token holds the private read scope, exactly as in the verbs it calls.
- The dashboard must not become where numbers are defined. If a pane needs a quantity no verb returns, the fix is
  a field on the verb, reviewed there.
