## Background

The viewer of FrankenRobotics (a Three.js r186 page under `viewer/`, N32b-10) reaches people in one of two forms:
as a page opened beside a running daemon, and as a **self-contained replay**: one HTML file, exported by the verb
`telemetry.export-html`, that replays an episode with its overlays and fetches nothing from the network. Both
need the page packaged into a single file with every script and style inline. This bead is that packaging step
and the byte budgets it must meet.

There are two routes. The **plain route** inlines the page and the vendored Three.js and is always built. The
**FrankenThreeD route** passes the page through a sibling project's build command when the page stays inside
that project's admitted feature subset. FACT about FrankenThreeD today (read from its README): it is at an early
phase; it pins Three.js r186; an ingest command routes an ordinary application's WebGPU renderer to a new backend
for an admitted feature subset; pixel parity holds for ten scenes on a software Vulkan driver; no hardware run
and no speedup have been measured; single-file packaging of its own is not built. FACT: it has four crates and
its runtime crate pins asupersync 0.5.0, so nothing in this project's Rust build graph may link it. It is
therefore a packaging route and a possible future accelerator, reached as a subprocess of the viewer's build
scripts, and never a dependency. Because it has no single-file packaging, the HTML export is this project's own
build step in both routes.

Budgets (TARGET). An exported replay is one HTML file of at most 15 MB. The replay packet format sets a default
cap of 8 MiB for the whole file and budgets 600,000 bytes of it for the page, so the page bundle produced here
must fit in 600,000 bytes.

## Scope

In: `viewer/build/pack.mjs` (the plain route); the bundle's structure and determinism; the size report and the
600,000-byte and 15 MB checks; the hook for the FrankenThreeD route and its explicit-failure and fallback
behaviour; how the bundle is handed to the packet writer; the supply-chain facts recorded for the vendored
library.
Out: the page's code (N32b-10 to -12, N32b-40); the packet writer in `frob-chronicle` and its size rule for
payload blocks; measuring INT-F3D-01 (BD-300); the gate on complete packets (N32b-43).

## Technical approach

**1. Plain route (always built).** `node viewer/build/pack.mjs --out viewer/dist/page.html` does, in order:

1. Verify `viewer/vendor/three-r186/three.module.min.js` against `vendor.lock` (length and both hashes). Mismatch:
   stop.
2. Resolve the page's ES modules in a fixed order (lexicographic by path after the entry module) and concatenate
   them with the vendored library into one inline module script. No minifier is required for correctness; a
   pinned minifier may be used, and its version is part of the bundle's recorded inputs. Only the overlays and
   Three.js modules the page imports are included (the library is used in its tree-shakeable module form).
3. Inline the styles. Emit one HTML document: doctype, the content security policy meta element, a `<main>` root,
   the inline style, the inline script, and a placeholder comment `<!--FROB-PACKET-BLOCKS-->` where the packet
   writer inserts its header and data blocks.
4. Write the bundle and a manifest `page.manifest.json`: byte length, BLAKE3 and SHA-256 of the bundle, the list
   of input files with hashes, the Three.js release, tool versions, and the feature list the page uses (WebGL 2
   calls and, if present, WebGPU entry points).

Determinism: no timestamps, no absolute paths, no random identifiers; the same inputs give the same bytes on
Linux and macOS. The manifest's digest is recorded by the packet writer as the exporter's page identity.

**2. Size checks.** The build fails if the bundle exceeds 600,000 bytes (TARGET), printing a table of bytes per
input module, largest first. A second check, applied by the export verb on the finished file, enforces the
whole-file caps (8 MiB default for packets; 15 MB absolute ceiling for any exported replay). The 600,000-byte
figure is tight for a 3D library: the bundle includes only what the page imports, and the size table is the tool
for keeping it so. If the page cannot be held to the budget, that is one of the two triggers of the packet's kill
gate (KILL-REPLAYPACK, decided in N32b-32); this build step reports the number and never silently drops features
to fit.

**3. Hand-off to the packet writer.** `viewer/dist/page.html` and `page.manifest.json` are committed to the
repository (a generated file, changed only by running `pack.mjs`, and reviewed as such), so that building any
Rust crate needs no Node: the Node tooling stays development-only and outside every Cargo build graph. A check
(`node viewer/build/pack.mjs --verify`, run by the tests below and in continuous integration) rebuilds the bundle
from its inputs and fails if the bytes differ from the committed file. `frob-chronicle` embeds the committed file
at compile time as `viewer_page::BYTES` with `viewer_page::LEN` and `viewer_page::MANIFEST_DIGEST`; a compile-time
check fails the build if the embedded bytes' BLAKE3 differs from the committed manifest's. The writer
(N24a-41) uses `LEN` in its size computation, never the budget, and reports the page digest in each export
envelope.

**4. FrankenThreeD route (optional).** `node viewer/build/pack.mjs --route f3d` runs, as a subprocess at the
pinned revision of the sibling repository, `node tools/ingest/cli.mjs app.html --build-app out --pack-html
replay.html`, on the unpacked page. Rules: (a) the route is attempted only when the manifest's feature list is
inside the admitted subset recorded for that revision; (b) an unadmitted feature must make the subprocess fail
explicitly; the build then falls back to the plain bundle and records the reason in the manifest
(`route: "plain", f3d_refused: "<feature>"`); (c) the route's output is used only after INT-F3D-01 has a recorded
pass for the revision; until then the route is built for comparison and not shipped; (d) the subprocess gets a
copy of the inputs in a scratch directory and no access to the state root.

**5. No network.** The bundle contains no absolute URL outside data URIs and a short allow-list of licence
texts. A build-time scan and a run-time test (driver with networking disabled, request log empty) both check it.

**6. Licences.** Three.js is MIT-licensed; its notice is embedded in the bundle as a comment and listed in the
manifest, so every exported replay carries it.

## Acceptance criteria

- [ ] `viewer/dist/page.html` is produced, is at most 600,000 bytes, and two builds on two platforms are
      byte-identical (digest recorded in the manifest).
- [ ] A changed byte in the vendored library, or a `vendor.lock` mismatch, stops the build.
- [ ] The bundle contains no fetchable URL; opened with networking disabled, the driver's request log is empty.
- [ ] A page deliberately grown past 600,000 bytes fails the build with the per-module size table.
- [ ] With `--route f3d` and a page using an unadmitted feature, the subprocess fails explicitly, the plain bundle
      is produced, and the manifest records the refused feature.
- [ ] `frob-chronicle` embeds the committed bundle and exposes its real length and manifest digest; a bundle that
      differs from its manifest fails the Rust build, and `pack.mjs --verify` fails on a stale committed bundle.
      (That every export envelope reports them is the writer's, N24a-41, checked end to end by N32b-40.)
- [ ] `xtask check-deps` shows no crate of the sibling renderer in any Cargo graph.

## Test plan

### Unit tests
`viewer/tests/pack.test.mjs` and `crates/frob-chronicle/tests/page_embed.rs`:
- `pack_is_deterministic`: two runs, equal bytes; with the input file order shuffled on disk, equal bytes.
- `pack_has_no_timestamp_or_path`: the bundle contains no build date and no home directory string.
- `vendor_mismatch_stops_build`.
- `size_budget_enforced`: a 600,001-byte bundle fails; 600,000 passes.
- `no_external_urls`: scan for `http:`, `https:` and protocol-relative references outside the allow-list.
- `placeholder_present_once`: exactly one `<!--FROB-PACKET-BLOCKS-->`.
- `f3d_unadmitted_feature_falls_back` (run only where the sibling checkout is present; otherwise reported
  `not run` with the reason, never as a pass).
- `embedded_page_digest_matches_manifest` (Rust side).
- `verify_detects_stale_bundle`: a committed bundle built from an older module fails `--verify` naming the
  module.
- `cargo_build_needs_no_node`: `frob-chronicle` builds with `node` absent from the path.

### End-to-end script and logging
`scripts/e2e/viewer_pack.sh` (header `bead=N32b-13 milestone=M2 labels=tether,suite seed=13 needs=cpu
plants=grown-page,build-time-stamp,public-font-url,f3d-silent-partial`, each plant one negative control below,
the fourth run only where the sibling checkout is present; owned here, rerun as steps
`pack-*` by N32b-14's `viewer_overlays.sh`): build the bundle twice, compare digests with each other and with the
committed manifest (`--verify`); open it in both pinned browsers of N32b-44 with networking disabled and check the
request log; run the build-time URL scan; build `frob-chronicle` and read back `viewer_page::LEN` and
`MANIFEST_DIGEST` through its test binary; run the grown-page and unadmitted-feature controls (the second only
where the sibling checkout is present, otherwise logged `not run` with the reason). It sources the STD-E2E helper
and writes `target/e2e-logs/viewer_pack/<utc>.ndjson` and a transcript; each line has `ts`, `script`, `bead`,
`step`, `event`, the exact command line, exit code, wall time, bundle bytes against 600,000, the per-module size
table, external requests against 0, the two build digests and the manifest digest, the browser name, version and
hash, the route taken and any refused feature, and on failure the first differing byte offset or the offending
URL with the artifact paths; then a `summary`. The check that an exported replay embeds this bundle (digest in the
export envelope equal to the manifest's) needs the writer and is a step of N32b-40's script.

### Known answers and negative controls
- Known answer: with a 600,000-byte page inside an 8,388,608-byte file, the binary payload may be at most
  (8,388,608 − 600,000) × 3/4 = 5,841,456 bytes; the writer's figure must use the real page size instead of
  600,000 when the page is smaller.
- Negative control: a page grown past 600,000 bytes; the size check fails with the per-module table.
- Negative control: a bundler that stamps the build time; determinism fails.
- Negative control: a page importing a font from a public URL; the scan and the offline run fail.
- Negative control: a route wrapper that, on an unadmitted feature, silently ships the route's partial output;
  the fallback test fails.

## Considerations

- RISK-19: the viewer drifts outside the sibling renderer's admitted subset. Likelihood low; signal: INT-F3D-01;
  mitigation: the plain bundle is the fallback and is always built. The sibling route changes rendering cost
  only, and rendering is outside every claim the project makes.
- An upstream work item exists to relax an exact `serde_json` pin in the sibling; it matters only if its crates
  were ever linked, which this design forbids.
- The minifier is a supply-chain input of every exported file. It is pinned by hash and listed in the manifest;
  building without it is supported and is the reference for the determinism test.
- A native viewport on the Mac would bypass this packaging entirely; none is funded.
