## Background

The design studio of FrankenRobotics is one loop: an agent makes a robot design, the system checks it and
proposes repairs, a controller is synthesized, a run is estimated and executed, a failure is explained and
looked at, the design is edited, old and new are compared on paired worlds, and the winner is promoted to the
trusted tier. The surface chapter writes this loop down as a session of thirteen commands. This bead turns that
session into an end-to-end script that drives the real `frob` binary, so that the loop is known to work as a
whole before any agent is asked to perform it.

It complements two other things. The fresh-agent test (GATE-TETHER-01: a fresh agent given only the generated
documentation completes 20 scripted studio tasks with at least 18 correct and no budget violation; seed BD-313)
measures whether an agent can *find* the loop. This script measures whether the loop *exists*: if it fails, the
agent test is not worth running. The same transcript is one of the worked examples from which the agent
documentation is generated (N32b-17), so script and documentation cannot drift apart unnoticed.

The numbers printed in the written session are illustrative (a mass of 15.1 kg, a success rate of 0.44, an
e-value of 310). The script therefore asserts structure and rules, never those values: exit codes, the presence
and consistency of envelope fields, accounting identities, and the principles of the surface (every answer says
what changed; estimates never run physics; budgets fall by what was charged; evidence labels move only by
promotion).

## Scope

In: `scripts/e2e/session_studio.sh`; its two lanes (any host on `batch-cpu`; a CUDA host at the written scale);
the planted first finding; assertions per step; its log.
Out: the verbs themselves; the agent test (BD-313); the mission session (N32b-16). The documentation seed BD-313
names a wrapper `scripts/e2e/worked_sessions.sh` that runs both worked sessions; this script is the studio half
it calls, and the per-step assertions specified here are that half's content.

## Technical approach

Setup: temporary state root; `frobd` started; one session opened with scopes `design:read, design:write,
control:run, sim:read, sim:run, telemetry:read, explain:read, eval:run, predict:write` (as the catalogue names
them) and a budget; the token exported to the environment. Every `mutate` and job-submitting call carries
`--key`; the written session omits keys for brevity, and the surface refuses a missing key, so one extra step
checks exactly that.

| # | Command (lane values in brackets) | Asserts |
|---|---|---|
| 0 | `frob design new quad-a --template quadruped-12dof --json` without `--key` | Exit 3, `FROB-REF-805` |
| 1 | `frob design new quad-a --template quadruped-12dof --key d1 --json` | Exit 0; `result.design` is a content address; `bound` echoes it |
| 1b | `frob design edit quad-a swap-actuator --joints '*.knee' --to <small card> --key d1b --json` | Exit 0 (plants an undersized knee) |
| 2 | `frob design check quad-a --json` | Exit 2; a finding of the actuator-envelope analysis on the knee with severity, a message with a percentage, and at least one ranked repair that is a typed edit with predicted effects; `next_actions[0].command` is a runnable `frob design edit …` line |
| 3 | The first repair, executed verbatim from `repairs[0]` with `--key d3` (`swap-actuator … --to qdd-l`) | Exit 0; a new design version; the symmetry report says the group is preserved; `expected_parent` was the previous head |
| 4 | `frob design check quad-a --json` | Exit 0; closure `closed`; a mass with unit; the knee finding gone |
| 5 | `frob control synth quad-a --key c5 --json` | Exit 0 or 2; a gait with its source named; three-outcome reporting present |
| 6 | `frob sim estimate quad-a --scene terrain:stairs@0.4 --worlds 2048 [64] --seconds 20 --tier gpu-cuda [batch-cpu] --json` | Exit 0; point estimate with a 90% interval, lower ≤ point ≤ upper, or the mark `uncalibrated`; memory and disk; `cost.gpu_s = 0`; the ledger shows no new job |
| 7 | `frob predict register --metric success --interval 0.6 0.9 --confidence 0.8 --for next --key p7 --json` | Exit 0 where implemented; otherwise exit 5 `FROB-REF-724` with `first_milestone` shown |
| 8 | `frob sim run quad-a --scene terrain:stairs@0.4 --worlds … --seconds 20 --tier … --key r8 --json` | Exit 0 or 2; a run identifier; success rate with its denominator; evidence label `provisional`; `budget` left fell by `cost`; terminal counts (completed, failed, refused, unstarted) sum to the planned worlds |
| 9 | `frob explain run <run> --budget 600 --json` | Exit 0 or 2; a first cause with the channel and statistic that support it; the answer fits the 600-token budget and carries handles for drill-down |
| 10 | `frob telemetry stills <run> --world <a failing world> --at failure --json` | Exit 0; an image artifact handle; three frames at −0.5 s, 0 s and +0.2 s around the terminal event |
| 11 | `frob design edit quad-a set-param foot.radius 0.022 0.030 --key d11 --json` | Exit 0; a new version; the edit's inverse is recorded |
| 12 | `frob eval compare quad-a@prev quad-a --task stairs-0.4 --key e12 --json` | Exit 0 or 2; per metric a verdict from {`settled`, `tied`, `inconclusive`, `incomparable`, `infeasible`}; an e-value; pairs used ≤ the cap (96); the five pair counts sum to the planned pairs; the first divergent event; the change between the two versions echoed (`set-param foot.radius`); label `provisional` |
| 13 | `frob eval promote <result> --tier referee --key m13 --json` | Exit 0 or 2; the label is `established` only if the referee result lies inside the frozen envelope, otherwise it stays `provisional` with the reason; the evidence block's tier is the referee's |

Rules asserted across all steps:

1. With `--json`, exactly one envelope on standard output per call (progress events, if any, precede it as
   separate lines); exit code 1 never occurs.
2. `bound` holds immutable identifiers for every mutable name used; `quad-a@prev` and `quad-a` resolve to
   different addresses after step 11.
3. Every envelope has an `evidence` block; no step's class exceeds `Tested`; `reality` is `no-claim` throughout.
4. The session's remaining budget after the script equals the opening budget minus the sum of `cost` over
   charged steps (to the unit), and `frob session show` agrees.
5. Re-running step 8 with the same key and arguments returns the stored result with `idempotent_replay: true`
   and no new charge.
6. A bounded wait: step 8 with `--sync-wait-ms 0` returns exit 8 with a job handle whose `progress` has a
   denominator; `frob job wait` then returns the same result as the unbounded call.

Lanes. `cpu`: 64 worlds on `batch-cpu`, runs on any host. `cuda`: 2,048 worlds on `gpu-cuda`, runs only where a
CUDA device passes `frob spark check`; otherwise reported `not run` with the reason. Seeds are explicit and
logged; the script is idempotent (fresh state root each run).

## Acceptance criteria

- [ ] `scripts/e2e/session_studio.sh --lane cpu` exits 0 on a correct build; every row's assertions hold.
- [ ] The `cuda` lane passes on the Linux host, or is recorded `not run` with the device reason.
- [ ] Step 7 behaves as specified on both sides of the milestone at which `predict.register` lands.
- [ ] The budget identity of rule 4 holds to the unit, and rule 5 shows no double charge.
- [ ] The transcript produced by the script is the source of the studio worked example in the agent documentation
      (a generated-file check compares them).
- [ ] Each planted defect below makes the script exit non-zero at the named step.

## Test plan

### Unit tests
None of its own beyond the helper: `crates/frob-conformance/tests/session_assertions.rs` checks the assertion
library on stored envelopes (`one_envelope_rule`, `pair_counts_sum`, `terminal_counts_sum`,
`budget_delta_equals_cost`, `estimate_interval_ordered`), each with a passing and a failing stored input.

### End-to-end script and logging
`scripts/e2e/session_studio.sh`. Log: `target/e2e-logs/session_studio/<utc-timestamp>.ndjson` and a
human-readable transcript beside it (the transcript is what the documentation embeds). Every line has `ts`,
`script`, `bead`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line
with the token redacted, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed), measured values with units and thresholds (estimate and interval against the charged cost;
pairs used against the cap; counts against planned; budget before and after), digests where state is compared
(design versions, the replayed result), and on failure the first differing value with the paths of the envelope
and the state root copy. The `summary` line gives assertions passed and failed and names GATE-TETHER-01 as the
gate this script is a precondition for (it does not record it).

### Known answers and negative controls
- KA-757: a_only + b_only + both + neither + unscored = planned, on the comparison of step 12.
- KA-766: completed + failed + refused + unstarted = planned, on the run of step 8.
- Planted defects (test builds): (1) an estimate verb that creates a job: step 6 fails on the ledger check;
  (2) a promote that labels a result `established` without a referee run: step 13 fails on the evidence tier;
  (3) a repair whose printed command does not parse: step 3 fails; (4) a run that charges twice on replay: rule 5
  fails; (5) a compare that reports a percentage with no pair counts: step 12 fails.
- Metamorphic relation: running the script with a different session budget changes only budget fields.
- Determinism lanes: twice on one machine (equal digests of designs and runs under the same seeds); debug and
  release; Linux and macOS on the `cpu` lane; the `cuda` lane against its determinism class.

## Considerations

- The written session shows `design check` flagging the stock template's knee; whether the stock template
  really has that defect is a property of the catalogue, not of the surface, so the script plants the defect with
  a typed edit and does not depend on it.
- The illustrative e-value and success rate must never be asserted; a future drafter tempted to "tighten" the
  script with them would turn an end-to-end test into a physics regression test with no derivation behind it.
- The 600 in step 9 is a token budget for the summary, not a compute budget.
- If the comparison's verdict is `inconclusive` on the small lane, step 13 promotes the run of step 8 instead;
  the rules about labels are the same.
