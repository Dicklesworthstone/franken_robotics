## Background

The second way to use FrankenRobotics is to ask a mission query instead of scoring one design: "which designs in
this family can deliver and place this payload in every admitted world, and which provably cannot?" The system
answers with an *inner* set (cells of the design family, each with a constructive witness that every design in
it meets the mission), an *outer* set (what has not been excluded), exclusions with witnesses, and unresolved
cells. The agent then picks a cell, makes a design, attacks it with adversarial worlds, shrinks a failure to a
minimal counterexample world, intervenes to find the cause, edits, revalidates what the edit left standing,
qualifies the result in the blinded lane, bundles the certificates and has the offline auditor check them.

The surface chapter writes this as a session of twenty commands. This bead is that session as an end-to-end
script on the real binaries. It is the precondition for the fresh-agent mission test (GATE-TETHER-13: 10 scripted
mission tasks with at least 9 correct, no budget violation, no instruction taken from a poisoned import; fourth
milestone; seed BD-373), in the same way that the studio script precedes the studio agent test.

Four points of the written session are rules, not illustrations, and the script asserts each:

1. The inner set contains only cells with a constructive witness, so the agent tests a cheaper *unresolved* cell
   instead of trusting it.
2. A rollout that fails refutes one controller, not the design, and the envelope says so.
3. The qualification arithmetic is exact (below).
4. The discovery scopes in the token give no way to read the sealed worlds.

All other printed numbers (412 cells, 640 GPU-seconds, 60 of 64 forks) are illustrative and are not asserted.

## Scope

In: `scripts/e2e/session_mission.sh`; its lanes; assertions per step; the exact qualification arithmetic; its
log.
Out: the verbs; the agent test and its poisoned-import arm (BD-373); `solve.run` (BD-372). The documentation seed
BD-313 names a wrapper `scripts/e2e/worked_sessions.sh` that runs both worked sessions; this script is the
mission half it calls.

## Technical approach

Setup: temporary state root; before `frobd` starts, two grants written with `e2e_session grant` (STD-E2E item
17; a root token is minted only from a principal's grant, N32b-01): `agent`, with the seventeen scopes and the
two budget amounts of step 1 in the grant's form (`gpu:seconds=1800`, `cpu:core_seconds=7200`), and `owner`,
with `qual:admin` and `eval:read` (the owner's session of BD-261, as N32b-01's open point on the owner's session
defines it); `frobd`; the owner helper opens the owner's session (`e2e_session open own --principal owner
--scopes qual:admin,eval:read`) and with it the qualification campaign of the claim family the mission's
requirement resolves to (`frob eval ledger --action open --task <the mission's task> --world-family <its
family> --json`, an admin action with no key), which it closes at the end (`frob eval ledger <campaign> --action
close --json`); the agent session is step 1, opened through `e2e_session open s1 --principal agent …` with no
token in its environment and its token exported (the helper keeps it out of every log and transcript). Step 1
names `--principal agent`, which the written session omits: two principals are granted here, and a root call
without `principal` would then be `FROB-REF-802`. Every key is written `--key "$(e2e_key <label>)"` with the
label the table shows. The written session's six scopes do not cover its own
later commands under the verb registry, so step 1 adds exactly what the registry rows require: `mission:write`
(`mission new`), `mission:read` (`mission check`, `mission show`), `job:read` (`job wait`), `result:run` (`result
revalidate`), `cert:write` (`prove bundle`), and, for rule 4, the read and run scopes of every verb the rule
calls (`telemetry:read`, `run:read`, `run:run`, `autopsy:read`, `explain:read`, `artifact:read`; `sim:run` is
already held). Holding them is what makes rule 4 a test of the firewall: a refusal there can then only be
`FROB-REF-840`, never a missing scope.

**Rule 3: the qualification arithmetic.** Requirement: failure probability at most p₀ = 0.05. Total error budget
α = 0.05; submission i receives αᵢ = α / [i·(i + 1)], so α₁ = 0.025 and α₂ = α/6 = 0.008333…. With n = 200 sealed
worlds and k failures, the one-sided exact binomial (Clopper–Pearson) upper bound at level αᵢ is the p that
solves Σ_{j=0..k} C(n, j)·pʲ·(1 − p)ⁿ⁻ʲ = αᵢ; the design qualifies when that bound is at most p₀.

| k failures of 200 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| Upper bound at α₁ = 0.025 | 0.0183 | 0.0275 | 0.0357 | 0.0432 | 0.0504 |
| Upper bound at α₂ = 0.05/6 | 0.0237 | 0.0337 | 0.0425 | 0.0505 | 0.0582 |

So the first submission can qualify with at most 3 failures and a second with at most 2: each retry costs power,
by design. For k = 0 the bound has the closed form 1 − αᵢ^(1/n): 1 − 0.025^(1/200) = 0.018275. Step 17 must print
`alpha_1 = 0.025`, `units = 200` and "qualified is reachable only with at most 3 failures"; the script recomputes
the table with exact rational binomial sums and bisection and compares to four decimals.

**Rule 4: sealed worlds.** After step 18 the script calls, with the agent's token, `telemetry query`, `run show`,
`sim replay`, `run fork`, `autopsy show`, `explain run`, `telemetry stills` and `artifact read` on the
qualification run and on an address guessed from the receipt: each is refused with `FROB-REF-840`, and a
`FROB-REF-720` on any of them fails the step as "did not reach the firewall"; the receipt lists what stays sealed
until the campaign closes; no world address or per-unit outcome appears in any envelope
or log.

Lanes. `cpu`: a small mission instance and `batch-cpu` budgets (`cpu_core_s` in place of `gpu_s`), any host.
`gpu`: the written budgets on the Linux host; recorded `not run` elsewhere. Seeds explicit and logged.

## Acceptance criteria

- [ ] `scripts/e2e/session_mission.sh --lane cpu` exits 0 on a correct build with every row's assertions holding.
- [ ] The four rules are each asserted by a named step and each fails on its planted defect.
- [ ] The dry-run arithmetic equals the table to four decimals and spends no level; the real submission records
      index 1 and level 0.025.
- [ ] `frob-verify` accepts the bundle offline and rejects it after one byte is flipped.
- [ ] The session's budget identity holds: opening budget − Σ cost = `session show` left, per unit.
- [ ] The transcript is the source of the mission worked example in the agent documentation.

## Test plan

### Unit tests
`crates/frob-conformance/tests/qualify_arithmetic.rs`:
- `alpha_schedule`: αᵢ for i = 1..4 at α = 0.05 are 1/40, 1/120, 1/240, 1/400 exactly; partial sums α·n/(n + 1).
- `exact_bound_table_alpha1`: 0.0183, 0.0275, 0.0357, 0.0432, 0.0504 for k = 0..4.
- `exact_bound_table_alpha2`: 0.0425 at k = 2 and 0.0505 at k = 3.
- `closed_form_k0`: 1 − 0.025^(1/200) = 0.018275 to six decimals.
- `admissible_failures`: at most 3 at α₁, at most 2 at α₂.
- `cell_accounting`: inner + excluded + unresolved = total on stored answers.

### End-to-end script and logging
`scripts/e2e/session_mission.sh` (header: `bead=N32b-16 milestone=M4 labels=tether,mission,session seed=16
needs=cpu,frobd
plants=inner-without-witness,search-refutes-design,wald-bound,failed-worlds-list,sealed-artifact-read,flag-absent,no-telemetry-scope`,
the seven planted defects below in order, so that the runner's `--verify-plants` can run each; the `gpu` lane is
an `e2e_skip` with the device reason on a host without the device). Log:
`target/e2e-logs/session_mission/<utc-timestamp>.ndjson` plus a transcript. Every line: `ts`, `script`, `bead`, `step`, `event`, the exact command line (token redacted), exit
code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, identities, seed), measured
values with units and thresholds (cell counts and their identity; job progress with denominator; the bound table
against the recomputed one; inherited and rerun counts; budget before and after), digests where state is
compared (the bundle, the receipt), and on failure the first differing value with artifact paths. The `summary`
line names GATE-TETHER-13 as the gate this script is a precondition for. Sealed data never enters the log: the
script logs refusal codes for the sealed-read attempts and nothing else.

### Known answers and negative controls
- KA-762: exact binomial bound, 200 worlds, α = 0.025: 0.0183, 0.0275, 0.0357, 0.0432, 0.0504 for 0 to 4
  failures. KA-760: Σ αᵢ = α·n/(n + 1) < α.
- Planted defects: (1) an inner set that includes a cell with no witness: step 7 fails; (2) a `nemesis search`
  envelope that says the design is refuted: step 11 fails; (3) a dry run that uses a normal (Wald)
  approximation, p̂ + 1.96·√(p̂·(1 − p̂)/n): bounds 0.0318 at k = 3, 0.0466 at k = 5 and 0.0536 at k = 6, so it would
  admit up to 5 failures instead of 3: step 17 fails; (4) a qualify envelope with
  a `failed_worlds` list: step 18 fails; (5) a sealed run readable through `artifact read`: rule 4 fails; (6) a
  bundle whose flag is absent: step 20 fails (absence is not read as false); (7) a script run whose session lacks
  `telemetry:read`: rule 4 reports `FROB-REF-720` for `telemetry query` and the step fails instead of passing
  vacuously.
- Determinism lanes: twice on one machine (equal query, answer and bundle digests under the same seeds); both
  platforms on the `cpu` lane; `frob-verify` on a machine with neither the daemon nor a GPU.

## Considerations

- Whether a mission synthesis that stops on budget with certified cells exits 2 or another code is an open
  question of the mission subsystem with the default "exit 2 with `resolution-unmet`"; the script accepts 0 or 2
  at step 6 and records which.
- The script consumes one level of a real error budget on a synthetic campaign; the campaign is created and
  closed by the helper so that no production campaign is touched.
- The written session's step numbering omits keys on some mutating calls; the script supplies them everywhere,
  because a missing key is refused. Where the written session's spelling is illustrative and the registry row
  differs, the script uses the row: `nemesis search` takes `--task` and `--legality` as the row requires and adds
  the session's `--mission` (the option of BD-273 that confines the search to the mission's world family);
  `eval qualify` is called in the session's own mission-bound form, which BD-259 defines and the row carries;
  the edit's value has its unit and `--expected-parent`; and a `run fork` precedes the intervention, whose
  input is a fork handle.
