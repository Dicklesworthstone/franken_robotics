## Background

An agent arriving at FrankenRobotics knows nothing about it. What it reads first decides whether it finds the
design loop or wanders. The command `frob robot-docs` is that first reading: it prints the guide, the verbs, the
schemas and worked examples, and with `--cluster` it prints one task cluster. Two acceptance gates hand a fresh
agent *only* this output and score what it can then do (20 studio tasks with at least 18 correct; 10 mission
tasks with at least 9 correct), and a third scores diagnosis. The documentation is therefore a product surface
with a measured outcome, not a manual.

Two design decisions (DESIGN) shape it.

- *Generated, never written twice.* The verb registry (`registries/verbs.toml`) defines each verb once: name,
  cluster, kind, capabilities, schemas, refusals, idempotency rule, cost model, examples, task clusters. The
  command line, the MCP tools, the schemas and this documentation are all generated from it. Hand-written prose
  exists only as registry fields and as a small set of guide pages kept beside the registry; nothing is authored
  in a second place. Reason: documentation that can disagree with the surface will, and an agent cannot tell
  which is right. Rejected: a hand-maintained guide checked by review.
- *Sized for a context window.* The registry holds about 243 verbs (163 found mechanically in the plan's inventory,
  55 named by chapters and 25 further `analyze` verbs; the registry's own count is authoritative). Printing all of
  it would exhaust an agent's
  context before it acted. Output is therefore layered (guide, then cluster, then verb) and each layer is sized
  to a stated token budget with handles for drill-down. The same reasoning limits a task cluster to seven tools.

Known risk this serves (risk register): the agent surface is too large and agents get lost; signals are failures
of the two agent gates and serial turns per accepted answer; the mitigations are clusters of at most seven
tools, `session.focus`, `next_actions` and this guide.

## Scope

In: the documentation source model; the generator; the `robot-docs` verb (registry entry, options, output
schema); the guide pages and their order; layering and token budgets; the compact encoding; worked examples
drawn from end-to-end transcripts; the generated-file check.
Out: the skill file, the MCP resource and prompt texts generated from the same model (N32b-18); the operator
verbs `capabilities`, `schema`, `doctor` (N32b-19, N32b-20); registering MCP resources and prompts (seed BD-298,
with N32a-25 and N32a-26); the fresh-agent tests (seeds BD-313, BD-373). Layering with the seeds: the first form
of the verb and its generator arrives with the registry skeleton (seed BD-022); this bead is the generator and
the layered, budgeted output at the first milestone's verb set; seed BD-313 completes the guide's content for
the full registry and measures it with the studio agent gate.

## Technical approach

**1. Source model** (`frob-verbs::docs`, built from the static registry table at compile time).

```rust
// DESIGN: intent, not signatures.
struct DocModel { guide: Vec<GuidePage>, clusters: Vec<ClusterDoc>, verbs: Vec<VerbDoc>, examples: Vec<Worked> }
struct GuidePage { id: &'static str, order: u16, title: &'static str, body: Markdown, source: PageSource }
struct ClusterDoc { name: &'static str, activity: &'static str, tools: Vec<VerbRef> /* ≤ 7 */ }
struct VerbDoc { name, kind, purpose /* one sentence */, when_to_use, cost_class, capabilities, input_schema,
                 output_schema, refusals: Vec<RefusalRef>, examples: Vec<&'static str>, first_milestone,
                 task_clusters, per_surface_defaults }
struct Worked { id: &'static str, title: &'static str, steps: Vec<Step /* command, exit, one-line outcome */> }
```

`VerbDoc` fields come from the registry entry and nowhere else. `purpose`, `when_to_use` and `cost_class` are
registry fields (a lint requires them, bounded in length). `Worked` examples are generated from the transcripts
of the end-to-end session scripts (the studio session, N32b-15, M3; the mission session, N32b-16, M4), committed
by those scripts under `docs/agents/transcripts/`, so an example is a run that passed. Before a transcript exists
(at this bead's milestone neither does), its page names the session, its script and its first milestone and
says it is not yet available in this build; no transcript is ever written by hand (fail-closed).

**2. Guide pages**, in this order (each a file under `registries/docs/`, registered by a `[[guide_page]]` row so
that other subsystems can contribute pages without editing this crate):

1. `reader-map`: what to read for which task, as a table from task to task cluster to first command. Always the
   first page.
2. `how-to-ask`: verbs are questions with budgets; the five things never implicit (units, seeds, budgets,
   versions, capabilities); the envelope and its fields; `next_actions`.
3. `exit-codes-and-refusals`: the exit table (0, 2, 3, 4, 5, 6, 7, 8, 9; 1 is never deliberate), the three failure
   classes (domain, protocol, transport) and what to do in each: read `refusal.repairs`; fix the call; never
   resubmit blindly, call `job.find` with the idempotency key.
4. `long-work`: idempotency keys, the bounded synchronous wait (`sync_wait_ms`, exit 8, `job.wait`), progress
   with denominators, cancellation that drains.
5. `evidence`: the seven claim kinds, the four evidence classes, `provisional` against `established`, the
   `reality: no-claim` line, the three no-authorization flags.
6. `clusters`: the task-cluster directory.
7. Worked sessions: the studio session and the mission session.
8. Contributed pages (for example a machine role table), in registered order.

**3. The verb.** `frob robot-docs [--cluster <name>] [--verb <name>] [--budget <tokens>] [--encoding plain|compact]
[--json]`. Kind `read`; no capability required (registry `capabilities = []`; DESIGN: the orientation verbs
must answer any session, because an agent cannot learn which scopes to ask for without reading them; the
registry row of record, VERBS-operator (a dependency), registers `capabilities = []` with `public = true` and the
inputs `--cluster`, `--verb`, `--budget <tokens>` and `--encoding`; this bead serves that row and enters no second
one); task cluster `orient`. `--budget` here counts tokens of output: `robot-docs` is a `read` verb, whose kind
carries no compute-budget property, so the name does not collide with the common `budget` of `run` verbs.

- No option: the guide pages, then the cluster directory (one line per cluster: name, activity, tool names).
  Default budget 4,000 tokens (TARGET).
- `--cluster <name>`: that cluster's activity and, per tool, purpose, when to use, cost class, required scopes,
  the refusal codes with one-line meanings, and one example. Default budget 2,500 tokens (TARGET).
- `--verb <name>`: the long form: all of `VerbDoc`, the schemas' field tables, every example. This is also the
  body of the MCP resource for that verb.
- `--json`: the envelope's `result` holds the model slice as structured data plus `rendered` text.

**4. Token budget.** Tokens are estimated as ⌈UTF-8 bytes ÷ 4⌉ (a declared estimate; no tokenizer is linked). The
renderer fills the budget in priority order (reader map, how to ask, exit codes, clusters, then the rest); what
does not fit is replaced by a handle line of the form `more: frob robot-docs --verb design.check` or `more: frob
robot-docs --cluster simulate`. Output is never cut mid-item: an item is either whole or a handle, and the last
line states `shown <a> of <b> items; budget <n> tokens`. `--encoding compact` uses the suite's compact
table encoding for the cluster and verb tables.

**5. Hygiene of content.** No text that originated in an import ever enters the model (design names, asset
metadata and the like are never documentation); the generator's inputs are registry files and transcripts of
runs on built-in fixtures only (invariant INV-TETHER-13, enforced with N32b-18). Refusal one-liners come from the
refusal registry.

**6. Generated-file check.** The rendered guide is also written to `docs/agents/ROBOT_DOCS.md` by the generator;
`xtask check-generated` regenerates and fails on any difference.

## Acceptance criteria

- [ ] `frob robot-docs` prints the reader map first and stays within 4,000 estimated tokens; `--cluster author`
      lists exactly the registry's tools for `author`, each with purpose, cost class, refusals and one example.
- [ ] For every verb in the registry, `--verb <name>` exists and lists every refusal code of the entry with the
      registry's exit code.
- [ ] Every example line printed by any layer parses as a valid invocation of its verb (checked by running each
      through the argument parser in a dry mode).
- [ ] A change to a registry entry changes the output; no hand-edited file can change it (generated-file check).
- [ ] With `--budget 800`, output ends with the shown-of-total line and contains only whole items and handles.
- [ ] The worked-session pages are generated only from transcripts committed by the session scripts; with none
      committed they name each session, its script and first milestone and contain no transcript; with a planted
      transcript fixture (labelled `synthetic`) the page equals it step for step.
- [ ] The `robot-docs` registry row lists no capability, and the verb answers a session holding no scope.
- [ ] The verb is reachable as the MCP tool `robot_docs` with identical content (parity diff empty).

## Test plan

### Unit tests
`crates/frob-verbs/tests/robot_docs.rs`:
- `model_built_from_registry_only`: the model's verb set equals the registry's; a verb entry with an empty
  `purpose` fails the registry lint.
- `reader_map_first`.
- `cluster_layer_matches_registry`: for each task cluster, tool names equal the registry assignment; at most 7.
- `examples_parse`: every example of every verb parses.
- `refusals_listed_with_exit`: for every registered verb, `--verb <name>` lists exactly its full refusal list (its
  chapter codes plus the codes appended for its kind), each with the refusal registry's exit; `doctor`, whose
  chapter list is empty, lists only its appended codes (802 with exit 3, 724 with exit 5, and the rest of its kind's).
- `budget_whole_items_only`: budgets of 400, 800, 2,500 and 4,000 tokens: estimated size ≤ budget; no item is
  truncated; handles resolve to valid commands.
- `token_estimate_rule`: a 4,001-byte text counts 1,001 tokens.
- `compact_encoding_roundtrip`: the compact table decodes to the same rows.
- `no_import_text_in_model`: the generator rejects an input string of the untrusted type at compile time (a
  compile-fail test) and at run time for transcripts (a transcript containing a non-fixture design name fails).
- `generated_file_in_sync`.
- `worked_pages_only_from_transcripts`: with no transcript the page holds the placeholder and no command lines;
  with a synthetic transcript fixture the page lists its steps in order with exit codes; a hand-added step in
  `registries/docs/` fails the generator.
- `no_scope_required`: the registry row of `robot-docs` has `capabilities = []`; when tokens exist (from M2), a
  session opened with no scopes receives the guide (exit 0).

### End-to-end script and logging
`scripts/e2e/robot_docs.sh` (header `bead=N32b-17 milestone=M1 labels=tether,verb`): runs `frob robot-docs`,
`--cluster` for every cluster, `--verb` for every verb, and `--budget 800`; extracts every example and every
`more:` handle and executes each with `--estimate` or a dry parse; compares CLI output with the MCP tool's over
stdio; runs `xtask check-generated` on `docs/agents/ROBOT_DOCS.md`. It sources the STD-E2E helper and writes
`target/e2e-logs/robot_docs/<utc>.ndjson` and a transcript; each line has `ts`, `script`, `bead`, `step`,
`event`, the exact command line, exit code, wall time, the envelope's `evidence` block, estimated tokens against
the budget, examples parsed against the total, handles resolved against the total, the digest of each rendered
layer (CLI and MCP), and on failure the first failing example or the first differing line with its layer; then a
`summary` naming GATE-TETHER-02.

### Known answers and negative controls
- Known answer: the cluster `orient` lists `capabilities`, `doctor`, `robot_docs`, `schema`, `design_templates`,
  `scene_list`, `session_show` (seven tools) plus the three base tools named separately.
- Negative control: a registry entry given an eighth tool in a task cluster: the lint fails.
- Negative control: an example with a misspelt flag: `examples_parse` fails.
- Negative control: a renderer that truncates at the byte budget: `budget_whole_items_only` fails.
- Negative control: a hand edit of `docs/agents/ROBOT_DOCS.md`: the generated-file check fails.

## Considerations

- The ⌈bytes ÷ 4⌉ estimate is crude; real tokenizers differ by model. The budget is a ceiling on the estimate,
  and the measured outcome that matters is the agent gates, not the count.
- At the first milestone many verbs are not yet implemented; the guide marks each verb's `first_milestone` and
  points to `frob capabilities` for what this build can do, so a fresh agent is not sent to a refusal.
- The guide is in English only; identifiers and commands are ASCII.
- Changing guide wording changes agent behaviour in the gates; guide edits are therefore reviewed with a re-run
  of the fresh-agent tests once those exist.
