## Background

`frob capabilities --json` answers the question an agent should ask before spending a budget: *what can this
build actually do?* It lists what is implemented and what is not, with the resolved modes and ceilings of each
device. It is one of the four operator verbs (with `doctor`, `robot-docs`, `schema`), all in the default task
cluster `orient`, so a fresh agent sees it first; it is also the MCP resource `frob://capabilities`.

"Implemented" has a strict meaning in this project. A capability is implemented only when all eight conditions
hold; otherwise it must be described as partial, with the missing items named:

1. Code exists in the crate the capability is mapped to.
2. That crate ships a `CONTRACT.md` with ten sections (purpose, inputs, outputs, invariants, refusals,
   determinism class, evidence class of outputs, validity domain, oracles, known gaps).
3. Known-answer tests pass against a pinned oracle that was never regenerated from the candidate.
4. Outputs that cross the agent boundary carry the claim product (claim kind, evidence class set by the weakest
   input, tier, determinism class, model identity, seed, the no-authorization flags).
5. A CPU reference path exists; where a GPU path is claimed, a retained differential check against the CPU path
   exists for the same kernels.
6. The capability is reachable through `frob --json` with a documented schema and exit code and, where the
   registry exposes it to agents, through `frob-mcp`.
7. Cancellation is tested: request, drain, finalize, with no leaked device resources.
8. Its gate has a recorded pass carrying measured values, in a receipt naming the commit, the hardware
   fingerprint and the seed.

Two riders: a capability that emits a family certificate is implemented only when the offline auditor accepts
its bundle and rejects the registered mutations; a Frontier or Moonshot capability only when its pilot and its
kill-gate decision are on record, and one that fell back at its kill gate is described by the name of the
fallback.

Design decision (DESIGN): the verb reports status; it never asserts it. Status is computed from the gate
register and from mechanical checks, by the same generator that produces the repository's honest-status table,
so an agent, the README and the dashboard's gate view cannot disagree. Rejected: a hand-maintained capability
list (it would be optimistic by default).

## Technical approach

**1. Capability map.** The verb reads `registries/capabilities.toml` (schema `frob.capability/1`, compiled into
`frob-verbs`), which N00-02 defines: one record per capability with `id` (`cap:<name>`), `verbs`, `crate`,
`contract`, `known_answers`, the envelope test, `cpu_reference` and `gpu_diff`, the schema name, `mcp`,
`cancellable` and `cancel_test`, `gates`, `tier` (`solid`, `frontier`, `moonshot`), `pilot`, `kill_gate`,
`fallback`, `first_milestone` and `family_certificate`. This bead adds no field and keeps no second copy.

**2. Status.** The verb calls the status function of N00-02 and prints its result unchanged: per condition
`met`, `unmet` or `not-applicable` with a pointer to its evidence, and one of four statuses.

| Status | Rule (as N00-02 defines it) |
|---|---|
| `implemented` | All applicable conditions met, and both riders where they apply |
| `partial` | The handler is linked and at least one condition or rider is unmet; `missing` lists the unmet conditions by number and text |
| `not-in-build` | No handler is linked (the verb arrives at a later milestone, or its feature group is off); it carries `missing` and its `first_milestone` |
| `killed` | Its kill gate is recorded as fired; `fallback` names what is in force |

**3. Use by dispatch (`FROB-REF-724`).** The rule is N00-02's and is exercised here from the caller's side: a
call to a verb whose capability is `not-in-build` or `killed` is refused with `FROB-REF-724` (the verb is not
implemented in this build), exit 5, retry `never`, with the entry's `first_milestone` or `fallback` in the
refusal and the repair "see `frob capabilities`"; a `partial` capability runs with the warning
`partial: conditions <list> unmet`. What this bead checks is agreement: every verb the listing shows as
`not-in-build` or `killed` is refused when called, and no other is.

**4. Output** (`frob.capabilities.out/1`).

- `build`: commit, the toolchain, the stack receipt digest, enabled feature groups.
- `capabilities[]`: `id`, `verbs`, `tier`, `status`, `conditions` (eight entries: state and evidence pointer),
  `missing`, `gates` (identifier, status, measured value), `first_milestone`, `fallback`.
- `gates[]`: the whole gate register as rows (identifier, claim kind, milestone, status, measured, date, controls
  caught), for the dashboard's gate view and for exit reviews.
- `devices[]`: per device (each CUDA card, the Metal device, `batch-cpu`, the referee): `backend`, `available`,
  the hardware fingerprint, resolved modes (for each requested tier name such as `gpu-cuda` or `gpu-metal`: the
  mode actually used and why, for example a strict profile falling back to `batch-cpu`), determinism classes
  attainable, arithmetic features (64-bit integers, exact predicates), and ceilings: device memory, the largest
  admitted world count per shape class, the admitted compute envelope. A ceiling that has not been measured is
  reported as `unknown`, never as a default number.
- `summary`: counts by status.

The sections `capabilities[]` and `summary` exist from M0 (N00-02); this bead adds `build`, `gates[]` and
`devices[]` and changes nothing in the first two.

Paged with a cursor when `--limit` is given (the row is `paginated = true`, so the generator adds `cursor`,
`limit` and `follow` and appends 806 and 807; the cursor is the authenticated `frob.cursor/1` of N32a-10, and
its frontier is the pair (registry digest, gate-register digest) of the first page: a later page asked for after
a gate was recorded is refused `FROB-REF-807` and the listing restarts, so pages never mix two states, DESIGN);
filters `--verb` (from M0, BD-022, whose handler has that filter only) and, added by this bead at M1 as the row
of VERBS-operator dates them, `--device`, `--status`, `--cluster` and `--milestone`; `--missing` (from M0,
N00-02) is the same as `--status partial,not-in-build`. What each selects (DESIGN; the plan names no filter):
`--verb <name>`, `--status <list>`, `--cluster <registry cluster>` and `--milestone <Mn>` keep the rows of
`capabilities[]` that list that verb, have one of those statuses, have a verb in that cluster, or have that
`first_milestone`, and `summary` counts the rows kept; `--device <id>` keeps that one row of `devices[]`, and an
identifier that names no device of the host is `FROB-REF-802` with `pointer: /device` and the present
identifiers in the repair; `build` and `gates[]` are never filtered. Kind `read`;
no capability scope required (the row of record, VERBS-operator, writes `capabilities = []` with `public =
true`, as for `robot-docs`: the question "what can this build do" must be answerable before an agent knows which
scopes to ask for, so a session whose token carries no scope is answered); evidence block class `Tested`, tier
`static`, determinism `exact`.

**5. Surfaces.** CLI `frob capabilities [--status …] [--json]`; MCP tool `capabilities`; from M3 the resource
`frob://capabilities` serves the same JSON (N32a-25). The human-readable form prints one line per capability with a status
word and the missing condition numbers.

## Acceptance criteria

- [ ] The verb's `capabilities[]` section equals, record for record, what the status function of N00-02
      returns for the loaded map; this bead's code computes no status.
- [ ] On a build where a verb's handler is absent, calling it returns `FROB-REF-724`, exit 5, and `capabilities`
      lists it `not-in-build` with its `first_milestone`.
- [ ] A capability whose gate is `not-run` in the register is `partial` with condition 8 in `missing`; setting
      the gate to `pass` (with controls and evidence, through the recorder) makes it `implemented` with no other
      change.
- [ ] A capability whose kill gate is recorded as fired is `killed` and names its fallback.
- [ ] The `gates` section equals the gate register row for row; the README status table generated from the same
      register agrees (generated-file check).
- [ ] `devices` reports the backends present on the host and marks unmeasured ceilings `unknown`.
- [ ] CLI and MCP tool return the same content (the resource is compared with this verb by N32a-25 at M3).
- [ ] `scripts/e2e/operator_verbs.sh` passes its `cap-*` steps with the logging below.

## Test plan

### Unit tests
`crates/frob-verbs/tests/capabilities_output.rs` (real registries; a fixture gate register for state changes):
- The tests of the map's lint, of the status rules (the sixteen-case table, the killed and not-in-build cases,
  the Frontier rider) and of the dispatch rule are N00-02's, in `crates/frob-verbs/tests/capabilities.rs`; this
  bead's tests are in `crates/frob-verbs/tests/capabilities_output.rs`.
- `output_equals_status_function`: for a fixture map and gate register, each printed record equals the status
  function's result.
- `listing_agrees_with_dispatch`: every verb listed `not-in-build` or `killed` returns `FROB-REF-724` when
  called (exit 5, retry `never`, `first_milestone` or `fallback` present), and every other verb does not.
- `gate_rows_equal_register`.
- `unmeasured_ceiling_is_unknown`.
- `filters_and_paging`: `--status partial --limit 10` pages without repeats and the pages concatenate to the
  unpaged listing; a cursor with changed filters is refused (`FROB-REF-806`); a gate recorded through the
  recorder between page 1 and page 2 makes page 2 `FROB-REF-807`, exit 3; `--device batch-cpu` returns one
  `devices[]` row and the unfiltered `capabilities[]`; `--device no-such-device` is `FROB-REF-802` with
  `pointer: /device`; `--milestone M1` and `--cluster design` keep exactly the rows the fixture map assigns them,
  and `summary` counts those rows.

### End-to-end script and logging
`scripts/e2e/operator_verbs.sh` (header `bead=N32b-19 milestone=M1 labels=tether,verb`; owned here, extended by
N32b-20 with steps `schema-*` and `doctor-*` at M2), steps `cap-*`: `frob capabilities --json`; pick one
`not-in-build` verb from the answer and call it (expect exit 5, `FROB-REF-724`); pick one `implemented` verb and
call its first example (expect exit 0 or 2); compare the MCP tool over stdio with the CLI; `--status partial
--limit 10` paged to the end, then the cursor reused with a changed filter (expect `FROB-REF-806`). It sources the
STD-E2E helper and writes `target/e2e-logs/operator_verbs/<utc>.ndjson` and a transcript; each line has `ts`,
`script`, `bead`, `step`, `event`, the exact command line, exit code, wall time, the `evidence` block, counts by
status, the refusal code against expected, the digest of the listing on each surface, and on failure the first
differing row between surfaces; then a `summary` naming GATE-TETHER-02.

### Known answers and negative controls
- Known answer: for a fixture capability map none of whose verbs has a linked handler, every capability is
  `not-in-build`; the summary counts sum to the number of capabilities.
- Negative control: a capability map that marks a verb implemented by a literal field (planted `status =
  "implemented"`): the schema of the map has no such field and the load fails (the loader rule is N00-02's;
  here the verb must then refuse to print a listing).
- Negative control: a gate set to `pass` by editing the register with empty `controls`: the register's own check
  refuses it, and `capabilities` continues to report `partial`.
- Negative control: a verb build that computes a status of its own (a planted `implemented` for a capability
  the status function calls `partial`): `output_equals_status_function` fails. The control "a dispatcher that
  refuses partial capabilities" is N00-02's.

## Considerations

- The verb is only as honest as the gate register; the register's rules (a pass needs a caught control, a
  recording session other than the implementer, and resolvable evidence) are what make it so.
- Agents will use `status` to plan. A capability that is `partial` because its gate has not run yet is common
  during development; the warning tells the agent the evidence is weaker without blocking work.
- Open point (owner: Tether lead; fail-closed default: refuse): whether a `killed` capability whose fallback is
  another verb should redirect. Default: no redirect; the refusal names the fallback and the agent decides.
