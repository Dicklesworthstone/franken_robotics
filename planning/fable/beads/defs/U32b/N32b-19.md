## Background

`frob capabilities --json` answers the question an agent should ask before spending a budget: *what can this
build actually do?* It lists what is implemented and what is not, with the resolved modes and ceilings of each
device. It is one of the four operator verbs (with `doctor`, `robot-docs`, `schema`), all in the default task
cluster `orient`, so a fresh agent sees it first; it is also the MCP resource `frob://capabilities`.

"Implemented" has a strict meaning in this project. A capability is implemented only when all eight conditions
hold; otherwise it must be described as partial, with the missing items named:

1. Code exists in the crate the capability is mapped to.
2. That crate ships a `CONTRACT.md` with ten sections (purpose, inputs, outputs, invariants, refusals,
   determinism class, evidence class of outputs, validity domain, oracles, known gaps).
3. Known-answer tests pass against a pinned oracle that was never regenerated from the candidate.
4. Outputs that cross the agent boundary carry the claim product (claim kind, evidence class set by the weakest
   input, tier, determinism class, model identity, seed, the no-authorization flags).
5. A CPU reference path exists; where a GPU path is claimed, a retained differential check against the CPU path
   exists for the same kernels.
6. The capability is reachable through `frob --json` with a documented schema and exit code and, where the
   registry exposes it to agents, through `frob-mcp`.
7. Cancellation is tested: request, drain, finalize, with no leaked device resources.
8. Its gate has a recorded pass carrying measured values, in a receipt naming the commit, the hardware
   fingerprint and the seed.

Two riders: a capability that emits a family certificate is implemented only when the offline auditor accepts
its bundle and rejects the registered mutations; a Frontier or Moonshot capability only when its pilot and its
kill-gate decision are on record, and one that fell back at its kill gate is described by the name of the
fallback.

Design decision (DESIGN): the verb reports status; it never asserts it. Status is computed from the gate
register and from mechanical checks, by the same generator that produces the repository's honest-status table,
so an agent, the README and the dashboard's gate view cannot disagree. Rejected: a hand-maintained capability
list (it would be optimistic by default).

## Scope

In: the capability map (`registries/capabilities.toml`); the status computation; the verb's output schema; the
per-device section; how dispatch uses the map to raise `FROB-REF-724`; the MCP resource text; tests.
Out: the gate register and its recorder (the conformance unit); `doctor` and `schema` (N32b-20); device probing
(the Spark beads).

## Technical approach

**1. Capability map** (`registries/capabilities.toml`, compiled into `frob-verbs`).

```toml
[[capability]]
id = "design.check"            # usually a verb; a mechanism behind several verbs may be listed once
verbs = ["design.check"]
crate = "frob-analyze"
tier = "S"                     # S | F | M
gates = ["GATE-ATEL-02"]       # condition 8
known_answers = ["KA-…"]       # condition 3
gpu_path = false               # condition 5 needs the differential check only when true
cancellable = false            # condition 7 applies to verbs that start work
pilot = ""                     # required for F and M
kill_gate = ""                 # required for F and M when one exists
fallback = ""                  # the name used if the kill gate fired
first_milestone = "M1"
```

A lint requires every registry verb to belong to exactly one capability and every listed gate and known answer
to exist.

**2. Status computation.** For each capability, each condition is `met`, `unmet` or `not-applicable`, with a
pointer to its evidence: (1) the handler is linked in this binary; (2) `check-contracts` result for the crate;
(3) the listed known answers have a passing record against a pinned oracle; (4) the verb's output schema embeds
the evidence block and, for exporting verbs, the authorization flags; (5) a CPU path is registered and, if
`gpu_path`, a current differential check exists; (6) the verb is in the generated CLI and, if its registry entry
exposes it, in the served tool list; (7) a cancellation test is recorded, or not applicable; (8) every listed
gate has status `pass` in the gate register. Overall status:

| Status | Rule |
|---|---|
| `implemented` | All applicable conditions met, and both riders where they apply |
| `partial` | The handler is linked and at least one condition is unmet; `missing` lists the unmet conditions by number and text |
| `not-in-build` | No handler is linked (the verb arrives at a later milestone, or its feature group is off) |
| `killed` | Its kill gate is recorded as fired; `fallback` names what is in force |

**3. Use by dispatch (`FROB-REF-724`).** A call to a verb whose capability is `not-in-build` or `killed` is
refused with `FROB-REF-724` (the verb is not implemented in this build), exit 5, retry `never`, with the entry's
`first_milestone` or `fallback` in the refusal and the repair "see `frob capabilities`". A `partial` capability
*runs*: its envelope carries a warning `partial: conditions <list> unmet` and its evidence block is whatever the
claim product gives. DESIGN reading, stated because the alternative deadlocks: if a partial capability were
refused, no gate could ever be run through the surface to make it implemented.

**4. Output** (`frob.capabilities.out/1`).

- `build`: commit, the toolchain, the stack receipt digest, enabled feature groups.
- `capabilities[]`: `id`, `verbs`, `tier`, `status`, `conditions` (eight entries: state and evidence pointer),
  `missing`, `gates` (identifier, status, measured value), `first_milestone`, `fallback`.
- `gates[]`: the whole gate register as rows (identifier, claim kind, milestone, status, measured, date, controls
  caught), for the dashboard's gate view and for exit reviews.
- `devices[]`: per device (each CUDA card, the Metal device, `batch-cpu`, the referee): `backend`, `available`,
  the hardware fingerprint, resolved modes (for each requested tier name such as `gpu-cuda` or `gpu-metal`: the
  mode actually used and why, for example a strict profile falling back to `batch-cpu`), determinism classes
  attainable, arithmetic features (64-bit integers, exact predicates), and ceilings: device memory, the largest
  admitted world count per shape class, the admitted compute envelope. A ceiling that has not been measured is
  reported as `unknown`, never as a default number.
- `summary`: counts by status.

Paged with a cursor when `--limit` is given; filters `--status`, `--cluster`, `--milestone`. Kind `read`; no
capability scope required; evidence block class `Tested`, tier `static`, determinism `exact`.

**5. Surfaces.** CLI `frob capabilities [--status …] [--json]`; MCP tool `capabilities`; resource
`frob://capabilities` (the same JSON). The human-readable form prints one line per capability with a status
word and the missing condition numbers.

## Acceptance criteria

- [ ] Every registry verb appears under exactly one capability; the lint fails on an orphan verb.
- [ ] On a build where a verb's handler is absent, calling it returns `FROB-REF-724`, exit 5, and `capabilities`
      lists it `not-in-build` with its `first_milestone`.
- [ ] A capability whose gate is `not-run` in the register is `partial` with condition 8 in `missing`; setting
      the gate to `pass` (with controls and evidence, through the recorder) makes it `implemented` with no other
      change.
- [ ] A capability whose kill gate is recorded as fired is `killed` and names its fallback.
- [ ] The `gates` section equals the gate register row for row; the README status table generated from the same
      register agrees (generated-file check).
- [ ] `devices` reports the backends present on the host and marks unmeasured ceilings `unknown`.
- [ ] CLI, MCP tool and resource return the same content.

## Test plan

### Unit tests
`crates/frob-verbs/tests/capabilities.rs` (real registries; a fixture gate register for state changes):
- `every_verb_has_one_capability`.
- `status_rules_table`: sixteen constructed capabilities covering each condition unmet in turn, both riders, the
  killed case and the not-in-build case; expected status and `missing` for each.
- `partial_runs_with_warning`: a partial verb answers with `warnings` naming the unmet conditions.
- `not_in_build_is_724`: exit 5, retry `never`, `first_milestone` present.
- `killed_names_fallback`: a capability with kill gate `KILL-TUI` fired reports fallback "no dashboard".
- `gate_rows_equal_register`.
- `unmeasured_ceiling_is_unknown`.
- `frontier_needs_pilot_and_decision`: tier F with all eight met and no pilot record is `partial`.
- `filters_and_paging`: `--status partial --limit 10` pages without repeats; a cursor with changed filters is
  refused (`FROB-REF-806`).

### End-to-end script and logging
`scripts/e2e/operator_verbs.sh` (shared with N32b-20), steps `cap-*`: `frob capabilities --json`; pick one
`not-in-build` verb from the answer and call it (expect exit 5, `FROB-REF-724`); pick one `implemented` verb and
call its first example (expect exit 0 or 2); compare the MCP tool and the resource with the CLI. NDJSON lines:
`ts`, `script`, `bead`, `step`, `event`, command, exit code, wall time, the `evidence` block, counts by status,
the refusal code against expected, and the first differing row between surfaces.

### Known answers and negative controls
- Known answer: on the planning-stage repository (no code) every capability is `not-in-build`; the summary
  counts sum to the number of capabilities.
- Negative control: a capability map that marks a verb implemented by a literal field (planted `status =
  "implemented"`): the schema of the map has no such field and the load fails.
- Negative control: a gate set to `pass` by editing the register with empty `controls`: the register's own check
  refuses it, and `capabilities` continues to report `partial`.
- Negative control: a dispatcher that refuses partial capabilities: `partial_runs_with_warning` fails.

## Considerations

- The verb is only as honest as the gate register; the register's rules (a pass needs a caught control, a
  recording session other than the implementer, and resolvable evidence) are what make it so.
- Agents will use `status` to plan. A capability that is `partial` because its gate has not run yet is common
  during development; the warning tells the agent the evidence is weaker without blocking work.
- Open point (owner: Tether lead; fail-closed default: refuse): whether a `killed` capability whose fallback is
  another verb should redirect. Default: no redirect; the refusal names the fallback and the agent decides.
