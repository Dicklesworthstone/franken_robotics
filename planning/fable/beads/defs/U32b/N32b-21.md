## Background

Tether, the surface of FrankenRobotics (the `frob` command line, the daemon `frobd`, the MCP server `frob-mcp`),
defines twenty-two refusal codes: four for budgets (`FROB-REF-701` to `-704`), five for capabilities (`-720`,
`-723`, `-724`, `-725`, and `-726`, a built mechanism not admitted for the run's purpose or tier), ten for the
protocol (`-801` to `-810`), and three refusals the specification states without a number, raised under the
interim numbers the registry bead gives them while their allocation is held (`-836` a replay packet over its
byte cap, `-837` frames from a chunk neither stored nor pinned, `-838` an MCP resource read over 4 MiB; they are
entries of the interim list, not registry rows, until the hold is released). The registry bead (N32-REF) fixes
for each its trigger, ranked repairs, retry class and exit code. Its twenty-third code, the internal fault
`-990`, is fired by the forced panic of the failure-class bead (BD-299) and is only read back here. A refusal row is a promise about behaviour; this bead is
the test that each promise holds from the user's side, on both surfaces, on a real daemon.

Three things are tested that unit tests of a mechanism do not show. (1) *The whole path*: a planted violation
travels through the real parser, dispatch, daemon and serializer and comes back as one envelope with the right
code and exit. (2) *Parity*: the CLI envelope and the MCP tool result (`isError: true` with the envelope as
structured content) are the same, with one permitted difference (an unknown tool on MCP is answered by the
library with a JSON-RPC error before any generated code runs). (3) *Repairs work*: the first ranked repair of
every refusal is executed and must lead to an accepted call, because a repair an agent cannot execute is worse
than none.

The battery also checks the three standing rules of the boundary: refuse, never truncate; a budget stop
publishes nothing partial as a result; a misspelt parameter is a refusal, not a default. And it contributes one
clause of the failure-class gate (GATE-TETHER-04): every refusal code maps to exactly one exit code.

## Scope

In: `scripts/e2e/tether_refusals.sh`; one planted violation per code; CLI and MCP halves; execution of the first
repair; the standing-rule checks; the code-to-exit uniqueness check over the whole registry as served; the
read-back of every registry row through `frob schema frob.refusal/1`, `frob robot-docs` and the resource
`frob://registry/refusals` (moved here from N32-REF, which cannot depend on the verbs and the resource that
serve its rows).
Out: defining the rows (N32-REF); the mechanisms; the three failure classes as such, including the killed
connection (seed BD-299); the two replay-packet refusals that reuse other chapters' codes (`-562` for a fork
overlay below class D2 and `-724` for fork content before the fork-harness gates pass), and the over-cap refusal
as a measured clause of GATE-TETHER-16 (N32b-43).

## Technical approach

Setup: a temporary state root, whose `safety.toml` the script writes with two `principal.<id>` tables (agents A
and B) granting the scopes and amounts the cases and their first repairs use (a root token is minted only from
a principal's grant, N32b-01); `frobd` on `batch-cpu` with a small environment; two agent sessions with small
budgets, each opened with `--principal <id> --key <k>` and no token in the environment; `frob-mcp` on loopback
HTTP and over stdio. Each case runs through the CLI and again through an MCP
client; both results are stored and compared field by field.

**Standing-rule checks.** (a) *Never truncate*: a `telemetry query` whose answer exceeds one page returns a
`cursor` and `frontier`, and concatenated pages equal the row count the summary states; no envelope anywhere in
the battery exceeds the size limit by silently dropping rows. (b) *Nothing partial*: after 702, `run show` has no
result fields and `eval` verbs refuse the run as a scoring source. (c) *Misspelt is refused*: every `run` and
`mutate` verb in the registry is called once with one extra unknown parameter and must answer 802, on both
surfaces.

**Uniqueness.** The script reads `frob://registry/refusals` and the CLI's refusal table and asserts that code →
exit is a function for the whole registry, and that every exit observed in the battery equals the registry's.

**Read-back.** Every row of `registries/refusals.toml` that this chapter owns appears with the same code,
message, exit, retry class and ranked repairs in `frob schema frob.refusal/1 --json` (the code enumeration and
the example), in `frob robot-docs --json` (the page `exit-codes-and-refusals`) and in
`frob://registry/refusals`. The rows are twenty (N32-REF): the nineteen fired above that are rows (701 to 704,
720, 723 to 726, 801 to 810) and the internal fault 990. The three held requests (836, 837, 838) are not rows
while the hold of N35x-01 stands; they are read back from the interim list that `frob schema --refusals --json`
serves (member `interims`: for each request its slug, its interim code, the bead that owns the interim use and
its ledger status), and the code each case above was answered with is the interim listed for its request. A
row present on one surface and absent or different on another, an interim entry missing from the list, or one
of the three served as a row, fails the step and names it and the surface.

**Parity comparison.** For each case the CLI envelope and the MCP structured content are compared after removing
`cost.wall_ms` and declared per-surface defaults; the unknown-verb case is the single listed exemption and the
script asserts the exemption list has exactly that one entry. Case 838 has no CLI half (a resource read is an MCP
operation only) and is not counted as a parity case.

**Step names.** Each step is named `refusal_<code>_<surface>` or `refusal_<code>_repair` (for example
`refusal_803_cli`, `refusal_803_mcp`, `refusal_803_repair`), the prefix the test standard binds to a refusal
code, so the gate report maps steps to rows.

## Acceptance criteria

- [ ] All twenty-two codes are fired: twenty-one on the CLI, of which twenty produce an identical envelope over
      MCP and one (801) produces the library's unknown-tool error; 838 over MCP only.
- [ ] Each case shows exactly one envelope, `ok: false`, the expected code, exit and retry class, a non-empty
      `repairs` list, and an unchanged ledger where the table says nothing was charged.
- [ ] The first repair of every code is executed and accepted (or, for 810, the recovery by key succeeds).
- [ ] The three standing rules hold; the code-to-exit map is a function over the whole registry.
- [ ] The script records `refusal_codes_fired = 22`, `parity_cases = 20` and `parity_exemptions = 1`.
- [ ] The read-back finds the twenty rows (990 among them) identical in the schema, the agent guide and the
      resource, and the three interim entries in the interim list; none of 836, 837 and 838 is served as a row.
- [ ] Neither 726 reason is ever answered with `FROB-REF-724`.
- [ ] Each negative control below turns the script red at the named case.

## Test plan

### Unit tests
`crates/frob-conformance/tests/refusal_battery_plan.rs`: `battery_covers_all_tether_codes` (the plan file lists
each of the twenty-two exactly once; every row of `registries/refusals.toml` that N32-REF owns appears in it,
except 990, which the plan lists as read back only, and so does the interim of each of its three held
requests); `expected_exits_match_registry`; `step_names_bound` (every step id matches `refusal_<code>_(cli|mcp|repair)`
with a registry code); `test_hooks_absent_from_release` (the `--force-admit` and second-publisher hooks do not
exist in a release build).

### End-to-end script and logging
`scripts/e2e/tether_refusals.sh` (header: `bead=N32b-21 milestone=M3 labels=tether,refusals,surface
gates=GATE-TETHER-04,GATE-TETHER-03 seed=21 needs=cpu,frobd,mcp plants=ignore-unknown-flags,silent-truncation,partial-on-budget-stop,exit-mismatch,free-text-mcp-error,island-as-724,guide-row-dropped`,
the seven negative controls below in order; every `run` and `mutate` call carries its own key, and the CLI and
MCP halves of one case use distinct keys, `<case>-cli` and `<case>-mcp`, so that the MCP half is a second request
and not a stored receipt, except where the case is about the key itself, 803). Log:
`target/e2e-logs/tether_refusals/<utc-timestamp>.ndjson` and a transcript.
Every line has `ts`, `script`, `bead`, `step` (the code and surface, for example `refusal_803_cli`,
`refusal_803_mcp`, `refusal_803_repair`), `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line or the
JSON-RPC request with secrets redacted, exit code or JSON-RPC error code, wall time, the envelope's `evidence`
block, the refusal's `code`, `pointer`, `observed`, `required`, `unit` and `retry` against expected values,
ledger digests before and after, and on failure the first differing field between expectation and observation
or between surfaces, with both envelopes' paths. The `summary` line gives assertions passed and failed, codes
fired of 22, rows read back of 20, interim entries read back of 3, and names GATE-TETHER-04 (the clause on one exit per code) and GATE-TETHER-03.

### Known answers and negative controls
- KA-755: the exit-code table on malformed, unknown, over-budget, unscoped and conflicting inputs.
- KA-756 for case 808; KA-763 for case 803 (one job and one charge; the same key with another digest is refused,
  exit 7).
- Negative controls (test builds): (1) a parser that ignores unknown flags: case 802 and standing rule (c) fail;
  (2) a serializer that drops rows past a size limit: standing rule (a) fails; (3) a budget stop that publishes
  the worlds finished so far as a result: rule (b) fails; (4) a registry row whose exit differs between the CLI
  table and the MCP resource: uniqueness fails; (5) an MCP error hook that returns free text instead of the
  envelope skeleton: parity fails for 802; (6) a living-world admission that answers `island-in-training` with
  724: case 726 fails; (7) a refusal row dropped from the agent guide's page: the read-back fails naming the row.
- Determinism lanes: the battery twice on one machine gives the same codes, exits and pointers; both platforms.

## Considerations

- Several cases need a test-only hook to reach a state that correct operation prevents (an under-reserved job, a
  conflicting chunk). The hooks live behind the negative-control feature; a release build without them still
  runs every other case and reports the hooked cases `not run` with the reason.
- Codes whose mechanism arrives late (703 and 704 with the dispatcher at the third milestone) make this battery a
  third-milestone bead; from the first milestone on, the subset whose mechanisms exist runs in CI and the rest
  are reported `not-in-build`.
- Overlaps with codes owned by other chapters (a design-patch stale parent; a telemetry cursor mismatch; a chunk
  key conflict recorded by the store) are resolved in the registry bead; this battery asserts the surface codes.
