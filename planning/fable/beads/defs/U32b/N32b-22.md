## Background

Tether is the surface of FrankenRobotics: the verb registry, the envelope, the command line `frob`, the daemon
`frobd` with its job ledger and dispatcher, the MCP server `frob-mcp`, the dashboard and the viewer. Thirteen
invariants state what must be true of that surface in every execution. Each belongs to a mechanism built
elsewhere, and each mechanism's own bead tests it. This bead exists for a different reason: an invariant is only
as good as the test that can fail, and a list of thirteen statements spread over many beads is easy to believe
without checking. Here the thirteen are collected into one battery in the conformance crate, each as a property
test with a planted violation that the test must catch, registered in the negative-control registry.

The project's rule on this is explicit: for every law, invariant and proof obligation a property test, and for
every gate at least one negative control; a check that nothing can fail validates nothing.

## Scope

In: `crates/frob-conformance/tests/tether_invariants.rs` and `scripts/e2e/tether_invariants.sh`; for each
invariant its statement, the property tested, the generator of cases, the planted violation, and the mechanism
bead it constrains; the invariant register rows.
Out: the mechanisms; the five proof obligations (N32b-23); the chapter's known answers (N32b-24).

## Technical approach

Each row is one test function (named `inv_tether_NN_…`) plus one mutant behind the negative-control feature. Where
a property needs a running daemon it runs on the deterministic runtime with seeded schedules and a CPU stand-in
for the device, and again in the end-to-end script on the real daemon with `batch-cpu`.

**Register rows.** Each invariant is a row of `registries/invariants.toml`, section `tether` (the one invariant
register, in the format its Spark, Habitat and Chronicle sections use: `id`, `statement`, `verification`,
`test`, `negative_control`, `tier`, `first_milestone`, `owner_bead`; a file of this chapter's own would be a
private registry, which the registry lint refuses), so that the join "every invariant has a test and a caught
control" is a query and is checked in CI. The controls are records of
`crates/frob-conformance/registry/controls.toml`, one per planted violation and never two for one plant. Where
the plant is that of a catalogue entry or of a known-answer row's control cell (the reused counterexamples
CX-345 to CX-348, and the receipt without the unstarted count of KA-766, among them), the control is the one
the seeding tool derived (N38b-05, the only writer of such a record). Where a Tether gate states it (the
hand-added flag of GATE-TETHER-02, the neighbouring-slot read of GATE-TETHER-09, the wait that cancels its job
of GATE-TETHER-12), it is the record N32b-25 registered for that gate. In both cases this battery's test
reports to the existing control and adds none. Only where nothing states the plant does this bead register a
record, under BD-025's rules: `seed = "INV-TETHER-NN"` (the form admitted for an invariant, resolved to its
gate through `registry/rule_gates.toml`), the number appended in order and never chosen by hand. The run that
shows a plant caught is the test `nc_<nnnn>_<invariant>_caught`, the prefix the test standard binds to a
control.

**Case generation.** Seeds are explicit; each property runs a fixed number of cases in CI (TARGET: 10³ for
daemon properties on the deterministic runtime, 10⁴ for pure ones) and a longer nightly lane.

## Acceptance criteria

- [ ] Thirteen tests exist, named by invariant, and pass on a correct build.
- [ ] For each, the mutant build makes that test fail and no other mechanism's unit tests are needed to see it.
- [ ] The registry join reports thirteen invariants, thirteen tests, at least thirteen controls caught.
- [ ] The end-to-end script reproduces INV-TETHER-02, -05, -10, -11, -12 and -13 on the real binaries.
- [ ] `CONTRACT.md` of `frob-verbs` lists the thirteen statements in its invariants section with the test names.

## Test plan

### Unit tests
The thirteen `inv_tether_NN_*` tests above, plus:
- `invariant_register_complete`: section `tether` of `registries/invariants.toml` has exactly INV-TETHER-01 to
  -13, each with a test and a control; no plant of the table is the target of two controls (a scratch registry
  with an `INV-TETHER-05` control beside the one seeded from CX-345 fails naming both numbers).
- Thirteen `nc_<nnnn>_inv_tether_NN_caught` tests, one per mutant, each building the mutant behind the
  negative-control feature and asserting that its invariant's test fails.
- `fuzz_corpus_seeds_fixed`: the fuzz corpus of INV-TETHER-02 is regenerated from its seed and equals the stored
  digest.
Selected expected values: for INV-TETHER-04 the worked comparison 19 + 2 + 40 + 3 + 0 = 64; for INV-TETHER-07 the
value 9,007,199,254,740,993 must arrive unchanged as a string; for INV-TETHER-02 the unknown verb `desing.check`
yields one envelope with `FROB-REF-801` and exit 3.

### End-to-end script and logging
`scripts/e2e/tether_invariants.sh` (header: `bead=N32b-22 milestone=M3 labels=tether,invariants,conformance
seed=22 needs=cpu,frobd,mcp plants=panic-exit-1,lookup-then-insert,client-only-handle,wait-cancel-cancels-job,dashboard-run-verb,description-appends-import,offset-pagination`,
the mutants of the six real-binary invariants in order, then `offset-pagination` for N32b-23's group
`obligations-*`, which also reuses `lookup-then-insert`): writes the one grant with `e2e_session grant inv
--scopes <the trials' scopes and amounts>` before `frobd` starts on the temporary state root, then opens one
root session for the trials with `e2e_session open trials --principal inv …` (STD-E2E item 17: no token in the
call's environment, the token kept out of every log and exported; a root token is minted only from a principal's
grant, N32b-01; the submitters of one trial share the session, because a key is scoped to principal and verb);
runs the six real-binary properties named above, 20 seeded trials each (TARGET); for INV-TETHER-10 it kills each
of the three clients in turn. Keys, each written with `e2e_key`: the submitters of one INV-TETHER-05 trial share
one key, label `inv05-<trial>` issued once and passed by every submitter, because one key under contention is the
property; every other trial submits under its own label (`inv10-<client>-<trial>`, `inv11-<case>-<trial>`), so
that no trial reads a receipt stored by an earlier one; recovery is `frob job find --verb sim.run --key <the
trial's key> --json`. Log: `target/e2e-logs/tether_invariants/<utc-timestamp>.ndjson` and a transcript; every line has `ts`,
`script`, `bead`, `step` (the invariant identifier), `event`, the exact command line, exit code, wall time, the
envelope's `evidence` block, trials run and trials passed against the threshold (all), ledger and digest-chain
digests where state is compared, and on failure the seed, the first differing value and the state-root copy's
path. The `summary` line lists the invariants exercised.

### Known answers and negative controls
- The thirteen planted violations of the table are the negative controls; each is registered and must be caught
  in the same CI run that records the test as passing.
- Counterexamples reused as mutants: the two-statement idempotency check, offset pagination, the time-only
  cursor and the bare 64-bit integer (the chapter's catalogued counterexamples).
- Determinism lanes: every property twice on one machine with the same seeds; debug and release; both platforms;
  INV-TETHER-08 additionally across worker counts.

## Considerations

- Duplication with mechanism beads is deliberate and bounded: this battery holds one property per invariant, not
  the mechanisms' full test suites. If a mechanism bead's own test already has the same shape, this battery
  calls it instead of copying it.
- INV-TETHER-08 at full scale (1,000 episodes in 100 co-tenancies on devices) is the slot-invariance gate; here it
  runs on the CPU stand-in and `batch-cpu`.
- An invariant found violated in the field is first reproduced as a new case in this battery, then fixed.
