## Background

A kill gate is a decision written before the data that decides it: a trigger, a fallback named in advance, and a
statement of what changes downstream on each branch. KILL-MCP governs how agents reach FrankenRobotics over the
Model Context Protocol.

The design of record, by the owner's ruling of 2026-11-22: the MCP server `frob-mcp` is built on the suite's MCP
library, is an ordinary member of the core workspace build graph on the one Rust toolchain T, links the verb
crate `frob-verbs` and runs verbs **in process** through the dispatch interface, handing long work to the daemon
`frobd` as jobs. Its source sits under `surface/frob-mcp` because it is a surface, not because it is a separate
workspace. The earlier default, a server in its own workspace talking to the daemon over a local socket, is now
only this gate's first fallback. Two recorded open questions were settled by that ruling and are kept as
decisions: whether the core moves to a toolchain on which the server may join the graph (decided: one toolchain
T for the whole graph, chosen at the toolchain admission gate), and whether `frob-mcp` can link handler crates
in process (decided: yes, once the library has been brought onto T).

Why a kill gate is still needed. FACT, the starting state (observed 2026-11-21): the simulation foundation pins
`nightly-2026-07-06`, which its toolchain file identifies as rustc 1.99.0-nightly; the MCP library declares
`rust-version = "1.100"` and pins `nightly-2026-08-25`; as found, the two do not build on one compiler. The
library's published package 0.13.0 carries asupersync 0.5.0 while its source tree pins 0.6.2, the foundation
consumes asupersync by path and the tensor sibling requires 0.6.2. Both mismatches are fixed in the siblings by
this program (every sibling is the owner's): one upstream work item brings the library onto T with its own test
suite and conformance checks passing there; another aligns the siblings on one published asupersync version. If
that work cannot be finished inside the first milestone, the program must not wait on it.

## Technical approach

**The gate, as registered.**

| Field | Value |
|---|---|
| Kill gate | KILL-MCP |
| Decided at | The first-milestone exit; re-read at the second-milestone exit with the M1 verb set |
| Trigger | The admission gate INT-FMCP-01 cannot pass within the first milestone's budget after both upstream work items have been attempted |
| Measurement | INT-FMCP-01: `frob-mcp` builds in the core graph on T with exactly one asupersync package (`cargo tree -d` shows no duplicate); it lists the tools generated from the verb registry; it passes the MCP protocol smoke test over stdio and over HTTP |
| Fallback 1 | `frob-mcp` as its own workspace, linking `frob-verbs` with the `registry-only` feature (the verb table, schemas and envelope types, no physics crate), talking to `frobd` over the local socket in newline-delimited JSON |
| Fallback 2 | Agents use the CLI, which is complete on its own |

**Decision function** (pure; inputs are records, not opinions).

```
decide(int_fmcp_01: {pass | fail | not-run, clauses: [bool; 3]},
       fd_fmcp_01_attempted: bool, fd_asup_01_attempted: bool, at_exit_review: bool)
  -> does-not-fire | fires(fallback-1) | fires(fallback-2) | undecided
```

1. `int_fmcp_01 = pass`: does not fire.
2. Not at the exit review: undecided (the budget has not run out).
3. At the exit review, not passed, and either upstream item has no recorded attempt (a landed change, or a
   documented blocker with its evidence): undecided, escalated to the owner. The gate cannot fire on work that
   was never tried.
4. At the exit review, not passed, both attempted: fires. Fallback 1 if the socket form passes the same smoke
   test in its own workspace; otherwise fallback 2.

**Reachability of fallback 1, demonstrated before it is needed.** The adapter has one dispatch interface with
two back ends (decision ADR-TETHER-03); `frob-verbs` has the `registry-only` feature (ADR-TETHER-02). A test in
the default build runs the protocol smoke test with `frob-mcp --dispatch=socket` against a running `frobd`, and
a build check compiles `frob-mcp` against `frob-verbs` with `registry-only` and no physics crate. Both must pass
at the first milestone whatever the gate decides, so that firing costs configuration, not design.

**Consequences by branch.**

| Outcome | What changes |
|---|---|
| Does not fire | The design of record stands. `frobd --mcp` may host the server. With no daemon, CPU-tier verbs run in process over MCP and the envelope says so. Nothing else changes |
| Fires, fallback 1 | `surface/frob-mcp` becomes its own workspace with its own lockfile and exactly one asupersync package of its own; it shares the registry table, schemas and envelope types through `registry-only`, so the parity gate still compares the served tool list with the registry. Every verb call crosses the socket: with no daemon running the MCP server answers nothing but the operator verbs it can serve from the registry. `frobd --mcp` is unavailable. The MCP half of the "runs in process" statements in documentation is removed. The invariants of the surface are unchanged (a killed adapter never owns a job). The upstream work items stay open, and their switch-over rule applies |
| Fires, fallback 2 | No MCP server ships. The beads that build MCP tools, task clusters, the bounded wait on MCP, resources, prompts and the Tasks adapter are closed as not built and described by the fallback's name; the MCP acceptance gate is recorded `killed`; the parity gate's MCP half is not applicable; the agent tests run through the CLI and the skill file |
| Re-reading at the second milestone | INT-FMCP-01 is re-run with the M1 verb set. If the design of record now passes while a fallback is in force, the switch-over is one change: the workspace membership and the default dispatch back end; the gate row is amended, not rewritten |

**Fail-closed default until decided.** No MCP surface is advertised to agents; the CLI is the surface.

**Record.** An architecture decision record (statement, the three clause results of INT-FMCP-01, the state of
the two upstream items, the branch, the consequences) and the gate register row, entered by a session that did
not do the upstream work.

## Acceptance criteria

- [ ] The decision function exists as tested code in the conformance crate and is applied to the recorded
      inputs; its output equals the recorded branch.
- [ ] The architecture decision record exists with measured clause results, dated, citing the admission record.
- [ ] The socket smoke test and the `registry-only` build check pass in the default build.
- [ ] On the firing branches, the beads that exist only on the in-process branch are closed with the fallback's
      name, and `frob capabilities` reports the MCP surface accordingly.
- [ ] The second-milestone re-reading is recorded as an amendment with the M1 verb set's result.
- [ ] The first-milestone exit review can read the outcome without opening build logs.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_mcp.rs`:
- `decide_pass_does_not_fire`.
- `decide_before_exit_is_undecided`.
- `decide_unattempted_upstream_is_undecided`: not passed, one upstream item unattempted.
- `decide_fires_fallback_1_when_socket_form_passes`; `decide_fires_fallback_2_otherwise`.
- `duplicate_runtime_fails_clause_one`: a fixture `cargo metadata` with two asupersync packages gives clause 1
  false.
`surface/frob-mcp/tests/socket_backend_smoke.rs`: the protocol smoke test (initialize, `tools/list`, one
`tools/call` of `capabilities`, shutdown) over stdio with the socket back end.

### End-to-end script and logging
`scripts/e2e/kill_mcp_decision.sh`: runs `cargo tree -d -p frob-mcp`, counts asupersync packages; starts
`frob-mcp` over stdio and over loopback HTTP and runs the smoke test in process; repeats it with
`--dispatch=socket` against `frobd`; diffs the served tool list against `frob schema --list`; recomputes the
decision and compares it with the record. NDJSON lines per the shared helper (`ts`, `script`, `bead`, `step`,
`event`, command, exit code, wall time, the `evidence` block of each envelope): package count against 1, tools
listed against the registry's count for the milestone, smoke steps passed, the recomputed branch against the
recorded one; the `summary` line names KILL-MCP and INT-FMCP-01.

### Known answers and negative controls
- Known answer: `capabilities` over MCP returns the same envelope as `frob capabilities --json`.
- Negative control: a decision recorded as "fires" while an upstream item has no attempt record is rejected by
  the recomputation.
- Negative control: a build that pulls the library's published package (which carries the older asupersync)
  shows two packages and fails clause 1.
- Negative control: a decision entered by the session that did the upstream work is refused by the recorder.

## Considerations

- RISK-03 (two asupersync versions in one build; high) is the practical trigger: three siblings still pin the
  older version. `xtask check-deps` forbids it, and this gate's first fallback is the escape if a surface still
  brings a second package.
- Fallback 1 reintroduces a second toolchain file for one workspace, which the one-toolchain rule otherwise
  withdrew; that cost is the reason it is a fallback.
- The library states its own limits (its newest protocol era is under implementation and unverified; wire
  cancellation is only partly qualified; one measured conformance run passed 112 of 115 named server checks and
  is not a conformance claim). None is a trigger here; they bound what the MCP gate can claim later.
