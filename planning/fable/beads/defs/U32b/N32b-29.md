## Background

A kill gate is a decision written before the data that decides it. KILL-MCPTASKS governs one optional, Frontier
feature of the MCP server `frob-mcp`: presenting a long-running job to an MCP client as a protocol-native
**Task**.

The primary contract for long work does not involve Tasks. Every tool whose registry kind is `run` takes a
bounded synchronous wait (`sync_wait_ms`); if the job finishes inside it the result is returned, otherwise the
envelope carries exit code 8 and a **job handle** with progress, an interval for the time remaining and
`poll_after_ms`, and the agent continues with `job_wait`. That handle contract works on every client and every
protocol era. Decision ADR-TETHER-06 fixes the relation: the MCP Tasks extension is an optional adapter over the
job ledger, never the primary contract. Reason: the library labels the extension experimental and its own
implementation provisional (FACT, read 2026-11-21 at the pinned commit: the 2026-07-28 Tasks methods
`tasks/get`, `tasks/update` and `tasks/cancel` run on a process-local in-memory store unless an application
store is supplied through `final_tasks`, and task creation needs a `task_supervisor`).

The adapter: where a client negotiates the Tasks extension, a `run` tool may also surface its job as an MCP Task
through an application-owned store backed by the job ledger, so that task identifiers survive a restart of
`frob-mcp`. The ceiling is stated first: no compute is saved; the benefit is client-native progress display,
bounded by the number of long jobs in a session. Because the mechanism is Frontier, a paper-scale pilot with a
falsifier runs before it is funded: 20 scripted jobs over the in-memory transport, comparing Task states with
the ledger; one disagreement falsifies it.

## Scope

Overlap, for the lead to resolve: the other Tether unit, which owns the MCP server, has also drafted a decision
bead for this gate (N32a-29), with the pilot as N32a-28 and the adapter as N32a-30. Only one decision bead should
be loaded. This draft was written because the chapter's gates subsection belongs to this unit; if N32a-29 is
kept, what this draft adds (the state mapping the pilot checks, the standing incompatibility clause on every pin
advance, and the rule that a killed adapter is removed and not left dormant) can be folded into it.

In: the gate's definition; the decision function; the procedure, including the standing clause about
incompatible change; consequences by branch; the decision record.
Out: the pilot and the adapter (the MCP beads of the other Tether unit); the bounded wait and job handles, which
exist on both branches.

## Technical approach

**The gate, as registered.**

| Field | Value |
|---|---|
| Kill gate | KILL-MCPTASKS |
| Decided at | The third milestone; the incompatibility clause stays live afterwards |
| Trigger | The pilot fails, or the protocol extension changes incompatibly |
| Measurement | Pilot: for each of 20 scripted jobs (covering: completes inside the wait; completes after it; fails; is cancelled by `job.cancel`; is cancelled through the Task; survives a restart of `frob-mcp` mid-run; is refused at admission; stops on budget), the sequence of Task states observed by the client is compared with the job's ledger states under the fixed mapping below. Incompatibility: after a pin advance of the library, the adapter fails to compile or the pilot fails |
| Fallback | Job handles only |

State mapping the pilot checks (DESIGN; the adapter defines no state of its own):

| Ledger state | Task state shown |
|---|---|
| `admitted`, `running`, `preempted` | working (with progress numerator, denominator and unit) |
| `complete` | completed, result = the job's envelope |
| `failed`, `failed_to_start` | failed, with the envelope's refusal |
| `cancelled` | cancelled, with the last committed tick |
| `refused` (admission) | no Task is created; the tool call returns the refusal envelope |

**Decision function.**

```
decide(pilot: {jobs: u32, disagreements: u32, restart_survived: bool} | not-run,
       extension_incompatible: bool)
  -> does-not-fire | fires | undecided
```

1. `extension_incompatible`: fires (at any time, including after a "does not fire").
2. `pilot = not-run` or `jobs < 20`: undecided.
3. `disagreements ≥ 1` or `restart_survived = false`: fires.
4. Otherwise: does not fire.

**Procedure.** (1) Confirm the pilot was registered before it ran and that its negative control was caught (an
adapter on the library's default in-memory store loses its tasks on restart, so the restart case must fail
there). (2) Apply the function. (3) Write the architecture decision record and the register row from a session
that did not build the adapter. (4) Add the standing check to the compatibility train: whenever the library's
pin advances, the pilot re-runs; a failure re-opens this decision as fired.

**Consequences by branch.**

| Outcome | What changes |
|---|---|
| Does not fire | The adapter is funded behind the feature `frontier-mcp-tasks`, off by default until the MCP acceptance gate has passed with it on. `run` tools advertise task support only to clients that negotiated the extension. The handle contract is unchanged and remains what documentation teaches first |
| Fires | No Task is ever advertised; the adapter's code and feature are removed from the tree, not left dormant; `frob capabilities` reports the capability `killed` with fallback "job handles only". Nothing else changes: `sync_wait_ms`, exit 8, `job_wait`, `job_cancel`, progress notifications and resource subscriptions on `frob://job/{id}` are all independent of Tasks |

**Fail-closed default until decided.** Job handles only.

## Acceptance criteria

- [ ] The decision function is tested code and, applied to the pilot's stored record, returns the recorded
      branch.
- [ ] The architecture decision record states the branch, the 20 jobs' outcomes, the disagreement count and the
      library commit.
- [ ] On the firing branch no served tool advertises task support (checked on the served tool list for a client
      that negotiates the extension) and the feature does not exist in `Cargo.toml`.
- [ ] On the surviving branch the default build has the feature off.
- [ ] The compatibility train's checklist includes the pilot re-run.
- [ ] The MCP acceptance gate's record states which branch was in force when it was measured.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_mcptasks.rs`:
- `pilot_not_run_is_undecided`; `nineteen_jobs_is_undecided`.
- `one_disagreement_fires`: (20, 1, true).
- `restart_loss_fires`: (20, 0, false).
- `clean_pilot_does_not_fire`: (20, 0, true).
- `incompatibility_overrides_clean_pilot`.
- `state_mapping_total`: every ledger state has exactly one row in the mapping.

### End-to-end script and logging
`scripts/e2e/kill_mcptasks_decision.sh`: reads the pilot record; recomputes the decision; connects an in-memory
client that negotiates the Tasks extension and one that does not, lists tools from both, and checks the
recorded branch's consequence (task support advertised to the first only on the surviving branch with the
feature on; to neither otherwise); on both branches runs one long job to exit 8 and completes it with
`job_wait`. NDJSON lines per the shared helper: `ts`, `script`, `bead`, `step`, `event`, the JSON-RPC request or
command, exit or error code, wall time, the `evidence` block, pilot jobs and disagreements against 20 and 0, the
recomputed branch against the record; `summary` names KILL-MCPTASKS.

### Known answers and negative controls
- Known answer: the handle contract on both branches: a job that outlives the wait returns exit 8 with a
  denominator in its progress, and `job_wait` later returns the result.
- Negative control: the adapter on the in-memory store, restarted mid-job: the Task is gone while the ledger job
  runs on; the pilot must count a disagreement.
- Negative control: a mapping that shows a preempted job as failed; the pilot must count a disagreement.
- Negative control: a decision recorded "does not fire" from a pilot of 12 jobs is rejected.

## Considerations

- The value at stake is small by the ceiling's own statement. The gate exists to stop a provisional protocol
  feature from becoming a second job model with its own states and failure modes.
- Wire cancellation of a Task must follow the surface's rule for waits: cancelling the wait is not cancelling
  the job, unless the call asked for that; cancelling a Task is defined as `job.cancel` and drains. The pilot
  covers both.
- If the extension stabilizes later with different semantics, re-opening is a new decision record.
