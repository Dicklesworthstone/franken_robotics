## Background

A kill gate is a decision written before the data that decides it. KILL-TUI governs whether FrankenRobotics
ships a terminal dashboard at all.

`frob-tui` is an optional program for a person watching a campaign: six panes (races, budgets, devices, queue,
failures, evidence) and a gate-status view, built on the suite's terminal UI library. It is an ordinary client
with no private interface: every number it shows comes from a named verb. Its ceiling was stated before any work:
a convenience; no claim and no agent workflow depends on it. That is why its kill gate has the cheapest fallback
in the program: no dashboard, with `job.list` and `session.show` carrying the same numbers and the daemon's
events available as line-delimited JSON.

Two things could make the dashboard not worth shipping, and they are the trigger. First, the build-graph rule:
every workspace of this project resolves exactly one asupersync package, and the terminal library has an
optional executor feature pinned exactly to an older asupersync version (FACT); the library must be admitted
with default features off and that feature forbidden, with one asupersync package or none in `frob-tui`'s
graph. Second, test stability: the dashboard's acceptance is a snapshot test per pane on a recorded daemon
trace, and a terminal renderer whose output cannot be made byte-stable would turn that gate into a flaky test
that people learn to ignore.

## Scope

In: the gate's definition; the decision function; the procedure; consequences by branch; the decision record.
Out: the dashboard (N32b-06 to -08); the measurements (N32b-09 and the admission gate in seed BD-300, which
records this decision's outcome with the dashboard-and-viewer gate); the viewer, which is unaffected.

## Technical approach

**The gate, as registered.**

| Field | Value |
|---|---|
| Kill gate | KILL-TUI |
| Decided at | The third milestone |
| Trigger | FrankenTUI cannot be admitted with one asupersync package; or the snapshot tests cannot be made stable |
| Measurements | (a) the number of distinct asupersync packages in `cargo tree -d -p frob-tui` (limit: at most 1) and whether the crate builds on the project toolchain with the executor feature off; (b) over 20 replays of the recorded trace on each of two platforms, the number of replays whose pane dumps differ from the stored snapshots, after at most one repair cycle (limit: 0 of 40) |
| Also read | The admission gate INT-FTUI-01 (one asupersync package or none; the job pane rendered from a recorded event stream equals its stored snapshot in the headless harness; idle processor use at most 2% of one core) |
| Fallback | No dashboard; `job.list` and `session.show` carry the same numbers |

**Decision function.**

```
decide(builds_on_T_without_executor: bool, asupersync_packages: u32,
       unstable_replays: u32, replays: u32, repair_cycles_used: u8,
       admission_gate: pass | fail | not-run)
  -> does-not-fire | fires | undecided
```

1. `builds_on_T_without_executor = false` or `asupersync_packages > 1`: fires. (If the library does not build on
   the project toolchain, the remedy is an upstream change in the library or the toolchain train; the crate gets
   no toolchain of its own, and until that lands the fallback is in force.)
2. `replays < 40` or `admission_gate = not-run`: undecided.
3. `unstable_replays > 0` and `repair_cycles_used = 0`: undecided; one repair cycle is allowed.
4. `unstable_replays > 0` and `repair_cycles_used ≥ 1`: fires.
5. `admission_gate = fail` (for example idle processor use above 2%) after one repair cycle: fires.
6. Otherwise: does not fire.

**Procedure.** (1) Read the measurement file written by the dashboard conformance script (package count, replay
stability, idle processor use, kill-safety and noninterference results) and the admission gate's record; check
commit, host fingerprint and that the script's negative controls were caught (a pane that prints local time; a
build with the executor feature). (2) Apply the function. (3) Write the architecture decision record and the
register row from a session that did not build the dashboard.

**Consequences by branch.**

| Outcome | What changes |
|---|---|
| Does not fire | `frob-tui` ships as an optional binary in the core workspace. `xtask check-deps` keeps refusing the executor feature and any physics dependency. The dashboard half of the dashboard-and-viewer gate is recorded from the conformance run |
| Fires | The crate is removed from the default workspace members and not shipped; the README and `robot-docs` say "no dashboard" and name the replacement commands: `frob job list --json` (queue, size classes, waits, preemptions, estimate calibration), `frob session show --json` (budgets, children, the daemon's overhead line), `frob capabilities --json` (gate status), and the daemon's event stream as line-delimited JSON. `frob capabilities` reports the dashboard `killed` with fallback "no dashboard". The dashboard half of the dashboard-and-viewer gate is recorded `killed`; the viewer half stands on its own. The pane definitions (which verb field a person reads for which question) are kept as a documentation page, because they remain true of the verbs |
| Either branch | No agent-facing behaviour changes; nothing else in the program depended on the dashboard |

**Fail-closed default until decided.** No dashboard is shipped or documented as available.

## Acceptance criteria

- [ ] The decision function is tested code; applied to the recorded measurements it returns the recorded branch.
- [ ] The architecture decision record gives the package count, replays and unstable replays, repair cycles
      used, idle processor use, the admission gate's result, and the measurement file's hash.
- [ ] On the firing branch: `cargo metadata` for the default workspace has no `frob-tui` member; the README says
      "no dashboard"; the three replacement commands return every number the panes would have shown (checked
      against the pane definitions' source pointers).
- [ ] On the surviving branch: `check-deps` fails on a planted executor feature.
- [ ] The register row is filled by a fresh session; the dashboard seed's gate record cites it.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_tui.rs`:
- `two_runtime_packages_fire`: (true, 2, 0, 40, 0, pass).
- `does_not_build_fires`: (false, 0, 0, 0, 0, not-run).
- `unstable_first_time_undecided`: (true, 1, 3, 40, 0, pass).
- `unstable_after_repair_fires`: (true, 1, 1, 40, 1, pass).
- `stable_and_admitted_does_not_fire`: (true, 1, 0, 40, 1, pass) and (true, 0, 0, 40, 0, pass).
- `too_few_replays_undecided`: (true, 1, 0, 39, 0, pass).
- `fallback_covers_every_pane_number`: every source pointer in the seven pane definitions names a verb among
  those available without the dashboard.

### End-to-end script and logging
`scripts/e2e/kill_tui_decision.sh`: reads `target/gates/GATE-TETHER-14.dashboard.json` and the admission record;
recomputes the decision; then checks the recorded branch from the user's side: on the surviving branch runs
`frob-tui --replay` and `--dump` once; on the firing branch runs the three replacement commands against a
seeded daemon and confirms each pane number has a field. NDJSON lines per the shared helper: `ts`, `script`,
`bead`, `step`, `event`, command, exit code, wall time, the `evidence` block, package count against 1, unstable
replays against 0 of 40, idle processor percent against 2, the recomputed branch against the record; `summary`
names KILL-TUI and INT-FTUI-01.

### Known answers and negative controls
- Known answer: the fallback loses no number: the Budgets pane's α schedule (αᵢ = α/[i·(i + 1)], sum spent
  α·n/(n + 1)) is returned by the scorecard verb with or without a dashboard.
- Negative control: a decision of "does not fire" recorded with two asupersync packages in the measurement file
  is rejected by the recomputation.
- Negative control: three repair cycles presented as one (the measurement file's history shows three snapshot
  regenerations) is rejected: cycles are derived from history.
- Negative control: a decision entered by the session that built the panes is refused by the recorder.

## Considerations

- An upstream work item exists to relax the library's exact pin on the older asupersync in its optional
  executor; it has low priority because nothing here needs the executor. If a future dashboard feature wanted
  it, that item would become a precondition and this gate would be re-read.
- Whether `frob-tui` stays in the core workspace or becomes an annex is an open question with default "core";
  the admission gate's build result is what would change it, and an annex would still be bound by the
  one-package rule.
- Killing the dashboard is cheap now and stays cheap only while no number is defined in a pane. That is the
  reason for the number-reproduction rule in its tests.
