## Background

A kill gate is a decision written before the data that decides it. KILL-REPLAYPACK governs one way of showing a
recorded episode to someone who was not at the terminal: the **offline replay packet**, a single HTML file
written by `telemetry.export-html` that replays a parent world and up to 16 counterfactual forks with overlays,
makes no network request, and is at most 8 MiB by default.

The packet is a view over records that already exist. It computes no fork, no attribution and no verdict and
contains no stepping code; it draws recorded rows. Its acceptance gate (GATE-TETHER-16, Known answer, third
milestone) asks, for two fixtures each with a parent and 16 forks: the file is at most 8,388,608 bytes; it opens
and plays from a local file with the network disabled in two pinned browsers under a headless driver; two
exports are byte-identical; every block digest equals the source's; 100 probe points per packet equal
`telemetry.query` within channel quantization; the null-fork deviation is zero; the over-cap request is refused
with its size table.

Two things can make the single file not worth keeping, and they are the trigger. The gate may keep failing:
browsers differ, files opened from disk are restricted in ways servers are not, and byte-identical export is a
strict requirement. Or the page may not fit its byte budget: the format reserves 600,000 bytes of the 8 MiB for
the page, which is tight for a page that vendors a 3D library. Everything the packet shows is available by
other means, which is why the fallback loses convenience and no information.

## Scope

In: the gate's definition; the decision function; the procedure; consequences by branch; the decision record.
Out: the packet writer, the page and the gate's measurement (N32b-40 to N32b-43, N32b-13, and the writer bead of
the telemetry cluster); the build packet (the manufacturing chapter).

## Technical approach

**The gate, as registered.**

| Field | Value |
|---|---|
| Kill gate | KILL-REPLAYPACK |
| Decided at | The third milestone |
| Trigger | GATE-TETHER-16 fails after one repair cycle; or the page cannot be held to its byte budget |
| Measurements | (a) the gate's record: seven clauses, each pass or fail, with measured values; (b) the page bundle's byte length from its build manifest against 600,000 bytes (TARGET), after one size-reduction cycle |
| Fallback | `run.export` to the run file format, stills with overlays (`telemetry.stills`) and the live viewer; no single-file packet |

**Decision function.**

```
decide(gate_clauses: [pass | fail; 7] | not-run, gate_repair_cycles_used: u8,
       page_bytes: u64, page_budget: u64, size_cycles_used: u8)
  -> does-not-fire | fires | undecided
```

1. Gate not run: undecided.
2. `page_bytes > page_budget` and `size_cycles_used = 0`: undecided; one reduction cycle is allowed (remove
   unused library modules, drop a minifier setting, move an overlay behind a build flag), recorded with the
   per-module size table before and after.
3. `page_bytes > page_budget` and `size_cycles_used ≥ 1`: fires.
4. Any gate clause failed and `gate_repair_cycles_used = 0`: undecided; one repair cycle is allowed.
5. Any gate clause failed and `gate_repair_cycles_used ≥ 1`: fires.
6. Otherwise: does not fire.

**Outcomes as the register writes them (N40-03).** "Does not fire" is recorded as `not-fired`, "fires" as
`fired`. `undecided` is not a recorded outcome: the bead stays open while an allowed cycle runs, and if the M3
exit arrives first (a cycle still running, or the gate not run because the fork-harness gates are not yet
recorded for the build) the entry is `deferred`, with `deferred_to` and the reason. The bead closes on any of
these. The measuring bead N32b-43 closes on its recorded measurement, passing or failing (its closing rule),
so this decision never waits on a pass.

The seven clauses, in the order recorded: file size at most 8,388,608 bytes; opens and plays offline in both
pinned browsers; two exports byte-identical; every block digest equals the source's; 100 of 100 probe points per
packet within quantization; null-fork deviation exactly zero; the over-cap request refused with its size table.

**Procedure.** (1) Read the gate record and the page manifest; check commit, host fingerprint, the pinned
browser versions, and that the gate's negative controls were caught (a writer that budgets by binary payload; an
exporter that stamps the time). (2) Apply the function. (3) Write the decision record
`docs/adr/ADR-KILL-REPLAYPACK-M3.md` (the one place every decision record lives; the kill-gate record form
with its required fields: gate, milestone, trigger as registered, the seven clause values and the page size
with the gate record's hash, branch taken, fallback in force, what changes downstream, the deciding session)
and the `decision` entry of the kill record in the register (`outcome`, `adr`, `date`, `session` and
`receipts`: the receipt hash of the run of GATE-TETHER-16, at least one for `not-fired`), from a session that
did not build the packet. Priority: this decision is one step more
urgent than its milestone's default, because the third-milestone exit review waits on it.

**Consequences by branch.**

| Outcome | What changes |
|---|---|
| Does not fire | `telemetry.export-html` stays, with fork sections licensed per build by the fork-harness gates. The 8 MiB default cap and the 15 MB ceiling stay as written |
| Fires | No single-file packet. `telemetry.export-html` answers with the refusal for a capability not in this build (`FROB-REF-724`, exit 5), naming the fallback; `frob capabilities` reports it `killed` with fallback "run export, stills, live viewer". The three replacements are documented in `robot-docs` with one worked example each: `frob run export <run>` (a manifest and column files readable with no device and no daemon, checked offline by the auditor); `frob telemetry stills <run> --world <w> --at failure --overlay contact-cones,film` (contact sheets with the same overlays, and `telemetry.inspect-pixel` for the quantity under a pixel); the live viewer on a daemon (live mode, N32bp1-01, where it is shipped; under its own fail-closed default it is not, and then the viewer page has no source left, so the fallback is `run export` with stills and `telemetry.inspect-pixel`, which carry every overlay quantity, and the documentation says so). The fork ghost and tables remain available in the live viewer where shipped and, in every case, through the fork and attribution verbs. A build packet omits its optional replay file and is otherwise unchanged. The packet format and the page's packet-reading code are removed from the tree; the viewer's overlays are untouched |
| Either branch | No evidence changes: a packet is a view, importing one creates no evidence, and no verdict ever depended on one |

**Fail-closed default until decided.** Parent-only packets may be exported for development; none is cited in a
report or attached to a build packet.

## Acceptance criteria

- [ ] The decision function is tested code; applied to the recorded gate clauses and page size it returns the
      recorded branch.
- [ ] The architecture decision record lists the seven clause results with measured values, the repair and size
      cycles used, the page's byte length and the gate record's hash.
- [ ] On the firing branch: `frob telemetry export-html` returns `FROB-REF-724` naming the fallback; a build
      packet is produced without a replay file and passes its own checks; the three replacement commands run on
      the gate's two fixtures.
- [ ] On the surviving branch: the default cap is 8,388,608 bytes and an over-cap request is refused.
- [ ] The kill record's `decision` entry carries one of the registered outcomes and is filled by a fresh session.

## Test plan

### Unit tests
`crates/frob-conformance/tests/kill_replaypack.rs`:
- `gate_not_run_undecided`.
- `page_over_budget_first_time_undecided`: 640,000 bytes, 0 cycles.
- `page_over_budget_after_cycle_fires`: 600,001 bytes, 1 cycle; `page_at_budget_ok`: 600,000 bytes.
- `one_clause_failed_first_time_undecided`; `one_clause_failed_after_repair_fires` (the byte-identity clause).
- `all_clauses_pass_does_not_fire`.
- `outcome_words`: does-not-fire maps to `not-fired` and fires to `fired`; an `undecided` result at the M3 exit
  is written `deferred` with a non-empty `deferred_to` and `reason`; a decision entry with any other outcome
  word is refused by the register's loader.
- `payload_ceiling_from_page_size`: with a 600,000-byte page the binary payload ceiling is
  (8,388,608 − 600,000) × 3/4 = 5,841,456 bytes; with a 500,000-byte page it is 5,916,456 bytes.

### End-to-end script and logging
`scripts/e2e/kill_replaypack_decision.sh`: reads the gate record and the page manifest; recomputes the
decision; checks the recorded branch from the user's side: on the surviving branch exports one packet from the
docking fixture and runs `--check` on it; on the firing branch runs `frob telemetry export-html` (expects exit
5), then `frob run export <run> --out <dir under the export root> --key "$(e2e_key krp-export)" --json` (a run
verb: it carries a key, written with `e2e_key`), `frob telemetry stills … --overlay contact-cones` and `frob telemetry inspect-pixel`
on the same run, and, where live mode is shipped, opens the run in the live viewer (log
`target/e2e-logs/kill_replaypack_decision/<utc>.ndjson` with a transcript). NDJSON lines per the shared helper: `ts`, `script`, `bead`, `step`, `event`, command, exit
code, wall time, the `evidence` block, the seven clause values against their thresholds, page bytes against
600,000, the recomputed branch against the record; `summary` names KILL-REPLAYPACK and GATE-TETHER-16.

### Known answers and negative controls
- Known answers: the size arithmetic above; a 6,200,000-byte request is 8,266,667 bytes encoded and 8,866,667
  with the page, over the cap.
- Negative control: a decision of "does not fire" recorded while the byte-identity clause is `fail` is rejected
  by the recomputation.
- Negative control: a page held under budget by silently dropping an overlay that the header's channel table
  still lists; the gate's probe clause fails for that overlay, so the record is not a pass.
- Negative control: a decision entered by the session that built the writer is refused by the recorder.

## Considerations

- The second trigger is about engineering cost, not correctness: a page that needs repeated surgery to stay
  under 600,000 bytes will keep costing. One reduction cycle is the stated allowance.
- Raising the cap is not a repair. The 8 MiB default and the 15 MB ceiling are part of the format; a different
  cap would be a new format version with its own gate.
- The two fallbacks interact: if KILL-REPLAYPACK fires and live mode was not shipped (its origin question,
  N32bp1-01), no page draws a recorded episode at all. That outcome is acceptable (no claim depends on a
  picture) but must be stated in the decision record and in `robot-docs`, not discovered.
- WebGPU is not a way out of the byte budget or the offline clause: it is exposed only in secure contexts, and
  whether a file opened from disk is one is left to the browser, so the packet's page must work with WebGL 2.
