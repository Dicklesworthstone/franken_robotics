## Background

Agents see FrankenRobotics over MCP through **task clusters**: at most seven tools chosen for one activity, plus
three base tools that are always listed (`session_focus`, `job_wait`, `job_cancel`). An agent switches activity
with `session_focus {cluster}`: the server enables the target cluster's tools and disables the previous
cluster's for that session, the MCP library then omits disabled tools from `tools/list`, refuses a direct call
to one, and emits its catalog-changed notification. This keeps an agent's context small (TARGET: the base tools
plus one cluster occupy at most 12 kB of `tools/list`) while the registry holds about 160 verbs.

That design assumes two things about the client, the agent harness, which this project does not control. First,
that it speaks a protocol era the library serves: the library's automatic policy serves MCP 2026-07-28 clients
and the exact 2024-11-05 handshake (FACT, read 2026-11-21). Second, that it acts on a catalog-changed
notification by listing tools again. A harness that lists tools once at start-up and never again would keep
showing the old cluster and never see the new one.

This is the open question OPEN-TETHER-2 (owner: Tether lead; it blocks the MCP acceptance gate, whose focus
clause reads "after `session_focus` the list holds at most seven tools plus the base three"). Its fail-closed
default is already designed: static clusters fixed by a launch flag, plus one generic tool `verb_invoke` for
clients that never re-list. This bead is the experiment that replaces the default with a measured mode per
harness, and records the default where a harness cannot do better.

## Technical approach

**The four focus modes, best first.**

| Mode | How the visible set changes | Needs from the client |
|---|---|---|
| `dynamic` | `session_focus` enables and disables tools per session; the list changes | Session state on the connection; re-listing after the catalog-changed notification |
| `tag-filter` | The client lists with `includeTags: ["task:<cluster>"]` (and the base tools' tag); `session_focus` returns the names and one-line purposes of the cluster's tools | The ability to pass list filters; no notification handling |
| `static` | The server is launched with `--clusters a,b`; the listed set is fixed for the process | Nothing; the operator picks clusters per agent role |
| `invoke` | One generic tool `verb_invoke {verb, arguments}`, validated against the verb's schema, beside the base tools; the agent reads `robot-docs` for what exists | Nothing |

In every mode authority is the capability token, not the visible set.

**Probe suite** (`surface/frob-mcp/tests/client_probe/` plus a recorder that sits between a real harness and the
server and logs JSON-RPC frames; the probe server is the real `frob-mcp` with the M1 verbs).

| Probe | Observation recorded |
|---|---|
| P1 handshake | The protocol version the client offers and the one negotiated; whether the 2024-11-05 handshake is exact |
| P2 initial list | Whether the client pages `tools/list` (follows `nextCursor`) when the server's page size is small |
| P3 re-list on notification | After `session_focus` and the catalog-changed notification, whether a new `tools/list` arrives within 10 s, and whether the model's next call can use a newly enabled tool without restarting the harness |
| P4 stale call | Whether the harness still offers a disabled tool to the model, and what it does with the refusal |
| P5 list filters | Whether the harness can be configured to send `includeTags` |
| P6 progress | Whether it sends a progress token and surfaces progress notifications |
| P7 cancellation | Whether its own tool-call timeout or a user interrupt sends a wire cancellation; its tool-call timeout in seconds |
| P8 resources and prompts | Whether it lists and reads resources, subscribes to `frob://job/{id}`, and exposes prompts |
| P9 structured content | Whether it passes `structuredContent` (the envelope) to the model, or only text |

**Harnesses.** Every agent harness in use by the owner's swarm tooling at the time of the experiment, each
recorded by name, version and launch configuration; at least the two most used over stdio and one over loopback
HTTP. The list is data in the result, not fixed here.

**Decision rule (per harness, pure function of the probe record).**

1. P1 fails (neither era): the harness cannot use `frob-mcp`; recorded as CLI-only with the skill file.
2. P3 passes and P4 shows no stale offers: `dynamic`.
3. Else P5 passes: `tag-filter`.
4. Else: `static`, with `invoke` enabled in addition if the agent's role needs verbs outside its static clusters.

Secondary settings recorded from the probes: if P9 fails, the server's text content carries a compact rendering
of the envelope (exit, refusal code, `next_actions`) for that harness; if P7's timeout is below the maximum
bounded wait plus margin, the harness's row caps `sync_wait_ms` (input to N32b-34); if P6 fails, progress is
read with `job_wait`.

**Outputs.** (a) `registries/mcp_clients.toml`: one row per harness and version with the nine observations, the
chosen mode and the launch line. (b) A page contributed to `robot-docs` ("connecting your harness") generated
from that table. (c) A recorded decision closing OPEN-TETHER-2 with the table's digest; the fail-closed default
remains the rule for any harness not in the table. (d) For the MCP acceptance gate: the focus clause is measured
in `dynamic` mode on the in-memory transport (the server's behaviour) and, for each harness in the table, in its
chosen mode (what an agent actually sees), and both are recorded.

## Acceptance criteria

- [ ] The probe suite runs against the real `frob-mcp` for each listed harness and writes a frame log per probe.
- [ ] `registries/mcp_clients.toml` exists with a row per harness: nine observations, mode, launch line.
- [ ] The decision rule is tested code; each row's mode equals the rule applied to its observations.
- [ ] For each harness, an end-to-end focus switch in its chosen mode shows the model able to call a tool of the
      new cluster, with at most seven cluster tools plus the base three visible (or, in `invoke` mode, the
      generic tool).
- [ ] A harness absent from the table is launched in `static` mode with `invoke` (the fail-closed default), and
      the documentation says so.
- [ ] OPEN-TETHER-2 is closed by a recorded decision citing the table.

## Test plan

### Unit tests
`crates/frob-conformance/tests/open_tether_2.rs`:
- `rule_dynamic`: P1 ok, P3 ok, P4 clean gives `dynamic`.
- `rule_tag_filter`: P3 fails, P5 ok gives `tag-filter`.
- `rule_static_default`: P3 and P5 fail gives `static`.
- `rule_cli_only`: P1 fails.
- `table_rows_match_rule`: every row of the registry file.
`surface/frob-mcp/tests/focus_modes.rs` (in-memory transport, real server): `dynamic_list_changes_and_notifies`;
`tag_filter_lists_seven_plus_base`; `static_clusters_fixed`; `verb_invoke_validates_against_schema` (a misspelt
argument is refused with `FROB-REF-802`); `disabled_tool_call_refused`.

### End-to-end script and logging
`scripts/e2e/mcp_client_probe.sh <harness-config>`: launches the recorder and `frob-mcp`, drives the harness
through a scripted prompt that asks it to list tools, focus on `author`, and call `design_check`; runs P1 to P9;
writes the observations. Log: `target/e2e-logs/mcp_client_probe/<utc-timestamp>.ndjson` and a transcript; every
line has `ts`, `script`, `bead`, `step` (the probe), `event`, the JSON-RPC method or command, exit or error
code, wall time, the envelope's `evidence` block where a tool was called, the observation with its threshold
(re-list within 10 s; visible tools against 7 + 3), and on failure the frame log's path. The `summary` line
gives the chosen mode. Model prompts and outputs are not logged beyond tool calls.

### Known answers and negative controls
- Known answer (server side): after `session_focus {cluster: "mission"}` in `dynamic` mode the list holds
  `mission_new`, `mission_check`, `mission_synthesize`, `mission_refute`, `mission_distinguish`, `mission_show`,
  `result_revalidate` and the three base tools.
- Negative control: a scripted client that ignores the notification must be classified `static` or `tag-filter`,
  never `dynamic`.
- Negative control: a scripted client that offers a stale disabled tool must fail P4.
- Negative control: a server build with a cluster of eight tools must fail the visible-set assertion.

## Considerations

- Harnesses change faster than this project's milestones. The table is keyed by version, the probe is cheap to
  re-run, and an unknown version gets the default.
- `static` mode with role-specific clusters is not a degraded experience for a swarm in which each agent has one
  job; the suite's mail server runs that way (FACT). The cost falls on a single generalist agent.
- `invoke` mode gives up per-tool schemas in the tool list, so the model relies on `robot-docs` and on refusals
  to learn argument names; it is the last resort for that reason.
- The library itself calls its newest protocol era unverified; a harness that negotiates it may hit library
  defects, which are recorded as upstream work items, not worked around here.
