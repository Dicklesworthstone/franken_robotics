## Background

The viewer of FrankenRobotics is a web page (`viewer/`, Three.js, not Rust), and the offline replay packet is a
single HTML file that embeds that page. Both are tested by loading them in a real browser that nobody watches: a
*headless* browser driven by a script. Several pieces of work depend on such a lane: the page's own tests, the
packaging check that the bundle makes no network request, the viewer conformance script that compares an overlay
value under a pixel with the telemetry channel, the FrankenThreeD packaging pilot that compares rendered frames,
and the acceptance gate of the replay packet, GATE-TETHER-16, whose second clause reads: the file "opens and
plays from a local file with the network disabled in two pinned browsers under a headless driver".

A browser is foreign software that updates itself, and a test that passes on "whatever browser is installed"
proves nothing reproducible. The gate therefore says *pinned*: the exact builds are named, their hashes are
recorded, and a run states which build it used. No other bead owns those pins, the driver or the way networking
is switched off, so each consumer would otherwise invent its own. This bead owns them once. Tier Solid: this is
test tooling, with no physics and no claim of its own.

Decision recorded here (DESIGN). Two engine families are pinned, one Chromium-family build and one Gecko-family
build, so that an accident of one implementation cannot decide a gate. Rejected: one browser (a quirk of its
local-file handling would pass or fail the gate alone); the browser installed on the host (not reproducible);
a browser embedded as a Cargo dependency (the rule of the workspace is that Node and browser tooling are
development-only and never enter the build graph of any `frob` binary).

## Scope

In: the pin file `tools/browsers.lock`; the fetch-and-verify script; the launcher module used by every viewer
test runner; switching networking off at two levels, and the one narrower mode that allows loopback only; forcing a software rasterizer; the request log and console
log readers; the record of browser name, version and hash on every test line; the lane's self-test and its
negative controls; the admission record of the tools as development-only.
Out: the page and its test entry `window.__frobViewerTest` (N32b-10); the page's packet reader (N32b-40); the
bundle and its byte budgets (N32b-13); the conformance and gate scripts that use this lane (N32b-14, N32b-43);
the FrankenThreeD pilot's frame comparison (N33c-24); the supply-chain rules for vendored libraries (BD-306).

## Technical approach

**1. The pin file** (`tools/browsers.lock`, TOML; DESIGN). One table per tool and platform:

```
[[browser]]
name      = "chromium"            # or "firefox"
family    = "chromium"            # chromium | gecko
version   = "<exact build string>"
platform  = "linux-x86_64"        # and "macos-arm64": the two machines of the project
archive_sha256 = "<64 hex>"
binary_sha256  = "<64 hex>"
driver    = { name = "<driver binary>", version = "<exact>", sha256 = "<64 hex>" }
source    = "<where the archive was obtained; provenance only>"

[node]
version = "<exact>"               # the runtime of viewer/build/*.mjs
sha256  = { "linux-x86_64" = "<64 hex>", "macos-arm64" = "<64 hex>" }
```

The exact builds are chosen when this bead is executed and are not fixed here; what is fixed is that there are
two families, each on both platforms, each with a binary hash. The file has a digest (BLAKE3 of its canonical
bytes) that every test log line carries.

**2. Fetch and verify** (`tools/browsers/fetch.sh`, development-only). Downloads each archive into
`target/browsers/<name>-<version>-<platform>/`, verifies the archive hash, unpacks, verifies the binary and
driver hashes, and writes nothing elsewhere. A hash mismatch stops with exit 1 and the two hashes; nothing is
left unpacked. With `--offline` it verifies an existing cache and downloads nothing. Browsers are never
installed system-wide, never auto-update (the update mechanism is disabled by launch options and the unpacked
directory is read-only), and are never redistributed.

**3. The launcher** (`viewer/build/browser.mjs`). One function, `launch(name, options)`, returning a session:
- it refuses to start unless the binary on disk hashes to the value in the lock (checked at every launch);
- it starts the browser headless through the browser's standard automation protocol, with a fresh profile
  directory under `target/`;
- **networking off, twice.** At the browser level the session is put offline and given a proxy that points at a
  closed loopback port, so that any request fails and is logged. At the host level the browser process is
  started without a route: on Linux in an empty network namespace; on macOS under a sandbox profile that denies
  network access. If host-level isolation cannot be set up, the session reports `host_isolation: unavailable`,
  and a caller that needs the clause (the packet gate) records `not run` with that reason, never a pass;
- **loopback only, for live mode.** `launch(name, { network: "loopback" })` is the one other mode (the default is
  `"off"`), used by live mode's tests (N32bp1-01) to reach a daemon on the same host. At the browser level the
  proxy keeps pointing at the closed port, with a bypass list of exactly `127.0.0.1` and `[::1]`. At the host
  level, on Linux the browser runs in a fresh network namespace whose only interface is loopback, and the
  launcher exposes `isolatedLoopback(command)` so that the caller starts the daemon under test inside the same
  namespace; on macOS the sandbox profile allows connections to `localhost` only. Every other request still fails
  and is logged, and the session's launch line records `network: loopback`. A packet or bundle test that is
  launched in this mode is refused by the launcher (a test declares its mode, and the packet and bundle runners
  declare `"off"`);
- **software rasterizer.** Rendering is forced onto the browser's software path so that the lane runs on a host
  without a GPU and gives the same pixels twice; the session reports whether WebGL 2 is available and stops with
  a clear error if it is not;
- session methods: `open(fileUrl)` (only `file://` URLs are accepted), `evaluate(expression)` (used to call the
  page's test entry), `requestLog()` (every request the page attempted, with its URL), `consoleErrors()`,
  `pixels(rect)` (raw RGBA of a rectangle), `close()`.

**4. What every run records.** The launcher writes one NDJSON line at launch and one at close through the shared
logging helper: browser name, family, version, binary hash, driver version, platform, the lock digest, whether
host isolation was in force, the rasterizer in use, and at close the counts of attempted requests and console
errors. Gate records (for example the record of GATE-TETHER-16) copy these fields.

**5. Self-test.** `viewer/tests/fixtures/selftest.html` (labelled `synthetic`): an inline-script page that draws
one triangle with WebGL 2 at fixed coordinates and sets `window.__frobViewerTest = { ready: true }`. The
self-test opens it in both browsers and checks readiness, an empty request log, no console error, and that the
pixel at the triangle's centroid has the triangle's colour and the pixel at a corner has the clear colour.

**6. Admission.** The browsers, their drivers and the Node runtime are entered as development-only tools in the
dependency admission record (name, version, hash, use, confinement: test tooling outside every Cargo workspace,
fallback: the lane is `not run`). Moving a pin is a recorded change: the lock changes, the self-test and the
consumers' tests are re-run, and the admission record is updated in the same change.

Determinism: with the software rasterizer the self-test's pixel dump is identical twice on one machine; across
platforms only the probed pixels are compared, not whole frames. Evidence class of anything this lane reports:
`Tested`, with the browser builds named.

## Acceptance criteria

- [ ] `tools/browsers.lock` names one Chromium-family and one Gecko-family build, each for `linux-x86_64` and
      `macos-arm64`, each with archive, binary and driver hashes, and the Node runtime with its hashes.
- [ ] `tools/browsers/fetch.sh` verifies every hash; a tampered archive or binary stops it with exit 1 and both
      hashes printed; `--offline` downloads nothing.
- [ ] `launch` refuses a binary whose hash differs from the lock, and a browser that reports a version other
      than the pinned one.
- [ ] The self-test passes in both browsers on both machines: ready, 0 requests, 0 console errors, the two
      probed pixels as expected; its pixel dump is identical twice on one machine.
- [ ] A page that attempts a network request is detected: the request appears in `requestLog()` and fails.
- [ ] In `"loopback"` mode a request to a daemon on `127.0.0.1` inside the isolated namespace succeeds, and a
      request to any other address fails and is logged; a runner that declares `"off"` cannot obtain a
      `"loopback"` session.
- [ ] Where host-level isolation is unavailable the session says so, and the self-test reports that clause as
      `not run`.
- [ ] Every launch and close writes its NDJSON line with name, family, version, binary hash and lock digest.
- [ ] No Cargo manifest in the repository gains a dependency from this bead (`xtask check-deps` unchanged), and
      the tools appear in the admission record as development-only.

## Test plan

### Unit tests
`viewer/tests/lane/` (run by `viewer/build/test.mjs`):
- `lock_parses_and_is_complete`: two families × two platforms; every hash is 64 hexadecimal digits.
- `launch_refuses_hash_mismatch`: a copied binary with one byte changed is refused before it is started.
- `launch_refuses_version_drift`: a lock row with another version string than the binary reports is refused.
- `open_accepts_file_urls_only`: an `http://` URL is refused by `open`.
- `selftest_ready_both_browsers`; `selftest_pixels`: centroid pixel equals the triangle colour, corner pixel the
  clear colour.
- `request_log_catches_fetch`: `viewer/tests/fixtures/fetches.html` (synthetic) calls `fetch` on a remote URL
  and loads a remote image; both appear in the log and neither succeeds.
- `console_errors_are_read`: a page that throws at load yields one console error.
- `loopback_mode_reaches_loopback_only`: in `"loopback"` mode the planted page reaches a test server started with
  `isolatedLoopback` on `127.0.0.1` and fails its remote `fetch` (both logged); in `"off"` mode the loopback
  request fails too.
- `off_runner_cannot_get_loopback`.
- `pixel_dump_repeatable`: two launches, identical bytes for the self-test rectangle.

### End-to-end script and logging
`scripts/e2e/viewer_browsers.sh` (header `bead=N32b-44 milestone=M2 labels=tether,viewer,gauntlet seed=44
needs=cpu plants=fetching-page,tampered-binary,isolation-skipped`, each plant one negative control below; no
gate): runs `tools/browsers/fetch.sh --offline` (or a fetch when the cache is empty),
then the self-test and the two planted pages in each browser, then the loopback-mode check against a test
server started with `isolatedLoopback`. It sources the shared helper and writes
`target/e2e-logs/viewer_browsers/<utc-timestamp>.ndjson` and a transcript; every line has `ts`, `script`, `bead`,
`step`, `event`, the command line, exit code and wall time; `metric` lines give requests attempted (threshold 0
for the self-test, at least 2 for the planted page), console errors, and the lock digest; `assert` lines cover
hash verification, readiness and the probed pixels with expected and found values; on failure the first
differing hash or pixel and the path of the profile directory. The `summary` line names the browsers used and
states that no gate is claimed by this script.

### Known answers and negative controls
- Known answer: the self-test's two probed pixels (triangle colour at the centroid, clear colour at the corner).
- Negative control: the planted fetching page must be caught by the request log; a lane that reported it clean
  would make the "no network request" clauses of the bundle and of the packet gate unfailable.
- Negative control: a tampered binary must be refused at launch.
- Negative control: with the host-level isolation deliberately skipped, the session must report it as
  unavailable and must not report the clause as passed.
- Determinism lanes: the self-test twice on one machine; on both platforms (probed pixels only).

## Considerations

- Local files are the hard case: browsers restrict what a page opened from disk may do, and they differ. That is
  the reason the gate asks for two browsers and the reason this lane accepts `file://` only.
- The pinned builds are obtained for development and test and are not redistributed; their licences are noted
  in the admission record. Nothing here ships to a user.
- A browser family may stop offering a software WebGL 2 path on one platform. Then that family's row for that
  platform is recorded as unavailable, the lane is `not run` there, and the pin is moved by a recorded change;
  the gate is not weakened to one browser.
- Hardware rendering is exercised by nobody's gate through this lane; frame rates are neither measured nor
  claimed.
- The supply-chain rules for vendored viewer libraries and exact pins apply to these tools as well once they
  are gated; until then the hashes in the lock are the control.
