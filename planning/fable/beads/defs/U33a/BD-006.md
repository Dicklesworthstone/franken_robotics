## Background

**ADR-SUITE-01 (DESIGN): FrankenSim is consumed by path dependency, confined behind the airlock crate
`frob-fsim`, pinned by commit in `franken-stack.lock`.**

The owner's brief is to use FrankenSim for the physics to the greatest extent possible. The referee tier (the
most trusted simulation tier) needs FrankenSim's multibody crate `fs-mbd` and contact crate `fs-contact` whole,
with geometry, integrators, optimizers and the ledger. Those two crates are about 438 thousand lines with their
tests (FACT: 291,848 and 146,603 lines of Rust). Copying that would be a fork. What is consumed and what is owned
is stated plainly: FrankenSim is the referee and the source of geometry kernels, structure-preserving
integrators, optimizers, statistics and the design ledger; the batched engine (kernel library, fixed-step convex
compliant solve, model-variant tables, GPU backends, the gym) is FrankenRobotics code.

Two sibling products chose otherwise, and their reasons must be answered. FrankenMining rejected a Cargo
dependency on FrankenSim because it would link two asupersync versions, needs a different nightly for one
crate's const-generic feature, failed `cargo check` on fifteen targets at the time, and uses out-of-repository
relative paths; its stack lock records `posture = "lift"` (FACT: `franken_mining/franken-stack.lock`, row
`FD-FSIM-00`). FrankenTextiles lifts files one by one. Why the decision differs here:

1. *The need is different in kind.* Those products took numerics files. This one needs the multibody and
   contact engines.
2. *The mechanism has precedents, and their limit is known.* Five crates sit outside FrankenSim's workspace with
   their own `[workspace]` table and consume `fs-*` crates by path (`apps/instrument-lab/render-gpu`,
   `apps/instrument-lab/render-gpu-piano`, `apps/pocket-watch/engine-watch`, `crates/fs-cmaes-viz-wasm`,
   `crates/fs-flyer-wasm`), but all five live inside FrankenSim's directory tree and inherit its
   `.cargo/config.toml`. One project outside the tree consumes four crates by path
   (`jazz_chord_progression_editor_html/tools/piano-v2-soundboard-pack`) and carries no patch entry, no toolchain
   file and no build-identity setting, so it is not evidence that an out-of-tree build passes today. **This gate
   is the first measurement of the out-of-tree case.**
3. *Each objection has a mitigation that is a gate.* One toolchain T for the whole graph (INT-TOOLCHAIN-01); the
   workspace root repeats three things Cargo does not propagate from a path dependency; exactly one asupersync
   package per build (INT-ASUP-01); volatile types named in one crate only.
4. *The fallbacks are written down, in order*: a pinned FrankenSim worker process, then a lift (KILL-FSIM).

This is the measurement that bet BET-04 stands on ("FrankenSim can be consumed by path from outside its tree,
stably, and the nightly coupling through its units crate does not block the core"; falsifier: this gate or
INT-TOOLCHAIN-01 fails, or upstream breakage costs more than 20% of working days in any four-week window).

**Known hazards on the day of reading (FACT, 2026-11-21; each is re-read at the pin by bead N33a-09, never copied
into a record):** (1) churn: 409 commits touched `crates/fs-mbd` in thirty days, on 17 distinct days; (2) an
unfrozen composition contract (`COMPONENT_CONTRACT_VERSION` is 0); (3) a stale constellation lock (it pins
asupersync 0.5.0 while the lockfile resolves 0.6.2 by path); (4) a nightly feature, `generic_const_exprs`, in
the units crate `fs-qty`; (5) `fs-la/build.rs` panics unless `FRANKENSIM_DEPGRAPH_RECEIPT` or
`FRANKENSIM_DEPGRAPH_SALT` is set, and outside the tree nothing sets it; (6) a large closure: a path dependency
on `fs-mbd` compiles 42 other FrankenSim crates and about 1.57 million lines of library source, the crate set M1
needs is 65 crates and about 2.06 million lines, and FrankenSim's lockfile holds 479 packages of which 262 come
from the registry; (7) a contact capacity of 21; (8) dirty trees (32 modified paths at head `483d09c682f2`).

## Technical approach

**What is built.** The crate `crates/frob-fsim` with path dependencies on exactly five FrankenSim crates:
`fs-ga` (geometric algebra and Lie façades), `fs-mbd` (multibody), `fs-contact`, `fs-time` (integrators) and
`fs-query` (geometry queries), default features off unless the crate needs one to compile (each such feature is
recorded). The crate holds one integration test, `tests/admission_int_fsim_01.rs`, that names one public item
from each of the five crates and calls one function of each on a trivial input, so that `cargo check
--all-targets` proves the whole closure type-checks and links from this repository.

**The three root settings (HYPOTHESIS: Cargo propagates none of them from a path dependency; FrankenSim's own
manifest states this for profiles, and this gate settles it for patches and `[env]`).**
1. `[patch.crates-io] asupersync = { path = "../asupersync" }` in the root `Cargo.toml`, repeating FrankenSim's
   entry so that the graph holds one asupersync package.
2. FrankenSim's FrankenSQLite profile overrides (`[profile.dev.package.fsqlite…]` and kin), copied from
   FrankenSim's manifest at the pinned commit by reading it, not from design text.
3. The build-identity environment in the root `.cargo/config.toml`: `[env] FRANKENSIM_DEPGRAPH_SALT =
   "franken-robotics-dev-v1"`, naming this project's own development equivalence class (bead N33a-08).

**Procedure.**
1. Run `xtask check-stack --write-receipt --reason admission --gate INT-FSIM-01`; record the receipt hash and the
   drift class (on-pin, stale-lock or drift) of every sibling. Whether each difference from FrankenSim's own
   lock is a fast-forward or a divergence is classified, not assumed.
2. *Candidate (a).* With `rust-toolchain.toml` naming the suite's common nightly (`nightly-2026-08-31` on the
   day of reading), run `cargo check --all-targets -p frob-fsim` through the build-offload shim, from an empty
   target directory, under a one-hour timeout and with at most 8 jobs. This is the **cold check**.
3. If (a) fails, capture the first failing crate and error verbatim, then repeat step 2 on *candidate (b)*,
   FrankenSim's present pin (`nightly-2026-07-06`, rustc 1.99.0-nightly). Record which candidate builds. If
   `fs-qty` is what fails on (a), record that separately: it selects the upstream change (macro-generated
   dimension products behind a feature, or removing `fs-qty` from `fs-evidence`) over a local workaround.
4. **Warm check**: rerun the same command with no change, then after touching one source file of `frob-fsim`.
5. Measure for the cold run: wall time; peak resident memory of the whole cargo process tree, which is the
   figure compared with the 16 GiB limit (DESIGN, the same statement in N41-19: the envelope bounds the machine,
   and eight compiler processes that are each small can together exceed it). The tree total is the peak of the
   summed resident memory of the tree as the offload shim samples it on the worker that ran the build; the
   largest single process (the maximum resident set size that `/usr/bin/time -v` on Linux and `/usr/bin/time -l`
   on macOS report) is recorded beside it and is not the figure compared; the number of FrankenSim crates
   compiled; lines of library source compiled (counted from the manifests' package list); the package count of
   the tracked `Cargo.lock` and how many come from the registry.
6. **Necessity tests**, each in a scratch copy: remove the patch entry (expected: a second asupersync package in
   `cargo tree -d`, or a resolution error); remove the profile overrides (expected: builds; the difference in
   test time is recorded); unset the build-identity variable (expected: `fs-la`'s build script panics and the
   build **fails closed**).
7. Write the admission record (schema `frob.admission/1`): the command, its output hash and excerpt, this
   repository's commit, the receipt hash, FrankenSim's revision, the candidate, the measured values against the
   thresholds, the necessity-test outcomes, the drift classes. A failing result is recorded as failing; the step
   is not repeated until it happens to pass.

**Thresholds (TARGET until recorded).** The cold check fits the machine envelope: at most one hour of wall
time, 16 GiB of memory and 8 cores. `cargo check --all-targets` exits 0. Exactly one asupersync package in the
graph (proved formally by INT-ASUP-01; observed here).

**Fail-closed rule.** The build-identity variable has no default in any build script of this repository. A
missing value stops the build with FrankenSim's own panic message; it is never papered over with an `unwrap_or`.

Determinism and evidence: the record is evidence class `Tested` for "the closure type-checks at this pin on
this toolchain"; it makes no claim about physics. The costs are measurements on a named host.

## Test plan

### Unit tests (`cargo test -p frob-fsim --test admission_int_fsim_01`)
- `links_five_crates`: one public item of each of `fs-ga`, `fs-mbd`, `fs-contact`, `fs-time`, `fs-query` is named and a trivial call of each returns (the items are chosen at the pin and listed in the record).
- `build_identity_is_set`: `option_env!("FRANKENSIM_DEPGRAPH_SALT")` (or the receipt variable) is `Some` at compile time; the test prints which.
- `one_asupersync_in_metadata`: parsing `cargo metadata` output of the core workspace finds exactly one package named `asupersync`.
- `closure_counts_recorded`: the counted FrankenSim crates in the graph equal the number in the record (guards against a stale record).

### End-to-end script and logging
`scripts/e2e/admission_m0.sh` (bead N33a-28), steps `int_fsim_01_cold`, `int_fsim_01_warm`,
`int_fsim_01_necessity`: runs the commands above for real, writes the record, and asserts exit codes. Each NDJSON
line carries the command line, exit code, wall time, peak memory in bytes, the candidate, the receipt hash, each
measured value with its unit and threshold, and on failure the first failing crate and error line. The
necessity step logs three `assert` events (patch removed, overrides removed, salt unset) with observed outcomes.

### Known answers and negative controls
- Negative control (registered for INT-FSIM-01): the build with the build-identity variable unset must fail; if it succeeds, the gate has not passed, whatever the positive test says.
- Negative control: a record written for a commit whose lockfile lacks `fs-mbd` is refused by the validator of N33a-07.
- Sibling facts re-read and stored in the record: package counts 479 and 262; closure sizes 42 crates and about 1.57 million lines, 65 crates and about 2.06 million lines. A changed value is a finding, not an error.
- Determinism lanes: `cargo check` twice with no change does no work the second time (the warm figure); the record's measured counts are identical on the Mac and on `trj` for the same commits.

## Considerations

- **KILL-FSIM** watches this gate: it fires if INT-FSIM-01 cannot pass within two weeks of M0 effort, or its cold check exceeds the machine envelope, or upstream breakage exceeds 20% of working days in any four-week window. Fallback (a): one pinned FrankenSim worker process per device exchanging whole jobs through the airlock traits. Fallback (b), only if (a) fails its own gate or the pin can no longer be built: lift the minimal referee set. The lift is priced against a closure of about 1.5 million lines, not against two crates, which is why these build costs are recorded.
- OPEN-SUITE-5 (budget for the cold build of the M1 closure on the build workers): default the machine envelope; decided by this gate's numbers and the owner. OPEN-SUITE-3 (dirty asupersync checkout for development): default yes for development with the tree hash in the receipt, and no PASS.
- RISK-01 (FrankenSim API churn), RISK-02 (the toolchain train) and RISK-23 (dirty trees) all read this record.
- No sibling checkout is modified. If FrankenSim does not build on candidate (a), the remedy is an upstream change in FrankenSim's repository under its own rules (its toolchain file is advanced there), and T is candidate (b) until that lands.
- If this gate fails outright, the first implementation session still completes its other observations, and the failure is its most important result.
