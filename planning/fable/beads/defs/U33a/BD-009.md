## Background

Chronicle is the subsystem of FrankenRobotics that stores what happened: runs, episodes, telemetry, digests,
verdicts and the evidence behind every claim. Its storage decision (ADR-CHRON-01, DESIGN): **metadata in a
ledger on FrankenSQLite, bulk data in content-addressed column files.** Reason: the ledger needs transactions
and queries; traces need sequential writes and deduplication. This is the pattern of FrankenSim's own
`fs-ledger` crate (FACT), and FrankenRobotics reaches FrankenSQLite through `fs-ledger` where it fits, behind
the airlock crate `frob-fsim` (feature group `ledger`).

FrankenSQLite is the owner's Rust rewrite of SQLite. It is foundation `FD-FSQL` in the foundation ledger:
posture Consume, confined to `frob-chronicle` (through `fs-ledger`), with `frob-conformance` allowed to use its
pager module as an oracle. FACT (read 2026-11-21): head `79b735cb265a`, toolchain `nightly-2026-08-31`, an
asupersync requirement of `0.6.2` from the registry with default features off, which FrankenSim patches to its
path checkout; FrankenSim's manifest carries profile overrides for the `fsqlite` packages and states that Cargo
does not propagate profiles to path consumers, which is why the workspace root repeats them.

The admission gate **INT-FSQL-01**: *the ledger opens, writes, and recovers after a forced kill mid-write.* It
is an M0 gate because everything from the first referee rollout onward writes its digest to the ledger, and
because the crash-consistent job protocol of later milestones (chunk publishing as one transaction, leases, a
contiguous committed frontier) is only as sound as the transaction underneath it. The seed done-condition is
that the forced-kill test passes 100 times.

Fallback named in advance, if admission fails: an append-only JSON-lines ledger with the same schema (one
record per line, a per-line checksum, a truncated final line discarded on open). No milestone waits on
FrankenSQLite; M1 depends on it, so a failure here is decided at M0, not discovered at M1.

## Scope

In: the trait `Ledger` (v0) and its in-process adapter over `fs-ledger` and FrankenSQLite; the minimal M0
tables; the forced-kill harness; the admission record; the JSON-lines fallback's interface (declared, built
only if the gate fails).
Out: Chronicle's schema and `.frun` episodes (BD-090); the chunk protocol (BD-091); deterministic simulation
testing of the publish path under asupersync's lab runtime (BD-096); the `Session` and `Recompute` traits of
the same feature group (N33a-17); the memo store's eviction policy (BD-220).

## Technical approach

**Trait (DESIGN: intent, not signatures; module `frob_fsim::ledger`, feature `ledger`).**

```rust
pub trait Ledger {
    fn open(path: &Path, schema: SchemaVersion, opts: OpenOptions) -> Result<Self, LedgerRefusal> where Self: Sized;
    fn begin(&mut self) -> Result<Txn<'_>, LedgerRefusal>;                 // one writer at a time
    fn integrity_check(&self) -> Result<IntegrityReport, LedgerRefusal>;  // structural check after open
    fn recovered(&self) -> RecoveryReport;        // what open found: clean | rolled-back-incomplete-txn | replayed-log
}
impl Txn<'_> {
    fn put(&mut self, table: TableId, key: &[u8], row: &[u8]) -> Result<(), LedgerRefusal>;
    fn get(&self, table: TableId, key: &[u8]) -> Result<Option<Vec<u8>>, LedgerRefusal>;
    fn commit(self) -> Result<CommitSeq, LedgerRefusal>;   // durable before it returns
    // dropping a Txn without commit rolls it back
}
```

No FrankenSQLite or `fs-ledger` type is public. Rows are canonical bytes produced by the caller; the adapter
does not interpret them. `CommitSeq` is a monotone 64-bit counter assigned inside the committing transaction (a
string in every JSON view, because it can exceed 2⁵³).

**M0 tables.** `meta` (schema version, creation receipt hash), `run` and `episode` in the minimal form the
first referee rollout needs (run identity, model identity, tier, final state digest, the stack receipt hash).
Schema changes after M0 go through versioned migrations owned by Chronicle.

**Rules.** (1) A commit that returns has been made durable by the mechanism FrankenSQLite provides at the pin
(its write-ahead or journal mode and sync level are read from its configuration and recorded in the admission
record, not assumed). (2) Open after an unclean stop either rolls back the incomplete transaction or replays a
complete one; it never exposes part of a transaction. (3) A ledger whose schema version is newer than the
binary's is refused, never opened read-write. (4) Every FrankenSQLite error is converted to a typed
`LedgerRefusal` with the upstream reason; a corruption report is an integrity refusal and is never retried.

**The forced-kill harness (`crates/frob-fsim/tests/ledger_forced_kill.rs` and the helper binary
`ledger_kill_probe`).** One trial, for seed s:
1. The parent creates an empty scratch directory and starts the child with (path, seed s, N = 200
   transactions, k = 8 rows per transaction).
2. The child opens the ledger and runs transactions i = 1..N. Transaction i writes rows whose content is a pure
   function of (s, i, row index), plus a chain value c_i = BLAKE3(c_{i−1} ‖ rows of i), with c_0 = zero. Before
   `begin` it writes the line `B i` to a pipe; after `commit` returns it writes `C i`.
3. The parent draws from seed s a kill point: a transaction index j uniform in 1..N and a phase in {before
   begin, inside the transaction after a random number of `put` calls, after commit before the acknowledgement
   is read}. It sends SIGKILL when the pipe shows that point (for the inside phase the child pauses on a second
   pipe after the chosen `put`, so the kill lands inside the write deterministically).
4. The parent reopens the ledger in-process. Assertions:
   a. `open` succeeds and `integrity_check` is clean;
   b. **prefix**: the transactions present are exactly 1..m with m ∈ {a, a + 1}, where a is the last index the
      parent saw acknowledged (`C a`); no transaction is present in part (each present transaction has all k
      rows and its chain value verifies);
   c. `recovered()` is consistent with what was found.
5. The parent then starts a second child that resumes at m + 1 and runs to N uninterrupted. The final chain
   value must equal the chain value of an uninterrupted reference run with the same seed.
6. In 10 of the 100 trials (seeds 90 to 99) a second kill is sent during the reopening of step 4 (kill during
   recovery), followed by another reopen with the same assertions.

The gate passes when trials for seeds 0 to 99 all pass, on the Mac and on the Linux host. The test runs under a
timeout and inside the machine envelope (well under a minute per trial; TARGET).

**Admission record.** Gate INT-FSQL-01, `covers.crates` naming the FrankenSQLite packages and `fs-ledger` as
they appear in the tracked lockfile, the command, output, receipt hash, the recorded journal and sync
configuration, 100 of 100, and the negative control's result.

Determinism: the content written is a pure function of the seed; kill timing is controlled by the pipes, so a
failing seed reproduces. Evidence class of the result: `Tested`.

## Acceptance criteria

- [ ] The forced-kill test passes for seeds 0 to 99 (100 of 100), including the 10 kill-during-recovery trials, on both hosts (seed done-condition).
- [ ] After every trial the ledger holds exactly a prefix of transactions, m ∈ {a, a + 1}, and the resumed run's final chain value equals the uninterrupted reference.
- [ ] The negative control is caught: the planted non-transactional writer leaves a partial transaction in at least one of 100 trials and the prefix assertion fails on it.
- [ ] `cargo tree -d` on the core workspace shows one asupersync package with FrankenSQLite in the graph (observation here; the gate is INT-ASUP-01).
- [ ] A ledger with a newer schema version is refused; a deliberately corrupted file (one flipped byte in a data page of a closed ledger) is reported by `integrity_check` or refused at open, never read as valid.
- [ ] An admission record for INT-FSQL-01 exists with the measured count, the configuration read at the pin, and the receipt hash.
- [ ] The `ledger` section of `frob-fsim`'s `CONTRACT.md` states durability, recovery behaviour, the single-writer rule and the fallback.

## Test plan

### Unit tests (`cargo test -p frob-fsim ledger`)
- `open_write_read`: one transaction of 8 rows, reopen, all 8 read back byte-identical.
- `rollback_on_drop`: a transaction dropped without commit leaves no row.
- `commit_seq_monotone`: 1,000 commits give 1..1000 with no gap.
- `newer_schema_refused`.
- `corruption_detected`: flip one byte in the middle of the file; `open` or `integrity_check` reports it.
- `second_writer_refused`: a second handle opened on the same path calls `begin` while the first handle's transaction is open (on one handle a second `begin` cannot compile, because `Txn` borrows the handle mutably); it returns a typed `busy` refusal within a bounded wait (the `OpenOptions` busy timeout, 1 s in the test), not a deadlock and not a hang, and after the first commits the second `begin` succeeds.
- `forced_kill_100` (the harness; `#[ignore]` by default and run by the gate command): seeds 0..99.
- `forced_kill_reproduces`: seed 17 run twice yields the same kill point, the same m, the same final chain value.
- `uninterrupted_reference_digest`: N = 200, k = 8, seed 0 → a chain value checked in as a golden value captured from the first run and re-derived by an independent script that recomputes the chain from the row function.

### End-to-end script and logging
`scripts/e2e/admission_m0.sh` (bead N33a-28), step `int_fsql_01`: runs the harness through the offload shim and
logs one line per trial with the seed, the kill index and phase, the last acknowledged index a, the recovered
m, the recovery report, the integrity result and the final chain digest; a `metric` line with passed and failed
counts against the threshold 100 of 100; then the control run with its first detected partial transaction.

### Known answers and negative controls
- Known answer: the prefix property and digest equality with an uninterrupted run, for every seed.
- Negative controls (registered for INT-FSQL-01): (1) a writer that splits one logical transaction into two auto-committed halves; (2) a harness build that skips the chain verification, which must then be failed by a planted row swap. A gate run in which control 1 is not caught is a FAIL.
- Metamorphic relation: the final chain value does not depend on where the kill happened.
- Determinism lanes: the reference digest is identical on both platforms and in debug and release.

## Considerations

- SIGKILL tests process death, not power loss: data the operating system has accepted survives a killed process. Power-loss durability depends on the sync level FrankenSQLite uses and on the platform (macOS needs a full-sync request to reach the medium); the admission record states the level in force and makes no power-loss claim at M0.
- The JSON-lines fallback keeps the same trait. Its recovery rule is "discard a final line whose checksum fails"; it has no queries, so Chronicle's query verbs would scan. It is a fallback, and no default wiring rests on it.
- Later uses of FrankenSQLite (the qualification ledger at M3) use the same crate and need no new admission; the pager policy used as a pattern and oracle for memo eviction is a different use with its own gate, INT-FSQL-02.
- Single-writer is deliberate at M0. FrankenSQLite's concurrent-writer mode is not relied on; the job engine serializes publishing.
- The ledger file may hold private-scene identities later; test ledgers hold synthetic rows only, and logs never include row payloads.
