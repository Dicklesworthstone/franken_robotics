## Background

Spark is the subsystem of FrankenRobotics between a derived kernel and a device result. Its CUDA backend lives
in an **annex workspace**, `spark/frob-spark-cuda`, outside the core workspace. The reason for the boundary is
never the compiler (the annex builds on T, the one toolchain of the build graph, and has no toolchain file of
its own); it is the unsafe and foreign-interface policy. The core denies unsafe code and has only Franken
runtime dependencies; a third-party driver binding with runtime compilation needs registered unsafe capsules
and its own lockfile, so that neither enters the core's resolution. The core never depends on an annex:
backends implement the core trait `KernelBackend` (bead BD-014).

The binding is `cudarc`, a third-party crate, foundation row `FD-CUDA`: posture Consume, annex only, confined
to this crate, admission gate INT-CUDA-01, fallback "none needed for CPU and Metal; the CUDA tier is absent".
FACT: the suite already uses it this way. FrankenSim's `render-gpu` pins `cudarc = "=0.19.9"` with the features
`driver`, `nvrtc` and `dynamic-loading`; the driver and NVRTC (NVIDIA's runtime compiler) load at run time, so
the build needs no CUDA toolkit; a `--precompile` recipe fills its binary cache on a host without a GPU. FACT:
the suite keeps its working GPU code outside FrankenSim's workspace because FrankenSim bans in-process foreign
kernels in production paths, which is why the GPU annexes stay in this repository.

`trj` is the project's Linux host with two RTX 4090 cards (24,564 MiB each, no NVLink; the driver reports a PCI
host bridge between them).

**INT-CUDA-01**: the pinned `cudarc` builds without a CUDA toolkit, loads the driver on `trj`, and runs a
kernel on both GPUs. The seed done-condition adds that the admission record states whether the pinned `cudarc`
binds graph capture and stream-ordered pools, because the M2 backend design depends on both (the step plan of
a bucket is captured once as a launch graph; transient device memory comes from a stream-ordered pool so that
a cancelled stream's allocations are released in order). A third-party gap is not an upstream work item: it is
confirmed or refuted here, and the annex binds the driver directly where a binding is missing.

## Scope

In: the annex workspace and its manifest; driver and NVRTC loading; device enumeration; compile of one
dialect unit; a v0 binary cache; buffers, launch and readback for one kernel through `KernelBackend`; a
receipt; the binding survey; typed refusals; the admission record.
Out: the full backend (launch-graph capture, the control block, stream-ordered pools, device faults and
cancellation: BD-172, BD-175); the arena, leases and the full cache with eviction (BD-173); the three-backend
bit comparison (BD-020); the IEEE probe and fingerprint (BD-017, BD-029); sharding across both cards (BD-199).

## Technical approach

**Workspace.** `spark/frob-spark-cuda/Cargo.toml` with its own `[workspace]` table and lockfile; dependencies:
`cudarc` at an exact pin with `driver`, `nvrtc`, `dynamic-loading` and default features off (the version is
chosen at this gate, starting from the suite's `=0.19.9`, and recorded); path dependencies on the core crates
`frob-core` and `frob-kernels`. No asupersync edge is added beyond what the core crates bring, and `cargo tree
-d` must show one asupersync package.

**Unsafe capsules.** Every `unsafe` block sits in a capsule: a module under 300 lines behind a safe API, with a
`SAFETY.md`, registered in `registries/capsules.toml`. v0 capsules: `driver_ctx` (initialization, device and
context handles), `module_launch` (module load, function lookup, launch), `buffers` (device allocation and
host copies). Unsafe is never used to work around a lifetime, aliasing, cancellation or synchronization
problem.

**Steps of v0 (each observable).**
1. *Load.* Open the driver and NVRTC libraries dynamically. A missing library is `FROB-REF-601` (device
   unavailable or lost; exit code 6; repair: rerun on another device or on `batch-cpu`), never a panic.
2. *Enumerate.* Report each device's name, compute capability, memory and driver version; on `trj` this must
   list two devices of architecture `sm_89`.
3. *Context.* One context and one host thread per device.
4. *Compile.* The compiled unit is the concatenation: shape-class `#define` lines, the CUDA prelude, the
   generated arithmetic body, the hand-written skeleton. Options: `-arch=sm_89`, `--fmad=false`, never
   `--use_fast_math`. The dialect lint runs first; a banned construct is `FROB-REF-251` before any compiler
   sees the text. A compiler failure is `FROB-REF-603` with the diagnostics verbatim.
5. *Cache (v0).* Key: BLAKE3 over the expanded dialect text, the compile options, the prelude version, the
   compiler identity (NVRTC version), the device architecture and the driver version. Value: the CUBIN. Written
   aside and renamed; a hit is checked against its digest before use and a corrupt entry is a miss; an offline
   host that cannot recompile refuses with `FROB-REF-612`. Rust's default hasher is not used (it is not stable
   across toolchains). Directory under `${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/frob-kernel-cache` unless
   configured.
6. *Buffers.* Allocate once; copy host data in.
7. *Launch.* Load the module, look up the kernel, launch over the grid derived from the shape class, synchronize.
8. *Read back* after completion; return a `Receipt` with the twelve doctrine fields (device identity, driver
   and runtime, compiler and backend, kernel source hash, kernel and workload identity, CPU axes, reduction and
   determinism policy, CPU-versus-device comparison, the retained CPU reference, cancellation outcome, phase
   attribution, go or no-go) and device and wall seconds per phase.

**The test kernel.** The single-body Cayley step `K-cay-step` on 10⁶ unit quaternions (inputs: orientation
quaternion, position, body angular and linear velocity, step h; arithmetic uses only +, −, ×, ÷), from the one
dialect source, compared with the Rust reference loop on `batch-cpu`. v0 reports the comparison (count of
differing outputs, largest difference in units in the last place); whether it must be zero is the question of
the three-backend gate, not of this admission.

**The binding survey (recorded in the admission record).** For the pinned `cudarc`, list whether safe or raw
bindings exist for: graph creation and stream capture (begin capture, end capture, graph instantiate, graph
launch); memory pools (pool create, allocate from pool asynchronously, free asynchronously, pool trim);
streams and events; module load from a binary image. Each entry: `safe`, `raw-only` or `absent`, with the item
path. Decision rule for OPEN-SPARK-4 (default if undecided: preallocated transient buffers and per-launch
submission, with the throughput cost disclosed): where an entry is `absent`, the capsule may declare the
missing driver symbols itself under its `SAFETY.md`; if the owner refuses that, transient buffers are
preallocated in the arena and the hot path is unchanged.

**Precompile on a GPU-less host (feasibility only).** The verb `frob spark precompile sm_89` arrives at M2
(N21b-13, over the cache of N21b-12 and BD-173). What is proved here is the premise it rests on: NVRTC compiles
the unit to a CUBIN in a process that sees no CUDA device. The step runs on `trj` with `CUDA_VISIBLE_DEVICES`
set to the empty string (always available), and on a Linux build host with NVRTC and no GPU when one is
available (otherwise that half is recorded `not run`). It records the CUBIN's BLAKE3 and the compile seconds,
and compares the CUBIN byte for byte with the one compiled with device 0 visible from the same text and
options; the outcome is recorded, and a difference is a finding for N21b-12's precompile design, not a failure
of INT-CUDA-01. This Mac cannot be that host: NVRTC is published for Linux and Windows and not for macOS (FACT
to recheck here and recorded in the admission record); on the Mac a CUDA compile request is `FROB-REF-601`
(the compiler library is missing). The v0 cache writes **no entry** from a compile in a process without a
device of the architecture: its key contains the driver version of the device that will load the entry, which
such a process does not have (a build host without the driver has no driver library to ask), and an empty or
local stand-in would produce keys the target never computes. N21b-12 settles the cross-host fill with a
`TargetIdentity { architecture, compiler, driver }` read from the target host's `frob.fingerprint/1` record
(BD-029, which comes after this bead), refused with `FROB-REF-606` when the record's architecture differs from
the request, its compiler identity differs from the loaded NVRTC's, or no record is given.

Determinism and evidence: a v0 result is evidence class `Tested` for "the kernel ran on this device"; it is
marked `citable: false` until the hardware fingerprint exists.

## Acceptance criteria

- [ ] `cargo check` of the annex passes through the offload shim on a host with no CUDA toolkit installed (the build needs none).
- [ ] On `trj` the driver loads, two devices are enumerated, and the test kernel runs on device 0 and on device 1, each returning a receipt (seed done-condition).
- [ ] The admission record states, per item of the binding survey, whether the pinned `cudarc` binds graph capture and stream-ordered pools (seed done-condition), and records the pinned version.
- [ ] A second run of the same kernel is a cache hit (no NVRTC call, measured compile time near zero); a corrupted cache entry is detected and recompiled; with the compiler library hidden and no valid entry the refusal is `FROB-REF-612`.
- [ ] With the driver library hidden the refusal is `FROB-REF-601`; a source with a syntax error yields `FROB-REF-603` carrying the compiler's text; a source with `sinf` yields `FROB-REF-251` before compilation.
- [ ] `xtask check-unsafe` passes: every capsule is registered, under 300 lines, with its `SAFETY.md`; `cargo tree -d` in the annex shows one asupersync package or none.
- [ ] Each receipt validates (all twelve doctrine fields present) and the comparison with the Rust loop is recorded with its counts.
- [ ] The cold compile time of the unit and the cache-hit time are recorded (FACT for context: the suite's renderer reports about 5 s on an idle host and up to 15 minutes on a heavily loaded one).
- [ ] The precompile feasibility step has run on `trj` with `CUDA_VISIBLE_DEVICES` empty: NVRTC produced a CUBIN, its digest and the byte comparison with the device-visible CUBIN are recorded, and the cache directory gained no entry; the record states whether NVRTC is published for macOS at the pinned version.

## Test plan

### Unit tests (`cargo test` in the annex; device tests are `#[ignore]` and run on `trj` by the gate command)
- `cache_key_changes_with_each_input`: changing the text, an option, the prelude version, the compiler identity, the architecture or the driver version each changes the key (six sub-cases).
- `cache_roundtrip_and_digest_check`: store, load, flip one byte, load → miss.
- `cache_write_is_atomic`: a reader concurrent with a writer never observes a partial file (the aside-and-rename path is exercised 10³ times).
- `options_forbid_fast_math`: an option set containing `--use_fast_math` or lacking `--fmad=false` is rejected before NVRTC.
- `enumerate_two_devices` (device): two entries, architecture `sm_89`.
- `kernel_runs_on_each_device` (device): 10⁶ quaternions on device 0 and device 1; receipts valid; outputs of the two devices compared with each other and with the Rust loop, counts recorded.
- `driver_missing_refuses_601`, `compile_error_refuses_603`, `offline_corrupt_refuses_612` (with library paths redirected to an empty directory).
- `receipt_has_twelve_fields`.
- `nvrtc_compiles_without_visible_device` (device host, run with `CUDA_VISIBLE_DEVICES=""`): the unit compiles to a CUBIN for `sm_89`; the device count seen is 0; the cache directory's listing is unchanged afterwards (no entry without a driver identity).

### End-to-end script and logging
`scripts/e2e/admission_m0.sh` (bead N33a-28), step `int_cuda_01` (run on `trj`): builds the annex, runs the
device tests, runs the binding survey, writes the admission record. NDJSON lines carry the command, exit code,
wall time, per device the name, memory, driver and compiler versions, compile seconds cold and warm, device
seconds, the count of outputs differing from the Rust loop with the largest difference in units in the last
place, the survey table, and the precompile feasibility outcome (both CUBIN digests, their byte equality, cache
entries written: 0).

### Known answers and negative controls
- Known answer: the kernel's outputs on one synthetic input with exactly representable values (orientation identity, rotation increment (0, 0, 1.5) rad, no translation: unnormalized result (1, 0, 0, 0.75) and denominator 1.5625) are exact on each device.
- Negative controls (registered for INT-CUDA-01): the hidden driver must yield the typed refusal; a kernel source with one planted wrong constant must make the comparison with the Rust loop report differences (a comparison that cannot differ validates nothing).
- Determinism lanes: the same device twice gives bit-identical outputs (recorded); device 0 against device 1 is recorded; debug and release host builds give the same device outputs.

## Considerations

- Budget: the run stays inside the machine envelope (one device at a time, under a timeout); training-scale use of both cards needs the owner's envelope decision and is not part of this gate.
- OPEN-SPARK-6 (whether the two cards allow device-to-device access; default host-staged transfers) is not decided here; v0 uses one device at a time.
- RISK: a driver, system or binding update changes kernel results; this is why the driver and compiler versions enter the cache key and the receipt.
- If INT-CUDA-01 fails, the CUDA tier is absent and nothing else is blocked: M1 needs no GPU, and the Metal and CPU tiers remain.
- Kill gates that later read this backend (KILL-D1 on bit equality across backends, decided at M2) are not decided here.
