## Background

In FrankenRobotics the arithmetic body of a kernel is **derived, not hand-written** (construction C-14: kernels
are derived, typed by dimension, and carry certificates). A derivation program builds the kernel's expressions
symbolically, lowers them to the kernel intermediate representation `frob-kir` (typed single-assignment
programs in which every floating value carries a physical dimension; bead BD-018), and the representation's
emitters write Rust for the CPU reference and shared-dialect text for CUDA and Metal. The same symbolic objects
yield polynomial identities that a checker can decide, which is where a kernel's certificate comes from.

The symbolic engine is **FrankenSymPy**, the owner's Rust computer-algebra project, foundation row `FD-FSYM`:
posture build-time (plus subprocess and second checker for later uses), confined to the annex
`derive/frob-derive` and, for re-checking only, `frob-conformance`. It never enters a `frob` binary's runtime
graph. FACT (read 2026-11-21): head `29f847c14428`; its own toolchain pin is `nightly-2026-08-20`, different
from the rest of the suite; its workspace manifest refers to two sibling pin directories,
`../franken_numpy-pin` and `../frankenscipy-pin`, that do not exist on this machine
(`frankensympy/Cargo.toml:95–96`). DESIGN consequence: `derive/` depends on **individual `fsym-*` crates by
path** (not on the workspace), builds on T (the one toolchain of the build graph), has no toolchain file of its
own, and FrankenSymPy is moved to T by the toolchain train. FACT about what it can do: exact polynomial
identity checking with an offline verifier (`fsym-proof-kernel`, `fsym-capsule-consumer`); exact rational
linear algebra with certificates; common-subexpression elimination (`fsym-simplify`); it has no Lie-algebra
module, no quaternions and no noncommutative symbols in Rust, and its multi-output straight-line code
generation has a cap of 8,192 operations. Hence: explicit matrices and components are written out in the
derivation program, and `frob-kir` owns code generation.

**INT-FSYM-01**: `derive/` builds on T against the `fsym-*` crates by path, derives `K-cay-step`, and its
certificate replays in the offline auditor. The seed done-condition for this bead: regeneration reproduces the
checked-in sources bit for bit.

The two kernels are the group update of the integrator (construction C-05: time stepping stays on the group).
The Cayley map cay(x) = (I − x/2)⁻¹(I + x/2) is rational and lands exactly on the rotation group, so the update
uses only +, −, ×, ÷ and, for the normalization, one square root: operations IEEE 754 requires to be correctly
rounded. That makes it a candidate for bit-identical execution on CPU, CUDA and Metal (a HYPOTHESIS another
gate measures) and an object a polynomial identity checker can certify.

Tier: Frontier (derived arithmetic through the kernel representation is a Frontier mechanism with the kill gate
KILL-KIR at M2); at M0 this bead is the derivation spike, and the three-backend run of its output (bead BD-020)
is the paper-scale evidence that the route works.

## Technical approach

**Workspace.** `derive/frob-derive/Cargo.toml` with its own `[workspace]` table and lockfile; path
dependencies on the needed `fsym-*` crates at the pin of `franken-stack.lock` (the set is recorded: at least
the polynomial, simplification and proof-kernel crates), on `frob-kir` and on `frob-core`. Exactly one
asupersync package (FrankenSymPy consumes asupersync by path).

**`K-cay-step` (the program to derive; DESIGN, matching the first emitted kernel of the representation bead).**
State: a unit quaternion q = (q_w, q_x, q_y, q_z), dimensionless, and position p in metres. Inputs: body
angular velocity ω in s⁻¹, body linear velocity v in m·s⁻¹, step h in s. With a = h·ω (dimensionless) and
w = h·v (metres):
1. c = (1, a_x/2, a_y/2, a_z/2); q′ = q ⊗ c (Hamilton product; the increment is in the body frame, so it
   multiplies on the right): q′_w = q_w − (q_x·a_x + q_y·a_y + q_z·a_z)/2, and the vector part is
   q_v + q_w·a/2 + (q_v × a)/2.
2. d = 1 + (a·a)/4. The rotation of q′/√d is q composed with cay(â), where â is the skew matrix of a.
3. u = (w + ½·a × w + ¼·a·(a·w))/d, which is (I − â/2)⁻¹·w.
4. p′ = p + R(q)·u, with R(q) the rotation matrix of q written out in products of its components.
Outputs: q′ (unnormalized), d and p′.

**`K-normalize`.** n = ((q_w·q_w + q_x·q_x) + q_y·q_y) + q_z·q_z in that association; s = √n; outputs
(q_w/s, q_x/s, q_y/s, q_z/s) by four divisions. Division, not multiplication by a reciprocal, because one
correctly rounded division has one rounding where reciprocal-then-multiply has two. The summation order is
fixed at derivation time; reassociation is not an allowed rewrite afterwards.

**Derivation steps (per kernel).**
1. Declare symbols with their dimensions.
2. Build the output expressions with FrankenSymPy; choose the evaluation form (one operation per node, the
   association stated above, a Horner form where a polynomial in one variable appears).
3. Lower to a `frob-kir` program through the builder, which applies bounded common-subexpression elimination
   and the dimension checker (a sum of unlike dimensions is a build-time refusal).
4. Emit Rust and dialect text; write them with a header carrying the program's content hash (BLAKE3 over the
   canonical program bytes).
5. Build the identity statements (below) from the same symbolic objects and have FrankenSymPy's proof kernel
   check each (the `identity_*` tests). No certificate file is written here: BD-021's `certify` stage extracts
   the same statements from the lowered program, binds each to its card and writes `K-<name>.cert` beside the
   kernel with the kernel's content hash inside.
6. Record the digests of every emitted file in the kernel registry.

**Identities (polynomial, over the rationals; the certificates of BD-021 carry the same statements).**
- Norm (theorem card T-03): (q′_w² + q′_x² + q′_y² + q′_z²) − (q_w² + q_x² + q_y² + q_z²)·(1 + (a_x² + a_y² +
  a_z²)/4) = 0, an identity in seven variables. With ‖q‖ = 1 it gives ‖q′‖² = d.
- Cayley orthogonality (theorem card T-01), cleared of denominators: for the matrix R(c) of the unnormalized
  increment c, R(c)ᵀ·R(c) = d²·I (nine identities in a) and det R(c) = d³.
- Translation: (I − â/2)·(w + ½·a × w + ¼·a·(a·w)) − d·w = 0 (three identities in a and w). Hand check:
  the cross terms ±½·a × w cancel, −¼·a × (a × w) = −¼·(a·(a·w) − w·(a·a)), and a × a = 0, leaving
  w + ¼·(a·a)·w = d·w.
- `K-normalize` (the normalization clause of T-03): with a witness t for the square root and the side relation
  t² = n, the outputs satisfy Σ outᵢ² = 1, cleared of the denominator: (Σ outᵢ²)·t² − t² = n − t², which is
  zero modulo t² − n with cofactor −1. (The form (Σ outᵢ²)·t² − n = 0 holds for any t and would check nothing.)
A certificate is over the rationals with square roots as witnesses; it does not model rounding, and no bundle
may present a floating-point output as proved to satisfy its identity.

**Bit-for-bit regeneration (the done-condition, and how it is made true).** The derivation is a pure function
of its source and of the pinned `fsym-*` and `frob-kir` versions: no iteration over hash maps in an order that
depends on addresses or a random seed (ordered maps only); symbol and node naming by construction order; no
timestamps, host names or paths in any emitted file; a single canonical serialization. `xtask check-generated`
runs the derivation and compares every emitted byte with the checked-in files; any difference fails the check
and prints the first differing byte offset.

Determinism class of the derivation: D0. Evidence: the identities accepted here are a test result, not
evidence; the certificate BD-021 writes from them is evidence class `Certified` once the independent auditor
replays it (BD-027); until then it is recorded as produced, not checked.

## Acceptance criteria

- [ ] `derive/frob-derive` builds on T through the offload shim against the `fsym-*` crates by path, with one asupersync package in its graph.
- [ ] Regeneration reproduces the checked-in Rust and dialect sources bit for bit (seed done-condition), twice on one machine and on both hosts; the certificate files join the same comparison when BD-021 writes them.
- [ ] The derived `K-cay-step` program has the content hash checked in by the representation bead; if the chosen algebraic form differs, the golden hash is regenerated once here with the reason recorded, and the fixture values still hold.
- [ ] The emitted dialect text passes the dialect lint with zero findings; the emitted Rust contains no fused multiply-add and no platform transcendental.
- [ ] FrankenSymPy's proof kernel accepts each identity above, and rejects each planted false twin (a sign flipped in one term).
- [ ] An admission record for INT-FSYM-01 exists with the pin, the `fsym-*` crate set, the command and output, the digests of the generated files, and the status of the auditor replay (`pass` only after bead BD-027's replay; otherwise the record says which half is done).
- [ ] A seeded dimension violation in a derivation (adding metres to a dimensionless value) is refused at build time.

## Test plan

### Unit tests (`cargo test` in the annex)
- `cay_step_exact_fixture`: q = (1, 0, 0, 0), a = (0, 0, 1.5), w = 0 → q′ = (1, 0, 0, 0.75), d = 1.5625 (all exactly representable).
- `normalize_exact_fixture`: (1, 0, 0, 0.75) → n = 1.5625, s = 1.25, output (0.8, 0, 0, 0.6) as the correctly rounded `f32` values.
- `cay_step_small_angle`: q = identity, ω = (0, 0, 0.2) s⁻¹, h = 1 s → normalized (0.9950372, 0, 0, 0.0995037) to `f32` rounding; the rotation angle is 2·atan(0.1) = 0.19934 rad, not 0.2 (the Cayley map is second-order).
- `cay_step_translation`: q = identity, a = 0, v = (1, 2, 3) m·s⁻¹, h = 0.002 s → p′ − p = (0.002, 0.004, 0.006) m as correctly rounded `f32`.
- `identity_norm_accepted`, `identity_cayley_orthogonal_accepted`, `identity_translation_accepted`, `identity_normalize_accepted`.
- `identity_false_twins_rejected`: the norm identity with (1 − (a·a)/4), the translation identity with +½·â, det R(c) = d², and the normalization statement with its side relation t² − n removed are each rejected.
- `regeneration_is_deterministic`: run the derivation twice in one process and in two processes; byte-identical outputs.
- `no_ambient_data_in_outputs`: emitted files contain no absolute path, date or host name.
- `dimension_violation_refused`.
- Property test `emitted_rust_matches_symbolic`: for 10³ random rational inputs, the emitted Rust body evaluated in exact rational arithmetic (by an interpreter over the program) equals the symbolic expressions exactly.

### End-to-end script and logging
`scripts/e2e/admission_m0.sh` (bead N33a-28), step `int_fsym_01`: builds the annex, runs `cargo run -p xtask --
check-generated`, runs the derivation tests, then (when beads BD-021 and BD-027 have landed) `frob prove verify`
on the certificates of the two kernels, and writes the admission record. NDJSON lines carry the command, exit code, wall time, the
program hashes, the digests of each emitted file before and after regeneration with the first differing byte
offset on failure, the identity count accepted and the false twins rejected.

### Known answers and negative controls
- Known answers: the four fixtures; the identities with their hand check.
- Negative controls (registered for INT-FSYM-01): the three false twins; a derivation run with a hash-map-ordered symbol table (planted) must fail `regeneration_is_deterministic`; a checked-in generated file edited by hand must fail `check-generated`.
- Metamorphic relation: renaming every symbol consistently leaves the program's structure and the emitted arithmetic unchanged apart from names.
- Determinism lanes: twice on one machine; debug and release; Linux and macOS.

## Considerations

- KILL-KIR (decided at M2): if the derivation toolchain cannot express or emit more than 20% of the kernel arithmetic, or emitted kernels miss the speed bound of bet BET-01 (more than 1.3 times slower than hand-tuned equivalents after one optimization pass), arithmetic is hand-written in Rust and the dialect and bound by differential tests, and certificates fall back per KILL-LEMMA (exact-rational randomized identity tests recorded as `Tested`). These two kernels are the first data for that decision.
- Upstream work items that would simplify this bead, none of which it waits on: FD-FSYM-01 (multi-output straight-line code generation and lifting the 8,192-operation cap; interim: `frob-kir` owns code generation), FD-FSYM-02 (a Lie-algebra module; interim: explicit matrices here), FD-FSYM-04 (certificate families for matrix identities; interim: entry-wise polynomial identities, as above).
- The Cayley step is refused beyond ‖ω‖·h = 0.2 per substep (`FROB-REF-212`); the exact fixture with a = 1.5 is an arithmetic fixture outside that admission bound on purpose.
- If FrankenSymPy does not build on T at M0, the remedy is the upstream change that moves FrankenSymPy's pin to T in its own repository (NF-04, a leg of the first toolchain train). Until it lands, the toolchain matrix records the failing cell, INT-FSYM-01 is recorded `fail` with that reason, and NF-04's interim posture applies: the derivation runs as a subprocess built in FrankenSymPy's own workspace on its own channel (the plan's subprocess posture of FD-FSYM), its outputs are checked in with their digests and `check-generated` compares them. Only if that subprocess cannot run either does the fallback of KILL-KIR stand for these two kernels (arithmetic hand-written and bound by differential tests). The annex gets no toolchain file and is never built on a second toolchain: every crate of the build graph, `derive/frob-derive` included, builds on T, and a subprocess is not part of that graph.
