## Background

FrankenRobotics is built on sibling projects that the same owner maintains: FrankenSim (physics, geometry, the
design ledger), asupersync (structured concurrency), FrankenSQLite, FrankenTorch, franken_numpy, FrankenSymPy,
franken_lean, fastmcp_rust and a dozen more. The suite-consumption chapter of the design fixes what is taken from
each, in which form, behind which boundary, and what happens when a sibling does not hold still. This bead creates
the vocabulary everything else in that chapter is written in.

**Five postures** (DESIGN; the vocabulary the sibling product FrankenMining established, FACT):

| Posture | Meaning | What it permits in a build graph |
|---|---|---|
| **Consume** | A Cargo dependency at an exact pin, default features off | The crate is in the production graph of the crates its row confines it to |
| **Subprocess** | A binary or command-line tool we invoke; no crate in our build graph | Nothing; the tool is found on disk at a pinned revision |
| **Lift** | Copied source with a provenance header, a row in `registries/lifts.toml` and a golden test; re-owned here | The copied files only; the sibling crate is absent |
| **Oracle** | Development and test only; never in a production graph | A dev-dependency of `frob-conformance` or an out-of-process capture |
| **Pattern** | We copy the design, not the code | Nothing |

Each foundation has an `FD-` row (for example `FD-FSIM` for FrankenSim) stating its posture, its pin, the crates
allowed to touch it, an admission gate and a fallback. The reason for the fallback column is a program rule: no
milestone may be blocked by a sibling that has not converged.

Three rules shape the data model and are the reason this bead is more than a list of words:

1. **A posture belongs to a use, not to a repository.** One sibling may be consumed for one purpose and be an
   oracle for another (FrankenSQLite is consumed for the ledger and is a pattern and an oracle for its pager
   policies). A row therefore carries a list of uses, each with its own posture and confinement.
2. **A consumed FrankenSim crate may sit behind a Cargo feature that is off by default**, so that its compile
   closure is paid only by the milestone that needs it. The posture value `consume-path` therefore takes a
   `features` list (the airlock feature groups compiled by default).
3. **Subprocess is the first fallback for FrankenSim itself**: before any source is lifted, the referee moves
   behind a process boundary. Lift is the last resort because the smallest useful lift sits on a closure of about
   1.5 million lines.

One rule from the chapter's opening is recorded here because it governs every record this project writes about a
sibling: every statement about sibling code in the design was read on 2026-11-21 at named commits and is a FACT
with its path; a sibling fact goes stale when the sibling moves, so **a fact that a gate depends on is re-read by
that gate's admission test and is never copied from the design into a record**. The probes that do the re-reading
are bead N33a-09.

Rejected alternative: free-text posture notes in a README. Rejected because the dependency check must be able to
refuse a build edge that the declared posture forbids, and a tool cannot read prose.

## Scope

In: the posture enumeration and its allowed combinations as types in `xtask` (shared with the stack-lock parser of
N33a-03); the lift machinery (provenance header format, `registries/lifts.toml` schema, the golden-test rule and
its validator); the posture-to-graph rules as a table the dependency check consumes.
Out: the eighteen foundation rows themselves (N33a-02); the lock file parser (N33a-03); the dependency check that
enforces confinement (BD-003); any actual lift (none is planned: lifting happens only under fallback (b) of the
FrankenSim kill gate KILL-FSIM).

## Technical approach

**Types (DESIGN, in `xtask/src/stack/posture.rs`; plain Rust, standard library only).**

```rust
pub enum Posture { Consume, ConsumePath, Subprocess, Lift, Oracle, Pattern, BuildTime }
pub struct Use { pub posture: Posture, pub purpose: String, pub confined_to: Vec<String>, pub tier: Tier }
pub enum Tier { Solid, Frontier, Moonshot }
```

`ConsumePath` is Consume through a path dependency on a sibling checkout (FrankenSim, asupersync) as opposed to a
registry pin; `BuildTime` is consumption by an annex workspace that never enters a `frob` binary's runtime graph
(FrankenSymPy in `derive/`). The text forms in TOML are `consume`, `consume-path`, `subprocess`, `lift`, `oracle`,
`pattern`, `build-time`. An unknown posture string is a parse error, not a default.

**Posture-to-graph rules (the table `check-deps` consumes).** For a foundation crate c and a workspace crate w:

1. `consume` / `consume-path`: an edge w → c is allowed only if w is in the use's `confined_to`, and only with
   the dependency specification the posture names: for `consume`, an exact version requirement (`=x.y.z`, equal
   to the row's `version`) from the registry; for `consume-path`, a path dependency on the row's `path` (no
   version range, no git source); in both, `default-features = false`, with any features listed explicitly. An
   edge from an allowed crate with a caret requirement, or with default features on, is refused.
2. `oracle`: an edge is allowed only as a dev-dependency and only from the crates listed (normally
   `frob-conformance`); a normal dependency is a failure.
3. `build-time`: an edge is allowed only inside the named annex workspace.
4. `subprocess`, `pattern`: any Cargo edge to the sibling's crates, in any workspace, is a failure.
5. `lift`: no Cargo edge to the sibling; instead every lifted file must appear in `registries/lifts.toml`.

**The lift registry (DESIGN, schema `frob.lifts/1`).** `registries/lifts.toml` ships empty and schema-valid. One
record per lifted file:

```toml
[[lift]]
file        = "crates/frob-fsim/src/lifted/ga_motor.rs"   # path in this repository
foundation  = "FD-FSIM"
source_repo = "frankensim"
source_path = "crates/fs-ga/src/motor.rs"                 # repository-relative, never a machine path
source_rev  = "<40 hex>"
source_hash = "<BLAKE3 of the source file bytes at source_rev>"
lifted_hash = "<BLAKE3 of the file as lifted, before any local edit>"
golden_test = "crates/frob-fsim/tests/lift_ga_motor.rs"   # must exist and must name the lifted file
reason      = "KILL-FSIM fallback (b)"
date        = "<ISO date>"
```

**Provenance header.** Every lifted file begins with a comment block of fixed form, checked byte for byte against
its registry record: `// LIFTED from <source_repo>/<source_path> at <source_rev>`, `// source BLAKE3 <hash>`,
`// registry: registries/lifts.toml`, `// re-owned here: edits are ours and are tested by <golden_test>`.

**Validator (a library function `stack::lifts::validate`, called by `check-stack`; no seventh `xtask` subcommand
is added, because the workspace caps `xtask` at exactly six checks).** Steps:
1. Parse `registries/lifts.toml`; refuse unknown fields.
2. For each record: the file exists; its header matches the record; `golden_test` exists and contains the lifted
   file's module path.
3. Scan the workspace for files whose first line starts `// LIFTED from`; each must have a record (an
   unregistered lift is a failure).
4. For each foundation whose row has posture `lift`: no manifest in any workspace names a crate of that sibling.
5. Report findings as `{rule, file, message}`; any finding fails the check.

**What a golden test is.** A test that pins the behaviour of the lifted file against values captured from the
sibling at `source_rev` (never regenerated from the lifted copy), so that a later local edit that changes
behaviour is seen.

Determinism: the validator is a pure function of the tree (class D0). It writes nothing.

## Acceptance criteria

- [ ] The seven posture strings parse; an eighth string is a parse error naming the row.
- [ ] `registries/lifts.toml` (created empty by the first commit, BD-002) is empty and validates; this bead replaces BD-002's placeholder schema `schemas/registries/lifts.schema.json` with the schema of `frob.lifts/1` above (hand-written, as every registry-file schema is), and a test asserts that the schema's keys equal the keys the loader accepts.
- [ ] The validator fails on each planted defect: a file with a `// LIFTED from` header and no record; a record whose file is missing; a header whose revision differs from the record; a record with no golden test; a `lift` foundation that still has a Cargo edge.
- [ ] The posture-to-graph table is exported as data that BD-003's `check-deps` reads (one function `stack::posture::edge_allowed(use, from, kind, spec) -> bool`, where `kind` is normal, build or dev and `spec` is the dependency's specification as written in the manifest: version requirement or path, and `default-features`), with a unit test per rule.
- [ ] A use list with two postures for one sibling round-trips (FrankenSQLite: `consume` for the ledger, `pattern` and `oracle` for the pager policy).
- [ ] `xtask` still has exactly six subcommands.

## Test plan

### Unit tests (`cargo test -p xtask stack::posture stack::lifts`)
- `posture_strings_roundtrip`: each of the seven strings parses and prints back identically.
- `posture_unknown_is_error`: `posture = "vendored"` fails with the row identifier in the message.
- `edge_rules`: (consume, w in confinement, normal) → allowed; (consume, w outside) → refused; (oracle, `frob-conformance`, dev) → allowed; (oracle, `frob-conformance`, normal) → refused; (pattern, any, any) → refused; (subprocess, any, any) → refused; (build-time, crate inside `derive/`) → allowed, (build-time, core crate) → refused.
- `edge_spec_rules`: (consume, w in confinement, `=0.6.2`, default features off) → allowed; the same with `^0.6` → refused; with `0.6.2` (a caret requirement by Cargo's reading) → refused; with default features on → refused; (consume-path, the row's `path`, default features off) → allowed; the same with a git source or a different path → refused.
- `lifts_empty_registry_valid`: the shipped file validates with zero findings.
- `lifts_schema_matches_loader`: the property names of `schemas/registries/lifts.schema.json` equal the record keys the loader accepts; a record with an extra key `notes` is refused by both.
- `lifts_unregistered_file_caught` (synthetic fixture tree): a file with the header and no record → one finding, rule 3.
- `lifts_header_mismatch_caught`: record revision `aaaa…`, header revision `bbbb…` → one finding, rule 2.
- `lifts_golden_test_required`: record without `golden_test` → parse error.
- `lifts_paths_are_repo_relative`: a `source_path` beginning with `/` or containing a home directory is refused.

### End-to-end script and logging
Covered by `scripts/e2e/stack_receipt.sh` (bead N33a-27), step `lifts_registry`: it runs `cargo run -p xtask --
check-stack` on the clean tree (expects exit 0 and zero lift findings), then on a scratch copy with one planted
unregistered lifted file (expects a non-zero exit and one finding naming the file). Logged: the command line, exit
code, wall time, the finding list, and an `assert` line per expectation.

### Known answers and negative controls
- Negative controls: the five planted defects of the acceptance list; each is registered as a control of the workspace-check gate that `check-stack` belongs to.
- Metamorphic relation: reordering records in `lifts.toml` changes no finding.
- Determinism lanes: the validator's report is byte-identical twice on one machine and on Linux and macOS.

## Considerations

- No lift is expected. The registry and validator exist at M0 so that, if KILL-FSIM's fallback (b) ever fires, the first lifted file lands under a rule that already works; the design requires the README to state "lift-only" in that case and the upstream work items to stay open.
- A lift diverges from its sibling from the day it is made. The golden test pins behaviour at `source_rev`; it does not track the sibling. That is the cost the fallback order (worker process first, lift second) exists to avoid.
- Licence: every sibling is the owner's project, so a lift raises no third-party licence question; the header still records the origin for audit.
- If a future posture is needed (for example a pinned container image), it is added by an ADR and a new enum arm, never by a free-text field.
