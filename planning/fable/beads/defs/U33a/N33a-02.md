## Background

The **foundation ledger** is the list of every sibling project FrankenRobotics touches, with what it is used for
and where it is allowed to appear. It lives as rows of `franken-stack.lock` (a TOML file in the format the sibling
product FrankenMining uses, FACT: `franken_mining/franken-stack.lock`), one `[[foundation]]` row per sibling. The
workspace rule L-4 says each foundation is confined to the crates named in its row, and `xtask check-deps`
enforces that from this data. A foundation that is not in the ledger may not appear in any manifest.

This bead writes the eighteen rows as data. The parser and schema are bead N33a-03; the vocabulary of postures is
bead N33a-01 (Consume: a Cargo dependency at an exact pin; Subprocess: a tool we invoke; Lift: copied source;
Oracle: development and test only; Pattern: we copy the design, not the code). Terms: the **airlock** is the crate
`frob-fsim`, the only crate that may name types from FrankenSim's volatile crates; **bedrock-direct** is a short
list of small FrankenSim crates any crate may use (bead N33a-12); **T** is the one Rust toolchain of the whole
build graph; an **admission gate** (`INT-…`) is the test that must have a record before a foundation is used
above the airlock; a **kill gate** (`KILL-…`) names a trigger and a fallback in advance.

Why every row has a fallback: no milestone may wait on a sibling. The ledger is where that promise is written
per sibling, so a reviewer can check it without reading code.

## Scope

In: the eighteen rows below, with every use, confinement list, admission gate and fallback; the four "honest
notes" recorded as `note` fields; the test that the rows and the dependency firewall agree.
Out: the pins themselves (commit hashes are recorded at admission, by the admission beads); the receipt (N33a-04);
the admission records (N33a-07); upstream work items in sibling repositories (BD-008, BD-023, BD-037).

**Honest notes, recorded as the `note` field of four rows (FACT, each to be re-read by its admission test).**

- *franken_numpy* is an `f64` array library on heap vectors with no single-precision storage and no fixed-size
  matrix types, and it lists GPU arrays and automatic differentiation as out of scope. It is the right tool at
  the interchange boundary and as an oracle, and it is not put in a hot path. Its stride convention differs from
  FrankenTorch's (signed byte strides against unsigned element strides), which is why a typed converter sits at
  the boundary (bead BD-036).
- *frankensympy*'s workspace refers to two sibling pin directories, `../franken_numpy-pin` and
  `../frankenscipy-pin`, that do not exist on this machine, and it pins a different nightly from the rest of the
  suite (`frankensympy/Cargo.toml:95–96`, `frankensympy/rust-toolchain.toml`). `derive/` therefore depends on
  individual `fsym-*` crates by path, builds on T, has no toolchain file of its own, and FrankenSymPy is moved to
  T by the toolchain train.
- *frankentorch* tensors live on the host. `Device::Metal` and `Device::Cuda` are tags, and `ft-nn` and
  `ft-autograd` run on the CPU (as reported from a source reading; re-read at INT-FT-02). A device tag earns no
  GPU operator coverage. On-device learning kernels are written in this project, in the shared kernel dialect.
- *franken_threed* does not yet package a single self-contained page (`franken_threed/README.md`, "Honest
  status"). The viewer's self-contained HTML export is this project's own build step.

**Row fields beyond the table.** Each row also carries `first_needed` (the milestone at which the foundation is
first admitted: M0 for FD-FSIM, FD-ASUP, FD-FSQL, FD-FT (Metal), FD-CUDA, FD-FSYM, FD-FMCP, FD-FNP; M1 for FD-FSCI
and FD-FKER; M3 for FD-FTUI, FD-F3D and the schema fixtures of FD-FDGR; M5 for FD-FLN and scan import; M6 for
FD-FTX; M8 for FD-FFW; M2 at the earliest for FD-FJAX and only if the profile asks) and `critical_path` (true only
for FD-FSIM, FD-ASUP and FD-FSQL, the three M1 depends on).

**Admission is per use, never inherited.** A row may hold several uses that are admitted at different milestones
(FD-FT: the Metal gateway at M0, the CPU trainer crates at M2; FD-FNP: `fnp-io` at M0, `fnp-linalg` at M2). Each
use names its own record; the validator of N33a-07 refuses a use whose crates are in the lockfile with no record.

## Acceptance criteria

- [ ] `franken-stack.lock` holds exactly eighteen `[[foundation]]` rows with the identifiers above, and parses under the strict schema of N33a-03.
- [ ] Every row has a non-empty `fallback` or the explicit string `"none"`, and every row with posture `consume`, `consume-path` or `build-time` has a non-empty `confined_to`.
- [ ] The four notes are present on FD-FNP, FD-FSYM, FD-FT and FD-F3D.
- [ ] `check-deps` (BD-003), reading these rows, refuses a planted manifest edge from `frob-dyn` to `fs-mbd` (not in confinement), from `frob-core` to `franken-kernel` (a Pattern), and from any core crate to `ftx-drape` or `f3d-runtime`.
- [ ] The firewall consistency test passes: the three `critical_path` rows are exactly the foundations M1 depends on, and no row marked [F] or [M] has `critical_path = true`.
- [ ] No row contains a machine path; `path` values are relative (`../frankensim`).

## Test plan

### Unit tests (`cargo test -p xtask stack::ledger`)
- `ledger_has_eighteen_rows`: the identifiers equal the set FD-FSIM, FD-ASUP, FD-FSQL, FD-FT, FD-CUDA, FD-FNP, FD-FSCI, FD-FSYM, FD-FLN, FD-FMCP, FD-FTUI, FD-F3D, FD-FDGR, FD-FJAX, FD-FKER, FD-FTX, FD-FFW, FD-FSS.
- `ledger_every_row_has_fallback_and_gate_or_none`: FD-FFW and FD-FSS have `admission_gate = "none"`; all others name at least one `INT-` gate.
- `ledger_confinement_matches_crate_map`: every crate named in a `confined_to` exists in the crate map of the workspace (or is the token `bedrock-direct`).
- `ledger_critical_path_is_three`: exactly FD-FSIM, FD-ASUP, FD-FSQL.
- `ledger_pattern_rows_have_no_path_or_version`: FD-FJAX, FD-FFW, FD-FSS carry neither `path` nor `version`.
- `ledger_multi_use_rows`: FD-FSQL parses to three uses (consume, pattern, oracle); FD-FT to two with different `first_needed`.

### End-to-end script and logging
`scripts/e2e/stack_receipt.sh` (bead N33a-27), step `ledger_rows`: `cargo run -p xtask -- check-stack --json`
must list eighteen foundations with their postures; the script then plants the three forbidden edges of the
acceptance list one at a time in a scratch copy and asserts that `cargo run -p xtask -- check-deps` exits non-zero
naming the foundation and the offending crate. Each step logs the command, exit code, wall time and the finding.

### Known answers and negative controls
- Negative controls: the three planted edges; a row with `posture = "consume"` and empty `confined_to`; a nineteenth row for a sibling that the design does not admit (`franken_networkx`), which must fail the "eighteen rows" test until an ADR adds it.
- Metamorphic relation: permuting the rows changes neither the parse result (as a set) nor any check outcome.
- Determinism lanes: the parsed ledger serializes to identical canonical bytes twice on one machine and across platforms.

## Considerations

- Siblings named by the design and deliberately not in the ledger: franken_networkx (not admitted: tree and cycle algorithms on kinematic graphs are small and are written in `frob-design`); franken_markdown and frankenmermaid (optional subprocess for rendering a report, which is a view). FrankenSim crates `fs-conform`, `fs-truss` and `fs-g1-train` are not admitted inside FD-FSIM.
- Three siblings pin asupersync 0.5.0 (frankentui behind an optional executor feature, franken_threed, frankenjax). The ledger keeps them out of every graph or forbids the offending feature; RISK-03 (two asupersync versions in one build) is watched by INT-ASUP-01.
- A foundation's row changes only with an ADR; a pin changes only through the compatibility train (move the pin, write a new receipt, rerun the admission and parity gates, relock).
- OPEN-SUITE-1 (which asupersync version the whole graph resolves) has the default "the one published version the siblings are aligned on; until that lands, whatever FrankenSim's pinned commit builds with (0.6.2 by path on the day of reading)"; the FD-ASUP row's `version` field is filled at INT-ASUP-01.
