## Background

`franken-stack.lock` is the file that states which sibling projects FrankenRobotics is built on and at which
commits. It is TOML in the format the sibling product FrankenMining uses (FACT:
`franken_mining/franken-stack.lock`), with one `[[foundation]]` row per sibling and one top-level `toolchain`
field naming **T**, the single Rust toolchain on which the whole build graph (the core workspace, the two GPU
annexes, the derivation annex and the MCP server) builds. The file is checked by `xtask check-stack`, one of the
workspace's six checks.

A pin is a statement of intent. What was actually built is a different fact, captured by the resolution receipt
(bead N33a-04). This bead is the first half: a parser that turns the lock into typed data and refuses anything
ambiguous, so that the receipt writer, the dependency check and the admission validator all read the same
structure. Why strict: the two failure modes this file exists to prevent are a sibling silently off its pin and a
foundation used outside its confinement, and both are invisible if an unknown or misspelt field is ignored.

`xtask` is a small crate (cap 3 thousand lines) that runs no physics and holds no policy. The parser here is
self-contained and uses only the standard library plus `frob-core`'s strict TOML-subset reader
(`frob_core::registry::toml`, N34p2-01; the one TOML reader of the repository, which admits comments, inline
tables and dotted table headers, refuses floats and dates, and makes a key no loader took an `UnknownKey` error
with its line and column), so that reading the lock depends on no product type. The digest below is computed with
`fs-blake3`, the bedrock BLAKE3 crate that N33a-04's tree hash also uses (a domain-tagged stream over raw bytes,
which neither of `frob-core`'s two hashing entry points is). (`xtask` as a crate does link `frob-core`, the lowest layer, for the canonical writer
that writes the receipt and the generated files, N33a-04 and BD-004; it links no crate above it. An earlier
wording of this bead said `xtask` may not depend on `frob-core`; the layer rule forbids only upward edges, and
`xtask` is the highest layer.)

## Scope

In: the schema of `franken-stack.lock` (`frob.stack-lock/1`), the typed model, the parser, the validation rules,
canonical re-serialization and the **stack-lock digest**. This is the one specification of the lock's fields and
its strict reader: the workspace chapter's draft of `check-stack` (N34-13, superseded by N33a-05) listed the same
fields, and its two additions (the key of the `[auditor]` table, the unknown-table test) are folded in below.
Out: the row contents (N33a-02); the receipt (N33a-04); comparison against the newest receipt and the checkouts,
where a parser error is reported as the finding `stack.lock-schema` (N33a-05); the choice of T (BD-031, the
toolchain admission gate).

## Technical approach

**File shape (the two rows the design gives as the template).**

```toml
toolchain = "<T, chosen at INT-TOOLCHAIN-01; moved only by a toolchain train>"

[[foundation]]
id = "FD-FSIM"
name = "frankensim"
posture = "consume-path"
path = "../frankensim"
git_rev = "<40-hex commit recorded at INT-FSIM-01>"
toolchain = "<the channel in the sibling's own toolchain file at git_rev; equal to T after the train>"
features = ["referee", "geometry", "ledger"]            # airlock groups compiled by default
build_env = { FRANKENSIM_DEPGRAPH_SALT = "franken-robotics-dev-v1" }
confined_to = ["frob-fsim", "bedrock-direct"]
admission_gate = "INT-FSIM-01"
receipt = "<BLAKE3 of the resolution receipt this row was admitted under>"
fallback = "KILL-FSIM: (a) pinned worker process exchanging whole jobs; (b) lift the minimal referee set."

[[foundation]]
id = "FD-ASUP"
name = "asupersync"
posture = "consume"
version = "<the single version every workspace resolves>"
admission_gate = "INT-ASUP-01"
fallback = "FD-ASUP-01 aligns the siblings; a surface that still brings a second package: KILL-MCP fallback 1."
```

**Typed model (DESIGN, `xtask/src/stack/lock.rs`).**

```rust
pub struct StackLock { pub toolchain: Channel, pub foundations: Vec<Foundation> }
pub struct Foundation {
    pub id: FdId,                       // "FD-" + upper-case letters and digits
    pub name: String,
    pub uses: Vec<Use>,                 // from N33a-01; a single `posture` key is sugar for one use
    pub path: Option<RelPath>,          // required for consume-path and build-time
    pub git_rev: Option<GitRev>,        // Commit: exactly 40 lower-case hex digits; or Unadmitted ("unadmitted")
    pub version: Option<ExactVersion>,  // required for registry `consume`; "=x.y.z" semantics
    pub toolchain: Option<Channel>,     // the sibling's own channel at git_rev
    pub features: Vec<String>,
    pub build_env: BTreeMap<String, String>,
    pub confined_to: Vec<String>,
    pub admission_gate: GateRef,        // "INT-…", a range "INT-FSIM-01..18", or "none"
    pub receipt: Option<Blake3Hex>,     // the receipt this row was admitted under
    pub fallback: String,
    pub first_needed: Milestone, pub critical_path: bool, pub note: Option<String>,
}
```

**Fields and tables added by other beads (part of `frob.stack-lock/1`; the parser accepts exactly these).** Per
row: `required_at`, `optional_at` and `firewall_cells` (the dependency firewall as data, N33b-01; the key `uses`
is this bead's list of postures and is not reused for the firewall's cell text). At top level: `[freeze]` (the
tournament freeze, N33b-03); `[json_library]` (N34-04) with `package`, `version` and `allowed_in` (the crates
that may link the JSON library), and its sub-table `[json_library.features]` holding one sorted feature set per
binary target, keyed by the binary's name (not one unified feature list: features unify per build, so binaries
differ); and `[auditor]` (N34-25) with one key, `stable = "<channel of the certificate checker's own toolchain
file>"`, the stable channel of the independent checker. Each is validated by the bead that adds it, through a
hook of this parser; any other key or table is still `unknown-field` under rule 1.

**Validation rules (each a named error; none is a warning).**

1. Unknown top-level key, unknown table or unknown row key → `unknown-field` with the key and the row identifier.
2. `id` unique; `name` unique.
3. `git_rev`, where present, is 40 lower-case hexadecimal digits. A short hash, a branch name or a tag is refused
   (a pin names a commit).
4. `path` is relative, begins with `../` and contains no `..` component after the first; an absolute path or a
   home-directory path is refused. Identities are independent of machine paths.
5. `consume-path` and `build-time` require `path`; they require `git_rev` once the row's admission gate has a
   record (before that the literal `"unadmitted"` is the only other accepted value, so a placeholder cannot be
   mistaken for a pin).
6. Registry `consume` requires `version`, and it must be exact.
7. `features` entries for FD-FSIM must be airlock feature-group names: `referee`, `geometry`, `ledger`,
   `optimize`, `stats`, `spectral`, `actuation`, `structure`, `multiphysics` (`harness` is dev-only and never
   listed). The default list is exactly `["referee", "geometry", "ledger"]`.
8. `build_env` keys are upper-case identifiers; values are printable ASCII.
9. `toolchain` (top level and per row) is a channel string: `nightly-YYYY-MM-DD` or a stable version. A row's
   `toolchain` may differ from T while the row records a starting state before a toolchain train; the
   difference is not a parser error but the `off-T` condition of the one-toolchain rule (N33c-08: `check-stack`
   reports it as `stack.toolchain`, kind `off-T`, informational until the first adopted toolchain train and a
   failure after). DESIGN: this rule once made the difference a failure as soon as INT-TOOLCHAIN-01 had a record;
   under candidate (b) of §33.13 the consumed siblings already on the common nightly keep it until the scheduled
   train to (a), so that trigger would have failed every check from the gate to the train.
10. `receipt`, where present, is 64 lower-case hex digits and names a file that exists under `receipts/`.
11. `fallback` is non-empty.

**Canonical form and the stack-lock digest.** `StackLock::canonical_bytes()` serializes the typed model
deterministically: keys in a fixed order, rows sorted by `id`, strings NFC, no comments, LF line ends. The
**stack-lock digest** is BLAKE3 over those bytes with the domain tag `frob.stack-lock/1`. It changes when a pin,
a feature list, a build-environment entry or T changes, and not when a comment or the row order changes. It is
the value the airlock puts in every memoized referee key (bead N33a-06).

**API.** `stack::lock::load(path) -> Result<StackLock, LockError>`; `StackLock::digest() -> [u8; 32]`;
`StackLock::foundation(id)`. `LockError` carries the rule number, the row and the key. The parser is a pure
function of the file bytes (determinism class D0): `load` checks everything the file alone decides, including
the form of `git_rev` (`unadmitted` is the only accepted non-hex value) and of `receipt`. The parts of rules 5
and 10 that depend on state outside the file are a second, separate call,
`StackLock::check_admitted(&self, admitted: &BTreeSet<GateRef>, receipts_dir: &Path) -> Vec<LockError>`:
`unadmitted` on a row whose admission gate is in `admitted` is a rule-5 error; a `receipt` that names no file
under `receipts_dir` is a rule-10 error. (A row `toolchain` off T is never a `LockError`; see rule 9.) `check-stack` (N33a-05) calls both. The set of admitted gates
is read by the caller from the admission records (N33a-07, which depends on this bead, supplies the reader; until
it lands the set is empty), so the parser itself reads no record and no directory.

## Acceptance criteria

- [ ] The template above (with real values substituted) parses; so do the eighteen rows of N33a-02.
- [ ] Each of the eleven rules has a failing fixture that is refused with the named error, and none of them is downgraded to a warning.
- [ ] `canonical_bytes` of a lock and of the same lock with rows permuted and comments added are identical; changing one hex digit of one `git_rev` changes the digest.
- [ ] The parser has no dependency on any crate it checks (`cargo tree -p xtask` shows no `frob-*` crate other than those the workspace rules allow for `xtask`).
- [ ] `stack::lock::json_schema()` emits the JSON Schema of `frob.stack-lock/1` from the typed model (deterministic bytes); the committed file `schemas/frob.stack-lock.1.json` is written from it by the generator row of `check-generated` (BD-004, which depends on this bead) and never by hand.
- [ ] A lock whose FD-FSIM row has `git_rev = "unadmitted"` loads; `check_admitted` accepts it while INT-FSIM-01 is absent from the admitted set and refuses it under rule 5 once INT-FSIM-01 is in it; `load` alone never reads a record or a directory.

## Test plan

### Unit tests (`cargo test -p xtask stack::lock`)
- `lock_parses_template`: the two-row template → two foundations; FD-FSIM features = [referee, geometry, ledger]; build_env has one entry `FRANKENSIM_DEPGRAPH_SALT = franken-robotics-dev-v1`.
- `lock_rejects_unknown_field`: a row with `psture = "consume"` → rule 1, key `psture`.
- `lock_rejects_unknown_table`: a top-level table `[audit]` (misspelt `[auditor]`) → rule 1, key `audit`; `[auditor]` with a key other than `stable` → rule 1.
- `lock_rejects_short_rev`: `git_rev = "483d09c682f2"` (12 hex) → rule 3.
- `lock_rejects_absolute_path`: `path = "/Users/x/frankensim"` → rule 4; `path = "~/frankensim"` → rule 4.
- `lock_rejects_inexact_version`: `version = "^0.6"` → rule 6.
- `lock_rejects_unknown_group`: `features = ["referee", "fluid"]` → rule 7.
- `lock_rejects_duplicate_id`: two rows `FD-ASUP` → rule 2.
- `lock_digest_ignores_order_and_comments`: two files differing only in row order and comments → equal digests.
- `lock_digest_sees_pin_change`: one hex digit changed → different digest; a changed `build_env` value → different digest; a changed top-level `toolchain` → different digest.
- `lock_roundtrip_canonical`: `load(canonical_bytes(load(f)))` equals `load(f)`.
- `lock_json_schema_agrees_with_parser`: the property names of `json_schema()` for a row and for the top level equal the keys `load` accepts (including the hooked tables), two calls give identical bytes, and the template validates against it while a row with `psture` does not.
- `lock_unadmitted_rev_depends_on_admitted_set`: `git_rev = "unadmitted"` loads; `check_admitted` with an empty set → no error; with {INT-FSIM-01} → rule 5; `git_rev = "pending"` → rule 3 at `load`.
- `lock_row_toolchain_may_differ_from_t`: a row toolchain unequal to T loads, and `check_admitted` returns no error for it with or without INT-TOOLCHAIN-01 in the set (the `off-T` condition is N33c-08's); a row toolchain `nightly-2026-8-31` → rule 9 at `load`.
- `lock_receipt_must_name_a_file`: a well-formed `receipt` hash with no file under a scratch `receipts/` → rule 10 from `check_admitted`; with the file present → no error.
- Property test (`lock_canonical_is_idempotent`): for 10³ generated valid locks, canonical bytes of the re-parsed canonical form are identical.

### End-to-end script and logging
`scripts/e2e/stack_receipt.sh` (bead N33a-27), step `lock_parse`: runs `cargo run -p xtask -- check-stack --json`
on the repository and asserts that the report echoes T, the number of foundations and the stack-lock digest; then
runs it on eleven scratch copies, each with one planted violation, and asserts a non-zero exit with the expected
rule. Log lines carry the command, exit code, wall time, the rule and the digest.

### Known answers and negative controls
- Negative controls: the eleven planted violations; the permuted file (must not change the digest); the changed pin (must change it).
- Determinism lanes: canonical bytes and digest identical twice on one machine, in debug and release, on Linux and macOS (the file is read as bytes; no locale or path enters).

## Considerations

- The lock is edited by people and agents, so error messages name the row and the key and suggest the fix; the parser never guesses.
- TOML datetime and float values are not used anywhere in the schema, which removes two sources of non-canonical text.
- When KILL-FSIM's fallback (a) keeps the worker at an older FrankenSim pin, the FD-FSIM row gains a `worker_rev` and `worker_toolchain` pair; adding that key is an ADR and a schema bump to `frob.stack-lock/2`, not a silent extension.
- RISK-02 (the toolchain train costs more than M0 allows) shows up here as rows whose `toolchain` differs from T; the report line exists so that the difference is visible on every check.
