## Background

`franken-stack.lock` says which sibling commits FrankenRobotics intends to build on. What a build actually used
is a different fact, and inside the suite the two have already diverged (FACT, read 2026-11-21): FrankenSim's own
`constellation.lock` pins asupersync 0.5.0 at `7a0f2f55047c` while its `Cargo.lock` resolves asupersync 0.6.2 by
path, the local asupersync checkout is at `b32c5ba66315` with 267 modified paths, and FrankenSim's checkout itself
has 32 modified paths at head `483d09c682f2`. A pin cannot describe any of that.

The **resolution receipt** is the record of what was resolved: one canonical JSON file, written by
`xtask check-stack` at every admission and at every pin move, capturing source trees, requested features,
compiler channels, lockfiles and the constraints of direct and transitive siblings. Every admission record cites
a receipt hash, and every result in the Chronicle ledger carries the receipt hash of the binary that produced it,
which is what lets a later reader decide whether two results may be compared as results of the same stack.

Design decisions and their reasons (DESIGN):
- *Hash bytes when a tree is dirty.* A commit hash says nothing about uncommitted edits; the receipt hashes the
  tracked bytes so a dirty build still has an identity. Rejected: refusing to build on a dirty sibling, because
  other agents work in the sibling repositories all day and development would stop.
- *Classify disagreement the way FrankenSim does.* Its preflight distinguishes on-pin, stale-lock and drift; using
  the same three words lets a FrankenSim maintainer read our receipt.
- *No machine paths.* Receipts are compared across the two machines of the project (`trj`, the Linux host with
  two RTX 4090s, and the M5 Ultra Mac), so nothing in one may depend on a home directory.
- *Never move a sibling.* The writer only reads sibling checkouts.

## Scope

In: the receipt schema, the writer, the tree hash, the drift classifier, the duplicate-package scan, the store
under `receipts/`, and the determinism of all of it.
Out: comparing the newest receipt with the tree and failing the check (N33a-05); stamping the hash into binaries
and results (N33a-06); admission records that cite it (N33a-07).

## Technical approach

**Schema `frob.stack-receipt/1` (canonical JSON; the design's example, with field meanings).**

```json
{
  "schema": "frob.stack-receipt/1",
  "repo_rev": "<this repository's commit>",
  "toolchain": "<T>",
  "siblings": [
    {"fd": "FD-FSIM", "rev": "<40 hex>", "dirty": false, "tree_hash": null,
     "features": ["referee", "geometry", "ledger"],
     "own_lock": {"file": "constellation.lock", "hash": "<BLAKE3>", "agrees": false,
                  "class": "stale-lock | drift | on-pin"}},
    {"fd": "FD-ASUP", "rev": "<40 hex>", "dirty": true, "tree_hash": "<BLAKE3 of tracked bytes>"}
  ],
  "lockfiles": [{"workspace": "core", "hash": "<BLAKE3 of Cargo.lock>", "packages": 0, "registry": 0}],
  "patches": ["asupersync -> ../asupersync"],
  "profile_overrides": ["fsqlite*: opt-level 1"],
  "build_env": {"FRANKENSIM_DEPGRAPH_SALT": "franken-robotics-dev-v1"},
  "duplicates": [],
  "commands": [{"argv": ["cargo", "tree", "-d"], "exit": 0, "output_hash": "<BLAKE3>"}]
}
```

Field rules:
- `repo_rev`: the commit of this repository, plus `repo_dirty` and `repo_tree_hash` under the same rule as siblings.
- `siblings`: one entry per foundation with a checkout (postures consume-path, build-time, subprocess with a local
  tool), sorted by `fd`. `rev` is `git rev-parse HEAD` in the sibling; `dirty` is true when `git status
  --porcelain` over tracked files is non-empty; `tree_hash` is null when clean.
- `own_lock`: a sibling's own lock of its siblings (`constellation.lock` in FrankenSim, `SUITE.lock` in
  franken_lean) is hashed and compared with what this build resolves.
- `lockfiles`: one entry per workspace of this repository (core, the two GPU annexes, `apps/`, `derive/`,
  `bindings/`, `worker/`), with the package count and the count that comes from the registry.
- `patches`, `profile_overrides`, `build_env`: the three things Cargo does not propagate from a path dependency
  and that the workspace root therefore repeats (the asupersync patch entry, FrankenSim's FrankenSQLite profile
  overrides, the build-identity variable). Paths in `patches` are repository-relative.
- `duplicates`: packages that appear at two versions in one workspace, from `cargo tree -d`; an asupersync
  duplicate is listed first.
- `commands`: every external command the writer ran, with its exit code and the BLAKE3 of its standard output.

**Tree hash (algorithm).**
1. List tracked files with `git ls-files -z` in the sibling (untracked and ignored files are excluded).
2. Sort paths bytewise.
3. For each path feed the hasher: the path length as a 64-bit little-endian integer, the path bytes, the file
   mode bit for "executable" as one byte, the content length as a 64-bit little-endian integer, the content bytes.
   A symbolic link contributes its target text as content. A tracked file deleted in the working tree contributes
   the marker byte 0xFF and no content.
4. `tree_hash` = BLAKE3 of the stream, with the domain tag `frob.tree/1` fed first.
The hash is computed with the workspace's safe-Rust BLAKE3 (`fs-blake3`, a bedrock crate) and is independent of
file timestamps and of the checkout location.

**Drift classification (algorithm; the three classes FrankenSim's preflight uses).** For a sibling S whose own
lock (or our lock) names commit P for a dependency D, and whose checkout of D is at head H:
1. `on-pin`: H = P and D is clean.
2. `stale-lock`: D is clean, H ≠ P, and P is an ancestor of H (`git merge-base --is-ancestor P H` succeeds): the
   checkout is a fast-forward of the lock.
3. `drift`: anything else: D is dirty, or H is an ancestor of P (retreated), or neither is an ancestor of the
   other (diverged), or P is unknown to the repository. The receipt records which of `dirty`, `retreated`,
   `diverged`, `unknown-pin` applied.
Whether a difference is a fast-forward or a divergence is classified, never assumed.

**Writer steps.**
1. Load the lock (N33a-03); resolve each `path` relative to the repository root.
2. Read every toolchain file and tracked `Cargo.lock`; hash them.
3. For each sibling: `rev`, `dirty`, `tree_hash` if dirty, `own_lock`, drift class.
4. Run `cargo metadata --locked --format-version 1` and `cargo tree -d` per workspace through the build-offload
   shim (cargo is never invoked by absolute path); record commands and output hashes; fill `lockfiles` and
   `duplicates`.
5. Serialize canonically: object keys sorted, arrays in the stated order, no insignificant whitespace, strings NFC,
   integers as JSON integers (all are below 2⁵³).
6. Name the file by the BLAKE3 of its bytes: `receipts/<64 hex>.json`. Writing is atomic (write aside, rename).
   An existing file with the same name is left untouched.

**Path independence.** No field holds an absolute path, a user name or a host name. The writer's unit test runs
it from two different checkout locations and compares bytes.

Determinism class: D0 for an unchanged tree. Evidence class of a receipt: it is a record, cited by hash; it
carries no claim of its own. `check-stack` writes nothing outside this repository.

## Acceptance criteria

- [ ] A receipt computed twice on an unchanged tree is byte-identical (KA-767), and its file name equals the BLAKE3 of its bytes.
- [ ] Touching one tracked file in a sibling copy flips that sibling's `dirty` to true and changes `tree_hash` (the negative control of KA-767).
- [ ] The three drift classes are produced on constructed repositories: on-pin; a fast-forward (stale-lock); dirty, retreated, diverged and unknown-pin (drift, with the sub-reason).
- [ ] A receipt written from `/a/b/repo` equals one written from `/c/repo` for the same commits; a grep of the receipt for `/Users/`, `/home/` and the host name finds nothing.
- [ ] `duplicates` is non-empty on a workspace seeded with a second asupersync version, and lists it first.
- [ ] The writer makes no write and no `git` state change in any sibling (verified by running it against sibling copies mounted read-only).
- [ ] The first receipt of the repository exists under `receipts/` and its hash is recorded in the `receipt` field of the rows admitted under it.

## Test plan

### Unit tests (`cargo test -p xtask stack::receipt`; fixtures are small git repositories built by the test, labelled `synthetic`)
- `receipt_idempotent`: two runs → identical bytes; identical hash.
- `receipt_dirty_flips`: append one byte to a tracked file → `dirty = true`, `tree_hash` non-null and different from the hash after a second, different edit.
- `tree_hash_ignores_untracked_and_mtime`: add an untracked file and touch timestamps → hash unchanged.
- `tree_hash_sees_mode_and_deletion`: toggling the executable bit changes the hash; deleting a tracked file changes it.
- `tree_hash_length_prefix_prevents_ambiguity`: files (`ab`, `c`) and (`a`, `bc`) with concatenable contents give different hashes.
- `drift_on_pin`, `drift_stale_lock_fast_forward`, `drift_retreated`, `drift_diverged`, `drift_dirty`, `drift_unknown_pin`: six constructed histories → the expected class and sub-reason.
- `receipt_no_machine_paths`: generated from two temporary roots → equal bytes.
- `receipt_canonical_keys_sorted`: a byte-level check that object keys are in sorted order and no space follows a colon.
- `receipt_duplicates_lists_asupersync_first`: a synthetic `cargo tree -d` output with two duplicated packages.
- `receipt_store_is_content_addressed`: writing the same receipt twice creates one file; a truncated existing file with the right name is detected by re-hashing on read.

### End-to-end script and logging
`scripts/e2e/stack_receipt.sh` (bead N33a-27) drives the real `xtask` on the real tree and on scratch copies of
the siblings; it asserts KA-767 and its control and logs the receipt hash, each sibling's revision, dirty flag and
drift class, the package counts and the duplicate list.

### Known answers and negative controls
- KA-767: byte-identical receipt on an unchanged tree; control: one touched tracked file flips `dirty`, changes `tree_hash`, and `check-stack` fails (the failing half is N33a-05).
- Planted failures: an absolute path injected into `patches` must be refused by the writer; a sibling pin that is an unknown object must classify as drift, never as stale-lock.
- Metamorphic relations: the receipt is invariant under moving the whole checkout tree, under `git gc` in a sibling, and under reordering rows of the lock.
- Determinism lanes: twice on one machine; debug and release; Linux and macOS produce the same bytes for the same commits (the only platform-dependent input, the executable bit, is read from the git index, not from the file system).

## Considerations

- Hashing a large dirty tree costs time (FrankenSim's tracked source is millions of lines); the writer hashes only siblings that are dirty, and streams files. Expected cost is seconds, inside the 60-second budget of the six checks on a warm tree.
- RISK-23 (dirty or off-pin sibling trees make a receipt unrepeatable): the mitigation is exactly this record plus the rule that no gate records a PASS on a dirty tree (N33a-05).
- OPEN-SUITE-3 (is a dirty asupersync checkout acceptable for development builds between receipts?): default yes for development, with the tree hash in the receipt, and no gate records a PASS. Owner input is wanted at M0.
- The receipt contains repository-relative paths and commit hashes of the owner's projects; it contains no private-scene data and may be committed.
- If canonical JSON rules change workspace-wide, the schema name becomes `frob.stack-receipt/2`; old receipts stay valid under their own schema because they are cited by the hash of their bytes.
