## Background

`xtask check-stack` is one of the six workspace checks (the others are `check-layers`, `check-deps`,
`check-unsafe`, `check-generated`, `check-contracts`; a seventh needs the owner's approval). Its assignment is:
the stack lock, with the toolchain T, against lockfiles, toolchain files and sibling heads; the resolution
receipt; drift classification; and the check itself writes nothing to a sibling checkout.

The lock parser (N33a-03) and the receipt writer (N33a-04) produce data. This bead is the judgement: when does
the check fail, what may a gate record on the stack it finds, and how the tool proves that it never touches a
sibling. Three invariants of the suite-consumption design are enforced here:

- **INV-SUITE-03.** Every recorded gate result cites a resolution receipt, and no PASS is recorded on a dirty
  sibling tree.
- **INV-SUITE-04.** No sibling checkout is ever modified or moved by this project's tooling: `check-stack` writes
  nothing outside this repository, and its test runs it against a copy it cannot write to. A change to a sibling
  is made by an agent working in that sibling's repository under that repository's rules, never by a tool of
  this one.
- A working rule inherited from the suite: before a build failure is attributed to this repository,
  `check-stack` runs; an off-pin sibling is classified as a fast-forward or a divergence before any remedy is
  proposed; and a sibling checkout is never moved back to its pin to make a check pass.

Why "newest receipt" and not "the lock": the lock states intent and can be edited by hand; the receipt is what
the last admitted build resolved. Comparing the tree with the newest receipt detects a sibling that moved, a
lockfile that changed and a toolchain file that changed since the last admission, each of which invalidates
"same stack" for results recorded afterwards.

Rejected alternatives. (1) Trust `Cargo.lock` alone: it does not record a path dependency's commit or whether
its tree is dirty. (2) Refuse every dirty sibling: the siblings are worked on daily by other agents; a dirty tree
admits development builds, with its bytes hashed, and no gate records a pass on it. (3) Have `check-stack` repair
drift (check out the pinned commit). Rejected because other
agents work in the same sibling checkouts, a newer clean head must never be rolled back locally, and a tool that
rewrites a neighbour's working tree is the failure INV-SUITE-04 exists to prevent. The rule binds this
project's tooling only. Siblings are the owner's projects and are changed by this program: an upstream work item
is carried out by an agent working in the sibling's repository under that repository's rules, never by a tool of
this one.

Note on ownership: the seed bead BD-004 wires the `check-stack` subcommand into `xtask` together with three other
checks and the test that exactly six subcommands exist, and fixes the conventions every check follows: a finding
identifier is `<check>.<name>` and belongs to one check, exit codes are 0 clean, 2 findings and 3 usage, a report
carries `elapsed_ms`, and the common flags are `--root <dir>` and `--json`. This bead supplies the rules that
subcommand runs, as a library module, with their own tests, under those conventions. It is the one bead for the
body of `check-stack`: the workspace chapter's draft of the same check (N34-13) is superseded by this bead, with
its lock reader carried by N33a-03 and its receipt by N33a-04; the finding identifiers `stack.*`, the stale-lock
finding, the exit code and the 10-second share below come from that draft.

## Scope

In: the `check-stack` subcommand's two modes; the three-way comparison of the lock, the newest receipt and the
trees, with its finding identifiers and exit codes; the dirty-tree guard used by gate recording; the mode that
writes a new receipt; the proof that the tool writes nothing in a sibling; the structured report; the share of
GATE-WS-01 this check owns (the stale stack lock, plant 7) and its 10-second share of GATE-WS-04.
Out: the lock's schema and strict reader (N33a-03); the receipt's schema, writer, tree hash and drift classifier
(N33a-04); the first lock and receipt (BD-001); the failure on a second asupersync package, which belongs to
`check-deps` (rule `asup.duplicate`, N34-03) and to the admission gate INT-ASUP-01 (BD-008, which also owns the
finding `stack.asup-version` for a single package at the wrong version); the JSON-library table's rules (N34-04);
the six-subcommand test, the command table and the ownership rule over finding identifiers (BD-004); the
end-to-end run of the seven plants that records GATE-WS-01 and GATE-WS-04 (N34-14); the admission-record validator
(N33a-07); the registered tests of INV-SUITE-03 and INV-SUITE-04 with their planted violations (N33c-30, which
depends on this bead); the one-toolchain conditions, reported under `stack.toolchain-file` and `off-T` (N33c-08);
the refusal raised when evidence from another receipt is offered as same-stack evidence (FROB-REF-890, raised by
the evidence layer, N33a-06).

## Technical approach

**Modes (flags of the one subcommand; no new subcommand).**
- `cargo xtask check-stack` (default, verify): compute the current resolution in memory, compare with the newest
  receipt and the lock, report, exit 0 (clean), 2 (findings) or 3 (usage). Writes nothing.
- `check-stack --write-receipt --reason <admission|pin-move|toolchain-train> --gate <INT-…>`: computes the
  receipt from the trees and the lock, writes it under `receipts/`, updates `receipts/HEAD` and
  `receipts/LOCK_DIGEST` (the stack-lock digest of N33a-03 for the lock the receipt was written for; the two
  one-line files that `frob-core`'s build script embeds, N33a-06), each by write-to-temporary and rename, and
  prints the hash. On the tree BD-001 leaves (the bootstrap receipt present, neither one-line file written yet)
  the first run reproduces the bootstrap receipt byte for byte, writes no second receipt, and writes the two
  files naming it.
  It writes only inside this repository, never edits the lock and never touches a sibling. Used once per
  admission and per pin move (the compatibility train: move the pin, write a new receipt, rerun the admission and
  parity gates, relock).
- `check-stack --json`: the report as one JSON object on standard output (schema `frob.check-stack/1`).
- `--root <dir>`: the common flag of the six checks, used by the plant harness to run on a scratch copy.

**"Newest receipt".** The receipt named in `receipts/HEAD` (a one-line text file holding the hash of the most
recently written receipt; written atomically by `--write-receipt`). Time stamps are not used, so the choice is
reproducible. A missing or dangling `HEAD` is the failure `stack.receipt-missing` (kind `no-receipt`).

**Comparison algorithm (verify).** Three things are compared pairwise: the lock (intent), the newest receipt
(what the last admitted build resolved) and the trees (what is there now).
1. Load the lock; a parser error of N33a-03 is the finding `stack.lock-schema` with the parser's rule as its kind.
   Then run the lock's state-dependent rules, `StackLock::check_admitted` of N33a-03 (an `unadmitted` pin whose
   gate has a record, a `receipt` naming no file), reported the same way (a row toolchain off T is never a lock
   error: it is the kind `off-T` of `stack.toolchain` in the table below, N33a-03 rule 9); and the lift registry validator `stack::lifts::validate` of N33a-01, whose findings are
   `stack.lift`.
2. Compute the current resolution exactly as the receipt writer would (same code path), without writing.
3. Compare and produce findings. A finding has an **identifier** `stack.<name>`, which is the unit the ownership
   rule of BD-004 and the plant matrix of GATE-WS-01 count, and a **kind**, which names the precise condition
   (DESIGN: two drafts of this check named the same findings differently, one by identifier and one by kind; both
   vocabularies are kept, in these two fields, because the workspace gate's script asserts identifiers and the
   stack script asserts kinds).

   | Identifier | Kind | Condition | Fails |
   |---|---|---|---|
   | `stack.lock-schema` | the rule of N33a-03 (`unknown-field`, …) | the lock does not parse or validate, at `load` or at `check_admitted` | yes |
   | `stack.lift` | the rule of N33a-01's lift validator (record parse, header or golden test, unregistered lifted file, Cargo edge to a `lift` foundation) | `registries/lifts.toml` or a lifted file breaks a lift rule | yes |
   | `stack.receipt-missing` | `no-receipt` | `receipts/HEAD` is missing or dangling, or a row's `receipt` hash is absent from `receipts/` | yes |
   | `stack.receipt-hash` | `receipt-tampered` | a receipt file's name is not the hash of its bytes | yes |
   | `stack.toolchain` | `toolchain-changed` | the root `rust-toolchain.toml` channel differs from the lock's `toolchain` or from the newest receipt's | yes |
   | `stack.toolchain` | `off-T` | a foundation row's `toolchain` differs from T (condition 3 of N33c-08, which owns the rule and its tests) | only after the first adopted toolchain train (a line with `kind = "toolchain"` and `outcome = "adopted"` in `receipts/train-log.ndjson`) |
   | `stack.toolchain` | `row-toolchain-stale` | a foundation row's `toolchain` differs from the channel of the sibling's own toolchain file at the row's `git_rev` (condition 3 of N33c-08) | yes |
   | `stack.toolchain-file` | the condition of N33c-08 | a toolchain file other than the root's, the certificate checker's, or (only when the lock records the worker fallback) the worker's; the rule and its tests are N33c-08's | yes |
   | `stack.pin` | `lock-edited` | a row's `git_rev`, `features` or `build_env` differs from the newest receipt: the lock was edited without a new receipt (a stale stack lock; plant 7 of GATE-WS-01) | yes |
   | `stack.pin` | `off-pin` | a sibling's `rev` differs from the lock's `git_rev`; carries the drift class of N33a-04 relative to the pin (`stale-lock`, or `drift` with `dirty`, `retreated`, `diverged` or `unknown-pin`) | yes |
   | `stack.sibling` | `sibling-moved` | a sibling's `rev` differs from the newest receipt; classified `fast-forward`, `retreated` or `diverged` relative to the receipt's revision | yes |
   | `stack.sibling` | `sibling-dirty` / `dirty-changed` | `dirty` is true now and the receipt recorded clean, or recorded another `tree_hash` | yes |
   | `stack.sibling` | `sibling-dirty` / `dirty-unchanged` | `dirty` is true now and the receipt recorded dirty with the same `tree_hash` (allowed for development) | no |
   | `stack.own-lock` | `own-lock-disagrees` | a sibling's own lock (`constellation.lock`, `SUITE.lock`) disagrees with what is resolved, with its class; informational when the receipt already recorded the same class (FrankenSim's stale `constellation.lock` is the standing example, tracked by upstream work item FD-FSIM-16, whose switch-over rule is "`check-stack` reports on-pin") | only when the class changed |
   | `stack.lockfile` | `lockfile-changed` / `lockfile-missing` | a workspace's committed `Cargo.lock` hash differs from the receipt, or the file is missing | yes |
   | `stack.patch`, `stack.profile`, `stack.env` | `patch-missing`, `profile-override-missing`, `build-env-missing` | one of the three root settings that Cargo does not propagate from a path dependency (the root manifest's patch entries, its profile overrides, the build-identity environment in `.cargo/config.toml`) is absent, or differs from the lock or from the newest receipt | yes |
   | `stack.env` | `foreign-build-class` | the FD-FSIM row's build-identity salt equals the salt FrankenSim's own `.cargo/config.toml` sets at the pinned commit (another graph's equivalence class); the rule and its test are N33a-08's | yes |

   Duplicate packages are **not** a finding of this check. The receipt records them in `duplicates` as data, the
   report prints them as a fact, and the check exits 0 on a tree whose only defect is a second asupersync package.
   Reason (the plan's gate, correcting an earlier draft of this bead that failed on any asupersync duplicate): the
   workspace gate requires each plant to be caught by the check that owns it and by no other, and the six-check
   table gives "one asupersync package per binary" to `check-deps`. The duplicate still blocks a PASS, through the
   guard below, and fails the admission gate INT-ASUP-01 through `check-deps` and the receipt (BD-008).
4. Facts printed with every report: each sibling's drift class relative to the pin (`on-pin`, `stale-lock`,
   `drift` with its reason), the `duplicates` list, and `may_record_pass`.
5. Exit status: 0 when there are no findings, or only `dirty-unchanged` and informational `own-lock-disagrees`;
   2 otherwise; 3 for a usage error. Stated plainly: the check fails if the tracked lockfiles, the toolchain
   files or the sibling heads disagree with the newest receipt, or if the lock was edited without a new receipt.

**The dirty-tree PASS guard (library function `stack::guard::may_record_pass(receipt) -> Result<(), GuardRefusal>`).**
A gate result may be recorded as `pass` only if: the receipt it cites exists and hashes to its name; every
sibling entry in it has `dirty = false`; this repository's own tree was clean (`repo_dirty = false`); and
`duplicates` holds no asupersync entry. Otherwise the runner records the measured value with status `fail` or
`not-run` and the reason `dirty-stack`, never `pass`. A dirty sibling admits development builds only.

**Proof that the tool writes no sibling.** The module never opens a sibling path for writing and runs `git` in siblings only with
read-only subcommands (`rev-parse`, `status --porcelain`, `ls-files`, `merge-base --is-ancestor`, `cat-file`),
each with `--no-optional-locks` so that not even an index refresh is written. The integration test copies two
small sibling fixtures, removes write permission recursively, runs both modes and asserts success and an
unchanged byte-for-byte digest of each copy, `.git` directory included.

**Report (`frob.check-stack/1`).** `{toolchain, lock_digest, newest_receipt, current_hash, siblings: [{fd, rev,
class, reason, dirty}], duplicates: […], findings: [{id, kind, fd, detail, class, fails}], may_record_pass: bool,
wrote_receipt: null | hash, elapsed_ms}`. `may_record_pass` in the report is true only when no failing finding
was produced and the guard accepts the newest receipt; it is the one name for what an earlier draft called
`gate_eligible` (every sibling on-pin and clean).

**Cost.** The check is one of six that must together finish within 60 s on a warm tree (TARGET, GATE-WS-04); its
own share is 10 s in verify mode on a warm tree with the real siblings (TARGET). It shells out to `cargo tree -d`
once per workspace and hashes only dirty trees.

## Acceptance criteria

- [ ] On a clean tree whose newest receipt matches, `check-stack` exits 0 and reports `may_record_pass: true`.
- [ ] Each planted condition produces its finding and exit 2: a changed `Cargo.lock` (`stack.lockfile`); a changed toolchain file (`stack.toolchain`); a sibling advanced by one commit (`stack.sibling`, classified `fast-forward`); a sibling reset one commit back (`retreated`); a sibling on a side branch (`diverged`); a touched tracked file (`sibling-dirty`, `dirty-changed`); a removed `[patch.crates-io] asupersync` entry (`stack.patch`); a removed build-identity variable (`stack.env`).
- [ ] Plant 7 of GATE-WS-01: editing one `git_rev` in `franken-stack.lock` without a new receipt fails with `stack.pin` and exit 2, and no other check reports anything on that scratch copy.
- [ ] A scratch copy with a changed `Cargo.lock` and no new receipt fails with `stack.lockfile`; after `--write-receipt` it passes.
- [ ] A second asupersync version is recorded in `duplicates` and printed as a fact; `check-stack` exits 0 on that copy and `may_record_pass` is false; the failing check is `check-deps`.
- [ ] Verify mode finishes in under 10 s on a warm tree with the real siblings (TARGET; share of GATE-WS-04), and the report carries `elapsed_ms`.
- [ ] With a dirty sibling whose `tree_hash` equals the receipt's, the check exits 0 with `dirty-unchanged` and `may_record_pass: false`.
- [ ] `may_record_pass` refuses: a receipt with any dirty sibling; a receipt whose bytes do not hash to its name; a missing receipt.
- [ ] Both modes succeed against read-only sibling copies and leave them byte-identical (INV-SUITE-04).
- [ ] `--write-receipt` on an unchanged tree writes no new file and reprints the existing hash.
- [ ] No code path runs `git checkout`, `reset`, `stash`, `pull`, `fetch` or any write in a sibling (a source lint in the test greps the module for those words).

## Test plan

### Unit tests (`cargo test -p xtask stack::verify stack::guard`; synthetic git fixtures built per test)
- `verify_clean_passes`.
- `verify_lockfile_change_fails`: one byte appended to `Cargo.lock` → `lockfile-changed`.
- `verify_toolchain_change_fails`: `nightly-2026-08-31` edited to `nightly-2026-08-25` → `toolchain-changed`.
- `verify_sibling_fast_forward`, `verify_sibling_retreated`, `verify_sibling_diverged`: three histories → `sibling-moved` with the right class.
- `verify_dirty_unchanged_is_dev_ok`: receipt recorded dirty with hash h; tree still h → exit 0, guard false.
- `verify_dirty_changed_fails`.
- `duplicates_are_recorded_not_failed`: a synthetic duplicate list with asupersync 0.5.0 and 0.6.2 → exit 0, the list in the report, `may_record_pass` false; `guard_refuses_asupersync_duplicate`.
- `lock_edit_without_receipt_fails`: one `git_rev` edited in the lock, no new receipt → `stack.pin` with kinds `lock-edited` and `off-pin`, exit 2; an edited `features` list → `stack.pin`, `lock-edited`.
- `lockfile_missing_fails`: a workspace's `Cargo.lock` removed → `stack.lockfile`, `lockfile-missing`.
- `receipt_name_mismatch_fails`: one byte changed in the newest receipt → `stack.receipt-hash`.
- `finding_ids_are_namespaced`: every identifier the module can emit begins with `stack.` and each kind maps to exactly one identifier.
- `exit_codes`: clean 0; any failing finding 2; an unknown flag 3.
- `verify_root_settings_missing`: three sub-cases, one per repeated root setting.
- `verify_reports_lift_findings`: a planted file beginning `// LIFTED from` with no record → `stack.lift`, exit 2; the shipped empty registry → no `stack.lift` finding.
- `verify_reports_admitted_rules`: `git_rev = "unadmitted"` with INT-FSIM-01 in the admitted set → `stack.lock-schema` with rule 5; the same with an empty set → clean.
- `write_receipt_writes_head_and_lock_digest`: after `--write-receipt`, `receipts/HEAD` names the new receipt and `receipts/LOCK_DIGEST` equals the stack-lock digest of the lock; on the bootstrap tree (receipt present, neither file) the run writes the two files, writes no second receipt and prints the bootstrap hash; a crash simulated between temporary write and rename leaves the previous pair intact.
- `guard_refuses_dirty_receipt`, `guard_refuses_tampered_receipt`, `guard_refuses_missing_receipt`, `guard_accepts_clean_receipt`.
- `no_write_verbs_in_module`: the source lint.
- Property test `verify_is_pure`: for 200 random fixture states, two consecutive verify runs give identical reports and leave the fixture digest unchanged.

### End-to-end script and logging
`scripts/e2e/stack_receipt.sh` (bead N33a-27) runs the real binary through every planted condition above on
scratch copies and logs, per step, the command line, exit code, wall time, the finding kinds, the receipt hash
and `may_record_pass`. The read-only run logs the digest of each sibling copy before and after.
`scripts/e2e/workspace_checks.sh` (bead N34-14) plants the stale lock as plant 7 of 7 and logs the plant-by-check
matrix, asserting the identifier `stack.pin` and that the other five checks stay clean. On the clean tree it logs
one `metric` line per sibling (foundation identifier, revision, drift class, dirty flag) and the receipt hash in
the structured format of STD-E2E; logs carry repository-relative paths only.

### Known answers and negative controls
- KA-767's negative control is completed here: after one tracked sibling file is touched, `check-stack` fails
  (`stack.sibling`). KA-784 lists the workspace plants; the stale stack lock is the seventh plant of the gate and
  is this check's.
- Negative controls registered for the workspace-check gate: each planted condition; in addition a deliberately broken build of the module that skips the dirty comparison must be caught by `verify_dirty_changed_fails`.
- Metamorphic relation: running the check from a different working directory inside the repository gives the same report.
- Determinism lanes: the JSON report is byte-identical twice on one machine and on both platforms for the same tree.

## Considerations

- A gate run waits for a clean tree (the default answer to OPEN-SUITE-3). In practice that means gate runs are scheduled when the sibling an agent depends on is clean, or run against a clean export of the pinned commit; the receipt then records the export's revision with `dirty = false`.
- `sibling-moved: fast-forward` is the normal state between pin moves, because siblings change daily (409 commits touched FrankenSim's multibody crate in thirty days, FACT). It fails the check on purpose: the remedy is the compatibility train (move the pin, write a new receipt, rerun the admission and parity gates, relock), never a rollback.
- A build on a moved sibling is still possible for development; it is the PASS that is refused, not the compile.
- RISK-23 (dirty or off-pin sibling trees make a receipt unrepeatable; severity Medium; owner: Build lead): a drift class other than on-pin at a gate run is the leading indicator the risk register names. Mitigation: the receipt hashes bytes; no gate records a pass on a dirty tree; the compatibility train.
- The remedy for `stale-lock` is a pin move with a new receipt; for a stale sibling lock (`stack.own-lock`) it is an upstream work item in the sibling. A sibling's newer clean head is never rolled back locally.
- `xtask` links `frob-core` (its canonical writer writes the receipt, N33a-04, as it writes the generated files of `check-generated`). A sibling drift that breaks `frob-core`'s build therefore also breaks a rebuild of the tool that would diagnose it; the working rule "run `check-stack` before attributing a build failure" is then served by the last built `xtask` binary. If that proves insufficient in practice, the remedy is an ADR that moves the stack module behind its own small binary, not a second canonical writer.
- Privacy: receipts, reports and logs carry revisions and relative paths, never a user's directory.
- The guard is the only place this rule is implemented; the gate runner, the admission validator and the exit review all call it rather than re-deriving it.
