## Background

Two results may be compared, pooled or served from a cache as results of the same computation only if the same
stack produced them: the same sibling commits, the same toolchain, the same lockfiles. FrankenRobotics records
what a build resolved in a **resolution receipt** (canonical JSON, schema `frob.stack-receipt/1`, named by the
BLAKE3 hash of its bytes; bead N33a-04). The design then requires two things of every result:

1. *A result in the Chronicle ledger carries the receipt hash of the binary that produced it*, which is what lets
   a later reader decide whether two results may be compared as results of the same stack. The format rules add
   that an artifact that leaves the tool carries the stack receipt of the binary that wrote it.
2. *The airlock does not cache across pins*: every memoized referee result carries the **stack-lock digest** in
   its key. (The airlock is the crate `frob-fsim`, the only crate that names FrankenSim's volatile types; the
   referee is the most trusted simulation tier, which runs FrankenSim's own dynamics through it. The stack-lock
   digest is BLAKE3 over the canonical bytes of `franken-stack.lock`; bead N33a-03.)

Without the first, a comparison could silently straddle a pin move, and a ratio measured across a pin move is not
one measurement. Without the second, a FrankenSim change would be invisible to every cache in front of it, and a
stale referee answer would adjudicate a new one.

The refusal that makes the rule observable is `FROB-REF-890` (`stack-mismatch`): evidence recorded under another
stack receipt is offered as same-stack evidence without revalidation. Its registry entry is written by another
unit; the predicate that raises it lives here because every consumer must use the same one.

Rejected alternatives. (a) Keying caches on the FrankenSim commit alone: misses a toolchain train, a changed
feature list and a changed build-identity salt, each of which can change bits. (b) Keying on the receipt hash
alone: the receipt also changes when an unrelated sibling moves, which would flush referee caches for no reason;
the lock digest is the narrower identity for "the pins I was built against", and the receipt hash is the wider
identity for "what was resolved". Both are carried; each is used where it is the right one. (c) Comparing
receipts field by field to decide "close enough": no tolerance on identity; crossing receipts is done by
revalidation, which re-runs what the difference could have changed.

## Technical approach

**Types (DESIGN, `frob-core::stack`).**

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash)] pub struct StackReceiptHash([u8; 32]);
#[derive(Clone, Copy, PartialEq, Eq, Hash)] pub struct StackLockDigest([u8; 32]);
pub struct StackIdentity { pub receipt: StackReceiptHash, pub lock: StackLockDigest, pub dev: bool }

pub const BUILT_UNDER: StackIdentity = /* from the build script */;
pub fn same_stack(a: &StackIdentity, b: &StackIdentity) -> bool { !a.dev && !b.dev && a.receipt == b.receipt }
pub fn require_same_stack(a: &StackIdentity, b: &StackIdentity, what: &str) -> Result<(), Refusal>; // FROB-REF-890
pub trait StackKeyed { fn stack_key_component(&self) -> StackLockDigest; }  // implemented by airlock adapters
```

Text form: 64 lower-case hex digits with the prefixes `sr:` and `sl:`. Neither type has a constructor from an
arbitrary string outside the parser, so a receipt hash cannot be passed where a lock digest is expected.

**Build-time embedding.** `xtask check-stack --write-receipt` maintains two one-line files, `receipts/HEAD` (the
newest receipt hash) and `receipts/LOCK_DIGEST` (the digest of the lock that receipt was written for).
`frob-core/build.rs` reads both, emits them as compile-time environment values and registers
`rerun-if-changed` on the two files and on `franken-stack.lock`. Rules:
1. If either file is missing, the build script fails closed with a message naming `cargo run -p xtask --
   check-stack --write-receipt`. There is no "unknown" identity.
2. If the environment variable `FROB_STACK_DEV=1` is set, the identity is marked `dev: true`. This is the only
   way to build on a tree that `check-stack` would fail; a `dev` identity never compares as same-stack, and the
   gate runner refuses to record a PASS from it.
3. The build script does no hashing and reads no sibling: it copies two strings. The hashing lives in `xtask`.

**Where the identity is stamped.**
- *Envelope.* Every `frob --json` envelope carries `evidence.stack_receipt` (the `sr:` form) and, when `dev`,
  `evidence.stack_dev: true`.
- *Ledger.* Rows of `run`, `job` and `episode` carry `stack_receipt`; a chunk inherits its run's.
- *Exported artifacts.* A `.frun` manifest, a certificate bundle and every other exported format carry the
  receipt hash beside the schema name and the three no-authorization flags (the provenance-on-export rule of the
  format registry).
- *Memo keys.* Any key for a result computed through the airlock includes `stack_key_component()`. The key
  derivation is generated from declared inputs, and the lock digest is a declared input of every node kind whose
  executor names an airlock trait, so it cannot be forgotten for one node kind.

**The same-stack rule.** A consumer that combines or substitutes evidence calls `require_same_stack`:
comparisons and paired statistics (both arms), pooling into a calibration or fidelity ledger row, serving a memo
hit, promoting a result, and citing an earlier result as support. On a mismatch the refusal is `FROB-REF-890`
with `observed` and `required` receipt hashes, `retry: after-change`, and ranked repairs: (1) revalidate the
older evidence under the current stack (`result.revalidate`); (2) re-run it; (3) present the two as separate
results, each labelled with its stack. Exit code 3 at the command line (the `8xx` evidence-and-protocol family).

**What is not same-stack by construction.** A result produced by a worker process built under another receipt,
and a result that crossed the multiphysics bridge, are never merged into a same-stack or throughput claim
(INV-SUITE-05). The first is caught by this predicate because the worker reports its own receipt; the second is
an evidence-tier label and is outside this bead.

Determinism: all functions are pure. The identity is a constant of the binary.

## Acceptance criteria

- [ ] `frob doctor --json` prints the receipt hash and lock digest the binary was built under, and they equal `receipts/HEAD` and `receipts/LOCK_DIGEST`.
- [ ] Building `frob-core` with `receipts/HEAD` absent fails with the documented message (fail closed).
- [ ] An envelope from any verb contains `evidence.stack_receipt`; a ledger `run` row and an exported `.frun` manifest contain the same value.
- [ ] `require_same_stack` returns `FROB-REF-890` for two identities with different receipts, and for any identity with `dev: true`.
- [ ] A memoized referee result stored under lock digest A is not served to a request under lock digest B (a miss, not a hit).
- [ ] A compile-fail test shows that a `StackReceiptHash` cannot be passed as a `StackLockDigest`.
- [ ] `CONTRACT.md` of `frob-core` documents the two identities, the dev flag and the same-stack rule.

## Test plan

### Unit tests (`cargo test -p frob-core stack`, `cargo test -p frob-fsim stack_key`)
- `same_stack_reflexive_on_release_identity`: equal receipts, `dev: false` → true.
- `same_stack_false_on_different_receipt`: one differing hex digit → false.
- `same_stack_false_when_dev`: equal receipts, one `dev: true` → false.
- `require_same_stack_refuses_890`: the refusal carries code 890, both hashes and three repairs in the stated order.
- `text_form_roundtrip`: `sr:` and `sl:` strings parse and print; a 63-digit string is refused; an `sl:` string is refused by the receipt parser.
- `type_confusion_compile_fail` (trybuild): passing one type for the other does not compile.
- `stack_key_component_changes_key`: a referee memo key built with digest A differs from the key with digest B, all else equal; perturbing any other declared input also changes it (the live-dependency test for this input).
- `build_script_fails_closed` (integration, in a scratch copy): without `receipts/HEAD` the build fails; with `FROB_STACK_DEV=1` it succeeds and `BUILT_UNDER.dev` is true.

### End-to-end script and logging
`scripts/e2e/stack_receipt.sh` (bead N33a-27), step `identity_on_results`: runs `frob doctor --json` and one
cheap verb, asserts that both envelopes carry the receipt hash printed by `xtask check-stack --json`, then
replays a stored envelope fixture recorded under a different receipt into a comparison and asserts exit code 3
with `refusal.code = "FROB-REF-890"`. Logged: both hashes, the refusal object, and the first differing value.

### Known answers and negative controls
- Negative control (planted defect): a build of the memo-key derivation that omits the lock digest must be caught by `stack_key_component_changes_key`; registered as a control of the memo-graph gate.
- Negative control: an envelope with the `stack_receipt` field stripped must be refused by the ledger writer (a result without a stack identity is not stored).
- CX seed: "a pin is what was built" is false on the day of reading (FrankenSim's own lock says asupersync 0.5.0 while its lockfile resolves 0.6.2), which is why the identity is the receipt and not the pin.
- Determinism lanes: the constants are identical in debug and release builds of the same tree.

## Considerations

- The receipt hash changes at every admission and pin move, so long campaigns should not straddle one. The ten-fold tournament freezes every pin and the toolchain for its whole length for this reason; a pin move or a toolchain train voids the runs it spans.
- A `dev` identity is deliberately useless as evidence. It exists so that work continues while a sibling is mid-change; it must never appear in a gate record.
- The lock digest does not see a dirty sibling tree (the lock names commits). The receipt does. Referee memo hits are therefore additionally refused when `BUILT_UNDER.dev` is set.
- Privacy: both identities are hashes of repository metadata and contain no scene data; they may appear in logs.
- If a future need arises to compare across receipts that differ only in an unrelated sibling, the answer is a declared projection of the receipt with its own identifier and an ADR, not a relaxation of this predicate.
