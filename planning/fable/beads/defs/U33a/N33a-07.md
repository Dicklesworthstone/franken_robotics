## Background

A foundation (a sibling project FrankenRobotics builds on) is not used above the airlock crate until its
**admission gate** has a record. The admission gates are the `INT-…` identifiers: INT-TOOLCHAIN-01 for the one
toolchain T, INT-FSIM-01 to -18 for FrankenSim, INT-ASUP-01 and -02 for asupersync, INT-FSQL-01 and -02 for
FrankenSQLite, INT-FT-01 and -02 for FrankenTorch's Metal gateway, INT-CUDA-01 for the `cudarc` binding,
INT-FSYM-01 and -02 for FrankenSymPy, INT-FLN-01 and -02 for franken_lean, INT-FMCP-01 for fastmcp_rust,
INT-FNP-01 and -02 for franken_numpy, and the five off-critical-path sibling gates INT-FTUI-01, INT-F3D-01,
INT-FDGR-01, INT-FJAX-01 and INT-FTX-01. (INT-FSIM-12 is reserved and unused.)

Two facts from sibling projects fix the form of a record:

- FrankenMining found admission records for crates that were not in its build (FACT). The rule it adopted, and
  that binds here: **an admission record is valid only if it cites a commit of this repository whose tracked
  `Cargo.lock` contains the foundation, with the command, its output and the receipt hash.**
- Records live in `DEPENDENCY_ADMISSION.md`, a convention taken from FrankenThreeD (FACT:
  `franken_threed/DEPENDENCY_ADMISSION.md`).

Two rules of the gate register complete it: a gate passes only with a recorded measurement against its
threshold, and **an admission is never inherited**: a crate first used at M4 is admitted at M4, by its own
record, at the pin of that day. Thresholds in the gate table are TARGETs until a gate records measured values.
A failing value is a record too: the M0 milestone artifact is "every record, passing or failing".

This bead builds the record format and the tooling around it. The individual gates are run by their own beads,
which call the writer defined here.

## Scope

In: the record schema `frob.admission/1`; the writer (in `frob-conformance`); the validator (a library function
that `xtask check-stack` calls); the generator that renders `DEPENDENCY_ADMISSION.md`; the never-inherited check;
the status function behind `frob doctor`.
Out: running any gate; the toolchain matrix content (BD-031); `registries/gates.toml` semantics (the Gauntlet
unit); the `doctor` verb's envelope (BD-022).

## Technical approach

**Record (DESIGN, canonical JSON, one file per record under `receipts/admissions/<gate>/<hash>.json`, named by
the BLAKE3 of its bytes; append-only).**

```json
{ "schema": "frob.admission/1",
  "gate": "INT-FSIM-01", "foundation": "FD-FSIM",
  "covers": { "crates": ["fs-ga", "fs-mbd", "fs-contact", "fs-time", "fs-query"], "groups": [], "tool": null },
  "repo_rev": "<40 hex>", "workspace": "core",
  "stack_receipt": "sr:<64 hex>", "sibling_rev": "<40 hex>", "toolchain": "<channel>",
  "command": ["cargo", "check", "--all-targets", "-p", "frob-fsim"],
  "exit": 0, "output_hash": "<BLAKE3>", "output_excerpt": "<at most 4 KiB, tail of the output>",
  "measured": [ {"name": "cold_check_s", "value": 0, "unit": "s", "threshold": 3600, "relation": "<="} ],
  "controls": [ {"id": "NC-…", "caught": true} ],
  "facts_reread": [ {"fact": "fs-contact MAX_CONTACTS", "path": "crates/fs-contact/src/sustained/solve.rs:26", "value": "21"} ],
  "status": "pass | fail | not-run | killed",
  "host": {"class": "trj | m5-ultra", "fingerprint": "<hash or null>"},
  "recorded": {"date": "<ISO>", "session": "<id>", "implemented_by": "<id>"} }
```

The full command output is stored content-addressed under `receipts/outputs/<output_hash>.txt` (the excerpt is
for people; the hash is the citation). `facts_reread` holds the sibling facts the gate depends on, read at the
pin by the gate's own test and never copied from design text (the probes are bead N33a-09).

**Validity rules (the validator, `stack::admission::validate`; each a named finding).**
1. `lockfile-lacks-foundation`: for each crate in `covers.crates`, `git show <repo_rev>:<workspace lockfile>`
   contains a `[[package]]` with that name. A record for a crate that was not in the build is invalid.
2. `receipt-missing`: `stack_receipt` names a file under `receipts/` whose bytes hash to it, and that receipt's
   entry for the foundation has `rev = sibling_rev`.
3. `output-missing`: `receipts/outputs/<output_hash>.txt` exists and hashes to its name.
4. `pass-on-dirty`: `status = "pass"` requires `may_record_pass(receipt)` of N33a-05 (no dirty sibling, clean
   repository, no asupersync duplicate).
5. `pass-without-control`: `status = "pass"` requires at least one control with `caught: true`, and no control
   with `caught: false`.
6. `self-certified`: `status = "pass"` requires `recorded.session ≠ recorded.implemented_by`.
7. `tool-unpinned`: for Subprocess foundations (`covers.tool`), the record names the tool's repository revision
   and the BLAKE3 of the binary that ran.
8. `measured-missing`: every threshold the gate's row states has a `measured` entry with a value and a unit; a
   target is never written in place of a measurement.

**Never inherited (the check, run over the current tree).**
1. Enumerate what is in use: every foundation crate in each tracked `Cargo.lock` (matched to its `FD-` row by
   the ledger of N33a-02), and every airlock feature group of `frob-fsim` enabled by any manifest.
2. For each used crate or group, find the newest record whose `covers` names it. None → `unadmitted-use`.
3. That record's `sibling_rev` must equal the pin in the current lock. Otherwise → `admission-stale`: the pin
   moved, and the compatibility train requires the admission gate to be rerun at the new pin.
4. A record never covers what it does not list: FrankenTorch's Metal gateway record (INT-FT-01) does not admit
   `ft-nn`; the `referee` group record does not admit the `optimize` group.
`unadmitted-use` and `admission-stale` fail `check-stack` for crates that a workspace crate above the airlock
depends on; for crates used only by the gate's own test crate they are informational (the test is how the record
gets made).

**`DEPENDENCY_ADMISSION.md` is generated.** A generator in `frob-conformance` renders it from the record files:
a status table (gate, foundation, status, measured values against thresholds, receipt hash, date), then one
section per record with the command, the excerpt and the re-read facts, then the toolchain matrix and the
choice of T (data from BD-031). It is covered by the generated-files check, so it is never edited by hand. A
gate with no record prints as `not run`, never as passed.

**Status function.** `admission::status() -> Vec<FoundationStatus>` (foundation, uses, pin, newest record per
gate, drift class from the newest receipt). `frob doctor` prints it with the stack receipt hash; this is the
first bullet of the M0 milestone artifact.

**Writer.** `frob_conformance::admission::record(gate, covers, command, measured, controls, facts) ->
RecordHash` runs the command through the build-offload shim under a timeout, captures output, calls
`check-stack` to obtain the receipt, applies rules 4 to 6 to decide whether `pass` may be written, and writes
the files atomically. It refuses to overwrite.

## Acceptance criteria

- [ ] A record written for a real M0 gate validates; the generated `DEPENDENCY_ADMISSION.md` lists it with its measured values.
- [ ] Each planted invalid record is refused with its finding: a crate absent from the cited commit's lockfile; a missing receipt; a missing output file; `pass` on a receipt with a dirty sibling; `pass` with no caught control; `pass` where recorder and implementer are the same session; a threshold with no measured value.
- [ ] The never-inherited check reports `unadmitted-use` when a manifest enables the `optimize` group with only a `referee` record present, and `admission-stale` after the FD-FSIM pin is changed without a new record.
- [ ] A failing gate run produces a record with `status = "fail"` and its measured values, and the generated file shows it (a failing value is a record).
- [ ] `frob doctor --json` lists every foundation of the ledger with its newest record or `not run`, and the stack receipt.
- [ ] Editing `DEPENDENCY_ADMISSION.md` by hand fails the generated-files check.

## Test plan

### Unit tests (`cargo test -p xtask stack::admission`, `cargo test -p frob-conformance admission`; synthetic repositories)
- `record_roundtrip_canonical`: write, read, re-serialize → identical bytes; file name equals hash.
- `rule1_lockfile_lacks_foundation`: record covers `fs-mbd`; the cited commit's lockfile has no such package → finding.
- `rule2_receipt_rev_mismatch`: receipt says FrankenSim at `aaaa…`, record says `bbbb…` → finding.
- `rule4_pass_on_dirty_refused`, `rule5_pass_without_control_refused`, `rule6_self_certified_refused`, `rule8_target_as_measurement_refused` (a `measured` entry whose value field is absent).
- `never_inherited_group`: manifests enable `stats`; records cover `referee`, `geometry`, `ledger` → `unadmitted-use: stats`.
- `never_inherited_pin_move`: lock pin changed → `admission-stale` for every FD-FSIM record.
- `never_inherited_does_not_widen`: an INT-FT-01 record with `covers.crates = ["ft-kernel-metal"]` does not satisfy a use of `ft-nn`.
- `generator_prints_not_run`: a gate with no record renders as `not run`.
- `generator_is_deterministic`: two runs produce identical bytes.

### End-to-end script and logging
`scripts/e2e/admission_m0.sh` (bead N33a-28) writes real records for the M0 gates on the real tree, regenerates
`DEPENDENCY_ADMISSION.md`, runs `frob doctor --json`, and plants each invalid record in a scratch copy. Log lines
carry the gate, the record hash, the receipt hash, each measured value with unit and threshold, the control
identifiers with `caught`, and the validator findings.

### Known answers and negative controls
- Negative controls: the seven invalid records and the two never-inherited plants above, each registered as a control of the status-accounting gate (a planted self-certification and a planted PASS with an uncaught control must each be refused).
- CX seed: "an admission record for a crate is evidence that the crate is used" is false; FrankenMining's records for crates not in its build are the case, and rule 1 is the response.
- Determinism lanes: record bytes and the generated file are identical on both platforms for the same inputs.

## Considerations

- Records are append-only and small; outputs can be large (a cold `cargo check` log), so they are stored once by hash. Neither contains private-scene data.
- A gate may pass before its milestone; it may not move later without an ADR. The record carries the date, not a milestone.
- The validator trusts `git show` for old lockfiles; a shallow clone that lacks the cited commit yields the finding `commit-unreachable`, not a pass.
- "Admitted" is per use and per pin. This makes pin moves costly on purpose: the compatibility train (move the pin, write a new receipt, rerun the admission and parity gates, relock) is the only way forward.
- The exit review of each milestone (for M0, bead BD-044) is a query over these records plus `registries/gates.toml`.
