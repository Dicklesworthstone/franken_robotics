## Background

FrankenSim's linear-algebra crate `fs-la` has a build script that refuses to build without a declared build
identity. FACT (read 2026-11-21 at FrankenSim head `483d09c682f2`): `frankensim/crates/fs-la/build.rs` panics
unless the environment variable `FRANKENSIM_DEPGRAPH_RECEIPT` or `FRANKENSIM_DEPGRAPH_SALT` is set. Inside
FrankenSim the salt comes from its `.cargo/config.toml`, which a workspace outside the tree does not read. `fs-la`
is in the compile closure of `fs-ad` (forward-mode duals), `fs-mbd` (multibody) and `fs-contact`, so every
FrankenRobotics build that consumes FrankenSim by path meets this script. It is hazard 5 of the decision to
consume FrankenSim by path.

The behaviour is the one a careful sibling should have: it fails closed outside a declared equivalence class
instead of silently producing a binary whose numerical build cannot be identified. FrankenRobotics therefore
does not work around it. DESIGN: the core workspace sets its own salt, naming its own development equivalence
class, in its root `.cargo/config.toml`; evidence-bearing performance builds export a receipt instead; and no
build script or wrapper in this repository ever supplies a default when both are missing.

The upstream side is work item FD-FSIM-14 (priority P2), done in FrankenSim's repository under its rules: a
documented build-identity setting for path consumers outside the tree. Interim posture: the local salt and the
exported receipt described here. Switch-over rule: remove the local setting if FrankenSim publishes a default
class.

Rejected alternatives: (a) a wrapper script that exports a value if none is set: that converts a fail-closed
check into a fail-open one. (b) Patching `fs-la`'s build script through a Cargo `[patch]`: a local patch of a
sibling diverges from its head and does not survive a pin move; every sibling is changed in its own repository.
(c) Setting the variable in each developer's shell profile: not reproducible, and invisible to the receipt.

## Scope

In: the `[env]` entry of the root `.cargo/config.toml` and of every other workspace of this repository that
resolves FrankenSim (`apps/`, `worker/`, and any annex that does); the two build-identity modes and how a build
selects one; recording the mode in the stack receipt; the label that keeps a development-salt binary out of
performance evidence; the fail-closed tests.
Out: the measurement that the setting is needed at all (BD-006's necessity test); FD-FSIM-14 itself (an upstream
bead opened by BD-037); the performance harness (the performance unit).

## Technical approach

**Mode 1, development (the default).** Root `.cargo/config.toml`:

```toml
[env]
FRANKENSIM_DEPGRAPH_SALT = "franken-robotics-dev-v1"
```

The value names an equivalence class owned by this project. It is bumped (`-v2`, …) by an ADR whenever something
that could change `fs-la`'s numerical build changes without a pin move (a compiler flag set at the workspace
root, a target-feature change). The same string is the `build_env` entry of the FD-FSIM row in
`franken-stack.lock`, and `check-stack` fails if the two differ (identifier `stack.env`, kind `build-env-missing`,
N33a-05). This bead adds one kind to that identifier: a salt equal to the salt FrankenSim sets in its own
`.cargo/config.toml` at the pinned commit (read from the sibling checkout, read-only) claims another graph's
equivalence class and fails as `stack.env`, kind `foreign-build-class` (the rejection the upstream item
FD-FSIM-14 tests, "build identity claims another graph's class"); so does an empty `build_env` on the FD-FSIM
row.

**Mode 2, evidence-bearing.** A build whose timings or bits will enter a Performance or Parity claim sets
`FRANKENSIM_DEPGRAPH_RECEIPT` in the environment of the build command and does not rely on the salt. The exact
form of value that `fs-la/build.rs` accepts for the receipt variable is a sibling fact: it is read from the
build script at the pinned commit by the fact probe of N33a-09 and recorded in the admission record of
INT-FSIM-01 before the first such build. The procedure is fixed here:
1. `xtask check-stack` must exit 0 with `may_record_pass: true` (clean siblings, on the newest receipt).
2. The build command is run with the receipt variable set in the form the pinned build script requires.
   Removing the salt from the shell (`env -u`) does not remove it from the build: Cargo's `[env]` table supplies
   a variable that is absent from the process environment, and no command-line flag unsets an `[env]` entry, so
   with the mode-1 entry present both variables reach `fs-la`'s build script. Which one `fs-la` honours when both
   are set is therefore a sibling fact, read at the pin by the probe of N33a-09 beside the receipt form and
   recorded in the INT-FSIM-01 admission record. The build-script helper below holds that answer as a constant,
   `RECEIPT_WINS_WHEN_BOTH: Option<bool>`, `None` until the record has it and changed only by a commit that
   cites the record. If the receipt wins, mode 2 is in force with the salt still present; if the salt wins, or
   the answer is `None`, a build with both variables set is refused and no `depgraph-receipt` build is made
   until an ADR adopts a mechanism that withholds the `[env]` entry from evidence builds (for example moving it
   to a configuration file that evidence builds do not load), with its own test added here.
3. The stack receipt written for that build records `build_env` with the receipt variable and its value, and
   the binary's embedded identity (bead N33a-06) therefore differs from a development build's.
4. The performance harness prints `build_identity: depgraph-receipt` in its disclosure block.

**The label.** Every binary knows its mode through a compile-time constant
`frob_core::stack::BUILD_IDENTITY_MODE` with values `dev-salt` and `depgraph-receipt`, set by the same build
script that embeds the stack receipt hash (`frob-core/build.rs`, bead N33a-06), through a helper that reads both
variables, applies the precedence rule of step 2, and declares `rerun-if-env-changed` on each, so that a change
of mode rebuilds the constant instead of leaving a stale label. A result whose producing binary is `dev-salt`
may be recorded and studied, and may not be cited in a Performance or Parity gate record:
`frob_core::stack::build_identity::may_cite(gate_class) -> Result<(), &'static str>` returns the reason
`dev-build-identity` for a Performance or Parity gate under `dev-salt`. The one writer of gate rows,
`record_gate` (N38b-19), calls it beside the dirty-tree guard of N33a-05 and refuses `pass` when it errs, reading
the producing binary's mode from the harness receipt (`frob.gauntlet.receipt/1`, N38a-02); that call and that
field are those beads' work, and this bead supplies the constant and the function they use. Fail-closed default until the receipt form has been read at the pin: all builds are
`dev-salt`, and no Performance or Parity PASS can be recorded.

**No default, anywhere.** A source lint (a unit test of `xtask` that greps this repository's build scripts,
`.cargo/config.toml` files and shell scripts) refuses any construct that would supply the variable
conditionally: `${FRANKENSIM_DEPGRAPH_SALT:-…}`, `unwrap_or` on either variable, or `option_env!` with a
fallback. The only sanctioned sources are the `[env]` table (mode 1) and an explicit export on the command line
of an evidence-bearing build (mode 2).

**Every workspace that resolves FrankenSim carries the entry.** Cargo reads `.cargo/config.toml` from the
working directory upward, so the root file covers workspaces inside the repository tree; the test below proves
it for `apps/` and `worker/` instead of assuming it.

## Acceptance criteria

- [ ] The root `.cargo/config.toml` holds the salt; the FD-FSIM row of `franken-stack.lock` holds the same string; `check-stack` fails when they differ.
- [ ] A scratch copy whose config and lock both carry FrankenSim's own in-tree salt fails `check-stack` with `stack.env`, kind `foreign-build-class`; an empty `build_env` on the FD-FSIM row fails with `build-env-missing`.
- [ ] With the `[env]` entry removed and neither variable exported, a build of any crate that depends on `fs-la` fails with FrankenSim's own message (fail closed); no file in this repository makes it succeed.
- [ ] A build from `apps/` and from `worker/` sees the salt (the build succeeds with no export).
- [ ] The no-default lint passes on the repository and fails on a planted `${FRANKENSIM_DEPGRAPH_SALT:-x}` in a script.
- [ ] `BUILD_IDENTITY_MODE` is `dev-salt` in a default build; `may_cite` under that mode refuses a Performance and a Parity gate with `dev-build-identity` and accepts an admission gate (the recorder's refusal through it is N38b-19's test).
- [ ] The form of the receipt variable, and which of the two variables `fs-la`'s build script honours when both are set, are recorded as re-read facts in the INT-FSIM-01 admission record before any `depgraph-receipt` build is made; until then a build with both set is refused.

## Test plan

### Unit tests (`cargo test -p xtask build_identity`, `cargo test -p frob-core stack::build_identity`)
- `salt_matches_lock`: the string in `.cargo/config.toml` equals the FD-FSIM `build_env` entry.
- `foreign_salt_rejected`: a synthetic sibling whose `.cargo/config.toml` sets salt `s`; config and lock both set to `s` → `stack.env`, `foreign-build-class`; set to `franken-robotics-dev-v1` → clean; FD-FSIM `build_env = {}` → `build-env-missing`.
- `no_default_lint_clean`: zero findings on the repository.
- `no_default_lint_catches_shell_default`, `no_default_lint_catches_unwrap_or`, `no_default_lint_catches_option_env_fallback`: three planted files, one finding each.
- `mode_constant_is_dev_salt_by_default`.
- `performance_pass_refused_on_dev_identity`: under `dev-salt`, `may_cite` returns `dev-build-identity` for a Performance gate and for a Parity gate, and `Ok` for an admission gate.
- `modes_are_exclusive`: the build-script helper on synthetic environments: salt only → `dev-salt`; receipt only → `depgraph-receipt`; neither → refused (fail closed); both with `RECEIPT_WINS_WHEN_BOTH = None` or `Some(false)` → refused as ambiguous; both with `Some(true)` → `depgraph-receipt`.
- `mode_change_rebuilds` (integration, scratch copy, one target directory): a default build, then one with the receipt variable exported (with `RECEIPT_WINS_WHEN_BOTH` set to `Some(true)` in the scratch copy), then a default build again; `BUILD_IDENTITY_MODE` reads `dev-salt`, `depgraph-receipt`, `dev-salt`.
- `env_table_survives_env_u` (integration, scratch copy): a probe build script that prints whether `FRANKENSIM_DEPGRAPH_SALT` is visible, built under `env -u FRANKENSIM_DEPGRAPH_SALT`, still sees the `[env]` value; this pins the Cargo behaviour step 2 relies on, so a Cargo change that alters it is noticed.

### End-to-end script and logging
`scripts/e2e/admission_m0.sh` (bead N33a-28), step `build_identity`: (1) builds `frob-fsim` normally and logs
the mode; (2) in a scratch copy with the `[env]` entry removed, runs the same build and asserts a non-zero exit
whose output contains the build script's panic text; (3) builds from `apps/` and asserts success. Each line logs
the command, the exit code, wall time, the mode and, for step 2, the matched text of the failure.

### Known answers and negative controls
- Negative control for INT-FSIM-01 (shared with BD-006): the unset variable must fail the build.
- Negative control: a planted wrapper that exports a default must be caught by the lint.
- Determinism lanes: two development builds of the same tree embed the same mode and the same stack identity.

## Considerations

- The salt is not a secret and not a cache-busting trick; it is the name of an equivalence class. Changing it changes the stack-lock digest and therefore every memoized referee key, which is intended.
- If FrankenSim publishes a default class for outside consumers (FD-FSIM-14), the switch-over is: delete the `[env]` entry, rerun INT-FSIM-01, write a new receipt. Until then the interim posture stands, and no milestone waits on the upstream change.
- When the worker-process fallback keeps `worker/` at an older FrankenSim pin, that workspace's build identity is recorded in its own lockfile entry of the receipt; the two may differ, and a result from the worker carries the worker's identity.
- Open point, recorded so that it is not rediscovered: the design text says performance builds "export a receipt" without giving the receipt's form. The fail-closed reading adopted here is that no performance evidence is recorded until the form is read from the pinned build script.
