## Background

The batched step of FrankenRobotics solves, per world, small dense linear systems: a mass matrix of 18 to
about 60 degrees of freedom and a contact Hessian of similar size, factored by a batched dense Cholesky kernel
in single precision with scaling and refinement. Those kernels are this project's own code. To test them the
Gauntlet wants an independent double-precision answer for the same small matrices.

**franken_numpy** (foundation row `FD-FNP`) supplies one: its crate `fnp-linalg` has batch routines over
stacks of matrices in `f64`. The ledger gives the foundation two uses with two postures: array files at the
interchange boundary through `fnp-io` (Consume, admitted at M0 by INT-FNP-01 and INT-FNP-02) and `fnp-linalg`
as an `f64` oracle for small-matrix kernels (Oracle, first used at M2, when the kernels exist). **An admission
is never inherited**: the M0 record covers `fnp-io` and the stride converter, and says nothing about the
linear-algebra crate. This bead is the M2 record.

FACT about the library (read 2026-11-21; re-read at the pin): it is an `f64` array library on heap vectors
with no single-precision storage and no fixed-size matrix types, and GPU arrays and automatic differentiation
are out of its scope. That is exactly why it is an oracle and not a hot-path dependency. Its stride convention
(signed byte strides) differs from FrankenTorch's, so every array handed to it goes through the typed
converter of bead BD-036.

Fallback, named in the ledger: drop the oracle. The kernels are then checked against FrankenSim's `fs-la`
alone and against residual tests; no milestone waits on franken_numpy.

## Scope

In: the dev-dependency edge on `fnp-linalg`; the oracle adapter (stack of small matrices in, factor or solution
out, in `f64`); convention record; known answers and controls; the M2 admission record.
Out: the kernels under test and their error bounds (the kernel and precision beads); `fs-la` as an oracle
(another unit); any production use of franken_numpy beyond array files.

## Technical approach

**Edge.** `frob-conformance` gains a dev-dependency on `fnp-linalg` at the pin of `franken-stack.lock`,
default features off; `check-deps` enforces dev-only and the crate confinement of the ledger row. One
asupersync package must still hold (franken_numpy's requirement is optional and exact, `=0.6.2`).

**Adapter (`frob_conformance::oracle::small_dense`).**
`cholesky_batch(a: &Stack<f64>) -> Result<Stack<f64>, OracleRefusal>` (lower factors),
`solve_spd_batch(a, b) -> Result<Stack<f64>, OracleRefusal>`, and `eigvalsh_batch(a)` for condition numbers.
A `Stack` is n matrices of size m×m in row-major order with an explicit layout built through
`frob_core::view::ViewLayout`; no bare stride tuple is passed. Single-precision kernel inputs are widened to
`f64` exactly before the oracle is called.

**Convention record (read at the pin, stored with the fixtures).** Which triangle the factor routine returns
and whether the other triangle is zeroed; how a matrix that is not positive definite is reported (an error per
matrix, a flag, or a NaN fill); the storage order of a stack; whether the routine pivots. The adapter converts
all of these to this project's convention (lower factor, the upper triangle exactly zero, a typed refusal per
non-positive-definite matrix with its index in the stack).

**Known answers (through the adapter).**
1. Exact integer factorization: A = [[4, 12, −16], [12, 37, −43], [−16, −43, 98]] has the lower Cholesky
   factor L = [[2, 0, 0], [6, 1, 0], [−8, 5, 3]]; every intermediate is an integer, so the `f64` result is
   exact. With b = A·(1, 1, 1) = (0, 6, 39) the solve returns (1, 1, 1) to 10⁻¹² relative (the matrix is not
   well conditioned, so the solve is tolerance-checked while the factor is exact).
2. Identity stack: 1,000 copies of the 6×6 identity factor to the identity exactly.
3. Diagonal scaling: diag(1, 4, 9, 16) factors to diag(1, 2, 3, 4) exactly.
4. Reconstruction property: for 10³ seeded random symmetric positive definite matrices of size 18 and 35
   (built as M·Mᵀ + m·I), ‖L·Lᵀ − A‖_max ≤ 10⁻¹² · ‖A‖_max.
5. Not positive definite: [[1, 2], [2, 1]] (eigenvalues 3 and −1) is refused with its stack index.

**How the oracle is used.** A kernel test computes its single-precision result on `batch-cpu`, widens it,
and compares with the oracle under the kernel's own stated bound (a multiple of κ·u, with κ the condition
number from `eigvalsh_batch` and u the single-precision unit roundoff, 2⁻²⁴). Agreement is recorded with claim
kind `parity`. The oracle never produces a fixture that is checked in as truth for a later run of itself.

**Admission record.** `covers.crates = ["fnp-linalg"]` (and whatever franken_numpy packages it pulls), gate
field INT-FNP-01 with `covers` distinguishing this use, the stack receipt hash, the convention record's
digest, the measured residuals, and the caught controls.

Determinism: the oracle's results are recorded per platform; the exact cases are bit-identical everywhere.
Evidence: `Tested`, labelled `development-oracle` where it enters a report.

## Acceptance criteria

- [ ] The five known answers pass through the adapter at the pin; cases 1 (factor), 2 and 3 are exact.
- [ ] The convention record exists and the adapter's output is a lower factor with an exactly zero upper triangle for every case.
- [ ] A non-positive-definite matrix inside a stack of 100 is refused with its index, and the other 99 results are still returned or the whole call is refused, as the record states; it is never returned as a silent NaN.
- [ ] The negative control is caught: a kernel result with one sign flipped in L fails the parity comparison.
- [ ] Arrays reach `fnp-linalg` only through `ViewLayout`; a planted call with a bare stride tuple does not compile.
- [ ] An M2 admission record for `fnp-linalg` exists and validates; `check-deps` refuses a normal dependency on it.
- [ ] With the oracle absent the dependent parity tests report `not run: oracle absent`.

## Test plan

### Unit tests (`cargo test -p frob-conformance oracle::small_dense`)
- `chol_exact_integer_3x3`: L equals [[2, 0, 0], [6, 1, 0], [−8, 5, 3]] bit for bit.
- `solve_ones_3x3`: (1, 1, 1) to 10⁻¹² relative.
- `chol_identity_stack_1000`, `chol_diagonal_squares`.
- `chol_reconstruction_random_18_and_35`: the residual bound on 10³ seeded matrices per size.
- `not_spd_refused_with_index`: index 57 of a 100-stack.
- `stack_order_roundtrip`: a stack of 100 matrices whose k-th (k = 1, …, 100; k = 0 would not be positive definite) is k·I₄ returns the factors √k·I₄ in the same order, each diagonal entry equal to the correctly rounded `f64` square root of k.
- `fnp_linalg_edge_dev_only`: a planted normal dependency on `fnp-linalg` from `frob-conformance`, and any dependency on it from another crate, are refused by `check-deps`; with the oracle enabled the resolved graph holds one asupersync package.
- `widening_is_exact`: an `f32` matrix widened and narrowed returns the same bits.
- `sign_flip_parity_control`: detected.
- `oracle_absent_reports_not_run`.

### End-to-end script and logging
No script of its own; the oracle is exercised by the kernel parity scripts of the kernel beads. Its admission
is the step `fnp_linalg_admission` of `scripts/e2e/airlock_groups.sh` (bead N33a-34), which logs per known
answer the measured residual, its threshold, the convention digest and the control outcome.

### Known answers and negative controls
- The integer factorization above (L·Lᵀ reproduces A: row 2 gives 36 + 1 = 37 and −48 + 5 = −43; row 3 gives 64 + 25 + 9 = 98).
- Negative controls: the sign flip; the non-positive-definite matrix; a transposed stack order (planted in the adapter) must fail `stack_order_roundtrip`.
- Counterexample protected: strides can be copied verbatim between array libraries (false; element 12 instead of element 3 on the 2×2 case).
- Determinism lanes: exact cases identical on both platforms; tolerance cases recorded per platform.

## Considerations

- Two oracles for the same routines (`fnp-linalg` and FrankenSim's `fs-la`) are deliberate: when they disagree, neither is trusted and the closed-form cases decide.
- The oracle is `f64` on the host and is slow by design; it is never called inside a batched step or a performance measurement.
- If franken_numpy moves its pin, the admission is rerun; the M0 record does not cover it.
