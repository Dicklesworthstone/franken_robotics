## Background

**FrankenTorch** is the owner's Rust tensor and autograd library, foundation row `FD-FT`. The ledger gives it
two uses. The first, its Metal gateway crate `ft-kernel-metal`, is admitted at M0 for the Metal annex
(INT-FT-01, INT-FT-02). The second is this bead: the crates `ft-api`, `ft-nn`, `ft-optim` and `ft-serialize`,
used by the learning crate `frob-learn` **behind a feature**, with three jobs (DESIGN):

1. the **CPU trainer** for small runs and tests;
2. the **gradient oracle** against which this project's on-device backward kernels are differentially tested
   (gate GATE-CORTEX-02: on-device backward kernels match FrankenTorch autograd within 10⁻⁵ relative on 10³
   random batches);
3. **policy interchange** through safetensors.

An honest note fixes what FrankenTorch is not. Its tensors live on the host; `Device::Metal` and `Device::Cuda`
are tags, and `ft-nn` and `ft-autograd` run on the CPU (FACT as reported from a source reading; re-read at
INT-FT-02). A device tag earns no GPU operator coverage. On-device learning kernels (matrix products,
activations, Adam) are therefore written in this project, in the shared kernel dialect, and observations never
leave the device during a rollout. Upstream work item FD-FT-02 (P2) would add real device execution; its
interim posture is exactly the three jobs above, and its switch-over rule is gradient parity first, then
switch the trainer.

**An admission is never inherited.** The M0 record covers the gateway crate at the M0 pin. These four crates
are first used at M2 and are admitted at M2, by their own record, at the pin of that day. Fallback named in
the ledger: the CPU trainer uses the in-house kernels on `batch-cpu`, and policies are exchanged in the native
checkpoint format only.

## Scope

In: the feature `frankentorch` of `frob-learn`, its optional path dependencies and the `check-deps` rules for
them; the admission test of the four crates at the M2 pin, run on the sibling's own API in the one file
`crates/frob-learn/tests/admit_frankentorch.rs`: convention records; known answers and controls for autograd,
optimizer and serialization; the stride convention; the re-read of the host-tensor fact; the M2 admission
record.
Out: the bridge module `frob_learn::torch` (N23a-15, the learning chapter's bead, which depends on this bead
and is compiled under this feature): tensor views in and out, the module twin and its parameter mapping, the CPU
learner adapter, the oracle interface, safetensors with the policy manifest in its metadata, the no-sibling
fallback and the record of FD-FT-02's switch-over rule. Both drafts had specified that module, under two names
and two sets of function names; it is specified once, there. Also out: the on-device kernels and their parity
gate (BD-196); PPO (BD-197); device-resident views and ownership epochs (BD-193); the Metal gateway (BD-016,
BD-028).

## Technical approach

**Edge and feature.** The crate `frob-learn` and its reserved, empty feature `frankentorch` are N23a-01's (the
crate skeleton, a dependency); this bead fills the feature: `frob-learn` declares `frankentorch = ["dep:ft-api",
"dep:ft-nn", "dep:ft-optim", "dep:ft-serialize"]`, off by default, each an optional path dependency at the pin of `franken-stack.lock` with
default features off. `check-deps` enforces: only `frob-learn` may name these crates; no default build enables
the feature (ambition and optional-sibling features are named and off by default); the core's lockfile holds
one asupersync package (FrankenTorch requires `0.6.2`, default features off) and no `block` patch (that patch
belongs to the Metal annex only).

**The bridge is not built here.** The module that uses these crates is `frob_learn::torch` of N23a-15
(`to_ft` and `from_ft`, `module_from_layers` and `params_from_module`, `CpuLearner`, `reference_gradients`,
`write_safetensors` and `read_safetensors`; N23a-12's `to_torch` lowers a `NetworkSpec` onto the bridge). An earlier draft of this bead sketched the same module as `frob_learn::ft_bridge` with
`oracle_grad`, `cpu_train_step`, `export_safetensors` and `import_safetensors`, and with the refusal
`FROB-REF-617` for a view that cannot cross under a zero-copy contract; those names are withdrawn. DESIGN, the
refusal code: the bridge's input is the learning chapter's `TensorView` (BD-193), whose rule for a view the
receiver cannot represent is `FROB-REF-547`; `FROB-REF-617` remains the code of the array-file boundary of the
stride converter (BD-036). What this admission supplies to the bridge: the admitted dependency behind the
feature, and the convention records below, which the bridge's parameter mapping reads.

**Admission items on the sibling's API (recorded against the pinned commit in the stack lock).** (a) The stride
convention: a 2 × 2 contiguous `f32` tensor reports element strides (2, 1). (b) Reverse-mode gradients of a
two-layer MLP with tanh match central finite differences in double precision within 10⁻⁶. (c) Adam's first ten
steps on a quadratic match the closed-form recurrence. (d) A safetensors round trip preserves bytes and
metadata. (e) GRU forward on fixed weights matches a hand-computed two-step example: input and hidden size 1,
every input and recurrent weight 1, every bias 0, h₀ = 0, inputs (1, −1). With r = z = σ(x + h),
n = tanh(x + r·h) and the update h′ = (1 − z)·n + z·h, the states are h₁ = 0.2048242148 (r = z = σ(1) =
0.7310585786, n = tanh 1 = 0.7615941560) and h₂ = −0.4416346193; under the other common update
h′ = z·n + (1 − z)·h they are 0.5567699411 and 0.0833793813. The convention record states which update and
which placement of the reset gate the sibling uses, and the expected values follow the record (to 10⁻⁶
relative in `f32`). A failed item is the result: the fallback named above applies and the item is filed as an upstream work item with its failing
fixture.

**Convention records (read at the pin; stored with the fixtures).** Linear-layer weight shape (output by
input, or the transpose) and bias placement; activation definitions (tanh, ELU and its negative-side constant);
Adam's update order, bias-correction form and the placement of ε (inside or outside the square root); the GRU
gate equations (which update form, and whether the reset gate multiplies the recurrent term before or after its
weight); default dtype; safetensors tensor naming and byte order.

**Known answers (hand-checkable; computed with the sibling's own modules and optimizer, so that the admission
does not wait for the bridge; N23a-15 repeats cases 1 and 4 through its bridge in this project's parameter
order).**
1. *Gradient of a one-layer linear map with squared error.* y = W·x + b with W = [[1, 2], [3, 4]], b = (0, 0),
   x = (1, −1), target t = (0, 0), loss L = ½·‖y − t‖². Then y = (−1, −1), ∂L/∂y = (−1, −1), ∂L/∂W = (∂L/∂y)·xᵀ
   = [[−1, 1], [−1, 1]], ∂L/∂b = (−1, −1), ∂L/∂x = Wᵀ·(∂L/∂y) = (−4, −6).
2. *Tanh layer.* With z = 0.5, y = tanh z, L = y: dL/dz = 1 − tanh² 0.5 = 0.7864477329659274.
3. *One Adam step.* Parameter θ = 1, gradient g = 0.5, learning rate 0.1, β₁ = 0.9, β₂ = 0.999, ε = 10⁻⁸,
   first step: m = 0.05, v = 0.00025, bias-corrected m̂ = 0.5, v̂ = 0.25, update 0.1·0.5/(0.5 + 10⁻⁸), so
   θ = 1 − 0.099999998 = 0.900000002 (with ε outside the square root; the convention record says which form
   the sibling uses, and the expected value follows the record).
4. *Serialization round trip.* A parameter set written to safetensors and read back is bit-identical, and the
   file is byte-identical on rewrite.

**The host-tensor fact, re-read.** A test constructs a tensor tagged with a device, runs a forward and
backward pass, and records where the computation ran (by the sibling's own introspection where it offers one,
and by the absence of any device receipt). The record states plainly: operator coverage on device, zero.

**Admission record.** `covers.crates` = the four crates and what they pull, gate field INT-FT-02 with `covers`
distinguishing this use, the stack receipt hash, the convention digests, the measured values and the caught
controls.

Determinism: CPU autograd results are recorded per platform; the hand cases are exact or tolerance-checked as
stated. Evidence: `Tested`; oracle-based results are `parity`.

## Acceptance criteria

- [ ] A default build of the core has none of the four crates in its graph; with `--features frob-learn/frankentorch` it builds on T with one asupersync package.
- [ ] The four known answers pass on the sibling's API at the pin (case 1 exactly in `f32`; cases 2 and 3 to 10⁻⁶ relative in `f32`; case 4 bit-identical), and the five admission items (a) to (e) are recorded with measured values.
- [ ] The convention records exist and state the linear-layer weight shape, so that the bridge of N23a-15 can map case 1's ∂L/∂W to [[−1, 1], [−1, 1]] in this project's order (that mapping, and its transposed control, are tested there).
- [ ] The negative controls of the admission are caught: a critic gradient taken from a stored output instead of the current forward output; an Adam step with the bias correction omitted.
- [ ] The host-tensor fact is recorded at the pin: a device-tagged tensor computes on the CPU and earns zero device operator coverage.
- [ ] An M2 admission record for the four crates exists and validates; `check-deps` refuses an edge to `ft-nn` from any crate other than `frob-learn`.

## Test plan

### Unit tests (`cargo test -p frob-learn --features frankentorch --test admit_frankentorch`)
- `linear_mse_gradients`: the five gradient arrays of case 1.
- `tanh_gradient`: 0.7864477329659274 to 10⁻⁶ relative in `f32`.
- `adam_first_step`: θ after one step equals the value the convention record's form implies (0.900000002 for ε outside the root).
- `safetensors_roundtrip_bit_exact`, `safetensors_rewrite_byte_identical`.
- `admit_ft_stride_convention_elements_2_1`; `admit_ft_autograd_matches_fd`; `admit_ft_adam_ten_steps`; `admit_ft_safetensors_roundtrip`; `admit_ft_gru_two_step_hand_example` (items (a) to (e)).
- `stored_value_critic_control_fails`: critic output 2, stored value 0, return 0: the correct gradient into the bias is 2; the planted variant returns 0.
- `adam_no_bias_correction_control_fails`: the planted update is 0.1·0.05/(√0.00025 + 10⁻⁸) = 0.3162 instead of 0.1.
- `device_tag_earns_no_coverage`.
- `ft_edges_confined_to_frob_learn` (`cargo test -p xtask check_deps`, a scratch workspace): a planted dependency on `ft-nn` from `frob-dyn`, and a planted `default = ["frankentorch"]` in `frob-learn`, are each refused by `check-deps` naming the crate and the rule; the shipped optional edge is allowed; with the feature on, the resolved graph holds one asupersync package and no `block` patch entry.
- The tests of the bridge (`weight_mapping_transposed_control_fails`: with the mapping transposed, ∂L/∂W is reported as [[−1, −1], [1, 1]]; the compile-fail test that no bare stride tuple crosses; the property test that the oracle agrees with central differences in `f64` to 10⁻⁶ relative on 10² random small networks of two layers of width 8) are in N23a-15.

### End-to-end script and logging
No script of its own; the oracle is exercised by the gradient-parity script of the learning unit. Its admission
is the step `frankentorch_cpu_admission` of `scripts/e2e/airlock_groups.sh`, written by this bead (N33a-34, a
dependency, provides the script, its step table and the skip logic; the step is reported `skipped: not yet due
(M2)` while `--milestone` selects an earlier one). The step logs each
hand case's expected and measured values, the convention digests, the control outcomes and the device-coverage
record.

### Known answers and negative controls
- Hand cases 1 to 4. For the critic control: the reported sibling defect in another library's PPO update is exactly "gradient from the stored value" (0 where 2 is correct), which is why it is a registered control here.
- Negative controls: the two of the acceptance list; the third of the earlier draft, the transposed weight mapping, is a control of the bridge and is registered by N23a-15.
- Metamorphic relation: scaling the loss by k scales every gradient by k exactly for powers of two.
- Determinism lanes: results identical twice on one machine; recorded per platform.

## Considerations

- The gradient oracle is slow and on the host by design; it is never inside a rollout or a performance measurement.
- When FD-FT-02 lands, the switch-over rule is: gradient parity (GATE-CORTEX-02) against the new device execution, then switch the trainer; until then FrankenTorch's device tags are ignored.
- If this admission fails, M2 still trains: the on-device kernels and the in-house CPU path do not depend on FrankenTorch; what is lost is an independent gradient check, which is replaced by central differences on small networks.
- With the feature off, GATE-CORTEX-02 (whose text names FrankenTorch autograd) reads `not run: oracle absent`, and the fallback paths run (in-house kernels on `batch-cpu`, the finite-difference oracle whose receipts are labelled as the weaker oracle). Both are N23a-15's acceptance, and the gate's value is entered by its own bead (BD-196); this bead neither tests nor records them, because they need beads that come after it.
- Policy interchange (the M4 use) rides on `ft-serialize`; under the never-inherited rule it is covered by this record only while the pin is unchanged, and is re-admitted at the pin of its day.
