## Background

FrankenRobotics rules that every Frontier mechanism has a **pilot**: a small experiment with existing tools,
outside the workspace, with a falsifier fixed in advance, run before the mechanism's work is funded. A work
package whose pilot's falsifier holds is not funded; its fallback ships.

The mechanism here is the terminal dashboard `frob-tui`, built on FrankenTUI (the owner's terminal UI library;
foundation row `FD-FTUI`, Consume, Frontier). The design states that its admission gate INT-FTUI-01 "is also
the pilot, run on a recorded stream before the crate is funded". This bead is that run: the gate's three
conditions measured with a throwaway probe, before any pane is designed.

The three risks the pilot retires, each a FACT-based concern (read 2026-11-21): (1) FrankenTUI's runtime has
an optional `asupersync-executor` feature pinned exactly to asupersync 0.5.0, and this project allows exactly
one asupersync package per build and never 0.5.0, so the library must be usable with that feature off; (2)
snapshot tests are the only way a dashboard is verified here, so rendering must be deterministic in the
headless harness (`ftui-harness`); (3) a dashboard that spins while idle would steal a core from the jobs it
watches. A fourth, found by building: FrankenTUI is on `nightly-2026-08-31` and must build on T, the one
toolchain of this project's build graph.

**Ceiling, computed before the test:** the dashboard is a convenience for a person watching a campaign. Its
effect on every claim of the project, and on time to a decision by an agent, is zero. The most it can be worth
is the operator time it saves; the pilot therefore has a small budget and a low bar for stopping.

## Scope

In: the frozen protocol; a probe crate outside the core workspace; one recorded job-event stream; the three
measurements; the pilot record with its result and the funding recommendation.
Out: the dashboard itself (BD-300, which depends on this pilot); any change to FrankenTUI (upstream work, in
its repository, if the pilot shows one is needed).

## Technical approach

**Pilot record (written to `crates/frob-conformance/registry/pilots.toml` before execution, result appended
after).** Mechanism: `frob-tui` on FrankenTUI, Frontier. Tool and pin: FrankenTUI at the revision of the day
(head `5979b92cc576`, version 0.10.0 on the day of reading). Cost: at most one agent-day and no device.
Fallback and kill gate: KILL-TUI; no dashboard; the same events as line-delimited JSON, with `job.list` and
`session.show` carrying the same numbers.

**Protocol (frozen before execution).**
1. *Probe crate.* A crate under the scratch area, with its own `[workspace]`, depending by path on FrankenTUI
   with default features off and `runtime` and `native-backend` on. Build on T through the offload shim.
   Record: builds or not, with the first error; `cargo tree -d`; the count of asupersync packages in the graph.
2. *Executor necessity.* Confirm that nothing in the probe needs `asupersync-executor`; then enable it in a
   second scratch copy and record that asupersync 0.5.0 appears (the control showing the count check can fail).
3. *Recorded stream.* Capture one real job-event stream from the daemon's job protocol: a job of at least 200
   chunks with one cancellation and one refusal, as canonical JSON lines (events carry job identifier, state,
   progress with a denominator, estimate and last committed tick; no scene payloads).
4. *Job pane.* A minimal model, update and view with a `Table` and a `ProgressBar`, fed the stream in the
   headless harness; store the final frame and the frames at every hundredth event as snapshots.
5. *Stability.* Replay the stream 100 times; every replay must reproduce every stored frame byte for byte.
   Replay with the events delivered in bursts of random size (seeded): the frames at the same event indices
   must still match, since the model is a function of the event sequence.
6. *Idle cost.* Run the probe attached to a real terminal emulator (or a pseudo-terminal) for 60 s with no
   events; measure user plus system CPU time; compute the percentage of one core.

**Falsifier (any one).** The probe does not build on T without the executor feature after one repair cycle;
more than one asupersync package, or any 0.5.0 package, in the graph; any replay differs from its snapshot;
idle CPU above 2% of one core. If the falsifier holds, `frob-tui` is not funded and KILL-TUI is recorded as
fired with the measured cause.

**Result record.** For each step the measured value and pass or fail; the recommendation `fund` or `do not
fund`; if `do not fund` because of the toolchain alone, the upstream item needed in FrankenTUI is named with
its failing fixture, and the pilot may be rerun after it lands.

Evidence class: `Tested`; the pilot's stream is real, its pane is a throwaway.

## Acceptance criteria

- [ ] The pilot record exists in the register with the protocol, falsifier, ceiling, fallback, cost, tool and pin written before the run, and the result after it.
- [ ] Measured and recorded: build on T (yes or no, with the error); asupersync package count without the executor (expected 0 or 1) and with it (expected to show 0.5.0); replays matching out of 100 (threshold 100); idle CPU percent over 60 s (threshold 2).
- [ ] The burst-delivery replay matches the stored frames.
- [ ] A funding recommendation is recorded; BD-300 does not start on a `do not fund`.
- [ ] No file of the core workspace depends on FrankenTUI as a result of the pilot; the probe lives outside it.

## Test plan

### Unit tests
The pilot is an experiment, not a product; its checks are the probe's own assertions:
- `probe_builds_without_executor`.
- `asupersync_count_at_most_one`: parsing `cargo tree -d` output.
- `executor_brings_0_5_0`: the control copy shows the second version.
- `job_pane_replay_100`: 100 byte-identical replays against the stored frames.
- `job_pane_burst_invariance`: seeded burst sizes 1 to 50.
- `idle_cpu_under_two_percent`: (user + system CPU seconds)/60 ≤ 0.02.

### End-to-end script and logging
`scripts/pilots/ftui_pilot.sh` (kept with the pilot record; it is not part of the product's end-to-end
suite): runs steps 1 to 6 and writes NDJSON with, per step, the command, exit code, wall time and the measured
value against its threshold, plus the stream's digest and the snapshot digests; a final line with the
recommendation.

### Known answers and negative controls
- Known answer: a model that is a pure function of the event sequence renders the same frame for the same prefix, however the events are batched.
- Negative controls: the executor-enabled copy (the asupersync count must rise); a pane that reads the wall clock into a cell (planted) must break replay equality; a busy-wait redraw loop (planted) must exceed the idle threshold.
- Determinism lanes: replays identical on the Mac and on the Linux host.

## Considerations

- The pilot deliberately measures the gate's conditions and nothing about usefulness; usefulness is the owner's call and the ceiling says how little rides on it.
- If FrankenTUI needs its executor for the widgets wanted, the dashboard is not built: the executor's asupersync pin is the subject of upstream work item FD-FTUI-01 (P3), and its interim posture is "the executor feature is forbidden here".
- The recorded stream becomes a fixture of BD-300's snapshot tests if the pilot passes.
- No milestone waits on this pilot.
