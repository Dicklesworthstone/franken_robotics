## Background

The FrankenRobotics viewer is an ordinary Three.js r186 page that draws immutable telemetry snapshots; replays
are exported as one self-contained HTML file by this project's own build step. FrankenThreeD, a sibling
project, offers an optional second way to build that page. FACT (its `README.md`, read 2026-11-21): four crates
(`f3d-core` 10,688 lines, `f3d-math` 19,100, `f3d-graph` 7,507, `f3d-runtime` 31,564); Three.js r186 is pinned;
an ingest command routes an ordinary application's WebGPU renderer to a new backend for an admitted feature
subset; pixel parity holds for ten scenes on a software rasterizer; no hardware run and no speedup have been
measured; single-file packaging is not built. It pins asupersync 0.5.0 and `serde_json = "=1.0.151"`, so it can
never be a Cargo dependency of anything in this project's graph. Posture (foundation row `FD-F3D`): Pattern
now (its admission-record discipline is already adopted), Subprocess when the viewer's feature subset is
admitted there.

Every Frontier mechanism needs a pilot with a falsifier before its work is funded, and the design says the
admission gate INT-F3D-01 is the pilot of this item: **ten reference frames of the replay page built through
the route match the plain bundle within 1/255 per channel on at least 99.9% of pixels, and an unadmitted
feature fails explicitly.**

**Ceiling, computed before the test:** the route changes rendering cost only, and rendering is outside every
claim of the project (no gate, no decision time, no evidence depends on how fast a replay draws). FrankenThreeD
itself reports no measured speedup. The expected benefit today is therefore zero; the route is kept as a
future accelerator and a packaging option, and the pilot's job is to establish that it is harmless (pixel
parity) and honest (explicit failure), not that it is faster.

## Scope

In: the frozen protocol; the two builds of one replay page; ten reference frames each; the pixel comparison;
the unadmitted-feature probe; the pilot record and recommendation.
Out: the overlays and the export verb (BD-191 supplies the page; BD-300 completes the overlays); any change in
FrankenThreeD (upstream work item FD-F3D-01 concerns its `serde_json` pin and is not needed for a subprocess).

## Technical approach

**Pilot record (written to the pilot register before execution).** Mechanism: the FrankenThreeD renderer
route for the viewer, Frontier. Tool and pin: FrankenThreeD at the revision of the day (head `bf7abe16367e` on
the day of reading), its ingest command line; Node at the version its repository pins. Cost: at most one
agent-day, no device (software rasterizer). Fallback: the plain Three.js bundle, which always ships.

**Protocol (frozen before execution).**
1. *The page.* One replay of an analytic scene (a box settling on a plane with the contact-cone and energy
   overlays on), exported by `frob telemetry export-html` as the plain bundle `replay_plain.html`.
2. *The route.* From a scratch directory, run FrankenThreeD's ingest as a subprocess on the unpacked
   application: `node tools/ingest/cli.mjs app.html --build-app out --pack-html replay_f3d.html`. Record the
   exit code and output. Nothing of FrankenThreeD is added to any manifest.
3. *Reference frames.* Ten frame times fixed in advance: t = 0, then nine equally spaced through the replay,
   camera fixed, canvas 1,280 × 720, device pixel ratio 1. Render each frame of each build in a headless
   browser on a software rasterizer (the same one for both builds; its name and version recorded), and read
   back RGBA.
4. *Comparison.* For each frame, the share of pixels for which every channel differs by at most 1 (of 255).
   Pass per frame: at least 99.9%, that is, at most 921 of 921,600 pixels outside the bound.
5. *Unadmitted feature.* Add to a copy of the page one feature outside FrankenThreeD's admitted subset (chosen
   from its own list of unsupported features at the pin) and run the route. Pass: a non-zero exit with a
   message naming the feature. Fail: a successful build (silent acceptance) or a build whose frames differ.
6. *Self-containment.* Open `replay_f3d.html` with networking disabled; it must render. (FrankenThreeD says
   single-file packaging is not built; if `--pack-html` is absent at the pin, the step is recorded `not
   available` and the route's output is packed by this project's own packer for the comparison.)

**Falsifier (any one).** Any frame below 99.9%; silent acceptance of the unadmitted feature; the route cannot
be run without adding a Cargo dependency or network access at build time. If the falsifier holds, the route is
not wired into the viewer's build and the plain bundle is the only route.

**Result record.** Per frame the pixel share; the worst frame; the unadmitted-feature outcome; build times of
both routes (recorded for information only; no speed claim is made); the recommendation `wire as optional` or
`do not wire`.

Evidence class: `Tested` for pixel parity on the named rasterizer. No Performance claim.

## Acceptance criteria

- [ ] The pilot record exists with protocol, falsifier, ceiling, fallback, cost, tool and pin written before the run, and the result after it.
- [ ] Ten frame comparisons are recorded with their pixel shares against 99.9%.
- [ ] The unadmitted-feature probe's exit code and message are recorded.
- [ ] The comparison harness itself is validated: comparing the plain bundle with itself gives 100%, and with a copy whose colours are shifted by 2 levels on 0.2% of pixels gives a failure.
- [ ] No manifest of this repository gains an `f3d-*` dependency; the route ran as a subprocess only.
- [ ] A recommendation is recorded; BD-300 wires the route only on `wire as optional`.

## Test plan

### Unit tests (the comparison harness, `viewer/tests/pixel_compare.test.mjs`)
- `identical_images_are_100_percent`.
- `one_level_difference_everywhere_passes`: every channel off by exactly 1 → 100% within bound.
- `two_level_shift_on_0_2_percent_fails`: 1,844 of 921,600 pixels off by 2 → 99.8% < 99.9%.
- `threshold_boundary`: exactly 921 pixels outside → pass; 922 → fail.
- `alpha_channel_is_compared`.

### End-to-end script and logging
`scripts/pilots/f3d_route_pilot.sh` (kept with the pilot record): exports the page, runs both builds, renders
and compares the ten frames, runs the unadmitted-feature probe. NDJSON lines carry the command, exit code,
wall time, per frame the pixel share and the count outside the bound (threshold 921), the rasterizer's
identity, the digests of both HTML files, and the probe's message; a final line with the recommendation.

### Known answers and negative controls
- Known answer: 0.1% of 1,280 × 720 = 921.6, so at most 921 pixels may exceed the bound.
- Negative controls: the shifted-colour copy; a route build with one overlay disabled (planted) must fail parity on the frames where the overlay is visible; the unadmitted feature must fail explicitly.
- Determinism lanes: the software rasterizer gives identical frames twice on one machine; the comparison is repeated on both hosts and the shares recorded.

## Considerations

- Pixel parity on a software rasterizer says nothing about hardware; FrankenThreeD has no hardware run on record, and this pilot does not add one.
- The route is a build-time subprocess with a pinned revision and a pinned Node version; it is supply-chain surface, which is one more reason the plain bundle remains the default and the release path.
- If FrankenThreeD later publishes single-file packaging and a measured speedup, the pilot is rerun at that pin; an admission is never inherited.
- No milestone waits on this pilot.
