## Background

FrankenRobotics pins its sibling projects in `franken-stack.lock`, records what a build actually resolved in a
**resolution receipt** (canonical JSON, schema `frob.stack-receipt/1`, stored under `receipts/` and named by
the BLAKE3 hash of its bytes), and checks the two against the tree with `xtask check-stack`, one of the six
workspace checks. Every admission record cites a receipt hash; every result carries the receipt hash of the
binary that produced it; no gate records a PASS on a dirty sibling tree; and the tool never writes to a
sibling checkout. Those rules are implemented by six beads (the posture vocabulary and lift registry, the
ledger rows, the lock parser, the receipt writer, the verification rules and the stack identities). Each has
unit tests on synthetic repositories.

This bead is the user-visible proof that the whole chain works on the real tree with the real binary: a plain
shell script that drives `cargo run -p xtask -- check-stack` and `frob`, plants every kind of drift in scratch
copies, and logs what happened in the structured form the project uses for all end-to-end scripts. It exists
because the unit tests cannot show that the shipped `xtask` binary, run from a clean checkout through the
build-offload shim against the real sibling checkouts, behaves as specified; and because the exit review of
each milestone needs one command that re-proves it.

The known answer it carries is KA-767: a receipt computed twice on an unchanged tree is byte-identical;
negative control: touching one tracked file in a sibling flips `dirty`, changes `tree_hash`, and `check-stack`
fails.

## Scope

In: the script, its fixtures (scratch copies made at run time), its assertions and its log.
Out: the mechanisms (their own beads); admission gates (bead N33a-28); the one-asupersync gate INT-ASUP-01
(BD-008), though the duplicate plant here exercises the same finding.

## Technical approach

**Form.** `scripts/e2e/stack_receipt.sh`: POSIX shell with `set -eu`, sourcing the shared helper of `STD-E2E`
for logging and assertions. It is idempotent and seed-explicit (its only randomness is the choice of which
tracked file to touch in a sibling copy, drawn from a seed given as `--seed`, default 1). It never modifies
the repository or any sibling checkout: all plants happen in scratch copies under
`${BIG_SCRATCH:-${TMPDIR:-/tmp}}/frob-e2e-stack/<utc>/`, removed at the end unless `--keep` is given. Sibling
copies are made with `git clone --no-hardlinks` of the local checkouts at their current heads (small siblings
in full; for FrankenSim a shallow clone at the pin), so that planting never touches the originals.

**Steps (each a named `step` in the log).**
1. `preflight`: disk space check; tool versions; `cargo xtask` with no argument prints exactly the six
   subcommand names and exits 3 (the usage code of BD-004; no `--help` subcommand exists).
2. `lock_parse`: `check-stack --json` on the repository; assert the report echoes T, eighteen foundations and
   a 64-hex stack-lock digest. Then eleven scratch locks, one per parser rule (unknown field, duplicate id,
   short revision, absolute path, missing path for a path posture, inexact version, unknown feature group, bad
   environment key, toolchain string malformed, dangling receipt hash, empty fallback): each must exit non-zero
   naming its rule.
3. `ledger_rows`: assert the eighteen identifiers and postures; plant three forbidden edges in a scratch copy
   (a dynamics crate to `fs-mbd`; `frob-core` to `franken-kernel`; a core crate to `ftx-drape`) and assert
   `check-deps` exits non-zero naming the foundation and the crate, each time.
4. `lifts_registry`: zero lift findings on the tree; one planted unregistered lifted file → one finding.
5. `receipt_twice` (KA-767): `check-stack --write-receipt --reason admission --gate E2E` twice on the
   unchanged scratch tree; assert both runs print the same hash, exactly one file exists under `receipts/`,
   and `cmp` finds the two serializations identical.
6. `receipt_path_free`: move the scratch tree to a different directory; recompute; assert the same hash; grep
   the receipt for the scratch path, the user name and the host name; assert none.
7. `dirty_flip` (the control of KA-767): append one byte to one tracked file of one sibling copy; assert the
   in-memory resolution shows `dirty: true` and a non-null `tree_hash` for that sibling only, and that
   `check-stack` exits non-zero with `sibling-dirty` (`dirty-changed`).
8. `drift_classes`: on sibling copies, construct fast-forward (one new commit), retreated (reset one commit
   back) and diverged (a commit on a side history) states; assert the findings `sibling-moved` with the
   classes `fast-forward`, `retreated`, `diverged`.
9. `lock_receipt_lockfile_toolchain`, each plant on a fresh scratch copy: append a comment line to the scratch
   `Cargo.lock` (`lockfile-changed`), then run `--write-receipt` and assert the check passes again; remove one
   workspace's `Cargo.lock` (`lockfile-missing`); edit the scratch toolchain file's channel
   (`toolchain-changed`); edit one `git_rev` in the scratch `franken-stack.lock` without a new receipt
   (`stack.pin` with kinds `lock-edited` and `off-pin`: plant 7 of GATE-WS-01); change one byte of the newest
   receipt (`stack.receipt-hash`, `receipt-tampered`); delete `receipts/HEAD` (`stack.receipt-missing`). After
   every `--write-receipt` of the script, assert that `receipts/LOCK_DIGEST` equals the report's stack-lock
   digest.
10. `root_settings`: remove in turn the asupersync patch entry, the FrankenSQLite profile overrides and the
    build-identity entry from the scratch root; assert `patch-missing`, `profile-override-missing`,
    `build-env-missing`.
11. `duplicate_package`: point the scratch lock resolution at a second asupersync version; assert that
    `check-stack` records asupersync in the report's `duplicates` list, exits 0 and reports
    `may_record_pass: false` (a duplicate is a fact of this check, not a finding, N33a-05), and that
    `check-deps` on the same copy exits non-zero with `asup.duplicate` (the check that owns the plant).
12. `pass_guard`: ask the guard (through `check-stack --json`) whether a PASS may be recorded: `true` on the
    clean scratch tree; `false` with the dirty sibling of step 7; `false` with a receipt whose bytes were
    altered.
13. `read_only_siblings`: remove write permission recursively from two sibling copies; run verify and
    write-receipt; assert success; assert the digest of each copy (including its `.git` directory) is
    unchanged.
14. `identity_on_results`: `frob doctor --json` and `frob capabilities --json` (two read verbs of BD-022, so
    no `--key` is needed); assert `evidence.stack_receipt` equals
    `receipts/HEAD` and the lock digest `doctor` prints equals `receipts/LOCK_DIGEST`; feed a stored envelope
    recorded under another receipt to a comparison; assert exit code 3 and `refusal.code = "FROB-REF-890"`.
    The comparison sub-step needs a verb that raises the code (the pooling and pairing verbs of N33c-31, M1);
    until that bead has landed the sub-step is logged `not-run` with its key, never as passed, as the refusal
    registry N33-REF prescribes.
15. `cost`: time the verify mode on the warm real tree; log it against the six-check budget (60 s for all six
    together, TARGET).

**Logging (per the shared standard).** NDJSON to `target/e2e-logs/stack_receipt/<utc>.ndjson` with a
human-readable transcript beside it. Every line has `ts`, `script`, `bead` (this key, and for each step the
key of the bead whose mechanism it exercises), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`,
`end`), the exact command line, exit code and wall time; for `frob` calls the envelope's `evidence` block
(claim, class, tier, determinism, identities, seed); measured values with units and thresholds (the verify
time in seconds against its budget; counts of foundations, findings and files); digests where state is
compared (receipt hashes, sibling-copy digests before and after); and on failure the first differing value
(for example the first differing byte offset of two receipts) with the scratch paths needed to reproduce. A
final `summary` line gives assertions passed and failed and the known answers touched (KA-767). The log
contains repository metadata only.

**Exit status.** Non-zero if any assertion fails or any planted condition is not caught.

## Acceptance criteria

- [ ] The script passes from a clean checkout on the Mac and on the Linux host, through the offload shim, and is idempotent (a second run passes and leaves the repository and the siblings unchanged).
- [ ] KA-767 and its control are asserted and logged with both receipt hashes.
- [ ] Every one of the planted conditions of steps 2 to 4 and 7 to 12 is reported with its expected finding; a plant that is not caught fails the script.
- [ ] Step 13 shows byte-identical sibling copies after both modes.
- [ ] Step 14 shows the receipt hash on two envelopes, the lock digest equal to `receipts/LOCK_DIGEST`, and the `FROB-REF-890` refusal (or, before N33c-31 has landed, the sub-step logged `not-run` with that key).
- [ ] The NDJSON log validates against the shared log schema and ends with a `summary` line; no line contains an absolute path of the user's home directory outside the scratch root's variable form.
- [ ] The script's runtime is recorded and stays within a few minutes on a warm tree (it runs under a timeout).

## Test plan

### Unit tests
The script is itself a test. Its own correctness is guarded by a self-test mode, `--self-test`, which runs each
assertion helper against a known-good and a known-bad input (an identical pair of files and a differing pair; a
finding list that contains the expected kind and one that does not) and must report the bad ones. A shell lint
runs on the script in the repository's formatting lane.

### End-to-end script and logging
This bead is the script; see above. It is invoked by the M0 exit review (bead BD-044) and at every pin move by
the compatibility train (move the pin, write a new receipt, rerun the admission and parity gates, relock).

### Known answers and negative controls
- KA-767 with its control.
- Negative controls exercised: eleven parser plants; three forbidden edges; one unregistered lift; dirty, fast-forward, retreated and diverged siblings; changed and missing lockfile; changed toolchain file; a lock edited without a new receipt; a tampered receipt and a missing `receipts/HEAD`; three missing root settings; a duplicate asupersync (caught by `check-deps`); an altered receipt offered to the guard; an other-stack envelope.
- Mutation check of the script: with the `check-stack` binary replaced by a stub that always exits 0 (in the self-test), at least fifteen assertions must fail; this shows the script is looking.
- Determinism lanes: two runs with the same seed produce the same sequence of assertions and the same receipt hashes on the same tree.

## Considerations

- Cloning FrankenSim for a scratch copy is the expensive part; a shallow clone at the pin keeps it within the disk preflight, and the script skips sibling copies it does not plant in.
- The script must not be the thing that violates the read-only rule: it never runs a state-changing git command in an original sibling, and a guard at the top refuses to run if the scratch root resolves inside a sibling checkout.
- When a sibling is legitimately dirty on the developer's machine, steps on the real tree report `dirty-unchanged` and the PASS guard is `false`; the script records that and still passes, because its assertions about planted states run on clean copies.
- Windows is not a target; the script assumes a POSIX shell, `git` and the offload shim.
