## Background

asupersync is the suite's structured-concurrency runtime. Its capability context `Cx` (cancellation, budgets,
deadlines) appears in signatures throughout FrankenSim's executor crate `fs-exec` and therefore throughout this
project. Cargo identifies a package by name, version and source. Two asupersync packages in one build graph (two
versions, or the same version once from the registry and once from a path) are two unrelated crates: their `Cx`
types do not unify, a job context made by one cannot be passed to code compiled against the other, and
cancellation is silently lost at the seam. The rule (DESIGN, invariant INV-SUITE-02): **every binary links exactly
one asupersync package, and every workspace resolves the same published version.**

The starting state makes the rule non-trivial (FACT, read on 2026-11-21 from each sibling's manifests; re-read by
this bead's test, never copied into a record):

| Sibling | Head | asupersync requirement |
|---|---|---|
| frankensim | `483d09c682f2` | path `../asupersync`; `Cargo.lock` resolves 0.6.2; its own `constellation.lock` still pins 0.5.0 at `7a0f2f55047c` |
| asupersync | `b32c5ba66315` | it is 0.6.2, with 267 modified paths in the checkout |
| frankensqlite | `79b735cb265a` | `0.6.2` from the registry, default features off; FrankenSim patches it to the path |
| frankentorch | `8165d6a18028` | `0.6.2`, default features off |
| franken_numpy | `e8cb85f4e5ac` | `=0.6.2`, optional |
| frankenscipy | `edb7ae619c2d` | `0.6.2`, default features off |
| frankensympy | `29f847c14428` | path `../asupersync` |
| fastmcp_rust | `117388bcc169` | `=0.6.2` |
| frankentui | `5979b92cc576` | `=0.5.0`, optional, behind feature `asupersync-executor` |
| franken_threed | `bf7abe16367e` | `=0.5.0`, default features off |
| frankenjax | `fa93fb775e1c` | `0.5.0`, optional |

Three siblings still name 0.5.0 (RISK-03, High). The design answer has two halves. Here: a gate, INT-ASUP-01, that
measures package identity in every workspace. In the siblings: upstream work item **FD-ASUP-01** (priority P0, done
at M0), which aligns FrankenSim's constellation, FrankenTorch and fastmcp_rust on one published version by changes
made in those repositories. Every sibling is the owner's project, so a mismatch in a sibling is work this program
does there, under that repository's own `AGENTS.md`, gates and conventions. INT-ASUP-01 is the gate that proves
FD-ASUP-01.

Alternatives rejected. (1) A local `[patch]` that forces every sibling onto whatever path happens to be checked
out: it hides the disagreement instead of removing it, and a dirty path checkout is not a published version.
(2) Letting `frob-mcp` live in its own workspace so that a second package is tolerated: that is KILL-MCP's first
fallback, not the default wiring. (3) Admitting 0.5.0 for one optional feature: frankentui's executor feature is
forbidden, and frankenjax and franken_threed are never Cargo dependencies.

## Technical approach

**1. The measurement (DESIGN).** For each workspace W in {core (which contains `surface/frob-mcp`),
`spark/frob-spark-cuda`, `spark/frob-spark-metal`, `apps/`, `derive/`, `bindings/`, `worker/`} that exists at the
commit under test:

1. Run `cargo tree -d --workspace --locked --manifest-path W/Cargo.toml` and capture stdout. `-d` lists every
   package that occurs more than once in the resolution. PASS requires that no line names `asupersync`.
2. Run `cargo metadata --format-version 1 --locked` and select packages with `name == "asupersync"`. PASS requires
   exactly one, and its `version` equal to the `version` field of the FD-ASUP row of `franken-stack.lock`. Its
   `source` is recorded: `registry` or a repository-relative path (never an absolute machine path).
3. The "no binary links two" clause is decided by the rule `asup.duplicate` of `check-deps` (N34-03): the gate
   reads that check's report facts, one line per binary target of W (`frob`, `frobd`, `frob-mcp`, `frob-verify`,
   `frob-fsim-worker`, `frob-tui`, `xtask`, the annex binaries) with the asupersync version linked, its source,
   or `none`. As recorded evidence by a second tool, the gate also captures, per binary B,
   `cargo tree -e normal,build -p <crate of B> -i asupersync --locked` and hashes its output; that listing must
   print one root. If the listing and the check's report disagree about a binary, the gate fails and names it.
   This clause is what catches a duplicate that only one binary's feature set pulls in.
4. A workspace whose graph contains no asupersync at all (allowed for `frob-cert` built alone) is recorded as
   `none`, which is a pass for that workspace.

The measurement is a pure function of manifests and lockfiles. It builds nothing and writes nothing outside this
repository (INV-SUITE-04).

**2. Wiring, and which check fails on what (DESIGN).** The workspace gate GATE-WS-01 plants a second asupersync
package and requires it to be caught by the check that owns it and by no other; the design's table of checks
gives "one asupersync package per binary" and "no asupersync 0.5.0 anywhere" to `check-deps` and "the stack
lock against lockfiles" to `check-stack`. Hence:
- `check-stack` reads the FD-ASUP row, runs steps 1 and 2 per workspace, and writes into the resolution receipt:
  `duplicates` (the list of duplicated package names per workspace; empty on pass) and one `commands` entry per
  invocation with `argv`, `exit` and `output_hash` (BLAKE3 of stdout). It **fails** (finding
  `stack.asup-version`) when a workspace that resolves asupersync has no asupersync package at the row's
  version, which covers a lockfile whose version differs from the row and two workspaces that disagree. It
  **does not fail** on a duplicate: a non-empty `duplicates` is recorded as data. With the row at 0.6.2 and a
  planted second package at 0.5.0, the row's version is still present, so `check-stack` stays clean and the
  plant is caught by `check-deps` alone.
- `check-deps` is not extended by this bead. It runs `asup.duplicate` (N34-03) and the deny rows `asup.v0_5_0`,
  `ftui.executor-feature` and `suite.forbidden-package` (N33c-09); a version mismatch without a duplicate is
  not a finding there.
- **The gate evaluation** (a function called when the admission record of INT-ASUP-01 is written with the
  record writer of N33a-07; `xtask` gains no seventh subcommand): INT-ASUP-01 passes when `check-stack` exits
  zero, the newest receipt's `duplicates` names no `asupersync` in any workspace, `check-deps` exits zero, and
  steps 1 to 4 hold. A seeded second package therefore fails the gate, through `check-deps` and through the
  receipt's `duplicates`, while `check-stack` itself exits zero.
- The stack-lock row (TOML): `id = "FD-ASUP"`, `name = "asupersync"`, `posture = "consume"`,
  `version = "<V>"`, `admission_gate = "INT-ASUP-01"`,
  `fallback = "FD-ASUP-01 aligns the siblings; a surface that still brings a second package: KILL-MCP fallback 1."`
  The row exists from the stack lock's first version (N33a-02) and holds the version FrankenSim's pinned commit
  builds with; FD-ASUP-01's switch-over sets it to V.

**3. What the gate proves: FD-ASUP-01 (specified in the upstream bead FD-ASUP-01, on which this bead depends,
and in its sibling half NFp4-01, on which FD-ASUP-01 depends).** NFp4-01 chooses the one published version V
(the choice of OPEN-SUITE-1, with the procedure and its evidence) and changes frankensim (the asupersync entry of
its `constellation.lock` and its requirement), frankentorch and fastmcp_rust (their requirements), and asupersync
itself if a version must be published, each under that sibling's own rules with a mirrored bead; its closing
record gives V, V's commit and tag, the evidence, each repository's pre-change and landed commits and the four
mirrored-bead identifiers. FD-ASUP-01 copies that record into its own closing record, keeps the failing fixture
under `tests/upstream/FD-ASUP-01/`, and runs the switch-over (the compatibility train that moves the pins here and
sets `version = V` in the FD-ASUP row); it hands V, the evidence and the landed commits to this bead for the
admission record. The item's row in `registries/upstream.toml` (`open` → `landed` → `adopted`) is entered by
BD-037 from FD-ASUP-01's closing record, after this bead. The step-by-step procedure was drafted here as well;
the one copy is in those two beads, with the three details this draft had added (the byte comparison that
decides whether V is 0.6.2, the caret-requirement option for fastmcp_rust, and the `cargo tree -d` output of a
consumer workspace before the change kept with the fixture).

This bead's part of the switch-over is one step of that train: re-running INT-ASUP-01 against the new pins and
appending the record. INT-ASUP-01 proves the item in this sense: after the train, the measurement passes with V
in every workspace, and the record cites the sibling commit at which each change landed.

**4. Interim posture until FD-ASUP-01 lands.** One package identity per build stays enforced by `check-deps`. The
core workspace root repeats FrankenSim's `[patch.crates-io] asupersync` entry so that registry requirements and the
path resolve to one package. A surface that would still bring a second package stays out of the core graph under
KILL-MCP's first fallback. No milestone waits: M1 needs only what FrankenSim's pinned commit builds with.

**5. Evidence.** One record in `DEPENDENCY_ADMISSION.md` per run: the commit of this repository, the receipt hash,
each command with its output hash, the package count, V, and the sibling commits at which each FD-ASUP-01 change
landed (from FD-ASUP-01's closing record). Claim: Known answer about the build graph; class `Tested`; determinism
D0 (pure function of tracked files).

**6. Recording (N33a-07's form; this bead is the one recorder of INT-ASUP-01's one part, M0).** The suite chapter
has no register bead of its own, so this bead fills the `tier` and `controls` of the gate's row: the gate's entry
`INT-ASUP-01` in `g1_known_answers` runs the measurement and the gate evaluation on the real tree (steps 1 to 4,
`check-stack` and `check-deps` through `cargo xtask … --json`) and the four controls of the gate (the planted
0.5.0 consumer, the unpatched same-version pair, the single package at the wrong version, the doctored report
line) each on its scratch copy. `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers
--features gauntlet-mutations -- INT-ASUP-01` writes the harness receipt; the admission record is written with
N33a-07's writer citing it as `harness_receipt`; and the row is entered from the same receipt with
`cargo run -p frob-conformance --example record_gate -- --gate INT-ASUP-01 --receipt <hash>` by a session that did
not implement this bead. A failing run is recorded the same way. The re-run of FD-ASUP-01's switch-over is a new
run of the same entry at the new pins, recorded by this bead's recording session in the same form. No script
writes the record or the row.

## Acceptance criteria

- [ ] `cargo tree -d` evidence is recorded for each workspace, showing one asupersync package at the one published version V (the seed done-condition).
- [ ] No binary target links two asupersync packages: the report of `check-deps` (rule `asup.duplicate`, N34-03) shows one version or `none` per binary, the per-binary inverse tree has one root for every binary, and the two agree.
- [ ] A seeded second asupersync version fails (the seed done-condition): on the scratch-copy fixture with a planted `asupersync = "=0.5.0"` consumer, `check-deps` exits non-zero and names both versions and the path that introduces the second; the receipt written by `check-stack` lists `asupersync` under `duplicates`; the gate evaluation reports INT-ASUP-01 FAIL; and `check-stack` itself exits zero, so that the plant is caught by exactly one of the six checks (GATE-WS-01).
- [ ] A workspace whose single asupersync package has a version other than the FD-ASUP row's fails `check-stack` with `stack.asup-version` and produces no finding of `check-deps`.
- [ ] The gate run records that the deny rows of N33c-09 ran: on the clean tree they pass, and the gate's script shows `check-deps` failing a manifest that enables `ftui-runtime/asupersync-executor` and one that adds `frankenjax` or an `f3d-*` crate (the rows and their own tests are N33c-09's).
- [ ] The record cites, for each sibling change (frankensim, frankentorch, fastmcp_rust; asupersync if a release was needed), the sibling commit at which it landed through that sibling's own gates and its mirrored-bead identifier, as FD-ASUP-01's closing record gives them (copied from NFp4-01's); the changes themselves are NFp4-01's work, and the item's row in `registries/upstream.toml` is BD-037's, entered after this bead from the same closing record.
- [ ] FrankenSim's `constellation.lock` asupersync row equals what its `Cargo.lock` resolves (the test `constellation_asupersync_matches_cargo_lock` that NFp4-01 adds in FrankenSim, run at the pin), and `check-stack` reports the FrankenSim checkout itself `on-pin` and clean. The receipt's `own_lock` for FrankenSim is one class for the whole lock file and may still read `agrees: false` because of its other stale rows (franken_numpy, frankenscipy, frankensqlite, frankentorch, franken_networkx), which FD-FSIM-16 refreshes at M1; that is recorded, and is not a failure of this gate.
- [ ] The FD-ASUP row of `franken-stack.lock` carries V; the receipt's `duplicates` is empty; the record cites the receipt hash.
- [ ] The record carries V and the evidence for choosing it (NFp4-01's choice of OPEN-SUITE-1, from FD-ASUP-01's closing record), or states that OPEN-SUITE-1's fail-closed default is still in force; the decision record of OPEN-SUITE-1 is N33c-35's, which reads this record.
- [ ] If FD-ASUP-01 cannot land within the M0 budget, the record says so, the interim posture is verified by the same checks, and the fact is handed to the M0 exit review (BD-044) for the KILL-MCP decision.
- [ ] INT-ASUP-01 is recorded in N33a-07's form (section 6): the `g1_known_answers` entry `INT-ASUP-01` with the gate's four controls registered and caught in the same run; the admission record's `harness_receipt` and the row entered with `record_gate --gate INT-ASUP-01 --receipt <hash>` cite the one receipt; the row carries the measured package counts; the recording session is not one that implemented this bead.

## Test plan

### Unit tests
In `xtask/tests/` (real `cargo metadata` on real fixture workspaces under `xtask/tests/fixtures/`, labelled
`synthetic`; no mocks):
- `asup_single_package_passes`: fixture workspace with one path-patched asupersync stand-in; asserts exit 0, `duplicates == []` and gate PASS.
- `asup_second_version_fails_gate`: fixture with a planted `=0.5.0` consumer; asserts that the gate evaluation fails, that the receipt's `duplicates` names `asupersync` with both versions, that `check-deps` exits non-zero and prints the introducing dependency path, and that `check-stack` exits zero.
- `asup_same_version_two_sources_fails_gate`: registry 0.6.2 and path 0.6.2 without the patch entry; asserts gate failure and a `duplicates` entry (two package identities at one version).
- `asup_version_differs_from_stack_lock_fails`: one package at a version other than the FD-ASUP row's; asserts `check-stack` fails with `stack.asup-version` and `check-deps` reports nothing. `asup_two_workspaces_disagree_fails`: two workspaces each with one package, at different versions; `check-stack` fails and names both workspaces.
- `asup_inverse_tree_agrees_with_report`: on the binary-scoped duplicate fixture, the per-binary inverse tree shows two roots for the one binary and the report of `check-deps` shows the same; a doctored report line that disagrees with the tree fails the gate and names the binary.
- The rule-level cases drafted here have one copy each, in the bead that owns the rule: the binary-scoped duplicate (`binary_scoped_duplicate_caught`, N34-03); 0.5.0 banned even when it is the only package (`denies_asupersync_0_5_0_when_unique`, N33c-09); the frankentui executor feature (`denies_ftui_executor_feature`, N33c-09).
- `receipt_records_commands`: the receipt contains one `commands` entry per invocation with a 64-hex `output_hash`; two runs on an unchanged tree give byte-identical receipts (KA-767).
- `check_writes_nothing_to_sibling`: run against a read-only copy of a sibling tree; asserts success and no write attempt (INV-SUITE-04).
- `no_absolute_paths_in_receipt`: asserts no string beginning with `/Users/` or `/home/` appears.

### End-to-end script and logging
`scripts/e2e/suite_asup_identity.sh`: runs `cargo xtask check-stack` and `cargo xtask check-deps` on the real
tree, runs the gate's tier entry with `e2e_tier g1_known_answers INT-ASUP-01 --mutations` and logs its receipt
hash and the four controls caught (the script records nothing: the row is entered by the recording session from
that receipt), then reads the newest receipt under `receipts/` and the INT-ASUP-01 record of `DEPENDENCY_ADMISSION.md`
through the record validator of N33a-07 and asserts one asupersync package per workspace at the FD-ASUP row's
version, an empty `duplicates`, and that the record cites that receipt's hash. (The user-side view of the same
facts through `frob doctor --json` is asserted by N33b-20 and N33a-28, which depend on this bead and on the
`doctor` verb of BD-022; this bead, a lower seed, does not call it.) It then copies the workspace manifests to a scratch directory, plants the second
version, and asserts there that `check-deps` fails with `asup.duplicate`, that the receipt lists the duplicate,
that the gate evaluation reports FAIL and that `check-stack` exits zero; then plants a single package at a
version other than the row's and asserts the converse (`check-stack` fails, `check-deps` is silent). Logged per STD-E2E: each command line, exit code, wall time, the
envelope's evidence block, metrics `asupersync_packages` (threshold 1 per workspace), `workspaces_checked`,
`duplicates`, the receipt hash, and on failure the first duplicated package with its two dependency paths. Summary
line names gate INT-ASUP-01.

### Known answers and negative controls
Known answer: exactly one package per workspace, the same version in all. Negative controls of the gate: the
planted 0.5.0 consumer; the unpatched same-version pair; the single package at the wrong version; the doctored
report line. The binary-scoped duplicate and the forbidden feature are controls of the rules in N34-03 and
N33c-09 and are re-run by the gate's script. Metamorphic:
reordering workspace members or dependencies leaves the receipt's `duplicates` and package count unchanged.
Determinism: twice on one machine gives identical receipts; the check has no platform-dependent output because it
stores repository-relative identities only.

## Considerations

- RISK-03 (two asupersync versions in one build) is the risk this bead retires; its earliest signal is `cargo tree -d` at this gate. RISK-55: other agents work in the same sibling repositories; reserve files through Agent Mail and keep each sibling change small.
- OPEN-SUITE-1 (which version): default as stated. OPEN-SUITE-3 (dirty asupersync checkout between receipts): development builds allowed with the tree hash in the receipt; no gate records a PASS on a dirty tree, so the PASS of this gate needs a clean asupersync tree or the registry package.
- OPEN-SUITE-6: computational crates take asupersync's `Cx` wherever cancellation is observed; a capability-free token from `frob-core` is used only if this gate fails after FD-ASUP-01 and a fallback splits the graph.
- The priority P0 orders the work; it does not make a milestone wait. The interim posture ships meanwhile.
- A sibling's newer clean head is never rolled back locally to make this check pass; an off-pin sibling is classified (on-pin, stale-lock, drift) before any remedy.
- Pins and T are frozen during the ten-fold tournament; a later asupersync release is adopted only by a compatibility train outside that window.
