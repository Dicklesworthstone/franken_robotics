## Background

The Mac tier of the simulator (tier name `gpu-metal`) reaches Apple's Metal through one safe gateway owned by a
sibling project: crate `ft-kernel-metal` (version 0.1.3) in FrankenTorch. The annex `spark/frob-spark-metal`
consumes it (foundation row FD-FT, posture Consume). INT-FT-01 (bead BD-016) proves that the gateway builds in the
annex and runs one kernel. A crate that compiles is not yet admitted: for each source file this project leans on,
a first admission test must pass before any code above the boundary calls it. INT-FT-02 is that test for
`frankentorch/crates/ft-kernel-metal/src/compute.rs` (1,680 lines; FACT at head `8165d6a18028`), which is reused as
"a safe gateway to custom Metal Shading Language kernels".

The test has three clauses, and each protects a design decision that would otherwise rest on reading:

1. **A buffer stays resident across two command buffers.** Spark's device arena keeps every per-world slab on the
   device for the life of an environment and synchronizes with the host once per chunk. If state had to be
   re-uploaded per command buffer, the Metal tier would have no throughput argument at all.
2. **The gateway returns a completion receipt from the device.** A run is labelled native on a device only if its
   receipt carries a completed command buffer with start and end times from that device (readback rule R4), and
   timers cover completion, never enqueue alone (R5). FACT: `Receipt.device_seconds` spans Metal's `GPUStartTime`
   to `GPUEndTime`.
3. **A device tag alone earns zero operator coverage.** FACT (reported from a source reading; re-read by this
   test): FrankenTorch tensors live on the host, `Device::Metal` and `Device::Cuda` are metadata, and `ft-nn` and
   `ft-autograd` run on the CPU. A coverage table that counted "tensor tagged Metal" as GPU execution would report
   progress that does not exist. On-device learning kernels are therefore written in this project's shared kernel
   dialect, and FrankenTorch serves as CPU trainer, gradient oracle and policy interchange.

Alternative rejected: binding Metal directly beside the gateway to obtain richer receipts. A second binding needs
an owner decision (OPEN-SPARK-5); missing gateway features are upstream work item FD-FT-01, done in FrankenTorch's
repository, and until it lands Spark works inside the gateway's limits.

## Scope

In: the three-clause admission test, run on the M5 Ultra; its negative controls; the re-read of the gateway facts
the Metal backend's design depends on, each recorded at the pin; the rule that fills operator coverage from
receipts; the admission record.

Out: building the gateway and the first kernel (BD-016); the Metal backend proper with packed arguments, batch
chains and snapshot blits (BD-174); the hardware fingerprint and the Metal language-version probe (BD-029); device
faults and the commit fence (BD-175); gradient parity with FrankenTorch (BD-196); changes to the gateway (FD-FT-01).

## Technical approach

File: `spark/frob-spark-metal/tests/admission_int_ft_02.rs`. It uses the real gateway on the real device; nothing
is mocked. Kernel sources are two fixture kernels in the shared dialect, compiled under the gateway's
`MathMode::Safe` (fast math off): `k_add_one` (a[i] ← a[i] + 1) and `k_times_two` (a[i] ← 2·a[i]).

**Clause 1, residency.**
1. `Gateway::open`; record `allocated_bytes` as B₀.
2. Allocate A with `buffer_f32` from host data a[i] = i for i in 0..4096 (every value and every result below is an
   exactly representable single-precision integer). Record `allocated_bytes` as B₁.
3. Batch 1: encode `k_add_one(A)`, `submit`, keep receipt R₁.
4. Batch 2, a second command buffer: encode `k_times_two(A)`, `submit`, keep receipt R₂. No host write to A
   happens between the two submits, and the same buffer handle is passed.
5. `read_f32(A)` must equal 2·(i + 1) for every i, bit for bit. `allocated_bytes` after batch 2 must equal B₁.
6. Negative control (planted defect `host-roundtrip`): a test-only wrapper re-uploads the original host array into
   A before batch 2. The result is then 2·i, the assertion of step 5 fails at i = 0 (0 where 2 is expected), and
   the control is registered as caught.

**Clause 2, device receipt.**
1. R₁ and R₂ each report kernel count 1; a third batch encoding both kernels reports kernel count 2.
2. `device_seconds` is strictly positive and not larger than the host wall time measured around `submit` plus one
   millisecond of slack; the host time is recorded beside it, never substituted for it.
3. DESIGN: the annex type `DeviceReceipt` has no public constructor other than from a gateway `Receipt` of a batch
   in terminal state `Completed`. A compile-fail test tries to build one from a host timer and must not compile.
   A second compile-fail test reads a batch output before `submit` returns and must not compile (rule R1 rests on
   the gateway's exclusive borrow of outputs; FACT: compile-fail tests exist in `compute.rs`).
4. Negative control (planted defect `enqueue-timer`): a wrapper that stamps a receipt at enqueue is rejected by
   the type in 3; the registry entry records the compiler error as the catch.

**Clause 3, coverage from receipts only.** DESIGN: an operator (a kernel of the registry) is `covered` on a
backend if and only if a `DeviceReceipt` from that backend exists for a batch that encoded it. Test: with
FrankenTorch's `ft-core` and `ft-nn` as dev-dependencies of the annex test, build a tensor tagged `Device::Metal`,
run a `Linear` forward on it, and assert (a) the gateway's submitted-batch counter and `allocated_bytes` did not
change, (b) the coverage table for `gpu-metal` lists zero operators for that operation, (c) the result equals the
same forward on a `Device::Cpu` tensor bit for bit. The record states the re-read fact with file and line.
Negative control (planted defect `tag-counts`): a coverage rule that keys on the tensor's device tag reports one
covered operator and the assertion (b) fails.

**Facts re-read and recorded at the pin** (each asserted where the API allows, otherwise recorded from source with
file and line): completion is synchronous (`dispatch` and `submit` block); at most 31 buffer arguments per kernel
(`MAX_ARGUMENTS`); buffers bind at offset zero; storage is `StorageModeShared` only; typed helpers are `f32`, `u32`
and bytes out; compilation is from source only, with no function constants and no binary archive; one device and
queue per process, the queue holding 64 command buffers; the wait cannot be interrupted; a failed batch is
reported, not re-run, and its outputs are undefined; the receipt holds a kernel count and device seconds only;
`max_threads_per_threadgroup` and `thread_execution_width` are read from the pipeline (rule R6: thread-group sizes
are multiples of the width that is read, never assumed).

**Record.** One entry in `DEPENDENCY_ADMISSION.md`: commit of this repository whose annex lockfile contains
`ft-kernel-metal`, FrankenTorch's commit, the command, its output hash, the resolution receipt hash, the device
name, the measured `device_seconds`, and the list of re-read facts with any that changed. Claim: Known answer;
class `Tested`; tier `gpu-metal`; determinism: exact integer results, so bit equality is required.

## Acceptance criteria

- [ ] A buffer stays resident across two command buffers: the read-back equals 2·(i + 1) for all 4,096 elements with no host write between the batches (the seed done-condition, first half).
- [ ] The receipt comes from the device: kernel counts 1, 1 and 2; `device_seconds` > 0 and within the host bound; `DeviceReceipt` cannot be constructed from a host timer (compile-fail).
- [ ] A device tag alone earns zero operator coverage: the tagged-tensor forward creates no command buffer and adds no covered operator (the seed done-condition, second half).
- [ ] The three planted defects (`host-roundtrip`, `enqueue-timer`, `tag-counts`) are each caught and registered in the negative-control registry.
- [ ] Every fact in the re-read list is recorded at the pin with file and line; a fact that no longer holds is flagged in the record and opens a review of the Metal backend's interim posture.
- [ ] The run stays inside the machine envelope (well under 16 GiB, 8 cores, one hour) and starts under a timeout.
- [ ] INT-FT-02 has a row in `registries/gates.toml` and an admission record citing a receipt hash; `frob doctor --json` lists it under FD-FT.

## Test plan

### Unit tests
`cargo test -p frob-spark-metal --test admission_int_ft_02` on the Mac:
- `resident_across_two_command_buffers`: expected `a[i] == 2·(i+1)`; first differing index reported on failure.
- `allocated_bytes_stable`: B after batch 2 equals B₁.
- `receipt_kernel_counts`: 1, 1, 2.
- `receipt_device_seconds_positive_and_bounded`.
- `device_receipt_needs_completed_batch` (compile-fail), `output_not_readable_before_submit` (compile-fail).
- `tagged_tensor_creates_no_command_buffer`, `tagged_tensor_zero_coverage`, `tagged_equals_cpu_forward`.
- `mutant_host_roundtrip_caught`, `mutant_tag_counts_caught` (each behind a test-only feature).
- `thread_execution_width_read_from_pipeline`: the dispatch uses a thread-group size that is a multiple of the reported width.
On hosts without Metal the tests report `skipped: backend absent`, which is recorded as `not run`, never as a pass.

### End-to-end script and logging
`scripts/e2e/suite_admission_m0.sh` (bead N33b-20), step `int_ft_02`: runs the test binary, then
`frob spark probe --backend gpu-metal --json` and `frob doctor --json`, and asserts that the FD-FT foundation shows
INT-FT-02 with its record and that the probe's coverage table has no operator without a device receipt. Logged per
STD-E2E: command, exit code, wall time, evidence block, metrics `resident_mismatches` (threshold 0),
`device_seconds`, `host_seconds`, `tag_only_covered_operators` (threshold 0), the device name and fingerprint id,
and on failure the first differing element.

### Known answers and negative controls
Known answer: (i + 1)·2 on 4,096 integers, exact. Negative controls: the three planted defects above. Metamorphic:
doubling the buffer length or swapping the two kernels' order changes the expected values to the corresponding
closed form ((2·i) + 1 for the swapped order) and nothing else. Determinism: two runs give identical read-backs;
`device_seconds` is a measurement and is not compared.

## Considerations

- RISK-08: the gateway is synchronous, takes at most 31 buffer arguments, binds at offset zero and compiles from source only. The consequences (packed slabs with an offset table, one batch per chunk, one blocked host thread per device, a watchdog on the wait) are the Metal backend's design and are not tested here; this bead only records that the limits are still as read.
- A failed batch is reported and not re-run and its outputs are undefined. The backend's commit fence (two committed slabs, `K-commit`, at most four attempts, then `FROB-REF-607`) depends on that fact; if the re-read shows it changed, the fence design is reviewed.
- "When another process hangs the GPU, macOS restarts it and aborts every command buffer in flight" (FACT, the gateway's `lib.rs`): a transient failure of this test is recorded with its terminal state and re-run, never silently retried inside the test.
- Upstream work item FD-FT-01 (P1) will add asynchronous completion, an interruptible wait, typed buffers, byte-offset binding and richer receipts. Its switch-over rule re-runs INT-FT-01 and INT-FT-02; clause 2 then gains per-kernel timing. FD-FT-02 (real device execution for tensors) would change clause 3; the rule "coverage from receipts only" stays.
- Admission is never inherited: when the pin moves, this test is re-run by the compatibility train and a new record is written.
