## Background

The studio loop is edit, check, compare, repeat. An agent changes one parameter of a design and asks for the
preflight again; most analyses read fields the edit did not touch. Memoization of the compiled model already
exists in the model compiler. This bead extends it to everything downstream: **one content-addressed graph that
sits in front of every verb's executor**, so that an edit recomputes only the analyses whose inputs changed.

Three rules shape the design, each learned from a failure:

1. **Keys are derived, not written.** A key is generated from the declared inputs of its node kind. The failure
   this prevents is a missing input: in an executed pilot (FACT), a reuse key that omitted the delivery time of an
   observation kept a promotion that the edit had revoked (the "stale promotion"). A hand-written key will
   eventually omit a field.
2. **Hits are bit-identical or not served** (invariant INV-ATEL-08). Results are placed by index and random
   streams are keyed by address, so a hit equals a recomputation bit for bit inside its determinism class. A
   result that is merely close is not a hit.
3. **The cache checks itself in production.** One hit in 64 is recomputed and compared. One digest mismatch stops
   serving that node kind and files a determinism violation. FACT: the sibling crate `fs-recompute` uses the same
   trip-wire pattern (`StoreError::DeterminismViolation`).

Where it lives (rule L-11, the two planes): kernels and the step never depend on a memo policy. The `Memo` trait
is declared in `frob-core`, the graph wraps each verb's executor in `frob-verbs`, and the bytes are stored in
`frob-chronicle`, through the node record and `Recompute` trait of bead N33b-15 (the sibling crate if its
admission passed, otherwise the local record).

Gate (TARGET): the analysis part of GATE-ATEL-12, due at M1: proof obligation PO-ATEL-07 holds (incremental
evaluation with the memo graph equals full recomputation, on 10⁴ random edit sequences, with shadow recomputation
in production); a shadow mismatch stops serving within one hit; `design check` after a one-parameter edit returns
in 0.2 / 0.5 / 1.0 s at the 50th / 95th / 99th percentile. The episode part of the gate is BD-220 at M2. This
bead also completes group gate INT-FSIM-16 by running its known answer and negative control through the
production graph.

Rejected alternatives: per-verb ad hoc caches (no shared policy, no shared shadow, and every one a new place to
omit an input); tolerance-level reuse for everything (FACT: `fs-recompute::Store::can_skip` can serve a node
cached under a looser requirement; that is allowed only for analyses that record an achieved error, never for
episodes); a cache that blocks when full (the store evicts and never blocks).

## Technical approach

**Node kinds (the whole table; this bead implements the rows marked M1).**

| Node kind | Key | A hit is served within | Note |
|---|---|---|---|
| Subterm compile | Subterm content hash, compiler version, card versions | D0 | Owned by the model compiler; indexed here |
| Analysis (M1) | The model identity restricted to the fields the analysis reads; analysis version; parameters | D0 | An edit outside those fields recomputes nothing |
| Controller synthesis (schema at M1) | Model identity, task interface, synthesis version | D0 or same-backend D2 | |
| Step plan | Shape class: topology bucket, capacities, contact law, sensor layout | — | A parameter edit recompiles nothing |
| Kernel binary | Kernel source hash, compiler, driver, device family | — | The binary cache of the GPU layer |
| Scene compile (schema at M1) | Scene identity, compiler version | D0 | |
| Episode (M2) | Model, scene, task, controller or policy, world address, tier, kernel versions, effort profile, device family | Same-backend D2; D1 where the device family holds it | Never across a D3 boundary |
| Comparison, summary | The identities of its inputs and the rule version | Derived | Recomputed from memoized episodes |

```rust
// DESIGN: intent, not signatures.
pub trait Memo {                                                   // frob-core
    fn lookup(&self, kind: NodeKind, key: &Blake3) -> MemoAnswer;  // Hit(record) | Miss | Disabled(kind)
    fn store(&self, node: NodeRecord) -> StoreAnswer;              // Stored | Identical | Violation
}
pub trait MemoKeyed {                                              // implemented by derive, per node kind
    const KIND: NodeKind; const VERSION: u32;
    fn declared_inputs(&self) -> InputList;                        // ordered, typed, canonical bytes
    fn key(&self) -> Blake3 { blake3(KIND, VERSION, self.declared_inputs().canonical_bytes()) }
}
pub enum Disposition { Hit, Miss, Shadowed { equal: bool }, Disabled, NoMemo }
```

**Key derivation.** `#[derive(MemoKeyed)]` on a request type lists its declared inputs; no executor builds a key
by hand, and `xtask check-generated` regenerates the schema listing. For an analysis the model input is a
*restricted identity*: the BLAKE3 hash of the canonical bytes of exactly the model fields named in the analysis's
field mask (for the mass roll-up: masses, centres of mass, inertias, the tree; not actuator cards, not sensors).

**Read tracking (how the mask is kept honest).** Analyses receive the model through `TrackedModel`, a view that
records every field path read. Two property tests exist per node kind:
1. *Declared-input test*: perturb each declared input in turn; the key must change.
2. *Live-dependency test*: perturb each field of the model in turn (every field, not only declared ones); either
   the key changes or the output digest is unchanged. In debug builds the wrapper also asserts that the read set
   of each execution is contained in the mask and fails the call otherwise.

**Serving.**
1. The wrapper computes the key and calls `lookup`.
2. *Miss*: run the executor, store the record (kind, key, inputs, output digest, class D0, measured cost, stack
   receipt), return with disposition `Miss`.
3. *Hit*: if the shadow selector fires (below), run the executor anyway and compare digests. Equal: serve, with
   `Shadowed { equal: true }`. Different: do not serve the stored result; return the fresh one; **disable the
   node kind** (every later lookup of the kind answers `Disabled` and executes); write a determinism-violation
   record with both digests, the key, the declared inputs and the read set; surface it in `frob doctor` and in
   the gate status. Re-enabling a kind is an explicit administrative action after the kind's version is bumped.
4. Otherwise serve the stored bytes with disposition `Hit`. The envelope's evidence is that of the stored result;
   a hit never upgrades a class.

**Shadow selector (DESIGN).** One hit in 64. The selector is deterministic and reads no clock: each node kind has
a hit ordinal n and a phase p = the low six bits of BLAKE3(kind, kind version); a hit is shadowed when
(n + p) mod 64 = 0. Every window of 64 consecutive hits of a kind therefore contains exactly one shadowed hit,
which is what bounds detection of a stale key to 64 hits. (A choice by key hash alone could leave one repeatedly
requested stale key unshadowed forever.)

**Loss model (recorded in the memo policy's contract).** States: valid hit, stale hit, miss. Actions: serve,
recompute, shadow. A stale result served costs 100 units against the GPU-seconds of a needless recomputation
(DESIGN ratio). Consequence: when in doubt the policy recomputes; a kind is never re-enabled automatically.

**Store policy.** Budget 64 GB by default (DESIGN); on exhaustion the store evicts and never blocks. Eviction is
S3-FIFO with admission weighted by recompute cost, because misses are not equally expensive (the policy bead is
BD-220; until then, least recent use weighted by cost). Nodes in the evidence closure of a live claim are pinned.
Tolerance-level reuse is allowed only for analyses that record an achieved error. The store can be deleted at any
time without losing a result that a claim cites, because cited evidence is pinned in Chronicle, not in the cache.

**Rollout and rollback.** Stage 1, *shadow only*: every lookup executes; would-be hits are compared and counted;
nothing is served. Stage 2: D0 analyses are served. Stage 3 (BD-220): D2 episodes. `--no-memo` on any verb
disables serving for that call (disposition `NoMemo`). The baseline for every comparison is full recomputation
per verb with compile-only memoization.

**What reuse to expect.** A controller-only edit reuses every model analysis; a mass or geometry edit reuses no
rollout and only the analyses whose masks exclude the edited fields; a comparison that follows a run of the
previous version on the same scene reuses that version's episodes at the comparison's addresses (M2).

Evidence: a served result carries the claim, class and determinism of the stored result; the memo graph adds no
claim of its own. Recorded in the ledger: every node record, every shadow comparison, every violation.

## Acceptance criteria

- [ ] PO-ATEL-07: over 10⁴ seeded random edit sequences on the first archetypes, `design check` through the memo graph returns byte-identical results to full recomputation after every edit.
- [ ] A shadow mismatch stops serving within one hit: with a planted key that omits one input, the first shadowed stale hit disables the kind, and no stale result is returned after it (the seed done-condition, analysis part of GATE-ATEL-12).
- [ ] INT-FSIM-16 through the production graph: incremental equals full on the 10⁴ sequences; the missing-input control is caught within 64 hits (the seed done-condition).
- [ ] Each analysis node kind passes its declared-input test and its live-dependency test; in debug builds a read outside the mask fails the call.
- [ ] A one-parameter edit outside an analysis's mask recomputes nothing for that analysis (disposition `Hit`); inside the mask it recomputes exactly that analysis and its dependants.
- [ ] `--no-memo` returns identical bytes with disposition `NoMemo`; deleting the store between two calls changes no result.
- [ ] `design check` after a one-parameter edit: measured 50th, 95th and 99th percentile latencies are recorded against the targets 0.2, 0.5 and 1.0 s on the first archetypes.
- [ ] The envelope reports the disposition; a hit's evidence block equals the stored result's.
- [ ] `CONTRACT.md` sections for the memo policy state the loss ratio, the shadow rate, the budget and the safe mode (`--no-memo`); the gate rows are recorded with measured values.

## Test plan

### Unit tests
`cargo test -p frob-verbs memo` and `-p frob-core memo`:
- `key_changes_for_each_declared_input` (per kind); `live_dependency_key_or_output` (per kind, every model field).
- `read_outside_mask_fails_in_debug`: an analysis with a deliberately narrowed mask.
- `miss_then_hit_bytes_equal`; `hit_evidence_equals_stored`.
- `shadow_window_has_exactly_one`: for 10 kinds and 6,400 hits each, every window of 64 has one shadowed hit.
- `shadow_mismatch_disables_kind_within_one_hit`: a planted stale key; after the mismatching shadow, the next lookup answers `Disabled`.
- `violation_record_has_both_digests_and_read_set`.
- `no_memo_flag_bypasses`; `store_deleted_between_calls_same_result`.
- `edit_outside_mask_recomputes_nothing`: edit a sensor mount; the mass roll-up is a hit. `edit_inside_mask_recomputes_dependants`: edit a link mass; mass roll-up and static stability recompute, the symmetry analysis's disposition follows its mask.
- `incremental_equals_full_1e4` (long lane): PO-ATEL-07.
- `loss_ratio_in_contract`: the contract record states 100 and the test reads it.
- Planted defects, each caught: `hand-written-key` (omits the analysis version), `serve-on-mismatch` (serves the stored result after a mismatch), `shadow-never` (selector disabled).

### End-to-end script and logging
`scripts/e2e/memo_graph_design_check.sh`: on archetype `quad-mammal`, (1) `frob design check --json` cold; (2) the
same again, expecting hits; (3) `frob design edit … set-mass …` then `design check`, expecting recomputation of the
mass-dependent analyses only; (4) `design check --no-memo`, expecting byte-identical results; (5) a run with the
planted stale-key feature, expecting a determinism violation in `frob doctor --json` and no stale output; (6) 200
one-parameter edits for the latency percentiles. Logged per STD-E2E: command, exit code, wall time, evidence
block, per-call `disposition` counts, metrics `check_latency_p50_s`, `_p95_s`, `_p99_s` (targets 0.2, 0.5, 1.0),
`stale_results_served` (threshold 0), `hits_until_disable` (threshold ≤ 64), result digests for the equality
checks, and on failure the first differing analysis with both digests. Summary names GATE-ATEL-12 and INT-FSIM-16.

### Known answers and negative controls
KA-771 (incremental equals full on 10⁴ edit sequences; a missing input is caught within 64 hits). The four-state
revalidation fixture is the origin of rule 1: a key without delivery time keeps a stale promotion. Negative
controls: the three planted defects and the missing-input kind. Metamorphic: two edits that commute give the same
final dispositions and bytes in either order; an edit followed by its inverse returns every analysis to a hit on
its original node. Determinism: results and dispositions are identical twice on one machine, across worker
counts, and in debug and release; a study statistic does not depend on memo hits (INV-ATEL-02), tested by running
one comparison with and without `--no-memo`.

## Considerations

- OPEN-ATEL-3: whether the sibling store is admitted on the toolchain T. The graph is written against the trait, so the answer changes one constructor.
- The latency targets are unmeasured TARGETs. The gate's latency figures govern its Performance reading; the equality and stop-on-mismatch clauses are its Known-answer reading.
- A disabled kind degrades latency, never correctness. A kind that is disabled twice is a design defect of its key schema, and the fix is a schema change with a version bump.
- Memory: analysis results are small; the 64 GB budget matters for episodes at M2. On exhaustion the store evicts; it never blocks a verb and never grows without bound.
- Privacy: node records inherit the private mark of their inputs; a memo hit never crosses a namespace, because the namespace is part of the model and scene identities.
- Interaction with revalidation: the memo graph answers "is this exact computation already done"; "does this verdict survive the edit" is a different question with its own engine and grades.
