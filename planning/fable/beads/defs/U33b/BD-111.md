## Background

The studio loop is edit, check, compare, repeat. An agent changes one parameter of a design and asks for the
preflight again; most analyses read fields the edit did not touch. Memoization of the compiled model already
exists in the model compiler. This bead extends it to everything downstream: **one content-addressed graph that
sits in front of every verb's executor that computes a node kind** (the registry marks those entries
`memo = true`; a verb that computes none has nothing to serve), so that an edit recomputes only the analyses whose
inputs changed.

Three rules shape the design, each learned from a failure:

1. **Keys are derived, not written.** A key is generated from the declared inputs of its node kind. The failure
   this prevents is a missing input: in an executed pilot (FACT), a reuse key that omitted the delivery time of an
   observation kept a promotion that the edit had revoked (the "stale promotion"). A hand-written key will
   eventually omit a field.
2. **Hits are bit-identical or not served** (invariant INV-ATEL-08). Results are placed by index and random
   streams are keyed by address, so a hit equals a recomputation bit for bit inside its determinism class. A
   result that is merely close is not a hit.
3. **The cache checks itself in production.** One hit in 64 is recomputed and compared. One digest mismatch stops
   serving that node kind and files a determinism violation. FACT: the sibling crate `fs-recompute` uses the same
   trip-wire pattern (`StoreError::DeterminismViolation`).

Where it lives (rule L-11, the two planes): kernels and the step never depend on a memo policy. The `Memo` trait
is declared in `frob-core`, the graph wraps each verb's executor in `frob-verbs`, and the bytes are stored in
`frob-chronicle`, through the node record and `Recompute` trait of bead N33b-15 (the sibling crate if its
admission passed, otherwise the local record).

The parts are owned by separate beads finished before this one: the trait, the node-kind registry, key
derivation and the two generated key tests are N28b-37's; the serve decision, the memo graph's one shadow selector,
the stop latch, the one lift rule, the loss model and the rollout modes are N28b-38's
(`crates/frob-chronicle/src/memo/`); the storage record is N33b-15's. Eviction under the byte budget (N33c-18,
N33c-19) and its differential oracle (N33c-20) follow this bead within M1; until they land, N28b-38's store
refuses admission at the budget and never blocks. This bead puts the parts in front of every analysis executor
and proves the assembly through the production graph. Their rules are restated below so that this bead reads alone; where a restatement and the
owning bead differ, the owning bead governs.

Gate (TARGET): the analysis part of GATE-ATEL-12, due at M1: proof obligation PO-ATEL-07 holds (incremental
evaluation with the memo graph equals full recomputation, on 10⁴ random edit sequences, with shadow recomputation
in production); a shadow mismatch stops serving within one hit; `design check` after a one-parameter edit returns
in 0.2 / 0.5 / 1.0 s at the 50th / 95th / 99th percentile. This bead owns the clause its seed names (a shadow
mismatch stops serving within one hit, through the production graph). The PO-ATEL-07 battery over 10⁴ design-edit
sequences, the latency protocol and the gate row with measured values are N28b-40's, which depends on this bead
and runs on the graph it wires; this bead runs smaller lanes of both. The episode part of the gate is BD-220 at
M2. This bead also runs group gate INT-FSIM-16's known answer and negative control through the production graph;
the gate's admission record and row are N33b-15's (one recorder per gate), and this run is a test of the assembly
that writes no gate row.

Rejected alternatives: per-verb ad hoc caches (no shared policy, no shared shadow, and every one a new place to
omit an input); tolerance-level reuse for everything (FACT: `fs-recompute::Store::can_skip` can serve a node
cached under a looser requirement; that is allowed only for analyses that record an achieved error, never for
episodes); a cache that blocks when full (the store evicts and never blocks).

## Technical approach

**Node kinds (the whole table, registered by N28b-37; this bead serves the row marked M1).**

| Node kind | Key | A hit is served within | Note |
|---|---|---|---|
| Subterm compile | Subterm content hash, compiler version, card versions | D0 | Owned by the model compiler; indexed here |
| Analysis (M1) | The model identity restricted to the fields the analysis reads; analysis version; parameters | D0 | An edit outside those fields recomputes nothing |
| Controller synthesis (schema at M1) | Model identity, task interface, synthesis version | D0 or same-backend D2 | |
| Step plan | Shape class: topology bucket, capacities, contact law, sensor layout | — | A parameter edit recompiles nothing |
| Kernel binary | Kernel source hash, compiler, driver, device family | — | The binary cache of the GPU layer |
| Scene compile (schema at M1) | Scene identity, compiler version | D0 | |
| Episode (M2) | Model, scene, task, controller or policy, world address, tier, kernel versions, effort profile, device family | Same-backend D2; D1 where the device family holds it | Never across a D3 boundary |
| Comparison, summary | The identities of its inputs and the rule version | Derived | Recomputed from memoized episodes |

The types this bead consumes (N28b-37's, restated): per node kind, `impl Memo` with `type Inputs:
DeclaredInputs` (derived; every field with its path), `type Output: Canonical`, `const KIND: MemoKind` (registry
row: name, version, serve class) and `fn compute(inputs: &Tracked<Self::Inputs>, cx) -> Result<Output, Refusal>`;
the node record is N33b-15's `NodeRecord` (one struct in `frob-core`: `kind`; `key`; `inputs`, the content hashes
of the whole inputs in declared order; `reads`, every field the computation actually read, with its value hash;
`deps`; `output`, the result digest; `class`; `device_family`; `achieved_error` where the kind records one;
`cost`; `stack_receipt`), stored through N33b-15's `Recompute` trait. The name `MemoNode` of earlier drafts is
retired; there is no second node type. There is no API that accepts a key from a caller. This bead adds, in
`crates/frob-verbs/src/memo.rs`:

```rust
// DESIGN: intent, not signatures.
pub enum Disposition { Hit, Miss, Shadowed { equal: bool }, Disabled, NoMemo }
// Hit: served from the store; Miss: computed and stored; Shadowed: a hit recomputed by the selector
// (the recomputed result is returned); Disabled: a hit of a latched kind, computed; NoMemo: --no-memo.
pub struct FieldMask(ReadSet);   // per analysis: its declared reads() (N28a-04); enters the key (below)
```

**Key derivation (N28b-37's rule, restated).** Keys are derived from the declared inputs; no executor builds a key
by hand, and `xtask check-generated` regenerates the schema listing. For an analysis the declared model input is
its read set, the field paths it declares in `reads()` (N28a-04's analysis contract): the *restricted identity* is
the BLAKE3 of the sorted (path, value hash) pairs of every declared field, taken from the model, and the key is
the hash of (kind, kind version, parameters, restricted identity, the card versions those fields name). Lookup is
by that key alone. (DESIGN, made in N28b-37: an earlier draft keyed on the fields actually read on one input, with
a two-step lookup; the plan generates keys from the declared inputs, and the declared-input test is meaningful
only for a declared set.) A declared field that a data-dependent computation did not read on some input stays in
the key; that costs a recomputation, never a stale hit. For the mass roll-up the read set is masses, centres of
mass, inertias and the tree, never actuator cards or sensors.

**Read tracking and the declared mask (this bead).** Each analysis's `FieldMask` is its declared `reads()` (for
the mass roll-up: masses, centres of mass, inertias, the tree); it enters the key as above and says what reuse to
expect. The computation still receives a `Tracked` model view: the fields actually read are recorded in the node's
`NodeRecord.reads`, and in debug builds the wrapper asserts that they are contained in the mask and fails the
call otherwise (a read outside the mask is either a mask to widen or a dependency nobody expected; it is also a
contract-test failure). N28b-37's generated tests run for every analysis kind this bead wires and every template
model: declared-input test (perturb each declared field, the key must change); live-dependency test (perturb
every field of every template model, either the key changes or the output digest is unchanged); and the
efficiency test (a field outside the declared read set leaves the key unchanged, so an unrelated edit really
recomputes nothing).

**Serving (the wrapper's steps; steps 1 and 3 call N28b-38's policy).**
1. With `--no-memo`: do not look up; run the executor; still store the node (so the flag can refresh or
   cross-check the store); disposition `NoMemo`.
2. The wrapper derives the key and looks it up. *Miss*: run the executor under tracking, store the `NodeRecord`
   (kind, key, inputs, the reads actually recorded, output digest, class D0, measured cost, deps, stack
   receipt), return with disposition `Miss`.
3. *Hit candidate* (a node stored under the key): N28b-38's serve decision runs (mode gate, latch, class gate,
   tolerance reuse for analyses that record an achieved error). A latched kind is computed, disposition `Disabled`. If the shadow selector
   fires (below), run the executor anyway and compare digests. Equal: return the recomputed result, with
   `Shadowed { equal: true }`. Different: do not serve the stored result; return the fresh one, with
   `Shadowed { equal: false }`; N28b-38's latch is set for the kind in the same ledger transaction (every later
   candidate hit of the kind, in any session, answers `Disabled` and executes); the determinism-violation record
   carries both digests, the key, the declared inputs and the read set; it is surfaced in `frob doctor` and in
   the gate status. The latch is a ledger record and survives restarts. Re-enabling is the lift rule below.
4. Otherwise serve the stored bytes with disposition `Hit`. The envelope's evidence is that of the stored result;
   a hit never upgrades a class.

The envelope's cost block carries N28b-38's `memo: { hit, served, shadowed, key }` and this bead's
`disposition`, so that a reader need not combine three booleans.

**The registry field `memo` and the generated `no_memo` (this bead; DESIGN where marked).** The wrapper fronts an
executor only where the registry says so. In one change this bead:
1. adds the row `memo` to N32a-02's later-field table, with its member on the emitted entry type: type bool,
   default `false`; rule: `true` on an entry whose executor the memo graph fronts, and dispatch wraps exactly
   the executors of those entries (an entry without it is never looked up, stored or shadowed); lint
   `memo-kind` (DESIGN): `memo = true` only on an entry whose kind is `read` or `run`, because a `mutate` or
   `admin` call changes state and is never served from a store;
2. writes NJL-01's variation 14 arm in `crates/frob-verbs/src/registry/derive.rs`: an entry with `memo = true`
   gets the generated input `no_memo` (boolean, default false; CLI `--no-memo`; outside every identity, since a
   served product is bit-identical to a computed one): nothing is served from the memo graph for that call in
   any store mode, every node is computed and still stored, and the disposition is `NoMemo`; no code is
   appended; an entry without the field gets nothing, so no verb offers a `--no-memo` that would do nothing;
3. sets `memo = true` on the rows in `registries/verbs.toml` at its change whose executors the wrapper fronts:
   `design.check` and `design.show` (VERBS-design) and `sim.run` (VERBS-sim), and `eval.run` and `eval.compare`
   (VERBS-eval) if their rows are already entered; a row among them that declares `no_memo` of its own drops it
   in the same change, since beside `memo = true` it fails NJL-01's lint `common-property-shadowed`.
A fronted row entered after this change carries `memo = true` from the change that enters it (NJL-01's staging
rule): `eval.run` and `eval.compare` if VERBS-eval's rows land later, `study.submit` (its row is entered at M1 by
a bead that depends on this one) and `train.start` (VERBS-train, M2).

**Shadow selector (N28b-38's, restated; the one selector of the memo graph, implemented in its `shadow.rs` and
called unchanged here, by BD-220's episodes, N28b-41's digest classes and N17b-13's cross-design kinds).** One
hit in 64, deterministic, reading no clock. Each *node* has a durable hit ordinal n: a per-node counter in the
memo store (`frob-chronicle`), incremented in the same ledger transaction that serves the hit, so it survives
restarts and two processes never draw the same ordinal (a CLI process that serves three hits and exits still
advances the window). Its phase is p = the low six bits of BLAKE3(kind ‖ kind version ‖ key). A hit is shadowed
when (n + p) mod 64 = 0. Every window of 64 consecutive hits of one node holds exactly one shadowed hit, so a
stale node is found within 64 of its own hits however it is requested; among keys hit once each, one in 64 is
chosen by key hash, which is the plan's wording ("one hit in 64, chosen by key hash"). Rejected: the key alone
(63 of 64 nodes are never shadowed however often they are served); one ordinal per *kind* (two keys of one kind
requested alternately, as when an agent re-checks designs A and B in turn, put every hit of one key on even
ordinals and the other's on odd ones, so one of them is never shadowed); a fresh hash per hit (right rate, no
bound: a node goes 64 hits unshadowed with probability (63/64)⁶⁴ ≈ 0.37). Two selectors over one store would
shadow different hits and leave each other's blind spots, so no caller adds another.

*Batched lookups.* When one verb call looks up many nodes at once (a `design check` that runs every analysis in
parallel, and BD-220's episode batches), the call reserves, at planning and in one store transaction, the next
ordinal of every node the batch will hit (k ordinals for a node hit k times) and assigns them to the batch's hits
in (address, member) order, where an analysis batch's address is the analysis's registry order. The shadowed
hits therefore do not depend on the order in which workers finish, and a replayed batch shadows the same hits.

**Lift rule (N28b-38's, restated; the one re-enable rule of the memo graph).** A latched kind serves again only
through the explicit call `Memo::reenable(kind, explanation)`, which appends a `memo-reenable` ledger record. It is
accepted
only when the explanation record names the violation it answers (by its record id), the cause, the fix (for a
key-schema defect: the new kind version; for a nondeterministic computation: the changed code identity; for a
cause outside the kind, such as a corrupted store entry: the purge of the offending entries), and carries a re-run
of the mismatching node under the fixed code that equals the fresh result byte for byte twice. A restart, a store
deletion or a bare version bump does not lift it, and nothing lifts it automatically (the loss model's
consequence). The plan's "until it is explained" (§17.11) is this record. The command-line surface of the call is
not in the verb registry (OPEN, Atelier lead; fail-closed default: no surface, so a disabled kind stays disabled,
which costs latency and never correctness).

**Loss model (N28b-38's, recorded in the memo policy's contract).** States: valid hit, stale hit, miss. Actions:
serve, recompute, shadow. A stale result served costs 100 units against the GPU-seconds of a needless
recomputation (DESIGN ratio). Consequence: when in doubt the policy recomputes; a kind is never re-enabled
automatically.

**Store policy (N28b-38's clause; its mechanism is N33c-18 and N33c-19 at M1).** Budget 64 GB by default
(DESIGN); on exhaustion the store evicts and never blocks: a write that cannot be admitted is not cached, and the
verb returns its computed result. Eviction is the S3-FIFO state machine over content hashes of N33c-18, with
admission weighted by recompute cost (N33c-19), because misses are not equally expensive; its fallback, if the
differential oracle INT-FSQL-02 (N33c-20) fails, is least-recently-used with the same cost-weighted admission,
never an unbounded store. Nodes in the evidence closure of a live claim are pinned. Tolerance-level reuse is
allowed only for analyses that record an achieved error. The store can be deleted at any time without losing a
result that a claim cites, because cited evidence is pinned in Chronicle, not in the cache. Analysis results are
small, so this bead never reaches the budget in its tests; the wrapper relies only on the never-waiting
`admit(node) → Admitted | NotCached(reason)` interface.

**Rollout and rollback (N28b-38's store modes).** `off` (the baseline: compile-only memoization), then `shadow`
(every candidate hit is recomputed and compared; nothing is served), then `analyses` (D0 analysis, compile and
scene nodes served; the mode this bead brings into use), then `episodes` (BD-220). Advancing a mode needs the
previous mode's shadow record (zero mismatches over at least 10⁴ shadowed hits per kind, under the release
profile); test harnesses use the `test` store profile. `--no-memo` on any verb whose entry has `memo = true`
disables serving for that call (disposition `NoMemo`). The baseline for every comparison is full recomputation per verb with compile-only
memoization.

**What reuse to expect.** A controller-only edit reuses every model analysis; a mass or geometry edit reuses no
rollout and only the analyses whose masks exclude the edited fields; a comparison that follows a run of the
previous version on the same scene reuses that version's episodes at the comparison's addresses (M2).

Evidence: a served result carries the claim, class and determinism of the stored result; the memo graph adds no
claim of its own. Recorded in the ledger: every node record, every shadow comparison, every violation.

## Acceptance criteria

- [ ] PO-ATEL-07, smoke lane: on 100 fixed edit sequences (1 to 20 edits each, over parameter, mass, sensor-mount, rename and inverse edits) on the first archetypes, `design check` through the memo graph returns byte-identical results to full recomputation after every edit. The 10⁴-sequence battery and its gate row are N28b-40's and run on this bead's graph.
- [ ] A shadow mismatch stops serving within one hit: with a planted key that omits one input, the first shadowed stale hit latches the kind, and no stale result is returned after it (the seed done-condition, analysis part of GATE-ATEL-12).
- [ ] INT-FSIM-16 through the production graph: N33b-15's synthetic 48-node known answer, registered as test-only analysis kinds and evaluated through the production wrapper and N28b-38's policy, gives incremental equal to full on 10⁴ seeded sequences; the missing-input control, requested repeatedly, is caught by the selector within 64 hits of the stale node (the seed done-condition).
- [ ] A batched `design check` shadows the same hits whatever order its workers finish in (ordinals reserved at planning in one store transaction, assigned in registry order).
- [ ] Each analysis node kind passes its declared-input test, its live-dependency test and the efficiency test, with the key derived from its declared `reads()` and looked up by key alone; every stored `NodeRecord.reads` is contained in the declared set; in debug builds a read outside the mask fails the call.
- [ ] A one-parameter edit outside an analysis's mask recomputes nothing for that analysis (disposition `Hit`); inside the mask it recomputes exactly that analysis and its dependants.
- [ ] `--no-memo` returns identical bytes with disposition `NoMemo`; deleting the store between two calls changes no result.
- [ ] `design check` after a one-parameter edit: 50th, 95th and 99th percentile latencies over 20 edits on `quad-mammal` are logged against the targets 0.2, 0.5 and 1.0 s as an early reading (the gate's protocol, 1,000 edits per template with the disclosure block, is N28b-40's).
- [ ] The envelope reports `memo: { hit, served, shadowed, key }` and the disposition; a hit's evidence block equals the stored result's.
- [ ] The shadow ordinal is durable and per node, through the production wrapper: across 64 separate processes each serving one hit of one analysis node, exactly one hit is shadowed; two keys of one analysis kind requested alternately 6,400 times each are each shadowed exactly 100 times; two concurrent processes never draw the same ordinal.
- [ ] The lift rule holds: `Memo::reenable` is rejected without an explanation record, with one whose re-run still mismatches, or after only a restart, a store deletion or a version bump; it is accepted with a matching re-run, and the `memo-reenable` record is in the ledger.
- [ ] `CONTRACT.md` sections for the memo policy state the loss ratio, the shadow rate, the budget and the safe mode (`--no-memo`). This bead writes no gate row: GATE-ATEL-12's row is N28b-40's and INT-FSIM-16's is N33b-15's (one recorder per gate); the measured values of its lanes are in its script's log for them.
- [ ] The field `memo` is a row of N32a-02's later-field table with its member and the lint `memo-kind`, added in one change with the variation 14 arm of `derive.rs`: an entry with `memo = true` has the generated `no_memo` (boolean, default false, CLI `--no-memo`) and no appended code; an entry without it has no `no_memo`; `design.check`, `design.show` and `sim.run` (and the eval rows present at the change) carry `memo = true` and declare no `no_memo` of their own; dispatch fronts with the wrapper exactly the executors of entries with `memo = true`.
- [ ] No cache across pins, through the production wrapper (N33a-06's rule): a result of an analysis kind whose executor names an airlock trait, stored under stack-lock digest A, is a miss under digest B (disposition `Miss`, the executor runs, nothing stored under A is served), and is a hit again under A.

## Test plan

### Unit tests
`cargo test -p frob-verbs memo` and `-p frob-core memo`:
- `key_changes_for_each_declared_input` (per kind); `live_dependency_key_or_output` (per kind, every model field);
  `field_outside_reads_keeps_key` (per kind: editing an undeclared field leaves the key unchanged).
- `read_outside_mask_fails_in_debug`: an analysis with a deliberately narrowed mask.
- `node_record_reads_within_declared_set`: after a cold `design check`, every stored `NodeRecord` of an analysis
  kind has `reads` contained in that kind's `reads()`, and its key equals the key re-derived from `reads()`.
- `miss_then_hit_bytes_equal`; `hit_evidence_equals_stored`.
- `shadow_window_has_exactly_one`: through the wrapper, for one node of each of 10 analysis kinds hit 6,400 times, every window of 64 consecutive hits of the node has exactly one shadowed hit; two keys of one kind requested alternately 6,400 times each are shadowed 100 times each (the per-kind-ordinal mutant shadows one of them 0 times and fails).
- `shadow_ordinal_survives_restart`: 64 store reopenings with one hit of one node each give exactly one shadowed hit; two threads drawing 6,400 ordinals of one node concurrently get 6,400 distinct ordinals and exactly 100 shadowed hits.
- `batch_shadow_independent_of_completion_order`: a `design check` batch of 12 analyses (3 hit twice) served by 8 workers finishing in 50 random orders shadows the same hits every time.

- `violation_record_has_both_digests_and_read_set`.
- `no_memo_flag_bypasses`; `store_deleted_between_calls_same_result`.

### Known answers and negative controls
KA-771 (incremental equals full on 10⁴ edit sequences; a missing input is caught within 64 hits). The four-state
revalidation fixture is the origin of rule 1: a key without delivery time keeps a stale promotion. Negative
controls: the three planted defects and the missing-input kind. Metamorphic: two edits that commute give the same
final dispositions and bytes in either order; an edit followed by its inverse returns every analysis to a hit on
its original node. Determinism: results and dispositions are identical twice on one machine, across worker
counts, and in debug and release; a study statistic does not depend on memo hits (INV-ATEL-02), tested by running
one comparison with and without `--no-memo`.

## Considerations

- OPEN-ATEL-3: whether the sibling store is admitted on the toolchain T. The graph is written against the trait, so the answer changes one constructor.
- The latency targets are unmeasured TARGETs. The gate's latency figures govern its Performance reading; the equality and stop-on-mismatch clauses are its Known-answer reading.
- A disabled kind degrades latency, never correctness. A kind that is disabled twice is a design defect of its key schema, and the fix is a schema change with a version bump.
- Memory: analysis results are small; the 64 GB budget matters for episodes at M2. On exhaustion the store evicts; it never blocks a verb and never grows without bound.
- Privacy: node records inherit the private mark of their inputs; a memo hit never crosses a namespace, because the namespace is part of the model and scene identities.
- Interaction with revalidation: the memo graph answers "is this exact computation already done"; "does this verdict survive the edit" is a different question with its own engine and grades.
