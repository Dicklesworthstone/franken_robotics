## Background

FrankenRobotics stands on about seventeen sibling foundations. A program with that many dependencies is blocked
by whichever one converges last unless it says, in advance, **which milestone needs which foundation**. The plan
does: the dependency firewall. A blank cell means the milestone does not depend on the foundation. A cell in
parentheses is used if the foundation is admitted and is not required for the milestone to exit.

What the table guarantees, in the plan's words. M1 depends only on FrankenSim, asupersync and FrankenSQLite. If
the GPU, symbolic and proof foundations all failed admission, M1 would still ship a referee-tier design studio
and the first mission slice on the CPU. The mission slice needs no symbolic or proof sibling, because its
certificates are checked by the offline auditor `frob-verify`, which uses the standard library alone. Nothing in
the last five rows is on a critical path. The M0 column carries the two upstream work items at priority P0,
FD-FMCP-01 and FD-ASUP-01; neither is on M1's critical path: if the MCP admission cannot pass within the M0
budget, KILL-MCP's fallbacks apply and M1's verbs are reached through the command line. M7 freezes every pin and
the toolchain T for the length of the tournament, because a ratio of times measured across a pin move or a
toolchain train is not one measurement.

What a missing foundation costs, per milestone (the plan's fallbacks): M0, a failed admission is the result and
its fallback is decided there; M1, CLI only and no kernel certificates, with the mission slice unaffected; M2,
the no-GPU variant, KILL-KIR, KILL-METAL; M3, local implementations against the same known answers, KILL-MCP,
KILL-TUI, plain Three.js; M4, the numerical lane of KILL-SYNTH-LINKAGE and policies exchanged in the native
checkpoint format only; M5, KILL-LEMMA, KILL-REFLECT, KILL-INGEST and the Foundry kill gates; M6, the epic is
not funded; M7, a pin move or a toolchain train voids the runs it spans; M8, the epic is not funded.

A table in a document does not stop an optional dependency from becoming a required one by accident (a default
feature, a convenience import). This bead turns the table into data that a test reads (DESIGN). Rejected: a
seventh `xtask` subcommand (the tool has exactly six by rule, and a seventh needs a named defect class and the
owner's approval); a separate registry file (the foundation rows already exist in the stack lock).

## Scope

In: two fields on each foundation row of `franken-stack.lock`; the loader; the consistency test between the
firewall, the admission gates and the gate status file; the per-milestone report that exit reviews read.

Out: the stack lock's other fields and the resolution receipt (the first part of the chapter); the build-level
proof that M1 ships without the optional foundations (bead N33b-02); the M7 freeze (N33b-03); the exit reviews
themselves (BD-044, BD-147 and their successors).

## Technical approach

**1. Data (DESIGN).** Each `[[foundation]]` row gains:

```toml
required_at = ["M1", "M2", "M3", "M4", "M5", "M6"]     # the milestone cannot exit without it (or its kill decision)
optional_at = []                                       # used if admitted; the cells in parentheses
uses = { M0 = "admit; file tests", M1 = "referee, geometry, ledger, memo store; study statistics", M7 = "frozen pin" }
```

`M0` is implicit for every foundation whose admission gate is due at M0 ("admit"). `uses` carries the cell text
so that a report can print the table. The table above is the initial content, row for row; `frozen pin` at M7 is
recorded for frankensim and asupersync and applies to every pin through the freeze mechanism.

**2. Loader and validation** (`xtask`, inside `check-stack`'s existing parse of the stack lock, adding no
subcommand): an unknown milestone name, a milestone listed as both required and optional, or a foundation with
neither field is a load-time error.

**3. The consistency test** (`crates/frob-conformance/tests/firewall.rs`, run in the default lane; it reads files
and runs no physics):
1. For every foundation F and every milestone M in `required_at(F)`: F's row names an `admission_gate`, and that
   gate (or the group gate of the feature group first used at M) exists in `registries/gates.toml`.
2. For the milestone under review (passed as `FROB_MILESTONE`, default the current one in the gate file): every
   required foundation's gate has status `pass`, or `killed: fallback adopted` with the fallback text of the row
   recorded; any other status fails the test and names the foundation. An optional foundation's gate may have any
   status, and a `fail` or `not run` there is printed as "used only if admitted: not admitted".
3. No foundation has a gate record older than its last pin move (an admission is never inherited: the record's
   receipt must be the newest receipt that lists the foundation at its current revision).
4. The set of foundations required at M1 is exactly {frankensim, asupersync, frankensqlite}. This is a frozen
   assertion: changing it requires changing the test and is therefore a visible decision.
5. The last five rows of the table (frankentui, franken_threed, drone reconstruction, franken_textiles,
   franken_firmware) have empty `required_at`.

**4. The report.** `cargo xtask check-stack --report firewall` (an output mode of the existing subcommand) prints,
for a milestone, three lists: required and admitted; required and not admitted (with the kill gate and fallback
of each); optional with their status. Exit reviews attach this output.

Evidence: none is claimed; this is a structural check, determinism D0.

## Acceptance criteria

- [ ] Every foundation row of `franken-stack.lock` carries `required_at`, `optional_at` and `uses`, and the printed report reproduces the table above cell for cell.
- [ ] The consistency test passes on the real tree at M0 and fails each planted inconsistency: a required foundation whose gate is `not run` at the reviewed milestone; a foundation added to `required_at = ["M1"]` beyond the three; an admission record whose receipt predates the current pin; a parenthesized foundation marked required.
- [ ] `xtask` still has exactly six subcommands (its own test asserts this); the report is a mode of `check-stack`.
- [ ] The M0 exit review can run the report and obtain the list of admissions M0 owes: toolchain, FrankenSim (path consumption, the file-by-file tests, the worker fallback), asupersync, FrankenSQLite, FrankenTorch's Metal gateway, `cudarc`, FrankenSymPy, franken_numpy and fastmcp_rust.

## Test plan

### Unit tests
- `firewall_rows_complete`: every foundation has the three fields; unknown milestone names are rejected.
- `firewall_report_matches_fixture`: the rendered table equals a checked-in fixture of the table above.
- `m1_requires_exactly_three`: asserts the frozen set.
- `last_five_rows_never_required`.
- `required_gate_must_be_pass_or_killed`: synthetic gate files (labelled `synthetic`) for each status; only `pass` and `killed: fallback adopted` are accepted.
- `optional_gate_any_status_is_reported_not_failed`.
- `stale_admission_detected`: a record whose receipt lists an older revision fails.
- `both_required_and_optional_rejected`.

### End-to-end script and logging
`scripts/e2e/suite_firewall.sh` (shared with bead N33b-02): step `data` runs `cargo xtask check-stack --report
firewall --milestone M0` and the conformance test, then repeats on a scratch copy of the stack lock with one
planted inconsistency and expects failure. Logged per STD-E2E: command, exit code, wall time, metrics
`required_admitted`, `required_missing` (threshold 0 at an exit), `optional_admitted`, `planted_caught`, the hash
of the stack lock, and on failure the foundation and milestone at fault.

### Known answers and negative controls
Known answer: the rendered table equals the fixture; the M1 required set has three members. Negative controls:
the four planted inconsistencies. Metamorphic: reordering foundation rows changes no verdict. Determinism: a pure
function of three tracked files.

## Considerations

- "Admit" at M0 for a foundation first used later does not replace the later admission: a crate first used at M4 is admitted at M4 by its own record at the pin of that day. Item 3 of the test is what keeps the M0 record from being read as permanent.
- The firewall states dependency only; what each milestone delivers is defined by the milestone chapter. If the two disagree, the milestone chapter's "needs" row governs and this data is corrected by a dated change.
- A failed admission of a required foundation is not a failure of the program if its kill gate's fallback is adopted; the test accepts exactly that status and no softer one.
- frankenscipy has no admission gate of its own: it is admitted with FrankenSim's path-consumption gate, because FrankenSim already pins it; the row's `admission_gate` says so.
- Risk rows served: upstream work costing more than planned (an upstream item is never a mitigation by itself; its interim posture is), and a foundation defect surfacing late.
