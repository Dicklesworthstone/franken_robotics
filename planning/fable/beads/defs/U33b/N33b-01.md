## Background

FrankenRobotics stands on about seventeen sibling foundations. A program with that many dependencies is blocked
by whichever one converges last unless it says, in advance, **which milestone needs which foundation**. The plan
does: the dependency firewall. A blank cell means the milestone does not depend on the foundation. A cell in
parentheses is used if the foundation is admitted and is not required for the milestone to exit.

What the table guarantees, in the plan's words. M1 depends only on FrankenSim, asupersync and FrankenSQLite. If
the GPU, symbolic and proof foundations all failed admission, M1 would still ship a referee-tier design studio
and the first mission slice on the CPU. The mission slice needs no symbolic or proof sibling, because its
certificates are checked by the offline auditor `frob-verify`, which uses the standard library alone. Nothing in
the last five rows is on a critical path. The M0 column carries the two upstream work items at priority P0,
FD-FMCP-01 and FD-ASUP-01; neither is on M1's critical path: if the MCP admission cannot pass within the M0
budget, KILL-MCP's fallbacks apply and M1's verbs are reached through the command line. M7 freezes every pin and
the toolchain T for the length of the tournament, because a ratio of times measured across a pin move or a
toolchain train is not one measurement.

One cell is a choice (DESIGN, stated identically in N40-07). The plan prints the firewall twice: by foundation in
the suite chapter (the table above) and by milestone in the milestone chapter. They agree everywhere except at
M7 for fastmcp_rust: the suite chapter prints "rival access" without parentheses, which would make it required,
and the milestone chapter lists "fastmcp_rust for rival access" under "uses if admitted". Used here: optional
(the cell is in parentheses and M7 is in `optional_at`). Reason: the last fallback of KILL-MCP is the command
line, which is complete on its own, so a tournament whose rival reaches the verbs through the command line is
still a tournament, and no milestone may be blocked by one failed bet.

What a missing foundation costs, per milestone (the plan's fallbacks): M0, a failed admission is the result and
its fallback is decided there; M1, CLI only and no kernel certificates, with the mission slice unaffected; M2,
the no-GPU variant, KILL-KIR, KILL-METAL; M3, local implementations against the same known answers, KILL-MCP,
KILL-TUI, plain Three.js; M4, the numerical lane of KILL-SYNTH-LINKAGE and policies exchanged in the native
checkpoint format only; M5, KILL-LEMMA, KILL-REFLECT, KILL-INGEST and the Foundry kill gates; M6, the epic is
not funded; M7, a pin move or a toolchain train voids the runs it spans; M8, the epic is not funded.

A table in a document does not stop an optional dependency from becoming a required one by accident (a default
feature, a convenience import). This bead turns the table into data that a test reads (DESIGN). Rejected: a
seventh `xtask` subcommand (the tool has exactly six by rule, and a seventh needs a named defect class and the
owner's approval); a separate registry file (the foundation rows already exist in the stack lock).

## Scope

In: the firewall as data, entered once: the fields `required_at`, `optional_at` and `firewall_cells` on each
foundation row of `franken-stack.lock`, which are the only place where the project states which foundation is
required or optional at which milestone (DESIGN: the cell text was drafted under the key `uses`, which the
stack-lock format already gives to a row's list of postures, N33a-01 and N33a-03, so it is renamed); the loader; the data-level consistency test between the firewall, the admission
gates and the gate status file (it reads three tracked files and no build graph); the classification of each
foundation at a milestone (admitted, fallback adopted, missing; optional and admitted or not); the two frozen
assertions (M1 requires exactly three foundations; the last five rows are never required); the per-milestone
report that exit reviews read.

Out: the stack lock's other fields and the resolution receipt (the first part of the chapter); the build-level
proof that M1 ships without the optional foundations (bead N33b-02); the M7 freeze (N33b-03); the exit reviews
themselves (BD-044, BD-147 and their successors). Also out, and all in N40-07, which depends on this bead and
reads this data without keeping a copy of the membership: the firewall applied at a milestone exit to what the
milestone's targets actually link (`foundation-outside-firewall`); the by-milestone view of the table (needs,
uses if admitted, if missing) with the field `if_missing` of `registries/milestones.toml`; the verdict on a
required foundation that is missing (blocked unless its route, a kill decision or a variant record, is on
record); the first-use milestone rule (`admission-inherited`). The rule that an admission is never inherited,
per use and per pin, is implemented once, in N33a-07 (`unadmitted-use`, `admission-stale`); the test here calls
it.

## Technical approach

**1. Data (DESIGN).** Each `[[foundation]]` row gains:

```toml
required_at = ["M1", "M2", "M3", "M4", "M5", "M6"]     # the milestone cannot exit without it (or its kill decision)
optional_at = []                                       # used if admitted; the cells in parentheses
firewall_cells = { M0 = "admit; file tests", M1 = "referee, geometry, ledger, memo store; study statistics", M7 = "frozen pin" }
```

`M0` is implicit for every foundation whose admission gate is due at M0 ("admit"). `firewall_cells` carries the
cell text so that a report can print the table. The table above is the initial content, row for row; `frozen
pin` at M7 is recorded for frankensim and asupersync and applies to every pin through the freeze mechanism. The
three rows of the foundation ledger that the table does not print (FD-FJAX, FD-FKER, FD-FSS) carry
`required_at = []` and empty `firewall_cells`; FD-FJAX has `optional_at = ["M2"]` (its admission only if the M2
profile asks) and the other two `optional_at = []` (DESIGN: every row carries all three keys, so the loader has
no special case).

**2. Loader and validation** (`xtask`, inside `check-stack`'s existing parse of the stack lock, adding no
subcommand; the three keys are validated through the hook of the stack-lock parser, N33a-03): an unknown
milestone name, a milestone listed as both required and optional, or a row missing any of the three keys (an
empty list or table is allowed) is a load-time error.

**3. The consistency test** (`crates/frob-conformance/tests/firewall.rs`, run in the default lane; it reads files
and runs no physics):
1. For every foundation F and every milestone M in `required_at(F)`: F's row names an `admission_gate`, and that
   gate (or the group gate of the feature group first used at M) exists in `registries/gates.toml`.
2. Classification, for the milestone under review (passed as `FROB_MILESTONE`, default the current one in the
   gate file). A required foundation is `admitted` (its gate has status `pass`), `fallback-adopted` (status
   `killed: fallback adopted`, with the fallback text of the row recorded) or `missing` (any other status: `not
   run`, `fail`, `blocked`, or `killed` without the recorded fallback). An optional foundation is `admitted` or
   `not-admitted`; its gate may have any status, nothing about it fails, and a `fail` or `not run` there is
   printed as "used only if admitted: not admitted". The test asserts that the classification is total (every
   foundation in `required_at` or `optional_at` of the milestone gets exactly one class) and agrees with the gate
   file. It does not decide whether a `missing` required foundation blocks an exit. DESIGN: that verdict is given
   in one place, step 5 of the exit check of N40-07, which blocks and names the foundation unless the route of
   the milestone's `if_missing` field is on record (the kill decision, or a variant record such as M2's no-GPU
   variant). Reason: the plan lets M2 exit with CUDA and Metal not admitted under the no-GPU variant, so a rule
   here that accepted `pass` and `killed: fallback adopted` and nothing else would contradict it.
3. No required foundation's admission is stale (an admission is never inherited: after a pin move the admission
   gate is rerun at the new pin). The test does not compare receipts itself: it calls
   `stack::admission::never_inherited` of N33a-07, the one implementation of the rule, and fails on any
   `admission-stale` finding for a foundation in `required_at` (the newest record covering the foundation must
   have `sibling_rev` equal to the pin in the current lock).
4. The set of foundations required at M1 is exactly {frankensim, asupersync, frankensqlite}. This is a frozen
   assertion: changing it requires changing the test and is therefore a visible decision. It also equals the set
   of rows with `critical_path = true` (the ledger field of N33a-02), so the two statements of one fact in one
   file cannot drift apart.
5. The last five rows of the table (frankentui, franken_threed, drone reconstruction, franken_textiles,
   franken_firmware) have empty `required_at`.

**4. The report.** `cargo xtask check-stack --report firewall` (an output mode of the existing subcommand) prints,
for a milestone, three lists: required and admitted; required and not admitted (with the kill gate and fallback
of each, and whether the class is `fallback-adopted` or `missing`); optional with their status. Exit reviews
attach this output, and the exit check of N40-07 prints it inside the "Foundations" section of the exit report
beside its own verdicts.

Evidence: none is claimed; this is a structural check, determinism D0.

## Acceptance criteria

- [ ] Every foundation row of `franken-stack.lock` (all eighteen) carries `required_at`, `optional_at` and `firewall_cells`, and the printed report reproduces the table above cell for cell.
- [ ] The consistency test passes on the real tree at M0 and fails each planted inconsistency: a foundation added to `required_at = ["M1"]` beyond the three; an admission record whose pin predates the current pin (the finding is N33a-07's `admission-stale`); a parenthesized foundation marked required; a required foundation whose row names no admission gate present in the gate file.
- [ ] A required foundation whose gate is `not run` at the reviewed milestone is classified `missing`, is listed in the report under "required and not admitted" and is counted in `required_missing`; that it blocks the exit unless its route is on record is asserted in N40-07, not here.
- [ ] fastmcp_rust has M7 in `optional_at` and not in `required_at`, with the DESIGN note above; N40-07 states the same.
- [ ] No file other than `franken-stack.lock` states which foundation is required or optional at a milestone (the by-milestone table of N40-07 is rendered from these fields).
- [ ] The report is an output mode of the existing `check-stack` subcommand (registered by N33a-05), and this bead adds no subcommand; the count of six is asserted by BD-004's test, not here.
- [ ] The M0 exit review can run the report and obtain the list of admissions M0 owes: toolchain, FrankenSim (path consumption, the file-by-file tests, the worker fallback), asupersync, FrankenSQLite, FrankenTorch's Metal gateway, `cudarc`, FrankenSymPy, franken_numpy and fastmcp_rust.

## Test plan

### Unit tests
- `firewall_rows_complete`: every foundation has the three fields (FD-FJAX, FD-FKER and FD-FSS with empty `required_at`); unknown milestone names are rejected; a row missing `optional_at` is rejected.
- `critical_path_agrees_with_m1`: the rows with `critical_path = true` are exactly those with M1 in `required_at`; a scratch lock that sets `critical_path = true` on FD-FT fails.
- `firewall_report_matches_fixture`: the rendered table equals a checked-in fixture of the table above.
- `m1_requires_exactly_three`: asserts the frozen set.
- `last_five_rows_never_required`.
- `required_gate_classification`: synthetic gate files (labelled `synthetic`) for each status: `pass` → `admitted`; `killed: fallback adopted` with the row's fallback text recorded → `fallback-adopted`; `not run`, `fail`, `blocked`, and `killed` without the fallback text → `missing`.
- `fastmcp_m7_is_optional`: M7 ∈ `optional_at`, M7 ∉ `required_at` for the fastmcp_rust row.
- `optional_gate_any_status_is_reported_not_failed`.
- `stale_admission_detected`: a record whose receipt lists an older revision fails, through the `admission-stale` finding of N33a-07's function (the test asserts that it calls that function and holds no comparison of its own).
- `both_required_and_optional_rejected`.

### End-to-end script and logging
`scripts/e2e/suite_firewall.sh` (owned by this bead; N33b-02, which depends on it, adds the step
`m1_isolation`): step `data` runs `cargo xtask check-stack --report
firewall --milestone M0` and the conformance test, then repeats on a scratch copy of the stack lock with one
planted inconsistency and expects failure. Logged per STD-E2E: command, exit code, wall time, metrics
`required_admitted`, `required_fallback_adopted`, `required_missing` (reported with the foundations named; the
exit verdict on it is N40-07's), `optional_admitted`, `planted_caught`, the hash of the stack lock, and on
failure the foundation and milestone at fault.

### Known answers and negative controls
Known answer: the rendered table equals the fixture; the M1 required set has three members. Negative controls:
the four planted inconsistencies. Metamorphic: reordering foundation rows changes no verdict. Determinism: a pure
function of three tracked files.

## Considerations

- "Admit" at M0 for a foundation first used later does not replace the later admission: a crate first used at M4 is admitted at M4 by its own record at the pin of that day. Item 3 of the test is what keeps the M0 record from being read as permanent.
- The firewall states dependency only; what each milestone delivers is defined by the milestone chapter. If the two disagree, the milestone chapter's "needs" row governs and this data is corrected by a dated change.
- A failed admission of a required foundation is not a failure of the program if its kill gate's fallback is adopted: the classification gives that status its own class, `fallback-adopted`, and no softer status receives it. Everything else is `missing`, and whether a missing foundation may be passed over at an exit (only by a recorded route) is decided by N40-07.
- Division of the firewall between three beads, so that nothing is specified twice: this bead holds the data and the checks that need only tracked files; N33a-07 holds the admission records and the per-use, per-pin never-inherited check; N40-07 holds what needs a build graph or the milestone calendar (the exit check, the first-use milestone, the routes).
- frankenscipy has no admission gate of its own: it is admitted with FrankenSim's path-consumption gate, because FrankenSim already pins it; the row's `admission_gate` says so.
- Risk rows served: upstream work costing more than planned (an upstream item is never a mitigation by itself; its interim posture is), and a foundation defect surfacing late.
