## Background

The dependency firewall states that **M1 depends only on FrankenSim, asupersync and FrankenSQLite**: if the GPU,
symbolic and proof foundations all failed admission, M1 would still ship a referee-tier design studio and the
first mission slice on the CPU. The mission slice needs no symbolic or proof sibling, because its certificates
are checked by the offline auditor `frob-verify`, which uses the standard library alone. If the MCP admission
cannot pass, agents reach M1's verbs through the command line, which is complete on its own. The cost of a
missing optional foundation at M1 is stated in advance: CLI only, and no kernel certificates.

That statement is a promise about a build that nobody would otherwise make: every developer's tree has all the
siblings checked out, so an accidental hard dependency on an optional one (a default feature, a convenience
import, an oracle that leaked out of a dev-dependency) is invisible until the day a sibling breaks. This bead
makes the promise a test (DESIGN): build the M1 product with every optional foundation left out, and run the M1
battery against that binary. It is the build-level half of the firewall; the data-level half is bead N33b-01.

Rejected: trusting rule L-4 (confinement of each foundation to named crates) alone. Confinement says where a
foundation may be named; it does not say the product still works when the confined crate is not built.

## Scope

In: a named feature set of the core binaries that enables no optional foundation; the dependency assertion on
that build; the M1 battery run against the isolation binary; the typed behaviour of verbs whose capability is
absent; negative controls; the record for the M1 exit review.

Out: the firewall data (N33b-01); the airlock's group stubs and `FROB-REF-790` (N33b-09); the no-GPU variant of
M2 (the milestone and Spark beads); the MCP fallbacks themselves (the Tether beads under KILL-MCP).

## Technical approach

**1. The isolation feature set (DESIGN).** `frob-cli` declares a feature set `m1-core` that builds `frob` and
`frobd` from the core workspace with: the airlock's default groups only (`referee`, `geometry`, `ledger`) plus
the statistics crate the study types use; the MCP library not linked; array-file export through franken_numpy
off (the consumer's fallback, plain binary columns, on); no FrankenTorch bridge; no derivation tool; no GPU
annex (the annexes are separate workspaces and are simply not part of this build). Every optional foundation is
therefore behind a feature of its consuming crate, default-on or default-off as that crate's bead decides, and
removable.

**2. The dependency assertion** (`crates/frob-conformance/tests/isolation.rs`). From
`cargo metadata --no-default-features --features m1-core` for the two binaries:
1. the set of this repository's crates in the graph has **direct** edges to sibling packages of exactly three
   foundations: frankensim (through `frob-fsim` and the bedrock-direct list), asupersync, frankensqlite;
2. no package of fastmcp_rust, frankentorch, `cudarc`, frankensympy, franken_lean, franken_numpy, frankenscipy,
   frankentui, franken_threed or frankenjax is a direct dependency of any crate of this repository in the graph
   (what FrankenSim's own closure brings transitively is listed in the output and is not a violation);
3. `frob-verify` built alone has zero dependencies;
4. the graph contains exactly one asupersync package.

**3. The battery against the isolation binary** (script below). Everything M1 must deliver without parentheses
runs: the referee rollout of the built-in humanoid; `design check` stages 1 to 6 on the first archetypes; the
actuator and energy checks on the referee; a paired comparison (an anytime study) on the cart fixture; the
first mission slice (the docking family, the stance family, the pusher battery) with bundles checked by
`frob-verify`; telemetry summaries and `explain`.

**4. Absent capabilities answer by name.** In the isolation binary, a verb that needs something left out
returns one envelope with a refusal and never panics or falls back silently: MCP-only entry points are absent
from `frob capabilities`; array-file export returns the plain-column artifact and says so in `warnings`; a
request for a kernel certificate returns `FROB-REF-724` (not implemented in this build) or `FROB-REF-790`
(airlock group absent), exit 5. `frob doctor --json` lists the three foundations as admitted and the others as
`not built`.

**5. Record.** The run's summary (binary digest, stack receipt hash, the dependency list, the battery's
assertion counts) is written as a hash-named receipt of the conformance run (the receipt mechanism of N38a-02;
the dependency assertion runs as `FROB_TEST_SEED=0 cargo test -p frob-conformance --test isolation`) and attached
to the M1 exit review as the evidence for "M1 depends only on three foundations". It does not wait for the
Gauntlet's M1 capstone (BD-146), which is related, not a prerequisite: the isolation build exercises the M1 verbs
themselves. Evidence: structural; no claim of the seven is made.

## Acceptance criteria

- [ ] The `m1-core` build of `frob` and `frobd` succeeds from a tree in which the optional siblings' checkouts are made unreadable to the build (a scratch copy with those directories absent), proving no build script or path dependency reaches them.
- [ ] The dependency assertion holds: direct sibling edges go to frankensim, asupersync and frankensqlite only; one asupersync package; `frob-verify` has zero dependencies.
- [ ] The M1 battery passes against the isolation binary: referee rollout digest equal to the full build's; `design check` results byte-identical to the full build's on the first archetypes; the comparison returns the same statistic; the mission slice's bundles verify offline.
- [ ] Every verb in the M1 registry either works or returns a typed refusal naming the absent capability; none exits with code 1.
- [ ] Negative controls are caught: a planted direct edge from `frob-analyze` to an `fsym-*` crate; a planted default feature that links the MCP library into `m1-core`; a planted use of an array-file call without its feature guard (the build fails or the assertion fails).
- [ ] The summary is recorded for the M1 exit review with the stack receipt hash.

## Test plan

### Unit tests
- `isolation_direct_edges_three_foundations`; `isolation_one_asupersync`; `frob_verify_zero_dependencies`.
- `planted_fsym_edge_fails`; `planted_mcp_default_feature_fails`; `planted_unguarded_array_call_fails` (an
  array-file call outside its feature guard fails the `m1-core` build or the assertion).
- `absent_capability_is_typed`: for each verb whose registry row names an optional capability, the isolation binary returns `FROB-REF-724` or `FROB-REF-790` with exit 5 and one envelope.
- `doctor_lists_not_built`: the foundation list distinguishes `admitted`, `not admitted` and `not built`.

### End-to-end script and logging
`scripts/e2e/suite_firewall.sh`, step `m1_isolation` (seed-explicit, idempotent, scratch store per run):
1. copy the workspace manifests and sources to a scratch tree whose `../` holds only frankensim, asupersync and
   frankensqlite checkouts at their pins; build `frob` and `frobd` with `m1-core` under a timeout inside the
   machine envelope;
2. `frob doctor --json`: assert three admitted foundations and the stack receipt;
3. `frob sim run g1 --tier referee --seconds 2 --key iso-run-1 --json`: assert the digest equals the full
   build's (the full build's reference call carries its own key, `full-run-1`: a `run` verb without a key is
   `FROB-REF-805`, and two compared runs under one key would return one stored receipt);
4. `frob design check quad-mammal --json` and the other first archetypes: assert equality with the full build;
5. `frob eval compare cart-a cart-b --task dock --key iso-cmp-1 --json` (reference call: `full-cmp-1`): assert
   the pair counts identity and equal e-value;
6. the mission-slice script against this binary; `frob-verify` on each bundle;
7. one call per absent capability, asserting the typed refusal.
Logged per STD-E2E: every command line, exit code, wall time, the evidence block, metrics
`direct_foundations` (threshold exactly 3), `digest_equal_full_build` (true), `verbs_ok`, `verbs_refused_typed`,
`verbs_exit_1` (threshold 0), `build_wall_s`, `peak_rss_gib`, and on failure the first differing digest or the
offending dependency path. The summary line lists the assertions and no gate (this script supports the M1 exit
review).

### Known answers and negative controls
Known answer: the isolation binary and the full binary give identical digests on every M1 result that does not
involve an optional capability (the capability set differs; the physics and the analyses do not). Negative
controls: the three planted defects. Metamorphic: enabling one optional feature at a time changes the capability
list by exactly that capability and changes no digest. Determinism: the comparison of digests is itself the
determinism check across two builds of one stack receipt.

## Considerations

- The build excludes optional siblings by construction; it does not simulate their failure at run time, because an optional foundation that was built and admitted is simply present. The property tested is that nothing M1 needs is behind one.
- FrankenSim's closure brings other siblings' crates transitively (it pins frankenscipy and others for its own use). "Depends only on three" is a statement about direct edges and about what this project's code calls; the output lists the transitive siblings so that the statement is not read as more than it is.
- The isolation build costs one more cold build of the M1 closure (about 65 FrankenSim crates and 2.06 million lines); it runs at the exit review and after pin moves, not on every commit.
- If this test fails near the M1 exit, the remedy is to put the offending use behind its feature, never to add a foundation to the required set; changing the required set is a visible edit of the firewall data and its frozen test.
