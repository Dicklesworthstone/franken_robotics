## Background

The ten-fold tournament at M7 compares this project's design loop with the strongest composed rival, and its
result is a ratio of times. The dependency firewall has one row for it: **M7 freezes every pin and the toolchain
T for the length of the tournament, because a ratio of times measured across a pin move or a toolchain train is
not one measurement.** The milestone table states the consequence: a pin move or a toolchain train voids the runs
it spans. The upstream-work rules repeat it: an upstream change that lands is adopted only through its
switch-over rule, and neither a pin nor T moves during the tournament.

A "pin" is the commit of a sibling foundation recorded in `franken-stack.lock`; T is the one Rust toolchain of
the whole build graph. Both normally advance through a compatibility train (move the pin, write a new resolution
receipt, re-run the admission and parity gates, relock). Every result in the ledger carries the receipt hash of
the binary that produced it, which is what lets a later reader decide whether two results may be compared as
results of the same stack.

The freeze needs a mechanism (DESIGN) because the default behaviour of a healthy project is to keep moving: an
agent that fixes a sibling defect mid-tournament and runs a train would silently split the tournament in two.
Rejected: a convention in a document (nothing would stop the train); freezing by never touching the siblings'
checkouts (this project's tools never move a sibling checkout anyway, and the siblings' own heads keep moving;
the freeze is about what this repository builds against).

## Scope

In: a freeze record in the stack lock; `check-stack` behaviour while frozen; the compatibility train's refusal to
run while frozen; the harness-side rule that runs under different receipts are never pooled and that a move
voids the spanning runs; opening and closing the freeze as recorded acts; tests.

Out: the tournament's design, arms and decision rule (the ten-fold beads); the train procedure itself (N33b-04);
the toolchain train (the last part of the chapter); what happens to upstream work during the freeze (it
continues in the siblings; adoption waits).

## Technical approach

**1. The freeze record (DESIGN).** A table in `franken-stack.lock`:

```toml
[freeze]
campaign = "<tournament campaign identifier>"
receipt  = "<BLAKE3 of the resolution receipt every tournament run must carry>"
opened   = "<commit of this repository that opened the freeze>"
closed   = ""            # empty while the freeze is in force; set by the commit that closes it
reason   = "ten-fold tournament"
```

The frozen receipt fixes, in one hash, this repository's toolchain, every sibling revision, the requested
feature groups, the lockfiles, the patches and the build-identity settings.

**2. `check-stack` while frozen.** If `[freeze]` exists with an empty `closed`: the newest receipt under
`receipts/` must be the frozen one; every sibling head must be on-pin and clean (a dirty or off-pin sibling is a
failure here, not a development-build warning); `rust-toolchain.toml` must equal the frozen T; any difference
fails the check with the message "stack frozen for campaign <id>: <what moved>". The check still writes nothing
outside this repository.

**3. The train refuses.** The compatibility train (N33b-04) and the toolchain train read the freeze record
first and stop with the same message. The only way to move a pin during a freeze is to close the freeze in a
commit that says so, which voids the tournament runs not yet complete (rule 5).

**4. The harness.** Every tournament run record carries the receipt hash of the binary that produced it (it is
part of the envelope's evidence identities already). At submission the harness refuses a run whose binary's
receipt differs from `[freeze].receipt` with `FROB-REF-890` (`stack-mismatch`: evidence recorded under another
stack receipt is offered as same-stack evidence without revalidation). At analysis, the pooled ratio is computed
only over runs with the frozen receipt; the analysis prints the count of excluded runs and their receipts, and a
cell with any excluded run is reported `void: stack moved` unless it is re-run.

**5. Opening and closing.** Opening requires: all gates due at the M7 entry recorded as pass or killed with
fallback; `check-stack` on-pin for every sibling; the receipt written at the opening commit. Closing is a commit
that sets `closed`, names the reason (`tournament complete` or `aborted: <reason>`), and is recorded in the
tournament's own record. After an abort every run of the campaign is void and the tournament restarts under a
new freeze.

**6. Rival arms.** The incumbent arm's pinned versions are frozen by the tournament's own protocol; this bead
adds only that fastmcp_rust (used for rival access at M7) is among the frozen pins.

## Acceptance criteria

- [ ] With an open freeze, `check-stack` fails on each of: a new receipt; a sibling moved one commit; a dirty sibling tree; a changed toolchain file; a changed lockfile. With the tree at the frozen state it passes.
- [ ] The compatibility train and the toolchain train refuse to start while the freeze is open and name the campaign.
- [ ] The harness refuses to submit a run built under another receipt with `FROB-REF-890`, and the analysis excludes and reports runs with a foreign receipt; a cell containing one is `void: stack moved`.
- [ ] Opening a freeze with a sibling off-pin or a due gate not recorded is refused.
- [ ] Closing the freeze is a recorded act; after an abort, runs of the campaign are marked void in the tournament record.
- [ ] `check-stack` writes nothing to any sibling checkout (run against a read-only copy).

## Test plan

### Unit tests
`xtask/tests/freeze.rs` on synthetic stack fixtures (labelled `synthetic`):
- `frozen_tree_passes`; `frozen_new_receipt_fails`; `frozen_sibling_moved_fails`; `frozen_dirty_sibling_fails`; `frozen_toolchain_changed_fails`; `frozen_lockfile_changed_fails`.
- `open_requires_on_pin_and_gates`; `close_sets_reason`.
- `train_refuses_while_frozen` (the train script's preflight).
`crates/frob-conformance/tests/freeze_pooling.rs`:
- `submit_foreign_receipt_refused_890`; `analysis_excludes_foreign_receipts`: ten synthetic run records, two with another receipt; the pooled statistic uses eight and reports two; the affected cell is void.
- `ratio_across_pin_move_is_not_pooled`: a planted analysis that pools all ten is detected by comparing its denominator with the count of frozen-receipt runs.

### End-to-end script and logging
`scripts/e2e/suite_freeze.sh`: on a scratch copy of the stack (never the real siblings): open a freeze; run
`cargo xtask check-stack` (pass); advance a scratch sibling by one commit and re-run (fail, message names the
campaign and the sibling); attempt the train (refused); submit one tournament dry-run record under the frozen
receipt (accepted) and one under a different receipt (exit code for an `8xx` evidence refusal with
`FROB-REF-890`); close the freeze with reason `aborted: test` and assert the dry-run records are void. Logged per
STD-E2E: command, exit code, wall time, evidence block, the `refusal` events, metrics `moves_detected`
(expected 1), `runs_pooled`, `runs_excluded`, the frozen receipt hash, and on failure the first field of the
receipt that differs.

### Known answers and negative controls
Known answer: a receipt computed twice on an unchanged tree is byte-identical (KA-767), so a frozen tree stays
passable for the whole campaign. Negative controls: each kind of move; the pooling mutant; a freeze opened on an
off-pin tree. Metamorphic: the order in which runs are submitted does not change which are pooled. Determinism:
structural checks only, pure functions of tracked files and run records.

## Considerations

- The freeze can last weeks. Upstream work continues in the siblings during it; only adoption waits. A defect found mid-tournament that makes the frozen stack wrong is a reason to abort and restart, and the cost of that is why every gate due before M7 must be recorded before the freeze opens.
- A dirty sibling admits development builds outside a freeze; inside one it is a failure, because the receipt would hash bytes that no commit names and the run could not be reproduced.
- The risk row this serves: dirty or off-pin sibling trees make a receipt unrepeatable. Its signal is a drift class other than on-pin at a gate run.
- Compute envelope: the tournament itself needs approval classes beyond the default envelope; this bead adds no compute.
- If the owner decides mid-campaign that a pin must move for all arms, that is a dated amendment made before the measurements it governs, recorded as a close-and-reopen with the affected cells re-run.
