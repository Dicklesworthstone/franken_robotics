## Background

FrankenRobotics pins each sibling foundation at a commit in `franken-stack.lock`. FrankenSim moves fast (FACT:
409 commits touched `crates/fs-mbd` in the thirty days to 2026-11-21, on 17 distinct days), so pins must advance
regularly or the project falls behind the fixes it lands upstream itself. The plan's rule (DESIGN): **pins
advance through a compatibility train: move the pin, write a new receipt, rerun the admission and parity gates,
relock.** Three companions of that rule: a sibling's newer clean head is never rolled back locally; the airlock
crate stays whatever lands, because the sibling's API still moves daily; and the fallbacks stay written down
while no default wiring rests on one.

The train is also how an upstream work item is adopted. Every such item has a switch-over rule (what must be
re-run when its change lands); a landed change is adopted only by a train that runs that rule.

Two measurements depend on the train and exist nowhere else. Risk RISK-01 (FrankenSim API churn) is signalled by
"adapter changes per pin move". Bet BET-04 (FrankenSim can be consumed by path, stably) is falsified, and kill
gate KILL-FSIM fires, when **upstream breakage costs more than 20% of working days in any four-week window**. A
kill gate whose trigger nobody measures cannot fire. This bead defines the procedure, the log that carries those
two numbers, and a rehearsal at M0, because a procedure that has never run is a hope.

Rejected: advancing pins ad hoc when something breaks (admissions go stale without a record; results from two
stacks get compared); following sibling heads without a pin (no result is reproducible); moving a sibling
checkout back to its pin to make a check pass (forbidden: the off-pin sibling is classified as a fast-forward or
a divergence before any remedy, and this project's tooling never moves a sibling checkout).

## Scope

In: the train procedure as a script with a preflight, an abort path and one landing commit; the list of gates a
train re-runs; the train log and its schema; the definition and computation of the breakage share; the rehearsal
on one FrankenSim pin move; tests on scratch stacks.

Out: `check-stack` and the receipt writer (BD-004 and the stack-lock beads); the toolchain train; the freeze
(N33b-03); the KILL-FSIM decision (N33b-05); the upstream registry (BD-037).

## Technical approach

**1. The procedure** (`scripts/train/pin_move.sh`; plain shell that calls the existing checks; it holds no
policy of its own and edits only this repository).

1. *Preflight.* Refuse if a freeze is open. Run `cargo xtask check-stack`; for each foundation in the train the
   sibling checkout must be clean and either `on-pin` or `stale-lock` (a fast-forward of the lock). `drift`
   (dirty, retreated or diverged) stops the train with the classification; nothing is "fixed" by resetting.
   Disk and envelope preflight: the cold check of the M1 closure must be expected to fit one hour, 16 GiB and
   8 cores.
2. *Target.* The target revision is the sibling's clean head on its `main`, as checked out by whoever works in
   that sibling under its rules; the script reads it and never writes there. Several siblings may ride one train
   when they must move together.
3. *Move the pin.* Edit `git_rev` (and the recorded sibling toolchain channel) in `franken-stack.lock`; re-resolve
   the affected lockfiles; re-read the three settings Cargo does not propagate from a path dependency and repeat
   any change at this repository's root: the `[patch.crates-io] asupersync` entry, the FrankenSQLite profile
   overrides, and the build-identity environment for the linear-algebra crate.
4. *Receipt.* `check-stack` writes the new resolution receipt; its hash goes into the foundation row.
5. *Adapt.* If the build fails, the fix is confined to `frob-fsim` (and to bedrock-direct users for bedrock
   crates). The script records `adapter_lines_changed` from the diff of `crates/frob-fsim`.
6. *Re-run gates.* All admission gates of the moved foundations that are in use at the current milestone (for
   FrankenSim: path consumption, the file-by-file tests, the group gates of every enabled group, the worker
   fallback), INT-ASUP-01, the parity gates that compare this project's tiers with the referee, and the
   switch-over rule of every upstream item that landed between the old and new revisions (read from
   `registries/upstream.toml`). Each writes its record with the new receipt hash.
7. *Invalidate.* Memoized referee results carry the stack-lock digest in their keys and go cold by construction.
   Evidence recorded under the old receipt stays valid as history and cannot be offered as same-stack evidence
   (`FROB-REF-890`) until revalidated. Where a switch-over rule says "re-baseline the fidelity ledger once",
   the train does it and records the old and new envelopes.
8. *Land.* One commit carries the lock, the lockfiles, the receipt, the admission records, the gate rows and the
   train-log row. The commit message lists the commands and results.
9. *Abort.* If any re-run gate fails and cannot be repaired inside the train, nothing lands: the working tree is
   restored to the old pin, the train-log row is still written with `outcome = "aborted"` and the failing gate,
   and the matching upstream item is opened or updated with the failing fixture.

**2. The train log** (`registries/trains.toml`, schema `frob.train-log/1`, loaded with the other registries; an
unknown field is a load-time error):

```toml
[[train]]
id = "T-0007"
date = "2026-12-03"
moves = [{ fd = "FD-FSIM", from = "<40 hex>", to = "<40 hex>", class_before = "stale-lock" }]
receipt_before = "<BLAKE3>"
receipt_after = "<BLAKE3>"
gates = [{ gate = "INT-FSIM-01", status = "pass" }, { gate = "INT-FSIM-03", status = "pass" }]
upstream_adopted = ["FD-FSIM-16"]
adapter_lines_changed = 42
wall_hours = 3.5
outcome = "landed"                      # landed | aborted

[[breakage]]
date = "2026-12-01"
days_blocked = 0.5                      # in half days
cause = "fs-mbd signature change broke frob-fsim at sibling head needed for FD-FSIM-12"
train = "T-0007"
```

**3. The breakage share (DESIGN; the definition BET-04 and KILL-FSIM need).** A breakage incident is a half day
or more on which work in this repository was blocked because a sibling changed: a failed or aborted train, an
adapter rewrite forced by a sibling head that an upstream item needs, or a sibling head that no longer builds on
T. It is logged the day it happens with its cause. The share over a window is the sum of `days_blocked` in the
window divided by the working days in it; for a four-week window that is 20 working days, so the threshold of 20%
is 4 days. The script prints the share for the trailing four weeks at every train and
`scripts/train/breakage_share.sh` recomputes the worst four-week window in the whole log.

**4. Rehearsal at M0.** One real train of FrankenSim from the admission pin to a newer clean head, recorded end
to end: wall hours, gates re-run with results, adapter lines changed, and whether the three root settings needed
a change. If the newer head breaks admission, the rehearsal ends as a recorded abort, which is an equally valid
rehearsal.

## Acceptance criteria

- [ ] On a scratch stack the script performs a full train (move, receipt, gates, one landing commit) and a full abort (nothing landed, row written), and both are reproducible from the log row.
- [ ] The preflight refuses a train from a `drift` sibling, from a dirty tree and under an open freeze; in no case does it write to a sibling checkout (run against a read-only copy).
- [ ] After a landed train, `check-stack` passes and reports every moved sibling `on-pin`; every re-run gate's record cites the new receipt; no record cites the old one for a moved foundation as current.
- [ ] A result recorded under the old receipt, offered as same-stack evidence after the train, is refused with `FROB-REF-890`; a memoized referee result from the old pin is a miss.
- [ ] The breakage share computed from a synthetic log with 4.5 blocked days in one four-week window is 22.5% and flags the threshold; with 3.5 days it is 17.5% and does not.
- [ ] The M0 rehearsal on FrankenSim is recorded in `registries/trains.toml` as `landed` or `aborted`, with adapter lines changed and wall hours, and is cited by the KILL-FSIM decision.
- [ ] The landing commit of the rehearsal contains the lock, receipt, admission records and log row together.

## Test plan

### Unit tests
`scripts/train/tests/` (shell tests on scratch git repositories that stand in for siblings, labelled `synthetic`;
real `git` and real `cargo metadata`, no mocks):
- `train_fast_forward_lands`; `train_abort_restores_old_pin`; `train_refuses_drift`; `train_refuses_dirty`; `train_refuses_under_freeze`.
- `train_never_writes_sibling`: sibling copies are read-only; the train still completes.
- `train_reruns_listed_gates`: with a stub gate list of three, all three have new records; removing one from the run fails the landing check.
- `train_adopts_upstream_switch_over`: an upstream item landed in the span has its switch-over gates in the run and its status becomes `adopted`.
`cargo test -p frob-core registries::trains`:
- `train_log_schema_round_trip`; `unknown_field_rejected`.
- `breakage_share_window`: the 22.5% and 17.5% cases; `worst_window_found` across a log with two clusters.
- `receipt_before_after_differ_on_move`; `receipt_identical_on_no_move` (KA-767).

### End-to-end script and logging
`scripts/e2e/suite_compat_train.sh`: builds two scratch sibling repositories and a scratch consumer, runs a
landing train and an aborting train, then `frob doctor --json` on the consumer to assert the receipt shown is the
new one, and a stale-evidence query to assert `FROB-REF-890`. Logged per STD-E2E: command, exit code, wall time,
the envelope's evidence block (receipt identity), metrics `gates_rerun`, `gates_passed`, `adapter_lines_changed`,
`breakage_share_4w` (threshold 0.20), `sibling_writes` (threshold 0), both receipt hashes, and on failure the
first step that differed from the expected sequence.

### Known answers and negative controls
Known answer: a receipt computed twice on an unchanged tree is byte-identical, and touching one tracked file in a
sibling flips `dirty` and changes `tree_hash` so that `check-stack` fails (KA-767 and its control). Negative
controls: a train that skips a gate; a train that lands on a failing gate; a script variant that resets a sibling
to its pin (caught by the read-only sibling test). Metamorphic: a train that moves two siblings gives the same
final receipt as two trains moving one each in either order, when neither depends on the other. Determinism: the
log row and receipts are pure functions of the trees.

## Considerations

- RISK-01 (High): FrankenSim API churn in `fs-mbd` and the `Component` trait, whose composition contract version is still 0. Signal: adapter changes per pin move, and BET-04's breakage share. Mitigations: the airlock, the pin, this train, upstream item FD-FSIM-08 (freeze the trait as contract v1), and KILL-FSIM with the worker process first.
- RISK-23: dirty or off-pin sibling trees make a receipt unrepeatable. A dirty sibling admits development builds only; no gate records a PASS on a dirty tree (OPEN-SUITE-3 default).
- Cadence is a judgement, not a rule: a train costs a cold build and the admission lanes, so it runs when an upstream item lands that this project wants, when a sibling fix is needed, and otherwise at each milestone exit. Pins and T do not move during the ten-fold tournament.
- The breakage log depends on honest entries. The script lowers the cost of honesty by prompting for an entry whenever a train aborts or `check-stack` reports drift.
- Other agents work in the siblings. The train never edits them; an upstream change needed to make a train pass is separate work in the sibling, with file reservations through Agent Mail and the sibling's own gates.
