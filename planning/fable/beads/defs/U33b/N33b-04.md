## Background

FrankenRobotics consumes its sibling projects at exact pins. `franken-stack.lock` holds one `[[foundation]]` row
per sibling (`id`, `posture`, `path`, `git_rev`, `toolchain`, `features`, `build_env`, `confined_to`,
`admission_gate`, `receipt`, `fallback`), and `cargo xtask check-stack` compares that lock with the tracked
lockfiles, the toolchain files and the sibling heads. A pin is a statement of intent; what was built is a
different fact, recorded in a **resolution receipt** (`frob.stack-receipt/1`, canonical JSON under `receipts/`,
named by its BLAKE3 hash).

The siblings do not hold still. FACT: 409 commits touched FrankenSim's `crates/fs-mbd` in the thirty days to
2026-11-21, on 17 distinct days; its composition contract is at version 0; its own constellation lock was stale.
Pins must therefore advance regularly, or the project falls behind the fixes it lands upstream itself. The
plan's rule (DESIGN): **pins advance through a compatibility train: move the pin, write a new receipt, rerun the
admission and parity gates, relock.** Three companions of that rule: a sibling's newer clean head is never
rolled back locally; the airlock crate `frob-fsim` stays whatever lands, because the sibling's API still moves
daily; and the fallbacks stay written down while no default wiring rests on one.

The train is also how an upstream work item is adopted. Every upstream work item of this program (the `FD-…`
beads: a change this program makes in a sibling's repository) has a switch-over rule (what must be re-run when
its change lands), and ends with a pin move; a landed change is adopted only by a train that runs that rule.
This bead turns the plan's one sentence into a procedure that an agent can run without judgment calls, a script
that enforces its guards, and a log from which the cost of consumption is measured.

Two measurements depend on the train and exist nowhere else. Risk RISK-01 (FrankenSim API churn) is signalled by
"adapter changes per pin move". Bet BET-04 (FrankenSim can be consumed by path from outside its tree, stably)
is falsified, and kill gate KILL-FSIM fires, when **upstream breakage costs more than 20% of working days in any
four-week window**. A kill gate whose trigger nobody measures cannot fire. This bead defines the procedure and
the log that carries those two numbers; the first real train at M0, because a procedure that has never run is a
hope, is the next bead (N33bp2-01), split from this one so that the procedure every upstream work item depends
on is finished without waiting for a real upstream head.

Why a train and not something lighter. Rejected: advancing pins ad hoc when something breaks (admissions go
stale without a record; results from two stacks get compared); floating on a sibling's `main` with no pin (no
result could be reproduced, and two results could not be compared as results of one stack); rolling a sibling's
checkout back to its pin or to an old commit when its head breaks us (forbidden: the checkouts are shared with
other agents and with the sibling's own work; the off-pin sibling is classified as a fast-forward or a
divergence before any remedy, and this project's tooling never moves a sibling checkout); a local patch or fork
to get past a breakage (it diverges from the sibling's head and does not survive the next pin move); inheriting
an admission across a pin (an admission is never inherited: a record is valid only for the commit it cites).

## Technical approach

**Terms.** A sibling's drift class, as `check-stack` reports it: `on-pin` (head equals `git_rev`, tree clean);
`stale-lock` (the checkout is a fast-forward of the pin); `drift` (dirty, retreated or diverged). The same three
classes are applied to the sibling's own lock (`constellation.lock`, `SUITE.lock`) against what it builds.

**Names (DESIGN; the plan gives the train one sentence and no file names, and two drafts of this procedure
chose differently).** The script is `scripts/train/compat_train.sh`; the runbook is
`docs/runbooks/compat-train.md`; the log is `receipts/train-log.ndjson`, one JSON object per line; a train's
`outcome` is `adopted` or `abandoned`; the share the script prints is `breakage_share_28d`. Reasons: the log
sits beside the receipts it cites and is appended by scripts, where a hand-edited table under `registries/`
would invite edits after the fact; the toolchain train (NF-02), its first run (NF-05) and the rehearsal (NF-06)
append to and read the same file under these names; and `landed` is already a status of an upstream item in
`registries/upstream.toml` (`open` → `landed` → `adopted`), so a train outcome named `landed` would give one
word two meanings in one log line. The other draft's names (`scripts/train/pin_move.sh`,
`registries/trains.toml`, `landed`/`aborted`, `breakage_share_4w`) are not used anywhere.

**1. Procedure `train(S, C)`: advance sibling S to commit C** (`scripts/train/compat_train.sh --sibling <FD>
--to <rev> [--dry-run]`; plain shell that calls the existing checks; it holds no policy of its own and edits
only this repository).

1. *Preconditions, each a refusal of the script by name if false.*
   (a) `frozen`: no freeze is in force. `franken-stack.lock` holds no `[freeze]` table whose `closed` field is
   empty (the table is opened and closed, as recorded commits, by the tournament freeze of the stack lock, bead
   N33b-03, for the length of a ten-fold tournament; it names the campaign and the frozen receipt).
   (b) `dirty-tree`: this repository's tree is clean and its last receipt verifies.
   (c) `not-a-descendant`: C is a commit on S's `main`, and the present pin is an ancestor of C
   (`git merge-base --is-ancestor`): a pin only moves forward.
   (d) `drift`: `cargo xtask check-stack` classifies every foundation in the train; S's checkout must be at C,
   clean, and either `on-pin` or `stale-lock` (a fast-forward of the lock). `drift` (dirty, retreated or
   diverged) stops the train with the classification; nothing is "fixed" by resetting. A dirty tree admits
   development builds only.
   (e) Disk and envelope preflight: the cold check of the M1 closure must be expected to fit one hour, 16 GiB
   and 8 cores.
   The target revision is the sibling's clean head on its `main`, as checked out by whoever works in that
   sibling under its rules. The script never checks out, fetches into, resets or otherwise writes to a sibling
   checkout (INV-SUITE-04); it reads the head and never writes there.
2. *Coupled siblings.* If S's own lock at C names other consumed siblings (FrankenSim's constellation names
   asupersync, FrankenSQLite, FrankenTorch, franken_numpy and frankenscipy), each is classified against that
   lock. A coupled sibling that must move moves in the same train (several siblings may ride one train when
   they must move together); one that disagrees and cannot move stops it.
3. *Move the pin.* In the row of S set `git_rev = C` and `toolchain` to the channel of S's own toolchain file
   at C. Regenerate the tracked lockfiles of every workspace (the core and `worker/`). Re-read the three
   settings Cargo does not propagate from a path dependency and repeat any change at this repository's root:
   the `[patch.crates-io] asupersync` entry, the FrankenSQLite profile overrides, and the build-identity
   environment for the linear-algebra crate.
4. *Receipt.* `cargo xtask check-stack` writes the new receipt: revisions, `dirty`, features, the hash and
   class of each sibling's own lock, lockfile hashes with package and registry counts, patches, profile
   overrides, build environment, duplicates, and the commands run with output hashes. Paths in it are
   repository-relative. Its hash goes into the foundation row.
5. *Build on T.* `cargo check --workspace --all-targets --locked`, recording cold and warm times, peak memory
   and package count against the machine envelope (one hour, 16 GiB, 8 cores).
6. *Adapt.* If the build fails, the fix is confined to `frob-fsim` (and to bedrock-direct users for bedrock
   crates): a FrankenSim API change costs one crate. The script records `adapter_lines_changed` from the diff
   of `crates/frob-fsim`. An adapter change made inside the train rides in the train's one commit.
7. *Re-run the gates, each citing the new receipt.*
   (i) Every admission gate that has a record for S and is in use at the current milestone, at the new pin
   (for FrankenSim: path consumption INT-FSIM-01 with the G1 digest recomputed inside FrankenSim at C, the
   file-by-file tests INT-FSIM-02 to -11, the group gates of every enabled group, the worker fallback
   INT-FSIM-18 with the worker rebuilt), and INT-ASUP-01.
   (ii) The parity gates that compare this project's tiers with the referee and have S on their path
   (GATE-KIN-02, GATE-KIN-03, GATE-TRAC-02 for FrankenSim; GATE-SPARK-02 and GATE-CORTEX-02 for FrankenTorch).
   (iii) The foundation-fact probes (GATE-WS-06, GATE-WS-09): a probe that now passes upstream is recorded as
   fixed and its interim posture is reviewed.
   (iv) Every fixture under `tests/upstream/`, and the switch-over rule of every upstream item that landed
   between the old and new revisions (read from `registries/upstream.toml`): a fixture that flipped from
   failing to passing means its upstream item has landed; its row becomes `landed`, its own switch-over rule is
   run in this train, and on adoption the row becomes `adopted`.
   (v) The six `xtask` checks.
   A train that re-runs only the gates on S's path is allowed; skipping a gate on S's path is not.
8. *Invalidate.* Memoized referee results carry the stack-lock digest in their keys and go cold by
   construction: none is served across a pin. Results in the Chronicle ledger carry the receipt hash of the
   binary that produced them; evidence recorded under the old receipt stays valid as history and cannot be
   offered as same-stack evidence until revalidated (`FROB-REF-890`, `stack-mismatch`). A referee worker built
   under another receipt refuses jobs (`FROB-REF-791`, `referee-worker-mismatch`). The frozen envelopes of the
   fidelity ledger are not re-baselined by a train unless the switch-over rule of the upstream item being
   adopted says "re-baseline the fidelity ledger once" (FD-FSIM-02 and FD-FSIM-12, once each, with a written
   rationale); the train then does it and records the old and new envelopes.
9. *Relock and record.* One commit carries `franken-stack.lock` with the row's `receipt` hash, the lockfiles,
   the receipt file, the admission records (a `DEPENDENCY_ADMISSION.md` record with this repository's commit,
   the commands, output hashes, measured values and the receipt hash), the gate rows and the train-log line.
   The commit message lists the commands and results.
10. *Abandon.* If any step from 5 on fails and cannot be repaired inside the train by an adapter change, nothing
    is adopted: this repository's lock, lockfiles and receipt return to the previous state (the sibling is not
    touched), the train-log line is still written with `outcome = "abandoned"` and the failing gate, and the
    remedy is one of: an adapter change in `frob-fsim` followed by a new train; an upstream work item, opened
    or updated with the failing fixture; or, when the trigger below is met, KILL-FSIM's fallback.

**2. The train log** (`receipts/train-log.ndjson`, schema `frob.train-log/1`; append-only; the strict reader
sits with the registry loaders in `frob-core`, and an unknown field is a load-time error). One line per train:

```json
{"schema": "frob.train-log/1", "id": "T-0007", "kind": "pin", "date": "2026-12-03",
 "moves": [{"sibling": "FD-FSIM", "from_rev": "<40 hex>", "to_rev": "<40 hex>", "class_before": "stale-lock"}],
 "receipt_before": "<BLAKE3>", "receipt_after": "<BLAKE3>",
 "gates": [{"gate": "INT-FSIM-01", "status": "pass"}, {"gate": "INT-FSIM-03", "status": "pass"}],
 "failing_gate": "", "upstream_items": ["FD-FSIM-16"], "adapter_lines_changed": 42, "wall_seconds": 12600,
 "outcome": "adopted", "blocked_dates": [], "cause": ""}
```

`kind` is `pin` for this procedure, `toolchain` for a line the toolchain train writes (NF-02), and `breakage`
for an incident with no train run (a sibling head that no longer builds on T; an adapter rewrite forced by a
sibling head that an upstream item needs). `moves` has one entry per sibling that rode the train. `outcome` is
`adopted` or `abandoned`; `failing_gate` is set on an abandoned line. `upstream_items` lists the items adopted.
`blocked_dates` lists the working days (whole days, ISO dates) on which this train or incident blocked work in
this repository, and `cause` says why in one sentence (for example "fs-mbd signature change broke frob-fsim at
the sibling head needed for FD-FSIM-12"). `receipt_after` equals `receipt_before` on an abandoned line.

Two of these fields are read outside this bead and are therefore fixed for `frob.train-log/1`: the field names
`kind` and `outcome` and the values `toolchain`, `adopted` and `abandoned`. The one-toolchain condition of
`check-stack` (N33c-08) reports a foundation off T as informational until the log holds a line with
`kind = "toolchain"` and `outcome = "adopted"`, and as a failure after; that line is written by step 7 of the
toolchain train (NF-02). Both value sets are closed (`kind`: `pin`, `toolchain`, `breakage`; `outcome`:
`adopted`, `abandoned`), and the strict reader rejects any other value as it rejects an unknown field. Renaming
either field, or giving a value another meaning, is a new schema version made in one commit with N33c-08.

**3. The breakage share (one definition, held by the trigger ledger N33a-10).** A breakage day is a working day
(Monday to Friday) on which a build, an admission gate or a parity gate of this repository failed for a cause
located in a sibling (established by running `xtask check-stack` first, and by the failing output), and
recovering needed a change to the airlock or to pins. In the train's terms that is: a failed or abandoned
train, an adapter rewrite forced by a sibling head that an upstream item needs, or a sibling head that no
longer builds on T. A day counts once however many incidents fall on it, and a day spent on planned upstream
work in a sibling's repository is not a breakage day. The share over a window of 28 consecutive calendar days
is the number of distinct breakage days divided by the 20 working days in it; the trigger is a share above
0.20, that is 5 days or more.

What the script does with it: for every date in `blocked_dates` it appends one `[[breakage_day]]` entry to the
trigger ledger (`docs/delivery/kill-fsim/ledger.toml`), with the ledger's fields: `date`, `pin_from`, `pin_to`,
`kind` (`build` for a failure of step 5, `admission-gate` or `parity-gate` for a failure of step 7,
`api-change` for an adapter rewrite), `located` (the sibling, from the `check-stack` classification),
`evidence` (the admission record hash or the commit of the adapter change) and `cost_hours`. At every train it
prints `breakage_share_28d`, the share for the trailing 28 days, and `scripts/train/breakage_share.sh` reports
the worst window in the whole log; both call the ledger's evaluation and compute nothing by another rule.

**4. Kill gate KILL-FSIM (decided at M0, then rolling).** Trigger: INT-FSIM-01 cannot pass within two weeks of
M0 effort, or its cold check exceeds the machine envelope, or the breakage share exceeds 0.20 in any four-week
window. Fallback (a): the volatile crates move behind a process boundary, one pinned FrankenSim worker per
device exchanging whole jobs through the same airlock traits; the worker can stay on an old pin while the core
moves. Fallback (b), only if (a) fails INT-FSIM-18 or the pin can no longer be built on any available
toolchain: lift the minimal referee set with provenance headers and golden tests, state "lift-only" in the
README, and keep the upstream items open. This bead supplies the breakage measurement; the evaluation of the
trigger is N33a-10's and the decision is an ADR (N33b-05).

**5. The first real train at M0 (done by N33bp2-01).** One real train of FrankenSim from the admission pin to a
newer clean head (the first pin move after INT-FSIM-01), recorded end to end: wall time, gates re-run with
results, adapter lines changed, and whether the three root settings needed a change. If the newer head breaks
admission, the run ends as a recorded `abandoned` train, which is an equally valid rehearsal. This bead's script
must make that run possible without edits: the real run uses it unchanged.

## Acceptance criteria

- [ ] `scripts/train/compat_train.sh --sibling <FD> --to <rev> [--dry-run]` implements steps 1 to 10 and refuses, by name, each of: freeze in force (`frozen`); this tree dirty (`dirty-tree`); target not a descendant of the pin (`not-a-descendant`); sibling checkout dirty or not at the target (`drift`).

- [ ] A train whose gate fails leaves `franken-stack.lock`, the lockfiles and `receipts/` byte-identical to their state before it, apart from one `abandoned` line in the train log.

- [ ] No gate result recorded during a train cites a receipt with `dirty: true` (INV-SUITE-03).
- [ ] A result recorded under the old receipt, offered as same-stack evidence after the train, is refused with `FROB-REF-890`; a memoized referee result from the old pin is a miss.

- [ ] On a scratch stack, the adopting commit of a train contains the lock, receipt, admission records and log line together (the real first train, and its acceptance, are N33bp2-01's).
- [ ] `xtask` still has exactly six subcommands.

## Test plan

### Unit tests
In `xtask/tests/train_guards.rs`, driving the real script against real git repositories created in a temporary
directory (each labelled `synthetic`: a stand-in sibling with one crate and a toolchain file; real `git` and
real `cargo metadata`; no mocks). DESIGN: the guard tests are Rust tests that run the shell script, so that the
one test runner of the workspace runs them; no second runner under `scripts/train/tests/` exists.
- `refuses_backward_move`: pin at commit 3 of 5, target commit 2; expected refusal `not-a-descendant`, exit non-zero, no file changed.
- `refuses_diverged_target`: target on a side branch not containing the pin; expected the same refusal.
- `refuses_dirty_sibling`: one tracked file touched in the sibling; expected class `drift`, refusal, and the receipt (if computed) with `dirty: true` and a changed `tree_hash`.
- `refuses_dirty_tree`: one tracked file touched in this repository; expected refusal `dirty-tree`.
- `refuses_under_freeze`: the stack lock holds a `[freeze]` table with an empty `closed` field; expected refusal `frozen` naming the campaign and the frozen receipt.
- `abandons_and_restores_on_gate_failure`: the stand-in's commit 4 changes a function's result that a stand-in gate checks; expected outcome `abandoned`, lock and lockfiles byte-identical to before, the old pin restored.
- `adopts_fast_forward`: target commit 5 that passes; expected new receipt, row `receipt` equal to its hash, one `adopted` log line.
- `writes_nothing_to_sibling`: the sibling directory is made read-only; `adopts_fast_forward` still passes.
- `reruns_listed_gates`: with a stand-in gate list of three, all three have new records; removing one from the run fails the adoption check.
- `adopts_upstream_switch_over`: an upstream item landed in the span has its switch-over gates in the run and its status becomes `adopted`.
- `breakage_share_known_answer`: a log with 20 working days of which 5 have an abandoned train; expected 0.25, above the 0.20 trigger; with 4, expected 0.20, not above it. `worst_window_found`: across a log with two clusters the worst window is reported.
- Property test for INV-SUITE-03: over 200 random sequences of (touch, commit, train) operations, no adopted line cites a receipt whose sibling entry is dirty.

`cargo test -p frob-core registries::trains`:
- `train_log_schema_round_trip`; `unknown_field_rejected`.
- `kind_and_outcome_values_closed`: lines with `kind` `pin`, `toolchain` and `breakage` and `outcome` `adopted` and `abandoned` load; `kind = "compat"` and `outcome = "landed"` are rejected; a `toolchain`/`adopted` line is found by the query N33c-08 uses (first line with that pair).
- `receipt_before_after_differ_on_move`; `receipt_identical_on_no_move` (KA-767).

### End-to-end script and logging
The rehearsal on a scratch stack, `scripts/e2e/train_rehearsal.sh`, is NF-06 and depends on this bead: it runs
an adopting train and an abandoned train on stand-in siblings, reads the new receipt back through
`frob doctor --json`, and offers stale evidence to get `FROB-REF-890`. The first real run is wrapped by
`scripts/e2e/first_train_fsim.sh` (N33bp2-01). This bead's own script logs in the same form whenever it runs,
in the guard tests and for real (per STD-E2E, to `target/e2e-logs/compat_train/<utc-timestamp>.ndjson` with a
transcript beside it), and the guard tests assert that the log of each synthetic run validates against
`frob.e2elog/1` and ends with a `summary`: one NDJSON line per step of the procedure, with the command, exit code, wall time, the envelope's
evidence block (receipt identity), the receipt hash before and after, the drift classes, the measured build
times and peak memory against the envelope, the names and results of the gates re-run, the metrics
`gates_rerun`, `gates_passed`, `adapter_lines_changed`, `breakage_share_28d` (threshold 0.20) and
`sibling_writes` (threshold 0), and on failure the first step that differed from the expected sequence.

### Known answers and negative controls
- KA-767: a receipt computed twice on an unchanged tree is byte-identical; touching one tracked file in a sibling flips `dirty`, changes `tree_hash`, and `check-stack` fails. The train's step 4 is run twice in the test and compared.
- Negative controls: each guard test above is a planted violation the script must catch. In addition: a train that skips a gate; a train that adopts on a failing gate; a script variant that resets a sibling to its pin (caught by the read-only sibling test); a train run with the row's `receipt` left at the old hash, which must fail `check-stack` (the stale-stack-lock plant of GATE-WS-01).
- Metamorphic relations: two trains to commits 4 then 5 leave the same lock, lockfiles and receipt as one train to commit 5 (the log differs by one line); a train that moves two siblings gives the same final receipt as two trains moving one each in either order, when neither depends on the other.
- Determinism lanes: the log line and the receipts are pure functions of the trees; the receipt is identical when the train is run twice from the same starting state, and on Linux and macOS (it holds no machine path).

## Considerations

- RISK-01 (High): FrankenSim API churn in `fs-mbd` and the `Component` trait, whose composition contract version is still 0. Earliest signal: adapter lines changed per pin move, and BET-04's breakage share, both in the train log. Mitigations: the airlock, the pin, this train, upstream item FD-FSIM-08 (freeze the trait as contract v1), and KILL-FSIM with the worker process first.
- RISK-23: dirty or off-pin sibling trees make a receipt unrepeatable. The receipt hashes tracked bytes when a tree is dirty, and no gate records a PASS on one. OPEN-SUITE-3 (owner): a dirty asupersync checkout is acceptable for development builds between receipts and for nothing else; that is the default until decided.
- The cold build of the M1 closure is 65 crates and about 2.06 million lines (FACT), so a full train is not free. OPEN-SUITE-5 (owner): the budget is the machine envelope until decided.
- Cadence is a judgement, not a rule: a train costs a cold build and the admission lanes, so it runs when an upstream item lands that this project wants, when a sibling fix is needed, and otherwise at each milestone exit.
- A train is also the moment a sibling's fix is noticed: step 7 (iv) is how an upstream item becomes `landed` without anyone remembering to check.
- Pins of every arm and every sibling, and T, are frozen for the length of the M7 tournament, because a ratio of times measured across a pin move is not one measurement; a train run during a freeze would void the tournament, which is why the freeze guard is a refusal and not a warning.
- The freeze record is declared by the tournament freeze of the stack lock (N33b-03): a `[freeze]` table in `franken-stack.lock` with `campaign`, `receipt`, `opened`, `closed` and `reason`. This procedure only reads it, and refuses with the message `check-stack` gives while frozen ("stack frozen for campaign <id>: <what moved>"); if the record's form changes, only guard (a) changes.
- The breakage log depends on honest entries. The script lowers the cost of honesty by prompting for an entry whenever a train is abandoned or `check-stack` reports drift.
- Other agents work in the siblings. The train never edits them; an upstream change needed to make a train pass is separate work in the sibling, with file reservations through Agent Mail and the sibling's own gates.
