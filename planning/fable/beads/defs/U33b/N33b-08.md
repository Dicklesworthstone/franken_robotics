## Background

Every sibling this project consumes is the owner's project. A limitation, defect or mismatch in a sibling is
therefore work this program does, in the sibling's repository, under that repository's own `AGENTS.md`, gates and
conventions. Each such change is an **upstream work item**: a bead here with the label `upstream`, mirrored in
the sibling's tracker, with a priority, an **interim posture** (what this project does until the change lands)
and a **switch-over rule** (what is re-run when it does). The interim posture and the switch-over rule exist so
that no milestone waits on a sibling change landing. The rules of the scheme: upstream changes are additive (a
new mode, type or feature, never a change to existing behaviour, with any lossiness self-described); each item
carries one reproducible failing fixture and a description of the needed argument or result; the sibling's rules
bind the work (for FrankenSim: its layer checks, its contracts, its unsafe-capsule discipline, its ban on
in-process foreign kernels in production paths, and its ban on branches and worktrees); other agents work in the
same repositories, so a change reserves its files through Agent Mail before editing and lands on the sibling's
`main` through the sibling's gates. The priority of an item states its value to this project and orders it in
this program's queue; no priority makes a milestone wait.

The risk register adds the sentence this bead enforces: **an upstream work item is never a mitigation by
itself; its interim posture is** (RISK-20: upstream work costs more than planned or is done in the wrong order;
signal: an item older than two milestones with no change of state, or a P0 item still open at the M0 exit
review). A posture that is only a sentence can lapse without anyone noticing: a dependency creeps in, a known
answer starts citing a routine that was never admitted. So each posture gets a standing test, and each
switch-over rule gets a checklist the compatibility train can execute.

## Scope

In: for the twelve items the suite chapter adds, one standing check per interim posture, wired to the upstream
registry; the switch-over checklist of each; the staleness report for RISK-20; tests with planted lapses.

Out: the upstream changes themselves and their beads; the registry and mirrored beads (BD-037), apart from the
two optional fields this bead adds to its loader; the admission and oracle tests whose results some checks read
(BD-033, BD-034, BD-035, BD-036, N33c-27); the two P0 executions (the upstream beads FD-ASUP-01 and FD-FMCP-01, proved by the gates of BD-008 and BD-023); items raised by other chapters (their own units test their postures).

**2. Wiring to the registry (schema extension of `registries/upstream.toml`, DESIGN).** Each item gains two
optional fields: `posture_test` (the name of its standing check) and `switch_over_steps` (the ordered, executable
form of the item's `switch_over`: a list of gate identifiers and commands). This bead adds both to the known-field
list of BD-037's loader in `frob-core`, whose rule that an unknown field is a load-time error stays; the schema
name stays `frob.upstream/1`, because the fields are optional and every file valid before is valid after. The
loader also checks that every gate and test that `switch_over` names appears among the item's
`switch_over_steps` when that field is present, so the two cannot drift apart. The registry test fails if an item with status `open` or `landed` has no `posture_test`, or names one
that does not exist. DESIGN: the rule is enforced for the twelve items of the table and for every other item whose
row sets `posture_test`; an `open` or `landed` item of another chapter without one is not a failure here (its own
unit owns its posture) and is listed by the staleness report of step 5 as `posture: untested`, a RISK-20 signal.
An item whose status is `adopted` must have no remaining local posture code flagged
`remove-on-switch-over` (each such site carries a comment tag with the item identifier, and a grep-level test
counts them).

**3. The standing checks** live in `crates/frob-conformance/tests/upstream_postures.rs`, one test per item,
named `posture_fd_fsim_10` and so on. Most are thin: they read the result of the admission test or the
dependency rule that already measures the property and assert it still holds, so that a lapse fails here with
the item's name even if the original test was edited. Where a capability does not exist yet (the eviction oracle
before M2) the test logs `skipped: capability absent`, which is not a pass.

**4. Switch-over checklists.** `scripts/train/switch_over.sh <item>` prints and runs the `switch_over_steps` of
an item inside a compatibility train: the gates to re-run, the local code to delete or replace (by tag), the
status change `landed` → `adopted`, and the one-time actions such as "re-baseline the fidelity ledger once".
The train's landing check fails if a landed item in the span has unexecuted steps.

**5. The staleness report (RISK-20).** `scripts/train/upstream_report.sh` lists items older than two milestones
with no change of state, P0 items still open, `open` or `landed` items with no `posture_test`, and items whose mirrored bead in the sibling changed state without
the bead here (the signal of RISK-55, a collision with other agents in a sibling). It is run at every milestone
exit review.

## Acceptance criteria

- [ ] Each of the twelve items has a `posture_test` in the registry and the named test exists; eleven pass at M1 and the eviction-oracle row is logged as skipped until M2.
- [ ] Each planted lapse fails its own test and names the item: `fs-g1-train` added to a manifest; a known-answer row citing `planar_drive`; an adapter truncating 22 contacts to 21; the salt removed from the root config; `use fs_qty::…` in `frob-analyze`; a receipt without `own_lock`; a bare stride tuple in a boundary signature; the MCP library made a hard dependency of `frob-cli`; the forbidden frankentui feature enabled; an identifier whose text form breaks the shared grammar.
- [ ] The registry test fails an `open` item with no posture test and an `adopted` item with remaining `remove-on-switch-over` tags.
- [ ] `switch_over.sh` on a scratch registry executes the steps of one item in order and refuses to mark it `adopted` when a re-run gate fails.
- [ ] The staleness report lists a planted stale item and a planted P0-still-open item, and is attached to the M1 exit review.

## Test plan

### Unit tests
- `posture_fd_fsim_10` … `posture_fd_fker_01`: twelve tests, each asserting the observable in the table.
- `lapse_<item>_caught`: ten planted lapses behind test-only fixtures (scratch manifests, synthetic registry rows labelled `synthetic`), each expected to fail its posture test.
- `registry_open_item_needs_posture_test` (one of the twelve without it fails); `other_chapter_item_without_posture_listed_untested` (a synthetic `open` item of another chapter without `posture_test` passes the registry test and appears in the staleness report as `posture: untested`); `registry_adopted_item_has_no_tags`.
- `build_without_salt_fails_closed`: a scratch consumer of the linear-algebra crate with both build-identity variables unset fails at the build script, as the sibling intends.
- `upstream_loader_accepts_posture_fields`: a row with `posture_test` and `switch_over_steps` loads; a row with another unknown field still fails; a row whose `switch_over_steps` omits a gate its `switch_over` names fails with both fields named.
- `identifier_text_form_round_trip` (the posture of FD-FKER-01): reads the result of N33c-27's oracle test `franken_kernel_text_forms_agree` (`TraceId`, `DecisionId` and `DecisionPolicyId` against the sibling's `PolicyId`) and its `ClaimId` and `EvidenceId` grammar tests, and fails with the item's name if any is absent or failed; it runs no second round trip and adds no second edge to franken-kernel, whose one owner is N33c-27.
- `stale_item_reported`: an item created at M0 with no state change is reported when the current milestone is M2 or later.

### End-to-end script and logging
`scripts/e2e/suite_upstream_postures.sh`: runs the posture tests, then on scratch copies plants three lapses (a
forbidden dependency, a cited non-oracle, a removed salt) and expects the matching failures; runs
`switch_over.sh` on a scratch item; runs the staleness report. Logged per STD-E2E: command, exit code, wall time,
metrics `postures_checked` (12), `postures_passing`, `postures_skipped` (with reasons), `lapses_caught` (3 of 3),
`stale_items`, `p0_open`, the hash of `registries/upstream.toml`, and on failure the item and the observable
that lapsed.

### Known answers and negative controls
Known answers are those of the admission tests the postures read (the 2×2 stride case reads element 3; the
22-contact refusal; the three PPO probe values; the chord (0, 2/π) m). Negative controls: the ten planted lapses.
Metamorphic: reordering registry rows changes no verdict; marking an item `adopted` without removing its tagged
local code flips exactly one test. Determinism: structural checks; pure functions of tracked files.

## Considerations

- What the upstream work items do not change: M1 depends only on FrankenSim, asupersync and FrankenSQLite, and no upstream item is on the M1 critical path. If none has landed the plan still ships: the referee lowers joints, owns its transaction and migrates witnesses; the Metal backend runs inside the gateway's present limits; and if the two P0 items cannot land within the M0 budget, KILL-MCP's fallbacks apply. An upstream change that lands is adopted only through its switch-over rule; a sibling's newer clean head is never rolled back locally, and neither a pin nor T moves during the tournament.
- The costs of upstream work, its ordering and collisions with other agents are risks, not schedule items: RISK-20 (owner: project lead) and RISK-55 (file-reservation conflicts on a sibling path; mitigation: reservations before any edit, small additive changes, the interim posture ships meanwhile).
- This bead adds tests and two small scripts, no process. Each test names a defect class it would catch (a lapsed posture), which is the bar for adding any check.
- Third-party gaps are not upstream work items and are not tested here (the `cudarc` bindings are confirmed or refuted at their own admission gate).
