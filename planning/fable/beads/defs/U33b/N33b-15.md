## Background

The design studio answers the same question many times with small changes: an agent edits one parameter and asks
for the analyses again. A **memo graph** stores every result by the content identity of its inputs, so that an
edit recomputes only what it touched. Its mechanism and policy are bead BD-111. This bead supplies the storage
record underneath it and the admission of the sibling crate that provides one.

FACT (FrankenSim head `483d09c682f2`): `fs-recompute` is 3,034 library lines (5,661 with tests); a non-optional
path dependency on it compiles 10 other FrankenSim crates plus FrankenSQLite; it needs `fs-qty`. Its manifest
describes a content-addressed Merkle graph of results with slack, skip-soundness certificates and invalidation.
Read in its source: a skip oracle (`Store::can_skip` serves a node cached under a looser requirement if it
achieved enough), pins that are never evicted, an independent checker, and a trip-wire error
(`StoreError::DeterminismViolation`) raised when two different results are offered for one key. It is reached by
the memo graph only, from `frob-verbs` and `frob-chronicle`, through the airlock's `ledger` feature group (on by
default).

Each feature group of the airlock has a **group gate**: the form of the first path-consumption gate applied to one
group at the milestone that first uses it. The group compiles from this repository behind its feature, one known
answer passes through the airlock trait, and one negative control fails. For `fs-recompute` the gate is
INT-FSIM-16 (first needed at M1; thresholds are TARGETs):

| Known answer through the airlock | Negative control |
|---|---|
| Incremental recomputation equals full recomputation on 10⁴ random edit sequences | An input missing from a key is caught by the shadow recompute within 64 hits |

Whether the sibling crate passes on the project's one toolchain T is open question OPEN-ATEL-3 (owner: suite
lead; it blocks the memo-graph gate). Its fail-closed default: **the same node record is implemented locally in
`frob-chronicle`, against the same known answers.** The memo graph must not care which implementation is behind
the trait, so this bead defines the trait and the record first and admits the sibling second.

## Scope

In: the node record and the `Recompute` trait; the sibling-backed implementation behind feature `ledger`; the
local implementation in `frob-chronicle` used when admission fails; the INT-FSIM-16 test (both the known answer
and the negative control) run against whichever implementations build; the admission record and the OPEN-ATEL-3
decision note.

Out: key derivation per node kind, the shadow policy in production, stop-serving and `--no-memo` (BD-111);
episode nodes (BD-220); eviction and the pager-policy oracle (BD-220 with INT-FSQL-02); the ledger and session
traits of the same group (the chronicle beads); revalidation grades (the Atelier beads).

## Technical approach

```rust
// DESIGN: intent, not signatures. In frob-core so that both implementations and the memo graph share it.
pub struct NodeRecord {
    pub kind: NodeKind,                    // subterm-compile | analysis | controller | scene-compile | episode | derived
    pub key: Blake3,                       // derived from the declared inputs of the kind (never hand-written)
    pub inputs: Vec<InputRef>,             // content hashes of the inputs, in declared order
    pub output: Blake3,                    // digest of the result bytes
    pub class: DeterminismClass,           // D0 … D2: the class inside which a hit is bit-identical
    pub achieved_error: Option<Ratio>,     // only for analyses that record one; enables tolerance-level reuse
    pub cost: RecomputeCost,               // measured cost of producing it; used by admission and eviction
    pub stack_receipt: Blake3,             // the resolution receipt of the binary that produced it
}
pub trait Recompute {
    fn get(&self, key: &Blake3) -> Result<Option<NodeRecord>, StoreRefusal>;
    fn put(&self, node: NodeRecord) -> Result<PutOutcome, StoreRefusal>;     // Inserted | Identical | Violation
    fn can_skip(&self, key: &Blake3, need: &Requirement) -> Result<Skip, StoreRefusal>;
    fn invalidate(&self, input: &InputRef) -> Result<Vec<Blake3>, StoreRefusal>;   // keys that depended on it
    fn pin(&self, key: &Blake3, reason: PinReason) -> Result<(), StoreRefusal>;
    fn check(&self, key: &Blake3) -> Result<CheckVerdict, StoreRefusal>;     // the independent checker's replay
}
```

Rules:
1. **Identical or violation.** `put` of a key that exists with the same `output` returns `Identical`; with a
   different `output` it returns `Violation` (the sibling's `DeterminismViolation`, converted and not
   reinterpreted) and stores nothing.
2. **No reuse across pins.** `stack_receipt` is part of every key that covers a referee-backed result; a lookup
   under another receipt is a miss.
3. **Tolerance-level reuse is opt-in by kind.** `can_skip` may answer from a looser cached requirement only when
   `achieved_error` is present; for every other kind it answers only on an exact key.
4. **Pins outlive eviction.** A pinned node is never evicted by either implementation.
5. **Storage.** Bytes live in the Chronicle store (FrankenSQLite, admitted by INT-FSQL-01); the fallback is an
   append-only JSON-lines file with the same schema.

**Two implementations.** `frob_fsim::ledger::SiblingRecompute` wraps `fs-recompute` (feature `ledger`).
`frob_chronicle::memo::LocalRecompute` is a plain content-addressed table with a reverse index from inputs to
keys; about a few hundred lines, no skip-soundness certificates, exact-key reuse plus rule 3. Both pass the same
conformance suite below; the memo graph is built against the trait.

**INT-FSIM-16, the known answer.** A synthetic computation graph (labelled `synthetic`): a directed acyclic graph
of 48 nodes in 6 layers, each node an integer function of two to four parents and one leaf parameter (for
example a wrapping sum of parent values times a small odd constant plus the leaf), so that values are exact and
any stale parent changes the result. An edit sequence is 1 to 20 edits, each setting one leaf to a new value.
For each of 10⁴ seeded sequences, addressed by `(seed, index)`:
1. evaluate incrementally: after each edit, `invalidate` the leaf, recompute the returned keys in topological
   order through `get`/`put`, and read every node;
2. evaluate fully: rebuild an empty store and compute every node from scratch;
3. pass when the 48 output digests agree after every edit of every sequence.
The run also asserts that the number of recomputed nodes per edit equals the size of the edited leaf's
descendant set (an implementation that recomputes everything would pass step 3 and prove nothing).

**INT-FSIM-16, the negative control.** Node kind `planted::missing-input` derives its key from all inputs but
one. After an edit to the omitted input, lookups of that kind are stale hits. A minimal shadow harness in the
test recomputes one hit in every window of 64 consecutive hits of a kind and compares digests. Pass: the first
mismatch is reported at or before the 64th hit after the edit, `put` returns `Violation`, and the harness stops
serving the kind. A second control, `planted::recompute-nothing`, skips invalidation entirely and must fail the
known answer.

**Admission record and the open question.** `DEPENDENCY_ADMISSION.md` entry: commit, command, output hash, receipt
hash, whether the sibling implementation compiled on T, the 10⁴-sequence result for each implementation, the hit
ordinal at which the control was caught, and the added compile cost. The record states the OPEN-ATEL-3 outcome:
`sibling admitted` (the memo graph uses `SiblingRecompute`) or `local record in force` (the default), with the
reason. Claim: Known answer; class `Tested`; tier host; determinism D0.

## Acceptance criteria

- [ ] Incremental recomputation equals full recomputation on 10⁴ seeded random edit sequences, for every implementation that builds; the recomputed-node count per edit equals the descendant-set size.
- [ ] The planted missing-input kind is caught by the shadow harness within 64 hits; the `put` of the differing result returns `Violation` and stores nothing.
- [ ] `LocalRecompute` passes the full conformance suite on its own, so the fallback of OPEN-ATEL-3 is exercised whether or not the sibling is admitted.
- [ ] A node stored under one stack receipt is a miss under another; pinned nodes survive an eviction pass.
- [ ] No crate other than `frob-fsim` names an `fs-recompute` type; `frob-verbs` and `frob-chronicle` are the only crates on the group's consumer list for this crate (`xtask check-deps`).
- [ ] INT-FSIM-16 has an admission record citing a receipt hash and a row in `registries/gates.toml`; the OPEN-ATEL-3 outcome is written in the record and handed to its owner.

## Test plan

### Unit tests
A shared suite `frob_core::memo::conformance` instantiated for both implementations:
- `put_get_round_trip`; `put_identical_is_idempotent`; `put_different_output_is_violation`.
- `invalidate_returns_exact_descendants`: on the 48-node graph, editing a layer-0 leaf returns that leaf's descendant keys and no others.
- `incremental_equals_full_1e4` (long lane; 10² sequences in the default lane): expects zero digest differences; reports `(seed, index, edit, node)` of the first difference.
- `recomputed_count_equals_descendants`.
- `can_skip_exact_key_only_without_achieved_error`; `can_skip_looser_requirement_with_achieved_error`.
- `miss_across_stack_receipts`; `pinned_survives_eviction`.
- `missing_input_caught_within_64_hits`: expects the catch ordinal ≤ 64 and the kind no longer served.
- `recompute_nothing_mutant_fails`.
- `sibling_refusal_converted_with_reason` (sibling implementation only).

### End-to-end script and logging
`scripts/e2e/suite_airlock_groups.sh` (bead N33b-21), step `ledger_recompute`: runs the long lane for both
implementations under a timeout and reads `frob doctor --json` for the gate row and the OPEN-ATEL-3 note. Logged
per STD-E2E: command, exit code, wall time, evidence block, metrics `edit_sequences` (10⁴), `digest_mismatches`
(threshold 0), `control_caught_at_hit` (threshold ≤ 64), `implementation` (`sibling` or `local`), `cold_check_s`,
and on failure the address of the first differing node with both digests.

### Known answers and negative controls
KA-771: incremental recomputation equals full recomputation on 10⁴ random edit sequences, exact; its negative
control: an input missing from a key is caught by the shadow recompute within 64 hits. Second control: the
recompute-nothing mutant. Metamorphic: applying the edits of a sequence in an order that commutes (edits to
different leaves) gives the same final digests; relabelling node identifiers leaves the set of output digests
unchanged. Determinism: the result digests are a pure function of `(seed, index)`; twice on one machine, across
worker counts, debug and release, and across platforms (integer arithmetic only) they are identical.

## Considerations

- OPEN-ATEL-3 (owner: suite lead; blocks GATE-ATEL-12 and -15): the default holds until decided. Nothing above the trait changes with the decision, which is the point of defining the record in `frob-core`.
- `fs-recompute` depends on `fs-qty`, which enables an incomplete nightly compiler feature. A toolchain train can therefore break this crate's build without touching its code; the local record is also the answer to that.
- The sibling's skip-soundness certificates are not required by the memo graph at M1. If they are adopted later for analyses with achieved errors, that is a change to rule 3 with its own test.
- The 10⁴-sequence run is integer arithmetic on 48 nodes and takes seconds; it is still kept in the long lane with a 10² subset by default, so that the default lane stays fast.
- An admission is never inherited: the gate is re-run at each pin move by the compatibility train, and a store written under the old receipt is treated as cold.
