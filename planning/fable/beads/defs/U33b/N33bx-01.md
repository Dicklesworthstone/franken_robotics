## Background

Family certificates are checked by one program, the offline auditor `frob-verify`, which depends on the standard
library alone. The open question OPEN-LEMMA-4 asks whether one auditor is enough or a certificate needs a second
independent checker, and names two candidates: FrankenSymPy's capsule consumer for polynomial kinds, and
`fs-checker`, FrankenSim's checker of evidence packages outside the solving process. The decision bead N12-29
runs a disagreement experiment with one arm per candidate. Its `fs-checker` arm has nothing to run on.

The reason is a rule that stays. The suite chapter classes `fs-checker` as **Pattern**: it is the model for
`frob-verify` and is not linked, because it reaches the units crate `fs-qty` through its package format and the
auditor may depend on nothing. The dependency check enforces "no direct edge from any crate of this repository"
(N33b-09), and only its pin facts are on file (N25a-32). So the checker can serve the experiment in one way
only: as a separate process, built in FrankenSim's own tree at the pinned commit, under an admission record of
its own. A posture belongs to a use, not to a repository: the same crate stays Pattern for the auditor and
becomes **Oracle, reached as a Subprocess** (development and test only) for the experiment.

FACT (read 2026-11-22 at FrankenSim head `95a7fba8e8a7`; re-read at the pin by this bead's lane):
`frankensim/crates/fs-checker` is a library with no binary target. Its only direct dependency is the package
format `fs-package` (the manifest states the hard constraint: no solver stack and no licence gate in its graph).
Entry points: `check(&EvidencePackage) -> CheckReport` and `check_json(text, expected_root, verifier)`, which
denies every external capability by default; `Verdict` is `Pass` or `Fail`; `CHECKER_PROTOCOL_VERSION` is 7 and
`CHECKER_SUPPORTED_PACKAGE_FORMAT` is 9. Its semantic module is a closed registry of two witness families,
`frankensim/exact-interval` (a bounded interval straight-line program) and `frankensim/bounded-linf-residual`
(a dense linear residual certificate), with caps: 4,096 interval nodes; residual rows and columns each at most
128 and at most 16,384 entries; a witness of at most 256 KiB; at most 4,096 witnesses and 8 MiB of witness
payload per package; at most 10⁶ charged arithmetic operations per package. FrankenSim's own command line links
the checker but only checks packages retained in its ledger by run identifier
(`crates/fs-cli/src/package.rs`); nothing checks a file handed to it.

So an out-of-process run needs an entry point that does not exist. Every sibling is the owner's project: the
missing entry is work this program does in FrankenSim's repository, as upstream work item `FD-FSIM-42` (row
written by NFx-01), priority P3, with an interim posture and a switch-over rule. Rejected: a runner crate in
this repository with a path dependency on `fs-checker`, in any workspace (it is the forbidden edge, and
`check-deps` fails it); adding a runner file to a scratch export of the sibling (a local patch standing in for
an upstream change); dropping the arm without a record (the experiment would then silently cover fewer kinds).

## Technical approach

**1. The upstream change (in `frankensim`, crate `fs-checker`, under FrankenSim's `AGENTS.md`).** Additive: a
binary target `fs-checker` with no new dependency (DESIGN; the final shape is decided under the sibling's
rules, after re-reading what the package format's public writer allows):
- `fs-checker check <package.json> [--expected-root <hex>]`: runs `check_json` with every capability denied
  and prints one line of canonical JSON: schema `fs-checker.verdict/1`, protocol and package-format versions,
  `verdict` (`pass` or `fail`), the Merkle root, per-family counts and operations charged, the findings with
  their codes, and the decision hash. Exit 0 pass, 1 fail, 2 usage or unreadable input.
- `fs-checker pack --family <id> <witness-file>`: builds a minimal package around one canonical witness with
  the package format's own writer, so that a foreign producer does not re-implement content addressing.
- `fs-checker registry`: prints the closed registry (families, schema version, every cap) as canonical JSON.
Input is read up to the package cap plus one byte and refused above it; the output is a pure function of the
input bytes. Binding rules: the sibling's layer checks, contract (`CONTRACT.md` of the crate gains the entry),
unsafe-capsule discipline, no branches and no worktrees; files reserved through Agent Mail first; landing on
the sibling's `main` through its own gates; a mirrored bead in its tracker whose identifier goes in the row.

**2. The use.** The `FD-FSIM` row of `franken-stack.lock` gains one entry in `uses`: postures oracle and
subprocess; purpose "re-check of interval and residual witnesses in the second-checker experiment"; confined to
a child process driven from `frob-conformance`; admission by this bead's record; fallback "arm not run".

**3. The tool at the pin.** `tools/oracle/build_fs_checker.sh` exports the pinned FrankenSim commit read-only
into `target/oracle/frankensim-<rev>/`, builds there with FrankenSim's own toolchain file, lockfile and Cargo
configuration (`cargo build --release --locked -p fs-checker --bin fs-checker`), and writes the binary to
`target/oracle/fs-checker/<rev>/` with its BLAKE3. No manifest of this repository names the crate; the sibling
checkout is not written.

**4. The admission lane** (`crates/frob-conformance/tests/oracle_fs_checker.rs`; it starts a child process and
links nothing of the sibling). Each call: closed standard input, no network, a wall-time limit of 60 s, output
capped at 1 MiB; a timeout or a crash is a failure of the call, never a pass.
1. `registry` equals the pin facts on file: exactly the two families and the caps above.
2. *Interval known answer.* f(x, y) = x·y + 3 on x ∈ [1, 2], y ∈ [−1, 4]. Each variable occurs once, so
   interval evaluation is exact: x·y ∈ [−2, 8] and f ∈ [1, 11]. A witness claiming f ∈ [0, 12] passes; one
   claiming f ∈ [2, 10] fails.
3. *Residual known answer.* A = [[2, 1], [1, 3]], x = (1, 2), b = (4, 6): A·x = (4, 7), residual (0, 1),
   largest absolute entry 1. A claimed bound of 2 passes; a claimed bound of 0 fails.
4. *Closed registry and caps.* A witness of family `frob/poly-identity` fails with a finding that names the
   family; an interval program of 4,097 nodes and a residual with 129 rows are refused by the cap and not
   evaluated; a package with one flipped byte fails on its content address.
5. *Firewall.* `cargo metadata` of every workspace of this repository contains no package named `fs-checker`.
The witness encoding (schema version 1 of each family) is re-read at the pin; the numbers of cases 2 and 3 are
fixed here and only their encoding follows the sibling.

**5. The record** (`frob.admission/1`, written by the record writer under `--gate INT-FSIM-01`, FrankenSim's
admission gate, with `covers` naming this use, the form N33a-21 and N33a-22 use for a later use of an admitted
foundation; the gate register has no row for it): `foundation = "FD-FSIM"`, `covers.tool = "fs-checker"`, no
crate listed, the tool's repository revision and the BLAKE3 of the binary that
ran, the command, output hash, receipt hash, the four `facts_reread`, the measured verdicts, the controls
caught, and `status`. `DEPENDENCY_ADMISSION.md` gains the entry `fs-checker (oracle, subprocess; first use
M4)`; `frob doctor` lists it. On the conformance side the tool is a row of the oracle register (N38a-04,
reached through NFx-01): `[[oracle]]` `id = "fs-checker"` in `crates/frob-conformance/registry/oracles.toml` with
`posture = "out-of-process"`, `pin = { kind = "commit", repo = "frankensim", value = <pinned commit> }`,
`admission = { test = "oracle_fs_checker", control = <the three planted drivers' rows>, status, date }`, `roles =
["second-checker:exact-interval", "second-checker:bounded-linf-residual"]` (development and test only), and
`held_out = "no out-of-process entry at the pin (FD-FSIM-42 open)"` while the record is `not-run`; it serves N12-29's
arm only once `admission.status = "admitted"`, and a pin move goes through a `[[pin_move]]` record. The three
planted drivers are rows of `crates/frob-conformance/registry/controls.toml`. Claim: Known answer; class `Tested`; tier host; determinism D0.

**6. Interim posture.** Until the entry exists at the pin the record is `not-run` with the reason "no
out-of-process entry at the pin (FD-FSIM-42 open)", the `fs-checker` arm of N12-29 is recorded `not run`, and
OPEN-LEMMA-4's fail-closed default holds: one auditor with the mutation suite of GATE-LEMMA-03.

**7. Close rule and switch-over.** This bead closes when the record is `pass` or `fail`, or when the M4 exit
review starts, whichever comes first; in the last case the record is `not-run`, the row stays `open`, and N12-29
decides on its other arms. Switch-over, whenever the change lands: move the pin through the compatibility train
(new receipt, admission and parity gates, relock), run this lane, then run the arm of N12-29; the decision
record is amended only if the arm shows an "auditor too permissive" disagreement.

## Test plan

### Unit tests

In FrankenSim (under its conventions): `cli_check_pass_and_fail_exit_codes`; `cli_output_is_canonical_and_stable`;
`cli_pack_roundtrip` (a packed witness checks to the same verdict as the same witness inside a package built
by the library); `cli_registry_lists_two_families`; `cli_refuses_oversize_input_unread`.
Here, `cargo test -p frob-conformance --test oracle_fs_checker`:
- `registry_matches_pin_facts`: two families; caps 4,096, 128, 16,384, 10⁶.
- `interval_known_answer`: [0, 12] pass; [2, 10] fail.
- `residual_known_answer`: bound 2 pass; bound 0 fail.
- `unknown_family_rejected`; `interval_cap_refused_unevaluated`; `residual_cap_refused`; `flipped_byte_fails_content_address`.
- `no_fs_checker_package_in_any_workspace`.
- `missing_binary_records_not_run`: with no tool present the lane writes a `not-run` record and reports zero passes; it never passes.
- `oracle_row_held_out_until_admitted`: with the record `not-run` the `fs-checker` row of `oracles.toml` is `held_out` and is refused as a second checker; after a scratch `pass` record with its control caught it is `admitted`.
- `child_timeout_is_failure`: a `synthetic` stand-in that sleeps past the limit yields a failed call.

### End-to-end script and logging

`scripts/e2e/oracle_fs_checker.sh`: builds the tool (or records its absence), runs the lane, writes the record,
then asserts through `frob doctor --json` that the record is listed with its receipt hash and status. Logged
with the shared helper to `target/e2e-logs/oracle_fs_checker/<utc>.ndjson`: `cmd` events with the exact command
lines, exit codes and wall times; `metric` events `tool_rev`, `tool_blake3`, `cases_passed` (of 8),
`controls_caught` (of 3); one `assert` event per case with the verdict line the tool printed; the firewall
assertion; on failure the case name, the expected and the printed verdict, and the path of the offending
package; a final `summary` with the record's status. No bundle content of a private scene is logged.

### Known answers and negative controls

Known answers: the exact range [1, 11] of x·y + 3 on the box; the residual (0, 1) with largest entry 1.
Negative controls of the lane (planted drivers, each must fail a test): one that reads exit code 1 as a pass;
one that reports a pass when the binary is absent; one that loosens a failing claim before sending it (it
sends [0, 12] where the case says [2, 10]). Controls of the tool: the four rejections of case 4. Metamorphic:
widening an accepted claim never turns it into a failure; reordering independent witnesses in a package leaves
each verdict unchanged. Lanes: verdict bytes identical twice on one machine and on both platforms.

## Considerations

- The oracle reads two witness families. It can only speak for the kinds N12-29 translates without loss
  (`interval-box`, and `taylor-box` where the translation is exact); a translation defect shows up as a
  disagreement and is classified there, not here.
- A second program is a second trusted base for the experiment only. No certificate becomes `Certified` because
  this tool accepted it, and no report names it as a checker unless OPEN-LEMMA-4 is decided that way.
- Building in a read-only export costs one cold build of a small cone (the package format and its
  dependencies); the binary is cached per revision.
- RISK-55 (collisions in the sibling) and RISK-36 (the proposer and the checker share a defect) are the two
  risks this bead touches; the first is met by file reservation, the second is what the experiment measures.
- If the sibling's maintainers' rules place the entry elsewhere (for example in its command-line crate), the
  lane changes only its build command.
