## Background

Foundry (crate `frob-foundry`, tier Frontier, milestone M5) allocates manufacturing tolerances from
sensitivities: a feature with sensitivity sᵢ and cost coefficient cᵢ gets tᵢ ∝ (cᵢ/sᵢ²)^(1/3) under a variance
budget. That allocation is first order. It is wrong where the quantity is not close to linear over the
tolerance band, and the design says what happens then: a robustness check evaluates the true quantity at the
band extremes, and "features that fail fall back to worst-case boxes by interval evaluation
(`fs-uq::product_epistemic`), which is also the fallback of KILL-TOLERANCE". A worst-case box answers a
different question from a variance: over every combination of deviations inside the tolerances, what are the
largest and smallest values of the quantity?

FrankenSim's `fs-uq` sits in the airlock's `stats` feature group, admitted at M3 for sampling, multilevel
estimation and importance weights. Its consumer list did not name `frob-foundry`; ADR-SUITE-03 (N33bx-02) adds
it. The module Foundry needs was not part of the M3 admission. An admission is never inherited: a use first
made at M5 is admitted at M5, by its own record, at the pin of that day. This bead builds the entry and admits
it.

FACT (read 2026-11-22 at FrankenSim head `95a7fba8e8a7`; re-read at the pin by this bead's lane):
`frankensim/crates/fs-uq/src/product_epistemic.rs` (452 lines) is "worst-case propagation of epistemic
parameter boxes, not probability sampling". The caller supplies a callback that must **enclose one fixed
real-valued model on every closed box it is given, including singleton boxes**; "ordinary point samples or
corner evaluations are not enclosures". The bounds are conditional on that contract, and the producer "does
not mint Verified evidence or validate physical models". `EpistemicConfig` holds an absolute tolerance in the
units of the quantity and a maximum of live cells (at most 4,096). `EpistemicExecution::new(plan, config)` is
advanced by `advance(allowance, cancelled, enclose)`, or by `advance_until_compliance` for a decision against
an upper limit, with interruptible variants. `EpistemicStatus` is one of `Paused`, `Complete` (both extrema
enclosed to the requested width), `DecisionReached`, `EvaluationLimit`, `CellLimit`, `ParameterResolution`,
`Cancelled`, `Refused`.

The hazard is in the callback. A caller that evaluates the quantity at the corners of a box and returns the
hull has satisfied the type and broken the contract, and for a quantity with an interior extremum the result
is too small. Rejected: computing worst cases in Foundry by corner enumeration (wrong for exactly the
features that reach this path, the ones the linear model fails on); Monte Carlo over the tolerance band (a
sample maximum is not a bound); linking `fs-uq` from `frob-foundry` (rule L-2).

## Technical approach

**1. Trait (DESIGN: intent, not signatures; module `frob_fsim::stats::epistemic`, feature `stats`).**

```rust
pub trait EpistemicBox {
    fn limits(&self) -> EpistemicLimits;                       // live-cell cap and parameter cap, read at the pin
    fn extrema(&self, domain: &[ParamBox], cfg: &EpistemicCfg, cx: &Cx,
               enclose: &mut dyn FnMut(&[Interval]) -> Result<Interval, EncloseError>)
        -> Result<EpistemicOutcome, RefereeRefusal>;
    fn decide_upper(&self, domain: &[ParamBox], limit: f64, cfg: &EpistemicCfg, cx: &Cx,
                    enclose: &mut dyn FnMut(&[Interval]) -> Result<Interval, EncloseError>)
        -> Result<UpperDecision, RefereeRefusal>;
}
pub struct EpistemicCfg { pub absolute_tolerance: f64 /* units of the quantity */, pub max_cells: usize, pub max_evaluations: u64 }
pub struct EpistemicOutcome { pub minimum: Interval, pub maximum: Interval, pub status: EpistemicStatus,
                              pub evaluations: u64, pub cells: usize, pub witness: Option<ParamBoxWitness> }
pub enum UpperDecision { Holds, Violated { witness: ParamBoxWitness }, Undecided { status: EpistemicStatus, maximum: Interval } }
```

`Interval` is the outward-rounded interval of the bedrock-direct crate. `minimum` encloses the true minimum
and `maximum` the true maximum; the worst-case range is [`minimum.lo`, `maximum.hi`].

**2. Rules.**
1. *Statuses are reported, never upgraded.* Only `Complete` means both extrema are enclosed to the tolerance.
   `CellLimit`, `EvaluationLimit`, `ParameterResolution` and `Cancelled` return the current outer enclosures
   with the status; the outer range is still valid and is wider than asked. The consumer decides what a wider
   range means (Foundry reports the feature with the wide box and the status, never as converged).
2. *The enclosure contract is spot-checked.* For each box the adapter hands to the callback it also evaluates
   the callback on up to 8 seeded singleton points of that box (addressed by cell identity, so the checks are
   reproducible) and refuses with `enclosure-contract-violated`, naming the box and the point, if a point
   value is not inside the box value. This catches corner sampling and stale closures; it proves nothing, and
   the contract says so.
3. *Class of the result.* An outcome is an enclosure conditional on the callback. It is `Certified` only when
   the callback is an interval extension that carries its own certificate (exact or interval evaluation of a
   kinematic map); with any other callback it is `Estimated`. The adapter records which.
4. *Capacities are data.* `max_cells` above `limits()` is refused by name; nothing is clamped.
5. *It converts and never reinterprets.* `Refused` and callback errors become typed refusals carrying the
   upstream reason; an empty or inverted box and a non-finite bound are refused before the sibling is called.

**3. Admission lane** (`crates/frob-fsim/tests/admission/epistemic.rs`, lane `--features stats`).
1. Facts re-read at the pin and recorded: the module's contract sentences, the status list, the cell cap, the
   signatures of `new` and `advance`.
2. *Linear stack.* q = x₁ + 4·x₂ with x₁ ∈ [−16.0, 16.0] µm and x₂ ∈ [−6.35, 6.35] µm (the worked allocation
   for sensitivities 1 and 4 under a 10 µm budget). Each variable occurs once, so the extension is exact:
   maximum 16.0 + 4 × 6.35 = 41.4 µm, minimum −41.4 µm, status `Complete` (the whole box evaluates exactly to
   the outer bounds; the evaluation count, which includes the sibling's own point boxes, is recorded and not
   asserted). The budget is a
   standard deviation of 10 µm on the stack with tolerances quoted at k = 3 (N33b-14), so the statistical
   half-width at the same k is 30 µm; the worst-case half-width is 1.38 times that (4.14 standard deviations),
   which is why a worst-case box is a fallback and not the default.
3. *Zero first-order sensitivity.* q = x² on x ∈ [−0.3, 0.3] mm: range [0, 0.09] mm². With tolerance 10⁻⁴ the
   maximum's enclosure contains 0.09 and the minimum's contains 0, each of width at most 10⁻⁴. A first-order
   model predicts no deviation at all.
4. *Interior extremum.* q = x·(1 − x) + y on x ∈ [0, 1], y ∈ [0, 0.1]: maximum 0.35 at x = ½, y = 0.1;
   minimum 0. With tolerance 10⁻⁶ both are enclosed to that width. The four corners give 0, 0.1, 0 and 0.1.
5. *Decision.* For case 4, `decide_upper(0.4)` is `Holds`; `decide_upper(0.3)` is `Violated` with a witness
   box that contains x = ½.
6. *Limits.* Case 4 with `max_cells = 4` and tolerance 10⁻⁹ ends in `CellLimit`; its outer range still
   contains [0, 0.35]; it is never reported `Complete`.
7. *Refusals.* An inverted box; a callback that returns NaN; `max_cells = 4,097`.

**4. Record.** `DEPENDENCY_ADMISSION.md` entry `fs-uq::product_epistemic (first use, M5)` under `FD-FSIM`:
`covers.crates = ["fs-uq"]`, commit, command, output hash, receipt hash, the facts, the measured enclosures,
evaluations and cells per case, the controls caught, status. No row in the gate register; `frob doctor` lists
it. Claim: Known answer; class `Tested`; tier host; determinism D0 (a fixed bisection order and seeded
spot-checks).

**5. If admission fails.** Worst-case boxes are computed in `frob-foundry` by plain interval evaluation with
uniform bisection over the bedrock-direct intervals, to a stated depth: valid, wider and slower. Each
`worst-case-box` feature of the tolerance report then carries `enclosure: "local-bisection"` in place of
`"product-epistemic"` (the per-feature field of N31a-33's report), and the failing case goes to the upstream register through
BD-037's procedure. KILL-TOLERANCE's fallback then rests on the local path.

### Known answers and negative controls

Known answers: ±41.4 µm; [0, 0.09] mm²; [0, 0.35]. Counterexample kept in view: "a zero first-order
sensitivity is not insensitivity" (the square). Negative controls (planted, each must fail a test):
`planted::corner-hull` callback (maximum 0.1 where 0.35 is true); `planted::upgrade-status` adapter reports
`Complete` at the cell limit; `planted::clamp-cells` silently lowers 4,097 to 4,096; `planted::midpoint-only`
callback returns the value at the box centre as a degenerate interval (the spot-check fails on the first
non-centre point). Metamorphic: shrinking the domain never raises the maximum's upper end; adding a constant
c to the quantity shifts both enclosures by c. Lanes: identical enclosures twice on one machine, in debug and
release, on both platforms.

## Considerations

- The spot-check costs up to 8 extra callback evaluations per box; with a 4,096-cell cap that is bounded and
  small beside a tolerance study. It can be disabled only for a callback that carries its own certificate.
- Interval extensions suffer from dependency (x·(1 − x) on [0, 1] evaluates to [0, 1] at the root), which is
  why subdivision is needed and why the cell limit is a normal outcome for many variables. More than about
  eight coupled features should be grouped by interface before this path is used; the report then says so.
- A worst-case box is deliberately pessimistic. Reporting it beside the statistical allocation, with both
  numbers, is the design; replacing one by the other is not.
- A pin move invalidates the record; the compatibility train re-runs this lane with the other admissions.
