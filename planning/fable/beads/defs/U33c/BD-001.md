## Background

FrankenRobotics consumes its sibling projects (FrankenSim above all) as Cargo path dependencies from a workspace
that lives outside the siblings' trees. This bead creates that workspace. It is the first step of the first
implementation session and every other bead builds on it. It produces an observation, not a scaffold: whether an
out-of-tree workspace resolves and checks with the settings below, and what the sibling trees looked like on that
day.

Three facts about FrankenSim decide what the root must contain (FACT, read 2026-11-21 at FrankenSim head
`483d09c682f2`; each is re-read at the pin by this bead and never copied from here into a record):

1. Cargo does not propagate a `[patch]` table, profile overrides or `[env]` settings from a path dependency.
   FrankenSim's own manifest states the rule for profiles in the comment above `[profile.dev.package.fsqlite]`
   (`frankensim/Cargo.toml`). That the same holds for patches and `[env]` in our graph is a HYPOTHESIS which the
   first FrankenSim build (BD-006, INT-FSIM-01) settles. The root therefore repeats three things: FrankenSim's
   `[patch.crates-io] asupersync` entry, its FrankenSQLite profile overrides, and the build-identity variable.
2. `frankensim/crates/fs-la/build.rs` panics unless `FRANKENSIM_DEPGRAPH_RECEIPT` or `FRANKENSIM_DEPGRAPH_SALT`
   is set. Inside FrankenSim the salt comes from its `.cargo/config.toml`, which an outside workspace does not
   read. `fs-la` is in the closure of `fs-ad`, `fs-mbd` and `fs-contact`. The core sets its own salt, naming its
   own development equivalence class.
3. Sibling trees drift: FrankenSim's `constellation.lock` pins asupersync 0.5.0 while its `Cargo.lock` resolves
   0.6.2 by path, the asupersync checkout had 267 modified paths and FrankenSim's 32. A pin states intent; a
   receipt records what was there.

One toolchain serves the whole build graph (decision of the owner, 2026-11-22, recorded as OPEN-SUITE-2: the core,
the GPU annexes, the derivation tool and the MCP server all build on one toolchain T; no annex carries a toolchain
file; `lean/` is not Rust; `frob-cert` additionally builds alone on a stable release). T is chosen later, at
INT-TOOLCHAIN-01 (BD-031). Until then the toolchain file names candidate (a), the suite's common nightly
`nightly-2026-08-31`, as the provisional T. Rejected alternatives: a toolchain file per annex (the reason for an
annex boundary is the unsafe and foreign-interface policy, never the compiler); building on FrankenSim's older pin
by default (it would leave fastmcp_rust, which declares `rust-version = "1.100"`, outside the graph, and the plan
does not build on an ignored `rust-version`).

## Scope

In: the root manifest, the toolchain file, `.cargo/config.toml`, `franken-stack.lock`, the first resolution
receipt under `receipts/`, the bootstrap script that writes it, and a green `cargo check` through the build-offload
shim. This bead is step 1 of the first implementation session as far as it creates things: it is the only bead
that writes the four files and the only one that writes the first receipt.

Out, with the bead that has it:
- the session's record of step 1: the session header, the three repeated settings printed from the files, the
  check re-run and recorded pass or fail in the session's format (`docs/delivery/sessions/first/step-1/`,
  `record.json` of schema `frob.sessionstep/1`), the `cargo metadata` and `cargo tree` artifacts that give the
  package-count baseline for step 2, and the verification that this bead's receipt regenerates byte for byte:
  N41-18, which depends on this bead, creates no file of the workspace and writes no receipt of its own;
- `xtask` subcommands (BD-003, BD-004); companion documents and registries (BD-002); any `frob-*` library
  crate; the FrankenSim path dependencies themselves (BD-006); the choice of T (BD-031).

## Technical approach

**Files (DESIGN).**

1. `Cargo.toml`, a virtual workspace manifest:
   - `[workspace] members = ["crates/*"]`, `exclude = ["spark", "apps", "derive", "bindings", "worker"]`
     (those directories are separate workspaces; `surface/frob-mcp` is added to `members` by BD-023 when it
     exists). The `xtask` package lives at `crates/xtask/`, the place the repository layout (N34-01) and every
     check bead (BD-003, BD-004) give it, so the glob covers it. `[workspace.lints.rust] unsafe_code = "deny"`. No `rust-version` key: T is pinned by the toolchain
     file.
   - `[patch.crates-io] asupersync = { path = "../asupersync" }`, copied from the entry in `frankensim/Cargo.toml`
     at the pinned commit. Before any crate uses asupersync Cargo reports the patch as unused; that warning is
     expected and recorded.
   - The FrankenSQLite profile overrides, copied verbatim from the `[profile.*.package.fsqlite…]` tables of
     `frankensim/Cargo.toml` at the pin (the receipt summarizes them as `"fsqlite*: opt-level 1"`).
   - One member must exist for `cargo check` to have a package. FACT to check on T: Cargo rejects a virtual
     manifest with no members. The member is the `xtask` package with a `main` that prints usage and exits 3
     (the usage-error code of the `xtask` surface, which BD-003 and BD-004 keep: 0 clean, 2 findings, 3 usage);
     its six subcommands arrive with BD-003 and BD-004. No `frob-*` crate is created here, because source that was
     never compiled against its contract does not land.
2. `rust-toolchain.toml`: `[toolchain] channel = "nightly-2026-08-31"`, `components = ["rustfmt", "clippy"]`,
   with a comment that this is the provisional T (candidate (a)) until INT-TOOLCHAIN-01 records T, after which it
   moves only by a toolchain train. It is the only toolchain file in the repository apart from the stable one
   `frob-cert` will carry.
3. `.cargo/config.toml`: `[env] FRANKENSIM_DEPGRAPH_SALT = "franken-robotics-dev-v1"`, and
   `[alias] xtask = "run --locked --package xtask --"`, the alias through which every check bead and script
   runs `cargo xtask <check>` (written here with the file, so that the checks of BD-003 and BD-004 find it;
   the rules and tests of the `[env]` entry are N33a-08's).
   Evidence-bearing performance builds export `FRANKENSIM_DEPGRAPH_RECEIPT` instead; that path is not exercised
   here.
4. `franken-stack.lock`, TOML in FrankenMining's format (FACT: `franken_mining/franken-stack.lock`). Top level:
   `toolchain = "nightly-2026-08-31"`. One `[[foundation]]` row per foundation the M0 milestone admits. Fields:
   `id`, `name`, `posture` (one of the seven text forms of N33a-01: `consume-path`, `consume`, `subprocess`,
   `lift`, `oracle`, `pattern`, `build-time`; a row with several uses is completed in the `uses` form by N33a-02), `path`,
   `git_rev` (40 hex), `toolchain` (the channel in the sibling's own toolchain file at `git_rev`), `features`,
   `build_env`, `confined_to`, `admission_gate`, `receipt` (BLAKE3 of the receipt the row was admitted under),
   `fallback`. The two rows that must be complete on day one:

   ```toml
   [[foundation]]
   id = "FD-FSIM"
   name = "frankensim"
   posture = "consume-path"
   path = "../frankensim"
   git_rev = "<40-hex head read today; recorded again at INT-FSIM-01>"
   toolchain = "nightly-2026-07-06"
   features = ["referee", "geometry", "ledger"]
   build_env = { FRANKENSIM_DEPGRAPH_SALT = "franken-robotics-dev-v1" }
   confined_to = ["frob-fsim", "bedrock-direct"]
   admission_gate = "INT-FSIM-01"
   receipt = "<BLAKE3 of the first receipt>"
   fallback = "KILL-FSIM: (a) pinned worker process exchanging whole jobs; (b) lift the minimal referee set."

   [[foundation]]
   id = "FD-ASUP"
   name = "asupersync"
   posture = "consume"
   version = "<the single version every workspace resolves; 0.6.2 by path today>"
   admission_gate = "INT-ASUP-01"
   fallback = "FD-ASUP-01 aligns the siblings; a surface that still brings a second package: KILL-MCP fallback 1."
   ```

   Rows for frankensqlite (`FD-FSQL`, INT-FSQL-01), frankentorch (`FD-FT`, INT-FT-01), `cudarc` (`FD-CUDA`,
   INT-CUDA-01), frankensympy (`FD-FSYM`, INT-FSYM-01), fastmcp_rust (`FD-FMCP`, INT-FMCP-01) and franken_numpy
   (`FD-FNP`, INT-FNP-01) are written with their head, channel and gate. The other ten rows of the foundation
   ledger (FD-FSCI to FD-FSS) are written by N33a-02, which completes all eighteen with their uses, confinement
   and fallback; a later foundation's pin enters its row only at its own admission, never earlier.
5. The first resolution receipt, `receipts/<blake3>.json`, schema `frob.stack-receipt/1`, canonical JSON (object
   keys sorted by code point, arrays in their stated order, no insignificant whitespace, strings in NFC, integers
   as JSON integers, no timestamp). The receipt format is specified once, by N33a-04; this bead writes the same
   bytes that N33a-04's writer will write on the same tree, so the field list and the tree hash below are that
   bead's. Fields: `schema`; `repo_rev`, `repo_dirty`, `repo_tree_hash` (this repository, under the same rule as
   a sibling); `toolchain`; `siblings[]`, one per foundation of the lock that has a checkout, sorted by `fd`, each
   `{fd, rev, dirty, tree_hash (only when dirty, else null), features, own_lock {file, hash, agrees, class,
   reason}}` with `class` one of `on-pin` (at the pin and clean), `stale-lock` (clean, and a fast-forward of the
   sibling's own lock) or `drift`, and `reason` null except under `drift`, where it is one of `dirty`,
   `retreated`, `diverged`, `unknown-pin`; `lockfiles[] {workspace, hash, packages, registry}`; `patches[]`;
   `profile_overrides[]`; `build_env{}`; `duplicates[]` (an asupersync duplicate listed first); `commands[]
   {argv, exit, output_hash}`. Paths are repository-relative; no absolute path (`/Users/...`), user name or host
   name appears.
6. The tree hash of a dirty tree (N33a-04's definition, repeated so this bead stands alone): list tracked files
   with `git ls-files -z`; sort the paths bytewise; feed BLAKE3 first the domain tag `frob.tree/1`, then for each
   path its length as a 64-bit little-endian integer, the path bytes, one byte for the executable bit, the content
   length as a 64-bit little-endian integer and the content bytes; a symbolic link contributes its target text;
   a tracked file deleted in the working tree contributes the byte 0xFF and no content. Timestamps and the
   checkout location do not enter.

**The bootstrap script.** `xtask check-stack` does not exist yet, so `scripts/bootstrap/first_receipt.sh` writes
the first receipt with `git`, `cargo metadata --locked`, `cargo tree -d` and `b3sum`. It reads sibling trees only
(`git -C <sibling> rev-parse HEAD`, `git status --porcelain`, `git merge-base --is-ancestor` for the drift class,
and for a dirty tree the stream of item 6 built with `git ls-files -z` and `printf`, piped to `b3sum
--no-names`) and writes nothing outside this repository. When N33a-04 and N33a-05 land, `check-stack
--write-receipt` must reproduce this receipt byte for byte on the same tree (a difference is a defect in one of
the two writers, settled against N33a-04's specification); the script is then deleted with the owner's
permission or kept as a cross-check.

**Order of work.** (1) Write the four files with an empty `receipt` field, and the `xtask` skeleton. (2) Run
`cargo check --workspace --all-targets` through the offload shim (never `cargo` by absolute path; isolated
target directory `${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/frob-skeleton`), under a timeout of 20 minutes (DESIGN,
the same command line and limit the session's step record uses, N41-18), inside the machine envelope (16 GiB, 8
cores, one hour). This first check writes `Cargo.lock`. (3) Commit the files, the skeleton and the generated
`Cargo.lock` together, with the check's command and result in the commit message: source lands only after it
compiled (§34.7), and the lockfile must be tracked because an admission record is valid only if it cites a
commit whose tracked `Cargo.lock` contains the foundation. (4) Run the bootstrap script on that clean commit;
`repo_rev` is the commit of step 3, and `cargo metadata --locked` reads the committed lockfile. (5) Write the
receipt hash into the lock rows and commit the receipt and the lock together. Verification recomputes every
field except `repo_rev` from the tree and requires `repo_rev` to be an ancestor of `HEAD`.

Determinism: the receipt is a pure function of tracked bytes and revisions. Evidence: an admission record in
`DEPENDENCY_ADMISSION.md` with the commands, their outputs and the receipt hash; no gate PASS is recorded while a
sibling tree is dirty (the record then says `development build`).

## Acceptance criteria

- [ ] `cargo check` exits 0 on the skeleton through the offload shim; the command line, exit code, wall time and output hash are in the admission record. (Seed done-condition, first half.)
- [ ] Re-running the receipt generator on the unchanged tree gives byte-identical JSON; its BLAKE3 equals the file name under `receipts/` and the `receipt` field of the lock rows. (Seed done-condition, second half; known answer KA-767.)
- [ ] `rust-toolchain.toml` names `nightly-2026-08-31`; `franken-stack.lock` top-level `toolchain` equals it; no other toolchain file exists in the repository.
- [ ] `Cargo.lock` is tracked at `repo_rev`, and the receipt's `lockfiles[]` entry for `core` is the BLAKE3 of that committed file; `cargo xtask` (through the alias) prints usage and exits 3.
- [ ] `.cargo/config.toml` sets `FRANKENSIM_DEPGRAPH_SALT`; with the variable removed, a probe build of `fs-la` by path fails closed with the build script's panic (run once here as a probe, re-run as the negative control of BD-006).
- [ ] The receipt records for every sibling its 40-hex revision, `dirty`, and the drift class of its own lock; FrankenSim's `constellation.lock` disagreement is classified, not assumed.
- [ ] The receipt and the admission record contain no absolute path.
- [ ] Touching one tracked file in a copy of a sibling flips `dirty`, changes `tree_hash` and makes verification fail.
- [ ] No sibling checkout is modified: `git status --porcelain` of every sibling is identical before and after the script.

## Test plan

### Unit tests

`scripts/bootstrap/tests/` (shell, run by `scripts/e2e/suite_workspace_skeleton.sh`), all on real trees:
- `receipt_is_canonical`: object keys in code-point order at every level (so `build_env` comes first and `toolchain` last at the top level), no whitespace outside strings, `schema` equal to `frob.stack-receipt/1`, siblings in `fd` order; parse and re-serialize with sorted keys gives the same bytes.
- `tree_hash_matches_definition`: on a `synthetic` three-file git tree (one executable file, one plain file, one tracked file deleted in the working tree) the script's `tree_hash` equals the BLAKE3 of the stream of item 6 assembled independently in the test (expected: equal); flipping the executable bit alone changes it.
- `drift_reason_recorded`: on the dirty fixture `class` is `drift` and `reason` is `dirty`; on the clean fixtures `reason` is null.
- `receipt_twice_identical`: two runs, `cmp` equal (KA-767).
- `receipt_has_no_absolute_path`: no match for a leading `/` path or the home directory in the file.
- `lock_parses_and_names_T`: the TOML parses; top-level `toolchain` equals the channel in `rust-toolchain.toml`.
- `drift_class_table`: on three `synthetic` sibling fixtures (a clean checkout at its lock; a fast-forward of its lock; a dirty tree) the classes are `on-pin`, `stale-lock`, `drift`.

### End-to-end script and logging

`scripts/e2e/suite_workspace_skeleton.sh` (depends on the shared helper of STD-E2E once it exists; until then it
writes the same line format itself): runs `cargo check` through the shim, the receipt generator twice, the
verification, the dirty-sibling control on a scratch copy, and the salt-removed probe. Each step logs `ts`,
`script`, `bead: BD-001`, `step`, `event`, the exact command, exit code, wall time, the receipt hash, the count
of siblings by drift class, and on failure the first differing byte offset and both file paths. The final
`summary` line lists assertions passed and failed and `gates: [INT-TOOLCHAIN-01 (provisional T only)]`.

### Known answers and negative controls

KA-767: a receipt computed twice on an unchanged tree is byte-identical; control: one touched tracked file in a
sibling copy flips `dirty`, changes `tree_hash`, and verification fails. Second control: the salt removed, the
`fs-la` probe build must fail. Third control: a receipt edited by one character must not verify. Determinism
lanes: twice on one machine; on both machines (`trj` and the Mac) the receipts differ only where sibling trees
differ, which the diff must show field by field.

## Considerations

- OPEN-SUITE-1 (which asupersync version the graph resolves to): default, the one published version FD-ASUP-01
  aligns the siblings on; until it lands, whatever FrankenSim's pinned commit builds with (0.6.2 by path). The
  `FD-ASUP` row records it; INT-ASUP-01 decides (BD-008).
- OPEN-SUITE-3: a dirty asupersync checkout admits development builds only, with the tree hash in the receipt.
- The receipt's `repo_rev` cannot be the commit that contains the receipt's own hash. The two-commit order above
  resolves it; `check-stack` must apply the same rule.
- RISK-02 (the toolchain train costs more than M0 allows) and RISK-23 (dirty or off-pin sibling trees make a
  receipt unrepeatable) both show first in this bead's receipt.
- If candidate (a) cannot build FrankenSim, BD-006 reports it and BD-031 moves the file to candidate (b),
  `nightly-2026-07-06`; this bead does not pre-empt that.
