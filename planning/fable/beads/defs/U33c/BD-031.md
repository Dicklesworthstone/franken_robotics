## Background

One Rust toolchain, T, serves the whole build graph of FrankenRobotics: the core workspace, the two GPU annexes,
the derivation tool `derive/frob-derive` and the MCP server `surface/frob-mcp`. The owner decided this on
2026-11-22 (recorded as OPEN-SUITE-2, kept in the register as a decided question: the alternative was a core on
one nightly and the MCP server in a workspace of its own on another). This gate chooses T, records it, and proves
that every part of the graph builds and tests on it.

The siblings do not start on one toolchain. FACT, read 2026-11-21 from each `rust-toolchain.toml`: FrankenSim
pins `nightly-2026-07-06` (rustc 1.99.0-nightly); frankensympy `nightly-2026-08-20`; fastmcp_rust
`nightly-2026-08-25` and declares `rust-version = "1.100"`; asupersync, frankensqlite, frankentorch,
franken_numpy, frankenscipy, franken_lean, frankentui, franken_threed, frankenjax and the drone-reconstruction
project pin `nightly-2026-08-31`; franken_firmware is on stable 1.99.0. Four nightlies and one stable release are
in play.

Two candidates for T, in order of preference:

- **(a)** the suite's common nightly, `nightly-2026-08-31`. It requires advancing FrankenSim's pin from
  `2026-07-06` in FrankenSim's repository, and moving frankensympy from `2026-08-20` and fastmcp_rust from
  `2026-08-25`.
- **(b)** FrankenSim's present pin, `nightly-2026-07-06`, if FrankenSim cannot yet build on (a). fastmcp_rust's
  declared `rust-version` and toolchain file are then changed so that it builds on that pin, and the train to (a)
  is scheduled.

The named risk is the `fs-qty` coupling (RISK-21). `fs-qty` is the one FrankenSim crate that enables a nightly
feature, `generic_const_exprs`, which the compiler marks incomplete; `fs-evidence` depends on it directly and
through `fs-evidence` so do `fs-ivl` and nearly every physics crate. The coupling can bite in three ways: (1) a
toolchain train moves T to a nightly where the feature has regressed, and candidate (a) is exactly such a move for
FrankenSim; (2) a crate in the graph needs a newer compiler than any nightly on which `fs-qty` compiles, which is
the shape of the starting state (fastmcp_rust at 1.100 against a 1.99 nightly); (3) a stable-only target appears
(firmware export would be one). This gate serves BET-04 (FrankenSim can be consumed by path from outside its
tree, stably, and the nightly coupling does not block the core).

## Scope

In: running the matrix harness; the decision rule; writing T into `franken-stack.lock` and
`rust-toolchain.toml`; the admission record; two ADRs (the choice of T, the `frob-units` decision); the gate row.
Out: the harness (N33c-01); the coupling count (N33c-02); the import rule and its plant (N33c-03); the upstream
changes in fastmcp_rust (BD-023, FD-FMCP-01) and in FrankenSim (FD-FSIM-15, FD-FSIM-31); the conditional crate
`frob-units` (N33c-05, N33c-06); later trains (N33c-08).

## Technical approach

1. **Run the matrix.** Six build sets on four nightlies, nineteen run cells (the harness of N33c-01): `fs-qty`
   alone and the bedrock-direct list on all four; the M1 closure (`referee`, `geometry`, `ledger`) on
   `2026-07-06`, `2026-08-25` and `2026-08-31`; the core with the Metal annex on `2026-07-06` and `2026-08-31`;
   `surface/frob-mcp` with fastmcp_rust on `2026-07-06`, `2026-08-25` and `2026-08-31`; `derive/frob-derive`
   with the `fsym-*` crates on `2026-07-06`, `2026-08-20` and `2026-08-31`. Every cell gets a record: pass, or
   the first failing crate and error.
2. **Apply the decision rule (DESIGN).** T is the first candidate, in the order (a) then (b), on which every row
   passes, with the upstream changes that candidate needs.
   - If `fs-qty` compiles on the candidate, nothing else changes.
   - If `fs-qty` is what fails on candidate (a), the preferred fix is an upstream change in FrankenSim: FD-FSIM-15
     (land the macro-generated dimension products that `fs-qty` documents as its own fallback, behind a feature)
     or the smaller FD-FSIM-31 (remove the `fs-qty` dependency from `fs-evidence`, or put it behind a feature).
     T is candidate (b) until that change lands and the train to (a) runs.
   - If some other crate fails on (a), the cell names it, the upstream work item for that sibling is opened or
     updated, and T is (b) if every row passes there.
   - If no candidate passes every row, the gate records FAIL with the failing cells; BET-04's falsifier has
     fired and the M0 exit review decides between the worker fallback, KILL-MCP's fallbacks and `frob-units`.
   - `frob-units` is created only by the later rule: `fs-qty` fails on T after a toolchain train and the upstream
     change cannot land within that train. At this gate the decision is recorded as "hatch closed" or "hatch
     open", with the cell that forced it.
3. **Record T.** In one commit: `rust-toolchain.toml` `channel = "<T>"`; `franken-stack.lock` top-level
   `toolchain = "<T>"`; each foundation row's `toolchain` field set to the channel in that sibling's own
   toolchain file at its `git_rev`. A new resolution receipt is written for that commit.
4. **Build and test on T.** `cargo check --all-targets --locked` and `cargo test --locked` for the core, both
   GPU annexes (CUDA on `trj`, Metal on the Mac), `derive/frob-derive` and `surface/frob-mcp`, each recorded with
   command, exit code, wall time and output hash.
5. **The `fs-qty` coupling test.** The plant of N33c-03 (a crate other than `frob-core` and `frob-fsim` that
   lists `fs-qty` as a dependency) is run and `xtask check-deps` must fail on it. The coupling count of N33c-02
   is attached to the record.
6. **Two ADRs**, numbered next in the ADR-SUITE series after ADR-SUITE-02:
   - *The choice of T*: the candidate chosen; the matrix summary; every sibling pin a toolchain train must move
     to reach or leave T (for (a): FrankenSim from `2026-07-06`, frankensympy from `2026-08-20`, fastmcp_rust
     from `2026-08-25`; for (b): fastmcp_rust's `rust-version` and toolchain file, and the scheduled train to
     (a)); the rule that T moves only by a toolchain train and never during the ten-fold tournament.
   - *The `frob-units` decision*: hatch closed or open; the evidence (the `fs-qty` row); the state of FD-FSIM-15
     and FD-FSIM-31; the trigger that would reopen the question.
7. **Admission record** in `DEPENDENCY_ADMISSION.md`: gate, date, this repository's commit (whose tracked
   `Cargo.lock` contains the foundations), the matrix as a table, the receipt hash, the two ADR links, PASS or
   FAIL. No PASS is recorded if any sibling tree was dirty during the T-column cells; the record then says
   `development build` and names the dirty trees. A row in `registries/gates.toml` carries the gate's `claim_id`.

After this gate T moves only by a toolchain train: one coordinated change that moves T here and in every consumed
sibling that needs it, followed by the admission and parity gates.

## Acceptance criteria

- [ ] Every one of the nineteen run cells has a recorded result, and the matrix is in `DEPENDENCY_ADMISSION.md`. (Seed done-condition.)
- [ ] Every row passes on the column chosen as T, and the whole graph (core, both annexes, `derive/frob-derive`, `surface/frob-mcp`) builds and tests on T.
- [ ] T is identical in `rust-toolchain.toml` and in `franken-stack.lock`; the receipt for that commit exists and verifies.
- [ ] The choice of T is an ADR that names the sibling pins a toolchain train must move. (Seed done-condition.)
- [ ] A direct `fs_qty` dependency outside `frob-core` and `frob-fsim` fails `xtask check-deps`. (Seed done-condition.)
- [ ] The `frob-units` decision is an ADR. (Seed done-condition.)
- [ ] No cell was built with an ignored `rust-version`.
- [ ] The gate row in `registries/gates.toml` shows the measured result and the negative controls caught.

## Test plan

### Unit tests

- `decision_rule_table` (in the script's test directory): on six `synthetic` matrix summaries the rule returns
  the expected outcome: all pass on (a) → T = (a), hatch closed; only `fs-qty` fails on (a), all pass on (b) →
  T = (b), upstream FD-FSIM-15 or -31 named, train scheduled; only `frob-mcp` fails on (b) and all pass on (a) →
  T = (a); a non-`fs-qty` crate fails on (a), all pass on (b) → T = (b) with that sibling named; no column passes
  → FAIL; a T-column cell `not-run` → the gate is `incomplete`, never PASS.
- `lock_and_toolchain_agree`: a tree where the two files name different channels fails the stack check.

### End-to-end script and logging

`scripts/e2e/suite_toolchain_matrix.sh`: runs the harness (resuming finished cells), prints the matrix, applies
the decision rule, runs the build-and-test commands on T, runs the `fs_qty` import plant against `xtask
check-deps`, and verifies the receipt. It logs one `cmd` event per cargo invocation (exact command, exit code,
wall time), one `metric` event per cell (status, peak memory with unit, package count), an `assert` event per
acceptance criterion with observed and required values, and a `summary` with assertions passed and failed and
`gates: [INT-TOOLCHAIN-01]`. On failure it logs the first failing crate and the path of the captured output.

### Known answers and negative controls

- Known answer: with T recorded, `rustc -V` inside the repository prints the channel named in the lock.
- Negative controls (each must be caught): the planted `fs_qty` import outside the two allowed crates; a tree
  with a second toolchain file in an annex (the stack check must fail); a matrix summary with one T-column cell
  flipped to `fail` (the decision rule must not return PASS); a cell record made on a dirty sibling tree offered
  for a PASS (refused).
- Determinism lanes: the decision is a pure function of the matrix summary; run the rule twice and on both
  machines from the same summary.

## Considerations

- OPEN-SUITE-2 is decided and stays in the register with its decision: one toolchain T for the whole graph;
  fastmcp_rust brought onto T by FD-FMCP-01; `frob-mcp` a member of the core graph running verbs in process. This
  gate and INT-FMCP-01 confirm it. KILL-MCP's fallbacks apply only if INT-FMCP-01 cannot pass within the M0
  budget after FD-FMCP-01 and FD-ASUP-01 have been attempted.
- OPEN-SUITE-4 (the alias set of `frob_core::qty` and whether it stays within 64) is decided with this gate by
  the Marrow lead (N33c-04).
- RISK-02: the train costs more than M0 allows or breaks a sibling. Leading indicator: a failing cell here, or
  FD-FMCP-01 still open at the M0 exit review. RISK-21: the `fs-qty` row after any pin move.
- The reported structure of the coupling (22 crates coupled to `fs-qty`, 12 directly and 10 through another
  crate; removing `fs-qty` from `fs-evidence` frees 8) is a FACT to recheck, not relied on by the decision.
- M7 freezes every pin and T for the length of the tournament, because a ratio of times measured across a
  toolchain train is not one measurement.
