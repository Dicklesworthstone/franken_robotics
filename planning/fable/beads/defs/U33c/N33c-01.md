## Background

The admission gate INT-TOOLCHAIN-01 chooses the one Rust toolchain T of the whole build graph. It records a
matrix, not one result, because the siblings start on four different pinned nightlies and the risk is specific:
`fs-qty`, FrankenSim's units crate, enables the nightly feature `generic_const_exprs`, which the compiler marks
incomplete (FACT: `frankensim/crates/fs-qty/src/lib.rs:20–21`), and nearly every physics crate depends on it. The
build graph is therefore tied to nightlies on which that feature still compiles one crate. A single green build on
one nightly would not show which other nightlies are open to a later toolchain train, nor which crate blocks which
candidate.

This bead builds the instrument: a script that fills every cell of the matrix and writes one structured record
per cell. The gate bead (BD-031) runs it, reads the records and decides. Keeping the instrument separate lets it
be re-run unchanged after every pin move and every toolchain train, which is when RISK-21 (the `fs-qty` coupling)
shows its leading indicator: the `fs-qty` row of this matrix.

The matrix (columns are the four nightlies in play; "run" cells are recorded, "—" cells are not applicable):

| Build set | `nightly-2026-07-06`, candidate (b) | `nightly-2026-08-20` | `nightly-2026-08-25` | `nightly-2026-08-31`, candidate (a) |
|---|---|---|---|---|
| 1. `fs-qty` alone | run | run | run | run |
| 2. Bedrock-direct list | run | run | run | run |
| 3. M1 closure (airlock groups `referee`, `geometry`, `ledger`) | run | — | run | run |
| 4. Core with the Metal annex (`ft-kernel-metal`) | run | — | — | run |
| 5. `surface/frob-mcp` with fastmcp_rust | run | — | run | run |
| 6. `derive/frob-derive` with the `fsym-*` crates | run | run | — | run |

Nineteen cells are run and five are not applicable. The first and last columns are the two candidates for T. The
middle columns are the present pins of frankensympy (`2026-08-20`) and fastmcp_rust (`2026-08-25`), recorded as
the starting state. The bedrock-direct list is the ten FrankenSim crates any crate may use directly: `fs-ga`,
`fs-math`, `fs-qty`, `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`, `fs-ad`.

## Scope

In: `scripts/admission/toolchain_matrix.sh`, the probe manifests it builds, the cell record schema, resource
limits, resumption. Out: the decision and its ADR (BD-031); the coupling-graph count (N33c-02); upstream changes in
any sibling.

## Technical approach

1. **Probe workspaces (DESIGN).** Build sets 1 and 2 use throwaway probe workspaces under
   `tests/admission/toolchain/<set>/` in this repository: a manifest that path-depends on the crates of the set
   (default features off), a one-line `lib.rs` that names one type from each, no toolchain file, its own empty
   `[workspace]` table (so Cargo does not attach the probe to the core workspace, whose `members` would otherwise
   claim it or refuse it), its own committed `Cargo.lock`, and the two root settings a workspace root must
   repeat (the asupersync patch entry and the FrankenSQLite profile overrides, which Cargo reads only from the
   root manifest of the workspace being built). The build-identity salt is not repeated and not exported: the
   cell runs cargo with the probe directory as its working directory, inside this repository, so Cargo reads the
   root `.cargo/config.toml` (BD-001) and its `[env]` entry reaches `fs-la`'s build script, which is the only
   sanctioned source of the salt (N33a-08; an export by the harness would be a second one). No cell runs cargo
   inside a sibling checkout: a sibling's own `Cargo.lock` and target directory are never touched. Sets 3 to 6
   build the real targets: the core workspace with `frob-fsim` default groups; the core plus
   `spark/frob-spark-metal`; the core with `surface/frob-mcp`; `derive/frob-derive`. A set whose target does not
   exist yet is recorded `not-run` with the bead that will create it (sets 4, 5, 6 need BD-016, BD-023, BD-019).
2. **One cell.** For build set s and channel c: `cargo +<c> check --all-targets --locked` in the set's workspace,
   through the build-offload shim, with `CARGO_TARGET_DIR=${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/frob-matrix/<s>/<c>`
   so that cells never share artifacts, `-j 8`, a one-hour timeout and a 16 GiB memory limit (the machine
   envelope). For the column chosen as T the cell also runs `cargo +<c> test --locked` for sets 3 to 6, because
   the gate says the graph builds and tests on T. `--ignore-rust-version` is never passed: a cell that fails
   because a crate declares a newer minimum is a failure of kind `rust-version`.
3. **Cell record.** Appended to `receipts/matrix/<utc>.ndjson`, schema `frob.toolchain-matrix/1`, canonical JSON
   per line: `set`, `channel`, `rustc_version` (output of `rustc +<c> -V`), `argv`, `status` (`pass`, `fail`,
   `not-run`, `not-applicable`), `exit`, `wall_s`, `peak_rss_bytes`, `packages` (count from `cargo metadata`),
   `first_error {crate, code, line}` for a failure (the first compiler error only, as text of at most 400
   bytes), `failure_kind` (`feature-regressed`, `rust-version`, `resolve`, `build-script`, `timeout`,
   `memory`, `other`), `receipt` (the stack-receipt hash in force), `siblings_dirty` (true if any sibling tree is
   dirty), `output_hash` (BLAKE3 of the full captured output, kept beside the record).
4. **Resumption and idempotence.** A cell is keyed by `(set, channel, receipt)`. Re-running skips cells that
   already have a `pass` or `fail` record for the same key unless `--force` is given; a `not-run` cell is
   always tried again (its target may have landed without a new receipt) and is recorded `not-run` again while
   the target is still absent. The script exits non-zero if any run cell lacks a record of status `pass`,
   `fail` or `not-run`, and zero otherwise: a failing cell is a result, not a script failure.
   Selection flags: `--sets <list>`, `--channels <list>`, `--test-channel <c>` (the column on which sets 3 to
   6 also run their tests) and `--timeout-s <n>` (default 3600, the envelope's hour; the unit tests lower it). The first implementation session's step 3 (N41-20) runs its four `fs-qty` cells as
   `toolchain_matrix.sh --sets 1`, so its records are this schema's and the gate (BD-031) resumes them as the
   finished first row; a record of the `fs-qty` row made any other way is not resumed.
5. **Read-only toward siblings.** The script never writes inside a sibling checkout, never moves a sibling to a
   pin, and installs toolchains only through the machine's normal toolchain manager. Before a failure is
   attributed to this repository it calls the stack check (the bootstrap verification of BD-001 until `xtask
   check-stack` exists) and records the drift class of every sibling in the cell.
6. **Summary.** After the last cell the script prints the matrix as a table of `pass`/`fail`/`—` and writes
   `receipts/matrix/<utc>.summary.json` with, per column, whether every run row passed.

Determinism: statuses are reproducible for a fixed receipt; times and memory are measurements with units. Nothing
here is evidence of a physical claim; the records are admission evidence only.

## Acceptance criteria

- [ ] All nineteen run cells have a record of status `pass`, `fail` or `not-run` (a `not-run` names the bead that creates its target); the five not-applicable cells are present with status `not-applicable`.
- [ ] Every record carries the rustc version string, the receipt hash and the dirty flag; a record made on a dirty sibling tree is marked and cannot be cited for a PASS.
- [ ] No cell exceeds one hour, 16 GiB or 8 cores; a cell that hits a limit is recorded `fail` with kind `timeout` or `memory`, not retried silently.
- [ ] A failing cell names the first failing crate and error code; for a failure in `fs-qty` the kind is `feature-regressed` when the error concerns `generic_const_exprs`.
- [ ] Re-running on an unchanged tree runs no cargo command and reproduces the same summary.
- [ ] `git status --porcelain` of every sibling is unchanged by a full run.

## Test plan

### Unit tests

Shell tests under `scripts/admission/tests/`, on real toolchains with small real crates:
- `cell_pass`: a probe crate with no dependencies passes on all four channels.
- `cell_fail_names_crate`: a `synthetic` probe crate that enables a non-existent feature gate fails; the record's `first_error.crate` is that crate.
- `cell_rust_version`: a `synthetic` probe crate declaring `rust-version = "9.0"` fails with kind `rust-version`; the script does not pass `--ignore-rust-version`.
- `cell_timeout`: a probe whose build script sleeps past `--timeout-s 5` is recorded `fail` with kind `timeout`.
- `not_run_is_retried`: a set whose target directory is absent is recorded `not-run` naming its bead; after the target is created (same receipt), a plain re-run builds that cell and replaces nothing else.
- `resume_skips_done`: second invocation executes zero cargo commands.
- `record_is_canonical`: each line parses, keys sorted, and re-serializes identically.
- `probe_is_own_workspace`: `cargo metadata` of the core workspace lists no package under `tests/admission/`, and the set-1 probe resolves with its own lockfile.
- `select_sets_and_channels`: `--sets 1 --channels nightly-2026-08-31` runs exactly one cell; a following full run resumes it and runs the other eighteen.
- `siblings_untouched`: after a full run of set 1 on the four channels, `git status --porcelain` and the `Cargo.lock` hash of the FrankenSim checkout are unchanged.
- `cell_build_script_salt_unset`: a copy of the set-2 probe (which reaches `fs-la` through `fs-ad`) placed under the scratch root, outside this repository so that no `.cargo/config.toml` lies above it, and run with neither build-identity variable in the environment, fails with kind `build-script` and `first_error.crate = "fs-la"`; the same probe inside the repository passes, which shows the salt arrives from the `[env]` table alone.
- `harness_exports_no_salt`: the harness's source and every `argv` it records contain neither `FRANKENSIM_DEPGRAPH_SALT` nor `FRANKENSIM_DEPGRAPH_RECEIPT`.

### End-to-end script and logging

`scripts/e2e/suite_toolchain_matrix.sh` (BD-031) drives this harness; the first session's step 3 (N41-20) runs
it alone. The harness sources the STD-E2E helper `scripts/e2e/lib.sh` and logs through it (it writes no log line
of its own format), to `target/e2e-logs/toolchain_matrix/<utc>.ndjson` with a transcript: per cell a `cmd` event
(`e2e_cmd`, with the cell's expected exits, since a failing cell is a result) with the exact command, exit code
and wall time, and a `metric` event (`e2e_metric`) with `peak_rss_bytes` and `packages`; the final `summary`
gives counts of cells by status.

### Known answers and negative controls

Planted failures the harness must report as failures: the non-existent feature gate; the impossible
`rust-version`; a path dependency on a directory that does not exist (kind `resolve`); the build-identity salt
unset for a probe that reaches `fs-la`, built outside the repository tree (kind `build-script`, the fail-closed
behaviour of `frankensim/crates/fs-la/build.rs`; inside the tree the `[env]` entry would supply it). A harness that reported any of these as `pass` would validate nothing.
Lanes: run twice on one machine and compare statuses; run on `trj` and on the Mac and compare statuses for sets
1, 2, 3, 5, 6 (set 4 exists only on the Mac).

## Considerations

- Cold builds of the M1 closure are large: 65 FrankenSim crates and about 2.06 million lines of library source
  (FACT, counted 2026-11-21). Three such cells may approach the envelope each; the script runs cells one at a
  time and performs a disk preflight first. OPEN-SUITE-5 (the cold-build budget) defaults to the envelope.
- Other agents build in the sibling repositories. The isolated target directories keep this harness from
  contending for their build locks.
- The four channel names are the starting state. After a toolchain train the column set changes; the columns are
  read from a small table at the top of the script, and the summary names them.
