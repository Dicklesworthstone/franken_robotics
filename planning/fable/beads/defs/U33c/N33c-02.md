## Background

`fs-qty` is FrankenSim's units crate (compile-time dimensional analysis, runtime-checked quantities, SI parsing;
8,950 library lines). It is the only crate in FrankenSim that enables a nightly feature, `generic_const_exprs`
(FACT: `frankensim/crates/fs-qty/src/lib.rs:20–21`; a search of `crates`, `apps` and `xtask` found no other
crate-level feature attribute). Because `fs-evidence` depends on `fs-qty` directly, and `fs-ivl` and nearly every
physics crate depend on `fs-evidence`, the whole build graph is tied to nightlies on which that incomplete feature
still compiles.

Two upstream work items in FrankenSim would loosen the tie, and their relative value depends on the shape of the
coupling:

- FD-FSIM-15 (priority P1): land the macro-generated dimension products that `fs-qty` documents as its fallback,
  behind a feature, so consumers are not tied to `generic_const_exprs`.
- FD-FSIM-31 (priority P2): remove the `fs-qty` dependency from `fs-evidence`, or put it behind a feature. A
  smaller change.

The plan carries a reported reading of the graph that was not repeated when the plan was written (FACT to
recheck): of 22 crates coupled to `fs-qty`, 12 depend on it directly and 10 only through another crate, and
removing `fs-qty` from `fs-evidence` alone would free 8 of the 22. INT-TOOLCHAIN-01 must record the measured
structure. This bead measures it, so that the choice between the two upstream items, and the cost of the
`frob-units` escape hatch, rest on a count and not on a report.

## Scope

In: a read-only script that computes the coupling sets from Cargo metadata at the pinned FrankenSim commit, and a
record attached to the INT-TOOLCHAIN-01 admission. Out: any change in FrankenSim (the upstream work items are
separate beads opened under BD-037); the decision (BD-031).

## Technical approach

1. **Input.** `cargo metadata --format-version 1 --locked --offline --manifest-path <copy>/Cargo.toml`, run on a
   read-only copy (or a `git worktree`-free export made with `git archive`) of FrankenSim at the `git_rev` of
   `franken-stack.lock`, so that nothing can be written into the sibling checkout. Only the `resolve` graph over
   workspace members with normal (non-dev, non-build) edges is used; optional dependencies are counted twice,
   with default features and with all features.
2. **Definitions (DESIGN).** For a population P of FrankenSim crates:
   - D(P) = crates in P with a direct normal dependency on `fs-qty`;
   - I(P) = crates in P whose transitive closure contains `fs-qty` but which are not in D(P);
   - C(P) = D(P) ∪ I(P), the crates coupled to `fs-qty`;
   - F31(P) = crates in C(P) that are no longer coupled when the single edge `fs-evidence → fs-qty` is deleted
     from the graph (the effect of FD-FSIM-31);
   - for each crate in I(P), the list of direct dependencies through which it reaches `fs-qty` (its "carriers").
3. **Populations.** The plan's report does not define its population, so the script reports three and states
   which, if any, reproduces 22 / 12 / 10 / 8:
   - P₁: every crate this project consumes: the ten bedrock-direct crates (`fs-ga`, `fs-math`, `fs-qty`,
     `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`, `fs-ad`) plus every crate named in an
     airlock feature group (`referee`, `geometry`, `ledger`, `optimize`, `stats`, `spectral`, `actuation`,
     `structure`, `multiphysics`, `harness`);
   - P₂: the M1 closure, the transitive closure of the groups `referee`, `geometry`, `ledger` (reported as 65
     crates);
   - P₃: every member of FrankenSim's workspace.
4. **Output.** `receipts/coupling/<utc>.json`, schema `frob.qty-coupling/1`, canonical JSON: `frankensim_rev`,
   `feature_mode` (`default` or `all`), and per population `{name, size, direct[], indirect[] with carriers,
   freed_by_fd_fsim_31[], still_coupled_after_31[]}`, plus `reported = {coupled: 22, direct: 12, indirect: 10,
   freed: 8}` and `reproduced_by` (a population name or `none`).
5. **Use.** The record's hash and its headline counts go into the INT-TOOLCHAIN-01 admission record. If
   `reproduced_by` is `none`, the admission record says so and the upstream work item FD-FSIM-31 is updated with
   the measured numbers through its bead; the reported numbers are not cited again.

Determinism: exact (a pure function of the manifests at one revision). No physics, no evidence class.

## Acceptance criteria

- [ ] The script exits 0 and writes the record for both feature modes at the pinned revision.
- [ ] For each population the four counts satisfy |C| = |D| + |I| and F31 ⊆ C; every indirect crate lists at least one carrier.
- [ ] The record states whether 22 / 12 / 10 / 8 is reproduced, and by which population.
- [ ] The headline counts and the record hash appear in the INT-TOOLCHAIN-01 admission record.
- [ ] FrankenSim's checkout is byte-identical before and after (`git status --porcelain` and `git rev-parse HEAD`).
- [ ] The coupled list contains `fs-evidence` and `fs-ivl` (both FACT: `fs-evidence` depends on `fs-qty` directly; `fs-ivl` through `fs-evidence`), and does not contain `fs-ga`, `fs-math`, `fs-rand`, `fs-blake3`, `fs-simd`, `fs-exec` or `fs-ad`.

## Test plan

### Unit tests

`scripts/admission/tests/coupling_*.sh` with a `synthetic` five-crate workspace fixture (`q`; `e → q`; `i → e`;
`m → i, e`; `z` with no edge to `q`):
- `direct_indirect_split`: D = {e}, I = {i, m}, C = {e, i, m}.
- `freed_by_edge_removal`: deleting `e → q` frees {e, i, m}; adding a second edge `m → q` leaves m coupled and frees {e, i}.
- `carriers_listed`: i's carrier is e; m's carriers are i and e.
- `optional_edges_two_modes`: an optional edge `z → q` appears only in mode `all`.

### End-to-end script and logging

A step of `scripts/e2e/suite_toolchain_matrix.sh` (BD-031): runs the script at the pin, logs a `metric` event per
population with `coupled`, `direct`, `indirect`, `freed` (unit: crates) against the reported values, and an
`assert` event for the membership checks of the last acceptance criterion.

### Known answers and negative controls

Known answers: the five-crate fixture above, exact. On the real graph, the membership facts from the
bedrock-direct table (which of the ten depend on `fs-qty`: `fs-ivl` yes through `fs-evidence`, `fs-evidence` yes
directly, the others no). Negative control: a script variant that counts dev-dependencies must change the fixture
counts when a dev edge `z → q` is added, and the real script must not. Lanes: twice on one machine, and on both
machines at the same revision, byte-identical output.

## Considerations

- `cargo metadata` can rewrite a lockfile; `--locked --offline` and the read-only copy are both required so that
  the rule "this project's tooling never modifies a sibling checkout" (INV-SUITE-04) holds even for a
  measurement.
- The count is a property of one FrankenSim revision. It is re-measured at every pin move, with the matrix.
- If FD-FSIM-31 frees most of what this project consumes, it becomes the preferred upstream change before
  FD-FSIM-15 despite its lower listed priority; that reprioritization is a note for the upstream bead, not a
  decision of this one.
