## Background

Layer rule L-6 of the workspace says: no bare `f64` physical quantity in a public signature above layer 1;
quantities are `frob_core::qty` types or group elements. Units are SI. The types come from FrankenSim's `fs-qty`,
which depends on an incomplete nightly compiler feature (`generic_const_exprs`). If that feature regresses on the
project's toolchain and the upstream fix cannot land in time, the project swaps in its own small stable crate,
`frob-units`. The swap is the "escape hatch", and it is only cheap if it was prepared from the first commit.

DESIGN (the escape hatch, kept cheap): the core never imports `fs_qty` by name outside `frob-core` and
`frob-fsim`. Quantity types reach every other crate through one re-export module, `frob_core::qty`. While the
hatch is closed that module re-exports `fs-qty`. If it opens, the module re-exports `frob-units` instead, and the
change is one module plus the conversions in the airlock crate `frob-fsim`. Layer rule L-2 states the same from
the other side: only `frob-fsim` names types from FrankenSim's volatile crates; the bedrock-direct list is the
only exception; and `fs-qty` is named only through `frob_core::qty`.

For the swap to be possible the module must not expose `fs-qty`'s open-ended dimension arithmetic to the rest of
the project. It exposes a **closed set of aliases** (Length, Mass, Torque, and so on) and the products and
quotients among them. A quantity outside the set is added to it or carried as a checked runtime value. That cost
is accepted and stated.

Counterexample to the shortcut "a dimension vector is all the typing a quantity needs" (CX-354): a torque and an
energy have the same dimension vector (kilogram 1, metre 2, second −2), so dimension checking alone cannot
separate them. Both `fs-qty` and `frob-units` therefore keep them as distinct aliases over the same dimension, and
the test adds a torque to an energy and expects a compile error.

Rejected alternatives: letting each crate depend on `fs-qty` directly (a swap would then touch every crate);
exposing a generic `Quantity<D>` from `frob_core::qty` (a stable replacement cannot express generic dimension
arithmetic, so code written against it could not move).

## Technical approach

1. **Module contract (DESIGN).** `frob_core::qty` exports exactly:
   - the aliases listed in `registries/qty_aliases.toml` (one row per alias: `name`, `dimension` as six signed
     8-bit exponents in the order metre, kilogram, second, kelvin, ampere, mole, which is `fs-qty`'s order, FACT:
     `fs-qty/src/lib.rs`, `DIMENSION_COUNT = 6`; `kind`, a tag that separates aliases with equal dimension;
     `unit`, the SI unit string);
   - the products and quotients in `registries/qty_products.toml` (rows `lhs`, `op`, `rhs`, `out`); at most one
     output per ordered pair; where two aliases share the output dimension (force × length is an energy or a
     torque) the table names one and the other is reached by a named constructor (`Torque::from_force_arm`);
   - `Checked`, a runtime quantity `{ value: f64, dimension: [i8; 6] }` for data loaded at run time, with
     `Checked::into_alias::<A>()` that refuses on a dimension mismatch (refusal `FROB-REF-102`, unit or dimension
     error) and never silently converts;
   - nothing generic over a dimension parameter. The module has a `#![deny]`-style test that its public items
     are exactly the registry rows plus `Checked`.
2. **Starter alias set (DESIGN, proposal for OPEN-SUITE-4; the quantities used by the algebraic core, the design
   language, actuators, dynamics, families and contact).** Length, Area, Volume, Angle, Ratio, Mass, Density,
   Time, Frequency, AngularVelocity, AngularAcceleration, Velocity, Acceleration, Force, Torque, Energy, Power,
   Momentum, Impulse, AngularMomentum, MomentOfInertia, Stiffness, AngularStiffness, Damping, AngularDamping,
   Pressure, Temperature, HeatCapacity, ThermalResistance, Current, Voltage, Resistance, Inductance, Charge,
   TorqueConstant, FrictionCoefficient. Thirty-six aliases. Groups with equal dimension and distinct kinds:
   Torque/Energy/AngularStiffness (kilogram 1, metre 2, second −2); Frequency/AngularVelocity (second −1);
   Momentum/Impulse (kilogram 1, metre 1, second −1); AngularMomentum/AngularDamping (kilogram 1, metre 2, second
   −1: N·m·s/rad and kg·m²/s); Angle/Ratio/FrictionCoefficient (dimensionless). Every unordered pair inside a
   group gets a compile-fail test (3 + 1 + 1 + 1 + 3 = 9 pairs), and a unit test derives the groups from the
   registry so that a new alias that shares a dimension cannot enter without its pair tests.
3. **The confinement rule.** The row is BD-003's `L-2.fs-qty-direct` of `xtask check-deps`: the package `fs-qty`
   may appear as a direct dependency only of `frob-core` and `frob-fsim` (which covers `frob-units`'
   differential test, a dev-dependency inside `frob-fsim`). Any other crate of any workspace of this repository
   with a direct normal, build or dev edge to `fs-qty` fails the check with the crate name and the edge. Because
   a crate cannot write `use fs_qty::…` without that edge, the manifest rule is sufficient; this bead adds a
   second, cheaper text check that lists any `fs_qty::` path in `crates/**/src` outside the two allowed crates
   as a hint (a fact of the report, not a finding), and the plant below.
4. **Alias-count gate (TARGET).** The alias set stays at or below 64. Above that the product table (up to 64² =
   4,096 ordered pairs, of which only the registered ones exist) is no longer reviewable by a person, and the
   question returns to the owner as OPEN-SUITE-4. A test counts the registry rows and fails above 64.
5. **Generated, never edited.** The alias and product declarations in `frob_core::qty` are generated from the two
   registry files and compared by `xtask check-generated`: this bead adds the row `Quantity aliases and
   products | registries/qty_aliases.toml, registries/qty_products.toml | the generated declarations file of
   frob_core::qty | Regenerate, compare bytes` to that check's generator table (BD-004).

Determinism: compile-time only. Evidence: none; this is a typing discipline.

## Acceptance criteria

- [ ] A scratch crate that lists `fs-qty` as a dependency and is neither `frob-core` nor `frob-fsim` fails `xtask check-deps`, which names the crate and the edge; the clean tree passes.
- [ ] `frob_core::qty` exports exactly the registry aliases, the registered products and `Checked`; a test enumerates and compares.
- [ ] Compile-fail tests exist and fail to compile as required: pressure + time; and the nine equal-dimension pairs (torque + energy, torque + angular stiffness, energy + angular stiffness, frequency + angular velocity, momentum + impulse, angular momentum + angular damping, angle + ratio, angle + friction coefficient, ratio + friction coefficient).
- [ ] Every pair of registry aliases with equal dimension vectors has distinct `kind` tags and a compile-fail test, checked by a test that derives the pairs from the registry.
- [ ] Every registered product has a test that the output alias has the sum (or difference) of the operand dimension vectors.
- [ ] `Checked::into_alias` refuses a mismatched dimension with `FROB-REF-102` and returns the value bits unchanged on a match.
- [ ] The alias count is at most 64 and the count is printed by the test.
- [ ] `cargo xtask check-generated` is clean on the tree, and one byte changed in the generated declarations of `frob_core::qty` fails it with `gen.differs`.

## Test plan

### Unit tests

`cargo test -p frob-core qty`:
- `alias_registry_matches_exports`: the set of public type names equals the registry.
- `product_dimensions_add`: for every product row, dim(out) = dim(lhs) ± dim(rhs), exactly.
- `no_duplicate_product`: no ordered pair has two outputs.
- `checked_roundtrip_bits`: for 10⁴ seeded values including −0.0, subnormals and the largest finite value, `Checked → alias → Checked` preserves `to_bits()`.
- `checked_mismatch_refuses`: a `Checked` with dimension (1, 0, −1, 0, 0, 0) converted to `Length` returns `FROB-REF-102` with observed and required dimensions.
- `alias_count_at_most_64`.
- `equal_dimension_pairs_covered`: groups the registry rows by dimension vector; every group of two or more has distinct `kind` tags, and every unordered pair inside a group has a file under `compile_fail/` (expected on the starter set: 5 groups, 9 pairs).
- `compile_fail/` (trybuild-style, real compiler): `pressure_plus_time.rs`, `torque_plus_energy.rs`, `torque_plus_angular_stiffness.rs`, `energy_plus_angular_stiffness.rs`, `frequency_plus_angular_velocity.rs`, `momentum_plus_impulse.rs`, `angular_momentum_plus_angular_damping.rs`, `angle_plus_ratio.rs`, `angle_plus_friction_coefficient.rs`, `ratio_plus_friction_coefficient.rs`, each with the expected error.

`xtask` tests: `check_deps_rejects_fs_qty_outside_allowed` on a scratch copy with the planted crate (finding
`L-2.fs-qty-direct`); `fs_qty_path_hint_reported` (a `use fs_qty::Length` in a third crate's source is listed under
`facts`, not as a finding); `qty_generator_row` (the committed declarations equal the generator's output over the
two registries; one changed byte → `gen.differs`; a row added to `qty_aliases.toml` without regeneration →
`gen.differs`).

### End-to-end script and logging

`scripts/e2e/qty_confinement.sh` (owned by this bead; header `bead=N33c-03 milestone=M0 labels=suite,marrow
plants=fs-qty-direct,qty-generated-byte`), sourcing the STD-E2E helper; BD-031's `suite_toolchain_matrix.sh`,
which depends on this bead, runs it as a stage. It runs `cargo test -p frob-core qty` and `cargo xtask
check-generated` on the real tree (both clean); copies the tree to scratch, plants the forbidden dependency, runs
`cargo xtask check-deps --root <copy> --json`, expects exit 2 with a finding `L-2.fs-qty-direct` naming the crate
and the edge, and logs an `assert` event `planted_fs_qty_import_caught` with the exit code and the matched line;
on a second copy changes one byte of the generated declarations and expects `gen.differs`. Logged per STD-E2E:
`cmd` events with exit code and wall time, `metric` events `alias_count` (threshold 64) and `equal_dimension_pairs`
(9 on the starter set), and a `summary`.

### Known answers and negative controls

KA-779 (the part that holds while the hatch is closed): a pressure added to a time fails to compile; its negative
control: a torque added to an energy must fail to compile although both have dimension vector (kilogram 1, metre
2, second −2). CX-354. Planted defects: a product row whose output has the wrong dimension (the dimension test
must fail); an alias exported without a registry row (the export test must fail); a 65th alias (the count test
must fail); a 37th alias `WorkDone` with the dimension of energy and no compile-fail file (the pair-coverage test
must fail and name the missing pairs). Lanes: debug and release compile the same set; the compile-fail tests run on T and, if `frob-units`
exists, on stable.

## Considerations

- OPEN-SUITE-4 (owner: Marrow lead; decided with INT-TOOLCHAIN-01): the alias set and whether it stays within 64.
  Fail-closed default: the quantities used by the algebraic core through contact only, the starter set above.
- GPU buffers are raw `f32` with the dimension recorded in the buffer schema; this module types the host API,
  not the kernels.
- Rule L-6 (no bare `f64` physical quantity in a public signature above layer 1) is enforced by the signature
  scan of N34-05 in each crate's conformance test, which accepts the aliases of this module as quantities; this
  bead counts no signatures.
- `fs-qty`'s SI parsing is used by the design language; if the hatch opens, parsing moves with the module, which
  N33c-06 covers.
- A reader of this bead should not conclude that `fs-qty` is weak: the closed set is a restriction this project
  places on itself to keep a replacement possible.
