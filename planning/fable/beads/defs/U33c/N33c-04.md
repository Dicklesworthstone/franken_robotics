## Background

Every public signature above layer 1 of FrankenRobotics carries typed physical quantities from one module,
`frob_core::qty`. That module exposes a closed set of aliases (Length, Torque, Energy, …) and a table of products
and quotients among them, instead of open-ended dimension arithmetic, so that the units crate behind it can be
replaced (`fs-qty` today; the stable crate `frob-units` if the nightly feature `fs-qty` needs stops compiling on
the project's toolchain).

OPEN-SUITE-4 is the open question: which aliases are in the set, and does the set stay within 64? Its owner is
the Marrow lead (the lead of the algebraic core), and it is decided with the admission gate INT-TOOLCHAIN-01. The
bound of 64 is a TARGET with a reason: products and quotients are generated by a declarative macro from a table,
and above about 64 aliases that table is no longer reviewable by a person. The fail-closed default while the
question is open: the quantities used by the algebraic core, the design language, actuators, dynamics, body
families and contact, and nothing else.

This is a decision bead. It blocks nothing by waiting, because the default holds; it must close before a crate
above layer 1 freezes its public contract, since adding an alias later is cheap but renaming one is a breaking
change to every signature that uses it.

## Scope

In: the review of the starter set against the quantities the first crates really need; the decision record; the
frozen registry files. Out: the module mechanics and tests (N33c-03); `frob-units` (N33c-05).

## Technical approach

1. **Collect demand.** From the contracts (or, where a contract does not exist yet, the type sketches) of
   `frob-lie`, `frob-algebra`, `frob-design`, `frob-model`, `frob-actuate`, `frob-dyn`, `frob-contact` and
   `frob-phylum`, list every physical quantity that appears in a public signature, with its SI dimension and the
   signatures that use it.
2. **Compare with the starter set of N33c-03** (thirty-six aliases: Length, Area, Volume, Angle, Ratio, Mass,
   Density, Time, Frequency, AngularVelocity, AngularAcceleration, Velocity, Acceleration, Force, Torque, Energy,
   Power, Momentum, Impulse, AngularMomentum, MomentOfInertia, Stiffness, AngularStiffness, Damping,
   AngularDamping, Pressure, Temperature, HeatCapacity, ThermalResistance, Current, Voltage, Resistance,
   Inductance, Charge, TorqueConstant, FrictionCoefficient). For each demanded quantity decide: an existing
   alias; a new alias; or `Checked` (the runtime quantity that carries its dimension as a value), which is the
   right home for a quantity used in one loader and nowhere in a signature.
3. **Rules for admitting an alias (DESIGN).** (a) It appears in at least two public signatures or in one
   signature of a layer-0 or layer-1 crate. (b) It has an SI unit string. (c) If its dimension equals an existing
   alias's, it gets a distinct kind and a compile-fail test against each alias of the same dimension. (d) Its
   products and quotients are only those some signature needs; no row is added "for completeness".
4. **Count and headroom.** Record the count n and the headroom 64 − n. If n exceeds 48, the record names the
   aliases most likely to be demanded by the later subsystems (sensors, control, learning, structure) and states
   whether the bound will hold; if n would exceed 64, the question goes to the owner with two options written
   out: raise the bound with a generated review aid for the product table, or move rarely used quantities to
   `Checked`.
5. **Record.** An ADR in the ADR-SUITE series: the final alias list with dimension vectors and kinds, the product
   table size, the count, the rejected candidates with the reason, and the trigger for revisiting (a subsystem
   whose contract needs five or more new aliases). `registries/qty_aliases.toml` and
   `registries/qty_products.toml` are updated to the decided set and regenerated.

No code beyond the registry rows is written here.

## Acceptance criteria

- [ ] A table of demanded quantities by crate exists in the ADR, each mapped to an alias or to `Checked`.
- [ ] The decided alias count n is recorded and n ≤ 64; the alias-count test of N33c-03 passes on the decided registry.
- [ ] Every pair of aliases with equal dimension has a distinct kind and a compile-fail test.
- [ ] The ADR is signed off by the Marrow lead, or the default is recorded as taken with the date and the reason no decision was made.
- [ ] OPEN-SUITE-4 is marked decided (or default-taken) in the open-question register with a link to the ADR.

## Test plan

### Unit tests

No new test code; this bead re-runs `cargo test -p frob-core qty` on the decided registry. The tests that must
pass are `alias_registry_matches_exports`, `product_dimensions_add`, `no_duplicate_product`,
`alias_count_at_most_64` and the `compile_fail/` set, with one added compile-fail file for each new pair of
equal-dimension aliases the decision introduces.

### End-to-end script and logging

The step of `scripts/e2e/suite_toolchain_matrix.sh` that runs the `frob-core` quantity tests logs a `metric` event
`qty_alias_count` with value n, unit `aliases`, threshold 64, and an `assert` event that the registry digest
equals the digest named in the ADR.

### Known answers and negative controls

Known answer: with the starter set unchanged, n = 36 and the equal-dimension groups are Torque/Energy/
AngularStiffness, Frequency/AngularVelocity, Momentum/Impulse and Angle/Ratio/FrictionCoefficient. Negative
control: a registry with two aliases of equal dimension and equal kind must be rejected by the registry
validator (they would be the same type under two names).

## Considerations

- Fail-closed default until decided: the starter set only; a crate that needs a quantity outside it uses
  `Checked` and records the need for this bead.
- The decision interacts with `frob-units`: every alias and product must be expressible on a stable compiler by a
  declarative macro. An alias whose arithmetic needs generic dimension products is refused here.
- Angle is dimensionless in SI and still gets its own kind, because the project's tolerance rule forbids one
  unitless epsilon across angles, impulses and temperatures.
