## Background

If the escape hatch opens (the units crate `fs-qty` no longer compiles on the project's toolchain and the upstream
fix cannot land within the toolchain train), the project's quantity types become those of the stable crate
`frob-units`. FrankenSim's own crates still speak `fs-qty` in their signatures, wherever they still compile, and
in every case when the referee runs as a worker process built on an older pin. Something must convert at the
boundary.

That something is the airlock crate `frob-fsim`, the only crate allowed to name FrankenSim's volatile types.
DESIGN: conversions to and from `fs-qty` live in `frob-fsim` only, so the rule "only `frob-fsim` names types from
FrankenSim's volatile crates, and `fs-qty` is named only through `frob_core::qty`" (L-2) still holds after the
switch. The switch itself is one module: `frob_core::qty` stops re-exporting `fs-qty` and re-exports `frob-units`.

While both crates exist they are tested against each other. The known answer KA-779: every alias product agrees
with `fs-qty` in a differential test while both exist; a round trip through the airlock conversion preserves the
value bits.

This bead is conditional on N33c-05 and is not started unless the hatch opens. It closes either way, because the
M0 exit review (BD-044, priority 0) depends on it: hatch open, it is built to this text and closes `pass`; hatch
closed, it closes `withdrawn` citing BD-031's `frob-units` ADR (`withdrawn: not needed: escape hatch closed,
docs/adr/<that ADR>`), as N33c-05 does (N41-17, rule 5: a bead on a branch a decision did not take). A later
toolchain train whose ADR opens the hatch (NF-02, step 3) reopens both beads and does not proceed until both close
`pass`. Priority 0, the milestone's default, for that reason: its close is on the M0 exit's path on either branch.

## Scope

In: the conversion functions in `frob-fsim`; the differential test of the two crates; the one-module switch in
`frob-core`; the build probe that the switched graph has no `fs-qty` edge outside `frob-fsim`. Out: the crate
`frob-units` (N33c-05); the decision to open the hatch (BD-031 at INT-TOOLCHAIN-01, then NF-02 at each toolchain
train); the one-toolchain checks (N33c-08).

## Technical approach

1. **Conversion surface (DESIGN).** Module `frob_fsim::qty_bridge`. For each alias A of the registry, two free
   functions: `to_fs(a: frob_units::A) -> fs_qty::<corresponding type>` and `from_fs(q: fs_qty::…) ->
   frob_units::A`. Free functions, not `From` impls: neither type is local to `frob-fsim`, so the orphan rule
   forbids the trait impls, and a named function keeps every crossing greppable. Both are `#[inline]`, take and
   return SI base units, and perform no arithmetic: the value's 64 bits are moved unchanged.
2. **Correspondence table.** Generated from `registries/qty_aliases.toml`, which gains a column `fs_qty_type`
   naming the `fs-qty` type or alias of the same dimension and kind. A registry row without a correspondence is
   a build error of `frob-fsim` (the alias cannot cross the airlock), listed by name.
3. **Runtime quantities.** `checked_to_fs(c: frob_units::Checked)` and `checked_from_fs(…)` for `fs-qty`'s
   runtime-checked quantity: the six exponents are copied in order (metre, kilogram, second, kelvin, ampere,
   mole on both sides) and the value bits are unchanged.
4. **The switch.** In `frob-core`: `pub mod qty { pub use frob_units::*; }` replaces the `fs-qty` re-export,
   behind no feature flag (one build graph has one answer). `frob-core`'s manifest drops `fs-qty` and gains
   `frob-units`. The dependency-rule row of N33c-03 changes to: `fs-qty` may be a direct dependency of
   `frob-fsim` only. The bedrock-direct crates that depend on `fs-qty` themselves (`fs-evidence` directly,
   `fs-ivl` through it) are then reachable only through `frob-fsim` or through the worker, which the ADR that
   opens the hatch must state.
5. **Differential test (while both exist).** A dev-only test crate target inside `frob-fsim` (the one place
   allowed to see both): for every product row `L op R = O` of the registry and for seeded operand values, compute
   the product in `frob-units` and in `fs-qty` and compare `to_bits()` of the results and the dimension of the
   outputs. If `fs-qty` does not compile on T (the reason the hatch opened), the test builds in the `worker/`
   workspace on the pinned older toolchain and is run there; the admission record says which.
6. **Record.** The ADR that opens the hatch cites the differential test's result and the list of aliases with no
   `fs-qty` correspondence (expected: none).

## Acceptance criteria

- [ ] For every alias, `from_fs(to_fs(x)).value().to_bits() == x.value().to_bits()` on the test vectors, including −0.0, subnormals, infinities and a NaN with a non-default payload.
- [ ] For every registered product and quotient, the `frob-units` result and the `fs-qty` result agree bit for bit and in dimension on 10⁴ seeded operand pairs.
- [ ] After the switch, `cargo tree` for every workspace shows `fs-qty` as a direct dependency of `frob-fsim` only; `xtask check-deps` passes on the clean tree and fails on a planted second edge.
- [ ] After the switch, every crate above the airlock compiles without source changes other than those forced by an alias with no correspondence (count recorded; zero expected).
- [ ] The switch is a diff confined to `frob-core`'s `qty` module and manifest, `frob-fsim`'s bridge, and the rule row; the commit touches no other crate.
- [ ] The compile-fail tests of N33c-03 still fail to compile after the switch.

## Test plan

### Unit tests

`cargo test -p frob-fsim qty_bridge` (in the workspace where both crates compile):
- `roundtrip_bits_all_aliases`: the vectors above, every alias.
- `checked_dim_order`: a `Checked` with exponents (1, 2, 3, 4, 5, 6) crosses and returns with the same six numbers in the same order.
- `differential_products`: every product row, 10⁴ seeded pairs, bits and dimension.
- `differential_parse`: the unit-string fixtures (`"60 mm"`, `"0.1 N·m"`, `"9.81 m/s^2"`, `"12 V"`) parse to the same value bits and dimension in both crates.
- `no_correspondence_is_build_error`: a `synthetic` registry row with an empty `fs_qty_type` makes the generator fail with the alias name.

### End-to-end script and logging

`scripts/e2e/suite_units_hatch.sh` (owned by N33c-05, which writes stage 1; this bead adds stages 2 to 4): (1)
builds and tests `frob-units` on T and on stable; (2) runs the
differential test where `fs-qty` compiles and logs which toolchain that was; (3) applies the switch on a scratch
copy, builds the core, runs `cargo xtask check-deps`, and runs the `frob-core` quantity tests; (4) plants a
second `fs-qty` edge and expects the check to fail. It logs `cmd` events with the exact commands and both
compiler versions, `assert` events for each acceptance criterion, a `metric` event with the count of product rows
compared, and on a mismatch the first differing alias pair with both bit patterns in hex.

### Known answers and negative controls

KA-779 in full: every alias product agrees with `fs-qty` in a differential test while both exist; a round trip
through the airlock conversion preserves the value bits; a pressure added to a time fails to compile; negative
control: a torque added to an energy must fail to compile although both have dimension vector (kilogram 1, metre
2, second −2). Planted defects the tests must catch: a bridge function that multiplies by 1.0 + 2⁻⁵² (the bit
test fails); a `Checked` bridge that swaps the kelvin and ampere exponents (the order test fails); a product row
whose `frob-units` output alias differs from `fs-qty`'s kind (the differential test fails). Lanes: debug and
release; both machines.

## Considerations

- If `fs-qty` cannot be compiled on any available toolchain, the differential test cannot run and the hatch is
  opened on the strength of `frob-units`' own tests alone; the admission record must say that KA-779's
  differential clause is `not run`, with the reason.
- The value-preserving bridge assumes both crates store SI base units in an `f64`. That is a FACT to re-read in
  `fs-qty` at the pin before the bridge is written; a scaled internal representation would make the bit test
  fail on its first run, which is the intended detection.
- Closing the hatch again after FD-FSIM-15 lands is the same switch in reverse and is covered by the same tests.
