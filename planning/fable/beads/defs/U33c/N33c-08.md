## Background

One toolchain, T, builds every crate that any `frob` binary links: the core, the GPU annexes, the derivation tool
and the MCP server. T is recorded in two places, `franken-stack.lock` and `rust-toolchain.toml`. No annex carries
a toolchain file of its own. `lean/` is not Rust and keeps its own toolchain. `frob-cert` (the independent
auditor) builds on T inside the graph and also alone on a stable release, with its own stable toolchain file.
One exception is a fallback by design: when the FrankenSim worker process is kept at an older pin (the first
fallback of KILL-FSIM), the `worker/` workspace builds on that pin's toolchain.

T is chosen once, at INT-TOOLCHAIN-01. After that it moves only by a **toolchain train**: one coordinated change
that moves T in this repository and in every consumed sibling that needs it, followed by the admission and
parity gates. The reason for the ceremony: a toolchain move changes what every crate compiles to, the siblings
are separate repositories with their own gates and other agents working in them, and a half-moved graph is a
graph that does not build. Rejected alternative: letting each workspace float to the newest nightly (the
`fs-qty` crate depends on an incomplete compiler feature, so "newest" is not safe, and a ratio of times measured
across a toolchain change is not one measurement).

The first train may be needed at once: if T was chosen as candidate (b), FrankenSim's present pin
`nightly-2026-07-06`, the train to candidate (a), `nightly-2026-08-31`, is scheduled by the ADR of BD-031.

## Scope

In: the written procedure `docs/runbooks/toolchain-train.md`; the conditions `xtask check-stack` enforces for the
one-toolchain rule; a dry-run script for a proposed T′; the record a train leaves. Out: the changes inside
siblings (each is an upstream work item under that sibling's rules); the `check-stack` engine (BD-004); the
matrix harness (N33c-01).

## Technical approach

**Enforced conditions (rows for `check-stack`, DESIGN).**

1. The channel in `rust-toolchain.toml` equals the top-level `toolchain` of `franken-stack.lock`.
2. No other file named `rust-toolchain` or `rust-toolchain.toml` exists in the repository, except
   `crates/frob-cert/rust-toolchain.toml` (which must name a stable release, never a nightly) and
   `worker/rust-toolchain.toml`, allowed only when the lock's `FD-FSIM` row carries `worker_rev` (a worker kept
   at an older pin) and then required to equal that row's `worker_toolchain`.
3. For every foundation row with posture `consume` or `consume-path`, the row's `toolchain` field equals the
   channel in the sibling's toolchain file at the row's `git_rev`. After a completed train every such field
   equals T; before it, a difference is reported as `off-T` with the sibling's name (a report at M0, a failure
   once the ADR of the train says the train is complete).
4. The newest resolution receipt names the same T.

**The procedure (numbered; each step leaves a record).**

1. *Propose.* State T′, the reason (a sibling needs it; a fix landed; the scheduled move from (b) to (a)), and
   the siblings whose toolchain file or declared `rust-version` must change (from the suite survey, N33c-07).
2. *Dry run.* `scripts/admission/toolchain_train_dryrun.sh <T′>` runs the matrix harness with T′ as an extra
   column over all six build sets (`fs-qty` alone; the bedrock-direct list; the M1 closure; the core with the
   Metal annex; `surface/frob-mcp` with fastmcp_rust; `derive/frob-derive` with the `fsym-*` crates), using the
   siblings' current heads. Every row must pass, or the failing crate is named.
3. *Decide on `fs-qty`.* If `fs-qty` is what fails on T′: the preferred fix is the upstream change in FrankenSim
   (FD-FSIM-15, or the smaller FD-FSIM-31). If that change cannot land within this train, either the train is
   abandoned and T stays, or the escape hatch opens and `frob-units` is created (N33c-05, N33c-06). The choice is
   an ADR; a train never proceeds with a failing `fs-qty` row and no decision.
4. *Change the siblings.* For each sibling in the list, an upstream work item in that repository, under its own
   `AGENTS.md`, gates and conventions, with its files reserved through Agent Mail before any edit, landing on
   that sibling's `main`. The change is the toolchain file and, where T′ requires it, the declared
   `rust-version`; the sibling's own test suite must pass on T′. No sibling checkout is moved or edited by a tool
   of this repository.
5. *Move the pins and T in one commit here.* Each moved sibling's `git_rev` and `toolchain` in
   `franken-stack.lock`; the top-level `toolchain`; `rust-toolchain.toml`. Relock every workspace with
   `--locked` afterwards to confirm.
6. *Write a new resolution receipt* for that commit.
7. *Rerun the gates.* Every admission gate already recorded (the INT gates admitted so far, each by its own
   script) and the parity gates in force. A gate that passed before and fails now blocks the train's completion.
8. *Record.* An ADR: T, T′, the sibling commits, the receipt hash, the gate results, and the next scheduled
   train if any. `DEPENDENCY_ADMISSION.md` gets one entry per re-run gate.

**Freeze.** During the ten-fold tournament (milestone M7) every pin and T are frozen; a train requested inside
the freeze window is refused by the procedure and recorded as deferred.

## Acceptance criteria

- [ ] `xtask check-stack` fails on each of: a channel mismatch between the lock and the toolchain file; a toolchain file planted in `spark/frob-spark-cuda/`; a nightly named in `frob-cert`'s toolchain file; a `worker/` toolchain file with no `worker_rev` in the lock. It passes on the clean tree.
- [ ] The dry-run script produces a matrix column for T′ and exits non-zero when any row fails, naming the crate.
- [ ] The runbook exists with the eight steps, the `fs-qty` decision point and the freeze rule, and names for each step the record it leaves.
- [ ] If T was chosen as candidate (b): the train to `nightly-2026-08-31` has a scheduled bead and its dry-run result is recorded; if T is candidate (a), this criterion is recorded as not applicable.
- [ ] A rehearsal on a scratch copy (T′ = T, a no-op train) executes steps 2, 5, 6 and 7 and leaves a receipt that differs from the current one only in `repo_rev`.

## Test plan

### Unit tests

`xtask` tests on scratch copies of the real tree:
- `stack_rejects_channel_mismatch`, `stack_rejects_annex_toolchain_file`, `stack_rejects_nightly_in_frob_cert`, `stack_rejects_worker_toolchain_without_worker_rev`, `stack_accepts_worker_toolchain_with_worker_rev` (each plants one file or one field and asserts the exit status and the message).
- `stack_reports_off_T_sibling`: a foundation row whose `toolchain` differs from T is reported with the sibling's name.

Script test: `dryrun_names_failing_crate` with a `synthetic` probe crate that fails only on the proposed channel.

### End-to-end script and logging

`scripts/e2e/suite_toolchain_train.sh`: performs the no-op rehearsal on a scratch copy, runs the four plants
against `cargo xtask check-stack`, and runs the dry run with T′ = T. It logs `cmd` events for every invocation, an
`assert` event per plant with the exit code observed and required, the two receipt hashes with the list of
differing fields, and a `summary` naming `gates: [INT-TOOLCHAIN-01]`.

### Known answers and negative controls

Known answer: a no-op train leaves every gate result unchanged and a receipt equal to the previous one except
`repo_rev`. Negative controls: the four plants above; a train commit that moves the toolchain file and not the
lock (must fail `check-stack`); a dry run in which one sibling was silently left on its old channel while its
crate needs T′ (the matrix cell must fail and name it). The stale-stack-lock plant of GATE-WS-01 (7 of 7 plants
caught, each by the check that owns it and by no other) is the same family, and these plants must not be caught
by any check other than `check-stack`.

## Considerations

- RISK-02: the train costs more than M0 allows, or breaks a sibling. Mitigation in this bead: the dry run comes
  before any sibling is touched, and candidate (b) is the reserve.
- RISK-55: an upstream change collides with other agents in the same sibling. File reservations before edits;
  small additive changes; the interim posture ships meanwhile.
- A sibling's newer clean head is never rolled back locally to make a train pass.
- OPEN-WS-3 (the stable release in `frob-cert`'s toolchain file) is decided at that crate's first commit; this
  bead only enforces "stable, not nightly".
- A train is also the moment the `fs-qty` coupling can bite (way 1 of the three); the matrix's first row is its
  leading indicator.
