## Background

One toolchain, T, builds every crate that any `frob` binary links: the core, the GPU annexes, the derivation tool
and the MCP server. T is recorded in two places, `franken-stack.lock` and `rust-toolchain.toml`. No annex carries
a toolchain file of its own. `lean/` is not Rust and keeps its own toolchain. `frob-cert` (the independent
auditor) builds on T inside the graph and also alone on a stable release, with its own stable toolchain file.
One exception is a fallback by design: when the FrankenSim worker process is kept at an older pin (the first
fallback of KILL-FSIM), the `worker/` workspace builds on that pin's toolchain.

T is chosen once, at INT-TOOLCHAIN-01. After that it moves only by a **toolchain train**: one coordinated change
that moves T in this repository and in every consumed sibling that needs it, followed by the admission and
parity gates. The reason for the ceremony: a toolchain move changes what every crate compiles to, the siblings
are separate repositories with their own gates and other agents working in them, and a half-moved graph is a
graph that does not build. Rejected alternative: letting each workspace float to the newest nightly (the
`fs-qty` crate depends on an incomplete compiler feature, so "newest" is not safe, and a ratio of times measured
across a toolchain change is not one measurement).

A rule that is only written down erodes: one annex gains a toolchain file "for now", one sibling row keeps an
old channel after a train, and the graph has two compilers without anyone having decided it. This bead makes
the one-toolchain rule a set of conditions that `cargo xtask check-stack` fails on, so that between trains the
state "one T everywhere" is checked on every run, and so that a train's last step has something exact to pass.

## Scope

sibling row that is not yet on T; the planted violations and their tests on scratch copies of the real tree;

Out, with the bead that has it:

## Technical approach

**Enforced conditions (rows for `check-stack`, DESIGN).**

1. The channel in `rust-toolchain.toml` equals the top-level `toolchain` of `franken-stack.lock`.
2. No other file named `rust-toolchain` or `rust-toolchain.toml` exists in the repository, except
   `crates/frob-cert/rust-toolchain.toml` (which must name a stable release, never a nightly) and
   `worker/rust-toolchain.toml`, allowed only when the lock's `FD-FSIM` row carries `worker_rev` (a worker kept
   at an older pin) and then required to equal that row's `worker_toolchain`. Identifier
   `stack.toolchain-file`, kinds `extra-toolchain-file`, `nightly-in-frob-cert`, `worker-toolchain`. The two
   worker keys do not exist in `frob.stack-lock/1`: N33a-03 adds them only by an ADR and a schema bump to `/2`
   when KILL-FSIM's fallback (a) is taken. Until then the lock model's worker pin is always absent and any
   `worker/` toolchain file fails; the condition is written as a function of the model's optional worker pin, so
   that the exception exists and is tested now, on synthetic model values.
3. For every foundation row with posture `consume` or `consume-path`, the row's `toolchain` field equals the
   channel in the sibling's toolchain file at the row's `git_rev` (read with `git show`, never by checking the
   sibling out), and equals T. A difference from T is reported as `stack.toolchain`, kind `off-T`, with the
   sibling's name and channel: informational until the first adopted toolchain train, a failure after. The
   trigger is read from the train log, not from an ADR: a line of `receipts/train-log.ndjson` with
   `kind = "toolchain"` and `outcome = "adopted"` (written by step 7 of NF-02; schema `frob.train-log/1` of
   N33b-04; this condition reads only those two fields with `frob-core`'s strict JSON reader, and an absent file
   means no train has been adopted). DESIGN: a train is the only event that brings every consumed sibling onto
   T, and under candidate (b) siblings already on the common nightly stay there after INT-TOOLCHAIN-01 until the
   scheduled train to (a), so the trigger is the train and not the gate (N33a-03 rule 9 says the same). A
   difference between the row's `toolchain` and the sibling's own file at `git_rev` is a failure at once
   (`stack.toolchain`, kind `row-toolchain-stale`): the row must say what the sibling pins.
4. The newest resolution receipt names the same T. Conditions 1 and 4 are the row `stack.toolchain`, kind
   `toolchain-changed`, that N33a-05 implements; they are listed here because the rule is four conditions, and
   this bead's plants test them as part of it, without a second implementation.

**`lean/` (DESIGN, the same statement in NF-02).** The scan of condition 2 matches the two Rust file names
anywhere in the repository, `lean/` included. `lean/` is not Rust: its own toolchain is a `lean-toolchain`
file, which is not a Rust toolchain file and is outside the rule. A `rust-toolchain.toml` planted under `lean/`
is a violation like any other. Reason: the plan's sentence "`lean/` is not Rust and keeps its own toolchain"
is about Lean's compiler; exempting the directory from the scan would leave one place where a second Rust
compiler could enter unseen.

**Messages.** Each condition fails with its own message line, naming the file or the row at fault; the
`off-T` line names the sibling and its channel. The wording follows the message conventions of `check-stack`
(N33a-05). The conditions read files of this repository and the siblings' toolchain files at their pinned
revisions; like the rest of `check-stack` they write to no sibling checkout (INV-SUITE-04).

**What relies on them.** The toolchain train (NF-02) ends its one commit by running `check-stack`: a train
commit that moved the toolchain file and not the lock fails condition 1, a leg that did not land leaves an
`off-T` row under condition 3, and a receipt written before the move fails condition 4. The tournament freeze
(N33b-03) relies on the same conditions to state that T did not move during a campaign.

## Acceptance criteria

- [ ] `xtask check-stack` fails on each of: a channel mismatch between the lock and the toolchain file; a toolchain file planted in `spark/frob-spark-cuda/`; a nightly named in `frob-cert`'s toolchain file; a `worker/` toolchain file with no `worker_rev` in the lock. It passes on the clean tree.
- [ ] A `rust-toolchain.toml` planted under `lean/` fails condition 2; a `lean-toolchain` file there does not.
- [ ] A foundation row whose `toolchain` differs from T is reported as `stack.toolchain`, `off-T`, with the sibling's name: informational (exit 0 if nothing else is found) while `receipts/train-log.ndjson` holds no adopted toolchain train, a failure once it holds one; a row whose `toolchain` differs from the sibling's own toolchain file at `git_rev` fails at once with `row-toolchain-stale`.
- [ ] Under `frob.stack-lock/1` a `worker/rust-toolchain.toml` always fails `stack.toolchain-file`, `worker-toolchain`; the condition function accepts it for a synthetic model value carrying a worker pin with an equal channel and refuses it for an unequal one.
- [ ] A receipt that names another T than the lock fails condition 4.
- [ ] Each plant is caught by `check-stack` and by no other `xtask` check.

## Test plan

### Unit tests

`xtask` tests on scratch copies of the real tree:
- `stack_rejects_channel_mismatch`, `stack_rejects_annex_toolchain_file`, `stack_rejects_nightly_in_frob_cert`, `stack_rejects_worker_toolchain_without_worker_rev` (each plants one file or one field and asserts the exit status, the identifier, the kind and the message).
- `worker_exception_on_model_values`: the condition function with a synthetic worker pin equal to the planted `worker/` channel → no finding; unequal → `worker-toolchain`; absent → `worker-toolchain`.
- `stack_rejects_rust_toolchain_under_lean`; `stack_ignores_lean_toolchain_file`.
- `stack_reports_off_T_sibling`: a foundation row whose `toolchain` differs from T is reported with the sibling's name, exit 0; `off_T_fails_after_train_adopted`: the same row with a scratch train log holding a `kind = "toolchain"`, `outcome = "adopted"` line is a failure (exit 2); with only an `abandoned` line, or a `kind = "compat"` line, it stays informational.
- `row_toolchain_must_match_sibling_file`: a row `toolchain` unequal to the channel in a synthetic sibling's toolchain file at `git_rev` → `row-toolchain-stale`; the sibling's working tree is not read (a different channel in the working tree only changes nothing).
- `stack_rejects_receipt_on_other_T`.

The dry-run test `dryrun_names_failing_crate` (a `synthetic` probe crate that fails only on the proposed
channel) moved with the dry run to NF-02, where it is `dry_matrix_blocks_on_failing_cell`.

### End-to-end script and logging

`scripts/e2e/suite_one_toolchain.sh`: on a scratch copy of the real tree it runs the four plants of the first
acceptance line, the `lean/` pair and the train-commit plant (the toolchain file moved, the lock not) against
`cargo xtask check-stack`, then the clean tree. It logs through the STD-E2E helper `cmd` events for every
invocation, an `assert` event per plant with the exit code observed and required and the message line, and a
`summary` naming `gates: [INT-TOOLCHAIN-01]`. The no-op train and the dry run with T′ = T, which this script
once also ran, are run by the rehearsal NF-06 (its step 13) with NF-02's script.

### Known answers and negative controls

Known answer: the clean tree passes all four conditions. Negative controls: the four plants above; a train
commit that moves the toolchain file and not the lock (must fail `check-stack`). The stale-stack-lock plant of
GATE-WS-01 (7 of 7 plants caught, each by the check that owns it and by no other) is the same family, and
these plants must not be caught by any check other than `check-stack`. The known answer of a no-op train (a
receipt equal to the previous one except `repo_rev`) and the control "one sibling silently left on its old
channel while its crate needs T′" belong to the procedure and are in NF-02. Determinism: the verdict and the
message lines are a pure function of the tree.

## Considerations

- RISK-02: the train costs more than M0 allows, or breaks a sibling. This bead's part of the mitigation is
  that a half-moved graph cannot pass `check-stack`; the dry run before any sibling is touched, and candidate
  (b) as the reserve, are NF-02's.
- OPEN-WS-3 (the stable release in `frob-cert`'s toolchain file) is decided at that crate's first commit; this
  bead only enforces "stable, not nightly".
- The `worker/` exception exists only for the first fallback of KILL-FSIM. If that fallback is never taken, the
  exception is never exercised outside its test.
- `off-T` is a report before the first train completes because, when T is candidate (b), the siblings already
  on `nightly-2026-08-31` are not moved backward and keep a different channel until the train to (a); making
  it a failure from the first day would block M0 on a state the plan allows.
- A train is also the moment the `fs-qty` coupling can bite (way 1 of the three); the matrix's first row is its
  leading indicator, and the decision at a train is NF-02's step 3.
