## Background

A build of FrankenRobotics may contain exactly one asupersync package (asupersync is the suite's structured
concurrency runtime; two versions in one binary would give two incompatible cancellation contexts). The siblings
do not all agree: frankentui pins `=0.5.0` behind an optional feature `asupersync-executor`, franken_threed pins
`=0.5.0`, and frankenjax requires `0.5.0` optionally and uses the third-party `egg` crate, while the consumed
siblings resolve 0.6.2 (FACT, read 2026-11-21). The design consequence: one asupersync version, and 0.5.0 never
enters a graph. FrankenSim's constellation, FrankenTorch and fastmcp_rust are aligned on one published version by
changes in those repositories (FD-ASUP-01, gate INT-ASUP-01); frankentui's executor feature is forbidden; and
frankenjax and franken_threed are never Cargo dependencies. `xtask check-deps` enforces all three.

Several other siblings are named by the design and deliberately kept out of the dependency graph. Each has a
posture: **Pattern** (the design is copied, not the code), **Oracle** (development and test only, never in a
production graph), **Subprocess** (a binary this project invokes; no crate in the build graph), or **not
admitted**. A posture that lives only in prose is forgotten the day someone adds a convenient dependency. This
bead writes the postures as data and makes `check-deps` refuse what they forbid.

## Scope

In: the deny rows, the posture register `registries/siblings.toml` (posture columns), their plants and tests.
Out: the `check-deps` engine and its layer rules (BD-003); the one-package-per-binary invariant test (N33c-29);
the `serde_json` single-version rule (N33c-38); the confinement of `fs-qty` (N33c-03).

## Technical approach

**The register (DESIGN).** `registries/siblings.toml`, one row per sibling: `name`, `posture` (a list, because a
posture belongs to a use and one sibling may be consumed for one purpose and be an oracle for another), `cargo`
(`allowed`, `dev-only`, `never`), `allowed_in` (crate names), `forbidden_features`, `reason`, `fallback`. Rows
this bead fills (FACT columns were checked in code on 2026-11-21 and are re-read by the suite survey):

| Sibling | Checked fact | Posture | Cargo | Use |
|---|---|---|---|---|
| frankentui | 0.10.0; `ftui-runtime` has an optional exact pin on asupersync 0.5.0 behind `asupersync-executor` (`crates/ftui-runtime/Cargo.toml:56, :81`) | Consume [F] | allowed in `frob-tui` only, default features off, `runtime` and `native-backend` on; `asupersync-executor` forbidden | The dashboard |
| franken_threed | four crates; pins asupersync `=0.5.0` and `serde_json = "=1.0.151"` | Pattern; Subprocess [F] | never in a workspace that builds a `frob` binary; an admission-probe workspace under `tests/admission/` may path-depend on an `f3d-*` crate with its `serde` feature off | Its admission-record discipline (already adopted); an optional renderer route for the viewer; the ray-transform probe |
| frankenjax | `fj-egraph` on third-party `egg`; requires asupersync 0.5.0 | Pattern | never | Reference semantics for batching and differentiation transforms; e-graph rule sets |
| franken_textiles | `ftx-drape`, about 116 thousand lines; exact pin `serde_json = "=1.0.151"` | Oracle; Subprocess [M] | never | Cloth reference, run as a worker process in its own workspace |

| franken_firmware | eighteen crates including `franken-hal`, `franken-control`, `franken-platform`; stable 1.99.0 | Pattern [M] | never | The hardware-abstraction boundary for firmware export. Exported firmware never touches a register, a bus or a stop relay |

| franken_surveillance_system | — | Pattern | never | The twin package and the camera-model contract |

**The deny rows (read by `check-deps` over `cargo metadata` of every workspace: core, both GPU annexes, `apps/`,
`derive/`, `bindings/`, `worker/`).**

1. *No asupersync 0.5.0 anywhere.* Any resolved package `asupersync` with version 0.5.x in any workspace fails,
   naming the path of dependents that brought it.
2. *The frankentui executor.* If `ftui-runtime` is in a graph, its resolved feature set must not contain
   `asupersync-executor`; frankentui crates may be direct dependencies of `frob-tui` only.
3. *Never-dependency siblings.* No package whose manifest path lies under `../frankenjax`, `../franken_threed`,
   `../franken_textiles`, `../franken_firmware`, `../franken_networkx`, `../franken_markdown`,
   `../frankenmermaid` or `../franken_surveillance_system` may appear in any resolved graph, at any depth, for any
   target or feature combination. The check resolves with every optional feature group enabled, because a build
   that never enables a feature resolves cleanly and the conflict appears only when the flag is first turned on.
4. *Dev-only siblings.* `franken-kernel` may appear only as a dev-dependency of `frob-conformance`; a normal edge
   from any crate, or any edge from `frob-core`, fails.
5. *Third-party carried by a forbidden sibling.* The crate `egg` in any graph fails, with the hint that it
   arrives through frankenjax.

Each failure prints the rule name, the offending package and one dependency path. `check-deps` itself stays
inside the six-subcommand limit of `xtask`: these are rows of its table, not a new check.

## Acceptance criteria

- [ ] `registries/siblings.toml` validates against its schema and contains the nine rows above with posture, cargo policy, reason and fallback.
- [ ] Five plants on scratch copies each fail `cargo xtask check-deps` with the named rule: (1) a path dependency that resolves asupersync 0.5.0; (2) `frob-tui` enabling `ftui-runtime/asupersync-executor`; (3) a `frob-design` dependency on `fnx-algorithms`; (4) a normal dependency of `frob-core` on `franken-kernel`; (5) a `derive/` dependency on `fj-egraph`.
- [ ] The clean tree passes with every optional feature group enabled.
- [ ] A plant behind an optional feature that no default build enables (a feature `cloth-oracle` adding `ftx-drape`) is still caught.
- [ ] Each plant is caught by `check-deps` and by no other of the six checks.

## Test plan

### Unit tests

`xtask` tests (`cargo test -p xtask check_deps_suite`), each on a scratch copy of the real tree with one planted
manifest edit and real `cargo metadata`:
- `denies_asupersync_0_5_0`, `denies_ftui_executor_feature`, `denies_never_dependency_sibling` (parameterized over the eight directories), `denies_franken_kernel_normal_edge`, `allows_franken_kernel_dev_edge_in_conformance`, `denies_egg`, `catches_plant_behind_optional_feature`.
- `siblings_registry_schema`: a row with an unknown posture or a missing `reason` is a load error.

### End-to-end script and logging

`scripts/e2e/suite_deps_rules.sh` (shared with N33c-29 and N33c-38): for each plant, copies the tree, applies the
edit, runs `cargo xtask check-deps`, and asserts a non-zero exit and the rule name in the output; then runs the
clean tree with all features. It logs one `cmd` and one `assert` event per plant (rule expected, rule reported,
exit code), and a `summary` with plants caught out of plants planted.

### Known answers and negative controls

The plants above are the negative controls; a deny rule that no plant can trip validates nothing. Known answer:
on the clean tree `cargo tree -d` lists no duplicate `asupersync`. Counterexample to the shortcut "a passing build
means the pins are compatible": a build that never enables the oracle's feature flag resolves, and the conflict
appears only when the flag is first turned on at the oracle's milestone; hence resolution with every optional
feature group enabled. Lanes: both machines (the Metal annex resolves only on the Mac, the CUDA annex on `trj`).

## Considerations

- RISK-03: two asupersync versions in one build; leading indicator `cargo tree -d` at INT-ASUP-01.
- RISK-19: the viewer drifts outside franken_threed's admitted subset; plain Three.js is the fallback and is
  always built.
- Path-based rule 3 depends on siblings living beside this repository under `~/projects`; a sibling consumed from
  a registry instead would be matched by package name, which the register also lists.
- If frankentui's executor is ever wanted, the upstream work item FD-FTUI-01 (relax the exact 0.5.0 pin) must
  land first; until then the feature is forbidden and nothing here needs it.
