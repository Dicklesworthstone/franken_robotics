## Background

FrankenSim is the referee of FrankenRobotics: the trusted CPU physics against which the fast tiers are judged. It
is consumed as path dependencies behind one airlock crate, `frob-fsim`. FrankenSim moves daily (409 commits to its
multibody crate in thirty days), and its closure is large (the set M1 needs is 65 crates and about 2.06 million
lines). If in-process consumption stops being tenable, the first fallback is not to copy source but to move the
referee behind a process boundary.

**ADR-SUITE-02: before any FrankenSim source is lifted, the referee moves behind a process boundary.** [S]
`frob-fsim` has two build modes behind the same traits. In mode `inproc` (the default) the adapters call
FrankenSim through path dependencies. In mode `remote` every volatile `fs-*` dependency is compiled out and the
adapters speak a job protocol to a worker process built from the same crate at the pinned commit. Reason: a lift
of the minimal referee set sits on a closure of about 1.5 million lines and cutting it free is engineering the
worker avoids entirely, while a worker keeps FrankenSim's real code as the referee at an old pin for as long as
needed. Rejected: a lift first (cost above); a per-call remote procedure interface (the solver and its working
set must stay together on one side, and per-tick calls would put process overhead inside loops).

This bead defines the protocol both sides speak. It exchanges whole jobs and bounded chunks. It never carries a
per-link, per-ray or per-tick call.

## Scope

In: message types, canonical encoding, the job hash, the chunk partition and digests, framing, protocol
versioning, in module `frob_fsim::job` (compiled in both modes; no FrankenSim type in it). Out: the client
adapters (N33c-11); the worker binary (N33c-12); supervision and the receipt handshake (N33c-13); the gate run
(BD-038).

## Technical approach

**Messages (the three of the design, plus three control messages added here as DESIGN and labelled so).**

```
job    = { job_hash, stack_receipt, model (compiled referee model, canonical bytes), scene, initial_states,
           control (a schedule, or a controller program the worker evaluates), horizon, cadence, seeds,
           outputs (state columns, events, digests, energy-ledger rows) }
chunk  = { job_hash, index, first_step, last_step, columns, events, digest, final: bool }
refuse = { job_hash, code, upstream_reason }
hello  = { protocol, stack_receipt, receipt_class, features, pid }  (worker → client, once, first)  DESIGN
resume = { job_hash, next_index }                              (client → worker, with a resubmission) DESIGN
cancel = { job_hash }                                          (client → worker)                    DESIGN
```

1. **Canonical bytes.** A job header is canonical JSON written by this project's own writer: keys sorted by code
   point, no insignificant whitespace, integers above 2⁵³ as decimal strings, rationals as reduced integer pairs,
   no float in the header (times are integer ticks of a rational base unit; `horizon` is a step count; `cadence`
   is `{dt: [num, den] seconds, chunk_steps: C, sample_every: n}`). Bulk data (`model`, `scene`,
   `initial_states`, a control schedule) are binary blocks referenced from the header by `{len, blake3}`.
   Canonical job bytes = header bytes ‖ the blocks in header order.
2. **Job hash.** `job_hash` = BLAKE3 (32 bytes) of the canonical job bytes with the `job_hash` member absent.
   Submission is idempotent on the hash: submitting the same bytes twice yields the same chunks and never two
   runs' worth of different results.
3. **Fixed chunk partition.** Chunk k covers steps [k·C, min((k + 1)·C, horizon)), C = `chunk_steps`. `first_step`
   and `last_step` are the inclusive ends. The partition depends only on the job, so a restarted worker
   regenerates the same boundaries and the client resumes from the last contiguous chunk whose digest it holds.
   `final` is true on the chunk whose `last_step` is `horizon − 1`; a zero-step job (a batch evaluation at the
   initial states) has exactly one chunk with `first_step = 0`, `last_step = −1` written as the string `"none"`,
   and `final: true`.
4. **Chunk content and digest.** `columns` are little-endian binary columns of the outputs the job asked for
   (state columns in `f64`, digests, energy-ledger rows), in the fixed order of the `outputs` list; `events` is a
   canonical JSON array (contact events, refusals of individual worlds). `digest` = BLAKE3(`job_hash` ‖ `index`
   as u64 LE ‖ `first_step` as u64 LE ‖ step count as u64 LE ‖ column bytes ‖ event bytes). Because it covers
   only job-determined bytes, the digest of a chunk computed in process and through the worker is the same value
   if and only if the outputs are bit-identical.
5. **Refusal.** `code` is a FrankenRobotics refusal code; `upstream_reason` carries FrankenSim's own typed
   refusal text unchanged. The adapter converts and never reinterprets: a FrankenSim refusal becomes a typed
   referee refusal carrying the upstream reason, and is never retried with weakened inputs.
6. **Receipt.** `stack_receipt` in a job names the resolution receipt (BLAKE3) the caller expects the referee to
   have been built under: the `receipt` of the `FD-FSIM` row of `franken-stack.lock`. The worker's `hello`
   reports the receipt it was built under, and `receipt_class`: `gate` for a build on clean sibling trees,
   `development` for a build made with dirty trees (which can never back a gate PASS). `features` lists the
   airlock groups the worker was compiled with and its capacities as data (for example
   `sustained_contact_capacity: 21`). A receipt mismatch is a refusal (`FROB-REF-791`), not a warning.
7. **Framing.** One frame = `u32` little-endian payload length, one byte kind (1 hello, 2 job, 3 chunk, 4 refuse,
   5 resume, 6 cancel), payload. Payload = `u32` LE header length, the canonical JSON header, then the binary
   blocks. Maximum frame 1 GiB (TARGET); a larger chunk is a protocol error, so `chunk_steps` must be chosen to
   bound chunk size. Transport is a local socket or a pipe; the framing is identical on both.
8. **Version.** `protocol` is the string `frob.fsim-job/1`. A client refuses a worker with another major
   version with `FROB-REF-791` and the two version strings.

Types (DESIGN, Rust sketch; the in-memory `Chunk` carries the step count, and the wire header carries the
design's `last_step` = `first_step` + `steps` − 1, or the string `"none"` when `steps` = 0; the decoder checks
that the two agree): `struct Job { header: JobHeader, blocks: Vec<Block> }`, `struct Chunk { job_hash:
Hash, index: u64, first_step: u64, steps: u64, columns: Vec<u8>, events: Vec<u8>, digest: Hash, final_: bool }`,
`enum Frame { Hello(Hello), Job(Job), Chunk(Chunk), Refuse(Refuse), Resume(Resume), Cancel(Cancel) }`, with
`encode(&Frame, &mut impl Write)` and `decode(&mut impl Read) -> Result<Frame, ProtocolError>`.

Determinism: exact; encoding is a pure function. The module depends on `frob-core` (hashing, canonical writer)
and on nothing from FrankenSim.

## Acceptance criteria

- [ ] `encode` then `decode` is the identity on every frame kind; `decode` then `encode` reproduces the input bytes.
- [ ] The job hash is unchanged by re-encoding and changes when any member or any block byte changes.
- [ ] The partition function returns the same chunk boundaries for any (horizon, C), covers every step exactly once, and marks exactly one final chunk.
- [ ] An integer above 2⁵³ in a header round-trips exactly as a string; a float literal in a header is rejected by the reader.
- [ ] A frame with a wrong length prefix, an unknown kind or a truncated block is a typed `ProtocolError`, never a panic.
- [ ] The module compiles with `--no-default-features --features mode-remote` (no `fs-*` crate in its closure) and with the default features (mode `inproc`). The Cargo features `mode-inproc` and `mode-remote` are the pair the airlock skeleton declares (N33a-11); this bead relies only on their existence, and N33c-11 gives them their content.
- [ ] The protocol section of `frob-fsim`'s `CONTRACT.md` lists the six frames, the hash rule and the partition rule.

## Test plan

### Unit tests

`cargo test -p frob-fsim job::` (default features, and `--no-default-features --features mode-remote`):
- `frame_roundtrip_all_kinds`: seeded frames of each kind.
- `job_hash_excludes_itself_and_is_stable`: hash computed twice and after a decode/encode cycle is equal.
- `job_hash_sensitive`: flipping one bit of `seeds`, of `horizon`, of a block changes the hash (three cases).
- `partition_known_answers`: horizon 2,000, C = 250 → 8 chunks, boundaries 0–249, …, 1750–1999, final on index 7; horizon 2,001 → 9 chunks, the last with one step; horizon 0 → one final chunk with zero steps, encoded with `last_step` `"none"`.
- `last_step_agrees_with_steps`: a chunk header whose `last_step` disagrees with `first_step` and `steps` is a `ProtocolError`.
- `chunk_digest_binds_position`: the same column bytes at index 3 and index 4 have different digests.
- `u64_as_string`: 9,007,199,254,740,993 (2⁵³ + 1) survives; the JSON-number form is rejected.
- `decode_rejects_malformed`: 1,000 seeded truncations and bit flips of valid frames return `ProtocolError`.
- Property test: for random (horizon ≤ 10⁶, C ≤ 10⁴) the chunks tile [0, horizon) with no gap or overlap.

### End-to-end script and logging

Exercised by `scripts/e2e/suite_worker_fallback.sh` (BD-038), which logs for every chunk a `metric` event with
`index`, `first_step`, `last_step` and the digest in hex from both the in-process and the worker run, and on a
mismatch the first differing chunk index and the paths of both chunk files.

### Known answers and negative controls

Known answers: the partition cases above; the 2⁵³ + 1 integer (a client that reads doubles would decode it as
9,007,199,254,740,992). Negative controls: a chunk key built from a tick range supplied by the sender instead of
the fixed partition (two overlapping ranges [0, 100) and [50, 150) would both be accepted; the partition test
must reject any chunk whose bounds are not partition extents); a digest that omits `index` (the position-binding
test fails). Lanes: twice on one machine; debug and release; the encoded bytes of a fixture job are identical on
`trj` and on the Mac.

## Considerations

- The header carries no private-scene data in clear beyond what the job needs; logs print hashes and sizes of
  blocks, never their contents.
- The same protocol shape is reused for the cloth oracle worker (N33c-28), which is why the encoding lives in a
  module with no FrankenSim type.
- A fixed overhead per job is the cost of the fallback, so the referee is called in rollouts and never inside a
  loop; the protocol deliberately offers no cheaper granularity.
- `chunk_steps` trades resume granularity against frame size; the default is 250 steps (DESIGN), revisited with
  the first measured chunk sizes.
