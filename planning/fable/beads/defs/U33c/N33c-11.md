## Background

`frob-fsim` is the airlock: the only crate that may name types from FrankenSim's volatile crates. It exposes
FrankenRobotics-native traits (`RefereeDynamics`, `RefereeContact`, `Integrator`, `PortSystem`, and the traits of
the other feature groups) and adapts them. Under ADR-SUITE-02 the crate has two build modes behind the same
traits. In mode `inproc`, the default, the adapters call FrankenSim through path dependencies. In mode `remote`
every volatile `fs-*` dependency is compiled out and the adapters speak the job protocol to a worker process (the
binary `frob-fsim-worker`, built from this same crate in mode `inproc` at the pinned FrankenSim commit).

This is the first fallback of the kill gate KILL-FSIM. Its trigger: the path-consumption gate INT-FSIM-01 cannot
pass within two weeks of M0 effort, or its cold check exceeds the machine envelope (one hour, 16 GiB, 8 cores),
or upstream breakage exceeds 20% of working days in any four-week window (the threshold of BET-04). When it
fires, the core is rebuilt in mode `remote` and stops compiling FrankenSim's volatile crates at all; the
bedrock-direct crates that still pass their own admission stay path dependencies, and those that do not are
lifted first, since they are small.

What the fallback preserves: the referee is FrankenSim's own code; teleport from a device tier to the referee (a
job whose initial state is a snapshot); shadow sampling; promotion. What it costs: a fixed overhead per job, so
the referee is called in rollouts and never inside a loop; and a second build to keep, though only at pin moves.
What it does not solve: an API change still costs the adapter, but the worker can stay on an old pin while the
core moves.

The mode is built and exercised at M0 although the fallback is not active, because a fallback that has never run
is a hope (CX-356).

## Scope

In: the Cargo feature layout of the two modes; the client that implements the airlock traits by submitting jobs;
idempotent submission; resume; cancellation; conversion of refusals; labelling of results with the referee's
receipt. Out: the protocol encoding (N33c-10); the worker (N33c-12); spawning and supervising it, and the receipt
handshake (N33c-13); the gate measurement (BD-038).

## Technical approach

1. **Features (DESIGN).** `crates/frob-fsim/Cargo.toml`: features `inproc` (default) and `remote`. Every `fs-*`
   dependency of the volatile set is `optional = true` and enabled only by `inproc` (through the group features
   `referee`, `geometry`, `ledger`, …, each of which implies `inproc`). `remote` enables none of them. Exactly one
   mode: `#[cfg(all(feature = "inproc", feature = "remote"))] compile_error!` and the same for neither. The
   bedrock-direct crates (`fs-ga`, `fs-math`, `fs-rand`, `fs-blake3`, and the rest of that list) are not
   affected by the mode.
2. **One trait surface at job granularity.** The traits a crate above the airlock calls are whole-job calls:
   `rollout(job) -> ChunkStream`, `evaluate(model, states, outputs) -> Columns` (a zero-step job), and
   `teleport(snapshot, job)` (a rollout whose `initial_states` block is a snapshot from a device tier). In mode
   `inproc` they execute in this process and yield the same `Chunk` values, computed by the same chunking code
   as the worker uses. In mode `remote` they submit jobs. Any finer-grained helper (a single forward-dynamics
   call used by a unit test) is `#[cfg(feature = "inproc")]` and is not part of the trait surface, so no crate
   above the airlock can come to depend on a per-tick call.
3. **Client algorithm (`frob_fsim::remote::Client`).**
   1. Build the canonical job, compute `job_hash`, set `stack_receipt` to the referee receipt of the stack lock.
   2. Obtain a connection from the supervisor (N33c-13); read `hello`; refuse with `FROB-REF-791` on a receipt
      or protocol mismatch before sending anything.
   3. Send `job`, or `job` plus `resume { next_index }` if chunks 0 … next_index − 1 are already held with
      verified digests.
   4. For each `chunk` frame: check `job_hash`; check that `index` is the next expected and that its bounds are
      the partition extent for that index; recompute the digest over the received bytes and compare with the
      frame's; append to the local chunk file; advance. Any violation is a protocol fault: the chunk is
      discarded and the job is resubmitted with `resume`.
   5. On `refuse`: return the typed referee refusal with `upstream_reason` attached, unchanged. Never retry with
      weakened inputs.
   6. On connection loss or worker death: ask the supervisor for a new worker, resubmit with `resume` from the
      last contiguous verified chunk, at most R = 3 times (DESIGN), then return a refusal that names the last
      committed step.
   7. On cancellation of the caller's context: send `cancel`, stop reading, report the last committed chunk
      index. A dropped handle is not a cancellation receipt.
4. **Result labelling.** Every result returned in mode `remote` carries `referee_receipt` (the worker's receipt)
   and `referee_mode: remote`. A memoized referee result carries the stack-lock digest in its key in both modes
   (the adapter rule "no cache across pins"). Results from a worker whose receipt differs from the core binary's
   own receipt are not same-stack evidence with in-process results (INV-SUITE-05; the refusal `FROB-REF-890`
   guards the merge).
5. **Capacities as data.** The 21-contact capacity of FrankenSim's sustained solver (FACT:
   `frankensim/crates/fs-contact/src/sustained/solve.rs:26`) is a field of `RefereeContact` in both modes; in
   mode `remote` it is taken from the worker's `hello.features`, checked when a model is compiled and again at
   run time, so an over-capacity contact set is a refusal by name and is never silently truncated.
6. **Feature groups in remote mode.** A verb that needs a group the worker was not built with is refused with
   `FROB-REF-790` (`foundation-group-absent`), naming the group, from `hello.features`.

Determinism: the client adds no arithmetic; outputs are the worker's bytes. Cancellation is tested. The CPU
reference path is mode `inproc`.

## Acceptance criteria

- [ ] `cargo tree -p frob-fsim --no-default-features --features remote` lists no volatile `fs-*` crate; enabling both modes or neither fails to compile with a clear message.
- [ ] A crate above the airlock compiles unchanged against both modes (checked with `frob-conformance`'s referee smoke test built twice).
- [ ] The same job through `inproc` and through `remote` yields equal chunk digests (measured by BD-038).
- [ ] Resubmitting a job with `resume { next_index: k }` returns chunks k onward, each with the digest of the uninterrupted run.
- [ ] A worker refusal reaches the caller as a typed refusal with the upstream reason text unchanged; no retry with altered inputs is attempted (retry counter asserted zero for refusals).
- [ ] Cancelling mid-job returns the last committed chunk index and leaves no worker job running.
- [ ] Every remote result carries `referee_receipt` and `referee_mode`.

## Test plan

### Unit tests

`cargo test -p frob-fsim --no-default-features --features remote remote::` against the real worker binary (built
by the test harness from the `worker/` workspace; no mock worker):
- `handshake_then_job`: a 500-step job returns 2 chunks at C = 250 and a final flag.
- `resume_after_kill`: the worker is killed after chunk 0; the client resubmits with `resume { 1 }`; all digests equal the uninterrupted run's.
- `rejects_out_of_partition_chunk`: a test-only worker flag makes it send a chunk with shifted bounds; the client discards it and resubmits.
- `rejects_corrupt_chunk`: one flipped byte in transit (a test-only transport wrapper) is detected by the digest check.
- `refusal_passthrough`: a model with 22 contacts in one island returns the typed capacity refusal with FrankenSim's reason string.
- `cancel_reports_last_committed`.
- `evaluate_zero_step_job`: forward dynamics at one G1 state through a zero-step job equals the in-process value bit for bit.
- Compile tests: `both_modes.rs` and `no_mode.rs` fail to compile.

### End-to-end script and logging

`scripts/e2e/suite_worker_fallback.sh` (BD-038) runs the rollout through both modes; this bead contributes the
client-side `metric` events (submission to first chunk in ms, chunks received, resumes performed) and `refusal`
events with code and upstream reason.

### Known answers and negative controls

KA-780 (digest equality through the worker, also after a kill). MR-37: a job run through the worker process
returns the digests of the same job run in process, also after the worker is killed and the job resubmitted;
mutation: a worker built at a different commit (refused). Planted defects: a client that accepts chunks without
recomputing the digest (the corrupt-chunk test must fail it); a client that resumes from `next_index + 1` (a gap;
the contiguity assertion catches it). Lanes: debug and release; twice on one machine.

## Considerations

- RISK-01 (FrankenSim API churn) and RISK-22 (the closure makes builds slow): mode `remote` removes the closure
  from the core's build entirely, which is its second benefit beyond the kill gate.
- Fixed overhead per job is measured by BD-038 (at most 50 ms per job and at most 5% of wall time on jobs of one
  second or more, TARGET). Callers that would place a referee call inside a loop must batch states into one
  `evaluate` job.
- If the worker stays on an old pin while the core moves, the adapter's conversion code must serve both the old
  job schema and the new traits; the protocol version string exists for that day.
