## Background

The daemon's job protocol and the Chronicle ledger writer are concurrent code whose failures are rare
interleavings: a crash between a chunk write and its commit, a cancel at an unlucky await point, completions out
of order. They cannot be tested by waiting. asupersync, the suite's structured-concurrency runtime, ships a lab
runtime for deterministic simulation testing, and this project already links asupersync, so the harness costs no
new package.

FACT (read 2026-11-21 at asupersync head `b32c5ba66315`; re-read by this bead): `asupersync/src/lab/` is about 127
thousand lines; its module header lists virtual time, deterministic scheduling by seed, trace capture and replay,
schedule exploration, test oracles, cancellation injection at await points and chaos injection (`src/lab/mod.rs`).
It is compiled under the `full-runtime` feature and re-exports `LabConfig` and `LabRuntime` (`src/lib.rs:237,
:502`). `chaos.rs` (918 lines), `ldfi.rs` (567), `replay_minimization.rs` (991), `dual_run.rs` and
`snapshot_restore.rs` exist.

**Use (DESIGN).** Every test of `frobd`'s job protocol and of the Chronicle writer runs under `LabRuntime` with a
recorded seed. Faults are injected by schedule: a kill inside a chunk write, a cancel at each await point,
completions out of order, a storage error. A failing schedule is minimized and stored as a replay fixture. Device
work is represented by a stub whose timing the lab clock controls, and a dual-run scenario compares the stub
against a real device on a small job.

**Posture.** Consume, as a dev-dependency of `frob-chronicle`, `frob-verbs` and `frob-conformance`; it is the same
single asupersync package. Gate: INT-ASUP-02. **Fallback:** the chaos tests at kernel-batch boundaries with a
hand-written virtual clock, which keep fault injection and lose schedule exploration.

**One caution.** `lab/conformal.rs` (906 lines) calibrates the lab's own oracle metrics and is not a general
interval library, so the interval on a runtime estimate (the daemon's job-time estimates) takes its design from
that file and none of its code.

## Scope

In: the admission of the lab runtime (facts re-read, feature wiring, one-package check); a small shared test
support module with the fault-schedule vocabulary, seed recording, minimization and the replay-fixture store; the
fallback clock, specified and built only if the admission fails. Out: the simulation tests of the ledger and the
submit path themselves (BD-096); the device stub and dual run (N33c-16); the gate measurement (N33c-17).

## Technical approach

1. **Admission probe.** A test in `frob-conformance` that: enables `asupersync` with `full-runtime` as a
   dev-dependency only; constructs `LabConfig` with a seed and a `LabRuntime`; runs a two-task program with one
   channel twice under the same seed and asserts identical captured traces; runs it under two different seeds
   and records whether the traces differ. The probe records the re-read facts: the feature name, the two
   re-exported types, and the presence of the chaos, lineage-driven fault selection, replay-minimization,
   dual-run and snapshot-restore modules, each by a compile-time use, not by a file listing.
2. **One package.** After the dev-dependency is added, `cargo tree -d -e dev` shows exactly one `asupersync`;
   the `full-runtime` feature must not pull a second version or a forbidden crate. `xtask check-deps` confirms
   that no non-dev edge enables `full-runtime` unless the daemon itself needs it.
3. **Fault-schedule vocabulary (DESIGN).** `frob_conformance::lab::Fault`:
   `Crash { at: AwaitPoint }`, `Cancel { at: AwaitPoint }`, `TornWrite { byte_offset }`, `StorageError { op }`,
   `Reorder { a, b }`, `Duplicate { msg }`, `Delay { msg, ticks }`, `LeaseExpiry { holder }`, `DeviceLoss`,
   `DiskFull`, `ClockJump { ticks }`, `ClientDisconnect { reconnect_after }`. An `AwaitPoint` is named by the
   path under test and an ordinal (`publish#3`), so that coverage ("every await point on the publish and submit
   paths was hit by a crash fault at least once") is countable.
4. **A run.** `Scenario { seed, faults: Vec<Fault>, program }` executes under `LabRuntime`; after it, the
   registered oracles run. The outcome is `Pass`, or `Fail { oracle, trace }`.
5. **Minimization and fixtures.** A failing scenario is reduced with the sibling's replay minimizer to a seed, a
   fault list and a schedule of minimal length, and stored as `tests/fixtures/lab/<oracle>-<blake3>.replay`
   (canonical bytes: seed, faults, schedule, the asupersync version and the stack-receipt hash). A fixture
   replays in under a second (TARGET) and is run by `cargo test` forever after. A fixture recorded under another
   asupersync version is re-validated, not trusted.
6. **Seeds are recorded.** Every lab test prints its seed on failure and accepts `FROB_LAB_SEED` to reproduce.
7. **Fallback (built only if the probe or INT-ASUP-02 fails after one repair cycle).** A hand-written virtual
   clock in `frob-conformance` (`VirtualClock { now: u64 ticks }` advanced explicitly; timers as a binary heap
   keyed by `(tick, sequence)`), used by chaos tests that inject cancellation at kernel-batch boundaries under a
   deterministic schedule. It keeps fault injection and loses schedule exploration; the gate INT-ASUP-02 is then
   recorded as failed with this fallback in force, and the simulation-testing beads are re-scoped to the chaos
   tier.

Determinism: exact under a seed (that is the property being admitted). Nothing here is evidence for a physical
claim.

## Acceptance criteria

- [ ] The admission probe passes: one seed, two runs, identical traces; the facts (feature name, `LabConfig`, `LabRuntime`, the five modules) are recorded with the asupersync revision.
- [ ] `cargo tree -d` over every workspace shows one asupersync package after the dev-dependency is added.
- [ ] The fault vocabulary covers the four schedule faults of the design (kill inside a chunk write, cancel at each await point, out-of-order completions, storage error) and the remaining menu of the simulation-testing chapter.
- [ ] A deliberately failing scenario (an oracle that rejects any reorder) is minimized to a fixture that replays to the same failure in under a second.
- [ ] `FROB_LAB_SEED` reproduces a failure bit for bit.
- [ ] No code from `lab/conformal.rs` is used or copied; a text check for its symbols in this repository is empty.
- [ ] The admission is recorded in `DEPENDENCY_ADMISSION.md` with the commit, command, output hash and receipt hash.

## Test plan

### Unit tests

`cargo test -p frob-conformance lab::`:
- `probe_same_seed_same_trace`, `probe_two_seeds_recorded`.
- `fault_roundtrip`: every `Fault` variant serializes to canonical bytes and back.
- `await_point_coverage_counts`: a three-await `synthetic` program reports three points; a schedule set that crashes each once reports full coverage, and one that skips a point reports it by name.
- `minimize_planted_reorder_bug`: a `synthetic` two-message protocol with a planted bug that loses the second message when delivery is reordered; the harness finds it, minimizes to a two-step schedule, stores the fixture, and replays it.
- `fixture_rejects_other_version`: a fixture whose recorded asupersync version differs is re-validated before use.
- If the fallback is built: `virtual_clock_orders_timers` (timers at ticks 5, 3, 5 fire in order 3, 5 (first registered), 5).

### End-to-end script and logging

`scripts/e2e/suite_lab_runtime.sh` (N33c-17) runs the probe first and logs the asupersync revision, the feature
set, the trace hash of the two same-seed runs, and the one-package assertion.

### Known answers and negative controls

Known answer: identical traces for one seed. Negative controls: the planted reorder bug must be found (a harness
that explores one schedule only would miss it); a scenario run with a wall-clock sleep inside the program must be
rejected by the harness (real time has no place under the lab clock; the test asserts a refusal to run).
Lanes: twice on one machine; debug and release; both machines must give the same trace hash for the probe.

## Considerations

- The lab runtime is large; it is a dev-dependency only and must not reach a production binary's graph.
- asupersync's checkout had 267 modified paths on the day of planning; an admission on a dirty tree is a
  development record and INT-ASUP-02 cannot record a PASS on it.
- The runtime-estimate interval mentioned in the caution is owned by the daemon's estimate beads; this bead only
  carries the prohibition on reusing the lab's calibration code.
- OPEN-SUITE-6 (whether computational crates take asupersync's `Cx` or a capability-free token) affects which
  crates can be driven under the lab runtime directly.
