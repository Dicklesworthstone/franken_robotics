## Background

The daemon's job protocol is tested by deterministic simulation under asupersync's lab runtime: virtual time,
scheduling by seed, faults injected by schedule. A real GPU cannot run under a virtual clock, so in those tests
device work is represented by a stub whose timing the lab clock controls. With a stub, a whole campaign simulates
in milliseconds and every interleaving is reproducible.

A stub is also a risk: it can drift into testing a protocol the real workers do not follow. The design therefore
requires a dual-run scenario that compares the stub against a real device on a small job, and requires the same
ledger state from both. This bead builds the stub and the dual run. The gate INT-ASUP-02 (N33c-17) relies on
both.

## Scope
In: `frob_conformance::lab::StubDevice`, which extends the M1 fake device of BD-096 (the same pure outcome
function of the world address) to the `KernelBackend` trait, so that the device job engine cannot tell it from a
device; its timing model under the lab clock; fault hooks; the dual-run scenario against `batch-cpu` and then a
device, and its comparison.
Out: the lab harness (N33c-15); the M1 scenarios, oracles and CPU dual run (BD-096, a dependency); the job
protocol under test (BD-210); the gate measurement (N33c-17).

## Technical approach

1. **The stub (DESIGN).** `StubDevice` implements the same backend trait the job engine uses for a real device.
   It runs no physics. For each world and chunk it returns an outcome that is a pure function of the world
   address and the chunk extent: `outcome(addr, extent) = BLAKE3("stub" ‖ run_seed ‖ world ‖ episode ‖
   first_tick ‖ ticks)`, expanded to the byte length of the requested columns. Because results are placed by
   address, a stub run is bit-reproducible and independent of scheduling, like a real tier.
2. **Timing under the lab clock.** Each kernel batch takes a virtual duration drawn from a declared model:
   `duration = base + per_world · worlds`, with an optional seeded jitter keyed by `(addr, batch index)`. The stub
   awaits the lab clock for that duration, so completion order across devices and slots is a function of the
   seed and the schedule, and the lab scheduler may interleave a fault at the await.
3. **Fault hooks.** The stub honours the schedule faults that concern a device: `DeviceLoss` (the await returns a
   device fault and uncommitted work is dropped), `Delay`, out-of-order completion of two batches, and
   cancellation at the batch boundary (the stub reports the last committed tick per world, as a real backend
   does).
4. **The dual-run scenario.** One small job (DESIGN: 64 worlds, one episode of 256 control ticks published as 4
   chunks of 64 ticks, one device slot, no faults; 64 is the smallest chunk length a run may be admitted with,
   N29b-18, and the real side is a real run, so an earlier figure of 50 ticks per chunk could not be run) is
   executed twice through the same job engine:
   - against `StubDevice` under `LabRuntime`;
   - against a real tier: `batch-cpu` on every machine, and each device family the machine has.
   The *protocol-visible ledger state* must be identical: the set of chunk extents committed, their order on the
   committed frontier, lease acquisitions and releases, job state transitions, receipt fields that do not depend
   on payload (counts, extents, idempotency binding), and the terminal receipt's accounting (completed, failed,
   refused and unstarted trial counts sum to the planned number). Payload bytes and digests differ by
   construction and are excluded by a declared mask; the mask is a short list in the scenario file and is itself
   reviewed.
5. **Dual run with one fault.** The same job with a cancellation at the second batch boundary, on the stub and
   on `batch-cpu`: both must report the same last committed tick per world and the same job state.
6. **Where it uses the sibling.** The comparison is driven by the lab runtime's dual-run facility if its
   interface fits (FACT to re-read: `asupersync/src/lab/dual_run.rs` exists); otherwise the scenario runs the two
   executions itself and compares canonical dumps of the ledger. The admission record says which.

Determinism: the stub is exact by construction; the real side meets its tier's class. The stub is test support
and is labelled `synthetic` in every log line it appears in.

## Acceptance criteria

- [ ] `StubDevice` passes the same backend conformance tests the job engine applies to a real backend for protocol behaviour (admission, chunk publish, cancel, fault report).
- [ ] Two stub runs with one seed produce identical ledgers; two seeds produce different completion orders and the same committed set.
- [ ] The dual-run scenario reports identical protocol-visible ledger state for the stub and for `batch-cpu`, and for each device family present.
- [ ] The dual run with a cancellation reports the same last committed tick per world on both sides.
- [ ] The comparison mask lists only payload-dependent fields; a planted protocol difference outside the mask is detected.
- [ ] The stub is not reachable from any non-test target (`cargo tree` of the `frob` binaries does not contain the module's feature).

## Test plan

### Unit tests

`cargo test -p frob-conformance lab::stub::`:
- `outcome_is_pure_function_of_address`: the same address and extent give the same bytes across runs, slots and submission orders.
- `timing_follows_model`: with `base` = 3 ticks and `per_world` = 1 tick, a 5-world batch completes at virtual tick 8.
- `device_loss_drops_uncommitted`: after `DeviceLoss` in batch 2, chunks of batch 1 are on the frontier and none of batch 2.
- `cancel_reports_last_committed`.
- `dual_run_ledger_equal_batch_cpu`: the scenario of item 4.
- `dual_run_ledger_equal_devices`: the same scenario against each device backend the machine has (`gpu-cuda` on `trj`, `gpu-metal` on the Mac), one case per family; on a machine with none the case reports `not-run: no device` and is never counted as a pass, so the acceptance line for device families is met only on the two machines together.
- `dual_run_with_cancel_equal`.

### End-to-end script and logging

A step of `scripts/e2e/suite_lab_runtime.sh` (N33c-17): runs the dual-run scenario on the machine's real tiers and
logs, per tier, an `assert` event `dual_run_ledger_equal` with the BLAKE3 of the masked ledger dump from each
side, and on a mismatch the first differing ledger row and both dump paths. Lines produced with the stub carry
`fixture: synthetic`.

### Known answers and negative controls

Known answer: the terminal receipt's trial counts sum to the planned number on both sides. Negative controls
(planted defects the dual run must catch): a stub that commits chunks out of partition order; a stub that reports
success for a cancelled batch; a stub that publishes a chunk before acquiring its lease. Each differs from the
real tier in protocol-visible state and must fail the comparison. A fourth control guards the mask: adding
"job state" to the mask must be rejected by the scenario's mask validator, which allows payload fields only.
Lanes: twice on one machine; debug and release; both machines.

## Considerations

- The stub's honesty is bounded by the dual run's job: a small fault-free job and one cancellation. Behaviours
  only a real device shows (driver faults, memory pressure) stay with the chaos tests on devices; the stub does
  not replace them.
- If the stub and the real tier ever disagree, the default assumption is that the stub is wrong; the stub is
  changed, and the disagreement is stored as a regression scenario.
- The real-device side of the dual run needs a device and counts against the machine envelope; it is a small job
  and runs in seconds.
