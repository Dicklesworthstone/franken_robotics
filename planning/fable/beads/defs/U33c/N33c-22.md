## Background

The derivation tool `derive/frob-derive` turns symbolic expressions into straight-line kernel programs and emits
them for three backends. A pilot (N33c-21) decides whether extraction over an e-graph, restricted to rewrites that
change no bit, shrinks those programs by at least 10% on at least three kernels while staying bit-identical. This
bead is the work that follows a passing pilot: making the extraction a regular pass of the derivation pipeline.
It exists only on that branch. If the pilot is dropped by its ceiling (arithmetic below 20% of step time) or
fails, this bead is closed as not funded and the fallback stays in force: common-subexpression elimination only,
through `fsym-simplify`, which the annex already uses.

The posture toward frankenjax, whose `fj-egraph` crate inspired the item, is Pattern: nothing of it is linked,
because it would add the third-party `egg` crate and a second asupersync version to the graph. The pass is
written here.

Why it matters when it is funded: fewer operations per kernel on every backend at no cost in determinism, since a
class-E rewrite changes no bit and therefore no kernel identity's results, no digest and no fidelity ledger
entry. Why it is small even then: the ceiling is the arithmetic share of step time multiplied by the reduction in
operations.

## Scope

In: the pass in the pipeline; per-kernel budgets; manifests updated with the pass's statistics; rule traces
attached as certificates; regeneration of checked-in kernel sources; the switch and its default. Out: the pilot
and the gate (N33c-21); class-R rewrites (reassociation, distribution, fused multiply-add), which make a
different kernel with a new identity, an error bound and a fidelity run, and are not this pass; per-design
specialization.

## Technical approach

1. **Place in the pipeline.** After lowering to the straight-line program and the existing
   common-subexpression pass, before register scheduling and emission: `slp → cse → egraph_extract → schedule →
   emit`. The pass consumes and produces the same representation; emitters are untouched.
2. **Rules.** Exactly the closed class-E table used by the pilot: commutation of + and ×; x × 1; x + (−0);
   double negation; select simplification; folding of exact constant operations; scaling by a power of two where
   the declared ranges exclude overflow and underflow. The table lives in one file with one unit test per rule
   showing exactness on its domain, and one per excluded rewrite showing a counterexample (reassociation: in
   `f32`, (10⁸ + (−10⁸)) + 1 = 1 and 10⁸ + ((−10⁸) + 1) = 0; x × 0 with x = NaN; x − x with x = ∞; x + 0 with
   x = −0).
3. **Budgets.** Per kernel: at most 50,000 e-nodes and 30 saturation iterations (the pilot's values, revised
   from its statistics), and a wall-time bound of 60 s per kernel in the derivation build. On a budget stop the
   pass extracts from the e-graph as it stands; the result is still valid because every state of the e-graph
   represents only exact equalities.
4. **Acceptance per kernel (enforced by the pass).** The extracted program replaces the baseline only if (a) its
   weighted operation count is strictly lower; (b) it is bit-identical to the baseline on the kernel's
   conformance vectors in every precision the kernel is emitted in; (c) its rule trace replays in the independent
   checker. Otherwise the baseline is kept and the manifest records why.
5. **Resource metadata.** Register pressure and stack bytes are recomputed after extraction. The buffer-argument
   count (limited to 31 on a Metal compute function) is unaffected by the pass, but register pressure can rise
   when sharing lengthens live ranges; a program whose bounds now exceed a backend limit is rejected in favour
   of the baseline. The manifest gains `egraph { enodes, iterations, ops_before, ops_after, trace_digest, budget_stop }`.
6. **Identity.** A class-E rewrite changes no kernel result. The kernel's *source* hash changes, so the binary
   cache key changes and binaries are rebuilt; the kernel's conformance digests do not change, and a test
   asserts that 1,000 worlds keep their state digests across the switch.
7. **Certificates.** The rule trace is bound to the kernel's content hash as a `rewrite-trace` certificate
   (theorem card T-27: a class-E rewrite trace maps the source program to the target program using only rules of
   the closed table; equality is over the reals, and bit-exactness in floating point is a test, not that
   theorem).
8. **Switch.** Feature `frontier-egraph` of `derive/frob-derive`, off by default (no default build enables a
   `frontier-*` feature). Checked-in generated kernel sources are regenerated with the feature on in one commit,
   and `xtask check-generated` then regenerates with the same setting recorded in `registries/kernels.toml`.
   Turning the pass off again is one flag and one regeneration.

Determinism: the pass is deterministic (stable iteration order over e-classes, ties in extraction broken by
e-node hash) so that regeneration reproduces checked-in sources bit for bit.

## Acceptance criteria

- [ ] The pass runs on every derived kernel inside its budgets; for each kernel the manifest records operations before and after, or the reason the baseline was kept.
- [ ] Every replaced kernel is bit-identical to its baseline on its conformance vectors on `batch-cpu`, CUDA and Metal, in each emitted precision.
- [ ] Every replaced kernel carries a rule trace that replays in the independent checker; a kernel without one is not replaced.
- [ ] State digests of 1,000 worlds over 1,000 steps are unchanged by switching the pass on.
- [ ] Regeneration with the recorded setting reproduces the checked-in sources bit for bit (`xtask check-generated` passes).
- [ ] No default build enables the feature; `xtask check-deps` confirms no frankenjax package and no `egg`.
- [ ] The total weighted operation count over the kernel library and its change are reported, with the measured step-time change on workloads Q and H and its ceiling beside it.

## Test plan

### Unit tests

`cargo test -p frob-derive --features frontier-egraph pass::`:
- `rule_exactness_table`: one test per rule, 10⁴ random inputs each including special values, bitwise equality.
- `excluded_rewrite_counterexamples`: the four counterexamples above.
- `keeps_baseline_when_not_smaller`; `keeps_baseline_on_register_overflow`.
- `deterministic_extraction`: two runs give the same program hash.
- `manifest_fields_written`.
- `budget_stop_still_valid`: with the node budget set to 100, the extracted program is bit-identical to the baseline.

### End-to-end script and logging

`scripts/e2e/suite_egraph_pilot.sh` gains a second mode `--all-kernels`: regenerates the kernel library with the
feature on, runs `frob spark check` on every backend present, runs the 1,000-world digest comparison through
`frob sim run` with and without the regenerated kernels, and logs per kernel a `metric` event (`ops_before`,
`ops_after`, `replaced`, `trace_digest`) and for the whole library `ops_total_change` and
`step_time_change_fraction` beside `ceiling_fraction`; digest mismatches log the first differing world address
and stage.

### Known answers and negative controls

Known answers: the regrouping case returns 1 in `f32`; the 1,000-world digests are unchanged. Negative controls:
a reassociation filed as a class-E rule must be rejected by the trace checker (the registered mutation of the
rewrite-control test); a pass that skips the conformance comparison and replaces unconditionally must be caught
by a planted rule x × 0 → 0 on a kernel whose vectors include NaN. Lanes: twice on one machine; debug and
release; `batch-cpu` against each device family, each against its determinism class.

## Considerations

- Priority 3: funded only after the pilot passes; most likely never started.
- Sharing more subterms lengthens live ranges and can raise register pressure on GPUs; the pass accepts a
  smaller program only when resource bounds still hold.
- The specialization of kernels for survivor designs is a different mechanism with its own kill gate; the two
  must not be confused when gains are reported.
- If the derivation toolchain's kill gate fires (KILL-KIR), derived kernels are replaced by hand-written ones and
  this pass has nothing to act on.
