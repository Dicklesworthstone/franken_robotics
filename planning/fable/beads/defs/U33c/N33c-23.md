## Background

`frob-tui` is a terminal dashboard for a person watching a campaign: jobs, races, budgets and gate status. It is
built on frankentui, a sibling terminal-interface library. FACT (read 2026-11-21 at head `5979b92cc576`): version
0.10.0, twenty crates under `frankentui/crates`, about 1.15 million lines, on `nightly-2026-08-31`; an Elm-style
runtime (`Model`, `Cmd`) in `ftui-runtime`; a pane workspace in `ftui-layout`; widgets including `Table`,
`ProgressBar`, `LogViewer` and `StatusLine`; `ftui-harness` supports headless tests with shadow-run comparison
and determinism fixtures. `ftui-runtime` carries an optional exact pin on asupersync 0.5.0 behind the feature
`asupersync-executor` (`crates/ftui-runtime/Cargo.toml:56, :81`).

The dashboard is a Frontier [F] item with a stated ceiling: a convenience for a person watching a campaign; no
claim and no agent workflow depends on it. It issues only read verbs (plus job cancellation under a token with
that scope, after a confirmation) and has no private interface.

**Posture.** Consume, with default features off and `runtime` and `native-backend` on; the executor feature is
forbidden, because it would bring a second asupersync package (0.5.0) into the graph. `frob-tui` reads the
daemon's event stream over the local socket and links no physics crate. If frankentui does not build on the
project's one toolchain T, the remedy is an upstream change in frankentui or a toolchain train; until it lands
the fallback applies, and the crate gets no toolchain of its own.

**Gate INT-FTUI-01** (TARGET; first needed at M3): one asupersync package or none in its graph; the job pane
rendered from a recorded event stream equals its stored snapshot in the headless harness; idle processor use at
most 2% of one core. **The gate is also the pilot**, run on a recorded stream before the crate is funded.
**Kill:** the gate fails, or frankentui cannot be built without its executor (the kill gate KILL-TUI: frankentui
cannot be admitted with one asupersync package, or the snapshot tests cannot be made stable). **Fallback:** no
dashboard; the same events as line-delimited JSON, and `job.list` and `session.show` carry the same numbers.

## Scope
In: the pilot record, written to the pilot register before the run; a probe crate outside the core workspace that
builds frankentui with the allowed feature set; one pane (the job pane) rendered from a recorded stream in the
headless harness; the snapshots and the replay-stability runs; the idle-CPU measurement; the gate record of
INT-FTUI-01 and the funding recommendation that the KILL-TUI decision (N32b-31) reads.
Out: the dashboard with its six panes (the capstone BD-300 and the dashboard beads N32b-06 to N32b-09, none of
which starts on a `do not fund`); the daemon; any change in frankentui (upstream work in its repository: FD-FTUI-01
relaxes the exact 0.5.0 pin and is needed only if the executor is ever wanted).
This bead replaces the duplicate draft N33a-23; its protocol, falsifier and replay checks are folded in below.

## Technical approach

1. **Probe crate.** `tools/pilots/ftui-probe/`, a crate with its own `[workspace]` table outside the core workspace (a
   pilot runs before the mechanism is funded; `crates/frob-tui`, behind the feature `frontier-tui`, off by
   default, is created by the dashboard beads only on a `fund` recommendation). Dependencies: the frankentui crates by path at the pinned revision
   with `default-features = false, features = ["runtime", "native-backend"]`; `frob-core` for envelope types; no
   `frob-fsim`, no kernel, no physics crate. Because `frob-core` reaches FrankenSim's `fs-blake3` and `fs-qty` by
   path, the probe's root manifest repeats the three root settings the core repeats (FrankenSim's
   `[patch.crates-io] asupersync` entry, its profile overrides, and `.cargo/config.toml` with
   `FRANKENSIM_DEPGRAPH_SALT`) and commits its own `Cargo.lock`, as the admission probes of N33c-01 do; no cargo
   command runs inside a sibling checkout.
2. **Graph check.** `cargo tree -d -e normal,build` for the probe workspace must show one
   `asupersync` package or none through frankentui, and `ftui-runtime`'s resolved features must not contain
   `asupersync-executor` (the deny row of `xtask check-deps`). `cargo check` and `cargo test` run on T; a failure
   to build on T is recorded with the first failing crate and decides OPEN-WS-2's branch (below).
3. **Recorded stream.** `tests/fixtures/tui/job_events_01.ndjson`: a real stream recorded from the job protocol
   (one line per event: job admitted, chunk committed with progress `done/total`, estimate updated, preempted,
   resumed, cancelled, completed, refused), at least 2,000 events covering 20 jobs in four size classes. Recorded
   from a real run on `batch-cpu`; if the daemon's stream does not exist yet at pilot time, the fixture is built
   from the M2 job receipts and labelled `synthetic`, and the pilot is repeated on a real stream before BD-300
   closes.
4. **The job pane (the "Queue" pane of the dashboard in its minimal form).** A table: job identifier, agent,
   size class, state, progress with its denominator, wait time, estimate against actual, preemption count; a
   status line with counts by state. Model update is a pure function `update(model, event) -> model`; the view
   is a pure function of the model and the terminal size.
5. **Snapshot test.** In `ftui-harness`, headless, terminal size 120 × 40: feed the recorded stream, render after
   events 1, 500, 1,000 and the last, and compare each rendered buffer (cells with their style attributes) with
   stored snapshots `tests/fixtures/tui/job_pane_<n>.snap`. Equality is exact. The test runs 20 times; any
   difference between runs is a stability failure (one of KILL-TUI's triggers).
6. **Idle CPU.** With the stream ended and the pane displayed in a pseudo-terminal, measure process CPU time over
   60 s of wall time: (user + system CPU seconds) / 60 ≤ 0.02. Measured three times; the maximum is recorded.
7. **Record and decision.** Admission record (N33a-07's writer) with the frankentui revision, the `cargo tree -d`
   output hash, the snapshot hashes, the idle-CPU figures, and as `harness_receipt` the receipt of the gate's tier
   run; the INT-FTUI-01 part is entered from that receipt with `cargo run -p frob-conformance --example
   record_gate -- --gate INT-FTUI-01 --receipt <hash>`, by a session that did not implement the probe (N38b-19
   refuses `self-certified`). Funding decision (ADR): PASS → BD-300 proceeds on frankentui; FAIL after one repair
   cycle, or no build without the executor → the recommendation is `do not fund`, KILL-TUI is recorded by its
   decision bead N32b-31 and the fallback is the dashboard's description from then on.
8. **On `do not fund`.** The pilot's `[[pilot.result]]` carries the verdict `falsifier-holds`, and the session
   that records the funding decision closes the dashboard beads N32b-06 to N32b-09 `withdrawn`, citing the pilot
   and that result (N41-17, rule 7): they exist only for the funded dashboard and could never become ready. The
   KILL-TUI decision N32b-31, which depends on N32b-09, then becomes ready and is taken from the pilot's record
   alone: it fires on the failed admission after the repair cycle and asks for no dashboard replays, which could
   never exist.

**Pilot record and frozen protocol (DESIGN).** Before anything is built, a record is written to
`crates/frob-conformance/registry/pilots.toml`: mechanism `frob-tui` on frankentui, Frontier; tool and pin
(frankentui at the revision of the day); cost at most one agent-day and no device; the ceiling stated in the
Background; fallback and kill gate KILL-TUI (no dashboard; the same events as line-delimited JSON). The steps
above are the protocol and are not changed after the first run. Three checks are part of it besides the gate's
own:
- *Executor necessity.* Confirm that nothing in the probe needs `asupersync-executor`; then enable it in a
  second scratch copy and record that asupersync 0.5.0 appears (the control showing the count check can fail).
- *Replay stability.* Replay the recorded stream 100 times: every replay reproduces every stored frame byte for
  byte. Replay it again with the events delivered in bursts of seeded random size (1 to 50): the frames at the
  same event indices still match, because the model is a function of the event sequence.
- *Stream content.* The recorded stream contains at least one job of 200 or more chunks, one cancellation and
  one refusal; events carry job identifier, state, progress with a denominator, estimate and last committed
  tick, and no scene payload.

**Falsifier (any one).** The probe does not build on T without the executor feature after one repair cycle;
more than one asupersync package, or any 0.5.0 package, in its graph; any replay differs from its snapshot;
idle CPU above 2% of one core. If it holds, `frob-tui` is not funded and KILL-TUI is recorded as fired with the
measured cause. If the only cause is the toolchain, the upstream change needed in frankentui is named with its
failing fixture, and the pilot may be rerun after it lands. Recommendation recorded: `fund` or `do not fund`.

## Acceptance criteria
- [ ] The probe builds and tests on T with `runtime` and `native-backend` only; `asupersync-executor` is absent from the resolved feature set.
- [ ] `cargo tree -d` shows one asupersync package or none in the graph that includes frankentui.
- [ ] The job pane rendered from the recorded stream equals its four stored snapshots, in 20 of 20 runs.
- [ ] Idle processor use is at most 2% of one core over 60 s, in each of three measurements.
- [ ] `cargo tree` of the probe contains no `fs-mbd`, `fs-contact`, `frob-dyn`, `frob-contact` or kernel crate.
- [ ] The admission record, gate row and funding ADR exist; the pilot record names the falsifier, the ceiling, the fallback and the result.
- [ ] The fallback is demonstrated: the probe's `--ndjson` mode prints the same recorded events as line-delimited JSON with the per-state counts and progress the pane's status line shows; for a stream recorded from a real run, `frob job list --json` (N29a-23) over that run's ledger reports the same per-state counts; for a `synthetic` stream that comparison is marked `not-run: synthetic stream`.
- [ ] The pilot record exists in the register with protocol, falsifier, ceiling, fallback, cost, tool and pin written before the run, and the result after it.
- [ ] 100 of 100 replays reproduce the stored frames, and the burst-delivery replay matches them at the same event indices.
- [ ] The executor-enabled scratch copy shows asupersync 0.5.0 in `cargo tree -d`.
- [ ] A recommendation `fund` or `do not fund` is recorded; no dashboard bead starts on `do not fund`, where the pilot result's verdict is `falsifier-holds` and N32b-06 to N32b-09 are closed `withdrawn` citing the pilot and that result.
- [ ] No manifest of the core workspace depends on frankentui as a result of the pilot; the probe lives outside it.

## Test plan

### Unit tests

`cargo test` in the probe workspace:
- `update_is_pure`: applying the same event sequence twice yields equal models.
- `progress_has_denominator`: a progress event without `total` is rejected by the model, not rendered as a bare count.
- `counts_by_state_sum`: admitted + running + preempted + done + refused + cancelled equals the number of jobs seen.
- `snapshot_job_pane_{1,500,1000,last}` (headless harness).
- `resize_does_not_panic`: sizes from 20 × 5 to 300 × 100.
- `job_pane_replay_100`: 100 byte-identical replays against the stored frames.
- `job_pane_burst_invariance`: seeded burst sizes 1 to 50 give the same frames at the same event indices.
- `executor_brings_0_5_0`: the control copy shows the second asupersync version.

### End-to-end script and logging

`scripts/e2e/suite_tui_pilot.sh`: builds the probe through the offload shim; runs `cargo tree -d` and
`cargo xtask check-deps`; runs the snapshot tests 20 times; starts the pane on a pseudo-terminal and measures
idle CPU; prints the fallback's JSON lines and compares their per-state counts with the pane's status line;
then runs the gate's tier, `e2e_tier <tier> INT-FTUI-01 --mutations` (the four controls below), and logs the
receipt hash the recorder cites (the script records no gate value). It
logs `cmd` events (command, exit code, wall time), `metric` events `asupersync_packages` (threshold ≤ 1),
`snapshot_equal_runs` (threshold 20 of 20) and `idle_cpu_fraction` (threshold 0.02), and on a snapshot mismatch
the first differing cell (row, column, expected, observed) with both buffer dumps. The `summary` names `gates:
[INT-FTUI-01]`.

### Known answers and negative controls

Known answer: the snapshots. Negative controls: enabling `asupersync-executor` in a scratch copy must fail
`check-deps` and show two asupersync packages in `cargo tree -d`; a recorded stream with one event removed must
change at least one snapshot (otherwise the snapshot does not depend on the stream); a pane variant with a busy
redraw loop must fail the idle-CPU threshold. Lanes: 20 runs on one machine; Linux and macOS terminals; debug and
release.

## Considerations
- OPEN-WS-2 (whether `frob-tui` stays in the core workspace or becomes an annex): default core. If this gate
  shows frankentui does not build on T, the remedy is an upstream change in frankentui or the toolchain train,
  with no dashboard until it lands.
- frankentui is large (about 1.15 million lines); its build cost is recorded and the feature keeps it out of
  every default build.
- Logs and snapshots contain job identifiers and agent names from the fixture only; no private-scene data.
- A pane that reads the wall clock into a cell (planted) must break replay equality; it is a registered negative
  control of this gate beside the three above.
- The pilot measures the gate's conditions and nothing about usefulness; usefulness is the owner's call, and the
  ceiling says how little rides on it. No milestone waits on this pilot.
- If the pilot passes, the recorded stream becomes a fixture of the dashboard's snapshot tests.
