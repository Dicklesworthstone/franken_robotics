## Background

`frob-tui` is a terminal dashboard for a person watching a campaign: jobs, races, budgets and gate status. It is
built on frankentui, a sibling terminal-interface library. FACT (read 2026-11-21 at head `5979b92cc576`): version
0.10.0, twenty crates under `frankentui/crates`, about 1.15 million lines, on `nightly-2026-08-31`; an Elm-style
runtime (`Model`, `Cmd`) in `ftui-runtime`; a pane workspace in `ftui-layout`; widgets including `Table`,
`ProgressBar`, `LogViewer` and `StatusLine`; `ftui-harness` supports headless tests with shadow-run comparison
and determinism fixtures. `ftui-runtime` carries an optional exact pin on asupersync 0.5.0 behind the feature
`asupersync-executor` (`crates/ftui-runtime/Cargo.toml:56, :81`).

The dashboard is a Frontier [F] item with a stated ceiling: a convenience for a person watching a campaign; no
claim and no agent workflow depends on it. It issues only read verbs (plus job cancellation under a token with
that scope, after a confirmation) and has no private interface.

**Posture.** Consume, with default features off and `runtime` and `native-backend` on; the executor feature is
forbidden, because it would bring a second asupersync package (0.5.0) into the graph. `frob-tui` reads the
daemon's event stream over the local socket and links no physics crate. If frankentui does not build on the
project's one toolchain T, the remedy is an upstream change in frankentui or a toolchain train; until it lands
the fallback applies, and the crate gets no toolchain of its own.

**Gate INT-FTUI-01** (TARGET; first needed at M3): one asupersync package or none in its graph; the job pane
rendered from a recorded event stream equals its stored snapshot in the headless harness; idle processor use at
most 2% of one core. **The gate is also the pilot**, run on a recorded stream before the crate is funded.
**Kill:** the gate fails, or frankentui cannot be built without its executor (the kill gate KILL-TUI: frankentui
cannot be admitted with one asupersync package, or the snapshot tests cannot be made stable). **Fallback:** no
dashboard; the same events as line-delimited JSON, and `job.list` and `session.show` carry the same numbers.

## Scope

In: a probe crate that builds frankentui with the allowed feature set; one pane (the job pane) rendered from a
recorded stream in the headless harness; the snapshot; the idle-CPU measurement; the gate record and the funding
decision. Out: the full dashboard with its six panes (BD-300); the daemon; any change in frankentui (upstream
work item FD-FTUI-01 would relax the exact 0.5.0 pin and is needed only if the executor is ever wanted).

## Technical approach

1. **Probe crate.** `crates/frob-tui` is created in its minimal form (it is the future home of the dashboard;
   feature `frontier-tui`, off by default). Dependencies: the frankentui crates by path at the pinned revision
   with `default-features = false, features = ["runtime", "native-backend"]`; `frob-core` for envelope types; no
   `frob-fsim`, no kernel, no physics crate.
2. **Graph check.** `cargo tree -d -e normal,build` for the workspace with the feature on must show one
   `asupersync` package or none through frankentui, and `ftui-runtime`'s resolved features must not contain
   `asupersync-executor` (the deny row of `xtask check-deps`). `cargo check` and `cargo test` run on T; a failure
   to build on T is recorded with the first failing crate and decides OPEN-WS-2's branch (below).
3. **Recorded stream.** `tests/fixtures/tui/job_events_01.ndjson`: a real stream recorded from the job protocol
   (one line per event: job admitted, chunk committed with progress `done/total`, estimate updated, preempted,
   resumed, cancelled, completed, refused), at least 2,000 events covering 20 jobs in four size classes. Recorded
   from a real run on `batch-cpu`; if the daemon's stream does not exist yet at pilot time, the fixture is built
   from the M2 job receipts and labelled `synthetic`, and the pilot is repeated on a real stream before BD-300
   closes.
4. **The job pane (the "Queue" pane of the dashboard in its minimal form).** A table: job identifier, agent,
   size class, state, progress with its denominator, wait time, estimate against actual, preemption count; a
   status line with counts by state. Model update is a pure function `update(model, event) -> model`; the view
   is a pure function of the model and the terminal size.
5. **Snapshot test.** In `ftui-harness`, headless, terminal size 120 × 40: feed the recorded stream, render after
   events 1, 500, 1,000 and the last, and compare each rendered buffer (cells with their style attributes) with
   stored snapshots `tests/fixtures/tui/job_pane_<n>.snap`. Equality is exact. The test runs 20 times; any
   difference between runs is a stability failure (one of KILL-TUI's triggers).
6. **Idle CPU.** With the stream ended and the pane displayed in a pseudo-terminal, measure process CPU time over
   60 s of wall time: (user + system CPU seconds) / 60 ≤ 0.02. Measured three times; the maximum is recorded.
7. **Record and decision.** Admission record with the frankentui revision, the receipt hash, the `cargo tree -d`
   output hash, the snapshot hashes, the idle-CPU figures; a gate row. Funding decision (ADR): PASS → BD-300
   proceeds on frankentui; FAIL after one repair cycle, or no build without the executor → KILL-TUI is recorded
   and the fallback is the dashboard's description from then on.

## Acceptance criteria

- [ ] The probe builds and tests on T with `runtime` and `native-backend` only; `asupersync-executor` is absent from the resolved feature set.
- [ ] `cargo tree -d` shows one asupersync package or none in the graph that includes frankentui.
- [ ] The job pane rendered from the recorded stream equals its four stored snapshots, in 20 of 20 runs.
- [ ] Idle processor use is at most 2% of one core over 60 s, in each of three measurements.
- [ ] `cargo tree -p frob-tui` contains no `fs-mbd`, `fs-contact`, `frob-dyn`, `frob-contact` or kernel crate.
- [ ] The admission record, gate row and funding ADR exist; the pilot record names the falsifier, the ceiling, the fallback and the result.
- [ ] The fallback is demonstrated: the same recorded events print as line-delimited JSON through `frob job list --json` style output with the numbers the pane shows.

## Test plan

### Unit tests

`cargo test -p frob-tui --features frontier-tui`:
- `update_is_pure`: applying the same event sequence twice yields equal models.
- `progress_has_denominator`: a progress event without `total` is rejected by the model, not rendered as a bare count.
- `counts_by_state_sum`: admitted + running + preempted + done + refused + cancelled equals the number of jobs seen.
- `snapshot_job_pane_{1,500,1000,last}` (headless harness).
- `resize_does_not_panic`: sizes from 20 × 5 to 300 × 100.

### End-to-end script and logging

`scripts/e2e/suite_tui_pilot.sh`: builds the probe through the offload shim; runs `cargo tree -d` and
`cargo xtask check-deps`; runs the snapshot tests 20 times; starts the pane on a pseudo-terminal and measures
idle CPU; prints the fallback's JSON lines and compares their per-state counts with the pane's status line. It
logs `cmd` events (command, exit code, wall time), `metric` events `asupersync_packages` (threshold ≤ 1),
`snapshot_equal_runs` (threshold 20 of 20) and `idle_cpu_fraction` (threshold 0.02), and on a snapshot mismatch
the first differing cell (row, column, expected, observed) with both buffer dumps. The `summary` names `gates:
[INT-FTUI-01]`.

### Known answers and negative controls

Known answer: the snapshots. Negative controls: enabling `asupersync-executor` in a scratch copy must fail
`check-deps` and show two asupersync packages in `cargo tree -d`; a recorded stream with one event removed must
change at least one snapshot (otherwise the snapshot does not depend on the stream); a pane variant with a busy
redraw loop must fail the idle-CPU threshold. Lanes: 20 runs on one machine; Linux and macOS terminals; debug and
release.

## Considerations

- OPEN-WS-2 (whether `frob-tui` stays in the core workspace or becomes an annex): default core. If this gate
  shows frankentui does not build on T, the remedy is an upstream change in frankentui or the toolchain train,
  with no dashboard until it lands.
- frankentui is large (about 1.15 million lines); its build cost is recorded and the feature keeps it out of
  every default build.
- Logs and snapshots contain job identifiers and agent names from the fixture only; no private-scene data.
