## Background

FrankenRobotics has a browser viewer: an ordinary Three.js page that replays recorded episodes, with a
self-contained HTML export that is this project's own build step. franken_threed is a sibling that offers two
things. FACT (read 2026-11-21 at head `bf7abe16367e`, from `franken_threed/README.md`): four crates (`f3d-core`
10,688 lines, `f3d-math` 19,100, `f3d-graph` 7,507, `f3d-runtime` 31,564); Three.js r186 is pinned; an ingest
command routes an ordinary application's WebGPU renderer to a new backend for an admitted feature subset; pixel
parity holds for ten scenes on a software rasterizer; no hardware run and no speedup have been measured;
single-file packaging is not built. It pins asupersync 0.5.0 and `serde_json = "=1.0.151"`.

**Use.** Its `DEPENDENCY_ADMISSION.md` discipline is already adopted by this project. The viewer is an ordinary
Three.js r186 page, so it can later be passed through the ingest command. **Posture:** Pattern now; Subprocess
when the viewer's feature subset is admitted there; never a Cargo dependency (it would bring asupersync 0.5.0 and
a conflicting exact `serde_json` pin into the graph).

This is a Frontier [F] item. **Ceiling:** the route changes rendering cost only, and rendering is outside every
claim of the ten-fold test. **Gate INT-F3D-01** (TARGET; first needed at M3), which is also the pilot: ten
reference frames of the replay page built through the route match the plain bundle within 1/255 per channel on
at least 99.9% of pixels, and an unadmitted feature fails explicitly. **Fallback:** the plain bundle, which is
always built.

## Scope

In: a build-script step under `viewer/` that passes the replay page through franken_threed's ingest command as a
subprocess; the ten reference frames; the pixel comparison; the unadmitted-feature test; the record and funding
decision. Out: the viewer and its overlays (BD-300); the HTML export; any change in franken_threed (FD-F3D-01
covers its `serde_json` pin).

## Technical approach

1. **The route as a subprocess (DESIGN).** `viewer/build/route_f3d.sh <bundle-dir> <out-dir>` invokes the ingest
   command of a franken_threed build at the pinned revision (built in its own workspace, on its own lockfile, by
   its own repository's rules; nothing of it enters a workspace of this repository). Inputs: the plain bundle's
   entry module and its renderer construction. Output: a bundle whose renderer is routed to the sibling's
   backend. The script records the franken_threed revision, the command line and the output hash, and exits
   non-zero with the sibling's message when the page uses a feature outside the admitted subset.
2. **Reference scene and frames.** One recorded episode of the reference quadruped on the flat-ground fixture
   (public assets only), replayed with a scripted camera: ten frames at fixed episode times (t = 0, 0.2, …,
   1.8 s), canvas 1280 × 720, device pixel ratio 1, antialiasing off, a fixed clear colour, no post-processing,
   no time-dependent shader input other than the episode time. The frame list and settings are a fixture file
   (`viewer/tests/frames_01.json`).
3. **Rendering both bundles.** A pinned headless browser with a software rasterizer renders each of the ten
   frames from the plain bundle and from the routed bundle and writes PNG files. The browser is a development-time
   tool (Oracle posture): its version is recorded in the admission record and it is never in a production
   dependency graph. If the routed backend needs WebGPU and the software rasterizer cannot provide it, the pilot
   records that fact as its result (the route cannot be compared on this machine) and the gate is `not run`, with
   the fallback in force.
4. **Comparison.** For each frame, decode both PNGs to 8-bit RGBA. A pixel matches if max over channels of
   abs(a − b) ≤ 1 (that is 1/255). The frame passes if matching pixels / total pixels ≥ 0.999 (at 1280 × 720,
   at most 921 differing pixels of 921,600). All ten frames must pass. The comparison tool is a small Rust test
   helper in the viewer's test directory using the standard library and the project's own PNG reader, or the
   headless harness's built-in reader; it reports the worst frame, its match fraction and the bounding box of
   differing pixels.
5. **Unadmitted feature.** A variant page that uses one feature outside the admitted subset (chosen from the
   sibling's own status table at the pin; for example a post-processing pass) is passed through the route. The
   route must fail explicitly: non-zero exit, a message naming the feature, and no output bundle. A silent
   fallback to another renderer would count as a failure of the gate.
6. **Record and decision.** Admission record (revision, receipt hash, browser version, the ten match fractions,
   the unadmitted-feature message); gate row; funding ADR: PASS → the viewer build offers the routed bundle as an
   option beside the plain one (never instead of it); FAIL or `not run` → the plain bundle only, and the item is
   revisited when franken_threed reports a hardware run.

No evidence of any physical claim is produced; rendering is a view.

## Acceptance criteria

- [ ] The route runs as a subprocess; `xtask check-deps` confirms no `f3d-*` package in any workspace that builds a `frob` binary.
- [ ] All ten reference frames match within 1/255 per channel on at least 99.9% of pixels, or the gate is recorded `fail` or `not run` with the reason.
- [ ] The unadmitted-feature page fails explicitly with the feature named and produces no bundle.
- [ ] The plain bundle is built in every case and is byte-identical whether or not the route ran.
- [ ] The admission record, gate row and funding ADR exist; the pilot record names the falsifier, the ceiling, the fallback and the result.
- [ ] The frames, both sets of PNGs and the comparison report are stored as artifacts of the run with their hashes.

## Test plan

### Unit tests

Viewer test helper (`cargo test -p frob-conformance viewer_compare`):
- `identical_images_match_fraction_one`.
- `one_channel_off_by_one_still_matches`: every pixel differs by 1 in red → fraction 1.0.
- `off_by_two_fails_pixel`: a 30 × 31 block (930 pixels) differing by 2 in one channel at 1280 × 720 gives fraction 0.99899… and the frame fails; a 30 × 30 block (900 pixels) gives 0.99902… and passes.
- `size_mismatch_is_error`.
- `bounding_box_reported`.

### End-to-end script and logging

`scripts/e2e/suite_f3d_pilot.sh`: builds the plain bundle with `frob telemetry export-html` on the fixture
episode; runs the route; renders both bundles; compares; runs the unadmitted-feature variant. It logs `cmd`
events (each command, exit code, wall time), per frame a `metric` event `match_fraction` (threshold 0.999) with
the count of differing pixels, an `assert` event for the explicit failure with the matched message, the hashes
of both bundles, and on failure the worst frame's index and the paths of the two PNGs and the difference image.
The `summary` names `gates: [INT-F3D-01]` and the outcome (`pass`, `fail` or `not-run`).

### Known answers and negative controls

Known answers: the helper's block cases (900 differing pixels pass, 930 fail, at 1280 × 720). Negative controls:
a routed bundle with the clear colour changed by 2/255 must fail every frame; a frame list with one episode time
shifted by one step must fail (so the comparison is sensitive to content); the unadmitted-feature page. Lanes:
the comparison twice on one machine with identical fractions; the software rasterizer makes frames reproducible
across runs, and cross-machine differences are recorded.

## Considerations

- RISK-19: the viewer drifts outside franken_threed's admitted subset. Leading indicator: this gate. Mitigation:
  plain Three.js is the fallback and is always built.
- franken_threed does not yet package a single self-contained page; the viewer's self-contained HTML export
  remains this project's own build step whatever this pilot finds.
- An exact-pin conflict (`serde_json = "=1.0.151"` there, 1.0.154 in this project's graph) is one more reason the
  posture is Subprocess; the upstream work item FD-F3D-01 relaxes the pin, and its switch-over rule is to re-run
  this gate.
- The headless browser is a foreign tool admitted for development and test only.
