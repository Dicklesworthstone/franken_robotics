## Background

The MCP server of FrankenRobotics, `frob-mcp`, is built on fastmcp_rust, a sibling MCP framework. It registers
tools generated from the verb registry and serves catalogs, stills, reports and schemas as resources. Its
posture is Consume: `surface/frob-mcp` is a member of the core workspace that links `frob-verbs` and runs verbs in
process, once the upstream work item FD-FMCP-01 has brought fastmcp_rust onto the project's one toolchain T. The
admission gate is INT-FMCP-01 (`frob-mcp` builds in the core graph on T with exactly one asupersync package,
lists the tools generated from the verb registry, and passes the MCP protocol smoke test over stdio and HTTP).
The fallback is the kill gate KILL-MCP: first `frob-mcp` as its own workspace talking to the daemon over a local
socket in newline-delimited JSON, then the CLI alone, which is complete on its own.

The design of the server leans on specific facts about the library. FACT (read 2026-11-21 at head
`117388bcc169`): workspace version 0.13.0; the facade package is `fastmcp-rust`, with `fastmcp-core`,
`-protocol`, `-transport`, `-server`, `-client`, `-macros`, `-console` and `-cli`, about 1.23 million lines;
`ServerBuilder` offers `new(name, version)`, `tool`, `resource`, `resource_template`, `prompt`,
`task_supervisor`, `final_tasks` and `build` (`crates/fastmcp-server/src/builder.rs`); the task methods
`tasks/get`, `tasks/update` and `tasks/cancel` are served by default (`README.md`); it pins asupersync `=0.6.2`
and declares `rust-version = "1.100"`.

The suite chapter's rule: a sibling fact that a gate depends on is re-read by that gate's admission test and is
never copied from the plan into a record. fastmcp_rust is about to be changed by this program itself (its
toolchain file and declared `rust-version`, under FD-FMCP-01; its asupersync pin, under FD-ASUP-01), so the
facts must be re-read after those changes, at the revision that is actually pinned: both items are dependencies
of this bead, and the probe cannot build on T before FD-FMCP-01 has landed.

## Scope

In: a probe that compiles against the library at the pinned revision and asserts each fact by use; a record of
the facts for the INT-FMCP-01 admission. Out: the server (`surface/frob-mcp`, BD-023); the upstream changes
(FD-FMCP-01, FD-ASUP-01); the protocol smoke test (BD-023).

## Technical approach

1. **Probe workspace (DESIGN).** `tests/admission/fastmcp_facts/`: a small package with a path dependency on the
   `fastmcp-rust` facade at the `git_rev` of the `FD-FMCP` row of `franken-stack.lock` (N33a-02), built on T with
   the root patch entry for asupersync. It is an admission probe, not a member of the core workspace, so that it
   can be built before `frob-mcp` exists and after every pin move. Because it sits under the repository root, its
   manifest carries its own empty `[workspace]` table (otherwise Cargo attaches it to the core workspace and
   refuses it as a non-member), repeats the asupersync patch entry the core root carries, commits its own
   `Cargo.lock`, and builds into its own target directory; this is the probe-workspace rule of the admission
   harness (N33c-01).
2. **Facts asserted by compilation (each a tiny function that would fail to compile if the fact were false).**
   - `ServerBuilder::new(name, version)` exists and returns a builder.
   - The builder has methods named `tool`, `resource`, `resource_template`, `prompt`, `task_supervisor`,
     `final_tasks` and `build`; the probe calls each with the simplest valid argument.
   - The facade re-exports what the probe needs without reaching into sub-crates.
3. **Facts asserted at run time.**
   - A server built with no task configuration answers `tasks/get`, `tasks/update` and `tasks/cancel` over an
     in-memory or stdio transport: each returns a protocol-valid response (a result or a typed "unknown task"
     error), not "method not found". The probe records which.
   - An unknown tool name yields the library's invalid-parameters error before any handler runs (the design maps
     this case specially on the MCP surface).
4. **Facts read from manifests and the lockfile.**
   - Workspace version (expected 0.13.0 at the starting state).
   - The asupersync requirement (expected `=0.6.2` at the starting state; after FD-ASUP-01, the one published
     version every sibling pins).
   - The declared `rust-version` (expected `1.100` at the starting state; after FD-FMCP-01, a value T
     satisfies).
   - The `serde_json` requirement and enabled features (expected `=1.0.154` with `arbitrary_precision`), because
     the JSON library's unified feature set in every binary that links the server follows from it.
   - Whether the library forbids unsafe code at its crate roots (the reason the server may be an ordinary core
     member and not an annex).
   - The BLAKE3 of the licence file, whose rider the supply-chain admission record reproduces (a changed hash is
     a changed fact, listed for review; it does not set exit 3).
5. **Record.** `receipts/facts/fastmcp-<rev>.json` (canonical JSON): each fact with `expected_at_planning`,
   `observed`, `how` (`compiled`, `ran`, `read`) and `changed: bool`. A changed fact that the server's design
   depends on (a renamed builder method; task methods no longer served by default) sets exit status 3 and is
   listed first. The INT-FMCP-01 admission record, written by BD-023 (which depends on this bead), cites the
   file's hash and lists its changed facts; this bead delivers the file and its hash.
6. **No write to the sibling.** The probe builds with its own target directory and never runs a command inside
   the fastmcp_rust checkout.

Determinism: exact for a fixed revision. No evidence class.

## Acceptance criteria

- [ ] The probe builds on T against the pinned revision with one asupersync package in its graph.
- [ ] Each builder method of the list compiles in use; a missing method is reported by name, not as a bare build failure.
- [ ] The three task methods are answered by a default-built server; the response kinds are recorded.
- [ ] The manifest facts (version, asupersync requirement, `rust-version`, `serde_json` requirement and features, unsafe policy) are recorded with planned and observed values.
- [ ] The record `receipts/facts/fastmcp-<rev>.json` exists in canonical JSON with every fact's four fields, changed facts first; its BLAKE3 is printed in the script's `summary` for BD-023's INT-FMCP-01 admission record to cite (the citation is BD-023's acceptance, not this bead's).
- [ ] The fastmcp_rust checkout is unmodified by the probe.

## Test plan

### Unit tests

In the probe package (`cargo test` in `tests/admission/fastmcp_facts/`, real library, no mock):
- `builder_surface_compiles` (the compile-time facts; one test per method so a failure names it).
- `default_server_serves_task_methods`: three requests over an in-process transport; none returns "method not found".
- `unknown_tool_is_invalid_params`.
- `manifest_facts_read`: parses the sibling manifest and lockfile and compares with the expected table.

A script test `facts_record_flags_change`: with a `synthetic` expected table in which one method name is altered,
the record marks it changed and the exit status is 3.

### End-to-end script and logging

`scripts/e2e/suite_fastmcp_facts.sh`: sources the STD-E2E helper and writes
`target/e2e-logs/suite_fastmcp_facts/<utc>.ndjson` with a transcript; builds and runs the probe through the
offload shim, writes the record, and logs a `cmd` event per command (exact command, exit code, wall time), one
`assert` event per fact (name, expected, observed, how), a `metric` event `asupersync_packages` (threshold
exactly 1), the pinned `git_rev` and the record's hash, on a changed fact the file and line where it was read
or the compile error's first line, and a `summary` with facts confirmed and facts changed and an empty `gates`
list (STD-E2E's `gates[{id, measured_ok, controls_caught}]` names gates a script measures; this one measures none,
and the INT-FMCP-01 record that cites the facts is BD-023's). The script records `git -C <fastmcp_rust> status --porcelain` and the
checkout's tree hash before the first step and after the last, and logs their equality as an `assert` (the
checkout may already be dirty; the probe must not change it).

### Known answers and negative controls

Known answers at the starting state (the record's `expected_at_planning` column): version 0.13.0; asupersync
`=0.6.2`; `rust-version = "1.100"`; the seven builder methods; three task methods served. At the pinned revision
after the two upstream items: the asupersync requirement equals the one published version of FD-ASUP-01 and the
declared `rust-version` is satisfied by T (both recorded `changed: true` as expected changes, which do not set
exit 3); the builder methods and task methods unchanged. Negative controls: the altered expected table (must be
flagged); a probe built with a second asupersync version forced by a planted dependency (must fail the
one-package metric); the probe built against the starting revision `117388bcc169` on FrankenSim's older nightly
must fail on the declared minimum version, which is recorded as the reason the upstream item exists, and
`--ignore-rust-version` is never used to hide it. Lanes: both machines; after each pin move.

## Considerations

- The library's own documentation says support for the newest protocol revision is under implementation and
  provisional; the task extension is called experimental. The probe records behaviour, and the server's design
  decides what to rely on.
- KILL-MCP fires only if INT-FMCP-01 cannot pass within the M0 budget after FD-FMCP-01 and FD-ASUP-01 have been
  attempted; this probe is the first place a blocking change in the library would show.
- fastmcp_rust's licence text carries a rider that is reproduced in the admission record of the supply-chain
  rules; the probe records the licence file's hash so that a change is noticed.
