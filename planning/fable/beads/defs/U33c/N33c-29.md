## Background

The suite chapter maintains five invariants, each checked by one of the six checks of the workspace tool `xtask`.
This bead carries the two that `check-deps` owns.

- **INV-SUITE-01** No crate other than `frob-fsim` and the bedrock-direct users names a FrankenSim type
  (`check-deps`).
- **INV-SUITE-02** Every binary links exactly one asupersync package (`check-deps`).

Why the first matters: FrankenSim's API moves daily. The airlock crate `frob-fsim` is the only crate that may
name types from FrankenSim's volatile crates, so an upstream API change costs one crate. A short bedrock-direct
list is exempt because those crates' types are the vocabulary of the mathematics: `fs-ga`, `fs-math`, `fs-qty`
(named only through `frob_core::qty`), `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`,
`fs-ad`. Everything else goes through the airlock. Why the second matters: asupersync is the structured
concurrency runtime; two versions in one binary mean two cancellation contexts that do not interoperate, and the
suite has three siblings that still pin 0.5.0 beside the 0.6.2 the consumed siblings resolve.

An invariant enforced by a tool needs a test of the tool: a planted violation that the check must catch (a gate
that nothing can fail validates nothing), and a property test that the rule is the rule stated, over generated
dependency graphs.

## Scope

In: the two rule definitions as rows of the `check-deps` table; planted violations; property tests on generated
graphs; the registration of the plants in the negative-control registry. Out: the `check-deps` engine and the
layer rules (BD-003); the deny rows for forbidden siblings (N33c-09); the `fs-qty` confinement (N33c-03); the
gate INT-ASUP-01 and the upstream alignment FD-ASUP-01 (BD-008).

## Technical approach

1. **INV-SUITE-01 as a manifest rule (DESIGN).** Let V be the set of FrankenSim packages (every package whose
   manifest path lies under the FrankenSim checkout) minus the bedrock-direct list B. For every package of this
   repository, in every workspace: a direct dependency edge (normal, build or dev) to a member of V is allowed
   only from `frob-fsim` (and from the manifest-only package of the `worker/` workspace, which re-targets
   `frob-fsim`). An edge to a member of B is allowed from any crate, except `fs-qty`, which is allowed only from
   `frob-core` and `frob-fsim`. Since Rust code cannot name a type of a crate it has no edge to, except through a
   re-export, the manifest rule covers direct naming.
2. **Closing the re-export hole.** `frob-fsim`'s public API must not re-export a volatile type. A test in
   `frob-fsim` (`tests/public_api.rs`) walks the crate's public items with rustdoc's JSON output for the pinned
   toolchain and fails if any public signature mentions a path rooted in a member of V. This is a test of the
   airlock, registered with the invariant; `xtask` itself gains no seventh check.
3. **Feature groups.** The same table lists, per airlock feature group (`referee`, `geometry`, `ledger`,
   `optimize`, `stats`, `spectral`, `actuation`, `structure`, `multiphysics`, `harness`), the crates allowed to
   enable it; `check-deps` fails a crate that enables a group it is not listed for. `harness` is dev only;
   `multiphysics` is off in every default build.
4. **INV-SUITE-02 as a resolution rule.** For every binary target of every workspace (`frob`, `frobd`,
   `frob-mcp`, `frob-verify`, `frob-fsim-worker`, `frob-tui`, `xtask`, the annex binaries), compute the set of
   resolved packages named `asupersync` in the binary's dependency closure, with every optional feature group
   enabled and for each target platform in use. The set must have exactly one element; `frob-verify` and
   `frob-cert` must have zero (the independent auditor depends on nothing). Two packages with the same version
   and different sources (registry and path) count as two.
5. **Failure output.** Rule name, the binary or crate, the offending package identifiers with sources, and one
   dependency path for each, so that the sibling that brought the second package is named.
6. **Registration.** Both plants below are registered in the negative-control registry with the invariant they
   guard, and the second-asupersync plant is the one the workspace gate GATE-WS-01 lists among its seven plants
   (each caught by the check that owns it and by no other).

## Acceptance criteria

- [ ] Plant A (a crate above the airlock, for example `frob-analyze`, gains a path dependency on `fs-mbd`): `cargo xtask check-deps` fails, names INV-SUITE-01, the crate and the edge.
- [ ] Plant B (`frob-fsim` re-exports `fs_mbd::articulated::Tree` publicly): the public-API test fails and names the item.
- [ ] Plant C (a second asupersync package is brought into `frob`'s closure by a path dependency that pins 0.5.0): `check-deps` fails, names INV-SUITE-02, both packages and the path to each.
- [ ] Plant D (the same version from two sources: registry and path): `check-deps` fails.
- [ ] Plant E (a crate not listed for the group enables `frob-fsim/multiphysics`): `check-deps` fails.
- [ ] The clean tree passes; each plant is caught by `check-deps` (or the registered airlock test for plant B) and by no other check.
- [ ] `frob-verify`'s closure contains zero asupersync packages.

## Test plan

### Unit tests

`cargo test -p xtask check_deps_inv_suite`:
- `inv_suite_01_planted_volatile_edge` (plant A), `inv_suite_01_bedrock_allowed` (a crate depending on `fs-ga` passes), `inv_suite_01_fs_qty_special_case` (a crate depending on `fs-qty` directly fails; through `frob-core` passes).
- `inv_suite_01_feature_group_allowlist` (plant E).
- `inv_suite_02_two_versions` (plant C), `inv_suite_02_same_version_two_sources` (plant D), `inv_suite_02_auditor_has_none`.
- Property test for INV-SUITE-01: for 10³ generated workspace graphs (`synthetic`: random DAGs over package names drawn from this repository's crates, B and V), the rule accepts exactly the graphs in which every edge into V starts at `frob-fsim`; compared against a three-line reference predicate.
- Property test for INV-SUITE-02: for 10³ generated closures with zero to three asupersync packages, the rule accepts exactly those with one (or zero for the auditor).

`cargo test -p frob-fsim --test public_api`: plant B and the clean API.

### End-to-end script and logging

`scripts/e2e/suite_deps_rules.sh`: for each plant A to E copies the tree to scratch, applies the edit, runs the
check through the real `cargo xtask check-deps` (and the public-API test for B), and asserts the exit status and
the invariant's name in the output; then runs the clean tree. It logs a `cmd` and an `assert` event per plant
(invariant expected, invariant reported, exit code, the path printed), a `metric` event
`asupersync_packages_per_binary` for every binary (threshold exactly 1; 0 for `frob-verify`), and a `summary`
with plants caught of plants planted.

### Known answers and negative controls

Known answers: `cargo tree -d` on the clean tree lists no duplicate `asupersync`; `cargo tree -p frob-cert`
prints one line. The five plants are the negative controls. A control on the check itself: a variant of the rule
that inspects only the core workspace must miss plant C when it is planted in the `apps/` workspace, and the real
rule must catch it (the binaries are linked in `apps/`). Lanes: both machines (the CUDA annex resolves on `trj`,
the Metal annex on the Mac); with every feature group enabled and with defaults.

## Considerations

- OPEN-SUITE-1 (which asupersync version the whole graph resolves to): default, the one published version
  FD-ASUP-01 aligns the siblings on; until it lands, whatever FrankenSim's pinned commit builds with (0.6.2 by
  path). INV-SUITE-02 is about package identity, so it holds under either answer.
- OPEN-SUITE-6: if INT-ASUP-01 fails after FD-ASUP-01 and a fallback splits the graph, a surface that still
  brings a second package moves to its own workspace (for `frob-mcp`, the first fallback of KILL-MCP);
  INV-SUITE-02 then holds per workspace binary, which is how the rule is written.
- Honesty about the closure: path dependencies on FrankenSim bring third-party crates such as `nalgebra` and
  `rayon` transitively; "Franken-only" describes direct edges, and INV-SUITE-01 is likewise about direct naming.
- RISK-01 (FrankenSim API churn) is what INV-SUITE-01 contains; RISK-03 (two asupersync versions) is what
  INV-SUITE-02 detects.
