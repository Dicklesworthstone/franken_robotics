## Background

The suite chapter maintains five invariants, each checked by one of the six checks of the workspace tool `xtask`.
This bead carries the two that `check-deps` owns.

- **INV-SUITE-01** No crate other than `frob-fsim` and the bedrock-direct users names a FrankenSim type
  (`check-deps`).
- **INV-SUITE-02** Every binary links exactly one asupersync package (`check-deps`).

Why the first matters: FrankenSim's API moves daily. The airlock crate `frob-fsim` is the only crate that may
name types from FrankenSim's volatile crates, so an upstream API change costs one crate. A short bedrock-direct
list is exempt because those crates' types are the vocabulary of the mathematics: `fs-ga`, `fs-math`, `fs-qty`
(named only through `frob_core::qty`), `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`,
`fs-ad`. Everything else goes through the airlock. Why the second matters: asupersync is the structured
concurrency runtime; two versions in one binary mean two cancellation contexts that do not interoperate, and the
suite has three siblings that still pin 0.5.0 beside the 0.6.2 the consumed siblings resolve.

An invariant enforced by a tool needs a test of the tool: a planted violation that the check must catch (a gate
that nothing can fail validates nothing), and a property test that the rule is the rule stated, over generated
dependency graphs.

## Scope

In:
- the scope of INV-SUITE-01's volatile-edge rule: its exceptions (the manifest-only package of `worker/`, the
  standalone workspaces that are skipped and printed) and the finding `fsim.standalone-edge`, added to the rule
  `fsim.volatile-edge` whose code and identifier are BD-003's rule 1 (DESIGN: one definition; this bead had
  drafted the same rule a second time); and the test that closes the re-export hole in `frob-fsim`;
- the invariant battery of both invariants: plants A to F run end to end, the property tests on generated
  graphs, the control on the check itself, and the registration of the plants in the negative-control
  registry.

Out, with the bead that has it:
- The definition of INV-SUITE-02's rule (the per-binary closure walk, the finding `asup.duplicate`, the count
  required of each binary, the report format) and its single-case unit tests: N34-03. This bead tests that rule
  on plants and generated closures and restates only what a test needs to assert.
- The enforcement of the airlock feature groups (`fsim.group-not-allowed`): N34-03, reading the feature records
  of N33a-11 and N33b-09. Plant E here tests it.
- The `check-deps` engine and the layer rules (BD-003); the deny rows for forbidden siblings and asupersync
  0.5.0 (N33c-09); the `fs-qty` confinement (N33c-03); the gate INT-ASUP-01 (BD-008, which runs these rules and
  depends on this bead) and the upstream alignment (FD-ASUP-01).

## Technical approach

1. **INV-SUITE-01 as a manifest rule (DESIGN).** Let V be the set of FrankenSim packages (every package whose
   manifest path lies under the FrankenSim checkout) minus the bedrock-direct list B. For every package of this
   repository, in every workspace: a direct dependency edge (normal, build or dev) to a member of V is allowed
   only from `frob-fsim` (and, the exception this bead adds to BD-003's `fsim.volatile-edge`, from the
   manifest-only package of the `worker/` workspace, which re-targets `frob-fsim`). An edge to a member of B is
   allowed from any crate, except `fs-qty`, which is allowed only from `frob-core` and `frob-fsim` (BD-003's
   `L-2.fs-qty-direct`). Since Rust code cannot name a type of a crate it has no edge to, except through a
   re-export, the manifest rule covers direct naming. The rule ranges over the seven workspaces of the
   repository. Standalone workspaces that build no shipped binary (admission probes under `tests/admission/`,
   N33c-01, such as the `fs-qty` and `fs-la` probes, which must name FrankenSim packages to test them; pilots
   under `tools/pilots/`; oracle workers under `tools/oracle/`) are outside it. `check-deps` prints each one it
   skips with its path and the reason `standalone`, so the report shows what the rule does not cover, and an
   edge from a package of the seven into a package of a standalone workspace is itself a finding
   (`fsim.standalone-edge`), so nothing in a shipped graph reaches FrankenSim through a probe.
2. **Closing the re-export hole.** `frob-fsim`'s public API must not re-export a volatile type. A test in
   `frob-fsim` (`tests/public_api.rs`) walks the crate's public items with rustdoc's JSON output for the pinned
   toolchain and fails if any public signature mentions a path rooted in a member of V. This is a test of the
   airlock, registered with the invariant; `xtask` itself gains no seventh check.
3. **Feature groups (rule in N34-03; tested here).** The ten airlock feature groups (`referee`, `geometry`,
   `ledger`, `optimize`, `stats`, `spectral`, `actuation`, `structure`, `multiphysics`, `harness`) each have a
   list of crates allowed to enable them, kept as feature records in `crates/frob-fsim/contract.toml`;
   `check-deps` fails a crate that enables a group it is not listed for (finding `fsim.group-not-allowed`).
   `harness` is dev only; `multiphysics` is off in every default build. This bead plants one violation (plant E)
   and defines nothing of the rule.
4. **INV-SUITE-02 (rule in N34-03; tested here).** What the tests below assert of that rule: for every binary
   target of every workspace (`frob`, `frobd`, `frob-mcp`, `frob-verify`, `frob-fsim-worker`, `frob-tui`,
   `xtask`, the annex binaries and the device-enabled `frob` and `frobd` of `apps/`), the set of resolved
   packages named `asupersync` in the binary's dependency closure, with every optional feature group enabled
   and for each target platform in use, has at most one element; exactly one for a binary that links the
   runtime; zero for `frob-verify` and `frob-cert` (the independent auditor depends on nothing). Two packages
   with the same version and different sources (registry and path) count as two.
5. **Failure output of the volatile-edge rule.** The finding line follows the report format of the check
   (`frob.xtask.report/1`, BD-003): the rule identifier `fsim.volatile-edge`, the invariant INV-SUITE-01, the
   crate, the offending package with its source, and the edge; the same edge raises no `L-4` finding (BD-003). The tests of INV-SUITE-02 assert that the line of `asup.duplicate`
   names the invariant, both packages with their sources and one dependency path for each, so that the sibling
   that brought the second package is named.
6. **Registration.** Every plant below (A to F) is registered in the negative-control registry with the
   invariant it guards, and the second-asupersync plant is the one the workspace gate GATE-WS-01 lists among its seven plants
   (each caught by the check that owns it and by no other).

## Acceptance criteria

- [ ] Plant A (a crate above the airlock, for example `frob-analyze`, gains a path dependency on `fs-mbd`): `cargo xtask check-deps` fails, names INV-SUITE-01, the crate and the edge.
- [ ] Plant B (`frob-fsim` re-exports `fs_mbd::articulated::Tree` publicly): the public-API test fails and names the item.
- [ ] Plant C (a second asupersync package is brought into `frob`'s closure by a dummy path dependency of `frob-verbs` that pins 0.5.0; this is plant 3 of GATE-WS-01): `check-deps` fails with `asup.duplicate`, names INV-SUITE-02, both packages and the path to each. The deny row `asup.v0_5_0` of N33c-09 fires on the same plant, in the same check.
- [ ] Plant D (the same version from two sources: registry and path): `check-deps` fails.
- [ ] Plant E (a crate not listed for the group enables `frob-fsim/multiphysics`): `check-deps` fails.
- [ ] The clean tree passes; each plant is caught by `check-deps` (or the registered airlock test for plant B) and by no other check.
- [ ] `frob-verify`'s closure contains zero asupersync packages.
- [ ] Standalone probe, pilot and oracle workspaces are printed as skipped with their paths; plant F (`frob-verbs` gains a path dependency on the `fs-la` admission probe package) fails with `fsim.standalone-edge`.

## Test plan

### Unit tests

`cargo test -p xtask check_deps_inv_suite`:
- `inv_suite_01_planted_volatile_edge` (plant A), `inv_suite_01_bedrock_allowed` (a crate depending on `fs-ga` passes), `inv_suite_01_fs_qty_special_case` (a crate depending on `fs-qty` directly fails; through `frob-core` passes).
- `inv_suite_01_probe_workspaces_skipped`: a probe under `tests/admission/` with an edge to `fs-la` is listed as skipped, not as a finding; `inv_suite_01_standalone_edge_fails` (plant F).
- The single-case unit tests of the two rules defined in N34-03 are that bead's (`group_allow_list` for plant E; `second_asupersync_by_path_fails` for plant C, `same_version_two_sources_fails` for plant D, `frob_verify_links_none` for the auditor). They were drafted here under the names `inv_suite_01_feature_group_allowlist`, `inv_suite_02_two_versions`, `inv_suite_02_same_version_two_sources` and `inv_suite_02_auditor_has_none`; one copy remains, there. This bead runs plants C, D and E end to end and adds the property tests.
- Property test for INV-SUITE-01: for 10³ generated workspace graphs (`synthetic`: random DAGs over package names drawn from this repository's crates, B and V), the rule accepts exactly the graphs in which every edge into V starts at `frob-fsim`; compared against a three-line reference predicate.
- Property test for INV-SUITE-02: for 10³ generated closures with zero to three asupersync packages, the rule of N34-03 raises `asup.duplicate` exactly for those with two or three; for a closure marked as the auditor's it accepts exactly those with zero; a closure with none is reported `none` without a finding. (The draft said "accepts exactly those with one"; the count rule of N34-03, DESIGN, treats a binary that does not link the runtime as `none`, not as a violation.)

`cargo test -p frob-fsim --test public_api`: plant B and the clean API.

### End-to-end script and logging

`scripts/e2e/suite_deps_rules.sh` (created by N33c-09 with its logging contract; this bead adds its steps): for
each plant A to F copies the tree to scratch, applies the edit, runs the
check through the real `cargo xtask check-deps` (and the public-API test for B), and asserts the exit status and
the invariant's name in the output; then runs the clean tree. It logs a `cmd` and an `assert` event per plant
(invariant expected, invariant reported, exit code, the path printed), a `metric` event
`asupersync_packages_per_binary` for every binary (threshold: at most 1, and exactly 1 for a binary that links
the runtime; 0 for `frob-verify`), and a `summary` with plants caught of plants planted. The script is shared
with N33c-09 and N33c-38, which add their own plants to it.

### Known answers and negative controls

Known answers: `cargo tree -d` on the clean tree lists no duplicate `asupersync`; `cargo tree -p frob-cert`
prints one line. The six plants are the negative controls. A control on the check itself: a variant of the rule
that inspects only the core workspace must miss plant C when it is planted in the `apps/` workspace, and the real
rule must catch it (the binaries are linked in `apps/`). Lanes: both machines (the CUDA annex resolves on `trj`,
the Metal annex on the Mac); with every feature group enabled and with defaults.

## Considerations

- OPEN-SUITE-1 (which asupersync version the whole graph resolves to): default, the one published version
  FD-ASUP-01 aligns the siblings on; until it lands, whatever FrankenSim's pinned commit builds with (0.6.2 by
  path). INV-SUITE-02 is about package identity, so it holds under either answer.
- OPEN-SUITE-6: if INT-ASUP-01 fails after FD-ASUP-01 and a fallback splits the graph, a surface that still
  brings a second package moves to its own workspace (for `frob-mcp`, the first fallback of KILL-MCP);
  INV-SUITE-02 then holds per workspace binary, which is how the rule is written.
- Honesty about the closure: path dependencies on FrankenSim bring third-party crates such as `nalgebra` and
  `rayon` transitively; "Franken-only" describes direct edges, and INV-SUITE-01 is likewise about direct naming.
- RISK-01 (FrankenSim API churn) is what INV-SUITE-01 contains; RISK-03 (two asupersync versions) is what
  INV-SUITE-02 detects.
