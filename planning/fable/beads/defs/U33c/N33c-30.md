## Background

Two of the suite chapter's five invariants are owned by `xtask check-stack`, the check that compares the stack
lock with lockfiles, toolchain files and sibling heads and writes the resolution receipt.

- **INV-SUITE-03** Every recorded gate result cites a resolution receipt, and no PASS is recorded on a dirty
  sibling tree (`check-stack`).
- **INV-SUITE-04** No sibling checkout is ever modified or moved by this project's tooling (`check-stack` writes
  nothing outside this repository, and its test runs it against a copy it cannot write to). An upstream change
  is made by an agent working in the sibling's repository under that repository's rules, never by a tool of this
  one.

Why the first: a pin is a statement of intent and what was built is a different fact; the two have already
diverged inside the suite (a stale constellation lock; checkouts with hundreds of modified paths). A gate result
without a receipt cannot be compared with another result as "the same stack", and a PASS measured on bytes that
no commit names cannot be reproduced. Why the second: the siblings are shared repositories with their own rules
and other agents at work; a sibling's newer clean head is never rolled back locally, and an off-pin sibling is
classified as a fast-forward or a divergence before any remedy is proposed. A tool that "helpfully" checks out
the pinned commit would destroy someone's working tree.

## Scope
In: the two invariants as checked conditions; planted violations; the test against sibling copies that cannot be
written; a syscall-level confirmation that the check opens nothing for writing outside the repository.
Out: the `check-stack` subcommand shell (BD-004), its comparison rules and dirty-tree guard (N33a-05) and the
receipt writer (N33a-04), which these tests exercise and depend on; the one-toolchain conditions (N33c-08); the
evidence-type rule about results across receipts (N33c-31).

## Technical approach

1. **INV-SUITE-03, the conditions `check-stack` evaluates over the records (DESIGN).** Two receipts are in
   play and are kept apart: a part of `registries/gates.toml` (schema `frob.gates/1`, N40-01) names in its
   `receipt` field the **harness receipt**, the hash-named output file of the run; that file carries the
   **stack receipt** hash of the binary that produced it (`evidence.stack_receipt`, stamped by N33a-06), which
   names a resolution receipt under `receipts/`. The check resolves both. N40-01 names the harness receipt by
   hash and not by place; a check that resolves a hash needs one place, so the recording session commits it as
   `receipts/gates/<hash>.json` (DESIGN here, requested of N40-01). Findings carry the identifier
   `stack.gate-receipt` with the kinds below, so that `check-stack` emits nothing outside `stack.*` (N33a-05).
   1. Every part with status `pass` or `fail` has a 64-hex `receipt`, the file `receipts/gates/<hash>.json`
      exists and hashes to its name (kind `harness-receipt-missing`), and the stack receipt it cites exists
      under `receipts/` and hashes to its name (kind `stack-receipt-unresolved`).
   2. Every admission record (the record files under `receipts/admissions/`, never the generated
      `DEPENDENCY_ADMISSION.md`) cites a stack receipt that resolves and a commit of this repository whose
      tracked `Cargo.lock` contains the foundation. These are rules 1 and 2 of N33a-07's validator, which
      `check-stack` already runs (`stack.admission-record`, kinds `lockfile-lacks-foundation`,
      `receipt-missing`); this bead plants them as part of the invariant and adds no second implementation.
   3. For every part with status `pass`: in the cited stack receipt, every sibling entry in the gate's
      foundation closure has `dirty: false`. A `pass` on a receipt with a dirty sibling fails (kind
      `pass-on-dirty`), naming the gate, the part's milestone, the stack receipt and the dirty sibling.
   4. A part recorded on a stack receipt with a dirty sibling may have status `fail`, or `not-run` with
      `detail = "dirty-stack"` (the reason gate scripts record when `may_record_pass` is false, N33c-33), and
      never `pass`. DESIGN: an earlier draft allowed a result `development` here; `frob.gates/1` has a closed set
      of seven statuses (N40-01) and no such one, and a development observation on a dirty tree is an envelope
      stamped with its stack receipt (N33a-06), never a register row.
   The check reads the register through `frob-core`'s TOML reader (N34p2-01), taking from each part only
   `status`, `receipt` and `detail` and from each gate its foundations, because `xtask` does not link
   `frob-conformance`, which holds the register's strict loader (N38b-18, N40-01). It records no gate itself
   (`xtask` runs no physics, records no gate and holds no policy).
2. **INV-SUITE-04, by construction and by test.**
   - Construction: `check-stack` invokes only read operations on siblings: `git rev-parse`, `git status
     --porcelain`, `git ls-files`, `git cat-file`, `git merge-base --is-ancestor`, and file reads. It never runs
     `git checkout`, `reset`, `stash`, `clean`, `fetch`, `pull`, or any `cargo` command with a sibling as its
     working directory or manifest path without `--locked --offline` and an external target directory. The list
     of allowed sibling commands is a constant in the source, and a unit test asserts that no other command
     string is constructed.
   - Test with a copy it cannot write to: the test makes copies of three small `synthetic` sibling repositories
     (one clean, one dirty, one with a lock that its checkout fast-forwards), removes write permission
     recursively from the copies (and, on Linux, also runs under a mount namespace or a user that lacks write
     permission), points the stack lock at the copies, and runs `check-stack`. It must complete, classify drift
     correctly, and write the receipt inside this repository.
   - Syscall confirmation: the same run under a system-call tracer (`strace -f -e trace=file` on Linux;
     `dtruss` or the sandbox profile on macOS where permitted) shows no open-for-write, rename, unlink, mkdir or
     chmod on any path under a sibling. Where tracing is unavailable the permission test stands alone and the
     record says so.
   - Before-and-after digest: for the real siblings, BLAKE3 over `git status --porcelain=v2 --branch` output and
     the head is identical before and after every `check-stack` run in the end-to-end script.
3. **Drift classification is never a repair.** The check prints, for an off-pin sibling, `on-pin`, `stale-lock`
   (the checkout is a fast-forward of the lock) or `drift` (dirty, retreated or diverged), and a suggested next
   step for a person; it has no flag that changes a sibling.
4. **Registration.** The plants below are registered in the negative-control registry with the invariant each
   guards. None of them is one of the seven plants of the workspace gate GATE-WS-01: that gate's stale-stack-lock
   plant is caught by the comparison rule of N33a-05 and run by N34-14's script. The read-only-copy test here
   classifies the same condition (`stale-lock`) on an unwritable copy, which is the INV-SUITE-04 half of it.

## Acceptance criteria

- [ ] Plant A (a gate part with status `pass` and an empty `receipt`; and, separately, one whose harness receipt cites a stack receipt absent from `receipts/`): `cargo xtask check-stack` fails with `stack.gate-receipt` (`harness-receipt-missing`, then `stack-receipt-unresolved`), naming INV-SUITE-03 and the gate.
- [ ] Plant B (a `pass` part whose stack receipt has a sibling of the gate's closure with `dirty: true`): the check fails with `stack.gate-receipt`, `pass-on-dirty`, naming the gate, the receipt and the sibling.
- [ ] Plant C (a stack receipt file whose contents do not hash to its name): the check fails with `stack.receipt-hash` (N33a-05).
- [ ] Plant D (an admission record file naming a commit whose `Cargo.lock` does not contain the foundation): the check fails with `stack.admission-record`, `lockfile-lacks-foundation` (N33a-07).
- [ ] A `fail` part, and a `not-run` part with `detail = "dirty-stack"`, on a dirty stack receipt pass the check.
- [ ] `check-stack` completes against read-only sibling copies, with correct drift classes, and writes only inside this repository.
- [ ] The tracer run (where available) shows zero write-class system calls on sibling paths; the real siblings' status digests are unchanged across the run.
- [ ] The source-level allowlist test confirms that no mutating git or cargo command is constructed for a sibling path.

## Test plan

### Unit tests

`cargo test -p xtask check_stack_inv_suite`:
- `inv_suite_03_pass_without_receipt` and `inv_suite_03_stack_receipt_unresolved` (plant A), `inv_suite_03_pass_on_dirty_sibling` (plant B), `inv_suite_03_receipt_hash_mismatch` (plant C), `inv_suite_03_admission_commit_lacks_foundation` (plant D), `inv_suite_03_fail_and_dirty_not_run_allowed` (a `fail` part and a `not-run`/`dirty-stack` part on a dirty receipt → no finding).
- `inv_suite_03_reads_only_three_part_fields`: a register row carrying every field of `frob.gates/1` plus an unknown one loads in this check (the strict loader of N40-01, not this check, refuses the unknown field); a part with no `status` key gets no finding from this check (its absence is the strict loader's finding, not an INV-SUITE-03 one).
- `inv_suite_04_readonly_copies`: the permission test described above; asserts exit 0, the three drift classes (`on-pin`, `drift`, `stale-lock`), and that the copies' trees hash the same before and after.
- `inv_suite_04_command_allowlist`: enumerates every command the module can construct for a sibling path and compares with the allowlist.
- Property test for INV-SUITE-03: over 10³ generated registries (`synthetic` parts with random statuses, harness and stack receipts present or absent, dirty flags), the check accepts exactly those in which every `pass` or `fail` part cites a harness receipt that resolves to a stack receipt that resolves, and every `pass` cites a clean one; compared with a reference predicate.

### End-to-end script and logging

`scripts/e2e/suite_stack_invariants.sh` (sources the STD-E2E helper; writes
`target/e2e-logs/suite_stack_invariants/<utc>.ndjson` and a transcript): records the status digests of the real
siblings; runs
`cargo xtask check-stack` on the clean tree; runs the four plants on scratch copies; runs the read-only-copy
test; runs the tracer variant where the platform allows; records the status digests again. It logs a `cmd` and
an `assert` event per plant (invariant expected and reported, exit code), `metric` events
`sibling_write_syscalls` (threshold 0) and `siblings_changed` (threshold 0), the receipt hash written, the drift
class of every sibling, on a failure the offending path and system call (tracer) or the gate, receipt and
sibling named (plants), the tracer used or `tracer: unavailable` with the reason, and a `summary` with plants
caught of plants planted.

### Known answers and negative controls

Known answer KA-767 restated for the check: a receipt computed twice on an unchanged tree is byte-identical;
touching one tracked file in a sibling copy flips `dirty`, changes `tree_hash`, and `check-stack` fails. Negative
controls: plants A to D; a variant of the check with a `--fix-pins` behaviour (a test-only build that runs `git
checkout` in a sibling copy) must be caught by the read-only test (the command fails on the unwritable copy) and
by the allowlist test. Lanes: Linux and macOS, because permissions and tracing differ; twice on one machine.

## Considerations

- OPEN-SUITE-3 (is a dirty asupersync checkout acceptable for development builds between receipts?): default
  yes for development, with the tree hash in the receipt; no gate records a PASS. Condition 4 implements that
  default in the register (decision bead N33c-33).
- RISK-23 (dirty or off-pin sibling trees make a receipt unrepeatable): leading indicator, a drift class other
  than on-pin at a gate run.
- RISK-55 (collisions with other agents in a sibling): INV-SUITE-04 keeps this project's tools out of that
  problem entirely; people and agents change siblings, under the sibling's rules, with files reserved first.
- The measurement scripts of this unit (the suite survey, the coupling count, the toolchain matrix) follow the
  same read-only rule and are covered by their own before-and-after assertions.
