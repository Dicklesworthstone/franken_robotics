## Background

FrankenRobotics builds against sibling checkouts that live beside it on disk. On the day the plan was written the
asupersync checkout (the suite's concurrency runtime, which FrankenSim patches to a path dependency) had 267
modified paths at head `b32c5ba66315`, and FrankenSim's own checkout had 32 at head `483d09c682f2` (FACT, read
2026-11-21). Other agents work in those repositories, so their trees are often dirty for reasons that have
nothing to do with this project.

A pin names a commit. A dirty tree is not a commit: the bytes that were compiled are named by no revision. The
resolution receipt handles this by hashing the tracked bytes when a tree is dirty (`dirty: true`, `tree_hash`),
and the rule already fixed is that a dirty sibling admits development builds only and no gate records a PASS on a
dirty tree.

**OPEN-SUITE-3.** Is a dirty asupersync checkout acceptable for development builds between receipts? Owner: the
project owner. Decided at: INT-FSIM-01 (the first out-of-tree FrankenSim build) and wanted as owner input at M0.
Fail-closed default if undecided: yes for development, with the tree hash in the receipt; no gate records a PASS.
What the default costs: a gate run waits for a clean tree.

This is an owner decision because the alternatives trade the owner's time and the siblings' freedom against
this project's schedule, and no measurement settles that.

## Scope

In: preparing the decision (the options with their consequences, the measurement of how often trees are dirty),
recording it, and wiring the outcome into the tooling's default. Out: the receipt mechanics (BD-004); the
invariant's test (N33c-30); the evidence rule for results from different receipts (N33c-31).

## Technical approach

1. **Measure the situation.** For two weeks of M0 work (or the M0 duration, whichever is shorter), every
   `check-stack` run appends one line to `receipts/drift-log.ndjson`: date, per consumed sibling its head, dirty
   flag, modified-path count and drift class. From it compute, per sibling, the share of runs with a dirty tree
   and the longest clean interval. This is the evidence the owner decides on.
2. **The options, written out for the owner.**
   - **A (the default).** Dirty trees are acceptable for development builds. The receipt records the tree hash.
     Results carry result class `development`; no gate records a PASS; gate runs wait for a clean tree or use
     option C for that run.
   - **B (strict).** No build against a dirty sibling at all: `check-stack` fails and every build stops. Cost:
     this project's agents are blocked whenever another agent has uncommitted work in asupersync or FrankenSim;
     with the trees dirty on most days at planning time, this would stall M0.
   - **C (clean export for gates).** Development as in A. For gate runs, the build reads each consumed sibling
     from a clean export of its pinned commit (`git archive` of the revision into a scratch directory outside the
     sibling, never a checkout, branch or worktree inside it), so that a PASS never depends on the state of a
     shared working tree. Cost: disk and a second cold build per gate run; the stack lock's `path` is overridden
     for that run and the receipt records `source: export`.
   - **D (PASS on dirty with tree hash).** Allow a gate PASS on a dirty tree if the tree hash is recorded.
     Rejected by the plan's rules already: the bytes cannot be re-obtained from any revision, so the result
     cannot be reproduced; listed only so the record shows it was considered.
3. **Recommendation carried to the owner.** A for development together with C for gate runs: it removes the wait
   for a clean tree without weakening the rule that a PASS names a commit.
4. **Record.** An ADR in the ADR-SUITE series with the drift statistics, the option chosen, and the date; the
   open-question register is updated (decided, or default taken with the reason no decision was made). If the
   owner chooses C, a follow-up bead is opened for the export path in the build recipes; if B, `check-stack`'s
   default changes to fail on dirty and the cost is recorded as a schedule risk.
5. **Tooling default.** Until decided: `check-stack` exits 0 with a warning on a dirty consumed sibling when
   invoked with `--development`, and non-zero without that flag; gate scripts never pass the flag.

## Acceptance criteria

- [ ] The drift log exists with at least ten days of entries (or the whole of M0) and the per-sibling dirty shares are computed.
- [ ] The decision record lists options A to D with consequences and the recommendation, and carries the owner's choice or the note "default taken" with the date.
- [ ] OPEN-SUITE-3 is marked decided or default-taken in the open-question register, linked to the record.
- [ ] `check-stack` behaves as the decision says: with the default, a dirty sibling passes only under `--development`, and a gate row with result `pass` on a dirty receipt is rejected.
- [ ] The M0 exit review's checklist cites this record under "open questions due".

## Test plan

### Unit tests

`cargo test -p xtask check_stack_dirty_policy`:
- `dirty_fails_without_development_flag`: on a scratch sibling with one modified tracked file, exit non-zero and the sibling named.
- `dirty_passes_with_development_flag_and_records_tree_hash`: exit 0; the receipt has `dirty: true` and a 64-hex `tree_hash`.
- `clean_tree_has_null_tree_hash`.
- `drift_log_line_appended`: one canonical line per run with the five fields.

A script test for the statistics: on a `synthetic` log of ten runs with a sibling dirty in seven, the share is
0.7 and the longest clean interval is computed from the dates.

### End-to-end script and logging

A step of `scripts/e2e/suite_stack_invariants.sh` (N33c-30): runs `cargo xtask check-stack` with and without
`--development` against a scratch copy of a sibling with a planted modification, and logs `assert` events for
both exit codes, the `tree_hash`, and a `metric` event `dirty_share` per real sibling from the drift log (unit:
fraction of runs).

### Known answers and negative controls

Known answer: touching one tracked file in a sibling flips `dirty` and changes `tree_hash` (the negative control
of the receipt's own known answer). Negative control for the policy: a gate script modified to pass
`--development` must be caught by the invariant check that refuses a `pass` row on a dirty receipt. Lanes: both
machines, since each has its own sibling checkouts and its own drift.

## Considerations

- Fail-closed default until decided: development yes, with the tree hash; no PASS.
- RISK-23 (dirty or off-pin sibling trees make a receipt unrepeatable): this decision is its mitigation's
  open half.
- Two development builds on dirty trees rarely share a receipt, so their results cannot be pooled as same-stack
  evidence; agents iterating during M0 should expect `FROB-REF-890` when mixing results across rebuilds.
- The export of option C must be made outside the sibling repository: FrankenSim's rules forbid branches and
  worktrees, and this project's tooling never writes into a sibling.
- The question names asupersync; the same policy applies to every consumed sibling, and the record says so.
