## Background

asupersync is the suite's structured-concurrency runtime: tasks, cancellation, budgets, and the context value
`Cx` that carries them. FrankenRobotics links it for all async code, with exactly one package identity per build.
Two open questions about it are decided when the gate INT-ASUP-01 records its result (one asupersync package in
each workspace, the same published version in all of them, no binary linking two), which is also the gate that
proves the upstream work item FD-ASUP-01 (FrankenSim's constellation, FrankenTorch and fastmcp_rust aligned on one
published asupersync version by changes in those repositories; priority P0, at M0).

**OPEN-SUITE-1.** Which asupersync version does the whole graph resolve to? Owner: build lead. Fail-closed
default: the one published version FD-ASUP-01 aligns the siblings on; until it lands, whatever FrankenSim's
pinned commit builds with (0.6.2 by path today). Starting state (FACT, read 2026-11-21): FrankenSim resolves
0.6.2 by path while its own constellation lock says 0.5.0; frankensqlite, frankentorch, frankenscipy require
0.6.2 from the registry; franken_numpy and fastmcp_rust pin `=0.6.2`; frankentui, franken_threed and frankenjax
name 0.5.0 and never enter a graph.

**OPEN-SUITE-6.** Do computational crates take asupersync's `Cx`, or a capability-free token from `frob-core`?
Owner: Tether lead (the lead of the agent-facing surface and daemon). Fail-closed default: asupersync's `Cx`
wherever cancellation is observed; the token only if INT-ASUP-01 fails after FD-ASUP-01 and a fallback splits the
graph.

The second question blocks work in a quiet way: it fixes the signature of every long-running function in the
dynamics, contact, analysis and learning crates. Changing it later touches every one of them. The trade: `Cx`
gives real cancellation, budgets and the lab runtime's fault injection at every await point, at the price of
naming an asupersync type in computational crates; a local token keeps those crates free of the runtime (so they
would survive a split graph or a second runtime version) at the price of a thinner contract and an adapter.

## Scope

In: the evidence for both decisions, the decision records, and the small artifacts each outcome needs (the
version in the stack lock; the context type alias and its rule). Out: the gate and the upstream alignment
(BD-008); the token or the context implementation in `frob-core` (BD-005); KILL-MCP (BD-023).

## Technical approach

**OPEN-SUITE-1.**

1. Read from the INT-ASUP-01 record: the `cargo tree -d` output per workspace; the single resolved version; its
   source (path or registry); the state of FD-ASUP-01 in each sibling.
2. Decision rule (DESIGN): if FD-ASUP-01 has landed, the version is the published one all three siblings pin,
   resolved from the registry or from the path of the clean checkout at that tag, as the receipt shows; the
   `[patch.crates-io] asupersync` entry at the workspace root is kept only if FrankenSim's own manifest still
   carries it at the pin. If FD-ASUP-01 has not landed at the M0 exit review, the version is what FrankenSim's
   pinned commit builds with (0.6.2 by path), INT-ASUP-01 is recorded as failing or development-only, and the
   surfaces that would bring a second package stay out of the core graph under the first fallback of KILL-MCP.
3. Record: the `FD-ASUP` row of `franken-stack.lock` (`version`, and `git_rev` when resolved by path), an ADR
   with the three siblings' pins, and the open-question register entry.

**OPEN-SUITE-6.**

1. Inventory: list the crates that observe cancellation or budgets (the batched step and the referee step at
   chunk boundaries; long analyses; controller synthesis; learners; the job engine; the airlock's remote
   client), and for each whether it awaits (needs an executor) or only polls a flag at safe boundaries.
2. Options.
   - **A (the default): `Cx` wherever cancellation is observed.** Computational crates take `&Cx` (re-exported
     as `frob_core::cx::Cx`, so the import path is one module, as for quantities). Pure kernels and anything
     below a chunk boundary take nothing.
   - **B: a capability-free token.** `frob_core::cancel::Token` with `is_cancelled()`, `checkpoint() ->
     Result<(), Cancelled>` and a remaining-budget query, supplied by the daemon through the job context of rule
     L-10; computational crates never name an asupersync type; the daemon adapts `Cx` to the token at the
     boundary.
   - **C: split by layer.** `Cx` at layer 6 and above (job engine, ledger, surfaces); the token in layers 1 to 5.
3. Decision rule (the default, restated as a test): if INT-ASUP-01 passes on the whole graph, take A. If it
   fails after FD-ASUP-01 has been attempted and a fallback splits the graph (a surface in its own workspace
   with its own asupersync), take B for every crate that both graphs link, because a type from one asupersync
   package is not the same type in the other. C is recorded as considered and is the migration path from A to B
   if the graph splits later.
4. What must be true under either answer (acceptance of the seam): cancellation is observed at every chunk
   boundary and at every kernel-batch boundary; a cancelled computation reports the last committed tick per
   world; the lab runtime can inject a cancel at each await point of the job protocol; kernels and the step do
   not depend on a dispatcher or a scheduler (the two-planes rule).
5. Record: an ADR with the inventory, the option chosen and the migration rule; `frob-core`'s contract states
   the context type; a `check-deps` row enforces the outcome (under B or C: no direct asupersync edge from the
   listed computational crates).

## Acceptance criteria

- [ ] The `FD-ASUP` row of the stack lock names one version and its source, equal to what `cargo tree -d` shows in every workspace; the ADR for OPEN-SUITE-1 lists the three siblings' pins after FD-ASUP-01 or the reason it has not landed.
- [ ] The inventory of cancellation-observing crates exists, each marked "awaits" or "polls".
- [ ] The ADR for OPEN-SUITE-6 states the option taken (A unless the graph split), signed off by the Tether lead or recorded as default taken with the date.
- [ ] `frob-core` exports exactly one context path for computational crates (`frob_core::cx::Cx` or `frob_core::cancel::Token`), and a `check-deps` row enforces the corresponding dependency rule.
- [ ] Both questions are marked decided or default-taken in the open-question register.
- [ ] A cancellation test on the referee rollout (cancel at a chunk boundary) passes under the chosen context type and reports the last committed tick.

## Test plan

### Unit tests

- `cargo test -p xtask check_deps_context_rule`: under option A, a computational crate importing asupersync other than through `frob_core::cx` fails; under option B, any asupersync edge from a listed computational crate fails. The test is parameterized by the decided option read from `registries/decisions.toml`.
- `cargo test -p frob-core cx` (or `cancel`): `checkpoint_reports_cancel`: after cancellation the next checkpoint returns the cancelled result; `budget_query_monotone`: the remaining budget never increases.
- `cargo test -p frob-fsim cancel_at_chunk_boundary`: a 2,000-step rollout cancelled after chunk 3 returns chunks 0 to 3 and names tick 999 as the last committed.

### End-to-end script and logging

A step of `scripts/e2e/suite_deps_rules.sh`: prints `cargo tree -d` per workspace, asserts one asupersync
package, compares the resolved version and source with the stack-lock row, and runs the context-rule plant. It
logs `metric` events `asupersync_packages` (threshold exactly 1) and the resolved version string per workspace,
and `assert` events for the lock agreement and the plant.

### Known answers and negative controls

Known answer: with a 250-step chunk, a cancel delivered during chunk 4 leaves tick 999 as the last committed.
Negative controls: a seeded second asupersync version must fail the one-package assertion (the gate's own
control); a computational crate with a direct asupersync import must fail the context rule; a cancellation that
is observed only at job end (the checkpoint omitted in the chunk loop) must fail the chunk-boundary test. Lanes:
both machines; every workspace.

## Considerations

- Fail-closed defaults until decided: the version FrankenSim's pin builds with; `Cx` wherever cancellation is
  observed.
- RISK-03: two asupersync versions in one build; three siblings still pin 0.5.0. Mitigation: FD-ASUP-01 at P0;
  `check-deps` forbids 0.5.0 and the frankentui executor feature; KILL-MCP's first fallback if a surface still
  brings a second package.
- The independent auditor `frob-cert` takes neither answer: it has no dependency at all.
- Under option A the lab runtime can drive computational crates directly; under option B it drives them through
  the daemon's adapter, which narrows what deterministic simulation can explore below the job engine.
- M7 freezes every pin, including asupersync's, for the length of the tournament.
