## Background

Cargo resolves one version of a 1.x package per build graph. Several siblings pin the JSON library `serde_json`
exactly, and the pins disagree. FACT (confirmed in each `Cargo.toml` on 2026-11-21): franken_textiles and
franken_threed pin `=1.0.151`; fastmcp_rust pins `=1.0.154`; frankenscipy requires 1.0.154 or later; `ftx-drape`
(the cloth crate of franken_textiles) takes its workspace pin. FrankenSim's bedrock depends on FrankenSciPy, so a
graph that links FrankenSim resolves 1.0.154.

The consequence: the cloth oracle `ftx-drape` cannot be a dependency of a crate that also links FrankenSim. Its
admission gate therefore runs it as a worker process that exchanges whole jobs, in its own workspace, until the
pin is relaxed in franken_textiles (upstream work item FD-FTX-01, priority P3; the same relaxation for
franken_threed is FD-F3D-01). The interim posture for franken_threed: its crates are used only with their
`serde` feature off, outside every workspace that builds a `frob` binary, and its renderer route is a
subprocess.

Admission test of this foundation fact: `cargo metadata` resolves the graph that the cloth-oracle gate needs, or
reports the conflict. The workspace gate GATE-WS-06 turns it into a standing check: `xtask check-deps` reports
exactly one `serde_json` version per binary and fails a graph that adds `ftx-drape` to the core workspace.

There is a second reason to watch this one package. The feature set of the JSON library in a `frob` binary is
decided by whichever sibling is linked (one enables insertion-ordered maps, another arbitrary-precision numbers),
which is why canonical bytes come only from this project's own writer. Version and features are checked
together.

## Scope

In: the single-version rule for `serde_json` per binary; the conflict probe; the plant that adds `ftx-drape` to
the core workspace; the recorded pins. Out: the feature-set guard and the four-way feature build (the canonical
reader and writer bead); the cloth oracle worker (N33c-28); the upstream pin relaxations (FD-FTX-01, FD-F3D-01).

## Technical approach

1. **The rule (a row of the `check-deps` table).** For every binary target of every workspace of this
   repository: the set of resolved packages named `serde_json` in its dependency closure, with every optional
   feature group enabled, has exactly one element, or zero for binaries that must not link it (`frob-verify`, and
   any crate where `serde` is not allowed: `serde` and `serde_json` at exact pins are allowed in boundary crates
   only, namely `frob-io`, `frob-verbs`, `frob-chronicle`, `frob-design`, `frob-spec` and `surface/frob-mcp`,
   never in a hot path). The single version must equal the version recorded in `franken-stack.lock`
   (`serde_json = "<version>"`, 1.0.154 at the starting state).
2. **Report.** `cargo xtask check-deps` prints one line per binary: `binary`, `serde_json` version, source, and
   the count (1 or 0). A count of 2 or more fails and prints one dependency path per version.
3. **The conflict probe (the admission test of the fact).** `scripts/admission/pin_conflict_probe.sh` builds a
   scratch manifest outside every workspace that depends by path on (a) one FrankenSim crate that reaches
   FrankenSciPy and (b) `ftx-drape`, and runs `cargo metadata --format-version 1 --offline`. Expected at the
   starting state: resolution fails, and the error names two incompatible exact requirements on `serde_json`
   (`=1.0.151` and a requirement that only 1.0.154 or later satisfies). The script records the outcome as
   `conflict` with the two requirement strings and their origins, or as `resolves` with the resolved version if
   the pins have been relaxed. It does the same for an `f3d-*` crate with its `serde` feature on, and again with
   the feature off (expected: resolves, because the pin is not reached).
4. **The plant.** On a scratch copy of the tree, add `ftx-drape` as a path dependency of a core crate behind an
   optional feature (`cloth-oracle`) that no default build enables. `cargo xtask check-deps` must fail: either
   resolution itself fails (the check reports the conflicting requirements and exits non-zero, never a bare
   crash) or, if pins were relaxed, the never-dependency rule for franken_textiles fires. The plant is caught
   because the check resolves with every optional feature group enabled.
5. **Recorded pins.** The probe writes `receipts/facts/serde-json-pins-<utc>.json`: for each watched sibling
   (franken_textiles, franken_threed, fastmcp_rust, frankenscipy, frankensqlite, frankensim's lockfile) the
   requirement string, the manifest path and line, the features it enables, and the sibling revision. The suite
   survey reads the same keys.
6. **Switch-over.** When FD-FTX-01 lands, the probe's outcome becomes `resolves`; the cloth gate is then re-run
   with `ftx-drape` as a dev-dependency of the conformance harness, and the worker is kept if `cargo metadata`
   still reports a conflict. The single-version rule stays whatever the outcome.

Determinism: exact for fixed manifests. `--offline` keeps the probe from touching the network or the registry
index, and scratch manifests keep it from writing a lockfile into a sibling.

## Acceptance criteria

- [ ] `cargo xtask check-deps` prints the `serde_json` version for every binary and reports exactly one per binary (zero for `frob-verify`), equal to the stack lock's.
- [ ] The conflict probe reports `conflict` for FrankenSim with `ftx-drape` at the starting state, naming both requirements, or `resolves` with the version if the pin has been relaxed; either outcome is recorded with the sibling revisions.
- [ ] The plant that adds `ftx-drape` to the core workspace behind an off-by-default feature fails `check-deps` with a readable reason.
- [ ] A second plant (a dummy crate pinning `serde_json = "=1.0.151"` added to a boundary crate) fails with the two versions and a path to each.
- [ ] `serde_json` appears in no crate outside the six boundary crates as a direct normal dependency.
- [ ] The pins record exists and its hash is cited by the GATE-WS-06 record.
- [ ] No sibling checkout is modified by the probe.

## Test plan

### Unit tests

`cargo test -p xtask check_deps_serde_json` (scratch copies, real `cargo metadata`):
- `one_version_per_binary_clean_tree`.
- `two_versions_fail_with_paths` (the dummy exact pin).
- `ftx_drape_plant_fails_behind_optional_feature`.
- `auditor_has_no_serde_json`.
- `non_boundary_crate_with_serde_json_fails`: a planted direct dependency in `frob-dyn`.
- `version_must_equal_stack_lock`: the lock says 1.0.154 and a scratch graph resolves another patch version.

Script tests for the probe with two `synthetic` crates pinning `=1.0.0` and `=1.0.1` of a small real package:
the probe reports `conflict` with both strings; with one pin relaxed it reports `resolves`.

### End-to-end script and logging

`scripts/e2e/suite_deps_rules.sh` runs the rule on the clean tree and both plants; `scripts/e2e/suite_ws06.sh`
(N33c-40) runs the probe and reads the result. They log one `metric` event per binary (`serde_json_versions`,
threshold exactly 1), `assert` events for each plant with the rule reported, the probe's outcome with both
requirement strings, and the record's hash.

### Known answers and negative controls

Known answer at the starting state: the core graph resolves `serde_json` 1.0.154; FrankenSim plus `ftx-drape`
does not resolve. Negative controls: the two plants. The second plant is the "second exact pin on one package"
instance of the late risk row "an exact version pin in a sibling blocks an oracle", which must raise its signal
in 100 of 100 runs. Counterexample to the shortcut "a passing build means the pins are compatible": a build that
never enables the oracle's feature flag resolves, and the conflict appears only when the flag is first turned on
at the oracle's milestone; the resolution check therefore runs with every optional feature group enabled.
Lanes: both machines; every workspace.

## Considerations

- A relaxed pin upstream changes the probe's outcome and nothing else here; the never-dependency rule for
  franken_textiles remains until an ADR moves the cloth oracle from Subprocess to a dev-dependency.
- The same shape of conflict can arise for any exactly pinned package; the rule is written for `serde_json`
  because that is where the suite's pins disagree today, and the probe script takes the package name as an
  argument.
- Exact pins in this project's own boundary crates are deliberate (a floating JSON library could change parsing
  behaviour under a digest), which is why a conflict is resolved upstream or by a process boundary, never by
  loosening the local pin.
