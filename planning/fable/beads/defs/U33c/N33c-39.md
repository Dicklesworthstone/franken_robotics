## Background

The Metal backend of FrankenRobotics lives in an annex workspace, `spark/frob-spark-metal`, built on FrankenTorch's
generic Metal compute gateway `ft-kernel-metal`. The gateway in turn sits on a third-party binding crate. What
that binding exposes bounds what kernel sources may use, and two facts about it were read late.

FACT (confirmed in the registry source on 2026-11-21): under `ft-kernel-metal` 0.1.3 the binding is `metal`
0.33.0. Its language-version enumeration ends at Metal Shading Language 3.1 (`metal-0.33.0/src/library.rs:363`).
It already exposes indirect thread-group dispatch and thread-group memory length (`src/encoder.rs:1715`, `:1730`),
which the gateway does not wrap.

FACT to recheck (reported; re-run by the hardware fingerprint): a compile probe on the M5 Ultra is reported to
show that Metal Shading Language 3.2 and 4.0 provide no 64-bit integer atomic add and no 64-bit compare-and-swap.
The consequence for kernels (how a count beyond 2³² is kept without 64-bit atomics) belongs to the GPU chapter;
this bead only makes sure the facts are recorded where the gates look for them.

Admission test of the fact: INT-FT-01 (the gateway builds in the Metal annex, with FrankenTorch's `block` patch
repeated at the annex root, and runs a kernel on this Mac) records the language version the gateway compiles
under. Interim posture: dialect sources use no construct newer than version 3.1; the upstream work item FD-FT-01
(priority P1) wraps the existing bindings, among its other items (part of that work is wrapping and not new
binding work, precisely because the binding already exposes indirect dispatch and thread-group memory length).
The workspace gate GATE-WS-06 requires that the Metal language version and the 64-bit atomic probe are recorded
in the fingerprint.

## Scope

In: a compile-time re-read of the three binding facts in the annex; the language version read back and checked
against the one BD-016 entered in the INT-FT-01 admission record; the dialect rule "nothing newer than 3.1" with a plant; a check that the fingerprint record
carries the language version and the 64-bit atomic result. Out: the gateway and the annex (BD-016); the
fingerprint and its probes (BD-029 and the fingerprint's probe beads); wrapping the bindings (FD-FT-01, upstream
in FrankenTorch); wide counters (the GPU chapter's beads).

## Technical approach

1. **Binding facts by compilation (in `spark/frob-spark-metal/tests/binding_facts.rs`; the annex may name the
   binding crate because it resolves it through the gateway).**
   - *Enumeration end.* A `match` over the binding's language-version enumeration that names every variant up to
     3.1 and has no wildcard arm: it compiles only if no later variant exists. A second test, expected to fail to
     compile, names a 3.2 variant; when the binding gains one, that compile-fail test starts compiling and the
     harness reports "fact changed".
   - *Indirect dispatch and thread-group memory length.* Two functions that take a compute command encoder and
     call the binding's indirect thread-group dispatch method and its thread-group memory length setter. They
     are never executed; compiling is the assertion.
   - *Versions.* The resolved versions of `metal` (expected 0.33.0) and `ft-kernel-metal` (expected 0.1.3) are
     read from the annex lockfile.
2. **The language version the gateway compiles under.** The annex's first kernel compile (the Cayley step of
   INT-FT-01) is issued with an explicit language-version option where the gateway offers one, and the version
   actually used is read back (from the compile options echoed in the gateway's receipt, or, if the gateway
   offers no read-back, from a probe kernel that uses the version macro of the shading language and writes it to
   a buffer). The value, with how it was obtained, is this bead's `msl_version` in the facts record of item 5.
   The INT-FT-01 admission record is BD-016's (a dependency; records are append-only, N33a-07) and already holds
   the language version in force; `msl_version` must equal it, and a difference is a changed fact, listed first.
3. **The dialect rule.** One row for the dialect lint: Metal-side constructs are limited to Metal Shading
   Language 3.1. Concretely, the Metal prelude declares its language version as 3.1, the lint's list of admitted
   built-ins and qualifiers is the 3.1 set intersected with what the shared dialect allows, and the emitter
   passes version 3.1 to the compiler so that a newer construct is a compile error, not a silent success on a
   newer system compiler. A plant: a dialect source using a construct introduced after 3.1 must be rejected by
   the lint and, with the lint bypassed, by the compile at version 3.1.
4. **The fingerprint check.** A test reads the stored hardware fingerprint record of the Mac
   (`frob.fingerprint/1`) and asserts that the Metal device entry contains: the compiler and language version;
   the result `64-bit integers: yes | no`; the result `64-bit atomics: yes | no`; and the digests of the probe
   kernels that produced them. The expected value for 64-bit atomics is not asserted (it is the fact being
   rechecked); the assertion is that it is recorded, with the probe's compile log hash when the answer is `no`.
5. **Record.** `receipts/facts/metal-binding-<utc>.json`: the three binding facts with `expected_at_planning`,
   `observed` and `how`; the `msl_version`; the two fingerprint fields as read. Its hash is cited by the
   GATE-WS-06 record that N33c-40 enters. A changed fact (a newer enumeration variant; the gateway now wrapping indirect dispatch)
   is listed first and is a note to revisit the interim posture.

Determinism: compile-time facts are exact; the probe kernel's version read-back is exact.

## Acceptance criteria

- [ ] The exhaustive `match` over the language-version enumeration compiles with variants up to 3.1 and no wildcard; the compile-fail test naming a 3.2 variant fails to compile (or the fact is recorded as changed).
- [ ] The two functions using indirect thread-group dispatch and thread-group memory length compile against the binding.
- [ ] The facts record carries `msl_version` and how it was obtained, equal to the language version in BD-016's INT-FT-01 admission record (or listed first as a changed fact).
- [ ] The dialect plant with a post-3.1 construct is rejected by the lint, and by the compiler at version 3.1 when the lint is bypassed.
- [ ] The Mac's fingerprint record contains the Metal language version and the 64-bit integer and 64-bit atomic results with probe digests.
- [ ] The facts record exists and its hash is printed for N33c-40's GATE-WS-06 record to cite (the citation is N33c-40's acceptance, a bead that depends on this one).

## Test plan

### Unit tests

In the annex (`cargo test` in `spark/frob-spark-metal`, on the Mac; real binding, real device for item 2):
- `language_version_enum_ends_at_3_1` and `compile_fail/language_version_3_2.rs`.
- `indirect_dispatch_and_threadgroup_memory_exposed` (compile-only).
- `binding_versions_from_lockfile`: `metal` 0.33.0, `ft-kernel-metal` 0.1.3, or recorded as changed.
- `msl_version_readback`: the probe kernel writes the version it was compiled under; equals the option passed.
- `fingerprint_has_language_and_atomic_fields`.

Dialect lint test (`cargo test -p frob-kir lint_metal_version`): `rejects_post_3_1_construct`; `accepts_3_1_set`.

### End-to-end script and logging

`scripts/e2e/suite_ws06.sh` (N33c-40), on the Mac: runs `frob spark fingerprint --device metal:0 --key
ws06-fp-<run> --json` (a `run` verb: without its idempotency key it is refused with `FROB-REF-805`), extracts the
Metal entry, and logs `assert` events `msl_version_recorded` and `atomic64_probe_recorded` with the values, the
`msl_version` of the facts record beside the language version of BD-016's INT-FT-01 admission record, and the
facts record's hash. On `trj` the step logs `not-applicable`
with the reason (no Metal device).

### Known answers and negative controls

Known answers at the starting state: the enumeration ends at 3.1; both encoder methods exist; `metal` 0.33.0.
Negative controls: the post-3.1 dialect plant; a fingerprint record with the atomic field removed (the test must
fail); a `match` with a wildcard arm added (a review rule: the test file is checked for the absence of `_ =>`,
because a wildcard would make the enumeration test pass for any binding). Lanes: the Mac only for device steps;
compile-only facts also on `trj` if the binding crate builds there, otherwise recorded as not applicable.

## Considerations

- The system compiler on a newer operating system may accept newer constructs by default; pinning the language
  version in the emitter is what makes "no construct newer than 3.1" a property of the build and not of the
  machine. A driver or system update changes the fingerprint identity and makes device results uncitable until
  the check is re-run.
- The gateway accepts at most 31 buffer arguments and currently offers one synchronous batch per chunk; those
  limits and their upstream remedies are in FD-FT-01 and are not restated here.
- If FD-FT-01 migrates the gateway to another binding crate, the three facts are re-read against the new crate
  and this bead's tests are updated in the same change. That change is NFp1-52 (stage 5 of FD-FT-01, M2: the
  migration from `metal` 0.33 to `objc2-metal`): when stage 5 is adopted it re-points the binding-fact tests of
  this bead to the new crate (its version, its language-version enumeration, the indirect dispatch and
  thread-group memory length calls) and moves the version assertions to the new resolved versions, and it keeps
  the dialect hold at 3.1; raising that ceiling needs its own decision and its own compile probe.
- RISK-48 of the register (a driver, system or binding update changes kernel results) is the standing risk
  behind recording these facts.
