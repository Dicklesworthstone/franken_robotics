## Background

Every sibling repository FrankenRobotics consumes belongs to the same owner, so a limitation, defect or mismatch
found in a sibling is work this program does, in the sibling's repository, under that repository's own
`AGENTS.md`, gates and conventions. Each such change is an **upstream work item**: a bead in this program's graph
with the label `upstream`, mirrored as a bead in the sibling's tracker, and recorded in `registries/upstream.toml`
with five things: the change, a priority, the interim posture here, the switch-over rule, and one reproducible
failing fixture. No milestone waits on an upstream change landing, and no local patch or fork stands in for one.
A defect found in a sibling becomes an admission test here and an upstream work item there, in that order.
Upstream changes are additive (a new mode, entry point, type or feature, never a change to existing behaviour),
and before an upstream change edits a file it reserves that file through Agent Mail and follows the sibling's
coordination rules.

A seed bead opens the upstream work items of the main register. The late foundation facts added more. Five have
identifiers in the register:

interim posture is still needed.

## Scope

In: register rows for the eleven items (five with their identifiers; six assigned the next free identifiers by

changes (each is its own `upstream` bead once registered); the register's format and the main items (BD-037).

2. **For each of the eleven rows.**
   1. Write the row in `registries/upstream.toml` with the five required things and the fixture's path in this
      repository (the admission probe's test, which is the reproducible failing fixture) and the sibling
      revision at which it was observed.
   2. Open the bead here with the label `upstream`, the priority, and the probe bead as `related`.
   3. Mirror it as a bead in the sibling's own tracker, following that repository's rules; record the mirrored
      identifier in the row.
   4. In the probe's test, add a comment-free machine-readable link: the test carries an attribute or a table
      entry `upstream = "<identifier>"`, so that when the probe reports `fixed upstream` the register row can be
      found and its switch-over rule run.
3. **Consistency check.** A test in `frob-conformance` reads `registries/upstream.toml` and the negative-control
   registry and asserts: every foundation-fact row 1 to 14 has an upstream identifier or the note "no upstream
   change" (row 7's worker posture and row 8's part of FD-FT-01 are covered by identifiers); every upstream row
   has a fixture that exists; no identifier is reused; counts by repository and priority are printed (the main
   register had 53 items before these six: 33 in frankensim, 3 in frankentorch, 5 in frankensympy, 2 in
   franken_lean and one each in ten other repositories or groups; two P0, eight P1, sixteen P2, twenty-seven
   P3).
4. **What registration does not do.** It moves no pin, edits no sibling file, and blocks no milestone. An item
   that lands is adopted only through its switch-over rule and a compatibility train (move the pin, write a new
   receipt, rerun the admission and parity gates, relock).

## Test plan

### Unit tests

`cargo test -p frob-conformance upstream_register`:
- `rows_have_five_things`: every row has the five required fields non-empty.
- `fixtures_exist`: every fixture path resolves to a test in this repository.
- `identifiers_unique_and_never_reused`: against the tombstone list.
- `foundation_fact_rows_linked`: rows 1 to 14 each map to an identifier or an explicit note.
- `counts_by_repo_and_priority`: after this bead, frankensim 38, franken_threed 2, total 59; printed.

### End-to-end script and logging

A step of `scripts/e2e/suite_ws09.sh` (N33c-48): runs the consistency test and, for each probe that reports
`fixed upstream`, prints the register row and its switch-over rule as an `assert` event `switch_over_due` with the
identifier; logs the counts as `metric` events.

### Known answers and negative controls

Known answer: 53 items before, 59 after; frankensim 33 + 5 = 38; franken_threed 1 + 1 = 2. Negative controls: a
row with an empty switch-over rule must fail `rows_have_five_things`; a row whose fixture path points to a
deleted test must fail `fixtures_exist`; an identifier reused for a different change must fail the uniqueness
test. Lanes: not applicable beyond running the test on both machines.

## Considerations

- RISK-55: an upstream change collides with other agents working in the same sibling repository. Registration
  is the cheap part; the changes themselves reserve files first and land small.
- The priority of an upstream work item states its value to this project and orders it in this program's queue.
  No priority makes a milestone wait: the interim posture holds until the switch-over rule has been run.
- An upstream work item is never a mitigation by itself; its interim posture is.
- The six new identifiers are assigned by the register's owner; this bead must not guess numbers that another
  drafter of the register may also be assigning. Until assigned, the working names above are the keys.
- A third-party gap is not an upstream work item; none of these eleven is third-party.
