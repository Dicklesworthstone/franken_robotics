## Background

A reader should be able to find the crate for any mechanism, and a tool should be able to refuse a dependency the
design forbids. `xtask` is that tool: a small binary crate in the core workspace (layer 7, tier Solid, cap 3
thousand lines with tests) that contains exactly six checks. This bead writes the first two. They enforce the
layer and dependency rules, which are DESIGN decisions with these reasons:

- **L-1** A crate depends only on lower crates. Lower means a lower layer number, or the same layer and an
  earlier row of the crate map (a smaller rank). Each crate declares both in its manifest
  (`[package.metadata.frob] layer = 3`, `rank = 2`). A chapter that needs a different order inside a layer
  changes the rank by ADR; a cycle is never admitted. Counterexample for the intra-layer clause: if rows inside
  a layer were unordered, `frob-arena` could depend on `frob-opt` for comparison while `frob-opt` depends on
  `frob-arena` for batteries, and Cargo would reject the cycle only after both were written. The rank makes the
  second edge a failure on the day it is added.
- **L-2** Only the airlock crate `frob-fsim` names types from FrankenSim's volatile crates, so that an API change
  in a sibling that moves daily costs one crate. The only exception is the bedrock-direct list (below), and
  `fs-qty` is named only through `frob_core::qty`, which keeps the units escape hatch a one-module change.
- **L-3** The core never depends on an annex. Backends implement core traits.
- **L-4** Each foundation (a sibling repository or third-party crate this project consumes) is confined to the
  crates named in its row of the stack lock.
- **L-5** Core runtime dependencies are the standard library and Franken foundations. `serde` and `serde_json`
  at exact pins are allowed in boundary crates only (`frob-io`, `frob-verbs`, `frob-chronicle`, `frob-design`,
  `frob-spec`, `surface/frob-mcp`), never in a hot path. Forbidden everywhere: tokio and its ecosystem, a direct
  Rayon pool, BLAS and LAPACK, C or C++ numerical libraries. A Python interpreter is forbidden everywhere except
  `bindings/frob-gymnasium`.
- **L-9** `frob-cert` (the offline certificate checker) has an empty dependency table, and only `frob-verbs`,
  `frob-cli` and `frob-conformance` may depend on it: a checker that shares code with a producer can share its
  defect.
- **L-10** A lower crate reaches a service above it only through a trait it defines itself; five standing
  inversions are registered. **L-11** Two planes: kernels and the step never depend on a dispatcher, a memo
  policy, an estimator or a scheduler: no crate of layers 1 to 3 holds one. Decisions about what to run live at
  layer 4 and above and in the daemon. Compile memoization in `frob-model` is a pure cache keyed by identity with
  a fixed bound, not a policy; the memo graph for results sits in front of verb executors in `frob-verbs`, with
  its bytes in `frob-chronicle`.

Honesty about the closure: path dependencies on FrankenSim bring its transitive closure, which includes
third-party crates such as `nalgebra` and `rayon` (FACT: 262 registry packages among the 479 in
`frankensim/Cargo.lock`). "Franken-only" describes direct edges; the checks say so in their output.

Rejected alternatives: a general-purpose dependency linter configured by file (the rules here are few, fixed and
tied to this project's own tables; a compiled table changes only by a reviewed commit); enforcing layers by review.

## Scope

In: the `xtask` binary with its command-line surface and report format; `check-layers`; `check-deps` for the
rules listed in the title, plus the forbidden-edge table of the proof boundaries.
Out, each in its own bead: suite rules of `check-deps` (one asupersync package, the frankentui feature, airlock
feature groups, default-off tier features: N34-03); the JSON-library feature guard (N34-04); the deep
auditor-independence rules (N34-25); the other four checks and the six-subcommand test (BD-004, N34-07, N34-08,
N33a-05 for `check-stack`); the crate map (N34-02); the rows of the inversion register
`crates/xtask/src/inversions.rs` and the four `frob-core` port traits (N34-06, which depends on this bead: this
bead writes the L-10 rule code and tests it on `synthetic` register fixtures; N34-06 fills the five real rows).

## Technical approach

**Surface.** `cargo xtask <check> [--root <dir>] [--json]`, through an alias in `.cargo/config.toml`. `--root`
points a check at a scratch copy. Exit codes: 0 clean; 2 findings; 3 usage error; anything else is a fault of
the tool. With `--json` the check writes one report, schema `frob.xtask.report/1`:
`{"check", "ok", "root", "findings": [{"rule", "subject", "path", "line", "message", "repair"}], "facts": {…},
"elapsed_ms"}`. Every finding has a stable rule identifier; ownership of a defect class is defined on those
identifiers, so that one planted defect is reported by one check.

**Inputs.** For each workspace of the workspace table, two reads of `cargo metadata`, both through `frob-core`'s
JSON admission reader (N34-17): `cargo metadata --format-version 1 --no-deps --locked --offline` gives the declared
direct edges with their kinds and each package's `[package.metadata.frob]` table; `cargo metadata
--format-version 1 --locked --offline` (resolved, from the lockfile and the local cache) gives, for every
dependency package, its `links` key and its build dependencies (step 4 of `check-deps`) and the resolved closure
for the facts of step 7. `--no-deps` alone cannot answer either. Manifests are read through `frob-core`'s strict
TOML-subset reader (`frob_core::registry::toml`, N34p2-01); `franken-stack.lock` is read through the stack-lock
parser built on it (`stack::lock::load`, N33a-03), so the lock has one reader. `xtask` depends on `frob-core`,
the bedrock crate `fs-blake3` (the streamed tree hash and the stack-lock digest of N33a-03 and N33a-04) and the
standard library only (FACT: the sibling's own `xtask` likewise links no TOML or JSON library). Neither check compiles anything or touches the network: a resolution that would need the
network is a usage error (exit 3) with the repair "run `cargo fetch` once through the build shim".

**check-layers**, in order:
1. Crate-map validation: `ADR-WS-01.unlisted-crate`, `map.metadata-mismatch`.
2. For every edge A → B between crates of this repository, of any kind (normal, build, dev; DESIGN: a test that
   needs a higher crate belongs in the higher crate, and shared fixtures are files, not crates):
   `L-1.upward` if layer(B) > layer(A); `L-1.rank` if the layers are equal and rank(B) ≥ rank(A).
3. `L-3.core-to-annex` for any edge from a core crate to an annex crate or to a path under `spark/`, `derive/`,
   `bindings/` or `apps/`; `L-3.annex-to-annex` for an edge between two annexes outside `apps/`.
4. The inversion register `crates/xtask/src/inversions.rs` (rows: identifier, trait path, defining crate,
   allowed implementing crates, authority `standing` or `adr = "<path>"`): `L-10.unregistered-inversion` (a
   marker line `// frob:inversion <id>` with no row), `L-10.unlisted-implementor` (an `impl <Trait> for` outside
   the row's allowed crates), `L-10.wrong-home` (the trait is defined in a crate other than the row's),
   `L-10.inversion-without-adr` (a row that is not `standing` and names no ADR file that exists). That the real
   register has exactly the five `standing` rows of rule L-10 is the register's own test (N34-06).
5. `L-11.controller-in-compute-plane` if a crate of layers 1 to 3 declares `plane = "decision"` or carries a
   `[[controller]]` record in its `contract.toml` (the record every adaptive controller must have).

**check-deps**, in order:
1. `fsim.volatile-edge` (rule L-2, the invariant INV-SUITE-01): a crate other than `frob-fsim` has a direct edge
   (normal, build or dev) to a FrankenSim crate outside the bedrock-direct list `fs-ga`, `fs-math`, `fs-qty`,
   `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`, `fs-ad`. DESIGN: this is the one
   definition of the rule and the identifier that INV-SUITE-01's tests and the feature-group beads cite (an
   earlier wording here called it `L-2.volatile-outside-airlock` while N33c-29 defined the same rule again as
   `fsim.volatile-edge`); N33c-29 adds its two exceptions (the manifest-only package of `worker/`, standalone
   probe workspaces, with the finding `fsim.standalone-edge`) and its invariant battery. `L-2.fs-qty-direct`:
   `fs-qty` is a direct dependency of a crate other than `frob-core` and `frob-fsim` (the one row of the `fs-qty`
   confinement; N33c-03 adds its plant and a text hint). `L-2.airlock-reexport`: `frob-fsim` re-exports the root
   of a volatile crate (`pub use fs_…` or `pub extern crate fs_…`, a source scan).
2. `L-4.foundation-confined`: every direct dependency of one of our crates that is not a crate of this
   repository must belong to a `[[foundation]]` row of `franken-stack.lock` (matched by path prefix for
   `consume-path` and `build-time` rows, by package name and version for `consume` rows), and one use of the row
   must admit the edge under the posture-to-graph rules of N33a-01 (`stack::posture::edge_allowed(use, from,
   kind, spec)`): the depending crate is in the use's `confined_to` (the token `bedrock-direct` admits the list
   above from any crate, `any` admits every crate), an `oracle` use admits only a dev-dependency, and a
   `subprocess` or `pattern` use admits no edge. `L-4.edge-spec`: the crate is admitted but the specification is
   not the posture's: a `consume` edge whose requirement is not `=x.y.z` equal to the row's `version`, a
   `consume-path` edge that is not a path dependency on the row's `path`, or either with default features on.
   DESIGN, one finding per defect: for the FD-FSIM row the crate side of the confinement is rule 1's, so a
   volatile edge is reported once, as `fsim.volatile-edge`, and L-4 checks only its specification. Initial rows:
   frankensim → `frob-fsim` plus bedrock-direct; asupersync → all async code; frankensqlite →
   `frob-chronicle`, `frob-conformance`; frankentorch → `spark/frob-spark-metal`, `frob-learn` behind a feature;
   `cudarc` → `spark/frob-spark-cuda`; franken_numpy → `frob-chronicle`, `frob-conformance`,
   `bindings/frob-gymnasium`; frankenscipy → `frob-conformance`; frankensympy → `derive/frob-derive`,
   `frob-conformance` (re-check only); fastmcp_rust → `surface/frob-mcp`; frankentui → `frob-tui`;
   franken-kernel → `frob-conformance` (oracle). A foundation with posture pattern, subprocess or oracle-only
   worker has an empty list and is never a Cargo dependency.
3. `L-5.third-party`: a core crate has a direct dependency from a registry or a git source that no foundation
   row admits, other than `serde` and `serde_json` in the six boundary crates. `L-5.serde-outside-boundary`;
   `L-5.serde-not-exact` (the requirement is not of the form `=x.y.z`).
4. `L-5.forbidden`, on direct edges of every crate of every workspace, by package name: the tokio family
   (`tokio`, `tokio-*`, and async stacks built on it such as `hyper`, `tonic`, `axum`, `tower`, `reqwest`);
   `rayon` and `rayon-core`; BLAS and LAPACK bindings (`blas*`, `lapack*`, `openblas-src`, `intel-mkl-src`,
   `netlib-src`, `accelerate-src`, `ndarray-linalg`, `nalgebra-lapack`); in the core, any direct dependency
   whose manifest has a `links` key or a build dependency on `cc`, `cmake` or `bindgen`. Each row of the name
   table carries its reason; the non-goal register (N00-23, which depends on this bead) adds the hardware-I/O
   and ROS client rows with the reason `nongoal = "NONGOAL-04"`, and no other list of forbidden names exists
   for direct edges.
   `L-5.python-outside-bindings`: `pyo3`, `cpython`, `rustpython*` or a `numpy` binding anywhere but
   `bindings/frob-gymnasium`.
5. `L-9.cert-has-deps`: any entry in `[dependencies]`, `[dev-dependencies]` or `[build-dependencies]` of
   `crates/frob-cert/Cargo.toml`. `L-9.cert-dependent`: a crate other than the three allowed depends on it.
6. `edge.forbidden`: the proof-boundary table. Initially it has one row, `frob-arena` → `frob-nemesis`
   (qualification code must not link the searcher). The row is listed although the layers already forbid the
   edge, so that a rank or layer change by ADR cannot permit it silently. To keep one owner per defect, the
   table is evaluated only on edges that satisfy the layer rules: while the layers forbid the edge,
   `check-layers` reports it and this check stays silent.
7. Facts (not findings) in the report: per workspace, the number of packages and of registry packages in the
   resolved closure, and the transitive hits of the forbidden list with one dependency path each.

Determinism class D0: findings are sorted by (rule, subject, path); the same tree gives the same report bytes.

## Acceptance criteria

- [ ] Seed done-condition: in scratch copies, a deliberate upward edge (`frob-lie` → `frob-design`), an
      intra-layer edge against rank (`frob-arena` → `frob-opt`) and a forbidden dependency (`tokio` in
      `frob-dyn`) each fail, with `L-1.upward`, `L-1.rank` and `L-5.forbidden` respectively, exit 2.
- [ ] The clean tree passes both checks with exit 0 and zero findings.
- [ ] Each planted edge is reported by its owning check only: the two layer plants leave `check-deps` clean and
      the forbidden dependency leaves `check-layers` clean (the ownership rule of GATE-WS-01, measured for all
      seven plants by N34-14).
- [ ] INV-WS-01 (the dependency graph respects layer and rank): a property test over 10³ seeded random crate
      graphs shows `check-layers` reports a finding exactly when some edge violates the order.
- [ ] A direct `fs_qty` dependency outside `frob-core` and `frob-fsim` fails (`L-2.fs-qty-direct`); a
      dependency on `fs-mbd` from `frob-dyn` fails with `fsim.volatile-edge` alone (no `L-4` finding on the same
      edge); `fs-ga` from `frob-lie` passes.
- [ ] `L-4` decides through N33a-01's `edge_allowed` on rows read by N33a-03's parser: frankensqlite from
      `frob-arena` fails `L-4.foundation-confined`; asupersync from `frob-dyn` with a caret requirement, or with
      default features on, fails `L-4.edge-spec`; franken-kernel as a dev-dependency of `frob-conformance`
      passes and as a normal dependency fails.
- [ ] `serde_json = "1"` in `frob-verbs` fails (`L-5.serde-not-exact`); `serde` in `frob-dyn` fails.
- [ ] A dependency in `frob-cert` fails (`L-9.cert-has-deps`); `frob-lemma` → `frob-cert` fails with
      `L-9.cert-dependent` although the ranks alone would permit the edge.
- [ ] The rules of this bead in both checks, including the shared resolved `cargo metadata` read, finish in
      under 10 s on a warm tree (budget share of GATE-WS-04 in BD-004's table, TARGET).
- [ ] `xtask`'s only dependencies are `frob-core` and `fs-blake3`; `--json` output validates against
      `frob.xtask.report/1`.

  `check-layers` and nothing from `check-deps`; with a `synthetic` map that ranks `frob-nemesis` below
  `frob-arena` the same edge gives `edge.forbidden` from `check-deps` and nothing from `check-layers`.

- `exit_codes`: clean tree 0; a finding 2; an unknown subcommand or a missing `--root` directory 3.
- `report_is_sorted_and_stable`: two runs give identical bytes.
- `random_graph_property` (INV-WS-01).

### End-to-end script and logging

`scripts/e2e/workspace_checks.sh` (bead N34-14) copies the tree to a scratch directory, plants each defect, runs
all six checks with `--json`, and logs per cell of the plant-by-check matrix the command, exit code, wall time,
the rule identifiers reported and the expected owner, in the structured format of STD-E2E. The lines this bead
owns are the plants `upward-edge` (`frob-lie` → `frob-design`), `edge-against-rank` (`frob-arena` → `frob-opt`;
the plant identifier of CX-363 in the counterexample registry N34-CX) and the
extra plants `tokio-in-dyn` and `cert-dependent`: each NDJSON line carries `ts`, `script`, `bead: "BD-003"`,
`step`, `event`, the exact `cargo xtask` command line, exit code, `elapsed_ms` against the 10 s share of
GATE-WS-04, the sorted list of rule identifiers, the expected owner, and the BLAKE3 digest of the `--json`
report; on a miss it logs the first unexpected rule and the scratch-copy path. The clean-tree run logs the
`facts` block (package and registry-package counts per workspace) so that the closure is visible in every run.

## Considerations

- OPEN-WS-1 (owner: Build lead): the rank order inside layers 4 and 5 may need edges the map did not foresee.
  Default: the map's order; a change is an ADR. The check never admits a cycle.
- The cap of `xtask` is 3 thousand lines with tests; six checks with fixtures will press on it (RISK-18). If it
  reaches 115%, the registry readers move into `frob-core` or an ADR raises the cap; no seventh check appears.
- The foundation table comes from the stack lock, so adding a foundation is one row there plus its admission
  record, not a code change here.
- `xtask` runs no physics, records no gate and holds no policy.
- RISK-03 (two asupersync versions in one build) and the toolchain-train risk are caught by the suite rules of
  N34-03, which extend this check.
