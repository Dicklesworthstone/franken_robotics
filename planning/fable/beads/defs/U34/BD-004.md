## Background

`xtask` is the workspace's policy tool: a small binary crate in the core (layer 7, tier Solid). DESIGN: it
contains exactly six checks: `check-layers`, `check-deps`, `check-unsafe`, `check-generated`, `check-contracts`,
`check-stack`. A seventh check needs a named defect class it would have caught and the owner's approval. Reason:
a sibling product recorded how process tooling grows until running it becomes the work; fixing the number, and
testing the number, is the guard. Everything the workspace and suite-consumption rules ask a tool to enforce is
assigned to one of the six:

| Check | Enforces |
|---|---|
| `check-layers` | Rule L-1 with layer and rank, L-3 (the core never depends on an annex), L-10 (registered inversions), L-11 (two planes) |
| `check-deps` | L-2, L-4, L-5, L-9; one asupersync package per binary; no asupersync 0.5.0 anywhere; the forbidden frankentui feature; airlock feature groups enabled only by the crates listed for them; L-12's default-off rule; the JSON-library guard |
| `check-unsafe` | The deny lint in the core; every annex capsule registered, under its line limit, with its `SAFETY.md` |
| `check-generated` | L-8 (generated files are never edited) for schemas, the command-line and MCP surfaces generated from `verbs.toml`, generated kernel arithmetic, and the README status table |
| `check-contracts` | `CONTRACT.md` sections; `contract.toml`; every format row has an owner, a round-trip test and a refusal test; every release path has a demo file whose claims exist in `gates.toml`; every crate's line count against its cap, with 115% as a failure that an ADR clears |
| `check-stack` | The stack lock, with the toolchain T, against lockfiles, toolchain files and sibling heads; the resolution receipt; drift classification; the check itself writes nothing to a sibling checkout |

`xtask` runs no physics, records no gate and holds no policy. Its own cap is 3 thousand lines, and its test suite
asserts that the subcommand count is six.

This seed bead writes the fourth check, assembles all six behind one command table, and carries the two gates
that judge the set. The other three checks named in its title are split into their own beads because each is
several days of work: `check-unsafe` (N34-07), `check-contracts` (N34-08), `check-stack` (N33a-03, N33a-04,
N33a-05).

## Scope

In: `check-generated`; the command table and help text; the six-subcommand test; the ownership rule over finding
identifiers; the in-crate plant matrix on a miniature workspace; timing instrumentation.
Out: the bodies of the other five checks (BD-003, N34-03, N34-04, N34-07, N34-08, N34-09, N34-25, and
N33a-03 to N33a-05 for `check-stack`); the status-table generator's rules (BD-002); the end-to-end run on the real
tree that records the two gates (N34-14); the rules later beads add inside `check-generated` (below).

## Technical approach

**check-generated.** Rule L-8: generated files are never edited; the check regenerates and compares. A generator
is a pure function from registry files to output files, written in `xtask::generate` with `frob-core`'s registry
readers and canonical writer, and depending on none of the crates that consume its output. Table (data):

| Generator | Inputs | Outputs | Mode |
|---|---|---|---|
| Format and verb schemas | `registries/formats.toml`, `registries/verbs.toml` | `schemas/frob.*.json`, one file per schema identifier with `/` written as `.` | Regenerate, compare bytes |
| Stack-lock schema | The typed model of the stack lock (`stack::lock`, N33a-03) | `schemas/frob.stack-lock.1.json` | Regenerate, compare bytes |
| Admission document | The record files under `receipts/admissions/` and the first-commit header (`xtask::generate::admission_doc`, N33a-07) | `DEPENDENCY_ADMISSION.md` | Regenerate, compare bytes |
| Refusal codes | `registries/refusals.toml` | The generated `RefusalCode` enum in `frob-core` | Regenerate, compare bytes |
| Honest-status table | `registries/gates.toml` | The block between the status markers of `README.md` | Regenerate, compare bytes |
| Kernel arithmetic | Kernel manifests in `registries/kernels.toml` | Generated arithmetic under `kernels/` | Digest: each file's BLAKE3 must equal the digest its manifest records |

The kernel row uses digests because re-deriving kernel arithmetic needs the symbolic-derivation annex and would
break the 60-second budget; the derivation lane regenerates and this check proves nobody edited the result.
DESIGN: the generated paths are exactly the outputs column. The hand-written schemas of the first commit and their
later edits (the registry-file schemas under `schemas/registries/`, `schemas/demo.schema.json` and
`schemas/contract.schema.json`; BD-002, N34x-03, N34-07, N33a-01) are reviewed source, not outputs: they are
not regenerated and never `gen.orphan`, which is reported only for a `schemas/frob.*.json` file that no row
produces. (An earlier wording gave the first row the output `schemas/**`, which made every hand-written schema
an orphan on the clean tree.)
Every generated file carries a marker on its first line naming its generator and inputs. Findings:
`gen.differs` (path and first differing line), `gen.missing`, `gen.orphan` (a file under a generated directory
that no generator produces), `gen.digest`, `gen.marker-missing`, `gen.status-invalid` (the status generator
refused a registry row, for example a pass with no measured value). `cargo xtask check-generated --write`
rewrites the regenerable outputs; it never rewrites a digest and never touches files outside the outputs
column. Output bytes are deterministic: sorted rows, fixed widths, `\n` endings.

Later rules inside this check (each is a generator row or a rule added to `check-generated` by its own bead; none
is a new check): the per-bead logs `docs/delivery/logs/<bead>.ndjson` (schema `frob.beadlog/1`) become a second
input of the honest-status table, and their append-only chain is recomputed so that an edited or deleted earlier
line fails (N29a-09, M1); the committed export of the artifact graph is checked against the registry so that every
`claim_id` of a closing line resolves (BD-095, M1); the command-line and MCP surfaces generated from
`registries/verbs.toml`, which by ADR-TETHER-01 are one static table that `frob-verbs`'s build script emits into
`$OUT_DIR/verbs_table.rs` (neither `frob-cli` nor `surface/frob-mcp` holds a per-verb table, so no committed
copy exists here to compare): N32a-02 (M0) adds the rule that re-runs that emitter and compares bytes, and fails a
build made with its `FROB_VERBS_REGISTRY` override; the generated printout `docs/generated/refusals.md` and the
refusal registry's cross-chapter checks (N35-33, M0). The generator interface of this bead therefore takes a list
of input globs per row, not one file. DESIGN: an earlier wording of the table above gave the verb tables as
committed Rust files under `frob-cli` and `surface/frob-mcp`, which contradicts ADR-TETHER-01.

**The command table.** One static array of six `(name, fn)` pairs; `cargo xtask <name> [--root <dir>] [--json]`.
No `all` subcommand exists: running all six is a loop in a script. No argument prints the six names and exits 3.
Exit codes: 0 clean, 2 findings, 3 usage.

**Ownership rule.** Each finding identifier belongs to one check. The plant harness defines "caught by" as "the
check exits 2 with at least one finding" and "caught by no other" as "every other check exits 0". For that to
hold, each plant is applied to a scratch copy together with the normalization a legitimate change of the same
kind would carry: a plant that changes a manifest regenerates the scratch lockfile and writes a new resolution
receipt in the scratch copy, so that the only defect left is the planted one.

**GATE-WS-01** (TARGET; claim Known answer; M0): a deliberate upward edge, a deliberate intra-layer edge against
rank, a second asupersync package, an unregistered capsule, an edited generated file, a contract missing a
section and a stale stack lock are each planted in a scratch copy; each plant is caught by the check that owns
it and by no other: 7 of 7 plants caught, 0 failures on the clean tree. Owners, in the same order:
`check-layers`, `check-layers`, `check-deps`, `check-unsafe`, `check-generated`, `check-contracts`,
`check-stack`.

**GATE-WS-04** (TARGET; claim Performance; M0): the six checks together finish in at most 60 seconds on a warm
tree, so that they are run and not skipped. "Warm" means `xtask` is already built and the operating system's
file cache holds the tree. Budget shares (this table is the one authority; each check's bead cites its line):
`check-layers` and `check-deps` 25 s together, split as 10 s for the rules of BD-003 (including the one resolved
`cargo metadata` read per workspace that every `check-deps` rule shares), 7 s for the suite rules of N34-03
(which add the `--all-features` resolution), 5 s for the JSON-library guard of N34-04 (one `cargo tree` per
binary target) and 3 s for the auditor rules and shared-source scan of N34-25; `check-unsafe` 5 s,
`check-generated` 10 s, `check-contracts` 10 s, `check-stack` 10 s. The shares sum to the 60 s of the gate, so a
check that exceeds its share is reported by name even when the total still passes. Each report carries
`elapsed_ms`.

## Acceptance criteria

- [ ] INV-WS-05: the test `exactly_six_subcommands` passes, and adding a seventh entry to the command table
      makes it fail (the test compares the set of names, not only the count).
- [ ] Plant 5 of GATE-WS-01: changing one byte of a generated schema file (`schemas/frob.*.json`) fails
      `check-generated` with `gen.differs` and exit 2, and no other check reports anything on that scratch copy.
- [ ] On the clean tree the hand-written schemas under `schemas/registries/`, `schemas/demo.schema.json` and
      `schemas/contract.schema.json` raise no finding; a stray `schemas/frob.unknown.1.json` raises `gen.orphan`.
- [ ] `check-generated --write` followed by `check-generated` exits 0 on any tree whose registries are valid;
      hand-editing the README status block afterwards fails.
- [ ] A kernel arithmetic file with one changed character fails with `gen.digest`.
- [ ] The in-crate plant matrix on the miniature workspace shows the diagonal: 7 plants × 6 checks, 7 expected
      failures, 35 expected passes, and 6 passes on the clean copy.
- [ ] Seed done-condition, GATE-WS-01: 7 of 7 plants caught, each by the check that owns it and by no other, on
      the real tree (measured and recorded by N34-14).
- [ ] Seed done-condition, GATE-WS-04: the six checks finish within 60 s on a warm tree (measured and recorded
      by N34-14, with the per-check times).
- [ ] `xtask` is within its cap of 3 thousand lines, or the scope conversation has produced an ADR.
- [ ] Closing rule: this bead closes on its own tests; the two gate rows are written by the end-to-end run, by a
      session that did not implement the checks.

## Test plan

### Unit tests

`cargo test -p xtask`:
- `exactly_six_subcommands`: the names are exactly the six above (INV-WS-05).
- `unknown_subcommand_is_usage_error`: exit 3, the six names printed.
- `generated_schema_roundtrip`: generate into a temporary tree, compare, expect clean; flip one byte, expect
  `gen.differs` with the right line.
- `orphan_schema_file_is_finding` (a stray `schemas/frob.unknown.1.json` → `gen.orphan`; a hand-written
  `schemas/registries/x.schema.json` → no finding); `missing_generated_file_is_finding`; `marker_required`.
- `stack_lock_schema_regenerates`: the committed `schemas/frob.stack-lock.1.json` equals the output of N33a-03's
  typed model; one changed byte → `gen.differs`.
- `write_mode_touches_only_outputs`: a recursive hash of everything outside the outputs column is unchanged.
- `check_generated_detects_edit` (INV-SPARK-08, the name the invariant register row of the Spark chapter cites:
  generated code is never edited by hand; the check regenerates and compares digests): one byte changed in a
  generated kernel source under `kernels/` fails with `gen.digest` naming the file and the manifest digest; one
  byte changed in each regenerable output of this bead's table (a schema, the stack-lock schema, the admission
  document, the `RefusalCode` enum, the status block)
  fails with `gen.differs` and the first differing line; the unedited tree is clean.
- `write_mode_does_not_rewrite_digests`.
- `status_block_regenerates_byte_identical`; `status_pass_without_measured_is_invalid`.
- `plant_matrix_diagonal` (`crates/xtask/tests/plants.rs`): builds a miniature `synthetic` workspace (three core
  crates, one annex, one registry of each kind, a two-commit sibling repository), applies each of the seven
  plants with its normalization, runs the six checks in process, and asserts the 7 × 6 matrix. Plant 3 (a
  second asupersync package) exercises the rule of N34-03 and plant 7 (a stale stack lock) the rule of N33a-05,
  which is why both are prerequisites of this bead.
- `every_finding_id_has_one_owner`: the union of finding identifiers across checks has no duplicates.

### End-to-end script and logging

`scripts/e2e/workspace_checks.sh` (bead N34-14) is the script of this capability: it runs the six checks on the
clean real tree and on seven scratch copies and logs the matrix, the per-check wall times against their shares
and the 60-second total, and the two gate lines, in the structured format of STD-E2E. This bead also adds to
`scripts/e2e/status_table.sh` (created by BD-002) the steps that need `check-generated`: on the five-row
fixture, `cargo xtask check-generated --write` then `cargo xtask check-generated` (exit 0 after the invalid row
is removed, exit 2 with `gen.status-invalid` before), and a hand edit of the README block → exit 2 with
`gen.differs` and the first differing line (the first clause of GATE-GAUNT-10); each logged as a `cmd` and an
`assert` line with the report's finding identifiers.

### Known answers and negative controls

KA-784 (workspace checks: each planted violation is caught; exact; tier G0 on the host; the planted violations
are the controls). Negative controls for the harness itself: a plant applied **without** its normalization must
be reported by two checks (proving the harness can see double reporting); a no-op plant must leave all six
clean (proving the harness does not pass by failing everything). Determinism: `--json` reports are byte-identical
twice on one machine apart from `elapsed_ms`, which the comparison excludes.

## Considerations

- The guard against a seventh check is social as well as mechanical: the test can be edited. The rule is that
  such an edit names the defect class the new check would have caught and cites the owner's approval.
- Several rules are deliberately **not** checks: quantity-typed signatures and silent libraries are enforced by
  lints and conformance tests (N34-05), and the bead-log check rides inside the generated-artifact check.
- If `check-generated` nears its 10-second share, the first lever is to skip regeneration when the input digests
  equal those recorded in the output markers.
- A milestone exit is a query over the gate registry; this tool only keeps the registry's printout honest.
- The cap of 3 thousand lines with tests is the tightest in the workspace (RISK-18); generators are the largest
  part and move to the crates that own their registries only by ADR.
