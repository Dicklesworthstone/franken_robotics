## Background

`frob-core` is layer 0 of the core workspace: every other crate depends on it and it depends on almost nothing.
It holds the vocabulary that must mean the same thing everywhere: what an identity is, how strong a result is,
what a refusal looks like, and the statement that no result authorizes anything. Tier: Solid. Cap: 8 thousand
lines with tests.

The central design decision is that the rule "a result inherits the weakest claim among its inputs" is a **type**
and not prose. Reason: an optimizing agent will find any path by which a statistical result can be reported as a
proof, and a rule that lives in a style guide is such a path. Every result of the system makes exactly one of
seven kinds of claim (Proof, Known answer, Parity, Fidelity, Design comparison, Reality, Performance), with one of
four evidence classes ordered Estimated < Tested < Certified < Proved. Only a Proof claim can be Proved or
Certified; no amount of testing becomes a proof. A result built from several inputs carries a claim product whose
class is the minimum, and the type offers no conversion to a stronger class.

Smallest case that breaks the obvious alternatives ("majority" or "best input"): design A was evaluated on the
referee tier and design B on a fast tier that is still provisional. A majority or best-input rule labels their
comparison established; the product labels it provisional, which is all the evidence supports. Worked case: a
comparison of two designs consumes a kernel whose group-membership identity is Certified, a friction coefficient
from an interface-card field marked `assumed` (Estimated), and a paired study on a GPU tier under determinism
class D2 (Tested). The product is a Design comparison of class Estimated, its weakest input is the friction field
of the card, its tier is the GPU tier, and its reality scope is `no-claim`.

Rejected alternatives. (1) A class field with a setter and a review rule: the setter is the path. (2) One
constructor that takes a class argument: any crate could mint Proved. (3) Linking the sibling kernel crate for
identifier types: it depends on `serde`, and `frob-core` admits no `serde` (rule L-5 confines `serde` to named
boundary crates).

## Technical approach

Dependencies: the standard library, `fs-blake3` and `fs-qty` (two crates of the bedrock-direct list of FrankenSim
whose types are vocabulary; path dependencies at the pinned commit). No `serde`, no async runtime.

1. **Identities and hashing (`id`).** `Blake3` is a 32-byte digest with text form of 64 lower-case hexadecimal
   digits. Two hashing entry points, and no third:
   - `hash_blob(bytes) -> Blake3`: plain BLAKE3 of the bytes, for blobs addressed by hash (column files, meshes,
     weights), so that an ordinary BLAKE3 tool reproduces it (DESIGN).
   - `identity(schema: &SchemaName, canonical: &CanonicalBytes) -> Blake3`: BLAKE3 in derive-key mode with the
     schema name (for example `frob.design/1`) as the context string and the canonical bytes as key material.
     This is the binding convention for every artifact identity: the identity of an artifact is the BLAKE3 hash
     of its canonical bytes under a domain string equal to its schema name.
   `CanonicalBytes` is an opaque type with no public constructor in this bead; its only constructors are the
   canonical writer and the checked-canonical reader path. Nothing can therefore hash a file as written, or an
   in-memory rendering, into an identity. Typed identities are newtypes over `Blake3`: `DesignId`, `ModelId`,
   `SceneId`, `KernelId`, `PolicyId` (a learned or synthesized control policy, not the decision rule of N34-11),
   `EpisodeId`, each with a short text prefix and a parser. DESIGN, a closed list: `d:`, `m:`, `s:`, `k:`, `p:`,
   `e:` in that order, followed by the 64 hexadecimal digits; the parser refuses any other prefix, and the
   prefixes of the artifact-graph identifiers of N34-11 (`clm:`, `ev:` and the others it fixes) never collide with
   these, so a bare identifier names its type.
   An identity names bytes and carries no verdict: a hash identifies, and only a recorded implication licenses
   reusing a verdict.
   `SchemaName { name, major }` prints as `frob.<name>/<major>`; an identifier in the name is lower-case ASCII
   with dots and hyphens.
2. **Evidence (`evidence`).** DESIGN sketch (fixes intent, not signatures):
   ```rust
   pub enum EvidenceClass { Estimated, Tested, Certified, Proved }      // Ord: weakest first
   pub enum ClaimKind { Proof, KnownAnswer, Parity, Fidelity, DesignComparison, Reality, Performance }
   pub struct Evidence<K> { class: EvidenceClass, scope: Scope, assumptions: AssumptionSet,
                            receipts: Vec<ReceiptId>, flags: NoAuthorization, kind: PhantomData<K> }  // all private
   pub struct ClaimProduct {
       kind: ClaimKind, class: EvidenceClass,          // minimum over inputs; no setter
       weakest: InputRef,                              // the input that set the class: content hash and field path
       scope: Scope,                                   // design family, world family, quantifier order, horizon, validity region
       tier: TierMeet, determinism: DetClass,          // weakest among inputs
       reality: RealityScope,                          // NoClaim, or the calibrated family a band was issued for
       conditions: FlagSet,                            // union: tier-sensitive, controller-sensitive, model-conditional
       inputs: Vec<InputRef>, authorization: NoAuthorization }
   impl ClaimProduct { pub fn combine(kind: ClaimKind, parts: &[ClaimProduct]) -> Result<ClaimProduct, Refusal>; }
   ```
   `combine` is the only way to build a product from parts:
   1. An empty `parts` is an error of the caller (a typed `Refusal`); leaves are built by the constructors below.
   2. `class` = min over parts; if `kind` is not `Proof`, the result is further capped at `Tested`.
   3. `weakest` = the part attaining the minimum; ties break by lowest content hash, then field path, so the
      answer is deterministic.
   4. `determinism` = the weakest of D0 > D1 > D2 > D3 > D4 (D0 exact; D1 bitwise across backends; D2 bitwise
      per backend and independent of batch composition; D3 inside a tolerance with decision agreement; D4
      unspecified, never evidence).
   5. `tier` = the meet in the order `static` (no physics) above `referee` above the fast tiers `batch-cpu`,
      `gpu-cuda`, `gpu-metal`, which are mutually incomparable; the meet of two different fast tiers is the set
      of both, printed `batch-cpu+gpu-metal` (DESIGN; the promotion ladder that orders tiers for trust belongs to
      the dynamics chapter, and this type only refuses to round upward).
   6. `scope` = intersection; a mismatch of quantifier order between parts is a refusal (FROB-REF-881: evidence
      establishes a different quantifier prefix than the query's), never a silent weakening.
   7. `reality` = `NoClaim` unless every part names the same calibrated family; `conditions` = union, and a
      consumer cannot drop a condition; `inputs` = the sorted, de-duplicated union.
   Leaf constructors: `estimated(..)` is public (everything that is not a checker, a test harness or a study
   creates Estimated; an actuator, interface or material card creates one leaf per field from that field's
   provenance, so a single assumed number is visible as the weakest input of everything built on it).
   `tested(..)` and the raw Proof-marker constructor are hidden doorway functions marked `#[deprecated]` with a
   note naming the only crates that may call them (the conformance harness and the study runner for Tested;
   `frob-lemma` for Proof evidence of class Certified or Proved). The workspace lint table denies `deprecated`;
   the lint-table check (N34-07) fails on any `allow(deprecated)` outside the listed call sites.
3. **Flags (`auth`).** `False` is a unit type whose only serialization is the JSON literal `false`.
   `NoAuthorization { execution_authorized: False, hardware_safety_signoff: False, sim_to_real_certified: False }`
   has one value. `PacketAuthorization { base, fabrication_released: False }` adds the build-packet flag. No
   constructor, setter or parser yields `true`: the parser returns an error on `true` and on a missing field
   (absence is not read as false; the reader-side refusal is FROB-REF-816, and FROB-REF-833 in the auditor).
   The serialized object is spelled `flags` in a certificate bundle, `authorization` in an envelope and a build
   packet, and `no_authorization` in a verdict, a qualification receipt and a counterexample world; the three
   field names inside are the same everywhere.
4. **Refusals (`refusal`).** `Refusal { code, message, pointer, observed, required, unit, detail, affected_claims,
   retry: Never | AfterChange | Backoff, repairs: Vec<Repair> }`, repairs ranked. `detail: Option<String>` exists
   for the allocation ledger's interim codes (N35-33 rule 7): it is absent on every raise of a code under its own
   meaning and present on every interim raise, equal to the ledger request's slug or to the row's fixed
   `interim_detail` (for example FROB-REF-883 with `detail = "registration-after-outcome"`), beside the
   `pointer`, `observed` and `required` the request states; an absent `detail` is omitted from the serialized
   refusal, never written as `null` (the envelope's `refusal` object, N32a-03). Three standing rules: refuse,
   never truncate; a budget stop publishes nothing partial as a result; a misspelt parameter is a refusal, not a
   default. `RefusalCode` is an enum generated from `registries/refusals.toml` (one variant per row; the
   generated file is compared by the generated-file check), so a code that is not in the registry does not
   compile. `RefusalRegistry::load()` parses the embedded registry once at start and fails with
   `UnknownRefusalCode`, `DuplicateRefusalCode` or `ExitMismatch` when: a serialized refusal (from a worker, a
   ledger row, a verb's declared refusal list) names a code with no row; two rows share a code; a row's `exit`
   is outside the family rule. Families: 1xx design and model, 2xx numerics and integrator admission, 3xx scene,
   4xx control and estimation, 5xx learning and evaluation protocol, 6xx backend and device, 7xx budget and
   capability, 8xx evidence and protocol, 9xx internal. Exit codes of the binaries: 3 for 1xx to 5xx and for 8xx
   other than the listed codes below; 4 for 70x; 5 for 72x and 73x and for a listed capability code; 6 for 6xx;
   7 for conflicts; 9 for integrity faults and 9xx; 1 is never emitted on purpose. Codes are never reused.
   Every row states `exit`, and the loader checks that it equals the exit of the row's sub-family under the
   registry's **exit rule**, which is data: the `[exit_rule]` table of `registries/refusals.toml` (completed and
   owned by N35-33), one entry per range with its exit, and three exception lists that override the range for
   the codes they name, whatever the family: `conflict` (exit 7: 803, 804 and 809, and 112, a stale parent in a
   design patch, which lies in `1xx`), `integrity` (exit 9: 810) and `capability` (exit 5: 840, an `8xx` code
   that reports a missing scope or capability). A code is in at most one list and a listed code must exist in the
   registry; either violation fails the load. The loader first
   checks the `[exit_rule]` table against the fixed exit table of the surface (the one the exit-code bead N32a-03
   states), which the data may complete but never contradict: 1xx to 5xx → 3; 6xx → 6; 70x → 4; 72x and 73x → 5;
   8xx → 3; the three lists override the range for their codes; 9xx → 9, with `retry = "never"`. The `7xx` decades that table does not name
   (71x, 74x to 79x) get their exit only from an `[exit_rule]` entry (N35-33 enters 74x → 4, 76x → 4 and
   79x → 5), and a code in a decade with no entry does not load. `ExitMismatch` names the row and the rule entry
   for each of: an `[exit_rule]` entry that contradicts the fixed table; a row whose `exit` differs from its
   range's; a row in a range with no entry. In particular a `9xx` row with exit 3 does not load: `9xx` stays the
   internal, integrity family. DESIGN (an earlier wording here hard-coded the rule and let a row in an unnamed
   `7xx` decade choose any exit in {3, 4, 5, 6, 7}, against N35-33's rule that a `7xx` code's exit is fixed by
   its decade).
5. **Registry reader (`registry::toml`, N34p2-01).** The strict reader of the TOML subset (tables and arrays of
   tables, dotted headers, basic strings, integers, booleans, arrays, inline tables, `#` comments; no dotted keys
   on the left of `=`, literal or multi-line strings, floats or dates) is specified, built and tested in
   N34p2-01, which creates this crate; this bead adds no second reader. The refusal-registry loader of item 4 is
   written on it with its `Fields` helper, so a duplicate key, an unknown key for the row type, or a construct
   outside the subset is an error with line and column. `xtask` uses the same reader for registries,
   `contract.toml`, the stack lock and this repository's manifests, and no TOML library enters `frob-core` or
   `xtask` (rule L-5).
6. **Quantities (`qty`).** One module re-exports a closed alias set of `fs-qty` quantity types (the quantities
   the algebra, design, actuator, dynamics, family and contact chapters use; at most 64 aliases, TARGET). No
   other crate except the airlock imports `fs_qty` by name. If the units escape hatch opens, this module
   re-exports `frob-units` instead and nothing else changes.

Determinism class D0 throughout. The crate prints nothing (rule L-7).

## Acceptance criteria

- [ ] An unknown refusal code is a load-time error: a registry fixture whose verb row names `FROB-REF-999` makes
      `RefusalRegistry::load` return `UnknownRefusalCode` (seed done-condition).
- [ ] Converting a claim product to one of its factors fails to compile (seed done-condition): doctests marked
      `compile_fail` with pinned error codes for `From<ClaimProduct> for Evidence<_>`, for a setter of `class`,
      and for a public constructor that takes a class.
- [ ] A flag has no setter (seed done-condition): `compile_fail` doctests for assigning a `bool` to a flag field
      and for constructing `False` from `true`; parsing `{"execution_authorized": true, …}` and an object with a
      field missing both return errors.
- [ ] `combine` over 10⁴ seeded random part sets returns class = min, determinism = weakest, conditions = union;
      no public function returns a class above the minimum of its inputs.
- [ ] `identity` under two different schema names gives two different digests for the same canonical bytes.
- [ ] `cargo tree -p frob-core` shows `fs-blake3` and `fs-qty` and no `serde`; `CONTRACT.md` has its ten sections
      (purpose, inputs, outputs, invariants, refusals, determinism class, evidence class of outputs, validity
      domain, oracles, known gaps).

## Test plan

### Unit tests

`cargo test -p frob-core` (no mocks; registry fixtures are `synthetic` files):
- `class_order`: Estimated < Tested < Certified < Proved.
- `combine_worked_case`: {Certified kernel, Estimated card field, Tested D2 GPU study} as a Design comparison →
  class Estimated, weakest = the card field's reference, determinism D2, reality NoClaim.
- `combine_caps_non_proof_at_tested`: two Certified parts under kind KnownAnswer → Tested.
- `combine_exact_over_estimated_is_estimated` (known answer KA-221: an exact argument over an Estimated material
  card is Estimated).
- `combine_quantifier_mismatch_refuses`: parts with prefixes ∀world ∃policy and ∃policy ∀world → FROB-REF-881.
- `combine_is_order_independent` (property): any permutation of parts gives equal products.
- `conditions_cannot_be_dropped` (property): the result's flag set contains every part's.
- `tier_meet_of_two_fast_tiers_is_both`; `static_is_neutral`.
- `flags_serialize_three_false`: the only serialization is the three `false` fields.
- `flags_parse_rejects_true_and_missing` (known answer KA-828).
- `registry_duplicate_code_fails`; `registry_exit_family_rule` (on a `synthetic` registry whose `[exit_rule]`
  has 74x → 4: a 70x row with exit 3 fails; a `9xx` row with exit 3 fails; a 740 row with exit 4 loads and with
  exit 5 fails; a planted 77x row fails because no entry covers its decade; an `[exit_rule]` entry 9xx → 3 or
  6xx → 4 fails as contradicting the fixed table; 803 listed under `conflict` loads with exit 7, and an 8xx row
  with exit 7 that is not listed fails; 112 listed under `conflict` loads with exit 7 and with exit 3 fails; 810
  listed under `integrity` loads with exit 9; 840 listed under `capability` loads with exit 5 and with exit 3
  fails, and an unlisted 8xx row with exit 5 fails; a code listed under both `conflict` and `capability` fails;
  a listed code with no row fails);
  `refusal_detail_is_optional` (a refusal without `detail` serializes with no `detail` member and reads back
  equal; one with `detail = "registration-after-outcome"` round-trips with it);
  `registry_unknown_row_key_is_error` (a refusal row with `exti = 3` → `UnknownKey` naming `exti` with its line
  and column, through the reader's `Fields`). The reader's own tests (`toml_duplicate_key_is_error`,
  `toml_outside_subset_is_error_with_position`, `toml_reads_a_manifest` and the rest) are N34p2-01's.
- `blake3_empty_blob`: `hash_blob(b"")` =
  `af1349b9f5f9a1a6a0404dea36dcc9499bcb25c9adc112b7cc9a93cae41f3262`.
- `id_text_roundtrip` (property): print then parse is the identity for every identity type; a wrong prefix fails.

### End-to-end script and logging

`frob-core` has no verb of its own. Its behaviour is observed from the user's side by the envelope tests of the
verb skeleton (BD-022) and by the gate script of the claim product and flags (N12-11), which log the envelope's
`evidence` block (claim, class, tier, determinism, identities, seed) for every command through the shared helper
of STD-E2E. This bead's own evidence is the `cargo test -p frob-core` transcript with the doctest count.

### Known answers and negative controls

KA-221 (class of a combined result is the minimum of its inputs), KA-828 (a flag set to `true` is refused; a
removed field is also refused), KA-829 (the product of {Tested on the referee, Tested and provisional on a fast
tier} is provisional). Counterexample protected: CX-109 (an exact argument yields a Certified result: false over
an Estimated card). Negative controls: a scratch build in which `class` gains a setter must make the
compile-fail doctest fail to fail; a `combine` mutant that takes the maximum is caught by the random-set
property. Determinism lanes: twice on one machine; debug and release; Linux and macOS; identical digests and
products (D0).

## Considerations

- INV-NUM-06 (the class of a result is the weakest class among what produced it) is enforced here by type, with
  the compile-fail tests for any conversion upward.
- The `fs-qty` coupling (RISK-21): `fs-qty` enables an incomplete nightly compiler feature. The re-export module
  is the cheap side of the escape hatch; OPEN-SUITE-4 (alias set, at most 64; owner: Marrow lead) defaults to the
  quantities those chapters use.
- OPEN-SUITE-6: whether computational crates take the async runtime's context or a capability-free token from
  this crate. Default: the runtime's context wherever cancellation is observed; this crate stays free of it.
- The doorway mechanism depends on every crate inheriting the workspace lint table; the lint-table scan is part
  of the mechanism.
- The tier meet is deliberately weaker than a total order; if the dynamics chapter fixes a total trust order the
  type narrows by ADR.
- The refusal registry starts with no 9xx row. This bead allocates no number: numbers are filed through the
  allocation ledger `registries/refusal_allocations.toml` (N35-33, with the owner's ruling on the full `8xx`
  family in N35x-01 and the second round in N35x-02), and the chapter's registry bead governs each row's meaning
  and repairs. The first `9xx` rows requested there are integrity faults, each exit 9 and `retry = "never"` by
  the family rule above: a device result that fails receipt validation at the agent boundary (raised by N21a-02
  at M0 and N21c-28 at M2), a scene pack whose content does not match its identity, and the panic caught at the
  top of `main` (N32a-03). A proposal to use `9xx` as an "evidence and protocol, continued" block with exit 3
  cannot load (`ExitMismatch`), which is the mechanical form of the family table.
