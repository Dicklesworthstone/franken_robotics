## Background

FrankenRobotics identifies every artifact by the hash of its canonical bytes. The format registry
(`registries/formats.toml`) gives each of thirteen formats one identifier, one schema name with a major version,
one owner crate and one canonical encoding; everything else is a view. Seven of the thirteen exist at the first
CPU milestone, M1: the design, the module, the card, the task, the mission, the run and the certificate bundle.
This seed bead makes the registry true for those seven: each row is confirmed against the crate that landed,
each owner's reader and writer is put through the shared round-trip harness, and the gate is recorded for them.

**GATE-WS-02** (TARGET; claim Known answer; due at M1 for the formats that exist, then at each new format;
complete at M5): for each format, 10,000 seeded round trips canonical → value → canonical with zero byte
differences; where a view exists, 10,000 round trips view → canonical → view with zero differences; every one of
10,000 single-byte mutations either fails to parse or changes the identity; and each reader survives 10⁷ fuzz
executions with zero panics before the format's first release. Negative control: a reader built with key-order
canonicalization disabled must fail the first clause.

Why this is one bead and not seven notes in seven crates: the property is the same for every format, the
failure it prevents (two artifacts with one identity, or one artifact with two) is a workspace-level failure,
and a registry row is a promise that only a recorded measurement keeps. Tier: Solid. The M1 release (the CPU
studio preview) is the first release of all seven formats, so the fuzz clause is due here for each.

## Scope

In: the seven registry rows in final form; the harness wiring in each owner's conformance test (generator,
clause tests, refusal tests, fuzz target); the adapter that lets the standard-library-only bundle reader be
tested without depending on the core; the gate-size run and its seven records; the second-parser plant.
Out: the formats themselves (their owners' beads: BD-054 and BD-057 for the design and its view, BD-060, BD-069,
BD-122, BD-126, BD-090, BD-026 with BD-027 and BD-133 for the bundle); the harness (N34-22); the registry types
(N34-19); the user-side script (N34-23); the remaining six formats (BD-410).

## Technical approach

**The seven rows** (the registry's content for these formats; producers and consumers are part of each row):

| Identifier | Ext. | Schema | Owner | Produced by | Consumed by | Canonical form and views |
|---|---|---|---|---|---|---|
| `FMT-FBOT` | `.fbot` | `frob.design/1` | `frob-design` | Agents and people; typed edits; importers in `frob-io`; proposals from `frob-opt`, `frob-synth`, `frob-mission` | `frob-model`, `frob-analyze`, exporters in `frob-io`, the viewer | Canonical JSON. View: an S-expression text, lossless in both directions and optional |
| `FMT-FMODULE` | `.fmodule` | `frob.module/1` | `frob-design` | Authored; extracted from a design by a typed edit | `frob-design` (composition), `frob-model` | Canonical. Carries its port contract |
| `FMT-FCARD` | `.fcard` | `frob.card/1` | `frob-actuate` | Authored from data sheets with per-field provenance; `frob-ground` as a new revision with fitted values | `frob-actuate`, `frob-model`, `frob-arena` (randomization from stated uncertainty), `frob-foundry` | Canonical. Kinds, a closed list: actuator, transmission, battery, interface, material, soil, optical, sensor, payload |
| `FMT-FTASK` | `.ftask` | `frob.task/1` | `frob-spec` | Authored; fixtures in `frob-arena` | `frob-learn`, `frob-arena`, `frob-opt`, `frob-nemesis` | Canonical |
| `FMT-FMISSION` | `.fmission` | `frob.mission/1` | `frob-spec` | Agents | `frob-mission`, its only evaluator; `frob-lemma` | Canonical |
| `FMT-FRUN` | `.frun` | `frob.run/1` | `frob-chronicle` | `frob-chronicle`, from the step's telemetry buffers | Replay, `frob-autopsy`, `frob-ground`, `frob-arena`, the viewer | Canonical: a manifest and chunked binary columns. Views: array files, summaries, stills |
| `FMT-FROBCERT` | `.frobcert` | `frob.cert/1` | `frob-cert` (schema and reader) | `frob-lemma` (the writer, written against the schema and sharing no code with the reader) | `frob-cert` and `frob-verify`; `frob-verbs` | Canonical. One file, self-contained |

**Per-format decisions this bead records in the rows** (registry rule 4: each owner names one rule for
floating-point fields that bear identity and tests it):

| Format | Number rule | View kind | Notes for the harness |
|---|---|---|---|
| Design, module | Exact: a quantity is a string of an exact decimal and a unit token; the canonical decimal is the shortest that equals the exact rational, a non-terminating value is a ratio (`"1/3 m"`); angles in degrees or turns are exact rationals of a turn | Design: `lossless` (S-expression). Module: none | Constructor terms stay unexpanded; defaults are written out; generator from the archetype templates and the random valid-design generator |
| Card | Exact decimal strings with units, each field with its provenance | None | One generator per card kind; nine kinds |
| Task | Exact strings in unit-normalized predicates | None | Requirement terms, randomization blocks |
| Mission | Exact numbers as strings (rationals as `"p/q"`, reduced, positive denominator) | None | The quantifier list is ordered and is part of the identity |
| Run | Manifest: integers above 2⁵³ and tick indices as decimal strings, digests as hex; columns are binary blobs addressed by hash | `export` (array files, summaries, stills): one-way renderings | Mutations are applied to the manifest and, separately, to column bytes |
| Bundle | Rationals as reduced pairs of integer strings; no JSON number with a fraction or an exponent | None | Tested through the adapter below |

The design, mission and bundle rules are fixed by their own chapters. The card, task and run rules are the
defaults this bead proposes (DESIGN); each owner's contract confirms or replaces its rule, and a row without one
does not load.

Views are of two kinds, and the registry row says which (DESIGN): a `lossless` view is in bijection with the
canonical form and gets the gate's second clause; an `export` view is a one-way rendering, for which the second
clause does not apply and the test instead asserts that it has no identity and that offering it back as the
artifact is refused.

**Work, per format:**
1. Confirm the row against the landed crate (owner, schema name, extension, kinds); correct the registry if the
   owner's contract decided otherwise, and regenerate `schemas/`.
2. In the owner's `tests/conformance.rs`, implement the harness's `Subject` (the seeded generator of valid
   values) and add the tests `fmt_<ext>_roundtrip`, `fmt_<ext>_refusals`, a fuzz target `fmt_<ext>_read`, and
   for the design `fmt_fbot_view_roundtrip`. Commit-lane sizes: 10,000 round trips and mutations, 10⁵ fuzz
   executions.
3. For the run format, add the column clause: a single-byte change in any column file makes the chunk's content
   hash differ from the manifest's and the read refuses.
4. For the bundle: `frob-cert` depends on nothing, so it cannot implement a trait of `frob-core`. The
   conformance crate (which may depend on everything) holds the adapter: bundles are generated by `frob-lemma`'s
   writer from seeded proof objects; clause 1 is "the auditor accepts the bundle and its re-serialization equals
   the input bytes"; clause 3 is "every single-byte mutation is rejected by the auditor or changes the bundle
   hash computed by the auditor's own hash"; clause 4 fuzzes the auditor's reader.
5. Run the gate lane for the seven formats: the four clauses at full size (10⁷ fuzz executions each) and the
   negative-control build with key-order canonicalization disabled, which must fail clause 1 for each of the six
   formats written by the core's canonical writer; for the bundle the control is a `frob-lemma` writer build
   with the same defect, which the auditor must reject as not canonical.
6. Plant a second parser for one registered extension and confirm `check-contracts` fails.
7. Write seven records (format, clause counts, differences, executions, panics, control outcome, seed, commit,
   receipt). The gate's row in the registry stays partial ("7 of 13 formats") until BD-410.

## Acceptance criteria

- [ ] Seed done-condition, GATE-WS-02 for these formats: for each of the seven, 10,000 round trips with zero
      byte differences; for the design, 10,000 view round trips with zero differences; 10,000 single-byte
      mutations each refused or identity-changing; 10⁷ fuzz executions with zero panics.
- [ ] The negative control is caught for all seven (key-order canonicalization disabled fails clause 1).
- [ ] Seed done-condition: a second parser for a registered extension fails `check-contracts`
      (`fmt.second-parser`).
- [ ] Each owner's generator reaches every field of its generated schema (the harness's field-coverage check).
- [ ] A changed byte in a run's column file is refused on read with the chunk named.
- [ ] `{"b":1,"a":2}`-style respellings of an artifact of every format bind to the identity of its canonical
      spelling.
- [ ] The seven registry rows load, each with a number rule and a view kind; `schemas/` regenerates clean.
- [ ] Seven gate records exist with measured values; the status table prints the gate as partial, not passed.
- [ ] Closing rule: the records are entered by a session that did not implement the formats or the harness.

## Test plan

### Unit tests

In each owner crate (`cargo test -p <owner> --test conformance fmt_`): `fmt_fbot_roundtrip`,
`fmt_fbot_view_roundtrip`, `fmt_fbot_refusals`; `fmt_fmodule_roundtrip`, `fmt_fmodule_refusals`;
`fmt_fcard_roundtrip` (parameterized over the nine kinds), `fmt_fcard_refusals` (an unknown kind refuses);
`fmt_ftask_roundtrip`, `fmt_ftask_refusals`; `fmt_fmission_roundtrip` (quantifier order changes the identity),
`fmt_fmission_refusals`; `fmt_frun_roundtrip`, `fmt_frun_column_mutation`, `fmt_frun_export_view_has_no_identity`,
`fmt_frun_refusals`. In the conformance crate: `fmt_frobcert_roundtrip`, `fmt_frobcert_mutations`,
`fmt_frobcert_refusals` through the adapter. Every refusal test covers an unknown major version, an unknown
field at two depths and a duplicate member, with the owner's stated code.

### End-to-end script and logging

`scripts/e2e/format_registry.sh` (bead N34-23) runs the gate lane for the landed formats and exercises each
format from the user's side through `frob`; it logs per format and clause the counts, differences against 0,
fuzz executions against 10⁷, panics against 0, the control's outcome, seeds, and on failure the first failing
index and artifact, in the structured format of STD-E2E.

### Known answers and negative controls

KA-781 (the objects `{"b":1,"a":2}` and `{"a":2,"b":1}` have one identity; exact; tier G0 on the host; control: a
reader built with key-order canonicalization disabled must fail). KA-782 (the gate's statement for each format;
exact; tier G3 on the host; same control). Counterexamples seeded into the control registry against this gate:
CX-358 (hash the file as written), CX-359 (hash the in-memory value), CX-360 (the view is lossless, so hash
either form), CX-361 (tolerate unknown fields). Negative controls: the no-key-sort builds; the second parser;
the mutated column byte; an owner reader patched to ignore one unknown field. Determinism lanes: the commit lane
twice on one machine; debug and release; Linux and macOS; identical canonical bytes and identities (class D0).

## Considerations

- OPEN-WS-4 (owner: Augur lead; decided by the contract of `frob-spec`): whether `.fmission` is owned by
  `frob-spec` or by `frob-mission`. Default: `frob-spec`, because a task's requirements and a mission's
  quantified statement are written in one requirement language and a certificate about a mission must quote the
  statement exactly. If the contract decides otherwise, the row's owner changes and the tests move with it.
- The design's S-expression view has its own kill gate (fallback: JSON is the only syntax). If it fires, the
  row's view is removed and the second clause is not applicable to any M1 format; the gate does not fail for it.
- The gate lane is about seven times 10⁷ fuzz executions plus the control builds: minutes to tens of minutes of
  CPU, inside the default machine envelope, run under the envelope guard.
- A format whose owner slips past M1 is recorded as pending in the registry, and the gate's M1 statement is
  about the formats that exist; nothing here is rounded up.
- The bundle's adapter must not become a second bundle parser: it calls the auditor's reader and the writer in
  `frob-lemma` and contains no parsing of its own (the single-parser search covers the conformance crate too).
