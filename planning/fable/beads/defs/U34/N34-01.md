## Background

The repository holds more than one Cargo workspace on purpose: the core, in which unsafe code is denied and every
direct runtime dependency is a Franken foundation or the standard library, and the **annexes**, separate
workspaces with their own lockfiles for code the core's rules exclude (GPU driver bindings with registered unsafe
capsules, a Python binding, build-time symbolic derivation). The core never depends on an annex (rule L-3); backends
implement core traits. The workspace table, the forbidden-package list, the layout and the lockfile and
toolchain-file rules are N34p4-02's.

This bead builds the one place where core and annex meet: the `apps/` workspace, which links them into the
device-enabled `frob` and `frobd` binaries, with the backend registration that refuses a misconfigured set at
start. It also checks, with the annex workspaces present, that every workspace it reaches resolves `--locked` and
that a core-to-annex edge is reported by `check-deps` and by no other check. Tier: Solid.

DESIGN, with its reason: there is no binary per backend. An earlier draft of the Spark annex bead had
`apps/frob-cuda` and `apps/frob-metal`; the plan's layout links "into frob, frobd", so the backend is a feature of
those two binaries, and a script that names `frob` gets the same command surface on every host.

## Scope

In: the `apps/` workspace and its two link packages; the backend-registration entry points in `frob-cli`; the
start-time refusal `FROB-REF-601` for a misconfigured backend set; the steps of `scripts/e2e/workspace_layout.sh`
(created by N34p4-02) that build and run the core and `apps/` binaries; the `--locked` resolution of the M0
workspaces this bead reaches; the six-check ownership of the core-to-annex plant. This bead is the one statement of
the `apps/` binaries; the Spark annex policy bead N21a-01, which depends on this bead, restates none of it.
Out: the workspace table, the forbidden-package list, the layout and the lockfile, toolchain-file and directory
rules (N34p4-02); the Spark-specific policy (N21a-01): ADR-SPARK-01 as a decision record, invariant INV-SPARK-01
asserted on the core's resolved graph, the test that the Metal `block` patch is present at every root that
resolves the gateway, the fail-closed `exploratory` default for OPEN-SPARK-1 and the wording of what Spark may
claim; the toolchain-file plant (`check-stack`, N33c-08); the capsule registry and `check-unsafe` (N34-07); the
annex crates' contents (BD-015 CUDA, BD-016 Metal, BD-019 derivation, BD-301 Gymnasium adapter); the worker and
its workspace (BD-038).

## Technical approach

1. **The apps workspace.** `frob-cli` (core, layer 7) owns the logic of both binaries and exposes
   `frob_cli::main_with(backends: BackendSet) -> ExitCode` and `frobd_main_with(..)`. The core workspace builds
   `frob` and `frobd` with the CPU reference backend only. `apps/frob` and `apps/frobd` are two-line binaries
   that construct a `BackendSet` from the annex crates selected by features (`cuda`, `metal`) and call the same
   entry points; they hold no logic and are the link packages of the `link` row of N34p4-02's table. The `apps/`
   root repeats FrankenTorch's `[patch.crates-io] block` entry, because it resolves the Metal gateway and a patch
   entry is not inherited across workspaces. A device-enabled build needs no vendor toolkit at build time: the
   CUDA driver and its runtime compiler are loaded at run time. `apps/` commits its `Cargo.lock` and builds with
   `--locked` on T (N34p4-02's lockfile rule).
2. **Registration.** A backend is a value that implements the core's backend trait; registration is by name, and
   a duplicate name or a backend whose declared device family does not match the host refuses at start with a
   typed refusal, never at first use: FROB-REF-601 (device unavailable: the registered backend cannot be opened
   as declared), exit 6, with `pointer` the backend name and `observed` either `registered twice` or the declared
   family against the host's families; repairs: rebuild `apps/` with one feature per device family; run the
   core-built `frob` on the CPU reference backend. DESIGN: a backend that cannot be opened uniquely as declared
   is unavailable, so the device family's code and exit 6 apply rather than a new code. No core crate names an
   annex type.
3. **Every workspace resolves.** With the annex workspaces of BD-015, BD-016 and BD-019 present, the script's
   resolution step (N34p4-02) covers `core`, `spark-cuda`, `spark-metal`, `apps` and `derive`. `worker` (BD-038)
   and `bindings` (BD-301) join the same step when their manifests exist; a row without a manifest is logged
   `absent`, never as passed.
4. **Ownership of the core-to-annex plant.** The scratch copy in which a core crate gains a `cudarc` dependency
   (N34p4-02's plant) is run through all six checks: `check-deps` reports it and the other five exit 0.

## Acceptance criteria

- [ ] `cargo metadata --locked` succeeds in the `core`, `spark-cuda`, `spark-metal`, `apps` and `derive`
      workspaces; a row of the table without a manifest is logged `absent`.
- [ ] `apps/frob` builds with the feature `cuda` on `trj` (the Linux host with two RTX 4090 cards of 24 GB each
      and no link between them) and with the feature `metal` on the Apple-silicon Mac Studio, without a CUDA
      toolkit installed at build time (the driver and NVRTC load at run time).
- [ ] `apps/frob` built with the feature for the host's device family reports that backend and the CPU reference
      backend in `frob doctor --json`; the core-built `frob` reports the CPU reference backend only.
- [ ] A build of `apps/frob` that registers two backends under one name exits at start with a refusal envelope
      (FROB-REF-601, exit 6, `observed: "registered twice"`) before any verb runs.
- [ ] After the `apps/` build for the host, the core `Cargo.lock` still holds none of the forbidden packages of
      N34p4-02's table (the device build resolves them in `apps/Cargo.lock` only).
- [ ] The core-to-`cudarc` scratch copy fails `check-deps` and no other of the six checks.

## Test plan

### Unit tests

- `crates/frob-cli/tests/backend_set.rs` (real backends: the CPU reference backend registered twice under two
  names, no mock): `duplicate_name_refuses_at_start`; `unknown_family_refuses_at_start`;
  `cpu_only_set_lists_one_backend`.

### End-to-end script and logging

The steps this bead adds to `scripts/e2e/workspace_layout.sh` (created by N34p4-02): build the core `frob` and the
`apps/frob` for the host through the build-offload shim; run `frob doctor --json` from each and compare the backend
lists; run the duplicate-name build and assert the refusal envelope; grep the core lockfile again after the device
build; run the six checks on the core-to-`cudarc` scratch copy and assert the one owner. Each step logs through the
shared helper of STD-E2E to `target/e2e-logs/workspace_layout/<utc>.ndjson`: one `cmd` line per command with exit
code and wall time, one `assert` line per expectation with the first offending backend, package or check on
failure, the backend lists, and the `summary` line. Idempotent; scratch under
`${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}`.

### Known answers and negative controls

Known answer: the core-built `frob` lists exactly one backend, the CPU reference backend. Negative controls: the
duplicate backend name; a backend declaring a device family the host lacks; the core-to-`cudarc` edge, which a
second reporting check would turn into a failed ownership assertion. Live-dependency proof: removing the device
feature from the `apps` build removes the device backend from `frob doctor`. Determinism: the backend list is
sorted by name and identical twice on one machine.

## Considerations

- A device-enabled binary is built only from `apps/`. A script or a release recipe that builds `frob` from the
  core and expects a GPU backend gets a typed refusal naming the missing backend, never a silent CPU run.
- The `apps/` root must repeat the `block` patch at every pin move of FrankenTorch; N21a-01's test asserts it at
  every root that resolves the gateway.
- Security: the `apps/` lockfile is reviewed like the core's; committed lockfiles and `--locked` builds are the
  supply-chain rule (N34p4-02).
