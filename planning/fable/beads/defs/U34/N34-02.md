## Background

FrankenRobotics is a large program: 43 crates in seven workspaces, written by many agents in parallel. Two things
keep it reviewable. A reader must be able to find the one crate that owns any mechanism, and a tool must be able
to refuse a dependency or a crate that the design forbids. Both need the crate map as data, not as a table in a
document. This bead puts the map into the `xtask` crate (workspace tooling, layer 7, tier Solid) as one compiled
table that the six workspace checks read, and it implements the rule that the list is closed.

**ADR-WS-01 (DESIGN): the crate list is closed. A new crate is created only for a distinct dependency, a distinct
device target, or a proof boundary.**

- *A distinct dependency*: the code needs a foundation, a feature group of the airlock crate `frob-fsim`, or a
  third-party crate that its natural home must not link. `frob-foundry` is the plain case: the `structure` group
  adds 13 FrankenSim crates and about 412 thousand lines of library source beyond what M1 compiles (FACT, counted
  from the sibling's manifests on 2026-11-21), and no other crate needs them. `derive/frob-derive` is another:
  it links FrankenSymPy, which no runtime crate may link.
- *A distinct device target*: the code compiles for a different processor, runtime or host. The two `spark`
  annexes, `frob-tui` and `bindings/frob-gymnasium` are of this kind.
- *A proof boundary*: the code states or checks something whose trust must not depend on the code around it.
  `frob-cert` is the plain case. `frob-spec` is one because certificates and qualification verdicts quantify over
  its sentences. `frob-phylum` is one because "a world's trajectory does not depend on the batch it ran in" is
  tested at its boundary. `frob-nemesis` is one because the discovery lane may not read confirmation worlds, and
  a crate boundary lets the dependency check enforce that qualification code does not link the searcher.

Rejected reasons: "it is getting long" (a module is the unit of organization inside a crate) and "a different
person owns it". The rule governs additions; the 43 crates were fixed together with the subsystems, one bounded
context each, and are not re-litigated by it. The opposite pressure is handled the same way: two crates are
merged when no dependency, target or proof boundary separates them any longer. `frob-lifecycle`, the one
all-Moonshot crate, is the first candidate if its pilot fails, and its fallback is deletion, not absorption.

Rejected alternative for the data: a registry file under `registries/`. The registry list is fixed (verbs,
refusals, kernels, gates, formats, upstream, lifts, capsules, cards) and a caps file edited freely would turn a
scope decision into a one-line change nobody reviews. A compiled table changes only by a commit to `xtask` that
cites an ADR.

## Scope

In: `crates/xtask/` as a package with the library module `crate_map` (no subcommand yet); the table below; the
reader of `[package.metadata.frob]`; the closed-list rule and the ADR record fields; the non-Rust caps; tests.
Out: the checks that consume the table (`check-layers`, `check-deps` in BD-003; line counts against caps in
N34-08); the workspace manifests themselves (BD-001, N34-01).

## Technical approach

DESIGN (sketch fixes intent, not signatures), `crates/xtask/src/crate_map.rs`:

```rust
pub enum Layer { Core(u8), Annex }                       // Core(0..=7)
pub enum Reason { Original, Dependency, DeviceTarget, ProofBoundary }
pub struct CrateRow { name: &'static str, dir: &'static str, layer: Layer, rank: u8,   // rank: 1-based row in its layer
                      tiers: &'static [Tier], chapters: &'static [&'static str], cap_kloc: u16,
                      reason: Reason, adr: Option<&'static str>, conditional: Option<&'static str> }
pub const CRATE_MAP: &[CrateRow] = &[ /* the 43 rows below, then conditional rows */ ];
```

Each crate's manifest declares `[package.metadata.frob] layer = 3` and `rank = 2` (annex crates write
`layer = "annex"`), the convention FrankenSim uses for its own layers (FACT: `[package.metadata.frankensim] layer`
in `frankensim/crates/fs-exec/Cargo.toml`). Rank is the 1-based position of the crate inside its layer, in
dependency order: a crate may depend on a lower layer, or on the same layer and a smaller rank. Caps are thousands
of lines of Rust including tests. A cap is a claim about scope that can be wrong in both directions: it triggers a
scope conversation at 115% and is not an estimate of effort or schedule.

Arithmetic the table must satisfy (FACT about the table): caps per layer 0 to 7 are 28, 40, 84, 92, 98, 78, 62,
47; annexes 32; total 561 over 43 crates (39 core: 38 under `crates/` and `surface/frob-mcp`; 4 annex). Eight
core crates hold only Frontier or Moonshot content (`frob-gait`, `frob-shield`, `frob-ground`, `frob-synth`,
`frob-foundry`, `frob-lifecycle`, `frob-mission`, `frob-tui`); their caps sum to 74 and the remaining 487 is the
spine and the mixed crates. The total at the 115% trigger is 645. The tier column gives the tiers of the crate's
contents: a crate marked F or M alone contains no Solid mechanism, its mechanisms carry their pilots and kill
gates in their own beads, and nothing marked M is on a critical path. Each crate is specified by the subsystem
named in its row; this table is the index.

Rules implemented here:

1. **Closed list.** `crate_map::validate(workspace_members)` returns a finding `ADR-WS-01.unlisted-crate` for any
   member package of any workspace that has no row. A row whose directory does not exist yet is not a finding:
   crates arrive with their first implementation session.
2. **Metadata equals the row.** A member whose `[package.metadata.frob]` layer or rank is missing or differs from
   its row is a finding `map.metadata-mismatch`.
3. **Additions.** A row beyond the original 43 must carry `reason` other than `Original` and an `adr`
   identifier; the ADR names which of the three reasons applies, the edge that `check-deps` or `check-layers`
   will then enforce, and the cap. A unit test fails a row with `Reason::Original` and `adr: Some(..)` or the
   reverse.
4. **Merges and deletions.** The row is removed by a commit citing the ADR; its name goes to a `TOMBSTONES` list
   so that it is never reused.
5. **Conditional rows.** `frob-units` (layer 0, cap 3, standard library only) exists only if the toolchain
   admission gate INT-TOOLCHAIN-01 forces the units escape hatch. Its row carries
   `conditional: Some("INT-TOOLCHAIN-01")`, is not counted in the totals, and is accepted as a member only when
   the directory exists.
6. **Non-Rust caps** (constants beside the table): kernel sources in the shared dialect, 20 thousand lines; the
   viewer, 12 thousand lines of JavaScript; the Python half of the Gymnasium adapter, 1 thousand lines; the Lean
   project, no cap stated.
7. **Targets that are not crates.** `frob-fsim-worker` is a binary target of `frob-fsim`; `frob-verify` is a
   binary target of `frob-cert`. Neither has a row.

Determinism class D0: the table and its validation are pure functions of the manifests.

## Acceptance criteria

- [ ] `crates/xtask/src/crate_map.rs` holds exactly 43 counted rows; names, layers, ranks, tiers and caps equal
      the table above.
- [ ] Unit tests prove the arithmetic: per-layer sums 28, 40, 84, 92, 98, 78, 62, 47; annexes 32; total 561;
      Frontier-or-Moonshot-only sum 74; trigger ⌊561 × 1.15⌋ = 645.
- [ ] Ranks inside each layer are the contiguous integers 1..n with no repeats.
- [ ] A scratch workspace with an extra member `frob-extra` yields `ADR-WS-01.unlisted-crate`; a member whose
      manifest says `rank = 3` where the row says 2 yields `map.metadata-mismatch`.
- [ ] A row added without an ADR identifier fails the table's own unit test.
- [ ] `frob-units` absent: no finding. `frob-units` present without the conditional row: finding.
- [ ] No subcommand is added by this bead (the six-subcommand test of BD-004 stays satisfiable).

- `addition_requires_reason_and_adr`; `tombstoned_name_cannot_return`.
- `conditional_row_not_counted`.

### End-to-end script and logging

None of its own: the table is exercised from the user's side by `scripts/e2e/workspace_checks.sh` (bead N34-14),
which plants an unlisted crate as one of its extra cases and logs the finding's rule identifier, the command, exit
code and wall time through the shared helper of STD-E2E.

### Known answers and negative controls

Known answers: the nine cap sums and the total above. Counterexample protected (CX-363, "crates inside one layer
need no order"): without ranks, `frob-arena` could depend on `frob-opt` for comparison while `frob-opt` depends on
`frob-arena` for batteries, and Cargo would reject the cycle only after both were written; the table fixes arena
below opt. Negative controls: the unlisted crate; the mismatched rank; a row with a duplicated rank. Determinism:
identical findings twice on one machine and across platforms.

## Considerations

- OPEN-WS-1 (owner: Build lead; decided by the first contract of each crate): the rank order inside layers 4 and
  5, where chapters may need edges the table did not foresee. Fail-closed default: the order above; a change is an
  ADR and a table edit; a cycle is never admitted.
- OPEN-WS-2 (owner: Tether lead; decided by the frankentui admission gate INT-FTUI-01): whether `frob-tui` stays
  in the core workspace. Default: core. If frankentui does not build on the one toolchain, the remedy is an
  upstream change, with no dashboard until it lands; the row does not move to an annex by default.
- OPEN-WS-5 (owner: Cortex lead; decided by the adapter's contract): whether the Gymnasium adapter binds in
  process or across a process boundary. Default: across a process boundary with shared array files, so that no
  interpreter is ever in a `frob` binary.
- RISK-18 (crate scope caps are exceeded early; signal: a crate at 115% in `check-contracts`): a crate that
  reaches 115% stops taking new mechanisms until an ADR raises the cap with a reason or moves a mechanism out. A
  crate that ships its chapter in half its cap is not a problem to be fixed.
- RISK-33 (breadth starves the spine; signal: lines added to Frontier-only and Moonshot-only crates while a
  critical-path exit slips): the tier column is what lets a report separate the 74 from the 487.
- `xtask` itself has the smallest cap (3 thousand lines with tests). The table is data and should stay under
  150 lines.
