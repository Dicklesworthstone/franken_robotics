## Background

`check-deps` is one of the six workspace checks of the `xtask` tool. Its first rules (who may depend on what)
are written in BD-003. This bead adds the rules that come from consuming a suite of sibling repositories whose
pins and features move, and the rule that keeps frontier work out of default builds. All are DESIGN decisions
enforced by tool, because each failure they prevent is silent at build time. Tier: Solid.

- **One async runtime package per binary.** Every binary links exactly one `asupersync` package, every workspace
  resolves the same published version, and version 0.5.0 never enters a graph. FACT (2026-11-21): three siblings
  still pin 0.5.0 (frankentui's optional executor, franken_threed's runtime crate, frankenjax, optional); the
  MCP library's registry package 0.13.0 carries 0.5.0 while its source tree pins 0.6.2; FrankenTorch requires
  0.6.2; FrankenSim consumes the runtime by path. Two runtime packages in one binary mean two schedulers, two
  cancellation trees and types that do not unify. The siblings are aligned upstream (upstream work item
  FD-ASUP-01), and this rule is what notices a regression.
- **Forbidden sibling forms.** frankentui's `asupersync-executor` feature is forbidden; frankenjax and
  franken_threed are never Cargo dependencies of a graph that a `frob` binary links.
- **Airlock feature groups.** The airlock crate `frob-fsim` exposes its traits in Cargo feature groups so that a
  crate above it compiles only the closure it uses. The groups bound what a crate above the airlock may name,
  always; a group may be enabled only by the crates listed for it.
- **L-12.** Features that select a tier of ambition are named and off by default: `frontier-*` and `moonshot-*`
  features gate every Frontier and Moonshot mechanism in a mixed crate, and no default build enables one
  (invariant INV-WS-04). Reason: a moonshot must never sit on a critical path, and "it was only compiled in"
  is how one gets there.
- **Resolution with everything on.** Counterexample to "a passing build means the pins are compatible": a build
  that never enables an oracle's feature flag resolves, and the conflict appears only when the flag is first
  turned on at the oracle's milestone. The resolution check therefore runs with every optional feature group
  enabled.

## Scope

In: the five rule groups above inside `check-deps`; their data tables; unit tests and plants.
Out: the upstream alignment itself (FD-ASUP-01, FD-FMCP-01, done in the sibling repositories); the admission
gates that record the measured package counts (BD-008, BD-023); the JSON-library guard (N34-04); the gate of the
late-risk register that reads the planted second pin (the risk-register unit).

## Technical approach

Inputs: for each workspace, `cargo metadata --format-version 1 --locked` **with** the resolve graph, once with
default features and once with `--all-features`; the committed lockfiles; `franken-stack.lock`.

1. **Per-binary closure.** For every binary target in every workspace (`frob`, `frobd`, `frob-mcp`,
   `frob-verify`, `frob-fsim-worker`, `frob-tui`, `xtask`, the device-enabled `frob` and `frobd` of `apps/`),
   walk the resolve graph from its package over normal and build edges with the features that target enables,
   and collect the packages named `asupersync`.
   - `asup.duplicate`: more than one package (two versions, or one from the registry and one by path).
   - `asup.version-mismatch`: a workspace resolves a version other than the one in the stack lock's asupersync
     row, or two workspaces resolve different versions.
   - `asup.v0_5_0`: an `asupersync` package of version 0.5.0 anywhere in any lockfile.
   `frob-verify` must have none (its crate has no dependency at all).
2. **Forbidden forms.** `ftui.executor-feature`: the feature `asupersync-executor` of any frankentui package is
   enabled in any resolution. `suite.forbidden-package`: a package of frankenjax or franken_threed appears in
   the resolved graph of the core, `apps` or a `spark` annex. (A workspace may carry one only if a foundation
   row of the stack lock lists that workspace and names its admission gate; no such row exists initially, so
   the rule fails closed.)
3. **Airlock groups** (`fsim.group-not-allowed`). Data table, DESIGN, compiled from which crates the design says
   reach each group; a crate that enables a group without being listed fails, and a row changes only with the
   group's admission record:

   | Group | Default | May be enabled by |
   |---|---|---|
   | `referee`, `geometry` | on | Any core crate of layer 2 or above, through the airlock's traits |
   | `ledger` | on | `frob-chronicle`, `frob-verbs` |
   | `optimize` | off | `frob-opt`, `frob-arena`, `frob-mission` |
   | `stats` | off | `frob-nemesis`, `frob-arena`, `frob-ground`, `frob-opt`, `frob-mission` |
   | `spectral` | off | `frob-gait`, `frob-lifecycle` |
   | `actuation` | off | `frob-actuate` |
   | `structure` | off | `frob-foundry`, `frob-ground` |
   | `multiphysics` | off, gated bridge | `frob-scene` (evaluation tier only) |
   | `harness` | dev only | `frob-conformance`, as a dev-dependency |

   `fsim.default-set`: the default feature set of `frob-fsim` is exactly `referee`, `geometry`, `ledger`.
   `fsim.group-absent` is the matching runtime refusal (FROB-REF-790: a verb needs an airlock feature group that
   this binary was not built with) and is not raised by this check.
4. **Tier features (L-12, INV-WS-04).** `tier.default-on`: any feature named `frontier-*` or `moonshot-*` is in
   a `default` feature list, or is enabled by a dependency declaration inside the core workspace without an
   explicit feature of the same tier on the depending crate, or is enabled in the default-feature resolution of
   any binary. `tier.unnamed`: a crate whose crate-map tier includes F or M has a `contract.toml` feature of
   tier F or M whose name lacks the prefix.
5. **All-features resolution** (`resolve.all-features`). The `--all-features` resolution of each workspace must
   succeed; a failure reports the two requirements that conflict. Runs offline against the committed lockfile;
   when the lockfile cannot satisfy all features the finding names the package.
6. **Ownership.** A second asupersync package is a finding of this check only. The stack check records
   duplicates in the resolution receipt as data and does not fail on them, so that a planted second package is
   caught by exactly one check.

Report facts: per binary, the asupersync version linked; per workspace, the enabled airlock groups by crate.

## Acceptance criteria

- [ ] A scratch copy in which `frob-verbs` gains a dummy path dependency that pulls a second `asupersync`
      package fails with `asup.duplicate`, naming both versions and one dependency path each; `check-layers`,
      `check-stack` and the other checks stay clean on the same copy (the third plant of GATE-WS-01).
- [ ] A lockfile containing `asupersync 0.5.0` fails with `asup.v0_5_0` even when no binary links it.
- [ ] Enabling `asupersync-executor` on frankentui in `frob-tui` fails; adding an `f3d-*` package to a core crate
      fails.
- [ ] `frob-dyn` enabling `optimize` fails with `fsim.group-not-allowed`; `frob-opt` enabling it passes.
- [ ] INV-WS-04: a `frontier-gait` feature added to a `default` list fails; the same feature enabled explicitly
      by a binary's non-default feature passes.
- [ ] A planted second exact pin on one package behind an optional feature fails `resolve.all-features` and
      passes the default resolution.
- [ ] Every binary's report line shows exactly one asupersync version, equal to the stack lock's, and
      `frob-verify` shows none (INV-SUITE-02).
- [ ] The rules of this bead add at most 10 s to `check-deps` on a warm tree (TARGET, share of GATE-WS-04).

## Considerations

- RISK-03 (two asupersync versions in one build; severity High; owner: Build lead). If a surface still brings a
  second package after the upstream alignment, the MCP kill gate's first fallback moves that surface into its
  own workspace; this check then verifies the rule per workspace as before.
- The toolchain-train risk: two asupersync packages in the duplicate listing is its earliest signal besides a
  failing cell of the toolchain matrix.
- The airlock table is an initial reading of the design; the first contract of each consuming crate confirms or
  changes its rows, and each off-by-default group is admitted by its own group gate at the milestone that first
  uses it. Until a row lists a crate the check refuses it.
- franken_threed and frankenjax are named in two ways by the design (never Cargo dependencies; used behind a
  feature or in the derivation annex if admitted). The fail-closed reading is implemented: absent from every
  graph until a stack-lock row with an admission gate lists the workspace.
- Supply chain: committed lockfiles and `--locked` are assumed; a missing lockfile is a finding of the stack check.
