## Background

The canonical bytes of every artifact are written by this project's own writer, never by a JSON library. That is
the first defence against a dependency feature changing digests. This bead is the second: a guard in
`check-deps` (one of the six checks of the `xtask` tool; tier Solid) that reports, for every binary, which
version of the JSON library it links and with which **unified** feature set, and fails when either differs from
what the stack lock records.

Why a guard is needed at all. FACT (read 2026-11-21):
- Cargo unifies features across a build graph. The `preserve_order` feature of `serde_json` switches its maps
  from sorted to insertion order; a sibling records that it "leaked into every downstream consumer via feature
  unification, silently switching serde_json maps to insertion order across their whole build".
- `frankenscipy/Cargo.toml:59` enables `preserve_order` and `float_roundtrip`; FrankenSim's bedrock depends on
  FrankenSciPy, and FrankenSim's lockfile resolves `serde_json` 1.0.154 with `indexmap` among its dependencies,
  which only `preserve_order` adds.
- `fastmcp_rust/Cargo.toml:54` enables `arbitrary_precision`, which changes how numbers are represented; the MCP
  server is a member of the core graph, so that feature is in the unified set of every binary that links it.
- Sibling pins differ: `franken_textiles` and `franken_threed` pin `=1.0.151`, `fastmcp_rust` pins `=1.0.154`,
  `frankenscipy` requires 1.0.154 or later. A Cargo graph holds one version of a 1.x package, so two exact pins
  cannot share a graph.

The feature set of the JSON library in a `frob` binary is therefore decided by whichever sibling is linked, and
not by this workspace. Boundary crates (`frob-io`, `frob-verbs`, `frob-chronicle`, `frob-design`, `frob-spec`,
`surface/frob-mcp`) do link the library for foreign formats, views and transport. If its behaviour changes
under them without notice, a view changes, a foreign file is read differently, and any code that wrongly routed
a canonical byte through it changes digests. The guard makes the change loud on the commit that causes it.

Rejected alternative: pin the feature set in this workspace's manifest. A manifest can add features to the
unified set and can never remove one that a dependency turned on.

## Scope

In: every rule of `check-deps` about the JSON library, in one place: one version per binary, equal to the stack
lock's; the unified feature set per binary, equal to the stack lock's; which binaries and which crates may link
the library at all; the exact-pin conflict under the all-features resolution; the `[json_library]` table of
`franken-stack.lock` that the guard compares against, which is the only record of the library's version in the
lock; the per-binary report line; unit tests with dummy dependencies.

Out, with the bead that has it:
- the foundation fact that makes the one-version rule bite in this suite (franken_textiles and franken_threed
  pin `=1.0.151`, fastmcp_rust `=1.0.154`, FrankenSciPy needs 1.0.154 or later), its admission test
  `scripts/admission/pin_conflict_probe.sh`, the record of the siblings' pins, the plant that adds the cloth
  crate `ftx-drape` to the core workspace behind an off-by-default feature, the switch-over when the upstream
  pin is relaxed, and the `serde_json` clause of GATE-WS-06: N33c-38, which depends on this bead. Its plants
  are caught by this guard's findings and it adds no rule of its own; an earlier draft of that bead restated
  the one-version rule as a separate row of the `check-deps` table and recorded the version in the lock as a
  bare key, and both are now only here;
- the canonical writer (N34-18); the four-way build of the conformance binary and the golden corpus, which
  prove the writer is immune (N34-21); the stack lock's other rows, its schema and parser, and the receipt
  (BD-001, N33a-03, N33a-04); the cloth oracle's worker-process posture (N33c-28).

## Technical approach

1. **Recorded expectation.** `franken-stack.lock` gains one table (DESIGN), validated by this bead through the
   hook of the stack-lock parser (N33a-03):
   ```toml
   [json_library]
   package = "serde_json"
   version = "<the single resolved version, e.g. 1.0.154>"
   allowed_in = ["frob-io", "frob-verbs", "frob-chronicle", "frob-design", "frob-spec", "frob-mcp"]

   [json_library.features]          # per binary: the unified set its own build resolves; sorted
   frob = ["arbitrary_precision", "float_roundtrip", "preserve_order", "std"]
   frob-verify = []                 # links none
   # one key per binary target of every workspace; a binary with no key is a finding
   ```
   Why per binary (DESIGN): features unify over the packages one build selects, so binaries legitimately differ
   (the auditor links no JSON library; a binary that links the MCP server carries `arbitrary_precision`; one
   that links only FrankenSim carries `preserve_order` and `float_roundtrip`), and the rule "for every binary,
   the feature set equals the stack lock" needs one expected set per binary. The values are written at the
   admission of the first sibling that links the library and change only through a pin move with a new
   resolution receipt.
2. **Per-binary facts.** For every binary target of every workspace, the features its own build resolves:
   `cargo tree -p <package> --target <triple> -e features -i serde_json --locked --offline` (feature resolution
   for that package alone, as `cargo build -p` does), giving the `serde_json` packages in its closure and the
   features enabled on each. The workspace-unified set from `cargo metadata` (BD-003's shared read) is printed
   as a fact beside it and never compared, because it over-approximates each binary. The check prints one line
   per binary: name, version, source, the count of `serde_json` packages in its closure (1, or 0 for a binary
   that links none), and the sorted features. The count is taken a second time with every optional feature
   group enabled, so that a package reached only behind an off-by-default feature is counted.
3. **Findings.**
   - `json.multiple-versions`: a binary's closure holds more than one `serde_json` package; the finding prints
     one dependency path per version.
   - `json.version-drift`: the version differs from the stack lock.
   - `json.direct-outside-boundary`: a crate that is not in `allowed_in` names `serde_json` or `serde` as a
     direct normal dependency. `serde` and `serde_json` at exact pins are allowed in the
     boundary crates only and never in a hot path; this finding catches a direct use in, for example,
     `frob-dyn` even when the binary also links a boundary crate, which `json.unlisted-binary` would not.
   - `json.feature-drift`: a binary's resolved feature set differs from its key in `[json_library.features]` in
     either direction, or a binary has no key; the finding lists the added and removed features and, for each
     added feature, one dependency path to a package that enables it.
   - `json.unlisted-binary`: a binary links the library although none of the crates in its closure is in
     `allowed_in` (`frob-verify` must link none).
   - `json.exact-pin-conflict`: with every optional feature group enabled, two packages in a workspace's graph
     state different exact requirements on `serde_json`; this is what a graph that adds the cloth oracle's
     crate to the core workspace produces, and it is reported with both requirements and their origins. Where
     the conflict makes resolution itself fail, the check reports the finding from the resolver's error and
     exits non-zero; it never ends in a bare crash. The suite's own instance of this finding, the plant that
     adds `ftx-drape`, and the admission probe of the pins are N33c-38's.
4. **What the guard does not do.** It does not judge whether a feature is harmful. A drift is a prompt for a
   human decision recorded as a pin move: re-run the golden-corpus digests, write a new receipt, update the
   table. The check itself never edits the lock.
5. **Annexes.** Each workspace is checked against the same table; a workspace that legitimately differs (none at
   plan time) would carry its own `[json_library.<workspace>]` table added by ADR.

Determinism class D0. Cost: the resolve graph is already loaded by the shared read of `check-deps`; the guard
adds one `cargo tree` per binary target (about ten) and a walk, within its 5 s line of the GATE-WS-04 share
table in BD-004 (TARGET).

## Acceptance criteria

- [ ] On the clean tree the check prints one line per binary and reports exactly one `serde_json` version per
      binary (zero for `frob-verify`), equal to the stack lock's `[json_library]` version, and each binary's
      feature set equal to its key in `[json_library.features]`.
- [ ] A scratch graph that resolves another patch version than the stack lock records fails with
      `json.version-drift`; a planted direct dependency on `serde_json` in a non-boundary crate fails with
      `json.direct-outside-boundary`; a binary with two versions fails with `json.multiple-versions` and a
      dependency path to each.
- [ ] A scratch copy that adds a dummy dependency enabling `preserve_order` to a binary whose key does not list
      it fails with `json.feature-drift`, naming the feature and the dummy crate as its source; the same for a
      dummy dependency enabling `arbitrary_precision`.
- [ ] Removing a listed feature from the graph (dropping the sibling that enabled it) also fails: drift is
      reported in both directions.
- [ ] A scratch graph that adds a crate pinned to `=1.0.151` beside one pinned to `=1.0.154` fails with
      `json.exact-pin-conflict` under the all-features resolution.
- [ ] `frob-verify` links no JSON library; a plant that adds one to `frob-cert` is reported by the auditor rule
      of `check-deps` (L-9) and by `json.unlisted-binary`, both inside this one check.
- [ ] Clause of GATE-WS-05 carried here (TARGET; Known answer; M0): the guard is the detector whose signal the
      four-way feature build of N34-21 relies on; in each of the three non-baseline builds of that script the
      guard reports the planted feature.

## Test plan

### Unit tests

`cargo test -p xtask json_guard`, on `synthetic` scratch workspaces resolved by the real `cargo metadata`. The
library is represented by a local stand-in package named `serde_json` with the same feature names, so that the
tests need no network; one integration test marked for the admission lane runs against the real library in the
committed lockfile.
- `one_version_per_binary`; `two_versions_is_finding` (with one dependency path per version).
- `version_must_equal_stack_lock`: the lock says 1.0.154 and a scratch graph resolves another patch version →
  `json.version-drift`.
- `non_boundary_crate_with_serde_json_fails`: a planted direct dependency in a crate outside `allowed_in`
  (the stand-in for `frob-dyn`) → `json.direct-outside-boundary`.
- `auditor_links_none`: the stand-in for `frob-verify` has count 0; a planted dependency makes it
  `json.unlisted-binary`.
- `preserve_order_added_is_drift`; `arbitrary_precision_added_is_drift`; `float_roundtrip_removed_is_drift`.
- `drift_names_the_enabling_package`: the dependency path in the finding ends at the dummy crate.
- `per_binary_sets_differ_legitimately`: in a scratch workspace where binary A links a dummy crate enabling
  `arbitrary_precision` and binary B does not, both match their own keys and no drift is reported, although the
  workspace-unified set (printed as a fact) contains the feature; a binary with no key → `json.feature-drift`.
- `binary_without_boundary_crate_must_not_link`: a scratch binary that pulls the library through a non-boundary
  crate is `json.unlisted-binary`.
- `exact_pin_conflict_under_all_features`; `no_conflict_under_default_features` (the same graph resolves when
  the feature is off, which is the counterexample to "a passing build means the pins are compatible").
- `report_lines_sorted_by_binary`.

### End-to-end script and logging

`scripts/e2e/canonical_json.sh` (bead N34-21) runs `cargo xtask check-deps --json` in each of its four build
configurations and logs the guard's lines (binary, version, feature set), the exit code and the first differing
feature in the structured format of STD-E2E. `scripts/e2e/workspace_checks.sh` (N34-14) includes the two dummy
dependencies among its extra plants.

### Known answers and negative controls

Known answer: exactly one `serde_json` version per binary. Negative controls: the dummy dependency that enables
the two library features (the planted instance of the late-risk register, which must raise its named signal in
100 of 100 runs); the second exact pin. Live-dependency proof: removing the dummy dependency restores a clean
report. Determinism: identical report bytes twice on one machine.

## Considerations

- Risk (a dependency feature changes canonical bytes: a sibling that enters the build graph switches the JSON
  library to insertion-ordered maps or to another number representation, and digests of unchanged artifacts
  move; severity High; owner: Workspace lead). Earliest signal: this guard's `json.feature-drift`, or a golden
  digest that changes with no change to its artifact. Mitigation: canonical bytes come only from this project's
  writer; the four-way build; the stack lock records the feature set.
- Risk (an exact version pin in a sibling blocks an oracle; severity Medium; owner: Suite lead): the oracle runs
  as a worker process in its own workspace, and the pin move is an upstream work item in the sibling.
- The guard reads the resolver's view; it cannot see a feature enabled only for a build script on another host.
  The four-way build covers behaviour, the guard covers configuration.
- The `[json_library]` table is this bead's addition to the stack lock's format; the stack check treats an
  unknown table as an error, so both land together.
