## Background

The crates of the core are stacked in layers 0 to 7, and a crate may depend only on lower crates (rule L-1). Some
services live high in the stack and are needed low in it: a layer-5 crate that forks a recorded run needs the
telemetry store of layer 6; a layer-3 step needs to know whether its job was cancelled, which only the daemon at
layer 7 knows. Rule L-10 is how that is done without an upward edge:

**L-10 (DESIGN).** A lower crate reaches a service that lives above it only through a trait it defines itself,
as backends do under rule L-3 (the core never depends on an annex; backends implement core traits). The standing
inversions are five:

| # | Trait | Defined in | Implemented or supplied by |
|---|---|---|---|
| 1 | The device backend | `frob-kernels` (trait `KernelBackend`, bead BD-014); the layer rule's text says `frob-dyn` | The annex crates (`spark/frob-spark-cuda`, `spark/frob-spark-metal`) |
| 2 | The evidence sink | `frob-core` | `frob-chronicle` |
| 3 | The trace source | `frob-core` | `frob-chronicle` |
| 4 | The job context, for cancellation and budgets | `frob-core` | The daemon (`frob-verbs` job engine, `frob-cli`) |
| 5 | The certificate sink | `frob-core` | `frob-lemma` |

This is what lets a layer-5 crate such as `frob-autopsy` fork a recorded run without depending on layer 6.
Rejected alternatives: (1) move the stores down the stack (the telemetry and job stores bring the ledger and the
async runtime into every low crate); (2) allow named upward edges (a cycle is never admitted, and an exception
list for edges is how layering erodes); (3) callbacks as boxed closures passed ad hoc (no register, so nobody can
say how many inversions exist).

The same rule serves the two-planes convention (rule L-11): computation and decision are separate. A kernel can
be replayed without the policy that chose to run it, and a policy can be replaced without touching a digest. A
trait defined low and implemented high is the only door through which a decision made above reaches a
computation below.

This bead writes traits 2 to 5 in `frob-core` (layer 0, tier Solid) and the register that the layer check reads.

## Scope

In: `frob_core::ports` with the four traits, their small data types, a null implementation of each for tests of
lower crates, and the marker convention; `crates/xtask/src/inversions.rs`, the register of the five.
Out: the device-backend trait (trait 1, owned by the kernel and dynamics beads); the implementations
(`frob-chronicle` for 2 and 3, the daemon for 4, `frob-lemma` for 5); the enforcement in `check-layers` (BD-003);
the `Memo` trait of the memo graph, which is declared in `frob-core` by its own bead and is registered here only
if a crate below its implementor comes to need it.

## Technical approach

```rust
// DESIGN sketch: fixes intent, not signatures. Module frob_core::ports. Each trait carries the marker line.

// frob:inversion evidence-sink
pub trait EvidenceSink: Send + Sync {
    /// Record one evidence item; returns its content-derived identifier. Never blocks a hot loop: callers
    /// hand over a record per result or per chunk, not per step.
    fn record(&self, item: EvidenceRecord<'_>) -> Result<EvidenceId, Refusal>;
}
// frob:inversion trace-source
pub trait TraceSource: Send + Sync {
    /// A committed snapshot of one world at or before `tick`, with its state digest and determinism class.
    fn snapshot(&self, run: RunRef, world: WorldAddr, tick: Tick) -> Result<SnapshotRef, Refusal>;
    /// Committed columns of one stream over a tick range, in fixed logical chunks.
    fn columns(&self, run: RunRef, world: WorldAddr, stream: StreamRef, range: TickRange)
        -> Result<ColumnCursor<'_>, Refusal>;
}
// frob:inversion job-context
pub trait JobContext: Send + Sync {
    fn checkpoint(&self) -> Result<(), Cancelled>;      // cancellation is observed here, at safe boundaries
    fn budget(&self) -> BudgetView;                     // remaining wall, CPU-core, device and checker seconds
    fn charge(&self, cost: Cost) -> Result<(), Refusal>;   // budget exhausted: stop at a safe boundary
    fn trace_id(&self) -> TraceId;
}
// frob:inversion certificate-sink
pub trait CertificateSink: Send + Sync {
    /// Hand a plain proof object to the bundle writer; returns the bundle hash once the offline checker accepted.
    fn submit(&self, proof: ProofObjectRef<'_>) -> Result<BundleRef, Refusal>;
}
```

Rules:

1. **Small, typed and synchronous.** A port trait takes and returns values of `frob-core` types only (identities,
   quantities, refusals). It names no async runtime type, so `frob-core` stays free of the runtime; an
   implementation may bridge to the runtime's context above.
2. **Refusals pass through unchanged.** A port never converts a refusal of the service into success with a
   default. `checkpoint` returning `Cancelled` is a request to drain and finalize, not an error to log and
   ignore; a budget stop publishes nothing partial as a result.
3. **Null implementations for tests.** `ports::null::{NullEvidence, NullTrace, FixedJob, NullCertificates}` are
   real implementations with defined behaviour (record nothing and return the content-derived identifier; refuse
   every trace request with a typed refusal; a job context with a fixed budget and a flag a test can raise;
   refuse every certificate). They are labelled `synthetic` in any evidence they touch. They are not mocks of a
   store: they are the defined behaviour of "no store attached", which a CPU-only verb run with no daemon uses.
4. **The register.** `inversions.rs` lists one row per inversion: identifier, trait path, defining crate,
   allowed implementing crates, and its authority: `standing` (one of the five inversions rule L-10 names) or
   `adr` (the path of the ADR that admitted it). At M0 it has the five standing rows. The layer check
   (BD-003) verifies that each marker line `// frob:inversion <id>` in the tree corresponds to a row, that the
   trait is defined in the row's crate, that every `impl <Trait> for` in the workspace lies in an allowed crate,
   that there are exactly five `standing` rows, and that every other row names an `adr` file that exists
   (`L-10.inversion-without-adr`). A further inversion is a table edit with an ADR, visible in review. Rows
   already planned by later beads: `restorable` and `energy-sink` (N16a-01, M1) and `controller`,
   `action-filter`, `state-source` (N22a-01, M1), all under ADR-WS-05; `member-sizer` (N34x-01, M3) under
   ADR-WS-04. The row format is fixed here at M0 so that those beads add rows and do not change the format.
5. **No policy below layer 4.** No type in `frob_core::ports` chooses what to run: there is no scheduler, no
   memo policy, no estimator. A request for one of those in a port is a design error against rule L-11.

Evidence and ledger: the evidence sink is the only way a crate below layer 6 writes to the ledger; each record
carries the claim kind, the evidence class, the determinism class, the identities of its inputs and the seed.

## Acceptance criteria

- [ ] The four traits exist in `frob_core::ports`, each preceded by its marker line; the register has five rows,
      all `standing`, in the row format above (with the `adr` authority field that later rows use).
- [ ] A scratch crate at layer 5 that depends only on `frob-core` compiles a function taking `&dyn TraceSource`
      and passes `check-layers`; the same crate with a direct dependency on `frob-chronicle` fails it.
- [ ] An `impl EvidenceSink for X` planted in `frob-control` (not an allowed implementor) fails `check-layers`
      with rule `L-10.unlisted-implementor`; a marker with an unknown identifier fails with
      `L-10.unregistered-inversion`.
- [ ] `FixedJob` with its flag raised makes `checkpoint` return `Cancelled`; with a zero budget `charge` returns
      the budget refusal (FROB-REF-702: budget exhausted during a run; stopped at a safe boundary; nothing
      partial published).
- [ ] `frob-core` gains no dependency.

## Test plan

### Unit tests

`cargo test -p frob-core ports`:
- `null_evidence_returns_content_id`: recording the same item twice returns equal identifiers.
- `null_trace_refuses_by_name`: every request returns a typed refusal, never an empty success.
- `fixed_job_cancel_is_observed_at_checkpoint`; `fixed_job_budget_stops`.
- `ports_are_object_safe`: each trait is usable as `&dyn`.
`cargo test -p xtask inversions`: `register_has_five_standing_rows` (exactly five rows are `standing`, and they
are the five of rule L-10; every other row carries an `adr`); `marker_without_row_is_finding`;
`implementor_outside_allow_list_is_finding`; `trait_defined_in_wrong_crate_is_finding`;
`row_without_adr_is_finding` (a sixth row planted with neither `standing` nor `adr`, and one whose `adr` path does
not exist, each → `L-10.inversion-without-adr`); negative control of the count: a planted sixth row marked
`standing` makes `register_has_five_standing_rows` fail (a sixth inversion must come with an ADR, not by
relabelling).

### End-to-end script and logging

`scripts/e2e/workspace_checks.sh` (bead N34-14) includes the two planted L-10 cases among its extra plants and
logs the rule identifier each raised. Cancellation through the job context is exercised end to end by the job
protocol scripts of the daemon beads (request, drain, finalize, no leaked resources).

### Known answers and negative controls

Known answer: five standing inversions exist, the ones rule L-10 names; at M0 they are the only rows, and every
row added later cites its ADR (ten rows at M1 with the five of ADR-WS-05; eleven at M3 with ADR-WS-04). Negative
controls: the unlisted implementor; the unregistered marker; the row without an ADR; a `JobContext`
implementation whose `checkpoint` always returns `Ok` must fail the cancellation test of any consumer (planted
in the consumer's test, not shipped). Determinism: the register check is D0.

## Considerations

- OPEN-SUITE-6 (owner: Tether lead; decided at the asupersync admission gate): whether computational crates take
  the async runtime's context or a capability-free token from `frob-core`. Default: the runtime's context
  wherever cancellation is observed; the `JobContext` trait is the capability-free form and is what a crate uses
  when it must not name the runtime.
- Rule L-10 places the device-backend trait in `frob-dyn` (layer 3), while the Spark chapter and the kernel
  harness bead BD-014 define the first backend trait, `KernelBackend`, in `frob-kernels` at M0. DESIGN: the
  register's first row names `frob-kernels`. Reason: it is a core crate of layer 3 ranked below `frob-dyn`
  (rank 1 against rank 3), so every crate that calls a backend may depend on it and no core crate depends on
  an annex, which is all the rule requires. If a later bead moves the trait, the row moves in the same commit;
  the layer check fails when the row and the trait's crate disagree.
- Hot loops emit no per-iteration JSON and library crates do not print (rule L-7); a sink is called per result or
  per chunk.
- Revisit if a port grows a method that returns a policy decision: that method belongs at layer 4 or above.
