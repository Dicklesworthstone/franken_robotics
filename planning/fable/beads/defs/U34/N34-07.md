## Background

The core workspace of FrankenRobotics contains no unsafe code, by lint, and plans zero exceptions: SIMD comes
from FrankenSim's safe façade crate and arenas from FrankenSim's substrate. The offline certificate checker
`frob-cert` goes further and forbids unsafe code at its crate root. Unsafe code exists only in the annex
workspaces (the CUDA and Metal backends), because a driver binding cannot be written without it.

DESIGN (the capsule discipline, adopted from FrankenSim; FACT: `frankensim/unsafe-capsules.json` and the
"Unsafe Code" section of `frankensim/AGENTS.md`): every unsafe region in an annex is a **capsule**: one file or
module, under 300 lines, behind a safe API, with a `SAFETY.md` beside it that states the invariants the safe API
maintains, and a row in `registries/capsules.toml`. No total is promised for the annexes: a driver binding with
pools, graphs and runtime compilation needs what it needs, and the count is reported per capsule. Unsafe is
never used to work around a lifetime, aliasing, cancellation or synchronization problem.

`check-unsafe` is the one of the six checks of the `xtask` tool (tier Solid) that enforces this. Because it is
the check that reads the lint configuration, it also verifies two other things that depend on every crate
inheriting the workspace lint table: the print lints of rule L-7, and the doorway by which only named crates may
construct evidence of a strong class.

Rejected alternatives: (1) permit unsafe in the core "with review" (the suite's own experience is that reviewed
exceptions multiply); (2) a global line budget for annex unsafe (it would be either too small for a real driver
binding or too large to mean anything; per-capsule limits are checkable).

## Scope

In: the `check-unsafe` subcommand; the schema and rules of `registries/capsules.toml`; the `SAFETY.md` section
list and its checked-in template; the lint-table inheritance rule; the doorway scan. This bead is the one
definition of the capsule row and of the `SAFETY.md` sections: the Spark annex policy bead N21a-01, which
depends on this bead, cites them and no longer carries a field list of its own. Out: the capsules themselves
(BD-015, BD-016 and the backend beads); the annex policy as a decision, with invariant INV-SPARK-01 and the
`exploratory` default (N21a-01); the choice of lints for L-6 and L-7 (N34-05); the doorway functions (BD-005)
and their one caller (BD-021).

## Technical approach

**Registry row** (`registries/capsules.toml`, DESIGN):

```toml
[[capsule]]
id = "cuda.driver-load"                  # stable
workspace = "spark-cuda"
path = "spark/frob-spark-cuda/src/capsule/driver_load.rs"
safe_api = ["DriverHandle::open", "DriverHandle::symbol"]     # the public items that wrap it
lines = 212                              # counted by the check; the row's value must equal the count
unsafe_blocks = 7
safety_doc = "spark/frob-spark-cuda/src/capsule/driver_load.SAFETY.md"
reason = "dlopen of the vendor driver and symbol lookup"
```

DESIGN (one schema): the Spark annex bead had drafted the row as `name`, `path`, `lines`, `purpose`,
`safety_doc`. The fields above are kept, because the check needs `workspace`, `safe_api` and `unsafe_blocks`;
`id` is what that draft called `name` and `reason` what it called `purpose`. A `SAFETY.md` template with the
four section headings of rule 7 is checked in at `registries/capsules.SAFETY.template.md` (DESIGN path) and is
what a new capsule copies. The first commit (BD-002) ships `registries/capsules.toml` with zero rows and a
placeholder schema under `schemas/registries/`; this bead replaces that schema with the row above, and the file
still validates with zero rows.

**Rules**, each with a stable identifier:

1. `unsafe.core-lint`: the root manifest's `[workspace.lints.rust]` table lacks `unsafe_code = "deny"`, or any
   core source file contains `#![allow(unsafe_code)]` or `#[allow(unsafe_code)]`. (A core crate that does not
   inherit the table is rule 10's `lints.not-inherited` only, so that one defect yields one finding.)
2. `unsafe.core-token`: the token `unsafe` appears as a keyword in a core source file (a tokenizer scan that
   skips strings and comments). The lint already makes this a compile error; the scan is what lets the check run
   without compiling and catches code behind a `cfg` the default build does not compile.
3. `unsafe.cert-forbid`: `crates/frob-cert/src/lib.rs` or a binary root of that crate lacks
   `#![forbid(unsafe_code)]`.
4. `capsule.unregistered`: an annex source file contains an `unsafe` block, function, trait or impl and no
   registry row's `path` covers it.
5. `capsule.over-limit`: a registered capsule file has 300 lines or more (blank and comment lines included; the
   limit is on what a reviewer must read).
6. `capsule.count-mismatch`: the row's `lines` or `unsafe_blocks` differs from the measured count (the registry
   is a record of what was reviewed; a change to the file needs the row touched in the same commit).
7. `capsule.no-safety-doc`: the `SAFETY.md` file is missing, or lacks any of its four sections: *What is
   unsafe here*, *Invariants the safe API maintains*, *Why safe Rust cannot do this*, *How it is tested*. The
   first section also states what the foreign side (the driver, the runtime) may do and is assumed to do; the
   last names the tests that exercise the boundary. (The check verifies the headings and that no section is
   empty; the content is the reviewer's.)
8. `capsule.unsafe-in-api`: an item listed in `safe_api` is itself `unsafe fn` or returns a raw pointer.
9. `capsule.stale-row`: a row whose path does not exist.
10. `lints.not-inherited`: a core crate does not inherit the workspace lint table, or overrides `deprecated`,
    `clippy::print_stdout` or `clippy::print_stderr` at crate level in a library target.
11. `doorway.unlisted-allow`: an `allow(deprecated)` attribute anywhere in the core other than at the call sites
    of the doorway table. Initial table (DESIGN, data in `xtask`): the raw constructor of Proof-claim
    evidence may be called only from the issuing module of `frob-lemma`; the constructor of Tested leaves only
    from the harness module of `frob-conformance` and the study runner of `frob-arena`. The doorway functions
    live in `frob-core`, are hidden from documentation and are marked deprecated with a note naming their
    callers; the workspace lint table denies `deprecated`, so a call from any other crate is a compile error,
    and this scan is what stops a crate from opting out of the lint.

**Report facts** (`--json`): one line per capsule with identifier, lines, unsafe blocks and the safe API; totals
per annex. No threshold is applied to the totals.

The check reads source files and manifests only; it compiles nothing. Determinism class D0.

## Acceptance criteria

- [ ] On the clean tree the check exits 0 and prints the per-capsule table.
- [ ] Plant 4 of GATE-WS-01: an `unsafe` block added to an annex file with no registry row fails with
      `capsule.unregistered` and exit 2, and no other check reports anything on that scratch copy.
- [ ] An `unsafe` block in a core crate behind `#[cfg(feature = "never")]` fails with `unsafe.core-token`.
- [ ] A capsule file grown to 300 lines fails; at 299 lines with a matching row it passes.
- [ ] A capsule whose `SAFETY.md` lacks the section *Invariants the safe API maintains* fails; so does one
      whose section is present and empty.
- [ ] The `SAFETY.md` template and the registry schema are checked in; a capsule created by copying the
      template and filling its four sections passes rule 7.
- [ ] A second `allow(deprecated)` in any core crate fails with `doorway.unlisted-allow`; the one in
      `frob-lemma`'s issuing module passes.
- [ ] A core crate without `[lints] workspace = true` fails with `lints.not-inherited`.
- [ ] The check finishes in under 5 s on a warm tree (TARGET; share of GATE-WS-04).

### End-to-end script and logging

`scripts/e2e/workspace_checks.sh` (bead N34-14) plants the unregistered capsule as plant 4 of 7 and logs, for

format of STD-E2E; on the clean tree it logs the capsule table as a `metric` line (capsule count, lines per
capsule against the limit of 300).

## Considerations

- Upstream rule: FrankenSim's own unsafe-capsule discipline binds any change this program makes in FrankenSim's
  repository; this check governs this repository only.
- If asynchronous pool calls are missing from the pinned driver binding, a capsule may declare the missing driver
  symbols itself under its `SAFETY.md`; that is a registered capsule like any other.
- The 300-line limit counts the file. A capsule that needs more is split along its safe API, not exempted.
- The doorway scan is part of the claim-product mechanism, not an extra: without it a crate could opt out of
  the workspace lints and mint strong evidence.
- Security: the capsule registry is the review surface for memory safety of the device backends; a kernel cache
  or driver load outside a capsule cannot exist in a tree that passes this check.
