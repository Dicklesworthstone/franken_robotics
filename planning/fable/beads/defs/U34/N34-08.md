## Background

A capability of FrankenRobotics counts as implemented only when eight conditions hold; the second is that its
crate ships a `CONTRACT.md` with ten sections: purpose, inputs, outputs, invariants, refusals, determinism class,
evidence class of outputs, validity domain, oracles, known gaps. DESIGN: every crate ships that file and a
`tests/conformance.rs`, and a crate becomes a dependency target only after its contract lands. Reason: a crate
that others build on before it has said what it guarantees is where incompatible assumptions accumulate.

Beside the prose sits a small machine-readable record, `contract.toml`, with the crate's layer and rank, its
determinism class, the evidence class of its outputs, its budgets, its feature flags with their tiers, and its
safe mode (what the crate does when a budget is exhausted or a calibration check fails, which is always to fall
back to its reference path or to refuse by name). This is the suite convention "contracts as code": it replaces
an ad hoc habit with something a tool can check, and it is assigned to an existing check so that adopting it
adds no seventh.

`check-contracts` is the one of the six checks of the `xtask` tool (tier Solid) that validates the record
against the manifest and the registries. It does not grade the prose. It is also where crate size is measured:
every crate has a scope cap in thousands of lines of Rust including tests; a cap triggers a scope conversation
at 115% and is not an estimate of effort. A crate that reaches 115% stops taking new mechanisms until an ADR
either raises the cap with a reason or moves a mechanism out.

Rejected alternatives: (1) grade contract prose with heuristics (a tool that scores prose invites prose written
for the tool); (2) keep budgets and safe modes only in prose (nothing could then check that a verb's declared
refusal exists or that a frontier feature names its kill gate).

## Scope

In: the `check-contracts` subcommand for the rules below; the `CONTRACT.md` template under `assets/templates/`;
the line counter. Out: the JSON-Schema file for `contract.toml` and the `demo.yaml` schema (BD-002); the
registry cross-checks for format rows, demo files and the single-owner rule (N34-09); the shadow-run and
controller records (N34-10); the release-manifest cells added to this check by the delivery chapter.

## Technical approach

**The record** (`crates/<crate>/contract.toml`, DESIGN; validated against `schemas/contract.schema.json`):

```toml
[crate]
name = "frob-contact"
layer = 3
rank = 2
plane = "compute"                 # compute | decision (layers 1 to 3 are always compute)
determinism = "D2"                # D0 | D1 | D2 | D3 | D4: the strongest class the crate claims for its outputs
evidence = "Tested"               # Estimated | Tested | Certified | Proved: class of outputs it creates as leaves
gates = ["GATE-TRAC-01"]          # gates this crate's contract cites
refusals = ["FROB-REF-121"]       # codes the crate raises

[budgets]                         # per call unless a key says otherwise; units in the key
wall_ms = 50
memory_mib = 256

[safe_mode]
on_budget = "refuse:FROB-REF-702"         # refuse:<code> | reference-path
on_calibration = "reference-path"

[features]
"frontier-film" = { tier = "F", kill = "<its kill gate>", pilot = "<its pilot record>" }   # one row per manifest feature

[api.float_ok]                    # public signatures allowed a bare float, each with a reason (rule L-6)
"buffers::DeviceView::as_f32" = "raw device buffer; its dimension is recorded in the buffer schema"
```

**Rules**, each with a stable identifier:

1. `contract.missing`: a workspace member has no `CONTRACT.md` or no `contract.toml`.
   `contract.missing-for-target`: a crate that another crate of this repository depends on lacks either file
   (same defect, reported with the dependents, because this is the rule about dependency targets).
2. `contract.section-missing`: `CONTRACT.md` lacks one of the ten level-two headings, spelled as above, or a
   section's body is empty. Order is not checked; content is not graded.
3. `contract.no-conformance-test`: `tests/conformance.rs` is missing.
4. `contract.schema`: `contract.toml` fails its schema (unknown key, wrong type, missing required key).
5. `contract.layer-mismatch`: `layer` or `rank` in the contract differs from the crate map. (The manifest's
   `[package.metadata.frob]` is compared with the crate map by the layer check, so a wrong manifest and a wrong
   contract are two defects with two owners, and one wrong file is reported once.)
6. `contract.features-mismatch`: the set of feature names in `[features]` differs from the manifest's
   `[features]` (excluding `default`); a feature of tier F or M lacks the `frontier-` or `moonshot-` prefix, or
   lacks its kill gate.
7. `contract.unknown-reference`: a code in `refusals` is absent from `registries/refusals.toml`; a gate in
   `gates` is absent from `registries/gates.toml`; a kill gate named by a feature is absent from the gate
   registry.
8. `contract.safe-mode`: `on_budget` or `on_calibration` is neither `reference-path` nor `refuse:<code>` with a
   registered code. There is no third behaviour: a crate never continues with a degraded answer under its own
   name.
9. `contract.plane`: `plane` is not one of the two words. A value that contradicts the crate's layer (a crate
   of layers 1 to 3 declaring `decision`) is rule L-11 and is reported by the layer check only, so that the
   defect has one owner.
10. `contract.float-ok`: an `[api.float_ok]` entry has an empty reason (the entry's use is tested by the crate's
    own conformance test; this check only validates the table's shape and reports the count per crate).
    `contract.determinism-evidence`: `determinism = "D4"` together with `evidence` above `Estimated`; or
    `evidence` of `Certified` or `Proved` in a crate other than those the doorway table allows to create such
    leaves (the table is data in `xtask`, written by N34-07, and read here, not copied).
11. **Line counts.** For each crate: physical lines of every `*.rs` file under the crate directory (source,
    tests, benches, examples; build output excluded). Report `lines`, `cap`, and the ratio. `cap.over-115`
    (a finding, exit 2) when lines ≥ 1.15 × cap. Between 100% and 115% the crate is listed under `facts.watch`
    with no finding. The failure is cleared by an ADR that raises the cap in the crate map or moves a mechanism
    out; there is no per-crate waiver key. Also reported, without findings: lines of generated Rust (files whose
    first line carries the generated marker), the dialect kernel sources against 20 thousand lines, the viewer's
    JavaScript against 12 thousand, the Python half of the Gymnasium adapter against 1 thousand, and the
    workspace total against 561 and its 115% trigger of 645.

Inputs: manifests, the crate map, the registries, the source tree. The check compiles nothing and runs no test.
Determinism class D0; findings sorted by (rule, crate).

**Template.** `assets/templates/CONTRACT.md` holds the ten headings with one line of guidance each (for example
under *Known gaps*: "what a caller might assume and must not"). New crates start from it.

## Acceptance criteria

- [ ] Plant 6 of GATE-WS-01: deleting the *Validity domain* section from one crate's `CONTRACT.md` fails with
      `contract.section-missing` and exit 2, and no other check reports anything on that scratch copy.
- [ ] A crate added as a dependency of another before its `CONTRACT.md` exists fails with
      `contract.missing-for-target`, naming the dependent.
- [ ] `layer = 4` in the contract of a layer-3 crate fails; a feature present in the manifest and absent from
      the contract fails; `frontier-film` renamed `film` fails.
- [ ] A refusal code that is not in the registry fails with `contract.unknown-reference`.
- [ ] `on_budget = "degrade"` fails with `contract.safe-mode`.
- [ ] A `synthetic` crate with a cap of 1 thousand lines and 1,150 lines fails with `cap.over-115`; with 1,149
      lines it is listed under `facts.watch` and passes; with 1,000 lines it is listed as at cap and passes.
- [ ] The report's workspace total equals the sum of the per-crate counts, and the cap total is 561.
- [ ] `schemas/contract.schema.json` (created by the companion-documents bead BD-002, on which this bead
      depends) lists every key this check reads. A key introduced by another bead (`plane`,
      `[api.float_ok]`, `[[replaces]]`, `[[controller]]`, and the list `verbs = [...]` of the verbs whose
      handlers a crate owns, which the verb-registry reconciliation NJL-03 reads; the `[[gate]]` declaration
      block with owner or consumer role, claim, milestone parts and threshold numbers, and for a kill gate its
      trigger, fallback and decision point, which the gate-register lint N40-09 and the kill-decision
      cross-check N40-30 read, defined by N34x-02; that block also admits the chapter-side fields the
      chapter register beads moved into it and that the lint does not compare: `criterion`, `criteria`,
      `measured_by`, `fixture`, `script`, `kill`, `notes`, `form_hash`, `strata_fixture` and `bet`, with the
      shapes N34x-02 gives them) is added to the schema file by the bead that introduces it, and a `contract.toml` that uses a key
      absent from the schema fails `contract.schema`.
- [ ] The check finishes in under 10 s on a warm tree (TARGET; share of GATE-WS-04).

## Test plan

### Unit tests

`cargo test -p xtask check_contracts`, on `synthetic` scratch workspaces:
- `ten_sections_required` (ten cases, one per removed heading); `empty_section_fails`; `extra_sections_allowed`.
- `conformance_test_required`.
- `contract_toml_schema` (unknown key; wrong type; missing `[safe_mode]`).
- `layer_rank_must_match_crate_map`; `wrong_manifest_alone_is_not_reported_here`.
- `features_must_match_manifest`; `tier_feature_needs_prefix_and_kill_gate`.
- `unknown_refusal_fails`; `unknown_gate_fails`.
- `safe_mode_values` (`reference-path`, `refuse:FROB-REF-702` pass; `degrade`, `refuse:FROB-REF-000` fail).
- `d4_with_tested_fails`; `certified_outside_doorway_crates_fails`.
- `line_count_exact`: a fixture with files of 10, 20 and 30 lines counts 60; a file under the build-output
  directory is not counted.
- `cap_thresholds`: 1,149 / 1,150 against cap 1.
- `dependency_target_needs_contract`.

### End-to-end script and logging

`scripts/e2e/workspace_checks.sh` (bead N34-14) plants the missing section as plant 6 of 7 and logs the
plant-by-check matrix. On the clean tree it logs one `metric` line per crate (lines, cap, ratio, threshold 1.15)
and the workspace total, so that the size of every crate is on record at every gate run, in the structured
format of STD-E2E.

### Known answers and negative controls

KA-784 (a contract missing a section is one of the planted violations that must be caught). Known answer of the
counter: the fixture total of 60 lines. Negative controls: the plants above; a build of the check with the
115% comparison written as `>` instead of `≥` must fail the 1,150-line case. Determinism: identical reports twice
on one machine and across platforms (line endings are counted by `\n`, so a checkout with other endings is
reported as a tree fault, not silently recounted).

## Considerations

- RISK-18 (crate scope caps are exceeded early; severity Medium; owner: Project lead). Earliest signal: a crate
  at 115% of its cap in this check. Mitigation: the scope conversation at 115%; an ADR raises the cap or moves a
  mechanism; no silent growth.
- A cap can be wrong in both directions; the report never flags a crate for being small.
- `xtask`'s own cap is 3 thousand lines and this check counts it like any other.
- The record is deliberately small. A field is added to `contract.toml` only when a check will read it.
- The delivery chapter adds release-manifest cells to this same check (each cell declares the kind of evidence
  it rests on); that work has its own gate and reuses this bead's registry loaders.
