## Background

A release of FrankenRobotics is anything a user outside the implementing swarm is told they can use. One of the
suite conventions adopted by the workspace is a **demo file linked to claims for every release path**:
`demos/<demo_id>/demo.yaml` lists the `demo_id`, the `claim_id`s it demonstrates, commands that finish in under
60 seconds on the CPU tier (TARGET), and checksums of their outputs. The rule that follows is short: no demo, no
release. A capability with no demo is not released.

What a demo is, and is not (DESIGN). A demo is evidence that a path runs: from a clean checkout, through the
`frob` binary, in under a minute, producing the bytes it says it produces. It is never evidence for the claim's
numbers, which come from the gate that measured them. Reason for the separation: a demo small enough to run in a
minute cannot carry a gate's statistics, and a gate's campaign cannot be rerun by a newcomer; conflating them
produces either slow demos nobody runs or "gates" that are demonstrations.

The static half of the rule (the file validates, its claims exist in the gate registry, every released
capability has one) is checked on every commit by `check-contracts`. `xtask` runs no physics, so the dynamic half
needs the product to be run. The code that runs one demo directory is built once, in the demo harness (N00-29:
the executor `e2e_demo_run` and its run-time rules). This bead is the script that applies it to every demo of
the tree and adds the release rule. It is the end-to-end script behind the milestone exit rule "every
demonstration runs from a clean checkout, through `frob --json` and, where the registry exposes the verb to
agents, through `frob-mcp`". Tier: Solid.

Rejected alternatives: (1) demos as prose in the README (they rot within a week); (2) checking checksums in
`xtask` (it would have to run the product); (3) allowing demo commands to call scripts (a demo then shows the
script's path, not the product's).

## Technical approach

**The file** (schema: BD-002 and N34x-03; run-time meaning and optional keys: N00-29, summarized after the
example and governed there). Example, `demos/m0-doctor/demo.yaml`:

```yaml
demo_id: m0-doctor
claim_ids:
  - "clm:<64 hex of the admission claim it demonstrates>"
commands:
  - "frob doctor --json"
  - "frob schema frob.envelope/1 --json"
checksums:
  "frob schema frob.envelope/1 --json": "b3:<digest of the canonical result>"
compare:                                   # doctor's result depends on the host (devices, caches), so no
  "frob doctor --json": ["stack_receipt"]  # checksum: the stack receipt is compared exactly instead
tier: cpu
```

Every command that does not demonstrate a refusal carries exactly one of a checksum and a `compare` list (the
static rule `demo.expectation-shape` of N34-09); `frob doctor` exits 0, or 2 on a host where a check has a
finding, and both are accepted by the executor's default.

What the executor of N00-29 does with such a file, in brief, so that the script below can be read alone (the
rules themselves, with their tests, are N00-29's): each command starts with `frob` and runs with `--json` from
the root of the checkout under test, with a fresh store in an empty scratch directory; each has a wall limit of
60 s on the CPU tier (TARGET), and a demo that names a device tier is refused unless `--tier` is given on a
host that has the device; the expected exit code is 0 or 2 unless the demo declares another for the command
(`expect_exit`, with `expect_refusal` for a refusal it demonstrates); a checksum is the BLAKE3 hash of the
canonical bytes of the command's `result` member, written `b3:…`, or, where the output is not D0 or D2, the
fields named under `compare` are compared exactly; every envelope carries its `evidence` block and, for an
exporting verb, the three no-authorization flags, all false; and a command whose verb the registry exposes to
agents is repeated as an MCP tool call over stdio with the same `result` checksum (`--mcp`, on by default when
`frob-mcp` is built). The per-command expectations (`expect_exit`, `expect_refusal`, `compare`, `expect`) are
maps keyed by the command line, as `checksums` is.

**The script** (plain shell; sources the shared helper of STD-E2E; `--only <demo_id>`, `--release <milestone>`,
`--from-clean` to clone the commit into scratch and build there):

1. Run `cargo xtask check-contracts --json`; stop if it reports a demo finding.
2. Enumerate `demos/*/demo.yaml`; for `--release`, take the release's list of paths and assert each has a demo
   (the dynamic counterpart of the static rule, so that a release cut on a stale tree is still caught).
3. For each demo: call the executor (`e2e_demo_run`, N00-29) on its directory; from the executor's log lines
   record per command the wall time against 60 s, the exit code, the checksum against its expected value, the
   claim identifiers, and the evidence block. A failure of any expectation in any demo fails the script.
4. Summarize: demos run, passed, failed; slowest command; released paths with and without a demo.

Logging (STD-E2E format) to `target/e2e-logs/demos/<utc>.ndjson` with a transcript: one `cmd` line per command
(exact command line, exit code, wall time); one `metric` line per command with `wall_s` and threshold 60; one
`assert` line per checksum with expected and observed digests and, on a mismatch, the path of the saved output
and the first differing member; the envelope's `evidence` block (claim, class, tier, determinism, identities,
seed); a `summary` line. Demo outputs are synthetic or built-in fixtures; a demo may not read a private scene.

## Acceptance criteria

- [ ] `scripts/e2e/demos.sh` on a tree with the worked example passes: each command exits with an accepted code
      (0, or 2 for `doctor` on a host with findings), each under 60 s, the checksum and the compared field match;
      the worked example passes `check-contracts` (step 1) with no demo finding.
- [ ] A demo that the executor fails (a command over 60 s; an edited checksum; a missing evidence block; an MCP
      result checksum that differs from the CLI's) fails the script, and the summary names the demo and the
      failed expectation. The executor's own acceptance on each of these cases is N00-29's.
- [ ] A demo whose command is `bash run.sh` is refused before anything runs (by the static check, step 1).
- [ ] `--release M1` fails when a path of the M1 release has no demo, naming the path.
- [ ] Every `demos/*/demo.yaml` of the tree is run, the North-Star demo directories included; none is skipped
      without a line in the summary saying why (a device tier on a host without the device).
- [ ] The runner leaves no process behind and writes only under its scratch directory and the log directory.
- [ ] From `--from-clean`, the whole M1 demo set runs inside the default machine envelope.

## Test plan

### Unit tests

`scripts/e2e/tests/demos_selftest.sh` (run by the helper's suite; real `frob` binary, `synthetic` demo
directories in a temporary tree): `passing_tree_passes`; `one_failing_demo_fails_the_script_and_is_named`;
`release_path_without_demo_fails`; `only_selects_one_demo`; `from_clean_builds_and_runs`;
`static_finding_stops_before_any_run`. The tests of the run-time rules themselves (the slow demo, the checksum
mismatch, the refusal code, the missing evidence block, the true flag, the compared-fields mode) are the
executor's self-test, `scripts/e2e/tests/demo_run_selftest.sh` of N00-29.

### End-to-end script and logging

This bead is the script, as specified. From the user's side it runs only `frob` commands taken from the demo
files and `frob-mcp` over stdio for the repeated calls (both through the executor of N00-29), and
`cargo xtask check-contracts`.

### Known answers and negative controls

Known answer: the worked example's checksum, pinned at capture time by the fresh-context session that records
the demo, not by its author. Negative controls: the script command; the missing demo for a released path; a
tree in which one demo fails (the script must fail and name it). The slow demo, the edited checksum, the true
flag and the live-dependency proof (changing the built-in fixture a demo reads changes its checksum) are
controls of the executor, in N00-29. Determinism lanes: each demo twice on one machine,
and on Linux and macOS, must give equal `result` checksums (demos are restricted to classes D0 and D2 on the
CPU tier for that reason).

## Considerations

- M0 has no release (it produces an internal admission record); the first release is the M1 studio preview, so
  the first real use of `--release` is at the M1 exit. The M0 worked example exists to prove the runner.
- 60 seconds is a TARGET on the development host; the log records the host fingerprint, and a slower host is
  reported, not excused.
- A demo that needs a device, a long campaign or sealed data is not a demo. Such evidence is cited by receipt in
  the release manifest, in the order evidence can be procured: authorable at once, pinned external comparison,
  operator or dataset, native device.
- The checksum covers `result` only (a rule of the executor, N00-29); when this script finds two runs of one
  demo with different checksums, the cause is something timing-dependent in `result`, which is a defect of that
  verb's schema and is reported as such.
- Privacy and licences: demo fixtures are built-in or generated; an asset whose licence forbids redistribution
  cannot appear in a demo.
