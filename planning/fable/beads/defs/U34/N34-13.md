## Background

FrankenRobotics consumes sibling repositories (FrankenSim and others) by path at pinned commits. A pin is a
statement of intent; what was built is a different fact, and the two have already diverged inside the suite.
FACT (2026-11-21): FrankenSim's own constellation lock pins the async runtime at 0.5.0 while its `Cargo.lock`
resolves 0.6.2 by path; the runtime's checkout had 267 modified paths; FrankenSim's checkout had 32. A result
computed against one stack must not be compared with a result computed against another as if they were the same
stack.

Two files carry the facts. `franken-stack.lock` (TOML, one row per foundation; FACT: the format follows a sibling
product's stack lock) states the intent: the one toolchain T, each foundation's posture, path, commit, features,
build environment, the crates it is confined to, its admission gate and its fallback. A **resolution receipt**
(canonical JSON, schema `frob.stack-receipt/1`, kept under `receipts/` and named by its hash) records what was
actually resolved. `check-stack` is the one of the six checks of the `xtask` tool (tier Solid) that compares the
lock, the newest receipt and the trees, classifies drift, and writes a receipt when asked.

Working rule this check serves: before a build failure is attributed to this repository, `check-stack` runs. An
off-pin sibling is classified as a fast-forward or a divergence before any remedy is proposed, and a sibling
checkout is never moved back to its pin to make a check pass. The check itself writes nothing to a sibling
checkout (invariant INV-SUITE-04: no sibling checkout is ever modified or moved by this project's tooling).

Rejected alternatives: (1) trust `Cargo.lock` alone (it does not record a path dependency's commit or whether
its tree is dirty); (2) refuse every dirty sibling (the siblings are worked on daily by other agents; a dirty
tree admits development builds, with its bytes hashed, and no gate records a pass on it); (3) let the tool
check out the pinned commit (other agents work in those checkouts).

## Scope

In: the `check-stack` subcommand in its two modes; the readers for the lock and the receipt; the drift
classifier; the receipt writer. Out: the first lock and receipt (BD-001); the admission gates that cite receipts
(the suite-consumption beads); the JSON-library table's rules (N34-04); the refusal raised when evidence from
another receipt is offered as same-stack evidence (FROB-REF-890, raised by the evidence layer).

## Technical approach

**The lock** (fields per `[[foundation]]`, DESIGN): `id` (for example `FD-FSIM`), `name`, `posture`
(`consume-path`, `consume`, and the non-linking postures), `path`, `git_rev` (40 hex), `toolchain` (the channel
in the sibling's own toolchain file at that commit), `features` (airlock groups compiled by default),
`build_env`, `confined_to`, `admission_gate`, `receipt` (hash of the receipt the row was admitted under),
`fallback`; `version` for registry rows. Top level: `toolchain = "<T>"`. Further tables: `[json_library]` and
`[auditor] stable = "<channel of the certificate checker's own toolchain file>"`. An unknown table or key is an
error.

**The receipt** (canonical JSON written by `frob-core`'s writer; no timestamp, no machine path):

```json
{"schema":"frob.stack-receipt/1","repo_rev":"<this repository's commit>","toolchain":"<T>",
 "siblings":[{"fd":"FD-FSIM","rev":"<40 hex>","dirty":false,"tree_hash":null,"features":["referee","geometry","ledger"],
              "own_lock":{"file":"constellation.lock","hash":"<BLAKE3>","agrees":false,"class":"stale-lock"}}],
 "lockfiles":[{"workspace":"core","hash":"<BLAKE3 of Cargo.lock>","packages":0,"registry":0}],
 "patches":["asupersync -> ../asupersync"],"profile_overrides":["fsqlite*: opt-level 1"],
 "build_env":{"FRANKENSIM_DEPGRAPH_SALT":"franken-robotics-dev-v1"},
 "duplicates":[],"commands":[{"argv":["cargo","tree","-d"],"exit":0,"output_hash":"<BLAKE3>"}]}
```

Receipt rules: it captures source trees, requested features, compiler channels, lockfiles and the constraints of
direct and transitive siblings in one file. When a tree is dirty the receipt hashes the tracked bytes
(`tree_hash` = the identity of the sorted list of repository-relative path and blob hash for every tracked
file). A dirty sibling admits development builds only. Identities are independent of machine paths. Every
admission record cites a receipt hash, and a result in the ledger carries the receipt hash of the binary that
produced it. `duplicates` records duplicate packages as data; this check does not fail on them (the dependency
check owns that defect).

**Drift classes**, per sibling, from read-only `git` queries (`rev-parse HEAD`, `status --porcelain`,
`merge-base --is-ancestor`, `ls-files`; run with optional index locks disabled so that even a status query
writes nothing): `on-pin` (head equals `git_rev`, clean); `stale-lock` (the pin is an ancestor of the head: a
fast-forward); `drift` with a reason: `dirty`, `retreated` (the head is an ancestor of the pin) or `diverged`.
The same three classes are applied to a sibling's own lock file (`constellation.lock`, `SUITE.lock`), which is
hashed and compared.

**Verify mode** (`cargo xtask check-stack`), findings:
1. `stack.lock-schema`; `stack.receipt-missing` (no receipt, or a row's `receipt` hash is absent from
   `receipts/`); `stack.receipt-hash` (a receipt file's name is not the hash of its bytes).
2. `stack.toolchain`: the root `rust-toolchain.toml` channel differs from the lock's `toolchain` or from the
   newest receipt's. `stack.toolchain-file`: a toolchain file other than the root's, the certificate checker's,
   or (only when the lock records the worker fallback) the worker's.
3. `stack.pin`: a row's `git_rev`, `features` or `build_env` differs from the newest receipt (the lock was
   edited without a new receipt: a stale stack lock).
4. `stack.sibling`: a sibling's head, dirty flag or `tree_hash` differs from the newest receipt; the finding
   carries the drift class and reason. Equality with a receipt that recorded a dirty tree passes.
5. `stack.lockfile`: a workspace's committed `Cargo.lock` is missing or its hash differs from the receipt.
6. `stack.patch`, `stack.profile`, `stack.env`: the root manifest's patch entries or profile overrides, or the
   build-identity environment in `.cargo/config.toml`, differ from the receipt.
Facts: every sibling's class; `gate_eligible` = every sibling `on-pin` and clean (the gate recorder refuses to
record a pass otherwise; invariant INV-SUITE-03: every recorded gate result cites a resolution receipt, and no
pass is recorded on a dirty sibling tree).

**Write mode** (`cargo xtask check-stack --write-receipt`): computes the receipt from the trees and the lock,
writes `receipts/<hash>.json`, prints the hash. It writes only inside this repository. It is run once per
admission and per pin move (the compatibility train: move the pin, write a new receipt, rerun the admission and
parity gates, relock). It never edits the lock and never touches a sibling.

Determinism class D0: a receipt computed twice on an unchanged tree is byte-identical.

## Acceptance criteria

- [ ] KA-767: a receipt computed twice on an unchanged tree is byte-identical; touching one tracked file in a
      sibling flips `dirty`, changes `tree_hash`, and verify mode fails with `stack.sibling`.
- [ ] Plant 7 of GATE-WS-01: editing one `git_rev` in `franken-stack.lock` without a new receipt fails with
      `stack.pin` and exit 2, and no other check reports anything on that scratch copy.
- [ ] A scratch copy with a changed `Cargo.lock` and no new receipt fails with `stack.lockfile`; after
      `--write-receipt` it passes.
- [ ] INV-SUITE-04: the check's test runs both modes against sibling copies on which every file and the `.git`
      directory are read-only; both modes succeed, and a recursive hash of each sibling copy is unchanged.
- [ ] A sibling whose head is a descendant of the pin is classified `stale-lock`; an ancestor, `retreated`;
      neither, `diverged`; modified tracked files, `dirty`.
- [ ] No absolute path of the machine appears in a receipt (a scan for the home directory and for a leading
      slash in every path field).
- [ ] A stray `spark/frob-spark-cuda/rust-toolchain.toml` fails with `stack.toolchain-file`.
- [ ] Verify mode finishes in under 10 s on a warm tree with the real siblings (TARGET; share of GATE-WS-04).

## Test plan

### Unit tests

`cargo test -p xtask check_stack`. Siblings are `synthetic` git repositories created by the test in a temporary
directory with real `git` (three commits, so that ancestor and descendant cases exist); no network:
- `receipt_is_deterministic`; `receipt_has_no_machine_paths`; `receipt_name_is_its_hash`.
- `drift_on_pin`; `drift_stale_lock`; `drift_retreated`; `drift_diverged`; `drift_dirty`.
- `dirty_tree_hash_changes_with_one_byte`; `dirty_equal_to_receipt_passes`.
- `lock_edit_without_receipt_fails`; `lockfile_change_without_receipt_fails`; `toolchain_mismatch_fails`.
- `stray_toolchain_file_fails`; `worker_toolchain_allowed_only_with_fallback_row`.
- `own_lock_classified`: a sibling whose own lock names an older commit of a third repository is `stale-lock`.
- `unknown_lock_table_fails`.
- `duplicates_are_recorded_not_failed`.
- `read_only_siblings_are_untouched` (INV-SUITE-04).

### End-to-end script and logging

`scripts/e2e/workspace_checks.sh` (bead N34-14) plants the stale lock as plant 7 of 7 and logs the plant-by-check
matrix. On the clean tree it logs one `metric` line per sibling (foundation identifier, revision, drift class,
dirty flag) and the receipt hash in the structured format of STD-E2E; logs carry repository-relative paths only.

### Known answers and negative controls

KA-767 (stack receipt computed twice on an unchanged tree: byte-identical; exact; tier G5 on the host; negative
control: touching one tracked file in a sibling flips `dirty`, changes `tree_hash`, and the check fails). KA-784
lists the workspace plants; the stale stack lock is the seventh plant of the gate. Negative controls: the
touched file; the edited pin; a build of the check that hashes only the head commit (ignoring dirty bytes) must
fail `dirty_tree_hash_changes_with_one_byte`. Determinism lanes: twice on one machine; Linux and macOS produce
the same receipt bytes for the same trees.

## Considerations

- RISK-23 (dirty or off-pin sibling trees make a receipt unrepeatable; severity Medium; owner: Build lead).
  Earliest signal: a drift class other than `on-pin` at a gate run. Mitigation: the receipt hashes bytes; no gate
  records a pass on a dirty tree; the compatibility train.
- OPEN-SUITE-3 (is a dirty runtime checkout acceptable for development builds between receipts?): default yes
  for development, with the tree hash in the receipt; no gate records a pass.
- A sibling's newer clean head is never rolled back locally; the remedy for `stale-lock` is a pin move with a
  new receipt, and for a stale sibling lock an upstream work item in the sibling.
- Hashing every tracked byte of a large dirty sibling costs about a second; the check does it only for dirty
  trees.
- Privacy: receipts and logs carry revisions and relative paths, never a user's directory.
