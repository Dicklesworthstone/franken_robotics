## Background

The workspace of FrankenRobotics is kept reviewable by six checks in the `xtask` tool: `check-layers`,
`check-deps`, `check-unsafe`, `check-generated`, `check-contracts`, `check-stack`. A check that nothing can fail
validates nothing, and a check that takes too long is skipped. Two gates of the workspace chapter say so with
numbers, both due at M0 (TARGET thresholds):

- **GATE-WS-01** (claim: Known answer). A deliberate upward edge, a deliberate intra-layer edge against rank, a
  second asupersync package, an unregistered capsule, an edited generated file, a contract missing a section and
  a stale stack lock are each planted in a scratch copy; each plant is caught by the check that owns it and by
  no other: 7 of 7 plants caught, 0 failures on the clean tree.
- **GATE-WS-04** (claim: Performance). The six checks together finish in at most 60 seconds on a warm tree, so
  that they are run and not skipped.

This bead is the end-to-end script that measures both from the user's side, on the real repository with the real
sibling checkouts, and records them. It is a test bead: it builds no check. Tier: Solid.

Why "and by no other" matters: if a planted upward edge also tripped the stack check (because the lockfile
changed) and the contract check, a real violation would arrive as three failures with three stories, and an
agent would fix the wrong one. One defect class, one owner, one message.

## Scope

In: `scripts/e2e/workspace_checks.sh`; the seven plants as small patch functions with their normalization; the
extra plants contributed by sibling beads (reported separately, each asserted against all six checks); timing; the
entries of GATE-WS-01 and GATE-WS-04 in the conformance crate's tier tests (N38a-02's runner), which invoke the same
six commands on the same plants; the two gate records through N38b-19's recorder.
Out: the checks themselves; the in-crate plant matrix on a miniature workspace (BD-004), which runs in the unit
suite on every commit, whereas this script runs on the real tree at gate time.

## Technical approach

The script is plain shell, sources the shared helper of STD-E2E, takes `--seed` (unused by the plants, recorded
for uniformity) and `--keep` (keep scratch copies on failure), is idempotent, and exits non-zero on any failed
assertion. Every cargo invocation goes through the build-offload shim; scratch copies live under
`${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/frob-ws-checks/`; the whole run starts under a timeout of ten minutes and a
disk preflight (the scratch copies are source-only copies of this repository, without build output).

Steps:

1. **Preflight.** Record the commit, the toolchain channel, the newest resolution receipt hash and the drift
   class of every sibling. Build `xtask` once (not timed).
2. **Clean tree.** Run each of the six checks with `--json`. Assert exit 0 and zero findings for each. Log one
   `metric` line per check with `elapsed_ms`.
3. **Warm timing (GATE-WS-04).** Run the six checks three more times back to back; the measured value is the
   median of the three totals of `elapsed_ms`, in seconds, against the threshold 60. Log the three totals, the
   median, the per-check medians against their shares (25, 5, 10, 10, 10 s), the host's hardware fingerprint,
   core count and load average.
4. **Plants (GATE-WS-01).** For each plant: make a fresh scratch copy; apply the patch; apply the plant's
   normalization; run the six checks with `--root <copy> --json`; assert that exactly the owning check exits 2
   and the other five exit 0; log the cell results and the finding identifiers.

   | # | Plant | Patch | Normalization | Owner | Expected finding |
   |---|---|---|---|---|---|
   | 1 | Upward edge | `frob-lie` gains a path dependency on `frob-design` | Regenerate the scratch lockfile offline; write a new receipt in the copy | `check-layers` | `L-1.upward` |
   | 2 | Edge against rank | `frob-arena` gains a path dependency on `frob-opt` | Same | `check-layers` | `L-1.rank` |
   | 3 | Second asupersync package | `frob-verbs` gains a path dependency on a fixture crate that depends on a second package named `asupersync` | Same | `check-deps` | `asup.duplicate` |
   | 4 | Unregistered capsule | An `unsafe` block appended to a non-capsule file of an annex | None | `check-unsafe` | `capsule.unregistered` |
   | 5 | Edited generated file | One byte changed in a generated schema file `schemas/frob.*.json` (not a hand-written schema under `schemas/registries/`) | None | `check-generated` | `gen.differs` |
   | 6 | Contract missing a section | The *Validity domain* section removed from one `CONTRACT.md` | None | `check-contracts` | `contract.section-missing` |
   | 7 | Stale stack lock | One `git_rev` changed in `franken-stack.lock` | None (no new receipt: that is the defect) | `check-stack` | `stack.pin` |

   Until the crates a plant names exist in the tree, the script substitutes the lowest and highest crates
   present in the same roles and logs the substitution; the gate is recorded only with real crates.
5. **Harness controls.** (a) Plant 1 with its lockfile regenerated but **no new receipt** must be reported by
   two checks (`check-layers` with `L-1.upward` and `check-stack` with `stack.lockfile`): the harness can see
   double reporting. (b) A no-op plant leaves all six
   clean. (c) A copy with two plants at once (1 and 6) is reported by exactly their two owners.
6. **Extra plants**, logged in a separate section and not counted in the 7 of 7: an unlisted crate (closed crate
   list) and an unregistered inversion marker and an implementor outside the allow list (rule L-10), the three
   extra plants of N34p4-01 (`check-layers`); `tokio` as a
   direct dependency of `frob-dyn` (`check-deps`, `L-5.forbidden`) and an edge `frob-lemma` → `frob-cert`
   (`check-deps`, `L-9.cert-dependent`), the two extra plants of BD-003; the plants of N33c-09 (`check-deps`,
   M0): its five plants (a path dependency that resolves asupersync 0.5.0, `frob-tui` enabling
   `ftui-runtime/asupersync-executor`, a `frob-design` dependency on `fnx-algorithms`, a normal dependency of
   `frob-core` on `franken-kernel`, a `derive/` dependency on `fj-egraph`), the plant behind the optional feature
   `cloth-oracle`, a lockfile holding an unlinked `asupersync` 0.5.0, and an `f3d-*` package or `frankenjax` in a
   core crate, each with the finding identifier N33c-09 names; a default-on `frontier-*` feature; the
   two dummy dependencies that enable JSON-library features; one crate given an extra `*.rs` file of plain lines
   that brings it to 115% of its cap (`check-contracts`, `cap.over-115`, from N34-08: the scope-cap rule of the hygiene list,
   which the hygiene test of N00-08 leaves to this check); a library `println!` and
   a bare `f64` public signature (lints and conformance tests, run here through `cargo clippy` and
   `cargo test` on the scratch copy). The extra plants are rows of one table in the script (patch function,
   contributing bead, milestone from which it runs, owning check or test, expected identifier), so that later
   beads add rows without touching the matrix: the two register cases of N16a-01 (M1), the prematurely
   promoted mechanism of N34-10 (M1), and the unlisted `MemberSizer` implementor and the register row without
   an ADR of N34x-01 (M3). A row whose milestone is not reached is logged as `not due`, never skipped silently.
   Every extra plant owned by one of the six checks is applied with the normalization of the seven and run
   through all six: it must be reported by its owning check and by no other, and the `summary` line counts the
   extra plants caught by another check (0 expected); the rows owned by a lint or a test run only that lint or
   test.
7. **Gate lines and receipt.** Write one log line each for GATE-WS-01 (measured: plants caught by their owner
   only, n of 7; clean-tree failures) and GATE-WS-04 (measured: median seconds) with thresholds, the commit, the
   receipt hash and the fingerprint. The script writes no row of `registries/gates.toml`: it runs the gates'
   entries of the conformance crate through the harness helper (`e2e_tier g0_laws GATE-WS-01`, and the tier
   named by GATE-WS-04's record for that gate; each is `FROB_TEST_SEED=<seed> cargo test -p frob-conformance
   --test <tier> -- <gate>`, which invokes the same six commands on the same plants and writes a hash-named
   receipt), logs each receipt's hash, and the recording session, which must not be the session that implemented
   the checks, enters each value with `cargo run -p frob-conformance --example record_gate -- --gate <id>
   --receipt <hash>`. A run on a tree where a sibling is not `on-pin` and clean logs the measurement and marks
   it not eligible for a pass.

Logging (the STD-E2E format): newline-delimited JSON to `target/e2e-logs/workspace_checks/<utc>.ndjson` with a
human transcript beside it; every line has `ts`, `script`, `bead`, `step`, `event`; `cmd` lines carry the exact
command line, exit code and wall time; `assert` lines carry the plant number, the check, expected and observed
exit codes and the finding identifiers, the plant's control record (its `NC-` identifier and its seed: CX-363's
plant `edge-against-rank` for plant 2, KA-784 for the others), whether it was caught and the gate, and on
failure the first unexpected finding and the path of the kept scratch copy; `metric` lines carry values with units and thresholds; the final `summary` line gives assertions
passed and failed and the gates touched. No sibling path outside the repository-relative form is logged.

## Acceptance criteria

- [ ] On the clean tree all six checks exit 0 with zero findings.
- [ ] GATE-WS-01: 7 of 7 plants are caught by the owning check and by no other (42 cells: 7 expected failures on
      the diagonal of the table above, 35 passes), and the three harness controls behave as stated.
- [ ] Every extra plant of step 6 that is due and owned by one of the six checks is reported by that check and by
      no other (the N33c-09 plants by `check-deps` alone); the summary's count of extra plants caught by another
      check is 0.
- [ ] GATE-WS-04: the median total of three warm runs is at most 60 s on the development host, recorded with
      per-check times.
- [ ] Both gate lines exist in the log with measured values, thresholds, commit, receipt hash and fingerprint.
- [ ] The script leaves the working tree and every sibling checkout unchanged (a recursive hash of tracked files
      before and after, logged).
- [ ] Re-running the script gives the same matrix; only times differ.

## Test plan

### Unit tests

The script has a self-test mode (`--self-test`) run by the unit suite of the end-to-end helper: it executes the
plant functions against the miniature `synthetic` workspace of `crates/xtask/tests/` and asserts that each patch
applies, that each normalization leaves `cargo metadata --locked` working, and that the matrix parser reads a
recorded report correctly (one recorded report per check is kept as a fixture). It also asserts that every row
of the extra-plant table names a patch function that exists and an identifier in the expected form, and that a
row dated after the current milestone is logged `not due`.

### End-to-end script and logging

This bead is the script: `scripts/e2e/workspace_checks.sh`, as specified above. Typical invocation:
`scripts/e2e/workspace_checks.sh --seed 0`. It drives `cargo xtask check-layers|check-deps|check-unsafe|
check-generated|check-contracts|check-stack` only; it never calls a check's internals.

### Known answers and negative controls

KA-784 (workspace checks: a deliberate upward edge, a deliberate intra-layer edge against rank, a second
asupersync package, an unregistered capsule, an edited generated file and a contract missing a section are each
caught; tolerance exact; tier G0 on the host; the planted violations are the controls). The seventh plant, the
stale stack lock, is in the gate's own statement. CX-363 is plant 2. The harness controls of step 5 are the
negative controls of the script itself. Each plant is registered in the negative-control registry of the
conformance crate with its gate, kind `planted-input`, target check and expected finding, so that the gate
cannot record a pass without them. Determinism: the matrix is identical twice on one machine and on Linux and
macOS; times are compared against thresholds, not against each other.

## Considerations

- The run fits the default machine envelope (16 GiB, 8 cores, one hour) with a wide margin; no approval is
  needed. If the scratch copies of a large tree press on disk, the copy is made with hard links for unchanged
  files and the plants write copies of the files they touch.
- A dirty sibling makes the timing and the matrix valid as development measurements and ineligible as a recorded
  pass; the remedy is a clean tree at the pin, never moving a sibling.
- GATE-WS-04 is a performance claim on named hardware; its line carries the fingerprint and the load average,
  and a rerun on a busier host is a new measurement, not a failure of the earlier one.
- If a plant is caught by two checks, the fix is in the checks' ownership (or in the plant's normalization),
  never in the expectation.
- The conformance harness has no agent verb and no `xtask` subcommand, and `xtask` records no gate. The gate's
  row in the verification tier of laws and self-tests is this script's run: the conformance crate's test target
  for that tier, selected by `GATE-WS-01`, invokes the same six commands, and its hash-named receipt is what the
  recording session cites in the gate registry.
- The M0 exit review reads this log; it does not rerun the implementation.
