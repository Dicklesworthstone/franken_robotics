## Background

FrankenRobotics is built by many agents working at once on shared machines, beside sibling projects that other
agents are changing at the same time. A set of working rules is inherited from the machine-level agent
instructions and from the suite's main simulation project (FACT: `frankensim/AGENTS.md`), and adopted here. They
exist because each was learned from a failure: a local compile that starved every other agent, a deleted file
nobody could restore, a branch that diverged for a week, a sibling checkout "fixed" by moving it back to a pin
while someone was working in it, a week of tooling that shipped no capability.

Rules stated in a document are followed until the first deadline. This bead does two things. It records every
rule with the point at which something other than goodwill enforces it. And it builds the mechanical pieces the
rules need that no other bead owns: a **machine-envelope guard** that every heavy script lane sources, so that a
run starts under its limits instead of being remembered to, and the **pre-commit recipe** that rules 7 and 8 name.
The table is written into `AGENTS.md` by N34p4-04, after the companion-documents bead BD-002 has created the file;
the guard needs no document, so it is built first. Tier: Solid.

## Scope

In: the rule table below, each rule with its enforcement point; `scripts/lib/envelope.sh`, added to the shared
script helper: the guard for runs that start outside the verbs (builds, tests, heavy shell lanes), which enforces
the per-run limits of the class in force (wall time, memory, cores), the process-group rule and the presence of an
approval for anything above E0; the pre-commit recipe `scripts/precommit.sh`; their tests.

Out, with the bead that has it: the table as the reviewed section "Working rules" of `AGENTS.md` (N34p4-04);
`AGENTS.md` as a whole and the other companion documents (BD-002). The second
enforcement point of the same limits, for everything started through `frob`: the verbs' admission of a job by
compute class, the needed-class computation, the device-hour meter and refusal `FROB-REF-761` (N36-20); the
guard has no meter, so the cumulative limits of a class (device-hours per gate, per campaign, per pretraining
run) are enforced only there, and a script lane that spends device time above E0 starts its runs through
`frob` or, for a process that is not a verb (a pilot or a training run on an incumbent stack, a baseline
script), through `frob-launch`, the command form of N36-20's metered launch function `run_admitted`; an arm
started any other way is not metered and is not evidence. The guard's classes above E0 therefore serve only
builds, tests and lanes that exceed E0 in memory, cores or wall time without spending device time. The record
both enforcement points read, `registries/compute_envelope.toml`: its class tables, schema
and loader (N21c-35) and its request rows with the owner's rulings (N44-01); the guard defines no approval
format of its own. The daemon's size classes (BD-296); the build-offload shim itself (machine infrastructure);
the workspace checks.

## Technical approach

**The rules, each with its reason and its enforcement point.**

| # | Rule | Enforced by |
|---|---|---|
| 1 | Cargo runs through the build-offload shim, which queues for a worker and never compiles locally; cargo is not invoked by absolute path. Projects stay under `~/projects`. | The guard refuses a command line whose first word is an absolute path ending in `/cargo`; every script in `scripts/` calls plain `cargo` |
| 2 | Isolated target directories use `${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}/<name>`; large scratch uses `${BIG_SCRATCH:-${TMPDIR:-/tmp}}/<name>`. | Helper functions `frob_target_dir <name>` and `frob_scratch_dir <name>` in the guard; scripts use nothing else |
| 3 | A disk preflight precedes heavy lanes. | `frob_disk_preflight <path> <needed_gib>` in the guard; a heavy lane that skips it fails its own self-test |
| 4 | **The machine envelope.** No run on any host uses more than 16 GiB of memory, 8 cores or one hour of wall time without the owner's written approval given before it starts; builds and tests count; a run longer than a few minutes starts under a timeout; when an agent stops, its jobs stop. | `frob_envelope_run` (below) |
| 5 | Lanes that need more (the world bank on the M5 Ultra, training campaigns on the two RTX 4090 cards, the ten-fold tournament) name their budget in their work package and wait for that approval. Until it is given, the envelope is the default of the open question on the compute envelope. | The guard reads an approval record; without one the default applies |
| 6 | No file is deleted without explicit permission. No branches and no worktrees: work lands on `main`, and file reservations through Agent Mail replace branches. | Scripts in `scripts/` contain no deleting command outside their own scratch directory (a self-test greps for it); reservations are a working practice |
| 7 | `ubs` runs on changed files before a commit. Formatting, lints and tests run before a commit. Beads are managed with `br` and triaged with `bv --robot-*`. | The pre-commit recipe `scripts/precommit.sh`: `ubs` on changed files, `cargo fmt --check`, `cargo clippy`, `cargo test` for touched crates, the six workspace checks |
| 8 | Source that was never compiled does not land. The commit message carries the commands and their results. | The pre-commit recipe prints the block to paste; the first commit contains no crate that has not compiled |
| 9 | Code is changed by focused patches, not by scripts or broad regular-expression rewrites. An existing file is revised in place; a new file must be new functionality or a required contract or test artifact. | Review; the exit review samples commits for file sprawl |
| 10 | Before a build failure is attributed to this repository, the stack check runs. An off-pin sibling is classified as a fast-forward or a divergence before any remedy is proposed, and a sibling checkout is never moved back to its pin to make a check pass. | `cargo xtask check-stack` (N33a-05; the drift classes are N33a-04's) is the first step of the build-failure recipe in `AGENTS.md`; the check writes nothing to a sibling |
| 11 | Process is never the product. Before non-product work an agent answers three questions: which capability, defect or blocker does this address; is it the smallest direct action; is it worth its cost now. If any answer is unclear the work is not done. | The exactly-six rule for workspace checks; bead close reasons that cite a test's output; the exit review |
| 12 | The machine-level rule on Apple Simulator audio applies to any use of a device simulator. This project uses none. | Nothing to enforce; recorded so that a later use inherits it |

**The guard** (`scripts/lib/envelope.sh`, POSIX shell, sourced through the shared helper of STD-E2E):

```
frob_envelope_run [--class E0|E1|E2|E3] [--mem-gib N] [--cores N] [--wall-s N]
                  [--approval ROW-ID] [--registry FILE] -- CMD…
```

1. Resolve limits. Default class E0: 16 GiB, 8 cores, 3,600 s, one device; these four values are the only
   limits written in the guard, so that it fails closed when the registry is absent. A request above E0 needs
   `--approval ROW-ID`, the `id` of a `[[request]]` row of `registries/compute_envelope.toml` (`--registry FILE`
   substitutes a scratch copy in tests). That file is the one record of classes and approvals (DESIGN, shared
   with N21c-35, N44-01 and N36-20: two approval records could disagree about the same run). The guard reads
   from the row `class`, `packages` and `admits` (the scope: the work packages and the gates or campaigns it
   covers), `limits`, `status`, `approved_by`, `date` and `expires`, and from the class table of the same file
   the class's `state`. It accepts the row only if its status is `approved` or `amended`, its `approved_by` and
   `date` are filled, it has not expired, its class is at least the class asked and is itself `approved` or
   `amended`; the limits applied are the row's. Because the guard is POSIX shell and runs before any crate is
   built, it reads the row with a line-oriented reader; the registry's lint keeps `[[request]]` rows to one
   `key = value` per line for that reason. The hash of the row's text is logged. Without a valid row the guard
   refuses before starting anything and
   exits with the code the helper maps to "budget refused at admission" (4). The proposed classes are E1 (a
   named gate measurement: both machines, all cores, memory up to the device budget, 2 hours per run, 12
   device-hours per gate), E2 (a design campaign: 48 device-hours), E3 (pretraining of one family policy: 500
   device-hours, approved per run with its ceiling and kill rule written first); they are proposals until the
   owner ratifies or amends them.
2. Start the command in its own process group under a wall-clock timeout; set the address-space limit where the
   platform honours it and otherwise sample resident memory every second and stop the group above the limit;
   cap parallelism by exporting the job-count variables build and test tools read.
3. On timeout, on a limit breach, or when the calling shell exits or is signalled, terminate the whole process
   group (the rule "when an agent stops, its jobs stop").
4. Emit `start`, `metric` (peak resident memory, wall time, exit code) and `end` lines in the structured log
   format; a breach is an `assert` failure naming the limit, the observed value and the threshold.

The guard holds no policy beyond the limits table. Determinism: limits and the decision to refuse are functions
of the arguments and the approval record.

**The pre-commit recipe** (`scripts/precommit.sh`, POSIX shell, sourcing the shared helper; rules 7 and 8). Each
step runs under `frob_envelope_run` at class E0, in this order: (1) `ubs` on the files changed against `HEAD`;
(2) `cargo fmt --check`; (3) `cargo clippy` and `cargo test` for the crates the change touches, through the
build-offload shim; (4) the shell test suites under `scripts/lib/tests/` (this bead's `envelope_test.sh`; later
beads add theirs); (5) every workspace check that `cargo xtask` prints when called with no argument (the
subcommand list of the `xtask` surface, which exits 3 after printing it), so the recipe never names a check that
does not exist and runs a new one without an edit. A failing step fails the recipe with that step's exit code and
names the step. At the end the recipe prints the block of commands and results to paste into the commit message
(rule 8).

## Acceptance criteria

- [ ] `scripts/precommit.sh` runs the five steps in order under the guard, fails with the failing step's code
      and name when one step fails, runs exactly the checks `cargo xtask` lists, and prints the commit-message
      block of commands and results.
- [ ] `frob_envelope_run -- sleep 5` with `--wall-s 1` terminates the command within 2 s, exits non-zero and
      logs the breach with observed and threshold values.
- [ ] A command that allocates 2 GiB under `--mem-gib 1` is stopped and logged.
- [ ] A background child started by the guarded command does not survive the guard's exit (process-group kill),
      including when the calling shell receives a termination signal.
- [ ] `--class E2` without `--approval` refuses before the command starts (exit 4); with a row whose `class`
      is E1, whose status is `requested`, whose class is still `proposed`, or which has expired, it also
      refuses; with an approved E2 row of a scratch `registries/compute_envelope.toml` it runs under the row's
      limits and logs the row's hash.
- [ ] `frob_target_dir x` prints a path under `${RCH_TARGET_BASE:-${TMPDIR:-/tmp}}`; an absolute-path cargo
      command is refused.
- [ ] Every script under `scripts/e2e/` runs its heavy steps through the guard (a self-test lists scripts that
      call `cargo` or `frob` on a run verb outside it).
- [ ] The same self-test lists as a defect a pilot or training command started outside `frob-launch`: in any
      script under `scripts/` whose header carries the label `pilot` or `train`, and in any
      `frob_envelope_run` call with `--class` above E0, a command whose first word is not `frob`, `frob-launch`,
      `cargo` or a function of the shared helper. The scan is of script text and needs no launcher to exist.

## Test plan

### Unit tests

`scripts/lib/tests/envelope_test.sh`, run by `scripts/precommit.sh` and by the helper's own suite (real
processes, no mocks): `timeout_kills`; `memory_limit_kills` (a small allocator loop in a scratch file);
`process_group_is_reaped`; `signal_to_parent_reaps_children`; `class_above_default_needs_approval`;
`approval_class_mismatch_refuses`; `approval_row_requested_refuses`; `approval_row_expired_refuses`;
`approval_class_still_proposed_refuses`; `missing_registry_means_e0`; `absolute_cargo_refused`; `target_dir_convention`;
`disk_preflight_refuses_when_short` (asks for more than the filesystem has);
`precommit_runs_listed_checks` (a scratch tree whose `cargo xtask` lists two checks: both run, and no other);
`precommit_fails_on_failing_step` (a planted formatting error fails step 2 with its name);
`precommit_prints_commit_block`; `device_lane_outside_launcher_is_flagged` (three `synthetic` scripts: one labelled `pilot` that runs
`python3 train.py` bare, and one that runs it under `frob_envelope_run --class E2 --approval R1`, are both
listed with file and line; one that runs
`frob-launch --scope campaign:c1 --request R1 --devices 1 --cores 8 --mem-gib 16 --wall-s 3600 -- python3 train.py`
is not listed).

### End-to-end script and logging

`scripts/e2e/envelope.sh`: runs the cases above from the user's side and, as the positive case, wraps
`cargo metadata --format-version 1 --no-deps --locked --offline` in the guard at class E0 (a command the
skeleton of BD-001 already supports), and runs `scripts/precommit.sh` on a clean scratch checkout. It logs through
the shared helper to
`target/e2e-logs/envelope/<utc>.ndjson`: every `cmd` with its exact command line, exit code and wall time; every
limit with observed value, unit and threshold; the approval record's hash; a `summary` line with assertions
passed and failed. It deletes nothing outside its scratch directory.

### Known answers and negative controls

Known answers: the default limits (16 GiB, 8 cores, 3,600 s, one device). Negative controls: the over-time
command; the over-memory command; the orphan child; the campaign-class request with no approval; the training
command started outside the launcher. Live-dependency
proof: raising `--wall-s` above the command's duration makes the same command pass. Platforms: the tests run on
the Mac and on the Linux training host; where the address-space limit is not honoured the sampling path is the
one tested.

## Considerations

- OPEN-SPARK-2 (owner: the project owner; due at M0): the compute envelope. Fail-closed default: class E0 (16
  GiB, 8 cores, one hour, one device). What the default cannot run, by arithmetic: one device-hour at 50 to 500
  thousand environment steps per second is 0.18 to 1.8·10⁹ steps; the performance gates that use 24 threads or
  two devices; a world bank far above 16 GiB; the rank-agreement experiment (about 45 device-hours, or 5 to 7.5
  where specialists are reused); family-policy pretraining at published sizes. Work packages above the default
  name the class they ask for and what runs if it is not approved.
- RISK-10 (no compute envelope is approved, so the performance gates, the rank-agreement experiment and
  pretraining cannot run as specified; severity High; signal: the open question still at E0 when M1 opens).
- The guard is a seat belt, not the authority: the verbs refuse a job above the envelope in force on their own
  (FROB-REF-761, with the device-hour meter; N36-20), and the guard covers scripts that run outside them. Both
  read one record, so an approval is written once; that the two give the same verdict on one shared scratch
  registry is asserted by N36-20, which depends on this bead.
- This bead is non-product work and answers the three questions of rule 11: it addresses the blocker that heavy
  lanes cannot be started safely by a swarm; one shell file is the smallest direct action; it is needed before
  the first admission runs.
