## Background

The first commit of the implementation repository is not a scaffold of empty crates. DESIGN: it ships the
documents, the registries and the stack facts from which every later statement about the project is generated,
and it may contain no crate at all, because source that was never compiled does not land. Crates arrive with the
first implementation session, each with its contract. A sibling product shipped its companions with its plan and
recorded that as worth repeating (FACT); another found admission records for crates that were never in its
build, which is why the first commit already carries a stack lock and a resolution receipt.

What ships with the first commit:

1. `AGENTS.md` (the working rules).
2. `README.md` with an honest-status table generated from the gate registry.
3. The plan document.
4. `franken-stack.lock` (one row per foundation; the one toolchain T).
5. The first resolution receipt under `receipts/` (what was actually resolved, hashed).
6. `DEPENDENCY_ADMISSION.md` (the format, and no record yet).
7. One `rust-toolchain.toml` for the whole build graph. It names the first candidate for T, the suite's common
   nightly, until the toolchain admission gate records the choice.
8. `.cargo/config.toml` with the build-identity setting that a sibling's linear-algebra crate requires when it
   is consumed from outside its own tree.
9. The registries (`verbs.toml`, `refusals.toml`, `kernels.toml`, `gates.toml`, `formats.toml`, `upstream.toml`,
   `lifts.toml`, `capsules.toml`, `cards/`), schema-valid, and empty except `formats.toml`, which carries the
   thirteen format rows with their owners.
10. The schemas for `demo.yaml` and `contract.toml`.
11. The initial beads, including the two upstream work items at priority P0: FD-FMCP-01 (bring the MCP library
    onto T in its own repository) and FD-ASUP-01 (align the consumed siblings on one published version of the
    async runtime).

Those items are produced by other beads. This bead is the end-to-end check, from the outside, that the set is
complete, consistent and honest on a clean checkout: the user-visible capability "clone the repository and see
its true state". Tier: Solid. Rejected alternative: trusting each producing bead's own tests; the failure this
catches is an item that exists but disagrees with another (a receipt that does not match the lock, a README
table that was typed, a registry row with no owner).

## Scope

In: `scripts/e2e/first_commit.sh` and its assertions; a re-run mode for later commits (the same inventory must
stay true for the life of the repository). Out: producing any of the items (BD-001 for the workspace, toolchain
file, lock and receipt; BD-002 for the companions, registries and schemas); the six checks (the script calls
those that exist and skips, by name, those that do not yet).

## Technical approach

The script is plain shell, sources the shared helper of STD-E2E and the envelope guard, works on a fresh clone
of the commit under test in a scratch directory (never on the working tree), and exits non-zero on any failed
assertion. Steps and assertions:

1. **Clone and list.** `git clone --no-hardlinks <repo> <scratch>` at the commit under test; record the commit.
2. **Presence.** Each of the files of items 1 to 10 exists at its path. `registries/` holds exactly the nine
   entries listed; `schemas/` holds at least the two schemas.
3. **Registries.** Every registry file parses and validates against its schema; eight have zero rows;
   `formats.toml` has exactly thirteen rows with thirteen distinct identifiers (`FMT-FBOT`, `FMT-FMODULE`,
   `FMT-FCARD`, `FMT-FSCENE`, `FMT-FCLEAR`, `FMT-FTASK`, `FMT-FMISSION`, `FMT-FENERGY`, `FMT-FSKILL`,
   `FMT-FMCW`, `FMT-FRUN`, `FMT-FBUILD`, `FMT-FROBCERT`), thirteen distinct extensions and thirteen distinct
   schema names of the form `frob.<name>/1`, each with a non-empty owner crate.
4. **Toolchain.** Exactly one `rust-toolchain.toml` governs the build graph (the certificate checker's own
   stable toolchain file appears only once that crate exists); its channel equals the lock's `toolchain`.
5. **Lock and receipt.** `franken-stack.lock` parses; every `receipt` hash it names exists under `receipts/`;
   each receipt file's name equals the BLAKE3 hash of its bytes; the newest receipt's toolchain, sibling
   revisions and lockfile hashes agree with the lock and the tree (through `cargo xtask check-stack` once that
   check exists; before that, by the script's own comparison of the listed fields). The receipt contains no
   machine path.
6. **Build identity and patches.** `.cargo/config.toml` sets the build-identity variable; the root manifest
   repeats the async-runtime patch entry and the storage engine's profile overrides that a path dependency does
   not propagate.
7. **Status table.** Regenerating the README status block from `registries/gates.toml` gives identical bytes;
   with an empty registry the table has a header, no rows and a zero count. No gate prints as passed.
8. **No uncompiled crate.** For every directory that contains a `Cargo.toml` with a `[package]` table,
   `cargo check --locked -p <name>` succeeds through the build-offload shim under the default envelope. A commit
   with no crate passes this step trivially and the log says "0 crates".
9. **Initial beads.** The bead store lists FD-FMCP-01 and FD-ASUP-01 at priority 0 with the label `upstream`;
   each names its sibling repository, its interim posture and its switch-over rule.
10. **Honesty scan.** No file in the commit claims a measured result: `DEPENDENCY_ADMISSION.md` has zero
    records; `gates.toml` has zero rows with a measured value.

Later commits: `--mode standing` drops the "empty" assertions of steps 3, 7 and 10 (registries fill, gates are
measured) and the "exactly nine" of step 2 (later beads add registry files, such as the compute envelope and
the routes not taken), and keeps every consistency assertion: each registry file present, the nine and any
added, has its schema under `schemas/registries/` and validates against it.

Logging (STD-E2E format) to `target/e2e-logs/first_commit/<utc>.ndjson` with a transcript beside it: one `cmd`
line per command with its exact command line, exit code and wall time; one `assert` line per numbered assertion
with the observed and expected values and, on failure, the first offending path or row; digests of the lock, the
newest receipt and the generated status block; a `summary` line with counts.

## Acceptance criteria

- [ ] On the first commit the script passes all ten steps and logs "0 crates" or the list of crates checked.
- [ ] Each of these planted defects in a scratch clone makes exactly the named step fail: a missing
      `DEPENDENCY_ADMISSION.md` (2); a fourteenth format row with a duplicate extension (3); a second toolchain
      file under an annex directory (4); a receipt whose bytes were edited after naming (5); a hand-edited
      status block (7); a crate directory whose source does not compile (8); a missing P0 upstream bead (9); a
      gate row with a measured value in the first commit (10).
- [ ] The script never writes outside its scratch directory and never touches a sibling checkout.
- [ ] `--mode standing` passes on a later commit in which registries have rows and gates have measurements,
      and in which a tenth registry file with its schema has been added; the same tenth file without a schema
      fails step 3.
- [ ] The whole run stays inside the default envelope and under ten minutes on a commit with no crate.

## Test plan

### Unit tests

`scripts/e2e/tests/first_commit_selftest.sh`: builds a `synthetic` miniature repository (the eleven items in
minimal valid form) in a temporary directory, runs the script against it and expects a pass; then applies each
of the eight planted defects in turn and expects the named step, and only that step, to fail. The registries and
receipts of the miniature are produced by the real generators and the real hash, not written by hand.

### End-to-end script and logging

This bead is the script, `scripts/e2e/first_commit.sh [--commit <rev>] [--mode first|standing]`, as specified.
From the user's side it runs `git`, `cargo check`, and where they exist `cargo xtask check-stack`,
`cargo xtask check-generated` and `frob doctor --json` (which lists the admitted foundations and the stack
receipt once the binary exists).

### Known answers and negative controls

Known answers: thirteen format rows; eight empty registries; zero measured gates; one governing toolchain file.
Negative controls: the eight planted defects. Live-dependency proof: changing one sibling revision in the lock
of the miniature repository makes step 5 fail, so the comparison reads the lock. Determinism: two runs on one
commit give identical assertion results and digests.

## Considerations

- The first commit names a provisional toolchain; the script checks agreement between the file and the lock, not
  the particular channel, so the toolchain admission gate can change both in one commit.
- If the upstream tracker of a sibling is unreachable, step 9 checks this repository's bead store only and logs
  the mirror as unchecked; it does not fail the inventory for a sibling's availability.
- Step 8 is the mechanical form of "source that was never compiled does not land". It is also the slowest step
  once crates exist; in standing mode it checks only crates changed since the previous passing run.
- Nothing here measures a gate; the script supports the M0 exit review, which reads its log.
