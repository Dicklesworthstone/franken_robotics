## Background

Every artifact that agents exchange, cite and cache (a design, a task, a mission, a scene manifest, a run
manifest, a receipt) is JSON whose canonical bytes hash to the artifact's identity. Two readers that disagree
about what a file says therefore disagree about which robot was simulated, under one hash. This bead builds the
one reader every format owner in the core uses to admit JSON. It is the mechanism behind the rule "a duplicate
key refuses", for every artifact format, and it is written in `frob-core` (layer 0, tier Solid) so that no owner
reaches for a library parser.

Smallest case: `{"wheel_radius_mm": 60, "wheel_radius_mm": 75}` names one member twice. A reader that keeps the
first value simulates a 60 mm wheel, one that keeps the last simulates 75 mm, and both hash the same bytes.

DESIGN: admission validates the **raw bytes** before any map is built or any digest is computed. Reasons the
reader may not lean on a JSON library (FACT, read 2026-11-21): the library's feature set in a `frob` binary is
decided by whichever sibling is linked, not by this workspace, because Cargo unifies features across a build
graph. `frankenscipy/Cargo.toml:59` enables `preserve_order` and `float_roundtrip`; `fastmcp_rust/Cargo.toml:54`
enables `arbitrary_precision`, which changes how numbers are represented; `franken_textiles/Cargo.toml` records
that without `float_roundtrip` a decimal may be read one unit in the last place off, which flipped
point-in-polygon verdicts in its fixtures. A library map also keeps one value per name silently.

Rejected alternatives: (1) parse with the library and check for duplicates afterwards (the duplicate is already
gone); (2) share the reader with the offline auditor (the auditor must share no code with any producer, so it
has its own reader and the two are compared on a golden corpus); (3) Unicode-normalize member names (a format
that wants to forbid confusable names does so in its schema; the reader compares code points exactly).

## Scope

In: `frob_core::json` (the admission reader, the value tree with byte spans, the fault type), the identifier
rule, the typed number accessors, the checked-canonical path that yields `CanonicalBytes`, a fuzz target.
Out: the canonical writer (N34-18); mapping faults to refusal codes and the order of admission on the CLI and
MCP surfaces (N34-20); each format's schema-directed reading (the format owners); the auditor's own reader
(BD-026); the golden corpus and the four-way feature build (N34-21).

## Technical approach

```rust
// DESIGN sketch: fixes intent, not signatures.
pub enum Json<'a> { Null, Bool(bool), Num(&'a str),            // the number's source lexeme; never parsed to a float here
                    Str(String), Arr(Vec<Json<'a>>), Obj(Vec<(String, Json<'a>)>) }   // members in source order
pub struct Limits { max_bytes: usize, max_depth: u16, max_string: usize, max_number_len: usize }
pub fn admit<'a>(bytes: &'a [u8], limits: &Limits) -> Result<Admitted<'a>, AdmissionFault>;
pub fn validate_identifier(s: &str) -> Result<(), AdmissionFault>;
```

Checks, in this order; the first failure is returned with a byte offset and a JSON Pointer to the enclosing value:

1. **Size and encoding.** Length at most `max_bytes` (default 64 MiB; an owner may lower it). Valid UTF-8, no
   byte-order mark. Faults: `too-large`, `not-utf8`, `bom`.
2. **Grammar** (RFC 8259): one value, optional surrounding white space, nothing after it (`trailing-data`).
   Raw control characters inside a string are a fault. Numbers follow the JSON grammar exactly (`01`, `+1`,
   `.5`, `1.` are faults; `number-form`). Depth at most `max_depth` (default 64; `too-deep`).
3. **Escape decoding.** `\uXXXX` escapes are decoded; a surrogate escape must be half of a valid pair
   (`lone-surrogate`). Decoded strings are Unicode scalar sequences.
4. **Duplicate member names.** In every object, at every nesting level, member names are compared **after**
   escape decoding, by code point, with no normalization. `{"a":1,"a":2}` is a duplicate. Detection: sort
   the object's decoded names and compare neighbours, O(n log n) per object. Fault: `duplicate-member` with the
   name and both byte offsets. Nothing is kept from an object that has one.
5. **Numbers are lexemes.** `Num` keeps the source text. Typed accessors apply the schema's type:
   - `as_int53()`: an integer lexeme (no fraction, no exponent, not `-0`) with magnitude at most 2⁵³ − 1 =
     9,007,199,254,740,991; otherwise `int53-range` (2⁵³ + 1 = 9,007,199,254,740,993 would decode to
     …992 in a binary64 reader, which is why the type stops at 2⁵³ − 1).
   - `as_u64str()` / `as_i64str()` on a **string**: must match `^(0|[1-9][0-9]{0,19})$`, with an optional
     leading minus for the signed type, and fit the integer type.
   - `as_f64_lexeme()`: returns the lexeme and its correctly rounded binary64 (the standard library's parser is
     correctly rounded); `NaN` and infinities are not representable in the grammar and have no spelling.
   - Exact decimals and rationals arrive as strings and are parsed by the owner (`"0.42 m"`, `"1/3 m"`, a
     reduced pair with a positive denominator). No value that bears identity depends on a float parser.
6. **Identifier rule.** An identifier in an envelope (a request identifier, an idempotency key, a name used as
   a handle) is a nonempty string of printable characters: no code point below 32, and not 127. Fault:
   `identifier-not-printable` or `identifier-empty`. An identifier therefore survives a round trip through a
   shell variable.
7. **Checked-canonical path.** `Admitted::into_canonical(schema_writer)` re-serializes the admitted value with
   the canonical writer and returns `CanonicalBytes` only if the bytes equal the input. A reader may also accept
   a non-canonical file (white space, any key order) as a *view of the term*: the owner builds its typed value
   and the writer produces the canonical bytes that are hashed. The objects `{"b":1,"a":2}` and `{"a":2,"b":1}`
   thus have one identity.

Properties: no panic on any input; no recursion deeper than `max_depth`; memory linear in the input; determinism
class D0 (the same bytes give the same value or the same fault with the same offset on every platform). The
module has no dependency beyond the standard library and prints nothing.

Negative-control builds (DESIGN): a mutant is selected by a custom compiler configuration flag
(`--cfg frob_nc="dup-first-wins"`, `"dup-last-wins"`, `"skip-escape-decode"`), declared in the crate's lint
table, and never by a Cargo feature, because a feature can be switched on by unification from an unrelated crate
and a mutant must not be reachable that way.

## Acceptance criteria

- [ ] `{"wheel_radius_mm": 60, "wheel_radius_mm": 75}` is refused with `duplicate-member` and both offsets.
- [ ] Duplicates that differ only by escapes are refused at nesting depths 1 to 8 (the GATE-WS-05 corpus rows).
- [ ] 9007199254740991 passes `as_int53`; 9007199254740992 and 9007199254740993 fail; the same values as
      `u64str` strings pass.
- [ ] `validate_identifier` refuses the empty string and any string containing a code point below 32 or 127, and
      accepts every other string.
- [ ] A decimal whose nearest double differs between a correctly rounded parser and a parser one unit in the
      last place off keeps its lexeme unchanged through admit and re-serialization.
- [ ] Each of the three mutant builds fails the corresponding test (negative controls caught).
- [ ] The fuzz target `admit` runs 10⁷ executions with zero panics, and every accepted input re-admits to an
      equal tree after re-serialization.
- [ ] Clause of GATE-WS-05 carried here (TARGET; claim Known answer; M0): every duplicate and every bad
      identifier in the golden corpus is refused by this reader; the surfaces' clause and the gate record belong
      to N34-20 and N34-21.

## Test plan

### Unit tests

`cargo test -p frob-core json` (fixtures are literal byte strings; no mocks):
- `dup_plain`, `dup_after_escape` (`{"a":1,"a":2}`), `dup_nested_depth_8`, `dup_in_array_element`.
- `no_false_duplicate`: `{"a":1,"A":2}` and `{"é":1,"é":2}` are accepted (no normalization).
- `int53_bounds`; `minus_zero_is_not_int53`; `u64str_pattern` (`"018"` and `"18446744073709551616"` refused);
  `number_grammar` (`01`, `+1`, `.5`, `1.`, `1e` refused; `1e5` admitted as a lexeme and refused by `as_int53`).
- `lone_surrogate_refused` (`"\ud800"`); `surrogate_pair_decodes` (`"😀"`).
- `bom_refused`; `invalid_utf8_refused`; `raw_control_in_string_refused`; `trailing_data_refused`.
- `depth_limit` (65 nested arrays refused at the default); `size_limit`.
- `identifier_rule`: `"a b"` accepted, `""`, `"a\u0007"`, `"a\u007f"` refused.
- `view_and_canonical_agree`: admitting `{"b":1,"a":2}` and `{"a":2,"b":1}` and writing each yields the bytes
  `{"a":2,"b":1}`; only the second passes `into_canonical` unchanged (known answer KA-781).
- `fault_offsets_are_stable` (property): the reported offset is a function of the input bytes.

### End-to-end script and logging

`scripts/e2e/canonical_json.sh` (bead N34-21) drives this reader from the user's side through `frob` and
`frob-mcp` on the golden corpus and logs, per corpus entry, the command, the exit code, the refusal detail, and
whether a job identifier was created, in the structured format of STD-E2E.

### Known answers and negative controls

KA-781: one identity for the two key orders. Counterexamples protected: CX-358 (hash the file as written) and
CX-361 (tolerate unknown fields; here the sibling rule, tolerate a repeated field). Negative controls: the three
mutant builds; a reader that parses numbers through binary64 changes 9007199254740993 and is caught by the
lexeme test. Metamorphic relations: inserting white space, or reordering members, never changes the admitted
tree up to member order; escaping any character of a member name never hides a duplicate. Determinism lanes:
twice on one machine; debug and release; Linux and macOS (D0).

## Considerations

- The two refusals named for this reader in the chapter (duplicate member name after escape decoding; identifier
  not printable) have no code of their own in the refusal registry. Until the registry's owner mints codes, the
  surfaces report them under the existing codes for a duplicate field in an artifact (FROB-REF-103) and for
  arguments that fail the schema (FROB-REF-802), with the fault kind in the refusal's `observed` field.
- The reader is deliberately not the auditor's reader. The conformance crate compares the two on a golden corpus;
  a disagreement is a finding against both.
- Performance envelope: linear scan plus one sort per object; a 64 MiB manifest admits in well under a second
  (TARGET, measured in the crate's benchmark, not gated).
- Security: every limit is checked before allocation proportional to a declared length; hostile depth, size and
  number length are refusals.
