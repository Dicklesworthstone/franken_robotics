## Background

An artifact's identity is the BLAKE3 hash of its canonical bytes under a domain string equal to its schema name.
"Canonical bytes" must therefore be one byte string per value, on every machine, in every build. This bead
builds the writer that produces them, in `frob-core` (layer 0, tier Solid).

DESIGN: canonical bytes are produced by this project's writer from the typed term, with keys sorted by code
point **explicitly**. No canonical byte is produced by serializing a library map or a library number.

Why. FACT (read 2026-11-21): the `preserve_order` feature of the common JSON library switches its maps from
sorted to insertion order, and Cargo unifies features across a build graph. `frankensqlite/Cargo.toml` records
that the feature "leaked into every downstream consumer via feature unification, silently switching serde_json
maps to insertion order across their whole build", and removed it for that reason. `frankenscipy/Cargo.toml:59`
enables `preserve_order` and `float_roundtrip`; FrankenSim's bedrock depends on FrankenSciPy, and its lockfile
resolves the JSON library at 1.0.154 with `indexmap` among its dependencies, which only `preserve_order` adds.
`fastmcp_rust/Cargo.toml:54` enables `arbitrary_precision`, and the MCP server is a member of the core graph.
Smallest case: `{"b": 1, "a": 2}` re-serialized through a library map is `{"a":2,"b":1}` in one build and
`{"b":1,"a":2}` in another, and a digest over those bytes changes when an unrelated crate enters the graph.

Three shortcuts this writer exists to prevent, each with its smallest counterexample:
- "Hash the file as written": two files that differ in key order or white space would be two designs, and every
  memoized analysis of the first would miss on the second.
- "Hash the in-memory value": a hash of a debug rendering or of a struct's layout changes with the compiler, so
  the same design would change identity at a pin move and every cached result would be orphaned.
- "The view is lossless, so hash either": the S-expression and the JSON of one design are different bytes; a
  cache keyed on whichever arrived first holds two entries for one design and two verdicts a reader could cite
  as independent.

## Technical approach

```rust
// DESIGN sketch: fixes intent, not signatures.
pub trait Canonical { fn write(&self, w: &mut Value<'_>) -> Result<(), CanonError>; }
pub struct CanonWriter { /* output buffer; one pending-member list per open object */ }
impl<'w> Value<'w> {
    pub fn null(self); pub fn bool(self, b: bool);
    pub fn str(self, s: &str);
    pub fn int53(self, n: i64) -> Result<(), CanonError>;        // refuses outside ±(2⁵³ − 1)
    pub fn u64str(self, n: u64); pub fn i64str(self, n: i64);    // decimal strings
    pub fn decimal(self, d: &ExactDecimal);                       // a string: shortest exact decimal
    pub fn rational_pair(self, p: &Int, q: &Int) -> Result<(), CanonError>;   // ["p","q"], reduced, q > 0
    pub fn rational_slash(self, p: &Int, q: &Int) -> Result<(), CanonError>;  // "p/q", or "p" when q = 1
    pub fn f64_shortest(self, x: f64) -> Result<(), CanonError>; // refuses NaN and ±∞
    pub fn array(self, f: impl FnOnce(&mut Array<'_>) -> Result<(), CanonError>) -> Result<(), CanonError>;
    pub fn object(self, f: impl FnOnce(&mut Object<'_>) -> Result<(), CanonError>) -> Result<(), CanonError>;
}
pub fn to_canonical<T: Canonical>(schema: &SchemaName, term: &T) -> Result<CanonicalBytes, CanonError>;
```

Rules the writer implements:

1. **Encoding.** UTF-8, no byte-order mark, no insignificant white space, no trailing newline.
2. **Objects.** Members are buffered per object and emitted sorted by the code points of their names. For UTF-8
   this equals byte order; it is **not** UTF-16 code-unit order, which differs for names beyond the Basic
   Multilingual Plane (U+FFFF sorts before U+10000 here). A repeated name is `CanonError::DuplicateMember`: a
   typed term can never produce a file its own reader would refuse.
3. **Strings.** Minimal escapes only: `\"`, `\\`, and `\u00XX` in lower-case hexadecimal for code points below
   32. Nothing else is escaped; 127 and all non-ASCII are written raw. This is the same canonical form the
   offline auditor checks by "re-serialize and compare bytes", implemented a second time on purpose.
4. **Numbers.** Integers of magnitude up to 2⁵³ − 1 are JSON numbers with no sign on zero, no leading zero, no
   fraction and no exponent. Integers above that travel as decimal strings. Not-a-number and infinity are not
   representable. A rational is a reduced pair of integers with a positive denominator; a non-reduced or
   negative-denominator input is an error, never silently reduced. For a binary64 field that bears identity the
   owner chooses one of two rules and tests it: an exact rational or decimal string, or the shortest decimal
   that round-trips to the same binary64. The writer's `f64_shortest` produces the shortest round-trip digits,
   lays them out by one fixed rule (plain notation when 10⁻⁶ ≤ |x| < 10²¹, otherwise one digit, a point, the
   remaining digits and `e+N` or `e-N`; an integral value has no point; negative zero is written `-0`), and
   verifies by re-parsing that the result round-trips before emitting it.
5. **Arrays** keep their order; ordering a set is the owner's job and is part of its schema.
6. **`CanonicalBytes`.** Exactly two constructors exist: `CanonWriter::finish` and the reader's
   checked-canonical path (bytes that were admitted and that equal their own re-serialization). The identity
   function accepts only `CanonicalBytes`, so a file as written, a view, or a debug rendering cannot be hashed
   into an identity by any call sequence that compiles.
7. **No library types.** The module's public API takes no map type and no library number type. `frob-core` has
   no `serde` dependency at all, so the rule cannot be broken inside the crate; boundary crates that do link the
   JSON library use it for foreign formats and views only, and convert to typed terms before this writer.

Determinism class D0: the bytes are a function of the term alone, on every platform, toolchain and feature set.

Negative-control builds, selected by `--cfg frob_nc="…"` and never by a Cargo feature: `no-key-sort` (members
emitted in insertion order: the control named by the format gate), `utf16-sort`, `escape-all-non-ascii`.
The conformance crate additionally holds a **mutant writer that serializes a library map**; it is not in this
crate, because this crate must not link the library.

## Acceptance criteria

- [ ] A term with members inserted as `b` then `a` writes `{"a":2,"b":1}`; so does the reverse insertion order.
- [ ] `write → admit → write` is the identity on bytes for 10⁴ seeded random terms (property), and
      `admit → write` of a non-canonical spelling yields the canonical bytes.
- [ ] `int53` refuses 2⁵³ and −2⁵³; `f64_shortest` refuses NaN and ±∞ and round-trips 10⁶ seeded random
      doubles bit for bit, including subnormals and −0.
- [ ] A duplicate member name written through the API is an error, not output.
- [ ] `CanonicalBytes` has no public constructor other than the two named (a `compile_fail` doctest attempts a
      struct literal and a `From<Vec<u8>>`).
- [ ] The `no-key-sort` build fails the first acceptance line (negative control caught); the `utf16-sort` build
      fails the supplementary-plane ordering test.
- [ ] Clause of GATE-WS-05 carried here (TARGET; Known answer; M0): canonical digests of the golden corpus are
      identical across the four feature combinations, and the mutant writer that serializes a library map fails
      under `preserve_order`; measured by N34-21.

## Test plan

### Unit tests

`cargo test -p frob-core canon`:
- `sorts_members_by_code_point`: names `"b"`, `"a"`, `"aa"`, `"B"` are written as `B`, `a`, `aa`, `b`.
- `supplementary_plane_order`: U+FFFF precedes U+10000 (byte order EF BF BF < F0 90 80 80).
- `minimal_escapes`: `"\u0001"` is written `\u0001`, `"\n"` as `\u000a`, `"é"` and U+007F raw, `"\""` as `\"`.
- `int53_edges`: 9007199254740991 written as a number; 9007199254740992 refused by `int53` and written by
  `u64str` as `"9007199254740992"`.
- `rational_forms`: (3, 14) → `["3","14"]` and `"3/14"`; (6, 28) and (3, −14) are errors; (3, 1) → `"3"`.
- `f64_layout`: 0.1 → `0.1`; 1e-6 → `0.000001`; 1e-7 → `1e-7`; 1e20 → `100000000000000000000`; 1e21 → `1e+21`;
  5e-324 → `5e-324`; −0.0 → `-0`; 1.0 → `1`.
- `roundtrip_random_terms` (property); `roundtrip_random_doubles` (property).
- `identity_changes_with_schema`: the same bytes under `frob.design/1` and `frob.task/1` give different digests.
- `key_order_identity` (known answer KA-781): the two insertion orders of `{a: 2, b: 1}` have one identity.

### End-to-end script and logging

`scripts/e2e/canonical_json.sh` (bead N34-21) builds the conformance binary four ways and compares the canonical
digests of the golden corpus; it logs the digest of every artifact per build, the first differing artifact on
failure, and the gate line for GATE-WS-05 in the structured format of STD-E2E.

### Known answers and negative controls

KA-781 (one identity for `{"b":1,"a":2}` and `{"a":2,"b":1}`). Counterexamples protected: CX-358, CX-359,
CX-360. Negative controls: the three mutant builds here; the library-map mutant writer in the conformance crate.
Oracle: the canonical bytes of a 100-artifact subset of the golden corpus are also produced by an independent
script under `tools/oracle/` using a different language's standard library (sorted keys, the same escape and
number rules), captured once and pinned under `tests/fixtures/oracle/`; the writer must reproduce them byte for
byte. Determinism lanes: twice on one machine; debug and release; Linux and macOS; the four feature sets (D0).

## Considerations

- The auditor's canonical form and this one must be the same form, written twice. The conformance crate compares
  them; a change to the escape or number rule is an ADR that touches both and re-pins the oracle fixture.
- Sorting by code point rather than by UTF-16 code unit is a deliberate difference from a common canonical-JSON
  scheme; a consumer that re-canonicalizes with that scheme gets other bytes for names beyond U+FFFF, and such a
  rendering is a view with no identity.
- Risk (a dependency feature changes canonical bytes; severity High; owner: Workspace lead): the earliest signal
  is a unified feature set of the JSON library that differs from the stack lock, or a golden digest that changes
  with no change to its artifact. Mitigations: this writer; the four-way build; the feature set in the stack lock.
- A buffered object costs memory proportional to its largest object; large payloads are blobs addressed by hash,
  never members.
