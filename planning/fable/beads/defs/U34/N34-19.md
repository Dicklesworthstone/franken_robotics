## Background

An artifact that agents exchange, cite and cache needs an identity that does not depend on who wrote the bytes.
FrankenRobotics has thirteen artifact formats (a design, a module, a card, a scene, a clearance complex, a task,
a mission, an energy budget, a skill, a minimal counterexample world, a run, a build packet, a certificate
bundle). Without one rule for all of them, each owner would decide for itself what "the same artifact" means.

**ADR-WS-03 (DESIGN): every artifact format has one identifier, one schema name with a version, one owner crate,
and one canonical encoding. Everything else is a view.** A format is canonical when the hash of its canonical
bytes is the artifact's identity. A view is a rendering for a reader or another tool; it is never hashed, signed
or cited. The registry lives in `registries/formats.toml`; `schemas/` is generated from it.

Counterexamples to the shortcuts this rule forbids:
- "Hash the file as written": two files that differ in key order or white space would be two designs, and every
  memoized analysis of the first would miss on the second.
- "Hash the in-memory value": a hash of a debug rendering or of a struct's layout changes with the compiler, so
  the same design would change identity at a pin move and every cached result would be orphaned.
- "The view is lossless, so hash either": the S-expression and the JSON of one design are different bytes. A
  cache keyed on whichever arrived first would hold two entries for one design and, worse, two verdicts that a
  reader could cite as independent.
- "Tolerate unknown fields": a reader that ignores an unknown required field such as a contact-law selector
  would simulate a different robot from the one described and report it under the same identity.

This bead puts the rule into types in `frob-core` (layer 0, tier Solid), so that the wrong thing does not
compile where a type can prevent it and is refused by name where it cannot.

## Scope

In: `frob_core::format` (the registry loader, the owner trait, `Canonical<T>` and `View<T>`, the version gate,
blob references, export provenance, migration links). Out: the registry file and generated schemas (BD-002 and
the generated-file check); each owner's schema and reader (the format owners); the registry cross-checks of the
contract check (N34-09); the round-trip harness (N34-22); refusals at the verb boundary (N34-24).

## Technical approach

**The registry content** (thirteen rows; identifier, extension, schema, owner, canonical form and views):

| Identifier | Ext. | Schema | Owner | Canonical or view |
|---|---|---|---|---|
| `FMT-FBOT` | `.fbot` | `frob.design/1` | `frob-design` | Canonical JSON. View: an S-expression text, lossless in both directions and optional |
| `FMT-FMODULE` | `.fmodule` | `frob.module/1` | `frob-design` | Canonical. Carries its port contract |
| `FMT-FCARD` | `.fcard` | `frob.card/1` | `frob-actuate` | Canonical. Kinds, a closed list in the registry: actuator, transmission, battery, interface, material, soil, optical, sensor, payload |
| `FMT-FSCENE` | `.fscene` | `frob.scene/1` | `frob-scene` | Canonical: the manifest. Cooked bricks and meshes are derived blobs addressed by hash |
| `FMT-FCLEAR` | `.fclear` | `frob.clearance/1` | `frob-scene` | Canonical and derived: reproducible from the identities of its inputs |
| `FMT-FTASK` | `.ftask` | `frob.task/1` | `frob-spec` | Canonical |
| `FMT-FMISSION` | `.fmission` | `frob.mission/1` | `frob-spec` | Canonical |
| `FMT-FENERGY` | `.fenergy` | `frob.energy/1` | `frob-shield` | Canonical |
| `FMT-FSKILL` | `.fskill` | `frob.skill/1` | `frob-control` | Canonical. Weights are blobs addressed by hash |
| `FMT-FMCW` | `.fmcw` | `frob.mcw/1` | `frob-nemesis` | Canonical and derived |
| `FMT-FRUN` | `.frun` | `frob.run/1` | `frob-chronicle` | Canonical: a manifest and chunked binary columns. Views: array files, summaries, stills |
| `FMT-FBUILD` | `.fbuild` | `frob.build/1` | `frob-foundry` | Canonical: the manifest. Views: STEP and mesh files, bills of materials |
| `FMT-FROBCERT` | `.frobcert` | `frob.cert/1` | `frob-cert` (schema and reader); the writer is `frob-lemma` | Canonical. One file, self-contained |

Why two formats are owned by `frob-spec` and not by their evaluators: a task's requirements and a mission's
quantified statement are written in one requirement language, and a certificate about a mission must quote that
statement exactly. One parser and one canonical form remove the question of whether the learner, the arena and
the mission evaluator read the same sentence.

**Types** (DESIGN sketch; fixes intent, not signatures):

```rust
pub struct FormatId(&'static str);                        // "FMT-FBOT"
pub struct FormatRow { id: FormatId, extension: &'static str, schema: SchemaName, owner: &'static str,
                       producers: &'static [&'static str], consumers: &'static [&'static str],
                       canonical: CanonKind, views: &'static [ViewKind], kinds: &'static [&'static str],
                       // the five fields of N34x-03:
                       decision: Option<&'static str>,     // only on a row beyond the thirteen (N34-27)
                       float_rule: FloatRule,              // shortest-roundtrip | exact-rational | none
                       view_kind: ViewMode,                // lossless | export | none
                       writer: Option<&'static str>,       // only FMT-FROBCERT: frob-lemma
                       auditor_reader: &'static [&'static str] }   // only FMT-FRUN: files under crates/frob-cert/
pub struct FormatRegistry { /* loaded once from the embedded registries/formats.toml */ }

/// Implemented by the owner crate, and by no other crate, for its format.
pub trait ArtifactFormat { const ID: FormatId; type Value: Canonical;
    fn read(bytes: &[u8], limits: &Limits) -> Result<Canon<Self>, Refusal>; }   // admit, version gate, schema

pub struct Canon<F: ArtifactFormat + ?Sized> { value: F::Value, bytes: CanonicalBytes, id: Blake3 }  // has an identity
pub struct View<F: ArtifactFormat + ?Sized> { kind: ViewKind, text: String }   // no identity method exists
pub struct BlobRef { hash: Blake3, len: u64 }                                   // plain BLAKE3 of the blob's bytes
pub struct ExportProvenance { schema: SchemaName, authorization: NoAuthorization, stack_receipt: Blake3 }
pub struct MigrationLink { from: Blake3, from_schema: SchemaName, by: EditRef } // new artifact → old identity
```

**Registry rules and how each is carried.**

1. **One owner.** The owner crate holds the schema, the canonicalization rule, the reference reader and the
   version refusal. No other crate parses the bytes; a crate below the owner's layer receives typed values. The
   one deliberate exception named with the registry: `frob-cert` reads only `.frobcert`, and a bundle embeds the
   canonical bytes and hashes of the statements it is about, so the auditor never needs another crate's reader.
   The storage chapter adds a second duty that this rule must admit (FACT: a `.frun` bundle has its hashes and
   chains checked by `frob-verify` with the standard library alone): the auditor holds its own reader of the
   `.frun` manifest and column-file header (N29a-03), written from the byte-level contract, sharing no source
   with `frob-chronicle` and decoding no column. It is recorded in the `FMT-FRUN` row as `auditor_reader` and
   is the only second implementation the single-parser search exempts. Carried by: the
   trait is implemented once per format; the loader refuses two rows with one extension, schema or identifier;
   the search for a second parser is the contract check's (invariant INV-WS-03).
2. **Identity.** The identity of an artifact is the BLAKE3 hash of its canonical bytes under a domain string
   equal to its schema name. A view has no identity. Carried by: only `Canon<F>` exposes `id()`; it can be built
   only by `ArtifactFormat::read` or from a typed value through the canonical writer.
3. **Versions.** The schema name carries a major version. Adding an optional field keeps it. A reader refuses an
   unknown major version and an unknown required field, and never parses on a best-effort basis. Carried by
   `version_gate(found, supported) -> Result<(), VersionFault>`, which every `read` calls before any field is
   interpreted, and by the rule that a reader refuses every field it does not know: a field is "known optional"
   only if the reader's own schema lists it, so a file that uses a newer optional field is refused by an older
   reader with the repair "use a build that reads this schema revision". The owner maps the fault to its
   chapter's code where one exists (FROB-REF-125 for a design, FROB-REF-103 for an unknown design field) and to
   the registry's code FROB-REF-891 (`format-version-unsupported`: unknown major version, or an unknown required
   field) otherwise. Migration is a typed edit that produces a new artifact with a `MigrationLink` to the old
   one; the old identity stays valid for citing old evidence.
4. **Numbers.** Integers above 2⁵³ travel as strings. Not-a-number and infinity are not representable. Each
   owner names one rule for floating-point fields that bear identity (shortest round-trip decimal, or exact
   rationals) and tests it. Carried by the canonical writer's number methods; `FormatRow` records the owner's
   choice in `float_rule`, and a row without one fails to load if the schema has a binary64 field.
5. **Payloads.** Large data are blobs addressed by hash and referenced from a canonical manifest. A manifest
   never embeds a path on the machine that wrote it. Carried by `BlobRef` (no path field exists) and by
   `assert_no_machine_path(bytes)`, which owners call in their writers' tests: it fails on a string beginning
   with `/`, `~`, a drive letter or containing `/Users/` or `/home/`.
6. **Provenance on export.** An artifact that leaves the tool carries the no-authorization flags (three fields,
   all false), the schema name, and the stack receipt of the binary that wrote it. Carried by
   `ExportProvenance`, which has no constructor without all three and whose flags type has one value.

A view offered where an identity is required is refused by name (FROB-REF-892, `view-is-not-identity`: to hash,
to sign, to cite as evidence, or as a cache key); in code this is a missing method, and at the verb boundary it
is a refusal (N34-24). Determinism class D0 for every function here.

## Acceptance criteria

- [ ] The loader reads the thirteen rows; a registry with a duplicate extension, schema name or identifier, or a
      row with no owner, fails to load with the row named.
- [ ] `View<F>` has no method returning an identity, a digest or `CanonicalBytes` (three `compile_fail` doctests:
      hashing a view, using a view as a memo key type, passing a view to the identity function).
- [ ] `version_gate` refuses `frob.task/2` against `frob.task/1` and accepts `frob.task/1`; an owner without a
      chapter code gets FROB-REF-891 from the provided mapper.
- [ ] `ExportProvenance` cannot be constructed without a stack receipt and a schema name (`compile_fail`), and
      serializes the three flags as `false`.
- [ ] `assert_no_machine_path` fails on `"/Users/x/scene.bin"` and passes on a `BlobRef`.
- [ ] A `MigrationLink` round-trips through the canonical writer and reader, and the old identity it names is
      unchanged by the migration.
- [ ] `frob-core` stays within its cap of 8 thousand lines and gains no dependency.

## Test plan

### Unit tests

`cargo test -p frob-core format` (the real loader on the real `registries/formats.toml`, plus `synthetic`
registries for the failing cases):
- `thirteen_rows_load`; `owners_match_table` (each identifier maps to the owner crate above);
  `card_kinds_closed_list` (nine kinds).
- `duplicate_extension_fails`; `duplicate_schema_fails`; `missing_owner_fails`; `float_rule_required`;
  `writer_only_on_cert_row` (a `writer` equal to the owner, or on another row, fails to load);
  `auditor_reader_only_on_run_row`; `view_mode_consistent` (a row with a view and `view_kind = "none"` fails).
- `version_gate_cases`: equal major accepted; higher and lower major refused; malformed schema name refused.
- `unknown_field_is_never_ignored`: a toy format's reader refuses a file with one extra member.
- `canon_identity_is_domain_separated`: the same canonical bytes read as two toy formats have two identities.
- `export_provenance_shape`; `no_machine_path_cases`; `migration_link_roundtrip`.
A toy format (`frob.toy/1`, defined in the test module, labelled `synthetic`) exercises the trait end to end.

### End-to-end script and logging

`scripts/e2e/format_registry.sh` (bead N34-23) exercises these types from the user's side for every registered
format that exists: it reads, re-writes, converts views, and triggers the three registry refusals through
`frob`, logging the envelope's `evidence` block and the artifact identities in the structured format of STD-E2E.

### Known answers and negative controls

KA-781 (one identity for `{"b":1,"a":2}` and `{"a":2,"b":1}`). Counterexamples protected: CX-358, CX-359,
CX-360, CX-361. Negative controls: a toy reader that ignores unknown fields must fail
`unknown_field_is_never_ignored`; a `View` given an `id()` method in a scratch build must make the three
`compile_fail` doctests fail to fail. Determinism lanes: twice on one machine; debug and release; Linux and
macOS.

## Considerations

- OPEN-WS-4 (owner: Augur lead; decided by the contract of `frob-spec`): whether `.fmission` is owned by
  `frob-spec` or by `frob-mission`. Fail-closed default: `frob-spec`, for the reason given above (one parser for
  the requirement language; a certificate quotes the statement exactly).
- A certificate was issued for the wrong statement (pre-mortem scenario): the mitigation that belongs here is
  that a bundle embeds the canonical bytes of the statement, so the auditor compares bytes, not a paraphrase.
- Two codes exist for an unsupported version (the design chapter's and the registry's). The rule above keeps
  both without ambiguity: an owner with its own code uses it; the registry's code covers every other format.
- The forward-compatibility rule is deliberately strict: a new optional field makes new files unreadable by old
  builds. The alternative, ignoring unknown fields, is counterexample CX-361.
- Blob hashes are plain BLAKE3 so that an ordinary tool reproduces them; artifact identities are domain-separated
  by schema name so that equal bytes in two formats are two artifacts.
