## Background

Every request to FrankenRobotics arrives as bytes: a command line with JSON arguments and file paths, or an MCP
tool call. Some of those bytes become artifacts with identities, and some become jobs that cost budget. The
admission reader of `frob-core` validates raw JSON bytes before any map is built: it refuses a member name that
repeats after escape decoding, at any nesting level, and it refuses an identifier that is empty or contains a
non-printable character. This bead fixes **where** that reader runs in the life of a request, on both surfaces,
so that a refused request leaves no trace that looks like work.

DESIGN: the refusal is issued by the CLI and by the MCP server before a job is planned or a budget is charged.
Reasons. (1) A request whose bytes are ambiguous has no meaning to plan: `{"wheel_radius_mm": 60,
"wheel_radius_mm": 75}` is two requests. (2) A job identifier, an idempotency binding or a budget charge created
before the refusal would have to be undone, and undo paths are where ledgers go wrong. (3) An agent that is
refused at admission can fix the call and retry at no cost; the envelope says nothing was charged.

The hard part is the MCP surface. The MCP library parses each frame with a general JSON library before any
handler of ours runs, and that library keeps one value per repeated name (and, with the features unified into
this build, may reorder maps and re-spell numbers). By the time a generated tool handler sees its arguments, a
duplicate is already gone. The check must therefore sit in front of the library, on the frame's bytes.

Rejected alternatives: (1) check for duplicates inside the verb (too late on MCP, and every verb would repeat
it); (2) accept the library's parse on MCP and check only files (the two surfaces would then disagree about the
same request, which the surface-parity rule forbids); (3) refuse after planning and roll back.

Owner: `frob-verbs` for the admission order, with a guard in `surface/frob-mcp`. Tier: Solid.

## Scope

In: the admission pipeline's first stages in `frob-verbs`; the CLI's raw-argument path; the byte-level frame
guard of `frob-mcp`; the mapping of admission faults to refusals; tests that nothing was planned or charged.
Out: the reader (N34-17); routing a file to its format owner and the view-versus-identity rule (N34-24, M1); the
idempotency protocol, the job engine and budgets themselves (the Tether beads); the golden corpus and the gate
record (N34-21).

## Technical approach

**Admission order** (DESIGN; `frob_verbs::admit`). A request passes these stages in order, and a failure at one
stage returns its refusal without entering the next:

1. **Bytes.** Every JSON payload of the request is admitted by `frob_core::json::admit` on its raw bytes:
   inline JSON arguments, an arguments file, and every artifact file named by path whose extension is a JSON
   format. Size limits apply first.
2. **Identifiers.** Every argument whose schema type is an identifier (idempotency key, request identifier,
   session and handle names, artifact names) passes `validate_identifier`.
3. **Schema.** Arguments are checked against the verb's input schema: unknown parameter, wrong type, a number
   outside ±(2⁵³ − 1) in a number-typed field.
4. **Capability.** The session token's scopes.
5. **Idempotency.** The key is bound to the resolved content, atomically.
6. **Estimate and budget.** The cost estimate against the remaining budget; the admission guard.
7. **Plan and job.** A plan or job identifier is created; the budget is charged as work proceeds.

Stages 1 to 3 are pure functions of the request bytes and the registry. Nothing is written before stage 5: no
ledger row, no idempotency binding, no job identifier, no charge. An envelope refused at stages 1 to 3 has
`ok: false`, exit 3, `cost` of zero device and CPU seconds, and no `job` field.

**Refusal mapping** (the chapter names the two faults without minting codes; existing codes carry them until the
registry's owner decides otherwise):

| Fault | Where | Code | `observed` | `retry` | Ranked repairs |
|---|---|---|---|---|---|
| `duplicate-member` | Request arguments | FROB-REF-802 (arguments fail the schema) | `duplicate-member:<name>` with a JSON Pointer in `pointer` | `after-change` | 1. Remove the repeated member. 2. If two values were meant, send two requests |
| `duplicate-member` | An artifact file | The owner's code for a repeated field (FROB-REF-103 for a design: unknown, misspelt or duplicate field) | Same, with the file and pointer | `after-change` | 1. Remove the repeated member from the file. 2. Regenerate the file with the owner's writer |
| `identifier-not-printable`, `identifier-empty` | Request arguments | FROB-REF-802 | The fault and the code point | `after-change` | 1. Use printable characters only (code points 32 and above, not 127) |
| `int53-range` | A number-typed argument | FROB-REF-808 | The lexeme | `after-change` | 1. Send the value as a decimal string in a string-typed field |
| Other byte faults (`not-utf8`, `bom`, `grammar`, `too-deep`, `too-large`, `lone-surrogate`) | Anywhere | FROB-REF-802 for arguments; the owner's invalid-file code for an artifact | The fault and byte offset | `after-change` | 1. Re-encode as UTF-8 JSON within the stated limits |

**CLI.** The CLI owns its parser, so stage 1 runs on the argument bytes as received: `--args '<json>'`,
`--args-file <path>`, and artifact paths. Flags that take scalars are identifiers or numbers and pass stages 2
and 3 directly. Malformed input still produces exactly one envelope on standard output.

**MCP.** `frob-mcp` places a byte-level guard in front of each transport it offers: for stdio, the line reader
that feeds the library; for streamable HTTP, the request-body reader. The guard admits each incoming frame's
bytes with the same reader. A frame that fails is answered by the guard itself with a tool result whose
`isError` is true and whose structured content is the same refusal envelope the CLI prints (for a tool call), or
with a JSON-RPC invalid-request error (for a frame that is not a tool call); the library never sees it. A frame
that passes is handed to the library unchanged, and the generated handler then runs stages 2 to 7 on arguments
re-read from the admitted tree, not from the library's parsed value, so that number spelling and member order
are those of the request.

Surface parity: for the same request content, the two surfaces return envelopes equal in `ok`, `exit`,
`refusal.code`, `refusal.pointer` and `refusal.observed`.

Evidence: a refusal envelope carries no claim; its `evidence` block is the neutral product (class Estimated, no
claims, `reality: no-claim`). Determinism class D0 for stages 1 to 3.

## Acceptance criteria

- [ ] Clause of GATE-WS-05 (TARGET; Known answer; M0): every duplicate and every bad identifier of the golden
      corpus is refused on both surfaces before a job identifier exists (recorded by N34-21).
- [ ] `frob sim run --args '{"seconds": 2, "seconds": 3}' --json` prints one envelope with `ok: false`, exit 3,
      FROB-REF-802, `observed` naming `seconds`; `frob job list --json` (or the ledger's job count) is unchanged;
      the session budget is unchanged.
- [ ] The same request as an MCP tool call returns `isError: true` with the same refusal fields, and the
      library's handler was not invoked (a counter in the generated dispatcher stays at zero).
- [ ] A duplicate that differs only by an escape (`"seconds"` and `"seconds"`) is refused on both surfaces.
- [ ] An idempotency key containing a tab or a bell character is refused at stage 2; after the refusal the same
      corrected request with a printable key is accepted, and the refused key is not bound.
- [ ] A design file with a repeated member, passed by path, is refused with the owner's duplicate-field code
      before any compile product or memo entry is created.
- [ ] 9007199254740993 in a number-typed argument is refused with FROB-REF-808 and reaches no verb.
- [ ] The surface-parity comparison over the corpus's refused entries finds zero differing fields.

## Test plan

### Unit tests

`cargo test -p frob-verbs admit` and `cargo test -p frob-mcp guard` (the real reader, the real registry, an
in-memory ledger file on disk; no mocks):
- `stages_run_in_order`: a request that fails stages 1 and 4 reports stage 1 only.
- `refused_request_writes_nothing`: the ledger file's hash is unchanged after 100 refused requests.
- `refused_key_is_unbound`; `refused_request_has_zero_cost_and_no_job`.
- `duplicate_in_args`, `duplicate_after_escape`, `duplicate_nested_depth_8`, `duplicate_in_artifact_file`.
- `identifier_faults` (empty, U+0007, U+001F, U+007F); `identifier_boundary` (U+0020 and U+007E accepted).
- `int53_out_of_range_is_808`.
- `mcp_guard_refuses_before_library` (the library's in-memory transport receives no frame);
  `mcp_guard_passes_bytes_unchanged` (a valid frame arrives byte-identical);
  `mcp_handler_reads_admitted_tree` (a large integer sent as a string arrives with its spelling intact).
- `surface_parity_on_refusals` (property over generated malformed requests).

### End-to-end script and logging

`scripts/e2e/canonical_json.sh` (bead N34-21) drives both surfaces with the golden corpus: for each entry it
runs the `frob` command and the equivalent MCP tool call through `frob-mcp` over stdio, and logs the exact
command or frame digest, the exit code, the refusal code and fault, the job count before and after, and the
budget before and after, in the structured format of STD-E2E.

### Known answers and negative controls

Known answer: the job count and the budget are unchanged by a refused request. Counterexample protected: a
reader that keeps the first of two values and one that keeps the last simulate two different wheels under one
hash. Negative controls: a build of `frob-mcp` with the guard bypassed (arguments taken from the library's parsed
value) must accept the duplicate tool call and fail the test; a build of the pipeline with stage 5 before stage 1
must leave a bound key and fail `refused_key_is_unbound`. Determinism: stages 1 to 3 give identical refusals
twice on one machine and across platforms.

## Considerations

- HYPOTHESIS: the MCP library's stdio and HTTP transports can be fronted by a byte-level reader without
  changing the library. The test that settles it is `mcp_guard_passes_bytes_unchanged` on both transports. If it
  fails, the fix is an upstream work item in the library's repository (a raw-frame hook), and until it lands the
  MCP surface documents that duplicate detection in tool arguments applies to artifact files only; the gate's
  MCP clause then stays open.
- The one permitted difference between the surfaces remains the unknown-verb case, which the library answers
  before generated code runs.
- If the MCP kill gate moves the server into its own workspace, the guard moves with it unchanged.
- Security: this is the first code to touch untrusted bytes on both surfaces; limits are enforced before
  allocation, and imported text is never interpolated into a refusal message without its untrusted mark.
- Two faults have no code of their own in the refusal registry; the mapping above is the fail-closed default
  and is recorded with the registry rows of N34-REF.
