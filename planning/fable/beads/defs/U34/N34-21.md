## Background

Every artifact of FrankenRobotics is identified by the hash of its canonical JSON bytes. Two things can break
that silently. A reader can accept bytes that mean two things (a repeated member name, an identifier with a
control character, a number that a binary64 parser rounds). And a dependency can change what a JSON library does
inside this build: Cargo unifies features across a build graph, a sibling enables `preserve_order` (maps keep
insertion order instead of sorted order) and another enables `arbitrary_precision` (numbers are represented
differently), so the library's behaviour in a `frob` binary is decided by whichever sibling is linked.

The defences are an admission reader on raw bytes, a canonical writer that sorts keys itself and never
serializes a library map or number, an admission order that refuses before any job exists, and a guard that
reports the library's unified feature set. This bead is the test that all four work together, from the user's
side, and it records the gate:

**GATE-WS-05** (TARGET; claim Known answer; M0). A golden corpus of 10³ artifacts, including duplicates that
differ only by escapes at depths 1 to 8, integers at 2⁵³ ± 1, non-printable identifiers, and decimals whose
nearest double differs between parsers: every duplicate and every bad identifier is refused on both surfaces
before a job identifier exists; canonical digests are identical across the four feature combinations; the
mutant writer that serializes a library map fails under `preserve_order`.

Tier: Solid. This is a test bead; it builds no mechanism.

## Scope

In: the corpus and its generator; the probe program built four ways; the library-map mutant writer; the script
and the gate record. Out: the reader, the writer, the admission order and the guard (N34-17, N34-18, N34-20,
N34-04); the per-format round-trip harness (N34-22); the comparison of this reader with the offline auditor's
own reader on a shared corpus (the conformance beads of the certificate chapter).

## Technical approach

**The corpus** (`tests/fixtures/canon/corpus.ndjson`, 1,000 entries; generated once by a seeded generator in the
conformance crate, then committed; each entry has `id`, `class`, the bytes in base64, `expect`, and where it
applies `twin` and `canonical_digest`). Composition (DESIGN):

| Class | Count | Content | Expected |
|---|---|---|---|
| `canonical` | 200 | Valid artifacts already in canonical form: stack receipts, request envelopes, claim pre-images, and `synthetic` documents shaped like designs and tasks | Admitted; bytes unchanged by the writer; digest equals the pinned value |
| `respelled` | 200 | The same 200 values with other key orders, white space and optional escapes | Admitted; canonical bytes and digest equal the twin's |
| `duplicate` | 160 | Twenty per nesting depth 1 to 8; in half of them the two names differ only by escapes | Refused, `duplicate-member` |
| `integer` | 80 | 2⁵³ − 1, 2⁵³ and 2⁵³ + 1 and their negatives, as JSON numbers and as decimal strings, in number-typed and string-typed fields | 9,007,199,254,740,991 admitted as a number; 9,007,199,254,740,992 and …993 refused as numbers (`int53-range`) and admitted as strings |
| `identifier` | 120 | Identifiers containing each code point 0 to 31 and 127 at the start, middle and end; the empty identifier; the boundary characters 32 and 126; non-ASCII printable text | Control characters and empty refused; the rest admitted |
| `decimal` | 120 | Decimals at rounding ties and at the subnormal boundary, taken from published float-parsing stress cases (for example 2.2250738585072011e-308 and a 54-digit tie between 1 and the next double), each with the bit pattern of the correctly rounded binary64 | Admitted; the lexeme survives unchanged; the binary64 equals the recorded bits |
| `malformed` | 120 | Byte-order mark, invalid UTF-8, lone surrogate escapes, depth 65, trailing data, number-grammar faults, keys beyond the Basic Multilingual Plane (valid; they pin the sort order) | As labelled per entry |

Pinned digests come from an independent oracle: a script under `tools/oracle/` that implements the canonical
form with another language's standard library, run once, its output stored under `tests/fixtures/oracle/` with
a capture record; it is never regenerated from this project's writer.

**The probe.** A fixture workspace under the conformance crate's fixtures (not a member of any workspace of the
repository, so the closed crate list is untouched), built only by this script. Its one binary reads the corpus
and, per entry, prints one line: the reader's verdict and fault, the canonical digest from this project's
writer, the digest of the **mutant writer** (the same value pushed into the JSON library's map type in source
order and serialized by the library), and the library's enabled features. The fixture has two optional path
dependencies, each a dummy crate that does nothing except depend on the JSON library with one feature:
`dummy-preserve-order` and `dummy-arbitrary-precision`. Four builds: neither, the first, the second, both.

**The script** (`scripts/e2e/canonical_json.sh`; plain shell; sources the shared helper and the envelope guard;
seed-explicit: `--seed` selects which 100 corpus entries get the slow surface test when `--quick` is given; the
gate run uses all):

1. Log the corpus file's digest and the oracle capture record.
2. Build the probe four ways through the build-offload shim; run each on the corpus.
3. Assert, per entry, the reader's verdict equals `expect` in all four builds.
4. Assert the canonical digest of every admitted entry is identical across the four builds, equals its twin's
   where it has one, and equals the pinned oracle digest.
5. Assert the mutant: in the two builds with `preserve_order`, the mutant's digest differs from the canonical
   digest for at least every `respelled` entry whose source order is not sorted (the mutant fails); log how many
   entries the mutant gets right by luck in each build.
6. Run `cargo xtask check-deps --json --root <fixture>` for each build and assert the JSON-library guard reports
   the planted feature in the three non-baseline builds and nothing in the baseline.
7. Surfaces. For every `duplicate` and refused `identifier` entry: submit it through the CLI
   (`frob sim run --args-file <entry> --json`, or as the idempotency key for identifier entries) and as the
   equivalent MCP tool call over stdio. Before and after each call read the count of job and run rows in the
   ledger (from the ledger block of `frob doctor --json` at M0; from `frob job list --json` once it exists) and
   the session budget. Assert: `ok` false, exit 3, the expected refusal fields, the job count unchanged, the
   budget unchanged, and equal refusal fields on the two surfaces.
8. Write the gate line: corpus size, refused-as-expected count on each surface, the number of digest
   differences across builds (threshold 0), the mutant's failure count under `preserve_order` (threshold: at
   least 1), with the commit, the resolution receipt hash and the host fingerprint.

Logging (STD-E2E format) to `target/e2e-logs/canonical_json/<utc>.ndjson` with a transcript: every `cmd` with
exact command line, exit code and wall time; per-entry `assert` lines carrying the entry identifier, class,
expected and observed verdicts and digests; on failure the first differing entry, its base64 bytes and the two
digests; the envelope's `evidence` block for surface calls; a `summary` line with assertions passed and failed
and the gate touched. Corpus entries are synthetic and carry no private-scene data.

## Acceptance criteria

- [ ] The corpus has exactly 1,000 entries with the class counts above; its generator, given its seed,
      reproduces the committed file byte for byte.
- [ ] All four builds agree with `expect` on every entry.
- [ ] Zero canonical-digest differences across the four builds; zero differences from the pinned oracle digests.
- [ ] The mutant writer's digests differ from the canonical ones under `preserve_order` (it fails), and the
      baseline run logs how often it agreed.
- [ ] 160 of 160 duplicates and every refused identifier entry are refused on the CLI and on the MCP surface
      with no new job and no budget change.
- [ ] 2⁵³ − 1 is admitted as a number; 2⁵³ and 2⁵³ + 1 are refused as numbers and admitted as strings.
- [ ] Every `decimal` entry keeps its lexeme, and the binary64 obtained equals the recorded bits.
- [ ] The gate line for GATE-WS-05 is written with measured values; the registry row is updated by a session
      that did not implement the mechanisms.

## Test plan

### Unit tests

`cargo test -p frob-conformance canon_corpus`: `corpus_counts`; `corpus_is_reproducible_from_seed`;
`every_duplicate_differs_only_as_labelled` (the escape-only half decodes to equal names);
`twins_decode_to_equal_values`; `decimal_bits_are_correctly_rounded` (checked against exact rational arithmetic:
the recorded double is the nearest to the decimal's exact value, ties to even); `mutant_is_a_real_library_call`
(the mutant's source contains the library's map type; a guard against the mutant being edited into the real
writer).

### End-to-end script and logging

This bead is the script, as specified. Invocation: `scripts/e2e/canonical_json.sh --seed 34` for the gate run;
`--quick` for a pre-commit run over 100 entries per class of surface test.

### Known answers and negative controls

KA-781 (the objects `{"b":1,"a":2}` and `{"a":2,"b":1}` have one identity) is corpus entry pair 1. Counterexamples
exercised: CX-358 (hash the file as written), CX-359 (hash the in-memory value), CX-360 (hash either view).
Negative controls, each registered against GATE-WS-05 in the conformance crate's control registry: the
library-map mutant writer under `preserve_order`; the reader built with first-wins and with last-wins duplicate
handling (selected by a compiler configuration flag, never a Cargo feature), each of which must admit the 160
duplicates and fail step 3; the MCP guard bypassed, which must fail step 7; the dummy dependency that enables
both library features, which is also the planted instance of the late-risk register. Metamorphic relation:
re-spelling an artifact never changes its digest; adding a second copy of any member always turns admission into
refusal. Determinism lanes: the script twice on one machine; debug and release builds of the probe; Linux and
macOS; the four feature sets: identical digests in every lane (class D0).

## Considerations

- The four builds are small (the probe links `frob-core` and the JSON library only) and fit the default machine
  envelope easily; the surface step dominates and runs about 260 entries on two surfaces.
- If the baseline graph of the real binaries already has both library features on, that is expected: the guard
  records it in the stack lock. The four-way build uses a minimal fixture precisely so that "without" is real.
- A corpus entry is never edited in place: a new case gets a new identifier and the corpus digest changes with
  an ADR-free commit that cites the defect it captures.
- The MCP half depends on the byte-level guard hypothesis of N34-20; if that fails, the gate stays open with the
  CLI half recorded.
- The decimal class proves a negative (no value depends on the library's float parser); it cannot prove the
  library is wrong, only that this project does not ask it.
