## Background

Every artifact format of FrankenRobotics has one owner crate, which holds its schema, its canonicalization rule
and its reference reader; no other crate parses the bytes. An artifact's identity is the hash of its canonical
bytes; a view (the S-expression text of a design, an array-file export of a run, a bill of materials) is a
rendering for a reader or another tool and is never hashed, signed or cited.

Those two rules are easy to state inside one crate and easy to break at the surface, where files arrive by path
from agents. This bead makes the verb layer the place where they hold for every verb at once, and gives the two
failure modes their registered refusals:

- **FROB-REF-893 `format-owner-bypass`**: a file with a registered extension reaches a verb through a path that
  did not go through its owner's reader. Example: an agent passes `quad.fbot` to a generic import verb as a
  foreign file, or stores it as an opaque blob and offers the blob where a design is expected. If that were
  allowed, a second reading of the design would exist, with its own idea of defaults and duplicates.
- **FROB-REF-892 `view-is-not-identity`**: a view is offered where an identity is required: to hash, to sign, to
  cite as evidence, or as a cache key. Counterexample to "the view is lossless, so hash either": the
  S-expression and the JSON of one design are different bytes; a cache keyed on whichever arrived first would
  hold two entries for one design and, worse, two verdicts that a reader could cite as independent.

DESIGN: verbs never see file bytes of a registered format. The verb layer's input stage resolves every artifact
argument to a typed, canonical value with an identity, through the owner's reader, before the verb's executor
runs; the envelope's `bound` field reports the immutable identifiers every name was resolved to. Reason: the
weakest point of a one-owner rule is the hundredth verb, written in a hurry, that opens a file itself.

Rejected alternatives: (1) let each verb call the owner's reader (ninety-nine do and one does not); (2) accept
views silently wherever an identity is needed, converting on the fly (the caller then believes the view's bytes
were what was signed or cited); (3) refuse views everywhere (views exist because agents edit nested terms more
reliably in them; they are welcome as inputs to work).

Owner: `frob-verbs` (layer 6, tier Solid).

## Scope

In: the artifact-input stage of `frob-verbs`; the parameter kinds in verb schemas and the rule that a parameter
has one; how the forms of an argument (fixture reference, identity, inline JSON, path, name) are told apart;
routing of a resolved `@fixture:<name>` reference (the resolver itself is N34p3-01, M0); the routing table
generated from the format registry; the two refusals and the version refusal at the verb boundary; tests on the
formats that exist at M1. Out: the owners' readers; raw-byte admission (N34-20, which runs first); the memo
graph's key type and the bundle writer's input type (their own beads; this bead supplies the typed value they
accept); the single-parser search in the tree (N34-09).

## Technical approach

**Parameter kinds** (declared per parameter in the `params` field of each verb row of `registries/verbs.toml`, a
field of N32a-02's closed entry schema that names this bead as its owner; DESIGN):

| Kind | Accepts | Resolved to | Typical use |
|---|---|---|---|
| `artifact-input<F>` | A path or inline JSON in canonical or any other spelling, or a registered view of F; also an identity or a mutable name, as `artifact-ref<F>` accepts | `Canon<F>` (typed value, canonical bytes, identity) by the owner's reader; a view is converted by the owner's view codec | A design to check, a task to run |
| `artifact-ref<F>` | An identity in its text form (for example `d:41aa…`) or a mutable name that resolves to one | `Canon<F>` fetched from the store by identity and re-checked against it | A design to compare, a run to replay |
| `artifact-identity<F>` | An identity, or a file whose bytes are exactly canonical | `Canon<F>` by the strict identity-bearing read path; anything else refuses | What is to be signed, embedded in a bundle, cited as evidence, or used as a memo key |
| `foreign-file` | A file of a format this project does not own (URDF, MJCF, a mesh, a log) | Bytes, with the untrusted mark | Importers |

**One kind per parameter (DESIGN; asked by the verb registries of every cluster).** A parameter that accepts a
name or an identity as well as a path (the design argument of most verbs; a run given as an identifier or as a
`.frun` path) is declared `artifact-input<F>`: never two kinds, and never `artifact-ref<F>`, which is for a
parameter that cannot take a path. Reason: where a path can arrive, the path jail (FROB-REF-734) and the payload
sniff (FROB-REF-828) must be in the verb's refusal list, and NJL-01's generator appends codes by kind:
`artifact-input<F>` gets 891, 734 and 828; `artifact-identity<F>` gets 891, 892, 734 and 828; `foreign-file` gets
893, 734 and 828; `artifact-ref<F>` gets 891 only. The forms of an `artifact-input<F>` argument are told apart
by the text of the value alone, in this order, so that a request never means something else because of what the
working directory holds:
1. `@fixture:<name>`: a fixture reference (below).
2. The text form of an identity of F (its typed prefix and 64 hexadecimal digits): fetched from the store by
   identity and re-checked against it.
3. A JSON object (an object-valued tool argument; on the command line a value that starts with `{`): inline JSON.
4. A value that starts with `/`, `./`, `../` or `~`, or that ends in the extension of F, of one of F's views or
   in `.json` (`quad.fbot`, `quad.sexpr`, `designs/quad.json`): a path. A path that names no file is refused as a
   path and is never retried as a name.
5. Anything else: a mutable name, resolved once in the store by the *Resolve* step of the dispatch pipeline
   (N32a-04; from M3 in the caller's namespace, N32b-03), before the request is digested (`quad-a`,
   `agent-17/quad-a`).
Whatever the form, `bound` reports the identity it resolved to.

**Fixture references** (the form end-to-end scripts and examples pass verbatim; STD-E2E defines the syntax).
`@fixture:<name>` is accepted by every `artifact-input<F>`, `artifact-identity<F>` and `foreign-file` parameter
and denotes a file, the files of a directory or a directory under the workspace's `fixtures/` directory. The
resolver is N34p3-01, a dependency split from this bead because scripts of M0 beads already pass the form: it
owns the grammar, the read-only root the build records, the `bound.fixtures` echo (reference, workspace-relative
path, BLAKE3 digest of each resolved file) and the refusal for an unknown, ambiguous or malformed reference
(the ledger request `fixture-reference-unresolved`, reported as FROB-REF-802 with an `observed` value until a
number is assigned). This bead adds two things at M1. (a) Which file of a fixture directory "has the
parameter's format" is decided as routing decides it: N34p3-01's lookup of F's extension in the embedded
registry file is replaced by the typed format registry (N34-19), and a `.json` file whose top-level `schema`
member names F counts as a file of F. (b) A resolved fixture file then goes through routing below like any
path, so a fixture is refused for the same reasons a path is (`@fixture:` of a `.fbot` given to a `foreign-file`
parameter is FROB-REF-893), and the identity it resolves to is reported in `bound` under the parameter's name
beside its `bound.fixtures` entry.

**Routing** (`frob_verbs::input::resolve`), after raw-byte admission:

1. Determine the format of each file argument from its extension and, for JSON, from its top-level `schema`
   member, using the routing table generated from `registries/formats.toml` (the table carries the marker that
   exempts it from the single-parser search).
2. If extension and `schema` member disagree, or a registered format arrives in a parameter of another format's
   kind, refuse with FROB-REF-802 (arguments fail the schema), `observed` naming both formats.
3. If a file with a registered extension, or JSON whose `schema` member is a registered schema name, arrives in a
   `foreign-file` parameter or as an opaque blob reference: FROB-REF-893. Repairs, ranked: 1. pass the file to
   the parameter of its own format; 2. if a conversion was intended, use the owner's import or view verb.
4. Call the owner's reader. A version fault becomes the owner's version refusal, or FROB-REF-891
   (`format-version-unsupported`: unknown major version, or an unknown required field) for an owner with no code
   of its own. Repairs: 1. migrate the artifact with the owner's migration edit, which produces a new artifact
   linked to the old identity; 2. use a build that reads this schema revision.
5. For `artifact-identity<F>`: if the argument is a view, or JSON that is not byte-for-byte canonical, or a
   reference that resolves to a stored view: FROB-REF-892, with `observed` saying which (`view:sexpr`,
   `non-canonical-spelling`) and `affected_claims` naming the claim kinds that would have cited it. Repairs,
   ranked: 1. convert with the owner's view verb (for a design, `frob design view --as json`) and pass the
   canonical file or its identity; 2. pass the identity printed in the `bound` field of the envelope that
   produced the artifact.
6. Put every resolved identity in the envelope's `bound` field, keyed by parameter name.

All three refusals exit 3 with `retry: after-change`, and are issued before a plan or job exists.

**What the types then guarantee.** A verb's executor receives `Canon<F>` values only. The bundle writer, the
evidence sink and the memo graph take identities or `Canon<F>`; none has a method that accepts a view or raw
bytes, so "hash, sign, cite, cache-key" each have exactly one typed entrance. An `artifact.read` by digest
returns bytes for display or export; feeding those bytes back as a `foreign-file` is caught by rule 3, and
feeding them back to their own format's parameter is ordinary input.

Evidence: a resolved artifact contributes a leaf to the result's claim product with its identity as the input
reference. Determinism class D0 for routing.

## Acceptance criteria

- [ ] `frob design check quad.fbot --json` and the same design given as `quad.sexpr` both succeed and report
      the same `bound.design` identity.
- [ ] `frob design import quad.fbot --format urdf --json` (a registered format in a foreign-file parameter)
      refuses with FROB-REF-893, exit 3, before any job exists.
- [ ] A JSON file named `quad.json` whose `schema` member is `frob.design/1`, passed as a foreign file, refuses
      with FROB-REF-893; passed to a design parameter it is accepted (routing by schema member).
- [ ] A `.ftask` passed where a design is expected refuses with FROB-REF-802 naming both formats.
- [ ] An identity-required parameter given the S-expression view refuses with FROB-REF-892 and
      `observed: "view:sexpr"`; given a re-spelled JSON (keys reordered) it refuses with
      `observed: "non-canonical-spelling"`; given the canonical file or the identity it is accepted.
- [ ] `"schema": "frob.task/2"` refuses with FROB-REF-891; `"schema": "frob.design/9"` refuses with the design
      owner's own version code.
- [ ] The same requests through `frob-mcp` return the same refusal fields (surface parity).
- [ ] No verb executor in `frob-verbs` takes a path or byte slice for a registered format (a source scan in the
      crate's conformance test: executor signatures mention `Canon<` or identity types only).
- [ ] Each registry fixture of FROB-REF-891, -892 and -893 (N34-REF, with its sidecar) run through the
      artifact-input stage returns its code, the sidecar's `observed` value and the row's ranked repairs; the
      design owner's fixtures for the same conditions return its own codes, not 891.
- [ ] Each of the three codes is raised by the mechanism its row names and by no other code path (a source scan
      for the enum variants: 891 in the version-gate mapper and owners' readers; 892 and 893 in the
      artifact-input stage only).
- [ ] The M1 verbs' generated refusal lists include the three codes wherever a verb takes an artifact parameter:
      NJL-01's generator appends them from the `params` field (891 for any `artifact-input`, `artifact-ref` or
      `artifact-identity` parameter, 892 for an `artifact-identity` parameter, 893 for a `foreign-file`
      parameter; and 734 and 828 for the three kinds that can take a path, `artifact-input`, `artifact-identity`
      and `foreign-file`, never for `artifact-ref`), so the rows of record need not repeat them in their chapter
      lists; a verb row naming a code absent from the refusal registry fails to load.
- [ ] One design reaches `frob design check` as a path (`quad.fbot`), as its identity (`d:…`), as a mutable name
      (`quad-a`) and as `@fixture:designs/quad.fbot`, and all four report the same `bound.design` identity; with
      a file named `quad-a` in the working directory the name still resolves in the store (form 5, not a path).
- [ ] `@fixture:` references at M1: a fixture directory holding one `quad.json` whose `schema` member is
      `frob.design/1` resolves for a design parameter (format by schema member, not only by extension); a
      resolved fixture goes through routing (a `.fbot` fixture given to a `foreign-file` parameter is
      FROB-REF-893); the envelope carries both `bound.design` and the `bound.fixtures` entry of N34p3-01.

### End-to-end script and logging

`scripts/e2e/artifact_inputs.sh` (this bead; header `bead=N34-24 milestone=M1 labels=workspace,tether,verb`)
runs each acceptance command above through `frob` and the equivalent tool call through `frob-mcp` over stdio, on
the M1 formats (design JSON and its S-expression view, `.ftask`, a `synthetic` design at schema major 9 and a task
at major 2): it asserts the exit code, refusal code, `observed` and `pointer` equal across the surfaces, the
`bound.design` identity equal for the JSON and the view, and the ledger row counts and commit sequence (`frob
doctor --section ledger --json`) unchanged by each refusal. It then passes one design in the four forms (path,
identity, name, `@fixture:` reference) and asserts one `bound.design`, logging for the fixture form the
reference, the resolved path and the digest from `bound.fixtures`. It sources the STD-E2E helper and writes
`target/e2e-logs/artifact_inputs/<utc>.ndjson` with a transcript; each line has `ts`, `script`, `bead`, `step`
(the case), `event`, the exact command, exit code, wall time, the refusal code and `observed`, the `bound`
identities, the envelope's `evidence` block and the BLAKE3 digest of each input file; on failure the differing
field with both envelopes saved and the command that reproduces it; then a `summary`. N34-23's
`scripts/e2e/format_registry.sh`, which depends on this bead, extends the same checks to every landed format.

### Known answers and negative controls

Known answer: one design given as JSON and as its S-expression view binds to one identity (KA-781's rule at the
surface). Counterexamples protected: CX-360 (the view is lossless, so hash either form), CX-358 (hash the file as
written), CX-361 (tolerate unknown fields). Negative controls: a build in which the identity-required path
converts views silently must fail `view_as_identity_is_892` (N34-CX's plant `view-converted-silently`, plant 1
of CX-360, which this bead builds: a `cfg(feature = "nc-<nnnn>")` branch in step 5 of routing, compiled only
with `--features gauntlet-mutations,frob-verbs/nc-<nnnn>`, the `NC-` record the seeding tool derives from that
plant; under it a view is accepted where an identity is required, the defect by which the S-expression and the
JSON of one design would get two cache entries); a build in
which the foreign-file parameter skips rule 3 must fail the 893 tests; a planted verb executor that takes a
path fails the signature scan; a build that classifies an argument by looking in the working directory must
fail `name_wins_over_a_file_of_the_same_name`.
Live-dependency proof: changing one quantity in the design changes `bound.design`. Determinism: routing and
refusals are identical twice on one machine and across platforms.

## Considerations

- A claim does not outlive its inputs: the `bound` identities are what revalidation compares after an edit, so a
  result cannot silently refer to "the design at that path".
- Format sniffing by `schema` member reads only the top-level member after raw-byte admission; a hostile file
  cannot steer routing by a nested or duplicated `schema`, because duplicates were already refused.
- Private scenes: routing never copies an artifact's bytes into a refusal message; pointers and identities only.
- The S-expression view may be killed by its own gate (fallback: JSON is the only syntax); the parameter kinds
  and FROB-REF-892 remain, because other formats have views.
- Revisit if a verb needs partially parsed artifacts (for example a streaming read of a very large run
  manifest): that is an owner API returning a typed cursor, not an exception to routing.
