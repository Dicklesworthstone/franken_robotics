## Background

FrankenRobotics answers design questions with certificates, and every certificate travels in a `.frobcert`
bundle that an independent program, `frob-verify`, re-checks before anyone relies on it. A certificate is only
as good as the independence of what checks it. If the checker shares a parser, a hash implementation, an
arithmetic library or a units crate with the code that produced the bundle, one defect can make both agree.

**ADR-WS-02 (DESIGN): `frob-cert` and its binary `frob-verify` depend on the Rust standard library and on
nothing else, and no proposer depends on them.** The rule is structural, in six parts:

1. `crates/frob-cert/Cargo.toml` has an empty `[dependencies]` table: no `frob-*` crate, no FrankenSim crate (so
   no units crate and no nightly feature), no async runtime, no `serde`. It inherits nothing from the workspace
   manifest.
2. It carries its own toolchain file naming a stable release. A copy of the directory alone builds with
   `cargo build --release` on that compiler. This also frees the auditor from the risk that the workspace
   nightly stops compiling the units crate.
3. It forbids unsafe code at the crate root, reads only the files named on its command line, opens no socket,
   reads no environment variable and spawns no process.
4. It implements for itself what it needs: a canonical JSON reader, BLAKE3 (checked against the published test
   vectors), exact integer and rational arithmetic, outward-rounded interval arithmetic, and the checkers for
   each certificate kind. Its cap of 12 thousand lines accounts for that.
5. No crate that produces a claim or a certificate depends on it. Only `frob-verbs` (to expose the check as a
   verb), `frob-cli` and `frob-conformance` may (rule L-9). The bundle writer lives in `frob-lemma` and is
   written against the schema, sharing no code with the reader.
6. A FrankenSymPy-based re-check of the same bundles runs in `frob-conformance` as a second opinion. It is an
   oracle for the auditor, never a part of it.

Counterexample to the shortcut "reuse `frob-core`'s hashing in the checker": a canonicalization defect in
`frob-core` that drops a field before hashing would be reproduced by the checker, and a bundle whose statement
differs from the one the proposer evaluated would pass. With two implementations the hashes disagree and the
bundle is rejected.

The crate and its end-to-end independence script are built by other beads. This bead is the every-commit guard:
the part of `check-deps` (one of the six checks of the `xtask` tool; tier Solid) that keeps the structure true
after the day it was first made true, and that reports the gate's first clause on every commit.

## Scope

In: the auditor rules of `check-deps` beyond the two manifest rules of BD-003; the shared-source scan; clause
(a) of GATE-WS-03 (the dependency count of `frob-cert` is zero) as a fact of the check's JSON report, measured
on every commit.
Out, with the bead that has it: the end-to-end script `auditor_independence.sh` (N25b-05, which depends on this
bead) that copies the crate, builds it offline and traces system calls, runs this check as one of its steps, and
assembles the gate's receipt from the four clauses under the conditions for `pass` (all four measured under one
resolution receipt, none on a dirty tree); the M1 run of that script with the corpus-wide clause and the record of
GATE-WS-03's M1 part (N25bp4-01, by a session that implemented none of the clauses, with N38b-19's `record_gate`).
This bead writes no gate row. Also out: the crate itself (BD-026); the corpus-wide verdict comparison between the standalone binary and the in-daemon verb
(N12-34); the second-opinion re-check (N12-10); the behavioural gates of the auditor (what it must accept and
reject), which belong to the certificate chapters.

## Technical approach

Rules added to `check-deps`, each with a stable identifier:

1. `cert.inherits-workspace`: any key in `crates/frob-cert/Cargo.toml` of the form `x.workspace = true` or
   `{ workspace = true }` (package fields, lints, dependencies). The manifest states edition, version and lints
   literally.
2. `cert.no-toolchain-file`: `crates/frob-cert/rust-toolchain.toml` is missing, or its channel is not a stable
   release of the form `1.N` or `1.N.P` (a channel beginning `nightly` or `beta` is a finding).
   `cert.toolchain-moved`: the channel differs from the value recorded in the stack lock's auditor row; a move
   is an ADR and a lock edit.
3. (Owned elsewhere.) A `src/lib.rs` or binary root of `frob-cert` without `#![forbid(unsafe_code)]` is
   `unsafe.cert-forbid` of `check-unsafe` (N34-07), the check that owns every unsafe-code rule. It is not
   repeated here: an earlier draft had a rule `cert.unsafe-not-forbidden` in this check, which would have
   reported one defect from two checks, against the one-owner rule of GATE-WS-01.
4. `cert.ambient-access` (source scan of `crates/frob-cert/src`): a path containing `std::env`, `std::net`,
   `std::process::Command`, `std::os::unix::net`, or an `extern "C"` block. The scan is textual and
   conservative; a false positive is resolved by rewriting the code, not by an allow-list.
5. `cert.source-escape`: a `#[path = "…"]` attribute or an `include!`, `include_str!` or `include_bytes!` whose
   argument resolves outside `crates/frob-cert/`; a symbolic link inside the crate directory; a `build.rs`.
6. `cert.shared-source` (the earliest signal of RISK-36): any source file under `crates/frob-cert/src` whose
   bytes, after removing blank lines and comment lines, are identical to a source file of another crate of this
   repository or of a sibling named in the stack lock, or that shares a run of 40 or more identical consecutive
   code lines with one (DESIGN threshold; the conformance crate's oracle files and test vectors are exempt by
   path). Implemented with rolling hashes over normalized lines; cost is linear in the tree.
7. `cert.writer-links-reader`: `frob-lemma` (the bundle writer) or any crate of layers 0 to 5 depends on
   `frob-cert`, directly or transitively through a crate of this repository other than the three allowed.
8. Facts in the report: the dependency count of `frob-cert` (must be 0, so `cargo tree -p frob-cert` prints one
   line), its line count against the 12 thousand cap, and the stable channel named.

**The gate and this bead's clause.** GATE-WS-03 (TARGET; claim Known answer; milestone M1 in the gate register)
has four clauses: (a) the dependency count of `frob-cert` is zero; (b) the copied directory builds on its stable
compiler with no network access; (c) the standalone binary and the in-daemon verb return identical verdicts on
the whole conformance corpus; (d) a system-call trace of an audit shows no network and no process creation.
Clause (a) is measured by this check on every commit and printed in its JSON report as
`facts.frob_cert.dependency_count` beside the line count and the stable channel; (b) and (d) are measured by
the independence script at M0; (c) by the corpus comparison at M1. The script of N25b-05 assembles the four
clauses into one receipt; the gate's row in `registries/gates.toml` has one recorder, N38b-19's `cargo run -p
frob-conformance --example record_gate -- --gate GATE-WS-03 --receipt <hash> --part M1`, run by N25bp4-01 at M1
from an M1 receipt: `pass` only when all four have measured values in the same resolution receipt, none measured
on a dirty tree, recorded by a session that implemented none of them; until then the part's status is
`not-run`, which the status table shows as open (DESIGN: an earlier draft of this bead assembled the row itself
and named the interim state `open`; one row has one recorder and the register's status word).

Determinism class D0.

## Acceptance criteria

- [ ] INV-WS-02 (`frob-cert` has no dependency and no proposer depends on it): on the clean tree the report shows
      dependency count 0 and no dependent outside `frob-verbs`, `frob-cli`, `frob-conformance`.
- [ ] Each of these plants in a scratch copy fails with its rule and exit 2: a `frob-core` dependency in
      `frob-cert`; `edition.workspace = true`; a nightly channel in the toolchain file; a `std::env::var` call;
      an `include_str!("../../frob-core/src/json.rs")`; a copy of a 60-line function from `frob-core` pasted
      into `frob-cert`; a `frob-cert` dependency in `frob-lemma`. A removed `forbid(unsafe_code)` is reported by
      `check-unsafe` (N34-07) and by nothing in this check.
- [ ] The shared-source scan reports no finding on the clean tree, and the auditor rules with the scan finish
      within their 3 s share of GATE-WS-04 (BD-004's table; TARGET).
- [ ] `cargo xtask check-deps --json` reports clause (a) of GATE-WS-03 with its measured value 0 on every commit
      from M0; the independence script (N25b-05) reads it into the gate's receipt, from which N25bp4-01 records
      the row; this bead writes neither.

## Test plan

### Unit tests

`cargo test -p xtask cert_rules` on `synthetic` scratch copies of a minimal `frob-cert`:
- `empty_deps_pass`; `any_dependency_fails`; `dev_dependency_fails`; `build_script_fails`.
- `workspace_inheritance_fails` (three spellings).
- `toolchain_stable_passes` (`1.99.0`); `toolchain_nightly_fails`; `toolchain_missing_fails`.
- `cert_forbid_is_not_reported_here`: a scratch copy without `#![forbid(unsafe_code)]` gives no `check-deps`
  finding (the rule is `check-unsafe`'s).
- `ambient_access_scan`: one case per forbidden path.
- `include_outside_crate_fails`; `path_attribute_outside_fails`; `symlink_fails`.
- `shared_file_detected`; `shared_40_line_run_detected`; `shared_39_line_run_not_reported`;
  `comment_and_blank_changes_do_not_hide_sharing`.
- `only_three_dependents_allowed`.

### End-to-end script and logging

`scripts/e2e/auditor_independence.sh` (bead N25b-05, which depends on this bead; its M1 run and the gate's
record are N25bp4-01's) is the script of this capability from the user's side. Its step 3a runs `cargo xtask check-deps --json`, with an `assert` line for the
auditor facts (dependency count 0, stable channel named, zero shared-source findings) and a `metric` line
carrying the gate's clause (a), logged in the structured format of STD-E2E beside the script's own clauses. The
step is specified in that bead; what this bead guarantees for it is the shape of the report's `facts` block.

## Considerations

- RISK-36 (the proposer and the checker share a defect; severity High; owner: Lemma lead). Earliest signals: a
  source file shared between `frob-cert` and a proposer; a checker dependency beyond the standard library.
  Mitigations: this ADR, rule L-9, GATE-WS-03, the checker-independence campaign, and a second checker if one is
  not enough.
- OPEN-WS-3 (owner: Lemma lead; decided at the first commit of `frob-cert`): which stable release the toolchain
  file names. Default: the newest stable release on that day, then moved only by ADR.
- Independence of implementation cannot be proved by a scan: two people can write the same bug twice. The scan
  catches copying; the mutation campaigns catch shared misunderstanding.
- The 40-line threshold trades false alarms on boilerplate against missed copying; test vectors and published
  constants (the hash's initialization values, for example) are data files exempt by path, not code.
