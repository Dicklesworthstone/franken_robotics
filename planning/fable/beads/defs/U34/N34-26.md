## Background

Every request to FrankenRobotics is admitted on its raw bytes before anything is planned. The gate that checks
this, **GATE-WS-05** (TARGET; claim Known answer; M0), requires that every duplicate member name and every bad
identifier of a golden corpus is refused on both surfaces (the `frob` command line and the MCP server)
**before a job identifier exists**. The admission order of `frob-verbs` promises more than the envelope shows:
a request refused in its first three stages (bytes, identifiers, schema) writes nothing at all: no ledger row,
no idempotency binding, no job identifier, no budget charge.

A promise of absence needs an observation, and at M0 the user's side has none. The verbs that list work arrive
later (`run.list` at M1, `job.list` at M2). The envelope of the refused call says "no `job` field", but that is
the claim under test, not an independent reading of the store. DESIGN: the operator verb `doctor`, which exists
at M0 and is read-only by contract, gains a **`ledger` block**: the row count of every table of the caller's
store and the store's last commit sequence. The end-to-end script of GATE-WS-05 reads the block before and
after each refused request and asserts that it did not change.

Why this is sufficient (reasoning). The ledger adapter (the trait `Ledger` over FrankenSQLite, module
`frob_fsim::ledger`) admits one writer at a time and assigns a monotone 64-bit commit sequence inside every
committing transaction. If the commit sequence read after a request equals the one read before it, no
transaction committed in between, so no `run` row, `episode` row, execution entry, binding or job row was
written. Row counts alone could be fooled by a delete followed by an insert; the commit sequence cannot. The
counts are kept because they say **what** changed when the assertion fails, which is what a person debugging
the admission order needs first.

Where it sits: `frob-verbs`, operator cluster, kind `read`, tier Solid, first milestone M0. It serves the
workspace chapter's rule that a refused request leaves no trace that looks like work.

Rejected alternatives: (1) the test opens the ledger file with a database tool (a second reader of a store the
project reaches through exactly one adapter, and nothing promises that FrankenSQLite's file is readable by
another tool); (2) bring `run.list` and `job.list` forward to M0 (they need the full ledger schema, namespaces
and frontier-pinned pagination, which are M1 and M2 work); (3) a hidden flag or a test-only verb (the registry
is the surface: a path agents cannot see is a path nobody else tests); (4) trust the refusal envelope (it is
the statement being checked).

## Scope

In: the `ledger` member of `frob.doctor.out/1` and its section name (`--section ledger`); the read-only count
function over the ledger adapter; the schema addition and its example; findings for an unclean or unreadable
store; unit tests; the script `scripts/e2e/doctor_ledger.sh`.
Out: `doctor`'s other blocks and the verb skeleton (BD-022); the `Ledger` trait, its M0 tables and its recovery
rules (BD-009); the rows that `sim.run` writes (BD-024); the admission order whose silence this block observes
(N34-20); the golden corpus, the surface run and the gate record (N34-21, which reads this block); `run.list`
and `job.list` (the Chronicle and job-protocol beads at M1 and M2; from then on they give the same observation
by name, and this block stays as the store-level reading); the full ledger schema (BD-090), whose new tables
this block reports without a code change.

## Technical approach

**The block** (DESIGN; the field spellings are fixed here). Example after two `frob sim run` invocations of one
manifest on a fresh store, each under its own idempotency key (the same key twice would return the first
invocation's stored receipt and run nothing, BD-024's re-execution rule):

```json
"ledger": {
  "present": true,
  "store_digest": "b3:<BLAKE3 of the store path's canonical text>",
  "schema_version": "1",
  "recovered": "clean",
  "commit_seq": "2",
  "tables": [
    {"table": "episode", "rows": "1"},
    {"table": "execution", "rows": "2"},
    {"table": "meta", "rows": "1"},
    {"table": "run", "rows": "1"}
  ],
  "work_rows": "4"
}
```

Rules.

1. **Read-only.** The store is opened through the adapter with a read-only option. `doctor` never creates a
   store: when no ledger exists at the store path the block is `{"present": false, "commit_seq": "0",
   "tables": [], "work_rows": "0"}`, and that is not a finding. No transaction is begun.
2. **Adapter additions** (DESIGN; an open option and three read methods on the trait of BD-009, no schema
   change, no sibling type made public): `OpenOptions::read_only()`; `fn count(&self, table: TableId) ->
   Result<u64, LedgerRefusal>`; `fn last_commit(&self) -> CommitSeq`; and `fn tables(&self) -> Vec<TableId>`
   listing the tables the opened schema version declares. If the adapter as delivered already offers
   equivalents, they are used unchanged.
3. **Integers as strings.** `commit_seq`, every `rows` and `work_rows` are decimal strings, because each is a
   64-bit integer and the envelope carries integers that can exceed 2⁵³ − 1 as strings.
4. **Tables.** `tables` lists every table of the opened schema version, sorted by name in code-point order. A
   table added by a later migration (`job`, `chunk`, `frontier`, a binding table) appears with its count and
   needs no change here. `work_rows` is the sum of `rows` over every table except `meta`.
5. **Nothing but counts.** No row key, payload, identity or path is printed. The store path appears only as a
   digest, because a ledger may later hold identities of private scenes.
6. **Findings** (one finding each, with a repair, in BD-022's finding shape; `doctor` repairs nothing; severity
   `low` for `ledger.recovered` and `high` for the other two, so each gives exit 2): `ledger.recovered` when
   the adapter's recovery report is not `clean` (repair: re-run the interrupted command; the report names
   whether an incomplete transaction was rolled back or a complete one replayed); `ledger.integrity` when the
   structural check fails (repair: restore the store from its last good copy; never read it as valid);
   `ledger.schema-newer` when the store's schema version is newer than the binary (repair: use a newer `frob`).
7. **Cost.** `doctor` must stay fast. With `--section ledger` the block is always computed. Without a section
   argument it is computed if counting takes under 200 ms (TARGET) and otherwise replaced by `{"present": true,
   "skipped": "budget"}`; the gate script always passes `--section ledger`.
8. **Surfaces.** The same block is returned by the MCP tool `doctor`, generated from the same registry entry;
   no new verb and no new flag is added.

Evidence on the block, as on the rest of `doctor`: class `Tested`, tier `static`, determinism `exact`,
`claims: []`, `reality: no-claim`. For a given store state the block is a pure function of the store
(determinism class D0). Nothing is recorded in the ledger by reading it.

**How GATE-WS-05 uses it.** For each refused corpus entry the script reads the block, submits the entry, reads
the block again and asserts the two `ledger` members have equal canonical bytes. At M0 "no job identifier
exists" is read as: the commit sequence is unchanged and no `run`, `episode` or `execution` row was added.
Budget: at M0 there is no persistent budget (a call carries its own `--budget`, and sessions are declared but
not yet served), so an envelope `cost` of zero together with an unchanged commit sequence shows that nothing
was charged; once session budgets exist, the session's own reading is asserted beside this one.

## Acceptance criteria

- [ ] `frob doctor --section ledger --json` on a fresh store path prints `present: false`, exits 0 and creates
      no file (the directory listing before and after is equal).
- [ ] After one `frob sim run g1 --tier referee --seconds 2 --key dl-run-1 --json` on the built-in model the
      block shows `run` 1, `episode` 1 and `execution` 1; after a second invocation of the same manifest under
      another key (`--key dl-run-2`) `execution` is 2, `run` and `episode` are unchanged and `commit_seq` has
      increased.
- [ ] After a refused request (`frob sim run --args '{"secondz": 2}' --key dl-refused-1 --json`: an unknown parameter, refused by
      the verb's schema stage with FROB-REF-802, exit 3) the `ledger` member has the same canonical bytes as
      before the request. DESIGN: the instrument is proven on a refusal the verb skeleton already issues, so
      that this bead does not wait for the admission order it observes; the duplicate-member and identifier
      refusals are N34-20's, which depends on this bead, and are read through this block by N34-21.
- [ ] One hundred consecutive `doctor` calls leave the store file's hash unchanged.
- [ ] Every count and the commit sequence are strings; `tables` is sorted; the example of `frob.doctor.out/1`
      with the block validates, and `frob schema --verb doctor --out --json` shows the block.
- [ ] The MCP tool call returns a `ledger` member with canonical bytes equal to the command line's.
- [ ] The block contains no path, key or payload: a scan of the output for the store path and for every row
      key written by the test finds none.
- [ ] A store with a planted newer schema version gives exit 2 with `ledger.schema-newer`; a store left by a
      killed writer gives a `recovered` value other than `clean` and the finding `ledger.recovered`.
- [ ] The planted early write (below) makes the before-and-after comparison fail.
- [ ] The block is reachable through `frob --json`, documented in the `CONTRACT.md` of `frob-verbs`, and a
      Ctrl-C during `doctor --section ledger` yields one envelope and no stray output.

## Test plan

### Unit tests

`cargo test -p frob-verbs doctor_ledger`, with the real adapter on a temporary store on disk (no mocks):
- `absent_store_is_not_created`: block is the absent form; the directory is still empty.
- `counts_follow_writes`: two transactions put 3 rows in `run` and 2 in `episode`; the block shows "3" and
  "2", `work_rows` "5", and `commit_seq` grew by 2.
- `rollback_leaves_block_unchanged`: a transaction dropped without commit changes no member.
- `tables_sorted_and_strings`: order and JSON types.
- `new_table_appears_without_code_change`: a `synthetic` schema version that declares an extra table `job`
  lists it with "0".
- `work_rows_excludes_meta`.
- `newer_schema_is_finding`; `unclean_recovery_is_finding`; `integrity_failure_is_finding` (one flipped byte
  in a data page of a closed store).
- `block_has_no_payload` (property): for generated row keys and payloads, the output contains none of them.
- `doctor_is_read_only`: store hash equal before and after 100 calls.
- `skipped_only_without_section`: with the counting limit (a parameter of the count function, 200 ms by
  default) set to zero, plain `doctor` returns the skipped form and `--section ledger` returns the counts.

### End-to-end script and logging

`scripts/e2e/doctor_ledger.sh` (header `bead=N34-26 milestone=M0 labels=workspace,tether,verb`; plain shell;
sources the shared helper of STD-E2E; idempotent on a scratch store; `--seed` is passed to `sim.run`): (1) `frob doctor --section ledger --json` on an empty scratch store;
(2) `frob sim run g1 --tier referee --seconds 2 --key "$(e2e_key run-1)" --json`, then the same manifest with
`--key "$(e2e_key run-2)"`, reading the block after each (two keys, so that the second invocation executes; every
run-verb call of the script, the refused one included, carries a key issued by `e2e_key`); (3) the refused request of the
acceptance list (an unknown parameter) on the command line and the same request as an MCP tool call over
stdio, reading the block before and after each;
(4) one hundred `doctor` calls with the store's hash compared; (5) the planted-store cases for the three
findings. It asserts the counts and equalities of the acceptance list. It logs to
`target/e2e-logs/doctor_ledger/<utc>.ndjson` with a transcript beside it; every line has `ts`, `script`, `bead`,
`step` (the numbered step above) and `event`: every `cmd` with exact command line,
exit code and wall time; the envelope's `evidence` block; one `assert` line per comparison with the canonical
digests of the two blocks and, on failure, the first differing member and the path of both saved envelopes; a
`metric` line with the wall time of `doctor --section ledger` against 200 ms; a `summary` line with assertions
passed and failed and the gate served (GATE-WS-05, touched, not recorded here). Only the built-in model is
used; no private-scene data can reach the log. The gate's own script, `scripts/e2e/canonical_json.sh`
(N34-21), calls the same reading in its surface step.

### Known answers and negative controls

Known answers: a fresh store reads as absent with zero counts; two referee runs of one manifest under two keys
give one `run` row, one `episode` row and two execution entries; a refused request leaves the block byte-identical. Negative
controls, registered against GATE-WS-05 in the conformance crate's control registry: a build of `sim.run`
that writes its `run` row before stage 1 of admission (the before-and-after comparison must fail); a `doctor`
build that opens the store for writing and touches a `meta` row (`doctor_is_read_only` must fail); a count
function that omits the `execution` table (`counts_follow_writes` must fail). Metamorphic relations: reading
twice changes nothing; the order of two independent writes does not change the final counts. Determinism
lanes: twice on one machine, debug and release, Linux and macOS: equal canonical bytes of the block for equal
store states (class D0).

## Considerations

- The block is an instrument for a gate, not a query surface. It must not grow filters, listings or
  identities; those belong to `run.list` and `job.list`.
- If FrankenSQLite at the pin cannot count a table without scanning it, counts are still exact and the 200 ms
  rule above keeps plain `doctor` fast. If the ledger's admission fails and the append-only JSON-lines fallback
  is in use, counts come from a scan of that file and `commit_seq` is the number of complete transactions in
  it; the block's shape does not change.
- OPEN (owner: the job-protocol beads; due with the idempotency protocol at M2): whether idempotency bindings
  live in the ledger or in a store of their own. Fail-closed default: the gate script asserts the commit
  sequence here and, once it exists, `job.list` as well; if bindings get their own store, its commit sequence
  is added to this block as a second member before that store ships.
- When the daemon serves requests, `doctor` reads the daemon's store through the daemon; the meaning of the
  block is unchanged.
- Risk: `work_rows` is mistaken for a progress measure. The registry description of `doctor` says what the
  block is for.
- Security and privacy: counts and a digest only; the store path and row contents never leave the process.
