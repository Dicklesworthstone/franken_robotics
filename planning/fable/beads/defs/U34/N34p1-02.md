## Background

FrankenRobotics identifies every artifact by the BLAKE3 hash of its canonical bytes under a domain string equal
to its schema name, and keeps one registry of its thirteen artifact formats (`registries/formats.toml`): one
identifier, one schema name with a major version, one owner crate and one canonical encoding each; everything
else is a view, which is never hashed, signed or cited. Two formats land at M3 and are both **canonical and
derived**: their bytes are reproducible from the identities of their inputs.

- The clearance complex `.fclear` (`frob.clearance/1`, owner `frob-scene`): two-sided cells, path witnesses and
  component cuts computed from a scene and a footprint family by `scene.fit` (BD-233). Consumed by
  `frob-analyze`, `frob-mission` and `frob-lemma`.
- The minimal counterexample world `.fmcw` (`frob.mcw/1`, owner `frob-nemesis`): the output of the shrinker of
  `nemesis.shrink` (BD-274). Consumed by `frob-arena` (regression batteries), `frob-autopsy`, `frob-mission` and
  the viewer.

**GATE-WS-02** (TARGET; claim Known answer; M1 for the formats that exist, then at each new format; complete at
M5): for each format, 10,000 seeded round trips canonical → value → canonical with zero byte differences; where a
view exists, 10,000 round trips view → canonical → view with zero differences; every one of 10,000 single-byte
mutations either fails to parse or changes the identity; and each reader survives 10⁷ fuzz executions with zero
panics before the format's first release. Negative control: a reader built with key-order canonicalization
disabled must fail the first clause.

Both formats are first released with M3, so their gate lane is due at M3. They are one bead because they share
the one clause no earlier format needed, re-derivation, and its live-dependency proof. Tier: Solid (the
subsystems are partly Frontier; the registry rule is not).

## Scope

In: the two rows in final form; each owner's `Subject` and named conformance tests; the re-derivation clause;
the flags clause of `.fmcw`; the gate-lane run and two records; the two rows of the script's verb table. Out:
the formats themselves (BD-233, BD-274); the harness (N34-22); the script (N34-23); `.fscene` (N34p1-01); the
M4 formats (N34p1-03); the build packet and the thirteen-of-thirteen record (BD-410).

## Technical approach

**Rows and number rules** (registry rule 4; DESIGN defaults proposed here, confirmed or replaced by each owner's
contract; a row without a number rule does not load):

| Format | Number rule | View kind |
|---|---|---|
| `.fclear` | The owner's layout (N19b-27): cell bounds are not JSON numbers but little-endian `i16` millimetres in the cell blob, outward-rounded when computed (c_lo down, c_hi up) and never re-rounded by the writer; lengths in the manifest are exact decimal strings in metres, so identity never depends on a float parser; counts and indices are JSON integers below 2⁵³ (above it, strings); no NaN or infinity | None |
| `.fmcw` | World parameters as the shortest round-trip decimal of their binary64 values; seeds, counter keys and tick indices as decimal strings | None (the viewer's rendering is an `export` view with no identity) |

**Re-derivation clause** (`fmt_<ext>_rederive`): "canonical and derived" means reproducible from the identities
of its inputs. For 100 seeded inputs, regenerate the artifact from the input identities alone (for `.fclear` the
full derivation key of N19b-27: scene identity, footprint family, slab, fixture-mode assignment, movables setting,
lattice, producer settings and refinement request, through the reader's `verify_derivation`; for `.fmcw` the
promoted failure's identity, the candidate and the shrink settings) and compare bytes and identity with the stored
artifact: zero differences. A derived artifact lists its
input identities in its manifest, and changing one input identity changes the artifact's identity (the
live-dependency proof: an input that does not move the output is a stale cache waiting to happen).

**Flags clause for `.fmcw`** (registry rule 6): a counterexample world spells the object `no_authorization`
with the three fields `execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`, all `false`; a
file edited to `true` or with a field removed is refused on read. An exported `.fclear` carries the same three
fields under the export's `authorization` object, the schema name and the writing binary's stack receipt.

**Work:**
1. Confirm both rows against the landed crates; regenerate `schemas/`; `check-generated` clean.
2. In `crates/frob-scene/tests/conformance.rs` and `crates/frob-nemesis/tests/conformance.rs`: the `Subject`
   generators (reaching every schema field: cells, witnesses, cuts; world parameters, the failure's address, the
   shrink trace) and the tests below.
3. Script rows: `.fclear | M3 | frob scene show (the feasibility block) | frob scene fit on a built-in scene and
   footprint family`; `.fmcw | M3 | frob sim replay of the world file (the reader BD-274's own script uses) | frob
   nemesis shrink on a planted failure`.
4. Release identities (CX-359): three fixed-seed fixtures per format are committed under
   `crates/frob-conformance/fixtures/formats/fclear/` and `…/fmcw/`, and their rows (format identifier, fixture
   path, identity, first release `M3`, with the toolchain, commit and resolution receipt) are appended to
   `crates/frob-conformance/fixtures/formats/release_identities.toml`, the file BD-141 creates; its test
   `fmt_release_identities_hold` recomputes them, and BD-410 compares them again at M5.
5. Gate lane: `scripts/e2e/format_registry.sh --formats fclear,fmcw --lane gate`; two records (clause counts,
   differences, executions, panics, re-derivation differences, control outcome, seed, commit, receipt, host
   fingerprint), each written by a session that did not implement the formats with `cargo run -p frob-conformance
   --example record_gate -- --gate GATE-WS-02 --receipt <hash> --part M3` (there is no `frob conformance` command). The gate row prints the count of passed formats of thirteen ("10 of 13" once `.fscene` has
   passed), still partial.

Determinism class D0 for every clause. Evidence class of the records: Tested.

## Acceptance criteria

- [ ] GATE-WS-02 for `.fclear` and `.fmcw`: 10,000 round trips each with 0 byte differences; 10,000 mutations each
      with 0 accepted-unchanged; 10⁷ fuzz executions each with 0 panics; the key-order control caught; recorded
      before the M3 release.
- [ ] Each format re-derives from its input identities with 0 byte differences over 100 seeded cases; changing
      one input identity changes the artifact's identity in every case.
- [ ] `.fmcw` carries `no_authorization` with three `false` fields; `true` or a removed field is refused.
- [ ] `release_identities.toml` holds three rows for each of the two formats with first release `M3`, and
      `fmt_release_identities_hold` passes with them.
- [ ] Both generators reach every schema field; the script's gate line prints the true count of thirteen and
      no pass.

## Test plan

### Unit tests

`cargo test -p frob-scene --test conformance fmt_fclear`: `fmt_fclear_roundtrip`, `fmt_fclear_refusals`
(unknown major version → FROB-REF-891 or the owner's own code; unknown member at two depths; duplicate member;
a view on the identity path → FROB-REF-892), `fmt_fclear_mutations`, `fmt_fclear_rederive`,
`fmt_fclear_input_identity_is_live`. `cargo test -p frob-nemesis --test conformance fmt_fmcw`:
`fmt_fmcw_roundtrip`, `fmt_fmcw_refusals`, `fmt_fmcw_mutations`, `fmt_fmcw_rederive`,
`fmt_fmcw_input_identity_is_live`, `fmt_fmcw_flags`. Fuzz targets `fmt_fclear_read`, `fmt_fmcw_read` (10⁵ in the
commit lane, 10⁷ in the gate lane).

### End-to-end script and logging

`scripts/e2e/format_registry.sh --formats fclear,fmcw` (commit lane) and `--lane gate`, steps 1 to 11 of the
script for each format, plus a re-derivation step: the writing verb is run a second time on the same inputs in a
fresh scratch store and the identities must be equal. NDJSON through the STD-E2E helper to
`target/e2e-logs/format_registry/<utc>.ndjson`: `bead: "N34p1-02"`, step, event, exact command line, exit code,
wall time, the envelope's `evidence` block, both identities of the re-derivation, `metric` lines per clause with
thresholds (differences 0, executions 10⁷, panics 0, re-derivation differences 0), the control's outcome, digests
of exported files, and on failure the first failing index, seed and saved artifact path; a `summary` line with
the count of passed formats of thirteen.

### Known answers and negative controls

KA-781 (respellings bind one identity) and KA-782 for both formats (exact; tier G3 on the host). Counterexamples:
CX-358, CX-359 (identities recorded at this first release are compared at M5), CX-360, CX-361. Negative controls:
the `writer-no-key-sort` build (N34-18's mutant, N34-CX's plant 1 of CX-358); a derived artifact regenerated with one input identity changed (must differ); a writer
planted to omit one input identity from the manifest (the live-dependency test must fail); a flag set to `true`
in an `.fmcw`. Determinism lanes: commit lane twice on one machine; debug and release; Linux and macOS.

## Considerations

- Re-derivation of `.fmcw` runs the shrinker, which can be expensive; 100 cases use the smallest planted failures
  of BD-274's fixture set and stay inside the default machine envelope under the envelope guard.
- A clearance complex is a certificate input to `frob-lemma`; a byte difference on re-derivation is a defect in
  the clearance computation's determinism, not in this gate, and is filed against BD-233.
- If either subsystem falls back at its kill gate before M3, its row is recorded under the fallback's name or
  tombstoned by ADR; the count of thirteen changes only by that ADR.
