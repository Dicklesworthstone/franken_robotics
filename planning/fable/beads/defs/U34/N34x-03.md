## Background

Three small files of the workspace are validated against hand-written schemas that ship with the first commit:
each crate's `contract.toml` against `schemas/contract.schema.json`; each release path's `demos/<id>/demo.yaml`
against `schemas/demo.schema.json`; and the thirteen rows of `registries/formats.toml` against the registry's
row schema under `schemas/registries/`. The first-commit bead writes those schemas from the plan's first
description: a demo has `demo_id`, `claim_ids`, `commands` and `checksums`; a format row has identifier,
extension, schema name, owner crate, producers, consumers and canonical-or-view; a contract has layer and rank,
determinism class, evidence class, budgets, feature flags and safe mode. All three validations refuse an unknown
key, which is the point of a schema.

The beads that later read these files need more keys, each for a stated reason:

| File | Key | Read by | Why |
|---|---|---|---|
| `demo.yaml` | `tier` | The demo executor (N00-29) and runner (N34-12) | A demo runs on the CPU tier; one that names a device tier is refused unless the runner is invoked for that tier on a host that has the device |
| `demo.yaml` | `expect_exit`, `expect_refusal` | The demo executor | A demo may demonstrate a refusal: exit 3 with a named code is then the expected outcome, and a refusal path is a legitimate release path; a command expected to complete with findings declares exit 2 |
| `demo.yaml` | `compare` | The demo executor | An output that is not deterministic at class D0 or D2 on the CPU tier cannot have a checksum; the demo lists the fields compared exactly instead |
| `demo.yaml` | `expect` | The demo executor | A command's envelope must contain a JSON subset saved in a file of the demo directory |
| `demo.yaml` | `title`, `milestone`, `actors`, `lane`, `fresh_agent`, `not_evidence_for` | The North-Star harness (N00-29): its index runner, two-lane rule and fresh-agent rule | One form for every demo file, the scenarios' and the release demos' alike, because one executor and one index read them all |
| format row | `float_rule` | The registry loader | Each owner names one rule for floating-point fields that bear identity (shortest round-trip decimal, or exact rationals); a row without one fails to load if its schema has a binary64 field |
| format row | `view_kind` | The round-trip harness | A `lossless` view is in bijection with the canonical form and is tested in both directions; an `export` view is a one-way rendering |
| format row | `writer` | The single-parser search | The certificate bundle's writer is a different crate from its owner and reader; the search exempts the declared writer for that row only |
| format row | `auditor_reader` | The single-parser search | The offline auditor's standard-library-only reader of a run bundle is the one sanctioned second implementation, listed by path |
| format row | `decision` | The registry loader | A row beyond the thirteen plan formats exists only by the owner's ruling on schema-named files (N34-27), and the loader refuses such a row without the citation |
| `contract.toml` | `plane`, `[api.float_ok]`, `[[replaces]]`, `[[controller]]`, `verbs`, `[[gate]]` | The contract check and three conformance checks | Each is added to the schema by the bead that introduces it (the contract check's rule) |

For the contract the rule "the introducing bead adds its key" has an owner per key. For the demo file the owner
is now the first-commit bead: BD-002 ships all eleven optional demo keys in `schemas/demo.schema.json` at M0,
because the M0 scenarios use them and the static check refuses an unknown key (an earlier text of this bead
added them at M1, which would have been a second definition, one milestone late). For the format row the rule
still has no owner: the format-type bead puts the registry file and its schema out of scope, and the
first-commit bead predates the fields. A row that carries `float_rule` would then fail validation on the day it
lands. This bead adds the five format-row fields; for the demo file it adds no key and pins the shapes of the
eleven (whose meaning the demo harness N00-29 defines and governs), tightening the first-commit schema in place
where it states only a bare type; and, for all three files, it adds a test that makes the gap impossible to
reopen. Tier: Solid.

Rejected: generating the three schemas from the reader types (it would change the first commit's hand-written
schemas into generated files and move them under another check; possible later, not needed to close this);
allowing unknown keys (a misspelt key would then be ignored, which the project's standing rule forbids: a
misspelt parameter is a refusal, not a default).

## Technical approach

**1. The demo keys: none added; their shapes pinned (DESIGN; the keys are in `schemas/demo.schema.json` from the
first commit, BD-002; the meaning of each is N00-29's).** BD-002 states each key with its type (`tier`: `cpu` or
a device tier; `expect_exit`: an integer exit code; `expect_refusal`: a refusal code; `compare`: a list of
`result` fields; `expect`: a path; `title`: a string; `milestone`: `M0` to `M8`; `actors`: a list of strings;
`lane`: `cpu`, `device` or `long`; `fresh_agent`: a boolean; `not_evidence_for`: the constant `numbers`). The
shapes below agree with those types and are narrower in four places (the enumeration of `tier`, the values of
`expect_exit`, the non-empty pointer list of `compare`, the form of an actor's name); this bead edits the
hand-written schema to state the narrower form, and `demo_schema_cases` holds one accepted and one rejected
case for each. No property is added or removed: the schema has fifteen properties before and after.
The per-command expectations are maps keyed by the command line exactly as `checksums` is (N00-29, N34-12), and
each map's keys must be members of `commands` (checked by the contract check's demo group, since JSON Schema
cannot compare two members):
- `tier`: one of `cpu`, `gpu-cuda`, `gpu-metal`; default `cpu`; a release cell that needs a device cites a
  device receipt, so a non-CPU demo is the exception.
- `expect_exit`: a map from a command line to an integer, one of 0, 2, 3; a command absent from the map expects
  "0 or 2". Other exit codes are not demonstrable outcomes (4 to 7 depend on the host's budgets, devices and
  concurrent state; 8 is not final; 9 is indeterminate).
- `expect_refusal`: a map from a command line to a refusal code string; a command is in it exactly when its
  `expect_exit` is 3; the code must exist in `registries/refusals.toml` (checked by the contract check's demo
  group, not by JSON Schema).
- `compare`: a map from a command line to a non-empty list of JSON Pointers into the command's `result`. For a
  command whose `expect_exit` is 3 neither a checksum nor a comparison is required (its outcome is the refusal
  code); for every other command exactly one of `checksums[command]` and `compare[command]` is present (checked
  by the demo group, rule `demo.expectation-shape` of N34-09).
- `expect`: a map from a command line to a relative path of a JSON file inside the demo directory (by
  convention under `expected/`), the subset the envelope must contain.
- `title`: a non-empty string. `milestone`: `M0` to `M8` (the North-Star scenarios are tagged M1 to M5 and M7,
  NS-24 being the M7 tournament; a release demo may belong to any milestone). `actors`: a non-empty list of distinct lower-case
  hyphenated names. `lane`: one of `cpu`, `device`, `long`. `fresh_agent`: a boolean, default false.
  `not_evidence_for`: the constant `numbers` (a demo shows a path runs and is never evidence for a claim's
  numbers; the key exists so that the statement travels with the file).

**2. The format-row schema gains (DESIGN):**
- `float_rule`: `shortest-roundtrip`, `exact-rational` or `none` (`none` only when the format's schema has no
  binary64 field; the loader checks that against the generated schema).
- `view_kind`: `lossless`, `export` or `none`; a row whose canonical-or-view text names a view must not say `none`.
- `writer`: a crate name; present only when the writing crate differs from the owner (the certificate bundle).
- `auditor_reader`: a list of file paths inside `crates/frob-cert/`; present only on the run-bundle row.
- `decision`: a path under `docs/adr/` (the record of N34-27's ruling, `docs/adr/ADR-WS-06-format-rows.md`;
  every decision record lives in that directory); required on every row beyond the thirteen plan formats and
  forbidden on the thirteen (the loader of N34-19 holds the thirteen identifiers as a constant list; N34-27).

**3. Key tables (DESIGN).** Each strict reader is driven by a table of the keys it accepts, and exposes it:
`pub const KEYS: &[KeySpec]` with `path` (dotted, `[]` for arrays), `required`, and `owner` (the bead that
introduced the key). The readers concerned: the contract reader of the contract check; the demo reader shared by
the static demo check and the runner; `FormatRow`'s loader. A reader that accepted a key outside its table would
not compile, because the table is what it dispatches on.

**4. The agreement test.** `crates/xtask/tests/schema_keys.rs` loads each schema file and each key table and
asserts, per file kind:
1. every key path in the table is a property of the schema, with the same requiredness;
2. every property of the schema is in the table (a schema key that no reader reads is dead and fails);
3. the schema sets `additionalProperties: false` at every object level;
4. every `owner` names a bead key present in the commit's bead export, when one is present (skipped, and logged
   as skipped, outside the tracker's checkout).
A file kind with a schema and no reader yet is reported `pending: <file kind>` until the M1 exit and is an
error after it.

**5. Where it runs.** The test is an ordinary `cargo test -p xtask` target; it adds no subcommand, so the number
of workspace checks stays six. Determinism class D0. Nothing enters the run ledger.

## Acceptance criteria

- [ ] `schemas/demo.schema.json` accepts a demo with `tier: cpu`, a demo whose command has `expect_exit` 3 and
      `expect_refusal` `FROB-REF-103`, a demo with `compare` for one command, and a `synthetic` demo that uses all
      eleven optional keys (N00-29's worked example `demos/ns-01/demo.yaml`, which uses nine of them, is accepted
      as well, and so is `milestone: M7`); it rejects (by schema or by the demo group, which
      the case names) a command with `expect_exit` 3 and no code, a code for a command whose `expect_exit` is
      not 3, `expect_exit` 4, a command with both a checksum and a comparison, `lane: gpu`,
      `not_evidence_for: claims`, and an expectation keyed by a command line that is not in `commands`. The
      schema's property set is BD-002's fifteen, unchanged by this bead (`demo_schema_has_fifteen_keys`).
- [ ] The format-row schema accepts the thirteen rows with `float_rule` and `view_kind` on each, `writer` on the
      certificate row and `auditor_reader` on the run row; it rejects `writer` equal to the owner,
      `auditor_reader` on any other row, a fourteenth row without `decision`, and `decision` on one of the
      thirteen.
- [ ] The agreement test passes on the three schemas; each of its four clauses has a planted failure it catches.
- [ ] A key added to a reader's table without a schema entry fails the test naming the key and its owner bead;
      a schema property with no table entry fails naming the property.
- [ ] Every contract key listed in the table above is present in schema and table with its introducing bead as
      owner, at the milestone of that bead.
- [ ] The count of `xtask` subcommands is still six.

## Test plan

### Unit tests
`cargo test -p xtask --test schema_keys` (the real schema files; planted schemas and tables are in-memory
copies labelled `synthetic`):
- `demo_keys_agree`; `format_row_keys_agree`; `contract_keys_agree`.
- `table_key_missing_from_schema_fails`; `schema_key_missing_from_table_fails`;
  `open_object_fails` (an object level without `additionalProperties: false`); `requiredness_mismatch_fails`.
- `demo_schema_cases`: the accepted demos (five, one with `milestone: M7`) and the seven rejected demos of the
  first criterion; `milestone: M9` is rejected; the four narrowed shapes each have a rejected case (`tier:
  gpu`, `expect_exit` 5, an empty `compare` list, an actor `Fresh Agent`).
- `demo_schema_has_fifteen_keys`: the property names of the schema are exactly the four required and eleven
  optional keys of BD-002; a sixteenth fails.
- `expectation_maps_keyed_by_command`: each of `expect_exit`, `expect_refusal`, `compare` and `expect` given as
  a scalar is rejected; given as a map keyed by a listed command it is accepted.
- `format_row_schema_cases`: the accepted thirteen, a `synthetic` fourteenth with `decision`, and the four
  rejected rows.
- `pending_reader_reported_then_error`: with the milestone marker at M0 the missing reader is `pending`; at the
  M1 exit it fails.

### End-to-end script and logging
`scripts/e2e/schema_keys.sh`: (1) `cargo test -p xtask --test schema_keys`; (2) `cargo xtask check-contracts
--json` on a scratch tree holding one demo with each optional key and the thirteen format rows with their five
new fields, asserting no schema
finding; (3) the same tree with a misspelt key `expect_refusl`, asserting exit 2 and a finding that names the
file, the line and the unknown key; (4) `frob --json schema frob.envelope/1` as a smoke check that the binary
under test is the commit's. It logs through the STD-E2E helper to
`target/e2e-logs/schema_keys/<utc-timestamp>.ndjson`: `cmd` lines with exact command line, exit code and wall
time; `metric` lines for keys per file kind in table and in schema; one `assert` per clause and per plant with
the first differing key; a `summary` line. No private-scene data is involved.

### Known answers and negative controls
- Known answers: fifteen keys in the demo schema (the first commit's four required and eleven optional ones),
  none added here; five fields added to the format row; thirteen format rows.
- Negative controls (each must be caught): the misspelt demo key; a reader table with a key the schema lacks; a
  schema with a dead property; an object level left open; a `writer` on a row whose owner writes it.
- Metamorphic: reordering properties in a schema or entries in a table changes nothing.
- Determinism: pure functions of files in the tree, equal twice on one machine and across platforms.

## Considerations

- The enumeration of `tier` follows the tier names the surface uses; if a tier is renamed, the schema and the
  runner change in one commit and the test holds them together.
- `expect_exit` is deliberately narrow. A demo that needs exit 4 to 7 is demonstrating the host, not the product.
- The first-commit schemas stay hand-written. If a later decision generates them from the key tables, this test
  becomes the generator's check and the tables stay the single source.
- What would make us revisit: a fourth hand-written schema with a strict reader; it joins the test by exposing
  a key table.
