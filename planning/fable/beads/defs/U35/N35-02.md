## Background

Every result records a determinism class (D0 exact; D1 bitwise across backends; D2 bitwise per backend, run to
run and independent of batch size, slot, co-tenant worlds, bucket capacity and shard count; D3 agreement inside
a recorded envelope together with agreement of task decisions; D4 nothing). A class is **claimed by a contract
and tested**: a kernel's manifest claims a class, and the Gauntlet's determinism tier (G5) and the gates
measure whether a device family actually holds it. Something has to read those measurements and decide which
class a given run may print. That component is the determinism classifier. Other parts of the system ask it
two questions: "which class did this backend attain for this kernel set?" (memoized episodes, forks, teleport,
paired comparison) and "what class is this run?" (every envelope).

Two rules bind it. The weakest input wins: the class of a result is the weakest class among the kernels,
placements, profile and inputs that produced it (INV-NUM-06). A class is never raised by relabelling, only by
running again under a stricter profile. And one posture: fail closed. A kernel set with no current record on a
device family is of unrecorded class, which every consumer treats as D4.

Why it matters. Past simulators' GPU kernels passed tests and diverged in the field, so nobody trusted fast
results (failure mode 3 of the program's risk review; its detector is a world whose digest depends on the
batch it ran in, or divergence-ledger entries without explanations). RISK-04: bit equality across backends may
be unattainable on a device family; the mitigation is that each family's best attainable class is measured and
recorded, class D3 with the decision-level test is used where D1 fails, and the property claimed is
batch-composition invariance, with bit equality only where D1 is attained. The classifier is where that
mitigation becomes mechanical. Tier: Solid. It serves BET-02 (one source, three backends, inside declared
determinism classes).

## Scope

In: the attestation record and its currency rule; the classification algorithm for a kernel set on a placement
and for a pair of placements; the class of a run; the per-family D1 status and the consequences of KILL-D1;
the wording table; negative controls. Out: the measurements themselves (`spark.check` and its sweeps, BD-176;
the invariance gate, BD-181; the decision-level test, BD-177; exact-kernel byte equality, BD-030); the type
(N35-01); profiles (N35-04); licences (N35-07).

## Technical approach

**Attestation record (DESIGN; `frob.detrecord/1`, stored in the divergence ledger beside the check rows).**

```text
key        kernel_set (sorted KernelIds, or a StepPlanId) · placement pattern (backend per stage) ·
           device family · fingerprint digest (hardware, driver, compiler) · determinism profile
evidence   exact_bytes     : pass | fail | absent     byte equality of exact and guarded kernels on every backend
           repeat          : pass | fail | absent     identical digests twice, across worker counts, debug and release
           composition     : pass | fail | absent     identical per-world digests across batch size, slot, capacity,
                                                      co-tenants and shard count
           cross_bits[cpu] : pass | fail | absent     bit equality of every float kernel output with `batch-cpu` f32
           envelope[pair]  : ledger row id | absent   recorded disagreement envelope against another placement
           decisions[pair] : equivalent | not-equivalent | insufficient-ensemble | absent
receipts   the gate or check receipt hashes for each evidence field
```

**Currency.** A record is current for a run only if its fingerprint digest, every kernel content hash, the step
plan identity and the profile equal the run's. A toolchain or driver change moves code generation, so it
changes the fingerprint and makes every record of that family stale until `spark check` runs again.

**Classification of a kernel set on one placement (numbered; pure function of current records).**
1. If any kernel in the set has no current check row: class `unrecorded` (reads as D4).
2. Kernels of class `exact`, and the decisions of `guarded` kernels: D0 if `exact_bytes` is `pass`; otherwise
   `unrecorded`.
3. Floating kernels: D2 if `repeat` and `composition` are both `pass`. If `repeat` passes and `composition` is
   absent or failed, the set is **not** D2: it is D3 against its own isolated run if an envelope row and a
   `decisions: equivalent` row exist for that comparison (D3 is both, as for a pair below), and D4 otherwise,
   with the reason `batch-dependent`. If `repeat` is absent the set is
   `unrecorded`; if `repeat` failed it is D4 with the reason `not-repeatable`, whatever `composition` says.
   (The referee steps one world per instance; its `composition` evidence is structural and recorded as
   `pass: single-world`.)
4. The set's class is the meet of steps 2 and 3 over its kernels.

**Classification of a pair of placements (what a cross-backend comparison, a teleport or a cross-family pairing
may claim).**
1. Same placement pattern and device family: the single-placement class.
2. Different families, or one family under two placement patterns (a stage placed on a different backend in
   each): D1 if both are D2 and `cross_bits` is `pass` for every floating kernel of the plan on both, and the
   D1 status of every family involved is `attained`.
3. Otherwise D3 if an `envelope` row and a `decisions: equivalent` row exist for the pair, the task and the
   workload.
4. Otherwise D4: the pair is unpaired by declaration.

**Class of a run.** `class(run) = meet(class of its step plan on its actual placement, ceiling of its declared
profile, class of every input that is a computed result)`. Profile ceilings: `reference-replay` and
`device-replay` D2; `cross-backend` D1 if attained, otherwise D3; `fast-training` D4. The ceiling enters
`classify_run(plan_class, ceiling: DetClass, inputs)` as an argument: the profile type and its ceiling table are N35-04's, which calls this
function and depends on this bead, so the classifier names no profile type. Inputs that are data
identified by content hash (a design, a scene, policy weights) do not lower the class: an evaluation of weights
that were trained under class D4 is itself D2 under `device-replay`, because it is deterministic given the
weights. The tag `trained_under: D4` on such a policy is checked by the licences (N35-07), not by the meet.

**Per-family D1 status.** `d1: hypothesis | attained | not-attained`, set only by the recorded outcome of
GATE-SPARK-01 and GATE-SPARK-02 for the family. Until then it is `hypothesis`, which classifies as
not attained. If kill gate KILL-D1 fires for a family (the gates show it cannot hold bit equality with
`batch-cpu` for the floating kernels of the step), the status is `not-attained` with the decision record's
identifier, and three consequences follow mechanically: the family is D2 for itself and D3 against others; a
teleported world from it is labelled a tolerance replay; a comparison whose arms ran on different families is
unpaired. Report wording changes with it (below).

**No upgrade path.** The classifier never rewrites the class stored on an existing result. A later, stronger
record applies to later runs. To hold a stronger class, the world is run again; the new result has a new
identity.

**Wording table (consumed by reports and by `CONTRACT.md` generation).**

| Record state | Words a report may use |
|---|---|
| `repeat: pass` only | "repeats bit for bit as the same batch on this device family" (parity with incumbents) |
| `repeat` and `composition` pass | "a world's trajectory does not depend on the batch it ran in, on this device family" |
| D1 attained | "bit-identical to the CPU reference on this device family" |
| D3 pair | "tolerance replay; decisions agree within the recorded bounds" |
| anything else | "no determinism claim" |

**Surface.** No new verb. `frob spark check` prints the class attained per kernel and for the full step;
`frob spark place` and `frob sim estimate` print the class a planned run will carry before it runs; every
envelope's `evidence.determinism` is the run's class, with `evidence.determinism_reason` (the weakest input)
and the receipt identifiers.

## Acceptance criteria

- [ ] `classify_set` and `classify_pair` are pure functions of the supplied records; the same records give the same class on every platform.
- [ ] A kernel set with one stale check row (fingerprint digest changed by one field) classifies as `unrecorded`, and the envelope prints D4 with reason `stale-check`.
- [ ] `repeat: pass` with `composition: absent` classifies as D3 or D4 with reason `batch-dependent`, never D2.
- [ ] A cross-family pair is D1 only with `cross_bits: pass` on both and status `attained`; with status `hypothesis` it is at most D3.
- [ ] With the KILL-D1 decision recorded for a family, teleport output carries the label `tolerance-replay`, a cross-family comparison is admitted only as unpaired, and no report string contains "bit for bit" for that family.
- [ ] A run under `fast-training` is D4 whatever its records; an evaluation of the resulting weights under `device-replay` is D2.
- [ ] The class stored on an existing result is unchanged after a stronger record is added (a test adds the record and re-reads the result).
- [ ] Negative control: a planted nondeterministic reduction (a floating reduction whose order depends on scheduling) fails `repeat`, and the classifier returns a class below the manifest's claimed D2.
- [ ] Negative control: a result with its determinism field removed is classified D4 by every consumer.

## Test plan

### Unit tests
(Records in these tests are constructed fixtures, labelled `synthetic`; the classifier itself is the real code.)
- `classify_exact_kernels_d0`: `exact_bytes: pass` → D0; absent → `unrecorded`.
- `classify_float_needs_repeat_and_composition`: the four combinations of pass and absent give D2, D3 or D4 with `batch-dependent`, `unrecorded`, `unrecorded`; `repeat: fail` with `composition` pass or absent gives D4 with `not-repeatable`.
- `classify_pair_same_family_two_patterns`: one family under two placement patterns follows rule 2 (D1 only with `cross_bits: pass` and `attained`), not rule 1.
- `classify_referee_single_world`: referee records give D2 with `composition: pass: single-world`.
- `classify_pair_d1_requires_attained`: status `hypothesis`, `attained`, `not-attained` × `cross_bits` pass or fail: D1 only for (`attained`, pass).
- `classify_pair_d3_requires_decisions`: an envelope without a decision record → D4; `insufficient-ensemble` → D4; `equivalent` → D3.
- `run_class_is_meet` (property, 10⁴ cases): random plan class, profile ceiling and input classes; result equals the minimum.
- `policy_tag_does_not_lower_class`: weights tagged `trained_under: D4`, evaluated under `device-replay` with full records → D2.
- `currency_fields`: changing each of fingerprint digest, a kernel hash, the step plan id and the profile makes the record stale.
- `no_upgrade_of_stored_class`: as in the acceptance criteria.
- `wording_table_total`: every record state maps to exactly one row.

### End-to-end script and logging
`scripts/e2e/num_classifier.sh [--tier batch-cpu|gpu-cuda|gpu-metal] --seed <s>`: (1) `frob spark check --all
--backend <tier> --seed <s> --key ncl-check-<tier>-<run-id> --json`: assert a claimed and an attained class per
kernel and for the step; the composition evidence is BD-181's and comes later (BD-181 depends on this bead), so
here every floating kernel prints D3 or D4 with `batch-dependent`, never D2, and exact kernels print D0 where
`exact_bytes` passes; (2) `frob spark place --tier strict:<tier> --workload Q --worlds 1024 --json`: assert the
class the planned run would carry equals the classifier's reading of step 1's records, with the weakest kernel
named; (3) `cargo test -p frob-kernels --release --test classifier_e2e` against the script's state root: step
1's check rows read back; the same rows against a run whose fingerprint digest differs in one field classify
`unrecorded` and print D4 with `stale-check`; a planted floating reduction whose order depends on scheduling
(registered only in the test) checked twice through the real check path fails `repeat` and classifies below
its claimed D2; CX-366's seeded but reordered arm is refused D2. The class on `sim.run` envelopes (the profile ceilings that enter a run's class are N35-04's, which calls
`classify_run` and depends on this bead), with the replay and fork consequences of a stale record, is asserted
by N35-31's script, the later lane. Logs go through the
STD-E2E helper to `target/e2e-logs/num_classifier/<utc-timestamp>.ndjson`:
`cmd` lines with exact command line, exit code and wall time; the evidence block of each envelope; `metric`
lines `class_attained`, `class_printed`, `d1_status`; `assert` lines with expected and observed class; on
failure the record identifiers and the first differing evidence field; a `summary` line.

### Known answers and negative controls
- KA-804 (the class of a combined result is the weakest among what produced it).
- CX-366 (seeding the generator does not make two arms a replayable pair): `seeded_but_reordered_arm_is_not_d2`
  runs one world twice with the same seed and a conformance reduction whose order differs between the runs;
  the draws are identical, the digests differ, and the classifier refuses D2. The arm is built here under the
  plant identifier of CX-366's control in N35-CX, `seeded-reordered-arm` (kind `planted-input`; its fixture,
  the two runs' records with a `synthetic` header, is
  `crates/frob-kernels/tests/fixtures/seeded-reordered-arm/`), so that the control the seeding tool of N38b-05
  derives from CX-366 finds its plant; N35-07 offers the same fixture for attribution and asserts
  `FROB-REF-562`. This bead writes no row of `controls.toml`.
- The two entries of the program's negative-control register for the determinism classifier: a planted
  nondeterministic reduction is classified below its claimed class; a D4 result offered unlabelled is refused
  on every path (the refusals are measured in BD-269).
- Determinism lanes: the classifier runs twice and across worker counts with identical output.

## Considerations

- A family may hold `repeat` and fail `composition` for one kernel only. The class is per kernel set, so a step
  plan that avoids that kernel can still be D2; the envelope names the weakest kernel.
- The classifier reads records; it does not run tests. A slow check must not be triggered implicitly by a
  verb that only needs the class: the verb refuses with `FROB-REF-247` or prints D4 and names
  `frob spark check` as the repair.
- The M2 stop decision reads this component: if no device family holds batch-composition invariance, M2 falls
  back to its no-GPU variant and device results are labelled exploratory.
- Mixed placements (a stage that fell back to the host inside a device run) are their own placement pattern
  and need their own records; a fallback that happens only sometimes makes the pattern, and so the class,
  depend on the run, which is why the placement receipt is part of the key.
