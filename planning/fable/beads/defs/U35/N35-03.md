## Background

A determinism class is claimed by a contract and tested by the Gauntlet's determinism tier, G5, which runs each
subject "twice on one machine; across worker counts; debug and release; across platforms; across backends,
each against its class". The device families have their own lanes (run-to-run digest equality per device
family, owned by the Spark unit). The two CPU tiers need the same treatment, because everything else is
measured against them: `batch-cpu` is the reference every device is compared with, and the `referee` is the
trusted tier in double precision.

What each CPU tier claims:

- `batch-cpu` (our own batched kernels in Rust, in `f32` and `f64`): class D2, and since its floating kernels
  use only +, −, ×, ÷, correctly rounded square root and deterministic elementary functions written from
  those, with no fused multiply-add, the same bits are expected on the aarch64 Mac and on the x86-64 Linux
  host. That expectation is what "class D1" means on the CPU side, so it is measured here and not assumed.
- `referee` (the sibling simulation library's articulated dynamics behind the airlock crate): class D2 on one
  machine. It aims at the sibling's cross-architecture class by using its deterministic elementary functions,
  but FACT: the sibling's dynamics crate currently calls the platform's `sqrt`, `sin` and `cos` and makes no
  cross-architecture claim. Closing that is upstream work item FD-FSIM-07; until it lands, agreement of the
  referee across machines is a tolerance statement (class D3).

Three hazards from the chapter's table are tested by these lanes directly. *Thread scheduling*: completion
order varies, so results are placed by index, never by arrival (INV-NUM-01). *CPU worker count and tile size*:
a reduction tree shaped by tile boundaries changes with the worker count, so tree shape must be a function of
logical index only. *Hash-map iteration*: its order is unspecified and must not affect outputs. Tier: Solid.

## Scope

In: the lane definitions for the two CPU tiers; the fixture set; the comparison (per-world digests and
committed-state hashes); the records the determinism classifier reads (`repeat` evidence, N35-02); negative
controls for each lane; the cross-architecture rows, with the referee row gated on FD-FSIM-07. These are the
CPU rows of GATE-GAUNT-07, the gate of the determinism tier.

Out, with the bead that has it: the tier that owns that gate (N38a-35: every kernel and every verb against
its declared class on generated inputs and demo requests, the `backends` lane, the batch-composition relation
on 10⁴ worlds, decision-level equivalence, the account and the gate's record). It depends on this bead, reads
these receipts and runs no reference workload on a CPU tier itself; its lane `twice` is fed by this bead's
`repeat` and `restart`, its `workers` by `workers` and `tiles`, its `profiles` by `build`, its `platforms` by
`arch`. The same lanes per device family (N21b-39). Batch-composition invariance (BD-181); the tile program
itself (BD-160); the upstream change (FD-FSIM-07).

## Technical approach

**Lanes (each compares arrangement A with arrangement B of the same world addresses; equality is of per-world
digest chains, of BLAKE3 hashes of committed snapshots, and of the bit patterns of every floating statistic in
the run summary, since cross-world sums are where a tile-shaped reduction would show).**

| Lane | A against B | Tiers | Must hold |
|---|---|---|---|
| `repeat` | The same command twice in one process | both | Byte-equal |
| `restart` | Two process launches | both | Byte-equal (catches per-process hash seeds) |
| `workers` | Worker counts 1, 2, 8 and all cores (36 on the Mac) | `batch-cpu` | Byte-equal |
| `tiles` | Tile sizes 1, 8, 64 and 1,024 worlds per tile (`--tile-worlds` admits powers of two from 1 to 1,024, BD-160; another value is `FROB-REF-802`) | `batch-cpu` | Byte-equal |
| `build` | Debug build against release build | both | Byte-equal |
| `chunk` | Chunk lengths 1, 6 and 100 control intervals | both | Byte-equal at common boundaries |
| `resume` | Run whole against split at a snapshot and resumed | both | Byte-equal |
| `arch` | aarch64 (the Mac) against x86-64 (host `trj`) | `batch-cpu` `f32` and `f64`; `referee` | `batch-cpu`: byte-equal. `referee`: recorded `not-run` with the reason `upstream FD-FSIM-07` until the pin moves; then byte-equal under the deterministic mode |

**Fixture set (frozen with a content hash before the first run).** The built-in two-second single-robot
rollout of the referee smoke test; workload Q (reference quadruped, 18 degrees of freedom) walking on flat
ground under the baseline controller, 64 world addresses, 1,000 control intervals; a contact-rich drop fixture
(to exercise sort and compaction); one mixed batch of two body plans. The `f64` and `f32` variants of
`batch-cpu` both run.

**Procedure per lane.**
1. Run A and B through the real `frob sim run` with identical seeds, addresses, design, scene, task and
   policy identities, each arrangement under its own idempotency key (a reused key would return the first
   arrangement's stored receipt and compare a run with itself). The arrangement is set by `--workers N` and
   `--tile-worlds N` (BD-160's operator inputs of `sim.run`, `batch-cpu` only) and by `--chunk-intervals N`, the
   conformance-build override of the chunk-length rule (N21b-22's, which N21b-39 and N21c-39 also use); they
   change no result by contract, are present in the conformance build the lanes and the script use, and are
   recorded in the receipt of each arrangement.
2. Compare the digest chains per world address (never per slot); on equality compare snapshot hashes.
3. On a difference, call the first-divergence search over the digest chain to name chunk, step, stage, kernel
   and quantity, and store the record.
4. Write one receipt per (tier, lane) with the fingerprint digests of both arrangements and the outcome, and
   append the `repeat` evidence row the classifier reads. The `arch` lane transports only digests and hashes
   between machines (a few kilobytes), never state.

**Negative controls (conformance builds only; each must fail its own lane and no other).**

| Control | Plant | Lane that must catch it |
|---|---|---|
| `arrival-placement` | Results written to output rows in completion order of worker tasks | `workers` |
| `tile-shaped-tree` | A floating sum over worlds (the run summary's mean return) reduced sequentially inside each tile and pairwise across tiles, instead of by a tree over world index | `tiles`, `workers` (the lanes compare the summary's floating statistics bit for bit as well as per-world digests) |
| `hashmap-order` | Contact pairs emitted in the iteration order of a hash map seeded per process | `restart` |
| `debug-fold` | A three-term `f32` sum grouped as ((1 + 2⁻²⁴) + 2⁻²⁴) in debug builds and (1 + (2⁻²⁴ + 2⁻²⁴)) in release builds: bit patterns 0x3F800000 and 0x3F800001 | `build` |
| `platform-sin` | One kernel calls the platform sine in place of the deterministic one | `arch` (and possibly none on one machine, which is the point) |
| `fused-on-arm` | One product–sum compiled with a fused multiply-add on aarch64 only | `arch` |
| `snapshot-without-warm-start` | The solver's warm-start buffer left out of the snapshot | `resume` |

**Specificity.** Each control is run through its own lane (must fail) and through `repeat` (must pass, except
where the plant is keyed on the process). A control that fails a lane it is not keyed on is itself defective.

**Loading the controls (DESIGN).** A control is planted with `--mutant <name>` on `frob sim run` in the
conformance build. The loader is N21b-42's, the one loader of that input, with one namespace for every mutant (a
name registered twice fails the registry's load). `debug-fold` and `snapshot-without-warm-start` are N21b-42's
mutants, which have `batch-cpu` twins and the same plant and lane as above; this bead reuses them by name and
builds no second copy. The other five (`arrival-placement`, `tile-shaped-tree`, `hashmap-order`,
`platform-sin`, `fused-on-arm`) are this bead's plants, each a host seam under
`crates/frob-conformance/src/mutants/` or a variant kernel under `crates/frob-conformance/kernels/mut/`, keyed on
the arrangement variable it observes, so they take no `:<key>` suffix. Each has a row in the one registry
`crates/frob-conformance/registry/controls.toml`, a `Control` record of BD-025 with no private field, as
N21b-42 registers its own: `kind = "mutation"`, `feature` its plant's flag, `gate = ["GATE-GAUNT-07"]` (the
determinism tier's gate, whose CPU rows these lanes supply), `seed = "GATE-GAUNT-07"` (the form for a control
whose planted failure no catalogue entry or known-answer row states), `target` the lane's owner test, `defect`
the plant of the table above, `expect` the lane that must fail. The row is what makes the name loadable; the
lanes, tiers and specificity stay in this bead's test table. Reason: one loader and one name per plant, so a
lane on the CPU and a lane on a device that look for the same defect run the same code.

## Acceptance criteria

- [ ] All seven single-machine lanes are byte-equal for `batch-cpu` (`f32` and `f64`) and the applicable ones for the referee, on the Mac and on `trj`, over the frozen fixture set.
- [ ] The `arch` lane is byte-equal for `batch-cpu` in `f32` and `f64` between the two machines; a failure is recorded with its first divergence and blocks any class D1 attestation that names `batch-cpu` as the reference.
- [ ] The referee's `arch` row reads `not-run` with the reason `upstream FD-FSIM-07` and the pinned sibling commit until the switch-over, and is never recorded as passed before it.
- [ ] Each of the seven controls fails its own lane, with the first-divergence record naming the planted kernel or host function.
- [ ] The five controls this bead plants have one row each in `controls.toml` and load through N21b-42's loader by `--mutant <name>`; `debug-fold` and `snapshot-without-warm-start` are N21b-42's rows, reused and not registered twice (the registry's load fails on a duplicate name).
- [ ] Each lane writes a hash-named receipt and a `repeat` evidence row keyed by tier, fingerprint digest and step plan.
- [ ] Results are compared by world address; a test that permutes slots between A and B still reports equality.

## Test plan

### Unit tests
- `lane_matrix_is_frozen`: the fixture set's content hash equals the registered value; a changed scenario changes it.
- `compare_by_address_not_slot`: two runs with permuted slots and equal per-address digests compare equal.
- `debug_fold_fixture_bits`: the two groupings give 0x3F800000 and 0x3F800001.
- `tile_tree_shape_is_index_function`: the reduction plan for 1,000 elements (which 64 and 1,024 do not divide, so the last tile is partial) is identical for tile sizes 1, 8, 64 and 1,024.
- `each_control_fails_only_its_lane` (seven cases, short configuration of 50 control intervals).
- `cpu_lane_controls_load_by_name`: the five rows this bead adds pass BD-025's `controls::validate` (`kind = "mutation"`, a `feature`, gate GATE-GAUNT-07, seed form `GATE-<AREA>-nn`) and each name loads through N21b-42's loader with no key; `--mutant arrival-placement:1` is `FROB-REF-802`; a scratch copy of the registry with a second `debug-fold` row fails to load.
- `referee_arch_row_gated`: with the upstream registry row at `open`, the lane returns `not-run` and exit 2; at `adopted`, it runs.

### End-to-end script and logging
`scripts/e2e/num_cpu_lanes.sh [--tier batch-cpu|referee] [--lane <name>|all] [--peer <host>] [--seed <s>]`.
Steps: `fixtures` (verify the frozen hash); one step per lane (two `frob sim run <fixture> --tier <t> --seed <s>
… --key cl-<lane>-<arm>-<run-id> --json` invocations with the arrangement's options and distinct keys, each
envelope showing `idempotent_replay: false`, then `frob telemetry divergence <run A> <run B> --mode exact
--json` on inequality); `controls` (each control through its lane in the conformance build, the lane's two
arrangements run with `--mutant <name>` and their own keys `cl-<lane>-<name>-<arm>-<run-id>`, expecting failure);
`arch` (runs the local half, fetches the peer's digests when `--peer` is given, otherwise logs a `skip` event
`no peer` and records the row `not-run`). Logs through the STD-E2E helper to
`target/e2e-logs/num_cpu_lanes/<utc-timestamp>.ndjson`: `cmd` lines with exact command line, exit code and
wall time; the evidence block (claim known-answer, class, tier, determinism, identities with fingerprint
digest, seed); `metric` lines per lane (`worlds_compared`, `digests_equal`, threshold: all equal); on failure
the first differing world address, chunk, step, stage and kernel with both digests and the snapshot paths; a
`summary` line naming the lanes run, skipped and failed.

### Known answers and negative controls
- The one-ulp grouping fixture (0x3F800000 against 0x3F800001).
- The seven controls above; CX-146's case for the tile lane: in `f32`, with a = 10⁸, b = −10⁸, c = 1,
  (a + b) + c = 1 and a + (b + c) = 0.
- Metamorphic: permuting world indices permutes results and changes nothing else; splitting a rollout at a
  snapshot and resuming equals running it whole.
- Determinism lanes: this bead is the lanes.

## Considerations

- The `arch` lane needs both machines. Where the peer is unavailable the row is `not-run`, and class D1 is
  not attested against a `batch-cpu` reference that has not passed it.
- Debug builds are slow; the `build` lane uses the short configuration (50 control intervals, 8 worlds).
- If `batch-cpu` differs across architectures after one repair cycle, the reference for device comparison is
  pinned to one architecture and every D1 record names it; that weakening is recorded as an ADR.
- Compute: all lanes fit the default envelope (16 GiB, 8 cores, one hour) except `workers` at 36 cores, which
  needs the gate-measurement class; without approval that row is `not-run`.
