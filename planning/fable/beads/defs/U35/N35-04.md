## Background

A determinism class (D0 exact, D1 bitwise across backends, D2 bitwise per backend and independent of the batch,
D3 tolerance with agreeing decisions, D4 nothing) is a property a result ends up with. A **profile** is what a
run asks for: a named set of pins. A run declares one profile; its result carries it. The profile is how a user
or an agent says "this run is the record", "this run is for paired comparison on this card", "this run will be
compared with another machine" or "this run only has to produce weights", and how the system knows which
arithmetic, ordering and identity facts it must hold fixed and write down.

| Profile | Class | What is pinned | What it is for |
|---|---|---|---|
| `reference-replay` | D2 on `batch-cpu` and on the referee; D1 against a device where attained | Solver, arithmetic, toolchain, order and addresses. Declared state and logical events are byte-identical on repeat and across checkpoint and restart | The record; teleport targets; attribution; the numeric side of certificates |
| `device-replay` | D2 on one device family | Stable reductions, sorted contacts, select-only masks, the fingerprint. Identical on repeat and under any permutation or regrouping of worlds | Training, evaluation and paired comparison on that family |
| `cross-backend` | D1 if attained, otherwise D3 with the decision-level test | Physically scaled state error, impulse and work residuals, event times and task decisions; the first divergence is kept | Promotion; teleport, labelled exact or tolerance; results that cross machines |
| `fast-training` | D4, labelled | Only the knobs the profile lists, all recorded | Producing weights, and nothing else |

A second, independent choice is the **precision profile** of the single-precision contact solve: `default` (no
refinement) or `stiff` (for near-rigid contact and the optional hard-contact law: one step of iterative
refinement whose residual is accumulated in a double-float pair). The verb registry gives `sim.run` two options
for these, `--determinism` and `--precision`, beside its existing step-profile option.

Design reasons. Profiles are named, not assembled from flags, so that a result's provenance is one word plus a
digest of the pins and two results can be compared for "same profile" exactly. The physics step stays class D2
in every profile (decision ADR-NUM-05: a nondeterministic training profile exists only as labelled class D4,
relaxing the learner and shard order and never the physics), so no profile is a way to make physics faster by
making it irreproducible. Tier: Solid. The `fast-training` row is defined here as a name and a ceiling; its
knobs, tag and rules are N35-06.

## Scope

In: the profile and precision types; the pin set of each profile and its digest; option parsing on `sim.run`
and on the verbs that run worlds (`sim.replay`, `eval.run`, `train.start`, `run.fork`); defaults per tier;
admission against the class the verb requires, with `FROB-REF-247`; the degraded-world policy option; the
profile record on results and snapshots. Out: the classifier (N35-02); licences (N35-07); the `fast-training`
knobs (N35-06); the refinement kernel and the conditioning figure (BD-156 and the Spark unit's conditioning
bead); the end-to-end script (N35-31).

## Technical approach

**Types (DESIGN; `frob_core::det::profile`).**

```rust
pub enum DetProfile { ReferenceReplay, DeviceReplay, CrossBackend, FastTraining }
pub enum PrecisionProfile { Default, Stiff }
pub enum DegradedPolicy { Refuse, ContinueFlagged }
pub struct Pins {
    solver:     SolverPins,      // contact law, iteration count, tolerances (in scaled variables), warm start on
    arithmetic: ArithPins,       // width (f32 | f64), math mode (IEEE safe), precision profile, refinement steps
    toolchain:  ToolchainPins,   // compiler identities, kernel content hashes, step plan identity
    order:      OrderPins,       // reduction = pairwise-anchored; sort = stable-total; masks = select
    addresses:  AddressPins,     // run seed, address scheme version, stream registry version
    fingerprint: Option<Digest>, // hardware fingerprint digest, for device profiles
}
pub struct ProfileRecord { profile: DetProfile, precision: PrecisionProfile, degraded: DegradedPolicy,
                           ceiling: DetClass, pins_digest: Digest }   // carried by every result and snapshot
```

`pins_digest` is BLAKE3 over the canonical serialization of `Pins`. Two results have "the same profile" exactly
when their `ProfileRecord`s are equal.

**Which pins each profile requires.** `reference-replay`: all five groups; no fingerprint needed on CPU tiers.
`device-replay`: `order`, `toolchain` and `fingerprint` must be present and current; `solver`, `arithmetic` and
`addresses` are recorded. `cross-backend`: two `Pins` (one per placement) plus the comparison record
(state error in physically scaled units, impulse and work residuals, event times, task decisions, first
divergence); the profile is only meaningful for a pair. `fast-training`: the physics pins of `device-replay`
plus the relaxed learner knobs, each recorded with its value.

**Options.** `--determinism {reference-replay|device-replay|cross-backend|fast-training}`,
`--precision {default|stiff}`, `--on-degraded {refuse|continue-flagged}`.

**Defaults.** Tier `referee` and `batch-cpu`: `reference-replay`. Tiers `gpu-cuda` and `gpu-metal`:
`device-replay`. A verb that compares placements (`sim.replay --tier`, promotion) sets `cross-backend` itself.
`fast-training` is never a default: it is off by default and enabled per job, never per installation, so no
configuration file or environment variable can select it; only the option on the training verb can.
`--precision default`; `--on-degraded refuse`.

**Admission (numbered; runs before any world is stepped).**
1. Parse the options against the verb's generated schema. An unknown name is a schema refusal; a misspelt
   option is a refusal, never a silent default.
2. Check applicability: `fast-training` only on training verbs; `cross-backend` only where two placements are
   named; `reference-replay` on a device tier only where the family's class D1 is attained. A violation is
   `FROB-REF-247` with the applicable profiles listed.
3. Resolve the actual placement with the placement planner and ask the classifier (N35-02) for the class
   attainable for (step plan, placement pattern, profile).
4. Compare with the minimum class the verb declares for this use (N35-07). Below it: `FROB-REF-247`
   ("the determinism class a verb requires is not attainable on the requested placement"), exit 3, with
   `observed` the attainable class and its records, `required` the class and the use, and repairs: a placement
   where it is attained (`batch-cpu` first); `frob spark check --sweeps all` if the record is stale; the weaker
   use the licence table offers.
5. Build `Pins`, compute `pins_digest`, write the `ProfileRecord` into the job, the step plan identity and
   every snapshot.

**Precision profiles.** `default`: no refinement. `stiff`: one refinement step; one step multiplies the
relative error of the solve by about κ·u (κ the condition number of the scaled system, u = 2⁻²⁴), taking an
error of order 0.03 on near-rigid contact states to order 10⁻³. The number of refinement steps is a constant of
the shape class, so the launch graph stays static and the precision profile is part of the step plan identity:
`default` and `stiff` runs of one world are different computations, and comparing them is a class D3 pair, not
a replay.

**Degraded worlds.** A world whose conditioning lower bound satisfies κ̂·u > limit (default 0.1; OPEN-NUM-4,
frozen by N35-29) is marked `Degraded: ill-conditioned`. Under `refuse` the run refuses with `FROB-REF-248`
and publishes nothing partial as a result; under `continue-flagged` it continues, the world's results carry the
flag, and every summary states the count excluded or flagged.

**Snapshots.** A snapshot is bound to its `ProfileRecord`. Restoring it under another profile is a comparison
replay, not a continuation: the restore succeeds only through the verbs that label their output accordingly
(`sim.replay --tier`), and a plain continuation with a different `pins_digest` is refused with `FROB-REF-247`.

**What `reference-replay` promises, as a test.** Declared state and logical events are byte-identical (a) on
repeat, (b) across a checkpoint and restart at any committed boundary. "Declared state" is the snapshot
content: group elements, velocities, anchored cell indices, contact memory, warm starts, clock phase
accumulators, packet queues, controller and estimator state, the step counter that indexes random streams.

## Acceptance criteria

- [ ] `frob sim run --determinism <p> --precision <q>` accepts exactly the four and the two names; any other value exits 3 with a schema refusal that lists the enumeration.
- [ ] With no options, a referee or `batch-cpu` run records `reference-replay`, a device run `device-replay`, and both `default` and `refuse`.
- [ ] `fast-training` cannot be selected by configuration or environment: a planted setting in the configuration file is ignored with a warning finding (exit 2), and only the option on a training verb selects it.
- [ ] `--determinism reference-replay --tier gpu-metal` on a family whose D1 status is not `attained` exits 3 with `FROB-REF-247`, zero worlds stepped, and repairs naming `batch-cpu`.
- [ ] Every result envelope and every snapshot carries the `ProfileRecord`; two runs with identical options have equal `pins_digest`; changing any one pin changes it.
- [ ] Under `reference-replay` on `batch-cpu`: a run repeated, and a run split at a snapshot and restarted, are byte-identical in state digests and in the logical event log.
- [ ] `--precision stiff` changes the step plan identity and records one refinement step; a continuation of a `default` snapshot under `stiff` is refused with `FROB-REF-247`.
- [ ] A planted ill-conditioned world (κ̂·u > 0.1) gives `FROB-REF-248` under `refuse` with nothing partial published, and a flagged result under `continue-flagged`.
- [ ] The options are reachable through `frob --json` and through the generated MCP tool, with the same enumerations.

## Test plan

### Unit tests
- `profile_names_roundtrip`: the four profile names and two precision names parse and print; `"device_replay"` and `"fast"` fail.
- `profile_defaults_by_tier`: referee, `batch-cpu`, `gpu-cuda`, `gpu-metal` → the defaults above.
- `fast_training_only_by_option`: configuration and environment plants do not select it.
- `pins_digest_sensitivity` (property): flipping any single field of `Pins` changes the digest; reordering map entries does not.
- `admission_refuses_below_required` (table test): for each (verb use, attainable class) pair of the licence table, admission passes or returns 247 as the table says.
- `precision_in_step_plan_identity`: `default` and `stiff` give different `StepPlanId`s for one shape class.
- `snapshot_profile_binding`: restore with a different `pins_digest` is refused; restore through the teleport path is labelled `comparison-replay`.
- `degraded_policy_paths`: a synthetic factor diagonal (labelled `synthetic`) with max/min ratio 2,000 gives κ̂ = 4·10⁶, κ̂·u = 0.238 > 0.1: `refuse` → 248; `continue-flagged` → flag.

### End-to-end script and logging
`scripts/e2e/num_profiles.sh` is bead N35-31. It drives the options above through the real `frob` binary on
each tier present and logs through the STD-E2E helper (every `cmd` with exact command line, exit code and wall
time; the evidence block; `refusal` events with code, `observed`, `required` and first repair; digests where
state is compared; a `summary` line).

### Known answers and negative controls
- The licence refusal known answer KA-802 depends on admission here for its `FROB-REF-247` paths.
- Negative controls: a build in which admission step 4 is skipped must be caught by
  `admission_refuses_below_required`; a `Pins` serialization that omits the toolchain group must be caught by
  `pins_digest_sensitivity`.
- Determinism lanes: `reference-replay` twice on one machine, across worker counts, and debug against release
  (N35-03's lanes run under this profile); `device-replay` twice and under slot permutation (BD-181).

## Considerations

- The step-profile option (`lockstep`, `strict`, `referee`) and the determinism profile are different axes:
  the first chooses the step algorithm, the second what is held fixed and recorded. The registry row keeps
  three options; merging them was rejected because a `strict` step can run under `reference-replay` or
  `cross-backend`.
- Ceiling for `fast-training`, stated before any test: inference and learning together are about 13% of
  training wall-clock on one incumbent stack, so relaxing them gains at most 1/(1 − 0.13) ≈ 1.15 on one device;
  its real use is the asynchronous two-device variant, whose pilot is N35-05.
- OPEN-NUM-4 (the limit for `Degraded: ill-conditioned` and the refinement count of `stiff`; default κ̂·u above
  0.1 and one step; owner: Spark lead; decided by GATE-SPARK-18) is read from the frozen record of N35-29.
- A profile is part of memo keys: a memoized episode is reused only under an equal `ProfileRecord` on the same
  backend and fingerprint.
