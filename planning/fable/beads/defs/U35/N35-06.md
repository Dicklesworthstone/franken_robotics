## Background

Determinism class D4 means "no guarantee": a result of class D4 is never evidence. The class has exactly one
sanctioned use, the `fast-training` profile, which exists so that a learner may trade reproducibility for speed
without that trade leaking into anything that is later cited. Decision ADR-NUM-05: a nondeterministic training
profile exists only as labelled class D4, relaxing the learner and shard order and never the physics; the
reason given is that the asynchronous two-device variant must not pass as deterministic. The learning chapter's
matching decision is that speed in the learner must not weaken the evidence.

**Scope of the profile (DESIGN).** The physics step stays class D2 in every profile. `fast-training` relaxes
only:

- the order in which shards deliver collected segments and gradient sums (asynchronous collection, with a
  declared bound on version lag);
- the learner's reduction order and matrix-product implementation (the matrix-multiply kernel `K-gemm` may use
  a device matrix path, which is admitted nowhere else: reduced precision or a vendor matrix path leaves class
  D2);
- minibatch composition by arrival.

Its only output is a set of weights tagged `trained_under: D4`. Three rules bind it:

1. No number observed during such a run (a learning curve, a training return) is evidence (`FROB-REF-861`).
2. Every claim about the resulting policy comes from re-evaluation under `device-replay` or stricter, which is
   deterministic given the weights.
3. The profile is off by default and is enabled per job, never per installation.

The bans on fast-math, fused multiply-add, built-in transcendentals and floating-point atomics in batched
kernels hold under this profile too: it relaxes ordering and placement only.

Why a label and not a prohibition. Forbidding nondeterministic training outright would forgo the one place
where it is harmless: weights are data, and an evaluation of given weights under a D2 profile is as
reproducible as any other. Why not a silent option: under class D4 nothing about a run can be replayed, so its
numbers could not be reproduced, promoted or attributed; the refusal is by code, not by convention.

Tier: the label, the tag, the rules and the refusals are Solid. The asynchronous knob is Frontier under
KILL-SHARD and exists only if the pilot (N35-05) funds it.

## Scope

In (the profile product-wide; this is the one bead that specifies what a `fast-training` job writes): the knob
registry, its closure and its admission from the pilot record; the job-level enablement and the rule that
nothing but a job argument enables it; the D4 label and the profile name on every result, checkpoint, receipt
and policy of such a run, with the empty `claims` list and the `non_claims` entry on training-time envelopes;
the tag on exported weights and its propagation through the artifact graph; the re-evaluation record and the
policy's standing, computed from the graph; the citation check that every citing verb outside `frob-learn`
calls, with its raising of `FROB-REF-861` (its wiring into the M3 verbs is BD-269's, which depends on this
bead); this bead's own end-to-end lane; what the profile may never touch (the physics, the bans); binding row 10 of the
`numerics` battery (N35-30, which reports it `pending: M3` until this bead lands) to this bead's tests
`reeval_twice_identical_digests` and `citation_check_three_cases`.

Out, with the bead that has it:

- The trainer's half (N23a-18, M2, a dependency of this bead): which learner reductions switch under the
  profile, the tagging of `train.status` lines and of the manifest the trainer exports, the function
  `frob-learn::citation_check` and its use at `frob-learn`'s own verbs, where an un-re-evaluated D4-trained
  policy is reported with the learning chapter's code `FROB-REF-867`. This bead generalizes that check to
  every other citing verb and owns the registry, the enablement option and the graph.
- The evidence boundary (N37-28, which depends on this bead): "absent means D4", the five consumer checks,
  `FROB-REF-825`. That bead reads the labels written here and specifies none of them.
- The asynchronous update and the device matrix kernels themselves; the licence table (N35-07); the planted
  cases at the verbs and both gate rows (the capstone BD-269 with its script N35-32).

## Technical approach

**Knob registry (DESIGN; a table in `frob-core`, generated into the `train.start` schema).**

| Knob | Values | Default under the profile | Admitted when |
|---|---|---|---|
| `learner_reduction` | `fixed-tree` (class D2 order), `arrival` | `arrival` if funded, else `fixed-tree` | Pilot verdict `funded` for the learner relaxation |
| `matrix_path` | `dialect` (plain `f32` products in the kernel dialect), `device` | `device` if admitted, else `dialect` | Same verdict; and the device family's matrix path is listed in the fingerprint |
| `minibatch_order` | `address-keyed` (permutations from address-keyed streams), `arrival` | `arrival` if funded, else `address-keyed` | Same verdict |
| `collection` | `synchronous`, `asynchronous` | `synchronous` | Pilot verdict `funded` for asynchronous collection, and KILL-SHARD not fired |
| `max_version_lag` | A non-negative integer number of updates | none: required when `collection = asynchronous` | With `collection` |

A default never selects an unadmitted value, so `--determinism fast-training` with no `--knob` is never
refused for a knob the caller did not name; only an explicit `--knob` with an unadmitted value is (below).
When no knob at all is admitted, the profile is accepted only for a job that declares another registered D4
reason (analytic-gradient training), and otherwise returns `FROB-REF-724` citing the pilot record (N35-05's
fallback). No other field of a job changes under the profile. In particular the step plan, the kernel set, the contact
law, the precision profile, the reductions inside physics kernels and the addressed random streams are those of
`device-replay`. A request that sets a knob not in the table, or a knob whose admission condition fails, is
refused before the job starts (a schema refusal for an unknown knob, which is `FROB-REF-802`, "arguments fail
the schema, including an unknown parameter", exit 3; for an unfunded one the capability refusal
`FROB-REF-724`, exit 5, DESIGN, the code of N35-05's fallback, with `pointer` `knobs.<name>` and the pilot
record in `observed`). A `--knob` given under any profile other than `fast-training` makes the job's kernel set
classify D4 when its value is a D4-making one (`matrix_path = device`, `learner_reduction = arrival`,
`minibatch_order = arrival`, `collection = asynchronous`) and is refused with `FROB-REF-247` by the licence
check (N35-07's training rule). The five rows are the whole set: shard delivery (`collection` with
`max_version_lag`), the learner's reduction order, the matrix-product path and minibatch composition by
arrival.

**Enablement.** Only `frob train start --determinism fast-training [--knob k=v …]`. Every knob's value is
written into the job record and the training receipt. Configuration files and environment variables cannot
select the profile (N35-04): the profile is enabled by an argument of one job, and no key of the owner-held
configuration and no session scope makes it a default. The option is `--determinism` on every verb that
takes a determinism profile (`train.start`, `eval.run`, `sim.run`); `--profile` names a step profile
(`lockstep`, `strict`, `referee`) and never a determinism profile.

**Labelling (every artifact of the run).**
1. The job, every `train.status` line, every checkpoint and the training receipt carry `determinism: "D4"`,
   `profile: "fast-training"` and the knob values. Every training-time result (a learning curve, a return, an
   in-training evaluation, a `train.status` envelope) has a claim product whose determinism is D4 and an
   empty `claims` list, and its envelope says the profile in `evidence` and repeats, in `non_claims`,
   `training-numbers: not-evidence`.
2. The exported policy file's manifest carries `trained_under: "D4"`, the profile name, the job identity and
   the knob values. The weights' identity (`PolicyId`, a content hash) is unaffected: weights are data.
   DESIGN (one statement, the same in N23a-18 and N37-28): the tag is spelled `trained_under`, the name the
   profile's definition gives it, and it is the field the citation check and the standing read. The policy
   manifest `frob.policy/1` also has, for every policy, a `trained_on` block with a `determinism` member (the
   class of the training profile); for such a policy it reads `"D4"`. Tag and member are written by the
   exporter from the one job record, and a manifest in which they disagree is refused on import. Reason: the
   schema's member exists for every policy and cannot be dropped, and a second spelling of the tag inside
   that block would let two readers look in two places.
3. In the artifact graph, every node derived from the run inherits the D4 class through the claim product
   (weakest input wins), **except** an evaluation of the exported weights, whose inputs are the weights as data
   and a run under its own profile. That evaluation is class D2 under `device-replay` and is linked to the
   policy as its `re_evaluation`.

**Standing of a D4-trained policy.** `standing = uncited` until at least one re-evaluation record exists for
the same `PolicyId` under `device-replay` or stricter (`reference-replay`, or `cross-backend` with D1); then
`standing = re-evaluated`, listing the record identifiers. Standing is computed from the artifact graph, never
stored as a flag that could be set by hand.

**The citation check (`FROB-REF-861`).** Any verb that attaches a number to a gate record, a scorecard, a
comparison, a promotion, a report or a claim runs the check on each cited input:
1. If the input is a value whose producing job has `profile: fast-training` (a learning curve point, a
   training return, a training-time success rate): refuse with `FROB-REF-861`; `observed` names the value and
   its job; the first repair is `frob eval run --policy <id> --determinism device-replay`.
2. If the input is a claim about a policy with `trained_under: D4` and `standing = uncited`: refuse with
   `FROB-REF-861` (at `frob-learn`'s own verbs the same condition is reported with the learning chapter's code
   `FROB-REF-867`; one condition, one code per raising site).
3. If the input is a re-evaluation record: admit it; it is the thing cited.
The refusal has exit code 3, family "evidence and protocol", `retry: after-change`.

One check, two raising sites (DESIGN; the same statement is in N23a-18). The function is
`frob-learn::citation_check(policy_id, cited_metric)`, written at M2 by N23a-18 and applied there to
`frob-learn`'s own verbs (the `train.export` summary and the training-gate record builder). This bead wraps
the same function for every other citing verb (`frob_verbs::evidence::cite_check(input)`, which raises 861),
and BD-269 calls the wrapper at each citing verb of M3. The code depends on the case and the site: a number observed
during the run (case 1) is `FROB-REF-861` at every site, as the profile's known answers have it for a cited
training return; an un-re-evaluated D4-trained policy (case 2) is `FROB-REF-867` where a `frob-learn` verb is
the consumer and `FROB-REF-861` at every other citation point. Reason: two chapters each defined a code for
case 2, and one condition must give one code per raising site.

**Determinism of the re-evaluation.** Because evaluation is deterministic given the weights, a D4-trained
policy evaluated twice under `device-replay` on the same world addresses returns identical digests. This is
the profile's known answer.

**Ceiling, stated before any test.** Inference and learning together are about 13% of training wall-clock on
one incumbent stack, so relaxing them gains at most 1.15 on one device; the profile's real use is the
asynchronous two-device variant. The pilot record carries our own measured numbers.

## Acceptance criteria

- [ ] `frob train start` without `--determinism fast-training` never produces a D4 result; with it, every status line, checkpoint, receipt and the exported manifest carry the D4 label and the knob values.
- [ ] The physics of a `fast-training` job is byte-identical to the same job under `device-replay` when the learner is frozen (a conformance mode that applies zero updates): equal per-world digests over 1,000 control intervals. With the learner running, the per-world state digests of a collection under `fast-training` equal those of a replay of the same world addresses with the same weights under `device-replay`.
- [ ] A knob not in the registry is a schema refusal (`FROB-REF-802`); `collection = asynchronous` without `max_version_lag` is refused before the job starts, and without a `funded` pilot verdict it is refused with `FROB-REF-724`, exit 5, the knob in `pointer` and the pilot record in `observed`.
- [ ] Row 10 of the `numerics` battery is bound to this bead's tests and the battery's status no longer reports it `pending`.
- [ ] No configuration key, environment variable or session scope enables the profile: the owner-held configuration schema has no such key.
- [ ] Every training-time envelope of such a job has an empty `claims` list and `training-numbers: not-evidence` in `non_claims`; the exported manifest's `trained_under` tag and `trained_on.determinism` member both read D4, and a manifest in which they disagree is refused on import.
- [ ] `cite_check` given a training return of a `fast-training` job as the cited input of a gate record, a scorecard and a report returns `FROB-REF-861` in each context with exit 3 and the re-evaluation command as first repair (the same citations through the verbs are BD-269's case 6).
- [ ] A policy with `trained_under: D4` and no re-evaluation has `standing = uncited` and is refused as the subject of a claim; after `frob eval run --determinism device-replay` it is `re-evaluated` and the evaluation is admitted.
- [ ] Evaluating that policy twice under `device-replay` on the same addresses gives identical digests (KA-801).
- [ ] No kernel loaded by a `fast-training` job violates the bans: the lint and the compile-flag audit (N35-18) pass on its kernel set, and the device matrix path is loaded only for `K-gemm`. The lint runs on every kernel regardless of profile and fails on a planted fused multiply-add in a kernel of such a job.
- [ ] The standing of a policy cannot be changed except by adding a re-evaluation record: a planted manifest edit that removes `trained_under` changes the `PolicyId`-bound manifest hash and is refused on import.

## Test plan

### Unit tests
- `knob_registry_closed`: the five knobs parse; a sixth, or any other key in a profile request, is a schema error (`FROB-REF-802`).
- `knob_admission_reads_pilot`: with synthetic pilot records (labelled `synthetic`) `funded` / `not funded`, admission of `collection = asynchronous` passes / is refused with the record named.
- `knob_defaults_follow_admission`: with the learner relaxation `not funded` and asynchronous collection `funded`, `--determinism fast-training` with no `--knob` starts with `fixed-tree`, `dialect` and `address-keyed` and is not refused; with nothing funded and no declared D4 reason it is `FROB-REF-724`.
- `d4_label_propagates`: a graph of job → checkpoint → policy → training-curve export: every node is D4.
- `re_evaluation_is_d2`: job (D4) → policy (data) → evaluation under `device-replay`: the evaluation's claim product has determinism D2 and the policy's standing becomes `re-evaluated`.
- `citation_check_three_cases`: a training return → 861; an uncited D4-trained policy → 861; its re-evaluation → admitted.
- `standing_is_computed`: no API sets standing; a compile-fail test pins the absence of a setter.
- `physics_unchanged_under_profile`: the step plan identity of a `fast-training` job equals that of the same job under `device-replay`.
- `physics_digests_equal_under_profile`: per-world state digests of a collection under `fast-training` equal a replay of the same addresses with the same weights under `device-replay`.
- `labels_on_every_artifact`: job row, receipt, status envelope, checkpoint manifest and exported manifest each carry D4 and the profile name; training-time envelopes have empty `claims` and the `non_claims` entry.
- `ban_lint_independent_of_profile`: the lint's verdict on a kernel is the same under every profile, and a planted fused multiply-add fails it under `fast-training`.
- `no_default_enable_key`: the owner-held configuration schema has no key, and the session scope no flag, that selects the profile.
- `manifest_tag_and_member_agree`: an exported manifest with `trained_under: "D4"` and `trained_on.determinism: "D2"` is refused on import.
- `reeval_twice_identical_digests` (KA-801): the exported policy of a short `fast-training` job on `batch-cpu`, evaluated twice under `device-replay` on the same 256 world addresses, gives identical per-world digests and an evaluation of class D2. The boundary bead N37-28 reads this result and does not repeat the test.

### End-to-end script and logging
This bead's own lane is `scripts/e2e/num_fast_training.sh [--seed N]` (default seed 3506; idempotent; every
run verb under its own key, so that no call is answered from another's stored receipt), on `batch-cpu`. Steps:
`preflight` (`frob --json doctor`; the pilot record's knob verdicts, logged; with no knob funded the script
uses the conformance D4 job and says so); `train_d4` (`frob --json train start quad-ref --task quad-flat-velocity
--tier batch-cpu --determinism fast-training --key ft-train-$SEED-<run-id>` for 20 iterations, then `frob
--json train status` and `frob --json train export <job> --out <scratch>`: every status line, the receipt and
the manifest carry D4, the profile and the knob values; `trained_under` and `trained_on.determinism` both read
D4; training-time envelopes have empty `claims` and `training-numbers: not-evidence`); `knobs` (`--knob
nonsense=1` → 802; `--knob collection=asynchronous` without a funded verdict → 724 with `pointer`
`knobs.collection`; `--determinism device-replay --knob learner_reduction=arrival` → 247); `no_default` (the
profile set in a scratch configuration file: ignored, warning finding, exit 2); `reeval` (`frob --json eval run
--policy <P> --task quad-flat-velocity --stream dev --seeds 1 --tier batch-cpu --determinism device-replay --key
ft-reeval-a-$SEED-<run-id>` and the same under `ft-reeval-b-…`: both envelopes `idempotent_replay: false`,
identical per-world digests, class D2); `cite` (`cargo test -p frob-verbs --release --test fast_training_e2e`
against the script's state root: `cite_check` on J's training return, on P before and after the
re-evaluation, giving 861, 861 and admitted, and P's standing read through `frob --json evidence trace <P>`;
the planted manifests with `trained_under` removed and with a disagreeing member refused on import). The
citations through the M3 verbs and the gate are N35-32's (`scripts/e2e/num_licences_d4.sh`, which runs after
BD-269). Logs through the STD-E2E helper to `target/e2e-logs/num_fast_training/<utc>.ndjson` with a transcript:
every `cmd` with exact command line, exit code and wall time; the evidence block (the training job's lines show
determinism D4, the evaluations D2); `refusal` events with code, `pointer`, `observed`, `required` and first
repair; `metric` lines for the two evaluation digests (threshold: equal); on failure the artifact identifiers
and the first differing digest; a `summary` with counts.

### Known answers and negative controls
- KA-801: a policy trained under `fast-training` and evaluated twice under `device-replay` gives identical
  digests; negative control: citing its training return is refused (`FROB-REF-861`).
- KA-802: a cited training return is refused.
- Negative controls of this bead: a build in which the citation check is disabled (the planted citation is
  then accepted, and the gate test must fail); a `fast-training` job with a planted nondeterministic reduction
  inside a physics kernel (the frozen-learner comparison must fail).
- Determinism lanes: the re-evaluation twice on one machine and under slot permutation (class D2); the
  training run itself is run twice and is *expected* to differ when `arrival` knobs are active; a test asserts
  only that both runs carry the D4 label.

## Considerations

- Kill gate KILL-SHARD (decided at M2: paired lower bound of two-card strong scaling at equal task quality
  below 1.6 after one optimization pass). If it fires, no asynchronous collection is funded, the `collection`
  knob stays `synchronous`, and the profile keeps only the knobs the pilot funded.
- Three codes meet here: 861 (this chapter), 867 (the learning chapter: a D4 training result cited without
  re-evaluation) and 825 (the safety chapter: a result of class D4 offered as evidence). The reading used is in
  the refusal registry bead (N35-REF) and is the same in N23a-18 and N37-28: a run-time number cited is 861
  everywhere; an un-re-evaluated policy is 867 at `frob-learn`'s verbs and 861 elsewhere; a stored D4 result
  offered to one of the five consumers is 825, except that a D4 arm at the admission of a paired comparison is
  542 at `eval.compare`, 533 at the Arena study admission and 561 at the licence check (N35-REF's division).
- A D4-trained policy is admissible as data like any other policy file; the weight format allowlist and the
  ban on code in payloads apply unchanged.
- A training curve is useful for a human to look at. It may be shown, labelled D4, in `train.status` and the
  dashboard; it may not enter any artifact that carries a claim.
