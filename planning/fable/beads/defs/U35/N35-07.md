## Background

Every result carries a determinism class: D0 exact; D1 bitwise across backends; D2 bitwise per backend and
independent of the batch a world ran in; D3 agreement inside a recorded envelope with agreeing task decisions;
D4 nothing. Decision ADR-NUM-01: every verb declares the minimum determinism class of its inputs, and refuses
below it. The reason: a statistic that pairs, replays or attributes is only as good as the replay under it.

| Use | Minimum class | Below it |
|---|---|---|
| Certificates, digests, world addresses, strict predicates, requirement verdicts at a boundary | D0 | Refused at build time (`FROB-REF-252`) |
| Replay of a world on another tier with a claim of bit equality (`sim.replay --tier`) | D1 across families; D2 within one | The replay is labelled a tolerance replay and compared by the decision-level test |
| Paired comparison on common world addresses (`eval.compare`) | Both arms D2 on one device family with the batch-independence gate (GATE-SPARK-15) current, or D1 across families: `paired-exact` | D3: allowed as `paired-by-address`, labelled, with the realized pair correlation reported beside the verdict. Any arm D4 or of unrecorded class: refused (`FROB-REF-561`). Arms on different families without D1: unpaired by declaration |
| Interventional attribution and counterfactual forks | D2 with GATE-SPARK-15 current | Refused (`FROB-REF-562`) |
| Promotion of a fast-tier result | D3 with a ledger envelope and the decision-level test | D4: refused |
| Reuse of a memoized episode | D0 for analyses; D2 on the same backend and fingerprint for episodes | Recomputed |
| Training | D2 by default | D4 only as the labelled profile |
| A performance figure | Any class, stated in the disclosure block | — |

**Why pairing and attribution need replay.** Seeding a generator fixes the draws, not the order of a
reduction. A difference of one unit in the last place grows like e^(λt) in contact-rich dynamics and reaches
order one after about ln(2²⁴)/λ ≈ 16.6/λ seconds, for a largest Lyapunov exponent λ that is measured per task.
The variance of a paired difference scales with 1 − ρ: if uncontrolled arithmetic lowers the correlation
between arms from 0.95 to 0.50, a comparison needs (1 − 0.50)/(1 − 0.95) = 10 times the episodes (illustrative
values). A paired test under class D3 remains valid as statistics, which is why it is allowed and labelled.
Under class D4 nothing about an arm can be replayed, so its verdict could not be reproduced, promoted or
attributed; that is the reason for the refusal, and the refusal is by code, not by convention.

This bead is the table as data and the one function every admitting verb calls. It is at M2 because replay,
teleport and forks arrive at M2; the paired-comparison rows are exercised on devices at M3 by the gate bead
(BD-269). Tier: Solid. It protects construction C-15 (evidence is a test martingale: pairing by world address
is refused under an uncontrolled determinism class) and C-29 (a deterministic forkable simulator is a causal
model: with bitwise replay, a fork is an intervention; without it, a fork is two unrelated runs).

## Scope

In: the `min_determinism` declarations in the verb registry; the `Use` enumeration; `licence::check`; the
labels it returns; the currency condition; the four refusals raised here with their repairs; the citation rule
for device results; a registry lint. Out: the classifier that supplies an arm's class (N35-02); the

realized pair correlation and the divergence rate (N35-08); `fast-training` (N35-06); the verbs' own logic;
the gate (BD-269).

## Technical approach

**Declarations (DESIGN).** Each row of `registries/verbs.toml` gains a `uses` list, one entry per way the verb
consumes results: `{ use, min, across_families_min, needs_current = ["composition" | "cpu_device_check"],
below = "refuse:<code>" | "label:<label>" | "recompute" }`. The generated schema prints the list in the verb's
help, so an agent can read what a verb needs before calling it. A registry lint (`check-contracts`) fails a
verb of kind `run` that consumes stored results and declares no `uses`.

**Types (DESIGN; `frob_core::det::licence`).**

```rust
pub enum Use { ExactArtifact, BitReplay, PairedComparison, Attribution, Fork, Promotion,
               MemoAnalysis, MemoEpisode, Training, PerformanceFigure, CiteDeviceResult }
pub struct ArmFacts { class: Option<DetClass>, family: DeviceFamily, profile: ProfileRecord,
                      composition_current: bool, cpu_check_current: bool, fingerprint: Digest }
pub enum Licence { Exact, PairedExact, PairedByAddress { needs: DecisionRecordId }, Unpaired,
                   ToleranceReplay, Recompute, Admitted }
pub fn check(u: Use, arms: &[ArmFacts], pair: Option<PairFacts>, asked: Asked) -> Result<Licence, Refusal>;
```

`PairFacts` carries the pair class from the classifier (D1, D3 with its decision record, or none). `Asked`
carries what the request demanded: `pairing = exact | by-address | unpaired | default` and
`replay = bit-equal | any`.

**The check, per use (numbered rules; the first that applies decides).**

*Bit replay (`sim.replay --tier`).* 1. Same family and class D2 with a current record, or different families
with pair class D1: `Exact`; the replay must then match digest for digest. 2. Otherwise, if the request
demanded `bit-equal`: `FROB-REF-247` (the class is not attainable on that placement). 3. Otherwise
`ToleranceReplay`: the output is labelled `tolerance-replay`, compared by the decision-level test, and its
first divergence is recorded.

*Paired comparison.* 1. Any arm with class D4, or with no recorded class: `FROB-REF-561`, naming the arm.
2. Both arms on one family, both D2, `composition_current` for both: `PairedExact`. 3. Arms on different
families with pair class D1: `PairedExact`. 4. Arms on different families without D1: if the request demanded
`exact` or left the default, `FROB-REF-561` ("paired across device families without class D1"); if it asked
`by-address` and a decision-equivalence record exists for the task and the placement pair,
`PairedByAddress`; if it asked `unpaired`, or no such record exists and it asked `by-address`, `Unpaired`
(with a finding that pairing was not available). 5. Same family but only D3 (for example `repeat` holds and
the batch-independence record is stale): `PairedByAddress` if a decision record exists and the request allows
it, otherwise `FROB-REF-561` with the repair `frob spark check --sweeps all`.
A `PairedByAddress` verdict is labelled `paired-by-address` and must print the realized pair correlation
beside the verdict (N35-08); a verb that returns the label without the correlation fails its schema.

*Attribution and forks.* Source run class D2 and `composition_current`: `Admitted`. Otherwise `FROB-REF-562`,
with repairs: teleport the world to `batch-cpu` and fork there; re-run under `device-replay` on a family with a
current record; renew the record.

*Promotion.* Fast-tier result of class D3 or better, with a fidelity-ledger envelope for the quantity and a
decision-equivalence record: `Admitted`. Class D4: refused with the evidence boundary's code for a D4 result
offered as evidence (`FROB-REF-825`, owned by the safety chapter).

*Memo reuse.* Analyses: D0 required. Episodes: D2 with an equal `ProfileRecord`, backend and fingerprint
digest. Otherwise `Recompute`: never a refusal, never a hit.

*Training.* D2 by default. `fast-training` only through its option (N35-06).

*Performance figure.* Any class; the check only verifies that the class is present for the disclosure block.

*Citing a device result.* `cpu_check_current` must hold for every kernel of the result's step plan on that
device family, driver and compiler. Otherwise `FROB-REF-864`, with repairs `frob spark check`, then
`frob spark fingerprint` if the fingerprint changed, then citing the `batch-cpu` result.

*Exact artifacts.* Certificates, digests, addresses, strict predicates and requirement verdicts at a boundary
are D0 by type. There is no run-time path that offers a floating comparison for them: the kernel toolchain
refuses a strict predicate in bare floating point at build time (`FROB-REF-252`), and `check(ExactArtifact, …)`
with an arm below D0 is a programming error surfaced as an internal refusal in tests.

**"Current" means** the record's fingerprint digest, kernel content hashes, step plan identity and profile
equal the run's (the classifier's currency rule).

**Envelope fields.** `pairing: "paired-exact" | "paired-by-address" | "unpaired"`,
`replay: "exact" | "tolerance"`, `licence: { use, min, class_observed, records }`.

## Acceptance criteria

- [ ] Every verb in the registry that consumes stored results declares `uses`; the lint fails a planted verb without them.
- [ ] `check` is a pure function; a table test over every (use, arm class, family relation, currency, asked) combination returns the licence or the refusal the rules above state, with no combination unhandled.
- [ ] A D4 arm and an unrecorded arm in a paired comparison each return `FROB-REF-561` naming the arm; a cross-family pair demanded as paired without D1 returns `FROB-REF-561`; the same pair asked `unpaired` is admitted and labelled.
- [ ] A fork or attribution on a source run below D2, or with a stale batch-independence record, returns `FROB-REF-562`; the same request after teleport to `batch-cpu` is admitted.
- [ ] `sim.replay --tier` across families without D1 produces a `tolerance-replay` label, never an `exact` one, and with `--require bit-equal` returns `FROB-REF-247`.
- [ ] A memoized episode with a different fingerprint digest or `ProfileRecord` is recomputed (the receipt shows a miss with reason), never served.
- [ ] A device result whose check is stale cannot be cited: `FROB-REF-864` with `frob spark check` as first repair.
- [ ] Every refusal raised here carries `observed` (class and records), `required` (class and use) and ranked repairs, exit code 3.
- [ ] The licence label and the observed class appear in the envelope of every admitted request.

## Test plan

### Unit tests
- `licence_table_total`: enumerates all combinations (11 uses × classes {none, D4, D3, D2, D1, D0} × {same family, different} × currency × asked) and asserts the rule that fires; no combination panics.
- `paired_d4_arm_refused_561`, `paired_unrecorded_arm_refused_561`, `paired_cross_family_demanded_refused_561`, `paired_cross_family_unpaired_admitted`.
- `paired_same_family_d2_current_is_exact`; `paired_d3_with_decision_record_is_by_address`; `paired_by_address_without_record_falls_to_unpaired`.
- `attribution_below_d2_refused_562`; `fork_stale_composition_refused_562`.
- `bit_replay_cross_family_is_tolerance`; `bit_replay_demanded_refused_247`.
- `memo_episode_fingerprint_mismatch_recomputes`; `memo_analysis_requires_d0`.
- `cite_device_result_needs_current_check_864`.
- `verbs_registry_uses_lint`: a planted `run` verb without `uses` fails.
- `label_requires_correlation`: an envelope with `pairing: paired-by-address` and no `pair_correlation` field fails schema validation.

### End-to-end script and logging
No script of its own, because the verbs that call the check (replay, forks, the memo graph, comparison) are
other beads and must not be prerequisites of the check they call. Two scripts drive it through the real `frob`
binary. At M2, the `licences_*` steps of `scripts/e2e/num_profiles.sh` (bead N35-31):
`frob --json sim replay <episode> --tier batch-cpu` from each device family present (label `exact` or
`tolerance` as the classifier says); the same with `--require bit-equal` on a family without D1 (expect 247);
`frob --json run fork` on a run whose record was made stale by the conformance fingerprint override (expect
562), then after `frob spark check --sweeps all` (expect admission); a memo hit and a forced miss. At M3,
`scripts/e2e/num_licences_d4.sh` (bead N35-32, the gate script) adds the paired-comparison and citation cases.
Both log through the STD-E2E helper: `cmd` lines with exact command line, exit code and wall time; the
evidence block; `refusal` events with code, `observed`, `required`, first repair; `assert` lines with expected
and observed licence label; a `summary` line.

### Known answers and negative controls
- KA-802: a class D4 arm in a paired comparison and a cross-family pair demanded as paired without class D1
  are refused (`FROB-REF-561`); attribution below class D2 is refused (`FROB-REF-562`).
- CX-366: seeding the generator does not make two arms a replayable pair (the motivating case; its arithmetic
  is KA-803 in N35-08).
- Negative controls: a build in which rule 1 of the paired check is removed (a D4 arm is then admitted; the
  table test must fail); a verb that bypasses the check (caught by the registry lint and by the end-to-end
  sweep).
- Determinism: the check is exact (class D0); its tests run twice with identical output.

## Considerations

- Three statements had to be reconciled: D3 pairs are "allowed as `paired-by-address`"; arms on different
  families without D1 are "unpaired by declaration"; and `FROB-REF-561` refuses a request "as paired across
  device families without class D1". The rule used: across families without D1, pairing is never granted
  silently; it is refused when demanded as exact pairing, granted as `paired-by-address` only on explicit
  request and only with a decision-equivalence record, and otherwise the comparison is unpaired. This reading
  is flagged for the lead in the coverage file.
- KILL-D1: if a device family cannot hold bit equality with `batch-cpu`, every cross-family row above takes its
  "without D1" branch for that family, permanently; nothing else changes.
- The attribution chapter has its own code for attribution-time refusals under an uncontrolled class
  (`FROB-REF-584`); 562 is the licence check on the source run at admission.
- The check does not run tests. If a record is missing, the repair names the command that produces it.
