## Background

The determinism classes of the program (D1: the same bits on CPU, CUDA and Metal; D2: the same bits run to run
on one device family, independent of the batch) can only hold if kernels use arithmetic whose result is fixed
by the IEEE standard and by the kernel's source, not by a compiler's taste. The numerics chapter therefore
bans, in batched kernels, on every backend and in every profile (the labelled training profile relaxes
ordering and placement only, and admits a device matrix path for the learner's matrix-multiply kernel and
nothing else):

- any fast-math relaxation;
- any fused multiply-add, contracted by a compiler or written explicitly;
- any built-in transcendental function, and the reciprocal-square-root built-in;
- any floating-point atomic;
- any strict predicate in bare floating point.

A lint enforces the list in the shared kernel dialect's sources and in the Rust of the kernel crate
(`mul_add`, `sin`, `cos`, `exp`, `ln`, `powf` and their kin are rejected; `sqrt` is correctly rounded and
allowed), with `FROB-REF-251` at build time. The device probe records how each device family rounds an
explicit fused operation, as data for open question OPEN-NUM-1; the ban does not wait on it.

Why each ban. Platform elementary functions differ across libraries and GPUs, so only deterministic functions
written in the dialect from +, −, ×, ÷, √ and selects are used. Compilers contract a·b + c into one fused
operation by default on some backends, which changes the last bit. Floating-point atomics are the main source
of GPU nondeterminism (FACT, source register): compaction and reductions use count, exclusive scan, write, and
integer atomics are allowed only for maximum, minimum, bitwise or and wrapping add. A strict comparison in
bare `f32` is wrong exactly at the boundary (2²⁴ + 1 is not an `f32`; a recorded pilot mislabelled 36% of
near-boundary cases), so strict predicates use exact or guarded kernels.

The lints themselves are other beads (the dialect lint with the prelude; the Rust kernel lint with the kernel
intermediate representation). What is missing, and is this bead, is the evidence that the bans hold in what is
actually compiled and run: one normative table, a corpus that every lint must reject, an audit of the options
each backend really passes to its compiler, and canaries that fail at run time if a compiler contracted or
relaxed anyway. Tier: Solid.

## Scope

In: the ban table as the normative statement of the five bans (six rows, the reciprocal square root having its
own), completed in the registry file the lints load; the ban corpus in the conformance crate, one file per
banned token per language, with the test that a token added to the table is enforced without a code change;
the compile-option audit from recorded options; the seven ban canaries `K-canary-bans` through the production
compile path on each backend; the record for OPEN-NUM-1.

Out, with the bead that has it:
- The lints and their wiring (BD-013 for the engine and dialect rules 1 to 4 and 6; N21a-10, a dependency of
  this bead, for rules 5, 7, 8 and 9, the Rust kernel lint, the reader of the registry file and its schema,
  the call of the lint in every compile path and the cache's refusal of an unlinted unit). This bead tests
  that those lints reject every banned token; it implements no lint.
- The lint's own planted-defect corpus, `crates/frob-kir/tests/lint_corpus/` (N21a-10): at least two sources
  per rule for all nine dialect rules, which tests each rule's shape. The corpus here is a different one: it
  is exhaustive over the tokens of the ban table and covers the five bans only.
- The check of compile options before compilation (the lint call in `KernelBackend::compile`, N21a-10). The
  audit here reads what was recorded after the fact, in receipts and cache keys.
- The two double-float canaries `K-canary`, their start-up check, the device capability `double_float`, the
  fingerprint field `canaries` and `FROB-REF-609` (N21b-36, at M0). The seven canaries here are other kernels
  with another consequence; the two sets share one arithmetic fact, noted below.
- Predicate typing and the build-time refusal `FROB-REF-252` (BD-053); the device probe (BD-017); hazards
  other than the five bans (N35-19, N35-20).

## Technical approach

**Ban table (DESIGN; `registries/kernel_bans.toml`; the lints read their token lists from it, so a token added
here is enforced everywhere).** Division of the file between two beads: N21a-10 builds both lints to load
their banned tokens from this file, defines its schema and reader, and creates it with the token arrays its
rules reject (the Rust method list and the dialect tokens of rules 2 to 4). This bead completes it as the
normative table: the six rows below with an admitted form each, the strict-predicate row (enforced by BD-053,
not by a token lint), and every spelling confirmed against the pinned compilers when the row is written. The
Rust column below and the method list in N21a-10 are the same list; after this bead the file is the only
place it is kept. The list below is the content.

| Ban | Rust kernel sources | CUDA dialect expansion | Metal dialect expansion | Admitted form |
|---|---|---|---|---|
| Fast-math | fast-math intrinsics and attributes; any crate-level or command-line fast-math flag | The compiler's fast-math option; reassociation pragmas | The fast math mode; functions from the `fast` namespace | IEEE safe mode on every backend |
| Fused multiply-add | `mul_add`; the fused intrinsics; a target-feature attribute that enables contraction | `fma`, `fmaf`, the explicit rounded-fused intrinsics; contraction left on | `fma`; contraction left on | a·b + c as two operations; the split product for double-float |
| Transcendental built-ins | `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `exp`, `exp2`, `exp_m1`, `ln`, `log`, `log2`, `log10`, `ln_1p`, `powf`, `powi`, `hypot`, `cbrt` | The corresponding C functions in both precisions | The corresponding shading-language functions | `det_*` functions written in the dialect |
| Reciprocal square root | (none in the standard library; vendor intrinsics) | `rsqrt`, `rsqrtf` | `rsqrt` | 1 / `sqrt(x)` as two correctly rounded operations |
| Floating-point atomics | An atomic integer used to carry a float's bit pattern in a compare-and-swap loop | Atomic add, exchange or compare-and-swap on a floating type | Atomic operations on a floating type | Count, exclusive scan, write; integer atomics for maximum, minimum, or and wrapping add only |
| Strict predicate in bare floating point | A comparison whose result feeds a verdict, a termination or a region boundary, typed `float` | The same | The same | The exact-integer class, or a guarded residual with a derived error bound and an exact fallback |

`sqrt`, division and the four basic operations are allowed: the IEEE standard requires them correctly rounded.

**Corpus (`frob-conformance/corpus/bans/`).** One minimal file per banned token per language (Rust module,
dialect source), plus an `allowed` file per language containing `sqrt`, division, a select, a `det_*` call and
a permitted integer atomic. The test runs each lint on each file: every banned file must be rejected with
`FROB-REF-251` naming file, line, token and ban (the strict-predicate files with `FROB-REF-252`); each allowed
file must pass. A banned token inside a comment or a string must not be reported. The corpus test is generated
from the table: a token in the table with no corpus file fails the test, so the table and the corpus cannot
drift apart.

**Compile-option audit.** For every kernel compiled on every backend, the receipt and the cache key record the
options passed. The audit asserts, from those records and not from source: floating-point contraction is off;
no fast-math option is set; on Metal the safe math mode is selected (FACT: that backend's default mode may
contract multiply-adds and assume no NaNs); on the CPU no fused or fast-math code generation option is in the
build profile. A kernel whose record lacks the options is treated as failing.

**Run-time canaries (small kernels in the dialect, compiled by the ordinary production path and run through
the kernel harness on `batch-cpu`, CUDA and Metal; each returns raw bit patterns).**

| Canary | Computation in `f32` | Correct bits | What a violation returns |
|---|---|---|---|
| Contraction | a = 1 + 2⁻¹² (0x3F800800); r = a·a + (−(1 + 2⁻¹¹)) | 0x00000000, because a·a = 1 + 2⁻¹¹ + 2⁻²⁴ is a tie that rounds to even, 1 + 2⁻¹¹ | 0x33800000 (2⁻²⁴) if the product and sum were fused |
| Reassociation | (1 + 2²⁴) − 2²⁴ | 0x00000000, because 1 + 2²⁴ rounds to 2²⁴ | 0x3F800000 (1.0) if reassociated |
| Signed zero | (−0.0) + (+0.0) | 0x00000000 | 0x80000000 if the addition was folded away under a no-signed-zeros assumption |
| NaN | x = 0·∞; return select(x ≠ x, 1, 0) | 1 | 0 if NaNs were assumed absent |
| Division | 1 / 3 | 0x3EAAAAAB | Another pattern if a reciprocal estimate was substituted |
| Square root | √2 | 0x3FB504F3 | Another pattern if an estimate was substituted |
| Reciprocal square root | 1 / √2 computed as two operations | 0x3F3504F3 | Another pattern if a reciprocal-square-root built-in was substituted |

A failed canary on a device family refuses that family for floating kernels until the compile path is fixed,
and is recorded in the divergence ledger with the compiler identity.

Relation to the double-float canaries (N21b-36). The plan names two start-up canaries, the sum and product
canaries of `K-canary`, which prove that a compiler kept an error-free transformation; they are built at M0 by
N21b-36 with their own refusal. The seven canaries here are a DESIGN addition of this bead: they prove that
the production compile path did not contract, reassociate or relax ordinary arithmetic, and they are a second
kernel, `K-canary-bans`, run by `spark.check` in conformance, not a start-up check. The contraction
canary and the product canary of N21b-36 rest on the same fact, (1 + 2⁻¹²)² = 1 + 2⁻¹¹ + 2⁻²⁴, a tie that
rounds to even, and name the same bit pattern for 2⁻²⁴, 0x33800000; they detect different rewrites (a fused
product here; a folded error term there), and neither replaces the other.

**OPEN-NUM-1 (whether an explicit fused multiply-add is ever admitted in batched kernels).** Default: no.
Owner: Spark lead. It blocks nothing. Evidence: the probe's record of fused rounding on each family. This
bead writes the question's row in the decision register as `open, default no` with an evidence table read
from the probe report (per device family: is an explicit fused operation available; is it correctly rounded
with a single rounding on the probe's vectors; do all families in use agree bit for bit), and with the
conditions a future "yes" would have to meet: identical fused results on every family in use including the
CPU reference; a declared kernel sub-class so that manifests show which kernels use it; re-derived error
bounds for every guarded predicate downstream; and a recorded benefit (for example the double-float product at
3 operations instead of 17).

## Acceptance criteria

- [ ] `registries/kernel_bans.toml` holds the six rows with token lists per toolchain; both lints read their tokens from it (a token added to the file is rejected by the next lint run without a code change).
- [ ] Every corpus file with a banned construct is rejected with `FROB-REF-251` (or `-252` for the strict-predicate files) naming file, line and token; every `allowed` file passes; tokens in comments and strings are not reported.
- [ ] The compile-option audit passes for every kernel of the M2 library on every backend, from recorded options; a kernel compiled with a planted contraction-on option fails it.
- [ ] All seven canaries return the correct bits on `batch-cpu`, on each RTX 4090 and on Metal, through the production compile path.
- [ ] With the planted contraction-on option, the contraction canary returns 0x33800000 on a backend that fuses, and the family is refused for floating kernels.
- [ ] The audit and the canaries take a kernel set and a profile as inputs, so the `fast-training` kernel set can be audited without a code change (that check, with the device matrix path only for the learner's matrix-multiply kernel, is N35-06's acceptance; N35-06 depends on this bead). A synthetic profile (labelled `synthetic`) whose kernel set has one kernel compiled with contraction on fails the audit.
- [ ] The decision register has the OPEN-NUM-1 row with default `no`, the evidence table per device family and the conditions for admission.

## Test plan

### Unit tests
- `ban_table_rows`: six bans; every row has tokens for the three toolchains and an admitted form.
- `corpus_rust_rejected` (one case per token: `mul_add`, `sin`, `cos`, `exp`, `ln`, `powf` and the rest), `corpus_dialect_rejected`, `corpus_allowed_passes` (`sqrt`, division, select, `det_cos_2pi`, integer atomic maximum; the `det_*` call is one of N21a-11's registered set, which has no `det_sin`, and an unregistered `det_*` name is a build error there).
- `corpus_comment_and_string_ignored`.
- `strict_predicate_corpus_252`: a kernel that returns `a < b` on `f32` inputs as a verdict is refused; the same comparison inside a guarded kernel with a derived bound passes.
- `canary_expected_bits_host`: the seven correct patterns computed on the host in software (integer emulation of the rounding), independent of the kernel path.
- `contraction_canary_arithmetic`: exact rational check that (1 + 2⁻¹²)² = 1 + 2⁻¹¹ + 2⁻²⁴ and that the tie rounds to even.
- `audit_reads_recorded_options`: a receipt without options fails; one with contraction on fails.
- `bans_planted_contraction_audit` and `bans_planted_contraction_canary` (conformance build; on each device present, selected by `FROB_TEST_DEVICE`): the `K-canary-bans` kernel compiled with contraction on fails the audit, and on a backend that fuses returns 0x33800000 for the contraction canary and the family is refused for floating kernels; a backend that does not fuse records that and the audit alone is the control.
- `lint_tokens_from_registry`: adding a synthetic token (labelled `synthetic`) to a copy of the table makes the lint reject a file containing it.

### End-to-end script and logging
`scripts/e2e/num_bans.sh [--tier batch-cpu|gpu-cuda|gpu-metal|all] --seed <s>`: (1) `corpus`: `FROB_TEST_SEED=<s>
cargo test -p frob-conformance --release corpus_` (the lints over the corpus, the table-generated corpus check
and the strict-predicate files); (2) `options`: `frob spark precompile <target> --workload Q --key
nb-pc-<target>-<run-id> --json` for each device target present (for example `sm_89`), then the compile-option
audit over the resulting receipts and cache keys; (3) `canaries`: `frob spark check --kernel K-canary-bans
--backend <tier> --seed <s> --key nb-canary-<tier>-<run-id> --json` on each tier, reading back the seven bit
patterns; (4) `planted`: the planted contraction-on build in a conformance configuration
(`FROB_TEST_DEVICE=<id> cargo test -p frob-conformance --release bans_planted_`), expecting the audit to fail and,
where the backend fuses, the canary to return 0x33800000 and the family to be refused for floating kernels;
(5) `probe`: `frob spark probe --device <id> --suite ieee --seed <s> --key nb-probe-<id>-<run-id> --json` to
read the fused-rounding rows into the OPEN-NUM-1 evidence table, then `frob artifact read` of the decision
register row. Each run verb carries its own key and each envelope shows `idempotent_replay: false`. Logs
through the STD-E2E helper to `target/e2e-logs/num_bans/<utc-timestamp>.ndjson` with a transcript beside it:
`ts`, `script`, `bead`, `step`, `event`; `cmd` lines with exact command line, exit code and wall time; the
evidence block (claim known-answer, class, tier, determinism D0 for the canary patterns, identities with
fingerprint digest and compiler identity, seed); `refusal` events for each corpus rejection (code 251 or 252,
file, line, token); `metric` lines per canary and tier (expected and observed pattern); `assert` lines for the
audit per kernel; a `skip` event for an absent tier, never counted as passed; a `summary` line.

### Known answers and negative controls
- KA-805: the lint rejects `mul_add`, `sin`, `cos`, `exp`, `ln`, `powf` and their kin at build time
  (`FROB-REF-251`); `sqrt` is correctly rounded and allowed.
- The strict-comparison case of the kernel chapter: 16,777,216 < 16,777,217 is true in integers and false in
  `f32`.
- Negative controls: the planted contraction-on option (audit and canary); a lint with one token removed from
  its list (the corpus file for that token is then accepted and the corpus test fails); a canary kernel
  compiled with the fast math mode on Metal in a conformance configuration (the NaN or signed-zero canary
  must fail). The last is judged by the rule N21b-36 uses for its fast-math build (one convention for both
  canary sets): HYPOTHESIS that the compiler rewrites the pattern; the outcome is recorded per compiler, and
  if a compiler keeps every pattern under fast math the record says so and the control that cannot be vacuous
  is the audit, which fails on the recorded option whatever the compiler did with it.
- Determinism lanes: canary patterns twice on one machine, and equal across `batch-cpu`, CUDA and Metal (they
  are exact known answers, so equality across backends is required regardless of class D1).

## Considerations

- BET-02's control "a planted contraction (fused multiply-add) in one backend must be detected" is discharged
  here (audit and canary) and in the cross-backend check; it does not break batch independence, so the
  invariance gate does not see it.
- A compiler update can silently change defaults; the audit runs on every fingerprint change, since the
  kernel cache is keyed by compiler and driver and a change re-runs the check.
- The canaries prove the absence of specific rewrites, not of all; the lint and the options audit carry the
  general guarantee, and the cross-backend comparison of every kernel is the final net.
- The double-float pair deliberately avoids a fused operation (the split product with splitter 4097 = 2¹² + 1,
  17 operations instead of 3); its own start-up canaries belong to the Spark unit.
- OPEN-NUM-1 stays open by design; this bead must not be read as authorizing a fused operation anywhere.
