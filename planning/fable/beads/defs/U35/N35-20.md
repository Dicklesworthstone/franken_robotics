## Background

The numerics chapter lists 31 hazards through which determinism and precision are lost, each with the fact
that makes it a hazard and the rule that removes it. Part 1 of the register (N35-19) carries the hazards of
arithmetic and representation and defines the register's format (`registries/numeric_hazards.toml`: one row
per hazard with fact, rule, enforcement point, owners and a smallest-case test). This bead carries the other
fifteen: hazards that come from the *order* in which things happen (reductions, atomics, sorting, thread
completion, draws consumed in sequence), from what a world shares with its *batch* (composition, padding,
learner reductions, shards), and from the *lifecycle* of a run (warm starts, retries, toolchain changes).

These are the hazards that make a simulator pass its tests and then diverge in the field: a reduction whose
order follows scheduling replays correctly 999 times in 1,000, and 0.999¹⁰⁰⁰ = 0.37, so a campaign of a
thousand windows would replay exactly about one time in three. The rules below remove the dependence instead
of making it rare. Tier: Solid.

## Scope

In: fifteen rows with fact, rule, enforcement point, owner and test; the tests where no owner bead already has
the smallest case, and a binding where it does; the part-2 steps of the script. Out: the mechanisms (owner
column); the register's format and part 1 (N35-19).

## Technical approach

| HZ-28 | Retries and restores | A retried step that keeps part of its state diverges | A retry restores the whole committed state | Transactional step and commit fence; BD-081, BD-175 | `hz28_retry_equals_clean`: a step forced to retry once ends with the digest of a clean run with the same plan; the conformance variant that resubmits without restoring the committed slab differs |

**Binding rule.** As in part 1: where the owner bead has the smallest case as a test, the row names it; the
tests written here run against owners' public surfaces with no mocks.

**Cross-check of the whole table.** A registry test asserts that parts 1 and 2 together hold exactly the 31
identifiers HZ-01 to HZ-31 with no gap and no duplicate, so that a row cannot be dropped by either part.

## Acceptance criteria

- [ ] The fifteen rows of this part are in `registries/numeric_hazards.toml` with fact, rule, enforcement point, owners and a test; together with part 1 the register holds exactly HZ-01 to HZ-31.
- [ ] Each of the fifteen tests (or bound owner tests) passes on `batch-cpu`; the kernel-level ones (HZ-03, -04, -05, -09, -13, -14, -20, -28) pass on each device family present.
- [ ] Each test demonstrates the hazard as well as the rule, with the numbers or bit patterns listed (2⁻¹⁰ m/s for HZ-13; 0.25 against 0.5 for HZ-21; r₀ against r₁ for HZ-23; 0x3F800007 against 0x3F800008 for HZ-03).
- [ ] The workspace lint of HZ-08 is active (a planted hash-map iteration in an artifact-writing module fails the build check).
- [ ] HZ-11: after a fingerprint change no cached kernel loads, every check row is stale and citing a device result is refused (`FROB-REF-864`, the citation rule of N35-07: first repair `frob spark check`) until the check is run again.
- [ ] HZ-14: with padded and terminated lanes filled with 10³⁰, reward sums and gradient sums are bit-identical to those with neutral fill.
- [ ] Rows whose owner mechanism is not yet present are listed `pending` with their milestone, never as passed.

## Test plan

### Unit tests
The tests named in the table, in `crates/frob-conformance/tests/hazards_order.rs`, plus:
- `hazard_register_complete`: the union of parts 1 and 2 is HZ-01 to HZ-31, each once.
- `hz_campaign_replay_arithmetic`: 0.999¹⁰⁰⁰ = 0.3677 (the reason "rarely nondeterministic" is not accepted).
- `hz21_empty_shard_and_zero_count`: splits ({1, 0, 0, 0}, {}), ({1, 0}, {0, 0}), ({1}, {0, 0, 0}) all give 0.25; with no valid sample on either shard the update is skipped and the weights are unchanged bit for bit.
- `hz14_fill_values`: the reward and gradient sums with padded lanes filled with −0.0, with 10³⁰ and with NaN are bit-identical (the mask is a select, so even NaN in a masked lane does not propagate).

### End-to-end script and logging
`scripts/e2e/num_hazards.sh --part 2 --seed <s>` (the script of N35-19, which this bead extends with the part-2
steps): `FROB_TEST_SEED=<s> cargo test -p frob-conformance --release --test hazards_order` on the host, and with
`FROB_TEST_DEVICE=<id>` on each device present for the kernel-level rows (HZ-03, -04, -05, -09, -13, -14, -20,
-28); for the rows whose fixture kernel is registered, `frob spark check --kernel <fixture kernel> --backend
<tier> --seed <s> --key "$(e2e_key nh2-<row>-<tier>)" --json` on each tier; for HZ-09, `frob sim run --workload Q
--tier <t> --worlds 8 --seconds 4 --seed <s> --telemetry T3 --key "$(e2e_key nh2-whole-<t>)" --json` (the
reference quadruped workload; `T3` so that the record holds restart snapshots, which the default level does
not store), then `frob sim replay --run <whole> --world <w> --from-snapshot <a mid-run snapshot of the traced
world w> --key "$(e2e_key nh2-resume-<t>)" --json` (exit 0, `Bitwise`, is the split run equal to the whole one),
and the same pair with `--mutant snapshot-without-warm-start` on the `sim run` in the conformance build
(`sim.replay` takes no `--mutant`; labels `nh2-whole-m-<t>` and `nh2-resume-m-<t>`; the replay exits 2 at the
first solve after the resume); for HZ-28, a clean run of the same workload (`--key "$(e2e_key nh2-clean-<t>)"`)
against one with `--inject-faults seed=<s>,count=1` forcing one retry (`--key "$(e2e_key nh2-retry-<t>)"`),
compared with `frob telemetry divergence <clean> <retry> --mode exact --json`; for
HZ-11, the test `hz11_fingerprint_change_invalidates` (the fingerprint override is a test seam of the conformance
build, not a verb option), followed by `frob spark cache --list --backend <cuda|metal> --json` to log the cache
state. Every run verb carries its own key, and runs compared with each other never share one. It logs through
the STD-E2E helper to the log of N35-19's script (`target/e2e-logs/num_hazards/<utc-timestamp>.ndjson`): `cmd`
lines with exit code and wall time and the evidence block, one `assert` line per hazard and tier (identifier,
expected, observed), `refusal` events for the citation attempt of HZ-11, digests where state is compared, on
failure the first divergent step and kernel with the paths of both digest chains, a `skip` event for an absent
device, never counted as passed, and a `summary` line with rows bound, pending and failed.

### Known answers and negative controls
- KA-786 (−0.0 padding), KA-793 (draws with one extra leg), KA-800 (histogram order); the gradient known
  answer 0.25 of the two-device update rule; the dynamics chapter's retry relation (a retry of a transactional
  step equals a clean run with the same plan).
- CX-367, CX-371; the catalogue's entries for the mergeable sketch and for unordered floating-point scatter.
- Each row's broken variant is its negative control, asserted inside the same test or bound to a registered
  mutant (`arrival-placement`, `tile-shaped-tree`, `hashmap-order`, `snapshot-without-warm-start`,
  `batch-wide-reduction`, the fence-disabled seam).
- Metamorphic: splitting a rollout at a snapshot and resuming equals running it whole; a retry equals a clean
  run; permuting sample arrival leaves an update unchanged.
- Determinism lanes: host tests twice, across worker counts and build profiles; kernel-level rows per backend
  against the family's class.

## Considerations

- HZ-20 and HZ-21 are the two rows the labelled `fast-training` profile relaxes; under that profile their
  tests are not run as pass conditions, and the profile's own tests assert the D4 label instead (N35-06).
- HZ-11 is why the classifier treats check rows as records with currency: a class attested under one driver
  says nothing under the next.
- Racy controls (the atomic-counter compaction) are admitted per device family before they count: 20 trial
  pairs, at least 19 differing; otherwise `not-discriminating` on that family.
- The lint of HZ-08 applies to modules that write outputs. Hash maps used for lookup only are untouched; a
  sorted iteration or an ordered map is the repair.
