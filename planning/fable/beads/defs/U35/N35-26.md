## Background

When the system cannot do what was asked, it refuses: a refusal has a stable code, a message and ranked
repairs. Codes fall in families: `1xx` design and model; `2xx` numerics and integrator admission; `3xx` scene;
`4xx` control and estimation; `5xx` learning and evaluation protocol; `6xx` backend and device; `7xx` budget
and capability; `8xx` evidence and protocol (for example citing a provisional result as established); `9xx`
internal. The consolidated registry is `registries/refusals.toml`.

Three standing rules govern every refusal path in the program:

1. **Refuse, never truncate.** A result is whole or it is a refusal. A long answer is paginated and says so;
   it is never cut silently.
2. **A budget stop publishes nothing partial as a result.** A job that runs out of budget ends with a budget
   refusal; what it computed so far is job state, not an answer.
3. **A misspelt parameter is a refusal, not a default.** An unknown or misspelt name never falls back to the
   default value of the parameter the caller meant.

One clarification of the second rule: a mission query answers with certified cells, each of which is a
complete result with its own certificate, so a budget stop returns the cells certified so far together with
the unresolved remainder, and the envelope says that the answer is incomplete. No cell is ever returned
half-certified.

The rules exist because the callers are agents. An agent that receives a truncated list plans on a wrong
picture of the world; one that receives a partial result treats it as the answer; one whose misspelt
`--stifness 2e5` silently ran at the default stiffness draws a conclusion about a robot it did not simulate. A
rule of this kind is not enforced by any single verb's tests, because the next verb added can break it. This
bead enforces it as a sweep generated from the verb registry, so that every verb, present and future, is
covered. Tier: Solid.

## Scope

In: the generated sweep for each rule on the CLI and MCP surfaces; the mission-query clarification; the
family-to-exit consistency check for raised codes; the script. Out: the refusal type, registry loader and
envelope (BD-005, BD-022); pagination itself; budgets and the job engine; the fifteen rows this chapter
defines (N35-REF); the three failure classes on both surfaces (the Tether unit's gate GATE-TETHER-04: first
recorded at M2, closed on the full M3 registry by BD-299, which depends on this bead). That gate classifies
every failure as domain, protocol or transport, compares the envelopes of the two surfaces, checks the
code-to-exit map over the complete registry and runs the kill campaign; it takes its misspelt-parameter
stimulus from this bead's generator and does not repeat the three rules. This bead checks the code-to-exit
map only for the codes its own cases raise.

## Technical approach

**Generation.** `frob_conformance::refusal_rules::cases(registry)` reads `registries/verbs.toml` and the
generated input schemas and emits, per verb, the cases below. A verb present in the registry for which no
case of an applicable rule can be generated (for example a `run` verb with no budget parameter and no
declared exemption) fails the sweep's completeness check. Exemptions are explicit rows in the sweep's own
table with a reason, and are counted in the summary.

**Rule 1: never truncate.**
1. For every verb whose output schema contains an array: build a fixture store in which the array's true
   length exceeds the page size by one; call the verb; assert that either the full array is returned, or the
   envelope carries `cursor` and `frontier` and following the cursor yields exactly the missing elements; the
   union of pages equals the store's content and no element repeats.
2. For every verb with a capacity-bounded computation (contact capacity, row capacity, import size limits):
   exceed the capacity; assert a refusal, or a result that carries an explicit flag and the count of what was
   dropped (the `continue-flagged` policy), never an unflagged shorter result.
3. For every text field with a length cap in an output schema: assert that an over-long value is refused at
   the source or carried by reference, never clipped.

**Rule 2: no partial result on a budget stop.**
1. For every `run` verb with a budget (wall time, episodes, device-seconds): submit a job that needs more
   than its budget; assert exit code 4 (budget), `ok: false`, a `70x` refusal with `observed` and `required`,
   and that the artifact store holds no result for the request. The object kinds of the store are BD-097's
   table (`column`, `snapshot`, `certificate`, `receipt`, `report`, `still`, `bundle` at M1; it has no kind
   `result`), and `artifact.list` filters by `--run` or `--kind`, so the check is: `frob --json artifact list
   --run <run>` shows the committed chunks (`column`, and `snapshot` where the run stored any) and the job's
   one `receipt`, and no `report`, `certificate`, `still` or `bundle`; and that receipt, read with `frob --json
   artifact read <digest>`, says `budget-stop` (N32a-08) and carries no result. Two cases per verb,
   because a refusal at admission would let the rule pass without anything having run: (b), required from
   M1, a job that is admitted and then stopped: the smallest fixture made slow (a long simulated horizon)
   under a wall-time ceiling of 2 s, which it exhausts after at least one committed chunk, ending `failed`
   with `FROB-REF-702` (the job engine's budget stop at a safe boundary, N32a-08); (a), for every verb that
   publishes an estimate (registry field `estimable`; at M1 the estimate check of BD-022 and BD-135, from M2
   the conformal upper-end admission of N32a-15), a budget below the estimate's upper end, refused at
   admission with `FROB-REF-701` and the estimate attached. Case (b) is the one that tests the rule: a
   budgeted verb whose sweep produced only `701` fails the completeness check.
2. Assert that a later request for the same idempotency key returns the stored refusal, not a result.
3. *Mission queries.* For `mission.synthesize` and `mission.refute` on the M1 fixtures with a budget that
   stops after some cells: assert the envelope says the answer is incomplete (`resolution-unmet`), lists the
   certified cells and the unresolved remainder, that every returned cell has a certificate that
   `frob --json prove verify` accepts, and that no cell without a complete certificate is present.

**Rule 3: a misspelt parameter refuses.**
1. For every verb and every named parameter p: generate three misspellings (drop one character; transpose two
   adjacent characters; append `_`), skipping any that collide with another valid name; call the verb with
   the misspelt name and a valid value; assert exit code 3, a protocol refusal for schema validation, the
   offending name in `pointer`, and no side effect (the store's content hash is unchanged).
2. For every authored input format that exists at the milestone (design, module, card, task and mission
   files): add an unknown field at each nesting level; assert the design-and-model refusal for an unknown,
   misspelt or duplicate field, with the field path in `pointer`.
3. On the MCP surface: the same parameter cases through the generated tools; assert the input-validation
   error mapped to the same envelope skeleton with exit-3 semantics.
4. Enumerations: for every enumerated option (for example a profile name) pass a near-miss value; assert a
   refusal that lists the enumeration.

**Family and exit consistency.** Every refusal raised during the sweep is checked against the registry: the
code exists; its family matches the kind of fault provoked (a misspelt parameter must never surface as a
`9xx` internal code); its exit code is the registry's.

**Output.** A table per rule: verbs covered, cases run, cases passed, exemptions with reasons.

## Acceptance criteria

- [ ] The sweep generates at least one case of every applicable rule for every verb in `registries/verbs.toml`; the completeness check fails when a verb is added without a case or an exemption (planted verb).
- [ ] Rule 1: for every array-valued output, the union of pages equals the fixture store's content; no verb returns an unflagged shortened result when a capacity is exceeded.
- [ ] Rule 2: every budgeted `run` verb ends a starved job with exit 4 and a `70x` refusal, and the store holds no result artifact for it; each such verb has an admitted-then-stopped case (`FROB-REF-702`, at least one committed chunk) and, if it publishes an estimate, an admission case (`FROB-REF-701`); the idempotent replay returns the same refusal.
- [ ] Rule 2, clarified: a starved mission query returns only complete, independently verifiable cells plus the unresolved remainder, and its envelope says the answer is incomplete.
- [ ] Rule 3: every misspelt parameter on every verb exits 3 with the name in `pointer` and leaves the store unchanged; every unknown field in every authored format is refused; MCP and CLI agree.
- [ ] No case surfaces a `9xx` code or exit code 1.
- [ ] The sweep re-runs unchanged at each later milestone and its coverage grows with the registry (the summary prints verbs covered against verbs registered).

## Test plan

### Unit tests
- `cases_cover_registry`: for a fixture registry of five verbs (labelled `synthetic`), the generator emits the expected 5 × rule cases; removing a case fails completeness.
- `misspellings_generated`: `stiffness` → `stifness`, `stfifness`, `stiffness_`; a misspelling equal to another valid parameter is skipped.
- `page_union_equals_store`: a fixture list of 101 items with page size 100 → two pages, union of 101, no repeat.
- `budget_stop_leaves_no_result`: a job starved after its first chunk → the run's listing holds `column` rows and one `receipt` that says `budget-stop`, and nothing of another kind; a planted `report` row for the run fails the check.
- `admission_only_fails_completeness`: a fixture budgeted verb whose generated rule-2 cases all end in `FROB-REF-701` at admission (none admitted and stopped) → the completeness check fails and names the verb.
- `mission_stop_returns_complete_cells`: a stance-family query stopped after three cells → three cells with verifying certificates and a remainder; a planted half-certified cell in the response is rejected by the check.
- `family_exit_consistency`: a planted handler that maps a schema failure to an internal code is caught.
- `exemption_requires_reason`.

### End-to-end script and logging
`scripts/e2e/num_refusal_rules.sh [--surface cli|mcp|both] [--rule 1|2|3|all]`: builds the fixture store,
runs the generated cases through the real `frob` binary and, for the MCP surface, through `frob-mcp` over its
standard transport, and prints the three tables. Logs through the STD-E2E helper to
`target/e2e-logs/num_refusal_rules/<utc-timestamp>.ndjson`: one `cmd` line per case with the exact command
line, exit code and wall time; a `refusal` event per expected refusal with code, family, `pointer`,
`observed`, `required` and first repair; `assert` lines for store-unchanged checks with the content hashes
before and after; `metric` lines per rule (`verbs_covered`, `verbs_registered`, `cases`, `passed`,
`exemptions`); on failure the verb, the parameter, the response received and the path of the fixture store; a
`summary` line. Hostile or private strings are not used; the fixture store is synthetic and labelled so.

### Known answers and negative controls
- The exit-code table's known answer on a fixture of malformed, unknown, over-budget, unscoped and conflicting
  inputs (each maps to the exit code and refusal code the surface chapter states; KA-755: malformed →
  `FROB-REF-802`, exit 3; unknown → `-801`, exit 3; over-budget → `-701`, exit 4; unscoped → `-720`, exit 5;
  conflicting → `-803`, exit 7, the same five rows BD-299 exercises with real tokens at M3).
- Negative controls (conformance builds): a verb that clips its output array at the page size without a
  cursor (rule 1 must fail it); a job engine that publishes the last committed chunk as a result on a budget
  stop (rule 2); a parser built with unknown-argument tolerance (rule 3); a mission responder that returns a
  cell whose certificate is absent (the clarification).
- Determinism: the sweep's case list is a pure function of the registry; two runs produce the same cases in
  the same order.

## Considerations

- The sweep is generated, so its cost grows with the surface: about ten cases per parameter. At M1 this is a
  few thousand fast calls; long-running verbs are exercised with their smallest fixture and a tiny budget.
- Rule 2 does not forbid keeping work: committed chunks remain job state and a resumed job may use them. What
  is forbidden is presenting them as the answer.
- OPEN-AUGUR-7 (the exit code of a mission query that stops on budget with certified cells; default exit 2
  with `resolution-unmet`; owner: Tether lead) decides one detail of the clarified rule; the sweep reads the
  expected exit code from the registry so that the decision changes data, not the test.
- A numerical refusal, a budget stop and a physical failure of the robot are three different outcomes: the
  first two are refusals, the third is a result with findings. The sweep asserts that a simulated fall is
  never reported as a refusal.
