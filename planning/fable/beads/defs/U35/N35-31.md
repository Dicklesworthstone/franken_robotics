## Background

At M2 a user or an agent meets the numerics chapter through four things on the command line: the determinism
class printed on every result; the two options of `sim.run` that choose a determinism profile
(`reference-replay`, `device-replay`, `cross-backend`, `fast-training`) and a precision profile (`default`,
`stiff`); the `numerics` block that says what bounds each result; and the refusals that stop a request whose
class is too weak for what it asks (a replay with a claim of bit equality, a fork, a continuation under
another profile) or whose numbers left their admissible range (an ill-conditioned solve under the `refuse`
policy; an anchored offset that left its cell range in one step).

Each of those is built and unit-tested by its own bead. This bead is the end-to-end proof that they work
together through the real `frob` binary on real fixtures: plain shell, seed-explicit, idempotent, exiting
non-zero on any failed assertion, with the structured log of the program's testing standard. It is the
user-side script for the capability "run worlds under a declared profile and read what the numbers may
claim". It adds no mechanism. Tier: Solid.

## Scope

In: the script, its steps, assertions and log lines. Out: everything the script calls (profiles N35-04;
classifier N35-02; licences N35-07; the certificate block N35-27; anchored positions and the conditioning
record, reached through the precision-battery bead BD-179; teleport BD-204; forks BD-205; memoized episodes
BD-220). The paired-comparison and `fast-training` licences are M3 and belong to N35-32.

## Technical approach

**Invocation.** `scripts/e2e/num_profiles.sh [--tier referee|batch-cpu|gpu-cuda|gpu-metal|all] [--seed N]
[--steps profiles,precision,anchor,certificate,licences,classifier|all]`. Defaults: every tier present, seed
1, all steps. Fixtures: the built-in single-robot rollout; workload Q (reference quadruped) for 100 control
intervals on 64 world addresses; the conformance fixtures `ill-conditioned` (a near-rigid contact state whose
conditioning lower bound gives κ̂·u above the limit) and `runaway` (a body given a velocity that carries an
anchored offset past its range in one step, and a variant that walks out of the scene's declared cell
bounds).

**Steps.**
1. `preflight`: `frob --json doctor`; `frob --json spark devices`; `frob --json schema sim.run`, asserting the
   two options and their enumerations are in the generated schema (four profile names; `default`, `stiff`,
   `f32`, `f64` for `--precision`, with the recognized-and-refused values listed as such).
2. `profiles`:
   - `frob --json sim run --tier <t>` with no option: assert the recorded profile is `reference-replay` on
     `referee` and `batch-cpu`, `device-replay` on device tiers, precision `default`, degraded policy `refuse`,
     and that `evidence.determinism` equals the class the classifier attests for that placement.
   - `--determinism devcie-replay` (a misspelt value): exit 3, a schema refusal listing the enumeration.
   - `--determinism fast-training` on `sim.run`: exit 3, `FROB-REF-247`, applicable profiles listed.
   - `--determinism reference-replay --tier gpu-metal` (and `gpu-cuda`) where the family's D1 status is not
     `attained`: exit 3, `FROB-REF-247`, zero worlds stepped, first repair naming `batch-cpu`.
   - `reference-replay` on `batch-cpu`: the run twice, and split at a snapshot and restarted: identical
     digest chains and identical logical event logs.
   - A snapshot taken under `default` continued under another numerical profile: `frob --json run fork <run>
     --world <w> --at <tick> --precision stiff` (a fork continues the parent's state) and `frob --json sim
     replay --run <r> --world <w> --from-snapshot <hash> --tier batch-cpu --precision f64` without
     `--comparison`: each exit 3, `FROB-REF-894` (the snapshot container's code for a continuation under
     another profile, N29-REF; never 247, which is a class not attainable on the placement), first repair a
     comparison replay; the same replay with `--comparison`: admitted and labelled a comparison replay.
3. `precision`:
   - `--precision stiff`: assert a different step plan identity from `default` and `refinement_steps: 1` in
     the `numerics` block.
   - The `ill-conditioned` fixture under the default policy: exit 3, `FROB-REF-248`, `observed` carrying
     `kappa_lower_bound` and κ̂·u, first repair `--precision stiff`; no result artifact published.
   - The same with `--on-degraded continue-flagged`: exit 2 (completed with findings), the world counted
     under `degraded.ill-conditioned`, results flagged.
   - Width: `--precision f64 --tier batch-cpu` and `--precision f32 --tier batch-cpu` admitted, the
     `ProfileRecord` and the `numerics` block carrying width `f64` and `f32` respectively with profile
     `default`, and different `pins_digest`s; `--precision f64` on a device tier present, and `--precision f32`
     on the referee: exit 6, `FROB-REF-604`, zero worlds stepped, first repair `--tier batch-cpu`;
     `--precision f31`: exit 3, the schema refusal listing the enumeration; `--precision f16` where N18b-27
     (not a dependency of this bead) has landed: exit 3, `FROB-REF-245`; otherwise a `skip` event
     `capability absent` naming N18b-27, never counted as passed.
4. `anchor`: the `runaway` fixture: exit 3, `FROB-REF-249`, the body, axis and offset in `observed`; the
   out-of-bounds variant: `FROB-REF-249` naming the cell index and the scene bounds. A normal world that
   crosses a cell boundary completes with no refusal and a changed cell index.
5. `certificate`: workload Q on 64 world addresses on each tier; then for four of those addresses, `frob sim
   replay --run <r> --world <w> --alone` and `frob sim replay --run <r> --world <w> --batch-size 1024
   --co-tenants <seed>` (the same world beside 1,023 seeded co-tenants): assert the replayed world's two
   `numerics` blocks are equal field for field, every field of the run's block is populated or
   `not-applicable` with a reason, and κ̂ appears only under a name ending in `lower_bound`. (The full
   arrangement sweep of the block, slots, capacities and shards, is N35-27's own lane.)
6. `licences` (the M2 subset):
   - `frob --json sim replay <episode> --tier batch-cpu` from each device family: label `exact` where the
     pair class is D1 or the family is `batch-cpu` itself, `tolerance-replay` otherwise; with
     `--require bit-equal` on a family without D1: `FROB-REF-247` (N35-07's option, on `sim.replay`'s row in
     VERBS-sim).
   - `frob --json run fork <run> --world <w> --at <tick> --change '<setpoint> := <value>'` on a run of class D2 with a current
     batch-independence record: admitted. The same while the record is made stale by the conformance
     fingerprint override (BD-176's conformance seam, N21c-05's `FROB_INJECT_IDENTITY` on the driver string):
     `FROB-REF-562`, first repair teleport to `batch-cpu`. Then the override is lifted (while it is in force
     every device verb, the re-check included, is `FROB-REF-606` at admission, N21c-05) and, after `frob --json
     spark check --all --backend <family> --sweeps all`, the same fork is admitted again.
   - A memoized episode requested again under the same profile, backend and fingerprint: a hit (the receipt
     says so and the digests equal the stored ones); under `--precision stiff`: a recomputation with the miss
     reason; with the fingerprint override in force: `FROB-REF-606`, exit 6, at admission, never served from
     the memo (N21c-05: a receipt whose identity differs from the live one is never reused as a memoized
     episode); the override is then lifted.
7. `classifier`: with the fingerprint override in force: a new device run (`frob --json sim run --tier
   <device>`) is refused `FROB-REF-606`, exit 6, `pointer` naming `driver`, before any kernel launches, first
   repair `frob spark fingerprint`; `frob --json spark check --action list` shows that family's rows `stale`;
   and an attempt to cite a device result recorded in step 2 as gate evidence (`cargo run -p frob-conformance
   --example record_gate -- --gate <gate id> --receipt <hash>`, which passes the result through the evidence
   boundary's `citable` hook, BD-176) returns `FROB-REF-864` and records nothing. The override is lifted at the
   end of the step. The class a stale row gives a kernel set (`unrecorded`, printed D4 with reason
   `stale-check`) is N35-02's assertion at test level: under the override no device run is admitted to print
   it.
8. `summary`.

**Keys.** Every `run` verb the script calls (`sim run`, `sim replay`, `run fork`, `spark check`) carries its own
idempotency key `np-<step>-<n>-<tier>-<run-id>` (`<run-id>` the script run's UTC timestamp): the two
`reference-replay` runs of step 2, the split and restarted run, the two replays of step 5 and the re-check of
step 6 never share a key, and every envelope must show `idempotent_replay: false`, since a reused key returns the
stored receipt and would compare a run with itself. The memo step's hit is decided by the memo graph's identity
(profile, backend, fingerprint, address), not by the idempotency key, so a new key still hits.

**Logging.** The script sources the shared helper of STD-E2E and writes newline-delimited JSON to
`target/e2e-logs/num_profiles/<utc-timestamp>.ndjson` and a human-readable transcript beside it. Every line
has `ts`, `script`, `bead` (`N35-31`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `skip`, `end`),
the exact command line, exit code and wall time. `cmd` lines carry the envelope's `evidence` block (claim,
class, tier, determinism, identities including fingerprint digest, step plan identity and `pins_digest`,
seed). `refusal` events carry the code, the exit code, `pointer`, `observed`, `required`, `retry` and the
first repair. `metric` lines carry the `numerics` block's fields with units and thresholds (κ̂·u against the
limit in force; group error against 4 ulp; `rho_max` against 10⁻⁴ with `zero_work_worlds`), the digests compared and the memo
hit or miss reason. `assert` lines carry expected and observed values. On failure the log gives the first
differing value (for block equality, the field; for digest equality, the chunk and world address) and the
paths of the artifacts needed to reproduce. The final `summary` line counts assertions passed and failed.
Worlds are named by address; nothing from a private scene is written.

## Acceptance criteria

- [ ] The script exits 0 only if every assertion passed; two consecutive runs with the same seed produce the same digests, the same refusal codes and the same memo outcomes.
- [ ] Every refusal the script provokes has the registered code and exit code: 245, 247, 248, 249, 562, 864 and 894 with exit 3; 604 and 606 with exit 6; a continuation under another profile answered with 247 fails the step; the schema refusal with exit 3; `continue-flagged` completes with exit 2.
- [ ] On a machine without a device the device steps are logged as `skip` events with the reason `capability absent`, never as passed, and the script still exits 0 if the CPU steps pass.
- [ ] `reference-replay` on `batch-cpu` is byte-identical on repeat and across checkpoint and restart.
- [ ] The `numerics` block is identical for the same worlds in two arrangements on every tier present.
- [ ] A fork is refused on a stale record and admitted after the override is lifted and the check renewed; a memoized episode is served only under an equal profile, backend and fingerprint.
- [ ] The log validates against the STD-E2E line schema; every `cmd` line has an exit code, wall time and evidence block.

## Test plan

### Unit tests
The script has no unit tests of its own; `scripts/e2e/tests/num_profiles.bats` (run by the harness's
self-test) checks: option parsing; that an unexpected exit code from `frob` in any step makes the script exit
non-zero with the failure counted; that `skip` events are not counted as passed; that log lines validate.

### End-to-end script and logging
This bead is the script; see the steps and logging above.

### Known answers and negative controls
- KA-804 at run level (the class printed equals the weakest among kernels, placement, profile and inputs);
  KA-790 and KA-791 through the `anchor` step's normal cell crossing; KA-799's naming rule in the
  `certificate` step.
- Negative controls exercised: the misspelt profile name (a refusal, not a default); the stale fingerprint
  (device runs and memo reuse refused 606, check rows `stale`, forks refused 562, citation refused 864); the `ill-conditioned` and `runaway` fixtures; a
  conformance build in which profile admission is skipped must make step 2's `FROB-REF-247` assertions fail
  (run once by the harness's self-test to show the script can fail).
- Determinism lanes: step 2's repeat and restart on `batch-cpu`; step 5's two arrangements per tier.

## Considerations

- The limit behind `FROB-REF-248` is read from the frozen record of open question OPEN-NUM-4 where it exists
  and is 0.1 otherwise; the script logs which.
- The `licences` step needs teleport, forks and the memo graph (BD-204, BD-205, BD-220, all dependencies), so
  every sub-step runs; a `skip` event there is a failure of this bead, not an allowed outcome.
- All fixtures fit the default compute envelope (16 GiB, 8 cores, one hour, one device).
- Under kill gate KILL-D1's fallback for a device family the expected labels change (`tolerance-replay`
  everywhere for that family); the script reads the family's D1 status and asserts accordingly, so it needs
  no change when the gate is decided.
