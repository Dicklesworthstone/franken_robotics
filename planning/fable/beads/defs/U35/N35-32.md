## Background

Two gates at M3 show that determinism classes have consequences. GATE-SPARK-17 (Known answer; TARGET): each
licence refusal fires on its planted case (a class D4 arm in a paired comparison; attribution below class D2;
a cited training return; a cross-family pair demanded as paired), and a policy trained under the labelled
`fast-training` profile re-evaluates to the same digest twice. GATE-SAFE-09 (Known answer): a result produced
under the nondeterministic training profile is refused on each of the five paths on which evidence is
consumed (paired statistics, promotion, qualification, a certificate, a build packet), and the same policy
re-evaluated under class D2 is accepted.

(Class D4 means no reproducibility guarantee and is never evidence; class D2 means the same bits run to run
on one device family, independent of the batch a world ran in. `fast-training` is the only profile that
produces D4: it relaxes the learner's ordering and nothing in the physics, and its only output is a set of
weights tagged `trained_under: D4`.)

A gate is recorded only from a run of the real binaries with its negative controls shown to fail and, for a
gate made of refusals, with the twin requests shown to succeed, so that it cannot be passed by a system that
refuses everything. This bead is that run as a script: plain shell, seed-explicit, idempotent, exiting
non-zero on any failed assertion, with a structured log. It adds no mechanism. Tier: Solid.

## Scope

In: the script, its steps, assertions and log lines; both surfaces (CLI and MCP). Out: everything the script
calls (BD-269 and the beads under it).

## Technical approach

**Invocation.** `scripts/e2e/num_licences_d4.sh [--tier batch-cpu|gpu-cuda|gpu-metal|all]
[--surface cli|mcp|both] [--seed N]`. Defaults: every tier present, both surfaces, seed 1.

**Fixtures built by the script (small, inside the default compute envelope).** A `device-replay` evaluation
E_A of the baseline controller on 256 world addresses of the reference quadruped's flat velocity task on
tier T; the same on a second family or on `batch-cpu` (E_A′); a `fast-training` job J of 20 iterations on the
same task producing policy P, its training-time summary R (class D4) and its learning curve C; a class D3 run
S (a device run compared against `batch-cpu` on a family without class D1); a D2 run whose
batch-independence record is then made stale by the conformance fingerprint override.

**Steps.**
1. `preflight`: `frob --json doctor`; device and fingerprint status; the pilot record's verdict for the
   `fast-training` knobs (logged; if no knob is funded the script uses the conformance D4 job and says so).
2. `train_d4`: `frob --json train start --determinism fast-training …`; assert every status line, the
   receipt and the exported manifest carry determinism D4, the profile name and the knob values.
3. `case_1` to `case_6`: the planted requests, in order: `eval compare` with a D4 arm (expect 561); with an
   arm whose class field is absent (561); cross-family with default pairing (561); `autopsy attribute` on S
   (562); `run fork` on the stale run (562); attaching J's final return to a scorecard (861). For each:
   assert exit code 3, the code, that `observed` and `required` name the class and the use, and the first
   repair.
4. `twins`: the admissible versions: both arms under `device-replay` on one family (`paired-exact`); the
   cross-family request with `--pairing unpaired` (`unpaired`) and, where a decision-equivalence verdict
   exists for the pair, with `--pairing by-address` (`paired-by-address`, with a pair correlation printed);
   the attribution after `frob --json sim replay --tier batch-cpu`; the fork after
   `frob --json spark check --sweeps all`; the scorecard with the re-evaluation attached.
5. `reevaluate`: `frob --json eval run --policy P --determinism device-replay` twice on the same 256
   addresses, on each tier present; assert identical digests and that P's standing is `re-evaluated`.
6. `five_paths`: R offered to `eval compare` and to `study compare` (expect 561, 825), to `eval promote`
   (825), in an `eval qualify` request (825), as a certificate bundle input (825), and as build-packet
   evidence through the boundary function's conformance request (825; logged `boundary function` until the
   real verb exists). Then the re-evaluation of P offered on each path: accepted.
7. `unlabelled`: a copy of R with its determinism and profile fields removed, offered on the five paths:
   refused on each.
8. `misclassified`: a run with the conformance scheduling-dependent reduction, declared `device-replay`:
   assert the classifier prints a class below D2 and that a comparison and a fork on it are refused.
9. `sweep`: R offered to every verb whose registry row declares `uses`: assert no acceptance.
10. `mcp`: steps 3, 4 and 6 repeated through `frob-mcp`; assert the same codes inside tool results marked as
    errors with the same envelope.
11. `gate`: `cargo test -p frob-conformance --test g5 -- GATE-SPARK-17 GATE-SAFE-09`.
12. `summary`.

**Logging.** The script sources the shared helper of STD-E2E and writes newline-delimited JSON to
`target/e2e-logs/num_licences_d4/<utc-timestamp>.ndjson` and a human-readable transcript beside it. Every line
has `ts`, `script`, `bead` (`N35-32`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`),
the exact command line, exit code and wall time. `cmd` lines carry the envelope's `evidence` block (claim,
class, tier, determinism, identities, seed): the training job's lines show D4 and the evaluations D2.
`refusal` events carry the code, exit code, `pointer`, `observed`, `required`, `retry` and the first repair.
`metric` lines carry the two re-evaluation digests per tier (threshold: equal), the `pairing` label of each
twin, the pair correlation where printed, and the count of result-consuming verbs swept against the count
that refused. `assert` lines carry expected and observed codes and labels. On failure the log gives the
request file, the response and the identifiers of the artifacts offered. The final `summary` line counts
assertions and names both gates. Worlds are named by address; nothing from a private scene is written.

**Hand-off.** The script does not write `registries/gates.toml`; a recording session that did not implement
the work enters the rows from the log and the receipts.

## Acceptance criteria

- [ ] The script exits 0 only if every planted case was refused with its code, every twin was admitted with its label, the two digests of each re-evaluation were equal, and the gate test passed.
- [ ] Every refusal has exit code 3 and the registered code: 561 (three cases and one path), 562 (two cases), 861 (one case), 825 (four paths and the stored-study path).
- [ ] The five paths refuse R and accept the re-evaluation; the unlabelled copy is refused on all five.
- [ ] The sweep reports zero acceptances of R across all result-consuming verbs.
- [ ] CLI and MCP agree on every code and label.
- [ ] Where a verb of a path does not exist yet, the sub-step is logged `skipped: capability absent` (or `boundary function` for the build packet), never as passed, and the summary lists what remains to re-measure.
- [ ] The log validates against the STD-E2E line schema; two consecutive runs with the same seed give the same codes, labels and re-evaluation digests.

## Test plan

### Unit tests
The script has no unit tests of its own; `scripts/e2e/tests/num_licences_d4.bats` (run by the harness's
self-test) checks: option parsing; that an accepted planted case makes the script exit non-zero; that a
refused twin does the same; that `skipped` sub-steps are not counted as passed; that log lines validate.

### End-to-end script and logging
This bead is the script; see the steps and logging above.

### Known answers and negative controls
- KA-801 (step 5 and the refusal of step 3's sixth case), KA-802 (steps 3 and 4), the safety chapter's D4
  known answer (steps 6 and 7), KA-803 (the pair correlation printed in step 4).
- CX-366.
- Negative controls exercised: the unlabelled D4 result; the misclassified run; and, by the harness's
  self-test once, a conformance build with the comparison's admission check removed, on which the script must
  fail at `case_1`.
- Determinism lanes: step 5 is the lane for the re-evaluation (twice per tier); the training job is expected
  to differ between runs when an arrival-order knob is active and is not compared.

## Considerations

- The training job is deliberately tiny; its policy is poor and that is irrelevant: the gates are about
  labels, refusals and re-evaluation determinism, not about learned behaviour.
- Cross-family cases need two placements. On a machine with one device family the second placement is
  `batch-cpu`, which is a family of its own for this purpose.
- If kill gate KILL-SHARD fired and the pilot funded no knob, the script's D4 job is the conformance one; the
  summary states which was used, and the gate rows carry that fact.
- The build-packet path is re-measured at the milestone where the real verb lands; this script already
  contains the call and switches from the boundary function to the verb when the capability is present.
