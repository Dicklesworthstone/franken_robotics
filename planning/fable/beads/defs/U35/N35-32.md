## Background

Two gates at M3 show that determinism classes have consequences. GATE-SPARK-17 (Known answer; TARGET): each
licence refusal fires on its planted case (a class D4 arm in a paired comparison; attribution below class D2;
a cited training return; a cross-family pair demanded as paired), and a policy trained under the labelled
`fast-training` profile re-evaluates to the same digest twice. This bead's script measures that gate. The
other, GATE-SAFE-09 (Known answer): a result produced under the nondeterministic training profile is refused
on each of the five paths on which evidence is consumed (paired statistics, promotion, qualification, a
certificate, a build packet), and the same policy re-evaluated under class D2 is accepted. It is the safety
chapter's gate and is measured by that chapter's script, `scripts/e2e/safe_d4.sh` (N37-29), which is the only
script that offers a D4 result on the five paths.

(Class D4 means no reproducibility guarantee and is never evidence; class D2 means the same bits run to run
on one device family, independent of the batch a world ran in. `fast-training` is the only profile that
produces D4: it relaxes the learner's ordering and nothing in the physics, and its only output is a set of
weights tagged `trained_under: D4`.)

A gate is recorded only from a run of the real binaries with its negative controls shown to fail and, for a
gate made of refusals, with the twin requests shown to succeed, so that it cannot be passed by a system that
refuses everything. This bead is that run as a script: plain shell, seed-explicit, idempotent, exiting
non-zero on any failed assertion, with a structured log. It adds no mechanism. Tier: Solid.

## Scope

In: the script for GATE-SPARK-17, its steps, assertions and log lines; both surfaces (CLI and MCP).

Out, and which bead has it:

- The five-path matrix of GATE-SAFE-09 (a D4 result offered, labelled and unlabelled, to paired statistics,
  promotion, qualification, a certificate and a build packet; the D2 re-evaluation accepted on each), the sweep
  of every result-consuming verb, and the record of that gate: N37-29 (`scripts/e2e/safe_d4.sh`). The steps
  this script once had for them (`five_paths`, `unlabelled`, `sweep`) are that script's now.
- Everything the script calls: BD-269 and the beads under it.

## Technical approach

**Invocation.** `scripts/e2e/num_licences_d4.sh [--tier batch-cpu|gpu-cuda|gpu-metal|all]
[--surface cli|mcp|both] [--seed N]`. Defaults: every tier present, both surfaces, seed 1.

**Fixtures built by the script (small, inside the default compute envelope).** A `device-replay` evaluation
E_A of the baseline controller on 256 world addresses of the reference quadruped's flat velocity task on
tier T; the same on a second family or on `batch-cpu` (E_A′); a `fast-training` job J of 20 iterations on the
same task producing policy P, its training-time summary R (class D4) and its learning curve C; a class D3 run
S (a device run compared against `batch-cpu` on a family without class D1); a D2 device run on tier T whose
batch-independence record reads stale while the conformance fingerprint override (N21c-05's
`FROB_INJECT_IDENTITY`, BD-176's seam) is in force and current again once it is lifted. The override acts on a
device's driver string, so on a machine with no device the fork case and its twin are logged as a `skip` event
`no device`, never counted as passed.

**Keys.** Every call of a run verb (`train start`, `eval run`, `eval compare`, `autopsy attribute`, `run
fork`, `sim replay`, `spark check`) carries `--key nl4-<step>-<case>-<tier>-<surface>-$SEED-<run-id>`, so each
request is its own run and two runs that are compared never share a key (a shared key would return the first
one's stored receipt).

**Steps.**
1. `preflight`: `frob --json doctor`; device and fingerprint status; the pilot record's verdict for the
   `fast-training` knobs (logged; if no knob is funded the script uses the conformance D4 job and says so).
2. `train_d4`: `frob --json train start quad-ref --task quad-flat-velocity --backend batch-cpu --worlds 64
   --steps-per-collection 32 --steps 40960 --determinism fast-training --key …` (twenty collections of 64 × 32
   environment steps, N35-06's job; `train.start` takes `--backend`, not `--tier`); assert every status line,
   the receipt and the exported manifest carry determinism D4, the profile name and the knob values.
3. `case_1` to `case_6`: the planted requests, in order: `eval compare` with a D4 arm (expect 542, the
   comparison path's code, raised by `pairing::admit` before the licence check), and the same two arms given
   to the check directly with `cargo run -p frob-conformance --example licence_harness -- check --case 1`
   (expect 561, KA-802's site); with an arm whose class field is absent (561); cross-family with default
   pairing (561); `autopsy attribute` on S (562); `run fork` on the stale run with the override in force (562); attaching J's
   final return to a scorecard (861). For each: assert exit code 3, the code, that `observed` and `required` name the class
   and the use, and the first repair.
4. `twins`: the admissible versions: both arms under `device-replay` on one family (`paired-exact`); the
   cross-family request with `--pairing unpaired` (`unpaired`) and, where a decision-equivalence verdict
   exists for the pair, with `--pairing by-address` (`paired-by-address`, with a pair correlation printed);
   the attribution after `frob --json sim replay --tier batch-cpu`; the fork after the override is lifted
   (while it is in force every device verb, the re-check included, is `FROB-REF-606` at admission, N21c-05) and
   `frob --json spark check --all --backend <T> --sweeps all` has renewed the record. The scorecard twin needs
   the re-evaluation and is step 5's.
5. `reevaluate`: `frob --json eval run --policy P --task quad-flat-velocity --stream dev --seeds 1 --tier <T>
   --determinism device-replay` twice on the same 256 addresses under two distinct keys, on each tier present;
   assert both envelopes show `idempotent_replay: false` and identical digests; then the scorecard with the
   re-evaluation's success rate attached is admitted where case 6 was refused (twin 6′). No verb prints a
   policy's standing (`re-evaluated` from here on); N35-06's `fast_training_e2e` reads it from the artifact
   graph.
6. `misclassified`: a run of the conformance build loaded with N35-15's scheduling-dependent mutant
   (`frob --json sim run … --tier <T> --determinism device-replay --mutant cross-world-atomic-compaction --key …`,
   on a family where that mutant was admitted; elsewhere logged `not-discriminating`, never counted as passed):
   assert the classifier prints a class below D2 and that a comparison and a fork on it are refused.
7. `mcp`: steps 3 and 4 and twin 6′ repeated through `frob-mcp`; assert the same codes inside tool results marked as
   errors with the same envelope.
8. `gate`: `FROB_TEST_SEED=$SEED cargo test -p frob-conformance --test g5_determinism -- GATE-SPARK-17` (the
   tier target's full name).
9. `summary`.

Not in this script: offering R on the five evidence paths (to `study compare`, `eval promote`, `eval qualify`,
a certificate bundle and a build packet, each `FROB-REF-825`), the unlabelled copy of R on the same paths, and
the sweep of R over every verb whose registry row declares `uses`. Those steps, with their repetition through
`frob-mcp` and the G5 row of GATE-SAFE-09, are in `scripts/e2e/safe_d4.sh` (N37-29). The one D4 request on
the paired-statistics side that stays here is `case_1`: a D4 arm in `eval compare`, which is the admission of
a new comparison and is refused with 542 at the verb (561 at the licence check called directly).

**Logging.** The script sources the shared helper of STD-E2E and writes newline-delimited JSON to
`target/e2e-logs/num_licences_d4/<utc-timestamp>.ndjson` and a human-readable transcript beside it. Every line
has `ts`, `script`, `bead` (`N35-32`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`),
the exact command line, exit code and wall time. `cmd` lines carry the envelope's `evidence` block (claim,
class, tier, determinism, identities, seed): the training job's lines show D4 and the evaluations D2. `refusal`
events carry the code, exit code, `pointer`, `observed`, `required`, `retry` and the first repair. `metric`
lines carry the two re-evaluation digests per tier (threshold: equal), the `pairing` label of each twin and the
pair correlation where printed. `assert` lines carry expected and observed codes and labels. On failure the log
gives the request file, the response and the identifiers of the artifacts offered. The final `summary` line
counts assertions and names GATE-SPARK-17. Worlds are named by address; nothing from a private scene is written.

**Hand-off.** The script does not write `registries/gates.toml`. The GATE-SPARK-17 row is entered by BD-269
(on which this bead depends) from its own measured outcomes. The script produces a receipt (its log
reference, receipt hashes and per-tier digests); a recording session that did not implement the work then
records the gate again from it with `cargo run -p frob-conformance --example record_gate -- --gate
GATE-SPARK-17 --receipt <hash>` (the one writer of gate rows, N38b-19), which adds the receipt to the row's
measured history, and a failed script is recorded as a failed measurement.

## Acceptance criteria

- [ ] The script exits 0 only if every planted case was refused with its code, every twin was admitted with its label, the two digests of each re-evaluation were equal, and the gate test passed.
- [ ] Every refusal has exit code 3 and the registered code: 542 (case 1 at `eval compare`), 561 (case 1 at the check, cases 2 and 3), 562 (two cases), 861 (one case); a build whose `eval compare` answers 561 for the D4 arm fails `case_1`.
- [ ] The script offers no D4 result on the five evidence paths and records nothing for GATE-SAFE-09; its summary names GATE-SPARK-17 only.
- [ ] CLI and MCP agree on every code and label.
- [ ] Where a verb of a case does not exist yet, the sub-step is logged `skipped: capability absent`, never as passed, and the summary lists what remains to re-measure.
- [ ] The log validates against the STD-E2E line schema; two consecutive runs with the same seed give the same codes, labels and re-evaluation digests.

## Test plan

### Unit tests
The script has no unit tests of its own; `scripts/e2e/tests/num_licences_d4.bats` (run by the harness's
self-test) checks: option parsing; that an accepted planted case makes the script exit non-zero; that a
refused twin does the same; that `skipped` sub-steps are not counted as passed; that log lines validate.

### End-to-end script and logging
This bead is the script; see the steps and logging above.

### Known answers and negative controls
- KA-801 (step 5 and the refusal of step 3's sixth case), KA-802 (steps 3 and 4), KA-803 (the pair correlation
  printed in step 4). The safety chapter's D4 known answer (KA-834) is exercised by N37-29's script.
- CX-366.
- Negative controls exercised: the misclassified run; and, by the harness's
  self-test once, a conformance build with the comparison's admission check removed, on which the script must
  fail at `case_1`.
- Determinism lanes: step 5 is the lane for the re-evaluation (twice per tier); the training job is expected
  to differ between runs when an arrival-order knob is active and is not compared.

## Considerations

- The training job is deliberately tiny; its policy is poor and that is irrelevant: the gates are about
  labels, refusals and re-evaluation determinism, not about learned behaviour.
- Cross-family cases need two placements. On a machine with one device family the second placement is
  `batch-cpu`, which is a family of its own for this purpose.
- If kill gate KILL-SHARD fired and the pilot funded no knob, the script's D4 job is the conformance one; the
  summary states which was used, and the gate rows carry that fact.
- The build-packet path, with its re-measurement at the milestone where the real verb lands, belongs to the
  five-path script of N37-29 and is no longer part of this one.
