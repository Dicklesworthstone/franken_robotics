## Background

Every refusal of the system has a stable code `FROB-REF-nnn`, a message and ranked repairs. An agent repairs by
code, a verb lists the codes it may return, and every code maps to exactly one exit code. The first digit is the
family, by what is refused: `1xx` design and model; `2xx` numerics and integrator admission; `3xx` scene; `4xx`
control and estimation; `5xx` learning and evaluation protocol; `6xx` backend and device; `7xx` budget and
capability; `8xx` evidence and protocol (for example citing a provisional result as established); `9xx` internal.
Exit codes follow the family: 3 for `1xx` to `5xx` and for `8xx` other than conflicts; 4 and 5 inside `7xx`; 6 for
`6xx`; 7 for conflicts; 9 for integrity faults, which are `FROB-REF-810` and all of `9xx`. A code is never reused
and a retired number stays retired. The machine-readable registry is `registries/refusals.toml`; the bead N35-33
owns it as a whole (an allocation ledger `registries/refusal_allocations.toml`, a pure allocation rule, the exit
rule per sub-family, cross-chapter checks).

FACT (counted from the printed registry of 294 rows): of the 99 numbers 801 to 899, 94 are printed (801 to 835,
840 to 881, 883 to 899). `FROB-REF-882` is retired in favour of `FROB-REF-582` (state from one model grafted onto
another) and may not be reused. **Four numbers are free: 836, 837, 838, 839.** No `9xx` row is printed.

FACT (read from the chapter registries): subsections added late state refusals in words, with no number, and most
of their owners classify them as evidence-or-protocol refusals. By the requesting beads' own classification the
second allocation round (N35x-02) holds 22 requests for `8xx`: mission queries 6 (one of them, BD-362's
`synthesis-out-of-scope`, filed in polishing round 1), structure and manufacture 8 (one of them, the packet
assembler's `packet-inconsistent`, filed in polishing round 1), telemetry 1, calibration 3, the surface 1, the
workspace's admission reader 2, the studio 1. Reclassified strictly by what is refused, 1 of the 22 leaves the
family (a binding of the model refused at run admission, to `1xx`); the others match conditions the family
already holds (sealed-set protocol, dataset admission, certificate and report evidence). The first allocation
round (N35-33) has its own `8xx` requests, which its rule 8 leaves unassigned: Kinesis 2
(`solve-queues-unqualified`, `ancestor-path-after-kill`), Arena's campaign and qualification-ledger refusals
(six by N24-REF's count), Performance 1 (a performance report whose rates violate the unit ordering) and
Surface 2 (`packet-over-byte-cap`, `packet-frames-not-retained`, proposed 836 and 837): 11. That leaves 32
requests (21 and 11) against 4 free numbers.

The requesting beads have each improvised, and the improvisations disagree: one proposes a continuation block
`901` to `907` inside `9xx` with exit 3 and enters it by default; one uses `838` as a provisional number; two ask
for "the next free `8xx` code"; two keep their refusals as `detail` values of existing codes. `9xx` with exit 3
contradicts the family table and the exit rule, and it takes the numbers that two integrity faults need (a scene
pack whose content does not match its identity; a device result that fails its own schema). This is a decision
about the code convention of the whole system, so it is the project owner's, on the proposal of the registry's
owner. It is due at the M0 exit: before the M1 mechanisms publish codes in results, logs and schema snapshots,
after which every change is a retirement.

## Scope

In: the options, the recommendation and the fail-closed default; the hold that enforces the default in the
allocation ledger; the capacity report per family; the record of the ruling and what it changes. Out: the
allocation rule and the first round (N35-33); the second-round requests and their families (N35x-02); the meaning,
message and repairs of any row (the chapter's registry bead); the code type and loader (BD-005); the envelope's
refusal block and the exit-code table of the surface (N32a-03).

## Technical approach

**Options put to the owner.**

| Option | What it is | For | Against |
|---|---|---|---|
| A. Reclassify | Apply "family by what is refused" to every request before numbering | Costs nothing; no convention changes | Not sufficient alone: 32 requests (the second round's 21 and the first round's 11) remain for 4 numbers |
| B. Four-digit continuation | A family that is full continues at `F100` to `F999`: the evidence family at `FROB-REF-8100` onward. The family is still the first digit | One condition keeps one code, one message, one exit; nothing printed changes; unlimited room | The code pattern widens from three digits to three or four: the generated code type, the envelope schema, the exit rule's ranges and every consumer that assumed three digits |
| C. Continuation inside `9xx` | `901` to `907` and onward as "evidence and protocol, continued" | No pattern change | `9xx` is internal with exit 9; the rows would carry exit 3 and fail the exit rule; integrity faults lose their family |
| D. Sub-reasons | Each new refusal is a `detail` value of the nearest existing code, permanently | No new numbers | An agent repairs by code and the repairs differ per sub-reason; per-verb refusal lists and "one code, one exit" lose resolution; two identifiers for one condition |

**Recommendation (DESIGN): A, then B for what remains; C and D are not taken.** Reason: B is the only option that
keeps the rule the whole surface is built on (a stable code with its own message and ranked repairs), and at M0
no code has been published, so widening the pattern costs one generator change and one schema pattern. D is kept
only as the interim form it already is.

**What B changes if ruled (each a one-line edit in the bead that owns the artifact).** The code pattern becomes
`FROB-REF-[1-9][0-9]{2,3}` in the registry schema, in the generated code type and in `frob.envelope/1`; the exit
rule gains one row per four-digit hundred in use (`81xx` → 3, with the same `conflict` and `integrity` lists);
the printout sorts by family, then numerically; codes are compared as whole tokens everywhere (`FROB-REF-810` is
a prefix of `FROB-REF-8100`, so a substring match is a defect and the registry test plants one).

**Fail-closed default (in force from the day this bead lands until the ruling is recorded).**
1. *Hold.* The ledger gains a table `[[hold]] family = "8xx"`, `numbers = [836, 837, 838, 839]`, `until =
   "docs/adr/ADR-NUM-refusal-8xx.md"` (DESIGN name) and a fifth request status, `held`. The allocation function
   never assigns a held number; a request whose family has no free number outside a hold receives `held`. The
   first round assigns no `8xx` number (N35-33 rule 8: its `8xx` requests stay `requested` with reason
   `owner-decision` until the hold lands), so the hold covers all four free numbers and every `8xx` request of
   both rounds becomes `held` when it lands.
2. *Interim.* A held request is raised under its interim code with a `detail` discriminator behind one named
   constant, as the ledger's interim rule requires. A held request with no fitting interim code keeps its raising
   bead open on that point; the mechanism still refuses and is not shipped as passing.
3. *No `9xx` row with an exit other than 9.* The loader's exit rule already fails such a row; the default says
   in words that the proposed `901` to `907` are not entered and that `838` is a held proposal, never an
   interim (N35-33 rule 7: a proposed, held or unassigned number is never an interim) and not a registry row;
   the request that proposed it raises its interim code with a `detail` value, as item 2 says.
4. *No four-digit code* loads before the ruling.
Silence is not a decision: each milestone exit lists the held requests by slug and the question as open.

**Capacity report (generated, so that the question cannot be forgotten).** `docs/generated/refusals.md` gains a
table per family: numbers printed, assigned since, retired, held, free, and requests `requested`, `held`. A
family whose requests exceed its free numbers is marked `over capacity`.

**The record of the ruling.** The ADR states the option, the date, the owner's reason, the list of held requests
and what each becomes. On ruling: the hold is lifted or replaced, the second round is re-run (it is a pure
function of the ledger and the registry), and each interim use becomes a one-line change with a schema-snapshot
update. Determinism class D0 throughout; nothing here enters the run ledger.

## Acceptance criteria

- [ ] The ADR exists at the M0 exit with the four options, the counts above re-derived from the ledger, and the
      owner's ruling, or the explicit statement that the fail-closed default stands; it is re-read at each exit.
- [ ] The registry test derives the free set of `8xx` from the printed rows as exactly {836, 837, 838, 839} and
      the retired set as {882}.
- [ ] With the hold in place, the allocation function assigns no number of the hold to any request, in 100
      shuffled orders of the requests; every `8xx` request without a number has status `held`.
- [ ] A planted `9xx` row with exit 3 fails the load; a planted row `FROB-REF-8100` fails the load before the
      ruling and, if B is ruled, loads with exit 3 afterwards.
- [ ] The capacity table is generated, byte-stable across two runs, and marks `8xx` as `over capacity`.
- [ ] The interim list served by `frob --json schema` shows every held request with its interim code, its
      `detail` value and the bead that raises it.

## Test plan

### Unit tests
`cargo test -p frob-core refusal_capacity` (the real registry and ledger; planted files are scratch copies
labelled `synthetic`):
- `free_set_8xx_is_836_to_839`; `retired_882_never_free`.
- `hold_blocks_assignment`: a request for `8xx` with the hold present → `held`; with the hold removed → 836.
- `hold_is_order_independent`: 100 seeded shuffles, the same set of `held` rows.
- `first_round_8xx_all_held`: the first-round ledger has no assigned `8xx` number; with the hold present every
  `8xx` request of both rounds (the first round's 11 and the second round's 21) is `held`.
- `held_proposal_not_interim`: a planted row with `interim = 838` fails the ledger check.
- `nine_xx_exit_three_fails`; `four_digit_code_needs_ruling`; `whole_token_match` (a search for `FROB-REF-810`
  in a text containing only `FROB-REF-8100` finds nothing).
- `capacity_table_counts`: for a synthetic family with 3 free numbers and 5 requests the table prints 3 free,
  2 held, `over capacity`.

### End-to-end script and logging
`scripts/e2e/refusal_family_capacity.sh`: (1) `cargo test -p frob-core refusal_capacity`; (2) `cargo xtask
check-generated` and a read of the capacity table; (3) `frob --json schema`, asserting that the interim list
equals the ledger's `held` rows; (4) for one held request whose raising mechanism exists, a request through
`frob --json` that provokes it, asserting the interim code, the `detail` value and exit 3 (logged `skipped:
capability absent` where the mechanism has not landed, never as passed). It logs through the STD-E2E helper to
`target/e2e-logs/refusal_family_capacity/<utc-timestamp>.ndjson`: `cmd` lines with exact command line, exit code
and wall time; `metric` lines per family (printed, free, held, requested); `refusal` events with code, `detail`,
exit and first repair; one `assert` per check; a `summary` line. No private-scene data is involved.

### Known answers and negative controls
- Known answers: 94 printed rows in `8xx`; 5 unprinted numbers, of which 1 retired; 22 second-round requests by
  the chapters' classification and 21 after reclassification, plus the first round's 11 (Kinesis 2, Arena 6,
  Performance 1, Surface 2): 32 against 4 free numbers.
- Negative controls (each must be caught): a ledger row assigned 837 while the hold stands; a `9xx` row with
  exit 3; a four-digit row before the ruling; a reuse of 882; a capacity table edited by hand.
- Metamorphic: permuting the requests changes no status. Determinism: integers and strings only, class D0,
  identical on every platform.

## Considerations

- The recommendation amends a convention the plan states (three-digit codes), which is why the owner rules. If
  the owner prefers D, the registry needs a `[[detail]]` table with its own message and repairs per sub-reason
  and the verb refusal lists must name code and detail; that cost is the reason D is not recommended.
- The same shortage will reach other families later; B is stated for any family, and only `8xx` is held now.
- Two integrity faults (the scene pack whose content does not match its identity; the device result that fails
  its own schema) are requested as the first rows of `9xx` (N35x-02 and the first round). Keeping `9xx` internal
  is what gives them exit 9 by rule.
- What would make us revisit: a published code that must change after M1, which is a retirement and an alias
  for one release, never an in-place edit.
