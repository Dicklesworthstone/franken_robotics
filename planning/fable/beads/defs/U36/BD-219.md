## Background

`sim.estimate` is the read verb an agent calls before it spends compute: what will this run cost in memory and in
time, does it fit this device, and which compute-envelope class does it need. It never runs physics. Two rules
shape it: **every estimate is an interval** (a calibrated interval for time and an exact figure for memory, never
a point for time), and **a job that does not fit is refused before anything is allocated** (`FROB-REF-602`).

The model behind the verb is the performance program's. Its central fact corrects a common assumption: device
memory does not limit the number of worlds. By the byte model a world is about 35 kB (reference quadruped) or
97 kB (reference humanoid), so 8,192 worlds are 0.28 GB and 0.79 GB, 1 to 3% of a 24 GB card. Memory limits
distinct scenes, camera frames and rollout storage; throughput and iteration latency limit worlds.

**Per-world byte model (DESIGN, `f32`).** n is the number of degrees of freedom, C the contact capacity, R the row
capacity.

| Term | Bytes | Q: n = 18, 13 bodies, C = 32, R = 160 | H: n = 35, 30 bodies, C = 64, R = 320 |
|---|---|---|---|
| Kinematic and dynamic cache | 4·(61·bodies + 17·n) | 4,396 | 9,700 |
| Mass matrix, Hessian and factor | 12·n² | 3,888 | 14,700 |
| Dense constraint Jacobian | 4·R·n | 11,520 | 44,800 |
| Row records | 48·R | 7,680 | 15,360 |
| Contact records | 96·C | 3,072 | 6,144 |
| State, warm starts, solver vectors, actuator state | estimate | about 4,000 | about 6,000 |
| **Total** | | **about 35 kB** (34.6 kB before rounding) | **about 97 kB** (96.7 kB) |

These sit inside the ranges of a derived estimate in the source register, 20 to 53 kB and 56 to 180 kB (over row
capacities of 60 to 280 and 125 to 700), and beside an
incumbent's measured 88.4 kB per humanoid world at 8,192 worlds (FACT, to be re-read). Tier: Solid. Rejected
alternatives: estimating memory by trial allocation (it allocates, and fails late); a single bytes-per-world
constant per robot (row capacity, not the robot, decides the bytes: the dense Jacobian is a quarter to a half of
them).

## Scope

This bead is the estimator's verb: it assembles the parts of three component beads (scenes, time, frames) into
one record and one fit test and depends on them; none of them depends on this bead.

DESIGN (split in polish round 1, recorded so that the seed's provenance stays readable). The plan's seed for this
key, "the `sim.estimate` cost and memory model", lists the throughput-rows bead (BD-217) as its dependency and
GATE-SPARK-22 as its done-condition. Both now belong to the gate's capstone N36p1-01, which depends on this bead,
on the four components, on the end-to-end script (N36-32) and on BD-217, and which runs the gate on every device
and records it. Reasons: (1) more than forty beads (the daemon's admission, budgets, the world bank, the fleet
model, the rerun planners, the shard runtime) need the verb and its refusal, not the measured gate, and while
the verb waited on the M2 parity campaign with its optimization pass, every one of them waited too; (2) as
drafted, this bead's acceptance required a gate record that only the script could produce, while the script
depended on this bead. This bead keeps every mechanism the seed names; nothing of the gate is dropped.

In: the memory model built on the per-world byte function (the slab catalogue with the exact state term,
per-bucket terms, learner terms, the live-interval peak, the fixed overhead per fingerprint); the device budget at
admission; the fit test over the whole request and the refusal; the estimate record and the verb, with the
`--workload` argument group attached by calling N36-33's resolver; the embedding of the components' groups in the
record; the hook for the envelope class.

The per-world byte function itself is not written here. There is one in the workspace,
`frob_kernels::estimate::per_world_bytes`, with the five closed-form terms of the table above, the per-coordinate
vector term, both Jacobian layouts and its own tests (the ten exact products of KA-814, the capacity deltas). It
is written by N17a-07, a dependency, because the placement table of `phylum.plan` needs it first and is finished
earlier in the graph; N17a-07 also writes the planning record of device budgets (`DeviceBudget`) and owns the
population placement table and `FROB-REF-740`. This bead builds the estimator in the same module on that
function and that record, replaces the function's planning estimate of the state term with the catalogue's exact
bytes, and asserts that `sim.estimate` and `phylum.plan` print the same bytes for the same shape class. Components, each a dependency: the per-scene model with its slabs,
group and repairs (N36-16); the time model and its conformal interval, with the coverage clause (N36-17); camera
frame buffers with their slabs, group and repairs (N36-19). The compendium's D.9 oracles (N12-49, a dependency)
are the known answers the record's units and scene figures are checked against; they are read, never
regenerated. Out: the Kinesis output groups (N16b-26, the dynamics unit's verb bead, which
depends on this bead); the values of the record's `role` and `preferred_machines` fields (N21c-07, which
depends on this bead; the schema here only declares them); the resolver behind `--workload` (N36-33, a dependency, called here); bytes touched per
world-step in the run receipt (N36-18, the gate's fourth clause; the estimator reads nothing from it); the
end-to-end script and the gate test target that assembles the four clauses into one record per device (N36-32,
which depends on this bead); measuring GATE-SPARK-22 on every device and recording it (N36p1-01, the capstone).
A bead elsewhere that needs the estimator verb depends on this bead; one that needs a single part depends on that
component; one that needs the gate measured depends on N36p1-01.

## Technical approach

**Where the code lives (DESIGN).** The model is `frob_kernels::estimate` (layer 3), because it must use the same
slab catalogue and layout planner that the device arena uses and because nothing may depend on the conformance
crate. The verb is in `frob-verbs`; the gate check is in `frob-conformance`.

**Memory, numbered.**
1. Resolve the request (designs, scene, task, tier, profile, contact law, world count) to shape classes and
   buckets; round each bucket's world count up to a multiple of the execution width (32).
2. For each bucket build the slab catalogue symbolically: the per-world terms of the table, obtained from
   `per_world_bytes` (N17a-07) and never recomputed here, with the state term
   taken from the catalogue (configuration, velocity, anchored position, warm starts, solver vectors, actuator
   state) instead of the table's estimate; the world rows (24 bytes each); model tables (about 192 bytes per link
   per variant); the statistics ring.
3. Add optional terms when requested: PPO rollout storage 4·T·(observations + privileged observations + actions +
   4) bytes per world for a horizon of T steps (24 kB at T = 24 with 48 observations, a 187-ray height scan and 12
   actions, comparable to the physics state); the hard-contact law's R × R operator, 4·R² bytes per world
   (102 kB for Q, 410 kB for H), budgeted separately and by the largest island; policy and optimizer parameters;
   scene memory; camera frame buffers.
4. Run the arena layout planner in plan-only mode: slabs are aligned and packed, and each slab has a **live
   interval** over the stages of the step plan. The memory figure is the peak over stages of the bytes of all
   slabs alive at once (the largest set of slabs alive at once), not the sum of all slabs.
5. Add the device's fixed overhead for this fingerprint (context and compiled kernels), a constant measured once
   per fingerprint digest and re-measured when the digest changes.
6. Report the total as an exact integer with its breakdown by slab class, and the Jacobian layout used (dense, or
   the path table in which a contact row stores only the coordinates on its support path, about R·(6 + depth)
   instead of R·n).

**Device budgets** (one record, `DeviceBudget`, shared with the placement table of N17a-07). On a CUDA card: free memory at admission, read from the hardware fingerprint, less a reserve
(planning figure: 16 to 19 GB usable of 24 GB, an assumption until measured). On the Mac (FACT, measured on this
machine's Metal device and re-read by the fingerprint): the working-set limit is about 222.7 GiB and the largest
single buffer about 167.0 GiB. Consequences (DESIGN): the arena splits its slabs so that none exceeds the largest
buffer; the device budget is the working-set limit less a host reserve, by default 85% of it (about 189 GiB, or
203 GB), because on unified memory the CPU's allocations compete for the same pool.

**Capacity consequences (arithmetic, carried as known answers).** 8,192 worlds of Q are 0.28 GB and of H 0.79 GB.
One RTX 4090 with 16 to 19 GB usable holds about 0.46 to 0.55 M worlds of Q or 0.17 to 0.20 M of H before rollout
storage. The Mac's budget holds about 5.8 M worlds of Q or 2.1 M of H.

**Fit and refusal.** If the peak exceeds the budget of the requested device: `FROB-REF-602` ("the memory estimate
exceeds the device budget at admission"), exit code 6, carrying the fingerprint digest; `observed` = the estimate,
`required` = the budget; ranked repairs: fewer worlds (the largest world count that fits is computed and named), a
smaller capacity, or the Mac. `sim.estimate` itself returns the same finding with `fits: false` and exit code 2;
the refusal is raised by any run verb at admission, before any device allocation. Order at admission (DESIGN):
the fit test comes first, then the compute-envelope check (`FROB-REF-761`, N36-20), then session budgets. Reason:
a job that cannot fit the device is not repaired by approving a larger envelope class, so a job that fails both
is refused with `FROB-REF-602` and its fit repairs, never with 761's "request the class" repair.

**Record (`frob.sim.estimate.out/1`, base groups; Rust type `CostEstimate`, the name the study-plan type sketch
already uses for the estimate a plan carries; its fields are not sketched anywhere else and are defined here).**
`memory {total_bytes, by_class[], per_world_bytes,
worlds_padded, jacobian_layout, budget_bytes, fits, largest_worlds_that_fit}`; `time {lo_s, hi_s, level,
calibrated, stratum}`; `device_seconds {lo, hi}`; `envelope {needed, in_force}`; `fingerprint`. Every figure has
a unit and a source; memory is class `Estimated` labelled exact-by-model, and becomes comparable with a measured
high-water mark through the gate. Inside `memory` three groups are printed apart: `memory.worlds` (this bead),
`memory.scenes` (the value N36-16 returns) and `memory.frames` (the value N36-19 returns); their slabs enter one
catalogue, and the fit test is applied to the live-interval peak over all of them. The `time` group is the
interval N36-17 returns, at its two levels, with no point value. The schema also declares two top-level fields
that this bead does not compute: `role` (one of the seven role tags of the two machines' role table) and
`preferred_machines` (the machines for that role in order of preference), printed beside `envelope`. They are
filled by N21c-07, which depends on this bead and derives them from this record with its `role_of(verb,
resolved_args, estimate)`; until that bead lands the two fields are absent, never empty or guessed (DESIGN:
the role table needs the estimate, so the estimate cannot wait for the role table).

**GATE-SPARK-22** (claim: Known answer; M2; TARGET). `sim.estimate` memory is within 5% of measured high-water
marks at 1, 8, 64 and 256 worlds and at capacity for Q and H on each device; a job that does not fit is refused
before allocation; time estimates fall inside their intervals on at least 90% of held-out runs; bytes touched per
world-step are measured per launch. This bead builds what the first two clauses check: the exact memory figure
with its breakdown by slab class, and the refusal before any allocation, observable through the device's
allocated-bytes counter. The third clause is the time-model bead's (N36-17) and the fourth the bytes-touched
bead's (N36-18). The gate entry (run as `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test
g1_known_answers -- GATE-SPARK-22`) that
assembles the four into one record per device is the script bead's (N36-32), and the measured record on every
device, with capacity points and held-out coverage, is the capstone's (N36p1-01). A record with a clause missing
is not written as measured.

## Acceptance criteria

- [ ] The memory figure is checked against reality before the gate campaign: on `batch-cpu`, and on each device family present on the machine where the bead is closed, for Q and H at 1, 8, 64 and 256 worlds, the estimate's total is within 5% of the arena's measured high-water mark of a run of the same request, and the record prints both with their relative difference. The seed's done-condition, GATE-SPARK-22 recorded as measured on every device and at capacity, is carried by the capstone N36p1-01, which depends on this bead.
- [ ] KA-814, through the record: the breakdown `by_class[]` of the estimate prints the five formula terms exactly (4,396; 3,888; 11,520; 7,680; 3,072 for Q and 9,700; 14,700; 44,800; 15,360; 6,144 for H); totals 34.6 kB and 96.7 kB before rounding with the table's state estimates. Raising the row capacity by one changes the per-world estimate by 4·n + 48 bytes (120 for Q, 188 for H). The terms come from `per_world_bytes` (N17a-07), whose own tests pin the products.
- [ ] One byte model: for the same shape class and Jacobian layout, `sim.estimate` and `phylum.plan` print the same bytes per padded world, and no second byte formula exists in the workspace (test `one_byte_model_two_verbs`).
- [ ] KA-816: 8,192 worlds give 0.28 GB (Q) and 0.79 GB (H); rollout storage is 24,096 bytes per world at the stated sizes; the R × R operator is 102,400 and 409,600 bytes; 16 to 19 GB hold 0.46 to 0.55 M worlds of Q or 0.17 to 0.20 M of H.
- [ ] A request that does not fit is refused with `FROB-REF-602` before any allocation (the device's allocated-bytes counter is unchanged) and names the largest world count that fits.
- [ ] On the Mac no planned slab exceeds the largest single buffer, and the budget is 85% of the working-set limit read from the fingerprint.
- [ ] The verb performs no physics step (the engine's step counter stays at zero) and is reachable through `frob --json` and `frob-mcp` with its schema documented.
- [ ] The estimate prints the envelope class the job needs.
- [ ] The schema `frob.sim.estimate.out/1` declares `role` and `preferred_machines` as optional top-level fields: a record without them validates (this bead's build), and so does one that carries a role tag (a non-empty string in the registry name grammar; which tags exist is N21c-07's table and lint) and an ordered machine list (the form N21c-07 fills); an empty tag, or a machine list without a tag, is a schema fault.
- [ ] The record embeds the components' groups: `memory.scenes` and `memory.frames` apart from `memory.worlds`, and the `time` group at both levels with no point field; the fit test uses the peak over all slabs.
- [ ] Verb-level refusals of the components: one scene per world on 8,192 worlds is refused with the shared-variant repair first and never offers fewer worlds; a two-camera 640 × 480 task at 8,192 worlds on a 24 GB card returns `fits: false` with the repairs fewer worlds, the Mac, a different task with smaller cameras, in that order.
- [ ] `frob sim estimate --workload Q --worlds 8192 --json` resolves through N36-33's resolver (no second parser) and prints the same breakdown as the request typed out in full.
- [ ] `CONTRACT.md` entries exist for the model and the verb (validity domain: the shape classes and backends it was checked on).

## Test plan

### Unit tests

`cargo test -p frob-kernels estimate`:
- The tests of the per-world function (the ten exact products of KA-814 with sums 30,556 and 90,704 before the state term; R + 1 → +120 bytes for Q and +188 for H; C + 1 → +96 bytes; the Jacobian term under the path-table layout) are N17a-07's, where the function is written.
- `breakdown_is_the_function`: the record's `by_class[]` for Q and H equals the fields of `per_world_bytes`, with the state term replaced by the slab catalogue's bytes; `row_capacity_delta_in_record`: R + 1 moves `per_world_bytes` in the record by 120 (Q) and 188 (H).
- `one_byte_model_two_verbs`: for the 18, 36 and 64 buckets of the placement table, the per-world bytes of `sim.estimate` equal those `phylum.plan` prints.
- `worlds_8192_totals` (KA-816): 8,192 × 34,556 = 283 MB; 8,192 × 96,704 = 792 MB.
- `rollout_storage`: 4 × 24 × (48 + 187 + 12 + 4) = 24,096 bytes.
- `hard_contact_operator`: 4 × 160² = 102,400; 4 × 320² = 409,600.
- `card_capacity`: 16·10⁹ ÷ 34,556 = 463,016 worlds; 19·10⁹ ÷ 96,704 = 196,475.
- `mac_budget`: 0.85 × 222.7 GiB = 189.3 GiB = 203.3 GB; ÷ 96,704 = 2.10 M worlds.
- `live_interval_peak_not_sum`: two scratch slabs of 100 MB with disjoint live intervals peak at 100 MB, not 200 MB.
- `slab_split_under_max_buffer`: a 200 GiB slab is planned as two.
- `width_rounding`: 100 worlds → 128.
- `fits_world_budget`: 65,536 humanoid worlds at 97 kB are 6.36 GB and fit a 16 GiB world budget.
- `does_not_fit_names_largest`: world budget 4 GiB, humanoid at 97,000 bytes per world → `largest_worlds_that_fit` = 44,278 (floor of 4·2³⁰ ÷ 97,000), with the count the arena would actually allocate, a multiple of 32, reported beside it as 44,256.
- `no_physics_executed`.
- `fit_precedes_envelope`: 524,288 quadruped worlds (about 18.1 GB) on a 16 GiB device budget under E0 → `FROB-REF-602`
  (exit 6), not `FROB-REF-761`; 100,000 quadruped worlds on two declared devices under E0 (each shard fits) →
  `FROB-REF-761`.
- `path_table_layout_in_record`: the record's `jacobian_layout` and its Jacobian term follow the step plan's layout.
- `estimate_matches_arena_high_water_batch_cpu`: for Q and H at 1, 8, 64 and 256 worlds on `batch-cpu`, the
  estimate's total and the arena's high-water mark of a two-second run of the same request differ by at most 5%
  (the device rows are measured by the capstone).
- `workload_resolves_like_typed_request`: `--workload H` and the typed request give identical records.
- `role_fields_declared_optional`: the schema accepts a record with neither `role` nor `preferred_machines`, and one with `role: "large-memory"` and `preferred_machines: ["mac"]`; it rejects `role: ""` and a `preferred_machines` list without a `role`.
- `agrees_with_compendium_d9` (the oracles of N12-49): the `memory.scenes` group for one dense 10 m × 10 m × 3 m
  interior at 2 cm prints 37,500,000 samples and 75,000,000 bytes; the job shape the verb hands the time model for
  64 worlds and 10 simulated seconds at h = 1/400 s carries 256,000 world-steps (one world-second is 400
  world-steps), and a request stated in env-steps with a control period of 1/50 s is converted at d = 8; a
  record that mixes the two units fails, as the oracle's negative control requires.

### End-to-end script and logging

`scripts/e2e/sim_estimate_gate22.sh` (N36-32, which depends on this bead; its steps `memory`, `capacity`,
`refusal`, `scenes`, `cameras` and `envelope_class` exercise this verb): for Q and H on each device, `frob sim estimate … --json` then
`frob sim run … --key <a key per run> --json` at 1, 8, 64, 256 worlds and at capacity; compares the estimate with the run's measured
high-water mark; provokes the refusal and checks that nothing was allocated. Logged: every term of the breakdown,
budget, estimate, measured mark, relative difference against 0.05, the refusal with its repairs.

### Known answers and negative controls

- KA-814 (negative control: a capacity change must change the estimate by 4·n + 48 bytes per row; a model with the Jacobian term frozen at the default capacity must fail `row_capacity_delta` in N17a-07 and `row_capacity_delta_in_record` here), KA-816, KA-826.
- CX-381 ("device memory limits the number of worlds"): the test `worlds_are_not_the_binding_term` shows 8,192 worlds at 1 to 3% of a 24 GB card while two 640 × 480 cameras on 8,192 worlds need 37.5 GiB and return `fits: false`. Its control is the plant `per-world-bytes-only` of the counterexample registry N36-CX (kind `mutation`), built by this bead: a `cfg` branch of the fit test in `frob_kernels::estimate`, behind the Cargo feature the control's record names (N38b-05) and compiled only under `gauntlet-mutations`, that takes the peak over the `worlds` slabs alone and omits scenes and camera frames. Under it the two-camera request at 8,192 worlds is admitted, and `worlds_are_not_the_binding_term` must fail.
- Negative controls registered against GATE-SPARK-22: an estimator that sums all slabs instead of taking the live-interval peak (over-estimates beyond 5% on a plan with shared scratch); an admission path that allocates before checking the fit (the allocated-bytes counter moves).
- Determinism: the estimate is a pure function of the request, the shape classes and the fingerprint; identical on repeat and across machines for the same fingerprint record.

## Considerations

- OPEN-SPARK-3 owns the capacities of the two reference workloads; a capacity change is a new step-plan identity and a new estimate, and the 5% check is repeated.
- The byte formula of the dynamics chapter, 4·(61·n_b + 17·n + 3·n² + 24·C + R·n + 12·R + 10·n), is this table with part of the state term (10·n floats) made explicit; it gives 31,276 bytes for Q before the remaining state. One implementation serves both: the function of N17a-07 names the two sums `five_terms` (30,556 for Q) and `formula` (31,276), and the Kinesis group of this verb (N16b-26) prints the second from it.
- The "16 to 19 GB usable" figure for a 24 GB card is an assumption; the fingerprint's free-memory reading replaces it, and on a loaded `trj` it can be much less.
- "At capacity" on the Mac is far above the default machine envelope of 16 GiB and needs the gate-measurement class; without it that point of the gate is `not run` with the reason (recorded by the capstone N36p1-01). The verb itself needs no class: it allocates nothing.
- A fleet job carries this estimate's cost interval, and the daemon's admission uses the interval's upper end; an underestimate wastes a whole budget stop, an overestimate costs only a refusal.
- The estimate is only as current as its fingerprint: a driver or compiler change invalidates the fixed-overhead constant and the time calibration, and the verb says `uncalibrated` until they are redone.
