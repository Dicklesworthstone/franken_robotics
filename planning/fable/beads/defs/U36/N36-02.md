## Background

Every throughput target, every incumbent measurement and every parity ratio of the performance program is stated
on one of two **reference workloads**. A target is only comparable across time, machines and simulators if the
workload behind it is the same bytes each time, so the workloads are data with an identity, not prose.

| Workload | Robot | Degrees of freedom | Bodies | Contact capacity C | Row capacity R | Step h | Newton iterations | Decimation d |
|---|---|---|---|---|---|---|---|---|
| Q | Reference quadruped, 12 actuated joints, 16 foot samples, flat and rough ground | 18 | 13 | 32 | 160 | 2 ms | 4, warm-started | 10 (50 Hz control) |
| H | Reference humanoid, 29 actuated joints | 35 | 30 | 64 | 320 | 2 ms | 4, warm-started | 10 (50 Hz control) |

These are DESIGN defaults; the capacities are frozen at M2 by the open question OPEN-SPARK-3. Terms: *degrees of
freedom* counts the six of the floating base plus the actuated joints (6 + 12 and 6 + 29). *Contact capacity* C is
the largest number of simultaneously active contacts a world's buffers hold. *Row capacity* R is the largest number
of constraint rows in the per-world solve. *Decimation* d is the control period divided by h: one control tick is
d physics steps. *Newton iterations* is the fixed number of iterations of the convex contact solve every world
runs in lockstep, warm-started from the previous step. A world that overflows C or R is marked `Degraded` with a
reason; it is never truncated silently.

**Row capacity rule (known answer KA-815).** Four rows per contact (normal, two tangential, spin) plus one limit
row and one stiction or backlash row per actuated joint, rounded up to a multiple of 8: 128 + 12 + 12 = 152 for
Q, already a multiple of 8 and raised to 160 as a registered decision of the reference workload; 256 + 29 + 29 =
314 for H, rounded up to 320. TARGET: fewer than one world-step in 10⁴ is marked `Degraded` for
capacity on the standard battery; otherwise the capacity is raised and every target row is measured again.

Tier: Solid. Rejected alternatives: letting each measurement choose its own robot and capacities (figures stop
being comparable); taking the incumbents' native settings as the definition (incumbents do not share a step or a
decimation; native settings are a second, separately labelled measurement).

## Scope

In: the two workload records and their variants; the row-capacity function; the identity; the loader and its
checks; the matched and native setting records for comparators. Out: the robot models themselves (the model
compiler and import beads); the target rows (N36-01); freezing the capacities (the OPEN-SPARK-3 decision);
restating rows if h changes (N36-26); resolving a workload inside a run verb (the `--workload` selector,
N36-33, which uses this bead's record type and adds no parser).

## Technical approach

**Record (DESIGN name `frob.workload/1`; file `registries/workloads.toml`).**

```toml
[workload.Q]
robot        = "ref-quadruped-12"        # the admitted 12-joint quadruped model, by ModelId once the compiler exists
actuated     = 12
dof          = 18
bodies       = 13
foot_samples = 16                        # collision sample points on the feet
contact_cap  = 32
row_cap      = 160
row_cap_override = { rule = 152, reason = "raised to the next multiple of the execution width 32 (reference-workload decision; OPEN-SPARK-3)" }
h_s          = "1/500"
newton_iterations = 4
warm_start   = true
decimation   = "10/1"                    # 50 Hz control
worlds       = 8192                      # the world count of the single-card rows
grounds      = ["flat", "rough"]
status       = "default"                 # "default" until OPEN-SPARK-3 freezes it, then "frozen" with the ADR reference

[workload.H]
robot = "ref-humanoid-29"; actuated = 29; dof = 35; bodies = 30
contact_cap = 64; row_cap = 320; h_s = "1/500"; newton_iterations = 4; warm_start = true
decimation = "10/1"; worlds = 8192; grounds = ["flat", "heightfield"]; status = "default"
```

**Which robots.** The plan fixes the counts (12 and 29 actuated joints, 13 and 30 bodies) and not the product
names. DESIGN default, stated so that both sides of a matched comparison run the same model: `ref-quadruped-12` is
the 12-joint quadruped the incumbents' own benchmark tasks use, taken from the permissively licensed public model
collection the project already lists as its source of reference robots (BSD-3); `ref-humanoid-29` is the 29-joint
humanoid that the incumbent nightly benchmark reports on and that the sibling simulation suite also ships with
provenance. The choice is recorded in this file and frozen together with the comparator revisions (decision bead
N36-25). Reference robots are parity fixtures and benchmark baselines; they are never the source of a claim about
a physical robot.

**Row-capacity function (`frob_core::perf::workload::row_cap`, beside the record type).**
`row_cap(contact_cap, actuated) = round_up(4·contact_cap + 2·actuated, 8)`: 152 → 152 and 314 → 320. This is the
one row rule of the workspace: the dynamics chapter's capacity table states it ("rounded up to a multiple of 8")
and its six rows confirm it (quadruped 152; hexapod 4·32 + 2·18 = 164 → 168; humanoid 314 → 320; wheeled base
4·16 + 2·4 = 72; wheel-leg quadruped 4·32 + 2·16 = 160; tracked base 4·64 + 2·4 = 264), and the capacity registry
of that chapter (N16a-14, which depends on this bead) applies the same rule, as its `default_rows`, to every
workload and to the per-run `--capacity` override; it is asked to call this function, so that the rule has one
implementation. DESIGN, correcting an earlier draft of this bead that rounded to a granule of 32: that
granule reproduces 160 and 320 and no other row of the table (it would give 192, 96 and 288 for the hexapod, the
wheeled base and the tracked base), so two row rules would have coexisted, and a Q run with a changed contact
capacity would have had one row capacity through this registry and another through `--capacity`.
Q's 160 is therefore not the rule's value. The plan prints 160 for Q and says its 152 rows "are raised to 160"
without a reason; the record carries the raise as `row_cap_override = { rule = 152, reason }`, and the reason
recorded is this bead's reading (DESIGN): 160 is the next multiple of 32, the execution width of both device
families (a CUDA warp and a Metal SIMD-group), so the rows of the workload on which every throughput row is
measured fill whole groups of lanes in the row-parallel stages; H's 320 is already such a multiple. The loader
checks that a stored `row_cap` equals the function's value, or carries a `row_cap_override` whose `rule` equals
the function's value and whose `reason` is not empty, so a capacity cannot drift from the rule silently.

**Identity.** `WorkloadId` = BLAKE3 over the canonical record. It is cited by every disclosure block (through the
scene and model identities once they exist) and by every target row. Changing any field changes the identity,
and a measurement made under an old identity cannot be compared with a target stated on the new one.

**Comparator settings.** For each incumbent arm the registry holds two setting records per workload:
`matched` (the incumbent run at our h, d and iteration count where its solver allows; where it does not, the
nearest admissible setting and the difference, in writing) and `native` (the incumbent's own recommended step for
the task, with its source). Parity is measured twice, once under each, and the native comparison is made in
env-steps/s and in time to a return threshold only. Storage (DESIGN): `[[setting]]` records in this file, one per
comparator name, workload and kind (`matched` | `native`), with `h_s`, `decimation`, the iteration count, and
`source` (native) or `difference` (matched, where the incumbent's solver does not admit our values), each with a
content hash. The comparator registry (BD-039) builds its warm configurations on these records and cites their
hashes in `configurations.matched` and `configurations.native`, so the step settings of a comparison are written
once, here.

**Record type and parser (`frob_core::perf::workload`).** The type `Workload`, its strict parser and `WorkloadId`
live in `frob-core`: run verbs and the estimator resolve workloads, and nothing may depend on the conformance
crate.

**Loader checks (`frob-conformance`, module `perf::workloads`, on top of that parser).** Unknown field → error; `dof = 6 + actuated`;
`row_cap` rule; `decimation` integer for reference workloads; `h_s × decimation` equals the control period
(20 ms); status `frozen` requires an ADR reference.

**Evidence.** Registry data; class `Tested` only in the sense that its checks pass. Nothing here is a measurement.

## Acceptance criteria

- [ ] `registries/workloads.toml` holds Q and H with the values of the table; the registry lint accepts it.
- [ ] KA-815: the Q record holds R = 160 (rule value `row_cap(32, 12)` = 152, raised by its `row_cap_override` with the reason recorded) and the H record R = 320 = `row_cap(64, 29)` (314 rounded up to a multiple of 8); the intermediate sums 152 and 314 are printed.
- [ ] `WorkloadId` is stable across platforms and changes when any field changes.
- [ ] Matched and native setting records exist for each comparator of the parity baseline, each native record with its source.
- [ ] A record with `status = "frozen"` and no ADR reference fails the lint.
- [ ] The loader is used by the parity-baseline script and by the target register; neither restates the numbers.
- [ ] The record type, parser and identity are in `frob-core`; the conformance module adds the lint and holds no second parser.

## Test plan

### Unit tests

`cargo test -p frob-core perf::workload` (the type, the strict parser and the identity, where they live):
- `identity_changes_with_any_field` (property test over single-field edits); `identity_stable_across_platforms`
  (a pinned digest of the canonical Q record, checked on both machines); `unknown_field_refused`.

`cargo test -p frob-conformance perf::workloads` (the lint on top of that parser):
- `row_capacity_known_answer` (KA-815): Q: 4·32 + 12 + 12 = 152, the rule gives 152 and the registered raise
  gives 160; H: 4·64 + 29 + 29 = 314 → 320. The registry's two records hold 160 and 320.
- `row_capacity_per_row_delta`: raising C by 1 raises the unrounded row count by 4.
- `row_capacity_rule_is_multiple_of_8`: the six rows of the dynamics chapter's capacity table: (32, 12) → 152;
  (32, 18) → 164 → 168; (64, 29) → 314 → 320; (16, 4) → 72; (32, 16) → 160; (64, 4) → 264. A granule of 32 would
  give 192, 96 and 288 for the second, fourth and sixth; the test pins the plan's rule.
- `dof_is_six_plus_actuated`: 18 and 35.
- `control_period_is_20ms`: h = 1/500 s × 10 = 1/50 s.
- `override_requires_reason`: a `row_cap` that differs from the rule with no override, with an empty reason, or
  with an override whose `rule` is not the function's value, is rejected; Q's record as committed is accepted.
- `frozen_requires_adr`.
- `native_settings_have_source`.

### End-to-end script and logging

`scripts/e2e/perf_parity_baseline.sh` (N36-29) prints both records with their identities in its `workloads` step
and asserts that every measured row names one of them. Logged: `WorkloadId`, the eight fields, the row-capacity
sum before and after rounding.

### Known answers and negative controls

- KA-815 (exact; tier G1, host).
- Negative controls, each planted in a scratch registry: an H record with `row_cap = 314` (the rounding removed) must fail the rule check; a Q record with its raise removed (`row_cap = 152`, no override) satisfies the rule and must fail `row_capacity_known_answer`, which pins the registered 160.
- Metamorphic: reordering keys in the file does not change the identity.

## Considerations

- OPEN-SPARK-3 (owner: the Spark lead; default: the capacities above and the bucket set {12, 18, 24, 36, 48, 64} for degree-of-freedom capacities; decided by the M2 profile). A change of capacity changes the bytes per world by 4·n + 48 bytes per row (120 bytes per row for Q, 188 for H) and therefore the memory estimate, the bytes touched per step and every throughput row; the rows are re-measured, never rescaled.
- OPEN-PERF-4: if the default physics step moves from 2 ms, h and d here change and every target row is restated before any gate cites it (N36-26).
- The rule (a multiple of 8) is the plan's; the reason recorded for Q's raise to 160 is this bead's reading, and the plan gives none. If the capacity decision changes Q's contact capacity or withdraws the raise, the stored value and its override change together; the function does not.
- Ground variants matter: the humanoid heightfield row is about a third slower than the flat row on an incumbent (1.68 M against 2.55 M world-steps/s), so a figure must name its ground.
