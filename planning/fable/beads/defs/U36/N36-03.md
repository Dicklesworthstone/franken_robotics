## Background

FrankenRobotics treats engine throughput as a **parity requirement**: the engine has to stay inside a stated
tolerance of the strongest incumbent simulator measured on the same hardware, and every speed figure has to be
measured in a way that cannot flatter us. The first way a speed figure flatters its author is by leaving its unit
ambiguous. Simulators quote two different things under the word "steps per second":

- a **world-step**: one physics step of length h of one world (stages 1 to 9 of the batched step: kinematics,
  collision, compaction, dynamics terms, constraint rows, solve, integration; stage 10, sensors and rewards, runs
  only on control ticks);
- an **env-step**: one control tick of one world, which is d world-steps followed by observation, reward and reset
  logic, and which may or may not include policy inference and learning.

d is the **decimation**: the control period divided by h. An env-step count means nothing without the number of
physics steps inside it. FACT (source register, to be re-read from the primary sources before a gate cites it):
incumbents do not share a decimation. One publishes its quadruped task at a control period of 20 ms over a physics
step of 4 ms (d = 5); another reports 1.20 M env-steps/s of physics as 4.8 M physics steps per second (d = 4). The
reference workloads of this project use h = 2 ms and d = 10.

**ADR-PERF-02 (decision).** Two units, world-steps and env-steps, each written with its decimation. Reason: an
env-step count means nothing without the number of physics steps inside it. Rejected alternatives: a single unit
"steps/s" (the ambiguity this bead removes); world-steps only (training and full-step figures are naturally counted
in control ticks, and incumbents publish them that way); a free-text unit string (cannot be checked).

This bead supplies the types and the one check every later performance record depends on. It is at M0 because the
first performance records of the project are the incumbent measurements on `trj` (the Linux host with two RTX 4090
cards), and they must already carry a unit and a decimation. Tier: Solid.

## Scope

In: the unit and rate types; conversions; the definition of a rate; the settings label (matched or native); the
ordering invariant INV-PERF-01 as a pure check; wire form and schema validation of a rate. Out: the disclosure
block that carries rates (N36-13); the campaign runner and timers (BD-216); the paired ratio (N36-06); the target
register (N36-01).

## Technical approach

**Definitions carried in the types.**

| Term | Definition |
|---|---|
| World-step | One physics step of length h of one world |
| Env-step | One control tick of one world: d world-steps, then observation, reward and reset logic. A row says whether policy inference and learning are included |
| Decimation d | Control period ÷ h. An integer for every reference workload. Where a task's rational clocks make it non-integer, the mean number of world-steps per control tick is reported as a reduced rational |
| World-second | One second of simulated time of one world: 1/h world-steps |
| Device-second | One second of one device's wall-clock occupancy, including compilation, admission, transfer and synchronization |
| Rate | Completed work ÷ wall-clock from submission to completion. Steps of worlds marked `Degraded` (a capacity overflowed) or `Faulted` (a non-finite value) are counted separately and are not in the numerator |

**Types (DESIGN; module `frob_core::perf::units`, no dependencies beyond `frob-core`).**

```rust
pub struct Decimation { num: u32, den: u32 }            // reduced; den = 1 for the reference workloads; num ≥ den ≥ 1
pub enum StepScope { PhysicsOnly, FullEnvStep, Training } // what is inside the timed loop
pub struct Inclusion { pub observe_reward_reset: bool, pub policy_inference: bool, pub learning: bool }
pub enum Settings {                                      // how a comparator was configured
    Matched { h: Rational, d: Decimation, newton_iterations: u8 },   // the incumbent run at our h, d and iteration count
    Native  { h: Rational, d: Decimation, source: String },          // each stack at its own recommended step
}
pub enum RateUnit { WorldStepsPerSec, EnvStepsPerSec, WorldSecPerWallSec, EpisodesPerSec, RealTimeMultiple }
pub struct StepCounts { pub valid: u64, pub degraded: u64, pub faulted: u64 }
pub struct Rate {
    value: f64, unit: RateUnit, decimation: Option<Decimation>, h: Option<Rational>,
    scope: StepScope, inclusion: Inclusion, settings: Settings,
    counts: StepCounts, wall_s: f64,                     // submission to completion
}
```

Constructors enforce the rules, so an ill-formed rate cannot exist in memory:
1. `Rate::steps(unit, …)` for `WorldStepsPerSec` or `EnvStepsPerSec` requires a decimation and h; there is no
   constructor without them. `RealTimeMultiple` (used for a single referee world) takes none: no decimation applies.
2. `value = counts.valid ÷ wall_s`; the constructor takes the counts and the interval, never a pre-divided number.
   `degraded` and `faulted` world-steps are stored beside it and never added to `valid`.
3. `scope` and `inclusion` must agree: `PhysicsOnly` has all three flags false; `FullEnvStep` has
   `observe_reward_reset` and nothing else unless stated; `Training` has all three true.

**Conversions (exact rationals on the integer part).** world-steps/s = d × env-steps/s; env-steps/s =
world-steps/s ÷ d; world-seconds per wall-second = world-steps/s × h. Conversion never crosses a `StepScope`: it
changes the unit of one measurement and does not turn a physics-only figure into a full-step figure.

**The ordering invariant INV-PERF-01.** In env-steps/s, for one hardware key (machine, device, world count,
workload, settings): training ≤ full environment step ≤ physics only. `check_ordering(rates) -> Result<(),
OrderingViolation>` converts every step rate of the group to env-steps/s and tests the two inequalities exactly as
reported. The smallest contradiction: 400 k env-steps/s of training at d = 10 is 4.0 M world-steps/s inside
training, and cannot stand beside a physics-only figure of 2.0 M world-steps/s (200 k env-steps/s) on the same
card. The violation names the two rates, both values in both units and the hardware key.

Noise does not excuse a violation. The three rates of a group come from one campaign; if run-to-run spread is
larger than the non-physics overhead, the campaign has not resolved that overhead and its report is rejected, with
the repair "more pairs, or a longer duration".

**Comparability.** `comparable(a, b)` is true only if both are in one unit after conversion and (i) both carry
`Matched` settings with equal h, d and iteration count, or (ii) both are env-steps/s under `Native` settings.
World-steps/s at different decimations are refused as a comparison: a comparison at native settings in world-steps
is a comparison of settings.

**Wire form.** JSON object inside `frob.perf.disclosure/1` (N36-13): `{"value": "…", "unit": "env_steps_per_s",
"decimation": "10/1", "h_s": "1/500", "scope": "training", "inclusion": {…}, "settings": {…}, "counts": {…},
"wall_s": "…"}`. Numbers travel as strings where they exceed the exact range of a double. The wire form is read
with the JSON admission reader of `frob-core` (N34-17; the core has no JSON library). A step rate without
`decimation` fails schema validation with a typed error whose pointer is `rates[i].decimation`. This module
returns typed errors (`RateSchemaError`, `OrderingViolation`) and builds no refusal code; where they reach an
agent they are `FROB-REF-862` (a performance figure without a complete disclosure block; exit code 3), raised by
the disclosure check for a block's rates (N36-13) and by report validation for a report's groups (BD-216): a
missing decimation with pointer `rates[i].decimation` and the repair "restate the figure with its decimation";
an ordering violation as the interim of the held ledger request `rates-violate-unit-ordering` (N36-REF; N35-33
rule 7), with `detail = "rates-violate-unit-ordering"`, pointer `rates.ordering` and a message naming
INV-PERF-01. The slug and the pointer are two named constants of this module (`ORDERING_DETAIL`,
`ORDERING_POINTER`, DESIGN), which both raising sites use, so that the code's assignment changes one line.

**Determinism and evidence.** Pure host arithmetic, class D0 (exact) for conversions on counts; the rate value is
a measurement of class `Tested`. Nothing is written to the ledger by this module.

## Acceptance criteria

- [ ] `frob_core::perf::units` exists with the types above; a step rate cannot be constructed without a decimation (a compile-fail test and a schema test).
- [ ] KA-806: a report with 400 k env-steps/s of training at d = 10 beside 2.0 M world-steps/s of physics on the same card is rejected by `check_ordering`; the same report with the decimation omitted is also rejected (at parse time).
- [ ] `Degraded` and `Faulted` world-steps never enter the numerator: a run with 1,000,000 world-steps of which 300 are `Degraded` reports 999,700 valid steps.
- [ ] A non-integer decimation is carried as a reduced rational and converts exactly.
- [ ] `comparable` refuses world-steps/s at d = 4 against world-steps/s at d = 10 under native settings and accepts the same pair in env-steps/s.
- [ ] The crate's `CONTRACT.md` documents the module (inputs, outputs, invariants, refusals, determinism class D0 for conversions).
- [ ] The checks are library functions that the entries of GATE-SPARK-19 call from M2 (BD-216 registers them in the tier target `g1_known_answers`, run as `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g1_known_answers -- GATE-SPARK-19`); at M0 this bead's own unit tests show both planted reports rejected.

## Test plan

### Unit tests

`cargo test -p frob-core perf::units`:
- `conversion_world_env`: 400,000 env-steps/s at d = 10 → 4,000,000 world-steps/s; 1,200,000 env-steps/s at d = 4 → 4,800,000; 4,800,000 world-steps/s at d = 4 → 1,200,000 env-steps/s.
- `world_seconds`: 1,700,000 world-steps/s at h = 1/500 s → 3,400 world-seconds per wall-second; 275,000 → 550.
- `ordering_known_answer` (KA-806): {training 400 k env-steps/s d = 10; physics 2.0 M world-steps/s d = 10} → `OrderingViolation { training_env: 400000, physics_env: 200000 }`.
- `ordering_accepts_consistent_triple`: 400 k physics, 340 k full step, 280 k training (env-steps/s, d = 10) passes.
- `ordering_rejects_equal_scope_mismatch`: a `FullEnvStep` rate above the physics rate by one step per second is rejected (strict rule, no tolerance).
- `missing_decimation_is_schema_error`: JSON without `decimation`, read through N34-17's reader → `RateSchemaError` with pointer `rates[0].decimation`.
- `ordering_constants`: `ORDERING_DETAIL` is `"rates-violate-unit-ordering"` and `ORDERING_POINTER` is `"rates.ordering"`.
- `rational_decimation`: control period 25 ms over h = 2 ms → 25/2; 400 env-steps/s → 5,000 world-steps/s.
- `numerator_excludes_degraded_and_faulted`.
- `scope_inclusion_agreement`: `PhysicsOnly` with `learning: true` fails to construct.
- `native_world_steps_not_comparable`; `matched_requires_equal_h_d_iterations`.
- Property test (INV-PERF-01; the property runner of STD-TEST's `frob_core::testkit`): for random (physics, overhead ≥ 0, learner ≥ 0) per-step times, the derived triple always passes; swapping any two members fails unless they are equal.

### End-to-end script and logging

No script of its own. `scripts/e2e/perf_parity_baseline.sh` (N36-29) at M0 and `scripts/e2e/perf_harness_gate19.sh`
(N36-30) at M2 assert on every logged `metric` line that a step rate has `unit`, `decimation`, `h_s`, `scope` and
the three step counts, and run the two planted reports of KA-806, logging the rejection with its pointer.

### Known answers and negative controls

- KA-806 (exact; tier G1, host): the 400 k against 2.0 M report is rejected; negative control: the same report with the decimation omitted must also be rejected.
- CX-374: quoting env-steps and world-steps side by side without a decimation; the incumbent pair d = 5 and d = 4 is the fixture of `native_world_steps_not_comparable`. Its control is the plant `units-without-decimation` of the counterexample registry N36-CX (kind `mutation`), built by this bead: a `cfg` branch in `frob_core::perf::units`, behind the Cargo feature the control's record names (N38b-05) and compiled only under `gauntlet-mutations`, in which `comparable` skips its test of decimation and settings. Under it a report quoting env-steps beside world-steps with no common decimation is accepted, and `native_world_steps_not_comparable` must fail.
- Planted defect registered against GATE-SPARK-19: a build whose `check_ordering` compares raw values without converting units accepts the KA-806 report; the gate test must fail on it.
- Determinism lanes: conversions are exact; run twice and in debug and release with identical results.

## Considerations

- OPEN-PERF-4: if the default physics step moves from 2 ms, every stored rate keeps its own h and d, so old records stay interpretable; the target rows are restated by N36-26.
- A rate is completed work: a timer that stops at enqueue would inflate every figure. The timer rule (INV-PERF-02) is enforced where timers live (BD-216); this module only refuses a rate whose interval is not submission-to-completion by type.
- The same confusion exists for rewards and discounts (a penalty of 1 per control step over 10 s totals 500 at 50 Hz and 1,000 at 100 Hz for the same motion); that is the learning chapter's rule and is not handled here.
- Kept deliberately small: types and pure checks only, so that every crate that emits a rate can depend on it.
