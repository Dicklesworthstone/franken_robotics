## Background

Method rule of the performance program: **regressions are test failures against a tolerance band, on the smoke
battery.** Once the engine has been brought inside its parity tolerance, nothing keeps it there except a check
that runs on every change that can move a rate. Without it the usual drift happens: each feature costs one or two
percent, nobody measures, and a year later the engine is at half its tolerance (the pre-mortem entry "throughput
landed far under the parity band and agents stopped waiting").

The lane has to solve one problem a correctness test does not have: timing on a shared, loaded machine is noisy
(`trj`, the Linux host with the two RTX 4090, is often heavily loaded; the Mac throttles with temperature). A
naive "fail if slower than last time" test is either flaky or blind. The lane therefore compares a candidate with
a kept baseline **in pairs**, with the same estimator the rest of the program uses, and fails only on a confident
regression. Memory is different: allocated bytes are exact, so any increase is caught exactly.

Tier: Solid. Rejected alternatives: absolute thresholds per row (they encode one machine on one day); a
dashboard with no failing test (drift is seen and tolerated); running the full parity rows on every change (too
long for the default compute envelope).

## Scope

In: the smoke row set; the kept baseline; the band and its tests; the memory check; the unexplained-speedup flag;
the lane as a test target. Out: the full parity rows and gates (BD-217); the optimization ledger (N36-07); the
estimator (N36-06); defining the `smoke` battery's scenarios (the task chapter).

## Technical approach

**Smoke rows (DESIGN; each fits the default compute envelope: one device, under an hour in total).**

| Smoke row | Tier and size | What is recorded |
|---|---|---|
| S1 | Reference quadruped workload, physics only, `batch-cpu`, 8 threads, 256 and 8,192 worlds | Primary rate, 99th-percentile step time, peak memory |
| S2 | The same, full environment step | The same |
| S3 | Reference humanoid workload, physics only, `batch-cpu`, 8 threads, 256 worlds | The same |
| S4 | Quadruped physics, each available device, 8,192 worlds | The same, plus bytes touched per world-step |
| S5 | Humanoid physics, each available device, 8,192 worlds | The same |
| S6 | Edit to first step on the warm path, each available device | 50th and 95th percentile latency |
| S7 | The `smoke` battery of the task chapter, one pass on `batch-cpu` | Wall time and valid world-steps |

**Baseline.** For each machine fingerprint the lane keeps the baseline build (binary and kernel cache entry,
content-addressed) and its recorded figures. The baseline advances only when a change lands with an optimization
ledger entry or with an accepted, explained cost (below).

**The band, numbered.**
1. For each smoke row run a paired campaign, candidate against the kept baseline binary, at least ten pairs,
   short runs (DESIGN: 2 s per arm on `batch-cpu`, 5 s on devices).
2. Regression: the one-sided 95% upper bound of candidate ÷ baseline is below 1 − b, with band b = 0.03 (TARGET;
   the mirror of the 1.03 an optimization must show). Computed as 1/L of the swapped campaign, where L is the
   paired lower bound of baseline ÷ candidate. The test fails and prints the row, the bound and both disclosure
   block identifiers.
3. Unexplained speedup: the paired lower bound of candidate ÷ baseline is above 1 + b and no optimization ledger
   entry cites the change. The test fails with `unexplained-speedup`: a gain nobody claimed is a semantics change
   until shown otherwise (RISK-45).
4. Inconclusive: neither bound crosses its limit. The test passes and records the interval; inconclusive is not
   stored as "no change".
5. Memory: peak allocated device bytes and host bytes of the candidate must equal the baseline's exactly for the
   same workload and capacities; any difference fails with the slab that changed, unless the change set declares
   it.
6. Latency rows (S6): compared on the 95th percentile with the same paired rule on the times.

**Accepting a cost.** A feature may legitimately cost throughput. Then the change carries a `perf-cost` note with
the row, the measured bound and the reason; the lane passes with the note, the baseline advances, and the note is
listed in the next exit review. A cost that takes a parity row below its tolerance cannot be accepted this way: it
re-opens that row's gate.

**When it runs.** As `cargo test -p frob-conformance --test g1 -- perf_regression` on every change that touches
kernels, backends, the step plan, the arena, sensors on the step path or the learner; nightly on each machine for
the device rows. It never runs concurrently with another timing job on the same machine.

**Evidence.** Lane results are class `Tested` diagnostics; they are not Performance claims and are not cited as
such (their runs are short). Each run stores its pairs records.

## Acceptance criteria

- [ ] The lane exists as a test target and runs S1 to S3 and S7 inside the default envelope on either machine, and S4 to S6 where a device is present.
- [ ] A planted 5% slowdown in one kernel (a redundant pass over a buffer) fails the lane on the affected rows and names them.
- [ ] A planted 5% speedup obtained by skipping work (a masked lane dropped) fails with `unexplained-speedup`.
- [ ] An A/A run (candidate identical to baseline) passes on at least 95 of 100 trials on `batch-cpu`.
- [ ] A change that adds one slab fails the memory check with the slab's name; the same change with a declaration passes.
- [ ] A `perf-cost` note advances the baseline and is listed; a cost that drops a parity row below tolerance is refused.
- [ ] Each failure message contains the row, the bound, the band, the pair count and both block identifiers.

## Test plan

### Unit tests

`cargo test -p frob-conformance perf::regression`:
- `band_decisions`: upper bound 0.96 → regression; 0.98 → inconclusive; lower bound 1.04 with no ledger entry → `unexplained-speedup`; lower bound 1.04 with an entry → pass.
- `upper_bound_is_inverse_of_swapped_lower_bound`.
- `memory_exact_compare`: 1 byte more → fail; declared → pass.
- `baseline_advances_only_with_entry_or_note`.
- `cost_below_tolerance_refused`: a note that would put target row 1 under 0.67 of the incumbent is rejected.
- `inconclusive_is_recorded_as_interval`.
- `no_concurrent_timing_jobs`: the lane takes a machine-wide advisory lock and refuses to start under contention.

### End-to-end script and logging

`scripts/e2e/perf_harness_gate19.sh` (N36-30), step `regression_lane`: builds the two planted variants (the slow
kernel and the skipped lane) behind test-only features, runs the lane against each and against an identical
build, and asserts fail, fail and pass. Logged per row: pairs, both bounds against 1 ± 0.03, memory before and
after, the verdict.

### Known answers and negative controls

- Negative controls are the lane's own acceptance: the planted slowdown, the planted work-skipping speedup, the extra slab.
- A/A control: identical builds must not fail (the false-alarm rate is bounded by the 95% level per row; with seven rows the lane reports the per-row levels so that a multi-row false alarm is recognizable).
- Metamorphic: scaling both arms' durations by two leaves the verdict unchanged on a quiet host.

## Considerations

- RISK-09: the lane is where host noise would otherwise turn into flaky tests; pairing and the inconclusive outcome are the answer, and the standing A/A count of the harness gate tells when a machine has become too noisy to judge.
- The band b = 0.03 is a TARGET and is revisited after the first month of lane history: if A/A spread on `trj` is wider than the band can resolve in ten pairs, the lane uses more pairs, never a wider band chosen after a failure.
- Short runs over-weight fixed costs; that is acceptable for detecting change and is the reason lane figures are never cited as rates.
- Under the default compute envelope the device rows run one device at a time; nothing here needs a larger class.
