## Background

FACT (`frankensim/AGENTS.md`, rule 1.1, adopted by this workspace): no run on any host uses more than 16 GiB of
memory, 8 cores or one hour of wall time without the owner's written approval given before it starts; builds and
tests count; a run longer than a few minutes starts under a timeout; when an agent stops, its jobs stop. The
project's open question OPEN-SPARK-2 asks the owner for a compute envelope beyond that. Its fail-closed default is
that FrankenRobotics inherits the rule for CPU work and limits a GPU job to **one device and one hour** until the
owner approves an envelope.

**What the default cannot run, by arithmetic.**

- One device-hour at 50 to 500 k env-steps/s is 0.18 to 1.8·10⁹ env-steps.
- The performance gates themselves: the humanoid CPU row uses 24 threads, the strong- and weak-scaling rows use
  two devices, and the world bank holds far more than 16 GiB.
- The rank-agreement experiment between evaluation rungs needs about forty per-design trainings: about 45
  device-hours, or, where specialists are reused, 5 to 7.5 device-hours.
- Pretraining of a family policy at published sizes (FACT, source register): 1.6·10⁹ steps are 0.9 to 9
  device-hours; 5·10⁹ are 2.8 to 28; 2·10¹² are 1,100 to 11,000, which is 23 to 230 days on two cards and is not
  planned in any envelope.

**The proposal to the owner** (OPEN; nothing above E0 runs until it is ratified or amended):

| Class | Scope | Proposed limits |
|---|---|---|
| E0 | Default | 16 GiB, 8 cores, 1 hour, one device |
| E1 | A named gate measurement | Both machines, all cores, memory up to the device budget, 2 hours per run, 12 device-hours per gate |
| E2 | A design campaign | 48 device-hours |
| E3 | Pretraining of one family policy | 500 device-hours, approved per run with its ceiling and kill rule written first |

The estimator prints the class a job needs, and a job above the class in force is refused before it starts
(`FROB-REF-761`). The owner decision and its registry are another unit's bead; this bead is the machinery that
makes the class in force bind every run: a meter that knows how many device-hours a gate or a campaign has
already consumed, and an admission check on every path that starts work. Tier: Solid. Rejected alternatives:
relying on agents to remember the rule (the rule is violated the first time a campaign is resumed by a fresh
session); checking only single-run limits (the cumulative limits per gate and per campaign are the ones that
matter for E1 to E3).

## Scope

In: the resource vector of a job; the device-hour meter; the admission check and its refusal; the timeout rule;
the hook used by out-of-process runs (incumbent arms); the printing of the needed class. Out: the registry, the
decision packet and the needed-class function's definition (N21c-35); the cost and memory model that produces the
estimate (BD-219); the daemon's own budgets and size classes.

## Technical approach

**Resource vector (DESIGN, `frob_core::envelope::Demand`).** `memory_bytes` (the estimate's exact memory figure,
or a declared bound for an out-of-process run), `cores`, `devices` (count and which), `wall_s_upper` (the upper
end of the time interval; a point estimate is never used), `device_s_upper` = devices × wall_s_upper, `scope`
(`gate:<id>`, `campaign:<id>`, `pretrain:<run>` or `adhoc`), `machine`.

**Needed class.** The smallest class whose limits contain the demand, given the scope's consumption so far:
E0 if memory ≤ 16 GiB, cores ≤ 8, devices ≤ 1 and wall ≤ 1 h; else E1 if the scope is a named gate, wall ≤ 2 h per
run and consumed + device_s_upper ≤ 12 device-hours for that gate; else E2 if the scope is a campaign and consumed
+ device_s_upper ≤ 48 device-hours; else E3 if the scope is one pretraining run, consumed + device_s_upper ≤ 500
device-hours, and the run's approval record carries its ceiling and kill rule; otherwise `above every class`. The
proposal gives no per-run wall limit, core limit or memory limit for E2 and E3; until the owner states them the
fail-closed reading is that they inherit E1's (2 hours per run, memory up to the device budget), since long work
is chunked and resumable.

**The meter (`frob-verbs`, table `envelope_meter` in the ledger).** One append-only row per finished or stopped
run: scope, job identity, machine, devices, device-seconds of occupancy (wall-clock from submission to completion
per device, including compilation, admission, transfer and synchronization), core-seconds, peak memory, outcome.
A refused job writes nothing. A cancelled or failed job writes what it used. `consumed(scope)` is the sum; it is
never reset, and a re-measurement of a gate adds to the same scope unless a new approval is recorded.

**Admission, numbered.**
1. Build the demand from the estimate (or the declaration, for out-of-process runs).
2. Read the class in force from the registry (E0 when no approval is on record).
3. Compute the needed class with `consumed(scope)`.
4. If needed > in force: refuse before any allocation or launch with `FROB-REF-761` ("a job exceeds the compute
   envelope in force"; exit code 4; `retry: after-change`; `observed` = the demand, `required` = the limits of the
   class in force; ranked repairs: a smaller job that fits, with the largest world count, thread count or duration
   that does; split into runs under the per-run limit; request the named class from the owner). A campaign-class
   job of the daemon with no approved envelope keeps its own refusal `FROB-REF-704`.
5. If admitted: start the run under a timeout equal to the class's per-run wall limit; at the timeout the run is
   cancelled by request, drain and finalize, publishes nothing partial as a result, and its use is metered.
6. A gate whose measurement needs an unapproved class is recorded `not run` with the reason "OPEN-SPARK-2: class
   E<n> not approved", never `fail` and never `pass`.

**Where the check sits.** In the one function through which `frob-verbs` starts any run verb or job
(`admit_run`), so that the CLI, the MCP server and the daemon cannot differ; and exported as
`frob_core::envelope::admit` for the conformance campaign runner, which calls it before launching any arm,
including out-of-process incumbent runs, with a declared demand.

**Evidence.** Refusals and meter rows are ledger records; the meter's totals are exact sums of receipts.

## Acceptance criteria

- [ ] With no approval on record: a two-device job, a 24-thread job, a job with an upper wall estimate of 70 minutes and a 20 GiB job are each refused with `FROB-REF-761` before any device allocation, each naming the limit crossed and the class needed (E1).
- [ ] A one-device job with an upper estimate of 50 minutes and 8 GiB is admitted and runs under a one-hour timeout.
- [ ] With E1 approved in a scratch registry for `gate:GATE-SPARK-21`: runs are admitted until the gate's meter reaches 12 device-hours; the run that would cross it is refused, and the refusal prints the remaining budget.
- [ ] KA-823: the arithmetic helpers reproduce 0.18 to 1.8·10⁹ env-steps per device-hour; 0.9 to 9, 2.8 to 28 and 1,100 to 11,000 device-hours for 1.6·10⁹, 5·10⁹ and 2·10¹² steps; 23 to 230 days on two cards.
- [ ] An E3 run without a written ceiling and kill rule is refused even when E3 is approved in general.
- [ ] A run stopped by its timeout publishes no result and appears in the meter with its device-seconds.
- [ ] The conformance campaign runner cannot launch an arm, ours or an incumbent's, without passing `admit`: its launch function takes an `Admitted` token that only `admit` constructs, and a compile-fail test shows that a launch without the token does not build.
- [ ] `CONTRACT.md` of `frob-verbs` lists `FROB-REF-761` with its trigger and repairs.

## Test plan

### Unit tests

`cargo test -p frob-core envelope` and `cargo test -p frob-verbs envelope_meter`:
- `needed_class_cases`: (8 GiB, 8 cores, 1 device, 50 min, adhoc) → E0; (2 devices, 90 min, gate) → E1; (24 cores, 30 min, gate) → E1; (1 device, 70 min, adhoc) → above E0 with no scope that admits it (refused); (30 device-hours, campaign) → E2; (300 device-hours, pretrain with ceiling and kill rule) → E3; (600 device-hours) → above every class.
- `upper_end_not_point`: point 50 min, upper end 70 min → refused under E0.
- `cumulative_limit_e1`: consumed 11.5 device-hours, demand 1.0 → refused; demand 0.4 → admitted.
- `meter_counts_cancelled_and_failed`; `meter_ignores_refused`; `meter_is_append_only`.
- `device_hour_arithmetic` (KA-823): 50,000 × 3,600 = 1.8·10⁸; 500,000 × 3,600 = 1.8·10⁹; 1.6·10⁹ ÷ 1.8·10⁹ = 0.89 h and ÷ 1.8·10⁸ = 8.9 h; 5·10⁹ → 2.78 and 27.8 h; 2·10¹² → 1,111 and 11,111 h; ÷ 2 cards ÷ 24 = 23.1 and 231 days.
- `timeout_equals_per_run_limit`; `timeout_publishes_nothing`.
- `not_run_reason_text`.

### End-to-end script and logging

`scripts/e2e/perf_envelope_meter.sh` (owned by this bead; sources the shared end-to-end helper; seed-explicit and
idempotent; uses scratch registries and `synthetic` job specifications so that no refused job spends device time):
runs `frob sim run @fixture:envelope-two-device --json`, `frob sim run @fixture:envelope-24-threads --json` and a
70-minute fixture under the default registry, then under a registry with E1 approved for a named gate, then with
the meter pre-loaded to 11.5 device-hours. Asserts refusal code, exit code 4, pointer, the class needed and the
remaining budget. Each NDJSON line has `ts`, `script`, `bead`, `step`, `event`, the command line, exit code, wall
time, the evidence block, the demand vector with units, the class in force and needed, the meter total before and
after, and on failure the first differing field. A `summary` line counts assertions.

### Known answers and negative controls

- KA-823 (the envelope arithmetic; the refusal is exact).
- Negative controls: an admission path that uses the point estimate (must fail `upper_end_not_point`); a meter that resets on a new session (must fail `cumulative_limit_e1` when the test opens a fresh session between runs); a gate recorder that writes `fail` for an unapproved class.
- Determinism: admission is a pure function of the demand, the registry and the meter; the same inputs give the same verdict on both machines.

## Considerations

- RISK-10 (no compute envelope is approved, so the performance gates, the rank-agreement experiment and pretraining cannot run as specified; likelihood high; early sign: the question still at E0 when M1 opens). Mitigation built in here: every refusal names the class to request, and every gate records `not run` with that reason, so the cost of the default is visible in the exit review.
- The envelope is a ceiling on spend, not a schedule. Host load on `trj` and thermal state on the Mac change how much work a device-hour buys; the meter counts device-hours regardless.
- Out-of-process incumbent runs declare their demand; a declaration that proves too small is caught by the timeout and by the measured peak memory in the meter, and the next admission for that scope uses the measured values.
- Builds and tests count toward the machine rule; cargo already runs through the build-offload shim, which is outside this meter.
