## Background

FACT (`frankensim/AGENTS.md`, rule 1.1, adopted by this workspace): no run on any host uses more than 16 GiB of
memory, 8 cores or one hour of wall time without the owner's written approval given before it starts; builds and
tests count; a run longer than a few minutes starts under a timeout; when an agent stops, its jobs stop. The
project's open question OPEN-SPARK-2 asks the owner for a compute envelope beyond that. Its fail-closed default is
that FrankenRobotics inherits the rule for CPU work and limits a GPU job to **one device and one hour** until the
owner approves an envelope.

**What the default cannot run, by arithmetic.**

- One device-hour at 50 to 500 k env-steps/s is 0.18 to 1.8·10⁹ env-steps.
- The performance gates themselves: the humanoid CPU row uses 24 threads, the strong- and weak-scaling rows use
  two devices, and the world bank holds far more than 16 GiB.
- The rank-agreement experiment between evaluation rungs needs about forty per-design trainings: about 45
  device-hours, or, where specialists are reused, 5 to 7.5 device-hours.
- Pretraining of a family policy at published sizes (FACT, source register): 1.6·10⁹ steps are 0.9 to 9
  device-hours; 5·10⁹ are 2.8 to 28; 2·10¹² are 1,100 to 11,000, which is 23 to 230 days on two cards and is not
  planned in any envelope.

**The proposal to the owner** (OPEN; nothing above E0 runs until it is ratified or amended):

| Class | Scope | Proposed limits |
|---|---|---|
| E0 | Default | 16 GiB, 8 cores, 1 hour, one device |
| E1 | A named gate measurement | Both machines, all cores, memory up to the device budget, 2 hours per run, 12 device-hours per gate |
| E2 | A design campaign | 48 device-hours |
| E3 | Pretraining of one family policy | 500 device-hours, approved per run with its ceiling and kill rule written first |

The estimator prints the class a job needs, and a job above the class in force is refused before it starts
(`FROB-REF-761`). The owner decision and its registry are another unit's bead; this bead is the machinery that
makes the class in force bind every run: a meter that knows how many device-hours a gate or a campaign has
already consumed, and an admission check on every path that starts work. Tier: Solid. Rejected alternatives:
relying on agents to remember the rule (the rule is violated the first time a campaign is resumed by a fresh
session); checking only single-run limits (the cumulative limits per gate and per campaign are the ones that
matter for E1 to E3).

## Scope

In: enforcement of the compute envelope by the verbs, in one place. That is: the resource vector of a job
(`Demand`); the needed-class computation, the one such function in the workspace, with consumption so far per
scope; the device-hour meter; the admission check `admit_run` / `admit` and refusal `FROB-REF-761` with its
payload and repairs; the timeout rule; the `Admitted` token, its settlement `settle` and the hook used by
out-of-process runs (incumbent arms, pilots on incumbent stacks); the scratch-root hold applied at admission
(N32ax-03's `scratch_hold`, called); the printing of the needed class by the estimate; the rule for which of the two envelope refusal codes
fires where; where a demand's scope comes from, and the envelope token a launcher passes to a child run verb;
the slot in which the device-fit test runs before the class decision; the out-of-process launch function `run_admitted` and its command `frob-launch` (in
`frob-conformance`); the envelope arithmetic as the tested known answer KA-823; every test of the 761 refusal.

Out, with the bead that has it:
- The record `registries/compute_envelope.toml` (its schema, loader and lint), the class tables, the function
  `class_in_force` and the decision packet on OPEN-SPARK-2 are N21c-35. This bead depends on it, reads the
  record only through its loader and never writes it.
- The per-package request rows of that record, the owner's rulings on them and the not-approved fallbacks are
  N44-01; the end-to-end test of every row's refusal and fallback is N44-02.
- The script guard `scripts/lib/envelope.sh` for heavy lanes that run outside the verbs (builds, tests, shell
  lanes) is N34-15. It reads the same request rows and enforces the per-run limits of the class in force; it has
  no meter, so the cumulative limits (device-hours per gate, per campaign, per pretraining run) are enforced
  only here.
- The cost and memory model that produces the estimate, with the device-fit test and `FROB-REF-602`, which
  admission applies before the envelope check (BD-219); session budgets, reservation and settlement
  (`FROB-REF-701`, `-702`; N32a-15), which admission applies after the envelope check; the daemon's size
  classes, its classifier's and scheduler's `FROB-REF-704`, its admission guard and `FROB-REF-703` (BD-296).

## Technical approach

**Resource vector (DESIGN, `frob_core::envelope::Demand`).** `memory_bytes` (the estimate's exact memory figure,
or a declared bound for an out-of-process run), `cores`, `devices` (count and which), `wall_s_upper` (the upper
end of the time interval; a point estimate is never used), `device_s_upper` = devices × wall_s_upper, `scope`
(`gate:<id>`, `campaign:<id>`, `pretrain:<run>` or `adhoc`), `machine`.

**Needed class (`frob_core::envelope::needed_class(demand, consumed, registry)`; the one definition, also the
one `sim.estimate` prints).** The smallest class whose limits contain the job's estimated memory, cores, devices,
wall time (the interval's upper end) and cumulative device-hours for its gate or campaign, given the scope's
consumption so far. With the proposed limits (read from the class tables of the registry, never hard-coded
except E0):
E0 if memory ≤ 16 GiB, cores ≤ 8, devices ≤ 1 and wall ≤ 1 h; else E1 if the scope is a named gate, wall ≤ 2 h per
run and consumed + device_s_upper ≤ 12 device-hours for that gate; else E2 if the scope is a campaign and consumed
+ device_s_upper ≤ 48 device-hours; else E3 if the scope is one pretraining run, consumed + device_s_upper ≤ 500
device-hours, and the run's approval record carries its ceiling and kill rule; otherwise `above every class`. The
proposal gives no per-run wall limit, core limit or memory limit for E2 and E3; until the owner states them the
fail-closed reading is that they inherit E1's (2 hours per run, memory up to the device budget), since long work
is chunked and resumable.

**The meter (`frob-verbs`, table `envelope_meter` in the ledger).** One append-only row per finished or stopped
run: scope, job identity, machine, devices, `started` (the UTC instant at which the run started; the lifecycle
check of N41-17, rule 7, requires the approving request row's date to be no later than it), device-seconds of
occupancy (wall-clock from submission to completion
per device, including compilation, admission, transfer and synchronization), core-seconds, peak memory, outcome.
A refused job writes nothing. A cancelled or failed job writes what it used. `consumed(scope)` is the sum; it is
never reset, and a re-measurement of a gate adds to the same scope unless a new approval is recorded.

**Order at admission (DESIGN, stated identically in BD-219 and in the registry N36-REF).** The device-fit test
runs first (`FROB-REF-602`, BD-219), then this envelope check (for a job the daemon queues, after the daemon's
size classifier, below), then session budgets (`FROB-REF-701`, N32a-15). Reason for the first: a job that does
not fit the device is not repaired by approving a larger class, so a job that fails both tests is refused with
602 and its fit repairs, never with 761 and its "request the class" repair. Reason for the last: the envelope
bounds any single job whatever the session budget. The fit test is BD-219's and lands at M2, after this bead:
`admit_run` therefore has one slot, run before the class decision, in which a fit check is registered; it is
empty until BD-219 registers its test there, this bead tests the order with a `synthetic` check in the slot, and
BD-219's `fit_precedes_envelope` asserts it on the real one. `admit`, used by launchers of out-of-process work,
has no such slot: a declared demand has no slab catalogue to test.

**Admission, numbered.**
1. Build the demand from the estimate (or the declaration, for out-of-process runs).
2. Read the class in force for the demand's scope with `class_in_force(scope, registry, today)` (N21c-35): the
   class and limits of the approved, unexpired request row that admits the scope and whose class is ratified;
   E0 when no such row is on record, when the scope is `adhoc`, or when the registry cannot be read. For a
   `pretrain:<run>` scope the row is the per-run approval and must carry its ceiling and kill rule.
3. Compute the needed class with `consumed(scope)`.
4. If needed > in force: refuse before any allocation or launch with `FROB-REF-761` ("a job exceeds the compute
   envelope in force"; exit code 4; `retry: after-change`; `pointer` the limit crossed (`memory`, `cores`,
   `devices`, `wall` or `device_hours`); `observed` = the demand and the class needed, `required` = the class in
   force with its limits). The ranked repairs are the four of the registry row of N35-REF, in its order (a test
   reads them from the row): (1) a smaller job that fits, with the largest world count, thread count or duration
   that does; (2) split into runs that each fit under the per-run limit; (3) request approval of the class
   printed from the owner, with its ceiling and kill rule written first, naming the request row of the registry
   that would admit the scope when one exists; (4) take the registered not-approved fallback of the work package
   (the `not_approved_fallback` of that request row, printed when the row exists).
5. Under a scratch registries root (N32ax-03: root kind `override`, used by tests to approve a class without the
   owner), steps 2 to 4 decide from the scratch registry, but execution stays bounded by the record: after an
   admitting decision, `frob_core::registries::scratch_hold(needed, in_force_of_record, root_kind)` (N32ax-03) is
   applied, and when it returns a hold (the class needed exceeds the class in force of record) the job is never
   started. From M1, when the job ledger and its admission transaction exist, the job is admitted with
   `hold: scratch-approval`: no device allocation, no world stepped, until it is cancelled. At M0, with no job to
   hold, the run is not started and its envelope is refused with `FROB-REF-761`, whose payload adds
   `scratch_verdict: "admitted"`, so a test still observes what the scratch approval decided. A job whose needed
   class is within the class of record starts normally under either root.
6. If admitted and not held: start the run under a timeout equal to the class's per-run wall limit; at the
   timeout the run is cancelled by request, drain and finalize, publishes nothing partial as a result, and its use
   is metered.
7. A gate whose measurement needs an unapproved class is recorded `not run` with the reason "OPEN-SPARK-2: class
   E<n> not approved", never `fail` and never `pass`.

**Work launched outside the verbs.** Every launcher of out-of-process work obtains an `Admitted` token from
`frob_core::envelope::admit` with a declared demand and the scope of its envelope request row, and settles it
with `settle(token, usage)`, which returns the meter row (device-seconds per device, core-seconds, peak memory,
outcome) that the launcher appends to the `envelope_meter` table through the ledger, on completion, cancellation
or failure alike. This covers the conformance campaign runner's incumbent arms and the pilots run on incumbent
stacks outside the verbs (the learning pilots N23b-20 inheritance, N23b-21 distillation, N23b-22 equivariance,
N23b-36 short-horizon gradients and BD-324 alternative algorithms, admitted under envelope request rows R13 to
R17 of N44-01): their device-hours count against the same scope as runs made
through `frob`, so a cumulative limit cannot be escaped by launching around the verbs. A token not settled within
its class's per-run wall limit plus a grace of 10 minutes is settled by the meter itself at that limit, with
outcome `unsettled`, so an abandoned launcher still consumes its budget.

**The launch function and its command (DESIGN).** Out-of-process work is started by one function,
`frob_conformance::launch::run_admitted(token: Admitted, cmd: Command, limits: RunLimits) -> Settlement`, which
is the only way this workspace starts a non-`frob` process that spends envelope resources; the campaign runner
(BD-216, M2) calls it for every arm, ours or an incumbent's. A launcher that is a shell or Python program (the
incumbent parity baseline script N36-29 at M0; every pilot on an incumbent stack listed above) cannot construct a
token, so the function is also exposed as a command, the binary `frob-launch` of `frob-conformance`:

```
frob-launch --scope <gate:…|campaign:…|pretrain:…|adhoc> [--request <ROW-ID>] --devices <n> [--device-ids <list>]
            --cores <c> --mem-gib <g> --wall-s <s> [--registries-root <dir>] [--json] -- CMD…
```

1. Build the declared `Demand` from the flags (`wall_s_upper` = `--wall-s`) and call `admit`. A refusal prints the
   `FROB-REF-761` envelope and exits 4 without starting anything; a scratch-held decision (step 5 of admission)
   exits 4 with `scratch_verdict: "admitted"` and starts nothing.
2. Start CMD in its own process group under the class's per-run wall limit, with the same limits and the same
   termination rule as the script guard of N34-15 (an address-space limit where the platform honours it, else
   resident memory sampled every second; the whole group terminated on timeout, on a limit breach, or when
   `frob-launch` itself is signalled). On `trj` the child's environment sets `CUDA_VISIBLE_DEVICES` to the
   declared ids, so an arm cannot occupy a card it did not declare.
3. Measure the usage: device-seconds = (number of declared devices) × (wall time from start to the exit of the
   group), the meter's occupancy definition; core-seconds from the group's resource usage; peak resident memory
   from the sampling.
4. `settle` with outcome `completed`, `failed` (non-zero exit), `timed-out`, `limit-breach` or `cancelled`; the
   meter row is appended through the ledger; one JSON line (the row, with the token's id) is printed; the exit code
   is the child's, or 4 for a refusal, or the guard's breach code.

A pilot or baseline lane runs every arm through `frob-launch` under its envelope request row, and its record cites
the meter rows of its arms; an arm started any other way is not metered and is not evidence. The script guard of
N34-15 is for builds, tests and lanes that spend no device time above E0; it has no meter, so a lane above E0 uses
`frob-launch` or a `frob` run verb.

**Where a demand's scope comes from (DESIGN).** A launcher states it (`frob-launch --scope`; the campaign
runner's declaration). A run verb has no scope input: the common inputs the verb registry gives every `run` verb
are the idempotency key, the budget, the synchronous wait, `--estimate` and `on_cancel`. The demand of a run verb
takes, in this order: the scope of an envelope token it was started under (next paragraph); a scope the verb's
own bead derives from its inputs (`train.family` builds `pretrain:<run>` from its `--approval`, BD-320 and
N23b-24); otherwise `adhoc`, for which the class in force is always E0. A gate measurement or a campaign above
E0 that runs `frob` verbs is therefore started by the campaign runner (BD-216) or as the child of `frob-launch
--scope … [--request <ROW-ID>] -- frob …`; the same command started directly is refused with `FROB-REF-761`.

**The envelope token reaches the child (DESIGN; the child-side half of the one-meter-row rule of BD-216).**
`run_admitted` exports the token to its child's environment as `FROB_ENVELOPE_TOKEN=<token id>`, and the child's
own children inherit it. A `frob` run verb started with the variable set passes the token id with its request
(so that the rule holds whether the verb runs in process or hands the job to the daemon), and `admit_run` looks
the token up in the ledger:
1. The token is valid (issued by `admit`, not settled, inside its per-run wall limit) and its declared demand
   contains the verb's own demand (memory, cores, the devices by id, and the upper end of the wall estimate
   within the time the token has left): the verb adopts the token's scope and class, makes no class decision of
   its own and writes no meter row. The launcher's settlement is the arm's only row, and it already counts the
   child's occupancy.
2. The token is valid and the verb's demand is not contained in it (the declaration was too small): the verb is
   refused with `FROB-REF-761`, `pointer` the limit of the declaration that was crossed, `required` the token's
   declared demand. Nothing is started, and the launcher settles what it used.
3. The token is unknown, settled or expired: it is ignored, the envelope carries the warning `envelope-token:
   invalid`, and the verb decides under its own scope as if started directly.
Without this rule an arm of a gate campaign that is a `frob` run verb would be admitted twice, once by the runner
under the gate's scope and once by its own verb under `adhoc`: a two-device or E1 arm would be refused there, and
a one-device arm would be metered twice.

**Which envelope refusal fires where (DESIGN, stated identically in the registries N32-REF, owner of row 704,
N35-REF, owner of row 761, and N36-REF).** The plan gives two codes for a job above the envelope: `FROB-REF-761`
("a job exceeds the compute envelope in force") and `FROB-REF-704` ("a campaign-class job without an approved
compute envelope"), both exit 4 with `retry: after-change`. They are divided by raising site, so that one
oversized job gets one code. The plan's rule for the daemon's size classes is that the `campaign` class (a job
above the machine envelope) is "refused with `FROB-REF-704` until the owner approves" an envelope: a
job-submitting verb queued by the daemon is classified first, and a job in the `campaign` size class with no
approved envelope for its scope is refused with 704 by the size classifier (BD-296, M3), before envelope
admission is reached; a queued job whose approval expires or is withdrawn before dispatch is refused with 704 by
the scheduler. Every other case is 761, built only here: a run executed in process by `frob` (where no size
class exists), including under the default class E0; a launch through `frob-launch` or `run_admitted`; and a
daemon job with an approved envelope that still exceeds that class's per-run limits or the cumulative
device-hours of its scope. `admit_run` and `admit` never build 704. Until BD-296 exists only 761 can fire.
An earlier text of this bead had `admit_run` answer 761 at submission on every surface, the daemon included, and
kept 704 for dispatch alone; that left the plan's sentence about the `campaign` class without a raising site at
submission, and the three registries had already settled the division above.

**Where the check sits.** In the one function through which `frob-verbs` starts any run verb or job
(`admit_run`), so that the CLI, the MCP server and the daemon cannot differ in what the envelope admits (for a
queued job the daemon's size classifier runs before it, as above); and exported as
`frob_core::envelope::admit` for the conformance campaign runner, which calls it before launching any arm,
including out-of-process incumbent runs, with a declared demand.

**Evidence.** Refusals and meter rows are ledger records; the meter's totals are exact sums of receipts.

## Acceptance criteria

- [ ] With no approval on record: a two-device job, a 24-thread job, a job with an upper wall estimate of 70 minutes and a 20 GiB job are each refused with `FROB-REF-761` before any device allocation, each naming the limit crossed and the class needed (E1).
- [ ] A one-device job with an upper estimate of 50 minutes and 8 GiB is admitted and runs under a one-hour timeout.
- [ ] With E1 approved in a scratch registry for `gate:GATE-SPARK-21` and the meter pre-loaded to 11.5 device-hours for that gate: a run with an upper end of 0.4 device-hours is decided `admitted` (and held or not started, as below, since the class of record is E0), and a run of 1.0 device-hours is refused with `FROB-REF-761` printing the remaining budget of 0.5 device-hours.
- [ ] KA-823: the arithmetic helpers reproduce 0.18 to 1.8·10⁹ env-steps per device-hour; 0.9 to 9, 2.8 to 28 and 1,100 to 11,000 device-hours for 1.6·10⁹, 5·10⁹ and 2·10¹² steps; 23 to 230 days on two cards; 45 device-hours fits E2 and 1,111 fits no class. The planted arithmetic that forgets the two cards (46 to 463 days) fails the test.
- [ ] With no approval on record, `needed_class` returns E1 for a two-device demand (the value `sim.estimate` prints as `needs: E1` once BD-219 lands, asserted there and by N36-32's step `envelope_class`), and submitting the job returns `FROB-REF-761` before any allocation. With E1 approved in a scratch registry for the scope the demand carries (the launcher's `--scope`, a token's scope, or a verb's own), the decision changes to admitted and the job is still never started: the launcher exits 4 with `FROB-REF-761` carrying `scratch_verdict: "admitted"` and starts no process; a verb at M0 is refused the same way; from M1 a verb's job is admitted with `hold: scratch-approval`. In every case zero worlds are stepped and zero device bytes allocated, and cancelling a held job yields a cancellation receipt.
- [ ] A run verb started directly has scope `adhoc`. Started as the child of `frob-launch` (or of `run_admitted`) with a declaration that contains its demand, it adopts the token's scope and class and writes no meter row: the arm leaves exactly one `envelope_meter` row, the launcher's, under the token's scope and none under `adhoc`. With a declaration smaller than its demand it is refused with `FROB-REF-761` naming the limit of the declaration; with a settled or unknown token it warns and decides as if started directly.
- [ ] A check registered in the fit slot runs before the class decision: with a `synthetic` check that refuses, a job that is also above the class in force gets the check's refusal and not 761; with the slot empty it gets 761. (That the real fit test gives `FROB-REF-602` there is BD-219's `fit_precedes_envelope`.)
- [ ] An out-of-process launch (an incumbent arm, a pilot on an incumbent stack) is metered: its settled usage appears in `envelope_meter` under its scope, an unsettled token is charged at its per-run limit with outcome `unsettled`, and the next admission for that scope counts both.
- [ ] A run executed in process above the class in force, a launch through `frob-launch`, and a job with an approved scope that exceeds that class's per-run limit or the cumulative device-hours of its scope are each refused with `FROB-REF-761` and never `FROB-REF-704`; no path of `admit_run` or `admit` builds 704. The daemon's half (a `campaign`-class job with no approved envelope refused with 704 by the size classifier before envelope admission; a queued job whose approval lapses refused with 704 at dispatch) is asserted in BD-296's tests and in N44-02's script, and is skipped here with a reason until the classifier exists.
- [ ] An E3 run without a written ceiling and kill rule is refused even when E3 is approved in general.
- [ ] A run stopped by its timeout publishes no result and appears in the meter with its device-seconds.
- [ ] No arm, ours or an incumbent's, can be launched out of process without passing `admit`: `run_admitted` takes an `Admitted` token that only `admit` constructs, and a compile-fail test shows that a launch without the token does not build; the campaign runner (BD-216) and `frob-launch` both go through it.
- [ ] `frob-launch --scope gate:GATE-SPARK-21 --devices 1 --cores 2 --mem-gib 1 --wall-s 60 -- sleep 2` exits 0 and appends one meter row with outcome `completed`, its `started` instant and device-seconds between 2 and 3; the same command with `--devices 2` under the default registry exits 4 with `FROB-REF-761` and starts no process; with `--wall-s 1` around `sleep 5` the group is terminated within 2 s and the row's outcome is `timed-out`.
- [ ] `CONTRACT.md` of `frob-verbs` lists `FROB-REF-761` with its trigger and repairs.

- `scope_of_direct_verb_is_adhoc`: a run verb started with no token and no scope of its own has scope `adhoc`, so
  E1 approved for a gate in a scratch registry does not admit its two-device run (plain 761, no

### Known answers and negative controls

- KA-823 (the envelope arithmetic; exact to two significant figures; tier G1 on the host; the refusal is exact). The plan states no tolerance and no control for it, so they are set here: the tolerance is the two significant figures the plan prints, and the control is an arithmetic that forgets the two cards, which reports 46 to 463 days and must fail `device_hour_arithmetic`.
- Negative controls: an admission path that uses the point estimate (must fail `upper_end_not_point`); a meter that resets on a new session (must fail `cumulative_limit_e1` when the test opens a fresh session between runs); a gate recorder that writes `fail` for an unapproved class; a run verb that ignores the envelope token and writes its own `adhoc` meter row (must fail `token_adopted_by_child_verb`: two rows for one arm); a verb that adopts a token whose declaration is smaller than its demand (must fail `token_too_small_is_761`).
- Determinism: admission is a pure function of the demand, the registry and the meter; the same inputs give the same verdict on both machines.

## Considerations

- RISK-10 (no compute envelope is approved, so the performance gates, the rank-agreement experiment and pretraining cannot run as specified; likelihood high; early sign: the question still at E0 when M1 opens). Mitigation built in here: every refusal names the class to request, and every gate records `not run` with that reason, so the cost of the default is visible in the exit review.
- The envelope is a ceiling on spend, not a schedule. Host load on `trj` and thermal state on the Mac change how much work a device-hour buys; the meter counts device-hours regardless.
- Out-of-process incumbent runs declare their demand; a declaration that proves too small is caught by the timeout and by the measured peak memory in the meter, and the next admission for that scope uses the measured values.
- Builds and tests count toward the machine rule; cargo already runs through the build-offload shim, which is outside this meter.
- OPEN (owner: the lead, with the surface unit): a job submitted directly through a run verb, from the command line without the launcher or over MCP, cannot name the approved scope it belongs to, because no registry row gives run verbs such an input; yet the registries speak of a job that "cites an approved envelope", and an agent over MCP has no launcher. Fail-closed default, which this bead builds: such a job is `adhoc`, class E0, and work above E0 through a `frob` verb is started under a token (`frob-launch`, the campaign runner) or by a verb whose bead derives its scope. If a citation input is added to the run verbs it feeds the same `Demand.scope`, and nothing else here changes.
