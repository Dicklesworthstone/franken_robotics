## Background

GATE-SPARK-19 (claim: Known answer; earliest milestone M2; TARGET): the performance harness rejects a report that
violates the unit ordering or omits a decimation; the paired-bound known answer holds; of 100 A/A campaigns at
most 9 clear a threshold of 1.02; a figure without a complete disclosure block is refused.

This gate does not measure the engine. It measures the instrument: before any throughput figure of ours is
recorded, the harness that will record it has to be shown to reject the four ways a speed figure usually
misleads (an ambiguous unit, an inconsistent set of rates, a ratio read off noise, a figure with its settings
missing). The plan's rule for every gate applies: a gate that nothing can fail validates nothing, so each clause
is exercised with a planted defect that must be caught, registered before the passing run.

This bead is the end-to-end script: it drives the real `frob` binary and the harness's gate test target from the
user's side, and writes the structured log and the gate receipt.

## Scope

In: the script, its steps, assertions, logging; the registered controls. Out: the harness code (BD-216 and its
parts); the engine rows (BD-217).

## Technical approach

**Invocation.** `scripts/e2e/perf_harness_gate19.sh --machine trj|mac [--tiers batch-cpu,gpu-cuda,gpu-metal]
--seed <s>`. Plain shell; sources the shared end-to-end helper; seed-explicit; idempotent (campaign records are
content-addressed, a completed campaign is not re-run); exits non-zero on any failed assertion. Designed so that one tier per invocation fits the default compute
envelope: one device, 8 CPU threads, under 45 minutes (TARGET; the A/A step is 100 × 10 × 2 runs of 1 s, about 33
minutes). Tiers are run as separate invocations and their records are merged by the gate step.

**Steps.**
1. `preflight`: `frob doctor --json`; `frob spark fingerprint --json` (assert current); print the envelope class
   in force and the workload identities.
2. `units`: submit the two planted reports to the harness validator: (a) 400 k env-steps/s of training at d = 10
   beside 2.0 M world-steps/s of physics on the same card; (b) the same with the decimation omitted. Assert both
   are rejected, (a) with pointer `rates.ordering`, (b) with `FROB-REF-862` and pointer `rates[i].decimation`.
   Then submit the consistent triple (400 k, 340 k, 280 k env-steps/s) and assert acceptance.
3. `paired_known_answer`: feed a recorded campaign of ten pairs, each with ratio exactly 1.5 (fixture labelled
   `synthetic`), through the estimator; assert the lower bound equals 1.5 and the record shows s = 0, t = 1.833.
   Submit the same campaign truncated to nine pairs; assert `FROB-REF-863`.
4. `aa_campaigns`: for each tier requested, run 100 A/A campaigns of ten pairs: both arms are
   `frob sim run --tier <t> --workload Q --worlds 256 --seconds 1 --seed <s_i> --json` on the same build
   (8,192 worlds on devices). Assert that the number of campaigns whose lower bound exceeds 1.02 is at most 9;
   log the count and the distribution of bounds.
5. `disclosure`: take a real report from step 4; assert its block is complete; delete each field in turn from a
   copy and assert `FROB-REF-862` with the right pointer; set `energy` to zero and assert refusal.
6. `ceiling_first`: submit a speed-experiment campaign with no ceiling record, and one with ceiling 1.46 and goal
   2.0; assert `FROB-REF-866` for both; submit one with goal 1.4 and assert admission.
7. `timer_completion`: run the harness against the test-only backend shim that reports completion late; assert
   the run is rejected (INV-PERF-02).
8. `optimization_ledger` and `regression_lane`: run the landing check on the scratch ledger of planted defects
   and the regression lane on the two planted build variants; assert the expected failures.
9. `refusal_exit_codes`: for one case of each refusal, invoke through `frob … --json` where a verb surface exists
   and assert exit code 3 (`-862`, `-863`, `-866`) and the envelope's `refusal` fields (`code`, `pointer`,
   `retry`, ranked `repairs`).
10. `gate`: `cargo test -p frob-conformance --test g1 -- GATE-SPARK-19` assembles the gate record from the step
    results and writes the receipt (commit, command, output, receipt hash, fingerprint digest, seed).

**Logging.** NDJSON to `target/e2e-logs/perf_harness_gate19/<utc-timestamp>.ndjson` and a transcript beside it.
Every line: `ts`, `script`, `bead`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the
exact command line, exit code, wall time, and the envelope's evidence block (claim, class, tier, determinism,
identities, seed). `metric` lines: for A/A, campaign index, n, ℓ̄, s, t, the lower bound against 1.02 and the
running count against 9; for the known answer, the bound against 1.5. `refusal` lines: code, pointer, exit code,
the repairs offered. On failure: the first differing value (for example the first campaign that pushed the count
to 10, with its pairs record path) and the artifact paths. Final `summary`: assertions passed and failed, the A/A
count per tier, `gates: ["GATE-SPARK-19"]`. No scene data is logged; the workload is a public reference robot on
flat ground.

## Acceptance criteria

- [ ] The script exits 0 on a correct build and writes a receipt for GATE-SPARK-19 with the measured A/A counts per tier (measured values, not the threshold).
- [ ] Each of the four clauses of the gate has at least one planted defect in the registry of negative controls, and the script shows each being caught.
- [ ] With the estimator replaced by its mean-returning mutant, the script exits non-zero at `paired_known_answer` or `aa_campaigns`; with the ordering check's unit conversion removed, at `units`; with the completeness check treating absent as not applicable, at `disclosure`.
- [ ] Each invocation (one tier) stays inside the default envelope (one device, 8 threads, under an hour) and says so in its summary with the measured wall time.
- [ ] Every NDJSON line has the required fields; the `summary` line names the gate.
- [ ] Re-running after success performs no new campaigns and reproduces the same receipt hash.

## Test plan

### Unit tests

None of its own beyond a shell lint and a dry-run mode (`--plan`) that prints the steps and exits 0 without
running; the code under test is covered by the unit tests of the harness beads.

### End-to-end script and logging

This bead is the script; steps, assertions and log fields are defined above.

### Known answers and negative controls

- KA-806 (ordering; the omitted-decimation control), KA-807 (ten pairs at 1.5 → 1.5; the A/A control), KA-812 (ceiling refusal), KA-825 (the two refusals).
- Registered controls (each must make the script fail when planted): the unit-blind ordering check; the mean-returning estimator; the always-A-first runner on a fixture with a warm-up effect; the completeness check that accepts absent fields; the early timer.
- Determinism lanes: steps 2, 3, 5, 6 are exact and must give identical logs (apart from timestamps) twice on one machine and on both machines; step 4 is a measurement whose count is recorded, not compared across machines.

## Considerations

- RISK-09: if `trj` is too loaded for pairing to cancel its noise, step 4 fails there. That is a finding about the machine, recorded as such; ratios from that machine are not admitted until the count passes, and the Mac's count is unaffected.
- The A/A runs are short (1 s) so that the gate fits the default envelope; short runs are noisier than the parity rows will be, which makes this a conservative test of the estimator.
- The script is re-run whenever the harness, the estimator or the disclosure schema changes, and at every milestone exit from M2 on.
