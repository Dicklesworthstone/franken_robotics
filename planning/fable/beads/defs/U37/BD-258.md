## Background

Several agents share one daemon, two machines and a pair of expensive devices. The threat model's fourth
asset is "budgets and other agents' work", threatened by a client that retries blindly and by an agent
writing into another's lineage; its first is the owner's machines, threatened by an agent that is confused,
wasteful or acting on injected text. Capabilities are the answer to "who may do what": a session holds a
**capability token** with scopes such as `design:write`, `sim:run`, `gpu:seconds=600`, `scene:import` and
`train:run`. Each agent has its own design namespace and lineage; no agent can rewrite another's history. A
shared leaderboard and archive are read-only views.

Authorization distinguishes **three acts**, and scopes keep them apart: *reading* an existing trace,
*allocating* a job, and *publishing* an export. A token that can read cannot thereby spend, and one that can
spend cannot thereby publish. Reason: the damage of each act is different (disclosure, cost, something
leaving the machine), and an injected instruction should need the specific grant for the specific harm.

One scope does not exist: no scope grants reading a confirmation world (the sealed worlds that judge a
qualification request). That isolation has its own three layers and its own bead; this bead supplies the
capability layer they stand on.

Seed done-condition: GATE-SAFE-10 (path jail: a corpus of traversal, absolute-path and swapped-link attempts
is refused on every path-taking argument of every verb), and a session without the scope receives the refusal
and no partial data. Design alternatives rejected: ambient authority by operating-system user (every agent on
the machine is the same user); per-verb passwords or allow-lists in configuration (cannot be attenuated for a
sub-agent); bearer tokens with holder-side offline derivation (the budget of a derived token must be debited
from its parent in the ledger anyway, so derivation goes through the daemon).

## Scope

This seed bead is the capstone of the capability layer. The parts of the layer are built by component beads;
this bead depends on each of them, does not rebuild them, and closes the layer over the whole M3 surface.

Built by the components: the scope catalogue with its lint, the token format and its authentication tag, the
daemon key, minting, and the verification step in the dispatcher before any handler, with `FROB-REF-720` and
`FROB-REF-723` (N32b-01); attenuation, the debit of a derived budget from its parent and the return of the
unspent part (N32b-02); namespaces, lineage ownership with `FROB-REF-725`, and the shared archive and
leaderboard views (N32b-03); the verb surfaces `session.open` and `session.show` (N32b-04); the path jail
mechanism with its M1 gate record (N37-11). Steps 1, 2, 4, 5 and 6 of the Technical approach state those parts
again so that the layer can be read in one place; where a component bead is more detailed, the component
governs its part. For the token (step 1), the scope catalogue and its grammar (step 2) and the verification
order (step 5) the component is N32b-01: this bead restates its token field for field and adds no field, no
second wire form and no second key location, and the token's own tests (round trip, tampering, expiry, closed
session, unknown scope) are written once, in N32b-01, and re-run here on the M3 surface.

In this bead: the registry lint that keeps the three acts apart, run over every verb of the M3 registry
(step 3); the decision on how a verb's scopes are named (by the verb's own cluster, never by the object it
reads) and on which scopes imply a `:read` scope, which the 30 cluster registry beads (`VERBS-…`) carry as
proposals until this bead fixes them (step 2); per-session and
per-namespace roots for the path jail, with the private root reachable only under the private scopes
(step 7); the scope matrix over every verb, with the byte-level check that a refusal carries no partial data
(step 8a); the path-jail sweep re-run on the M3 surface under three tokens and two namespaces, and the M3
record of GATE-SAFE-10 (step 8b).

Out: budget accounting, rate limits and the admission guard (N37-13); the remote-worker manifest (N37-14);
the qualification scopes and sealed reads (BD-261); private-scope semantics (BD-305); the mapping of a
transport credential to a token (N32a-27); the end-to-end scripts (N37-15 for scopes, attenuation,
namespaces, budgets and workers; N37-12 for the gate; the script of the same mechanisms on the surface side
is N32b-05).

## Technical approach

1. **Token (DESIGN; schema `frob.token/1`; the layout is N32b-01's, restated).** The payload, in canonical
   JSON:
   ```json
   { "session": "s:41aa…", "principal": "agent-7", "namespace": "agent-7", "parent": null,
     "scopes": ["cpu:core_seconds=7200", "design:read", "design:write", "disk:bytes=2147483648",
                "export:report", "gpu:seconds=600", "sim:run", "telemetry:read"],
     "issued_ns": "1798675200000000000", "expires_ns": "1798761600000000000", "key_id": "9c1e4a7702b35d18" }
   ```
   On the wire a token is `frobtok1.<base64url(canonical JSON payload)>.<base64url(tag)>`, where `tag` is the
   keyed BLAKE3 hash of the canonical payload bytes under the daemon's token key (32 random bytes at
   `<state root>/keys/token.key`, mode 0600, never printed) and `key_id` is the first 8 bytes of
   BLAKE3(token key) in hex. That file is the token key only: the key that tags pagination cursors is a second
   file, `<state root>/daemon.key` (N32a-10, N32a-14), and neither key verifies the other's tags (N32b-01).
   Integers that can exceed 2⁵³ are decimal strings. The CLI and the stdio MCP
   server read the token from the environment (`FROB_SESSION_TOKEN`, or a file named by
   `--session-token-file`); the HTTP transport takes it as a bearer credential.
   One layout, with the reason (DESIGN). An earlier draft of this bead gave the token other names and another
   shape: `not_after` where the component has `expires_ns`, `mac` where it has `tag`, a stored `id`, a
   namespace written `ns:agent-7`, a separate `budgets` object with a fourth entry `trace_bytes`, and the tag
   inside the JSON body. The plan fixes none of this; N32b-01 builds the token a milestone earlier and its
   layout stands, so that the type has one definition. What that draft carried survives as follows: budgets
   are budget scopes inside `scopes`, as the plan writes them (`gpu:seconds=600`; the CLI spellings `gpu_s`,
   `cpu_core_s` and `disk_bytes` of `session.open --budget` are stored as `gpu:seconds`, `cpu:core_seconds`
   and `disk:bytes`); the amounts left are in the session row of the ledger and never in a token, which is
   immutable; the trace-byte budget is a unit of the session budget ledger, set from the principal's grant and
   accounted by N37-13, not a token scope; the token identifier is derived and never stored: `tk:` followed by
   the BLAKE3 of the canonical payload, which is safe to log because it does not yield the tag.
2. **Scope vocabulary** (the catalogue `registries/scopes.toml` and its grammar are N32b-01's). Grammar
   `^[a-z][a-z0-9-]*:[a-z][a-z0-9_-]*(=[0-9]+)?$`; an unknown scope string makes a token invalid
   (`FROB-REF-723`). The list: the generated forms `<cluster>:read`, `<cluster>:run`, `<cluster>:write` and
   `<cluster>:admin`, which N32b-01's catalogue generates from M2 for exactly the (cluster, kind) pairs some
   registry row cites (`design:write`, `study:write`, `train:admin`, `store:admin`, …; this bead adds no second
   catalogue and no scope of its own); the named spending scopes `study:submit`, `mission:run`, `nemesis:run`,
   `autopsy:run`, `qual:run`; the named write scopes `scene:import`, `ground:import`, `cert:write`;
   `export:report`, `export:packet`, `export:policy`; `private:read`, `private:export`; the named admin scopes
   `job:cancel` and those added under the named-scope rule (N32bx-02: `ground:retire`); and budgets
   `gpu:seconds=N`, `cpu:core_seconds=N`, `disk:bytes=N`. The owner's qualification scope is minted only from
   the owner-held configuration and can never be the result of a derivation.

   **Naming rule (DESIGN, decided here).** A registry row cites scopes of the verb's own cluster (the part of
   `cluster.verb` before the dot), by the row's kind: `read` → `<cluster>:read`; `run` → `<cluster>:run` or a
   named spending scope; `mutate` → `<cluster>:write` or a named write scope; `admin` → `<cluster>:admin`,
   `job:cancel` or a named admin scope; plus `export:*` when the row exports and `private:*` where step 7
   applies (and, on the two `run` rows that create a named object, that object's named write scope as their
   spending scope: `scene.import` with `scene:import`, `prove.bundle` with `cert:write`; step 3). A scope is
   never named after the object the verb reads or the engine it spends on: `sense.symmetry`
   cites `sense:read`, not `design:read`, and `sense.calibrate` cites `sense:run`, not `sim:run`. The plan's
   examples `design:write` and `sim:run` are the clusters `design` and `sim`. Reason: one rule generates all
   rows of the registry and, through N32b-01's generated forms, the whole catalogue by construction; scoping by
   object needs a second table from verb to object kind, and a verb that reads three kinds would cite three
   scopes whose union is wider than the act it performs. Rejected for that reason: the sensing unit's draft
   (`design:read` for the three sense reads, `sim:run` for the five sense runs).

   **Implied read (DESIGN, decided here).** `<cluster>:run` and `<cluster>:write` each imply `<cluster>:read`
   (a session that may run or edit a cluster's objects can see them through the result anyway). The
   implication is applied when a scope set is stored, never when it is checked: the minting step closes the
   requested set under it before computing the tag, and a derivation closes the child's request the same way
   before the subset test, so verification and attenuation stay plain set inclusion and a token's `scopes`
   list is always closed. The rule goes by the spelling of the scope (N32b-01's sentence, adopted here): a
   scope spelled `<c>:run` or `<c>:write` whose `<c>` is a registry cluster implies `<c>:read` when the
   catalogue has it, whether the catalogue lists it among the generated forms or among the named spending and
   write scopes (`mission:run`, `nemesis:run`, `autopsy:run`, `qual:run` and `cert:write` have that spelling;
   the plan's worked session holds `mission:run` and no `mission:read` and reads its mission answers). Every
   other scope implies nothing: `study:submit`, `scene:import`, `ground:import`, `job:cancel` and the other
   named admin scopes, `<cluster>:admin`, `export:*`, `private:*` and the budget scopes (an admin act, an
   import or a publication needs its own grant). A derived request listing `sense:run` without `sense:read` is
   therefore granted both and is not a widening, because the parent's closed set holds both. The closure is
   one function, `Scopes::close_implied`, written in N32b-01 (minting is there and precedes this bead) and
   called by N32b-01's minting and N32b-02's derivation; this bead fixes the rule it applies and defines no
   second copy. Their tests are unchanged, because a closed set is still a set, and the verification step
   reads no rule.
3. **The three acts in the registry.** Each verb row lists `capabilities`. Lint
   (`crates/frob-verbs/tests/scope_acts.rs`), which takes each scope's kind from its catalogue row (`read`,
   `spend`, `write`, `publish`, `private`, `admin`, `budget`; N32bx-02's `scope-kind-act`), never from the
   scope's suffix: a verb of kind `read` requires only scopes of kind `read` (`<cluster>:read`, or a named read
   scope such as the owner-held `session:audit` of N32bx-01) plus `private:read` when applicable; a verb of
   kind `run` requires a scope of kind `spend` (`<cluster>:run` or a named spending scope) and is
   charged against a budget; a verb that writes an artifact outside the store (registry field
   `exports = true`, a bool in the entry schema) requires an `export:*` scope in addition, listed in its
   `capabilities`, or, where only one input option writes outside the store (`sim.run --resolved-out`), in
   that option's `option_capabilities` (N32b-01's map from an option to the scopes it additionally needs), so
   that a call without the option needs no publish scope; a verb of kind `admin` requires a
   `<cluster>:admin` scope, `job:cancel` or a named admin scope; a verb of kind `mutate` requires a write
   scope (`<cluster>:write`, or a named write scope `scene:import`, `ground:import`, `cert:write`) and acts in
   the caller's namespace. A guarded action inside a row (`actions = [{name, kind, capabilities}]`, the form
   N32bx-02 uses for `ground.band#retire`) is linted by its own kind. Every cited scope obeys the naming rule
   of step 2 (own cluster, or a named scope of the catalogue). No verb may list a scope that is not in the
   vocabulary. Every exporting row passes: `design.export` cites `export:report` beside `design:read` (its
   URDF, MJCF or GLB file under the export root is a publication like `run.export`'s).

   Three forms of the registry as it stands, which the lint accepts and nothing else (DESIGN). (i) A row
   with `public = true` and `capabilities = []` (the operator verbs `doctor`, `capabilities`, `schema`,
   `robot-docs`, and `session.focus`, `session.open`, `session.show`, `session.close`; N32a-02's RL-10) needs
   no grant (N32b-01, step 4 of its verification) and is exempt from the rule of its kind; its
   `option_capabilities` and actions are linted by their own kinds (`session.show`'s `all` with
   `session:read`, its action `audit` with `session:audit`). Without this exemption the three `mutate` session
   rows fail the lint. (ii) A named write scope is accepted as the spending scope of a `run` row that creates
   the named object, and only of that row: `scene:import` on `scene.import` (the import is a job that writes a
   scene pack) and `cert:write` on `prove.bundle` (VERBS-prove). (iii) `cert:write` is also `prove.bundle`'s
   publish scope (`exports = true`; the export kind of a certificate bundle): none of `export:report`,
   `export:packet` or `export:policy` names a certificate bundle, and the plan's worked session runs `frob
   prove bundle … --out` holding `cert:write` and no `export:*` scope (N32b-16, BD-409), so it is the publish
   scope of an exporting row of the `prove` cluster and of no other row. N37-18's export door takes it as the
   publish scope of that export kind.
4. **Minting and attenuation.** `session.open` (kind `mutate`) with no parent mints a root token for a
   principal from that principal's grant in the owner-held configuration (N32b-01's minting, restated): the
   principal is the `principal` input, or, when it is omitted, the one principal the configuration grants
   (several granted: `FROB-REF-802`, pointer `/principal`; an unlisted principal or none granted:
   `FROB-REF-723`); omitted `scopes` grant no non-budget scope (authority is always named) and an omitted
   budget unit takes the grant's amount; a request beyond the grant is `FROB-REF-723` naming the widening
   element. A root call that presents a valid token is `FROB-REF-723`: a holder derives and never opens a
   second root beside its token, so over MCP `session_open` is derive-only. With `derive` (`derive: true`; CLI
   `--derive`; N32b-04) it mints a child of the caller's own token, which travels in `FROB_SESSION_TOKEN` or
   `--session-token-file` and never as an argument (N32b-01): scopes must be a subset of the parent's; each budget at most the parent's remaining amount;
   `expires_ns` no later than the parent's; namespace equal to the parent's (a derived session works in its
   parent's namespace with less authority: a sub-agent is the same agent's helper, not a new tenant; N32b-02
   and N32b-03 state the rule, and the sub-namespace that an earlier draft of this bead allowed is not part
   of it). A widening on any of these is `FROB-REF-723` (token invalid or expired, or an
   attenuation that would widen scopes or budget; exit 5). The child's budget is **debited from the parent**
   in the same ledger transaction that records the session; `session.close` returns the unspent part.
   `session.show` prints scopes, budgets left, namespace, focus, the parent chain by identifier and the safety
   configuration digest.
5. **Verification before anything else.** For every request the dispatcher, before resolving any argument and
   before any handler code runs (the order is N32b-01's steps 1 to 6): (a) parses the three parts of the
   token and checks the keyed hash under the key named by `key_id` in constant time; (b) checks expiry and
   that the session is open; (c) checks the verb's required scopes are present, else `FROB-REF-720` (the
   session token lacks a required scope; exit 5; `pointer: /session/scopes`; `observed` the held scopes,
   `required` the missing ones; the two repairs of the registry row; `retry: after-change`); (d) for a write,
   checks the target lineage and namespace, else
   `FROB-REF-725` (a write outside the caller's namespace or lineage; exit 5). A refusal envelope has
   `ok: false`, the refusal, and no `result`, no `cursor`, no `job`: the caller receives **no partial data**.
   A streamed or paginated answer performs the check before its first frame; a token that expires during a
   wait ends the wait with `FROB-REF-723`, leaves an admitted job running, and the job is recoverable by its
   idempotency key under a valid token.
6. **Namespaces and shared views.** Every design, lineage, job, study and export belongs to a namespace.
   Reads across namespaces are allowed only through the shared views. The shared archive is a grow-only set
   keyed by content address, merged by union; the leaderboard is derived from it with ties broken by a total
   order (metric, then content address), so two daemons that merge in either order reach the same view.
   Lineage identifiers are plain strings usable as message-thread identifiers by the suite's agent mail
   system, so a swarm coordinates with the tools it already has. Private objects never enter a shared view.
7. **Per-session roots.** The path jail's roots become per session: the project root is shared read-only
   outside the session's namespace directory; the export root is `exports/<namespace>/` beneath the configured
   export root (created on first use, mode 0700); the private root is reachable only when the token holds
   `private:read` (reads) or `private:export` with the per-call flag (exports), otherwise a path argument
   bound to it is `FROB-REF-734` with `observed = root-unset`. Handles are retained per session and dropped at
   `session.close`.
8. **Tests that carry the gate.** (a) The scope matrix: for each verb and each required scope, a token
   lacking exactly that scope is refused with `FROB-REF-720` and an envelope with no `result`; with all
   scopes the same call succeeds. (b) The path-jail sweep of the path-jail script, re-run for every verb of
   the M3 surface under three tokens (no private scopes; `private:read`; `private:read` and
   `private:export`) and two namespaces.
9. **Classes.** Authorization decisions are D0. Tokens, sessions and refusals are recorded in the job ledger;
   a refused request writes a row `refused {session, verb, code}` and charges nothing.

## Acceptance criteria

- [ ] GATE-SAFE-10 on the full surface (TARGET): the traversal, absolute-path and swapped-link corpus is
      refused on every path-taking argument of every verb, per session root and namespace; recorded with
      counts (seed done-condition).
- [ ] The scope matrix passes for every verb: a session without the scope receives `FROB-REF-720`, exit 5,
      and no partial data (seed done-condition); a byte-level check of the refusal envelope finds no `result`.
- [ ] A derived token with one extra scope, a larger budget, a later expiry or a foreign namespace is refused
      with `FROB-REF-723`; a valid derivation debits the parent, and closing the child returns the remainder.
- [ ] A forged token (one flipped bit in payload or `tag`), an expired token and a token naming an unknown scope
      are each `FROB-REF-723` (N32b-01's tests, re-run on the M3 surface).
- [ ] Agent A's write into agent B's lineage is `FROB-REF-725`; A sees B's designs only through the shared
      archive.
- [ ] Merging two daemons' shared archives in either order gives the same set and the same leaderboard order.
- [ ] The registry lint for the three acts passes; a planted `run` verb with only a `:read` scope fails it; a
      planted exporting verb without an `export:*` scope fails it; a `mutate` row citing `study:write` and an
      `admin` row citing `train:admin` pass it; `sim.run` with `export:report` only under the option
      `resolved_out` passes it, and the same row with the option's entry removed fails it; the eight `public`
      rows, `scene.import` (`scene:import`) and `prove.bundle` (`cert:write` alone, `exports = true`) pass it;
      a planted `sim.run` citing `scene:import` as its only spending scope and a planted exporting
      `report.run` citing `cert:write` in place of `export:report` each fail it.
- [ ] The naming rule holds over every row of the M3 registry: each cited scope is of the row's own cluster or
      a named scope of the catalogue; a planted `sense.symmetry` row citing `design:read` fails the lint.
- [ ] Every minted and every derived token's `scopes` is closed under the implied-read rule: a session opened
      with `sense:run` alone holds `sense:read` and can call `sense.symmetry`; one opened with `sense:admin`
      or `export:report` alone gains no `:read` scope.

a temporary state root; no mocks):

  bit of a 300-byte token; `expiry_boundary`; `closed_session_refused`; `unknown_scope_rejected`), and so

### End-to-end script and logging
`scripts/e2e/safe_capabilities.sh` (N37-15) for scopes, attenuation and namespaces, and
`scripts/e2e/safe_path_jail.sh` (N37-12) for the gate, both against the real `frob`, `frobd` and `frob-mcp`,
logging per STD-E2E the command line, exit code, refusal code, the session identifier and the derived token
identifier `tk:…` (never the token), scopes held and required, and budgets before and after. The M1 script

KA-835 (path jail corpus refused on every path-taking argument of every verb; exact). Known answers of this

refusals for existing and non-existing objects); a build that accepts a superset derivation; the path-jail
controls of N37-11. Determinism lanes: decisions identical across platforms; the archive merge property under
random orders.

## Considerations

- A refusal must not reveal whether an object exists in another namespace or in the private root: the scope
  check precedes resolution, so the refusal is the same either way.
- Whoever holds the daemon key can mint anything; it is owner-held, and a local user with root is outside the
  threat model.
- Tokens in environment variables are visible to same-user processes; a sub-agent should be given a derived
  token with the smallest scopes and budget that its task needs. The agent guide says so.
- Open question on retention of idempotency keys and job logs (owner: the project owner; default 30 days)
  bounds how long a closed session's records remain; see N37-30.
- The dashboard is an ordinary client: read verbs only, plus `job.cancel` under a token that holds that scope.
