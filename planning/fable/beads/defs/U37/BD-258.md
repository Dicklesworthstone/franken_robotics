## Background

Several agents share one daemon, two machines and a pair of expensive devices. The threat model's fourth
asset is "budgets and other agents' work", threatened by a client that retries blindly and by an agent
writing into another's lineage; its first is the owner's machines, threatened by an agent that is confused,
wasteful or acting on injected text. Capabilities are the answer to "who may do what": a session holds a
**capability token** with scopes such as `design:write`, `sim:run`, `gpu:seconds=600`, `scene:import` and
`train:run`. Each agent has its own design namespace and lineage; no agent can rewrite another's history. A
shared leaderboard and archive are read-only views.

Authorization distinguishes **three acts**, and scopes keep them apart: *reading* an existing trace,
*allocating* a job, and *publishing* an export. A token that can read cannot thereby spend, and one that can
spend cannot thereby publish. Reason: the damage of each act is different (disclosure, cost, something
leaving the machine), and an injected instruction should need the specific grant for the specific harm.

One scope does not exist: no scope grants reading a confirmation world (the sealed worlds that judge a
qualification request). That isolation has its own three layers and its own bead; this bead supplies the
capability layer they stand on.

Seed done-condition: GATE-SAFE-10 (path jail: a corpus of traversal, absolute-path and swapped-link attempts
is refused on every path-taking argument of every verb), and a session without the scope receives the refusal
and no partial data. Design alternatives rejected: ambient authority by operating-system user (every agent on
the machine is the same user); per-verb passwords or allow-lists in configuration (cannot be attenuated for a
sub-agent); bearer tokens with holder-side offline derivation (the budget of a derived token must be debited
from its parent in the ledger anyway, so derivation goes through the daemon).

## Scope

In: the token format and its authentication; minting and attenuation at `session.open`; verification in the
dispatcher before any handler; the scope vocabulary and the registry lint for the three acts; namespaces and
the shared read-only views; per-session and per-namespace roots for the path jail; the scope matrix test; the

admission guard (N37-13); the remote-worker manifest (N37-14); the qualification scopes and sealed reads

## Technical approach

1. **Token (DESIGN; schema `frob.token/1`, canonical JSON).**
   ```json
   { "schema": "frob.token/1", "id": "tk:6f0c…", "session": "s:41aa…", "principal": "agent-7",
     "namespace": "ns:agent-7", "parent": null,
     "scopes": ["design:read", "design:write", "sim:run", "telemetry:read", "export:report"],
     "budgets": { "gpu_s": "600", "cpu_core_s": "7200", "disk_bytes": "2147483648", "trace_bytes": "1073741824" },
     "not_after": "1798761600000000000", "mac": "b3k:…" }
   ```
   `id` is the BLAKE3 identity of the body without `mac`; `mac` is keyed BLAKE3 over the same canonical bytes
   under the daemon key (32 random bytes in the state root, mode 0600, never printed). Integers that can
   exceed 2⁵³ are decimal strings. The CLI and the stdio MCP server read the token from the environment; the
   HTTP transport takes it as a bearer credential.
2. **Scope vocabulary.** Grammar `^[a-z][a-z0-9-]*:[a-z][a-z0-9_-]*(=[0-9]+)?$`; an unknown scope string makes
   a token invalid. The list: `<cluster>:read` and `<cluster>:run` for each verb cluster; `design:write`;
   `scene:import`; `train:run`; `study:submit`; `mission:run`; `nemesis:run`; `autopsy:run`; `qual:run`;
   `cert:write`; `ground:import`; `export:report`, `export:packet`, `export:policy`; `private:read`,
   `private:export`; `job:cancel`; `<cluster>:admin` for the other admin verbs (DESIGN: the scope list as specified
   names only `job:cancel`, and every admin verb needs some scope); and budgets `gpu:seconds=N`,
   `cpu:core_seconds=N`, `disk:bytes=N`. The owner's qualification scope is minted only from the owner-held
   configuration and can never be the result of a derivation.
3. **The three acts in the registry.** Each verb row lists `capabilities`. Lint
   (`crates/frob-verbs/tests/scope_acts.rs`): a verb of kind `read` requires only `:read` scopes (plus
   `private:read` when applicable); a verb of kind `run` requires a `:run` or named spending scope and is
   charged against a budget; a verb that writes an artifact outside the store (registry field
   `exports = […]`) requires an `export:*` scope in addition; a verb of kind `admin` requires `:admin` or
   `job:cancel`; a verb of kind `mutate` requires a write scope and acts in the caller's namespace. No verb
   may list a scope that is not in the vocabulary.
4. **Minting and attenuation.** `session.open` (kind `mutate`) with no parent mints a root token for a
   principal from that principal's grant in the owner-held configuration. With `--derive-from <token>` it
   mints a child: scopes must be a subset of the parent's; each budget at most the parent's remaining amount;
   `not_after` no later than the parent's; namespace equal to the parent's or a sub-namespace
   (`ns:agent-7/sub-1`). A widening on any of these is `FROB-REF-723` (token invalid or expired, or an
   attenuation that would widen scopes or budget; exit 5). The child's budget is **debited from the parent**
   in the same ledger transaction that records the session; `session.close` returns the unspent part.
   `session.show` prints scopes, budgets left, namespace, focus, the parent chain by identifier and the safety
   configuration digest.
5. **Verification before anything else.** For every request the dispatcher, before resolving any argument and
   before any handler code runs: (a) parses the token and checks the keyed hash in constant time; (b) checks
   expiry and that the session is open; (c) checks the verb's required scopes are present, else
   `FROB-REF-720` (the session token lacks a required scope; exit 5; `observed` the held scopes, `required`
   the missing ones; `retry: after-change`); (d) for a write, checks the target lineage and namespace, else
   `FROB-REF-725` (a write outside the caller's namespace or lineage; exit 5). A refusal envelope has
   `ok: false`, the refusal, and no `result`, no `cursor`, no `job`: the caller receives **no partial data**.
   A streamed or paginated answer performs the check before its first frame; a token that expires during a
   wait ends the wait with `FROB-REF-723`, leaves an admitted job running, and the job is recoverable by its
   idempotency key under a valid token.
6. **Namespaces and shared views.** Every design, lineage, job, study and export belongs to a namespace.
   Reads across namespaces are allowed only through the shared views. The shared archive is a grow-only set
   keyed by content address, merged by union; the leaderboard is derived from it with ties broken by a total
   order (metric, then content address), so two daemons that merge in either order reach the same view.
   Lineage identifiers are plain strings usable as message-thread identifiers by the suite's agent mail
   system, so a swarm coordinates with the tools it already has. Private objects never enter a shared view.
7. **Per-session roots.** The path jail's roots become per session: the project root is shared read-only
   outside the session's namespace directory; the export root is `exports/<namespace>/` beneath the configured
   export root (created on first use, mode 0700); the private root is reachable only when the token holds
   `private:read` (reads) or `private:export` with the per-call flag (exports), otherwise a path argument
   bound to it is `FROB-REF-734` with `observed = root-unset`. Handles are retained per session and dropped at
   `session.close`.
8. **Tests that carry the gate.** (a) The scope matrix: for each verb and each required scope, a token
   lacking exactly that scope is refused with `FROB-REF-720` and an envelope with no `result`; with all
   scopes the same call succeeds. (b) The path-jail sweep of the path-jail script, re-run for every verb of
   the M3 surface under three tokens (no private scopes; `private:read`; `private:read` and
   `private:export`) and two namespaces.
9. **Classes.** Authorization decisions are D0. Tokens, sessions and refusals are recorded in the job ledger;
   a refused request writes a row `refused {session, verb, code}` and charges nothing.

## Acceptance criteria

- [ ] GATE-SAFE-10 on the full surface (TARGET): the traversal, absolute-path and swapped-link corpus is
      refused on every path-taking argument of every verb, per session root and namespace; recorded with
      counts (seed done-condition).
- [ ] The scope matrix passes for every verb: a session without the scope receives `FROB-REF-720`, exit 5,
      and no partial data (seed done-condition); a byte-level check of the refusal envelope finds no `result`.
- [ ] A derived token with one extra scope, a larger budget, a later expiry or a foreign namespace is refused
      with `FROB-REF-723`; a valid derivation debits the parent, and closing the child returns the remainder.
- [ ] A forged token (one flipped bit in body or `mac`), an expired token and a token naming an unknown scope
      are each `FROB-REF-723`.
- [ ] Agent A's write into agent B's lineage is `FROB-REF-725`; A sees B's designs only through the shared
      archive.
- [ ] Merging two daemons' shared archives in either order gives the same set and the same leaderboard order.
- [ ] The registry lint for the three acts passes; a planted `run` verb with only a `:read` scope fails it; a
      planted exporting verb without an `export:*` scope fails it.

`cargo test -p frob-verbs --test caps --test scope_acts` and `-p frob-cli --test session` (the real ledger in
a temporary state root; no mocks):
- `token_roundtrip_and_mac`; `flipped_bit_rejected` (every bit of a 300-byte token); `expired_rejected`;
  `unknown_scope_rejected`.
- `derive_subset_ok`; `derive_extra_scope_refused`; `derive_budget_over_remaining_refused` (parent 600 GPU
  seconds with 250 spent: a child asking 351 is refused, 350 is granted and the parent shows 0 left);
  `derive_later_expiry_refused`; `close_returns_unspent` (child granted 350, spent 100: parent regains 250).
- `admin_scope_not_derivable`.
- `scope_matrix_<cluster>`: generated from the registry.
- `refusal_has_no_result_field`.
- `namespace_write_refused_725`; `shared_archive_union_is_commutative_associative_idempotent` (property test
  over random sets); `leaderboard_total_order` (equal metrics ordered by content address).
- `per_session_export_root`: two namespaces cannot name each other's export directory.
- `private_root_needs_scope`.
- `planted_run_verb_with_read_scope_fails_lint`; `planted_export_without_scope_fails_lint`.

### End-to-end script and logging
`scripts/e2e/safe_capabilities.sh` (N37-15) for scopes, attenuation and namespaces, and
`scripts/e2e/safe_path_jail.sh` (N37-12) for the gate, both against the real `frob`, `frobd` and `frob-mcp`,
logging per STD-E2E the command line, exit code, refusal code, the token identifier (never the token), scopes
held and required, and budgets before and after.

### Known answers and negative controls
KA-835 (path jail corpus refused on every path-taking argument of every verb; exact). Known answers of this
bead: the attenuation arithmetic above (600 − 250 = 350 grantable; 350 − 100 = 250 returned). Negative
controls: a `mutants` build whose dispatcher checks scopes after resolving arguments (a refused read of an
existing run must then leak the run's existence through a different error; the matrix asserts identical
refusals for existing and non-existing objects); a build that accepts a superset derivation; the path-jail
controls of N37-11. Determinism lanes: decisions identical across platforms; the archive merge property under
random orders.

## Considerations

- A refusal must not reveal whether an object exists in another namespace or in the private root: the scope
  check precedes resolution, so the refusal is the same either way.
- Whoever holds the daemon key can mint anything; it is owner-held, and a local user with root is outside the
  threat model.
- Tokens in environment variables are visible to same-user processes; a sub-agent should be given a derived
  token with the smallest scopes and budget that its task needs. The agent guide says so.
- Open question on retention of idempotency keys and job logs (owner: the project owner; default 30 days)
  bounds how long a closed session's records remain; see N37-30.
- The dashboard is an ordinary client: read verbs only, plus `job.cancel` under a token that holds that scope.
