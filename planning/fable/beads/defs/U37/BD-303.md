## Background

Simulation results are not a safety case for a physical robot. Reports carry that no-claim line, and the
line is machine-readable: every exported artifact carries three fields, each with the constant value `false`:
`execution_authorized`, `hardware_safety_signoff`, `sim_to_real_certified`. Build packets carry a fourth,
`fabrication_released`, with the same rule. The flags say what no result of this project is: permission to
run on hardware, a safety sign-off, or a statement about a physical robot (the last is a Reality claim, made
only through the calibration lane).

Where the flags sit, by artifact:

| Artifact | Where the flags sit |
|---|---|
| Build packet `.fbuild` | Manifest root, and in each generated drawing and bill-of-materials header |
| Firmware export (Moonshot) | A constant in the generated crate and in its manifest; the code compiles only against hardware interfaces the caller supplies and never addresses a register, a bus socket or an emergency-stop relay |
| Controller and policy exports (`.fskill`, `train.export`, `control.show --export`) | File header |
| Certificate bundle `.frobcert`, reports, HTML replays | Manifest; visible banner in rendered forms |
| The envelope of every exporting verb | `authorization` |

In code the flags are one type with a single value (decision ADR-SAFE-01: a boolean can be set, a constant
cannot); every schema declares each field as the constant `false`; no verb, flag or configuration produces
`true`. A reader that meets `true`, or an artifact of ours without the fields, treats it as foreign and
refuses it (`FROB-REF-816`); absence is not read as false. Authorizing hardware is a human act that happens
outside this project and leaves no trace in these artifacts.

The type, the schema fragment, the locator registry and the reader-side refusal exist from M1 (N37-23). This
seed bead carries them across **every exporting verb that exists at M3**, adds the visible banner in rendered
forms, fixes the locator contract for the artifact kinds that arrive later, and records the gate for the full
surface. Gate **GATE-SAFE-01** (Known answer, TARGET): every artifact produced by every exporting verb
carries the three fields, all `false`; negative control: an artifact edited to `true`, and one with the fields
removed, are each refused by the importer and by `frob-verify`. It is one of the four recurring gates re-run
at every milestone exit. Invariant INV-SAFE-05: every exported artifact carries the three authorization
flags, each `false`; no code path writes another value. Seed done-condition: GATE-SAFE-01.

## Scope

In: locator rows and flags for every M2 and M3 exporter; the banner text and where it is rendered; header
carriers for binary and container formats; the contract rows for M4, M5 and M8 kinds; the recurring-gate rule;
the M3 record. Out: the type, the schema fragment and the reader check (N37-23); the auditor's rule; the
build packet's writer and fourth flag, the skill artifact and firmware export themselves (their own beads,
which depend on this one); the sweep script (N37-24).

## Technical approach

1. **Rows added for the M2 and M3 surface** (`registries/exports.toml`; each row names verb, kind, format,
   carrier, pointer, spelling and flag count):
   | Verb | Artifact kind | Carrier and place |
   |---|---|---|
   | `telemetry.export-html` | Self-contained replay packet | The header in canonical JSON at the top of the file (`/authorization`), and the banner in the page |
   | `telemetry.stills` (when written to the export root) | Still or contact sheet (an image) | Sidecar `<name>.frob.json`; also an image text chunk `frob:authorization` |
   | `train.export` | Policy file | The checkpoint container's metadata under the key `frob.authorization/1` (the file header), and the policy manifest |
   | `control.show --export` | Controller export | File header object |
   | `report.design`, `report.run`, `report.mission` | Report | Report manifest (`/authorization`); banner in every rendered form |
   | `prove.bundle` | Certificate bundle | `flags` in the bundle; `authorization` in the bundle listing |
   | `artifact.export`, `run.export` | Any stored kind; run bundle | By format: manifest, or sidecar for a view |
   | `design.export` | URDF or MJCF view | Sidecar and head comment |
   | scene pack export | Scene pack | Pack manifest |
   | `eval.qualify`, `eval.ledger` | Qualification receipt | `authorization` in the receipt |
   | `task.verdict`, `eval.scorecard` exports | Verdict record, scorecard | `no_authorization` |
   | `nemesis.shrink` | Minimal counterexample world | `no_authorization` |
   | `scene.purge` | Purge receipt | `authorization` |
   Every one of these verbs also returns `authorization` in its envelope.
2. **Contract rows for later kinds** (written now with `since` set to their milestone, so the sweep expects
   them the day the verb is registered): the skill artifact `.fskill` (M4; file header); the build packet
   `.fbuild` (M5; four flags at the manifest root and in each generated drawing and bill-of-materials header;
   its reader refuses with the manufacturing chapter's code); the replication kit (M5; manifest); the firmware
   export (M8, Moonshot; a constant in the generated crate, `pub const AUTHORIZATION: NoAuthorization`, and in
   its manifest). For the firmware export the contract also records the boundary this chapter sets: the
   generated code compiles only against hardware interfaces the caller supplies and never addresses a
   register, a bus socket or an emergency-stop relay; a source scan of the generated crate for register
   access, bus-driver or stop-circuit code is part of that bead's acceptance.
3. **The banner (DESIGN text, generated from the type so it cannot drift).** In every rendered form of a
   report (plain text, Markdown, HTML), at the top of the self-contained replay page, and on the first line of
   the human-readable output of every exporting verb:
   `Simulation results are not a safety case for a physical robot. execution_authorized: false ·
   hardware_safety_signoff: false · sim_to_real_certified: false`
   (a build packet's rendered documents add `· fabrication_released: false`). The banner is not removable by
   an option, and a report template without it fails the report generator's template lint. It sits beside the
   `reality:` line that every report prints.
4. **Header carriers for non-JSON containers.** A binary container that has a metadata map (the policy
   checkpoint) stores the canonical JSON of the flags object as the value of one registered key; a column file
   of a run bundle carries no flags itself and is covered by the bundle manifest that lists its hash; an image
   carries a text chunk and always has a sidecar. The reader of each container extracts the object and calls
   the shared reader-side check; a container of ours without it is `FROB-REF-816`.
5. **The sweep is milestone-aware and recurring.** The conformance battery `flags` runs every verb that has a
   locator row whose `since` is at or before the current milestone, collects every file written under the
   export root and every envelope, locates the flags by the registry and asserts: present; exactly three (or
   four) fields; each the JSON literal false. A file under the export root that matches no locator row fails
   the sweep. For each artifact kind it then makes two mutants (one flag set to `true`; the object removed)
   and a third (the value `"false"` as a string) and offers each to the importing reader of that kind and, for
   bundle kinds, to `frob-verify`: all must be refused. The exit-review bead of every milestone cites this
   battery's record for that milestone's surface.
6. **Gate record.** Exporting verbs swept (n of n with a row), artifact kinds, artifacts inspected by kind,
   violations (0), mutants refused by the importer (3 per kind) and by the auditor (per bundle kind), banner
   present in rendered forms (n of n), controls caught.

## Acceptance criteria

- [ ] GATE-SAFE-01 on the M3 surface (TARGET): every artifact produced by every exporting verb carries the
      three fields, all `false`; the `true` mutant and the stripped mutant of each kind are refused by the
      importer and by `frob-verify`. Recorded with counts (seed done-condition).
- [ ] Every verb with a non-empty `exports` field has a locator row; every file the sweep finds under the
      export root matches a row.
- [ ] The banner text appears in every rendered report form, in the replay page and in the human-readable
      output of every exporting verb; a template without it fails the lint.
- [ ] A policy file exported by `train.export` carries the flags in its container metadata and its manifest;
      stripping the metadata key makes admission of that file as a checkpoint of this system refuse with
      `FROB-REF-816`.
- [ ] Contract rows exist for the skill artifact, the build packet (four flags), the kit and the firmware
      export, each with its milestone.
- [ ] No verb, command-line option, configuration key or environment variable changes any flag (the
      no-off-switch sweep's flag row passes on the M3 surface).

## Test plan

### Unit tests
`cargo test -p frob-verbs --test exports_m3 -p frob-chronicle --test flag_carriers`:
- `m3_exporters_have_rows` (generated from the registry).
- `replay_header_flags_and_banner`; `still_sidecar_and_text_chunk`; `policy_container_metadata_flags`;
  `report_manifest_flags`; `receipt_flags`; `verdict_no_authorization`; `mcw_no_authorization`;
  `purge_receipt_flags`.
- `banner_text_is_generated_from_type`: the rendered string equals the generator's output for the constant.
- `template_without_banner_fails_lint`.
- `unknown_file_under_export_root_fails_sweep` (a planted stray file).
- `mutants_per_kind_refused`: for each kind, `true`, stripped and string-false → `FROB-REF-816` from the
  kind's reader.
- `contract_rows_present_for_later_kinds`.

### End-to-end script and logging
`scripts/e2e/safe_flags.sh` (N37-24), profile `m3`, against the real `frob`, `frobd` and `frob-verify`
binaries, with the structured logging of STD-E2E: per verb the command line and exit code; per artifact the
kind, digest, carrier, pointer and the three values found; per mutant the reader, the exit code and the
refusal code.

### Known answers and negative controls
KA-828 (an artifact with one flag set to `true` is refused by the importer and by `frob-verify`; exact;
control: an artifact with the fields removed is also refused). Negative controls registered against
GATE-SAFE-01: a fixture exporter that omits the object; one that writes `true`; one that writes `"false"`;
a planted exporting verb with no locator row; a report template without the banner. Metamorphic relation:
the flags object is byte-identical across every artifact kind after canonicalization. Determinism lanes: the
sweep's counts are identical in debug and release and on Linux and macOS.

## Considerations

- The gate recurs at every exit because every milestone adds exporters; a new exporter without a row fails
  the registry test on the day it is added, long before an exit.
- The banner is deliberately redundant with the fields: the fields are for programs, the banner for a person
  who opens a report or a replay.
- A build packet may one day be accompanied by a human review record; that is an imported record with its own
  provenance and changes no flag.
- The risk this serves is the misuse of an export as a permission; nothing here assesses the safety of any
  design, and no report may say otherwise.
