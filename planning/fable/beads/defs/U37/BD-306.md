## Background

Supply chain, in one line: exact pins; admission records with real build evidence; kernel caches checked by
content hash before load. The safety chapter gives six rules.

1. **One runtime package.** Each workspace (the core and every annex) must resolve exactly one `asupersync`
   package; the workspace tool checks it from `cargo metadata`. FACT, 2026-11-21: `fastmcp_rust`'s source tree
   pins 0.6.2 and its registry package 0.13.0 carries 0.5.0; FrankenTorch requires 0.6.2; FrankenSim consumes
   it by path; `ftui-runtime`'s optional executor feature and FrankenThreeD's `f3d-runtime` pin 0.5.0. The
   rule decides which form of each sibling may be linked. The consumed siblings are aligned on one published
   version in their own repositories by the upstream work item FD-ASUP-01, and the admission gate INT-ASUP-01
   proves it.
2. **Pins and locks.** Siblings are pinned by commit, registry crates by exact version. Every workspace
   commits its lockfile and builds with `--locked` on the one toolchain of the build graph. An admission
   record names the commit, the toolchain, the features, the licence and the build log that proves it compiled
   here.
3. **Kernels.** Kernel sources are generated from this repository only. A binary kernel cache is keyed by
   source hash, compiler, driver and hardware fingerprint and is checked by content hash before load; a
   mismatch recompiles and is logged.
4. **The auditor.** `frob-verify` uses the standard library only, so checking a certificate bundle trusts
   none of the dependency graph that produced it.
5. **The viewer.** Three.js is vendored at a pinned version with its hash; an exported replay fetches nothing.
6. **Sibling repositories are changed in place, never patched locally.** A defect found in one becomes an
   admission test here and an upstream work item, done in the sibling's repository under its own gates and
   pinned here by commit through the compatibility train. No local patch or fork stands in for it.

Invariant INV-SAFE-08: each workspace resolves exactly one `asupersync` package, and no kernel loads without
a matching content hash. Gate GATE-SAFE-06 (Known answer, TARGET): one `asupersync` package per workspace;
all lockfiles committed; a kernel cache entry with one flipped byte is refused; `frob-verify` builds with no
dependency outside the standard library. The gate's first record is taken at M2 by the supply-chain script
(N37-22) on mechanisms that exist by then. This seed bead completes the rules that script does not cover
(exact-version pins, `--locked` everywhere, admission-record contents, the type-level guarantee on kernel
loads, kernel provenance, the vendored viewer, the no-local-patch rule) and re-records the gate at M3 over
every workspace that exists then. Seed done-condition: GATE-SAFE-06.

Constraint that shapes the work: the workspace tool has exactly six checks, and a seventh needs a named
defect class and the owner's approval. Everything here is therefore an extension of `check-deps` (dependency
rules), `check-stack` (the stack lock, lockfiles, receipts) or `check-generated` (generated and vendored
files), or a test in the owning crate. No new subcommand is added.

## Scope

In: the six rules as checks and types; the re-record of GATE-SAFE-06 at M3. Out: the M2 measurement script
(N37-22); building the kernel cache itself (device chapter); the auditor crate (certificate chapter); the
asupersync alignment in the siblings (suite chapter); third-party notices (N37-18).

## Technical approach

1. **Exact pins (`check-deps`).** For every manifest of every workspace: a registry dependency's requirement
   must be `=x.y.z` (no caret, tilde, wildcard, range or bare version); a sibling is a path or git dependency
   whose commit is the `git_rev` of its row in `franken-stack.lock`; a git dependency without `rev` fails; a
   dependency source other than the default registry or a listed sibling fails. The single-runtime rule is
   evaluated per workspace and per binary target from `cargo metadata`, and no `asupersync` 0.5.0 may appear.
   The forbidden feature of `ftui-runtime` (its executor) and any edge to `f3d-runtime` fail the check.
2. **`--locked` everywhere (`check-stack`).** Every lockfile is tracked. The check scans the repository's
   scripts, the workspace tool's own command lines, `.cargo/config.toml` aliases and the end-to-end helper for
   invocations of cargo's build, check, test, run, tree and metadata commands and fails on one without
   `--locked` (the helper exposes one function for cargo calls, so the scan has one place to look). A build
   that would modify a lockfile fails instead.
3. **Admission records (`check-stack`).** `DEPENDENCY_ADMISSION.md` carries one machine-readable block per
   admitted foundation and per admitted third-party crate (DESIGN, TOML inside a fenced block):
   ```toml
   [[admission]]
   id = "FD-FMCP"                       # or the crate name for a registry crate
   gate = "INT-FMCP-01"
   repo_commit = "<this repository's commit>"
   source = "git:<url>@<40 hex>"        # or "registry:<name>@=<version>"
   toolchain = "<T>"
   features = ["…"]
   licence = "MIT"
   licence_text = "b3:<digest of the recorded licence text, required when the licence has a rider>"
   command = ["cargo", "test", "--locked", "-p", "…"]
   build_log = { path = "receipts/logs/<hash>.log", hash = "b3:…" }
   receipt = "b3:<resolution receipt hash>"
   ```
   Validation: every field present; `repo_commit` is an ancestor of `HEAD` whose tracked lockfile contains the
   source at that commit or version (the rule that an admission is valid only if the dependency was really in
   the build); `build_log` exists and hashes to the stated value; `receipt` names a file under `receipts/`.
   Every package in every lockfile that is not a member of this repository maps to exactly one admission
   block, directly or as part of a foundation's recorded closure; an unmapped package fails.
4. **Kernels: provenance and verified loads.**
   - Provenance: every kernel the build can launch has a `KernelId` in the kernel registry embedded at build
     time, whose source is generated from this repository at this commit (the generated-file check already
     regenerates and compares digests). No verb or configuration key names a kernel file; the cache directory
     is the only place binaries are read from.
   - Verified loads (DESIGN): the device loaders take only a `VerifiedKernel`, a type whose sole constructor
     is `KernelCache::fetch(key) -> Result<VerifiedKernel, Miss>`, which recomputes the BLAKE3 of the entry's
     bytes and compares it with the digest stored under the key before returning. A mismatch is a miss:
     it writes an event `kernel-cache-mismatch {key, expected, observed, path}` to the job log and the ledger,
     quarantines the bad file under `<cache>/quarantine/<observed digest>` and triggers recompilation; if
     recompilation is unavailable the run refuses with `FROB-REF-612`. Because the loader cannot be handed raw
     bytes, "no kernel loads without a matching content hash" is enforced by the type and pinned by a
     compile-fail test.
   - The key (owned by the device chapter, restated because the gate depends on it): BLAKE3 over the expanded
     dialect text, compile options, prelude version, compiler identity, device architecture and driver
     version. An entry copied from a host with another fingerprint has another key and is never looked up.
5. **Auditor.** `check-deps` asserts the auditor crate's manifest has an empty dependency table of every kind
   and that only the three permitted crates depend on it.
6. **Viewer (`check-generated`).** `viewer/vendor/VENDOR.toml` lists each vendored file with name, version
   (Three.js r186), source, licence and BLAKE3. The check hashes the files and compares. A static scan of the
   viewer page and of every exported replay fixture fails on any remote reference: `http://` or `https://` in
   a `src`, `href`, `import`, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` or CSS `url()`; a
   protocol-relative URL; a `<link rel="preconnect">`. The dynamic half (the page opened from a local file
   with the network disabled, zero requests) is the replay-packet gate's test and is cited in the record.
7. **No local patches (`check-stack`).** The resolution receipt lists every `[patch]` entry. Allowed: a patch
   that redirects a sibling to its checkout listed in the stack lock (for example `asupersync` to its sibling
   path, and FrankenTorch's own patch repeated at the Metal annex root). Refused: a patch whose target lies
   inside this repository; a `vendor/` or `third_party/` directory containing a crate whose name matches a
   sibling's crate; a copied sibling source file not recorded in `registries/lifts.toml` (the registry used
   only by the last-resort fallback that lifts a minimal referee set). A sibling defect is recorded as an
   admission test here plus an upstream work item bead labelled `upstream`.
8. **Re-record at M3.** Run the supply-chain script on the M3 tree; workspaces now include the terminal
   dashboard, the Gymnasium-compatible bindings and the full MCP surface; append the results of steps 1 to 7.

## Acceptance criteria

- [ ] GATE-SAFE-06 at M3 (TARGET): one `asupersync` package per workspace, all lockfiles committed, a flipped
      cache byte refused, `frob-verify` with no dependency outside the standard library, on every workspace
      present; recorded with counts (seed done-condition).
- [ ] `check-deps` fails on a planted caret requirement, a git dependency without `rev`, a second
      `asupersync`, the `ftui-runtime` executor feature, and a dependency added to the auditor crate.
- [ ] `check-stack` fails on a cargo invocation without `--locked` in a script, an untracked lockfile, an
      admission block missing `build_log` or `licence`, an admission whose `repo_commit` lockfile lacks the
      dependency, a lockfile package with no admission, and a `[patch]` to a directory inside the repository.
- [ ] A device loader cannot be called with unverified bytes (compile-fail test); a flipped entry is
      quarantined, logged and recompiled, and the run's digest is unchanged.
- [ ] `check-generated` fails when one byte of the vendored Three.js file changes, and the static scan fails
      on a replay fixture containing a remote script reference.
- [ ] The subcommand-count test of the workspace tool still reports six.

`cargo test -p xtask` and `-p frob-kernels --test verified_kernel` (planted trees are `synthetic` copies in a
temporary directory):

- `git_dep_needs_stack_lock_rev`.
- `single_runtime_per_workspace_and_binary`.
- `forbidden_feature_fails`; `auditor_dependency_fails`.
- `script_without_locked_fails`; `untracked_lockfile_fails`.
- `admission_block_fields_required`; `admission_commit_must_contain_dependency`;
  `every_locked_package_has_admission`.
- `patch_into_repo_fails`; `vendored_sibling_crate_fails`; `lift_must_be_registered`.
- `verified_kernel_only` (compile-fail: a loader call with `&[u8]`).
- `flipped_entry_is_miss_logged_quarantined`: a `synthetic` entry, bit 0 of the middle byte flipped → a miss,
  one event with both digests, the file moved to quarantine.
- `foreign_fingerprint_entry_never_looked_up`.
- `vendor_hash_mismatch_fails`; `remote_reference_scan` (eight planted forms, each caught).
- `xtask_has_six_subcommands`.

### End-to-end script and logging
`scripts/e2e/safe_supply_chain.sh` (N37-22), re-run at M3 with an added step `m3_rules` that runs the three
workspace checks and, in scratch copies, each planted violation above, logging per STD-E2E the command line,
exit code, the check that caught each plant (exactly one check per plant) and the gate summary.

### Known answers and negative controls
KA-833 (one `asupersync` package per workspace; all lockfiles committed; `frob-verify` builds with no
dependency outside the standard library; exact; control: a kernel cache entry with one flipped byte is
refused). Negative controls: every planted violation in the unit tests; a `mutants` loader that accepts raw
bytes (the compile-fail test must then compile and so fail the suite). Each plant must be caught by the check
that owns it and by no other, as the workspace chapter requires of its own plants. Determinism lanes: check
results identical on Linux and macOS.

## Considerations

- Path dependencies on the simulation foundation bring its transitive closure, which includes third-party
  registry crates; "one admission per package" is satisfied for those by the foundation's recorded closure at
  its pinned commit, hashed in the receipt, and not by hand-written blocks per crate.
- A dirty sibling tree admits development builds only; no gate records a pass on one. `check-stack` never
  moves a sibling checkout.
- The quarantine directory is capped with the cache; a quarantined file is evidence for a hardware or
  transfer fault report and is never loaded.
- If the kernel toolchain's kill gate fires and kernel arithmetic becomes hand-written, "generated from this
  repository only" still holds: the sources are in the repository and the registry, and the verified-load
  rule is unchanged.
- The seed lists this bead at M3 while the gate's first date is M2; the M2 record is N37-22's.
