## Background

**Imports are hostile input.** A robot description (URDF, MJCF) and the mesh files it references come from the
network, from another tool, or from an agent that was handed them. The threat model lists "a hostile imported
file" among the in-scope threats to the owner's machines. The rule: the URDF, MJCF and mesh importers are safe
Rust with limits on size, nesting depth and polygon count, a violated limit is refused with `FROB-REF-832`,
each importer has a fuzz target, and an import always returns a loss report (the list of fields dropped,
defaults filled and elements not supported).

Facts the design rests on (DESIGN of the import chapter, restated): the XML reader is in-house, reads elements
and attributes only, and refuses document-type declarations and entities, so entity-expansion attacks have no
mechanism to use; macros are expanded outside (no xacro, no script found in a model is ever executed; the
importer records the hash of the expanded document and the name of the tool the user says produced it);
relative references resolve only inside the import root.

Why limits are a registry and not constants: a refusal must be able to say which limit was hit, what was
observed, and how the owner raises it deliberately. Rejected alternatives: best-effort import that truncates a
mesh or drops deep elements (silent loss; the standing rule is refuse, never truncate); a `--max-size` verb
flag (an agent-reachable switch; limits change only through the owner-held configuration).

Gate served: GATE-SAFE-07 (Known answer, TARGET, earliest M2): at least 10⁷ fuzz executions per importer with
no panic; each limit is reached by a crafted file and refused. This bead builds the limits, the corpus and the
targets; the campaign and the gate record are N37-06 (M2) and BD-307 (complete surface, M3).

## Scope

In: the design-importer rows of the import profile registry; bounded decoding in the XML reader, the URDF and
MJCF mappers and the mesh readers; `FROB-REF-832` with its fields and repairs; the generator of at-limit and
over-limit files; the fuzz target functions and the in-house seeded driver with a smoke budget; the rule that
every import path ends in a loss report or a refusal. Out: the importers' mapping logic and loss-report schema
(BD-065, BD-066); the scene compiler's decode limits and `FROB-REF-303` (the scene chapter); weight files
(N37-07); the 10⁷ campaign (N37-06); path confinement of references (N37-11).

## Technical approach

1. **Profile rows (DESIGN defaults; `registries/import-profiles.toml`, profile `default`).** The profile name
   comes from the owner-held configuration key `import.profile`; the profile's digest enters the import
   receipt.
   | Importer | Limit | `default` | `fuzz` profile |
   |---|---|---|---|
   | `xml` | `max_bytes` | 67,108,864 (64 MiB) | 4,096 |
   | `xml` | `max_depth` (element nesting) | 64 | 8 |
   | `xml` | `max_elements` | 2,000,000 | 256 |
   | `xml` | `max_attrs_per_element` | 256 | 8 |
   | `xml` | `max_children_per_element` | 65,536 | 32 |
   | `xml` | `max_attr_bytes` (raw attribute value) | 65,536 | 128 |
   | `mjcf` | `max_includes`, `max_include_depth` | 256, 8 | 4, 2 |
   | `mesh` | `max_bytes` per file | 268,435,456 (256 MiB) | 4,096 |
   | `mesh` | `max_polygons` per mesh | 5,000,000 | 64 |
   | `mesh` | `max_meshes` per import, `max_total_polygons` | 4,096; 20,000,000 | 4; 128 |
   Profiles `default`, `large-building` and `fuzz` ship (the same three names the scene compiler uses).
   Values are DESIGN defaults recorded with their reason and confirmed against the reference robots at the
   first import parity run.
2. **Bounded decoding.** One `Budget` value per import carries the profile and running counters. Rules: a
   counter is incremented before the work it counts; the decoder stops at the first exceeded limit; no
   allocation is sized from a length field before the field has been checked against the profile (binary STL
   declares a triangle count in bytes 80 to 83: the reader checks `count ≤ max_polygons` and
   `84 + 50·count = file size` before reserving anything); parsing is iterative with an explicit stack, so
   depth is bounded by the profile and not by the call stack; include files count against `max_bytes` in
   total. Mesh readers (`frob-io::mesh`): binary and ASCII STL and OBJ; every other mesh container goes
   through the scene decoder under its own profile.
3. **The refusal.** `FROB-REF-832`, "an import over its size, depth or polygon limit". Exit 3;
   `retry: after-change`. Fields: `pointer` (file digest, and line and column or byte offset), `observed`,
   `required` (the limit value), `unit` (`bytes`, `levels`, `elements`, `polygons`, …), plus `limit` (the
   registry key) and `profile` (name and digest). Ranked repairs (DESIGN): (1) reduce the input: decimate the
   mesh below the polygon limit, prune or split the document; (2) expand macros outside and remove generated
   duplication; (3) ask the owner to select a larger import profile in the owner-held configuration. Nothing is
   imported on refusal: no design, no partial mesh in the store.
4. **Loss report always.** Every importer entry point returns `Result<(Imported, LossReport), Refusal>`: the
   type makes "an import with no loss report" unrepresentable. An empty report is written with its lists
   present and empty, and with the counts of sanitized and truncated strings from the untrusted-text type.
   Elements that request code execution in other tools (plugin elements, script hooks) are never loaded; they
   are loss-report entries of kind `unsupported: executable-extension`, and under `--strict` the import refuses
   with the import chapter's unsupported-element code.
5. **Crafted limit corpus.** A deterministic generator (`crates/frob-io/tests/limit_corpus.rs`, seed-free) writes,
   for every row of the table, a file exactly at the limit and a file one unit over, under both `default`-sized
   logic (using the `fuzz` profile's small values so the files are tiny) and one `default`-profile case per
   importer for bytes. Depth: nested `<a>` elements; elements: siblings; attributes: `a0="" … aN=""`;
   attribute bytes: one value of length L; polygons: a binary STL whose header declares L triangles with a
   body of matching size; a lying STL (declared count 4,294,967,295, body 84 bytes); includes: a chain and a
   fan. Files are labelled `synthetic`.
6. **Fuzz targets.** One function per importer in `crates/frob-io/fuzz_targets/`:
   `xml_reader(&[u8])`, `urdf_import(&[u8])`, `mjcf_import(&[u8])` (includes served from an in-memory root),
   `stl_reader(&[u8])`, `obj_reader(&[u8])`. Each runs the real code under the `fuzz` profile and asserts the
   oracle: the call returns `Ok` with a loss report or `Err` with a registered refusal; no panic; no call
   longer than 1 s; peak allocation at most 64 times the input length plus 1 MiB (measured by a counting
   allocator in the test binary); on `Ok`, the produced design passes the canonical round trip.
   Driver (DESIGN): `frob-conformance::fuzz`, standard library only, a seeded mutational engine (bit flips,
   byte insertions and deletions, splices between corpus entries, dictionary tokens such as `<robot`, `<link`,
   `<joint`, `<mujoco`, `<include`, `solid`, `facet`, `v `, `f `, long digit runs, deep nesting generators)
   whose stream is a counter-based function of (seed, target, execution index), so any failing execution is
   reproduced from three integers. The seed corpus is the reference robots plus the limit corpus. An optional
   coverage-guided engine may drive the same target functions from a separate `fuzz/` workspace if its
   development-only dependency is admitted; it adds executions and never replaces the seeded lane.
   Smoke budget in the ordinary test run: 10⁵ executions per target (TARGET: under 60 s per target on 8
   cores).
   **Command forms (declared here; BD-025's rule for harness drivers: there is no `frob-conformance` binary,
   and a driver whose code lives in another crate is an example of that crate).** Two example targets, each a
   thin argument parser over the library code above that exits non-zero when its own assertions fail:
   `crates/frob-io/examples/gen_limit_corpus.rs`, run as `cargo run -p frob-io --example gen_limit_corpus --
   --out <dir>` (writes the files of step 5 through the same generator function `limit_corpus.rs` calls, names
   each file by its digest, and prints one JSON object listing (limit key, at/over, digest)); and
   `crates/frob-conformance/examples/fuzz.rs`, run as `cargo run -p frob-conformance --example fuzz --
   --target <t> --executions <N> --seed <s> [--jobs <J>] [--range a..b]` (drives one target through
   `frob_conformance::fuzz`; one progress line per 10⁶ executions on standard error; one JSON object on
   standard output with `executions`, `panics`, `timeouts`, `oracle_violations`, `max_alloc_ratio` and
   `unique_refusal_codes`).
7. **Classes.** D0: a refusal is a function of the bytes and the profile. Imports create Estimated leaves for
   every filled default (the import chapter's rule); nothing here raises a class.

## Acceptance criteria

- [ ] For every limit row, the at-limit file imports (or parses) and the one-over file is refused with
      `FROB-REF-832`, exit 3, `observed = limit + 1`, the limit key and the profile digest.
- [ ] The lying STL (declared 4,294,967,295 triangles in an 84-byte file) is refused without allocating more
      than 1 MiB.
- [ ] 10⁵ depth-nested elements are refused by the depth limit with no stack overflow.
- [ ] Every importer entry point has the `Result<(Imported, LossReport), Refusal>` shape (a compile-time
      signature test), and an import of a clean file returns a loss report with all lists present.
- [ ] A document with a plugin or script element imports with a loss-report entry
      `unsupported: executable-extension`; nothing is executed or loaded.
- [ ] Each of the five fuzz targets survives the smoke budget with the oracle intact; a failing execution
      index replays to the same failure.
- [ ] No limit can be changed by a verb argument (asserted by the no-off-switch sweep of N37-02).

## Test plan

### Unit tests
`cargo test -p frob-io --test limits --test limit_corpus --test fuzz_smoke`:
- `limit_<key>_at_and_over`: one test per limit key of the table (12 keys: six of `xml`, two of `mjcf`, four
  of `mesh`), each asserting acceptance at L and `FROB-REF-832` with `observed = L + 1` at L + 1.
- `stl_declared_count_checked_before_alloc` (counting allocator: peak under 1 MiB).
- `depth_bomb_no_overflow`.
- `includes_count_against_total_bytes`: two includes of 3,000 bytes under the `fuzz` profile exceed 4,096.
- `refusal_imports_nothing`: after a refused import the store holds no new object (digest listing equal).
- `loss_report_always_present`.
- `executable_extension_listed_not_loaded`.
- `fuzz_smoke_<target>`: 10⁵ executions each, seed 1.
- `fuzz_replay_is_deterministic`: executions 0 to 999 of seed 7 give identical inputs twice.

### End-to-end script and logging
This bead creates `scripts/e2e/safe_importers.sh` (plain shell, sourcing the shared helper of STD-E2E) with
its M1 steps: `gen_corpus` (write the at-limit and over-limit files with `cargo run -p frob-io --example
gen_limit_corpus -- --out target/e2e/safe_importers/corpus`), `limits_design` (each file through
`frob --json design import`: exit 0 or 2 with a loss report at the limit; exit 3 with `FROB-REF-832` and
`observed = limit + 1` over it; the store listing unchanged after a refusal), `code_payloads` (the eight
code-bearing signatures and the over-bound expression of the data-not-code bead: exit 3 with `FROB-REF-828`
or the bound), and `fuzz_smoke` (10⁵ executions per target through `cargo run -p frob-conformance --example
fuzz -- --target <t> --executions 100000 --seed 1`). It logs to
`target/e2e-logs/safe_importers/<utc-timestamp>.ndjson`, per the helper: the command line, exit code, wall
time, the envelope's `evidence` block, refusal code, `limit`, `observed`, `required`, the profile digest, and
one `metric` line per fuzz target with executions, panics, timeouts and worst allocation ratio against their
thresholds; a `summary` with counts. The M2 bead N37-06 adds the scene rows, the 10⁷ campaign, the memory
measurement, the planted defects and the gate record to the same script.

### Known answers and negative controls
Known answers: `observed = L + 1` for every row; 84 + 50·count = file size for binary STL. Negative controls
(each must be caught): a `mutants` build with the polygon check removed fails its row; a build whose STL
reader reserves from the declared count fails the allocation test; a planted `unwrap()` on a malformed
attribute is found by the smoke fuzz within 10⁵ executions (the planted defect is registered against
GATE-SAFE-07). Determinism lanes: refusal fields identical on Linux and macOS and in debug and release; the
fuzz input stream identical across worker counts.

## Considerations

- Limits that are too tight refuse real robots; the reference robots are imported under `default` as part of
  the import parity gate, which is the check that the defaults are not absurd.
- The in-house driver is coverage-blind. It is deterministic and dependency-free, which the gate needs; the
  optional guided engine is where deep parser bugs are more likely to be found, and its use is a dependency
  decision recorded in the admission file, never a link into a shipped binary.
- Memory: decode of a file at the byte limit stays within a stated multiple of the input (TARGET 4 times for
  XML, 2 times for meshes; measured and recorded by N37-06).
- Scene files hit the scene chapter's `FROB-REF-303` for the same class of event; the two codes are kept
  because they have different owners and repairs, and both are listed in the refusal registry.
