## Background

GATE-SAFE-07 (claim: Known answer; TARGET; earliest M2): **at least 10⁷ fuzz executions per importer with no
panic; each limit is reached by a crafted file and refused.** The gate register dates it to M2, the milestone
at which the design importers (URDF, MJCF, meshes) and the scene compiler's source decoder all exist. The
seed bead for importer fuzzing sits at M3 and closes the gate over the complete surface; this bead is the M2
measurement, so that the M2 exit review has a recorded value and a caught negative control.

It is also the end-to-end script of the capability "an agent imports a file": everything is driven through the
real `frob` binary on real files, from the user's side. A gate that nothing can fail validates nothing, so the
script also runs two planted defects that must be caught.

## Scope

In: the script in its gate form. Its M1 steps (corpus generation, design-importer limits, code payloads, the
smoke fuzz) were created with the limits themselves (N37-05), and its `weights` step with the weight reader
(N37-07); this bead adds the scene rows, the long fuzz campaign under the default compute envelope (the
weight reader included), the memory-at-limit measurement, the two planted defects, minimization and
registration of any crash, and the gate record at M2. The full step list is given below so that the script is
specified in one place. Out: the limits, targets and driver (N37-05); the weight reader, its caps and its
specimen step (N37-07); the allowlist decision (N37-08); the scene decoder (scene chapter); importers that
arrive at M3 (BD-307).

## Technical approach

`scripts/e2e/safe_importers.sh [--long] [--seed N] [--jobs J]` (plain shell; sources the shared helper of
STD-E2E; idempotent; default seed 1; default `--jobs 8`, inside the default compute envelope of 16 GiB, 8
cores, 1 hour). Without `--long` each fuzz target runs 10⁵ executions so the script is usable in an ordinary
test run; the gate record requires `--long` (10⁷ per target).

Steps (every call of a `run` or `mutate` verb below, `design import`, `scene compile`, `task new` and
`eval run` included, carries `--key "$(e2e_key <step>-<digest>)"`, STD-E2E's key helper; without a key the
call is `FROB-REF-805`):

1. `build`: `cargo build --release -p frob-cli -p frob-conformance` (the script records the binary's stack
   receipt hash from `frob doctor --json`).
2. `gen_corpus`: `cargo run -p frob-io --example gen_limit_corpus -- --out target/e2e/safe_importers/corpus`
   (N37-05's example; there is no `frob-conformance` binary) writes the
   at-limit and over-limit files of every limit row (design importers: bytes, depth, elements, attributes per
   element, children per element, attribute bytes, includes, include depth, mesh bytes, polygons per mesh,
   meshes per import, total polygons), plus the lying STL (declared count 4,294,967,295 in 84 bytes). All
   files are `synthetic`.
3. `limits_design`: for each pair, `frob --json design import <file> --key "$(e2e_key limits-<digest>)"`.
   Assertions: at-limit → exit 0 or 2, `result.loss_report` present with every list present; over-limit →
   exit 3, `refusal.code = FROB-REF-832`, `refusal.observed = limit + 1`, `refusal.required = limit`, the
   limit key and profile digest present; `frob --json artifact list` before and after an over-limit import
   returns the same digests (nothing partial imported).
4. `limits_scene`: the scene chapter's at-limit and over-limit sources through `frob --json scene compile`;
   over-limit → exit 3 with the scene decode refusal `FROB-REF-303` naming the limit.
5. `code_payloads`: eight files with registered extensions whose first bytes are the signatures of an ELF
   file, a Mach-O file, a portable executable, a WebAssembly module, a script with an interpreter line, a
   pickle stream, a zip archive and compiler bitcode → exit 3, `FROB-REF-828`, `observed` naming the kind; and
   `frob --json task new` with a 4,097-node expression → exit 3 with the bound quoted.
   `weights` (the step N37-07 created; listed here so the step list is complete): `frob --json eval run
   <design> --policy <file> --battery smoke --key "$(e2e_key w-<digest>)"` (the policy form needs a population, else
   `FROB-REF-802` before admission) on an admitted checkpoint and on each refused weight specimen (pickle, zip, HDF5, NumPy,
   trailing bytes, gap, overlap, NaN, infinity, extra and missing tensor, unlisted family, unknown metadata
   key: exit 3 with `FROB-REF-828` and its `observed`; the three caps one over: `FROB-REF-832`), and the
   origin cases (a GRU trained here and passed back: admitted; the `synthetic` outside GRU: refused under
   the allowlist in force).
6. `fuzz_campaign`: for each target in `xml_reader`, `urdf_import`, `mjcf_import`, `stl_reader`, `obj_reader`,
   `scene_decode`, `weights_reader` (the last on the weight allowlist in force at the M2 exit: the OPEN-SAFE-1
   decision, or its default recorded as "default adopted"; N37-08): `cargo run --release -p frob-conformance
   --example fuzz -- --target <t> --executions <N> --seed <seed> --jobs <J>` (N37-05's example). The driver
   prints one progress line per 10⁶ executions on standard error and, on standard output, a final JSON object
   with `executions`, `panics`, `timeouts` (over 1 s), `oracle_violations`, `max_alloc_ratio` and
   `unique_refusal_codes`, which the script saves under `target/e2e/safe_importers/campaign/<target>.json`
   with the range list. Assertions: `executions ≥ N`;
   `panics = 0`; `timeouts = 0`; `oracle_violations = 0`; `max_alloc_ratio ≤ 64`.
   Budget (TARGET): at most 7 minutes per target at 10⁷ on 8 cores (about 336 µs of single-core time per
   execution: 7 × 60 s × 8 cores / 10⁷). One invocation of the script stays under 55 minutes, inside the
   one-hour envelope; when the seven targets together would exceed that, `--long` splits the campaign into
   invocations over disjoint index ranges of the same seed (`--range a..b`), each inside the envelope, and the
   record sums them (`executions = Σ ranges`, the ranges listed). A campaign is never shortened.
7. `memory_at_limit`: import the `default`-profile at-limit XML (64 MiB) and mesh (256 MiB) under
   `/usr/bin/time`; record peak resident memory. TARGET: at most 4 times the input for XML and 2 times for a
   mesh, and under 16 GiB in any case.
8. `planted_defects` (builds with `--features gauntlet-mutations`, the feature that builds planted defects,
   convention 1): (a) a planted `unwrap()` on a malformed attribute:
   the campaign at 10⁵ executions must report at least one panic and write a minimized reproducer; (b) the
   polygon check removed: step 3's polygon row must fail. The step passes only if both defects are detected.
9. `receipt` (on `--long`): `e2e_tier g4_chaos GATE-SAFE-07 --mutations` (STD-E2E: `FROB_TEST_SEED=$SEED
   cargo test -p frob-conformance --test g4_chaos --features gauntlet-mutations -- GATE-SAFE-07`). The gate's
   entry reads the campaign summaries of step 6 by digest, re-executes a seeded sample of 10⁴ indices per
   target and every stored reproducer (so the totals are shown reproducible from (seed, target, index)),
   re-checks every limit row through the importer functions, and runs the registered controls; its one
   hash-named receipt carries the per-importer executions and zero counts, the limit rows refused of rows
   tested and the controls caught. The script asserts from it (`e2e_get --file "$E2E_LAST_RECEIPT"`) that the
   counts equal steps 3 to 8 and every control is `caught`. The script records nothing.

**Recording (not part of the script; one recorder).** This bead records the M2 part of GATE-SAFE-07 (BD-307
records the complete surface at M3). A session that did not implement the importers or N37-05 enters it from
the receipt with `cargo run -p frob-conformance --example record_gate -- --gate GATE-SAFE-07 --receipt <hash>
--part M2`; the recorder refuses a pass when a registered control was not run or not caught.

**Crash handling.** A failing execution is identified by (seed, target, index); the driver re-runs it,
minimizes it by delta debugging to a local minimum, stores it under
`crates/frob-io/fuzz_corpus/regressions/<target>/<digest>` and adds it to the regression list that the
ordinary unit tests replay. A crash is a FAIL of the gate, and the reproducer becomes a permanent negative
control with the fix.

**Logging (the shared helper).** Newline-delimited JSON at
`target/e2e-logs/safe_importers/<utc-timestamp>.ndjson` and a transcript beside it. Every line: `ts`,
`script`, `bead` (`N37-06`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed), measured values with units and thresholds, digests where store state is compared, and on
failure the first differing value with the artifact paths (the corpus file, the reproducer). Final `summary`:
assertions passed and failed, and `gates: ["GATE-SAFE-07"]`. File contents of the corpus are never logged;
files are named by digest.

## Acceptance criteria

- [ ] `safe_importers.sh --long` exits 0 on a clean build and its `g4_chaos` receipt carries GATE-SAFE-07 with:
      at least 10⁷ executions for each of the seven importers, zero panics, zero timeouts, zero oracle
      violations; every limit row reached by a crafted file and refused (TARGET).
- [ ] No script line runs `frob-conformance` as a command (`no_conformance_command` passes on the script).
- [ ] The same script exits non-zero when run against the `gauntlet-mutations` build without the `planted_defects`
      expectation (that is, the planted panic is found and the missing polygon check is caught).
- [ ] Over-limit imports leave the store unchanged (digest listings equal before and after).
- [ ] Peak memory at the byte limits is recorded and within the stated multiples.
- [ ] The run fits the default compute envelope; the log's `summary` names the gate; the record is written by
      a session that did not implement the importers.

## Test plan

### Unit tests
The script's own pieces are tested without the long campaign: `cargo test -p frob-conformance --test
fuzz_driver`: `driver_stream_is_counter_based` (execution i of seed s is the same input whatever `--jobs`
is); `minimizer_reaches_local_minimum` on a synthetic failing predicate ("contains bytes 3C 21"): the result
is 2 bytes; `tier_entry_refuses_altered_summary` (a campaign summary with one count changed after it was
written fails the gate entry's digest and sample check, so the receipt cannot carry it).

### End-to-end script and logging
This bead is the script. Quick mode (`safe_importers.sh`) is part of the ordinary end-to-end suite; `--long`
is run for the gate at the M2 exit and again at every later exit that adds an importer.

### Known answers and negative controls
Known answers: `observed = limit + 1` for every limit row; 0 panics in 7 × 10⁷ executions; the 2-byte
minimizer result. Negative controls registered against GATE-SAFE-07: the planted `unwrap()`; the removed
polygon check; an STL reader that reserves from the declared count (caught by `max_alloc_ratio`). Metamorphic
relation: permuting the order of the limit files changes no verdict. Determinism lanes: the campaign's final
line is identical for the same (seed, executions) twice on one machine and with `--jobs 1` and `--jobs 8`;
refusal fields are identical on Linux and macOS.

## Considerations

- 7 × 10⁷ executions at a few microseconds to a few hundred microseconds each fit the envelope; if a target is
  slower than about 336 µs of single-core time per execution on average (10⁷ executions in 7 minutes on 8
  cores) its campaign is split across invocations with disjoint index ranges, and the record sums them. It is
  never shortened.
- The seeded engine is deterministic and coverage-blind; if the optional coverage-guided engine is admitted its
  executions are recorded in a separate column and do not replace the seeded count.
- The gate re-runs whenever an importer or a limit changes; BD-307 extends it to the importers that arrive at
  M3 and hands the corpora to the conformance batteries.
- The weight allowlist (OPEN-SAFE-1, owner: the learning lead) blocks this gate in the register, so the
  weight reader is part of the M2 record: it is fuzzed on the allowlist in force at the M2 exit, which is the
  decision or, failing one, the fail-closed default (the single layout and family of the reference policy)
  recorded as "default adopted". Any later allowlist row re-runs the `weights_reader` campaign (BD-307 at M3).
