## Background

In the first version an agent submits data: designs, task specifications, controller configurations and policy
weights. It cannot submit kernels or arbitrary programs (INV-SAFE-01: no verb accepts a kernel, a program or an
expression outside the closed language). Reward terms are expressions in the closed, total requirement
language: bounded size, no loops, no recursion. The safety chapter records one possible widening and assigns
it tier **Frontier**: *sandboxed custom reward terms*, that is, a reward term supplied as a small program that
runs inside a sandbox.

**OPEN-SAFE-3.** *Whether sandboxed custom reward terms (Frontier) are admitted, and in what sandbox.* Owner:
the project owner. Blocks: M4 (the milestone whose task families and co-design campaigns would be the first
users). **Fail-closed default: not admitted; the closed expression language only.**

The project's hygiene rule for Frontier work applies: a Frontier mechanism states its ceiling before any test
and names a paper-scale pilot with a falsifier that must be on record before the work is funded. No pilot
has been named for this item, because under the default nothing is built. This bead therefore carries both the
decision and the definition of the pilot that must run first if the owner leans towards admitting.

Why the default is the right resting state. A verdict never depends on a reward term (a verdict is a pure
function of the trace and the task identity), so custom reward code can never strengthen evidence; it can only
make training more convenient. Against that small gain stand: a new input kind that is code; a sandbox whose
escape is a defect class this project has otherwise designed out; and determinism (a reward evaluated outside
the batched kernels breaks the device-resident loop or the class-D2 replay of training).

## Scope

In: the options and their costs; the ceiling; the pilot with its falsifier; the conditions any admitted form
must satisfy; the record of the decision (the ADR and the register row of OPEN-SAFE-3); the kill condition
named in advance. This bead is the decision bead of OPEN-SAFE-3. Out: the page that puts this question to the
owner in one group with OPEN-SAFE-2, OPEN-SAFE-4 and OPEN-CHRON-4, the validator of owner ADRs (a relaxing
answer names its option and, for a general sandbox, the sandbox), the generated record
`registries/policy/data-policy.toml` and the cross-check that the capability report equals it (the owner
packet N41-11, on which this bead depends); building any sandbox (no
bead exists for it; one is created only by a decision to admit, and depends on the pilot bead that the same
decision creates); the requirement-reward pilot of the task chapter, which compares reward terms inside the
closed language.

## Technical approach

1. **Options.**
   | Option | What an agent submits | Runs where | Main cost |
   |---|---|---|---|
   | A (default) | Expressions in the closed language only | Batched kernels on every tier | None; a term the language lacks cannot be written |
   | B | Requests for new operators, added to the language by a reviewed change | As A | Review time per operator; the language grows |
   | C | A straight-line program in the kernel intermediate representation, as data: typed, dimension-checked, no loops, bounded node count | Batched kernels on every tier, like a generated kernel | A new submission path into kernel generation; the kernel-cache key and the task identity must include the term's bytes |
   | D | Byte code for a general sandbox with a fuel limit and no host calls | The host CPU, per step, outside the device loop | A second execution model; reward leaves the device; class D2 for training is lost on devices |
   Options B and C keep the property that inputs are total and bounded; C is "code" only in the sense that a
   requirement expression is. Option D is the only one that needs a sandbox in the usual sense.
2. **Ceiling, stated before any test.** No decision-time gain can be claimed: reward terms never enter a
   verdict. The benefit is bounded by the share of task definitions agents want to write that the closed
   language cannot express; if that share is small, B covers it at lower risk.
3. **The pilot (paper scale, no code).** Take at least 30 task definitions: the task families of the
   evaluation chapter through M4 and public locomotion and manipulation task definitions from the source
   register. For each reward term, classify it as (i) expressible in the closed language today, (ii)
   expressible after adding one total operator, (iii) expressible as a bounded straight-line program,
   (iv) needing loops, state beyond the declared signals, or external calls. Record the table and its counts.
   **Falsifier:** if class (iv) is under 10% of terms and classes (iii) plus (iv) are under 25% (TARGET
   thresholds, fixed before counting), the mechanism is not funded and option A or B stands. The pilot's
   output is a table with sources, one line per term; it takes no compute.
4. **Conditions on any admitted form** (they hold for C and D alike and would be written into the mechanism
   bead's acceptance):
   - reward only: a submitted term can never be a requirement, a success predicate or a metric;
   - total and bounded: a static bound on operations per world-step, checked before admission;
   - dimensionally homogeneous, by the same checker as kernels;
   - deterministic under the profile in force, and subject to the same bans as every batched kernel (no
     fast-math relaxation, no fused multiply-add, no built-in transcendental, no floating-point atomic);
   - no input other than the task's declared signals; no output other than one scalar per world;
   - its bytes enter the task identity and the kernel-cache key; results under it carry a condition flag
     `custom-reward`, joined by union like every other condition, and a result carrying the flag is excluded
     from qualification (the consequence the owner page of N41-11 states and the owner accepts by admitting);
   - for option D the ADR names the sandbox and its five properties: process isolation, no network, no file
     system, a time and memory cap, deterministic arithmetic;
   - there is no configuration key that admits custom terms (DESIGN: a key would be an off switch for
     INV-SAFE-01): the state is reported by `frob capabilities --json` as `custom_reward_terms`, it changes
     only with the ADR and the mechanism bead the ADR creates, and the policy record of N41-11 lists the
     expected value under `[capabilities]`;
   - its validator is an importer with limits and a fuzz target under the importer gate;
   - INV-SAFE-01 is restated with the admitted form as an enumerated exception, by ADR.
5. **Kill condition, named in advance.** Any escape from the admitted form's bounds, any digest difference
   between two runs of a training job attributable to the term, or any path by which a term's value reaches a
   verdict: the form is removed and option A is restored. Results that used it keep their condition flag.
6. **Record.** An ADR for OPEN-SAFE-3, `docs/adr/ADR-PROG-09-custom-reward-terms.md` (DESIGN: the four owner
   questions of the grouped row take the program's consecutive identifiers ADR-PROG-08 to -11), naming the
   option, the reason, the rejected options and the pilot table's hash, with the decided value of
   `custom_reward_terms` in the machine-readable front matter block that the owner packet's validator and
   policy record read (the question is put to the owner in the grouped packet N41-11 at the M3 exit); the open-question register updated; under options C or D, a new pilot bead and a new
   mechanism bead depending on it. Deadline: before M4 opens its task-family work; if undecided, "default
   adopted" is recorded and the M4 task families use the closed language.

- [ ] The open-question register shows OPEN-SAFE-3 with its state.

## Test plan

### Unit tests
Under the default: `custom_reward_field_absent` (no task schema leaf accepts byte code or a program);
`capabilities_reports_not_admitted`. These run with the data-not-code suite.

### End-to-end script and logging
No script of its own: this bead adds two calls to step `code_payloads` of `scripts/e2e/safe_importers.sh`
(N37-06's script, which has no `task new` call carrying a program): `frob --json task new crt.ftask.json --key
crt-1` (a `mutate` verb: the key is required, so that the assertion below is the sniff's and never 805) whose
task document (named with a registered view of `.ftask`, `.ftask.json`; VERBS-task) holds the bytes of a WebAssembly module, as an agent
would try to smuggle a compiled reward term: expected exit 3, `FROB-REF-828`, `observed` naming the
WebAssembly kind of the sniff table; and `frob --json task new` with a `reward_program` member in the JSON
request and the key `crt-2`: expected `FROB-REF-802` (no such property exists).
The shared helper logs the command line, the exit code and the refusal; the `summary` counts the assertion.

### Known answers and negative controls
Known answer: under the default the WebAssembly reward term is refused with `FROB-REF-828`. Negative control:
a build with `--features gauntlet-mutations` whose task schema accepts a `reward_program` property must fail
the leaf lint. The pilot's
falsifier is its own control: thresholds are written into the ADR before the terms are counted.

## Considerations

- The requirement-reward pilot of the task chapter (three arms, with its own kill gate) answers a different
  question: whether requirement-derived reward terms inside the closed language help training. Its result is
  an input to this decision: if requirement terms suffice, the case for custom terms weakens further.
- Option C couples this decision to the kernel toolchain's own kill gate: if derived kernels fall back to
  hand-written arithmetic, a submitted intermediate-representation program has no lowering and C falls with
  it.
- Security review of D would need its own threat rows (escape, fuel exhaustion, timing channels); nothing in
  the present threat model covers a general sandbox.
