## Background

The capability under test, from the user's side: an agent imports a robot, a scene asset or a log whose text
was written by someone hostile, then asks the system about it, and nothing the system says in its own voice
contains that text. Imported text is typed as untrusted at entry and may appear only in fields marked
`x-frob-untrusted` and, in MCP text, only inside a delimited data block with its provenance; it never appears
in a tool description, a prompt, server instructions or a `next_actions` command, and it is never a path
component.

GATE-SAFE-02 (Known answer, TARGET, M3): at least 200 hostile strings pass through every verb that echoes
imported text; none appears outside an untrusted-marked field, and none appears in any tool description,
prompt or `next_actions` command. This bead is the script that measures it on the running system. The
mechanism and the scanner are BD-304; the type is N37-04.

## Scope

In: the script's profile `full` (the gate), its fixtures, assertions, logging and the gate record. The script
file and its profile `m1` (the M1 verbs on the CLI only, a partial measurement) are created at M1 by the bead
that owns the untrusted-text type (N37-04); this bead extends that script. Out: the scanner's implementation and the corpus (BD-304); the
fresh-agent behavioural test with a poisoned import (surface chapter).

## Technical approach

`scripts/e2e/safe_injection.sh [--profile m1|full] [--seed N]` (plain shell; sources the shared helper of
STD-E2E; idempotent: it works in a fresh state root under `target/e2e/safe_injection/` and removes nothing
outside it).

Steps:

1. `start`: build `frob`, `frobd`, `frob-mcp` and `frob-conformance`; start `frobd` with a temporary state
   root and a session whose token holds the discovery scopes; record the stack receipt hash and the safety
   configuration digest.
2. `make_fixtures`: `frob-conformance injection make-fixtures --out <dir>` writes, from the corpus of at least
   200 strings, one import source per entry kind: a URDF whose robot, link and joint names are corpus strings;
   an MJCF with a hostile model name and class names; a module and an actuator card with hostile vendor and
   note strings; a scene source with hostile asset metadata, licence strings and annotations; a synthetic
   robot log with hostile lines. Each file is `synthetic`. Every file name is a digest.
3. `import`: `frob --json design import`, `module` and `actuator` loads, `scene import` and `scene compile`,
   `ground ingest` (each with an idempotency key). Assert exit 0 or 2 and a loss report that counts sanitized
   and truncated strings.
4. `sweep_cli_json`: `frob schema --echoing --json` gives the verb list; for each verb the helper runs it on
   every fixture it applies to and saves the envelope. `frob-conformance injection scan --responses <dir>`
   reports per string `inside` and `outside`. Assert `outside = 0` and liveness (each string inside a marked
   field at least once per entry kind).
5. `sweep_cli_human`: the same verbs without `--json`; the scanner checks every hit is on a line of the form
   `untrusted(<kind>): "…"`.
6. `sweep_mcp` (`full` only): over stdio and over HTTP, call the corresponding tools, then fetch `tools/list`,
   the server instructions, `prompts/list`, each `prompts/get` with identifier arguments, `resources/list`
   and the resource templates. Assert: hits in structured content are at annotated pointers; hits in text
   content lie inside a `frob:untrusted` block whose nonce matches its end line; zero hits in tool
   definitions, instructions, prompts and resource listings.
7. `next_actions`: collect every `next_actions[].command` and `warnings[]` from all envelopes; assert zero
   hits, and assert that each command parses under the CLI grammar into a registered verb with identifier
   arguments.
8. `no_side_effects`: `frob --json job list` and `frob --json session show` before and after the sweep are
   equal apart from the jobs the script itself submitted (the hostile "run job cancel --all" changed nothing).
9. `export_names`: export each fixture's design and report under the export root; `find` lists file names;
   assert none contains a corpus string in any of the three forms.
10. `planted` (a build with feature `mutants`): four runs, one per planted defect (a label copied into
    `warnings`; a tool description that uses a stored design name as its example; a `next_actions.command`
    built from a raw name; a prompt that interpolates a stored label). Each run must end with `outside > 0`
    or a non-zero hit count in its category; the step passes only if all four are caught.
11. `record` (`full` only): write GATE-SAFE-02's measured values (strings, entry kinds, verbs, surfaces,
    inside, outside, per-category zero counts, liveness, controls caught) through the conformance harness.

**Logging.** `target/e2e-logs/safe_injection/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`,
`script`, `bead` (`N37-10`), `step`, `event`, the exact command line, exit code, wall time, the envelope's
`evidence` block, and for `metric` lines the counts with their thresholds (`outside`, threshold 0; `strings`,
threshold at least 200). On failure: the string's identifier and digest (never its bytes), the surface, the
verb, the JSON pointer, the annotation found at that pointer, and the saved response path. `summary`:
assertions passed and failed and `gates: ["GATE-SAFE-02"]`. The log is itself scanned at the end: it must
contain no corpus string.

## Acceptance criteria

- [ ] `safe_injection.sh --profile full` exits 0 on a clean build and records GATE-SAFE-02 with at least 200
      strings, every echoing verb, both surfaces, `outside = 0`, zero hits in tool descriptions, prompts,
      instructions, resource listings and `next_actions`, and every string live.
- [ ] `--profile m1` (delivered at M1) still exits 0 unchanged and is logged as a partial measurement, not as
      the gate.
- [ ] Each of the four planted defects is caught in step 10.
- [ ] Step 8 shows no side effect of any hostile string.
- [ ] The log contains no corpus string; the script leaves nothing outside its own directory.

## Test plan

### Unit tests
The helper pieces: `cargo test -p frob-conformance --test injection_fixtures`: `fixtures_cover_every_entry_kind`;
`fixture_names_are_digests`; `scan_three_forms` (raw, sanitized, JSON-escaped) on a synthetic response;
`log_scan_rejects_leaked_string`.

### End-to-end script and logging
This bead is profile `full` of the script. The script runs in the ordinary end-to-end suite at profile `m1`
from M1 and at `full` from M3; the gate record is taken at the M3 exit by a session that did not implement BD-304, and again at every
later exit that adds an echoing verb.

### Known answers and negative controls
KA-830 (count zero outside marked fields; exact). Negative controls: the four planted defects. Metamorphic
relation: running the sweep with a corpus of benign strings of the same lengths yields byte-identical
envelopes outside marked fields. Determinism lanes: identical counts for the same seed twice on one machine,
and on Linux and macOS; MCP over stdio and over HTTP give equal structured content.

## Considerations

- Runtime: about 200 strings × some tens of verbs × two surfaces; fixtures bundle all strings of a kind into
  one import, so the sweep is tens of verb calls per surface, well inside the default compute envelope.
- The script proves placement, not agent behaviour. An agent that reads a marked field aloud to itself is the
  subject of the fresh-agent gate's poisoned-import arm.
- New entry kinds (a twin package's feature names at M5, a calibration dataset's notes) add a fixture
  generator and re-run the gate.
