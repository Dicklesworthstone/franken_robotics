## Background

One rule of the capability model is stated by the safety chapter because the statistics of the qualification
lane depend on it: **a discovery session cannot read a confirmation world.** The blinded lane gives the i-th
confirmation request of a campaign the level α_i = α / [i·(i + 1)] on fresh sealed world clusters, which
bounds the chance of any false promotion by α across an agent's adaptive retries. That bound holds only if no
retry is informed by the worlds that judged the last one.

The counterexample the rule answers (CX-384): if `eval.qualify` returned which worlds failed, an agent could
run an adversarial search near those worlds, patch for them and resubmit; the α_i schedule would then bound
an error rate for a procedure that is no longer the one being run. So the receipt carries only the decision,
the index, the level spent, the units used and a hash.

Decision **ADR-SAFE-02**: isolation is enforced by capability, by a separate store and by address namespace,
**all three**. Reason: statistical error control across adaptive retries is void if one read path exists, so
one defect must not be a leak. The three independent layers:

1. **Capability.** No scope grants it. `eval.qualify` returns a verdict, counts and a receipt. Every other
   verb that could expose a world (`telemetry.*`, `sim.replay`, `run.fork`, `run.show`, `autopsy.*`,
   `nemesis.*`, `explain.*`, stills, replays, `artifact.read`) refuses a confirmation run with
   `FROB-REF-840`, and no token an agent can hold or derive changes that.
2. **Store.** Confirmation chunks live under a separate root with a separate key, opened only by the
   qualification executor inside the daemon. A discovery handler has no handle to it.
3. **Address.** Confirmation worlds are drawn from a sealed seed in their own address namespace. The samplers
   of discovery verbs reject any address in that namespace, so no discovery run can coincide with a
   confirmation world by construction.

Two further rules: an owner-held audit scope can open a confirmation cluster, and using it retires the
cluster, which is never drawn from again; and the request for a qualification is committed to the ledger
before its worlds are drawn.

The firewall itself (scopes, the sealed type, the enumerated paths, the fuzz, the audit) is built by the
qualification chapter's firewall bead. What no mechanism bead proves is the word "independent": that each
layer alone is not load-bearing. This bead is that test, together with the safety chapter's invariant and
proof obligation.

## Scope

In: three one-layer-removed builds and one all-removed build; the sealed-value dictionary scan over the
enumerated paths on each; the exact disjointness test (PO-SAFE-02); the invariant sweep (INV-SAFE-03); the
commit-before-draw order audit; the permanence of cluster retirement; running the leak build under the
adaptive-retry simulator; appending the results to the record of GATE-SAFE-03. Out: the firewall's
construction and its own fuzz gate; the lane's protocol and receipts; the level arithmetic.

## Technical approach

1. **Refusal.** `FROB-REF-840` (owned by the qualification chapter; the safety chapter's earlier code
   `FROB-REF-730` is retired in its favour and must not appear in the registry): a confirmation world or run
   is not readable in a discovery session: sealed confirmation data asked for before close. Exit 5.
2. **Builds** (feature `mutants`, never shipped; each is one `cfg` in one module):
   | Build | Removed | What still stands |
   |---|---|---|
   | `iso-no-cap` | The dispatcher's confirmation check (layer 1) | Store handle absent from discovery handlers; samplers reject the namespace |
   | `iso-shared-store` | The separate root: discovery handlers can open the confirmation root (layer 2) | Dispatcher check; samplers |
   | `iso-open-namespace` | The samplers' rejection of confirmation-namespace addresses (layer 3) | Dispatcher check; separate store |
   | `iso-none` | All three | Nothing (the liveness build) |
3. **The dictionary scan.** For a test campaign the executor exports, to the test harness only, a dictionary
   of sealed values: world addresses, cluster digests, per-unit outcome vectors, trace and still digests, the
   sealed key. On each build, a session holding every discovery scope and the qualification run scope
   attempts the enumerated read paths (the firewall's registry file; at least 25) against the open campaign,
   plus three constructed attacks: a `sim.run` asked for an address inside the confirmation namespace; an
   `artifact.read` of a guessed chunk digest; a `nemesis.search` seeded at a confirmation address. Every
   response (envelope, progress frames, error text, MCP structured and text content, the job log tail) is
   scanned for any dictionary value.
   Expected: zero hits on the clean build and on each of the three one-layer-removed builds (the refusal code
   may differ from 840 on those builds; the oracle is "no sealed value", not the code); **at least one hit on
   `iso-none`**, which proves the scan can see a leak.
4. **PO-SAFE-02: the address namespaces of discovery and confirmation are disjoint.** Exact, class D0: the
   namespace is a field of the address, compared as integers. Tests: (a) over 10⁶ addresses produced by every
   discovery sampler (scene draws, randomization, adversarial search proposals, forks, replays) the namespace
   field is never the confirmation value; (b) over 10⁵ cluster derivations the field is always the
   confirmation value; (c) every public constructor of an address that takes a namespace argument is
   enumerated by a signature scan, and each discovery-side one rejects the confirmation value.
5. **INV-SAFE-03: no discovery session can obtain any per-world datum of a confirmation run.** A property
   test drives random sequences of 50 verbs (drawn from the registry with identifier arguments substituted by
   confirmation identifiers, near misses and valid discovery identifiers) under random discovery tokens,
   10⁴ sequences, with the dictionary scan as oracle. Side channels that are accepted and documented are
   excluded from the oracle and listed in the record: total compute cost, `units_used`, and the fact of early
   stopping.
6. **Commit before draw.** For every request of the test campaign the ledger sequence number of its commit
   precedes that of its first cluster derivation. Control build `iso-draw-first` derives first; the audit must
   flag it.
7. **Retirement is permanent.** Open one cluster with the owner's audit scope; restart the daemon; submit 20
   further requests: the retired cluster's counter never reappears, and the cluster's data stays sealed from
   discovery sessions after the campaign closes (the default retention: retired clusters are kept sealed
   indefinitely).
8. **The gate's negative control.** The build that returns per-world outcomes in the receipt is run in the
   campaign simulator with the scripted adversary under 500 adaptive retries on no-signal worlds. Expected:
   the adaptive-retry gate's bound (false promotion in at most 123 of 2,000 campaigns, TARGET) is exceeded and
   the receipt-shape check fails, so the leak is detected by that gate.
9. **Record.** Appended to GATE-SAFE-03's evidence: paths attempted, hits per build, the liveness hit,
   disjointness counts, sequences run, the order audit, the retirement check and the control's outcome.

## Acceptance criteria

- [ ] GATE-SAFE-03 (TARGET): a session holding every discovery scope attempts at least 25 enumerated read
      paths against a confirmation run; all return `FROB-REF-840`; the leaking test build is detected by the
      adaptive-retry gate. Recorded with counts.
- [ ] On each of `iso-no-cap`, `iso-shared-store` and `iso-open-namespace` the dictionary scan finds zero
      sealed values over all paths and the three constructed attacks.
- [ ] On `iso-none` the scan finds at least one sealed value (liveness).
- [ ] PO-SAFE-02: zero confirmation-namespace addresses from 10⁶ discovery draws; 10⁵ of 10⁵ derivations in
      the confirmation namespace; every discovery-side constructor rejects the confirmation value.
- [ ] INV-SAFE-03: zero hits over 10⁴ random verb sequences.
- [ ] `iso-draw-first` is flagged by the order audit; the retired cluster is never drawn again across a
      restart.
- [ ] `FROB-REF-730` does not exist in the refusal registry.

## Test plan

### Unit tests
`cargo test -p frob-conformance --test confirmation_isolation` (a real daemon on `batch-cpu` with a
`synthetic` test campaign; `--features mutants` for the build matrix):
- `clean_build_all_paths_840`: one row per enumerated path; exit 5.
- `layer_matrix_no_leak`: the three one-layer-removed builds × all paths → zero dictionary hits.
- `liveness_all_removed_leaks`.
- `sampler_never_yields_confirmation_namespace` (10⁶ draws, seed 1);
  `derivation_always_confirmation_namespace` (10⁵).
- `address_constructors_enumerated`: the signature scan's list equals a reviewed list.
- `random_sequences_no_sealed_value` (10⁴ sequences of 50 verbs, seed 1).
- `commit_precedes_draw`; `draw_first_build_flagged`.
- `audit_retires_cluster_permanently`.
- `retired_code_730_absent`.

### End-to-end script and logging
`scripts/e2e/safe_confirmation_layers.sh`: builds the five binaries, opens a test campaign on each, runs the
path list and the three attacks through the real `frob` binary and `frob-mcp`, then the simulator step for
the leaking build. Logged per STD-E2E: build name, verb, command line, exit code, refusal code, dictionary
hits (threshold 0, or at least 1 for `iso-none`), the disjointness counts, and a `summary` naming
GATE-SAFE-03. The dictionary is never written to the log; the log is scanned with it at the end and must be
clean.

### Known answers and negative controls
KA-831 (a session holding every discovery scope attempts at least 25 enumerated read paths against a
confirmation run: all return `FROB-REF-840`; exact; tier G4, daemon; control: a test build that leaks
per-world outcomes is detected by the adaptive-retry gate). CX-384. Known answer for the level schedule the
rule protects: Σ_{i=1..n} α/[i·(i + 1)] = α·n/(n + 1) < α. Negative controls: `iso-none`; `iso-draw-first`;
the leaking-receipt build. Determinism lanes: the random sequences are seeded and replay; refusals are D0.

## Considerations

- The oracle on one-layer-removed builds is absence of sealed values, not a particular code: with the
  dispatcher check removed, the refusal comes from the store or the sampler and may be a not-found.
- Whoever holds the owner's qualification scope is trusted; that is outside the threat model, as is a local
  user with root reading the confirmation root directly.
- A sealed family built on a private scan needs both isolations to pass; the private mark is a separate
  mechanism with its own refusal.
- New verbs: the firewall's path registry fails the build until a new verb is classified, so the path list
  here cannot silently fall behind the surface.
- Risk served: RISK-34 (qualification gamed by adaptive retries or by a leak from sealed worlds).
