## Background

The threat model's fifth asset is people near a physical robot, and the threat is an exported artifact
mistaken for permission to run hardware. (Operating hardware is out of scope: this project never does it.)
The safety chapter's statement: **simulation results are not a safety case for a physical robot**, and
reports carry that no-claim line. The line is also machine-readable. Every exported artifact carries three
fields, each with the constant value `false`: `execution_authorized`, `hardware_safety_signoff`,
`sim_to_real_certified`. Build packets carry a fourth, `fabrication_released`, with the same rule.

Decision **ADR-SAFE-01**: the three flags are a type with one inhabitant, not three booleans. Reason: a
boolean can be set; a constant cannot. In code the flags are one type with a single value whose only
serialization is the three `false` fields; every schema declares each field as the constant `false`; no verb,
flag or configuration produces `true`. **A reader that meets `true`, or an artifact of ours without the
fields, treats it as foreign and refuses it (`FROB-REF-816`); absence is not read as false.** The offline
auditor checks the fields in every bundle. Authorizing hardware is a human act that happens outside this
project and leaves no trace in these artifacts.

Rejected alternatives: three `bool` fields defaulting to false (a setter, a deserializer or a struct literal
can produce `true`); omitting the fields "because they are always false" (an artifact without them is
indistinguishable from one produced by a tool that makes no such promise, which is why absence is refused).

Invariant **INV-SAFE-05**: every exported artifact carries the three authorization flags, each `false`; no
code path writes another value. Proof obligation **PO-SAFE-03**: the authorization type has one inhabitant
(verification: a compile-time test and a schema check; a build that adds a second value fails the workspace
tool). Gate **GATE-SAFE-01** (Known answer, TARGET; M1, then re-run at every milestone exit): every artifact
produced by every exporting verb carries the three fields, all `false`; negative control: an artifact edited
to `true`, and one with the fields removed, are each refused by the importer and by `frob-verify`.

The type itself lives in the foundation crate (a unit type `False` that serializes as the JSON literal false;
`NoAuthorization` with three `False` fields; `PacketAuthorization` adding the fourth), and the M0 gate pins
it with compile-fail tests. This bead is the M1 layer on top: the schemas, the registry of where each
exported kind carries the object, the reader-side refusal, and the proof obligation's checks.

## Scope

In: schema generation and lint for the flags object; `registries/exports.toml` (the locator registry); the
shared reader-side check and `FROB-REF-816`; PO-SAFE-03's compile-time, schema and source-scan checks; the
flags on the M1 exporting verbs, which are what GATE-SAFE-01 measures at M1. Out: the M1 record of GATE-SAFE-01,
made by N37-24 (the M1 part's one recorder, which depends on this bead) from the tier receipt of its script
`safe_flags.sh`; the type and its compile-fail tests (the
foundation and certificate beads); the full M3 surface, rendered banners and later artifact kinds (BD-303);
the auditor's own rule and code `FROB-REF-833`; the build packet's fourth flag and its code `FROB-REF-860`
(the manufacturing chapter); the script (N37-24).

## Technical approach

1. **The flags object in every schema.** The schema generator emits, for any schema that describes an
   exported artifact or the envelope of an exporting verb, the fragment
   ```json
   { "type": "object", "additionalProperties": false,
     "required": ["execution_authorized", "hardware_safety_signoff", "sim_to_real_certified"],
     "properties": { "execution_authorized": {"const": false}, "hardware_safety_signoff": {"const": false},
                     "sim_to_real_certified": {"const": false} } }
   ```
   from the Rust type, under the property name the format uses: `authorization` in an envelope and a build
   packet, `flags` in a certificate bundle, `no_authorization` in a verdict, a qualification receipt and a
   counterexample world. The three field names are the same everywhere. Schema lint
   (`crates/frob-verbs/tests/flag_schemas.rs`): every schema reachable from the output schema of a verb whose
   registry entry has `exports = true` (a bool in N32a-02's entry schema), or marked `exported = true` in the
   format registry, contains the fragment exactly; any schema in
   which one of the four flag names appears with anything but `{"const": false}` fails. One extension is
   admitted, from M2: the replay packet's header object adds the property `banner`, `{"const": <the sentence
   of frob_core::auth::banner>}`, beside the three flags (N37p1-01, which writes it, takes it out before
   calling `check_carried` and refuses any other value); the lint accepts that one property on that one
   schema, generated from the same function, and nowhere else.
2. **The locator registry (DESIGN).** `registries/exports.toml`, one row per (exporting verb, artifact kind):
   ```toml
   [[export]]
   verb = "run.export"
   kind = "run-bundle"          # the artifact kind written
   format = "FMT-FRUN"
   carrier = "manifest"         # manifest | envelope-only | header | sidecar | embedded-metadata
   pointer = "/authorization"   # JSON pointer inside the carrier
   name = "authorization"
   flags = 3                    # 4 for a build packet
   since = "M1"
   ```
   A verb whose entry has `exports = true` and no row here fails the registry test, so a new exporter cannot
   be missed. Carriers: a canonical-JSON manifest carries the object at `pointer`; a view in a foreign format
   (URDF, MJCF, mesh, image) cannot be trusted to carry it, so its carrier is `sidecar`: a file
   `<name>.frob.json` written beside it in the same atomic export, containing the schema name, the view's
   BLAKE3, the stack receipt hash and the flags; where the foreign format has a comment or metadata channel
   the same line is also written there (an XML comment at the head of a URDF or MJCF export).
3. **M1 rows.** `artifact.export` (any stored kind; carrier by format), `run.export` (run bundle manifest),
   `design.export` (URDF or MJCF view with sidecar), `prove.bundle` (certificate bundle, `flags`),
   `control.show --export` (controller export, file header object), and the envelope of each of these
   (`authorization`). Stored verdict records carry `no_authorization`.
4. **Reader-side check, one function.** `frob_core::auth::check_carried(value) -> Result<NoAuthorization,
   FlagFault>` takes the parsed flags object (or its absence) and returns the constant or a fault:
   `Missing { field }`, `True { field }`, `NotFalse { field, found }` (the string `"false"`, the number 0,
   `null`), `Extra { field }`. Every reader of an artifact this system writes calls it before using any other
   field: the reference reader of each format owner crate, the import path of `artifact.read` for bundles,
   the in-tree `prove.verify`, and the sidecar reader for views. A missing sidecar beside a view that claims
   to be ours is `Missing`. The auditor crate has its own implementation of the same rule (it shares no code),
   reported under its own code.
5. **The refusal.** `FROB-REF-816`, "an artifact whose authorization flags are missing or not `false`".
   Exit 3; `retry: never`. Fields: `pointer` (the artifact and the carrier pointer), `observed` (the fault),
   `required` (`the three flags, each the literal false`). Ranked repairs (DESIGN): (1) re-export the artifact
   from its source with this tool, which always writes the flags; (2) if the file comes from another tool,
   bring it in through the importer for foreign data (for example a robot description through
   `design.import`), where it is data with a loss report and never an artifact of this system; (3) there is
   no way to make this system accept a `true` flag. The refused artifact is not stored.
6. **PO-SAFE-03: three checks.**
   - Compile time, in the foundation crate: `const _: () = assert!(core::mem::size_of::<NoAuthorization>() ==
     0);` and an irrefutable destructuring of a value into its three `False` fields. Adding a second value
     (a `bool` field, a second variant of `False`) breaks one of them.
   - Schema: the generated fragment is compared with a golden copy by the generated-file check of the
     workspace tool, so a build that adds a second value fails that check.
   - Source scan (a test): the four flag identifiers occur in non-test source only in the foundation crate's
     `auth` module and in the auditor crate; an occurrence elsewhere (an ad hoc serializer) fails.
7. **Nothing produces true.** A row of the no-off-switch sweep replays an export with `--authorize`,
   `--execution-authorized=true`, a JSON member `"execution_authorized": true` in the request and a
   configuration key of that name: each is `FROB-REF-802` or a configuration error, and the exported
   artifact still carries three `false` fields.
8. **Classes and records.** D0. The flags are part of the claim product of every result and are written into
   the ledger with each export record.

## Acceptance criteria

- [ ] GATE-SAFE-01 at M1 (TARGET) is met by this bead's mechanisms: every artifact produced by every M1 exporting
      verb carries the three fields, all `false`; an artifact edited to `true` and one with the fields removed are
      each refused by the importer (`FROB-REF-816`) and by `frob-verify`. The measurement, with counts per
      kind, is N37-24's script and the record is N37-24's, from that script's receipt; this bead writes no
      gate row.
- [ ] The schema lint passes; a planted exported schema without the fragment fails; a planted
      `"execution_authorized": {"type": "boolean"}` fails.
- [ ] Every verb with `exports = true` has a locator row; a planted exporter without one fails the registry
      test.
- [ ] `check_carried` returns the right fault for: a missing field; `true`; `"false"`; `0`; `null`; an extra
      fourth field on a three-flag kind; and accepts exactly three (or, for a packet, four) literal `false`.
- [ ] A URDF export has its sidecar and its head comment; deleting the sidecar makes re-import of the pair as
      "ours" refuse with `FROB-REF-816`.
- [ ] PO-SAFE-03: the size assertion and the destructuring compile; a scratch crate that adds a `bool` field
      fails to compile; the golden-fragment comparison fails on a changed fragment; the source scan fails on a
      planted occurrence.
- [ ] The four "produce true" attempts change nothing.

## Test plan

### Unit tests
`cargo test -p frob-core --test auth_carried -p frob-verbs --test flag_schemas --test exports_registry`:
- `carried_ok_three_false`; `carried_ok_four_false_for_packet`.
- `carried_missing_each_field` (three cases); `carried_true_each_field` (three cases);
  `carried_string_false_refused`; `carried_zero_refused`; `carried_null_refused`; `carried_extra_refused`.
- `absence_is_not_false`: an artifact with no flags object → `Missing`, never the constant.
- `schema_fragment_is_golden`; `planted_boolean_flag_schema_fails`; `exported_schema_without_fragment_fails`.
- `every_exporter_has_locator`; `planted_exporter_without_locator_fails`.
- `sidecar_written_atomically_with_view`; `missing_sidecar_refused`.
- `zero_sized_one_inhabitant` (the compile-time assertion; and a compile-fail scratch crate with a `bool`).
- `flag_identifiers_only_in_auth_and_auditor` (source scan).
- `no_argument_produces_true` (the four attempts).
- Property test (INV-SAFE-05): for 10³ random M1 export requests, the written artifact parses and
  `check_carried` returns the constant.

### End-to-end script and logging
`scripts/e2e/safe_flags.sh` (N37-24) drives every exporting verb through the real `frob` binary, checks every
artifact with the locator registry, and runs the two mutants through the importer and `frob-verify`.

### Known answers and negative controls
KA-828 (an artifact with one no-authorization flag set to `true` is refused by the importer and by
`frob-verify`; exact, verdict; tier G0, host and auditor; control: an artifact with the fields removed is
also refused). Counterexample protected: "an artifact with no authorization fields is neutral" is false; the
auditor rejects an artifact in which a flag is missing exactly as it rejects one in which
`execution_authorized` is true. Negative controls registered against GATE-SAFE-01: a fixture exporter that
omits the object; one that writes `true`; one that writes the string `"false"`; a reader that treats absence
as false (the `mutants` build must accept the stripped artifact and the test must fail). Determinism lanes:
exported bytes of the flags object identical on Linux and macOS, debug and release.

## Considerations

- Three codes speak about flags: `FROB-REF-816` (readers of this system's artifacts), the auditor's
  `FROB-REF-833` (a flag missing or true in a bundle) and the manufacturing chapter's `FROB-REF-860` (an
  export without the flags, or any attempt to produce a true flag, on a build packet). They are kept because
  they have different owners; each is raised by exactly one component.
- A sidecar can be separated from its view by a person. The view alone is then, correctly, not an artifact
  of this system and is refused as one; it can still be imported as foreign data.
- The seed bead for the flags sits at M3 and covers the full surface; the gate register dates the gate to M1
  and repeats it at every exit, which is why this M1 bead exists.
