## Background

Every number that crosses the agent boundary carries a **claim product**: the meet, over all of its inputs,
of proof class (Proved, Certified, Tested, Estimated), tier, determinism class, and the reality and
model-conditional labels. The weakest input wins by construction. The second asset of the threat model is
evidence, and one of its threats is "a result cited as more than it is"; an optimizing agent will find any
path by which a statistical result can be reported as stronger, so the rule is a type and not prose.

The safety chapter's statements about the boundary:

- The envelope serializer accepts evidence only as a claim-product value. The type has no constructor from
  literals outside its owning crate and no conversion toward a stronger class, so nothing can be converted
  into a proof.
- An envelope names which of the seven claims (Proof, Known answer, Parity, Fidelity, Design comparison,
  Reality, Performance) its result supports and lists explicit non-claims, at least `reality: no-claim`
  wherever the calibration lane has supplied no data.
- A certificate bundle stores the product together with its inputs, and `frob-verify` recomputes it.
- Citing a result above its product is refused (`FROB-REF-819`).

Smallest case that breaks the obvious alternatives: design A was evaluated on the referee and design B on a
fast tier, still provisional. A "majority" or "best input" rule labels their comparison established. The
product labels it provisional, which is all the evidence supports.

Invariant **INV-SAFE-06**: the evidence in an envelope equals the claim product of its inputs. Gate
**GATE-SAFE-08** (Known answer, TARGET; the gate register dates it to M1): over random sets of input evidence
the envelope's class equals the meet; no public function returns a stronger class than its inputs. The
Gauntlet lists the same test among its certifier checks ("the claim product: random sets of input evidence;
the envelope's class equals the meet; no public function raises a class").

The type and `combine` are in the foundation crate and have their own unit property. What that does not show
is the property **at the boundary**: that what the serializer prints is the meet of what the verb consumed,
for real verbs, and that no function anywhere in the workspace hands back stronger evidence than it was
given. This bead measures both at M1. The seed bead for the boundary (BD-308) extends it to the M3 surface.

## Scope

In: the conformance verb that combines stored evidence through the real dispatcher and serializer; the random
generator; the meet oracle written independently of `combine`; the envelope-side lint for `claims` and
non-claims; the public-API scan with its registry of per-function properties; the smallest case; the M1 gate
record. Out: the type (foundation crate); the claim registry and leaf-creation rules (program chapter); the
citation refusal (N37-26); the auditor's recomputation (certificate chapter); the full surface (BD-308).

## Technical approach

1. **The boundary type rule.** A handler returns `VerbResult<T> { value: T, evidence: ClaimProduct, … }`; the
   envelope's `evidence` member is produced only by `ClaimProduct`'s serializer. Compile-fail tests in
   `frob-verbs`: building an envelope with evidence from a string, from a class literal, from a struct
   literal, or from a deserialized JSON value (the type implements no deserializer in `frob-verbs`; reading a
   stored product goes through the ledger's typed loader).
2. **Serialized form** (the `evidence` block; DESIGN, extending the envelope example):
   `{ "kind": …, "class": …, "tier": …, "determinism": …, "standing": "provisional" | "established",
   "reality": "no-claim" | <calibrated family>, "conditions": […], "claims": […], "non_claims": […],
   "weakest": { "input": <content hash>, "field": <path> }, "inputs": <count>, "inputs_root": <digest> }`.
   `standing` is derived: `established` exactly when every input is established (computed on the referee or
   by static analysis, or promoted with a ledger record), otherwise `provisional`. `non_claims` always
   contains `reality: no-claim` unless every input names the same calibrated family.
3. **The conformance verb.** In builds with the feature `conformance` only, the registry gains
   `conformance.combine` (kind `read`): input, a claim kind and a list of references to stored leaf results;
   output, an empty result whose evidence is `combine(kind, the stored products)`. It is a real handler behind
   the real dispatcher and serializer, labelled `synthetic` in its evidence, and absent from release builds
   (the registry parity gate checks that).
4. **Random sets.** A seeded generator makes N = 10⁴ sets (TARGET), each of 1 to 16 leaves. A leaf has a
   class drawn from the four; a tier from `static`, `referee`, `batch-cpu`, `gpu-cuda`, `gpu-metal`; a
   determinism class from D0 to D4; a standing; a reality scope (no-claim, or one of two calibrated families);
   0 to 3 conditions from `tier-sensitive`, `controller-sensitive`, `model-conditional`; and a quantifier
   prefix from two (so that mismatches occur). Leaves are stored through the doorway constructors that the
   conformance harness is permitted to call (Tested and Estimated directly; Certified and Proved through the
   certificate crate's test doorway), so no forbidden constructor is used.
5. **The independent oracle.** Written in the conformance crate without calling `combine`:
   class = minimum over leaves, then capped at Tested unless the kind is Proof; determinism = the weakest of
   D0 > D1 > D2 > D3 > D4; tier = the meet with `static` above `referee` above the mutually incomparable fast
   tiers (two different fast tiers give the set of both); standing = established only if all are;
   reality = no-claim unless all leaves name one family; conditions = union; a quantifier mismatch = the
   quantifier refusal (`FROB-REF-881`) in place of a product. For each set the test calls
   `frob --json conformance combine …` and compares every member of `evidence` with the oracle, and
   `weakest.input` with a leaf attaining the minimum class.
6. **Envelope lint for claims and non-claims.** For every M1 verb, the output schema requires
   `evidence.claims` (an array over the seven kinds, possibly empty) and `evidence.non_claims`; a registry row
   states which claim kinds the verb's results may ever support, and a test asserts that 10³ real envelopes
   per verb (from the M1 batteries) stay inside that list and contain `reality: no-claim`.
7. **The public-API scan (second clause of the gate).** From the documentation JSON of every workspace crate
   (generated by the toolchain's documentation tool and read with the in-house JSON reader), list every
   public function or method whose signature has `ClaimProduct` or `Evidence<_>` in a parameter and in the
   return type, and every one that returns either with no evidence parameter.
   - Functions of the first kind must each have a row in `registries/evidence-functions.toml` naming a
     property test; the scan fails on a missing row. Each named property feeds 10³ random inputs and asserts:
     output class ≤ the minimum input class; output determinism no stronger than the weakest; output tier no
     higher than the meet; output conditions ⊇ the union; output standing no higher than the lowest.
   - Functions of the second kind are leaf constructors and must be exactly the doorway list (who may create
     which class); an extra one fails the scan.
8. **The smallest case as a known answer.** Leaves: A = Tested, referee, established; B = Tested, `batch-cpu`,
   provisional. `conformance combine --kind design-comparison A B` → class Tested, tier `batch-cpu`, standing
   `provisional`, weakest = B.
9. **Record.** Sets run, mismatches (0), functions scanned by kind, functions without a property (0),
   leaf constructors outside the doorway list (0), envelopes linted per verb, controls caught.

## Acceptance criteria

- [ ] GATE-SAFE-08 at M1 (TARGET): over 10⁴ random sets of input evidence the envelope's class equals the
      meet (and tier, determinism, standing, reality and conditions equal the oracle); no public function
      returns a stronger class than its inputs (every scanned function has a passing property). Recorded with
      counts.
- [ ] KA-829: the product of {Tested on the referee, Tested and provisional on a fast tier} is provisional.
- [ ] The four compile-fail cases fail to compile for the intended reason.
- [ ] `conformance.combine` is absent from a release build's registry and tool list.
- [ ] A planted public function `fn upgrade(p: ClaimProduct) -> ClaimProduct` with no registry row fails the
      scan; with a row, its property fails.
- [ ] Every M1 envelope has `claims` and `non_claims` with `reality: no-claim`.

## Test plan

### Unit tests
`cargo test -p frob-conformance --test claim_boundary --features conformance` and `-p frob-verbs --test
envelope_evidence`:
- `oracle_matches_combine_on_all_pairs`: the 16 ordered class pairs, the 25 determinism pairs, the 25 tier
  pairs (a cross-check of the oracle itself against hand-written tables).
- `random_sets_through_serializer` (10⁴ sets, seed 1).
- `smallest_case_provisional` (KA-829).
- `quantifier_mismatch_refuses_not_weakens`.
- `weakest_is_a_minimum_class_leaf` and is deterministic under permutation of the leaves.
- `conformance_verb_absent_in_release`.
- `api_scan_lists_expected_functions` (compared with a reviewed list); `planted_upgrade_fails_scan`.
- `leaf_constructors_equal_doorway_list`.
- `envelope_has_claims_and_non_claims` per M1 verb.
- Compile-fail: evidence from a string; from a class literal; from a struct literal; from a JSON value.

### End-to-end script and logging
This bead creates `scripts/e2e/safe_claim_boundary.sh` with its profile `m1` (the M3 bead N37-27 later adds
profile `m3` to the same script). Profile `m1` builds `frob` with the `conformance` feature, runs the
random-set campaign (`frob --json conformance combine …` for each of the 10⁴ sets), the smallest case and the
API scan, and records the gate. It sources the shared helper of STD-E2E and logs to
`target/e2e-logs/safe_claim_boundary/<utc-timestamp>.ndjson`: every command line, exit code, wall time and
`evidence` block; the seed; `metric` lines `sets` and `mismatches` (threshold 0); on a mismatch the leaves,
the oracle's block, the observed block and the first differing member; the scan's counts; and a `summary`
naming GATE-SAFE-08.

### Known answers and negative controls
KA-829 (claim product of {Tested on the referee, Tested and provisional on a fast tier}: provisional; over
random sets of input evidence the envelope's class equals the meet; exact; tier G0; control: a public
function that returns a stronger class than its inputs). Negative controls registered against GATE-SAFE-08:
a `mutants` `combine` that takes the maximum class; one that takes the majority standing; one that takes the
best tier; the planted `upgrade` function; a handler that builds its evidence from only its first input (the
random-set test must fail on the first set whose weakest leaf is not first). Metamorphic relations: permuting
the leaves changes nothing; adding a leaf can only weaken or leave each member. Determinism lanes: identical
results for the same seed twice, in debug and release, on Linux and macOS (D0).

## Considerations

- The oracle is a second implementation of a small rule; that is deliberate, so that a defect in `combine`
  is not reproduced by the test that checks it.
- The scan depends on the documentation tool's JSON format, which moves with the toolchain; the reader checks
  the format version and the gate is re-run at each toolchain train.
- The tier meet is weaker than a total order by design (two fast tiers are incomparable); if the dynamics
  chapter fixes a total trust order the oracle's table changes by ADR.
- The gate is registered in two work packages' evidence (the claim-product package at M1 and the safety
  package at M3); the record of this bead is the M1 one.
