## Background

The capability under test, from the user's side: an agent may train a policy under the fast, nondeterministic
training profile (`fast-training`, determinism class D4, which guarantees nothing about repeatability). What
it gets is weights. Every number the training run printed is labeled D4 and is refused wherever evidence is
required: paired statistics, promotion, qualification, a certificate, a build packet. When the agent
re-evaluates the same weights under a deterministic profile (class D2), that evaluation is accepted on the
same five paths.

GATE-SAFE-09 (Known answer, TARGET, M3): a result produced under the nondeterministic training profile is
refused on each of the five paths; the same policy re-evaluated under D2 is accepted. The known answer's
negative control: the D4 result offered unlabeled is refused too.

## Scope

In: the script, which is the one script that offers a D4 result on the five evidence paths and whose tier
receipt GATE-SAFE-09 is re-recorded from (BD-269's rule); fixtures; the five-path matrix in three variants
(labeled, unlabeled, re-evaluated), on the command line and through `frob-mcp`; the sweep of every
result-consuming verb; the neighbouring-code checks; planted defects; logging; the gate's measured values;
the helper example the script calls.

The helper is declared here as an example of the conformance crate (BD-025's rule; there is no
`frob-conformance` binary): `crates/frob-conformance/examples/d4.rs`, run as `cargo run -p frob-conformance
--example d4 -- <sub> …`, a thin argument parser over the harness library that prints one JSON object on
standard output and exits non-zero on a failed check, with four subcommands: `plant-study --arm <result>
--arm <result>` (writes a stored study through the conformance build's store doorway and prints its
identifier), `strip-determinism <result> --out <file>` (a copy of the result artifact with only its
determinism member removed), `admit-probe --use build-packet --result <result>` (calls the admission function
with the registered build-packet requirement and prints the refusal or admission), and `kernel-lint --job
<job>` (runs the ban lint of frob-kir, N21a-10, and the compile-option audit of N35-18 over the kernel set
recorded in the job's receipt).

Out, and which bead has it:

- The licence refusals of the numerics chapter and their gate GATE-SPARK-17 (a D4 arm at the admission of a
  paired comparison, attribution and forks below class D2, a cited training return, a cross-family pair
  demanded as paired, with their admissible twins): N35-32 (`scripts/e2e/num_licences_d4.sh`). That script no
  longer offers anything on the five paths.
- The mechanisms: N37-28 and the numerics chapter's licence bead (BD-269).

## Technical approach

`scripts/e2e/safe_d4.sh [--seed N] [--updates 200]` (plain shell; sources the shared helper of STD-E2E;
idempotent; a fresh project and state root under `target/e2e/safe_d4/<run>/`; the daemon on `batch-cpu`, and
on a device where present; everything fits the default compute envelope).

**Sessions.** From M2 a call to the daemon without a token is `FROB-REF-723`. Before `frobd` starts the
script writes two grants with STD-E2E's `e2e_session grant`: `agent-d4` with the scopes that the rows of the
verbs its steps call cite (read from `frob schema --verbs --json`, not written by hand) plus a CPU budget
scope, and `owner` with `eval:read,qual:admin` (the `principal.owner` table of N37-02, the one that may list
the owner-only `qual:admin`), for the test campaign of the qualification path. After start it opens both
roots through the command-line adapter (`e2e_session open d4 --principal agent-d4 --scopes <that list>
--budget <the budget>`, `e2e_session open own --principal owner --scopes eval:read,qual:admin`; no token in
the opening command's environment, scopes named, since omitted scopes grant no non-budget scope). As the
owner (`e2e_session use own`) it opens the test campaign (`frob --json eval ledger --action open --task
<reference flat-velocity task> --world-family <synthetic sealed family>`, an `admin` action with no key);
every other step runs as `agent-d4` (`e2e_session use d4`).

Steps (every `run` and `mutate` call carries its own `--key`, the CLI spelling of the idempotency key, so
that no assertion meets `FROB-REF-805` first; the keys are `d4-<step>-<n>`):

1. `train_d4`: `frob --json train start <reference quadruped> --task <reference flat-velocity task>
   --determinism fast-training --steps-per-collection 256 --steps $((256 * updates)) --key d4-1-1` (the design
   is `train.start`'s positional input, and the budget of `<updates>` collections is given in environment
   steps: VERBS-train has no `--updates` input); wait; `train status`; `train export`. (A determinism profile
   is given with `--determinism`; `--profile` takes a step profile such as `lockstep`, `strict` or `referee`
   and is not used for it.) Assert: the job receipt,
   the status envelope and the exported policy's manifest each say determinism D4 and profile
   `fast-training`; the status envelope's `claims` is empty and its `non_claims` contains
   `training-numbers: not-evidence`. Save the identifiers of: the final training return (`R_d4`), the
   in-training evaluation (`E_d4`), the policy (`P`).
2. `baseline`: train or load a baseline policy under the default deterministic profile and evaluate it under
   `device-replay` (`E_base`, D2), so that paired paths have a second arm.
3. `five_paths_labeled`: offer the D4 results:
   1. paired statistics: `frob --json study compare <S_d4>`, where `S_d4` is a stored study whose two arm
      results are `E_base` and `E_d4`. `study.compare` takes a stored study (positional), and `study plan`
      refuses a D4 arm with `FROB-REF-533` (step 7), so the study is written by
      `cargo run -p frob-conformance --example d4 -- plant-study --arm <E_base> --arm <E_d4>` through the
      conformance build's store doorway; it stands for a study that holds a D4 arm by another route (an imported study record). Steps 4
      and 6 plant their studies the same way, with the stripped copy and with `E_d2` as the second arm;
   2. promotion: `frob --json eval promote <R_d4>`;
   3. qualification: `frob --json eval qualify` with `<E_d4>` named as the candidate's supporting result, and
      a second request whose tier plan names `fast-training` (a test campaign opened by the owner session);
   4. certificate: `frob --json prove bundle` citing `<E_d4>` as an input;
   5. build packet: `cargo run -p frob-conformance --example d4 -- admit-probe --use build-packet --result
      <E_d4>` (the admission function with the build-packet requirement; replaced by the real verb from M5).
   Assert for each: exit 3, `refusal.code = FROB-REF-825`, `observed` contains `D4` and `fast-training`,
   a repair whose command is an `eval run … --determinism device-replay` on `P`; the session budget unchanged.
   Where a verb of a path does not exist yet, the sub-step is logged `skipped: capability absent` (the
   build-packet path is logged `admission probe` until the real verb exists), never as passed, and the summary
   lists what remains to re-measure.
4. `five_paths_unlabeled`: `cargo run -p frob-conformance --example d4 -- strip-determinism <E_d4> --out
   <file>` writes a copy of the result artifact with its determinism member removed and offers it by path (as an imported artifact) to the same five
   consumers. Assert each is refused (`FROB-REF-825` with `observed: unrecorded`); none is accepted.
5. `reevaluate`: `frob --json eval run --policy <P> --task <reference flat-velocity task> --stream dev
   --seeds 1 --determinism device-replay --key d4-5-<n>` twice, with `n` = 1 and 2 (`E_d2`, `E_d2′`; the
   policy form of VERBS-eval, whose population is the task with its development stream; `--seed` is not an
   input of `eval.run`, whose seed spelling is `--run-seed`). Assert identical result digests and `evidence.determinism = D2`; the report line reads
   "trained under fast-training (D4); evaluated under device-replay (D2)".
6. `five_paths_d2`: offer `E_d2` on the same five paths. Assert no refusal with code 825 on any path; where a
   path has further requirements that the fixture does not meet (for example a required standing), the
   refusal is that requirement's code and is logged as `determinism: admitted`; with the fixture arranged to
   meet them (the comparison promoted), the calls succeed.
7. `neighbours`: `frob --json study plan` with one arm's profile `fast-training` → `FROB-REF-533`
   (`study::admit`, the Arena side of the layer rule); `frob --json eval compare` with `E_d4` as an arm →
   `FROB-REF-542` (`pairing::admit` runs before the determinism licence, VERBS-eval; the stored-study request
   of step 3 is the one that answers 825); `frob --json eval compare` with the stripped copy of step 4 as an
   arm → `FROB-REF-561` (an arm of unrecorded class, which 542 does not cover); `frob --json report run`
   citing `R_d4` → `FROB-REF-861`. Assert exactly these codes (one code per request).
8. `bans_and_physics`: `cargo run -p frob-conformance --example d4 -- kernel-lint --job <the D4 job>` passes; per-world state digests of a
   sample of 64 worlds collected under `fast-training` equal their replay under `device-replay`; a
   `fast-training` request with an extra knob `fast_math=true` is `FROB-REF-802`.
9. `planted` (builds with `--features gauntlet-mutations`; each must fail the named step): unrecorded determinism read as
   D2 (step 4); promotion skipping the admission function (step 3); the weights' training class propagated
   into evaluation (step 5 or 6).
10. `sweep`: `R_d4` and `E_d4` offered to every verb whose registry row declares `uses`: assert no acceptance;
    the count of result-consuming verbs swept is logged against the count that refused.
11. `mcp`: steps 3, 4 and 6 repeated through `frob-mcp`; assert the same codes inside tool results marked as
    errors, with the same envelope.
12. `receipt`: `e2e_tier g5_determinism GATE-SAFE-09 --mutations` (STD-E2E; KA-834 is tier G5; the
    long target name, since the `no_conformance_command` lint refuses the short one): the gate's tier entry runs
    KA-834 with the controls registered against the gate in one run. Assert on `$E2E_LAST_RECEIPT` with
    `e2e_get --file` that the gate's value carries, for each of the five paths, labeled refused, unlabeled
    refused and D2 accepted, the digest equality of the two re-evaluations, and every control `caught`.

**Recording.** The script writes nothing to `registries/gates.toml`. BD-269 entered GATE-SAFE-09's row once,
from its own measured outcomes and N37-28's output; when this script has run, a recording session that did
not implement the work records the gate again from this script's receipt with `cargo run -p
frob-conformance --example record_gate -- --gate GATE-SAFE-09 --receipt <hash>`, which adds the receipt to
the row's measured history (BD-269's rule; N38b-19 is the one writer of gate rows), with this log as
evidence beside it.

**Logging.** `target/e2e-logs/safe_d4/<utc-timestamp>.ndjson` and a transcript. Every line: `ts`, `script`,
`bead` (`N37-29`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact command
line, exit code, wall time, the envelope's `evidence` block (claim, class, tier, determinism, profile,
identities, seed); for steps 3, 4 and 6 one `refusal` or `assert` line per path with `path`, `variant`
(`labeled`, `unlabeled`, `d2`), the code, `observed`, `required` and the repair command; `metric` lines
`paths_refused_labeled` (5 of 5), `paths_refused_unlabeled` (5 of 5), `paths_admitted_d2` (5 of 5),
`reeval_digest_equal` (true), `consumers_swept` against `consumers_refused` (equal). On failure: the path, the
variant, and the saved envelope path. `summary`: assertions passed and failed and `gates: ["GATE-SAFE-09"]`.

## Acceptance criteria

- [ ] On a clean build the script exits 0 and its receipt carries GATE-SAFE-09's value, from which the gate
      is recorded again: 5 of 5 paths refuse the labeled D4 result with `FROB-REF-825`; 5 of 5 refuse the
      unlabeled one; 5 of 5 admit the D2 re-evaluation as far as determinism is concerned.
- [ ] The two D2 evaluations have identical digests.
- [ ] Steps 7 and 8 pass: the neighbouring codes are exactly 533 (`study plan`), 542 (`eval compare`, D4
      arm), 561 (`eval compare`, unrecorded arm) and 861 (`report run`); the bans and the physics digests
      hold under the profile.
- [ ] The script passes the `no_conformance_command` lint (BD-025): every harness call is a `cargo run …
      --example` form and the tier target is named `g5_determinism`.
- [ ] Each of the three planted builds fails at its named step.
- [ ] Refused requests charge no budget (session budgets equal before and after steps 3 and 4).
- [ ] The sweep reports zero acceptances of the D4 results across all result-consuming verbs.
- [ ] The command line and `frob-mcp` agree on every code of the five-path matrix.
- [ ] A sub-step whose verb does not exist yet is logged `skipped: capability absent` (or `admission probe` for
      the build packet) and is never counted as passed.

## Test plan

### Unit tests
`cargo test -p frob-conformance --test d4_helpers`: `strip_determinism_removes_only_that_member`;
`admit_probe_uses_registered_requirement`; `path_matrix_has_five_rows`; `plant_study_holds_given_arms` (the
planted study's arm results are exactly the two named, and its record passes the store's schema check).

### End-to-end script and logging
This bead is the script. It runs in the ordinary end-to-end suite from M3 with 200 updates, and for the gate
at the M3 exit; the fifth path is re-run with the real build-packet verb at M5.

### Known answers and negative controls
KA-834 (refused on each of the five paths; the same policy re-evaluated under D2 is accepted; exact, verdict;
tier G5; control: the D4 result offered unlabeled). Known answer adopted from the numerics chapter: a
`fast-training` policy evaluated twice under `device-replay` gives identical digests. Negative controls: the
three planted builds. Metamorphic relation: the number of training updates changes no verdict of steps 3 to
7. Determinism lanes: refusals identical twice on one machine and on Linux and macOS; the re-evaluation is run
twice, across worker counts, and on each device family present, each against its class.

## Considerations

- On a single CPU host the profile's relaxations may happen to produce repeatable numbers; the label and the
  refusals do not depend on observing nondeterminism, only on the declared profile.
- The qualification path needs a test campaign opened under the owner's qualification scope; the script uses
  the same test-campaign fixture as the qualification-lane script and never reads sealed data.
- If asynchronous two-device training is killed, the script still runs the profile on one device or on
  `batch-cpu`.
