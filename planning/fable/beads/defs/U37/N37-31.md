## Background

Decision ADR-SAFE-04 of the safety chapter: paths are resolved beneath retained directory handles, never by
checking a string and reopening, because a check on a string is defeated by a link swapped between the check
and the open. Smallest case: `exports/a` is checked as inside the export root, then replaced by a link to
another directory before it is opened; a string check passes and the write lands outside. The mechanism that
implements the decision is the path jail of `frob-verbs` (bead N37-11), which opens every component of a
path argument relative to the handle of the previous component.

Two rules of the project collide with that mechanism, and no recorded decision settles the collision:

- **Rule L-5** (workspace chapter): core runtime dependencies are the standard library and the Franken
  foundations; `serde` and `serde_json` at exact pins are the only third-party crates allowed, in boundary
  crates. `xtask check-deps` reports any other direct registry dependency of a core crate as the finding
  `L-5.third-party`.
- **The core denies unsafe code** (`unsafe_code = "deny"` for the core workspace; unsafe code lives only in
  annex workspaces, each with a registry of capsules and a `SAFETY.md`).

The Rust standard library cannot open a path relative to a held directory descriptor. Handle-relative opening
therefore needs either a library that wraps the operating system's facility, or foreign calls written here,
which are unsafe code. The safety chapter's own evidence points at the library: FACT, the suite's MCP
library takes the same approach for its filesystem resources, `fastmcp_rust/Cargo.toml` line 100 reads
`cap-std = { version = "=4.0.3", default-features = false }`, and `crates/fastmcp-server/Cargo.toml` uses it;
in that repository's lockfile `cap-std` 4.0.3 depends on `cap-primitives`, `io-extras`, `io-lifetimes` and
`rustix`. `cap-std` is a capability-based filesystem library whose directory type opens paths relative to a
held descriptor and refuses escapes. Because `frob-mcp` is built in the core graph and links the MCP library,
those packages are expected to be in the core lockfile already (HYPOTHESIS; step 2 below settles it).

That expectation is not an admission. The rule of the suite chapter is that an admission is never inherited:
a crate is admitted by its own record, at the pin of the day it is first used, and a record never covers what
it does not list. The MCP library's use of `cap-std` admits nothing for `frob-verbs`. Until a record and a
named exception exist, the path jail runs in a fail-closed interim posture: read arguments resolve only when
no component is a symbolic link, and write arguments other than a fresh run-private directory created by the
process are refused with `FROB-REF-734`, `observed = root-unset`. Under that posture no verb can export to
the export root, so the M1 exporting verbs do not work and the M1 record of GATE-SAFE-10 covers refusals only.

This bead is the decision, the evidence it rests on and the exception row. It is tier Solid. It serves the
threat-model rows "the owner's machines" (a hostile or confused path argument) and "private places" (a write
that lands outside the private or export root). Owner of the decision (DESIGN: no open question is registered
for it, so no owner is on record): the project owner, on the recommendation of the workspace lead.

## Scope

In: the options and what each costs; the admission test of `cap-std` for `frob-verbs` with its record; the
named exception to rule L-5 as a row that `check-deps` reads; the ADR; the condition under which the
exception is withdrawn; the fallback named in advance. Out: the path jail itself, its corpus and its gate
(N37-11, N37-12); per-session roots (BD-258); the admission-record format, writer and validator (N33a-07);
the `check-deps` implementation (BD-003); the M3 rule that every package of every lockfile maps to one
admission block with licence and build log (BD-306), which this record satisfies for `cap-std` when it lands;
third-party notices (N37-18).

## Technical approach

1. **Options.**
   | Option | What changes | Cost |
   |---|---|---|
   | A (recommended) | `cap-std = "=4.0.3"`, default features off, as a direct dependency of `frob-verbs` only, used only in module `frob_verbs::jail` | One named exception to L-5; a third-party crate in the trusted path of every file open |
   | B | Handle-relative opening written here with foreign calls to the operating system (`openat` and, on Linux, `openat2` with the beneath-root flag) | Unsafe code, which the core denies: the calls would live in a new annex crate with a capsule registry and `SAFETY.md`, reached from `frob-verbs` through a trait; two platforms to maintain |
   | C | Keep the interim posture for good | No dependency and no unsafe code; exporting verbs cannot write to the export root, so the M1 product does not export |
   | D | Reuse the MCP library's filesystem type | `frob-verbs` would depend on the MCP library, which is confined to `surface/frob-mcp` by the foundation-confinement rule (L-4); the CLI path would link a server library to open a file |
   Option A is recommended because the package is already pinned by a consumed sibling at an exact version,
   so the pin is not a new supply-chain decision, and because B moves the same operating-system calls into
   code this project would have to audit itself.
2. **Admission test (the evidence for option A).** Run on the one toolchain T, on both machines (Linux and
   macOS), from a branch that adds the dependency line to `frob-verbs`, and written with the admission writer
   of the conformance crate (N33a-07): `cargo run -p frob-conformance --example admission -- record --gate
   ADMIT-CAP-STD --input <path>`, with no `--harness-receipt` (the test goes through no Gauntlet tier, so the
   key is `null`). The input's `covers.crates` names `cap-std` and every package step 2.1 finds it adds;
   `measured` holds step 2.1's values; `controls` holds the wrong opener of step 2.4; `facts_reread` holds step
   2.2's. The record's `sibling_rev` is the MCP library's pin in the stack lock (foundation `FD-FMCP`), the
   pin the exception follows. No `INT-` identifier exists in the gate register for it (DESIGN: the ADR
   proposes the row name; until then the record's `gate` field is `ADMIT-CAP-STD` and the row prints under
   third-party admissions).
   1. *Build.* `cargo check -p frob-verbs --locked` after regenerating the lockfile once. Measured: the
      number of `[[package]]` entries in the core lockfile before and after (TARGET: difference 0 if the MCP
      library's closure already contains every package; any new package is listed by name in the record);
      the number of versions of `cap-std`, `cap-primitives` and `rustix` in the lockfile (TARGET: 1 each);
      the change in cold check time of `frob-verbs` (recorded, no threshold).
   2. *Facts re-read at the pin* (into the record's `facts_reread`): the `cap-std` requirement line of
      `fastmcp_rust/Cargo.toml` at the commit pinned in the stack lock; the `license` field of the `cap-std`
      4.0.3 manifest and of each package it adds, verbatim; whether each of those packages contains unsafe
      code (expected: yes, in the packages that wrap system calls; recorded, since the core's deny rule
      applies to this repository's code and not to dependencies).
   3. *Behaviour probes* (`crates/frob-verbs/tests/admit_cap_std.rs`, real temporary directories, a root
      handle `R` and a sentinel directory `S` outside it, whose tree digest is taken before and after):
      | Probe | Action through `R` | Expected |
      |---|---|---|
      | `parent_refused` | open `../x` and `a/../../x` | error; nothing opened |
      | `absolute_refused` | open `/etc/hosts` | error |
      | `link_out_refused` | `a` is a link to `S`; open `a/f` for reading | error |
      | `link_in_followed` | `a` is a link to `b` inside `R`; open `a/f` for reading | the file `b/f` |
      | `create_through_link_refused` | `a` is a link to `S`; create `a/out` | error; `S` unchanged |
      | `final_link_not_followed` | `out` is a link to `S/f`; create-new `out` | error; `S/f` unchanged |
      | `swap_1000` | a helper alternates `a` between a directory and a link to `S` while 1,000 files are created as `a/out-<i>` | each call succeeds inside `R` or fails; `S` unchanged |
      | `rename_same_handle` | create a temporary name and rename it onto the final name relative to one handle | the final name holds the complete bytes |
      | `fstat_from_handle` | metadata of an opened file | available from the handle with no second lookup by name |
   4. *Negative control (the probes can fail).* The same nine probes are run against a deliberately wrong
      opener written with the standard library (canonicalize, compare the prefix, reopen by name).
      `swap_1000` must put at least one file in `S` for that opener within 1,000 calls on each platform; if
      it does not, the recipe is too slow to prove anything and the test is reported `not-live`, which is a
      failure of the admission test.
   A record with status `pass` requires all nine probes on both platforms, one version of each package, the
   control caught, and a recorder session different from the implementing session (the validator's rules).
3. **The exception row (DESIGN).** The stack lock gains one row for `cap-std` in the same form as a
   foundation row: package and exact version; posture `registry, exact pin, equal to the MCP library's pin`;
   use `handle-relative path resolution`; confinement `frob-verbs` (module `jail`); admission record hash;
   fallback `interim posture, then option B`; the ADR's path. `check-deps` suppresses `L-5.third-party` for
   exactly the triple (crate `frob-verbs`, package `cap-std`, version `=4.0.3`) when such a row exists with
   a valid `pass` record, and for nothing else. The row adds two findings: `L-5.exception-unadmitted` (the
   dependency line is present and the row or its record is missing or stale) and `L-5.exception-drift`
   (the version differs from the MCP library's pin in the stack lock, which would put two copies in the
   lockfile). A source scan confines use: `cap_std` may be named only in `crates/frob-verbs/src/jail/`.
4. **Pin moves.** The exception is tied to the MCP library's pin. When the compatibility train moves that
   library and its `cap-std` requirement changes, the admission test is rerun at the new version and the row
   is rewritten in the same change. A stale record (its `sibling_rev` no longer the MCP library's pin in the
   lock) fails `check-deps` as `L-5.exception-unadmitted`; `check-stack`'s never-inherited check enumerates
   foundation crates only (N33a-07) and does not see `cap-std`, so the exception's staleness is this row's
   finding.
5. **The ADR.** `docs/adr/` gains a record titled for ADR-SAFE-04's dependency: the option chosen, the
   reason, the rejected options, the admission record's hash, the date and the decider. If the owner chooses
   B, C or D the ADR says so and names what follows: for B, a new annex crate and its bead, on which the
   path jail then depends; for C, the list of exporting verbs that stay disabled; D is recorded as rejected
   unless the confinement rule is itself changed by ADR.
6. **Withdrawal, named in advance.** The exception is withdrawn (the row removed, the path jail returned to
   the interim posture until option B exists) if any probe of step 2.3 fails on a supported platform at the
   pinned version; if a later version of the MCP library drops `cap-std`, leaving this project its only
   consumer, and the owner does not re-affirm it; or if a published defect in the pinned version reopens
   the swapped-link case. Results recorded before a withdrawal keep their evidence; no result depends on
   which library opened a file.
7. **Classes.** The probes are class D0 except `swap_1000`, a concurrency test whose oracle (nothing lands
   in `S`) holds on every schedule. The record is evidence of class Tested for the statement "at this pin, on
   these two platforms, the nine probes hold"; it is no claim about other versions or platforms.

## Acceptance criteria

- [ ] An ADR for the dependency of ADR-SAFE-04 exists and names one option, or the M1 entry record states
      "undecided: the path jail ships the interim posture and exporting verbs are refused".
- [ ] Under option A: an admission record with status `pass` exists for `cap-std` 4.0.3 confined to
      `frob-verbs`, with the nine probes passing on Linux and on macOS, the negative control caught on both,
      the lockfile counts measured, and the licence strings recorded verbatim.
- [ ] `xtask check-deps` passes with the dependency line in `frob-verbs` and the row present; it fails with
      `L-5.third-party` when the same line is planted in `frob-io`, with `L-5.exception-unadmitted` when the
      row is removed, and with `L-5.exception-drift` when the version is changed to `=4.0.2`.
- [ ] The core lockfile contains exactly one version of `cap-std`, `cap-primitives` and `rustix`.
- [ ] A planted `use cap_std` outside `crates/frob-verbs/src/jail/` fails the source scan.
- [ ] `frob doctor --json` lists `cap-std` among admitted third-party packages with its pin, its record hash
      and its confinement.
- [ ] The generated `DEPENDENCY_ADMISSION.md` shows the record; a gate with no record prints `not run`.

## Test plan

### Unit tests
`cargo test -p frob-verbs --test admit_cap_std` (the nine probes of step 2.3, by the names in the table, and
`wrong_opener_is_caught` for the control) and `cargo test -p xtask --test deps_exception`:
- `exception_row_suppresses_only_its_triple`: the row admits (`frob-verbs`, `cap-std`, `=4.0.3`); the same
  package in `frob-io` is still `L-5.third-party`.
- `missing_row_is_unadmitted`; `stale_record_is_unadmitted` (a record whose cited commit's lockfile lacks
  the package, and a record whose `sibling_rev` differs from the MCP library's pin in the lock).
- `version_drift_detected`: the row at `=4.0.3` with the MCP library's pin moved to another version.
- `use_outside_jail_fails_scan`.
- `lockfile_single_version`: parses the real core lockfile and counts versions of the three packages.

### End-to-end script and logging
No script of its own. `scripts/e2e/safe_path_jail.sh` (N37-12) logs, in its `start` line, the admission
record hash under which the jail's write path is enabled, or `interim-posture` when there is none, so that
every gate record of GATE-SAFE-10 states which opener it measured. The admission writer's own run is logged
by the conformance crate: command line, exit code, wall time, the output hash and the measured values.

### Known answers and negative controls
Known answer of this bead: with `a` swapped between a directory and a link to the sentinel directory during
1,000 creates, the sentinel directory's digest is unchanged (exact). Negative controls: the wrong opener of
step 2.4 (must leak on each platform); the three planted `check-deps` violations of the acceptance list; a
planted record with the recorder equal to the implementer (must be refused as `self-certified`).
Determinism lanes: the lexical probes give identical results on Linux and macOS; the swap probe is run on
both and under two worker counts of the helper.

## Considerations

- This is the only named exception to rule L-5 that the safety chapter asks for. It must not become a
  pattern: the row format admits one triple, and a second exception needs its own ADR and record.
- The dependency's own packages contain unsafe code and system calls. That is the point of the choice: the
  alternative is the same calls written and audited here. The record states it plainly.
- Supply chain: the pin is exact and equal to a consumed sibling's, the lockfile is committed and builds use
  `--locked`, so the package bytes are fixed by checksum. The licence text of each added package enters the
  third-party notices generated for binaries.
- Platform differences: beneath-root resolution uses a kernel facility where one exists and a component walk
  elsewhere; the probes are run on both machines because the two paths share no code.
- If the owner has not decided when the path jail is otherwise complete, the interim posture ships and the
  M1 exit record lists the exporting verbs as refused; that is a visible cost, not a silent one.
- What would reopen the decision: a standard-library interface for opening relative to a directory handle
  (the exception is then removed), or a second consumer inside the core (the confinement is then reviewed).
