## Background

The Gauntlet is the subsystem of FrankenRobotics that decides whether a gate may record PASS. Its crate is
`frob-conformance` (layer 7, the top layer; tier Solid). Its first duty is to the things that issue certificates
and verdicts (the certificate checker, the qualification lane, the solvability oracle, the rank-agreement ledger,
the monitors, the statistics), because "a false certificate is worse than an ordinary wrong answer" (FACT: the
agent instructions of FrankenSim, the sibling simulation library). Its second duty is to the program's own
numbers: any number in the planning documents is a TARGET, or a FACT about something else, until a gate records
it, and the Gauntlet is the only path by which it becomes a result.

This bead fixes where each owned thing lives, and turns the six architecture decisions of the subsystem into
checks that fail when a decision is broken. The decisions exist because each names a specific way a verification
program rots:

- **ADR-GAUNT-01. The Gauntlet has no agent verb and no `xtask` subcommand.** Its tiers are test targets of
  `frob-conformance`, run by `cargo test -p frob-conformance --test <tier> -- <gate or row>`. A run writes a
  hash-named receipt; the recording session enters the row of `registries/gates.toml` that cites it. Reasons: a
  harness driven through the surface it judges is a path to self-certification; and `xtask` holds exactly six
  checks, runs no physics and records no gate. The verbs under test are called by the harness exactly as an agent
  would call them. Rejected: a `frob gauntlet …` verb family; a seventh `xtask` check.
- **ADR-GAUNT-02. Registries are data and the document is their printout.** The printed known-answer suite, the
  printed counterexample catalogue, the gate register and the README status table are generated from
  `registries/gates.toml` and the registry files of `frob-conformance`. Reason: a hand-edited table drifts from
  the tests that are supposed to back it. A KA or CX number is never reused and never renumbered; new rows append.
- **ADR-GAUNT-03. Every gate is registered with its failing control before its passing test is written.** Reason:
  "a gate no deficient model can fail validates nothing" (FACT: the suite's Wright Flyer plan). The control is the
  specification of what the gate detects.
- **ADR-GAUNT-04. Foreign tools are comparison instruments, never dependencies and never baselines of record.**
  They run out of process, under a pin, on fixtures captured by script. Reasons: FrankenSim's adapter rule
  (FACT), and the finding that a sibling's training code violated three of the rules it would have been an oracle
  for.
- **ADR-GAUNT-05. Ceiling first.** No speed or efficiency experiment runs until the largest ratio it could show
  has been computed from a phase breakdown. Reason: a planning pilot measured 1.345 on a test whose ceiling was
  about 1.46; the experiment could not have confirmed its claim, and nobody had computed that beforehand.
- **ADR-GAUNT-06. One fixture identity per physical case.** A case stated by a mathematical construction and
  again by the subsystem that implements it is one fixture with two rows: the first tests the mathematics on the
  host and the second tests the subsystem on its tiers. Reason: two copies of a fixture's constants are two
  chances to disagree.

## Scope

In: the directory layout of the crate; the ownership table; one check per decision; the crate's `CONTRACT.md`
and `contract.toml`; the scope cap. Out: the content of each owned thing (tiers N38a-02; oracles N38a-04;
experiments N38a-07; pilots N38a-09; known answers N38a-12; relations N38a-14; battery N38a-20; chaos N38a-23;
the catalogue and its seeding N38b-05; the allocation ledger N38a-40; the harness reasons N38-REF); the
negative-control registry and the gate status file (drafted with BD-025).

## Technical approach

**Layout (DESIGN; paths relative to `crates/frob-conformance/`).**

| Owned thing | Where it lives | Consumers |
|---|---|---|
| Tier runners G0 to G5 | `tests/g0_laws.rs` … `tests/g5_determinism.rs`, one test target per tier | CI, milestone exits |
| Oracle fixtures, pins | `fixtures/` here and `tests/fixtures/oracle/` at the root; capture scripts in `tools/oracle/` | Tiers G1, G2 |
| Known-answer suite | `registry/known_answers.toml`; one derivation file per fixture in `docs/derivations/` (its front matter lists the rows it serves) | Tier G1; the printed suite |
| Counterexample catalogue and seed map | `registry/counterexamples.toml`; `registry/seed_map.toml`, `registry/seed_findings.toml` (written by the seeding tool) | The seeding tool; the printed catalogue |
| Negative-control registry | `registry/controls.toml` | Every gate; seeded from the counterexample catalogue |
| Allocation ledger of KA and CX numbers after plan time | `registry/allocations.toml` | Both loaders; chapter registry beads |
| Harness reasons | `registry/reasons.toml` | Every tool of the crate; end-to-end scripts |
| Metamorphic relation registry | `registry/relations.toml` | Tier G3 |
| Standard battery and its frozen identity | `battery/`; identity in the ledger | Fidelity ledger, divergence ledger, detectors |
| Chaos schedules and minimized regressions | `chaos/` | Tier G4; the daemon's simulation tests |
| Pilot register | `registry/pilots.toml` | Work-package funding |
| Experiment register, comparator pins, oracle register | `registry/experiments.toml`, `registry/comparators.toml`, `registry/oracles.toml` | Method experiments; G2 |
| Gate status | `registries/gates.toml` (repository root) | README status table; the gate register |
| Ten-fold harness | `tenfold/` | The ten-fold test |

**Checks (all in `tests/decisions.rs`, run as `cargo test -p frob-conformance --test decisions`).**
1. `adr01_no_verb_no_xtask`: no entry of `registries/verbs.toml` has an owner crate `frob-conformance` or a name
   beginning `gauntlet.`; the `xtask` subcommand list is exactly `check-layers`, `check-deps`, `check-unsafe`,
   `check-generated`, `check-contracts`, `check-stack`.
2. `adr01_receipt_named_by_hash`: a tier run writes `target/gauntlet/receipts/<blake3 of content>.json`; a
   receipt whose name is not the hash of its bytes is rejected by the reader.
3. `adr02_printouts_regenerate`: regenerating the printed known-answer table, the printed counterexample table
   and the README status table from the registries reproduces the committed files byte for byte.
4. `adr02_ids_append_only`: against the previous commit's registries, no KA, CX, NC or MR identifier disappears,
   is renumbered or is reused for a different case.
5. `adr03_control_before_test`: every gate row of `registries/gates.toml` whose status is not `not-run` has a
   non-empty `controls` list whose entries exist in `registry/controls.toml`; and in the commit history a gate's
   first control was registered no later than its first passing receipt.
6. `adr04_no_foreign_tool_linked`: `cargo metadata` over every workspace shows no dependency edge from a
   production crate to any package named in `registry/comparators.toml` or `registry/oracles.toml` with posture
   `out-of-process`.
7. `adr05_ceiling_before_speed`: every record of `registry/experiments.toml` whose claim is a speed or efficiency
   ratio has a `ceiling` block dated before its first run record, and `ceiling.value ≥ success_threshold`.
8. `adr06_one_fixture_identity`: rows of `registry/known_answers.toml` that carry the same `fixture` name resolve
   to one derivation file and one constants block; two rows whose constants are equal and whose fixture names
   differ are reported.
9. `nothing_depends_on_conformance`: no workspace manifest lists `frob-conformance` under dependencies or
   dev-dependencies.
10. `scope_cap`: the crate's Rust line count, tests included, is reported against the cap of 24,000 lines; 115%
    (27,600) fails until an architecture decision record raises the cap or moves a mechanism out.

`CONTRACT.md` carries the ten required sections (purpose, inputs, outputs, invariants, refusals, determinism
class, evidence class of outputs, validity domain, oracles, known gaps). Outputs of the harness are evidence of
class `Tested`; the harness creates no `Proved` or `Certified` leaf.

## Acceptance criteria

- [ ] The directories and files of the layout exist, each registry file schema-valid (possibly empty).
- [ ] Each of the ten checks passes on the clean tree.
- [ ] Each check fails on its planted violation (listed under negative controls) and names it.
- [ ] `CONTRACT.md` has its ten sections; `contract.toml` states layer 7, determinism class and evidence class.
- [ ] The crate depends on everything it needs and nothing depends on it.

## Test plan

### Unit tests

The ten checks above are the unit tests. Inputs and expected values: check 1 expects exactly six subcommand
names; check 2 a receipt named `0000….json` rejected; check 10 with a planted 27,601-line count fails and
27,599 passes.

### End-to-end script and logging

`scripts/e2e/gauntlet_decisions.sh` (header: `bead=N38a-01 milestone=M0 labels=gauntlet gates=GATE-GAUNT-10`).
In a scratch copy it plants each violation in turn and runs the `decisions` target, using `e2e_expect_caught`;
then runs it clean. Log at `target/e2e-logs/gauntlet_decisions/<utc>.ndjson`: one `cmd` per run with exit code
and wall time, one `assert` of kind `negative-control` per plant, the crate line count as a `metric` against
24,000, and the `summary`.

### Known answers and negative controls

Planted violations, one per check: a verb `gauntlet.run` added to the verb registry; a seventh `xtask`
subcommand; a hand-edited cell of the printed known-answer table; KA-010 reused for a different case; a gate set
to `pass` with empty `controls`; a production crate depending on a comparator package; a speed experiment with no
ceiling, and one whose ceiling 1.46 is below its threshold 2.0; two rows with equal constants under two fixture
names; a dev-dependency on `frob-conformance` from another crate. Determinism lane: the checks are class D0 and
give identical output twice on one machine and on both platforms.

## Considerations

- Check 5's history clause needs the repository history; in a shallow clone it reports `not-evaluated`, never
  pass.
- The crate depends on everything, so it is the slowest to build; tier targets are split so that tier G0 and the
  `decisions` target build without device annexes.
- Risk: the harness becomes the product ("process is never the product"). Each registry exists because a named
  gate reads it; one that nothing reads is deleted.
