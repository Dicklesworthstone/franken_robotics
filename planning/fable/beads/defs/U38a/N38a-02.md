## Background

The Gauntlet (the verification subsystem of FrankenRobotics, crate `frob-conformance`) sorts every conformance
test into exactly one of six tiers. The tiers are those of the sibling simulation library FrankenSim (FACT), read
for robots. A tier says what kind of evidence a test produces; a *site* says where it executes. Keeping the two
apart matters because one truth that holds on the most trusted tier and, within an envelope, on a fast tier is
two results, not one.

Sites: `host` (exact or double-precision arithmetic inside a test binary); `auditor` (the standalone certificate
checker `frob-verify`); `referee` (the most trusted dynamics tier, in `f64`); `strict` (the CPU batch tier
`batch-cpu` under its transactional `strict` profile); `lockstep` (the throughput tiers); `cuda`; `metal`;
`daemon` (`frobd` under the deterministic simulation runtime).

DESIGN choice: one Cargo test target per tier, with a filter by gate or by registry row, and a receipt per run.
Reason: a tier is the unit a milestone exit asks for ("G1 for every row due"), a filter is how one gate is
re-measured, and a receipt named by the hash of its content is what a recording session can cite without trusting
the session that ran it. Rejected: one monolithic test target (cannot be built without device annexes); a custom
runner binary or a verb (the harness must not be reachable through the surface it judges).

## Scope

In: the tier and site types; what each tier contains; the test registration and selection mechanism; the receipt.
Out: the leading tests per subsystem (N38a-03); the known-answer suite (N38a-12, N38a-13); relations (N38a-14);
chaos (N38a-23); determinism lanes in detail (N38a-35); the self-tests of certifiers; recording in
`registries/gates.toml`.

## Technical approach

**Types (DESIGN sketch).**
```rust
pub enum Tier { G0Laws, G1KnownAnswers, G2Parity, G3Metamorphic, G4Chaos, G5Determinism }
pub enum Site { Host, Auditor, Referee, Strict, Lockstep, Cuda, Metal, Daemon }
pub struct Entry {            // one registered conformance test
    pub id: &'static str,     // e.g. "ka:KA-501@host", "mr:MR-06@strict", "law:se3-adjoint"
    pub tier: Tier, pub site: Site,
    pub gates: &'static [&'static str],          // gates this entry measures
    pub controls: &'static [&'static str],       // NC ids it must catch in the same run
    pub milestone: Milestone, pub budget: Budget, // envelope class; default 16 GiB, 8 cores, 1 hour
    pub run: fn(&mut Ctx) -> Outcome,            // Pass{measured}, Fail{first_diff}, Refused{code}, Skipped{why}
}
```
An entry belongs to exactly one tier and names exactly one site; the same case on two sites is two entries.
Entries are collected in static tables per tier (`tests/g1_known_answers.rs` builds its table from the registry
and from `fn` items of the owning modules); there is no procedural macro.

**Tier contents.**

| Tier | Kind | Content carried from the earlier design | Content this design adds |
|---|---|---|---|
| G0 | Laws and self-tests | The algebraic laws of the Lie-group core; functor laws of the model compiler; cone laws; dimension checks on every kernel | Claim-product laws (the class of a result is the minimum over inputs); the level series Σ α/[i·(i + 1)] = α·m/(m + 1); polarity laws of revalidation; self-tests of the certifiers; layer and dependency checks |
| G1 | Known answers | Analytic and synthetic truths of the subsystems | The whole printed known-answer suite: 835 rows at plan time (FACT, counted from the registry's seed) |
| G2 | Parity | Agreement with pinned oracles and published benchmark problems | Incumbent simulators as comparison instruments; conventional solvers against family answers; published anchors for the reality-calibration subsystem |
| G3 | Metamorphic | Relations that hold without knowing the answer | 42 further relations generated by the new constructions |
| G4 | Chaos | Cancellation at every boundary, injected faults, capacity overflow, device loss, malformed input | Crash consistency of the job and chunk protocols; deterministic simulation of the daemon and ledger; fuzzing of the thirteen format readers; the confirmation firewall |
| G5 | Determinism | Twice on one machine; across worker counts; debug and release; across platforms; across backends, each against its class | Batch-composition invariance; decision-level equivalence under class D3; exact-integer and guarded kernels; refusal of paired statistics under an uncontrolled class; results of class D4 refused until re-evaluated |

**Selection.** `cargo test -p frob-conformance --test g1_known_answers -- <filter>` where the filter is a gate
(`GATE-ARENA-05`), a row (`KA-501`), a site (`@referee`) or a milestone (`due:M1`). With no filter the target runs
every entry whose milestone is at or before the current one (`FROB_MILESTONE`, default from
`registries/gates.toml`). An entry whose site is unavailable (no CUDA device) is `Skipped` with the reason; a skip
is never a pass and the receipt counts it.

**Order within a row.** A row runs first on the weakest site that can decide it (`host` before `referee` before
`strict` before the device sites), then on every site its gate names; a failure on an earlier site does not
suppress the later ones, and each site produces its own outcome line.

**Controls in the same run.** For each gate touched, the runner executes every registered control of that gate
after the passing entries and records `caught` or `missed`. A gate's line in the receipt is `pass` only through
the test kit's `GateReport` (no control caught in this run prints `not-eligible`; a missed control prints `fail`
whatever the passing tests say).

**Receipt (`frob.gauntlet.receipt/1`, canonical JSON, file name = BLAKE3 of the bytes, under
`target/gauntlet/receipts/`).** Fields: `tier`, `filter`, `commit`, `dirty`, `toolchain`, `fingerprint` (hardware
fingerprint digest), `seed`, `profile`, `started`, `wall_ms`, `entries[{id, site, outcome, measured{name, value,
unit, threshold}, first_diff, determinism, synthetic}]`, `controls[{id, gate, outcome}]`,
`gates[{id, line}]`, `counts{pass, fail, refused, skipped, obligations}`, `session` (the identity of the session
that ran it). A receipt is evidence of class `Tested`. It is not a gate status: a different, fresh-context
session enters the status and cites the receipt.

## Acceptance criteria

- [ ] Six test targets exist, one per tier; each builds without the others' device dependencies where its sites
      allow (G0 and the host and auditor entries of G1 build with no annex).
- [ ] An entry with two tiers or no site does not compile or is rejected at table construction.
- [ ] The four filter forms select the expected entries; an empty selection is an error, not a pass.
- [ ] A run writes a receipt whose file name equals the hash of its bytes; a receipt altered by one byte is
      rejected by the reader.
- [ ] A gate with a passing entry and no caught control prints `not-eligible`; with a missed control, `fail`.
- [ ] A skipped site is counted and named in the receipt.
- [ ] The weakest-site-first order is observed and every named site produces its own outcome.

## Test plan

### Unit tests

`crates/frob-conformance/tests/tier_runner.rs`, using a small table of real entries (the G0 law
Σ α/[i·(i + 1)] = α·m/(m + 1) for α = 1/20 and m = 1…500 in exact rationals; the docking grid known answer on
`host`):
- `entry_single_tier_single_site`: table construction rejects a duplicate id and an id whose suffix disagrees
  with its site.
- `filter_by_gate`, `filter_by_row`, `filter_by_site`, `filter_by_milestone`: each returns the expected ids.
- `empty_selection_is_error`: filter `KA-999999` exits non-zero.
- `site_order`: for a row registered on `strict`, `host` and `referee` the execution order is host, referee,
  strict.
- `receipt_name_is_hash`, `receipt_tamper_rejected`.
- `gate_line_needs_caught_control`: the three outcomes.
- `skip_counted_not_passed`: with `E2E_DEVICES=cpu`, a `@cuda` entry is `Skipped` and the gate line is not pass.
- `level_series_exact`: Σ over i = 1…m of (1/20)/[i·(i + 1)] equals (1/20)·m/(m + 1) for each m up to 500.

### End-to-end script and logging

`scripts/e2e/gauntlet_tiers.sh` (header: `bead=N38a-02 milestone=M0 labels=gauntlet gates=GATE-GAUNT-01
plants=drop-control`). It runs each tier target with a small filter, checks the receipts, then plants
`drop-control` (the control list of one gate emptied in a scratch registry) and requires the gate line to become
`not-eligible`. Log at `target/e2e-logs/gauntlet_tiers/<utc>.ndjson`: each cargo command with exit code and wall
time, receipt hashes as digests, per-tier counts as `metric` lines, the negative-control assertion and the
`summary`.

### Known answers and negative controls

Known answers: the level series (exact); the docking grid counts 344, 217, 9 (KA-501). Negative controls: the
emptied control list; the tampered receipt; an entry registered under two tiers; a row that passes on `host` and
is given a planted wrong tolerance on `referee`, which must show as a second, failing outcome and not be merged.
Determinism lanes: receipts of tier G0 are byte-identical twice on one machine apart from `started`, `wall_ms`
and `session`.

## Considerations

- Tier runs above the default machine envelope (training-scale G5 lanes, 10⁵ chaos schedules) name their budget
  in the entry and wait for the owner's approval; until then they run at a reduced, printed count.
- Open: the Gauntlet's runtime budget per change, per night and per release on each machine is undecided; the
  fail-closed default is the `smoke` and `fixtures` batteries per change and everything else nightly.
- A gate may pass before its milestone and may not move later without an architecture decision record.
