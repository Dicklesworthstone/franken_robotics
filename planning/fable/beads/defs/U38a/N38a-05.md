## Background

FrankenRobotics keeps seven kinds of claim apart (Proof, Known answer, Parity, Fidelity, Design comparison,
Reality, Performance), because each is established by a different kind of evidence. The most tempting confusion
is between Parity and Reality: agreeing with another simulator, or with a published figure for the same robot,
feels like agreeing with the world. It is not. Agreement with an oracle shows that two programs agree; two
programs that share a solver have correlated error; and an incumbent that has itself been compared with hardware
carries its authors' claim under their conditions, which does not transfer.

The second confusion this bead closes is structural: a foreign tool that becomes a dependency becomes a baseline
of record. Foreign tools run out of process and never enter a production dependency graph.

DESIGN: both rules are enforced by construction and by a planted failure, not by review. The result type of a
tier-G2 test has no constructor for any claim kind other than `Parity` (INV-GAUNT-03). Rejected: a lint on
report wording (an optimizing agent finds any path by which a comparison can be reported as reality, and a style
rule is such a path).

## Scope

In: the G2 result type; the `published-anchor` and `synthetic` statuses; the out-of-process rule and its check;
the M0 measurement of oracle hygiene. Out: the register and fixture rules (N38a-04); the development oracle
(N38a-06); the `reality:` line on reports (BD-139).

## Technical approach

**Rule 4. Agreement with an oracle is Parity and is never reported as Reality.**
```rust
// DESIGN sketch, crate frob-conformance
pub struct ParityResult {                 // the only record a G2 entry can return
    oracle: OracleId, pin: Pin, fixture: FixtureId,
    status: ParityStatus,                 // Oracle | PublishedAnchor | Synthetic | DevelopmentOracle
    measured: Vec<Measured>, tolerance: Tolerance,
}
impl ParityResult { pub fn claim_kind(&self) -> ClaimKind { ClaimKind::Parity } }  // constant
// No `From<ParityResult>` for a reality record exists; no field, flag or builder changes the kind.
```
- `PublishedAnchor`: a comparison with a published figure for the same robot. It is scheduled at M3 and is
  recorded as Parity with this status, never as Reality.
- `Synthetic`: a comparison with data from a simulator standing in for reality; it is never promoted.
- The permitted wording of a parity result in any report is "matches ⟨oracle⟩ at ⟨pin⟩ within ⟨tolerance⟩ on
  ⟨fixture⟩"; the word "verified" is not used.
- The recorder refuses a gate row whose `claim` is `reality` when its evidence resolves to a `ParityResult`.
  Where (DESIGN): this bead adds one function, `claim_matches_evidence(row, resolved_evidence)`, to the gate
  recorder's validation (step 7 of the recorder, N38b-19, in this same crate); it returns the harness reason
  `claim-evidence-mismatch` ("the row's claim kind is stronger than the kind its evidence can carry"; repairs, in
  order: record the row with claim `parity`; cite evidence of the claimed kind; leave the gate `not-run`; process
  exit 3, nothing written) when the claim is `reality` and any evidence item is a `ParityResult` of any status.
  The reason is registered in the Gauntlet's harness-reason registry (`registry/reasons.toml`, N38-REF). The
  `synthetic` and `development-oracle` origin labels are refused in the same recorder step by N38b-07's rule;
  this bead does not restate it.

**Rule 3. Foreign tools run out of process and never enter a production dependency graph.**
1. Every `out-of-process` row of the oracle register names its executable or container digest; the runner starts
   it as a child process with a fixed argument vector, a timeout and no shared memory, and reads its output from
   a file.
2. Check `no_foreign_tool_in_production_graph`: for each binary of each workspace (`frob`, `frobd`, `frob-mcp`,
   `frob-verify`, `frob-fsim-worker`), the resolved dependency closure contains no package named in the register
   with posture `out-of-process`, and no binding crate for one. The same rule is enforced continuously by the
   dependency firewall of `xtask check-deps`; this check is the Gauntlet's own planted-failure test of it.
3. An interpreter appears nowhere except the optional Gymnasium-compatible binding, which is never in a
   production graph.

**Oracle hygiene, measured (the M0 part of GATE-GAUNT-05; TARGET).** All four clauses hold:
(a) every fixture has a pin, a date and a capture script; (b) a planted fixture regenerated from the candidate
fails CI; (c) no foreign tool appears in any production dependency graph; (d) a planted tier-G2 result offered as
Reality is refused.

## Acceptance criteria

- [ ] `ParityResult::claim_kind` is a constant; a compile-fail test shows there is no conversion into a reality
      record and no setter for the kind.
- [ ] A planted G2 result submitted for a gate whose claim is `reality` is refused by the recorder, with the
      refusal naming the claim mismatch.
- [ ] A comparison with a published figure prints status `published-anchor` and claim `parity`.
- [ ] The production-graph check passes on the clean tree and fails when a comparator package is added as a
      dependency of any production crate.
- [ ] The four clauses of the hygiene measurement are each measured with a caught control, and the M0 part of
      GATE-GAUNT-05 is recorded by this bead from the tier receipt (`record_gate --part M0`).

## Test plan

### Unit tests

`crates/frob-conformance/tests/parity_typing.rs`:
- `parity_kind_is_constant`: for all four statuses `claim_kind()` is `Parity`.
- `no_reality_conversion` (compile-fail): `RealityRecord::from(parity)` does not compile.
- `no_kind_setter` (compile-fail): assigning the kind does not compile.
- `published_anchor_is_parity`: a comparison of a simulated cost of transport 0.42 with a published 0.45 at
  tolerance 10% yields status `PublishedAnchor`, kind `Parity`.
- `reality_gate_refuses_parity_evidence`: a `reality` row citing a receipt whose entry is a `ParityResult` with
  status `PublishedAnchor` is refused with `claim-evidence-mismatch` and `registries/gates.toml` is unchanged
  (byte-equal before and after); the same receipt recorded under claim `parity` is accepted.
- `wording_is_permitted_form`: the rendered sentence matches "matches … at … within … on …".
- `out_of_process_spawn_only`: an oracle row with posture `out-of-process` and no executable is rejected.
- `production_graph_clean`; `production_graph_plant_caught`.

### End-to-end script and logging

`scripts/e2e/oracle_hygiene.sh` (header: `bead=N38a-05 milestone=M0 labels=gauntlet,oracle,gate

which runs the gate's rows (N38a-04's fixture rows and this bead's typing and production-graph rows) with

<hash> --part M0`, from that receipt, by a session that did not implement the measured rules; the record cites
N38a-04 and this bead. Log at `target/e2e-logs/oracle_hygiene/<utc>.ndjson`: each command with exit code and
wall time, the four clauses as `assert` lines tagged with the gate, the two negative-control assertions, the
count of fixtures and of production binaries inspected as `metric` lines, the receipt hash, and the `summary`.

### Known answers and negative controls

Negative controls (each must be caught): the parity result offered as reality; the comparator added to a
production manifest; the fixture regenerated from the candidate (shared with N38a-04). Counterexample carried:
"two programs that share a solver have correlated error", so agreement of two tiers that consume the same
parameter card cannot reveal a wrong card. Determinism lane: class D0, identical twice.

## Considerations

- No dataset has been admitted to the reality-calibration subsystem; every report therefore prints
  `reality: no-claim`, a legitimate terminal state, and no exported artifact carries a true
  `sim_to_real_certified` flag (the flag has no setter).
- Risk: common-mode error. Every tier consumes the same cards, so tier agreement hides a wrong card; reports that
  support a benchmark claim print the share of card fields whose provenance is `generic` or `assumed`.
- The published-anchor comparison at M3 uses figures recorded at search-summary level; each is re-read from its
  primary source before a gate cites it.
