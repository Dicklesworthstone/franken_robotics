## Background

Every Frontier and Moonshot mechanism of FrankenRobotics needs a small pilot with a falsifier before its work
package is funded. Several pilots (in the control, learning, evaluation, adversarial-world and
counterfactual-debugging subsystems) need rigid-body dynamics with contact, and they are due before this
program's own CPU referee tier exists at M1. The design therefore admits one incumbent simulator at a pinned
release as a *development oracle*: a tool, out of process and outside the product, on which such pilots may run.

The danger is obvious and is the reason for this bead: a result from someone else's simulator could quietly
become evidence about this system. Rule 7 of the oracle rules bounds it: a result obtained on the development
oracle funds or kills a work package and supports no gate; when the same pilot is re-run on the CPU referee and
the verdict differs, the referee's verdict stands and the difference is recorded against the kill gate
KILL-DEVORACLE.

Rejected alternatives: waiting for the referee for every pilot (delays every funding decision past M1);
treating incumbent results as parity evidence (they would then appear in gate rows).

## Scope

In: the register entry and pin; the launcher; setting the label `development-oracle` on every record the lane
produces, with the lane's own stripped-label and gate-citation tests; the re-run queue and the verdict comparison
that feeds the kill gate. Out: the label as a condition flag of the claim product, its propagation rule, its
printing and the general refusal of an unlabeled record (N38b-07, on which this bead depends); which release is
pinned (the decision N38b-35, on which this bead depends); the kill-gate decision itself (N38b-24); each
pilot's protocol (its owning subsystem); the incumbent phase ledger (BD-040).

## Technical approach

1. **Entry and pin.** One row of the oracle register with `id = "development-oracle"`, posture `out-of-process`,
   an exact release and container digest, the licence, and `roles = ["pilot"]` only. It has no parity role and no
   reality role. Until the open question is decided the row is `not-admitted` and the fail-closed default holds:
   there is no development oracle, and the pilots that need dynamics wait for the CPU referee.
2. **Admission test.** A pendulum and a free-falling box on the pinned release reproduce their analytic period
   and impact time within the tool's own stated tolerance; the negative control is the same script at a
   different release, which the version guard refuses.
3. **Launcher.** `tools/oracle/devoracle/run.sh --pilot <id> --protocol <file> --seed <n> --out <dir>` runs on
   the Linux host `trj` under the pinned container, records the run environment (release, driver, card, host
   load, warm or cold caches, repetitions) and writes results with the header `kind = "development-oracle"`. The
   environment record is not the Performance disclosure block `frob.perf.disclosure/1` (N36-13): a lane result
   makes no Performance claim, and no speed figure is taken from it.
4. **Label.** Every record produced by the lane carries `development-oracle` in its evidence; the label is a
   condition flag joined by union through the claim product, so nothing computed from such a record can drop it.
   A record from this lane with the label removed is refused wherever it is offered.
5. **No gate.** The recorder refuses any gate row whose evidence resolves to a `development-oracle` record. The
   pilot register accepts such a record only in a pilot's `result` block, with `site = "development-oracle"`.
6. **Re-run queue.** Each pilot run on the lane gets a queue entry `{pilot, protocol_hash, devoracle_verdict}`.
   When the CPU referee exists, the same frozen protocol is re-run on it; the entry gains `referee_verdict` and
   `changed = (verdicts differ)`. The referee's verdict replaces the development-oracle verdict in the pilot
   register.
7. **Feeding the kill gate.** Trigger of KILL-DEVORACLE (TARGET, decided at M1): of the first five pilots re-run
   on the CPU referee, two or more change verdict. Fallback: development-oracle results lose standing as funding
   evidence; pilots for work packages not yet funded wait for the CPU referee; packages funded on a reversed
   pilot are re-decided. This bead produces the count `changed_of_first_five`; the decision bead reads it.

## Acceptance criteria

- [ ] The register row exists with posture, pin kind and the single role `pilot`; with no pin recorded the lane
      refuses to run and prints the default (wait for the referee).
- [ ] A record produced by the lane carries `development-oracle`; a copy with the label stripped is refused.
- [ ] A gate row citing a lane record is refused.
- [ ] The re-run queue lists every lane pilot; a re-run with a different verdict sets `changed = true` and
      replaces the verdict in the pilot register, keeping the history.
- [ ] `changed_of_first_five` is computed from the queue and is exposed to the kill-gate decision.

## Test plan

### Unit tests

`crates/frob-conformance/tests/devoracle.rs`:
- `role_is_pilot_only`: adding `parity:*` to the row is a load error.
- `label_propagates`: a statistic computed from one labelled and one unlabelled record is labelled.
- `stripped_label_refused` (planted record).
- `gate_refuses_devoracle_evidence`.
- `queue_verdict_change`: verdicts `falsifier-rejected` then `falsifier-holds` (the register's two verdicts)
  give `changed = true`; equal verdicts give `false`.
- `first_five_count`: the sequence (same, changed, same, changed, same) gives 2, which meets the trigger; (same,
  changed, same, same, same) gives 1, which does not.
- `no_pin_no_run`.

### End-to-end script and logging

`scripts/e2e/devoracle_lane.sh` (header: `bead=N38a-06 milestone=M0 labels=gauntlet,pilot,oracle
gates=GATE-GAUNT-08 needs=second-host plants=strip-label`). With a pin recorded it runs the admission test and
one registered pilot protocol on `trj`; without one it asserts the refusal and exits as skipped for the live
steps. It then offers the result to a gate row (refused), strips the label (refused) and prints the queue. Log
at `target/e2e-logs/devoracle_lane/<utc>.ndjson`: commands with exit codes and wall time, the run environment as
`metric` lines, the two refusals, `changed_of_first_five` as a `metric` with threshold `< 2`, and the `summary`.

### Known answers and negative controls

Known answers of the admission test: the small-angle pendulum period 2π·√(L/g) (L = 1 m, g = 9.81 m/s²:
2.0061 s) and the fall time √(2h/g) (h = 1 m: 0.4515 s). Negative controls: the stripped label; a gate citing a
lane record; a run at a release other than the pin. Determinism lane: results of the lane are judged at class
D3 at best; no bitwise claim is made about a foreign tool.

## Considerations

- Kill gate named in advance: KILL-DEVORACLE, trigger and fallback as in step 7; if it fires, every funding
  decision that rested on a reversed pilot is re-decided and pending pilots wait for the referee.
- The lane must not be used as the adjudicating simulator of the ten-fold test in development or tuning.
- Host load on `trj` is recorded with every run; a pilot whose verdict depends on timing states its band.
- Licence of the chosen release is recorded; if it forbids publishing results, pilot records cite revisions and
  fetch instructions only.
