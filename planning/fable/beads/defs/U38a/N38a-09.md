## Background

FrankenRobotics grades every mechanism by ambition: Solid [S] (established engineering), Frontier [F] (published
research not yet productized, or a narrowed form of a mechanism whose strong form failed review) and Moonshot [M]
(a synthesis proposed by this program, behind a feature flag, never on the critical path). The program's hygiene
rule for the two upper tiers: every Frontier and Moonshot mechanism has a *pilot*, a small experiment with
existing tools, outside the workspace, that runs before the mechanism's work package is funded. A pilot is small
enough to run on a CPU in a day, uses exact or hand-checkable arithmetic where it can, is registered before it
runs, and has an outcome that is not known in advance. A pilot that cannot fail is not a pilot. Its result,
including a negative one, is recorded and the mechanism's tier and scope are revised to match.

The Gauntlet (the verification subsystem, crate `frob-conformance`) owns the register and the rule. It does not
own the protocols: each pilot is designed by the subsystem that owns its mechanism (the constructions; the
scene, sensor, GPU, control, learning, evaluation, mission-query, adversarial, counterfactual, calibration and
structure subsystems each tabulate theirs). Dozens of beads across the program write one record into this
register; this bead gives them the file, the schema and the check.

The rule (GATE-GAUNT-08, TARGET): no Frontier or Moonshot work package is funded without a pilot record that has
a falsifier, a computed ceiling, a fallback and a result. A work package whose pilot's falsifier holds is not
funded; its fallback ships.

Two obligations attach to the upper tiers (DESIGN), and the register checks both. Every [F] and [M] item names
a paper-scale pilot with a falsifier that must run before its work package is funded, and states the ceiling of
its benefit before any speed test is run. Every [F] and [M] item has a kill gate with a fallback named in
advance, and the fallback is a mechanism of a lower tier that the design already contains, so that losing the
item costs a capability and never the critical path. The reason is the planning record itself: every pilot run
while the specification was written ended with its strong baseline tying or winning, and one speed test turned
out to have had no power to confirm its own claim. An upper-tier capability counts as implemented only when its
pilot and its kill-gate decision are on record, and a capability that fell back is described by the fallback's
name. At most four [M] items are active at once in any milestone.

Rejected alternative: pilots recorded as prose in a delivery log. A funding decision must be a query over data,
and "the protocol was frozen before the run" must be checkable from hashes and dates.

A second draft of this register, N00-07 (the document-control unit's "pilot ledger"), specified the same file
with another schema name, other field names and another funding function. It is superseded by this bead. One
file, one schema and one rule remain; what that draft had and this one lacked is folded in below (the
completeness check, the Moonshot cap as a refusal, the rule that a fallback is of a lower tier, the `void`
state, the list of refusal reasons, the seed list of pilots still to run, its tests and its end-to-end step),
and each place where the two differed is settled and marked.

## Scope

In: the file, its schema and identifier grammar, the registration-before-run mechanism, the funding check per
mechanism and per package with its refusal reasons, the `S`-tier record a chapter may require, the frozen
sampling-controller count read by `control.mpc`, the completeness check ("every upper-tier mechanism has a row"),
the Moonshot cap, the seed list of pilots still to run, the printout, and the example target `pilots` that serves
the queries. Out: the seed records of the twenty pilots already run at plan time, with their
recorded results and consequences (N38a-10, which enters them in this file as history); re-running those pilots (BD-041, BD-042, BD-043,
BD-030, N38a-11); the development-oracle lane (N38a-06); each pilot's protocol.

## Technical approach

**Record (`crates/frob-conformance/registry/pilots.toml`; schema `frob.gauntlet.pilot/1`).** One file; the short
spelling `registries/pilots.toml` used in some planning notes refers to this same file. One schema name: the
superseded draft called it `frob.pilot/1`, and pilot beads that still write that name mean this schema; the
loader accepts `frob.gauntlet.pilot/1` only (DESIGN: the name the register and the plan-time ledger N38a-10
already share).
```toml
[[pilot]]
id         = "PILOT-RANK-01"                 # grammar below; append-only, never reused or deleted
mechanism  = "…"                             # the mechanism the pilot decides (what would be funded)
tier       = "F"                             # F | M | S (S only with required_by, below)
required_by = "§27.17"                       # required when tier = "S": the subsection that demands the pilot
owner      = "§…"                            # owning section
bead       = "BD-310"                        # the bead that runs the pilot
work_package = "WP-…"                        # what its result funds or kills
gated_beads = ["…"]                          # optional; the mechanism beads whose readiness this record gates
protocol   = { path = "docs/pilots/PILOT-RANK-01.md", blake3 = "…", frozen = "<date>", ledger_seq = "…",
               sampling_episodes_per_design = 24 }   # last field optional, see below
falsifier  = "…"                             # the observable outcome that kills the mechanism, with its number
ceiling    = { statement = "…", value = "…", basis = "…" }   # largest benefit, computed beforehand
fallback   = { ships = "…", kill_gate = "KILL-…",
               also = [{ ships = "…", pilot = "PILOT-…" }] }  # `also` optional, see rule 5
cost       = { cpu_core_h = "…", gpu_h = "0", wall_h = "…", envelope = "default" }
tool       = { name = "…", pin = "…", site = "host" }         # host | development-oracle | referee | batch-cpu
status     = "registered"                    # registered | running | reproduced | differs | falsifier-holds
                                             #   | falsifier-rejected | inconclusive | withdrawn | void
plan_time_records = ["PILOT-PT-08"]          # optional; ids of plan-time ledger records (N38a-10) that hold
                                             #   this mechanism's paper-scale result; never copied here
integrated_gate = "GATE-…"                   # optional; the gate that must still measure the integrated
                                             #   mechanism; a pilot result never sets any part of it
[[pilot.result]]                             # appended, never edited
date = "…"; protocol_blake3 = "…"; site = "…"; environment = "…"; commands = ["…"]
values = [{ name = "…", observed = "…", expected = "…", kind = "exact" }]
verdict = "falsifier-rejected"; limits = ["…"]; receipt = "blake3:…"; synthetic = true
```

Where the superseded draft's record differed (DESIGN, one form kept): the tier is the letter `F` or `M`, not the
word; the protocol's digest and date sit in the `protocol` table (`blake3`, `frozen`), not in top-level
`protocol_digest` and `registered`; `fallback` and `kill_gate` are the two fields of the `fallback` table;
`cost.envelope` holds the envelope class (its `cost.class`); results are appended `[[pilot.result]]` tables, not
one overwritten `result`; its statuses map as `held` → `falsifier-rejected`, `falsified` → `falsifier-holds`,
and `void` is adopted as below. Identifiers are mnemonic, as the pilot beads already write them, and never
reused or deleted.

**Identifier grammar (DESIGN; the loader rejects any other form with `pilot-id-form`, naming the record).**
`^PILOT-(C-[0-9]{2}(-[a-z]+)?|PT-([0-9]{2}|S[0-9])|[A-Z]{2,14}-[0-9]{2})$`:
- `PILOT-C-<nn>`: the pilot of construction C-nn (`PILOT-C-19`, `PILOT-C-40`), with a lower-case suffix when one
  construction has more than one pilot (`PILOT-C-06-law`, `PILOT-C-31-tube`, `PILOT-C-31-shield`).
- `PILOT-PT-<nn>` and `PILOT-PT-S<n>`: the plan-time ledger records of N38a-10 (`S` for its supplementary set).
- `PILOT-<SET>-<nn>` for every other pilot: `<SET>` an upper-case mnemonic of 2 to 14 letters naming the mechanism
  or the chapter, `<nn>` two digits from 01 in registration order within the set. Sets in use at this review
  include RANK, ATLAS, AUTOPSY, KIN, LEMMA, MARROW, SOS, TETHER, PEER, MONO, EQUIV, TRANSPORT, FAMILYKERNEL, and
  the DESIGN ids proposed by the mission-query and synthesis beads, each confirmed here as conforming:
  PILOT-COUPLING-01 (N25e-01), PILOT-WEAKVAR-01 (N25e-23), PILOT-NUISANCE-01 (N25e-40), PILOT-LABELS-01 (N25c-39),
  PILOT-CODESIGN-01, PILOT-TRAJOPT-01, PILOT-PLACEMENT-01 and PILOT-REGRESSOR-01 (N25e-18), beside the
  construction pilots PILOT-C-34 and PILOT-C-40 (N25c-24), and those of the GPU and performance beads:
  PILOT-FLEET-01 (N21c-10, WP-46), PILOT-SPECIALIZE-01 (N21c-17, WP-46), PILOT-MEGA-01 (N21c-21, WP-80) and
  PILOT-SHARD-01 (N36-09, WP-48).
A set needs no registration of its own: uniqueness of the whole identifier is the check. A name without its
two-digit number (an earlier `PILOT-REUSE-GRADE3`, `PILOT-RUNTIME-CLOSURE`, `PILOT-CONTINUUM-ARM`) does not load.

**Registration before run.**
1. The owner writes the protocol file and the record with status `registered`; the protocol's hash and the ledger
   sequence number of the registration are stored.
2. A result may be appended only if its `protocol_blake3` equals the registered hash and its date and ledger
   sequence follow the registration. A result under a changed protocol is rejected; changing a protocol after a
   run needs a new pilot identifier, and the old record keeps its result.
2a. *Committed receipt.* The receipt a result cites (`receipt = "blake3:<hash>"`) is committed byte-identical at
   `receipts/pilots/<hash>.json` (the hash without its `blake3:` prefix) in the commit that appends the result,
   beside the gate receipts under `receipts/gates/` (N40-01, "Where receipts live"). The loader refuses a result
   whose file is absent or whose bytes do not hash to the name (`pilot-receipt-uncommitted`). A kill-gate
   decision of a `pilot-before-funding` row (KILL-FLEET, KILL-SPECIALIZE, KILL-MEGA) cites that hash in its
   `receipts`, and N40-03 resolves it under `receipts/pilots/`.
3. The four mandatory parts are checked at registration: `falsifier` (must contain a comparison with a number or
   an exact count), `ceiling` (a value or the literal `none on speed` with a reason), `fallback.ships` and
   `fallback.kill_gate` (an identifier that exists in the gate register, or `to-register` with the proposed
   wording when the mechanism has no gate yet). DESIGN, where the two drafts differed: `to-register` is accepted
   at registration, so that a pilot can be registered before its gate row exists, and it blocks funding; a
   record funds only when its kill gate exists in the gate register.
4. A pilot whose expected outcome is certain (falsifier text empty, or `cannot fail`) is rejected.
5. `fallback.ships` names a mechanism whose tier is lower than the pilot's (a Moonshot fallback for a Frontier
   mechanism is rejected), so that the fallback is something the design already contains; for `tier = "S"` it
   names a Solid mechanism (nothing is lower). DESIGN, for fallbacks that also ship an upper-tier mechanism only
   where that mechanism's own pilot funded it (PILOT-REGRESSOR-01 also ships the static mass-placement program of
   §25.21 where its pilot funded it): the unconditional part stays in `ships` and must satisfy this rule alone;
   each conditional part goes in `fallback.also` with the identifier of the pilot record that funds it, which must
   exist; an `also` entry never satisfies the lower-tier rule, and it ships only while `fundable` answers
   `Fundable` for that pilot's mechanism.
5a. *Tier S.* The tiers are those of the capability record. A Solid mechanism needs no pilot, but a chapter may
   still require one before its work package is funded (§27.17 does so for the Autopsy coalition machinery).
   Such a record carries `tier = "S"` and `required_by` naming that subsection (a record with `tier = "S"` and no
   `required_by` is rejected, and `required_by` on an F or M record is allowed but not needed). The record is
   entered with its true tier, so the printout and the capability status never show a Solid mechanism as
   Frontier; the funding rule treats it exactly as an upper-tier record; the completeness check does not require
   S mechanisms to have records; the Moonshot cap does not count it.
5b. *Sampling-controller count.* `protocol.sampling_episodes_per_design` (optional, integer ≥ 1) is the episode
   count per design that the pilot's protocol declares for a sampling controller. `control.mpc --protocol <id>`
   (N22a-24) reads it through `pilots::sampling_allowance(id) -> Option<u32>` and admits up to that count for the
   protocol's own jobs; an identifier that is not a registered record, a void record, or a record without the
   field admits nothing beyond the default three. The value is frozen with the protocol: a record whose value
   differs from the one stored at registration is `void` (rule 6).
6. **Void.** The registered protocol hash never changes. If the protocol file in the tree no longer hashes to
   it, the record's effective status is `void`: it blocks funding until the file is restored or the changed
   protocol is registered under a new identifier. Results already appended under the registered hash stay.
   (The superseded draft voided the pilot; this draft rejected the new result and asked for a new identifier.
   Both hold: the result is rejected and the record is void.)

**Load reasons (DESIGN names; registered in `registry/reasons.toml`, N38-REF).** `pilot-id-form` (the grammar
above); `reused` and `removed` (an identifier repeated, or one of the previous commit's missing: the
registry-diff reasons); `pilot-part-missing` (rule 3, naming the part); `pilot-cannot-fail` (rule 4);
`result-protocol-mismatch` and `result-before-registration` (rule 2); `pilot-receipt-uncommitted` (rule 2a);
`fallback-tier-not-lower` (rule 5); `fallback-also-unknown` (an `also` entry naming no record);
`tier-s-without-required-by` (rule 5a); `plan-time-record-unknown` (a `plan_time_records` identifier that is not a
ledger record): twelve load reasons, beside `moonshot-cap` at the status change, which is also a funding reason.

**The funding rule.** It answers per mechanism, and the package answer is derived from those (DESIGN: a work
package may hold independent upper-tier mechanisms, WP-32 holds three: twin-lane ingestion N19c-01, drone-lane
ingestion N33c-25 and `dressing.assets` N19a-40, and a held falsifier on one must not block the beads of
another, nor the fallback work of either; N19c-06 is the interim posture of a held ingestion pilot).
`pilots::fundable_mechanism(work_package, mechanism) -> Fundable | Blocked{reason}` applies the conditions below
to the records of that one mechanism. `pilots::fundable(work_package) -> PackageFunding { status: Fundable |
Partial | Blocked, mechanisms: [(mechanism, pilot ids, Fundable | Blocked{reason})] }` is `Fundable` when every
mechanism of the package is, `Blocked` when none is, `Partial` otherwise. `pilots::fundable_bead(key)` answers
for one bead: the mechanism of every record whose `gated_beads` lists the key, or, for a bead named by no
`gated_beads`, every upper-tier mechanism of its work package (the package answer, so a package with one
mechanism needs no `gated_beads`). A pilot's own bead is never gated by the register: for a key that is the
`bead` of a record (the bead that runs the pilot and produces its verdict), `fundable_bead` ignores that record
and the package answer, and answers `Fundable` with the note `pilot-bead` unless another mechanism's record lists
the key in its `gated_beads`; a record that lists its own `bead` there has that entry ignored, so no pilot waits
on its own result (N33c-25 names this case). The conditions, per mechanism:
- every Frontier or Moonshot mechanism mapped to the work package (and every mechanism with a `tier = "S"`
  record) has a pilot record;
- each such record has a result whose verdict is `falsifier-rejected` (the mechanism survived) or `reproduced`
  (for a re-run of a recorded pilot);
- a verdict `falsifier-holds` blocks the work package and prints the fallback and its kill gate;
- a result whose site is `development-oracle` funds provisionally and is queued for a re-run on the CPU referee;
  such a result funds or kills a work package and supports no gate, and if the referee's verdict differs, the
  referee's verdict stands;
- `inconclusive` blocks, and the record states what would make the pilot decisive;
- a record with a non-empty `plan_time_records` list takes, for its plan-time part, the derived status of the
  linked ledger records instead of a copied result (DESIGN, for the mission-query pilot rows of N25d-40, so that
  one check has one stored result): the part counts as `reproduced` only when **every** linked record's
  status is `reproduced`, a `registered` or `running` record counting as not run (the same mapping that the
  ledger bead N38a-10 exposes as `pilots::rerun_status`; this bead implements the status read in the register,
  so it does not wait for the ledger, and the test uses scratch records); any `differs` makes
  the record `Blocked{plan-time-differs}` naming the record; any `not-run` makes it
  `Blocked{plan-time-not-run}`. A record whose mechanism also has a to-run part still needs its own appended
  result for that part. An identifier in the list that is not a ledger record is a load error. The function
  reads the ledger at call time, so a later `differs` on a linked record withdraws funding readiness without
  editing the mechanism's record. A linked record's `reproduced` never sets `integrated_gate` or any other gate
  row.
`Blocked{reason}` lists every upper-tier mechanism of the package with its reason, one of: `missing` (no
record), `unregistered` (a record without a frozen protocol), `void`, `registered` or `running` (no result
yet), `falsifier-holds`, `inconclusive`, `kill-gate-to-register`, `moonshot-cap`, `plan-time-differs`,
`plan-time-not-run`. A falsified pilot means the
fallback ships, and the mechanism's capability record (N00-02) is printed under the fallback's name. The
milestone-entry review calls `fundable` per package, and the funding decision points of the work packages call
it before a package is opened; a `Partial` package is opened for its fundable mechanisms only. A bead for a
Frontier or Moonshot mechanism is not ready until `fundable_bead` returns `Fundable` for it. The command form is
an example target of this crate (BD-025: the crate has no default binary):
`cargo run -p frob-conformance --example pilots -- fundable --all --json` (every package, with its status and the
per-mechanism lines), `-- fundable --package <WP-nn> --json`, `-- fundable --bead <key> --json` and
`-- complete --json` (the completeness check below). An older spelling `cargo run -p frob-conformance -- pilots
fundable …` in any bead means this command. The superseded draft named the function `may_fund` and the command
`pilots may-fund`; one name is kept.

**Completeness.** Every capability record with tier Frontier or Moonshot (N00-02), every kernel-manifest entry
and every verb-registry row carrying an upper-tier tag must be named by the `mechanism` field of at least one
pilot. `pilots::complete() -> Vec<MissingPilot>` reads whichever of those registries exist at the commit; an
upper-tier mechanism with no row fails the test with its identifier. Beside the failures, `complete` lists as
warnings (printed, not failing; DESIGN) the records without `gated_beads` in a work package that holds more than
one upper-tier mechanism: their mechanism beads are answered by the package, so one held falsifier would block
the others' beads as well (fail-closed, but coarser than the per-mechanism rule); the warning names the record,
its pilot bead and the package's other mechanisms, so the pilot bead can list the beads it gates.

**Moonshot cap.** At most four pilots or work packages of tier `M` have status `running` in one milestone. A
fifth is refused at the status change, and `fundable` reports `moonshot-cap` for its package.

**Seed list of pilots still to run** (known at conversion; each row is registered by the pilot bead of its

**Printout.** `tests/pilots_printout.rs` regenerates `docs/delivery/pilots.md` (one row per pilot: mechanism,
tier, falsifier, ceiling, fallback, status, last verdict) and fails on a hand-edited file.

## Acceptance criteria

- [ ] The file exists and validates; identifiers are append-only (a reused or deleted identifier fails).
- [ ] A record missing its falsifier, ceiling, fallback or kill gate is rejected at registration.
- [ ] A result whose protocol hash differs from the registered one, or that predates registration, is rejected.
- [ ] `fundable` blocks a work package with a missing pilot, with `falsifier-holds`, and with `inconclusive`;
      it allows one whose pilots all carry `falsifier-rejected`.
- [ ] GATE-GAUNT-08, first clause (TARGET): a scan of every funded Frontier or Moonshot work package finds a
      complete pilot record with a result; the scan's count and any violation are recorded.
- [ ] The printout regenerates byte for byte.
- [ ] A pilot whose protocol file changed after registration is `void` and blocks funding; a fallback of a tier
      not lower than the pilot's is rejected at registration; a record whose kill gate is still `to-register`
      blocks funding.
- [ ] `fundable` refuses a package whose Frontier mechanism has no pilot, an unregistered one, a void one, an
      unfinished one or a falsified one, and names the mechanism and the reason in each case.
- [ ] The completeness check fails when an upper-tier capability, kernel-manifest entry or verb row has no pilot
      row, and lists every row of the seed list that is not yet registered.
- [ ] A fifth Moonshot pilot set to `running` in one milestone is refused.
- [ ] A record with `plan_time_records` is fundable for that part only when every linked ledger record is
      `reproduced`, and blocked with `plan-time-differs` or `plan-time-not-run` otherwise; no ledger value is
      copied into it, and no linked result sets a gate.
- [ ] GATE-GAUNT-08 can be evaluated from this file alone: no Frontier or Moonshot work package is funded without
      a pilot record that has a falsifier, a computed ceiling, a fallback and a result.
- [ ] Every identifier on file matches the grammar; a non-conforming one fails the load with `pilot-id-form`.
- [ ] A record with `tier = "S"` loads only with `required_by`, is funded or blocked exactly as an upper-tier
      record, needs a Solid fallback, and is not counted by the Moonshot cap.
- [ ] `fundable` answers per mechanism: a package with one mechanism `falsifier-holds` and another
      `falsifier-rejected` is `Partial`, and `fundable_bead` answers `Fundable` only for the beads of the second.
- [ ] `pilots::sampling_allowance` returns the frozen `protocol.sampling_episodes_per_design` of a registered,
      non-void record and `None` otherwise; a changed value voids the record.
- [ ] A `fallback.also` entry must name an existing pilot record and never satisfies the lower-tier rule.
- [ ] Every load rejection and every `Blocked` reason is a reason string of `registry/reasons.toml` (N38-REF, a
      dependency) and is printed as `reason=<id>`; the load reasons are the twelve listed above.
- [ ] A result whose receipt is not committed at `receipts/pilots/<hash>.json`, or whose committed bytes do not
      hash to that name, is refused with `pilot-receipt-uncommitted`.
- [ ] `fundable_bead` of a record's own `bead` answers `Fundable` (note `pilot-bead`) whatever that record's or its
      package's status, unless another mechanism's record gates it.
- [ ] `complete` warns, without failing, for each record without `gated_beads` in a package holding more than one
      upper-tier mechanism; `pilots_expected.toml` holds the KILL-SHARD row and the `pilot` identifiers of the
      FLEET, SPECIALIZE, MEGA and SHARD rows.

## Test plan

### Unit tests

`crates/frob-conformance/tests/pilot_register.rs`:
- `schema_roundtrip`: a complete record parses and re-serializes to the same canonical bytes.
- `four_parts_required`: four planted records, each missing one part, each rejected naming the part.
- `cannot_fail_rejected`: falsifier `"none"` is rejected.
- `result_needs_frozen_protocol`: a result with a different hash is rejected; with the same hash accepted.
- `result_before_registration_rejected`.

### End-to-end script and logging

`scripts/e2e/pilot_register.sh` (header: `bead=N38a-09 milestone=M0 labels=gauntlet,pilot,gate
gates=GATE-GAUNT-08 plants=unfunded-without-pilot,protocol-changed,receipt-uncommitted`). In a scratch registry
it registers a pilot, appends a result with its receipt committed at `receipts/pilots/<hash>.json` of the scratch
tree, queries the funding rule (and `fundable --bead` of the pilot's own bead, which answers `Fundable` with the
note `pilot-bead`), then plants a funded work package with no pilot, a result under a changed protocol and a
result whose receipt file is absent, requiring each to be caught. Log at `target/e2e-logs/pilot_register/<utc>.ndjson`:
commands with exit codes and wall time, the number of pilots per status as `metric` lines, the funding verdict
per work package, the three negative-control assertions with their reasons, and the `summary` naming
GATE-GAUNT-08. A further step,
`all_upper_tier_packages_at_m0` (folded from the superseded draft's `scripts/e2e/pilot_ledger.sh`, which is not
written), loads the real file, calls `fundable --all --json` for every work package tagged [F] or [M],
and asserts that at M0 every such package is refused with a named reason; it logs per package an `assert` line
with mechanisms, pilot ids, statuses and the refusal reason, and the counts of packages fundable, partial and
refused. A last step builds a scratch package with two Frontier mechanisms, gives one a `falsifier-holds` result
and the other `falsifier-rejected`, and asserts `Partial`, with `fundable --bead` answering `Fundable` for a bead
gated by the second and `Blocked{falsifier-holds}` for a bead gated by the first. Every call uses the example form
`cargo run -p frob-conformance --example pilots -- …`.

## Considerations

- At most four Moonshot items are active at once; the funding rule reports the count of active [M] pilots, and
  the cap is enforced as stated above.
- The register is read by the funding check, by the capability status function and by the milestone exit
  review; it is not a place for narrative. A negative pilot result revises the mechanism's tier and scope in the
  same change; it is never left as a footnote.
- The plan-time check ledger of the document-control unit (N00-06) is a separate record of nine checks; it
  depends on re-run beads that depend on this register, so this bead cannot depend on it, and the gate is
  evaluated from this file alone.
- A pilot outside the default machine envelope names its budget in `cost.envelope` and waits for approval.
- Risk named in the program's pre-mortem: breadth starves the spine; the signal is a work package funded without
  its pilot, which this check turns into a failure.
- Pilots are evidence for funding, never for a gate of the product; their records are labelled `synthetic` or
  `development-oracle` where that applies.
