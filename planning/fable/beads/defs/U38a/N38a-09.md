## Background

FrankenRobotics grades every mechanism by ambition: Solid [S] (established engineering), Frontier [F] (published
research not yet productized, or a narrowed form of a mechanism whose strong form failed review) and Moonshot [M]
(a synthesis proposed by this program, behind a feature flag, never on the critical path). The program's hygiene
rule for the two upper tiers: every Frontier and Moonshot mechanism has a *pilot*, a small experiment with
existing tools, outside the workspace, that runs before the mechanism's work package is funded. A pilot is small
enough to run on a CPU in a day, uses exact or hand-checkable arithmetic where it can, is registered before it
runs, and has an outcome that is not known in advance. A pilot that cannot fail is not a pilot. Its result,
including a negative one, is recorded and the mechanism's tier and scope are revised to match.

The Gauntlet (the verification subsystem, crate `frob-conformance`) owns the register and the rule. It does not
own the protocols: each pilot is designed by the subsystem that owns its mechanism (the constructions; the
scene, sensor, GPU, control, learning, evaluation, mission-query, adversarial, counterfactual, calibration and
structure subsystems each tabulate theirs). Dozens of beads across the program write one record into this
register; this bead gives them the file, the schema and the check.

The rule (GATE-GAUNT-08, TARGET): no Frontier or Moonshot work package is funded without a pilot record that has
a falsifier, a computed ceiling, a fallback and a result. A work package whose pilot's falsifier holds is not
funded; its fallback ships.

Rejected alternative: pilots recorded as prose in a delivery log. A funding decision must be a query over data,
and "the protocol was frozen before the run" must be checkable from hashes and dates.

## Scope

In: the file, its schema, the registration-before-run mechanism, the funding check, the printout. Out: the seed
records of the pilots already run at plan time (N38a-10); re-running those pilots (BD-041, BD-042, BD-043,
BD-030, N38a-11); the development-oracle lane (N38a-06); each pilot's protocol.

## Technical approach

**Record (`crates/frob-conformance/registry/pilots.toml`; schema `frob.gauntlet.pilot/1`).**
```toml
[[pilot]]
id         = "PILOT-0031"                    # append-only
mechanism  = "…"                             # the mechanism the pilot decides
tier       = "F"                             # F | M  (an S mechanism needs no pilot)
owner      = "§…"                            # owning section and bead key
work_package = "WP-…"                        # what its result funds or kills
protocol   = { path = "docs/pilots/PILOT-0031.md", blake3 = "…", frozen = "<date>", ledger_seq = "…" }
falsifier  = "…"                             # the observable outcome that kills the mechanism, with its number
ceiling    = { statement = "…", value = "…", basis = "…" }   # largest benefit, computed beforehand
fallback   = { ships = "…", kill_gate = "KILL-…" }
cost       = { cpu_core_h = "…", gpu_h = "0", wall_h = "…", envelope = "default" }
tool       = { name = "…", pin = "…", site = "host" }         # host | development-oracle | referee | batch-cpu
status     = "registered"                    # registered | running | reproduced | differs | falsifier-holds
                                             #   | falsifier-rejected | inconclusive | withdrawn
[[pilot.result]]                             # appended, never edited
date = "…"; protocol_blake3 = "…"; site = "…"; environment = "…"; commands = ["…"]
values = [{ name = "…", observed = "…", expected = "…", kind = "exact" }]
verdict = "falsifier-rejected"; limits = ["…"]; receipt = "blake3:…"; synthetic = true
```

**Registration before run.**
1. The owner writes the protocol file and the record with status `registered`; the protocol's hash and the ledger
   sequence number of the registration are stored.
2. A result may be appended only if its `protocol_blake3` equals the registered hash and its date and ledger
   sequence follow the registration. A result under a changed protocol is rejected; changing a protocol after a
   run needs a new pilot identifier, and the old record keeps its result.
3. The four mandatory parts are checked at registration: `falsifier` (must contain a comparison with a number or
   an exact count), `ceiling` (a value or the literal `none on speed` with a reason), `fallback.ships` and
   `fallback.kill_gate` (an identifier that exists in the gate register, or `to-register` with the proposed
   wording when the mechanism has no gate yet).
4. A pilot whose expected outcome is certain (falsifier text empty, or `cannot fail`) is rejected.

**The funding rule.** `pilots::fundable(work_package) -> Fundable | Blocked{reason}`:
- every Frontier or Moonshot mechanism mapped to the work package has a pilot record;
- each such record has a result whose verdict is `falsifier-rejected` (the mechanism survived) or `reproduced`
  (for a re-run of a recorded pilot);
- a verdict `falsifier-holds` blocks the work package and prints the fallback and its kill gate;
- a result whose site is `development-oracle` funds provisionally and is queued for a re-run on the CPU referee;
- `inconclusive` blocks, and the record states what would make the pilot decisive.
A bead for a Frontier or Moonshot mechanism is not ready until this function returns `Fundable` for its work
package.

**Printout.** `tests/pilots_printout.rs` regenerates `docs/delivery/pilots.md` (one row per pilot: mechanism,
tier, falsifier, ceiling, fallback, status, last verdict) and fails on a hand-edited file.

## Acceptance criteria

- [ ] The file exists and validates; identifiers are append-only (a reused or deleted identifier fails).
- [ ] A record missing its falsifier, ceiling, fallback or kill gate is rejected at registration.
- [ ] A result whose protocol hash differs from the registered one, or that predates registration, is rejected.
- [ ] `fundable` blocks a work package with a missing pilot, with `falsifier-holds`, and with `inconclusive`;
      it allows one whose pilots all carry `falsifier-rejected`.
- [ ] GATE-GAUNT-08, first clause (TARGET): a scan of every funded Frontier or Moonshot work package finds a
      complete pilot record with a result; the scan's count and any violation are recorded.
- [ ] The printout regenerates byte for byte.

## Test plan

### Unit tests

`crates/frob-conformance/tests/pilot_register.rs`:
- `schema_roundtrip`: a complete record parses and re-serializes to the same canonical bytes.
- `four_parts_required`: four planted records, each missing one part, each rejected naming the part.
- `cannot_fail_rejected`: falsifier `"none"` is rejected.
- `result_needs_frozen_protocol`: a result with a different hash is rejected; with the same hash accepted.
- `result_before_registration_rejected`.
- `fundable_matrix`: verdicts (rejected, rejected) → `Fundable`; (rejected, holds) → `Blocked` naming the
  fallback; (rejected, missing) → `Blocked`; (inconclusive) → `Blocked`.
- `devoracle_funds_provisionally`: flagged `provisional` and queued.
- `ids_append_only`.

### End-to-end script and logging

`scripts/e2e/pilot_register.sh` (header: `bead=N38a-09 milestone=M0 labels=gauntlet,pilot,gate
gates=GATE-GAUNT-08 plants=unfunded-without-pilot,protocol-changed`). In a scratch registry it registers a
pilot, appends a result, queries the funding rule, then plants a funded work package with no pilot and a result
under a changed protocol, requiring each to be caught. Log at `target/e2e-logs/pilot_register/<utc>.ndjson`:
commands with exit codes and wall time, the number of pilots per status as `metric` lines, the funding verdict
per work package, both negative-control assertions, and the `summary` naming GATE-GAUNT-08.

### Known answers and negative controls

Known answer for the schema: the docking pilot's record (two gains: 561 cells, 344 admitted, 217 excluded, nine
on the boundary; falsifier "one grid cell where the closed form and an independently written scenario-tree
linear program disagree"; ceiling "a witness ends a futile policy search and does not speed a search that can
succeed"; fallback "witnesses are checked when supplied and not searched for"). Negative controls: the funded
package with no pilot; the changed protocol; the missing falsifier; the edited printout. Determinism lane: class
D0; identical twice.

## Considerations

- At most four Moonshot items are active at once; the funding rule reports the count of active [M] pilots.
- A pilot outside the default machine envelope names its budget in `cost.envelope` and waits for approval.
- Risk named in the program's pre-mortem: breadth starves the spine; the signal is a work package funded without
  its pilot, which this check turns into a failure.
- Pilots are evidence for funding, never for a gate of the product; their records are labelled `synthetic` or
  `development-oracle` where that applies.
