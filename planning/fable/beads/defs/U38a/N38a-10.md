## Background

Before any FrankenRobotics code existed, twenty small pilots were run on the program's load-bearing ideas. Each
is a FACT about a small program on a small model, kept in one reproduction archive (the single `.zip` in
`planning/`). They shaped the design: several rules of the program exist because of one of them. The program's
rule is that each is re-run at M0 inside this repository and recorded before any gate cites it (GATE-GAUNT-08,
second clause, TARGET: the plan-time pilots re-run at M0 and reproduce every count exactly and every timing ratio
inside its recorded band).

This bead seeds the pilot register with the twenty rows as data: the expected values, the consequence each had,
which bead re-runs it, and the three statements of what the pilots did not do. The re-run beads then append
results to these records; the ledger makes "all twenty re-run" a query. Rejected alternative: each re-run bead
inventing its own record; the M0 exit could then not tell a missing pilot from one never listed.

## Scope

In: twenty seed records, their expected values, owners, limits; the completeness check. Out: executing any pilot
(the owner beads); the register's schema and funding rule (N38a-09).

## Technical approach

**Seed records.** One `[[pilot]]` per row with `status = "registered"`, `tool.site = "host"` (or as stated),
`synthetic = true`, and an `expected` list. Counts and rationals are `kind = "exact"`; printed decimals are
`kind = "printed-digits"`; timing ratios are `kind = "band"`.

**Limits, stored once as `limits` and copied into every result (what the pilots did not do is part of the
record).**
1. None used FrankenSim dynamics, FrankenSim contact or a real sensor pipeline. The analytic pilots used small
   CPU programs and conventional solvers; the native runs executed one scalar decision kernel; the planar sill
   pilots used their own law and scorer. No hypothesis of the program was tested by running FrankenRobotics
   code, because none existed.
2. Every pilot's strong baseline tied or won. A lifted linear program tied the projection; a programmed expert
   tied the probe generator and direct measurement beat both on the withheld law; exact Bayes tied the sensor
   calculation; a scenario tree tied the docking family; a dependency graph tied the receipt; quantifier
   elimination produced the pusher answers. What survives is an interface and a discipline, not a speed claim.
3. No physical claim follows. The material laws are artificial, the loads stipulated, the plants scalar.

**Completeness check (`tests/plan_time_pilots.rs`).** (a) Exactly twenty seed records exist with the identifiers
`PILOT-PT-01` … `PILOT-PT-20`. (b) Each names a re-run owner. (c) At M0 exit each has at least one result;
`reproduced` requires every `exact` expected value to match and every `band` value to lie in its band;
otherwise `differs` with both values. (d) No gate row cites a plan-time pilot value unless the record is
`reproduced`. (e) Every result carries the three limits and `synthetic = true`.

**Bands for timing ratios (DESIGN, since none is recorded).** The band of a ratio is the minimum to maximum of
the per-trial ratios in the original receipt (for the pusher: nine warm and nine fresh-process pairs). A re-run
median outside the band is recorded as `differs` with both values.

## Acceptance criteria

- [ ] Twenty seed records exist with the expected values of the table and the three limits.
- [ ] The completeness check passes when all twenty have results and fails naming any pilot without one.
- [ ] A record marked `reproduced` with one mismatching exact value fails the check.
- [ ] A gate row citing a pilot that is `registered` or `differs` is refused.
- [ ] The M0 summary line reads: pilots re-run n of 20, reproduced r, differing d, each difference listed.

## Test plan

### Unit tests

- `twenty_seed_records`: identifiers 01 to 20, each with owner and at least one expected value.
- `expected_values_typed`: 344, 217, 9 and 561 are `exact` integers; 27/32 is an exact rational; 1.345 is a
  `band` value; 0.9207 is `printed-digits`.
- `reproduced_requires_all_exact`: a result with 343 admitted is `differs`.
- `band_from_receipt`: the band of nine ratios (1.21 … 1.48) is [1.21, 1.48]; 1.50 is outside.
- `limits_copied`: a result without the three limits is rejected.
- `gate_cannot_cite_unreproduced`.
- `sum_checks`: 344 + 217 = 561; 521 + 521 + 0 + 1,103 = 2,145; 7 + 87 = 94 and 94 + 62 = 156; 675 + 225 = 900.

### End-to-end script and logging

`scripts/e2e/plan_time_pilots.sh` (header: `bead=N38a-10 milestone=M0 labels=gauntlet,pilot
gates=GATE-GAUNT-08 plants=missing-rerun`). It loads the ledger, prints the status table, runs the completeness
check, and with `missing-rerun` planted (one result removed in a scratch registry) requires the failure. Log at
`target/e2e-logs/plan_time_pilots/<utc>.ndjson`: the counts re-run, reproduced and differing as `metric` lines
against the threshold 20 of 20, one `assert` per pilot, the negative control, and the `summary`.

### Known answers and negative controls

The table's values are the known answers of the ledger; the arithmetic identities of `sum_checks` guard against
transcription errors. Negative controls: the removed result; the altered count; a result with a protocol hash
that differs from the frozen one. Determinism lane: the ledger check is class D0.

## Considerations

- The archive on disk at drafting time is a later revision than the digest recorded with the pilots; each re-run
  records the digest it actually used.
- Rows 19 and 20 were computed by scripts that were not retained; their re-run re-creates the computation
  (N38a-11) and a difference from the recorded range is a finding, not a failure of the re-run.
- The ceiling value of row 9 was first printed with a withdrawn attribution (1.345 ÷ 0.94 = 1.43); the ledger
  carries the corrected derivation 842.8 ÷ 575.7 = 1.46.
