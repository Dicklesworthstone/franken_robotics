## Background

Before any FrankenRobotics code existed, twenty small pilots were run on the program's load-bearing ideas:
static, scalar or toy-dynamics programs with expectations registered before they ran. Each is a FACT about a
small program on a small model, not about FrankenRobotics, kept in one reproduction archive (the single `.zip`
in `planning/`). They were run outside this repository, and the program re-derived several of their values by
hand or by script without re-executing the archive. **None of them uses FrankenSim dynamics, contact or a real
sensor pipeline; the integrated system remains a hypothesis.** They shaped the design: several rules of the
program exist because of one of them. Two things follow. Each pilot is re-run at M0 inside this repository and
recorded before any gate cites it (GATE-GAUNT-08, second clause, TARGET: the plan-time pilots re-run at M0 and
reproduce every count exactly and every timing ratio inside its recorded band). And every sentence that leans on
one must be traceable to its row.

This bead is the one ledger of those checks and of their re-run status. It seeds the pilot register with the
twenty rows as data: the expected values, the consequence each had, which bead re-runs it, and the three
statements of what the pilots did not do. The re-run beads then append results to these records; the ledger
makes "all twenty re-run" a query.

The same checks are named in three places of the planning record, and the ledger joins them by identifier
instead of keeping three lists: the twenty-row pilot table (the rows of this ledger, the set that the gate
counts); a nine-row review table that groups them and says what each supports (the `review_group` and
`supports` fields below); and the 25-row table of the source register, which gives each check a citable source
id `SRC-CHK-nn` (bead NAB-15; the `covers` field below). Two checks of the source register lie outside the
twenty and were made with scripts that were not retained (a CPU reference rate and the Metal memory limits);
they get supplementary records here so that their re-run status has one home as well.

Rejected alternatives. (1) Each re-run bead inventing its own record: the M0 exit could then not tell a missing
pilot from one never listed. (2) A second ledger file for re-run status beside the pilot register (a file
`plan_time_checks.toml` with identifiers `PTC-nn` was drafted and is withdrawn, DESIGN): two files would hold
the status of one check, and the re-run beads already write their results into the pilot register.

## Technical approach

**File and identifiers.** The records live in the pilot register `crates/frob-conformance/registry/pilots.toml`
(schema `frob.gauntlet.pilot/1`, N38a-09), in a block marked `plan_time = true`. The twenty are
`PILOT-PT-01` … `PILOT-PT-20` with `set = "§38.5"`; the four supplementary records are `PILOT-PT-S1`,
`PILOT-PT-S2`, `PILOT-PT-S3` and `PILOT-PT-S4` with `set = "supplementary"`. Identifiers are append-only.

**Seed records.** One `[[pilot]]` per row with `status = "registered"`, `tool.site = "host"` (or as stated),

register that this record's status governs), `bundle_receipt` (the digest of the check's receipt inside the
reproduction archive, or `none: script not retained`, or `none: not in the plan-time record` for a check the

**Limits (what the pilots did not do is part of the record).** The text of record is stored once, on the
archive record `SRC-REC-05` of the source register (NAB-15); the ledger reads it from there and copies it into
every result at append time (DESIGN: one stored text, so the two registers cannot drift). The three limits:
1. None used FrankenSim dynamics, FrankenSim contact or a real sensor pipeline. The analytic pilots used small
   CPU programs and conventional solvers; the native runs executed one scalar decision kernel; the planar sill
   pilots used their own law and scorer. No hypothesis of the program was tested by running FrankenRobotics
   code, because none existed.
2. Every pilot's strong baseline tied or won. A lifted linear program tied the projection; a programmed expert
   tied the probe generator and direct measurement beat both on the withheld law; exact Bayes tied the sensor
   calculation; a scenario tree tied the docking family; a dependency graph tied the receipt; quantifier
   elimination produced the pusher answers. What survives is an interface and a discipline, not a speed claim.
3. No physical claim follows. The material laws are artificial, the loads stipulated, the plants scalar.

The first limit is printed in the header of every report generated from the ledger.

**Reproduction rule.** A result appended by a re-run bead carries, beyond the register's result fields, the
commit, the hardware fingerprint, the seed, and the archive revision it ran (commit and digest, per NAB-15).
- The revision rule of the source register (NAB-15): a record's expected values are compared with the output
  of the **cited** revision (commit `a635b91`, 241,568 bytes, SHA-256
  `0326e89d76b88a2aa7d198d53556f80ab131fe5a902113dd37f7f32e93b09a4f`, recovered from repository history); a run
  on the working-tree revision (commit `47e8e89`, 275,178 bytes, SHA-256
  `9620da42ec82c175209bbcea21ec71d376da31b687f4f2729e36c20476cd7980`) is a second result on the same record. A
  record that has only a working-tree result stays `not-run` for the cited comparison and says so.
- An `exact` value reproduces only if exactly equal; a `printed-digits` value if equal to the printed digits; a
  `range` value if contained; a `band` value if inside its band.
- A record is `reproduced` when every expected value of every appended result reproduces; otherwise `differs`,
  with both values kept. An expected value for which a result carries no observed value does not reproduce
  (`differs`, listed as missing). A difference is never rounded to agreement.
- When a record becomes `differs`, the check lists the statements that cite it (from the citation lint's
  report) for review, and the hypothesis-register row it supports is reopened through the append-only register
  (N00-10), never by editing the old record.
- Row 9: the ceiling is recomputed from the re-run's own residual (full median ÷ residual), not copied from the
  recorded 1.46.

**Bands for timing ratios (DESIGN, since the plan records none).** The band of a ratio is the minimum to
maximum of the per-trial ratios in the original receipt (for the pusher: nine warm and nine fresh-process
pairs). A re-run median outside the band is recorded as `differs` with both values. This is the convention of
the re-run bead BD-043. Rejected: a fixed band of ±15% around each recorded median (drafted, withdrawn): the
receipt's own spread is evidence, an arbitrary percentage is not, and two conventions for one band would let a
re-run reproduce under one and differ under the other.

**Derived re-run status (the one interface other tools read).** `pilots::rerun_status(id) -> not-run |
reproduced | differs`: `not-run` while the record's status is `registered` or `running` (no result yet),
otherwise the record's status. `pilots::status_of_source("SRC-CHK-nn")` returns the status of the record whose
`covers` lists that id, and `not-run` for a source id that no record covers (fail closed: `SRC-CHK-13` has no
row in the twenty and is covered by the supplementary record S3; `SRC-CHK-24` and `SRC-CHK-25` are covered by no
record and stay uncitable by a gate until their re-run owner adds a supplementary record). The source register sets `reread_before_gate` of a plan-check source from
this function, and the citation lint (NAB-10) reads it.

**Command forms (two subcommands of the `pilots` example target of N38a-09; the crate has no default binary).**
They are the one path by which a re-run bead's script reaches the ledger, so that no script edits the registry
file by hand (BD-041, N38a-11 and N00-35 call them; the other re-run owners, BD-030, BD-042, BD-043 and
N16c-45, append the same result fields and are asked to use the same commands):
- `cargo run -p frob-conformance --example pilots -- append-result <record> --result <file.json> [--registry
  <path>]` appends one `[[pilot.result]]` to the plan-time record `<record>` from a JSON document with `bead`
  (the key of the appending bead), the result fields of the register (date, protocol hash, site, environment,
  commands, values) and those of the reproduction rule below (commit, hardware fingerprint, seed, archive
  revision and digest). The append path
  copies the stored limits into the result, compares every value with the record's `expected` list and derives
  the record's status; the document carries no status, and one that states `reproduced` or `differs` is
  rejected. It refuses, with a reason of `registry/reasons.toml` and a non-zero exit, an unknown record, a record
  outside the `plan_time` block, a result under another protocol hash, a document whose limits differ from the
  stored text, and a `bead` that is not the record's `rerun_owner` (`unexpected-owner`). It prints the record's
  derived status. `--registry` names a scratch copy for tests; the default is the real file.
- `cargo run -p frob-conformance --example pilots -- rerun-status <record> --json [--registry <path>]` prints
  `pilots::rerun_status` for a record, or `pilots::status_of_source` when `<record>` is a `SRC-CHK-nn` id: the
  status (`not-run`, `reproduced`, `differs`), the number of results, and whether a cited-revision result is
  among them. It exits 0 for every status and non-zero only for an identifier that is neither.

**Completeness check (`tests/plan_time_pilots.rs`).** (a) Exactly twenty seed records exist with the
identifiers `PILOT-PT-01` … `PILOT-PT-20`, and the four supplementary records. (b) Each names a re-run owner
and a bundle receipt or one of the two `none:` reasons. (c) At M0 exit each of the twenty has at least one result; `reproduced`
requires every `exact` expected value to match and every `band` value to lie in its band; otherwise `differs`
with both values. (d) Every `SRC-CHK` id is covered by at most one record, and the uncovered ids are printed.
(e) Every result carries the three limits, and the record's `limits_extra` where it has one, equal to the
stored text, and `synthetic = true`. (f) Cross-check
(`ledger_and_sources_agree`): every figure that appears both in a record's `expected` list and in the source
record it covers is equal under exact typed comparison; a mismatch fails with
`pilot.expected-differs-from-source` naming both values. The source register's figures are the values of record
for citation; the ledger's `expected` values are what a re-run is compared with; this test keeps them one list.

## Acceptance criteria

- [ ] Twenty seed records and four supplementary records exist with the expected values of the tables, their
      re-run owners, review groups, `covers` ids and bundle receipts, the three limits, and the fourth limit as
      `limits_extra` on rows 1 to 12, 15, 16 and S3; S4 names N16c-45, covers no source id and carries
      `bundle_receipt = "none: not in the plan-time record"`.
- [ ] `append-result` appends a result and prints the derived status; it rejects a document that states a
      status, a foreign owner, another protocol hash and altered limits; `rerun-status` prints the status of a
      record and of a source id.
- [ ] Rows 19 and 20 name N38a-11 as their only `rerun_owner`; a record listing a second owner is reported by
      the completeness check as `unexpected-owner` (a harness reason of `registry/reasons.toml`, N38-REF).
- [ ] The completeness check passes when all twenty have results and fails naming any pilot without one.
- [ ] A record marked `reproduced` with one mismatching exact value fails the check; 11,519 of 11,520 and 560 of
      561 are `differs`.
- [ ] `rerun_status` returns `not-run` for a `registered` record and for an uncovered source id; the citation
      lint's refusal of a gate row that cites such a record is tested in NAB-10 against this function.
- [ ] `ledger_and_sources_agree` passes on the seed data and fails on a planted transcription error.
- [ ] After BD-030, BD-041, BD-042, BD-043, N38a-11 and N00-35 close, every record (the twenty and S1 to S3) is
      `reproduced` (every count exact, every timing ratio inside its band) or `differs` with the consequences
      listed; S4 stays `not-run` until N16c-45 runs at M2 and is not counted in the M0 summary. This bead closes
      on the check's behaviour over scratch registries; the real count is read at the M0 exit.
- [ ] GATE-GAUNT-08's re-run clause can be evaluated from this ledger alone.
- [ ] The M0 summary line reads: pilots re-run n of 20, reproduced r, differing d, each difference listed.
- [ ] The statement "none uses FrankenSim dynamics, contact or a real sensor pipeline" is printed in the header
      of every report generated from the ledger.

### End-to-end script and logging

`scripts/e2e/plan_time_pilots.sh` (header: `bead=N38a-10 milestone=M0 labels=gauntlet,pilot
gates=GATE-GAUNT-08 plants=missing-rerun`). It loads the ledger, prints the status table, runs the re-run
commands of the owning beads where they are available and appends their results to a scratch copy of the
registry (`append-result … --registry <scratch>`), prints each record's status with `rerun-status`, runs the

failure. Log at `target/e2e-logs/plan_time_pilots/<utc>.ndjson`: per check a `metric`
line with recorded value, re-run value, band and verdict; the commit, fingerprint and seed; the counts re-run,
reproduced, differing and not-run as `metric` lines against the threshold 20 of 20; one `assert` per pilot; the
negative control; and the `summary` naming GATE-GAUNT-08. (One script; a second script name
`plan_time_checks.sh` was drafted for the same run and is withdrawn.)

## Considerations

- The archive on disk at drafting time is a later revision than the digest recorded with the pilots (the cited
  revision is in repository history at commit `a635b91`, as above); each re-run
  records the digest it actually used. If the archive cannot be located, the affected rows are re-derived from
  first principles by their re-run beads and the record says `bundle_receipt = "unavailable"`.
- A re-run that differs is a result, not an embarrassment: it changes a hypothesis verdict through the
  append-only register, never by editing the old record.
- Rows 19 and 20 were computed by scripts that were not retained; their re-run re-creates the computation and a
  difference from the recorded range is a finding, not a failure of the re-run.
- Row 15 ran on the three GPUs; its re-run needs both machines and is the only row that does.
- The ceiling value of row 9 was first printed with a withdrawn attribution (1.345 ÷ 0.94 = 1.43); the ledger
  carries the corrected derivation 842.8 ÷ 575.7 = 1.46.
- The ledger is seeded first and the re-run beads append to it: it depends on none of them.
