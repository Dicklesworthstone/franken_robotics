## Background

A *known answer* is a case whose truth is known without the system under test: an analytic value, an exact
count, a synthetic construction. In FrankenRobotics the claim "the implementation recovers an analytic or
synthetic truth" is one of seven kinds of claim and is established only by a known-answer test with a derivation
on file. The Gauntlet (the verification subsystem, crate `frob-conformance`) owns the suite as data: the
registry is the authority and the printed suite in the planning documents is its printout. At plan time the suite
has 835 rows, KA-001 to KA-835, grouped by chapter, each with its truth, tolerance, tier and negative control
(FACT, counted from the registry's seed): by tier 135 at G0, 591 at G1, 16 at G2, 36 at G3, 19 at G4 and 38 at
G5; 14 rows carry a printed mark (≡) sharing the fixture of an earlier row in another chapter. The appendix legend
leaves the complete map to the registry, so more rows name an earlier row's fixture through `same_as` than the
fourteen printed marks show.

It replaces an earlier, shorter list, every item of which must be carried as rows: group and cone laws; mobility
of the Sarrus, Bennett and four-bar linkages; growth vectors; Elroy's beanie; pendulum, top and ballistic
invariants; the contact battery; motor and thermal constants; sensor readings; the mass-spiral fixed point; leg
inverse-kinematics solution counts; ledger closure for a damped pendulum.

DESIGN: one row per case and site-independent truth, in TOML, with the printout generated. Reason: a hand-edited
table drifts from the tests that back it. Rejected: known answers embedded only in test source (cannot be
counted, joined to gates or printed).

## Scope

In: the file and row schema; the loader's validation; the five rules for a row; the derivation-file format; the
eligibility states; the printout generator; the carried-list audit; the plan-time counts as assertions. Out: the
rows themselves (each chapter's registry bead); running rows on tiers and the gate's accounting (N38a-13); the
decisions on missing tolerances and controls (N38b-27 for the 133 rows printed `to set`, N38b-28 for the 325
rows that state no control, and the chapter beads that pay the owed controls, such as N38b-34), which fill rows
this loader already accepts as obligations.

## Technical approach

**Row (`crates/frob-conformance/registry/known_answers.toml`; one `[[ka]]` per row).**
```toml
[[ka]]
id        = "KA-501"                       # append-only; never reused, never renumbered
section   = "§20.16"                       # where stated; plus owner = "GATE-SENS-13" | "PO-…" | "INV-…"
fixture   = "docking-grid"                 # fixture identity; rows sharing a physical case share this name
same_as   = ""                             # "KA-nnn" when the row uses the fixture of an earlier row
case      = "U = ½ + i/32, i = 0…16; ε = j/64, j = 0…32"
truth     = { kind = "counts", value = { admitted = 344, excluded = 217, boundary = 9 } }
tolerance = { kind = "exact" }             # exact | abs | rel | printed-digits | gate | to-set
tier      = "G1"; sites = ["host", "strict", "cuda", "metal"]
control   = { text = "Unguarded single precision misclassifies near the boundary", nc = ["NC-…"] }
derivation = "docs/derivations/docking-fixture.md"
label     = "DESIGN"                       # DESIGN arithmetic | FACT (pilot, sibling source or publication)
due       = "M1"
printed   = ""                             # the value as first printed, when a recomputation disagrees
slug      = ""                             # optional: the provisional tag of a row appended after plan time
```
`slug` mirrors the field of the counterexample catalogue (N38b-05): a late case first cited by a working tag
(`reflex-lift-linear`, `trac-ka-bound`) keeps that tag here after its number is issued, so the mapping from tag
to number is in the data; the tag is unique across rows and is empty on the 835 plan-time rows.

One optional field is not shown in the example: `safe = "higher" | "lower"`, the declared safe direction of a row
whose truth is a threshold, which rule 3 of the control loader reads (N38b-28: a control whose planted value is not
strictly on the unsafe side is rejected `cannot-fail`): `"higher"` for an episode count, a margin or a bound on an
error, `"lower"` for a claimed probability or a tolerance. N38b-57 declares it on the counting rows of the suite
(KA-664 carries `safe = "higher"`, N26-KA). Any other value is a load error naming the row; a row without the field
has no declared direction, and its control is checked by running it (N38b-28).

**A late row before its block is issued (DESIGN).** A row of a case stated after plan time may be entered before
the allocation ledger (N38a-40) has issued its owner's block, as N23-KA, N24-KA, N30-KA, N37-KA and N23a-37's
`offpolicy-01` do: `id = ""`, `slug` the provisional tag, every other field as for a numbered row. Reason: the row,
its derivation file and its test can land and run at their own milestone without a number being typed (rule 6 of
N38a-40), and the tag is already the row's lasting `slug`. The loader accepts it and treats it as follows: a row
with an empty `id` and an empty `slug` is a load error; the identifier rules (contiguity, append-only, the block
check of N38a-40) do not apply to it, since it holds no number, while `slug` uniqueness does; it is addressed by
its `slug` (in the runner binding `ka:<slug>@<site>` of N38a-13, in reports and in the printout, whose KA column
prints the tag); `due` selection (`due:<milestone>`, N38a-13) and eligibility treat it like any row; no row's
`same_as` names it, and its own `same_as` may name a numbered row (its number, when issued, is above every issued
block). Once the block is issued, the owner sets `id` in the commit that maps its tags in table order, keeping
`slug`; setting the `id` of an unnumbered row is an append, not a renumbering. A row still unnumbered at its
owner's milestone after the block is issued fails N38a-40's rule 5 (`provisional-tag-past-due`), because only a
numbered row's own `slug` is exempt.

**Five rules for a row, each enforced by the loader or by a meta-test.**
1. **A derivation on file.** The file the row's `derivation` names states the model, the derivation, the numeric
   value with its digits, and the error budget of the test (truncation order, round-off bound, tier envelope).
   Two layouts are admitted, and the loader resolves the file from `derivation` alone: one file per fixture,
   `docs/derivations/<fixture>.md`, shared by the rows of that case (N10b-08's `docking-fixture.md`); or one file
   per row, `docs/derivations/<fixture directory>/<row>.md`, for a fixture whose manifest hashes each analytic
   row's derivation (N24b-03; N24b-04 writes `docs/derivations/fixture-cart-sill-dock/` for KA-602 to KA-611).
   The file's front matter lists the rows it serves, each by KA identifier (or by `slug` for a row first cited by
   a working tag), with the tests that check it (crate, test name and owning bead, or `pending: <bead>` until that
   bead lands), the carrier bead and, for an owed row, the owing bead; and, where they apply, the FACT source
   (`pilot` or `reread`, below) and `conditional_on` (below). A row whose file is missing, or does not list the
   row, is `obligation: derivation`. A hash of a derivation file (the derivation hashes of a fixture manifest,
   which enter `FixtureId`, N24b-03) covers the body below the front matter only, so adding a test name, a
   served row or a `pending` mark never changes a fixture's identity.
2. **A tolerance with a reason.** `exact` for integers, rationals, Booleans, verdicts and digests. For real
   values, the tolerance of the owning gate, scaled as the numerics rules require (physically scaled units;
   power-of-two scaling). `printed-digits` means half a unit in the last digit printed. A row whose tolerance is
   `to-set` is not eligible to pass until its derivation file states one (133 rows at plan time).
3. **A negative control.** The mutation or planted failure that must make the row fail. A row whose control is
   `none stated` cannot support a gate until a control is registered (325 rows at plan time). A boundary
   behaviour ("a 4 mm film is refused") is not a control: the registry needs a mutation, the build or input in
   which the limit was removed. Rows whose `control.text` only restates a refusal are flagged `boundary-only`.
4. **A tier and a site.** A row runs first on the weakest site that can decide it, then on every tier its gate
   names. A truth that holds on the referee and inside the fidelity envelope on the fast tiers is two results,
   not one; the schema therefore lists sites, and the runner reports per site.
5. **Values are not improved in transit.** The suite carries each chapter's printed value. Where a recomputation
   disagrees, the row keeps the printed value in `printed`, is listed in the reconciliation table, and its gate
   cites the derivation file once the reconciliation is closed. The loader never rewrites a value.

**Eligibility of a row (computed).** `eligible` (derivation, tolerance and registered control present, and for a
FACT row its re-run done); `obligation: tolerance`; `obligation: control`; `obligation: derivation`;
`obligation: rerun`; `flagged: unreconciled`. Only `eligible` rows are counted as passing by any gate.

**Conditional rows (DESIGN).** A row that exists only if a recorded decision opens its condition carries in its
derivation front matter `conditional_on = "<decision bead>: <condition>"` (KA-779 under `BD-031: escape-hatch`,
written by N33-KA). While the key is present the row's computed state is `conditional (<decision>)`, whatever its
other fields: neither eligible nor an obligation. The loader parses the key (a bead key, a colon and a non-empty
condition; any other value is a load error naming the file) and returns it with the row's eligibility, which is
what the G1 runner reads to print `not-run: conditional (<decision>)` (N38a-13). The decision bead removes the
key in the commit that opens the condition, and the row then takes its ordinary state.

**Re-run state of a FACT row (DESIGN).** A FACT row carries a value measured or published elsewhere (a plan-time
pilot, a sibling source, a publication), and is re-run or re-read in this repository before a gate cites it. The
state is not stored in the row: one check has one stored status, which is why the doctrine chapter's rows
(N09-KA) moved it out of the row and why the pilot ledger (N38a-10) refused a second file of re-run state. The
row's derivation file names the source in its front matter, in one of two forms:
- `pilot = "PILOT-…"` for a pilot result: the status is read from the pilot register through N38a-09's status
  read (a dependency; the mapping N38a-10 exposes as `pilots::rerun_status`: `registered` or `running` →
  `not-run`, `reproduced`, `differs`);
- `reread = { receipt = "blake3:…", session = "…", date = "…" }` for a sibling source or a publication, written
  by the session that re-derived or re-read the value here, the receipt naming the run or the archived source.
A FACT row is `obligation: rerun` while its pilot is not `reproduced`, or while it names no pilot and has no
`reread` with a receipt; a pilot status `differs` also makes it `flagged: unreconciled` (rule 5). DESIGN, in
place of a requested pair of row fields `rerun` and `rerun_receipt` (the counterexample catalogue's pair of that
name, N38b-05, stays its own): a row field would be a second copy of a status the register already holds for
every pilot-derived row. A `[[ka]]` row carrying `rerun` or `rerun_receipt` is refused by the parser as an unknown
field.

**One file.** The suite has exactly one physical file, `crates/frob-conformance/registry/known_answers.toml`
(the logical name `registries/known_answers.toml` used in some notes resolves to it). Each chapter's registry
bead (`N<chapter>-KA`) appends its rows to this file; no chapter keeps a file of its own. The loader fails with
`ka-second-file` naming the path when any other file in the repository matches `known_answers*.toml` or
`known-answers*.toml`, or is a `.toml` file under any directory named `known_answers` or `known-answers`
(FACT at review: three chapter registry beads first drafted `registries/known-answers/<chapter>.toml`, and in
round 2 more were found drafting `registry/known_answers/<chapter>.toml` or
`registries/known_answers/<chapter>.toml`, a spelling the first form of this check missed; all now name this
file, and the check keeps it that way). The reasons
`ka-second-file` and `boundary-only` are harness reasons of `registry/reasons.toml` (N38-REF).

**Loader validation.** The rules below run in `frob-conformance` on the rows returned by the test kit's parser
(`frob_core::testkit::registry`, STD-TEST), the one reader of the file; this bead adds no second parser. Identifiers
contiguous and append-only against the previous commit (for numbers above KA-835 the contiguity rule is amended by
the allocation ledger of N38a-40, whose validator this loader calls once that bead lands: a hole inside a `reserved`
or `filling` block is allowed); a non-empty `slug` is unique; `same_as` names a row that exists at the commit, has
the lower identifier and has the same `fixture` (one fixture identity per physical case). The earlier row is the
lower-numbered one, not the one appended first: between two rows above KA-835 numbered from two blocks of the
ledger, the row with the higher number names the lower, whichever landed first (TF-18 and K41-10), and a link to a
lower row that lands later is set in the commit that adds it (KA-821 to KA-361, in N16-KA's commit); `safe`, when
present, is `higher` or `lower`; a row with an empty `id` is a late row (above) and needs its `slug`; `tier` and
`sites` consistent (a G3 row names a relation in the relation registry; a G4 or G5 row has a truth of the form "zero
violations" or "equal digests"); every `nc` exists in the control registry; a `label = "FACT"` row's derivation file
names its source (`pilot` or `reread`, above), and a `pilot` that is not a record of the register is a load error.

**Printout.** `tests/known_answers_printout.rs` regenerates the printed suite (grouped by chapter, columns KA,
where stated, the case, the truth, tolerance, tier, negative control) and the coverage table (per chapter: rows,
rows with no stated control, rows with tolerance to set) and compares with the committed files. The where-stated
column prints `≡ KA-nnn` from `same_as` on every row that has one, so the links the registry holds beyond the
fourteen printed marks are printed too (among them KA-809 to KA-014, KA-812 to KA-001, KA-818 to KA-010, KA-819
to KA-013, KA-820 to KA-011, KA-821 to KA-361 and KA-828 to KA-030). Beside the counts, the loader reports the
rows with a `same_as`, row by row, each marked printed or registry-only, and their total.

**Carried-list audit.** `registry/carried_v02.toml` maps each of the twelve items of the earlier list to the KA
rows that carry it; a meta-test fails on an item with no row.

## Acceptance criteria

- [ ] The file validates; the loader rejects a reused, renumbered or missing identifier, and a second
      known-answer file anywhere in the repository.
- [ ] The plan-time counts hold on the seeded registry: 835 rows; 133 with tolerance to set; 325 with no stated
      control; by tier 135, 591, 16, 36, 19, 38; 14 printed shared-fixture marks, each carried as `same_as`. The
      total of rows with a `same_as` is reported separately, row by row, and is not one of these counts. A change
      in a count is reported with the rows that changed, not silently accepted.
- [ ] A row's derivation file is its fixture's file or a per-row file; a front-matter edit (a test name, a
      `pending` mark, a served row) leaves every derivation hash unchanged, and an edit of the body changes it.
- [ ] A row whose derivation front matter carries `conditional_on` is `conditional (<decision>)`, neither eligible
      nor an obligation, and the loader returns the decision to the G1 runner.
- [ ] `same_as` names an existing lower-numbered row of the same fixture; between two rows above KA-835 the higher
      names the lower.
- [ ] The optional `safe` field loads with `"higher"` or `"lower"` and is returned with the row; any other value
      fails the load naming the row.
- [ ] A late row (`id` empty, its tag in `slug`) loads outside the identifier checks, is selected by `due` and
      reported under its tag; a row with neither `id` nor `slug` fails the load; setting its `id` later, with the
      `slug` kept, passes the append-only check.
- [ ] Each of the five rules has a planted row it rejects or downgrades (negative controls below).
- [ ] No row with `to-set` or `none stated` is reported `eligible`.
- [ ] No FACT row is `eligible` before its pilot record reads `reproduced` or its derivation carries a `reread`
      with a receipt; such a row is `obligation: rerun`.
- [ ] The printed suite and the coverage table regenerate byte for byte.
- [ ] Each of the twelve carried items maps to at least one row.

### End-to-end script and logging

`scripts/e2e/known_answer_registry.sh` (header: `bead=N38a-12 milestone=M0 labels=gauntlet,registry
gates=GATE-GAUNT-02 plants=renumber,edit-printout`). It validates the registry, prints the eligibility counts,
regenerates the printouts, and plants a renumbered row and a hand-edited printout cell, each of which must be
caught. Log at `target/e2e-logs/known_answer_registry/<utc>.ndjson`: commands with exit codes and wall time,
rows per eligibility state (`conditional` included) and per tier as `metric` lines (obligations against the
threshold zero for rows due by M3), the `same_as` total with its printed and registry-only parts, the two
negative-control assertions and the `summary`.

### Known answers and negative controls

The registry's own known answers are its counts. Negative controls: the renumbered row; the edited printout; a
row passing with tolerance `to-set`; a row whose derivation file omits it; a second fixture name for equal
constants; a second known-answer file; a `same_as` naming a higher-numbered row; a conditional row reported
eligible. Determinism lane: class D0; the printout is byte-identical on both platforms.

## Considerations

- Open (fail-closed defaults): a row with no tolerance is not counted as passing; a row with no control supports
  no gate; an unreconciled value keeps its printed form and is flagged. The count of such rows due by M3 must be
  zero by M3.
- Two rows may serve one formula with different illustrative cards; they are separate fixtures with separate
  identities, by decision.
- Some truths are named in their chapters and not written (the pendulum period, the precession of a top, the
  pole of the two-wheeled balancer, the hydraulic cylinder); their rows carry no value until the derivation file
  exists, and are `obligation: derivation`.
- A counterexample found in use (a false certificate, a false promotion, a withdrawn result) appends rows here
  and becomes a permanent control.
