## Background

The known-answer suite of FrankenRobotics (835 numbered rows at plan time, each an analytic or synthetic truth
with a tolerance, a tier and a negative control) is run by tier G1 of the Gauntlet, the verification subsystem
in crate `frob-conformance`. This bead is the run itself as a user of the repository sees it: one command per
milestone that executes every row due, on every site its gate names, runs each row's control, and prints an
account that cannot flatter.

The gate it measures (GATE-GAUNT-02, claim kind Known answer, TARGET, due at every milestone exit): every row
that is due at the milestone passes on its tier inside its tolerance, with a derivation file; no row with
tolerance `to set` or control `none stated` is counted; the count of such rows is printed and is zero by M3 for
rows due by M3.

The account matters because of two failure modes recorded in sibling projects: partial coverage rounded up, and
failures moved out of the denominator. The rule here: a failure is a failed row, never an excluded row, and an
obligation (a row that cannot yet be judged) is printed as an obligation.

## Scope

In: the dispatch of rows to check functions, the per-site execution, the control run, the account, the receipt.
Out: the registry and its rules (N38a-12); each row's check function (the owning subsystem's bead, bound by
identifier); writing the gate status.

## Technical approach

1. **Binding.** A row is bound to code by a table entry `ka:<id>@<site>` whose function computes the observed
   value on that site (through the public verbs where the row belongs to a subsystem with a verb, exactly as an
   agent would call them; directly in exact arithmetic for `host` rows). A unit test named `ka_<nnn>_…` in the
   owning crate is a second, developer-level binding and does not replace the runner entry.
2. **Selection.** `cargo test -p frob-conformance --test g1_known_answers -- due:<milestone>` selects rows with
   `due` at or before the milestone. Filters by row, gate, chapter (`ch:20`) and site also exist.
3. **Per row.** (a) compute eligibility from the registry; an ineligible row still runs where a function is
   bound, but its outcome is reported as `obligation`, never as pass; (b) run on the weakest site first, then on
   every listed site; (c) compare with `assert_ka` under the row's tolerance; (d) run every registered control of
   the row and record `caught` or `missed`; (e) emit one outcome per site.
4. **Two results, not one.** A row with sites `referee` and `lockstep` yields two outcome lines with their own
   measured values; a pass on one never implies the other.
5. **Outcome states.** `pass`; `fail` (with the first differing value); `obligation: <what is missing>`;
   `unbound` (due and no function: counted as a failure of the gate); `skipped: <site unavailable>`;
   `control-missed` (the row passed and its control was not caught: the row counts as failed);
   `not-run: conditional (<decision>)`, for a row whose derivation file's front matter carries `conditional_on =
   "<decision bead>: <condition>"`. Such a row exists only if a recorded decision opens its condition (KA-779,
   the `frob-units` aliases against `fs-qty`, is built only if the escape hatch of INT-TOOLCHAIN-01 opens:
   `conditional_on = "BD-031: escape-hatch"`, written by N33-KA). While the key is present the row's outcome on
   every site is this state, whether or not a function is bound: it is not eligible, not a pass, not an
   obligation, not unbound and not a failure, and the gate line does not depend on it. The bead that records
   the decision removes the key in the commit that opens the condition; from that commit the row is an ordinary
   due row, `unbound` until its carriers bind it. (DESIGN: the key's presence is the one signal, so a row can
   never pass while its condition is closed and never hide behind the condition once it is open.)
6. **The account (printed and in the receipt).** For the selected milestone: rows due; eligible; passed on every
   site; failed; unbound; obligations by kind (tolerance, control, derivation, unreconciled); conditional rows
   not run, each with its decision; controls run, caught, missed; skipped sites. A conditional row stays in the
   count of rows due and enters no other count, so it leaves the denominator no more than a failure does. The gate line is produced only through the test kit's `GateReport`: `pass`
   requires zero failed, zero unbound, zero control-missed, zero skipped on a required site, and, for milestones
   M3 and later, zero obligations among rows due by M3.
7. **Receipt.** The hash-named tier receipt with one entry per row and site.

## Acceptance criteria

- [ ] The command above runs every due row on every listed site and prints the account.
- [ ] GATE-GAUNT-02 (TARGET): every due row passes inside its tolerance with a derivation file; rows with
      tolerance to set or no stated control are not counted and their count is printed; that count is zero by M3
      for rows due by M3.
- [ ] A due row with no bound function makes the gate fail and is named.
- [ ] A row whose control is not caught makes the gate fail although the row's value passed.
- [ ] A row on two sites prints two outcomes.
- [ ] A due row whose derivation front matter carries `conditional_on` prints `not-run: conditional (<decision>)`
      and is counted in its own line of the account, neither as a pass nor as unbound; with the key removed and
      no function bound it is `unbound` and fails the gate.
- [ ] Reachable from the user's side: the script below drives the run and, for rows owned by a verb, the row's
      function calls `frob --json` and reads the envelope.

## Test plan

### Unit tests

`crates/frob-conformance/tests/g1_account.rs`, on a scratch registry of six real rows (the docking grid counts;
the level series α·m/(m + 1); a pendulum period with tolerance `to-set`; a row with control `none stated`; a row
bound on two sites; an unbound row):
- `account_counts`: due 6; eligible 4 (the unbound row is complete in the registry); passed 3; obligations 2
  (one tolerance, one control); unbound 1; 6 = 3 + 2 + 1, so no row leaves the denominator.
- `unbound_fails_gate`.
- `obligation_never_passes`: the pendulum row computes the right value and is still reported as an obligation.
- `control_missed_fails_row`: the unmutated build is registered as the mutant, so the control cannot be caught.
- `two_sites_two_outcomes`.
- `m3_requires_zero_obligations`: with the milestone set to M3 the same registry fails the gate; at M1 the
  obligations are printed and the gate line depends only on the other counts.
- `skip_on_required_site_blocks`.
- `conditional_row_not_run`: a seventh scratch row whose derivation front matter carries `conditional_on =
  "BD-031: escape-hatch"` prints `not-run: conditional (BD-031: escape-hatch)` with and without a bound function;
  the account reads due 7 = passed 3 + obligations 2 + unbound 1 + conditional 1 and the gate line is the one
  the other six rows give; with the key removed and no function the row is `unbound`.

### End-to-end script and logging

`scripts/e2e/known_answers_g1.sh` (header: `bead=N38a-13 milestone=M1 labels=gauntlet,gate,known-answer
gates=GATE-GAUNT-02 plants=drop-derivation,mutant-not-caught`). Steps: run the G1 target for the current
milestone; read the receipt; assert the account; in the stage `verb-row`, call one verb-owned row from the
user's side (`frob task fixture fixture:cart-sill-dock --layer analytic --key fx-1 --json`, the form of the
verb registry VERBS-task) and compare the envelope's value with the registry (the verb is N24b-03's, an M1 bead
this one does not depend on: before it lands the stage logs `skipped: task.fixture not in build`, never a
pass, and from the M1 exit run of this script a skip of the stage fails it); plant `drop-derivation` (a derivation file removed in a scratch copy: the row must become an
obligation) and `mutant-not-caught` (the gate must fail). Log at
`target/e2e-logs/known_answers_g1/<utc>.ndjson`: each command with exit code and wall time, the envelope's
evidence block for the verb call, the account as `metric` lines (failed, unbound, control-missed against the
threshold zero; obligations with the milestone rule), the receipt digest, both negative-control assertions, and
the `summary` naming GATE-GAUNT-02.

### Known answers and negative controls

Known answers used by the run's own tests: KA-501 (344, 217, 9 of 561); the level series for α = 1/20;
KA-807 (paired lower bound 1.5). Negative controls: the dropped derivation; the uncaught mutant; an unbound due
row; a tolerance widened in the registry without a reason (rejected by the loader). Metamorphic relation:
running the rows in any order, or one at a time, gives the same account. Determinism lanes: the `host` and
`auditor` outcomes are class D0 and identical twice and across platforms; device-site outcomes are judged
against the class their gate names.

## Considerations

- The whole suite does not fit the per-change budget; per change the `smoke` and `fixtures` batteries run and the
  full G1 target runs nightly (the fail-closed default of the open question on the Gauntlet's runtime budget).
- Rows that quote a planning pilot or a publication are FACT about their source; they run only after the pilot
  has been re-run here or the source re-read, and say so in the outcome.
- A row whose printed value disagrees with its own formula keeps the printed value and is flagged; its gate
  cites the derivation file once the reconciliation is closed.
