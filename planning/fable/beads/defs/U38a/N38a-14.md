## Background

A *metamorphic relation* is a property that must hold between two or more runs of a system without anyone
knowing the right answer of either run: permute the worlds and the results permute; scale every unit by a power
of two and every bit of the significands is unchanged; split a rollout at a snapshot and resume, and the digest
equals the unsplit run. For a simulator whose outputs have no closed form, these relations are the strongest
cheap tests there are, and many of them encode exactly the design's distinguishing promises (a world does not
depend on the batch it ran in; a fork replays bit for bit).

The Gauntlet (the verification subsystem of FrankenRobotics, crate `frob-conformance`) keeps the relations as a
registry and runs them as tier G3. Each relation is a test over random scenarios on every tier it names, and it
is registered with the mutation that must break it. The second half is the point: a relation that still holds
when the property it protects is deliberately broken is not testing that property (PO-GAUNT-02: every relation
is broken by its registered mutation).

DESIGN: mutations are compiled in, behind a Cargo feature that no product build can enable, and selected at run
time by name. Rejected: source-level mutation tools (third-party, slow, and they mutate what they like, not the
registered defect); mutations as separate branches (they rot).

## Scope

In: the registry file and record; the scenario generator; the G3 runner and its counts; the mutation harness;
the account. Out: the relations' content (N38a-15 to N38a-18); each relation's transform and comparison code
(the owning subsystem's bead, bound by identifier); the end-to-end measurement (N38a-19).

## Technical approach

**Record (`crates/frob-conformance/registry/relations.toml`).**
```toml
[[relation]]
id        = "MR-06"                         # append-only; MR-C01… for the eleven carried relations
statement = "…"                             # the relation, in one sentence
source    = ["C-21"]                        # construction, invariant, gate or section it comes from
sites     = ["strict", "lockstep", "cuda", "metal"]
compare   = "bits"                          # bits | exact | digest | bound | order | leading-order
bound     = ""                              # for compare = bound | order: the formula or the expected order
mutation  = { name = "scale-by-ten", text = "A scale factor of 10", feature = "mut-mr-06" }
entry     = "mr:MR-06"                      # runner entry prefix; per site "mr:MR-06@strict"
owner     = "§…"; due = "M2"
```

**A relation in code (DESIGN sketch).**
```rust
pub trait Relation {
    type Scenario;                                   // drawn from the address-keyed generator
    fn scenario(&self, g: &mut Gen) -> Self::Scenario;
    fn base(&self, s: &Self::Scenario, site: Site) -> Observed;       // one run
    fn follow_up(&self, s: &Self::Scenario, site: Site) -> Observed;  // the transformed run(s), mapped back
    fn compare(&self, a: &Observed, b: &Observed) -> Verdict;         // per the record's `compare`
}
```

**Runner (`tests/g3_metamorphic.rs`).**
1. For each selected relation and each of its sites, draw N scenarios from the generator of the test kit
   (seed from the relation identifier and the release seed; a scenario is a function of (seed, index), so any
   subset reproduces).
2. N = 10⁴ per site per release (TARGET). On the `referee` site the fail-closed default is 10³ with the reduced
   count printed in the account. Per change, a smoke count of 32 per site runs.
3. Run base and follow-up through the public surface where the relation belongs to a verb, compare, and on the
   first violation stop that relation on that site, shrink the scenario with the kit's shrinker, and store the
   minimal scenario in `registry/relation_regressions/<id>.toml`, replayed first on every later run.
4. Account per relation and site: scenarios run, violations (zero to pass), reduced-count flag.

**Mutation harness.**
1. Each mutation is a `cfg(feature = "mut-…")` branch at the mutated site in the owning crate, enabled only
   through the umbrella feature `gauntlet-mutations` of `frob-conformance`'s dev profile; a release or default
   build with any `mut-*` feature enabled fails to compile (a `compile_error!` guard keyed on the profile).
2. `cargo test -p frob-conformance --test g3_metamorphic --features gauntlet-mutations -- mutant:<id>` runs the
   relation with its mutation active, at up to 10³ scenarios; the expected outcome is at least one violation.
3. A mutant that survives is a failure of the relation's test (`mutation-survived`), reported with the count of
   scenarios tried; the relation cannot pass its gate until the test is strengthened or the mutation re-stated.
4. A mutation that cannot be planted as described (the code path no longer exists) is `mutation-stale` and is
   reviewed at the milestone exit; it is never counted as caught.

**Gate (GATE-GAUNT-03, claim kind Known answer, TARGET; M2, then every exit).** Each relation holds on 10⁴
random scenarios per tier it names per release, and each registered mutation breaks its relation.

## Acceptance criteria

- [ ] The registry validates; identifiers are append-only; every record has a statement, a source, at least one
      site, a comparison kind and a mutation.
- [ ] The runner draws reproducible scenarios, stops and shrinks on a violation, and stores the regression.
- [ ] The reduced referee count is printed whenever it is used; a relation run at a reduced count never prints
      as having met 10⁴.
- [ ] A `mut-*` feature in a default or release build is a compile error.
- [ ] A surviving mutant and a stale mutation are each reported and each blocks the relation's pass.
- [ ] The account lists every relation by site with scenarios run and violations.

## Test plan

### Unit tests

`crates/frob-conformance/tests/relation_harness.rs`, with two real relations on exact arithmetic:
(a) "sorting a list then reversing equals sorting descending" with mutation "unstable comparator on ties";
(b) the unit-system relation on the pendulum period 2π·√(L/g) (scale lengths by 4 and times by 2, gravity
unchanged: the period scales by exactly 2) with mutation "scale by 10":
- `scenario_is_address_function`: scenario 137 is identical when drawn alone or as part of 10⁴.
- `violation_stops_and_shrinks`: a planted violation at scenario 911 is reported once, shrunk and stored.
- `regression_replayed_first`.
- `mutant_must_fail`: relation (b) under its mutation reports a violation within 10 scenarios.
- `survivor_reported`: a deliberately harmless mutation (a renamed variable) yields `mutation-survived`.
- `stale_mutation_reported`.
- `reduced_count_printed`: with the referee default the account says 1,000 of 10,000.
- `mut_feature_guard` (compile-fail): enabling `mut-mr-06` in the release profile does not compile.

### End-to-end script and logging

Covered by N38a-19 (`scripts/e2e/metamorphic_g3.sh`), which drives this harness from the user's side and logs
per relation and site. This bead's own script, `scripts/e2e/relation_harness.sh` (header: `bead=N38a-14
milestone=M2 labels=gauntlet plants=harmless-mutation`), runs the two example relations and the planted
survivor and logs commands, counts as `metric` lines and the negative-control assertion to
`target/e2e-logs/relation_harness/<utc>.ndjson`.

### Known answers and negative controls

Known answer: with lengths × 4 and times × 2 (gravity unchanged) the period 2π·√(L/g) scales by exactly 2, a
power of two, so every significand bit is unchanged; with lengths × 10 it scales by √10, which is not
representable, so the bits change. Negative controls: the surviving harmless
mutation; the stale mutation; a relation with an empty mutation field (rejected by the loader). Determinism
lane: scenario generation is class D0; the account is identical twice for the exact relations.

## Considerations

- Cost: 53 relations (11 carried and 42 added) × sites × 10⁴ scenarios is large; relations that need a rollout
  use short horizons chosen by their owners, and the release run names its budget. Open: affordability on the
  referee; default 10³, printed.
- A mutation is a defect, not a boundary: "the request is refused at the limit" tests the limit; the mutation is
  the build in which the property was removed.
- Relations whose comparison is `bits` are only meaningful under determinism class D2 or better on that site;
  under D3 the relation is restated as a bound or it is not run on that site.
