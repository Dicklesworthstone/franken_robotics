## Background

A *metamorphic relation* is a property that must hold between two or more runs of a system without anyone
knowing the right answer of either run: permute the worlds and the results permute; scale every unit by a power
of two and every bit of the significands is unchanged; split a rollout at a snapshot and resume, and the digest
equals the unsplit run. For a simulator whose outputs have no closed form, these relations are the strongest
cheap tests there are, and many of them encode exactly the design's distinguishing promises (a world does not
depend on the batch it ran in; a fork replays bit for bit).

The Gauntlet (the verification subsystem of FrankenRobotics, crate `frob-conformance`) keeps the relations as a
registry and runs them as tier G3. Each relation is a test over random scenarios on every tier it names, and it
is registered with the mutation that must break it. The second half is the point: a relation that still holds
when the property it protects is deliberately broken is not testing that property (PO-GAUNT-02: every relation
is broken by its registered mutation).

DESIGN: mutations are compiled in, each behind its own Cargo feature that no product build can enable, by the
suite's one mutation mechanism (N38b-04; N34-CX rule 4): the relation's mutation is a control record of
`registry/controls.toml` with `seed = "MR-nn"`, and its branch is `cfg(feature = "nc-<nnnn>")` in the owning
crate, NC-nnnn being that record. A mutant build rebuilds only the owning crate and its dependents. (An earlier
draft named the features `mut-mr-<nn>` and selected all compiled-in mutants at run time by name; that was a
second mechanism beside the control runner's, and the runner could not plant it.) Rejected: source-level
mutation tools (third-party, slow, and they mutate what they like, not the registered defect); mutations as
separate branches (they rot).

## Scope

In: the registry file and record; the scenario generator; the G3 runner and its counts; the mutation harness;
the account. Out: the relations' content (N38a-15 to N38a-18); each relation's transform and comparison code
(the owning subsystem's bead, bound by identifier); the end-to-end measurement (N38a-19).

## Technical approach

**Record (`crates/frob-conformance/registry/relations.toml`).**
```toml
[[relation]]
id        = "MR-06"                         # append-only; MR-C01… for the eleven carried relations
statement = "…"                             # the relation, in one sentence
source    = ["C-21"]                        # construction, invariant, gate or section it comes from
sites     = ["strict", "lockstep", "cuda", "metal"]
compare   = "bits"                          # bits | exact | digest | bound | order | leading-order
bound     = ""                              # for compare = bound | order: the formula or the expected order
mutation  = { name = "scale-by-ten", text = "A scale factor of 10", control = "NC-…", feature = "nc-…" }
                                            # an array of such tables where the relation names several
                                            #   planted defects (MR-01 and MR-08 name two each)
entry     = "mr:MR-06"                      # runner entry prefix; per site "mr:MR-06@strict"
owner     = "§…"; due = "M2"
generated_from = "C-21.S3"                  # optional: the contract statement the relation was generated from
```
The file has one parser, STD-TEST's `testkit::registry::Relations` (`Relations::get("MR-06") -> RelationRow { id,
statement, source, sites, compare, bound, mutations, entry, owner, due, generated_from }`, with `mutations` read
from `mutation` as one table or an array of tables; the type is `RelationRow` because `Relation` is this bead's
trait below). This bead's validation of the record's rules, `relations::validate`, is a function of
`frob-conformance` that runs on the rows that parser returns; no second reader of the file exists.
`generated_from` (optional) names one statement of a construction's specification, in the form `C-nn.Sk`
(statement k of construction C-nn, as the `SPEC-C-nn` beads number them), when the relation was produced from
that statement by the constructions' generator and not written by hand. The loader checks the form
(`^C-[0-9]{2}\.S[0-9]+$`) and that the construction is among the record's `source` entries; it does not open
the specification. The construction-coverage check of N10a-05 (its check C) reads the field to show that the
property tier is generated from the constructions, and counts a record without it as written by hand.

**A relation in code (DESIGN sketch).**
```rust
pub trait Relation {
    type Scenario;                                   // drawn from the address-keyed generator
    fn scenario(&self, g: &mut Gen) -> Self::Scenario;
    fn base(&self, s: &Self::Scenario, site: Site) -> Observed;       // one run
    fn follow_up(&self, s: &Self::Scenario, site: Site) -> Observed;  // the transformed run(s), mapped back
    fn compare(&self, a: &Observed, b: &Observed) -> Verdict;         // per the record's `compare`
}
```

**Runner (`tests/g3_metamorphic.rs`).**
1. For each selected relation and each of its sites, draw N scenarios from the generator of the test kit
   (seed from the relation identifier and the release seed; a scenario is a function of (seed, index), so any
   subset reproduces).
2. N = 10⁴ per site per release (TARGET). On the `referee` site the fail-closed default is 10³ with the reduced
   count printed in the account. Per change, a smoke count of 32 per site runs. The count of a run is the
   runner's argument `--count <N>` after the filter (`… --test g3_metamorphic -- <id>@<site> --count 32`);
   absent, it is the release count of the site. A run below the release count carries `reduced = {count,
   target}` on its entries in the receipt (N38a-02), so it can never be recorded as having met the gate's
   count.
3. Run base and follow-up through the public surface where the relation belongs to a verb, compare, and on the
   first violation stop that relation on that site, shrink the scenario with the kit's shrinker, and store the
   minimal scenario in `registry/relation_regressions/<id>.toml`, replayed first on every later run.
4. Account per relation and site: scenarios run, violations (zero to pass), reduced-count flag.

**Mutation harness.**
1. Each mutation is a `cfg(feature = "nc-<nnnn>")` branch at the mutated site in the owning crate (or, for a
   mutation that reuses an existing record under step 5, that record's feature in place of `nc-<nnnn>` here and
   below), built only with `--features gauntlet-mutations,<crate>/nc-<nnnn>`; an `nc-*` feature without
   `gauntlet-mutations`, or in
   a release or default build, fails to compile (the `compile_error!` guard of N38b-04, keyed on the profile).
   The relation record's `mutation.control` and `mutation.feature` name the record and the feature.
2. `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g3_metamorphic --features
   gauntlet-mutations,<crate>/nc-<nnnn> -- mutant:<id>` runs the relation with its mutation active, at up to
   10³ scenarios; the expected outcome is at least one violation. The control runner of N38b-04 applies the
   same build when it runs the control for GATE-GAUNT-03, so the two paths plant one branch.
3. A mutant that survives is a failure of the relation's test (`mutation-survived`), reported with the count of
   scenarios tried; the relation cannot pass its gate until the test is strengthened or the mutation re-stated.
4. A mutation that cannot be planted as described (the code path no longer exists) is `mutation-stale` and is
   reviewed at the milestone exit; it is never counted as caught.
5. **Registered as controls (DESIGN).** Each relation's mutation is also one record of the negative-control
   registry `registry/controls.toml`, registered by the relation's bead (N38a-15 to N38a-18): `seed = "MR-nn"`,
   `kind = "mutation"`, `feature = "nc-<nnnn>"`, `gate = ["GATE-GAUNT-03", …]` (plus every gate
   named in the relation's `source`), `target` the mutated site, `defect` the mutation text, `expect` "MR-nn
   reports at least one violation on <site>". Reason: the control runner runs every control of a gate whenever
   the gate runs, and a gate passes only through a caught control; a mutation known only to the G3 runner would
   be invisible to that rule. Reuse first (BD-025: one plant, one record): a mutation whose planted defect a
   catalogue entry's plant, a known-answer row's control cell or another bead's record already states is not
   registered again; the relation's `mutation.control` and `mutation.feature` name that record and its feature
   exactly as the record writes it (for a seeded record the feature is named by its plant, `cx-<nnn>`, not
   `nc-<nnnn>`), and the record lists GATE-GAUNT-03 and the gates of the relation's `source` beside its own (for
   a seeded record through its plant's gates in the chapter's catalogue, since only the seeding tool writes it;
   for another bead's record, the relation's bead adds them to its `gate` list, gates being only ever added). The
   relation bead depends on the bead whose record it names. The loader checks the map between mutations and
   controls, one control per
   mutation, every relation with at least one (a relation that names two planted defects has two controls,
   and `mutant:<id>` runs each as its own build), and fails with `relation-without-control` (a relation, or one
   of its mutations, with no control) or `control-without-relation` (a mutation control whose relation or
   mutation is gone).
   These two reasons, and `mutation-survived`, `mutation-stale` and the binding check's `due-unbound`, are
   harness reasons of the Gauntlet's reason registry (`registry/reasons.toml`, N38-REF), with meaning, repair
   and exit status there.

**Gate (GATE-GAUNT-03, claim kind Known answer, TARGET; M2, then every exit).** Each relation holds on 10⁴
random scenarios per tier it names per release, and each registered mutation breaks its relation.

## Acceptance criteria

- [ ] The registry validates; identifiers are append-only; every record has a statement, a source, at least one
      site, a comparison kind and a mutation; `generated_from`, where present, has the form `C-nn.Sk` and names
      a construction of the record's `source`.
- [ ] The runner draws reproducible scenarios, stops and shrinks on a violation, and stores the regression.
- [ ] The reduced referee count is printed whenever it is used; a relation run at a reduced count never prints
      as having met 10⁴.
- [ ] An `nc-*` feature in a default or release build, or without `gauntlet-mutations`, is a compile error; no
      `mut-*` feature exists in the workspace.
- [ ] A surviving mutant and a stale mutation are each reported and each blocks the relation's pass.
- [ ] Every mutation of every relation is a registered control of GATE-GAUNT-03 in `registry/controls.toml`,
      one control per mutation; a relation with two mutations has two controls and both must be caught; a
      mutation that an existing record already plants names that record, which lists GATE-GAUNT-03, and no
      second record exists for it.
- [ ] The account lists every relation by site with scenarios run and violations.

## Test plan

### Unit tests

`crates/frob-conformance/tests/relation_harness.rs`, with two real relations on exact arithmetic:
(a) "sorting a list then reversing equals sorting descending" with mutation "unstable comparator on ties";
(b) the unit-system relation on the pendulum period 2π·√(L/g) (scale lengths by 4 and times by 2, gravity
unchanged: the period scales by exactly 2) with mutation "scale by 10":
- `scenario_is_address_function`: scenario 137 is identical when drawn alone or as part of 10⁴.
- `violation_stops_and_shrinks`: a planted violation at scenario 911 is reported once, shrunk and stored.
- `regression_replayed_first`.
- `mutant_must_fail`: relation (b) under its mutation reports a violation within 10 scenarios.
- `survivor_reported`: a deliberately harmless mutation (a renamed variable) yields `mutation-survived`.
- `stale_mutation_reported`.
- `reduced_count_printed`: with the referee default the account says 1,000 of 10,000; `--count 32` on a `host`
  relation prints 32 of 10,000 and sets `reduced` in the receipt.
- `generated_from_form`: `generated_from = "C-21.S3"` on a record whose `source` lists C-21 loads; `"C-21"`,
  `"c-21.s3"` and `"C-14.S5"` on that record are load errors naming the record; a record without the field
  loads.
- `mut_feature_guard` (compile-fail): enabling an example relation's `nc-<nnnn>` feature in the release profile,
  or without `gauntlet-mutations`, does not compile.
- `mutation_is_registered_control`: each of the two example relations has exactly one `kind = "mutation"`
  record in a scratch `controls.toml`, with `seed` its MR id and `feature` equal to the relation's
  `mutation.feature`, naming GATE-GAUNT-03; deleting it fails the load with `relation-without-control`. A
  third scratch relation whose mutation names a scratch seeded record (`seed = "CX-…"`, `feature = "cx-…"`,
  gates including GATE-GAUNT-03) loads with no `MR-` record; adding a second record for that plant under the
  relation's `seed = "MR-…"`, which no mutation of the relation names, fails with `control-without-relation`;
  with GATE-GAUNT-03 missing from the reused record's `gate` the load fails naming the record.

### End-to-end script and logging

Covered by N38a-19 (`scripts/e2e/metamorphic_g3.sh`), which drives this harness from the user's side and logs
per relation and site. This bead's own script, `scripts/e2e/relation_harness.sh` (header: `bead=N38a-14
milestone=M2 labels=gauntlet plants=harmless-mutation`), runs the two example relations and the planted
survivor and logs commands, counts as `metric` lines and the negative-control assertion to
`target/e2e-logs/relation_harness/<utc>.ndjson`.

### Known answers and negative controls

Known answer: with lengths × 4 and times × 2 (gravity unchanged) the period 2π·√(L/g) scales by exactly 2, a
power of two, so every significand bit is unchanged; with lengths × 10 it scales by √10, which is not
representable, so the bits change. Negative controls: the surviving harmless
mutation; the stale mutation; a relation with an empty mutation field (rejected by the loader). Determinism
lane: scenario generation is class D0; the account is identical twice for the exact relations.

## Considerations

- Cost: 53 relations (11 carried and 42 added) × sites × 10⁴ scenarios is large; relations that need a rollout
  use short horizons chosen by their owners, and the release run names its budget. Open: affordability on the
  referee; default 10³, printed.
- A mutation is a defect, not a boundary: "the request is refused at the limit" tests the limit; the mutation is
  the build in which the property was removed.
- Relations whose comparison is `bits` are only meaningful under determinism class D2 or better on that site;
  under D3 the relation is restated as a bound or it is not run on that site.
