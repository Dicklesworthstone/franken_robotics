## Background

FrankenRobotics tests itself with metamorphic relations: fifty-three properties (eleven carried from an earlier
design, forty-two added) that must hold between runs without knowing the answer of either, each registered with
the mutation that must break it. The registry and the harness are the Gauntlet's (crate `frob-conformance`).
This bead is the end-to-end measurement of the gate that owns them:

GATE-GAUNT-03 (claim kind Known answer; TARGET; due at M2 and at every later milestone exit): each relation
holds on 10⁴ random scenarios per tier it names per release, and each registered mutation breaks its relation
(the proof obligation PO-GAUNT-02).

It is a separate bead because the measurement is a user-visible capability of the repository: one script that a
fresh-context session runs to obtain the receipt it will cite, with a log that shows what was run, on which
site, at which count, and which planted defects were caught. A relation that holds and whose mutant survives
has not passed, and the script's account must make that impossible to overlook.

## Scope

In: the script, its modes (smoke, release, mutants), its assertions and log. Out: the harness and the records
(N38a-14 to N38a-18); wiring of relations that land after M2 (their owners bind them and this script picks them
up by due milestone); writing the gate status.

## Technical approach

**Script `scripts/e2e/metamorphic_g3.sh`.** Header: `bead=N38a-19 milestone=M2 labels=gauntlet,gate,metamorphic
gates=GATE-GAUNT-03 needs=cpu plants=harmless-mutation,reduced-count-hidden timeout_s=3600`.

Steps.
1. `registry`: load `relations.toml`; assert 53 records (MR-C01 to MR-C11, MR-01 to MR-42); list those due at
   the current milestone; fail on a due relation with no runner entry for a listed site.
2. `relations`: for each due relation and site run
   `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g3_metamorphic -- <id>@<site> --count <N>`; N is
   10⁴ in release mode,
   32 in smoke mode (`E2E_SMALL=1`), and 10³ on the `referee` site under the fail-closed default. Sites absent on
   this host (`cuda` on the Mac, `metal` on the Linux host) are skipped and named; the gate is not claimable
   from one host alone, and the script says which host's sites remain.
3. `mutants`: for each mutation of each due relation run
   `… --features gauntlet-mutations,<crate>/nc-<nnnn> -- mutant:<id>` (the feature named by the relation's
   `mutation.feature`, the suite's one mutation mechanism; a relation with two mutations gives two builds);
   expect at least one violation; record `caught`, `mutation-survived` or `mutation-stale`.
4. `surface`: for the relations that belong to a verb, the follow-up runs go through `frob --json` (for example
   MR-C09 splits `frob sim run quad-a … --profile referee --key mrc09-<n> --json` at a snapshot and resumes it;
   MR-35 round-trips a design through `frob design view quad-a --as sexpr --json` and back with `--as json`, and
   compares the `DesignId` that `frob design show quad-a --json` reports before and after, the forms of the verb
   registry); the envelope's evidence block is logged for each such command.
5. `account`: per relation and site: scenarios run, violations, reduced-count flag, mutant outcome; totals; the
   gate line through the test kit's `GateReport` (pass only if every due relation has zero violations at the
   full count on every site and every mutation was caught).
6. `receipt`: read the hash-named tier receipt and log its digest.

**Modes.** `--smoke` (per change: 32 scenarios, mutants at 64); `--release` (the gate's counts, run under an
approved envelope where the total exceeds one hour); `--only <filter>` (`carried`, `MR-01..MR-14`, a single
identifier, or a site).

**Plants.** `harmless-mutation`: one relation's mutation is replaced in a scratch registry by a no-op; the
script must report `mutation-survived` and exit 1. `reduced-count-hidden`: the account's reduced-count flag is
suppressed in a scratch build of the printer; the linter rule "a relation run below its count never prints as
meeting it" must fail the log.

## Acceptance criteria

- [ ] The script runs every due relation on every available site and every due mutation, and exits 0 only if all
      relations hold and all mutations are caught.
- [ ] The account shows counts per relation and site; a reduced referee count is printed as `1000 of 10000`.
- [ ] GATE-GAUNT-03 is claimable only in release mode with every named site run (on both hosts where sites are
      split across them); smoke mode logs `gates_claimable: false`.
- [ ] Both plants are caught.
- [ ] A due relation with no runner entry fails step 1 and is named.
- [ ] The log validates against the end-to-end log schema and contains no private-scene data.

## Test plan

### Unit tests

The script has no code of its own beyond shell; the account logic it relies on is tested in
`crates/frob-conformance/tests/metamorphic_account.rs` on the two exact example relations of the harness:
`account_pass` (zero violations, mutants caught → pass); `account_survivor_blocks` (one surviving mutant → fail);
`account_reduced_count_not_full` (1,000 of 10,000 → not claimable); `account_skip_named` (a skipped site is listed
and blocks the claim); `filter_ranges` (`MR-01..MR-14` selects fourteen identifiers).

### End-to-end script and logging

The script above. Log at `target/e2e-logs/metamorphic_g3/<utc>.ndjson` through the shared helper: one `cmd` line
per cargo and `frob` invocation with exact command line, exit code and wall time; the evidence block of every
envelope (claim kinds, class, tier, determinism, identities, seed); per relation and site a `metric` line
`violations` with threshold `== 0` and a `metric` line `scenarios` with threshold `>= N`; per mutation an
`assert` of kind `negative-control` with `caught`; on a violation the first differing value, the shrunk scenario
and the path of the stored regression; the receipt digest; a `summary` with counts of relations held, mutations
caught, sites skipped, and the gate touched.

### Known answers and negative controls

Known answers asserted directly by the script as spot checks of the registry: 53 records; the padding identity
(−0.0) + (+0.0) = +0.0 behind MR-C07; 400 ÷ 13 = 30.77 Hz behind MR-15; the Cholesky scaling example behind
MR-07; 13/256 behind MR-14. Negative controls: every registered mutation (the content beads list them); the two
plants of this script. Determinism lanes: in smoke mode the script is run twice and the two logs must be equal
after removing timestamps, run identifiers, wall times and paths; `bits` relations are additionally run at
worker counts 1 and 8.

## Considerations

- Budget: the release run is the largest recurring test of the repository after training; it names its envelope
  and is scheduled nightly or per release, never per change.
- Open: whether 10⁴ scenarios per relation per tier per release is affordable on the referee; default 10³,
  printed. The gate's record states the count actually run.
- A relation owned by a mechanism whose kill gate fired is `superseded` in the registry; the script lists it and
  does not count it as held.
- Mutations are compiled only in the dev profile; the script verifies (`cargo tree -e features`) that the
  release binaries under test were built without any `nc-*` feature and logs their build identities.
