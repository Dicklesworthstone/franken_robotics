## Background

FrankenRobotics has two *full fixtures*: `fixture:cart-sill-dock` (a loaded, current-limited cart crosses a
12 mm door sill and docks; the question is whether a 75 mm front wheel beats a 60 mm one) and
`fixture:quad-split-grip` (a quadruped on a landing with a low-grip strip). Each has three parts: an *analytic
layer* (rows that are pure arithmetic or closed forms on the fixture's constants), a frozen development batch,
and a pre-analysis of its decision rule. The analytic layer is cheap, exact or nearly so, and sensitive to
precisely the code most likely to be changed carelessly: contact, actuator models, clocks and the requirement
language.

The rule of the verification subsystem (the Gauntlet, crate `frob-conformance`): the fixtures' analytic layers
run on every change that touches contact, actuators, clocks or the requirement language. This bead makes that
rule mechanical. Rejected alternative: running them nightly only; the defects they catch (an integrator order
swap, a comparator made non-strict, a clock scheduled by step count) are cheapest to fix in the change that
introduced them.

## Scope

In: the path list of the `fixtures` row of the trigger table; the runner entry for the analytic layers; the
G1 filter form `battery:<name>`; the per-change script; the check that the map is complete. Out: the trigger table's file, format and loader, and the
`smoke` row (N24b-01, a dependency); the fixtures and their analytic rows (BD-123, BD-202); the development
batches and pre-analyses; the manifests and identities of the `fixtures` and `smoke` batteries (defined by
N24b-01, registered and wired into the per-change run by BD-146); the run schedule of the four triggers and its
budgets (N38b-25, which reads this table and keeps no second one).

## Technical approach

**Trigger map: the `fixtures` row of the one trigger table.** There is one table,
`registries/batteries/triggers.toml`, whose format and loader belong to the battery manifests (N24b-01), so that
CI, a local pre-push check and the run schedule (N38b-25) read one source; this bead does not create a second
file (an earlier draft had placed a copy at `crates/frob-conformance/registry/triggers.toml`; check (d) below
fails on a second trigger file). This bead owns the path list of the `fixtures` row: the union of the battery bead's
list and the Gauntlet's, since a missing pattern skips a required run while an extra one only costs a run.
```toml
[[trigger]]
battery = "fixtures"
paths = ["crates/frob-contact/**", "crates/frob-actuate/**", "crates/frob-sense/src/clock*",
         "crates/frob-sense/src/clock/**", "crates/frob-sense/src/packet/**", "crates/frob-spec/**",
         "crates/frob-dyn/**",
         "crates/frob-arena/src/fixtures/**", "kernels/**", "assets/cards/**", "assets/fixtures/**",
         "crates/frob-conformance/registry/known_answers.toml"]
reason = "contact, actuators, clocks, requirement language"
```
A change is the set of paths that differ from the merge base (`git diff --name-only`). If any path matches, the
`fixtures` battery is required for that change.

**The filter form `battery:<name>` (DESIGN; this bead adds it to the G1 target's selection, beside N38a-02's
gate, row, site and milestone forms).** `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test
g1_known_answers -- battery:<name>` selects the G1 entries of the `ka` items that `battery::resolve(<name>,
"all")` (N24b-01) lists, in manifest order. An item with `task` and no `ka` is not a tier entry and is not
selected. A name that `battery::resolve` refuses, or whose items select no G1 entry, is an error under the
selection's rule (non-zero exit, never a pass). The receipt's `filter` is `battery:<name>`. BD-146's per-change
run uses this form.

**What runs.** `cargo test -p frob-conformance --test g1_known_answers -- battery:fixtures` selects the rows of
the two analytic layers and the requirement-monitor known answers (the `ka` items of the `fixtures` manifest);
from the user's side,
`frob task fixture fixture:cart-sill-dock --layer analytic --key fx-<change> --json` (the form of the verb
registry VERBS-task; and `fixture:quad-split-grip` when it exists). Each row runs on
`host` first, then on `referee` or `strict` where the row names it.

**Rows of the first fixture's analytic layer (values carried for the check; owned by the fixture's bead).**
Total mass 8.000 kg (60 mm design) and 8.225 kg (75 mm design); tread force cap 40 N and 32 N (two driven
wheels, 0.2 N·m/A, 6 A, over the wheel radius); lip lever a = √(2rh − h²) at h = 12 mm: 36.000 mm and 40.694 mm;
friction demand at front lift-off a/(r − h): 0.7500 and 0.6459; the wheel-loop one-tick spectral radius 0.9207
with the measured-current feed-forward term; the single-wheel admission cases (with μ = 0.70 and a 1.2 N·m cap
only the 75 mm wheel is admitted; with μ = 0.80 and a 0.95 N·m cap only the 60 mm wheel is).

**Completeness of the map.** `tests/trigger_map.rs`: (a) every crate whose contract lists contact, actuation,
clock or requirement responsibilities has at least one matching path; (b) every file that defines a constant
used by an analytic row is matched (found by the rows' declared `inputs`); (c) a path pattern that matches
nothing in the tree is reported as stale; (d) exactly one file named `triggers.toml` maps paths to batteries
(any other, such as one under `crates/frob-conformance/registry/`, fails the test with its path).

**Budget.** The analytic layers must finish in under 60 s on the CPU (TARGET) so that they are run and not
skipped; the script reports the wall time against that threshold.

## Acceptance criteria

- [ ] A change touching any mapped path requires and runs the `fixtures` battery; a change touching only
      unrelated paths (documentation, the viewer) does not.
- [ ] The filter `battery:<name>` selects the G1 entries of the battery's `ka` items, and an empty selection is
      an error.
- [ ] The analytic rows of the first fixture reproduce the values above within their tolerances on `host` and on
      the referee where named.
- [ ] Both registered negative controls of the fixture are caught in the same run (below).
- [ ] The map-completeness test passes, and fails when a mapped crate is renamed without updating the map or when
      a second trigger file appears; the `fixtures` row lives in `registries/batteries/triggers.toml` only.
- [ ] The run finishes within 60 s on the CPU, with the measured time recorded.

## Test plan

### Unit tests

- `trigger_matches_contact_change`: the path `crates/frob-contact/src/cone.rs` triggers; `viewer/src/app.js`
  does not; `crates/frob-spec/src/monitor.rs` triggers; so do `crates/frob-sense/src/clock.rs` and
  `crates/frob-sense/src/clock/phase.rs` (N24b-01's pattern `clock*` and this bead's `clock/**` both kept).
- `stale_pattern_reported`.
- `single_trigger_table`: a planted `crates/frob-conformance/registry/triggers.toml` fails the test, naming it.
- `fixtures_row_is_union`: every pattern of the battery bead's `fixtures` list (`crates/frob-dyn`,
  `assets/fixtures/`, `crates/frob-sense/src/clock*` included) is matched by the row.
- `inputs_are_mapped`: the file holding the cart's wheel radius is matched by a pattern.
- `battery_filter_selects_ka_items`: `battery:fixtures` selects exactly the G1 entries of the manifest's `ka`
  items, in manifest order; a scratch manifest that adds a `task` item selects the same entries.
- `battery_filter_empty_is_error`: an unknown battery name, and a scratch battery whose items are all `task`
  items, each exit non-zero naming the filter.
- `analytic_rows_values`: 8.000, 8.225, 40, 32, 36.000, 40.694, 0.7500, 0.6459 (host, printed digits).
- `single_wheel_admission`: for W = 25 N, h = 12 mm: r = 60 mm needs M = W·a = 0.900 N·m and μ ≥ 0.7500;
  r = 75 mm needs 1.017 N·m and μ ≥ 0.6459; the two admission cases select the stated wheel.

### End-to-end script and logging

`scripts/e2e/fixtures_on_change.sh` (header: `bead=N38a-22 milestone=M1 labels=gauntlet,fixtures,per-change
gates=GATE-ARENA-04 plants=euler-order,torque-only`). It computes the changed paths, decides whether the battery
is required, runs it (always, when invoked with `--force`), and checks values and timing. Plants:
`euler-order` (an explicit update of current before wheel speed at 0.5 ms: the wheel-loop row must report about
1.497 where 0.9207 is true, and fail); `torque-only` (the single-wheel admission checked on torque alone: both
wheels admitted in the first condition, which must fail). Log at
`target/e2e-logs/fixtures_on_change/<utc>.ndjson`: the diff command and the matched patterns, each `frob` and
cargo command with exit code and wall time, the envelope's evidence block, one `assert` per row with expected
and observed values, wall time as a `metric` against `<= 60 s`, both negative-control assertions, and the
`summary`. The script records no gate: GATE-ARENA-04's parts are recorded by BD-123 (the referee) and BD-212,
each from its own receipt (one recorder per part).

### Known answers and negative controls

Known answers: the eight arithmetic rows; 0.9207; the single-wheel values 0.900 N·m, 1.017 N·m, 0.7500, 0.6459.
Negative controls: the Euler-order mutation (the registry's example control, 1.497 against 0.9207) and the
torque-only admission check. Determinism lanes: the `host` rows twice on one machine and on both platforms,
identical; the referee rows inside the gate's tolerance.

## Considerations

- A constant of a fixture changed after its freeze changes the fixture's identity; the trigger then also
  requires the fixture's own identity check.
- The trigger map is path-based and can miss an indirect dependency; the nightly full G1 run is the backstop.
- The second fixture joins at M2; until then its rows are `not-yet-due`, not skipped silently.
