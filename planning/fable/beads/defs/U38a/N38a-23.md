## Background

Tier G4 of the Gauntlet (the verification subsystem of FrankenRobotics, crate `frob-conformance`) is chaos:
deliberate faults injected into a running system. The standard it applies is one sentence: every case must end
in its typed refusal or in a state the invariants accept, with no leaked resource. A simulator that runs batches
on GPUs under a daemon with a persistent ledger has many places where a fault can leave something half-done: a
device buffer still leased, a job charged twice, a chunk committed with other bytes, a result published from an
uncommitted read. None of those shows up in a happy-path test.

Ten families of injection are defined (cancellation; device faults; transaction faults; job protocol; chunk
protocol; daemon and ledger; capacity; malformed input; confirmation firewall; worker fallback). They share a
framework, which is this bead: how a fault schedule is described and seeded, how "no leaked resource" is
decided, how coverage of injection points is counted, and how a failing schedule becomes a small permanent
regression. The families themselves are three sibling beads.

DESIGN: schedules are data, generated from a seed, replayable, and minimized on failure. Reason: a chaos failure
that cannot be replayed cannot be fixed, and one that takes minutes to replay will not be kept. TARGET: 10⁵
seeded schedules per release; every await point on the publish and submit paths hit by a crash fault at least
once; every failing schedule minimized to a regression that replays in under a second.

Rejected alternatives: random fault injection with wall-clock timing (not replayable); sleeping and killing
processes from shell only (cannot reach an await point deterministically).

## Scope

In: the schedule format; injection-point registration; the outcome oracle; the resource-leak audit; coverage
accounting; minimization and the regression store; the G4 runner. Out: the families' injections and oracles
(N38a-24, N38a-25, N38a-26); the lab runtime itself (a sibling library); the end-to-end measurement (N38a-27).

## Technical approach

**Injection points.** A point is a named place where a fault can be applied: `kernel-batch-boundary:<stage>`,
`await:<path>:<n>` (the n-th await point of the publish or the submit path), `tx:between-check-and-commit`,
`device:<event>`, `ledger:write`, `lease:expiry`, `clock:jump`, `disk:full`, `reader:<format>`. Points are
declared by the owning crate through the job-context trait that `frob-core` defines (the standing inversion by
which lower crates reach cancellation and budgets); a build without the `chaos` dev feature compiles the hooks
to nothing. The registry `crates/frob-conformance/chaos/points.toml` lists every point with its owner, family
and the faults it accepts; a point present in code and absent from the registry fails the tier's self-check.
The fault kinds are the vocabulary of the lab runtime's support module, `frob_conformance::lab::Fault`
(N33c-15: crash, cancel, torn write, storage error, reorder, duplicate, delay, lease expiry, device loss, disk
full, clock jump, client disconnect), written in a schedule in kebab case with the variant's fields, and an
`await:<path>:<n>` point is that module's `AwaitPoint` (`publish#3` is `await:publish:3`), so coverage of await
points is counted once for the lab tests and for G4. This bead adds the points outside the lab runtime
(kernel-batch boundaries, devices, readers) and the schedule's family, site, workload and expectation; it
defines no second fault type.

**Schedule (`frob.gauntlet.chaos/1`).**
```toml
seed = "…"; family = "job-protocol"; site = "daemon"   # host | strict | lockstep | cuda | metal | daemon
[[fault]] at = "await:submit:3"; kind = "crash"; occurrence = 1
[[fault]] at = "ledger:write";  kind = "torn-write"; byte_offset = 17
workload = { verb = "sim.run", args = "…", worlds = 8, ticks = 200 }
expect = { outcome = "refusal:FROB-REF-…" }             # or "accepted-state"
```
A schedule is generated as a function of (release seed, family, index), the release seed being `FROB_TEST_SEED`
(STD-TEST, recorded in the receipt by N38a-02); with the lineage-driven selector, faults
that could have broken the outcome of a recorded successful run are tried before random ones.

**Outcome oracle.** After the workload and any recovery step, exactly one of:
1. `refusal`: the caller received an envelope with `ok: false`, the expected code and its exit code; or
2. `accepted-state`: every invariant named by the family holds on the final ledger and device state; and in
   both cases
3. `no-leak`: the resource audit is clean.
Anything else is a violation: a panic, a hang past the schedule's virtual or wall deadline, an exit code 1
(which is never emitted on purpose), an untyped error, a result published from uncommitted state, a silent
truncation.

**Resource audit.** Counters taken before and after, which must be equal once the system is idle: device
buffers and arena leases per backend; open file handles and temporary files under the scratch root; ledger
transactions open; jobs in a non-terminal state; leases held; budget reserved and not charged or released;
worker processes alive; kernel-cache entries half-written. Each counter is supplied by its owner through the
same context trait; a counter that cannot be read is a failure of the audit, not a pass.

**Coverage.** Per release: schedules run per family; for each injection point, the number of schedules that hit
it with each accepted fault kind. The tier fails coverage when any `await:publish:*` or `await:submit:*` point
has zero crash hits, or when the total is below the declared count (10⁵, or the reduced count the run printed).

**Minimization and regressions.** A violating schedule is reduced: (a) drop faults one at a time while the
violation persists; (b) shrink the workload (worlds, ticks) by halving; (c) for simulated runs, minimize the
scheduling choices with the lab runtime's schedule minimizer, through N33c-15's minimization step (no second
minimizer). The result (seed, fault list, workload, and the
schedule of minimal length) is stored as `crates/frob-conformance/chaos/regressions/<family>/<blake3>.toml`,
must replay in under one second on the CPU (TARGET; a slower one is kept and flagged), and is run first on every
later invocation. A regression is never deleted.

**Runner.** `FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test g4_chaos -- <family>[@<site>]
[--count N]`; per change the
regressions and 64 fresh schedules per family; per release the full count. The receipt lists per family:
schedules, violations, leak findings, coverage holes, regressions replayed.

## Acceptance criteria

- [ ] The schedule format, the point registry and the runner exist; a point in code that is missing from the
      registry fails the self-check.
- [ ] The oracle classifies a planted panic, hang, exit code 1, untyped error and leaked lease as violations,
      each named.
- [ ] The audit reports a planted leak of each resource kind and passes on a clean run.
- [ ] Coverage reports a publish or submit await point with zero crash hits.
- [ ] A violating schedule is minimized, stored, and replays in under one second.
- [ ] A build without the `chaos` dev feature contains no injection hook (checked by symbol search of the
      release binaries).

## Test plan

### Unit tests

`crates/frob-conformance/tests/chaos_framework.rs`, on a small real workload (the canonical-bytes round trip of
a design file through a temporary file, with points `reader:fbot` and `disk:full`):
- `schedule_is_seed_function`: schedule 1,234 of a family is identical when generated alone or in a batch.
- `fault_kinds_are_lab_vocabulary`: every `kind` a schedule may hold parses to a `frob_conformance::lab::Fault`
  variant, and `await:publish:3` names the same point as the lab's `publish#3`; an unknown kind is rejected.
- `oracle_refusal_ok`: a truncated file yields the reader's typed refusal, exit code 3, audit clean.
- `oracle_flags_panic`: a planted `unwrap` on the truncated file is a violation.
- `oracle_flags_exit_one`.
- `audit_flags_temp_file_leak`: a planted temporary file left behind is reported with its path class.
- `coverage_hole_reported`: with one point never hit, the account names it.
- `minimize_drops_irrelevant_faults`: a three-fault schedule whose violation needs one fault minimizes to that
  fault.
- `regression_replays_under_one_second`.
- `hooks_absent_without_feature`.

### End-to-end script and logging

Measured by `scripts/e2e/chaos_g4.sh` (N38a-27). This bead's own script `scripts/e2e/chaos_framework.sh`
(header: `bead=N38a-23 milestone=M2 labels=gauntlet,chaos plants=leak-lease`) runs the framework's example
workload, the planted leak and one minimization, logging commands, the audit counters before and after as
`metric` lines, the negative control and the `summary` to `target/e2e-logs/chaos_framework/<utc>.ndjson`.

### Known answers and negative controls

Known answer: the audit counters of a clean run are equal before and after. Negative controls: the planted
panic; the planted leak; a schedule whose expected refusal code is wrong (must fail, not pass by accident); an
unregistered injection point. Determinism lane: generating and replaying a schedule under the simulation
runtime is class D0 (same seed, same interleaving, same ledger bytes).

## Considerations

- Budget: 10⁵ schedules per release is feasible only because the daemon families run under virtual time with a
  simulated device; kernel families on real devices run fewer schedules and print their count.
- The chaos hooks are a second code path; the symbol check and the compile-to-nothing rule keep them out of
  product builds.
- Cancellation is part of the definition of "implemented" for every capability: request, drain, finalize, with
  no leaked device resources. A capability without a G4 entry is described as partial.
