## Background

FrankenRobotics is a robotics simulation and design system written in Rust. Its verification subsystem is called
the Gauntlet and lives in one crate, `frob-conformance`, at the top layer (layer 7) of the workspace: it depends
on every other crate and nothing depends on it. The Gauntlet decides whether a *gate* (a numbered acceptance
threshold such as GATE-ARENA-04) may record a pass. Every number in the planning documents is a TARGET or a FACT
about something else until a gate records it, and the Gauntlet is the only path by which it becomes a result.

This bead creates the crate at milestone M0 with the one mechanism every later gate needs first: the
*negative-control registry* and the check that a gate with no control cannot pass. A negative control is a
planted defect (a mutated build, a hostile input, a bad design, a separating world, a broken experimental
procedure) that a gate's test must catch. The reason is a rule the program takes from a sibling project (FACT):
"A gate no deficient model can fail validates nothing." Sibling projects also recorded how agent swarms produce
the appearance of progress (87 work items closed within 12 seconds on one shared reason, serving figures from a
stand-in, FACT); the registry is the mechanical response.

Decisions that govern the crate (DESIGN, with reasons and rejected alternatives).
- ADR-GAUNT-03: every gate is registered with its failing control before its passing test is written. Reason:
  the control is the specification of what the gate detects. Rejected: adding controls after a gate passes
  (the gate then defines the control, not the reverse).
- ADR-GAUNT-01: the Gauntlet has no agent verb and no `xtask` subcommand; tiers are Cargo test targets. Reason:
  a harness driven through the surface it judges is a path to self-certification, and `xtask` holds exactly six
  checks. Rejected: a `frob gauntlet` verb; a seventh check.
- ADR-GAUNT-02: registries are data and printed tables are their printouts. Reason: a hand-edited table drifts
  from the tests that back it.

Terms. Tier G0 laws and self-tests; G1 known answers; G2 parity with pinned oracles; G3 metamorphic relations;
G4 chaos; G5 determinism. `KA-nnn` a known answer, `CX-nnn` a counterexample (the smallest case that breaks a
tempting shortcut), `NC-nnnn` a negative control. Tier Solid (no pilot needed).

## Technical approach

**How the Gauntlet is run (ADR-GAUNT-01, stated once here for every bead that runs it).** There is no
`frob conformance` command, verb or subcommand; there is no binary named `frob-conformance` (so no
`frob-conformance run …`, `record …`, `report …`, `open …` or any other subcommand of that name), and the crate
has no default binary. A run of a gate or a known-answer row is
`FROB_TEST_SEED=<seed> cargo test -p frob-conformance --test <tier> -- <gate|row>`, where `<tier>` is the test
target named by the gate record's `tier` field (`g0_laws`, `g1_known_answers`, `g2_parity`, `g3_metamorphic`,
`g4_chaos`, `g5_determinism`; the short forms `g0` to `g5` are not target names), with
`--features gauntlet-mutations` when its controls are run; the run writes a hash-named receipt (N38a-02). A
recording is the recorder's example target,
`cargo run -p frob-conformance --example record_gate -- --gate <id> --receipt <hash>` (N38b-19). A bead or script
that writes `frob conformance run <gate>` means the cargo form above; one that writes `frob-conformance <sub> …`
means `cargo run -p frob-conformance --example <harness> -- <sub> …` of the example that owns `<sub>` (for the
studio, `atelier_harness`, first created by N28c-27 or N28c-28 at M1; the studio beads add subcommands). The lint
below refuses every wrong form in any script, so none can be implemented.

**Crate.** `crates/frob-conformance/`: a library, its test targets, its example targets and a closed list of
operator binaries; no verb and no `xtask` subcommand. DESIGN: the plan's ADR-GAUNT-01 forbids an agent verb and
an `xtask` subcommand and runs tiers as test targets; it names no binary, and the program's operator tools that
must link the whole workspace can live only in this layer-7 crate. Rejected: "no binary at all" (stated by an
earlier text of this bead; the end-to-end log tool and the ten-fold operator tools already live here, and a rule
nobody can keep invites the improvised `frob-conformance <sub>` spellings this lint now refuses); a runner binary
(a gate would then be runnable outside `cargo test`, the one form the receipt and the recorder trust).
- *Test targets* (`tests/<name>.rs`): the six tier targets, the only way a gate or a known-answer row is run, and
  the crate's own checks (`registry_check`, `no_conformance_command`, `binaries_declared`, and those of other
  beads such as `registry_allocations`, `pilot_register`, `recorder`, `tenfold` and `g0_doctrine`). `g0_doctrine`
  (N10a-01, which creates it with the family `d2_*`; N10a-02 to N10a-09 add the other doctrine families of `d1_*`
  to `d19_*`) is a check target and not a seventh tier: an ordinary libtest target whose argument is a name
  filter (`--test g0_doctrine -- d2`), which runs no gate entry and no known-answer row and records no gate. The
  tier runner selects only by gate, row, site or milestone (N38a-02), so a doctrine family is not an entry of
  `g0_laws`. ADR-GAUNT-01's tier form (`--test <tier> -- <gate|row>`) does not govern it, lint rule 5 below
  admits it as a declared test target, and scripts run it as an ordinary command, not as a tier.
- *Example targets* (`examples/<name>.rs`): thin argument parsers over library functions of `frob_conformance`,
  each printing one JSON object on standard output and exiting non-zero when its own assertions fail. The
  Gauntlet's own: `record_gate` (N38b-19; its `reaffirm` mode is N29bp1-01's), `validate_register` (N40-01) and
  `pilots` (N38a-09: `fundable`, `complete`). Others are declared by the beads that write them, for example
  `registry_report` (N28-CX) and `atelier_harness` (first created by N28c-27 or N28c-28 at M1; the studio beads
  add subcommands: the studio's harnesses are subcommands of this one
  example). A harness reader or driver of another subsystem is an example of this crate, or of its owning crate
  when its code lives there (`cargo run -p <crate> --example <name> -- …`).
- *Operator binaries* (`[[bin]]` entries with an explicit `name` and `path`; the manifest sets `autobins = false`,
  so a binary exists only by declaration and its command name is the declared one): `frob-e2e` (STD-E2E, the
  end-to-end log tool), `frob-tenfold` and `frob-tenfold-score` (N39a-01), and those other beads declare (for
  example `frob-golden`, NJL-07; `frob-mcp-drive`, NJL-08; `frob-surface-diff`, NJL-02; `frob-pilot`, BD-385,
  whose source file is `src/bin/frob_pilot.rs`; `decision-sweep`, NAB-22, whose source file is
  `src/bin/decision_sweep.rs`). Each has a row in `CONTRACT.md` naming its owning bead and
  stating what it reads and writes. STD-E2E, a dependency of this bead, lands first: it creates the manifest
  with `autobins = false`, no `default-run` and the one entry
  `[[bin]] name = "frob-e2e", path = "src/bin/frob-e2e.rs"`, and `CONTRACT.md` with the binary table holding
  that binary's row. This bead completes both rather than creating them (the rest of the manifest, the ten
  sections, the other rows), and `binaries_declared` checks that entry and that row.
- For all three kinds: none is named `frob-conformance`; the manifest has no `default-run`; none is a `frob` verb
  or an MCP tool; no binary or example runs a tier in place of `cargo test`; and no binary or example writes a row
  of `registries/gates.toml` except `record_gate` (one recorder per gate). A binary or example may produce a
  receipt or a record that a gate later cites.

`Cargo.toml` lists every workspace crate under `[dependencies]` only as needed by a target; device annexes are
optional features (`cuda`, `metal`) so that G0 and the host entries of G1 build with no annex. Features:
`gauntlet-mutations`, the umbrella of planted defects (a default or release build with it enabled is a compile
error). It enables the `conformance` feature of every workspace crate that declares one, the convention under
which a crate keeps its test facilities (plant hooks, probes, planted solver options): for example
`frob-dyn/conformance` and `frob-kernels/conformance`, which hold the plant hook of N29a-25, and
`frob-contact/conformance` (N16b-15, N18bx-03). A battery run with `--features gauntlet-mutations` therefore needs
no second feature for those facilities. A test-support verb, a real handler that exists only in a build with its
crate's `conformance` feature (N37-25's `testprobe.combine` in `frob-verbs`), is registered in the verb cluster
`testprobe` and never under `conformance`: no verb, cluster or MCP tool carries that name, so rule 1 of the lint
below has no exception, and such a verb is absent from the product binaries' registry and tool list. A
per-control mutation feature, that is the feature a control's `feature` field names (`<crate>/cx-262`,
`<crate>/nc-<nnnn>`), is never in the umbrella: the control runner adds `<crate>/<feature>`, exactly as the
record writes it, on its own command line, one control per build (N38b-04). DESIGN: a crate's
`conformance` feature compiles facilities that change nothing unless armed (N29a-25 proves an armed but empty
schedule is the identity), whereas a mutation feature changes behaviour and must be isolated to its own build.
The product binaries (`frob`, `frobd`, `frob-mcp`, `frob-verify`) carry no `conformance` and no mutation feature
(`cargo tree -e features`, N38b-04's check). Scope cap: 24,000 lines (a cap that triggers a scope conversation at
115%, not a schedule).

**Layout.** `tests/g0_laws.rs`, `g1_known_answers.rs`, `g2_parity.rs`, `g3_metamorphic.rs`, `g4_chaos.rs`,
`g5_determinism.rs` (each a test target with a static, initially empty entry table and one self-test);
`tests/registry_check.rs`; `registry/controls.toml`, `registry/counterexamples.toml`,
`registry/known_answers.toml`, `registry/relations.toml`, `registry/pilots.toml` (files created with their
schema header; content arrives through their own beads); `src/controls.rs` (types and validation);
`CONTRACT.md` with the ten sections (purpose, inputs, outputs, invariants, refusals, determinism class, evidence
class of outputs, validity domain, oracles, known gaps).

**Control record (`registry/controls.toml`; one `[[control]]` per record).**
```toml
[[control]]
id        = "NC-0412"                       # stable, append-only, never reused (INV-GAUNT-07)
seed      = "CX-262"                        # the catalogue entry or KA row it came from; "" if found in use
gate      = ["GATE-ARENA-04"]               # every gate that must catch it; at least one
kind      = "mutation"                      # mutation | planted-input | planted-design | planted-world | a-a
target    = "frob-actuate::stage::integrate"   # code path, verb, fixture or procedure the defect is planted in
defect    = "explicit Euler, current before wheel speed, at 0.5 ms"
expect    = "wheel-loop row reports spectral radius 1.497 where 0.9207 is true; the row fails"
last_seen = { caught = true, session = "…", date = "…" }   # written by the recorder (N38b-19) from the receipt's control line, never by hand
```
DESIGN additions to this base record, each optional: `feature = "cx-262"` (the Cargo feature that plants a
`mutation`, declared in the target crate. It is named by its plant, here the plant `BD-123:cx-262` of the
catalogue entry, as N38b-05's seeding writes it, because a plant is named before its control has a number; a
control registered directly by its bead may name its feature after the control, `nc-<nnnn>`, as the relation
mutations of N38a-14 do. Whatever its name, it is the feature the runner builds and the guards cover);
`fixture = "…"` (the file that carries a planted input, design or world); `due = "M1"`;
`permanent = true` (a control created from a false certificate, false promotion or withdrawn result found in
use; never removable); `state = "runnable" | "obligation"` (default `runnable`; written `obligation` by the
seeding tool of N38b-05 for an entry with no numeric case yet or an unreproduced FACT case: it has an
identifier and gates, is not run, and makes no gate eligible).

**Loader validation (`frob_conformance::controls::validate`, errors are typed and name the record).** The file
has one parser, `frob_core::testkit::registry::Controls` (STD-TEST: one reader per file); this function runs on
the rows that parser returns and is the schema owner, so the parser's `Control` type carries every field above,
the optional ones included.
1. `id` matches `NC-` plus four digits; identifiers are strictly increasing in file order (else `out-of-order`),
   none occurs twice (`reused`), and none of the previous commit's identifiers is missing (`removed`) or changed
   in `seed`, `kind` or `target` (`renumbered`). These are the registry-diff reasons of N38-REF. One change of
   `target` is admitted (DESIGN): a record whose `target` in the previous commit was a placeholder and which had
   no `last_seen` there (an obligation, or a control whose plant was not yet built: it has never been recorded
   as run) may take the target its chapter or planting bead later states. A placeholder is what N38b-05's
   seeding writes while the chapter states no target: the plant identifier `<bead key>:<plant name>` (one colon,
   for example `BD-123:cx-262`) or the `CX-nnn` number of an entry with no plant. The new target is not a
   placeholder, so a record changes this way at most once; every other change of `target` is `renumbered`.
2. `gate` is non-empty and every entry exists in `registries/gates.toml`.
3. `kind` is one of the five (else `kind-not-closed`); a `mutation` names a `feature` and the other kinds name a
   `fixture` (else `feature-missing`, `fixture-missing`). That the feature is declared in the target crate's
   manifest, and that the fixture exists and begins with a kind header (`synthetic`), is checked, with the same
   two reasons, for every control listed by a gate whose status is not `not-run`. For any other control an
   unbuilt plant is not a load error (DESIGN): controls are seeded from the catalogue before their plants exist
   (N38b-05), so a load-time existence check would make the whole registry unloadable at M0; the control runner
   reports such a control `stale` when it is run (N38b-04), and a gate whose control is stale cannot pass. Rule
   2's reasons are `no-gate` and `unknown-gate`. Every reason string is registered in the reason vocabulary
   (N38-REF).
4. `defect` and `expect` are non-empty; `expect` states an observable (a value, a refusal code, a failed row).
   Else `defect-or-expect-empty` (a control-loader reason of N38-REF, like the others).
5. Rule "a control is a defect, not a boundary": a record whose `defect` only restates a limit of the product
   ("the request is refused at the limit", detected by `kind = planted-input` with `expect` equal to the
   product's own refusal and no `removed_check` field) is rejected with `boundary-not-control`. The valid form
   names the build or input in which the limit was removed (`removed_check = "<what is disabled>"`).
6. `seed` has one of the admitted forms, each naming the registry in which N38b-05's join resolves it: `CX-nnn`
   (the counterexample catalogue); `KA-nnn` (the known-answer registry); `MR-nn` or `MR-Cnn` (the relation
   registry, for a relation's registered mutation: `MR-01` to `MR-42` are the added relations and `MR-C01` to
   `MR-C11` the eleven carried relations of N38a-15, whose controls are seeded `MR-C<nn>`); `CERT-nn` (the certifier register, for a broken certifier); `INV-<AREA>-nn`
   and `PO-<AREA>-nn` (an invariant or proof obligation, through `registry/rule_gates.toml`); `RISK-nn` (a row of
   the risk register); `SAFE-Xnn` (an example of the safety chapter's catalogue that has no CX number yet);
   `GATE-<AREA>-nn` (a control registered first for a gate whose planted failure no catalogue entry or row
   states, ADR-GAUNT-03); and `""` only on a record with `permanent = true` (a defect found in use before its
   catalogue entry exists). Any other form is rejected with `unknown-seed-form`. The loader checks the form; the
   join checks that the identifier exists.

**Who writes a record (DESIGN; the seed form decides, and this is the one statement of it).**
- A record seeded `CX-nnn` or `KA-nnn` is written only by the seeding tool of N38b-05, from the catalogue entry
  or from the row's stated control cell. The chapter states the plant in its catalogue entry or its row and
  never writes the record, by hand or by copy.
- A record of any other seed form is appended by the bead that owns what the seed names, under the rules above,
  at the next free `NC-` number above the file's highest (STD-TEST's number rule): the relation's bead for
  `MR-nn` and `MR-Cnn` (N38a-15 to N38a-18); the certifier's bead for `CERT-nn`; the bead that tests the
  invariant or the obligation for `INV-…` and `PO-…` (for example N32b-22, N32b-23, N29b-15); the risk-detector
  beads for `RISK-nn` (N41-32 to N41-37); the safety catalogue bead for `SAFE-Xnn` (N37-CX); the bead that
  measures the gate for `GATE-…` (for example N21c-31, N32b-25, N35-15, N38a-24); and N38b-04's procedure for a
  permanent control found in use.
- Reuse first. Such a bead resolves each of its plants against the registry as seeded (N38b-05's tool, run
  over its chapter's catalogue entries and rows) and registers only a plant that no catalogue entry and no
  stated control cell states; for a plant that one states, it lists the seeded record and writes no second
  one. One plant has one record.
- The seeding tool writes no record of these other forms and rewrites none; its join resolves each such seed in
  its own registry (the relation registry, the certifier register, `registry/rule_gates.toml`, the risk
  register, the gate register).
Reason: a counterexample or a known-answer row exists as data before any mechanism bead runs, so a tool can
derive its control and keep 894 source items consistent; a gate's, an invariant's or a risk's planted failure
that nothing else states exists only in the bead that plants it. Rejected: the tool as the only writer of every
form (it would need a second catalogue of gate, invariant and obligation plants, written by the same beads that
now write the record, and ADR-GAUNT-03's control would be registered one step later than its gate).

**No wrong command form (`tests/no_conformance_command.rs`).** Every file under `scripts/` and `xtask/` is
scanned line by line (a line whose first non-blank character is `#` is a comment and is skipped). A hit fails the
test with the file, the line, the offending text and the form to use instead. The forms refused, checked in this
order:
1. `frob conformance` followed by anything: replacement, the tier-target form above.
2. The word `frob-conformance` used as a command name (at the start of a command: line start, or after `|`,
   `||`, `&&`, `;`, `$(`, `then`, `do`, `exec`, or after leading `VAR=value` assignments), whatever follows
   (`run`, `record`, `report`, `seed`, `open`, `risks`, `probe`, …): there is no binary of that name. The message
   lists the three admitted replacements: for a gate or a known-answer row, the tier-target form; for a recording,
   `--example record_gate`; for a harness reader or driver, `cargo run -p frob-conformance --example <name> -- …`
   (or `-p <owning crate>`). The crate name after `-p` or `--package`, inside a path (`crates/frob-conformance/`)
   or quoted as a crate name is not a command and is not flagged.
3. `cargo run` with `-p frob-conformance` and neither `--bin <name>` nor `--example <name>`: the crate has no
   default binary (for example `cargo run -p frob-conformance -- pilots fundable` is refused, naming
   `--example pilots`).
4. `--test g0` to `--test g5` followed by a character that is not a letter, a digit or `_`: the message prints the
   long target name (`g1` → `g1_known_answers`).
5. `--test <t>`, `--example <e>` or `--bin <b>` in a command with `-p frob-conformance`, where the name is not a
   target the crate declares (a test: `tests/<t>.rs` or a `[[test]]` entry; an example: `examples/<e>.rs` or an
   `[[example]]` entry; a binary: a `[[bin]]` entry): `unknown-target`, listing the declared names of that kind.
A filter without `--test` (`cargo test -p frob-conformance tenfold::baseline`) is a legal Cargo form and is not
flagged.

**Declared binaries (`tests/binaries_declared.rs`).** The manifest sets `autobins = false` and has no
`default-run`; every file under `src/bin/` has a `[[bin]]` entry and a row in `CONTRACT.md`'s binary table; no
entry is named `frob-conformance`. A static scan checks that no file under `src/bin/` or `examples/` other than
`examples/record_gate.rs` calls the register's write functions (`register::record`, `register::write`,
`recorder::reaffirm`), so that `record_gate` stays the one writer of a gate row. A second check reads every
workspace manifest and requires each crate that declares a `conformance` feature to be listed in
`gauntlet-mutations`, and no mutation feature to be listed there: neither a feature that a control's `feature`
field in `registry/controls.toml` names (`cx-262`, whatever its spelling) nor any `nc-*` feature.

**The registry check (`tests/registry_check.rs`, the M0 form of GATE-GAUNT-01).**
1. Load `registries/gates.toml` and `registry/controls.toml`.
2. For every gate record whose status is not `not-run`: `controls` must be non-empty (INV-GAUNT-02, structural
   half). For every gate record: every listed control must exist and must name this gate in its own `gate` list
   (the two files agree in both directions).
3. A gate whose status is `pass` must list at least one control in state `runnable`, and every listed
   `runnable` control must have `last_seen.caught = true` from the run that produced the cited receipt; a
   control in state `obligation` counts toward neither (it is reported beside the gate).
4. Any violation fails the test with the gate identifier and the reason (`no-control`, `dangling-control`,
   `one-way-link`, `uncaught-control`).
A gate with no control may exist only with status `not-run` and is printed in the check's output as
`not-eligible`.

**First content at M0.** Gate rows for the gates due at M0 (the Gauntlet's own GATE-GAUNT-01, -05, -08, -10 and
the M0 gates of other subsystems as their beads register them), each with at least one control. Three reserved
identifiers bind the examples used across the documents: NC-0412 (the wheel-loop Euler-order mutation, seed
CX-262: true spectral radius 0.9207, mutant 1.497), NC-0398 and NC-0399 (the two controls of GATE-ARENA-05).

**Evidence.** The check's output is evidence of class `Tested`, kind `known-answer`, determinism class D0.

## Acceptance criteria

- [ ] `cargo test -p frob-conformance` builds and runs six tier targets and `registry_check` with no device annex.
- [ ] Seed done-condition: a gate registered without a negative control fails the registry check (GATE-GAUNT-01
      for M0), shown by the planted record of the test plan.
- [ ] The validator rejects each planted malformed control with its typed reason: `out-of-order`, `reused`,
      `removed`, `renumbered`, `no-gate`, `unknown-gate`, `kind-not-closed`, `feature-missing`,
      `fixture-missing`, `defect-or-expect-empty`, `boundary-not-control`, `unknown-seed-form` (twelve plants,
      one test each, listed below).
- [ ] A placeholder `target` (a plant identifier or a `CX-nnn` number) on a record with no `last_seen` is
      replaced once by the stated target without `renumbered`; every other change of `target` is refused.
- [ ] `CONTRACT.md` states that no `frob conformance` command and no `frob-conformance` binary exist, gives the
      cargo form of a run and of a recording, and lists every declared binary with its owning bead; a script
      that uses any of the five refused forms fails `no_conformance_command` naming the line and the
      replacement (five plants, below).
- [ ] No workspace manifest depends on `frob-conformance`; the crate is at layer 7; `gauntlet-mutations` cannot
      be enabled in a default or release build; it lists the `conformance` feature of every crate that declares
      one and no mutation feature (none that a control's `feature` names, and no `nc-*` feature).
- [ ] `binaries_declared` passes: `autobins = false`, no `default-run`, every `src/bin/*.rs` declared and in
      `CONTRACT.md` (`frob-e2e`'s entry and row, written by STD-E2E, among them), no binary named `frob-conformance`, and no binary or example other than `record_gate`
      calls a register write function.
- [ ] `CONTRACT.md` has its ten sections; no entry of the verb registry belongs to this crate.
- [ ] Every M0 gate row has a non-empty `controls` list before any M0 gate records a pass.

## Test plan

### Unit tests

`crates/frob-conformance/tests/registry_check.rs` and `src/controls.rs` inline tests, on real files:
- `control_roundtrip`: the NC-0412 record parses and re-serializes identically.
- `control_ids_append_only`: NC-0010 twice → `reused`; NC-0012 before NC-0011 → `out-of-order`; an identifier of

### End-to-end script and logging

`scripts/e2e/conformance_v0.sh` (header: `bead=BD-025 milestone=M0 labels=gauntlet,registry
gates=GATE-GAUNT-01 plants=empty-controls,dangling-control,wrong-command-forms`). Steps: build the crate; run
`registry_check` on the clean tree (expect exit 0); in a scratch copy empty the `controls` list of one `not-run`
gate (expect exit 0 and the gate printed `not-eligible`), then set that gate's status to `pass` (expect non-zero
and the reason `no-control`, since every M0 gate is `not-run` on a clean tree and only a claimed pass makes the
empty list a failure); restore and plant a dangling control identifier (expect `dangling-control`); then run
`cargo test -p frob-conformance --test no_conformance_command` and `--test binaries_declared` on the clean tree
(expect exit 0), and once more with a scratch script under `scripts/` holding the five refused forms of the unit
test (expect non-zero, and each of the five lines named with its replacement in the test output). Log through
the shared helper to `target/e2e-logs/conformance_v0/<utc>.ndjson`: each command with exit code and wall time,
the count of gates and controls loaded and the number of scripts scanned as `metric` lines, one `assert` per
plant with `kind: negative-control` and `caught` (one per refused form, with the replacement text printed), the
evidence block (claim `known-answer`, class `Tested`, determinism D0, seed 0), and the `summary` naming
GATE-GAUNT-01.

## Considerations

- Path aliases: some documents say `registries/negative_controls.toml`; the physical file is
  `crates/frob-conformance/registry/controls.toml`, and a second physical copy is a lint failure.
- The check is deliberately a Cargo test, not an `xtask` check: `xtask` records no gate and holds no policy.
- A bead or script that still writes `frob-conformance <sub> …`, `cargo run -p frob-conformance -- …` or
  `--test g0` to `--test g5` is wrong and is corrected in its own bead; the lint is what keeps a missed spelling
  from reaching an implementation.
- A binary in this crate links every workspace crate, so its build is the crate's slowest; prefer an example for a
  thin reader of registries, and a declared binary for a long-lived operator tool (the end-to-end log tool, the
  ten-fold tools).
- Risk (register row 8, "the swarm closed beads that proved plumbing"): signals are shared close reasons, a gate
  without a caught control, a pass recorded by the implementing session; this crate is the mitigation and
  GATE-GAUNT-01 is re-run at every milestone exit.
- Open: negative controls for 325 known-answer rows are not yet stated (fail-closed default: such a row supports
  no gate); see the closure beads N38b-28 onward.
- Revisit the record format if a control kind appears that the five kinds cannot express.
