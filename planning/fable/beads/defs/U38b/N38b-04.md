## Background

The Gauntlet (the verification subsystem of FrankenRobotics, crate `frob-conformance`) keeps one record per
*negative control* in `crates/frob-conformance/registry/controls.toml`. A control is a planted defect that a gate's
test must catch. The record format and the structural check (a gate with no control cannot pass) are created
with the crate (BD-025). This bead makes the registry operative: it runs each control, decides `caught` or
`missed`, and enforces the five rules that turn a list of planted defects into a guard against false progress.

The five rules (DESIGN, each with its reason).
1. A gate with no control in the registry cannot record a pass (invariant INV-GAUNT-02, gate GATE-GAUNT-01).
   Reason: "a gate no deficient model can fail validates nothing" (FACT, a sibling project's plan).
2. A control is run every time its gate is run; a gate run in which a control was not caught is a FAIL of the
   gate, whatever the passing test says. Reason: a control caught once and never re-run says nothing about the
   test as it stands today.
3. A control is a defect, not a boundary. "The request is refused at the limit" tests the limit; the control is
   the build or input in which the limit was removed. Reason: a boundary case exercises the product working as
   designed and cannot show that the test would notice the product broken.
4. A control that has never failed its gate in any recorded run is itself suspect and is reviewed at each
   milestone exit: either the defect cannot be planted as described or the gate is not looking.
5. A false certificate, a false promotion or a withdrawn result found in use becomes a permanent control,
   together with the counterexample that exposed it.

Rejected alternatives: sampling a subset of controls per run (rule 2 would hold only on average); mutation
testing by random source mutation (the planted defect must be the specific shortcut a rule exists to prevent,
not an arbitrary edit).

## Scope

In: the control runner for the five kinds of control; outcome semantics; the run history; the suspect-control
report; the permanent-control procedure; stale controls. Out: the record schema and structural check (BD-025);
seeding records from the counterexample catalogue (N38b-05); writing a gate status (N38b-19); the mutation
harness of metamorphic relations (N38a-14, same mechanism, different registry).

## Technical approach

**Kinds and how each is run (`src/control_runner.rs`; DESIGN).**

| Kind | What is planted | How the runner applies it | `caught` means |
|---|---|---|---|
| `mutation` | A wrong formula or implementation choice, as a `cfg(feature = "nc-<nnnn>")` branch at the target site in the owning crate | Rebuild the gate's tier target with `--features gauntlet-mutations,<crate>/nc-<nnnn>` and re-run the entries of every gate the control names | At least one entry of each named gate fails, with the observable stated in `expect` |
| `planted-input` | A request that asks for an unsound conclusion (a tie verdict at n = 64; a certificate with its quantifiers reordered) with the product's check removed, or offered to the checker directly | Submit the fixture through the public verb or checker | The stated refusal code or `reject` is returned |
| `planted-design` | A design that a wrong screen or prune would accept or discard wrongly | Run the screen or analysis on the fixture | The exact classifier's verdict is reported and the wrong screen's verdict is flagged |
| `planted-world` | A world or world pair that separates the shortcut from the rule (an alias pair; a third docking gain 33/32; a doorway narrower than the body) | Run the method on the world or pair | The method separates them as `expect` states |
| `a-a` | A wrong experimental procedure: an A/A campaign, or a scripted adversary (peeking at a fixed-n test; resubmission to reused clusters; audit bits chosen after the outcomes) | Run the campaign or adversary against the harness | The A/A arm does not clear its threshold, or the adversary's success rate matches `expect` |

**Algorithm (called by the tier runner after a gate's passing entries; rule 2).**
1. `controls = Controls::for_gate(gate)`. If empty, return `NoControl` (the gate line prints `not-eligible`).
2. For each control, in identifier order: check it can be planted (`mutation`: the feature exists and compiles;
   others: the fixture exists and has its `synthetic` header). If not, outcome `stale`.
3. Apply it by kind and compare the observation with `expect`. Outcomes: `caught`, `missed`, `stale`.
   A mutant build that passes every entry is `missed`. A `caught` whose observable differs from `expect` (the
   gate failed for another reason) is `caught-unexpected` and counts as `missed` until `expect` is corrected:
   a control must fail for the stated reason.
4. Emit one line per control into the run's receipt and the unit-test evidence stream
   (`kind: nc, id, gate, status: caught|missed|stale, observed, expected`).
5. The gate's line is `pass` only if every passing entry passed and every control is `caught`; any `missed` or
   `stale` makes it `fail` or `not-eligible` respectively. This decision is made only by the test kit's
   `GateReport::finish`.

**Mutation guard.** A build with any `nc-*` feature and without `gauntlet-mutations`, or under the release
profile, is a compile error (`compile_error!`). Product binaries are checked to carry none (`cargo tree -e
features`).

**History (`registry/control_history.ndjson`, append-only, one line per recorded run).** Fields: `id`, `gate`,
`receipt` (hash), `outcome`, `commit`, `session`, `date`. Written by the recording session together with the gate
row and the record's `last_seen`; never by the session that implemented the capability.

**Suspect report (rule 4; `tests/control_review.rs`).** At a milestone exit, list every control with zero
`caught` lines in the history among the gates due, and every `stale` control. Each listed control needs a typed
disposition in `registry/control_reviews.toml`: `replanted` (defect re-stated), `gate-strengthened`, or
`withdrawn` with a reason. An exit with an undisposed suspect control fails GATE-GAUNT-01.

**Permanent controls (rule 5).** Procedure when a false certificate, false promotion or withdrawn result is
found in use: (1) append the counterexample to `registry/counterexamples.toml` with the next CX number;
(2) append a control with `permanent = true`, `seed` = that CX, `kind` by the table above, attached to the gates
of the rule that failed; (3) add its row to the regression set of the owning subsystem. The loader refuses to
delete a permanent control or to remove a gate from its `gate` list.

**Evidence.** Outcomes are evidence of class `Tested`; a control result is never a known answer by itself.

## Acceptance criteria

- [ ] Each of the five kinds has a working example control and a runner path; the wheel-loop mutation (NC-0412:
      true spectral radius 0.9207, mutant 1.497) is `caught` by GATE-ARENA-04's row when that row exists, and by
      a host stand-in row at M0.
- [ ] A gate run with one control `missed` prints `fail` although every passing entry passed.
- [ ] A control whose gate fails for a reason other than `expect` is not counted as caught.
- [ ] `stale` is never counted as caught; a gate with only stale controls is `not-eligible`.
- [ ] The suspect report lists a planted never-caught control and blocks the exit until it has a disposition.
- [ ] A permanent control cannot be deleted or detached (loader error).
- [ ] No product binary carries an `nc-*` feature.

## Test plan

### Unit tests

`crates/frob-conformance/tests/control_runner.rs`, real builds and fixtures:
- `mutation_caught_wheel_loop`: one-tick spectral radius of the sampled wheel loop is 0.9207 with the specified
  feedforward R·i; with the Euler-order mutation at a 0.5 ms step it is 1.497; outcome `caught`.
- `planted_input_tie_at_64`: a fixed-n study requesting a tie verdict at n = 64 (first reachable at n = 86) is
  refused with FROB-REF-532; outcome `caught`. With the pre-analysis check disabled in a mutant build the
  request is admitted and the control of that mutant is `caught` by the row that enumerates reachable verdicts.
- `planted_world_third_gain`: docking with gains {1, 2} admits ε < (U + ½)/4; adding gain 33/32 at ε = 1/64
  leaves no exact docking; a transported certificate is rejected; outcome `caught`.
- `a_a_does_not_clear`: ten pairs of equal arms give a paired lower bound of exactly 1; 1.02 is not cleared.
- `missed_makes_gate_fail`: a no-op mutation (feature present, code unchanged) is `missed`; gate line `fail`.
- `caught_for_wrong_reason`: a mutant that panics elsewhere is `caught-unexpected`, counted as `missed`.
- `stale_control`: a feature removed from the manifest → `stale`; gate `not-eligible`.
- `suspect_listed`, `suspect_needs_disposition`, `permanent_cannot_be_removed`.

### End-to-end script and logging

`scripts/e2e/control_runner.sh` (header: `bead=N38b-04 milestone=M0 labels=gauntlet,registry
gates=GATE-GAUNT-01 plants=noop-mutation,stale-feature,never-caught`). It runs one gate with its controls on the
clean tree (expect `pass`), then plants in a scratch copy a no-op mutation (expect `fail`), a stale feature
(expect `not-eligible`) and a never-caught control at a simulated exit (expect the review to block). Log at
`target/e2e-logs/control_runner/<utc>.ndjson`: every cargo command with exit code and wall time, one `metric`
line per control (`caught`, `missed`, `stale` counts against thresholds all, 0, 0), the three negative-control
assertions, the evidence block and the `summary`.

### Known answers and negative controls

Known answers used: 0.9207 and 1.497 (CX-262); the tie first reachable at 86 pairs (KA-002); 1/65 m best
worst-case error with the third gain (CX-282). Negative controls of the runner itself: the no-op mutation, the
wrong-reason mutant, the stale feature, the undisposed suspect. Determinism: outcomes are class D0 for exact
rows and follow the row's class otherwise; the runner's verdict is identical twice on one machine.

## Considerations

- Cost: a `mutation` control needs a rebuild of the affected crates; controls are grouped by crate so one
  rebuild serves several, and runs above the default machine envelope (16 GiB, 8 cores, one hour) name their
  budget. Per change only the controls of the touched gates run; all controls run at a milestone exit.
- A mutation branch is production source under a feature; it must stay tiny and reviewed, and a crate's line cap
  counts it.
- Interaction: learning gates need behavioural controls (zero-weight, random and shuffled-label policies), run
  through the `a-a` and `planted-input` paths (N38b-08).
- Revisit rule 2's "every time" if the full control run per release exceeds its budget; the fail-closed default
  is to run fewer gates, never fewer controls per gate.
