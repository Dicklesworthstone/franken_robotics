## Background

A training pipeline can run end to end, write checkpoints, export a policy and print a number while having
learned nothing. A test that only checks the pipeline ran is a *plumbing* test. The verification subsystem of
FrankenRobotics (the Gauntlet, crate `frob-conformance`) lists the answer among its guards against false
progress:

- **Behaviour, not plumbing.** A learning gate needs a learned behaviour and failing controls: zero-weight,
  random and shuffled-label policies must fail the same threshold.

The smallest case that shows the difference (carried in the counterexample catalogue): an exported all-zero
policy head passes a plumbing test; it must fail the return threshold. This bead makes the three controls a
standing requirement of every gate that claims a learned behaviour, supplies their construction, and wires
them into the negative-control registry so that such a gate cannot pass without them.

Rejected alternative: a single "untrained policy" control. Each of the three catches a different defect: a
zero policy catches thresholds that standing still can meet; a random policy catches thresholds any motion can
meet; a shuffled-label policy catches a learner whose improvement does not come from the reward or the labels.

## Scope

In: the definition of a learning gate; the three controls and how each is built; their registration; the lint;
the planted plumbing-only gate. Out: the training algorithm and its own known answers; exploitation detectors;
the return thresholds (the learning subsystem's).

## Technical approach

**Which gates.** A gate row carries `learned = true` when its threshold is a statement about a trained policy
(a return, a success rate, a tracking error, time to a threshold). The first is the M2 training gate on the
reference quadruped's flat velocity task; later ones include family policies, inheritance and distillation.

**The three controls (each an NC record of kind `planted-input`, target the evaluation of the gate, expect
"fails the gate's threshold").**

| Control | Construction | What it shows when it passes the threshold (a defect) |
|---|---|---|
| Zero-weight | The gate's policy architecture with every weight and bias zero, exported through the same export path and evaluated by the same evaluation as the trained policy | The threshold can be met by the null action, or the evaluation does not read the policy |
| Random | The same architecture with weights drawn from its initialization law, keyed by (gate, seed) so the draw is reproducible; no training step | The threshold can be met by arbitrary motion |
| Shuffled-label | The same training run with the learning signal decoupled from behaviour: for reinforcement learning the advantages (or rewards) are permuted across samples inside each batch by an address-keyed permutation; for distillation the teacher's labels are permuted across states. Same budget, same seeds otherwise | The improvement does not come from the signal: the metric rises for another reason (an exploit, a leak of the evaluation, a curriculum effect) |

**Rules.**
1. All three are evaluated on the same worlds, tier, horizon and threshold as the trained policy, in the same
   run (a control is run every time its gate is run).
2. Each must fail the threshold, with its measured value recorded beside the trained policy's. If any passes,
   the gate fails whatever the trained policy scored.
3. The trained policy's margin over the best control is printed (difference with its interval); a gate whose
   margin interval contains zero is reported `behaviour-not-shown` even if the threshold is met.
4. A training gate record without the three controls is refused (existing refusal FROB-REF-544).
5. A policy trained under the labelled nondeterministic profile is re-evaluated under a stricter class before
   any of this is cited; the controls are evaluated under the same stricter class.

**Lint (`tests/learning_controls.rs`).** Every gate row with `learned = true` lists three controls whose
`defect` fields are exactly `zero-weight`, `random`, `shuffled-label`; a missing one makes the gate
`not-eligible`.

**Planted plumbing-only gate (the negative control of this mechanism).** A fixture gate whose threshold is
"the exported policy file exists and evaluates without error"; the zero-weight control passes it, so the lint
and rule 2 must reject the gate.

## Acceptance criteria

- [ ] Every `learned` gate lists the three controls; a gate missing one is `not-eligible`.
- [ ] On the M2 training gate the three controls fail the return threshold and the trained policy passes it,
      all in one run; the margin over the best control is printed with its interval.
- [ ] The planted plumbing-only gate is rejected because the zero-weight control passes it.
- [ ] A shuffled-label run uses the same budget and seeds as the real run and differs only in the permutation.
- [ ] A training gate record submitted without controls is refused.

## Test plan

### Unit tests

`crates/frob-conformance/tests/learning_controls.rs`:
- `zero_policy_is_all_zero`: every tensor of the exported control is zero; its action is the null action.
- `random_policy_reproducible`: same (gate, seed) gives identical weights on both machines.
- `shuffle_is_permutation`: the multiset of advantages in a batch is unchanged; their assignment to samples is
  not; the permutation is a function of (address, step).
- `controls_share_evaluation`: the four evaluations name the same battery identity, tier, horizon, threshold.
- `any_control_passing_fails_gate`.
- `margin_interval_contains_zero_is_flagged`.
- `lint_requires_three`; `plumbing_only_gate_rejected`.
- `record_without_controls_refused` (FROB-REF-544).

### End-to-end script and logging

`scripts/e2e/learning_controls.sh` (header: `bead=N38b-08 milestone=M2 labels=gauntlet,cortex
gates=GATE-GAUNT-01 plants=plumbing-only-gate`). It runs `frob train start` for the reference task at a small
budget twice (the real run; the shuffled-label run), builds the zero and random policies, runs `frob eval run`
on all four with one battery, and checks the outcomes; then the plant. Log at
`target/e2e-logs/learning_controls/<utc>.ndjson`: commands, exit codes, wall time; the four returns with units
against the threshold; the margin and its interval; the battery identity; evidence blocks (tier, determinism
class, seed); the plant's rejection; the `summary`.

### Known answers and negative controls

Known answer: the zero policy's return on a velocity-tracking task equals the return of standing still, which
the task's reference scorecard states. Negative controls: the plumbing-only gate; a shuffled run that
accidentally keeps the true signal (the permutation equal to the identity must be detected by
`shuffle_is_permutation`). Determinism: evaluations under class D2 on one backend; control weights D0.

## Considerations

- Cost: one extra training run (the shuffled one) per learning gate at the gate's budget; runs above the
  default machine envelope name their budget and wait for approval, and may run at a reduced, printed budget.
- An honest zero policy can legitimately pass a badly chosen threshold; that is a finding about the threshold,
  and the gate fails until the threshold is corrected by a dated amendment made before a new measurement.
- A policy that wins by exploiting a contact-model artifact is the business of the exploitation detectors; the
  shuffled-label control is not a substitute for them.
