## Background

GATE-GAUNT-01 is the gate that makes every other gate of FrankenRobotics meaningful. Claim kind: known answer.
Threshold (TARGET): every gate recorded as PASS has a registered negative control that it catches; a run over
all controls shows each caught by every gate it names. It is due at every milestone exit and is one of four
recurring gates re-run at each exit after the first. A negative control is a planted defect registered in
`crates/frob-conformance/registry/controls.toml`; "caught" means the gate's test fails, for the stated reason,
when the defect is planted. The rule behind it: a gate that no deficient model can fail validates nothing. The
definition of done of the program repeats it: "Every gate has a caught negative control."

This bead is the end-to-end script that measures the gate for a given milestone, and the definition of its
measured value. The six per-milestone conformance beads (BD-025 for M0, then BD-146, BD-223, BD-318, BD-377,
BD-411) supply the content that must be in place at each exit; this script is what they all run.

## Scope

In: the script, the measured values, the log, the planted failures of the measurement itself. Out: the control
runner (N38b-04); the registry and its seeding (BD-025, N38b-05); the recorder (N38b-19).

## Technical approach

`scripts/e2e/gauntlet_controls.sh <milestone>` (header: `bead=N38b-09 milestone=M0 labels=gauntlet,gate,exit
gates=GATE-GAUNT-01 plants=detach-control,noop-control`).

Steps.
1. `list`: read `registries/gates.toml`; select every gate whose status is `pass` and every gate with a part
   due at or before `<milestone>`. Emit `metric` lines: gates selected, gates with zero registered controls
   (threshold 0 among `pass` rows).
2. `structural`: `cargo test -p frob-conformance --test registry_check` (expect exit 0): no `pass` row with an
   empty `controls` list, no dangling or one-way link.
3. `run-all-controls`: for each selected gate, grouped by tier target and by crate (the groups share the
   `gauntlet-mutations` build and its cache; each `mutation` control is still planted in a build of its own,
   with only its own feature added by the control runner, N38b-04), run `FROB_TEST_SEED=0
   FROB_MILESTONE=<milestone> cargo test -p frob-conformance --test <tier> --features gauntlet-mutations --
   <gate>` (one filter, the gate, as N38a-02's selection accepts it; the milestone is the environment variable,
   never a second word after `--`). Collect, for every pair (control, gate it names), the outcome `caught`,
   `missed`, `stale` or `not-yet-due` (a control whose `due` is later than the part being run, N38b-04), and
   the receipt path each run prints.
4. `matrix`: build the control × gate matrix and write it with the step-3 receipt paths to
   `target/gauntlet/controls/<milestone>.json`. The gate's measured value is the triple (pairs caught, pairs
   total, pass rows without a caught control); the threshold is (total, total, 0). A `not-yet-due` pair is
   listed apart with its due milestone and counted in neither total.
5. `suspects`: run `FROB_MILESTONE=<milestone> cargo test -p frob-conformance --test control_review`; every
   control that has never been caught in recorded history, and every stale control, must have a typed
   disposition. (The milestone is read from `FROB_MILESTONE`, N38b-04; a word after `--` would be a test-name
   filter that selects no test and passes.)
6. `plants` (in a scratch copy): (a) detach the only control of one passing gate, expect step 2 to fail with
   `no-control`; (b) replace one control's mutation by a no-op, expect that pair to read `missed` and the
   measured triple to fall below threshold.
7. `gate-entry`: run the gate's own entry, `FROB_TEST_SEED=0 FROB_MILESTONE=<milestone> cargo test -p
   frob-conformance --test g1_known_answers --features gauntlet-mutations -- GATE-GAUNT-01`. The entry
   (`tests/control_matrix.rs` registers it in the G1 target; DESIGN) reads `target/gauntlet/controls/
   <milestone>.json`, re-reads each step-3 receipt it names (hash checked), recomputes the triple and passes only
   at the threshold; in the same run the control runner plants the gate's own two controls, so the receipt
   carries GATE-GAUNT-01's line and both controls `caught`, which the recorder's same-run rule requires (N38b-19
   step 4). Without this run no receipt has a GATE-GAUNT-01 line, and the gate could never be recorded.
8. `end`: print the triple, the list of missed pairs, the `not-yet-due` pairs, the list of obligations (controls
   registered but not yet runnable because their source states no numeric case or no control) and the hash of
   the step-7 receipt.

A fresh-context session records GATE-GAUNT-01 for the milestone from the step-7 receipt with the recorder
(N38b-19); the script itself never runs the recorder (STD-E2E, `self-recording`). The gate's own controls are the
two plants of step 6, registered by N38b-23 as NC records of kind `planted-input`; they are also the gate's two
listed controls, which recording requires `caught` in that receipt.

**Logging.** `target/e2e-logs/gauntlet_controls/<utc>.ndjson` and a transcript. One `cmd` event per cargo
invocation (exact command, exit code, wall time); one `metric` event per (control, gate) pair with `outcome`;
summary metrics `pairs_caught`, `pairs_total`, `pass_rows_without_caught_control`, `suspects_undisposed`
(threshold 0), `obligations`; `assert` events for steps 2, 4, 5 and both plants, with on failure the first
missed pair and the path of the mutant build log; the evidence block `{claim: known-answer, class: Tested,
determinism: per row, seed: 0, identities: commit, toolchain, fingerprint}`; the final `summary` with counts and
GATE-GAUNT-01.

## Acceptance criteria

- [ ] On a tree where every passing gate has caught controls the script exits 0 and prints a full matrix.
- [ ] A passing gate with no control, a missed pair, a stale control or an undisposed suspect each make it exit
      non-zero and name the gate and control.
- [ ] Both plants are caught on every run.
- [ ] The script takes a milestone argument and produces the M0 to M5 measurements used by BD-025, BD-146,
      BD-223, BD-318, BD-377 and BD-411; it is re-run at the exits of M6, M7 and M8.
- [ ] Runs above the default machine envelope (16 GiB, 8 cores, one hour) are split by crate and resume from
      the last finished group; the reduced coverage of an interrupted run is printed, never rounded up.

## Test plan

### Unit tests

`crates/frob-conformance/tests/control_matrix.rs`:
- `matrix_from_outcomes`: 3 controls × 2 gates with one `missed` gives (5, 6, 1) when the missed pair belongs
  to a pass row.
- `full_matrix_passes`; `obligation_not_counted_as_caught`; `stale_blocks`.
- `selection_by_milestone`: on a fixture `gates.toml` with rows due at M0, M1 and M3 and one `pass` row due at
  M3, the argument `M1` selects the M0 and M1 rows and the `pass` row, and nothing else.
- `interrupted_run_resumes`: a run stopped after two of three crate groups resumes at the third and re-runs
  neither finished group; an interrupted run reports `pairs_total` of the groups run with `coverage: 2/3`,
  never the full total.
- `ritual_run_rejected`: a run in which either plant was not caught is rejected whatever its matrix says.
- `not_yet_due_counted_apart`: a fixture pair whose control is due M2, run for M1, appears in the
  `not-yet-due` list and changes neither `pairs_caught` nor `pairs_total`.
- `gate_entry_reads_matrix`: the GATE-GAUNT-01 entry on a fixture matrix of (6, 6, 0) passes; on (5, 6, 1) it
  fails with the missed pair named; with one receipt named by the matrix altered by a byte it fails naming
  `receipt-hash-mismatch`; its receipt lists both of the gate's controls.

### End-to-end script and logging

As above. Selection: `scripts/e2e/run-all.sh --label exit --milestone <M>`.

### Known answers and negative controls

Known answer of the measurement: on the fixture registry of the unit test the triple is (5, 6, 1). Negative
controls: the detached control; the no-op control. Live-dependency proof: adding one control to one gate raises
`pairs_total` by exactly one. Determinism: the matrix is identical twice on one machine for D0 to D2 rows; for
rows of class D3 the outcome (caught or missed) is the compared quantity, not the digests.

## Considerations

- Cost grows with the number of mutant builds (one per mutation control); grouping by crate, so that a
  mutant rebuilds only its own crate and its dependents, and caching by (commit, feature set) keep a
  milestone run inside the nightly budget, which is still an open question (fail-closed default: `smoke` and
  `fixtures` controls per change, everything else nightly).
- A control registered as an obligation does not make its gate eligible; the count of obligations due by M3
  must be zero by M3.
- Risk: the script becomes a ritual. Guard: the suspect review and the plants; a script run in which no control
  was missed and no plant was caught is itself rejected.
