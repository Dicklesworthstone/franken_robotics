## Background

FrankenRobotics records acceptance in one data file, `registries/gates.toml`, at the repository root. It holds
one record per gate, kill gate and admission gate: 421 identifiers at the end of the first planning phase (FACT:
278 convergence gates, 111 kill gates and 32 admission gates in that inventory; later subsections add more,
which append). The printed gate register is its printout, and where a subsystem's own text and the register
differ the register governs. The verification subsystem (the Gauntlet, crate `frob-conformance`) owns the file's
*status accounting*: what a record must say before it may read `pass`.

Why it exists: a number in the design is a TARGET until a gate records a measured value, and sibling projects
showed gates that were never run printing as passed, and the session that built a capability declaring it
passed. The record below makes "not run", "failed", "killed with a fallback" and "no claim" four different
states, and makes `pass` conditional on a caught negative control (a planted defect the gate's test must catch)
and on a recording session that did not implement the capability.

DESIGN: one TOML file with generated views (ADR-GAUNT-02), written only by a recording session that cites a
hash-named receipt of a harness run (ADR-GAUNT-01: no verb and no `xtask` subcommand writes a gate). Rejected:
a status column edited by hand in a README; a Boolean `passed`, which cannot tell "not run" from "failed".

## Scope

In: the base part of the one schema `frob.gates/1`: the base fields and the meaning of each; the closed set of
claim kinds; the status set and the meaning and rule of each status; the four conditions under which `pass` is
refused, stated as the contract the validator implements; the types `Claim`, `Status`, `GateBase` and
`PartBase` with parsing and printing of a base record; the plan-time count as an assertion.

Out, with the bead that has it: the register layer on the same schema (N40-01, the gate-register chapter's bead,
which depends on this bead): the fields it adds (`kind`, `consumers`, `recurring`, `needs`, and on a part
`scope`, `commit`, `command`, `receipt`, `fingerprint`, `seed`, `detail`; the admission and kill fields), the
nine rules of the register, the loader and the validator `validate()`, the write path `record()`, and the ten
write-time refusals with their reason strings and planted rows. Every cross-field rule is checked there and
only there: this bead states the four `pass` conditions and the rules of each status as the contract, and the
validator's tests for them (`pass_refused_without_control`, `pass_refused_when_control_missed`,
`pass_refused_self_certified`, the unresolved-evidence and target-as-measurement cases, `no_claim_only_for_reality`,
the `killed` and `blocked` cases, `ids_append_only`) are N40-01's. There is one schema file and one definition
of each field; this bead and N40-01 print the same record. Also out: the recording procedure and session
identity (N38b-19); generated views (N38b-20); the control registry (BD-025).

## Technical approach

**Base record (schema name `frob.gates/1`; the register layer adds fields to the same schema).** The base
fields are shown; a comment marks where the register layer's fields (N40-01) sit.
```toml
[[gate]]
id         = "GATE-ARENA-05"
claim      = "known-answer"        # proof | known-answer | parity | fidelity | design-comparison | reality | performance
claim_id   = "clm:…"               # identifier of the claim the pass rests on; resolves in the artifact graph
section    = "24.17"               # the defining subsection, whose chapter owns the gate
threshold  = "eval.preanalyze reproduces the fixed-n tables exactly and refuses the unreachable verdict"
milestone  = "M1"                  # earliest milestone at whose exit a record is required
tier       = ["G1:host"]           # Gauntlet tier and execution site of the measuring test
controls   = ["NC-0398", "NC-0399"]  # registered negative controls; every one must be caught in the same run
# register layer, gate level: kind, consumers, recurring, needs
[[gate.part]]                      # one per milestone at which a part of the gate is due; most gates have one
milestone  = "M1"
status     = "not-run"             # not-run | pass | fail | killed | blocked | no-claim | superseded
measured   = ""                    # the value with its unit and interval, or the count; never the target
evidence   = []                    # ledger sequence numbers and trace identifiers
recorded   = { date = "", session = "", implemented_by = "" }
# register layer, part level: scope, commit, command, receipt, fingerprint, seed, detail
```

**Status is recorded per part (DESIGN, settled with the register layer).** An earlier form of this record
carried `status`, `measured`, `evidence` and `recorded` once per gate. The register's rule that a gate with two
milestones has a part due at each (35 convergence gates and 3 admission gates at plan time) cannot be recorded
that way without a premature pass or a late one, so the four fields live on `[[gate.part]]`, and a gate with
one milestone has one part. A gate's own status is derived and never stored: `not-run` when no part is
recorded; otherwise the status of its latest due part. Every rule below that speaks of a record's status, of
`pass` or of `measured` applies to a part.

**Kill rows measure nothing.** A kill gate's row (register layer `kind = "kill"`) decides and measures nothing,
so it carries none of the measurement fields `claim`, `claim_id`, `threshold`, `tier`, `controls` and
`[[gate.part]]` (its own fields, `trigger`, `fallback`, `decided` and the others, are the register layer's). The
base parse therefore requires those fields only on rows of kind `admission`, `convergence` or `program`, and a
kill row that carries one fails the load naming the field (N40-01's check). Field rules 1, 3 and 4 below apply to
admission, convergence and program rows only.

**Field rules.**
1. `claim` takes exactly one of the seven kinds and nothing else: *proof* (a checker accepted a proposition in
   the declared model), *known-answer* (an analytic or synthetic truth recovered), *parity* (agreement with a
   pinned reference tool or published number), *fidelity* (a faster tier tracks a more trusted one),
   *design-comparison* (one design or method beats another on a stated family of worlds), *reality* (agreement
   with physical measurement), *performance* (a speed or scale figure on named hardware). A gate whose source
   row reads "Performance of the method" or "method" is recorded as `design-comparison`, because it compares
   methods and does not measure the engine.
2. `status` meanings: `not-run` (no record; printed "not run"; never shown as passed); `pass`; `fail` (a failing
   value is a record, so that it can be reproduced: it requires `measured`, and the register layer's part fields
   `commit`, `command` and a `receipt` that resolves as in rule 3(d)); `killed` (names the kill gate that fired and the fallback now in force; the capability is
   described by the fallback's name from then on; both are written in the part's `detail`); `blocked` (waits
   on an open question, whose identifier is in `detail`; the status is part of this set and its rule is checked
   by the register layer); `no-claim` (a terminal status, legitimate only for gates whose claim is `reality`;
   it is the resting status of an import-lane gate, one whose measurement needs a bench, a physical board, a
   scan, real-robot data or a human panel, marked `needs = "import-lane"` by the register layer and due at no
   milestone's exit); `superseded` (replaced by a named gate, whose identifier is in `detail`).
3. `pass` is refused in four cases: (a) `controls` is empty; (b) any listed control was not caught in the same
   run as the passing measurement; (c) `recorded.session` is a member of `recorded.implemented_by` (the sorted,
   comma-joined set of implementing sessions computed by the recorder, N38b-19; a co-implementer is refused as
   much as the sole implementer); (d) an `evidence`
   item or the `claim_id` does not resolve in the artifact graph (the content-addressed graph of claims,
   evidence items and executions; a dangling or tombstoned node prints `evidence: unavailable` and cannot be
   cited, existing refusal FROB-REF-869), or the part's `receipt` does not name a committed file
   `receipts/gates/<hash>.json` whose bytes hash to it (the recorder commits that copy with the row, N38b-19).
4. `measured` carries the measured value, not the target, with unit and interval (or a count such as
   "561 of 561"); a record whose `measured` is empty or byte-equal to `threshold` is not a pass.
5. Identifiers are unique and append-only; a retired identifier is tombstoned, never reused.
6. A milestone exit is a query over this file: every gate with a part due at the milestone is `pass` or
   `killed` with its fallback adopted; a `fail` with no kill gate blocks the exit.

**Status reconciliation (recorded as an architecture decision).** The register's own semantics list `not run`,
`pass`, `fail`, `killed: fallback adopted` and `blocked: ⟨open question⟩`; this base record lists six values
with `no-claim` and `superseded` and without `blocked`. The file uses the union of seven: the base six, plus
`blocked` owned by the register layer (it requires the open question's identifier). Printed forms: `not-run` →
"not run"; `killed` → "killed: fallback adopted (<fallback>)"; `blocked` → "blocked: OPEN-…".

**Code.** Types `Claim` (seven variants), `Status` (seven variants, `Blocked` included, so that the enum is
defined once), `GateBase` and `PartBase` in `crates/frob-conformance/src/register/row.rs`, with no
dependency outside `frob-core`, so that the generated-file check can print tables without depending on the
conformance crate. N40-01 defines `GateRow`, `Part` and `Kind` in the same module as these base types plus its
added fields, and `validate.rs` and `write.rs` beside it. Loading and printing are pure functions of the file
bytes (determinism class D0). What this bead's code rejects is what a type can reject at parse time: an unknown
or doubled claim, an unknown status, a missing base field. Everything that compares two fields or looks
outside the record is the validator's.

**Plan-time assertion.** A meta-test compares the count of records per kind with a committed expectation file
(`registry/gate_counts.toml`: 278, 111, 32 for the first inventory, then each dated addition) and reports the
identifiers that differ; a change is accepted only with a new dated line.

## Acceptance criteria

- [ ] The example record loads; an unknown status, an unknown claim, two claims, or a missing field each fail
      the load and name the gate; a kill row loads without the measurement fields, which it never carries.
- [ ] "Performance of the method" is rejected as a claim value and mapped to `design-comparison` only by an
      explicit row edit.
- [ ] The four `pass` conditions and the rule of each status are written in the schema file's comments and in
      `CONTRACT.md` as the contract of the validator. Their planted records (the planted self-certification and
      the planted pass with an uncaught control are the two that GATE-GAUNT-10 names; `no-claim` on a
      non-reality gate; `killed` without a kill-gate identifier and fallback name) are rejected by N40-01's
      validator and tested there; this bead's acceptance does not wait for them.
- [ ] A base record with two parts (M1 and M3) loads, prints both, and reports the gate's derived status from
      its latest due part; a gate with no part recorded prints "not run".
- [ ] The count assertion holds on the seeded file and reports a planted extra record.
- [ ] One schema file serves this bead and the register layer; no second definition of a gate record exists,
      and the record printed here equals the base fields of the record printed in N40-01.

## Test plan

### Unit tests

`cargo test -p frob-conformance register::base` (fixtures labelled `synthetic`):
- `base_record_roundtrip`: the GATE-ARENA-05 example parses and prints identically.
- `claim_is_one_of_seven`: each of the seven loads; `"method"`, `"performance of the method"`, `["parity",
  "performance"]` are rejected.
- `status_closed_set`: the six base values and `blocked` load; `"passed"`, `"ok"`, `""` are rejected.
- `two_part_record_roundtrip`: a gate with parts at M1 and M3 parses and prints identically; its derived status
  is that of the M3 part once M3 is due, and `not-run` with no part recorded.
- `missing_base_field_names_gate`: on a convergence row, each base field removed in turn fails the load with the
  gate's identifier.
- `kill_row_carries_no_measurement_fields`: a `kind = "kill"` row with no `claim`, `claim_id`, `threshold`,
  `tier`, `controls` or `[[gate.part]]` parses and prints identically.
- `count_assertion`: 278 + 111 + 32 = 421 on the first inventory fixture.
The cross-field cases this bead first listed (`pass_needs_controls`, `pass_needs_same_run_catch`,
`pass_needs_other_session`, `pass_needs_resolving_evidence`, `measured_is_not_target`, `no_claim_only_reality`,
`killed_names_fallback`, `superseded_names_successor`, `ids_unique_append_only`) are validator tests and are in
N40-01 (`pass_refused_without_control`, `pass_refused_when_control_missed`, `pass_refused_self_certified`,
`pass_requires_all_fields`, `no_claim_only_for_reality`, `killed_and_superseded_need_detail`, `ids_append_only`).

### End-to-end script and logging

Exercised by `scripts/e2e/status_accounting.sh` (bead N38b-21), which records a real measurement, regenerates the
status table and plants the refused records. This bead's own script, `scripts/e2e/gate_record_schema.sh`
(header: `bead=N38b-18 milestone=M0 labels=gauntlet,registry gates=GATE-GAUNT-10 plants=bad-claim,bad-status`),
validates the committed file and two planted files, logging to `target/e2e-logs/gate_record_schema/<utc>.ndjson`:
commands with exit codes and wall time, records per status and per claim as `metric` lines, one `assert` per
plant, and the `summary`.

### Known answers and negative controls

Known answer: the inventory count 421 = 278 + 111 + 32. Negative controls: the four refused `pass` records; the
two-claim record; `no-claim` on a non-reality gate. Metamorphic relation: permuting records leaves every
generated view unchanged apart from order. Determinism: D0, byte-identical printing on both platforms.

## Considerations

- A second count exists in the documents (112 kill gates in the register's introduction against 111 in the
  inventory); the expectation file records which identifiers each count includes, and the meta-test reports the
  difference instead of choosing.
- The claim-identifier prefix is shown as `clm:` here and as `c:` in the per-bead log example; the identity
  module of `frob-core` fixes one, and both files follow it.
- Until the artifact graph exists (M1), resolution is checked against the ledger of the M0 spike; a pass
  recorded then is re-resolved when the graph lands.
- Risk: a pass recorded by the implementing session; signal: equal session identities; mitigation: refusal (c)
  and the exit review by a fresh-context session.
