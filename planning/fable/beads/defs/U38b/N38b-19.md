## Background

In FrankenRobotics a gate (a numbered acceptance threshold) is recorded in `registries/gates.toml`. The
verification subsystem (the Gauntlet, crate `frob-conformance`) has no agent verb: a tier of the harness is a
Cargo test target, a run writes a *receipt* (a canonical JSON file named by the BLAKE3 hash of its bytes, with
the commit, toolchain, hardware fingerprint, seed, the measured values, one line per negative control and one
line per gate), and a *recording session* then enters the gate's row, citing the receipt. This bead is that
recording step.

Two rules make the step more than a file edit. First, invariant INV-GAUNT-02: every gate that records a pass
has at least one registered negative control that was caught in the same run. Second, invariant INV-GAUNT-05
("no self-certification"): a pass is recorded by a session that did not implement the capability; the exit
review of a milestone is likewise done by a fresh-context session. The reason is recorded experience from
sibling projects, where the swarm that built a thing also declared it done (risk signal: "a PASS recorded by the
session that implemented the capability").

DESIGN: the recorder is a library function plus a Cargo example target, `cargo run -p frob-conformance --example
record_gate -- --gate <id> --receipt <hash> [--part <milestone>]`. An example target is neither a verb nor an
`xtask` subcommand, so the harness is not reachable through the surface it judges. Rejected: letting the tier
runner write the status itself (the session that ran the test would certify it); a `frob gate record` verb.
The example is the one writer of a row of `registries/gates.toml` (BD-025's rule for the crate's targets). Its
argument parser has one further mode, `reaffirm`, which N29bp1-01 adds (the demotion of recorded parts whose
evidence became unavailable): `cargo run -p frob-conformance --example record_gate -- reaffirm --registry
registries/gates.toml …`; with no mode word the example records. This bead provides the dispatch and the lock the
mode takes; the mode's walk, report and tests are N29bp1-01's.

## Scope

In: the recording algorithm; how the two session identities are obtained; the same-run rule; the recorder's
refusals; the receipts a part cites and the receipt set; recording a part again; the side effects (committed
receipts, control history, bead log line, regenerated views). Out: the record schema
(N38b-18); the register layer's extra validation (N40-01's validator) and kill decisions (N40-03's kill
records); the views' generators (N38b-20); the citation guard `cite` (N29b-10, which wires it into step 6); the
re-affirmation of recorded parts against the live graph (N29bp1-01, which takes this recorder's lock).

## Technical approach

**Session identities (DESIGN).** Every agent session has an identifier (`session:<name>`), exported as
`FROB_SESSION` by the session harness and written as a `Frob-Session:` trailer on each commit it makes.
- `recorded.session` = `FROB_SESSION` of the session running the recorder.
- `recorded.implemented_by` = the set of sessions on commits that changed the capability: the union of
  `Frob-Session` trailers over commits, from the opening of the beads that deliver the gate up to the receipt's
  commit, that touch the crates named by those beads; plus every session on an `implement` line of those beads'
  logs. Stored sorted and comma-joined.
- Refusal `self-certified` when `recorded.session` is a member of `implemented_by`.
This is a discipline check, not authentication: an identity can be falsified by a session that sets another
name. The planted self-certification test and the exit review are the detection; the limit is stated in
`CONTRACT.md`.

**Algorithm (`register::record`).**
1. Load the receipt `target/gauntlet/receipts/<hash>.json`; recompute BLAKE3 of the bytes; mismatch →
   `receipt-hash-mismatch`.
2. The receipt's `commit` must be an ancestor of `HEAD` and its `dirty` flag false → else
   `receipt-commit-unknown`, `receipt-dirty-tree`. Its `stack_dev` must be false → else `receipt-stack-dev`, for
   any status: a result of a development stack identity is never a record (N33a-06; N40-01, "Where receipts
   live"). Beside these guards the recorder calls `frob_core::stack::build_identity::may_cite(gate_class)`
   (N33a-08) with the gate's claim, reading the producing binary's mode from the receipt's `build_identity`
   (`dev-salt` or `depgraph-receipt`, `frob_core::stack::BUILD_IDENTITY_MODE`, N38a-02); when it errs a `pass` is
   refused with `dev-build-identity` (a Performance or Parity gate under `dev-salt`); a `fail` is recorded.
3. Find the gate's line. `pass` in the receipt is required to record `pass`; `fail` records `fail` with the first
   differing value; `not-eligible` records nothing (`gate-line-not-eligible`); `no-claim: <reason>` records status
   `no-claim` with `detail = "<reason>"`, only on a gate whose `claim` is `reality` (else
   `no-claim-on-non-reality`, the register validator's reason). That fourth line is written only by the Reality
   lane's tier entry (BD-397) and asserts no measurement, so the same-run rule of step 4 does not apply to it. A line whose receipt carries
   `reduced: <count> of <target>` (a run below the gate's stated count, N38b-25) never records `pass` against
   the full-count threshold → `reduced-not-recordable` (repair: run the full count, or record the reduced value
   as measured, never as a pass at the full count).
4. Same-run rule: every identifier in the row's `controls` must appear in the receipt's `controls` list for this
   gate with outcome `caught`. Missing → `control-missing-from-receipt`; `missed` or `stale` →
   `control-not-caught`. An empty `controls` list → `pass-without-control`.
5. Compute the session identities; refuse `self-certified`.
6. Resolve every evidence item and the `claim_id` in the artifact graph; a dangling or tombstoned node →
   `evidence-unresolved`. From M1 this resolution is the call `cite(claim, scopes)` of N29b-10, wired into this
   step by that bead: a claim whose state is not `Resolved` (refusal FROB-REF-869) is reported here as
   `evidence-unresolved` with the state and the missing nodes. At M0, before the artifact graph exists, the step
   checks the ledger of the M0 spike (N38b-18) and the pass is re-resolved when the graph lands.
7. Run the register layer's validator on the candidate row, then the checks that other beads of this crate add
   to this step through one hook list (`register::record::CHECKS`, each a pure function of the candidate row and
   the resolved evidence returning `Ok` or a harness reason): `claim_matches_evidence` (added by N38a-05 at M0;
   reason `claim-evidence-mismatch`: the row's claim kind is stronger than the kind its evidence can carry),
   `origin_labels_admissible` (added by N38b-07 at M0; reasons `origin-label-mismatch`: the recomputed claim
   product carries a `synthetic` or `development-oracle` label the presented evidence lacks, and
   `origin-not-admissible`: development-oracle evidence for any gate, or synthetic evidence for a `reality`
   gate), `exploratory_not_cited` (added by N21c-34 at M0; reason `evidence-unresolved` with cause
   `exploratory: OPEN-SPARK-1 <status>`: a Performance or Parity part whose evidence is a device receipt while
   ADR-SPARK-01 is not `ratified`), `receipts_of_record` (added by N32ax-03 at M0; reason `receipt-not-of-record`:
   an evidence receipt for which `frob_core::registries::assert_of_record` fails, because it was made under a
   scratch or snapshot registry root or with a run-time registry in its fail-closed reading) and `potency_current`
   (added by N38a-36 at M3; reasons `no-potency-record`: an evidence item produced by a
   registered analysis, screen or attribution method has no potency record on the corpus version in force, and
   `not-potent`: its record's verdict is `not-potent`). The recorder owns the hook and its order (validator
   first, then the hooks in registration order; the first refusal stops the step); the checks and their tests
   are those beads'. Until a check's bead lands its entry is absent and the step runs without it.
8. Write: `status`, `measured` (the receipt's measured values with units and intervals, or the count),
   `evidence`, `recorded = { date, session, implemented_by }`, and the receipt hash, commit, command, fingerprint
   and seed (all six are required of a `pass` by the register's rule 1, N40-01).
9. Side effects in the same commit: commit a byte-identical copy of each receipt the part cites, and of its
   receipt set if it has one, at `receipts/gates/<hash>.json` (N40-01, "Where receipts live"); the part cites
   that hash, never a copy under another name. Set each control's `last_seen` in `registry/controls.toml`; append
   one line per control to `registry/control_history.ndjson`; append a `gate-record` line of `frob.beadlog/1`
   (N29a-09) to the delivering bead's log `docs/delivery/logs/<bead>.ndjson` (verdict, claim identifiers,
   `recorded_by`, gate, and `receipt` = the same hash written into the part's `receipt`); regenerate the status
   views.
10. Print the row and the list of regenerated files. Nothing is written if any step refuses.

**Lock (DESIGN).** Steps 1 to 10 run under one exclusive lock on the gate registry: a lock file
`registries/gates.toml.lock` created with exclusive create, holding the session and the start time, removed on
exit; a second recorder waits up to a stated timeout and then refuses with the holder named; a stale lock (its
process gone) is reported, never silently broken. The re-affirmation command of N29bp1-01, which demotes recorded
`pass` parts whose evidence became unavailable, takes the same lock, so a demotion and a recording never
interleave on one registry.

**Receipts of a part (DESIGN).** A receipt is written per tier run (N38a-02), and a gate whose entries sit in two
tiers (GATE-TRAC-08: its law rows in `g1_known_answers`, its rut row in `g4_chaos`) is measured by one run of
each, as N40-08's `one_run` rule allows (one receipt per tier where rows differ by tier). `--receipt` is therefore
repeatable, one per tier target the part's entries run in: `record_gate -- --gate <id> --receipt <hash>
--receipt <hash> [--part <milestone>]`. The receipts of one recording come from one commit; two of one tier, or
receipts of two commits, are refused with `receipt-set-invalid`, naming the tier or the commits. Steps 1 to 7
apply to each receipt. The part's line is `pass` only if every receipt's line for the gate is `pass`, `fail` if
any is `fail` (the first differing value of the first failing receipt in tier order), and `not-eligible`
otherwise; `measured` and `evidence` are the union in tier order (G0 to G5). With one receipt nothing changes.
With several, the recorder writes a receipt set: canonical JSON of schema `frob.gauntlet.receipt-set/1`, fields
`gate`, `part` and `members` (the receipt hashes in tier order), named by the BLAKE3 hash of its bytes and
committed beside its members under `receipts/gates/`. The part's `receipt` is the set's hash, its `commit` the
members' one commit, and its `command`, `fingerprint` and `seed` list the members' values in tier order,
separated by `; `. A reader of a part's receipt (the register's validator, N40-01; `check-stack`, N33c-30; the exit
review, N40-05; the bead-log checks of N29a-09 and N41-17) follows a set to its members.

A part measured on several machines (GATE-SPARK-21 on `trj` and this Mac; GATE-SPARK-22 on three devices of two
machines) is recorded from one receipt per tier: the receipt of the final run of the gate's filter on one machine,
whose entries read the other machines' collated outputs and re-check the thresholds, so that the receipt it cites
carries every measured value and every control outcome of the part. This is the form of BD-142, BD-217, N21a-24
and N36p1-01.

**Recording a part again (DESIGN).** A recorded part is recorded again only from newer receipts of the same gate
and part, through every step above. The new recording replaces the part's fields and its `recorded.date` dates the
change; the receipts of the earlier recording stay committed under `receipts/gates/`, so the earlier value remains
in the history. Each part has one recording bead, the bead that measures the gate, named in the gate's register
row. One other bead may record the part once more: the bead that lifts a row which the recording bead
recorded against a fallback named in advance (a row of a lower-priority Frontier or Moonshot mechanism;
GATE-TRAC-08's rut row, recorded by BD-366 on the fallback "off; terrain resets each episode" and lifted by
N18b-17, both at M4). Its recording session implemented neither bead, which `implemented_by` checks as for any
recording. It gives a receipt for every tier of the part from runs at its own commit, so that no row is lost: a
recording whose receipts omit an entry that the replaced recording measured and that is still registered is
refused with `part-rows-dropped`, naming the entry.

**Other statuses.** `killed` is never written by the recorder: it is derived by N40-03's
`apply_decisions(&Register) -> Register` (a dependency), the one place a gate becomes `killed`, when the kill row
whose `reads` names the gate has a decision in force with outcome `fired`, the decision record
`docs/adr/ADR-<gate-name>-<milestone>.md` with N40-03's required fields, and the gate's recorded status `fail`;
the derived row carries `detail = "<kill gate>: <fallback>"` and describes the capability by the fallback's name.
The recorder keeps writing the measured history underneath (a later receipt of a killed gate records its `fail`
or `pass` value as usual; the derived status is recomputed from it). `no-claim`: only for a `reality` gate, with
the reason (for example `no-dataset-admitted`), from the receipt line of step 3. `fail`: recorded with the measured value; a failing value is a
record and blocks the milestone exit unless a kill gate covers it.

**Refusal reasons (recorder errors, not agent-facing refusal codes; exit status 3).** `receipt-hash-mismatch`,
`receipt-commit-unknown`, `receipt-dirty-tree`, `gate-line-not-eligible`, `pass-without-control`,
`control-missing-from-receipt`, `control-not-caught`, `self-certified`, `evidence-unresolved`,
`reduced-not-recordable`, each with the repair (re-run the tier; register the control first; record from a fresh
session; cite a live receipt; run the full count); `receipt-stack-dev` (re-run the tier from a binary built under
a clean stack receipt); `dev-build-identity` (rebuild under `depgraph-receipt` and re-run; or record the value
without citing it as a pass); `receipt-set-invalid` (give one receipt per tier, all from one commit);
`part-rows-dropped` (add the receipt of the dropped entry's tier). The register validator's reasons of step 7
(for example `no-claim-on-non-reality`) are N40-01's. Beside them, step 7's hooks return `claim-evidence-mismatch`
(repairs, in order: record the row with claim `parity`; cite evidence of the claimed kind; leave the gate
`not-run`), `origin-label-mismatch` (cite the receipt as produced; re-run on the real tier),
`origin-not-admissible` (re-run on the CPU referee; record a non-reality claim),
`receipt-not-of-record` (re-run under the registries of record),
`no-potency-record` (run the potency check on the current corpus; cite a different method) and `not-potent`
(improve the method and re-run on the held-out half; leave the gate `not-run`), with the same exit status 3 and
nothing written. The reason strings and repairs are those of the reference table N38-REF.

**Evidence and determinism.** A recorded row is evidence of class `Tested` (or the class of the claim it
cites); the recorder is deterministic (D0) apart from `date`.

## Acceptance criteria

- [ ] Recording a passing receipt writes the row, the control history, the bead log line and the views in one
      commit; re-running with the same receipt is a no-op.
- [ ] A planted self-certification is refused (`self-certified`), and the same receipt recorded by another
      session is accepted (GATE-GAUNT-10, clause 2).
- [ ] A planted pass whose receipt shows one control `missed`, or omits a listed control, is refused
      (GATE-GAUNT-10, clause 3; INV-GAUNT-02).
- [ ] A receipt altered by one byte, from a dirty tree, or from an unknown commit is refused.
- [ ] A pass citing a tombstoned evidence item is refused.
- [ ] A receipt line marked `reduced` is refused for a full-count threshold (`reduced-not-recordable`).
- [ ] Two recorders started on one registry serialize through the lock; no write is torn, and the re-affirmation
      command of N29bp1-01 waits on the same lock.
- [ ] `measured` in the written row equals the receipt's measured values, never the threshold text.
- [ ] Step 7 runs the validator and then every registered hook; a refusal from any of them exits 3 with its
      reason and writes nothing.
- [ ] `CONTRACT.md` states the identity mechanism and its limit.
- [ ] The recorder never writes `killed`; a gate whose kill decision in force is `fired` reads `killed` only in the
      output of N40-03's `apply_decisions`.
- [ ] A receipt with `stack_dev = true` is refused (`receipt-stack-dev`); a `pass` of a Performance or Parity gate
      from a receipt whose `build_identity` is `dev-salt` is refused (`dev-build-identity`), and the same receipt
      records a Known-answer gate.
- [ ] A receipt line `no-claim: <reason>` records `no-claim` with the reason in `detail` on a `reality` gate and is
      refused on any other gate (`no-claim-on-non-reality`).
- [ ] Every receipt a part cites, and its receipt set, is committed byte-identical at `receipts/gates/<hash>.json`
      in the commit of the row, and the bead log's `gate-record` line carries the part's `receipt`.
- [ ] A part recorded from receipts of two tiers cites a receipt set whose members resolve; two receipts of one
      tier, or of two commits, are refused (`receipt-set-invalid`); a recording that drops an entry the replaced
      recording measured is refused (`part-rows-dropped`).

## Test plan

### Unit tests

`crates/frob-conformance/tests/recorder.rs`, on a scratch repository built by the test (real git, real files):
- `record_pass_happy_path`: gate with controls NC-A and NC-B, both `caught` in the receipt, recorder session
  `s2`, implementer `s1` → row `pass`; history has two lines; the log line has `recorded_by: "session:s2"`.
- `record_idempotent`: second call changes no byte.
- `refuse_self_certified`: recorder `s1`, commits by `s1` → refused; a co-implementer set {`s1`, `s3`} refuses
  `s3` as well.
- `refuse_control_missed`, `refuse_control_absent_from_receipt`, `refuse_empty_controls`.
- `refuse_tampered_receipt`, `refuse_dirty_tree`, `refuse_unknown_commit`.
- `refuse_unresolved_evidence`: a dangling node and a tombstoned node, each refused with the node named.
- `refuse_reduced_count`: a receipt line `reduced: 1000 of 10000` against a threshold stated at 10⁴ → refused.
- `lock_serializes_recorders`: two recorder processes on one scratch registry; the second waits and then writes
  a valid file; a planted stale lock is reported with its holder.
- `fail_is_recorded`: a failing receipt writes `fail` with the first differing value.
- `killed_is_derived_not_written`: in a scratch register whose kill row KILL-X reads GATE-Y and has decision
  `{outcome = "fired", adr = "docs/adr/ADR-KILL-X-M2.md", …}`, recording a failing receipt of GATE-Y writes status
  `fail` with the measured value; no byte of the stored row is `killed`; `apply_decisions` on the same register
  prints GATE-Y `killed` with `detail = "KILL-X: <fallback>"`; with the decision outcome `not-fired` it prints
  `fail`.
- `no_claim_only_reality`: a receipt line `no-claim: no-dataset-admitted` on a `reality` gate with no control in
  the receipt → status `no-claim`, `detail = "no-dataset-admitted"`; the same line on a `performance` gate →
  `no-claim-on-non-reality`, nothing written.
- `refuse_stack_dev`: a receipt with `stack_dev = true` → refused for a `pass` line and for a `fail` line.
- `refuse_dev_build_identity`: `build_identity = "dev-salt"` → the `pass` of a `performance` gate and of a `parity`
  gate refused with `dev-build-identity`, a `known-answer` gate recorded; under `depgraph-receipt` all three record.
- `receipt_committed_and_logged`: after a recording, `receipts/gates/<hash>.json` in the new commit is
  byte-identical to the harness receipt, and the bead log's `gate-record` line has `receipt` equal to the part's.
- `receipt_set_two_tiers`: a gate with an entry in `g1_known_answers` and one in `g4_chaos`, two receipts at one
  commit → a set file whose `members` are the two hashes in tier order, the part's `receipt` its hash, every
  member committed; one member `fail` → the part `fail`; two receipts of `g1_known_answers`, or two commits →
  `receipt-set-invalid`.
- `rerecord_keeps_rows`: a part recorded from G1 and G4 receipts and then from a newer G4 receipt alone →
  `part-rows-dropped` naming the G1 entries; from newer G1 and G4 receipts → the part replaced, the earlier
  receipts still under `receipts/gates/`.
- `mode_word_dispatch`: `record_gate -- frobnicate --gate GATE-X` exits non-zero with the usage text listing the
  modes and leaves `gates.toml` byte-identical; with no mode word the same arguments plus `--receipt` record. (The
  `reaffirm` mode and its test under the shared lock are N29bp1-01's, which adds it.)
- `measured_copied_from_receipt`: value "0.9207 (1)" with its unit, not the threshold sentence.
- `hook_refusal_stops_write`: a test hook registered in `CHECKS` that returns a harness reason makes the recorder
  exit 3 with `reason=<id>` and leaves `gates.toml`, the control history and the bead log byte-identical; with
  the hook list empty the same receipt records `pass` (the hooks of N38a-05, N38b-07, N21c-34, N32ax-03 and
  N38a-36 are tested in those beads).

### End-to-end script and logging

`scripts/e2e/status_accounting.sh` (bead N38b-21) drives the recorder from the user's side. This bead's script,
`scripts/e2e/record_gate.sh` (header: `bead=N38b-19 milestone=M0 labels=gauntlet,gate gates=GATE-GAUNT-10
plants=self-certify,missed-control,tampered-receipt`), works in a scratch clone of the repository under the run's
`work/` (the recorder commits, so it needs a repository of its own) and never in the checkout of record: it runs
a small tier filter, records its gate in the clone from a second session identity, then replays the three
plants, each of which must be refused with its reason; the committed `registries/gates.toml` of the checkout is
read only for its digest, logged at the start and the end, and must be unchanged. Step group `reaffirm-*` is
N29bp1-01's (its lines carry `bead=N29bp1-01`): on the clone's registry and logs it closes a fixture bead on the
recorded claim, tombstones one evidence object of the recorded gate and of that bead through BD-095's
test-support example, runs `cargo run -p frob-conformance --example record_gate -- reaffirm --registry <scratch
registry> --logs <scratch logs> --store <dir> --json`, and checks the demoted part, the appended line, the report
and a second run that changes nothing. Log at `target/e2e-logs/record_gate/<utc>.ndjson`: commands with exit codes and wall time, the receipt
hash and the digest of the clone's `gates.toml` before and after, the digest of the checkout's `gates.toml`, the
committed `receipts/gates/<hash>.json` of the recording, one `refusal` event per plant with the reason, the
evidence block of the recorded row, and the `summary`.

### Known answers and negative controls

Negative controls: the self-certifying session; the missed control; the omitted control; the tampered receipt;
the tombstoned evidence; the development-stack receipt; the `dev-salt` pass of a Performance gate; two receipts
of one tier; the re-recording that drops a row. Live-dependency proof: changing one measured value in a fresh receipt changes the
written `measured` and the regenerated README cell. Determinism: D0 apart from `date`; two recordings of one
receipt by one session are byte-identical.

## Considerations

- A bead closes only with a log line whose verdict is `pass`, whose claim identifiers resolve and whose
  recording session is not the implementing session (existing refusal FROB-REF-815 for a close without a
  resolving line from another session). A closed bead is not acceptance: acceptance is the gate's row.
- A close reason shared by several beads is a failure signal handled by the close audit (N38b-03).
- If the swarm runs with one session only, nothing can pass: that is the intended fail-closed behaviour.
- Performance: recording is file work; no budget concern.
