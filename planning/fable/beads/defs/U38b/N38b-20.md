## Background

FrankenRobotics keeps its acceptance state in one data file, `registries/gates.toml` (one record per gate, kill
gate and admission gate). Decision ADR-GAUNT-02 of the verification subsystem (the Gauntlet, crate
`frob-conformance`) says registries are data and documents are their printouts. Invariant INV-GAUNT-06 makes
that binding for status: status tables are generated from `registries/gates.toml` and never edited. Three views
are named: the README's *honest-status table*, the release rubric (the per-milestone statement of what a user
may be told they can use), and the dashboard's view of gates. A milestone exit is a query over the same file.

Reason: a hand-edited table drifts from the tests that are supposed to back it, and an optimistic README is the
cheapest form of false progress. Rejected alternatives: a status table maintained by the implementing sessions;
a dashboard with its own store of gate state (the dashboard has no private interface and issues read verbs only).

## Scope

In: the register of generated views (which file, which generator, which inputs); the content rules of the
README table; the gate section of the release rubric; the dashboard feed; the equality test; the planted
hand-edit. Out: the generator of the README file's other sections (BD-002); the printed gate register and the
exit query (`needs`); the printed known-answer suite (N38a-12); the recorder that changes the file (N38b-19).

## Technical approach

**Generated views (`crates/frob-conformance/registry/generated.toml`; DESIGN).**

| View | Output | Inputs | Generator |
|---|---|---|---|
| README honest-status table | The block between `<!-- gates:begin -->` and `<!-- gates:end -->` of `README.md` | `registries/gates.toml` | `register::print::readme_table` |
| Release rubric, gate section | `docs/release/STATUS.md` | `registries/gates.toml`, `registries/milestones.toml` | `register::print::rubric` |
| Dashboard feed | The `gates` array of `frob capabilities --json` | `registries/gates.toml` (embedded at build time) | `register::print::capabilities_json` |
| Printed counterexample catalogue | `docs/registers/COUNTEREXAMPLES.md` | `registry/counterexamples.toml` | `catalogue::print` |
| Printed control registry | `docs/registers/CONTROLS.md` | `registry/controls.toml`, `registry/control_history.ndjson` | `controls::print` |

Each generator is a pure function of its input bytes (determinism class D0), lives in a module that depends
only on `frob-core`, and is callable by `xtask check-generated` without linking the conformance crate.

**README table: one row per gate, in file order.**

| Column | Content |
|---|---|
| Gate | Identifier; a kill gate is marked ✖ |
| Claim | One of the seven kinds |
| Milestone | Earliest milestone; parts listed where a gate closes in parts |
| Status | "not run"; "pass"; "FAIL"; "killed: fallback adopted (<fallback name>)"; "blocked: OPEN-…"; "no-claim"; "superseded by <gate>" |
| Measured | The measured value with unit and interval, or the count; empty when not run. Never the target |
| Controls | "<caught> of <registered> caught" from the cited run; "none registered" in bold when empty |
| Recorded | Date and recording session; receipt hash prefix |

Rules: a failing gate appears as failing; a capability that fell back appears under the fallback's name; a
`not-run` gate is never rendered with a mark that could be read as success; a `no-claim` on a Reality gate is
printed as the state, not as a pass; the word "verified" appears nowhere. A footer prints the totals per status
and the count of gates with no registered control.

**Release rubric, gate section.** For each milestone M0 to M8: the gates due there with their statuses, the
kill decisions with their fallbacks, and the three sentences of the rubric row (what a user can do, what must be
true before release, what must not be said) copied from `registries/milestones.toml`. A release path's demo file
may cite only claims that exist in `gates.toml` (checked by the delivery unit's contract check).

**Dashboard feed.** The dashboard reads gates only through `capabilities` (read verb). The feed carries, per
gate: `id`, `claim`, `milestone`, `status`, `measured`, `controls_caught`, `controls_total`, `fallback`. The
pane table of the dashboard design lists no gate pane; DESIGN: the gate list is a section of its Evidence pane.

**Cross-check, not a second source.** The generator also verifies that every `pass` row has a resolving line in
its bead's log (`docs/delivery/logs/<bead>.ndjson`, verdict `pass`, recorded by another session); a missing line
fails generation. The log contributes no cell: content comes from `gates.toml` only.

**Equality test (GATE-GAUNT-10, clause 1; `tests/status_views.rs`).** Regenerate every view in memory and
compare with the committed bytes; print the first differing line. `xtask check-generated` runs the same
comparison in the six-check suite.

## Acceptance criteria

- [ ] The README block equals a fresh generation from `gates.toml`, byte for byte (GATE-GAUNT-10, clause 1).
- [ ] A hand edit of one status cell, of one measured value, or of the totals footer fails `tests/status_views`
      and `xtask check-generated`, naming the line.
- [ ] A `fail` row prints "FAIL"; a `killed` row prints the fallback's name; a `not-run` row prints "not run".
- [ ] A `pass` row without a resolving bead-log line fails generation.
- [ ] `frob capabilities --json` carries the `gates` array and it equals the file's content.
- [ ] No generated view contains the word "verified"; no view names a capability more broadly than its gate.
- [ ] Every generator's module compiles with `frob-core` as its only workspace dependency.

## Test plan

### Unit tests

`crates/frob-conformance/tests/status_views.rs` (fixtures labelled `synthetic`):
- `readme_table_golden`: a fixture file of seven gates, one per status, renders to the committed golden block.
- `fail_is_printed_as_fail`, `fallback_named`, `not_run_never_marked_passed`, `no_claim_is_not_pass`.
- `controls_cell_counts`: 2 of 2 caught; "none registered" for an empty list.
- `footer_totals`: totals equal the counts by status.
- `hand_edit_detected`: change "not run" to "pass" in the committed block → mismatch at that line.
- `pass_without_log_line_fails_generation`.
- `capabilities_feed_equals_file`.
- `generation_is_pure`: two generations give identical bytes; reordering rows in the file reorders rows only.
- `no_forbidden_words`: "verified" absent.

### End-to-end script and logging

`scripts/e2e/status_accounting.sh` (bead N38b-21) measures the gate. This bead adds
`scripts/e2e/status_views.sh` (header: `bead=N38b-20 milestone=M0 labels=gauntlet,registry gates=GATE-GAUNT-10
plants=edit-readme-cell`): regenerate, compare, run `cargo xtask check-generated`, run `frob capabilities
--json` and compare its `gates` array with the file, then plant a hand-edited cell and expect both checks to
fail. Log at `target/e2e-logs/status_views/<utc>.ndjson`: commands with exit codes and wall time, digests of
each generated view and of `gates.toml`, the first differing line on the plant, and the `summary`.

### Known answers and negative controls

Known answer: the golden block for the seven-status fixture. Negative controls: the hand-edited cell; a
generator fed a second input file (must not change output); a `pass` row with no log line. Metamorphic relation:
recording one more gate changes exactly one row and the footer. Determinism: D0 on both platforms.

## Considerations

- Two passages of the design name different inputs for the table (the gate file alone; the gate file and the
  per-bead logs). This bead resolves it: one content source, one cross-check.
- The README's remaining sections are the companion-documents bead's; only the marked block is generated here.
- The printed gate register is generated by the gate-register unit from the same file; both generators share
  the row printer.
- Honest status includes results that went against the design: a release ships at least one such result with
  its commands, addresses and seeds.
