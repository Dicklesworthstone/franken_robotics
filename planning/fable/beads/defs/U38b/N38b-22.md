## Background

The verification subsystem of FrankenRobotics (the Gauntlet, crate `frob-conformance`) states seven invariants
and three proof obligations about itself. They are the properties that keep the harness from certifying its
own output: fixtures are never regenerated from the candidate; a pass needs a caught control and a different
recording session; agreement with an oracle is never called Reality; stand-in evidence is labelled; status
tables are generated; identifiers are never reused. Each is enforced inside the mechanism it constrains. This
bead gathers all ten into one suite that runs on every change, each with a planted violation, so that none can
lapse unnoticed, and it implements the two that no other bead owns in full: the append-only check of
identifiers on a registry diff (INV-GAUNT-07) and the suite-level binding of the seed-completeness join
(PO-GAUNT-03).

## Scope

In: the table of ten with statement, check, planted violation and owning bead; the suite target; the registry
diff tool. Out: the mechanisms themselves (owning beads).

## Technical approach

**The ten identifiers.**

| Identifier | Statement | How it is checked | Planted violation that must be caught | Mechanism |
|---|---|---|---|---|
| INV-GAUNT-01 | No fixture is regenerated from the candidate | Fixtures are written only by scripts under `tools/oracle/` whose inputs exclude the workspace's build products; CI fails on a fixture changed without a pin record | A fixture file rewritten from the candidate's own output with its header kept | N38a-04 |
| INV-GAUNT-02 | Every gate that records PASS has at least one registered control that was caught in the same run | Schema check on `gates.toml`; the recorder refuses to write `pass` otherwise | A pass row with an empty control list; a pass whose receipt shows the control missed | BD-025, N38b-19 |
| INV-GAUNT-03 | Agreement with an oracle is recorded with claim kind `parity` | The record type of a tier-G2 result has no constructor for another kind | A hand-written G2 result offered as `reality` | N38a-05 |
| INV-GAUNT-04 | Evidence computed from a fixture, a stand-in or the development oracle is labelled `synthetic` or `development-oracle` | The label is a flag propagated through the claim product; an unlabeled record is refused | A record whose inputs are synthetic and whose evidence block lacks the label | N38b-07, N38a-06 |
| INV-GAUNT-05 | A PASS is recorded by a session that did not implement the capability | Session identities in the record; the recorder refuses a recording session that is a member of the implementing set | A self-certifying session; a co-implementer recording | N38b-19 |
| INV-GAUNT-06 | Status tables are generated from `registries/gates.toml` and never edited | The generated-file check and the equality test of the views | A hand-edited README cell | N38b-20 |
| INV-GAUNT-07 | KA, CX and control numbers are append-only | A registry diff that reuses or renumbers an identifier fails CI | A renumbered KA row; a CX number reused for a new case; a deleted control | This bead |
| PO-GAUNT-01 | The paired lower bound of the harness is exact on constructed inputs | Ten pairs of constant ratio r return r; an A/A campaign does not clear 1.02 | A ratio-of-means harness | N38a-08 |
| PO-GAUNT-02 | Every metamorphic relation is broken by its registered mutation | The mutation is applied in a test build and the relation's test must fail | A no-op mutation | N38a-14 |
| PO-GAUNT-03 | The registry seed is complete: every CX entry and every stated negative control of the known-answer suite maps to a control with at least one gate | A join over the three registries with no unmatched row | A catalogue entry removed from the seed map | N38b-05 |

**Registry diff tool (INV-GAUNT-07; `crates/frob-conformance/tests/registry_diff.rs` and
`src/registry_diff.rs`).**
1. Inputs: the registry files at the merge base (`FROB_DIFF_BASE`, default the parent commit) and at `HEAD`:
   `known_answers.toml`, `counterexamples.toml`, `controls.toml`, `relations.toml`, `certifiers.toml`,
   `registries/gates.toml`.
2. For every record compute a *content fingerprint*: the BLAKE3 hash of its immutable fields (for a known
   answer: section, fixture and case; for a counterexample: shortcut and defined-in; for a control: seed, kind
   and target; for a relation: statement; for a gate: section and kind).
3. Findings: `removed` (an identifier present at the base and absent at HEAD); `reused` (same identifier,
   different fingerprint); `renumbered` (same fingerprint under a different identifier, with the old one
   gone); `out-of-order` (a new identifier not greater than every existing one of its family); `gap`.
   For the KA and CX families the last two read the allocation ledger
   (`crates/frob-conformance/registry/allocations.toml`, N38a-40), because blocks issued to different chapters
   fill at different milestones: a new identifier inside a block issued to its row's owner is in order even
   when a higher number of a later block already exists, and a hole inside a block whose status is `reserved`
   or `filling` is not a `gap`. A new identifier above the plan-time maximum and inside no block is
   `out-of-order` here as well as `unallocated-number` in N38a-40's single-tree check; the two checks must agree
   on every number.
4. Allowed changes: appending records; changing mutable fields (a tolerance being set, a control being
   registered, a status, `last_seen`, a derivation path); tombstoning with an explicit `retired = true` and a
   reason, which keeps the identifier in the file; and the one change of a control's `target` that the seeding
   tool makes (N38b-05 step 2): from its placeholder (the plant's identifier `<bead>:<name>`, or the CX number
   of an entry with no plant, recognised by its form) to the target the chapter states. The base fingerprint is
   then recomputed with the new target; a change of a target that is no longer a placeholder is `reused`.
5. Any finding fails the test and prints the identifier, the kind of finding and both versions.

**Suite target (`tests/invariants.rs`).** One test per row named `inv_gaunt_0N_…` or `po_gaunt_0N_…`. Each runs
the real check on the clean tree (must pass) and on its planted violation in a scratch copy (must fail with
the expected reason). Rows whose mechanism lands at a later milestone (PO-GAUNT-01 at M1, PO-GAUNT-02 at M2)
are registered now and report `not-due` until then; they are never reported as passing early.

## Acceptance criteria

- [ ] Ten tests exist, named by identifier; eight pass with their plants caught at M0, and the two later ones
      report `not-due` and then pass at M1 and M2.
- [ ] The registry diff catches a removed, a reused, a renumbered and an out-of-order identifier in each of the
      six registries, and accepts an append and a tombstone.
- [ ] The suite runs on every change inside the per-change budget (seconds; file work only).
- [ ] Each planted violation is registered as a negative control of the gate that owns the invariant.

## Test plan

### Unit tests

`crates/frob-conformance/tests/registry_diff.rs`:
- `append_is_allowed`: KA-836 added after KA-835, inside a block issued to its chapter in the scratch
  `allocations.toml` (without the block it is `out-of-order`, step 3).
- `placeholder_target_set_once`: a control whose `target` moves from its placeholder `SPEC-C-01:cx-019` to a
  code path gives no finding; a second change of that target gives `reused`.
- `removed_detected`: KA-500 deleted.
- `reused_detected`: KA-501's case replaced by a different case.
- `renumbered_detected`: KA-501 moved to KA-900 with identical content.
- `out_of_order_detected`: CX-200b or CX-150 inserted as "new".
- `allocated_blocks_fill_in_any_order`: with blocks KA-850..=867 (`reserved`) and KA-868..=869 (`filling`)
  issued, a commit adding KA-868 before any of 850 to 867 gives no finding; a later commit adding KA-850 gives
  no `out-of-order`; a commit adding KA-870 with no block gives `out-of-order`.
- `mutable_fields_allowed`: tolerance `to-set` → `abs 0.1`; `last_seen` updated.
- `tombstone_allowed`: `retired = true` with a reason keeps the row.
- `fingerprint_stable`: whitespace and key order do not change a fingerprint.
`tests/invariants.rs`: the ten rows as described.

### End-to-end script and logging

`scripts/e2e/gauntlet_invariants.sh` (header: `bead=N38b-22 milestone=M0 labels=gauntlet
gates=GATE-GAUNT-01,GATE-GAUNT-05,GATE-GAUNT-10 plants=one-per-invariant`). It runs the suite, then applies
each plant in a scratch clone and re-runs the matching check, expecting a failure with the stated reason. Log at
`target/e2e-logs/gauntlet_invariants/<utc>.ndjson`: commands with exit codes and wall time; one `assert` per
identifier for the clean run and one per plant (`kind: negative-control`, `caught`); for the diff tool the
identifier and finding kind; counts as `metric` lines (invariants checked 10, plants caught against the number
due); the `summary`.

### Known answers and negative controls

Negative controls: the ten plants of the table. Metamorphic relation: reformatting a registry file (key order,
whitespace) produces no finding. Determinism: D0; identical output on both platforms.

## Considerations

- The diff base matters: on a rewritten history the tool compares with the last recorded registry digest in
  the ledger as well, so that a force-push cannot erase an identifier unseen.
- Identifier families grow (certifier and anchor identifiers were added by this design); a new family is added
  to the tool with its fingerprint rule.
- The suite duplicates no logic: each row calls the owning mechanism's check; only the diff tool is new code.
