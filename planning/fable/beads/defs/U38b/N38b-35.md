## Background

FrankenRobotics uses foreign tools only as comparison instruments: they run out of process, under a pin, on
fixtures captured by script, and are never dependencies or baselines of record (decision ADR-GAUNT-04 of the
verification subsystem, the Gauntlet). Two uses need a choice that the design leaves open as OPEN-GAUNT-4:

1. **The development oracle**: one incumbent simulator at a pinned release, used for paper-scale pilots that
   must run before the program's own trusted CPU tier (the referee) exists. Every result from it is labelled
   `development-oracle`, funds or kills a work package, supports no gate, and is re-run on the referee later.
2. **The comparator set**: the incumbent batched simulators (a CPU engine, its GPU ports, and the learning
   stacks built on them) at exact releases and container digests, frozen in
   `crates/frob-conformance/registry/comparators.toml`, used for throughput and training-time parity, as
   context for mixed batches, and as the rival arms of the ten-fold test.

The question: **which incumbent release is the development oracle, and which releases and container digests
form the comparator set.**

**The second half is one decision with OPEN-PERF-2.** The performance program asks the same thing as its own
open question OPEN-PERF-2 ("which incumbent revisions and configurations are the comparators"). There is one
comparator set, so there is one decision record for it: the ADR of bead N36-25, filed under both identifiers,
with its rows in the one registry file that the incumbent harness bead BD-039 defines. This bead decides the
first half, the development oracle, and closes OPEN-GAUNT-4 by citing that ADR for the second half.

- Owner: the rival audit (the study that measures the incumbents before any mechanism is funded against them).
- Blocks: GATE-GAUNT-05 (oracle hygiene: every fixture has a pin, a date and a capture script); every pilot
  that needs dynamics before M1.
- Fail-closed default: no development oracle; those pilots wait for the CPU referee. For comparators: the
  revisions in the source register, frozen before any paired run; an arm with no frozen comparator reports
  `not run`.

Reason the pin matters: a comparator pin does not move between the freeze and the end of the study that uses
it, and a moved pin voids the runs it spans; an unpinned oracle makes every fixture irreproducible.

## Scope

In: the decision packet for the development oracle; the selection rules for it; its record in
`registry/oracles.toml`; its default; the closing record of OPEN-GAUNT-4, which holds the development-oracle
decision and a reference to the comparator-set ADR.

Out, with the bead that has it:
- The comparator-set decision (which releases, commits, container digests and configurations; the selection
  rule that each comparison gets the strongest composed rival in its strongest warm configuration; the freeze
  and change rules; the default of unfrozen source-register rows; the ADR): N36-25. This bead depends on it
  and writes nothing into `comparators.toml`.
- The file `crates/frob-conformance/registry/comparators.toml`, its row schema, the loader that rejects a
  floating tag and the check on pin moves after a freeze: BD-039. The incumbent harness and the measurements
  taken with it: BD-039, BD-040.
- The oracle register and the `[[pin_move]]` record: N38a-04. The development-oracle lane's mechanics
  (N38a-06); the kill gate on it (N38b-24).

## Technical approach

**Decision packet (`docs/decisions/OPEN-GAUNT-4.md`).** For each candidate for the development oracle: the exact
release tag and commit; the container image digest (or the lockfile digest of its environment); the licence;
which reference robots and tasks it runs unmodified; whether it runs in double precision on the CPU (needed
because its pilots stand in for runs on the CPU referee, which is double precision; the oracle has no parity
role, only `pilot`, N38a-06); the host and device it was audited on; known defects relevant to the
pilots. For the comparator set the packet holds one line: a pointer to `docs/decisions/OPEN-PERF-2.md` (N36-25),
which carries the same facts for every comparator together with each one's strongest warm configuration.

**Selection rules (DESIGN; fixed before the choice).**
1. The development oracle is a CPU, double-precision engine with a stable release, chosen for being the
   reference its own ecosystem trusts, not for speed. Exactly one is chosen.
2. (The rule for the comparator set, that each comparison gets the strongest composed rival at a pinned
   version in its strongest warm configuration, is applied by N36-25 and is stated there.)
3. The development oracle is admitted like a dependency: a pin, an admission test (it reproduces its own
   published or documented figure on the audit host within the stated tolerance) and a negative control (a
   deliberately wrong pin is detected by digest). N36-25 applies the same rule to each comparator.
4. Nothing chosen is linked into any production binary; the dependency firewall checks it.

**Record written on decision.**
```toml
# registry/oracles.toml
[[oracle]]
id = "development-oracle"; posture = "out-of-process"
pin = { kind = "release", value = "<tag>", commit = "<sha>", sha256 = "<container or lockfile digest>" }
admission = { test = "…", control = "NC-…", status = "not-admitted", date = "" }
roles = ["pilot"]; held_out = ""
tool = "<name>"; label = "development-oracle"; decided = "<date>"; decision = "ADR-…"
```
DESIGN: this is the `[[oracle]]` record of the oracle register (N38a-04: `id`, `posture`, `pin`, `admission`,
`roles`, `held_out`), not a second shape. The release tag and the digest sit in `pin` (`value`, `sha256`), the
commit is added to `pin` as `commit`, and the decision adds four fields the register allows on this row: `tool`,
`label`, `decided`, `decision`. The first draft's flat `release`, `commit` and `digest` fields are these. The
row's only role is `pilot`; its admission test and its lane are N38a-06's.
No comparator record is written here. The comparator rows live in
`crates/frob-conformance/registry/comparators.toml` under BD-039's schema (`name`, `role`, `release`,
`source_revision`, `container_digest`, `configurations`, `uses`, `frozen_at`, `frozen_for`, `state`,
`reference`, and the rest), and their decision fields are written by N36-25. DESIGN (correction of this bead's
first draft, which sketched a second record shape with `id`, `commit`, `digest`, `config`, `frozen`, `study` and
a `role` list of uses): those are BD-039's `name`, `source_revision`, `container_digest`, `configurations`,
`frozen_at`, `frozen_for` and `uses`; a row this draft called `provisional` is `state = "default"` with an
empty `frozen_at`. Reason: one file must have one schema, and the seed's harness identity is keyed on its names.

**Closing record of OPEN-GAUNT-4** (in the packet and as the ADR `docs/adr/ADR-OPEN-GAUNT-4.md`, in the one
directory for decision records): the development-oracle decision (or its default) and `comparator_set = "<ADR of
N36-25>"`. The question is closed when both are on record. The row OPEN-GAUNT-4 of `registries/open.toml`
(N41-OPEN8) then moves to `decided` with `adr` naming the record, or to `defaulted` if the development-oracle
half is defaulted at the M0 exit (N41-03); a row left `open` past its M0 deadline blocks the M0 exit.

**Default if undecided at the M0 exit.** `oracles.toml` has no development-oracle record; the funding rule
treats pilots that need dynamics as waiting. The default is recorded as a decision. (The comparator half has its
own default, held by N36-25: the source-register revisions as unfrozen rows, `state = "default"` with an empty
`frozen_at`, and every paired run against them refused until they are frozen.)

## Acceptance criteria

- [ ] The packet lists every candidate with release, commit, digest, licence and audit host.
- [ ] Either one development-oracle record exists with all fields, or the default is recorded and the funding
      rule reports the waiting pilots.
- [ ] The development-oracle record has an exact release, a commit and a digest; a record with a floating tag
      ("latest", a branch name) is rejected by the oracle register's loader.
- [ ] The closing record cites the comparator-set ADR of N36-25 by identifier; this bead has written no row and
      no field into `comparators.toml`. (That every comparator row has an exact release, a commit, a digest, a
      configuration and a freeze date, and that a pin changed after its freeze date without a new record fails
      CI, are acceptance lines of N36-25 and BD-039.)
- [ ] The register row OPEN-GAUNT-4 names `docs/adr/ADR-OPEN-GAUNT-4.md`, with status `decided`, or `defaulted`
      if the default holds.
- [ ] The development-oracle pin changed after `decided` without a `[[pin_move]]` record fails CI.
- [ ] No chosen tool appears in any production dependency graph.
- [ ] GATE-GAUNT-05's fixture clause can be evaluated: every fixture captured from a chosen tool carries that
      tool's pin, a date and a capture script.

## Test plan

### Unit tests

`crates/frob-conformance/tests/open_questions.rs`: `development_oracle_needs_exact_pin` (tag `main` rejected; a
40-hex commit with a digest accepted); `development_oracle_wrong_digest_detected` (a record whose `pin.sha256`
differs by one hex digit from the digest of the pulled image's manifest is rejected, the matching one accepted);
`one_development_oracle_at_most`; `development_oracle_pin_move_detected`;
`default_makes_dynamics_pilots_wait`; `closing_record_cites_comparator_adr` (a closing record with an empty
`comparator_set` is rejected). The comparator tests of the first draft are run where the rows are:
`floating_reference_refused` and `frozen_pin_cannot_move` in BD-039, `unfrozen_comparator_refuses_pairing` and
`pin_move_after_freeze_detected` in N36-25.

### End-to-end script and logging

The fixture clauses of GATE-GAUNT-05 are run by the oracle-register and oracle-hygiene scripts (N38a-04,
N38a-05), the comparator pins by the incumbent harness's script (`perf_parity_baseline.sh`, N36-29); none of them
checks this decision's own record, so this bead adds `scripts/e2e/open_gaunt_4.sh` (header: `bead=N38b-35
milestone=M0 labels=gauntlet,oracle,decision gates=GATE-GAUNT-05
plants=floating-tag,second-oracle,unrecorded-pin-move,empty-comparator-set`; sources the STD-E2E helper; works
on a scratch copy of `registry/oracles.toml` and of the packet). Steps: (1) `record`: in the scratch tree, `cargo
test -p frob-conformance --test oracle_register` (N38a-04's loader, which reads `registry/oracles.toml`; there is
no `frob conformance` verb) and `cargo test -p frob-conformance --test open_questions -- development_oracle`;
one `assert` that either exactly one `development-oracle` row exists with `pin.value`
an exact release, `pin.commit` 40 hex digits and `pin.sha256`, or the default is on record as a decision; when
the default holds, one `metric` `pilots_waiting` (unit `pilots`) from the funding rule's report (`cargo run -p
frob-conformance --example pilots -- fundable --all --json`, N38a-09); (2) `closing`:
the closing record of OPEN-GAUNT-4 is read and its `comparator_set` is asserted to equal the ADR identifier of
N36-25, and the register row OPEN-GAUNT-4 asserted to name that record with status `decided` or `defaulted`;
`git diff --stat` over `comparators.toml` for this bead's commits is asserted empty; (3) `firewall`: the
production dependency graph (`cargo tree -e normal` per production binary) is asserted to contain no chosen tool;
(4) plants, each with `e2e_expect_refusal` naming the loader's rejection: a floating tag (`main`) on the record;
a second `development-oracle` row; the pin moved after `decided` with no `[[pin_move]]` record; a closing record
with an empty `comparator_set`. Log at `target/e2e-logs/open_gaunt_4/<utc>.ndjson` with the transcript; every
line has `ts`, `script`, `bead`, `step`, `event`; `cmd` lines the exact command, exit code and wall time; the
record's pin and the registry digest as `digest` lines; failed assertions the first differing field with observed
and expected values and the scratch paths; the `summary` the decision identifier, the counts and GATE-GAUNT-05.

### Known answers and negative controls

Negative controls: a floating tag on the development-oracle record; a digest that does not match the pulled
image; a second development oracle; the development-oracle pin moved after the decision with no record. Determinism: not applicable (a recorded decision); the loader checks are D0.

## Considerations

- If the development oracle is chosen and later two or more of the first five pilots reverse on the referee,
  its results lose standing as funding evidence (N38b-24).
- An incumbent that has itself been compared with hardware gives no Reality: agreement with it is Parity.
- Licences of incumbent tools and assets are recorded with the pins; a tool whose licence forbids the intended
  use is not chosen.
- The denominator of the ten-fold ratio depends on these pins; the risk that incumbents are faster or their
  loop shorter than assumed is addressed by measuring them first, at M0.
