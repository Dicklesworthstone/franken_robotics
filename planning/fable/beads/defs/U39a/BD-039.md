## Background

FrankenRobotics claims that the time from a robot-design question to an independently accepted answer is ten
times shorter than with the strongest composed rival. The rival is built from incumbent simulators and learning
stacks. A hygiene rule of the program says: **the incumbent is measured before a mechanism is funded against
it**. Versions are pinned, the strongest warm configuration is recorded, and the phase ledger of the incumbent
loop is taken on the program's Linux host `trj` (two RTX 4090 with 24 GB each and no link between them) before
any ratio is written. The reason is that no end-to-end phase ledger of an agent-driven design loop on the current
incumbent stacks has been published (FACT about the sources read), and a ratio without a measured denominator is
not a ratio. The program's risk register names the failure this prevents: the denominator of the ten-fold ratio
is wrong, because incumbents are faster, or their loop is shorter, than a composite of published figures.

This bead builds the instrument for that measurement: a harness that installs, pins and launches the incumbents
**out of process**. DESIGN (ADR-GAUNT-04): foreign tools are comparison instruments, never dependencies and never
baselines of record; they run out of process, under a pin, on fixtures captured by script. Reasons: the
foundation library's adapter rule, and the finding that agreement with an oracle is Parity and never Reality.
Rejected: linking an incumbent as a library (it would enter the product's dependency graph and its licence);
quoting published figures instead of measuring (they come from different stacks and hardware; absolute
throughput on an RTX 4090 was not found in the sources, whose figures are for other cards).

The first use is the **rival audit** of the parity-baseline gate GATE-TENFOLD-01 at M0: pin every incumbent by
revision, record what each one documents that it can do, and freeze a warm configuration for each after tuning
on reference tasks only. The same pins later serve the rival arms of the ten-fold test, the incumbent arms of
the mixed-batch head-to-head experiment, the proxy-adequacy pilot of the scene chapter, and the neutral
adjudicating simulator.

## Scope

In: the comparator registry; recorded environments; the launcher; the harness identity; warm-configuration
records with their tuning logs; the disclosure-block capture for incumbent runs; the licence record; pin-move
records. Out: the timed measurements (seeds BD-040 on `trj`, BD-142 on the Mac, BD-143 for the agent-driven
loop); phase tagging of launched processes (N39a-25); the capability register's content; composing arm B for a
stratum (N39a-20).

## Technical approach

**1. Candidates (FACT about the releases read for the plan; each is re-read and re-pinned by revision here).**
MuJoCo and MuJoCo Warp 4.0.1 (with the MuJoCo Playground and mjlab training stacks), Newton 1.8.0, Isaac Lab
3.0.0 (on Newton or PhysX), Genesis 1.4.7, Drake 1.58.0, ManiSkill 3.0.1. Published context to be re-measured:
about 2.55 million humanoid world-steps per second for one stack on an RTX 6000 Ada; a flat-ground quadruped
policy trained in about 410 s on one RTX 4090 and about 325 s on two, with a compile region of about 45 s inside
those times.

**2. Comparator registry (`crates/frob-conformance/registry/comparators.toml`).**
```toml
[[comparator]]
name = "…"; role = "engine" | "learner" | "stack" | "solver" | "adjudicator-candidate"
release = "…"; source_revision = "<commit>"; container_digest = "sha256:…"
runtime = { python = "…", cuda = "…", driver = "…" }
licence = { spdx = "…", permits_publishing_comparison = "yes" | "no" | "unknown", source = "…", read_at = "…" }
recipe = "b3:…"; lock = "b3:…"; warm_config = "b3:…"; capabilities = ["<register row ids>"]
pinned_at = "…"; pinned_by = "…"
```
A row with a release tag but no commit and no container digest is refused by the loader.

**3. Recorded environments (`tools/oracle/incumbents/<name>/`).** `recipe` (base image by digest, system
packages by version), `lock` (every package with its hash), `build.sh`, `run.sh`, `smoke.sh`. An environment is
built once on `trj`, stored by container digest, and run with no network. `frob-tenfold incumbent build <name>`
records the digest; a rebuild that yields a different digest is a new pin.

**4. The launcher (`frob-tenfold incumbent run <name> --config <hash> -- <task args>`).** Numbered behaviour:
(1) resolve the registry row; (2) verify the container digest and the warm configuration's hash, refusing on a
mismatch; (3) apply the device, core and memory limits of the request; (4) start the container out of process
with the task; (5) capture standard output and error, exit status and wall time; (6) write a run record with the
harness identity, the host's hardware fingerprint digest, the host load at start, and the disclosure block.
No product crate links, imports or vendors any incumbent package; the workspace dependency check must stay
green with this bead's code present.

**5. The harness identity.** `harness_id = BLAKE3(canonical(sorted comparator rows) ‖ launcher source hash ‖
recipe and lock hashes)`. It appears on every run record. **A changed revision changes the harness identity**:
moving any pin, rebuilding any environment or changing any warm configuration yields a new identity, and
measurements under different identities are never pooled. Moving a pin is a deliberate event with its own
record (`pin-move`: old and new values, reason, who, when); a comparator pin does not move between an arm's
freeze and the end of the study that uses it.

**6. Strongest warm configurations.** For each incumbent, a configuration record chosen after tuning on
**reference tasks only** (the incumbent's own home tasks, for example a flat-ground quadruped velocity task and a
humanoid task; never a mission of the ten-fold suite):
`{world_count, time_step, substeps, control_decimation, solver: {iterations, tolerance}, contact_capacity,
precision, compile_cache: "warm", graph_capture, learner: {recipe, hyperparameters}, selection: "shortest time
to the task's return threshold" | "highest throughput at matched settings", tuning_log: "b3:…"}`.
"Warm" means caches populated (kernels compiled and cached on disk, shaders cached); cold start is measured
separately. The tuning log lists every run with its settings, device-seconds and result, so the choice is
auditable.

**7. The disclosure block on every figure.** Any Performance figure produced through the harness carries:
hardware and driver; backend, compiler and kernel versions; world count; time step, substeps and control
decimation; solver iterations and tolerance; contact capacity and mean active contacts per world; sensors
enabled; whether the policy and learning are included; scene; determinism class; warm-up and duration; whether
launch graphs were captured; median and 99th-percentile step time; peak memory; the unit of every rate with its
decimation; cold or warm with compile times and cache state; thermal state and host load; the comparator's
revision and configuration; energy where a credible meter exists and a named gap where it does not. A figure
without the complete block is refused as a Performance claim (FROB-REF-862).

**8. Capability and licence records.** Each registry row links to the rows of the incumbent capability register
(what the incumbent *documents* it can do, with the source and pin: per-world model parameters in one batch,
state-preserving model edits, opt-in run-to-run determinism, mixed topologies in one batch, electrical and
thermal actuator models, sampling control without training, interior generators, agent access over MCP). The
licence record states whether publishing a comparison is permitted. Default while the owner's decision is open:
revisions and fetch instructions only are distributed; an incumbent whose licence forbids publication is replaced
by the next strongest, and the replacement is printed.

## Acceptance criteria

- [ ] Seed done-condition: the pinned incumbents run on `trj` from a recorded environment (each `smoke.sh` passes
      from its stored container digest with the network disabled), and a changed revision changes the harness
      identity.
- [ ] Every candidate has a registry row with a commit, a container digest, a licence record and a warm
      configuration with its tuning log; rows without a commit or digest are refused.
- [ ] A launch with a mismatching digest or configuration hash is refused before the container starts.
- [ ] Every run record carries the harness identity, the fingerprint digest, host load and a complete disclosure
      block; a planted record with one field removed is refused.
- [ ] No incumbent package appears in any manifest or lockfile of the workspace.
- [ ] The rival-audit part of GATE-TENFOLD-01 is recordable: every incumbent pinned with its capability rows and
      licence, warm configurations frozen (the timed rows are the parity-baseline bead's).

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- incumbent::`
- `identity_changes_with_revision`: changing one row's `source_revision` changes `harness_id`; reordering rows
  does not.
- `identity_changes_with_warm_config`.
- `registry_requires_pin`: a row with only a release tag → refused.
- `digest_mismatch_refused`: launcher with a wrong digest → refusal before start.
- `disclosure_complete`: a block with every field → accepted; each single-field deletion → refused.
- `pin_move_record_required`: a registry diff with no `pin-move` record → the check fails.
- `no_foreign_dependency`: the workspace metadata contains no package from the candidate list.

### End-to-end script and logging

`scripts/e2e/incumbent_harness.sh` (header: `bead=BD-039 milestone=M0 gates=GATE-TENFOLD-01 needs=cuda`; skips
with code 77 off `trj`). Steps: print the registry and the harness identity; for each pinned incumbent run its
smoke task (a ten-second batched step of its home robot) from the stored environment with the network disabled;
verify the run record's disclosure block; copy the registry to the scratch directory, change one revision and
assert that the identity changes; attempt a launch with a planted digest and assert the refusal. Logs per line:
the command, exit code, wall time, comparator name and pin, container digest, harness identity, host load, the
disclosure block's digest, each refusal, and a summary naming GATE-TENFOLD-01 as touched (not passed: the timed
rows belong to the parity baseline). Throughput numbers printed by smoke tasks are logged as metrics without
thresholds.

### Known answers and negative controls

Known answers: none of physics; the harness's own invariants (identity is a function of the pins). Published
figures the later measurements must reproduce within 20% or explain in writing: about 410 s (one RTX 4090) and
about 325 s (two) to train the flat-ground quadruped policy; a compile region of about 45 s. Negative controls:
an incumbent run from a mutable environment (an unpinned package upgrade changes the digest; the launcher
refuses); a figure with its decimation omitted (the disclosure check refuses); a silent pin move (the identity
changes and the pin-move check fails); an incumbent imported into a product crate (the dependency check fails).
Determinism: registry hashing is D0; incumbent runs are measurements under the incumbent's own determinism
settings, which the disclosure block records.

## Considerations

- OPEN (project lead): licences; blocks GATE-TENFOLD-01; default as stated. OPEN: which revisions are the
  comparators; default the revisions read for the plan, frozen here.
- Compute: smoke tasks fit the default envelope (one device, one hour, 8 cores, 16 GiB). The parity
  measurements on both cards and all cores need the owner's approval of the gate-measurement class; without it
  only single-card, eight-core rows are recorded and the others are `not run`.
- `trj` is often heavily loaded (FACT); the harness records load and does not wait for quiet.
- Incumbent environments are large (tens of gigabytes each); they are stored by digest outside the repository.
- The harness never treats an incumbent's output as truth: agreement with it is Parity.
- Revisit when an incumbent ships a major release during the program: a new pin is a new identity and the M7
  tournament refreshes the audit before its freeze.
