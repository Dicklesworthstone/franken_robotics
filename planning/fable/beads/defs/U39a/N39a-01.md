## Background

FrankenRobotics is a robotics simulation and design system whose central claim is comparative: the wall-clock time
from a robot-design question to an *independently accepted answer* is ten times shorter than with the strongest
composed rival. The "ten-fold test" is the protocol that confirms that claim, reports it as something smaller, or
withdraws it. Nothing in the protocol is a result: every threshold is a DESIGN choice or a TARGET, and every figure
about an incumbent is a FACT about its source that is re-read before a gate cites it. The claim under test is the
program's bet BET-13 (ten-fold on the sealed suite, on at least one named stratum), and the tie rule is BET-14
(the mechanisms need this engine). The test is the only evidence the program accepts for either. Engine
throughput is a parity requirement with its own gates; it is an input to this test and never a substitute for it.

The test needs a measuring instrument that is not the product. That instrument, the **ten-fold harness**, lives in
the verification crate `frob-conformance` (workspace layer 7, tier Solid, scope cap 24 thousand lines for the whole
crate; nothing depends on it). This bead builds its skeleton: where the code lives, the five record types every
other harness bead reads and writes, how a record becomes bytes and a content address, and which part of the code
may compute a published number.

Three DESIGN decisions shape it.

1. **The harness has no product verbs of its own.** It measures FrankenRobotics through the same public `frob`
   verbs a user has, and drives every rival tool out of process. Reason: a harness reached through the surface it
   judges is a path to self-certification, and foreign tools are comparison instruments that never enter a
   production dependency graph (ADR-GAUNT-01, ADR-GAUNT-04). Rejected: `frob tenfold …` verbs (the judged surface
   would write its own evidence); an `xtask` subcommand (`xtask` holds exactly six checks and runs no physics).
2. **Its records are harness records, not product formats.** They are not among the registered file formats of the
   product. They carry the schema names `frob.tenfold.mission/1`, `frob.tenfold.freeze/1`, `frob.tenfold.ledger/1`,
   `frob.tenfold.receipt/1` and `frob.tenfold.report/1`, and they travel in the replication kit that lets a third
   party recompute and re-run a gate.
3. **Every published number is recomputable from records by code that depends on nothing outside the standard
   library.** Reason: the same argument that keeps the offline certificate auditor `frob-verify` dependency-free:
   a third party must be able to build the scorer on a clean machine and get every ratio, interval, count and
   verdict bit for bit. Rejected: scoring with a statistics library (a version change moves a published digit);
   binary floating point in stored quantities (two platforms print two values).

## Scope

In: the module tree; the operator binary and the scorer binary as empty shells with argument parsing; the common
rules of the five records (header, numerics, canonical bytes, content addresses, strict reading); identifier types;
the on-disk store layout; the lint and the standalone build that enforce the scorer boundary. Out: the fields and
behaviour of each record, which are in the bead that owns it: mission card (N39a-05), freeze manifest (N39a-18),
phase ledger (N39a-23, N39a-24), receipt (N39a-09), report (N39a-36).

## Technical approach

**Layout (DESIGN).**
```
crates/frob-conformance/src/tenfold/
  mod.rs  ids.rs  canon.rs  store.rs  refusal.rs
  records/{mission,freeze,ledger,receipt,report}.rs
  roles.rs  seal.rs  preopen.rs  clock.rs  cost.rs
  suite/{strata,grid,family,controls}.rs      arms/{freeze,terms,schedule,advocate,arm_c,swap}.rs
  phase/{interval,exclusive,resource,closure,tagmap,levers}.rs
  accept/{battery,family,submission,adjudicator}.rs
  score/{ratio,bootstrap,guard,noninferiority,verdict,warm,monitor,ceiling,preanalysis,normal,rng}.rs
crates/frob-conformance/src/bin/frob-tenfold.rs         operator tool of the adjudicator and the gate runner
crates/frob-conformance/src/bin/frob-tenfold-score.rs   the scorer
crates/frob-conformance/tests/tenfold.rs                test target: cargo test -p frob-conformance --test tenfold
kit/scorer/Cargo.toml                                   standalone package that builds score/ with one path dependency
```
`frob-tenfold` is an operator tool like the end-to-end log tool of the same crate; it is not a `frob` verb and is
never exposed over MCP. The crate's manifest sets `autobins = false` (BD-025), so both binaries exist only by
declaration: this bead adds two `[[bin]]` entries with an explicit name and path,
`{ name = "frob-tenfold", path = "src/bin/frob-tenfold.rs" }` and
`{ name = "frob-tenfold-score", path = "src/bin/frob-tenfold-score.rs" }`, and one row each in the binary table of
the crate's `CONTRACT.md`, naming this bead as owner and stating what the binary reads and writes (`frob-tenfold`:
reads and writes the gate store `tenfold/<gate>/` and the harness registries; `frob-tenfold-score`: reads harness
records and writes only the scorer's derived records, append-only, never rewriting an input). Neither binary writes a
row of `registries/gates.toml`; a gate value cited from their records is recorded by `record_gate`.

**The scorer boundary.** Everything under `score/`, plus `ids.rs`, `canon.rs` and `records/`, may import only `std`
and `frob_cert` (the auditor's crate, which has an empty dependency table and supplies a strict canonical JSON
reader, BLAKE3, exact integers and exact rationals). No `f64::ln`, `exp`, `powf` or other platform mathematics
library call is allowed there; the two transcendental functions the statistics need (Φ and Φ⁻¹) are implemented in
`score/normal.rs` from IEEE-754 basic operations only, so their bits are the same on every platform. Enforcement:
(a) a unit test parses every `use`, `extern crate` and path expression of those files and fails on any other
crate root or any banned method name; (b) `kit/scorer/Cargo.toml` builds the same source files through `#[path]`
modules with exactly one dependency, a path to `frob-cert`, and `cargo build --offline` of it must succeed.

The boundary is one list (DESIGN: `BOUNDARY_FILES` in `tests/tenfold.rs`, paths relative to the crate's `src/`),
read by the lint of (a) and matched one to one by the `#[path]` modules of (b); a `crate::` or `super::` path in a
listed file may name only another listed file. A function that a `score/` file calls is therefore in a listed
file, or the lint fails. A bead that later puts a file inside the boundary enters it in the list and in the kit
package in its own change, and the lint and the offline build then cover it. Two such files are known now:
`tenfold/phase/inputs.rs`, the ledger selectors that the ratio and the ceilings read through (entered by N39a-24),
and `thesis/calc.rs`, the exact ceiling calculators that `score/ceiling.rs` calls (written by N00-17 under the same
rule, entered by N39a-37).

**Common rules of every record.**
- *Header.* `schema` (one of the five names), `gate` (`M0-baseline`, `M1-baseline`, `M3-partial`, `M7-tournament`,
  or `rehearsal-<name>` for records that contain no sealed material).
- *Numerics.* JSON numbers are used only for small counts (integers of magnitude below 2⁵³). Every quantity is a
  string. A duration is seconds as a decimal string matching `^(0|[1-9][0-9]*)(\.[0-9]{0,2}[1-9])?$`, read exactly
  into integer milliseconds (`u64`). DESIGN: the fraction has at most three digits and no trailing zero, so every
  duration has exactly one spelling and two records that mean the same time have the same content address
  (`"1.5"` is canonical; `"1.50"` and `"1.500"` are refused, never rewritten). A ratio is an exact reduced rational `"p/q"` with its decimal rendering beside it.
  Rendering rule: a point estimate is rounded half-to-even at the printed precision; a confidence bound is rounded
  outward (an upper bound up, a lower bound down), so a printed bound is never tighter than the computed one.
- *Canonical bytes.* UTF-8 JSON with object keys sorted bytewise, no insignificant whitespace, no duplicate keys,
  strings in their shortest valid escaping; this is the canonical form of the auditor's reader, reused unchanged.
- *Content address.* `b3:` followed by 64 lower-case hexadecimal digits: BLAKE3 over the canonical bytes. A record
  that names its own hash (`manifest_hash`, `receipt_hash`, `report_hash`) is hashed with that field set to `""`.
- *Strict reading.* An unknown field, a missing field, a quantity given as a JSON number, a non-canonical duration
  (`"01"`, `"1.5000"`, `"1e3"`, `"-1"`) and an unknown schema version are each refused with a harness refusal
  reason that names the JSON pointer at fault. Readers never repair input. The reasons are the rows of the
  ten-fold refusal registry (N39-REF, which binds them to its file and generated enum after this bead), with
  these ids and exit codes: `record-unknown-field`, `record-missing-field`, `record-duplicate-key` (exit 3);
  `record-noncanonical-number` (a quantity given as a JSON number, or a non-canonical duration; exit 3);
  `record-unknown-schema` (exit 3); `record-hash-mismatch` (a stored content address or self-hash that does not
  verify; exit 9, integrity); and, for the store below, `store-overwrite` (exit 9). A refusal is printed as
  `{"refusal": {"reason": …, "pointer": …, "observed": …, "required": …, "repairs": […]}}` (N39-REF's shape).
- *Flags.* Every record that leaves the store carries the three no-authorization flags `execution_authorized`,
  `hardware_safety_signoff`, `sim_to_real_certified`, all `false`, and `reality: "no-claim"`: acceptance in this
  test happens in simulation.

**Identifier types (DESIGN, `ids.rs`).** `GateId`; `Arm` ∈ {A, B, C, D}, where A is FrankenRobotics, B the
strongest composed rival, C the ablation arm (a short robust program over an incumbent engine), D the optional
product layer over an incumbent engine; `StratumId` (eleven names, N39a-12); `FamilyId` (`f:` + hash); `MissionHash`;
`CampaignIndex` (`u32`); `Regime` ∈ {`cold`, `warm`}; `Phase` (thirteen names plus `unattributed`, N39a-23);
`Millis(u64)`; `Hash32`.

**Store layout (DESIGN).** One directory per gate, owned by the adjudicator role; arms have no read access to it.
```
tenfold/<gate>/roles.json  seal.ndjson  comments.ndjson  strata.json  families.json  preanalysis.json
tenfold/<gate>/cards/<mission-hash>.json          public part of each mission card
tenfold/<gate>/sealed/<mission-hash>.json         sealed part, adjudicator only until the gate closes
tenfold/<gate>/freeze/<arm>-<stratum>.json
tenfold/<gate>/campaigns/<stratum>/<family>/<campaign>/<arm>/{campaign.json,intervals.ndjson,ledger.json,
                                                             transcript.ndjson,receipts/<index>.json}
tenfold/<gate>/report.json
```
Writes are append-only: a file is written once under a temporary name and renamed; a second write of different
bytes to the same path is refused.

**Determinism and evidence.** Reading, canonicalizing, hashing and every `score/` computation are class D0:
identical bytes on every platform, in debug and release. Measured times are measurements and carry no determinism
class. Records are class `Tested`.

## Acceptance criteria

- [ ] The module tree, the two binaries and the test target exist and build; `frob-tenfold --help` and
      `frob-tenfold-score --help` list their subcommands; neither appears in the product's verb registry.
- [ ] Both binaries are `[[bin]]` entries with explicit `name` and `path` and each has its row in `CONTRACT.md`'s
      binary table; BD-025's `cargo test -p frob-conformance --test binaries_declared` passes with them present.
- [ ] The crate's `CONTRACT.md` gains a "Ten-fold harness" part covering its ten sections (purpose, inputs, outputs,
      invariants, refusals, determinism class, evidence class, validity domain, oracles, known gaps).
- [ ] Canonicalization is idempotent and a re-serialized record has identical bytes and the same content address.
- [ ] Every strictness rule above is exercised by a test that expects the refusal.
- [ ] The boundary lint fails on a planted `use rand` and a planted `x.ln()` under `score/`; the standalone scorer
      package builds offline with one path dependency.
- [ ] `frob-tenfold record check <file>` exits 0 on a valid record; otherwise it exits with the reason's code (3,
      or 9 for `record-hash-mismatch`) and prints the reason and the pointer at fault.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- records::`
- `schema_names_are_five`: the set of accepted schema names is exactly the five above.
- `seconds_exact`: `"1500"` → 1,500,000 ms; `"0.001"` → 1 ms; `"1.5"` → 1,500 ms; `"14400"` → 14,400,000 ms;
  `"1.0005"` (four fraction digits), `"1.50"` and `"1.500"` (trailing zero), `"1."`, `"01"`, `"-1"`, `"1e3"` and the
  JSON number `1500` are refused, each with the pointer at fault.
- `writer_emits_canonical_seconds`: rendering `Millis` back to a string for every value in 0..=10⁵ ms and for
  14,400,000 ms gives a string the reader accepts and that round-trips to the same `u64`.
- `canon_idempotent`: for 10³ generated records, canon(canon(x)) = canon(x) and key order of the input does not
  change the address.
- `self_hash_rule`: a freeze manifest hashed with `manifest_hash` blanked reproduces its own `manifest_hash`;
  changing any other field changes it.
- `unknown_field_refused`, `duplicate_key_refused`, `missing_field_refused`: each names the JSON pointer and its
  reason (`record-unknown-field`, `record-duplicate-key`, `record-missing-field`), exit 3.
- `render_rules`: 45/17 renders `2.647`; the upper bound 0.11734615… renders `0.1174` at four places (outward);
  the lower bound 0.11734615… renders `0.1173`.
- `scorer_boundary_lint`: passes on the tree; fails on each planted violation; a scratch file entered in
  `BOUNDARY_FILES` with `use rand` fails it, a listed file with no `#[path]` module in `kit/scorer/` fails it, and
  a `score/` file that calls `crate::tenfold::store` (not listed) fails it naming the path.
- `append_only_store`: a second write of different bytes to one path is refused (`store-overwrite`, exit 9);
  identical bytes are a no-op.

### End-to-end script and logging

`scripts/e2e/tenfold_records.sh` (header `# e2e: bead=N39a-01 milestone=M0 seed=1 needs=cpu`). Steps: build both
binaries; `frob-tenfold record check` on one valid fixture per schema and on eight planted bad records; build the
standalone scorer package offline; print the address of each fixture twice and compare. It sources the shared
helper `scripts/e2e/lib.sh` (STD-E2E) and writes NDJSON to `target/e2e-logs/tenfold_records/<utc>.ndjson`
with a transcript beside it; it logs, per line, the command, exit code, wall time, the record's schema and
address, each expected refusal with its reason and pointer, on a mismatch the first differing byte offset with
both fixture paths, and a summary with assertion counts. No fixture contains sealed material.

### Known answers and negative controls

Known answers: the sample ledger of the phase-ledger bead (exclusive phases 600, 360, 20, 0, 12, 96, 150, 60, 40,
0, 30, 42, 90 and 0 s) sums to its clock of 1,500 s exactly; 54,000/20,400 reduces to 45/17. Negative controls:
a duration as a JSON number; a record with a field renamed; a scorer file importing a foreign crate; a record
whose stored hash was computed without blanking. Determinism lanes: the address of every fixture is identical
twice on one machine, in debug and release, and on both hosts (arm64 macOS, x86-64 Linux): class D0.

## Considerations

- The reading "depends on nothing outside the standard library" is taken to include the auditor's crate, whose own
  dependency table is empty. If a reviewer rejects that reading, the scorer vendors copies of the four routines it
  uses; the boundary lint already isolates them. Settled for the kit: the standalone scorer of the replication
  kit (N39b-19) takes the stricter reading. It includes the auditor's source files for canonical JSON, BLAKE3 and
  exact arithmetic by path and is built with the bare compiler (`rustc`, no package manager), so it has no crate
  dependency at all; the `kit/scorer/Cargo.toml` build of step (b), with its single path dependency, remains the
  in-workspace build of the same source files, and both must produce the same output bytes.
- Sealed parts of mission cards live beside public parts on the adjudicator's store. Their confidentiality rests on
  the role and capability rules of N39a-02, not on this layout.
- The store is small (records, not telemetry); agent transcripts are the bulk and are stored as files referenced by
  address.
- Revisit if the product's format registry later wants these records as product formats: the decision here is that
  it does not, because a product format would bind the product's reader to the instrument that judges it.
