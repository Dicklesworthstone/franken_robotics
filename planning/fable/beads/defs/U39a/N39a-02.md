## Background

The ten-fold test compares the time to an *independently accepted* answer between FrankenRobotics (arm A) and rival
arms built on incumbent simulators (arm B, the strongest composed rival; arm C, a short robust program over an
incumbent engine). A comparison run by one party on its own product measures that party's leniency with itself. The
protocol therefore names three parties and keeps them apart for the life of a gate (the partial gate at milestone
M3, the tournament at M7).

- The **builders** wrote FrankenRobotics.
- The **rival advocates** build and tune the rival arms and have written no FrankenRobotics code.
- The **adjudicator** writes the sealed missions and the referee protocol, runs acceptance and releases receipts,
  and belongs to neither group.

**INV-TENFOLD-01**: the builder, rival-advocate and adjudicator roles are disjoint for the life of a gate, for
people and for agent sessions; a person or an agent session holds exactly one of the three.

Two further rules belong to the same mechanism. The referee protocol (the adjudicator's written procedure for
accepting answers) is **not written by the builders**: the adjudicator writes it from the public class
descriptions, the mission grammar and the schemas; builders and advocates may comment on drafts through one logged
channel until the suite hash is committed; after that it is frozen. And the identity of the adjudicator decides
what words a result may use. DESIGN: the adjudicator is an external party, a person or a team with no authorship
in any arm. If none can be engaged, the fail-closed default is a fresh-context agent session with no write access
to any arm, operating from the protocol document alone under a named human, with every action logged; every ratio
measured that way is labelled `self-adjudicated`.

Rejected alternatives: trusting declarations of role without a mechanical check (the sibling projects documented
how agent swarms certify their own work); letting builders write "neutral" acceptance code for convenience (the
acceptance code would then share the builders' modelling errors).

## Scope

In: the role registry and its checks; the permission matrix on harness actions; the logged comment channel and its
closing; the authorship check on the referee protocol and the acceptance code; the adjudication and advocacy
labels and the wording lock they impose. Out: naming the people (owner decisions, see `needs`); sealing order
(N39a-15); what the adjudicator does when accepting (N39a-06 to N39a-09); leak detection and disqualification (the
other unit of this chapter).

## Technical approach

**1. Role registry (`tenfold/<gate>/roles.json`, written at sealing step 1, append-only until the gate closes).**
```
{ "gate": "M3-partial",
  "assignments": [ { "identity": "id:…", "kind": "person" | "agent-session", "role": "builder" | "advocate" |
                     "adjudicator", "since": "<utc>", "operator": "id:…" (agent sessions: the named human),
                     "statement": "b3:…" (signed text: no FrankenRobotics authorship, or no authorship in any arm) } ],
  "adjudication": "external" | "self-adjudicated", "rival_advocacy": "external" | "internal", "hash": "b3:…" }
```
An identity is a public-key fingerprint for a person and, for an agent session, the session identifier issued by
the daemon together with the model revision and the operator. `register(identity, role)` refuses an identity that
already holds a role in this gate (`role-conflict`), and no assignment is ever removed or changed.

**2. Checks that make the registry more than a declaration.**
1. *Authorship.* For every advocate identity, the product repository's history must contain no commit by that
   identity (author or committer); for the adjudicator, neither the product repository nor any rival arm pack may.
   A hit refuses the registration (`role-authorship`).
2. *Session lineage.* An agent session that has called any `frob` verb as arm A's agent, or held a write
   capability on any arm's workspace, cannot be registered as adjudicator; the daemon's session records are the
   evidence. The adjudicator's sessions hold the capability scope that administers sealed data (`qual:admin` on
   the adjudicator's own sealed key) and no write scope on any arm.
3. *Actor on every action.* Each harness action is recorded with its actor identity. The permission matrix:

| Action | Builder | Advocate | Adjudicator |
|---|---|---|---|
| Publish class descriptions, schemas, development missions | yes | no | yes |
| Comment on a protocol draft (before the suite hash) | yes | yes | n/a |
| Write or change the referee protocol or acceptance code | no | no | yes |
| Write sealed missions, commit suite and protocol hashes, open the suite | no | no | yes |
| Tune and freeze arm A | yes | no | no |
| Tune and freeze arms B, C | no | yes | no |
| Object in writing that the rival is under-built | yes | no | rules on it |
| Run acceptance, issue receipts, release paired results | no | no | yes |
| Read sealed cards, worlds, probe points, per-world outcomes before close | no | no | yes |
   An action outside the matrix is refused (`role-not-permitted`) and logged.
4. *Acceptance code provenance.* Every file under the adjudicator's acceptance tree must have only adjudicator
   identities as authors; one builder- or advocate-authored line refuses the protocol hash commit
   (`acceptance-code-authorship`). Builders supply schemas, the Gymnasium-compatible adapter (the binding through
   which a rival learning stack can drive this environment) and the development missions. They supply no
   acceptance code.

**3. The comment channel (`comments.ndjson`).** Append-only entries `{seq, ts, actor, role, draft: "b3:…",
text_hash, text}`. It is the only path by which builders and advocates influence the protocol. It closes when
sealing step 2 (the commitment of the suite and protocol hashes) is recorded: a later append is refused
(`channel-closed`). The channel's final hash is recorded with step 2.

**4. Labels and the wording lock.** `adjudication` ∈ {`external`, `self-adjudicated`} and `rival_advocacy` ∈
{`external`, `internal`} are copied from the registry into every campaign record, receipt and report. Rules the
report writer (N39a-36) enforces:
- under `self-adjudicated` a ratio may be reported, but the words "independently accepted" and "ten-fold" are
  withheld (`wording: locked-pending-replication`) until an external party has re-run the replication kit and that
  re-run is on record;
- under `rival_advocacy: internal` every result prints `rival: internally advocated`;
- a stratum adjudicated across home simulators instead of a neutral one prints `adjudication: cross-home` (N39a-08).
Self-adjudication mode additionally requires: the session started with an empty context and only the protocol
document and public schemas mounted; a named human operator in the registry; an action log with one line per
adjudicator action, hashed into the gate's ledger.

**5. Life of a gate.** Roles are fixed from the first registry write to the reveal at the gate's close. A new gate
has a new registry; a person may hold a different role in a different gate only if the authorship checks pass.

## Acceptance criteria

- [ ] INV-TENFOLD-01 holds as a property: no sequence of registrations yields one identity with two roles.
- [ ] A planted session that issued arm A verbs is refused as adjudicator; a planted advocate with one product
      commit is refused.
- [ ] Each row of the permission matrix is enforced; nine planted out-of-role actions are refused and logged.
- [ ] The comment channel refuses an append after step 2; its hash is in the step-2 record.
- [ ] A protocol hash commit with one builder-authored acceptance file is refused.
- [ ] Under the default mode every report carries `self-adjudicated` and the two words are absent from its text.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- roles::`
- `inv_tenfold_01_property`: 10⁴ random sequences of register calls over 20 identities and 3 roles; assert no
  identity ever appears with two roles and every conflicting call returned `role-conflict`.
- `authorship_blocks_advocate`: a synthetic repository history with identity X as committer of one commit → X as
  advocate refused; as builder accepted.
- `session_lineage_blocks_adjudicator`: a session record with one arm-A verb call → refused.
- `matrix_rows`: for each of the nine actions and each role, allowed exactly as tabulated (27 cases).
- `channel_closes_at_step_2`: append before → accepted; after → `channel-closed`.
- `acceptance_tree_authorship`: tree with only adjudicator authors → commit accepted; one foreign author → refused.
- `wording_lock`: a report under `self-adjudicated` with verdict `ten-fold` renders "measured … (wording locked
  pending external replication)" and contains neither locked phrase; with a recorded external re-run it unlocks.

### End-to-end script and logging

`scripts/e2e/tenfold_roles.sh`: on a rehearsal gate, registers three synthetic identities, attempts each
out-of-role action through `frob-tenfold`, opens and closes the comment channel around a synthetic step 2, and
builds a rehearsal report under both adjudication modes. Logs every command with exit code and wall time, each
refusal with its reason, the registry hash, and the presence or absence of the locked words; the summary line
names GATE-TENFOLD-04 as touched (roles are a precondition of the seal), not as passed.

### Known answers and negative controls

Negative controls, each of which must be caught: one identity registered as builder and adjudicator; an advocate
with product authorship; an adjudicator session with arm-A lineage; a comment after the hash commit; acceptance
code written by a builder; a self-adjudicated report that prints "ten-fold". Metamorphic relation: permuting the
order of registrations of distinct identities does not change which registrations succeed.

## Considerations

- OPEN (owner): who the adjudicator is; fail-closed default as described, with the label. OPEN (owner): who the
  advocates are and their budget; default agent sessions that have contributed nothing to FrankenRobotics, 40
  device-hours per stratum, and the label `rival: internally advocated` on every result.
- An agent session's "identity" is only as strong as the daemon's session records; the check is evidence of
  separation, not a proof against a determined operator. The named human operator is the accountable party.
- Risk named in the program register: no neutral party is named, so nobody outside can confirm the result. The
  countermeasures are these labels and the replication kit.
- Privacy: identities in published records are key fingerprints; names stay in the adjudicator's store.
