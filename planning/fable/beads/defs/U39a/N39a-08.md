## Background

An answer in the ten-fold test is *independently accepted*. For answers decided by running a design (a qualified
design; a counterexample and its repair) that means the acceptance battery runs in a simulator that is neither
arm's own.

DESIGN: dynamic acceptance batteries run in a **neutral adjudicating simulator** that meets four conditions:

1. neither arm used it for training, tuning or screening on that stratum;
2. its contact model was derived independently of both arms;
3. it runs deterministically on a CPU;
4. it is pinned by revision.

The reason is that an arm scored in its own engine is scored on its own modelling errors, and two programs that
share a solver have correlated error. The default candidate is Drake at a pinned release (FACT about the source
read for the plan: a CPU multibody engine with its own convex contact solver; release 1.58.0 was the one read; the
release is re-read and re-pinned before a gate cites it). On a stratum where an arm uses that engine as a tool,
or where it cannot represent the mission, the adjudicator substitutes another engine that meets the four
conditions. If none exists the stratum falls back to **cross-home adjudication**: an answer must pass in the
highest-trust tier of *both* arms (the product's CPU referee tier and the rival's CPU reference), run by the
adjudicator, and the report labels the stratum `adjudication: cross-home`.

Two interface decisions follow. Models reach the adjudicating simulator through a **neutral exchange
description** that the adjudicator's own importer reads, so that neither arm's importer shapes the test. A
controller runs as a **separate process** behind the observation and action interface with the mission's clocks,
so that any controller, trained or synthesized, from any arm, is run the same way. The gap between an arm's home
simulator and the adjudicator is that arm's risk, equally for both.

Rejected: scoring each arm in its home simulator (measures leniency); scoring both in the product's referee
(the builders' model would judge the rival); linking the adjudicating simulator into the harness (foreign tools
are comparison instruments, run out of process under a pin, and never enter a dependency graph).

## Scope

In: the adapter trait and its out-of-process implementation for the default candidate; the four-condition check;
the exchange description and what it must carry; the controller process protocol; the cross-home mode; the
per-stratum adjudication record. Out: which engine is chosen per stratum (the decision OPEN-TENFOLD-1, N39b-26,
carried with OPEN-PROG-2; this bead implements the default candidate and the check any candidate must pass); the
observation and action interface the controller process speaks (the Gymnasium-compatible adapter BD-301); the battery arithmetic
(N39a-06); the acceptance test of the adjudicator itself (N39a-10); the decision when no engine passes (N39a-11).

## Technical approach

**1. Adapter (DESIGN, `accept/adjudicator.rs`).**
```
trait AdjudicatingSim {
    fn identity(&self) -> SimPin;                     // name, revision, container digest, build flags
    fn can_represent(&self, card: &MissionCard) -> Representability;   // per feature: terrain, films, tracks…
    fn run_episode(&self, world: &WorldDraw, model: &ExchangeModel, ctrl: &ControllerSpec,
                   horizon: Millis, seed: u64) -> EpisodeTrace;        // deterministic
}
```
The implementation launches the engine in a container named by digest (the incumbent harness of BD-039 supplies
the launcher, the recorded environment and the identity hashing), passes inputs as files, and reads a trace file.
`SimPin` enters every decision record and every receipt hash.

**2. The four conditions as checks (`frob-tenfold adjudicator check --stratum s`).**
1. *Not used by an arm.* Search every arm's freeze manifest (engine, learner, outer loop, tool layer), tuning log
   and process tag map for the engine's name, package identifiers and container digest. A hit on the stratum
   fails the condition; a hit during tuning after the fact is a disqualifying event for that arm. The adapter
   also appends one line per launch (identity, role, stratum, time) to its access log in the gate store
   (`tenfold/<gate>/adjudicator_access.ndjson`), and the search reads that log beside the arms' own records: a
   launch under a builder or advocate identity is a hit.
2. *Independent contact model.* A declared provenance statement: the engine's contact formulation and its source,
   with a statement that it shares no solver code with either arm's engine; checked against the arms' dependency
   lists. This is a DESIGN judgement recorded by the adjudicator, not a computation.
3. *Deterministic on a CPU.* The same episode run twice, and on two worker counts, produces byte-identical traces
   on 20 development clusters per stratum.
4. *Pinned.* The identity resolves to an exact revision and container digest; a moved pin changes `SimPin` and
   voids prior acceptance of the adjudicator.
`can_represent` returns, per card feature, `native`, `approximated: <how>` or `unsupported`. An `unsupported`
feature on a stratum's cards triggers substitution or cross-home mode for that stratum.

**3. The neutral exchange description (DESIGN).** A directory per submitted design:
- `model.xml`: a rigid-body description in a public robot-description format produced by the product's exporter or
  the rival's own, with links, inertias, joints with limits, collision primitives and meshes;
- `actuation.json`: per actuator the torque-speed envelope, gear ratio, reflected inertia and delay, as plain
  numbers with units (no engine-specific actuator plug-in);
- `sensors.json`: the observation vector layout, sample periods and latency per channel;
- `contact.json`: material pair parameters by named surface, in units, with the friction law's name;
- `loss.json`: what the exporter could not express (the loss report). A loss that touches a requirement term
  fails the export, so that no arm is scored on a silently simplified model.
The adjudicator's own importer reads these files. It is part of the acceptance code and is written by the
adjudicator role only.

**3a. The decision's probes, re-run through the description.** The decision that names each stratum's simulator
(N39b-26, a dependency) ran its representability probes (stairs, gaps, stepping stones and rubble as terrain; a
liquid film with reduced friction on a patch; a tracked running gear on stairs and soft ground; wheels on a ramp
with payload; a conveyor; a door closer and a castor chair; sensor timing through the observation interface) as
hand-built `synthetic` fixtures in the candidate's own model format, under
`fixtures/tenfold/adjsim_probes/<candidate>/`, because the description did not exist at M2. This bead writes each
probe a stratum's decision relied on once more as an exchange-description directory (same geometry, parameters
and planted answer, under `fixtures/tenfold/adjsim_probes/exchange/`), imports it with the adjudicator's
importer and runs it against the same planted answer and tolerance (`frob-tenfold adjudicator check --stratum s
--probes`). Per probe, with the native outcome read from the decision's log by digest:
- passes both ways: `can_represent` reports the feature as the decision recorded it;
- passed natively and fails through the description: a defect of the description or the importer, repaired here;
  while one stands the stratum's adjudication record cannot be written with mode `neutral`;
- fails both ways: the candidate is removed from that stratum and the decision N39b-26 is reopened for it
  (substitution, or cross-home mode), with the probe's log digest in the record's `representability`.

**4. The controller process.** The harness starts the submitted controller as its own process with no network,
the card's CPU allowance and a fixed start-up budget. Protocol: newline-delimited frames over a pipe; the
simulator sends `obs{tick, t, values[]}` at each control instant of the card's control clock, and the controller
must reply `act{tick, values[]}` before the per-tick deadline of that clock; observations are delivered with the
card's declared latency. Missed deadline, non-finite value, wrong length or early exit: the cluster fails. The
controller sees only the declared observation channels; privileged simulator state is not reachable from it.

**5. Cross-home adjudication.** When no neutral engine meets the four conditions for a stratum, each submission is
run by the adjudicator in two simulators: the product's CPU referee tier and the rival's CPU reference at the
rival's frozen revision, both through the same exchange description and controller protocol. The battery decision
is the conjunction (accepted iff accepted in both, each at the submission's level). The stratum's record and
every report line carry `adjudication: cross-home`. If neither home referee can run the other arm's answers, the
stratum is `descriptive`.

**6. Per-stratum adjudication record.** `{stratum, mode: "neutral" | "cross-home" | "descriptive", sim: SimPin |
[SimPin, SimPin], representability: {...}, conditions: [4 results], decided_by, decided_at, hash}`; committed with
the suite hash.

## Acceptance criteria

- [ ] The default adapter runs a development episode out of process from a recorded environment and returns a
      trace; changing the container digest changes `SimPin`.
- [ ] The determinism check passes on 20 development clusters for `legged-quad` and `wheeled` (byte-identical
      traces twice and across two worker counts).
- [ ] A planted arm whose tuning log names the adjudicating engine fails condition 1 for that stratum.
- [ ] An export with a loss touching a requirement term is refused; a clean export imports and steps.
- [ ] A controller that replies late, with a non-finite value or a wrong-length vector fails its cluster; it
      cannot read any channel outside the declared observation vector.
- [ ] In cross-home mode an answer that passes in one home simulator only is rejected, and the label is printed.
- [ ] Every probe the decision N39b-26 lists for a stratum in scope has been re-run through the exchange
      description, with both outcomes in the stratum's adjudication record; no record has mode `neutral` while a
      probe passes natively and fails through the description, and a probe failing both ways has reopened the
      decision for its stratum.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- adjudicator::`
- `pin_identity_changes`: two digests → two `SimPin` hashes.
- `condition_1_search`: freeze manifests and tag maps with and without the engine name → fail and pass.
- `representability_matrix`: a card with a film patch on an engine declared `unsupported` for films → the stratum
  is routed to substitution or cross-home.
- `exchange_loss_blocks`: loss report naming a friction term that the requirement reads → refused.
- `controller_protocol`: scripted controllers (on time; 1 tick late; NaN; short vector; exits at tick 10) → pass,
  fail, fail, fail, fail.
- `observation_latency`: a channel declared with 20 ms latency is delivered two 10 ms ticks late.
- `cross_home_conjunction`: (pass, pass) → accepted; (pass, fail) and (fail, pass) → rejected.
- `probe_rerun_outcomes`: three `synthetic` probes with recorded native outcomes. Native pass and exchange pass →
  the feature is reported as recorded. Native pass, and an importer planted to drop the film patch's friction
  scale → reported as a defect of the description, and writing the stratum's record with mode `neutral` is
  refused. Fail both ways →
  the candidate is removed from the stratum, which is routed to substitution or cross-home, and the record names
  the probe's log digest.

### End-to-end script and logging

`scripts/e2e/tenfold_adjudicator_sim.sh`: exports a reference quadruped and a reference differential-drive base
with `frob` to the exchange description, imports them with the adjudicator's importer, runs one development
episode each with a baseline controller process, repeats for the determinism check, then runs the planted
late-controller and lossy-export cases, and last re-runs the decision's probes through the exchange description
(`frob-tenfold adjudicator check --stratum … --probes`). It sources `scripts/e2e/lib.sh` (STD-E2E) and writes
NDJSON to `target/e2e-logs/tenfold_adjudicator_sim/<utc>.ndjson`. Logs each command, exit code, wall time,
`SimPin`, trace digests (first and second run, and the two worker counts) with a digest-equality assertion, the
per-tick deadline and the worst reply latency in milliseconds against it, each refusal with its reason, per probe
the native outcome with its log digest, the outcome through the description, the planted answer, the observed
value and the tolerance, and on a digest mismatch the
first differing tick and field with both trace paths. Its header is `needs=cpu` (the adjudicating simulator runs
on a CPU, and the helper's `needs` field has no value for an installed container); the script itself checks for
the recorded environment of the default candidate and skips with code 77, logging the reason, where it is not
installed.

### Known answers and negative controls

Known answers: on the neutral engine, the subset of the product's known-answer suite that the engine can express
(for example a free-falling body's impact time and a block at rest on an incline below the friction angle) inside
the engine's own stated tolerances; these are the first clause of the adjudicator's acceptance gate. Negative
controls: an engine build with a nondeterministic thread schedule (the determinism check fails); a controller
given privileged state (a noninterference test detects the dependence); an arm that touched the adjudicating
simulator during tuning (condition 1 fails; the arm is disqualified). The last is entry TF-CX-15 of the harness's
counterexample registry (N39-CX; gates GATE-TENFOLD-03 and GATE-TENFOLD-05), and this bead writes its planted
input under the registry's plant name, as the `synthetic` fixture directory
`crates/frob-conformance/fixtures/tenfold/controls/judge_in_tuning_logs/`: an arm pack whose tuning log names the
adjudicating engine's package identifier and container digest, with a matching line in the adapter's access log.
It is caught when `frob-tenfold adjudicator check --stratum s` fails condition 1 naming the arm and the log
line; the disqualification that follows (`adjudicator-in-tuning`) is the disqualification engine's (N39b-01),
and the kill decision N39a-11 reads the result.

## Considerations

- OPEN: which simulator adjudicates each stratum, and whether it can represent terrain, films and tracks.
  Fail-closed default: a pinned incumbent CPU engine that no arm trains in; where it cannot represent the mission,
  cross-home adjudication, labelled.
- KILL-TENFOLD-ADJ: no neutral simulator passes acceptance for a stratum → cross-home, labelled; failing that,
  `descriptive` (decision bead N39a-11).
- The adjudicating simulator is a third model, not the world: agreement with it is Parity, never Reality.
- Licence: the adjudicating engine is not redistributed; records pin revisions and give fetch instructions.
- Common-mode risk remains where arms and adjudicator share parameter cards (friction coefficients read from the
  same card); the record lists which exchange fields came from which card provenance.
