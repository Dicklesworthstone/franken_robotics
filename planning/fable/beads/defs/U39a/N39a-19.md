## Background

The ten-fold ratio compares systems. It must not compare agents, hardware, thermal state, documentation, or luck
in the order of runs. The protocol therefore binds every arm to the same terms and schedules the runs so that
whatever cannot be equalized is shared.

**Equal terms (binding; DESIGN).** The same agent model at one pinned revision for the whole gate, the same token
and tool-call caps per campaign, a fresh context per campaign, and no human in the loop. The same hardware
envelope: the primary result is on matched devices, one RTX 4090 of the Linux host `trj` (two RTX 4090 with 24 GB
each and no link between them) and the same number of CPU cores per campaign, with card assignment and run order
randomized and counterbalanced and the arms interleaved in time so that load and temperature are shared. The same
calibration data, reusable prior answers and proof problems. The same documentation budget: arm A's agent reads
the product's generated documentation; the agents of arms B and C read the incumbents' own documentation and an
advocate-written guide no longer than the product's documentation, frozen with the arm. A second result on each
arm's best-supported platform may be run (arm A may add the Apple M5 Ultra machine); a platform an arm cannot use
is printed as `unavailable`, and a gap that exists on one platform only is a portability observation, not the
ratio.

Reason for interleaving: FACT about the Linux host: it is often heavily loaded, so measurements record the load.
A block of arm A runs on a quiet night and a block of arm B runs on a busy afternoon would measure the afternoon.

Rejected: letting each arm use "its best" agent (the ratio would then be conditional on two agents); running all
of one arm first (confounds the arm with time, load and temperature); matching by nominal device model only
(`trj`'s two cards can differ in thermal headroom, hence counterbalanced card assignment).

## Scope

In: the equal-terms record of a gate and the checks that every freeze manifest and campaign agrees with it; the
documentation budget measurement; the schedule generator and its properties; the second-platform rule. Out: caps
enforcement mechanics (N39a-04); the freeze manifest (N39a-18); what the agent is (owner decision).

## Technical approach

**1. The equal-terms record (`tenfold/<gate>/terms.json`, committed at sealing step 2).**
```
{ "agent": {"model": "…", "revision": "…", "token_cap_in": "…", "token_cap_out": "…", "tool_call_cap": 0,
            "fresh_context": true, "sampling_seed": "per-campaign" | "unavailable"},
  "human_in_loop": false,
  "hardware": {"primary": {"host": "trj", "devices_per_campaign": 1, "device_model": "RTX 4090",
               "cpu_cores": 8, "memory_gib": "…", "fingerprints": ["b3:…", "b3:…"]},
               "secondary": {"A": "m5-ultra" | null, "B": "…" | "unavailable", "C": "…" | "unavailable"}},
  "shared_inputs": {"calibration_data": ["b3:…"], "prior_answers": ["b3:…"], "proof_problems": ["b3:…"]},
  "documentation_budget_tokens": 0, "cache_budget": {"disk_bytes": "…", "device_bytes": "…"},
  "schedule_seed": "…", "hash": "b3:…" }
```
Checks at freeze and at every campaign start: the manifest's `agent` block equals `terms.agent`; the campaign's
caps equal the terms; the workspace's shared inputs are exactly `shared_inputs` plus the card's permitted inputs;
the device the schedule assigned is one of the two fingerprints (`terms-mismatch` names the field).

**2. Documentation budget.** `documentation_budget_tokens` is the token count of arm A's generated documentation
under the common agent's tokenizer (measured by the harness, not declared). For arms B and C the budget applies
to the *advocate-written guide* only: its token count must not exceed the budget (`guide-over-budget`). The
incumbents' own published documentation is additionally readable by their agents, at the pinned revisions, from a
local mirror hashed into the pack (no live web access during a campaign, for any arm).

**3. Fresh context and no human.** Each campaign starts a new agent session whose only inputs are the card, the
permitted inputs and the documentation; the harness's agent proxy rejects a session identifier it has seen. Any
operator action on a running campaign is an intervention entry and a flag on the campaign (N39a-04).

**4. The schedule (`arms/schedule.rs`; generated from `schedule_seed`, hashed into step 6).**
Units to schedule: for each cell, each family, each campaign index, one campaign per arm (A, B, C). Properties,
each a checkable predicate over the generated schedule:
1. *Interleaved in time.* The campaigns of one pair-set (same mission, same campaign index, all arms) are placed
   in adjacent slots; with two devices, two of them run concurrently on the two cards and the third follows on
   the card that frees first. No arm ever has more than two consecutive slots on a card.
2. *Randomized order.* Within each pair-set the order of arms is a uniformly random permutation drawn from the
   schedule seed.
3. *Counterbalanced.* Over a cell, each arm occupies each position (first, second, third) equally often up to a
   difference of one, and runs on each of the two cards equally often up to a difference of one. The generator
   draws permutations in balanced blocks (all six orders of three arms per six pair-sets; card assignment
   alternating within a block from a random start).
4. *Same cores.* Every campaign gets the same number of pinned CPU cores, from disjoint sets when two campaigns
   run concurrently; the adjudicating batteries run on cores reserved for the adjudicator, so adjudication
   latency does not depend on which arm is running beside it.
5. *Family order randomized.* The order of families within a cell is a random permutation (the futility monitor
   reads per-family ratios in this order).
6. *Recorded conditions.* At each campaign start the harness records host load averages, device temperature and
   utilization, and the co-tenant campaign's arm; these go to the campaign record so that a load imbalance is
   visible afterwards.
A harness-fault re-run takes the next free slot under the next campaign index with a fresh random order for that
pair-set.

**5. Second platform.** A separately labelled result set `platform: best-supported` may be run per arm. Its
ratios are never pooled with the primary set and never carry the word. An arm with no path on a platform prints
`unavailable` in that cell; a missing cell is published, not omitted.

## Acceptance criteria

- [ ] Every freeze manifest of a gate and every campaign record agrees with `terms.json` field by field; a planted
      mismatch in each field is refused with the field named.
- [ ] The advocate guide's measured token count is at most the budget; a guide one token over is refused.
- [ ] For a cell of 24 families and three arms (24 pair-sets, 72 campaigns) the generated schedule satisfies the
      six properties: each arm is first, second and third 8 times each; each arm runs on each card 12 times (± 1
      with re-runs); no arm has more than two consecutive slots on a card.
- [ ] Two schedules from one seed are identical; from different seeds they differ.
- [ ] A reused agent session identifier is rejected by the proxy.
- [ ] A best-supported-platform ratio cannot be merged into a primary cell (`platform-mixed`).

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- terms::`
- `terms_fieldwise`: one test per field (agent revision, token cap, cores, device fingerprint, shared inputs).
- `guide_budget`: guide tokens = budget → accepted; budget + 1 → `guide-over-budget`.
- `schedule_counterbalanced`: m = 24, arms = 3 → position counts (8, 8, 8) per arm; card counts 12 and 12.
- `schedule_interleaved`: maximum run length of one arm on one card ≤ 2 over 10³ seeds.
- `schedule_deterministic`: same seed → same bytes.
- `schedule_uniformity`: over 6,000 pair-sets the six arm orders each occur 1,000 times (balanced blocks).
- `rerun_slot`: a harness-fault pair gets campaign index + 1 and a new permutation.
- `platform_not_pooled`.

### End-to-end script and logging

`scripts/e2e/tenfold_equal_terms.sh`: on a rehearsal gate, writes terms, freezes two synthetic arms (one with a
planted agent-revision mismatch), generates the schedule for a 12-family cell, runs four short interleaved
synthetic campaigns across two CPU "device" stand-ins, and prints the recorded conditions. Logs each command,
exit code, wall time, the terms hash, the schedule hash, position and card counts per arm against their
expected values, host load at each start, each refusal with its field, and the summary.

### Known answers and negative controls

Known answers: the balance counts above. Negative controls: a schedule that runs all of arm A first (the
interleaving predicate fails); arms on different agent revisions; a guide longer than the product's
documentation; a campaign with a human answer injected (the flag is set and printed). A/A control (run when the
partial gate is rehearsed): the same frozen arm scheduled as both arms of 10 pairs must give a pooled ratio whose
descriptive interval covers 1 and a per-family ratio above 1.5 in none of the 10 pairs (TARGET), which tests the
schedule and the timekeeper together.

## Considerations

- "The same agent" favours whichever system the agent already knows; the result is stated as conditional on the
  pinned agent, and human engineering time, learning curves and usability for a person are outside the test.
- Two concurrent campaigns share a host: memory bandwidth and CPU caches are contended. Counterbalancing shares
  the effect between arms; the recorded co-tenant makes it analyzable.
- Device-hours: the default cell (24 families, three arms, a 4 h deadline) is at most 288 device-hours, above the
  default compute envelope; each run needs the owner's approval of a campaign class.
- The schedule seed is committed at step 2 and revealed at step 6, so nobody can choose it after seeing the arms.
