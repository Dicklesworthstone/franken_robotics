## Background

A comparative result is most easily abused at the moment it is written down: a ratio quoted without its regime,
its sample size or its interval; a warm figure quoted without the standing investment behind it; a number about a
system that was never run. The ten-fold test therefore fixes what a report contains before any result exists, and
makes the report a harness record (`frob.tenfold.report/1`) that a third party can recompute from the ledgers and
receipts, not a document someone types.

Two rules shape the record.

**Descriptive reporting, always (DESIGN).** Whatever the verdict, every cell (a stratum and a regime) reports:
time-to-acceptance curves per arm; completion probability by the deadline H; conditional times; the per-phase
ratio of the two ledgers; every cost column; every false positive, false negative and abstention; the fastest
qualifying baseline and all arms with raw pairings. A per-mission best-of-rivals ensemble may be shown as an
extra lower bound and is labelled as one. Nothing is inferred about systems that were not run.

**INV-TENFOLD-08.** Every reported ratio carries its regime, m (families), n (pairs), H, [L, U], the adjudication
label and the freeze hashes; a warm ratio also carries S (the standing-asset cost) and N* (the crossover reuse
count).

Reason for making the second a type and not a style rule: a ratio that can be printed bare will be. Rejected: a
free-form report template checked by review; a summary table that drops cells with no verdict (a cell that could
not be confirmed is part of the result).

## Scope

In: the record's structure (the one layout of `frob.tenfold.report/1`); the `ReportedRatio` and `DescriptiveRatio`
types; the descriptive tables and how each is computed; the limits printed on every report; the completeness rules,
as refusals that any generator of the record must raise; the rule that the rendering is a pure function of the
record. Out: the gate report generator (N39b-14, which depends on this bead): the command that assembles the record
from the scorer and the outcome engine, the per-cell fields beyond the descriptive block (guard, tie test, recovery
ratios, ceilings, phase ledgers, costs, sentences, evidence digests, the portfolio ratio), the closed label
vocabulary derived from the gate's records, the Markdown and HTML renderings and the golden card tables. Also out:
the verdict and its inputs (N39a-27 to N39a-35); outcome wording and program actions (N39b-05); the wording lint
and the limits block as shipped text (N39b-15); the kit (N39b-18); recovery ratios and ablations (N39b-43,
N39b-45); the ceilings content (N39a-37), which the record references by hash; the lost-factor records (N39a-26),
which rule 4 checks against, and the pre-run notice (N39a-34), which rule 2 checks against; the counters of the
anti-shortcut controls (N39a-14), copied per cell; the learner-swap diagnostic (N39a-22), which is built after this
bead and is referenced by an optional hash that no completeness rule requires. Also out: the metric contract
(N00-19): the document that defines the answer, the clock, the charged-time rule and the four properties, and the
conformance test `check_report` with its ten violations. That bead holds no report record of its own; this record
is the one stored report, its cells implement the contract's view `RatioReportView`, and passing `check_report` is
a completeness rule here (rule 7).

## Technical approach

**1. The record (DESIGN).**
```
{ "schema": "frob.tenfold.report/1", "gate": "M3-partial", "suite": "b3:…", "protocol": "b3:…",
  "thresholds": "b3:…", "prerun_notice": { … verbatim … },
  "labels": { "adjudication": "external" | "self-adjudicated", "rival": "externally advocated" | "internally advocated",
              "reality": "no-claim", "cost_claim": "none", "agent": {"model": "…", "revision": "…"} },
  "cells": [ { "cell": {"stratum": "…", "regime": "…"}, "status": "confirmatory" | "descriptive: <reason>",
               "ratio": <ReportedRatio>, "ratio_ab": <ReportedRatio>, "ratio_ac": <ReportedRatio>,
               "verdict": { … the verdict record … }, "completion": { … }, "coverage": { … } | "not-applicable",
               "tie": { … }, "monitor": { … }, "ledgers": {"A": {…pooled…}, "B": {…}, "C": {…}},
               "ledger_status": {"closed": 0, "open": 0}, "ceilings": "b3:…", "descriptive": { … step 3 … },
               "controls": { … counters of the anti-shortcut controls … } } ],
  "not_run": [ {"stratum": "…", "reason": "…"} ], "voided": [ … ], "disqualifications": [ … ],
  "diagnostics": { "learner_swap": "b3:…" }, "lost_factors": "b3:…",
  "authorization": {"execution_authorized": false, "hardware_safety_signoff": false, "sim_to_real_certified": false},
  "scorer": {"build": "…", "source": "b3:…"}, "report_hash": "b3:…" }
```

One layout (DESIGN). There is one record of this schema, and the gate report generator (N39b-14) fills it. That
bead's own sketch lists per-cell fields this one does not show (`result_type`, `c`, the guard block, the
bootstrap method and seed, the tie-test and recovery blocks, `censored`, `excluded_pairs`, `ceilings_on_rival`,
`phase_ledgers`, `costs`, `rate_ratio`, `outcomes`, `sentences`, `evidence`, and the top-level `portfolio` and
`limits`); they are added to this layout under those names. Where the two sketches spell the same thing
differently, the names here govern: `suite`, `protocol` and `thresholds` (not `suite_hash`, `protocol_hash`,
`params_hash`); `labels` as an object with one key per kind of label, whose values come from the closed
vocabulary of N39b-14; `status` (not a boolean `confirmatory`); `ledger_status` (not `ledger_open`); and a ratio
always as a `ReportedRatio` object, of which a flat `ratio`, `ratio_decimal` and `bounds` are the `value`, `L`,
`U` and `interval` fields.

**2. `ReportedRatio` (the only way a ratio enters a report).**
```
{ "value": {"rational": "45/17", "decimal": "2.647"}, "regime": "cold" | "warm at 10 amendments",
  "m": 24, "n": 24, "deadline_s": "14400", "L": "…", "U": "…", "interval": "bc-family-bootstrap/1" | "degenerate",
  "adjudication": "…", "freezes": {"A": "b3:…", "B": "b3:…", "C": "b3:…"}, "against": "B" | "C",
  "warm": {"S_A_s": "…", "S_B_s": "…", "n_star": 5 | "never"} | null }
```
The constructor refuses a missing field (`ratio-incomplete`) and refuses `warm: null` when the regime is warm
(`warm-without-assets`). The renderer's ratio-printing function accepts only this type; per-family ratios and
per-phase ratios are printed through a second type, `DescriptiveRatio`, that always renders with the suffix
"(descriptive)" and cannot be placed in a verdict sentence.

**3. The descriptive block, per cell (each from ledgers, receipts and campaign records only).**

| Table | Definition |
|---|---|
| Time-to-acceptance curve | For each arm, the step function F(t) = share of campaigns accepted by time t, listed at every acceptance time up to H; censored campaigns never step |
| Completion by H | F(H) per arm, as a count of n and with the exact upper bound on the miss rate (the zero-count bound when the count is zero) |
| Conditional times | Among accepted campaigns: minimum, quartiles, maximum of T per arm; and the count it is conditional on |
| Per-phase ratio | Σ exclusive time per phase, rival ÷ arm A, over pairs with both ledgers closed; `n/a` where the divisor is zero |
| Cost columns | Per arm: GPU-hours, CPU-hours, energy or its named gap, tokens, tool calls, human minutes, money; per-accepted-answer figures; designs decided per hour; compute per accepted decision at a matched error rate |
| Error table | Per arm: submissions rejected, by class (battery, obligation open, malformed); accepted answers later overturned; confident answers on unresolved missions; `unknown` offered on identifiable missions; truthful unknowns accepted (abstentions); missed withdrawals; unnecessary invalidations; false-certificate signals |
| Raw pairings | One row per pair: family, campaign index, T or `c` for each arm, labels, superseded attempts; and the name of the fastest qualifying rival |
| Ensemble lower bound | Σ_j min(T_B,j, T_C,j) ÷ Σ_j T_A,j with restricted times, labelled `ensemble: lower bound only` |

**4. Labels and limits printed on every report (not optional text).**
- `reality: no-claim`: acceptance happens in simulation; the adjudicating simulator is a third model, not the
  world. (A calibrated reality band covering the mission would change the label; none exists for this test.)
- The clock stops at the first accepted answer; quality beyond the acceptance threshold is not scored.
- Both arms are driven by one agent; the ratio is conditional on the pinned agent, and human engineering time is
  outside the test.
- Cost columns are reported and no cost claim is made.
- Nothing is inferred about an incumbent, a version or a configuration outside the frozen arms, or about missions
  outside the sealed population; manipulation with hands, flight and soft bodies are outside the suite.
- Standing assets for a mission class are charged; the engineering that produced either system is not.
- Step rate, rendering and safety are outside every claim here.

**5. Completeness rules (each a refusal of `report build`).**
1. Every stratum of the registry appears: as cells, or under `not_run` with its reason (`report-stratum-missing`).
2. Every cell of the pre-run notice appears with the same status (`report-status-drift`).
3. Every cell has one pooled phase ledger per arm and a ceilings reference evaluated on the rival's ledger.
4. Every fired kill gate has its record; every disqualification and voided cell is listed with its evidence.
5. Wording: under a locked adjudication label the two locked phrases do not occur anywhere in the rendering; a
   cell without the verdict `ten-fold` never renders the word for its class.
6. No ratio appears in the rendering that is not a `ReportedRatio` or a `DescriptiveRatio`.
7. The record passes the metric contract's test `check_report` (N00-19) over its cells and their campaigns; a
   violation refuses the build (`report-contract-violation`, listing the violations by letter). Three of the ten
   (a ratio without its interval, without the rival's freeze hash, a warm ratio without its crossover count)
   cannot arise in this record, because `ReportedRatio` cannot be constructed without those fields; the rest
   are the contract's own: a mission missing from a ratio, cold and warm pooled, failed amendments
   omitted, a resource column absent or unequal caps, a scoped claim kept after a false certificate, a ratio
   above the completion cap 1/q of its own counts, an open phase ledger, and the word "ten-fold" on a cell
   whose verdict is not `ten-fold` (which rule 5 also states).

**6. Rendering.** `frob-tenfold report build --gate <id>` writes `report.json` and a Markdown rendering generated
from it; the rendering is a pure function of the record (the kit's scorer regenerates it byte for byte). The
command, its assembly of the record and the rendered forms (Markdown and a static HTML page) are built in the
gate report bead N39b-14; this bead supplies the types, the descriptive tables and the completeness rules that
command enforces. Sentences about outcomes are produced by the outcome-rules module (N39b-05) from the verdict
records.

## Acceptance criteria

- [ ] INV-TENFOLD-08 holds as a property: every ratio object in a generated report validates as a complete
      `ReportedRatio`; removing any one field makes `report build` refuse.
- [ ] A warm ratio without S and N* cannot be constructed.
- [ ] Each descriptive table is produced for every cell, including `descriptive` and `withdrawn` cells.
- [ ] A registry stratum absent from both `cells` and `not_run` refuses the build.
- [ ] The rendering of a self-adjudicated report contains neither locked phrase; the rendering is byte-identical
      when regenerated from the record on a second machine.
- [ ] The seven limits of step 4 and the three no-authorization flags (all false) appear in every report.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- report::`
- `reported_ratio_complete_property`: 10³ generated reports; every ratio validates; field-deletion mutants refuse.
- `warm_requires_assets`.
- `curve_from_times`: times (700, 800, 900, 1,500, 2,100, censored) at H = 14,400 → F steps to 1/6, …, 5/6 and
  never reaches 1; completion 5 of 6.
- `zero_count_bound_printed`: 24 of 24 completed → miss-rate upper bound 0.1174 printed beside the zero.
- `conditional_times`: quartiles of the five accepted times; the count 5 printed.
- `per_phase_ratio`: the worked single pair → `train` 4,920/150 = 32.8; `compile` 540/12 = 45; `screen`
  0/96 = 0; `certify` and `synthesize` (0 ÷ 0) print `n/a`.
- `error_table_counts`: a campaign set with 2 rejections, 1 overturn and 1 missed withdrawal.
- `not_run_required`, `status_drift_refused`, `locked_words_absent`, `no_bare_ratio` (the renderer has no
  function that formats a rational with a multiplication sign outside the two ratio types).
- `render_is_pure`: same record → same bytes.
- `contract_violation_refuses_build`: a record whose cell reports R = 9 with completion 22 of 25 for arm A
  (cap 25/3) is refused with `report-contract-violation` naming violation (f).

### End-to-end script and logging

Covered by `scripts/e2e/tenfold_rehearsal.sh` (N39a-41): after scoring the rehearsal cells it runs
`frob-tenfold report build`, validates the record, regenerates the rendering twice and compares digests, deletes
a field from a ratio and expects the refusal, and greps the rendering for the locked phrases. Log lines carry the
report hash, the cell count, the count of ratio objects validated, each refusal, and the digest comparison.

### Known answers and negative controls

Known answers: the curve and completion figures above; 32.8 for the worked pair's `train` phase ratio. Negative
controls: a report builder that omits `descriptive` cells; a warm table that prints the limit ratio in the ratio
column; a rendering edited by hand (its digest no longer matches the record's regeneration); a ratio rendered
from the per-family table inside a verdict sentence (type error); a report that prints "ten-fold" for a
`measured` cell.

## Considerations

- The record is long by design: the per-pair table of a tournament of eleven strata has thousands of rows. It is
  a data file; the rendering paginates and says so.
- Transcripts and per-world outcomes are referenced by address and released only after every arm has closed.
- A report can be honest and still misleading if read selectively; the pre-run notice at the top and the
  `not_run` list are there so that what was *not* shown is on the first page.
- No private-scene data can appear: such data cannot enter a mission card.
