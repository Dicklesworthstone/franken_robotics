## Background

The ten-fold protocol is enforced by refusals: a freeze that comes too late is refused, a confirmatory cell that
cannot reach its verdict is refused, a verdict requested before its sample is complete is refused, a speed
comparison whose ceiling is below its goal is refused. The protocol's text states these in prose. The product
has a registry of numbered refusal codes for its verbs, but the ten-fold harness has no product verbs, and the
product's registry lists no code defined by the ten-fold protocol.

DESIGN: the harness therefore carries its own small registry of **refusal reasons**: stable kebab-case strings,
each with a meaning, a trigger and ranked repairs, used by the operator tool `frob-tenfold`, the scorer
`frob-tenfold-score` and every harness record that can say "refused". Where a reason is the harness-side form of
a refusal the product already registers, the row names that code, so that the two vocabularies stay aligned.
Reasons: tests and exit reviews need to assert *which* refusal occurred, not merely that something failed; and a
reason that is free text drifts.

Rejected: inventing new `FROB-REF-…` numbers here (the product registry has one owner and codes are never
reused); reusing product codes for harness conditions they do not describe.

## Scope

In: the registry file, its loader and its two-way consistency test; the rows for the first half of the protocol
(position, estimand, acceptance, suite, arms, phase ledger, statistics, ceilings); exit codes of the two harness
binaries. Out: the rows of the second half (see `needs`); any change to the product registry.

## Technical approach

**1. File and loader.** `crates/frob-conformance/registry/tenfold_refusals.toml`, one table per reason:
`[[reason]] id = "…"; meaning = "…"; trigger = "…"; repairs = ["…", "…"]; maps_to = "FROB-REF-…" | ""; exit = 3`.
The loader refuses duplicate or unknown ids at start-up. A refusal is emitted as
`{"refusal": {"reason": "<id>", "pointer": "<JSON pointer or record path>", "observed": …, "required": …,
"repairs": [...], "maps_to": "…"}}` on standard output, with the exit code of its row.

**2. Exit codes of `frob-tenfold` and `frob-tenfold-score` (DESIGN, aligned with the product's).** 0 completed;
2 completed with flags (for example a `ledger-open` run was built); 3 refused; 4 refused for budget or envelope;
9 integrity fault (a hash, signature or chain does not verify). 1 is never emitted on purpose.

**3. The reasons.** Repairs are ranked; "—" in the last column means no product code describes the condition.

**4. Consistency test.** A unit test collects every reason literal used in the harness source and every `id` in
the file and requires the two sets to be equal; a reason removed from code stays in the file marked `retired`
and is never reused.

## Acceptance criteria

- [ ] The registry file holds every reason above and loads; duplicate and unknown ids fail at start-up.
- [ ] The two-way consistency test passes; adding an unregistered reason literal to the harness fails it.
- [ ] Every refusal emitted by either binary has the JSON shape of step 1 and the exit code of its row.
- [ ] Rows that map to a product code quote that code's registered meaning correctly (checked against the
      product registry at build time; a missing product code fails the build).
- [ ] No row allocates a new product code.

## Test plan

### Unit tests

`cargo test -p frob-conformance --test tenfold -- refusal_registry::`
- `loads_and_unique`.
- `code_and_registry_agree` (both directions).
- `maps_to_exist`: every `maps_to` value is present in `registries/refusals.toml`.
- `exit_codes`: a sample of ten reasons, each provoked through its binary, returns the tabulated exit code.
- `shape`: emitted refusals parse against the refusal shape and carry at least one repair where the table has one.
- `retired_never_reused`.

### End-to-end script and logging

`scripts/e2e/tenfold_refusals.sh`: provokes one refusal from each row's first reason on rehearsal fixtures (a
record with a number-typed duration, a role conflict, a card of the wrong kind, an out-of-order sealing step, a
late freeze, a four-family confirmatory cell, a verdict before n, a ceiling below its goal, and so on) and
asserts reason, exit code and first repair with the shared helper's refusal assertion. Each line logs the
command, exit code, wall time, the reason, the pointer, the first repair and the product code it maps to.

### Known answers and negative controls

Known answers: the row count equals the number of distinct reason literals in the harness. Negative controls: a
refusal emitted as free text (the shape test fails); a reason reused with a new meaning; a mapping to a product
code whose meaning differs (the build-time check quotes both).

## Considerations

- OPEN (registry owner): whether the harness reasons that correspond to protocol rules a product user could also
  hit (for example `verdict-before-n`) deserve product codes. Default: no new codes; the mapping column is the
  bridge.
- The other unit of this chapter adds rows for disqualification, leaks, the kit and the population claim; the
  file is shared and the consistency test covers the union.
- Reason strings appear in gate records and exit reviews; renaming one after a gate has been recorded breaks
  citations, hence the never-reuse rule.
