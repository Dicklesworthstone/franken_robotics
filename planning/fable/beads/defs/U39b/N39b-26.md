## Background

In the ten-fold test an answer is accepted by an acceptance battery run in a simulator that is neutral between
the arms. The question which simulator that is, for each stratum of the mission suite, is open. It is recorded
in the program's open-question register together with the question of who the adjudicator is (as one item,
needed before any sealed world family exists, with its need date at M2). Owner of this half: the adjudicator
with the lead of the verification subsystem. It blocks the adjudicator-acceptance gate (GATE-TENFOLD-05).

Fail-closed default that holds until it is decided: a pinned incumbent CPU engine that no arm trains in; where
it cannot represent the mission, cross-home adjudication, labelled (an answer must pass in the highest-trust
tier of both arms, run by the adjudicator).

The four conditions a candidate must meet (DESIGN): neither arm used it for training, tuning or screening on
that stratum; its contact model was derived independently of both arms; it runs deterministically on a CPU; it
is pinned by revision. Default candidate: Drake at a pinned release (FACT from the source register: a CPU
multibody engine with its own convex contact solver).

## Scope

In: the decision OPEN-TENFOLD-1 itself: the candidate table per stratum with the evidence for the four
conditions, the representability probes that inform it, the decision rule, the simulator's part of the one
decision record, and the list handed to the kill gate that covers the no-candidate case.

Out, with the bead that has it: who adjudicates (N39b-27, the other half of the same owner question); the owner
packet of OPEN-PROG-2 (N41-06, a dependency of this bead): the page on which this table is put to the owner, the
register rows, the configuration record `registries/tenfold/adjudication.toml` that projects this decision per
stratum, and its validator (which re-checks, from the arms' manifests, that no arm used the named engine on the
stratum); the acceptance measurement of the chosen simulator, GATE-TENFOLD-05 (the adjudication beads); the
fallback decision KILL-TENFOLD-ADJ (N39a-11).

## Technical approach

1. **Strata to decide.** For the partial gate: `legged-quad`, `wheeled`, `envelope`, `sensing`. For the
   tournament also: `legged-biped`, `tracked`, `hybrid`, `rebody`, `failure`, `throughput`, and `facility` if it
   runs. Family-answer strata (`envelope`) use direct evaluation tools as well as, or instead of, a dynamic
   simulator; the decision names those tools (exact rational evaluation at probe points; an SMT or interval
   tool on the raw mission statement).
2. **Candidate table per stratum.** Rows: the default candidate and at least one alternative that meets the
   four conditions. Columns: the four conditions (with evidence: arm manifests and tuning logs for the first;
   documentation of the contact model for the second; a twice-run digest for the third; the pin for the
   fourth); representability of each feature the stratum's missions need.
3. **Representability probes** (each a small scripted check with a known outcome): stairs, gaps, stepping
   stones and rubble as terrain; a liquid film with reduced friction on a patch; a tracked running gear on
   stairs and soft ground; wheels on a ramp with payload; a moving surface (a conveyor); a door closer and a
   castor chair for interiors; sensor timing through an observation interface with the mission's clocks. A
   probe fails if the simulator cannot express the element or reproduces a planted answer wrongly.
   DESIGN: at M2 the probes are hand-built fixtures in the candidate's own model and scene format, labelled
   `synthetic` and stored with their planted answers under `fixtures/tenfold/adjsim_probes/<candidate>/`. They
   are not run through the neutral exchange description or on development missions, because both are built at
   M3 for the simulator this decision names: the adapter and the description (N39a-08) depend on this bead,
   and the development missions exist only with the suite. When the adapter exists it re-runs every probe as
   a model exported through the description; a probe that passed natively and fails through the description
   is a defect of the description, and one that fails both ways removes the candidate from that stratum and
   reopens this decision for it.
4. **Decision rule.** Per stratum, the first candidate that meets the four conditions and passes every probe the
   stratum needs is named, with its revision. If an arm uses the default candidate as a tool on a stratum, the
   adjudicator substitutes another engine that meets the conditions. If no candidate passes, the stratum is
   referred to the kill gate KILL-TENFOLD-ADJ (cross-home adjudication, labelled; failing that, `descriptive`).
5. **Record.** Part 2 ("the simulator per stratum") of the one decision record of the owner question,
   `docs/adr/ADR-PROG-02-adjudication.md`, with one section per gate (the partial gate; the tournament): the
   table, the probe logs by digest, the named simulator or tools per stratum, the pin, and the date; entered
   before the suite hash of that gate is committed. Part 1 of the same file is the party, written by N39b-27.
   DESIGN: one file for both halves, because the register carries them as one question (OPEN-PROG-2). The
   configuration record of N41-06 is generated from this file: the machine-read content of part 2 is one
   fenced `toml` block whose first line is `# part 2: simulators`, with one table per gate and stratum
   holding the fields of that record (`stratum`, `mode`, `simulator`, `pin`, `container`, `tools`,
   `provisional`, `kill_adr`); after writing it this bead runs `frob-tenfold adjudication generate` and
   asserts that the record's strata equal the block.

## Acceptance criteria

- [ ] Every stratum of the partial gate has a named adjudicating simulator (or tools) with a pin, or a referral
      to the fallback, recorded before any sealed world family for that stratum is written.
- [ ] The candidate table has evidence for each of the four conditions; a candidate used by an arm on the
      stratum is rejected.
- [ ] Each representability probe has a fixture in the candidate's own format, labelled `synthetic`, and a log with its planted answer and the outcome; the list of probes is handed to the adapter bead N39a-08 for the re-run through the exchange description.
- [ ] The default is recorded as in force for any stratum not yet decided.

## Test plan

### Unit tests

`cargo test -p frob-conformance tenfold::adjsim`: `four_conditions_all_required`; `probe_set_by_stratum` (the
`tracked` stratum requires the track and stair probes; `envelope` requires none of the dynamic probes);
`undecided_stratum_reports_default`; `candidate_named_in_arm_manifest_rejected` (a freeze or tuning log naming
the candidate's identity on the stratum removes it from that stratum's table, not from others);
`first_passing_candidate_named` (rule order is the table order); `no_candidate_refers_to_kill_gate` (the
stratum is listed for KILL-TENFOLD-ADJ, never silently given the default); `record_precedes_suite_hash` (a
record dated after the gate's suite-hash entry is refused).

### End-to-end script and logging

`scripts/e2e/tenfold_adjsim_probes.sh` (bead N39b-26): runs each probe fixture on the candidate in the
candidate's own input format (through the out-of-process oracle harness, BD-039), twice, asserting equal
digests (determinism) and the planted outcomes. Header `bead=N39b-26
milestone=M2 labels=tenfold,e2e gates=GATE-TENFOLD-05 seed=390126 plants=nondeterministic-threads,
arm-used-candidate`. Logged as NDJSON through the shared helper, one line per event with `ts`, `script`, `bead`,
`step`, `event`, the exact command, exit code and wall time: the candidate's pin and container digest; per probe
its stratum, element, planted answer, observed outcome and the two run digests; per stratum the four conditions
with the digest of each piece of evidence and the named simulator or the referral; on failure the first
differing value and the probe's input path. The `summary` lists probes passed and failed, plants caught, and
`gates: [{id: "GATE-TENFOLD-05", measured_ok, controls_caught}]` with `gates_claimable: false` (the acceptance
measurement belongs to the adjudication beads). Out-of-process only; the candidate is never linked.

### Known answers and negative controls

Known answers: each probe's planted answer (for example a block on a 30° incline with friction coefficient 0.5
slides, with 0.7 it holds, since tan 30° = 0.577). Negative controls: a candidate build with a nondeterministic
thread setting must fail the twice-run digest check; a planted arm manifest that names the candidate on
`wheeled` must remove it from that stratum's table.

## Considerations

- Acceptance in any simulator is not reality; every report prints `reality: no-claim`.
- A candidate that is also one of the rival's possible engines on some stratum can still adjudicate the strata
  where no arm uses it.
- Licences: the simulator's licence must permit publishing results obtained with it (N39b-32).
- What would reopen the decision: an arm's freeze manifest that names the chosen simulator on a stratum.
