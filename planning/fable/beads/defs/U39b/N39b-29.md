## Background

The gates of the ten-fold test are campaigns of many long runs. By the program's machine rule nothing above the
default compute class (16 GiB of memory, 8 cores, one hour of wall time, one device) runs without the owner's
written approval. The partial gate and the tournament are far above it, so each needs an approved class: a
campaign class for each run, and the pretraining class where an arm builds a standing asset (for example a
family policy pretrained before any clock starts). The open question is owned by the project owner and blocks
both program gates. Fail-closed default: nothing above the default class runs, the gate is recorded as
`not run`, and M3 does not exit.

## Scope

In: the content of the decision OPEN-TENFOLD-4 and its record (the ADR `ADR-PROG-16` and its supporting file
`decisions/OPEN-TENFOLD-4.md`); the cost arithmetic; the request document derived from measured baseline times;
the options; what runs under each answer; scheduling to the approved cap and the refusal of a campaign beyond it.

Out, and where it is: the early envelope notice at the M0 exit (from this bead's planning values, before any
baseline exists) and the one-page request at the M1 exit; the generated configuration record
`registries/tenfold/owner-inputs.toml` whose `[envelope]` table is a projection of this decision; the M3 exit
check that reads the partial gate's record (N41-15, on which this bead depends for the record format; the rule
that check applies is stated in step 6 below in the same words); the classes' definition (the performance
program); the runs.

## Technical approach

1. **Cost of a cell.** A cell with m families, c campaigns per family, deadline H and arms X costs
   m·c·Σ_X E[min(T_X, H)] device-hours. Worst case, when every run is censored: m·c·|arms|·H. With m = 24,
   c = 1, three arms and H = 4 h: 24 × 3 × 4 = 288 device-hours per cell. HYPOTHESIS: about 70 device-hours per
   design cell at restricted mean times near 1.5 h, 1.0 h and 0.4 h for arms B, C and A (24 × 2.9 = 69.6).
2. **Other items of the request.** Advocate tuning: at least 40 device-hours per stratum. Acceptance batteries
   (the `adjudicate` phase) in the adjudicating simulator on CPU cores: n sealed world clusters per submission,
   estimated from development missions. Standing assets: each arm's declared build cost S, under the
   pretraining class where it is a pretrained policy. The rehearsal. Re-runs of pairs after a harness fault
   (at most one per pair). Level 2 of the replication kit at the tournament.
3. **The partial gate's request (four cells).** Expected and worst case per cell from the measured incumbent
   baseline (the rival's restricted mean times on development missions) and from our own estimates with their
   intervals; totals; the calendar time on one machine with two cards at one device per campaign (the primary
   result uses matched devices: one RTX 4090 and the same number of CPU cores per campaign, arms interleaved).
   Illustration with the planning values: two design cells at about 70 device-hours and two family cells
   (CPU-bound, counted in core-hours), plus 160 device-hours of advocate tuning, is about 300 device-hours
   expected and 4 × 288 + 160 = 1,312 in the worst case.
4. **The tournament's request.** The same arithmetic per stratum run, with 24 families per cell by default and at
   least 32 for a cell that declares a population result, on both machines, as a campaign class per campaign
   and a pretraining class where an arm pretrains. A run under the pretraining class is approved per run, with
   its ceiling and its kill rule written first. If the tournament's request is not approved, fewer strata run,
   and each omitted stratum is declared `not run` with the reason.
5. **Options for the owner.** (a) Approve the request as computed. (b) Approve a cap; the adjudicator then
   chooses, before sealing, which cells run, and each omitted cell or stratum is declared `not run` with the
   reason. (c) Approve only CPU strata (`envelope`, `sensing`) at the class their campaigns need: the design
   cells are `not run`. (d) No approval: the default.
6. **What each answer means for the gate.** GATE-TENFOLD-06 passes when every cell *in scope* has its record;
   under (b) and (c) the scope is what was approved and the record lists the rest as `not run`. A run that would
   exceed the class in force is refused before it starts (FROB-REF-761); there is no partial credit for a
   truncated campaign.
   Under (d), the default (DESIGN; the same rule is stated in N41-15, which owns the M3 exit check). The
   ten-fold chapter gives the default as "nothing above the default class runs, the gate is recorded as
   `not run`, and M3 does not exit"; the work-package table gives the consequence of no approval as "the partial
   gate runs its CPU strata". The two are reconciled as follows. With no approval, a campaign runs only if it
   fits the default class (16 GiB, 8 cores, one hour, one device); a campaign above it is refused before it
   starts (`FROB-REF-761`). The CPU strata (`envelope`, `sensing`) run whatever campaigns fit; the device strata
   are `not run`, with the reason. If no stratum has a record, GATE-TENFOLD-06 is `not run` and M3 does not
   exit. If the CPU strata are recorded and the device strata are `not run` with the reason, that is a recordable
   outcome and M3 may exit on it. Reason: this keeps both statements of the plan true, adds no capability under a
   default, and never lets a milestone exit on a gate with no record. Option (c) differs from (d) only in the
   class the CPU strata may use: under (c) their campaigns may exceed the default class up to what was approved.
7. **Record.** `decisions/OPEN-TENFOLD-4.md` with the request, the option chosen, the approved device-hours per
   gate and per class, any cap, and the date. The harness reads the approved totals and stops scheduling new
   campaigns at the cap (campaigns in progress run to their end or to H).
   One decision has one record of authority (DESIGN, the same statement in N41-15 and in the four
   decision beads N39b-28, N39b-29, N39b-31 and N39b-33): the ADR that the open-question register requires, which
   the register row's `adr` field cites. The ADRs are `ADR-PROG-15` (OPEN-TENFOLD-3, advocates), `ADR-PROG-16`
   (OPEN-TENFOLD-4, envelope), `ADR-PROG-17` (OPEN-TENFOLD-6, agent) and `ADR-PROG-18` (OPEN-TENFOLD-8, thresholds),
   under `docs/adr/`. The file `decisions/OPEN-TENFOLD-<n>.md` is the ADR's supporting file: the request, the
   options, the figures and the evidence. The ADR cites it by path and digest, and it states no decision that the
   ADR lacks. Reason: the register's rule is that a decision or a default is an ADR, while the request and its
   arithmetic are too long for one and change until the decision is taken.
   This bead writes `ADR-PROG-16` when the owner decides; if the deadline is reached first, the register's default
   writer writes it with the default above. Either way the `[envelope]` table of the configuration record
   (`partial_gate`, `tournament`, `pretraining`, `approved_device_hours`) is regenerated from it by N41-15's
   generator, and that table is where the harness reads the approved totals.
8. **Where the ruling is enforced (one approval, two readers).** Admission of a campaign is not the harness's:
   every run that spends envelope resources passes the admission of N36-20 before it starts, arm A's jobs
   through the run verbs under the campaign's launcher token and an incumbent arm's processes through
   `frob-launch --scope <scope> …`, and that admission reads the class in force for the run's scope from the
   approved, unexpired request row of `registries/compute_envelope.toml` (the one record of envelope classes
   and approvals: its schema and loader are N21c-35's, its request rows N44-01's). The rows of this decision
   (DESIGN, from the plan, which makes OPEN-TENFOLD-4 the envelope of both gates, §39.19):
   - *The partial gate's campaigns* have a row of their own, which this bead files under N44-01's rule for a
     new request (the next free identifier from R29): `packages = ["WP-60"]`, `scope` the partial gate's
     campaigns, `admits = ["campaign:tenfold-M3-partial"]`, class E2 amended with the two limits below,
     `open_question = "OPEN-TENFOLD-4"`, `not_approved_fallback` "the partial gate runs its CPU strata". They
     are not admitted under R6, although the plan's table names them in that row: R6 is also the rank-agreement
     pilot's row and is ruled by N41-08 on OPEN-PROG-4 (variant A amends it to E1 with a ceiling of at most 12
     device-hours), and one row carries one ruling, one class and one cumulative limit, so the gate's
     campaigns would draw on the pilot's budget and be refused once it was spent.
   - *The tournament's campaigns* are admitted by R9 (packages WP-76 and WP-77), whose ruling is this
     decision's: R9's `open_question` is OPEN-TENFOLD-4 and its `admits` holds
     `campaign:tenfold-M7-tournament`.
   - *A standing asset* that an arm builds by pretraining has one per-run row under the pretraining class (a
     `pretrain:<run>` scope), with its ceiling and kill rule written first.
   The scopes are `campaign:` scopes because N36-20's needed class gives a `gate:` scope at most E1 (two hours
   per run, 12 device-hours per gate) and gives E2 only to a campaign scope: a campaign scoped to the gate
   would be refused with `FROB-REF-761` at any approval. The owner's ruling on OPEN-TENFOLD-4 is entered as
   the ruling of those rows (`status` `approved`, `amended` or `declined`; `decision` the path of
   `ADR-PROG-16`; `limits` as approved): with a row left `requested` the class in force for its scope stays
   E0, and every campaign above it is refused with `FROB-REF-761` whatever the ADR says. The request of steps
   3 and 4 states, per row, the two limits the campaigns need and the class defaults do not give: a wall time
   per run of at least the largest deadline H of the gate's strata (E2's per-run wall time is otherwise
   read as E1's two hours, N36-20), and the cumulative device-hours of the gate (the expected and worst-case
   totals of step 3, against E2's 48); both are amendments the owner approves with the row. Campaigns are
   launched under the scope the approved row admits, read from its `admits` and never typed. The `[envelope]`
   table is the harness's copy of the same totals, used to plan the schedule and to stop scheduling at the cap:
   `approved_device_hours` of a gate must equal the cumulative limit of the approved row that admits that
   gate's scope, and a difference is refused before the first campaign is scheduled, with the harness reason
   `envelope-not-approved` (exit 4, N39-REF) naming both values.

## Acceptance criteria

- [ ] The request exists with expected and worst-case device-hours per cell and in total, derived from measured
      baseline times, before the partial gate's suite hash is committed.
- [ ] The decision or the default is recorded; the gate's scope in the registration equals what was approved.
- [ ] A campaign scheduled beyond the approved total is refused with FROB-REF-761 (exit 4) before it starts, by
      the admission of N36-20 under the scope the approved row admits.
- [ ] The ruling is entered in the request rows of `registries/compute_envelope.toml` that admit the gates'
      campaign scopes (the partial gate's own row, filed by this bead; R9; and a per-run row for each standing
      asset), with the per-run wall time and the cumulative device-hours approved, and in no other row (R6 is
      N41-08's); an `[envelope]` table whose `approved_device_hours` differs from the approved row's limit is
      refused with `envelope-not-approved` before any campaign is scheduled.
- [ ] The scope list written for the registration marks every omitted cell `not run` with the reason, in the
      form the report prints; that the report shows it is asserted where the report exists (step `envelope` of
      N39b-12's rehearsal).

## Test plan

### Unit tests

`cargo test -p frob-conformance tenfold::envelope`: `worst_case_cell` (24, 1, 3 arms, 4 h: 288);
`expected_cell` (1.5, 1.0, 0.4 h: 69.6); `cap_stops_scheduling_not_running`; `unapproved_scope_is_not_run`;
`population_cell_cost_scales_with_m` (32 families: 384 worst case); `default_runs_only_campaigns_in_default_class`
(with no approval, a CPU-stratum campaign declared at 8 cores and one hour is scheduled and one declared at 4 h
is refused with FROB-REF-761); `record_must_equal_register_row` (an `[envelope]` table with 300 approved
device-hours against an approved row with a cumulative limit of 300 passes; against 48, or against a row still
`requested`, it is refused with `envelope-not-approved`, exit 4, naming both values);
`run_longer_than_row_allows_is_refused` (a row approved with 7,200 s per run and a stratum deadline of 14,400 s:
the request check reports the row as insufficient before any campaign is scheduled).

### End-to-end script and logging

`scripts/e2e/tenfold_envelope.sh`, owned by this bead and built only on its dependencies (header `bead=N39b-29
milestone=M3 labels=tenfold,e2e gates=GATE-TENFOLD-06,GATE-TENFOLD-07 seed=392929 needs=cpu
plants=row-left-requested,record-above-row,start-past-cap`), under a scratch registry root
(`e2e_registries_scratch`, so the run can claim no gate): (1) `FROB_TEST_SEED=392929 cargo test -p
frob-conformance tenfold::envelope`; (2) with the default registry, `frob-launch --scope
campaign:tenfold-M3-partial --devices 1 --cores 8 --mem-gib 1 --wall-s 3600 -- sleep 1` is admitted (an E0
job) and the same launch with `--wall-s 14400` exits 4 with `FROB-REF-761` and starts no process; (3) with the
partial gate's row filed and approved in the scratch registry for `campaign:tenfold-M3-partial` (class E2,
14,400 s per run, a cumulative limit of 3 device-hours), and a scratch `ADR-PROG-16` whose `[envelope]` table is
generated with the same total: a launch declaring `--wall-s 7200` is decided `admitted` by the scratch approval
and, the class of record being E0, is held and not started (exit 4 with `scratch_verdict: "admitted"`, N36-20
step 5); one declaring `--wall-s 14400` (4 device-hours against 3) is refused with `FROB-REF-761`, pointer
`device_hours`; a launch declaring `--wall-s 10800` under `gate:GATE-TENFOLD-06` is refused with
`FROB-REF-761` and the needed class `above every class` (a gate scope reaches at most E1); and the schedule
this bead plans for a two-cell `synthetic` gate stops at the cap and lists the omitted cell `not run` with the
reason. The
scratch root keeps every decision deterministic: nothing above E0 starts, so no assertion depends on what a
run consumed. (4) The plants: the row left `requested` while the ADR approves (every launch above E0 refused
without `scratch_verdict: "admitted"`, and the request check names the row), an `[envelope]` total above the
row's limit (`envelope-not-approved`, exit 4), and a harness build under `--features gauntlet-mutations` that
schedules a campaign whose declared worst case exceeds the remaining budget (caught by the admission's
refusal, pointer `device_hours`). Logged as NDJSON through the STD-E2E helper (`ts`, `script`, `bead`, `step`,
`event`, exact command line, exit code, wall time, seed): estimated and approved device-seconds as `metric`
lines against the cap, each admission decision with its scope, needed class, class in force and
`scratch_verdict`, each refusal with its code, pointer, exit code and first repair, the digests of the scratch
ADR, of the configuration record and of the registry row, each plant as a `negative-control` assertion with `caught`;
on failure the first differing value and the scratch paths; a final `summary` with assertion counts and
`gates_claimable: false`. Later, step `envelope` of `scripts/e2e/tenfold_partial_gate.sh` (N39b-12, which
depends on this bead) plants an approval of half the rehearsal's cost and asserts the stop at the cap, the
refusal and the `not run` line of the rehearsal report.

### Known answers and negative controls

Known answers: 288; 69.6; 1,312. Negative control: a harness that starts a campaign whose worst case exceeds the
remaining approved budget must be caught by `cap_stops_scheduling_not_running`.

## Considerations

- The classes themselves are a proposal awaiting ratification; if their limits change, the request is restated.
- Raising a deadline H to satisfy the horizon cap raises the worst case in proportion.
- The estimate of our own arm's time before M3 is a planning value; its interval is printed, not a point.
