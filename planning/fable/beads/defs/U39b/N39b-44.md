## Background

The program bets that its mechanisms need its own engine (the engine-necessity bet). The opposite hypothesis is
live and untested: that a thin layer over an incumbent simulator would do. Whether it would is decided by a
measured recovery ratio at the partial gate and the tournament, not by a count of feature gaps. But one fact can
be established much earlier and cheaply. FACT (source register): in the incumbent documents read, run-to-run
determinism, heterogeneous worlds and the fastest solver sit on different solver paths, so each is available
and their conjunction is not shown. Arm W, the composed incumbent, is therefore built as *one pipeline*, on one
fixed-topology brief and one mixed-topology contact-rich brief, before this system's arm exists, and the
property that binds when all are demanded at once is recorded. One expensive incompatibility can sink the layer;
several rarely exercised gaps may leave it competitive. Feature counts decide neither.

This is a condition of GATE-TENFOLD-13: the one-receipt pipeline for arm W is built and its binding property
recorded before any engine-internal work package beyond M2 is funded. The bead therefore sits in M2 although
the gate's recovery ratios are first recorded at M3: its record must exist when M3's packages are funded.

"One receipt" means that a single recorded run of a single pipeline exhibits all the demanded properties
together; separate demonstrations of each property on different solver paths do not count.

## Scope

In: the pipeline on incumbent engines; the two briefs; the property matrix; the binding-property record; the
funding condition. Out: the sealed-suite arm W (the rival-arm beads build on this); recovery ratios (N39b-43);
ablations (N39b-45). Work here is on incumbent tools out of process, by sessions with the rival-advocate role;
nothing of it enters the product's dependency graph.

## Technical approach

1. **Portable methods to layer** (each implemented with the incumbent's own facilities where it has them):
   native state restore and forks; per-topology buckets, or the engine's own heterogeneous solver; a sampling
   controller, or a multi-embodiment prior with checkpoint resume; racing and stopping (an anytime-valid
   elimination rule from the published literature); importance-weighted failure search; a second engine as
   referee for promoted candidates.
2. **Demanded properties** (each must hold in the same run): P1 run-to-run determinism (a repeated run gives
   identical state digests); P2 heterogeneous worlds in one batch (different topologies); P3 the engine's
   fastest solver path; P4 state restore and fork of a single world from a batch; P5 per-world model parameters
   in one batch; P6 replay of one world outside its batch; P7 a referee check on a second engine with a
   recorded discrepancy.
3. **Briefs.** (a) Fixed topology: a quadruped family with parametric variants only (P2 is vacuous, the rest
   apply). (b) Mixed topology, contact-rich: three-, four- and five-legged bodies in one batch on rough ground.
   Both are development briefs with public cards; a small design loop (propose, screen, race, promote, check)
   is run end to end without an agent, scripted, so that the result does not depend on agent behaviour.
4. **Property matrix.** For each engine candidate and brief: each property alone (available, with its solver
   path and settings); each pair; all together. An entry is `holds`, `fails` (with the error or the observed
   violation, for example differing digests) or `not expressible`. Throughput (world-steps per second, under a
   complete disclosure block) is recorded for the fastest path alone and for the all-together configuration.
5. **The binding property.** If the conjunction `fails` or is `not expressible`: the minimal set of properties
   whose removal makes the rest hold, and for each such set the throughput of the remainder. If the conjunction
   holds: the property whose requirement costs the most throughput relative to the fastest path (the ratio
   all-together ÷ fastest, and the same with each property dropped in turn). The record names one binding
   property per brief, with numbers.
6. **The receipt.** One run record per brief in which the all-together configuration (or the largest feasible
   subset) executes the scripted loop: digests of two repeats (P1), the batch composition (P2), the solver path
   (P3), a fork and its divergence from its parent under one changed action (P4), the parameter table (P5), a
   single-world replay digest equal to its in-batch digest (P6), the referee discrepancy (P7), the phase
   ledger, and the disclosure block.
7. **Funding condition.** The record's digest is entered in the project ledger. An engine-internal work package
   beyond M2 (one whose justification is a property an incumbent layer lacks) must cite the binding property
   this record names, or another measured gap; a package citing an engine-internal gap that this record shows
   the incumbent closes is not funded on that ground.
8. **Two unverified gaps checked here.** Replay of one world outside its batch (P6) and solver-internal
   certificates (whether the incumbent's solver exposes a residual or dual certificate a checker could verify)
   are recorded as verified present, verified absent, or still unverified with the reason.

9. **Admission and metering.** Every incumbent run of the pipeline is out-of-process work that spends device
   time, so it is started through `frob-launch` (N36-20's command over `run_admitted`, reached through BD-216)
   under scope `gate:GATE-TENFOLD-13` with a declared demand (devices, cores, memory, wall time): a run above the
   class in force is refused with `FROB-REF-761` and its matrix entry is `not run` with that reason, never
   `fails`; each admitted run leaves one `envelope_meter` row, and the receipt cites the meter rows of its runs.
   A run started any other way is not metered and is not evidence. Under the default class E0 (one device, eight
   cores, 16 GiB, one hour per run) both briefs' runs are sized to fit, one device each; no row of N44-01's register
   admits GATE-TENFOLD-13 above E0 today, so a run that needs more is recorded `not run: no envelope` until such a
   row is filed and approved, and the record says which entries that leaves open.

Falsifier of the pilot reading: the all-together configuration holds on both briefs within 0.8 of the fastest
path's throughput. Then no engine-internal property is shown to bind, the expected ratio against the composed
incumbent on such missions is near one, and engine-internal packages need another justification.

## Acceptance criteria

- [ ] One pipeline exists on at least one incumbent engine and runs both briefs' scripted loops.
- [ ] The property matrix is complete for both briefs, each entry with evidence; throughput figures carry
      complete disclosure blocks.
- [ ] A binding property is named per brief with its numbers, or the falsifier is recorded as holding.
- [ ] The two unverified gaps have a recorded status.
- [ ] The record's digest is in the ledger before the M2 exit review, and the funding check refuses a planted
      engine-internal package that cites no measured gap.

## Test plan

### Unit tests

`cargo test -p frob-conformance tenfold::onereceipt`: `matrix_requires_all_pairs`;
`binding_is_minimal_removal_set` (conjunction fails; removing P1 alone restores it: binding property P1);
`binding_by_cost_when_conjunction_holds` (fastest 2.0 M, all-together 1.1 M, without P1 1.9 M: binding P1,
ratio 0.55); `falsifier_at_point_eight`; `funding_check_requires_measured_gap`; `unmetered_run_is_not_evidence`
(a matrix entry whose run cites no `envelope_meter` row is rejected; a run refused with `FROB-REF-761` is `not
run`, never `fails`).

### End-to-end script and logging

`scripts/e2e/tenfold_one_receipt.sh` (owned by this bead; sources the shared end-to-end helper; seed-explicit;
needs `cuda`; incumbents out of process, each run through `frob-launch --scope gate:GATE-TENFOLD-13 …`): builds
the pipeline environment from the pins, runs each property alone, pairwise and together on both briefs, repeats
the all-together run for P1, and writes the receipt. `E2E_SMALL=1` runs brief (a) at 64 worlds. NDJSON to
`target/e2e-logs/tenfold_one_receipt/<utc-timestamp>.ndjson` with a transcript beside it; every line has `ts`,
`script`, `bead`, `step`, `event`, the exact command line, exit code, wall time and the evidence block; logged:
each matrix entry as an `assert` or a recorded failure with the engine, brief, property set and solver path;
throughput `metric` lines in world-steps/s with their decimation and disclosure-block identifier; each run's
meter row (scope, device-seconds) and any `FROB-REF-761` refusal as a `refusal` line; the two repeat digests; the
receipt's digest; on failure the first property whose evidence is missing and the run paths. A final `summary`
counts assertions, names the binding property per brief and `gates: ["GATE-TENFOLD-13"]`.

### Known answers and negative controls

Known answer (FACT to be re-read at the audit): one incumbent's mixed batch of three-, four- and five-legged
bodies runs at 0.86 of the harmonic mean of its homogeneous rates, on a solver that is not deterministic and is
slower than its framework's reduced-coordinate solvers. Negative controls: a "receipt" assembled from two
different runs (rejected: the run identifiers differ); a determinism claim from a single run (rejected: two
repeats are required); a throughput figure without its disclosure block.

## Considerations

- Incumbents move quickly; the record is dated and pinned, and is refreshed at the tournament's audit.
- The scripted loop is deliberately agent-free; agent-driven use of arm W is measured later with the common
  agent.
- A layer can be competitive with the conjunction failing if the failing property is rarely needed; the record
  therefore also states how often each brief's loop actually used each property.
