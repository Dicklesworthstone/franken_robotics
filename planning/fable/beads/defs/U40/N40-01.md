## Background

A **gate** in this program is a named, numbered condition with a threshold: a foundation may be used only after its
*admission gate* (`INT-…`) has a record; a capability counts only after its *convergence gate* (`GATE-…`) has one; a
bet is abandoned by a *kill gate* (`KILL-…`, printed with ✖) whose trigger and fallback are written before the
measurement; and a handful of *program gates* decide whether the program continues as planned. The gate register is
the single list of all of them. It is data: `registries/gates.toml`, one record per gate, and every printed table (the
README's honest-status table, the register's own tables, the milestone exit reports, the release rubric, the
dashboard's gate view) is generated from that file and from nothing else.

This bead fixes what a record is and the nine rules every record obeys. It exists because the sibling projects showed
how a program can look finished when it is not: gates that were never run printed as green, a gate was re-scoped
after its measurement came in low, and the session that built a capability also declared it passed. The rules below
make each of those states unrepresentable or refused at write time. DESIGN decisions and the alternatives rejected:

- *One file, generated views* (ADR-GAUNT-02: registries are data and the document is their printout). Rejected: a
  hand-edited status table, because a hand-edited table drifts from the tests that are supposed to back it.
- *No verb and no `xtask` subcommand writes a gate* (ADR-GAUNT-01). A tier of the verification harness is a test
  target of `frob-conformance`, run as `cargo test -p frob-conformance --test <tier> -- <gate or row>`; the run writes
  a hash-named receipt; a recording session then enters the row that cites the receipt. Rejected: a `frob gate pass`
  verb, because a harness driven through the surface it judges is a path to self-certification, and `xtask` holds
  exactly six checks, runs no physics and records no gate.
- *A missing measurement is a status of its own.* Rejected: a boolean `passed`, which cannot tell "not run" from
  "failed" and tempts a default of true.

Terms: a **negative control** is a planted defect that the gate's test must catch (registry
`frob-conformance/registry/controls.toml`, identifiers `NC-nnnn`); a **receipt** is the hash-named output file of a
harness run; the **artifact graph** is the content-addressed graph of claims, evidence and executions behind
`frob evidence trace`; a **fresh-context session** is an agent session that did not implement the capability.

## Scope

In: the register layer of the one schema `frob.gates/1`: the fields added to the base record (`kind`, `consumers`,
`recurring`, `needs`, `blocks_exit`; on a part `scope`, `commit`, `command`, `receipt`, `fingerprint`, `seed`, `detail`; the
admission and kill fields); the printed forms of the statuses; the nine rules as validation; the ten write-time
refusals; the committed home of the receipt files a part cites (`receipts/gates/<hash>.json`, step 1); the loader,
the validator and the write path, which are the only place a cross-field rule of a gate record is checked.
Out, with the bead that has it: the base record (N38b-18, the Gauntlet's status-accounting bead, on which this bead
depends): the base fields `id`, `claim`, `claim_id`, `section`, `threshold`, `milestone`, `tier`, `controls` and,
on a part, `milestone`, `status`, `measured`, `evidence`, `recorded`; the meaning of each; the closed sets of claim
kinds and statuses as the types `Claim` and `Status`; the statement of the four conditions under which `pass` is
refused and of each status's rule, which this bead's validator implements and tests; the plan-time count
assertion. There is one schema file: N38b-18 writes it with the base fields and this bead adds its fields to the
same file. Also out: the rows themselves (N40-02, N40-10), kill-gate decision records and amendments (N40-03), the
exit query (N40-04), the README table generator (seed BD-002), the negative-control registry (seed BD-025), the
artifact graph (seed BD-095). The file's top-level tables other than `[[gate]]` are added to the same schema by the
bead that defines each, additively (a file without them still loads; inside one, an unknown field fails the load):
`[[amendment]]` (N40-03), `[[shared_fixture]]` and `[[related_threshold]]` (N40-08), `[[fallback_exit]]` (N40-32),
`[[variant]]` (N40-33, used by N40-34). An unknown top-level table fails the load.

## Technical approach

**1. The record (DESIGN; the base fields are the Gauntlet chapter's, the fields marked ＋ are added here).**

```toml
[[gate]]
id         = "GATE-KIN-04"
kind       = "convergence"         # ＋ admission | convergence | program | kill
claim      = "known-answer"        # proof | known-answer | parity | fidelity | design-comparison | reality | performance
claim_id   = "clm:…"               # the claim identifier the PASS rests on; resolves in the artifact graph
section    = "16.17"               # the defining subsection: its owner (rule 9)
consumers  = []                    # ＋ other subsections that state the same gate from their side
threshold  = "…"                   # the brief; the full criterion is the defining bead's
milestone  = "M1"                  # the earliest milestone (rule 6)
recurring  = false                 # ＋ true for the gates of rule 8
needs      = "simulator"           # ＋ simulator | import-lane (a bench, a board, a scan, real-robot data or a human panel)
blocks_exit = true                 # ＋ false only for the five sibling admission gates (pilots off every critical path)
tier       = ["G1:host"]
controls   = ["NC-0412"]           # registered negative controls; empty forbids pass
[[gate.part]]                      # ＋ one per milestone at which a part is due; a single-part gate has one
milestone  = "M1"
scope      = "referee rows"
status     = "not-run"             # not-run | pass | fail | killed | blocked | no-claim | superseded
measured   = ""                    # the value with unit and interval, or the count; never the target
commit     = ""                    # ＋ commit of this repository
command    = ""                    # ＋ the exact command line
receipt    = ""                    # ＋ BLAKE3 hash of the receipt file, committed as receipts/gates/<hash>.json
fingerprint = ""                   # ＋ hardware fingerprint; with the seed, required by the definition of "implemented"
seed       = ""
evidence   = []                    # ledger sequence numbers and trace identifiers
recorded   = { date = "", session = "", implemented_by = "" }
detail     = ""                    # ＋ for killed: kill gate and fallback; for blocked: the OPEN identifier
```

Admission rows carry `foundation` and `first_needed` and are mirrored in `DEPENDENCY_ADMISSION.md`. Kill rows carry
`trigger`, `fallback`, `decided`, `mode`, `reads` and `decision` (and, where they apply, `reread` and
`scope_kind`), with the owner in `section` and the consumer chapters in `consumers`, as for every gate (N40-03). A
kill row decides and measures nothing, so it carries none of the measurement fields (`claim`, `claim_id`,
`threshold`, `tier`, `controls`, `[[gate.part]]`); `decided` stands for its `milestone`, and its printed state is
the decision in force (N40-03, step 7). A kill row carrying a measurement field fails the load naming the field.

**Where receipts live (DESIGN, adopted at the request of `check-stack`'s INV-SUITE-03 test, N33c-30).** A tier run
writes its receipt (`frob.gauntlet.receipt/1`, N38a-02) under `target/gauntlet/receipts/<hash>.json`, which is not
committed. The part names it by hash, and the recorder (N38b-19) commits a byte-identical copy at
`receipts/gates/<hash>.json` in the same commit as the row, so that the cited file resolves on every clone: for
the exit review, which reads receipts (N40-05), for the register's own validator (rule 1), and for `check-stack`.
`receipts/gates/` holds every receipt file a part cites, each named by the BLAKE3 hash of its bytes. A part
measured by runs of several tiers cites a receipt set (`frob.gauntlet.receipt-set/1`, N38b-19: the gate, the part
and its member receipts in tier order), committed there beside its members; a reader of the part's receipt follows
the set to its members, and each member resolves the same way. A copy kept
under another name (for example a script's `receipts/gates/<gate>/lanes-<commit>.json`) is a convenience and is
never what a part cites. The resolution receipts of the stack lock stay at `receipts/<hash>.json` (§33.5). A harness
receipt carries the stack receipt of the binary that produced it (`stack_receipt`, in the `sr:` form of N33a-06,
and `stack_dev`, true for a development identity), which is how a recorded result cites a resolution receipt
(INV-SUITE-03). The validator here checks that the part's receipt file exists and hashes to its name; whether the
stack it names was clean is `check-stack`'s (`stack.gate-receipt`, N33c-30), because only `xtask` reads sibling
trees, and a development identity is refused by the recorder.

The record is the base record of N38b-18 with the fields marked ＋ added; the two beads print one record. The
per-part placement of `status`, `measured`, `evidence` and `recorded` is settled in both (DESIGN: a gate with two
milestones has a part due at each, so a single status per gate would force a premature pass or a late one). A
gate's own status is derived, never stored: `not-run` with no part recorded, otherwise the status of its latest
due part.

`needs` (DESIGN) records the hygiene rule that a gate needs only what a simulator has. A gate whose measurement
needs a bench, a physical board, a building scan, real-robot data or a human review panel is `import-lane`: its
claim is `reality` and it is due at no exit (the exit query of N40-04 skips it and prints it in a section of its
own; at plan time the one such gate is the first real calibration cell of the Reality lane, GATE-GROUND-10). Its
status follows the dataset question, in the same words as N30b-22, N30b-25, N38b-26 and N41-10: `blocked` with
`detail = "OPEN-GROUND-1"` while the question (OPEN-GROUND-1 and its owner half OPEN-GAUNT-1) is undecided; the
terminal `no-claim` with `detail = "no-dataset-admitted"` once the default is recorded as a decision (the row is
entered by the Reality lane's first record, BD-397, form B); `pass` only on a real cell scored on sealed data. Readers of the field: the exit query, and hygiene check H-6 of N00-08, which fails a row whose
threshold names such a need while `needs` says `simulator`. An `import-lane` row whose claim is not `reality` is
caught by the existing refusal `no-claim-on-non-reality`, since its resting status would be refused.

`blocks_exit` (DESIGN, default `true`) marks the five sibling admission gates (INT-FTUI-01, INT-F3D-01,
INT-FDGR-01, INT-FJAX-01, INT-FTX-01), which are the pilots of foundations off every critical path and block no
milestone: N40-02 enters them with `false`. Reader: the exit query of N40-04, which prints such a row in any state
and never waits on it. A row with `blocks_exit = false` whose `kind` is not `admission` fails the load.

**2. Statuses (seven; a reconciliation recorded here).** The register chapter lists `not run`, `pass`, `fail`,
`killed: fallback adopted`, `blocked: ⟨open question⟩`; the Gauntlet chapter's schema lists `not-run`, `pass`, `fail`,
`killed`, `no-claim`, `superseded`. The file uses the union: `not-run` (prints "not run", shown as open, never as
passed); `pass`; `fail`; `killed` (prints "killed: fallback adopted", with the kill gate and the fallback's name);
`blocked` (prints "blocked: OPEN-…", or "blocked: claim reading" for a late row whose two-claim defining row
awaits its owner's confirmation of the governing claim, N40-10; these are the only two blocking causes);
`no-claim` (terminal, only for gates whose claim is `reality`); `superseded`
(a gate replaced by another, naming it). A row with no part recorded is `not-run`.

**3. The nine rules, as checks of `validate()`.**

1. *A gate passes only with a recorded measurement against its threshold.* `pass` requires `measured`, `commit`,
   `command`, `receipt`, `fingerprint`, `seed` non-empty, every `evidence` entry and `claim_id` resolving, and
   `receipt` naming a file `receipts/gates/<receipt>.json` whose bytes hash to it, and, when that file is a receipt
   set, each of its members likewise (else `evidence-unresolved`). A
   `fail` is a record too: it requires `measured`, `commit`, `command` and a `receipt` that resolves the same way,
   so that a failing value can be reproduced and its stack read.
2. *A kill gate names trigger and fallback in advance and is never quietly re-scoped.* A kill row's `trigger`,
   threshold or `fallback` differs from the last amendment only if a dated amendment precedes the measurement
   (N40-03). A kill gate that fires is not a failure of the program: the fallback is the plan.
3. *Exactly one of the seven claims*, on every row of kind `admission`, `convergence` or `program` (a kill row
   carries none, step 1). `claim` is one value of the closed set. A chapter row reading "method" or
   "Performance of the method" is `design-comparison`. A row that named two claims takes the claim of its governing
   part (the list is N40-02's).
4. *Where a chapter and the register differ, the register governs*: on a gate's identity, its claim, its earliest
   milestone, a kill gate's trigger, fallback and decision point, and every number the register states. `threshold`
   is a brief: the full criterion with fixtures and controls is the defining subsection's, and a clause the brief
   leaves out is not waived.
5. *Every convergence gate has a registered negative control that it catches.* `pass` is refused when `controls` is
   empty or any control was not caught in the same run (INV-GAUNT-02).
6. *Earliest milestone.* `milestone` is the first exit at which the gate must have a record; a part is due at each
   milestone of `[[gate.part]]`. A milestone exits when every part due there is `pass` or `killed` with its
   fallback adopted. A `fail` on a convergence gate with no kill gate blocks the exit.
7. *Admission is never inherited.* A foundation first used at a later milestone is admitted then, by its own
   record, at the pin of that day (N40-07 checks it).
8. *Recurring gates.* GATE-GROUND-01, GATE-SAFE-01, GATE-GAUNT-01 and GATE-TENFOLD-09 are re-run at every exit
   after their first: `recurring = true` makes the exit query (N40-04) demand a fresh part per later exit. Gates
   of later subsections that recur (GATE-GAUNT-02, -03, -05, -10; GATE-WS-08 at every release) carry the same
   flag, entered by N40-10; each recurs from the milestone of its first part.
9. *Owner.* The chapter of the defining subsection owns the gate and its fixtures. Six kill gates are stated in two
   chapters; each is listed once under its owner, with the other chapter in `consumers`.

**4. Write-time refusals (DESIGN reason strings of the validator; not agent-facing refusal codes).**

| Reason | Condition | Repair |
|---|---|---|
| `pass-without-control` | `pass` with `controls` empty | Register the control first (ADR-GAUNT-03) |
| `control-not-caught` | a listed control has `last_seen.caught = false` for this run | Fix the gate's test or the plant |
| `self-certified` | `recorded.session` is a member of `recorded.implemented_by`, the sorted, comma-joined set of implementing sessions (INV-GAUNT-05; N38b-18) | Record from a fresh-context session |
| `evidence-unresolved` | an evidence item or `claim_id` dangles or is tombstoned | Re-run; cite a live receipt |
| `target-as-measurement` | `measured` empty or byte-equal to `threshold` | Record the measured value |
| `claim-not-one-of-seven` | `claim` outside the set, or two values | Apply rule 3 |
| `no-claim-on-non-reality` | `no-claim` on a gate whose claim is not `reality`, or with no reason in `detail` | Use `not-run` or `fail`; on a Reality gate name the reason (`no-dataset-admitted`) |
| `blocked-without-question` | `blocked` with neither an `OPEN-…` identifier nor `claim-reading: <bead>` in `detail` | Name the question, or the chapter bead whose owner must confirm the claim reading (N40-10) |
| `killed-without-decision` | `killed` with no kill gate (for a `program` row with no kill gate, the bet whose written consequence is the fallback, e.g. BET-12's re-plan), fallback and ADR in `detail` | Record the decision (N40-03) |
| `duplicate-id` / `reused-id` | an identifier appears twice, or a retired one returns | Identifiers are append-only |

**5. Code (DESIGN).** `crates/frob-conformance/src/register/{mod,row,validate,write}.rs`: `GateRow` and `Part`
(the base types `GateBase` and `PartBase` of N38b-18 plus the added fields), `Kind`; the enums `Status` and
`Claim` are N38b-18's and are not redefined, so an unknown claim, a doubled claim or an unknown status already
fails at parse, and the reason string `claim-not-one-of-seven` is the validator's name for that failure;
`load(path) -> Result<Register, Vec<Violation>>`; `record(part, receipt, session)` which
runs every refusal before writing. Parsing uses the registry loader of `frob-core` (seed BD-005). The row types and
the table printer have no dependency outside `frob-core`, so that `xtask check-generated` can regenerate tables
without depending on `frob-conformance`. Determinism: loading and printing are pure functions of the file bytes;
rows are printed in file order, which is identifier order within kind.

## Acceptance criteria

- [ ] `registries/gates.toml` loads under schema `frob.gates/1`; an unknown field, an unknown status and an unknown
      claim each fail the load with the row identifier.
- [ ] Each of the ten write-time refusals fires on its planted row and names its reason;
      `cargo run -p frob-conformance --example validate_register -- --file registries/gates.toml` exits 0 on the
      committed file and non-zero, naming the row and the reason, on each planted file.
- [ ] GATE-GROUND-10 (the import-lane gate) reads `blocked` with `OPEN-GROUND-1` until the dataset question is
      recorded, then `no-claim` with `no-dataset-admitted`, and is in no exit's due set in either state.
- [ ] A row with no recorded part prints "not run" in every generated view, never "pass" (the done-condition of
      seed BD-002 holds through this loader).
- [ ] Every `pass` and `fail` part names a committed receipt `receipts/gates/<hash>.json` whose bytes hash to
      `<hash>`; a part whose receipt exists only under `target/gauntlet/receipts/`, or whose file hashes to another
      value, is refused with `evidence-unresolved`; a `fail` part with an empty `receipt` is refused naming the
      field.
- [ ] A kill row that carries `claim`, `threshold`, `tier`, `controls` or a `[[gate.part]]` fails the load naming
      the field; rule 3 is not applied to kill rows.
- [ ] Rule 8 is a check of `validate()` over whatever rows are present: of the compiled-table rows, the four
      recurring gates are flagged and no other is; of the rows of later subsections, exactly GATE-GAUNT-02, -03,
      -05, -10 and GATE-WS-08 are, each recurring from its first part. It is proven here on a `synthetic` register
      holding those identifiers and one planted extra flag; it holds on the real file as N40-02 and N40-10 enter
      their rows (both depend on this bead and run this validator).
- [ ] `pass` cannot be written by a session that is a member of `implemented_by`, a co-implementer included
      (GATE-GAUNT-10's planted self-certification is refused).
- [ ] A `pass` whose control was not caught in the same run is refused (GATE-GAUNT-10's second plant; GATE-GAUNT-01).
- [ ] `crates/frob-conformance/CONTRACT.md` lists the register module's inputs, outputs, invariants and refusals.
- [ ] The reconciliation of the two status lists is recorded as an ADR and cited in the schema file.

## Test plan

### Unit tests

`cargo test -p frob-conformance register::` (no mocks; fixtures under `crates/frob-conformance/tests/register/`,
each labelled `synthetic`).

- `status_default_is_not_run`: a row with zero parts recorded → `Status::NotRun`, printed "not run".
- `pass_requires_all_fields`: remove in turn `measured`, `commit`, `command`, `receipt`, `fingerprint`, `seed` from a
  valid pass part → six refusals, each naming the field.
- `receipt_resolves_under_receipts_gates`: a pass part whose 64-hex `receipt` has its file at
  `receipts/gates/<hash>.json` → accepted; the same file present only under `target/gauntlet/receipts/` →
  `evidence-unresolved`; a file at the right path with one byte changed (its hash no longer equals its name) →
  `evidence-unresolved`; a `receipt` naming a committed receipt set whose two members are committed → accepted,
  and with one member missing → `evidence-unresolved` naming the member.
- `fail_is_a_record`: a `fail` part with `measured = "0.41"`, a commit, a command and a resolving receipt →
  accepted; the same part with `receipt = ""` → refused naming `receipt`.
- `kill_row_has_no_measurement_fields`: a `kind = "kill"` row with no `claim` loads; the same row with
  `claim = "known-answer"`, or with `controls = ["NC-0001"]`, or with one `[[gate.part]]`, fails the load naming
  the field.
- `pass_refused_without_control`: `controls = []` → `pass-without-control`.
- `pass_refused_when_control_missed`: control `NC-0001` with `caught = false` → `control-not-caught`.
- `pass_refused_self_certified`: `session = "s1"`, `implemented_by = "s1"` → `self-certified`; with
  `implemented_by = "s1,s3"` the co-implementer `session = "s3"` → `self-certified`; `"s2"` accepted.
- `claim_closed_set`: each of the seven values loads; `"method"`, `"performance of the method"` and
  `["parity","performance"]` are rejected.
- `no_claim_only_for_reality`: `no-claim` on GATE-GROUND-10 (reality) accepted; on GATE-KIN-01 refused.
- `blocked_needs_open_id`: `detail = "OPEN-SPARK-1"` accepted; `detail = "claim-reading: N16c-05"` accepted;
  empty, or `"waiting"`, refused.
- `killed_and_superseded_need_detail`: `killed` with no kill gate, fallback and ADR in `detail` →
  `killed-without-decision`; `superseded` whose `detail` names no existing gate fails the load.
- `target_as_measurement`: `measured` empty, or byte-equal to `threshold` → refused.
- `evidence_unresolved`: a dangling evidence item, a dangling `claim_id`, and a `receipt` with no file under
  `receipts/gates/` → refused.
- `import_lane_rests_at_no_claim`: a `reality` gate with `needs = "import-lane"` loads with a `blocked` part
  (`detail = "OPEN-GROUND-1"`), then with a `no-claim` part (`detail = "no-dataset-admitted"`), and in both
  states is absent from every exit's due set; `no-claim` with an empty `detail` is refused with
  `no-claim-on-non-reality`;
  `needs = "import-lane"` on a `known-answer` gate is caught by `no-claim-on-non-reality`.
- `blocks_exit_defaults_true`: a row without the field loads with `blocks_exit = true`; `false` on an admission
  row loads; `false` on a convergence row fails the load naming the row.
- `recurring_set_is_four`: on a `synthetic` register, the set of `recurring = true` rows among the
  compiled-table rows must equal {GATE-GROUND-01, GATE-SAFE-01, GATE-GAUNT-01, GATE-TENFOLD-09} and among the late
  rows {GATE-GAUNT-02, GATE-GAUNT-03, GATE-GAUNT-05, GATE-GAUNT-10, GATE-WS-08}; a planted `recurring = true` on
  GATE-KIN-04, and a missing flag on GATE-SAFE-01, each fail `validate()` naming the row.
- `ids_append_only` (property test, INV-GAUNT-07 applied to gates): over 10³ random edit scripts, any script that
  renumbers or reuses an identifier is rejected and any pure append is accepted.
- `print_is_pure`: printing the same bytes twice, in debug and release, gives identical output.

### End-to-end script and logging

`scripts/e2e/gate_register_semantics.sh` (sources the shared helper of STD-E2E): copies the tree to a scratch
directory; runs `cargo test -p frob-conformance --test register`; then for each of the ten planted rows applies the
plant and runs the validator, which lives in `frob-conformance` and not in `xtask` (`cargo run -p frob-conformance
--example validate_register -- --file <planted gates.toml>`, an example target of this bead, for the load-time
plants; the write-path plants `self-certified` and `control-not-caught` through `record()` in the test target
`cargo test -p frob-conformance --test register -- write_path`, asserting `gates.toml` unchanged by digest; the
recorder binary `record_gate` is N38b-19's, which depends on this bead, and its end-to-end run is N38b-21's), and
asserts a non-zero exit and the reason string; then plants a hand-edited status table (RC-06) and asserts that `cargo xtask check-generated` fails
and names the line; then asserts on the clean tree that GATE-GROUND-10 prints its resting state and appears in
no exit's due set; then, only where a `frob` binary with the registry-driven status source of N00-02 is built,
that `frob capabilities --json` reports no capability as implemented whose gate is `not-run` (the `frob` skeleton
BD-022 and N00-02 both come after this bead in the graph, through N38b-19, so on a tree without them the step is
logged `skipped: capability absent`, never as passed; N00-02 carries the same assertion as its own acceptance).
Each step logs `ts`, `script`, `bead`, `step`, `event`, the command line, exit code, wall time, the reason
string, the digest of `gates.toml` before and after each write-path plant, and on failure the first differing value
and the path of the planted file; `metric` lines give `plants_refused` (threshold 10 of 10) and `recurring_flagged`
(threshold: exactly 4 among the compiled-table rows of N40-02, and exactly 5 more among the late rows of N40-10
when they are present); the evidence block is `{claim: known-answer, class: Tested, tier: G0:host, determinism: D0, seed: 0}`;
the final `summary` line counts assertions and names GATE-GAUNT-10 and GATE-GAUNT-01.

### Known answers and negative controls

Known answers: seven statuses; seven claims; four recurring gates; ten refusals (N40-KA rows R-01 to R-04).
Negative controls (N40-CX rows RC-01 to RC-06): a PASS with no control; a PASS with an uncaught control; a

## Considerations

- The parts model changed the Gauntlet chapter's single-status record; the two beads now agree: N38b-18's base
  record carries `status`, `measured`, `evidence` and `recorded` on `[[gate.part]]`, as here. A gate with any due
  part not recorded prints "not run".
- Many gates have parts at more than one exit (FACT, counted from the register): among the compiled rows, 36
  convergence rows (the 35 of the compiled tables and GATE-MARROW-01, whose parts are M0 and M1) and 3 admission
  rows (INT-FSIM-07, INT-FMCP-01, INT-FDGR-01), N40-02's `parts_equal_exits`; among the rows of later subsections,
  12 (GATE-FID-09 and GATE-WS-07 with three parts each, ten gates with two, GATE-MARROW-06 among them with its M1
  and M2 parts), N40-10 and N40-KA R-23. A single status per gate would force either a premature pass or a late
  one.
- The file is read by the README table, the exit query, the release rubric, the dashboard and `check-contracts`
  (every release path has a demo whose claims exist in the file). A registry that nothing reads is deleted: each
  added field above names its reader.
- Risk: a recording session that copies the threshold into `measured`. The `target-as-measurement` refusal catches
  byte equality only; the exit review (N40-05) reads receipts.
- Receipts are committed: one canonical JSON file per recorded part, typically kilobytes. A receipt is never
  deleted while a part cites it (a deleted one makes the part `evidence-unresolved` and the claim prints
  `evidence: unavailable`, N40-CX RC-55); a superseded part keeps its receipt.
- Size: the validator and printer stay under 800 lines; `frob-conformance` has a cap of 24 thousand.
