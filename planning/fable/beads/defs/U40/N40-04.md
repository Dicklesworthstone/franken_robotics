## Background

"A milestone exit is a query over the gate register." A milestone is a set of demonstrations with recorded values,
not a date, and the question "may M2 exit?" must be answerable by a program and not by a meeting. This bead builds
that program: given a milestone, it lists every gate part due at that exit (admission, convergence, program,
recurring), every kill decision due, the status and evidence of each, and a verdict. The nine exit-review beads
(seeds BD-044, BD-147, BD-224, BD-319, BD-378, BD-412, BD-427, BD-434, BD-442) each start by regenerating this
report; an exit review implements nothing and closes only when the report is clean.

Why a generated report and not a checklist kept by hand: at M2 alone 80 convergence parts, 2 admission parts and 14
kill decisions are due; a hand list of that size is where a gate goes missing. The rule that a milestone exits when
every gate with a part due there has a record that is a pass or a kill decision with its fallback adopted is
mechanical, and the report applies it mechanically. The report is deliberately not the exit itself: a milestone
does not exit on a count of gates; its exit line (the observable in the milestone registry, N40-06) must also be
demonstrated, and a fresh-context session records the exit (N40-05).

## Scope

In: the query, the report in Markdown and JSON, the blocking rules, recurring gates, variants, the load table. Out:
the review procedure and its human-readable dispositions (N40-05); the data (N40-02, N40-10, ledger beads); the
README status table (seed BD-002).

## Technical approach

**1. Inputs.** `registries/gates.toml` (N40-01 to N40-03, N40-10), `registries/milestones.toml` (N40-06),
`frob-conformance/registry/controls.toml`, the ledger and artifact graph for resolution, and an optional variant
record (N40-33, N40-34).

**2. The due set of milestone Mn.**
1. Every `[[gate.part]]` whose `milestone` is Mn (admission, convergence and program rows, late rows included).
2. For every `recurring` gate whose first part is at an earlier milestone, one part at Mn: GATE-GROUND-01 and
   GATE-SAFE-01 (first at M1), GATE-GAUNT-01 (every exit), GATE-TENFOLD-09 (first at M1); and of the later
   subsections GATE-GAUNT-02, -05, -10 (every exit from M0), GATE-GAUNT-03 (every exit from M2), GATE-WS-08 (every
   release). A recurring part is fresh only if its receipt's commit is the exit candidate's commit.
3. Every kill row with `decided = Mn` and mode `exit`; every `standing` or `rolling` row whose start is at or
   before Mn; every `pilot-before-funding` row whose work package asked for funding in Mn.
4. The program rows whose "when" names Mn, read from the program row itself. (The gates-by-exit table omits
   GATE-TENFOLD-09 at M1, GATE-TENFOLD-10, -11 and -13 at M3 and GATE-TENFOLD-11, -12 and -13 at M7; the program
   rows state them, and the program rows govern.)
5. Gates tied to no milestone (GATE-GROUND-10) are printed in a separate section at every exit from M5 and never
   block.

**3. Per part, the report prints**: identifier, kind, claim, part scope, threshold brief, status, measured value,
receipt hash and commit, controls registered and caught in that run, recording session and implementing session,
whether evidence resolves, and a disposition slot for the reviewer (N40-05).

**4. Blocking rules** (a part blocks the exit unless one of the lines makes it non-blocking):

| State of a due part | Blocks? |
|---|---|
| `pass`, every control caught in the same run, session ≠ implementer, evidence resolves | No |
| `pass` failing any of those three conditions | Yes: the pass is void and is printed as `not run` |
| `killed`, with a kill decision `fired` and its ADR | No: the fallback is the plan |
| `fail` on a convergence gate that some kill gate reads, decision not yet recorded | Yes: record the decision |
| `fail` on a convergence gate that no kill gate reads | Yes |
| `not-run` | Yes, unless a variant record lists the gate with its reason (then printed `not run (variant: …)`, never as passed) |
| `blocked` | Yes, until the open question is answered or has taken its default by ADR |
| `no-claim` on a Reality gate | No: a recorded `no-claim` is a record |
| Sibling admission gate (`blocks_exit = false`) in any state | No; printed |
| Kill decision due with no outcome or no ADR | Yes |
| A gate that passed before its milestone | No; it may pass early |
| A part whose milestone was moved later with no ADR | Yes (`moved-later-without-adr`) |

**5. Verdict.** `exit-ready` when no part blocks; otherwise `not-ready` with the blocking list. The report also
prints: the exit observable of the milestone and whether its demonstration receipts exist; the count of controls
that have never failed their gate in any recorded run (reviewed at each exit: either the defect cannot be planted
as described or the gate is not looking); the count of close reasons shared by more than one bead (a failure
signal); and the load table.

**6. The load table (known answer; parts due per exit, from the compiled register tables).**

| Exit | M0 | M1 | M2 | M3 | M4 | M5 | M6 | M7 | M8 |
|---|---|---|---|---|---|---|---|---|---|
| Admission gates | 23 | 4 | 2 | 6 | 0 | 4 | 2 | 0 | 0 |
| Convergence gates | 11 | 59 | 80 | 77 | 49 | 25 | 7 | 0 | 7 |
| Kill decisions | 2 | 4 | 14 | 28 | 30 | 18 | 9 | 0 | 8 |

M2 and M3 carry half of the convergence parts, and M3 and M4 more than half of the kill decisions. That
concentration is by design, since those exits are where the engine and the method are decided, and it is a schedule
risk. M7 has no subsystem gate of its own: its exit is the tournament. The kill row sums to 113 because KILL-MCP is
decided at M0 and re-read at M1. The later subsections add parts on top (N40-10); the report prints both counts.

**7. Outputs and invocation (DESIGN).** `cargo test -p frob-conformance --test exit -- report --milestone M2` writes
`docs/delivery/exits/M2/gate-report.md` and `gate-report.json` (schema `frob.exitreport/1`) and a hash-named
receipt. No verb and no `xtask` subcommand is added. The JSON carries the commit, the register digest, the due
list, the blocking list and the verdict. Determinism: a pure function of the input files; the same commit gives the
same bytes.

## Acceptance criteria

- [ ] For each of M0 to M8 the due set from the compiled tables has the sizes of the load table, exactly.
- [ ] The four recurring gates appear at every exit after their first; a recurring part recorded at an older commit
      is reported stale.
- [ ] The seven ten-fold parts that the gates-by-exit table omits are in the due sets of M1, M3 and M7.
- [ ] Each row of the blocking table is exercised by a planted register and gives the stated answer.
- [ ] A `pass` recorded by the implementing session, or with an uncaught control, is printed as `not run` and blocks.
- [ ] A fired kill gate with its ADR makes its failed gate non-blocking and prints the fallback's name.
- [ ] The report is byte-identical when regenerated at the same commit; its JSON validates against its schema.
- [ ] On the seeded register with no measurement at all, every exit is `not-ready` and nothing prints as passed.

## Test plan

### Unit tests

`cargo test -p frob-conformance exit::`.

- `due_counts_match_load_table`: 27 numbers (3 rows × 9 exits) as above.
- `kill_decisions_sum_113`: Σ over exits = 113; KILL-MCP is the only row counted twice.
- `recurring_due_every_exit`: GATE-GROUND-01 and GATE-SAFE-01 due at M1…M8; GATE-GAUNT-01 at M0…M8;
  GATE-TENFOLD-09 at M1…M8.
- `program_rows_govern`: GATE-TENFOLD-09 ∈ due(M1); {-10, -11, -13} ⊂ due(M3); {-11, -12, -13} ⊂ due(M7).
- `blocking_table`: twelve fixtures, one per row, each asserting blocks / does not block.
- `void_pass_prints_not_run`: session = implementer → printed status `not run`, blocking reason `self-certified`.
- `no_claim_is_a_record`: GATE-HAB-03 `no-claim` at M5 → not blocking; `no-claim` on GATE-FOUNDRY-01 → load error.
- `sibling_gate_never_blocks`: INT-FTUI-01 `fail` at M3 → listed, not blocking.
- `early_pass_allowed`: GATE-FOUNDRY-01 `pass` recorded during M4 → satisfies its M5 part.
- `variant_not_run_listed`: with a no-GPU variant record naming GATE-SPARK-03, that part is non-blocking and printed
  `not run (variant: no-GPU)`; without the record it blocks.
- `never_failed_controls_counted`: three controls, one with no recorded catch → count 1.

### End-to-end script and logging

`scripts/e2e/exit_query.sh`: on a scratch copy seeded with a synthetic register (all rows, no measurements),
generates the nine reports and asserts nine `not-ready` verdicts and zero rows printed as passed; then records
synthetic passing parts for M0 with caught controls, asserts `exit-ready` for M0 only; then applies each planted
defect of N40-CX RC-01 to RC-06 and RC-13 in turn and asserts the verdict returns to `not-ready` with the right
reason. Logs per step: command, exit code, wall time, register digest, due counts measured against expected, the
blocking list, and on failure the first differing row and the report path; `summary` names GATE-GAUNT-01 and
GATE-GAUNT-10.

### Known answers and negative controls

N40-KA R-11 (the load table), R-12 (113), R-13 (recurring sets). Negative controls: RC-01 to RC-06, RC-13, and
RC-14 (a gate dropped from the due set by editing its part milestone to a later exit with no ADR). Metamorphic
relations: permuting rows of the register leaves every report unchanged; adding a passing early part never turns
`exit-ready` into `not-ready`. Determinism: twice on one machine, debug and release, macOS and Linux: equal bytes.

## Considerations

- The report cannot see whether a demonstration was honest; it sees receipts. The reviewer reads them (N40-05).
- A variant record is powerful (it unblocks `not-run` parts), so it is an ADR with a closed list of gates and a
  reason per gate, and the report prints every such part in a separate, conspicuous section.
- Performance: the query is linear in rows (about 550 identifiers); it runs in well under a second and is part of
  no physics path.
- If the Gauntlet chapter's bead models one status per gate instead of parts, the due set is computed from a
  `milestones` list on the row and the same tests apply.
