## Background

The program is delivered in nine milestones, M0 to M8. **A milestone is a set of demonstrations with recorded
values, not a date.** Three tools need the milestones as data: the exit query (N40-04) needs each milestone's exit
observable, the schedule gate (N40-11) needs the planning estimates and the start and exit times, and the README
needs the names. This bead records them in one registry file so that none of the three keeps its own copy.

It also records, as the file's commentary and in each epic, why the program has this shape. The first wedge is
chosen to start where value is deliverable with the fewest unproven dependencies: **M1 is a design studio on the CPU
referee tier, with the first mission slice.** It needs only three foundations (the sibling physics library, the
async runtime and the embedded database). It already demonstrates the thesis in small: a typed design, static
analyses from Lie theory, a synthesized controller, a rollout on the transactional referee, structured telemetry,
and a mission query answered over a family of designs with a certificate that an independent auditor re-checks, all
through one verb registry. GPUs arrive at M2 on top of something that already works. Three further reasons:

1. *The result is not in the step.* An infinitely fast environment step cannot deliver a ten-fold ratio of design
   loop time. The parts of the thesis that no GPU can rescue (what an answer is, how it is checked, how an amendment
   withdraws it) are exercised at M1 on fixtures whose answers are known exactly (scenarios NS-13 and NS-22).
2. *The rival is measured while M1 is built.* M0 and M1 time the incumbent loop on the Linux workstation `trj`, so
   M2's engine work is funded against a measured denominator and not against a published one.
3. *A CPU studio survives every admission failure.* If the GPU, symbolic and proof foundations all failed admission,
   M1 would still ship.

The order of evidence: measure the rival (M0, M1); put the mission slice on the CPU (M1); run the rank-agreement
experiment as soon as two rungs exist (a pilot on incumbent tools by M3, on our tiers at M4); hold a partial
ten-fold gate (M3); run the tournament (M7). Alternative rejected: GPU first, studio later, because every claim
would then rest on unadmitted foundations and an unmeasured rival for the first half of the program.

## Scope

In: the registry file, its schema, its loader, the derived quantities, the recording of start and exit times. Out:
the content of each milestone (the nine epics), the schedule gate's decision (N40-11), work packages (their epics).

## Technical approach

**1. The file** `registries/milestones.toml` (schema `frob.milestones/1`, DESIGN):

```toml
[[milestone]]
id             = "M1"
name           = "Referee studio and first mission slice, CPU only"
critical_path  = true
estimate_weeks = 5            # DESIGN planning estimate, elapsed weeks for a swarm; "per-epic" for M6 and M8
exit_observable = "NS-01, NS-07 and the docking scenario demonstrated; the schedule gate (BET-12) met"
demonstrates   = ["NS-01", "NS-07", "NS-22", "NS-13 (CPU)"]
work_packages  = ["WP-07", "…"]
started        = ""           # commit and UTC time of the first bead of the milestone moving to in-progress
exited         = ""           # commit and UTC time of the exit record
exit_record    = ""           # path of docs/delivery/exits/M1/EXIT.md
```

**2. The nine rows.**

| M | Name | Critical path | Estimate (weeks) | Exit is defined by |
|---|---|---|---|---|
| M0 | Spine and airlock | Yes | 2 | The admission records, one kernel on three backends, and the incumbent phase ledger on `trj` |
| M1 | Referee studio and first mission slice, CPU only | Yes | 5 | NS-01, NS-07 and the docking scenario demonstrated; the schedule gate (BET-12) met |
| M2 | Batch, backends, families | Yes | 6 | Kill decisions for the kernel toolchain, contact, Metal and mixed batches recorded as ADRs |
| M3 | Places, tasks, adversaries, qualification | Yes | 6 | The partial ten-fold gate (GATE-TENFOLD-06) recorded, whatever the ratio |
| M4 | Amortized control, co-design, mission queries at scale | Yes | 8 | Rank agreement measured; the family-policy bets decided |
| M5 | Proofs, reality, manufacture | No; may overlap M4 | 6 | The Reality lane has a record or a recorded no-claim |
| M6 | Frontier physics | No | Per epic, 2 to 6 each | Per-epic plans and kill gates |
| M7 | The ten-fold tournament | Yes; needs M4, not M5 or M6 | 6, including a two-week freeze and rehearsal | The measured ratio published with its phase ledger (GATE-TENFOLD-07) |
| M8 | Frontier delivery | No | Per epic | Per-epic plans and stop rules |

**3. Derived quantities (computed, never typed).** Critical path = M0, M1, M2, M3, M4, M7: 2 + 5 + 6 + 6 + 8 + 6 =
33 weeks. M0 plus M1 = 7 weeks. The schedule gate asks its question if they take more than 1.5 × 7 = 10.5 weeks for
the cause that bet BET-12 names. `elapsed(Mi)` = `exited` − `started` in weeks, from the recorded times.

**4. Rules attached to the rows.**

- The estimates exist to make BET-12 testable. They are not acceptance evidence and no gate cites them. The loader
  exposes them only to the schedule-gate computation; `check-contracts` fails if any gate row's threshold names an
  estimate.
- M5 does not gate M7: a sealed stratum of the tournament that needs a mechanism of M5 or M6 which has not landed
  is declared `not run` in the tournament report, with the reason.
- M5 may overlap M4. M6 and M8 are per-epic and pause whenever M4 or M7 is slipping, since nothing in them is on
  the critical path.
- Each milestone is described by the same seven fields, which the nine epics fill: purpose, artifact, what it
  demonstrates, acceptance, kill gates decided, owner input wanted, and the decision to stop or re-plan.
- Thresholds repeated in milestone text are TARGETs and the gate register governs them; week counts are DESIGN
  planning estimates; scenario numbers are the North-Star scenarios' own.

**5. Code.** `crates/frob-conformance/src/register/milestones.rs`: `load`, `critical_path() -> Vec<Id>`,
`estimate_sum(ids)`, `elapsed_weeks(id)`. Start and exit times are written by the exit runner (N40-05) from the
bead logs, not by hand.

## Acceptance criteria

- [ ] The file loads with nine rows; identifiers M0 to M8, unique, in order.
- [ ] `critical_path()` returns [M0, M1, M2, M3, M4, M7] and `estimate_sum` of it is 33; of [M0, M1] it is 7.
- [ ] The schedule threshold computes to 10.5 weeks.
- [ ] No row of `registries/gates.toml` names a week count; a planted gate threshold citing "5 weeks" fails
      `cargo xtask check-contracts`.
- [ ] `exit_observable` of every row is non-empty and equals the table above.
- [ ] `started` and `exited` are written only by the exit runner; a hand edit is detected by comparison with the
      bead logs.

## Test plan

### Unit tests

`cargo test -p frob-conformance register::milestones::`.

- `nine_rows_in_order`: ids = M0…M8.
- `critical_path_is_six`: [M0, M1, M2, M3, M4, M7].
- `critical_path_sum_33`: 2 + 5 + 6 + 6 + 8 + 6 = 33.
- `m0_m1_sum_7_threshold_10_5`: 7 and 10.5 exactly (rational arithmetic, 21/2).
- `per_epic_estimates_not_summed`: M6 and M8 contribute no number; summing them is a type error.
- `elapsed_weeks`: started 2027-01-04T00:00Z, exited 2027-02-22T00:00Z → 7.0.
- `m7_needs_m4_only`: the dependency list of M7 contains M4 and neither M5 nor M6.
- `estimate_not_cited_by_gate` (negative control): a synthetic gate row whose threshold contains
  `estimate_weeks` → rejected.

### End-to-end script and logging

`scripts/e2e/milestone_registry.sh`: loads the file through the conformance test target, prints the derived
quantities, and asserts 33, 7 and 10.5; plants a tenth row and a duplicate identifier and asserts both are
rejected; regenerates the README status table with `cargo xtask check-generated` and asserts the milestone names
it prints equal the registry, then runs `frob capabilities --json` and asserts every capability's milestone tag is
one of the nine identifiers. Logs each
command, exit code, wall time, the measured values beside the expected ones, and the file digest; on failure the
first differing field.

### Known answers and negative controls

N40-KA R-15 (the nine rows), R-16 (33, 7, 10.5). Negative controls N40-CX RC-20 (an estimate cited as acceptance
evidence), RC-21 (an exit time typed by hand that the logs do not support). Determinism: pure function of the file.

## Considerations

- The estimates are for a swarm and are deliberately coarse. Their only consumer is the schedule gate; treating
  them as a schedule to be met is the failure the "line counts are scope caps, never schedules" rule names.
- If the owner re-plans after the schedule gate, the new estimates are an amendment with a date and a reason; the
  old rows stay in history.
- A registry that nothing reads is deleted. Readers of this file: N40-04, N40-11 and the README generator.
