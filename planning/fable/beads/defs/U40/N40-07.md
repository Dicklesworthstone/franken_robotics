## Background

FrankenRobotics is built on sibling libraries (a physics library, an async runtime, an embedded database, a tensor
library with a Metal gateway, a symbolic engine, a proof checker, an MCP server library, an array library and
others). A **foundation** is one of these as consumed here. A foundation is not used above the airlock (the one
crate through which sibling code enters) until its **admission gate** has a record in `DEPENDENCY_ADMISSION.md`.

The **dependency firewall** says, for each milestone, which foundations the milestone *needs*, which it *uses if
admitted*, and what happens *if a foundation is missing*. Its purpose is that no milestone silently comes to rest on
a foundation that was never tested for the use it is now put to, and that a failed admission has a planned route
instead of a stall. Two rules make it enforceable: **an admission is never inherited** (a foundation or an airlock
group first used at a milestone is admitted at that milestone, by its own record, at the pin of that day), and
**M7 freezes every pin** (a ratio of times measured across a pin move is not one measurement).

Alternative rejected: admit each sibling once, at M0, for everything. A sibling moves; a group of it that M0 never
exercised (statistics, spectral analysis, structures) may be broken at the pin of the day it is first needed, and a
blanket M0 record would hide that.

## Scope

In: the firewall as it is applied at a milestone exit. The check `firewall(Mn)`, run by the exit runner over what
the milestone's targets actually link; two fields on each row of `registries/milestones.toml` (`needs_note` and
`if_missing`); the by-milestone view of the firewall (the nine-row table below, rendered, not entered); the verdict
on a required foundation that is not admitted (blocked unless its route is on record); the milestone half of "never
inherited" (`admission-inherited`: a covering record written before the use existed); the audit of the M7 freeze
window at the M7 exit; the "Foundations" section of the exit report.

Out, with the bead that has it:
- Which foundation is required or optional at which milestone, as data. It is entered once, on the foundation rows
  of `franken-stack.lock` (`required_at`, `optional_at`, `firewall_cells`; the key `uses` on those rows is the
  posture list of N33a-01 and is not read here), by N33b-01, with its loader, its data-level
  consistency test, the classification of each foundation at a milestone, the frozen assertions (M1 requires exactly
  three foundations; the last five rows are never required) and the report `check-stack --report firewall`. This
  bead depends on N33b-01, reads that data and keeps no copy of the membership.
- The admission record, its validator, and the never-inherited rule per use and per pin (findings `unadmitted-use`
  and `admission-stale`): N33a-07. This bead depends on it and calls its function; it holds no second
  implementation.
- The freeze itself (the `[freeze]` record of the stack lock, `check-stack` while frozen, the trains' refusal, the
  rule that runs under different receipts are never pooled): N33b-03, a bead of M7, related and not a dependency
  because it is later.
- The admission tests themselves (the suite units' beads for each `INT-…` gate), the layer and dependency lints
  (`check-layers`, `check-deps`, seeds BD-003 and BD-004), the stack lock's rows and pins (N33a-02) and the choice of
  T (seed BD-031).

## Technical approach

**1. The table, as a view.** The plan prints the firewall twice: by foundation in the suite chapter and by
milestone in the milestone chapter (the table below). They are one fact. DESIGN: the membership (which foundation,
at which milestone, required or used if admitted, and for what) is entered once, on the foundation rows of the
stack lock (N33b-01), because a second entry per milestone could disagree with the first, and the plan's two
printings already do in one cell (see below). The by-milestone table is therefore rendered: `firewall_view(Mn)`
builds the "Needs" cell from the foundations with Mn in `required_at` and the "Uses if admitted" cell from those
with Mn in `optional_at`, each with its `firewall_cells[Mn]` text. This bead enters only what the lock does not hold, as two
fields on each row of `registries/milestones.toml`:

- `needs_note`: the part of the "Needs" cell that is not a foundation use. At M0: nothing is relied on, the one
  toolchain T is chosen, the listed foundations are admitted, and the two P0 upstream work items are done. At M7:
  every pin and T frozen for the length of the tournament. Empty for the other seven.
- `if_missing`: the last column as text, with `routes`, the machine-readable list of what counts as the route (kill
  gate identifiers whose decision ADR must exist, and variant records such as `variant:no-gpu`).

The one cell where the plan's two printings differ (DESIGN, stated identically in N33b-01): the suite chapter's
table prints fastmcp_rust's M7 cell, rival access, without parentheses, which would make it required; the row of
M7 above lists it under "uses if admitted". Used: optional (M7 is in `optional_at` of the fastmcp_rust row and not
in `required_at`). Reason: the last fallback of KILL-MCP is the command line, which is complete on its own, so a
tournament whose rival reaches the verbs through the command line is still a tournament, and no milestone may be
blocked by one failed bet.

**2. Admission gates first needed per exit** (from the register; the firewall's rows and these lists must agree):
M0: INT-TOOLCHAIN-01; INT-FSIM-01 to -11, -18; INT-ASUP-01; INT-FSQL-01; INT-FT-01, -02; INT-CUDA-01; INT-FSYM-01,
-02; INT-FMCP-01; INT-FNP-01, -02 (23). M1: INT-FSIM-07 (under witness migration), INT-FSIM-16, INT-FSQL-02,
INT-FMCP-01 for the M1 verbs (4). M2: INT-ASUP-02; INT-FJAX-01 only if the profile asks (2). M3: INT-FSIM-13, -14;
INT-FMCP-01 for the full surface; INT-FTUI-01; INT-F3D-01; INT-FDGR-01 for the schema fixtures (6). M5: INT-FSIM-15;
INT-FLN-01, -02; INT-FDGR-01 for scan import (4). M6: INT-FSIM-17; INT-FTX-01 (2).

**3. The exit check `firewall(Mn)`** (in `crates/frob-conformance/src/exit/firewall.rs`, run by the exit runner).

1. Compute U, the set of sibling packages and airlock feature groups reachable from the binaries and test targets
   that the milestone's demonstrations and gates run (`cargo metadata` with the features those targets enable).
2. Compute A, the allowed set: every foundation (with its crates and airlock groups) whose `required_at` or
   `optional_at` in the stack lock names a milestone up to Mn, read through the loader of N33b-01; M0 counts for
   every foundation whose admission gate is due at M0. Fail on any element of U not in A
   (`foundation-outside-firewall`), naming the package and the crate that pulled it in.
3. *Admission per use and per pin.* Call `stack::admission::never_inherited(tree, U)` of N33a-07. Its two findings
   fail the exit under their own names: `unadmitted-use` (no record covers u; a record never covers what it does
   not list) and `admission-stale` (the newest covering record is not at the pin of the current lock). This check
   adds no second implementation and no second name for either.
4. *Never inherited, the milestone half.* Let first(u) be the earliest milestone whose targets reach u. Among the
   records covering u that step 3 returns, at least one must carry a pin (`sibling_rev` and `toolchain`) that is
   the stack lock's pin at a commit inside first(u), and its test must have been run at that pin with u in use:
   at the record's `repo_rev` a manifest enables the group, or the lockfile contains the crate. A record made at
   an earlier milestone, at an older pin, for a group not exercised then, fails (`admission-inherited`). Example:
   `frob-fsim`'s `stats` group is first reached at M3; INT-FSIM-14 must have an M3 record at the M3 pin even
   though INT-FSIM-01 passed at M0. This half needs first(u) and the milestone calendar (`started` and `exited` of
   the milestone rows), which is why it is here and not in N33a-07.
5. *Missing foundations.* Take the classification of N33b-01 for Mn. For every required foundation classed
   `missing` (its gate has any status other than `pass`, or `killed: fallback adopted` with the row's fallback
   text recorded), the route of `if_missing.routes` must be on record: the kill decision ADR, or the variant
   record named in the table (for M2, the no-GPU variant record). Without it the exit is blocked with
   `missing-foundation-without-route`, naming the foundation. `fallback-adopted` needs its kill ADR and nothing
   more. An optional foundation never blocks, whatever its gate says. This is the only place where the verdict on
   a missing required foundation is given.
6. At M7 only, the audit of the freeze window. The window is the one the freeze record of N33b-03 defines: from
   the commit `[freeze].opened` to the commit `[freeze].closed`. Every sibling pin and T in `franken-stack.lock`
   is identical at the first and the last commit of the window, and every run record of the campaign carries the
   frozen receipt; otherwise `pin-moved-during-freeze`, and the runs spanning the move are listed and are void.
   N33b-03 enforces the freeze while it is open; this step is the reading of it at the exit and compares nothing
   that N33b-03 has not recorded.

**4. Output.** A section "Foundations" in the exit report: the three lists of N33b-01's report for the milestone
(required and admitted; required and not admitted; optional with their status), then per foundation, first use,
admission gate, record pin, verdict; plus the missing-foundation routes taken.

## Acceptance criteria

- [ ] `needs_note` and `if_missing` are present for all nine milestones, and the rendered nine-row view (membership from the stack lock, notes and routes from the milestone rows) equals the table.
- [ ] `registries/milestones.toml` holds no list of foundations per milestone: the membership is read from `franken-stack.lock`, and fastmcp_rust at M7 renders under "uses if admitted".
- [ ] The admission lists of step 2 equal the register's admission parts due per exit (23, 4, 2, 6, 0, 4, 2, 0, 0).
- [ ] A crate of M1 that links a `cudarc` package fails `foundation-outside-firewall` at the M1 exit.
- [ ] A group first reached at M3 with only an M0 record fails `admission-inherited`.
- [ ] A foundation used with no record fails `unadmitted-use`, and one whose newest record is at an older pin fails `admission-stale`; both come from the function of N33a-07, and this crate contains no other implementation of them.
- [ ] A required foundation whose gate is `fail`, `not run` or `blocked` at the reviewed milestone, with no recorded route, blocks with `missing-foundation-without-route` and is named; with its kill ADR or variant record it does not block.
- [ ] A changed pin inside a synthetic tournament window is reported with the runs it voids.

## Test plan

### Unit tests

`cargo test -p frob-conformance exit::firewall::` (synthetic dependency graphs as `cargo metadata` JSON fixtures).

- `view_equals_table`: the nine rendered rows equal the table (membership per column per milestone; notes; routes).
- `allowed_set_is_cumulative`: A(M2) ⊇ A(M1) ⊇ A(M0); `cudarc` ∈ A(M2), ∉ A(M1).
- `allowed_set_read_from_lock`: changing `optional_at` of one synthetic foundation row changes A and the view, with no edit of the milestone rows.
- `outside_firewall_detected`: graph(M1) containing `cudarc` → failure naming the edge.
- `never_inherited`: group `stats` first reached at M3, record pinned at an M0 commit → `admission-inherited`;
  record pinned at an M3 commit → pass.
- `per_use_findings_are_delegated`: a use with no record → `unadmitted-use`; a record at an older pin →
  `admission-stale`; both are the findings returned by `stack::admission::never_inherited`.
- `first_use_is_earliest_reach`: a group reached at M2 by a test target only still counts as first used at M2.
- `missing_route_required`: INT-CUDA-01 and INT-FT-01 failed at M2 with no variant record → block with
  `missing-foundation-without-route`; with the no-GPU variant record → pass. The same with the gates `not run` and
  `blocked`; a gate `killed: fallback adopted` with its ADR → pass without a variant record.
- `optional_never_blocks`: INT-FNP-01 failed at M1 (franken_numpy is optional there) → reported, exit not blocked.
- `sibling_gates_listed_not_blocking`: INT-FTUI-01 failed at M3 → route KILL-TUI required, exit not blocked by the
  gate itself.
- `freeze_window`: the window is read from a synthetic `[freeze]` record; lock digest equal at both ends and every
  run on the frozen receipt → pass; one sibling commit changed in between → fail with the list of run identifiers
  in the window.

### End-to-end script and logging

`scripts/e2e/dependency_firewall.sh`: on a scratch copy, runs `cargo xtask check-deps` and `check-stack`, then the
firewall check for M0; plants a path dependency on an unadmitted sibling crate in an M1 crate and asserts the
failure names it; plants an old-pin record for a new group and asserts `admission-inherited`; marks INT-CUDA-01
`fail` at M2 with no variant record and asserts `missing-foundation-without-route`, then adds the no-GPU variant
record and asserts the block clears; plants a sibling pin change inside a synthetic `[freeze]` window and asserts
`pin-moved-during-freeze` with the voided run identifiers. Logs through the STD-E2E helper to
`target/e2e-logs/dependency_firewall/<utc>.ndjson`: per step `ts`, `script`, `bead`, `step`, `event`, the command
lines, exit codes, wall times, the sets U and A (package names and counts as `metric` lines), the lock digest, the
evidence block `{claim: known-answer, class: Tested, tier: G0:host, determinism: D0, seed: 0}`, each finding name,
and on failure the first offending package and the manifest path; the `summary` line counts assertions and names
INT-TOOLCHAIN-01 and INT-ASUP-01.

### Known answers and negative controls

N40-KA R-17 (the nine firewall rows), R-18 (admission parts per exit). Negative controls N40-CX RC-22 (an inherited
admission), RC-23 (a foundation used outside its milestone's set), RC-24 (a pin moved inside the freeze window).
Determinism: the check is a function of the lockfile, the metadata and the registry; equal inputs give equal
verdicts on macOS and Linux.

## Considerations

- "Reachable" is computed with the features the milestone's targets enable. A resolution check with every optional
  feature group enabled also runs, because a build that never enables an oracle's feature flag resolves, and the
  conflict appears only when the flag is first turned on at the oracle's milestone.
- A dirty sibling checkout is acceptable for development builds with the tree hash in the receipt and no PASS
  recorded; the firewall check refuses to evaluate on a dirty sibling.
- The check reads; it never writes to a sibling checkout.
- If a milestone legitimately needs a foundation earlier than the table says, the table changes by ADR and the
  admission gate gains a part at that milestone. The change is made in the stack lock's fields (N33b-01); the view
  here follows.
- Division of the firewall between three beads, so that nothing is specified twice: N33b-01 holds the data and the
  checks that need only tracked files; N33a-07 holds the admission records and the per-use, per-pin
  never-inherited check; this bead holds what needs a build graph or the milestone calendar.
