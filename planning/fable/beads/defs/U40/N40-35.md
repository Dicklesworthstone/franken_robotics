## Background

An **open question** is a decision the plan has not taken, written so that not taking it is safe: each has an
owner, a deadline expressed as the gate or milestone it blocks, a **fail-closed default**, and the evidence that
would decide it. Nothing is decided by silence: at its deadline an undecided question takes its default, and the
default is recorded as an ADR. Most questions are decided by measurement. A small set can only be decided by the
project owner's judgement (how GPU code is housed, how much compute may be spent, who adjudicates, what is
published). Each milestone lists the owner input it wants, and a question is asked **one milestone before the gate
it blocks**.

This bead turns those per-milestone lists into a calendar that the exit reviews read, with each question's default
and what the default costs, and a check that at every exit each question due is either answered or has taken its
default by ADR and is reported with the capability it removed. Without it the failure mode is the quiet one: a
question nobody answered, a capability nobody removed, and a result that silently assumes the generous answer.

## Scope

In: the calendar rows; the five clauses of the decision rule as checks; the exit-time listing; the reminder one
milestone ahead. Out: the full register of questions (the open-questions unit and the chapter units); the
decisions themselves (the owner; each question that blocks work has its own decision bead with label
`owner-decision`, written by the unit that owns it).

## Technical approach

**1. The decision rule (five clauses, each a check).**

1. *A default removes a claim or a capability. It never adds one.* "GPU results are labelled exploratory", "no
   pretraining", "`reality: no-claim`" and "refuse" are defaults. "Assume the catalogue price" is not. Check: every
   row's `default_effect` is in the closed set of the question register (N41-03, loader rule 2: `removes-claim`,
   `removes-capability`, `labels-result`, `refuses`, `keeps-conservative-value`, `none`); the calendar reads that
   field from the question's row and holds no copy of it.
2. *A question is asked one milestone before the gate it blocks.* The owner-input line of each milestone lists the
   questions due. A question that reaches its deadline at its default is reported in the exit review with the
   capability it removed.
3. *Evidence decides where evidence exists.* A question whose row names a gate, a profile or a pilot is decided by
   that measurement and not by preference. Only the owner's questions are decided by judgement.
4. *A closed question is tombstoned, not reused.* Its identifier stays in the register with the ADR that closed it.
5. *The register adopts the identifiers the chapters defined.* A chapter's text governs the mechanism behind a
   question, and the gate register governs any threshold a question touches.

**2. The calendar (`[[owner_input]]` records in `registries/open.toml`, an additive table of schema `frob.open/1`
of N41-03: `milestone`, the milestone whose owner-input line lists the row; `question`, the identifier, or
`input: <text>` for the two inputs that have none (the M1 reading of the M0 ledger, the M8 funding per epic);
`ask`; `cost_of_default`).** A row with a question identifier copies nothing else: its default, `default_effect`,
`blocks`, `deadline` and `asked_at` are read from the question's `[[open]]` row, so the table below is a printout
of the two together and a difference between them is not possible. Only an `input:` row carries its own `default`
and `blocks`. The loader fails on an `[[owner_input]]` whose identifier has no `[[open]]` row, or that carries a
field the question's row owns.

The first column is the row's `milestone`: the milestone whose owner-input line lists it, at whose exit an answer
is wanted. A row of M(n+1) is what the exit of Mn prints as "asked now" (check c).

**3. What the defaults add up to (the test a default must pass before it is written).** If every question stayed
at its default, the program would still exit M0 to M5 and M7 (rehearsed in N40-32). The resulting product would be
a CPU-first studio with exploratory GPU results, no family policy, cheap rungs that only discard, generic cards
and assumed norms, no Reality claim, a ten-fold ratio labelled `self-adjudicated`, and a private repository. Every
one of those limits would be printed on the results it touches.

**4. Checks (`crates/frob-conformance/src/exit/owner_input.rs`, attached by this bead to step 10 of the exit runner
of N40-05 as the record `owner-calendar` of `scripts/exit/checks.toml`, since M0; it reads the query `due(Mn)` of
N41-03).** The crate `frob-conformance` has no binary of its own (BD-025), so the check is a subcommand,
`calendar`, that this bead adds to the example target `open_questions` which N41-03 declares
(`crates/frob-conformance/examples/open_questions.rs`; the subcommand's code is the module above). The record's
`command` is `cargo run -p frob-conformance --example open_questions -- calendar`, which the runner calls as
`cargo run -p frob-conformance --example open_questions -- calendar <Mn> --root <dir> --json`; it prints the one
JSON object of the attached-check contract and exits 0 whenever it ran. At the exit of Mn:
(a) every row of `due(Mn)` (deadline at or before Mn, not `closed`, whoever owns it) whose reading is `silent`
blocks the exit with the harness reason `open-decided-by-silence`: it must be `answered` (its deciding record, or
for an owner's question an ADR by the owner) or `defaulted` (an ADR recording the default, written with `cargo
run -p frob-conformance --example open_questions -- default <id> --exit <Mn>` of N41-03) before the exit. The deadline decides, not the gate named in `blocks`: OPEN-SPARK-1 has deadline M0
and blocks the M2 exit, so its answer or its default ADR is required at the M0 exit and is already in force
when M2 is reviewed;
(b) for every `defaulted` row, the capability or claim removed appears in the exit record's "capabilities removed"
section and the affected results carry the label; (c) print the `[[owner_input]]` rows of M(n+1) as "asked now";
(d) no result in the ledger since the deadline carries a claim that the default removes (for example a device
Performance claim while OPEN-SPARK-1 is at its default);
(e) at load, every `[[open]]` row whose `owner` is `Owner` and whose status is `open` has at least one
`[[owner_input]]` row whose `milestone` is at or before its deadline, so that no owner's question reaches its
deadline without having been put to the owner (the table above satisfies it for the 25 such rows at entry:
OPEN-PHYLUM-3; OPEN-SPARK-1, -2, -5; OPEN-SHIELD-2; OPEN-CORTEX-1; OPEN-AUGUR-4, -10; OPEN-CHRON-4;
OPEN-TETHER-5; OPEN-SUITE-3, -5; OPEN-SAFE-2, -3, -4; OPEN-PROG-1 to -5; OPEN-GAUNT-1; OPEN-TENFOLD-3, -4, -6,
-8);
(f) for each gate due at Mn whose status is `not-run`, name the `defaulted` questions whose `blocks` list holds
that gate, with the harness reason `open-default-blocks-exit`. The block itself is the gate query's (N40-04: a
`not-run` gate blocks); this check says which default is behind it, and the block clears when the gate has a
record. For OPEN-TENFOLD-4 at M3 that is the rule of N41-15: the strata that fit the default class recorded and
the others `not run` with the reason is a record; every stratum `not run` is not.

## Acceptance criteria

- [ ] The calendar loads with the rows above; every row has a default whose effect is in the closed set of clause 1.
- [ ] At each exit, a question due with neither an answer nor a default ADR blocks; with either, it does not.
      OPEN-SPARK-1 (deadline M0, blocks the M2 exit) blocks the M0 exit while `silent`.
- [ ] An `Owner` row with no `[[owner_input]]` row at or before its deadline is a load error; the 25 such rows at
      entry all load.
- [ ] A `not-run` gate due at the exit that a defaulted question lists in `blocks` is reported with that question
      and the reason `open-default-blocks-exit`; once the gate has a record the report is empty.
- [ ] The check is registered as `owner-calendar` in the exit runner's table, with the command `cargo run -p
      frob-conformance --example open_questions -- calendar`, and the runner propagates its blocks; no script
      of this bead names a `frob-conformance` binary.
- [ ] A defaulted question is reported with the capability it removed, and results after the deadline carry the
      label the default requires.
- [ ] A planted result that claims what a default removed is refused by check (d).
- [ ] The next milestone's questions are printed in each exit record.
- [ ] A closed question's identifier is never reused (the loader rejects a second, different question under a
      tombstoned identifier).

## Test plan

### Unit tests

`cargo test -p frob-conformance exit::owner_input::`.

- `default_effect_closed_set`: `"assume the catalogue price"` as a default → rejected (it adds a claim).
- `due_question_blocks`: OPEN-SPARK-1 (deadline M0) at the M0 exit with no ADR → blocks with
  `open-decided-by-silence`; with the default ADR → the exit proceeds; at the M2 exit with that ADR → the M2
  variant is expected and the exit proceeds; at the M2 exit with still no ADR → blocks. A row whose deadline is
  M2 does not block the M0 exit. Replayed through the runner of N40-05 with this check registered as
  `owner-calendar` (the runner's own test of that case uses a synthetic stand-in).
- `owner_rows_have_calendar_row`: a register in which OPEN-SPARK-5 has no `[[owner_input]]` row → load error
  naming it; a row for it at M3 (after its M2 deadline) → the same error; at M2 → loads.
- `default_behind_not_run_gate_named`: scratch M3 exit with GATE-TENFOLD-06 `not-run` and OPEN-TENFOLD-4
  `defaulted` → the report names the question with `open-default-blocks-exit`; with a gate record whose CPU

### End-to-end script and logging

`scripts/e2e/owner_input_calendar.sh`: on a synthetic register walks the exits M0 to M7 with every question left
unanswered; asserts that each exit blocks until the default ADRs are recorded, then proceeds (at the M3 exit the
synthetic gate register holds the partial ten-fold gate `not-run`: the report names OPEN-TENFOLD-4 by check (f),
and the walk proceeds once a record with the strata that fit the default class is supplied), and that the final
product description lists the seven limits of step 3; then plants a device Performance claim under the default of
OPEN-SPARK-1 and asserts the refusal; then plants a default that adds a claim (RC-53) and a reused tombstoned
identifier (RC-54) and asserts each load error. Logs through the STD-E2E helper to
`target/e2e-logs/owner_input_calendar/<utc>.ndjson`: per step `ts`, `script`, `bead`, `step`, `event`, command,
exit code, wall time, the evidence block `{claim: known-answer, class: Tested, tier: G0:host, determinism: D0,
seed: 0}`, per exit the questions due, answered, defaulted and asked next, the capabilities removed, the digest of
`registries/open.toml`, and on failure the first question with no record; the `summary` line counts assertions.

### Known answers and negative controls

Known answers: the calendar rows; the six in order; the seven limits of the all-defaults product (N40-KA R-29).
Negative controls: N40-CX RC-52 (a question decided by silence: deadline passed, no ADR, work proceeding on the
generous answer), RC-53 (a default that adds a claim), RC-54 (a tombstoned identifier reused), RC-59 (a calendar row with its own

`owner_rows_have_calendar_row`), RC-64 (a `not-run` gate behind a defaulted question reported with no question
named; caught by `default_behind_not_run_gate_named`).

## Considerations

- The calendar is a view of the question register, not a second register: each row cites its question's
  identifier, and the question's own bead governs its wording.
- An owner's late answer is welcome and does not rewrite history: the default ADR stays, a new ADR supersedes it
  from its date, and gates recorded under the default keep their records.
- Four questions were closed before implementation (two retired by architecture decisions; two decided by the
  owner: one toolchain T for the whole build graph, and the MCP server in the core graph running verbs in
  process). Four defaults are confirmed by the gate register and open only to new evidence: the anchored cell of
  8 m, the parity tolerance of 0.67, the rank-agreement pair (0.7, 0.5), and two revalidation verbs over one
  engine.
