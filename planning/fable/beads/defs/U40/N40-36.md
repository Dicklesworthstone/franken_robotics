## Background

The gate register is only worth having if a reader outside the implementing swarm can trust what it prints: that
"pass" means a measurement was taken, by someone other than the implementer, against a threshold fixed
beforehand, with a planted defect caught in the same run, and that the evidence can be followed from the printed
row back to the receipt. Each of those properties has unit tests in its own bead. This bead is the **end-to-end
test of the whole path**, driven from the user's side with the real binaries, on a real (small) gate: a
measurement is taken by the conformance harness, recorded by a fresh session, shows up in the generated status
table and in `frob capabilities`, resolves through `frob evidence trace`, and moves a milestone's exit report from
`not-ready` toward `exit-ready`; and every way of faking that path is refused.

It is one end-to-end bead for one user-visible capability: *the honest status of the program*. It is placed at M1
because the evidence trace (the artifact graph) lands at M1; a reduced form without the trace runs from M0.

## Scope

In: the script, its fixture gate, its assertions and its logging. Out: the mechanisms under test (N40-01, N40-02,
N40-04, N40-05, N40-10 and seeds BD-002, BD-025, BD-095); the kill-decision path (N40-37).

## Technical approach

**1. The fixture gate.** A real, cheap gate with a closed-form answer and a registered negative control is used so
that nothing is mocked: the admission gate INT-FSIM-02 on the host tier (power ⟨wrench, twist⟩ is frame-invariant
to 10⁻¹² relative; the analytic Jacobian agrees with central differences to 10⁻⁷ relative at 1,000 seeded
configurations), with its control (a deliberately reversed adjoint, which must fail at least three fixtures). Any
M0 gate with a host-tier test and a control can stand in; the script takes the gate identifier as a parameter and
defaults to this one. The fixture register is a scratch copy of the real one.

**2. The script** `scripts/e2e/gate_register_path.sh` (plain shell; idempotent; seed-explicit; sources the shared
helper of STD-E2E):

1. `start`: clone the working tree at HEAD into a scratch directory; record the commit and the register digest.
2. Baseline: `cargo xtask check-generated` (exit 0); `frob capabilities --json` (the fixture gate's capability is
   listed as *not implemented* or *partial*, because its row is `not-run`); regenerate the M0 exit report
   (`cargo test -p frob-conformance --test exit -- report --milestone M0`) and assert `not-ready` with the fixture
   gate in the blocking list. Assert that no row prints as passed.
3. Measure: `cargo test -p frob-conformance --test g1 -- INT-FSIM-02` with `--seed 1`; assert exit 0 and that a
   hash-named receipt was written; assert the receipt names the commit, the hardware fingerprint and the seed.
4. Control: run the same target with the control `NC-…` enabled; assert the gate's test *fails* (the control is
   caught) and that `last_seen.caught = true` is written for this run.
5. Record as a fresh session: enter the row's part with the receipt, `session = e2e-fresh`,
   `implemented_by = e2e-impl`; assert the validator accepts it.
6. Views: `cargo xtask check-generated` after regeneration (exit 0); the README table shows the gate as `pass` with
   its measured value; `frob capabilities --json` shows the measured value and not the target; the M0 exit report
   no longer lists the gate as blocking.
7. Trace: `frob evidence trace <claim_id> --json`; assert the closure contains the receipt, the control run and
   the execution, that every hash recomputes, and that the envelope's evidence block names the claim kind (Known
   answer), class, tier, determinism class, identities and seed.
8. Refusals, each in a fresh scratch copy, each asserting a non-zero exit and the reason string:
   (a) record with `controls = []` → `pass-without-control`; (b) record while the control was not caught →
   `control-not-caught`; (c) record with `session == implemented_by` → `self-certified`; (d) cite a receipt hash
   that does not exist → `evidence-unresolved`; (e) copy the threshold text into `measured` →
   `target-as-measurement`; (f) edit the README table by hand to say `pass` → `check-generated` fails; (g) delete
   the receipt after recording → `frob evidence trace` prints `evidence: unavailable` and the exit report voids
   the pass; (h) move the part's milestone to a later exit with no ADR → `moved-later-without-adr`.
9. Late gate: assert that GATE-WS-05 (a gate of a later subsection, due at M0) appears in the M0 exit report and
   in the regenerated register printout inside the workspace table.
10. `end`: print the summary.

**3. Logging (structured newline-delimited JSON to `target/e2e-logs/gate_register_path/<utc>.ndjson`, with a
human-readable transcript beside it).** Every line: `ts`, `script`, `bead` (`N40-36`), `step`, `event` (`start`,
`cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code, wall time, the envelope's
`evidence` block where a verb returned one, measured values with units and thresholds (the two relative errors beside 10⁻¹² and 10⁻⁷, the
count of fixtures the control failed against 3), digests where state is compared (register before and after, receipt,
README table), and on failure the first differing value and the artifact paths needed to reproduce. A final
`summary` line gives assertions passed and failed and the gates touched (GATE-GAUNT-01, GATE-GAUNT-10,
GATE-CHRON-10, and the fixture gate).

## Acceptance criteria

- [ ] The script exits 0 on a clean tree and non-zero if any assertion fails; a second run in the same tree gives
      the same result (idempotent).
- [ ] Before the measurement nothing prints as passed; after a valid record exactly the fixture gate changes.
- [ ] Each of the eight refusals of step 8 fires with its reason.
- [ ] The evidence trace resolves from the printed row to the receipt and its hashes recompute.
- [ ] The late gate is present in the exit report and the printout.
- [ ] The log has one `cmd` line per command with exit code and wall time, one `assert` line per assertion, one
      `refusal` line per refusal, and a `summary` line; it contains no private-scene data.
- [ ] The script runs in under 3 minutes on the CPU tier (TARGET) and is part of the exit runner for every
      milestone.

## Test plan

### Unit tests

None of its own: this bead is a test. Its helper functions in the shared shell library (JSON field extraction,
digest comparison) are covered by STD-E2E's tests. A self-test `scripts/e2e/gate_register_path.sh --selftest`
plants a deliberately wrong expected value and asserts that the script fails and logs the first differing value.

### End-to-end script and logging

As specified in the technical approach: `scripts/e2e/gate_register_path.sh [--gate <identifier>] [--seed N]`.

### Known answers and negative controls

Known answers: the fixture gate's own (10⁻¹² and 10⁻⁷ relative; the control fails at least three fixtures); the M0 due
counts before recording (23 admission, 11 convergence, 2 kill decisions, 8 late parts). Negative controls: the
eight refusals (N40-CX RC-01 to RC-06, RC-14, and RC-55, a deleted receipt behind a recorded pass). Determinism
lanes: the script is run twice on one machine and its register and report digests compared; in debug and release;
on macOS and on Linux; the digests must be equal in each lane because every step is a pure function of the tree
and the seed.

## Considerations

- The script uses a scratch copy and never writes to the real `registries/gates.toml`.
- If the fixture gate's mechanism is not yet implemented when this bead is first run, the script's baseline half
  (steps 1, 2, 8f, 9) still runs and the rest is reported as `skipped: fixture not implemented`, which is a
  failure at any exit.
- The script is deliberately small and fast so that it is run and not skipped.
