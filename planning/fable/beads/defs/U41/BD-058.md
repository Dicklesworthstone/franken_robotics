## Background

A design is immutable: nothing is modified in place. Every change is a **typed edit** that takes one design to
another, and a design's history is a path of edits in a content-addressed lineage graph. Edits are the morphisms of
the design category. Each edit kind has preconditions, an inverse where one exists, a declared effect on the two
symmetry groups (the mechanical group Γ_mech and its observation-preserving subgroup Γ_obs), and a scope of
invalidation that the compile pipeline computes and the catalogue predicts.

This bead builds the engine and its single-edit verb `design.edit` in `frob-design` (layer 2, tier Solid). It serves
the studio loop (an agent edits, checks, simulates, compares), the optimizers (which move declared levers only,
ADR-SKEL-07) and lineage tools (diff, blame, bisect), all of which need edits that are named, checkable and
reversible.

Why typed edits and not free-form patches of JSON (the rejected alternative): a text patch can write a derived
inertia, change a number an optimizer was never meant to free, or break a symmetry without anyone being told. A
typed edit states which field class it touches, so the engine can refuse an edit to a locked path, report the
symmetry effect before the edit is committed, and name the inverse. The standing rule is refusal instead of repair
in silence: an invalid edit is refused with a stable code and ranked repairs that are themselves typed edits.

## Scope

In: the `EditOp` type for every kind of the catalogue; per-kind preconditions; application to the unexpanded term;
instance-scoped edits that split a constructor; the inverse of each applied edit; the declared symmetry effect; the
verb `design.edit` with schemas, the CLI target grammar (term paths, instance selectors, `--joints`, bare and
two-value forms), idempotency and expected parent through the admission transaction (N32a-09); the edit record;
the lock check on an edit's write set, which every edit path calls (the lever handle of N14a-06, `design.patch`,
`module.substitute`); the **design store** that every design verb commits through (versions, named heads moved
only by compare-and-swap, edit records; below). This is the first bead in build order that commits a design
version, and no other bead owned the store: `design.new` (N14a-21), `design.patch` (BD-059) and the stale-parent
branch of N32a-09 all read or write it.

Out: multi-operation patches, `require` analyses and the stale-parent diff (BD-059; this verb shares the engine and
the store); the catalogue's conformance against computed symmetry and invalidation (N14a-17); the computed
invalidation set (BD-063); `swap-module` classification as leaf-local or global (BD-077); `migrate` semantics and
certificates (N14a-18); the lineage tables over the edit records and the queries diff and blame (BD-113); the
edit kind `extract-module`, which turns a subterm into a `frob.module/1` file and needs the module format of BD-060
(a later seed), as row 23 of the catalogue (N41p2-01); creating a named design (`design.new`, N14a-21, which
depends on this bead through the lever interface); the end-to-end script through `frob` and `frob-mcp`, which needs
`design.new` to create the design it edits and therefore runs in N41p2-02.

The catalogue file `registries/edits.toml` is shared with N14a-17, which depends on this bead. Its schema, the
same in both beads (DESIGN): one `[[edit]]` per row with `row` (1 to 22), `kinds` (the operation names the row
groups; the union over the 22 rows is the 32 kinds listed below), `example`, `symmetry_effect`, `scope` and
`fixture`. The division:

- This bead creates the file and its loader, and enters for every row the fields the engine reads: `row`,
  `kinds`, `example`, `symmetry_effect` and `scope`. The values are transcribed from the catalogue table, which
  is printed once, in N14a-17, together with the vocabularies of the two prediction columns (seven values of
  `symmetry_effect`; the product classes of `scope`); this bead does not print a second copy. The engine
  compares the union of `kinds` with its own set of `EditOp` kinds, resolves a row's `symmetry_effect` to the
  declared effect of one edit (below), and copies `scope` into the result as the predicted scope.
- N14a-17 owns the file from then on: it adds the `fixture` of each row, tests the declared effect against the
  computed groups and the predicted scope against the computed invalidation set, and corrects a row the test
  shows to be wrong or too wide. The inverse law is tested here on identifiers (one fixture per kind in this
  bead's test module, and generated edits); N14a-17 repeats it on the catalogue's fixtures through to
  bit-identical compiled products.

Until BD-063 lands, a result carries the predicted scope and no `invalidation.set`; until the symmetry functor
N14a-11 is in the build, it carries the declared effect and no computed one.

## Technical approach

Layout (DESIGN): `crates/frob-design/src/edit/{op.rs, pre.rs, apply.rs, inverse.rs, scope.rs}`; verb handler in
`crates/frob-verbs/src/design/edit.rs`.

```rust
// DESIGN sketch: intent, not signatures.
pub struct EditOp { kind: EditKind, target: Target, args: Term }
pub enum Target { Path(Path),                    // into the unexpanded term: every image changes
                  Instance(InstanceId, Path) }   // one image only: splits the enclosing constructor
pub struct Applied { design: Design, edit_id: Blake3,   // hash of (parent DesignId, canonical op)
                     inverse: Vec<EditOp>,              // empty when no inverse exists; else 1 or 2 ops
                     symmetry: SymmetryEffect, predicted_scope: Scope, diff: TermDiff }
pub fn apply(parent: &Design, op: &EditOp, locks: &LockSet) -> Result<Applied, Refusal>;
```

**The kinds** (operation names inside the 22 catalogue rows): `set-param`; `regear`; `swap-actuator`; `add-limb`,
`remove-limb`; `move-mount`; `reshape`; `mirror`, `radial` (with `mode: wrap | fuse | unwrap`); `closure-add`,
`closure-remove`; `set-fill`; `set-material`; `set-limits`; `set-contact-law`; `swap-module`; `add-sensor`,
`move-sensor`, `remove-sensor`; `retime`; `add-payload`, `move-payload` (with `remove: true` as the inverse form);
`set-bus`, `swap-battery`; `set-budget`; `declare-lever` (with `remove: true`), `set-lever`, `lock`, `unlock`;
`assert-symmetry`; `rename`; `migrate`. The engine's set of row kinds must equal the catalogue's. The engine's kind
registry is open to extension by a later bead only together with a catalogue row: N41p2-01 adds row 23
(`extract-module`, with `inline: true` as its inverse form) to the file and its kind to the engine in one change,
which makes 23 rows and 33 kinds.

**Application, as numbered steps.**

1. Resolve the target. A `Path` must name an existing node of the kind the edit requires; otherwise `FROB-REF-103`
   with the nearest existing path.
2. Check locks: a write to a path in `locks`, or under a locked block name, refuses with `FROB-REF-111` unless the
   edit is `unlock`. A `set-lever` outside the lever's bounds or off its manifold refuses with `FROB-REF-111`.
3. Check the kind's preconditions (table below). All use exact quantities; units are checked before values.
4. If the target is an `Instance` under a `mirror`, `radial` or `serial`, first split the constructor: rewrite it
   into explicit `attach` subterms using the constructors' own reflection and rotation rules (BD-056's `images` and
   `reflect_component`, so the split design elaborates to an equal instance tree and compiles to a bit-identical
   model), then apply the edit to the one named image. The result lists the split constructors by term path in
   `symmetry.split`.
5. Rewrite the term, canonicalize, and compute the new `DesignId`. A derived inertia is never an edit target:
   inertia follows geometry (Region, fill, material); only a `declared` body's mass properties are data.
6. Build the inverse (below), the diff (structural and parameter), the declared symmetry effect and the predicted
   scope from the catalogue row; attach the computed symmetry and the computed invalidation set when the functors
   are present in the build.
7. Commit through the design store (below): insert the version, the edit record (`edit_id`, parent, child,
   canonical op, inverse, caller namespace, idempotency key) and move the head, in the one transaction of the
   admission protocol (N32a-09).

**The design store** (DESIGN; tables in the database of the job ledger, the one N32a-09's admission transaction
runs in, so that the binding, the stale-parent check and the head move are atomic):

```
design_version(design_id PRIMARY KEY, canonical_bytes BLOB, schema, canon_rev, created_seq)  -- write-once
design_head(namespace, name, head, updated_seq, UNIQUE(namespace, name))
design_edit_record(edit_id, parent, child, kind,          -- kind: edit | patch | new
                   ops_canonical, inverse_canonical, patch_id, namespace, idempotency_key, seq)
```

- Versions are content-addressed: inserting an existing `design_id` is a no-op, and a row is never updated.
- A head moves only by compare-and-swap (`UPDATE design_head SET head = child WHERE namespace = ? AND name = ?
  AND head = parent`); zero rows updated means a stale parent, which each verb reports with its own code and the
  current head (`design.edit` and `design.new`: `FROB-REF-804`; `design.patch`, whose document names the parent:
  `FROB-REF-112`; exit 7 for all). A create (`design.new`) is a compare-and-swap from absent: an existing name is
  the same conflict.
- One edit record per committed version, written in the same transaction as the version and the head move:
  `design.edit` writes kind `edit` with one op; `design.patch` (BD-059) writes kind `patch` with the ordered ops
  and its patch id; `design.new` writes kind `new` with no parent. BD-113 builds the lineage graph (nodes, edges,
  diff, blame) over these records and does not write a second history.
- API (DESIGN): `Store::get(DesignId)`, `Store::head(ns, name)`, `Store::commit(ns, name, expected_parent,
  child, record) -> Result<(), StaleParent>`, `Store::create(ns, name, design, record)`. The verbs call nothing
  lower.

| `set-limits` | Non-empty, non-inverted interval per coordinate, or `unbounded` | `FROB-REF-107` |

| `migrate` | A registered migration exists for the schema pair | `FROB-REF-125` |

**Inverses.** For a value-setting kind the inverse is the same kind with the parent's value at that path; for a
paired kind it is the partner (`add-limb` ↔ `remove-limb` carrying the removed subterm, `closure-add` ↔
`closure-remove`, `lock` ↔ `unlock`, `add-sensor` ↔ `remove-sensor`, `wrap` ↔ `unwrap`); `rename` renames back;
`assert-symmetry` restores the previous assertion or removes it. An instance-scoped edit has a two-operation inverse:
set the value back on the image, then `fuse` the images into the original constructor (the `fuse` precondition
proves they are exact images again). `migrate` has no inverse: the old object stays in place and old runs replay
against it. Law (the seed condition): for every edit with an inverse, applying the inverse to the child yields a
design whose `DesignId` equals the parent's.

**Symmetry effect** (declared; one of `preserved`, `reported`, `grows`, `none`, with the row's qualifier). An edit
through a `Path` under a constructor is `preserved` for the value-setting kinds; the same edit through an `Instance`
is declared `reported` and carries `symmetry.split`, the term paths of the constructors it split (the generators
the term no longer carries, which is how a caller sees "broken if applied to one leg" before the groups are
computed). The declaration never replaces the computed groups (INV-SKEL-07); when the symmetry functor is present,
the result carries both and a disagreement is a finding against the catalogue.

The four values are the effect declared for one edit. The catalogue row holds one of the seven values of
N14a-17's `symmetry_effect`, and the engine resolves it for the edit at hand (DESIGN; one mapping, stated here
and used by N14a-17's test): `none` → `none`; `preserved` → `preserved`; `grows` → `grows`; `reported` →
`reported`; `preserved-under-constructor` → `preserved` when the target is a `Path` under a `mirror` or
`radial`, so that the edit applies to every instance, and `reported` otherwise (an `Instance` target, or a path
under no constructor); `mech-preserved-obs-recomputed` → `reported` with the qualifier `obs` (Γ_mech declared
unchanged; Γ_obs carried before and after); `both-recomputed` → `reported` with the qualifier `both`. A row
whose table text adds a case ("broken if applied to one leg", "a one-sided change is reported") resolves to
`reported` in that case.

**Verb.** `design.edit`, kind `mutate`, cluster `design`, first milestone M1, capability `design:write`.

- CLI (the form the registry example and the plan's sessions use): `frob design edit <design> <op> <target>
  [<value>…] [--instance <id>] [--expected-parent <id>] --key <k> --json`, for example `frob design edit quad-a
  set-param /limbs/of/of/chain/1/body/region/capsule/1 "0.24 m" --expected-parent d:7a3e… --key agent-7/turn-41/a
  --json`, `frob design edit quad-a set-param foot.radius 0.030 m --key ed-1 --json` and `frob design edit quad-a
  swap-actuator --joints '*.knee' --to qdd-l --key ed-2 --json`. `<design>` is a name (resolved to its head, echoed
  in `bound`) or a `DesignId`.
- Targets (DESIGN). `<target>` is either a JSON pointer into the term (begins with `/`), or a **selector**
  `<instance pattern>.<field>`; kinds that act on joints also take `--joints <pattern>`. A pattern is matched
  against the instance identifiers of the parent's identifier map (N14a-07) segment by segment from the right; `*`
  matches one segment, so `knee`, `*.knee` and `leg.*.knee` all match `leg.fl.knee`. The field is a dotted path
  relative to the matched node (`region.sphere`, `transmission.belt.ratio`) or one of two aliases, `radius` (a
  sphere's radius; element 0 of a capsule or cylinder) and `length` (element 1 of a capsule or cylinder); an alias
  on another Region kind refuses with `FROB-REF-103` listing the explicit paths. The matched set resolves to: the
  term path of one constructor subterm when it is exactly every image of that subterm (an edit to all images,
  `preserved`; `foot.radius` and `--joints '*.knee'` on `quad-a` resolve this way); an `Instance` target when it is
  one instance under a constructor, or when `--instance` names one (split, `reported`); the node's own path when it
  is one instance under no constructor. Any other match set refuses with `FROB-REF-103`, listing the matches and
  the two resolvable alternatives. The resolved target is echoed in the answer as a term path.
- Values. A value carries its unit token (`0.030 m`); a bare number is read in the coherent SI unit of the
  target's dimension and echoed with that unit (DESIGN: the plan's sessions write `foot.radius 0.022 0.030`).
  Two values after a quantity target (`set-param foot.radius 0.022 0.030`) mean *expected current value, new
  value*: if the parent's value differs from the first, the edit refuses with `FROB-REF-804` (exit 7), its payload
  naming the field, the expected and the current value and the current head (DESIGN: a field-level stale read is
  the same conflict as a stale parent; N32-REF's row of 804 carries this trigger, its payload fields `field`,
  `expected` and `current`, and the repair: read the field at the head and resubmit).
- Input schema `frob.design.edit.in/1`: `design`, `op` (kind, path, selector or instance, args), `expected_parent`,
  `idempotency_key`. Output schema `frob.design.edit.out/1`: `design_id`, `parent`, `edit_id`, `resolved_target`,
  `inverse`, `diff`, `symmetry {declared, split, computed}`, `invalidation {predicted_scope, set}`, in the standard
  envelope with the claim product (kind Structural, class `Tested`, determinism D0, all no-authorization flags
  false).
- Idempotency and the stale parent go through the admission transaction of N32a-09 (one atomic binding of
  principal, verb, key and request digest): the same key with the same parent and op returns the version already
  created; the same key with different content refuses with `FROB-REF-803` (exit 7, both resolutions shown); a call
  without a key refuses with `FROB-REF-805` (exit 3, before anything is written); an `expected_parent` that is not
  the head of the lineage refuses with `FROB-REF-804` (exit 7) and returns the current head. `FROB-REF-112` is not
  raised here: it is the stale `parent` field inside a `design.patch` document (BD-059).
- Exit codes: 0 on success; 3 on a refusal of the edit, with the code, the path, the observed value and ranked
  repairs as typed edits; 7 on a conflict (803, 804). The registry entry lists `FROB-REF-101, -102, -103, -105,
  -106, -107, -108, -111, -114, -121, -123, -125, -126` and the surface codes `FROB-REF-803, -804, -805`.

## Acceptance criteria

- [ ] Every row kind of `registries/edits.toml` has an `EditOp` implementation and a fixture; the two sets are equal.
- [ ] For every kind with an inverse, on its fixture and on 10⁴ generated edits, edit followed by inverse returns the
      parent's `DesignId` (the seed condition), including the two-operation inverse of an instance-scoped edit.
- [ ] `set-param` on the thigh length through the term path changes all four legs and is declared `preserved`; the
      same edit with `--instance leg.fl` splits the constructors, changes one leg, is declared `reported` and lists
      both mirrors in `symmetry.split`.
- [ ] The split of a constructor by itself (before the value is changed) elaborates (N14a-07) to an instance tree
      equal to the original's up to identifiers, source sets and the parity record. The same split compiled to a
      bit-identical model is asserted by N14a-17 on the catalogue fixtures (the kinematic functor BD-061 is a later
      seed).
- [ ] The selector forms resolve as stated: `foot.radius` and `--joints '*.knee'` on `quad-a` to the leg subterm's
      path (`preserved`, no split); `leg.fl.knee` to one instance (split); `leg.fl.*.radius`, matching several
      distinct nodes, refuses with `FROB-REF-103` and lists the matches; a bare number is echoed with its SI unit; the
      two-value form with a wrong expected value refuses with `FROB-REF-804`, exit 7.
- [ ] An edit to a locked path refuses with `FROB-REF-111`; after `unlock` it succeeds.
- [ ] An attempt to write a derived inertia is refused; a `declared` body's mass properties are editable.
- [ ] Each precondition row is exercised by a planted edit that returns its code, exit status 3 and a repair.
- [ ] The verb's executor (`cargo test -p frob-verbs design_edit`, on a design created with `Store::create`)
      returns one envelope with the claim product; a repeated idempotency key returns the same version; the
      same key with another op refuses with `FROB-REF-803` (exit 7); a call without a key refuses with
      `FROB-REF-805` (exit 3); a stale `expected_parent` refuses with `FROB-REF-804` (exit 7) and names the head.
      The same through the `frob` binary and through `frob-mcp` (tool `design_edit`) is asserted by N41p2-02.
- [ ] The design store: two edits on one head with the same expected parent, in 100 seeded interleavings, give
      exactly one commit and one `FROB-REF-804`; every committed version has exactly one edit record and a
      version row written in the same transaction (fault injection between the inserts leaves neither); a
      version row is never updated.
- [ ] `CONTRACT.md` of `frob-design` documents kinds, preconditions, inverses and refusals; the verb has its
      registry entry, schemas and exit-code table.
- [ ] Open clauses of the definition of implemented: the gate record (the patch gate GATE-SKEL-08 and the functor
      gate GATE-SKEL-02 close in BD-059 and BD-063).

### End-to-end script and logging
The script `scripts/e2e/design_edit.sh` needs a named design to edit, and the verb that creates one (`design.new`,
N14a-21) depends on this bead through the lever interface (N14a-06), so the script is written and run by N41p2-02,
which depends on both. Its content, fixed here so that the two beads agree: create `quad-a` from the worked
quadruped file with `frob design new`; run `frob design edit` for `set-param` (term path), `set-param foot.radius
0.030 m` (selector), `set-fill`, `swap-actuator --joints '*.knee' --to qdd-l` (all images, no split) and
`swap-actuator --instance leg.fl` (split), each followed by its returned inverse; assert each answer's `parent` is
the previous `design_id`, its declared effect and `symmetry.split` match the catalogue row and the target form, and
the final `DesignId` equals the first; the key replay (same `design_id`), the key reuse (803, exit 7), the missing
key (805, exit 3), the stale `--expected-parent` and the wrong two-value expectation (804, exit 7); six refusal
fixtures; the first edit repeated over `frob-mcp` (tool `design_edit`) with the same `design_id`. This bead
delivers the fixtures it reads: `fixtures/edits/quad-a.fbot` and the six refusal fixtures
`fixtures/edits/refuse_*.json`, each with its expected code and exit in `fixtures/edits/expect.toml`.

### Known answers and negative controls
- Known answer: edit then inverse returns the same `DesignId` (exact). The mirror-swap and shared-bus rows of the
  substitution known answer are tested where the invalidation set exists (BD-063, BD-077).
- Negative controls (mutants): an inverse built from the child's value instead of the parent's (the law fails); an
  engine that applies an instance edit to all images (the split test fails); an engine that skips the lock check;
  an engine that lets a `set-param` write `mass_properties` of a non-declared body; a selector resolver that sends a
  match of every image to `Instance` (an unnecessary split: `selector_resolution` and the e2e's no-split assert
  fail).
- Metamorphic: two edits on disjoint paths commute (same final `DesignId` in either order); `rename` changes the
  `DesignId` and no mechanical product.
- Determinism lanes: twice on one machine; debug and release; Linux and macOS: identical identifiers.

## Considerations

- The `fuse` and `unwrap` modes and the `remove` forms are DESIGN additions inside existing catalogue rows, made so
  that every edit except `migrate` has an inverse expressible as typed edits; they add no row kind.
- A split is visible in the term and in the lineage: an agent that edits one leg sees the constructor replaced by
  explicit limbs, which is the honest record that the symmetry is gone.
- Rollouts are never reused across a mass or geometry edit; which verdicts survive an edit is decided from recorded
  read sets (BD-063), not from this bead's predicted scope.
- Security: edit arguments are data; imported text in `rename` or `meta` is marked untrusted and never interpreted.
- What would make us revisit: a kind whose inverse cannot be made exact (then the row states "no inverse" and the
  law excludes it by name, never silently).
