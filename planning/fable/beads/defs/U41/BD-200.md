## Background

Domain randomization draws the parameters of each simulated world from a distribution so that a policy, or a design
verdict, does not fit one parameter set. In most simulators the ranges are free-floating numbers in a task file,
which nobody can trace to what is known about the hardware. Here the rule is (DESIGN): **every randomized parameter
traces to an uncertainty on a card** (an actuator, interface, material or sensor card with per-field provenance and
uncertainty), and there are no free-floating ranges. The consequences are what make the rule worth a bead:

- a verdict under randomization is a statement over the card's band, and a verdict that changes sign inside that
  band can be labelled card-conditional with the field that decides it;
- every tier reads the same card, so agreement between tiers says nothing about the card; randomizing over its
  stated uncertainty is one of the three defences against that common-mode error;
- a randomization width cannot be narrowed by editing a task: it narrows only when a card is updated after an
  admitted validation.

The second half of the bead is how the values are drawn: **by address**. A drawn value is a pure function of the
world address, the registered stream of the parameter and the physical entity it belongs to, so two runs at one
address draw the same value in any batch, any world replays alone, and two designs compared at the same addresses
see the same floors and the same gusts. Tier Solid; crate `frob-learn` (Cortex), reading cards from `frob-actuate`
and the contact and sensor crates, and writing the per-world parameter row of the batched step.

Rejected alternatives: ranges in the task file (untraceable, and silently wider or narrower than what is known); a
per-environment generator seeded once (draws depend on slot and on how many parameters come before); randomizing
numerical parameters together with physical ones (a smaller time step would silently stiffen a fitted foot spring).

## Scope

In: the `randomize` block of a task as compiled into a randomization plan; resolution of each entry to a card
field band and to a parameter-row column; the no-interval refusal; the laws (uniform on an interval, truncated
normal from a spread); the addressed draw at reset; the list of resolved values handed to the episode record; the
summary on results. Out: storing resolved values in episode records, the objective over the randomization (mean
or a tail measure) and the held-out rule (N23b-03); adaptive reweighting inside a card's support (N23b-04,
Frontier); numerical perturbations as exploitation detectors (their own bead); scene and layout randomization and
shared latents such as wetness (the scene beads); sensor noise draws per sample (the sensing beads).

## Technical approach

Module (DESIGN): `crates/frob-learn/src/randomize/{plan.rs, resolve.rs, draw.rs}`; kernel `K-randomize` in
`frob-kernels` (floating, D2) for device-resident parameter rows.

**Task syntax** (inside `.ftask`; DESIGN spelling):

```toml
[[randomize]]
target = "actuator:knee#torque_constant"      # card reference and field path; resolved per instance
scope  = "episode"                            # episode | run
law    = "card"                               # the card's own law; the only Solid choice
[[randomize]]
target = "interface:rubber-60a/tile#mu"
scope  = "episode"
entity = "tile"                               # keyed by the physical thing, not by the design
```

**Compilation to a plan** (at environment admission; refusals come before any world exists).

1. Resolve `target` to concrete card instances of the admitted designs and scene (every knee actuator; every tile
   region) and to the parameter-row column that carries the field on the batched tiers. A field with no column is
   refused with the list of randomizable fields (level P-A carries link lengths, inertias, gear ratios,
   actuator-card parameters, foot radii and friction).
2. Read the field's band. Admitted uncertainties and their laws:

   | Card uncertainty | Law | Support |
   |---|---|---|
   | `interval [lo, hi]`, or an `abs` or `rel` half-width | Uniform | The interval |
   | `normal` with σ | Normal with mean the nominal value | The card field's validity bounds where stated, else nominal ± 4σ; the truncation is written into the plan |
   | `exact`, or no uncertainty | None | Refused |

3. **The refusal** (seed condition). A field whose uncertainty is `exact` or absent refuses randomization: refusal
   `randomize-no-interval` (exit code 3), with `observed` = the field and its provenance, and ranked repairs:
   (a) state an uncertainty on the card (a new card version with provenance); (b) override the field in the design
   with provenance `designed` and an interval; (c) remove the entry.
4. Check that the entry names a physical parameter. A numerical parameter (time step, iteration count, stiction
   speed, regularization) is refused here with a pointer to the detectors that vary those.
5. Assign the stream: the registered stream `param` with `entity` = the 64-bit hash of (card field path, instance
   port name or tile index). The instance port name, not a running index, identifies an actuator, so adding a leg
   shifts no other leg's draw.
6. Emit `RandomizationPlan { entries: [{column, law, lo, hi, nominal, sigma, stream, entity, scope}], id }`; its
   content hash enters the task identity.

**Drawing** (at reset under the reset mask; `scope = "run"` draws once with episode fixed at 0).

1. For world address a and entry e: x = the first word of the draw block at (a, stream `param`, e.entity,
   step = 0, index = 0); u = (x ≫ 8)·2⁻²⁴.
2. Uniform: value = lo + u·(hi − lo), evaluated in the parameter row's precision with no fused multiply-add; the
   result is clamped into [lo, hi] by select (the product can round up by one unit in the last place).
3. Normal: attempt j = 0 … 7 uses index j: n_j from the addressed normal pair; candidate = nominal + σ·n_j; the
   first candidate inside the support is taken. If none is, the value is clamped to the nearer bound and the
   episode is flagged `randomization-clamped`. Every attempt is addressed, so the result is still a pure function
   of the address.
4. Write the value into the world's parameter row; append (path, instance, stream, entity, value with unit,
   support, law) to the episode's resolved list.

**Results.** Every result of a randomized run carries, in its claim product's model identity, the plan
identifier, and in its summary the share of randomized fields by provenance (`measured`, `datasheet`, `generic`,
`assumed`). Evidence class is set by the weakest card field read; randomization never raises it.

**Surfaces.** No new verb: the plan is compiled by every verb that creates an environment (`sim.run`, `eval.run`,
`train.start`), which returns the plan summary and the refusal. `frob task check <task> --design <d> --json`
(the task admission path) reports the same refusal without running anything.

## Acceptance criteria

- [ ] Seed condition: a task that randomizes a card field whose uncertainty is `exact` or absent is refused before
      any world is created, with the field named and the three repairs; exit code 3 on the CLI and the same refusal
      over MCP.
- [ ] Seed condition: for 1,000 addresses, the resolved values of every entry are bit-identical when the world
      runs alone, in batches of 64 and 4,096, under slot permutation, at two bucket capacities, on one and two
      shards, and when replayed with `sim.replay`.
- [ ] The same address gives the same interface friction per tile for two designs with different leg counts; the
      per-instance actuator draws of legs present in both designs are equal.
- [ ] 10⁶ uniform draws lie in [lo, hi] inclusive and their mean and variance are within three standard errors of
      (lo + hi)/2 and (hi − lo)²/12; truncated-normal draws lie in the support.
- [ ] A numerical parameter in `randomize` is refused; a field with no parameter-row column is refused with the
      list of randomizable fields.
- [ ] Changing a card's interval changes the plan identifier and the task identity; changing nothing reproduces
      both.
- [ ] The resolved list handed to the episode record has one entry per (entry, instance) with unit and support.
- [ ] `CONTRACT.md` of `frob-learn` documents the laws, the truncation rule, the refusal and the streams used.
- [ ] Open clauses of the definition of implemented: the gate record (the task-family gate GATE-ARENA-01 and the
      composition-invariance gate GATE-SPARK-15 close in their own beads); the device differential check of
      `K-randomize`.

## Test plan

### Unit tests
`crates/frob-learn/tests/randomize.rs`; real cards from the generic catalog, no mocks.
- `exact_field_refused`: gear ratio fixed by tooth counts (`exact`) → `randomize-no-interval`, repairs listed.
- `missing_uncertainty_refused` (a synthetic card built through the override path).
- `uniform_known_value`: lo = 0.4, hi = 0.8, x = 0x80000000: u = 0.5 exactly, value 0.6 (to one unit in the last
  place in `f32`); x = 0xFFFFFFFF: u = 1 − 2⁻²⁴, value ≤ 0.8.
- `uniform_moments_1e6`; `truncated_normal_support`; `clamp_flag_after_eight_attempts` (σ so large that the support
  is rarely hit, with a planted address whose eight candidates all miss).
- `same_address_any_batch` (the seed test); `replay_alone_same_values`.
- `extra_leg_shifts_nothing`: quadruped and five-legged variant share tile frictions and the four common knees'
  torque constants.
- `numerical_parameter_refused`; `no_column_refused_with_list`.
- `plan_id_changes_with_card_interval`.
- Mutants: `index_by_instance_order` (entity from a running index: the extra-leg test fails);
  `draw_by_slot` (the batch test fails); `range_from_task_file` (a planted `range = [0, 2]` key in the task is an
  unknown field and refuses; a build that honours it fails the traceability test).

### End-to-end script and logging
`scripts/e2e/randomization_from_cards.sh`: (1) `frob task check fixtures/velocity-flat.ftask --design
fixtures/quad-a.fbot --json` with an entry on an `exact` field: expect exit 3 and the refusal; (2) the corrected
task run with `frob sim run --tier batch-cpu --worlds 64 --seed 21 --json`, then with `--worlds 4096`, then one
world replayed alone with `frob sim replay`: assert equal resolved values for the common addresses; (3) the same
with the five-legged design: assert equal tile frictions. Logs: `cmd`, exit code, wall time, evidence block with
plan identifier and seed, `refusal` with code and repairs, digests of the resolved-value tables with the first
differing (address, entry) on failure, `metric` lines for the provenance shares, a `summary`.

### Known answers and negative controls
- KA-793 and KA-795 applied to parameters (addressed draws; the extra-leg case); counterexample CX-143
  (agreement between the referee and the fast tiers is not evidence that the card is right; randomization over the
  card's band is the defence this bead supplies).
- Negative controls: the three mutants; the planted `exact` field; the planted numerical parameter.
- Metamorphic: reordering `randomize` entries in the task changes no drawn value; adding an entry changes no other
  entry's values.
- Determinism lanes: twice on one machine; across worker counts and batch sizes; `batch-cpu` in `f32` and `f64`
  each against its own precision; devices later against their class (the integer draws are D0 everywhere).

## Considerations

- Randomization width from a card does not narrow without an admitted validation (INV-GROUND-05): a candidate
  posterior from a fit leaves the plan unchanged.
- A range beyond the card is not available here; where it is offered later it is labelled `beyond-card` and its
  results cannot be cited for the carded hardware.
- Correlated fields (a wet floor that lowers friction and changes optics together) are drawn once through a shared
  latent by the scene, not by two entries here.
- With generic cards most bands are `assumed`; results then stay `Estimated`, and `--strict-data` refuses a verdict
  that rests on them. That is the fail-closed state until catalog data with provenance is admitted.
- What would make us revisit: geometry randomization that changes the tree (it is a model variant, not a parameter
  row), or a parameter whose law needs correlation inside one card.
