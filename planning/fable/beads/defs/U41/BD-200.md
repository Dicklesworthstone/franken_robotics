## Background

Domain randomization draws the parameters of each simulated world from a distribution so that a policy, or a design
verdict, does not fit one parameter set. In most simulators the ranges are free-floating numbers in a task file,
which nobody can trace to what is known about the hardware. Here the rule is (DESIGN): **every randomized parameter
traces to an uncertainty on a card** (an actuator, interface, material or sensor card with per-field provenance and
uncertainty), and there are no free-floating ranges. The consequences are what make the rule worth a bead:

- a verdict under randomization is a statement over the card's band, and a verdict that changes sign inside that
  band can be labelled card-conditional with the field that decides it;
- every tier reads the same card, so agreement between tiers says nothing about the card; randomizing over its
  stated uncertainty is one of the three defences against that common-mode error;
- a randomization width cannot be narrowed by editing a task: it narrows only when a card is updated after an
  admitted validation.

The second half of the bead is how the values are drawn: **by address**. A drawn value is a pure function of the
world address, the registered stream of the parameter and the physical entity it belongs to, so two runs at one
address draw the same value in any batch, any world replays alone, and two designs compared at the same addresses
see the same floors and the same gusts. Tier Solid; crate `frob-learn` (Cortex), reading cards from `frob-actuate`
and the contact and sensor crates, and writing the per-world parameter row of the batched step.

Rejected alternatives: ranges in the task file (untraceable, and silently wider or narrower than what is known); a
per-environment generator seeded once (draws depend on slot and on how many parameters come before); randomizing
numerical parameters together with physical ones (a smaller time step would silently stiffen a fitted foot spring).

## Scope

In: the `randomization` section of a task as compiled into a randomization plan; resolution of each entry to a card
field band and to a parameter-row column; the no-interval refusal; the laws (uniform on an interval, truncated
normal from a spread); the addressed draw at reset; the list of resolved values handed to the episode record; the
summary on results; the `--resolved-out` writer (path jail, header line); the injected band reader. Out: the flags
carrier and the export door of the `--resolved-out` file (N37p1-01, N37-18); the width-source trait and the
correlated sampler (N30a-28, N30a-27); storing resolved values in episode records, the objective over the randomization (mean
or a tail measure) and the held-out rule (N23b-03); adaptive reweighting inside a card's support (N23b-04,
Frontier); numerical perturbations as exploitation detectors (their own bead); scene and layout randomization and
shared latents such as wetness (the scene beads); sensor noise draws per sample (the sensing beads).

What this bead stands on: the band accessor over card fields (N15b-06); the parameter row of per-world variants
(BD-169); addressed draws with the stream registry and entity keys (BD-180, and through it N35-23 and N35-24).
The admission check that every range of a task term names its card field is a sibling check on the task side
(N23a-05); this bead owns the refusal for a field with no interval.

## Technical approach

Module (DESIGN): `crates/frob-learn/src/randomize/{plan.rs, resolve.rs, draw.rs}`; kernel `K-randomize` in
`frob-kernels` (floating, D2) for device-resident parameter rows.

**Task syntax** (the task's `randomization` section of §24.4; the task file has one format, BD-122's, whose
canonical form is JSON and whose S-expression view is shown here; the JSON form is the same tree; DESIGN
spelling):

```lisp
(randomization
  (draw knee-kt :from actuator:knee#torque_constant   ; card reference and field path; resolved per instance
        :scope episode                                 ; episode | run
        :law card)                                     ; the card's own law; the only Solid choice
  (draw tile-mu :from interface:rubber-60a/tile#mu
        :scope episode :law card
        :entity tile))                                 ; keyed by the physical thing, not by the design
```

Each `draw` has a name unique in the section. A key outside `:from`, `:scope`, `:law`, `:entity` and the keys
that later beads add to the same form (`:domain` and `:stream`, N24c-36; `:key`, N24c-36, which recognises a
`:key <counter>` clause, `control-tick`, `footfall-index`, `contact-index`, `draw-index` or `training-counter`,
only to refuse it with FROB-REF-556; `:beyond-card`, N23b-03) is an unknown field and is refused by the task
compiler (FROB-REF-103). An earlier draft spelled the section as TOML
`[[randomize]]` tables with a `target` key; that form is withdrawn. `:entity tile` names a tile region that the
scene lists (a finite set, one parameter-row column per region); per-cell field exposure at contact time, at a
declared cell size and any position, is N19ax-03's and N24c-36's.

**`:from` sources and the extension point** (DESIGN). `:from` has one form, `<kind>:<path>#<field or dimension
id>`. This bead resolves card fields (`actuator:`, `interface:`, `material:`, `sensor:` with a field path) through
its own card resolver, and it owns the extension point through which other source kinds plug in: a table of
resolvers keyed by source-kind prefix, handed to the compiler by `frob-verbs` together with the band reader (the
same injection, for the same layering reason), each implementing `DrawSourceResolver::resolve(address) ->
Result<DrawSource, Refusal>` with `DrawSource { law, unit, support, nominal, row_id, provenance, consumer }`. The
kinds registered so far, each by the bead that owns the registry and depends on this one:

| Source kind | Address | Resolver (milestone) |
|---|---|---|
| card field | `<card kind>:<card>#<field path>` | this bead (M2) |
| disturbance-law row | `registry:disturbances/<slug>[#<dimension id>]` (pushes, gusts) | N24cp3-02 (M2) |
| hazard-registry row | `registry:hazards/<archetype>:<slug>[#<dimension id>]` | BD-227 (M3) |

A registry row is resolved like a card field: its entry's distribution is the law and its range the support; the
resolver returns the row identifier (`disturbances.push`) and the row's provenance, which the compiler copies into
the plan entry and every resolved value of it. The dimension id may be left out only for a row with exactly one
drawn entry (the resolver's rule). A registry value has no parameter-row column: the resolver names its consumer
(the disturbance application through the exposure domain of N24c-36; the hazard's world parameter), and the drawn
value is handed to that consumer and recorded in the resolved list. A `:from` whose prefix has no resolver in the
build (for example `registry:hazards/…` before BD-227 lands), or that its resolver does not find (an unknown slug or
dimension id, or an id naming a fixed entry), is FROB-REF-103 pointing at `:from`, with the source kinds the build
resolves. A row with no usable law (a hazard row whose only mechanism is Frontier) is refused like a card field
with no interval (step 3 below), naming the row.

**Compilation to a plan** (at environment admission; refusals come before any world exists).

1. Resolve `:from` to concrete card instances of the admitted designs and scene (every knee actuator; every tile
   region) and to the parameter-row column that carries the field on the batched tiers. A field with no column is
   refused with the list of randomizable fields (level P-A carries link lengths, inertias, gear ratios,
   actuator-card parameters, foot radii and friction).
2. Read the field's band through the band reader the compiler is handed by its caller, never by calling a card
   or ground module itself (DESIGN, layering: `frob-learn` is layer 4 and `frob-ground` layer 5, so the compiler
   names no `frob-ground` item). At this bead the reader is the card's own stated band through N15b-06's
   accessor, injected by `frob-verbs`, which composes every run. N30a-28 (M5, which depends on this bead) gives the
   reader its final form, the trait `CardWidthSource` in `frob-actuate` with the plain implementation
   `CardOwnWidths` (this behaviour) and `GroundWidths` injected by `frob-verbs`; a card version with a covariance
   block then takes its draws from the `CorrelatedDraw` sampler that `CardWidthSource::sampler` returns (N30a-27).
   Admitted uncertainties and their laws:

   | Card uncertainty | Law | Support |
   |---|---|---|
   | `interval [lo, hi]`, or an `abs` or `rel` half-width | Uniform | The interval |
   | `normal` with σ | Normal with mean the nominal value | The card field's validity bounds where stated, else nominal ± 4σ; the truncation is written into the plan |
   | `exact`, or no uncertainty | None | Refused |

3. **The refusal** (seed condition). A field whose uncertainty is `exact` or absent refuses randomization (exit
   code 3), with `observed` = the field and its provenance, and ranked repairs:
   (a) state an uncertainty on the card (a new card version with provenance); (b) override the field in the design
   with provenance `designed` and an interval; (c) remove the entry. The code is raised through the one constant
   `frob_learn::refusal::RANDOMIZE_NO_INTERVAL`, which holds the number the allocation ledger's first round
   assigns at M0 to the request `randomize-no-interval` (proposed 571, interim `none`; the registry row is
   N23bx-03's). The slug is the request's name and is never raised as a code, and the proposed number is never
   raised (N35-33 rule 7); were the request still unassigned when this bead lands, the mechanism still refuses and
   the bead stays open on that point.
4. Check that the entry names a physical parameter. A numerical parameter (time step, iteration count, stiction
   speed, regularization) is refused here (exit code 3), whose repairs point to the detectors of `eval.detect`
   that vary those. The code is raised the same way, through the constant
   `frob_learn::refusal::RANDOMIZE_NUMERICAL_PARAMETER`, which holds the number the first round assigns to N23-REF's
   request `randomize-numerical-parameter` (proposed 572); never the slug, never the proposal.
5. Assign the stream and the draw address through N35-24's helpers, on N35-23's registered rows:
   - a card field of a design instance: stream `task-parameter` (identifier 2), `by_param` with the stable path
     `<field path>@<instance port name>`, whose 32-bit entity is N35-23's `entity_of_name`; component j for
     attempt j of the law (0 for a uniform);
   - an entry with `:entity tile`: stream `scene-field` (identifier 3), `by_cell` with the tile region's index as
     the entity; because two fields of one tile share that entity, the component carries the field:
     component = (low 29 bits of `entity_of_name("scene-field", <field path>)`) · 8 + j. Two fields of one task
     whose 29-bit values collide are refused at admission like any entity collision of N35-23.
   - an entry from a registry source: the stream and key the draw declares (`:stream`, N24c-36), never call
     order; the dimensions of one row drawn by one draw use one key with consecutive components (N24cp3-02).
   The instance port name, not a running index, identifies an actuator, so adding a leg shifts no other leg's
   draw.
6. Emit `RandomizationPlan { entries: [{column or consumer, law, lo, hi, nominal, sigma, stream, entity,
   component_base, scope, provenance, row_id (registry sources only)}], id }`; its
   content hash enters the task identity.

**Drawing** (at reset under the reset mask; `scope = "run"` draws once with episode fixed at 0).

1. For world address a and entry e: x = the first word of the draw block at the address of step 5 (tick 0,
   attempt j = 0); u = (x ≫ 8)·2⁻²⁴ (`uniform_f32` of N35-22, `K-x-philox`'s conversion on devices).
2. Uniform: value = lo + u·(hi − lo), evaluated in the parameter row's precision with no fused multiply-add; the
   result is clamped into [lo, hi] by select (the product can round up by one unit in the last place).
3. Normal: attempt j = 0 … 7 uses the block at attempt j of step 5: n_j = `normal_f32` of N35-22 on that block
   (words b₀ and b₁; one normal per block, no cached second output); candidate = nominal + σ·n_j; the
   first candidate inside the support is taken. If none is, the value is clamped to the nearer bound and the
   episode is flagged `randomization-clamped`. Every attempt is addressed, so the result is still a pure function
   of the address.
4. Write the value into the world's parameter row (or hand it to the registry source's consumer); append (path,
   instance, stream, entity, value with unit, support, law, provenance, and for a registry source the row
   identifier) to the episode's resolved list.

**Results.** Every result of a randomized run carries, in its claim product's model identity, the plan
identifier, and in its summary the share of randomized fields by provenance (`measured`, `datasheet`, `generic`,
`assumed`), registry rows counted by their row's provenance. Evidence class is set by the weakest card field read; randomization never raises it.

**Surfaces.** No new verb. The plan is compiled on the environment-admission path that every verb creating an
environment shares (`sim.run` with a task, N16b-25; `eval.run`; `train.start`), and each returns the plan summary
or the refusal. Their JSON output gains a `randomization` block: the plan identifier, the provenance shares and,
per world address, the digest of that world's resolved list. The operator option `--resolved-out <file>` (outside
every identity) writes the resolved lists as JSON lines (address, draw, instance, value with unit, support, law,
provenance, and the row identifier for a registry source), the same list that N23b-03 stores in the episode
record. The file argument is a `frob.path/1` resolved through the
path jail (N37-11) under the session's export root; a path that leaves it is `FROB-REF-734` (on sim.run's
refusal list) and no byte is written. The file is written by one writer function, and its first line is
reserved for the header object of schema `frob.diag-header/1`: this bead writes it with `schema` and `kind`
(`diagnostic`), and every following line is a data record. The beads that make the file an export plug into
that writer and depend on this bead: N37p1-01 (M2) adds the flags carrier (`authorization` in the header line);
N37-18 (M3) settles that the write takes an `ExportGrant` from `frob_verbs::export::admit` under export kind
`diagnostic` and adds `privacy`, `licences` and `notices` to the header. No second writer of the file exists. `frob task check <task> --design <d> --json` (BD-122's
verb; the optional `--design` resolves `:from` against that design's instances) reports the same refusals without
running anything, and `frob sim replay --run <r> --world <w> --key <k> --json` (BD-203; a `run` verb, so it takes
a key) reports the replayed world's resolved-list digest.

## Acceptance criteria

- [ ] Seed condition: a task that randomizes a card field whose uncertainty is `exact` or absent is refused before
      any world is created, with the field named and the three repairs; exit code 3 on the CLI and the same refusal
      over MCP.
- [ ] Seed condition: for 1,000 addresses, the resolved values of every entry are bit-identical when the world
      runs alone, in batches of 64 and 4,096, under slot permutation, at two bucket capacities, on one and two
      shards, and when replayed with `sim.replay`.
- [ ] The same address gives the same interface friction per tile for two designs with different leg counts; the
      per-instance actuator draws of legs present in both designs are equal.
- [ ] 10⁶ uniform draws lie in [lo, hi] inclusive and their mean and variance are within three standard errors of
      (lo + hi)/2 and (hi − lo)²/12; truncated-normal draws lie in the support.
- [ ] A numerical parameter in `randomization` is refused with the code assigned to `randomize-numerical-parameter`
      (raised through its constant); a field with no parameter-row column is refused with the list of randomizable
      fields; an unknown key in a `draw` is refused with `FROB-REF-103`. No source file of `frob-learn` contains
      the literal slug `randomize-no-interval` or `randomize-numerical-parameter`, or the number 571 or 572, outside
      the two constants' registry lookups.
- [ ] The `:from` extension point: a registered source kind resolves through its resolver, its value is drawn by
      address on the draw's declared stream, and its resolved-list entry carries the row identifier and the row's
      provenance, counted in the provenance shares; a prefix with no resolver in the build, or an unknown slug or
      dimension id, is `FROB-REF-103` at `:from`; a registry row with no usable law is refused with the
      no-interval code naming the row.
- [ ] Two fields of one tile region draw from different blocks (the component of step 5); a planted pair of
      field paths whose 29-bit values collide is refused at admission.
- [ ] Changing a card's interval changes the plan identifier and the task identity; changing nothing reproduces
      both.
- [ ] The resolved list handed to the episode record has one entry per (entry, instance) with unit and support.
- [ ] `CONTRACT.md` of `frob-learn` documents the laws, the truncation rule, the refusal and the streams used.
- [ ] Open clauses of the definition of implemented: the gate record (the task-family gate GATE-ARENA-01 and the
      composition-invariance gate GATE-SPARK-15 close in their own beads); the device differential check of
      `K-randomize`.

### Known answers and negative controls
- KA-793 and KA-795 applied to parameters (addressed draws; the extra-leg case); counterexample CX-143
  (agreement between the referee and the fast tiers is not evidence that the card is right; randomization over the
  card's band is the defence this bead supplies).
- Negative controls: the three mutants; the planted `exact` field; the planted numerical parameter.
- Metamorphic: reordering the `draw` entries of `randomization` changes no drawn value; adding an entry changes no
  other entry's values.
- Determinism lanes: twice on one machine; across worker counts and batch sizes; `batch-cpu` in `f32` and `f64`
  each against its own precision; devices later against their class (the integer draws are D0 everywhere).

## Considerations

- Randomization width from a card does not narrow without an admitted validation (INV-GROUND-05): a candidate
  posterior from a fit leaves the plan unchanged.
- A range beyond the card is not available here; where it is offered later it is labelled `beyond-card` and its
  results cannot be cited for the carded hardware.
- Correlated fields (a wet floor that lowers friction and changes optics together) are drawn once through a shared
  latent by the scene, not by two entries here.
- With generic cards most bands are `assumed`; results then stay `Estimated`, and `--strict-data` refuses a verdict
  that rests on them. That is the fail-closed state until catalog data with provenance is admitted.
- What would make us revisit: geometry randomization that changes the tree (it is a model variant, not a parameter
  row), or a parameter whose law needs correlation inside one card. The second is taken up by N30a-27, which
  depends on this bead: a card version with a `[covariance]` block is drawn through the `CorrelatedDraw` sampler
  that the injected `CardWidthSource` returns (N30a-28) as a Gaussian copula by address, and independent marginal
  sampling of such a card becomes a lint error in this compiler.
- Registry examples (NJL-02's rule: the bead that makes an example run adds its rows): where the `sim.run` example
  in its `--task` form and the `task.check` example (`frob task check t:kitchen-tray --json`) run through this
  compiler, this bead adds to `fixtures/verbs/identities.toml` the rows for their abbreviated identities that the
  verbs' implementing beads have not already added, each with the fixture that stores the object and `since =
  "M2"`.
