## Background

Four risks were found late, from facts about the foundations rather than from design reasoning. Each has an
earliest signal that an existing check already produces. A signal that has never been seen to fire is a hope, so
the rule (DESIGN) is that the detector of each row is exercised by a **planted instance** registered in the
negative-control registry: a deliberately constructed case in which the hazard is present, on which the signal must
fire every time. Gate GATE-WS-07 records this:

> Known answer. Each of the four planted instances raises its named signal in 100 of 100 runs; `xtask check-deps`
> resolves the graph with every feature group enabled and fails on the planted second pin; no row of the register
> lacks a planted instance. M0 for the two build rows, M2 for the sampler row, M3 for the suite row.

This bead delivers the M0 part: the two build rows and the register-wide clause. The sampler row is N41-38
and the suite row N41-31.

**Row A (RISK-56): a dependency feature changes canonical bytes.** FACT (to be re-read at the pinned versions):
the JSON library used across the suite has a feature that switches its maps to insertion order and a feature that
changes its number representation, and Cargo unifies features across a build graph. A sibling that enters the
graph with either feature enabled would change the bytes that a library-map serializer writes, and with them the
digests of unchanged artifacts. Mitigation: canonical bytes come only from this project's own writer, which sorts
by code point explicitly and never serializes through a library map; the build is tried in the four feature
combinations; the stack lock records the unified feature set. Signals: `xtask check-deps` reports a unified
feature set of the JSON library that differs from the stack lock; a golden digest changes with no change to its
artifact.

**Row B (RISK-57): an exact version pin in a sibling blocks an oracle.** FACT (to be re-read): the cloth oracle's
workspace takes an exact pin on the JSON library (`=1.0.151`), which cannot share a build graph with a sibling that
requires another exact version. Mitigation: the oracle runs as a worker process in its own workspace; the pin move
is an upstream work item. Signals: dependency resolution reports two exact requirements on one package; the
oracle's admission gate cannot build.

Counterexample to the shortcut "a passing build means the pins are compatible": a build that never enables the
oracle's feature flag resolves, and the conflict appears only when the flag is first turned on at the oracle's
milestone. The resolution check therefore runs with every optional feature group enabled.

## Scope

In: the two planted instances as fixtures; the 100-variant generator for each; the all-feature-groups resolution
mode exercised on the second pin; the positive controls (no false alarm on the clean graph); the gate record for
the M0 rows; the register-wide check that every risk row has a planted control. Out: the detectors themselves (the
JSON guard and the exact-pin probe are parts of `check-deps` owned by the workspace and suite units); the sampler
row (N41-38) and the suite row (N41-31); the canonical writer (its own bead).

## Technical approach

Fixtures (DESIGN): `tests/controls/ws07/{json_features/, exact_pin/}`; generator and harness in
`crates/frob-conformance/src/controls/ws07.rs`; script `scripts/e2e/ws07_build_plants.sh`.

**Instance A, the dummy feature dependency.**

1. A scratch overlay of the workspace manifest adds one path crate, `ctl-json-features`, that depends on the JSON
   library with the map-order feature and the number-representation feature enabled.
2. Variants (seeded, 100): the dummy enters as a direct dependency of a random core crate, as a transitive
   dependency two levels down, through an optional feature group, or through a dev-dependency of a crate whose
   tests are built; with one feature, the other, or both.
3. Expected on every variant: `xtask check-deps` exits non-zero and reports the binary, the unified feature set
   found, the feature set recorded in the stack lock and the path through which the feature entered.
4. Second half of the row's signal, shown both ways: (a) with the project's writer, the digests of the golden
   corpus of 1,000 artifacts are unchanged under all four feature combinations (the mitigation holds); (b) with
   the library-map mutant writer (a control build that serializes through the library's map), at least one golden
   digest changes under the map-order feature (the hazard is real, and the golden corpus detects it).

**Instance B, the second exact pin.**

1. A scratch overlay adds `ctl-exact-pin`, which requires the JSON library at an exact version different from the
   one the stack lock resolves, and is reachable only through an optional feature group `ctl-oracle` that is off
   by default.
2. Variants (seeded, 100): the conflicting requirement sits on a random package among those the lock pins exactly
   or resolves uniquely; the dummy is reached through one of the registered optional groups or a new one; the
   requirement is exact (`=x.y.z`) or an exact pre-release.
3. Expected on every variant: the default-feature graph resolves (`cargo metadata --format-version 1 --offline`
   on the overlay's manifest, recorded, to show the shortcut's failure); `cargo xtask check-deps --root <overlay>
   --json`, whose guard resolves each graph a second time with every optional feature group enabled (N34-04,
   step 2; there is no separate mode to select), exits non-zero with `json.exact-pin-conflict`, naming the
   package, the two exact requirements and the two requirers.
4. The repair printed with the failure is the row's mitigation: run the oracle as a worker process in its own
   workspace, and open or cite the upstream work item for the pin move.

**Positive controls.** On the unmodified workspace both checks pass in 100 of 100 runs (no false alarm), in the
default-feature resolution and in the resolution with every optional feature group enabled.

**Register-wide clause.** The harness loads `registries/risks.toml` and the negative-control registry and asserts
that every open row names a planted control that is registered, or declared with a due milestone not yet
reached (the loader rule of N41-01; binding and staging in N41-32), and that the four late rows name the
controls of this gate. The clause reads the whole register, so it needs all four parts of the rows (N41-RISK1 to
N41-RISK4) and N41-32's M0 bindings; all are dependencies.

**Gate record.** `registries/gates.toml`, GATE-WS-07, its one M0 part (scope "the two build rows"; the record and
its parts at M0, M2 and M3 are entered by N40-10, and a gate has one part per milestone, N40-01): `measured` carries
both instances, "json-features fired n of 100; exact-pin fired n of 100", with the positive-control counts, and
the receipt also holds the register-wide clause's result; the commit, the stack receipt and the seed. The script
writes no gate row: it produces the receipt, and the recording session (not the implementer) records the M0 part
from it with `cargo run -p frob-conformance --example record_gate -- --gate GATE-WS-07 --receipt <hash> --part M0`
(one recorder per gate part, N38b-19's `--part <milestone>`: the gate has three parts, and N41-38 and N41-31
record theirs with `--part M2` and `--part M3`; this bead is the one that measures the M0 part). The registered controls of the part
are the plants themselves, seeded from N41-CX's rows and not written here: X41-06 (`dummy-dep-insertion-order`,
instance A, `planted-design`) and X41-01 (`second-pin-behind-feature`, instance B, `planted-design`); the catching
tests are named in N41-CX's compiled-in table. The uncaught-control check is the library-map mutant for row A and
the default-mode resolution for row B (which must be recorded as passing, proving that default mode alone would
miss). The M2 part (the sampler row, N41-38) and the M3 part (the suite row, N41-31) stay `not-run`.

Determinism: resolution and feature unification are exact, class D0; variants are seed-explicit. Evidence class of
the gate record: `Tested`.

## Test plan

### Unit tests
`crates/frob-conformance/tests/ws07_build.rs`; real `cargo metadata` resolution on scratch overlays, no mocks.
- `json_features_direct`, `json_features_transitive`, `json_features_optional_group`, `json_features_dev_dep`: each
  reports the feature set and the path.
- `golden_digests_stable_four_way` (project writer); `library_map_mutant_changes_digest` (control build).
- `exact_pin_default_resolves`; `exact_pin_all_groups_fails`; `exact_pin_names_both_requirers`.
- `clean_workspace_no_alarm_both_modes`.
- `variant_generator_is_seeded`: the same seed yields the same 100 overlays.
- `every_risk_row_has_planted_control`: over the 59 rows, each open row names a registered control, or a
  declared one whose due milestone is not yet reached; a scratch copy with one control removed fails, naming the
  row.

### End-to-end script and logging
`scripts/e2e/ws07_build_plants.sh`: for seeds 1 to 100, builds each overlay in a scratch directory through the
offload shim, runs `cargo xtask check-deps --root <overlay> --json` (one run: the guard resolves the default
features and every optional feature group, N34-04) and, for instance B, the default-feature `cargo metadata
--format-version 1 --offline`, and records one `assert` line per variant (seed, variant kind, exit code, the
reported feature set or the two requirements). A `metric` line
per instance gives "fired" against the threshold 100, and "false alarms" against 0. The golden-corpus comparison
logs the digest of the corpus index under each feature combination. The register-wide clause runs last, with one
`assert` line per open risk row (row, control identifier, `registered` or `declared` with its due milestone).
Final `summary`: assertions passed and failed,
gate GATE-WS-07 touched (its M0 part, "the two build rows"). Wall time is recorded; the whole script stays
inside the default machine envelope.

### Known answers and negative controls
Known answers: 100 of 100 for each instance; 0 false alarms; four feature combinations with identical golden
digests. Negative controls: the two plants themselves; the library-map mutant writer; the default-feature
resolution alone, which must miss instance B (recorded as the demonstration that the resolution with every
optional group is needed);
a risk row with its control removed, which must fail the register-wide clause.
Determinism lanes: twice on one machine; Linux and macOS; identical reports byte for byte.

## Considerations

- The plants live in scratch overlays and never in the workspace manifest; the script fails if a control crate is
  found in the real graph.
- "100 of 100" for a deterministic check is made meaningful by variants: the feature or pin enters by different
  routes. A detector that inspects only direct dependencies fails the transitive variants.
- If the JSON library is replaced or its features renamed, row A's fixture is rewritten for the new hazard and the
  gate row re-recorded; the risk does not retire while any shared serialization library is in the graph.
- Sibling repositories are never edited by this test.
