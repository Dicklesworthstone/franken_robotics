## Background

An **open question** is a decision the design has not taken, written so that not taking it is safe. Every one has
an owner, a deadline expressed as the gate or milestone it blocks, a **fail-closed default**, and the evidence that
would decide it. Nothing is decided by silence: at its deadline an undecided question takes its default, and the
default is recorded as an architecture decision record (ADR). Five clauses make the rule operational.

1. **A default removes a claim or a capability. It never adds one.** "GPU results are labelled exploratory", "no
   pretraining", "`reality: no-claim`" and "refuse" are defaults. "Assume the catalogue price" is not.
2. **A question is asked one milestone before the gate it blocks.** A question that reaches its deadline at its
   default is reported in the exit review with the capability it removed.
3. **Evidence decides where evidence exists.** A question whose row names a gate, a profile or a pilot is decided
   by that measurement and not by preference. Only the owner's questions are decided by the owner's judgement.
4. **A closed question is tombstoned, not reused.** Its identifier stays in the register with the ADR that closed
   it.
5. **The register adopts the identifiers the chapters defined.** A chapter's text governs the mechanism behind a
   question, and the gate register governs any threshold a question touches. Where a chapter named no owner, the
   lead of its subsystem owns the question.

The register holds 147 questions in its subsystem table: 141 raised by the subsystem chapters, of which four are
closed, and six at program level. The questions raised by the verification chapter and the ten-fold chapter are
adopted under the same rule with the owners and defaults those chapters state: OPEN-GAUNT-2 to -8 and
OPEN-TENFOLD-3 to -9; OPEN-TENFOLD-1 and -2 are one question with OPEN-PROG-2. With these fourteen the register
holds 161.

Without a register that a program reads, the failure is the quiet one: a question nobody answered, a capability
nobody removed, and a result that silently assumes the generous answer. This bead makes the register a file with a
loader, in `frob-conformance` beside the exit runner (not in `xtask`, whose scope is fixed at six checks). The
per-milestone owner calendar is a view of this register and is carried by the bead that owns the milestones.

## Scope

In: the schema of `registries/open.toml`; the loader and its rules, with the completeness check of rule 8; the default-ADR template and its writer; the
linkage from each question to the bead that decides it; tombstones and aliases; the generated printout; the
listing of the all-defaults product; the query `due(Mn)` that lists, for an exit, the rows at their deadline with
their status and ADR (the data the exit-time check reads).

Out, with the bead that has it: the rows (N41-OPEN1 to N41-OPEN8); the decisions themselves (each question's own
decision or experiment bead); the per-milestone calendar and the exit-time check that a question due with neither
an answer nor a default ADR blocks the exit (N40-35; that rule is specified and tested there, over this register);
step 10 of the exit procedure, which calls that check, calls this bead's `default` subcommand when the reviewer
takes a default, and copies the listing into the exit record (N40-05, which holds no open-question rule of its own);
the all-defaults exit rehearsal (N40-32).

## Technical approach

Files (DESIGN): `registries/open.toml` (schema `frob.open/1`), `crates/frob-conformance/src/exit/open.rs`,
`docs/adr/templates/open-default.md`, generated `docs/delivery/open-questions.md` and `registries/open.lock`
(rule 9).

**The command target.** `frob-conformance` has no binary (BD-025, ADR-GAUNT-01), so the register's commands are
one example target of that crate, declared here: `crates/frob-conformance/examples/open_questions.rs` (DESIGN
name, the one N15b-25, N25d-47 and N33b-03 cite), run as `cargo run -p frob-conformance --example open_questions
-- <subcommand> ...`. This bead writes four subcommands: `check --complete` (rule 8), `due --exit <Mn>`,
`default <id> --exit <Mn>` and `defaults-product`; each takes `--root <dir>` and `--json`, prints one JSON object,
and exits 0 when it ran as specified below and 1 on a load error or a failed check. Beads that depend on this one
add their subcommands to the same target in their own change, over this bead's library: `calendar <Mn>` (N40-35)
and `require <id>` and `page <id>` (N41-05). A subcommand the target does not know exits 2 with its usage.

**Record.**

```toml
[[open]]
id        = "OPEN-KIN-1"
question  = "The default physics step and Newton iteration budget"
owner     = "Kinesis lead"                     # a role; "Owner" for the project owner
default   = "2 ms; 4 iterations with warm start"
default_effect = "keeps-conservative-value"    # removes-claim | removes-capability | labels-result | refuses |
                                               # keeps-conservative-value | none
decided_by = { kind = "measurement", ref = "the fidelity-throughput frontier at M2" }   # measurement | gate |
                                               # pilot | owner | adr
blocks    = ["M2 frontier"]                    # gate ids, milestone names, or "nothing"
deadline  = "M2"                               # the exit at which the default is taken if undecided:
                                               # M0 to M8, or "none", or "per-row" (rule 3)
asked_at  = "M1"                               # computed: one milestone before `deadline`
note      = ""                                 # optional commentary on the deadline or the asking (rule 3)
tracked_by = ""                                # `per-row` questions only: the registry query that counts them
decision_bead = "N16a-16"                      # the bead that decides it; empty only if `blocks` is "nothing"
pending_decision_bead = false                  # true while `decision_bead` names only the seed bead of the mechanism
status    = "open"                             # open | decided | defaulted | closed
adr       = ""                                 # the ADR that decided, defaulted or closed it
decision_digest = ""                           # optional: BLAKE3 (64 lowercase hex) of a decided row's decision
                                               # table; OPEN-KIN-6: the bound table of docs/adr/ADR-KIN-OPEN-6.md
                                               # (written by N16c-11, read by BD-212); write-once (rule 9)
aliases   = []                                 # for example OPEN-TENFOLD-1 and -2 on OPEN-PROG-2
confirmed_by_gate_register = false             # true for the four defaults the gate register already fixes
```

**Loader rules** (each a typed load error naming the row, printed with its harness reason of N41-REF: rules 1, 3,
6, 8 and 9 `open-rule-broken`; rule 2 `open-default-adds-claim`; rule 4 `open-closed-without-record`; rule 5
`open-id-reused`; rule 7 `open-no-decision-bead`).

1. Every row has a non-empty owner, default, `decided_by` and deadline (clause structure).
2. `default_effect` is in the closed set; a default whose text adds a claim (the lint looks for effect `adds`, which
   is not in the set, and the reviewer classifies each default once) is rejected (clause 1).
3. `deadline` is a milestone (`M0` to `M8`) and `asked_at` is the milestone before it; a row whose deadline is M0
   is asked at M0 and listed first (clause 2). Two other values exist for rows that one milestone cannot describe
   (DESIGN; the parts N41-OPEN1 to N41-OPEN8 print such rows with words in their Deadline column). `none`:
   allowed only where `blocks` is `nothing` or the row is `closed`; the row is never due and has no `asked_at`.
   `per-row`: a question that stands for many small obligations, each due with the gate or section it belongs to
   (OPEN-GAUNT-2, -3 and -6); the row names in `tracked_by` the registry query that counts the obligations still
   open by milestone, and it has no `asked_at`. Words printed after a milestone in a part's table (a
   parenthesis, "again before the M7 pin freeze", "M4 needs the answer on its first day") are commentary: they
   go to `note`, and the value is the milestone.
4. A row with `decided_by.kind` of `measurement`, `gate` or `pilot` cannot be set to `decided` unless the named
   record exists in the gate register, the pilot register or the ledger; an owner's ADR alone does not close it
   (clause 3). Rows with kind `owner` are closed by an ADR signed as the owner's.
5. A `closed` or `decided` row keeps its identifier; a new row reusing it is rejected; aliases resolve to exactly
   one row (clause 4).
6. Identifiers match `OPEN-<SUBSYS>-<n>` with a subsystem code from the fixed list; a row with no owner in its
   chapter takes the subsystem lead (clause 5).
7. Every row whose `blocks` is not "nothing" names a `decision_bead` that exists in the tracker export. Rows that
   block nothing may leave it empty and are listed in the printout as "carried in considerations". A row whose
   chapter has not yet written its decision bead sets `pending_decision_bead = true` and names the seed bead of
   the mechanism; the loader then fails at the row's `asked_at` milestone if the marker is still set, so the gap
   surfaces one milestone before the deadline.
8. Counts, as a completeness check (`cargo run -p frob-conformance --example open_questions -- check
   --complete`, run by the exit runner and by N41-04's test `register_total_is_161`, which depends on all eight parts): 147 rows in the subsystem table set (141 + 6), 14 adopted rows, 161 in all, four
   settled at entry (OPEN-SKEL-1 and OPEN-AUGUR-6 with status `closed`, retired by architecture decisions;
   OPEN-SUITE-2 and OPEN-TETHER-1 with status `decided`, by the owner; the check names these four identifiers
   with their statuses and does not count statuses, because other rows become `decided` as the program runs),
   and four with `confirmed_by_gate_register` (OPEN-NUM-3, OPEN-PERF-1, OPEN-REFLEX-2, OPEN-ATEL-4).
   The plain load applies rules 1 to 7 and 9 only, so that the eight parts of the rows (N41-OPEN1 to N41-OPEN8,
   which depend on this bead) can land one at a time without a part failing for rows it does not own.
9. A decision is recorded once. `decision_digest`, when not empty, is 64 lowercase hexadecimal characters and
   appears only on a row whose status is `decided`. It may not change while the row is `decided`: the generated
   history file `registries/open.lock` (schema `frob.open.lock/1`, one `(id, decision_digest)` pair for every row
   that has carried a digest, written by the printout's generator and kept append-only by the workspace's
   generated-file check, as `registries/streams.lock` is for the stream registry, N35-23) holds the first digest
   each row carried, and a decided row whose digest differs from its pair (a second, different hash) fails the
   load, naming the row, the locked digest and the new one. A decided row whose first digest is not yet in the
   file loads, and the regeneration appends its pair. Reason (DESIGN): a decision that downstream records cite by
   hash (OPEN-KIN-6's bound table, which BD-212 cites in the one re-baseline of GATE-FID-01) must not be
   rewritten in place; a revised decision is a new ADR that supersedes the old one.

**Taking a default.** `cargo run -p frob-conformance --example open_questions -- default <id> --exit <Mn>` (run by
the exit reviewer through the exit
script, never automatically) writes an ADR from the template with: the question, the default text, the capability
or claim it removes, the gates recorded `not run` or run in their variant because of it, and the label that
results must now carry; then sets `status = "defaulted"`. A later answer does not rewrite history: the default ADR
stays, a new ADR supersedes it from its date, and gates recorded under the default keep their records.

**The due query.** `cargo run -p frob-conformance --example open_questions -- due --exit <Mn>` (function
`due(Mn)` in `exit/open.rs`) lists the rows
whose `deadline` is Mn or earlier and whose status is not `closed`, each with one of three readings: `answered`
(status `decided` with its ADR), `defaulted` (with the default ADR and the capability removed), or `silent`
(status still `open` with no ADR). It only reports; the rule that a `silent` row blocks the exit is the
owner-input calendar's check (N40-35), which reads this query, and the exit runner propagates that block.
A `none` row is never listed. A `per-row` question is listed with the count of its obligations due by Mn that
are still open (from `tracked_by`): it is omitted when that count is zero, reads `silent` while the count is
above zero and no default ADR of this exit names those rows, and reads `defaulted` once the `default <id> --exit
<Mn>` subcommand has written an ADR listing the rows that stay at their default (for OPEN-GAUNT-2: the known-answer rows
still without a tolerance, which are then not counted as passing). The four rows settled at entry and due at M0
read `answered`. At entry sixteen rows have deadline M0: OPEN-SPARK-1, -2, -4, -6; OPEN-SUITE-1 to -6;
OPEN-WS-3; OPEN-PERF-2; OPEN-TETHER-1; OPEN-PROG-1; OPEN-GAUNT-4; OPEN-TENFOLD-7. Two of them are `answered`
(OPEN-SUITE-2, OPEN-TETHER-1), so fourteen must be answered or defaulted before M0 exits.

**The all-defaults product** (the test a default must pass before it is written). `cargo run -p frob-conformance
--example open_questions -- defaults-product` prints the product that results if every row stays at its default: a CPU-first studio with
exploratory GPU results, no family policy, cheap rungs that only discard, generic cards and assumed norms, no
Reality claim, a ten-fold ratio labelled `self-adjudicated`, and a private repository; every one of those limits
printed on the results it touches. The program must still exit M0 to M5 and M7 in that state. The six questions
that matter most, in the order they fall due: OPEN-SPARK-1 and OPEN-SPARK-2 at M0, OPEN-PROG-4 at M1, OPEN-PROG-2
at M2, OPEN-CORTEX-1 at M3 and OPEN-PROG-1 before the pins are frozen for M7. The six are a fixed list of the
subcommand, printed in this order (K41-16): OPEN-PROG-1 is placed by its second asking before the M7 pin freeze
(its `note`), not by its `deadline` of M0, so the order is not a sort on `deadline`.

**Printout.** `docs/delivery/open-questions.md` is generated: one table per subsystem with identifier, question,
default, owner, what it blocks or what decides it, status and the deciding bead.

## Acceptance criteria

- [ ] The example target `open_questions` builds and runs its four subcommands on the fixture registry; an
      unknown subcommand exits 2 with the usage.
- [ ] A conforming fixture registry loads, and a generated 161-row fixture (147 + 14, with the four closed and the
      four confirmed identifiers of rule 8) passes `check --complete`; each of the nine loader rules has a
      planted violation that is rejected with the row named (rule 8: one row removed from the generated fixture;
      rule 9: a decided row whose `decision_digest` differs from its pair in `registries/open.lock`).
      The real rows are written by N41-OPEN1 to N41-OPEN8: the 161 on the real file are asserted by N41-04 (its
      load step and its test `register_total_is_161`).
- [ ] A default that adds a claim is rejected; the four closed rows cannot be reopened or reused.
- [ ] A measurement-decided row cannot be marked decided without its record; an owner row can be closed by an
      owner ADR.
- [ ] Every row that blocks something names an existing decision bead; the printout lists the rows carried in
      considerations.
- [ ] `default <id> --exit <Mn>` writes an ADR that names the removed capability and the label, and the exit
      record lists it.
- [ ] `due --exit <Mn>` lists every row at or past its deadline that is not `closed`, each as `answered`,
      `defaulted` (with the removed capability) or `silent`; it exits zero whatever it lists, because the block on a
      `silent` row is the calendar check's (N40-35), not this command's.
- [ ] `defaults-product` prints the seven limits and the six questions in due order.
- [ ] The printout regenerates byte-identically; aliases OPEN-TENFOLD-1 and -2 resolve to OPEN-PROG-2.

## Considerations

- The register is the authority for a question's default; a chapter's text governs the mechanism, and the gate
  register governs any threshold the question touches. The loader compares quoted thresholds with the gate
  register for the four confirmed rows.
- Many questions are decided by measurements that the program will take anyway; for those the decision bead is an
  experiment or a decision at a gate, and the owner is a subsystem lead. Only about two dozen need the project
  owner.
- Classifying each default's effect is done once by a reviewer and stored; the closed set makes "adds a claim"
  unrepresentable, which is the point.
- The printout is for people; agents read the registry.
