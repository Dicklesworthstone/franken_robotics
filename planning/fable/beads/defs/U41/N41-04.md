## Background

The risk register, the pre-mortem tables and the open-question register are each loaded and checked by unit tests.
What unit tests cannot show is the behaviour that matters: at a real milestone exit, run by the real exit script on
a repository in some particular state, does a fired risk signal with no recorded outcome actually stop the exit,
and does a question nobody answered actually take its default, in writing, with the capability it removes? This
bead is the end-to-end script for that user-visible pipeline. The "user" here is the fresh-context reviewer who
runs the exit.

The script works on a scratch copy of the repository's registries, so that planting a fired signal or an unanswered
question never touches the real records. It is the standing negative control of the exit review itself: a version
of the exit runner that lets a silent signal or a silent question through must fail this script.

## Scope

In: the script, its scratch fixture, its planted states, its assertions and its structured log. Out: the loaders
and review steps (N41-01, N41-03, N41-PM); the gate-register end-to-end scripts (N40-36, N40-37); the build and
late planted instances of GATE-WS-07 (N41-02, N41-38, N41-31), which this script only invokes when their milestone is
reached.

## Technical approach

Path: `scripts/e2e/registers_exit.sh`; plain shell; sources the shared helper; idempotent; seed-explicit (the only
randomness is the choice of which rows to plant, drawn from `--seed`, default 1). It creates
`target/e2e-scratch/registers_exit/<utc>/` with copies of `registries/risks.toml`, `registries/premortem.toml`,
`registries/open.toml`, a minimal `registries/gates.toml`, an empty `docs/adr/` and `docs/delivery/exits/`, and
points the exit runner at it through the runner's `--root` option.

**Walk.**

1. *Load.* Run the loaders on the real registries: expect 59 risks (severity totals 28 High, 29 Medium, 2 Low;
   first readable 21, 9, 11, 15, 1 and 2 rows at M0 to M5), 27 stories, 6 outcome reasons, 161 questions. Run
   the three register-wide checks and expect each to pass: `cargo run -p frob-conformance --example risks --
   check --complete` (no gap, 59 rows), `cargo run -p frob-conformance --example risks -- check --cross` (every
   open question a risk row cites exists in the open-question register) and `cargo run -p frob-conformance
   --example open_questions -- check --complete` (161, the four rows settled at entry, the four confirmed); the
   example targets are N41-01's and N41-03's (`frob-conformance` has no binary, BD-025). Then, on scratch copies, remove RISK-07, rename OPEN-SPARK-2 and remove one question
   row in turn, and expect the matching check to fail with `risk-series-broken`, `risk-dangling-ref` and
   `open-rule-broken`.
2. *M0 exit, nothing recorded.* Run `scripts/exit/risk-review.sh M0 --root <scratch> --json` and the
   open-question listing, `cargo run -p frob-conformance --example open_questions -- due --exit M0 --root
   <scratch> --json`. Expect: 21 risk rows selected; mechanical detectors pre-filled; the exit blocked because rows lack
   readings; the questions due at M0 listed with OPEN-SPARK-1 and OPEN-SPARK-2 first; outcome reason 1 warns (no
   incumbent phase measurement on record).
3. *M0 exit, readings entered, one signal fired with no outcome.* Plant a failing matrix cell for the toolchain
   admission (the signal of RISK-02) in the scratch gate register and fill all readings. Expect: blocked, naming
   RISK-02.
4. *Three outcomes.* In turn record (a) the KILL-MCP decision with its ADR, (b) an ADR changing a mechanism, (c) a
   written reason; expect the block to clear each time, and to remain when the named ADR file is missing.
5. *M0 exit, questions.* Sixteen rows have deadline M0 and are listed, OPEN-SPARK-1 and OPEN-SPARK-2 first:
   OPEN-SPARK-1, -2, -4, -6; OPEN-SUITE-1 to -6; OPEN-WS-3; OPEN-PERF-2; OPEN-TETHER-1; OPEN-PROG-1;
   OPEN-GAUNT-4; OPEN-TENFOLD-7. Two read `answered` at entry (OPEN-SUITE-2, OPEN-TETHER-1). Any `per-row`
   question with obligations due at M0 is listed with its count. With the other fourteen unanswered: expect the
   exit blocked by the calendar check (N40-35's subcommand, `cargo run -p frob-conformance --example
   open_questions -- calendar M0 --root <scratch> --json`), each named `silent` with `open-decided-by-silence`.
   Run `cargo run -p frob-conformance --example open_questions -- default <id> --exit M0 --root <scratch>` for
   each silent row; expect one default ADR per row naming what it removes
   (OPEN-SPARK-1: GPU results labelled exploratory; OPEN-SPARK-2: nothing above class E0; OPEN-SUITE-3: no PASS
   on a dirty tree; OPEN-SUITE-5: the machine envelope), as many ADRs as silent rows, and the exit to proceed.
   Record the incumbent phase measurement; expect outcome reason 1 to clear.
6. *M2 exit.* Advance the scratch state to M2. OPEN-SPARK-1 is at the default taken at M0: expect no new ADR to
   be demanded for it, the exit record to list "device results labelled exploratory" under capabilities removed
   and to expect the no-GPU variant. The rows whose deadline is M1 or M2 are now due and block until each is
   answered or defaulted. The 9 and 11 rows first readable at M1 and M2 join the review. A planted device
   Performance claim dated after the default is refused.
7. *M3 exit.* With OPEN-TENFOLD-4 at its default and the scratch gate register holding the partial ten-fold gate
   `not-run` for every stratum: expect the exit blocked, the gate listed `not-run` and the question named with
   `open-default-blocks-exit` (the one default that can hold an exit). Record an approval and nothing else:
   expect it still blocked, because the gate has no record. Supply a gate record with the strata that fit the
   default class measured and the others `not run` with the reason: expect the block to clear. With
   OPEN-CORTEX-1 unanswered at its M3 deadline: expect its default ADR to be demanded, and once it is written
   "family policies" under capabilities removed and the M4 variant with no family policy expected. Plant a
   fired RISK-26 (the composed arm at 1.3 times in the scratch partial-gate ledger): expect the tie outcome to
   be demanded.
8. *Self-review.* Re-run step 4 with a reviewer identity that appears as an implementer: expect refusal.
9. *Generated printouts.* Regenerate `docs/delivery/risks.md` and `docs/delivery/open-questions.md` in the scratch
   root and compare with the registries (no hand edits survive).
10. *Planted instances.* For every risk row whose `first_readable` is at or before the walked milestone and whose
    planted control is runnable in the scratch root (the registry marks which are), fire it and assert the
    detector reports the signal. When this bead lands those are the 18 M0 rows bound by N41-32 (a dependency);
    the plants bound later (N41-33 to N41-37, and the late rows of N41-02, N41-38 and N41-31) join the walk
    through the same registry marks, with no change to the script, and the `metric` line logs how many fired
    against how many are marked runnable (all marked rows must fire; at least 18).

**Logging** (the shared format, to `target/e2e-logs/registers_exit/<utc>.ndjson` and a transcript). Every line
has `ts`, `script`, `bead` ("N41-04"), `step`, `event`. `cmd` lines carry the exact command, exit code and wall
time. `assert` lines carry what was expected and observed (row or question identifier, status, blocking or not).
`metric` lines carry counts with their expected values: risks selected per exit (21, then 21 + 9 + 11 = 41 at M2,
then 56 at M3), fired, not readable; questions due, answered, silent and defaulted (16, 2, 14 and then 14 at the
M0 exit, not counting `per-row` questions); warnings present. Each `assert` or `metric` line that exercises a row
of the unit's registries carries its identifier: the planted cases X41-09 to X41-14, X41-18 to X41-22, X41-24
and X41-48 of N41-CX, and the known answers K41-01 to K41-18 of N41-KA with expected value, observed value and
verdict. `refusal` lines carry the registered reason (N41-REF) and the runner's refusal text; the log linter
rejects a reason that is not registered. On failure the line names the first row or question whose behaviour differed and the
scratch paths needed to reproduce. The final `summary` gives assertions passed and failed and lists no gate (this
script measures no gate; it protects the exit review). No private-scene data can appear: the script reads
registries only.

## Acceptance criteria

- [ ] The script exits 0 on a correct implementation and non-zero if any assertion fails.
- [ ] Each of the ten steps produces its expected block or pass; the counts 21, 41 and 56 are asserted, and at
      the M0 exit the sixteen questions due, two answered and fourteen defaulted one ADR each.
- [ ] The three register-wide checks pass on the real registries and each fails on its broken scratch copy with
      its registered reason.
- [ ] At the scratch M3 exit an approval alone does not clear the block behind OPEN-TENFOLD-4; a gate record
      does.
- [ ] Three mutant runners (`nc-<nnnn>` builds of `frob-conformance`, run through `--mutant <nnnn>`) are each
      caught: one that treats a fired signal without outcome as a warning; one that lets a due question pass with
      neither answer nor default ADR; one that accepts a self-review. A default build has none of the three.
- [ ] The script is idempotent (two runs with the same seed produce logs that differ only in timestamps and
      scratch paths) and stays inside the default machine envelope, finishing in under two minutes (TARGET).
- [ ] The log passes the shared log linter; every `assert` has expected and observed values.

## Test plan

### Unit tests
The script's helper functions (scratch setup, planting a gate value, reading the runner's JSON) have shell unit
tests under `scripts/e2e/tests/registers_exit_helpers.sh`: `scratch_is_isolated` (the real registries' digests are
unchanged after a run); `plant_gate_value_round_trips`; `runner_json_parse_counts`.

### End-to-end script and logging
This bead is the script. It is run by the end-to-end runner at every change to the registries or the exit code,
and by each milestone's exit review as its first step.

### Known answers and negative controls
Known answers: 59, 27, 6, 161; selections of 21, 41 and 56 rows at the M0, M2 and M3 exits; the two questions first
in the M0 listing; sixteen questions with deadline M0, two answered at entry and fourteen to answer or default.
Negative controls: the three mutant runners, under the program's mutation convention (BD-025, N38b-04) and not
an environment switch, so that no real exit can run a mutant: each is a `cfg(feature = "nc-<nnnn>")` branch of
`frob-conformance` at the guard it disables (the review's block on a fired row without outcome and its implementer
check, N41-01; the calendar check's block on a `silent` row, N40-35), added by this bead as the catching bead
(N41-CX) and numbered by the control seeded from X41-11, X41-14 and X41-19 whose `removed_check` names that guard.
The script's `--mutant <nnnn>` option builds the example targets with `--features
gauntlet-mutations,frob-conformance/nc-<nnnn>`, and a run under each must exit non-zero, naming the step whose
expected block did not occur; the planted fired signal; the planted unanswered questions; the planted device claim under a default;
the self-review; the three broken registers of step 1; an approval recorded for OPEN-TENFOLD-4 with no gate
record, which must not clear the M3 block. Determinism: the walk is exact; logs are stable up to timestamps.

## Considerations

- The script walks M0, M2 and M3 because those exits exercise every rule at least once (first review, first
  default with a variant, the default that blocks). Later exits use the same code paths.
- If the registries' row counts change by design (a new risk, a new question), the known answers here change in
  the same commit; a count that changes without this script changing is the drift the script exists to catch.
- The scratch root must not be used as evidence for a real exit; its records are labelled `synthetic`.
