## Background

OPEN-PROG-1 is one of the six open questions that matter most, and the only one that comes due twice: at the first
push of the repository, and again before the pins are frozen for the ten-fold tournament at M7. It asks three
things that only the project owner can answer: whether the repository is public or private; which licence file it
carries; and, the half added when the ten-fold test was designed, **who outside the program can replicate the
ten-fold result**.

Why it matters. The product's central claim is a measured ratio against incumbent tools, accepted by an evaluator
independent of both arms. A result that only its authors can re-run is a weaker kind of evidence than one a third
party has re-run. The plan therefore prepares two artifacts for an outsider whatever the answer: the **replication
kit** (the published manifests, pins, seeds, receipts and scripts from which every number of the report is
recomputed and one pair per stratum is re-run) and **`frob-verify`**, the offline auditor that checks certificates
with no dependency beyond the standard library, on a machine with neither the agent nor a GPU.

Fail-closed default (in force until the owner answers, and recorded as an ADR if a deadline passes): **private;
the suite's licence file; the replication kit and the `frob-verify` binary are the only artifacts prepared for a
third party.** What the default costs: a private repository cannot be independently confirmed (risk RISK-52), so
no report may say that the result was independently confirmed, and a ratio measured without a neutral party is
labelled `self-adjudicated`.

## Scope

In: the decision record; the options with their consequences; the guard that keeps the repository's actual
visibility and licence equal to the recorded decision; the wording consequences; the second asking before the M7
pin freeze. Out: the adjudicator and neutral party (OPEN-PROG-2, N41-06); the replication kit itself; asset licence
enforcement.

## Technical approach

**Commands.** `frob-conformance` has no binary (BD-025), so this bead's two register commands are subcommands it
adds, in its own change, to N41-03's example target `open_questions` (`crates/frob-conformance/examples/
open_questions.rs`): `page <id>` and `require <id> [--json]`, run as `cargo run -p frob-conformance --example
open_questions -- page OPEN-PROG-1` and `cargo run -p frob-conformance --example open_questions -- require
OPEN-PROG-1 --json` (the form N33b-03 calls).

**What is put to the owner** (one page, `docs/delivery/decisions/OPEN-PROG-1.md`, generated from the register by
the `page OPEN-PROG-1` subcommand; this bead's attached check of the exit runner regenerates it at the M0 exit and
again at the M6 exit, one milestone before the M7 freeze):

| Option | Visibility | Licence | Outside replication | Consequences |
|---|---|---|---|---|
| A (default) | Private | The suite's licence file | Nobody; kit and auditor prepared | No "independently confirmed" wording; `self-adjudicated` unless OPEN-PROG-2 names a neutral party with access |
| B | Private, with a named external replicator given read access | The suite's licence file | The named party re-runs the kit | The report may state who re-ran it and what they re-ran; nothing broader |
| C | Private until the tournament report, then public with the kit | A licence chosen by the owner | Anyone | Asset and scene packs must be redistributable before publication; sibling pins must be reachable by an outsider |
| D | Public from the first push | A licence chosen by the owner | Anyone | As C from day one; private-scene and research-only material never enters the repository |

**Recording the answer.** An ADR `docs/adr/ADR-PROG-01-visibility.md` with the option, the licence identifier, the
named replicator if any, and the date; the register row moves to `decided`. If the first push happens with no
answer, the exit reviewer takes the default by the register's default writer, and the ADR says so.

**Guard** (DESIGN; a check in the release checker and in the exit runner, not a seventh `xtask` check):
`scripts/release/visibility-guard.sh` reads the ADR and compares it with (a) the `LICENSE` file's identifier line,
(b) the visibility of the configured remotes as reported by the hosting service's command-line tool, queried with
a generic client and no project details beyond the repository's own name. A public remote under a private
decision, or a licence file that differs from the decision, fails the guard. With no network the guard reports
`unverified` and the release checker treats that as a failure for a release and as a warning for an exit. This
bead delivers the script and its exit codes (0 agree, 3 mismatch with the reason on the first line, 0 with the
reading `unverified` when there is no network), and attaches it to the exit runner of N40-05 by a record of
`scripts/exit/checks.toml`: `id = "visibility-guard"`, `owner = "N41-05"`, `step = 10`, `since = "M0"`, command
`scripts/release/visibility-guard.sh` under the runner's check contract (`<Mn> --root <dir> --json`). In that
mode the script exits 0 whenever it ran (the contract of N40-05; its exit 3 is the release checker's mode only): a
mismatch is a block with the reason `release-visibility` (N41-REF), `unverified` is a warning, and the check's
section carries the decision in force and, at the M0 and M6 exits, the decision page below. The release checker (N41-27) calls the same script and treats
`unverified` as a failure.

**Wording consequences** (enforced by the claims-wording lint over reports and documentation; this bead enters
the phrases below in the claims-wording registry of N00-15 as `[[conditioned_phrase]]` rows, so the registry's
lint refuses or allows them by the option in force). Each row names its `reader`, the command that prints the
decision in force as JSON, and the `field` it reads: here `cargo run -p frob-conformance --example open_questions
-- require OPEN-PROG-1 --json`, which prints `{id, status, option, licence, replicator, adr}` with `option` one of `A` to `D` as recorded in the
ADR, and `A` when the row is `open` or `defaulted`. The two rows: (1) patterns "independently confirmed",
"independently replicated", "open source": `allowed = ["C", "D"]`, and under B the `scoped_form` (DESIGN) "re-run
by {replicator}: {scope}" is the one sentence in which a replication may be stated; (2) pattern "replicable from
the published kit": `allowed = ["C", "D"]` with `also_gates = ["GATE-TENFOLD-08"]` (the replication kit's gate).
In words: under options A and B the phrases "independently confirmed", "independently replicated" and "open
source" are refused; under B the report names the replicator and the scope; under C and D "replicable from the
published kit" is allowed once the kit's own gate has passed.

**Second asking.** At the M6 exit the same page is generated again with the state of the kit and of OPEN-PROG-2.
The M7 pin freeze must not start while this row is `open`: either an answer or the default ADR must exist. This
bead provides the check, `cargo run -p frob-conformance --example open_questions -- require OPEN-PROG-1` (exit 0
when the row is `decided` or
`defaulted` with its ADR; non-zero, naming the row and its deadline, while it is `open`); the opening of the
tournament freeze (N33b-03, M7) calls it before it writes its freeze record.

## Acceptance criteria

- [ ] The register row for OPEN-PROG-1 is `decided` or `defaulted` with an ADR before the first push; the M0 exit
      record lists it either way.
- [ ] The guard fails on a planted public remote under a private decision, and on a planted licence file that
      differs from the decision; it passes when both agree.
- [ ] The wording lint refuses "independently confirmed" in a report under options A and B, and allows the scoped
      statement under B.
- [ ] `cargo run -p frob-conformance --example open_questions -- require OPEN-PROG-1` exits non-zero while the
      row is `open` and zero once it is decided or defaulted with its ADR (the check the opening of the M7 freeze,
      N33b-03, calls).
- [ ] The two wording rows are `[[conditioned_phrase]]` records of the claims-wording registry whose reader is
      `cargo run -p frob-conformance --example open_questions -- require OPEN-PROG-1 --json`, and switching the recorded option from A to C switches the lint's verdict
      on "replicable from the published kit" once the kit's gate has passed.
- [ ] The guard is registered as the check `visibility-guard` of the exit runner: at a scratch M0 exit it exits 0,
      a mismatch blocks with `release-visibility`, `unverified` is listed as a warning and does not block, and the decision page is in the
      check's section at the M0 and M6 exits.
- [ ] The decision page is generated from the register (no hand-written copy) at M0 and at the M6 exit.

## Test plan

### Unit tests
`scripts/release/tests/visibility_guard.sh` and `crates/frob-conformance/tests/open_prog1.rs`:
`public_remote_under_private_decision_fails`; `licence_mismatch_fails`; `agreeing_state_passes`;
`no_network_is_unverified`; `wording_refused_under_private` (a report fixture containing "independently
confirmed"); `scoped_statement_allowed_under_b`; `require_refuses_while_open`; `require_passes_when_defaulted`;
`default_adr_written_at_first_push_deadline`; `page_generated_from_register` (the page's bytes are a function of
the row and the kit state; a hand edit is overwritten); `require_json_reports_option` (`A` while open or
defaulted; the ADR's option once decided); `guard_as_exit_check` (through the runner of N40-05 on a scratch
repository: mismatch → a block naming `visibility-guard`; no network → a warning, verdict unaffected).

### End-to-end script and logging
`scripts/e2e/owner_prog1.sh`: on a scratch repository with a scratch remote configuration, walks default → guard
pass; plants a public remote → guard fail; plants a mismatching `LICENSE` → guard fail; records option B →
wording check on a report fixture (refused phrase and allowed scoped statement); runs `cargo run -p
frob-conformance --example open_questions -- require OPEN-PROG-1` with the row reopened → refusal, and after the
default is taken → pass. Logs: `cmd`, exit code, the decision in force, the guard's observed
visibility and licence, `refusal` lines for the lint and the freeze, and a `summary`.

### Known answers and negative controls
Known answers: the default text; the four options. Negative controls: the planted public remote; the planted
licence mismatch; the planted wording; a decision file edited without a new ADR date (the register's change check
refuses it).

## Considerations

- Sibling repositories are the owner's and several are private; a public FrankenRobotics whose build needs private
  siblings is not replicable by an outsider. Options C and D therefore require that every pinned sibling be
  reachable, or that the kit ship the worker binaries it needs; the decision page lists the pins and their
  visibility.
- Private scenes and research-only assets must never depend on this answer: they are marked and excluded by their
  own rules whatever the visibility.
- Changing from private to public later is possible; the reverse does not un-publish anything. The page says so.
- A late answer does not rewrite history: reports issued under the default keep their wording.
