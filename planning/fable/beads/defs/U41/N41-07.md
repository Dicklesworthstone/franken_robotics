## Background

The learning subsystem exposes a vectorized environment to its own on-device trainer. The ten-fold test also needs
the **rival arm** to reach that environment with the tools an incumbent user would bring, which speak the
Gymnasium interface. A Gymnasium-compatible adapter (`bindings/frob-gymnasium`, a Frontier work package at M3) is
therefore built in any case, and gated: GATE-CORTEX-16 measures its conformance and its overhead, and if it fails,
kill gate KILL-GYMADAPT replaces it by letting the rival drive whole rollouts through the job interface.

The open question is about the product, not the test: **does the adapter ship as a supported, published binding,
or does it exist only as the rival's access path in the ten-fold test and as a conformance target?** Supporting a
published binding to a foreign ecosystem is a standing cost (packaging, versioning against that ecosystem's
releases, documentation, issue handling) and a doctrine matter (the product's binaries contain no foreign-language
interpreter). Only the owner can weigh that against the benefit, which is that external learning stacks get a
supported route into the environment.

Fail-closed default: **built and gated (GATE-CORTEX-16) for the test and for conformance; not a supported public
surface; no interpreter in any `frob` binary.** What the default costs: external learning stacks have no supported
route into the environment; and if the adapter fails its gate the rival drives whole rollouts through the job
interface. Needed by M3, when the adapter lands and the M3 release rubric must say what it is.

## Scope

In: the decision record; what "supported" would add as work; the labels and documentation rules under each
answer; the release-manifest consequences. Out: building the adapter and its gate; the transport question (one
charged copy per step across a process boundary by default) and the binding question (across a process boundary
with shared array files), which are engineering decisions with their own bead.

## Technical approach

**What is put to the owner at the M2 exit** (one milestone early):

| Answer | What ships | Added work if chosen | What may be said |
|---|---|---|---|
| Default: test path only | The adapter in the repository, built by the tournament harness and the conformance suite; marked `support: none` in its manifest | None beyond the gate | "A Gymnasium-compatible adapter exists for conformance and for the comparison protocol"; nothing about support |
| Supported binding | A published package with a version policy, a compatibility matrix against the foreign interface's releases, user documentation, examples that run as demos, and a place in the release rubric | A packaging pipeline; a conformance run in the release checker; a deprecation policy; a named maintainer role | "Supported from release N for interface versions X to Y", with the measured overhead from the gate's disclosure block |

In both cases the invariants hold: no interpreter is linked into any `frob` binary (the adapter is a separate
process that exchanges arrays by the declared transport); the adapter adds no capability the verb registry lacks;
its results carry the claim product like any other.

**Recording.** ADR `docs/adr/ADR-PROG-03-gymnasium.md`; the register row moves to `decided` or `defaulted`. The
adapter's manifest field `support` is set from the ADR (`none` or `supported`), and three readers obey it: the
README generator (lists the adapter under "conformance tools" or under "surfaces"); the release checker (under
`supported`, a release must include the adapter's conformance run and compatibility matrix; under `none`, a
release note that advertises the adapter is refused); the documentation lint (the word "supported" beside the
adapter is refused under `none`).

**Interaction with the kill gate.** If KILL-GYMADAPT fires, the question is moot for that release: there is no
adapter to support; the ADR records that the answer is deferred to the next release in which the gate passes, and
the default stays in force.

## Acceptance criteria

- [ ] The register row is `decided` or `defaulted` with an ADR at the M3 exit, and the exit record lists it.
- [ ] The adapter's manifest carries `support` equal to the ADR; a mismatch fails the release checker.
- [ ] Under the default, a release note or README line that calls the adapter supported is refused; under
      `supported`, a release without the conformance run and matrix is refused.
- [ ] A check confirms that no `frob` binary links an interpreter (symbol and dependency scan) under either answer.
- [ ] If KILL-GYMADAPT fired, the ADR records the deferral and the README lists no adapter surface.

## Test plan

### Unit tests
`crates/frob-conformance/tests/open_prog3.rs`: `manifest_support_matches_adr`; `advertised_under_none_refused`;
`supported_without_conformance_run_refused`; `no_interpreter_in_frob_binaries` (dependency-tree scan of every
binary target); `kill_gate_fired_defers_decision`.

### End-to-end script and logging
`scripts/e2e/owner_prog3.sh`: generates the README and a release manifest under each answer on a scratch tree and
asserts the adapter's placement and the checker's verdicts; plants the advertising line under the default (expects
refusal). Logs: `cmd`, exit code, the decision in force, `refusal` lines, a `summary`.

### Known answers and negative controls
Known answers: the default text; the two manifest values. Negative controls: the planted advertising line; a
planted dependency on an interpreter crate in a scratch binary target (must fail the scan); a manifest set to
`supported` with no ADR.

## Considerations

- Choosing "supported" later is cheap; withdrawing support after publication is not. The page says so.
- The benefit is real for adoption and is not part of the ten-fold thesis either way; the decision does not change
  any gate.
- Licence: a published binding inherits the repository's licence decision (OPEN-PROG-1); a private repository
  cannot publish one.
