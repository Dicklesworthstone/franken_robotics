## Background

The first implementation session is a runbook of eight steps, done before anything else and in order. Each step
produces an **observation, not a scaffold**: a measured fact about the foundations, recorded whether it passes or
fails. The session ends with four honest measurements (does FrankenSim consume cleanly; does fastmcp_rust build
and pass its own checks on the chosen toolchain; do the three backends agree on one algebraic kernel; what does
the rival's loop cost on our card), two sets of exact known answers reproduced with a negative control caught, and
a two-second humanoid rollout on the referee. It does not end with a forest of empty crates.

Working rules for every step of the session: every build goes through the build-offload shim (which queues for a
worker and never compiles locally; cargo is not invoked by absolute path); every run stays inside the default
envelope of 16 GiB, 8 cores, one hour and one device; a sibling repository is changed only as an upstream work
item, in that repository, under its own rules and with its files reserved; a failing result is recorded as
failing, and no step is repeated until it happens to pass.

**Step 1** tests the first assumption everything else stands on: that a workspace **outside** FrankenSim's
directory tree can be made to build against the suite at all. FrankenSim's own excluded crates live inside its
tree and inherit its configuration; the one known outside consumer carries no patch entry, no toolchain file and
no build-identity setting, so it is not evidence. Cargo does not propagate three things from a path dependency to
the workspace that consumes it, so the core workspace must repeat them at its root:

1. the `[patch.crates-io]` entry for asupersync that FrankenSim uses;
2. the profile overrides FrankenSim sets for FrankenSQLite's package (FACT: FrankenSim's manifest states that
   profile overrides are not inherited by a consumer);
3. the build-identity setting: FrankenSim's linear-algebra crate has a build script that fails closed unless a
   dependency-graph receipt or a salt is present in the environment (FACT: `frankensim/crates/fs-la/build.rs`
   panics unless `FRANKENSIM_DEPGRAPH_RECEIPT` or `FRANKENSIM_DEPGRAPH_SALT` is set); inside FrankenSim the salt
   comes from its `.cargo/config.toml`, which an outside workspace does not read.
That patches and environment settings behave as profiles do in our graph is a HYPOTHESIS; this step and the next
settle it.

## Scope

In: running the step on the workspace that the workspace-skeleton bead created; the commands; the observation;
its record. Out: creating the files (the skeleton bead, on which this step depends); consuming a FrankenSim crate
(step 2); the receipt's format and the check that compares receipts (their own beads).

## Technical approach

Preconditions: the repository contains the workspace manifest, one `rust-toolchain.toml` naming candidate (a) for
the toolchain T (the suite's common nightly; `nightly-2026-08-31` on the day of writing, a FACT to re-read) as the
provisional T, `franken-stack.lock`, and `.cargo/config.toml`.

Procedure (each command line and its full output are saved under
`docs/delivery/sessions/first/step-1/`; nothing is edited by hand):

1. Record the session header: commit, host, date, the toolchain file's content, the stack lock's digest.
2. Show the three repeated settings as they stand at the root: print the `[patch.crates-io]` table of the
   workspace manifest, the `[profile.*.package.*]` overrides, and the `[env]` table of `.cargo/config.toml`
   (the core's own salt names its own development equivalence class; it is not FrankenSim's value).
3. `cargo check --workspace --all-targets` through the offload shim, with a 20-minute timeout. Save exit code,
   wall time and the last 200 lines.
4. `cargo metadata --format-version 1` and `cargo tree --workspace -e normal` saved as artifacts (the package
   count at this point is the baseline for step 2).
5. Write the first resolution receipt: for every sibling named in the stack lock, the checkout's head commit,
   whether the tree is clean, the byte hash of the tree, and its **drift class** against the lock (the closed
   set of the receipt format: `on-pin` for the clean state, and classes that tell a fast-forward from a divergence
   and from a dirty tree); the receipt's own hash is recomputable from the lock and the trees.
6. Negative check, to show the record is sensitive: in a scratch copy, touch one file of one sibling checkout and
   regenerate the receipt; the sibling's class must leave `on-pin` (the dirty class) and the receipt hash must
   change. The scratch
   copy is discarded.

**The record this step leaves** (`step-1/record.json`, schema `frob.sessionstep/1`; step 8 copies its summary into
`DEPENDENCY_ADMISSION.md`): `step`, `commands` with exit codes and output digests, `commit`, `toolchain`,
`observation` = { `cargo_check`: pass or fail, `wall_seconds`, `packages`, `receipt_hash`, `drift_classes` per
sibling }, `decides` = ["the hypothesis that an out-of-tree workspace builds with the three repeated settings
(first half; step 2 completes it)", "the first receipt"], `verdict` (`pass`, `fail` or `recorded`).

What the observation decides: whether an out-of-tree workspace builds with the three repeated settings, and the
first receipt against which every later drift is measured. If `cargo check` fails, the failure text is the
observation; the session continues with step 2.

## Acceptance criteria

- [ ] `cargo check` on the workspace is green through the offload shim, or its failure is recorded verbatim with
      exit code; either way `record.json` exists and validates.
- [ ] The three repeated settings are printed in the record from the files as they are.
- [ ] The receipt lists every sibling of the stack lock with head, cleanliness, tree hash and drift class, and its
      hash recomputes from the lock and the trees.
- [ ] The scratch negative check shows `dirty` and a changed receipt hash.
- [ ] No local compile happened (the shim's log shows the build ran on a worker); the run stayed inside the default
      envelope.
- [ ] No sibling repository was modified (their heads and tree hashes are equal before and after the step).

## Test plan

### Unit tests
The record validator has tests in `crates/frob-conformance/tests/session_record.rs`: `record_requires_commands_and_
digests`; `verdict_fail_is_valid_and_kept`; `receipt_hash_recomputes`; `drift_class_closed_set`.

### End-to-end script and logging
`scripts/session/first/step-1.sh` runs the procedure and is itself the end-to-end script; it sources the shared
helper and logs `start`, one `cmd` line per command (exact command line, exit code, wall time), `metric` lines
(packages, wall seconds), `assert` lines (receipt recomputes; scratch check shows `dirty`), and `end`, with a
`summary`. It is idempotent: a second run on the same commit produces the same receipt hash.

### Known answers and negative controls
Known answer: the receipt hash recomputed from the lock and the trees equals the recorded one. Negative controls:
the touched-file scratch check; in a second scratch copy, the `[env]` salt removed (expected to make step 2's
build fail closed; here it is only recorded that the setting is present).

## Considerations

- The provisional T may change in step 3; this step records what T was when it ran.
- A dirty sibling is acceptable for a development build with the tree hash in the receipt; no gate may record a
  PASS on it. The session records the drift classes and does not clean anybody's tree.
- The cold check time recorded here is for an empty workspace; the figure that matters for the worker-process
  decision is step 2's.
