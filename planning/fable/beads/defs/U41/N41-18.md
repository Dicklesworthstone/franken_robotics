## Background

The first implementation session is a runbook of eight steps, done before anything else and in order. Each step
produces an **observation, not a scaffold**: a measured fact about the foundations, recorded whether it passes or
fails. The session ends with four honest measurements (does FrankenSim consume cleanly; does fastmcp_rust build
and pass its own checks on the chosen toolchain; do the three backends agree on one algebraic kernel; what does
the rival's loop cost on our card), two sets of exact known answers reproduced with a negative control caught, and
a two-second humanoid rollout on the referee. It does not end with a forest of empty crates.

Working rules for every step of the session: every build goes through the build-offload shim (which queues for a
worker and never compiles locally; cargo is not invoked by absolute path); every run stays inside the default
envelope of 16 GiB, 8 cores, one hour and one device; a sibling repository is changed only as an upstream work
item, in that repository, under its own rules and with its files reserved; a failing result is recorded as
failing, and no step is repeated until it happens to pass.

**Step 1** tests the first assumption everything else stands on: that a workspace **outside** FrankenSim's
directory tree can be made to build against the suite at all. FrankenSim's own excluded crates live inside its
tree and inherit its configuration; the one known outside consumer carries no patch entry, no toolchain file and
no build-identity setting, so it is not evidence. Cargo does not propagate three things from a path dependency to
the workspace that consumes it, so the core workspace must repeat them at its root:

1. the `[patch.crates-io]` entry for asupersync that FrankenSim uses;
2. the profile overrides FrankenSim sets for FrankenSQLite's package (FACT: FrankenSim's manifest states that
   profile overrides are not inherited by a consumer);
3. the build-identity setting: FrankenSim's linear-algebra crate has a build script that fails closed unless a
   dependency-graph receipt or a salt is present in the environment (FACT: `frankensim/crates/fs-la/build.rs`
   panics unless `FRANKENSIM_DEPGRAPH_RECEIPT` or `FRANKENSIM_DEPGRAPH_SALT` is set); inside FrankenSim the salt
   comes from its `.cargo/config.toml`, which an outside workspace does not read.
That patches and environment settings behave as profiles do in our graph is a HYPOTHESIS; this step and the next
settle it.

## Scope

In: the session's record of step 1, made on the workspace that the workspace-skeleton bead (BD-001) created:
the session header; the three repeated settings printed from the files as they stand; `cargo check` run through
the shim and recorded, pass or fail; the `cargo metadata` and `cargo tree` artifacts (the package-count
baseline for step 2); the verification that the first resolution receipt regenerates byte for byte, with its
hash and the drift class of every sibling copied into the record; the scratch negative check replayed; the
record `step-1/record.json`, its validator and the step script. The validator is the one every step of the session
uses (later steps add cases to it); it and its tests live in the conformance crate created by BD-025, and the step
script sources the logging helper of STD-E2E, so both are dependencies. They stand only on the workspace and on
`frob-core` v0 (BD-005), so the session's record can be validated in the first days of M0.

Out, with the bead that has it:
- creating the workspace and writing the first receipt: the root manifest, `rust-toolchain.toml`,
  `.cargo/config.toml`, `franken-stack.lock`, the receipt `receipts/<blake3>.json`, the generator
  `scripts/bootstrap/first_receipt.sh` that writes it, the two-commit order that puts the receipt's hash into
  the lock, and the skeleton's entry in `DEPENDENCY_ADMISSION.md`: BD-001, on which this step depends. The plan
  names BD-001 for step 1; this bead adds the session's record of it and writes no file of the workspace and no
  receipt;
- consuming a FrankenSim crate (step 2); the receipt's format and drift classification (N33a-04) and the check
  that compares receipts (their own beads).

## Technical approach

Preconditions: the repository contains the workspace manifest, one `rust-toolchain.toml` naming candidate (a) for
the toolchain T (the suite's common nightly; `nightly-2026-08-31` on the day of writing, a FACT to re-read) as the
provisional T, `franken-stack.lock`, and `.cargo/config.toml`.

Procedure (each command line and its full output are saved under
`docs/delivery/sessions/first/step-1/`; nothing is edited by hand):

1. Record the session header: commit, host, date, the toolchain file's content, the stack lock's digest.
2. Show the three repeated settings as they stand at the root: print the `[patch.crates-io]` table of the
   workspace manifest, the `[profile.*.package.*]` overrides, and the `[env]` table of `.cargo/config.toml`
   (the core's own salt names its own development equivalence class; it is not FrankenSim's value).
3. `cargo check --workspace --all-targets` through the offload shim, with a 20-minute timeout. Save exit code,
   wall time and the last 200 lines.
4. `cargo metadata --format-version 1` and `cargo tree --workspace -e normal` saved as artifacts (the package
   count at this point is the baseline for step 2).
5. Verify the first resolution receipt. The receipt was written by BD-001 (`receipts/<blake3>.json`, schema
   `frob.stack-receipt/1`): for every sibling named in the stack lock, the checkout's head commit, whether the
   tree is clean (`dirty`), the byte hash of the tree when it is dirty, and its **drift class** against the
   sibling's own lock. The classes are the closed set of the receipt format, three and no more: `on-pin` (the
   checkout is at the pin and clean), `stale-lock` (clean, and a fast-forward of the pin) and `drift` (dirty,
   retreated, diverged or an unknown pin, with the sub-reason stored beside the class). This step runs BD-001's
   generator again on the unchanged tree and compares its output with the stored receipt byte for byte; the
   receipt's hash must equal its file name and the `receipt` field of the lock rows. The record takes the
   receipt hash and the class of every sibling from the stored receipt. If a sibling checkout moved between
   BD-001 and this step, the regenerated receipt differs: it is then stored beside the first as a further
   receipt, the record lists the differing fields, and the first receipt is never overwritten.
6. Negative check, to show the record is sensitive: in a scratch copy, touch one tracked file of one sibling
   checkout and regenerate the receipt with the same generator; that sibling's `dirty` must become true, its
   class must leave `on-pin` and read `drift` (sub-reason dirty), its `tree_hash` must change, and the receipt
   hash must change. The scratch copy is discarded. (This is BD-001's control for KA-767, replayed inside the
   session so that the session record shows it; the control is registered once, by BD-001.)

**The record this step leaves** (`step-1/record.json`, schema `frob.sessionstep/1`; step 8 copies its summary into
`DEPENDENCY_ADMISSION.md`): `step`, `commands` with exit codes and output digests, `commit`, `toolchain`,
`observation` = { `cargo_check`: pass or fail, `wall_seconds`, `packages`, `receipt_hash`, `receipt_regenerates`:
true or false, `drift_classes` per sibling }, `decides` = ["the hypothesis that an out-of-tree workspace builds
with the three repeated settings (first half; step 2 completes it)", "the first receipt"], `verdict` (`pass`,
`fail` or `recorded`). The skeleton's own entry in `DEPENDENCY_ADMISSION.md` (commands, outputs, receipt hash)
is written by BD-001; step 8's copy of this record's summary cites the same receipt hash and adds no second
receipt.

What the observation decides: whether an out-of-tree workspace builds with the three repeated settings, and the
first receipt against which every later drift is measured. If `cargo check` fails, the failure text is the
observation; the session continues with step 2.

## Acceptance criteria

- [ ] `cargo check` on the workspace is green through the offload shim, or its failure is recorded verbatim with
      exit code; either way `record.json` exists and validates.
- [ ] The three repeated settings are printed in the record from the files as they are.
- [ ] The receipt of BD-001 lists every sibling of the stack lock with head, cleanliness, tree hash and drift
      class, and regenerating it on the unchanged tree gives the same bytes; the record holds its hash. This
      step writes no receipt on an unchanged tree.
- [ ] Every drift class in the record is one of `on-pin`, `stale-lock`, `drift`.
- [ ] The scratch negative check shows `dirty: true`, class `drift` and a changed receipt hash.
- [ ] No local compile happened (the shim's log shows the build ran on a worker); the run stayed inside the default
      envelope.
- [ ] No sibling repository was modified (their heads and tree hashes are equal before and after the step).

## Test plan

### Unit tests
The record validator has tests in `crates/frob-conformance/tests/session_record.rs`: `record_requires_commands_and_
digests`; `verdict_fail_is_valid_and_kept`; `receipt_hash_recomputes`; `drift_class_closed_set` (a record
holding any class other than `on-pin`, `stale-lock` or `drift`, for example `dirty` as a class, is rejected).

### End-to-end script and logging
`scripts/session/first/step-1.sh` runs the procedure and is itself the end-to-end script; it sources the shared
helper and logs `start`, one `cmd` line per command (exact command line, exit code, wall time), `metric` lines
(packages, wall seconds), `assert` lines (receipt regenerates byte for byte; scratch check shows `dirty: true`
and class `drift`), and `end`, with a `summary`. It calls BD-001's generator and never writes under `receipts/`
on an unchanged tree. It is idempotent: a second run on the same commit produces the same receipt hash.

### Known answers and negative controls
Known answer: the receipt hash recomputed from the lock and the trees equals the recorded one (KA-767, owned
and registered by BD-001). Negative controls: the touched-file scratch check; in a second scratch copy, the
`[env]` salt removed (expected to make step 2's build fail closed; here it is only recorded that the setting is
present; BD-001 runs the `fs-la` probe build that shows the failure).

## Considerations

- The provisional T may change in step 3; this step records what T was when it ran.
- A dirty sibling is acceptable for a development build with the tree hash in the receipt; no gate may record a
  PASS on it. The session records the drift classes and does not clean anybody's tree.
- The cold check time recorded here is for an empty workspace; the figure that matters for the worker-process
  decision is step 2's.
