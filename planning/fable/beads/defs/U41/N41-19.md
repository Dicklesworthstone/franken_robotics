## Background

The whole program consumes FrankenSim, a large and fast-moving sibling library, by path at a pinned commit, through
one airlock crate. The bet that this is affordable (BET-04) stands on a measurement that had not been taken when
the plan was written: does a crate **outside** FrankenSim's tree, depending by path on its geometric-algebra and
multibody crates, build and compute the same numbers as FrankenSim computes for itself? Step 2 of the first
session takes that measurement, with the smallest program that can: build FrankenSim's built-in G1 humanoid model,
run forward dynamics at one state, and compare a digest with the digest a test inside FrankenSim produces at the
same commit.

FACTs that make this non-trivial (each to be re-read at the pinned commit): a path dependency on the multibody
crate compiles 42 other FrankenSim crates and about 1.57 million lines; its linear-algebra crate's build script
fails closed outside the tree without the build-identity setting; 409 commits touched the multibody crate in the
thirty days before planning. If the cold check exceeds the machine envelope, or the effort to get the admission
passing exceeds its budget, kill gate KILL-FSIM names the fallbacks in order: a pinned FrankenSim worker process
first, a lift of a minimal referee set second.

Session rules apply (offload shim; default envelope; no sibling edited; a failing result is recorded as failing and
not retried until it passes). **If this step fails, the session still completes steps 3 to 8, because none of them
depends on it, and the failure is the session's most important result.**

## Scope

In: running the step on the artifacts of the admission bead and the airlock's first version; the commands; the
four observations (digest equality, sensitivity, build cost, the two-second rollout); the record. Out: writing the
consuming crate, the digest test inside FrankenSim and the referee wrapper (the two seed beads this step depends
on); the worker-process fallback (its own bead); the `sim.run` verb (a later M0 bead; this step calls the crate's
test binary directly).

## Technical approach

Procedure (artifacts under `docs/delivery/sessions/first/step-2/`):

1. *Cold check.* With an empty, isolated target directory (under the offload shim's target base), run
   `cargo check -p frob-fsim --all-targets` with a 60-minute timeout. Record wall time, peak resident memory of
   the heaviest compiler process as the shim reports it, and the package count from `cargo metadata`.
2. *Warm check.* Run the same command again unchanged; record wall time.
3. *Fail-closed control.* In a scratch copy with the build-identity variable removed from `.cargo/config.toml`, run
   the same check; it must fail in the linear-algebra crate's build script. Record the failure line.
4. *Digest inside FrankenSim.* In FrankenSim's checkout at the pinned commit, without modifying it, run the
   existing test that prints the digest of forward dynamics for the built-in G1 model at the fixed state (the
   state, the digest function and the test's name are those the admission bead fixed). Record the digest.
5. *Digest from here.* Run the consuming crate's test that builds the same model through the airlock, evaluates
   forward dynamics at the same state and prints the digest. Record it and compare byte for byte.
6. *Sensitivity control.* Perturb one input (the first joint position by one unit in the last place) and confirm
   that the digest changes; a digest that does not change is a defect of the digest, recorded as a failure.
7. *Two-second rollout.* Step the model on the referee for two seconds of simulated time at the referee's default
   step from the fixed initial state with zero actuation, and record the final-state digest, the number of steps,
   and wall time. Run it twice; the two digests must be equal.

**The record** (`step-2/record.json`, schema `frob.sessionstep/1`): commands with exit codes and output digests;
`observation` = { `digest_frankensim`, `digest_here`, `digests_equal`, `perturbed_digest_differs`,
`cold_check_seconds`, `warm_check_seconds`, `peak_memory_gib`, `packages`, `fail_closed_without_setting`,
`rollout_digest`, `rollout_steps`, `rollout_repeat_equal` }; `decides` = ["INT-FSIM-01", "BET-04's measurement",
"whether KILL-FSIM's worker process is needed at once", "the hypothesis of step 1, second half"]; `verdict`.

What the observation decides: the admission INT-FSIM-01; the figures BET-04 stands on; whether the worker-process
fallback is needed at once (if the cold check is over the envelope of one hour, 16 GiB, 8 cores, or the digests
cannot be made equal).

## Acceptance criteria

- [ ] The record states whether the two digests match; if they do, the admission record of INT-FSIM-01 is filled
      from this run; if they do not, both digests and the first differing intermediate (link index and quantity,
      where the tests print it) are recorded and the step's verdict is `fail`.
- [ ] Cold and warm check times, peak memory and package count are recorded with units.
- [ ] The build fails closed with the build-identity variable unset.
- [ ] A one-unit-in-the-last-place perturbation changes the digest.
- [ ] The two-second rollout ran twice with equal final digests, or its failure is recorded.
- [ ] FrankenSim's checkout is byte-identical before and after the step.

## Test plan

### Unit tests
None new: the step runs tests owned by its dependencies. The record validator's tests (shared with step 1) cover
`digests_equal_requires_both_digests` and `verdict_fail_keeps_all_observations`.

### End-to-end script and logging
`scripts/session/first/step-2.sh`: the procedure above, with the shared logging helper: `cmd` lines for each
command with exit code and wall time; `metric` lines for cold seconds, warm seconds, peak memory and packages
against the envelope thresholds (3,600 s, 16 GiB); `assert` lines for digest equality, sensitivity, fail-closed
and rollout repeatability, each with both values; on failure the first differing value and the artifact paths.
`summary` names INT-FSIM-01 as touched.

### Known answers and negative controls
Known answer: the digest printed by FrankenSim's own test at the pinned commit (an oracle that is never
regenerated from this repository). Negative controls: the perturbed input; the unset build-identity variable.
Determinism: the rollout twice on one machine with equal digests.

## Considerations

- The digest compares numbers produced by the same code compiled in two graphs; a mismatch points at feature
  unification, a patch that did not apply, or a different dependency version, and the saved `cargo tree` output of
  both graphs is the first thing to compare.
- The two-second rollout has no known answer yet; it is recorded so that the first referee artifact exists and can
  be reproduced by a fresh session later.
- Peak memory matters as much as time: the envelope caps both.
