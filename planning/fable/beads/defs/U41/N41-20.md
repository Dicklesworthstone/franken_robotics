## Background

The owner decided that the whole build graph uses **one toolchain T**, and that the MCP server crate `frob-mcp` is
a member of the core graph running verbs in process. That decision has a cost that falls due in the first
session. On the day of planning the siblings were apart (FACTs to be re-read): four nightlies and one stable
release were in play; FrankenSim pinned `nightly-2026-07-06`; the suite's common nightly, most siblings' pin, was
`nightly-2026-08-31`; FrankenSymPy pinned `nightly-2026-08-20` and fastmcp_rust `nightly-2026-08-25`; fastmcp_rust
declared a minimum compiler version of 1.100 while FrankenSim's pin was a 1.99 nightly; and three siblings still
pinned asupersync 0.5.0 while FrankenSim's lockfile resolved 0.6.2 by path. A build may contain exactly one
asupersync package, and the units crate `fs-qty` enables an incomplete compiler feature that not every nightly
still builds.

Step 3 turns those statements into counts taken on this machine, fixes T on the evidence of step 2, and then does
the first piece of upstream work of the program: bringing fastmcp_rust onto T **in fastmcp_rust's own repository,
under its own rules** (upstream work item FD-FMCP-01, priority P0). The candidates for T, in order of preference:
(a) the suite's common nightly; (b) FrankenSim's present pin, if step 2 showed that FrankenSim does not build on
(a), with the toolchain train to (a) scheduled.

Session rules apply: offload shim; default envelope; a sibling is changed only as an upstream work item, in that
repository, under its own rules and with its files reserved; a failing result is recorded as failing.

## Scope

In: the three counts; the choice of T from step 2's record; the run of the fastmcp_rust change, its suite and its
conformance checks on T; the record. Out: the change set itself and its landing through fastmcp_rust's gates (the
upstream work item's bead and the admission bead this step depends on); aligning asupersync across siblings
(FD-ASUP-01); the full toolchain matrix (its own bead, which this step seeds); `frob-mcp` in the core graph (the
admission INT-FMCP-01, completed by its bead).

## Technical approach

Procedure (artifacts under `docs/delivery/sessions/first/step-3/`):

1. *Count asupersync.* `cargo tree -d --workspace` in the core workspace through the offload shim; record how many
   asupersync packages the build contains and at which versions and sources. Expected for a pass: one.
2. *Which nightlies compile `fs-qty` alone.* For each of the four nightlies in play, in an isolated target
   directory, `cargo +<nightly> check -p fs-qty` against FrankenSim's checkout (read-only; the override is on the
   command line, no file in the sibling is touched). Record pass or fail per nightly with the first error line.
   These are the first cells (the `fs-qty` row) of the toolchain matrix.
3. *Fix T.* Read step 2's record. If FrankenSim built and matched on candidate (a), T = (a). If it did not build on
   (a), T = (b) from here on, and the record says so with the failing evidence. Write T into `rust-toolchain.toml`
   and the stack lock only if it changed, as one commit that names the evidence.
4. *fastmcp_rust on T, in its repository.* Reserve the files to be touched through the coordination tool; read its
   `AGENTS.md`; on a branch, set its toolchain file to T and, where T requires it, its declared `rust-version`;
   make no other change in this step.
5. *Build and check it.* In fastmcp_rust's workspace: `cargo build --workspace`, `cargo test --workspace`, and its
   MCP conformance checks as its own documentation defines them, all through the offload shim. Record each
   command's exit code, test counts (passed, failed, ignored) and wall time.
6. *Record the result, passing or failing.* If everything is green, the change proceeds through fastmcp_rust's own
   gates under the upstream work item, and its mirrored bead is updated. If anything fails, the failing tests and
   errors are recorded verbatim and nothing is forced: the upstream item stays open, and the admission bead
   decides whether the fix is small or whether KILL-MCP's fallbacks must be considered at the M0 exit.
7. *Release reservations* and record the sibling's head before and after.

**The record** (`step-3/record.json`, schema `frob.sessionstep/1`): `observation` = { `asupersync_packages`: count
and list, `fs_qty_by_nightly`: map, `T`: the chosen nightly and which candidate it is, `T_changed_from_provisional`,
`fastmcp_build`, `fastmcp_tests`: counts, `fastmcp_conformance`: counts, `sibling_branch`, `sibling_head_before`,
`sibling_head_after` }; `decides` = ["INT-ASUP-01 and the need for FD-ASUP-01", "the choice of T and the
`frob-units` decision rule", "FD-FMCP-01, and with it whether INT-FMCP-01 can pass in the core graph"]; `verdict`.

What the observation decides: the number of asupersync packages (the admission INT-ASUP-01 and the upstream
alignment FD-ASUP-01); which nightlies build `fs-qty` (the choice of T and the rule for the units escape hatch: if
`fs-qty` fails on the chosen T, the preferred fix is an upstream change in FrankenSim and T is candidate (b) until
it lands); whether fastmcp_rust builds and passes its own checks on T (FD-FMCP-01, and with it whether INT-FMCP-01
can pass in the core graph).

## Acceptance criteria

- [ ] The asupersync package count and list are recorded from `cargo tree -d`.
- [ ] Each of the four nightlies has a recorded pass or fail for `fs-qty` alone.
- [ ] T is recorded with the candidate letter and the evidence from step 2; the toolchain file and the stack lock
      agree with it.
- [ ] fastmcp_rust's build, test suite and MCP conformance checks were run on T in its own repository, and their
      results are recorded with counts, passing or failing.
- [ ] The only files changed in fastmcp_rust are its toolchain file and, where required, the declared
      `rust-version`; the change is on a branch under a file reservation; no other sibling was modified.
- [ ] The record validates; the bead closes on the recorded observation whatever the verdict.

## Test plan

### Unit tests
None new. The record validator covers `t_must_be_candidate_a_or_b`, `sibling_change_lists_only_allowed_files`
(a diff touching any other path fails validation) and `counts_are_integers`.

### End-to-end script and logging
`scripts/session/first/step-3.sh` with the shared logging helper: `cmd` lines for every command; `metric` lines for
the asupersync count (threshold 1), per-nightly results, test counts; `assert` lines for "T equals toolchain file
equals stack lock", "sibling diff limited to the allowed files" and "reservations released"; `summary` naming
INT-ASUP-01, INT-TOOLCHAIN-01 and INT-FMCP-01 as touched (partial).

### Known answers and negative controls
Known answers: none numeric; the expected state for a pass is one asupersync package and green suites. Negative
controls: a scratch manifest with a seeded second asupersync version must show two packages in `cargo tree -d`; a
scratch sibling diff that also edits a source file must fail the record validation.

## Considerations

- This step may legitimately end with T = (b) and a red fastmcp_rust suite; both are results, and the M0 exit
  review reads them.
- Under candidate (a) the same toolchain train must also advance FrankenSim's pin and move FrankenSymPy; those
  are separate upstream beads and are not attempted inside the session.
- Other agents may be working in the sibling; the reservation and the small, additive change are what keep the
  collision risk low.
- The nightly names are facts of one day and are re-read by the matrix bead.
