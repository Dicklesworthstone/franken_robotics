## Background

The owner decided that the whole build graph uses **one toolchain T**, and that the MCP server crate `frob-mcp` is
a member of the core graph running verbs in process. That decision has a cost that falls due in the first
session. On the day of planning the siblings were apart (FACTs to be re-read): four nightlies and one stable
release were in play; FrankenSim pinned `nightly-2026-07-06`; the suite's common nightly, most siblings' pin, was
`nightly-2026-08-31`; FrankenSymPy pinned `nightly-2026-08-20` and fastmcp_rust `nightly-2026-08-25`; fastmcp_rust
declared a minimum compiler version of 1.100 while FrankenSim's pin was a 1.99 nightly; and three siblings still
pinned asupersync 0.5.0 while FrankenSim's lockfile resolved 0.6.2 by path. A build may contain exactly one
asupersync package, and the units crate `fs-qty` enables an incomplete compiler feature that not every nightly
still builds.

Step 3 turns those statements into counts taken on this machine, fixes T on the evidence of step 2, and then
checks the first piece of upstream work of the program: bringing fastmcp_rust onto T, which is done **in
fastmcp_rust's own repository, under its own rules** by the upstream work item FD-FMCP-01 (priority P0); the
session builds and checks the result on T in a scratch clone and records it, passing or failing. The candidates for T, in order of preference:
(a) the suite's common nightly; (b) FrankenSim's present pin, if step 2 showed that FrankenSim does not build on
(a), with the toolchain train to (a) scheduled.

Session rules apply: offload shim; default envelope; a sibling is changed only as an upstream work item, in that
repository, under its own rules and with its files reserved; a failing result is recorded as failing.

## Scope

In: the three counts; the session's working choice of T, made from step 2's record and the `fs-qty` row alone, and
written into the toolchain file and the stack lock; the run of the fastmcp_rust change, its suite and its
conformance checks on that T; the record.

Out, with the bead that has it: the choice of T as the gate INT-TOOLCHAIN-01 records it (BD-031, which depends on
this step): the full matrix of six build sets on four nightlies, the decision rule applied to every row, the two
ADRs (the choice of T; the `frob-units` decision), the foundation rows' toolchain fields with the new resolution
receipt, the admission record and the gate row. That bead takes this step's `fs-qty` cells as the first row of its
matrix and confirms this step's T or replaces it; where the two differ, the gate's choice governs and the files are
rewritten in the gate's commit. This step writes no ADR and records no PASS of the gate. Also out: the change set
itself and its landing through fastmcp_rust's gates (the upstream work item's bead and the admission bead this
step depends on); aligning asupersync across siblings (FD-ASUP-01); `frob-mcp` in the core graph (the admission
INT-FMCP-01, completed by its bead).

## Technical approach

Procedure (artifacts under `docs/delivery/sessions/first/step-3/`):

1. *Count asupersync.* `cargo tree -d --workspace` in the core workspace through the offload shim; record how many
   asupersync packages the build contains and at which versions and sources. Expected for a pass: one.
2. *Which nightlies compile `fs-qty` alone.* `scripts/admission/toolchain_matrix.sh --sets 1` (the harness of
   N33c-01): for each of the four nightlies in play it checks the probe workspace `tests/admission/toolchain/1/`
   of this repository, which path-depends on `fs-qty`, with `cargo +<nightly> check --all-targets --locked`
   through the offload shim and a target directory of its own per cell. No cargo command runs inside
   FrankenSim's checkout, so its `Cargo.lock` and target directory are never touched (INV-SUITE-04). Record pass
   or fail per nightly with the first error and the failure kind, as the harness writes them to
   `receipts/matrix/<utc>.ndjson` (schema `frob.toolchain-matrix/1`). These are the first cells (the `fs-qty`
   row) of the toolchain matrix, and because they are the harness's own records the gate (BD-031) resumes them as
   its finished first row; a row made any other way would not be resumed.
3. *Fix T (the session's working choice).* Read step 2's record. If FrankenSim built and matched on candidate (a),
   T = (a). If it did not build on (a), T = (b) from here on, and the record says so with the failing evidence.
   Write T into `rust-toolchain.toml` (`channel = "<T>"`) and the stack lock (top-level `toolchain = "<T>"`) only
   if it changed, as one commit that names the evidence. This is the same rule as the gate's, applied to the two
   rows the session has (FrankenSim's closure from step 2 and `fs-qty` from point 2): the gate INT-TOOLCHAIN-01
   (BD-031) applies it to all six build sets and may still move T, for example when a row this session did not
   run (the Metal annex, `derive/frob-derive`) fails on (a). Until that gate records its choice, T is this one,
   and every later step of the session builds on it.
4. *fastmcp_rust on T, as the upstream item left it.* The change itself (the toolchain file set to T, the declared
   `rust-version` where T requires it, and any repair the newer nightly forces) is made, reserved and landed on
   fastmcp_rust's `main` by the upstream work item FD-FMCP-01, a dependency; this step makes no change in the
   sibling. Record the commit FD-FMCP-01 landed (or, if it closed `fallback` because KILL-MCP fired, the commit
   and failing evidence it recorded), the files it changed, and the sibling's head and tree hash.
5. *Build and check it, outside the sibling's checkout.* Clone that commit into
   `target/upstream-scratch/fastmcp_rust@<rev>` (the same scratch place FD-FMCP-01's script uses; never building
   inside the sibling's checkout) and run there, on T and without `--ignore-rust-version`:
   `cargo build --workspace --all-targets --locked`, `cargo test --workspace --locked`, and its MCP conformance
   checks as its own documentation defines them, all through the offload shim. Record each command's exit code
   and wall time; for the test suite its counts (passed, failed, ignored), where a pass needs zero failed; for the
   MCP conformance checks (the named server-mode checks of its README) their counts against the baseline of 112 of
   115 passing and 0 failing measured at revision `1c2dc896`, every check whose state changed from that baseline
   listed by name. The two baselines are not interchangeable: 115 is the number of conformance checks, not of
   tests.
6. *Record the result, passing or failing.* If everything is green, the record is the session's confirmation of
   FD-FMCP-01 on this T. If anything fails, the failing tests and errors are recorded verbatim and nothing is
   forced: the admission bead and the M0 exit review read the record and decide whether KILL-MCP's fallbacks must
   be considered.
7. *Record the siblings' heads and tree hashes after the step*, and compare them with those before.

**The record** (`step-3/record.json`, schema `frob.sessionstep/1`): `observation` = { `asupersync_packages`: count
and list, `fs_qty_by_nightly`: map, `T`: the chosen nightly and which candidate it is, `T_changed_from_provisional`,
`fastmcp_commit`: the commit built and whether FD-FMCP-01 closed `pass` or `fallback`, `fastmcp_build`,
`fastmcp_tests`: counts, `fastmcp_conformance`: counts, `matrix_records`: the cell records of point 2 by hash,
`sibling_heads_before`, `sibling_heads_after` (head and tree hash of every sibling) }; `decides` = ["INT-ASUP-01 and the need for FD-ASUP-01", "the choice of T and the
`frob-units` decision rule", "FD-FMCP-01, and with it whether INT-FMCP-01 can pass in the core graph"]; `verdict`.

What the observation decides: the number of asupersync packages (the admission INT-ASUP-01 and the upstream
alignment FD-ASUP-01); which nightlies build `fs-qty` (the choice of T and the rule for the units escape hatch: if
`fs-qty` fails on the chosen T, the preferred fix is an upstream change in FrankenSim and T is candidate (b) until
it lands); whether fastmcp_rust builds and passes its own checks on T (FD-FMCP-01, and with it whether INT-FMCP-01
can pass in the core graph).

## Acceptance criteria

- [ ] The asupersync package count and list are recorded from `cargo tree -d`.
- [ ] Each of the four nightlies has a recorded pass or fail for `fs-qty` alone, as a cell record of
      `toolchain_matrix.sh --sets 1`; a following full run of the harness by BD-031 skips those four cells.
- [ ] T is recorded with the candidate letter and the evidence from step 2; the toolchain file and the stack lock
      agree with it.
- [ ] fastmcp_rust's build, test suite and MCP conformance checks were run on T, at the commit FD-FMCP-01 left, in
      a scratch clone, and their results are recorded with counts against the baseline, passing or failing.
- [ ] This step changed no sibling: every sibling's head and tree hash are equal before and after, and no cargo
      command of the step ran with its working directory inside a sibling checkout.
- [ ] The record validates; the bead closes on the recorded observation whatever the verdict.

## Test plan

### Unit tests
None new in a crate of their own. The record validator (N41-18) gains `t_must_be_candidate_a_or_b`,
`siblings_unchanged_by_step` (a record whose sibling head or tree hash differs before and after fails
validation with `reason=session-sibling-changed`, the harness reason of N41-REF),
`fs_qty_cells_are_matrix_records` (a `fs_qty_by_nightly` entry with no matching cell record fails) and
`counts_are_integers`.

### End-to-end script and logging
`scripts/session/first/step-3.sh` with the shared logging helper: `cmd` lines for every command; `metric` lines for
the asupersync count (threshold 1), per-nightly results, the suite's test counts (threshold: 0 failed) and the
conformance counts against their baseline (112 of 115 passing, 0 failing); `assert` lines for "T
equals toolchain file equals stack lock", "siblings unchanged (head and tree hash)", "no cargo command ran inside
a sibling checkout" (every `cmd` line's working directory is in this repository or the scratch clone) and "a
second `toolchain_matrix.sh --sets 1` runs zero cells"; `summary` naming INT-ASUP-01, INT-TOOLCHAIN-01 and
INT-FMCP-01 as touched (partial).

### Known answers and negative controls
Known answers: none numeric; the expected state for a pass is one asupersync package and green suites. Negative
controls: a scratch manifest with a seeded second asupersync version must show two packages in `cargo tree -d`; a
scratch record whose sibling tree hash after the step differs from before (X41-36, a sibling patched locally
outside its upstream work item) must fail the record validation with `session-sibling-changed`.

## Considerations

- This step may legitimately end with T = (b) and a red fastmcp_rust suite; both are results, and the M0 exit
  review reads them.
- Under candidate (a) the same toolchain train must also advance FrankenSim's pin and move FrankenSymPy; those
  are separate upstream beads and are not attempted inside the session.
- Other agents may be working in the sibling; the step only reads its history and builds a scratch clone, so it
  cannot collide with them (the reservations belong to FD-FMCP-01, which edits).
- The nightly names are facts of one day and are re-read by the matrix bead.
