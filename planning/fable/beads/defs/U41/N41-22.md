## Background

Step 4 of the first session ran a twenty-line Cayley step on Metal and compared it bit for bit with a Rust loop.
Step 5 runs **the same kernel text with the CUDA prelude** on the training machine `trj`, on both of its RTX 4090
cards, and compares with the same Rust loop. With both steps recorded the program has its first three-way
observation: one algebraic kernel on the CPU, on Metal and on CUDA.

Why it is a separate step. The CUDA path has its own toolchain facts (FACTs to re-read at admission): the binding
crate is pinned to an exact version with its driver, runtime-compiler and dynamic-loading features, so that the
driver and the runtime compiler are loaded at run time and the build needs no vendor toolkit; dialect source is
compiled per device architecture to a cached binary; compile flags disable multiply-add fusion; each device has
one context and one host thread; the two cards have no direct link, and whether they allow device-to-device
access is an open question recorded by the hardware fingerprint. The step also runs on a different machine,
which is often heavily loaded, so its timings are context and not measurements of anything.

Session rules apply (builds through the offload shim; default envelope of one device for one hour per job, so the
two cards are two jobs; no sibling edited; failures recorded as failures).

## Scope

In: the first observations on CUDA, taken with the first version of the CUDA annex, before the derived kernel,
the comparator and the probe verb exist: the hand-written Cayley step of step 4 on both cards, the square-root
half of the unary IEEE probe on card 0; the commands; the record `frob.sessionstep/1`; the three-way comparison
with step 4.

Out, with the bead that has it:
- The annex and its admission (BD-015, the seed bead this step depends on); the hardware fingerprint (BD-029);
  launch graphs (N21b-03).
- The gate GATE-SPARK-00 itself (BD-020): the same comparison on the derived, checked-in text of `K-cay-step`
  through `spark.check`, with divergence-ledger rows, its two negative controls and the gate record. The
  three-way table of this step is an earlier observation that BD-020's record cites; it enters no row for the
  gate.
- The gate GATE-SPARK-01 itself (BD-017): the full probe (reciprocal, the sampled operand pairs, the
  contraction detector), its comparison rule and classes, the report `frob.probe/1` and the attainable class.
  Procedure step 6 below applies that bead's comparison rule to the square root alone and sets no class.
- The per-family class decision: KILL-D1 (N21b-34).

## Technical approach

Procedure on `trj` (artifacts under `docs/delivery/sessions/first/step-5/`, copied back as files; only seeds,
kernel text, digests and records cross between the machines):

1. Record the devices: for each card, model, memory, driver version, runtime-compiler version, device
   architecture; and the host load at the time.
2. *Kernel text.* Take the dialect body saved in step 4 (same BLAKE3 hash) and prepend the CUDA prelude; save the
   combined text and hash. Compile with the runtime compiler with contraction disabled; record the flags and the
   compiled binary's hash.
3. *Inputs and reference.* Regenerate the 10⁶ inputs from the seed of step 4 and confirm the input digest equals
   step 4's; compute the Rust-loop reference on `trj`'s CPU and confirm its digest equals step 4's reference
   digest (the reference must be the same bits on both hosts, or the comparison means nothing).
4. *Run on card 0, then on card 1,* as two separate jobs. For each: count of elements differing from the
   reference, first difference if any, output digest.
5. *Contraction control.* Compile once with fusion enabled and run on card 0; record whether the output differs.
6. *Square root, exhaustive,* on card 0: all 2³² bit patterns against the correctly rounded reference, mismatches
   by class. (The reciprocal comparison belongs to the full probe.) Comparison rule, classes and chunking are
   those step 4 used, which are the probe bead BD-017's: bit patterns against Rust `f32::sqrt`; both-NaN lanes
   agree in value with payload agreement recorded; mismatches counted as `normal`, `subnormal-operand`,
   `subnormal-result`, `signed-zero`, `overflow-edge`; 256 chunks of 2²⁴ lanes.
7. *Three-way table.* CPU reference digest, Metal digest (from step 4's record), CUDA digests for both cards:
   equal or not, pairwise.

**The record** (`step-5/record.json`, schema `frob.sessionstep/1`): `observation` = { `devices`, `flags`,
`kernel_body_hash` (equal to step 4's), `input_digest_equal_to_step_4`, `reference_digest_equal_to_step_4`,
`card0`: { `differing_elements`, `digest` }, `card1`: the same, `fusion_enabled_differs`, `sqrt_mismatches`,
`three_way`: pairwise equality, `host_load` }; `decides` = ["GATE-SPARK-00 (CUDA rows and the three-way
statement)", "the first half of GATE-SPARK-01 for the CUDA family", "the best attainable determinism class of the
CUDA family, input to KILL-D1", "INT-CUDA-01's first run"]; `verdict`. As in step 4, `decides` repeats the
session table's "decides or informs" column; the gate rows are entered by BD-020 and BD-017 from their own runs.

What the observation decides, with step 4: GATE-SPARK-00 (agreement inside the class, recorded in the divergence
ledger); the first half of GATE-SPARK-01; each family's best attainable determinism class.

## Acceptance criteria

- [ ] The kernel ran on both cards; the record gives the number of differing elements per card (zero for a pass)
      and the first difference if any.
- [ ] The kernel body hash, the input digest and the reference digest equal those of step 4.
- [ ] The fusion-enabled control was run and its outcome recorded.
- [ ] The square-root comparison covered all 2³² inputs on one card, with mismatch counts by class.
- [ ] The three-way table is in the record.
- [ ] Each card's run was its own job inside the default envelope; nothing but text, seeds, digests and records
      crossed machines.
- [ ] The record validates; the bead closes on the recorded observation whatever the verdict.

## Test plan

### Unit tests
None new on the device. Host-side, in `crates/frob-conformance/tests/session_record.rs`:
`reference_digest_is_host_independent` (the Rust loop's digest for the recorded seed is a golden value, equal to
step 4's reference digest, checked on both machines); `prelude_concatenation_keeps_body_hash` (prepending the CUDA
prelude leaves the BLAKE3 hash of the dialect body equal to step 4's); `step5_record_requires_both_cards` (a
`frob.sessionstep/1` record for step 5 with `card1` missing, or with `kernel_body_hash` different from step 4's
and verdict `pass`, is rejected; the same record with verdict `fail` and the difference stated is valid).

### End-to-end script and logging
`scripts/session/first/step-5.sh` (run on `trj`) sources the shared logging helper of STD-E2E and writes
`target/e2e-logs/step-5/<utc-timestamp>.ndjson` and a transcript; every line carries `ts`, `script`, `bead`
(`N41-22`), `step` and `event`. It logs `start`; one `cmd` line per command with the exact command line, exit
code and wall time; `metric` lines for differing elements per card (threshold 0), square-root mismatches by class
(threshold 0 for finite non-negative operands), compile time and host load (context, no threshold); `assert`
lines for the three equalities with step 4 (body hash, input digest, reference digest, each with both digests)
and for each pair of the three-way table; on any difference, the first differing element index with both values
in hexadecimal, and the paths of the record, the kernel text and the compiled binary needed to reproduce; `end`;
and a `summary` with assertions passed and failed, naming INT-CUDA-01, GATE-SPARK-00 and GATE-SPARK-01 as touched
(partial). Evidence fields: tier `gpu-cuda`, device identifiers, determinism class as measured, seed.

### Known answers and negative controls
Known answers (K41-29): the reference digest of step 4; the correctly rounded square root. Negative controls: the
fusion-enabled compile; a one-ulp change planted in the CUDA prelude (the macro `FROB_F32_BITS(b)` of BD-013
redefined as the reinterpretation of `(b) + 1u`, so that each constant the kernel writes by bit pattern, step 4's
1 and ½, moves to the next float up), which the three-way comparison must report as a difference on that backend
only. That plant is the case of X41-50: the script compares the same output once more through the mutant
comparison of N41-21 (feature `kernel-tolerance-comparison`, an absolute tolerance of 10⁻⁵; the plant moves a
unit-quaternion component by less than 10⁻⁶), which must report no difference, so that the bit-for-bit comparison
is shown to be what catches it. The last control is a seed altered by one in a scratch copy of the step-4 record,
which the input-digest equality must catch before any device run.

## Considerations

- A difference between the two cards of one family would itself be a finding (the same binary on the same
  architecture should agree); it is recorded and escalated, not averaged away.
- Compile time on a loaded host is noisy and is recorded only as context; the binary kernel cache makes later
  runs independent of it.
- If the runtime compiler cannot be loaded (driver mismatch), the failure is the observation and the admission
  bead decides the repair.
- Kill gate: if the CUDA family cannot be made bit-equal to the CPU, KILL-D1 (N21b-34, decided at M2) takes its
  named fallback: class D2 within the family and D3 against the others, with paired statistics refused under an
  uncontrolled class. This step only supplies the first evidence; it decides nothing.
- Whether the two cards allow device-to-device access is OPEN-SPARK-6; its fail-closed default (host-staged
  transfers of small statistics only) holds here, and nothing in this step needs peer access.
