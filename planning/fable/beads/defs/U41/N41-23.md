## Background

The product's thesis is a ratio against incumbent tools. A ratio has a denominator, and the plan's rule is that
**the incumbent is measured before a mechanism is funded against it**, on our own card, at pinned versions, in its
strongest warm configuration. The reason is arithmetic: if an incumbent already trains a flat-ground quadruped in
minutes, then no speedup of training alone can make a design loop ten times faster, and the ceiling of each lever
must be computed from the measured phases before any speed test is designed. One planning-time pilot showed how a
speed test can be incapable of confirming its own claim: a specialized solver measured 1.345 times a composed one
with a residual of work it did not touch, so that no solver could have shown more than about 1.46 times.

Step 6 of the first session takes the first measured entries of that denominator. No FrankenRobotics code is
compared with anything in this step; the point is to know the denominator before building against it. The
published context for the last figure (a FACT from the source register, to be re-read at its primary source) is
about 410 s to the return threshold of a flat-ground quadruped velocity task on one RTX 4090, of which about 45 s
is compilation, so the run fits the default envelope of one device and one hour.

Session rules apply (default envelope; a failing or surprising result is recorded as it is; nothing is repeated
until it looks better).

## Scope

In: running four measurements of one pinned incumbent stack on one card through the out-of-process harness; the
disclosure block; the record; the first row of the incumbent phase ledger. Out: the harness and its pinned
environment, and the complete parity baseline on both cards and both workloads (the two seed beads this step
depends on); the Mac-side baselines (the M1 completion bead); any comparison with our own code.

## Technical approach

The incumbent runs **out of process**, driven by a script under `tools/oracle`, from a recorded environment
(container digest or lockfile hash); no incumbent code is linked into any product binary, and its outputs are
typed as Parity context, never as Reality.

Procedure on `trj`, one RTX 4090 (artifacts under `docs/delivery/sessions/first/step-6/`):

1. *Pin and disclose.* Record the incumbent stack's name, revision and environment digest from the oracle
   register; the driver and card; the host load (load average and other GPU tenants) at the start and end of each
   measurement; whether caches were warm; the repetition count.
2. *Cold start to the first step.* From a fresh process with cold kernel and asset caches: wall-clock from launch
   to the completion of the first simulation step of the flat-ground quadruped task at the stack's own
   recommended world count. Repeat five times (a DESIGN count, written into the disclosure block; caches cleared
   each time); record every value.
3. *A parameter edit to the first step.* With the process warm: change one link length of the robot model by its
   own tools' intended route, and measure wall-clock until the first step of the edited model. Repeat 5 times.
4. *A topology edit to the first step.* The same for an edit that adds one link and joint. Repeat 5 times.
5. *Wall-clock to the return threshold.* Train its flat-ground quadruped velocity task with the stack's own
   reference configuration to the return threshold that the stack's documentation or the published comparison
   uses; record wall-clock, split into compilation and training where the stack reports it, the threshold, the
   world count and the step count. One run; a second only if the first was interrupted (recorded).
6. *Enter the ledger.* Each figure goes into the incumbent phase ledger as a measured row with its disclosure
   block, beside the published figure where one exists, with the relative difference; a difference above 20% from
   a published figure is written up (configuration, hardware, version) rather than reconciled by tuning.

**Disclosure block** (attached to each figure): incumbent revision and environment digest; driver; card; host
load; cache state (cold or warm); repetition count and every repetition's value; world count and step size; the
command line; the date.

**The record** (`step-6/record.json`, schema `frob.sessionstep/1`): `observation` = { `cold_start_s`: [5 values],
`param_edit_to_first_step_s`: [5], `topology_edit_to_first_step_s`: [5], `time_to_threshold_s`, `compile_s`,
`threshold`, `worlds`, `published_context_s`: 410, `relative_difference` }, each with its disclosure block;
`decides` = ["the first row of GATE-SPARK-21", "the denominator of BET-13", "the ceilings for the quadruped
class", "the planning value of GATE-CORTEX-05"]; `verdict` (`recorded`; there is no pass or fail for a
measurement of somebody else's software).

What the observation decides: the denominator of the ten-fold bet; the ceilings stated before anything is built
for the quadruped class (the class was given an expected range of 3 to 10, and the measured training time is what
that range rests on); the planning value for the training-time parity gate. It is also the answer to the first
"every gate passed and the claim still failed" reason: nothing confirmable exists without an incumbent
measurement on record at the M0 exit.

## Acceptance criteria

- [ ] The four measurements are recorded with every repetition and a complete disclosure block each.
- [ ] The incumbent ran out of process from the pinned environment; a changed revision would change the harness
      identity (asserted by re-reading the identity after the run).
- [ ] The time to threshold is entered beside the published figure with the relative difference; a difference
      above 20% has a written explanation in the record.
- [ ] The run stayed inside the default envelope (one device, one hour per job, 16 GiB, 8 cores), or the step
      records exactly which measurement could not and was not run.
- [ ] No FrankenRobotics figure appears in the record.
- [ ] The first row of GATE-SPARK-21 is recorded with measured values, the commit, the hardware fingerprint if it
      exists yet, and the seed where the incumbent exposes one.

## Test plan

### Unit tests
The ledger writer's tests (owned by the harness bead) are re-run. This step adds validation cases:
`disclosure_block_required_per_figure`; `repetitions_all_kept` (a record with a mean but no per-repetition values
is rejected); `no_own_code_figures_in_step_6`.

### End-to-end script and logging
`scripts/session/first/step-6.sh` (run on `trj`) with the shared logging helper: `cmd` lines with the incumbent's
command lines; `metric` lines for each measured value with unit, repetition index and host load, and for the
published context beside it; `assert` lines for "environment digest equals the oracle register" and "disclosure
complete"; `summary` naming GATE-SPARK-21 as touched (first row). Logs carry no private-scene data.

### Known answers and negative controls
There is no known answer for a measurement. The published context (about 410 s, about 45 s of it compilation) is a
FACT to compare with, not a target. Negative controls: a record with a figure lacking its disclosure block is
rejected; a harness run with a different incumbent revision has a different identity and its figures cannot be
entered in the same ledger row.

## Considerations

- The loaded host makes single measurements noisy; repetitions are kept individually so that later analysis can
  use medians or paired lower bounds. No figure is dropped as an outlier in this step.
- Licences: whether the incumbent's licence permits publishing a comparison is a separate open question; this
  step records figures internally either way.
- The edit-latency measurements depend on what counts as "the stack's intended route" for an edit; the route used
  is written into the disclosure block so that a rival advocate can later challenge it.
- If the incumbent is faster than its published figure, that is the more important result, and the ceilings are
  recomputed from it.
