## Background

Two fixtures put a cart at a dock, and both have answers that need no simulator. Step 7 of the first session
reproduces those answers in this repository with a program that uses the standard library alone, in exact
rational arithmetic, and plants one negative control. It exists because the thesis rests on exact known answers:
before any simulator is trusted, the program must show it can compute a strict decision exactly and catch the one
change that should alter it. The program is the seed of the checking code in the offline auditor and of the
fixture's derivation file, and it holds the first known answers reproduced in this repository.

**The docking family.** Position in metres, time in seconds. A robot docks in three one-second ticks from
x₀ = v₀ = 0, with acceleration g·u_k held constant over tick k, a hidden fixed gain g ∈ {1, 2}, commands bounded by
|u_k| ≤ U, and target (x₃, v₃) = (1, 0). Exact zero-order-hold integration gives v₃ = g·(u₀ + u₁ + u₂) and
x₃ = g·(5u₀/2 + 3u₁/2 + u₂/2). The only informative packet is the first velocity reading v₁ = g·u₀, which arrives
either before the second command is decided (on time) or after the third is committed (late). With the early
packet carrying additive error in [−ε, +ε] and first command p = u₀, the terminal equations force u₁ = 1/g − 2p
and u₂ = p − 1/g; the actuator bounds for both gains give 1 − U ≤ p ≤ (U + 1/2)/2; and the two reading sets,
centred at p and 2p, must be disjoint, p > 2ε. The mission is solvable exactly when

  ε < (U + 1/2)/4, with equality excluded.

Session rules apply (default envelope; a failing result is recorded as failing).

## Scope

In: running the exact program once, in session order, in debug and release and twice each; reading its checks,
its negative control and the analytic rows of the cart, sill and dock fixture from its output; the session-step
record (`frob.sessionstep/1`) with the program's source hash and the observation.

Out, and where it is: the program `tools/pilots/docking_exact` itself, its rational type, every check listed
below, its test module, the rule that it uses the standard library alone and holds no floating-point type, and
the re-run of the pilot from its reproduction bundle with the records in the pilot register: BD-041, the seed
bead this step depends on. This step writes no code and adds no check; the checks are listed below so that the
step can be read alone, and where the two differ BD-041 governs. The fixture's simulation rows; the mission
engine that later recovers the family through public verbs.

## Technical approach

Program: `tools/pilots/docking_exact` (standard library only; integers and a small rational type over `i128`
with reduced fractions; no floating point anywhere). One location (DESIGN, the same statement in BD-041, which
had placed the program in a test file of the conformance crate): a standalone crate with an empty dependency
table, written by BD-041; the conformance target `crates/frob-conformance/tests/pilot_docking.rs` calls the same
crate, so the session and the battery of GATE-GAUNT-08 run one program. Reason: "the standard library alone" is
checkable on an empty dependency table, and the seed of the auditor's arithmetic must not inherit the
conformance crate's dependencies. Its source hash is recorded. Checks, in order (artifacts under
`docs/delivery/sessions/first/step-7/`):

1. *Grid.* 17 actuator bounds U = 1/2 + k/32, k = 0 … 16, and 33 error levels ε = j/64, j = 0 … 32: 561 cells.
   Classify each by ε < (U + 1/2)/4, that is j < 16 + k/2. Expected: **344 admitted, 217 excluded, nine of the
   excluded cells lying exactly on the boundary** (the cells with k even and j = 16 + k/2).
2. *Witness sequences.* Integrate the cart exactly, tick by tick, for (u₀, u₁, u₂) = (1/4, 1/2, −3/4) with g = 1 and
   (1/4, 0, −1/4) with g = 2: both must end at (x₃, v₃) = (1, 0) exactly and stay within U = 3/4.
3. *Equality case.* At U = 3/4 and ε = 5/16 with p = 5/8, the reading sets are [5/16, 15/16] and [15/16, 25/16]:
   both worlds can read 15/16, while the required second commands are −1/4 (g = 1) and −3/4 (g = 2). The cell is
   excluded.
4. *Late packet.* For every one of the 561 cells, a causal controller must issue one command vector in both
   worlds; x₃ scales with g, so it cannot equal 1 for both gains: all 561 late-packet cells are excluded.
5. *Three-gain amendment.* Admit a third gain 33/32. At U = 3/4 and ε = 1/64 the reading (65/64)·p is possible for
   both g = 1 and g = 33/32 for every first command, so both worlds receive the same remaining commands; the final
   positions are c and 33c/32; the smallest achievable worst absolute error is 1/65 m, at c = 64/65.
6. *Negative control.* Replace the strict comparator by a non-strict one (ε ≤ (U + 1/2)/4) and re-classify:
   **exactly nine cells change**, the nine boundary cells, and the count becomes 353 admitted.
7. *The analytic layer of the cart, sill and dock fixture.* Recompute the rows that are pure arithmetic on the
   fixture's constants, read from its constants file: total masses 8.000 kg and 8.225 kg (the two wheel variants);
   tread force caps 40 N and 32 N; lip levers √(h·(2r − h)) = 36.000 mm and 40.694 mm at a 12 mm sill for wheel
   radii 60 mm and 75 mm; friction demands at front lift-off, lever/(r − h) = 0.7500 and 0.6459. Exact values are
   kept as rationals or as square roots of integers (√1296 = 36 exactly; √1656) and printed to the stated digits.
   A constant changed after this point changes the fixture's identity (architecture decision ADR-ARENA-10).

**The record** (`step-7/record.json`, schema `frob.sessionstep/1`): `observation` = { `cells`: 561, `admitted`:
344, `excluded`: 217, `boundary`: 9, `witness_g1`, `witness_g2`: final states, `equality_reading`: "15/16",
`late_packet_excluded`: 561, `three_gain_worst_error`: "1/65", `control_cells_changed`: 9,
`fixture_rows`: the eight values, `fixture_identity` (the BLAKE3 digest of the fixture's constants file as read),
`program_hash` }; `decides` = ["the fixtures of GATE-AUGUR-03 and GATE-ARENA-04",
"doctrine rule D-18, that a strict decision is computed exactly", "the shape of the auditor"]; `verdict`.

What the observation decides: that the fixtures later used by the mission gate and the task-fixture gate have
answers this repository can reproduce; that strict decisions are computed exactly and never by the sign of a
floating-point residual; and the shape of the auditor (small, exact, dependency-free).

## Acceptance criteria

- [ ] The program reports 561 cells: 344 admitted, 217 excluded, nine on the boundary.
- [ ] Both witness sequences reach (1, 0) exactly; the equality case shows the common reading 15/16 and the two
      second commands; all 561 late-packet cells are excluded; the three-gain worst error is 1/65 m at c = 64/65.
- [ ] The non-strict control changes exactly nine cells, and the test fails if the number is anything else.
- [ ] The eight fixture rows are reproduced to the stated digits from the fixture's constants.
- [ ] The program depends on the standard library only (its manifest has an empty dependency table) and contains
      no floating-point type (a source lint).
- [ ] The record carries the program's source hash; the run takes under one second (TARGET) inside the default
      envelope.

## Test plan

### Unit tests
None new: the step runs the program's own test module, which BD-041 owns and names (`grid_counts`,
`boundary_cells_are_even_k` with the nine pairs (k, j) = (0, 16), (2, 17), …, (16, 24), `witness_g1`,
`witness_g2`, `equality_reading`, `late_packet_all_excluded`, `third_gain_worst_error`,
`nc_nonstrict_changes_nine`, `lip_lever_r60_is_36_exact`, `lip_lever_r75_squared_is_1656`,
`friction_demand_three_quarters_exact`, `rational_type_reduces`, `manifest_has_no_dependencies`,
`source_has_no_float_type`). The record validator's tests (shared with the other steps of the session) cover
the record; this step adds one case to them in `crates/frob-conformance/tests/session_record.rs` (the
validator and that test file are N41-18's, a dependency of this step):
`step7_record_counts_consistent` (a step-7 record is rejected when `admitted + excluded ≠ cells`, when
`control_cells_changed ≠ boundary`, or when `fixture_identity` is absent; the record 561 = 344 + 217 with 9 and 9
passes, and 561 with 345 + 217 fails).

### End-to-end script and logging
`scripts/session/first/step-7.sh` sources the shared logging helper of STD-E2E and writes
`target/e2e-logs/step-7/<utc-timestamp>.ndjson` and a transcript; every line carries `ts`, `script`, `bead`
(`N41-24`), `step` and `event`. It logs `start`; one `cmd` line per run (debug and release, twice each) with the
exact command line, exit code and wall time (TARGET under 1 s); `metric` lines for each count against its expected
value; `assert` lines for each exact equality with both sides printed as fractions; the negative control's `assert`
with expected 9 and observed; an `assert` that the four runs' outputs are byte-identical (their BLAKE3 digests);
the program hash and the fixture identity as digests; on failure the first differing value (the cell (k, j) or
the row name, expected and observed) and the paths of the program output and the record; `end`; and a `summary`
with assertions passed and failed, naming GATE-GAUNT-08 (plan-time pilot re-run) as touched and GATE-AUGUR-03 and
GATE-ARENA-04 as seeded. Evidence fields: class `Tested`, labelled `synthetic`, determinism D0, seed `none`
(the program draws nothing).

### Known answers and negative controls
Known answers (exact; K41-31 to K41-33): 561, 344, 217, 9; the two witness sequences; 15/16; 561 late-packet
exclusions; 1/65 m; masses 8.000 and 8.225 kg; caps 40 N and 32 N; levers 36.000 mm and 40.694 mm; demands 0.7500
and 0.6459. Negative controls: X41-34, the non-strict comparator (nine cells change; any other number fails);
X41-51, one constant of the fixture changed in a scratch copy of its constants file (the 75 mm wheel radius made
76 mm) while the recorded identity is kept: the script recomputes the identity, finds it differs from the record
and fails with `session-record-invalid`, and the lever row reads √1680 = 40.988 mm instead of 40.694 mm. A second
control for the
rational type (the same grid evaluated in `f32` on the boundary screen) is not part of this step (the exact-integer
kernel probe owns it). Determinism: byte-identical output in debug and release, on Linux and macOS.

## Considerations

- The comparator is the whole point: the nine boundary cells are where a floating-point comparison or a
  non-strict inequality silently changes the answer.
- A screen compiled for the gain set {1, 2} is not reused on {1, 33/32, 2}: under that amendment every one of its
  positive labels is wrong. The record keeps the gain support with the counts.
- No timing or device claim follows from a scalar model; this step produces known answers only.
