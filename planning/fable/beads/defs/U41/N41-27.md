## Background

A **release** is anything a user outside the implementing swarm is told they can use. The moment of release is
when overstatement does its damage: a capability described more broadly than what was tested, a demo that stands
in for a measurement, a failing gate left out of a status table. Nine rules apply to every release.

1. **Implemented means the eight conditions.** Each capability in the release meets all eight conditions of
   "implemented", or is listed as partial with the missing conditions named.
2. **No demo, no release.** Each release path has a demo file whose claims exist in the gate register and whose
   commands finish in under 60 seconds on the CPU tier (TARGET). A demo shows that a path runs; the numbers come
   from the gate.
3. **The status table is generated.** The README's honest-status table is produced from the gate registry. A
   failing gate appears as failing, and a fallback appears under the fallback's name.
4. **Each cell names its capability and its limit.** No capability is described more broadly than the fixture that
   qualified it. "Exact static family with independent active vertical reactions" is a release cell; "mission
   synthesis" is not.
5. **A losing experiment reproduces as readily as a winning one.** The release ships the commands, addresses and
   seeds for at least one result that went against the plan.
6. **Performance comes with its disclosure block**, and any ratio against an incumbent with the ten-fold
   measurement protocol.
7. **Every exported artifact carries the flags**, all false, and nothing in the release documentation contradicts
   them.
8. **The exit review was done by a fresh-context session**, and its record is part of the release.
9. **Reality is stated.** Every report in the release prints `reality: no-claim` or names its calibrated cell.

The eight conditions of rule 1, restated so that this bead stands alone. A capability is implemented only when:
(1) code exists in the crate the design maps it to; (2) the crate ships a `CONTRACT.md` with ten sections
(purpose, inputs, outputs, invariants, refusals, determinism class, evidence class of outputs, validity domain,
oracles, known gaps); (3) known-answer tests pass against a pinned oracle that was never regenerated from the
candidate; (4) outputs that cross the agent boundary carry the claim product (kind of claim, evidence class set by
the weakest input, tier, determinism class, model identity, seed, the no-authorization flags), and no naked
numbers reach an agent; (5) a CPU reference path exists, and where a GPU path is claimed a retained differential
check against the CPU path exists for the same kernels; (6) the capability is reachable through `frob --json`
with a documented schema and exit code and, where the verb registry exposes it to agents, through the MCP server;
(7) cancellation is tested: request, drain, finalize, with no leaked device resources; (8) its gate has a recorded
PASS carrying the measured values, not the targets, in a receipt that names the commit, the hardware fingerprint
and the seed. Two riders: a capability that emits a certificate about a family travels in a certificate bundle
that the offline auditor accepts on a machine with neither the agent nor a GPU, rejecting the registered
mutations; a Frontier or Moonshot capability needs its pilot and its kill-gate decision on record, and one that
fell back is described by the name of the fallback.

## Scope

In: the release manifest's capability cells as far as the nine rules read them; the checker; its refusals; the
per-capability verification of the eight conditions at release time (re-evaluated, not trusted from a cached
status). Out: the manifest schema's evidence-kind fields and the device-receipt checks (N41-29, which extends the
workspace contract check); the per-milestone rubric (N41-28); the capability registry itself; demos; the status
table generator.

## Technical approach

Files (DESIGN): `releases/<milestone>/release.toml` (schema `frob.release/1`, defined in `frob-core` together with
the evidence-kind fields of N41-29); `crates/frob-conformance/src/release/{manifest.rs, rules.rs}`; command
`frob-conformance release check releases/M1/release.toml --json` (wrapped by `scripts/release/check.sh`); report
`target/release/<milestone>/report.json`.

**Manifest, the part read here.**

```toml
milestone = "M1"
commit    = "<hash>"
exit_record = "docs/delivery/exits/M1/EXIT.md"
[[cell]]
capability = "cap:mission.synthesize.static-family"
name   = "Exact static family with independent active vertical reactions"   # rule 4: capability and limit
fixture = "fixture:stance-family"            # the fixture that qualified it
gates  = ["GATE-AUGUR-03"]
demo   = "demos/mission-static-family/demo.yaml"
status = "implemented"                       # or "partial" with `missing = [..]`, or "fallback" with its name
[[losing_result]]                            # rule 5
claim  = "<claim id>"
commands = ["frob ... --seed 7"]
addresses = "<address set id>"
```

**Rule checks** (each failure is a refusal of the release with a rule number, the cell and a repair).

1. Recompute each cell's capability status with the capability registry's status function at the release commit.
   `implemented` in the manifest requires all eight conditions and the applicable riders; `partial` requires the
   manifest's `missing` list to equal the computed one; a cell whose computed status is `Fallback` must be named
   by the fallback's name.
2. Each cell has a demo file; every claim identifier in the demo exists in the gate register; run the demo's
   commands on the CPU tier and require each to finish in under 60 seconds and its output checksums to match.
3. Regenerate the README status table from the gate registry and compare bytes with the committed table; a
   failing gate must appear as failing and a fallback under its own name.
4. Breadth: the cell's `name` is compared with the qualifying fixture's registered scope: every scope term of the
   fixture (the limits recorded with it) must appear in the name or in the cell's `limits` list, and the name must
   not be a bare cluster or verb name. A registry of forbidden broad names per capability (for example "mission
   synthesis" for the static-family cell) is checked.
5. At least one `losing_result` exists, its claim resolves in the artifact graph to a result whose verdict went
   against a registered prediction, bet or hypothesis, and its commands with the given seeds reproduce the
   recorded digests (run at check time where they fit the demo budget; otherwise the recorded reproduction receipt
   is required).
6. Every performance figure in the release documentation and in cell metadata has a disclosure block (revision,
   driver, device, host load, cache state, repetition count); every ratio against an incumbent cites a ten-fold
   protocol record; a bare figure is refused.
7. Every artifact listed for export carries the no-authorization flags, all false; the documentation is scanned by
   the wording lint for statements that contradict them (authorization, certification or safety approval).
8. `exit_record` exists for the milestone, was recorded by a session that implemented none of the milestone's
   beads, and is included in the release bundle.
9. Every report in the release bundle prints a reality line that is `no-claim` or names a calibrated cell that
   exists in the calibration registry.

The checker's verdict is `release-ok` or a list of refusals. It is run by the exit runner before any release note
is written, and again on the final bundle.

## Acceptance criteria

- [ ] Each of the nine rules has a planted violation in a scratch manifest that the checker refuses with the rule
      number, the cell and a repair.
- [ ] A cell marked `implemented` whose capability lacks any one of the eight conditions is refused under rule 1,
      naming the missing condition; the eight single-condition plants are all caught, and so are the two riders.
- [ ] A cell marked `partial` with a `missing` list that differs from the computed one is refused.
- [ ] A demo that takes 61 seconds, or cites a claim absent from the gate register, is refused under rule 2.
- [ ] A hand-edited status table is refused under rule 3; a failing gate missing from the table is refused.
- [ ] The cell named "mission synthesis" for the static-family fixture is refused under rule 4; the full name is
      accepted.
- [ ] A release with no losing result is refused under rule 5.
- [ ] The checker is deterministic and its report is part of the release bundle.

Known answers: the nine rules; the eight conditions and two riders; the 60-second demo budget; the example cell
names. Negative controls: the planted violations above (one per rule, eight for rule 1's conditions).
Determinism: the checker is exact apart from demo timing, which is compared with its budget.

## Considerations

- Rule 1 recomputes status at release time on purpose: a capability can regress from implemented to partial when
  a gate is re-run and fails, and a release must show that.
- Rule 4 is the hardest to mechanize. The check enforces scope terms and forbidden names; the fresh-context
  reviewer still reads every cell name, and the exit record says so.
- Rule 5 needs a losing result to exist; the program will have them (a pilot that falsified, a kill gate that
  fired, a bet that lost). A release with none is suspicious, which is why the rule refuses it.
- A release at milestone N includes every earlier release's rules; the checker therefore runs all nine at every
  milestone, with the rubric adding what must and must not be said.
