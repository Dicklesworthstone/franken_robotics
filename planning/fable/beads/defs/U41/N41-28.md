## Background

The nine release rules say what every release must satisfy. The rubric says, milestone by milestone, **what the
release is, what a user can do with it, what must be true before it is released, and what must not be said about
it**. The last column is as important as the others: most overstatement happens in a release note, in words that
no gate measures. This bead keeps the rubric as data and wires its four columns to checks: the "can" column to the
release manifest's cells, the "must be true" column to gates and records, and the "must not be said" column to
the wording lint.

Two rules span the table. A release at milestone N includes every earlier release's rules. A capability withdrawn
by a later kill gate is removed from the next release's table with the ADR that withdrew it, and stays visible
there as withdrawn.

## Scope

In: the rubric registry `registries/rubric.toml`, which is the one source of the three sentences of each row
(what a user can do, what must be true, what must not be said); the mapping of each row's columns to checks; the
cumulative rule; the withdrawal rule; the generated rubric document `docs/delivery/releases.md`.
Out: the status views generated from `registries/gates.toml` alone: the README table, the dashboard feed and the
gate section of the rubric, `docs/release/STATUS.md` (gates due per milestone with their statuses, kill decisions
with their fallbacks), with the register of generated views and the equality test (N38b-20, a dependency: this
bead reads gate statuses through that bead's generator and registers its own document in that register; that
bead prints none of the three sentences). Also out: the nine release rules and the checker core (N41-27);
evidence kinds and dispositions (N41-29); the wording lint's engine (N00-01) and the claims-wording registry with
its gate-conditioned lint (N00-15); the content of each milestone's demonstrations.

## Technical approach

File (DESIGN): `registries/rubric.toml` (schema `frob.rubric/1`), one `[[release]]` per milestone with `name`,
`user_can` (capability identifiers), `must_be_true` (gate identifiers, record checks), `must_not_say` (phrase
patterns with the condition under which each is lifted), read by `crates/frob-conformance/src/release/rubric.rs`.

**The rubric.**

| Milestone | Release | A user can | Must be true before it is released | Must not be said |
|---|---|---|---|---|
| M0 | None. An admission record, internal | Read which foundations were admitted and what the rival's loop costs on the training machine | Every admission has its record; the incumbent ledger has its disclosure blocks | Anything about FrankenRobotics' own speed or accuracy |
| M1 | Studio preview, CPU | Write and import designs, run `design check`, simulate on the referee, read telemetry and the energy ledger, and ask the first mission queries with certificates checked by `frob-verify` | The North-Star scenarios NS-01, NS-07 and NS-22 demonstrated by a fresh agent; GATE-AUGUR-05 and GATE-LEMMA-03; the schedule gate (BET-12) recorded | Any GPU or throughput statement; "qualified"; realism of any scene |
| M2 | Gym release | Train and evaluate at scale on CUDA, Metal or `batch-cpu`, run many designs in one batch, replay any world alone, fork a run | Parity figures published with disclosure blocks, inside or outside tolerance; the M2 kill decisions recorded; a determinism class on every result; device results labelled exploratory unless the GPU-annex decision (OPEN-SPARK-1) is ratified | An advantage over incumbents; bit equality beyond the class each device attained |
| M3 | Qualification release | Evaluate in seven interior archetypes, compare under a declared study, qualify a result in the blinded lane, find and shrink failures, attribute a failure | GATE-QUAL-01 and the firewall gates (GATE-QUAL-02, GATE-SAFE-03); GATE-NEMESIS-03; GATE-AUTOPSY-03; the partial ten-fold gate recorded with its phase ledgers | The word ten-fold, unless the ten-fold decision rule permits it; realism while norms are `assumed` |
| M4 | Design-science release | Run co-design campaigns over families, use family policies and inheritance where admitted, ask mission queries at scale, search retrofits, state an energy-budget claim | Rank agreement on record for every class a rung may eliminate in; the family-policy bets decided; every rung's label printed on its results | A safety claim above `Tested`; a ranking from a rung without a record |
| M5 | Evidence release | Obtain kernel certificates, issue a reality band inside a calibrated cell, ingest a real place privately, emit a build packet | The Reality lane has a record or a recorded no-claim; every flag false; material and card provenance printed | Sim-to-real certification; fabrication release; "physically validated" beyond a named calibrated cell |
| M6 | Frontier profiles, one per epic, behind feature flags | Enable an epic's physics and run its known answers | The epic's pilot and kill decision are on record; its results carry its tier | That any frontier profile is part of the ten-fold thesis |
| M7 | The tournament report | Read the measured ratio per stratum and re-run the published artifacts | Publication whatever the ratio; pins recorded; every certificate replayed; the adjudication status stated, `self-adjudicated` if no neutral party served | "Independently accepted" without a neutral party; ten-fold outside the confirmed strata |
| M8 | Frontier delivery, one per epic, Moonshot | Use an epic that passed its gate | Its gate recorded; its stop rule not triggered | That the plan depended on it |

**Checks.**

1. *"Can" against cells.* Every capability in a release manifest for milestone N must appear in the `user_can`
   list of some row with milestone ≤ N (cumulative); a cell for a capability the rubric does not offer at that
   milestone is refused. A capability in the rubric that the manifest omits is listed as "not in this release"
   with the reason (not built, partial, withdrawn).
2. *"Must be true".* Each entry is a gate (read from the gate register: status `pass` with value and control, or
   the recorded fallback) or a named record check: "every admission has its record" (the admission validator),
   "disclosure blocks present" (the performance-figure scan of the release checker), "North-Star scenario
   demonstrated by a fresh agent" (the demo index, with the session identity rule), "kill decisions recorded"
   (every kill gate due at the milestone has an ADR), "a determinism class on every result" (envelope scan of the
   release bundle), "every rung's label printed" (report scan), "pins recorded" (the stack lock's freeze record),
   "every certificate replayed" (auditor receipts for each cited bundle), "the adjudication status stated".
   M2's conditional entry is read from the open-question register: if OPEN-SPARK-1 is not ratified, every device
   result in the bundle must carry the exploratory label.
3. *"Must not be said".* Each entry compiles to patterns for the wording lint, scoped to the release bundle
   (README, release notes, reports, demo descriptions, verb help text): for M0, any performance or accuracy
   statement about this product; for M1, GPU, throughput, "qualified", scene realism; for M2, comparative
   advantage and unqualified bit equality; for M3, "ten-fold" unless the tournament or partial-gate record
   permits it for the named stratum, and realism while any norm field is `assumed`; for M4, safety claims above
   `Tested` and rankings from a rung with no record; for M5, "sim-to-real certified", "released for
   fabrication", "physically validated" outside a named calibrated cell; for M6, frontier profiles as part of the
   thesis; for M7, "independently accepted" without a neutral party, and ten-fold outside confirmed strata; for
   M8, dependence of the plan on a Moonshot. Each pattern carries its lifting condition, evaluated from records,
   so the lint permits the statement exactly when the evidence exists. Earlier rows' prohibitions stay in force
   until their own lifting condition holds.
4. *Withdrawal.* When a kill gate fires for a capability that an earlier release offered, the next release's
   generated table lists the capability as `withdrawn` with the ADR; omitting it, or listing it as offered, is
   refused.

**Command.** The crate `frob-conformance` has no binary of its own name (BD-025, ADR-GAUNT-01), and the rubric
is checked as the last stage of N41-27's example target, which this bead extends in its own change (the stage's
code in `src/release/rubric.rs`): `cargo run -p frob-conformance --example release_check -- <manifest> --root
<tree> --json` runs the visibility guard, the nine rules and then the four rubric checks below, and prints one
JSON object with the verdict and every refusal. No second target exists.

**Refusals.** The rubric check exits 3 and prints `reason=<id>` on its first line (harness reasons of N41-REF):
`rubric-not-offered` (check 1), `rubric-unmet` (check 2, naming the entry and the gate or record read),
`rubric-forbidden-statement` (check 3, naming the phrase, the file and line, the row whose prohibition applies and
its lifting condition), `rubric-withdrawal-omitted` (check 4). The same lint pass that applies the "must not be
said" patterns also receives the dispositions of N41-29's check (the manifest field `disposition` of that bead, a
dependency), so a release note that rewords a `tied`, `infeasible`, `incomparable` or `inconclusive` study is
refused in that pass (reason `release-disposition`, owned by N41-29).

**Generated view.** `docs/delivery/releases.md` is generated from the rubric and the manifests: per milestone, the
four columns with the state of each "must be true" entry and the active prohibitions. It is the only document
that prints the three sentences, and `registries/rubric.toml` is their only source (DESIGN: the status-views
bead N38b-20 first copied them into `docs/release/STATUS.md` from the milestone registry, which has no such
fields; that copy is removed there). The state of a "must be true" entry that is a gate is not computed a second
time: it is the status the generator `register::print::rubric` of N38b-20 prints for that gate, and the document
links to `docs/release/STATUS.md` for the full gate section. The document is registered in the register of
generated views that N38b-20 creates (`crates/frob-conformance/registry/generated.toml`: output
`docs/delivery/releases.md`; inputs `registries/rubric.toml`, the release manifests and `registries/gates.toml`;
generator `release::rubric::print`), so `xtask check-generated` covers it like every other view.

## Acceptance criteria

- [ ] The registry holds the nine rows above; each `must_be_true` entry resolves to a gate or a named record
      check; each `must_not_say` entry has at least one pattern and a lifting condition.
- [ ] A manifest cell for a capability the rubric does not offer at its milestone is refused; an M2 manifest may
      include M1's capabilities.
- [ ] An M1 release note containing a throughput figure, or the word "qualified", is refused; the same note is
      accepted at the milestone where the lifting condition holds.
- [ ] "Ten-fold" in an M3 bundle is refused unless the decision-rule record permits it for the named stratum.
- [ ] A device result without the exploratory label in an M2 bundle is refused while OPEN-SPARK-1 is not
      ratified.
- [ ] A capability withdrawn by a fired kill gate appears as `withdrawn` with its ADR in the next release's
      table; a table that omits it is refused.
- [ ] `docs/delivery/releases.md` regenerates byte-identically, is listed in the register of generated views, and
      a hand edit of it fails `xtask check-generated`.
- [ ] The three sentences of every row appear in `registries/rubric.toml` and in no other registry; the gate
      statuses shown in the document equal those of `docs/release/STATUS.md` for the same commit.
- [ ] `cargo run -p frob-conformance --example release_check -- <manifest> --root <tree> --json` runs the rubric
      stage after the nine rules; `scripts/e2e/release_rubric.sh` passes, and fails under its plant
      `rubric-not-cumulative`.

### End-to-end script and logging
`scripts/e2e/release_rubric.sh` (this bead; header `bead=N41-28 milestone=M1 labels=delivery,gauntlet
plants=rubric-not-cumulative`) sources the shared helper of STD-E2E and runs the check as a user meets it, on the
scratch bundles of the unit tests (labelled `synthetic`; no registry of record is changed and no gate is claimed).
Steps: (1) the command above on a clean M1-shaped scratch bundle: exit 0 and `release-ok`; (2) the same command on
each planted bundle, one forbidden statement per milestone row (M0 to M8), a cell outside the rubric, an unmet
`must_be_true` entry, a withdrawn capability omitted from the next table, and a `tied` study reworded as a win:
exit 3, the first line `reason=rubric-forbidden-statement`, `rubric-not-offered`, `rubric-unmet`,
`rubric-withdrawal-omitted` or `release-disposition`, with the phrase, file and line or the entry named; (3) the
same M1 prohibition in an M2 bundle, once with its lifting record present (accepted) and once without (refused:
the cumulative rule); (4) `docs/delivery/releases.md` regenerated twice (equal bytes) and then hand-edited
(`cargo xtask check-generated --json` fails, naming it). With the plant `rubric-not-cumulative` (a check built to
read only the row of the release's own milestone) the M2 bundle without its lifting record is accepted and the
script must fail. It writes `target/e2e-logs/release_rubric/<utc>.ndjson` and a transcript; every line has `ts`,
`script`, `bead`, `step` and `event`; `cmd` lines carry the exact command line, exit code and wall time; one
`assert` per planted bundle gives the expected and observed reason and exit code; `refusal` lines carry the
reason, the row and its lifting condition; on failure the log names the first bundle that was not refused and the
scratch path; a final `summary` counts assertions passed and failed. The whole bundle built from the
repository's own registries is checked again by `scripts/e2e/release_check.sh` (N41-30), which runs the rubric
beside the nine rules and the evidence-kind check.

### Known answers and negative controls
Known answers (K41-36, K41-40): the nine rows; the two spanning rules. Negative controls: one planted forbidden
statement per milestone row, among them X41-37 (a figure for this product's speed in the M0 record) and X41-45 (a
throughput figure or "qualified" in an M1 note; "ten-fold" in an M3 bundle with no permitting record); a cell
outside the rubric; X41-44 (a withdrawn capability omitted from the next table); X41-05 (a `tied` study reworded as
a win in a release note); an M2 bundle that repeats an M1 prohibition whose lifting record does not yet exist (the
cumulative rule must refuse it). Determinism: exact.

## Considerations

- Patterns catch the plain forms of an overstatement. The fresh-context reviewer reads the release note too; the
  lint's job is that the obvious forms never ship.
- The lifting conditions tie words to records; a statement becomes sayable when, and only when, its evidence is
  recorded.
- M6 and M8 releases are per epic and behind feature flags; they never change what the M5 and M7 releases say.
- If a milestone exits in a variant (M2 without GPU, M4 without a family policy) the rubric row is filtered by the
  variant's record: capabilities the variant lacks are "not in this release", with the reason.
