## Background

Two rules were added to the release rules late, after an audit of how evidence gets overstated without anyone
lying. They add to the rubric and change none of its rows.

**Evidence is procured in dependency order.** Every release cell names the kind of evidence it rests on, and a
cell is never scheduled ahead of the kind it needs. There are four kinds, in order:

| Kind | What it is | Available |
|---|---|---|
| Authorable at once | Analytic fixtures, exact checkers, certificates, CPU runs on the referee and on `batch-cpu` | From M0 |
| Pinned external comparison | An incumbent re-measured on the same hardware under the performance disclosure block | From the M0 phase ledger |
| Operator or dataset | Bench logs, scans of real places, proficiency-matched operator trials | When the import lane has an admitted dataset |
| Native device | A completed run on the device family that the cell names, with a placement receipt that shows no fallback | When that device ran it |

A successful CPU run on the large-memory Mac, or in a shell session on the training machine, establishes the CPU
path and nothing about a device path. A cell that names CUDA or Metal therefore needs a receipt whose actual
backend equals the requested one for every stage it claims. Counterexample: a step plan in which one stage fell
back to the host produces correct results and a receipt; a release cell that cites it for device throughput
describes a path that did not run.

**Tied, infeasible, incomparable and inconclusive are complete dispositions.** A study that ends in one of them
has delivered its result. The release prints it under that name, with the evidence that produced it, and no
release note rewords it as a win, a loss or work in progress. Reason: a rubric that counts only decisive outcomes
pays for overstated ones.

The check that enforces the first rule is part of the workspace's contract check: `xtask check-contracts` reads
the release manifest and, for each cell, verifies the kind of evidence it declares, the class of each cited
receipt and, for a device cell, the equality of requested and actual backend on every stage. Owner: `xtask`, with
the manifest schema in `frob-core`. It is an extension of an existing check, so the tool keeps its six checks.

## Scope

In: the evidence fields of the release manifest schema in `frob-core`; the extension of `check-contracts`; the

## Technical approach

**Schema** (`frob-core`, `frob.release/1`; the fields added to each `[[cell]]`):

```toml
evidence_kind = "authorable" | "external-comparison" | "operator-or-dataset" | "native-device"
device        = "cuda" | "metal"            # required when evidence_kind = "native-device"
stages        = ["kinematics", "solve", …]  # the stages the cell claims on the device
receipts      = ["<receipt id>", …]         # placement, admission, comparison or dataset receipts
study         = "<study id>"                # when the cell rests on a study
disposition   = "settled" | "tied" | "infeasible" | "incomparable" | "inconclusive"   # copied from the study
listed_as     = "capability" | "result"     # how the release presents the cell
```

**Checks added to `check-contracts`** (each failure prints: release cell lacks evidence of the kind it declares,
with the cell, the declared kind and what was found; exit status non-zero).

1. *Kind present and consistent.* Every cell declares one kind. A cell whose text or `gates` name a device family,
   device throughput or a device determinism class must declare `native-device`; a cell that states a ratio or
   comparison against an incumbent must declare `external-comparison`; a cell that states a Reality band must
   declare `operator-or-dataset`.
2. *Receipt class.* Each cited receipt's class must match the kind: `authorable` needs a gate record or auditor
   receipt at a CPU site; `external-comparison` needs an incumbent ledger row marked **re-measured** on the same
   hardware with its disclosure block (a row marked published-context does not satisfy it);
   `operator-or-dataset` needs an admitted dataset's manifest; `native-device` needs placement receipts.
3. *No fallback on any claimed stage.* For a `native-device` cell: for every stage in `stages`, every cited
   placement receipt shows actual backend equal to requested backend equal to `device`, and no fallback flag. A
   receipt from a CPU tier, however successful, does not satisfy a device cell.
4. *Dependency order.* A cell's milestone must not precede the availability of its kind: `external-comparison`
   requires the phase ledger row to exist at or before the release commit; `operator-or-dataset` requires an
   admitted dataset; `native-device` requires the receipts' dates to precede the release. A manifest that
   schedules a cell ahead of its evidence is refused at planning time as well as at release time.
5. *Complete dispositions.* A cell with a `study` copies the study's recorded verdict into `disposition`; a
   mismatch is refused. A cell whose disposition is `tied`, `infeasible`, `incomparable` or `inconclusive` must
   have `listed_as = "result"` and its name must contain the disposition word; listing it as a capability is
   refused. The wording lint is given the cell's disposition and refuses release text that describes it as a win,
   a loss, "in progress" or "preliminary success".

**Gate GATE-WS-08** (known answer; M1, and at every release). A release manifest with four planted cells is
rejected on each:

1. a device cell backed only by a CPU receipt;
2. a device cell whose receipt records a fallback on one stage;
3. a comparison cell whose incumbent figure is published and not re-measured;
4. a cell whose study ended `inconclusive` and is listed as a capability.

The gate record holds, for each planted cell, the refusal produced and the check that produced it; the positive
control is the same manifest with the four cells corrected (a device receipt with no fallback; a re-measured
ledger row; the inconclusive study listed as a result under its own name), which must pass. At each later release
the four plants are re-run against the then-current schema.

Determinism: the check is exact (class D0). Evidence class of the gate record: `Tested`.

## Acceptance criteria

- [ ] The four planted cells are each rejected with the stated message naming the cell; the corrected manifest
      passes (GATE-WS-08, recorded with commit and the four refusals).
- [ ] A device cell with a receipt in which seven of eight claimed stages ran on the device and one fell back is
      rejected, naming the stage.
- [ ] A cell that states a device throughput and declares `authorable` is rejected by the consistency rule.
- [ ] A cell scheduled at a milestone before its evidence kind is available is rejected.
- [ ] A cell whose `disposition` differs from its study's recorded verdict is rejected; a `tied` study listed as a
      result under the name "tied" passes.
- [ ] `xtask` still has exactly six subcommands (the existing count test passes).
- [ ] The check runs inside the 60-second budget of the workspace checks.

## Considerations

- The fallback counterexample is the important one: a run that fell back is correct, has a receipt and looks like
  success. Only the per-stage equality of requested and actual backend distinguishes it.
- Published figures remain useful context and are printed as such; they never stand in for a comparison.
- A release with many `inconclusive` cells is an honest release; the rule exists so that honesty is not punished
  by a rubric that only counts wins.
- Placement receipts arrive at M2; at M1 the gate runs on synthetic receipts that conform to the schema, and its
  record says so. The re-run at the M2 release uses real ones.
