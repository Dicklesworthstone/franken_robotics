## Background

The definition of done, the nine release rules, the rubric by milestone and the evidence-order check are each
tested in their own crates on small fixtures. A release, though, is a bundle that a person outside the swarm
receives: a manifest, a README with a status table, reports, demos, an exit record. Whether the checks protect
that bundle can only be shown by building one and attacking it. This bead is the end-to-end script for the
release pipeline, run from the user's side with the real `frob` binary and the real workspace checks. It is also
where gate GATE-WS-08 is measured: its gate stage produces the receipt from which the gate's value is recorded.

## Scope

In: the script with its two stages, its scratch release tree, the planted variants, the assertions, the
structured log, the tier entry of GATE-WS-08 and its receipt. Out: the checkers (N41-26 to N41-29); the gate
recorder and the recording itself (N38b-19: a session that implemented none of the checkers runs it on the
receipt); demos, their executor and the capability registry (N00-29, N34-12, N00-02); the reality line on the
envelopes (BD-139); the visibility guard (N41-05, reached through N41-27); the exit runner (N40-05).

## Technical approach

Path: `scripts/e2e/release_check.sh`; plain shell; sources the shared helper; idempotent; seed-explicit (planted
variants are chosen by `--seed`, default 1, and all are run by default).

**Two stages, two runs (DESIGN).** The bundle stage (the default) builds a release tree and attacks it, which
needs changed copies of registries; the gate stage (`--gate`) measures GATE-WS-08. They cannot be one run: a run
that works on scratch registries is marked `registries: override` and `gates_claimable: false` by the helper, and
its log can claim no gate (the log linter's rule `scratch-registries`). The gate stage therefore touches no
registry and no scratch tree.

Scratch tree of the bundle stage: the run's scratch root `target/e2e-scratch/release_check/<run_id>/`, with the
copy of `registries/` made by the helper `e2e_registries_scratch` (the one way a script changes a registry) and,
beside it, a generated `releases/M1/release.toml`, a README, the bundle's reports, the demos, an exit record from
the exit runner run on that root, and a scratch remote configuration with a `LICENSE` file that agree with the
OPEN-PROG-1 decision in force (the scratch configuration of N41-05's guard tests, so that the visibility guard
answers without network). The checkers are pointed at the tree with `--root`.

**Build the bundle (the positive path).**

1. `frob capabilities --json`: capability statuses at this commit.
2. Generate the M1-shaped manifest: one cell per capability that the rubric offers at M1 and whose computed status
   is implemented, partial or fallback; each with its qualifying fixture, gates, demo and evidence kind
   (`authorable` for everything at M1).
3. Produce the bundle's reports with real runs: the commands of the bundle's demo files, run through the demo
   executor of N00-29 (`e2e_demo_run <demo directory>`, which runs every command of a `demo.yaml` through the real
   `frob` binary with `--json`; at M1, for example, `frob design check demos/ns-01/inputs/quad-a.fbot --json`), and
   keep the envelopes. At M1 the report surfaces are the `--json` envelopes, whose `evidence.reality` member is
   the reality line, and their human renderings (BD-139). The `report.*` verbs first exist at M3; from that
   milestone the step also keeps `frob report run <run> --json` for one run of the bundle. The script itself
   calls no verb of kind `run` outside a demo file, so it adds no idempotency key of its own.
4. Regenerate the README status table from the gate registry.
5. Add one losing result from the registry of results that went against a prediction (at M1 at least a
   falsified pilot or a failed planted expectation exists; if none is recorded the script fails here, which is
   rule 5 working).
6. Run the checkers in order: `cargo run -p xtask -- check-contracts --root <tree> --json` (evidence kinds);
   `cargo run -p frob-conformance --example release_check -- <tree>/releases/M1/release.toml --root <tree> --json`
   (the visibility guard, the nine rules and the rubric; the example target of N41-27); `cargo run -p
   frob-conformance --example done_check -- --milestone M1 --root <tree> --json` (the done report, expected mostly
   `not-yet` at M1; the example target of N41-26). Expect exit 0 from the first and `release-ok` from the second.
   The crate `frob-conformance` has no binary of its own name (BD-025), so no command of this script begins with
   that word.

**Attack the bundle (one variant at a time, each expected to be refused with the named rule).**

| Variant | Planted change | Expected refusal |
|---|---|---|
| R1a to R1h | For one cell, remove each of the eight conditions in turn in a scratch capability registry, in order: (1) code absent from the mapped crate; (2) no `CONTRACT.md`, or one missing a section; (3) a known-answer test whose oracle was regenerated from the candidate; (4) an output that reaches the agent without its claim product (a naked number); (5) no CPU reference path; (6) no documented schema or exit code for `frob --json`; (7) no cancellation test; (8) a gate `pass` with a target in place of a measured value | `release-rule-1`, naming the condition |
| R1r, R1s | A Frontier cell with no pilot record (upper-tier rider); a family-certificate cell whose bundle the offline auditor has not accepted (certificate rider) | `release-rule-1`, naming the rider |
| R2 | A demo whose `frob sim run` command has a horizon that takes more than 60 s on the CPU tier (a demo command must begin with `frob`, so a shell sleep would be refused by the static check before the rule is reached); a demo citing a claim absent from the gate register | `release-rule-2` |
| R3 | The status table edited by hand to hide a failing gate | `release-rule-3` |
| R4 | The static-family cell renamed "mission synthesis" | `release-rule-4` |
| R5 | The losing result removed | `release-rule-5` |
| R6 | A throughput figure in the README with no disclosure block; a ratio against an incumbent with no protocol record and no paired lower bound | `release-rule-6` |
| R7 | An exported artifact with one no-authorization flag true; a README sentence claiming certification | `release-rule-7` |
| R8 | The exit record recorded by an implementing session | `release-rule-8` |
| R9 | A report with its reality line removed | `release-rule-9` |
| V1 to V3 | The visibility guard that the release checker runs before the nine rules (N41-27, with N41-05's guard): the scratch remote made public while the decision in force is the default, private; the scratch `LICENSE` identifier line changed so that it differs from the decision; the scratch remote configuration removed, so that the guard reads `unverified` | `release-visibility` (all three; `unverified` is a warning at an exit and a refusal at a release), the refusal printing the decision in force and the first mismatch |
| Q1 to Q4 | Rubric: a GPU statement in the M1 note; the word "qualified"; a cell for a capability the rubric offers only at M3; a capability withdrawn by a fired kill gate in a scratch register, omitted from the table | `rubric-forbidden-statement` (Q1, Q2); `rubric-not-offered` (Q3); `rubric-withdrawal-omitted` (Q4) |
| W1 to W4 | The four planted cells of GATE-WS-08: a device cell backed only by a CPU receipt; a device cell whose receipt records a fallback on one stage; a comparison cell whose incumbent figure is published and not re-measured; an `inconclusive` study listed as a capability | `check-contracts`: `release-evidence-kind`, "release cell lacks evidence of the kind it declares" (W1 to W3); `release-disposition` (W4) |
| D1 | A scratch gate register in which one clause's gate has status `pass` with no measured value | The done report shows that clause `false` |

Each refusal is matched on the reason identifier printed on the checker's first line (`reason=<id>`, registered in
N41-REF) and on the exit status (3 for the two example targets of `frob-conformance`, 2 for an `xtask` finding),
never on message prose. Variant D1 is not a refusal: the done report is produced with exit 0 and the assertion is
on the clause's state.

**The gate stage (`scripts/e2e/release_check.sh --gate`).** The script writes no row of `registries/gates.toml`
and calls no recorder (one recorder per gate, N38b-19; the log linter's rule `self-recording`). GATE-WS-08 has an
entry, written by this bead, in the conformance crate's tier target named by the gate record's `tier` field. The
passing part of the entry runs `check-contracts` on the corrected manifest of N41-29's fixtures and requires exit
0. The gate's registered controls are the four planted cells, seeded by N38b-05 from N41-CX's rows X41-03, X41-02,
X41-04 and X41-05 (in the order W1 to W4; N41-CX, a dependency, writes those rows and their planted fixtures, and
without them the register holds no control for this gate): the control runner submits each planted manifest to the same check and
counts it `caught` only when it is refused with its registered reason. The stage runs the entry through the
helper, `e2e_tier <tier> GATE-WS-08 --mutations`, which is `FROB_TEST_SEED=<seed> cargo test -p frob-conformance
--features gauntlet-mutations --test <tier> -- GATE-WS-08`; asserts from the receipt that the gate's line is
`pass` and that four of four controls are `caught`; and logs the receipt's hash. A recording session that
implemented none of the checkers then enters the value with `cargo run -p frob-conformance --example record_gate
-- --gate GATE-WS-08 --receipt <hash> --part M1`, and with a fresh part at every release, the gate being
recurring. A miss is a `fail` line in the receipt, recorded the same way with the first plant that was accepted.
At M1 the receipt says that the placement receipts of W1 and W2 are synthetic (N41-29); from M2 they are real
`frob.placement/1` records.

**Logging** (to `target/e2e-logs/release_check/<utc>.ndjson` and a transcript). Every line has `ts`, `script`,
`bead` ("N41-30"), `step`, `event`. `cmd` lines: exact command, exit code, wall time, and for `frob` commands the
envelope's evidence block (claim, class, tier, determinism, identities, seed). `assert` lines: variant, expected
reason identifier, observed reason identifier and exit code. `metric` lines: demo wall times against 60 s; plants
rejected against their expected counts (8 + 2 for rule 1; 3 for the visibility guard; 4 for the planted cells);
counts of done-report states; the digests of the real registries and README before and after the run (they must
be equal). `refusal` lines carry the reason identifier, the checker, the cell and the first ranked repair. On
failure: the first variant that was not refused, and the scratch paths to reproduce. Final `summary`: assertions
passed and failed. The bundle stage's summary says `registries: "override"` and claims no gate; it lists the gates
the demos cite as read. The gate stage's log has the `cmd` line of `e2e_tier` with its `receipt` field, one
`assert` per control (`kind: negative-control`, `caught`), a `metric` line "controls caught" against 4, and a
summary that names GATE-WS-08 with the receipt's hash. No private-scene data is used: all fixtures are generated.

## Acceptance criteria

- [ ] On a correct implementation the positive path yields `release-ok` and the script exits 0.
- [ ] Every variant in the table is refused with the expected rule; a variant that passes makes the script fail
      and names it. The three visibility variants are each refused with `release-visibility`.
- [ ] The gate stage's receipt shows GATE-WS-08 `pass` with four of four controls caught and the corrected
      manifest passing, and its hash is in the log; the script contains no call of `record_gate` and no write to
      `registries/gates.toml`, and the gate stage creates no scratch registry.
- [ ] The done report is produced and attached; variant D1 flips exactly one clause.
- [ ] No command of the script begins with `frob-conformance`, and no verb the script calls is later than the
      milestone under test (at M1: `capabilities` and the commands of the M1 demo files).
- [ ] The script is idempotent, stays inside the default machine envelope, and finishes in under five minutes
      (TARGET; demos are bounded at 60 s each).
- [ ] The log passes the shared linter: every `assert` has expected and observed values; the summary lists the
      gates.

## Test plan

### Unit tests
Shell unit tests for the script's helpers under `scripts/e2e/tests/release_check_helpers.sh`:
`scratch_tree_is_isolated` (digests of the real registries and README unchanged after a run);
`variant_table_is_complete` (every rule number 1 to 9, the visibility guard and every gate plant W1 to W4 has at
least one variant); `manifest_generator_is_deterministic`; `gate_stage_claims_from_registries_of_record` (the log
of `--gate` says `registries: "of-record"` and names a receipt; the log of the bundle stage says `"override"` and
names no gate); `no_self_recording` (a source scan of the script finds no `record_gate` and no write to
`registries/gates.toml`). The tier entry has its own test in the conformance crate,
`ws08_entry_passes_and_controls_caught` (the corrected manifest passes; each of the four planted manifests is
refused with its reason; with N41-29's any-stage mutant the control of W2 is `missed` and the gate's line is
`fail`).

### End-to-end script and logging
This bead is the script. Both stages run on every change to the release checkers, the rubric, the capability
registry or the manifest schema, and as a step of every milestone's exit review from M1 on (with the milestone's
own rubric row and, from M2, real placement receipts for W1 and W2); the gate stage's receipt is what the review's
recording session cites.

### Known answers and negative controls
Known answers (K41-34 to K41-39): nine rules, eight conditions, two riders, four gate plants; `release-ok` on the
clean bundle. Negative controls: every variant of the table (it applies X41-02 to X41-05, X41-40 to X41-45 and
X41-47 on the whole bundle); the gate's four registered controls in the gate stage; three mutant checkers
selected by the helper's plant switch `E2E_PLANT_FAILURE` (one that trusts the manifest's `status` field instead
of recomputing; one that accepts any receipt for a device cell; one that skips the wording lint), each of which
must make the script fail.
Determinism: the script's verdicts are exact; only wall times vary.

## Considerations

- At M1 several rubric capabilities will be partial; the bundle is still a valid test object, because rule 1
  accepts partial cells with their missing conditions named.
- The scratch bundle is never published and its records are labelled `synthetic` where planted.
- As milestones add capabilities, the variant table grows by rubric rows only; the nine rules and the gate plants
  are stable.
