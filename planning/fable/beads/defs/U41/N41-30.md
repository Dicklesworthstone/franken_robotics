## Background

The definition of done, the nine release rules, the rubric by milestone and the evidence-order check are each
tested in their own crates on small fixtures. A release, though, is a bundle that a person outside the swarm
receives: a manifest, a README with a status table, reports, demos, an exit record. Whether the checks protect
that bundle can only be shown by building one and attacking it. This bead is the end-to-end script for the
release pipeline, run from the user's side with the real `frob` binary and the real workspace checks. It is also
where gate GATE-WS-08 is measured on a whole manifest and recorded.

## Scope

In: the script, its scratch release tree, the planted variants, the assertions, the structured log, the gate
record. Out: the checkers (N41-26 to N41-29); demos and the capability registry; the exit runner.

## Technical approach

Path: `scripts/e2e/release_check.sh`; plain shell; sources the shared helper; idempotent; seed-explicit (planted
variants are chosen by `--seed`, default 1, and all are run by default). Scratch tree:
`target/e2e-scratch/release_check/<utc>/` with a copy of `registries/`, a generated `releases/M1/release.toml`, a
README, two reports produced by real runs, the demos, and an exit record from the exit runner in scratch mode.

**Build the bundle (the positive path).**

1. `frob capabilities --json`: capability statuses at this commit.
2. Generate the M1-shaped manifest: one cell per capability that the rubric offers at M1 and whose computed status
   is implemented, partial or fallback; each with its qualifying fixture, gates, demo and evidence kind
   (`authorable` for everything at M1).
3. Run two real commands that produce reports for the bundle: `frob design check fixtures/quad-a.fbot --json` and
   `frob sim run --tier referee --task fixtures/drop-and-stand.ftask --seed 3 --json`, then `frob report run <run>
   --json`; keep their envelopes.
4. Regenerate the README status table from the gate registry.
5. Add one losing result from the registry of results that went against a prediction (at M1 at least a
   falsified pilot or a failed planted expectation exists; if none is recorded the script fails here, which is
   rule 5 working).
6. Run the checkers in order: `cargo run -p xtask -- check-contracts` (evidence kinds), `frob-conformance release
   check releases/M1/release.toml --json` (nine rules and rubric), `frob-conformance done --json` (the done
   report, expected mostly `not-yet` at M1). Expect `release-ok` from the first two.

**Attack the bundle (one variant at a time, each expected to be refused with the named rule).**

| Variant | Planted change | Expected refusal |
|---|---|---|
| R1a to R1h | For one cell, remove each of the eight conditions in turn in a scratch capability registry (no contract; a known answer with tolerance unset; no envelope test; no CPU reference; no schema; no cancel test; a gate `pass` with a target in place of a measured value; code absent) | Rule 1, naming the condition |
| R1r | A Frontier cell with no pilot record | Rule 1, upper-tier rider |
| R2 | A demo padded with a 61-second sleep; a demo citing a claim absent from the gate register | Rule 2 |
| R3 | The status table edited by hand to hide a failing gate | Rule 3 |
| R4 | The static-family cell renamed "mission synthesis" | Rule 4 |
| R5 | The losing result removed | Rule 5 |
| R6 | A throughput figure in the README with no disclosure block | Rule 6 |
| R7 | An exported artifact with one no-authorization flag true; a README sentence claiming certification | Rule 7 |
| R8 | The exit record recorded by an implementing session | Rule 8 |
| R9 | A report with its reality line removed | Rule 9 |
| Q1 to Q3 | Rubric: a GPU statement in the M1 note; the word "qualified"; a cell for a capability the rubric offers only at M3 | Rubric refusals |
| W1 to W4 | The four planted cells of GATE-WS-08: a device cell backed only by a CPU receipt; a device cell whose receipt records a fallback on one stage; a comparison cell whose incumbent figure is published and not re-measured; an `inconclusive` study listed as a capability | `check-contracts`: release cell lacks evidence of the kind it declares (W1 to W3); disposition refusal (W4) |
| D1 | A scratch gate register in which one clause's gate has status `pass` with no measured value | The done report shows that clause `false` |

**Gate record.** After W1 to W4 are each rejected and the corrected manifest passes, the script writes the
GATE-WS-08 measurement (four of four plants rejected; positive control passed) through the gate-recording command,
with commit and seed; on any miss it records the failure with the first plant that was accepted.

**Logging** (to `target/e2e-logs/release_check/<utc>.ndjson` and a transcript). Every line has `ts`, `script`,
`bead` ("N41-30"), `step`, `event`. `cmd` lines: exact command, exit code, wall time, and for `frob` commands the
envelope's evidence block (claim, class, tier, determinism, identities, seed). `assert` lines: variant, expected
rule, observed refusal text and exit code. `metric` lines: demo wall times against 60 s; plants rejected against
their expected counts (8 + 1 for rule 1; 4 for the gate); counts of done-report states. `refusal` lines carry the
checker's message. On failure: the first variant that was not refused, and the scratch paths to reproduce. Final
`summary`: assertions passed and failed; gates touched: GATE-WS-08 (measured), and the gates the demos cite
(read). No private-scene data is used: all fixtures are generated.

## Acceptance criteria

- [ ] On a correct implementation the positive path yields `release-ok` and the script exits 0.
- [ ] Every variant in the table is refused with the expected rule; a variant that passes makes the script fail
      and names it.
- [ ] GATE-WS-08 is recorded with four of four plants rejected and the positive control passing.
- [ ] The done report is produced and attached; variant D1 flips exactly one clause.
- [ ] The script is idempotent, stays inside the default machine envelope, and finishes in under five minutes
      (TARGET; demos are bounded at 60 s each).
- [ ] The log passes the shared linter: every `assert` has expected and observed values; the summary lists the
      gates.

## Test plan

### Unit tests
Shell unit tests for the script's helpers under `scripts/e2e/tests/release_check_helpers.sh`:
`scratch_tree_is_isolated` (digests of the real registries and README unchanged after a run);
`variant_table_is_complete` (every rule number 1 to 9 and every gate plant W1 to W4 has at least one variant);
`manifest_generator_is_deterministic`.

### End-to-end script and logging
This bead is the script. It runs on every change to the release checkers, the rubric, the capability registry or
the manifest schema, and as a step of every milestone's exit review from M1 on (with the milestone's own rubric
row and, from M2, real placement receipts for W1 and W2).

### Known answers and negative controls
Known answers: nine rules, eight conditions, four gate plants; `release-ok` on the clean bundle. Negative
controls: every variant of the table; three mutant checkers selected by an environment switch (one that trusts
the manifest's `status` field instead of recomputing; one that accepts any receipt for a device cell; one that
skips the wording lint), each of which must make the script fail.
Determinism: the script's verdicts are exact; only wall times vary.

## Considerations

- At M1 several rubric capabilities will be partial; the bundle is still a valid test object, because rule 1
  accepts partial cells with their missing conditions named.
- The scratch bundle is never published and its records are labelled `synthetic` where planted.
- As milestones add capabilities, the variant table grows by rubric rows only; the nine rules and the gate plants
  are stable.
