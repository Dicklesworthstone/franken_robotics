## Background

A design (`frob.design/1`, `.fbot`) is a term whose leaves are components and whose inner nodes are constructors.
A **module** (`frob.module/1`, `.fmodule`, BD-060) is a design subterm with open ports, parameters and a contract,
stored on its own and referenced by content hash (`"std/leg-3r-qdd.fmodule@b3:9a4e…"`); a design imports it with
`use` (`module`, `at`, `bind`, `rename`). The format registry's row for the module format says a module is
"authored, or extracted from a design by a typed edit", and the worked module of the specification is the leg of
the worked design `quad-tray` "extracted by a typed edit". The module-format bead BD-060 places that edit with the
edit engine (BD-058), and BD-058's catalogue of 22 rows (32 kinds) has no kind for it. Nothing else carried it; this
bead does.

Why an edit and not a separate tool: extraction changes the design term (the subterm is replaced by a `use`), so it
must go through the same engine as every other change: a lock check, a lineage record, a returned inverse, a
declared symmetry effect and a predicted invalidation scope. It does not change the robot: the elaborated tree, every
compile product and the `ModelId` are the same before and after. That is the edit's postcondition, checked on every
call, because an extraction that changes the robot is a silent edit under a refactoring's name.

DESIGN: the edit is row 23 of the typed-edit catalogue, added to the 22 rows of the specification's table, because
its effect differs from every existing row (symmetry `none`, scope `none`); grouping it with `swap-module` (row 13,
symmetry `reported`, scope leaf-local or global) would predict invalidations that never happen. Rejected: a
`module.extract` verb outside the edit engine (a second path that writes designs, with its own locks and history).

Terms. *Limb subterm*: an `attach` node (`{"attach": "<body>.<port>", …}`) and everything under it, possibly under
`mirror`, `radial` or `serial` constructors. *Referrer*: a field outside the subterm that names a node inside it (a
lever or lock path, a closure port, a payload mount, a sensor parent written as an instance identifier). *Port
signature*: the module's ports with kind, frame and power sign (C-12; the component port kinds are N14a-02's).

## Scope

In: the edit kind `extract-module` and its inverse form `inline: true` in the engine of BD-058; derivation of the
port signature; parameters and the re-pointing of levers; the contract's mass guarantee; writing, hashing, checking
(BD-060's `check_module`) and storing the module; the postcondition `ModelId` unchanged; catalogue row 23 with its
fixture; the kind added to the test generator's edit vocabulary (N14b-01's `sample_edit`, precondition: an
`attach` subterm whose outside referrers are all lever paths, parameters declared for each); the end-to-end
script.

Out: the module format, `use` elaboration and `check_module` (BD-060); port junctions (N15b-01); the module verbs
(N15b-02); substitution of a module by another (BD-077, `swap-module`); the conformance test of every catalogue row
against computed groups and invalidation sets (N14a-17, which depends on this bead and tests row 23 with the
others); the worked module fixture and its comparison with `quad-tray` (ART-L2).

## Technical approach

Layout (DESIGN): `crates/frob-design/src/edit/extract.rs`; the row in `registries/edits.toml`.

**Arguments** (`op.args` of `frob.design.edit.in/1`): `path` (the limb subterm), `name` (the module's name),
`ports` (optional: renames of derived ports and added `signal` ports), `params` (optional: `{id, path, unit and
bounds | kind "card:<family>"}`), `contract` (optional: guarantees and assumptions other than mass). A
parameter's `path` is written as the module stores it (BD-060's spelling): a JSON pointer from the root of the
module document, in the grammar of a `.fbot` lever, so every target starts with `/body/` (the specimen's `thigh` is
`/body/chain/1/body/region/capsule/1`, its `knee_card` `/body/chain/2/actuator`). The subterm at the design path
`<path>` becomes the module's `/body`, so the parameter path `/body/<rest>` names the design path
`<path>/<rest>`; that correspondence is what step 2 compares lever paths against. CLI: `frob design edit <design> extract-module <path>
--name <module-name> [--args @extract.json] [--expected-parent <id>] --key <k> --json`.

**Steps.**

1. Resolve `path`: it must name an `attach` node; otherwise `FROB-REF-103`, with the nearest enclosing `attach`
   path as the first repair. The module's mount is the attach port (`torso.hip_mount` gives a `mech` port with
   frame `hip_mount`).
2. Referrers. Collect every reference from outside the subterm into it. A `closure` with one port inside and one
   outside refuses (`FROB-REF-103`, the closure path listed: a module is a leaf of the tree, the second of the four
   conditions of a leaf-local substitution). A lever whose design path `<path>/<rest>` lies inside must
   correspond to a declared parameter whose path is `/body/<rest>`: it is then re-pointed to the binding (`<use path>/bind/<param id>`) and the `use` writes that
   binding explicitly with the current value, so the lever path resolves. Any other referrer refuses
   (`FROB-REF-103`), listing every referrer with two repairs: declare a parameter for each lever path; remove the
   reference. Sensor parents written as patterns (`joints:*`, `feet:*`) and identifiers stay valid because step 7
   keeps every instance identifier.
3. Locks: the write set (the subterm path and every re-pointed lever path) goes through BD-058's lock check
   (`FROB-REF-111`).
4. Port signature, derived from the subterm with N14a-02's component port kinds, all with power `into-module`:
   `mount` (`mech`, the attach port's frame); `bus` (`elec`, `nominal` the bus's nominal voltage) and `sink`
   (`thermal`) when the subterm holds an actuator that is a member of the bus; one `contact` entry per end effector
   with its law (ids `contact-0 …` in instance order). The caller's `ports` may rename a derived port and may add
   `signal` ports (`msg`, a rational `rate` in hertz, `latency_max`). A declared port that contradicts the derived
   signature (another kind, frame or power sign, or a power port the subterm does not have) refuses with
   `FROB-REF-114`; a power sign other than `into-module` refuses with `FROB-REF-108`; a contact entry whose law is
   not its end effector's refuses with `FROB-REF-121`.
5. Parameters: each path starts with `/body/` and resolves inside the subterm (`FROB-REF-103` otherwise, at
   `params[i].path`); its default is the subterm's current
   value at the path, so the elaborated tree is unchanged; a current value outside the declared bounds refuses
   (`FROB-REF-111`); a card parameter must name a card of its family.
6. Contract: `guarantees.mass` is the exact interval [min, max] of the body's mass roll-up over the default and every
   corner of the parameter box (the computation `check_module` repeats); `port_inertia` is `sym-psd-6`; the
   caller's other guarantees and assumptions are copied and verified by `check_module` where a checker exists. A
   field that the module schema requires and the caller did not supply refuses (`FROB-REF-103`, naming it); a
   `bus_demand` without a time-resolved profile is admission-only, as BD-060 types it.
7. Write the module canonically (BD-060's writer), compute its reference hash and contract digest, run
   `check_module`. Replace the subterm by the `use` term (BD-060's spelling: `module` the reference, `at` the attach
   port, `bind`, and the `rename` map that keeps every instance identifier equal to the parent's).
8. Postcondition: compile parent and child (N14a-21's compile path). The `ModelId`, every compile product digest
   and the instance-identifier map must be equal. Otherwise refuse with `FROB-REF-114` (DESIGN: the imported
   module would not reproduce the subterm it replaces), naming the first differing product; nothing is stored.
9. Commit in one transaction: the module file into the caller's namespace module store (content-addressed under
   `<namespace>/modules/<name>.fmodule`, resolvable by `module.show` and `module.check` through its reference); the
   new design version, its edit record and the head move through BD-058's design store.

**Inverse** `extract-module {inline: true}` at the `use` path: splice the recorded original subterm back and
re-point the levers to their original paths; the result's `DesignId` equals the parent's. The module file stays in
the store (content-addressed objects are never deleted by an edit).

**Catalogue row 23** (entered in `registries/edits.toml` together with the kind, so that the engine's kind set and
the catalogue's stay equal: 23 rows, 33 kinds): `row = 23`, `kinds = ["extract-module"]`, example "Leg subterm of
`quad-tray` → module `leg-3r-qdd`", `symmetry_effect = "none"`, `scope = ["none"]`, and its `fixture`: the leg of
`quad-a` (`/limbs/of/of`) with parameters `thigh`, `knee_ratio`, `knee_card` (the paths of `quad-a`'s three levers).

**Output** (the edit envelope of BD-058) adds `result.module` (`ref`, `contract_digest`, the derived port signature)
and `result.model_id_unchanged: true`. Evidence: class `Tested`, determinism D0.

## Acceptance criteria

- [ ] On `quad-a`, extracting `/limbs/of/of` with parameters `thigh`, `knee_ratio`, `knee_card` gives a design whose
      `ModelId`, compile product digests and instance identifiers equal the parent's; the three levers point at
      `/limbs/of/of/bind/<id>`; the module passes `check_module`; its mass guarantee equals the exact [min, max] of
      the roll-up over the corners of the parameter box (thigh 0.15 m and 0.30 m, each knee card; the belt ratio
      changes no mass).
- [ ] The inverse returns the parent's `DesignId`, byte for byte.
- [ ] The derived signature of the leg is `mount` (`mech`, `hip_mount`), `bus` (`elec`, 22.2 V), `sink`
      (`thermal`) and one `contact` entry with law `foot-patch`; a caller's `ports` renaming `contact-0` to `sole`
      and adding `state` (`signal`, `joint-state/3`, 1000 Hz, 1 ms) is accepted.
- [ ] Each refusal is produced by its planted call with its code and exit 3: an unmapped lever (103, the lever
      listed); a crossing closure (103); a non-`attach` target (103); a declared port of the wrong kind (114); an
      out-of-module power sign (108); a contact law that is not the foot's (121); a locked path (111); a
      parameter bound that excludes the current value (111).
- [ ] The kind and row 23 are in the engine and in `registries/edits.toml` together; N14a-17's
      `catalogue_matches_engine_registry` passes with 33 kinds.
- [ ] `scripts/e2e/design_extract_module.sh` passes and fails under its plant.

## Test plan

### Unit tests

`cargo test -p frob-design --test edit_extract` (real designs and the real compiler; no mocks):
- `extract_quad_a_leg_model_unchanged`; `extract_then_inline_restores_design_id`;
- `extract_levers_repointed`: the three lever paths resolve to the bindings, and `set-lever thigh 0.24 m` on the
  child gives the same `ModelId` as the same lever move on the parent;
- `extract_mass_guarantee_exact`: the stored interval equals the min and max of the roll-up at the four corners
  (thigh 0.15 m or 0.30 m; `qdd-m` or `qdd-l`), as rationals;
- `extract_derived_signature`; `extract_ports_rename_and_signal`;
- `extract_unmapped_lever_refuses_103`; `extract_crossing_closure_refuses_103`; `extract_non_attach_refuses_103`;
  `extract_port_kind_contradiction_114`; `extract_power_sign_108`; `extract_contact_law_121`;
  `extract_locked_path_111`; `extract_param_bounds_111`;
- `extract_postcondition_catches_model_change`: under the planted mutant `use-drops-rename` (elaboration of `use`
  ignores `rename`), the edit refuses with 114 naming the first differing product and stores nothing. The mutant
  is a `cfg(feature = "mutant-use-drops-rename")` branch at BD-060's `use` elaboration in `frob-design`, declared
  by this bead under N38b-04's rule for mutation features (it implies the crate's `conformance` feature, is never
  a default, and the crate's release-profile `compile_error!` guard keeps it out of product builds); the test is
  compiled only with it and runs as `cargo test -p frob-design --features mutant-use-drops-rename --test
  edit_extract`;
- `extract_under_mirrors_compiles_once`: the child's leg product is computed once and served three times, as the
  parent's is.

### End-to-end script and logging

`scripts/e2e/design_extract_module.sh --seed <s>` (sources the STD-E2E helper; seed explicit; idempotent; every
`mutate` call, the inverse of step 6 included, passes `--key "$(e2e_key <label>)"`, STD-E2E's rule, and the steps
below write the label alone, as `--key x-3`):
(1) `frob design new quad-a --file fixtures/edits/quad-a.fbot --key x-1 --json`; (2) `frob design show quad-a
--json`, capture `model_id`; (3) `frob design edit quad-a extract-module /limbs/of/of --name leg-quad-a --args
@fixtures/extract/quad-a-leg.json --key x-3 --json` (the args declare the parameters `thigh`, `knee_ratio`,
`knee_card`, rename `contact-0` to `sole` and add the signal port `state`), assert `model_id_unchanged` and the
derived signature;
(4) `frob design show quad-a --json`: the same `model_id`; (5) `frob module show <ref> --json` and `frob module check
<ref> --json`: exit 0, five ports, three parameters, digest match; (6) the returned inverse: `DesignId` equals d₀;
(7) the eight refusal fixtures of `fixtures/extract/refuse_*.json`: exit 3 and the code of `expect.toml`. Plant
`use-drops-rename` (STD-E2E `E2E_PLANT_FAILURE`): the script runs against a debug `frob` built with `cargo build -p
frob --features frob-design/mutant-use-drops-rename` (a code mutant cannot be injected into a product binary), and
step 3 must refuse with 114, which the script's success assertion reports as a failure. NDJSON to `target/e2e-logs/design_extract_module/<utc>.ndjson` with a transcript: `ts`,
`script`, `bead: "N41p2-01"`, `step`, `event`, the exact command line, exit code, wall time, the envelope's
`evidence` block, `DesignId` and `ModelId` before and after, the module reference and contract digest, the derived
port signature, refusal code and first repair; on failure the first differing product or field with both values
and the fixture paths; a final `summary`.

### Known answers and negative controls

- Known answer: extraction leaves `ModelId` unchanged and its inverse restores `DesignId` (exact).
- Known answer: the leg's derived signature (four entries, above); the mass interval at the four corners.
- Negative controls: the eight refusal fixtures; the `use-drops-rename` mutant; a mutant that skips step 2
  (feature `mutant-extract-skip-referrers` of `frob-design`, declared the same way: an unmapped lever then
  dangles and `extract_unmapped_lever_refuses_103` fails).
- Metamorphic: extracting and then substituting the same module by itself (`swap-module` to the same hash) is
  leaf-local and invalidates nothing; extraction commutes with a `set-param` outside the subterm.
- Determinism lanes: twice; debug and release; Linux and macOS: identical module bytes, hashes and `DesignId`s.

## Considerations

- The worked module of the specification lists parameters (`thigh`, `knee_card`) that are not the levers of
  `quad-tray` (`half_width`, `knee_ratio`, `foot_radius`); two of those levers point into the leg. Extracting the
  leg of `quad-tray` with exactly the specimen's parameters therefore refuses under step 2 unless `knee_ratio` and
  `foot_radius` are declared as parameters too, or the two levers are removed first. The worked fixture's own
  bead (ART-L2) states which it does; this bead does not weaken step 2 to make a specimen fit.
- How a module parameter names its target in the body is open in the module format; BD-060's fail-closed default
  is a JSON pointer from the module document's root, starting with `/body/`, as ART-L2's fixture writes it. This
  bead writes that spelling and maps it to design paths by the correspondence of the Arguments paragraph; if the
  open question is decided otherwise, only that mapping changes.
- KILL-SKEL-SUBST does not touch extraction: its fallback makes substitutions global, and extraction substitutes
  nothing.
- Imported or authored names and module names are untrusted text, echoed only in marked fields.
