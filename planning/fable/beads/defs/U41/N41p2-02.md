## Background

A design in FrankenRobotics is immutable: every change is a **typed edit** that takes one design version to
another, with preconditions, an inverse where one exists, a declared effect on the mechanical symmetry group
Γ_mech and its observation-preserving subgroup Γ_obs, and a predicted scope of invalidation. The edit engine and
its single-edit verb `design.edit` are BD-058 (`frob-design`, layer 2, tier Solid). An agent reaches the verb
through the `frob` command line or through the MCP server `frob-mcp` (tool `design_edit`); both are generated from
one verb registry entry, so they must give the same answer.

BD-058 could not carry its own end-to-end script: the script must first create a named design with `design.new`
(N14a-21), and `design.new` depends on BD-058 through the lever interface (N14a-06, whose handle emits `set-lever`
edits). This bead runs the script BD-058 specified, after both exist, so that the user-visible claims of the edit
verb are checked where an engineer or an agent meets them: an edit through a term path changes every image of a
`mirror` and preserves the symmetry; the same edit on one instance splits the constructor and reports the
symmetry it broke; every edit's returned inverse restores the parent's `DesignId`; retries are safe; a stale
expected parent is refused with the current head.

Terms. *Selector*: `<instance pattern>.<field>` matched against instance identifiers from the right, `*` matching
one segment (`*.knee` matches `leg.fl.knee`). *Split*: rewriting a `mirror`, `radial` or `serial` into explicit
`attach` limbs so that one image can be edited alone; recorded in `symmetry.split`. *Fuse*: the inverse of a
split, refused unless the limbs are exact images again. *Expected parent*: the `DesignId` the caller believes is
the head of the named design.

## Scope

In: the script `scripts/e2e/design_edit.sh`, its NDJSON log and summary, and its plants. Out: the engine, the verb,
the design store and the fixtures (BD-058, which writes `fixtures/edits/`); `design.new` (N14a-21); the catalogue
conformance of every row against computed groups and invalidation sets (N14a-17, whose rows N14a-29 drives through
the CLI); patches (BD-059, N14a-29); the studio loop with `design.check` after edits (N28a-29).

## Technical approach

`scripts/e2e/design_edit.sh --seed <s>` (sources the STD-E2E helper; seed explicit; idempotent: every run uses a
fresh scratch namespace `e2e-design-edit-<seed>-<utc>`). Every call of `design.new` and `design.edit`, each returned
inverse included, passes `--key "$(e2e_key <label>)"` (STD-E2E's rule: keys are written with `e2e_key`, which
gives `e2e-design_edit-<label>` and contains no seed or time); the table writes the label alone (`--key de-2`), an
inverse takes the label of its edit with `-inv` (`de-2-inv`), steps 10 and 11 reissue `de-7` with `e2e_key de-7
--again` (a deliberate replay), and step 12 omits the key on purpose.

| 16 | step 2's edit repeated through `frob-mcp` (stdio, tool `design_edit`) on a fresh name created by step 1's command | the same `design_id` as the CLI answer for the same parent and op |

Plants (STD-E2E `E2E_PLANT_FAILURE`, checked by `run-all.sh --verify-plants`): `inverse-from-child` (BD-058's mutant
that builds an inverse from the child's value) must fail step 3; `split-all-images` (the mutant that applies an
instance edit to all images) must fail step 8; `selector-always-instance` (the selector resolver that sends a match
of every image to `Instance`) must fail step 7's no-split assertion. Each is a code mutant of BD-058's engine, so
under a plant the script runs every step against a debug `frob` built in its scratch target directory with `cargo
build -p frob --features frob-design/mutant-<plant>` (the features `mutant-inverse-from-child`,
`mutant-split-all-images` and `mutant-selector-always-instance`, which BD-058 declares under N38b-04's rule for
mutation features: they imply `conformance`, are never defaults, and a release-profile build with one does not
compile, so no plant reaches the release binary of the unplanted run).

Logging (charter section 6): NDJSON to `target/e2e-logs/design_edit/<utc>.ndjson` with a transcript beside it.
Every line has `ts`, `script`, `bead: "N41p2-02"` (and `under_test: "BD-058"`), `step`, `event` (`start`, `cmd`,
`assert`, `refusal`, `metric`, `end`), the exact command line, exit code, wall time, the envelope's `evidence` block
(claim kind, class, tier, determinism, `bound.design`, seed), the `DesignId` before and after, `resolved_target`,
the declared symmetry effect and `symmetry.split`, the edit's `edit_id`; `refusal` lines with code, pointer,
observed, required and the first repair; on failure the first differing field with both values and the paths of
the fixture and of both answers. A final `summary` line gives assertions passed and failed and the plants
verified.

## Test plan

### Unit tests

The script is the test; the unit tests of the engine are BD-058's. A shell self-test runs steps 1 to 3 against a
binary built with the `inverse-from-child` mutant and checks the non-zero exit.

### End-to-end script and logging

As above: `scripts/e2e/design_edit.sh`, driving `frob design new`, `frob design edit` and `frob-mcp`; logs under
`target/e2e-logs/design_edit/`.

### Known answers and negative controls

- Known answer: edit followed by its returned inverse returns the parent's `DesignId` (exact), for the five edit
  forms of steps 2 to 9, including the two-operation inverse of a split.
- Hand values: `foot.radius` resolves to `/limbs/of/of/chain/3/foot/region/sphere`; a bare `0.030` is
  `"0.03 m"`; the stale two-value form reports 0.021 m expected and 0.030 m current (the value step 5 left).
- Negative controls: the three plants; the six refusal fixtures, each yielding its own code and no other.
- Metamorphic: steps 6 and 7 applied in either order give the same final `DesignId` (disjoint paths commute).
- Determinism lanes: the same seed gives the same sequence of `DesignId`s twice, with debug and release
  binaries, on Linux and macOS.

## Considerations

- Exit 7 is information: steps 11, 13 and 14 assert that the answer carries what a caller needs to retry or
  rebase (both digests; the current head; the current value).
- The MCP step uses stdio, not HTTP, so that it needs no port; the HTTP transport is covered by the surface's
  own smoke test.
- Runtime target: under 20 s on a laptop; no GPU.
