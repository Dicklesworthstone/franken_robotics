## Background

FACT: the machines this program runs on are shared, and the rule that governs them, inherited from the sibling
simulator's agent instructions and adopted here, is that no run on any host uses more than 16 GiB of memory, 8 cores
or one hour of wall time without the owner's written approval given before it starts. Builds and tests count; a run
longer than a few minutes starts under a timeout; when an agent stops, its jobs stop. The fail-closed default of the
open question on the compute envelope (OPEN-SPARK-2) adds the device rule: a GPU job is limited to one device and one
hour. That default is called class E0.

What E0 cannot run, by arithmetic (the plan's known answer on the envelope): one device-hour at 50 to 500 thousand
environment steps per second is 0.18 to 1.8·10⁹ steps. The performance gates themselves need more: one row uses 24
threads, two use two devices, and the world bank holds far more than 16 GiB. The rank-agreement experiment needs about
forty per-design trainings, about 45 device-hours, or 5 to 7.5 where specialists are reused. Pretraining a family
policy at published sizes of 1.6·10⁹ steps is 0.9 to 9 device-hours and at 5·10⁹ steps 2.8 to 28; at 2·10¹² steps it
is 1,100 to 11,000 device-hours, which is 23 to 230 days on two cards and is not planned in any envelope.

The proposal to the owner (OPEN; nothing above E0 runs until it is ratified or amended):

| Class | Scope | Proposed limits (TARGET budgets, not measurements) |
|---|---|---|
| E0 | Default | 16 GiB, 8 cores, 1 hour, one device |
| E1 | A named gate measurement | Both machines, all cores, memory up to the device budget, 2 hours per run, 12 device-hours per gate |
| E2 | A design campaign | 48 device-hours |
| E3 | Pretraining of one family policy | 500 device-hours, approved per run with its ceiling and kill rule written first |

Ten groups of work packages need more than E0, and each names its class and what happens if the class is not
approved. This bead is the decision that puts those ten requests in front of the owner as one list and records the
answer. It exists because of RISK-10 (severity High): no compute envelope is approved, so the performance gates, the
rank-agreement experiment and pretraining cannot run as specified; its signal is the open question still at E0 when
M1 opens; its mitigation is that the classes are proposed at M0, every package above E0 names its budget, and M2 and
M4 have variants that fit E0. Every request has a fallback, so a refusal is a recorded outcome and never a blocked
program.

Alternatives rejected. (1) One blanket approval of everything above E0: the machine rule asks for approval before each
run starts, and the classes exist so that an approval carries a ceiling. (2) Leaving the requests inside the beads that
need them: the owner would never see the total, which is the risk as stated. (3) Raising the default: other agents and
other projects share the machines.

## Scope

In: the register of the ten requests; the record of the owner's ruling per row; the rule that makes a bead above E0
not ready until its row is approved; the rule for adding a row. Out: the definition and ratification of the classes
(the decision on OPEN-SPARK-2); the estimator that computes the class a job needs and refuses a job above the class in
force (BD-219); the daemon's `campaign` size class (BD-296); the script guard that enforces the envelope outside the
daemon (N34-15); the end-to-end test of the refusals and fallbacks (N44-02).

**The record (DESIGN).** One row per request in `registries/envelopes.toml`, the same registry in which the
family-policy decision records its row (N23a-22) and whose approval records the script guard accepts (N34-15):

```
[[request]]
id = "R6"                      # stable; a new request takes the next number
packages = ["WP-60"]
scope = "the rank-agreement pilot; the partial gate's campaigns"
class = "E2"
limits = { device_hours = 48 } # for E1: mem = "device budget", cores = "all", wall_s_per_run = 7200, device_hours = 12
not_approved_fallback = "cheap rungs are `uninformative`; the partial gate runs its CPU strata"
open_question = "OPEN-PROG-4"
status = "requested"           # requested | approved | amended | declined
approved_by = ""               # required when status is approved or amended
date = ""                      # ISO date of the ruling
decision = ""                  # path of the decision note under docs/decisions/
expires = ""                   # the gate or campaign after which the approval lapses
ceiling = ""                   # E3 only: the run's ceiling in device-hours, written before approval
kill_rule = ""                 # E3 only: the rule that stops the run, written before approval
```

Readers, so that the registry is not an orphan: the estimator and the daemon's admission take the class in force for
a job from the approved rows that match its scope and refuse a job above it before it starts (`FROB-REF-761`); the
script guard takes the same rows as approval records; N44-04 checks that the packages named are the fourteen of the
table; exit reviews read the status of each row. If the estimator's bead settles on another carrier for the class in
force, this registry is folded into it and not kept as a second source.

**Procedure.**

1. At M0 write the ten rows with status `requested`, and add the class and fallback to each affected package epic
   (done in the epics of this unit).
2. Present the list to the owner with the class ceilings: E1 at most 2 hours per run and 12 device-hours per gate; E2
   at most 48 device-hours per campaign; E3 at most 500 device-hours per run.
3. The owner rules on each row in writing: approve, amend (a different class or limits) or decline. Silence is
   `requested`, which is treated exactly as declined: the default E0 stays in force.
4. On approval: fill `status`, `approved_by`, `date`, `decision`, `expires`; the beads of the row become ready.
5. On decline or silence: the fallback of the row is in force. The gates the row names are recorded `not run` with
   the reason, never as a pass; beads that exist only under approval close as superseded with the decision's
   identifier, and beads that can stand on the fallback run in their fallback form.
6. A bead that discovers a need above E0 adds a row first, with its class and its not-approved fallback. A row
   without a fallback is not accepted: no request may leave the program blocked on an approval.
7. If the owner amends the classes themselves, every row is re-read against the new limits and the rows whose class
   no longer covers their need return to `requested`.

**Readiness rule (DESIGN).** A bead whose run exceeds the machine envelope (the parity baselines, training, the
head-to-head, the rank-agreement experiment, the partial gate, the tournament) names its row and is not ready until
that row's approval is recorded. A bead for a Frontier or Moonshot mechanism is in addition not ready until its
pilot has a recorded result.

## Acceptance criteria

- [ ] `registries/envelopes.toml` is schema-valid and holds the ten rows above with their packages, class and fallback.
- [ ] The owner's ruling on each row, or the explicit statement that the default stands, is recorded at the M0 exit
      with the reading of RISK-10; at each later exit the rows first needed by the next milestone are re-read.
- [ ] No row has status `approved` or `amended` without `approved_by`, `date` and a decision note; no E3 row is
      approved without `ceiling` and `kill_rule`.
- [ ] Every bead that runs above E0 cites a row, and none was started before its row's approval date.
- [ ] For every declined or pending row, each gate it names has status `not run` with the reason in
      `registries/gates.toml`, and no report cites a figure from a run above E0.
- [ ] The fourteen package epics named in the table state the same class and fallback as the registry (N44-04,
      check `wp_envelope_packages`).

## Test plan

### Unit tests

In the tests of the crate that loads the registries (the registry loader of the base crate), with no mocks:

- `envelope_rows_match_table`: loads the committed file; expects ten rows, R1 to R10, with the packages and classes of
  the table (for example R3: `["WP-44"]`, E1; R7: `["WP-61"]`, E3; R9: `["WP-76", "WP-77"]`, E2).
- `class_limits`: E0 = 16 GiB, 8 cores, 3,600 s, 1 device; E1 = 7,200 s per run and 12 device-hours per gate;
  E2 = 48 device-hours; E3 = 500 device-hours.
- `approved_requires_record`: a row with status `approved` and an empty `approved_by` fails to load.
- `e3_requires_ceiling_and_kill_rule`: an approved E3 row with either field empty fails to load.
- `row_requires_fallback`: a row with an empty `not_approved_fallback` fails to load.
- `pending_is_default`: with every row `requested`, the class in force for any scope is E0.
- `envelope_arithmetic`: device-hours for 1.6·10⁹ steps at 500 and 50 thousand steps per second are 0.89 and 8.9;
  for 5·10⁹ steps 2.8 and 27.8; for 2·10¹² steps 1,111 and 11,111, that is 23 and 231 days on two cards; 45
  device-hours fits E2 and 1,111 fits no class.

### End-to-end script and logging

`scripts/e2e/envelope_packages.sh`, specified in N44-02: for each row, the estimate names the class, the job is
refused under E0 before it starts, and the fallback form is admitted; logged through the shared helper of STD-E2E.

### Known answers and negative controls

Known answer KA-823 (the compute-envelope arithmetic above; exact to two significant figures; tier G1 on the host).
The plan states no tolerance and no control for it, so this bead sets them: negative control, an arithmetic that
forgets the two cards reports 46 to 463 days and must fail `envelope_arithmetic`. Planted failures the loader must
catch: an approval without an approver, an E3 approval without a kill rule, a row without a fallback, an eleventh row
that names a package key that does not exist.

## Considerations

- **Five open questions meet in this list.** OPEN-SPARK-2 (the classes; default E0; blocks GATE-SPARK-03, -04, -20
  and -21 as specified), OPEN-PHYLUM-3 (default: the one-device, one-hour rule, which admits the pilot and not the
  full experiment), OPEN-NEMESIS-3 (default: certify to 10⁻⁵), OPEN-PROG-4 (default: not run above E0, every cheap
  rung `uninformative`) and OPEN-CORTEX-1 (default: no pretraining). This bead decides none of them; it records what
  each ruling means per package.
- **Two refusal codes exist for one condition.** A job above the compute envelope in force is refused with
  `FROB-REF-761`; the daemon's `campaign` size class, defined as above the machine envelope, is refused with
  `FROB-REF-704` (exit code 4) until the owner approves an envelope. The estimator's and the daemon's beads must state which fires
  where; until they do, tests accept `FROB-REF-761` at estimation and submission and `FROB-REF-704` at scheduling.
- **Builds and tests count** toward the envelope, so the cold build of the M1 closure is itself bounded by E0
  (OPEN-SUITE-5).
- **An approval is not a result.** A run inside an approved class still needs its disclosure block, and a figure
  from a run that exceeded its class is not cited.
- What would make us revisit: a measured rate far from the 50 to 500 thousand steps per second the arithmetic
  assumes, which would resize every row.
