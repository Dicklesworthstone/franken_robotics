## Background

FACT: the machines this program runs on are shared, and the rule that governs them, inherited from the sibling
simulator's agent instructions and adopted here, is that no run on any host uses more than 16 GiB of memory, 8 cores
or one hour of wall time without the owner's written approval given before it starts. Builds and tests count; a run
longer than a few minutes starts under a timeout; when an agent stops, its jobs stop. The fail-closed default of the
open question on the compute envelope (OPEN-SPARK-2) adds the device rule: a GPU job is limited to one device and one
hour. That default is called class E0.

What E0 cannot run, by arithmetic (the plan's known answer on the envelope): one device-hour at 50 to 500 thousand
environment steps per second is 0.18 to 1.8·10⁹ steps. The performance gates themselves need more: one row uses 24
threads, two use two devices, and the world bank holds far more than 16 GiB. The rank-agreement experiment needs about
forty per-design trainings, about 45 device-hours, or 5 to 7.5 where specialists are reused. Pretraining a family
policy at published sizes of 1.6·10⁹ steps is 0.9 to 9 device-hours and at 5·10⁹ steps 2.8 to 28; at 2·10¹² steps it
is 1,100 to 11,000 device-hours, which is 23 to 230 days on two cards and is not planned in any envelope.

The proposal to the owner (OPEN; nothing above E0 runs until it is ratified or amended):

| Class | Scope | Proposed limits (TARGET budgets, not measurements) |
|---|---|---|
| E0 | Default | 16 GiB, 8 cores, 1 hour, one device |
| E1 | A named gate measurement | Both machines, all cores, memory up to the device budget, 2 hours per run, 12 device-hours per gate |
| E2 | A design campaign | 48 device-hours |
| E3 | Pretraining of one family policy | 500 device-hours, approved per run with its ceiling and kill rule written first |

Ten groups of work packages need more than E0, and each names its class and what happens if the class is not
approved. Beyond the plan's table, the drafted beads found eighteen more needs: one (the two-card fingerprint of
GATE-SPARK-07, needed at M0) is written here as an eleventh row, and seventeen are reserved row identifiers (R12 to
R28) that their own beads file, with their estimates, before their first run. This bead is the decision that puts all of them in front of
the owner as one list and one total, and records the answer. It exists because of RISK-10 (severity High): no compute envelope is approved, so the performance gates, the
rank-agreement experiment and pretraining cannot run as specified; its signal is the open question still at E0 when
M1 opens; its mitigation is that the classes are proposed at M0, every package above E0 names its budget, and M2 and
M4 have variants that fit E0. Every request has a fallback, so a refusal is a recorded outcome and never a blocked
program.

Alternatives rejected. (1) One blanket approval of everything above E0: the machine rule asks for approval before each
run starts, and the classes exist so that an approval carries a ceiling. (2) Leaving the requests inside the beads that
need them: the owner would never see the total, which is the risk as stated. (3) Raising the default: other agents and
other projects share the machines.

**The record (DESIGN).** One `[[request]]` row per request in `registries/compute_envelope.toml` (schema
`frob.compute_envelope/1`), the one record of envelope classes and approvals. The file, its loader and its lint are
N21c-35's; the class tables in it (limits, state `proposed`, `approved` or `amended`, and `in_force = "E0"`) are that
bead's content, and the request rows are this bead's. There is no second file: an earlier sketch that kept the
requests in a separate `registries/envelopes.toml` is not built, because the verbs' admission (N36-20) and the script
guard (N34-15) must reach the same verdict from the same approvals. The family-policy decision records its per-run
rows in this same table (N23b-24), and the approval the script guard accepts is a row of it (N34-15). A row, with the
fields N21c-35's schema fixes:

```
[[request]]
id = "R6"                      # stable; a new request takes the next number
parent = ""                    # a per-run approval under a standing E3 request names that request (for example "R7")
packages = ["WP-60"]
scope = "the rank-agreement pilot; the partial gate's campaigns"   # prose, for the owner
admits = ["campaign:rank-agreement", "gate:GATE-CORTEX-12", "gate:GATE-TENFOLD-06"]
class = "E2"
limits = { device_hours = 48 } # for E1: mem = "device budget", cores = "all", wall_s_per_run = 7200, device_hours = 12
not_approved_fallback = "cheap rungs are `uninformative`; the partial gate runs its CPU strata"
open_question = "OPEN-PROG-4"
status = "requested"           # requested | approved | amended | declined
approved_by = ""               # required when status is approved or amended
date = ""                      # ISO date of the ruling
decision = ""                  # path of the owner's ruling, a decision record under docs/adr/ (the packet put to the owner may sit under docs/decisions/)
token = ""                     # hash of the decision note, set with the ruling
expires = ""                   # the gate, campaign or date after which the approval lapses
ceiling = ""                   # E3 only: the run's ceiling in device-hours, written before approval
kill_rule = ""                 # E3 only: the rule that stops the run, written before approval
```

`admits` (DESIGN) lists the admission scopes the row covers, in the form the enforcement bead uses for a job's scope:
`gate:<id>` for each gate of the row's last column, `campaign:<id>` for each campaign the packages name,
`pretrain:<run>` for one pretraining run. It is what lets admission match a job to its row; the beads that measure the
gates add or correct scopes when they cite the row. Limits are copied from the class and differ from it only where
the owner amends the row. A job's scope is, in this order, the token of the launcher it runs under (`frob-launch`,
the campaign runner), the scope a run verb cites with its common run input `envelope_scope` (command line
`--envelope-scope <gate:…|campaign:…|pretrain:…>`), a scope the verb derives from its own inputs (`train.family`),
otherwise `adhoc`, whose class in force is E0; a citation that contradicts the launcher's token is refused (N36-20,
convention 14). A step that runs a job "for this job's scope" through a run verb therefore cites the row's scope
with `--envelope-scope`, or runs under a launcher that holds it.

Readers, so that the rows are not orphans: admission (N36-20) takes the class in force for a job from the approved,
unexpired row that admits its scope, through `class_in_force` of N21c-35, and refuses a job above it before it starts
(`FROB-REF-761`); the script guard (N34-15) reads the same row by its `id`; the lifecycle check (N41-17, rule 7) reads
each row's status and date; N44-04 checks that the packages named in rows R1 to R10 are the fourteen of the table,
that R11 names WP-35, and that every package any row names cites that row's identifier in its epic; exit reviews read
the status of each row.

**Why the reserved rows are not written at M0.** Their estimates belong to the beads that will run them: the pilots'
ceilings and falsifiers are written before approval and frozen with each protocol, the fleet run length depends on
which single machine the fleet pilot finds better, and five of the budgets (R17, R18, R20, R22, R27) are not given by
the plan. A row
written now would carry figures this bead does not own. The owner still sees them in the M0 total (step 2), so the
total is not hidden inside the beads (alternative 2 above). Because N44-04 derives its expected set from the register
and the reservation table, filing a reserved row needs no change to N44-04.

**Procedure.**

1. At M0 write the eleven rows R1 to R11 with status `requested`, and add the class and fallback to each affected
   package epic, with the row's identifier (done in the epics of this unit; the epics of the reserved rows cite their
   identifiers too).
2. Present the list to the owner with the class ceilings: E1 at most 2 hours per run and 12 device-hours per gate; E2
   at most 48 device-hours per campaign; E3 at most 500 device-hours per run. The total has three parts, shown
   separately: the eleven rows at their class ceilings; the reserved rows R12 to R28 at their stated estimates (R12
   at most 12 device-hours under E1; R13 about 70; R14 and R15 about 10 each; R16 about 60; R17 and R18 stated by
   their protocols, R18 about 3.3 times R17; R19 about 6 to 9; R20 sized from R16's pilot, at most 48 under E2; R21
   about 40; R22 stated by its protocol; R23 about 10; R24 at most 12 under E1; R25 at most 15; R26 at most 12, and
   only if its smoke run needs it; R27 stated by its protocol; R28 about 25 under E2); and the one request no class
   covers, R13, which needs an amendment (R20 joins it
   if its estimate exceeds 48). Silence on the reserved rows at M0 is not a ruling: each is ruled on when it is filed.
3. The owner rules on each row in writing: approve, amend (a different class or limits) or decline. Silence is
   `requested`, which is treated exactly as declined: the default E0 stays in force.
4. On approval: fill `status`, `approved_by`, `date`, `decision`, `token`, `expires`; the beads of the row become
   ready (the lifecycle rule of N41-17). For a row with its own open question, that question's decision bead does
   this step and this bead only confirms the row loads.
5. On decline or silence: the fallback of the row is in force. The gates the row names are recorded `not run` with
   the reason, never as a pass; beads that exist only under approval close `withdrawn` citing the row and its
   decision record (N41-17, rule 2: they claim no capability, and `superseded` is kept for a killed capability), and
   beads that can stand on the fallback run in their fallback form.
6. A bead that discovers a need above E0 adds a row first, with its class and its not-approved fallback. A row
   without a fallback is not accepted: no request may leave the program blocked on an approval. A bead named in the
   reservation table files its reserved identifier; any other bead takes the next free identifier from R29 and, in
   the same commit, states it in its package epic's Envelope bullet. The new row is put to the owner when filed,
   with the running total of approved device-hours.
7. If the owner amends the classes themselves, every row is re-read against the new limits and the rows whose class
   no longer covers their need return to `requested`.

**What a row means for readiness.** The lifecycle rule is stated and checked in N41-17 (rule 7): a bead whose run
exceeds the machine envelope (the parity baselines, training, the head-to-head, the rank-agreement experiment, the
partial gate, the tournament) names its budget and is not ready until the owner's approval is recorded; a Frontier
or Moonshot bead is in addition not ready until its pilot has a recorded result. This register supplies the envelope
half of that check: "names its budget" means the bead cites a row `id` of this table, and "approval recorded" means
that row has status `approved` or `amended` with `approved_by`, `date`, `decision` and `token` filled, on or before
the bead's first run. A row that is `requested` or `declined` leaves the bead not ready in its over-envelope form and
ready in its fallback form.

## Test plan

### Unit tests

In the tests of the crate that loads the registries (`frob_core::envelope::registry`, N21c-35's loader), on the
committed file, with no mocks:

- `envelope_rows_match_table`: loads the committed file; expects the eleven rows R1 to R11, with the packages and
  classes of the tables (for example R3: `["WP-44"]`, E1; R7: `["WP-61"]`, E3; R9: `["WP-76", "WP-77"]`, E2; R11:
  `["WP-35"]`, E1, `admits = ["gate:GATE-SPARK-07"]`), and no identifiers outside R1 to R11 other than filed
  reserved rows and rows from R29 on.
- `reserved_rows_match_reservation`: for each identifier R12 to R28 present in the file, its packages equal the
  reservation's (R12 `["WP-46"]`; R13, R14, R16 and R20 `["WP-61"]`; R15 `["WP-29"]`; R17 and R18 `["WP-33"]`; R19
  `["WP-11"]`; R21, R22 and R27 `["WP-79"]`; R23 `["WP-73"]`; R24 `["WP-75"]`; R25 and R26 `["WP-27"]`; R28
  `["WP-47"]`) and its
  `not_approved_fallback` is non-empty; a class or scope that differs from the reservation carries a `decision`
  note. With none of them present, as committed at M0, the test passes and logs the seventeen as `reserved, not
  filed`.
- `identifiers_unique_and_ordered`: row identifiers are unique and of the form `R<n>`; R1 to R11 are all present;
  identifiers above R28 are contiguous from R29. A request no longer needed keeps its row, `declined` with its
  decision note, so an identifier is never reused.
- `rows_limits_equal_class_limits`: each row's `limits` equal those of its class in the same file (E1 = 7,200 s per
  run and 12 device-hours per gate; E2 = 48 device-hours; E3 = 500 device-hours) unless its status is `amended`.
- `every_row_admits_a_scope`: each row has a non-empty `admits`, every `gate:<id>` in it is a gate of the gate
  register, and no scope is admitted by two rows.
- `pending_is_default`: with every row `requested`, as committed at M0, the class in force for each admitted scope
  is E0.
- `every_row_has_fallback_and_question`: no row has an empty `not_approved_fallback` or `open_question`.

The loader's own rejections (an approval without an approver, an E3 approval without ceiling and kill rule, a row
without a fallback, an unknown package key) are unit tests of N21c-35 (`approved_requires_record`,
`e3_requires_ceiling_and_kill_rule`, `row_requires_fallback`); the class limits as committed values are its
`class_limits_committed`; the envelope arithmetic (0.89 and 8.9 device-hours for 1.6·10⁹ steps at 500 and 50
thousand steps per second; 2.8 and 27.8 for 5·10⁹; 1,111 and 11,111 for 2·10¹², that is 23 and 231 days on two
cards; 45 device-hours fits E2 and 1,111 fits no class) is N36-20's `device_hour_arithmetic`.

## Considerations

- **Five open questions meet in this list.** OPEN-SPARK-2 (the classes; default E0; blocks GATE-SPARK-03, -04, -20
  and -21 as specified), OPEN-PHYLUM-3 (default: the one-device, one-hour rule, which admits the pilot and not the
  full experiment), OPEN-NEMESIS-3 (default: certify to 10⁻⁵), OPEN-PROG-4 (default: not run above E0, every cheap
  rung `uninformative`) and OPEN-CORTEX-1 (default: no pretraining). This bead decides none of them; it records what
  each ruling means per package.
- **Two refusal codes, divided by where they are raised** (N32-REF row 704, N35-REF row 761, N36-20; convention
  14). The daemon's size classifier refuses a `campaign`-class job whose scope has no approved envelope with
  `FROB-REF-704` when the job is submitted, before envelope admission, and the scheduler raises it again at
  dispatch and at resume when the approval the job was queued under has lapsed (BD-296). Every other case is
  `FROB-REF-761`, raised before the job starts: a job above the class in force for its scope, or above an approved
  scope's per-run or cumulative limit, at estimation and at run admission on every surface, including a daemon job
  that cites an approved envelope and still exceeds it. Both are exit code 4, and both envelope checks come before
  the session-budget check `FROB-REF-701`.
- **Builds and tests count** toward the envelope, so the cold build of the M1 closure is itself bounded by E0
  (OPEN-SUITE-5).
- **An approval is not a result.** A run inside an approved class still needs its disclosure block, and a figure
  from a run that exceeded its class is not cited.
- What would make us revisit: a measured rate far from the 50 to 500 thousand steps per second the arithmetic
  assumes, which would resize every row.
