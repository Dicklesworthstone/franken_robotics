## Background

No run on the shared machines may use more than 16 GiB of memory, 8 cores, one hour of wall time or one device
without the owner's written approval given before it starts. That default is envelope class E0. Three larger classes
are proposed: E1 for a named gate measurement (both machines, all cores, memory to the device budget, 2 hours per
run, 12 device-hours per gate), E2 for a design campaign (48 device-hours) and E3 for pretraining of one family policy
(500 device-hours, approved per run with its ceiling and kill rule written first). Ten groups of work packages have
registered a request above E0 in the plan's table, an eleventh request (R11, the two-card fingerprint of
GATE-SPARK-07) is written at M0, and seventeen more rows (R12 to R28) are reserved for beads that file them before
their first run; each says what happens if it is not approved (the register, the reservations and the owner's ruling
are N44-01).

The rule is only as good as its enforcement, and enforcement has two properties that are easy to get wrong. The
refusal must come before anything starts: a job that is stopped after an hour has already broken the rule. And a
refusal must leave the program able to continue: the not-approved form of every request must itself be admitted and
must be the thing that runs. This bead is the end-to-end test of both, from the user's side, for every row of the
register. It also protects the product's own statement that the system estimates a job's cost and class itself and
never takes the size from the agent.

Subsystem: delivery, with the estimator of the performance program; tier Solid; milestone M2, when `sim.estimate`
exists; re-read at every later exit as further rows become testable. It serves RISK-10 (no envelope is approved, so
gates cannot run as specified): with this test the consequence of that risk is always a recorded `not run`, never an
unapproved run and never a silent pass.

Alternative rejected: testing the envelope only through the script guard that wraps heavy shell lanes. That guard is
a seat belt for builds, tests and lanes that spend no device time above E0, and it has no meter; the authority is the
verbs' own refusal, and that is what agents meet. Work launched outside the verbs above E0 (the pilots of R13 to R17,
R21, R23, R25 and R26, which run on incumbent stacks or existing tools, the treatment arms of R27 and the two-card
arms of R28, which N22b-07 and N36-22 start under the launcher, and the incumbent arms of R1) goes through the
metered launcher `frob-launch` of N36-20, so for those rows the launcher is the first thing an agent meets and is what
is tested here. A run verb reaches the scope a row admits by citing it with the common run input `--envelope-scope
<scope>` (`envelope_scope` over MCP; convention 14, NJL-01), as the child of `frob-launch --scope` (or of the campaign
runner), whose token gives it the scope, or through an input from which its own verb derives the scope
(`train.family --approval`); with none of these its scope is `adhoc`, whose class in force is always E0 (N36-20). The
steps below that need a row's scope cite it, and repeat the submission under the launcher.

## Scope

In: `scripts/e2e/envelope_packages.sh`, its row table, its assertions and logs. Out: the estimator and its cost model
(BD-219); the admission check, the device-hour meter and the rule for which refusal code fires where (N36-20); the
daemon's size classes and the `campaign` refusal at dispatch (BD-296); the register, the reservations and the ruling
(N44-01); the launcher `frob-launch` and its meter (N36-20), which this test drives for the launcher rows; the
script guard (N34-15) and its own tests; the gate measurements and the pilots themselves, none of which this test
runs.

For a reserved row not yet filed in the committed register, the steps run on a scratch row built from the
reservation (packages, class expected, scopes), labelled `synthetic`; once the row is filed, on a copy of the filed
row. Where the reservation names no single class (R17, R18, R22 and R27: the class that covers a budget the protocol
states), the scratch row takes E1 for the row's gate scope, the smallest class above E0 that a gate scope can have. A
launcher row never runs its pilot or its arms: the launched command is a probe that writes a marker file and exits.

Every call of a run verb carries `--key envpkg-<row>-<step>-<form>-<path>-s<seed>` (`<form>` is `over` or
`fallback`; `<path>` is `adhoc`, `cited` or `launcher`, prefixed `d` for a submission through `frobd`, as in
`dcited`), so that no call returns another call's stored receipt, and an uncited resubmission of a job that a cited
call already bound is not answered `FROB-REF-803` (the cited scope is part of the request's content).

A row whose verb (or, for R18, whose algorithm) is not yet in the verb registry is logged `pending: verb absent` and
counts as neither pass nor fail. The script fails if a row is still marked pending when its verb is present in the
registry, so a row cannot be forgotten when its verb lands. The same rule holds for the daemon half of step 2 and for
step 7, both pending until the daemon reports the `campaign` size class of BD-296.

**Steps for each active row admitted by the verbs.** S is a scope from the row's `admits` (the gate of the
representative job for a gate row; its campaign or pretraining run otherwise). "Under S" means the verb job is
submitted in two forms, each asserted: directly, citing the scope with the common run input `--envelope-scope S`
(convention 14; the form an agent over MCP uses, as `envelope_scope`, since it has no launcher), and as the child of
`frob-launch --registries-root <scratch> --scope S --request <row>` with the job's demand from step 1 declared
(`--devices`, `--device-ids`, `--cores`, `--mem-gib`, and `--wall-s` the upper end of its wall interval), whose token
gives the child its scope. A verb whose own bead derives S from its inputs (`train.family --approval`, R7 and R10) is
started directly with that input instead of the citation.

1. With every register row at `requested` (the default), estimate the job: `frob --json sim estimate` for a
   simulation job, otherwise the job's own run verb with `--estimate` and its key (BD-219: the estimate record's
   `envelope {needed, in_force}`, priced under the scope the run would carry). Assert exit zero, the class needed
   equals the table, and the class in force is E0.
2. Submit the job with no citation (scope `adhoc`), in process, with no daemon running (the in-process path, where no
   size class exists). Assert a typed refusal with code `FROB-REF-761`, exit code 4, and, from receipts and counters:
   zero worlds stepped, no device allocation, no job row, no charge to the session budget. A 704 at this step is a
   failure that names the row: an in-process run has no size class. Once the daemon reports its `campaign` size
   class (BD-296), the same job is also submitted through `frobd`, uncited and again citing `--envelope-scope S`: a
   job above the machine envelope is in the `campaign` class, and since no approved row admits its scope the size
   classifier refuses it with `FROB-REF-704` before envelope admission is reached (the plan's rule for that class),
   exit code 4, with the same zero counters; a 761 there is a failure that names the row. Until then this half is
   logged `pending: scheduler absent`.
3. Submit the job under S, in both forms. Assert `FROB-REF-761`, exit code 4, nothing started (the launcher starts no
   child; the cited submission leaves no job row and steps no world), and the refusal's four ranked repairs in the
   order of N35-REF's row 761, read from `registries/refusals.toml`: (1) a smaller job that fits, naming the largest
   world count, thread count or duration that does; (2) a split into runs that each fit the per-run limit; (3) a
   request for the class printed, naming this register row, then a resubmission citing S with `--envelope-scope`;
   (4) the row's `not_approved_fallback`, whose text is the table's fallback form. (Step 2's uncited submission has
   scope `adhoc`, which no row admits, so its repairs (3) and (4) name no row; this is logged.)
4. Run the estimate on the fallback form. Assert class needed E0. Submit it with no citation and `--sync-wait-ms 0`,
   assert it is accepted (exit code 8 with its job handle), then cancel it before its first chunk (`frob job cancel
   <job> --json`) and assert the three phases of cancellation (request, drain, finalize) with no leaked device memory.
   For a row whose fallback runs nothing (R9 declares its cell `not run`, R10 funds nothing, and so does every
   reserved row whose fallback is `not run`), this step asserts instead what step 6 asserts.
5. Switch to a scratch registry (`--registries-root`, N32ax-03) in which this row alone is `approved` with approver,
   date and decision note. Submit the job under S. The decision comes from the scratch registry and execution stays
   bounded by the record (N32ax-03's hold; from M1 a verb's job is held, N36-20 admission step 5): the cited
   submission, with `--sync-wait-ms 0`, is admitted and held (exit code 8 with its job handle; state `admitted`,
   `hold: scratch-approval`), and after 5 s zero worlds are stepped and zero device bytes allocated; cancelling it
   yields a cancellation receipt. The launcher form exits 4 with `scratch_verdict: "admitted"` and starts no child.
   The row's text hash is logged. Then assert that the approval is scoped: the job of a different row citing that
   row's scope is a plain 761 (no `scratch_verdict`, no hold), and this job submitted with no citation (scope
   `adhoc`) under the same scratch registry is a plain 761 as well.
6. For a row left declined, assert on the scratch gate registry that every gate the row names has status `not run`
   with a reason citing the row; plant a `pass` on one of them and assert the check fails.
7. Dispatch, through `frobd` (each active verbs row: its job is above the machine envelope, so in the daemon's
   `campaign` size class). With the row approved in the scratch registry, submit the job through `frobd` citing S
   with `--sync-wait-ms 0`: the size classifier reads the scope as approved and admission holds the job (`hold:
   scratch-approval`). Assert that the dispatcher never places it: after 5 s, state `admitted` with the hold, zero
   worlds stepped and no device allocation. Then set the scratch row's `expires` to a past date and assert, after
   the next dispatch pass, that the job is still held and was neither re-sized nor refused (BD-296: the dispatch pass
   skips held jobs); cancel it and assert a cancellation receipt. A placement, or a `FROB-REF-704` for the held job,
   is a failure that names the row. The scheduler's own 704 at dispatch, for a job queued under an approval of record
   that lapses, needs an approval of record, which this script never writes (it never touches the committed
   registry and never starts a run above E0); it is held by BD-296's unit tests `campaign_dispatch_704_after_withdrawal`
   and `campaign_restart_reenqueue_rechecked`, and this step logs it `skipped: dispatch-time 704 needs an approval of
   record`, never as passed. The step is logged `pending: scheduler absent` until the daemon reports the `campaign`
   size class.

**Steps for each launcher row** (R13 to R17, R21, R23 and R25 to R28), on `frob-launch` (N36-20) with
`--registries-root` set to the scratch copy, `--scope` the scope the row admits (R14 `gate:KILL-DISTILL`, R15
`gate:KILL-EQUIV`, R17 `gate:KILL-SHORTGRAD`, R16 one `campaign:` scope of BD-324, R13 the pilot's scope as filed, R21
`campaign:pilot-skill-transport`, R23 `gate:GATE-HAB-09`, R25 `campaign:pilot-reflex-mpc`, R26 `gate:KILL-RESIDUAL`,
R27 `gate:GATE-REFLEX-09`, R28 `campaign:perf-row9-humanoid`), `--request <row>` and the pilot's or arm's declared
demand (devices, cores, memory, wall time):

G1. With the row absent or `requested`: `frob-launch --scope <S> --request <row> --devices <d> --cores <c> --mem-gib
    <g> --wall-s <w> --json -- <probe>` with the pilot's demand (above E0). Assert exit code 4 with `FROB-REF-761`
    and no `scratch_verdict` before the probe starts (no marker file, no meter row), and that the refusal's four
    repairs follow N35-REF's row 761 in order, the third naming the row and the fourth printing its not-approved
    fallback.
G2. A probe whose declared demand is inside E0 (one device, two cores, 1 GiB, 60 s) under the same scope S: assert
    exit zero, the marker present and exactly one new meter row under scope S with outcome `completed`: the launcher
    is not a blanket block, and work launched outside the verbs is charged to its pilot's scope.
G3. With the row approved in the scratch registry (approver, date, decision note; for R13 the amended class with its
    ceiling and the falsifier written): the pilot-sized launch of G1 is decided admitted and, since the class of
    record is E0, held by the scratch rule (N36-20, admission step 5): assert exit 4 with `scratch_verdict:
    "admitted"`, the row's text hash logged, no marker and no meter row. With the approval of a different row passed
    instead, assert exit 4 with `FROB-REF-761` and no `scratch_verdict`: an approval is scoped.
G4. With a row whose `class` is below the class asked (R13 filed as an unamended E2 while the declared demand needs
    the amended ceiling), assert exit 4 with `FROB-REF-761` and no `scratch_verdict`.
G5. The cumulative limit binds work launched outside the verbs: with the row approved and the scratch meter
    pre-loaded for scope S to 0.5 device-hours below the row's cumulative limit (11.5 of 12 for R14 and R15), a
    launch declaring 1.0 device-hour is refused with `FROB-REF-761` printing the remaining 0.5, and one declaring
    0.4 is decided admitted (`scratch_verdict: "admitted"`, held, nothing started).

**Class boundaries**, on a job specification labelled `synthetic` whose estimated cost is set by its world count and
duration: under an approved E1 row, an estimated run of 2 hours is admitted and 2 hours 1 minute is refused, and a
gate total of 12 device-hours is admitted and 12.1 refused; under E2, 48 device-hours admitted and 48.1 refused;
under an E3 row with a written ceiling of 100, 100 admitted and 101 refused, and 501 refused whatever the ceiling.

**Logging.** `target/e2e-logs/envelope_packages/<utc-timestamp>.ndjson` and a transcript beside it. Each line has
`ts`, `script`, `bead` (`N44-02`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time, and the envelope's `evidence` block (claim, class, tier, determinism, identities,
seed). Metrics: class needed and class in force per row; worlds stepped after a refusal (threshold 0); device bytes
allocated after a refusal (threshold 0); estimated device-hours at each boundary against its limit; per row, the
refusal code seen at submission (in process and, where active, through the daemon), the held job's state, hold,
worlds stepped and device bytes while held (thresholds 0) and after the dispatch pass; for launcher
rows, `frob-launch`'s exit code, the `scratch_verdict` where present, whether the marker exists, and the meter row
(scope, device-seconds, outcome) or its absence; for each submission, its scope and where the scope came from
(`launcher`, `citation`, `verb` or `adhoc`), its idempotency key, and the four repairs as printed. Every line names
the row identifier and its path (`verbs` or `launcher`) and, for a reserved row, whether
its scratch row came from the reservation or from the filed row. A failed assertion logs the first differing value
and the paths of the scratch registry and the envelope it compared. The final `summary` gives assertions passed and
failed, rows active, rows pending (with the reason: verb absent, scheduler absent), steps skipped (with the reason),
and `gates: []`.

      `not_approved_fallback`, which equals the table's fallback form.
- [ ] Every refusal at estimation, at in-process submission and from `frob-launch` carries `FROB-REF-761`;
      `FROB-REF-704` appears only from the daemon's size classifier (a `campaign`-class job submitted through `frobd`

      BD-296's scheduler lands; at that exit a job held under a scratch approval is never placed, re-sized or answered

- [ ] Work launched outside the verbs is metered: in G2 the probe leaves exactly one meter row under its pilot's

- [ ] After every refusal the counters show zero worlds stepped and zero device bytes allocated.
- [ ] Every fallback form is admitted under E0 and is cancelled cleanly: no leaked device memory after the cancel.
- [ ] A scoped approval decides `admitted` (and holds: nothing starts) for its own job under its scope, cited or

- [ ] A job that under-declares its devices (the specification says one, its placement plan needs two) is still
      classed E1: the class comes from the system's estimate, not from the declaration.
- [ ] The script itself runs inside E0 with a wide margin, under the helper's timeout, and never starts a run above E0.
- [ ] At each later exit the rows whose verbs have landed are active; a row marked pending while its verb exists
      fails the script.

## Test plan

### Unit tests

The row table is data; its helpers are tested in `scripts/lib/tests/envelope_packages_test.sh`:

- `row_pending_when_verb_absent`: a row whose verb is missing from a scratch verb registry is logged pending and the
  exit code is zero.
- `row_must_activate_when_verb_present`: the same row with the verb present and the row still marked pending exits
  non-zero naming the row; the same for step 7 with a daemon that reports the `campaign` size class.
- `row_table_matches_register`: the script's row table holds every row identifier of the committed register and of
  N44-04's envelope fixture (`docs/delivery/work-packages.envelope.tsv`), with the same packages; a register row
  missing from the table, or a table row whose packages differ, exits non-zero naming the row.
- `reserved_row_scratch_from_reservation`: with R15 absent from a scratch register, the scratch row built for G1 to
  G5 has `packages = ["WP-29"]` and the class of the reservation and is labelled `synthetic`; with R15 filed, the
  scratch row is a copy of the filed one; with R22 absent, its scratch row has `packages = ["WP-79"]`, class E1 and
  `admits = ["gate:GATE-AUGUR-23"]`.
- `run_keys_distinct`: for one seed, the idempotency keys the script builds are distinct across rows, steps, forms
  and submission paths; a planted duplicate exits non-zero naming both calls.
- `scratch_dir_outside_repo`: the scratch-directory resolver refuses a path inside the repository's worktree
  (including through a symbolic link) and exits non-zero naming the path.

### End-to-end script and logging

This bead is the script: `scripts/e2e/envelope_packages.sh`, with the steps and the log format above.

### Known answers and negative controls

Known answers: the class of each representative job as in the tables; the boundaries 2 hours, 12, 48 and 500
device-hours; the refusal part of the envelope known answer (a job above the class in force is refused before it
starts); the code at each point (761 at estimation, at in-process submission and at the launcher; 704 from the
daemon's size classifier; none for a job held under a scratch approval, at dispatch or after the approval lapses;
the scheduler's 704 for a lapsed approval of record is BD-296's unit tests'). Negative controls, each of
which must be caught: the under-declared job; the approval used outside its scope (verbs, step 5, and launcher, G3);
an approval that admits the same job submitted with no citation (`adhoc`, step 5); a 761 whose repairs are out of the
registry row's order or whose third repair names no row under a row's scope (step 3, G1);
the planted `pass` on a declined row's gate; an approved row with an empty approver, which must fail registry load
before any job is estimated; an approved E3 row without a kill rule; a launcher row whose probe leaves its marker after
a refusal (a launcher that starts the command before admitting); a launcher that writes no meter row for an admitted
probe (G2); a dispatcher that places a job held under a scratch approval, or re-sizes it and answers 704 once that
approval lapses (step 7). Determinism lanes: the class needed is a discrete
value and must be identical twice on one machine and on both machines; debug and release builds must agree.

## Considerations

- **Two refusal codes, divided by raising site** (the plan's §32.11.2: the `campaign` size class is "refused with
  `FROB-REF-704` until the owner approves" an envelope; convention 14; the division is stated identically in N32-REF,
  owner of row 704, in N35-REF, owner of row 761, in N36-REF, in N36-20 and in BD-296): a job queued by the daemon is
  classified first, and a `campaign`-class job whose scope has no approved envelope (uncited, or citing a scope no
  approved row admits) is refused with 704 by the size classifier, before envelope admission; a job queued under an
  approval of record that lapses before dispatch is refused with 704 by the scheduler, while a job held under a
  scratch approval is never re-sized (BD-296); every other case is 761 (`sim.estimate`, an in-process run,
  `frob-launch`, and a daemon job whose scope has an approved envelope and that still exceeds its class's limits).
  Both are exit code 4. The script asserts the code at each point, so an in-process run that raised 704, or a daemon
  that let a campaign-class job without approval reach envelope admission, is caught.
- **The scope of a verb job** (convention 14; N36-20, NJL-01): a run verb names the approved scope it belongs to with
  the common run input `envelope_scope` (`--envelope-scope <gate:…|campaign:…|pretrain:…>`); the scope of its demand
  is, in order, the token of a launcher it runs under, the citation, a scope the verb derives from its inputs,
  otherwise `adhoc` (class E0). A citation grants nothing by itself: a cited scope that no approved row admits is E0,
  so the uncited and the cited submissions of steps 2 and 3 are refused alike. The scoped steps cite S, the only path
  an agent over MCP has, and repeat under `frob-launch --scope`, so the two paths are held to one answer.
- **The launcher is metered, the script guard is not** (N36-20, N34-15): `frob-launch` settles every admitted
  launch into the device-hour meter, so the cumulative limits of a class bind work started outside the verbs; the
  script guard enforces only a run's memory, cores, wall time and devices, and is meant for builds, tests and lanes
  that spend no device time above E0. A pilot arm started under the guard instead of the launcher is not metered and
  is not evidence.
- **Field names of the estimate's output** (class needed, class in force) are fixed by the estimator's schema; the
  script reads them through one mapping at its top.
- **A test that needs an approval is a risk**: the approved rows exist only in the scratch registry, which the script
  deletes from its own scratch directory at the end; the committed registry is never touched, and the script fails
  if its scratch directory resolves inside the repository.
- If the owner amends the classes, the boundary cases are read from the registry's class table, not hard-coded.
