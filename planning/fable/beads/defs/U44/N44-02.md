## Background

No run on the shared machines may use more than 16 GiB of memory, 8 cores, one hour of wall time or one device
without the owner's written approval given before it starts. That default is envelope class E0. Three larger classes
are proposed: E1 for a named gate measurement (both machines, all cores, memory to the device budget, 2 hours per
run, 12 device-hours per gate), E2 for a design campaign (48 device-hours) and E3 for pretraining of one family policy
(500 device-hours, approved per run with its ceiling and kill rule written first). Ten groups of work packages have
registered a request above E0, each with what happens if the request is not approved (the register and the owner's
ruling are N44-01).

The rule is only as good as its enforcement, and enforcement has two properties that are easy to get wrong. The
refusal must come before anything starts: a job that is stopped after an hour has already broken the rule. And a
refusal must leave the program able to continue: the not-approved form of every request must itself be admitted and
must be the thing that runs. This bead is the end-to-end test of both, from the user's side, for every row of the
register. It also protects the product's own statement that the system estimates a job's cost and class itself and
never takes the size from the agent.

Subsystem: delivery, with the estimator of the performance program; tier Solid; milestone M2, when `sim.estimate`
exists; re-read at every later exit as further rows become testable. It serves RISK-10 (no envelope is approved, so
gates cannot run as specified): with this test the consequence of that risk is always a recorded `not run`, never an
unapproved run and never a silent pass.

Alternative rejected: testing the envelope only through the script guard that wraps heavy shell lanes. That guard is
a seat belt for scripts outside the daemon; the authority is the daemon's own refusal, and that is what agents meet.

## Scope

In: `scripts/e2e/envelope_packages.sh`, its row table, its assertions and logs. Out: the estimator and its cost model
(BD-219); the daemon's size classes and the `campaign` refusal (BD-296); the register and the ruling (N44-01); the
script guard (N34-15); the gate measurements themselves, none of which this test runs.

## Technical approach

Plain shell on the shared helper of STD-E2E, driving the real `frob` binary against a scratch copy of `registries/`.
Nothing above E0 is ever executed by the test: admitted jobs are cancelled before their first chunk.

**The row table** (in the script; one line per register row, with a representative job and the class it must need):

| Row | Packages | Representative job (labelled `synthetic` where no gate job exists yet) | Class needed | Fallback form that must be admitted | Active from |
|---|---|---|---|---|---|
| R1 | WP-34, WP-47 | A parity measurement of the reference quadruped workload on both RTX 4090 and on all cores | E1 | The same measurement on one card and eight cores | M2 |
| R2 | WP-21, WP-48 | `train.start` of the reference flat velocity task on two devices | E1 | The same on one device | M2 |
| R3 | WP-44 | One arm of the head-to-head on 512 topologies | E1, once per arm | The pilot-sized head-to-head inside one device-hour | M2 |
| R4 | WP-53 | `scene.bank` with a resident set estimated above 16 GiB | E1 | A resident set that fits 16 GiB | M3 |
| R5 | WP-55 | `nemesis.bound` certifying a rate of 10⁻⁶ | E2 | The same certifying 10⁻⁵ | M3 |
| R6 | WP-60 | The rank-agreement experiment of forty per-design trainings | E2 | The pre-registration with every cheap rung `uninformative` | M3 |
| R7 | WP-61 | `train.family` pretraining of one class | E3 | No pretraining: specialists with inheritance | M4 |
| R8 | WP-62, WP-28 | `opt.cascade` on the design benchmark at its registered size | E2 | The same sized to one device-hour, fewer briefs | M4 |
| R9 | WP-76, WP-77 | One tournament cell of 24 mission families on both machines | E2 (E3 for a pretraining arm) | The cell declared `not run` with its reason | M7 |
| R10 | WP-79 | Tree-policy pretraining | E3 | None: the epic is not funded | M8 |

A row whose verb is not yet in the verb registry is logged `pending: verb absent` and counts as neither pass nor
fail. The script fails if a row is still marked pending when its verb is present in the registry, so a row cannot be
forgotten when its verb lands.

**Steps for each active row.**

1. With every register row at `requested` (the default), run `frob --json sim estimate` on the job. Assert exit zero,
   the class needed equals the table, and the class in force is E0.
2. Submit the job. Assert a typed refusal with code `FROB-REF-761` (or `FROB-REF-704` where the daemon's `campaign`
   size class is what fires), its registered exit code, and, from receipts and counters: zero worlds stepped, no
   device allocation, no job row, no charge to the session budget.
3. Assert the refusal's ranked repairs name, first, the fallback form and, second, the register row to request.
4. Run the estimate on the fallback form. Assert class needed E0. Submit it, assert it is accepted (exit code 8,
   accepted and still running, or a completed result), then cancel it and assert the three phases of cancellation
   (request, drain, finalize) with no leaked device memory.
5. Switch to a scratch registry in which this row alone is `approved` with approver, date and decision note. Assert
   the class in force for this job's scope is the row's class, that submission is accepted (then cancelled before its
   first chunk), and that the job of a different row is still refused: an approval is scoped.
6. For a row left declined, assert on the scratch gate registry that every gate the row names has status `not run`
   with a reason citing the row; plant a `pass` on one of them and assert the check fails.

**Class boundaries**, on a job specification labelled `synthetic` whose estimated cost is set by its world count and
duration: under an approved E1 row, an estimated run of 2 hours is admitted and 2 hours 1 minute is refused, and a
gate total of 12 device-hours is admitted and 12.1 refused; under E2, 48 device-hours admitted and 48.1 refused;
under an E3 row with a written ceiling of 100, 100 admitted and 101 refused, and 501 refused whatever the ceiling.

**Logging.** `target/e2e-logs/envelope_packages/<utc-timestamp>.ndjson` and a transcript beside it. Each line has
`ts`, `script`, `bead` (`N44-02`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time, and the envelope's `evidence` block (claim, class, tier, determinism, identities,
seed). Metrics: class needed and class in force per row; worlds stepped after a refusal (threshold 0); device bytes
allocated after a refusal (threshold 0); estimated device-hours at each boundary against its limit. A failed assertion
logs the first differing value and the paths of the scratch registry and the envelope it compared. The final
`summary` gives assertions passed and failed, rows active, rows pending, and `gates: []`.

## Acceptance criteria

- [ ] At M2 rows R1, R2 and R3 and all class-boundary cases pass on `batch-cpu` and on each admitted device family; rows
      R4 to R10 are logged `pending: verb absent`.
- [ ] After every refusal the counters show zero worlds stepped and zero device bytes allocated.
- [ ] Every fallback form is admitted under E0 and is cancelled cleanly: no leaked device memory after the cancel.
- [ ] A scoped approval admits its own job and no other row's job.
- [ ] A planted `pass` on a gate of a declined row makes the script exit non-zero.
- [ ] A job that under-declares its devices (the specification says one, its placement plan needs two) is still
      classed E1: the class comes from the system's estimate, not from the declaration.
- [ ] The script itself runs inside E0 with a wide margin, under the helper's timeout, and never starts a run above E0.
- [ ] At each later exit the rows whose verbs have landed are active; a row marked pending while its verb exists
      fails the script.

## Test plan

### Unit tests

The row table is data; its two helpers are tested in `scripts/lib/tests/envelope_packages_test.sh`:
`row_pending_when_verb_absent` (a row whose verb is missing from a scratch verb registry is logged pending and the
exit code is zero) and `row_must_activate_when_verb_present` (the same row with the verb present and the row still
marked pending exits non-zero naming the row).

### End-to-end script and logging

This bead is the script: `scripts/e2e/envelope_packages.sh`, with the steps and the log format above.

### Known answers and negative controls

Known answers: the class of each representative job as in the table; the boundaries 2 hours, 12, 48 and 500
device-hours; the refusal part of the envelope known answer (a job above the class in force is refused before it
starts). Negative controls, each of which must be caught: the under-declared job; the approval used outside its scope;
the planted `pass` on a declined row's gate; an approved row with an empty approver, which must fail registry load
before any job is estimated; an approved E3 row without a kill rule. Determinism lanes: the class needed is a discrete
value and must be identical twice on one machine and on both machines; debug and release builds must agree.

## Considerations

- **Two refusal codes can fire for one condition** (`FROB-REF-761` for a job above the envelope in force, and
  `FROB-REF-704` for a `campaign`-class job without an approved envelope). The script accepts either at step 2 and
  logs which fired, until the estimator's and the daemon's beads state the division.
- **Field names of the estimate's output** (class needed, class in force) are fixed by the estimator's schema; the
  script reads them through one mapping at its top.
- **A test that needs an approval is a risk**: the approved rows exist only in the scratch registry, which the script
  deletes from its own scratch directory at the end; the committed registry is never touched, and the script fails
  if its scratch directory resolves inside the repository.
- If the owner amends the classes, the boundary cases are read from the registry's class table, not hard-coded.
