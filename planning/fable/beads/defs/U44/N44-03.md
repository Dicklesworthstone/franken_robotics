## Background

A work package is the unit between a milestone and a bead: a deliverable with its crates, the gates that accept it and
the packages it waits for. The program has eighty of them, `WP-01` to `WP-80`, each an epic in this tracker. The
package table has six columns (package, name, crates, milestone, key gates, depends on), and its last column, "depends
on", is the coarse view of the bead graph. The plan's rule (DESIGN) is that after conversion to beads the table is
regenerated from the graph by transitive reduction, so that the table and the graph cannot drift. This bead builds the
regenerator. It sits in the workspace subsystem, tier Solid, milestone M0, and serves every milestone exit review,
which reads the generated table to say which packages are complete.

Why it is needed, with numbers from the table as drafted (FACT, computed from the eighty rows): the "depends on" column
has 139 edges over 80 packages, it is acyclic, and its two roots are WP-01 and WP-33. It is not transitively reduced:
14 of the 139 edges are implied by others (for example WP-10 names WP-02 and WP-09, and WP-09 already reaches WP-02
through WP-07 and WP-03), so the reduced column has 125 edges. Two edges point from a package to one whose first
milestone is later (WP-62, first milestone M3, names WP-28 and WP-61, both M4), because WP-62 lands in two parts and
only its M4 part waits for them. And the drafted assignment of beads to packages already contains bead dependencies
that run against the column: a bead of WP-23 (feasibility tags for generated scenes) depends on a bead of WP-53 (the
clearance complex), while WP-53 as a whole waits for WP-23. A hand-kept column cannot stay true under these conditions.

Two properties of this tracker shape the design. First, a blocked epic blocks every one of its children, so the order
between packages is never a blocking dependency between epics: each epic keeps its `deps` empty, and each edge of the
drafted column is a non-blocking `related` link between the two package epics. A `related` link is stored once, on
the bead whose `related` field names the other (FACT, the tracker's export: the link appears in one issue's
dependency list, with type `related`). The drafted epics store most edges on the package waited for, so an epic's own
field need not list the packages of its "Waits for" line; read as undirected links, all 139 drafted edges are present
(FACT, the staging files at round 3). The real order therefore lives only in the dependencies of child beads, and the
regenerator is the only place where the package order is computed. Second, the quotient of an acyclic
bead graph by packages need not be acyclic, as the WP-23 and WP-53 example shows, and transitive reduction is unique
only for acyclic graphs. The regenerator therefore works on package parts, one node per package and milestone, and
reports any cycle that survives that split instead of hiding it.

Alternatives rejected. (1) A seventh `xtask` subcommand: refused by the rule that `xtask` has exactly six checks and
that a new one needs a named defect class and the owner's approval; this tool also reads the tracker, which `xtask`
must not depend on. (2) A new crate: no mechanism of the product needs it, and a crate needs a contract and a chapter.
(3) Keeping the column by hand and reviewing it at each exit: this is the drift the rule exists to prevent. (4) Making
the epics depend on each other and reading the order from them: it would block all children of a package whenever
any part of an earlier package is open, which is false for multi-milestone packages.

This is non-product work, so it answers the three questions that precede such work. Which capability, defect or
blocker: the drift between the package table and the graph, which the plan itself names, and 80 `related` fields and
tables of contents drafted by hand. Is it the smallest direct action: one shell script and its tests, no crate, no
check added. Is it worth its cost now: yes, at conversion, before the first exit review reads a package as complete.

## Scope

In: the script `scripts/wp-table.sh` with its modes `generate` and `check`; the fixture of the drafted table; the
generated files `docs/delivery/work-packages.md` and `docs/delivery/work-packages.json`; unit tests on fixture graphs.

Out: the structural and coverage checks that read the generated JSON (N44-04); the end-to-end script and its logging
(N44-05); the tracker itself and its export; editing the plan document, which this tool never does: a difference
between the regenerated column and the drafted one is reported, and a plan amendment is the owner's act.

## Technical approach

**Language and layout (DESIGN).** POSIX shell driving `jq` for JSON and `awk` for the graph; no other runtime. Files:
`scripts/wp-table.sh`; `scripts/lib/wp_graph.awk` (reachability, strongly connected components, reduction);
`scripts/lib/tests/wp_table_test.sh` and `scripts/lib/tests/fixtures/wp/*.jsonl`;
`docs/delivery/work-packages.plan.tsv` (the eighty drafted rows: package, first milestone, the drafted depends-on
list; committed once and changed only by a dated plan amendment).

**Input.** The tracker's JSONL export `.beads/issues.jsonl`, one issue per line, read without invoking the tracker.
Per issue the script needs: the identifier, the external reference that carries the bead key (`BD-nnn`, `N<chapter>-nn`,
`WP-nn`, `EPIC-…`), the type, the status, the labels, the parent link, the blocking dependencies and the `related`
links. Field names are
bound in one table at the top of the script, so a change of export schema is one edit; the first run prints the fields
it found and fails if a required one is absent.

**Algorithm.**

1. Read all issues. Build `key → issue` and fail on a duplicate key.
2. Package of a bead: follow parent links upward until an issue whose key matches `WP-[0-9][0-9]`. A bead whose chain
   ends at `EPIC-M<n>` or `EPIC-PROGRAM` without passing a package has no package (milestone exit reviews, owner
   decisions held at milestone level); these are counted and listed, not treated as errors. A chain that ends
   anywhere else, or loops, is an error.
3. Milestone of a bead: its label `m0` … `m8`. A bead with no such label is an error.
4. Nodes: one part `WP-nn@Mk` for each pair (package, milestone) that has at least one bead.
5. Edges: for every blocking dependency "a needs b" where both have a package, add `part(a) → part(b)` unless the two
   parts are equal. Keep one witness per edge, the pair (a, b) smallest in key order, so every edge can be explained.
   Then add the implicit edges between parts of one package (`WP-nn@Mk → WP-nn@Mj` for j < k), witness `implicit`,
   so that a later part always follows an earlier one; they enter the graph before step 6.
6. Strongly connected components by Tarjan's algorithm, visiting nodes and successors in key order so the result is
   deterministic. A component with more than one part is a package cycle: record its members and the witnesses of its
   internal edges, then collapse it to one node named by its members joined with `+`.
7. Transitive reduction of the resulting acyclic graph: with `reach(w)` the set of nodes reachable from w by one or
   more edges, an edge u → v is removed exactly when some other successor w of u (w ≠ v) has v ∈ reach(w). For an
   acyclic graph this result is unique.
8. Package view: package P depends on package Q (P ≠ Q) when some part of P has an edge to some part of Q in the
   unreduced part graph. If the package view is acyclic, reduce it by step 7; if not, print it unreduced with the
   cycle marked. The implicit edges of step 5 are internal to a package and never appear in the package view.
9. Columns regenerated beside the order: milestones (the set of parts, first milestone first); crates (the union of
   the crate labels of the children); gates (the epic's own `gates` field as key gates, and the union of the
   children's `gates` as all gates, which is how gates defined after the table was drafted reach the table);
   children by kind (seed, new, pilot, kill-gate decision, end-to-end, upstream) with open and closed counts.
10. Write `docs/delivery/work-packages.json` (parts, edges with witnesses, cycles, package view, columns) and
    `docs/delivery/work-packages.md` (the six-column table plus a part table), both with keys sorted and a trailing
    newline, so that two runs on one export give identical bytes.

**Links between package epics.** `related` links whose two ends are package epics are read as undirected: edge P → Q
of a column is linked when P's `related` names Q or Q's names P. The set of links is compared with the drafted column
(`docs/delivery/work-packages.plan.tsv`, which the epics' `related` fields copy) and with the regenerated package
view.

**Mode `check`.** Regenerates to a scratch directory and compares. It exits non-zero on: a committed generated file
that differs from a fresh generation (stale); a duplicate key, an unknown package key, a broken or looping parent
chain, a bead without a milestone label; an edge of the drafted column that no `related` link between its two
package epics records (`related-missing`, with both keys), so that the epics' statement that the order between
packages is recorded in `related` stays true; a package cycle that survives the split into parts, when run with
`--strict-acyclic`. It reports, without failing, the differences from the drafted column (`added` and `removed`
edges with witnesses), the links between package epics that are no edge of the drafted column (`related-extra`), the
differences between the links and the regenerated package view, and each epic whose `milestone` is not the first
milestone of its children.

**Evidence class and determinism.** The outputs are bookkeeping, not evidence: they carry no claim and no gate reads
them as a measurement. Determinism: byte-identical output for a given export on any host.

## Acceptance criteria

- [ ] `scripts/wp-table.sh generate` on the loaded graph writes both files, and a second run changes no byte.
- [ ] On the fixture that encodes the drafted table as one bead per package (139 edges), the reduced package view has
      exactly 125 edges and the 14 removed edges are: WP-10→WP-02, WP-11→WP-07, WP-15→WP-07, WP-31→WP-05, WP-38→WP-07,
      WP-41→WP-10, WP-44→WP-15, WP-54→WP-24, WP-58→WP-06, WP-61→WP-48, WP-67→WP-05, WP-68→WP-13, WP-76→WP-60,
      WP-80→WP-15.
- [ ] The same fixture reports no cycle, roots WP-01 and WP-33, and a longest chain of 17 edges ending at WP-77.
- [ ] A fixture with a planted two-package cycle at one milestone is reported with both witnesses and fails
      `check --strict-acyclic`; the same cycle split across two milestones is resolved by parts and passes.
- [ ] `check` fails on a hand-edited `docs/delivery/work-packages.md` (stale output), and names the first differing
      line.
- [ ] On the loaded graph every one of the 139 drafted edges is recorded by a `related` link in one direction or the
      other (`related-missing` is empty); with the link WP-01–WP-02 removed from a fixture, `check` fails naming both
      keys, and a link stored on either end satisfies it.
- [ ] Every edge in the JSON carries a witness pair of bead keys that exists in the export.
- [ ] The script contains no call to the tracker binary and writes nothing outside `docs/delivery/` and its scratch
      directory.
- [ ] No `xtask` subcommand is added: the change touches no file under `xtask/` (the count of exactly six is BD-004's
      test, which this bead does not wait for; once it exists it keeps passing).

## Test plan

### Unit tests

In `scripts/lib/tests/wp_table_test.sh`, run directly (`sh scripts/lib/tests/wp_table_test.sh`) and by the
pre-commit recipe `scripts/precommit.sh` of N34-15 once it exists; real `jq` and `awk`, fixtures labelled
`synthetic`.

- `tr_chain`: beads a→b→c plus a→c in three packages; expected reduced edges {A→B, B→C}; A→C removed.
- `tr_diamond`: A→B, A→C, B→D, C→D, A→D; expected removal of A→D only (four edges remain).
- `tr_keeps_parallel_paths`: A→B, A→C, B→D, C→D with no A→D; nothing removed.
- `plan_table_reduction`: the 80-package fixture; 139 edges in, 125 out, the 14 named removals, no cycle.
- `parts_resolve_two_milestone_package`: package X has beads at M3 and M4, package Y at M4, with X@M4→Y and Y→X@M3;
  expected: no cycle at part level; package view marks X↔Y as a cycle and prints it unreduced.
- `planted_cycle_reported`: X@M2→Y@M2 and Y@M2→X@M2; expected one component {X@M2, Y@M2} with two witnesses.
- `no_package_beads_counted`: three beads under `EPIC-M1` only; expected count 3 in `unpackaged`, exit zero.
- `broken_parent_chain_fails`: a bead whose parent key does not exist; expected non-zero exit naming the bead.
- `missing_milestone_label_fails`: expected non-zero exit naming the bead.
- `deterministic_bytes`: the fixture's lines shuffled; expected identical output digests.
- `witness_is_smallest_pair`: two bead pairs induce one edge; the witness is the pair smaller in key order.
- `implicit_edges_order_parts`: package X has beads at M1, M3 and M5 and no dependencies; expected part edges
  X@M3→X@M1 and X@M5→X@M3 with witness `implicit` (X@M5→X@M1 removed by the reduction), and no edge from X to X in
  the package view.
- `related_links_undirected`: drafted edges A→B and B→C; A's `related` names B and C's names B; expected
  `related-missing` empty and exit zero (each edge is linked on one end or the other).
- `related_missing_fails`: the same fixture with C's link removed; expected non-zero exit and one `related-missing`
  line naming B and C; an added link A–C, which is no drafted edge, is reported as `related-extra` without failing.

### End-to-end script and logging

`scripts/e2e/wp_table.sh`, specified in N44-05, runs `generate` and `check` on the real export and logs through the
shared helper of STD-E2E to `target/e2e-logs/wp_table/<utc>.ndjson`.

### Known answers and negative controls

Known answers: the reduction of the drafted table (139 → 125 edges, 14 named removals, longest chain 17, roots WP-01
and WP-33), and the three small graphs above, all exact. Negative controls, each of which must make a test fail: a
reduction that tests v ∈ reach(u) instead of v ∈ reach(w) for another successor w, which removes every edge (in
`tr_keeps_parallel_paths` it leaves zero edges where four are expected); a reduction run on a graph with an
uncollapsed cycle (non-unique result, caught by `planted_cycle_reported`); output that depends on input line order
(caught by `deterministic_bytes`); a comparison that reads `related` as directed, which reports most drafted edges
missing (caught by `related_links_undirected`). Metamorphic
relation: adding an edge that is already implied changes no reduced edge; removing a bead dependency that was the only
witness of an edge removes exactly that edge or reveals a previously implied one.

## Considerations

- **The export's field names are not fixed by the plan.** They are bound in one table and verified on the first run.
  If the tracker later offers a stable machine-readable graph view, the script reads that instead and the binding table
  shrinks.
- **Package cycles are information, not failures.** Each one means either that a bead sits in the wrong package or
  that a package must be read in parts. The default mode reports them; only `--strict-acyclic` fails, and exit
  reviews decide whether to run it.
- **Hygiene.** Every registry and generated file must have a named reader or be deleted. Readers here: the milestone
  exit reviews (package completeness), N44-04 (coverage and structure checks) and the epics' `related` fields. If
  none of them reads the files by the M1 exit, the script is deleted and the column is dropped from the table.
- **No private data** enters the files: keys, labels, counts and gate identifiers only.
- **What would make us revisit**: more than a handful of cycles surviving the split into parts, which would mean the
  membership rule (one package per bead, by crate at its milestone or by the crate where its gate is measured) is
  wrong for whole chapters and should be re-read by the owner.
