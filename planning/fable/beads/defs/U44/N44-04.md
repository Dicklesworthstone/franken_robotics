## Background

The eighty work packages are the map between the program's nine milestones, its 43 crates and its beads. The plan
states five things about that map that can be checked mechanically, and none of them is checked by anything else:

1. **Coverage** (DESIGN): every crate of the crate map has at least one package, and every milestone has at least one.
2. **Counts** (FACT about the table): counting a package at its first milestone there are ten at M0, fifteen at M1,
   eighteen at M2, fourteen at M3, eight at M4, five at M5, four at M6, two at M7 and three at M8; WP-69 is tied to no
   milestone; of the eighty, thirty-three are carried from the earlier version of the plan (WP-01 to WP-33) and
   forty-seven are new (WP-34 to WP-80).
3. **Membership** (DESIGN): a bead belongs to exactly one package, the one that owns its crate at its milestone or,
   where a bead touches several crates, the one that owns the crate in which its gate is measured. Milestone exit
   reviews belong to none.
4. **Upper tiers** (DESIGN): a tier tag on a package name marks Frontier or Moonshot content; that part of a package is
   funded only after its paper-scale pilot is on record, and its kill gate is decided at the milestone the register
   names. At most four Moonshot items are active at once in any milestone.
5. **Upstream work** (DESIGN): upstream work items are not a package of their own. Each is a bead labelled `upstream`
   inside the package whose gate its switch-over rule re-runs, done in the sibling's repository. The two items of
   priority P0 sit in WP-02 (FD-ASUP-01, one asupersync version across the siblings) and WP-06 (FD-FMCP-01,
   fastmcp_rust brought onto the one toolchain T).

This bead turns the five statements into checks over the loaded bead graph, with a planted defect for each. It sits in
the workspace subsystem, tier Solid, milestone M0. It serves the guard against false progress: a package that looks
complete because its beads are closed, while a crate it owns has no bead, or a Frontier mechanism was started with no
pilot, is exactly the failure the program's hygiene rules were written against.

Alternatives rejected: adding these checks to `xtask` (the six-check cap, and `xtask` must not read the tracker);
checking by review at each exit (the statements are exact and a script is cheaper and does not tire); folding them
into the regenerator of N44-03 (that script computes; this one judges, and its planted defects must not be able to
break generation).

## Scope

In: `scripts/wp-check.sh`, its fixtures (the coverage table below as `docs/delivery/work-packages.coverage.tsv`, and
the envelope fixture of check 11 as `docs/delivery/work-packages.envelope.tsv`), and its tests. Out: generation of
the table (N44-03); the end-to-end run on the real graph with logging (N44-05); the envelope register's content and
its reservation table (N44-01, a dependency: check 11 reads the rows R1 to R11 it writes, so the check on the loaded
graph has a register to read); the registry check that a gate has a negative control, which the conformance harness
owns (BD-025).

**The checks.** Each prints one line per violation with the keys involved, and the script exits non-zero if any
check marked *fails* has a violation.

1. `wp_keys_complete` (*fails*): the package epics are exactly `WP-01` … `WP-80`: eighty, no gap, no extra; 33 with
   number at most 33 and 47 above.
2. `wp_epic_shape` (*fails*): each package epic has type `epic`, an empty list of blocking dependencies, a parent
   `EPIC-M<n>` equal to its first milestone (WP-69, tied to no milestone, is filed under `EPIC-M5`), and a `related`
   list that contains only package keys.
3. `wp_milestone_counts` (*fails*): by first milestone the counts are 10, 15, 18, 14, 8, 5, 4, 2, 3 for M0 to M8
   with WP-69 excluded; every milestone has at least one package.
4. `wp_children_have_one_parent` (*fails*): every bead has one parent chain; it reaches exactly one package or none;
   the beads with none are listed. The nine milestone exit reviews (BD-044, BD-147, BD-224, BD-319, BD-378, BD-412,
   BD-427, BD-434, BD-442) must have none.
5. `wp_crate_coverage` (*fails* for a crate with no package or no bead; *reports* pairs outside the fixture): for
   every crate of the fixture, at least one package has a child bead that carries the crate's label; a child bead
   whose crate label names a crate that the fixture does not list for its package is reported as an uncovered pair,
   which is how a wrong package assignment shows.
6. `wp_gate_ids_exist` (*fails*): every identifier in a package epic's `gates` field is a row of
   `registries/gates.toml`, and each key gate of a package is measured by at least one child bead (a child names it in
   its own `gates`) or, where one bead covers the gate for several packages, by a bead of another package (or of no
   package) that names the gate in its own `gates` and that the epic's description names by key (DESIGN: for example
   GATE-SPARK-06 on WP-19, whose Metal rows are measured by BD-175 in WP-18 and N21b-25 in WP-46, both named on the
   gate's line of WP-19). The second case prints a `measured-elsewhere` line with the bead keys and does not fail; a
   key gate that no child measures and whose measuring beads the epic does not name fails, naming the gate and the
   beads that do measure it. DESIGN: the key gates of a package are every identifier of its `gates` field, kill gates
   included; a kill gate is measured by the bead that names it in its own `gates` (its decision bead, or the bead that
   produces the measurement it decides on). "Names by key" means anywhere in the epic's description: an acceptance
   line, a Considerations bullet or a member line. A package epic or a milestone epic is never the measuring bead,
   even when its own `gates` lists the gate, so an epic that names only another package cannot pass the check.
7. `wp_tier_tag_has_pilot` (*fails*): for each package with at least one child labelled `frontier` or `moonshot`,
   every such child that is not itself labelled `pilot`, `kill-gate`, `registry`, `owner-decision` or `exit-review`
   has a blocking path to a bead labelled `pilot` (in any package). The thirty packages whose names carry a tier tag
   are checked by name as well: [S],[F] on WP-27, -28, -29, -30, -44, -50, -53, -55, -62; [F] on WP-31, -32, -42, -46,
   -57, -59, -61, -64, -65, -66, -67, -68, -70, -71, -72; [F],[M] on WP-73, -74; [M] on WP-75, -78, -79, -80. A
   package whose children carry an upper tier while its name carries no tag is reported (not failed), so the table
   regenerated by N44-03 can print the tag from the children.
8. `wp_kill_gate_milestone` (*fails*): every child labelled `kill-gate` names a kill gate of the register, and its
   milestone label equals a decision milestone the register gives for that gate.
9. `wp_moonshot_cap` (*fails*): per milestone, the number of beads labelled `moonshot` and of type epic that are in
   progress is at most four.
10. `wp_upstream_placement` (*fails*): every bead labelled `upstream` has a package; FD-ASUP-01 is under WP-02 and
    FD-FMCP-01 under WP-06; no package has only upstream children.
11. `wp_envelope_packages` (*fails*): (a) the packages named by rows R1 to R10 of the envelope register (N44-01) are
    exactly WP-21, -28, -34, -44, -47, -48, -53, -55, -60, -61, -62, -76, -77 and -79, row by row as in the fixture,
    and R11 names WP-35; (b) a row R12 to R28 that is present names the packages of its reservation; (c) every
    package named by any row of the register, and every package of a reservation, has an epic whose Envelope bullet
    cites that row's identifier and its class; (d) every row identifier an epic cites is in the register or in the
    fixture. The expected set is therefore derived from the register and the fixture, and a filed reserved row needs
    no change here; a new row from R29 on is covered by (c) and (d) alone.
12. `wp_package_complete` (*reports*; *fails* with `--declare-complete WP-nn`): a package may be declared complete
    only when every child is closed, no two children share a close reason, and every key gate has a row with status
    `pass` or `killed: fallback adopted`. `not run` is not a pass.

**Determinism.** Output lines are sorted by check name and key; two runs on one input are byte-identical.

## Considerations

- **The drafted tier tags are incomplete, by the drafted beads' own labels.** Some untagged packages hold Frontier
  mechanisms with kill gates (for example campaign quotienting and paired design gradients in WP-63, the dashboard in
  WP-52, the derivation annex in WP-05), and WP-46 is tagged [F] while its M2 services are Solid. Check 7 therefore
  keys on the children's labels and only reports a name without a tag.
- **Coverage is by label, so labels must be right.** A bead with no crate label is invisible to check 5; the check
  lists beads under a crate-owning package that carry no crate label, and that list should be empty by the M1 exit.
- **Exceptions are visible.** An accepted exception is a row in a committed file, never a flag on the command line.
- **Hygiene.** The readers of this script's output are the exit reviews and N44-05. If no exit review cites it by
  the M1 exit, it is deleted with N44-03.
- **Open point for the lead**: WP-69 has no milestone in the table and is filed under M5 because the lane that would
  receive its data lands there; if the tracker gains an "unscheduled" bucket, checks 2 and 3 change one line.
