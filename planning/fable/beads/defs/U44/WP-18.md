## Background

**The row.** WP-18: CUDA backend. Crates: `spark/frob-spark-cuda`. Milestone: M2. Key gates: GATE-SPARK-02, -03, -06.
Waits for: WP-04, WP-15.

The CUDA backend runs the M2 kernels and the full step on the two RTX 4090 of `trj`, which is the training tier. The
package delivers device buffers, the step plan (`frob.stepplan/1`), launch-graph capture, stream-ordered pools,
receipts, and the handling of device faults and cancellation.

It is one unit of work because a backend is accepted as a whole on three counts: it agrees with `batch-cpu` inside its
declared determinism class, it meets the CUDA performance rows against the incumbent measured on the same card, and it
survives fault injection and cancellation without leaking device memory.

**Order.** It waits for WP-04 (the annex at version 0 and the admission of `cudarc`) and WP-15 (the kernels and the
step it must run and be compared with). (The order between packages is recorded in `related`, never in `deps`: a
blocked epic would block every child, so the child beads carry the real dependencies.)

## Test plan

### Unit tests
None of its own: the children's tests run beside the code with `cargo test -p <crate>`, without mocks. The package's
structural tests are in N44-04 (`wp_children_have_one_parent`, `wp_gate_ids_exist`, `wp_tier_tag_has_pilot`).
### End-to-end script and logging
The children's scripts under `scripts/e2e/` demonstrate the package through the real `frob` binary, with the
structured logs of STD-E2E. `scripts/e2e/wp_table.sh` (N44-05) prints this row with its children, the open count and
each gate's status, and fails if a gate above has no record when the package is declared complete.
### Known answers and negative controls
Carried by the children and their chapter registries. A gate above counts only when its registered negative control
has been shown to fail (GATE-GAUNT-01).

## Considerations

- **Envelope.** No request above the default E0 (16 GiB, 8 cores, one hour, one device) is registered. The
  measurements of GATE-SPARK-03 that use both cards or all cores are requested by the row of WP-34 and WP-47 (class E1
  per gate); under E0 only the single-card and eight-core rows run and the others are recorded `not run`.
- **KILL-D1** (decided at M2, in WP-46) reads GATE-SPARK-02 on this backend: a device family that cannot hold bit
  equality with `batch-cpu` becomes class D2 for itself and D3 against others.
- **KILL-PARITY** (decided at M2, in WP-47) reads the physics rows measured here: below 0.33 of the incumbent on the
  same card after one profile-guided pass, feature work on the device tier stops.
- OPEN-SPARK-1 and OPEN-SPARK-4 apply as in WP-04: until ADR-SPARK-01 is ratified, device results are labelled
  exploratory.
- The drain report after a cancel must be minted by the executor, not by the backend that is being drained.
