## Background

How many worlds fit on a device? The cost and memory model behind `sim.estimate` answers before anything is
allocated: a job whose memory estimate exceeds the device budget is refused at admission (FROB-REF-602), and a
population whose bytes exceed every admitted placement is refused (FROB-REF-740). GATE-SPARK-22 checks the
model against measured allocations. The model's per-world byte count depends on the robot's size and on two
default capacities, the contact capacity C and the constraint-row capacity R, which are DESIGN defaults frozen
at M2 (the performance chapter's values govern: C = 32, R = 160 for the reference quadruped and C = 64, R = 320
for the humanoid; an older pair of values in the dynamics chapter was reconciled to these). The card shows that
memory admits ten to a hundred times more worlds than the throughput targets use, that the dense Jacobian is a
third to a half of the bytes, and where the conclusion flips. Tier: Solid. Subsystems: Spark, Kinesis.

## Scope

In: `registries/cards/GB-41.toml`; test `gb_41`; controls. Out: the `sim.estimate` cost and memory model
(BD-219, N16b-26); the population memory model (N17a-07); the capacity freeze (N21b-18); the record of the
capacity reconciliation (NEG-11); scene memory (GB-07).

## Technical approach

**Equation.** Bytes per world in `f32` with a dense Jacobian:
B = 4·(61·n_b + 17·n) + 12·n² + 4·R·n + 48·R + 96·C + state, for n degrees of freedom, n_b bodies, contact
capacity C and row capacity R; the terms are the kinematic cache, the mass matrix with Hessian and factor, the
dense Jacobian, per-row data, per-contact data, and a few kilobytes of state. PPO rollout storage:
4·T·(observations + privileged observations + actions + 4) bytes per world for horizon T. The optional
hard-contact operator adds 4·R².

**Substituted (illustrative byte model, with one FACT), with goldens.**

| Output | Quadruped (n = 18, n_b = 13, C = 32, R = 160) | Humanoid (n = 35, n_b = 30, C = 64, R = 320) | Tolerance |
|---|---|---|---|
| Cache 4·(61·n_b + 17·n) | 4,396 | 9,700 | count |
| 12·n² | 3,888 | 14,700 | count |
| Jacobian 4·R·n | 11,520 | 44,800 | count |
| 48·R | 7,680 | 15,360 | count |
| 96·C | 3,072 | 6,144 | count |
| Sum without state | 30,556 | 90,704 | count |
| With about 4,000 and 6,000 bytes of state | 34,556 (printed 35 kB) | 96,704 (printed 97 kB) | count |
| 8,192 worlds | 0.2831 GB (printed 0.28) | 0.7922 GB (printed 0.79) | rel 10⁻⁴ |
| Share of a 24 GB card | 1.2% | 3.3% (printed "1 to 3%") | — |
| Jacobian share of bytes | 0.3334 | 0.4633 ("a third to a half") | rel 10⁻⁴ |
| Hard-contact operator 4·R² | 102,400 (102 kB) | 409,600 (410 kB) | count |

| Output | Golden | Printed |
|---|---|---|
| Rollout storage, T = 24, 48 observations, 187 height samples, 12 actions | 4·24·251 = 24,096 bytes | 24 kB per world |
| Worlds on 16 to 19 GB usable, quadruped at 35 kB | 457,143 to 542,857 | 0.46 to 0.55 M |
| Same, humanoid at 97 kB | 164,948 to 195,876 | 0.17 to 0.20 M |
| FACT: an incumbent's measured humanoid world at 8,192 worlds | 88.4 kB | 88.4 kB |
| Flip: 256 designs × 2,048 rollouts | 524,288 worlds; 18.35 GB at 35 kB | 18.4 GB |

**Intuition.** Memory admits ten to a hundred times more worlds than the throughput targets use. The dense
Jacobian is a third to a half of the bytes, so row capacity decides memory, and the bytes touched per step
decide speed.

**Assumptions.** A dense Jacobian; the capacities above, which are DESIGN defaults frozen at M2; scenes that
are shared and never one per world.

**Flip.** Sampling control per design multiplies worlds by the sample count: 256 designs × 2,048 rollouts is
524,288 worlds, 18.4 GB at 35 kB, at or beyond what one card has usable. The path-table Jacobian replaces R·n
by about R·(6 + depth) and removes most of the largest term.

**Lane A.** Integer arithmetic for every term.

**Lane B.** `sim.estimate` for the two reference workloads returns each term by name with these byte counts
and the total; the packed lowering's actual buffer sizes for a `synthetic` 18-degree-of-freedom, 13-body model
at C = 32, R = 160 equal the model's terms exactly (the estimate is computed from the same layout table, not
from a separate formula); for 524,288 quadruped worlds on a device whose budget is 16 GiB (about 18.1 GB of
estimate against 17.2 GB of budget) `sim.estimate` returns the finding `fits: false` with exit code 2,
`largest_worlds_that_fit` and the Jacobian as the largest entry of `memory.by_class`, and a run verb asked for
the same worlds is refused at admission with FROB-REF-602, exit code 6, before any device allocation (the
device's allocated-bytes counter unchanged; the device-fit test precedes the compute-envelope check, so this job,
which also exceeds E0's 16 GiB, is refused with 602 and not with FROB-REF-761), with BD-219's ranked repairs (fewer worlds, naming the largest
count that fits; a smaller capacity; the Mac); with the step plan's path-table layout the record's
`jacobian_layout` and Jacobian term change accordingly (the Flip); a population that fits no admitted
placement is refused with FROB-REF-740.

## Test plan

### Unit tests

- `gb_41_reference_terms`, `gb_41_reference_totals`, `gb_41_reference_rollout`, `gb_41_reference_world_counts`.
- `gb_41_mechanism_estimate_terms`, `gb_41_mechanism_layout_equals_estimate`, `gb_41_mechanism_estimate_fits_false`
  (exit 2), `gb_41_mechanism_602` (run verb, exit 6, nothing allocated), `gb_41_mechanism_740`.
- `gb_41_scaling`: doubling R doubles the Jacobian and row terms and quadruples the hard-contact operator.
- `gb_41_controls`: (a) the older capacities give 25,948 and 70,352 bytes before state (27 kB and 72 kB as
  first printed) and must miss the goldens; (b) a model that omits the Jacobian term under-estimates by a third
  to a half and fails the layout-equality test; (c) one scene per world added to the per-world bytes (75 MB,
  GB-07) is rejected: scenes are shared.

### End-to-end script and logging

NEG-02's script (`scripts/e2e/worked_cards.sh --card GB-41`) calls `frob sim estimate --workload Q --worlds 8192
--json` and `--workload H` (the workload form that
N36-33's resolver expands, BD-219), compares per-term bytes and totals, then asks `frob sim estimate --workload
Q --worlds 524288 --json` on the 16 GiB device and expects `fits: false` with exit code 2, and the run verb in
its registry form, `frob sim run <quadruped> --worlds 524288 --seconds 1 --tier <device> --key <k> --json`, on
the same device and expects FROB-REF-602 with exit code 6; logs the exact command lines, exit codes, each term,
the budget and the refusal payload.

### Known answers and negative controls

KA-814: per-world byte model in `f32` for Q (18 degrees of freedom, 13 bodies, C = 32, R = 160) and H (35, 30,
C = 64, R = 320): cache 4,396 and 9,700; mass matrix, Hessian and factor 3,888 and 14,700; and the remaining
terms as above. Determinism: integer arithmetic, D0.

## Considerations

- The state term ("a few kilobytes") is the only non-closed-form part; the estimate reports it from the layout
  table, and the card's 4,000 and 6,000 are illustrations.
- Gigabytes are 10⁹ bytes in this card; device budgets are stated in gibibytes and the verb prints both.
