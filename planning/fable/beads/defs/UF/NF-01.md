## Background

FrankenRobotics consumes its sibling projects at exact pins. `franken-stack.lock` holds one `[[foundation]]` row
per sibling (`id`, `posture`, `path`, `git_rev`, `toolchain`, `features`, `build_env`, `confined_to`,
`admission_gate`, `receipt`, `fallback`), and `cargo xtask check-stack` compares that lock with the tracked
lockfiles, the toolchain files and the sibling heads. A pin is a statement of intent; what was built is a
different fact, recorded in a **resolution receipt** (`frob.stack-receipt/1`, canonical JSON under `receipts/`,
named by its BLAKE3 hash).

The siblings do not hold still. FACT: 409 commits touched FrankenSim's `crates/fs-mbd` in the thirty days to
2026-11-21, on 17 distinct days; its composition contract is at version 0; its own constellation lock was stale.
Every upstream work item of this program (the `FD-…` beads) also ends with a pin move. DESIGN: a pin advances
only through a **compatibility train**: move the pin, write a new receipt, re-run the admission and parity
gates, relock. This bead turns that sentence into a procedure that an agent can run without judgment calls, a
script that enforces its guards, and a log from which the cost of consumption is measured.

Why a train and not something lighter. Rejected: floating on a sibling's `main` (no result could be reproduced,
and two results could not be compared as results of one stack); rolling a sibling's checkout back to an old
commit when its head breaks us (the checkouts are shared with other agents and with the sibling's own work; a
sibling's newer clean head is never rolled back locally); a local patch or fork to get past a breakage (it
diverges from the sibling's head and does not survive the next pin move); inheriting an admission across a pin
(an admission is never inherited: a record is valid only for the commit it cites).

The train also produces the number that one of the program's bets is judged by. BET-04 (FrankenSim can be
consumed by path from outside its tree, stably) is falsified, and kill gate KILL-FSIM fires, if upstream
breakage costs more than 20% of working days in any four-week window.

## Technical approach

**Terms.** A sibling's drift class, as `check-stack` reports it: `on-pin` (head equals `git_rev`, tree clean);
`stale-lock` (the checkout is a fast-forward of the pin); `drift` (dirty, retreated or diverged). The same three
classes are applied to the sibling's own lock (`constellation.lock`, `SUITE.lock`) against what it builds.

**Procedure `train(S, C)`: advance sibling S to commit C (DESIGN).**

1. *Preconditions, each a refusal of the script if false.* (a) No freeze is in force: `franken-stack.lock` holds
   no `[freeze]` table whose `closed` field is empty (the table is opened and closed, as recorded commits, by
   the tournament freeze of the stack lock, bead N33b-03, for the length of a ten-fold tournament; it names the
   campaign and the frozen receipt). (b) This repository's tree is clean and its last receipt verifies.
   (c) C is a commit on S's `main`, and the present pin is an ancestor of C (`git merge-base --is-ancestor`): a
   pin only moves forward. (d) S's checkout is at C and clean. The script never checks out, fetches into, resets
   or otherwise writes to a sibling checkout (INV-SUITE-04); bringing the checkout to C is done by whoever works
   in that repository. A dirty tree admits development builds only, and the train stops with class `drift`.
2. *Coupled siblings.* If S's own lock at C names other consumed siblings (FrankenSim's constellation names
   asupersync, FrankenSQLite, FrankenTorch, franken_numpy and frankenscipy), each is classified against that
   lock. A coupled sibling that must move moves in the same train; one that disagrees and cannot move stops it.
3. *Move the pin.* In the row of S set `git_rev = C` and `toolchain` to the channel of S's own toolchain file at
   C. Regenerate the tracked lockfiles of every workspace (the core and `worker/`).
4. *Receipt.* `cargo xtask check-stack` writes the new receipt: revisions, `dirty`, features, the hash and class
   of each sibling's own lock, lockfile hashes with package and registry counts, patches, profile overrides,
   build environment, duplicates, and the commands run with output hashes. Paths in it are repository-relative.
5. *Build on T.* `cargo check --workspace --all-targets --locked`, recording cold and warm times, peak memory
   and package count against the machine envelope (one hour, 16 GiB, 8 cores).
6. *Re-run the gates, each citing the new receipt.* (i) Every admission gate that has a record for S, at the new
   pin (for FrankenSim: INT-FSIM-01 with the G1 digest recomputed inside FrankenSim at C, the file-by-file tests
   INT-FSIM-02 to -11, the group gates already in use, INT-FSIM-18 with the worker rebuilt). (ii) The parity
   gates that have S on their path (GATE-KIN-02, GATE-KIN-03, GATE-TRAC-02 for FrankenSim; GATE-SPARK-02 and
   GATE-CORTEX-02 for FrankenTorch). (iii) The foundation-fact probes (GATE-WS-06, GATE-WS-09): a probe that now
   passes upstream is recorded as fixed and its interim posture is reviewed. (iv) Every fixture under
   `tests/upstream/`: one that flipped from failing to passing means its upstream item has landed; its row
   becomes `landed` and its own switch-over rule is run in this train. (v) The six `xtask` checks.
7. *Relock and record.* One commit holds `franken-stack.lock` with the row's `receipt` hash, the lockfiles, the
   receipt file and a `DEPENDENCY_ADMISSION.md` record (this repository's commit, the commands, output hashes,
   measured values, the receipt hash). Append one line to `receipts/train-log.ndjson`.
8. *If any step from 5 on fails.* The train is abandoned: this repository's lock, lockfiles and receipt return
   to the previous state (the sibling is not touched), the failure is logged with the failing gate, and the
   remedy is one of: an adapter change in `frob-fsim` (a FrankenSim API change costs one crate); an upstream work
   item; or, when the trigger below is met, KILL-FSIM's fallback.

**Consequences a pin move has elsewhere.** Memoized referee results carry the stack-lock digest in their key, so
none is served across a pin. Results in the Chronicle ledger carry the receipt hash of the binary that produced
them; offering evidence from another receipt as same-stack evidence without revalidation is refused
(`FROB-REF-890`, `stack-mismatch`). A referee worker built under another receipt refuses jobs (`FROB-REF-791`,
`referee-worker-mismatch`). The frozen envelopes of the fidelity ledger are not re-baselined by a train unless
the upstream item being adopted says so (FD-FSIM-02 and FD-FSIM-12, once each, with a written rationale).

**Train log (DESIGN), `receipts/train-log.ndjson`, one line per train:** `date`, `sibling`, `from_rev`, `to_rev`,
`class_before`, `outcome` (`adopted` or `abandoned`), `failing_gate`, `adapter_lines_changed`, `upstream_items`
(those adopted), `receipt`, `wall_seconds`. From it the script prints `breakage_share_28d`: the number of
working days in the last four weeks on which a train was abandoned or the build was broken by a sibling head,
divided by the working days in the window.

**Kill gate KILL-FSIM (decided at M0, then rolling).** Trigger: INT-FSIM-01 cannot pass within two weeks of M0
effort, or its cold check exceeds the machine envelope, or `breakage_share_28d` exceeds 0.20. Fallback (a): the
volatile crates move behind a process boundary, one pinned FrankenSim worker per device exchanging whole jobs
through the same airlock traits; the worker can stay on an old pin while the core moves. Fallback (b), only if
(a) fails INT-FSIM-18 or the pin can no longer be built on any available toolchain: lift the minimal referee
set with provenance headers and golden tests, state "lift-only" in the README, and keep the upstream items open.
This bead supplies the measurement; the decision is an ADR.

## Test plan

### Unit tests
In `xtask/tests/train_guards.rs`, driving the real script against real git repositories created in a temporary
directory (each labelled `synthetic`: a stand-in sibling with one crate and a toolchain file; no mocks):
- `refuses_backward_move`: pin at commit 3 of 5, target commit 2; expected refusal `not-a-descendant`, exit non-zero, no file changed.
- `refuses_diverged_target`: target on a side branch not containing the pin; expected the same refusal.
- `refuses_dirty_sibling`: one tracked file touched in the sibling; expected class `drift`, refusal, and the receipt (if computed) with `dirty: true` and a changed `tree_hash`.
- `refuses_under_freeze`: the stack lock holds a `[freeze]` table with an empty `closed` field; expected refusal `frozen` naming the campaign and the frozen receipt.
- `abandons_and_restores_on_gate_failure`: the stand-in's commit 4 changes a function's result that a stand-in gate checks; expected outcome `abandoned`, lock and lockfiles byte-identical to before.
- `adopts_fast_forward`: target commit 5 that passes; expected new receipt, row `receipt` equal to its hash, one `adopted` log line.
- `writes_nothing_to_sibling`: the sibling directory is made read-only; `adopts_fast_forward` still passes.
- `breakage_share_known_answer`: a log with 20 working days of which 5 have an abandoned train; expected 0.25, above the 0.20 trigger; with 4, expected 0.20, not above it.
- Property test for INV-SUITE-03: over 200 random sequences of (touch, commit, train) operations, no adopted line cites a receipt whose sibling entry is dirty.

### End-to-end script and logging
The rehearsal `scripts/e2e/train_rehearsal.sh` is NF-06 and depends on this bead. This bead's own script logs in
the same form when run for real: one NDJSON line per step of the procedure, with the command, exit code, wall
time, the receipt hash before and after, the drift classes, the measured build times and peak memory against
the envelope, and the names and results of the gates re-run.

### Known answers and negative controls
- KA-767: a receipt computed twice on an unchanged tree is byte-identical; touching one tracked file in a sibling flips `dirty`, changes `tree_hash`, and `check-stack` fails. The train's step 4 is run twice in the test and compared.
- Negative controls: each guard test above is a planted violation the script must catch; in addition, a train run with the row's `receipt` left at the old hash must fail `check-stack` (the stale-stack-lock plant of GATE-WS-01).
- Metamorphic relation: two trains to commits 4 then 5 leave the same lock, lockfiles and receipt as one train to commit 5 (the log differs by one line).
- Determinism lanes: the receipt is identical when the train is run twice from the same starting state, and on Linux and macOS (it holds no machine path).

## Considerations

- RISK-01 (FrankenSim API churn in `fs-mbd` and the `Component` trait): earliest signal is adapter lines changed per pin move and the breakage share, both in the train log. Mitigations: the airlock, the pin, this train, FD-FSIM-08, KILL-FSIM with the worker first.
- RISK-23 (dirty or off-pin sibling trees make a receipt unrepeatable): the receipt hashes tracked bytes when a tree is dirty, and no gate records a PASS on one. OPEN-SUITE-3 (owner): a dirty asupersync checkout is acceptable for development builds between receipts and for nothing else; that is the default until decided.
- The cold build of the M1 closure is 65 crates and about 2.06 million lines (FACT), so a full train is not free. OPEN-SUITE-5 (owner): the budget is the machine envelope until decided. A train that re-runs only the gates on S's path is allowed; skipping a gate on S's path is not.
- A train is also the moment a sibling's fix is noticed: step 6 (iv) is how an upstream item becomes `landed` without anyone remembering to check.
- Pins of every arm and every sibling are frozen for the length of the M7 tournament, because a ratio of times measured across a pin move is not one measurement; a train run during a freeze would void the tournament, which is why the freeze guard is a refusal and not a warning.
- The freeze record is declared by the tournament freeze of the stack lock (N33b-03): a `[freeze]` table in `franken-stack.lock` with `campaign`, `receipt`, `opened`, `closed` and `reason`. This procedure only reads it, and refuses with the message `check-stack` gives while frozen ("stack frozen for campaign <id>: <what moved>"); if the record's form changes, only guard (a) changes.
