## Background

The whole build graph of FrankenRobotics uses **one Rust toolchain, T**: the core, the GPU annexes
(`spark/frob-spark-cuda`, `spark/frob-spark-metal`), the derivation tool (`derive/frob-derive`) and the MCP
server (`surface/frob-mcp`). T is recorded twice, in `franken-stack.lock` (`toolchain = "<T>"`) and in the one
`rust-toolchain.toml` at the workspace root. No annex carries a toolchain file of its own; `lean/` is not Rust and
keeps its own toolchain; `frob-cert` builds on T in the graph and also alone on a stable release.

The siblings start apart. FACT (read 2026-11-21): four nightlies and one stable release are in play:
`nightly-2026-07-06` (frankensim, rustc 1.99.0-nightly), `nightly-2026-08-20` (frankensympy), `nightly-2026-08-25`
(fastmcp_rust, which also declares `rust-version = "1.100"`), `nightly-2026-08-31` (asupersync, frankensqlite,
frankentorch, franken_numpy, frankenscipy, franken_lean, frankentui, franken_threed, frankenjax, the drone
reconstruction project, franken_textiles), and stable 1.99.0 (franken_firmware, a pattern only).

T is chosen once, at gate INT-TOOLCHAIN-01 (BD-031), in this order of preference: (a) the suite's common
nightly, `nightly-2026-08-31` on the day of writing; (b) FrankenSim's present pin, if FrankenSim cannot yet build
on (a). After that gate, DESIGN: **T moves only by a toolchain train**: one coordinated change that moves T in
this repository and in every consumed sibling that needs it, followed by the admission and parity gates.

Why one coordinated change. Rejected: per-annex toolchain files (withdrawn by the owner's ruling of 2026-11-22;
two compilers in one product means two sets of bugs and no single statement of what was built); letting a
sibling's toolchain drift from T while this repository builds its code on T (the sibling's own gates then test a
different compiler from the one that ships its code here); moving T first and repairing siblings afterwards (a
blocked merge with nothing to fall back to: premortem story 25).

A named hazard rides on every train. `fs-qty`, FrankenSim's units crate, enables `generic_const_exprs`, a
nightly feature the compiler marks incomplete (FACT: `frankensim/crates/fs-qty/src/lib.rs:20–21`), and nearly
every physics crate depends on it. A train to a nightly on which that feature has regressed breaks one crate and
with it the graph (RISK-21).

## Scope

In: the procedure (`docs/runbooks/toolchain-train.md`); the script `scripts/train/toolchain_train.sh`; the matrix
re-run with the candidate as a new column; the rules for sibling legs; the `fs-qty` decision rule at a train;
guards and tests. Out: choosing the first T and the first matrix (BD-031); the first train's legs (FD-FMCP-01 in
fastmcp_rust, NF-03 in frankensim, NF-04 in frankensympy) and its run (NF-05); pin moves that do not change T
(NF-01); creating `frob-units` (decided by BD-031's rule; built only if forced).

## Technical approach

**When a train runs.** (i) T was chosen as candidate (b) and the scheduled move to (a) is due because FrankenSim
now builds on (a). (ii) The suite's common nightly has advanced and the consumed siblings are moving to it. (iii)
A crate in the graph needs a newer compiler than T. Never during a tournament freeze, and never as a side effect
of a pin move.

**Procedure `toolchain_train(T′)` (DESIGN).**

1. *Preconditions.* No freeze (`receipts/FREEZE.toml` absent); clean tree; last receipt verifies; `rustc -V` for
   T′ recorded.
2. *Dry matrix, no file changed.* With `RUSTUP_TOOLCHAIN=T′`, build and test each build set of the
   INT-TOOLCHAIN-01 matrix and record the cell: `fs-qty` alone; the bedrock-direct list (`fs-ga`, `fs-math`,
   `fs-qty`, `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`, `fs-ad`); the M1 closure
   (airlock groups `referee`, `geometry`, `ledger`); the core with the Metal annex (`ft-kernel-metal`);
   `surface/frob-mcp` with fastmcp_rust; `derive/frob-derive` with the `fsym-*` crates; and the build sets added
   since (the CUDA annex with the pinned `cudarc`, every airlock group in use, `worker/`). **Every row must pass
   on the column chosen as T.** A failing cell stops the train before anything moves.
3. *The `fs-qty` rule.* If `fs-qty` is what fails on T′, the preferred fix is an upstream change in FrankenSim
   (FD-FSIM-15: macro-generated dimension products behind a feature; or the smaller FD-FSIM-31: `fs-qty` out of
   `fs-evidence`), and T stays where it is until that change lands. If `fs-qty` fails on T after a later train
   and the upstream change cannot land within that train, the escape hatch opens: `frob-units` is created and
   `frob_core::qty` re-exports it (the change is one module plus the conversions in the airlock).
4. *Sibling legs.* A consumed sibling needs a leg if its own toolchain file is not T′ or its declared
   `rust-version` exceeds T′. Each leg is an upstream change in that sibling's repository, under its own
   `AGENTS.md` and gates, with files reserved through Agent Mail, a mirrored bead and a bead labelled `upstream`
   here: set its toolchain file to T′ (and its `rust-version` where T′ requires), repair what breaks, pass its
   own suite, land on its `main`. Legs land before T moves here. A leg changes no behaviour.
5. *The one change here.* One commit: `rust-toolchain.toml` to T′; `toolchain = "T′"` at the top of
   `franken-stack.lock`; for every sibling that had a leg, its row's `git_rev` to the landed commit and its
   `toolchain` to T′; regenerated lockfiles; the new receipt from `cargo xtask check-stack`.
6. *Gates on T′, each citing the new receipt.* The full matrix again (now for real); every admission gate with a
   record; the parity gates; the determinism lanes of tier G5 (twice on one machine; across worker counts; debug
   against release), because a compiler change is exactly what those lanes exist to catch; the six `xtask`
   checks. Kernel caches are keyed by compiler identity, so the first run after a train recompiles and says so.
7. *Record.* An ADR for the train (old T, new T, why, the legs with their commits, the matrix, what changed in
   measured build times); the matrix section of `DEPENDENCY_ADMISSION.md`; a line in `receipts/train-log.ndjson`
   with `kind = "toolchain"`.
8. *If step 6 fails.* The commit of step 5 is not made (or is reverted before anything depends on it): T stays.
   The landed legs stay in the siblings, since each is behaviour-neutral, but this repository's pins of those
   siblings do not advance unless a compatibility train on the old T accepts them. The failure is logged with
   the failing cell or gate.

**What `check-stack` and `check-deps` enforce between trains** (owned by BD-003 and BD-004, relied on here): the
toolchain files, the stack lock and the sibling heads agree with the newest receipt; there is exactly one
`rust-toolchain.toml` outside `lean/`; no direct `fs_qty` import outside `frob-core` and `frob-fsim`.

**Result identity across a train.** Identity is the hash of canonical bytes and does not change with the
compiler. Bits of floating-point results may: determinism class D2 promises the same bits per device family,
driver *and compiler*. Results from before and after a train carry different receipts and are not same-stack
evidence (`FROB-REF-890` if offered as such without revalidation).

## Acceptance criteria

- [ ] `docs/runbooks/toolchain-train.md` states the eight steps, the leg rule and the `fs-qty` rule, and is linked from `AGENTS.md`.
- [ ] `scripts/train/toolchain_train.sh --to <channel> [--dry-run]` runs the dry matrix, refuses on a failing cell, refuses under a freeze or on a dirty tree, and refuses while any consumed sibling's toolchain file differs from the target (naming the sibling).
- [ ] After a train: exactly one `rust-toolchain.toml` outside `lean/`; `franken-stack.lock` and it agree; every consumed sibling's row has `toolchain` equal to T; the receipt's `toolchain` equals T.
- [ ] Every row of the matrix passes on T, with each cell's command, exit code and output hash recorded.
- [ ] A train that fails a gate leaves T, the lock, the lockfiles and the receipts as they were, with one `abandoned` line in the train log.
- [ ] The ADR of the train names the sibling pins it moved (the form BD-031's ADR already requires).
- [ ] The script writes nothing to any sibling checkout (run against read-only copies).

## Test plan

### Unit tests
In `xtask/tests/toolchain_train.rs`, driving the real script on `synthetic` workspaces in a temporary directory
(two stand-in siblings, each one crate with its own toolchain file; real `rustup`, `cargo` and `git`; two
installed toolchains stand for T and T′):
- `dry_matrix_blocks_on_failing_cell`: one stand-in crate uses an item that only T has; expected: the cell fails, the train refuses, no file changes.
- `refuses_when_a_leg_has_not_landed`: one stand-in still names the old channel; expected refusal naming it.
- `refuses_second_toolchain_file`: a `rust-toolchain.toml` planted in a stand-in annex directory; expected refusal; the same file under `lean/` is accepted.
- `refuses_declared_minimum_above_target`: a stand-in with `rust-version` above T′; expected refusal naming the crate and both versions.
- `adopts_and_records`: both legs landed; expected one commit's worth of changes, a receipt with the new channel, a train-log line with `kind = "toolchain"`.
- `abandon_restores_everything`: a stand-in gate fails on T′; expected byte-identical lock, lockfiles and toolchain file.
- `fs_qty_rule_is_applied`: a stand-in "units" crate fails on T′; expected the refusal text to name FD-FSIM-15, FD-FSIM-31 and the `frob-units` fallback, in that order.

### End-to-end script and logging
NF-06 (`scripts/e2e/train_rehearsal.sh`) rehearses this procedure end to end. When run for real, this bead's
script logs one NDJSON line per step and per matrix cell: the command, exit code, wall time, the toolchain, the
build set, the output hash, and the receipt hash before and after.

### Known answers and negative controls
- Known answer (starting state, FACT to recheck at the first matrix): a 1.99.0-nightly compiler against a declared minimum of 1.100 is refused by Cargo; the matrix has six rows and four columns, with the cells marked "—" not required.
- Negative controls: each refusal test above; and a train attempted while `receipts/FREEZE.toml` exists must refuse with `frozen`.
- Metamorphic relation: a train from T to T′ and back to T (on the stand-ins) reproduces the original lockfile hashes and the original receipt apart from its history fields.
- Determinism lanes: the dry matrix run twice gives identical output hashes per cell.

## Considerations

- RISK-02: the toolchain train costs more than M0 allows, or breaks a sibling. Earliest signals: a failing cell of the matrix; FD-FMCP-01 still open at the M0 exit review. Mitigation: candidate (b) in reserve; legs before the move; KILL-MCP's fallbacks.
- RISK-21: the `fs-qty` coupling. Mitigation in order: quantities reach every crate only through `frob_core::qty`; the upstream changes FD-FSIM-15 and FD-FSIM-31; `frob-units` as the fallback. Of 22 crates coupled to `fs-qty`, 12 are reported to depend on it directly and 10 through another crate (FACT to recheck; the matrix run records it).
- Premortem story 25 (the train stalled and a merge was blocked): the dry matrix exists so that a stall is discovered before any file moves.
- A stable-only target would be a third way for the coupling to bite (firmware export, a Moonshot; franken_firmware is on stable 1.99.0). It is outside every train until that work is funded.
- If frankentui does not build on T when the dashboard is wanted, the remedy is an upstream change in frankentui or a train; the dashboard crate gets no toolchain of its own (OPEN-WS-2 default).
- M7 freezes every pin and T for the length of the tournament: a ratio of times measured across a toolchain train is not one measurement, and a train during the freeze voids the runs it spans.
- An upstream change that lands is adopted only through its switch-over rule; a train is one kind of switch-over and obeys the same rule that a sibling's newer clean head is never rolled back locally.
