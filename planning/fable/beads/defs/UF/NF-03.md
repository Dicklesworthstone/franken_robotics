## Background

The build graph of FrankenRobotics has one Rust toolchain, T. The preferred T, candidate (a), is the suite's
common nightly, `nightly-2026-08-31` on the day of writing, which most siblings already pin. FrankenSim, the
largest foundation and the one the referee is built on, pins `nightly-2026-07-06` (rustc 1.99.0-nightly; FACT,
`frankensim/rust-toolchain.toml`, read 2026-11-21). Candidate (a) therefore "requires advancing FrankenSim's pin
in FrankenSim's repository". The plan gives this change no `FD-` number: it is the FrankenSim leg of the first
toolchain train, named in the row of FD-FMCP-01 ("under candidate (a) the same toolchain train advances
FrankenSim's pin and moves frankensympy").

Two things are meant by "FrankenSim on T", and both are this bead. First, FrankenSim's crates must compile and
pass on T, because a path dependency is compiled by the consumer's toolchain: if they do not, T cannot be (a)
and the program falls back to candidate (b), FrankenSim's present pin. Second, FrankenSim's own toolchain file
must name T, so that FrankenSim's own gates test the compiler that builds its code here; otherwise this project
would rely on a compiler FrankenSim itself never ran.

The hazard is known in advance. `fs-qty` enables `generic_const_exprs`, which the compiler marks incomplete
(FACT: `frankensim/crates/fs-qty/src/lib.rs:20–21`; no other crate-level feature attribute was found in
`crates`, `apps` or `xtask`). A move of eight weeks of nightlies is exactly a move on which an incomplete
feature may have regressed. Rejected alternatives: carrying a second toolchain for FrankenSim's crates
(withdrawn; one graph, one compiler); leaving FrankenSim's file at the old channel while building it here on T
(its own gates would test another compiler).

## Scope

In: FrankenSim builds, tests and passes its gates on candidate (a); its `rust-toolchain.toml` names it; the
mirrored bead; the record that BD-031 and NF-05 consume. Out: choosing T (BD-031); the `fs-qty` remedies
themselves (FD-FSIM-15, FD-FSIM-31); refreshing its constellation lock (FD-FSIM-16); the train's run here
(NF-05); the fastmcp_rust and frankensympy legs (FD-FMCP-01, NF-04).

## Technical approach

{{RULES:frankensim}}

**The change, step by step.**

1. *Probe without changing anything.* In a clean clone at FrankenSim's current head, with
   `RUSTUP_TOOLCHAIN=nightly-2026-08-31`: build `fs-qty` alone; then the bedrock crates (`fs-ga`, `fs-math`,
   `fs-rand`, `fs-blake3`, `fs-ivl`, `fs-simd`, `fs-exec`, `fs-evidence`, `fs-ad`); then the whole workspace with
   all targets. Record each result. These are also cells of the INT-TOOLCHAIN-01 matrix.
2. *If `fs-qty` fails on (a).* Stop this bead at "blocked by `fs-qty`", record the compiler diagnostic, and hand
   over to FD-FSIM-15 or FD-FSIM-31. T is then candidate (b) until one of them lands and the train to (a) is
   scheduled. Nothing is forced past an incomplete-feature error.
3. *Otherwise, repair.* Fix what the newer nightly rejects: new lints, renamed or removed unstable features,
   inference changes. One commit per kind of repair, each passing FrankenSim's gates on the old channel too
   where that is possible, so that the last commit is only the toolchain file.
4. *Move the file.* `rust-toolchain.toml` to `nightly-2026-08-31`. The five crates that sit outside FrankenSim's
   workspace with their own `[workspace]` table and inherit its configuration
   (`apps/instrument-lab/render-gpu`, `apps/instrument-lab/render-gpu-piano`, `apps/pocket-watch/engine-watch`,
   `crates/fs-cmaes-viz-wasm`, `crates/fs-flyer-wasm`) are built too, WebAssembly targets included.
5. *Its gates on (a).* The whole test suite; its layer checks and contract checks; its verify-only constellation
   preflight (which refuses an off-pin or dirty sibling: if it refuses because the constellation lock is stale,
   that is FD-FSIM-16 and FD-ASUP-01, recorded and not worked around); its golden and determinism tests. A
   golden digest inside FrankenSim that moves under the new compiler is a finding to report in the mirrored
   bead, never an expectation to update silently.
6. *Record.* The landed commit; cold and warm build times and peak memory on (a) against those on the old
   channel; the list of repairs.

**Interim posture here.** If FrankenSim's crates already compile on (a) from this repository (the record of
BD-006), T is (a) and this bead only aligns FrankenSim's own file. If they do not, T is candidate (b),
fastmcp_rust is brought onto (b) by FD-FMCP-01, and the train to (a) waits for this bead.

**Fixture (DESIGN).** `tests/upstream/NF-03/`: the matrix cell "M1 closure on `nightly-2026-08-31`" as a script
with its expected result, plus the assertion that the channel in FrankenSim's toolchain file at the pinned
commit equals T. At the starting pin the second assertion fails (`nightly-2026-07-06`).

**Switch-over.** The toolchain train (NF-02), run as NF-05: T and FrankenSim's pin move in one change here; then
INT-TOOLCHAIN-01's matrix and INT-FSIM-01 are re-run on the new receipt (path dependencies on `fs-ga`,
`fs-mbd`, `fs-contact`, `fs-time`, `fs-query` pass `cargo check --all-targets` and reproduce the digest of a G1
forward-dynamics state computed inside FrankenSim at the pinned commit; the cold check fits one hour, 16 GiB
and 8 cores), with the file-by-file admission tests INT-FSIM-02 to -11.

**Fallback if the change cannot land.** T stays candidate (b). Every other consumed sibling already builds on
(b), because FrankenSim's own constellation builds them on it (asupersync, FrankenSQLite, FrankenTorch,
franken_numpy, frankenscipy); frankensympy and fastmcp_rust are the two that must be checked on it.

## Test plan

### Unit tests
In FrankenSim: its existing suite on the new channel is the test. Added there (additive):
- `toolchain_channel_is_recorded_once`: asserts that no crate inside the tree carries a second toolchain file that disagrees with the root (protects the five out-of-workspace crates).
Here (`tests/upstream/NF-03/`, real builds):
- `m1_closure_builds_on_candidate_a`: `cargo check --all-targets` of a probe crate with path dependencies on `fs-ga`, `fs-mbd`, `fs-contact`, `fs-time`, `fs-query` under `nightly-2026-08-31`; expected exit 0.
- `fs_qty_alone_builds_on_candidate_a`: expected exit 0; on failure the diagnostic is stored verbatim.
- `frankensim_channel_equals_t`: reads the channel at the pinned commit; expected T.
- `g1_digest_is_unchanged_by_the_compiler`: the G1 forward-dynamics digest computed on (a) equals the one computed on the old channel (expected equal in `f64`; a difference is reported with the first differing component, not hidden).

### End-to-end script and logging
`scripts/e2e/upstream_nf_03.sh --phase pre|post`. Phase `pre`: clones FrankenSim's pinned commit into
`target/upstream-scratch/frankensim@<rev>` (never building inside the sibling's checkout), runs the three probes
on `nightly-2026-08-31`, and records each cell. Phase `post`, after NF-05: `cargo xtask check-stack`, then
`frob doctor --json` (the foundation list shows FrankenSim with its record and `toolchain` equal to T), then
`frob sim run g1 --tier referee --seconds 2 --json`, asserting the state digest equals the one FrankenSim
computes for itself at the pinned commit.

### Known answers and negative controls
- Known answer: the digest of a G1 forward-dynamics state computed here equals the digest computed inside FrankenSim at the same commit (INT-FSIM-01); perturbing one input changes it.
- Negative control 1: with the build-identity variable (`FRANKENSIM_DEPGRAPH_SALT`) unset, the probe build fails closed in `fs-la`'s build script, on either channel; if it builds, the probe is not exercising FrankenSim's real build path.
- Negative control 2: a planted crate that uses an item removed between the two nightlies must make the workspace probe fail on (a).
- Determinism lanes: the digest twice on one machine; debug and release; this Mac and the Linux host, each against FrankenSim's same-platform class (its `fs-mbd` makes no cross-ISA claim).

## Considerations

- RISK-21 and RISK-02 both land here: this is the single most likely place for the first toolchain train to stall. The order of work (probe first, file last) is chosen so that a stall is known on day one.
- The M1 closure is 65 crates and about 2.06 million lines, and FrankenSim's lockfile holds 479 packages (FACT); a workspace-wide build on a new nightly is long. Use the offload workers and record the times; they feed OPEN-SUITE-5.
- FrankenSim's checkout had 32 modified paths and other agents commit there daily. Reserve `rust-toolchain.toml` and each file under repair, keep commits small, and expect to rebase the repair list onto a moving head.
- The ban on branches and worktrees in FrankenSim means the repairs go to `main` one at a time; each must therefore be valid on the old channel as well until the last commit flips the file.
