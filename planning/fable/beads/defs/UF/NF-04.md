## Background

FrankenSymPy is the build-time derivation engine and certificate checker of FrankenRobotics: `derive/frob-derive`
uses it to derive kernel arithmetic and to check polynomial, interval and rational certificates. The build graph
has one Rust toolchain, T, and `derive/` builds on T with no toolchain file of its own. FrankenSymPy pins
`nightly-2026-08-20`, a different nightly from the rest of the suite (FACT: `frankensympy/rust-toolchain.toml`,
head `29f847c14428`, read 2026-11-21). The different nightly is the starting state, and the plan states the
remedy: "frankensympy is moved to T by the toolchain train". The plan gives the change no `FD-` number; it is
the FrankenSymPy leg of the first train, named in the row of FD-FMCP-01. Its register row is written by NFx-01,
which numbers it `FD-FSYM-06` (P1; if that number was taken first, NFx-01 assigns the next free one and updates
this bead), registers this bead's fixture and opens the mirrored bead; this bead moves the row's `status` and
keeps the fixture current. The tests below use `derive/frob-derive` and the `K-cay-step` derivation (BD-019)
and the M0 certificate bundles with `frob prove verify` (BD-027).

Two further facts shape the work. FrankenSymPy's workspace refers to two sibling pin directories,
`../franken_numpy-pin` and `../frankenscipy-pin`, that do not exist on this machine (FACT:
`frankensympy/Cargo.toml:95–96`), which is why `derive/` depends on individual `fsym-*` crates by path and not on
the workspace. And FrankenSymPy consumes asupersync by path (`../asupersync`), so it shares the one runtime
package without a change.

Rejected alternatives: a toolchain file inside `derive/` (withdrawn: no annex carries one); building the
`fsym-*` crates here on T while FrankenSymPy's own gates run on `nightly-2026-08-20` (the certificate checker
this project trusts would then be tested on a compiler other than the one that builds it here).

## Scope

In: FrankenSymPy builds and passes its own suite on T; its `rust-toolchain.toml` names T; the mirrored bead; the
record NF-05 consumes. Out: `derive/frob-derive` and INT-FSYM-01 (BD-019); the code-generation and certificate
items (FD-FSYM-01 to -05); the missing pin directories, except to report what running the suite required.

## Technical approach

**Where the work is done, and under whose rules (binding).** The change is made in the `frankensympy` repository
(`../frankensympy` beside this one; head `29f847c14428` and toolchain channel `nightly-2026-08-20` when this was written on 2026-11-21, both FACT to
re-read), by an agent of this program working there under that repository's own `AGENTS.md`, gates and
conventions. Its workspace refers to two pin directories, `../franken_numpy-pin` and `../frankenscipy-pin`, that do not
exist on this machine (FACT: `frankensympy/Cargo.toml:95–96`), so its own build instructions are read before
its test suite is run.

1. Read that repository's `AGENTS.md` and its coordination rules first. They govern; where they differ from this
   bead, they win, and the difference is written into this bead's closing note.
2. Other agents work in the same repository. Before editing, reserve every file to be touched through Agent
   Mail and follow the repository's own coordination rules; release the reservations once the change has landed.
3. The change is additive (DESIGN): a new mode, entry point, type or feature. Existing behaviour is not changed,
   and any lossiness is self-described in the new item's documentation and return type.
4. It lands on that repository's `main` through its own tests and gates. Nothing in this repository patches,
   forks, vendors or edits the sibling, and no tool of this repository writes into its checkout (INV-SUITE-04).
5. The work is tracked twice: this bead, and a mirrored bead in the sibling's tracker whose identifier is stored
   in the `mirror` field of this item's row in `registries/upstream.toml` (schema `frob.upstream/1`). The row's
   `status` moves `open` → `landed` (merged on the sibling's `main`) → `adopted` (switch-over run here).

**The change, step by step.**

1. *Probe.* In a clean clone at FrankenSymPy's head, with `RUSTUP_TOOLCHAIN=<T>`: build the `fsym-*` crates that
   `derive/` uses (`fsym-calculus`, `fsym-polys`, `fsym-simplify`, `fsym-formal`, `fsym-proof-kernel`,
   `fsym-capsule-consumer`, `fsym-solvers` and their closure); then the workspace. Record each result; the first
   is the cell "`derive/frob-derive` with the `fsym-*` crates" of the INT-TOOLCHAIN-01 matrix.
2. *The pin directories.* If the workspace cannot be resolved without `../franken_numpy-pin` and
   `../frankenscipy-pin`, follow FrankenSymPy's own documented procedure for creating them, outside this
   repository. If no procedure is documented, record that as a finding in the mirrored bead and run the suite on
   the crates that resolve; do not invent the directories' contents.
3. *Repair and move.* Fix what T rejects, one commit per kind of repair; last, set `rust-toolchain.toml` to T.
   Under candidate (a) that is a move forward of eleven days of nightlies; under candidate (b)
   (`nightly-2026-07-06`) it is a move backward of six weeks, where a library item FrankenSymPy uses may not
   exist yet: each such use is replaced by an equivalent both compilers accept, and behaviour does not change.
4. *Its gates on T.* The whole suite, including the proof-kernel and capsule-consumer tests: a certificate
   checker's verdicts must be identical on both compilers. Its bytecode interpreter, exact arithmetic and
   Gröbner code are integer and rational, so results are expected to be bit-identical (HYPOTHESIS, tested).
5. *Record* the landed commit and the list of repairs.

**Interim posture here.** `derive/` builds on T against the `fsym-*` crates by path whatever FrankenSymPy's own
file says, as long as they compile on T (INT-FSYM-01). If they do not compile on T, derivation runs as a
subprocess built in FrankenSymPy's own workspace on its own channel, generated kernels are checked in with their
digests, and `check-generated` compares them: the product graph still has one toolchain.

**Fixture (DESIGN).** `tests/upstream/NF-04/`: the matrix cell above as a script with its expected result, plus
the assertion that the channel in FrankenSymPy's toolchain file at the pinned commit equals T (fails at the
starting pin: `nightly-2026-08-20`).

**Switch-over.** The toolchain train (NF-02), run as NF-05: T (if it moves) and FrankenSymPy's pin move in one
change here; then INT-FSYM-01 is re-run on the new receipt (`derive/` builds on T against the `fsym-*` crates by
path, derives `K-cay-step`, and its certificate replays in the offline auditor), and regeneration must reproduce
the checked-in kernel sources bit for bit.

**Fallback if the change cannot land.** The subprocess posture above; KILL-KIR and KILL-LEMMA remain the kill
gates of the derivation toolchain and the certificate route, and neither is triggered by this leg alone.

## Test plan

### Unit tests
In FrankenSymPy: its existing suite on T. Here (`tests/upstream/NF-04/`, real builds):
- `fsym_closure_builds_on_t`: `cargo check --all-targets` of a probe crate with path dependencies on the `fsym-*` crates `derive/` uses; expected exit 0.
- `frankensympy_channel_equals_t`: expected T.
- `kernel_regeneration_is_bit_identical_across_channels`: derive `K-cay-step` with the `fsym-*` crates built on the old channel and on T; expected identical emitted source and identical digest.
- `certificate_verdicts_agree`: replay the M0 instance certificates (T-01, T-03, T-04) with the checker built on each channel; expected the same verdict and the same canonical bytes.

### End-to-end script and logging
`scripts/e2e/upstream_nf_04.sh --phase pre|post`. Phase `pre`: clones the pinned commit into
`target/upstream-scratch/frankensympy@<rev>`, runs the probes on T and records the cells. Phase `post`, after
NF-05 (whose script runs it as a stage): `cargo xtask check-stack`; `cargo xtask check-generated` (the generated kernels equal their digests);
`frob prove verify --json` on the M0 certificates, asserting each replays offline.

Logging per STD-E2E: the script sources the shared helper and writes NDJSON to
`target/e2e-logs/upstream_nf_04/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line has `ts`,
`script`, `bead` (`NF-04`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time and the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed). It also records the sibling's pinned commit, the stack-receipt hash, the phase, each measured
value with its unit and threshold, digests where state is compared and, on failure, the first differing value
and the artifact paths needed to reproduce. A final `summary` line gives assertions passed and failed and the
gates touched. No private-scene data is logged.

### Known answers and negative controls
- Known answer: the Cayley-step kernel `K-cay-step` regenerates to the checked-in bytes; the quaternion norm identity ‖q·c‖² = ‖q‖²·‖c‖² (T-03) is certified as a polynomial identity on both channels.
- Negative control 1: a kernel source with one coefficient edited must fail `check-generated`.
- Negative control 2: a certificate for the sign-mutated identity must be rejected by the checker built on T.
- Determinism lanes: derivation twice on one machine gives identical digests; this Mac and the Linux host agree bit for bit (exact arithmetic, class D0).

## Considerations

- RISK-07 (FrankenSymPy budgets block derivations by expression swell) is unrelated to the compiler but is measured by the same probe: record derivation time and peak memory per kernel body on T.
- FrankenSymPy's interpreter caps an expression at 8,192 operations and its Gröbner bases at 1,024 polynomials (FACT); a compiler move must not change which derivations hit a cap. The regeneration test covers the M0 kernels only; later kernels join it as they are added.
- Under candidate (b) this leg is a backward move in time, the less comfortable direction; if it costs more than the subprocess posture, record that and let BD-031's ADR say so.
- No milestone waits on this bead. Its milestone label says when its switch-over gate first exists, not that the
  milestone's exit depends on it. Until the switch-over has been run, the interim posture above is the design of
  record. M1 depends only on FrankenSim, asupersync and FrankenSQLite, and no upstream work item is on its
  critical path.
- If this change never lands, the program still ships on the interim posture, at the cost stated there. A change
  that does land is adopted only through its switch-over rule: never by a local patch, a fork or a vendored copy,
  and never by rolling a sibling's newer clean head back. Neither a pin nor T moves during the ten-fold
  tournament of M7.
- The priority in the upstream register states the item's value to this project and its place in this program's
  queue. The risks carried at program level are the cost and ordering of upstream work and collisions with other
  agents in the same sibling; the mitigations are file reservation, small commits and the sibling's own gates.
