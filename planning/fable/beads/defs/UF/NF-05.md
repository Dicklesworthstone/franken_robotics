## Background

FrankenRobotics builds its whole graph on one Rust toolchain, T, chosen at gate INT-TOOLCHAIN-01 (BD-031) as
the first of two candidates on which every build set passes: (a) the suite's common nightly,
`nightly-2026-08-31`; (b) FrankenSim's present pin, `nightly-2026-07-06`. The consumed siblings start on four
different nightlies (FACT, read 2026-11-21): frankensim on `2026-07-06`, frankensympy on `2026-08-20`,
fastmcp_rust on `2026-08-25`, and asupersync, frankensqlite, frankentorch, franken_numpy and frankenscipy on
`2026-08-31`. "The siblings that are not on T are moved to it in their own repositories by a toolchain train."

The procedure is NF-02. The legs are separate beads, each done in its sibling's repository: FD-FMCP-01
(fastmcp_rust, priority P0), NF-03 (frankensim), NF-04 (frankensympy). This bead is the run itself: the one
coordinated change in this repository that follows the legs, the gates after it, and the record. It exists as
its own bead because a procedure that has never been run is a hope, and because the state it leaves, every
row of the stack lock with `toolchain` equal to T, is what later pin moves and the M7 freeze assume.

The stack lock states the target: each `[[foundation]]` row has a `toolchain` field, "the channel in the
sibling's own toolchain file at `git_rev`; equal to T after the train".

## Scope

In: running `toolchain_train` for the first time; the commit it produces; the gates re-run on the new receipt;
the ADR and the admission record; the list of siblings whose file still differs from T, with the reason, if any
leg could not land. Out: the procedure and script (NF-02); the legs (FD-FMCP-01, NF-03, NF-04); the choice of T
(BD-031); INT-FMCP-01 and INT-ASUP-01 (BD-023, BD-008).

## Technical approach

**Which case is being run** (read from BD-031's ADR, which names the sibling pins a train must move).

- *T is candidate (a).* The legs are frankensim (`2026-07-06` → T), frankensympy (`2026-08-20` → T) and
  fastmcp_rust (`2026-08-25` → T). All three have landed before this bead starts. After the run, every consumed
  sibling's file names T.
- *T is candidate (b).* At M0 only fastmcp_rust moves (its toolchain file and its declared `rust-version`, so
  that it builds on the 1.99 nightly), and frankensympy if NF-04 landed for (b). The siblings on `2026-08-31`
  are not moved backward: they already build on (b) inside FrankenSim's own constellation. The rows of those
  siblings keep a `toolchain` different from T, each listed in the ADR as "awaiting the train to (a)". The train
  to (a) is then scheduled as the second run of this same procedure and waits for NF-03, and with it for
  FD-FSIM-15 or FD-FSIM-31 if `fs-qty` is what blocks (a). This bead closes only when the train to (a) has run,
  or when an ADR records that (b) is T for the M0 and M1 exits and names the date of the next attempt.

**Steps (those of NF-02, with the first-run specifics).**

1. Confirm no freeze, a clean tree and a verifying receipt.
2. Dry matrix on the target with `scripts/train/toolchain_train.sh --to <T> --dry-run`: six build sets
   (`fs-qty` alone; the bedrock-direct list; the M1 closure of `referee`, `geometry`, `ledger`; the core with the
   Metal annex; `surface/frob-mcp` with fastmcp_rust; `derive/frob-derive` with the `fsym-*` crates) plus the
   CUDA annex with the pinned `cudarc` and `worker/`.
3. Confirm each leg: the sibling's `main` holds the landed commit; its checkout is at that commit and clean; its
   toolchain file names T; its mirrored bead is closed.
4. The one change here: `rust-toolchain.toml`; `toolchain` at the top of `franken-stack.lock`; `git_rev` and
   `toolchain` of each moved sibling's row; regenerated lockfiles; the receipt from `cargo xtask check-stack`.
5. Gates on the new receipt: the matrix for real; INT-FSIM-01 with the file-by-file tests INT-FSIM-02 to -11 and
   INT-FSIM-18; INT-ASUP-01; INT-FSQL-01; INT-FT-01 and -02; INT-CUDA-01; INT-FSYM-01 and -02; INT-FNP-01 and
   -02; INT-FMCP-01; the parity and determinism lanes that exist at M0 (the G1 referee digest; `K-cay-step` from
   one source on `batch-cpu`, CUDA and Metal; the exact and guarded predicate kernels); the six `xtask` checks.
6. Record: the ADR; the matrix and the per-gate results in `DEPENDENCY_ADMISSION.md`, each citing the receipt;
   one `kind = "toolchain"` line in `receipts/train-log.ndjson`; the upstream registry rows of the legs set to
   `adopted`.
7. If a gate fails: abandon as NF-02 prescribes (T and the lock unchanged here; the landed legs stay in their
   siblings), record the failing gate, and open the repair as an adapter change or an upstream item.

**Determinism class of the outcome.** The receipt is canonical JSON and must be byte-identical when recomputed
on the unchanged tree. Kernel caches are keyed by compiler identity, so the first device run after the train
recompiles and its receipt says so.

## Acceptance criteria

- [ ] `rust-toolchain.toml` and the `toolchain` of `franken-stack.lock` name the same channel, and no other Rust toolchain file exists except the two exceptions of N33c-08 (`crates/frob-cert/rust-toolchain.toml`, which names a stable release, and `worker/rust-toolchain.toml` only while the lock's `FD-FSIM` row carries `worker_rev`); `lean/`'s `lean-toolchain` is not a Rust toolchain file.
- [ ] Under candidate (a): the rows of frankensim, frankensympy and fastmcp_rust have `toolchain` equal to T and `git_rev` equal to each leg's landed commit; every other consumed sibling's row already equals T.
- [ ] Under candidate (b): the ADR lists every sibling whose file differs from T with "awaiting the train to (a)", and names what blocks (a) (the failing matrix cell and the upstream item that removes it).
- [ ] Every row of the matrix passes on T, and each gate of step 5 that exists has a record citing the new receipt; none was recorded on a dirty tree.
- [ ] The receipt recomputes byte-identically; `cargo xtask check-stack` passes; `cargo tree -d` shows no duplicate asupersync.
- [ ] `frob doctor --json` lists the admitted foundations with their records and the stack receipt, and the channel it reports equals T.
- [ ] The state of the train is handed to the M0 exit review: run and adopted; or run under (b) with the train to (a) scheduled; or abandoned, with the failing gate.

## Test plan

### Unit tests
The guard and procedure tests are NF-02's. Added here, against the real tree after the run:
- `all_sibling_channels_equal_t_or_are_listed`: for every `[[foundation]]` row with a Rust toolchain, the channel in the sibling's file at `git_rev` equals T, or the sibling appears in the ADR's "awaiting" list. Expected: no unlisted difference.
- `single_toolchain_file`: a walk of the repository finds exactly one `rust-toolchain.toml` that names a nightly (the root's, naming T); any other Rust toolchain file is one of N33c-08's two exceptions and satisfies its condition (`frob-cert`'s names a stable release; `worker/`'s exists only with a `worker_rev` in the lock). The check is `check-stack`'s, called here, not a second implementation.
- `receipt_names_t`: the newest receipt's `toolchain` equals the lock's.
- `legs_are_adopted`: the registry rows of the legs that moved in this train (FD-FMCP-01; `FD-FSIM-40`, NF-03; `FD-FSYM-06`, NF-04) read `adopted` and cite a receipt at least as new as the train's; under candidate (b), a leg that did not move (`FD-FSIM-40`, and `FD-FSYM-06` if NF-04 did not land for (b)) is not `adopted` and its sibling is on the ADR's "awaiting the train to (a)" list. A leg that moved but is not `adopted` fails.

### End-to-end script and logging
`scripts/e2e/toolchain_train_first.sh` (run after the train; idempotent, read-only): `cargo xtask check-stack`;
`frob doctor --json`; the build of each matrix row with `--locked`; `cargo tree -d` per workspace;
`frob sim run g1 --tier referee --seconds 2 --key tt-g1 --json` (BD-024), asserting the digest equals
FrankenSim's own at the pinned commit; `frob spark probe --device <the host's device: metal:0 on the Mac, cuda:0
on trj> --key tt-probe --json` (BD-017), the first device run after the train, whose receipt records the
recompiled kernel cache. Then, as stages, the `post` phase of each leg that moved in this train
(`scripts/e2e/upstream_fd_fmcp_01.sh`, `upstream_nf_03.sh`, `upstream_nf_04.sh`, each `--phase post`); under
candidate (b) a leg that did not move is logged `skipped: leg not moved`, never a pass. It asserts every
acceptance line that a command can check.

Logging per STD-E2E: the script sources the shared helper and writes NDJSON to
`target/e2e-logs/toolchain_train_first/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line has `ts`,
`script`, `bead` (`NF-05`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time and the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed). It also records the sibling's pinned commit, the stack-receipt hash, the phase, each measured
value with its unit and threshold, digests where state is compared and, on failure, the first differing value
and the artifact paths needed to reproduce. A final `summary` line gives assertions passed and failed and the
gates touched. No private-scene data is logged.

### Known answers and negative controls
- Known answer: after the train under candidate (a), the set of distinct channels over all consumed siblings' toolchain files is the singleton {T} (it was four channels before).
- Negative control 1: in a scratch copy, set one row's `toolchain` to the old channel; `all_sibling_channels_equal_t_or_are_listed` and `check-stack` must both fail.
- Negative control 2: in a scratch copy, add `spark/frob-spark-metal/rust-toolchain.toml`; `single_toolchain_file` must fail.
- Determinism lanes: the receipt twice on one machine; the matrix's output hashes on this Mac and on the Linux host (cells that do not apply to a platform are recorded "—", not passed).

## Considerations

- RISK-02 and premortem story 25: a stalled train blocks a merge. This bead's fallback is explicit in its own acceptance: run under (b), schedule (a), and say what blocks it.
- The M0 exit does not wait for the train to (a): INT-TOOLCHAIN-01 passes on whichever candidate every row passes on. What M0 must have is one T and the record.
- From this run on, T is frozen except by another train, and both T and every pin are frozen for the length of the M7 tournament.
- The legs are upstream work: if a sibling's own gates reject a leg, the leg is repaired there, under that repository's rules, never patched here. No milestone waits on an upstream change landing; this bead's two-case acceptance is how that rule is kept for the toolchain.
- KILL-MCP applies only if INT-FMCP-01 cannot pass within the M0 budget after FD-FMCP-01 and FD-ASUP-01 have been attempted; a train abandoned for another reason does not trigger it.
