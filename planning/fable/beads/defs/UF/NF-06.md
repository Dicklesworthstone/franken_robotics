## Background

Two procedures decide whether FrankenRobotics can live on moving foundations: the **compatibility train**, which
advances a sibling's pin (move the pin, write a new resolution receipt, re-run the admission and parity gates,
relock), and the **toolchain train**, which moves the one Rust toolchain T here and in every consumed sibling in
one coordinated change. Every upstream work item of the program (53 registered, each a change this program
makes in a sibling's repository) is adopted through the first; the second is how four nightlies become one.

Both are rare, manual-feeling operations, which is the kind that rots. The plan's rule for fallbacks applies to
procedures as well: one that has never run is a hope. This bead is the end-to-end rehearsal that runs both
trains, and one full upstream switch-over, against a scratch stack of stand-in siblings, from the user's side,
with every guard tripped once. It runs in CI-sized time (minutes, no FrankenSim build), so it can run on every
change to the train scripts and at every milestone exit.

Rejected: rehearsing against the real siblings (a rehearsal must be free to commit, dirty and diverge its
siblings, and no tool of this repository may write to a real sibling checkout); testing the scripts only by
their unit tests (the failures that matter are in the order of steps across files: lock, lockfiles, receipt,
registry, record).

## Scope

In: `scripts/e2e/train_rehearsal.sh`; the scratch-stack builder it uses; the assertions and logs. Out: the
procedures and their guard unit tests (NF-01, NF-02); the real first train (NF-05); the registry and its loader
(BD-037).

## Technical approach

**The scratch stack (`synthetic`, built fresh in `target/e2e-scratch/train/` on every run, seed-explicit).**

- `core/`: a copy of this repository's `xtask`, `scripts/train/`, `registries/` schema and an empty workspace
  with one crate `probe` that depends by path on the two stand-ins and calls one function of each.
- `sib-a/` and `sib-b/`: git repositories, each one small crate with its own `rust-toolchain.toml` and five
  scripted commits. In `sib-a`, commit 3 fixes a planted defect (`halve(3)` returns 1 before, 1.5 after) and
  commit 4 breaks the function `probe` calls. `sib-b` has its own lock file naming `sib-a`, so the two are
  coupled the way FrankenSim's constellation couples asupersync.
- `core/franken-stack.lock` with one row per stand-in; `core/registries/upstream.toml` with one item, `FD-X-01`,
  whose fixture asserts `halve(3) == 1.5` and so fails at commit 2; `core/receipts/`.
- Two installed toolchains stand for T and T′ (the pinned T and the newest other channel the host already has).

**Scenario, in order; each step asserts and logs.**

1. *Baseline.* `cargo xtask check-stack` passes at pins (2, 2); the receipt recomputes byte-identically (KA-767).
2. *Guard: dirty.* Touch one tracked file in `sib-a`; `check-stack` fails, the receipt shows `dirty: true` and a
   changed `tree_hash`; `compat_train.sh` refuses with class `drift`. Restore the file.
3. *Guard: backward.* Request a train of `sib-a` to commit 1; refusal `not-a-descendant`; nothing changes.
4. *Guard: read-only.* Make both stand-ins read-only for the rest of the run; every later step must still work.
5. *Pin move and switch-over.* Train `sib-a` to commit 3. Expected: the fixture of `FD-X-01` flips from failing
   to passing; the registry row moves `open` → `landed` → `adopted`; the lock row's `receipt` equals the new
   receipt's hash; `receipts/train-log.ndjson` gains one `adopted` line naming `FD-X-01`.
6. *Abandon.* Train `sib-a` to commit 4, which breaks `probe`. Expected: outcome `abandoned`; lock, lockfiles
   and receipts byte-identical to their state after step 5; one `abandoned` line with the failing gate.
7. *Coupled siblings.* Train `sib-b` to a commit whose own lock names `sib-a` at commit 5 while `core` pins 3.
   Expected: the script reports the coupling and refuses to move `sib-b` alone.
8. *Guard: freeze.* Write `receipts/FREEZE.toml`; both train scripts refuse with `frozen`; remove it.
9. *Toolchain train, blocked.* `toolchain_train.sh --to T′` while `sib-b`'s toolchain file names T: refusal
   naming `sib-b`.
10. *Toolchain train, run.* Use the stand-ins' commits whose toolchain file names T′; run the train. Expected:
    one `rust-toolchain.toml`; the lock's `toolchain` and both rows equal T′; every cell of the stand-in matrix
    passes; one `kind = "toolchain"` log line.
11. *Stack mismatch.* A result file recorded under the receipt of step 5 is offered as same-stack evidence
    after step 10; expected refusal `FROB-REF-890` (`stack-mismatch`).
12. *Breakage share.* The log now holds a known number of adopted and abandoned trains on known dates (the
    script sets the clock it passes to the train scripts); expected `breakage_share_28d` equal to the
    hand-computed value.

**What the script runs from the user's side.** `cargo xtask check-stack`; `scripts/train/compat_train.sh`;
`scripts/train/toolchain_train.sh`; `frob doctor --json` (to read the registry status and the receipt back
through the product's own surface); `cargo test -p probe`.

## Acceptance criteria

- [ ] `scripts/e2e/train_rehearsal.sh` exits 0 on a clean tree and non-zero if any of the twelve steps' assertions fails.
- [ ] Each of the guards (dirty, backward, coupled, freeze, leg not landed) is tripped exactly once and refused by its own name.
- [ ] The switch-over of step 5 moves the registry row through all three states and names the item in the train log.
- [ ] The abandoned train of step 6 leaves no byte changed outside the train log.
- [ ] The stand-in sibling directories are read-only from step 4 on, and the hash of each stand-in's working tree at the end equals its hash at step 4.
- [ ] The run takes at most five minutes on the build workers (TARGET) and needs no network.
- [ ] The script is listed in the M0 exit checklist and is re-run whenever `scripts/train/` or `xtask check-stack` changes.

## Test plan

### Unit tests
- `scratch_stack_is_reproducible`: building the scratch stack twice from the same seed gives identical commit hashes for both stand-ins (fixed author, date and message).
- `fixture_fails_at_two_passes_at_three`: `halve(3)` is 1 at commit 2 and 1.5 at commit 3, checked directly, so the rehearsal's "landed" signal is real.
- `scenario_steps_are_ordered`: the script's step table is parsed; steps 5 to 12 each declare the step whose state they start from.

### End-to-end script and logging
`scripts/e2e/train_rehearsal.sh [--seed N] [--keep]` is the deliverable.

Logging per STD-E2E: the script sources the shared helper and writes NDJSON to
`target/e2e-logs/train_rehearsal/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line has `ts`,
`script`, `bead` (`NF-06`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the exact
command line, exit code, wall time and the envelope's `evidence` block (claim, class, tier, determinism,
identities, seed). It also records the sibling's pinned commit, the stack-receipt hash, the phase, each measured
value with its unit and threshold, digests where state is compared and, on failure, the first differing value
and the artifact paths needed to reproduce. A final `summary` line gives assertions passed and failed and the
gates touched. No private-scene data is logged. For this script the `step` field takes the twelve names above; refusals are
logged as `refusal` events with the refusal name and the guard that produced it; the tree hashes of both
stand-ins are logged at steps 4 and 12; and the `summary` line lists the guards tripped and the three registry
states observed.

### Known answers and negative controls
- KA-767: the receipt computed twice on an unchanged tree is byte-identical; touching one tracked sibling file flips `dirty`, changes `tree_hash`, and `check-stack` fails (steps 1 and 2).
- Known answer for step 12: the scripted clock spans a window of 20 working days, of which 5 carry an abandoned train; the share is 5/20 = 0.25, above the 0.20 trigger of KILL-FSIM. With 4 such days it is 0.20, which is not above it.
- Negative controls, each a planted defect in a copy of the train scripts that the rehearsal must catch: (i) the ancestor check removed (step 3 must now fail the rehearsal); (ii) the restore on abandon removed (step 6); (iii) the freeze check removed (step 8); (iv) the registry update skipped (step 5); (v) a `git checkout` of the sibling inserted into the train script (step 4's read-only directories make it fail, and the tree-hash comparison catches a variant that only reads).
- Metamorphic relation: running the scenario with `sib-a` and `sib-b` renamed gives the same sequence of events and the same receipt hashes modulo the names.
- Determinism lanes: the script twice on one machine gives identical logs apart from `ts` and wall times; it is run on this Mac and on the Linux host.

## Considerations

- The rehearsal does not prove that the real siblings can be consumed; INT-FSIM-01 and the real trains do. It proves that the procedure's bookkeeping is right, which is the part nobody would otherwise exercise between real pin moves.
- INV-SUITE-04 (no sibling checkout is ever modified or moved by this project's tooling) is the invariant this script tests most directly; INV-SUITE-03 (no PASS on a dirty tree) is tested by step 2.
- If the tournament package renames the freeze marker, only step 8 changes.
- The five planted defects are registered in the negative-control registry of `frob-conformance`, so that the rule "a gate that nothing can fail validates nothing" is checked for the trains as for any gate (GATE-GAUNT-01 at each exit).
