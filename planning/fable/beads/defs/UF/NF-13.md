## Background

Every request to FrankenRobotics arrives as bytes, and the admission reader of `frob-core` validates the raw
JSON bytes before any map is built: a member name that repeats after escape decoding is refused at any nesting
level, and so is an identifier that is empty or holds a non-printable character. The rule of the workspace is
that this refusal is issued by the CLI **and by the MCP server** before a job is planned or a budget is charged.
Smallest case: `{"wheel_radius_mm": 60, "wheel_radius_mm": 75}` names one member twice; a reader that keeps the
first value simulates a 60 mm wheel, one that keeps the last simulates 75 mm, and both hash the same bytes.

On the CLI this is easy, because the CLI owns its parser. On the MCP surface it is not: `frob-mcp` is built on
the sibling library `fastmcp_rust`, which parses each incoming frame with a general JSON library before any
handler of this project runs. That library keeps one value per repeated name, and FACT
(`fastmcp_rust/Cargo.toml:54`, read 2026-11-22 at head `83e918637222`) it is built with
`serde_json = { version = "=1.0.154", features = ["arbitrary_precision"] }`, which also changes how numbers are
represented. By the time a generated tool handler sees its arguments, a duplicate is already gone. The bead that
fixes the admission order (N34-20) therefore places a byte-level guard in front of each transport `frob-mcp`
offers: the line reader that feeds the library on stdio, and the request-body reader on streamable HTTP.

That design rests on a HYPOTHESIS: *the library's stdio and HTTP transports can be fronted by a byte-level reader
without changing the library.* The tests that settle it are `mcp_guard_passes_bytes_unchanged` and
`mcp_guard_refuses_before_library` of N34-20, on both transports. This item is **conditional** on that
hypothesis failing. If it holds, no upstream change is needed and this bead is closed as not needed. If it
fails, the mismatch is in a sibling, every sibling is the owner's own project, and the fix is work this program
does in the sibling's repository: a raw-frame hook in `fastmcp_rust`. Upstream register priority: **P2** (a gate
clause, the MCP clause of GATE-WS-05, depends on the sibling's behaviour). Tier: Solid.

FACT about the transports (read 2026-11-22 at head `83e918637222`, toolchain channel `nightly-2026-08-25`,
`rust-version = "1.100"`; to re-read at the pin when the finding is recorded):
`crates/fastmcp-transport/src/lib.rs` defines `trait Transport` whose
`recv(&mut self, cx: &Cx) -> Result<JsonRpcMessage, TransportError>` returns an already parsed message;
`crates/fastmcp-transport/src/stdio.rs` defines `StdioTransport<R, W>` for any `R: Read`, `W: Write`, with
newline-delimited JSON framing in which an oversized line is a terminal framing error;
`crates/fastmcp-transport/src/http.rs` defines `HttpRequest` with `body: Vec<u8>`, `HttpRequestHandler` and
`HttpTransport<R, W>`; `crates/fastmcp-transport/src/codec.rs` defines
`Codec::decode_complete_message(&self, frame: &[u8])`. These suggest that a reader can be supplied from outside
and that the HTTP body is available as bytes, so the hypothesis is expected to hold; nothing was executed.

Rejected: patching, forking or vendoring the library here (nothing in this repository patches a sibling,
INV-SUITE-04); accepting the library's parse on MCP and checking only files (the two surfaces would then
disagree about one request, which the surface-parity rule forbids); replacing the library's transports with
transports of our own (a fork by another name, which gives up the library's conformance checks).

## Technical approach

**Step 0, here: the finding.** Copy the results of N34-20's two tests into `tests/upstream/NF-13/FINDING.md`:
for each transport (stdio, streamable HTTP), pass or fail, and for a failure which seam is missing:

1. *No outside reader.* The transport cannot be given the reader (stdio) or the body bytes (HTTP) by `frob-mcp`.
2. *No way to answer.* The guard can see a frame but cannot answer a refused one in order on the transport's
   write path without the library seeing the frame.
3. *Bytes not preserved.* The bytes the library decodes are not the bytes that arrived (re-framed or re-encoded
   before decoding).

If both transports pass, no row is written (the register's `status` has no closed state, and an unopened item
has no row): the reservation of `FD-FMCP-02` that NFx-01 holds for this bead in
`crates/frob-conformance/tests/data/upstream_series.toml` moves to that file's `tombstones` with the reason
"not needed (hypothesis held)" and the finding's date, so that the number is never reissued, and stop.

**Where the work is done, and under whose rules (binding), if step 0 finds a missing seam.** The change is made
in the `fastmcp_rust` repository (`../fastmcp_rust` beside this one), by an agent of this program working there
under that repository's own `AGENTS.md`, gates and conventions: read them first, and they govern; reserve every
file to be touched through Agent Mail, because other agents work there; the change is additive and lands on that
repository's `main` through its own tests and MCP conformance checks; nothing in this repository patches, forks
or vendors the sibling, and no tool of this repository writes into its checkout (INV-SUITE-04); the work is
mirrored as a bead in the sibling's tracker, whose identifier is stored in the `mirror` field of this item's row
in `registries/upstream.toml` (schema `frob.upstream/1`), and the row's `status` moves `open` → `landed` →
`adopted`. FD-FMCP-01 and FD-ASUP-01 touch the same repository; a change made while either is in flight shares
its reservation window.

**The change (DESIGN), only for the transport or transports that failed.** An optional hook in
`fastmcp-transport`, registered on the server builder or on the transport constructor as the sibling's
conventions prefer (names below are a sketch):

```rust
pub enum FrameVerdict { Pass, Reject { reply: Vec<u8> } }
pub trait RawFrameHook: Send + Sync + 'static {
    /// `frame`: exactly the bytes received (stdio: one line without its terminator; HTTP: the request body).
    fn on_frame(&self, frame: &[u8]) -> FrameVerdict;
}
```

1. The hook is called once per complete incoming frame, after the transport's own size limit and before
   `Codec::decode_complete_message`. An oversized line stays the terminal framing error it is today, and the
   hook is not called for it.
2. `Pass`: the library decodes the same bytes; the hook receives `&[u8]` and cannot alter them.
3. `Reject { reply }`: the library does not decode the frame, invokes no handler, creates no task and changes
   no session state; it writes `reply` through the same ordered write path as any reply (on HTTP: as the
   response body, with the status the library uses for a JSON-RPC error reply).
4. With no hook registered the transports behave byte for byte as before. Nothing else changes; no lossiness is
   introduced.

**Interim posture here.** The MCP surface documents that the duplicate-member and identifier checks on raw bytes
apply to artifact files named by path only, and not to inline tool arguments; the CLI, which is complete on its
own, applies them everywhere. The MCP clause of GATE-WS-05 is recorded `not run` with this reason and stays
open; the surface-parity comparison lists the refused corpus entries as the one known difference. The handler
still re-reads its arguments from the admitted tree wherever the guard could admit the frame.

**Fixture (DESIGN).** `tests/upstream/NF-13/`, in the form of the registered items' fixtures (an `#[ignore]`d
`frob-conformance` integration test `upstream_nf_13` with `expected.toml`): a probe server on `fastmcp_rust` at
the pinned commit with a hook that rejects any frame holding a repeated member name. It sends the tool call
`{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"probe","arguments":{"seconds":2,"seconds":3}}}`
over stdio and over HTTP and asserts that the handler's counter stays at 0 and that the reply is the hook's
bytes; then a valid frame, and asserts that the handler ran once on arguments equal to those sent. If the item
is opened, the fixture fails at the pin (it does not compile, or the first assertion fails), and `expected.toml`
records which; if it is not opened there is no fixture. Registry: when opened, this bead adds the item's row to
`registries/upstream.toml` with `bead = "NF-13"` and the identifier `FD-FMCP-02`, which NFx-01 reserves for it
(the next free number of the `fastmcp_rust` series, fixed and never reused), and in the same change sets
`opened = true` on that reservation in the series file, which is how NFx-01's register-wide test counts it.

**Switch-over (the compatibility train).** When the change is on the sibling's `main`: (1) move the sibling's pin
in `franken-stack.lock` to a clean commit that contains it (a pin only moves forward; a sibling's newer clean head
is never rolled back locally); (2) run `cargo xtask check-stack`, which writes a new resolution receipt
(`frob.stack-receipt/1`) under `receipts/`; (3) re-run that sibling's admission gates, the parity gates and the
gates this item names; (4) relock (`Cargo.lock` regenerated and committed, builds `--locked` on the one toolchain
T) and append the record, with the receipt hash, to `DEPENDENCY_ADMISSION.md`. Only then does the row's `status`
become `adopted` and the interim posture end. No PASS is recorded on a dirty sibling tree, and neither a pin nor
T moves while a ten-fold tournament is running.

**What the switch-over re-runs.** The MCP clause of GATE-WS-05 (TARGET; Known answer): every duplicate and every
bad identifier of the golden corpus is refused over MCP before a job identifier exists, and the surface-parity
comparison over the refused entries finds zero differing fields among `ok`, `exit`, `refusal.code`,
`refusal.pointer` and `refusal.observed`. INT-FMCP-01: `frob-mcp` builds in the core graph on T with exactly one
asupersync package, lists the tools generated from the verb registry, and passes the protocol smoke test over
stdio and HTTP. After adoption the guard of N34-20 is expressed as a hook that calls the same reader
(`frob_core::json::admit`), and the wrapper reader is removed for that transport.

**Fallback if the change cannot land.** The interim posture stays, with the gate clause open. If the MCP kill
gate (KILL-MCP) has moved `frob-mcp` into its own workspace, the guard and this item move with it unchanged; if
agents use the CLI alone, the item is closed as not needed.

## Test plan

### Unit tests
In the sibling (added, if the change is made; real transports over in-memory pipes, no mocks):
- `no_hook_is_byte_identical`: a recorded transcript of 20 frames gives the same replies, byte for byte, with the hook type compiled in and none registered.
- `rejected_frame_reaches_no_handler`: the duplicate tool call above; expected handler counter 0 and the hook's reply.
- `reject_reply_is_written_in_order`: three frames (pass, reject, pass); expected replies in the order 1, 2, 3.
- `hook_sees_exact_bytes`: a frame whose member name is written once plainly and once with an escape (`"seconds"` and `"\u0073econds"`), with unusual whitespace and member order; expected: the BLAKE3 digest the hook computes equals the sender's.
- `oversized_line_is_still_terminal`: a line one byte over the transport's limit; expected the framing error, and the hook's call counter at 0.
Here (`tests/upstream/NF-13/`):
- `upstream_nf_13`: the fixture, on stdio and on HTTP.
- `duplicate_refused_over_mcp_before_job`: the tool call with `{"seconds": 2, "seconds": 3}`; expected `isError: true`, FROB-REF-802 with `observed` naming `seconds`, job count and session budget unchanged.
- `large_integer_string_survives`: `"9007199254740993"` sent as a string arrives with its spelling intact.

### End-to-end script and logging
`scripts/e2e/upstream_nf_13.sh --phase pre|post` (plain shell, seed-explicit, idempotent, non-zero on failure).
Phase `pre`: prints the finding; if the item is open, runs `cargo test -p frob-conformance --test upstream_nf_13
-- --ignored` and asserts the failure recorded in `expected.toml`, then asserts the interim posture (the MCP
clause of GATE-WS-05 is `not run`, and `frob robot-docs --json` states the limit of the MCP surface). Phase
`post`, after the pin move: the fixture passes; the golden corpus is driven through `frob --json` and through
`frob-mcp` over stdio and HTTP; the registry row reads `adopted` with a receipt newer than the pin move.

Logging per STD-E2E: the script sources the shared helper and writes NDJSON to
`target/e2e-logs/upstream_nf_13/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line
has `ts`, `script`, `bead` (`NF-13`), `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`), the
exact command line or the frame's digest (never the frame's content), exit code, wall time and the envelope's
`evidence` block (claim, class, tier, determinism, identities, seed). It also records the sibling's pinned
commit, the stack-receipt hash, the phase, the counts of refused entries, job identifiers and budget before and
after with their thresholds and, on failure, the first differing field and the artifact paths needed to
reproduce. A final `summary` line gives assertions passed and failed and the gates touched.

### Known answers and negative controls
- Known answers: `{"wheel_radius_mm": 60, "wheel_radius_mm": 75}` is refused with `duplicate-member:wheel_radius_mm`; the job count and the budget are unchanged by a refused request; 9007199254740993 = 2⁵³ + 1 is not representable as a double, which is why it travels as a string.
- Negative controls, each of which must make a test fail: a hook that always answers `Pass` (the duplicate reaches the handler, so the test is shown to see the handler); a scratch copy of the sibling in which the hook is called after decoding (`hook_sees_exact_bytes` fails, because the repeated member is gone); a build of `frob-mcp` with the guard bypassed (the standing control of N34-20).
- Metamorphic relation: inserting whitespace between the tokens of a valid frame changes neither the verdict nor the typed arguments the handler receives.
- Determinism lanes: the verdict is a pure function of the frame's bytes (class D0); identical twice on one machine and on Linux and macOS.

## Considerations

- The item may never be opened: the transport facts above suggest the seams exist. It is written down so that, if the hypothesis fails, the open gate clause has an owner and the fix is made in the sibling and not as a local patch.
- Security: the hook is the first code to touch untrusted bytes on the MCP surface. Limits are applied before it runs, it never logs frame content, and imported text is never interpolated into a reply without its untrusted mark.
- The library's `arbitrary_precision` feature stays in the unified feature set of every binary that links it; the hook does not change that, which is why handlers keep re-reading arguments from the admitted tree.
- The one permitted difference between the surfaces remains the unknown-tool case, which the library answers before generated code runs.
- No milestone waits on this bead. Its milestone label says when its switch-over gate first exists, not that the
  milestone's exit depends on it. Until the switch-over has been run, the interim posture above is the design of
  record.
- If this change never lands, the program still ships on the interim posture, at the cost stated there. A change
  that does land is adopted only through its switch-over rule: never by a local patch, a fork or a vendored copy,
  and never by rolling a sibling's newer clean head back. Neither a pin nor T moves during the ten-fold
  tournament of M7.
