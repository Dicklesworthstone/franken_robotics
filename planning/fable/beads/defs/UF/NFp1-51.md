## Background

FrankenRobotics runs its batched physics on Apple silicon through Metal, and reaches Metal only through
FrankenTorch's `ft-kernel-metal`, a safe gateway to custom Metal Shading Language kernels (ADR-SPARK-09: Metal
is reached through `ft-kernel-metal`; missing gateway features are upstream work items done in FrankenTorch's
repository, never a local patch or a second binding; until they land the backend works inside the gateway's
present limits). The gateway's missing features are one register item, FD-FT-01 (register priority **P1**), in
five stages that land separately. Stages 1 and 2 (completion; buffers and arguments) are bead FD-FT-01, which
holds the item's register row and its fixture. This bead is stages 3 and 4. Stage 5 (Metal 4 command allocators
and the `objc2-metal` migration) is NFp1-52.

The gateway as it exists (FACT, version 0.1.3, `src/compute.rs`, `src/lib.rs`, read 2026-11-21): `library`
compiles source under `MathMode::Safe`, which disables fast math; buffers are `StorageModeShared` allocations;
`Gateway::batch` encodes several kernels in order into one serial compute encoder of one command buffer and
returns a `Receipt` with the kernel count and the device's execution time (`device_seconds`, spanning Metal's
`GPUStartTime` to `GPUEndTime`). The limits this bead removes, and what each costs the Metal tier today (§21.9):

| Limit today (FACT) | Consequence here (the interim posture) |
|---|---|
| Compilation from source only; no function constants; no binary archive | Shape-class constants are `#define` lines prepended to the dialect text; a warm start recompiles from a cached digest (the kernel cache, N21b-12) |
| Shared storage only; no private storage, blit or heap | Readback is a host copy after completion |
| The receipt has a kernel count and device seconds only | Per-kernel timing needs one batch per kernel in profiling mode (the M2 step profile, N21a-27) |

Part of this is wrapping, not new binding work: the `metal` 0.33.0 binding under the gateway is reported to
expose blit encoders and binary archives (FACT to recheck at the pin, by reading the binding's source).

Rejected, and withdrawn as a fallback: a Metal binding of our own beside the gateway (OPEN-SPARK-5: not without
an owner decision; default: stay inside the gateway's limits and accept KILL-METAL's fallback).

## Scope

In: stages 3 and 4 of FD-FT-01, in FrankenTorch; here, the Metal backend moved onto each as it lands (function
constants in place of `#define` prepends, archive entries in the kernel cache, private slabs with snapshot blits,
per-kernel times in the step profile), and the four gates re-run; the fixture's stage-3 and stage-4 assertions
and their stages in the e2e script. Out: stages 1 and 2, the register row and the fixture's creation (FD-FT-01);
stage 5 and the row's move to `adopted` (NFp1-52); the Metal backend itself (BD-174), the kernel cache
(N21b-12) and the step profile (N21a-27), which this bead moves onto the new API but does not own.

## Technical approach

**Where the work is done, and under whose rules (binding).** The change is made in the `frankentorch` repository
(`../frankentorch` beside this one; head `8165d6a18028` and toolchain channel `nightly-2026-08-31` when this was
written on 2026-11-21, both FACT to re-read), by an agent of this program working there under that repository's
own `AGENTS.md`, gates and conventions. FrankenTorch calls `ft-kernel-metal` its sanctioned unsafe boundary
(FACT: `frankentorch/crates/ft-kernel-metal/src/lib.rs`), so any new `unsafe` stays inside that crate and follows
its safety documentation.

1. Read that repository's `AGENTS.md` and its coordination rules first. They govern; where they differ from this
   bead, they win, and the difference is written into this bead's closing note.
2. Other agents work in the same repository. Before editing, reserve every file to be touched through Agent
   Mail and follow the repository's own coordination rules; release the reservations once the change has landed.
3. The change is additive (DESIGN): a new mode, entry point, type or feature. Existing behaviour is not changed,
   and any lossiness is self-described in the new item's documentation and return type.
4. It lands on that repository's `main` through its own tests and gates. Nothing in this repository patches,
   forks, vendors or edits the sibling, and no tool of this repository writes into its checkout (INV-SUITE-04).
5. The work is tracked on the item's one mirrored bead in FrankenTorch's tracker (its identifier is the `mirror`
   of FD-FT-01's row in `registries/upstream.toml`, schema `frob.upstream/1`); each stage is a note there. The
   row stays `landed` while any stage is not yet adopted.

**Stage 3, compilation (DESIGN; additive; every existing compile-fail guarantee kept).**

- *Function constants.* A pipeline built from a library function specialized by typed constant values
  (Metal's function-constant mechanism), so that shape-class constants specialize a kernel without editing its
  source text. The source form keeps working.
- *Binary archive and ahead-of-time compilation.* Compiled pipelines are stored in and loaded from a binary
  archive. The archive key covers everything that changes the compiled code: the source digest, the entry name,
  the function-constant values, the compile options (including `MathMode::Safe`), the language version, the
  device identity and the operating system and compiler build. A stale or corrupted entry is a miss and a
  recompile, never a wrong kernel; the gateway reports hits, misses and compilations.

**Stage 4, storage and timing (DESIGN; additive).**

- *Private storage with blits.* `StorageModePrivate` buffers, and a blit from a private buffer to a shared
  snapshot buffer encoded inside the same command buffer as the kernels that wrote it. A private buffer cannot be
  read by the host; the type system or a refusal says so.
- *Per-kernel timing in the `Receipt`.* One device start and end time per kernel of a batch, beside the existing
  `device_seconds`. On Apple-silicon GPUs counter sampling is reported to be available at stage boundaries and not
  at dispatch boundaries (FACT to recheck on this machine); if so, per-kernel times need one compute pass per
  kernel inside the command buffer, and the batch's own device time with and without per-kernel timing is
  measured and reported so that the cost of timing is known.

**Here, as each stage is adopted.** Stage 3: the backend's shape-class constants move from `#define` prepends to
function constants (the emitted bytes are compared on every M2 kernel first), and the kernel cache stores archive
entries under its BLAKE3 key, which gains the archive key's fields. Stage 4: snapshot slabs follow rule R3 (results
are blitted to a shared snapshot slab inside the same command buffer and read under R1; managed storage is not
used); the step profile takes per-kernel times from one batch instead of one batch per kernel. Where a backend
piece (BD-174, the kernel cache N21b-12, the step profile N21a-27) or a gate does not exist yet when a stage is
adopted, FD-FT-01's rule applies: the switch-over runs INT-FT-01, INT-FT-02 and the fixture; the piece is built
on the pinned gateway as its own bead specifies; and its move onto the stage's API is a lever of KILL-METAL's one
optimization pass (BD-217), landing only with identical digests and a paired lower bound of at least 1.03 (for
the archive, which changes no digest, with zero compilations at warm start).

**Rules on this side that must keep holding (§21.9).** R1: the host reads a device slab only after the command
buffer that last wrote it has completed and returned its receipt. R2: a terminal state other than `Completed`
invalidates every slab the batch could write; only a `Completed` receipt makes the other committed slab current;
on failure, restore and resubmit at most four times with growing waits, then refuse with `FROB-REF-607`. R3: as
above. R4: a run is labelled native on a device only if its receipt carries a completed command buffer with start
and end times from that device. R5: timers cover completion, never enqueue alone. R6: thread-group sizes are
multiples of the execution width read from the pipeline.

**Fixture.** `tests/upstream/FD-FT-01/` (written by FD-FT-01): its stage-3 assertion (a function constant) and
its stage-4 assertion (a receipt with per-kernel times) fail at the pin with signatures in `expected.toml`. When
each stage is adopted, this bead records that the assertion passes and updates the file.

**Switch-over (the compatibility train), per stage.** When the stage is on FrankenTorch's `main`: move the pin in
`franken-stack.lock` to a clean commit that contains it (forward only); `cargo xtask check-stack` writes a new
receipt (`frob.stack-receipt/1`); re-run INT-FT-01 (the gateway builds in the Metal annex, with FrankenTorch's
`block` patch repeated at the annex root, and runs a kernel on this Mac), INT-FT-02 (a buffer stays resident
across two command buffers; a completion receipt from the device; a device tag alone earns zero operator
coverage), GATE-SPARK-02 (every M2 kernel and the full step agree between `batch-cpu` in `f32` and the device
inside the declared class: bit-equal for class D1; for class D3 at most 4 ulp per kernel output, statistical
equivalence of 1,000-step rollouts and the decision-level test) and GATE-SPARK-04 (Metal throughput at least 25%
of one RTX 4090 at matched settings on this M5 Ultra, beside an incumbent with a Metal path measured on the same
machine); relock and append the record, with the receipt hash, to `DEPENDENCY_ADMISSION.md`. No PASS on a dirty
sibling tree; neither a pin nor T moves during a ten-fold tournament. A gate that does not exist yet has its
first run against the new pin.

**Fallback if a stage cannot land.** The interim posture of the table above stays. KILL-METAL (decided at M2):
if GATE-SPARK-04 fails after one optimization pass, or the Metal backend cannot hold run-to-run determinism,
Metal becomes a development and replay tier, CUDA is the training tier, and the Mac trains on `batch-cpu`.

## Acceptance criteria

- [ ] In FrankenTorch, per stage: the new API exists with tests; every existing test, including the compile-fail tests that make R1 a compile-time fact, still passes; any new `unsafe` is inside `ft-kernel-metal` with its safety note.
- [ ] Stage 3: a kernel specialized by function constant produces the same bytes as the `#define` form; a warm start from the archive compiles nothing; a corrupted or stale archive entry (changed source, changed constant value, changed language version, flipped bytes) is a miss.
- [ ] Stage 4: a private-storage result blitted to a shared snapshot equals the shared-storage result bit for bit; the receipt carries one time per kernel, and the cost of per-kernel timing on the batch's device time is recorded.
- [ ] Here: after each adopted stage INT-FT-01 and INT-FT-02 are re-run and recorded with the new receipt; where the backend pieces and gates exist at that pin, GATE-SPARK-02 and GATE-SPARK-04 are re-run, rules R1 to R6 are re-tested, and compile counts at warm start and the step profile's per-kernel shares are recorded before and after; where they do not, the record names each `first run against the new pin` with its bead.
- [ ] Here: every M2 kernel built with function constants emits output bytes identical to its `#define` build; no code in `spark/frob-spark-metal` binds Metal outside the gateway (a source scan).
- [ ] The fixture's stage-3 and stage-4 assertions pass after their stages are adopted, and the stage-5 assertion (added by NFp1-52) still fails at that pin.
- [ ] Every file edited in FrankenTorch was reserved through Agent Mail and released after landing; nothing in this repository patches, forks or vendors it; `cargo xtask check-stack` reports it on-pin and clean under the new receipt.

## Test plan

### Unit tests
In FrankenTorch (added, in `ft-kernel-metal`; run on Apple silicon):
- `function_constant_equals_define`: N = 12 as a constant and as a `#define`; identical output bytes.
- `function_constant_values_select_distinct_pipelines`: N = 12 and N = 13; different outputs, two archive keys.
- `archive_warm_start_compiles_nothing`: second open reports zero compilations.
- `archive_stale_entry_is_a_miss`: the same entry name with changed source, with a changed constant value and with a changed language version; expected a miss and one compilation each, and correct output.
- `archive_corrupted_entry_is_a_miss`: one byte of a stored entry flipped; expected a miss, never a load.
- `private_blit_equals_shared`: 10⁶ `f32` values; bit equality.
- `private_buffer_is_not_host_readable`: a host read of a private buffer is a compile-time error or a refusal.
- `receipt_has_per_kernel_times`: three kernels in one batch; three non-negative times whose sum is at most the batch's device time.
Here:
- `readback_rules_r1_to_r6`: the backend's rule tests, re-run per stage.
- `chunk_commit_survives_aborted_buffer`: an injected non-`Completed` terminal state; the committed slab is unchanged and the retry reproduces the digest.
- `kernel_cache_key_covers_archive_fields`: changing any one archive-key field changes the cache key.
- `profile_shares_match_one_batch_per_kernel`: per-kernel shares of the M2 step from one batch against the one-batch-per-kernel profiling mode; each share within 5 percentage points (DESIGN), median of 20 runs.

### End-to-end script and logging
`scripts/e2e/upstream_fd_ft_01.sh --phase pre|post --stage 3 --stage 4` (the script of FD-FT-01; this bead adds
its two stages). Phase `pre`: `cargo xtask check-stack`; `frob doctor --json` (the registry section shows the
item `landed`); the fixture run with `--ignored`, asserting that the stage-3 and stage-4 assertions fail with
their signatures. Phase `post`, on the Mac after each stage's pin move: the stage's assertions pass and the
stage-5 assertion still fails; the four gates are re-run where they exist at that pin (else logged `first run
against the new pin` with the bead key); `frob spark probe --device metal --suite all --key fdft01-probe-s<N>
--json`, `frob spark fingerprint --device metal --no-soak --key fdft01-fp-s<N> --json` and `frob spark check
--kernel K-cay-step --backend gpu-metal --key fdft01-check-s<N> --json`, each a `run` verb under its own key per
stage N; the Metal row of the performance harness where it exists. It logs compilations at warm start, archive
hits and misses, per-kernel times and the batch device time with and without them.

Logging per STD-E2E: the script sources the shared helper and writes NDJSON to
`target/e2e-logs/upstream_fd_ft_01/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line has `ts`,
`script`, `bead` (`NFp1-51`), `stage`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`),
the exact command line, exit code, wall time and the envelope's `evidence` block (claim, class, tier,
determinism, identities, seed). It also records the sibling's pinned commit, the stack-receipt hash, the phase,
each measured value with its unit and threshold, digests where state is compared and, on failure, the first
differing value and the artifact paths needed to reproduce. A final `summary` line gives assertions passed and
failed and the gates touched. No private-scene data is logged.

### Known answers and negative controls
- Known answers: identical bytes for N = 12 as a constant and as a `#define`; zero compilations at warm start; 10⁶ values bit-equal through a private buffer and a snapshot blit; a kernel matches a Rust loop bit for bit on 10⁶ quaternions (the admission of INT-FT-01).
- Negative controls: a stale archive paired with changed source must not be loaded; a corrupted entry must not be loaded; a host read of a private slab without its snapshot blit must be impossible or refused (R3); a receipt whose per-kernel times sum to more than its device time must fail `receipt_has_per_kernel_times`; phase `post --stage 4` before stage 4 is adopted must exit non-zero.
- Determinism lanes: each stage re-runs the device's run-to-run lane (same bits twice, and across worker counts) and the cross-backend lane against `batch-cpu` in its declared class. Timing values are measurements and are not compared for equality.

## Considerations

- RISK-08 (the gateway's limits throttle the Mac tier): the earliest signals are compile time at warm start and the cost of one batch per kernel in profiling mode; record both before and after.
- An archive key that misses a field is the one way this stage could return a wrong kernel instead of a slow one; the key test changes each field in turn, and because the key includes the device identity an archive copied
  from another machine is a miss.
- Stages 3 and 4 do not bear on BET-09 as directly as stages 1 and 2, which is why they follow FD-FT-01.
- No milestone waits on this bead; until a stage is adopted, its interim posture is the design of record. A
  stage that lands is adopted only through its switch-over: never by a local patch, a fork or a vendored copy,
  and never by rolling a sibling's newer clean head back. Neither a pin nor T moves during the ten-fold
  tournament of M7.
- The risks carried at program level are the cost and ordering of upstream work and collisions with other agents
  in FrankenTorch; the mitigations are file reservation, small commits and the sibling's own gates.
