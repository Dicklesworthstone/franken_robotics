## Background

FrankenRobotics runs its batched physics on Apple silicon through Metal, and reaches Metal only through
FrankenTorch's `ft-kernel-metal`, a safe gateway to custom Metal Shading Language kernels (ADR-SPARK-09: missing
gateway features are upstream work items done in FrankenTorch's repository, never a local patch or a second
binding). The gateway's missing features are one register item, FD-FT-01 (register priority **P1**), in five
stages that land separately: stages 1 and 2 are bead FD-FT-01 (which holds the register row and the fixture),
stages 3 and 4 are NFp1-51, and stage 5, the platform stage, is this bead. It is the last stage, so this bead also
moves the item's row to `adopted`.

The binding under the gateway is `metal` 0.33.0, which its maintainers have deprecated (FACT, §21.9: "pinned as
FrankenTorch pins it; the migration is part of FD-FT-01"). Its language-version enumeration ends at Metal Shading
Language 3.1 (`metal-0.33.0/src/library.rs:363`), so dialect sources use no construct newer than 3.1 (N33c-39,
which also pins that fact with compile tests naming the binding's enumeration and its version 0.33.0). The
successor binding is `objc2-metal`, generated from Apple's own headers (Appendix H.3: docs.rs/objc2-metal). Metal 4
adds command allocators, from which command buffers are created and whose memory is reused once the buffers that
used it have completed.

Rejected, and withdrawn as a fallback: a Metal binding of our own beside the gateway (OPEN-SPARK-5).

## Scope

In: stage 5 in FrankenTorch: the gateway's internals moved from `metal` 0.33 to `objc2-metal` behind an unchanged
public API, Metal 4 command allocators as an added submission path where the system provides them, and the
language versions the binding exposes; here, the switch-over, the binding-fact tests of N33c-39 re-pointed to the
new binding, the fixture's sixth (stage-5) assertion, and the row's move to `adopted` once every stage is adopted.
Out: stages 1 to 4 (FD-FT-01, NFp1-51); raising the dialect's language ceiling above 3.1, which needs its own
record (below); the Metal backend itself (BD-174).

## Technical approach

**Where the work is done, and under whose rules (binding).** The change is made in the `frankentorch` repository
(`../frankentorch` beside this one; head `8165d6a18028` and toolchain channel `nightly-2026-08-31` when this was
written on 2026-11-21, both FACT to re-read), by an agent of this program working there under that repository's
own `AGENTS.md`, gates and conventions. FrankenTorch calls `ft-kernel-metal` its sanctioned unsafe boundary
(FACT: `frankentorch/crates/ft-kernel-metal/src/lib.rs`), so any new `unsafe` stays inside that crate and follows
its safety documentation.

1. Read that repository's `AGENTS.md` and its coordination rules first. They govern; where they differ from this
   bead, they win, and the difference is written into this bead's closing note.
2. Other agents work in the same repository. Before editing, reserve every file to be touched through Agent
   Mail and follow the repository's own coordination rules; release the reservations once the change has landed.
3. The change is additive (DESIGN): a new mode, entry point, type or feature. Existing behaviour is not changed,
   and any lossiness is self-described in the new item's documentation and return type. For the binding
   migration, "additive" means the public API of the gateway and every observable output stay as they were.
4. It lands on that repository's `main` through its own tests and gates. Nothing in this repository patches,
   forks, vendors or edits the sibling, and no tool of this repository writes into its checkout (INV-SUITE-04).
5. The work is tracked on the item's one mirrored bead in FrankenTorch's tracker (its identifier is the `mirror`
   of FD-FT-01's row in `registries/upstream.toml`, schema `frob.upstream/1`); this stage is a note there.

**The change (DESIGN).**

1. *Migration first, behind the API.* Replace the gateway's use of `metal` 0.33 with `objc2-metal`, one area at a
   time (device and queue, library and pipeline, buffers, encoders and receipts, the stage-1 to stage-4
   features), each commit passing FrankenTorch's whole suite, compile-fail tests included. Before the first
   commit, record the output bytes of a fixed kernel set (the gateway's own tests plus the probe kernels of the
   fixture) on the old binding; after the last, the same kernels must give the same bytes. The binding changes the
   calls into Metal, not the compiler or the math mode, so equal bytes are expected (HYPOTHESIS, tested).
2. *Metal 4 command allocators.* An added submission path that creates command buffers from an allocator and
   resets the allocator only after every command buffer that used it has completed; the classic path stays and is
   the default where Metal 4 is not available. Both paths give the same bytes and receipts of the same form.
3. *Language versions.* The gateway reports the language version it compiles under and accepts a requested
   version up to what the binding exposes. Requesting 3.1 keeps today's behaviour.

**Here, at the switch-over.** INT-FT-01's record states the language version the gateway compiles under; the
fingerprint (`frob spark fingerprint`) re-runs the 64-bit atomic probe, since stage 5 does not change what kernels
may assume about 64-bit atomics (Metal Shading Language 3.2 and 4.0 are reported to provide no 64-bit integer
atomic add and no 64-bit compare-and-swap: FACT to recheck). The binding-fact tests of N33c-39
(`spark/frob-spark-metal/tests/binding_facts.rs`) report "fact changed" when the binding moves; they are re-pointed
to `objc2-metal` (its version, its language-version enumeration, the indirect dispatch and thread-group memory
length calls), and the version assertions move to the new resolved versions. The dialect stays at 3.1: raising
it is a separate decision recorded in the Spark chapter's decision record (N21c-24), with GATE-SPARK-02 re-run on
the new version, and is not made by this bead.

**Fixture.** `tests/upstream/FD-FT-01/` gains a sixth assertion, tagged stage 5, written when this bead starts:
the gateway's dependency closure at the pin contains no `metal` 0.33 crate and the gateway offers the
allocator-based submission path. It fails at the pin, with its signature recorded in `expected.toml`.

**Switch-over (the compatibility train).** When stage 5 is on FrankenTorch's `main`: move the pin in
`franken-stack.lock` forward to a clean commit that contains it; `cargo xtask check-stack` writes a new receipt
(`frob.stack-receipt/1`); re-run INT-FT-01 (the gateway builds in the Metal annex, with FrankenTorch's `block`
patch repeated at the annex root, which is re-checked because the binding's dependency closure changes), INT-FT-02,
GATE-SPARK-02 (bit-equal for class D1; for class D3 at most 4 ulp per kernel output, statistical equivalence of
1,000-step rollouts and the decision-level test) and GATE-SPARK-04 (at least 25% of one RTX 4090 at matched
settings on this M5 Ultra), and the language-version and atomic records GATE-WS-06 requires; relock and append the
record, with the receipt hash, to `DEPENDENCY_ADMISSION.md`. Then, if stages 1 to 4 are adopted too, the whole
fixture passes and the row's `status` becomes `adopted`. No PASS on a dirty sibling tree; neither a pin nor T moves
during a ten-fold tournament.

**Fallback if the change cannot land.** The gateway stays on `metal` 0.33, pinned as FrankenTorch pins it, and
the dialect stays at 3.1. The cost is a deprecated binding that receives no fixes: every compatibility train and
toolchain train re-runs INT-FT-01, so a binding that stops building on T is found at the train, not later.
FrankenTorch is the owner's own repository, so stage 5 is this program's work there; if it cannot land (its own
gates or `AGENTS.md` rule the change out for now, or the `objc2-metal` migration fails the byte comparison), the
reason is written in the mirrored bead and in `expected.toml` (the stage-5 assertion marked deferred, with the
reason, the date and what would reopen it), and the row becomes `adopted` when stages 1 to 4 are, with that note. KILL-METAL's fallback (Metal as a development and replay tier) is unaffected by this stage alone.

## Test plan

### Unit tests
In FrankenTorch (added, in `ft-kernel-metal`; run on Apple silicon):
- `binding_migration_preserves_kernel_bytes`: the fixed kernel set, outputs compared with the bytes recorded on the old binding; expected identical.
- `no_deprecated_metal_crate`: the crate's resolved dependency graph contains no `metal` package; expected none.
- `allocator_and_classic_paths_agree`: the same three-kernel batch through each path; identical bytes, two receipts with the same fields.
- `allocator_reset_waits_for_completion`: a reset requested while a command buffer from the allocator is in flight is a compile-time error or a refusal; after completion it succeeds.
- `language_version_is_reported`: with 3.1 requested, the reported version is 3.1.
- The stage-1 to stage-4 tests (`two_command_buffers_in_flight`, `forty_arguments`, `function_constant_equals_define`, `archive_warm_start_compiles_nothing`, `private_blit_equals_shared`, `receipt_has_per_kernel_times` and the rest), re-run unchanged on the new binding.
Here:
- `binding_facts_name_the_new_binding`: the re-pointed tests of N33c-39 pass and name `objc2-metal` and its resolved version.
- `readback_rules_r1_to_r6` and `chunk_commit_survives_aborted_buffer`, re-run.
- `dialect_still_3_1`: the Metal prelude declares 3.1 and the emitter passes 3.1 after the migration.

### End-to-end script and logging
`scripts/e2e/upstream_fd_ft_01.sh --phase pre|post --stage 5` (the script of FD-FT-01; this bead adds stage 5 and
the final adoption). Phase `pre`: `cargo xtask check-stack`; `frob doctor --json`; the fixture with `--ignored`,
asserting that the stage-5 assertion fails with its signature. Phase `post`, on the Mac after the pin move: the
whole fixture passes; the four gates are re-run where they exist at that pin (else logged `first run against
the new pin` with the bead key); `frob spark probe --device metal --suite all --key fdft01-probe-s5 --json`,
`frob spark fingerprint --device metal --no-soak --key fdft01-fp-s5 --json` (language version and 64-bit atomic
probe) and `frob spark check --kernel K-cay-step --backend gpu-metal --key fdft01-check-s5 --json`, each a `run`
verb under its own key; the Metal row of the performance harness where it exists; `frob doctor --json` shows the
row `adopted` with a receipt newer than the pin move.

Logging per STD-E2E: the script sources the shared helper and writes NDJSON to
`target/e2e-logs/upstream_fd_ft_01/<utc-timestamp>.ndjson` with a human-readable transcript beside it. Every line has `ts`,
`script`, `bead` (`NFp1-52`), `stage`, `step`, `event` (`start`, `cmd`, `assert`, `metric`, `refusal`, `end`),
the exact command line, exit code, wall time and the envelope's `evidence` block (claim, class, tier,
determinism, identities, seed). It also records the sibling's pinned commit, the stack-receipt hash, the phase,
each measured value with its unit and threshold, digests where state is compared, the binding and its version,
the language version, and on failure the first differing value and the artifact paths needed to reproduce. A
final `summary` line gives assertions passed and failed and the gates touched. No private-scene data is logged.

### Known answers and negative controls
- Known answers: the fixed kernel set's bytes before and after the migration; 1 + 2 + … + 40 = 820 and host element 128 at byte offset 512, still true on the new binding; a kernel matches a Rust loop bit for bit on 10⁶ quaternions (the admission of INT-FT-01).
- Negative controls: a scratch copy of the gateway manifest with `metal` 0.33 added back must fail `no_deprecated_metal_crate`; an allocator reset while in flight must be impossible or refused; a dialect source using a construct newer than 3.1 must still be rejected (N33c-39's plant); phase `post --stage 5` at the starting pin must exit non-zero.
- Determinism lanes: the device's run-to-run lane (same bits twice, and across worker counts) and the cross-backend lane against `batch-cpu`, on both submission paths.

## Considerations

- RISK-08 (the gateway's limits throttle the Mac tier) and the deprecation of `metal` 0.33: the earliest signal is a train at which INT-FT-01 fails to build on the old binding.
- The migration touches every Metal call in the gateway; it is the largest of the five stages in changed lines, which is why it is sequenced after stages 1 to 4 and done behind an unchanged API with a byte comparison.
- This stage does not change what kernels may assume about 64-bit atomics, and does not raise the dialect above 3.1.
- No milestone waits on this bead; until it is adopted the interim posture (the old binding, the classic path)
  is the design of record. A change that lands is adopted only through its switch-over: never by a local patch,
  a fork or a vendored copy, and never by rolling a sibling's newer clean head back. Neither a pin nor T moves
  during the ten-fold tournament of M7.
- The risks carried at program level are the cost and ordering of upstream work and collisions with other agents
  in FrankenTorch; the mitigations are file reservation, small commits and the sibling's own gates.
