## Background

asupersync is the suite's structured-concurrency runtime: cancellation, the capability context `Cx`, and the lab
runtime used for deterministic simulation testing. Every async path of FrankenRobotics uses it, and so do the
siblings it consumes. A Cargo package is identified by name, version and source, so two requirements that
resolve to different versions, or to the same version from a path and from the registry, put **two asupersync
packages** in one binary: two runtimes, two `Cx` types that do not unify, and cancellation that silently stops
at the seam. Invariant INV-SUITE-02 forbids it: every binary links exactly one asupersync package.

Upstream work item FD-ASUP-01 (priority **P0, done at M0**) aligns the three consumers that matter to the M0
graph, FrankenSim's constellation, FrankenTorch and fastmcp_rust, on **one published asupersync version, V**
(decision of the owner, 2026-11-22). Its work has two halves. This bead is the half done in the four sibling
repositories: choosing V, landing it in asupersync, frankensim, frankentorch and fastmcp_rust under their own
rules, the four mirrored beads, and the "before" evidence. FD-ASUP-01, which depends on this bead, is the half
done here: the root patch entry, the `franken-stack.lock` row, the failing fixture, the switch-over train and the
controls, which need this repository's workspace and its admission checks (`check-deps`, `check-stack`). The work
in the siblings needs nothing from this workspace, so it is a bead of its own and starts as soon as the suite
survey N33c-07 has re-read the siblings, instead of waiting behind the workspace's admission beads.

## Technical approach

**Where the work is done, and under whose rules (binding).** Four repositories are touched, each beside this one
(`../asupersync`, `../frankensim`, `../frankentorch`, `../fastmcp_rust`), by an agent of this program working there
under that repository's own `AGENTS.md`, gates and conventions; where they differ from this bead, they win, and the
difference is written into this bead's closing record. Other agents work in the same repositories (asupersync's
checkout had 267 modified paths), so every file is reserved through Agent Mail before it is edited and released
once the change has landed, and nobody else's uncommitted work is touched. For FrankenSim the rules include its
layer checks, its contracts and its ban on branches and worktrees, so the work is committed on `main` in small steps
that each pass its gates. Every change is additive and lands on that repository's `main` through its own tests and
gates. Each repository gets its own mirrored bead in its own tracker. Heads move fast, so every file named here is
re-read at the current head before it is edited. Nothing in this repository patches, forks, vendors or edits a
sibling, and no tool of this repository writes into a sibling's checkout (INV-SUITE-04): every build or listing
this bead makes for evidence runs in a scratch clone `target/upstream-scratch/<repo>@<rev>`.

**What it starts from (DESIGN: nothing of this workspace).** N33c-07's survey record
(`receipts/surveys/<utc>.json`, schema `frob.suite-survey/1`): each sibling's head, modified-path count and
asupersync requirement as written. This bead runs at M0, possibly before `franken-stack.lock` exists, so the
survey's fail-closed reading applies: with no stack lock every surveyed sibling counts as consumed. A sibling's
"current commit" below is the head that survey recorded, re-read before the first edit.

1. **Fix V (OPEN-SUITE-1).** V is a version of asupersync that (i) is published, (ii) corresponds to one clean,
   tagged commit of the asupersync repository, and (iii) every consumer in the table's first seven rows can build
   against. The expected answer is 0.6.2 if its published bytes equal a clean commit; otherwise the next version,
   published from a clean commit under asupersync's own release rules. Procedure: list the published versions;
   compare the registry bytes of 0.6.2 with the tracked bytes of asupersync at the commit FrankenSim's current
   commit builds against (the path checkout is dirty, so "0.6.2 by path" is not yet evidence of "0.6.2 as
   published"). If they agree, V = 0.6.2. If the path carries changes the suite needs, a new version is published
   from a clean asupersync head through that repository's own release gates, and V is that version. The decision
   and its evidence (the two digests compared, or the release commit) go into the closing record.
   If V is not 0.6.2, every other exact `=0.6.2` requirement in a surveyed sibling also blocks resolution
   (franken_numpy's optional one, behind a feature): before V is fixed, each such requirement is listed from the
   survey and from that sibling's manifests at its current commit (with the feature that activates it), and each
   is either moved to V in the same train (a further mirrored change in that repository, recorded in the closing
   record) or recorded as a feature that stays off in this project (DESIGN: V must not be chosen in a way that
   silently disables a consumer; FD-ASUP-01 verifies the choice with `cargo metadata` over this project's
   workspaces).
2. **The "before" evidence.** Before the first manifest edit in a consumer, `cargo tree -d --locked` is run in that
   consumer's workspace at its pre-change commit (frankensim, frankentorch, fastmcp_rust), in a scratch clone.
   The three listings are written to `tests/upstream/FD-ASUP-01/before.tree-d.txt`, one section per consumer
   headed `<repo>@<40-hex commit>`, and the file's BLAKE3 hash goes into the closing record. This is the "before"
   half of the evidence that INT-ASUP-01's "after" listing is compared with (FD-ASUP-01 records the hash in the
   fixture's `expected.toml`; the directory is the fixture directory BD-037 prescribes, and nothing else in it is
   written here).
3. **asupersync.** If no clean published commit exists for V: the release is cut there, under its rules, from a
   clean tree. This program does not publish from a tree that holds another agent's uncommitted work.
4. **frankensim.** Its constellation entry for asupersync is moved from 0.5.0 at `7a0f2f55047c` to V at V's commit,
   so that its own verify-only preflight (which treats an off-pin or dirty sibling as a refusal) agrees with what
   its `Cargo.lock` builds. Only the asupersync row is touched; the other stale rows are FD-FSIM-16. Its manifests
   name V as the version beside the path, and its `[patch.crates-io] asupersync` entry keeps pointing at the path
   for development. The test `constellation_asupersync_matches_cargo_lock` (below) is added with the change.
5. **frankentorch.** Its requirement becomes exactly V (today `0.6.2`, default features off); its lockfile is
   regenerated; its own suite passes.
6. **fastmcp_rust.** Its exact requirement becomes `=V` (today `=0.6.2`), or a caret requirement on V if that
   repository's rules allow one (an exact pin splits the graph again at the next release; see Considerations);
   lockfile regenerated; suite and MCP conformance checks pass. If FD-FMCP-01, which edits the same manifests for
   the toolchain, is in flight, the two changes are landed in one reservation.

**The closing record (DESIGN: the hand-over to FD-ASUP-01, which copies it into its own closing record for
BD-037).** V; V's commit and tag; the evidence for V (the two digests compared, or the release commit); the exact
requirements found in step 1, each with the commit that moved it to V or the feature recorded as staying off; for
each repository the pre-change commit and the landed commit; the four mirrored-bead identifiers, each beside its
repository and in the order of the row's `repo` (asupersync, frankensim, frankentorch, fastmcp_rust); the path and
BLAKE3 hash of `before.tree-d.txt`; the hash of the survey record it started from; and any difference between a
sibling's rules and this bead.

## Test plan

### Unit tests
In each sibling: its existing suite on the regenerated lockfile; no expectation edited. Added in FrankenSim
(additive):
- `constellation_asupersync_matches_cargo_lock`: the asupersync entry of `constellation.lock` equals the version and revision `Cargo.lock` resolves. Input today: 0.5.0 against 0.6.2; expected after the change: equal.
Here: none. This bead builds nothing in this repository's workspace; its checks are the script below, and the
tests at the pins here are FD-ASUP-01's.

### End-to-end script and logging
`scripts/e2e/upstream_fd_asup_01_siblings.sh` (plain shell, sources the shared helper of STD-E2E, no randomness,
idempotent, non-zero on failure). It works only in scratch clones under `target/upstream-scratch/`:
1. Re-runs the survey (`scripts/admission/suite_survey.sh`) and logs the record's hash and each surveyed
   sibling's asupersync requirement.
2. In a clone of asupersync at V's commit: asserts that V's tag points at that commit, that the tree is clean, and
   that the registry bytes of V and the tracked bytes there have equal digests (both logged).
3. In clones of frankensim, frankentorch and fastmcp_rust at their landed commits: `cargo tree -d --locked`,
   asserting no asupersync line; the manifests' requirement on asupersync, asserting V (`=V` or `^V` where an
   exact pin was replaced); in frankensim, `cargo test --locked constellation_asupersync_matches_cargo_lock`.
4. In a clone of frankensim at its pre-change commit: the same constellation check run as a read of the two files,
   asserting the disagreement (0.5.0 against 0.6.2 today). A check that sees no disagreement there is broken, and
   the script fails.
5. Recomputes the BLAKE3 hash of `tests/upstream/FD-ASUP-01/before.tree-d.txt` and asserts it equals the closing
   record's.

Logging per STD-E2E: NDJSON to `target/e2e-logs/upstream_fd_asup_01_siblings/<utc-timestamp>.ndjson` with a
human-readable transcript beside it. Every line has `ts`, `script`, `bead` (`NFp4-01`), `step`, `event` (`start`,
`cmd`, `assert`, `metric`, `refusal`, `end`), the exact command line, exit code and wall time; it also records each
repository and commit a step ran at, each digest compared and, on failure, the first differing value and the
paths needed to reproduce. No `frob` verb is called, so no envelope is logged. A final `summary` line gives
assertions passed and failed.

### Known answers and negative controls
- Known answer: in each consumer at its landed commit, `cargo tree -d` lists no asupersync line.
- Negative control 1: step 4 above (FrankenSim's pre-change commit must show the 0.5.0 against 0.6.2 disagreement).
- Negative control 2: a consumer manifest edited to `=V+1` in a scratch copy must make step 3's requirement check fail.
- Negative control 3: one tracked byte changed in a scratch copy of asupersync at V's commit must make step 2's digest comparison fail.
- Determinism: the survey record and the three listings are byte-identical on two runs over unchanged trees.

## Considerations

- An exact requirement (`=V`) in a consumer is brittle: the next asupersync release splits the graph again until every consumer moves. Each later move is one compatibility train (N33b-04).
- `franken-kernel` and `franken-evidence` live in the asupersync repository; FD-FKER-01 touches the same repository and should share a reservation window with this bead. FD-FMCP-01 edits the same fastmcp_rust manifests (step 6).
- A dirty asupersync checkout is acceptable for development builds between receipts and for nothing else (OPEN-SUITE-3); V is never chosen from one.
- The order of this bead and the first pins in `franken-stack.lock` is not fixed: if a consumer's first pin already contains its landed change, FD-ASUP-01 takes the fixture's failing signature from that consumer's pre-change commit recorded here.
- No milestone waits on this bead beyond FD-ASUP-01. If it cannot land within the M0 budget, the closing record says how far it got, FD-ASUP-01 records the consumer that still disagrees, and KILL-MCP's fallback is decided at the M0 exit review.
- The priority in the upstream register states the item's value to this project and its place in this program's queue. The risks carried at program level are the cost and ordering of upstream work and collisions with other agents in the same sibling; the mitigations are file reservation, small commits and the sibling's own gates.
