# COMPREHENSIVE PLAN FOR FRANKEN_ROBOTICS

> **FrankenRobotics** is a robot proving ground, a robot design studio for AI agents, and a mission-query engine,
> built as one mathematical instrument. It simulates legged, wheeled, tracked and hybrid robots in terrain and
> interior scenes with physics supplied by FrankenSim, runs thousands of worlds and hundreds of different robots at
> once on CUDA and Metal GPUs, and exposes a command line and an MCP server through which agents design a robot, test
> it, read what happened and improve it. It answers questions about families of designs and not only about single
> designs: which bodies can do this mission, which cannot and why, and which experiment would settle the rest. It
> searches for the worlds that break a design, shrinks each failure to a minimal counterexample world, and explains a
> failure by intervening on a replay of it. It carries a path from simulation to calibration against measured reality
> and to manufacturable output. Every layer is formulated in Lie theory and abstract algebra: configurations are group
> elements, joints are subgroups, contact is a cone program in the dual Lie algebra, symmetry is a finite group acting
> on the design, and the hot kernels are derived from that algebra instead of being typed in by hand. Repo
> `franken_robotics`; crate prefix `frob-`; binaries `frob` (CLI), `frobd` (job daemon), `frob-mcp` (MCP server),
> `frob-verify` (offline certificate auditor) and `frob-tui` (terminal dashboard).

## 0.1 Normative language, evidence labels and tiers

MUST, MUST NOT, SHOULD and MAY carry their RFC 2119 meanings. Five labels say what kind of statement a sentence is. A
number in this plan without one of these labels, or without an obvious label from its table header, is a defect in the
plan.

| Label | Meaning | Who may change it |
|---|---|---|
| **FACT** | Observed on 2026-11-21 in a sibling repo, on this machine, or in a cited public source. Code facts cite `repo/path`; web facts cite a URL in Appendix H. | New evidence only |
| **DESIGN** | A decision of this plan. It carries its reason. | An architecture decision record (ADR) |
| **HYPOTHESIS** | Believed, not established. It names the test that would confirm or kill it. | The named test |
| **TARGET** | A number we intend to hit. It is not a measurement until a gate records the measured value. | The gate that measures it |
| **OPEN** | Undecided. It has an owner, a deadline expressed as the gate it blocks, and a fail-closed default (§42). | The owner |

Three rules govern numbers that come from outside this repository.

1. **An external number is a FACT about its source, not about this system.** Every external figure is registered in
   Appendix H with its URL or path, the version or tag it was read at, how it was read (raw text, a rendered figure
   read by eye, or a derivation from published inputs), and the phrase "to be re-read from the primary source before a
   gate cites it". The phrase is not repeated in each sentence that uses the figure.
2. **A reported defect in a foundation is a FACT to recheck.** Where a review reported a defect in a sibling crate and
   this program has not reproduced it at a pinned commit, the statement is written "FACT (to recheck)", and it becomes
   an admission test and an upstream ask (§33, Appendix F) before anything depends on it.
3. **No number is written as a result.** Nothing in this plan was measured on FrankenRobotics. A ratio, a rate or a
   coverage figure that describes this system is a TARGET, or a HYPOTHESIS with the range the evidence supports.
   Headline multipliers do not appear.

Ambition is calibrated with the three tiers the suite already uses (FACT:
`frankensim/COMPREHENSIVE_PLAN_FOR_FRANKENSIM.md` §0). Every mechanism in this plan carries one.

- **[S] Solid**: established mathematics and engineering. The risk is implementation quality.
- **[F] Frontier**: published research that mainstream robot simulators have not productized, or a narrowed form of a
  mechanism whose strong form failed review (§0.8). Real engineering risk.
- **[M] Moonshot**: a synthesis proposed here. It lives behind a feature flag and never sits on the critical path.

The spine of this plan is [S]. The features that make it worth building are [F]. The [M] items are what would make it
unlike anything else, and the plan works without every one of them. Two obligations attach to the upper tiers (DESIGN;
the reason is in §0.7):

- Every [F] and [M] item names a **paper-scale pilot with a falsifier** that must run before its work package is
  funded, and states the **ceiling of its benefit** before any speed test is run.
- Every [F] and [M] item has a **kill gate with a fallback named in advance**. The fallback is a mechanism of a lower
  tier that the plan already contains, so that losing the item costs a capability and never the critical path.

Every mechanism, at any tier, states: what it is (types, data layout, algorithm); which crate owns it (§34); the verb
that exposes it (Appendix J); a known-answer or negative-control test (§38, Appendix M); and a gate with a numeric
threshold (§40). The word "verified" is not used for results anywhere in this plan or in the product's output. A
result is proved, certified, tested or estimated (§12), and it says which.

## 0.2 What "implemented" means

A capability is implemented only when all eight hold. Otherwise it MUST be described as partial, and the missing items
named.

1. Code exists in the crate this plan maps it to (§34).
2. The crate ships a `CONTRACT.md` with ten sections: purpose, inputs, outputs, invariants, refusals, determinism
   class, evidence class of outputs, validity domain, oracles, known gaps.
3. Known-answer tests pass against a pinned oracle that was never regenerated from the candidate (§38).
4. Outputs that cross the agent boundary carry the claim product of §8: the kind of claim, the evidence class set by
   the weakest input, a tier, a determinism class, a model identity, a seed, and the no-authorization flags. No naked
   numbers reach an agent (§29).
5. A CPU reference path exists. Where a GPU path is claimed, a retained differential check against the CPU path exists
   for the same kernels (§21).
6. The capability is reachable through `frob --json` with a documented schema and exit code, and, where the verb
   registry exposes it to agents, through `frob-mcp` (§32).
7. Cancellation is tested: request, drain, finalize, with no leaked device resources (§38).
8. Its gate has a recorded PASS carrying the measured values, not the targets, in a receipt that names the commit, the
   hardware fingerprint and the seed (§40).

Two riders apply to particular kinds of capability.

- **Family certificates.** A capability that emits a certificate about a family of designs or worlds (§25) is
  implemented only when the certificate travels in a `.frobcert` bundle and the independent offline auditor
  `frob-verify` accepts it on a machine with neither the agent nor a GPU, and rejects the registered mutations of it
  (§12).
- **Upper tiers.** An [F] or [M] capability is implemented only when its pilot and its kill-gate decision are on
  record (§0.7). A capability that fell back at its kill gate is described by the name of the fallback.

## 0.7 Plan hygiene rules

The first eight come from what the sibling plans recorded about their own mistakes. The rest come from the reviews,
audits and paper-scale pilots behind this version (§0.8).

- **The delivery log lives in `docs/delivery/`, never in this plan.** FrankenTextiles' §25 grew to 82% of its plan
  (FACT: Mining §0.7). This document states decisions; crate contracts and beads state progress.
- **A closed bead is not acceptance.** FrankenMining found 87 beads closed within 12 seconds with one shared close
  reason, serving figures from a stand-in (FACT: Mining App. K.2). Here a bead closes with a typed reason that cites
  its own test, and gates require a live-dependency proof (§38).
- **Process is never the product.** FrankenMining's `xtask` reached about 27% of its code (FACT: audit of
  `franken_mining`). `xtask` here has a hard scope: six checks, listed in §34. A new check needs a named defect class
  it would have caught. The same rule covers every registry, ledger and receipt this version adds: each exists because
  a named verb reads it or a named gate checks it, and one that nothing reads is deleted.
- **Line counts are scope caps, never schedules.** Per-crate figures in §34 are caps that trigger a scope conversation
  at 115%. FrankenTextiles set a ceiling and retired it at 1.9× (FACT: audit of `franken_textiles`).
- **Every number carries a label** (§0.1). Performance numbers also carry the disclosure block of §36, and any ratio
  against an incumbent carries the measurement protocol of §39.
- **The seven claims are never conflated** (§8), and each gate names exactly one of them.
- **Mathematics is written in Unicode, without LaTeX**, and every symbol is defined in §11 or Appendix D.
- **Sibling repos are read-only to this program.** Changes to them are requested as beads in their own trackers
  (Appendix F). An upstream change is never scheduled as a local bead, and no milestone depends on one without a
  fallback that needs no upstream change.
- **Every Frontier and Moonshot item needs a paper-scale pilot with a falsifier before it is funded.** A pilot is
  small enough to run on a CPU in a day, uses exact or hand-checkable arithmetic where it can, is registered before it
  runs, and has an outcome that is not known in advance. A pilot that cannot fail is not a pilot. Its result,
  including a negative one, is recorded in the review log (Appendix K) and its mechanism's tier and scope are revised
  to match.
- **The ceiling is computed before any speed test.** Before a speed comparison is locked, the ceiling implied by the
  work both arms share (authoring, checking, serialization, review) is computed, and the test is refused if the
  ceiling is below the claimed ratio. One pilot behind this version measured a specialized solver at 1.345× a composed
  one when shared overhead was 94% of the batch, so that no solver could have shown more than 1.46× (FACT, Appendix
  K): the test could not have confirmed the claim it was run to test.
- **A frozen decision rule is enumerated before sampling.** For every fixed-n rule the set of reachable verdicts at
  that n is listed first. One pilot rule with 64 pairs could return three of its four verdicts; the fourth was first
  reachable at 86 pairs (FACT, Appendix K).
- **Counterexamples are first-class.** Where a plausible shortcut is wrong, the plan gives the smallest hand-checkable
  case that breaks it, and the case enters the negative-control registry (§38) and the counterexample catalogue
  (Appendix N). A rule that ships without such a case has not been thought through.
- **Killed ideas stay on the page with the calculation that killed them** (Appendix C). A mechanism whose strong form
  was refuted is not built in that form, and its narrowed form is written with the claim that survived (§0.8).
- **Mechanisms are named plainly.** A label from a richer theory is used only when the mechanism uses that theory's
  theorems. A least-squares pose graph is a least-squares pose graph.
- **A gate needs only what a simulator has.** A gate that needs a physical board, a bench measurement, a building scan
  or a human review panel is written as an import lane with a recorded `no-claim` until the data exists (§30).
- **The incumbent is measured before a mechanism is funded against it.** Versions are pinned, the strongest warm
  configuration is recorded, and the phase ledger of the incumbent loop is taken on `trj` before any ratio is written
  (§39).

## 0.8 How evidence from the planning exercises binds the plan

Before this version was written, the load-bearing hypotheses of the program were put to refutation on paper: published
results were re-read at pinned versions, arithmetic was redone, sibling code was inspected, and a small number of
exact, CPU-scale pilots were run. No hypothesis was tested by running FrankenRobotics code. Each hypothesis received
one of four verdicts, and the verdict binds what this plan may say and build.

| State | Meaning | What the plan text may say | What is in scope |
|---|---|---|---|
| **ACTIVE** | Unrefuted and untested. Nothing narrows it yet. | The hypothesis, labelled HYPOTHESIS, with its test. No number as a result. | The test is scheduled early. Work that depends on the hypothesis is gated on it, and the plan states what it does if the test goes against it. |
| **NARROWED** | The strong form failed on evidence. A stated weaker claim survives. | Only the surviving claim, with the surviving numbers as HYPOTHESIS ranges. The strong form appears once, in Appendix C, with the refuting calculation. | The narrowed mechanism, at the tier its evidence supports, with a falsifier and a kill gate. |
| **REFUTED** | A calculation or an executed check shows the mechanism does not deliver what was claimed. | The strong form is not written as a goal, a bet or a target. What survives, often as hygiene, is named. | The strong form is not built. It may be reopened only by the reversal condition recorded with the verdict. |
| **DEFERRED** | Real, but not an answer to the question that was asked of it (here: time to a decision). | What it does deliver, under its own heading. It is not counted in the thesis of §2. | Built off the critical path, at [F] or [M], or not at all. |

The register follows. Numbers in the "what survives" column are ranges read from published work or computed from it
(sources in Appendix H). Each is a HYPOTHESIS about this system until the gate of the named section records a
measurement.

The register's answer to the question the program was asked is that no single mechanism delivers ten-fold. The thesis
that survives is a conjunction, and §2 states it. Three disagreements were left open by the evidence, and each has a
test that settles it:

- **Whether a sampling controller should be the default baseline.** The cost arithmetic says screening only. Settled
  by BET-06 and BET-27 on the design corpus (§22).
- **Whether kernel specialization pays.** It is refuted on an incumbent's step trace. Our own M2 profile decides (§21,
  §36).
- **Whether formal certificates change any design decision.** There is no evidence either way. Lemma records, for
  every certificate consumed by a decision, whether the decision would have differed without it (§12; BET-11, BET-20).

The same evidence binds three further things. Differentiators that the incumbent audit withdrew are not claimed
anywhere in this plan; §1.3 lists them. Numbers that the audit corrected replace the numbers of version 0.2 wherever
they appear; §2 and §36 carry the corrected figures. A verdict changes only on new evidence of the kind that produced
it: a pilot, a measurement at a gate, or a primary source re-read at a pinned version. The register is append-only,
and a changed verdict keeps its history.

### 1.4 What is already solved, and what nobody has composed

Each of the following exists and works (sources in Appendix H):

- Linear-time articulated-body dynamics in spatial algebra (Featherstone), and its Lie-group formulation (Park,
  Bobrow, Ploen).
- Convex, compliant contact that scales to thousands of GPU worlds (MuJoCo's formulation in MuJoCo Warp and Newton;
  Drake's SAP and its successors on the CPU).
- Lie-group and variational integrators with discrete conservation laws (Iserles et al.; Marsden and West; Lee, Leok,
  McClamroch).
- Invariant filtering for legged state estimation (Barrau and Bonnabel; Hartley et al.).
- Morphological symmetry groups and equivariant policies (Ordoñez-Apraez et al.), and the symmetry classification of
  gaits (Golubitsky, Stewart, Buono, Collins).
- Monotone co-design with guaranteed fixed points (Censi), grammar-based robot search, and trajectory optimization
  with design variables.
- Anytime-valid sequential inference, already implemented in FrankenSim (`fs-race`, `fs-eproc`), and published for
  robot policy comparison.
- Sampling-based predictive control of legged robots without offline training.
- One policy across a class of bodies, and policy sharing across design candidates.
- Certified collision-free regions of configuration space; support-region and wrench-cone feasibility as linear
  programs (Bretl and Lall; Orsolino et al.).
- Exact family answers on small plants by standard means. In the pilots behind this version, a lifted robust linear
  program, a projection, an SMT solver and quantifier elimination each returned the same complete family answer as a
  specialized method on every fixture tried (FACT, Appendix K).
- Adaptive stress testing and importance sampling for rare failures; delta debugging; conformal prediction; topology
  optimization.

What was not found is their composition: one design identity and one evidence ledger carried across static analysis,
simulation tiers, statistics, family queries, adversarial search, calibration and solid mechanics, in one typed
algebra, so that a statement proved or measured at one layer is usable at the next and is withdrawn when an edit
invalidates it. FrankenSim's thesis is that such a typed algebra collapses an archipelago of tools into a continuum
(FACT: FrankenSim plan §1). FrankenRobotics applies that thesis to robots and takes it one step further: the algebra
is not only the type system, it is the source code of the kernels.

That the composition is worth more than its parts is a HYPOTHESIS, and it is the central one. Partial precedents exist
(a co-design framework with a structural filter, a static sizing toolkit for arms, anytime-valid policy comparison).
Almost every mechanism in this plan can in principle be hosted by an incumbent engine with a layer on top (H-19,
ACTIVE). The only test of the composition is the end-to-end comparison against a composed incumbent baseline in §39,
and §4 (BET-14) says what the program does if that baseline ties.

### 1.5 What FrankenRobotics is

Six products that share one model, one evidence ledger and one verb registry.

1. **A proving ground (Arena, Cortex).** A vectorized, device-resident environment API over batched physics. It runs
   legged, wheeled, tracked and hybrid robots across generated terrain and generated or ingested interiors: homes,
   apartments, offices, warehouses, manufacturing plants, retail stores, commercial kitchens. Many different robots
   share one batch (Phylum). Missions are stated as requirements, and a result is qualified in a lane that the
   discovery process cannot read.
2. **A design studio for agents (Atelier, Tether).** A CLI and an MCP server with verbs to create and edit a robot
   design, analyze it without simulation, simulate it, compare it against another design with statistical honesty,
   read structured telemetry about why it behaved as it did, optimize it, and ask which earlier verdicts survive an
   edit.
3. **A mission-query engine (Augur).** Given a mission, a catalogue of parts, a controller class and a description of
   what the robot can observe and when, it returns the set of designs that can do the job: an inner set with
   witnesses, an outer set with exclusions, the unresolved cells between them, and the cheapest experiment that would
   shrink the gap. The body, a sensor and the building are all admissible answers.
4. **An adversary and a counterfactual debugger (Nemesis, Autopsy).** A search for the worlds that break a design,
   bounded by physical legality and by a witness that the design's own body could have coped; a reduction of each
   failure to a minimal counterexample world; valid bounds on rare failure rates; and an explanation of a failure
   obtained by intervening on forked replays, reported with the stability of the attribution.
5. **A path to reality and to the workshop (Ground, Foundry).** Calibration of the model against imported measurements
   with predictions frozen in advance, reality bands issued only inside a calibrated family, and build packets (parts,
   geometry, tolerances, fatigue margins) that carry machine-readable flags saying they authorize nothing.
6. **A mathematical instrument (Marrow, Lemma, Spark).** A Lie-algebraic formulation of design, simulation and control
   in which the mathematics is load-bearing: it generates kernels, supplies test oracles, prunes designs before
   simulation, and, where a checker can accept it, carries proofs and portable certificates that an offline auditor
   re-checks.

Five nouns recur and are defined in Appendix A. A **design** is a robot's intrinsic properties and connections. A
**world** is geometry, material fields, lighting, moving objects and their behaviour. A **task** is initial states,
observations, actions, goals, terminal events and metrics. A **mission** is a task family with requirements and the
quantifiers that relate designs, controllers and worlds. A **study** binds versions of these to controllers, random
streams, numerical settings, hardware profiles and one declared analysis rule.

## 2. The ten-fold thesis

The owner's ambition for this project is comparative: an order of magnitude better than every existing system at
getting from a robot-design question to an answer that can be trusted. This chapter states what that means as a
measurement, where the time in today's loops goes, which ceilings follow from that, which mechanisms the program bets
on, what will not deliver the result, and what range the evidence supports. The protocol is in §39. Nothing here is a
result.

### 2.1 The metric

**Time to an independently accepted answer.** DESIGN: the unit of success is an answer, not a step and not a score.
The reason is that every published bound on step speed, and every pilot behind this version, says the same thing: the
time between a question and a trusted answer is dominated by what happens around the step (§2.2).

- An **answer** is what the mission asks for. It is one of: a design and controller that pass a frozen acceptance
  battery; a family answer with inner and outer design sets and witnesses (§25); a correct withdrawal or confirmation
  of earlier verdicts after an amendment (§28); or a truthful `unknown` with the required witness, where the question
  is whether the evidence identifies the choice at all.
- **Independently accepted** means that a checker which is not the proposing system accepted it: an acceptance battery
  on worlds and in an evaluator that neither arm trained in, the offline auditor `frob-verify` for every submitted
  certificate, and a neutral adjudicator who releases receipts only after both arms close (§39).
- The **clock** T starts when the agent or engineer receives the mission and the permitted inputs. It stops when the
  checker accepts the first correct answer with all requested scope and precision. Unsuccessful runs, training,
  tuning, compilation, device transfer, waiting, investigation of unknowns, certificate checking, repair and review
  are all inside it.
- The **restricted mean time** at a common deadline H is RMT = E[min(T, H)], taken over the sealed missions of a
  stratum. A mission that is unresolved at H costs H.
- The **ratio** for a stratum is R = E[min(T_rival, H)] ÷ E[min(T_frob, H)], where the rival is the **strongest
  composed rival**: leading simulators, an optimizer, analytic bounds, a verifier and the same AI agent, assembled and
  tuned by a competent baseline engineer on development fixtures and then frozen (§39).

Four properties of the metric are fixed here because they shape the plan.

1. **Missed deadlines cap the ratio.** If the candidate misses a fraction q of deadlines, then R ≤ 1/q. With 12%
   unfinished the ratio cannot exceed 25/3 ≈ 8.33. Coverage is therefore a first-order design goal, and a refusal that
   arrives late is as costly as a failure.
2. **Correctness is a gate, not a term.** One false certificate disqualifies an arm from the scoped claim. A
   dangerously wrong accepted answer fails the mission. The time score is never improved by lowering the bar for what
   counts as accepted.
3. **Cold and warm runs are separate results.** A cold run includes authoring the environment and the design domain,
   for both arms. A warm campaign runs a declared sequence of amendments with identical reusable inputs and cache
   budgets, keeps failed amendments in the sequence, and reports the **crossover reuse count**: the number of
   amendments after which the candidate's one-time authoring has paid for itself. A fair rival also caches graphs,
   factors and compiled kernels.
4. **The clock is not the only column.** GPU-hours, CPU-hours, energy, agent tokens, human minutes and money are
   reported beside wall time under identical resource caps. Two derived units are reported for the design loop:
   designs decided per hour, and compute per established decision at a matched error rate.

The decision rule that turns measured ratios into the word "ten-fold", with its power analysis, its censoring rule and
its multiplicity control, is in §39. One finding binds it from here: a draft rule that required a point estimate of at
least 10 on every brief confirmed a true ratio of 10 in at most 18% of simulated campaigns (FACT, Appendix K). The
rule of §39 is therefore specified on a pooled ratio with at least ten paired campaigns per arm, and its power against
a true ratio of 10 is computed before the sealed suite is opened. A measured ratio is always reported with its
interval, whatever it is.

### 2.3 The ceilings

Each ceiling is arithmetic on the FACT rows above. Each is the reason one tempting strategy is not the plan.

1. **Engine speed alone.** At a fixed sample count, an infinitely fast environment step speeds training by at most
   1/(1 − s), where s is the step's share: about 7.8× for the rough-terrain humanoid, 6.7× for the hand and 1.9× for
   the cart-pole on one incumbent stack, and about 1.4× from physics alone on another. An incumbent already measures
   about 2.55 M humanoid world-steps/s. There is no order of magnitude left in the step, and a faster simulator alone
   cannot deliver ten-fold end to end.
2. **The design cycle alone.** A design-check-simulate-explain-edit cycle of 120 s with no training in it (NS-06) is
   3.0–3.5× faster than an incumbent quadruped cycle of 360–420 s, and about 15× faster than a 30-minute humanoid run.
   The comparison is valid only if a controller that needs no per-design training can stand in for a trained policy
   when designs are ranked. That is untested (BET-17).
3. **One design per agent turn.** With the same agent latency t in both arms and about 300 s of incumbent training,
   deciding one design per turn gives at most (300 + t)/t, which is 3.5–6× for t between 60 and 120 s, even if
   FrankenRobotics spent no compute at all. Against the one-card figure of 410 s the same cap is 4.4–7.8×. It is below
   ten either way.
4. **Compute per decision.** Let C be the incumbent's cost per trained candidate, c the cost of the cheap rung per
   design, c_T the cost of the training rung, and f the fraction of simulated designs that are trained. The compute
   ratio is C ÷ (c + c_T·f). With C = 410 GPU-s (one RTX 4090), an illustrative c of 38 GPU-s and c_T = 410 GPU-s
   (training at parity), the ceiling at f = 0 is about 10.8×, a ratio of ten needs f ≤ 0.7%, and no f reaches ten if
   the cheap rung costs more than 41 GPU-s. A cheaper cheap rung, many designs per rung, or a cheaper training rung is
   required; pruning alone is not enough.
5. **The general bound.** If a fraction f of the strong baseline's matched wall time is improved by a factor r and the
   method adds overhead h, the speedup is at most 1/(1 − f + f/r + h). Infinite acceleration of 85% of the time cannot
   reach ten. With f = 0.97, r = 40 and h = 0.02 the ceiling is about 13.5×. The three terms are measured on the
   rival's critical path, and a pruning ratio is never multiplied by a GPU speedup measured on work the pruning
   already removed.
6. **Unremovable cost.** If the cost that no mechanism removes (authoring the mission, checking certificates,
   serializing, reviewing) already exceeds one tenth of the strongest baseline's time, ten-fold requires changing
   another stage or changing the claim. In one pilot that cost was 94% of the batch.
7. **Completion.** R ≤ 1/q (§2.1). An arm that leaves one mission in eight unresolved cannot show ten-fold however
   fast it is on the rest.

Three smaller ceilings close other doors: per-design kernel specialization is capped near 1.2× on an incumbent's step
trace (H-04); exact reuse of rollouts after a mass or geometry edit is at most about 10% of compute (H-09); and
stopping rules give 2–5× when candidates are well separated and about 1× when they are not (H-10).

### 2.5 What will not deliver ten-fold

Stated plainly, so that no work package is funded on a hope the evidence has already closed.

- **A faster step.** Engine throughput is a parity requirement (§36). The plan must match incumbents closely enough
  that the levers above are not cancelled; it does not look for the result there.
- **Per-design kernel specialization.** Capped near 1.2×. It is an optimization for survivors, and only if our own
  profile shows the recursion share justifies it.
- **Half precision or tensor cores for contact.** Refuted (H-15). Not built.
- **Sampling control as the evaluator.** Even the most sample-efficient published controller costs about 4 × 10³ times
  a policy rollout per simulated second, so a battery of 256 twenty-second episodes takes about 86 minutes of a device
  against about 1.3 s for a policy. It is a fallback and a source of demonstrations (H-01).
- **One universal policy.** Out of reach at an affordable pretraining budget (H-02).
- **Static checks alone.** Pruning trivial failures caps near 1.19× on trainings. Their value is feedback in seconds
  and typed repairs, which is lever 1 and lever 7, not pruning.
- **Reusing rollouts across edits.** At most about 10% (H-09).
- **A faster solver for family queries.** In the pilot, a specialized solver measured 1.345× warm and 1.088× cold
  against a composed one, with a ceiling of 1.46× (FACT, Appendix K).
- **Certificates, full-room multiphysics and generative structure.** Certificates change what can be trusted, coupled
  multiphysics changes which failures are visible, and structure optimization improves the built object. None shortens
  the time to a decision (H-12, H-16), and none is counted in the thesis.
- **Any published ten-fold.** None was found for time to a qualified legged-robot design.

## 3. Twelve principles

Each principle is the short form of a section. The plan stands or falls with them.

1. **Algebra first, numbers last, and no ornamental mathematics.** State is stored as elements of Lie groups and
   advanced by maps that stay on the group. Every hot kernel is the image of an algebraic object under a derivation we
   can replay, with a content hash. A construction stays in the plan only if it owns a type, a verb an agent can call,
   a test that fails when the mathematics is wrong, and a measured payoff or a kill date (§9, §10, §13, §21).
2. **One model, three tiers, one ledger of disagreement; the CPU reference is permanent.** The referee tier, the CPU
   batch tier and the GPU tier run the same model, and their differences are measured and stored, never assumed away.
   GPUs propose and the referee disposes: a fast-tier result is provisional until it is promoted, and any world can be
   re-run alone on the CPU from its address (§16, §21, §29).
3. **Compose, don't enumerate; a body is data.** A robot is a composition of modules over typed ports, which is also
   FrankenSim's governing rule. Because a design lowers to tables and not to code, many different robots run in one
   batch, a new design recompiles nothing, and the unit of dispatch is a family (§14, §17).
4. **Consume the suite, never fork it, behind one airlock.** FrankenSim is taken by path dependency and pinned by
   commit; one crate names its volatile types. Sibling repositories are read-only, and what is missing is filed
   upstream as an ask with a failing fixture, never scheduled here. Fallbacks are named in order before they are
   needed (§33).
5. **Check before you simulate, simulate before you train, train before you claim; every design stands on day one.**
   Static analyses return in seconds with typed repairs. A baseline estimator and controller are synthesized from the
   model, so no design waits for a learned policy before it gets feedback. Each rung of the ladder is trusted only as
   far as its measured rank agreement with the rung above (§22, §23, §28).
6. **The unit of work is a decision over a family of designs, not a score for one design.** A mission names the design
   family, the worlds, what the controller may observe and when, and the quantifiers that relate them. The answer is
   an inner set, an outer set, witnesses, and the next experiment. The body, a sensor, the timing of a packet and the
   building are all design variables (§19, §20, §25).
7. **Counterexamples are an output.** The system searches for the world that breaks a design, shrinks it to the fewest
   edits that still break it, and ships it as a regression. Every rule in this plan travels with the smallest
   hand-checkable case that defeats a plausible shortcut, and every gate has a negative control it must catch (§26,
   §38, Appendix N).
8. **An edit invalidates evidence.** A hash identifies an artifact; only an implication licenses skipping a recheck.
   After any edit the system says which verdicts survive, which are withdrawn and what it would cost to restore them.
   One false reused verdict kills the reuse rule that produced it (§28, §29).
9. **Discovery cannot read confirmation worlds.** Search, tuning and training run in an open lane. Qualification runs
   on fresh sealed world clusters with pre-committed requests and an error budget that shrinks with each submission,
   so the error rate holds across an agent's adaptive retries. Anytime-valid studies and fixed-n studies are both
   offered and never mixed inside one study (§24).
10. **A proof is what a checker accepted; the weakest input wins and nothing is laundered into a proof.** Every result
    carries a claim product whose class is set by its weakest input, by construction of the type. A certificate about
    a family travels in a bundle that an offline auditor re-checks. The word "verified" is not used, and every
    exported artifact says in machine-readable form that it authorizes nothing (§8, §12).
11. **Refuse by name, never approximate in silence; `unknown` is an answer.** A request outside a validity domain gets
    a typed refusal with ranked repairs or a separating witness. A solver that fails leaves the verdict unknown; it
    does not become a failure of the design. Under load the system sheds presentation or refuses; it never lowers the
    physics tier of a running world (§35, §25).
12. **Engine speed is parity, not the thesis; a number is a target until a gate records it.** Throughput must match
    the incumbents and is not where the gain is sought. A recorded number names its world count, time step, substeps,
    solver iterations and contact count; a ratio against a rival names the rival's frozen configuration and every cost
    in the denominator; and a speed test is run only after its ceiling has been computed (§2, §36, §39).

## 4. Bets, each with its falsifier

A bet is a claim the project depends on and could lose. Each names what would falsify it, the competing arm it must
beat or the potency control that shows the test is able to fail, the fallback named in advance, and where it is
measured. Thresholds are TARGETs. Gates carried from version 0.2 are cited by identifier; for new bets the "tested at"
column names the owning section, and the gate identifier and threshold are in §40.

Two terms are used throughout. A **competing arm** is a rival method given the same information, the same budget and a
competent implementation; a bet that never meets one has not been tested. A **potency control** is a planted effect
that the test must detect, or a null on which it must stay silent; a test that passes without one may simply have no
power (§0.7). A falsified bet is reported as falsified, and its fallback ships under the fallback's own name.

BET-01 to BET-12 are carried from version 0.2 with their wording corrected by the incumbent audit. BET-13 onward are
new. BET-13, BET-14 and BET-17 are the three on which the thesis of §2 turns.

### 6.3 Anti-goals

Things that would make the product worse even if someone asked for them.

- Lowering physics fidelity silently to keep a frame rate or a throughput figure. Under load the system sheds
  presentation or refuses; it never changes the physics tier of a running world (FACT: the same rule in the Wright
  Flyer plan §4.3).
- Wrapping MuJoCo, PhysX or any foreign engine as the production engine. Foreign engines are development-time
  comparison oracles and the rival arm of the ten-fold test, run out of process (§38, §39). If the composed-incumbent
  arm ties, the layer ships over that engine openly, under BET-14, and not as a hidden dependency.
- Publishing a throughput number without the disclosure block (§36), or a ratio against an incumbent without the
  rival's frozen configuration and every cost in the denominator (§39).
- Accepting inertial parameters on faith. An imported model that is not physically consistent is refused or repaired
  with a recorded repair (§14).
- Putting a language model inside the physics or control loop.
- Hiding nondeterminism. A result whose determinism class is `Unspecified` is never cited as evidence, and paired
  statistics are refused under an uncontrolled class.
- Mathematical decoration, and ornamental labels on ordinary mechanisms. See D-2.
- Tuning against the confirmation benchmark, or letting discovery read confirmation worlds.
- Improving a time score by lowering the bar for what counts as accepted.
- Converting a tested or estimated result into a proof, by wording or by type. Using the word "verified" for a result.
- Silent clamping of a parameter, a command or a contact count. A clamp is a refusal or a recorded event.
- Multiplying a pruning ratio by a speedup measured on work the pruning already removed, or reporting an operation
  count as a speedup.
- Running a speed test whose ceiling is below the claim it is meant to test.
- Fast-math switches, fused multiply-add, built-in transcendentals or floating-point atomics in batched kernels.
- Scheduling a change to a sibling repository as a local bead.
- A gate that needs hardware, a bench or a review panel the program does not have. Such a gate is an import lane with
  a recorded no-claim.
- Composing two individually successful episodes and calling the result a composed guarantee.
- A learned correction between tiers, or a learned surrogate of the physics step, which would hide exactly the
  artifacts the trust ladder exists to expose.
- An exported artifact that could be mistaken for permission to run hardware.

## 7. North-Star scenarios

Each is a before-and-after acceptance story, tagged with the first milestone that can demonstrate it. In the "after"
parts, numbers are TARGETs or illustrative values unless the story says they are a known answer. Incumbent figures in
the "before" parts are FACTs from Appendix H. Verb spellings follow the registry (Appendix J); where a story names a
capability without a spelling, the registry is the authority. NS-01 to NS-12 are carried from version 0.2 with their
incumbent denominators corrected; NS-13 to NS-24 are new.

- **NS-01 Check before you simulate [M1].** *Before:* an agent edits XML, launches training, and learns minutes to
  about an hour later that the knees saturate (training takes about seven minutes for a flat-ground quadruped task and
  about an hour for a default rough-terrain humanoid run). *After:* `frob design check` returns in under two seconds:
  the mass spiral closes at 14.2 kg, peak knee torque demand exceeds the selected actuator's continuous rating by 31%,
  the design has mechanical symmetry group C₂ × C₂ of which its front-only depth camera preserves C₂, and three ranked
  repairs are offered as typed edits.
- **NS-02 Teleport a world [M2].** *Before:* world 1,337 of 4,096 produces NaNs on the GPU. Where an incumbent's
  deterministic mode is on, the same batch can be re-run on the same GPU; none documents a bitwise re-run of that one
  world on a CPU. *After:* `frob sim replay --world 1337 --tier batch-cpu` reproduces that world alone on the CPU from
  its address (seed, world, episode), stops at the first step whose digest differs from the GPU's or at the first
  refusal, and reports the contact that started it. Where the device reaches class D1 the digests agree to the end,
  and the report says which class applied.
- **NS-03 An honest A/B [M3].** *Before:* two designs are compared on mean reward over an arbitrary number of
  episodes. *After:* `frob eval compare A B --task warehouse-tote` runs both on common world addresses under a
  declared anytime-valid study, stops when the e-process crosses its threshold, and reports "B beats A on energy per
  metre, evidence 240 to 1, valid at any stopping time". It reports separately whether each design meets the mission's
  hard limits, because a paired win establishes neither.
- **NS-04 A kitchen with a wet floor [M3].** A humanoid crosses a generated commercial kitchen whose floor friction
  map includes a wet patch governed by the film-friction law. Telemetry reports slip distance per stance, the friction
  utilization margin, and the stills at the moment of the slip. The agent can ask which link a pixel belongs to.
- **NS-05 Symmetry for free [M4].** The studio reports the symmetry group of a hexapod and the subgroup that its
  sensors, payload and task preserve, lists the gaits that subgroup permits, and trains a policy equivariant under it
  that reaches the target return in at most 0.7× the steps of an unconstrained one.
- **NS-06 Thirty iterations in an hour, three hundred designs decided [M4].** An agent runs thirty
  design-check-simulate-explain-edit cycles on a wheel-leg hybrid in one hour on `trj`. Each cycle dispatches a family
  of at least ten variants in one batch, so at least three hundred designs are decided in the hour. Every design
  version is content-addressed, every comparison is a declared study, and `frob design bisect` finds the edit that
  broke stair climbing. The unit of the story is designs decided per hour: the cycle count alone is worth only
  3.0–3.5× against an incumbent quadruped loop (§2.3).
- **NS-07 An import that tells the truth [M1].** Importing a public humanoid description yields a loss report: which
  fields were dropped, which inertias fail the physical-consistency test, and which actuator limits were absent and
  filled from a card marked `ASSUMED`.
- **NS-08 Tracks on rubble [M4].** A tracked robot climbs stairs and crosses rubble; on soft soil the sinkage model is
  active and labelled Frontier in the evidence.
- **NS-09 The exploit is caught [M3].** A policy that scores well by exploiting contact compliance is re-evaluated on
  the referee tier; the score falls outside the promotion envelope and the result is labelled `provisional:
  tier-sensitive`. A design whose rank among finalists changes under another admissible contact law is labelled
  model-conditional and may not spend prototype budget.
- **NS-10 The same task on a Mac [M2].** The quadruped task trains on this Mac through Metal. Results agree with the
  CUDA run inside the declared determinism class, and the report says which class. The throughput is reported beside
  the one Metal-capable incumbent's on the same machine and beside one RTX 4090's.
- **NS-11 A kernel with a certificate [M5].** `frob prove kernel K-se3-cay-step` returns a certificate that the update
  stays on the group and conserves spatial momentum in free flight, checked by FrankenSymPy's proof kernel, with a
  Lean capsule re-checked by FrankenLean where the theorem's dependencies allow. The certificate says nothing about
  floating-point results, and its text says so.
- **NS-12 Your own kitchen [M5].** A walkthrough video becomes a private scene pack through the owner's existing
  reconstruction pipeline, and a candidate home robot is evaluated in it. Scale is labelled `ESTIMATED` unless
  anchored, surfaces the scan never saw are treated conservatively and listed as a re-scan request, and the scan never
  leaves the machine.
- **NS-13 A mission answered over a family [M1 on the CPU, M4 at scale].** *Before:* an agent evaluates candidate
  bodies one at a time and reports the best score. Nothing says whether an untried body would also work, or why a
  failed one cannot. *After:* the mission is a query with a free parameter. A robot carries 400 N on four point feet
  at (±a, ±b) with a = 1/3 m; its centre of mass may lie anywhere in a rectangle of half-dimensions 150 mm by 75 mm;
  each foot delivers a commanded normal force in [0, 160] N; the half-width b is free. `frob mission synthesize`
  returns I ⊆ F ⊆ O. Every b ≥ 3/14 m is in the inner set, with the corner allocation (160, 130, 110, 0) N as its
  witness. Every b < 3/14 m is excluded, with a dual vector as the impossibility witness: at b = 0.20 m one foot would
  have to carry 165 N. The answer says that the boundary has zero reserve on two constraints. `frob-verify` re-checks
  the bundle offline in exact rational arithmetic. When the mission is amended to a passive equal-spring suspension,
  `result.revalidate` withdraws the earlier inner set and says what must be re-solved: at b = ¼ m, which had been
  admitted with the allocation (155, 135, 105, 5) N, the springs deliver (175, 115, 85, 25) N against the 160 N
  rating. These numbers are a known answer (Appendix M), not targets.
- **NS-14 256 different robots in one batch [M2].** *Before:* a population of designs with different topologies is a
  sequence of rebuilds. On GPU engines a structural edit needs a host compile and a new graph capture, and one stack
  reports just-in-time compilation of one to three minutes. *After:* one dispatch steps 256 distinct designs (three
  leg counts, mixed link lengths and actuator cards, in size buckets) with 32 worlds each on one RTX 4090. No kernel
  is compiled. Each world reproduces the digest of its single-design run. The report carries the two numbers of N11
  against the incumbent's mixed batch and against the per-family-template control arm, and says which arm won.
- **NS-15 A minimal counterexample world of three edits [M3].** *Before:* domain randomization reports a failure tail
  of 0.4% and the agent reads logs to guess why. *After:* the Nemesis search (§26) finds a failing world inside the
  legality bounds, confirms with a witness that the candidate's own body and actuators could have completed the
  mission in it, and shrinks it to a `.fmcw` file of three edits against the nominal scene: a door sill raised by 9
  mm, a friction coefficient of 0.31 on one floor tile, and a depth packet delayed by 40 ms. Removing any one edit
  removes the failure. The world reproduces bit for bit and joins the regression battery.
- **NS-16 An autopsy that names the cause [M3].** *Before:* an agent given a failed episode orders the anomalies by
  time and guesses. *After:* Autopsy (§27) forks the snapshot taken before the fall under twelve typed interventions,
  singly and in pairs, on identical random streams. The placebo fork replays the failure bit for bit. The report says
  that lifting the knee torque limit prevents the fall in 94% of perturbed forks against a placebo flip rate of 3%, so
  it is a but-for cause, and that restoring nominal friction does so in 8%, so it is not. The gear-ratio intervention
  is re-run from the episode start, because winding temperature depends on the whole history. Attribution runs in
  double precision, and the first-ranked repair comes back as a typed edit. An episode whose placebo flip rate is high
  is labelled `chaotic: unattributable` and is given no cause.
- **NS-17 Qualification that survives 500 adaptive retries [M3].** *Before:* an agent submits fifty candidates against
  the same held-out scenes until one passes. Each comparison is valid alone and the campaign is not. *After:* `frob
  eval qualify` pre-commits the candidate, the baseline, the mission and the metrics. Submission i runs on fresh
  sealed world clusters at level α_i = α / [i·(i + 1)], a series that sums to α. The discovery lane cannot read those
  worlds, and only the decision and an aggregate receipt come back until the campaign closes. The gate behind the
  story drives the lane with 500 adaptive retries on worlds that carry no signal and requires a false-promotion rate
  of at most α, with power preserved on planted gains.
- **NS-18 A twelve-dollar ramp against a chassis redesign [M4].** *Before:* every repair an agent considers lives in
  the robot. *After:* a wheeled carrier fails kitchen doorway D. The clearance complex returns an impossibility cut
  that names the bottleneck, a 19 mm threshold. The retrofit catalogue (§19) reports that one 1:12 rubber threshold
  ramp, priced at USD 12, makes the mission solvable with the policy frozen, and that the alternative in the robot is
  a larger drive wheel that changes the gearbox and adds USD 140 in parts. Both enter the same budget, and the mission
  answer lists them as competing, testable decisions. Prices and dimensional norms come from a cited catalogue; where
  none is cited they are labelled `assumed`.
- **NS-19 A family policy walks an unseen design [M4].** *Before:* every new design waits for its own training run,
  about seven minutes for a quadruped and up to an hour for a humanoid. *After:* an agent lengthens the femur by 8%
  and widens the stance. The family policy of the quadruped class, conditioned on the design, walks it with no
  training. The report gives its return as 0.78 of the specialist reference for the class, the in-distribution check,
  and the rank-agreement status that says whether this rung may eliminate designs. When the design is shortlisted,
  inheritance from its parent reaches the target return in 12% of from-scratch steps. A six-legged variant falls
  outside the class, is flagged out-of-distribution, and is routed to the baseline controller.
- **NS-20 A build packet [M5].** *Before:* the loop ends with a scored design. *After:* from a qualified design and
  task, Foundry (§31) emits a `.fbuild` packet: a bill of materials against a pinned catalogue, faceted solid
  geometry, a tolerance stack that closes, fatigue margins computed from the simulated load histories, and one link
  re-optimized to be 18% lighter at equal margin. The packet's claim product is Estimated, because its material cards
  are, and every file in it carries the three no-authorization flags of §8, all false.
- **NS-21 A calibrated reality band [M5].** *Before:* every report says `reality: no-claim`. *After:* bench
  measurements of one quadruped on one floor are imported with their provenance. Predictions for the held-out episodes
  are frozen before the comparison. For that robot and task family, Ground reports a cost of transport of 0.62 with a
  band of [0.55, 0.71] at 90% nominal coverage from 20 calibration episodes, and states that coverage at this sample
  size varies by about six points. The same question about a design that was never built returns a refusal that names
  the missing calibrated family.
- **NS-22 The docking fixture [M1].** The first mission slice, on the CPU. A cart must reach position 1 at rest in
  three one-second ticks. Its acceleration is g·u with an unknown gain g ∈ {1, 2} and commands bounded by U. The only
  informative packet is the first velocity reading. *Before:* a simulator scores a given controller on sampled worlds
  and cannot say whether any controller exists. *After:* the mission query returns four facts, each with a
  certificate. With the packet on time and U = ¾, a first command of ¼ identifies the gain and both worlds dock
  exactly. Docking tolerates a sensor error ε exactly when ε < (U + ½)/4, so choosing the probe and the feedback
  together raises the tolerable error from 1/8 to 5/16 on the same actuator. With the packet late, no causal
  controller docks in both worlds. When a third gain 33/32 is admitted it aliases with gain 1 at an error radius of
  1/64, exact docking becomes impossible, and every label that was feasible reverses. These are known answers
  (Appendix M).
- **NS-23 An energy-budget safety claim [M4].** *Before:* a safety statement about a humanoid stepping off a kerb
  depends on a contact model that nobody trusts at impact. *After:* the claim is stated as an `.fenergy` budget: the
  kinetic and potential energy that can arrive at the ankle on a 12 cm step-down is below what the joint and its bump
  stop are rated to absorb, with every term taken from the energy ledger. No contact law enters the claim. A runtime
  shield enforces the budget as a filter on commands, at a measured cost and with a statistically measured margin. The
  claim product is Tested, and the type offers no conversion to Proved.
- **NS-24 The sealed ten-fold tournament [M7].** Missions in named strata are sealed, and some worlds come from an
  evaluator independent of both arms. The rival is the strongest composed incumbent workflow, improved by a competent
  baseline engineer on development fixtures and then frozen. Both arms get the same agent model, token budget,
  hardware envelope and prior information, in fresh contexts. A neutral adjudicator releases paired receipts after
  both arms close. The report gives, per stratum, the ratio of restricted mean times with its interval, cold and warm
  separately, the crossover reuse count, and a phase ledger for each arm that sums to wall-clock. Every submitted
  certificate is replayed by `frob-verify`, and one false certificate disqualifies that arm from the scoped claim.
  Where the composed-incumbent arm ties, the report says so and the layer ships for that stratum.

## 8. The seven claims and the claim product

Every result this system produces makes exactly one kind of claim, and each kind is established by a different kind of
evidence. Gates, reports and documentation keep them apart. Version 0.2 had six claims; this version adds **Design
comparison**, because "this design is better" and "this design meets the mission" are what the studio most often says,
and neither is a fidelity statement or a known answer.

### 8.1 The seven claims

| Claim | Meaning | Evidence that establishes it | What it does not establish |
|---|---|---|---|
| **Proof** | A stated proposition holds in the declared model. | A checker accepted it: a Lean kernel for a general theorem (class Proved); or, for an instance-level statement, FrankenSymPy's proof kernel, an interval or exact-rational certificate, or the offline auditor `frob-verify` on a family certificate bundle (class Certified) (§12). | Anything about floating-point results; the model's agreement with the world; any quantifier order other than the one stated. |
| **Known answer** | The implementation recovers an analytic or synthetic truth. | A known-answer test with a derivation on file (§38, Appendix M). | Correctness away from the tested cases. |
| **Parity** | The implementation reproduces a reference tool or a published number. | A fixture captured from a pinned oracle that was never regenerated from the candidate, or a comparison with a published figure under stated conditions (§38). | That either side is right. Two programs that share a solver have correlated error. Agreement with a published real-robot figure is still Parity. |
| **Fidelity** | A faster tier agrees with a slower, more trusted tier. | The fidelity ledger: per-quantity disagreement distributions on the standard battery, and agreement of the task decisions the two tiers lead to (§16, §35). | That the trusted tier is right. Anything outside the battery. |
| **Design comparison** | One design is better than another, or a design meets a mission, on a stated family of worlds. | A declared study, anytime-valid or fixed-n exact, on common world addresses; for a qualified result, the blinded qualification lane (§24, §28). | That either design meets a hard limit when the verdict is a paired one; anything outside the stated world family; anything about reality. |
| **Reality** | The simulation agrees with physical measurement. | Imported real-robot measurements with their own provenance, predictions frozen before comparison, and a reality band for a calibrated family (§30). Everywhere else this claim is `no-claim`, and reports say so. | Anything about a design that was never built or a family that was never calibrated. |
| **Performance** | A speed or scale figure on named hardware. | A recorded run with the disclosure block (§36); for a ratio against a rival, the protocol of §39. | Anything about another workload, world count or machine. |

Three clarifications fix the edges (DESIGN).

- **A claim has a kind and a class.** The kind is one of the seven. The class is one of the four evidence classes of
  §12, ordered Proved, Certified, Tested, Estimated from strongest to weakest. Only a Proof claim can be Proved or
  Certified. The other six are Tested or Estimated however much evidence they rest on: no amount of testing becomes a
  proof.
- **A family certificate is a Proof claim of class Certified.** It says that, in the declared model and under the
  declared assumptions, every design in an inner cell satisfies the mission, or none in an excluded cell does. The
  assumptions are inputs (rule 6 below).
- **A comparison of methods is a Design comparison.** The "method" gates of version 0.2, which test whether a method
  of this plan beats a competing arm on a corpus of designs, name this claim. The unit compared changes; the evidence
  required does not.

Each claim has a permitted wording, and reports use no other.

| Claim | Permitted wording in a report |
|---|---|
| Proof | "proved: ⟨statement⟩; checker ⟨name and build⟩; certificate ⟨hash⟩" or "certified: ⟨statement⟩; auditor `frob-verify` ⟨build⟩; bundle ⟨hash⟩" |
| Known answer | "recovers ⟨KA identifier⟩ within ⟨tolerance⟩" |
| Parity | "matches ⟨oracle⟩ at ⟨pin⟩ within ⟨tolerance⟩ on ⟨fixture⟩" |
| Fidelity | "tracks ⟨higher tier⟩ within ⟨envelope⟩ on ⟨battery⟩; decisions agree on ⟨share⟩" |
| Design comparison | "⟨B⟩ beats ⟨A⟩ on ⟨metric⟩, evidence ⟨e-value or exact interval⟩, study ⟨identifier⟩" or "qualified at level α_i on sealed clusters ⟨identifier⟩" |
| Reality | "inside the calibrated band for ⟨family⟩, nominal coverage ⟨level⟩ at n = ⟨count⟩" or "reality: no-claim" |
| Performance | "measured ⟨figure⟩ on ⟨hardware⟩; disclosure block ⟨identifier⟩" |

### 8.2 The claim product

In version 0.2 the rule "a result inherits the weakest claim among its inputs" was prose. Here it is a type (DESIGN).
The reason is that an optimizing agent will find any path by which a statistical result can be reported as a proof,
and a rule that lives in a style guide is such a path. `frob-core` owns the type; every verb's output envelope carries
one (§32); `frob-verify` reads one from every bundle (§12).

```rust
// DESIGN sketch: fixes intent, not signatures. Owned by frob-core.

/// The four evidence classes of §12. Combination takes the minimum.
pub enum EvidenceClass { Estimated, Tested, Certified, Proved }   // Ord: Estimated < Tested < Certified < Proved

/// Exactly one of the seven claims.
pub enum ClaimKind { Proof, KnownAnswer, Parity, Fidelity, DesignComparison, Reality, Performance }

/// What a result asserts, how strongly, about what, and that it authorizes nothing.
pub struct ClaimProduct {
    kind: ClaimKind,
    class: EvidenceClass,           // minimum over inputs; no setter
    weakest: InputRef,              // the input that set the class: content hash and field path
    scope: Scope,                   // design family, world family, quantifier order, horizon, validity region
    tier: Tier,                     // lowest physics tier among the inputs
    determinism: DetClass,          // weakest of D0..D4 among the inputs
    reality: RealityScope,          // NoClaim, or the calibrated family a band was issued for
    conditions: FlagSet,            // union over inputs: tier-sensitive, controller-sensitive, model-conditional
    inputs: Vec<InputRef>,          // every consumed artifact, each with its own claim product
    authorization: NoAuthorization, // three constants, all false
}

impl ClaimProduct {
    /// The only way to build a product from parts. Class, tier and determinism take the weakest; scope takes
    /// the intersection; conditions take the union; a mismatch of quantifier order is a refusal.
    pub fn combine(kind: ClaimKind, parts: &[ClaimProduct]) -> Result<ClaimProduct, Refusal>;
}

/// `False` is a unit type that serializes as the JSON literal false. No constructor produces `true`.
pub struct NoAuthorization {
    pub execution_authorized: False,
    pub hardware_safety_signoff: False,
    pub sim_to_real_certified: False,
}

// Three things do not exist, and a compile-fail test pins each: a conversion from ClaimProduct into a
// Proved value; a setter for `class`; a public constructor that takes a class as an argument.
```

A leaf product is created only by the component that produced the evidence: a checker creates Proved or Certified, the
Gauntlet harness and the study runner create Tested, and everything else creates Estimated. An actuator, interface or
material card creates one product per field from that field's provenance, so that a single assumed number is visible
as the weakest input of everything built on it.

A worked case. A comparison of two designs consumes: a kernel whose group-membership identity is Certified; a friction
coefficient from an interface card field marked `assumed`, which is Estimated; and a paired anytime-valid study on the
GPU tier under determinism class D2, which is Tested. The product is a Design comparison of class Estimated, its
weakest input is the friction field of the card, its tier is the GPU tier and so it is provisional until promoted
(§16), and its reality scope is `no-claim`. The report prints all of that in one line and offers, as its first next
action, the measurement that would raise the weakest input.

### 8.3 Rules

1. **A gate names exactly one claim.**
2. **A failure is a failed cell, never an excluded cell.** Partial coverage never rounds up, and every failed episode
   occupies a row.
3. **Parity is not Reality.** Agreeing with another simulator establishes that two programs agree. A comparison with a
   published real-robot figure, made before any calibration data is imported, is labelled Parity.
4. **Fidelity is directional.** It says the fast tier tracks the referee on a battery, not that either is right.
5. **The weakest input wins, by construction.** A proved kernel fed an assumed friction coefficient produces an
   estimate, and the type leaves no other outcome.
6. **Assumptions are inputs.** A certificate over a model with an assumed friction interval is Certified as a
   statement about that model. Any statement about the robot inherits the class of the assumption. A bundle lists its
   assumptions as inputs with their own claim products, and `frob-verify` refuses a bundle whose assumptions are
   missing.
7. **A comparison is relative.** A paired verdict that B beats A is emitted together with each design's own verdict on
   the mission's hard limits. A relative win with no regression does not establish that either design meets the
   mission.
8. **Quantifiers are part of the claim.** "For every world, some controller works" and "one controller works for every
   world" are different claims with different evidence. Evidence for the easier order is rejected, and the auditor
   rejects an unknown proof kind or a changed quantifier even when every hash is consistent. The smallest case that
   separates the two orders is in Appendix N: a plant in which every build has a command that works and no single
   command works for all builds.
9. **`unknown` is a verdict.** A solver failure, a timeout or a refusal leaves a verdict unknown. It is never recorded
   as a failure of the design and never as a success. Where contact is set-valued, a fork with any failing admissible
   branch invalidates a universal success claim.
10. **A claim does not outlive its inputs.** After an edit, a claim is carried forward only if revalidation shows that
    each input is unchanged or is implied by what changed (§28). A hash identifies an artifact; only an implication
    licenses reuse.
11. **Conditions travel.** Flags such as `tier-sensitive`, `controller-sensitive` and `model-conditional` are joined
    by union and cannot be dropped by a consumer. A model-conditional result may not spend prototype budget.
12. **Composition needs inclusion.** Two claims compose into a claim about a sequence only when the guaranteed end set
    of the first lies inside the entry set of the second, with matching clocks, uncertainty dependencies and state
    memory. Two individually successful episodes prove no such inclusion.
13. **Nothing authorizes.** Every exported artifact carries `execution_authorized: false`, `hardware_safety_signoff:
    false` and `sim_to_real_certified: false`. No verb, flag or configuration produces any other value.
14. **The word "verified" is not used.** Reports, documentation and tool output use the permitted wordings of §8.1.
